0.1 Why C++, and what it is actually for

C++ is C plus a set of mechanisms for expressing constraints that C cannot express at all — ownership, lifetimes, types, and invariants — and this guide is about those mechanisms and about the two decades of design decisions that produced them.

What the language added, and why each addition is not optional

C++ began as "C with classes" and became a language where you can write a container, an operating system kernel, a browser engine, or a game, with no runtime dependency beyond the standard library. That range exists because every major addition is a way of moving a class of mistake from run time to compile time, and each mechanism is the answer to a specific question C could not answer. Then the five things that follow, and each is a mechanism with a cost. References and move semantics exist because C's only parameter-passing mode is copying, which is correct and cheap for small objects and catastrophic for a large one — a move moves the resource instead of duplicating it, and it changes what a function may do to its argument. Templates exist because C's only abstraction is the void *, which erases the type and therefore cannot check anything — a template is a code generator, so the container's operations are checked against the element type at every use. RAII exists because C's resources are not tied to scope, so a leak is an ordinary outcome rather than an error — an object with a destructor releases whatever it holds when it goes out of scope, which converts a whole class of leak into a whole class of nothing-at-all. Exceptions exist because C's error convention is a return value, which is cheap and easy to ignore — an exception unwinds and guarantees the intermediate destructors run. And constexpr and concepts exist because "the compiler can work it out" and "this template is valid for this type" are both things a language should be able to say out loud, which C++ now can. Then the three things that go wrong, and each is a mechanism. Treating C++ as C with extra syntax, which produces a program that uses new and raw pointers and therefore has every problem C has plus more. Ignoring the cost model, which changes completely with the standard: copying is deep, moving is shallow, and a vector's reallocation moves every element unless you say otherwise. And Reaching for a template before knowing what the abstraction is, which produces four hundred lines of machinery expressing a concept that a struct of two integers would have expressed. Then the two practices, and both are disciplines. Use the standard library's containers and algorithms before writing your own, because they are better than yours will be on the first attempt and the second attempt is usually never. And Learn the four guarantees of every container operation, — what it costs, what it invalidates, whether it throws, and whether it allocates — because that is what distinguishes a choice of container from a guess.

/* Every major addition to C is a way of moving a class of mistake
   from RUN TIME to COMPILE TIME. Knowing which mistake is what makes
   the mechanisms make sense rather than being features to memorise. */

/* 1. MOVE SEMANTICS. C's only parameter-passing mode is COPYING. */
struct row {
    std::vector<double> cells;    /* 8 KB, heap-allocated         */
};
void by_value(row r);            /* copies: 8 KB + a heap alloc  */
void by_ref(row& r);             /* binds: nothing allocated      */
void by_const_ref(const row& r); /* binds, cannot modify         */
void by_move(row&& r);           /* STEALS the buffer             */

/* 2. TEMPLATES. C's only abstraction is void*, which erases the type
   and therefore cannot check anything. A template is a code
   generator, so every operation is checked against the element type
   at every use. */
static_assert(std::is_same_v<std::vector<int>::value_type, int>,
              "the container knows its element type");

/* 3. RAII. C's resources are not tied to scope, so a leak is an
   ORDINARY outcome rather than an error. An object with a
   destructor releases whatever it holds when it leaves scope. */
struct file_guard {
    std::FILE *f = nullptr;
    explicit file_guard(const char *p) : f(std::fopen(p, "rb")) {}
    ~file_guard() { if (f) std::fclose(f); }
    file_guard(const file_guard&) = delete;          /* no double  */
    file_guard& operator=(const file_guard&) = delete; /* close     */
    file_guard(file_guard&& o) noexcept : f(o.f) { o.f = nullptr; }
};

/* 4. EXCEPTIONS. C's error convention is a return value, which is
   cheap and easy to ignore. An exception unwinds AND GUARANTEES the
   intermediate destructors run. */
static int checked_div(int a, int b) {
    if (b == 0) throw std::invalid_argument("division by zero");
    return a / b;
}   /* Note what this bought: every object created between the throw
     site and the catch is destroyed on the way out. There is no
     equivalent in C, which is why every C error path is a leak
     waiting for the next person to add an early return.          */

/* 5. constexpr AND CONCEPTS. "The compiler can work it out" and
     "this template is valid for this type" are both things a
     language should be able to say OUT LOUD. */
template<typename T>
concept Summable = requires(T a, T b) { a + b; };

template<Summable T>
constexpr T twice(T v) { return v + v; }

static_assert(twice(21) == 42);   /* evaluated at COMPILE time */

/* THE THREE FAILURES.
   1. TREATING C++ AS C WITH EXTRA SYNTAX - which produces a program
      that uses new and raw pointers and therefore has every problem
      C has, plus more.
   2. IGNORING THE COST MODEL - which changed completely with the
      standard. Copying is deep, moving is shallow, and a vector's
      reallocation moves every element unless you say otherwise.
   3. REACHING FOR A TEMPLATE BEFORE KNOWING THE ABSTRACTION - which
      produces four hundred lines of machinery expressing a concept
      a struct of two integers would have expressed.             */

/* Two disciplines. USE THE STANDARD LIBRARY before writing your
   own: the containers and algorithms are better than yours will be
   on the first attempt, and the second attempt is usually never.
   And LEARN THE FOUR GUARANTEES of every container operation - what
   it costs, what it invalidates, whether it throws, and whether it
   allocates - because that is what distinguishes a choice of
   container from a guess. */

/* The same leak, written in the two styles, and what the difference
   costs. This is the whole argument for the language in one frame. */
#include <memory>
#include <cstdio>

/* BEFORE: manual ownership. The early return is correct; the FOURTH
   early return someone adds next year is the bug, and nothing about
   the shape makes it visible. */
static char *dup_manual(const char *s)
{
    char *p = new char[64];
    for (size_t i = 0; i < 64 && s[i]; ++i) p[i] = s[i];
    if (something_fails()) { delete[] p; return nullptr; }   /* remembered */
    if (another_check())  { delete[] p; return nullptr; }   /* remembered */
    return p;
}

/* AFTER: the type owns the memory, so the cleanup is a property of
   the type rather than of a code path. Adding a fifth exit does not
   add a fifth delete. */
static std::unique_ptr<char[]> dup_raii(const char *s)
{
    auto p = std::make_unique<char[]>(64);
    for (size_t i = 0; i < 64 && s[i]; ++i) p[i] = s[i];
    if (something_fails()) return nullptr;    /* nothing to do  */
    if (another_check())  return nullptr;    /* nothing to do  */
    return p;
}

/* AND: the caller now cannot do the two things that make manual
   memory hard. The delete is a compile error, and the copy is a
   compile error. */
static void use(std::unique_ptr<char[]> p) { p[0] = 'x'; }

int main()
{
    auto q = dup_raii("hello");
    use(std::move(q));       /* ownership transferred explicitly */
    /* auto bad = q;         copy: DELETED                      */
    /* delete[] q.get();     manual delete: DELETED            */
}

0.2 The toolchain, and what the standard level controls

A C++ build is a compiler, a linker, a build system and a standard level, and the standard level is the one that decides whether your code is C++20 or C++98 with extensions.

The pipeline and the four flags that matter

C++ compilation is the same six stages as C's — preprocessor, compiler, assembler, archiver, linker, build system — with two differences that matter. Template instantiation happens in the compiler, so a template that is only used in one place costs nothing anywhere else, and a header-only library's cost is paid per translation unit that includes it. And the linker can be very slow, because it must resolve every instantiation across every object. Then the four flags, and each is a requirement. Pin the standard level, because a feature that compiles today and not under the next default is a build that works for you and not for the person who builds it. Treat the warning level as an error, because the warnings a C++ compiler emits are almost entirely about the mistakes that survive review — an unused result, a shadowed name, a narrowing conversion. Build with exceptions enabled deliberately, because a release build that silently disables them is a program whose error handling compiles away. And Turn on sanitizers in a dedicated configuration, because memory and undefined-behaviour defects are cheap to find and impossible to find by review. Then the three things that go wrong, and each is a mechanism. Not pinning the standard level, which produces a build that depends on the compiler's default and therefore on the compiler's version. Turning off exceptions or RTTI in the release configuration without a reason, which makes a code path that was tested unreachable in the artifact that ships. And A slow link nobody diagnosed, which is almost always header bloat or a large translation unit, and which is worth fixing because a two-minute link is a two-minute tax on every change. Then the two practices, and each is a discipline. Have three build configurations and run all three in continuous integration, — sanitised debug, optimised debug, and release — because each finds a different class of defect. And Measure the link time and treat a regression as a defect, because it is the tax you pay on every single edit for the rest of the project's life.

      includes it.
   2. THE LINKER CAN BE VERY SLOW, because it resolves every

   1. NOT PINNING THE STANDARD LEVEL, which makes the build depend on

   2. TURNING OFF exceptions OR RTTI in the release configuration

   because each finds a different class of defect and none of them
   finds the others'. */
#if defined(SANITIZE)
#  pragma GCC diagnostic ignored "-Wmaybe-uninitialized"
   /* address + undefined: catches the use-after-free, the buffer
      overrun, and the signed overflow that a review cannot see */
#elif defined(OPTIMISE)

      when a check the compiler removed would have fired */
#else

#endif

     structured bindings                     C++17

   the standard is how you end up with a codebase nobody else can

   constraint a compiler enforces, not a feature you might want. */

#include <compare>      // C++20: three-way comparison
#include <span>         // C++20: a view over contiguous data
#include <ranges>       // C++20: ranges + lazy views
#include <concepts>     // C++20: constrained templates
#include <coroutine>    // C++20: coroutines
#include <format>       // C++20: type-safe formatting

#include <string_view>  // C++17: non-owning text
#include <optional>     // C++17: a value or nothing
#include <variant>      // C++17: a type-safe union

#include <filesystem>   // C++17: paths, portable, UTF-8 aware
#include <memory_resource>   // C++17: allocator injection

/* C++17: string_view is the change that removes a whole class of
   allocation. It is a POINTER AND A LENGTH, not an owning string -
   which is the same discipline the C guide reached by hand. */
static std::size_t count_words(std::string_view text)
{
    std::size_t words = 0;
    bool in_word = false;
    for (char c : text) {
        if (c == ' ' || c == '\n' || c == '\t') in_word = false;
        else if (!in_word) { in_word = true; ++words; }
    }
    return words;
}

/* C++20: a span is a pointer and a length with NO lifetime attached,
   so it accepts an array, a vector or a C array without an
   allocation or a copy. */
static int total(std::span<const int> xs)
{
    int sum = 0;
    for (int x : xs) sum += x;
    return sum;
}

/* C++20: the comparison operator, and it is not decoration. It
   generates the == from <=, so a <= change cannot leave == stale -
   which is the bug that lives in every hand-written operator pair. */
struct Version {
    int major, minor, patch;
    auto operator<=>(const Version &) const = default;   /* ALL THREE */
};

static_assert(Version{1,2,3} < Version{1,3,0});
static_assert(Version{1,2,3} == Version{1,2,3});

0.3 What to know before you start

You need C, or at least C's memory model, and you need to be willing to unlearn two habits from other languages.

The two habits that have to go

C++ is not garbage-collected, so a value has a lifetime and a destructor runs when it ends — which means "the object is gone" is a statement about scope, not about the last reference. And a value type is copied, not referenced, so passing a large object by value is a real cost rather than a shorthand, and returning one is a real cost rather than a pointer. Then the three things worth knowing before chapter one, and each is a requirement. Know what a dangling reference is before you know what a lambda is, because almost every C++ bug a beginner writes is a reference that outlived its referent, and the mechanism is identical in a lambda capture, an iterator and a pointer. Know the difference between the stack and the heap is not the question — know what decides it, and the answer is the lifetime, which is a property of the scope rather than of the storage the compiler picked. And Treat the value categories as a vocabulary, not as an optimisation, because lvalue, prvalue and xvalue are three kinds of expression and every copy-elision rule, every overload-resolution tie-break and every dangling bug is expressed in those terms. Then the three things that go wrong, and each is a mechanism. Learning templates before value categories, which makes forwarding references and perfect forwarding unreadable because they are the one place the distinction is load-bearing. Treating auto as "figure out the type for me", which is a proxy for deduction in a return position and a real hazard in a auto variable — a auto variable strips references and const, which is the mechanism behind an auto loop variable over a container of derived objects silently slicing them. And Assuming shared pointers are cheap, which is not what they are for; they are for shared ownership, and a program where a shared pointer is on a hot path is a program with a hidden contention point. Then the two practices, and both are disciplines. Compile every sample with warnings as errors, because the language is designed to tell you about the mistakes that matter and it only does so once. And Write one small program per mechanism before using it in a large one, because a lifetime bug in twenty lines is a stack trace and in twenty thousand is a wrong answer.

/* THE TWO HABITS THAT HAVE TO GO.

   1. C++ IS NOT GARbage-collected. A value has a LIFETIME and a
      destructor runs when it ends. "The object is gone" is a
      statement about SCOPE, not about the last reference.
   2. A VALUE TYPE IS COPIED, NOT REFERENCED. Passing a large object
      by value is a REAL COST, not a shorthand, and returning one is
      a real cost rather than a pointer.                        */

/* THE VALUE CATEGORIES, as a vocabulary. lvalue, prvalue and
   xvalue are three kinds of EXPRESSION, and every copy-elision
   rule, every overload-resolution tie-break and every dangling bug
   is expressed in those terms. */

static int  by_ref(const std::vector<int>& v);   /* no copy       */
static void take(std::string&& s);               /* binds and steals */

/* THE AUTO HAZARD. An auto VARIABLE strips references and const -
   which is the mechanism behind auto silently SLICING derived
   objects in a range-for. */
struct shape {
    virtual double area() const { return 0; }
    virtual ~shape() = default;
};
struct circle : shape { double r;
    explicit circle(double rr) : r(rr) {}
    double area() const override { return 3.14159 * r * r; } };

static void slice_demo() {
    std::vector<circle> v{ circle(2.0), circle(3.0) };

    for (auto s : v)          /* auto DEDUCES shape: SLICED       */
        (void)s.area();       /* calls shape::area -> 0.0         */

    for (const auto& s : v)   /* the reference is right           */
        (void)s.area();       /* calls circle::area              */

    for (auto* p : v)         /* pointer: no slice                */
        (void)p->area();

    /* auto in a RETURN POSITION is only deduction - it follows the
       return type - and never strips anything. The two uses of the
       keyword are unrelated and confusing people constantly.      */
}   /* Two disciplines. COMPILE EVERY SAMPLE WITH WARNINGS AS
     ERRORS, because the language is designed to tell you about the
     mistakes that matter and does so only once. And WRITE ONE SMALL
     PROGRAM PER MECHANISM before using it in a large one: a
     lifetime bug in twenty lines is a stack trace, and in twenty
     thousand it is a wrong answer nobody can reproduce.          */

/* Five things to recognise on day one. Each one is a line of C or
   Java that means something else here. */

#include <string>
#include <vector>
#include <memory>
#include <optional>

/* 1. A VECTOR IS NOT A POINTER and knows its own length. The C
   habit of carrying a length separately is unnecessary, and
   forgetting it is the bug you stop having. */
static std::size_t last_index_of(const std::vector<int> &v)
{
    return v.empty() ? 0 : v.size() - 1;   /* NO underflow: unsigned
                                              subtraction on 0 is a
                                              huge number, not -1  */
}

/* 2. REFERENCES ARE NOT POINTERS. They cannot be null, cannot be
   rebound, and the compiler keeps the aliasing straight. Use them
   for every output parameter and every view; use a pointer only when
   "might be absent" is a real state. */
static void bump(int &n) { ++n; }              /* always present   */
static void maybe(int *n) { if (n) ++*n; }     /* may be null     */

/* 3. OWNERSHIP IS IN THE TYPE. unique_ptr says "I own this";
   a shared_ptr says "we share this"; a raw pointer or a reference
   says "I borrow this and someone else owns it". */
struct Widget { int id; };

static void takes_ownership(std::unique_ptr<Widget> w) { w->id = 1; }
static void takes_shared(std::shared_ptr<Widget> w)   { w->id = 2; }
static void borrows(Widget *w)                         { w->id = 3; }

/* 4. A MOVED-FROM OBJECT IS VALID BUT UNSPECIFIED. It is not
   destroyed and not null - it is simply in a state you must not
   read until you assign to it. */
static std::string steal(std::string s)
{
    std::string taken = std::move(s);
    /* s is now valid but unspecified: usable, destructible,
       assignable. NOT usable for its old value. */
    return taken;
}

/* 5. EXCEPTIONS ARE FOR UNRECOVERABLE FAILURES, not for flow.
   The recover path is a return value. */
static std::optional<int> parse(const std::string &s)
{
    try {
        return std::stoi(s);
    } catch (const std::exception &) {
        return std::nullopt;      /* recover HERE, do not throw    */
    }
}

int main()
{
    std::vector<int> v{1, 2, 3};
    last_index_of(v);
    int n = 0; bump(n);
    takes_ownership(std::make_unique<Widget>());
    auto s = std::make_shared<Widget>();
    takes_shared(s); borrows(s.get());
    steal("copy me");
    parse("42");
}

0.4 How this guide is organised

The guide moves from the object model to the mechanisms, then to the interfaces, and it is ordered so that each chapter's assumptions are the previous chapter's conclusions.

Why this order

C++ tutorials usually teach syntax first and semantics second, and the result is a reader who can write a class but cannot say when a copy happens. This guide inverts that. The object model and value categories come first, because every later question — when is this copied, why did my reference dangle, what does this overload pick — is a question about those two. Then the memory mechanisms, because ownership is the single largest source of defects in modern C++. Then the type system, because templates and concepts are the language's abstraction and its constraint mechanism respectively. Then the library, because the standard library is what the type system exists to make possible. Then the three things every chapter has, and each is a property of the writing. A mechanism stated before its consequence, so the consequence is derivable rather than asserted. A list of what goes wrong with the mechanism behind each, because a C++ bug is almost never mysterious. And Practices, which are the habits that survive contact with a deadline. Then the two things about the code here, and both are stated so the wrong thing is not copied. Every sample is modern C++ — the current standard, with no compatibility shims, because a sample that teaches a 2003 idiom is a sample that teaches a bug. And exceptions are used where they are right — for unrecoverable errors at a boundary — and not used for expected outcomes, which is the convention the standard library itself follows. Then the two practices, and both are about reading. Read the "what goes wrong" list before the chapter, because it is the list of the errors you are about to make. And Compile every sample, because in C++ a sample you have compiled is a fact about your toolchain and one you have read is a claim about the language.

1.1 Objects, lifetimes and the three storage durations

A C++ object is a region of storage plus a type, and unlike a C struct it has a lifetime, a constructor and a destructor — which means almost every C++ defect is a statement about when those run.

Where an object lives, and how long it lives

An object has one of three storage durations. Automatic — a parameter, a local, a temporary — and its lifetime is its enclosing block, so its destructor runs at the closing brace even on an early return or an exception. Static — a namespace-scope variable, a function-local static, a member declared static — and its lifetime is the whole program, with initialisation before first use and destruction in reverse order at exit. Thread — one per thread, created with the thread and destroyed with it. Then the four rules that follow, and each is a requirement. Destruction happens in reverse order of construction, so an object may safely use one constructed before it and never one constructed after it — which is the rule that makes a member of a class safe to use in the destructor. An object that owns a resource must release it in its destructor, and the compiler generates the call for you, which is the entire basis of resource management in the language. A destructor must not throw, because it runs during unwinding and a throw from it terminates the program. And Temporary lifetimes are not obvious, — a temporary returned by a function lives until the end of the full expression, so binding it to a reference and extending the reference's life requires naming the type explicitly. Then the three things that go wrong, and each is a mechanism. Using a member in a destructor that is declared later in the class, which is a use of a destroyed object and reads whatever the storage holds now. Returning a reference to a local, which is the C dangling pointer in C++ clothing. And A function-local static with a constructor that throws, which retries the construction on the next call rather than propagating — a subtle and deliberate difference from a namespace-scope static. Then the two practices, and both are disciplines. Prefer automatic storage for everything, because it is the only duration whose lifetime the compiler proves from the braces. And When you must allocate dynamically, make the owner a value type so the ownership is in the type and the delete is in a destructor rather than in a code path somebody will forget.

/* An object is a region of storage plus a type - and unlike a C
   struct it has a LIFETIME, a constructor and a destructor. Almost
   every C++ defect is a statement about when those run. */

#include <cstdio>
#include <stdexcept>

/* THREE STORAGE DURATIONS.
   AUTOMATIC  a parameter, a local, a temporary. Lifetime is the
              enclosing BLOCK, so the destructor runs at the closing
              brace - on an early return, on an exception, always.
   STATIC     namespace-scope, function-local, or a static member.
              Whole program; initialised before first use; destroyed
              in REVERSE ORDER at exit.
   THREAD     one per thread, created and destroyed with it.       */

static std::FILE *open_file(const char *path)
{
    static int opened = 0;            /* initialised ONCE, even    */
    ++opened;                         /* if the constructor throws  */
    return std::fopen(path, "rb");
}   /* A function-local static's initialisation is retried on the
     NEXT CALL if the constructor threw. A namespace-scope static
     instead terminates the program. Deliberate, and surprising.   */

struct resource {
    FILE *f = nullptr;
    int  order = 0;

    explicit resource(const char *p, int n) : f(std::fopen(p, "rb")), order(n) {}
    ~resource() { if (f) std::fclose(f); }
    resource(const resource&) = delete;              /* no double  */
    resource& operator=(const resource&) = delete;
    resource(resource&& o) noexcept : f(o.f), order(o.order) { o.f = nullptr; }
};

/* RULE 1: DESTRUCTION IS IN REVERSE ORDER OF CONSTRUCTION. An
   object may safely use one constructed BEFORE it and never one
   constructed after it. */
static void reverse_order(int log)
{
    resource a("a", ++log);
    resource b("b", ++log);
    /* destroyed: b, then a - no matter how we leave */
}

/* RULE 2: AN OBJECT THAT OWNS SOMETHING RELEASES IT IN ITS
   DESTRUCTOR, and the compiler emits the call. That is the entire
   basis of resource management in the language. */
static int read_all(const char *path)
{
    resource r(path, 1);              /* acquired                */
    /* ... any early return, any throw, runs ~r HERE ... */
    return 0;
}

/* RULE 3: A DESTRUCTOR MUST NOT THROW. It runs during unwinding
   and a throw from it calls terminate. */
struct bad_dtor {
    ~bad_dtor() noexcept(false) { throw std::runtime_error("x"); }
};   /* If this fires during an exception, the process ends. Mark it
     noexcept and swallow, or log - but never throw. */

/* THE THREE FAILURES.
   1. USING A MEMBER IN A DESTRUCTOR THAT IS DECLARED LATER IN THE
      CLASS: it is already destroyed, so you read whatever the
      storage happens to hold. Declaration order in the class is
      destruction order, backwards.
   2. RETURNING A REFERENCE TO A LOCAL - the C dangling pointer, in
      C++ clothing.
   3. A FUNCTION-LOCAL STATIC WHOSE CONSTRUCTOR THROWS: the next
      call retries the construction rather than propagating, so a
      one-shot initialisation can run many times.              */

/* Two disciplines. PREFER AUTOMATIC STORAGE for everything, because
   it is the only duration whose lifetime the compiler proves from
   the braces. And WHEN YOU MUST ALLOCATE DYNAMICALLY, make the owner
   a value type so the ownership is IN THE TYPE and the release is
   in a destructor rather than in a code path somebody will forget. */

#include <memory>
#include <string>
#include <iostream>

/* THE THREE DURATIONS, and what destroys each object. */

/* AUTOMATIC: the block. A plain local, a parameter. Destroyed when
   the block ends, in REVERSE declaration order. */
static void automatic()
{
    Widget a;                       /* destroyed last  */
    Widget b;                       /* destroyed first */
    (void)a; (void)b;
}

/* STATIC: the program. Initialised once, before main. Destroyed at
   exit - and the destruction ORDER BETWEEN TRANSLATION UNITS is
   unspecified, which is why a static in a header is a bug even when
   it looks like one-use initialisation. */
static int counter = 0;             /* destroyed at exit  */

/* DYNAMIC: the allocation. Destroyed by whoever owns it. The four
   C++ ways to own it, in increasing order of cost. */
static void dynamic()
{
    auto raw   = new Widget;          /* MANUAL: never correct     */
    auto owned = std::make_unique<Widget>();      /* one owner     */
    auto shared = std::make_shared<Widget>();     /* many owners    */

    (void)raw;   /* who deletes this? */
    (void)owned;
    (void)shared;
    /* raw still leaks: nothing about the type changed, only about
       the OTHER two allocations */
}

/* THE DESTROYER, and the order rule that makes composition work. */
struct Resource {
    std::string name;
    explicit Resource(std::string n) : name(std::move(n)) {
        std::cout << "open " << name << '\n';
    }
    ~Resource() { std::cout << "close " << name << '\n'; }
    Resource(const Resource &)            = delete;  /* not copyable */
    Resource &operator=(const Resource &) = delete;
    Resource(Resource &&)            noexcept = default;
    Resource &operator=(Resource &&) noexcept = default;
};

/* Members are destroyed in REVERSE DECLARATION ORDER, which is the
   reason declaration order is a design decision and not a style
   preference: a member declared after another is destroyed BEFORE
   it, so anything the later member's destructor touches must still
   be alive. */
struct Session {
    Resource db{"db"};      /* destroyed SECOND */
    Resource cache{"cache"}; /* destroyed FIRST  */
};

1.2 lvalue, prvalue, xvalue — and why the distinction is load-bearing

Every expression in C++ is one of three value categories, and the categories decide whether a copy, a move, or nothing happens at all.

The three categories and the rules that follow from them

An lvalue has an identity — you can take its address — and it persists beyond the full expression. A named variable, a dereferenced pointer, a reference bound to an object, and a string literal are all lvalues. A prvalue is a value with no identity, produced by a constructor, a literal, or the result of an arithmetic operator. An xvalue is an object that is being treated as though it were about to be destroyed — the result of std::move, which is nothing more than a cast. Then the four rules that follow, and each is a requirement. Copying is initialising from an lvalue; moving is initialising from an xvalue, and since std::move produces an xvalue from anything, moving is a choice you make by asking for it. A function's parameter of type T copies; of type T& binds; of type T&& binds and steals. Temporary lifetime extends to the end of the full expression, not to the end of the statement and not to the end of the function, and the only way to extend it deliberately is to name the type in the declaration. And Copy elision is mandatory in some cases and permitted in others, which is why a class with a deleted copy constructor is still usable — the copy never happens. Then the three things that go wrong, and each is a mechanism. Passing a large object by value, which is a deep copy the caller pays for and the signature made invisible. std::move on a const object, which silently copies because the move constructor takes a non-const reference. And Binding a reference to a temporary returned from a function, which extends the temporary's life to the reference's scope and is a well-defined but easy-to-miss extension — and which is exactly why auto& on a factory call behaves differently from auto. Then the two practices, and both are disciplines. Take const T& by default and change it only when you have a reason to modify or to steal, because that single signature covers most uses and never surprises a caller. And Treat a missing const on a reference parameter as a question, because it means the function will modify or move from the argument and the caller may not expect either.

/* THREE VALUE CATEGORIES. This is the mechanism behind copy
   elision, overload resolution, and every dangling-reference bug in
   the language. */

/* An LVALUE has an identity: you can take its address, and it
   persists beyond the full expression. */
static void lvalues()
{
    int  x = 1;
    int* p = &x;             /* lvalue: addressable          */
    int& r = x;              /* lvalue                      */
    (void)r;
    const char *s = "text";  /* a string literal is an lvalue */
    (void)s;
}

/* A PRVALUE is a value with NO identity. */
static int prvalue() { return 42; }

/* An XVALUE is an object being treated as though it were about to
   be destroyed. std::move is NOTHING MORE THAN A CAST:
      template<class T> remove_reference_t<T>&& move(T&& t);
   It changes the value category. It does not move anything. The
   move happens at initialisation, from the xvalue. */
#include <utility>

struct heavy {
    std::vector<double> v;        /* 8 KB heap                   */
    heavy() : v(1000) {}
    heavy(const heavy& o) : v(o.v) { }         /* DEEP COPY      */
    heavy(heavy&& o) noexcept : v(std::move(o.v)) { }  /* STEAL     */
};

/* RULE 1: COPYING INITIALISES FROM AN LVALUE; MOVING INITIALISES
   FROM AN XVALUE. Because std::move produces an xvalue from
   anything, "moving" is a choice you make by asking. */
static void rule_one()
{
    heavy a;
    heavy b = a;                 /* copy: a is an lvalue        */
    heavy c = std::move(a);      /* move: std::move(a) is xvalue */
    (void)b; (void)c;            /* a is now valid but empty    */
}

/* RULE 2: T copies, T& binds, T&& binds and steals. */
static void copies(heavy h)          { }   /* deep copy        */
static void binds(heavy& h)          { }   /* binds, modifies  */
static void steals(heavy&& h)        { }   /* binds, steals    */

/* RULE 3: A TEMPORARY LIVES TO THE END OF THE FULL EXPRESSION, and
   binding a reference extends it to the reference's scope. This is
   the mechanism behind auto& behaving differently from auto. */
static std::vector<int> make() { return { 1, 2, 3 }; }

static void rule_three()
{
    auto  v  = make();       /* the vector is MOVED into v      */
    auto& v2 = make();       /* the temporary's life is EXTENDED
                                to v2's scope - well defined and
                                easy to miss                     */
    (void)v; (void)v2;
}   /* THE THREE FAILURES.
   1. PASSING A LARGE OBJECT BY VALUE: a deep copy the caller pays
      for, made invisible by the signature.
   2. std::move ON A CONST OBJECT: it silently COPIES, because the
      move constructor takes a non-const reference. The call looks
      like a move and is not.
   3. BINDING A REFERENCE TO A TEMPORARY: the lifetime extension is
      correct and is how auto& on a factory call differs from auto.

   Two disciplines. TAKE const T& BY DEFAULT and change it only when
   you have a reason to modify or to steal, because that one
   signature covers most uses and never surprises a caller. And
   TREAT A MISSING const ON A REFERENCE PARAMETER AS A QUESTION,
   because it means the function will modify or move from the
   argument and the caller may not expect either. */

#include <string>
#include <utility>
#include <vector>

/* THE FIVE CATEGORIES, and the one operation that distinguishes
   them. A CATEGORY IS ABOUT WHAT AN EXPRESSION NAMES, not about its
   type. */

int  g_value = 0;

int  &g_ref   = g_value;   /* an lvalue reference: still an LVALUE */

struct Holder {
    std::string text;
    std::string &get()        { return text; }  /* lvalue  */
    std::string  clone() const { return text; }  /* prvalue */
    std::string &&steal()    { return std::move(text); } /* xvalue */
    const std::string &peek() const { return text; } /* const lvalue */
};

static void takes_lvalue_ref(std::string &s)       { s += "!"; }
static void takes_rvalue_ref(std::string &&s)      { /* may steal */ }
static void takes_value(std::string s)             { /* a copy      */ }

static void demo()
{
    Holder h;

    takes_lvalue_ref(h.get());      /* lvalue: binds, no move     */
    takes_lvalue_ref(h.text);       /* lvalue: same               */

    takes_value(h.get());           /* PRVALUE: one COPY made     */
    takes_value(Holder{});          /* prvalue: no copy at all    */

    takes_value(std::move(h.text)); /* xvalue: move CONSTRUCTOR   */

    takes_rvalue_ref(h.clone());    /* prvalue: binds to &&       */
    takes_rvalue_ref(std::move(h)); /* xvalue                     */

    /* ...yet all four lines above can also be written as ONE call,
       and which overload runs is decided by the type of the
       ARGUMENT, not by the type of the object it came from. That
       is the entire point: copy elision and the rule of five are
       downstream consequences of this distinction. */
}

/* WHY IT IS LOAD-BEARING. The overload set is selected by category,
   so the same call with a one-character difference selects a
   different function. A type that is copyable but moveable gets
   both, and which one runs is decided here - not by a flag set
   somewhere in a base class. */

/* std::move DOES NOT MOVE. It is a cast to an rvalue reference, and
   the move happens at the parameter or return, where a move
   constructor can be selected. */
static void the_cast()
{
    std::string s = "hello";
    std::string t = std::move(s);
    /* s is now valid but unspecified: not empty, not destroyed,
       just no longer holding "hello". Reading it expecting the old
       value is the bug. */
    (void)t;
}

1.3 The special member functions, and the five that decide everything

A class has five functions the compiler will write for you if you do not, and which of them it writes depends on which of a handful of others you declared.

The rules that are not in the tutorial

The special member functions are a default constructor, a copy constructor, a copy assignment, a move constructor, and a destructor — plus the move assignment and the comparison operators. Then the three things that follow, and each is a requirement with a very specific consequence. Declaring any of them suppresses the others. Declare a destructor and the move constructor and move assignment are no longer generated, so your class becomes copy-only — which is a performance regression rather than a correctness one, and which is the single most common unintended consequence of adding a destructor. Declare a move constructor and the copy constructor and copy assignment are deleted, not merely not generated, which turns a compile error at every copy you did not write. A user-declared copy constructor makes the move constructor fall back to copying, which means a std::move on your type performs a deep copy and reports no diagnostic at all. Then the three things that go wrong, and each is a mechanism. A raw pointer member with the rule of three written by hand, which is a double free waiting for the one path that copies twice. A member that owns a resource and a class with a std::unique_ptr member, which makes the class move-only whether you wanted it to be or not. And A defaulted move constructor on a class whose member is a raw pointer, which moves the pointer and leaves both objects thinking they own it. Then the two practices, and both are disciplines. Let the compiler generate all of them and write none, by using the standard-library types as members — then the copy, move and destruction semantics are correct by construction and you have nothing to get wrong. And When you must manage a resource yourself, prefer wrapping it in a class with the five special members defaulted, so your type's semantics are the standard ones and a caller is never surprised.

#include <memory>
#include <string>

/* FIVE functions the compiler will write for you if you do not:
     default constructor, copy constructor, copy assignment,
     move constructor, destructor
   plus move assignment and the comparison operators.

   THE RULES THAT ARE NOT IN THE TUTORIAL.

   1. DECLARING ANY OF THEM SUPPRESSES THE OTHERS. Declare a
      destructor and the move constructor and move assignment are no
      longer generated - so your class silently becomes COPY-ONLY.
      That is a performance regression, not a correctness one, and
      it is the most common unintended consequence of adding a
      destructor to a class that did not need one.
   2. DECLARING A MOVE CONSTRUCTOR DELETES the copy constructor and
      copy assignment (deleted, not merely not generated), so every
      copy you did not write becomes a compile error.
   3. A USER-DECLARED COPY CONSTRUCTOR MAKES move() FALL BACK TO
      COPYING, so std::move on your type performs a deep copy and
      reports NOTHING. */

/* THE THREE FAILURES.
   1. A RAW POINTER MEMBER with the rule of three written by hand:
      a double free waiting for the one path that copies twice.
   2. A MEMBER THAT OWNS A RESOURCE alongside a class holding a
      std::unique_ptr: the class becomes MOVE-ONLY whether you
      wanted it to be or not.
   3. A DEFAULTED MOVE CONSTRUCTOR on a class whose member is a raw
      pointer: it moves the POINTER and leaves both objects
      believing they own it. */

/* RIGHT: let the compiler generate all of them, because the
   standard-library types as members are already correct. */
struct good {
    std::string                    name;      /* owns, copies, */
    std::vector<int>               values;    /* moves         */
    std::unique_ptr<Node>          root;      /* moves only    */
};   /* good is move-only, automatically, and correctly. It is
     move-only because unique_ptr is, not because anybody decided.
     A caller who wanted a copy finds out at COMPILE TIME rather
     than by reading the class. */

/* WRONG: the raw pointer with hand-written rules. */
struct manual {
    Node *p = nullptr;
    ~manual() { delete p; }
    manual(const manual& o) : p(new Node(*o.p)) { }   /* copies */
    /* no move constructor: std::move will COPY            */
    manual& operator=(const manual& o) { p = new Node(*o.p); return *this; }
};   /* Also wrong: the assignment leaks the old p. */

/* FIXED: wrap the raw pointer, or use unique_ptr. */
struct fixed {
    std::unique_ptr<Node> p;
    explicit fixed(Node* q) : p(q) {}
};   /* No destructor written. No copy operations written. Nothing
     to get wrong. */

/* Two disciplines. LET THE COMPILER GENERATE ALL OF THEM and write
   none, by using the standard-library types as members - then copy,
   move and destruction semantics are correct by construction. And
   WHEN YOU MUST MANAGE A RESOURCE YOURSELF, wrap it in a class
   with the five special members DEFAULTED, so your type's semantics
   are the standard ones and a caller is never surprised by a type
   that moved when they expected a copy. */

#include <string>
#include <utility>
#include <iostream>

/* THE FIVE THAT DECIDE EVERYTHING. Declare exactly one and the
   compiler does not generate the others. */
struct RuleOfZero {
    std::string name;         /* a member that manages itself, so
                                  every member of this group is
                                  defaulted or deleted correctly  */
    int id = 0;
    /* No destructor declared: the compiler generates one that
       destroys each member. */
    /* No copy ctor: generated, member by member. */
    /* No move ctor: generated, because there is no user-declared
       destructor or copy operation to suppress it. */
};

/* THE RULE OF FIVE, spelled out, and what each one must do. */
struct RuleOfFive {
    int *data = nullptr;
    std::size_t n = 0;

    explicit RuleOfFive(std::size_t count)
        : data(new int[count]()), n(count) {}

    ~RuleOfFive()                        { delete[] data; }

    RuleOfFive(const RuleOfFive &o)            /* COPY: deep copy */
        : data(new int[o.n]), n(o.n)
    { for (std::size_t i = 0; i < n; ++i) data[i] = o.data[i]; }

    RuleOfFive &operator=(const RuleOfFive &o)
    {
        if (this != &o) {                  /* SELF-ASSIGNMENT */
            auto *fresh = new int[o.n];
            for (std::size_t i = 0; i < o.n; ++i) fresh[i] = o.data[i];
            delete[] data;                 /* free AFTER the
                                               new one exists: if
                                               the allocation
                                               throws, this object
                                               is unchanged       */
            data = fresh; n = o.n;
        }
        return *this;
    }

    RuleOfFive(RuleOfFive &&o) noexcept      /* MOVE: take it */
        : data(o.data), n(o.n)
    { o.data = nullptr; o.n = 0; }           /* leave the source
                                                 in a valid
                                                 state          */

    RuleOfFive &operator=(RuleOfFive &&o) noexcept
    {
        std::swap(data, o.data);
        std::swap(n, o.n);
        return *this;
    }
};

/* THE RULE OF ZERO, which is what RuleOfFive should usually be. */
struct AlsoRuleOfZero {
    std::vector<int> values;      /* owns itself: nothing to write */
    std::string label;
};

/* WHAT DECLARING ONE SUPPRESSES. Declare a destructor and the
   compiler stops generating the MOVE operations - and since a
   move is what a std::vector does when you return by value, your
   class silently becomes copy-only and every call site pays a
   deep copy it does not know about. This is the single most common
   way a rule-of-zero class becomes a rule-of-three one. */
struct OneDeclaredDestructor {
    std::string s;
    ~OneDeclaredDestructor() = default;   /* now copy-only: the
                                              implicit move is
                                              suppressed          */
    /* Fix: declare the moves explicitly, defaulted:
         OneDeclaredDestructor(OneDeclaredDestructor &&) = default;
         OneDeclaredDestructor &operator=(OneDeclaredDestructor &&) = default;
       ...which is exactly what = default on all five means.       */
};

/* THE DESTROYER ORDER, and the hazard it creates: a member declared
   LATER is destroyed EARLIER, so a destructor that touches a member
   must not assume it is still alive. */
struct Order {
    std::string log{"log"};       /* destroyed SECOND */
    std::string cache{"cache"};   /* destroyed FIRST: if its
                                     destructor touches log, log
                                     is still alive. The reverse
                                     declaration would be UB. */
    ~Order() { /* both still alive HERE, in the body */ }
};

2.1 What a class actually declares

A class in C++ is a struct with access control and some default member functions — and the two things that surprise newcomers are that a member function may touch the object without a pointer and that a class is not by default assignable.

Four decisions a class makes

Declaring a class makes four decisions. What layout it has — the data members and their order, which determine the size and the padding. What can see what — the three access levels, and the fact that a derived class does not automatically see a base class's private members. What operations exist — which of copy, move, comparison and arithmetic are available, entirely determined by which members and special functions you wrote. And What the type promises — which is invisible unless you write it. Then the four rules that follow, and each is a requirement. Access control is per-name, not per-type, so two members of the same class can have different access and a derived class can see the public ones without the private ones. An invoked with the object type visible, — a member function is not a free function taking a pointer, it is a function with an implicit object parameter, which is why calling a member function on a temporary works and why a member function cannot be used as a plain callable without capturing the object. A class with a reference or const member cannot be default-constructed or assigned, because there is no sensible value for the reference. And The class layout is not an ABI unless you say so, so a class used across a shared-library boundary needs an explicit guarantee or it will be silently misread by a caller built against a different header. Then the three things that go wrong, and each is a mechanism. Making the data members public because they were public in a struct, which removes the only place an invariant could be enforced. Returning a reference to a private member from a public method, which hands out the ability to change what the class believes. And A class with a std::mutex or an atomic member, which is neither copyable nor movable — and which is correct, and which surprises a caller who stored it in a vector. Then the two practices, and both are disciplines. Keep the data members private and expose intent, not representation, because that is what makes the class changeable later without changing every caller. And Make a class that owns something non-copyable, or make it fully copyable — but never one without deciding, because the accidental default is a compile error at best and a shallow copy at worst.

#include <atomic>
#include <string>
#include <vector>

/* A class is a struct with access control and some default member
   functions. Declaring one makes FOUR decisions:
     1. its LAYOUT      - members and their order
     2. what sees what  - three access levels
     3. what operations exist - copy, move, compare, arithmetic
     4. what it PROMISES - which is invisible unless written    */

/* RULE 1: ACCESS IS PER-NAME, not per-type. */
class account {
    std::string owner_;        /* private                        */
    long        cents_ = 0;   /* private                        */
public:
    long balance() const { return cents_; }   /* public          */
    void  set_owner(std::string s) { owner_ = std::move(s); }
private:
    std::string note_;        /* a second private member        */
};   /* A derived class sees balance() and NOT owner_. That is
     not the same as "the base is private".                        */

/* RULE 2: A MEMBER FUNCTION IS NOT A FREE FUNCTION. It has an
   implicit object parameter, which is why calling one on a
   temporary works and why it cannot be used as a plain callable
   without capturing the object. */
static std::vector<std::string> names;

'; }

    account a;

                                          implicit argument, and
                                          you cannot take the
                                          address of a temporary  */

   1. MAKING DATA MEMBERS PUBLIC because they were public in a
      struct - which removes the only place an invariant could ever
      be enforced.
   2. RETURNING A REFERENCE TO A PRIVATE MEMBER from a public
      method, which hands out the ability to change what the class
      believes about itself.
   3. A CLASS WITH A MUTEX OR ATOMIC MEMBER: neither copyable nor
      movable - which is CORRECT, and which surprises a caller who
      tried to store one in a vector.                            */

/* A class with a reference member cannot be default-constructed or
   assigned: there is no sensible value for the reference, and the
   compiler says so rather than inventing one. */
class span {
    const int* p_;
    size_t     n_;
public:
    span(const int* p, size_t n) : p_(p), n_(n) {}
    /* no default ctor, no assignment - and the compiler says so */
    int  operator[](size_t i) const { return p_[i]; }
    size_t size() const { return n_; }
};

/* A class crossing a shared-library boundary needs an explicit ABI
   guarantee, or a caller built against a different header will read
   the wrong offsets. */
struct export_tag {};                    /* empty, at the top    */
struct export API final : export_tag {     /* layout frozen here   */
    int  version = 1;
    std::string payload;
};   /* Two disciplines. KEEP DATA MEMBERS PRIVATE and expose INTENT
     rather than representation, because that is what lets the class
     change its layout later without changing every caller. And
     MAKE A CLASS THAT OWNS SOMETHING NON-COPYABLE, or fully
     copyable - but never one without deciding, because the
     accidental default is a compile error at best and a shallow
     copy at worst. */

#include <string>
#include <vector>
#include <stdexcept>

/* WHAT A CLASS DECLARES, in the order the compiler reads it. */
class Account {
public:
    /* ORDER MATTERS: a member initialiser list can only mention
       members already DECLARED above it. Swap these two and the
       build fails with "used before its declaration" - which is
       the compiler enforcing initialisation order rather than list
       order, and the two are not the same. */
    explicit Account(std::string id, unsigned long opening)
        : id_(std::move(id)),        /* in DECLARATION order */
          balance_(opening)          /* ... not list order    */
    {
        if (id_.empty())
            throw std::invalid_argument("an account needs an id");
    }

    /* ACCESS. Note that const is on the METHOD, not the member:
       const on a member function is part of its type, so a const
       Account has a different interface from a mutable one and the
       compiler will not let you mix them up. */
    [[nodiscard]] const std::string &id()    const { return id_; }
    [[nodiscard]] unsigned long   balance() const { return balance_; }

    void deposit(unsigned long amount)
    {
        if (amount == 0) throw std::invalid_argument("zero deposit");
        balance_ += amount;         /* precondition checked HERE,
                                      where the invariant is known  */
    }

    /* NON-CONST, because it mutates - and therefore cannot be
       called on a const Account, which is what makes a const
       reference genuinely const-correct rather than a promise. */
    void withdraw(unsigned long amount)
    {
        if (amount > balance_) throw std::runtime_error("insufficient");
        balance_ -= amount;
    }

    /* THE THREE QUALIFIERS, and what each buys. */
    static std::size_t open_count() { return ++open_; }  /* shared
                                                             across
                                                             all
                                                             instances */
    const std::string &id()    const noexcept { return id_; }  /* cannot
                                                                   throw */
    void tag(const char *t) noexcept { tag_ = t; }        /* a fast
                                                              path   */

private:
    /* INVARIANT, stated in a comment the code enforces: balance_ is
       never negative, because withdraw refuses rather than clamps.
       A class is where invariants live, and this is the reason to
       have one at all. */
    std::string    id_;
    unsigned long  balance_ = 0;
    const char    *tag_     = nullptr;   /* a borrowed pointer: the
                                             class does NOT own it,
                                             and the comment says so */
    inline static std::size_t open_ = 0;
};

/* THE COMPOSITION FORM, which is usually the one you want, and is
   legal here because Account is copyable and movable by default. */
class Portfolio {
    std::vector<Account> accounts_;
public:
    void add(Account a) { accounts_.push_back(std::move(a)); }
    unsigned long total() const
    {
        unsigned long sum = 0;
        for (const auto &a : accounts_) sum += a.balance();
        return sum;
    }
};

2.2 Inheritance, virtual dispatch, and why composition usually wins

Inheritance gives you a substitutable relationship, and the cost is that every subclass becomes a promise about the base class — which is why the composition-over-inheritance advice is right far more often than it is given.

What virtual dispatch actually does

A virtual function call through a base pointer or reference dispatches to the derived implementation at run time, and the mechanism is a table in the object plus a constructor that fills it. The dispatch is only dynamic when the static type differs from the dynamic type, which means a call inside the base class's own member function on *this is also dynamic — and that is what makes the base's destructor and any base member function able to call something overridden. A constructor and a destructor are never virtual dispatch, because during construction the derived part of the object does not exist yet, which is the mechanism behind "the base constructor called a virtual function and got the base version". Then the four rules that follow, and each is a requirement. A class intended for derivation needs a virtual destructor, and the compiler will not tell you — the rule of three and five is the only protection, which is why the modern guidance is to write virtual or final deliberately. Never call a virtual function from a constructor or destructor, because the derived part is not yet or no longer constructed. Prefer holding by reference or pointer for polymorphic types, because a by-value parameter slices the object to the static type and then dispatches on the slice — a correct-looking call to the wrong implementation. And Prefer composition when the relationship is "has a" rather than "is a", because composition has no dispatch cost, no ordering constraint and no promise about future behaviour. Then the three things that go wrong, and each is a mechanism. Object slicing, which happens silently at every by-value assignment and parameter pass, and which is invisible because the code compiles and runs. Deleting through a base pointer without a virtual destructor, which frees the base part and leaks or corrupts the derived part. And A deep hierarchy where a change to a base method's contract breaks six subclasses, which is the reason the cost of inheritance is paid at every level. Then the two practices, and both are disciplines. Mark a base class virtual on its destructor from the day you write it, because adding it later is a breaking change for every caller that already deletes through a base pointer. And Use inheritance for substitutability and composition for everything else, because the only relationship that genuinely requires dynamic dispatch is the one where callers must not know the concrete type.

#include <cstdio>
#include <memory>
#include <vector>

/* Inheritance gives a SUBSTITUTABLE relationship. The cost is that
   every subclass becomes a PROMISE ABOUT THE BASE CLASS - which is
   why composition wins far more often than the advice suggests. */

/* Dynamic dispatch only happens when the STATIC type differs from
   the DYNAMIC type. Inside the base's own member function, this->*
   is still dynamic - which is what lets a base destructor call an
   overridden function. */
struct widget {
    virtual ~widget() = default;             /* VIRTUAL: see below */
    virtual void draw() const { std::puts("base"); }
    void render() const { draw(); }          /* DYNAMIC: this->    */
};

/* RULE 1: A CLASS INTENDED FOR DERIVATION NEEDS A VIRTUAL DESTRUCTOR.
   The compiler will not tell you. Without one:
     struct d : widget { int extra[64]; };
     widget* w = new d; delete w;   -> the base part is freed and
                                        the derived array leaks  */
struct good_base {
    virtual ~good_base() { std::puts("~good_base"); }
    virtual void draw() const { std::puts("base"); }
};
struct derived : good_base { ~derived() override { std::puts("~derived"); }
                              void draw() const override { std::puts("derived"); } };

/* RULE 2: NEVER CALL A VIRTUAL FUNCTION FROM A CONSTRUCTOR OR
   DESTRUCTOR. During construction the derived part does not exist
   yet, so you get the BASE version - with the derived members
   uninitialised. */
struct calling_in_ctor : good_base {
    int x = 0;
    calling_in_ctor() { draw(); }   /* calls good_base::draw, and
                                      x is 0                    */
    void draw() const override { std::puts("derived"); }
};

/* THE FAILURE NOBODY BELIEVES UNTIL THEY SEE IT: OBJECT SLICING.
   Silent, correct-looking, and it happens at every by-value
   parameter and every by-value assignment. */
static int area(const widget w) { w.draw(); return 0; }  /* SLICES */

static void slicing()
{
    derived d;
    widget w = d;          /* SILENTLY SLICED to widget        */
    w.draw();              /* prints "base"                    */
    area(d);               /* passes a SLICE                   */

    /* The by-reference form is the correct one. */
    auto by_ref = [](const widget& x) { x.draw(); };
    by_ref(d);             /* prints "derived"                 */

    /* And polymorphism without inheritance: a container of pointers,
       which is what composition looks like in practice. */
    std::vector<std::unique_ptr<widget>> all;
    all.push_back(std::make_unique<derived>());
    for (const auto& x : all) x->draw();     /* "derived"       */
}

/* RULE 4: COMPOSITION WHEN IT IS has-a, NOT is-a. No dispatch
   cost, no construction-order constraint, and no promise about
   future behaviour. */
struct engine { int rpm = 0; };
struct car    { engine e; void start() { e.rpm = 800; } };
/* car is not a vehicle; it CONTAINS an engine, and it can change
   what that engine is without breaking anything.               */

/* Two disciplines. MARK A BASE CLASS virtual ON ITS DESTRUCTOR from
   the day you write it, because adding it later is a BREAKING
   CHANGE for every caller that already deletes through a base
   pointer - and nobody finds out until they upgrade. And USE
   INHERITANCE FOR SUBSTITUTABILITY and composition for everything
   else, because the only relationship that genuinely requires
   dynamic dispatch is the one where callers must not know the
   concrete type. */

#include <memory>
#include <string>
#include <vector>
#include <iostream>

/* WHY COMPOSITION USUALLY WINS, shown as code rather than argued. */

/* INHERITANCE: an is-a relationship the compiler enforces only at
   the point of a virtual call. */
struct Notifier {
    virtual ~Notifier() = default;
    virtual void notify(std::string_view msg) = 0;   /* pure      */
    void notify_twice(std::string_view m) { notify(m); notify(m); }
};

struct EmailNotifier final : Notifier {              /* final: no
                                                         further
                                                         derivation,
                                                         so the
                                                         compiler
                                                         devirtualises */
    void notify(std::string_view m) override { std::cout << m << '\n'; }
};

/* COMPOSITION: a has-a relationship, and the type relationship is
   visible without a virtual call. */
struct Logger {
    void log(std::string_view m) { std::cout << "[log] " << m << '\n'; }
};

struct Service {
    Logger log;                       /* a MEMBER, not a base    */

    void run(std::string_view m)
    {
        log.log(m);
        log.log(m);
    }
};

/* THE THREE COSTS OF INHERITANCE, each visible above. */

/* 1. THE BASE IS PART OF THE OBJECT. Deriving from three bases
      means three vtables, and the object is as large as all of
      them - which matters when you are holding ten million of them. */
struct Base1 { virtual void f() {} };
struct Base2 { virtual void g() {} };
struct Base3 { virtual void h() {} };
struct Derived : Base1, Base2, Base3 { void f() override {} };
static_assert(sizeof(Derived) >= 3 * sizeof(void *));

/* 2. EVERY DERIVATION IS A COMMITMENT TO THE BASE'S INTERFACE. Add
      a virtual method to Base1 and every derived class - including
      the ones in a third-party library you did not write - may no
      longer compile, because it might now be abstract or
      ambiguously overridden. */
struct WidenedBase : Base1 { void g2() {} };   /* changes Base1 */

/* 3. THE COMPOSITION DIRECTION IS INVERTIBLE. A Service owns a
      Logger; a Logger knows nothing about Service. With inheritance
      the base often needs a downcast to answer a question only the
      derived class can answer, which is a cast that fails at run
      time instead of a type error at compile time. */
static void the_cast(const Notifier &n)
{
    if (const auto *e = dynamic_cast<const EmailNotifier *>(&n))
        e->notify("only email");
    /* dynamic_cast returns nullptr when wrong: the relationship you
       wanted to make compile-time is now a runtime question.     */
}

/* THE POLYMORPHIC VALUE PATTERN, which is the way to have either. */
struct Shape {
    virtual ~Shape() = default;
    [[nodiscard]] virtual double area() const = 0;
};
struct Circle final : Shape {
    double r;
    explicit Circle(double radius) : r(radius) {}
    [[nodiscard]] double area() const override { return 3.14159 * r * r; }
};

static double total_area(const std::vector<std::unique_ptr<Shape>> &shapes)
{
    double sum = 0;
    for (const auto &s : shapes) sum += s->area();
    return sum;
    /* unique_ptr, not Shape by value: you cannot slice through a
       unique_ptr by accident, because converting Shape to Shape
       does not compile. */
}

3.1 Why new is a defect generator, and what RAII replaced

Manual memory management in C++ has exactly two failure modes — a leak and a double free — and both come from the same place: the lifetime of a resource is a separate fact from the lifetime of the thing that uses it.

The two failures and the single cause

A leak happens when an allocation has no matching release on some path, and the most common path is the early return nobody thought about. A double free happens when two owners both believe they own the same allocation, and the most common cause is copying an object that holds a raw pointer. And a use-after-free happens when a pointer outlives its target, which is the same missing-fact problem as the other two. Then the four rules that follow, and each is a requirement. An object owns a resource through a member, and its destructor releases it. That is RAII, and it converts both failures into compile errors, because a copy constructor that would double-free becomes a deleted function. A raw new result is immediately handed to an owning type, so there is no window in which the allocation is unowned. Prefer a value on the stack to a heap allocation, unless you need a lifetime longer than the scope, a size known only at run time, or an incomplete type. And Never write delete in application code at all, because a type that owns something deletes it for you. Then the three things that go wrong, and each is a mechanism. Hiding a delete behind a getter that returns the raw pointer, which re-creates the problem for every caller. A type whose destructor is written by hand while a member also owns something, which is two owners. And Catching an exception between the allocation and the owning type, which is the one case where new is not exception-safe on its own — the reason the two-step form exists. Then the two practices, and both are disciplines. Use make_unique and make_shared rather than new plus a constructor call, because they are exception-safe and because the ownership is visible in one expression. And When a type owns something, default its copy operations and write no destructor, so the compiler generates correct semantics rather than you.

#include <memory>

/* TWO FAILURES, ONE CAUSE.
   LEAK          an allocation with no matching release on some path.
                 The most common path is the EARLY RETURN.
   DOUBLE FREE   two owners both believe they own it. The most
                 common cause is COPYING an object holding a raw
                 pointer.
   USE AFTER FREE a pointer that outlives its target - the same
                 missing-fact problem as the other two.            */

/* RAII: an object OWNS A RESOURCE THROUGH A MEMBER, and its
   destructor releases it. That converts both failures into COMPILE
   ERRORS, because the copy constructor that would double-free
   becomes a deleted function. */

/* THE WRONG WAY. Every line of this is a defect waiting. */
struct bad_raw {
    int* data;
    explicit bad_raw(size_t n) : data(new int[n]) {}
    ~bad_raw() { delete[] data; }

    bad_raw(const bad_raw& o) : data(new int[0]) {
        *data = *o.data;                 /* only one int, not all */
    }   /* BUG 1: the copy allocates the WRONG SIZE, so a shallow
           assignment of a large object corrupts the heap.
           BUG 2: no move constructor, so std::move COPIES.
           BUG 3: no operator=, so assignment LEAKS the old buffer. */
};

/* THE RIGHT WAY: no destructor, no copy operations, no delete. */
struct good_raw {
    std::vector<int> data;                /* owns, copies, moves */
    explicit good_raw(size_t n) : data(n) {}
};   /* Nothing to get wrong. The type's semantics are the standard
     ones and a caller is never surprised.                       */

/* THE ALLOCATION FORM. make_unique and make_shared rather than new
   plus a constructor call, because they are EXCEPTION-SAFE: if the
   constructor throws after new succeeded, the raw form leaks, and
   the make form does not. */
static std::unique_ptr<shape> make_shape(double r)
{
    /* RIGHT: if the constructor throws, the memory is freed. */
    return std::make_unique<circle>(r);

    /* WRONG, and the leak is invisible:
         auto p = new circle(r);       // if circle(r) throws, LEAK  */
}

/* PREFER A VALUE ON THE STACK unless you need a lifetime longer
   than the scope, a size known only at run time, or an incomplete
   type. A vector of small values holds them inline, which is faster
   than a vector of pointers because it is one allocation rather
   than n plus n. */
static std::vector<circle> by_value;     /* contiguous           */
static std::vector<std::unique_ptr<circle>> by_pointer;  /* n + n   */

/* THE THREE FAILURES.
   1. HIDING A delete BEHIND A GETTER that returns the raw pointer:
      re-creates the problem for every caller, and the getter is
      where the lifetime becomes invisible.
   2. A TYPE WHOSE DESTRUCTOR IS HAND-WRITTEN while a member also
      owns something: two owners, and only one of them knows.
   3. CATCHING AN EXCEPTION between the allocation and the owning
      type - the one case where new is not exception-safe on its
      own, which is exactly why make_unique exists.              */

/* Two disciplines. USE make_unique AND make_shared rather than new
   plus a constructor call, because they are exception-safe and the
   ownership is visible in one expression. And WHEN A TYPE OWNS
   SOMETHING, DEFAULT ITS COPY OPERATIONS and write no destructor,
   so the compiler generates semantics rather than you. */

#include <memory>
#include <vector>
#include <cstdio>

/* FOUR THINGS new DOES THAT A VALUE DOES NOT, and why each one is a
   defect waiting for a refactor. */

void four_ways_to_lose_a_pointer()
{
    /* 1. THE ALLOCATION SUCCEEDS AND THE CONSTRUCTOR THROWS. The
          memory is allocated; the object never completes
          construction; new DELETES the memory and propagates. This
          is the one case new gets right, and it is why make_unique
          is not merely shorter. */
    struct ThrowsInCtor { ThrowsInCtor() { throw 1; } };
    try { auto p = new ThrowsInCtor(); (void)p; } catch (...) { /* no leak */ }

    /* 2. THE POINTER IS LOST. There is now no way to name the
          allocation, and it lives until the process exits. */
    new int(42);

    /* 3. THE WRONG DELETE. A scalar new paired with delete[], or an
          array new paired with delete. Undefined behaviour, and the
          two forms are interchangeable enough to mistype. */
    auto p = new int[10];
    delete p;               /* WRONG: delete, not delete[] */

    /* 4. THE TYPE PUNNING. p is Widget*, the array is Widget[], and
          nothing in the pointer records which. */
    auto q = new Widget[10];
    delete[] q;             /* right, only if you remembered */
    (void)p; (void)q;
}

/* THE DELETE FORM THAT DEPENDS ON A TYPE, which is why a container
   of owning raw pointers cannot be deleted safely. */
struct Widget { Widget() = default; ~Widget() { std::puts("bye"); } };

static void the_container_problem()
{
    std::vector<Widget*> v;
    for (int i = 0; i < 3; ++i) v.push_back(new Widget);
    /* Now: which delete? The vector does not know, so you write a
       loop, and the loop is where the leak and the double free
       both come from. */
    for (auto *w : v) delete w;
}

/* THE FIX, and it is a change of TYPE rather than a change of
   discipline. */
static void the_fix()
{
    std::vector<std::unique_ptr<Widget>> v;
    for (int i = 0; i < 3; ++i) v.push_back(std::make_unique<Widget>());
    /* No delete anywhere. The destructor of each element runs in
       reverse order, exactly once, and a failure to delete is a
       COMPILE ERROR because there is no raw pointer to leak. */
}

/* AND WHY make_unique RATHER THAN unique_ptr(new T). Both do the
   same thing, but only one is a SINGLE EXPRESSION. The two-argument
   form has a window between the allocation and the construction
   where an exception leaves the pointer leaked - and the comment
   that fixed that in the standard library is one of the more
   famous in the language. */
static void two_expressions()
{
    std::unique_ptr<Widget> a(new Widget);          /* leaky window */
    std::unique_ptr<Widget> b = std::make_unique<Widget>();  /* not  */
    (void)a; (void)b;
}

3.2 unique_ptr, shared_ptr, and the four questions to ask

Three pointer types answer three ownership questions, and choosing correctly is a design decision that is either right or wrong in ways no test will find.

Three questions, three types

Does exactly one thing own this? Then it is a unique_ptr, which is the default and should be what you reach for first. Do several things genuinely share ownership, with the last one standing releasing it? Then it is a shared_ptr, and "genuinely" is the word that does the work. Does nobody own it and it is known to be alive? Then it is a raw pointer or a reference, and this is the most common correct answer. Then the four things to know, and each is a mechanism. A shared_ptr's control block is a separate allocation, so a shared_ptr costs two allocations and a make_shared costs one — which is the whole argument for make_shared. The count is atomic, so every copy is a contended atomic increment, which is why sharing in a hot loop is measurably expensive. A unique_ptr is exactly as large as a raw pointer, so it costs nothing over one, which removes the only real argument for using raw pointers for performance. And A raw pointer that observes without owning is a different type from one that owns, which is why a class with a raw pointer member and a unique_ptr member is a design smell: it says the ownership was never decided. Then the three things that go wrong, and each is a mechanism. A cycle of shared_ptrs, which never reaches a count of zero and leaks the whole cycle permanently. Using shared_ptr because it is easier, which makes ownership ambiguous and produces a program nobody can say who frees what. And Passing a unique_ptr by value as an output parameter, which is legal and reads as an input. Then the two practices, and both are disciplines. Default to unique_ptr and convert only with a deliberate reason, because every conversion to sharing is a design decision that is expensive to undo. And Use a raw pointer or reference for observing, and say so in the parameter type, because the parameter type is where a caller reads whether the function might keep the pointer.

#include <memory>

/* THREE QUESTIONS, THREE TYPES.
   Does EXACTLY ONE thing own this?          -> unique_ptr
   Do SEVERAL things genuinely share it?    -> shared_ptr
   Does NOBODY own it and is it known alive? -> raw pointer/ref   */

/* THREE FACTS THAT DECIDE THE COST.
   1. A shared_ptr's CONTROL BLOCK IS A SEPARATE ALLOCATION, so a
      shared_ptr costs two allocations and make_shared costs one.
      That is the whole argument for make_shared.
   2. THE COUNT IS ATOMIC, so every copy is a CONTENDED ATOMIC
      INCREMENT. Sharing in a hot loop is measurably expensive.
   3. A unique_ptr IS EXACTLY AS LARGE AS A RAW POINTER, so it costs
      nothing over one - which removes the last real argument for
      raw pointers on performance grounds.                       */

struct node {
    std::string name;
    std::vector<std::weak_ptr<node>> children;   /* WEAK, see below */
};

/* THE CYCLE. Two shared_ptrs that point at each other keep each
   other's count above zero forever, and the whole cycle leaks
   permanently - not until the process exits, but for good. The
   standard library does not detect it because detecting it would
   require a graph traversal on every destruction.

   THE FIX: the back-pointer is an OBSERVER, not an owner, so it is
   a weak_ptr. */
static std::shared_ptr<node> make_tree()
{
    auto root = std::make_shared<node>();
    root->name = "root";
    for (int i = 0; i < 3; ++i) {
        auto kid = std::make_shared<node>();
        kid->name = "kid";
        root->children.push_back(kid);      /* weak: no cycle    */
    }
    return root;
}

/* THE THREE FAILURES.
   1. A CYCLE OF shared_ptrs: never reaches zero, leaks permanently.
   2. USING shared_ptr BECAUSE IT IS EASIER: ownership becomes
      ambiguous, and the result is a program in which nobody can
      say who frees what.
   3. PASSING A unique_ptr BY VALUE as an output parameter, which is
      legal and READS AS AN INPUT at the call site.              */

/* The parameter type says whether the function might KEEP the
   pointer. This is the whole communication mechanism, and it is
   worth getting right because it is the only place a caller reads
   it from. */
static void observe(const node& n) { /* cannot store &n past here */ }
static void may_store(node& n)     { /* the signature says it      */ }

/* The conversion that has to be deliberate: unique_ptr to
   shared_ptr is free, shared_ptr to unique_ptr is not. */
static void ownership_transfers()
{
    auto u = std::make_unique<node>();          /* exclusive       */
    std::shared_ptr<node> s = std::move(u);     /* promoted, no cost*/
    s.reset();                                   /* count -> 0       */

    auto s2 = std::make_shared<node>();         /* shared           */
    /* std::unique_ptr<node> u2 = s2;  COMPILE ERROR: it would have
       to leave one other owner dangling, and the language will not
       do that for you. This is correct: a class with two shared_ptr
       members is genuinely shared, and converting one back to
       exclusive is a design change, not a cast.                 */
    (void)s2;
}   /* Two disciplines. DEFAULT TO unique_ptr AND CONVERT ONLY WITH
     A DELIBERATE REASON, because every conversion to sharing is a
     design decision that is expensive to undo. And USE A RAW POINTER
     OR REFERENCE for observing - and say so in the parameter type,
     because that type is where a caller reads whether the function
     might keep the pointer. */

#include <memory>
#include <vector>
#include <mutex>
#include <cstdio>

struct Widget { int id; explicit Widget(int i) : id(i) {} };

/* THE FOUR QUESTIONS, as code. Each shared_ptr below exists only
   because one answer was yes. */

/* 1. IS THE OWNERSHIP TRANSFERRED? If no, use a reference. */
static void borrows(Widget &w) { w.id = 1; }

/* 2. DOES ONE THING OWN IT FOREVER? If yes, unique_ptr. */
static std::unique_ptr<Widget> owns()
{
    return std::make_unique<Widget>(1);
}

/* 3. DO MANY THINGS SHARE IT AND THE LAST ONE FREES IT? If yes,
   shared_ptr - and you have accepted a control block and two
   atomic refcount operations per copy. */
static void shared()
{
    auto a = std::make_shared<Widget>(2);
    auto b = a;                       /* one control block, refcount 2 */
    a->id = 3;
    (void)b;
}

/* 4. DOES ANYTHING OBSERVE THE LIFETIME AND ACT ON IT - a cache, a
   connection pool, a subscription? Then use a WEAK POINTER, and the
   reason is that a shared_ptr cycle LEAKS. */
struct Node {
    std::shared_ptr<Node> next;      /* strong: this node owns next  */
    std::weak_ptr<Node>   back;      /* weak:   this node does NOT
                                          own its predecessor     */
    ~Node() { std::puts("node gone"); }
};

static void the_cycle()
{
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->next = a;                      /* the cycle: reference count
                                          on each is now 2, and
                                          dropping both local
                                          variables still leaves
                                          1 each. NOTHING IS
                                          FREED.                    */
    /* b->back is weak, so it does not add to the count */
}

/* THE BREAK, which is what weak_ptr is for. */
static void the_break()
{
    auto a = std::make_shared<Node>();
    std::weak_ptr<Node> w = a;
    a.reset();                        /* count 0: destroyed         */
    if (auto locked = w.lock()) {     /* lock() is the ONLY safe
                                         read: it succeeds only if
                                         the object is still alive */
        (void)locked;
    } else {
        std::puts("expired");
    }
}

/* THE PERFORMANCE ARGUMENT, which is measured rather than
   asserted: make_shared ONE allocation, unique_ptr(new T) TWO. */
static void the_allocation_count()
{
    auto a = std::make_shared<Widget>(1);
    auto b = std::shared_ptr<Widget>(new Widget(1));
    /* a: one block containing the control block AND the object.
       b: the object in one block, the control block in another.
       Two allocations instead of one, on every object. */
    (void)a; (void)b;
}

/* THE THREAD-SAFETY ARGUMENT: shared_ptr's reference count is
   atomic; the OBJECT it points at is not. Two threads sharing a
   shared_ptr and writing to the object are racing, and the shared
   pointer does not change that. */
static void threads_are_not_a_lock()
{
    static auto shared = std::make_shared<Widget>(0);
    std::mutex m;
    auto bump = [&] { std::lock_guard<std::mutex> g(m); ++shared->id; };
    /* the refcount is safe; the field needs the mutex, because
       the smart pointer synchronises LIFETIME, not ACCESS. */
    (void)bump;
}

4.1 Templates, deduction, and the two-phase lookup

A template is a code generator that the compiler runs once per distinct set of arguments, and almost every surprising thing about it comes from the fact that the body is compiled in a context where some names are not yet resolvable.

What happens when a template is instantiated

The compiler parses the template without knowing the arguments, then instantiates it when it sees a use. Names that do not depend on a template parameter are looked up at the point of definition, which means a helper function declared after the template is not found. Names that do depend on a parameter are looked up at the point of instantiation, which means two different uses can bind to two different functions. Then the four rules that follow, and each is a requirement. Put a call-dependent name in a dependent context, by writing template<typename T> before the call or by qualifying it with this->, so the lookup happens at instantiation. Template arguments are deduced from the call, and deduction has its own rules — a by-value parameter deduces a decayed type, so an array becomes a pointer and a const is dropped. Explicit template arguments must come before deduced ones, in a call, which is why the syntax looks odd. And Instantiation happens per distinct argument list, so a template in a header is instantiated in every translation unit that uses it, which is the whole mechanism behind header-only library compile times. Then the three things that go wrong, and each is a mechanism. A helper declared after the template, which fails with "was not declared in this scope" pointing at a line that looks correct. Deduction through a base class or a conversion, which does not happen — deduction is structural, so a function taking T will not accept a derived argument without a base reference or an explicit argument. And A template instantiated hundreds of times, which is invisible in the source and which is the reason a header-only library can take a minute to compile. Then the two practices, and both are disciplines. Constrain your templates with concepts rather than with static_assert inside them, because a concept is part of the signature and therefore participates in overload resolution. And Keep the template definition in a header, — which is not a style preference but a consequence of two-phase lookup, and which is why "explicit instantiation declaration" exists as the escape hatch.

#include <concepts>
#include <vector>

/* TWO PHASE LOOKUP: the body is parsed with the arguments UNKNOWN,
   which is the mechanism behind every surprising name-lookup error
   in templates.

   NAMES NOT DEPENDING ON A PARAMETER: looked up at the POINT OF
   DEFINITION. A helper declared after the template is not found.
   NAMES DEPENDING ON A PARAMETER: looked up at the POINT OF
   INSTANTIATION, so two uses can bind to two different functions. */

template<typename T>
static T twice(T v) { return v + v; }

/* THE FAILURE: the helper is declared BELOW. */
template<typename T>
static T bad(T v)
{
    /* helper(v);   -> "helper was not declared in this scope",
                       pointing at a line that looks correct      */
    return v;
}

template<typename T>
static T helper(T v) { return v; }

/* THE FIX: put the call in a dependent context. Either declare the
   template, or qualify with this->. */
template<typename T>
static T fixed(T v)
{
    template<typename U> static U helper(U x);
    return helper(v);
}

struct base   { int x() const { return 1; } };
struct derived : base {};

/* DEDUCTION IS STRUCTURAL. It does not walk base classes and does
   not apply user conversions. */
template<typename T> static int size_of(const T&) { return sizeof(T); }

static void deduction()
{
    derived d;
    /* size_of(d);       error: T deduces to derived, and the base
                         version does not match                 */
    int n = size_of(base{});       /* correct                    */
    (void)n;

    /* Arrays decay and const is DROPPED in a by-value parameter,
       which is the same rule as a plain function and surprises
       people who expected deduction to preserve them. */
    const int arr[4] = { 1, 2, 3, 4 };
    auto len = [](const auto& a) { return sizeof(a) / sizeof(a[0]); };
    /* len(arr) is 4 via const&. A by-value parameter would give
       sizeof(int*)/sizeof(int). */
}

/* EXPLICIT ARGUMENTS COME BEFORE DEDUCED ONES, which is why the
   syntax looks odd. */
template<typename T, typename U> static U cast(const T&) { return U{}; }
static void explicit_first()
{
    auto s = cast<double>(42);      /* T explicit, U deduced: no  */
    /* auto s2 = cast(42, double);   reads better, illegal       */
    (void)s;
}

/* Two disciplines. CONSTRAIN YOUR TEMPLATES with concepts rather
   than with a static_assert inside them, because a concept is part
   of the signature and therefore participates in overload
   resolution. And KEEP THE TEMPLATE DEFINITION IN A HEADER - not a
   style preference but a consequence of two-phase lookup, and the
   reason "explicit instantiation declaration" exists as the escape
   hatch for the rare case where you want it out of line. */

#include <concepts>
#include <vector>
#include <string>
#include <type_traits>

/* DEDUCTION: the type is taken from the argument, so the caller
   never names it. This is what makes a generic function usable
   without a cast at the call site. */
template <typename T>
constexpr bool is_power_of_two(T v) noexcept
{
    return v > 0 && (v & (v - 1)) == 0;
}

/* THE ARGUMENT IS NOT ANOTHER PARAMETER. Passing an array decays it
   to a pointer, which is why the size parameter cannot be deduced
   and must be explicit - the classic surprising deduction. */
template <typename T, std::size_t N>
constexpr std::size_t count_of(const T (&)[N]) noexcept { return N; }

static_assert(is_power_of_two(64));
static_assert(!is_power_of_two(63));
static_assert(count_of("hello") == 6);   /* 6 INCLUDING the NUL */

/* THE TWO PHASES, which is the one thing about templates that has to
   be understood rather than memorised. */
template <typename T>
void phase_two(T t) { t.member(); }        /* DEPENDENT: looked up
                                              at instantiation, and
                                              ordinary lookup ALSO
                                              applies            */
template <typename T>
struct Base { void member(); };

template <typename T>
struct Derived : Base<T>
{
    void call()
    {
        phase_two(*this);   /* phase one: Base<T>::member is NOT
                               found here by ordinary lookup, and
                               ADL does not apply to a base class -
                               so it FAILS unless you say
                               using Base<T>::member;             */
    }
};

/* THE FIX, and the fact that it is required is why two-phase
   lookup exists at all. */
template <typename T>
struct DerivedFixed : Base<T>
{
    using Base<T>::member;                 /* bring the base's names
                                              into the ordinary
                                              lookup set          */
    void call() { phase_two(*this); }
};

/* SFINAE, which is the mechanism underneath every trait in the
   standard library. */
template <typename T, typename = void>
struct has_size : std::false_type {};

template <typename T>
struct has_size<T, std::void_t<decltype(std::declval<const T &>().size())>>
    : std::true_type {};

static_assert(has_size<std::vector<int>>::value);
static_assert(!has_size<int>::value);

/* C++20 REPLACED IT WITH CONCEPTS, and the replacement is not
   cosmetic: the error is now a diagnostic that names the
   requirement, at the call, instead of a substitution failure
   somewhere in a declaration. */
template <std::integral T>
constexpr T clamp_positive(T v) noexcept
{
    return v < T{0} ? T{0} : v;
}

int main()
{
    /* call clamp_positive(1.5) and the compiler says: the value
       1.5 of type double does not satisfy the constraint
       std::integral. That message is the reason concepts exist. */
    return static_cast<int>(clamp_positive(-3));
}

4.2 Concepts: constraints that participate in overloads

A concept is a named, compile-time predicate over a type, and putting one in a signature turns a constraint from documentation into part of overload resolution.

What a concept buys over a static_assert

A static_assert inside a template body checks the constraint after the template has been selected, which means the failure is reported only if that overload was the best match — and if it was not, you get a confusing "no matching function" instead of the real reason. A concept appears in the signature, so an overload that requires Summable is not a candidate for an argument that is not summable, and a different overload is chosen instead. Then the four rules that follow, and each is a requirement. Write the concept in terms of an expression, using a requires clause, because the requirement is the expression the caller must be able to perform. Use concept-combinators to build hierarchies, so a constraint on strings and one on arithmetic compose into one on numbers. Keep concepts coarse, because a concept that constrains too finely partitions overload resolution into cases nobody designed. And Use std::same_as where identity matters, because it excludes derived types and is the mechanism behind many overload-resolution surprises. Then the three things that go wrong, and each is a mechanism. Constraining a parameter to a base class instead of a concept, which prevents a caller from passing a type that satisfies the requirement without inheriting. A concept that requires a conversion to succeed, which makes a concept depend on the overload set, and which can create a cycle the compiler diagnoses badly. And Concept-combining in a way that makes two overloads equally valid, which is ambiguity — and which concepts cannot fix, because ambiguity is a property of the two signatures and the concepts merely made both candidates. Then the two practices, and both are disciplines. Name concepts after the capability, not the type, — Summable rather than Numeric — because the capability is what a caller reads and the type list is what they will want to extend. And Start with one constraint per template and add only where a real overload ambiguity forced you to, because every constraint is a partition of the overload set and partitions accumulate.

#include <concepts>
#include <string>
#include <type_traits>

/* A concept is a named compile-time PREDICATE over a type. In a
   signature it is part of OVERLOAD RESOLUTION, not a check that runs
   after the overload was chosen. That difference is the whole
   argument. */

template<typename T>
concept Summable = requires(T a, T b) { a + b; };

/* A static_assert would check AFTER selection: */
template<typename T>
static T naively_sum(T a, T b)
{
    static_assert(Summable<T>);
    return a + b;
}
/* Call it with a string and an int. Overload resolution finds no
   match for naively_sum, because the two arguments have different
   types - fine. Call it through a template parameter whose
   instantiation happens with a non-summable type and you get the
   static_assert. The problem case is when a DIFFERENT overload
   exists: the constraint makes that overload ineligible instead of
   reporting why the intended one did not apply.               */

template<Summable T> static T sum(T a, T b) { return a + b; }

/* CONCEPT COMBINATORS build a hierarchy, so a constraint on strings
   and one on arithmetic compose into one on numbers. */
template<typename T> concept Streamable  = requires(T& s, const T& c) {
    { s << c } -> std::convertible_to<std::ostream&>;
};
template<typename T> concept Formattable  = Streamable<T> && Summable<T>;

static_assert(Summable<int>);
static_assert(Summable<double>);
static_assert(!Summable<int*>);      /* pointer arithmetic is not */
static_assert(!Summable<std::string>);  /* it does not add       */

/* same_as EXCLUDES DERIVED TYPES, and that exclusion is the
   mechanism behind a whole family of overload-resolution
   surprises: it is how you make an overload EXACT rather than
   "anything convertible". */
static std::string describe(std::string s)   { return "string " + s; }
static std::string describe(const char* s)   { return "cstr " + std::string(s); }
/* void* would be ambiguous with both without a concept; a concept
   fixes it.                                                  */

static void constraints()
{
    /* Each call resolves at COMPILE TIME to the overload whose
       concept the argument satisfies. No runtime cost, and the
       error for a non-summable type names the concept. */
    (void)sum(1, 2);
    (void)sum(1.5, 2.5);
    /* sum("a", "b");   error: the constraint on T fails, and the
                         message names Summable rather than "the
                         operator + is not defined for const
                         char*" - which is the whole point.     */
}   /* THE THREE FAILURES.
   1. CONSTRAINING A PARAMETER TO A BASE CLASS instead of a
      concept: it prevents a caller from passing a type that
      SATISFIES the requirement without inheriting.
   2. A CONCEPT THAT REQUIRES A CONVERSION to succeed: it makes the
      concept depend on the overload set, and a cycle here is
      diagnosed badly by every compiler.
   3. CONCEPT-COMBINING that makes two overloads EQUALLY VALID:
      ambiguity, which concepts cannot fix, because ambiguity is a
      property of the two signatures and the concepts merely made
      both candidates.

   Two disciplines. NAME CONCEPTS AFTER THE CAPABILITY, not the
   type - Summable rather than Numeric - because the capability is
   what a caller reads and the type list is what they will want to
   extend. And START WITH ONE CONSTRAINT PER TEMPLATE, adding more
   only where a real overload ambiguity forced you to, because every
   constraint is a partition of the overload set and partitions
   accumulate. */

#include <concepts>
#include <vector>
#include <string>
#include <numeric>

/* A CONCEPT IS A PREDICATE OVER TYPES, and it participates in
   overload resolution. That second half is the difference between
   a concept and a static_assert. */

template <typename T>
concept Streamable = requires(std::ostream &out, const T &v) {
    { out << v } -> std::same_as<std::ostream &>;   /* the RETURN
                                                       type is part
                                                       of the
                                                       requirement  */
};

/* A CONCEPT CAN BE COMPOSED, so a constraint reads as a
   specification rather than as an expression. */
template <typename T>
concept Sized = requires(const T &v) { v.size(); };

template <typename T>
concept SizedIterable = Sized<T> && requires(const T &v) {
    v.begin(); v.end();
};

template <SizedIterable T>
[[nodiscard]] std::size_t count_elements(const T &c)
{
    return static_cast<std::size_t>(std::distance(c.begin(), c.end()));
}

/* OVERLOADING ON A CONCEPT: two functions, same name, different
   constraints. The call is resolved because the argument satisfies
   one and not the other - which no amount of enable_if reads as
   clearly. */
template <std::integral T>
[[nodiscard]] int describe(T v) { return static_cast<int>(v) * 2; }

template <std::floating_point T>
[[nodiscard]] int describe(T v) { return static_cast<int>(v) + 1; }

/* AMBIGUITY IS THE PRICE, and it is diagnosed at the call rather
   than producing a silently wrong overload. */
template <typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;

template <Numeric T>
[[nodiscard]] T add(T a, T b) { return a + b; }

/* WHAT A CONCEPT CANNOT DO, which is worth knowing before reaching
   for one: it cannot express a runtime condition, it cannot be
   overloaded by the caller, and a satisfied concept says nothing
   about cost. A concept that is expensive to satisfy is checked
   once, at instantiation, so the check itself is not a run-time
   cost - but the property it verified may well be. */

int main()
{
    std::vector<int> v{1, 2, 3};
    count_elements(v);
    describe(21);      /* integral   -> * 2 = 42 */
    describe(1.5);     /* floating   -> + 1 = 2  */
    add(2, 3);
}

5.1 Containers: the four questions that pick one

There are six containers that cover almost every use, and choosing between them is four questions rather than a preference.

Four questions

Do you need random access by index? Then it is a vector or a deque. Do you need cheap insert and erase in the middle? Then it is a list. Do you need to look elements up by key? Then it is an unordered map. Do you need sorted iteration? Then it is a map or a set. Then the four things to know, and each is a requirement. A vector's elements are contiguous, so index access is a pointer add and every other operation benefits from cache locality — which is why a vector of small objects beats a list of pointers almost every time. A vector reallocates on growth and MOVES every element, so an element's address is invalidated, which is why a pointer or reference into a vector is a thing you must not keep across a push. An unordered_map does not preserve order and its iteration order depends on the hash, so a bug that reproduces with one set of keys and not another is usually this. And A deque does not invalidate references on push at the end, which is its one advantage over a vector and the only reason to choose it. Then the three things that go wrong, and each is a mechanism. A reference into a vector kept across a push_back, which is a use-after-free after the reallocation. Erasing from a vector while iterating it, which skips an element because the indices shifted. And Assuming unordered_map iteration is stable, which it is not even across two runs of the same program if anything inserted a different number of elements. Then the two practices, and both are disciplines. Reserve when you know the size, because it removes the reallocations and therefore the copies and the invalidations in one line. And Erase by iterator in a loop, and use the returned iterator to advance, because the return value is the next valid position and it is the only thing that knows where the container moved the elements.

#include <list>
#include <map>
#include <string>
#include <unordered_map>
#include <vector>

/* FOUR QUESTIONS THAT PICK THE CONTAINER.
   Random access by index?          vector or deque
   Cheap insert/erase in the middle? list
   Look up by key?                   unordered_map
   Sorted iteration?                map or set                     */

/* 1. A vector's ELEMENTS ARE CONTIGUOUS, so index access is a
   pointer add and everything else benefits from cache locality -
   which is why a vector of small objects beats a list of pointers
   almost every time. */
struct point { int x, y; };
static std::vector<point> pts;      /* contiguous: one cache line
                                       serves several elements   */

/* 2. A vector REALLOCATES ON GROWTH and MOVES every element, so
   addresses are invalidated. A pointer or reference into a vector
   must not survive a push_back. */
static void invalidation()
{
    std::vector<int> v{ 1, 2, 3 };
    int& first = v[0];
    /* v.push_back(4);  <-- reallocation may move everything, and
                           first now refers to the OLD storage.
                           The value is usually still readable,
                           which is what makes it dangerous.   */
    (void)first;

    /* The exception to the exception: std::deque does NOT
       invalidate references on push at the end, which is its one
       advantage over a vector and the only reason to choose it. */
    std::deque<int> d;
    int& f0 = d[0];
    d.push_back(1);
    (void)f0;
}

/* 3. AN unordered_map DOES NOT PRESERVE ORDER, and its iteration
   order depends on the hash and on the table's history of
   insertions. A bug that reproduces with one set of keys and not
   another is usually this. */
static std::unordered_map<std::string, int> counts;

/* THE THREE FAILURES.
   1. A REFERENCE INTO A VECTOR KEPT ACROSS push_back: a
      use-after-free after the reallocation.
   2. ERASING FROM A VECTOR WHILE ITERATING: the indices shift and
      you skip an element - the loop is correct-looking and misses
      every second match.
   3. ASSUMING unordered_map ITERATION IS STABLE: it is not, even
      between two runs of the same program if anything inserted a
      different number of elements. */

static void erase_while_iterating()
{
    std::vector<int> v{ 1, 2, 3, 4, 5, 6 };

    /* WRONG: erases 2 and 4, leaves 1,3,5,6 - and the intent was
       to remove all the even numbers, which it accidentally does.
       Change the predicate and it silently misses. */
    for (size_t i = 0; i < v.size(); ++i)
        if (v[i] % 2 == 0) v.erase(v.begin() + i);   /* skips    */

    /* RIGHT: the erase-remove idiom, or C++20's erase_if. */
    v.erase(std::remove_if(v.begin(), v.end(),
                           [](int x) { return x % 2 == 0; }), v.end());
    /* C++20: std::erase_if(v, pred);  - and it returns the count */
}

/* Two disciplines. RESERVE WHEN YOU KNOW THE SIZE, because it
   removes the reallocations and therefore the copies and the
   invalidations in one line. And ERASE BY ITERATOR IN A LOOP and
   use the RETURNED ITERATOR to advance, because that value is the
   next valid position and it is the only thing that knows where
   the container moved the elements to. */

#include <vector>
#include <deque>
#include <list>
#include <map>
#include <unordered_map>
#include <set>
#include <string>
#include <array>
#include <memory>
#include <iostream>

/* THE FOUR QUESTIONS, each of which eliminates most of the
   candidates before you look at any documentation. */

/* 1. IS THE ORDER MEANINGFUL? If not, unordered. */
static std::unordered_map<std::string, int> counts;   /* hash, no order */

/* 2. DO I LOOK THINGS UP BY KEY? If yes, a map - and then, does
      iteration order matter? Ordered costs a tree walk per insert. */
static std::map<std::string, int> ordered;

/* 3. IS IT AT BOTH ENDS? deque. A vector cannot push_front without
      moving every element, which is why the operation everyone
      reaches for is the one it cannot do cheaply. */
static std::deque<int> window;

/* 4. DO I NEED STABLE REFERENCES ACROSS INSERTION? list - and
      here is the honest reason almost nobody uses it: the node
      allocation per element costs more than the contiguous layout
      buys, so a vector plus indices is faster in practice. */
static std::list<int> stable_but_slow;

/* THE CHOICE AS A TABLE, which is the form worth memorising:
   vector   contiguous, O(1) random access, cheap insert at END
   deque    segmented, O(1) at BOTH ends, no pointer invalidation
   list     linked, O(1) insert ANYWHERE if you have an iterator
   map      balanced tree, O(log n) lookup, ORDERED iteration
   unordered_map  hash, O(1) average, iteration in bucket order
   array    contiguous, size FIXED at compile time, no allocation */

/* ITERATOR INVALIDATION, the thing that decides whether a piece of
   code works. */
static void the_invalidation_rules()
{
    std::vector<int> v{1, 2, 3};

    /* vector: ANY reallocation invalidates EVERY iterator and
       reference. Reserving is not a fix for the rule - it is a way
       of knowing when the reallocation happens. */
    v.push_back(4);                  /* may reallocate            */
    for (int *p = v.data(); p; ++p) { (void)*p; }

    /* erase invalidates the erased element's iterator and all
       AFTER it, and nothing before it. */
    v.erase(v.begin());              /* v.begin() onwards dead     */

    /* deque: push_front/push_back invalidate ITERATORS but not
       REFERENCES to existing elements. The distinction is real and
       it is why a deque is the container of choice for a queue
       that stores pointers into itself. */
    std::deque<std::shared_ptr<int>> q;
    q.push_front(std::make_shared<int>(1));
    /* auto ref = *(q.begin()); q.push_back(x); -- ref still valid */

    /* map/unordered: erase invalidates only the erased iterator.
       This is why an associative container is pleasant to mutate. */
    std::map<int, int> m{{1, 1}};
    for (auto it = m.begin(); it != m.end();) {
        if (it->first == 1) it = m.erase(it);   /* erase RETURNS
                                                       the next
                                                       iterator, so
                                                       the loop is
                                                       safe        */
        else ++it;
    }
}

/* AND THE ONE THAT CATCHES PEOPLE: iterating a map and modifying a
   VALUE is fine. Modifying a KEY is not, because it changes the
   ordering the iterator is walking. */
static void value_edit_is_fine(std::map<int, int> &m)
{
    for (auto &[k, v] : m) { v = k * 2; }      /* fine             */
    /* for (auto &[k, v] : m) { m[k * 2] = v; }  key changed: the
                                                    next ++ steps
                                                    into whatever
                                                    is now there   */
}

5.2 Algorithms: why a range beats a loop

An algorithm takes a range rather than a container, which means it cannot know the container's size — and that one constraint is what makes them composable, testable and worth reading.

The shape of every algorithm

A standard algorithm takes a pair of iterators delimiting a range and operates on that range. It does not know the container's size, so it works on a sub-range of a vector, a linked list, or a raw array without change. It does not know the element type, so it works on any type whose iterators satisfy the concept. And it returns an iterator or a value rather than modifying the container, which is why an algorithm that removes does so as a range and leaves you to erase. Then the four rules that follow, and each is a requirement. End iterators are computed once and reused, because a range whose end is computed from the container each iteration re-evaluates the size and is wrong for the algorithms that mutate. Algorithms that sort or partition require random-access iterators, so they do not work on a list — which is the reason a list has its own member sort. An algorithm that removes returns the new end, not the number removed, and that new end is what you pass to erase. And Algorithms are stable where the standard says so, so equal elements keep their relative order, which is the property that makes partition-then-erase predictable. Then the three things that go wrong, and each is a mechanism. Using an algorithm on a temporary range, which is fine until you compute the end separately from a temporary. Sorting with a comparator that is not a strict weak ordering, which is undefined behaviour and the mechanism behind a sort that crashes or produces garbage. And Using std::sort on a list, which does not compile, and the error message does not mention lists. Then the two practices, and both are disciplines. Prefer an algorithm to a hand-written loop whenever one fits, because the standard library's version is faster, correct for the empty and singleton cases, and tested. And When you write a loop that a visitor pattern is pretending to be, use a fold expression or a range adaptor instead, because the library's version has the edge cases handled and yours will not.

#include <algorithm>
#include <numeric>
#include <string>
#include <vector>

/* AN ALGORITHM TAKES A RANGE, not a container, and that single
   constraint is why they compose, work on sub-ranges, and are
   worth reading rather than rewriting. */

/* RULE 1: END ITERATORS ARE COMPUTED ONCE AND REUSED. A range
   whose end is recomputed each iteration re-evaluates the size and
   is wrong for every algorithm that mutates. */
static void ranges()
{
    std::vector<int> v{ 5, 3, 1, 4, 2 };
    auto first = v.begin();
    auto last  = v.end();

    auto mid = std::partition(first, last, [](int x) { return x < 3; });
    /* std::sort(first, last);   WRONG: last is no longer the end -
                                     only mid is, and sorting
                                     past the partition reads
                                     elements that were swapped */
    std::sort(first, mid);
    std::sort(mid, last);
    (void)v;
}

/* RULE 2: ALGORITHMS THAT SORT OR PARTITION REQUIRE RANDOM-ACCESS
   ITERATORS, so they do not work on a list - which is why a list
   has its own member sort. The error message does not mention
   lists. */
static void random_access_only()
{
    std::vector<int> v{ 3, 1, 2 };
    std::sort(v.begin(), v.end());     /* fine: contiguous        */

    std::list<int> l{ 3, 1, 2 };
    /* std::sort(l.begin(), l.end());  does not compile          */
    l.sort();                           /* the member function    */
}

/* RULE 3: AN ALGORITHM THAT REMOVES RETURNS THE NEW END, not the
   number removed. That value is what erase takes. */
static void remove_erase(const std::vector<std::string>& in,
                         std::vector<std::string>& out)
{
    out = in;
    auto new_end = std::remove_if(out.begin(), out.end(),
        [](const std::string& s) { return s.empty(); });
    out.erase(new_end, out.end());      /* the two-call idiom      */

    /* C++20 collapses it: */
    /* std::erase_if(out, [](const auto& s) { return s.empty(); }); */
}

/* THE THREE FAILURES.
   1. USING AN ALGORITHM ON A TEMPORARY RANGE - fine until you
      compute the end separately from a temporary.
   2. SORTING WITH A COMPARATOR THAT IS NOT A STRICT WEAK ORDERING:
      undefined behaviour. This is the mechanism behind a sort
      that crashes, or that produces a garbage order that looks
      plausible. 'return a < b' is correct; 'return a <= b' is not. */
static void strict_weak_ordering()
{
    std::vector<int> v{ 3, 1, 2, 1 };
    std::sort(v.begin(), v.end(), [](int a, int b) {
        return a <= b;                  /* WRONG: not irreflexive */
    });
    /* The rule: irreflexive (a<a is false), asymmetric, and
       transitive. A comparator failing any of these makes sort's
       behaviour undefined, and the compiler cannot help.          */
    std::sort(v.begin(), v.end(), [](int a, int b) { return a < b; });
}

/* Two disciplines. PREFER AN ALGORITHM TO A HAND-WRITTEN LOOP
   whenever one fits, because the library's version is faster,
   correct for the empty and single-element cases nobody remembers
   to handle, and tested. And WHEN YOU WRITE A LOOP THAT A VISITOR
   PATTERN IS PRETENDING TO BE, use a fold expression or a range
   adaptor - the library's version has the edge cases handled and
   yours will not. */

#include <algorithm>
#include <numeric>
#include <vector>
#include <string>
#include <ranges>
#include <iostream>

/* THE SHAPE OF EVERY LOOP ALGORITHMS REMOVE. */
static void four_loops_one_shape()
{
    std::vector<int> v{5, 3, 9, 1};
    std::string s{"olleh"};

    /* INDEX: positional, and the index is the only thing saying
       which element you are on. */
    for (std::size_t i = 0; i < v.size(); ++i) v[i] *= 2;

    /* ITERATOR: sequential, works on any forward range, and the
       three container types have different invalidation rules -
       which is the bug a generic loop hides. */
    for (auto it = v.begin(); it != v.end(); ++it) *it += 1;

    /* RANGE: no iterator to get wrong, and the type of the loop
       variable is the element type - so a mistake is a compile
       error. */
    for (int &x : v) x -= 1;

    /* ALGORITHM: the intent is in the NAME, which is the real
       benefit. "make it sorted" says more than the loop that
       achieves it. */
    std::sort(v.begin(), v.end());
    std::sort(s.rbegin(), s.rend());      /* reverse, no new container */

    /* PROJECTION, where a heterogeneous range would otherwise need
       a temporary vector of pairs. */
    std::vector<std::string> names{"al", "alexander", "bob"};
    std::sort(names.begin(), names.end(),
              [](const auto &a, const auto &b) { return a.size() < b.size(); });
}

/* C++20 RANGES: the algorithm takes the RANGE, not a pair of
   iterators, so the range and its bounds cannot be mismatched -
   which is a mistake a raw-iterator call can make and a human
   reads as obviously fine. */
static void ranges_and_views()
{
    std::vector<int> v{1, 2, 3, 4, 5, 6, 7, 8};

    auto evens = v | std::views::filter([](int x) { return x % 2 == 0; })
                   | std::views::transform([](int x) { return x * 10; });

    for (int x : evens) std::cout << x << ' ';    /* 20 40 60 80 */
    std::cout << '\n';

    /* LAZY: nothing runs until iteration, and nothing is
       materialised. The three stages above execute ONE pass over
       v, and if you never iterate, none of them runs. */
}

/* THE TRANSFORM A LOOP CANNOT EXPRESS, which is the honest reason to
   reach for an algorithm. */
static void the_reduce_case()
{
    std::vector<int> v{1, 2, 3};

    /* A loop says: accumulate. fold says: combine left to right,
       with the identity made explicit, and it is EXACTLY the same
       operation - so the loop can be replaced without a behaviour
       change and the accumulator's initial value is named. */
    int total = std::accumulate(v.begin(), v.end(), 0);

    /* transform_exclusive_scan is a prefix sum, and writing one as
       a loop is where off-by-one errors come from. */
    std::vector<int> prefix(v.size());
    std::partial_sum(v.begin(), v.end(), prefix.begin());

    /* The three that pay for themselves repeatedly: transform,
       accumulate, and remove_if - because all three state an
       intent, and all three are correct in the edge cases you would
       have to handle by hand. */
    std::vector<int> doubled(v.size());
    std::transform(v.begin(), v.end(), doubled.begin(),
                   [](int x) { return x * 2; });
}

/* WHERE AN ALGORITHM IS THE WRONG TOOL, so the rule has an edge: a
   loop that needs to touch two sequences in step, or that depends
   on the previous element, is clearer as a loop. */
static void the_pairwise_case(const std::vector<int> &a, const std::vector<int> &b)
{
    std::vector<int> diff(a.size());
    /* transform does not know the two are the same length, so it
       reads b past its end without complaint. A loop, or a size
       check first, is the honest form. */
    if (a.size() == b.size()) {
        std::transform(a.begin(), a.end(), b.begin(), diff.begin(),
                       [](int x, int y) { return x - y; });
    }
}

5.3 Strings, streams and formatting

The three string types and the two formatting systems each have a different cost model, and choosing by convenience rather than by cost is how a service ends up spending eighty per cent of its time in string handling.

Three strings, three cost models

std::string owns a heap buffer, is null-terminated, and every append may reallocate. std::string_view points at somebody else's bytes and costs nothing to create, which makes it the right parameter type for a read-only string and completely the wrong one for a member. std::array<char, N> is inline, fixed-size and does not allocate. Then the four things to know, and each is a requirement. A string_view does not own its characters, so a view into a temporary is a dangling view — the single most common defect in modern C++. A string's append is amortised constant time, because the buffer doubles, so a loop of a hundred thousand appends is not quadratic. Small strings are stored inline, which means a string under about fifteen characters never allocates at all, and a program full of short strings is faster than one that assumes otherwise. And Stream formatting is slow, measurably so, because a stream goes through a virtual dispatch per field and a locale lookup per character. Then the three things that go wrong, and each is a mechanism. Keeping a string_view into a temporary, which is the dangling-view case. Passing a string_view to an API that stores it, which requires the callee to copy and the compiler cannot tell you it did not. And Formatting in a loop, which is the mechanism behind a log statement that costs more than the work it describes. Then the two practices, and both are disciplines. Take string_view by default for a read-only parameter, because it accepts a string and a literal for free and cannot be the dangling owner. And Reserve when you know a string's final size, which removes the reallocations and the copies they involve.

#include <array>
#include <charconv>
#include <format>
#include <string>
#include <string_view>

/* THREE STRINGS, THREE COST MODELS.
   std::string            owns a heap buffer, null-terminated, every
                          append MAY reallocate
   std::string_view       points at somebody else's bytes, costs
                          nothing to create
   std::array<char, N>    inline, fixed size, never allocates      */

static void rule_one()
{
    /* A string_view does NOT OWN its characters. This is the single
       most common defect in modern C++. */
    std::string_view dangling = std::string("temporary");  /* WRONG */
    /* 'dangling' now points at a destroyed string. Reading it is
       use-after-free, and it may read correctly because the stack
       memory has not been overwritten yet.                      */
    (void)dangling;

    /* The rule: a view's lifetime must be SHORTER than the thing
       it views. A function taking a string_view promises its caller
       nothing about storing it. */
}

/* THE PARAMETER TYPE IS THE COMMUNICATION. string_view in the
   signature says "read only, and I do not keep it"; const string&
   says "read only, and you may pass a temporary". */
static size_t count_words(std::string_view s)
{
    size_t n = 0;
    for (char c : s) if (c == ' ') ++n;
    return n + 1;
}   /* accepts a string, a literal, or a substring - all free */

/* THE THREE FAILURES.
   1. KEEPING A string_view INTO A TEMPORARY.
   2. PASSING A string_view TO AN API THAT STORES IT: the callee
      must copy, and nothing tells you it did not.
   3. FORMATTING IN A LOOP: stream formatting goes through virtual
      dispatch per field and a locale lookup per character, which
      is the mechanism behind a log statement that costs more than
      the work it describes.                                     */

/* The modern formatter is not a stream and is much faster. */
static void fast_format(std::string& out, int id, double score)
{
    /* Compiles to a direct byte sequence. No stream, no locale,
       and the format string is CHECKED AT COMPILE TIME. */
    out = std::format("user {} scored {:.2f}", id, score);

    /* Parse without allocating at all: from_chars writes into your
       buffer and reports what it consumed, and it never throws. */
    char buf[32];
    auto [ptr, ec] = std::from_chars(buf, buf + sizeof buf, score);
    if (ec == std::errc{}) { (void)ptr; }

    /* to_chars is the output direction and is the allocation-free
       counterpart. */
    auto [end, ec2] = std::to_chars(buf, buf + sizeof buf, id);
    if (ec2 == std::errc{}) { *end = ''; }
}

/* RULE 2: AN APPEND IS AMORTISED CONSTANT TIME because the buffer
   doubles - so a loop of a hundred thousand appends is NOT
   quadratic, and pre-reserving is a constant-factor win rather than
   a complexity fix. */
static void reserve_wins()
{
    std::string slow, fast;
    for (int i = 0; i < 100000; ++i) slow += "x";     /* fine     */

    fast.reserve(100000);                                /* one      */
    for (int i = 0; i < 100000; ++i) fast += "x";      /* better   */
}  /* RULE 3: SMALL STRINGS ARE STORED INLINE - about fifteen
     characters - so a program full of short strings never allocates
     for any of them, which is why a struct with a string member is
     not necessarily an expensive struct.

     Two disciplines. TAKE string_view BY DEFAULT for a read-only
     parameter, because it accepts a string and a literal for free
     and cannot be the dangling owner. And RESERVE WHEN YOU KNOW A
     STRING'S FINAL SIZE, which removes the reallocations and the
     copies they involve. */

#include <string>
#include <string_view>
#include <sstream>
#include <iostream>
#include <charconv>
#include <iomanip>

/* THE FIVE THINGS THAT GO WRONG WITH std::string, and the type that
   fixes each one. */

/* 1. THE ALLOCATION. string_view is a pointer and a length with NO
      ownership, so passing one allocates nothing. */
static std::size_t find_char(std::string_view text, char c)
{
    auto at = text.find(c);
    return at == std::string_view::npos ? 0 : at;
}

/* THE HAZARD, and it is the reason a string_view parameter has to
   be thought about: a view does not own, so the thing it points at
   must outlive it. A view into a TEMPORARY is a dangling pointer
   the moment the full expression ends. */
static std::string_view the_dangling_case()
{
    std::string local = "hello";
    return local;              /* local is destroyed on return:
                                   the view outlives its data   */
    /* Fix: return std::string, and let the caller own it. */
}

/* 2. THE SUBSTRING COPIES. substr allocates; string_view does not. */
static std::string_view cheap_slice(std::string_view s)
{
    return s.substr(4, 8);      /* NO allocation: a pair of
                                   pointers, or a pointer and a
                                   length, into the ORIGINAL       */
}

/* 3. THE NUMBER PARSE. stoi allocates, throws, and has no error
      position. from_chars has neither problem. */
static bool parse_int(std::string_view text, int &out)
{
    const char *first = text.data();
    const char *last  = first + text.size();
    auto [ptr, ec] = std::from_chars(first, last, out);
    return ec == std::errc{} && ptr == last;   /* BOTH: a trailing
                                                   "12abc" must be
                                                   a failure, and
                                                   without the ptr
                                                   check it is a
                                                   success        */
}

/* 4. THE FORMATTING. ostream is SLOW - it goes through a virtual
      locale facet for every field - and it is the reason a logging
      call can dominate a hot path. std::format is neither. */
static void the_formatting_cost()
{
    /* SLOW: a locale lookup per field, plus a sentry per insertion */
    std::ostringstream os;
    os << "user " << id << " scored " << score << '\n';

    /* FAST, and type-checked at compile time: a wrong argument type
       is a compile error rather than a surprising runtime value. */
    std::string line = std::format("user {} scored {}", id, score);

    /* For fixed-width hexadecimal, the stream way and the fast way. */
    char buf[32];
    std::snprintf(buf, sizeof buf, "%08x", value);   /* needs a
                                                          buffer and
                                                          a check   */
    (void)os; (void)line; (void)buf;
}

/* 5. THE ENCODING. string is BYTES, and on Windows a narrow string
      is the active code page rather than UTF-8, so the same bytes
      mean different characters on the two platforms. */
static void the_encoding_trap()
{
    std::string utf8 = "caf\xc3\xa9";            /* UTF-8  */
    /* On Windows, this is NOT necessarily five characters: the
       narrow string functions interpret it in the active code
       page. Everything crossing a process or a file boundary must
       be UTF-8 by decision, not by platform default. */
    std::wstring wide = L"caf\u00e9";
    (void)utf8; (void)wide;
}

/* THE PRACTICAL SET. Use string for owned text, string_view for
   every function parameter that only reads, ostream for streams
   that genuinely stream, from_chars for parsing, and format for
   composing. Reach for the stream operators when you are debugging
   and for nothing else in a hot path. */

6.1 Three error strategies and the one that is wrong in production

C++ gives you four ways to report a failure and the choice between them is a design decision with real performance consequences, because exceptions are not free even when they are not thrown.

The four, and what each costs

A return value — an optional, a result type, or a status enum. An exception, which unwinds and runs destructors. An assertion, for a violated invariant rather than a bad input. Termination, for a situation the program cannot recover from. Then the four things to know, and each is a requirement. Throwing costs more than returning even when nothing is thrown, because the compiler must emit unwind tables and may inhibit certain optimisations — which is why a hot path returns and a cold path throws. An exception unwinds and guarantees every destructorer between the throw and the catch runs, which is the property that makes exceptions exception-safe and is the reason RAII is not optional in this language. An assertion is not an input check, and using one for input validation means your program's behaviour depends on whether it was compiled with them enabled. And Catching ... is almost always wrong, because it catches the programming errors you wanted to crash on. Then the three things that go wrong, and each is a mechanism. Throwing in a destructor, which terminates the program if it happens during unwinding. A noexcept function that throws, which terminates. And Catching by value, which slices the exception and loses whatever the derived part carried. Then the two practices, and both are disciplines. Return an expected result for anything the caller can act on, and throw only across an API boundary for something genuinely exceptional, which keeps the hot path free of unwind machinery. And Catch by const reference and rethrow deliberately when you are not handling it, so that adding a wrapper cannot accidentally swallow an error.

#include <optional>
#include <stdexcept>
#include <string>

/* FOUR WAYS TO REPORT A FAILURE, and the choice is a design
   decision with real performance consequences. */

/* 1. A RETURN VALUE: optional, a result type, a status enum. */
static std::optional<int> parse(const std::string& s)
{
    if (s.empty()) return std::nullopt;
    return 0;
}

/* 2. AN EXCEPTION, which unwinds and RUNS DESTRUCTORS. That is
   the property that makes the language exception-safe, and the
   reason RAII is not optional in it. */
static int checked_div(int a, int b)
{
    if (b == 0) throw std::invalid_argument("division by zero");
    return a / b;
}
static void unwinding_demo()
{
    auto g = std::make_unique<shape>();   /* acquired             */
    throw std::runtime_error("x");        /* ~g runs on the way   */
}   /* THAT is what an exception buys: every object constructed
     after 'g' and before the throw is destroyed, in reverse. No C
     equivalent exists, which is why every C error path is a leak
     waiting for the next early return.                          */

/* 3. AN ASSERTION, for a violated INVARIANT rather than a bad
   input. Using one for input validation means your program's
   behaviour depends on whether it was compiled with them on. */
static int confirmed(int n)
{
    assert(n >= 0);            /* our bug, not the caller's      */
    if (n < 0) return -1;       /* the caller's problem           */
    return n;
}

/* THE THREE FAILURES.
   1. THROWING IN A DESTRUCTOR: if it happens during unwinding,
      the program calls terminate.
   2. A noexcept FUNCTION THAT THROWS: terminate. The annotation
      is a promise and breaking it is not a warning. */

/* Throwing COSTS MORE THAN RETURNING even when nothing is thrown:
   unwind tables must be emitted and some optimisations are
   inhibited. That is why a HOT PATH RETURNS and a COLD PATH
   THROWS, and it is a performance fact, not a style preference. */
static void hot_path(int a, int b)
{
    if (b == 0) return;        /* expected: return              */
    consume(a / b);
}
static void cold_path(const Config& c)
{
    if (!c.valid) throw std::runtime_error("bad config");  /* rare  */
    start(c);
}

/* 4. CATCHING BY VALUE SLICES the exception and loses whatever the
   derived part carried - which is usually the diagnostic detail. */
static void catch_by_reference()
{
    try {
        throw std::runtime_error("connection refused: port 5432");
    }
    catch (const std::exception& e) {   /* by const reference    */
        log(e.what());                  /* the message survives   */
    }
    /* catch (...)  ALMOST ALWAYS WRONG: it catches the out_of_memory
       and the bad_cast you wanted to CRASH on, and continues as
       though nothing happened.                                          */
}

/* Two disciplines. RETURN AN EXPECTED RESULT for anything the
   caller can act on, and THROW ONLY ACROSS AN API BOUNDARY for
   something genuinely exceptional, which keeps the hot path free of
   unwind machinery. And CATCH BY CONST REFERENCE AND RETHROW
   DELIBERATELY when you are not handling it, so that adding a
   wrapper cannot accidentally swallow an error. */

#include <optional>
#include <variant>
#include <stdexcept>
#include <string>
#include <string_view>
#include <system_error>
#include <iostream>

/* THE FOUR SHAPES, and what each is actually for. */

/* 1. optional: "no value", and only no value. */
static std::optional<int> lookup(int key)
{
    if (key < 0) return std::nullopt;
    return key * 2;
}

/* 2. THE STATUS OUT-PARAMETER: success plus a reason, in types
      that cannot be confused. */
struct Status {
    std::error_code code;
    std::string     context;
    explicit operator bool() const noexcept { return !code; }
};

static Status read_config(std::string_view path)
{
    if (path.empty()) return { std::make_error_code(std::errc::invalid_argument),
                               "empty path" };
    return {};
}

/* 3. THE EXPECTED-LIKE VARIANT: a value OR an error, both typed. */
using ParseResult = std::variant<int, std::string>;   /* the error is
                                                           a string,
                                                           which is
                                                           a
                                                           compromise  */

static ParseResult parse(std::string_view s)
{
    if (s.empty()) return std::string("empty input");
    return std::stoi(std::string(s));
}

/* 4. EXCEPTIONS: for failures the caller cannot sensibly handle at
      this level, and that should be rare enough to document. */
static void reserves_memory()
{
    throw std::runtime_error("cannot continue without a buffer");
}

/* THE ONE THAT IS WRONG IN PRODUCTION: throwing across a noexcept
   boundary, and throwing to signal a control path. */
static void throwing_across_noexcept()
{
    try {
        /* A callback declared noexcept, called with a callback that
           throws. The exception is NOT propagated: std::terminate
           is called and the process dies with no diagnostic about
           what was being attempted. Declare the boundary noexcept
           only if nothing can throw inside it. */
        auto callback = []() noexcept { reserves_memory(); };
        callback();
    } catch (...) { /* never reached: terminate already ran */ }
}

/* THE RULE THAT DECIDES IT: WHO CAN DO ANYTHING ABOUT IT? If a
   caller has an alternative - a default, a retry, a different
   algorithm - the failure is a return value. If every caller would
   do the same thing, which is almost always "abort with a
   message", it is an exception, and it should be thrown at the
   boundary where you are about to abort rather than at the point
   where it was detected. */

/* THE COST, which is why the answer is "rarely": an exception
   unwinds the stack, running every destructor on the way. That is
   correct and it is not free - it is tens of microseconds, against
   a nanosecond for a branch. So the rule is not "never"; it is
   "never on a path that runs often". */
static void the_cost()
{
    try { if (something_unusual()) throw std::runtime_error("rare"); }
    catch (const std::exception &e) { (void)e; }
}

6.2 Concurrency: the four tools and the rule that matters

C++20 gave the language a memory model, which is a real advance — and the rule that comes with it is that the cost model of a primitive is not the one you would guess from its interface.

Four tools

An atomic for a single value. A mutex for an invariant involving more than one. A condition variable for waiting, with the same shutdown problem C has. An atomic wait or a semaphore for blocking without a mutex. Then the four things to know, and each is a requirement. Atomics have three memory orderings and only two of them are usually right, — relaxed for a counter nobody interprets, and acquire/release for publication. A mutex is the correct default, because it makes a set of reads and writes atomic as a group and atomics only make each field atomic. A condition variable wait must be in a loop, because a notification can arrive between the check and the wait and the condition can be false again when you wake. And Every thread needs a shutdown path, which is the same lifetime problem as signals in C and has the same answer: a flag plus a condition. Then the three things that go wrong, and each is a mechanism. An atomic used as a lock, which serialises nothing unless the read-modify-write is a compare-and-swap loop. Publishing data before the flag, which is the classic bug the release ordering exists to prevent. And Joining a thread that is blocked in a wait with no exit, which is a program that cannot be stopped. Then the two practices, and both are disciplines. Reach for a mutex first and drop to an atomic only when you can name the invariant it preserves, because a mutex is correct in every case. And Run the concurrency tests under a thread checker, because the checker finds races that no review finds and that a single-threaded test cannot see.

#include <atomic>
#include <condition_variable>
#include <mutex>
#include <thread>

/* THE RULE THAT MATTERS: the cost model of a primitive is not the
   one you would guess from its interface. An atomic LOOKS free and
   is a contended cache-line bounce under contention.            */

/* ORDERINGS. relaxed is for a counter nobody else interprets;
   acquire/release is the publication pattern and is what you want
   almost every other time; seq_cst is the safe default and the
   most expensive. */
struct mailbox {
    std::atomic<bool> ready{false};
    std::atomic<long> seq{0};
    void* payload = nullptr;
};

static void publish(mailbox& m, void* p)
{
    m.payload = p;
    /* The RELEASE ordering is what makes the write above visible to
       whoever sees ready == true. Without it the flag can be
       observed BEFORE the payload - which is the classic
       publication bug. */
    m.ready.store(true, std::memory_order_release);
}
static void* consume(mailbox& m)
{
    if (!m.ready.load(std::memory_order_acquire)) return nullptr;
    m.seq.fetch_add(1, std::memory_order_relaxed);
    return m.payload;
}   /* THE THREE FAILURES.
   1. AN ATOMIC USED AS A LOCK: an increment is atomic, so two
      threads can both read, both compute and both write - the
      increment loses one of them. Atomics do not serialise a
      read-modify-write sequence without a compare-and-swap loop.
   2. PUBLISHING DATA BEFORE THE FLAG, which is what the release
      ordering exists to prevent.
   3. JOINING A THREAD BLOCKED IN A WAIT WITH NO EXIT, which is a
      program that cannot be stopped, upgraded or debugged.        */

/* A MUTEX IS THE CORRECT DEFAULT. It makes a SET of reads and
   writes atomic as a group; an atomic per field makes each field
   atomic, which is a weaker and different property. */
struct pair_state { int x, y; };

class counter {
    mutable std::mutex        m_;
    std::condition_variable   cv_;
    bool stopping_ = false;
    long count_ = 0;
public:
    void bump()
    {
        std::lock_guard<std::mutex> g(m_);
        ++count_;                    /* both fields together    */
    }
    void stop()
    {
        { std::lock_guard<std::mutex> g(m_); stopping_ = true; }
        cv_.notify_all();             /* outside the lock         */
    }
    /* WAIT IN A LOOP. A notification can arrive between the check
       and the wait, and the condition can be false again when you
       wake - so one check is a lost wakeup. */
    void drain()
    {
        std::unique_lock<std::mutex> lk(m_);
        while (!stopping_ && count_ == 0)
            cv_.wait(lk);             /* unlocks, waits, relocks */
    }
};  /* Two disciplines. REACH FOR A MUTEX FIRST and drop to an atomic
     only when you can NAME the invariant it preserves, because a
     mutex is correct in every case and an atomic is correct only
     for a list you have to enumerate. And RUN THE CONCURRENCY TESTS
     UNDER A THREAD CHECKER - it finds races no review finds and that
     a single-threaded test cannot see by construction. */

#include <thread>
#include <mutex>
#include <atomic>
#include <shared_mutex>
#include <future>
#include <vector>
#include <chrono>

/* THE FOUR TOOLS, and which one a problem actually needs. */

/* 1. MUTEX: mutual exclusion. The default answer, and correct for
      almost every case. */
static int counter = 0;
static std::mutex counter_mutex;

static void bump()
{
    /* THE SCOPE IS THE INVARIANT. Copy what you need under the
       lock, do the work outside it, write back under it. Holding a
       mutex across I/O serialises every other thread behind the
       slowest disk in the program. */
    std::lock_guard<std::mutex> g(counter_mutex);
    ++counter;
}

/* 2. ATOMIC: one value, no compound invariant. The right tool when
      - and only when - you can NAME the single thing it protects. */
static std::atomic<long> hits{0};
static std::atomic<bool>  stopped{false};

static void record() { hits.fetch_add(1, std::memory_order_relaxed); }
static void stop()   { stopped.store(true, std::memory_order_release); }
static bool is_stopped() { return stopped.load(std::memory_order_acquire); }

/* THE HAZARD AN ATOMIC CANNOT COVER, and it is the reason a pair of
   atomics is not a mutex: each field is atomic, but the PAIR is
   not, so two threads can interleave between the reads. */
struct WrongPair {
    std::atomic<int>  in_flight{0};
    std::atomic<bool> stopping{false};

    void check()
    {
        /* A thread can observe stopping == true while in_flight is
           still 2. Both loads are individually correct and correctly
           ordered; the LOGIC is not. No detector finds this, because
           there is no data race to detect. */
        if (stopping.load(std::memory_order_acquire) && in_flight.load() == 0)
            begin_shutdown();
    }
};

struct RightPair {
    std::mutex m;
    int  in_flight = 0;
    bool stopping  = false;

    void check()
    {
        std::lock_guard<std::mutex> g(m);
        if (stopping && in_flight == 0) { begin_shutdown(); return; }
    }
};

/* 3. SHARED MUTEX: many readers, few writers, and the read path is
      genuinely expensive. Two atomic increments otherwise. */
static std::shared_mutex config_mutex;
static std::string config_value;

static std::string read_config()
{
    std::shared_lock g(config_mutex);       /* concurrent readers */
    return config_value;
}
static void write_config(std::string v)
{
    std::unique_lock g(config_mutex);       /* exclusive          */
    config_value = std::move(v);
}

/* 4. FUTURE: a value that will arrive later, and the one tool that
      propagates an exception across the thread boundary. */
static std::future<int> compute()
{
    return std::async(std::launch::async, []{ return expensive(); });
}

/* THE RULE THAT MATTERS MOST: two threads must not touch the same
   memory without one of the four above between them, and the choice
   between them is decided by the INVARIANT rather than by
   preference. Reach for the mutex first; drop to an atomic only
   when the thing it protects is one value and you can say which.
   An atomic is faster and strictly harder to use correctly, and
   that trade is worth taking once in a while and not otherwise. */

/* AND THE DEADLOCK THAT WAITING FOR: the shutdown protocol. A
   thread asked to stop may be blocked in a mutex or a join, so
   asking it to stop and then waiting is a deadlock unless every
   wait has a path out. */
static void shutdown_properly()
{
    std::lock_guard<std::mutex> g(counter_mutex);
    stopped = true;                       /* set the flag        */
    /* ... then RELEASE the lock before joining. Joining while
       holding the lock the worker needs is the deadlock.         */
}

6.3 Modules, the preprocessor, and what still cannot be fixed

The preprocessor is still in the language and still cannot see a symbol, and modules address most of that without replacing anything you rely on.

Two text-processing systems, one language

The preprocessor runs first and knows nothing about types, so a macro can produce something that does not compile. Modules are compiled units with an explicit interface, so a symbol is either exported or not and the compiler checks every use. Then the four things to know, and each is a requirement. A header inclusion is a textual paste, so a header with no include guard is included twice, and a header that defines a non-inline function is a link error in every translation unit after the first. Modules do not change the preprocessor, which still exists and is still the right tool for conditional compilation and for the two or three functions that must be macros. Module compilation order matters, and a build system that does not model it will produce intermittent failures. And An export is a promise about the interface, so the set of exported names is what a consumer sees and everything else is invisible — which is the point. Then the three things that go wrong, and each is a mechanism. A header without a guard, which duplicates every declaration. A macro that expands a declaration with a semicolon in it, which breaks at the use site in a way that reads as a compiler bug. And Assuming modules make the preprocessor unnecessary, which fails the first time a platform header needs it. Then the two practices, and both are disciplines. Use headers for the things headers are good at — declarations, templates, include-only libraries — and modules for everything else, because a module compiles once rather than once per translation unit. And Parenthesise every macro parameter and the whole expansion, without exception, which costs nothing and is the difference between a macro that works and one that is subtly wrong.

/* THE PREPROCESSOR still exists and still cannot see a symbol.
   MODULES address most of that without replacing it. */

/* 1. A HEADER INCLUSION IS A TEXTUAL PASTE. */
#pragma once                    /* the guard; cheap and sufficient */

/* 2. NON-INLINE FUNCTIONS IN A HEADER ARE A LINK ERROR in every
   translation unit after the first - which is why a header-only
   library marks everything inline or template or constexpr. */
inline int helper(int x) { return x + 1; }   /* inline: OK       */
template<typename T> T identity(T v) { return v; }  /* template */

/* 3. A MACRO THAT EXPANDS A DECLARATION WITH A SEMicolon IN IT
   breaks at the use site, in a way that reads like a compiler
   bug. */
#define BAD_DECLARE(t, n)  t n;      /* not a declaration, it is a
                                        DECLARATION plus a stray
                                        semicolon that breaks an
                                        if or a for                */
#define GOOD_DECLARE(t, n) do { t n; } while (0)

/* Parenthesise EVERY parameter and the WHOLE expansion. It costs
   nothing and it is the difference between a macro that works and
   one that is subtly wrong. */
#define BAD_MIN(a, b) a < b ? a : b        /* precedence         */
#define GOOD_MIN(a, b) ((a) < (b) ? (a) : (b))

/* 4. A MODULE HAS AN EXPLICIT INTERFACE, and everything not
   exported is invisible to a consumer. That is the whole point. */
export module geometry;

/* exported: visible to a consumer, checked by the compiler */
export namespace geo {
    struct point { double x, y; };
    double distance(const point&, const point&);
}

/* not exported: still compiled once, invisible from outside, and
   inlinable across the module boundary */
namespace detail {
    inline double square(double v) { return v * v; }
}

/* ---- and the interface, which is what a consumer sees ---- */
module;
#include <cmath>      /* the preprocessor still works inside a
                         module; it has to, because every platform
                         header needs it                         */
export module geometry;

export namespace geo {
    struct point { double x, y; };
    double distance(const point& a, const point& b)
    {
        /* detail::square is in the SAME translation unit, so this
           is one compiled copy rather than one per consumer. */
        double dx = a.x - b.x, dy = a.y - b.y;
        return std::sqrt(detail::square(dx) + detail::square(dy));
    }
}   /* THE THREE FAILURES.
   1. A HEADER WITHOUT A GUARD: every declaration is duplicated.
   2. A MACRO THAT EXPANDS A DECLARATION WITH A SEMicolon: the
      semicolon lands in the middle of an if or a for at the use
      site, and the error names the macro rather than the place.
   3. ASSUMING MODULES MAKE THE PREPROCESSOR UNNECESSARY: it fails
      the first time a platform header needs it, and they all do.

   Two disciplines. USE HEADERS FOR WHAT HEADERS ARE GOOD AT -
   declarations, templates, include-only libraries - and modules for
   everything else, because a module compiles ONCE rather than once
   per translation unit. And PARENTHESISE EVERY MACRO PARAMETER AND
   THE WHOLE EXPANSION, without exception. */

/* WHAT MODULES FIX, and the one thing they do not. */

/* THE HEADER IS COMPILED EVERY TIME. A declaration-only header is
   still parsed by every translation unit, and with enough of them
   the parse dominates the build. An include guard prevents
   re-parsing within one unit; it does nothing for the forty. */
#pragma once          /* cheaper than the guard dance, same effect */

/* THE MACRO LEAKS. A macro defined in a header is defined in every
   translation unit that includes it, including the ones whose
   authors did not know it existed - and a macro that renames a
   parameter is a defect the reader cannot see. */
#define MAX(a, b) ((a) > (b) ? (a) : (b))    /* a foot-gun in every
                                                 TU that includes
                                                 this header      */

/* THE INCLUDE ORDER IS A GLOBAL DEPENDENCY. Every .cpp has to
   include the headers of what it uses, in the same order
   everywhere, or a forward declaration in one place makes a build
   that is order-dependent - and it works on the machine of the
   person who wrote it. */

/* WHAT A MODULE DOES INSTEAD. It is compiled ONCE into an object
   file. Every TU that imports it reads the object file's index, not
   its source, so adding a function to a module does not re-parse it
   in forty places. */
export module geometry;                 /* the module interface */
export namespace geom {
    struct Point { double x, y; };
    double distance(Point a, Point b);  /* a DECLARATION: the body
                                           is not visible and is
                                           not reparsed          */
    double hypotenuse(double a, double b) { return distance({0,0}, {a,b}); }
}                                        /* anything NOT exported
                                           is invisible outside,
                                           including for a
                                           debugger to step
                                           into               */

/* THE PARTITION: the interface and the implementation are separate,
   and only the interface is exposed. */
module geometry.internal;    /* the implementation */
export module geometry;

/* THE ONE THING MODULES STILL DO NOT FIX, and it is the reason this
   chapter exists alongside them: the preprocessor is unaffected,
   because macros are expanded before anything sees a module. A
   macro is still global, still invisible to the type system, and
   still capable of rewriting a token in a header you did not know
   included yours. */

/* THE MIGRATION STATE, so the guidance is honest rather than
   absolute. Headers and modules interoperate: a module can import
   headers, and a translation unit can include a header that declares
   things a module also exports. What does NOT work is two modules
   exporting the same name into the same scope, or a header and a
   module claiming the same entity - which is a duplicate-definition
   error at a point that is hard to read. */

/* THE PRACTICAL ADVICE. In a codebase built entirely on headers,
   introducing modules is a change of build system, not a change of
   one file, because every include path has to resolve and the
   include order stops mattering only once nothing includes
   anything. Start with a leaf library with no dependencies, not
   with the header everybody includes. */

7.1 Build systems, dependency hygiene, and reproducible builds

A C++ build is a graph, and almost every C++ build problem is a graph problem: a target that rebuilds when it should not, a dependency that is not declared, or an include that means a rebuild.

What a build graph actually decides

A target declares what it consumes and what it produces; the build system decides the order. A declared dependency is a promise that a change to the input requires rebuilding the output, and the whole value of a build system is making that promise true rather than convenient. A header-only library makes the promise for every translation unit that includes it, which is why a change to one widely-included header is a full rebuild — and why that header should contain as little as possible. Then the four rules that follow, and each is a requirement. Declare every dependency explicitly, including the ones a tool could infer, because an inferred dependency is one the tool chose and you did not review. Keep a library's public headers minimal and its implementation in the source file, so a change to an implementation does not invalidate every consumer. Pin the toolchain version, so the compiler, the standard library and the linker are facts rather than whatever is on the machine. And Make the build reproducible, meaning the same source produces the same binary, which is what lets you trust a checksum. Then the three things that go wrong, and each is a mechanism. An undeclared dependency, which builds on your machine because the header happened to be included transitively and fails on a clean build. A build that is not reproducible, which embeds a timestamp or a path and produces a different binary from the same source — making a checksum meaningless. And A dependency graph nobody can read, which makes a full rebuild impossible to explain and therefore impossible to accept. Then the two practices, and both are disciplines. Make the clean build the fast build, by keeping the target count small, because a project where a clean build takes twenty minutes is a project where nobody runs one. And Measure the build, because build time is the tax on every change for the rest of the project's life and it grows silently.

#include <chrono>
#include <cstdio>

/* A C++ BUILD IS A GRAPH, and almost every C++ build problem is a
   graph problem. A target declares what it consumes and produces;
   the system decides the order.

   1. A DECLARED DEPENDENCY is a promise that a change to the input
      requires rebuilding the output. The whole value of a build
      system is making that promise TRUE rather than convenient.
   2. A HEADER-ONLY LIBRARY makes the promise for EVERY translation
      unit that includes it - which is why a change to one widely
      included header is a full rebuild. That header should contain
      as little as possible.                                     */

/* THE THREE FAILURES.
   1. AN UNDECLARED DEPENDENCY: builds on your machine because the
      header happened to be included TRANSITIVELY, and fails on a
      clean build or on somebody else's machine.
   2. A BUILD THAT IS NOT REPRODUCIBLE: embeds a timestamp or an
      absolute path, so the same source produces a different binary
      and a checksum of it means nothing.
   3. A DEPENDENCY GRAPH NOBODY CAN READ, which makes a full rebuild
      impossible to explain and therefore impossible to accept.    */

/* The mechanical fixes, in order of effect.

   1. A PRECOMPILED HEADER for the includes every translation unit
      needs and almost no translation unit changes. */
#include <vector>
#include <string>
#include <memory>

/* 2. SPLIT A HEADER: the interface in one file, the implementation
      in another. A change to the implementation then rebuilds one
      object file rather than every consumer. */

/* 3. FORWARD DECLARE in the header. This is the single most
      effective thing you can do for build time, because it removes
      the include entirely. */
namespace app { class connection; }   /* not: #include <conn.h> */

/* 4. Narrow the interface, not the class. A public header that
      exposes std::vector<std::string> forces every consumer to see
      the whole standard library; a public header that exposes a
      pointer or a small value type does not. */

/* THE TWO PRACTICES, and the first one is the whole discipline.
   MAKE THE CLEAN BUILD THE FAST BUILD by keeping the target count
   small: a project where a clean build takes twenty minutes is a
   project where nobody runs one, and a project where nobody runs
   one has no build system at all in practice.

   And MEASURE THE BUILD, because build time is the tax on every
   change for the rest of the project's life and it grows silently.
   A project that starts at a thirty-second build and is at four
   minutes after a year has lost an hour a day, and nobody decided
   that. */

/* THE FOUR PROPERTIES OF A BUILD, and which one is usually broken. */

/* 1. REPRODUCIBILITY: the same source produces the same binary. The
      usual culprits are a timestamp, a path baked into the binary,
      and a dependency resolved from a range rather than a lock. */
set(CMAKE_BUILD_TYPE Release)

/* 2. HERMETICITY: the build reads only what it declares. A find

      with different contents produce different binaries. */
find_package(fmt 10.2.1 EXACT REQUIRED)   /* EXACT: not a range   */

      when an unrelated file changes. CMake's dependency scanning is
      coarse, and a header that includes another header that
      includes another header means one change invalidates most of

add_library(core STATIC
    src/core.cpp
    src/parse.cpp

target_include_directories(core PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>

                                               set separated, so
                                               the installed
                                               package does not
                                               reference the
                                               source tree     */

/* 4. THE DEPENDENCY GRAPH, which is the one that actually costs
      time. Every target's include directories are PUBLIC by
      default and therefore propagate: a change to a leaf utility
      can invalidate the whole tree, which is how a 40-second
      incremental build becomes four minutes. */
target_link_libraries(core PRIVATE fmt::fmt)     /* PRIVATE: does
                                                       NOT
                                                       propagate,
                                                       which is
                                                       what you
                                                       want for
                                                       an
                                                       implementation
                                                       detail   */
target_include_directories(core PRIVATE src)      /* PRIVATE header
                                                         paths too   */

/* THE SANITIZER TARGET, as a separate build rather than a flag on
   the release one: the instrumentation changes timing and code
   layout, so a sanitizer run is not evidence about the shipped
   binary. */
add_executable(core_san src/main.cpp)
target_compile_options(core_san PRIVATE -fsanitize=address,undefined -g)

7.2 Profiling, the cost model, and four optimisations that work

C++ performance work goes wrong in a predictable way — guess, change, measure, see nothing, guess again — and the reason is that the cost model of a modern C++ program is not the one a C programmer carries over.

The cost model, and where it differs from C

Allocation is the expensive thing, not computation. A malloc is tens of nanoseconds and a tight arithmetic loop is nanoseconds per iteration, so a program's cost is usually its allocation count and its cache behaviour. Copying a container is a deep copy, so passing a vector by value in a loop is quadratic. Virtual dispatch is a load plus a branch, which is cheap and unpredictable, which is why a megamorphic call site is worse than a switch. And Exceptions cost at the boundary, not at the call, which is why a function that throws on every path is slow and a function that never throws is not. Then the four optimisations that reliably work, and each is a requirement. Reserve capacity, or use a container that does not reallocate, which removes both the allocations and the moves. Pass by const reference or by pointer, never by value for anything non-trivial, which removes a copy per call. Measure before and after with a profiler, because a change that improves a number in a microbenchmark can make the program slower by moving the working set. And Reserve before a loop that appends, which turns amortised growth into a single allocation. Then the three things that go wrong, and each is a mechanism. Optimising the wrong code, which is the ninety-nine per cent case and which a profiler finds in ten minutes. Making a change that improves a microbenchmark and worsens the program, because the benchmark's cache state is not the program's. And Fighting the optimiser, which is manual inlining and hand-unrolling the compiler already does — and which usually makes the code longer and slower. Then the two practices, and both are disciplines. Profile before you change anything, because the intuition about which code is slow is wrong more often than it is right. And Change one thing at a time and measure after each, because two changes that each improve the number by five per cent together improve it by five per cent.

#include <chrono>
#include <string>
#include <vector>

/* THE COST MODEL, AND WHERE IT DIFFERS FROM C.
   1. ALLOCATION IS THE EXPENSIVE THING, not computation. A malloc
      is tens of nanoseconds; a tight arithmetic iteration is a few.
      A program's cost is usually its ALLOCATION COUNT and its CACHE
      BEHAVIOUR, not its arithmetic.
   2. COPYING A CONTAINER IS A DEEP COPY, so passing a vector by
      value in a loop is quadratic.
   3. VIRTUAL DISPATCH IS A LOAD PLUS A BRANCH - cheap and
      UNPREDICTABLE, which is why a megamorphic call site is worse
      than a switch on the same values.
   4. EXCEPTIONS COST AT THE BOUNDARY, not at the call site, so a
      function that throws on every path is slow and one that never
      throws is not.                                            */

/* THE FOUR OPTIMISATIONS THAT RELIABLY WORK.

   1. RESERVE CAPACITY, or use a container that does not reallocate.
      This removes BOTH the allocations and the element moves. */
static void reserve_wins()
{
    std::vector<std::string> a, b;
    for (int i = 0; i < 10000; ++i) a += "x";      /* ~14 reallocs */

    b.reserve(10000);
    for (int i = 0; i < 10000; ++i) b += "x";      /* 1            */
}

/* 2. PASS BY CONST REFERENCE OR BY POINTER, never by value for
      anything non-trivial. One copy per call, and the copy is a
      heap allocation for a container. */
static size_t by_value(std::vector<int> v) { return v.size(); }   /* copy */
static size_t by_ref(const std::vector<int>& v) { return v.size(); } /* no */

/* 3. MEASURE BEFORE AND AFTER WITH A PROFILER, because a change
      that improves a microbenchmark can make the PROGRAM slower by
      moving the working set. A microbenchmark that fits in L1
      measures a cache that your program does not have. */

/* 4. RESERVE BEFORE A LOOP THAT APPENDS, which turns amortised
      growth into a single allocation. */

/* THE THREE FAILURES.
   1. OPTIMISING THE WRONG CODE - the ninety-nine per cent case,
      and a profiler finds it in ten minutes.
   2. IMPROVING A MICROBENCHMARK AND WORSENING the program, because
      the benchmark's cache state is not the program's.
   3. FIGHTING THE OPTIMISER: hand inlining and manual unrolling
      that the compiler already does, which usually makes the code
      longer and slower.                                          */

/* A defensible measurement, at least. */
template<typename F>
static double time_ms(F&& f, int trials = 7)
{
    f();                                   /* warm the cache       */
    double best = 1e18;
    for (int t = 0; t < trials; ++t) {
        auto t0 = std::chrono::steady_clock::now();
        f();
        double dt = std::chrono::duration<double, std::milli>(
            std::chrono::steady_clock::now() - t0).count();
        if (dt < best) best = dt;           /* the MINIMUM, not the mean */
    }
    return best;
}  /* Two practices. PROFILE BEFORE YOU CHANGE ANYTHING, because
     intuition about which code is slow is wrong more often than it
     is right. And CHANGE ONE THING AT A TIME and measure after
     each, because two changes that each improve the number by five
     per cent together improve it by five per cent - and you will
     conclude both are necessary. */

#include <vector>
#include <string>
#include <chrono>
#include <algorithm>

/* THE ORDER, because the instinct is to optimise before measuring:
   establish there IS a problem, in the configuration that ships;
   find which RESOURCE is the constraint; find where the time goes;
   and only then change something. */

/* FOUR OPTIMISATIONS THAT WORK, in the order they are worth trying. */

/* 1. ALGORITHM FIRST, always. A better algorithm beats a better
      compiler at every level, and the gap is exponential. */
static long sum_naive(const std::vector<int> &v)
{
    long total = 0;
    for (std::size_t i = 0; i + 1 < v.size(); ++i)
        for (std::size_t j = i + 1; j < v.size(); ++j)
            if (v[i] + v[j] == target) ++total;
    return total;
}
/* 4 million comparisons versus 4000 for a two-pointer sweep. No
   amount of -O3 closes a factor of a thousand. */

/* 2. ALLOCATION. It is the most common cost in a measured profile
      of C++ and the one with the largest constant factor. */
static std::vector<std::string> the_naive_build(int n)
{
    std::vector<std::string> out;
    for (int i = 0; i < n; ++i) out.push_back(std::to_string(i));
    return out;          /* n reallocations, n copies on each */
}

static std::vector<std::string> the_fixed_build(int n)
{
    std::vector<std::string> out;
    out.reserve(n);      /* ONE allocation. This is the single
                             largest measurable win in ordinary
                             C++ code.                        */

   premature optimisation: hand-unrolling, precomputing addresses,
   and avoiding a bounds check. The compiler already does all three
   at -O2, does them better than a human does, and does them
   again when the code changes. */

/* AND THE CORRECTNESS ARGUMENT, which outranks every measurement:
   an optimisation that changes the order of two floating-point
   additions changes the answer, because floating point is not
   associative. The compiler does not reorder floating-point
   arithmetic without permission precisely because of this. */
static double the_associativity_trap(std::vector<double> &v)
{
    double a = 0, b = 0;
    for (double x : v) a += x;

       multiply-add changes the result as well. Neither is a bug;
       both are a decision that must be recorded, because a
       different summation order is a different number. */
    (void)b;
    return a;
}

7.3 Testing value types, and what does not need a test

C++ makes value semantics the default, and that changes what testing is for: the interesting bugs are in ownership, lifetime and overload resolution, not in the arithmetic.

What to test, and what not to

Then the four rules that follow, and each is a requirement. Test the interface, not the implementation, because the interface is what a caller depends on and the implementation is what you are free to change. Give a test one reason to fail, which in C++ usually means no shared fixture state, because a test that fails in a suite but passes alone is order dependence and order dependence is a defect in the test. Test the boundary values of every container operation, because the empty and single-element cases are the ones the implementation handles differently. And Test with types other than the one you built it with, which catches a function that works only for the type it was instantiated with. Then the three things that go wrong, and each is a mechanism. A test that asserts on a stringified value, which fails when a message changes and passes when a result is wrong. A test that constructs the object in every case, which is slower and which hides a constructor defect. And Skipping the empty case, which is where the standard library itself has historically had the most bugs. Then the two practices, and each is a discipline. Use property-based testing for the algorithms, because a property is a statement that must hold for all inputs and a generator finds the counterexample in seconds. And Run the suite under sanitizers and at more than one optimisation level, because a bug that only appears when a check the compiler removed comes back is exactly the bug that escaped.

static std::vector<Money> split_evenly(Money total, int parts)
{

A.1 The idioms worth memorising

A working list of the constructs that solve a recurring problem, with the condition each one requires — because an idiom applied outside its condition is the defect.

The list, with the condition attached

Then the three rules that apply to the whole list, and each is a requirement. Every idiom has a condition, and the condition is the whole content of the entry. Prefer the standard type over the idiom, because the standard type is what the library's own algorithms take. And An idiom that hides a copy is a defect, which is the one thing to check about each. Then the two practices, and each is a discipline. Learn the condition with the idiom, because a half-learned idiom is a bug. And Replace an idiom with the standard type as soon as it exists, which is more often than people expect.

<p>There is no list of idioms that makes C++ safe, because the language's hazards are not syntactic - they are decisions about who owns what and what happens when something fails. What a list can do is name the decisions, so that a reader of your code can infer them from the types rather than reconstructing them from the control flow.

<p>The order the idioms appear in above is roughly the order they earn their place. Resource acquisition is first because it is the decision everything else depends on: once a type owns its resource and releases it in a destructor, every subsequent question - what happens on the early return, what happens if the next constructor throws, what happens if the loop breaks - has an answer that was decided once, at the type, rather than at every exit path. Ownership is not first because it is elegant; it is first because it converts an unbounded number of questions into a bounded number of types.

<p>Returning a value rather than a pair of out-parameters comes next for the same reason. A function with two out-parameters has two ways to fail and one way to succeed, and the caller has to read the signature to know which is which. A returned structure has one shape, and the compiler enforces that every path produces one. The general form of the observation: prefer a type that states the whole result, because the code that cannot represent an invalid state is the code that cannot be used invalidly.

<p>The rule of zero deserves its place in a list like this because it is the one that makes the others unnecessary. A class whose members all manage themselves needs none of the five special member functions written by hand, and gets a correct copy, a correct move and a correct comparison from the compiler. The only thing that can go wrong is declaring one of the five by hand and thereby suppressing the rest - most often by writing a destructor for a logging statement, which turns a movable class into a copy-only one and makes every call site pay for a deep copy it cannot see.

<p>The last two idioms are about the reader. Const on what does not change is documentation the compiler enforces: a const member function cannot modify state, so the interface says what it does rather than a comment claiming to. And making invalid states unrepresentable is the same idea at a larger scale - an optional rather than a sentinel, a tagged union rather than a type field and a switch that might be missing a case, a type that carries its own units rather than a comment saying which unit the number is in.

Those are matters of taste and of a project's existing style, and a list that includes them trains the reader to ignore the entries that matter. The entries above are the ones where following them removes a class of defect rather than a style difference - which is the only test worth applying to an idiom.

A.2 The traps, and what each one costs

Seven defects account for most C++ bugs found in review, and each has a one-line prevention.

The seven

Then the three things that make them hard, and each is a requirement. Most of them compile, which is why they survive review. Most of them are correct for the type you tested with, which is why they survive testing. And Most of them are silent, which is why they survive to production. Then the two practices, and each is a discipline. Turn on every warning, because three of the seven have a diagnostic. And Run the sanitizers in continuous integration, because another three are only findable there.

<p>Every trap in this list passes compilation, passes review, and passes the functional tests. That is the property they share, and it is why they survive. A defect that a test would catch is not a defect that reaches a customer; these are the ones where the test suite, having been written against the behaviour you intended rather than the behaviour you implemented, reports success on code that does something else.

<p>Slicing is the clearest example, because the compiler's type system actively endorses it. Passing a Derived by value to a function taking a Base is legal, type-correct and lossy: the base subobject is copied and the derived part is discarded, with no diagnostic anywhere. What makes it survive is that the derived part usually adds no data, only overridden behaviour - and the result is a call that dispatches to the base implementation on an object the caller believes is derived. The cost is a silently wrong answer; the fix is a reference, and the reason it is a habit worth building is that the same parameter accepts a temporary only by value, so there is a genuine tension and the reference version needs the temporary's lifetime kept in view.

<p>Iterator invalidation is the one that costs the most debugging time, because the symptom is a skipped element rather than a crash. Erasing inside a loop invalidates every iterator at or after the erased position, so incrementing from an invalidated iterator either dereferences freed memory or - more often, because the freed memory is still readable - skips the element after the one you removed. The fix is one line: erase returns the next iterator. The reason it is written as a trap rather than as advice is that the code reads correctly to anyone who has not thought about it, and reviewing it requires knowing the rule.

<p>The shared_ptr cycle is the most expensive to diagnose and the least likely to be spotted, because every tool reports the code as correct. A cycle of strong references is a leak with no allocation site, no unmatched free and no ownership violation - the reference counts are simply never allowed to reach zero, and a heap profiler is the only thing that will show it. The cycle is also a design statement rather than a mistake: it means two objects have decided each other is part of the other's lifetime, and usually only one of those decisions is intended.

<p>The remaining five share a mechanism worth naming. Each one has a correct-looking form and an incorrect form that differs by a small token - const versus not, a reference versus a value, unsigned versus signed, noexcept or not - and in every case the incorrect form produces a plausible result rather than a diagnostic. That is what makes these traps durable rather than beginner errors: they are the shape of the code you write when you are concentrating on the problem rather than on the language, and they are caught by a compiler warning or a sanitiser rather than by reading.

A.3 Terms, and the three used wrongly

Three words in C++ are used more loosely than the standard defines them, and the looseness is where most arguments about the language go wrong.

Three terms, defined and corrected

Then the three conventions worth adopting, and each is a requirement. A const T& parameter means the function will not modify the object through this pointer, and says nothing about the rest of the program. Move means the source is left in a valid but unspecified state, and "unspecified" is the whole reason using a moved-from object is not undefined behaviour — which is exactly why it is still a bug. And "Exception-safe" is one of three levels, and only the strongest is usually meant. Then the two practices, and each is a discipline. Say which level of exception safety a function has, because the answer determines whether a caller can rely on it. And Treat a moved-from object as destroyed, because the only thing guaranteed is that it is valid, and code that relies on validity is relying on an implementation detail.

<p>Four terms in this guide are used precisely and used loosely in roughly equal measure, and in each case the precise meaning carries a consequence that the loose one does not. The consequence is what makes the term worth defining rather than assuming: object versus subobject decides whether a union member is live, lifetime versus storage duration decides whether a pointer to a cleared string is valid, the three levels of unspecifiedness decide whether a program is merely non-reproducible or genuinely unconstrained, and a dependent name decides why code that compiles outside a template fails inside one.

<p>The union case is the most practically useful of the four, because it is the one where the loose reading leads to code that looks like it restores state. At most one union member is an object at any time; the others are inactive. Reading an inactive member gives a reinterpretation of the same bytes rather than the value that was stored in it, and for a member with a non-trivial constructor or destructor doing so is undefined behaviour outright. So the pattern of writing one member and reading another back does not work, which is surprising to anyone who thinks of the union as a type-safe variant - which is precisely what std::variant is for, and why it exists.

<p>Storage duration versus lifetime matters more often than it looks, because the two coincide in almost every case and so the distinction never appears until the one case where it does. A string_view over a string that has been cleared, or a span over a vector that has been reallocated, points at bytes that are still perfectly readable and belong to an object that no longer exists. Every byte is where it was; the object is gone. Reading through the view is undefined behaviour, and the reason it is worth naming is that no observable symptom distinguishes it from the correct case until the implementation is changed.

<p>The three levels of unspecifiedness are worth separating because the practical response differs. Unspecified behaviour costs reproducibility: a program that evaluates two arguments in an order nobody defined may behave differently between runs or between builds, and the fix is to sequence the operations explicitly. Implementation-defined behaviour costs portability: the choice was documented, so the code is correct on one platform and wrong on another, and the fix is to ask the compiler for the property rather than assume it. Undefined behaviour costs everything: the program may do anything, and the compiler may delete the code that would have detected the problem, which is why it cannot be reasoned about from the source alone.

<p>A dependent name is different from the other three, because it is a rule about lookup rather than a condition on a program. The rule is short: inside a template, a name that could depend on the template parameter is looked up partly at the point of definition and partly at the point of instantiation, and ordinary lookup at the point of definition applies in addition. The consequence people meet is that a base class member is not found by ordinary lookup from inside a template and is not found by argument-dependent lookup either, because ADL does not look in base classes. The fix is a using declaration naming the base, which is why the same code compiles in a non-template function and does not compile in a template one.

/* 1. "CONST REFERENCE PARAMETER". Used loosely to mean "the caller
      cannot change it".

   PRECISE: const T& in a parameter means THIS FUNCTION will not
   modify the object THROUGH THIS REFERENCE. It says nothing about
   any other reference to the same object, and nothing about what
   happens after the call returns.                            */

/* 2. "MOVE". Used loosely to mean "the old object is empty".

   PRECISE: a move leaves the source in a VALID BUT UNSPECIFIED
   state. Unspecified is the whole reason using a moved-from object
   is not UNDEFINED BEHAVIOUR - and is exactly why it is still a
   bug. Reading a moved-from string is defined; reading it and
   expecting its old contents is your error.                     */

/* 3. "EXCEPTION-SAFE". Used loosely to mean "it does not leak".

   PRECISE: three levels.
     BASIC      nothing leaks, no invariants broken. The usual
                minimum.
     STRONG     either succeeds or has NO EFFECT. What a caller
                actually wants when it is about to commit.
     NO-THROW    the operation cannot throw. Required of a
                destructor, a move assignment, and a swap.

   Saying "this function is exception-safe" without saying which
   level is as uninformative as saying "this function is correct".
   Two operations that are both strong may be composed safely; a
   strong and a basic may not, because the basic one's effect is
   already visible when the strong one throws.                    */

/* Three conventions worth adopting.
   1. SAY WHICH LEVEL of exception safety a function has.
   2. TREAT A MOVED-FROM OBJECT as destroyed.
   3. TAKE const T& BY DEFAULT for a read-only parameter.         */

/* Two practices, restated. SAY WHICH LEVEL a function has, because
   the answer determines whether a caller can rely on it - and
   because "it does not leak" is the answer that hides the case
   that matters. And TREAT A MOVED-FROM OBJECT AS DESTROYED,
   because the only thing guaranteed is that it is valid, and code
   that relies on validity is relying on an implementation detail
   that a future standard revision may change. */

/* THE TERMS, with the distinction that actually matters in each. */

/* 1. "OBJECT" vs "SUBOBJECT".

   PRECISE: an object is a region of data storage in the execution
   environment whose contents represent values. A subobject is a
   REGION OF THAT OBJECT - a base class subobject, a member
   subobject, an array element is NOT a subobject.

   LOOSE: "the things a class is made of", which merges subobjects
   with the temporaries and references that also participate.

   The distinction is load-bearing in one specific place: a union's
   members overlap in storage, so at most one of them is an object
   at a time. Writing one and reading another gives you a pointer
   reinterpretation, not a second live object - and for a
   non-trivially-copyable type it is undefined behaviour outright.
   Reading the inactive member to "restore" it does not work. */

/* 2. "LIFETIME" vs "STORAGE DURATION". These are NOT synonyms and
   the confusion produces real bugs.

   STORAGE DURATION is where the bytes live: static, thread,
      automatic, dynamic. It is a property of a VARIABLE and it is
      decided where the variable is declared.

   LIFETIME is when the object exists. It begins when
      initialisation completes and ends when the destructor starts
      or the storage is reused.

   They usually coincide, and where they do not, the object's
   lifetime can end while its storage continues - a pointer to it is
   then a pointer to an object that no longer exists, and using it
   is undefined behaviour even though every byte is still readable.
   A std::string_view over a std::string that has been cleared is
   the everyday version of this. */

/* 3. "UNSPECIFIED" vs "UNDEFINED" vs "IMPLEMENTATION-DEFINED",
   which is three conditions and not two.

   UNSPECIFIED       the implementation may choose, and does not
                     have to document the choice. Two runs may
                     differ. Argument evaluation order is the
                     canonical example: nothing constrains it, and
                     nothing promises it is the same at -O0 and -O2.

   IMPLEMENTATION-   the implementation must CHOOSE and must
   DEFINED           DOCUMENT it, and the compiler may reject the
                     program. char's signedness is the example:
                     documented per platform, and the reason the
                     same source is correct on one machine and
                     wrong on another.

   UNDEFINED         no requirement at all. The program may do
   BEHAVIOUR        anything, including producing a value no
                     conforming machine could produce, and the
                     compiler may assume the situation cannot arise
                     and delete the code that would have detected
                     it. Reading an uninitialised object is the
                     example, and the reason it is not "sometimes
                     wrong" is that the code checking it may no
                     longer be in the binary. */

/* 4. "DEPENDENT NAME" - the one that explains two-phase lookup.

   A name inside a template is DEPENDENT when its meaning can
   depend on the template parameter: T::member, or f(x) where
   x depends on T. A dependent name is looked up in two phases: at
   DEFINITION time for what can be known then, and at
   INSTANTIATION time for the rest, with ordinary lookup at the
   point of definition applying as well.

   The consequence people trip over: a base class member is not
   found by ordinary lookup from inside a template, and ADL does
   not look in base classes, so Base<T>::member is invisible until
   you write using Base<T>::member. That is why the fix is a using
   declaration rather than a qualified call, and why the same code
   works outside a template and fails inside one. */
