Welcome — Scalable Web Apps with Laravel + Vue

How this guide is organisedThe stack

A practical guide to building production-grade web applications with a Laravel backend and a Vue 3 frontend. It walks you through designing, building, testing and shipping the full stack, from Eloquent models through API routes and into the SPA components. By the end you can architect, implement and operate the whole system yourself.

A complete guide to building a production-grade, scalable web application with a Laravel (PHP) backend and a Vue 3 frontend. Single file, offline, progress saved locally.

How this guide is organised

The book is organised as a progression from Laravel backend architecture through the Vue frontend, then combines both for realtime, testing and deployment. Each chapter builds on the material before it, so following them in order gives a sensible learning path. Later chapters reuse the patterns introduced earlier instead of starting over.

  • Architecture & backend (Ch. 1–7) — structure, routing, Eloquent, auth (Sanctum), API resources, queues and caching.
  • Frontend (Ch. 8–11) — Vue 3 + Vite + TypeScript, routing, Pinia, forms and the API client.
  • Together (Ch. 12–16) — Inertia vs SPA, real-time with Reverb, testing, observability, deployment and scaling.

Laravel pairs beautifully with Vue two ways: a classic JSON API + SPA, or Inertia.js for a monolith feel with Vue components. This guide covers both and when to choose each.

The stack

A single reference table maps every layer of the stack to its recommended tool, from Eloquent and Sanctum on the backend to Vue 3, Vite, Pinia and Redis on the frontend. Use it as a quick recap whenever you forget which tool fills which role. Each choice is presented as the safe default for this kind of application.

Chapter one frames the big picture before you write any code, comparing a browser SPA talking to a JSON API against an Inertia setup and Blade-rendered islands. It argues that the modular monolith is the safe default architecture for most teams. Nailing the architecture here saves painful refactors later in the project.

A decision table compares Inertia against a separate JSON API and Blade islands, weighing each option for teams that need mobile or third-party clients. A standalone JSON API is the right choice when consumers besides your Vue SPA exist. Inertia suits single-app teams that want a modern SPA without hand-building data endpoints.

Keep your domain logic out of controllers by delegating work to action classes and services, which stay easy to reason about and test. Split the monolith into separate modules only when a real boundary demands independent scaling or team ownership. This avoids the premature complexity of microservices.

2 · Laravel Fundamentals

2.1 Routing and controllers2.2 The service container2.3 Artisan and the lifecycle

The core Laravel building blocks covered here are routing, controllers, the service container and your daily Artisan workflow. Routes map requests to controller methods, the container resolves dependencies automatically, and Artisan drives migrations, scaffolding and production caching. Master these fundamentals and every later chapter clicks into place.

2.1 Routing and controllers

API routes in routes/api.php delegate to named controllers, which stay thin by forwarding the real work to action classes. Route model binding injects models straight into methods and resource controllers provide conventional REST methods out of the box. This split keeps request handling clean and easy to test.

// routes/api.php
Route::middleware('auth:sanctum')->group(function () {
    Route::apiResource('posts', PostController::class);
});

// Controller: thin — delegate to an action
public function store(StorePostRequest $request, CreatePost $action)
{
    $post = $action->execute($request->validated(), $request->user()); // delegate; the action owns the logic
    return new PostResource($post);
}

A Sanctum-protected API resource route delegates to a thin controller that runs a CreatePost action and returns a shaped resource.

2.2 The service container

Laravel’s service container resolves dependencies for you, wiring objects together without manual instantiation. Bind an interface to its concrete implementation once in a service provider, then type-hint it in a constructor for automatic injection. Swapping implementations and injecting test mocks then becomes trivial.

// Bind an interface to an implementation
$this->app->bind(PaymentGateway::class, StripeGateway::class); // swap implementations in one place

// Constructor injection is resolved automatically
public function __construct(private PaymentGateway $gateway) {}

Bind the interface to a concrete class once, then rely on container auto-injection in constructors.

2.3 Artisan and the lifecycle

Artisan is the command line interface you use every day, covering serve for local development, make commands for scaffolding, migrate for schema changes, route:list for inspection and optimize for production caching. The framework lifecycle bootstraps the app and then routes each request through the HTTP kernel. One consistent workflow carries you from development to deployment.

php artisan serve # start the dev server
php artisan make:model Post -mrc       # model, migration, resource, controller
php artisan migrate
php artisan route:list
php artisan optimize                   # config/route/view cache for prod

A shell session showing the standard Artisan workflow, from starting a dev server through migrations to caching config for production.

Run php artisan optimize in production but never in local dev — cached config/routes hide changes and cause confusing bugs.

3 · Domain Structure & Actions

3.1 Actions and services3.2 DTOs and validation3.3 Domain events

Keep business rules out of controllers by moving them into single-purpose action classes and FormRequests that validate input early. Domain events then decouple side-effects like notifications and logging from the request cycle. The result is controllers that simply orchestrate the flow instead of implementing logic themselves.

3.1 Actions and services

An action class exposes one public execute method, accepts typed inputs and delegates persistence through a repository. This single-purpose design forms the backbone of clean Laravel domain logic, keeping each business operation focused and straightforward to test. Larger workflows compose several actions behind a dedicated service.

final class CreatePost
{
    public function __construct(private PostRepository $posts) {} // inject the repository

    // single entry point the controller calls
    public function execute(array $data, User $author): Post
    {
        return $this->posts->create([
            'title' => $data['title'],
            'body' => $data['body'],
            'author_id' => $author->id,
        ]);
    }
}

The CreatePost action takes validated data, injects its repository and returns a fresh Post, keeping controllers thin.

3.2 DTOs and validation

FormRequests validate incoming data before your action ever runs, declaring rules per field with matching messages. Laravel automatically returns structured 422 responses with per-field errors that the SPA can map back onto inputs. Data transfer objects then carry that validated payload into the action layer.

class StorePostRequest extends FormRequest
{
    // rules run before the controller or action
    public function rules(): array
    {
        return [
            'title' => ['required', 'string', 'max:200'], // required string, capped length
            'body'  => ['required', 'string', 'min:10'],
        ];
    }
}

A FormRequest declares per-field rules that run before the controller or action, so invalid data never reaches your logic.

3.3 Domain events

Fire events such as PostCreated from your actions and let listeners handle the follow-up work like sending mail, dispatching queues and broadcasting. This decouples side-effects from the request cycle so the controller stays focused on the primary operation. Listeners can run synchronously or be pushed onto a queue.

event(new PostCreated($post)); // fire-and-forget side-effects

// Listeners can queue work, send mail, broadcast, etc.
// Decouples side-effects from the request cycle.

Firing an event broadcasts intent while listeners handle mail, work or broadcasts, so side-effects leave the request cycle.

4 · Eloquent & Database

4.1 Models and relationships4.2 Migrations and indexes4.3 Avoiding N+1 with eager loading

Eloquent provides models, relationships, migrations and the query patterns that keep your database fast. The chapter’s main goal is avoiding N+1 queries from day one through eager loading and careful column selection. A solid schema defined in migrations underlies every model relationship you build.

4.1 Models and relationships

Eloquent models map to database tables, with fillable and casts protecting which attributes can be mass-assigned and how values are converted. Relationships are expressed as typed methods, for example a belongsTo method wiring the post model to the user. That lets you write fluent, chainable queries over related data.

class Post extends Model
{
    protected $fillable = ['title', 'body', 'author_id']; // only these are mass-assignable
    protected $casts = ['published_at' => 'datetime'];

    public function author(): BelongsTo { return $this->belongsTo(User::class); } // typed relation
    public function tags(): BelongsToMany { return $this->belongsToMany(Tag::class); }
}

A Post model lists its fillable attributes, casts a date column and wires author and tags as eager-loadable relationships.

4.2 Migrations and indexes

Migrations define the schema as versioned, replayable code so every environment can build the same database. They configure foreign keys, column types and indexes, and you keep indexes on the columns you filter or sort by such as published_at. Versioning schema this way prevents drift between environments.

Schema::create('posts', function (Blueprint $t) {
    $t->id();
    $t->foreignId('author_id')->constrained('users'); // FK to users, indexed
    $t->string('title');
    $t->text('body');
    $t->timestamp('published_at')->nullable()->index(); // index for date filters
    $t->timestamps();
});

This schema creates posts with a constrained author foreign key and an indexed nullable timestamp for date filtering.

4.3 Avoiding N+1 with eager loading

Eager loading with with on the query fetches related models in a single query instead of one per row, slashing overall query counts. Selecting only needed columns with select or pluck reduces the payload further. Strict mode enabled in development catches accidental lazy loads with an exception immediately.

// N+1: one query per author
$posts = Post::all();

// Fixed:
$posts = Post::with('author:id,name')
    ->select('id', 'title', 'author_id')
    ->latest()
    ->paginate(20);

// Enable strict mode in dev to catch lazy loads:
Model::preventLazyLoading(!app()->isProduction());

Eager loading via with() collapses the N+1 problem into one query, and preventLazyLoading turns regressions into errors in dev.

Use select() to fetch only needed columns, with() for relations, and paginate() for every list. Laravel Telescope or Debugbar reveals N+1s instantly.

5 · Authentication & Authorization

5.1 Sanctum for SPAs5.2 API tokens5.3 Policies and Gates

Authentication proves who a user is while authorization decides what they may do, and this chapter covers both with Sanctum and policies. Sanctum secures SPA cookie sessions and issues API tokens, while Gate and policies enforce ownership rules. The two layers together protect every route from anonymous abuse.

5.1 Sanctum for SPAs

Sanctum guards your Vue SPA with cookie-based, CSRF-protected authentication through the API. The login route checks credentials, regenerates the session and returns no content, with later requests riding on the session cookie. Clients must read the XSRF-TOKEN cookie and send it as a header for state-changing requests.

// stateful SPA auth: cookie-based, CSRF-protected
// config/sanctum.php stateful domains include your SPA origin
Route::post('/login', function (LoginRequest $r) {
    if (!Auth::attempt($r->only('email', 'password'))) {
        throw ValidationException::withMessages(['email' => 'Invalid credentials']);
    }
    $r->session()->regenerate();
    return response()->noContent();
});

// SPA sends X-XSRF-TOKEN header; axios includes it automatically.

A stateful login route checks credentials, regenerates the session and returns no content; the SPA then sends the CSRF token automatically.

5.2 API tokens

Sanctum issues plain-text API tokens with named abilities so third-party clients can act as a user. Each token is scoped to a narrow set of abilities, and the tokenCan method on the underlying model enforces them per request. Tokens can be issued and revoked individually for fine-grained control.

$token = $user->createToken('spa', ['posts:read', 'posts:write']); // scoped to this client
return ['token' => $token->plainTextToken];

// Protect + check abilities:
Route::middleware(['auth:sanctum', 'ability:posts:write'])->post('/posts', ...);

A personal access token scoped to read and write abilities is handed to the client, then enforced by the ability middleware.

5.3 Policies and Gates

Policies centralize authorization rules such as only the owner may update a post, with one method per action. Controllers and views enforce the same policy through Gate checks, so the authorization check cannot be misplaced. The SPA then surfaces or hides UI based on the matching ability flags.

class PostPolicy
{
    public function update(User $u, Post $p): bool { return $u->id === $p->author_id; } // owner-only rule
}
// Controller: $this->authorize('update', $post);

The policy encodes the owner-only rule and the controller invokes it with authorize, centralizing authorization.

Never expose raw models with sensitive columns. Use API Resources or $hidden to control exactly what leaves the server.

6 · API Resources & Errors

6.1 API Resources6.2 Consistent error responses6.3 Versioning

This chapter shapes what the frontend actually receives and keeps errors consistent. API Resources control the JSON contract field by field, a global handler standardises failures, and versioning buys you time when the contract changes. Together they keep the API predictable as it evolves.

6.1 API Resources

Resource classes map Eloquent models to clean JSON you fully control, including loaded relations and ISO-formatted dates. Resource collections wrap paginated lists so the response shape stays stable whether one item or many come back. You decide exactly which fields ever leave your API.

class PostResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id' => $this->id, // map only what the client needs
            'title' => $this->title,
            'body' => $this->body,
            'author' => new UserResource($this->whenLoaded('author')), // skips unless eager loaded
            'createdAt' => $this->created_at->toIso8601String(),
        ];
    }
}
// Collection: PostResource::collection(Post::paginate());

The resource dictates the JSON contract, including when a relation is loaded, and collections wrap paginated lists the same way.

6.2 Consistent error responses

A central exception renderer, typically the render method of the exception handler, turns validation failures and exceptions into one JSON shape. Every error then carries a status code and machine-readable details the SPA can read predictably. The frontend centralises handling for this contract in an Axios interceptor.

// bootstrap/app.php (Laravel 11+)
->withExceptions(function (Exceptions $e) {
    $e->render(function (ValidationException $ex) { // one shape for all validation errors
        return response()->json(['message' => $ex->getMessage(),
            'errors' => $ex->errors()], 422);
    });
});

A global exception renderer converts validation failures into one JSON shape, so the frontend only ever parses one error format.

6.3 Versioning

Prefix routes with a version such as api/v1 and keep the old versions alive while clients migrate to the new one. An OpenAPI specification documents the contract, letting the frontend generate TypeScript types straight from the backend definition. This approach buys time and safety when breaking changes are unavoidable.

Prefix routes with /api/v1, keep old versions until clients migrate, and publish an OpenAPI spec so the SPA can generate types.

7 · Queues, Events & Caching

7.1 Queues and jobs7.2 Caching7.3 Broadcasting events

Move slow work off the request path and reuse expensive results to keep responses fast and resilient. Queues, event broadcasting and caching work together: jobs handle background work, events notify other parts of the system, and the cache stores hot results. Each plays a clear role in moving effort away from user requests.

7.1 Queues and jobs

Dispatch jobs onto named Redis queues and run supervised workers with queue:work to process them. Horizon adds a dashboard, metrics and queue configuration so you can watch health and spread work across connections. Retries and failure handling keep transient errors from losing work permanently.

// generate the job class
php artisan make:job ProcessVideo
// dispatch onto a named queue
ProcessVideo::dispatch($video)->onQueue('media');

// Runner (prod): supervise workers
php artisan queue:work --queue=media,default --tries=3

// Laravel Horizon gives a dashboard + metrics for Redis queues.

A job is generated and dispatched to a named queue, then picked up by a worker; Horizon adds a dashboard and metrics around that.

7.2 Caching

Cache::remember holds an expensive result for a TTL and recomputes it once after expiry, with Redis as the backend. Tags let you flush a whole related group at once, for example every comment cache when a post changes. Choosing a good key scheme and TTL makes invalidation predictable.

// remember caches the result and recomputes after the TTL
$stats = Cache::remember('stats', now()->addMinutes(5), fn () =>
    Post::query()->selectRaw('count(*) as total')->first()
);

// Cache tags let you invalidate a group:
Cache::tags(['posts'])->flush();

Cache::remember stores the result for five minutes and recomputes on miss; tags let you flush a whole group in one call.

7.3 Broadcasting events

Broadcast Laravel events to private channels with a ShouldBroadcast event and the Reverb driver, authorizing subscriptions with channel closures. The Vue SPA listens with Laravel Echo and receives arriving items over the websocket connection. Only the authorized channel owner ever receives the payload, keeping data private.

class PostCreated implements ShouldBroadcast
{
    public function broadcastOn(): array { return [new PrivateChannel('user.'.$this->post->author_id)]; } // owner's private channel
}

// Frontend: Echo.private(`user.${id}`).listen('PostCreated', e => ...)

A model event implements ShouldBroadcast to a private channel, and Echo listens for it on the frontend.

8 · Vue 3 Frontend Foundations

8.1 Project setup8.2 Components with script setup8.3 Props, emits, slots

Scaffold a Vue 3 project with Vite and TypeScript, then build components the modern way. The script setup style with ref, computed, props and emits covers most of your UI without legacy options objects. This foundation underlies the routing and state chapters that follow.

8.1 Project setup

create-vue scaffolds the SPA with TypeScript, Vue Router and Pinia preconfigured so you can start coding immediately. A Vite dev server proxy forwards API calls to your local Laravel application, avoiding CORS during development. Everything from the build tool to the linting setup is in place after one command.

npm create vue@latest client # scaffold the SPA
# choose: TypeScript, Router, Pinia, ESLint, Prettier
cd client && npm install && npm run dev

// vite.config.ts — proxy API in dev
export default defineConfig({
  server: { proxy: { '/api': 'http://localhost:8000' } },
  plugins: [vue()]
});

create-vue scaffolds the app and the Vite proxy forwards /api calls to Laravel during development.

8.2 Components with script setup

The Composition API in script setup reads like plain TypeScript: ref tracks mutable state and computed derives values reactively with zero boilerplate. Watchers and lifecycle hooks slot in naturally when side effects are needed. Components stay small, focused and easy to reason about.

<script setup lang="ts">
import { ref, computed } from 'vue' // reactivity helpers
const count = ref(0)
const doubled = computed(() => count.value * 2) // derived value recomputes on change
function inc() { count.value++ }
</script>

<template>
  <button @click="inc">{{ count }} ({{ doubled }})</button>
</template>

A minimal script setup component shows reactive state, a computed double and a click handler bound with @click.

8.3 Props, emits, slots

defineProps types the data flowing into a component and defineEmits declares the events it can fire, making the contract explicit. Slots allow parent components to inject markup into a child’s layout between its own content. TypeScript then flags mismatches between what parents pass and what children expect.

const props = defineProps<{ post: Post }>() // typed input from parent
const emit = defineEmits<{ (e: 'select', id: number): void }>() // typed event contract

<article @click="emit('select', props.post.id)">{{ post.title }}</article>

Typed props define what flows in and a typed emit contract defines what flows out, so components stay predictable.

Prefer <script setup> + Composition API: it is the modern default and plays best with TypeScript inference.

9 · Routing, State & Data Fetching

9.1 Vue Router9.2 Pinia stores9.3 A typed API client

This chapter gives the SPA navigation, shared state and one typed way to talk to Laravel. Vue Router handles navigation between views, Pinia stores shared client-side state, and a single Axios client carries every request. The three concerns each get a dedicated pattern used throughout the guide.

9.1 Vue Router

Vue Router maps URL paths to view components with history mode and lazy route imports. A global beforeEach guard inspects route meta flags and redirects unauthenticated users to the login page. Mark public routes with a meta flag so the guard lets them through without a session.

const router = createRouter({
  history: createWebHistory(), // real browser history
  routes: [
    { path: '/', component: HomeView },
    { path: '/posts/:id', component: PostView, props: true }, // params passed as props
    { path: '/login', component: LoginView, meta: { public: true } },
  ],
})

router.beforeEach((to) => { // auth guard, runs before navigation
  if (!to.meta.public && !useAuth().isLoggedIn) return '/login'
})

Routes map URLs to components and a global beforeEach guard bounces unauthenticated users to the login page.

9.2 Pinia stores

Pinia keeps reactive client-side state in one place, with state, getters and actions defined in a setup-style store. Actions fetch data from the API and components read the store instead of duplicating fetch logic. Because stores are reactive, every component using the store updates when the data changes.

export const usePosts = defineStore('posts', () => {
  const items = ref<Post[]>([]) // reactive cache of posts
  const loading = ref(false)
  async function fetchAll() {
    loading.value = true
    try { items.value = await api.get('/posts') }
    finally { loading.value = false }
  }
  return { items, loading, fetchAll }
})

The store owns reactive items and loading state and exposes a fetchAll action that writes the API result into it.

9.3 A typed API client

A single Axios instance carries the base URL, withCredentials for cookies and one shared error handler. An interceptor watches for 401 responses, refreshes the expired token through a refresh endpoint, then retries the original request transparently. Wrapping the client in typed functions keeps Laravel endpoints strongly typed in the frontend.

const api = axios.create({ baseURL: '/api/v1', withCredentials: true }) // base URL and cookies in one place

// Sanctum CSRF cookie must be fetched first for cookie auth:
await axios.get('/sanctum/csrf-cookie')

api.interceptors.response.use(r => r.data, async (err) => { // unwrap data; refresh on 401
  if (err.response?.status === 401) await refreshToken()
  return Promise.reject(err)
})

One axios instance carries base URL and cookies, unwraps response data, and refreshes the token before retrying after a 401.

10 · Forms & UI Patterns in Vue

10.1 Forms and validation10.2 Loading, empty and error states10.3 Component performance

Real forms need validation, loading states and performance discipline, and this chapter shows the patterns shared by every data-heavy Vue screen. Composable functions wrap form state, submission and error mapping so views stay declarative. Applying the same pattern everywhere keeps the UI consistent and maintainable.

10.1 Forms and validation

A reactive form holds its fields, posts them with Axios, and maps Laravel 422 errors back onto the matching inputs. Submit stays guarded until the form is valid and not already pending, so users only send clean data. On success the form resets and the view moves on.

const form = reactive({ title: '', body: '' }) // two-way form state
const errors = ref<Record<string, string[]>>({})

async function submit() {
  try { await api.post('/posts', form); router.push('/posts') }
  catch (e) {
    if (e.response?.status === 422) errors.value = e.response.data.errors // map Laravel errors to fields
  }
}

A reactive form is posted to the API and a 422 response copies Laravel’s per-field errors back onto the form.

Laravel returns 422 with an errors map keyed by field — map it straight onto your form fields.

10.2 Loading, empty and error states

Every async view needs loading, empty, error and success states so the user is never staring at a blank screen while a request runs. Track a pending flag, check whether the data array is empty, and render a friendly error with a retry button when a call fails. This turns every fetch into an explicit state machine.

  • Every async view needs loading, empty, error and success states.

  • Never leave the user staring at a blank screen.

10.3 Component performance

Lazy-load route components and virtualise long lists to keep bundles small and the UI smooth. Avoid over-optimising until measurements show a real bottleneck. Keeping components small and splitting dependencies by route pays off on slow connections.

11 · Inertia.js Alternative

11.1 What Inertia gives you11.2 Forms with useForm

Inertia renders Vue pages straight from Laravel controllers without a separate API, passing props and data instead of JSON. It is ideal when you want SPA UX while sharing auth, middleware and content with the server in one place. The frontend skips client-side data plumbing entirely.

11.1 What Inertia gives you

Controllers return Inertia page responses that name the Vue component and pass props, sharing auth state and middleware along the way. The client swaps in the versioned page component and reuses the shared layout, moving via small XHR payloads. You skip the API layer and still get a modern SPA experience.

Inertia lets Laravel controllers return Vue pages directly with props — no separate API, no client-side routing config for data, and shared middleware/auth. Perfect for teams who want SPA UX without building an API.

// Controller
return Inertia::render('Posts/Index', [ // render a Vue page with props
    'posts' => PostResource::collection(Post::latest()->paginate(20)),
]);

// Vue page receives props
<script setup lang="ts">
defineProps<{ posts: Paginated<Post> }>()
</script>

A Laravel controller renders a Vue page with paginated posts as props, then the Vue page types those props directly.

11.2 Forms with useForm

The useForm composable tracks fields and posts them through Inertia’s visit mechanism, mapping Laravel validation errors straight into form.errors per field. It also manages processing state and resets the form on success. This keeps form handling consistent without a hand-rolled request client.

const form = useForm({ title: '', body: '' }) // tracks fields and submit state
form.post('/posts', { onSuccess: () => form.reset() })
// Validation errors from Laravel appear on form.errors automatically.

useForm posts the fields and surfaces Laravel validation errors out of the box, resetting the form on success.

12 · Real-time with Reverb + Echo

12.1 Server side12.2 Vue client with Laravel Echo

Push updates to the SPA the moment they happen on the backend using Laravel Reverb as the websocket server. Reverb broadcasts events over websockets and Laravel Echo subscribes in the Vue client. This replaces polling with instant, server-driven updates across authorized private channels.

12.1 Server side

Run the install:broadcasting command to wire Reverb in, then reverb:start to launch the server. Private channels are authorized by a channel closure or channel class that checks the authenticated user. Broadcasting events with ShouldBroadcast and a channel name routes payloads to the right subscribers.

php artisan install:broadcasting   # sets up Reverb
php artisan reverb:start

// authorize who may join the private user channel
Broadcast::channel('user.{id}', fn (User $user, $id) => (int) $user->id === (int) $id);

install:broadcasting wires Reverb, reverb:start runs it, and a channel closure authorizes who may join the private user channel.

12.2 Vue client with Laravel Echo

Echo connects the SPA to the Reverb server using the key from your environment and the configured broadcasting driver. Listen on a private signed channel and push arriving items straight into a Pinia store so the UI updates reactively. The server only delivers events the channel authorization allowed.

import Echo from 'laravel-echo'
window.Echo = new Echo({ broadcaster: 'reverb', key: import.meta.env.VITE_REVERB_KEY }) // connect to Reverb

Echo.private(`user.${auth.userId}`) // join the owner's private channel
    .listen('PostCreated', (e) => store.items.unshift(e.post)) // push new posts into state

Echo subscribes to the private channel for the current user and unshifts each new PostCreated payload into the store.

For scale, run Reverb behind a load balancer or use a managed service (Pusher/Ably). On reconnect, re-fetch missed state from the API.

13 · Testing the Full Stack

13.1 Pest / PHPUnit feature tests13.2 Frontend tests

Tests lock in behavior on both sides of the wire. Feature tests cover the Laravel API endpoints, component tests cover the Vue views, and Playwright end-to-end tests prove the whole flow in a real browser. Each layer trusts the one below it only after it is verified.

13.1 Pest / PHPUnit feature tests

Feature tests hit real endpoints with factory-built users or data and assert on status codes, the JSON response and database state. Pest wraps PHPUnit so each test reads like a sentence with describe and it blocks. These tests prove routes, validation and middleware behave exactly as specified.

it('creates a post', function () {
    $user = User::factory()->create(); // factory user, no real data
    $this->actingAs($user)
        ->postJson('/api/v1/posts', ['title' => 'Hi', 'body' => 'Body text'])
        ->assertCreated(); // expects HTTP 201
    expect(Post::count())->toBe(1);
});

A Pest feature test acts as a factory user, posts valid JSON, asserts the created status and verifies exactly one post was made.

13.2 Frontend tests

Vitest mounts components with testing utilities, simulates clicks and typing, and asserts on the rendered output and emitted events. Testing Library style queries keep the tests close to how a user actually sees the app. Playwright end-to-end tests then drive the complete login and data flow in a real browser.

// Vitest + Vue Test Utils
import { mount } from '@vue/test-utils'
test('increments', async () => {
  const w = mount(Counter)
  await w.find('button').trigger('click') // simulate a real click
  expect(w.text()).toContain('1')
})

// End-to-end with Playwright against the running app.

Vitest mounts the component, triggers a real click and asserts the rendered text, with Playwright covering the full user flow.

Use a separate test database and RefreshDatabase so tests never touch real data. Seed factories, not fixtures.

15 · Deployment & Scaling

15.1 Deploying Laravel15.2 Scaling15.3 CI/CD pipeline

Ship the app reliably today and grow it tomorrow with scripted deploys, stateless application nodes and a CI pipeline that tests every change. Each release follows the same repeatable sequence so nothing is left to memory. Scaling then adds nodes and Redis-backed services only when the traffic pattern calls for it.

15.1 Deploying Laravel

The production sequence runs composer install, php artisan migrate --force, config caching and a worker restart in a fixed order. Zero-downtime deploys point a symlink at the new release directory instead of overwriting files in place. This release sequence makes every deploy identical and easy to roll back.

composer install --no-dev --optimize-autoloader # prod deps only, optimized autoloader
php artisan migrate --force
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan queue:restart   # signal workers to reload code

# Zero-downtime: deploy to a new release dir, switch a symlink, reload php-fpm.

The production sequence installs prod dependencies, force-migrates, caches config and routes, then restarts workers with zero downtime.

15.2 Scaling

Stateless application nodes behind a load balancer, Redis for shared sessions and cache, and independent queue workers let you add capacity horizontally. Read replicas offload reporting queries and a CDN serves static assets from the edge. Each layer scales on its own axis when traffic demands it.

  • Stateless app nodes behind a load balancer; sessions in Redis/DB.
  • Horizon workers scale independently of web nodes.
  • Redis for cache, sessions and queues.
  • Read replicas for heavy read traffic; a CDN for the SPA.
  • Octane (Swoole/FrankenPHP) for a persistent-worker speedup.

15.3 CI/CD pipeline

A pipeline installs dependencies, runs tests, builds and pushes a container image on every push, then deploys with a fresh migrate and restart. Automation makes releases boring and safe because the same steps run every time. A failed check blocks the deploy, so only verified code reaches production.

- run: composer install --no-dev --prefer-dist # install prod-facing deps
- run: php artisan test # run the whole suite
- run: npm ci && npm run build
- run: docker build -t ghcr.io/acme/app:$GITHUB_SHA . # bake an immutable image
- run: docker push ghcr.io/acme/app:$GITHUB_SHA
# deploy: migrate --force, symlink switch, queue:restart

A CI pipeline installs dependencies, runs tests and the build, then tags and pushes a Docker image ready for deploy.

16 · Performance Tuning

16.1 Backend16.2 Frontend

Fix the obvious backend and frontend hotspots before buying bigger machines. Profile first with your profiler or Telescope, then apply caching, query reductions and bundle splitting where they will actually help. Measuring each change against a baseline guarantees the effort is worth it.

16.1 Backend

Kill N+1 queries, select only the columns you need, cache expensive reads and queue slow work off the request path. Consider OPcache or Laravel Octane to raise request throughput, but profile before guessing. Validate every optimization against a measured baseline.

  • Fix N+1s; select only needed columns; paginate.
  • Cache expensive reads and computed aggregates.
  • Queue anything slow (email, media, third-party calls).
  • Use OPcache + optimize; consider Octane.
  • Profile with Telescope, Blackfire or Xdebug before guessing.

16.2 Frontend

Code-split by route, virtualise long lists, debounce searches and abort stale requests with AbortController. Then measure bundle sizes with Lighthouse and real-user metrics such as Core Web Vitals. The frontend stays responsive by shrinking both what loads and what renders at any moment.

  • Code-split by route; analyse the bundle.
  • Virtualise long lists; debounce search; abort stale requests.
  • Cache API responses; use skeleton loaders.
  • Measure with Lighthouse and real-user metrics.
