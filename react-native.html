Welcome — How to Use This React Native Guide

What this guide assumesHow the chapters fit togetherThe stack you will build withConventions and how to read the code

React Native is how you build real iOS and Android applications with React: the same components, hooks and one-way data flow, rendered to platform views instead of the DOM. This guide takes a cold machine to a released application on the stack that has become the default — Expo, TypeScript, React Navigation and the New Architecture.

What this guide assumes

0.1 React Prerequisites

You can already write React. Components, props, state, hooks and the closure-over-state trap are assumed knowledge, because React Native changes the host environment and not the programming model. If React itself is new to you, learn it first — this guide will not stop to explain what a dependency array is, and the middle chapters move quickly. TypeScript familiarity is also assumed: every sample is typed, and the ecosystem's types are good enough that arguing with them is wasted time.

What you need on the machine is modest:

  • Node 22.13 or newer — the floor Expo SDK 57 sets, plus a package manager. The samples use npm; nothing depends on it.
  • Android Studio for the emulator and SDK 36 tooling. An Android device over USB or Wi-Fi works too and catches bugs the emulator hides.
  • macOS with Xcode 26.4 or newer only when you build for iOS. You can complete the first half of this guide without ever touching a Mac.
  • A real phone with Expo Go installed. The gap between an emulator and a five-year-old handset is where most performance lessons live.
# 1. verify the toolchain before you blame the framework
node -v              # v22.13 or newer
java -version        # JDK 17+ for Android builds
npx expo-doctor@latest   # validates a project against the SDK's expectations

# 2. create the project exactly the way this guide does
npx create-expo-app@latest field-notes --template default
cd field-notes
npx expo start        # Metro bundler + QR code, the loop you will live in

A note on versions

Everything here targets Expo SDK 57, which pins React Native 0.86 and React 19.2. React Native ships roughly six releases a year and each Expo SDK locks to exactly one of them, so a single number describes your whole native toolchain. Where behaviour differs between SDK versions — and after 2025 it rarely does — it is called out in a note rather than left for you to discover on a Friday deploy.

The stack you will build with

0.2 Framework Overview

Mobile has more framework arguments than any other corner of the ecosystem, so it is worth stating the position this guide takes and why. Expo is the default build system, React Navigation the default navigator, TanStack Query the default server-state layer, Reanimated plus Gesture Handler the default motion stack, and Jest with React Native Testing Library plus Maestro the default test pyramid. These are not the only defensible choices, but they are the ones that work together without configuration.

The reason to start from defaults is not laziness. Every native dependency in a React Native app has to be compiled into two binaries and kept compatible with one specific React Native version; a library chosen because its API is prettier but which lags two releases behind will cost you more than it saves. The packages below are all New-Architecture-native, actively maintained, and pinned together by the SDK.

# expo install resolves the versions YOUR SDK was tested with.

# a different React Native and fail at compile time, not install time.

npx expo install react-native-screens react-native-safe-area-context
npx expo install react-native-reanimated react-native-gesture-handler
npx expo install @tanstack/react-query zod react-hook-form

npx expo-doctor@latest

Why Expo is the default in 2026

Expo used to mean a walled garden: a curated set of native modules, and if you needed one outside it you ejected. That world ended with development builds. Native code is now compiled on demand with expo prebuild, your own modules are included like any other dependency, and the android/ and ios/ folders are generated artifacts you keep out of version control. What remains is a real choice: Expo supplies the SDK, the build service, over-the-air updates and the config plugins, and you supply any native code you like. Roughly four out of five new projects built on the service run the New Architecture with no migration work at all, which is the other half of the argument.

Conventions and how to read the code

0.3 Code Conventions

Code samples are complete, runnable files unless a comment says otherwise. TypeScript is strict, components are function components with hooks, exports are named, and styles live in a StyleSheet.create block at the bottom of the file rather than inline. When a type would hide the idea being taught it is elided with a comment — never silently.

Three rules appear in nearly every sample, so they are worth stating before you meet them:

  • State updates are functional. setCount(c => c + 1), not setCount(count + 1). Chapter 5 explains the closure that makes the second form wrong.
  • Styles are static. Dynamic values are passed as one of several style objects, or produced by a memoised factory — never by rebuilding the whole object in render.
  • Async work is cancelled. Every effect that fetches returns a cleanup that aborts. Chapter 7 shows why "the request came back after I navigated away" is a correctness bug, not a cosmetic one.
import { useCallback, useState } from 'react';
import { FlatList, Pressable, StyleSheet, Text, View } from 'react-native';
import type { Item } from '../lib/types';

export function ItemList({ data, onOpen }: {
  data: Item[];
  onOpen: (id: string) => void;
}) {
  const [selected, setSelected] = useState<string | null>(null);

  const handleSelect = useCallback((id: string) => {
    setSelected(id);
    onOpen(id);
  }, [onOpen]);

  return (
    <View style={styles.list}>
      <FlatList
        data={data}
        keyExtractor={(item) => item.id}
        renderItem={({ item }) => (
          <Pressable
            onPress={() => handleSelect(item.id)}
            style={[styles.row, selected === item.id && styles.rowOn]}
          >
            <Text style={styles.rowTxt}>{item.title}</Text>
          </Pressable>
        )}
      />
    </View>
  );
}

const styles = StyleSheet.create({
  list: { flex: 1 },
  row: { padding: 16, borderBottomWidth: StyleSheet.hairlineWidth },
  rowOn: { backgroundColor: 'rgba(0, 156, 255, 0.12)' },
  rowTxt: { fontSize: 16 },
});

What is deliberately not in this guide

There are no class components, no componentWillReceiveProps, no manual Linking state, no Flux implementations and no "wrap it in a setTimeout to fix the render". Where the old answer survives in real codebases — a library still exporting a class, a mixin-shaped API — it is mentioned as migration context, because you will meet it, but it is never the pattern you are taught to reach for. Web-only concerns (SSR, SEO, the DOM) appear only where they explain a difference, and the guide never pretends React Native is a browser.

1 · React Native and the React Model

React Native does not change how you think about React; it changes what React is rendering into. This chapter fixes the mental model — two threads, host components, a bundler that does not type-check — because every performance and debugging decision later depends on it.

What React Native actually is

1.1 Native Components

React is a description engine: you give it a function of state, it works out what should be on screen. What makes React web and React Native different is only the last step — React web commits a diff of DOM nodes, React Native commits a diff of native views. There is no web view, no HTML and no browser underneath: a View becomes a real UIView on iOS and a real android.view.ViewGroup on Android, laid out by the Yoga engine and drawn by the platform's own compositor.

The result is that a React Native application is two programs in one binary: a native shell that owns the window, permissions and every platform API, and a JavaScript program compiled to Hermes bytecode that owns the logic. They are not layered the way a website layers script over markup — the JS side runs on its own thread and reaches the native side through JSI, a direct function-call interface rather than a serialised message queue.

// the same App component, two hosts

// WEB: the host is the DOM
import { createRoot } from 'react-dom/client';
createRoot(document.getElementById('root')).render(<App />);

// REACT NATIVE: the host is the platform view system
import { AppRegistry } from 'react-native';
import { App } from './src/App';
AppRegistry.registerComponent('FieldNotes', () => App);

// everything above this line is identical React. everything below the
// registration is where the two worlds diverge: no document, no window,
// no CSS cascade - a shadow tree that UIKit and Android render for you.

Two consequences follow immediately. First, web instincts about layout and style are wrong in specific, predictable ways — chapter 4 covers exactly which. Second, "it is slow" splits into three different questions: is the JavaScript slow, is the layout slow, or is the paint slow? They are measured in different places and fixed in different ways, and the framework gives you no single number called FPS.

What React Native is not

It is not a browser in a shell — projects that wrap a web view are a different technology with a different failure mode, and React Native's whole point is that a scroll view is the platform's scroll view. It is also not a canvas framework: React Native does not draw pixels itself the way Flutter does, which is why platform widgets, system fonts and platform scroll physics come for free, and why a custom-drawn control costs more effort here than in a drawing library. What it is, is React with the DOM swapped for two native view systems and a runtime that connects them.

// one screen, three layers - name the layer before you diagnose
//
//   src/screens/Home.tsx     React: state, props, effects, memoisation
//   React runtime + Yoga     shadow tree, layout, diffing, events
//   platform views           UIView / android.view, drawing, scrolling
//
// "the screen is slow" means three different bugs:
//   JS slow     -> too many renders, heavy work in a handler   (ch 11)
//   layout slow -> deep trees, absolute positioning everywhere (ch 4)
//   paint slow  -> huge images, overlapping shadows, overdraw   (ch 11)
//
// the perf monitor shows JS FPS and UI FPS separately for exactly
// this reason. learn to read the two numbers as two sentences.

JavaScript runs in Hermes, Meta's engine built for React Native: it pre-compiles to bytecode during the app build rather than at startup, which cuts time-to-first-frame and memory on low-end devices. It is not V8, so micro-benchmarks you have seen for Node or Chrome do not transfer — measure on device, in the release build, or do not measure at all.

Host components, not DOM elements

1.2 Host API

React Native exposes a deliberately small set of host components, and each one maps to a real platform view. View is the box that everything else lives in — the closest thing to a div, but it cannot contain raw text. Text renders a string and is a native label, not a styling wrapper. Image, TextInput, ScrollView, FlatList, Pressable and Modal cover most of what you will build; everything else is composition.

The first invariant a beginner meets is that text must be wrapped. A string directly inside a View is not a style problem, it is an invariant violation — the renderer refuses it, because there is no platform view that means "bare text". The second is that there are no h1–h6, span or button: semantics that HTML gives you implicitly have to be supplied explicitly through accessibility props, which chapter 3 covers properly.

// WRONG: raw string inside a View -> invariant violation at runtime
<View>{unreadCount} messages</View>

// RIGHT: text is a first-class native component
<View><Text>{unreadCount} messages</Text></View>

// Text nests, and a nested Text inherits what it can from its parent -
// this is how you style one word inside a sentence
<Text style={styles.body}>
  {'You have '}
  <Text style={styles.strong}>{unreadCount}</Text>
  {' unread messages'}
</Text>

Props map across one-to-one but the names differ where the web leaked implementation detail: there is no className, only style; there is no onClick, only onPress and the gesture events chapter 9 covers. Unknown props are not silently attached to a node the way a stray attribute is in HTML — they are ignored or warned about, because there is no element object for them to land on.

Why there is no innerHTML

There is no HTML parser in React Native, so a string is never markup. That is a security property as much as a limitation: an entire class of injection bugs cannot exist because a value you interpolate into Text is always text. When an app needs rich text — bold ranges, links inside a paragraph, bilingual strings with different fonts — the answer is nested Text components or a library built on the platform's attributed-string APIs, never a string assembled from tags.

// semantics are explicit, because nothing is implicit any more
// a web <button> announces itself; this must announce itself too.
<Pressable
  accessibilityRole="button"
  accessibilityLabel={'Delete ' + item.title}
  accessibilityHint="Removes the note from every device"
  accessibilityState={{ disabled: isDeleting }}
  hitSlop={8}
  onPress={() => onDelete(item.id)}
>
  <Text style={styles.deleteLabel}>Delete</Text>
</Pressable>

// hitSlop grows the touch target without growing the layout box -
// the difference between a usable row and a "my app feels
// imprecise" bug report. 44x44pt minimum, always.

Because Text and Pressable are native, text selection, dynamic type and screen readers behave the way the platform expects — a VoiceOver user gets real label semantics, and system font scaling works if you used relative units. Props that look like decoration are often the platform contract in disguise.

The JS thread and the UI thread

1.3 Threading

Two threads matter on every frame. The JavaScript thread runs your components, effects, event handlers and network callbacks. The UI thread — the main thread — handles touch input, layout, drawing and the platform's own animations. Under the old architecture both were glued together by an asynchronous bridge that JSON-serialised every call; under the New Architecture JSI lets JavaScript call native functions directly, but the threads are still separate, and the separation is where most real-world jank comes from.

The rule that falls out is simple: a long synchronous task on the JS thread stops handling presses, even while the UI thread paints beautifully. An animation driven by JS callbacks stutters whenever a fetch resolves in the middle of it. Neither problem shows up on a laptop emulator, because a laptop has ten times the CPU of the phone your user bought in 2021.

// this freezes taps for 300ms even though the UI thread is idle
const handleSearch = (query: string) => {
  const hits = ALL_ITEMS.filter((i) =>
    i.title.toLowerCase().includes(query.toLowerCase())
  ); // 60,000 rows, synchronous, on the JS thread
  setResults(hits); // and only THEN does the press state repaint
};

// better: keep the handler short and let React yield.
// useTransition marks the list update as interruptible, so typing
// stays responsive while the expensive render catches up.
const [isPending, startTransition] = useTransition();
const handleSearch = (query: string) => {
  setInput(query);                     // urgent: the field itself
  startTransition(() => setResults(     // non-urgent: the big list
    filterItems(query)
  ));
};

The mirror-image problem lives on the UI thread: layout invalidation, deep view hierarchies and anything that has to synchronously measure before drawing. This is why an animation should never depend on a JS round trip — Reanimated, chapter 9, runs its animation logic on the UI thread as worklets precisely so that a busy JS thread cannot steal frames from a gesture.

Profiling the two threads

The in-app performance monitor (shake the device, or Cmd/Ctrl+M) reports JS FPS and UI FPS as separate numbers, and the gap between them is a diagnosis. Low JS FPS with healthy UI FPS means your React code is the bottleneck — usually renders, usually list item factories or context churn. Healthy JS FPS with stuttering UI FPS means layout or overdraw. Both low usually means you did both, or that the whole device is simply being pushed past what it can do.

// measure the JS side with the engine's own clock
const t0 = performance.now();
const rows = buildRows(lotsOfData);   // pure JS work
console.log('buildRows', (performance.now() - t0).toFixed(1), 'ms');

// measure what React commits by timing an effect around the update
useEffect(() => {
  const t = performance.now();
  requestAnimationFrame(() => {
    console.log('frame after commit', (performance.now() - t).toFixed(1));
  });
}, [rows]);

// the three numbers that matter on a mid-range Android:
//   handler duration   < 16ms  so the press feels instant
//   per-row build      <  1ms  so a 50-row batch fits one frame
//   frame after commit < 32ms  so scrolling never drops to 30fps

Never ship the measuring code. A console.log inside a row component runs thousands of times per second during a scroll, and on Android the cost of the bridge-free call is still not zero — logging is a classic way to turn a fast list into a slow one. LogBox also pauses the app on warnings in development, which makes timing measurements meaningless. Measure in a release build, on the slowest device you own.

Rendering, reconciliation and Fast Refresh

1.4 Fast Refresh

Reconciliation works exactly as it does on the web: React compares element trees by type and key, then commits the minimal set of updates to the host. The difference is that the host is a shadow tree of native views, so a "DOM mutation" becomes a layout-invalidating native call. The same lesson applies with more force — re-rendering is expensive not because functions are slow, but because every committed change potentially invalidates layout on a device with a fraction of a desktop's power.

In practice this means the React skills transfer intact: stable keys, derived state, colocated state, memoised callbacks passed to list items. What does not transfer is the tolerance for sloppiness. A web app with 4,000 unnecessary renders per second may still feel fine on a M-series laptop; the identical app on a budget Android will drop to single-digit FPS during a scroll.

import { memo, useCallback } from 'react';

// memo only pays when props are stable. the parent must not rebuild
// onPress inline, or every row re-renders on every parent render.
type RowProps = { item: Item; onOpen: (id: string) => void };

const Row = memo(function Row({ item, onOpen }: RowProps) {
  const handlePress = useCallback(
    () => onOpen(item.id),
    [item.id, onOpen]
  );
  return (
    <Pressable onPress={handlePress} style={styles.row}>
      <Text style={styles.title}>{item.title}</Text>
      <Text style={styles.meta}>{item.updatedAt}</Text>
    </Pressable>
  );
});

// onOpen comes from useCallback in the list screen, onOpen is stable,
// item changes only when the data changes: 200 rows, 1 render each.

Fast Refresh is the other half of the render story. It re-executes the edited module in place and swaps the component tree while keeping component state, so you can edit a screen and see the change without losing what you had typed. The rules are narrower than people assume: state is preserved when you edit a component's body, but a change to hook order deliberately resets state, and edits to module-level variables re-run the whole module.

When Fast Refresh lies to you

Preserved state is a convenience that can hide a class of bug: a module-level cache or a stale closure that would be re-created on a cold start keeps living through your edits, so the app works in development and misbehaves for a user who launches it fresh. The discipline that catches this is to restart the JS bundle (press r in the terminal, or reload from the dev menu) every time something feels subtly wrong, and to smoke-test a release build before you believe a fix.

// Fast Refresh behaviour, by edit type:
//
//   edit a component's body        -> refresh, component state KEPT
//   edit a hook's dependency list  -> refresh, state KEPT (re-run effect)
//   change the ORDER of hooks      -> refresh, state RESET (correct)
//   edit a module-level variable   -> module re-executes, state LOST
//   edit a file that exports none of its components -> full re-import
//   edit native code or a config plugin            -> NO REFRESH:
//                                      you are editing the binary,
//                                      so rebuild (ch 2)
//
// the trap: state kept == old closure may still be alive. when a fix
// "works" but a reload breaks it, you are debugging Fast Refresh,
// not your app. press r, then look again.

Fast Refresh only observes JavaScript. A change to app.config.ts, a config plugin, an asset registered with require() in a native-facing way, or a dependency with native code all require the binary to be rebuilt — which is chapter 2's entire subject. Knowing which of the four kinds of change you just made tells you whether to wait one second or four minutes.

How your code becomes an app

1.5 Build Pipeline

The pipeline from .tsx to a shipped binary has four stages, and knowing them explains most "it works on my machine" mysteries. Babel (via babel-preset-expo) strips TypeScript and compiles JSX. Metro, the bundler, resolves every import into one JavaScript bundle and serves it from memory during development. At build time Hermes compiles that bundle to bytecode, which is embedded in the binary. Native dependencies are autolinked and compiled into the same binary by Gradle or Xcode.

Development and production differ in exactly one dimension that matters: development Metro serves source with Fast Refresh, production ships minified bytecode that was compiled once, on a build machine, ahead of time. Anything that behaves differently between the two — timing, globals, environment values — is usually a difference in when something was evaluated, not in how.

src/**/*.tsx
     |  babel-preset-expo: strip types, compile JSX, handle env vars
     v
JS bundle (one file, every import inlined by Metro)
     |  dev:  served from memory, source maps, Fast Refresh
     |  release: hermesc -> index.android.bundle (Hermes bytecode)
     v
binary -- gradle/xcode link native modules (autolinked from node_modules)

# the four kinds of change, and what each one costs you:
#   source / asset     -> reload        (~1 second)
#   dependency (JS)    -> restart bundle (~2 seconds)
#   config plugin / app.config.ts -> expo prebuild  (~10 seconds)
#   native module code -> full rebuild  (~2-5 minutes)

Three practical facts fall out of this pipeline. Metro does not type-check: it transpiles TypeScript away, so a type error ships silently unless something else runs tsc --noEmit. Environment variables are inlined at bundle time, which is why only the EXPO_PUBLIC_ prefixed ones are visible in code. And asset references must go through require() so Metro can fingerprint and copy them — a string path that works in a dev server 404s in a release build.

The four kinds of change

Classifying a change before you make it saves real minutes every day. Editing a component or style is a reload. Adding or upgrading a pure-JavaScript dependency is a bundle restart. Anything read by app.config.ts — permissions, bundle identifiers, plugins — requires regeneration of the native projects with expo prebuild. Anything that touches Swift, Kotlin or C++ requires a full rebuild of the binary, which is why native iteration is planned in batches rather than attempted line by line.

{
  "scripts": {
    "start": "expo start",
    "android": "expo run:android",
    "ios": "expo run:ios",
    "typecheck": "tsc --noEmit",
    "test": "jest --ci --coverage",
    "lint": "eslint . --max-warnings 0",
    "build:preview": "eas build --profile preview",
    "submit:preview": "eas submit --platform android --profile preview"
  }
}

tsc --noEmit in the scripts above is not optional decoration. Metro strips types without evaluating them, so an app that compiles perfectly can still be full of type errors; if the only check is "does it bundle", the first type error you will properly see is the one a user's crash report points at. Chapter 11 wires this into CI so the question never arises.

2 · Environment Setup: Expo vs Bare Workflow

The setup decision is the one decision that is expensive to reverse, so it is worth making deliberately. This chapter lays out the three starting points, shows the commands for each, and gives you the criteria that actually decide between them — most of which are about who maintains the native folders, not about features.

The three ways to start

2.1 Starting Options

There are exactly three starting positions, and they differ in one dimension: who owns the android/ and ios/ folders. Expo Go means nobody does — you run the pre-built shell from the store and your JavaScript is the entire app. A development build means expo prebuild owns them: they are generated from your config, compiled into a binary that contains your native modules, and regenerated whenever the config changes. A bare React Native project means you do — the folders are committed, hand-edited and merged by hand on every upgrade.

The three are not three religions; they are three points on one axis, and moving along it is a supported operation in both directions. What is not supported is pretending to be at two points at once, which is the state that causes the most confusing failures.

# 1. Expo Go — zero native setup, but only the modules in the store shell
npx create-expo-app@latest my-app
npx expo start                    # scan the QR with Expo Go

# 2. development build — YOUR binary, ANY native module you can install
npx expo install expo-dev-client
npx expo run:android              # compiles a binary with your modules
npx expo run:ios                  # needs a Mac; simulator or cable

# 3. bare React Native CLI — you own the native folders from day one
npx @react-native-community/cli init MyApp

Expo Go is a preview environment, not a deployment target, and the failure mode is abrupt: install a package with native code, keep running in Expo Go, and the app dies at launch with a module-not-found error that looks like a broken install but is really a wrong runtime. Development builds end that class of problem — the binary you test is compiled from the same dependency list your users will get.

What each path costs you

The real difference between the paths is not what they can do today but who pays at upgrade time. Expo Go costs nothing because there is no native code to maintain, and caps you at the SDK's module list. A development build costs a one-time compile and then keeps costing only what config plugins cost. A bare project costs manual three-way merges on every React Native upgrade, twice — once for Gradle, once for CocoaPods — plus the CI machine that has to have exactly the right Xcode, JDK and Android SDK versions installed.

// who owns android/ and ios/?
//   Expo Go          nobody - those folders do not exist in your project
//   dev build        "expo prebuild" regenerates them from config; keep
//                    them out of git and treat them as build output
//   bare RN CLI      you do - commit them, patch them, merge upgrades
//
// what breaks first in each path:
//   Expo Go          any module outside the store shell's list
//   dev build        a config plugin you forgot to declare, or a native
//                    dependency pinned to the wrong React Native
//   bare CLI         every React Native upgrade, and "works on my Mac"
//                    CI that only the one engineer who set it up can run
//
// the direction that is HARD: going backwards. un-owning native folders
// you have patched for a year means replaying every patch as a plugin.

The store shell is not frozen in time — Expo updates Expo Go for each SDK, roughly three times a year — but it is frozen relative to your app. If a bug only reproduces in Expo Go, ask first whether the module you are testing is even present in that binary.

Creating a project

2.2 Project Template

The default template gives you TypeScript, a file-based router, linting and a sensible folder layout — more than you need on line one, but all of it removable. If you are following this guide's navigation chapter, which builds on React Navigation directly, note that the two are not rivals: the default router is implemented on top of React Navigation, so choosing the library instead of its file-based wrapper is a smaller decision than it looks.

Three settings are worth deciding before the first commit, because changing them later means touching every file: strictness of the type checker, path aliases, and where shared code lives. Relative imports like ../../../../lib/api are the symptom of not deciding the third one, and they make a folder move a diff across fifty files.

npx create-expo-app@latest field-notes
cd field-notes

# everything native goes through expo install so versions match THIS SDK
npx expo install expo-dev-client
npx expo install react-native-screens react-native-safe-area-context

# one-time project settings, before the first commit
npx expo lint --init               # eslint config for the project
npx expo install --save-dev jest-expo

# run it
npx expo start                     # JS + assets, any device on the LAN

Metro resolves the path alias declared in tsconfig.json natively in current SDKs — there is no Babel plugin to install and no bundler config to write, which is a change from a few years ago when the alias had to be declared three times and the third omission produced a runtime-only failure. Declare it once, in the file TypeScript already reads.

Project settings that pay off now

strict: true is the setting people skip and regret: React Native's own types and the types of every serious library are written assuming it, and without it null checks disappear from your own code while the libraries still return nullables. The alias turns folder structure into a stable import vocabulary — @/lib/api means the same thing from any depth. And the Jest preset matters now rather than later, because jest-expo configures the transform and the native mocks that every test in chapter 11 will depend on.

{
  "extends": "expo/tsconfig.base",
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] },
    "types": ["jest"]
  },
  "include": [
    "**/*.ts",
    "**/*.tsx",
    ".expo/types/**/*.ts",
    "expo-env.d.ts"
  ]
}

Run npx tsc --noEmit from your editor's task runner now, not in week six. Metro discards types without checking them, so the bundler will happily hand a type error straight to production — the alias and strict only buy their guarantee if something actually evaluates them.

Native code, prebuild and development builds

2.3 Builds

expo prebuild turns configuration into native projects. It reads app.config.ts, evaluates every config plugin, generates a fresh android/ and ios/, applies your permission strings, bundle identifiers, version numbers and plugin modifications, and then Gradle or Xcode compile them as usual. The discipline that makes this work is called Continuous Native Generation: keep the folders out of version control, express every native change as code that prebuild applies, and the native projects become reproducible build output instead of a hand-maintained fork.

What breaks this discipline is a hand edit. Someone opens Android Studio, changes a Gradle line so the build passes on Friday, and the change evaporates the next time prebuild runs with --clean — or worse, it silently survives in one developer's folder and never reaches anyone else's. Every native change has exactly two legal forms: a config plugin, or a dependency that autolinks.

# inspect exactly what your config evaluates to - no guessing
npx expo config --type public

# generate (or regenerate) the native projects
npx expo prebuild                 # applies config + plugins, keeps extras
npx expo prebuild --clean         # from scratch: what CI should do

# a plugin runs DURING prebuild and mods the generated project
# app.config.ts:
#   plugins: ['expo-notifications', './plugins/with-camera-usage.js']

# most native modules need NOTHING but installation - autolinking
# registers them at build time. plugins are for manifest-level edits:
# permissions, URL schemes, gradle properties, plists.

A config plugin is a small JavaScript function that edits the generated native project: append a key to Info.plist on iOS, add a permission or an intent filter to AndroidManifest.xml, set a Gradle property. You write one when a module needs platform metadata that installation alone cannot supply — a camera permission string is the canonical example, because iOS will terminate an app that calls the camera without a usage description, and no amount of JavaScript can add that string after the binary exists.

When a config plugin is not enough

Some changes are structural: a new build phase, a modified Gradle plugin, an entitlement for push notifications. For those, prefer an existing published plugin — nearly every popular SDK ships one — and write your own only for the delta. When you do write one, keep it idempotent, because prebuild may run repeatedly over an existing folder, and a plugin that appends a duplicate manifest entry on every run will eventually produce a build error on a machine you do not have access to.

// plugins/with-camera-usage.js - evaluated at prebuild time
const { withInfoPlist, AndroidConfig } = require('expo/config-plugins');

module.exports = function withCameraUsage(config) {
  // iOS: without this string the OS kills the app on camera access
  config = withInfoPlist(config, (cfg) => {
    cfg.modResults.NSCameraUsageDescription =
      'Scans QR codes to join a shared notebook.';
    return cfg;
  });

  // Android: a manifest permission, added idempotently
  config = AndroidConfig.Permissions.withPermissions(config, [
    'android.permission.CAMERA',
  ]);
  return config;
};

Never mix the two ownership models. If prebuild generates the native folders, treat every file inside them as read-only build output; if you need a permanent hand edit, you have chosen the bare workflow and should stop running --clean — or better, replay the edit as a plugin and move back. A project where half the native changes live in git and half live in plugins is the hardest state to debug in React Native, because neither git log nor expo config tells the whole story.

Simulators, devices and the dev loop

2.4 Device Setup

Your loop is Metro plus a target. Metro serves the JavaScript bundle from memory and pushes updates over a socket, so a save becomes a screen change in about a second — but that loop has three hidden dependencies: the emulator must be awake, the device must reach the bundler over the network, and Metro's cache must still be valid. When any of the three is wrong, the symptom is always "my change did not appear", and the fixes are ordered by cost.

Targets differ in ways that decide your test plan. The iOS simulator is fast and accurate for layout but shares your Mac's CPU, so it lies about performance. The Android emulator is accurate enough for most behaviour and still lies harder about performance, because emulated devices run on your desktop's cores. Only a physical device gives you real frame timing, real keyboard behaviour and real network conditions — and a five-year-old Android handset is worth more as a test device than three emulators.

npx expo start --clear            # reset Metro's cache: the 90% fix
npx expo start --tunnel           # different network than the phone? use this
npx expo start --lan              # default: same Wi-Fi, fastest path

# device-side tools
#   Android: shake the device (or press m in the terminal) - dev menu
#   iOS sim: Cmd+D in the simulator window - dev menu
adb logcat *:S ReactNativeJS:V    # JS console output, on a real device
adb shell input keyevent 82       # open the Android dev menu via cable

# the cold-start ladder, cheapest fix first
#   1. press r in the Metro terminal      (reload the bundle)
#   2. npx expo start --clear             (drop the bundler cache)
#   3. rebuild the dev binary             (native deps changed?)
#   4. npx expo-doctor                    (version matrix wrong?)
#   5. rm -rf node_modules && npm install (last, not first)

Network deserves special mention because it is the failure that looks like a framework bug. On a guest Wi-Fi network with client isolation, the phone simply cannot reach your laptop, and Metro reports nothing at all — the app sits on the old bundle. The tunnel option relays traffic through Expo's servers and costs some speed; the reliable alternative is a USB cable and adb reverse tcp:8081 tcp:8081, which puts the bundler on the device through the USB connection itself.

The five-minute cold start

Every React Native developer eventually loses time to a wedged environment, and the symptoms are always the same: Fast Refresh stopped, a module that certainly exists "cannot be resolved", or an emulator refuses to install an update. The order above — reload, clear cache, rebuild, diagnose, reinstall — resolves nearly all of it. The mistake that multiplies the cost is starting at step five: deleting node_modules does not fix a stale Metro cache, it just makes you wait while the real cause is still there.

// symptom -> first move (in order, never skip to the last one)
//
// "Unable to resolve module @/lib/api"      -> alias missing in
//    tsconfig or Metro cache stale: restart with --clear
// "Cannot find module 'expo-camera'"        -> you are in Expo Go:
//    that module needs a development build  (see above)
// white screen on launch, logs show a throw -> module-scope code ran
//    before setup finished; read logcat, not the Metro terminal
// Fast Refresh stopped applying edits       -> --clear, then check
//    the terminal for a bundling error it may have swallowed
// INSTALL_FAILED_UPDATE_INCOMPATIBLE         -> uninstall the app on
//    the device, then run again (signature changed after prebuild)
// pods failing after an SDK upgrade         -> pod install --repo-update
//    inside ios/, or npx expo run:ios --no-build-cache

Keep one physical Android and one physical iOS device in the test rotation from the first week. The bugs they catch — cut-out safe areas on notched phones, keyboards that cover the submit button, list scrolling with touch instead of a mouse wheel, animations that drop frames while the emulator reports sixty — are all bugs you would otherwise ship to users, and all of them are chapters in this guide for exactly that reason.

Deciding: Expo or bare

2.5 Decision Framework

The honest 2026 answer is that you start with Expo unless you can name a specific reason not to, and the reasons that survive scrutiny are narrow: you are embedding React Native inside an existing native application, you need a platform React Native's Expo support does not target, or you maintain a white-label product whose native forks are the product. "We might need native code later" is not a reason — that is what development builds are, and compiling your own binary with your own modules is the normal path, not an escape from one.

The decision should also account for who is on the team. A bare project is a permanent commitment to maintain two native build environments on every developer's machine and in CI; an Expo project is a commitment to express native changes as configuration. For a small team shipping its first mobile product, the second commitment is almost always cheaper, and it is reversible in a way the first one is not.

                    Expo Go      development build     bare RN CLI
native modules       SDK only     anything you install  anything
compile time         none         ~1-3 min, cached      ~1-3 min, cached
who owns native      nobody       prebuild (from config) YOU
upgrades             one command  one command + prebuild manual merges
OTA updates          built in     built in              wire it up
CI complexity        low          medium                high
"escapes"            none needed  prebuild --clean      stay and merge

# bringing an EXISTING bare app into Expo, without losing anything:
npx install-expo-modules@latest   # adds Expo modules alongside yours
npx expo install expo-updates     # OTA channel, optional but cheap
# npx expo prebuild              # only when you are ready to hand the
#                                 native folders to config as code

Read the matrix by column rather than by row. Expo Go and a development build are the same JavaScript project seen at two moments of maturity; the bare CLI is a different project. And the migration arrows are asymmetric: moving from Go to a development build is one install, while moving from bare back to generated native folders means replaying every hand edit as a plugin first.

Signals you are on the wrong path

Three signals are worth trusting. First, upgrades take a day of Gradle and pod conflicts rather than an hour — that is the bare workflow's recurring tax, and it grows with every native dependency. Second, only one engineer can run the build — that means native setup has become tribal knowledge instead of configuration. Third, a native change cannot be reproduced from a clean checkout — if a fresh clone does not produce the same binary, the native folders are no longer source code, whatever they are called in the repository.

// choose by answering four questions, in this order:
//
// 1. embedding RN in an EXISTING native app, or targeting a platform
//    Expo does not support?                     -> bare, and stay there
// 2. do you need a native SDK this week that is not in the Expo SDK?
//    (a payments SDK, BLE, a bespoke device)    -> development build.
//    installing it and compiling your own binary is ONE command; it
//    does not imply the bare workflow at all.
// 3. do you want OTA updates, reproducible CI, and no Xcode on
//    anybody's laptop?                          -> Expo, EAS Build
// 4. is this a team's first mobile product?     -> Expo, unconditionally.
//    the thing you will underestimate is not the app code, it is the
//    two native build environments you just signed up to maintain.
//
// revisit when any of the four stops being true - the migration in
// the other direction is a script, not a project.

The choice is revisitable in both directions, but not for free. Moving up the axis (Go to development build, development build to bare-ownership) is a command. Moving down — un-owning native folders you have patched by hand for a year — means converting every patch into a plugin first, which is the migration everyone wishes they had started at month two instead of month twenty.

React Native ships a small component vocabulary, and the whole framework is a set of opinions about composing it. This chapter covers the components you will use in every screen — what each one maps to natively, where each one costs memory, and the rules the platform enforces that the DOM never did.

View and Text: the two primitives

3.1 View and Text

View is the universal container: a native view that lays its children out with flexbox, clips or not according to overflow, and exists in every combination of the interface. There is no span, no section, no ul — semantic roles are supplied later through accessibility props rather than inferred from tag names, which is chapter 3's last section. Almost every layout bug in React Native is a statement about a View that has no size: a container with neither flex, nor a dimension, nor a content-bearing child will collapse to zero, exactly as an empty div does, but with no inspector nudge to tell you which of the three was missing.

Text is the one component that behaves unlike anything on the web. It is a native label — UILabel, TextView — so strings must live inside it, it can itself be pressed, and it accepts layout props like numberOfLines that a web paragraph expresses with CSS. Styles nest: a child Text inherits what it can from its parent, which is how a bold word inside a sentence is built without a wrapper element.

export function Headline({ title, subtitle, onPress }: Props) {
  return (
    <View style={styles.block}>
      <Text
        style={styles.title}
        numberOfLines={2}
        ellipsizeMode="tail"
        onPress={onPress}      // Text is pressable in its own right
      >
        {title}
      </Text>
      <Text style={styles.sub} selectable={false}>
        {subtitle}
      </Text>
    </View>
  );
}

const styles = StyleSheet.create({
  block: { paddingHorizontal: 16, paddingVertical: 12 },
  title: { fontSize: 20, fontWeight: '600', lineHeight: 26 },
  sub: { fontSize: 14, marginTop: 4, opacity: 0.7 },
});

The whitespace rules are the most common silent bug. JSX collapses a newline-adjacent text segment, so an expression and a word on separate lines lose the space between them — the string renders as 12unread and no error is raised, because both fragments are individually valid. The fix is to make the space explicit, and to know that any run of spaces in source collapses to one.

Text rules the DOM never taught you

Four rules account for nearly every text surprise. Raw strings outside a Text throw an invariant. Newlines in a JS string render as line breaks, but JSX source newlines do not. Runs of spaces collapse to a single space, so aligned source does not align output. And long unbroken tokens — URLs, IDs, table names — need an explicit ellipsizeMode and a width, or they will push the layout sideways instead of wrapping.

// WRONG: JSX eats the newline, so the space vanishes with it
<Text>
  {count}
  unread messages
</Text>                     // renders "12unread messages"

// RIGHT: one of these three forms
<Text>{count + ' unread messages'}</Text>
<Text>{count} unread messages</Text>
<Text>
  {count}{' '}
  unread messages
</Text>

// and remember: source "a    b" renders "a b" - one space survives.
// indentation inside a Text is output, not formatting. it never was
// formatting on the web either; here there is no CSS whitespace
// property to rescue you.

numberOfLines is not a truncation preference, it is a layout contract: it caps the box, and combined with ellipsizeMode it is what lets a row keep a stable height in a list. Rows whose heights change as titles wrap are a major cause of scroll jitter, because every wrap invalidates layout for everything below it.

Image, caching and expo-image

3.2 Caching and expo-image

Image from react-native loads a URI into a native image view with resizeMode controlling the fit, and it caches in memory for the lifetime of the process. That is the whole story for a prototype. Production apps reach for expo-image, which adds a persistent disk cache, a blurhash or main-color placeholder, an animated transition, priority and recycling — the difference between a feed that feels instant on a second visit and one that refetches everything on every visit.

The performance rule underneath both is that the decoder works on the whole bitmap. A 4000-pixel photo rendered into a 160-pixel thumbnail allocates the full image before scaling it down, and on Android that allocation is one of the fastest routes to an out-of-memory kill. The server should send thumbnails; the client should ask for a size; and the row slot should be sized before the bytes arrive so nothing reflows when they do.

import { Image } from 'expo-image';

const BLURHASH = 'L6PZfSjE.AyE_3t7t7R**0o#DgR4';

export function Cover({ uri, label }: { uri: string; label: string }) {
  return (
    <Image
      source={{ uri }}
      placeholder={{ blurhash: BLURHASH }}  // instant paint, no pop
      contentFit="cover"
      transition={180}
      cachePolicy="disk"                    // survives an app restart
      priority="normal"
      accessibilityLabel={label}
      style={styles.cover}
    />
  );
}

const styles = StyleSheet.create({
  cover: { width: '100%', aspectRatio: 16 / 9, borderRadius: 4 },
});

Two habits make images cheap. First, size the slot: an aspectRatio box reserves space before the download, so the list does not reflow halfway through a scroll — reflow during scroll is what produces the stutter users describe as "the app feels rough". Second, warm the cache for what is about to be visible: prefetching the next handful of rows while the user reads the first one moves the download off the moment of need.

Avoiding the layout jump

Layout jumps have a specific shape: row at height 88, image arrives, row grows to 140, every row below shifts, and because the finger was already down, the scroll position now points at different content. The defence is structural rather than cosmetic — every image lives in a box whose size is known from layout alone, and the image fills that box. When a source image can be any aspect ratio, the box still wins: contentFit="cover" crops instead of expanding.

// reserve the space FIRST, warm the cache EARLY
const styles = StyleSheet.create({
  row: { flexDirection: 'row', gap: 12, padding: 12 },
  thumb: { width: 84, height: 84, borderRadius: 4 }, // fixed: no reflow
  body: { flex: 1, justifyContent: 'center' },
});

// prefetch only what the user is about to see - prefetching a whole
// feed burns data and disk for rows that are never opened
const upcoming = data.slice(0, 10).map((i) => i.thumbUrl);
Image.prefetch(upcoming);

// measure the difference honestly: memory pressure on a low-end
// Android shows up as an OOM kill, not as a slow frame. use the
// memory meter in the dev menu while scrolling the real feed.

Never render an unbounded image list at full source resolution. The failure is not gradual — Android kills the process, iOS jetsams it, and the user sees the app "close randomly" with nothing in the logs you would recognise as your bug. Downsample on the server, cap the decoded size on the client, and treat the memory meter as a dashboard you check before release, not after the first store review mentioning crashes.

ScrollView and the windowing problem

3.3 Scroll Performance

ScrollView lays out every child it is given, eagerly, at mount. That is exactly right when the content is known and bounded — a form, a settings screen, a profile page — because a small number of native views laid out once is the cheapest thing a UI can do. It also gives you the integration points a static page needs: a pull-to-refresh control, keyboard avoidance, scroll-to-bottom on focus, and content insets that respond to the safe area.

The failure mode arrives the moment content is unbounded. A feed inside a ScrollView creates every row's native views before the first frame, so mount cost grows linearly with history, memory grows linearly with history, and the first scroll gesture pays for a layout pass over all of it on the UI thread. The windowed lists — FlatList and SectionList, both built on VirtualizedList — exist to break that linearity, and chapter 7 tunes them properly.

export function ProfileScreen({ user, reload, loading }: Props) {
  return (
    <ScrollView
      contentContainerStyle={styles.content}
      contentInsetAdjustmentBehavior="automatic"
      keyboardShouldPersistTaps="handled"
      refreshControl={
        <RefreshControl refreshing={loading} onRefresh={reload} />
      }
    >
      <Avatar user={user} />
      <Stats user={user} />
      <Biography text={user.bio} />
      <RecentNotes notes={user.recent} />   // bounded: 5 items
    </ScrollView>
  );
}

const styles = StyleSheet.create({
  content: { padding: 16, gap: 24, flexGrow: 1 },
});

Three props do most of the work. contentContainerStyle styles the content rather than the viewport — on the web you would use the inner wrapper div, and getting the two confused is why "my padding does not work" is a real support question. keyboardShouldPersistTaps decides whether a tap outside the keyboard dismisses it or activates the control under it, and "handled" is almost always the right value. refreshControl attaches the platform's native pull-to-refresh, which cannot be faked convincingly with JS.

Nested scroll: the rule

A screen may have one scrolling axis of its own; anything else is a negotiation that must be set up deliberately. A vertical ScrollView inside another vertical one requires the inner to have a bounded height and, on Android, nestedScrollEnabled — without both, one of them simply wins and the other becomes unscrollable depending on where the finger starts. Horizontal inside vertical is well-behaved, because the two gestures differ in direction and the responder system can tell them apart.

// choosing the container, once and for all:
//
//   content known, < ~20 views, does not grow   -> ScrollView
//   a form, a settings screen, a profile        -> ScrollView
//   a feed, chat history, gallery, search results
//     that can grow without bound               -> FlatList   (ch 7)
//   grouped data with sticky headers            -> SectionList (ch 7)
//
// why the number matters: ScrollView creates every child eagerly.
//   50 rows  -> 50 native views, laid out once, invisible cost
//  500 rows  -> 500 native views BEFORE first paint, one giant
//               layout pass on the UI thread, and every state change
//               above them invalidates all of them
//
// a list that "feels fine with mock data" and crawls with real data
// is almost always this decision, made too early.

If a screen needs both a long body and a fixed header or tab bar, do not nest a full-height scroll view inside another. Give the header its own row, let the body own the remaining flex, and let the body be the only scroller. One scroll owner per screen is the rule that keeps Android's nested scrolling predictable.

Pressable and touch handling

3.4 Touch Handling

Pressable is the primitive behind TouchableOpacity, TouchableHighlight and most library buttons: a component that participates in the responder system, reports press lifecycle events, and renders feedback through a style function instead of an animated wrapper. Its signature feature is that the pressed state arrives as an argument to style, so the visual response is a pure function of the interaction — no state to set, no effect to run, no re-render for a highlight.

Touch is not click. A tap has to be distinguished from the scroll that may follow it, from a long press, and from an accidental brush while the user is reaching for something else. The responder system resolves this by letting the scroll view claim the gesture once the finger moves past a slop distance, at which point the row's onPress will never fire — which is the behaviour you want, and the reason rows should be a single Pressable rather than a click handler on an inner element.

export function SaveButton({ onSave, busy }: Props) {
  return (
    <Pressable
      onPress={onSave}
      disabled={busy}
      hitSlop={8}                       // grow the target, not the box
      android_ripple={{ color: 'rgba(3, 77, 184, 0.25)' }}
      accessibilityRole="button"
      accessibilityState={{ disabled: busy, busy }}
      accessibilityLabel="Save note"
      style={({ pressed }) => [
        styles.btn,
        pressed && styles.btnPressed,
        busy && styles.btnBusy,
      ]}
    >
      <Text style={styles.label}>
        {busy ? 'Saving...' : 'Save'}
      </Text>
    </Pressable>
  );
}

const styles = StyleSheet.create({
  btn: { height: 48, borderRadius: 4, alignItems: 'center',
         justifyContent: 'center', paddingHorizontal: 20 },
  btnPressed: { opacity: 0.85 },
  btnBusy: { opacity: 0.5 },
});

hitSlop is the prop that separates a usable interface from a fiddly one: it extends the touch area without changing layout, so a 24-point icon in a 44-point row responds across the whole row while the visual design stays tight. delayLongPress tunes the long-press threshold, pressRetentionOffset decides how far the finger may drift before the press is lost, and onPressIn/onPressOut let you start and cancel an animation at exactly the moments the user's finger does.

Tap versus scroll

The arbitration rule is worth internalising: the responder that receives the touch first may keep it, and a scroll view that claims the gesture releases the tap permanently, even if the finger returns to the original position. That is why a row implemented as a full-area Pressable behaves correctly while a row with an inner button and a separate row handler does not — in the second design, the scroll and the button fight over the same touch, and the winner depends on where the finger started.

// what actually happens when a finger moves:
//   press-in        -> the row gets the responder, highlights
//   move ~10 points -> the scroll view claims the gesture
//   move back       -> the row does NOT regain it
//   release         -> no onPress, the list scrolled. correct.
//
// the design consequences:
//   1. one Pressable per row, covering the WHOLE row. an inner
//      button that only covers the icon gives a 24pt target in a
//      56pt row and users aim at the row.
//   2. do not attach a second gesture recognizer to the same area
//      unless you want to arbitrate between them yourself (ch 9).
//   3. onPress must be safe to receive a press that followed a
//      micro-scroll - check whether anything actually changed.
//   4. long press for secondary actions, but ALWAYS provide a
//      visible alternative: gestures without affordance are
//      undiscoverable, and inaccessible by definition.

A press handler that navigates must be idempotent for a double tap. Network plus navigation in one onPress with no guard is how a screen ends up pushed twice and a record created twice; guard with a ref or a pending state, and make the server side idempotent anyway — chapter 8 covers the submitting state properly, and chapter 14 makes the server assume duplicates arrive.

Accessibility and touch targets

3.5 Accessibility

Accessibility props are not a compliance checkbox layered on afterwards; they are the semantic layer that the tag soup of HTML gave you for free. A native view announces itself through role, label, value and state, and if you do not supply them the screen reader announces nothing useful — it reads the view's coordinates or, worse, stays silent. Supplying them also happens to make the interface better for everyone: a labelled icon button is easier to hit, understand and test.

The vocabulary is small. accessibilityRole says what the element is ("button", "header", "link", "tab"). accessibilityLabel says what it is called, and should read as an outcome — "Delete note", not "X". accessibilityState exposes disabled, selected, checked. accessibilityHint adds what happens next when the label alone is ambiguous. On a container, accessible groups its children into one focusable unit — useful for a row, dangerous for anything containing a control.

export function NoteRow({ item, onOpen, onArchive }: Props) {
  return (
    <Pressable
      accessible
      accessibilityRole="button"
      accessibilityLabel={'Note ' + item.title}
      accessibilityValue={{ text: 'Edited ' + item.editedLabel }}
      accessibilityHint="Opens the note for reading and editing"
      testID={'note-row-' + item.id}
      onPress={() => onOpen(item.id)}
      onLongPress={() => onArchive(item.id)}
      hitSlop={4}
      style={styles.row}
    >
      <Text style={styles.title}>{item.title}</Text>
      <Text style={styles.meta}>{item.editedLabel}</Text>
    </Pressable>
  );
}

Target size and font scaling are the two checks that catch real reports. Every actionable element needs a 44-point (iOS) or 48-dp (Android) touch area, which hitSlop provides without changing the design. And text must survive the platform's largest font setting: allowFontScaling defaults to true, which means a fixed-height row with numberOfLines will clip at large sizes — the accessible behaviour is to let the row grow, and clip only the truly decorative text.

Checking it without a device across the room

You can verify most of this without leaving the editor. Turn on VoiceOver in the iOS simulator or TalkBack on the Android emulator and navigate by focus: if the order jumps, if a control is silent, or if a label reads as gibberish, the props are wrong. Then query the same labels in tests — a testing library that resolves elements by accessibility label forces the labels to exist, so the test suite becomes a second enforcement of the same contract.

// per-screen accessibility checklist (run it in BOTH readers once):
//
//  roles      every actionable element has accessibilityRole
//  labels     outcome-first: "Delete note", never "X" or "icon"
//  state      disabled / selected / checked exposed, not implied
//  targets    44pt / 48dp minimum, or hitSlop grows the area
//  contrast   colour is never the only signal - pair icon or text
//  scaling    survives 200% font without clipping the ACTION
//  order      focus order matches visual order on every screen
//  motion     reduce-motion respected: swap animation for a fade
//
// and the two automated equivalents, both cheap:
//   jest:  getByLabelText('Delete note') fails if the label is gone
//   CI:    accessibility audit script over the tree (ch 11)
//
// a screen reader label is also a test selector and a voice-control
// target. write it once, get all three.

The fastest discipline is to navigate every new screen with TalkBack once before merging it. It costs two minutes and it finds unlabeled icon buttons, focus order that makes no sense, and controls that are visually 44 points but only respond to their inner 12 — the three defects users actually report, and none of which a screenshot review would ever catch.

4 · Styling and Flexbox on Mobile

React Native threw the cascade away, and what replaced it is a smaller and stricter system: style objects drawn from a fixed vocabulary, flexbox with defaults opposite to the web, a unit that is not a pixel, and no media queries at all. This chapter builds the model that makes a layout question answerable in one pass instead of five.

Styles are objects, not CSS

4.1 Style Objects

React Native has no CSS. The style prop takes a plain JavaScript object whose keys are drawn from a fixed, documented vocabulary — colour, margin, flex, opacity — and a key outside that vocabulary is not quietly ignored the way an unknown CSS property is ignored in a browser; it is reported. There are no selectors, so there is no specificity: the rule you wrote in March cannot beat the rule you wrote today, because there is no cascade to arbitrate between them. Every visual fact lives on the element that uses it, which makes a screen file readable top to bottom in a way that a component backed by four stylesheets rarely is.

What is given up is composition by class name. On the web you accumulate utility classes and let the stylesheet decide; here composition is code — arrays of style objects, flags spread into them, small functions that return an object — and the decision is made by position: the last entry in the array wins, always. That one rule is what makes theming tractable, because a theme override appended after a base style beats it by construction, and the component never needs to know which of its styles came from a theme. It also makes a falsey flag harmless: selected && styles.selected contributes false when the flag is off, and the array simply skips it.

import { StyleSheet, View, Text } from 'react-native';
import { palette } from '../theme/palette';

export function Card({ title, body, highlighted }) {
  // the flag is appended after the base style, so it wins - position
  // decides, there is no specificity to argue about
  const tone = highlighted ? styles.highlighted : styles.quiet;

  return (
    <View style={[styles.card, tone]}>
      <Text style={styles.title}>{title}</Text>
      <Text style={styles.body}>{body}</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  card: {
    borderRadius: 12,
    padding: 16,
    borderWidth: StyleSheet.hairlineWidth,
    borderColor: palette.border,
  },
  highlighted: { backgroundColor: palette.accent },
  quiet: { backgroundColor: palette.surface },
  title: { color: palette.text, fontSize: 17, fontWeight: '600' },
  body: { color: palette.textMuted, fontSize: 15, marginTop: 6 },
});

Two habits keep this from becoming the inline-style swamp that React on the web became. The first is one StyleSheet.create block per component, at the bottom of the file where it can be read as a summary of everything the component can look like. The second is never an object literal inside JSX: style={{ padding: 16 }} allocates a fresh object on every render and hands the engine something new to compare each time, for a value that never changes.

Why StyleSheet.create still exists

It looks like an identity function — you hand it an object and get the same object back — but in development it is a validator. A misspelled key or a value of the wrong type throws at module load with a stack that points at the line you wrote, instead of producing a silently missing margin that gets discovered on a physical device three days later. It also gives the type checker one object to check, so renaming a token becomes a refactor the compiler verifies rather than a hunt through inline literals. In production the function returns your object as-is; on the old architecture it had allocated a static identifier that crossed the bridge once per style, which was a real optimization, and that history is why the API survived the rewrite intact.

Mutation is the other trap. Styles passed to StyleSheet.create are frozen in development, so writing to a property throws where it happens rather than at the call site you blamed. If a component genuinely needs different values at run time, that is not a mutation, it is a second style in the array — and because position decides, the second style is also the correct place for it.

import { StyleSheet, View, Text } from 'react-native';
import { palette } from '../theme/palette';

// false disappears from the array; no nested ternaries, no dead object
export function Chip({ label, selected, disabled }) {
  return (
    <View
      style={[
        styles.chip,
        selected && styles.selected,
        disabled && styles.dimmed,
      ]}
    >
      <Text style={[styles.label, selected && styles.labelOn]}>
        {label}
      </Text>
    </View>
  );
}

const styles = StyleSheet.create({
  chip: {
    paddingHorizontal: 12,
    paddingVertical: 6,
    borderRadius: 999,
    borderWidth: 1,
    borderColor: palette.border,
    alignSelf: 'flex-start',
  },
  selected: { backgroundColor: palette.accent, borderColor: palette.accent },
  dimmed: { opacity: 0.45 },
  label: { fontSize: 13, color: palette.text },
  labelOn: { color: palette.accentInk, fontWeight: '700' },
});

Keep styles in the file that uses them. Shared styles should become a component or a wrapper function, never an imported stylesheet: the moment a style object is imported from another module you have reintroduced the cascade, with worse tooling and no inspector.

Flexbox defaults: column, not row

4.2 Flexbox Defaults

The default flexDirection in React Native is column; on the web it is row. The framework chose the direction a phone screen actually stacks — title above body above action — and the consequence is that every horizontal arrangement becomes an explicit decision you write down. Once a container sets row, two questions decide the entire layout, and they are always the same two: which axis is the main axis, where justifyContent distributes children, and where children sit on the cross axis, where alignItems places them. Reading any layout as main axis first, cross axis second, before touching a property, turns most layout debugging into a lookup rather than an experiment.

The default that catches people out is not the direction, it is shrinking. On the web a flex item shrinks to fit because flex-shrink defaults to 1; in React Native flexShrink defaults to 0. A row holding a long unbroken title and a timestamp therefore does not squeeze the title — it pushes the timestamp off the right edge, with no warning and no scroll, because the row itself is not a scroll region. The fix is a rule worth writing into a team convention: any child of a row that holds variable-length content gets flex: 1, and any child that must keep its exact size — an avatar, a badge, a button — gets flexShrink: 0 explicitly, so the intent survives even where the default already agrees with it.

The structural convention that follows is the screen skeleton: one root view at flex: 1, exactly one region that grows, everything else sized by its content. Screens built without that rule end up with three children all claiming to grow, which on a fixed-height screen means the middle one silently loses, and the bug presents as a footer that sometimes appears. Spacing between siblings no longer needs margin arithmetic either — gap has been supported since React Native 0.71, so a stack of items with even spacing is one property on the container.

import { View, Text, Pressable, StyleSheet } from 'react-native';
import { SafeAreaView } from 'react-native-safe-area-context';
import { palette } from '../theme/palette';

export function Screen({ title, children, onContinue }) {
  return (
    <SafeAreaView style={styles.root}>
      <View style={styles.header}>
        <Text style={styles.title}>{title}</Text>
      </View>

      {/* exactly one region grows: the body. headers and footers are
          sized by their content, so scrolling belongs to the body */}
      <View style={styles.body}>{children}</View>

      <View style={styles.footer}>
        <Pressable style={styles.cta} onPress={onContinue}>
          <Text style={styles.ctaText}>Continue</Text>
        </Pressable>
      </View>
    </SafeAreaView>
  );
}

const styles = StyleSheet.create({
  root: { flex: 1 },
  header: { paddingHorizontal: 16, paddingVertical: 12 },
  body: { flex: 1, paddingHorizontal: 16 },
  footer: { paddingHorizontal: 16, paddingTop: 8, paddingBottom: 12, gap: 8 },
  cta: { backgroundColor: palette.accent, padding: 14, borderRadius: 8 },
  ctaText: { color: palette.accentInk, textAlign: 'center', fontWeight: '600', fontSize: 16 },
  title: { fontSize: 20, fontWeight: '700', color: palette.text },
});

Centering: the three cases

Almost every centering question resolves to one of three answers, and naming the case first stops the property guessing. Center in both axes: put both justifyContent: 'center' and alignItems: 'center' on the container — the classic mistake is setting one and staring at a child that is still flush against an edge. Center along one axis only, such as a header row where the title sits mid-height but the action belongs at the end: alignItems: 'center' for the cross axis and justifyContent: 'space-between' to push the two ends apart. And center a single child without disturbing its siblings: alignSelf: 'center' on that child, which overrides the container's cross-axis decision for exactly one element. When none of the three fits, the container is usually the wrong shape — a child with no intrinsic height cannot be centered vertically, because there is nothing to center.

import { View, Text, Image, StyleSheet } from 'react-native';
import { palette } from '../theme/palette';

export function ThreadRow({ avatar, title, preview, time }) {
  return (
    <View style={styles.row}>
      <Image source={{ uri: avatar }} style={styles.avatar} />

      {/* flex: 1 on the variable-length middle. without it, a long
          title pushes the timestamp off the right edge, because
          flexShrink defaults to 0 in React Native */}
      <View style={styles.text}>
        <Text style={styles.title} numberOfLines={1}>{title}</Text>
        <Text style={styles.preview} numberOfLines={2}>{preview}</Text>
      </View>

      <Text style={styles.time}>{time}</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  row: { flexDirection: 'row', alignItems: 'center', gap: 12, paddingVertical: 10 },
  avatar: { width: 44, height: 44, borderRadius: 22, flexShrink: 0 },
  text: { flex: 1, flexShrink: 1 },
  title: { fontSize: 16, fontWeight: '600', color: palette.text },
  preview: { fontSize: 14, marginTop: 2, color: palette.textMuted },
  time: { fontSize: 12, color: palette.textMuted, flexShrink: 0 },
});

When a row runs off the right edge of the screen, the first suspect is the missing flexShrink on its variable-length child, not the row's own width. The row is only reporting what its children asked for, and a fixed-width child plus a zero-shrink child equals a container that cannot fit — on a screen with no horizontal scrollbar to absorb the difference.

Points, pixels and density

4.3 Pixel Scaling

A number in a React Native style is not a pixel. It is a density-independent point — a point on iOS, a density-independent pixel on Android — and the engine converts it to physical pixels using the screen's scale factor at layout time. The same 16 is therefore roughly the same physical length on a 160 dpi phone and a 520 dpi one, which is the entire reason mobile operating systems invented the unit: without it, every design either looks microscopic on a flagship or enormous on a cheap device, and the fix is never a media query.

The unit system is also deliberately tiny. There is no px, no rem, no em, no vh; lengths are unitless numbers, and the only string accepted in a length position is a percentage such as '50%', which resolves against the parent's measured size during layout. Because every number is the same unit, there is no unit arithmetic to get wrong either — marginBottom: 8 plus paddingTop: 8 is sixteen points, full stop, and the calc() class of bug has no way to enter the codebase. Percentages remain useful for one specific job: a child that should be a fixed fraction of a parent whose height you do not know, where flex would give you a ratio across the whole axis instead.

The other half of the equation is text. By default React Native scales fonts with the operating system's accessibility setting — a user who has set their phone to 200 percent text size will see your 15-point body copy at 30 points, which is correct and required for accessibility, and which will break any layout that assumed one size. The policy is set per element: allowFontScaling={false} opts a single element out entirely, and maxFontSizeMultiplier caps how far a single element may grow. Both are legitimate on genuinely fixed-shape elements — a counter pill, a chart axis label — and both are an accessibility defect when applied to body copy, because the user who needs the larger text cannot ask your component for it.

import { PixelRatio, useWindowDimensions } from 'react-native';

// the design comp is 390 pt wide. type follows the width but stops at
// both walls, so a foldable cannot turn body copy into a poster
const BASE_WIDTH = 390;
const MIN = 0.92;
const MAX = 1.15;

export function useTypeScale() {
  const { width } = useWindowDimensions();
  const raw = width / BASE_WIDTH;
  const clamped = Math.min(MAX, Math.max(MIN, raw));
  return Math.round(clamped * 100) / 100;
}

// snap a computed length to a whole physical pixel: a 14.4 pt rule
// laid across a half-pixel boundary comes out of the compositor
// blurred, which is why hairlines use StyleSheet.hairlineWidth
export function snap(points) {
  return PixelRatio.roundToNearestNear(points);
}

PixelRatio in practice

PixelRatio.get() returns the screen's scale factor — 2 on most phones, 3 on flagships, higher on tablets — and PixelRatio.getFontScale() returns the user's text-size multiplier separately, which is the value you need when a component must track accessibility text without tracking device density. getPixelSizeForLayoutSize converts points to physical pixels for the cases where you are drawing rather than laying out: exporting a view to an image, sizing a canvas, or preparing a bitmap for a native API that speaks pixels. Asset naming follows the same convention without any code at all — icon.png, icon@2x.png, icon@3x.png — but the require that loads them must stay static, because the bundler resolves module paths at build time and cannot follow a path assembled at run time.

import { View, Text, StyleSheet } from 'react-native';
import { palette } from '../theme/palette';

export function Readout({ value, hint }) {
  return (
    <View style={styles.row}>
      {/* a fixed pill: growing it with the OS font size would break
          the shape, so this element opts out */}
      <Text style={styles.badge} allowFontScaling={false}>
        {value}
      </Text>

      {/* prose follows the OS setting, capped so a 200 percent
          system size cannot swallow the rest of the screen */}
      <Text style={styles.hint} maxFontSizeMultiplier={1.6} numberOfLines={3}>
        {hint}
      </Text>
    </View>
  );
}

const styles = StyleSheet.create({
  row: { flexDirection: 'row', alignItems: 'center', gap: 8 },
  badge: {
    fontSize: 13, fontWeight: '700', color: palette.accentInk,
    backgroundColor: palette.accent, paddingHorizontal: 8,
    paddingVertical: 3, borderRadius: 999,
  },
  hint: { flex: 1, fontSize: 14, color: palette.textMuted },
});

Font scaling interacts with numberOfLines: truncation is decided after scaling, so a hint that fits at the default size can clip at 150 percent. If truncation matters, detect it rather than assume — onTextLayout reports the rendered line count, and a component that hides overflow it never measured is a component that hides content from exactly the users who enlarged the text.

Responsive layouts and breakpoints

4.4 Breakpoints

There are no media queries in React Native. The measurement comes from a hook: useWindowDimensions returns width, height, scale and font scale, and the component that calls it re-renders when the device rotates, when a foldable opens, or when the window is dragged into a split-screen pane on Android. That is the entire responsive system — read the width, branch on it, render a different arrangement — and it is simpler than media queries because the branch lives in JavaScript where it can be unit tested, instead of in a stylesheet where it is silently re-derived on every layout pass.

The discipline this demands is knowing where the branch belongs. A breakpoint decision belongs in the layout component that owns the arrangement — the one that decides whether the screen has one pane or two — and nowhere deeper. When every leaf calls its own useWindowDimensions, the whole subtree re-renders on each rotation, and a width value ends up coupled to a label that never actually changed. Measure once at the top, hand the decision down as a prop or through context, and a rotation costs one component's render instead of the screen's.

Coverage is three cases, not thirty devices. The narrow end is a small phone in portrait; the wide end is a tablet or a desktop-class window; the awkward middle is Android split-screen, where a phone in landscape can suddenly be handed a 480-point window that behaves like neither. A foldable adds one more wrinkle — the hinge sits in the middle of the window — and the window segments API, available since React Native 0.76, reports the usable segments so content can avoid the hinge instead of being cut by it. Rotation itself is the cheap test: every responsive screen should be opened sideways at least once before it ships, because width and height swap and a layout written against width alone will notice.

import { useWindowDimensions } from 'react-native';

// width classes, not device names: a new 5.8-inch phone lands wherever
// its width puts it, and a tablet in split-screen behaves like a phone
export const BREAKPOINTS = { sm: 0, md: 600, lg: 900, xl: 1200 };

export function useBreakpoint() {
  const { width } = useWindowDimensions();

  if (width >= BREAKPOINTS.xl) return 'xl';
  if (width >= BREAKPOINTS.lg) return 'lg';
  if (width >= BREAKPOINTS.md) return 'md';
  return 'sm';
}

// re-renders on rotation and on split-screen resize, so the consumer
// of this hook must own layout - not a leaf label that merely prints
export function useIsWide() {
  const { width } = useWindowDimensions();
  return width >= BREAKPOINTS.md;
}

Choosing breakpoints that mean something

Number the classes, not the phones. A lookup keyed to a device model list — small phone, large phone, tablet — fails the first time a new model ships, and it fails silently, because the new device simply falls into the wrong branch. Width thresholds are portable: compact below 600 points, medium from 600 to 899, expanded at 900 and above, which are the window size classes Material publishes and which map cleanly onto structural facts. Below 600 there is genuinely room for one pane; from 600 a master-detail pair fits side by side with readable columns; from 900 a permanently pinned navigation rail stops costing content width. When a threshold corresponds to a structural fact like those, it stays correct for years; when it corresponds to a device, it is wrong on release day for the next device.

import { View, StyleSheet } from 'react-native';
import { palette } from '../theme/palette';
import { useIsWide } from './useBreakpoint';

export function Inbox({ list, detail }) {
  const wide = useIsWide();

  return (
    <View style={styles.frame}>
      <View style={[styles.list, wide && styles.listPinned]}>
        {list}
      </View>

      {/* narrow: one pane, and the detail replaces the list through
          navigation (chapter 6). wide: both, side by side */}
      {wide ? <View style={styles.detail}>{detail}</View> : null}
    </View>
  );
}

const styles = StyleSheet.create({
  frame: { flex: 1, flexDirection: 'row' },
  list: { flex: 1 },
  listPinned: {
    maxWidth: 420,
    borderRightWidth: StyleSheet.hairlineWidth,
    borderColor: palette.border,
  },
  detail: { flex: 2, padding: 16 },
});

Set the device frame in your development client to the smallest width you support and leave it there for a day of work. Responsive bugs are found by being stuck at the narrow width, not by remembering to check it — and the narrow width is where a fixed maxWidth, an unshrinkable row, or a two-column form all fail first.

Design tokens and dark mode

4.5 Design Tokens and Dark Mode

A colour typed into a component is a decision made locally and enforced globally: it cannot be re-themed, checked for contrast, or changed in one place later. The rule that keeps a codebase themable is that components never see a hex code — they ask for a role: surface, raised surface, text, muted text, accent, border. Two palettes then satisfy every component, and adding a third mode — high contrast, AMOLED black, a corporate skin for a white-label build — becomes a data change rather than a refactor. It is the same discipline as CSS custom properties, with one difference: because styles are objects, the tokens must travel through JavaScript, so they need an owner rather than a global scope.

The owner is a small theme module. useColorScheme from React Native returns 'light', 'dark' or null, re-rendering the component when the system theme changes at run time; null means the user has expressed no preference, and the app must pick a side rather than ask again on every render. Following the system is the right default. A user who opens your app in a dark room with the phone on dark should not be flashbanged by a white screen, and a user whose wallpaper-driven theme changed mid-session should not need to restart. An in-app override, if you ship one, pins the scheme through Appearance.setColorScheme and passes null to hand control back to the system.

Two palettes sharing one vocabulary is only half of it; the palettes themselves must be checked rather than eyeballed. Contrast is a ratio with a threshold: 4.5 to 1 for body text, 3 to 1 for large text and for the edges of interactive controls, and every one of those pairs is a separate calculation — muted text against a raised surface is a different pair from muted text against the background, and passing one does not pass the other. The failure mode to watch for is the dark palette that is merely the light one inverted: pure white on pure black vibrates, and a muted grey tuned for paper reads as unreadable on navy. Design each theme against its own surfaces, then verify the pairs.

// theme/tokens.js - two palettes, one vocabulary. components import
// roles, never raw hex, and no component knows what a hex code is
export const palette = {
  dark: {
    bg: '#0b1220',
    surface: '#111a2c',
    surfaceRaised: '#18233a',
    text: '#e6edf7',
    textMuted: '#9aa8bf',
    accent: '#4dd2ff',
    accentInk: '#03203f',
    border: '#223049',
  },
  light: {
    bg: '#f5f7fb',
    surface: '#ffffff',
    surfaceRaised: '#eef2f8',
    text: '#0f172a',
    textMuted: '#475569',
    accent: '#0b5fbf',
    accentInk: '#ffffff',
    border: '#d7deea',
  },

Naming: the role, not the colour

A token called blue500 encodes where a colour sits in a ramp; a token called accent encodes what the colour is for, and only the second survives a re-theme. Role names also make the contrast audit greppable: every use of textMuted is a use of one audited pair, so the list of places to recheck when the value changes is a search result instead of a survey. The third layer, which arrives when a codebase grows, is the component token — a named decision such as cardBorder that resolves to a role plus a modification, defined once so twenty cards cannot drift apart by a point of opacity. Keep the layers pointing downward only: primitives are chosen by the theme, roles are chosen by the app, components consume roles. A component that reaches past its role to a primitive has quietly hardcoded a colour again.

import { createContext, useContext, useMemo } from 'react';
import { useColorScheme, StyleSheet, View, Text } from 'react-native';
import { palette } from './tokens';

const ThemeCtx = createContext(palette.dark);

export function ThemeProvider({ children }) {
  const scheme = useColorScheme();

  // null means no preference: fall back to dark once, rather than
  // choosing a side again on every render
  const colors = useMemo(
    () => (scheme === 'light' ? palette.light : palette.dark),
    [scheme]
  );

  return <ThemeCtx.Provider value={colors}>{children}</ThemeCtx.Provider>;
}

Most React Native performance bugs and most stale-screen bugs are state bugs wearing a different costume: two sources of truth, a closure that captured last render's value, a context that re-renders a whole screen to change one label. This chapter gives the decision procedure — where state lives, what is derived instead of stored, and which of your data is not client state at all.

The render cycle and useState

5.1 State Management

State is a value a component remembers between renders, and the only thing that makes it state is that the component can change it. Calling the setter schedules a new render of the component that owns the state — that component, not its children first and not its parent — and the render itself is a pure description of what the interface should look like at this moment. React Native does not surgically patch the parts that changed while your function runs; it re-runs the function, diffs the returned tree against the previous one, and hands only the difference to the native views. Every render must therefore be safe to run twice: no writes to outer variables, no network calls, no logging that assumes it happens once, nothing observable except what you return.

Renders batch. Several setter calls inside one event handler produce a single re-render, not three, and the same holds for updates queued in the same tick from an effect. Batching is why reading state immediately after calling its setter still shows the old value — the update has been queued, not applied — and it is the reason the functional form of the setter exists at all. It is also why anything measured during render produces suspicious numbers: the render you are timing may be the only one that runs, or it may be one of five, and neither result is a measurement of how long the user waited. Measure effects and committed work, not the render function.

Two conventions keep state honest. One owner: state is written by exactly one component, and everyone else receives it as a prop, because two components writing the same value means the values will disagree eventually and nothing will say so. And stable identity in lists: each row in a FlatList needs a key derived from a property of the item that never changes, because an index key tells React that a reordered list is the same items in new clothes — so scroll position, focus, and half-finished animations all attach to the wrong rows the moment the data changes.

import { useState } from 'react';
import { View, TextInput, Text, StyleSheet } from 'react-native';

export function SearchBox({ items, onPick }) {
  const [query, setQuery] = useState('');

Stale closures and functional updates

A function created during render closes over the values of that render, and if the function outlives it — in a timer, a subscription, a native event listener, an effect that never re-runs — it keeps reading those values forever. The canonical bug is a one-second interval whose callback does setCount(count + 1): the callback captured a count of zero on the first render, the setter never changes what the closure sees, and the counter increments once instead of forever. The functional form, setCount((c) => c + 1), defers reading the value to the moment the update is applied, so the latest state arrives regardless of which render scheduled the update. The second half of the same fix is ownership of teardown: an effect that starts a timer, a listener, or a native module subscription must return the function that stops it, or the work continues after unmount — firing setters on a component that no longer exists and holding the whole tree in memory.

import { useEffect, useState } from 'react';

export function useTicker(startAt) {
  const [count, setCount] = useState(startAt);

  useEffect(() => {
    const id = setInterval(() => {
      // functional update: reads the latest count at fire time, so
      // the closure captured at effect setup can never go stale
      setCount((c) => c + 1);
    }, 1000);

    // the effect owns the interval and tears it down; without this
    // a component that unmounts leaks a timer that keeps firing
    return () => clearInterval(id);
  }, []); // empty deps: set up once, tear down on unmount

  return count;
}

When a value seems to be stuck at its first render, reach for the functional setter before reaching for a ref. Refs are the right tool for values that genuinely are not part of the visual state — an animation frame handle, a native module instance — and the wrong tool for anything the interface displays, because a ref that holds displayed data has quietly left the render cycle and taken correctness with it.

Local, lifted or derived state

5.2 Derived State

Every state value answers three questions in order, and skipping the first two is how apps end up with a global store holding a modal's open flag. First, is it state at all — if it can be computed from other state or from props during render, it is derived, and derived values are computed, never stored. Second, does anything outside this component need it — if not, keep it local, because state that lives where it is used needs no wiring, no action, and no cleanup when the feature is deleted. Third, do two siblings both need it — if so, lift it to their lowest common ancestor and pass it down. That ancestor is not allowed to be the app root out of convenience: a value lifted higher than the lowest common ancestor re-renders everything below it for a change only two components felt.

Derived beats stored because stored derived values drift. The shape of the bug is always the same: a component keeps the full list, the current filter text, and a filtered copy, and one code path updates the first two without the third. The screen now disagrees with itself, and since both halves render, the disagreement is visible and rare — which is worse than a consistently wrong screen, because it cannot be reproduced on demand. Computing during render eliminates the class of bug: there is one input and one place where the output is produced, so no path can update one without the other. When the computation is genuinely expensive — sorting thousands of rows, parsing — wrap it in useMemo with the real dependencies, and treat the memo as a cache of a pure function rather than as a correctness device.

Prop drilling deserves its reputation only at depth. Three levels of a prop is not a problem, it is a component tree being explicit about its data flow, and it shows up in the type signature for free. The moment a prop is passed through components that do not use it, the tree is telling you the value belongs somewhere else — often to context for genuinely ambient data, often to a route parameter for data the navigation already owns, and often to the feature component itself, because the drill is evidence that state was colocated one level too low. Reach for a state library only when you can name the problem it solves that these three mechanisms do not; in most apps that moment arrives with cross-feature coordination, not with local UI state.

Derive, do not sync

The unmistakable smell of stored-derived state is an effect whose only job is to keep one variable matching another. If you find yourself writing an effect that sets filtered whenever query changes, delete the second variable and compute it. The effect version is not merely more code: it introduces a render where the two values disagree — the user types, the query updates, the screen still shows the old results, and the effect runs after paint to correct it — so the list visibly lags behind the keystroke on slower devices. The derived version has no such frame, because the render that sees the new query is the render that computes the new results. Effects are for synchronizing with things outside React: the network, timers, native modules, storage. When both sides of an effect are React state, one of them should not exist.

import { useMemo, useState } from 'react';
import { View, TextInput, FlatList } from 'react-native';

export function Catalog({ products }) {
  const [query, setQuery] = useState('');
  const [sort, setSort] = useState('name');

Context and the cost of sharing

5.3 Prop Drilling

Context exists to end prop drilling: one provider sits above the tree, consumers call useContext, and every component in between is untouched. The mechanics are worth stating precisely because the cost is usually discovered late. Passing a new value to the provider causes every component that called useContext for that context to re-render, regardless of depth and regardless of whether the consumer's output would change — the intermediate components that merely forward the prop are spared, but the consumers are not. Context is therefore a broadcast channel, and a broadcast re-renders everyone tuned in.

This makes the shape of the value decisive. A provider that passes a fresh object literal on every render — value={{ user, theme, online }} — creates a new identity each time, so every consumer re-renders on every render of the provider, which on a context mounted at the top of the app means every consumer re-renders whenever anything at the top changes. The fix is identity stability: build the value once per change with useMemo, or better, split the context so the volatile part and the stable part are separate broadcasts. A consumer that needs the user id should not re-render because the theme changed, and that is only achievable when those are two contexts with two values.

Context is also not a store. It has no subscriptions, no selectors, and no way for a consumer to declare that it only cares about one field — the unit of re-rendering is the whole value. That is exactly right for low-frequency, high-coverage data: the session, the color scheme, a feature flag, the current locale. It is wrong for a list of a thousand rows that changes on a keystroke, because every screen in the app subscribes to something that now churns. When you find yourself adding selectors or a version counter to a context, you have built a worse version of a store, and the honest move is to use the store — or the query cache from 5.5, if the data is actually server data.

Keeping the value stable

Three rules make context cheap in practice. Never pass an inline literal as the provider value — construct it with useMemo keyed on the state it actually contains, so identity changes only when content changes. Keep dispatch functions out of the value entirely: useReducer's dispatch is stable across renders by contract, so putting it in its own context gives you a channel whose value never changes and which therefore never re-renders a consumer — a trick that is impossible if dispatch rides along inside a state object. And place the provider as low as the sharing actually goes: a session provider above the entire app re-renders the entire app on sign-in, which may be correct, but a screen-scoped provider re-renders one screen. Placement is a performance decision, and it deserves the same thought as the value's shape.

import { createContext, useContext, useMemo, useState } from 'react';

const SessionCtx = createContext(null);

export function SessionProvider({ children }) {
  const [user, setUser] = useState(null);

  // the value object is rebuilt only when user changes. passed inline,
  // it would be a new reference on every render of this provider, and
  // every consumer would re-render on every parent render for free
  const value = useMemo(() => ({ user, signIn: setUser }), [user]);

  return <SessionCtx.Provider value={value}>{children}</SessionCtx.Provider>;
}

A context whose value changes on every keystroke has turned your broadcast channel into a render storm: every consumer re-renders for a change one of them made. Before adding a store, split the context or move the churning value down to the feature that owns it — most context performance problems are a scoping problem that a provider move fixes in one commit.

useReducer for feature state

5.4 Reducer Pattern

A second useState is the right answer until it is not, and the transition is recognizable: state has grown a compound shape, it has more than two or three transitions, and updates have started arriving from places far enough apart that reading them all in one screen is no longer possible. useReducer moves the transition logic out of the event handlers and into a single pure function — (state, action) => nextState — which can be called with any sequence of actions and asserted against, without rendering anything. That is the entire appeal: the rules of a feature become data you can test, log, and read, instead of a scatter of setters distributed across components.

The compound shape is the more common trigger. A feature with loading, error, and data as three separate booleans has an impossible state — both loading and error true — that some ordering of updates will eventually produce, because nothing enforces their relationship. A single status field with three legal values makes the illegal combination unrepresentable, and a reducer with a case per transition is the enforcement. This is the state-machine discipline applied at component scale, and it pays the same dividend: when a bug report says the screen is stuck, the question "which states can it be in, and what moved it there" has a finite answer found in one function.

The dispatch side matters as much. Dispatch is stable for the lifetime of the component, so it can be passed to contexts, memoized children, and native event handlers without becoming stale, and it can be captured in an effect that runs once without re-subscribing. Keep the reducer next to the feature — a shared generic reducer in a utils folder turns into a switch statement that every team hesitates to touch — and keep the action objects plain: a type and the minimum payload needed to compute the next state. If an action carries a whole object because the handler might need some of it, the reducer is computing with inputs it does not own, and the test that feeds it fixtures will tell you so first.

Actions as documentation

Read the switch statement and you have read the feature's contract: every state it can be in, every event it handles, and what each event does — in that order, with no prose to keep in sync. A reducer with cases named for verbs the user or the network can actually cause — start, succeed, fail, reset — documents better than a wiki page, because it cannot drift from the implementation. Exhaustiveness is the companion discipline: a default case that returns the previous state hides a typo in an action type behind a no-op, while a switch with no default — or, under TypeScript, no widening of the return — turns an unhandled action into a compile error. Add the case or fix the name; never absorb it silently.

// a whole feature's transitions in one place: these three fields are
// in exactly one shape at any time, and this function is where the
// guarantee lives. it is pure, so the test renders nothing
export function requestReducer(state, action) {
  switch (action.type) {
    case 'start':
      return { status: 'loading', data: null, error: null };
    case 'succeed':
      return { status: 'ready', data: action.payload, error: null };
    case 'fail':
      return { status: 'error', data: null, error: action.message };
    case 'reset':
      return { status: 'idle', data: null, error: null };
    default:
      // an unknown action is a typo: returning state hides it, so
      // in development this should throw rather than pass quietly
      return state;
  }
}

export const initialRequest = { status: 'idle', data: null, error: null };
import { useEffect, useReducer } from 'react';
import { requestReducer, initialRequest } from './requestReducer';

export function useFetch(url) {
  const [state, dispatch] = useReducer(requestReducer, initialRequest);

  useEffect(() => {
    let cancelled = false;
    dispatch({ type: 'start' });

    fetch(url)
      .then((r) => {
        if (!r.ok) throw new Error('HTTP ' + r.status);
        return r.json();
      })
      .then((payload) => {
        if (!cancelled) dispatch({ type: 'succeed', payload });
      })
      .catch((err) => {
        if (!cancelled) dispatch({ type: 'fail', message: String(err) });
      });

    // url is a dependency: when it changes the first response is
    // discarded on cleanup, so a slow answer cannot overwrite the
    // data the user navigated to while it was in flight
    return () => {
      cancelled = true;
    };
  }, [url]);

  return state;
}

Log every dispatched action with its previous state in development. One line per transition — start, then succeed — reconstructs the exact sequence that produced a bad screen, which is precisely the evidence a bug report never contains and the reason reducers pay for themselves before the feature is even finished.

Server state belongs in a query cache

5.5 Query Cache

Client state and server state behave nothing alike, and treating them the same is the most expensive category error in React data code. Client state — what is selected, what text is in the input, whether a panel is open — is owned by the app and changes because the user did something. Server state is remote, shared with every other client, and already changing without you: it goes stale on its own, it is fetched more than once by different screens, and it must be reconciled after every write. A useEffect that fetches into useState implements none of that: two components mounting the same data fire two requests, unmounting mid-flight loses the answer, and going back to a screen refetches from zero while showing an empty skeleton.

A query library — TanStack Query is the standard choice in React Native — replaces the hand-written effect with a cache keyed by a value you declare. The key is the identity of the data: two components asking for ['tasks', userId] share one request and one cached result, a third mounting while it is in flight joins the in-flight promise instead of starting a second one, and stale data paints immediately while a revalidation runs behind it. The hook's return value distinguishes the states the hand-written version conflates — no data yet versus data being refreshed — so a background refetch no longer flashes a loading skeleton over content the user is reading. Writing is the other half: a mutation hook that invalidates its keys after success makes "the list updates when I add an item" a two-line declaration instead of a chain of manual refetch calls threaded through navigation callbacks.

Placement follows from ownership. Data the server owns lives in the query cache and is read through hooks; data the interface owns lives in useState or a reducer locally; values the navigator already carries — the route id, the tab — are read from the route rather than copied into state, because a copy will not follow the user when they navigate. The pattern to refuse outright is mirroring cached data into component state "so it is easier to edit": the mirror starts equal and diverges on the first background update, and the screen now shows two answers to one question. Edit through a mutation, invalidate the key, and let the cache be the single copy.

Query keys and invalidation

Query keys are worth designing deliberately, because they are the cache's addressing scheme and the unit of every invalidation. Structure them hierarchically — ['projects', projectId, 'tasks'] — so that invalidating the prefix ['projects'] retires every project-derived query in one call after a project-wide change, while a narrow mutation invalidates only its leaf. A flat key like ['tasks'] for everything gives you all-or-nothing invalidation, which in a feature with lists, detail views, and counts means every write refetches everything and the cache stops paying for itself. Two knobs decide how it feels: staleTime, how long a result is trusted before a background revalidation is worth firing, and garbage collection, how long unobserved data stays cached — long enough that back-navigation is instant, short enough that a long session does not accumulate every screen's payload in memory.

import { useQuery } from '@tanstack/react-query';

// the key is the cache address: two components using this exact array
// share one request and one result, and a third mounting mid-flight
// joins the promise instead of starting a second network call
export function useProjects() {
  return useQuery({
    queryKey: ['projects', 'active'],
    queryFn: async () => {
      const res = await fetch(API + '/projects');
      if (!res.ok) throw new Error('HTTP ' + res.status);
      return res.json();
    },
    staleTime: 60000, // trusted for a minute: back-navigation paints
                      // instantly and focus does not refetch, but the
                      // data still revalidates once it goes stale
  });
}
import { useMutation, useQueryClient } from '@tanstack/react-query';

export function useCompleteTask() {
  const qc = useQueryClient();

  return useMutation({
    mutationFn: (id) =>
      fetch(API + '/tasks/' + id, { method: 'POST' }).then((r) => r.json()),

    // optimistic: paint the completion now, so the check mark is
    // instant, then reconcile with whatever the server actually did
    onMutate: async (id) => {
      await qc.cancelQueries({ queryKey: ['tasks'] });
      const before = qc.getQueryData(['tasks']);
      qc.setQueryData(['tasks'], (old) =>
        old.map((t) => (t.id === id ? { ...t, done: true } : t))
      );
      return { before };
    },

    // roll the snapshot back if the write failed, then refetch in
    // either case so the cache converges on the server's truth
    onError: (_err, _id, ctx) => qc.setQueryData(['tasks'], ctx.before),
    onSettled: () => qc.invalidateQueries({ queryKey: ['tasks'] }),
  });
}

Server state copied into component state is a fork, and a fork of remote data is always wrong within one background update. If a component needs to edit server data, mutate and invalidate; if it needs to transform server data for display, derive it during render. The cached query result should be the only copy that answers "what is on the server".

The navigator and the stack

6.1 Navigation Basics

React Navigation is a JavaScript library that coordinates native screen containers: the stack itself is real — pushed screens are native view controllers and fragments, transitions and swipe-back gestures run where the platform expects them — while the state machine deciding what is on top lives in JavaScript, where you can read it and test it. At the root of the app sits one NavigationContainer, and it is not optional: it owns the navigation state, serializes it for state persistence, forwards deep links into it, and provides the context that every useNavigation hook reads. Two containers in one tree means two states pretending to be one, and the classic symptom is a deep link that resolves on the first screen and goes nowhere.

A navigator declares its screens by name, and a screen is registered by passing the component to render — never a rendered element. The distinction is structural rather than stylistic. A component reference lets the stack own creation: the screen is not mounted when the navigator renders, only when its route is pushed, and at that moment it is mounted inside the navigator's container with navigation context, route params and the header already in place. An element built during the navigator's render does the opposite — it exists before any route does, outside the navigator's control, and navigate to its name has nothing left to push. The stack would be describing screens that were never in it.

What the native stack buys over a purely JavaScript stack is worth naming, because it explains the default. Screen content renders in a native container that can move independently of the JavaScript thread, so a list keeps scrolling during a heavy re-render instead of freezing with it. The back gesture is the platform's own, with its edge-swipe physics already correct. And pushed screens stay mounted underneath, so returning restores scroll position and half-typed form state for free. The cost is memory — ten screens in a stack are ten mounted trees — and the mitigation is architectural rather than configurational: use replace for one-way transitions, pop back to a known root after a flow completes, and keep every screen's lists virtualized so a screen parked in the stack does not hold a thousand rows of views.

import { NavigationContainer } from '@react-navigation/native';

Component, not element

The rule that resolves most navigator confusion is this: the stack stores components and renders them itself, on its schedule, inside its own tree. Given that, options may be a value or a function — a plain object for anything static, a function of route and navigation whenever the header must reflect data the screen has — because the function is re-evaluated each time the screen focuses. That is also how header buttons get a working navigation object without prop threading or a context of your own: the options function receives it as an argument. Static decisions belong on screenOptions at the navigator level, where one declaration configures every screen, and a per-screen options should only ever override what it actually changes — otherwise the same animation setting gets re-decided, differently, on a dozen screens.

Params: passing data between screens

6.2 Data Passing

A screen is addressed by name and parameterized by params: navigate('Detail', { id: note.id, origin: 'search' }) pushes the route, and the target reads the same object from its route. Two constraints shape what may go in them. They must be serializable — strings, numbers, booleans, plain objects and arrays — because the whole navigation state is written to disk for state persistence and mirrored across the native boundary, and a function or a native handle silently breaks both. And they must be small, because params ride on every navigation event and are stored with the state; the canonical payload for a detail screen is an id plus whatever the header needs, not the record itself.

The second constraint is the one that keeps data correct. A record passed through params is a copy frozen at push time: the list updates on a background refresh, the user returns to the detail screen, and it still shows the old values because its input never changed. Passing the id instead makes the screen a view over the source of truth — the query cache from 5.5 — which updates for everyone the moment new data lands. Params then carry exactly what navigation alone knows: which record, where the user came from, and any intent the next screen needs in order to choose its behavior. Everything else the screen should ask for by id, at render time, from the place that owns it.

Reading params defensively is part of the same discipline. The contract of route.params is optional: a deep link or a restored navigation state can arrive at any screen with fewer params than the in-app path provides, and an unguarded read of route.params.id turns that into a red screen. Guard the read, render the empty or error state for the missing case, and treat the guard as the screen's honest answer to what it needs in order to exist. Returning data backwards gets the same treatment: rather than pushing params back onto the previous screen, re-read the source of truth when that screen refocuses — it will refocus anyway, because that is what going back means — and a value pushed backwards is one more copy that can drift.

import { useNavigation } from '@react-navigation/native';
import { Pressable, Text, StyleSheet } from 'react-native';

export function NoteRow({ note }) {
  const navigation = useNavigation();

  return (
    <Pressable
      style={styles.row}
      onPress={() =>

Params are an interface, not a store

Treat a screen's params as its typed interface: the one list of inputs it accepts, stated at the call site where the screen is chosen. A screen reading eight params is a screen with eight inputs, and the natural shortcut — threading a whole object through because the caller already has one — turns that interface into an undocumented schema only the caller understands. Params also travel in one direction. They are handed to a screen when it is pushed, and a screen that needs to influence its parent does not write back through the navigator; it updates the shared state both screens read, and the parent sees the result on the refocus that brought it back. Navigation decides where you are and what you are looking at; state decides what is true. Keeping that split is what stops a navigation tree from quietly becoming a second, worse store.

import { useRoute } from '@react-navigation/native';
import { View, Text, StyleSheet } from 'react-native';
import { useNote } from './useNote';

  // can land here with nothing, and an unguarded read turns that into
  // a red screen instead of a rendered page with an error state

    return (
      <View style={styles.missing}>
        <Text style={styles.muted}>This note is no longer available.</Text>

  // returning to this screen paints instantly even though the

Never store what the app already knows in params because it was convenient at the call site. A record passed by value freezes the moment it is passed, and the next background update makes the screen quietly wrong — a bug that reproduces only after the data has changed, which is the hardest kind to see in development.

Tabs, drawers and nested navigators

6.3 Navigation Types

Every navigator holds its own stack of routes, and nesting them is how a real app is shaped: a tab navigator at the top, one stack per tab underneath, because tabs are peer destinations and each destination needs its own history. Two behaviors follow from the structure and are worth internalizing. Back inside a tab pops that tab's stack, and only when its stack is empty does attention return to the tab bar. And switching tabs does not unmount anything: each tab keeps its stack, its scroll offsets, and its half-finished form exactly where the user left them, which is the entire reason tabs exist — they are parallel places the user can return to, not screens that replace one another.

Naming across the boundary is where the nesting shows itself. A bare navigate('Detail') resolves against the navigator that owns the current screen — the current tab's stack — which is what you want for a link inside a tab. Reaching a screen in another tab requires the qualified form: the outer name picks the tab, screen picks the screen within that tab's stack, params lands on it. Both forms are matched by string with no compile-time check, and the wrong one fails by doing nothing, so route names belong in a shared constants module rather than as inline literals scattered through features. Drawers nest by identical rules — the container differs, the state machine does not.

Configuration follows the destination count. Three to five tabs with icon and label, a badge where a count exists, and no more: a tab bar with eight entries is not navigation, it is a menu that no longer fits. Tabs mount lazily, so a tab the user never opened has never mounted its stack — which is both the performance win and the reason startup work that must happen regardless belongs in an effect at the app root, not inside a tab's screen, where it may never run. Drawers suit secondary destinations and wide layouts, but they add an always-present gesture region on the left edge that competes with Android's back gesture; if the destinations are peers, tabs are the honest structure and the drawer is a hiding place.

Resolving a nested navigate

Resolution is a two-step lookup, and knowing which step failed tells you what to fix. An unqualified name is looked up in the current navigator: if the current tab's stack contains it, it pushes there. If it does not, the lookup walks to the parent, where a tab navigator's rules apply — the name may select an entirely different tab, mounting it first if needed. The qualified form skips the ambiguity by naming both steps explicitly. When a navigation call silently does nothing, the name is either misspelled or living in a navigator that is not an ancestor of the caller, and the shared route-name module eliminates the first case before anyone debugs the second.

// routes.js - every route name in one place. names are matched by
// string from anywhere in the app, and a typo in a navigate() call
// fails silently at runtime: no crash, no warning, nothing happens
export const ROUTES = {
  home: 'Home',
  feed: 'Feed',
  detail: 'Detail',
  settings: 'Settings',
  profile: 'Profile',
};

// cross-tab navigation: the outer name selects the tab, screen
// selects the screen inside that tab's stack, params land on it.
// this is the only way to target a screen not in your own stack

  navigation.navigate(ROUTES.settings, {
    screen: ROUTES.profile,
    params: { userId },

Tab state is part of the navigation state, which means it can be persisted — but only restore it deliberately. Reopening the app onto the exact screen the user left is often what they want, and it is occasionally a private screen behind a lock that no longer exists; decide per app, and clear the persisted state on sign-out so the next account never inherits the previous one's position.

Auth flows and the navigation gate

6.4 Auth Flows

An authenticated app is two navigators and a gate: a small stack with sign-in and sign-up, and the application stack, with a decision between them that lives above both. The decision is a state machine, not a boolean — restoring the saved session, signed out, signed in — and the third state is the one that separates a correct gate from a flickering one. While the token is being restored there is nothing to show: rendering the auth stack for a frame makes a signed-in user watch a login screen flash on every launch, and rendering the app stack for a frame hands a signed-out device a moment of private UI. The splash screen is covering that time anyway; gate on it.

The session itself has a home that is not React state. Tokens belong in platform secure storage — Keychain and Keystore, reached through expo-secure-store or a native module — because AsyncStorage is a plain unencrypted file and anything readable from the app sandbox is readable from a jailbroken device or a backup extract. On launch the gate reads storage, refreshes the token if needed, and only then flips to signed in; the read is async, which is exactly why the restoring state exists. The session provider sits at the app root, above the gate, because everything below it — the query cache, the navigators, user-scoped effects — needs to know who is signed in, and everything above it exists only to decide that.

Signing out is where gates usually go wrong, because it is a transition between trees rather than a screen inside one. Pushing the auth stack on top of the app stack leaves every private screen mounted underneath, still holding its data, reachable with the hardware back gesture or the iOS edge swipe — a logout that leaks. The gate avoids the problem by construction: when the session ends, the app tree unmounts and its navigation state goes with it. What must be done explicitly is everything cached alongside it — the query cache still holds the signed-out user's rows, the persisted navigation state still describes their screens, and in-memory feature state still holds whatever the last screen computed. One sign-out routine clears all three, in that order, and the session change is the trigger.

import { useContext } from 'react';
import { NavigationContainer } from '@react-navigation/native';
import { createNativeStackNavigator } from '@react-navigation/native-stack';
import { SessionCtx } from './session';
import { SignInScreen } from './SignInScreen';
import { HomeScreen } from './HomeScreen';

const Auth = createNativeStackNavigator();
const App = createNativeStackNavigator();

export function Root() {
  const { status } = useContext(SessionCtx); // restoring | in | out

  // while the token is being restored there is no navigator to show:
  // the auth stack for one frame signs the user out visually, and
  // the app stack for one frame signs them in falsely
  if (status === 'restoring') return null;

  return (
    <NavigationContainer>
      {status === 'in' ? (
        <App.Navigator>
          <App.Screen name="Home" component={HomeScreen} />
        </App.Navigator>
      ) : (
        <Auth.Navigator>
          <Auth.Screen name="SignIn" component={SignInScreen} />
        </Auth.Navigator>
      )}
    </NavigationContainer>
  );
}

Reset, do not push

Navigation offers three ways to arrive somewhere and only one of them is right at a gate. navigate and push add a route to the current stack, which is correct between screens and wrong between trees: the previous routes remain below, mounted, with their scroll positions and their data, and every back affordance in the app can lead back into them. replace swaps the top route, which is right for one-way steps inside a flow — an onboarding wizard should not be re-enterable backwards — but it still lives in one tree. What a sign-in or sign-out needs is CommonActions.reset, which declares a new root: a fresh index and route list, nothing below, nothing remembered. The imperative rule to carry is that arriving at a gate resets, arriving at a screen navigates, and a flow that must not be reversed replaces.

import { CommonActions } from '@react-navigation/native';
import { useQueryClient } from '@tanstack/react-query';

export function useSignOut(navigation) {
  const qc = useQueryClient();

  return async function signOut() {
    // token out of secure storage first: if any step below throws,
    // the device is signed out rather than stranded in a half state
    await clearSession();

    // reset, do not navigate: pushing SignIn on top of the app stack
    // leaves every private screen underneath it, still mounted, and
    // the back gesture returns straight to private data
    navigation.dispatch(
      CommonActions.reset({
        index: 0,
        routes: [{ name: 'SignIn' }],
      })
    );

    // the cache still holds the signed-out user's rows: an uncleared
    // query cache means the next account sees the previous one's
    // data for as long as it takes the first fetch to land
    qc.clear();
  };
}

Test sign-out as a journey, not a button. After it runs, press the hardware back gesture, background and reopen the app, and check that no cached row, restored route, or retained form field of the previous account survives — the leak almost always lives in the query cache or the persisted navigation state, not in the stack you just reset.

Deep links, back behaviour and state

6.5 Deep Links

A deep link is a URL that resolves to a screen, and the linking config is the translation table: prefixes declare which schemes and hosts belong to the app, and a config tree maps path patterns onto the same route names the navigators use — note/:id becomes the Detail route with { id: '42' } in its params. On a cold start the container parses the initial URL and builds the whole navigation state from it, so the app opens directly at the right screen with the right params; on a warm start it navigates there through the normal machinery. The same table drives both, which is why a deep link that works from a killed app but not from the background — or the reverse — points at state handling rather than at the config.

What lives outside the code is the part teams discover late. Universal links on iOS need an apple-app-site-association file served from the domain, App Links on Android need assetlinks.json, and Expo records the associations in app.json at build time; all three must agree on the same app identifiers or the OS decides the URL belongs to the browser and your handler never runs. Custom schemes are trivial to add and unreliable by nature — any app can register one, and an intent handler can be claimed — so they are right for development and wrong as the only entry point for a shared link. Test the paths users actually take: a link from a messaging app into a killed app, into a backgrounded app, and into an app sitting on a different screen.

Back deserves its own paragraph because it is a platform contract. On Android the hardware back gesture must go somewhere: the stack pops if it can, the tab bar falls back to the first tab if it must, and only the root may choose to leave the app — a choice worth confirming rather than performing silently, since a stray exit discards whatever the user was doing. On iOS there is no hardware button at all: back is the header button or the edge swipe, so every screen pushed without a header needs its own visible way out, and a modal needs an explicit close. State persistence rounds it out: the navigation state can survive a process death, which restores a user's exact position for free and can equally restore a signed-out user into a screen their account no longer reaches unless the gate clears it.

Back is a feature, not a default

Every pushed screen owes the user a way out, and the platform supplies two different notions of what that means. On Android, back is a system gesture the app does not own: React Navigation handles the common cases — pop the stack, then collapse to the first tab — and an app that swallows the gesture without offering anything in return has trapped its user. On iOS there is no hardware back at all; the header button and the edge swipe are the only exits, which makes a screen pushed with headerShown: false a screen that can strand whoever opened it unless it draws its own close control. The discipline is the same on both: intercept back only when the app is about to lose something — an unsaved draft, a multi-step flow mid-way — and when it intercepts, always present a visible alternative. A confirmation dialog is not a navigation strategy.

import { useEffect } from 'react';
import { BackHandler } from 'react-native';

// React Navigation already pops the stack on hardware back; a
// listener is only for the presses it must not handle: an unsaved
// draft, the root tab, leaving the app
export function useConfirmExit(navigation, isDirty) {
  useEffect(() => {
    const sub = BackHandler.addEventListener('hardwareBackPress', () => {
      // not handled: return false and the navigator pops as usual
      if (!isDirty) return false;

      // handled: ask instead of destroying the draft. showing the
      // dialog and returning true tells Android the press is spent
      showDiscardDialog({
        onDiscard: () => navigation.popToTop(),
      });
      return true;
    });

    // a listener added by a screen must be removed by that screen,
    // or the next screen to mount answers presses on behalf of one
    // that no longer exists
    return () => sub.remove();
  }, [navigation, isDirty]);
}

Walk the app's links the way a user does: open a shared URL into a killed app, into a backgrounded app, and into an app parked three screens deep — then press back from where each one landed. Cold-start routing, warm routing and back behaviour are three separate code paths in React Navigation, and only the first one usually gets tested.

The HTTP client and the request lifecycle

7.1 Request Lifecycle

Every request the app sends shares the same concerns: the base URL that changes per environment, the authorization header, a timeout, cancellation when the screen that asked is gone, and an error shape the screens can render without parsing raw responses. Writing fetch calls directly into components duplicates all five in every feature, and the duplication is where they drift — one screen remembers to send the token, another has no timeout, a third keeps a spinner spinning after navigation because nothing ever aborted the request. One client module is the fix, and it is a small module: a single request function that every call site wraps rather than reimplements.

Timeout deserves its own paragraph because React Native's fetch has none. On a desktop with a wired connection a hanging request is rare; on a phone it is ordinary — a connection accepted and then stalled during a handoff between cell towers leaves fetch pending indefinitely, so the screen shows its loading state forever and the retry button never appears, because from the app's point of view nothing failed. An AbortController with a timer converts that hang into an error the UI can display. The same controller links to the component's lifetime: when the screen unmounts or the user navigates away, the request is aborted rather than left running to completion for a screen nobody is looking at.

Error handling starts with the taxonomy, because the four failures look identical in a naive implementation and demand opposite responses. A thrown exception from fetch means the request never completed — offline, DNS, refused — and is usually transient. A response with ok false is a completed exchange with a bad answer: 4xx says the app asked wrongly, 5xx says the server answered wrongly, both need different UI. A timeout is a fifth case entirely — the server may still have processed the request, so retrying a GET is safe while retrying a payment is not. And a response that parses as invalid JSON is an error wearing a success costume, caught only by parsing inside a try. Normalize all five into one error object carrying a status and a retryable flag before any screen sees them.

const BASE = 'https://api.example.com';

export class HttpError extends Error {
  constructor(status, body, retryable) {
    super('HTTP ' + status);
    this.status = status;
    this.body = body;
    this.retryable = retryable; // 4xx is not; timeouts and 5xx are
  }
}

export async function request(path, options = {}) {
  const { method = 'GET', body, token, signal } = options;

  // a phone can hold a stalled connection open indefinitely; without
  // a timeout the request does not fail, it never returns, and the
  // screen sits in its loading state until the user force-quits
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), 15000);

  // the caller may also abort - unmount, navigation, a newer query -
  // and either signal stopping the transport is enough
  if (signal) signal.addEventListener('abort', () => ctrl.abort());

  try {
    const res = await fetch(BASE + path, {
      method,
      headers: {
        'Content-Type': 'application/json',
        ...(token ? { Authorization: 'Bearer ' + token } : {}),
      },
      body: body ? JSON.stringify(body) : undefined,
      signal: ctrl.signal,
    });

    if (!res.ok) {
      const parsed = await res.json().catch(() => null);
      const retryable = res.status >= 500 || res.status === 429;
      throw new HttpError(res.status, parsed, retryable);
    }

    return await res.json();
  } finally {
    clearTimeout(timer);
  }
}

One client, one place for headers

The header injection point is the part worth centralizing above all else. The access token changes — refreshed, rotated, replaced after sign-in — and if each call site reads it from storage at request time, then every feature needs the same async plumbing; if a call site caches it, the cached copy goes stale and requests fail with 401s that look like session expiry. A client that reads the current token at send time removes the question. The companion problem is refresh: on a 401 the natural implementation refreshes and retries, but five requests in flight when the token expires produce five refreshes racing to write the session, and one of them wins with an older token. The fix is single-flight — all callers await the same refresh promise, then retry once — and one retry only, because a second 401 with a freshly minted token is the server saying the session is over, which should sign the user out rather than loop them.

import { request, HttpError } from './http';
import { getAccessToken, refreshSession } from './session';

let inFlight = null;

// single-flight: five parallel 401s trigger one refresh, not five.
// the five callers await the same promise and then retry once each;
// without this, five token writes race each other and the loser
// leaves the next request carrying a token that is already rotated
function oncePerRefresh() {
  if (!inFlight) {
    inFlight = refreshSession().finally(() => {
      inFlight = null;
    });
  }
  return inFlight;
}

export async function authed(path, options = {}) {
  const token = await getAccessToken();

  try {
    return await request(path, { ...options, token });
  } catch (err) {
    if (!(err instanceof HttpError) || err.status !== 401) throw err;

    const fresh = await oncePerRefresh();

    // one retry only. a second 401 with a fresh token means the
    // session is genuinely gone, and looping here would sign the
    // user into an endless request cycle instead of out of it
    return request(path, { ...options, token: fresh });
  }
}

Never retry a non-idempotent request on an ambiguous failure. A timeout does not mean the server did nothing — the payment may have landed — so GETs and idempotent puts may back off and try again while posts wait for the user or carry an idempotency key the server recognizes.

FlatList: windowing and what makes lists jank

7.2 List Performance

FlatList is not a styled map. Its entire value is windowing: the list measures the viewport, renders the rows inside it plus a small buffer above and below, and unmounts the rest — so a feed of ten thousand rows costs the memory of twenty. Everything else about the component is in service of that trick, and every performance conversation about lists comes down to whether the window is doing its job. The baseline is the row itself: shallow, fixed in its outer dimensions, with images given their size before they load so a slow network cannot resize rows under the user's finger.

What breaks windowing falls into three families. Re-rendering: renderItem defined as an inline arrow recreates a component description every time the list renders, and if the row is not wrapped in memo, every visible row reconciles because of it — cheap for five rows, a frame dropped with forty. Unstable keys: an index key tells the list that a row inserted at the top shifted every identity below it, so inserting one item remounts the entire list, losing scroll anchors and in-flight image loads. And measurement: without getItemLayout, scrolling to an index means rendering rows until the list can guess where the index is, which on a long list is slow and visibly approximate — when row height is fixed, supplying the math costs four lines and removes the guessing.

The tuning knobs exist and are tempting: windowSize, initialNumToRender, maxToRenderPerBatch, removeClippedSubviews. They move real numbers, and they are the wrong first move, because a janky list with heavy rows stays janky after tuning and a light list rarely needs it. The order that works: fix the row's own cost first — count its views, size its images, memo it — then measure on a slow device, and only then adjust the window. A common source of jank that is neither the row nor the window is the scroll handler itself: work done per scroll event belongs behind a throttle on the native side, because a JavaScript function running on every frame of a gesture competes directly with the thread doing the scroll.

import { memo } from 'react';
import { FlatList, Image, Text, Pressable, StyleSheet } from 'react-native';

const ROW = 64; // fixed height: lets the list size its window and
                // answer scroll-to-index without measuring anything

// memo without stable props is decoration: it pays off only when
// renderItem and onOpen also keep their identity across renders
const Row = memo(function Row({ item, onOpen }) {
  return (
    <Pressable style={styles.row} onPress={() => onOpen(item.id)}>
      <Image source={{ uri: item.thumb }} style={styles.thumb} />
      <Text style={styles.title} numberOfLines={2}>{item.title}</Text>
    </Pressable>
  );
});

export function NoteList({ notes, onOpen }) {
  return (
    <FlatList
      data={notes}
      keyExtractor={(item) => item.id}

      // item and onOpen - keep identity between calls
      renderItem={({ item }) => <Row item={item} onOpen={onOpen} />}

Why a list scrolls badly

A dropped frame while scrolling is a budget problem: the JavaScript thread must finish its work in about sixteen milliseconds, and lists spend that budget on four things in a predictable order. Row reconciliation is first — which is why the memo on the row and the stable callback matter more than any list prop. Layout is second, and nested text is the expensive case: a row with text inside a view inside a view must compute all three boxes every time anything about it changes, which is why row height is fixed and depth is kept low. Image decoding is third: an image that arrives without a declared size renders at natural size, then reflows when it loads, so the row it occupies is laid out twice — declare the box first and let the picture fill it. Fourth is work done per scroll event, which is the only one of the four the user's gesture controls the cadence of, so it must be cheap by construction rather than by luck.

import { useCallback, useState } from 'react';
import { FlatList, Pressable, Text, StyleSheet } from 'react-native';

export function SelectableList({ notes }) {
  const [selected, setSelected] = useState(null);

  // stable identity: rows close over this once, so their memo
  // comparison keeps working instead of invalidating every render
  // the moment the selection state changes anywhere in the list
  const onOpen = useCallback((id) => {
    setSelected((current) => (current === id ? null : id));
  }, []);

  // each row's look now depends on state the list itself owns;
  // extraData is how the list learns that visible rows must be
  // re-rendered even though data - the array of notes - never
  // changed identity, which is otherwise invisible to it
  return (
    <FlatList
      data={notes}
      extraData={selected}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => (
        <Row
          item={item}
          onOpen={onOpen}
          selected={item.id === selected}
        />
      )}
    />
  );
}

});

Profile lists on the slowest device you support, not in the development client on a laptop. Windowing bugs are invisible where rows cost four milliseconds and visible where they cost sixteen, and the dev client runs unoptimized JavaScript that hides the difference you are trying to measure.

Pagination and infinite lists

7.3 Infinite Lists

An infinite list is two systems stitched together: a data layer that fetches successive pages and a view layer that asks for the next one when the user approaches the end. On the data side, cursor-based pagination is the correct default. An offset is a promise about the list staying still, and a list that gains three items between page two and page three silently drops or duplicates rows at the seam; an opaque cursor — the last item's id, signed or server-held — names a position rather than counting it, so concurrent inserts cannot shift the boundary. Pages are cached as an array of page objects rather than flattened, because the array is the honest record of what was asked for and it lets refetching re-run every page request through the same cache machinery.

The view side is where the failures concentrate. onEndReached is an event, not a button: it fires when the viewport approaches the threshold, it can fire several times during one gesture, and it fires once on mount whenever the content is shorter than the viewport — a cold empty list therefore triggers it immediately, twice, before the user has done anything. The guard belongs in exactly one place, written once: only fetch if there is a next page and no fetch is already running. Get that wrong and you get duplicate pages, which the dedupe step hides for a while and then stops hiding when the server's ordering puts the same item across a boundary twice. Dedupe by id when flattening, unconditionally — it is four lines and it converts an entire class of seam bugs into nothing.

Continuity is the last piece, and it is judged by whether the user notices the fetch at all. The list must not jump: appending to the end of a non-inverted list is naturally stable, while an inverted list — the chat pattern, newest at the bottom — must start at the end and append above the anchor. A failed next page is not a full-screen error: the list still holds everything it had, so the failure renders in the footer, where the retry affordance sits next to the thing it retries. And a footer spinner must occupy space before it has content — a footer that appears the instant loading starts adds height below the last row, nudging the scroll position the user was reading.
