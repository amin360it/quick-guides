12 · Container queries and responsive components

For fifteen years "responsive" meant one question: how wide is the viewport? That worked while a page had one layout, but a component that ships into a full-width hero, a 260 px sidebar and a 320 px mobile column cannot be described by a viewport width at all. At a 1200 px viewport the hero card is 600 px wide and the sidebar card is 260 px, so any single @media rule must be wrong for one of them. Container queries invert the question: the component declares itself a query container, and its descendants ask how much room they were given. Media queries do not go away — they still answer the genuinely global questions (colour scheme, print, reduced motion, the page shell) — but component layout becomes the component's own business, so a card can be dropped anywhere and look right without touching the CSS.

12.1 Container types, names and containment

A container query is only legal against an ancestor that has been marked as a query container with container-type. The value you choose decides which axes the browser is allowed to measure, and marking an element also switches on CSS containment for it — which is not a side effect but the entire mechanism.

What container-type actually turns on

The property takes three values. normal is the default and means the element is not a query container at all. inline-size establishes a container that can be queried on its inline axis only — width in a horizontal writing mode — and it is the right choice for the overwhelming majority of components. size establishes a container that can be queried on both axes, so @container (height > 20rem) becomes legal, but it requires the element to have a size in both axes that does not depend on its contents. Alongside the query container itself, the descendants that respond are matched by ordinary selectors inside the @container block, and the condition is re-evaluated whenever the container's size changes.

Marking an element as an inline-size container makes a second thing true at the same time: the element becomes a layout, style and inline-size containment box. Its children can no longer affect its inline size.

Naming a container so a query can find it

An unnamed @container (width > 30rem) is answered by the nearest ancestor container, whatever it happens to be. That is convenient until a component sits inside another component that is also a container: the inner query then measures the wrong box. container-name fixes this by giving the container an identifier that the query can require. The name is a <custom-ident>, and the shorthand container: rail / inline-size sets the name and the type in one declaration.

/* css — an inline-size container, named and unnamed */
.card-host {
  container-type: inline-size;   /* anonymous: nearest ancestor answers */
}

.sidebar {
  container-name: rail;          /* named: only this container answers */
  container-type: inline-size;
  /* identical shorthand: container: rail / inline-size; */
}

/* answered by whatever container is closest */
@container (width >= 30rem) {
  .card { grid-template-columns: 8rem 1fr; }
}

/* answered only by a container named "rail" */
@container rail (min-width: 24rem) {
  .nav-item { grid-template-columns: 1.5rem 1fr; }
}

Why containment is the price of admission

The browser cannot measure the container if the container's own size depends on the size of the things it is measuring — that is a circular definition. Containment breaks the cycle by promising that a container's inline size never depends on its contents. For a normal block-level element this is already true, so nothing visibly changes. For an element that used to shrink-wrap — inline-block, a float, an absolutely positioned box, a grid or flex item with auto sizing — applying container-type: inline-size makes it size as though it were empty. The content still renders, but the box no longer grows to fit it.

container-type: size goes further and contains the block axis too, which is why it demands a definite height: a fixed block-size, a grid row, or an explicit contain-intrinsic-size to fall back on. If none is available the element collapses and every query against it returns the same answer.

/* css — size containment needs a definite, content-independent size */
.terminal {
  container-type: size;                 /* enables block-size queries too */
  block-size: 20rem;                    /* must not depend on content */
  contain-intrinsic-size: auto 20rem;   /* size used while layout is skipped */
}

@container (block-size > 24rem) {
  .terminal__line { line-height: 1.8; }
}

Which container answers the query

A query is always answered by an ancestor container — never by the element being styled, and never by its descendants. When several ancestors qualify, the nearest one with a matching name or type wins. There is no syntax for testing two different containers in one condition; the equivalent is to nest the queries, which reads top-down the way the DOM does.

Two traps are worth memorising. First, container-type: inline-size on an element that previously shrink-wrapped will change the page layout even before you write a single query, because the element stops sizing to its content. Second, a @container block changes nothing unless an ancestor is actually a container — a stray query silently matches nothing rather than raising an error.

12.2 Container query units and intrinsic sizing

Container queries decide whether a rule applies. Container query units decide how much: they are length units that resolve against the query container instead of the viewport, which lets a component scale fluidly from its own available space with no breakpoints at all.

The six units

The units mirror the viewport family exactly, one letter changed. Where vw means 1% of the viewport width, cqw means 1% of the query container's width; where vh means 1% of the viewport height, cqh means 1% of the container's height. Two of them are writing-mode aware: cqi is the inline axis and cqb the block axis, so a vertical-writing-mode component keeps working without renaming anything. cqmin and cqmax take the smaller or larger of the two axes.

UnitResolves againstUse it for
cqw1% of the container's widthScale that must track the physical width
cqh1% of the container's heightVertical rhythm in a fixed-height panel
cqi1% of the container's inline sizeText, padding, spacing — the writing-mode aware default
cqb1% of the container's block sizeSpacing along the block axis
cqminThe smaller of the two axesElements that must never overflow either way
cqmaxThe larger of the two axesKeeps a decorative element visible in a thin container

Sizing a component from its own container

Because the units are relative to the container, a single declaration covers every context the component is dropped into. Wrapping them in clamp() keeps the result legible: the middle value does the fluid work, and the two bounds stop the type from becoming microscopic in a small sidebar or absurd in a hero. The same pattern applies to padding and corner radius, which is what makes a component look proportioned rather than merely resized.

/* css — fluid type and spacing with no breakpoints */
.card { container-type: inline-size; }

.card__title {
  /* 3.5% of the container's inline size, held between two limits */
  font-size: clamp(1.25rem, 3.5cqi, 2rem);
}

.card__body   { padding: 4cqi; }
.card__badge  { border-radius: max(0.25rem, 1.5cqi); }

/* 100cqi is the container's own inline size, so the map stays square
   and shrinks with the component rather than with the viewport */
.card__map {
  inline-size: 100cqi;
  aspect-ratio: 1;
}

When there is no container

If no ancestor is a query container, the units do not become invalid — they resolve against the small viewport, exactly as svw and svh would. That makes them a safe progressive enhancement: a component degrades to viewport-relative sizing rather than collapsing, and gains true container-relative sizing the moment an ancestor declares container-type. The failure is therefore a quality regression, not a layout break, which is the right way round.

Prefer cqi over cqw in general-purpose components. In a horizontal writing mode they are identical, and in a vertical one cqi still means "along the text flow", which is almost always what a spacing or type rule actually intended.

12.3 Media queries versus container queries

The two at-rules answer different questions, and knowing which question a rule is really asking is most of the discipline. @media asks about the device and its environment; @container asks about the space one element was given. Using the wrong one produces CSS that is correct in the page you tested and wrong everywhere else.

Two different questions

A media query can see things a container query cannot: the colour scheme and increased-contrast preference, the pointer type, the print medium, the dynamic range of the display, and whether the user has asked for reduced motion. A container query can see something a media query never can, because it is answered after the parent has already been laid out: how much room this particular instance of the component actually has. The practical rule is that the page shell — columns, the app bar, the sidebar whose visibility depends on the viewport — stays on media queries, while every component that will be reused stays on container queries.

Breakpoints belong to the component

A container breakpoint is not a device class, it is the width at which the component's own layout stops working. A media-object becomes viable when there is room for a fixed thumbnail and a text column, so the query is written against that number and never against "tablet". The same component in three slots then adapts three ways with one ruleset, which is what makes a design system composable instead of a pile of context-specific overrides.

/* css — one viewport question, one component question */
@media (min-width: 60rem) {
  .page { grid-template-columns: 16rem 1fr; }   /* shell layout: global */
}

@container (width >= 22rem) {
  /* true whenever a card is wide enough, wherever it was placed */
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

Supplying a fallback

Container queries and container query units are Baseline widely available, so a fallback is rarely needed for evergreen browsers. When the audience includes an embedded or legacy engine, the honest fallback is not a duplicated media query — that reintroduces exactly the coupling you removed — it is a simpler layout that needs no query at all. @supports keeps the two apart cleanly and fails safe, because the base rule is the one every engine understands.

/* css — fails safe: stacked by default, enhanced when supported */
.card { display: block; }

@supports (container-type: inline-size) {
  .card-host { container-type: inline-size; }

  @container (width >= 22rem) {
    .card { display: grid; grid-template-columns: 8rem 1fr; }
  }
}
A container query cannot be used to style the container itself, only its descendants. If a component needs to change as a whole, put the query on its children, or change the container's styling from a rule that does not depend on the query.

12.4 Style queries, range syntax and scroll state

The same @container machinery can ask about a container's computed style rather than its size, and about the scroll state it is in. Both extend the "the component answers its own questions" model well past layout: a theme or density set once on a host can drive every descendant, and a sticky header can restyle itself the moment it actually sticks.

Custom property style queries

@container style(--density: compact) evaluates the computed value of a custom property on the queried container. Because custom properties inherit, setting one variable on a host element is enough to switch every descendant that asks about it. This is deliberately narrower than it looks: the comparison is against the computed value, so a colour written as blue will not match #0000ff unless the property was registered with @property and given a real syntax, which makes the browser normalise both sides. Treat style queries as a way to branch on a token you control, not as a general "read any property" mechanism.

/* css — one variable on the host drives every descendant */
.toolbar {
  --density: compact;
  container-type: inline-size;
}

@container style(--density: compact) {
  .row { padding-block: 0.125rem; }
}

@container style(--density: cozy) {
  .row { padding-block: 0.5rem; }
}

/* range syntax compares numerically, which the plain form cannot */
.bell { --unread: 12; }

@container style(--unread > 9) {
  .bell__dot { background: var(--danger); }
}

Plain versus range syntax

The two forms behave differently even when they look alike. style(--n: 3) compares the computed value textually against 3, so a container holding calc(6 / 2) does not match. style(--n = 3) resolves both sides, parses them as a numeric type and compares the numbers, so it does match. Range syntax also cannot compare keyword values at all — style(--theme = dark) is always false, because dark is not a number, a length, an angle or a time. Use the colon for tokens and the comparators for measurements.

Scroll-state queries

An element with container-type: scroll-state can be queried on four conditions: whether it can still be scrolled in a given direction (scrollable), which way it was most recently scrolled (scrolled), whether it is currently snapped to an ancestor scroll-snap container (snapped), and whether a sticky element is currently stuck to an edge (stuck). This removes a class of JavaScript that previously waited on a scroll listener to add a shadow or reveal a "back to top" control.

/* css — a sticky header styles itself when it is actually stuck */
.sticky-head {
  position: sticky;
  inset-block-start: 0;
  container-type: scroll-state;
}

@container scroll-state(stuck: block-start) {
  .sticky-head { box-shadow: 0 2px 10px rgb(0 0 0 / 0.25); }
}

/* a scroll container can reveal its own affordance */
.scroller {
  overflow-y: auto;
  container-type: scroll-state;
}

@container scroll-state(scrollable: top) {
  .scroller__to-top { visibility: visible; }
}
Support is uneven across the @container family. Size queries and custom-property style queries are Baseline widely available; range style queries and scroll-state queries are newer and may be missing in some engines. Guard the newer ones with @supports (container-type: scroll-state) and make sure the unguarded base state is usable, since a query that matches nothing leaves the element in its default styling.

13 · Modern selectors and cascade control

For years the only tools for managing specificity were discipline and !important, and neither scaled. Four additions changed the arithmetic instead: :is() and :where() let a rule list alternatives without inflating its weight, :has() lets a selector look forwards as well as up, native nesting removes the repetition that made stylesheets unreadable, and @layer replaces the specificity contest with a declared order. @scope then caps how far a rule may travel at all. Held together they turn the cascade from something you fight into something you configure.

13.1 :is(), :where() and forgiving selector lists

These two pseudo-classes take a comma-separated selector list and match anything in it. The difference between them is exactly one thing, and it is the only thing that matters: :is() adopts the specificity of its most specific argument, while :where() contributes zero at every position.

One rule instead of many

Before :is(), three elements sharing a declaration needed either three rules or three selectors in one list — and the list form cannot express a shared ancestor cleanly. :is(a, b, c) collapses them, and its specificity is the specificity of the most specific argument in the list. That last detail is the whole point: the alternatives behave as if you had written the single hardest one, so adding a weak selector to the list cannot accidentally lower the rule's weight.

The zero-specificity reset

:where() is the same construct with its specificity removed. Its best use is not styling at all but resetting: a base stylesheet can zero out margins and resets in a way that any later author rule can override without escalating a specificity war. This is the modern replacement for the "put your reset first and hope" convention, because the ordering no longer depends on source position.

/* css — before: repetition, and a hard-to-override weight */
.card > .title  { color: var(--text); }
.card > .body   { color: var(--text); }
.card > .footer { color: var(--text); }

/* after: one rule. Specificity is that of the hardest argument (0-2-0) */
:is(.card > .title, .card > .body, .card > .footer) {
  color: var(--text);
}

/* :where() contributes nothing, so any author rule can beat it */
:where(ul, ol, dl) { margin: 0; padding-inline-start: 1.25rem; }
:where(h1, h2, h3, h4) { line-height: 1.2; }

Forgiving parsing

A selector list is normally all-or-nothing: one unparseable selector invalidates the whole rule. :is() and :where() use a forgiving list instead, so an unknown or invalid branch is dropped and the remaining branches still match. That makes them a safe place for future-facing selectors, but it also means a typo fails silently instead of breaking the rule loudly — the opposite trade-off to a plain list, and worth knowing when a rule mysteriously matches nothing.

Reach for :where() in any stylesheet that others will import: a reset, a normalise layer, or a design-system base. It removes the need for consumers to match your specificity, which is the single most common reason a framework's base styles become impossible to override.

13.2 :not() and :has(): negation and relation

:not() has grown up: it now accepts a full selector list rather than a single simple selector, so a whole class of "this but not that" rules can be written once. :has() is the genuinely new one — it selects an element based on what it contains, which is the parent selector CSS never had.

:not() with a selector list

In Selectors Level 4, :not() takes a complex selector list. That means :not(.is-disabled, .is-current) is legal and reads exactly as intended, replacing the older habit of chaining two negations. Its specificity, like :is(), is the specificity of the most specific argument, so a negation is never free — a rule containing :not(#id) acquires an id's weight even though it is excluding rather than targeting.

:has() reads forwards

:has() matches an element if any relative selector inside it matches a descendant, a sibling or a following relative to that element. This makes genuinely new patterns possible without JavaScript: a card that changes its layout because it contains an image, a form that marks itself invalid because one field is, a list item that draws a divider because another item follows it. The argument is a relative selector list, so a leading combinator such as > or + constrains the relationship.

/* css — negation with a list */
.nav a:not(.is-current, .is-disabled) { color: var(--accent); }

/* :has() — the parent reacts to its contents */
.card:has(> img)                { grid-template-rows: 12rem 1fr; }
.card:has(> .card__media)       { padding: 0; }
form:has(input:invalid)         { border-inline-start: 3px solid var(--danger); }
label:has(+ input:required)     { font-weight: 600; }

/* :not(:has(...)) is legal, and reads as "no child matches" */
.section:not(:has(article))     { display: none; }

Where :has() gets expensive

Three rules keep it predictable. It cannot be nested inside another :has(), and it cannot be used inside a pseudo-element — neither is a limitation to work around so much as a sign the selector has stopped describing a relationship between real elements. More importantly, the browser must re-run a :has() rule when the affected subtree mutates, so a rule attached to a broad subtree and re-queried on every keystroke can become a measurable cost. Scope it to a container rather than body or html, and prefer a leading combinator (:has(> img)) over an unconstrained descendant when the relationship is direct, both because it is stricter and because it lets the engine bail out sooner.

Because :has() is evaluated as part of matching, a rule like div:has(.thing) is not a "select the parent" operator in the DOM-traversal sense — it filters the elements that the rest of the selector already matched. The difference is invisible in output and very visible in performance.

13.3 Native CSS nesting

Nesting is now part of CSS itself, not a preprocessor feature. A rule may contain other rules, and the relationship between parent and child is expressed by adjacency instead of by repeating the parent's selector — with a well-defined specificity rule so the result is still predictable.

The & nesting selector

Inside a nested rule, & refers to the resolved parent selector list. Omitting it is allowed for a descendant child — a nested rule whose selector starts with a type or class is treated as though it began with & — but writing & explicitly is clearer and is required whenever the child must attach without a descendant combinator, as in &:hover or &.is-open. Nesting only changes how the selector is written; it never creates a new scope, and the selector produced is an ordinary descendant or compound selector against the real DOM.

Specificity inside a nested rule

This is the part that surprises people. The & selector does not take the specificity of the parent as written for one branch; it takes the specificity of the most specific selector in the parent's entire list. A nested rule inside .a, #b therefore behaves like :is(.a, #b) .c, which is 1-1-0 — the id's weight is inherited by both branches. If that is not what you want, split the parent list into separate rules so each nested block has a parent of the weight it deserves.

/* css — nesting with &, combinators and nested at-rules */
.card {
  display: grid;
  gap: 1rem;

  & .card__title { font-weight: 700; margin-block: 0; }
  &:hover,
  &:focus-visible { outline: 2px solid var(--accent); }
  > .card__media { aspect-ratio: 16 / 9; }

  /* at-rules nest too: this wraps the declarations below in @media */
  @media (width >= 40rem) {
    grid-template-columns: 8rem 1fr;
  }
}

/* specificity: the nesting selector matches the HARDEST branch of .a, #b */
.a, #b {
  & .c { color: red; }   /* equivalent to :is(.a, #b) .c  →  1-1-0 */
}

Declarations after nested rules

An earlier draft of the nesting specification required declarations to come before nested rules, which forced awkward rewrites. That restriction was removed: a declaration that follows a nested rule is collected into its own implicit block and applied in document order alongside the others. The practical consequence is that color: red written after a nested rule still wins over color: blue written before it, and the cascade order inside a rule matches reading order.

Nesting is not a substitute for a build step, and it is not scoping. If you need a boundary — styles that cannot leak out and, in particular, styles that a broad global selector will still override — use @scope rather than deeper nesting. Nesting shortens the text; scoping changes what the selector is allowed to match.

13.4 Cascade layers: declaring the order

A cascade layer is a named bucket that rule sets are sorted into before anything else is considered. Specificity still decides within a layer, but between layers the order you declare wins outright — which means a low-specificity utility rule can reliably beat a high-specificity component rule without a single !important.

Order is declared, not inferred

A layer's position is set the first time its name appears, either in a bare @layer a, b, c; statement — which declares names and order without adding any rules — or in the first @layer name { ... } block encountered. Declaring the whole order up front is the important habit, because it decouples priority from where the file happens to sit in the import graph. Later names take higher priority; a rule in a later layer beats a rule in an earlier layer regardless of specificity.

Unlayered styles and !important

Rules declared outside any layer are treated as belonging to an implicit final layer for normal declarations, so unlayered CSS always wins over layered CSS. That is how existing stylesheets stay untouched: layering a framework cannot break your overrides, only the other way round. Important declarations invert the whole ordering — the earliest layer wins them, and unlayered important declarations are weakest. This inversion is deliberate: it means a layer holding defensive, must-not-be-broken rules can be placed first and still be authoritative when it matters.

/* css — declare the order once; position decides priority */
@layer reset, base, components, utilities;

@layer reset      { * { box-sizing: border-box; margin: 0; } }
@layer base       { body { font-family: system-ui, sans-serif; } }
@layer components { .button { background: var(--accent); padding: .5rem 1rem; } }
@layer utilities  { .u-hidden { display: none; } }

/* unlayered: beats EVERY layer for normal declarations */
.button { background: crimson; }

@layer components {
  .button { background: var(--accent); }   /* loses to the rule above */
}

/* !important reverses it: the earliest layer wins */
@layer reset      { .button { color: black !important; } }
@layer components { .button { color: white !important; } }  /* reset wins */

Layering someone else's CSS

@import accepts a layer() clause, which drops the whole imported sheet into a named layer. Combined with a declared order, this is the cleanest way to consume a third-party stylesheet: it keeps its internal specificity intact while guaranteeing that your own rules, layered later, win. The one ordering constraint is that @import must still come before other rule sets except @charset and @layer statements, so the order declaration is usually the very first line of the entry stylesheet.

/* css — entry point: order first, then the imports into layers */
@layer vendor, reset, base, components, utilities;

@import url("framework.css") layer(vendor);
@import url("normalise.css") layer(reset);

/* a whole file can be layered without editing it */
@layer components {
  @import url("buttons.css");   /* nested @import is also layered */
}
A layer's order is fixed by its first appearance, so a bare @layer statement that names all layers is not optional decoration — it is the mechanism. Without it, order is whichever block the bundler emitted first, which is exactly the kind of implicit priority the feature exists to remove.

13.5 @scope: bounding a selector's reach

Nesting makes selectors shorter; @scope makes them narrower. It defines a subtree in which the enclosed rules are allowed to match, with an optional lower boundary — and adds a new cascade criterion, scope proximity, so that the nearest scope wins rather than the last one written.

Scoping roots and donut scopes

The prelude is @scope (root) to (limit). The root is the upper bound and the limit is the lower bound; the root is inclusive and the limit is exclusive, so a rule inside @scope (.article-body) to (figure) matches any qualifying element under .article-body but stops at a figure. That "donut" shape is precisely what a plain descendant selector cannot express without dragging the DOM structure into the selector, and it is what makes scoped rules robust when the markup is refactored. Inside the block, :scope refers to the scope root itself, and a rule with no :scope is still implicitly scoped — it cannot escape the subtree.

Specificity inside @scope

Bare selectors and & inside a scoped block behave as if :where(:scope) were prefixed, and :where() has zero specificity — so img inside @scope (.article-body) keeps the specificity of img, not of .article-body img. That is the opposite of the nesting rule, and it is the reason scoped rules are easy to override: the root you scoped to costs nothing. Writing :scope img explicitly does add class-level weight, because :scope is a pseudo-class, so use it only when the root itself must be targeted or the extra weight is genuinely wanted.

/* css — a donut scope, and implicit zero-weight scoping */
@scope (.article-body) to (figure) {
  img { border: 2px solid var(--line); }   /* any img, except inside a figure */
}

@scope (.card) {
  :scope { container-type: inline-size; }  /* the root itself */

  .card__title { margin-block: 0; }        /* effectively :where(.card) .card__title */
}

/* a scope limit can use :scope to require a relationship to the root */
@scope (.sidebar) to (:scope > .widgets) {
  a { text-decoration-thickness: 1px; }
}

Scope proximity breaks ties

When two scoped rules match the same element with equal importance, layers and specificity, the one whose scope root is fewer hops up the DOM tree wins. Nested theme wrappers are the classic case: a light theme containing a dark card containing another light card would, under source order, colour the innermost text wrong, because the dark rule happens to come later. With @scope the innermost paragraph is one hop from the light root and two from the dark one, so it resolves correctly with no naming tricks at all.

/* css — proximity resolves nested themes that source order cannot */
@scope (.theme-light) {
  :scope { background: #f7f7f7; }
  p { color: #111; }
}

@scope (.theme-dark) {
  :scope { background: #16181d; }
  p { color: #eee; }
}

/* a .theme-light inside a .theme-dark: the nearest root (light) wins */
@scope became Baseline newly available in 2026, so guard it if you support older evergreen versions. Note also that scoping bounds matching, not inheritance: a custom property or color set on a scoped root still inherits past the scope limit, because inheritance has no selector to filter on.

14 · Color science and modern color functions

CSS colour used to mean one thing: a point in sRGB, written as hex or rgb(). That model is a poor place to do arithmetic. Two colours mixed in sRGB pass through a muddy middle, "lighten by 10%" is not a perceptual operation, and a palette generated by rotating a hue angle produces tones that look unevenly spaced however evenly their numbers are spaced. Modern CSS exposes real colour spaces — oklch(), lch(), lab(), oklab(), and the wide-gamut color() function — plus two ways to compute with them, color-mix() and relative colour syntax. Together they let a palette be derived rather than hand-tuned, and derived palettes do not drift when a brand colour changes.

14.1 Perceptual colour: lab, lch, oklab and oklch

A perceptual colour space is one in which equal numeric changes look like equal visual changes. sRGB is not one: its channels are tied to the physical response of a monitor, not to human vision, so lightness in particular is distributed very unevenly — #444 is far closer to black than #888 is to #444.

sRGB's real defect

The problem is not that sRGB is old, it is that its axes do not line up with the questions designers ask. "Make this darker" is a question about perceived lightness; "make it less vivid" is a question about perceived saturation; "rotate the hue" is a question about perceived hue. In sRGB all three operations require moving several channels at once by amounts that depend on the starting colour, which is why a stylesheet full of hex codes has no predictable darken function without a preprocessor. Converting to a perceptual space makes each of those a change to a single number.

Reading oklch()

oklch(L C H / A) is the polar form of the Oklab space. L is perceptual lightness — 0 or 0% is black, 1 or 100% is white, and the values in between are distributed the way the eye distributes them. C is chroma, an unbounded but practically small number: near 0 is grey, and sRGB tops out somewhere around 0.37 depending on hue. H is a hue angle in degrees starting from a pinkish red at 0. The alpha channel after the slash works as in every other colour function. oklab() is the same space in Cartesian axes; lch() and lab() are the older CIE-based equivalents, which are also perceptual but less uniform than the OK variants, so hue angles are not interchangeable between the two families.

/* css — a three-step ramp built by moving ONE number: lightness */
:root {
  --brand-100: oklch(0.93 0.05 258);
  --brand-500: oklch(0.62 0.19 258);
  --brand-900: oklch(0.32 0.09 258);
}

/* the same model in cartesian axes: a and b instead of chroma and hue */
.oklab-form { color: oklab(0.62 -0.05 -0.16); }

/* alpha works exactly as elsewhere */
.overlay { background: oklch(0.62 0.19 258 / 0.4); }

Choosing hues that stay distinguishable

The practical advantage of a perceptual space shows up when a palette needs several hues. In sRGB, three colours with evenly spaced hue numbers look unevenly different, and some pairs merge when the palette is dimmed or printed. Holding L and C constant and spacing H evenly produces a categorical set that stays separable, because both of the other axes are fixed. Conversely, holding H constant and varying only L produces a single-hue ramp whose steps are visibly even, which is what a small palette usually needs for surfaces, borders and text.

Keep a hue constant and vary L for surfaces and text; keep L and C constant and vary H for categorical accents. Those two recipes cover most of what a design system needs, and neither can be expressed as reliably in sRGB.

14.2 Wide gamut: color() and Display P3

Most modern screens can display colours sRGB cannot describe, and color() is how CSS addresses them. The function takes a colour space as its first argument, so the same syntax reaches Display P3 today and any future space that a browser learns.

Speaking in P3

color(display-p3 r g b) takes three channels in the 0–1 range, or percentages, expressed in the Display P3 space. P3 is a superset of sRGB: every sRGB colour has a P3 equivalent, but not the reverse, so saturated greens, oranges and magentas that sRGB clamps into dullness are available. On a P3 display the difference is visible immediately; on an sRGB display the browser maps the colour back into gamut rather than discarding the declaration. The color-mix(), relative-colour and color() functions interoperate, so a P3 colour can be mixed or derived exactly like any other.

Gamut mapping

When a colour cannot be shown on the output device, the browser performs gamut mapping: it reduces chroma while preserving lightness and hue as far as it can, rather than clipping each channel independently. The older clipping behaviour produced hue shifts — a saturated orange sliding towards red — which is why oklch() values that lie outside sRGB look the way their numbers suggest rather than becoming a different colour. Because mapping is a fallback, a palette that must be exact on every device should keep its chroma inside the smaller gamut and use wide gamut only as an enhancement.

/* css — enhancement, not dependency */
:root {
  --accent: oklch(0.62 0.19 258);   /* safe everywhere, saturated enough */
}

/* a display that can show more gets more */
@media (color-gamut: p3) {
  :root { --accent: color(display-p3 0.25 0.32 0.9); }
}

/* feature detection when the value must be exact */
@supports (color: color(display-p3 1 0 0)) {
  .badge--vivid { background: color(display-p3 0.94 0.2 0.4); }
}

Detecting support

Two mechanisms exist and they answer different questions. @media (color-gamut: p3) asks whether the output device can show P3, which is what you want when choosing a more vivid colour. @supports (color: color(display-p3 1 0 0)) asks whether the engine parses the syntax at all. Both are needed for a robust enhancement: an engine that parses P3 on an sRGB screen will map it correctly, but an engine that does not parse it will drop the declaration and fall back to the previous value, which is a fine outcome as long as the base value was already good.

Never make a colour the only carrier of meaning, and never assume a wide-gamut colour will survive a screenshot, a print, or a colour-blindness simulation. P3 widens the available palette; it does not fix contrast, and a vivid accent used as text on a light surface is still a contrast problem even when it is beautiful.

14.3 color-mix() and relative colour syntax

Two functions turn a palette into a derivation. color-mix() blends two colours in a chosen space, and relative colour syntax takes a colour and re-writes its channels arithmetically. Both are resolved by the browser at computed-value time, so a theme change is a variable change and nothing else.

Mixing in a chosen space

color-mix(in oklch, A, B) blends two colours in the named space, with an optional weight on either side. The space matters: mixing blue and yellow in sRGB or in srgb-linear passes through grey, while mixing in oklab or oklch keeps the result vivid, because the blend happens along perceptual axes instead of along monitor channels. Mixing is alpha-aware — the calculation is performed with premultiplied alpha — so mixing a colour with transparent yields that colour at reduced alpha rather than a washed-out hue, which is exactly the behaviour a "ghost" background needs. Weighting an end point, as in var(--brand) 20%, shifts the blend without changing the space.

Relative colour syntax

oklch(from <colour> L C H) reads the channels of an existing colour into keywords and lets you compute new ones with calc() and clamp(). Each space supplies its own channel names — l c h and alpha for oklch(), r g b for rgb(), and so on — and from may take any colour expression, including a custom property. This is how a single brand token generates its own hover state, border tint and on-colour text without a second source of truth: the relationship is encoded once, and it holds for whatever brand colour is installed later.

/* css — derive every state from one token */
:root {
  --brand: oklch(0.62 0.19 258);

  --brand-hover: color-mix(in oklch, var(--brand), white 20%);
  --brand-tint:  color-mix(in oklab, var(--brand), transparent 88%);
  --brand-deep:  color-mix(in oklch, var(--brand), black 35%);
}

/* relative syntax: read a channel, compute a new one */
.card {
  --surface: oklch(0.72 0.14 250);

  /* darken the text by a fixed perceptual step, clamped to valid L */
  color: oklch(from var(--surface) clamp(0, calc(l - 0.45), 1) c h);
  border-color: oklch(from var(--surface) l c h / 0.4);
  background: var(--surface);
}

Choosing a space on purpose

The space argument is a design decision, not a default to leave alone. in oklch mixes hue along the shorter arc and is the better choice for brand colour ramps, because it keeps saturation across the blend. in oklab is the better choice when the blend must not introduce hue rotation at all, such as neutral surface steps. in srgb-linear reproduces what a light model does physically, which is occasionally the right answer for a shadow or a glow. Mixing text and background in a perceptual space is also the quickest way to guarantee the midpoint stays legible, since lightness moves predictably.

A relative colour is not registered unless it is assigned to a custom property with @property giving it a real syntax. That matters for style queries — an unregistered --brand holding oklch(...) compares textually, so @container style(--brand: oklch(0.62 0.19 258)) will fail on an equivalent but differently written value. Register the token if a style query must read it.

14.4 Accessible palettes from perceptual steps

A palette is not a list of pretty colours; it is a set of pairs, and accessibility is a property of every pair, not of any colour on its own. Perceptual colour spaces make both halves of that easier: they make a ramp evenly spaced by construction, and they make the contrast arithmetic predictable enough to verify.

Contrast belongs to the pair

The contrast ratio between two colours is computed from their relative luminance, which is a function of the sRGB channels after gamma decoding. That has two consequences worth stating plainly. First, a colour has no contrast until it is placed on something, so "is this brand colour accessible" is not a well-formed question — "is this text colour accessible on this surface" is. Second, perceptual lightness in oklch() correlates strongly with luminance but is not identical to it, so a palette built by even lightness steps is evenly spaced visually and approximately even in contrast — always verify the actual pairs rather than trusting the spacing.

A ramp you can verify

The workable recipe is to fix a hue, choose a small number of lightness steps, keep chroma inside the sRGB gamut at each step, and then check the specific combinations the interface actually uses: body text on each surface, muted text on the page background, focus rings against adjacent colours, and text on the accent. A ramp built this way is easy to audit, because every step is one declaration in one place and changing the hue does not require touching any of them.

/* css — one hue, evenly spaced lightness, chroma tapered at the ends */
:root {
  --step-0: oklch(0.98 0.01 258);   /* page background */
  --step-1: oklch(0.93 0.03 258);   /* raised surface   */
  --step-2: oklch(0.86 0.06 258);   /* borders, dividers */
  --step-3: oklch(0.72 0.12 258);   /* decorative fills  */
  --step-4: oklch(0.55 0.17 258);   /* accent, focus ring */
  --ink:    oklch(0.22 0.02 258);   /* body text */
}

/* check these pairs, not the colours on their own */
body    { background: var(--step-0); color: var(--ink); }
.muted  { color: oklch(from var(--ink) calc(l + 0.25) c h); }
.focus  { outline: 2px solid var(--step-4); outline-offset: 2px; }

Letting the browser pick the on-colour

contrast-color() takes a colour and returns whichever of two candidate colours has the greater contrast against it — by default black or white, and a different pair can be supplied. It reached Baseline in 2026, and it removes the common failure where an "on-accent" token was hard-coded for one accent and silently wrong for the next. Use it wherever a background is data-driven or user-configurable, and keep an explicit fallback so an engine without it still gets a deliberate colour.

/* css — the on-colour follows the background instead of being guessed */
.badge {
  background: var(--brand-500);
  color: #fff;                                  /* fallback for old engines */
  color: contrast-color(var(--brand-500));      /* guaranteed black or white */
}

/* a custom pair, when pure black is too harsh */
.hero {
  background: var(--step-4);
  color: contrast-color(var(--step-4), #fff, oklch(0.18 0.02 258));
}
Automated contrast is a floor, not a ceiling. A pair that passes 4.5:1 can still be unreadable if the type is thin or small, and a palette that passes every ratio can still be unusable for someone with deuteranopia if hue is the only distinction. Contrast maths handles the luminance problem; it does not handle the "these two status colours look the same" problem, which needs a second cue such as an icon, a label or a pattern.

15 · Advanced layout and motion

The last group of additions is about coordination: making separate grid items share one alignment, making spacing follow the writing mode instead of the screen, making a state change animate without JavaScript orchestrating it, and letting one element position itself against another. Each replaces coordination work that used to leak into markup, script or a magic number, and each has a fallback story that keeps the page usable while support catches up.

15.1 Subgrid and shared alignment

A card that contains a grid of its own has a familiar problem: its internal rows line up with nothing outside it, so a row of cards has titles at different heights as soon as one description runs long. Subgrid lets a nested grid borrow its parent's tracks, so the boxes remain separate but the lines are shared.

Why the problem exists

Two sibling grids are independent. Each resolves its own auto rows from its own content, so nothing forces card A's title track to be the height of card B's. The pre-subgrid fixes were all indirect: fixing a row height with a magic number, using flexbox with flex: 1 and hoping the content matched, or measuring with JavaScript. All of them encode a value that becomes wrong the moment the content changes.

Borrowing the parent's tracks

The subgrid keyword is accepted by grid-template-columns and grid-template-rows. For it to be meaningful the element must be a grid item that spans the tracks it intends to reuse, and it must not have gaps of its own along the subgridded axis — the parent's gaps apply. Children of the subgrid item then place into the shared lines with grid-row and grid-column, so a title, a body and a footer in each card can occupy rows 1, 2 and 3 of the shared grid and therefore align across every card in the row.

/* css — the card grid defines the tracks once, for every card */
.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(18rem, 1fr));
  grid-template-rows: auto 1fr auto;   /* title / body / actions */
  gap: 1rem;
}

.card {
  display: grid;
  grid-row: span 3;                    /* must span the tracks it reuses */
  grid-template-rows: subgrid;         /* adopt the parent's row lines */
}

/* children place into the SHARED rows, so they align across cards */
.card > .card__title   { grid-row: 1; }
.card > .card__body    { grid-row: 2; }
.card > .card__actions { grid-row: 3; }

Subgrid in both axes

The same keyword works for columns, and both axes can be inherited at once when the parent supplies a full track set. Column subgrid is the tool for a header row whose cells must align with a body row below — a data table built from separate elements, or a definition list where the label column must match the term column above it. The constraint is symmetric: a subgrid shares lines, so it cannot have a different number of tracks than the range it spans, and it cannot introduce its own gaps on that axis.

A subgrid item must span the tracks it borrows, and the parent's gaps along the subgridded axis replace the item's own. Getting this wrong produces a layout that looks correct in one card and collapses to a single row in the next, because the span and the track count no longer agree. For an older engine, provide a plain grid-template-rows: auto 1fr auto base and override it inside @supports (grid-template-rows: subgrid).

15.2 Logical properties and writing modes

Physical properties name a side of the screen: margin-left is left, whatever the text is doing. Logical properties name a side of the flow: margin-inline-start is the start of the inline axis, which is left in English, right in Arabic, and top when the writing mode is vertical.

Axes instead of directions

The inline axis runs along the text; the block axis runs down the flow. Almost every physical property has a logical counterpart: margin-inline and margin-block for the two axes, padding-inline-start and padding-block-end for individual sides, inset-inline and inset-block for positioning, and inline-size and block-size for width and height. Shorthands follow the same pattern, with the two-value forms mapping to the two axes. Writing them consistently means a layout is automatically correct for right-to-left locales, and no separate stylesheet or swap of left and right is needed.

Setting the writing mode

writing-mode changes the flow direction and, with it, the meaning of every logical property inside. vertical-rl is the standard choice for vertical text such as a book spine or a tab that reads top to bottom, and sideways-lr rotates Latin text as a block. Setting direction: rtl on a subtree handles the bidirectional case without a vertical flow. Because the logical properties resolve against the element's own writing mode, a component styled entirely with logical properties moves from horizontal to vertical with no changes at all.

/* css — one component, correct in every writing mode */
.panel {
  padding-block: 1rem;              /* top / bottom in horizontal-tb */
  padding-inline: 1.5rem;           /* left / right */
  margin-block-start: 2rem;         /* becomes margin-top, but flow-aware */
  border-inline-start: 3px solid var(--line);

  inline-size: min(60ch, 100%);     /* width  */
  block-size: auto;                 /* height */
}

/* vertical text: the same component, now measured down the page */
.spine {
  writing-mode: vertical-rl;
  text-orientation: mixed;
  padding-block: 0.5rem 1.5rem;     /* now left and right */
  inline-size: max-content;
}

/* right-to-left without a vertical flow */
.locale-ar { direction: rtl; }

Where logical properties surprise you

Two rules prevent most mistakes. Logical values are not always interchangeable with physical ones: a two-value margin: 1rem 2rem stays physical (block then inline equivalent is a coincidence of the shorthand's shape) so prefer the axis shorthands when you mean axes. And a percentage padding is resolved against the container's inline size regardless of the axis it is used on, which predates logical properties and has not changed; on a vertical writing mode this means padding percentages behave differently from what the direction suggests.

When auditing an existing stylesheet, grep for left, right, top, bottom, width and height. Every hit in layout CSS is a candidate for a logical equivalent, and converting them is the cheapest way to make a site support a second writing direction properly.

15.3 View transitions

The View Transition API animates between two states of the document rather than between two values of one property. The browser snapshots the old state, applies your DOM or navigation change, snapshots the new state, and animates the difference on a separate layer — named elements fly to their new positions, everything else cross-fades.

Same-document transitions

document.startViewTransition(callback) takes a function that mutates the DOM. The old rendering is captured, the callback runs, the new rendering is captured, and a set of pseudo-elements — ::view-transition-old, ::view-transition-new and one pair per named group — is animated with ordinary CSS animations. Assigning view-transition-name: card to an element in both states tells the browser they are the same object, so it interpolates position and size instead of cross-fading; the name must be unique at the moment a transition starts.

Cross-document transitions

For a multi-page site the API is declarative and needs no script: @view-transition { navigation: auto; } on a page opts it in, and a same-origin navigation to another opted-in page produces a transition. Both documents must opt in, and ::view-transition-old(root) and ::view-transition-new(root) style the default cross-fade. It is supported in Chromium and in Safari 18.2 and later, with Firefox still partial, so the honest position is that it is an enhancement: the navigation works identically with or without it, and the default cross-fade is already a reasonable result.

/* css — cross-document, opt in on both pages */
@view-transition { navigation: auto; }

/* restyle the default cross-fade */
::view-transition-old(root) { animation: fade-out 200ms ease both; }
::view-transition-new(root) { animation: fade-in  200ms ease both; }

@keyframes fade-out { to { opacity: 0; } }
@keyframes fade-in  { from { opacity: 0; } }

/* a shared element that should travel, not fade */
.avatar { view-transition-name: avatar; }
// js — same-document transition around a DOM change
function openPanel(panel) {
  if (!document.startViewTransition) {   // unsupported: just do the change
    panel.classList.add('is-open');
    return;
  }
  // startViewTransition returns a promise; the snapshot is taken
  // before the callback's mutations are captured
  document.startViewTransition(() => {
    panel.classList.add('is-open');
  });
}

Respecting motion preferences

A transition is decoration, and decoration must yield to prefers-reduced-motion. Because the animation is ordinary CSS on the view-transition pseudo-elements, the fix is ordinary too: inside a reduced-motion block, shorten the durations to near zero or set animation: none on the pseudo-elements. Do not disable the transition by removing @view-transition, because that would also remove the cross-fade that helps people with low vision follow the state change.

A view-transition group animates a snapshot, not the live element, so no layout is recalculated per frame and the cost is close to a single compositor animation. The flip side is that the snapshot can look stale during a long transition: content that changes mid-animation shows the old pixels until the transition completes.

15.4 Scroll-driven animations

A scroll-driven animation replaces time with scroll position. Instead of a keyframe animation advancing on a clock, its progress is tied to a timeline derived from how far a scroller has been scrolled or how far an element has travelled through its scrollport — so a reading-progress bar, a reveal-on-scroll effect or a parallax layer is one stylesheet rule and no event listener.

Timelines and ranges

animation-timeline is declared after the animation shorthand, because the shorthand resets it. A value of scroll() creates an anonymous scroll-progress timeline from the nearest scroller, or from root or self when those are named; view() creates a view-progress timeline from the element's own visibility within its scrollport. A named timeline set with scroll-timeline-name or view-timeline-name can be attached to a different element, which is how a progress bar outside a scroll container tracks the content inside it. animation-range then narrows the portion of the timeline the animation uses, with keywords such as entry, cover and exit for view timelines.

/* css — a reading-progress bar: no script, no scroll listener */
.reader-progress {
  position: fixed;
  inset-block-start: 0;
  inline-size: 100%;
  block-size: 3px;
  background: var(--accent);
  transform-origin: 0 50%;

  animation: progress linear both;
  animation-timeline: scroll(root block);   /* must follow the shorthand */
}

@keyframes progress {
  from { scale: 0 1; }
  to   { scale: 1 1; }
}

Revealing content as it enters

A view-progress timeline is the right tool for an entrance effect, because its 0% and 100% are defined by the subject's position relative to the scrollport rather than by the scroller's extents. animation-range: entry 10% cover 40% holds the animation still until the element is 10% into view and finishes it before the element reaches the middle, so the reveal completes while the reader is still arriving. Naming the timeline with view-timeline-name lets the element being animated differ from the element whose visibility drives the timeline.

/* css — reveal on entry, driven by the item's own visibility */
.reveal {
  animation: reveal linear both;
  animation-timeline: view();
  animation-range: entry 10% cover 40%;
}

@keyframes reveal {
  from { opacity: 0; translate: 0 1.5rem; }
  to   { opacity: 1; translate: 0 0; }
}

/* a named timeline on the parent, attached by a child */
.scroller {
  overflow-y: auto;
  scroll-timeline-name: --page;
  scroll-timeline-axis: block;
}
.scroller__fill { animation: progress linear both; animation-timeline: --page; }

Accessibility and fallback

Scroll-driven animations are not Baseline yet, so the declarations must be additive. If an engine does not understand animation-timeline it drops the declaration and the animation has no duration from the shorthand, which leaves the element in its final state — a safe outcome only if the base rule already sets the resting appearance. For a progress bar that means the bar should be visible and at full width by default and animated back from zero, not the other way round. Motion is also more than decoration here: an effect tied to scroll cannot be escaped by abandoning the animation, so anything that moves should be gentle, and a prefers-reduced-motion block should replace the translate with an opacity change or none at all.

Because the animation shorthand resets animation-timeline to auto, a declaration order mistake silently turns a scroll-driven animation into a time-based one. Always write the shorthand first, and prefer separate animation-name and animation-timeline declarations in code that is machine-generated.

15.5 Anchor positioning and sizing keywords

Anchor positioning lets one element be positioned and sized relative to another that it names, entirely in CSS. It replaces the JavaScript that measured a trigger, positioned a tooltip and re-ran on every scroll and resize, and it brings overflow handling along with it. The sizing keywords are the smaller half of the same story: they express intent about a box's size rather than a fixed number.

Anchors, areas and fallbacks

An element becomes an anchor by declaring anchor-name: --menu-btn. An absolutely or fixed positioned element then names it with position-anchor and picks a placement with position-area, which uses a nine-cell grid vocabulary such as block-end or block-end span-inline-end instead of coordinates. position-try-fallbacks lists alternatives — flip-block, flip-inline, or a custom @position-try block — and the browser applies the first that avoids overflowing the containing block or the viewport. position-visibility: anchors-visible hides the positioned element when its anchor is scrolled out of view, which closes the classic bug where a tooltip stayed on screen after its trigger had gone.

/* css — a menu tethered to its button, with overflow fallbacks */
.trigger { anchor-name: --menu-btn; }

.menu {
  position: fixed;
  margin: 0;
  position-anchor: --menu-btn;
  position-area: block-end span-inline-end;
  position-try-fallbacks: flip-block, flip-inline;
  position-visibility: anchors-visible;
}

/* a named alternative the browser may fall back to */
@position-try --menu-above {
  position-area: block-start span-inline-end;
  margin-block-end: 0.35rem;
}

/* anchored container queries react to which fallback is active */
@container anchored(fallback: --menu-above) {
  .menu__caret { rotate: 180deg; }
}

Sizing keywords and intrinsic ratios

Several properties now express a box's intent rather than a measurement. aspect-ratio lets a box derive one axis from the other, so an image or video placeholder can reserve its space before loading and eliminate layout shift. min-inline-size: 0 is the standard cure for grid and flex blowout, where a long unbreakable string refuses to shrink below its content. fit-content, max-content and min-content express sizing in terms of the content itself, and min(), max() and clamp() impose bounds without media queries. object-fit then decides what happens to replaced content inside the box the ratio created.

/* css — intent-based sizing */
.media {
  aspect-ratio: 16 / 9;        /* reserve space before the image loads */
  inline-size: 100%;
  object-fit: cover;           /* crop rather than distort */
}

.grid-item {
  min-inline-size: 0;          /* stop a long word blowing out the track */
}

.prose {
  inline-size: min(70ch, 100%); /* measure, never wider than the container */
  margin-inline: auto;
}

.chip {
  inline-size: fit-content;     /* as narrow as the content needs */
  max-inline-size: 100%;
}

/* field-sizing lets a control grow with its value instead of a guess */
.grown-input { field-sizing: content; }
Anchor positioning is not Baseline across every engine yet, and it degrades in a specific way: without it, position-area is ignored and the element falls back to ordinary absolute or fixed positioning. That means the fallback must place the tooltip somewhere sensible without the anchor, usually by also setting a top or inset value — and it is worth testing with the feature disabled, because the failure is a stray box rather than a missing one.
