0.1 Which shell, and what that decision costs

Choosing a shell is not a matter of taste and it is not about features. It is about where the script will run, who will run it, and whether the shebang you write can be honoured — because the script that fails with "bad interpreter" on a machine you do not control is a bug you shipped.

The three that matter, and the one that does not

bash is on every Linux distribution, is the default login shell on most, and is what the overwhelming majority of documentation assumes. sh is a POSIX specification rather than an implementation: on Debian and Ubuntu it is dash, on Red Hat it is bash in POSIX mode, and a script written for it runs on both plus busybox in a minimal container. zsh is the default on macOS and has a richer interactive feature set, which is a reason to use it at a prompt and emphatically not a reason to write a deployment script in it. fish is the one to be aware of precisely because it is not shell syntax — its variable expansion, quoting and command substitution all differ, so a fish script fails on Debian with a syntax error rather than a subtle misbehaviour.

# Which one is /bin/sh on this machine?
ls -l /bin/sh
# lrwxrwxrwx 1 root root 4 ... /bin/sh -> dash     (Debian, Ubuntu)
# lrwxrwxrwx 1 root root 9 ... /bin/sh -> bash     (Red Hat, Fedora)

# what does the shebang on this file actually resolve to?
head -1 script.sh
# what is available under a name?
command -v bash sh zsh fish dash busybox

Which one to write in, decided by the constraint

The question is not "which is best" but "what is the most hostile environment this will run in". A script that must run on a minimal container, on a rescue image, or on a system where nobody installed anything, must be POSIX sh and must start #!/bin/sh. A script that runs on a machine you administer can be bash with #!/usr/bin/env bash. A script that runs on macOS must be bash version 3.2 — the one Apple ships, from 2007 — unless you check the version, which is the detail that catches people when they use associative arrays or mapfile.

#!/bin/sh
# POSIX only: no arrays, no [[ ]], no == inside [ ]
if [ -f "$1" ]; then
    echo "found"
fi
n=0
while [ $n -lt 3 ]; do
    echo "$n"
    n=$((n + 1))
done

# portable function
log() {
    printf '%s %s
' "$(date -Is)" "$*"
}
log "this works on dash, busybox, bash and zsh"

The version trap, which is the real difference between bash and sh

POSIX sh is a subset, and bash in POSIX mode is sh plus extensions that are simply absent otherwise. The extensions you will reach for and then miss are: arrays and ${arr[@]}, associative arrays, [[ ]] with its own word-splitting rules, the =~ regex operator, mapfile and readarray, printf -v, negative array indices, and ${var,,} case conversion. Writing bash and shebanging it sh produces a script that passes a syntax check and fails at the first array, which is the worst possible outcome.

#!/usr/bin/env bash
set -euo pipefail

# these four lines fail on dash, and only fail when reached
declare -a files=("a.txt" "b.txt")     # dash: command not found
declare -A conf                       # dash: syntax error
[[ -n "$HOME" ]]                      # dash: [[: not found
if [[ "$x" =~ ^[0-9]+$ ]]; then :; fi # dash: syntax error

# the check that prevents it
if [ -n "${BASH_VERSION:-}" ]; then
    : # bashisms are safe here
else
    echo "this script needs bash" >&2
    exit 1
fi

A minimal script, in both dialects

The POSIX form is deliberately dull, because dull is what travels. The bash form adds the three options that turn a sequence of lines into a script that reports failures rather than ploughing through them: -e exits on an unhandled failure, -u turns an undefined variable into an error instead of an empty string, and o pipefail makes a pipeline fail if any stage does. Each has a documented list of exceptions, and section 1.1 covers the one that matters.

#!/usr/bin/env bash
set -euo pipefail

name="${1:-World}"          # ${:-} supplies a default AND is safe
                            # under set -u, unlike ${name}
readonly script_dir="$(cd "$(dirname "${BASH_SOURCE[0]}")" & pwd)"

if [ ! -d "$script_dir/config" ]; then
    echo "config directory not found next to $0" >&2
    exit 1
fi

for file in "$script_dir"/config/*.json; do
    [ -e "$file" ] || continue        # the glob stays literal if
    printf 'found %s
' "$file"        # no match, so skip it
done

What the rest of this guide assumes

That the reader is comfortable with variables, conditionals, loops and pipes — the four things every language shares — and is new to what a shell does differently. The three differences that cause the most damage to code arriving from another language are worth naming now. The shell expands a line before it runs it, so what you wrote and what runs are not always the same text. Unquoted variables word-split and glob, so a single filename with a space becomes two arguments. And a pipeline is several processes, so a variable assigned inside one is lost when it ends. Every quoting rule, every set -u requirement and every "use process substitution instead" recommendation later in this guide traces back to one of those three.

# all three in one example
f="/tmp/my report.pdf"

count=$(ls | wc -l)          # pipeline: count survives, because
                             # the assignment is the last stage
ls | while read -r x; do
    n=$((n + 1))             # pipeline: n is LOST. the loop runs
done                         # in a subshell that exits here.
echo "n is $n"               # -> n is (empty or an old value)

cp $f /backup/               # unquoted: 'my' and 'report.pdf'
cp "$f" /backup/             # quoted: one argument, correct

Three disciplines: shebang with /usr/bin/env rather than an absolute path, because bash is at /bin/bash on some systems and /usr/bin/bash on others and only env finds it either way; write POSIX sh if the destination is unknown, and bash only if you control it, because a bashism in a sh script passes a syntax check and fails at run time in production; and quote every expansion from the first line of your first script, because the failure mode is invisible until a filename contains a space, which is always a filename a user chose.
