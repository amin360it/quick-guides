1 · jQuery Fundamentals & Setup

1.1 What jQuery is and why it existed1.2 Including jQuery: CDN vs npm1.3 The $ function and document ready1.4 Chainability1.5 jQuery 3.x/4 notes — and when NOT to use it

Introduces what jQuery is, why it existed, and how to load and use it. You learn the two ways to bring the library in, via CDN or npm, and write your first script inside a document-ready handler. That handler makes sure your code runs only after the DOM is safe to touch. From there the chapter lines up the core ideas the rest of the guide builds on.

jQuery is a fast, small, feature-rich JavaScript library that makes HTML document traversal and manipulation, event handling, animation, and AJAX dramatically simpler across every browser. It rose to dominance in the 2010s and still powers a large share of the web’s legacy code.

1.1 What jQuery is and why it existed

1.1.1 JavaScript Alternatives

Explains the problem jQuery solved: the browser DOM APIs of its era were inconsistent across vendors, and working with them directly was painful. jQuery layered a uniform API on top, with fast selectors, chainable manipulation, normalized events, and AJAX helpers. Most of those ideas are now native in modern browsers as methods like querySelector and addEventListener. Understanding that history shows why jQuery exists and what modern code draws from it.

Browsers used to disagree on almost every DOM API, from selecting elements to listening for clicks. jQuery gave one API that worked everywhere, hid cross-browser quirks, and added conveniences such as chainable methods and CSS-selector queries long before querySelectorAll existed. The web needed it; modern browsers have since absorbed most of it.

// The same idea, then and now
// jQuery (still works today):
var items = $("li.item");        // CSS query that worked in old browsers

// Native equivalent:
const items = document.querySelectorAll("li.item");

Both lines select the same elements; the jQuery version was the only one that worked consistently in old browsers, which is exactly why it took over.

1.2 Including jQuery: CDN vs npm

1.2.1 npm Package Details

Shows the two ways to load jQuery into a page. The first is a script tag pointing at a Content Delivery Network URL, which is typical when a page owns its markup and needs no build step. The second is the npm package, installed into a project and bundled by your tooling. Either way you should load jQuery before your own scripts that depend on it.

<!-- CDN: easiest for a plain HTML page -->
<script src="https://code.jquery.com/jquery-3.7.1.min.js"></script>
<script>
  $(function () {
    console.log("jQuery " + $.fn.jquery + " loaded");
  });
</script>

The CDN script tag loads jQuery globally, and the ready handler prints the loaded version to prove it works before you go any further.

With a build tool, install from npm instead: npm install jquery, then import $ from "jquery". The global $ from a script tag is fine for classic pages; modules are better for bundled apps.

1.3 The $ function and document ready

1.3.1 DOMContentLoaded vs Ready

Explains the dollar sign alias and the document-ready pattern, the first jQuery code most people write. Using $(document).ready or the shorthand $(function(){...}) registers a callback that runs after the DOM is parsed and safe to manipulate. Scripts in the head otherwise run before the document structure exists and may fail. The ready handler keeps that first script reliable.

$(document).ready(function () {
  // Runs only after the DOM is ready to be manipulated
  $("h1").addClass("animated");
});

// The convenient shorthand — the same thing:
$(function () {
  $("h1").addClass("animated");
});

Both forms wait for the DOM to be ready before touching it, which is why a script in the head can still safely style elements at the bottom of the page.

1.4 Chainability

1.4.1 Read vs Write Rule

Shows jQuery’s signature feature: most methods return the same jQuery set they were called on, so calls chain together. For example $('div').addClass('a').find('p').hide() does three operations in one statement. Chainability relies on the read versus write rule, where a method called with an argument writes to all matched elements and called with no argument reads the first one. Keeping that rule in mind prevents chain surprises.

$("ul#menu")
  .addClass("open")        // returns the same selection
  .children("li")
  .first()
  .css("color", "tomato"); // ...so these can follow each other

// Getter vs setter: one argument reads, extra arguments write
var color = $("h1").css("color");   // reads the first match
$("h1").css("color", "red");        // writes to every match

Every setter returns the selection so calls flow downward, and the same method reads when given one argument or writes when given more.

jQuery methods return a jQuery object, not raw elements. Use .get(0) or [0] to reach the underlying DOM node when a native API demands it.

1.5 jQuery 3.x/4 notes — and when NOT to use it

1.5.1 Version Upgrade Notes

Explains the jQuery 3.x and 4.x landscape, including what changed between the versions and how to upgrade safely. It also lists the cases where native browser code beats jQuery, such as simple selection with querySelector or event handling with addEventListener. The honest take is that using jQuery less is still knowing how to use it well. You learn to recognise when the library helps and when it is redundant.

jQuery 3.x is the stable line you will meet on almost every legacy site. jQuery 4 removed long-deprecated code, dropped old browser support, and trimmed the size; both lines share the same core API. Skip jQuery entirely when you only need a few selectors and events — document.querySelectorAll, addEventListener, and fetch cover most of it.

Never load jQuery more than once on a page and never mix two versions. The second script tag overwrites $ and breaks plugins silently.

2 · Selectors & Traversal

2.1 CSS selectors2.2 Filters and pseudo-selectors2.3 Traversal: find, children, parent, siblings, closest2.4 each, eq, first, last

Covers selecting elements with the full CSS selector language plus jQuery’s extra pseudo-selectors, then moving through the tree with traversal methods. Together selection and traversal give you every way to reach the elements your code needs to work on. This grammar sits under every later chapter, since DOM manipulation, events, and effects all start from a selected set.

Every jQuery session begins with a selection. Chapter 2 is the grammar: how to target elements precisely, how to narrow a set with filters, and how to move around the tree once you have it.

2.1 CSS selectors

2.1.1 Selector Performance

Shows that $ takes the full CSS selector language, so anything CSS can address jQuery can select. You pass classes, IDs, attribute selectors, combinators such as descendant and child, and grouped comma-separated lists. The result is a jQuery object wrapping every matching element, ready for chaining. Prefer the most specific selector that still catches the elements you intend, because simpler selectors are usually faster.

$("#app")                    // by id
$(".alert.success")          // element with both classes
$("form input[type=radio]")  // attribute selector
$('a[href^="https"]')        // links whose href starts with https
$("article > p")           // direct children only
$("h1, h2, h3")              // grouped selector

These selectors address elements the same way CSS does, and $ always returns a collection — even for an id — that behaves like an array.

2.2 Filters and pseudo-selectors

2.2.1 Pseudo-selector Details

Shows the positional and state filters jQuery adds beyond plain CSS, placed at the end of a selector to narrow the matched set. Positional filters such as :first, :last, :eq(n), :even, and :odd pick members by index, while state filters like :visible, :hidden, :checked, and :has(selector) narrow by condition. For example $('li:has(span)') keeps only list items containing a span. Remember that :hidden includes elements hidden by CSS or offscreen.

$("li:first")           // first match of the set
$("li:last")
$("li:eq(2)")            // index 2 (the third item)
$("li:even")             // zero-based even indexes
$("input:enabled")       // enabled form fields only
$("input:checked")
$("div:visible")         // excludes display:none
$("li:not(.done)")

jQuery extends plain CSS with positional and state filters such as :eq, :even, :visible, and :not, which trim a selection without extra code.

2.3 Traversal: find, children, parent, siblings, closest

2.3.1 Traversal Methods Detail

Shows the core tree-walking methods that move a selection through the document. find returns descendants matching a selector, children gets direct children, parent climbs one level, and siblings reaches the other elements on the same level. closest walks upward and returns the first ancestor that matches, including the element itself. Each method returns a new jQuery set, so further filtering stays chainable and the original selection is untouched.

$("#card")
  .find("button")          // all descendants matching
  .first()
  .addClass("primary");

$("h2").parent();          // direct parent element
$("h2").siblings("p");     // siblings filtered by selector
$("h2").closest("section");// nearest ancestor matching

$("#card").children("li"); // direct children only

find searches downward, children stays one level down, parent and closest climb up, and siblings steps sideways — every method returns a fresh, chainable set.

2.4 each, eq, first, last

2.4.1 Iteration Details

Shows how to iterate over a selection and how to pick out a single member. each runs a callback for every element in the set, with the index and the raw DOM element available, and this bound to the element. eq(n) returns a wrapped jQuery object for the element at position n, often combined with :eq in a selector. first and last simply cut the ends off the current set while left-to-right order is preserved.

$("li").each(function (index, element) {
  // 'this' is the raw DOM element while the loop runs
  $(this).attr("data-index", index);
});

var third = $("li").eq(2);     // wrapped: usable in a chain
var first = $("li").first();   // wrapped too
var raw   = $("li")[0];        // unwrapped DOM node

each runs a callback per element with this bound to the raw node, while eq, first, and last keep results wrapped so chains can continue.

3 · DOM Manipulation

3.1 Content: html, text, val3.2 Attributes, properties, data3.3 Classes3.4 Inserting and removing nodes3.5 Wrapping, cloning, dimensions

Covers the create, update, and delete operations you perform on a page: reading and writing content, attributes, classes, and the surrounding structure. You use methods such as html, text, val, attr, prop, and data for values stored on elements, and insertion and removal methods for reshaping the tree. These tools are how jQuery pages actually change what the user sees.

Selecting an element is the set-up; changing it is the point. This chapter covers the content accessors, the class tools, and the insert-and-remove methods you will use constantly.

3.1 Content: html, text, val

3.1.1 HTML vs Text Safety

Shows the three content accessors jQuery uses to read and write what is inside an element. html returns or sets the inner markup, text handles plain text with HTML never interpreted, and val reads or sets form field values. Each method reads the first matched element and, when given an argument, writes to every matched element. Using text instead of html also avoids accidental script or markup injection.

var markup = $("#card").html();    // inner HTML as a string
$("#card").html("<p>Replace everything</p>");

$("#card").text("Plain text only");  // tags become literal, visible text
var heading = $("h1").text();        // read the first match

var email = $("#email").val();       // value of a form field
$("#email").val("me@example.com");   // set it

// html() parses markup; text() never does — pick text() for user input
$(".bio").text(userInput);   // shown as text, never executed

html parses and inserts markup, text inserts plain escaped text, and val exchanges form values — one argument reads, extra arguments write, and text is the safe choice for user data.

3.2 Attributes, properties, data

3.2.1 Attr vs Prop vs Data

Distinguishes the three ways to store and read data on elements so you pick the right one. attr reads and writes HTML attributes as they appear in markup, prop handles reflected DOM properties such as checked and disabled, and data works with data- attributes and converts types automatically. The classic confusion is calling attr where a real property such as a checkbox checked state is changing.

// Attributes live in the HTML source; properties are live DOM state
$("a").attr("href", "/new/path");    // writes the href attribute
$("img").removeAttr("title");

$("input").prop("checked", true);    // sets the live property
$("input").attr("checked", true);    // only writes the attribute

// data() bridges data-* without writing attributes back
$(".card").data("userId", 42);
var id = $(".card").data("userId");  // 42

// Rule of thumb: prop() for element state, attr() for HTML source

attr manipulates what is written in the HTML, prop sets the element’s live property such as checked, and data manages values through the data-* bridge.

3.3 Classes

3.3.1 The Class Trio

Shows the class trio that powers almost every UI state change: addClass and removeClass to switch classes on and off, toggleClass to flip them based on presence or a force argument, and hasClass as a boolean query. These compose into styling any state, such as showing an active tab or marking a validation error. Classes keep styling in CSS while jQuery only manages which ones apply.

$("#menu").addClass("open");            // always adds
$("#menu").removeClass("open");         // always removes
$("#menu").toggleClass("open");         // switches, respects state
$("#menu").toggleClass("open", isOpen); // force on/off from a boolean

var open = $("#menu").hasClass("open"); // true or false

addClass, removeClass, and toggleClass move UI states in and out, while hasClass reads the current state — the entire vocabulary of visual toggling.

3.4 Inserting and removing nodes

3.4.1 Insert Methods Detail

Shows the methods that reshape the document tree by moving nodes around. append and prepend insert content inside an element as its last or first child, while after and before insert outside it as the next or previous sibling. With no argument, empty removes all child content and remove takes the element out entirely, while detach removes but keeps its event handlers.

$("#list").append("<li>Last item</li>");    // child at the end
$("#list").prepend("<li>First item</li>"); // child at the start
$("#card").after("<p>After the card</p>");  // sibling after
$("#card").before("<p>Before the card</p>");// sibling before

$("#old").remove();             // delete the node and its events
$("#box").empty();              // remove all children, keep #box

append and prepend add children at either end, after and before add siblings, and remove deletes nodes entirely while empty clears contents but keeps the element.

3.5 Wrapping, cloning, dimensions

3.5.1 Clone Detail

Shows the structural helpers beyond plain insertion. wrap and wrapAll surround matched elements in new parent markup, clone duplicates nodes so you can copy them elsewhere without touching the original, and the dimension methods width, height, and position read element geometry. Cloning matters before events complicate the copy, and clone with true also copies attached handlers. Dimensions are read after layout, so call them once the DOM is settled.

$("code").wrap('<div class="code-block"></div>'); // wrap each match

var copy = $("#row").clone(true);      // deep clone, handlers included
$("#table tbody").append(copy);

var w = $("#box").width();             // content-box width
var h = $("#box").outerHeight(true);   // includes padding, border, margin
var pos = $("#box").offset();          // top/left relative to the document
$("main").css("height", 240);          // set a dimension inline

wrap wraps each element, clone(true) copies the node and its handlers, and the width, outerHeight, and offset methods read layout numbers that css() can also write.

Never insert strings built from user input with .html() or $(userInput) — that injects HTML. Escape with .text() or build nodes with document.createElement.

4 · Events

4.1 Binding with on, off, one4.2 The event object4.3 Event delegation with on()4.4 Namespaced and custom events

Covers jQuery’s event layer, which is still one of the simplest and strongest parts of the library. You bind and unbind handlers with on and off, delegate events through a selector argument, inspect the normalized event object, and fire your own custom events. Everything stays consistent across browsers, which was the whole point of the API when it was written.

Events are the input half of any interactive page. jQuery’s event API hides the browser differences in how events fire and delivers one consistent object to your handlers.

4.1 Binding with on, off, one

4.1.1 on/off/one Details

Shows the modern event binding API built around on, off, and one. on('click', handler) binds a handler and accepts an optional selector or data argument, while off removes previously bound handlers, optionally filtered by namespace. Every shorthand you know, such as click or hover, is just on under a familiar name. one binds a handler that fires only once and then removes itself.

$("#buy").on("click", function () {
  alert("Purchased");
});

$("#buy").off("click");          // remove that handler
$("#buy").one("submit", function () {   // fires exactly once
  console.log("First submit");
});

// Multiple events, one behavior
$("input").on("focus blur", function () {
  $(this).toggleClass("focus-ring");
});

on attaches handlers, off removes them, one limits a handler to a single fire, and spaces in the event string bind several events at once.

4.2 The event object

4.2.1 Event Properties

Shows the normalized event object jQuery passes to every handler, with the same fields in every browser. You read target and currentTarget for the element involved, pageX and pageY for coordinates, and key-related fields like which for keyboard events. preventDefault cancels the default browser action and stopPropagation stops the bubbling to parent elements. Rely on the normalized fields instead of browser-specific equivalents.

$("#field").on("keydown", function (e) {
  console.log("Key", e.key, "code", e.code);
  if (e.key === "Enter") { e.preventDefault(); submit(); }
});

$("img").on("click", function (e) {
  console.log("Clicked", e.target, "at", e.pageX, e.pageY);
});

$("a").on("click", function (e) {
  e.preventDefault();     // cancel navigation, keep the event alive
});

The handler receives a normalized event object with consistent properties such as key, target, pageX, and preventDefault across every browser.

4.3 Event delegation with on()

4.3.1 Delegation Details

Explains event delegation, a top-three jQuery pattern that works through the selector argument of on. When you call on('click', '.item', handler), the handler is attached to the container once and fires only for descendants matching the selector, no matter when they were added. Elements created later work immediately because the listener lives on an ancestor that already exists. Delegation also reduces the number of handlers on big lists.

// One delegated handler on an ancestor catches clicks from
// #todo items that exist today and any that appear later
$("#todo").on("click", "li", function () {
  $(this).toggleClass("done");
});

// New inserts need no rebinding:
$("#todo").append("<li>New item, still clickable</li>");

Passing a selector to on() binds one handler that matches dynamically added descendants, so newly appended items respond without rebinding.

Without delegation you would re-bind after every insert. Delegation is one handler for the whole subtree, which is also faster for large lists.

4.4 Namespaced and custom events

4.4.1 Namespacing Details

Shows namespaced events and custom events, which turn jQuery’s event system into a tiny pub/sub pattern. Namespacing a binding such as on('click.settings', handler) lets you remove only that group with off('click.settings'). trigger fires a handler synchronously and bubbles like a native event, while triggerHandler fires handlers without bubbling. Custom events, triggered on elements and caught by on('myEvent', handler), coordinate components cleanly.

// Namespaces let you remove one group of handlers
$("#x").on("click.menu", doMenu);
$("#x").off("click.menu");        // only the .menu handlers go

// Custom events sync modules without coupling them
$("#list").on("item:added", function (e, name) {
  renderRow(name);
});
$("#list").trigger("item:added", ["Telephone"]);   // extra args ride along

// trigger also fires real events like clicks
$("#buy").trigger("click");

Namespaces give removal precision, while trigger fires both custom events and real ones, letting modules communicate through declared events instead of direct calls.

5 · Effects & Animation

5.1 Show, hide, toggle, fade, slide5.2 The animate() method5.3 Queues, stop, delay, finish5.4 CSS vs animation performance

Covers the built-in effects API and the queue system behind it. show, hide, and toggle reveal or conceal elements, fade and slide animate opacity or height, and animate tweens any numeric CSS property across time. Because effects queue by default, the queue methods stop, delay, and finish let you control the flow. Well-chosen effects make state changes legible to the user.

Animation is where jQuery shines at the moment-to-moment level: a show, a fade, a slide that tells the eye what changed. This chapter also explains the queue that runs behind every effect.

5.1 Show, hide, toggle, fade, slide

5.1.1 Effects Detail

Shows the convenience animations for common visibility changes, each taking an optional duration and a callback. show, hide, and toggle animate the element’s display back and forth, fadeIn, fadeOut, and fadeToggle animate opacity, and slideDown, slideUp, and slideToggle animate height. The callback runs once the animation completes for every element in the set. Choosing the effect whose axis matches the change, such as fade for appearance, reads most naturally.

$("#panel").hide(300);         // fade out and collapse to display:none
$("#panel").show(300);
$("#panel").toggle(300);       // respects the current state

$("#msg").fadeOut("slow");     // opacity only
$("#msg").fadeIn("slow");
$("#msg").fadeToggle(200);

$("#drawer").slideUp(400);     // height only
$("#drawer").slideDown(400);

// The callback runs when the animation finishes
$("#panel").fadeOut(400, function () {
  console.log("Fully hidden");
});

show and hide animate display, fade animates opacity, slide animates height, and every call takes a duration plus an optional completion callback.

5.2 The animate() method

5.2.1 Animate Details

Shows the general animation engine behind the shortcuts. animate takes a map of numeric CSS properties plus a duration, easing, and options, and tweens those values smoothly, for example animate({ left: '+=30', opacity: 0.5 }). Since only numeric values animate, strings must be expressed as numbers or relative increments. The options object also includes step and complete callbacks for per-frame and finished work.

$("#ball").animate(
  {
    left: "+=120px",          // relative move from the current value
    opacity: 0.5,             // any numeric CSS property
    height: 80,
  },
  {
    duration: 600,
    easing: "swing",          // default; "linear" is the other built-in
    complete: function () {}, // runs when the animation ends
  }
);

animate moves any numeric CSS property from its current value, supports relative targets like +=120px, and takes an options object for easing and completion.

5.3 Queues, stop, delay, finish

5.3.1 Queue Details

Explains that jQuery animations queue by default, so chained effects play one after another rather than at once. delay inserts a timed pause into the queue, and stop halts the current animation, optionally jumping to the end, clearing the queue, or both. finish jumps every queued animation to its final state instantly. Controlling the queue is essential, otherwise several rapid calls can leave effects stampeding over each other.

// Effects share a per-element queue, so these run one after another
$("#box")
  .slideUp(300)
  .delay(150)              // pause between effects
  .slideDown(300);

// Rapid hover-overs pile up unless you stop the running effect
$(this)
  .stop(true, true)        // clear the queue, jump to the end
  .animate({ left: 40 }, 200);

$("#box").finish();        // end everything instantly at final values

$("#box").queue(function (next) {
  doSyncWork();            // any custom step can join the queue
  next();                  // release the next step
});

Effects run sequentially through a per-element queue, delay inserts a pause, and stop(true, true) clears pending steps and snaps to the end before restarting.

5.4 CSS vs animation performance

5.4.1 CSS Animation Performance

Explains what animates cheaply and what forces the browser to do expensive work. Properties such as transform and opacity run on the compositor without re-layout, while top, left, width, and height trigger re-layout every frame. That is why modern CSS transitions and animations often beat jQuery effects for the same job. Treat jQuery effects as convenience helpers and move to CSS when motion becomes a requirement.

Browsers composite transform and opacity on the GPU. Animating width, height, left, or top forces layout reflows on every frame, and jQuery’s historic convenience effects all touch those properties. Prefer transform: translate() or CSS transitions for anything that runs often.

/* Cheap: compositor-only */
#panel { transition: transform .3s, opacity .3s; }
#panel.is-open { transform: translateX(0); opacity: 1; }

/* Expensive under animation: width, height, top, left, margin */

Moving with transform and fading with opacity stay on the compositor, while animating box properties triggers layout — which is why jQuery’s position effects run slower.

Respect prefers-reduced-motion. If the user asks for less motion, skip or shrink animations — accessibility and performance in one habit.

6 · AJAX

6.1 $.ajax in full6.2 Shorthands: $.get, $.post, $.getJSON6.3 Serializing forms and building queries6.4 Promise callbacks: done, fail, always6.5 Modern fetch, for comparison

Covers how jQuery lets pages talk to a server without reloading, through $.ajax and its helpers. You configure a request with url, method, and data, serialise form inputs, handle failures in a central way, and chain promise-style callbacks. The shorthand methods sit on top of the same machinery, so one mental model covers the whole chapter.

AJAX is how a page updates with fresh data instead of reloading. jQuery’s layer handles encoding, parsing, and error plumbing so you can focus on the data.

6.1 $.ajax in full

6.1.1 AJAX Config Details

Shows the configuration object of $.ajax, the one method every other AJAX helper wraps. You pass a plain object with url, method, data, dataType, headers, timeout, and callbacks such as success, error, and complete. The library builds the request, handles serialisation and CORS, and passes a derived promise back. Everything in the rest of the chapter is a shorthand over this single call.

$.ajax({
  url: "/api/posts",
  method: "GET",                // or POST, PUT, DELETE
  dataType: "json",             // parse the response as JSON
  data: { page: 2 },            // query string for GET, body otherwise
  success: function (data, status, xhr) {
    renderPosts(data);
  },
  error: function (xhr, status, err) {
    console.error(status, err);
  }
});

$.ajax takes one options object describing the request; success and error run on the outcome, and dataType tells jQuery how to interpret the response.

6.2 Shorthands: $.get, $.post, $.getJSON

6.2.1 Shorthand Details

Shows the convenience wrappers for the common request patterns, which read like sentences instead of a configuration dump. $.get(url) and $.post(url, data, callback) carry out the named verbs, and $.getJSON(url) is $.get with dataType set to json. Each returns the same promise and accepts arguments that the underlying $.ajax call would spread across its options. Pick the shorthand when the defaults match your need.

$.get("/api/posts", { page: 2 }, function (data) {
  renderPosts(data);               // GET with a query string
});

$.post("/api/posts", { title: "Hello" }, function (data) {
  console.log("Created", data.id); // form-encoded body
});

$.getJSON("/api/posts/7.json", function (post) {
  renderPost(post);                // like $.get with dataType:"json"
});

$.get, $.post, and $.getJSON hide the options object, so a request collapses to a URL, optional data, and a success callback.

6.3 Serializing forms and building queries

6.3.1 Serialization Details

Shows how to turn a form into a request payload without hand-building query strings. serialize reads the form’s successful controls and returns a URL-encoded string ready for a query or body, while serializeArray returns an array of name and value objects for further processing. $.param encodes a plain object or nested structure into the same query format. Together these keep data handling automatic and consistent.

var qs = $("#search-form").serialize();
// "q=jquery&category=utils"   (URL-encoded, in field order)

var arr = $("#search-form").serializeArray();
// [{name:"q", value:"jquery"}, {name:"category", value:"utils"}]

$.get("/api/search", $("#search-form").serialize(), renderResults);

// Build query parameters explicitly
var params = $.param({ q: "jquery", page: 2 });   // "q=jquery&page=2"
$.get("/api/search?" + params, renderResults);

serialize flattens the form into an encoded query string and serializeArray gives the name/value pairs, both ready to send with $.get or $.post.

6.4 Promise callbacks: done, fail, always

6.4.1 Promise Details

Shows the promise-style chain most jQuery code uses for AJAX, which reads more naturally than the success and error options. Every request returns a promise that categorises completion state, and you attach done for success, fail for failure, and always for code that runs either way. You can also register global handlers that observe all requests. Chaining these callbacks keeps each request’s outcome handling in one place.

$.getJSON("/api/posts")
  .done(function (data) {
    renderPosts(data);
  })
  .fail(function (xhr, status, err) {
    $("#error").text("Request failed: " + status);   // tell the user
  })
  .always(function () {
    $("#spinner").hide();            // runs on success or failure
  });

// Global handlers: every request passes through these
$(document).ajaxStart(function () { $("#spinner").show(); });
$(document).ajaxStop(function () { $("#spinner").hide(); });

done, fail, and always attach success, error, and cleanup paths, while ajaxStart and ajaxStop toggle a spinner once for any number of in-flight requests.

6.5 Modern fetch, for comparison

6.5.1 Fetch Details

Shows the native fetch counterpart so you can translate between the two worlds. fetch(url, options) returns a Promise that resolves with a Response object, and you check response.ok before consuming the body as text or json. Error handling differs, since fetch only rejects on network failure and treats HTTP errors as responses. The ideas match even though the shapes differ.

fetch("/api/posts", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "Hello" })   // JSON body, not form-encoded
})
  .then((r) => { if (!r.ok) throw new Error("HTTP " + r.status); return r.json(); })
  .then(renderPosts)
  .catch((err) => console.error(err));

fetch uses native Promises and requires manual JSON and error handling, whereas jQuery encodes forms and parses JSON for you — the trade-off of one fewer dependency.

Prefer $.ajax with a deferred for new jQuery code and fetch for new vanilla code. Legacy endpoints returning XML or form-encoded bodies are where jQuery still shines.

7 · Utilities & Deferred

7.1 $.each, $.map, $.grep7.2 $.extend and type checks7.3 Deferred objects7.4 $.when and parallel requests

Covers the static helpers jQuery keeps on the $ object for working with arrays, objects, and type checks, plus the Deferred object that powers the async story. The utilities transform and inspect ordinary data, while Deferred and $.when coordinate asynchronous work such as parallel AJAX calls. Together they let you manage data and timing without extra libraries.

Beyond the DOM, jQuery ships a small toolkit of helpers for plain data, and the Deferred object that gives you control over asynchronous flow.

7.1 $.each, $.map, $.grep

7.1.1 Each Detail

Shows the array and object utilities for iteration, transformation, and filtering. $.each iterates every item and calls a callback with the index and value, $.map transforms each item and flattens the result into a new array, and $.grep filters an array by a predicate or inverted test. Each works uniformly on arrays and on objects. Returning undefined from the map callback drops that item.

var nums = [1, 2, 3, 4];

$.each(nums, function (i, n) {
  console.log(i + ": " + n);
});

var doubled = $.map(nums, function (n) { return n * 2; });       // [2,4,6,8]
var evens   = $.grep(nums, function (n) { return n % 2 === 0; }); // [2,4]

// The same helpers also iterate object keys
$.each({ name: "Ada", age: 36 }, function (key, value) {
  console.log(key, value);
});

$.each iterates arrays or objects, $.map transforms every element into a new array, and $.grep filters one array down — the same trio in every JavaScript toolkit.

7.2 $.extend and type checks

7.2.1 Extend Detail

Shows the merge utility and the type-check helpers. $.extend copies properties from one or more objects into a target, and with deep as the first argument it merges nested structures recursively. It is the workhorse of plugin option handling, merging user options over defaults. The isType helpers such as isArray, isFunction, and isPlainObject answer the classic detection questions that loose JavaScript typing raises.

var defaults = { color: "red", size: 12 };

// merge right into left; duplicate keys keep the rightmost value
var config = $.extend({}, defaults, { size: 20 });
// { color:"red", size:20 }

// deep merge with "true" first for nested objects
$.extend(true, {}, defaults, { meta: { theme: "dark" } });

// type checks
$.isArray([]);            // true
$.isFunction(alert);      // true
$.isPlainObject({ a: 1 });// true
$.isNumeric("42");        // true
$.type(null);             // "null"
$.type([]);               // "array"

$.extend merges objects left to right, with true as the first argument enabling a deep merge, and the is* helpers give trustworthy type checks that raw typeof cannot.

7.3 Deferred objects

7.3.1 Deferred Detail

Explains the mechanics of the Deferred object, the engine behind every jQuery AJAX promise. You create a deferred, later call resolve or reject to settle it, and attach chained callbacks with done, fail, and always. The promise method returns a read-only view so outside code can observe the outcome without resolving it. Because .then and the other methods return new promises, async work chains naturally.

function loadWithDelay(url, ms) {
  var d = $.Deferred();
  setTimeout(function () {
    d.resolve(fetchCached(url));   // hand data to the done() handlers
  }, ms);
  return d.promise();              // expose only the read-only side
}

loadWithDelay("/api/stats", 500)
  .done(function (data) { renderStats(data); })
  .fail(function () { showError(); });

A Deferred is a promise you control: resolve alerts done handlers, reject alerts fail handlers, and returning d.promise() keeps callers read-only.

7.4 $.when and parallel requests

7.4.1 When Detail

Shows $.when, the utility that synchronizes several deferreds or promises. You pass multiple arguments, and the returned promise resolves only after every one of them has resolved, receiving all their values as arguments to the done callback. If any input rejects, the result rejects with that reason. It is the standard way to launch several AJAX requests in parallel and wait for all of them.

var authors = $.getJSON("/api/authors");
var posts   = $.getJSON("/api/posts");

$.when(authors, posts)
  .done(function (authorsRes, postsRes) {
    renderDashboard(authorsRes[0], postsRes[0]);
  })
  .fail(function () {
    console.error("At least one request failed");
  });

// $.when on plain values resolves immediately
$.when(1, 2, doAsync()).done(function (a, b, result) {
  console.log(a + b, result);   // result = resolved value of doAsync()
});

$.when waits for every request in the list, passes each resolved value into done, and is fail-fast: one rejection runs the fail handler.

8 · Plugins & Extending

8.1 Extending $.fn8.2 Options with $.extend8.3 The chaining pattern and quality8.4 Popular plugins — and the deprecation caution

Shows how to write, configure, and chain your own jQuery plugins by adding methods to $.fn. A plugin is a function that runs against the selected set, merges user options over defaults, and returns the set for chaining. Extending jQuery this way is how the ecosystem stayed useful for over fifteen years. You also learn the habits that keep plugins predictable and how to vet plugins you inherit.

A plugin is the word for a jQuery extension that behaves like a built-in method. Writing one teaches you the chainable, options-driven style that made the ecosystem work.

8.1 Extending $.fn

8.1.1 fn Detail

Shows the basic plugin skeleton: a function attached to $.fn. Inside the plugin, this is the jQuery collection the plugin was called on, and the function runs once against the whole set rather than once per element. You apply collection methods or iterate with each depending on the behaviour needed. Returning this at the end keeps the plugin chainable with whatever follows.

// Define the plugin on $.fn
$.fn.glow = function () {
  // 'this' is the jQuery collection produced by the selector
  this.css("box-shadow", "0 0 8px gold");
  return this;              // keep the chain alive
};

// Use it like any built-in method
$("#logo").glow().css("border-radius", 4);

A plugin is just a method on $.fn where this is the selection, and returning this keeps chaining working exactly like the built-in methods.

8.2 Options with $.extend

8.2.1 Options Detail

Shows the defaults-and-options merge pattern that every published plugin uses. You declare plugin defaults on the function or on $.fn.plugin.defaults, then merge the caller’s options over them with $.extend so a caller only passes what they want changed. Deep options use the recursive form. The pattern makes plugins configurable without breaking callers as defaults grow.

$.fn.tooltip = function (options) {
  // merge caller options over the defaults, fresh on every call
  var settings = $.extend({}, $.fn.tooltip.defaults, options);

  return this.each(function () {
    var $el = $(this);
    $el.append("<span class=\"tip-inner\">" + settings.text + "</span>");
  });   // each() keeps the chain intact while visiting every element
};

// Publish defaults so callers (and later overrides) can read them
$.fn.tooltip.defaults = { text: "Default text" };

$(".hint").tooltip({ text: "Click to edit" });

Defaults live on the plugin, $.extend overlays caller options per call, and returning this.each applies the logic element by element while the chain keeps flowing.

8.3 The chaining pattern and quality

8.3.1 Pattern Detail

Enumerates the habits that make plugins play well with the rest of jQuery. Always return this so calls chain, iterate safely with each or collection methods, expose defaults publicly for inspection and modification, and scope plugin names to avoid collisions. Respect whether your code needs to loop per element or act on the set. These practices make plugins predictable, testable, and friendly to share.

  • Always return this unless the plugin is a getter by contract.
  • Iterate with this.each so every selected element gets the treatment.
  • Expose $.fn.name.defaults so global default changes are possible.
  • Dispatch on the first argument: plugin("method", ...) for method-style plugins.
$.fn.counter = function (method) {
  var methods = {
    reset: function () { return this.text("0"); },
    inc:   function () { return this.text((+this.text()) + 1); }
  };
  if (methods[method]) { return methods[method].apply(this, arguments); }
  // No matching method: treat the call as initialization
  return this;
};

$("#count").counter("inc");    // dispatches to methods.inc
$("#count").counter("reset");

Dispatching on the first string argument turns one plugin entry point into many methods, letting each public action stay small and chainable.

8.4 Popular plugins — and the deprecation caution

8.4.1 Popular Detail

Notes the famous plugin ecosystem built over jQuery’s peak years, from widgets and sliders to data tables and lightboxes. Most of those 2010s plugins are now abandoned, so the chapter carries a deprecation caution: vet anything you adopt before shipping it. Check maintenance, browser support, and whether native or framework equivalents now do the job. Favouring well-maintained modern solutions is the responsible default.

The ecosystem that grew around jQuery — lightboxes, datepickers, carousels, table plugins — seeded hundreds of proven patterns. Many are unmaintained today, and some depend on jQuery versions or features that are gone. Before adopting, check the last commit date, jQuery 3.x compatibility, the license, and whether a native <dialog>, a native picker, or a v-if in your framework already covers it.

Treat every plugin as code you inherit. If it fails on jQuery 3.x/4 or has had no release in years, writing the forty-line native version is often cheaper than supporting it.

9.1 Interop with vanilla JS

9.1.1 Interop Detail

Shows how jQuery and native code live in the same DOM without friction. jQuery sets wrap the same nodes the browser knows, so you pull the raw element out with get(0) or index zero and hand it to native APIs, and wrap any native node in $() to use jQuery on it again. Mixing styles is fine as long as you re-query deliberately and avoid stale references.

// jQuery → native: read the DOM node
var node = $("h1")[0];            // or .get(0)
var name = node.tagName;          // "H1": a native field

// native → jQuery: wrap it back
var $el = $(document.querySelector("#app"));
$el.addClass("booted");

// Events coexist; handlers are just functions
$("button").on("click", function () {
  var form = this.closest("form"); // native method on the raw element
  if (form) form.reset();
});

Indexing a jQuery set yields the native node, wrapping a node with $ restores the jQuery methods, and inside a handler this is always the raw element.

9.2 Migrating away

9.2.1 Migrate Detail

Shows a low-risk path off jQuery using the migrate plugin and native replacements. You load the migrate plugin temporarily so deprecated jQuery calls keep working while it logs what each one can be replaced with. Then you swap usage method by method, for example querySelector for $, addEventListener for on, and fetch for AJAX helpers. Removing usage incrementally keeps the app shippable at every step.

// Load jquery-migrate during the transition; it logs removed APIs
<script src="https://code.jquery.com/jquery-3.7.1.min.js"></script>
<script src="https://code.jquery.com/jquery-migrate-3.4.1.min.js"></script>

/* Native replacements for the most common calls */
$(sel)                  → document.querySelectorAll(sel)
$el.find(sel)           → $el.querySelectorAll(sel)
$el.addClass / removeClass → el.classList.add / remove
$el.text()              → el.textContent
$el.val()               → el.value
$el.on("click", fn)     → el.addEventListener("click", fn)
$el.html(str)           → el.innerHTML = str  /* sanitize first */

The migrate plugin logs every removed API while you work, and the table translates the ten most common calls — most migrations are this small subset in repeat.

jQuery.migrate is a temporary aid, not a runtime to keep. Treat its console warnings as your migration checklist.

9.3 Performance tips

9.3.1 Perf Detail

Gives the practical rules for keeping jQuery fast in real pages. Cache selections in variables instead of re-querying the DOM, delegate events so one handler serves many elements, batch DOM writes, and use the narrowest selector that gets the job done. jQuery itself is fast; the usual slowdowns come from repeated queries and forced layout thrash. These habits apply to the whole page, not just jQuery.

  • Cache selections that repeat: var $cards = $(".card"); — re-querying on every loop is the classic sin.
  • Start with the tightest selector: #id first, then scope with $("#app").find(".row").
  • Delegate with on(evt, sel, fn) instead of hundreds of individual bindings.
  • Avoid layout thrash: batch reads, then batch writes.
  • Detach before heavy edits: detach(), mutate, then re-append.
// Bad: the selector reruns on every loop iteration
for (var i = 0; i < 200; i++) {
  $("#row-" + i).addClass("even");
}

// Better: query once, reuse the set
var $rows = $("[id^=row-]");
$rows.addClass("even");      // one query, one pass

Querying once outside the loop and reusing the set avoids hundreds of wasted lookups — the single most common jQuery performance mistake.

9.4 Frameworks, accessibility, security

9.4.1 Frameworks Detail

Positions jQuery against modern frameworks and covers the habits that outlive any library. Frameworks bring component models, declarative rendering, and reactivity that far exceed what jQuery offers, while jQuery stays lean for progressive enhancement. The accessibility habits cover using real interactive elements and announcing state changes to screen readers, and the security habits cover treating user input as data, escaping HTML, and never injecting unvetted markup.

ConcernGuidance
FrameworksReact/Vue/Svelte own the render cycle; reach for jQuery only for legacy or interactivity outside that cycle
AccessibilityKeep keyboard focus, roles, and aria-* honest; effects must never trap focus
SecurityNever insert unsanitized strings via .html(); escape server output; validate on the client and again on the server
When to keep itLegacy apps, admin panels, pages without a bundler — jQuery is stable and widely understood

Frameworks give you state and rendering; jQuery gives you surgical DOM edits. They coexist only when jQuery touches nodes the framework does not render, and the two never trade nodes. That boundary is the difference between a working hybrid and a mystery.
