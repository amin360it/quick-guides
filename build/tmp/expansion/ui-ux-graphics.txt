<h2 id="ch1" data-toc>1 ▸ Orientation and the Design Process</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">This guide is the bridge between designing an interface and building it. It assumes you can already design something you like, and covers the part where a design meets HTML, CSS, a component library, a browser on a slow phone, and a screen reader — and has to survive all of it. Eight chapters take you from the research that decides what to build, through the flows, visuals and interactions that define how it behaves, to the accessibility, design systems and hand-off that keep it right once it ships.</p>

<h3 id="ch1-1" data-toc>1.1 What UI/UX design is</h3>
<p class="topic-desc">Interface design and experience design are different jobs that ship as one artefact. You will be responsible for both, so the first thing to learn is which question each one answers.</p>
<h4 id="ch1-1-split">The two halves of the discipline</h4>
<p><strong>User interface design</strong> is the surface: layout, typography, colour, components, spacing, and how a screen reads at a glance. <strong>User experience design</strong> is everything around that surface: who the users are, what they are trying to do, what happens when they fail, and whether the whole journey — the email, the invoice, the error message, the phone call they make when it breaks — holds together. A page can win on one and lose on the other: a beautiful checkout that asks for the same address twice is a UX failure rendered in UI polish.</p>
<div class="codeWrap"><pre><code>// the two questions, side by side
UI asks:   does this screen look right, read right, feel right?
UX asks:   can the user achieve their goal with this product?

// the same task, and what each discipline contributes
TASK: reset a forgotten password
UI:   the call-to-action is findable, the field is labelled,
      the error message is legible
UX:   the reset email arrives, the link works once, the new
      password is accepted, and the user is signed in afterwards

// almost every "nobody uses this feature" report is a UX problem
// wearing a UI costume. the button was visible; the journey was not.</code></pre></div>
<h4 id="ch1-1-spec">A design is a specification, not a picture</h4>
<p>The mindset shift worth making early: a design is not a picture of a screen. It is a <em>specification</em> for behaviour under conditions you cannot fully control. Every value you choose has to survive a 320 px viewport, 200% browser zoom, a colour-blind user, a slow network, a screen reader, and a user who has turned your animations off in the OS settings. If a choice cannot justify itself against that list, it is decoration, and decoration ships at its own risk.</p>
<div class="codeWrap"><pre><code>// the design has to survive all of these, at once
the design has to survive:
  - a 320px viewport
  - 200% browser zoom
  - a colour-vision-deficient user (1 in 12 men)
  - a slow network: 3G, fonts not loaded yet
  - a screen reader announcing every element in order
  - the OS "reduce motion" setting switched on

// and a brief must say what it means, not what it hopes
GOOD: "Raise the contrast of the secondary text to at least 4.5:1,
      use the 16px type scale, and give the primary action a 44px
      hit area."
BAD:  "Make the landing page pop a bit more."
// a brief you can hand to a developer with no follow-up questions
// is a design decision. anything else is an intention.</code></pre></div>
<div class="note"><p>You need three things to work like this: a vocabulary precise enough to brief a developer ("make it pop" is not actionable; "raise the contrast of the secondary text to 4.5:1" is), a grip on the constraints so you design inside them (font rendering differs, users override colours, zoom is a feature, and not everyone sees colour the way you do), and a system so a hundred screens stay coherent (tokens and components, not one-off decisions).</p></div>

<h3 id="ch1-2" data-toc>1.2 The design process: research, design, test, ship</h3>
<p class="topic-desc">Design work is a loop, not a waterfall. Each pass reduces a different risk: research reduces the risk of building the wrong thing, testing reduces the risk of building the right thing wrong, and shipping turns the loop from a prototype into a product.</p>
<h4 id="ch1-2-loop">Four stages, four questions</h4>
<p>The loop has four named stages, and each one answers a question the stage before it could not. The output of each stage is the input of the next, so nothing is thrown away — the insight from research becomes the persona that drives the flow that becomes the prototype that the test plan checks.</p>
<div class="codeWrap"><pre><code>// the loop, and the question each stage answers
STAGE     QUESTION IT ANSWERS              ACTIVITIES                    OUTPUT
research  are we building the right thing? interviews, surveys,          insights,
                                          analytics, competitive        personas,
                                          review                         journey maps
design    can we build it?                flows, wireframes,            prototype,
                                          content, hi-fi mockups        spec
test      did we build it right?          usability tests, expert       findings,
                                          review, 5-second tests        fixes
ship      does it stay right?             analytics, support,           release,
                                          QA against the spec           follow-up
// each pass tightens the loop. a release is the start of the next
// research pass, not the end of the work.</code></pre></div>
<h4 id="ch1-2-artifacts">The loop in one line</h4>
<p>A stage's output is only worth anything if the next stage consumes it. A persona nobody puts in front of a flow is a slide in a deck; a test finding nobody feeds back into the design is a report in a drawer. The practical version of the loop is short enough to hold in your head, and every artifact on it is something you will see again in the chapters ahead.</p>
<div class="codeWrap"><pre><code>research -&gt; synthesize -&gt; design -&gt; prototype -&gt; test -&gt; iterate -&gt; ship
   |            |           |           |             |
 personas    journey    user      wireframes    test plan,
             maps       flows,    and hi-fi     findings
                        site map

// carry forward is the whole point
//  personas  -&gt; drive the user flows      (ch2, ch3)
//  flows     -&gt; shape the layout         (ch3, ch4)
//  prototype -&gt; gets tested              (ch7)
//  findings  -&gt; update personas + the design system (ch2, ch8)</code></pre></div>
<div class="tip"><p>Iteration is not a correction, it is the method. A prototype is a falsifiable hypothesis: "if the user can find it in under a minute, the layout works." Test it cheaply, learn, and change the design. The designers who ship fastest are the ones who make their assumptions cheap to disprove.</p></div>

<h3 id="ch1-3" data-toc>1.3 Tools, and how the guide is organised</h3>
<p class="topic-desc">Nothing in this guide depends on a specific application. Figma is the most common design tool and is used for examples; Sketch, Adobe XD, Penpot and a text editor in your repository all work. The deliverables that matter are tool-independent and live beside the code.</p>
<h4 id="ch1-3-tools">Tool-independent deliverables</h4>
<p>Because design tools change and codebases do not, the artifacts that last are the ones a build step can read. A token file diffs in code review, an SVG can be committed, and a written state list survives the designer leaving. If a deliverable can only be opened in the tool that created it, treat it as a draft, not a source of truth.</p>
<div class="codeWrap"><pre><code>// deliverables that matter, and where they live
[ ] design tokens: colours, type, spacing, radius, shadows
    - as JSON in the repo, next to the code that consumes them
[ ] flow and site maps        - text or diagram files, committed
[ ] SVGs                     - minified, colour via currentColor
[ ] component states          - one line per state, written down
[ ] redlines                 - for the screens that carry risk only

// a Figma library is a good authoring tool and a poor source of
// truth, because it is not readable by the build and does not diff.</code></pre></div>
<h4 id="ch1-3-map">How the eight chapters fit together</h4>
<p>Chapters 2 and 3 build the evidence you design from — who the users are and how they move through the product. Chapters 4 and 5 are the visual systems: layout, colour and type. Chapter 6 turns those systems into behaviour, chapter 7 tests it, and chapter 8 makes it accessible, systematised and shippable. You can open any chapter on its own; each section is self-contained, and the roadmap below says where it sits.</p>
<div class="codeWrap"><pre><code># the arc: understand, design, behave, ship
 1 orientation and process     what this work is, the loop
 2 research and synthesis      interviews, personas, journeys, tests
 3 information architecture    maps, flows, navigation, search
 4 visual design principles    hierarchy, grid, balance, whitespace
 5 colour, type, imagery       the three visual systems
 6 interaction and components  states, feedback, motion, forms
 7 prototyping and testing     wireframes to hi-fi, testing methods
 8 accessibility and delivery  WCAG, tokens, libraries, hand-off</code></pre></div>
<div class="tip"><p>Design tokens in version control beat any tool's export. A single JSON or YAML file of colour, type, spacing and radius values, committed beside the code, is the thing that actually prevents drift. It can be read by a designer, a developer, and a build step, and it diffs properly. A Figma library is a good authoring tool and a poor source of truth.</p></div>

<h3 id="ch1-4" data-toc>1.4 The one rule that matters most</h3>
<p class="topic-desc">If you remember one thing from this guide, remember this: contrast is a hard requirement, not a preference. It is the single check that separates a design that looks finished from one that fails the moment it ships.</p>
<h4 id="ch1-4-ratios">The ratios that are law</h4>
<p>WCAG defines the numbers, and they are small enough to internalise. Normal text needs 4.5:1, large text and UI boundaries need 3:1, and AAA text needs 7:1. You will meet these numbers again in chapters 5 and 8; for now, learn to read this block as the spine of the whole guide.</p>
<div class="codeWrap"><pre><code>// Contrast is a hard requirement, not a preference.
//
//   4.5:1  normal text              (WCAG AA)
//   3:1    large text, 18.66px+ bold or 24px+ regular   (WCAG AA)
//   3:1    UI components and their boundaries           (WCAG 1.4.11)
//   7:1    normal text              (WCAG AAA)
//
// check EVERY pair you ship, in EVERY state, in BOTH themes, with
// real content, not placeholder. Grey-on-grey is the single most common
// defect in a "beautiful" design that fails the moment it ships.</code></pre></div>
<h4 id="ch1-4-check">Where the rule breaks first</h4>
<p>The pairs that fail are not the ones you think about — they are the ones you never tested. Text on a tinted card is checked against the page and passes, then sits on the card and fails. Placeholder text inherits a browser opacity. Text on the accent colour only exists in one theme in the file. Build the habit of listing the hard pairs up front, and the chapters on colour (ch5) and accessibility (ch8) will give you the machinery to check them properly.</p>
<div class="codeWrap"><pre><code>// the five pairs that fail most often, in order of damage
1. muted text on tinted cards       (check against the card, not the page)
2. placeholder text                 (browsers render it at ~54% opacity)
3. text on the accent colour        (buttons; check BOTH themes)
4. disabled text                    (3:1 floor even though WCAG exempts it)
5. icons that carry meaning         (3:1 as non-text contrast)
// rule: check every pair, in every state, in both themes, with real
// content. an automated pass at build time is the only reliable way.</code></pre></div>

<h2 id="ch2" data-toc>2 ▸ UX Research and Synthesis</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Research is how you replace assumptions with evidence. A week of interviews and a few usability tests cost less than one redesign of a launched feature, and the material they produce — personas, journey maps, insights — is what every later decision in this guide gets checked against.</p>

<h3 id="ch2-1" data-toc>2.1 Interviews and surveys</h3>
<p class="topic-desc">Interviews tell you why people behave the way they do; surveys tell you how many people behave that way. They answer different questions, so they are designed differently and their results must not be confused.</p>
<h4 id="ch2-1-interview">The interview that finds the truth</h4>
<p>Five to eight interviews is a working number for most products — past that, the same stories recur and you are paying for confirmation. The interview is a guided conversation, not a questionnaire: open with the consent and the frame, ask them to walk through a real past task (the "grand tour"), and follow the surprises. The most valuable minutes are the ones where the participant tells you what you were not asking about.</p>
<div class="codeWrap"><pre><code># interview script — 45 minutes, one guest, no script-sticking
00:00  consent, recording on, "there are no wrong answers" frame
00:03  grand tour: "walk me through your last [task], start to finish"
00:12  "what surprised you?"     # follow the surprise, not the next question
00:25  "the last time something went wrong"
00:35  "what would you change if you could?"
00:42  "who else should I talk to?"   # recruits the next participant

# the facilitator's refrains
"tell me more about that"        # instead of leading
"what did you expect to happen?" # instead of explaining
"and then what?"                 # instead of moving on</code></pre></div>
<h4 id="ch2-1-survey">Writing questions that measure behaviour</h4>
<p>A survey is useless if the items cannot be answered honestly. Ask about a specific past behaviour, not an opinion ("when did you last reset a password?" beats "is password reset useful?"), test one construct per item, and pilot the whole thing on two colleagues before you spend anyone's time on it. The checklist below catches the failures that kill data.</p>
<div class="codeWrap"><pre><code>[ ] asks about a specific past behaviour, not an opinion
    "when did you last reset a password?"  not  "is password reset useful?"
[ ] one construct per item; split "and" questions
[ ] no leading wording ("don't you think the search is slow?")
[ ] options are exhaustive and mutually exclusive;
    a "not applicable" option exists
[ ] every respondent can answer every item; no compound traps
[ ] piloted on two colleagues before fielding</code></pre></div>
<div class="warn"><p>One interview is a story; forty answers is a statistic. Never draw a percentage from interview notes, and never quote a survey item as if it explained why. The interview gives you the mechanism, the survey gives you the scale — you need both, and they do not substitute for each other.</p></div>

<h3 id="ch2-2" data-toc>2.2 Personas</h3>
<p class="topic-desc">A persona is a synthesis artefact: the useful pattern of goals, frustrations and constraints found across your interviews and data, given a name so a room can talk about it. It is not a character sketch and it is not a requirements document.</p>
<h4 id="ch2-2-artifact">A persona that earns its place</h4>
<p>Three to five personas cover most products; more than that and they are preferences, not patterns. Every attribute in the persona must trace back to evidence — the interview, the survey segment, the support tickets — or it is fiction, and fiction has no veto power in a design review. Note what the persona is explicitly for, so it cannot be misused.</p>
<div class="codeWrap"><pre><code>// persona as a working artefact — grounded, specific, evidence-linked
{
  "name": "Priya",
  "context": "frontend lead at a 40-person agency",
  "goals": [
    "ship one design system across five client projects",
    "cut design review cycles to under a week"
  ],
  "constraints": [
    "works in a browser, on a 14-inch laptop",
    "inherits legacy CSS she cannot refactor"
  ],
  "painPoints": [
    "developers override design decisions late in the sprint",
    "no single source of truth for colours and spacing"
  ],
  "evidence": [
    "interviews 3 and 5 of 8, June",
    "support-ticket analysis, May-June"
  ],
  "usedFor": "design reviews: 'would Priya understand this screen?'",
  "neverUseFor": "feature requests — personas set context, not requirements"
}</code></pre></div>
<h4 id="ch2-2-use">Using personas without being fooled by them</h4>
<p>Put the persona in front of every design review, and refresh it only when new evidence contradicts it. The failure modes are all versions of treating the persona as a fact: a persona invented to argue for a feature, a persona with no constraints (everyone is "tech-savvy and busy"), and a persona that outlives its evidence.</p>
<div class="codeWrap"><pre><code># persona hygiene checklist
[ ] every attribute traces to evidence, named in the file
[ ] 3-5 personas; anything more is a preference list
[ ] constraints recorded, not just goals
[ ] reviewed against each new round of research
[ ] retired when evidence no longer supports the pattern
# anti-patterns
  - "the primary user is anyone with an internet connection"
  - a persona created to justify a feature the team already decided
  - a persona whose frustrations are all the competitor's fault</code></pre></div>
<div class="note"><p>Personas do not request features. A persona that "wants a dashboard" is not a requirement — it is a statement that the team has not yet done the task analysis. Use the persona to check comprehension and suitability, and use task analysis (next section) to decide what to build.</p></div>

<h3 id="ch2-3" data-toc>2.3 Journey maps and task analysis</h3>
<p class="topic-desc">A journey map follows a person across touchpoints and time and captures the emotional arc; task analysis zooms into one goal and scores every step. Together they are the picture and the microscope of the experience.</p>
<h4 id="ch2-3-journey">Mapping the journey, not the screen</h4>
<p>Build the map from research: stages across the top, the user's actions, thoughts and pains in each stage, and an opportunity in every row. Current-state maps describe what happens today and are the honest starting point; future-state maps are the design target. If a stage has no pain and no opportunity, it either does not belong or you have not looked hard enough.</p>
<div class="codeWrap"><pre><code>STAGE      ACTION                  THOUGHT                 PAIN                     OPPORTUNITY
Discover   searches "team billing" "which tool is real?"    five tabs, no baseline   show price early
Compare    opens the pricing page  "can we trial it?"       trial link hidden        "Try it" above the fold
Decide     invites a teammate      "will billing work?"     no seat preview          live seat calculator
Adopt      sends first invoice     "did it save?"           no confirmation state    success screen, next step
Advocate   mentions it to a peer   "it just worked"         recommendation           referral link in product

// row rule: if a stage has no pain and no opportunity, you are
// describing the map you hoped for, not the journey users have.</code></pre></div>
<h4 id="ch2-3-task">Task analysis: scoring every step</h4>
<p>Pick the tasks that matter (login, pay, export, reset) and break each into steps. Score every step for frequency, importance and difficulty — the friction column comes from tests and support tickets, not from opinion. Steps that are frequent, important and difficult are the ones worth redesigning; the rest are not.</p>
<div class="codeWrap"><pre><code>TASK                          FREQUENCY   IMPORTANCE   DIFFICULTY   FRICTION
reset a forgotten password    weekly      high         low          needs help text
share a dashboard link        daily       high         medium       link is in a menu
change the billing email      rarely      medium       high         form reloads twice
export this week's report     weekly      high         high         toolbar hidden

// the redesign order
//   high frequency + high difficulty  -> fix now
//   high importance  + high friction  -> fix now
//   rare + easy                       -> leave alone, document it</code></pre></div>

<h3 id="ch2-4" data-toc>2.4 Usability testing</h3>
<p class="topic-desc">Usability testing is the fastest source of truth in the whole discipline: five participants will surface most of a flow's serious problems in a morning. The craft is in writing tasks that test goals rather than clicks, and in resisting the urge to rescue the participant.</p>
<h4 id="ch2-4-plan">Tasks and metrics, written before the session</h4>
<p>Each task must be a goal in the participant's language ("find the price for forty seats"), never a click-by-click instruction ("click the pricing link in the nav"), because the second one tests whether people can follow instructions, not whether the interface makes sense. Define the success metric and pass bar per task in advance — that is what turns a session into comparable data.</p>
<div class="codeWrap"><pre><code>TASK  SCENARIO                         METRIC              PASS BAR
T1    "sign up and create a project"   task success        80%+ completes unaided
T2    "find the price for 40 seats"    time on task        under 90 seconds
T3    "export this week's report"      errors per task     one or fewer
T4    "cancel and confirm the change"  mis-clicks          none on destructive paths

# facilitator rules
- observe; do not teach. "what did you expect to happen?" not "try the toolbar"
- the participant's wrong guess IS the data. do not fix it for them
- think-aloud: "tell me what you're looking at and what you're deciding"</code></pre></div>
<h4 id="ch2-4-metrics">Turning sessions into numbers</h4>
<p>Raw notes are anecdotes until they are scored. Task success and time-on-task are the workhorses; the System Usability Scale adds a comparable 0–100 score in ten questions. The scoring rules are simple enough to do on paper in the debrief, and the SUS score gives you something to trend across rounds.</p>
<div class="codeWrap"><pre><code>// per-task metrics
function taskSuccess(completed, attempts) {
  return completed / attempts;          // compare against the pass bar
}
function timeOnTask(seconds, baseline) {
  return seconds &lt;= baseline ? "pass" : "fail";
}

// System Usability Scale (SUS) — 10 items, 5-point agree/disagree
// odd items  (1,3,5,7,9):   item score = answer - 1
// even items (2,4,6,8,10):  item score = 5 - answer
// SUS = sum(item scores) * 2.5   ->   0 to 100
// 68+ is above average; under 51 is a serious usability problem
const answers = [4, 2, 5, 2, 4, 1, 4, 2, 3, 2];   // example row
const score = answers.reduce((sum, a, i) =&gt;
  sum + (i % 2 === 0 ? a - 1 : 5 - a), 0) * 2.5;
console.log('SUS:', score);</code></pre></div>
<h4 id="ch2-4-run">The moderator's three worst habits</h4>
<p>Novice moderators turn a test into a demo in three specific ways, all of them well-meaning. Each one destroys the data it was meant to protect: answering for the participant hides their model of the UI, reassurance teaches them the "right" answer, and demonstrating turns observation into instruction. Silence, then the one question, is the whole technique.</p>
<div class="codeWrap"><pre><code>// what not to do, and what to say instead
[ ] answering for the participant         -> stay quiet, wait longer
[ ] reassuring ("it's fine, everyone")    -> "there are no wrong answers"
[ ] teaching ("try dragging instead")     -> "what did you expect to happen?"
// if you explain more than twice in a session, your task was written
// as instructions. rewrite it as a goal.
// five participants finds most issues; three is the minimum to trust a
// finding at all.</code></pre></div>

<h3 id="ch2-5" data-toc>2.5 Synthesis: affinity mapping and insights</h3>
<p class="topic-desc">Synthesis is where messy notes become decisions. Affinity mapping clusters observations into themes, and insight statements turn those themes into claims you can design against — and argue about, productively.</p>
<h4 id="ch2-5-affinity">Affinity mapping that survives the room</h4>
<p>Write one note per observation, phrased as a fact with its source attached, then group the notes on a wall by theme. Name each cluster in the participants' language, not yours ("I gave up and called support" becomes the cluster "support is the last resort"). Count clusters, not notes: five clusters of three notes outrank fifteen scattered ones.</p>
<div class="codeWrap"><pre><code>// one note per observation, source attached
{ "id": "n14", "person": "g4", "quote": "I gave up and called support",
  "theme": "" }

// clustering
- drop every note onto the wall
- move them in silence first; argue only about the disputed few
- name each pile from the quotes, not from your vocabulary
- a quote in two piles = the theme is real, split it into two

// output check
//   5 clusters of 3 notes each   -> a report you can design from
//   15 notes, no clusters        -> you stored data, you did not synthesise</code></pre></div>
<h4 id="ch2-5-insight">Insight statements, not observations</h4>
<p>An observation is raw ("three users could not find the export link"); an insight explains the mechanism ("users call support instead because the toolbar appears only after a row is selected"). Insights are what you can design against, because they name the cause. If you cannot finish the sentence with evidence, you have an observation — which is fine, but it is not yet a finding.</p>
<div class="codeWrap"><pre><code># insight template
"When [context] happens, [user] does [behaviour] because [reason]."

# observation   ->  insight
users cannot find the export link
              ->  "When the page has no rows selected, users look for
                  the export action in the wrong toolbar, because the
                  actions that matter are hidden until a row is
                  selected."

# test an insight before you trust it
[ ] the mechanism is named (the "because" is filled in)
[ ] evidence is attached (sessions, quotes, counts)
[ ] it is falsifiable: a counter-example would change the design
# an insight with no "because" and no evidence is a guess with
# better punctuation.</code></pre></div>
<div class="tip"><p>Synthesis is not a meeting about feelings. It is a machine with two outputs — clusters and insight statements — and you run it until both are done. If the team leaves the room with neither, run it again with a stricter rule: no insight enters the backlog without evidence attached.</p></div>

<h2 id="ch3" data-toc>3 ▸ Information Architecture and Flows</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Information architecture is the invisible layout: how content is organised, named and reached. Before a single pixel, the structure decides whether the product makes sense. This chapter covers site maps and inventories, user flows, navigation and labelling, search, and the first-run experience that teaches it all.</p>

<h3 id="ch3-1" data-toc>3.1 Site maps and content inventories</h3>
<p class="topic-desc">A site map is the product's skeleton; a content inventory is the list of its bones. You cannot reorganise what you have not listed, and you cannot test a structure you have not drawn.</p>
<h4 id="ch3-1-sitemap">Drawing the skeleton</h4>
<p>Write the map as a nested list — indentation is the hierarchy. Every node is a page or a task, and the depth of the tree is a promise about how many clicks users will need. A node under three parents is a sign that the structure is organised by department (whose) rather than by task (why). Keep level-one items to five to nine, which is the number a person can hold in working memory when they scan a nav bar.</p>
<div class="codeWrap"><pre><code># site map — indentation is the hierarchy
/                      home: hero, trust signals, primary CTA
/about                 story, team, contact
/docs                  quick start
/docs/getting-started  install, first project
/docs/guides           three deep-dives
/docs/reference        API reference
/pricing               plans, comparison table, FAQ
/pricing/compare       detailed feature matrix
/help                  search, contact, status
/blog                  index of articles, tags

# structure tests
[ ] every level-one item answers "why am I here?" not "whose is it?"
[ ] no page lives under two parents
[ ] the task a user comes for is reachable in 2 clicks from home
[ ] dead pages (no inbound link, no nav entry) are deleted or merged</code></pre></div>
<h4 id="ch3-1-inventory">The content inventory</h4>
<p>Before reorganisation, list what actually exists — URL, title, type, owner, status, and a note recording why a page matters or does not. Inventories are the corrective to redesigning around the pages you remember; the useful ones find the orphaned and duplicated content nobody plans for, which is usually more of the site than anyone expects.</p>
<div class="codeWrap"><pre><code># content inventory (CSV-shaped, before migration)
URL              TITLE            TYPE      OWNER  STATUS     NOTES
/                Home             landing   mkt    published  hero copy outdated
/pricing         Pricing          landing   mkt    published  FAQ anchor missing
/docs/quick      Quick start      guide     eng    draft
/docs/guide-2019 Getting Started  guide     -      orphan     duplicate of /docs/quick
/thanks          Thank you        system    eng    published  noindex, keep
/search?q=       Search           system    eng    published  noindex

# actions the inventory forces
- duplicate guides   -> merge, keep the canonical URL
- orphan pages       -> re-home or retire
- "noindex" rows     -> confirm robots treatment, not deletion of useful content</code></pre></div>

<h3 id="ch3-2" data-toc>3.2 User flows and task flows</h3>
<p class="topic-desc">A user flow is the sequence of screens and decisions a person walks through to reach a goal. Drawing the flow before designing the screens is what stops the design from being a gallery of pages nobody can navigate between.</p>
<h4 id="ch3-2-flow">Notation that fits on a whiteboard</h4>
<p>Flows are drawn as nodes and arrows: a screen, a decision, a branch. Write the happy path first and make it short — every extra screen you add to the happy path is a cost you impose on every user, forever. Then name each arrow: an arrow that says "choose a plan" is a decision; an arrow that says "next" is a feature request.</p>
<div class="codeWrap"><pre><code># user flow, ASCII — happy path plus the first decision
[Start: /pricing]
    |
    | choose a plan
    v
[Sign up panel]
    |
    | submit email
    v
[email valid?] -- yes --> [Create account]
    |
    +-- no --> [inline error on the field] -- retry --> [email valid?]

[Create account] --> [dashboard empty state] --> [first CTA]

# rules
- one goal per diagram; name it in the title
- every arrow is a screen, an action, or a decision — label it
- the happy path has the fewest possible nodes
- a node with no inbound arrow is unreachable; delete it</code></pre></div>
<h4 id="ch3-2-errors">The error branches are the design</h4>
<p>Users meet the happy path rarely and the error paths constantly — a flow with only the happy path is a marketing diagram, not a specification. Draw the branch for every failure the system can produce: declined card, invalid email, expired session, empty result. The rule of thumb: every screen gets a next action, and every action gets a failure branch.</p>
<div class="codeWrap"><pre><code># the same flow, with the failure branches drawn
[Pay] -&gt; card declined? -- yes --> [inline error + retry] ----&gt; [Pay again]
                        +-- no  --> [confirmation screen + next step]

# dead-end check
- a dead-end is any screen with no visible next action
- "try again later" without a way to be notified is a dead end
- an error inside a modal that closes the modal is a dead end

# flow completeness checklist
[ ] every action has a failure branch
[ ] every screen has a next action, including final states
[ ] cancellation and "back" exist for multi-step flows
[ ] session expiry is handled, not just styled</code></pre></div>
<div class="warn"><p>The dead-end is the most common flow bug in shipped products: a "payment failed" screen with no retry button, an empty state with no way in, a success screen with nothing to do next. When you audit your flows, look for screens that end conversations instead of continuing them.</p></div>

<h3 id="ch3-3" data-toc>3.3 Navigation and labelling</h3>
<p class="topic-desc">Navigation is how users move; labelling is what they look for. Both are systems you can test, and both fail in the same way: labels that match internal vocabulary instead of the user's.</p>
<h4 id="ch3-3-patterns">The navigation patterns, and the markup they need</h4>
<p>Global nav is the top bar, local nav is the sidebar, and contextual nav is links inside content — a product usually needs all three, but only one level of each. Whatever the pattern, the markup matters as much as the look: a real <code>&lt;nav&gt;</code> landmark with real links and a correct <code>aria-current</code> on the active item is what a screen reader user navigates by, and it is cheap to get right.</p>
<div class="codeWrap"><pre><code>&lt;nav aria-label="Main"&gt;
  &lt;ul&gt;
    &lt;li&gt;&lt;a href="/docs" aria-current="page"&gt;Docs&lt;/a&gt;&lt;/li&gt;
    &lt;li&gt;&lt;a href="/pricing"&gt;Pricing&lt;/a&gt;&lt;/li&gt;
    &lt;li&gt;&lt;a href="/blog"&gt;Blog&lt;/a&gt;&lt;/li&gt;
    &lt;li&gt;&lt;a href="/help"&gt;Support&lt;/a&gt;&lt;/li&gt;
  &lt;/ul&gt;
&lt;/nav&gt;

// pattern rules
//   - one "current" indicator per page, in one place
//   - nav label sources: real links, not divs with click handlers
//   - an expanding menu announces its state (aria-expanded, ch6)
//   - five to nine top-level items; more is a hierarchy problem</code></pre></div>
<h4 id="ch3-3-labelling">Labelling that survives scanning</h4>
<p>Users do not read nav bars, they scan them for the word they brought with them — so the test for a label is findability, not clarity. Card sorting is the cheap version: put the product's pages on cards, ask people to group and name them, and look at where their names disagree with yours. The disagreements are the findings; the fix is renaming to the users' vocabulary, not arguing about it.</p>
<div class="codeWrap"><pre><code># card sort output — users group by task, not by department
group "account"    cards: profile, password, billing, teams
group "build"      cards: projects, apps, keys, deployment logs
group "learn"      cards: docs, guides, blog, support

# mismatch example
"settings" appeared in three groups in the same sort.
the word meant account settings, app settings and regional
settings to different people. rename ("Account", "Project settings",
"Language and region") or the word is ambiguous.

# label checklist
[ ] label = the word users search and scan for
[ ] no internal jargon, no product-invented verbs
[ ] every label tested against at least one card sort
[ ] "more" and "other" menus say what they contain</code></pre></div>

<h3 id="ch3-4" data-toc>3.4 Search and findability</h3>
<p class="topic-desc">Search is the second navigation system: it serves users who could not find it by browsing, so its quality is measured in how well it rescues them. Most "search doesn't work" complaints are really "search can't find what I call it".</p>
<h4 id="ch3-4-index">An index that understands synonyms</h4>
<p>The searchable index is a design artifact as much as an engineering one. Boosting exact-match fields (title, tags) above body text is a design decision, and so is the synonym map — a UK spelling "colour" must match a page that says "color" if your users mostly type either. Sketch the schema in the design phase; it is the spec the build will implement.</p>
<div class="codeWrap"><pre><code>// search index spec — field weights and synonyms, decided up front
{
  "fields": [
    { "name": "title",   "weight": 1.0 },
    { "name": "summary", "weight": 0.6 },
    { "name": "tags",    "weight": 0.8 },
    { "name": "body",    "weight": 0.2 }
  ],
  "synonyms": {
    "colour": ["color"],
    "ui": ["interface", "user interface", "front end"],
    "reset": ["forgot password", "recover", "lost password"]
  }
}
// a user who types "color" must hit the page that says "colour".
// define the synonym map with your support team — they hear the
// words users actually type.</code></pre></div>
<h4 id="ch3-4-facets">Faceted search: filtering, not querying</h4>
<p>Facets let users narrow a result set by attributes (price, region, status). The design rule is that facets filter the existing result set — they never change what is being searched — and each active facet must be visible and removable in one click. A facet with a single option is a filter the user cannot avoid, which is a search failure wearing a UI. The markup below is the accessible shape: a fieldset of labelled checkboxes, so each filter is announced with its own label.</p>
<div class="codeWrap"><pre><code>&lt;aside aria-label="Filter results"&gt;
  &lt;fieldset&gt;
    &lt;legend&gt;Plan type&lt;/legend&gt;
    &lt;label&gt;&lt;input type="checkbox" name="plan" value="free" checked&gt; Free&lt;/label&gt;
    &lt;label&gt;&lt;input type="checkbox" name="plan" value="paid"&gt; Paid&lt;/label&gt;
    &lt;label&gt;&lt;input type="checkbox" name="plan" value="trial"&gt; Trial&lt;/label&gt;
  &lt;/fieldset&gt;
  &lt;fieldset&gt;
    &lt;legend&gt;Region&lt;/legend&gt;
    &lt;label&gt;&lt;input type="checkbox" name="region" value="eu"&gt; EU&lt;/label&gt;
    &lt;label&gt;&lt;input type="checkbox" name="region" value="us"&gt; US&lt;/label&gt;
  &lt;/fieldset&gt;
&lt;/aside&gt;

// rules
//   - active facets are visible and removable in one click
//   - a facet with exactly one option is not a filter, remove it
//   - "no results" suggests: clear filters, search again, contact
//   - results announce their own count ("42 of 210")</code></pre></div>

<h3 id="ch3-5" data-toc>3.5 Onboarding and the first-run experience</h3>
<p class="topic-desc">The first session decides whether there is a second. Onboarding is not a feature tour — it is progressive disclosure tuned to the moment: give the user enough to do their first real task, and let the interface teach the rest.</p>
<h4 id="ch3-5-principles">Progressive disclosure, not a tutorial</h4>
<p>The first screen must answer two questions instantly: what is this, and what do I do first? Ask for only what the first task needs — an account creation form with six optional fields is six reasons to leave. Every step should be skippable and reversible, and progress should show steps remaining, not a confetti of completed arbitrary tasks. The single highest-leverage trick is to let the real interface load progressively instead of running a fake tour on top of it.</p>
<div class="codeWrap"><pre><code>[ ] first screen answers "what is this and what do I do first?"
[ ] one decision per step; account details deferred until they matter
[ ] progress shows what remains, not what was completed
[ ] every action is reversible; "skip for now" actually works
[ ] no tour overlay that blocks the interface it is explaining
[ ] the real interface, enabled progressively, beats a fake tutorial

# the requirement hierarchy for a signup flow
1. email + password        (the minimum to create an account)
2. workspace name          (needed for the first screen to make sense)
3. invite teammates        (defer to the empty state, not the form)
4. preferences             (defer until there is something to prefer)</code></pre></div>
<h4 id="ch3-5-empty">Empty states are onboarding</h4>
<p>The empty state is the only screen every new user sees, which makes it the most valuable real estate in the product. It must explain what belongs here, why it is empty, and how to fill it — in that order. A plain "You have no projects" with no way forward is the dead-end of chapter 3.2 wearing an empty state.</p>
<div class="codeWrap"><pre><code>&lt;div class="empty"&gt;
  &lt;svg aria-hidden="true" viewBox="0 0 24 24"&gt;&lt;!-- an illustration --&gt;&lt;/svg&gt;
  &lt;h2&gt;No projects yet&lt;/h2&gt;
  &lt;p&gt;Create one and it will appear here.&lt;/p&gt;
  &lt;a class="btn" href="/projects/new"&gt;Create project&lt;/a&gt;
&lt;/div&gt;

// empty state anatomy, in order
1. what this space is for      ("Projects")
2. why it is empty             ("You have not created one yet")
3. how to fill it              (one primary action; secondary as a link)
// and the mirrored states every list needs
   - first-run (new user)      - empty (no results for filters)
   - cleared (all done)        - error (could not load the list)</code></pre></div>
<div class="tip"><p>Every list in the product gets four states — data, empty, error, loading — and the empty and error ones are the ones users complain about in support tickets. Design them once, in the component (see ch6), and every screen that uses the list inherits them.</p></div>

<section class="chapter">
<h2 id="ch4" data-toc>4 ▸ Visual Design Principles</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Before colour or type, a layout tells the user what matters. Get hierarchy right and the rest is decoration; get it wrong and no amount of polish rescues the page. This chapter covers the signals of importance, grouping, the invisible grid, balance and eye path, and the deliberate use of space.</p>

<h3 id="ch4-1" data-toc>4.1 Hierarchy: levels and the signals of importance</h3>
<p class="topic-desc">Hierarchy is the answer to: when someone's eye lands here, what do they read first, and what do they skip? Everything on the page is competing for attention, and hierarchy is how you decide who wins.</p>
<h4 id="ch4-1-levels">Name the levels before you style them</h4>
<p>A page has roughly four to six levels of importance, and if you cannot say which level something is, that is the design problem. "Is this a tertiary button or a link?" means the hierarchy has not been decided. The common failure is three things competing at level one — the eye cannot prioritise three things, so it prioritises none.</p>
<div class="codeWrap"><pre><code>// a page has roughly 4-6 levels of importance. name them.
LEVEL 1  the page's single purpose: the main heading, the primary action
LEVEL 2  section headings
LEVEL 3  supporting content, secondary actions
LEVEL 4  metadata: timestamps, counts, helper text
LEVEL 5  chrome: nav, footer, legal

// if you cannot say which level something is, that is the design
// problem. "is this a tertiary button or a link?" means the
// hierarchy has not been decided.

// THE COMMON MISTAKE: too many levels competing
//  three things at LEVEL 1 on one screen. The eye cannot prioritise
//  three things, so it prioritises none of them and the user reads
//  none of it. Pick one.</code></pre></div>
<h4 id="ch4-1-signals">Five variables, pointing the same way</h4>
<p>Five visual variables carry hierarchy: size, weight, colour and contrast, space, and position. They are all usable, but the rule is that they must agree — a 28 px light-grey heading with 4 px of space above it says "important but not really", and that ambiguity is worse than committing to one. Size is the strongest signal; weight is cheaper than size, so prefer it for sub-levels; space is the most underrated.</p>
<div class="codeWrap"><pre><code>// 1. SIZE
//    the strongest signal. 32px is read before 16px, always.
//    if two things are the same size, the reader has no basis to
//    choose, so the design has failed to communicate priority.

// 2. WEIGHT
//    700 for headings, 400 for body, 300 for meta. Weight is cheaper
//    than size, so prefer it for sub-levels.
//    CAUTION: variable fonts let you pick any weight, which is a trap.
//    Six weights in one interface is noise. Three is a system.

// 3. COLOUR AND CONTRAST
//    the primary heading at full-contrast text colour; the secondary
//    at a lower one. A large, low-contrast heading reads as an
//    accident rather than a heading.

// 4. SPACE
//    the most underrated. Space around an element says "this is a
//    group, and this group matters". Space is what separates a
//    section from the next one without a line.
//    if two elements are 4px apart they are one group. if 32px
//    apart they are two things.

// 5. POSITION
//    top-left is read first on a left-to-right language. Anything in
//    the top-left region of the viewport gets attention that
//    something in the middle-right does not. Use it.

// THE RULE THAT MATTERS MOST
//    size, weight, colour, space and position must all point the same
//    way. The moment they disagree, the reader gets two conflicting
//    messages and reads neither.
//
//    a 28px light-grey heading with 4px of space above it says
//    "IMPORTANT but not really". That ambiguity is worse than
//    committing to one.</code></pre></div>

<h3 id="ch4-2" data-toc>4.2 Proximity, grouping and Gestalt</h3>
<p class="topic-desc">The Gestalt principles are not decoration; they are how the eye segments a page. Use them and the layout explains itself; ignore them and readers have to work out your structure by trial.</p>
<h4 id="ch4-2-principles">The principles that do the work</h4>
<p>Proximity is the workhorse — things near each other are perceived as a group, which is how you bind a label to its input with nothing more than distance. Similarity groups by appearance, continuity lets the eye follow a path, closure completes an incomplete circle, and connection — a physical line — removes all ambiguity where the association is critical. Figure and ground is the most powerful and least used: a modal needs a scrim, and a focused task needs everything else suppressed.</p>
<div class="codeWrap"><pre><code>// PROXIMITY: things near each other are perceived as a group
//   the workhorse. it is how you group a label with its input
&lt;label&gt;Email address&lt;/label&gt;
&lt;input type="email" name="email"&gt;
//   8px between them. 24px between this pair and the next.
//   the reader never has to be told which label belongs to which field.

// SIMILARITY: things that look alike are perceived as related
//   two cards with the same structure read as "the same kind of
//   thing". that is useful, so make all cards in a set look alike.

// CONTINUITY: the eye follows the smoothest path
//   a curved line that suggests a flow is followed. a straight
//   border that stops and starts is not.

// CLOSURE: the eye completes incomplete shapes
//   a circle with a 40px gap reads as "a circle", not "an arc".
//   use it for play buttons, avatars, and any shape that would be
//   expensive to draw completely.

// CONNECTION: connected elements are related
//   the most reliable of all. a line from a label to its control
//   removes all ambiguity. Use it where the association is critical.

// FIGURE AND GROUND: the thing you see depends on what you exclude
//   the most powerful and least used. a modal needs a scrim to
//   separate it from the page behind. A focused task needs
//   everything else visually suppressed.</code></pre></div>
<h4 id="ch4-2-mistakes">The Gestalt mistakes that ship anyway</h4>
<p>Three mistakes recur in real layouts, and each one is a principle applied backwards. Equal spacing everywhere means nothing groups; a border between two related items actively separates them; and a container that sits 8 px from its first child and 40 px from its neighbour makes the reader pick the wrong parent. The fix for all three is to state which elements are one group before you choose any distance.</p>
<div class="codeWrap"><pre><code>// COMMON GESTALT MISTAKES
//   - equal spacing everywhere, so nothing groups
//   - a border between two related items, which actively separates them
//   - a container that is 8px from its first child and 40px from its
//     neighbour, so the reader picks the wrong parent

// the audit
page  -&gt; 9 px gap here, 9 px there, 9 px everywhere: pick groups first
card  -&gt; a divider between title and body: do they belong together?
field -&gt; 24 px from its label but 8 px from the next field:
         which one does the label own?</code></pre></div>

<h3 id="ch4-3" data-toc>4.3 Alignment and the invisible grid</h3>
<p class="topic-desc">Every element on a page should align to something; almost nothing should be "roughly" placed. The column grid is the tool, CSS grid is the implementation, and the choice between grid and flex is a decision you should be able to name.</p>
<h4 id="ch4-3-columns">The twelve-column grid</h4>
<p>Twelve divides by 2, 3, 4 and 6, so you can make two-up, three-up, four-up and six-up layouts with no half columns — which is why it beat 16 (powers of two only) and 10 (too coarse for wide screens). A 1200 px container with 24 px gutters and 24 px margins gives a 1248 px page; components span column counts, never arbitrary widths.</p>
<div class="codeWrap"><pre><code>// every element on a page should align to something. almost nothing
// should be "roughly" placed.

// THE COLUMN GRID
//   12 columns, 24px gutters, a max-width container.
//   1200px content + 2 x 24px margins = 1248px page.
//   Components span column counts: a card is 4 columns, a hero is 8.

// WHY 12
//   it divides by 2, 3, 4 and 6, so you can make 2-up, 3-up, 4-up
//   and 6-up layouts with no half columns. 16 would give you powers
//   of two only; 10 is too coarse for a wide screen.

// IN CSS
.container { max-width: 1248px; margin-inline: auto; padding-inline: 24px; }
.grid {
  display: grid;
  grid-template-columns: repeat(12, minmax(0, 1fr));
  gap: 24px;
}
.span-4 { grid-column: span 4; }</code></pre></div>
<h4 id="ch4-3-flex">Grid or flex, and alignment as a decision</h4>
<p>Grid is two-dimensional — you know the rows and the columns up front — and it is for page layout, card grids and forms. Flex is one-dimensional — a row or column sized to its content — and it is for toolbars, chips and a centred logo. The mistake is flex for a page layout: it works until a second row must align with the first. And alignment itself is a decision: left-aligned text is faster to read; centred text is fine for a headline under sixty characters and terrible beyond it.</p>
<div class="codeWrap"><pre><code>// USE GRID OR FLEX, AND KNOW WHICH
//   Grid: two-dimensional. You know the rows AND columns up front.
//         Page layout, card grids, form layouts.
//   Flex: one-dimensional. You have a row or a column and want the
//         items sized to their content.
//         A toolbar of buttons, a row of chips, a centred logo.
//
// the mistake: flex for a page layout. It works until you need a
// second row to align with the first, and then you rewrite it in grid.

// ALIGNMENT AS A DECISION, NOT A DEFAULT
//   left-aligned text is faster to read for long passages. centred
//   text is fine for a headline under 60 characters and terrible for
//   anything longer, because the reader's eye has to find the next
//   line's start every time.
//   rule of thumb: if the text wraps to more than two lines, left it.</code></pre></div>

<h3 id="ch4-4" data-toc>4.4 Balance, focal points and the eye path</h3>
<p class="topic-desc">A page should have an entry point, a path, and an exit — and the whole composition should be balanced so the eye is led, not bounced. This section covers visual weight, optical balance, and how to test the path with five seconds of someone's time.</p>
<h4 id="ch4-4-weight">Visual weight and optical balance</h4>
<p>Weight is how "heavy" an element looks: dark, large, dense, saturated. Symmetric layouts read as stable and formal; asymmetric ones read as modern and dynamic — neither is better, but consistency is. Balance is optical, not mathematical: a circle's perceived centre sits slightly above its geometric centre, and a heavy text block overflows its box visually. When something looks 2 px off, nudge it; do not "fix" it back to a grid that is lying to you.</p>
<div class="codeWrap"><pre><code>// visual weight is how "heavy" an element looks: dark, large, dense,
//   detailed, saturated. The page should be balanced overall.

// SYMMETRY
//   symmetric layouts feel stable and formal. Banks, government,
//   anything implying trustworthiness.
//   asymmetric layouts feel modern and dynamic. Editorial, product,
//   anything implying movement or progress.
//   Neither is better. Pick one and be consistent.

// OPTICAL BALANCE, not mathematical
//   a circle's perceived centre is slightly above its geometric
//   centre. a triangle's weight sits below its centroid. Text set in
//   a heavy weight optically overflows its box.
//   the practical rule: when something looks 2px off, nudge it. Do
//   not "fix" it back to the grid.
//
//   letter-spacing, optical:
//     -0.01em  on large display type   (tighten)
//      0.02em  on small caps and tracking (open it)
//     -0.02em  on headings at 24px+
//   This is why two designers using the same font and size produce
//   different-looking headings. The spacing is doing work.

// WEIGHT BALANCE CHECK, a genuinely useful exercise
//   squint at your page until it blurs, or convert it to greyscale.
//   What reads as dark blobs? Those are your focal points. If there
//   are more than two or three, there is no hierarchy and the page
//   has no entry point.
//   Then look at it in greyscale to check that your palette is not
//   doing the work that size and space should be doing.</code></pre></div>
<h4 id="ch4-4-path">The entry point, the path and the exit</h4>
<p>The eye enters top-left in a left-to-right language, so that is where level-one content belongs; if your most important element is bottom-right, you either move it or build a lead-in above it. Text-dense pages follow an F-pattern (the eye returns to the left margin), so put the important words at line starts; sparse pages follow a Z-pattern only if the elements are visually connected. Every page needs an exit: an obvious next action that is the last thing the eye reaches.</p>
<div class="codeWrap"><pre><code>// a page should have an entry point, a path, and an exit.

// THE ENTRY POINT
//   top-left by default, in left-to-right languages. top-right in
//   right-to-left. The reader's eye goes there first, so that is
//   where LEVEL 1 content goes.
//   if your most important element is bottom-right, you have a
//   problem. Options: move it, or accept that you need something
//   above it to lead the eye down.

// THE PATH
//   arrange elements so the eye flows: a strong element, space, the
//   next element, space. Avoid two equal-weight elements side by
//   side with nothing leading between them: the reader stops.
//
//   F-pattern for text-dense pages: left-to-right, then down a little,
//   then left-to-right. It happens because the eye returns to the
//   left margin. Design for it: put the important words at line
//   starts, not line ends.
//   Z-pattern for sparse pages: top-left, top-right, bottom-left,
//   bottom-right. It happens only if the elements are visually
//   connected. Without connectors it is just a guess.

// THE EXIT
//   every page needs an obvious next action, and it should be the
//   last thing the eye reaches. A form with a submit button in the
//   top-left, above the fields, makes people hunt.

// TESTING THE PATH
//   the 5-second test: show someone the page for 5 seconds, cover
//   it, and ask what it is for and what the main action is. If they
//   are wrong, your hierarchy is not doing its job. No amount of
//   user research is needed for this and it catches most problems.</code></pre></div>

<h3 id="ch4-5" data-toc>4.5 Density and whitespace</h3>
<p class="topic-desc">Density is a decision about how much fits, made per screen rather than globally; whitespace is the element that groups, separates and prioritises. Together they decide whether a screen feels calm or instrumented — and both are systems, not instincts.</p>
<h4 id="ch4-5-density">Density is per context, not per product</h4>
<p>A landing page is spacious on purpose; a data table earns its compactness; a form does neither. The failure mode is one density for everything: a table with 48 px rows wastes the screen, a form with 12 px rows is unreadable and mis-clickable. Set density per context — CSS makes this cheap with a data attribute on a container — and respect the touch-target floor: 44 by 44 CSS pixels for anything tappable, which a 24 px icon button reaches with padding, not a smaller hit area.</p>
<div class="codeWrap"><pre><code>// DENSITY is a decision about how much fits, and it should be
// deliberate per screen rather than global.

SPACIOUS   landing pages, marketing, reading, onboarding
           32-48px between sections, generous line-height, lots of air
COMFORTABLE dashboards, settings, most application UI
           16-24px between groups, 1.5 line-height
COMPACT    data tables, admin, IDE-like tools, trading
           8px between rows, 32px row height, tight but not cramped

// THE FAILURE MODE
//   one density for everything. A data table with 48px rows wastes
//   the screen and forces scrolling. A form with 12px rows is
//   unreadable and mis-clickable.
//
//   Set density per context. CSS makes this cheap with a data
//   attribute on a container:
.table[data-density="compact"] td { padding-block: 6px; }
.table td { padding-block: 12px; }

// TOUCH TARGETS
//   44 x 44 CSS pixels is the accepted minimum for anything tappable.
//   This is a hard floor on a phone, and a sensible floor on desktop
//   too. A 24px icon button needs padding, not a smaller hit area:
.icon-btn { width: 44px; height: 44px; display: grid; place-items: center; }
.icon-btn svg { width: 20px; height: 20px; }   // small icon, big target</code></pre></div>
<h4 id="ch4-5-space">Whitespace as a tool, on a scale</h4>
<p>Whitespace does four jobs — separate, group, pad and breathe — and the values are part of a scale, not a judgement call at each instance. The 8-point scale covers it: 4 for micro gaps inside a button, 8 between a label and its control, 16 inside a card, 24 between cards, up to 96 for hero breathing room. The amateur tell is 13 px here and 11 px there: nothing is wrong individually and the whole thing feels accidental. Scale up and down, never halfway.</p>
<div class="codeWrap"><pre><code>// whitespace is not leftover space. it is the element that groups,
// separates and prioritises. It is the cheapest and most powerful
// tool in a design system.

// SPACE DOES FOUR JOBS
//   1. SEPARATE two unrelated things        24-32px
//   2. GROUP things that belong together   8-16px
//   3. PAD a container's contents          16-24px
//   4. BREATHE at the top of a section      48-64px

// THE INCONSISTENCY THAT MAKES A DESIGN LOOK AMATEUR
//   13px here, 16px there, 11px somewhere else. Nothing is wrong
//   individually and the whole thing feels accidental.
//   the fix is a scale, not a judgement call at each instance.

// A WORKING SCALE (8px base)
  4   micro: icon-to-label, inside a button
  8   tight: label to its control, chips
  16  base:  inside a card, between form fields
  24  group: between cards, between paragraphs
  32  section: between groups within a section
  48  block:  between sections
  64  major:  around major page bands
  96  hero:   above-the-fold breathing room

// THE INCREMENT RULE
//   scale values up, never down. if 24px is too much, use 16px.
//   if 16px is not enough, use 32px. Half-steps produce the noise
//   above, and no design in the history of design has ever needed
//   13px because of a real requirement.

// IF YOUR CONTENT DEMANDS IRREGULAR SPACING
//   a case study with images of different heights may need optical
//   adjustments. Use a small set of overrides (24, 28, 32) rather
//   than arbitrary values, and document them.</code></pre></div>

<section class="chapter">
<h2 id="ch5" data-toc>5 ▸ Colour, Typography and Imagery</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Three visual systems carry the look of a product: colour, type and imagery. Most colour problems are role problems, not "which blue" problems; most typography quality is a spec, not a taste; and imagery has rules of its own. This chapter folds the original colour and typography chapters together and adds the imagery rules that tie them to the interface.</p>

<h3 id="ch5-1" data-toc>5.1 Colour is a system, not a palette</h3>
<p class="topic-desc">A palette is what you picked. A system is what each colour does. The shift in practice is from deciding per component ("use #3B82F6 for the button") to deciding per role ("buttons use the primary role") — the first requires a decision every time, the second never does.</p>
<h4 id="ch5-1-why">Palette versus system</h4>
<p>A design with forty hex values has a palette and no system: adding one more button means picking one more hex, and nothing guarantees the new button matches the old one. A system answers, for each job, which colour and why — then any new component picks from the roles and consistency is automatic.</p>
<div class="codeWrap"><pre><code>// A PALETTE is what you picked. A SYSTEM is what each colour DOES.
//
//   A design with 40 hex values in it has a palette and no system.
//   Adding one more button means picking one more hex value, and
//   nothing guarantees the new button matches the old one.
//
//   A system answers: for this job, which colour, and why.
//   Then any new component picks from the roles, and consistency
//   is automatic.

// the shift in practice
//   "use #3B82F6 for the button"      a decision about a component
//   "buttons use the primary role"     a decision about the system
//   the first requires a decision each time. the second does not.</code></pre></div>
<h4 id="ch5-1-roles">The roles a colour can play</h4>
<p>Every colour in a mature interface has one of these jobs, defined once. Surfaces are the layers things sit on; content roles are three text weights plus on-accent text, which contrasts with its button, not with the page; borders, accent and status complete the set. The rule that prevents most disasters: you have one accent colour and a separate set of four status colours — if your accent is blue and your info is blue, a blue badge is ambiguous.</p>
<div class="codeWrap"><pre><code>// SURFACES - the layers things sit on
  surface/base        the page background
  surface/raised      a card, a panel: one step lighter
  surface/sunken      a well, a code block, a disabled field
  surface/overlay     a modal, a popover: above raised, with a scrim

// CONTENT - text and icons. three weights, no more.
  content/primary     headings and body text
  content/secondary   supporting text, labels
  content/disabled    non-interactive text
  content/on-primary  text ON a primary button. a separate role,
                      because it must contrast with the button, not
                      with the page.

// BORDERS
  border/subtle       dividers, table rules
  border/default      input outlines
  border/strong       focused or emphasised edges

// ACCENT - brand and state
  accent/primary      the brand action colour. ONE hue.
  accent/hover        its hover state
  accent/subtle-bg    a tinted background for selected rows and tags

// STATUS - these four are not brand colours and must never be swapped
  status/success      green
  status/warning      amber
  status/error        red
  status/info         blue

// THE RULE THAT PREVENTS MOST DISASTER
//   you have ONE accent colour, and a separate set of four status
//   colours. If your accent is blue and your info is blue, a blue
//   badge is ambiguous: is it your brand or is it informational?
//   Keep the accent visually distinct from the status set, or accept
//   that status always wins and never uses the accent hue.</code></pre></div>
<h4 id="ch5-1-ramp">Building a ramp that stays even</h4>
<p>A ramp is 50 to 950 following the Tailwind convention, and the steps are perceptually even so 500 and 600 read as the same colour at different intensities. HSL's lightness is not perceptual — equal L values look very different across hues — so build with HSL or OKLCH and store the result. OKLCH has perceived-uniform light steps, which is what makes a real 5% step rather than a guess.</p>
<div class="codeWrap"><pre><code>// a ramp is 50-950, following the Tailwind convention. it is not
// arbitrary: the steps are perceptually even, so 500 and 600 read as
// the same colour at different intensities.

  50    lightest: tinted backgrounds, dark-mode surfaces
  100   very light backgrounds
  200   disabled borders, subtle dividers
  300   placeholder text on light, disabled icons
  400   disabled content, decorative borders
  500   THE BASE. solid fills on light backgrounds.
  600   hover for a 500 fill. solid fills on dark backgrounds.
  700   text on light backgrounds, active states
  800   hover for a 600 fill
  900   headings on light backgrounds
  950   darkest: dark-mode text

// WHY EVEN STEPS MATTER
//   "brand blue" as a single hex value has to be darkened by hand for
//   hover and lightened for a subtle background, and each of those
//   hand-adjustments drifts. A ramp forces the relationships.

// HSL, and when it is the right tool
//   HSL is intuitive: hue (what colour), saturation (how vivid),
//   lightness (how light).
//   HSL's lightness is NOT perceptual. hsl(210 90% 50%) and
//   hsl(90 90% 50%) have the same L but very different perceived
//   lightness, because yellow is inherently lighter than blue.
//
//   so: HSL to build a ramp by hand, then convert to hex or OKLCH and
//   store THAT. Do not compute hover states with HSL arithmetic in
//   production code; the results will be uneven across hues.

// OKLCH, and why it is the better modern option
//   OKLab is perceptually uniform: equal steps in L look equal to the
//   eye, across every hue.
oklch(0.7 0.15 250)      lightness chroma hue
// L  0 (black) to 1 (white)
// C  0 (grey) to about 0.37 (most vivid hues)
// H  0-360 degrees, same as a colour wheel
// with OKLCH, "5% lighter" looks 5% lighter in yellow and in blue.
// the ramp comes out even by construction.
--brand-500: oklch(0.62 0.19 255);
--brand-600: oklch(0.55 0.19 255);   /* a real 5% step, not a guess */</code></pre></div>
<h4 id="ch5-1-naming">Naming by role, not by hue</h4>
<p>This is the single most important decision in a colour system, and every system gets it wrong initially. Naming by hue ("blue-500") bakes a brand choice into every component and makes re-theming a codebase search; naming by role ("color-accent") makes it a token swap. The three-layer pattern gives you both: primitives at the bottom (never used directly), semantic roles in the middle (what components consume), and component tokens only where a real exception exists.</p>
<div class="codeWrap"><pre><code>// THIS IS THE SINGLE MOST IMPORTANT DECISION IN A COLOUR SYSTEM
// and it is one every design system gets wrong initially.

BAD
  --blue-500: #3b82f6;
  --gray-100: #f3f4f6;
  .button-primary { background: var(--blue-500); }
  .button-secondary { background: var(--gray-100); }
  // now the brand changes and you are hunting 200 usages

GOOD
  --color-bg: #ffffff;
  --color-surface: #f9fafb;
  --color-text: #0f172a;
  --color-text-muted: #64748b;
  --color-accent: #3b82f6;
  --color-accent-hover: #2563eb;
  --color-border: #e2e8f0;
  .button-primary { background: var(--color-accent); }

// WHY IT IS BETTER, CONCRETELY
//   1. re-theming is a token swap, not a codebase search
//   2. a component cannot misuse a role. If .button-danger uses
//      --color-accent, that is a token change.
//   3. dark mode is a second token file, not a second stylesheet
//   4. roles survive a brand change, hex values do not

// THE THREE-LAYER PATTERN, which is how you get both
//   layer 1  PRIMITIVES: --blue-500, --slate-100. never used directly
//   layer 2  SEMANTIC:   --color-accent, --color-text-muted
//   layer 3  COMPONENT:  --button-bg, --input-border. only if a
//                          component genuinely needs an exception
// components consume layer 2. Primitives are for the token file only.</code></pre></div>

<h3 id="ch5-2" data-toc>5.2 Contrast, dark mode and colour vision</h3>
<p class="topic-desc">Three constraints turn a palette into an accessible system: ratios that must hold in every pair and state, a dark mode that is designed rather than inverted, and never encoding meaning in hue alone. All three are checkable.</p>
<h4 id="ch5-2-contrast">Contrast, computed not estimated</h4>
<p>Your eyes are bad at contrast and your monitor is calibrated differently from your users', so compute it. The ratios are 4.5:1 for body text, 3:1 for large text and UI boundaries, 7:1 for AAA. The failures rank predictably: muted text on tinted backgrounds, placeholder text (browsers render it near 54% opacity), disabled text, icon-only indicators, and text over images. Run the check over every token pair in both themes, in every state, at build time.</p>
<div class="codeWrap"><pre><code>// the ratios that matter (WCAG 2.2)
  4.5:1   body text under 18.66px bold / 24px regular
  3:1     large text at those sizes
  3:1     UI component boundaries, icons that carry meaning
  7:1     AAA for body text

// compute it, never estimate it. your eyes are bad at this and your
// monitor is calibrated differently from your user's.
function contrast(hex1: string, hex2: string): number {
  const L = (hex: string) =&gt; {
    const [r, g, b] = [1, 3, 5].map((i) =&gt; parseInt(hex.slice(i, i + 2), 16) / 255)
      .map((c) =&gt; (c &lt;= 0.03928 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4));
    return 0.2126 * r + 0.7152 * g + 0.0722 * b;
  };
  const a = L(hex1), b = L(hex2);
  return (Math.max(a, b) + 0.05) / (Math.min(a, b) + 0.05);
}
contrast('#64748b', '#ffffff');   // 4.76:1  passes for body text
contrast('#94a3b8', '#ffffff');   // 2.56:1  FAILS. still looks "grey text".

// WHERE CONTRAST FAILS, RANKED BY HOW OFTEN I SEE IT
//   1. MUTED TEXT ON TINTED BACKGROUNDS. light grey on a grey card is
//      usually ~2:1. The card background is not white, so you must
//      check against the card, not the page.
//   2. PLACEHOLDER TEXT. browsers render it at ~54% opacity by
//      default, which lands most designs below 4.5:1. Set it
//      explicitly and often it needs to be darker than you expect.
//   3. DISABLED TEXT. WCAG exempts disabled controls, but users still
//      need to read them. 3:1 is a reasonable floor.
//   4. ICONS WITHOUT LABELS. An icon that is the only way to do
//      something needs 3:1 as a non-text contrast requirement.
//   5. TEXT OVER IMAGES. You cannot check a static ratio; you need a
//      scrim or a gradient.

// CHECK ALL OF THEM
//   a contrast checker must run over EVERY token pair, in BOTH
//   themes, in EVERY state including hover and disabled. A single
//   automated pass at build time catches what a manual review misses
//   and what a designer will not catch at all.</code></pre></div>
<div class="tip"><p>Add a contrast check to your build. A script that loads the token file, tests every declared foreground/background pair, and fails CI on a violation. It takes an hour to write and it will catch a contrast regression in a component someone added at 6pm, which no review process reliably does.</p></div>
<h4 id="ch5-2-dark">Dark mode is a re-design, not an inversion</h4>
<p>The common failure is inverting the light theme: pure white on pure black is harsh, and pure black surfaces make elevation invisible. Four things break in a naive inversion. Elevation inverts (raised surfaces must stay lighter than the page, even in dark). Shadows stop working (depth comes from surface lightness and a subtle light border instead). Saturation blooms (the calm green on white looks neon on near-black — reduce saturation 10–20% and use lighter ramp steps). And pure black and white are both wrong at the extremes. Write a second token file, deliberately; the mapping is not 1:1 and a transform cannot know your intent.</p>
<div class="codeWrap"><pre><code>// the common failure: invert the light theme. this produces
//   pure white text on pure black, which is harsh, and pure black
//   surfaces, which makes elevation impossible to see.

// FOUR THINGS THAT BREAK IN A NAIVE INVERSION

// 1. ELEVATION INVERTS
//   light mode: raised surfaces are LIGHTER than the page, so they
//   appear to come forward.
//   dark mode: raised surfaces must be LIGHTER too, because
//   "closer to the light source" is how we read depth. But the page
//   is already dark, so "lighter" means a lighter dark.
body      { background: oklch(0.16 0.01 250); }   /* not black */
surface   { background: oklch(0.20 0.012 250); }  /* raised: lighter */
overlay   { background: oklch(0.24 0.014 250); }  /* above raised */
scrim     { background: rgb(0 0 0 / 0.6); }      /* darkens, not lightens */

// 2. SHADOWS STOP WORKING
//   there is nothing to cast a shadow onto when everything is dark.
//   depth comes from surface lightness and, optionally, a subtle
//   1px light border on raised surfaces.
.card { box-shadow: none; border: 1px solid var(--color-border); }
/* in dark mode, a light border reads as an edge. that is the
   substitute for the shadow you cannot see */

// 3. SATURATION BLOOMS
//   a colour that looks calm on white looks neon on near-black.
//   the same hex is a different colour perceptually. reduce
//   saturation in dark mode, typically by 10-20%, and use lighter
//   steps of the same ramp:
//   light:  blue-600   dark:  blue-400     (lighter, less saturated)

// 4. PURE BLACK AND PURE WHITE ARE WRONG
//   #000 on #fff is 21:1, which is glare. #fff on #000 is 15:1 in
//   the other direction and is also harsh.
//   cap both ends: text around 87-92% lightness, backgrounds 6-12%.

// THE PRACTICAL RULE
//   do not derive dark mode by transforming light mode in code.
//   write a second token file, deliberately. The mapping is not
//   1:1 and the transform cannot know your intent.
:root { --color-bg: #fff; --color-accent: oklch(0.55 0.19 255); }
[data-theme="dark"] { --color-bg: oklch(0.16 0.01 250); --color-accent: oklch(0.72 0.14 255); }</code></pre></div>
<h4 id="ch5-2-cvd">Colour vision deficiency: never hue alone</h4>
<p>Around 1 in 12 men and 1 in 200 women have some form of colour vision deficiency, and red-green is the common one. Red equals error and green equals success with no other difference is invisible to 8% of men. The rule is colour plus something else — an icon, a word, a shape, a position or a pattern. Charts are the hardest case: no rainbows, sequential ramps for ordered data, direct labels on the series, and a greyscale print as the test that survives everything.</p>
<div class="codeWrap"><pre><code>// WHAT YOU CANNOT DO
//   red = error, green = success, with no other difference. to a
//   deuteranope these are the same colour. 8% of men will see a
//   field validation state as neutral.

// WHAT YOU MUST DO: never encode meaning in hue alone
//   the rule is "colour plus something else". The something else
//   can be an icon, a word, a shape, a position or a pattern.

// status indicators, done properly
  error    red    + a warning triangle icon   + the word "Error"
  success  green  + a check icon              + the word "Saved"
  warning  amber  + an exclamation icon       + the word "Pending"

// form validation
  .field--error input { border-color: var(--status-error); }
  .field--error .error-msg::before { content: "!\00a0"; }  /* not colour alone */
  .field--error .error-msg { color: var(--status-error); }
// the red border, the icon and the message. remove the colour and it
// still works.

// CHARTS - the hardest case, because there is no text label
//   - do not use a rainbow. it is unreadable for CVD and bad for
//     greyscale printing
//   - use a sequential ramp for ordered data: light to dark of ONE hue
//   - use a small, CVD-safe categorical set for unordered data
//   - add direct labels on the lines or bars where possible. A legend
//     forces the reader to do arithmetic; a label does not.
//   - add patterns or marker shapes as a second channel:
//     solid line, dashed line, dotted line
//   - test by converting to greyscale. If the series merge, you need
//     labels or patterns.

// TESTING
//   - free browser extensions simulate each deficiency
//   - macOS and iOS have accessibility filters in display settings
//   - Windows has a colour filter setting
//   - most importantly: print it in greyscale. A chart that survives
//     greyscale survives everything.</code></pre></div>

<h3 id="ch5-3" data-toc>5.3 The type scale, line height and measure</h3>
<p class="topic-desc">Type is where most of a design's quality is visible and most of its accessibility lives. The specifics matter more than the taste, and the specs are knowable: a consistent scale, line height that scales inversely with size, and a measure in characters, not pixels.</p>
<h4 id="ch5-3-scale">Pick a base and a ratio, stop deciding per component</h4>
<p>A scale is a set of sizes with a consistent ratio. Sixteen pixels at a 1.25 ratio gives the minor-third set most sites ship; 1.333 is bolder and suits dashboards. The exact numbers matter less than the fact of a scale — 16/24/32 with consistent 1.5 leading reads as designed, while 15/22/31 reads as a Word document. Weights are part of the system: 400 body, 600 for sub-headings, 700 for the top level, and 300 only for large display type.</p>
<div class="codeWrap"><pre><code>// a scale is a set of sizes with a consistent ratio. pick a base and
// a ratio and stop deciding per component.

BASE 16px, RATIO 1.25 (minor third)
  xs    10.24   0.64rem   metadata, legal
  sm    12.80   0.80rem   helper text, captions
  base  16.00   1.00rem   body
  lg    20.00   1.25rem   lead paragraphs, h4
  xl    25.00   1.56rem   h3
  2xl   31.25   1.95rem   h2
  3xl   39.06   2.44rem   h1
  4xl   48.83   3.05rem   display

BASE 16px, RATIO 1.333 (perfect fourth) - bolder, good for dashboards
  sm    12      0.75rem
  base  16      1.00rem
  lg    21.3    1.33rem
  xl    28.4    1.78rem
  2xl   37.9    2.37rem
  3xl   50.6    3.16rem

// THE ROUNDED VERSION, which is what most systems actually ship
// because 1.333 at 16px is 21.3 and nobody types that
  12   14   16   20   24   32   40   48   64

// WHY A SCALE MATTERS MORE THAN THE EXACT NUMBERS
//   it makes the page feel systematic. 16/24/32 with consistent 1.5
//   line height reads as designed. 15/22/31 with inconsistent spacing
//   reads as a Word document. Nobody can name the difference; everybody
//   feels it.

// WEIGHT AND THE SHAPE OF A HIERARCHY
//   400 body, 600 h4/h5, 700 h1-h3 is a modern default.
//   300 only for very large display type, never for body.
//   800/900 for hero numbers, sparingly. A fully bold page has no
//   emphasis left to give.</code></pre></div>
<h4 id="ch5-3-leading">Line height is not a constant</h4>
<p>Line height scales inversely with size: large text needs less relative leading, small text needs more. A fixed 1.5 everywhere fails both ends — at 48 px it spreads the paragraph into disconnected lines, and at 12 px it crowds. Use unitless line-height (relative to the element's own size) so headings get correct leading automatically, never a fixed px value on a heading, which breaks the moment the font size changes. The heading rule that fixes most "headings feel wrong" reports: more space above a heading than below, because it belongs to what follows.</p>
<div class="codeWrap"><pre><code>// the rule
   large text needs LESS relative leading
   small text needs MORE

  size     line-height    notes
  12px     1.6            small text needs air to be legible
  14px     1.6
  16px     1.5            the workhorse. 1.5-1.7 is the sweet spot
  20px     1.5
  24px     1.4
  32px     1.25           headings want tightness
  48px     1.1
  64px     1.05

// 1.5 with a 16px font is 24px of leading: 16px of glyphs and 8px of
// space, 4px each side. At 48px with 1.5 you get 72px leading, so 24px
// between lines, and the paragraph falls apart into disconnected
// lines. That is why big headings look wrong at a fixed 1.5.

// the summary form: unitless line-height
body    { font-size: 1rem; line-height: 1.5; }     /* 24px */
h1      { font-size: 2.5rem; line-height: 1.15; }  /* 46px */
h2      { font-size: 2rem;   line-height: 1.2; }   /* 38px */
h3      { font-size: 1.5rem; line-height: 1.3; }
// unitless is relative to the element's own font-size, so a heading
// gets correct leading automatically. NEVER use a fixed px line-height
// on a heading: it breaks the moment someone changes the font size.

// LINE HEIGHT AND THE ELEMENT ABOVE
//   the space above a heading should be greater than the space below
//   it, because the heading belongs to what follows. 32px above,
//   16px below. This single rule fixes most "my headings feel wrong"
//   reports, and it is worth more than changing the font.</code></pre></div>
<h4 id="ch5-3-measure">Measure: line length in characters</h4>
<p>Body text reads best at 45 to 75 characters per line. The correct unit is <code>ch</code> — the width of a "0", proportional to the font — because it scales with the user's font size, which px and em-broken-widths do not. Wide containers without a max width on the prose are why a 1400 px page looks "cheap" for no other reason. Break the rule deliberately for sidebars (30–45 ch), table cells and labels; never wrap code.</p>
<div class="codeWrap"><pre><code>// measure is line length: how many characters sit on one line.
// the target is 45-75 characters for body text.

.prose {
  max-width: 65ch;        /* ch is the width of a "0", which is
                             proportional to the font. this is the
                             correct unit for line length, not px. */
}

/* or explicitly, for a two-column page */
.column { max-width: 680px; }

/* WHY ch AND NOT px OR em
   65ch scales with the user's font size. 65em would be 65 times the
   font size, which is absurd. 65px is 65px whatever the font, so a
   user at 200% zoom gets 130 characters per line and cannot read it. */

// WHEN TO BREAK THE RULE
//   - a sidebar or card: 30-45ch is fine
//   - a table cell: one or two lines, and that is acceptable
//   - a UI label: as long as the string needs
//   - a code block: horizontal scroll, never wrap. Wrapping code
//     changes its meaning.
//   - a form label: as long as it needs
//
// full-width body text at 1400px is roughly 180 characters per line.
// That is genuinely hard to read, and it is why a wide container with
// no max-width on the prose looks "cheap" even when nothing else is
// wrong with it.

// READING WIDTH ON MOBILE
//   a phone at 390px with 16px type gives about 45 characters, which
//   is at the bottom of the range. Raising body text to 17-18px on
//   mobile improves it, and is worth doing.</code></pre></div>
<div class="warn"><p>The fixed-px line height is the classic typographic bug: a heading set to <code>line-height: 32px</code> behaves fine until the font size changes, then the leading goes from tight to broken. If a line-height has px on it, it is a layout value, not a typographic one — and typographic values should always be unitless.</p></div>

<h3 id="ch5-4" data-toc>5.4 Pairing families, web fonts and optical detail</h3>
<p class="topic-desc">Two families is the practical maximum, web fonts are a performance decision, and the optical adjustments — letter-spacing, tabular numerals, tiny nudges — are where professional type is made, not chosen.</p>
<h4 id="ch5-4-families">Choice of families, and the system stack</h4>
<p>Three realistic categories cover almost everything: a neutral sans for everything (the system stack costs zero bytes and renders natively); a display face for headings with a neutral body where the two differ in more than weight; and a serif body with a sans UI for long-form work. Mono is a third voice for code and data only. The common failure: same family at different weights passed off as a pairing, which reads as accidental.</p>
<div class="codeWrap"><pre><code>// two families is the practical maximum. three is a curiosity.

// CATEGORY A: a neutral sans for everything
//   Inter, system-ui, -apple-system, "Segoe UI", Roboto, Helvetica
//   + the point: the system stack costs zero bytes and renders
//     natively on every platform
body { font-family: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif; }
//   "font-family: Inter" alone will make macOS and Windows look
//   different, because neither ships Inter. Either bundle it or use
//   the stack. Half-and-half is the worst outcome.

// CATEGORY B: display for headings, neutral for body
//   display   Playfair Display, Fraunces, Source Serif 4, a distinctive sans
//   body      Inter, Source Sans 3, system-ui
//   the rule for success: the two must differ in more than weight.
//   same-family at different weights is a common failure and looks
//   accidental.

// CATEGORY C: serif for body, sans for UI
//   body      Source Serif 4, Literata, Georgia, Charter
//   ui        Inter, system-ui
//   best for: long-form, articles, documentation
//   the risk: serif at 14px in a data table is unreadable. Use the
//   sans for anything dense.

// CATEGORY D: mono as a third voice
//   mono      JetBrains Mono, ui-monospace, SFMono-Regular, Menlo
//   use for: code, ids, versions, anything that is literally data
//   do not use for body. And keep it narrow: a mono used for
//   everything reads as a terminal, not a product.

// MONOSPACE
//   for code and identifiers, not as a design choice
/* code, kbd, samp, pre */
code, kbd, samp, pre { font-family: var(--font-mono); font-size: 0.9em; }
// 0.9em because monospace glyphs are visually larger than the same
// point size in a proportional face. At 1em code looks too big.</code></pre></div>
<h4 id="ch5-4-loading">Web fonts without the cost</h4>
<p>A web font is a performance decision as much as a design one. A typical family of four weights and two styles is eight files and 400 KB+ of WOFF2 — on a phone, several seconds of blocking text. Subset to the glyphs the interface actually uses (15–25 KB instead of 200 KB), limit weights to 400 and 700 (or one variable font), preload the critical one, and use <code>font-display: swap</code> with a metric-matched fallback so the swap does not jump the layout.</p>
<div class="codeWrap"><pre><code>// the cost of a font
//   a typical family: 4 weights, 2 styles = 8 files, 400KB+ of WOFF2
//   full Latin + Cyrillic + Greek can exceed 1MB
//   on a phone that is several seconds of blocking text

// 1. SUBSET. Most interfaces use 60-80 Latin glyphs. A subset of
//    exactly those is 15-25KB instead of 200KB.
//    do it in the build, per-language: a Japanese site needs a
//    different strategy from an English one.

// 2. LIMIT WEIGHTS. Two is usually enough: 400 and 700.
//    Every weight you add is a file and a request. If your design
//    needs 300/400/500/600/700/800, it needs fewer weights, not more.
//    A variable font is ONE file covering the whole range - the right
//    answer for a modern build.

// 3. PRELOAD THE CRITICAL ONE
//    the weight used above the fold, in the subset actually needed
&lt;link rel="preload" href="/fonts/inter-400.woff2" as="font"
      type="font/woff2" crossorigin&gt;

// 4. USE font-display SWAP, not BLOCK
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-400.woff2') format('woff2');
  font-weight: 400;
  font-display: swap;      /* show fallback immediately, swap in when
                              ready. BLOCK hides text for up to 3s
                              and is the cause of most "the site just
                              sits there" reports */
  size-adjust: 100%;       /* metric override, see below */
}

// 5. MATCH THE FALLBACK, or the swap will jump
@font-face {
  font-family: 'Inter Fallback';
  src: local('Arial');
  size-adjust: 107%;      /* scale the fallback to Inter's metrics */
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}
/* this makes the fallback occupy the same space as Inter, so the swap
   is nearly invisible. It is the single best thing you can do for
   perceived performance */

// 6. SUBSET BY LANGUAGE using unicode-range, so the browser downloads
//    only what the page needs
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-cyrillic.woff2') format('woff2');
  unicode-range: U+0301, U+0400-045F, U+0490-0491, U+04B0-04B1, U+2116;
}</code></pre></div>
<h4 id="ch5-4-optical">Optical adjustments and fluid type</h4>
<p>Letters are not rectangles: large display type tightens (minus 0.02 to 0.03 em), small caps open up (0.06 to 0.12 em), and all caps below 16 px is unreadable on purpose. Weight for small UI text is 500, not 400; numerals in tables are <code>tabular-nums</code> so columns line up. Fluid type is a marketing-page tool: <code>clamp()</code> with fixed bounds beats raw vw scaling, but three or four fixed steps with breakpoints is the more honest choice for an application.</p>
<div class="codeWrap"><pre><code>// LETTER-SPACING, by role
   DISPLAY  32px+     -0.02em to -0.03em   tighten; large type sets loose
   HEADING  24-31px   -0.015em
   BODY     16-20px    0                    leave it alone
   SMALL    14px      0                     leave it alone
   CAPS / TRACKING   0.06em to 0.12em      open it up; caps have no
                                           ascender/descender help
   ALL CAPS &lt; 16px    do not use            unreadable

h1 { font-size: 3rem; letter-spacing: -0.025em; }
.eyebrow { text-transform: uppercase; letter-spacing: 0.1em; font-size: 0.75rem; }

// FONT WEIGHT FOR SMALL TEXT
//   400 is too light below 16px. Use 500 for small UI text.
/* .label { font-size: 0.75rem; font-weight: 500; } */

// OPTICAL ALIGNMENT
//   text inside a button, badge or pill is rarely optically centred,
//   because glyphs have uneven side bearings. Quote marks, commas and
//   italics stick out. This is why a carefully centred label can look
//   off by a pixel. Nudge it. Optical beats geometric.

// NUMERALS IN TABLES
   font-variant-numeric: tabular-nums;   /* same width per digit, so
                                            columns line up */
   always for anything numeric: tables, prices, counters, timers
   never for running prose

// FLUID TYPE, when you must
h1 {
  /* min | preferred using vw | max */
  font-size: clamp(1.75rem, 1.1rem + 3.2vw, 3.5rem);
}
// 280px viewport -> 1.75rem (28px)
// 1280px viewport -> about 2.9rem
// 1920px viewport -> 3.5rem (56px), capped

// THE CRITIQUE, and it is fair
//   pure vw scaling is bad on its own: a 360px phone and a 320px phone
//   get different sizes, so the layout is unpredictable, and a 4K
//   monitor gets enormous text unless capped. clamp() fixes both.

// PREFER THIS INSTEAD for most designs
//   three or four fixed sizes with a breakpoint between them.
//   Predictable, and the designer can see exactly what ships.
//   Fluid is for a marketing page where the payoff is a continuous
//   feel. For an application, fixed steps are more honest.

// AVOID clamp() ON LINE HEIGHT
//   line-height: 1.2 is fine. A fluid line-height produces awkward
//   leading at the extremes. Set the ratio and let the size move.
//   But DO let space-around fluid, using the same clamp formula.</code></pre></div>
<h4 id="ch5-4-readability">The readability checklist</h4>
<p>Run this against any text-heavy design before it ships. Every line is a check you can automate or measure, and the two that catch the most shipped defects are the 45–75 character measure at 200% zoom and the contrast check on the actual background — the tinted card, not the page.</p>
<div class="codeWrap"><pre><code>// run this against any text-heavy design

[ ] body text is at least 16px, 18px is better for long-form
[ ] line length is 45-75 characters (measure with a ch-based max-width)
[ ] line height is 1.5 for body, lower for headings
[ ] body text meets 4.5:1 against its ACTUAL background
    (check tinted cards, not just the page)
[ ] no more than two type families, plus mono for code
[ ] weights limited to 400 and 700, plus 500 for small UI text
[ ] letter-spacing is 0 for body text
[ ] no all-caps below 16px
[ ] font-display: swap, with a metric-matched fallback
[ ] the font is subset, and total font payload is under 150KB
[ ] tabular-nums on any number in a column
[ ] headings have more space above than below
[ ] the type still works at 200% browser zoom
[ ] the type still works in forced-colours / high-contrast mode
[ ] italics work: a real italic face exists, or faked ones are avoided
[ ] line breaks never orphan a single word
    orphans: 2; widows: 2;  /* CSS, worth knowing about */</code></pre></div>

<h3 id="ch5-5" data-toc>5.5 Imagery and iconography</h3>
<p class="topic-desc">Images carry the emotional half of a design and icons carry a surprising amount of its function. Both have hard rules: vector versus raster decided by content, icon sets drawn on one grid with one voice, and alt text that is a real decision, not a form field.</p>
<h4 id="ch5-5-formats">SVG where it scales, WebP/AVIF where it photographs</h4>
<p>Format is decided by content, not preference. If the image is a shape that has to scale — logo, icon, chart — it is SVG, and SVG text stays selectable, translated and crisp. If it is a photograph, modern compressed formats (WebP, then AVIF) beat JPEG at the same quality. One rule above the rest: never let interface text ride inside a raster image — it is not selectable, not translatable, and invisible to screen readers and search engines.</p>
<div class="codeWrap"><pre><code>// raster vs vector, when each wins
FORMAT   WINS WHEN                    LOSES WHEN
SVG      logos, icons, charts,        photos, complex gradients,
         any shape that scales        fine texture; huge path data
PNG      screenshots, flat art,       large photos (24-bit lossless
         transparency at any size     is heavy)
WebP     photos, 24-bit with alpha,   old engines, lossless edge cases
         30% smaller than JPEG
AVIF     photos at best compression,  encode cost, browser support
         HDR
JPEG     photos where size beats      alpha, sharp edges (artefacts)
         everything

// the rule: if it scales, SVG. if it is a photo, WebP or AVIF.
// never let marketing JPEGs carry interface text meant to be read
// (it is not selectable, not translated, not accessible).</code></pre></div>
<h4 id="ch5-5-icons">An icon set is one voice, drawn on one grid</h4>
<p>Icons read as one family when they share a viewBox, a stroke weight, and a corner treatment. A 24 by 24 grid with a 2 px safe area is the common thumbprint: square glyphs take 18 px, circular ones 20 px, so they look optically equal. Colour comes from <code>currentColor</code>, never baked into the path, so the icon inherits its label's colour and its contrast follows automatically.</p>
<div class="codeWrap"><pre><code>// an icon system thumbprint
grid        24x24 viewBox, 2px padding as the safe area
stroke      1.5-2px uniform; one weight per set
corners     consistent radius per shape
optical     circle glyphs 20px, square glyphs 18px, on the 24 box
colour      via currentColor so the icon follows the text colour

&nbsp;// a set drawn on one grid with one stroke weight reads as one voice.
// mix sources and the differences show in the corners and the curves.

// anatomy rules
- filled and stroked styles never mix within one set
- an icon used alone needs a tooltip or a text alternative (ch6)
- test at 16px for the smallest size it will ship at
- same glyph for one concept everywhere: one "settings" icon, not three</code></pre></div>
<h4 id="ch5-5-alt">Alt text is a design decision</h4>
<p>Every image gets an alt decision, and the decision is per type. Decorative images get an empty alt; informative images get the equivalent text ("quarterly revenue chart: Q3 up 12%"); functional images name the action; complex images get a short alt plus a link to the full data. Write alt as if reading it aloud: never "image of", never repeating the caption, never keyword-stuffing.</p>
<div class="codeWrap"><pre><code>// alt text policy per image type
decorative      alt=""                (empty, skipped by assistive tech)
informative     the equivalent text   "Quarterly revenue chart: Q3 up 12%"
functional      the action            "Export report as PDF"
complex         short alt + a link to a full table or description

// good and bad, side by side
BAD:  &lt;img src="chart-q3.png" alt="image of a chart"&gt;
GOOD: &lt;img src="chart-q3.png"
           alt="Quarterly revenue: Q3 up 12% to EUR 41k"&gt;

// alt is not a caption: the caption says what the reader sees,
// the alt says what the image means. if the meaning is already in
// the surrounding text, the image is decorative and alt can be empty.</code></pre></div>
<div class="tip"><p>Test an icon set by removing the colour: sixteen monochrome glyphs that still read as distinct shapes are a set; ones that blur together need labels. The greyscale test that catches contrast defects also catches ambiguous icons.</p></div>

<section class="chapter">
<h2 id="ch6" data-toc>6 ▸ Interaction Design and Components</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">A component is the states it can be in, not the picture of its default state. This chapter turns the design systems work of the earlier chapters into behaviour: states and focus, feedback and status, microinteractions and motion, the anatomy of forms, and the navigation patterns that hold it all together.</p>

<h3 id="ch6-1" data-toc>6.1 States: designing behaviour, not pictures</h3>
<p class="topic-desc">Every interactive component has a family of states — default, hover, focus, active, disabled, busy — and each is a design decision with its own colours and contrast to pass. The component spec is the list of those states and what each one does.</p>
<h4 id="ch6-1-states">The state map comes before the artwork</h4>
<p>Write the states down before styling anything, one line each, with the background, text and border token per state. The states that get skipped in the map are the ones that fail in production: the disabled state that passes nothing along, the busy state that offers no feedback. The map below is the shape every interactive component should fill in, and the CSS shows the tokens doing the work.</p>
<div class="codeWrap"><pre><code>// component state map — fill this in before styling the component
STATE    TRIGGER                BACKGROUND       TEXT            BORDER
default  rendered               --accent         --on-accent     --
hover    pointer over           --accent-hover   --on-accent     --
active   pointer down           --accent-deep    --on-accent     --
focus    keyboard arrives       --accent         --on-accent     2px ring,
                                 (visible, see next section)      2px offset
disabled not available          --surface-sunken --text-disabled --
busy     work in progress       --accent         (spinner)       --

// the same map as CSS
.btn {
  background: var(--accent);
  color: var(--on-accent);
  min-height: 44px;
}
.btn:hover  { background: var(--accent-hover); }
.btn:active { transform: translateY(1px); }
.btn:focus-visible {
  outline: 2px solid var(--focus-ring);
  outline-offset: 2px;
}
.btn:disabled {
  background: var(--surface-sunken);
  color: var(--text-disabled);
  cursor: not-allowed;
}
.btn[aria-busy="true"] { cursor: progress; }</code></pre></div>
<h4 id="ch6-1-focus">Focus is a requirement, not decoration</h4>
<p>A visible focus indicator is WCAG 2.4.7, and for keyboard users it is the entire navigation system — they move by Tab and look for the ring. Never remove the outline without replacing it with something equally visible; the modern pattern is <code>:focus-visible</code>, which shows the ring only when the keyboard is in use and leaves mouse clicks clean. Pick one focus style — a 2 px ring with 2 px offset is the common one — and apply it consistently, because a ring that appears in half the components is worse than none.</p>
<div class="codeWrap"><pre><code>// visible focus, consistent across every interactive element
a:focus-visible, button:focus-visible,
input:focus-visible, select:focus-visible, textarea:focus-visible {
  outline: 2px solid var(--focus-ring);
  outline-offset: 2px;
  border-radius: var(--radius);   /* keep the ring's corners honest */
}

/* touch screens: enlarge the whole target, not just the ring */
@media (pointer: coarse) {
  button, a.btn { min-height: 48px; min-width: 48px; }
}

// rules
- never `outline: none` without a replacement focus style
- the ring must clear 3:1 against both the element and the page
- focus order follows visual order (ch8-1 has the keyboard audit)
- a modal traps focus, but must also offer an escape (Esc, and a close)</code></pre></div>
<div class="warn"><p>The "remove the outline for a cleaner look" pattern ships a lot, and it is the fastest way to make a product unusable by keyboard. If a stakeholder asks why the ring is there, the answer is WCAG 2.4.7 — and the fix, if the ring looks wrong, is to style it better, never to remove it.</p></div>

<h3 id="ch6-2" data-toc>6.2 Feedback and system status</h3>
<p class="topic-desc">Every action needs a visible result, and every system that takes time needs to say so. Feedback is a component: toasts and live regions for events, inline messaging for errors, and progress for anything slower than a blink.</p>
<h4 id="ch6-2-live">Announcing changes, politely and correctly</h4>
<p>The browser announces dynamic content to screen readers through live regions, and the choice of <code>polite</code> versus <code>assertive</code> is a design decision: a successful save can wait politely; a payment failure that must interrupt gets <code>role="alert"</code>. The markup is nearly invisible — a container with the attributes — and the JS is one assignment. The content rule matters as much: announce what changed and what to do next, not the raw technical detail.</p>
<div class="codeWrap"><pre><code>&lt;!-- transient success: polite, non-interrupting --&gt;
&lt;div class="toast" role="status" aria-live="polite"&gt;Project saved.&lt;/div&gt;

&lt;!-- must interrupt: assertive --&gt;
&lt;div class="toast toast--error" role="alert"&gt;
  Payment failed — your card was not charged. Try again.
&lt;/div&gt;

// the JS is one assignment, because the region already exists
function announce(message, assertive) {
  const box = document.getElementById(assertive ? "alertBox" : "statusBox");
  box.textContent = message;   // textContent, never innerHTML
}

// rules
- one live region per role, present in the DOM from the start
- "Saved", "Deleted", "2 items filtered" — announce the result and state
- a toast is transient for sighted users; the live region is what
  screen readers hear, so it must say the same thing
- never put focus-stealing dialogs behind a polite region</code></pre></div>
<h4 id="ch6-2-inline">Inline validation: the error lives with the field</h4>
<p>Validation errors belong next to the field they describe, announced by that field, and they must survive the extra information the user already typed. The pattern is three linked nodes: the hint (optional), the error (hidden until it fires), and the association via <code>aria-describedby</code>. The red border is decoration; the text is the message, and the message never relies on colour alone (ch5-2).</p>
<div class="codeWrap"><pre><code>&lt;label for="email"&gt;Work email&lt;/label&gt;
&lt;input id="email" name="email" type="email"
       aria-describedby="email-hint email-error"&gt;
&lt;p id="email-hint" class="hint"&gt;We only send receipts here.&lt;/p&gt;
&lt;p id="email-error" class="error" role="alert" hidden&gt;Enter a valid email.&lt;/p&gt;

// rules
- the error text names the problem and the fix ("Enter a valid email,
  like name@company.com")
- the field stays labelled and the hint stays available after the error
- validate on blur or submit, never on every keystroke for emails
- an error summary at the top of the form links to each failing field
  for long forms (WCAG 3.3.1, 3.3.3)</code></pre></div>

<h3 id="ch6-3" data-toc>6.3 Microinteractions and motion</h3>
<p class="topic-desc">Motion communicates state change faster than colour or text, and it is the easiest part of a design to get both pleasing and wrong. The specs are small: durations by role, one easing, and an explicit off switch for users who ask for one.</p>
<h4 id="ch6-3-timing">Durations, easing and what not to move</h4>
<p>Duration is role, not taste: 100–200 ms for feedback (button presses, toggles), 200–500 ms for movement (panels, menus), and 500 ms only for big reveals — anything longer reads as broken. Pick one easing and use it everywhere; <code>ease-out</code> for entrances, <code>ease-in-out</code> for loops, and never <code>linear</code> for UI, which looks mechanical. The first law of motion design: animate position, opacity and transform — the properties the compositor handles cheaply — and never layout-triggering properties like width or height on the main thread.</p>
<div class="codeWrap"><pre><code>/* durations: 100-200ms feedback, 200-500ms movement, 500ms+ is a reveal */
.btn:active { transition: transform 100ms ease-out; }

.panel {
  transition:
    transform 250ms cubic-bezier(0.2, 0, 0, 1),   /* entrances ease out */
    opacity   250ms ease;
}

/* what NOT to animate: layout properties that force reflow */
/* width, height, margin, top — animate transform/opacity instead */
.panel {
  transform: translateY(-8px);   /* instead of animating margin-top */
}

// microinteraction checklist
[ ] the animation answers "what state am I now in?"
[ ] one easing per product, listed in the motion tokens
[ ] feedback under 200ms; nothing decorative over 500ms
[ ] motion never the only channel for a state change (ch5-2)</code></pre></div>
<h4 id="ch6-3-reduce">Respect the user's motion setting</h4>
<p>Every product ships to people who have "reduce motion" on in the OS — some because vestibular disorders make parallax and large slides genuinely sickening. The response is a media query that collapses animation durations to near zero without removing the state change itself: the swap still happens, it just stops sliding. The design rule underneath is that motion is decoration layered on a state change that works without it.</p>
<div class="codeWrap"><pre><code>/* the standard off switch: state changes stay, motion stops */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

// the design rule
//   a state change must survive motion being off:
//   a tab switch still selects; a dialog still opens; an error still
//   appears. If the transition was the only signal, the design is
//   wrong for everyone, not just for reduced-motion users.
//
// test it: turn on the OS setting (or the browser emulation) and
// walk the primary flows. Every one must still complete.</code></pre></div>

<h3 id="ch6-4" data-toc>6.4 Forms and inputs</h3>
<p class="topic-desc">Forms are where UX is won and lost: the most-tested, most-abandoned component class in the product. The anatomy is small and fixed — label, control, hint, error — and the browser itself cooperates if the markup is honest.</p>
<h4 id="ch6-4-structure">Label, control, hint, error</h4>
<p>A form field is four coordinated nodes: a visible label bound to its control (an invisible placeholder is not a label — it disappears on input and is a placeholder for everyone, a problem for autofill and translation), the control with the right <code>type</code>, an optional hint, and an error (ch6-2). The label belongs above the field on narrow viewports and can sit beside it on wide ones — never inside where typing hides it.</p>
<div class="codeWrap"><pre><code>&lt;form action="/signup" method="post" novalidate&gt;
  &lt;div class="field"&gt;
    &lt;label for="name"&gt;Full name&lt;/label&gt;
    &lt;input id="name" name="name" type="text" autocomplete="name" required&gt;
  &lt;/div&gt;
  &lt;div class="field"&gt;
    &lt;label for="card"&gt;Card number&lt;/label&gt;
    &lt;input id="card" name="card" type="text" inputmode="numeric"
           autocomplete="cc-number"&gt;
  &lt;/div&gt;
  &lt;button type="submit"&gt;Start free trial&lt;/button&gt;
&lt;/form&gt;

// field rules
- placeholder is never the label; a label that vanishes on input
  fails autofill, translation and memory
- the right type/inputmode gives the right mobile keyboard:
  email, tel, url, number, search, inputmode="numeric"
- error text and hints are wired with aria-describedby (ch6-2)
- disabled fields are avoided entirely — a read-only value with an
  explanation beats a disabled mystery</code></pre></div>
<h4 id="ch6-4-autofill">The browser's form brain</h4>
<p>Browsers autofill forms they recognise, and recognition is driven by <code>autocomplete</code> tokens. The correct token buys free behaviour — the phone keyboard, the saved-password flow, the address book — and the omission of it makes your form the one users type out, and then abandon. The token list is the smallest useful subset; the full registry is in the HTML spec's "autofill field" section.</p>
<div class="codeWrap"><pre><code>// autocomplete tokens the browser understands (subset)
name, given-name, family-name, email, tel, url,
organization, street-address, address-level2, postal-code, country,
cc-name, cc-number, cc-exp, cc-csc,
username, current-password, new-password

// the pattern
&lt;input id="password" name="password" type="password"
       autocomplete="current-password"&gt;

// what correct tokens fix, without writing any code
- the right mobile keyboard (email keyboard for email, numeric for cards)
- the saved-password flow works, so users can actually log in
- address autofill works, so shipping forms stop dying at "country"
- password managers recognise the form and stop guessing</code></pre></div>
<div class="tip"><p>If a form has more than seven fields, consider a single-column layout — multi-column forms break the reading flow and double the perceived effort. And write the button in the user's language: "Start free trial" beats "Submit", and users who know what happens next are users who finish.</p></div>

<h3 id="ch6-5" data-toc>6.5 Navigation patterns</h3>
<p class="topic-desc">Tabs, breadcrumbs, pagination and load-more are each a contract between the UI and the user about how much structure is visible. The right pattern is chosen by task, not by habit, and each has accessibility wiring that is part of the design.</p>
<h4 id="ch6-5-tabs">Tabs with real semantics</h4>
<p>Tabs are for switching between views of the same data without leaving the page — they are not a substitute for pages, and they are not a way to hide content behind discovery. The accessible pattern wires three roles together — <code>tablist</code>, <code>tab</code>, <code>tabpanel</code> — with <code>aria-selected</code> and <code>aria-controls</code> so keyboard and screen-reader users get the same structure the mouse user sees. Arrow-key navigation inside the tablist is part of the pattern, and the panel must not be focus-hidden.</p>
<div class="codeWrap"><pre><code>&lt;div role="tablist" aria-label="Billing period"&gt;
  &lt;button role="tab" id="tab-monthly" aria-controls="panel-monthly"
          aria-selected="true"&gt;Monthly&lt;/button&gt;
  &lt;button role="tab" id="tab-yearly" aria-controls="panel-yearly"
          aria-selected="false"&gt;Yearly&lt;/button&gt;
&lt;/div&gt;
&lt;div role="tabpanel" id="panel-monthly" aria-labelledby="tab-monthly"&gt;
  &lt;!-- the monthly pricing --&gt;
&lt;/div&gt;
&lt;div role="tabpanel" id="panel-yearly" aria-labelledby="tab-yearly" hidden&gt;
  &lt;!-- the yearly pricing --&gt;
&lt;/div&gt;

// tab rules
- the selected tab carries aria-selected="true", and the panel is shown
- arrow keys move focus between tabs; Tab enters the panel
- tabs do not create a page-change; a browser back button is not lost
- if the content differs in structure, it is probably pages, not tabs</code></pre></div>
<h4 id="ch6-5-paging">Pagination versus infinite scroll</h4>
<p>Numbered pagination fits search results and logs, where the user hunts for a specific page and needs to know where they are. "Load more" fits a recent-first list that is secondary to the page's purpose, and it appends rather than replaces. Infinite scroll fits an endless feed with no goal — and it is wrong the moment the user needs a footer, a position, or an endpoint. The decision is task-first: the user must be able to say where they are and go back to it.</p>
<div class="codeWrap"><pre><code>// numbered pages: when the user hunts for a specific result
//    (search results, transaction logs) keep the position explicit
[Prev]  1 2 3 4 5  [Next]    "Page 3 of 12" — always in the heading

// load more: when the list is secondary and the order is newest-first
[Load more]   appends to the list, never replaces it
             announces the new count ("added 20 of 40")

// infinite scroll: only for an endless feed with no goal and no end
// the failure cases that end product careers:
- the footer becomes unreachable at the bottom of an infinite list
- the user's position is lost on reload (scroll restoration fails)
- a keyboard user has no way to step the pagination

// the acceptance test for any paging pattern
[ ] the user can say where they are, out loud
[ ] the user can return to a previous position
[ ] the pattern works without a mouse</code></pre></div>
</section>

<section class="chapter">
<h2 id="ch7" data-toc>7 ▸ Prototyping and Testing</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">A prototype is a design you can disagree with cheaply. Fidelity rises as questions narrow — structure first, then content, then polish — and every level is testable. This chapter covers the fidelity ladder, prototype logic, the testing methods that give you answers, and the loop that turns findings into the next version.</p>

<h3 id="ch7-1" data-toc>7.1 From wireframes to high fidelity</h3>
<p class="topic-desc">The fidelity of an artifact should match the question it is answering. A wireframe cannot test whether the brand feels right, and a polished mockup is wasted money while the structure is still wrong. The ladder below is the order that question follows.</p>
<h4 id="ch7-1-wireframe">The wireframe: structure with no colour</h4>
<p>A wireframe is the layout without the visual system: boxes and lines that say what is where and how big, so that hierarchy and flow can be argued about before anyone falls in love with a blue. It is fast deliberately — minutes, not days — and its defeat condition is the pixel-polished wireframe that nobody dares to change. ASCII is a perfectly good first form; the sketch below is a full page in ten seconds.</p>
<div class="codeWrap"><pre><code>+--------------------------------------------------------------+
| [logo]    Home  Docs  Pricing            [Sign in]  [CTA]     |
+--------------------------------------------------------------+
|                                                              |
|  H1  "Design systems that ship"                              |
|  Subhead — one sentence, 65ch max, real copy                 |
|  [  Primary CTA  ]    Learn more (text link)                 |
|                                                              |
|  +----------+   +----------+   +----------+                 |
|  | icon     |   | icon     |   | icon     |                 |
|  | heading  |   | heading  |   | heading  |                 |
|  | body text|   | body text|   | body text|                 |
|  +----------+   +----------+   +----------+                 |
|                                                              |
|  footer: links, legal, social                               |
+--------------------------------------------------------------+

// wireframe review questions — the only ones allowed at this stage
[ ] what is the one thing this page does?
[ ] what do you read first, second, third?
[ ] what is the exit — the next action?
// colour, fonts and imagery are not in scope yet</code></pre></div>
<h4 id="ch7-1-fidelity">Matching fidelity to the decision at risk</h4>
<p>Each rung answers a different question, and the cost jumps by an order of magnitude per rung. Paper structure and wireframes are for IA and hierarchy; mid-fi with real content tests navigation and usability; hi-fi with motion tests polish, brand and sign-off. The discipline is refusing the next rung until the current question is answered — mockups are the most expensive way to discover a flow problem.</p>
<div class="codeWrap"><pre><code>// the fidelity ladder: question first, cost second
FIDELITY   PURPOSE                        COST      REVIEW IT GETS
paper      explore structure in minutes   minutes   stakeholders, not usability
wireframe  layout, hierarchy, flows       hours     content and IA, not colour
mid-fi     real content, real states      days      usability and navigation
hi-fi      motion, polish, brand          weeks     final sign-off, design QA

// the discipline
[ ] structure is agreed before mid-fi (flow problems are cheapest here)
[ ] mid-fi carries REAL content — lorem ipsum hides both readability
    and content-shape problems (ch5-3, ch3-1)
[ ] hi-fi is entered with the test plan already written (ch7-3)
// a "polished wireframe" that nobody edits is a sign the rung was
// skipped in the wrong direction: too much craft, too little decision.</code></pre></div>

<h3 id="ch7-2" data-toc>7.2 Prototyping: tools and logic</h3>
<p class="topic-desc">A prototype is a flow you can press, and the difference between a demo and a prototype is which states are wired. Tools differ, but the specification that matters — the flow spec — is a table of the frames, the states and the hand-off, and it lives in the repo.</p>
<h4 id="ch7-2-flows">The flow spec: frames, states, entry points</h4>
<p>Before wiring anything, write the spec: the frame sizes you are actually shipping to, the states every screen admits, whether transitions are in scope, and the entry points a tester will start from. This table is the difference between a prototype the team shares and a prototype that answers a question — and it is exactly what a developer needs later, which is why it outlives the tool that made it.</p>
<div class="codeWrap"><pre><code>// prototype flow spec — write it before opening the tool
FIELDS                     VALUE
frames                     1440 x 900 (desktop)  390 x 844 (phone)
states per screen          default, error, empty, loading
transitions                none in click-through; animate only the key flow
entry points               dashboard CTA, empty state CTA
real content               yes — five key screens use final copy
hand-off                   tokens file + redlines for the five key screens

// screens that must be wired even though they are "boring"
- the error path of the primary flow (ch3-2)
- the empty states of every list that can be empty (ch3-5)
- the loading states, so testers do not mistake latency for design</code></pre></div>
<h4 id="ch7-2-logic">Click-through versus real logic</h4>
<p>A click-through prototype links screen to screen; a logic prototype encodes decisions — "if the email is invalid, show this error". Testers do not need full logic, but they need the states that would make them think the prototype is broken: the button that does nothing, the back button that is not there, the empty state that never loads. The checklist is the quality bar for any prototype you put in front of a user, because a tester who gets stuck on a missing state is testing your prototype, not your design.</p>
<div class="codeWrap"><pre><code>// the prototype readiness checklist
[ ] the "cancel" and "back" paths exist, end to end
[ ] error states are wired for at least the primary flow
[ ] empty states exist for every list that can be empty
[ ] loading states shown, not skipped
[ ] text is real content from the content inventory (ch3-1)
[ ] the prototype runs on a phone, not only a laptop
[ ] click targets are the sizes they will ship at (44px, ch4-5)

// the test worth running before the test
walk the prototype end to end yourself with the checklist open.
every gap you find is a tester about to find it for you — and
charge you the session to do so.</code></pre></div>

<h3 id="ch7-3" data-toc>7.3 Testing methods</h3>
<p class="topic-desc">Three methods cover most rounds: moderated testing (why), unmoderated testing (how many), and controlled comparison (which of two). Each earns its place by the question it answers; none of them is a substitute for the others.</p>
<h4 id="ch7-3-plan">The plan: tasks, metrics, pass bars</h4>
<p>Every session needs the same skeleton — scenarios written as goals, a metric per task, and a pass bar agreed before anyone opens the room (the full mechanics are in ch2-4). The table below is a complete round: four tasks, four metrics, and a pass bar that turns the session into a decision at the end of the day rather than an argument.</p>
<div class="codeWrap"><pre><code>TASK  SCENARIO                        METRIC              PASS BAR
T1    "sign up and create a project"  task success        80%+ complete unaided
T2    "find the price for 40 seats"   time on task        under 90 seconds
T3    "export this week's report"     errors per task     one or fewer
T4    "cancel and confirm the change" mis-clicks          none on destructive paths

// decide before the session, not after
- which tasks, in which order (calm first, stressful last)
- who recruits, and the screen that recruits them (ch2-2)
- who moderates and who only takes notes (separate people)
- the pass bar per task — "we will ship this if T1 and T3 pass"</code></pre></div>
<h4 id="ch7-3-fivesec">The five-second test and the ambiguity it finds</h4>
<p>The cheapest test in the discipline tests hierarchy, not usability: show the screen for five seconds, cover it, and ask what the page is for and what the main action is. Five people, ten minutes, and the result is binary — if four of five agree on both answers, the hierarchy is doing its job; any disagreement is a specific, localisable defect. It is the first test to run on any new screen, because it costs nothing and catches the failures that usability-testing sessions politely attribute to "task confusion".</p>
<div class="codeWrap"><pre><code># the five-second test — run on five people, score on agreement
1. show the screen for exactly five seconds
2. cover it
3. ask: "what is this page for?"
4. ask: "what is the main action?"
5. score: 4 of 5 agree on BOTH answers -> hierarchy works

# reading the results
"it's a pricing page" but the main action is "sign up" -> good, exit clear
nobody said "export report" on a reporting screen     -> level 1 is wrong
two different main actions named                      -> two entries, ch4-4

# why it works
hierarchy is judged in the first seconds or not at all.
a five-second pass does not prove the flow, but a failure proves
the hierarchy is broken and no downstream test will rescue it.</code></pre></div>
<h4 id="ch7-3-compare">A/B testing: one metric, pre-registered</h4>
<p>A controlled comparison is how you decide between two real designs, and the rules that make it science are the same as anywhere: one metric chosen before the test, a sample size agreed in advance, and a fixed stopping rule. A change without a pre-registered metric and a sample size is not an experiment — it is a redesign with extra steps.</p>
<div class="codeWrap"><pre><code>// pre-register the metric, the sample, and the stopping rule first
// metric: task success rate (completed / started)
function successRate(completed, started) {
  return completed / started;
}

// decide before the test starts
[ ] the ONE metric that decides ("signup completion", not "engagement")
[ ] n per arm (200 completions is a working minimum for UI changes)
[ ] the stopping rule ("run until n met, then compare with Fisher's
    exact test"; never "watch it until it looks better")
[ ] both variants pass the same accessibility checks first

// the discipline
a winner with p confidence against the pre-registered metric is a
decision. a winner you noticed while watching is a preference.</code></pre></div>


<h3 id="ch7-4" data-toc>7.4 Iterating from findings</h3>
<p class="topic-desc">A test that produces no change is a test that was not worth running. The closing loop of the process is triage: turn findings into an issue log, severity-rank them against the pass bars, fix, and re-test the changed tasks so the loop provably closed.</p>
<h4 id="ch7-4-log">The issue log: findings, not feelings</h4>
<p>Every finding gets a row with the evidence — the task, the frequency, the observed behaviour — so the fix can be argued against the data rather than against the moderator's memory. The discipline is the same as synthesis in ch2-5: a finding without the session, the task and the frequency attached is a claim without evidence.</p>
<div class="codeWrap"><pre><code>// issue log — one row per finding, evidence attached
ID  FINDING                                   SEVERITY  FREQUENCY/SOURCE
A   export link sits below the fold           P1        2 of 5 failed T3
B   "Cancel" looks like a ghost button,       P1        every session,
    users click it by accident                          missed in T4
C   error text contradicts the field label    P2        rare, survey note
D   primary CTA competes with the hero image  P3        opinion, check T1

// log rules
- one finding per row; a row with two findings is two rows
- the source is the session or task, never "I noticed"
- severity is assigned against the pass bars, not the pain felt:
  P1 blocks a pass bar, P2 wastes time but the task passes,
  P3 is polish and judgement</code></pre></div>
<h4 id="ch7-4-severity">Severity against the pass bar, not against feelings</h4>
<p>Rank findings by what they did to the metrics you pre-registered (ch7-3): a failed pass bar is P1 whatever the stakeholder's emotional reaction, and a cosmetic note is P3 even if it was mentioned first. The triage table is the bridge between the test and the sprint board — every row has an owner, a fix and a verification task, so "we tested it" ends in a signed-off change rather than a shared feeling.</p>
<div class="codeWrap"><pre><code>// triage: severity, fix, verification — one row per finding
ID  SEVERITY  FIX                             VERIFY
A   P1        move export above the fold      retest T3: 4 of 5 pass
B   P1        give Cancel a bordered variant  retest T4: confirm step
C   P2        rewrite the error text          lint strings against the
                                             label wording
D   P3        add a scrim behind the hero     visual QA, no metric

// the rule of three for a test round
[ ] every P1 has a fix and a retest in the same iteration
[ ] the retest runs the SAME task, so the metric is comparable
[ ] findings without a fix are re-opened, not forgotten</code></pre></div>
<h4 id="ch7-4-loop">Fix, re-test, close the loop</h4>
<p>Iteration is not a correction, it is the method: a prototype is a falsifiable hypothesis (ch1-2), and the retest is what falsifies it. Re-run the exact task that failed, against the exact pass bar, so the result is comparable to the first round — changing the design and the test at the same time tells you nothing. When the pass bar clears, close the row and record what changed in the design system (ch8), so the fix outlives the sprint.</p>
<div class="codeWrap"><pre><code># the closing loop, per round
1. run the round                -> issue log with evidence (7.4 above)
2. triage P1/P2/P3              -> fixes with owners
3. fix the design               -> update the prototype AND the spec
4. retest the SAME tasks        -> same scenarios, same pass bars
5. pass bars clear              -> close the row, note the design-system
                                  change in the ch8 documentation
# count the cost honestly
#   round cost  = sessions + fixes + retest time
#   round value = pass bars cleared + P1s kept out of production
# if value is not bigger than cost, the test plan is testing the
# wrong things — a testing problem, not a budget problem.</code></pre></div>
<div class="tip"><p>The cheapest way to make iteration fast is to keep the prototype's spec beside the tokens in the repo (ch8-2). A test finding then becomes a one-line change to a spec file rather than a round trip through a design tool, and the retest can start the same afternoon.</p></div>
</section>

<section class="chapter">
<h2 id="ch8" data-toc>8 ▸ Accessibility, Design Systems and Delivery</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">The final chapter closes the loop: the accessibility rules that turn a usable design into an accessible one, the tokens and component libraries that keep a hundred screens coherent, and the hand-off that delivers it all to engineering in a form that survives contact with a codebase.</p>

<h3 id="ch8-1" data-toc>8.1 WCAG essentials: the designer's checklist</h3>
<p class="topic-desc">WCAG 2.2 is organised around four principles — perceivable, operable, understandable, robust — and only a handful of its criteria are the designer's to own. Learn those criteria by number, because the numbers are the vocabulary of an accessibility audit and of the bug reports that follow.</p>
<h4 id="ch8-1-pour">The four principles, and the criteria that are yours</h4>
<p>POUR is the frame: perceivable (can it be sensed?), operable (can it be used?), understandable (does it make sense?), robust (does it survive assistive technology and time?). Within it, a designer owns a specific short list: 1.1.1 non-text content, 1.4.3 text contrast, 1.4.11 non-text contrast, 1.4.10 reflow, 2.4.7 focus visible, 2.5.8 target-size minimum (new in WCAG 2.2), and 3.3.1/3.3.3 error identification and suggestion. Learning the numbers turns "make the button accessible" into a checklist with a pass and a fail for each.</p>
<div class="codeWrap"><pre><code>// the designer's WCAG 2.2 criteria, with the number and the rule
1.1.1    every non-text element has a text alternative (ch5-5)
1.4.3    text contrast at least 4.5:1 (3:1 for large text) (ch5-2)
1.4.10   reflow: content works at 320px without scrolling both ways
1.4.11   non-text contrast at least 3:1: icons, boundaries, states
2.4.7    a visible focus indicator on every interactive element
2.5.8    target size at least 24x24 CSS px (44x44, ch4-5, is the
         comfortable floor)
3.3.1    errors are identified and described in text (ch6-2)
3.3.3    the error suggests a fix ("Enter a valid email, like ...")

// audit one screen, both themes, one pass per criterion
SCREEN:      checkout
CRITERION    LIGHT   DARK    NOTE
1.4.3        pass    pass    body 8.9:1, muted 4.8:1
1.4.11       pass    fail    spinner icon 2.2:1 on its chip, dark only
2.4.7        pass    pass    ring visible on all four inputs
2.5.8        fail    fail    the "remove" X is 20x20 with no padding
1.4.10       pass    pass    320px reflow tested on a real phone</code></pre></div>
<div class="note"><p>Reflow (1.4.10) is the requirement behind the 320px viewport test: at 320 CSS pixels of width there must be no horizontal scrolling, which means a fixed 1248px grid from ch4-3 has to genuinely collapse rather than shrink. Test it at 320px, at 200% zoom, and in forced-colours mode.</p></div>
<h4 id="ch8-1-keyboard">The keyboard audit</h4>
<p>The keyboard is not an optional input method for a small minority; it is what screen-reader users, power users and people with motor impairments rely on, and it is cheap to test by hand. The audit is a walking list: Tab order follows visual order, every interactive element is reachable, nothing traps focus, a skip link exists, and dialogs wrap focus but close on Esc. If you only run one accessibility test, run this one — it finds more avoidable defects per minute than any other.</p>
<div class="codeWrap"><pre><code>// skip link — the first focusable element on the page
&lt;a class="skip-link" href="#main"&gt;Skip to content&lt;/a&gt;
// .skip-link is visually hidden until it receives focus, then it
// appears top-left; every long page inherits the pattern.

// the keyboard audit, one pass, both themes
[ ] Tab from the top: order matches the visual order on screen
[ ] every link, button and input is reachable (no tabindex="-1"
    traps left behind)
[ ] the focus ring is visible at every stop (ch6-1)
[ ] dialogs: focus enters, wraps, and Esc closes; focus returns
[ ] custom controls answer with the right role and arrow keys
    (tabs, ch6-5)
[ ] 200% zoom plus keyboard only: the whole primary flow completes</code></pre></div>
<h4 id="ch8-1-headings">Headings, landmarks and a reading order that comes free</h4>
<p>Much of accessibility is agreeing with the browser instead of fighting it: one <code>h1</code> per page, heading levels that step down without skipping, and real landmarks — <code>header</code>, <code>nav</code>, <code>main</code>, <code>footer</code> — instead of divs with class names. Screen-reader users navigate by exactly these two systems, and a page whose visual structure and markup structure disagree forces them to read everything to find anything. The designer's job is to make sure the two structures are the same structure.</p>
<div class="codeWrap"><pre><code>&lt;!-- the accessible skeleton: landmarks plus one h1 --&gt;
&lt;header&gt;...&lt;/header&gt;
&lt;nav aria-label="Main"&gt;...&lt;/nav&gt;
&lt;main id="main"&gt;
  &lt;h1&gt;Checkout&lt;/h1&gt;
  &lt;h2&gt;1. Delivery&lt;/h2&gt;      &lt;!-- h2 under h1, never a skipped rung --&gt;
  &lt;h3&gt;Contact details&lt;/h3&gt;
&lt;/main&gt;
&lt;footer&gt;...&lt;/footer&gt;

// heading audit
[ ] exactly one h1 per page
[ ] levels step by one: h1 then h2 then h3, no skipped rungs
[ ] the headings, read alone, tell the story of the page
[ ] landmarks exist and are not empty; main holds the page's purpose</code></pre></div>

<h3 id="ch8-2" data-toc>8.2 Design tokens: one file, both themes</h3>
<p class="topic-desc">Design tokens are what the whole system reduces to: primitives at the bottom, semantic roles in the middle, component tokens only where a real exception exists. One file, checked into the repo, drives both themes and feeds the contrast check.</p>
<h4 id="ch8-2-layers">The three layers, and what each is for</h4>
<p>Recap the pattern from ch5-1 with its full weight: primitives are the named colours on the ramp, never used directly by components; semantic tokens say what a colour does (bg, surface, text, accent, status); component tokens exist only where a component genuinely needs its own value. The contract is that components consume the semantic layer, so re-theming is a token swap and a component cannot misuse a role even by mistake.</p>
<div class="codeWrap"><pre><code>// the three layers — where each hex value is allowed to live
LAYER       EXAMPLE                     WHO USES IT
primitives  --blue-500, --slate-100     the token file only
semantic    --color-bg, --color-accent  every component, every state
component   --button-bg                 only a real exception

// a violation to recognise in review
.button-danger { background: var(--blue-500); }
// the component reached past the semantic layer. if the brand
// changes, this one button silently keeps the old blue.</code></pre></div>
<h4 id="ch8-2-file">A working token file, both themes</h4>
<p>The whole system as one JSON file: the primitives, then a semantic block per theme. The two blocks are deliberately hand-written, not derived — dark mode is a re-design (ch5-2), and the differences are decisions, not transforms. Note the small asymmetries that carry the meaning: surface stays lighter than bg in both themes, accent is lighter and less saturated in dark, and text-muted moves down the ramp so it stays readable on dark surfaces.</p>
<div class="codeWrap"><pre><code>// tokens/color.json
{
  "primitives": {
    "slate": { "50": "#f8fafc", "100": "#f1f5f9", "200": "#e2e8f0",

  },

    },
    "dark": {
      "bg":          "{slate.950}",
      "surface":     "#111827",
      "surface-sunk":"{slate.900}",
      "text":        "{slate.100}",
      "text-muted":  "{slate.400}",
      "text-disabled":"{slate.600}",
      "on-accent":   "{slate.950}",
      "border":      "{slate.800}",
      "border-strong":"{slate.700}",

      "accent-hover":"{blue.400}",

// what the dark block does differently, and why

//   text is LIGHTER but not pure white   (less glare)
//   accent is LIGHTER and less saturated  (less bloom)
//   status colours are LIGHTER         (they need to pop on dark)
//   text-muted goes from 600 to 400    (600 is unreadable on dark)</code></pre></div>
<h4 id="ch8-2-generate">From JSON to CSS, with the contrast check attached</h4>
<p>The token file is the authoring format; the build turns it into CSS custom properties so the browser can use it. Because the file is data, the contrast calculation from ch5-2 can run over the same pairs where they are defined — in both themes, before they ever reach a screen. The check is attached to the source, not scattered across individual usages.</p>
<div class="codeWrap"><pre><code>// generated into CSS — the build emits exactly this shape
:root {
  --color-bg: #f8fafc;
  --color-surface: #ffffff;
  --color-accent: #2563eb;
  --color-text: #0f172a;
  /* ...one custom property per semantic token... */
}
[data-theme="dark"] {
  --color-bg: #020617;
  --color-surface: #111827;
  --color-accent: #3b82f6;
  /* ... */
}

// and the CI check that runs over the file, not the CSS
//   node contrast-check.js tokens/color.json
for each theme, for each (foreground, background) pair declared:
  text pairs     -> require at least 4.5:1
  ui pairs       -> require at least 3:1
  on failure     -> exit 1, name the token and the measured ratio
// the pairs are verified where they are defined rather than where
// they are used — which is how a 6pm regression gets caught.</code></pre></div>
<div class="tip"><p>Commit the token file beside the code (ch1-3) and let the build derive the CSS from it — never hand-sync. A designer edits one JSON, the developer gets one generated stylesheet, and the diff is a single line with a comment: "colour token: accent 600 to 500".</p></div>

<h3 id="ch8-3" data-toc>8.3 Component libraries</h3>
<p class="topic-desc">A component library is a spec plus a governance process: what every component is, in every state, with the tokens it consumes — and a rule for how new components get in. Without the second half, the library is a folder of pictures.</p>
<h4 id="ch8-3-spec">The spec: states, tokens, properties</h4>
<p>The unit of library work is the component spec, and it is written before the artwork: the states the component admits (from the state map in ch6-1), the tokens it consumes (never a hex literal), and the properties that are allowed to vary plus the values they may take. A spec that cannot be expressed as a table is a component that is not finished being designed.</p>
<div class="codeWrap"><pre><code>// component spec — the button, as a table the build can check
PROPERTY   VALUES                              DEFAULT
variant    primary | secondary | ghost         primary
size       sm (36px) | md (44px) | lg (52px)   md
states     default, hover, active, focus,      all required
           disabled, busy
tokens     bg / content / border per state     --accent / --on-accent
radius     var(--radius)                       fixed, never overridden
spacing    padding-inline per size             16px / 20px / 24px

// the same spec as JSON the library can validate
{
  "name": "button",
  "variants": ["primary", "secondary", "ghost"],
  "sizes": { "sm": 36, "md": 44, "lg": 52 },
  "states": ["default", "hover", "active", "focus", "disabled", "busy"],
  "tokens": { "default": { "bg": "--color-accent" } }
}</code></pre></div>
<h4 id="ch8-3-variants">Variants, exclusions and the half-designed state</h4>
<p>Two kinds of component addition fail predictably. The first is a variant that is really a new component wearing a flag — "button with an icon" is a property, "button that is a link" is a different component. The second is the half-designed state: the variant ships with default and hover drawn, and disabled, focus and busy inherit whatever the parent had — which is how a library produces components that fail the keyboard audit in ch8-1. The rule is that a variant is not done until every state in the spec has a value.</p>
<div class="codeWrap"><pre><code>// exclusions: named, so nobody reinvents them
button:
  - no custom border-radius (the corner scale owns it, ch4-5)
  - no new colour literal (the semantic layer owns the palette)
  - no shadow outside the shadow tokens (ch5-2 dark-mode rule)
  - no hover-only feedback (every state must survive motion off)

// the half-designed variant, recognised in review
"secondary button" ships with:
  default  drawn   hover  drawn   focus  INHERITED  disabled  INHERITED
// fix: a variant is done when every spec state has a value,
// and the tokens are named, not picked.</code></pre></div>
<h4 id="ch8-3-govern">Admission and retirement: the library is a process</h4>
<p>A library without admission rules fills with one-off components, and a library without retirement rules keeps them forever. Admission is a review: the component must be used in two or more places (one place is a page's private CSS, not a system), the spec must be complete, and the tokens must come from the semantic layer. Retirement is the same review in reverse: a component drops below two usages, its consumers migrate, and it is removed in a version bump — not left as a deprecated twin that two teams each believe is canonical.</p>
<div class="codeWrap"><pre><code>// admission checklist for a proposed component
[ ] used by 2+ screens or teams (one usage stays in the page)
[ ] spec table complete: variants, sizes, states, tokens
[ ] states include focus, disabled and busy (ch6-1)
[ ] tokens only from the semantic layer (ch8-2)
[ ] an owner is named; docs exist (ch8-5)
[ ] existing components were checked first — is this a variant?

// retirement, deliberately the same shape
[ ] fewer than 2 usages after the migration work
[ ] consumers migrated to the replacement in this version
[ ] removed in a major or minor bump, announced in the changelog</code></pre></div>

<h3 id="ch8-4" data-toc>8.4 Developer hand-off</h3>
<p class="topic-desc">A hand-off is complete when the developer stops needing to infer. Every value a developer has to guess is a design decision that ships by accident; the checklist below is the difference between handing over screens and handing over a specification.</p>
<h4 id="ch8-4-check">What a complete hand-off contains</h4>
<p>Type scale in rem, spacing scale, colour roles in both themes, radius and shadow tokens, the states of every interactive component, and the breakpoints with a reason for each. If a developer has to measure padding off a screenshot, the design is not finished. The checklist lives in the repo beside the tokens and is the same list the developer signs off against — hand-off is a two-party agreement, not a transfer.</p>
<div class="codeWrap"><pre><code>// hand-off checklist — every value a developer needs to build it
[ ] type scale in rem, with line heights (ch5-3)
[ ] spacing scale, named not numbered (ch4-5)
[ ] colour roles, both themes, as tokens (ch8-2)
[ ] radius and shadow from the scales, no literals
[ ] component states for every interactive component (ch6-1)
[ ] breakpoints with a reason each: content, not device widths
[ ] icons as SVG files, currentColor, on the set grid (ch5-5)
[ ] empty, error and loading states for every list (ch3-5)
[ ] motion tokens: durations, easing, reduced-motion block (ch6-3)</code></pre></div>
<h4 id="ch8-4-redline">Redlines for the risky screens only</h4>
<p>Redlines — annotated measurements — are expensive to keep honest, so spend them where the risk is: screens with tight spacing, optical adjustments, or alignment that cannot be inferred from the grid. A redline names the token or the exception; a screen that matches the grid and tokens gets no redlines at all. The test of a good redline is that a developer who deletes it and measures the screen arrives at the same numbers.</p>
<div class="codeWrap"><pre><code>// redline — only where the grid cannot answer
SCREEN: checkout, "payment summary" card

  +---------------------------------------------+
  |  Payment summary                     &lt;- 24px padding
  |                                       (token: space-24)
  |  subtotal         EUR 42.00                |
  |  VAT (21%)        EUR  8.82     &lt;- column: numbers right-
  |  ---------------------------------          aligned, tabular-nums
  |  total            EUR 50.82                |
  +---------------------------------------------+

  // exceptions called out, not left to inference
  - the divider is 1px var(--color-border), NOT the shadow scale
  - the "total" row uses space-32 above it, not space-24
  - the card is 4 columns on desktop, 11 columns on mobile
// a redline that repeats the grid is noise. keep the exceptions.</code></pre></div>
<h4 id="ch8-4-gaps">The gaps developers fill with guesses</h4>
<p>The hand-off failures that ship as bugs all have the same shape: a value the design never specified, filled in with the nearest available one. Text that truncates with an ellipsis instead of wrapping to a second line; a hover state that darkens a token that was never meant to darken; a loading state invented on the spot. The fix is a short ambiguity log maintained during design: every time you notice a "what happens when" you cannot yet answer, write it down, and nothing ships until the log is empty.</p>
<div class="codeWrap"><pre><code>// ambiguity log — every open question that would otherwise be
// answered by whoever happens to build the screen
OPEN                            ANSWERED WHEN
button with a very long label   wrap to two lines, centred,
                                min-height keeps the 44px hit area
hierarchy on a 320px table      the 12-col grid collapses; heading
                                scales with the fluid type (ch5-4)
how does the summary card       a 160ms ease-out entrance, and the
enter the screen?               reduced-motion block collapses it
                                to 0.01ms (ch6-3)
dark-mode icon colour           icons use currentColor and inherit
                                their label's colour (ch5-5)

// rule
[ ] every OPEN row has an owner and a decided answer before the
    hand-off checklist is signed
[ ] decided answers become tokens, specs or docs — never a
    developer's memory</code></pre></div>

<h3 id="ch8-5" data-toc>8.5 Documentation and governance</h3>
<p class="topic-desc">A design system is only as good as its documentation and the process that keeps it true. Documentation covers usage, not just appearance; versioning makes change safe; and a decision log keeps the reasons the system looks the way it does.</p>
<h4 id="ch8-5-docs">Document usage, not just appearance</h4>
<p>A component page shows the spec, the states, and — the part most libraries miss — how to use it: when to choose this component over its neighbours, a do-and-don't pair, and the accessibility notes that came free with the markup. Documentation is the mechanism that stops the same mistake being made twice in different teams, which is the entire economic argument for a library.</p>
<div class="codeWrap"><pre><code># component docs skeleton — markdown, in the repo beside the spec
# button.md

## When to use
Primary for the one action per screen; secondary for the runner-up;
ghost when the action must not compete (ch4-1 hierarchy levels).

## States (all required, ch6-1)
default, hover, active, focus, disabled, busy — tokens in the table.

## Do / Don't
DO   one primary action per view; make it the exit (ch4-4)
DON'T stack two primary buttons
DON'T disable with no reason — a read-only value with an
      explanation beats a disabled mystery (ch6-4)

## Accessibility
- focus ring from the shared rule (ch8-1)
- hover is never the only signal (ch5-2)
- disabled text holds 3:1 even though WCAG exempts it

## Tokens
variant to bg / content / border per state, from tokens/color.json</code></pre></div>
<h4 id="ch8-5-version">Versioning tokens and components</h4>
<p>Treat the design system like a dependency, because it is one: semver for tokens and components, a changelog that names what changed and why, and a deprecation path instead of silent replacement. A token re-colour is a minor bump; removing a component is a major one. The discipline that makes it work is that every bump is paired with a changelog line referencing the decision log, so a consumer can answer "why is the button bigger now?" in one hop.</p>
<div class="codeWrap"><pre><code>// changelog — the design system as a dependency
## 2.1.0 (2026-10-02)
- added: `space-28` token (optical override, ch4-5, see DEC-407)
- changed: `--color-accent` light from blue-700 to blue-600
  (contrast on tinted surfaces, DEC-409)
- changed: button min-height 40px to 44px (target size, WCAG 2.2)
- deprecated: `surface/overlay` — use `surface/raised` + scrim

## 2.0.0 (2026-09-04)
- removed: `alert-banner` component — consumers migrated to `banner`

// decision log — the reason behind the change, one entry per bump
DEC-409: accent moved one step lighter because the 700 hue failed
1.4.11 against the raised surface in dark mode (measured 2.6:1,
both themes, on the token file).</code></pre></div>
<h4 id="ch8-5-process">The review loop that keeps the system true</h4>
<p>Documentation dies unless a process keeps it honest: a named owner per component, a review for every admission and retirement (ch8-3), and the loop from ch7-4 wired into the system — a test finding that changes a component must change the spec, the docs and the changelog in the same change. The final measure of the whole guide is brutal and simple: a new designer on the team can ship a screen that looks like the product, passes the audits of ch8-1, and needs no hex values, no 13px spacing, and no imported opinions.</p>
<div class="codeWrap"><pre><code># the governance loop, per change
1. change requested (bug, test finding, brand update)
2. owner updates spec + tokens + docs together — one commit
3. review: semantic layer only? states complete? docs updated?
4. changelog entry plus a decision-log reference
5. version bump per semver; consumers see a diff, not a surprise

# the loop closes into the earlier chapters
- tokens come from ch8-2, states from ch6-1
- docs restate the do-and-don'ts of ch4, ch5 and ch6
- test findings enter through the issue log of ch7-4
// and the loop is the point: research to design to test to ship
// (ch1-2) ends where it started — with the next round of evidence.</code></pre></div>
<div class="note"><p>The definition of done for the whole system: a screen built on the tokens and components of ch8-2 and ch8-3 passes the audits of ch8-1 without a single new decision. When that is true, design has become maintenance — which is what a design system is for.</p></div>
