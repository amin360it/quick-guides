Chapter 6 covered the shape of a request. This chapter is about the parts you only meet in production: a settings object with three dozen keys, response converters, request headers that carry auth tokens, JSONP, CORS preflights, the difference between a failed request and a failed parse, the global ajax lifecycle, and the jqXHR object — a promise you can also abort mid-flight.

10.1 The full settings object and $.ajaxSetup

Every shorthand method is compiled into one $.ajax settings object before it runs. Learning the handful of keys that actually change behaviour — and where their defaults come from — removes most of the surprises.

The settings you will actually change

Six keys carry almost all of the meaning. dataType is what you expect back; contentType is what you are sending. Confusing the two is the most common AJAX bug: a request that sends application/json but never sets dataType still arrives as a string, because jQuery only auto-parses a response when the server's Content-Type or the dataType tells it to. data is an object for form-style bodies — jQuery URL-encodes it for GET and turns it into an application/x-www-form-urlencoded body for everything else unless you set processData: false. cache: false appends a timestamp to GET URLs so a cache-busting request always reaches the server, which matters constantly during development and matters for polling endpoints in production.

context is the quiet one. It sets the value of this inside every callback, so a handler can address the element it belongs to instead of re-querying the document for it. Passing context: $panel means the done callback can write to this directly and stays correct even if the panel has been replaced between request and response.

$.ajax({
  url: '/api/orders',
  method: 'POST',
  dataType: 'json',                                // what we expect back
  contentType: 'application/json; charset=utf-8',  // what we send
  data: JSON.stringify({ id: 42, qty: 2 }),
  headers: { 'X-CSRF-Token': csrfToken },
  timeout: 10000,
  cache: false,
  context: $('#orders')
}).done(function (orders) {
  // `this` is the jQuery set passed as context, not the jqXHR
  this.html(renderRows(orders));
});

Defaults live in one global object

$.ajaxSetup() merges into $.ajaxSettings, the single object every request inherits from. It is genuinely useful for a cross-cutting value such as a timeout or an X-Requested-With header, and genuinely dangerous for anything else, because the change is silent, global and sticky for the life of the page. A request made three screens later still carries whatever you set at boot. Per-request headers are merged shallowly on top of the setup defaults, so one call can add a header without clearing the rest.

The keys worth setting there are exactly the transport-level ones: dataType, headers, timeout, cache and accepts. Everything that describes a particular call — its URL, its body, its success handler — belongs at the call site where it can be read.

Keep $.ajaxSetup() to transport concerns — timeouts, default headers, a base dataType. Never put success, error or complete handlers there. A behaviour that applies to every request belongs in a global event (10.5), where it is visible and can be removed; a callback buried in a setup object is invisible at the call site and impossible to reason about when a request misbehaves.

10.2 beforeSend, headers and response converters

beforeSend runs after the transport is created but before it opens its socket; the headers map sets request headers per call; converters rewrite the body after the transport returns but before done() runs.

beforeSend: the last chance to change your mind

The beforeSend hook receives both the live jqXHR and the fully merged settings object. That makes it the right place for a token that has to be read at send time rather than at call time, for a per-request trace id, or for a decision to give up before spending a round trip. Returning false cancels the request outright and rejects the jqXHR, so anything hooked onto fail still runs and cleanup still happens. Do not throw from this function: the transport is already allocated, and an exception here leaves the request in an indeterminate state.

The per-call headers option is the declarative alternative for static values — a CSRF token, an Accept-Language. Reach for beforeSend only when the value must be computed at send time or when the request may be abandoned. Mixing the two is fine and common: static headers in the map, the conditional abort in the hook.

$.ajax({
  url: '/api/report.csv',
  dataType: 'text',
  beforeSend: function (jqXHR, settings) {
    jqXHR.setRequestHeader('Authorization', 'Bearer ' + getToken());
    if (!navigator.onLine) {
      return false;          // abort before the socket opens
    }
    settings.startedAt = Date.now();
  },
  converters: {
    'text csv': function (raw) {
      return raw.trim().split('\n');   // CSV text -> array of rows
    }
  }
}).done(function (rows) {
  console.log(rows.length + ' rows');
});

Converters and the parse that fails after a success

A converter is a pair of data types — "text json", "text xml", "text html" — and a function that transforms the first into the second. jQuery ships converters for the built-in types; a custom one buys you a new type for the cost of one function, as the CSV transform above does. The important consequence is that a 200 OK carrying malformed JSON is not a success. The transport succeeded, the converter threw, and the promise rejects with the text status "parsererror". The raw body is still on jqXHR.responseText, which is the only thing that lets you log what the server actually sent instead of a generic failure.

Because a converter runs inside the request pipeline, it must be cheap and it must be total: it either returns the converted value or throws. Side effects belong in done(), not in a converter, and a converter should never touch the DOM.

10.3 JSONP, CORS and cross-origin realities

JSONP is a script-tag hack from 2005; CORS is a contract the server must honour. Knowing which one you are looking at explains every cross-origin symptom, including the confusing one where the request clearly returned data but jQuery reports status 0.

What JSONP actually does

Setting dataType: 'jsonp' makes jQuery inject a <script> element pointing at your URL with a callback parameter appended, then evaluate whatever comes back. Because a script tag is not bound by the same-origin policy, this works against servers that were written to wrap their JSON in a function call. It is also strictly GET, has no real error detection — a failed script fires an error at best — and executes arbitrary third-party JavaScript in your page's origin. Treat it as legacy: if the remote server supports CORS, use CORS.

$.ajax({
  url: 'https://api.example.com/search',
  dataType: 'jsonp',
  jsonp: 'callback',              // the query parameter the server reads
  jsonpCallback: 'handleSearch'   // a predictable name, which is cacheable
}).done(function (data) {
  render(data);
});

CORS is a server contract, not a jQuery setting

For a cross-origin request the browser sends an Origin header and refuses to hand the response to your code unless the server replies with a matching Access-Control-Allow-Origin. jQuery cannot change that; no client code can. A request that fails this check is reported to jQuery as a network error with jqXHR.status === 0 and an empty statusText, because the browser never let the script read the real status. If you see status 0 against a URL that "works in Postman", you are looking at a missing or too-narrow CORS header, not a bug in the request.

Requests that send cookies or an Authorization header are preflighted: the browser first sends an OPTIONS request, and the server must answer it with the allowed methods, headers and credentials. Setting xhrFields: { withCredentials: true } tells the browser to include cookies cross-site, but it only takes effect when the server echoes back an exact origin — never * — together with Access-Control-Allow-Credentials: true. When the two halves disagree, the request fails with status 0 again, and the only visible clue is a console message the browser writes, not the page's own code.

10.4 Error handling, status codes and the jqXHR promise

A request can fail in four distinct ways — timeout, abort, an HTTP error status, or a body that does not parse. The fail callback hands you three arguments precisely so you can tell them apart instead of showing one generic message.

The three arguments to fail

fail(jqXHR, textStatus, errorThrown) gives you the transport, a short reason string, and the exception or HTTP status text. textStatus is one of "timeout", "error", "abort", "parsererror" or "nocontent"; jqXHR.status is the numeric HTTP status, or 0 when the browser blocked or cancelled the exchange. Branching on textStatus first and status second is the pattern that survives contact with real networks: a timeout and a 500 deserve different copy, and an abort usually deserves silence.

const req = $.ajax({
  url: '/api/save', method: 'PUT', data: payload, dataType: 'json'
});

req.done(function (res) {
  toast('Saved');
}).fail(function (jqXHR, textStatus, errorThrown) {
  if (textStatus === 'timeout') {
    toast('The server is slow. Try again.');
  } else if (textStatus === 'abort') {
    // the user navigated away; stay silent
  } else if (jqXHR.status === 422) {
    showFieldErrors(JSON.parse(jqXHR.responseText).errors);
  } else if (jqXHR.status >= 500) {
    report('server', errorThrown);
  } else {
    toast('Request failed (' + jqXHR.status + ')');
  }
}).always(function () {
  spinner.remove();
});

jqXHR is a promise and a transport at once

The object $.ajax returns is a jQuery Deferred decorated with the XMLHttpRequest surface. As a promise it exposes done, fail, always, then and progress; jQuery 3 made Deferreds Promises/A+ compatible and added catch and finally aliases, so a chain behaves the way a native fetch chain does and an exception thrown inside a then rejects the next promise rather than escaping. As a transport it exposes abort(), setRequestHeader(), getAllResponseHeaders(), overrideMimeType() and the live readyState, status and statusText properties.

That dual nature is the reason to keep the returned reference. Calling $.ajax(...) and dropping the result throws away the only handle that can cancel the request or read its headers. Keeping it in a variable costs nothing and turns a fire-and-forget call into something you can abort on navigation, which is the difference between a tidy single-page app and one that writes responses into elements that no longer exist.

10.5 Global events, aborting and upload progress

Global events fire for every request in the page, upload progress needs the native XHR object, and abort() is the only clean way to cancel — all three are about the page, not the individual call.

The global ajax lifecycle

Every request whose global setting is true — the default — fires a fixed sequence of events on document: ajaxSend, then ajaxSuccess or ajaxError, then ajaxComplete. Wrapped around the whole run, ajaxStart fires when the first in-flight request begins and ajaxStop when the last one finishes. That pair is the correct place for a global progress indicator, because it counts requests rather than firing once per call. A polling endpoint that should not light up the spinner can opt out with global: false, which is far cleaner than trying to suppress the event from the other side.

Global handlers are also the natural home for cross-cutting transport concerns: a trace header on every request via ajaxSend, one place that reports 401s to the auth layer via ajaxError, or a counter that logs how many requests an interaction triggers. Because they sit on document, they can be bound and unbound per view with a namespace, and they see the merged settings object so they know which URL failed.

Aborting and upload progress

jqXHR.abort() cancels the request and rejects the promise with the text status "abort", which the failure table above already tells you to swallow silently. The common pattern is to store the handle on the element that owns the operation and abort before starting a replacement, so a fast typist does not race two responses into one results list.

Upload progress needs the underlying XHR object, because the progress event lives on xhr.upload and jQuery does not surface it. Supplying an xhr function that builds the transport and attaches a listener is the supported way in. For a FormData body you must set processData: false and contentType: false; without them jQuery tries to serialise the FormData and overwrite the multipart boundary the browser generated, and the upload arrives corrupted.

const upload = $.ajax({
  url: '/api/upload',
  method: 'POST',
  data: formData,
  processData: false,   // do not turn FormData into a query string
  contentType: false,   // let the browser set the multipart boundary
  xhr: function () {
    const xhr = new window.XMLHttpRequest();
    xhr.upload.addEventListener('progress', function (e) {
      if (e.lengthComputable) {
        const pct = e.loaded / e.total * 100;
        $('#bar').css('width', pct + '%');
      }
    });
    return xhr;
  }
});

$('#cancel').on('click', function () { upload.abort(); });
For a whole class of requests that share a concern, $.ajaxPrefilter() runs before the settings are merged and can rewrite them — the standard example is switching a JSON request to JSONP when the origin is unknown, or naming every request for logging. It is the least-known hook in the AJAX layer and the only one that can change dataType before the pipeline is chosen.

11 · jQuery UI and interaction widgets

11.1 Draggable, droppable, resizable and sortable11.2 Datepicker and autocomplete11.3 Dialog, accordion, tabs and slider11.4 Effects, easing and the widget factory

jQuery UI is a separate library of interactions, widgets and effects built on the widget factory. It has been in maintenance mode for years, yet it still ships inside thousands of admin panels — and the factory it introduced is the model every robust jQuery plugin in chapter 12 follows.

11.1 Draggable, droppable, resizable and sortable

The interactions are a small state machine layered over mouse and touch events, plus a class contract that gives your CSS hooks for every stage of a drag.

The interactions and the mouse plugin underneath

draggable, droppable, resizable, sortable and selectable are all built on the internal $.ui.mouse plugin, which normalises pointer events, tracks a drag threshold, and manages capture. That shared base is why the options rhyme across widgets: handle, containment, disabled, cursor, delay. draggable alone is rarely the goal; it becomes useful when paired with droppable, whose accept option filters the drags it will receive and whose hoverClass gives the target a visual state. revert: 'invalid' on the draggable is the usual pairing — a card that was dropped on nothing snaps back, which reads as a refusal without any error message.

Every interaction implements the same method interface: call the widget with 'enable', 'disable', 'option' or 'destroy' as a string. This is the widget factory contract, and it is why learning one widget teaches you the calling convention for all of them. There is also a keyboard-accessibility gap here: drag interactions are pointer-first, so a sortable list needs explicit up/down controls for anyone who cannot drag, and that is work the widget does not do for you.

$('.card').draggable({
  revert: 'invalid',      // snap back when dropped outside a target
  containment: 'document',
  stack: '.card',         // keep the dragged card on top
  cursor: 'grabbing'
});

$('#trash').droppable({
  accept: '.card',
  hoverClass: 'trash-hover',
  drop: function (event, ui) {
    const $card = ui.draggable;
    $card.fadeOut(150, function () { deleteCard($card.data('id')); });
  }
});

Sortable is a data-model problem

Sorting looks like a DOM trick and is really a persistence problem. The DOM order is the rendered truth; the server needs a durable order that survives a reload and does not depend on markup. The robust pattern gives each row a stable data-id, reads the order from the DOM on the update event, and posts that array. The server writes the sequence numbers, and the next render produces exactly the order the user sees. Sending the label or the index instead of a stable id is the classic mistake: rename a row and it jumps position.

The other failure mode is re-rendering the list in place. If your code rebuilds the inner HTML after every mutation, it destroys the sortable widget's cached item set, and dragging silently stops working. Calling $list.sortable('refresh') after the DOM changes re-reads the items and restores it; forgetting it produces the bug report that says "sorting works until you add a row".

$('#task-list').sortable({
  handle: '.drag-handle',
  placeholder: 'sortable-placeholder',
  axis: 'y',
  update: function () {
    const order = $(this).sortable('toArray', { attribute: 'data-id' });
    $.post('/tasks/reorder', { ids: order }).fail(function () {
      toast('Could not save the new order');
    });
  }
}).disableSelection();

11.2 Datepicker and autocomplete

The two form widgets carry most of jQuery UI's real-world traffic, and both hide a contract that is easy to get subtly wrong.

Datepicker and the timezone trap

datepicker is configured with dateFormat, minDate, maxDate, firstDay and, for anything non-trivial, beforeShowDay, which returns whether a day is selectable plus a CSS class and a tooltip. The trap is the value itself: the widget hands you a JavaScript Date at local midnight, and the input holds a formatted string. If you then call new Date(value) on a string like "2026-10-15", most engines parse it as UTC midnight, which shifts to the previous day west of Greenwich. Stay inside the widget's own helpers — $.datepicker.formatDate() and $.datepicker.parseDate() — or keep the string and never construct a Date from it.

Accessibility matters here too: the input needs a real <label>, and the picker's trigger should be a keyboard-reachable button, because a datepicker opened only by pointer is unusable for anyone driving the page from a keyboard.

Autocomplete and the source contract

autocomplete's source option accepts an array, a URL string, or a function that receives the request and a response callback. The function form is the only one that supports cancel-aware remote search, because it can inspect request.term and ignore stale results. minLength stops a request per keystroke, and select is where you write the hidden id as well as the visible label — returning false from select keeps the chosen label in the field instead of replacing it with the value.

The widget already manages role="listbox" and aria-autocomplete, so it is a reasonable accessibility baseline, but it is not the ARIA combobox pattern and behaves inconsistently with screen readers on mobile. If you need a guaranteed-accessible combobox in 2026, this is a case where a purpose-built component beats the legacy widget.

// datepicker
$('#due').datepicker({
  dateFormat: 'yy-mm-dd',
  minDate: 0,
  firstDay: 1,
  beforeShowDay: function (date) {
    return [date.getDay() !== 0, '', 'Closed on Sundays'];
  }
});

// autocomplete with a remote source
$('#customer').autocomplete({
  minLength: 2,
  source: function (request, response) {
    $.getJSON('/api/customers', { q: request.term }, response);
  },
  select: function (event, ui) {
    $('#customer-id').val(ui.item.id);
    return false;             // keep the selected label in the field
  },
  response: function (event, ui) {
    if (!ui.content.length) { $('#hint').text('No matches'); }
  }
});

11.3 Dialog, accordion, tabs and slider

The container widgets are where jQuery UI shows its age and its convenience at the same time: they are quick to wire up and expensive to leave in the DOM.

Dialog replaces alert and confirm

dialog is the widget people actually adopt, because it is the only way to ask a question in the page instead of the browser chrome. modal: true adds a backdrop and manages focus; the buttons array defines the actions; autoOpen: false plus .dialog('open') is the standard pattern. The failure mode is lifecycle: a dialog left initialised keeps a focus trap, a backdrop node and a set of delegated handlers alive. If the trigger can fire more than once, either open the same instance or destroy it in close, but do not re-initialise on an element that already has a dialog attached. And because a modal traps focus, it must also be the element that receives focus when opened, or a keyboard user is stranded behind the backdrop.

Accordion, tabs and slider

accordion toggles panels and exposes active, collapsible and heightStyle; tabs switches panels and reports the active index through the activate event; slider reports a value through slide while dragging and change when the drag ends. The events matter more than the options: slide fires continuously, so it should only update a readout, while change is the correct place to persist a value. Sending one request per slide tick is a reliable way to flood a server from a single gesture.

All three approach the same limitation as the rest of jQuery UI: they were designed for a mouse-first desktop and their keyboard and touch behaviour, while present, is not the equal of a modern component library. Use them when the project already ships jQuery UI; reach for something else in greenfield work.

const $dlg = $('#confirm').dialog({
  autoOpen: false,
  modal: true,
  resizable: false,
  width: 420,
  buttons: [
    { text: 'Cancel', click: function () { $(this).dialog('close'); } },
    { text: 'Delete', class: 'danger', click: function () {
        doDelete();
        $(this).dialog('close');
      }
    }
  ],
  close: function () { $(this).dialog('destroy'); }
});
$('#ask').on('click', function () { $dlg.dialog('open'); });

$('#tabs').tabs({ active: 0, collapsible: true });
$('#budget').slider({
  range: 'min',
  value: 30,
  slide: function (event, ui) { $('#out').text('$' + ui.value); },
  change: function (event, ui) { saveBudget(ui.value); }   // once per gesture
});

11.4 Effects, easing and the widget factory

jQuery UI extends the core effect system with named transitions and a swappable theme, and it introduces the widget factory that chapter 12 uses to build something reusable.

Extended easing and effect methods

Core jQuery animates with swing and linear. jQuery UI adds a family of easings — easeInOutBounce, easeOutBack, easeOutElastic and the rest — and additional effect names such as blind, bounce, clip, drop, fold, highlight, puff and shake. They are reachable through show(), hide(), toggle() and effect(). Every one of them is JavaScript-driven frame animation, which cannot use the compositor and will stutter under load; they are appropriate for small chrome, not for a page-sized transition. You can also register your own easing by adding a function to $.easing, which is a one-liner and often better than pulling in the whole easing pack.

$.extend($.easing, {
  easeOutBack: function (t) {
    const c1 = 1.70158, c3 = c1 + 1;
    return 1 + c3 * Math.pow(t - 1, 3) + c1 * Math.pow(t - 1, 2);
  }
});

$('#panel').show('drop', { direction: 'up' }, 400, 'easeOutBack');
$('#msg').effect('highlight', { color: '#ffe08a' }, 900);

ThemeRoller and why you subclass, not restyle

Every jQuery UI widget is styled through a fixed class vocabulary — ui-widget, ui-state-default, ui-state-active, ui-state-disabled, ui-corner-all. ThemeRoller writes a stylesheet that defines those classes for one theme, and swapping the stylesheet re-skins every widget at once. That is the intended way to theme the library. Overriding a single widget with extra CSS is where projects get lost: the base rules are numerous and often more specific than they look, so a bespoke rule needs matching specificity and quickly becomes a fight.

When the change is behavioural rather than cosmetic, the widget factory is the answer: you extend the existing widget, override one method, and call this._super() to keep the original behaviour. That is exactly the mechanism chapter 12 generalises into a plugin pattern, and it is the single most transferable idea jQuery UI ever produced.

jQuery UI 1.13 was the last feature release and 1.14 is a compatibility release that drops legacy Internet Explorer support. The project is in maintenance, not development: bugs are fixed and security issues are patched, but new widgets are not coming. Treat it as a stable dependency to plan around, not a platform to build on.

12 · Writing robust plugins and the widget factory

12.1 $.fn extension patterns and method dispatch12.2 Options, defaults and per-element data12.3 Chaining, namespaced events and teardown12.4 The $.widget() lifecycle and common pitfalls

A plugin that only works on the page it was written for is a function. A plugin is a reusable contract: it initialises once, merges options, stores state, exposes methods, removes everything it added, and never leaks a global. This chapter is the difference between the two.

12.1 $.fn extension patterns and method dispatch

Extending $.fn adds your method to every jQuery object, which is powerful and easy to get wrong in two specific ways.

The this.each contract

A $.fn method may be called on a set of one, ten or zero elements. The contract is simple: iterate with this.each(), operate on each element, and return the original set so the call chains. Two rules follow from it. First, never assume this is a single element — this[0] works in the demo and fails the first time someone selects a class. Second, each is a loop, so anything that does not depend on the element — building a lookup table, reading options — happens once outside it, not once per element.

Wrapping the whole plugin in an immediately-invoked function that receives jQuery keeps the helper functions and defaults private and makes the plugin safe under $.noConflict(), where the global $ may belong to something else.

(function ($) {
  'use strict';

  const DEFAULTS = { speed: 200, prefix: 'Count: ', separator: ',' };

  function format(n, opts) {
    return opts.prefix + n.toLocaleString('en-US');
  }

  $.fn.counter = function (options) {
    const opts = $.extend({}, DEFAULTS, options);

    return this.each(function () {
      const $el = $(this);
      if ($el.data('counter')) { return; }     // idempotent init
      $el.data('counter', { value: 0, opts: opts });
      $el.text(format(0, opts));
    });
  };
})(jQuery);

Method dispatch and honest errors

A plugin that grows beyond options almost always grows methods too — refresh, destroy, value. The convention is to overload the first argument: if it is a string, treat it as a method name and dispatch; otherwise treat it as options. When the string is unknown, throw with $.error() rather than failing silently, because a typo that does nothing is much harder to find than an exception with a message. Returning this from the options path and the method's own value from the dispatch path keeps both the fluent style and the ability to read a result back.

The subtlety is that a method call on a multi-element set is ambiguous: it has to pick one element to operate on. this.eq(0) — the first element — is the conventional choice, and the documentation should say so plainly rather than pretending the method is set-wide.

$.fn.counter = function (methodOrOptions) {
  const args = Array.prototype.slice.call(arguments, 1);

  if (typeof methodOrOptions === 'string') {
    const state = this.eq(0).data('counter');
    if (!state || typeof state[methodOrOptions] !== 'function') {
      $.error('counter: no such method "' + methodOrOptions + '"');
    }
    const result = state[methodOrOptions].apply(state, args);
    return result === undefined ? this : result;   // keep chaining
  }

  const opts = $.extend({}, DEFAULTS, methodOrOptions);
  return this.each(function () { initCounter($(this), opts); });
};

// call site
$('.badge').counter();                       // initialise
$('.badge').counter('refresh');              // dispatch
$('.badge').counter({ prefix: 'Total: ' });  // re-init options

12.2 Options, defaults and per-element data

Options are how a plugin is configured and data is how it remembers; conflating the two is the root of most plugin state bugs.

Merge into a fresh object, never into the defaults

$.extend({}, DEFAULTS, options) is the correct call: the empty object is the target, the shared defaults are copied into it, and the user's options win. Writing $.extend(DEFAULTS, options) mutates the module-level defaults, so the second instance inherits the first instance's options. That bug is invisible with one instance and reproduces instantly with two. The defaults object itself must be created once, outside the plugin function, or you allocate a new one on every call for no reason.

Deep merging with $.extend(true, {}, DEFAULTS, options) is occasionally right for a nested configuration object, but it merges arrays element by element, which is almost never what a caller means. If an option is a list — accepted file types, animation steps — mark it as replace-not-merge in your own code and copy it wholesale.

State belongs in .data()

Per-element state goes in $el.data('pluginName', instance), not in an expando property on the DOM node and not in a closure keyed by index. .data() is stored per element, survives detaching and reattaching, is reachable from outside the plugin for debugging, and is removed by .removeData() in your teardown. It is also the standard way to make initialisation idempotent: if $el.data('pluginName') already exists, either return early or apply the new options to the existing instance instead of building a second one.

One caution: data- attributes are read once and then shadowed by the in-memory store. Setting data-counter="5" after the plugin has written its own value will not overwrite it, because .data() prefers what it has over what the attribute now says. Choose one source of truth and stick to it.

// options: fresh object, defaults copied in, caller wins
const opts = $.extend({}, DEFAULTS, options);        // right
$.extend(DEFAULTS, options);                          // wrong: mutates shared defaults
const nested = $.extend(true, {}, { retry: { count: 3 } }, options); // deep, rarely needed

// state: one handle per element, kept in .data()
function initCounter($el, opts) {
  const state = {
    value: 0,
    step: opts.step,
    bump: function (n) {
      this.value += n * this.step;
      $el.text(format(this.value, opts));
      $el.trigger('counter:change', [this.value]);
    }
  };
  $el.data('counter', state);
  $el.text(format(0, opts));
}

// later, from anywhere:
const state = $('#total').data('counter');
if (state) { state.bump(2); }

12.3 Chaining, namespaced events and teardown

A plugin that adds handlers must be able to remove exactly those handlers. Namespaces are the mechanism, and a destroy method is the promise.

Namespaced events make removal surgical

Appending .myPlugin to an event name creates a namespace. $el.on('click.myPlugin', fn) and later $el.off('.myPlugin') removes only the handlers that carry that namespace, leaving every other click handler on the element untouched. Without a namespace, .off('click') is a sledgehammer that silently breaks unrelated code — the classic "my plugin disabled the other plugin's button" report.

Namespaces also let you bind several events in one call with one teardown: .on('scroll.ns resize.ns', fn) and .off('.ns'). They are not hierarchical in the sense that .a.b means "both"; a handler bound as click.a.b is removed by .off('.a') or .off('.b') or .off('.a.b'). That is convenient and worth knowing before you nest namespaces carelessly.

Custom events as the plugin's public API

Triggering a namespaced custom event — $el.trigger('counter:change', [value]) — turns a plugin from a black box into something a page can react to without reaching into its internals. The extra-arguments array is passed to the handler after the event object, and because the event bubbles by default, a container can listen for its children's changes. This is the same idea as a modern component's emit, implemented in the events chapter you already have. Pair it with a destroy that removes the namespace and the data, and the plugin becomes genuinely removable rather than merely stoppable.

$.fn.scrollSpy = function (options) {
  const opts = $.extend({ offset: 80, active: 'is-active' }, options);

  return this.each(function () {
    const $win = $(window);
    const ns = '.scrollSpy';          // one namespace for every handler

    $win.on('scroll' + ns + ' resize' + ns, function () { update($(this).scrollTop()); });
    $(this).one('remove' + ns, function () { $win.off(ns); });
  });
};

// announce a change; page code reacts without knowing the internals
$el.trigger('counter:change', [state.value]);
$('#totals').on('counter:change', '.badge', function (event, value) {
  console.log('a badge changed to ' + value);
});

// destroy(): undo exactly what create() did
$.fn.counter.destroy = function () {
  return this.each(function () {
    const $el = $(this);
    $el.off('.counter').removeData('counter');
  });
};

// teardown from anywhere, without touching other listeners
$(window).off('.scrollSpy');

12.4 The $.widget() lifecycle and common pitfalls

The widget factory — inherited from jQuery UI — is a full plugin framework: option handling, method dispatch, event namespacing and a documented lifecycle, all in one factory call.

The lifecycle: _create, _setOption and _destroy

Calling $.widget('ns.name', prototype) does four things at once: it registers the widget, creates $.fn.name so $el.name() initialises it, stores the instance on the element under the key 'ns-name', and wires up method dispatch. Inside the methods, this is the instance: this.element is the wrapped element, this.options is the merged option set, this.namespace and this.widgetFullName identify it, this._on() binds handlers that are removed automatically on destroy, and this._trigger() fires the widget's lifecycle events.

The lifecycle is fixed. _create runs once with the current options; _init runs after _create and again whenever the widget is re-invoked without new options; _setOption receives every option call and must call this._super(key, value) so the value is actually stored; _destroy removes everything and should call this._super() when extending. Getting the sequence wrong is the source of the "options are ignored after the first call" class of bug.

$.widget('ams.keypad', {
  options: { keys: [1, 2, 3, 4, 5, 6, 7, 8, 9, 0], maxLength: 6, value: '' },

  _create: function () {
    this._on(this.element, { keydown: '_onKeydown' });
    this._refresh();
  },

  _onKeydown: function (event) {
    const key = String.fromCharCode(event.which);
    if (this.options.keys.indexOf(Number(key)) === -1) { return; }
    if (this.options.value.length >= this.options.maxLength) { return; }
    this._setOption('value', this.options.value + key);
    return false;
  },

  _setOption: function (key, value) {
    this._super(key, value);            // store it first
    if (key === 'value' || key === 'keys') { this._refresh(); }
  },

  _refresh: function () {
    this.element.text(this.options.value || '—');
    this._trigger('change', null, { value: this.options.value });
  },

  _destroy: function () {
    this.element.off('.keypad');
  }
});

// init, then call methods through the same function
$('#pin').keypad({ maxLength: 4 });
$('#pin').keypad('option', 'maxLength', 8);
$('#pin').keypad('destroy');

The pitfalls that bite every widget author

PitfallWhy it happensFix

The widget factory is available on its own as jquery-ui/widget in npm builds, without the rest of jQuery UI. If you want the lifecycle without the widgets, that is the smallest way to get it — or reach for a modern web component, which gives you the same encapsulation with the browser's own upgrade mechanism.

13 · Migrating off jQuery and performance

13.1 Measuring and optimising selectors13.2 Caching, detaching and batch DOM edits13.3 Event delegation versus direct binding13.4 jQuery Migrate and a phased migration path13.5 When jQuery is still the right tool

jQuery is not slow; unmeasured code is. This chapter is about the handful of patterns that actually move a frame budget, and about the two migration paths — incremental and rewrite — with the tools that make the incremental one safe.

13.1 Measuring and optimising selectors

The cost of a selector is the DOM traversal it performs, not the function call. Repeating a wide selector in a loop is the single most common performance defect in jQuery code.

What a selector actually costs

jQuery 3 routes nearly every selector through the browser's native querySelectorAll, falling back to its own Sizzle engine only for jQuery-specific pseudo-selectors such as :visible, :hidden, :animated, :eq and :contains. Those fallbacks are the expensive ones: they force jQuery to collect candidates and filter them in JavaScript, and they cannot be cached by the browser. On a document of a hundred thousand nodes, $('div:visible') walks the whole tree. Prefer a class you control: $('.is-visible') is a single native scan.

Because CSS selectors are matched right to left, $('#app .row td .label') starts from every .label in the page and climbs, not from #app downwards. Narrowing the left side of a selector helps the browser skip subtrees, but the reliable win is the one below: scope the query.

Cache the set and pass a context

Every $(...) call builds a new jQuery object and resolves the selector against the document unless you give it a context. In a loop, that is a fresh traversal per iteration. Hoisting the lookup out of the loop, and passing a cached ancestor as the second argument, turns N traversals into one plus N local scans.

The cost of a jQuery object is also worth remembering: wrapping an element is cheap relative to traversal but not free, so a hot loop that calls $(this) repeatedly inside each is doing avoidable work. Read the node once into a variable and reuse it. None of this matters at ten elements and all of it matters at ten thousand, which is why the profiler comes first.

// slow: a jQuery-only pseudo-selector cannot use querySelectorAll
$('li:visible').addClass('stale');

// faster: a class you control is a single native scan
$('li.is-visible').addClass('stale');

// scope once, reuse the set, avoid re-resolving per iteration
const $panel = $('#app');
const $labels = $panel.find('td .label');
$labels.addClass('stale');
Do not micro-optimise by hand. Before changing anything, profile: open the performance panel, record the interaction, and read the self-time under jQuery's own frames. Most "jQuery is slow" reports turn out to be one selector inside a scroll handler, one layout read in a loop, or an animation that should have been a CSS transition — all three of which this chapter covers. Optimising a selector that runs twice per page is wasted effort.

13.2 Caching, detaching and batch DOM edits

The DOM is not slow to read or write; it is slow when reads and writes are interleaved, because each read forces the browser to recompute layout after the write.

detach() is not hide()

hide() leaves the element in the document, so every style change on it still participates in layout and paint. detach() removes the subtree from the document while keeping its data and event handlers, so edits inside it touch nothing the browser is rendering. Append it back when the batch is done and there is one reflow instead of one per row. The distinction between remove() and detach() matters here: remove() discards the handlers and data, detach() keeps them.

DocumentFragment achieves the same for construction. Building nodes against a fragment and inserting it once is the classic answer to "appending a thousand rows takes four seconds", and it composes with jQuery because append accepts a fragment. For a large grid, the fastest option of all is usually to build one HTML string and assign it in a single write — provided every value is escaped, which is the security cost of that approach.

// batch edits off-DOM: one reflow instead of one per row
const $list = $('#list').detach();

rows.forEach(function (row) {
  $('<li>').text(row.label).attr('data-id', row.id).appendTo($list);
});

$list.appendTo('#panel');

Read, then write

Layout thrashing happens when a write is followed by a read of a property the browser has to re-layout to measure — offsetHeight, getBoundingClientRect(), scrollTop, and the computed styles jQuery reads for some of its effects. The fix is a simple discipline: collect every measurement first into plain variables, then perform every write. A loop that alternates $el.width() and $el.css(...) performs one forced layout per iteration; separated, it performs one.

Two more habits follow from the same principle. Prefer one class toggle to many inline style writes, because a class change is a single style recalculation and inline styles accumulate specificity debt. And route continuous visual changes — hover, focus, a progress bar — through CSS transitions or requestAnimationFrame, never through a jQuery animation on every scroll event.

// thrashing: each width() forces layout after the previous write
$('.cell').each(function () {
  const w = $(this).width();          // read -> layout
  $(this).css('height', w / 2);       // write
});

// batched: all reads, then all writes
const widths = $('.cell').map(function () { return $(this).width(); }).get();
$('.cell').each(function (i) { $(this).css('height', widths[i] / 2); });

13.3 Event delegation versus direct binding

Delegation is not an optimisation you apply everywhere; it is a choice with a specific win and a specific failure mode.

How delegation works, and what it buys

A delegated handler is bound to an ancestor and given a selector. When any descendant event bubbles up, jQuery walks the path from the target outward and tests each element against the selector, then calls the handler with this set to the matching element and event.delegateTarget set to the ancestor. Two things follow: one handler covers every current row and every row added later, and replacing the container's inner HTML cannot orphan the handler. In a list that re-renders after every AJAX call, that is the whole reason to delegate.

When direct binding wins

Delegation adds a match test per event per ancestor, so for a fixed, small set of elements that never change, a direct binding is cheaper and simpler. More importantly, delegation depends on the event bubbling. A child that calls event.stopPropagation() prevents the ancestor from ever seeing the event, and delegation is then silently dead — a failure that looks like "the click handler stopped working on one row". Focus-sensitive events are the other exception: focus, blur, mouseenter and mouseleave do not bubble, so jQuery simulates them when you delegate; the emulation is good but not free.

The rule of thumb: delegate on a stable ancestor when the content is dynamic, use direct binding on a static widget, and never mix stopPropagation into a page that relies on delegation. Namespace every handler you bind so teardown stays surgical, and prefer focusin/focusout when you genuinely need delegated focus handling.

// direct: one handler per row, and new rows need re-binding
$('#list li').on('click', handler);

// delegated: one handler on the container, works for future rows too
$('#list').on('click', 'li', handler);

// delegated teardown removes only this selector's bindings
$('#list').off('click', 'li');

// namespaced, multiple events, one handler
$('#editor').on('focusin.ns focusout.ns', 'input', function () {
  $(this).toggleClass('editing');
});
$('#editor').off('.ns');

13.4 jQuery Migrate and a phased migration path

Migrate is a diagnostic shim, not a compatibility layer to ship. It tells you precisely which lines depend on removed behaviour. The migration itself is a sequence of small, reversible steps.

What jQuery Migrate does

jQuery Migrate restores APIs removed by newer jQuery versions and logs a warning for each use, including the call stack that leads to it. Loading it after jQuery, running the application through its test pass, and reading the console is the cheapest audit you can do of an unfamiliar codebase's jQuery surface. In current builds you can silence the per-warning traces once the list is known, and you must remember to remove Migrate before shipping: any code that still depends on it will break at the next major upgrade.

The warning list is the deliverable, not the shim. Each entry names a removed API and the file that calls it, which converts "we should modernise someday" into a finite, ordered task list that can be estimated and assigned.

The phased path

Migrating a real application is not a rewrite; it is a measured sequence where every step is shippable. The order matters because each step de-risks the next.

#StepWhy it is safe here
1Inventory plugins and $.fn usageAnything not written in-house is the long pole; find it before committing to a plan
2Pin jQuery to the current 3.x releaseRemoves version drift so behaviour is reproducible
3Add Migrate and capture the warning listNo production change; the log becomes the task list
4Fix the warnings, then remove MigrateEach fix is small and independently testable
5Replace or wrap third-party pluginsEither a maintained fork or a thin native shim
6Introduce a module boundary around jQueryOne import point makes the next step mechanical
7Rewrite feature by feature to native or a frameworkOnly reached once the surface is small and known

The native equivalents you will use

Most of jQuery's daily surface has a one-line native twin, and recognising the mapping is what makes step 7 feel routine rather than risky. What does not have a twin is the accumulated value of the plugins, the forgiving cross-browser model, and the chainable animation queue — those are the parts worth an explicit decision.

// jQuery                          // native
$('#id');                           // document.getElementById('id')
$('.item');                         // document.querySelectorAll('.item')
$el.on('click', fn);                // el.addEventListener('click', fn)
$el.off('click', fn);               // el.removeEventListener('click', fn)
$el.addClass('on');                 // el.classList.add('on')
$el.toggleClass('on');              // el.classList.toggle('on')
$el.attr('href');                   // el.getAttribute('href')
$el.data('x');                      // el.dataset.x
$el.text('hi');                     // el.textContent = 'hi'
$el.hide();                         // el.hidden = true
$el.closest('.card');               // el.closest('.card')
$.ajax({ url, dataType: 'json' });  // fetch(url).then(r => r.json())

13.5 When jQuery is still the right tool

The migration calculus is not "old versus new". It is the size of the plugin surface, the shape of the rendering model, and the cost of the rewrite measured against the benefit.

Server-rendered pages and progressive enhancement

jQuery was designed for HTML produced by the server with behaviour layered on top, and that architecture has not stopped being a good one. On a server-rendered page, $(...) is a compact way to select and mutate existing markup, $.ajax has a request pipeline that fetch still makes you assemble by hand — JSON parsing, timeouts, encoding, progress — and the plugin ecosystem covers the dusty corners. A small administrative page with a table, a modal and a form gains very little from a rewrite and can lose a week to it.

Legacy constraints and plugin dependence

A CMS theme that loads jQuery, a page that depends on a datepicker whose only maintained version is a jQuery plugin, or an environment where the build tooling is fixed all point the same way: the library is not the problem being solved. jQuery 3.x is maintained and receives security fixes; the cost that genuinely matters is the shipped weight and the extra mental model, not correctness. Measure those before spending a rewrite on them.

The decision table

SituationReasonable choice
Server-rendered page, a few interactionsKeep jQuery; it is smaller than the rewrite
Heavy client-side state, frequent re-rendersMigrate to a framework; manual DOM sync is the actual bug source
Duplicated state across the DOM and JSFramework, or at minimum a single state object and a render function
One plugin is the only dependencyReplace that plugin with a native or framework equivalent; drop jQuery
Team knows vanilla JS and the surface is smallIncremental native replacement, no big-bang
Bundle size is the driver on a content siteDrop jQuery after step 4 of the migration table, not before
Legacy browser support is contractualKeep jQuery 3.x; jQuery 4 drops support you may still owe
The honest summary: jQuery's remaining advantage is the breadth of its plugin ecosystem and the ergonomics of DOM-plus-AJAX on server-rendered pages. Its cost is roughly 30 KB gzipped, an extra abstraction over the DOM, and a rendering model that cannot keep a large interactive UI in sync. Choose by measuring which side of that line the project sits on, not by the year on the calendar.
