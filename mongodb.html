Welcome — How to Use This MongoDB Guide

How this guide is organisedThe right mindsetTools you will use all course long

This guide teaches MongoDB from the ground up, starting with a single document and ending with sharded clusters and Node.js applications, all readable offline. Work through the twelve chapters in order and run each mongosh command yourself so the syntax becomes automatic. Every chapter builds on the previous one, so typing the code reinforces each concept before you move on.

This is a complete, self-paced path through MongoDB, from your first document to production operations and Mongoose applications. Everything runs in a single HTML file — no internet required, progress is saved in your browser.

How this guide is organised

The guide is split into three parts: fundamentals, advanced database features, and application development with Node.js. Every chapter opens by naming what you will achieve, then leads you through short worked examples in mongosh. Each chapter ends with copy-ready code blocks that you should retype yourself to build muscle memory.

  • Part I (Ch. 1–6) — foundations: the document model, BSON, CRUD, queries, indexes and the aggregation framework.
  • Part II (Ch. 7–9) — design and scale: schema design, transactions, replication and sharding.
  • Part III (Ch. 10–11) — applications and operations: MongoDB with Node and Mongoose, security, backups and monitoring.
  • Every chapter ends with exercises. Code is copy-ready; type it rather than pasting to build muscle memory.

The right mindset

The core idea is to model your data for how you will query it, not for how relational tables are numbered. Before choosing embedding or referencing, ask what reads your application performs most often. This query-first thinking drives every schema decision in the rest of the guide.

MongoDB rewards thinking in documents, not tables. You design the shape of a document around the queries your application actually runs, then verify with explain() and indexes. Learn to ask "what does a page in my app need?" before you model anything.

Keep the official docs open beside this guide at mongodb.com/docs. This guide explains the why and the sequence; the docs are the exhaustive reference.

Tools you will use all course long

You will rely on the MongoDB Shell (mongosh) for interactive learning, MongoDB Compass for visual inspection, and MongoDB Atlas for a hosted cluster. Install them once at the start and they carry you through every chapter. The guide shows you exactly when and how each tool is used.

1 · MongoDB Fundamentals & Setup

1.1 The document model vs the relational model1.2 Databases and collections1.3 Running MongoDB locally and on Atlas1.4 mongosh basics1.5 A CRUD-first tour

This chapter gets MongoDB running on your machine and introduces the document model, databases, collections, and a first CRUD tour. You install mongod locally or create an Atlas cluster, then connect with mongosh. By the end you have live documents in a working database and can insert and read data yourself.

MongoDB is a document database: data lives in JSON-like documents inside collections instead of rigid table rows. This chapter gets a server running, explains where the model differs from SQL, and walks your first CRUD operations.

1.1 The document model vs the relational model

Documents map closely to the objects your application already works with, while relational tables split data across rows and foreign keys. The comparison shows why embedding related fields is natural and where joins used to come from. Understanding this trade-off explains almost every later design decision in the guide.

Relational (SQL)Document (MongoDB)
A fixed table schema with columnsFlexible documents; each can vary in fields
Rows joined across tables via foreign keysRelated data embedded in, or referenced from, one document
Schema changes need migrationsNew fields are just new fields in new documents
Transactions span tablesOperations are atomic per document; multi-doc transactions exist too
Normalised by defaultModel data for the queries you run

Relational databases normalise to avoid redundancy; document databases shape data to match application reads, accepting some duplication as the price of fast, simple queries.

1.2 Databases and collections

A database is the top-level container and holds one or more collections, and each collection stores many similar documents. You create them implicitly by inserting, since neither exists until data arrives. The naming and sizing rules here shape how you organise everything that follows.

mongosh                        # connect to mongodb://localhost:27017
use shop                       # select the shop database (created lazily)
db.getName()                   // -> shop
show dbs                       # only non-empty databases appear
show collections               # collections in the current database
```
Not valid: this is a comment; run the real commands in mongosh.

mongosh connects to the local server, use switches or lazily creates a database, and nothing appears in show dbs until it holds data.

Nothing is physically created until you write your first document. MongoDB creates databases and collections lazily on first insert.

1.3 Running MongoDB locally and on Atlas

You can run MongoDB locally with the mongod server binary or use the hosted MongoDB Atlas service. Locally you start mongod and connect to mongodb://localhost:27017 with mongosh. On Atlas you create a cluster, whitelist your IP, and use the generated connection string, so you finish with a working connection either way.

# Local install on macOS with Homebrew
brew tap mongodb/brew
brew install mongodb-community@8.0

# Start MongoDB as a background service
brew services start mongodb-community@8.0

# Or run mongod directly with an explicit data path
mongod --dbpath /data/db --bind_ip 127.0.0.1

The package manager installs mongod, brew services keeps it running in the background, and mongod --dbpath lets you run a server manually pointing at a data directory.

# Altas: create a free cluster, then paste its connection string into mongosh
mongosh "mongodb+srv://alice:PASSWORD@cluster0.example.mongodb.net/shop?retryWrites=true"

Atlas hands you a connection string with the srv prefix that mongosh or your driver uses to reach the hosted cluster over TLS.

1.4 mongosh basics

mongosh is the interactive JavaScript shell for MongoDB, and this lesson covers its most useful built-in helpers. You will use show dbs, show collections, db, and use, plus help to inspect the current state. Learning to drive the shell is learning to drive MongoDB itself.

help                       # built-in summary of shell commands
db.help()                  # methods available on a database object
db.products.help()         # methods on a collection
show users                 # users in the current database
db.stats()                 # sizes and counts for the current database

These helpers summarise everything the shell can do and report current database state, so they are the natural starting point when you are stuck.

1.5 A CRUD-first tour

This tour runs each CRUD operation once in sequence: insertOne, find, updateOne, and deleteOne. You see how a filter selects documents and how each verb transforms the collection. This is the exact shape the next two chapters expand into full detail.

db.products.insertOne({ name: 'Notebook', price: 4, tags: ['office', 'paper'] })
db.products.find({})                       # read: every product in the collection
db.products.updateOne(
  { name: 'Notebook' },
  { $inc: { price: 1 } }                   # update: raise the price by 1
)
db.products.deleteOne({ name: 'Notebook' })   # delete: remove exactly one match
db.products.countDocuments({})             # how many rows remain

This tour shows the four verbs: insertOne, find, updateOne with an update operator, and deleteOne — the pattern you will repeat in every MongoDB application.

2 · Documents & BSON Types

2.1 From JSON to BSON2.2 _id and ObjectId2.3 Embedded documents vs references2.4 Arrays and dates2.5 Type coercion, flexible schema and limits

This chapter explains how documents are physically stored as BSON, the special role of the _id field and ObjectId, and how to embed data inside documents. Everything you type in JSON later becomes typed BSON values on disk. This is the vocabulary every query in the rest of the guide is written in.

Every document is BSON: a binary form of JSON with extra native types — dates, ObjectIds, and numbers. This chapter explains those types, the mandatory _id field, and how embedded subdocuments and arrays are represented.

2.1 From JSON to BSON

BSON is the binary-encoded JSON format MongoDB stores documents in, adding features plain JSON cannot express. It supplies typed values such as 32-bit and 64-bit integers, doubles, dates, and ObjectId. Knowing how the shell renders these types helps you interpret query results accurately.

JSON typeBSON addsExample
string—"Ada"
numberint (32-bit), long (64-bit), double42, NumberLong("9000000000")
—datenew Date("2026-09-18T12:00:00Z")
—ObjectIdObjectId("6650e3c9f1a2b3c4d5e6f708")
objectembedded subdocuments{ address: { city: "London" } }
array—[1, 2, 3]
—binary / regex / decimal128 / UUIDBinData(0, "...")

The shell hides most of this, but knowing the underlying types explains why a number queried as an integer does not match a stored double.

2.2 _id and ObjectId

Every document must have an _id field, which is automatically generated as an ObjectId when you insert. The ObjectId is a 12-byte value combining a timestamp, machine identifier, process id, and counter, so it is unique without coordination. You should treat _id as immutable and index it, since MongoDB already maintains a unique index on it.

db.users.insertOne({ name: 'Ada' })          // Mongo adds _id: ObjectId(...) for you
const u = db.users.findOne({ name: 'Ada' })
u._id instanceof ObjectId                    // true
u._id.getTimestamp()                         // when the ObjectId was generated
u._id.toString()                             // the well-known 24-hex-digit string
// You may supply your own _id: a string, number, or anything immutable
db.users.insertOne({ _id: 'u-42', name: 'Lin' })

If you omit _id, MongoDB generates an ObjectId that embeds a timestamp and machine identifier, making it roughly sortable by creation time; you can also supply your own unique _id.

Never change _id once a document exists. MongoDB indexes it and treats it as immutable; "renaming" a document means a new insert plus a delete.

2.3 Embedded documents vs references

You represent related data either by embedding subdocuments or arrays inside a document or by storing a reference to another document’s _id. Embedded data is read in a single round trip and keeps related fields together. References keep related data separate and require either the aggregation $lookup stage or a second query to join.

// Embedded: order lines live inside the order document
db.orders.insertOne({
  _id: ObjectId(),
  status: 'placed',
  items: [
    { sku: 'nbk-100', qty: 2, price: 4 },
    { sku: 'pen-200', qty: 5, price: 1.5 }
  ]
})

// Referenced: the customer lives in its own collection, pointed to by ObjectId
db.orders.insertOne({ customerId: ObjectId('6650e3c9f1a2b3c4d5e6f708'), total: 15.5 })

The first order embeds its line items so one read returns the whole order, while the second references a customer so it must be resolved with an extra lookup.

2.4 Arrays and dates

Arrays store list-shaped fields naturally, and BSON dates are Date objects that sort and range-query correctly. You can push into arrays with $push and query them with $in, $all, and $elemMatch. These two types cover most of the "list of things" data real documents need.

db.events.insertOne({
  title: 'Release party',
  startsAt: new Date('2026-06-01T20:00:00Z'),   // stored as ms since the Unix epoch
  attendees: ['ada', 'linus', 'grace']
})

db.events.updateOne(
  { title: 'Release party' },
  { $push: { attendees: 'alonzo' } }           // append one value to the array
)

db.events.find({ startsAt: { $lt: new Date() } })   // events already started

Arrays store repeating values and get $push/$pull operators, while BSON dates sort and compare like numbers — perfect for range queries.

2.5 Type coercion, flexible schema and limits

Documents are capped at 16 megabytes, field names count toward the size, and the order of fields is preserved as stored. Flexible schema still demands discipline because type coercion can silently change a number to a string. These practical constraints guide how you name fields and choose data types.

db.runCommand({ collStats: 'users' })       // size, avgObjSize, and index stats
db.users.find({ age: 25 })                  // matches 25 but NOT NumberLong(25) or "25"
// Because types matter, normalise how your app writes numbers.

collStats reports storage facts, and the find example shows why type coercion rules matter: an int 25, a long 25, and the string "25" are three different values.

Each document is capped at 16 MB and a field name repeats in every document, so short field names shrink the collection. Discipline comes from your application layer or schema validation.

3 · CRUD Operations

3.1 Inserting documents3.2 Reading documents with find3.3 Updating with $set, $inc, $push and $pull3.4 replaceOne, upserts and deletes3.5 bulkWrite and findOneAndUpdate

This chapter covers the full CRUD surface: insertOne and insertMany, find, updateOne with $set and $inc, replaceOne, deleteOne and deleteMany, plus upserts and bulkWrite. Each operation is a real mongosh command you run yourself. These seven verbs are the entire CRUD toolkit you will ever need.

CRUD in MongoDB is a small set of well-named methods, most of them plural or singular versions of the same idea. This chapter runs each one and explains the update operators that make updates fast.

3.1 Inserting documents

insertOne inserts a single document and insertMany inserts an array of documents in one call. Each returns an insertedId in the result, and writes are atomic per document. Use insertMany for bulk loading while staying under the 16-megabyte document and message size limits.

const result = db.products.insertOne({ name: 'Stapler', price: 8 })
result.insertedId                          // the generated or supplied _id

db.products.insertMany([
  { name: 'Ruler', price: 2 },
  { name: 'Pencil', price: 1 },
  { name: 'Pen', price: 1.5 }
], { ordered: false })   // continue inserting even if one document fails

insertOne and insertMany both return the ids they wrote, and the ordered option lets a failed batch keep going instead of stopping at the first error.

3.2 Reading documents with find

find filters documents using a query document, and an empty filter returns every document in the collection. It returns a cursor rather than an array, so you must iterate with forEach, next, or toArray to fetch results. Optional projection and sort apply before results stream back.

db.products.find({ price: { $lt: 5 } })      // matches priced under 5
db.products.find({})                         // every document
const cur = db.products.find({})
cur.toArray()                                // pull everything into memory
cur.count()                                  // number of matching documents
db.products.findOne({ name: 'Ruler' })       // exactly one document, or null

find builds a cursor you can iterate, count, or materialise with toArray, while findOne is the convenience form for "give me the first match".

3.3 Updating with $set, $inc, $push and $pull

updateOne applies update operators to the first matching document, and updateMany applies them to all matches. The operators $set, $inc, $push, and $pull change only the named fields, leaving the rest of the document untouched. This targeted behaviour avoids rewriting the whole document on every change.

db.products.updateOne(
  { name: 'Ruler' },
  { $set: { price: 3, onSale: true } }       // set (or add) fields; others untouched
)

db.products.updateMany({}, { $inc: { price: 1 } })   // every product costs 1 more

db.parts.updateOne({ _id: 1 }, { $push: { revisions: 'v2' } })   // append to array
db.parts.updateOne({ _id: 1 }, { $pull: { revisions: 'v2' } })   // remove from array

$set patches fields, $inc adds atomically, and $push/$pull grow or shrink arrays — the operator style means no whole-document rewrite and no lost field races.

updateMany with no filter, or a broad one, lets you rename a field across a collection in one statement — a scheme for what would be a migration in SQL.

3.4 replaceOne, upserts and deletes

replaceOne swaps a whole document for a new one, while deleteOne and deleteMany remove documents by filter. The upsert option turns a failed update or replace into an insert when no match exists. Upsert therefore converts an update into an insert while keeping the filter in place.

db.products.replaceOne(
  { name: 'Ruler' },
  { name: 'Ruler', price: 3, material: 'steel' }   // the whole document is replaced
)

db.inventory.updateOne(
  { sku: 'nbk-100' },
  { $set: { qty: 3 } },
  { upsert: true }        // insert a fresh document if the filter matched nothing
)

db.products.deleteOne({ name: 'Ruler' })
db.products.deleteMany({})                        // empty the collection
db.products.drop()                                // drop collection and indexes

replaceOne swaps the whole document body, upsert inserts when nothing matches, and deleteOne/deleteMany remove one or all matches while drop removes the entire collection.

3.5 bulkWrite and findOneAndUpdate

bulkWrite batches insertOne, updateOne, replaceOne, and deleteOne operations into a single round trip for application-side efficiency. findOneAndUpdate returns the document as it was before or after the update and is atomic. Together these round out production CRUD beyond the basic verbs.

db.products.bulkWrite([
  { insertOne: { document: { name: 'Eraser', price: 1 } } },
  { updateOne: { filter: { name: 'Notebook' }, update: { $inc: { price: 1 } } } },
  { deleteOne: { filter: { name: 'Pen' } } }
], { ordered: true })    // stop at the first error, or false to keep going

const ticket = db.tickets.findOneAndUpdate(
  { status: 'open' },
  { $set: { status: 'claimed' } },
  { returnDocument: 'after' }    // default returns the pre-update document; 'after' returns the new one
)

bulkWrite sends a mixed batch of inserts, updates, and deletes in one request, and findOneAndUpdate grabs the claimed document while flipping its state in a single atomic step.

4 · Querying & Projection

4.1 Comparison and logical operators4.2 Membership, existence and type4.3 Dot notation for embedded fields4.4 Array queries: $elemMatch, $size, $all4.5 Regex, paging and projections

This chapter covers query operators, dot notation for embedded fields, array queries, regex, pagination, and projections. Queries combine comparison and logical operators with cursor methods like sort, skip, and limit. Filtering well is the difference between a correct app and a fast one.

A query filter is a document describing what to match, and every operator starts with a dollar sign. This chapter builds from comparison operators up to array matching and projection.

4.1 Comparison and logical operators

Comparison operators such as $eq, $ne, $gt, $gte, $lt, and $lte test values inside query filters. The logical operators $and, $or, and $not combine conditions into richer filters, with $and implicit between fields. These operators compose into almost every filter you will write.

db.products.find({ price: { $gt: 10, $lte: 50 } })        // 10 < price <= 50
db.products.find({ price: { $ne: 0 } })                    // anything priced non-zero
db.products.find({ name: { $eq: 'Ruler' } })              // same as { name: 'Ruler' }
db.products.find({
  $or: [ { price: { $lt: 5 } }, { onSale: true } ]        // cheap OR featured
})
db.products.find({ $and: [ { price: { $gt: 1 } }, { qty: { $gt: 0 } } ] })

Comparison operators sit inside a field, while $or and $and combine whole conditions; the implicit default is already "and", so the explicit $and shows the intent.

4.2 Membership, existence and type

$in tests whether a field equals any of a list of values, and $nin is its complement. $exists checks whether a field is present regardless of value, and $type matches the BSON type of a field. Together they answer "is the value one of these" and "does the field exist at all".

db.products.find({ sku: { $in: ['nbk-100', 'pen-200'] } })   // any listed value matches
db.products.find({ sku: { $nin: ['nbk-100'] } })            // exclusive membership
db.users.find({ emailVerified: { $exists: true } })          // field must be present
db.users.find({ age: { $type: 'int' } })                     // only 32-bit integers
db.users.find({ tags: { $type: 'array' } })                  // field must be an array

$in/$nin test membership in a list, $exists checks a field’s presence (useful for schema drift), and $type queries by BSON type.

4.3 Dot notation for embedded fields

Dot notation addresses fields inside embedded documents and arrays of documents, for example address.city or items.price. It lets you query, project, and sort any depth of nested structure using a simple field path. This is the standard way to reach subdocument fields in MongoDB.

db.customers.insertOne({
  name: 'Ada',
  address: { city: 'London', zip: 'W1' }       // a subdocument
})
db.customers.find({ 'address.city': 'London' })

db.orders.find({ 'items.sku': 'nbk-100' })     // any element of the array matches

The quoted path 'address.city' descends into the subdocument, and 'items.sku' reaches inside every array element to find one matching sku.

4.4 Array queries: $elemMatch, $size, $all

When a plain dot query is not enough, you use the array-specific operators. $elemMatch requires a single array element to satisfy every condition in the expression, $size matches arrays of a given length, and $all matches arrays containing every listed element. These operators handle the tricky cases of querying inside arrays.

db.products.find({ tags: 'office' })                      // array contains the value
db.products.find({ tags: { $all: ['office', 'paper'] } }) // contains every listed value
db.products.find({ tags: { $size: 3 } })                  // exact array length
db.orders.find({
  items: { $elemMatch: { sku: 'nbk-100', qty: { $gte: 2 } } }   // one element satisfies BOTH
})

A bare value, $all and $size answer "contains", "contains all", and "that length", while $elemMatch requires a single array element to meet every condition at once.

4.5 Regex, paging and projections

Regex filters use the $regex operator to match patterns, and anchored patterns that start with a literal prefix can still use an index. Pagination uses cursor methods sort, skip, and limit. Projection documents keep or drop fields, cut transfer size, and can even allow a covered query.

db.users.find({ name: /^ada/i })                     // case-insensitive prefix
db.products.find({})
  .sort({ price: 1, name: 1 })    // ascending price, then ascending name
  .skip(20)                       // skip the first twenty (page 2)
  .limit(10)                      // return at most ten

A regex with an anchored prefix can still use an index, and sort, skip, and limit combine into page-based paging that matches the compound index shape.

db.orders.find(
  { customerId },
  { _id: 0, items: 1, total: 1, status: 1 }   // include these, drop _id
)
// Exclude style: everything except the big payload field
db.orders.find({}, { payload: 0 })

The second argument to find projects a subset — include with 1, exclude with 0 (mixing the two styles is not allowed) — shrinking what travels over the wire.

5 · Indexing & Performance

5.1 How indexes work and the _id index5.2 Creating single-field indexes5.3 Compound indexes5.4 Unique, sparse, partial and TTL indexes5.5 Covered queries and an index strategy

This chapter covers how indexes work, the always-present _id index, and creating single-field and compound indexes. You will also meet unique, sparse, partial, and TTL variants plus explain() to verify plans. This is where slow collection scans turn into fast indexed lookups.

Without indexes MongoDB scans every document. A good index turns a full collection scan into a direct lookup. This chapter shows how to create, inspect and prove the value of indexes.

5.1 How indexes work and the _id index

Indexes are B-tree structures that let MongoDB find and sort documents without scanning the whole collection. Every collection already has a unique index on _id that you cannot drop. Understanding the B-tree trade-off explains the write cost and disk space every additional index adds.

db.users.getIndexes()            // see every index on the collection
// Every collection ships with the unique index on _id:
// [ { "v": 2, "key": { "_id": 1 }, "name": "_id_" } ]
db.users.find({ _id: ... })      // answered straight from that index

getIndexes lists the collection’s indexes, and the mandatory _id index is why lookups by primary key never scan the collection.

5.2 Creating single-field indexes

You create an index with db.collection.createIndex({ field: 1 }) and an ascending or descending sort order. A query that filters on that field can then use the index instead of a collection scan. Indexes trade write overhead and disk for faster reads, so you should create only the ones queries actually need.

db.users.createIndex({ email: 1 })          // 1 = ascending, -1 = descending
db.users.find({ email: 'ada@example.com' }).explain('executionStats')
// executionStats.totalDocsExamined falls from N to 1 once the index exists

createIndex builds a lookup structure on email, and explain('executionStats') proves the win by showing how many documents the query actually examined.

5.3 Compound indexes

Compound indexes cover several fields, with the key order you list deciding which query shapes the index can serve. Equal-constraint fields should come before range or sort fields. The ESR rule (equality, sort, range) helps you pick the field order that best supports your queries.

db.orders.createIndex({ customerId: 1, createdAt: -1 })
// serves: filter by customerId, sort by createdAt
db.orders.find({ customerId }).sort({ createdAt: -1 })

db.orders.createIndex({ customerId: 1, status: 1, total: 1 })  // a "cover" candidate
db.orders.find(
  { customerId, status: 'open' },
  { _id: 0, total: 1 }          // every needed field lives in the index itself
)

Compound indexes follow a leftmost-prefix rule, so the same index serves different filters and sorts, and the last example reads entirely from the index.

5.4 Unique, sparse, partial and TTL indexes

The special index flavours each encode a rule in the database itself. A unique index rejects duplicate values, sparse indexes skip documents missing the field, partial indexes use a filter expression to index only matching documents, and TTL indexes expire documents after a set number of seconds. All four are created via createIndex options.

db.users.createIndex({ email: 1 }, { unique: true })          // reject duplicate emails

db.reviews.createIndex({ userId: 1 }, { sparse: true })       // skip docs lacking the field

db.orders.createIndex(
  { createdAt: 1 },
  { partialFilterExpression: { status: 'open' } }              // index only open orders
)

db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 })   // TTL: auto-delete after 1h

Unique enforces a constraint, sparse ignores missing fields, partial indexes a subset, and a TTL index makes MongoDB delete documents automatically after the stated seconds.

TTL indexes are the easiest correct way to expire sessions, notifications and logs. The background job that purges runs about every 60 seconds.

5.5 Covered queries and an index strategy

A practical strategy starts by identifying the read patterns with the highest frequency and impact, then builds indexes to serve them. You use explain() to confirm an index is actually used and check covering potential. Following this disciplined order beats guessing at indexes after a query is already slow.

  • Profile first: log slow queries (--slowms 100) or read explain() before adding anything.
  • Cover the hottest query shapes with compound indexes; keep prefixes reusable.
  • Make equality filters the leading keys, range keys next, and sort keys last.
  • Drop or shrink indexes you never use — every one slows writes.
  • Use hint() to test a candidate index before keeping it long term.

6 · Aggregation Framework

6.1 Pipelines, $match and $sort6.2 $group and accumulators6.3 $project and $addFields6.4 $unwind and array reshaping6.5 $lookup, $facet and $bucket

This chapter covers the aggregation pipeline from $match and $sort through $group, $project, $addFields, $unwind, $lookup, $facet, and $bucket. Aggregations transform raw documents into reports, graphs, and dashboard data. Each stage passes its output documents to the next in the chain.

The aggregation framework pipes documents through stages, each transforming the stream. It replaces SQL’s GROUP BY, JOIN and SELECT in a way that maps onto document shapes.

6.1 Pipelines, $match and $sort

The aggregation pipeline is an array of stages processed in order, starting with collection documents. Cheap stages such as $match and $sort should run early because $match uses indexes and shrinks the data every later stage sees. This ordering keeps the pipeline fast and readable.

db.orders.aggregate([
  { $match: { status: 'paid' } },      // stage 1: keep only paid orders
  { $sort: { total: -1 } }             // stage 2: biggest first
])
// Put $match before $group, $sort, or $lookup to let it use indexes.

An aggregation is an array of stages applied in order; a $match at the front filters early so later stages process far fewer documents and can use indexes.

6.2 $group and accumulators

$group groups documents by an _id key and computes accumulator expressions across each group. The accumulator operators include $sum, $avg, $min, $max, and $push, while $count counts documents. This is the MongoDB equivalent of SQL GROUP BY.

db.orders.aggregate([
  { $match: { status: 'paid' } },
  { $group: {
      _id: '$productId',                 // group by this field
      total:  { $sum: '$amount' },       // sum the amount per product
      count:  { $sum: 1 },               // count documents in the group
      avgAmount: { $avg: '$amount' },
      lastReview: { $last: '$review' }
  } },
  { $sort: { total: -1 } }               // best sellers first
])

A $field expression reads the field, and each accumulator folds the group’s documents into one result per distinct _id, giving totals, counts and averages.

6.3 $project and $addFields

$project reshapes output documents, keeping only the fields you name or computing new ones with expressions, similar to SELECT in SQL. $addFields adds new computed fields while preserving all existing fields. Use $addFields for temporary values that later stages need.

db.orders.aggregate([
  { $addFields: {
      totalCents:   { $multiply: ['$amount', 100] },
      yearMonth:    { $dateToString: { format: '%Y-%m', date: '$createdAt' } }
  } },
  { $project: { _id: 0, productId: 1, totalCents: 1, yearMonth: 1 } }
])

$addFields computes derived values for later stages, while $project keeps only the listed fields — together they rename, reshape and compute in place.

6.4 $unwind and array reshaping

$unwind deconstructs an array field into one output document per element, duplicating the other fields. It turns array data into rows that aggregations can then group and filter. Nearly every array report in MongoDB starts with $unwind.

db.orders.aggregate([
  { $unwind: '$items' },                       // one document per line item
  { $group: {
      _id: '$items.sku',
      qtySold: { $sum: '$items.qty' },
      revenue: { $sum: { $multiply: ['$items.qty', '$items.price'] } }
  } },
  { $sort: { revenue: -1 } }
])

$unwind duplicates each parent document once per array element, so a following $group can total quantities and revenue grouped by line-item sku.

6.5 $lookup, $facet and $bucket

$lookup performs a left outer join against another collection, matching local and foreign fields and attaching the results as an array. $facet runs several independent sub-pipelines in one pass, and $bucket groups values into defined ranges. Together these answer several related questions in a single query.

db.orders.aggregate([
  { $lookup: {
      from: 'customers',                  // the other collection
      localField: 'customerId',           // field in orders
      foreignField: '_id',                // field in customers
      as: 'customer'                      // the joined result lands here
  } }
])
// Each order now carries a customer array (usually one element).

$lookup joins the current pipeline against another collection by matching localField to foreignField, storing the matches in a new array field.

db.sales.aggregate([
  { $facet: {
      byCategory: [ { $group: { _id: '$category',  total: { $sum: '$amount' } } } ],
      byMonth:    [ { $group: { _id: { $dateToString: { format: '%Y-%m', date: '$soldAt' } }, total: { $sum: '$amount' } } } ],
      priceBands: [ { $bucket: { groupBy: '$amount', boundaries: [0, 10, 50, 100], default: 'Other' } } ]
  } }
])

$facet runs several independent pipelines over the same stream and returns one document with each result, while $bucket counts documents into numeric ranges.

Use find when you need documents back page by page; use aggregation when you need computed shape — counts, totals, joins or histograms.

7 · Schema Design & Data Modeling

7.1 Embedding vs referencing7.2 One-to-many patterns7.3 Normalisation vs denormalisation7.4 Schema validation with $jsonSchema7.5 Polymorphic and bucket patterns

This chapter covers the core modeling decisions: embedding versus referencing, one-to-many patterns, normalisation trade-offs, $jsonSchema validation, and the bucket pattern. You learn rules for both common and advanced shapes. Design decisions made here save years of pain later.

Document design is a deliberate act: what you embed, what you reference, and how you validate decides query speed, consistency and code simplicity. This chapter gives you the decision rules.

7.1 Embedding vs referencing

The decision rule is simple: embed data that is always read together and bounded in size, and reference data that grows without limit or is shared across many documents. Embedding gives single-round-trip reads, while referencing keeps one copy of the truth. You apply this rule to every pair of related fields.

Embed whenReference when
Read together nearly alwaysRead separately or only sometimes
Small and bounded (addresses, line items)Grows unboundedly (activity logs, posts)
No other document needs itShared (customer, product) and must stay consistent
Atomicity per parent mattersYou need to query the child on its own

The trade-off: embedding is one fast read and atomic, but inline copies go stale; referencing stays consistent but costs lookups or $lookup.

7.2 One-to-many patterns

A one-to-many relationship can be modelled three ways: embed the many side in the one side, reference the many side in an array in the one side, or reference the one side from each many document. Choose by how often you read the related data and how large the sets grow. One relationship, three valid data models.

// Pattern A: embed the many (bounded): a blog post with its three comments
db.posts.insertOne({ title: 'Hello', comments: [ { body: 'Nice', by: 'ada' } ] })

// Pattern B: reference the many (unbounded): one user, thousands of posts
db.posts.insertOne({ title: 'Hello', authorId: ObjectId('6650e3c9f1a2b3c4d5e6f708') })
db.posts.find({ authorId }).sort({ createdAt: -1 }).limit(20)   // + index on authorId

// Pattern C: reference the one (denormalised): the rare case of a "title" denormalised
db.posts.insertOne({ title: 'Hello', author: { id: ..., name: 'Ada' } })

Bounded children like comments drop straight in, unbounded children like posts move to their own collection with a referenced authorId, and occasional writes keep a denormalised copy fresh.

7.3 Normalisation vs denormalisation

Normalisation removes duplication and saves storage, but it costs extra round trips to reassemble data. Denormalisation duplicates values for fast, consistent reads at the cost of coordinated writes. Document databases intentionally bias towards denormalised, read-shaped data.

Normalised (references)Denormalised (embedded copies)
One source of truth per factFast single-read pages
Extra lookups and joinsExtra writes keep copies in sync
No stale duplicatesRisk of inconsistent copies
More round tripsFewer round trips, smaller transfers

Start embedded, split out only what genuinely needs to stand alone, and denormalise the read-heavy summary fields — for example the customer name on a finished order.

7.4 Schema validation with $jsonSchema

The $jsonSchema validator enforces document structure at the database layer using bsonType, required, properties, and patternProperties. You attach it to a collection with collMod or at creation time. It makes the flexible schema just strict enough without forcing a fixed table shape.

db.createCollection('users', {
  validator: { $jsonSchema: {
      bsonType: 'object',
      required: ['name', 'email'],
      properties: {
        name:  { bsonType: 'string', description: 'must be a string and is required' },
        email: { bsonType: 'string', pattern: '^[^@]+@[^@]+$' },
        age:   { bsonType: 'int', minimum: 0, maximum: 120 }
      }
  } }
})

db.runCommand({
  collMod: 'users',
  validator: { $jsonSchema: { ... } },   // tighten or relax the rule on a live collection
  validationLevel: 'moderate'            // warn instead of reject for old documents
})

A validator attached to a collection rejects writes that break the rule, and collMod can change or relax that validator on a live collection without a migration.

Validation runs on writes only — existing documents are untouched. Pick validationAction: 'warn' to report violations without blocking inserts.

7.5 Polymorphic and bucket patterns

The polymorphic pattern stores many document kinds in one collection, discriminated by a type field, which keeps queries and indexes practical when shapes vary. The bucket pattern groups time-series measurements into bounded arrays per time window. Both keep cardinality and index sizes under control.

// Polymorphic: one field flags the document kind
db.events.insertMany([
  { kind: 'click',  userId, url: '/home' },
  { kind: 'purchase', userId, amount: 12 }
])
db.events.createIndex({ kind: 1, createdAt: 1 })

// Bucket: sensor readings packed per sensor per hour, shrinking index entries
db.iot.readings.insertOne({
  sensorId: 's01',
  bucket: new Date('2026-09-18T10:00:00Z'),
  samples: [ { t: 0, v: 21.5 }, { t: 30, v: 21.7 }, { t: 60, v: 21.8 } ]
})
db.iot.readings.createIndex({ sensorId: 1, bucket: 1 })

The polymorphic pattern tags documents by a discriminator field for one indexed stream, and the bucket pattern packs many small readings into one document so one index entry covers many samples.

8 · Transactions & Consistency

8.1 Single-document atomicity8.2 Multi-document transactions8.3 Sessions and retryable writes8.4 Read and write concerns8.5 Read preference and causal consistency

This chapter covers single-document atomicity, multi-document transactions, sessions, read and write concerns, and read preference. Each mechanism controls a different layer of the consistency story. Understanding the layers tells you exactly what guarantee your application actually gets.

Every document write is atomic, and since MongoDB 4.0 multi-document transactions bring full ACID semantics for replica sets and sharded clusters. This chapter maps the consistency options and when to use them.

8.1 Single-document atomicity

MongoDB guarantees that every operation on a single document is atomic and all-or-nothing, so partially applied updates cannot happen. This is a real isolation guarantee, not a convention. Design documents so that one document represents one business transaction wherever possible.

A single updateOne with operators like $inc is atomic: no reader ever sees a half-applied update. Because documents hold related data, many "transactions" fit inside one document and need no transaction at all — prefer this shape first.

Started with $inc? Counters, balances and availability flags inside one document update atomically and stay consistent under any number of concurrent writers.

8.2 Multi-document transactions

Multi-document transactions group several reads and writes so they commit as one atomic unit. They require a replica set and a session, and you begin them with session.startTransaction() and then commit or abort. This is how you keep multiple documents consistent in changing business data.

const session = db.getMongo().startSession()   // a session backs the transaction
session.startTransaction()
try {
  db.getSiblingDB('bank').accounts.updateOne(
    { _id: 'alice' }, { $inc: { balance: -100 } }, { session }
  )
  db.getSiblingDB('bank').accounts.updateOne(
    { _id: 'bob' }, { $inc: { balance: 100 } }, { session }
  )
  session.commitTransaction()      // both updates become visible together
} catch (err) {
  session.abortTransaction()       // undo everything if either leg fails
  throw err
} finally {
  session.endSession()
}

startSession and startTransaction begin a scope, every statement carries the session, and commit or abort decides whether both balance changes land or neither does.

Transactions need a replica set — a standalone mongod rejects them. In Atlas and production every deployment is a replica set anyway.

8.3 Sessions and retryable writes

Sessions are server-side contexts that group a sequence of operations, and retryable writes automatically retry a write when the network fails. Drivers use sessions and retryable writes by default, so you mostly get this for free. Sessions are also a prerequisite for transactions and causal consistency.

const session = db.getMongo().startSession()
const order = session.getDatabase('shop').orders.insertOne({ total: 12 }, { session })
// Retryable writes: the driver retries a failed write automatically
mongosh "mongodb+srv://.../shop?retryWrites=true"   // modern defaults send this automatically

A session scopes related operations, and retryWrites lets the driver replay a write that failed mid-flight, so a dropped connection no longer means a lost insert.

8.4 Read and write concerns

Write concern declares when a write is acknowledged, from w:1 up to w:"majority" for a replica set. Read concern declares how fresh a read must be, from "local" to "majority" and snapshot. Both are dials that trade availability, durability, and consistency.

OptionValueMeaning
writeConcernw: 1 (default)Acknowledged by the primary
writeConcernw: majorityAcknowledged by the majority of members
writeConcernj: trueDurable in the journal before acknowledging
readConcernlocal (default)Read data as stored, may not be majority
readConcernmajorityOnly read data committed by the majority

If an acknowledged-but-unapplied write is acceptable you keep the cheap default; durable and majority levels trade latency for safety.

8.5 Read preference and causal consistency

Read preference routes reads to primary or secondary nodes, with modes such as primary, secondary, and nearest. Causal consistency, enabled on a session, guarantees that causally related operations are seen in copy order across secondaries. Both shape what a distributed read can actually observe.

const cursor = db.orders.find({}).readPref('secondaryPreferred')  // offload reads
// A causally consistent session: the read is guaranteed to see earlier writes
const session = db.getMongo().startSession({ causalConsistency: true })
const result = session.getDatabase('shop').orders.insertOne({ total: 9 }, { session })
const found = session.getDatabase('shop').orders.findOne({ _id: result.insertedId }, { session })

readPref routes scans to secondaries to protect the primary, and a causally consistent session orders reads after your own writes even when they hit different cluster members.

Secondary reads are eventually consistent: right after a majority write, a secondary may still lag briefly. Use readPreference: 'primary' for anything that must reflect the latest write.

9 · Replication & Sharding

9.1 Replica sets9.2 Failover and the oplog9.3 Shard keys, chunks and the balancer9.4 When to shard9.5 Atlas managed clusters

This chapter covers replica sets, automatic failover, the oplog, shard keys, chunks, and the balancer. Replication keeps data available when a node dies, and sharding spreads a huge collection across many servers. Together they are what keep MongoDB highly available and able to scale.

Replication makes copies of your data for availability; sharding splits data across many servers for scale. Atlas manages both for you — but you must understand them to size and design.

9.1 Replica sets

A replica set is a group of mongod instances where one primary handles writes and the others replicate its data as secondaries. You launch it with rs.initiate() and inspect members with rs.status(). The application always talks to the primary for writes.

# Start three mongod processes with the same replSet name
mongod --replSet rs0 --dbpath /data/rs0 --port 27017
mongod --replSet rs0 --dbpath /data/rs1 --port 27018
mongod --replSet rs0 --dbpath /data/rs2 --port 27019

# On the first member, define the set
rs.initiate({
  _id: 'rs0',
  members: [
    { _id: 0, host: 'localhost:27017' },
    { _id: 1, host: 'localhost:27018' },
    { _id: 2, host: 'localhost:27019', priority: 0 }   // priority 0: never primary
  ]
})
rs.status()    // who is primary, who is secondary, replication lag

Three mongod processes sharing one replSet name form a set; rs.initiate declares the members and rs.status shows the elected primary and the current replication lag.

9.2 Failover and the oplog

When the primary fails, the replica set detects it and an election promotes a secondary to primary automatically. The oplog is a capped collection on the primary that records every write, and secondaries replay it to stay in sync. This is the mechanism that drives all replication.

Secondaries read the primary’s oplog — a capped collection of every write — and replay it. If the primary dies, the set holds an election and one secondary is promoted within seconds; drivers reconnect to the new primary. A long-down secondary that falls behind the oplog window must resync.

rs.stepDown(10)                      # force an election (planned maintenance)
db.getSiblingDB('local').oplog.rs.count()   # see how much write history the oplog holds

rs.stepDown triggers a clean handover for maintenance, and the oplog’s size decides how long a lagging secondary can catch up before it must rebuild.

9.3 Shard keys, chunks and the balancer

Sharding splits a collection across shards using a shard key, and ranges of key values are delivered as chunks. The balancer migrates chunks between shards to keep distribution even. The shard key you choose decides which data lands on which server and how evenly it spreads.

# From mongos (the sharding router), not a mongod
sh.enableSharding('shop')
db.orders.createIndex({ customerId: 1 })     // index the shard key first
sh.shardCollection('shop.orders', { customerId: 1 })
sh.status()      // chunks, their ranges, and which shard owns each

# Chunks are ranges of the shard key; the balancer migrates them between shards
sh.startBalancer()
sh.enableAutoSplit().enable()    // allow big ranges to split

The shard key’s ranges become chunks distributed across shards, and the balancer quietly moves chunks to keep the cluster balanced while auto-split breaks oversize ranges apart.

The shard key is permanent — choose it for even, repeated value distribution. A key that is monotonic (like _id) piles new writes onto one shard.

9.4 When to shard

Shard only when you have exhausted vertical scaling, run out of disk or memory, or cannot fit the working set in RAM. The honest rule is that most teams should never shard, because the operating cost and complexity are real. Exhaust cheaper options first.

  • Shard only when one replica set cannot hold the working set or keep up with writes.
  • Exhaust single-set levers first: indexes, a bigger instance, read preference, archiving.
  • Sharding pays off past several hundred gigabytes or tens of thousands of writes per second.
  • Count the cost: distributed transactions, cross-shard queries, and an extra router tier (mongos).
  • Pick the shard key for a hot, high-cardinality, evenly distributed field.

9.5 Atlas managed clusters

Atlas maps these concepts onto its managed product, hiding the mechanics of replica set setup and sharding while keeping the choices visible. You select cluster tiers, enable backups, and configure read preference from the console. The same geos concepts apply underneath, just without manual host installation.

Atlas provisions the replica set for you, runs elections invisibly, and offers the sharded tier (M10+ with hash sharding) behind a GUI. You still choose instance size, read preference in the connection string, and whether a collection is sharded — knowledge of this chapter makes those choices deliberate instead of accidental.

10 · MongoDB with Node & Mongoose

10.1 The Node driver basics10.2 Connection pooling10.3 Mongoose schemas and models10.4 Validation and middleware10.5 Population

This chapter covers the Node driver, connection pooling, Mongoose schemas and models, validation, middleware, and population. This is MongoDB the way real applications use it, with JavaScript instead of raw shell commands. You build the same operations from Chapter 3 through a driver API.

The shell teaches MongoDB; applications talk to it through a driver or an ODM. Mongoose layers schemas, validation and middleware over the official driver — the pragmatic default for Node projects.

10.1 The Node driver basics

You connect with the official MongoDB Node driver using the connect method with a connection string and then pick a database and collection. Queries return a typed cursor and documents come back as JavaScript objects. Every MongoDB client in Node is built on this same API.

npm install mongodb

const { MongoClient } = require('mongodb')
const client = new MongoClient('mongodb+srv://cluster0.example.mongodb.net/shop')
async function main() {
  await client.connect()
  const db = client.db('shop')
  const user = await db.collection('users').findOne({ email: 'ada@example.com' })
  console.log(user?.name)
}
main().catch(console.error)

The driver turns a connection string into a client, a client into databases and collections, and collection methods carry the same CRUD verbs as the shell.

10.2 Connection pooling

You should create one client at startup and reuse it for the whole process, because the MongoClient maintains an internal pool of TCP connections. Creating a client per request exhausts connections and slows the app. A shared client keeps the pool warm, and you close it once at shutdown.

const client = new MongoClient(uri, {
  maxPoolSize: 50,          // cap concurrent sockets
  minPoolSize: 5,           // keep a few warm
  serverSelectionTimeoutMS: 5000   // fail fast if the cluster is unreachable
})
// Export one shared client (module singleton) — do NOT connect per request.

Pool settings bound how many sockets the one long-lived client opens, and the singleton pattern across the module keeps a warm pool instead of churning connections.

Connecting a new MongoClient inside every request exhausts file descriptors and stalls under load. Create one client at boot and reuse it for the process lifetime.

10.3 Mongoose schemas and models

Mongoose maps a schema definition to a collection and its model provides typed operations such as create, find, findOneAndUpdate, and deleteOne. The schema declares field types and defaults, and documents become validated BSON on save. This is the layer most Express applications interact with instead of the raw driver.

npm install mongoose

const { Schema, model } = require('mongoose')
await require('mongoose').connect('mongodb://localhost:27017/shop')

const userSchema = new Schema({
  name:  { type: String, required: true, trim: true },
  email: { type: String, required: true, unique: true },
  age:   { type: Number, min: 13, max: 120 },
  roles: [{ type: String, enum: ['user', 'admin'] }]
}, { timestamps: true })          // adds createdAt and updatedAt

const User = model('User', userSchema)      // uses the "users" collection
const ada = await User.create({ name: 'Ada', email: 'ada@example.com', age: 40 })
console.log(ada._id, ada.createdAt)

A schema describes fields, types, constraints and options, a model turns it into a collection handle, and create inserts while every schema rule runs as validation first.

10.4 Validation and middleware

Schema rules declare required fields, enum values, min and max ranges, and custom validators that run before a document is saved. Middleware hooks like pre and post run around save, validate, and remove operations. Mongoose validates on save and lets you inject logic before and after each operation.

userSchema.pre('save', function (next) {
  // 'this' is the document being saved (not an arrow function)
  if (this.isModified('password') && !this.passwordHash) {
    this.passwordHash = hashPassword(this.password)   // never store plain text
    this.password = undefined
  }
  next()
})

userSchema.post('save', function (doc) {
  console.log('Saved', doc.email)      // runs after a successful save
})

// Schema validation double-checks on the way in
await User.validate({ name: 'Too young?', age: 5 })   // rejects: age below min 13

The pre('save') hook runs before persist and can transform fields, while post('save') observes the result; schema-level constraints run inside validate automatically.

10.5 Population

Population automatically resolves a stored reference into the full referenced document in one call. You store the foreign _id in the child and call model.find().populate('field') to fetch the related data with a join. populate is the ergonomic aggregation $lookup.

const postSchema = new Schema({
  title:  { type: String, required: true },
  author: { type: Schema.Types.ObjectId, ref: 'User', required: true }
})
const Post = model('Post', postSchema)

const posts = await Post.find()
  .populate('author', 'name email')          // replace ObjectId with the real user
  .sort('-createdAt')
console.log(posts[0].author.name)            // a full user object, not a bare id

A ref on the ObjectId field declares the relationship, and populate('author') fetches the user documents in one extra query while letting you pick the fields.

populate has the same pitfall as SQL JOINs: populate in a loop causes N+1 queries. Fetch lists, then call populate once on the array of documents.

11 · Security & Operations

11.1 Authentication and RBAC11.2 TLS and network exposure11.3 Backups11.4 Monitoring11.5 The performance tuning checklist

This chapter covers authentication, role-based access control, TLS, network exposure, backups, monitoring, and a performance checklist. Operations keeps your data safe, available, and fast in production. Each lesson gives you commands you can run against your own server.

Enabling authentication, encrypting traffic, backing up and watching metrics turns a hobby server into a production one. This chapter is the operational checklist before any MongoDB goes to production.

11.1 Authentication and RBAC

You create users with db.createUser and grant least-privilege roles such as read, readWrite, and dbAdmin scoped to a database. Authentication in mongod settings forces every connection to log in with a named identity. Authorization therefore means each connection carries a scoped set of permissions.

// Start mongod with auth enabled
mongod --auth --bind_ip 127.0.0.1

// As the admin, create a least-privilege user for the app
db.getSiblingDB('admin').createUser({
  user: 'appUser',
  pwd: passwordPrompt(),                  // prompt instead of typing the secret
  roles: [ { role: 'readWrite', db: 'shop' }, { role: 'read', db: 'analytics' } ]
})

db.getSiblingDB('admin').getUsers()       // list users and their roles
db.getSiblingDB('admin').dropUser('appUser')

mongod --auth refuses unauthenticated connections, and an admin grants the app user read and write on shop but only read on analytics — least privilege in action.

11.2 TLS and network exposure

TLS encrypts traffic between clients and servers, and you enable it with net.tls settings and the --tls- options at startup or on the connection string. Network hardening limits exposure so only trusted hosts can reach the port. Credentials are useless if the connection itself leaks data.

# mongod.conf
net:
  bindIp: 127.0.0.1          # never listen on 0.0.0.0 by default
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/ssl/mongodb.pem
security:
  authorization: enabled

# Driver connects with the srv string, which implies TLS in Atlas; locally:
mongosh "mongodb://appUser:pass@localhost:27017/shop?authSource=admin&tls=true"

The config binds to localhost, forces TLS via a certificate, and requires authorization, while the connection string carries the authSource database and tls=true.

A public, unauthenticated, TLS-less MongoDB on 27017 is a well-known attack magnet. Default to bind_ip: 127.0.0.1 and expose through a firewall only what the app truly needs.

11.3 Backups

Logical backups use mongodump to export a database or collection and mongorestore to load it back, with --db and --collection to narrow scope. You can also snapshot to disk. A backup you cannot restore is a decoration, so practice restores on a test server.

# Dump one database to a folder
mongodump --uri="mongodb://localhost:27017" --db=shop --out=/backups/shop-2026-09-18

# Dump everything as a compressed archive
mongodump --archive=/backups/shop.full.gz --gzip --uri="mongodb://localhost:27017"

# Restore from either form
mongorestore --uri="mongodb://localhost:27017" /backups/shop-2026-09-18
mongorestore --archive=/backups/shop.full.gz --gzip --uri="mongodb://localhost:27017"

mongodump exports data to disk and mongorestore replays it; archives combine the dump and compression into one file you can ship to object storage.

Add your own oplog usage or Atlas continuous backups for point-in-time recovery; a nightly dump alone loses the writes of the current day.

11.4 Monitoring

Built-in commands give live health checks without extra tooling. Use db.serverStatus(), db.currentOp() and db.setProfilingLevel() to watch the server, plus the $currentOp aggregation and the explain plan for slow queries. Watch for slow queries, connection growth, and lagging secondaries.

mongostat --discover             # live reads, writes, connections and queue per second
mongosh --eval 'db.serverStatus().opcounters'   # total inserts/updates/deletes counters
mongosh --eval 'db.currentOp()'  # what is running right now (find slow queries)
db.killOp(opId)                  # terminate a runaway operation
rs.printSecondaryReplicationInfo()   # replication lag per secondary

mongostat gives the at-a-glance load, serverStatus and currentOp expose counters and in-flight operations, and the replication helper flags a lagging secondary.

11.5 The performance tuning checklist

The performance checklist lists fixes in the order most likely to make MongoDB fast, starting with missing indexes and bad query shapes, then moving to schema design and server resources. You verify each with explain() before changing hardware. Work the checklist before buying bigger machines.

  • Add the missing indexes (Chapter 5) — the highest-impact fix by far.
  • Reduce documents: project away heavy fields; shorten field names; archive old data.
  • Move reads to secondaries where eventual consistency is acceptable.
  • Put $match first in pipelines and keep write batches small.
  • Up the working set: enough RAM so hot documents live in cache, not on disk.
  • Watch mongostat for queue length and 100% disk or CPU before scaling out.

A.5 Glossary

The glossary defines the core vocabulary of the guide, from BSON and ObjectId to oplog, shard key, and populated. Every term links to where the guide teaches it. Read it so chapter reading never stalls on an unfamiliar word.

  • Document — a single record; a BSON object that can nest subdocuments and arrays.
  • Collection — a named group of documents, roughly a table without a fixed schema.
  • BSON — the binary JSON encoding MongoDB stores and transfers, with extra types.
  • ObjectId — the default 12-byte _id value with an embedded timestamp.
  • Cursor — the lazily evaluated result of find, iterated page by page.
  • Update operator — a dollar-prefixed modifier ($set, $inc) applied inside an update.
  • Projection — the filter that selects which fields a query returns.
  • Index — a B-tree structure that turns scans into lookups.
  • Pipeline — the ordered array of stages in an aggregation.
  • Shard key — the field (or fields) whose ranges divide a collection across shards.
  • Oplog — the capped collection of writes secondaries replay for replication.
  • Replica set — one primary plus secondaries that elect a new primary on failure.
  • Write concern — how many members must acknowledge a write before it is accepted.
  • Read concern — how fresh and "committed" a read must be.
  • Session — a client-scoped context that powers transactions and causal consistency.
  • Mongos — the router process that fronts a sharded cluster.
  • Validator — a $jsonSchema rule a collection enforces on writes.
