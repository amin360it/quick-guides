Orientation — Scope, Model and Conventions

0.1 Scope and audience0.2 The model in one page0.3 Objects, refs and the three trees0.4 Tooling and versions0.5 Version pins and what changed recently0.6 Conventions and how to read this guide

Git is the most widely deployed version control system in the world and one of the least understood at the level below the porcelain. This guide is written for engineers who use Git daily and need to reason about what it actually does: the object model, what a branch is, why a merge can be reversed and a rebase cannot, how the index differs from the staging area in most people’s understanding, and how to recover work they have already lost. It is reference material, not a tutorial, and it assumes the reader is capable of reading a plumbing command without a walkthrough.

0.1 Scope and audience

What this guide covers, and the one assumption it makes that most tutorials do not make explicit.

Git is a content-addressable file system with a version-control user interface bolted on top. Almost every confusing behaviour — the index, the reflog, why a rebase changes commit hashes, why a shallow clone behaves oddly — falls out of that one sentence. This guide therefore opens with the data model and returns to it, because the porcelain commands only make sense once the objects underneath them are understood.

The scope is the Git binary, the index, the ref database, the configuration system, and the collaboration workflows built on them: branching models, review, CI integration and the forensic work that follows an incident. It is not a tutorial for a first repository, and it does not cover hosting-provider features beyond those that change Git behaviour. Where a hosted platform adds something — pull requests, protected branches, required reviews — it is treated as a policy layer over the mechanics described here, not as a separate subject.

The assumption. The reader has used Git for at least six months, has committed, branched, merged and resolved a conflict, and has used the reflog to recover something at least once. Every section therefore begins from a point of knowledge and goes to the level where behaviour becomes predictable. Nothing here is introductory; a great deal of it is the kind of detail that is documented but rarely read, and that is exactly what causes the incidents.

The four object types, two pointer systems, and three places your changes can be at any instant. Everything else in Git is a convenience layer over this.

# The four object types, created and inspected for real. This is the whole
# data model; everything above it is arithmetic on hashes.
function buildCommit() {
  # 1. A blob is just bytes plus a header. The header is what makes it
  #    content-addressable and immutable: change a byte, change the hash.
  BLOB=$(printf 'hello\n' | git hash-object -w --stdin)
  #   → 95befdd0f5b1a6b4d2f2c1a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6
  #   With -t and --literally you can even create a blob that does not match
  #   its content. That is how git hash-object --literally exists, and it is
  #   a forensic tool rather than a feature.

  # 2. A tree maps names to hashes. The mode carries the permission bits and
  #    the type: 100644 regular, 100755 executable, 120000 symlink, 40000 tree.
  printf '100644 blob %s\treadme.md\n' "$BLOB" | git mktree
  #   → a tree hash
  #   Note it is NOT JSON and there is no key order guarantee on read, which
  #   is why a tree's hash is stable but its serialisation is not canonical.

  # 3. A commit names a tree and its parents. Author and committer differ on
  #    a rebase, which is the mechanical difference between the two objects.
  COMMIT=$(git commit-tree "$TREE" -p "$PARENT" -m "message")
  #   The message keeps its trailing newline; the hash covers the author,
  #   committer, timestamps, parents, tree and message. Change ANY of them and
  #   the hash changes, which is why an amend is a new object and not an edit.
  #   cat-file -p $COMMIT
  #   tree 9f2b1c…
  #   parent 3a1f0e…
  #   author  Dev <dev@example.com> 1759113600 +0100
  #   committer Dev <dev@example.com> 1759113700 +0100
  #  
  #   message
  #   message
}

# Reading an object. -p pretty-prints, -t gives the type, -s the size.
function inspect() {
  git cat-file -t  HEAD                    # "commit"
  git cat-file -p  HEAD                    # full content, resolved
  git cat-file -s  HEAD                    # bytes, which is how you tell
                                         # a blob from a huge one
  git cat-file --batch-check < list      # resolve 10,000 hashes fast
}

# The two pointer systems, and the difference that matters.
function pointers() {
  #  .git/refs/heads/*    — branch refs, plain files containing a hash.
  #                         Editable by hand, though you should not.
  #  .git/refs/remotes/*  — remote-tracking refs, written by fetch.
  #  .git/refs/tags/*    — tags, annotated or lightweight.
  #  .git/HEAD            — a symref: "ref: refs/heads/main". A pointer to a
  #                         pointer. Detached HEAD is HEAD containing a raw hash.

  #  The second store is the PACKFILE and the object database: loose
  #  objects in .git/objects/xx/yyyy…, packed into .git/objects/pack/.
  #  Refs live in the first store and point into the second. Deleting a
  #  branch deletes a ref, not the objects — which is why the objects are
  #  still recoverable from the reflog. This is the single most useful fact
  #  in this guide.
}

# The index is the part that surprises people. It is a serialised list of
# (mode, object hash, stage, stat cache) per tracked path, and the stat cache
# is what lets Git decide a file is unmodified without reading its content.

$ function showIndex() {
  function git ls-files --stage | head -5
  100644 95befdd0f5b1a6b4d2f2c1a2b3c4d5e6f708192  0  readme.md
  100755 a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d  0  scripts/build.sh
  120644 9f8e7d6c5b4a39281706f5e4d3c2b1a09f8e7d  0  assets/logo.svg
  #  mode  object hash  stage  path
  #
  #  STAGE is the conflict-resolution channel and almost nobody knows it:
  #    stage 0 = the normal, unmerged entry
  #    stages 1, 2, 3 = the common ancestor, ours, theirs
  #  A conflicted path has THREE entries. That is the entire mechanism behind
  #  git checkout --ours and --theirs, and it is why you can inspect the
  #  base version of a conflicted file:
  function conflictInternals() {
    function git ls-files -u
    100644 1a2b3c4 1  src/config.ts     # stage 1: merge base
    100644 5d6e7f8 2  src/config.ts     # stage 2: ours (HEAD)
    100644 9a0b1c2 3  src/config.ts     # stage 3: theirs

    #  So the "base" file everyone asks for is simply:
    function git show :1:src/config.ts
    #  And a three-way diff, which is what diff3 conflict style renders:
    function git diff --cc src/config.ts
  }
}

# The .git/index is a binary file but you can read it. This is the correct
# way to find an index entry whose path is misencoded or whose stage is stuck:
function indexPlumbing() {
  function git ls-files --debug src/config.ts
  100644 5d6e7f8 0  100644 0 1  1759113600 1759113600 readme.md
  # ctime:0  mtime:0  dev:1  ino:0  uid:0  gid:0  size:0  flags:0

  # The split-index and the sparse-index exist to make this file small and
  # fast for very large repositories. Both are opt-in, both change how the
  # index is stored, and neither changes semantics. If you are debugging a
  # large repo, turning on split-index is a 3–5× improvement in status speed
  # with no behavioural difference.
  function git config splitIndex true
  # To undo, and merge the shared index back into the main one:
  function git update-index --no-split-index
}

0.6 Conventions and how to read this guide

The conventions used, and the three commands that appear in nearly every section because they answer most questions.

# Every command in this guide is real and every flag is real. Where a command
# has a destructive form, the destructive form is shown and marked.
#
#   $  marks a shell prompt, and is not part of the command.
#   ⚠  marks a command that discards uncommitted work. There are five of them
#      in this guide and every one is written out in full.

# The three commands that answer most questions:
function theThree() {
  # 1. WHAT IS GOING ON RIGHT NOW, comprehensively.
  function git status
  #   Reports HEAD, the branch, upstream and its divergence, staged, unstaged,
  #   untracked, and unmerged paths. It is the right first command in almost
  #   every situation, including "why is nothing happening".
  #
  #   On branch main, 3 ahead and 1 behind origin/main.
  #     Unmerged paths are the first thing to check when a merge claims to have
  #     succeeded but the files look wrong.

  # 2. WHERE DID THIS HASH COME FROM, and what does it contain.
  function git log --oneline --graph --decorate --all -30
  #   --graph    draw the DAG. -30, not -3: the shape of history is the point.
  #   --decorate name the refs pointing at each commit. Without it you cannot
  #   see that a branch you forgot about still exists.
  #   --all      every ref, not just the current branch. Two branches that are
  #   60 commits diverged are the normal state of a busy repository.

  # 3. WHAT DID I JUST DO, in detail, line by line.
  function git show HEAD --stat
  #   The single most useful command for learning. Run it after every commit
  #   and after every rebase step, and the model in section 0.2 becomes concrete
  #   faster than any explanation.
}

The data model is not an implementation detail you can skip; it is the explanation for every surprising behaviour in the tool. This chapter goes from a byte of content to a repository, explains why hashes are immutable and therefore why amends and rebases create new objects, and establishes the reflog as the mechanism that makes almost all mistakes recoverable.

1.1 Blobs, trees and content addressing

Content addressing is the property that makes Git immutable, deduplicating and verifiable, and it also makes Git unable to do in-place edits.

// A blob's hash is computed over the literal bytes "hello\n" with a header
// prepended. Nothing else — not the filename, not the mode, not the time.
$ function git hash-object --stdin <<< "hello"
ce013625030ba8dba906f756967f9e9ca394464a

// The same content in two files is ONE blob. This is why a repository with
// 5,000 copies of a licence file stores it once.
$ function git hash-object -t blob --stdin <<< "hello"
ce013625030ba8dba906f756967f9e9ca394464a

// Consequence 1: deduplication is automatic and total. If the bytes match,
// the object is shared. There is no "similar file" logic; it is exact.
//
// Consequence 2: you cannot "change" a blob. You write a new one and point
// something at it. This is why `git add` after an edit does not modify the
// index entry — it replaces the hash in it.
//
// Consequence 3: identical content in different directories is one object, but
// the TREES differ because the paths differ. So you still get one blob and two
// tree entries. The tree is what encodes location.
//
// Consequence 4, and this one bites: because the hash covers the content, you
// can prove a file has not changed without reading it. `git diff` compares
// hashes first and only reads content when they differ. The stat cache in the
// index extends this to "has not been touched at all".

// The SHA-256 transition. Object format is chosen at init and is NOT
// convertible in place. The hashes are 64 characters instead of 40.
$ function git init --object-format=sha256 newrepo
//   Conversion of an existing repository requires git-filter-repo, which
//   rewrites every hash including in commit messages and tag objects. It is
//   a one-way operation and every collaborator must re-clone. Choose deliberately
//   at init; do not attempt it on a shared repository at 18:00 on a Friday.
//
//   The 2026 position: SHA-1 is not practically broken for this use. Git's
//   threat model is collision-forced chosen-prefix collision, which is
//   expensive and SHA-1's known weaknesses make it a bad long-term choice.
//   SHA-256 costs ~2× disk and is the right default for anything starting now.

1.2 Trees and modes

Trees are sorted binary-ish listings, and the four mode values you will meet. The sort order is unusual and it is the reason for a class of confusing merge behaviour.

// A tree's entries are sorted by name, treating '/' as a byte with a HIGHER
// value than most others. This means "a" comes before "a/b" — a directory
// and a file cannot collide, which is how Git represents a path in a tree.
//
// The practical consequence appears in merges. If branch A adds a FILE at
// path "foo" and branch B adds a DIRECTORY at "foo/bar", there is no content
// conflict — the trees are unambiguous — but the working tree cannot represent
// both, and Git reports "untracked working tree files would be overwritten".
// This is the D/F conflict and it is a filesystem limitation, not a bug.

// The mode values. Only four matter.
100644  regular file, non-executable        // the default on Linux and macOS
100755  regular file, executable           // git does not track the +x bit
                                         // separately, only the fact of it
120000  symbolic link — the blob holds the link TARGET as text
040000  subdirectory — the "hash" is a tree hash

// core.fileMode is the setting that causes the most confusion for new
// contributors. Git only notices a mode change if the filesystem
// reports it, and some filesystems and mounts do not.
$ function git config core.fileMode false
//   Set it on a filesystem with unreliable permissions — a VirtualBox share,
//   an NTFS mount, some network filesystems. On Linux leave it true.
//
//   The reverse problem: 100644 and 100755 are the only file modes Git records.
//   If your system has a setgid bit or ACLs on your scripts, Git will silently
//   ignore them and the bit will be lost on a fresh clone.

// Submodule entries are a fifth thing that looks like mode 160000. It is not
// a blob and it is not a tree: it is a commit hash, recorded directly in the
// superproject's tree. The submodule's own .git is a FILE containing a
// gitdir: pointer, which surprises people who look for a directory.
$ function git ls-tree HEAD
100644 blob 95befdd…    readme.md
100755 blob a1b2c3d…    scripts/build.sh
120000 blob 9f8e7d6…    latest-version
040000 tree 7c1e2f3…    src
160000 commit 4d5e6f7…  vendor/library

// Reading a tree recursively, and finding the largest objects in a
// repository — the two most useful plumbing commands for triage.
$ function git ls-tree -r -l HEAD | sort -k4 -n -r | head -20
//   mode  type  hash        size(KB)  path — sorted by size, descending.
//   The first command to run when a repository is unexpectedly large.

1.3 Commits, parents and the DAG

A commit is a snapshot plus a set of parents, and the history is a directed acyclic graph rather than a line. Every merge commit, every rebase and every cherry-pick is a consequence of that one sentence.

// A commit is a tree plus zero or more parents. The graph is a DAG because
// nothing points backwards and nothing can form a cycle: a commit's hash
// covers its parents' hashes, so a cycle would require a hash to cover
// itself.
//
//   A regular commit has ONE parent: its predecessor. History is a chain.
//   A merge commit has TWO or more: the two tips being joined. History branches
//   and rejoins, and the merge commit exists solely to record that the two
//   lines of development are related.
//
//   This is why a merge commit's tree can be any tree at all — including one
//   that was never the state of any branch. A merge is a claim that "this tree
//   is the correct union", not a record of anything that happened sequentially.
//
//   Consequence: `git bisect` works because the DAG is traversable, and it is
//   fast because the commit-graph caches the reachability bitmaps.
//   It is also why Git can find a merge base — the only commit that is an
//   ancestor of both tips. See section 2.2.

// Why an amend creates a NEW commit rather than editing one.
//
//   The commit object contains its own hash in nobody, but its PARENT hash is
//   inside it, and the committer timestamp is inside it. Changing either the
//   tree or the message changes the hash, and every child commit references the
//   parent BY HASH — so changing one commit's hash changes all of its
//   descendants too. This is a tree-wide consequence of content addressing.
//
//   Which is exactly why a rebase is expensive: it rewrites every descendant.
//   And exactly why `git replace` exists: it lets you tell Git to pretend one
//   object is another, so you can debug an old state without rewriting history.
$ function git replace --graft 3a1f0e 1a2b3c4 5d6e7f8
//   Now `git log` treats 3a1f0e as having parents 1a2b3c4 and 5d6e7f8, as if it
//   had been a merge. Grafts and replace refs are local and not pushed, which
//   makes them safe for forensics and useless for collaboration.
$ function git log --graph --oneline --decorate --all

1.5 Detached HEAD, and why it is not an error

Detached HEAD is a normal, intended state that people treat as a mistake. Understanding what it is removes the anxiety and the accidental deletions.

// Detached HEAD means HEAD contains a hash rather than "ref: refs/heads/x".
// It is what you get after `git checkout <commit>` and it is the correct
// state for bisecting, for inspecting a file at a point in history, and for
// trying out a commit before deciding to build on it.
$ function git checkout 1a2b3c4
#   Note: You are in 'detached HEAD' state. You can look around, make experimental
#   changes and commit them, and you can discard any commits you make in this
#   state without impacting any branches.

// The warning exists because of a real hazard, and the hazard is specific:
//
//   While detached, commits are only referenced by HEAD and the reflog. If you
//   `git checkout main` and then the reflog expires, those commits are gone.
//   The moment you do ANYTHING with them — commit, tag, branch — they are safe.
$ function git switch -c experiment
//   The fix, and it is the right habit: branch first, then experiment. Within
//   thirty seconds you have forgotten you were detached, and that is fine.

// `git switch` vs `git checkout`. The 2.23 split is worth using.
$ function git switch main
//   switch  — changes the working tree. Refuses to clobber uncommitted work
//             that would be lost, which checkout does not do reliably.
$ function git switch -c new-branch

//   checkout — the original command, now doing both files and refs. Kept for
//   compatibility and for muscle memory. It is not going away.
$ function git checkout main
$ function git checkout -b new-branch
$ function git checkout <path>

//   if a local change would be overwritten, while `git checkout main` will

$ function recover() {
  //  1. Find the commit. `git reflog` and `git reflog show <branch>`.
  function git reflog show feature
  //  2. Give it a name IMMEDIATELY, before anything can prune it.
  function git branch rescue 1a2b3c4
  //  3. Inspect it. It is a normal commit and everything works on it.
  function git show rescue --stat
  //  4. Put it back where it belongs.

//

The one habit that eliminates most data loss. Configure your editor or shell to run git status before every destructive command, and always dry-run git clean. Every one of them has a safe form that costs two seconds: stash, -n, diff first, name it before you delete it, and --force-with-lease.

2.1 What a branch actually is

A branch is a 41-byte file containing a commit hash. Every operational behaviour of branching, including the parts that look like features, follows from that.

A branch is a mutable ref: a file under .git/refs/heads/ whose entire content is a hexadecimal object name, optionally followed by a newline. Creating a branch writes a file; deleting one unlinks it; moving one rewrites it. There is no branch object in the database, no branch metadata, no creation time, no author and no message. The "branch created from" line printed by git branch is a reconstruction from the reflog, not a property of the branch.

Three consequences follow immediately. First, branch names are validated by check-ref-format and the rules are non-obvious: the name may not begin with a dot, may not contain .., may not end with .lock, may not contain ASCII control characters, space, ~, ^ or :, may not contain a sequence @{, and may not be the single character @. Second, a ref cannot point at a tree or a blob — git branch refuses, and update-ref will silently accept a tree hash if you pass it to a loose ref, which is a documented footgun that fsck will later report. Third, because the ref is the only mutable thing, publishing a branch is a ref update over the wire and nothing more, which is why pushing a branch is fast and pushing a tag is not.

Branches, remote-tracking branches, tags and HEAD live in one namespace of directories and one optional packed-refs file. The resolution rule is: symbolic ref first, then $GIT_DIR/refs/<name>, then the packed table. A loose ref shadows a packed entry of the same name permanently, which is why git pack-refs must delete the loose file or the two can disagree.

Two less obvious points deserve emphasis. git branch -m is not an atomic rename: it writes the new ref, moves the reflog, creates a symref-style redirect only when the old branch was the current branch of a worktree, and deletes the old ref. Second, git branch --set-upstream-to writes three config entries at once — branch.<name>.remote, branch.<name>.merge and, since 2.43, potentially the branch.<name>.pushRemote default — and a branch with a stale upstream is the most common cause of the "Your branch is ahead of 'origin/main' by 3 commits" message that has no effect on what a push does.

2.2 Merge bases

Every three-way merge is computed against a set of merge bases, and the common case of a single base hides the cases where the set has zero, one or many members. This subsection is where the interesting failures live.

A merge base of two commits is a commit that is an ancestor of both. The merge base used by a fast three-way merge is the best common ancestor: the member of the common ancestor set that no other common ancestor is a descendant of. git merge-base by default prints only one such commit, selected by date among the independent best ancestors, and that selection is a heuristic that only matters in criss-cross histories. --all prints every best common ancestor, which is what a recursive or octopus merge actually consumes.

The set of merge bases can be empty. Two commits that share no ancestor at all — the result of two unrelated inits, a repository rewritten with filter-repo on both sides, or two replace refs in play — have no base, and Git synthesises an empty tree as the base, so the merge becomes a pure two-way "add everything from both sides" and reports every file as conflicted if both sides added the same path. This is the classic fatal: refusing to merge unrelated histories guard, and --allow-unrelated-histories is the documented override.

--fork-point is a different animal entirely and is the source of most misreported bugs. It exists to answer "where did this branch start, given that the reflog of the remote-tracking ref knows what the remote used to be?" The algorithm looks for the newest commit reachable from the first argument that is not reachable from any of the other arguments, using the reflog of the upstream ref to find the point at which the local branch was forked. It was introduced for exactly one workflow: git pull --rebase after someone force-pushed a rewritten history over your branch’s base.

2.3 The three-way merge

A merge is a content-level three-way computation over trees, not a textual diff application. Understanding the three inputs — base, ours, theirs — predicts every conflict class you will meet.

Git does not merge patches. For each path, it takes the blob at the merge base, the blob on HEAD, and the blob in the other commit, and asks: for which sides did the content differ from the base? Non-overlapping changes merge cleanly; overlapping changes conflict; a change on one side against a deletion on the other conflicts; a delete/modify on both sides is a modify/delete conflict that the text-merge machinery cannot classify as a content conflict and reports separately. Rename detection then runs on the results, and a rename paired with any modification to the same file on the other side is a rename/modify conflict — the one class of conflict that produces a tree in which a path has been silently re-created at its old name.

When merge.conflictStyle is set to diff3 or zdiff3, the base region is shown inside the conflict markers. This is the single highest-leverage configuration change for merge conflict resolution and it should be set globally in any team that shares conflicts by patch.

Previewing a merge without touching the working tree has been possible since Git 2.38, and the new merge-tree is a genuine rewrite rather than the old script wrapper. In the new mode the repository is optional, arguments are explicit branch names rather than fetched refs, and renames and directory/rename conflicts are detected properly. It is the right tool for evaluating a merge in a pull-request pipeline without allocating a worktree.

2.4 Fast-forward, no-ff and integration history

A fast-forward moves a ref without creating a commit; --no-ff forces one. The choice is a statement about what your history should be able to answer later, and it is worth making deliberately per branch rather than by default.

Fast-forwarding means the current ref is an ancestor of the target and the update is a pure ref move: no commit, no index write, no working tree change, no ORIG_HEAD of consequence. It is cheap, and it destroys the information that an integration happened. If a branch is fast-forwarded into main and later has to be reverted, the revert reverts every commit, and there is no point in the graph at which those commits entered the trunk other than a commit message and a date.

--no-ff creates a merge commit with two parents, which is the only way the graph can later answer "which changes arrived together" and "which branch produced this set of commits". It is required for any branch that will be reverted as a unit, and it is what makes git revert of a range coherent. It costs one commit and produces the merge commits that some reviewers find noisy, which is a preference argument, not a technical one — the technical argument is that the information is otherwise unrecoverable.

2.5 Branching models compared

Four models account for nearly all real branching policy. The right choice is a function of release obligation, review latency and merge conflict exposure — not of team size alone.

The models differ on one axis that matters: how long a branch lives before its content reaches the trunk. GitHub Flow and trunk-based development hold that time to hours. git-flow holds one branch — develop — indefinitely, and creates a second long-lived branch for each release. GitOps and synchronisation flows invert the direction of integration entirely: the trunk is not edited by merge, it is declared by a pull request to a manifest, and an automated controller reconciles reality to that declaration. Branch lifetime is the strongest predictor of merge conflict frequency, and it is the variable the matrix below is really about.

2.6 Release branches, hotfixes and back-ports

Once a tag exists, the question is who maintains the line it names and how fixes propagate between lines. These are the operations that are simple individually and expensive when the policy is undefined.

A release branch is a promise: commits after the tag will not be added, so the tag remains a meaningful identifier. The mechanics that enforce the promise are a merge.ff configuration, a pre-receive hook, or a hosted platform’s branch protection with a "no direct pushes, no back-merge commits" rule. What the policy must answer is the forward-propagation question — when a bug is fixed on the release line, how does the fix reach main — and the answer determines whether the fix is made once or twice.

There are two defensible answers. Fix on trunk, back-port down. The fix is written and reviewed once on main, and the release branch receives a cherry-pick. This keeps trunk complete and makes the back-port a mechanical, conflict-light operation, at the cost that a regression may sit in production until the back-port lands. Fix on the release line, forward-merge up. The fix is written where users are, and trunk receives the merge from the release branch. This minimises time-to-fix for affected customers and creates a permanent divergence that must be carried until the release line is retired. The second model is mandatory for a certified or on-prem product where the release line is the one under validation; the first is correct for everything else.

Two operations in the table are routinely misdescribed. rebase does not "move commits" — it computes a new sequence of commits by applying patches, and the old commits remain in the object database as unreachable objects until garbage collection, which is the mechanism chapter 6 relies on. And merge --squash does not touch the index in the sense of "staging your changes": it stages the entire merge result, so if you have pre-existing staged work, it is silently folded into the squash unless you refuse. If the goal is "I committed something too early and want it back in the working tree, uncommitted", the correct answer is git reset --soft HEAD~1 — HEAD moves, nothing else does, and the commit’s content is now staged and ready to re-commit. If the goal is "I want to keep working on it but as a different set of commits", it is git reset --mixed HEAD~1 followed by re-adding selectively. If the goal is "erase it completely", it is git reset --hard HEAD~1 and the commit is still in HEAD@{1} until the reflog expires. Choosing among these is a question about intent, and Git cannot infer intent from the current state.

3.2 Rebase mechanics

Rebase is a sequence of three-way merges between patches and a new base. Understanding it as patch application rather than commit replay predicts every conflict, drop and hash change you will observe.

A rebase takes the commits reachable from HEAD but not from the upstream — the "todo list" — and for each one computes a three-way merge of three trees: the parent of the original commit, the original commit itself, and the current tip being built. The result is a new commit with the same author, author date and message, and a new committer and committer date. The original commits are not modified, moved, or deleted; they become unreachable and remain in the object database.

Two consequences follow. First, the operation is patch application, so a commit whose changes were already applied upstream will conflict or conflict-not depending on context, and a commit that becomes empty — because its entire content is already present — is dropped or, with --empty=keep in newer Git, retained. Second, because the committer date changes, the hash always changes even if the tree, author and message are identical. You can prove this directly with git commit-tree: build two commits with identical trees, authors and messages, differing only in committer date, and observe two hashes.

rebase.updateRefs=true is the configuration worth understanding in detail, because it changes the branch set during the operation. It instructs rebase to move any branch pointer that points to a commit being rebased, except branches checked out in another worktree. Use --no-autostash deliberately, not by accident. rebase.autoStash makes Git stash and re-apply uncommitted work around a rebase, which is convenient and occasionally lossy — the re-application happens as a plain merge and can conflict after the rebase has already succeeded, leaving a confusing state that is neither the rebase nor the original work. Setting it to false and requiring a clean working tree before a rebase makes the preconditions explicit, and the one-line cost is git stash && git rebase ... && git stash pop where the pop failure is visible and attributable.

3.3 Interactive rebase and autosquash

Interactive rebase is an editor over the todo list that the non-interactive rebase already computes. The commands are pick, reword, edit, squash, fixup, drop, exec, break, label and reset.

The rebase-todo file is the interface. Because it is a file, it can be generated rather than typed: --autosquash scans the log for commits whose subject begins with fixup!, squash!, amend! or fixup -C and rewrites the todo to move them next to their targets, changing the verb. git commit --fixup=<commit> and --squash=<commit> generate those prefixed subjects, which is what makes the whole mechanism usable without memorising the syntax.

# The full command set, and what each does to the current commit.
$ function rebase -i --autosquash HEAD~6

reword 6e7f8a9 test: cover the 409 path

exec make fmt && git add -A

reset 9c8d7a6
fixup -C 2d3e4f5 fixup! feat: add the retry budget
amend! 5f6a7b8 docs: correct the flag name
# pick     keep as-is (rewritten, new hash)
# reword   keep message, stop for the editor
# edit     stop after applying, before committing
# squash   combine, concatenate both messages, editor opens
# fixup    combine, keep only the target's message
# fixup -C like fixup but takes the FIXUP commit's message
# amend!   squash into the PRECEDING commit, not the original target
# drop     remove the commit entirely
# exec     run a shell command between commits
# break   stop here; `git rebase --continue` proceeds
# label/reset  internal branch; the portable alternative to /label

--autosquash requires the fixup commits to be in range, which is a real constraint: if you fixup! a commit that is already squashed away, or that is outside the range you are rebasing, the autosquash silently does nothing useful. The --keep-base option addresses the specific case where an exec git commit --amend changed the commit that is your fork point, causing rebase to rebase it again; --keep-base instead creates a new onto commit so the amendment is preserved and the earlier commit is not replayed. Neither is a substitute for checking git log --oneline @{u}..HEAD before a rebase.

Non-interactive use of the same machinery is worth having, because it removes the editor from CI and scripted history repair. --autosquash with --exec runs a command per commit; the GIT_SEQUENCE_EDITOR environment variable replaces the editor with any command, which is how a script can filter or reorder the todo without a human; and rebase.instructionFormat controls what each todo line looks like, which matters if you are parsing it. A break inside a script is a bug: it stops the operation and leaves the repository mid-rebase, and the script continues against an unfinished rebase.

Autosquash will happily reorder your commits into an unbuildable sequence. Squashing a "fix the tests" commit into the commit that broke them can produce an intermediate state in which the tests fail, and if any commit in the range is used as a bisect point or a CI cache key, that intermediate state becomes a real problem. Before a large autosquash on a shared branch, run git rebase -i --autosquash, read the todo, and check that each intermediate commit builds. If you need the sequence provable, git rebase --rebase-merges preserves the merge structure but does not make the sequence buildable; there is no automated answer.

3.4 Cherry-pick and its parent problem

A cherry-pick applies the patch a single commit introduces and creates a new commit with a new parent. The -m option exists because a merge commit’s "patch" is defined relative to a parent, and guessing wrong produces a commit that looks correct and is not.

git cherry-pick A..B is a range walk that applies each commit in the set individually, creating one commit per source commit, in topological order, and stopping at the first conflict. -n applies without committing, which is the mode to use when you want a single squashed result or when you want to inspect the intermediate conflicts. A range is ambiguous — is A..B the commits in B not in A, which is what Git does, or the other way round — and the answer is the first one, and this trips up people who expect A..B to be a symmetric difference.

The -m problem is the substantive one. A merge commit has two parents and therefore two candidate "diffs"; Git’s diff is always between a commit and one of its parents, so there is no such thing as the patch of a merge commit. -m 1 takes the patch from the first parent, which is what you want when a feature branch was merged into main and you want to move the feature’s work onto another line. -m 2 takes it from the second parent, which is what you want in the opposite case. Getting it backwards usually produces a conflict or an empty commit; occasionally it produces a commit that is syntactically valid and semantically nonsense, which is worse.

Cases where cherry-pick produces a wrong result without an error are worth naming explicitly. Picking a commit from a branch that was rebased: the patch may already be present under a different hash, and the result is a duplicate change. Picking a commit whose parent contained a refactor the target lacks: the patch applies if the code is textually similar and produces a subtly different function. Picking a fixup pair separately: the fixup applies to the original’s changes, which the target does not have. The defence in all three cases is the same — after the cherry-pick, diff the result against the source range’s tree and run the tests, which is the verification in 2.6.

Cherry-pick is not a substitute for a revert. git revert of a commit in your history produces an inverse patch and leaves the original visible, which is what an audit wants. 3.5 Squash, fixup and the linear-history illusion

Squashing produces a linear history that is not a complete history. Knowing which commits a squash destroys is what makes the decision about whether to use one an informed one.

There are three distinct squashing mechanisms and they are not interchangeable. merge --squash stages a merge result and leaves HEAD alone: you then make one commit, and the source branch’s commits never enter your history. An interactive rebase with squash rewrites the branch: the commits are combined into one, and the originals are unreachable. A fixup in an interactive rebase combines but discards the fixup commit’s message. Only the second and third rewrite the branch; only the first preserves the source branch as an independent ref you can point at.

The claim "squashed history is cleaner" is about presentation, and the cost is real and specific: the intermediate states, the failed attempts, the "revert that" and "revert the revert" pairs, and the individual authorship of the fixup contributions are all gone from the branch. That last one has a governance dimension — a squash that absorbs a contributor’s commits into one authored by the merger misrepresents who wrote what, and on a project with a DCO or CLA requirement the signed-off trailers are discarded with the commits.

3.6 Reset, restore and the destructive edge

The reset family is a pure function of (ref, index, working tree) triples. Understanding that it never touches untracked files, and knowing exactly which triple each flag selects, is the whole of it.

git reset [<mode>] [<commit>] has an argument-order subtlety that has been a source of accidents for twenty years: git reset [<commit>] -- <paths> is a path reset, which does not move HEAD and only rewrites the index entries for the named paths. git reset <commit> is a mixed reset, which moves HEAD and rewrites the whole index. The -- is the only thing distinguishing them, and a script that interpolates a variable into a reset command without a -- can change the meaning of the command entirely — git reset $FILE moves HEAD to the commit named by that file’s content when the file exists in the repository, which is not what anyone intends.

# The three modes, one commit, one uncommitted change, demonstrated.
$ echo 'draft' > notes.txt && git add notes.txt && git commit -m 'wip: notes'
$ echo 'work' > src/scratch.go
$ function log --oneline -2

$ git commit -m 'wip: notes'   # put it back where it was

$ # HEAD moved. notes.txt is now UNTRACKED: the commit that contained it
# is unreachable, and the file is no longer in the index.

# rewrites the working tree from the target tree, removing extra files
# that were TRACKED, and scratch.go survives because it was never tracked.

$ git checkout -b recovered HEAD@{1}   # the commit is still there
$ git checkout recovered -- notes.txt   # and so is its content

git restore is the two-argument, single-purpose member of the family, added in 2.23 specifically because git checkout overloaded two unrelated meanings onto one command. git restore <paths> takes content from the index by default; git restore --staged <paths> takes content from HEAD into the index. --source=<tree> overrides the source for both. It cannot move HEAD at all — that is the improvement over git checkout <branch>, which does. If you want the old behaviour spelled unambiguously, the equivalences are: git restore <paths> is git checkout -- <paths>, and git restore --staged <paths> is git reset HEAD <paths>.

The destructive edge is precise and worth stating as a rule. reset --hard destroys: the working tree content of every tracked path that differs from the target tree, and the index. It does not destroy: untracked files, untracked files that would be in the way (those cause a refusal), ignored files, or the objects themselves, all of which remain reachable from the reflog. The corollary is that reset --hard is recoverable by default and git clean -fd is not — which is the reverse of most people’s intuition, and the reason the two commands deserve opposite levels of caution.

Deliverable: both diffs, the git log --graph --oneline --all of the result, and the verification from the tip callout: git diff of the affected paths.
  5. Measure what a squash destroys. Build a branch of ten commits containing a WIP, a revert, a revert-of-revert, and two fixups. Squash it with rebase -i --autosquash and then, separately, with a platform-style combined message written by hand. For each, count the commits, the distinct authors, and the number of intermediate states that no longer exist. Run git fsck --unreachable --no-reflogs to show the originals survive, and state the expiry that would remove them. Deliverable: a comparison table with the destruction quantified.

A remote is a named URL plus a pair of refspecs, and almost every remote-related surprise follows from the fact that a fetch is a two-part operation: it updates remote-tracking branches, and it downloads objects into a repository that no ref in the local branch namespace points to. This chapter separates those two effects, because the "your branch is behind" message, the stale remote-tracking branch, and the unexpectedly large .git directory are all symptoms of confusing them. It covers fetch.prune, the difference between push.default modes and why the default changed in Git 2.0, --force-with-lease and --force-if-includes as the two independent safety nets, tag following and transfer.fsckObjects, and the fork workflow including the fetch refspec that a fork needs and a clone does not give you. 4.1 Remotes as configuration

A remote is three pieces of config and one file of bookkeeping. Knowing which is which tells you where to look when a remote behaves unexpectedly.

Adding a remote writes three configuration entries and creates a directory. remote.<name>.url is the fetch URL. remote.<name>.fetch is a refspec describing what a fetch will write and from where. remote.<name>.pushurl, if set, overrides the URL for pushes only, and its presence is invisible in git remote -v output unless you look at the right column. The directory .git/refs/remotes/<name>/ holds the remote-tracking branches, and .git/FETCH_HEAD is overwritten by every fetch with the mapping it just performed — which is why FETCH_HEAD is a useful forensic artefact for "what did this fetch actually get".

The refspec grammar is worth stating precisely, because almost everything about remotes follows from it: <src>:<dst>, where src is a ref name pattern on the remote, dst is a ref name pattern locally, and * matches one path component while ** matches across separators. A leading + means "force", permitting a non-fast-forward update. A refspec with no colon, such as main, is shorthand for refs/heads/main and is only valid on the command line. An empty src means "delete the matching local ref", which is what git push origin :refs/heads/old does.

4.2 Fetch, prune and what a fetch does not do

A fetch does two separable things: it negotiates and downloads objects, and it updates remote-tracking refs. Understanding the separation explains why a fetch can grow .git enormously without changing a single branch, and why deleting a remote branch does not shrink anything locally.

The download step is a negotiation: Git sends the commits the client claims to have, the server sends what is missing, and the client writes those objects into its object database. No ref is involved. The ref-update step then applies the refspec, moving refs/remotes/<remote>/*. The two steps are separable in practice: a fetch interrupted after download leaves objects with no ref pointing at them, and a fetch that updates a ref to a commit whose objects are missing is impossible, so the order is always download-then-update.

The consequence people are surprised by: git fetch on a large repository can add hundreds of megabytes of unreachable-but-soon-reachable objects while git status continues to say "up to date". And the inverse: deleting a branch on the remote removes nothing locally, because the objects it pointed to are still reachable from your local branches and your reflog, and the remote-tracking ref lingers until pruned.

# Watch the two separable effects of a fetch.
$ git count-objects -vH

$ du -sh .git

$ git fetch --verbose origin

$ git fsck --unreachable --no-reflogs 2>/dev/null | grep -c blob
418223

--prune interacts with tags in a way that produces surprise. By default a fetch’s refspec covers refs/heads/* only, so tags are fetched opportunistically: any tag pointing at an object the fetch downloaded is created locally, and nothing else. A tag created on the remote after your last fetch is not seen until a fetch that downloads the commit it points at, which means tag discovery is genuinely non-deterministic. --prune-tags makes the behaviour symmetric by adding a refspec for refs/tags/* to the fetch, and then --prune will delete local tags the remote no longer has — which is why fetch.pruneTags is a setting you enable deliberately and not by default.

Two fetch options are security-relevant rather than convenience features. fetch.fsckObjects validates the received objects with the same machinery as fsck, and transfer.fsckObjects does the same on the sending side, on the server. The second is the one that matters: a repository that accepts pushes should have transfer.fsckObjects=true and receive.fsckObjects=true set, because a client can otherwise push a deliberately malformed object that corrupts the repository for every future user. And fetch.writeCommitGraph lets a fetch write the commit graph as it goes, so a large CI clone gets the acceleration without a separate commit-graph write step.

Set fetch.prune=true globally and fetch.pruneTags=true only where you are sure. Stale remote-tracking branches are the direct cause of "I already deleted that branch" confusion, and pruning on every fetch removes the entire category. Pruning tags is different: a local tag may be something you created deliberately, and a repository whose tags are managed by a release process should not have them silently deleted by a routine fetch. If you do enable it, verify the release pipeline pushes tags to the same remote you fetch from, or you will delete the tags the pipeline published.

4.3 Tracking branches and push.default

A tracking relationship is two config entries with no ref of its own. Which of them a command consults depends on the command, and the mapping is the single most useful table in this chapter.

Setting a tracking relationship writes branch.<name>.remote and branch.<name>.merge. The first names the remote, the second names the ref on that remote — refs/heads/main, not origin/main. git push -u writes both plus, on a hosted platform with the right setup, nothing else; the remote-tracking ref origin/main is created by the push itself, because the push updates the remote and then updates the corresponding remote-tracking ref locally as a side effect of a successful push.

push.default decides where a bare git push goes, and its default changed incompatibly in Git 2.0 from matching to simple. Under simple, a push goes to the branch of the same name on the remote, and only if the local branch’s upstream is either that same branch or is unset. Under upstream, it goes to whatever the upstream says, which is how you push local-topic to origin/topic-for-review. Under current, same name, upstream ignored. Under matching — the old default, and the one people still have configured — every local branch with a same-named remote branch is pushed, which on a repository with a dozen stale local branches pushes a dozen branches and is a genuine incident.

# What push.default=simple does, and when it refuses.

fatal: refusing to push to a destination that is not a full mirror

Two of the client-side guards are complements to a third one, and all three should be on. --force-with-lease without a value is a compare-and-swap: Git records the remote-tracking ref you last saw and refuses the force-push if the destination has moved since. --force-with-lease=<ref>:<expect> pins the expected value explicitly, which is stronger because it does not depend on the remote-tracking ref being current — a git fetch between your push and someone else’s would otherwise update it. --force-if-includes is a different guard: it requires that the reflog of the destination shows your local commits are present, so you cannot remove commits you never had. push.useForceIfIncludes=true makes a plain --force behave as if that flag had been given, which closes the gap where a muscle-memory --force bypasses both guards.

None of this helps if the server is willing to accept anything. On a self-hosted server, receive.denyNonFastForwards=true is the non-negotiable floor: it rejects any update to a ref whose new value is not a descendant of the current one, which means even a bare --force fails and the client must re-fetch and reconcile. receive.denyDeletes=true refuses to let anyone remove a ref at all, which on a mirror is the difference between a repository and a vandalism target. receive.denyCurrentBranch=refuse — the default in a non-bare repository — stops a push from clobbering the working tree that branch is checked out from, and updateInstead changes that refusal into a working-tree update. receive.denyDeletes and receive.denyNonFastForwards are enforced by the receiving process before any hook runs, so they cannot be bypassed by a clever refspec, which is what makes them the floor rather than a policy.

4.4 Tags, refspecs and signed refs

Tags are refs, but they are the only refs whose update is not derived from ancestry. That is why pushing a tag is a non-fast-forward by default and why tag handling needs its own refspec.

A lightweight tag is a ref pointing directly at a commit. An annotated tag is a ref pointing at a tag object, which names a commit and carries a tagger, a message and optionally a signature. Both are updated without a fast-forward check, because the check is an ancestry test and a tag object is not a commit — so Git has no basis for a fast-forward claim and treats every tag update as a force. A push of a tag whose value differs from the remote’s is therefore rejected by the refs/tags/* fast-forward rule on most servers, which is the behaviour you want: a pushed tag is immutable.

Signing is a tag-level property in current Git. tag.gpgSign signs every annotated tag you create; commit.gpgSign signs every commit; and tag.forceSignAnnotated makes git tag -a behave as if -s were given, which removes the most common way unsigned tags get created by accident. Verification is git verify-tag for tags and git verify-commit for commits, both of which check the cryptographic signature and the trust level, and both of which need the keyring to contain the public key.

Refspecs for tags are the reason tag handling is separate in practice. A push uses the push refspec if one exists, otherwise the mirror of the fetch refspec, otherwise refs/heads/*:refs/heads/* — and the default configuration has no tag refspec at all, which is why git push does not push tags and why --follow-tags and --tags exist. A push.followTags push of annotated tags is almost always what a release process wants; a --tags push of every local tag is almost never what anyone wants, because it includes the local tags people made to test things.

4.5 Forks and the upstream relationship

A fork is a repository with a second remote. The refspec that a clone does not give you — upstream/* — is what makes the difference between tracking your own work and tracking the project.

When you fork on a hosted platform, the platform gives you two remotes' worth of URL and nothing else: your fork is where you push, and the original is where the project moves. The default clone refspec covers refs/heads/* on the one remote you cloned, and there is no configuration connecting your local branches to the original. Adding the second remote is one command, and the refspec it installs is the same mirror refspec as any other remote — which is all you need, because the upstream/ namespace is what makes the two histories comparable.

The failure mode is a fork workflow where a developer merges their own origin/main into their upstream/main in the wrong order, producing a local main that is a merge of two unrelated "mains" and a pull request with a diff of nothing. Diagnosing it takes one command: git log --oneline --left-right --cherry-pick main...upstream/main, which shows the two sides of the fork explicitly.

# The fork setup, complete, with the fetch that keeps both in sync.

4.6 Large repositories: shallow, partial, sparse, LFS

Four independent mechanisms reduce clone size and each trades a different capability. Knowing which capability each one costs is the whole of large-repository strategy.

Shallow clones (--depth, --shallow-since, --unshallow) download only the tips of each branch. The repository records the boundary in .git/shallow and Git pretends the missing ancestors do not exist. The cost is ancestry: git log stops at the boundary, git merge-base between a shallow and a deep commit can fail or return a wrong answer, and git bisect cannot walk past it. Partial clones (--filter) download all commits and trees but omit blobs, fetching them on demand from the origin. The repository is fully connected as a graph; the content is not. The cost is that the repository is only usable with network access, and a missing blob becomes a network round trip on a git show.

Sparse checkout (--sparse, sparse-checkout set) materialises only a subset of paths in the working tree. All objects are present; the working tree is partial. The cost is a working tree that does not match HEAD, and every tool that walks the tree must ask Git which paths are in the cone. Git LFS moves large binaries out of the blob store into a separate service, storing a pointer file in Git. The cost is that the real content is not in the repository at all, and a clone without an LFS client gets pointers where files should be.

# Shallow clones: fast, and they lie about history in specific ways.

5 · The Index, Staging Discipline and Undoing Things

5.1 The index as a staging area5.2 Adding precisely5.3 Restoring precisely5.4 The stash, and its two designs5.5 Ignore files, attributes and info/exclude5.6 Sparse, skip-worktree and assume-unchanged

The index is a second tree that nobody looks at directly, and every surprise in the staging area comes from forgetting that it exists. This chapter treats the index as the first-class object it is: a serialised snapshot of an entire tree at .git/index, stage entries and all, with its own consistency invariants that Git checks and reports. It then works through the two directions of staging precisely — add in its whole, partial, interactive, patch and intent-to-add forms, and restore in its staged, worktree and source forms — because the difference between add -p and add -e is the difference between a reviewable commit and an unreviewable one. The stash gets the treatment it deserves: it is a commit with three parents, not a clipboard, which is why stash pop can conflict, why stash drop is only as safe as your reflog, and why --keep-index and --staged do different things. The closing subsections cover the four mechanisms that make Git ignore a file — .gitignore, .git/info/exclude, core.excludesFile and .gitattributes — with their different scopes and the fact that only one of them is committed, and the three bit-manipulation flags that change Git’s view of tracked files without changing their content.

5.1 The index as a staging area

The index is a full tree snapshot on disk, versioned by a checksum, with a format that encodes rename detection and conflict stages. Reading it directly is the fastest way to become accurate about staging.

Every time Git compares the working tree to something, or writes something out to the working tree, it goes through the index. git status compares HEAD to the index, then the index to the working tree. git commit writes the index’s tree into a commit. git checkout writes the index into the working tree and then updates the index from the commit. The index is a serialised file at .git/index (or a split index, or a sparse index, depending on configuration) whose first line is DIRC, whose entries are sorted by path, and whose last twenty bytes are a trailing SHA-1 or SHA-256 over the content. That checksum is why two clones of the same commit can have byte-identical index files, and why a corrupted index is detected rather than silently misread.

Each entry carries stat information — size, mtime, device, inode, mode — so that git status can avoid reading file contents. That optimisation is where the racy git condition comes from: if a file is modified within the same second as the index was written, the stat data can match while the content differs, and Git’s only defence is to re-read the file. You can force the re-read with git update-index --really-refresh and you can turn the optimisation off entirely with core.trustctime=false plus git config core.checkStat minimal, at a cost in status speed.

The shared index and its locking protocol. Every index write takes .git/index.lock, writes a new file, and renames it into place; a failed write leaves the lock behind and every subsequent Git command refuses with fatal: Unable to create '.git/index.lock': File exists. The correct response is to find out what holds it — a stale lock from a killed process, a second Git process on a network filesystem, or an editor plugin — and only then remove it. A lock file containing a PID, which git commit does not write, is a convention of the commit.template hooks people install, not a Git feature. The core.preloadindex and feature.manyFiles settings exist for very large indexes, where the stat cache dominates the cost of every status call.

The index can be out of sync with the working tree in a way that survives a status. The dangerous combination is assume-unchanged on a file that is then modified and committed: status reports nothing, commit writes the old blob because the index entry was never refreshed, and the change is invisible in the commit. The bit is not recorded in the commit, so there is no trace of the file having been touched at all. This is why assume-unchanged should be set deliberately and cleared deliberately, and why a repository containing any assume-unchanged entries should be reported by git ls-files -v | grep -c '^[a-z]' in an audit. skip-worktree is the safer of the two bits for the use people usually want, because it does not suppress content comparison on checkout.

5.2 Adding precisely

The default git add stages a whole file. The flags exist because whole-file staging is frequently the wrong granularity, and the interactive modes are the tools that make a reviewable commit possible.

git add without paths walks the working tree from the current directory and stages every change it finds, including deletions. Its granularity is the file, always. -u restricts it to tracked files, which is the flag that prevents accidentally staging an untracked build artefact; -A and --all do the same thing from the repository root regardless of where you are, which is the historical difference that no longer matters now that pathspecs default to the repository root for git add -A. -f overrides .gitignore for a path you are deliberately adding, and -n is a dry run that prints what would be staged.

The interactive modes are where the value is. -p walks the diff hunk by hunk and asks y, n, q, a, d, s and e, where s splits a hunk at context boundaries and e hands the hunk to your editor for arbitrary editing. -i is -p with an interactive prompt for whole files. -e stages exactly what you leave in the editor, which is the most powerful and the most error-prone. --pathspec-from-file and --pathspec-file-nul take a list of paths from a file, which is how a script stages a computed set without shell-quoting hazards.

# The whole-file default, and the flag that prevents accidents.
$ git status --short

$ git add .

$ git reset && git add -u

$ git status --short

5.3 Restoring precisely

Three operations, one shared idea: choose a source tree and a destination. restore --staged writes the index, restore writes the working tree, and restore --source chooses where the content comes from.

The defaults matter and are asymmetric. git restore <paths> takes content from the index, not from HEAD, which surprises people who expect HEAD. git restore --staged <paths> takes content from HEAD, which matches what git reset HEAD <paths> did and what people expect. So "unstage a file" is restore --staged and "discard a change" is restore, and the two words mean opposite things to the two destinations. The --worktree flag on a --staged command makes it do both, and the shorthand for the very common "stage this and nothing else" is git restore --staged --worktree <path>, which is the porcelain replacement for git checkout HEAD -- <path>.

--source accepts any tree-ish: a commit, a tag, a branch, HEAD~3, a stash entry. Combined with --staged it populates the index from history without touching the working tree, which is how you stage a revert of a file’s history. Combined with --worktree alone it writes the file from history, which is how you extract a file that was deleted in a later commit. The --overlay and --no-overlay flags control what happens to untracked files that the source tree does not contain: by default a restore will not delete them, and --overlay makes it delete files that the checkout would otherwise leave alone.

# The four combinations, and what each writes where.
$ git status --short
M  src/retry.go      # staged
 M src/backoff.go    # unstaged
$ git restore --staged src/retry.go
$ # index := HEAD. Working tree untouched. Now both are unstaged.
$ git restore src/backoff.go
$ # working tree := index. The change is GONE. This is destructive.
$ git restore --source=HEAD --staged --worktree src/retry.go
$ # index := HEAD, working tree := HEAD: a hard revert of one path.
# Extract a file that no longer exists on the current branch.
$ git log --oneline --all -- docs/ARCHITECTURE.md | head -2

$ git restore --source=3a1f0e9 --worktree -- docs/ARCHITECTURE.md

$ git status --short

$ git add docs/ARCHITECTURE.md
$ # Plumbing form: bytes to stdout, no path logic, any name:
$ git cat-file blob HEAD:src/handler.py > /tmp/handler.py

The destructive edge of restore is narrow but sharp. git restore <paths> overwrites working tree content from the index, so the discarded content is gone unless the index’s blob is still reachable — and it usually is not, because the file was never committed in that state. git fsck --unreachable --no-reflogs may find the blob if it was ever staged; git stash before a restore is the reliable answer. The --worktree form with --source is not destructive in the same way when the file is untracked or skip-worktree is set, which is a sparse-checkout path: Git refuses rather than writing outside the cone, and the error names the pathspec.

$ git restore src/backoff.go     # content discarded
$ git fsck --unreachable --no-reflogs 2>/dev/null | grep blob | head -3

+		return 45 * time.Second
$ # Works only if the blob was staged at some point AND gc has not run.
# The reliable prevention, and it costs one command:

$ git restore src/backoff.go && git stash pop
$ # --keep-index leaves the index alone, so staged work is not
# stashed either. This is the "let me try something" wrapper.

# Interaction with skip-worktree, which is the sparse-checkout case:
$ git ls-files -v vendor/big.bin
S vendor/big.bin            # S = skip-worktree
$ git restore --worktree -- vendor/big.bin
error: pathspec 'vendor/big.bin' did not match any file(s) known to git

$ git update-index --no-skip-worktree vendor/big.bin

restore --staged on a path that does not exist in HEAD creates an empty-file entry rather than removing it. git restore --staged <newfile> where <newfile> is newly added and not in HEAD writes the HEAD version of that path, which does not exist, and the result is that the path is removed from the index — which is what you wanted — but only because Git treats a missing source as a deletion. The confusing case is a path that exists in HEAD and not in the working tree: restore --staged un-stages the deletion, putting the old content back in the index while the file remains absent on disk, so status then shows it as deleted in the working tree and unmodified in the index. That is arithmetically correct and reads as a bug. The unambiguous way to un-stage a deletion is git reset HEAD -- <path>, which is the same command and the same result; the confusion is in the reading, not the doing.

5.4 The stash, and its two designs

A stash entry is a commit with two or three parents that encodes the index and the working tree. Understanding it as a commit explains every stash behaviour, including the ones that lose work.

git stash push writes a merge commit whose first parent is HEAD, whose second parent is a commit holding the index state, and — when there were untracked files and -u was given — whose third parent holds them. It then resets the working tree and index to HEAD. That is why git stash on a repository with no changes reports No local changes to save and writes nothing, and why git stash show -p shows a diff against the first parent that includes the staged and unstaged changes together. git stash list is a reflog of refs/stash, so refs/stash@{2} is the third-most-recent and is a real commit you can diff, check out or branch.

The two designs are the stash as commit and the newer git stash create plus git stash store pair, which lets you build a stash object without moving refs/stash. That is what you want in a script that wants to snapshot the current state, run something, and restore it — because git stash create leaves the working tree alone and returns a commit hash, and git stash store is the separate decision to record it in the stash list. The pattern that replaces most scripted stashing is git stash create plus a git reset --hard plus a later git stash apply <hash>.

Never use the stash as a branch, and never stash clear while investigating. A stash is a commit with a ninety-day reflog expiry, not a ref you named. Ten stashes in, the one you want is stash@{7}, and tomorrow it is stash@{4} and you have started a rebase in between. When work needs to be set aside for more than a few minutes, make a branch: git switch -c wip/retry-budget && git commit -m 'WIP' && git switch main. It is one command longer than a stash and it cannot be lost, cannot be reordered by a subsequent stash, and shows up in git branch where you will see it.

5.5 Ignore files, attributes and info/exclude

There are four mechanisms that make Git ignore a path, they have different scopes, and only one of them travels with the repository. Knowing which is which prevents every version of "it works on my machine".

.gitignore files are committed, are hierarchical, and a rule in a deeper file overrides a rule in a shallower one. The last matching pattern wins, so order matters within a file and depth matters across files. Negation with ! re-includes, but a file cannot be re-included if a parent directory is excluded — the classic trap, where build/* plus !build/keep.txt does not work and build/* plus !build/ plus build/* plus !build/keep.txt does. .git/info/exclude is per-clone and uncommitted. core.excludesFile is per-user, conventionally ~/.config/git/ignore. .gitattributes is committed and is not an ignore mechanism at all: it configures filters, eol conversion, diff drivers, merge drivers and export-ignore, and it is the only one of the four that applies to other people.

The pattern syntax has four rules that cover almost every surprise. A pattern with no slash matches the basename at any depth, so *.log matches a/b/c.log. A pattern with a slash is anchored to the directory containing the .gitignore, so /build matches only at the top level. A trailing slash matches directories only. A leading **/ or a /**/ matches at any depth. Everything else is fnmatch with * not crossing a slash.

5.6 Sparse, skip-worktree and assume-unchanged

Two index bits and two index modes change what Git believes about a tracked file. They are routinely confused with each other, they are not interchangeable, and using the wrong one causes silent data loss.

assume-unchanged tells Git not to check the file’s content, full stop. The entry keeps a flag and status, diff and add all treat the file as unchanged regardless of what is on disk. skip-worktree tells Git the file does not exist in this working tree — which is what sparse checkout needs — and it is honoured differently by different commands. diff compares the index against HEAD and reports changes, which for a skip-worktree file are real changes in the index. status does not check the working tree for it, so a local modification to a skip-worktree file is invisible. The rule is: assume-unchanged for files you want Git to leave alone; skip-worktree for files that genuinely are not here, and the second only if you are using sparse checkout, which manages the bit for you.

# The two bits, and the difference in behaviour, demonstrated.
$ git ls-files -v config/local.yml

$ git update-index --assume-unchanged config/local.yml
$ git ls-files -v config/local.yml

$ echo 'debug: true' >> config/local.yml && git status --short

# records the file as unchanged while it differs on disk.
$ git commit -m 'chore: unrelated' && git show --stat HEAD | tail -1

$ git update-index --no-assume-unchanged config/local.yml
$ git status --short

Assert the index’s integrity in CI, because the two failure modes are silent. Two conditions catch almost everything: git diff --quiet after checkout fails the build if the checkout produced working tree content that differs from the index, which catches a broken smudge filter, a failed LFS pull and a half-completed checkout; and git ls-files -i --exclude-standard returning anything catches a .gitignore that was changed without untracking the files it now excludes. Both are three-line shell scripts, and both catch failures that otherwise surface as a mysterious test failure several steps later. Add git fsck --strict --no-dangling for object integrity and you have a complete pre-build assertion for the index, the tree and the object store.

6.1 Recovering a lost commit

Almost nothing is destroyed immediately. The reflog records every ref movement, and an object survives until garbage collection, which means the recovery window is measured in days by default.

Every operation that moves a ref appends a line to that ref’s reflog and to HEAD's reflog, naming the old value, the new value, the committer identity and a message. A commit becomes unreachable only when no ref and no reflog entry names it. In practice this means the four common loss scenarios are all recoverable: a reset --hard that discarded a commit, a branch -D on a branch you had not pushed, a rebase whose original commits are no longer on any branch, and a commit --amend that replaced a commit you wanted to keep. All four leave the objects in place, reachable from a reflog entry, until gc prunes them.

The expiry windows are the constraint. gc.reflogExpire defaults to 90 days for entries whose commit is still reachable and 30 days for entries whose commit is not, and gc.pruneExpire defaults to two weeks for unreachable loose objects. The interaction is that a lost commit gets the 30-day window, not the 90-day one, and the window starts when the reflog entry is written rather than when you notice the loss. If you know you have lost something, git reflog expire --expire=now --all followed by git gc --prune=now destroys it permanently, and it is worth knowing that command exists precisely so that you know not to run it.

# Scenario 1: a reset --hard threw away a commit you wanted.
$ function log --oneline -2
7f6e5d4 feat: add the retry budget
$ git reset --hard HEAD~1
HEAD is now at 3a1f0e base
$ # It is gone from the branch. It is not gone from the repository.
$ function reflog show HEAD -4

Two mechanisms let you tell Git that history is different from what it is, for a specific purpose, without rewriting anything. A replace ref is refs/replace/<object> pointing at a different object; Git substitutes it transparently in nearly every traversal, so a rewritten commit appears to have its original hash. Grafts are the older mechanism, a file of <commit> <parent> lines in .git/info/grafts, and they are deprecated in favour of replace refs. Both are local by default and both must be pushed to be shared, which is why a shallow clone is implementable as a graft file and why the combination of replace refs and a server that does not honour them is a source of confusion that only appears on one machine.

# Replace refs: lie to Git about one object, locally.
$ NEW=$(git commit-tree HEAD^{tree} -p HEAD^ -m 'alternative message')
$ git replace HEAD $NEW
$ function replace -l
3a1f0e9c4b7d2a8e5f6c1b3d4e5f60718293a4b5
$ function log -1 --format='%H %s'

$ # ^ the ORIGINAL hash with the new content. Every traversal - log, diff,
#   bisect - sees the replacement. `--no-replace-objects` bypasses it.
$ git replace -d 3a1f0e9c4b7d2a8e5f6c1b3d4e5f60718293a4b5
$ GIT_NO_REPLACE_OBJECTS=1 function log -1 --format=%s

# Replace refs can change a commit's PARENTS, which changes ancestry:
$ NO_PARENT=$(git commit-tree HEAD^{tree} -m 'as if it were a root commit')
$ git replace HEAD $NO_PARENT
$ function log --oneline | wc -l
1
$ git replace -d HEAD

Protecting against expiry while you investigate. The moment you suspect a loss, name the objects: git branch rescue/<what> <hash> for a commit, or git tag rescue/<what> <hash> for anything else. A ref is a reflog entry that does not expire, so naming the object converts a 30-day window into an indefinite one. If you do not yet know which object it is, git reflog --all --date=iso > reflog-$(date +%F).txt captures every reflog in the repository to a file outside .git, and that file is then your index for the search. It costs one command and it removes the clock entirely.

6.2 Bisect, manually and with bisect run

Bisect is a binary search over the commit graph with a human or a script in the loop. Its correctness depends on the test being a function of the commit alone, and almost every bisect that goes wrong is a violation of that.

git bisect start records a good commit, a bad commit, and every commit reachable from bad but not from good as a candidate. git bisect good and git bisect bad mark a candidate and Git checks out a midpoint. The search ends when one candidate remains, and git bisect log records every judgement so the whole session is auditable and reproducible with git bisect replay. git bisect reset returns to where you started; git bisect terms and git bisect skip handle the case where a commit cannot be classified, which is a legitimate outcome and the reason skip exists rather than forcing a false judgement.

git bisect run automates the judgement by executing a command at each candidate and reading its exit status: 0 means good, 1 to 124 (excluding 125) means bad, 125 means "skip this commit", and anything above 127 is an error that aborts the bisect. That contract is precise, and the most common failure is a test script that returns 1 for "the test infrastructure broke" — a compile error on a commit that predates a dependency, say. Such a commit will be reported as the culprit, confidently and wrongly.

# bisect run: the exit-code contract, which is the whole mechanism.
$ cat > /tmp/check-incident.sh <<'SH'
#!/bin/sh
# 0    -> good (the bug is not present)
# 1-124 -> bad  (the bug reproduces)
# 125  -> skip (this commit cannot be classified)
# >127 -> error, and the bisect ABORTS
go build ./... 2>/dev/null || exit 125   # will not build: skip
if go test ./internal/retry/ -run TestRetryBudget -count=1 >/dev/null 2>&1; then
  exit 0        # test passes: the bug is absent
else
  exit 1        # test fails: the bug is present
fi
SH
$ # Guard the shallow boundary explicitly. 125 skips; 1 would lie.
$ chmod +x /tmp/check-incident.sh
$ git bisect start HEAD v4.2.0
$ git bisect run /tmp/check-incident.sh
Bisecting: 101 revisions left to test after this (roughly 7 steps)
[7d6c5b4...] feat: retry budget
running /tmp/check-incident.sh
2c3d4e5... is the first bad commit
commit 2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8091a2b3c4d
Author: R Okonkwo <r.okonkwo@example.com>
Date:   Fri Sep 12 14:22:03 2025 +0100

    fix: clamp the backoff ceiling to the local maximum
$ git bisect log
# 8 steps for 203 revisions. A linear manual bisect would be 203.
$ git bisect reset

Three failure modes account for essentially all wrong bisect results. A non-hermetic test. If the test reads the current time, the network, a database row, or an environment variable that CI sets differently, it is not a function of the commit, and the bisect’s premise is violated. Skip accumulation. Skipped commits are excluded from the final answer, so a bisect with many skips can converge on a commit adjacent to the real one and report it as "the first bad commit" with no indication that the answer is approximate; git bisect log is where you find out. Merges. The bisect walks the commit graph as a DAG and treats every commit in the range as a candidate, so a merge commit and its parents are all candidates and the answer can be a commit that is not on any release line. git bisect --first-parent restricts the walk to the first-parent chain, which is what you want for a repository with a long release branch.

A bisect that is interrupted half-way leaves the repository in a detached, mid-bisect state that git bisect reset clears — but only if you remember to run it, and a forgotten bisect state is a genuinely confusing thing to find in a repository the next morning. Adding git bisect reset to a shell trap, or doing the whole thing inside git worktree add --detach and removing the worktree afterwards, removes the failure mode entirely.

6.3 Rewriting history with filter-repo

A history rewrite changes every commit hash downstream of the change. Understanding that consequence, and the four jobs a rewrite is actually done for, is what makes the operation safe to perform.

There are exactly four reasons to rewrite history, and each has a well-understood procedure. Removing a secret that was committed: rewrite every commit that contains the blob, then coordinate a force-push and require everyone to re-clone. Changing file paths — moving a directory, changing a case, splitting a monorepo: rewrite the paths in every commit. Editing commit metadata — fixing an author, stripping an email from an old commit, normalising message trailers: rewrite the commit objects themselves. Reducing size by dropping a large file from history: the object stops being reachable, and a subsequent gc reclaims it.

git filter-repo is a standalone Python tool that is not part of Git, is installed separately, and must be run against a fresh clone. It rewrites the object database rather than checking out and recommitting, so it handles hundreds of thousands of commits in minutes, it produces correct merge topology, and it removes the refs/original backup that filter-branch leaves behind — which is both a feature and a trap, because it means the pre-rewrite state is not in the repository at all. Its safety mechanism is the fresh-clone requirement: it refuses to run on a non-bare clone that has a working tree with a non-origin remote, and it removes origin to prevent an accidental push of the rewritten history.

# Job 1: remove a secret from every commit that contains it.
$ git clone --mirror https://github.com/acme/svc.git svc-rewrite.git
$ cd svc-rewrite.git
$ git filter-repo --path config/secrets.yaml --invert-paths --replace-refs delete-no-add
$ # The secret's blob is now unreachable, but still in the object
# database. Reclaim it, then verify it is GONE, not just unreachable.
$ git reflog expire --expire=now --all
$ git gc --prune=now --aggressive
$ git cat-file --batch-all-objects --batch-check='%(objectname) %(objecttype)' | \
    while read oid type; do
      [ "$type" = blob ] && git cat-file blob "$oid" 2>/dev/null | grep -q 'AKIA' && echo "STILL PRESENT: $oid"
    done
$ # Empty output is the only acceptable output. Verify in a FRESH
# clone of the rewritten repository, not in this one.
$ git log --all --oneline -- config/secrets.yaml | wc -l

$ git log --all -S 'AKIAIOSFODNN7EXAMPLE' --oneline | wc -l

The most common way a rewrite goes wrong is doing it on a working clone and pushing from there. filter-repo deliberately removes the origin remote to prevent exactly this, and --force will happily push the rewritten history to the original repository, which replaces the whole project history for everyone. The second most common is assuming the rewrite is complete because the working tree looks right. A rewrite is complete when a fresh clone of the rewritten repository contains no trace of the content — verified with git log --all -S for a string, git log --all -- <path> for a path, and a blob scan as in the first block. A working tree that has been checked out fresh from the rewritten history proves nothing about the old commits, because they are not reachable from the new tips and therefore were not checked out.

6.4 filter-branch, and why it is deprecated

The shell script that predates all of this, kept in the Git distribution for backwards compatibility. Understanding exactly how it fails is the strongest argument for filter-repo.

git filter-branch works by checking out each commit in turn, applying a command that rewrites the working tree, and committing the result — a full checkout and commit per commit, per branch. It emits a warning on every invocation telling you to use filter-repo instead, and the warning is accurate for four reasons. It is quadratic in a way that is not documented: on a repository with merges, a commit reachable by several paths is rewritten once per path, so the cost is the square of the number of merges. It is shell-script fragile, with quoting that breaks on paths with spaces and on the -- in a pathspec. It leaves the pre-rewrite state in refs/original/, which means the "removed" secret is still reachable in the repository and a casual git log --all still finds it. And it refuses to run on a dirty tree, which is correct and is also the source of a common workaround that is not.

# The dirty-tree refusal, and the workaround that is NOT safe.

6.5 Forensics: when did this line enter?

Two questions with exact answers: when did a piece of content first appear, and which commit last changed a given line. Git has a dedicated command for each, and both have non-obvious defaults.

git log -S<string> performs a pickaxe search: it reports the commits where the count of occurrences of the string changed, which means both the commit that added it and the commit that removed it, plus any commit that added a second occurrence. --pickaxe-all reports the commits that changed the count rather than requiring the addition to be on a specific side of the diff, which is what you usually want. -G<regex> is the same idea with a regular expression and is the better tool for structured content, because it will match a logfmt key or a function signature rather than requiring you to know the exact text. Both are slower than a plain log because every diff is computed, and both can be scoped with --<path> before they are run.

git blame attributes each line to the commit that last modified it, and its defaults are tuned for a small file in a small repository, not for a generated file or a heavily refactored one. The three flags that matter are -C, which detects a line moved from another file and attributes it to the file it came from; -M, which detects a line moved within the same file; and -w, which ignores whitespace when detecting both. Without them, a code movement reads as a deletion in one place and an addition in another, and a reformat reads as the rewriting of every line in the file — which is why a blame on a formatted file names the formatter and is worthless.

# When did this line enter the codebase, and who removed it.
$ function log --oneline -S'legacy-token-redirect' --all
9f8e7d6 feat: add the legacy token redirect shim
2c3d4e5 fix: remove the legacy token redirect
$ # TWO commits: the addition and the removal. Read which is which:
$ function log -S'legacy-token-redirect' --pickaxe-all --oneline --reverse
2c3d4e5 fix: remove the legacy token redirect
9f8e7d6 feat: add the legacy token redirect shim
$ # --reverse puts the story in order. `--all` includes every ref, which
# matters when the line was added on a branch that was never merged.
$ function show 9f8e7d6 --stat
 internal/auth/redirect.go | 24 ++++++++++++++++++++++++
$ # -G with a regex, for structured content:
$ function log --oneline -G'func\s+\(.*\)\s+Retry\(' --all
8b2c4d6 feat: add the retry budget
2c3d4e5 fix: clamp the backoff ceiling
$ # And -S with a regex, for content whose exact text you do not know:
$ function log --oneline -S'RETRY_BUDGET' --pickaxe-regex --all
$ # --pickaxe-regex makes the -S argument a regex. Slower, and it will
# match substrings; anchor it with \b if that matters.
$ # Combined with --follow to track a file across renames:
$ function log --oneline --follow -S'RETRY_BUDGET' -- internal/retry/budget.go
8b2c4d6 feat: add the retry budget
4d5e6f7 chore: move the retry code into its own package
1d2c3b4 initial commit
$ # --follow works on a single path and stops at a merge that changed the
# path on both sides, reporting "no such path" in the other parent. It is
# a linear walk pretending to be a graph walk, and that is a real limit.

# The four questions, and the command that answers each. Verified form.
$ # 1. When was this exact string introduced?
$ function log --diff-filter=A --oneline -- path/to/new/file
$ git log --format='%H %aI %an' -S'string' --reverse -- path/to/file | head -1
$ # --reverse | head -1 gives the introduction, not the last change.

# 2. Which release first contained it?
$ git tag --contains 9f8e7d6 | sort -V | head -1
v4.3.0
$ git describe --contains --match 'v*' 9f8e7d6
v4.3.0~12
$ # `--contains` is a reachability question, not a date one. A tag on a
# release BRANCH is in later tags too, so sort and take one.
# 3. Which commits touched this file in the window of interest?
$ function log --oneline --since=2025-09-01 --until=2025-09-15 -- internal/
$ git log -L 42,58:internal/retry/budget.go --oneline
9f8e7d6 feat: add the legacy token redirect shim
2c3d4e5 fix: clamp the backoff ceiling to the local maximum
8b2c4d6 feat: add the retry budget
$ # `log -L` is the one command that shows the HISTORY OF A LINE RANGE,
# including the text at each revision. It answers "what did this
# function look like when the incident happened".
# 4. Was this file ever at a different path? (the --follow question)
$ function log --follow --name-status --oneline -- internal/retry/budget.go
9f8e7d6 chore: move the retry code into its own package
R100  internal/auth/retry.go -> internal/retry/budget.go
4d5e6f7 chore: rename retry to budget across the tree

$ # R100 means a 100% similarity rename. The score is Git's measure,
# and it is what a rename-detection-heavy log looks like.

git log -S on a large repository is slow, and on a repository with a shallow boundary it is wrong. The pickaxe computes a diff for every commit in the range, which on a monorepo with binary content is minutes, not seconds. Always scope with -- <path> and --since before you run it, and prefer -G over -S when either will do since -G can be answered from the diff text without counting occurrences. The correctness problem is the same one as everywhere else in this chapter: on a shallow clone the range stops at the boundary, so -S reports the first commit present and not the first commit that ever contained the string. For a forensic question of the form "when did this enter the codebase", a shallow clone produces a confidently wrong answer, and the guard is the same one line: assert --is-shallow-repository is false before trusting a pickaxe result.

6.6 Integrity, fsck and verification

Git can tell you whether the object database is internally consistent and whether a commit or tag was signed by the key you expect. The checks are cheap, and almost nobody runs them.

git fsck validates that every object it can reach is well-formed and that the graph is connected. --strict turns on every additional check, which is what you want: it includes zero-padded file modes, tree entries with the wrong sort order, and missing author or committer fields. --full additionally checks every alternate object database and every pack, rather than trusting the index’s record of what is present. --unreachable reports objects no ref reaches, which after a rebase or a squash is the normal and expected output, and is not an error. fsck.skipList names a list of known issues to suppress, and its existence is a warning: a project using it has decided some corruption is tolerable.

Signature verification is a different question. verify-commit checks that a commit carries a valid signature from a key in your keyring; verify-tag does the same for a tag and additionally reports the tag’s target. Both need gpg.program to work, both need the public key imported, and both distinguish three outcomes: a good signature from an ultimate key, a good signature from a key whose trust you have not established, and no signature at all — the last of which is reported as error: no signature found and is a failure, not a pass. A commit signed by a key that is in the keyring but has no owner trust produces a warning that people routinely read as success.

# fsck: the forms, and what each is for.
$ git fsck
Checking object directories: 100% (1841/1841), done.
$ git fsck --strict --full
Checking object directories: 100% (1841/1841), done.
Checking objects: 100% (2841/2841), done.
$ # --strict includes: mode 0000/7777, tree sort order, missing author,
# malformed numbers in trees, and duplicate entries. Use it always.
$ git fsck --unreachable --no-reflogs 2>&1 | grep -c unreachable
418
$ # Unreachable is NOT an error. After a rebase or a squash it is expected,
# and it is how you find a lost commit. It becomes an error when
# the count is non-zero on a mirror you believe is clean.
$ git fsck --connectivity-only            # fast: no content validation
$ git fsck --no-dangling                   # suppress dangling tips
