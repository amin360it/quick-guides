Java is a statically typed, class-based language compiled to an intermediate bytecode that runs on the Java Virtual Machine. This guide is written against Java 25 LTS (released September 2025) and notes where a construct needs Java 21 LTS or is newer than it. Everything is real, runnable code; nothing depends on an IDE.

0.1 JDK, JRE and JVM: what each one is

The three acronyms name three different things that are often installed as one package. Getting the boundary right explains most "it works in my IDE but not on the server" problems.

The execution pipeline

Java source (a .java text file) is not executed directly. javac translates it to bytecode (a .class file), a compact, stack-based instruction set defined by the Java Virtual Machine Specification. The JVM then loads and runs that bytecode, translating hot paths to native machine code at runtime. Because the bytecode format and the JVM's semantics are specified independently of any CPU, one compiled artifact runs unmodified on every platform that has a compliant JVM — the "write once, run anywhere" property.

A JRE (Java Runtime Environment) is a JVM plus the core class library, enough to run compiled programs but not to compile them. Since JDK 9 the JRE is no longer shipped as a separate download for desktop use; instead the JDK itself, plus the jlink tool, is used to build a custom runtime image containing only the modules an application needs. A JDK (Java Development Kit) is a JRE plus the development tools: javac, jar, javadoc, jshell, jlink, jpackage, jcmd, jconsole and the rest.

Versioning is not what it looks like

java -version prints the feature version first, then the build. The old 1.8.0_402 style has been gone since JDK 9: Java 8 is 1.8, but Java 9 onwards is just 9, 21, 25. The JDK's own version string and the --release flag you compile with are separate concerns, and javac --release 21 on a JDK 25 compiler produces a class file that runs on a Java 21 runtime — this is the supported way to target an older LTS, and it is stricter than the obsolete -source/-target pair because it also checks the API surface.

# shell - one command answers "what am I running?"
java -version          # openjdk version "25.0.1" 2025-10-21 LTS
javac -version         # javac 25.0.1
java -XshowSettings:properties -version 2>>&1 | grep -i java.home

# Compile for an older LTS and prove the class file version.
javac --release 21 -d out src/Main.java
javap -verbose out/Main.class | grep 'major version'   # major version: 65
A class file's major version is the feature version + 44: Java 8 is 52, Java 11 is 55, Java 17 is 61, Java 21 is 65, Java 25 is 69. When a runtime refuses to load a class with UnsupportedClassVersionError, this number is the whole story.

0.2 Installing a JDK: Temurin, vendors and SDKMAN

There is one language specification and many JDK builds of it. Choosing a build is a support question, not a language question, and the choice is easily reversed because they all pass the same compliance tests.

Which build to pick

Eclipse Temurin (the Adoptium project) is the most widely deployed no-cost build and the safest default: it is TCK-tested, has a predictable quarterly patch cadence, and publishes long-term support for the LTS lines. Oracle JDK is the reference build and is free for development and for production use under the NFTC licence, but its support terms differ from Temurin's. Amazon Corretto, Azul Zulu, Microsoft Build of OpenJDK and BellSoft Liberica are all TCK-compliant alternatives; the practical differences are patch timing, additional collectors or profilers bundled in, and the commercial support contract behind them. What you must not do is pick the jre-only package if you intend to compile, or a non-LTS feature release if you want a five-year patch commitment.

Installing one, or several

On Linux the distribution package manager is fine for a single JDK, but most developers need to move between versions per project. SDKMAN handles that on macOS, Linux and WSL/Git Bash, and jenv or asdf do the same job. On Windows, either the Temurin MSI plus a manual JAVA_HOME change, or SDKMAN inside WSL, works; the JDK that Gradle and Maven use is chosen by JAVA_HOME, while the JDK that runs your shell commands is chosen by PATH. Confusing those two is the single most common build-environment bug.

# shell - SDKMAN, the cross-platform route
curl -s "https://get.sdkman.io" | bash
source "$HOME/.sdkman/bin/sdkman-init.sh"
sdk list java                 # every vendor and version, with an install id
sdk install java 25.0.1-tem   # Temurin 25 LTS
sdk install java 21.0.5-tem   # keep an older LTS beside it
sdk use java 21.0.5-tem       # current shell only
sdk default java 25.0.1-tem   # persist

# Pin the JDK for a directory (jenv), so `java` follows `cd`.
jenv add /Library/Java/JavaVirtualMachines/temurin-25.jdk/Contents/Home
echo 25 > .java-version
Set JAVA_HOME and never rely on a shim script to guess it. Gradle, Maven, Tomcat, most CI images and the Spring Boot Maven plugin all read JAVA_HOME directly, and a stale value silently builds with the wrong compiler while java -version in your terminal shows the right one.

0.3 Your first program: javac, java, and the classpath

A minimal Java program makes the compilation model concrete: the file name, the public type name and the way the launcher finds the entry point are all connected.

Source to running process

A public top-level type must live in a file whose name matches it exactly, case included: Greeter.java holds public class Greeter. The launcher needs a static void main(String[] args) method as its entry point. In Java 25, JEP 512 relaxed both rules — a single-file program may omit the class declaration and may use an instance void main() — which makes the teaching example genuinely shorter without changing how larger programs work.

// Greeter.java - the classic form; compiles on every version from Java 8 up
public class Greeter {
    public static void main(String[] args) {
        String who = args.length > 0 ? args[0] : "world";
        System.out.println("Hello, " + who + "!");
    }
}

# shell - compile then run
javac Greeter.java          # writes Greeter.class beside the source
java Greeter Ada            # Hello, Ada!

# Since Java 11 you can skip the explicit compile for a single file:
java Greeter.java Ada       # compiles in memory, runs, no .class left behind
java --enable-preview Greeter.java

The compact source file (Java 25)

Java 25 finalised compact source files and instance main methods. A file may contain bare statements; the compiler wraps them in an implicit class, and main need not be static or public. This is a real language change, not a script mode: the file still compiles to a normal class, and you grow into the explicit form by adding the class declaration when you need more than one method.

// Hello.java - Java 25 compact source file
void main() {
    System.out.println("Hello from a compact source file");
    for (int i = 1; i <= 3; i++) System.out.println("line " + i);
}

The classpath

java locates classes by searching the classpath: directories and jar files, separated by ; on Windows and : elsewhere. If a class is not on the classpath the launcher reports ClassNotFoundException or NoClassDefFoundError; if it is, but has no suitable main, the message is Main method not found. Since JDK 9 the more robust mechanism is the module path, where each jar declares which packages it exports and which it needs, but the classpath remains the default for the whole Maven Central ecosystem.

# shell - putting a directory and a jar on the classpath
java -cp "out;lib/gson-2.11.0.jar" com.acme.Main
java -classpath out:lib/postgresql-42.7.4.jar com.acme.Main   # Unix

# A runnable jar records its own Main-Class, so no -cp is needed:
java -jar app.jar

0.4 JShell: a read-eval-print loop for Java

JShell (JEP 222, standard since JDK 9) is an interactive tool that evaluates Java snippets without a class, a file or a compile step. It is the fastest way to check what an API actually does, and it is a first-class debugging aid rather than a teaching toy.

How it differs from compiling a scratch file

JShell maintains a live set of declarations. Typing an expression prints its value and type; typing a method adds it to the current session; typing a class behaves as if you had written it. Snippets are numbered, and /edit, /list, /vars, /methods, /history and /save operate on that numbered state. Uncaught exceptions do not terminate the session — they print and the prompt returns, which is exactly the behaviour you want when exploring an unfamiliar library.

# shell
jshell --enable-preview

// JShell session (the | marks the REPL, not source code)
|  Welcome to JShell -- Version 25.0.1
|  For an introduction type: /help intro

jshell> var names = java.util.List.of("Ada", "Grace", "Barbara");
names ==> [Ada, Grace, Barbara]

jshell> names.stream().map(String::toUpperCase).sorted().toList()
$2 ==> [ADA, BARBARA, GRACE]

jshell> String.format("%,.2f", 1234567.891)
$3 ==> "1,234,567.89"

jshell> /vars
|    List<String> names = [Ada, Grace, Barbara]
|    List<String> $2 = [ADA, BARBARA, GRACE]

jshell> /save scratch.jsh

Fed from a file or piped, for reproducibility

JShell reads a script with /open script.jsh or jshell --execution local script.jsh, which turns it into a lightweight test harness. Because the startup cost is roughly a second once warmed, it is also useful for a quick benchmark of two implementations — though for anything that needs a real measurement you should use JMH, covered in the JVM chapter.

# shell - a .jsh file is just a series of snippets
cat > check.jsh <<'EOF'
String s = "  hello  ";
System.out.println("[" + s.strip() + "]");
System.out.println(Character.isDigit('7'));
EOF
jshell --execution local check.jsh
JShell evaluates snippets with the same security context as any other JVM process. It is a developer tool, not a sandbox: a pasted snippet can read files and open sockets. Do not run unknown snippets on a machine you care about.

1.1 Primitive types, literals and widening

Java has eight primitive types and they have specified, platform-independent widths. That is unusual and valuable: a long is exactly 64 bits everywhere, so a binary file format written on one machine reads correctly on another.

The eight types and what each is for

Use int for almost all whole numbers and long when a value can exceed about two billion — file sizes, epoch milliseconds, ID spaces. byte and short exist mainly for binary formats and for arrays where memory density matters; arithmetic on them promotes to int first. double is the default for real numbers and follows IEEE 754, which means it cannot represent most decimal fractions exactly; for money use BigDecimal or a minor-unit long, never double. char is a single UTF-16 code unit, not a full Unicode character — an emoji is two chars, which is why String iteration by index is not the same as iteration by code point.

Widening, narrowing and the overflow that does not throw

Assignment from a narrower to a wider primitive (byte to int) is silent and lossless. The reverse requires an explicit cast and truncates; it never throws. Integer arithmetic wraps silently, so Integer.MAX_VALUE + 1 is Integer.MIN_VALUE. This is the behaviour you want in a hash function and the behaviour you do not want in a counter — use Math.addExact, Math.multiplyExact or long/BigInteger where the range is genuinely in doubt. Integer division truncates toward zero, and dividing a negative by a positive follows that rule, which surprises people migrating from languages that round down.

// Widening is implicit; narrowing needs a cast and can silently corrupt.
int big = 130;
byte truncated = (byte) big;              // -126  (130 - 256)

long max = Integer.MAX_VALUE;
int wrapped = (int) (max + 1);            // -2147483648, no exception

try {
    int safe = Math.addExact(Integer.MAX_VALUE, 1);
} catch (ArithmeticException e) {
    System.out.println("overflow detected: " + e.getMessage());
}

// Integer division truncates toward zero.
System.out.println(7 / 2);                // 3
System.out.println(-7 / 2);               // -3
System.out.println(7 % -2);               // 1
System.out.println(7.0 / 2);              // 3.5

// Underscores are ignored; 0x / 0b / 0o select the radix.
long salary = 1_250_000L;
int mask = 0b1011_0000;
System.out.printf("%d %s %s%n", salary, Integer.toBinaryString(mask), Integer.toHexString(255));
Never use == to compare floating-point values for equality, including against 0.0. 0.1 + 0.2 == 0.3 is false. Compare the absolute difference against a tolerance, or use BigDecimal with an explicit scale and RoundingMode for money and measurement.

1.2 Operators, precedence and short-circuit evaluation

The operator set is small and C-derived. Two things repay attention: the difference between the boolean operators that short-circuit and those that do not, and the precedence of the bitwise operators, which is lower than most people assume.

Short-circuit versus eager boolean operators

&& and || evaluate the right operand only when the result is not already determined. & and | on booleans evaluate both sides always. That distinction is not stylistic: list != null && !list.isEmpty() is safe, list != null & !list.isEmpty() throws NullPointerException. The eager forms are only appropriate when both operands are side-effecting and both effects are wanted, which is rare.

// Short-circuit guards the dereference.
String s = null;
boolean safe   = s != null && s.length() > 0;    // false, no NPE
// boolean boom = s != null &  s.length() > 0;   // NullPointerException

// Bit tricks on ints: | and & are bitwise here.
int READ = 0b001, WRITE = 0b010, EXEC = 0b100;
int perms = READ | WRITE;                 // 3
boolean canExec = (perms & EXEC) != 0;     // false
perms |= EXEC;                            // 7
perms &= ~WRITE;                           // 5
System.out.println(Integer.toBinaryString(perms));   // 101

// Ternary, and the ternary-with-autoboxing trap.
int n = 7;
String parity = (n % 2 == 0) ? "even" : "odd";

Precedence and the instanceOf-and-cast idiom

Precedence runs, from tightest to loosest: postfix, unary, cast, multiplicative, additive, shift, relational, equality, bitwise AND, bitwise XOR, bitwise OR, logical AND, logical OR, ternary, assignment. The shift and bitwise operators bind looser than equality, so a & b == c parses as a & (b == c) and does not compile on ints. Parenthesise bit manipulation. Since Java 16 the instanceof pattern removes the cast: if (obj instanceof String s) binds s in the true branch, and the compiler knows it is in scope.

Object value = "forty-two";
// Old idiom: check, then cast, then use.
if (value instanceof String) {
    String s = (String) value;
    System.out.println(s.length());
}
// Since Java 16: the binding is part of the test.
if (value instanceof String s && s.length() > 3) {
    System.out.println(s.toUpperCase());     // FORTY-TWO
}

// Shifts: >> is arithmetic (sign-extending), >>> is logical.
int neg = -8;
System.out.println(neg >> 1);      // -4
System.out.println(neg >>> 1);     // 2147483644
System.out.println(1 << 10);        // 1024
// Shifts mask the count to 5 bits (6 for long), so 1 << 33 == 2, not overflow.
System.out.println(1 << 33);       // 2
Enable -Xlint:all (and -Werror in CI) from the first day. Most precedence and boxing mistakes are reported as warnings long before they become runtime defects, and a project that starts clean stays clean.

1.3 Control flow, including switch expressions and pattern matching

Java has the four conventional constructs plus two modern ones that changed the shape of real code: the arrow form of switch, which does not fall through and can produce a value, and pattern matching for switch, which finalised in Java 21.

Loops, labels and the for-each form

The enhanced for loop works on anything Iterable or an array and is the default choice because it cannot go out of bounds. Use an indexed loop only when the index itself matters. Labels let a single break or continue target an outer loop, which is clearer than a boolean flag in a nested search.

String[] hosts = {"alpha", "beta", "gamma"};

for (String host : hosts) System.out.println(host);

// break/continue target the labeled loop, not the nearest one.
search:
for (int row = 0; row < 3; row++) {
    for (int col = 0; col < 3; col++) {
        if (row * col == 4) {
            System.out.println("found at " + row + "," + col);
            break search;
        }
    }
}

// while for an unknown trip count; do/while runs at least once.
int n = 1;
while (n < 100) n *= 2;             // 128
do { n--; } while (n > 0 && n % 5 != 0);

Switch statements and switch expressions

The colon form falls through, which is occasionally useful and usually a bug; the arrow form does not. A switch expression must be exhaustive, and for an enum or a sealed hierarchy the compiler enforces that, which turns "I forgot a case" from a runtime surprise into a compile error. Use yield to return a value from a block arm.

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

// Arrow statement: no fall-through, no break needed.
String kind(Day d) {
    return switch (d) {
        case SAT, SUN -> "weekend";
        case MON, TUE, WED, THU, FRI -> "weekday";
    };   // exhaustive by construction
}

// Pattern matching for switch (final in Java 21) with a guard.
String describe(Object o) {
    return switch (o) {
        case null            -> "nothing";
        case Integer i when i < 0 -> "negative int " + i;
        case Integer i       -> "int " + i;
        case String s        -> {
            int len = s.strip().length();
            yield "string of length " + len;
        }
        case int[] a         -> "array of " + a.length + " ints";
        default              -> "something else: " + o.getClass().getSimpleName();
    };
}

System.out.println(kind(Day.SAT) + " / " + describe(-3) + " / " + describe("  hi  "));
Matching case null explicitly is a Java 21 addition; without it, switch on a null reference throws NullPointerException, and the compiler says so rather than leaving it implicit. Ordering matters in a pattern switch too: the first matching arm wins, so put guarded and specific arms before general ones.

1.4 Arrays are objects with a fixed length

An array is a fixed-size, contiguous, zero-indexed object with a length field and a covariant element type. It is the fastest sequence Java has and the least forgiving.

Creation, defaults and copying

An array is created with new or an initialiser and its length never changes. Elements are default-initialised: 0 for numeric primitives, false for boolean, '\u0000' for char, null for references. Access outside [0, length) throws ArrayIndexOutOfBoundsException, which is one of the cheapest checks the JVM performs. Copy with Arrays.copyOf or System.arraycopy; do not loop unless the copy needs transformation.

int[] primes = {2, 3, 5, 7, 11};
int[] zeros  = new int[5];                   // all 0
String[] names = new String[3];              // all null

System.out.println(primes.length);           // 5
int[] bigger = Arrays.copyOf(primes, 8);     // pads with 0
System.arraycopy(primes, 1, bigger, 0, 3);   // overlapping-safe, fast

// Two-dimensional: an array of arrays, so rows may differ in length.
int[][] grid = new int[3][4];
int[][] jagged = {{1}, {2, 3}, {4, 5, 6}};
for (int[] row : jagged) System.out.println(Arrays.toString(row));

// Sorting and searching: mutating and binary-search pair.
int[] data = {5, 1, 4, 2, 3};
Arrays.sort(data);                           // [1, 2, 3, 4, 5]
System.out.println(Arrays.binarySearch(data, 4));   // 2

// Arrays are covariant: a String[] is an Object[].
Object[] objs = names;
objs[0] = Integer.valueOf(1);                // compiles, throws ArrayStoreException at runtime

When not to use an array

Prefer ArrayList or List.of for ordinary collections: they grow, they interoperate with the collections framework and streams, and the boxing cost for primitives is usually irrelevant. Reach for an array when the length is truly fixed and known, when you need primitive density (a million ints is 4 MB as an array and roughly ten times that as a boxed ArrayList<Integer>), or at an API boundary where the shape is contractual. Note also that an array is mutable and its contents are mutable: Arrays.asList(arr) gives a fixed-size view backed by the array, so a write through one is visible through the other. List.of(...) is the immutable alternative.

// Defensive copy: never hand an internal array to a caller.
final class IntBag {
    private final int[] values;
    IntBag(int[] values) { this.values = values.clone(); }
    int[] snapshot()     { return values.clone(); }
}

// A varargs parameter is an array, which is why this is a real aliasing bug.
static void printAll(String... items) {
    for (String s : items) System.out.print(s + " ");
    System.out.println();
}
printAll("a", "b", "c");                 // a b c

String[] backing = {"x", "y"};
printAll(backing);                       // passes the array itself, not a copy

// Stream over an array without boxing.
int sum = Arrays.stream(primes).sum();   // IntStream
System.out.println(sum + " " + Arrays.stream(primes).average().orElse(0));

1.5 String, StringBuilder, text blocks and var

String is immutable, final and the most used class in the language. Its operations, its encoding rules and the two syntax additions that changed how strings are written together cover most day-to-day string work.

Immutability, the string pool and encoding

A String's characters are never modified after construction; every "change" returns a new instance. String literals are interned in a pool, so two literals with the same text are the same object and == works; a string built at runtime is a different object, so == fails and equals is required. String stores UTF-16 internally and the class exposes charAt in code units, so an emoji occupies two indices. Use codePointCount and codePoints() when the text may contain non-BMP characters, and always pass an explicit Charset when converting to or from bytes.

String a = "java";
String b = "java";                    // same pooled literal
String c = new String("java");        // distinct object
System.out.println(a == b);           // true
System.out.println(a == c);           // false
System.out.println(a.equals(c));      // true - always compare with equals

// Common operations, all returning new strings.
String raw = "  Ada Lovelace  ";
System.out.println("[" + raw.strip() + "]");
System.out.println(raw.contains("Love"));
System.out.println(raw.replace("Ada", "Grace"));
System.out.println(String.join(", ", List.of("a", "b", "c")));
System.out.println("a,b,,c".split(",", -1).length);   // 4, -1 keeps trailing empties

// Unicode-aware length.
String emoji = "\uD83D\uDE00";        // grinning face
System.out.println(emoji.length());                  // 2 code units
System.out.println(emoji.codePointCount(0, emoji.length()));   // 1 character

// Formatted output: printf and formatted are the same engine.
System.out.printf("%s scored %.1f%% in %d ms%n", "Ada", 87.53, 42);
System.out.println(String.format("%,d", 1234567));

Text blocks

A text block (final in Java 15) is a multi-line string literal delimited by three double quotes. Incidental leading whitespace is stripped, based on the least-indented line and the position of the closing delimiter, and newlines are preserved as written. \ at end of line suppresses the newline, and \s preserves a trailing space that would otherwise be stripped. Use text blocks for SQL, JSON, HTML and shell snippets; concatenating those with "...\n" is now a defect rather than a style choice.

String sql = """
        SELECT id, email
          FROM users
         WHERE created_at >= ?
         ORDER BY id
        """;
System.out.println(sql.lines().count());     // 4 lines of content

String json = """
        {"name": "%s", "active": %b}
        """.formatted("Ada", true);
System.out.println(json.strip());

// \  at end of line joins; \s keeps a significant trailing space.
String joined = """
        one \
        two""";
System.out.println(joined);                  // "one two"

var and building strings efficiently

var (local variable type inference, final in Java 10) lets the compiler infer a local variable's type from its initialiser. It is not dynamic typing: the type is fixed at compile time and can be seen in the editor. It improves readability when the right-hand side already names the type, and hurts it when it does not — var x = get(); is strictly worse than naming the type. It works only for local variables with an initialiser, for indices in enhanced loops, and try-with-resources; it does not work for fields, parameters or return types. For repeated concatenation in a loop, use StringBuilder, because s += x in a loop allocates a new string every iteration and turns linear work quadratic.

var counts = new HashMap<String, Integer>();   // clear: the type is on the right
var users  = List.of("Ada", "Grace");        // List<String>
for (var u : users) System.out.println(u.toUpperCase());

// Quadratic: each += copies the whole accumulated string.
String slow = "";
for (int i = 0; i < 10_000; i++) slow += i;

// Linear: StringBuilder amortises growth in a char array.
var sb = new StringBuilder(16_000);
for (int i = 0; i < 10_000; i++) sb.append(i);
String fast = sb.toString();

// Since Java 9 the compiler turns a single += chain into invokedynamic,
// but a loop is still a loop. String.join covers the delimiter case.
System.out.println(String.join("-", "2026", "10", "14"));

Java's type system is nominal and single-inheritance based, with interfaces supplying the multiple-inheritance half. The modern additions — records, sealed hierarchies and switch patterns — formalise designs that used to require boilerplate and runtime checks.

2.1 Classes, objects, constructors and encapsulation

A class is a blueprint; an object is an instance with its own field storage and a reference to its class. Constructors initialise that storage, and access control decides which of it the outside world may touch.

Fields, methods and the four access levels

Access modifiers are ordered private, package-private (no modifier), protected, public. The practical rule is to keep fields private and expose behaviour, not data: a public mutable field cannot be guarded, cannot be observed, and cannot be reimplemented later. protected is the most dangerous level because it is visible both to subclasses anywhere and to the whole package, so it is a weak encapsulation boundary. static members belong to the class rather than an instance; final on a field means it must be assigned exactly once, which the compiler checks for definite assignment in every constructor. this disambiguates a field from a parameter; super refers to the parent's members.

public final class BankAccount {
    private final String owner;
    private long balanceCents;                       // mutable, but private
    private static long accountsOpened;              // shared, not per-instance

    public BankAccount(String owner) {
        this(owner, 0L);                             // constructor chaining
        accountsOpened++;
    }

    public BankAccount(String owner, long opening) {
        this.owner   = Objects.requireNonNull(owner, "owner");
        this.balance = Math.max(0, opening);
    }

    public void deposit(long cents) {
        if (cents <= 0) throw new IllegalArgumentException("deposit must be positive");
        balance += cents;
    }

    public boolean withdraw(long cents) {
        if (cents > balance) return false;            // failure as a value, not an exception
        balance -= cents;
        return true;
    }

    public long balanceCents() { return balance; }    // read-only accessor
    public static long accountsOpened() { return accountsOpened; }

    @Override public String toString() {
        return "%s: %d.%02d".formatted(owner, balance / 100, balance % 100);
    }
}

Object's contract: equals, hashCode and toString

Every class inherits equals, hashCode and toString from Object. If you override equals you must override hashCode consistently, or a HashMap or HashSet will store an object and then fail to find it. The contract is reflexive, symmetric, transitive, consistent, and a.equals(null) is always false. hashCode may change only if the fields used in equals change — which is why mutable objects make poor map keys. Since Java 7 the Objects.hash and Objects.equals helpers remove the hand-written null checks. Records (section 2.4) generate all three correctly, which is the main reason to prefer them for value types.

public final class Point {
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public int x() { return x; }
    public int y() { return y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        return o instanceof Point p && p.x == x && p.y == y;   // pattern, Java 16+
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point[x=%d, y=%d]".formatted(x, y); }
}

var map = new HashMap<Point, String>();
map.put(new Point(1, 2), "origin-ish");
System.out.println(map.get(new Point(1, 2)));   // works only because hashCode matches
Immutable classes are the simplest correctness tool in the language: no setter, all fields final, defensive copies of arrays and collections in and out, and the class itself final so a subclass cannot break the invariants. Immutability also gives you free thread safety — see chapter 6.

2.2 Inheritance, abstract classes and polymorphism

Single inheritance lets a class reuse and specialise its parent. It is the right tool when the subtype genuinely is the supertype and the supertype is designed for extension; otherwise composition is safer, and misuse of inheritance is the origin of most fragile class hierarchies.

Overriding, the annotation and dispatch

Instance methods are dispatched dynamically: the runtime class decides which override runs, regardless of the declared type of the reference. Fields are not — they are resolved statically, which is a frequent source of confusion, so never shadow a field. Always annotate an override with @Override so that a typo becomes a compile error rather than a silent overload. An override may widen access but never narrow it, and may narrow the return type (covariant returns). Marking a class final or a method final forbids further overriding, which is how you protect an invariant.

abstract class Shape {
    private final String name;
    protected Shape(String name) { this.name = name; }
    public String name() { return name; }

    public abstract double area();          // subclasses must supply this

    public String describe() {              // template method: shared algorithm
        return "%s has area %.3f".formatted(name, area());
    }
}

final class Circle extends Shape {
    private final double r;
    Circle(double r) { super("circle"); this.r = r; }
    @Override public double area() { return Math.PI * r * r; }
}

final class Rect extends Shape {
    private final double w, h;
    Rect(double w, double h) { super("rectangle"); this.w = w; this.h = h; }
    @Override public double area() { return w * h; }
}

List<Shape> shapes = List.of(new Circle(1), new Rect(2, 3));
for (Shape s : shapes) System.out.println(s.describe());   // dynamic dispatch

The fragile base class problem

Inheritance couples a subclass to its parent's implementation, not just its interface. A parent that adds a method with the same signature as an existing subclass method, changes a protected helper's contract, or relies on a self-call that a subclass overrides can break subclasses it has never seen. The remedies are: design for extension explicitly (document it, keep invariants in final or private helpers, prefer abstract methods over empty ones), or avoid inheritance in favour of composition. The classic example is a class that extends HashSet to count additions: it breaks the moment the parent adds a method that bypasses add. The fix is a wrapper class implementing Set and delegating, which is also what the JDK does for most of its unmodifiable wrappers.

// Fragile: a HashSet subclass that counts overrides add() only.
class CountingSet<E> extends HashSet<E> {
    int added;
    @Override public boolean add(E e) { added++; return super.add(e); }
    // addAll() in the parent does NOT call add(), so added is wrong after bulk ops.
}

// Robust: composition and delegation, with no location assumptions.
class InstrumentedSet<E> implements Set<E> {
    private final Set<E> delegate = new HashSet<>();
    private int added;
    @Override public boolean add(E e) {
        boolean changed = delegate.add(e);
        if (changed) added++;
        return changed;
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        boolean changed = false;
        for (E e : c) changed |= add(e);       // every path goes through add()
        return changed;
    }
    @Override public int size() { return delegate.size(); }
    @Override public boolean isEmpty() { return delegate.isEmpty(); }
    @Override public boolean contains(Object o) { return delegate.contains(o); }
    @Override public Iterator<E> iterator() { return delegate.iterator(); }
}
Prefer composition by default and use inheritance only for a genuine is-a relationship where the parent documents the extension points. Making every class final unless you intend it to be extended is a cheap habit that prevents a whole category of bugs.

2.3 Interfaces, default methods and functional contracts

An interface declares a type that any number of unrelated classes may implement, which recovers the multiple inheritance of type that the class rule forbids. Since Java 8 interfaces may carry implementation, and since 9 they may carry private helpers.

Abstract methods, default methods and static factory methods

All interface methods are implicitly public; all fields are implicitly public static final. A default method supplies an implementation that implementers inherit and may override, which is what let the JDK add List.sort, Iterable.forEach and the stream methods to published interfaces without breaking the world. A private method (Java 9+) factors out a helper shared by several defaults and is not part of the API. static methods on an interface are for factories and utilities that belong to the type — List.of, Comparator.comparing, Stream.of.

public interface Repository<T, ID> {
    Optional<T> findById(ID id);
    List<T> findAll();
    void save(T entity);

    default boolean exists(ID id) { return findById(id).isPresent(); }

    default void saveAll(Collection<T> entities) {
        entities.forEach(this::save);          // default built on abstract methods
    }

    // Diamond resolution helper: shared, not exposed.
    static <T> Repository<T, String> empty() {
        return new Repository<>() {
            public Optional<T> findById(String id) { return Optional.empty(); }
            public List<T> findAll() { return List.of(); }
            public void save(T entity) { throw new UnsupportedOperationException(); }
        };
    }
}

The diamond problem, and why a functional interface matters

If two interfaces both declare a default method with the same signature, a class implementing both does not compile until it overrides the method, and it can pick a side with InterfaceA.super.method(). That is a real ambiguity rule, not a resolution order, which is the key difference from C++. An interface with exactly one abstract method is a functional interface and is the target type of a lambda or method reference; @FunctionalInterface asserts that shape so a later added method breaks the build rather than breaking every lambda. The JDK's four core functional interfaces are Function, Consumer, Predicate and Supplier, plus the primitive specialisations that avoid boxing (chapter 5).

@FunctionalInterface
interface Validator<T> {
    List<String> validate(T value);            // the single abstract method
    default Validator<T> and(Validator<T> other) {
        return v -> { var a = validate(v); a.addAll(other.validate(v)); return a; };
    }
}

Validator<String> notBlank = s ->
        (s == null || s.isBlank()) ? List.of("must not be blank") : List.of();
Validator<String> longEnough = s ->
        (s != null && s.length() < 3) ? List.of("must be at least 3 characters") : List.of();

var problems = notBlank.and(longEnough).validate("ab");
System.out.println(problems);            // [must be at least 3 characters]

// Two interfaces with the same default: the class must disambiguate.
interface A { default String tag() { return "A"; } }
interface B { default String tag() { return "B"; } }
class Both implements A, B {
    @Override public String tag() { return A.super.tag() + B.super.tag(); }
}

2.4 Enums and records

Enums and records are the two cases where the compiler can generate the correctness machinery for you, and both are almost always better than the hand-written alternative.

Enums are real classes

An enum type has a fixed set of instances, created once at class initialisation, and each constant is a public static final field. Because they are objects, an enum can carry fields, constructors and methods, which turns a tag into a type that answers questions. Enums are safe in switch (since Java 14 the compiler checks exhaustiveness for switch expressions), they serialise robustly by name, and they are inherently thread-safe because the constant set is created during class loading. The values() array is a fresh copy on every call, so do not call it in a loop; EnumSet and EnumMap are the efficient collections for enum keys.

enum HttpStatus {
    OK(200, "OK"),
    NOT_MODIFIED(304, "Not Modified"),
    NOT_FOUND(404, "Not Found"),
    SERVER_ERROR(500, "Internal Server Error");

    private final int code;
    private final String reason;
    HttpStatus(int code, String reason) { this.code = code; this.reason = reason; }

    public int code() { return code; }
    public boolean isError() { return code >= 400; }

    public static HttpStatus fromCode(int code) {
        for (HttpStatus s : values()) if (s.code == code) return s;
        throw new IllegalArgumentException("unknown status " + code);
    }
}

System.out.println(HttpStatus.NOT_FOUND.code());        // 404
System.out.println(HttpStatus.NOT_FOUND.isError());     // true

// EnumSet is a bit vector: fast membership and bulk operations.
var retryable = EnumSet.of(HttpStatus.SERVER_ERROR);
System.out.println(retryable.contains(HttpStatus.OK));  // false

Records are transparent data carriers

A record (final in Java 16) declares its state in the header and the compiler generates a canonical constructor, accessor methods named after the components, and correct equals, hashCode and toString. Records are shallowly immutable — the references do not change, but a mutable list inside a record is still mutable, so copy defensively in a compact constructor. You may add static factories, extra methods and validation; you may not add instance fields. Use records for DTOs, value objects, tuple-like returns, map keys and any local grouping that a class would express with twenty lines of boilerplate. A record can implement an interface but cannot extend a class, and cannot be extended.

record Money(long cents, Currency currency) {
    // Compact constructor: validate and normalise, no field assignment needed.
    Money {
        if (cents < 0) throw new IllegalArgumentException("negative money");
        currency = Objects.requireNonNull(currency);
    }
    static Money usd(long cents) { return new Money(cents, Currency.US); }
    Money plus(Money other) {
        if (other.currency != currency) throw new IllegalArgumentException("currency mismatch");
        return new Money(cents + other.cents, currency);
    }
    boolean isZero() { return cents == 0; }
}

var a = Money.usd(1250);
var b = Money.usd(750);
System.out.println(a.plus(b));        // Money[cents=2000, currency=US]
System.out.println(a.equals(Money.usd(1250)));   // true - generated equals

// Records are the natural carrier for multiple return values.
record MinMax(int min, int max) {}
static MinMax bounds(int[] xs) {
    int lo = Integer.MAX_VALUE, hi = Integer.MIN_VALUE;
    for (int x : xs) { lo = Math.min(lo, x); hi = Math.max(hi, x); }
    return new MinMax(lo, hi);
}
var mm = bounds(new int[]{4, 9, -2, 7});
System.out.println(mm.min() + ".." + mm.max());     // -2..9

2.5 Sealed types and exhaustive pattern matching

A sealed interface or class names its permitted subtypes and nothing else may implement it. Final in Java 17, sealed types are what make a compiler-checked closed hierarchy possible, and combined with record patterns and pattern switch they replace visitor patterns and runtime instanceof chains.

Permits, and the three forms of a subtype

sealed interface Shape permits Circle, Rect, Triangle restricts the set of direct subtypes. A subtype must be declared final, sealed (continuing the hierarchy with its own permits list) or non-sealed (reopening extension for that branch). Because the compiler knows the complete set, a switch over a sealed type needs no default and the compiler rejects a switch that misses a case. Adding a new subtype then produces compile errors at every site that must handle it — the opposite of the visitor pattern, where a new case is silently ignored until it throws at runtime. This is the mechanism that makes "parse, don't validate" and algebraic-data-type modelling practical in Java.

sealed interface Shape permits Circle, Rect, Triangle {
    double area();
}
record Circle(double r) implements Shape { public double area() { return Math.PI * r * r; } }
record Rect(double w, double h) implements Shape { public double area() { return w * h; } }
record Triangle(double base, double height) implements Shape {
    public double area() { return base * height / 2; }
}

// No default arm: the compiler proves exhaustiveness over the sealed set.
static String classify(Shape s) {
    return switch (s) {
        case Circle(double r)              -> "circle of radius " + r;
        case Rect(double w, double h)      -> "rectangle " + w + "x" + h;
        case Triangle(double b, double h)  -> "triangle with base " + b;
    };
}

System.out.println(classify(new Circle(2)));            // circle of radius 2.0

Record patterns and nested deconstruction

A record pattern matches the type and destructures its components in one step, and patterns nest, so a tree or a message envelope is matched structurally rather than through accessor calls. Combined with a guard (when), this expresses rules that previously needed a sequence of if statements and casts. The cost is that pattern switch is still resolved on the runtime class, so a very long pattern list has the same dispatch cost as the equivalent instanceof chain; for hot paths where the type set is a closed sealed hierarchy, add an explicit discriminator or measure.

sealed interface Json permits JStr, JNum, JArr, JObj {}
record JStr(String value) implements Json {}
record JNum(double value) implements Json {}
record JArr(List<Json> items) implements Json {}
record JObj(Map<String, Json> fields) implements Json {}

static String render(Json j) {
    return switch (j) {
        case JStr(String s)                        -> '"' + s + '"';
        case JNum(double d)                        -> String.valueOf(d);
        case JArr(List<Json> items)                -> items.stream()
                .map(Main::render).collect(Collectors.joining(",", "[", "]"));
        case JObj(Map<String, Json> fields)       -> fields.entrySet().stream()
                .map(e -> '"' + e.getKey() + "\":" + render(e.getValue()))
                .collect(Collectors.joining(",", "{", "}"));
    };
}

// Nested record pattern with a guard.
sealed interface Event permits Click, Key {}
record Click(int x, int y) implements Event {}
record Key(String code, boolean ctrl) implements Event {}

static String handle(Event e) {
    return switch (e) {
        case Click(int x, int y) when x == 0 && y == 0 -> "origin click";
        case Click(int x, int y)                          -> "click at " + x + "," + y;
        case Key(String c, boolean ctrl) when ctrl        -> "shortcut " + c;
        case Key(String c, boolean ctrl)                  -> "key " + c;
    };
}
Sealed hierarchies pair naturally with records: make the interface sealed, make each variant a record, and every handler becomes an exhaustive switch with no cast and no unreachable default. If you find yourself writing a default arm that throws IllegalStateException, the type is not closed and should not be sealed — or the missing case is a real gap.

The collections framework is a set of interfaces with several implementations each, chosen by the operation that dominates. Generics are the compile-time type system over those containers, erased at runtime — and understanding the erasure explains every surprising signature you will meet.

3.1 List, Set, Map and Deque, and choosing between them

Four interfaces cover almost all needs. Choosing the right implementation is a matter of knowing which operation you are optimising and which guarantee you are buying.

The interfaces and their implementations

List is an ordered sequence with positional access. ArrayList is a growable array: get is O(1), appending is amortised O(1), insertion in the middle is O(n). LinkedList is a doubly linked list: it is the worst of both worlds in practice — O(n) positional access and poor cache behaviour — so prefer ArrayDeque whenever you need a queue or a stack. Set forbids duplicates. HashSet gives O(1) average membership and no order; LinkedHashSet preserves insertion order for a small memory cost; TreeSet keeps elements sorted in O(log n). Map maps keys to values; HashMap, LinkedHashMap and TreeMap mirror the three set behaviours, and EnumMap is a plain array indexed by the enum's ordinal when the keys are enum constants.

The factory methods and the mutability that matters

List.of, Set.of and Map.of create structurally immutable collections: they cannot be added to or removed from, they reject null elements, and they are compact. But they are only shallowly immutable — the elements themselves may be mutable. List.copyOf takes a snapshot of an existing collection and rejects nulls. Collections.unmodifiableList is different: it is a view, so the original still changes underneath. Use List.of for constants and copyOf for defensive copies, and never rely on a mutable class as a key or a set element.

var mutable = new ArrayList<String>();
mutable.add("alpha");
mutable.addAll(List.of("beta", "gamma"));

var immutable = List.copyOf(mutable);        // snapshot; mutable is unaffected later
// immutable.add("delta");                    // UnsupportedOperationException

var view = Collections.unmodifiableList(mutable);
mutable.add("delta");
System.out.println(view.size());             // 4 - the view changed too

var byId = new HashMap<Integer, String>();
byId.put(1, "one");
byId.putIfAbsent(1, "ONE");                  // no-op
byId.merge(2, "two", String::concat);        // insert or combine
byId.computeIfAbsent(3, k -> "value" + k);    // "value3"
System.out.println(byId.getOrDefault(9, "missing"));

// Insertion-ordered map: predictably iterates the way it was written.
var ordered = new LinkedHashMap<String, Integer>();
ordered.put("b", 2);
ordered.put("a", 1);
System.out.println(ordered);                 // {b=2, a=1}
Returning List.of from a public method is not the same as being null-safe. These factories throw NullPointerException on a null element, so a method that builds a list from user data must filter or reject nulls before calling them. And a HashMap with a mutable key is a live bug: mutate a field used by hashCode and the entry becomes unreachable even though it is still in the map.

3.2 Iteration, removal and the ConcurrentModificationException

Every collection is Iterable, which makes the enhanced for loop universal. Mutating a collection while iterating it is the single most common collections bug, and the failure mode is a fail-fast exception rather than silent corruption.

The iterator contract

iterator() returns an object with hasNext(), next() and optionally remove(). A collection tracks a modification count; the iterator compares it and throws ConcurrentModificationException on the next call after an external structural change. This is a best-effort detection, not a guarantee, which is exactly why the correct pattern is not "remove the check" but "use Iterator.remove() or removeIf". removeIf is the modern, one-line way to drop elements by predicate. An Iterator over a Map comes from keySet(), values() or entrySet(), all of which are views onto the same map.

var names = new ArrayList<>(List.of("Ada", "alan", "Grace", "bob"));

// Wrong: ConcurrentModificationException
// for (String n : names) if (Character.isLowerCase(n.charAt(0))) names.remove(n);

// Right, pattern 1: removeIf, one pass, no index bookkeeping.
names.removeIf(n -> Character.isLowerCase(n.charAt(0)));

// Right, pattern 2: explicit iterator when the loop body needs more.
var it = names.iterator();
while (it.hasNext()) {
    String n = it.next();
    if (n.length() > 4) it.remove();
}

// Right, pattern 3: iterate a copy when the shape changes unpredictably.
for (String n : List.copyOf(names)) { /* safe to mutate names here */ }

// Map traversal with entrySet, the only way to get keys and values together.
var ages = Map.of("Ada", 36, "Grace", 45);
for (var e : ages.entrySet()) System.out.println(e.getKey() + " -> " + e.getValue());
ages.forEach((k, v) -> System.out.println(k + " is " + v));

Views, sub-lists and equality

subList, keySet, values, entrySet, Arrays.asList and Collections.unmodifiable* all return views: writes through them reach the original and vice versa. A view is a performance win and an aliasing hazard. Equality for collections is defined by content and order for List, by content for Set, and by key-value pairs for Map — so Set and Map equality is unordered, which is why a HashSet and a LinkedHashSet with the same members are equals. Note that List.equals ignores the concrete class, so an ArrayList equals a LinkedList with the same elements.

var all = new ArrayList<>(List.of(1, 2, 3, 4, 5, 6));
List<Integer> window = all.subList(1, 4);         // [2, 3, 4], a view
window.set(0, 20);                                 // writes to index 1 of `all`
System.out.println(all);                           // [1, 20, 3, 4, 5, 6]

// Snapshot when you need independence.
List<Integer> copy = List.copyOf(window);

System.out.println(List.of(1, 2).equals(new LinkedList<>(List.of(1, 2))));   // true
System.out.println(Set.of(1, 2).equals(new LinkedHashSet<>(Set.of(2, 1)))); // true

// Arrays.asList is a fixed-size view of the array, not a copy.
Integer[] boxed = {1, 2, 3};
List<Integer> backing = Arrays.asList(boxed);
backing.set(0, 99);
System.out.println(boxed[0]);                      // 99
// backing.add(4);                                  // UnsupportedOperationException

3.3 Comparable and Comparator: ordering as data

Sorting needs an ordering, and Java separates the two cases: a type's natural ordering (Comparable) and an external ordering supplied at the call site (Comparator). The comparator API is a clean demonstration of why functional composition matters.

The two interfaces and the contract

Comparable<T> has one method, compareTo, and defines the type's default order; String, the wrapper types and LocalDate implement it. Comparator<T> is a functional interface with compare and a large set of static and default combinators: comparing, thenComparing, reversed, nullsFirst, nullsLast. Both contracts require a consistent, transitive ordering, and both require that comparing equal elements gives zero. The single most common violation is subtracting: return a.price() - b.price() overflows for large or negative values, so use Integer.compare or Comparator.comparingInt instead. Sorting uses a stable merge sort on objects, so the input order of equal elements is preserved, which is what makes multi-key sorting via thenComparing work.

record Employee(String name, String dept, int salary, Integer bonus) {}

var staff = new ArrayList<>(List.of(
    new Employee("Ada",    "eng",     120_000, 5_000),
    new Employee("Grace",  "eng",     140_000, null),
    new Employee("Alan",   "research", 95_000, 2_000),
    new Employee("Barbara","research", 95_000, 9_000)));

// Compound ordering: department ascending, then salary descending, then name.
Comparator<Employee> order =
    Comparator.comparing(Employee::dept)
              .thenComparing(Employee::salary, Comparator.reverseOrder())
              .thenComparing(Employee::name);

staff.sort(order);
staff.forEach(e -> System.out.println(e.dept() + " " + e.name() + " " + e.salary()));

// Null-safe with a key extractor; nulls last.
Comparator<Employee> byBonus = Comparator
        .comparing(Employee::bonus, Comparator.nullsLast(Integer::compareTo));

System.out.println(Collections.max(staff, byBonus).name());

// Build a TreeMap with an explicit order.
var byName = new TreeMap<>(Comparator.comparing(Employee::name));
staff.forEach(e -> byName.put(e, e.salary()));
byName.keySet().forEach(k -> System.out.print(k.name() + " "));

Total ordering versus equality

A TreeSet and TreeMap use the comparator as their notion of identity, not equals. If a comparator returns zero for two objects that are not equals, the set quietly discards one — the documented consequence is that SortedSet's behaviour is "inconsistent with equals". If you sort by a subset of the fields, keep the comparator consistent, or accept that duplicates by that key collapse. The fix when both behaviours are wanted is to append thenComparing on a unique field, or to use a LinkedHashMap to keep the first value seen.

// A comparator that ignores a distinguishing field collapses entries in a TreeSet.
var bySalary = new TreeSet<>(Comparator.comparingInt(Employee::salary));
bySalary.add(new Employee("Ada", "eng", 95_000, null));
bySalary.add(new Employee("Alan", "research", 95_000, null));
System.out.println(bySalary.size());        // 1 - Alan was treated as equal to Ada

// Make the order total by appending a tie-breaker.
var bySalaryThenName = new TreeSet<>(
        Comparator.comparingInt(Employee::salary).thenComparing(Employee::name));
bySalaryThenName.add(new Employee("Ada", "eng", 95_000, null));
bySalaryThenName.add(new Employee("Alan", "research", 95_000, null));
System.out.println(bySalaryThenName.size()); // 2
Sorting a mutable list by a field and then mutating that field is undefined behaviour: the list is no longer sorted and binary search will return nonsense. For a collection keyed by a mutable attribute, re-sort explicitly or hold the data in a TreeMap keyed by an immutable snapshot.

3.4 Generic methods, wildcards and type erasure

Generics moved type errors from runtime casts to compile-time checks, but they are implemented by erasure: type parameters exist for the compiler and are gone in the class file. Every limitation of the feature follows from that one decision.

Type parameters, bounds and PECS

A generic method declares its own type parameters: static <T> List<T> repeat(T value, int n). Bounds restrict the type: <T extends Comparable<T>>. A wildcard appears at a use site: List<?> is "a list of some unknown type", List<? extends Number> is a producer and List<? super Integer> is a consumer. The rule of thumb is PECS: Producer Extends, Consumer Super. A name for the constraint: List<Integer> is not a subtype of List<Number>, because that would allow adding a Double to a list of integers. Arrays are covariant and therefore unsound at runtime; generics are invariant and sound at compile time.

// A bounded generic method.
static <T extends Comparable<? super T>> T max(List<T> xs) {
    T best = xs.get(0);
    for (T x : xs) if (x.compareTo(best) > 0) best = x;
    return best;
}
System.out.println(max(List.of(3, 9, 4, 1)));       // 9

// PECS: read from ? extends, write to ? super.
static double sum(List<? extends Number> src) {
    double total = 0;
    for (Number n : src) total += n.doubleValue();
    return total;
}
static void fill(List<? super Integer> dst, int n) {
    for (int i = 0; i < n; i++) dst.add(i);
}
System.out.println(sum(List.of(1, 2.5, 3)));        // 6.5
var sink = new ArrayList<Number>();
fill(sink, 3);                                       // ArrayList<Integer> would also work
System.out.println(sink);

What erasure forbids

Because List<String> and List<Integer> erase to the same List, you cannot new T(), cannot create a generic array (new T[n]), cannot overload on List<String> versus List<Integer>, and cannot call instanceof List<String>. You cannot use a primitive as a type argument — List<int> is illegal, so boxing applies. Where you need the erased type at runtime you pass a Class<T> token or a TypeReference-style superclass capture. Unchecked-warning suppression is legitimate at a boundary where you have verified the invariant by hand, and should be accompanied by a comment saying what that invariant is.

// Class-token pattern: the erased type arrives as an argument.
static <T> T[] newArray(Class<T> type, int size) {
    @SuppressWarnings("unchecked")
    T[] arr = (T[]) java.lang.reflect.Array.newInstance(type, size);
    return arr;
}
String[] names = newArray(String.class, 3);

// Heap pollution: a varargs generic parameter is really an Object[].
@SafeVarargs
static <T> List<T> listOf(T... items) { return new ArrayList<>(Arrays.asList(items)); }
List<Integer> ints = listOf(1, 2, 3);

// A generic method with two parameters and a mapping function.
static <K, V> Map<K, V> indexBy(List<V> items, Function<V, K> keyFn) {
    var out = new HashMap<K, V>();
    for (V v : items) out.put(keyFn.apply(v), v);
    return out;
}
System.out.println(indexBy(List.of("ada", "grace"), String::length));   // {3=ada, 5=grace}
Do not use raw types in new code. A raw List disables every generic check on that reference and its calls, which reintroduces the ClassCastException that generics exist to prevent. When you must interoperate with a legacy API, confine the raw type to the smallest possible scope and convert to a wildcard or a parameterised type immediately.

4 · Exceptions and I/O

4.1 Checked and unchecked exceptions, try/catch/finally4.2 try-with-resources and the AutoCloseable contract4.3 java.nio.file: Path, Files and filesystem operations4.4 Buffered streams, character encodings and files that do not fit in memory

The exception system is a checked/unchecked split that Java alone among mainstream languages enforces. The I/O system has two APIs — the old stream-based java.io and the modern java.nio.file — and a buffering rule that separates fast code from slow.

4.1 Checked and unchecked exceptions, try/catch/finally

Every throwable is either an Error (a JVM-level failure you do not catch), a checked exception (a subclass of Exception that is not a RuntimeException) or an unchecked exception. The compiler forces you to acknowledge the checked kind; it does not force anything for the unchecked kind.

The taxonomy and whose fault it is

Checked exceptions model an expected, recoverable environmental failure — a missing file, a refused socket, a deadlock retry — that the immediate caller can plausibly handle. Unchecked exceptions model a programming error: NullPointerException, IllegalArgumentException, IndexOutOfBoundsException. The heuristic is that a checked exception should be recoverable by the caller and an unchecked one should not happen at all. Errors (OutOfMemoryError, StackOverflowError, LinkageError) indicate a condition the application cannot repair; catching them is almost always wrong. finally runs on both the normal and the exceptional path, and only once; it runs before a propagating exception continues, so returning from finally discards an in-flight exception. Do not do that.

import java.io.*;

class ConfigLoader {
    // Checked: the caller can retry, fall back, or report to the user.
    static String load(File f) throws IOException {
        if (!f.exists()) throw new FileNotFoundException(f.getPath());
        try (var in = new BufferedReader(new FileReader(f))) {
            return in.readLine();
        }
    }

    static int parseInt(String s) {
        try {
            return Integer.parseInt(s);
        } catch (NumberFormatException e) {           // unchecked in, checked out
            throw new IllegalArgumentException("not a number: " + s, e);
        }
    }

    public static void main(String[] args) {
        try {
            System.out.println(load(new File("config.properties")));
        } catch (FileNotFoundException e) {
            System.err.println("missing file: " + e.getMessage());
        } catch (IOException e) {
            System.err.println("I/O failed: " + e);
        } finally {
            System.out.println("attempt finished");   // always runs
        }
    }
}

Multi-catch, chaining and custom types

Several exception types that share a handler are caught in one clause with |; the parameter is implicitly final. Exception chaining (new IllegalStateException("...", cause)) preserves the original stack trace, so never lose the cause — a wrapper that discards it makes the failure undiagnosable. A custom exception is worth creating when callers need to distinguish the failure programmatically; it should carry the fields needed to describe it and usually extends the nearest matching JDK type. Catching Exception or Throwable broadly is only correct at the outermost boundary of a thread or a request, where the alternative is losing the failure entirely.

// A domain exception with the data a caller needs.
class InsufficientFundsException extends Exception {
    private final long requested, available;
    InsufficientFundsException(long requested, long available) {
        super("requested %d, available %d".formatted(requested, available));
        this.requested = requested;
        this.available = available;
    }
    public long shortfall() { return requested - available; }
}

// Multi-catch, and wrapping while keeping the cause.
try {
    Thread.sleep(10);
    Integer.parseInt("x");
} catch (InterruptedException | NumberFormatException e) {
    throw new IllegalStateException("startup failed", e);     // cause preserved
}

// Re-throwing with a more specific type (Java 7+ precise rethrow).
static void rethrow(boolean flag) throws java.io.IOException {
    try {
        if (flag) throw new java.io.IOException("io");
        throw new java.sql.SQLException("sql");
    } catch (Exception e) {
        throw e;      // compiler keeps the precise checked types
    }
}
Design the failure, not just the happy path. Document each method's checked exceptions in Javadoc with @throws, decide whether a failure is a value (Optional, boolean, a result record) or an exception, and apply that decision consistently. Exceptions are for exceptional flow; using them for ordinary control flow is both slower and harder to read.

4.2 try-with-resources and the AutoCloseable contract

Any resource holding an operating-system handle — a file, a socket, a database connection, a lock — must be released deterministically. try-with-resources (Java 7) is the mechanism, and it fixes the suppressed-exception problem that a hand-written finally cannot.

How it works and what it fixes

Resources declared in the try (...) header must implement AutoCloseable; they are closed in reverse declaration order, before any catch or finally block runs. If the body throws and close() also throws, the body's exception is the one thrown and the close failure is added as a suppressed exception, retrievable with getSuppressed(). The hand-written equivalent loses one of the two. Since Java 9 the resource variable may be effectively final and declared outside the header, which lets a method accept a resource and close it itself.

// The body's exception wins; close()'s failure is attached as suppressed.
class Flaky implements AutoCloseable {
    private final String name;
    Flaky(String name) { this.name = name; }
    public void work() { throw new IllegalStateException(name + " work"); }
    public void close() { throw new IllegalStateException(name + " close"); }
}

try {
    try (var f = new Flaky("resource")) {
        f.work();
    }
} catch (IllegalStateException e) {
    System.out.println(e.getMessage());                        // resource work
    for (Throwable s : e.getSuppressed()) System.out.println("suppressed: " + s.getMessage());
}

// Java 9+: close a resource the caller supplied.
static void drain(InputStream in) throws IOException {
    try (in) { in.transferTo(OutputStream.nullOutputStream()); }
}

Reading and writing safely

The pattern for real file work is a chain of buffered streams inside one try: closing the outermost closes the chain, and buffering turns one syscall per byte into one per several kilobytes. java.nio.file.Files covers the common whole-file cases in a single call — readString, writeString, readAllLines, newBufferedReader — and is usually the right first choice. For anything binary, BufferedInputStream plus DataInputStream or a ByteBuffer gives explicit control of endianness and alignment.

import java.io.*;
import java.nio.file.*;

Path path = Path.of("notes.txt");
Files.writeString(path, "first\nsecond\n", StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING);

for (String line : Files.readAllLines(path)) System.out.println(line);

// Streaming a large file: constant memory, explicit buffering.
try (var reader = Files.newBufferedReader(path)) {
    String line;
    while ((line = reader.readLine()) != null) System.out.println("> " + line);
}

// Binary: buffering is the difference between 4 KB and 1 MB per syscall.
try (var in = new BufferedInputStream(new FileInputStream("data.bin"));
     var out = new BufferedOutputStream(new FileOutputStream("copy.bin"))) {
    var buf = new byte[8192];
    int n;
    while ((n = in.read(buf)) != -1) out.write(buf, 0, n);
}
close() on a wrapper such as BufferedReader closes the underlying stream too. If two wrappers share one stream and both are closed, the second close is usually harmless for files but can be a use-after-free protocol error for network or native handles. Own the stream in exactly one place.

4.3 java.nio.file: Path, Files and filesystem operations

java.nio.file replaced java.io.File as the recommended API. Path is an immutable, provider-based location; Files is a static utility for operations; FileSystem abstracts the platform, which is what makes the same code work on Windows, POSIX and inside a zip filesystem.

Path arithmetic and the Files toolbox

A Path is not a string: resolve appends, resolveSibling replaces the last element, relativize computes a relative path, normalize removes . and .., and toAbsolutePath anchors it. Paths are compared with Files.isSameFile when symlinks are involved, because two different path strings can name one file. Files offers exists, isDirectory, size, createDirectories, move, copy, delete, deleteIfExists, walk, list and readAttributes. 

import java.nio.file.*;
import java.nio.file.attribute.*;
import java.io.IOException;

Path base = Path.of("build", "out");
Files.createDirectories(base);                       // parents as needed
Path config = base.resolve("app.properties");
Path sibling = config.resolveSibling("app.yml");     // build/out/app.yml
System.out.println(base.relativize(config));         // app.properties

Files.writeString(config, "port=8080\n");
System.out.println(Files.size(config) + " bytes");
System.out.println(Files.getLastModifiedTime(config).toInstant());

// Walk a tree, filtering by extension, streaming not loading.
try (var paths = Files.walk(base)) {
    paths.filter(p -> p.toString().endsWith(".properties"))
         .forEach(p -> System.out.println("found " + p));
}

// Atomic move when both paths are on the same filesystem.
Path tmp = base.resolve("app.properties.tmp");
Files.writeString(tmp, "port=9090\n");
Files.move(tmp, config, StandardCopyOption.REPLACE_EXISTING, StandardCopyOption.ATOMIC_MOVE);

// Read a whole small file in one call; prefer streaming for large ones.
String text = Files.readString(config);
System.out.println(text.strip());

Attributes, temporary files and permission

Files.readAttributes(path, BasicFileAttributes.class) returns size, timestamps, and whether the entry is a regular file, directory, symbolic link or other. Files.setPosixFilePermissions and PosixFilePermissions.fromString("rw-r--r--") set Unix permissions; on Windows the same attributes are emulated and the call may not throw but has no effect. Files.createTempFile and Files.createTempDirectory create a file with a randomly generated name in the system temp directory, and deleteOnExit is a JVM-shutdown hook — useful for tests, unsuitable for long-lived processes because it accumulates.

var attrs = Files.readAttributes(config, BasicFileAttributes.class);
System.out.printf("size=%d dir=%b symlink=%b%n",
        attrs.size(), attrs.isDirectory(), attrs.isSymbolicLink());

// POSIX permissions; silently a no-op on a Windows filesystem provider.
try {
    Files.setPosixFilePermissions(config,
            PosixFilePermissions.fromString("rw-r--r--"));
} catch (UnsupportedOperationException e) {
    System.out.println("no POSIX permissions here");
}

// Temp files, and a delete-on-exit safety net for tests.
Path scratch = Files.createTempFile("java-guide-", ".txt");
Files.writeString(scratch, "ephemeral");
scratch.toFile().deleteOnExit();

// Walking with a depth limit and a visitor that skips directories.
try (var s = Files.walk(base, 2)) {
    s.filter(Files::isRegularFile).forEach(System.out::println);
}

4.4 Buffered streams, character encodings and files that do not fit in memory

Two decisions determine I/O throughput and correctness: how many bytes each system call moves, and which character encoding converts between bytes and text. The first is a performance matter; the second is a data-integrity matter.

Buffering and why a raw stream is slow

A FileInputStream.read() issues one operating-system call per byte. A BufferedInputStream wraps it with an 8 KB array by default, so the same loop issues roughly one call per 8,192 bytes — a two-order-of-magnitude difference on a large file. The buffering is transparent: the code is unchanged, only the wrapper is. Writing is the same story, and an unflushed buffer means data that exists in memory and not on disk, which is why a writer must be flushed or closed. flush() forces the bytes out; close() flushes and releases the handle.

import java.io.*;
import java.nio.charset.StandardCharsets;

// Slow: one syscall per byte.
try (InputStream raw = new FileInputStream("big.dat")) {
    int b;
    long total = 0;
    while ((b = raw.read()) != -1) total++;
}

// Fast: same loop, buffered by the decorator.
try (InputStream in = new BufferedInputStream(new FileInputStream("big.dat"))) {
    int b;
    while ((b = in.read()) != -1) { /* work */ }
}

// Text always with an explicit charset.
try (var w = new BufferedWriter(new OutputStreamWriter(
        new FileOutputStream("out.txt"), StandardCharsets.UTF_8))) {
    w.write("caf\u00e9 \u2014 \u20ac\n");
    w.newLine();
}   // close() flushes

Encodings, and streaming files larger than memory

Text is bytes plus an encoding. The platform default was historically the source of "it works on my machine" mojibake, and Java 18 made UTF-8 the default for Files, PrintStream and friends; you should still pass StandardCharsets.UTF_8 explicitly when interoperating with another system. Strip a byte-order mark with Files.newBufferedReader or detect it deliberately. For a file too large to hold in memory, read line by line with BufferedReader.lines() or map the file with a MappedByteBuffer; for a directory tree, walk it and process one entry at a time. The invariant is that peak memory should not scale with file size.

// Stream lines with bounded memory, close the backing reader with the try.
try (var lines = Files.lines(Path.of("huge.csv"), StandardCharsets.UTF_8)) {
    long bad = lines.skip(1)
                    .map(String::strip)
                    .filter(l -> !l.isEmpty())
                    .map(line -> line.split(",", -1))
                    .filter(cols -> cols.length < 3)
                    .count();
    System.out.println(bad + " malformed rows");
}

// Count words across a tree in one pipeline, still streaming.
try (var s = Files.walk(Path.of("docs"))) {
    long words = s.filter(p -> p.toString().endsWith(".txt"))
                  .flatMap(p -> {
                      try { return Files.lines(p).map(String::strip); }
                      catch (IOException e) { throw new UncheckedIOException(e); }
                  })
                  .flatMap(l -> java.util.Arrays.stream(l.split("\\s+")))
                  .filter(w -> !w.isBlank())
                  .count();
    System.out.println(words + " words");
}
Prefer Files to File in new code: Files reports failures with useful IOException messages, follows the NIO provider abstraction, and the whole-file methods remove most try/finally boilerplate. Keep File only where a legacy API demands it.

5 · Lambdas, streams and functional Java

5.1 Functional interfaces, lambda syntax and closures5.2 Method references and constructor references5.3 Stream operations: map, filter, flatMap, reduce5.4 Collectors: grouping, partitioning and downstream reduction5.5 Optional and the null-avoidance strategy

Java 8 added lambdas, method references, a stream pipeline and Optional, and they changed how collections are processed far more than the syntax suggests. The pipeline reads as a description of the transformation rather than a sequence of loop steps.

5.1 Functional interfaces, lambda syntax and closures

A lambda has no type until it is given a target type, and the target must be a functional interface. That indirection is why a lambda can be passed to a standard-library method without any new interface being declared.

The four core interfaces and their primitive variants

Function<T,R> transforms, Consumer<T> acts, Predicate<T> tests and Supplier<T> produces. Each has primitive specialisations to avoid boxing: IntFunction, ToIntFunction, IntPredicate, IntSupplier and so on. The java.util.function package also provides BiFunction, UnaryOperator, BinaryOperator and the composition defaults andThen, compose, and, or and negate. Where a real domain concept exists — a Validator, a RetryPolicy — declaring your own functional interface gives the compiler a place to enforce the contract and gives tooling a name to show.

import java.util.function.*;

Function<String, Integer> length = String::length;
Predicate<String> isBlank          = String::isBlank;
Consumer<String>  print            = System.out::println;
Supplier<String>  greeting         = () -> "hello";

// Composition without extra syntax.
Function<Integer, Integer> plusOne = x -> x + 1;
System.out.println(length.andThen(plusOne).apply("abcd"));     // 5

Predicate<String> notBlank = isBlank.negate();
System.out.println(isBlank.or(notBlank).test("  "));           // true

// A lambda closes over effectively final locals; it may not reassign them.
int base = 10;
IntUnaryOperator addBase = n -> n + base;
System.out.println(addBase.applyAsInt(5));                     // 15
// base = 20;  // compile error: not effectively final

Closures, capturing and this

A lambda captures variables from its enclosing scope, and the captured local must be effectively final — assigned once. The reason is that the lambda may outlive the method invocation, so the captured value is copied at creation time, and allowing reassignment would define which copy is visible. Captured fields are read through this, so a lambda inside an instance method can see and mutate instance state; that is why a lambda in a field initialiser can deadlock a class initialiser. Inside a lambda, this refers to the enclosing instance, unlike an anonymous class where it refers to the anonymous instance — a difference that changes behaviour when a method is overridden.

class Counter {
    private int total;

    // Lambda: `this` is the Counter.
    Runnable lambda = () -> total++;

    // Anonymous class: `this` is the anonymous instance.
    Runnable anon = new Runnable() {
        private int total;                  // shadows Counter.total
        public void run() { this.total++; }
    };

    int total() { return total; }
}

// Callback style with a captured accumulator.
static <T> void each(List<T> items, Consumer<T> action) { items.forEach(action); }
var seen = new StringBuilder();
each(List.of("a", "b"), s -> seen.append(s));
System.out.println(seen);                   // ab

5.2 Method references and constructor references

A method reference is a shorter lambda for the case where the body simply calls an existing method. There are four forms, and learning to recognise them removes most of the noise from stream code.

The four forms

Type::staticMethod (for example Integer::parseInt) is a Function<String,Integer>. instance::method binds a receiver (System.out::println). Type::instanceMethod takes the receiver as the first argument (String::length is Function<String,Integer>, String::compareTo is a Comparator<String>). Type::new is a constructor reference, and an array constructor reference String[]::new is the idiomatic argument to Stream.toArray. The double colon is not a member access operator; it is a concrete reference to a method whose signature must match the target functional interface exactly.

import java.util.function.*;
import java.util.stream.*;

record User(String name, int age) {}

var names = List.of("ada", "grace", "alan");

names.stream().map(String::toUpperCase).forEach(System.out::println);   // instance form

// Type::instanceMethod takes the first argument as the receiver.
System.out.println(names.stream().mapToInt(String::length).sum());

// Constructor reference and array constructor reference.
Supplier<ArrayList<String>> factory = ArrayList::new;
String[] arr = names.toArray(String[]::new);
User[] users = Stream.of("Ada", "Grace")
                     .map(n -> new User(n, 30))
                     .toArray(User[]::new);

// Both of these are the same lambda; the method reference is clearer.
names.stream().map(s -> s.strip()).toList();
names.stream().map(String::strip).toList();

When a method reference is the wrong choice

A method reference cannot carry an argument, so anything beyond a straight pass-through stays a lambda. Overusing them hurts readability when the target method name is less informative than the parameter name: map(Person::name) is excellent, map(Person::get) is worse than p -> p.get("name"). Because a method reference is not an object literal, there is no per-call allocation — but a lambda that captures is instantiated once per evaluation of its enclosing expression, so a lambda created inside a tight loop is a small allocation each time; hoist it to a static final field when it captures nothing.

// Hoist a stateless lambda to a constant: one instance for the whole JVM.
static final Comparator<String> BY_LENGTH = Comparator.comparingInt(String::length);

// A reference to an overloaded method needs the target type to disambiguate.
Function<String, Integer> f = Integer::valueOf;         // (String) -> Integer
// Function<Integer, String> g = Integer::toString;     // ambiguous? no: (int) -> String

// Bound receiver instance form, useful for a fixed prefix.
var prefix = "id-";
names.stream().map(prefix::concat).forEach(System.out::println);

5.3 Stream operations: map, filter, flatMap, reduce

A stream is a lazy pipeline over a source. The pipeline is described once and executed once, and nothing runs until the terminal operation is called. This laziness is what allows a filter and a map to be fused into a single pass.

The pipeline shape and the four operation groups

Operations are: source (stream(), Stream.of, IntStream.range, Files.lines), intermediate and stateless (filter, map, flatMap, peek, mapMulti), intermediate and stateful (sorted, distinct, limit, skip, takeWhile), and terminal (collect, reduce, forEach, count, anyMatch, findFirst, toList). A stateful operation must see earlier elements before it can emit, so it buffers; placing sorted early in a long pipeline is a common cause of surprising memory use. A stream is consumed once: reusing it throws IllegalStateException.

import java.util.*;
import java.util.stream.*;

record Order(String customer, String sku, int qty, double unitPrice) {}

var orders = List.of(
    new Order("ada",   "KB-01", 2, 79.99),
    new Order("grace", "MS-10", 1, 24.50),
    new Order("ada",   "MS-10", 3, 24.50),
    new Order("alan",  "KB-01", 1, 79.99),
    new Order("grace", "HD-22", 1, 129.00));

// filter + map + sorted + terminal toList
var bigSpendLines = orders.stream()
        .filter(o -> o.qty() * o.unitPrice() > 100)
        .map(o -> "%s bought %d x %s".formatted(o.customer(), o.qty(), o.sku()))
        .sorted()
        .toList();
bigSpendLines.forEach(System.out::println);

// flatMap flattens a nested structure one level.
var byCustomer = orders.stream()
        .collect(Collectors.groupingBy(Order::customer,
                 Collectors.mapping(Order::sku, Collectors.toList())));
System.out.println(byCustomer);

// reduce: total revenue, and a version with an identity and a combiner.
double revenue = orders.stream()
        .mapToDouble(o -> o.qty() * o.unitPrice())
        .sum();
double revenueFold = orders.stream()
        .reduce(0.0, (acc, o) -> acc + o.qty() * o.unitPrice(), Double::sum);
System.out.printf("%.2f / %.2f%n", revenue, revenueFold);

Laziness, ordering and the primitives

Because the pipeline is lazy, an infinite source terminates as soon as a short-circuiting operation is satisfied: Stream.iterate(1, n -> n + 1).filter(n -> n % 7 == 0).findFirst() returns immediately. Also because it is lazy, peek is not a debugging substitute for a terminal operation — nothing executes without one, which is why a "logging" peek that appears to do nothing is working exactly as specified. IntStream, LongStream and DoubleStream avoid boxing and carry extra terminals (sum, average, summaryStatistics). Finally, use forEachOrdered rather than forEach when the encounter order matters; on a parallel stream, forEach deliberately does not preserve it.

// Lazy, infinite source; short-circuits at the first match.
long firstMultipleOf7 = Stream.iterate(1L, n -> n + 1)
        .filter(n -> n % 7 == 0)
        .findFirst()
        .orElseThrow();
System.out.println(firstMultipleOf7);        // 7

// IntStream avoids boxing and gives statistics in one pass.
var stats = IntStream.rangeClosed(1, 100).summaryStatistics();
System.out.printf("min=%d max=%d avg=%.2f sum=%d%n",
        stats.getMin(), stats.getMax(), stats.getAverage(), stats.getSum());

// takeWhile / dropWhile stop at the first false.
var sortedNums = List.of(1, 2, 3, 9, 4, 5);
System.out.println(sortedNums.stream().takeWhile(n -> n < 5).toList());   // [1, 2, 3]
System.out.println(sortedNums.stream().dropWhile(n -> n < 5).toList());   // [9, 4, 5]

// peek is a no-op without a terminal operation.
Stream.of(1, 2, 3).peek(System.out::println);          // prints nothing
Stream.of(1, 2, 3).peek(System.out::println).count();  // prints 1 2 3
Do not use a stream where the body needs to break out early, mutate external state conditionally, or handle checked exceptions. Streams are for mapping and aggregating; a loop is clearer for a search with side effects, and the exception noise from wrapping IOException in UncheckedIOException repeatedly is a sign the loop was the right tool.

5.4 Collectors: grouping, partitioning and downstream reduction

Collectors is the reduction vocabulary of the stream API. It answers "into what shape?" — a list, a map, a total, a joined string — and downstream collectors compose, so a grouped average or a nested map is one pipeline.

The common collectors

Collectors.toList, toSet, toMap and their toUnmodifiable* variants are the basic shapes. groupingBy produces a Map<K, List<V>> and accepts a downstream collector. partitioningBy always produces a two-entry map keyed by Boolean. joining concatenates strings with a delimiter, prefix and suffix. counting, summingInt, averagingDouble, mapping, filtering and teeing are the combinational ones. toMap throws IllegalStateException on a duplicate key unless a merge function is supplied, which is deliberate: a silent overwrite is the bug it prevents.

import java.util.*;
import java.util.stream.*;

record Sale(String region, String rep, String product, int units, double price) {}

var sales = List.of(
    new Sale("east", "ada",   "keyboard", 12, 79.99),
    new Sale("east", "ada",   "mouse",     7, 24.50),
    new Sale("west", "grace", "keyboard",  4, 79.99),
    new Sale("west", "grace", "monitor",   3, 219.00),
    new Sale("east", "alan",  "monitor",   2, 219.00));

// Group by region, then reduce each group to a total, in one pass.
Map<String, Double> revenueByRegion = sales.stream()
    .collect(Collectors.groupingBy(
        Sale::region,
        Collectors.summingDouble(s -> s.units() * s.price())));
System.out.println(revenueByRegion);

// Two-level grouping: region -> rep -> count.
Map<String, Map<String, Long>> unitsByRep = sales.stream()
    .collect(Collectors.groupingBy(Sale::region,
             Collectors.groupingBy(Sale::rep, Collectors.counting())));
System.out.println(unitsByRep);

// toMap with an explicit merge: never let the default overwrite.
Map<String, Double> totalPerRep = sales.stream()
    .collect(Collectors.toMap(
        Sale::rep,
        s -> s.units() * s.price(),
        Double::sum));
System.out.println(totalPerRep);

// joining, with a mapping downstream and a sorted stream.
String products = sales.stream()
    .map(Sale::product).distinct().sorted()
    .collect(Collectors.joining(", ", "[", "]"));
System.out.println(products);

partitioning, teeing and the identity of a reduction

partitioningBy is groupingBy specialised to a boolean predicate, and it always returns both keys even when one side is empty — useful because it removes a null check. teeing runs two collectors over the same stream and combines their results, which computes a mean or a min-and-max in one pass instead of two. The identity of a reduction must be genuinely neutral: using 0 as the identity for a string concatenation is fine; using "" as the identity for a numeric sum is a type error; and a mutable identity such as a shared ArrayList is wrong for a parallel stream because the combiner would merge aliased state.

// partitioningBy always has both keys, which is convenient.
Map<Boolean, List<Sale>> split = sales.stream()
    .collect(Collectors.partitioningBy(s -> s.units() > 5));
System.out.println(split.get(true).size() + " big / " + split.get(false).size() + " small");

// teeing: average and count in a single traversal.
record Stats(double avg, long n) {}
Stats stats = sales.stream().collect(Collectors.teeing(
    Collectors.averagingDouble(Sale::units),
    Collectors.counting(),
    Stats::new));
System.out.printf("avg units %.2f over %d lines%n", stats.avg(), stats.n());

// A custom downstream: the top product per region by units.
Map<String, Optional<Sale>> topByRegion = sales.stream()
    .collect(Collectors.groupingBy(Sale::region,
             Collectors.maxBy(Comparator.comparingInt(Sale::units))));
topByRegion.forEach((r, s) -> System.out.println(r + " -> " + s.orElseThrow().product()));

// Collect into a TreeMap to control key order.
var sorted = sales.stream().collect(Collectors.groupingBy(
        Sale::region, TreeMap::new, Collectors.summingInt(Sale::units)));
System.out.println(sorted);

5.5 Optional and the null-avoidance strategy

Optional<T> is a container that either holds one value or holds nothing, and it exists to make absence an explicit part of a method's signature. It is not a general-purpose null replacement, and using it as one reintroduces the problem it solves.

What it is for, and the methods that keep it usable

Its intended use is a return type where absence is a normal outcome: findById, max, findFirst. It forces the caller to make a decision with orElse, orElseThrow, orElseGet or a transformation chain, and the compiler will not let the value be used without unwrapping it. The methods to know are map, flatMap, filter, ifPresent, ifPresentOrElse, or, stream and isEmpty. Since Java 10, orElseThrow() with no argument throws NoSuchElementException and is the concise form of "this must be present".

import java.util.*;

record Customer(long id, String name, Address address) {}
record Address(String city, String country) {}

var repo = Map.of(1L, new Customer(1, "ada", new Address("London", "UK")));

// Absence is in the type, and the chain stays flat.
String country = Optional.ofNullable(repo.get(9L))
        .map(Customer::address)
        .map(Address::country)
        .orElse("unknown");
System.out.println(country);

// orElseThrow is the "required" case with a useful message.
Customer found = Optional.ofNullable(repo.get(1L))
        .orElseThrow(() -> new NoSuchElementException("customer 1"));

// ifPresentOrElse handles both branches without a null check.
Optional.ofNullable(repo.get(2L)).ifPresentOrElse(
        c -> System.out.println("found " + c.name()),
        () -> System.out.println("no such customer"));

// Optional.stream() turns a list of optionals into a stream of present values.
var ids = List.of(1L, 2L, 3L);
var present = ids.stream().map(repo::get).filter(Objects::nonNull).toList();
System.out.println(present.size());

Where Optional does not belong

Do not use Optional as a field type, a method parameter, a collection element, or a key in a map. It is not Serializable, it adds an allocation per call where a plain reference or a sentinel would do, and a parameter of type Optional forces every caller to wrap a value that is already present in the overwhelming majority of calls — use overloading or a default method instead. OptionalInt, OptionalLong and OptionalDouble exist for primitives. The wider strategy is: document nullability, use Objects.requireNonNull for preconditions, annotate with @Nullable/@NonNull so a static checker can verify, and reserve Optional for the return position where it expresses a real choice.

// Anti-patterns, each with the alternative.
class Bad {
    Optional<String> name;                          // field: use a plain field + null
    void save(Optional<String> tag) {}              // parameter: overload instead
    List<Optional<String>> tags;                    // element: filter before collecting
}
class Good {
    private String name;                            // nullable, documented + annotated
    void save() { save(null); }
    void save(String tag) { Objects.requireNonNullElse(tag, "default"); }

    Optional<String> nickname() {                  // return position: the right place
        return Optional.ofNullable(name).filter(n -> !n.isBlank());
    }

    // OptionalInt avoids boxing for the primitive case.
    OptionalInt best(List<Integer> xs) {
        return xs.stream().mapToInt(Integer::intValue).max();
    }
}
A method that returns Optional should never also be able to return a meaningful null, and a method that can return null should be named or annotated so that it is obvious. Mixing the two conventions in one codebase is worse than either convention alone.

Java's memory model is shared-memory threads with defined visibility rules. The modern approach is to avoid raw threads: hand work to an executor, model a pipeline as a CompletableFuture, and for blocking I/O use virtual threads, final in Java 21.

6.1 Threads, Runnable and the thread lifecycle

A thread is an independent path of execution with its own call stack, sharing the heap with every other thread in the JVM. Creating one is cheap by historical standards and still far from free, which is why executors exist.

Creating threads, and why you usually should not

There are two ways to define a task: implement Runnable or extend Thread. Prefer Runnable — it separates the work from the scheduling, works with every executor, and does not consume the single inheritance slot. Thread.ofPlatform() and Thread.ofVirtual() (Java 21) are the modern builder-based constructors. A thread moves through NEW, RUNNABLE, BLOCKED/WAITING/TIMED_WAITING and TERMINATED; getState() reports it. A thread that throws an uncaught exception invokes its handler and terminates; by default the stack trace goes to System.err. Daemon threads do not keep the JVM alive, which makes them suitable for background housekeeping and unsuitable for work whose result you need.

// Runnable, not Thread subclass.
Runnable job = () -> {
    System.out.println(Thread.currentThread().getName() + " running");
    try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

Thread t = new Thread(job, "worker-1");
t.start();
t.join();                                   // wait for termination
System.out.println(t.getState());           // TERMINATED

// The builder form (Java 21), with an uncaught-exception handler.
Thread worker = Thread.ofPlatform()
        .name("worker-", 0)
        .daemon(true)
        .uncaughtExceptionHandler((th, ex) -> System.err.println(th.getName() + ": " + ex))
        .start(job);

// Interruption is cooperative: sleep/wait throw, a loop must check.
Thread longTask = Thread.ofPlatform().start(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // do a chunk of work
    }
});
Thread.sleep(20);
longTask.interrupt();                       // sets the flag / throws at a blocking call

Sharing the heap, and the cost of a thread

Threads share all objects, so any mutable state reachable from two threads is a data race unless access is synchronised or the state is immutable. The classic failure is the lost update: two threads read a counter, both increment, both write, and one increment disappears. A platform thread on a 64-bit JVM reserves about a megabyte of stack by default, and each is a real operating-system thread, so a few thousand is the practical ceiling before scheduling and memory dominate. That limit is why the answer for I/O-heavy workloads is an executor or virtual threads rather than one thread per request.

// A demonstrable lost update, and the three fixes.
class Counter {
    private int unsafe;
    private final java.util.concurrent.atomic.AtomicInteger atomic = new java.util.concurrent.atomic.AtomicInteger();
    private int sync;
    private final java.util.concurrent.locks.ReentrantLock lock = new java.util.concurrent.locks.ReentrantLock();

    void bumpUnsafe() { unsafe++; }                      // race
    void bumpAtomic() { atomic.incrementAndGet(); }       // CAS, lock-free
    synchronized void bumpSync() { sync++; }              // monitor
    void bumpLock() { lock.lock(); try { sync++; } finally { lock.unlock(); } }
}

var c = new Counter();
var pool = java.util.concurrent.Executors.newFixedThreadPool(8);
for (int i = 0; i < 8; i++) pool.submit(() -> { for (int j = 0; j < 100_000; j++) c.bumpAtomic(); });
pool.shutdown();
pool.awaitTermination(5, java.util.concurrent.TimeUnit.SECONDS);
System.out.println("atomic should be 800000, was " + c.atomic.get());
Never call Thread.stop(), Thread.suspend() or Thread.resume(). They are deprecated for removal because they can leave a monitor held or a data structure half-updated, and there is no safe way for a library to defend against them. Interruption is the supported mechanism.

6.2 Synchronisation and the Java memory model

Synchronisation does two jobs, and forgetting the second is why correct-looking code fails intermittently. It provides mutual exclusion, and it establishes the happens-before relationship that makes one thread's writes visible to another.

Monitors, volatile and atomicity

Every object has a monitor; synchronized on a block or method acquires it, and release happens before a later acquire of the same monitor, so everything the releasing thread wrote becomes visible. Without that edge, a value written by one thread may never be seen by another — the CPU cache and the JIT are both allowed to keep the old value. volatile gives visibility and ordering but not atomicity, so it is right for a flag and wrong for a counter. AtomicInteger, AtomicReference and the VarHandle API use compare-and-set for lock-free atomicity. Since Java 9, VarHandle exposes the full set of memory-ordering modes (getAcquire, setRelease, compareAndExchange), which is the controlled alternative to volatile and to Unsafe.

class Shared {
    private volatile boolean running = true;    // visibility, not atomicity
    private final Object gate = new Object();
    private long total;

    void stop() { running = false; }            // visible to the loop immediately

    void run() {
        while (running) { Thread.onSpinWait(); }
    }

    // Mutual exclusion plus the happens-before edge for `total`.
    void add(long n) {
        synchronized (gate) { total += n; }
    }
    synchronized long total() { return total; }

    // The lock-free equivalent with VarHandle (Java 9+).
    private static final java.lang.invoke.VarHandle TOTAL;
    static {
        try {
            TOTAL = java.lang.invoke.MethodHandles.lookup()
                    .findVarHandle(Shared.class, "total", long.class);
        } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }
    void addCas(long n) {
        long current;
        do { current = (long) TOTAL.getVolatile(this); }
        while (!TOTAL.compareAndSet(this, current, current + n));
    }
}

Deadlock, livelock and the tools that find them

Deadlock needs two locks acquired in opposite orders by two threads. The prevention is a global lock-ordering discipline: always acquire in the same sequence, or acquire one lock, or use tryLock with a timeout and back off. jstack and jcmd <pid> Thread.print detect a cycle and print it explicitly. Livelock is the same disagreement without blocking — two threads repeatedly retrying and yielding to each other. Starvation is one thread never getting scheduled because its lock is always taken by a higher-priority or busier peer. The safest design removes the contention instead: confine mutable state to one thread, share only immutable objects, and use the concurrent collections rather than wrapping a HashMap in synchronized.

import java.util.concurrent.locks.ReentrantLock;

// Ordered acquisition, or a bounded retry, are the two defences.
class Transfer {
    private final Object a = new Object();
    private final Object b = new Object();

    void ordered(boolean forward) {
        Object first = forward ? a : b;
        Object second = forward ? b : a;
        synchronized (first) {
            synchronized (second) { /* both held, same order for everyone */ }
        }
    }

    // Timeout-based avoidance when a global order is impractical.
    static boolean tryBoth(ReentrantLock x, ReentrantLock y) throws InterruptedException {
        if (x.tryLock(50, java.util.concurrent.TimeUnit.MILLISECONDS)) {
            try {
                if (y.tryLock(50, java.util.concurrent.TimeUnit.MILLISECONDS)) {
                    try { return true; } finally { y.unlock(); }
                }
            } finally { x.unlock(); }
        }
        return false;      // caller backs off and retries with jitter
    }
}
The simplest way to make a class thread-safe is to make it immutable: final fields, no setters, defensive copies of arrays and collections. An immutable object is safely publishable from any thread with no synchronisation at all, because there is no write to race with. Prefer that to a correct lock when the design allows it.

6.3 ExecutorService, thread pools and the structured alternatives

An executor separates task submission from thread management, reusing a pool instead of creating a thread per request. The java.util.concurrent package is the entry point for essentially all concurrent code.

Pool types and the queue behind each

newFixedThreadPool(n) bounds concurrency with an unbounded queue, which is right for CPU-bound work and dangerous if tasks can submit tasks, because the queue can grow without limit. newCachedThreadPool() creates threads on demand and reuses idle ones, which suits short asynchronous tasks and can explode under load. newScheduledThreadPool(n) adds delay and rate repetition. newVirtualThreadPerTaskExecutor() (Java 21) creates a virtual thread per task with no pooling. Since Java 19, Executors.newThreadPerTaskExecutor(ThreadFactory) is the general form. A ThreadPoolExecutor configured directly exposes the queue and rejection policy, which is where the real tuning happens.

import java.util.concurrent.*;

record Page(String url, String body) {}

var pool = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());
try {
    // submit returns a Future; invokeAll fans out and waits for all.
    List<Future<Page>> futures = pool.invokeAll(urls.stream()
            .map(url -> (Callable<Page>) () -> fetch(url))
            .toList());

    List<Page> pages = new ArrayList<>();
    for (Future<Page> f : futures) {
        try { pages.add(f.get()); }
        catch (ExecutionException e) { System.err.println("failed: " + e.getCause()); }
    }
} finally {
    pool.shutdown();                          // no new tasks; waits for the queue
    if (!pool.awaitTermination(10, TimeUnit.SECONDS)) pool.shutdownNow();
}

Cancellation, shutdown and StructuredTaskScope

Future.cancel(true) interrupts the running thread; the task must cooperate, and a task that already completed returns false. A Future has no way to compose, so two dependent steps need either blocking get calls or a CompletableFuture. shutdown() stops accepting submissions and lets the queue drain; shutdownNow() interrupts running tasks and drains the queue into a return value; awaitTermination is how a program waits for a graceful stop. Java 21 added StructuredTaskScope (preview in 21, more settled since), which scopes a group of subtasks to a block: when the block exits, every subtask is finished, so cancellation and error propagation cannot leak. With it, StructuredTaskScope.ShutdownOnFailure cancels siblings as soon as one fails, which is the fan-out-and-merge pattern without manual bookkeeping.

import java.util.concurrent.*;
import java.util.concurrent.StructuredTaskScope;   // preview API

record Quote(String vendor, int price) {}

// Fan out to three vendors; first failure cancels the rest.
static Quote bestQuote(List<String> vendors) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        List<StructuredTaskScope.Subtask<Quote>> tasks = vendors.stream()
                .map(v -> scope.fork(() -> quote(v)))
                .toList();
        scope.join();                 // wait for all (or for the first failure)
        scope.throwIfFailed();        // rethrow here on the calling thread
        return tasks.stream().map(Subtask::get)
                    .min(Comparator.comparingInt(Quote::price)).orElseThrow();
    }
}

// Graceful shutdown of a pool, the pattern to copy.
var pool = Executors.newFixedThreadPool(4);
pool.shutdown();
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
    List<Runnable> neverRan = pool.shutdownNow();
    System.err.println(neverRan.size() + " tasks abandoned");
}

6.4 CompletableFuture: composing asynchronous work

CompletableFuture models a value that will exist later, and, unlike Future, it can be composed, combined, recovered and given a default. It is the standard way to express a pipeline of asynchronous steps without blocking a thread per step.

Creating, chaining and combining

supplyAsync starts a value-producing task and runAsync a void one, both on the common ForkJoinPool unless an executor is supplied — and supplying one is usually correct in a server, because the common pool is shared with every parallel stream in the process. thenApply transforms, thenCompose flattens a nested future, thenCombine joins two independent futures, allOf waits for many and anyOf for the first. The Async variants run the continuation on a different thread from the executor. handle and exceptionally are the recovery paths; whenComplete observes without changing the result.

import java.util.concurrent.*;

var io = Executors.newVirtualThreadPerTaskExecutor();

CompletableFuture<String> user = CompletableFuture.supplyAsync(() -> "ada", io);
CompletableFuture<List<String>> orders = CompletableFuture.supplyAsync(
        () -> List.of("KB-01", "MS-10"), io);

CompletableFuture<String> summary = user
        .thenCombine(orders, (u, o) -> u + " has " + o.size() + " orders")
        .exceptionally(ex -> "unavailable: " + ex.getCause().getMessage());

System.out.println(summary.join());     // ada has 2 orders

// Fan out to many, wait for all, tolerate individual failures.
List<CompletableFuture<Integer>> priceFutures = List.of("a", "b", "c").stream()
        .map(sku -> CompletableFuture.supplyAsync(() -> price(sku), io)
                .exceptionally(ex -> -1))
        .toList();

CompletableFuture.allOf(priceFutures.toArray(CompletableFuture[]::new)).join();
System.out.println(priceFutures.stream().map(CompletableFuture::join).toList());

io.shutdown();

Timeouts, and the pool that must not be starved

orTimeout and completeOnTimeout (Java 9) bound a stage without a manual scheduler. The classic failure mode is a pipeline whose stages all run on one small pool: a stage that blocks waiting for another future on the same pool consumes the thread the other stage needs and the whole thing stalls. The fixes are to give blocking work its own executor, to use thenComposeAsync with an explicit executor, or — best — to run the blocking steps on newVirtualThreadPerTaskExecutor where a blocked task parks rather than occupying a platform thread. Always shut down an executor you created; the common pool must not be shut down.

import java.util.concurrent.*;

var pool = Executors.newVirtualThreadPerTaskExecutor();
try {
    CompletableFuture<Integer> slow = CompletableFuture
            .supplyAsync(() -> { sleep(2_000); return 1; }, pool)
            .orTimeout(200, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> -1);

    System.out.println(slow.join());           // -1 after 200 ms, not 2 s

    // Retry: re-attempt the stage, bounded, with a delay.
    CompletableFuture<String> flaky = CompletableFuture.supplyAsync(() -> mayFail(), pool);
    CompletableFuture<String> retried = flaky
            .thenApply(CompletableFuture::completedFuture)
            .exceptionally(ex -> CompletableFuture.supplyAsync(() -> mayFail(), pool))
            .thenCompose(f -> f);
    System.out.println(retried.join());
} finally {
    pool.shutdown();
}
Do not call join() or get() on a future from inside a task running on the same pool. With a bounded pool this deadlocks as soon as the number of nested waits reaches the thread count; the symptom is a hang under load that never reproduces in a test with one request. Virtual threads make this far less likely because a parked task does not hold a carrier, but composing instead of blocking is still the correct design.

6.5 Virtual threads and Project Loom

Virtual threads, final in Java 21 (JEP 444), are threads scheduled by the JVM rather than the operating system. They exist so that the simple blocking style scales to hundreds of thousands of concurrent tasks, without rewriting everything as callbacks or reactive streams.

What they are, and the carrier relationship

A virtual thread is a Thread instance with a tiny stack stored on the heap. Many virtual threads are mounted on a small pool of platform threads called carriers — by default, one per available processor. When a virtual thread blocks on a supported operation (socket I/O, Thread.sleep, a java.util.concurrent synchroniser, LockSupport.park) the JVM unmounts it and frees the carrier for another virtual thread. The consequence is that a million concurrent tasks cost heap, not a million OS threads. Everything else is unchanged: Thread.currentThread() still works, stack traces still print, and debugging tools understand them.

import java.util.concurrent.*;

// One virtual thread.
Thread vt = Thread.ofVirtual().name("io-1").start(() -> System.out.println("on " + Thread.currentThread()));
vt.join();
System.out.println(vt.isVirtual());        // true

// A per-task executor: the default choice for blocking I/O in a server.
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = new ArrayList<>();
    for (int i = 0; i < 100_000; i++) {
        int id = i;
        futures.add(executor.submit(() -> {
            Thread.sleep(50);                       // parks, does not pin a carrier
            return "task " + id + " done on " + Thread.currentThread();
        }));
    }
    System.out.println(futures.get(0).get());
}   // ExecutorService is AutoCloseable since Java 19: closes on block exit

Pinning, thread locals and the migration rules

A virtual thread pins its carrier while it is inside a synchronized block or method that blocks, and it also pins while inside a native frame or a foreign function call. A pinned virtual thread prevents the carrier from being reused, which degrades to the old one-OS-thread-per-task behaviour without failing; -Djdk.tracePinnedThreads=full reports the cases. The remedy is to replace synchronized with ReentrantLock in code that may block while holding the monitor — synchronized is being reworked to cooperate, and later JDKs reduce the problem, but the lock migration is the portable fix. Two more rules: ThreadLocal still works but tens of thousands of copies of a large per-thread object is now a memory problem, so prefer ScopedValue (final in Java 25) for request-scoped data; and do not pool virtual threads, because their whole point is that creation is cheap and they are short-lived.

import java.util.concurrent.locks.ReentrantLock;

// Pin: blocking inside synchronized holds the carrier.
class Pinned {
    synchronized void fetch() {
        try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

// Portable fix: a ReentrantLock does not pin.
class Unpinned {
    private final ReentrantLock lock = new ReentrantLock();
    void fetch() {
        lock.lock();
        try {
            Thread.sleep(100);                  // unmounts the virtual thread
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }
}

// ScopedValue: immutable, request-scoped data with no ThreadLocal leak.
static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

static void handle(String id) throws Exception {
    ScopedValue.where(REQUEST_ID, id).run(() ->
        System.out.println("handling " + REQUEST_ID.get()));
    // outside the scope REQUEST_ID.isBound() is false
}
Virtual threads are for blocking work: I/O, database calls, waiting on other services. They are not for CPU-bound work — a computation that pegs a core still needs a platform thread and a bounded pool sized to the processor count, or it will simply create contention. A common production shape is a virtual-thread-per-request executor for the I/O layer and a fixed pool for the compute steps, with ForkJoinPool.commonPool() left to parallel streams.

7.1 Class loading, linking and initialisation

A class is not loaded when the JVM starts. It is loaded lazily, on first active use, by a ClassLoader, and the three phases — loading, linking and initialisation — have precise rules about when code runs.

The delegation model and the three built-in loaders

A class is identified by its fully qualified name and the loader that defined it, so the same class file loaded by two loaders produces two incompatible types and a ClassCastException that looks impossible. The standard loaders are the bootstrap loader (the core modules, written in native code, visible as null from getClassLoader()), the platform loader (a few JDK modules not in java.base) and the application loader (the classpath). They follow parent-first delegation: a loader asks its parent before trying itself, which prevents a classpath jar from shadowing java.lang.String. Application servers deliberately break that order and load web-app classes child-first, which is why two libraries bundled twice cause "instanceof fails" errors.

// The loader chain for a normal application class.
Class<?> c = java.util.ArrayList.class;
for (ClassLoader l = c.getClassLoader(); l != null; l = l.getParent()) {
    System.out.println(l);
}
// jdk.internal.loader.ClassLoaders$AppClassLoader@...
// jdk.internal.loader.ClassLoaders$PlatformClassLoader@...
// (bootstrap is null and is not printed)

System.out.println(String.class.getClassLoader());      // null
System.out.println(Object.class.getModule());           // module java.base

// Loading without initialising.
Class<?> lazy = Class.forName("com.acme.Config", false, c.getClassLoader());
Class<?> ready = Class.forName("com.acme.Config");      // runs static initialisers

Linking, initialisation and the static-block trap

Linking verifies the bytecode, prepares static fields with their default values, and optionally resolves symbolic references. Initialisation runs the class's <clinit> — the compiler-generated method holding static field initialisers and static { } blocks — and it happens exactly once, under a lock, on first active use: creating an instance, reading or writing a non-constant static field, calling a static method, or reflecting on it. A class is initialised when its superclass is. The trap is that the initialisation lock is held while the block runs, so a static initialiser that waits on another thread which needs the same class deadlocks, and a static initialiser that throws wraps the exception in ExceptionInInitializerError and leaves the class unusable for the life of the JVM. Keep static { } blocks trivial; move real work into a lazily invoked holder class or a method.

class Config {
    // Runs once, under the class-init lock, before anyone can use Config.
    static final java.util.Properties PROPS = new java.util.Properties();
    static {
        try (var in = Config.class.getResourceAsStream("/app.properties")) {
            if (in == null) throw new IllegalStateException("app.properties missing");
            PROPS.load(in);
        } catch (Exception e) {
            throw new IllegalStateException("config failed", e);   // becomes ExceptionInInitializerError
        }
    }
}

// Lazy holder idiom: the inner class is initialised on first call, safely,
// with no synchronisation in the fast path (the JVM guarantees it).
class ExpensiveService {
    private ExpensiveService() { }
    private static final class Holder { static final ExpensiveService INSTANCE = new ExpensiveService(); }
    static ExpensiveService instance() { return Holder.INSTANCE; }
}

7.2 Bytecode, the constant pool and the class-file format

Bytecode is a compact stack machine instruction set. Reading it is optional for ordinary work and essential for diagnosing a lambda that captures more than you expected, a checked cast that is not where you thought, or a generic signature the runtime cannot see.

Reading a disassembly

javap -c -p prints the instructions; -v adds the constant pool, the field and method tables, the class-file version and the bootstrap-methods table. Instructions are typed by their operand kind: iload/istore for int, aload/astore for references, invokevirtual for instance dispatch, invokestatic for a class method, invokespecial for constructors and private methods, invokeinterface for interface dispatch, and invokedynamic for lambdas, method references, string concatenation and record patterns. The constant pool holds every literal, type and name the class refers to; it is the mechanism that makes class files small and linking lazy.

// Disassemble a trivial method and read the stack machine.
public class Demo {
    public static int add(int a, int b, int c) { return a + b + c; }
    public static void main(String[] args) { System.out.println(add(1, 2, 3)); }
}

# shell
javac Demo.java
javap -c -p Demo
#   public static int add(int, int, int);
#     Code:
#        0: iload_0        // push a
#        1: iload_1        // push b
#        2: iadd           // pop two, push a+b
#        3: iload_2        // push c
#        4: iadd
#        5: ireturn

# Constant pool, class-file version and bootstrap methods.
javap -v Demo | sed -n '/Constant pool/,/^{/p' | head -20
javap -v Demo | grep -E 'major|minor|flags'

invokedynamic, lambdas and what erasure leaves behind

A lambda compiles to a private synthetic method plus an invokedynamic call site that is linked once, on first execution, by LambdaMetafactory. The linked call site returns an instance of the target functional interface whose method body calls the synthetic method; a lambda that captures no variables is a single shared instance, while one that captures is allocated per evaluation. String concatenation since Java 9 uses invokedynamic with StringConcatFactory, replacing the old StringBuilder chain. Generic type arguments are present in a class file only as signatures in the metadata, which is why reflection can report List<String> for a field but not for a bare instanceof. The ClassFile API (JEP 484, final in Java 24) lets code parse, transform and generate class files in pure Java without a third-party library such as ASM.

# shell - see the synthetic lambda method and the call site
javap -c -p -v LambdaDemo | grep -A3 'BootstrapMethods'
javap -c -p LambdaDemo | grep -E 'lambda\$|invokedynamic'

# Generic signatures live in metadata, not in the descriptor.

    List<String> names;
}

System.out.println(field.getType());            // interface java.util.List

7.3 The JIT compiler: tiers, inlining and escape analysis

Bytecode is interpreted at first and compiled to native code as it proves hot. That two-stage design is why a Java program gets faster for the first minute and why a micro-benchmark that ignores it measures the wrong thing.

Tiered compilation and the warm-up problem

HotSpot runs a C1 client compiler and a C2 server compiler. Tiered compilation (the default) starts by interpreting, then compiles with C1 for moderate speed-up with low overhead, and promotes the hottest methods to C2, which inlines aggressively and optimises across call boundaries. The interpreter collects profiling data — which branch is taken, which concrete type arrives at a megamorphic call site — and the optimisations are speculative: if a later execution violates an assumption, the compilation is discarded and the method is deoptimised back to the interpreter. The practical consequences are a warm-up period, and that a method reached on only one type may be inlined and then fall off a cliff when a second type appears.

# shell - watch which methods get compiled and why
java -XX:+PrintCompilation -XX:+UnlockDiagnosticVMOptions App 2>&1 | head -40

# Force a specific tier for a comparison.
java -XX:-TieredCompilation App            # C2 only: slower start, best peak
java -Xint App                             # interpreter only: for debugging

# The diagnostic log is the reliable source for inlining decisions.
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining App 2>&1 | head -30

Inlining, escape analysis and what the optimiser can do

C2's most valuable transform is inlining, which makes every later optimisation possible by removing the call boundary. Escape analysis then proves a newly allocated object never leaves the method and can be scalar-replaced — its fields become local variables and the allocation disappears. This is why a short-lived StringBuilder or a stream's intermediate objects often cost nothing in a hot loop. Lock elision removes a synchronised block on an object that provably never escapes; lock coarsening merges adjacent acquisitions. The lesson for measurement is that a benchmark must warm up, must consume its result so dead code is not eliminated, and must be run with the JIT engaged — which is exactly what JMH does.

// JMH is the only defensible way to measure. The annotations are the point.
// build.gradle: implementation 'org.openjdk.jmh:jmh-core:1.37'  +  jmh-generator-annprocess
import org.openjdk.jmh.annotations.*;
import java.util.concurrent.TimeUnit;

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
@Fork(2)
@State(Scope.Benchmark)
public class ConcatBench {

    @Param({"16", "256"}) int size;
    private String[] parts;

    @Setup public void setup() {
        parts = new String[size];
        for (int i = 0; i < size; i++) parts[i] = "x";
    }

    @Benchmark public String builder() {
        var sb = new StringBuilder();
        for (String p : parts) sb.append(p);
        return sb.toString();
    }

    @Benchmark public String join() { return String.join("", parts); }
}
Do not "optimise" by hand without a JMH number. Escape analysis, inlining and lock elision reorder the cost model completely: a stream pipeline that looks expensive can compile to the same thing as the loop, and an object allocation that looks cheap can become a megamorphic call site. Measure with a profiler (async-profiler, JFR) first, on the real workload, and only then change the code.

7.4 Garbage collection: G1, ZGC and choosing a collector

Java has no manual memory management, but it has several collectors with different pause profiles. The heap is divided by object age, and the collector choice is a latency-versus-throughput decision, not a correctness one.

Generational collection and the collector options

Most objects die young, so the heap is split into a young generation (Eden plus two survivor spaces) and an old generation. A minor collection copies surviving young objects to a survivor space until they are promoted by age; a major or full collection reclaims the old generation and is the expensive one. G1 (the default since Java 9) divides the heap into regions and collects the ones with the most garbage first while targeting a pause goal. Parallel maximises throughput and accepts long pauses. Serial is for small heaps and single-core machines. ZGC and Shenandoah are concurrent collectors with pause times measured in fractions of a millisecond regardless of heap size, at the cost of some throughput and more memory headroom; ZGC's generational mode is the default since Java 23, which removed its main historical disadvantage.

java -Xms2g -Xmx2g -XX:+UseZGC -XX:+ZGenerational App     # generational ZGC
java -Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=100 App
java -XX:+UseParallelGC -XX:ParallelGCThreads=8 BatchJob

# container may not have the memory the JVM would otherwise request.

# Inspect a running JVM without restarting it.
jcmd <pid> GC.heap_info
jcmd <pid> GC.heap_dump /tmp/heap.hprof
jcmd <pid> VM.flags
jstat -gcutil <pid> 1000 5

Leaks, memory pressure and the container problem

Java can leak: any object still reachable from a GC root is live, and a static Map that accumulates keys, a ThreadLocal in a pooled thread, a listener that is never removed, or an unbounded cache are the classic causes. A heap dump plus a dominator-tree analysis in a profiler names the retaining path directly. The container problem is that a JVM without -XX:MaxRAMPercentage or -Xmx historically sized the heap from the machine rather than the cgroup limit, so it grew until the container was killed by the OOM killer; JDK 10 onwards is container-aware by default and uses 25% of the limit unless told otherwise. And OutOfMemoryError: Java heap space means the live set does not fit — increasing the heap only postpones it unless the retaining reference is found.

# shell - container-aware sizing and a heap-dump-on-OOM safety net
java -XX:MaxRAMPercentage=75 -XX:InitialRAMPercentage=75 \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps App

# The JVM's own view of the container limit:
java -XshowSettings:system -version
Set -Xms equal to -Xmx for a long-running service. A fixed heap removes the growth pauses, makes the memory footprint predictable to the orchestrator, and makes a leak fail early and loudly instead of silently reserving more memory until the node evicts the pod.

7.5 The module system (JPMS) and runtime images

JPMS, introduced in Java 9 as Project Jigsaw, gives the JDK and any application a compile-time and runtime unit of encapsulation above the package. Its biggest effects today are the modular JDK itself and the ability of jlink to build a runtime containing only what an application uses.

module-info and the four directives

A module is a jar with a module-info.class at the root, produced from a module-info.java. It declares requires a dependency, exports a package to consumers, opens a package for deep reflection (which frameworks need) and uses/provides a service. A package that is not exported is inaccessible even by reflection unless the module is opened; that is the strong encapsulation the system exists to provide. The JDK itself is modularised, which is why java.sql and java.xml are separate modules you can leave out of a runtime image, and why the old rt.jar no longer exists.

// module-info.java for a small service.
module com.acme.orders {
    requires java.base;                 // implicit, but explicit is clearer
    requires java.sql;
    requires transitive com.acme.shared;   // callers also see shared's exports

    exports com.acme.orders.api;          // public API
    // com.acme.orders.internal is NOT exported and stays hidden.

    opens com.acme.orders.entity to org.hibernate.orm.core;   // reflection by one framework

    uses com.acme.orders.spi.PaymentProvider;
    provides com.acme.orders.spi.PaymentProvider
        with com.acme.orders.internal.StripeProvider;

    // Java 25 also accepts a module import declaration:
    // import module java.sql;
}

# shell - compile and run a multi-module application
javac -d out/orders --module-source-path src --module com.acme.orders
java --module-path out -m com.acme.orders/com.acme.orders.Main

# Inspect the module graph and a jar's declared module.
java --list-modules | grep java.sql
jar --describe-module --file orders.jar
java --show-module-resolution -m com.acme.orders/com.acme.orders.Main

The classpath is not dead, and the unnamed module

Almost all application code still runs on the classpath, in the unnamed module, which reads every named module and exports everything. A modular jar on the module path is strongly encapsulated; the same jar on the classpath loses its encapsulation entirely. That asymmetry is deliberate and transitional: it lets an unmodularised ecosystem keep working. The practical reasons to modularise an application are jlink (a runtime image of tens of megabytes instead of a 200 MB JDK), jpackage (a native installer built from that image), reliable configuration (missing dependencies fail at startup rather than at first use), and finer access control. The practical reason not to is that every dependency must be modular, and reflection-heavy frameworks need careful --add-opens flags.

# shell - a minimal runtime image for a modular app
jlink --module-path "$JAVA_HOME/jmods:out" \
      --add-modules com.acme.orders \
      --strip-debug --no-header-files --no-man-pages --compress=zip-6 \
      --output build/image

du -sh build/image              # often 40-70 MB instead of ~300 MB
build/image/bin/java --list-modules

# Deep reflection into a modular jar needs an explicit grant.
java --add-opens com.acme.orders/com.acme.orders.entity=ALL-UNNAMED -m com.acme.orders/...

8.1 Maven: the POM, lifecycle and plugins

Maven is declarative and opinionated: a project has one standard layout, one pom.xml, and a fixed lifecycle of phases. You configure plugins to hook into phases rather than scripting the build.

The lifecycle and the standard directory layout

The default lifecycle has phases validate, compile, test, package, verify, install and deploy, run in order: mvn package runs everything up to and including packaging. Source lives in src/main/java, resources in src/main/resources, tests in src/test/java. The pom.xml declares coordinates (groupId, artifactId, version), dependencies, and the build configuration for plugins. Because the layout is standard, a developer can move between projects and a tool can integrate without configuration.

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"

Scopes, dependency management and the effective POM

A dependency's scope controls when it is on the classpath: compile (default, everywhere), provided (compile and test only — a servlet API supplied by the container), runtime (needed at run time, not to compile — a JDBC driver), test, and import which is only valid inside dependencyManagement to pull in a BOM. Transitive versions are resolved by nearest-wins, so a version declared directly always beats one inherited. mvn dependency:tree shows the resolved graph and -Dverbose marks the omitted edges, which is how a surprising transitive downgrade is found. mvn help:effective-pom prints the merged result of the project, its parents and its profile activation, which is the only way to see what Maven actually used.

# shell - the three commands that resolve most Maven mysteries
mvn -q dependency:tree -Dincludes=com.fasterxml.jackson.core
mvn -q dependency:tree -Dverbose | grep omitted
mvn help:effective-pom -Doutput=effective.xml

# Force versions centrally with a BOM, then check what changed.
mvn versions:display-dependency-updates

mvn -o clean verify            # offline, fails rather than fetching

# Run one test class or one method.
mvn -Dtest=OrderServiceTest#rejectsNegativeQuantity test

For a release, every dependency must be a fixed release version, and the CI build should produce the artifact once and promote that exact file rather than rebuilding per environment.

8.2 Gradle: the build script, tasks and incremental execution

Gradle is a build system with a real programming model, using either Kotlin DSL or Groovy DSL. It trades Maven's rigid certainty for flexibility and, in a large project, for a much faster incremental build.

Tasks, plugins and the configuration cache

Gradle models work as tasks arranged in a directed acyclic graph; a task declares its inputs and outputs, and the up-to-date check skips it when nothing changed. Plugins add task sets: java gives compileJava, test, jar; application adds run and a start script; org.springframework.boot adds bootJar. The Kotlin DSL gives compile-time checking and IDE completion. The configuration cache (stable since Gradle 8) serialises the task graph so subsequent invocations skip configuration entirely; it is the single biggest build-time win and it constrains build-script style — no project lookups at execution time.

// build.gradle.kts
plugins {
    java
    application
    id("org.springframework.boot") version "3.5.0"
}

java {
    toolchain { languageVersion = JavaLanguageVersion.of(25) }
}

repositories { mavenCentral() }

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.5.0"))

    runtimeOnly("org.postgresql:postgresql:42.7.4")
    compileOnly("org.projectlombok:lombok:1.18.34")
    annotationProcessor("org.projectlombok:lombok:1.18.34")

    testImplementation(platform("org.junit:junit-bom:5.11.4"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

application { mainClass = "com.acme.orders.Main" }

    useJUnitPlatform()
    testLogging { events("passed", "skipped", "failed") }

./gradlew build                     # assemble + check
./gradlew test --tests 'com.acme.*OrderTest'
./gradlew bootRun                   # Spring Boot, from the plugin
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath

./gradlew --configuration-cache build
./gradlew build --scan              # shareable build scan

# A reproducible build: pin the wrapper so the version is part of the repo.

The wrapper, toolchains and locked dependencies

Commit the wrapper (gradlew, gradlew.bat, gradle/wrapper/); it makes the build use exactly the Gradle version recorded there, so CI and every developer agree. A toolchain declares the Java version the code needs and Gradle locates or downloads a matching JDK, which separates the JDK that runs Gradle from the JDK that compiles the code — the same distinction that trips people up with Maven and JAVA_HOME. dependencyLocking with --write-locks records resolved versions in a lock file, giving the reproducibility that Maven gets from a fixed version set and a BOM.

// Lock every resolved version for reproducibility.
dependencyLocking { lockAllConfigurations() }
// then: ./gradlew dependencies --write-locks   → gradle.lockfile in the repo

// A custom task with declared inputs/outputs, so it is cacheable.
abstract class GenerateBuildInfo : DefaultTask() {
    @get:Input abstract val version: Property<String>
    @get:OutputFile abstract val target: RegularFileProperty

    @TaskAction fun generate() {
        target.get().asFile.writeText("version=${version.get()}\n")
    }
}
tasks.register<GenerateBuildInfo>("buildInfo") {
    version = project.version.toString()
    target = layout.buildDirectory.file("generated/build-info.properties")
}
Do not put logic in the build script that belongs in a plugin or a test. A build script is code with no tests, and a subtle ordering bug in it produces a build that fails only on a clean checkout in CI. Keep scripts to coordinates, versions and task wiring; move anything conditional into a buildSrc or included-build plugin.

8.3 JUnit 5: tests, assertions and parameterised cases

JUnit 5 is three artifacts: the Platform (launcher and engine SPI), Jupiter (the programming model you write) and Vintage (a bridge for JUnit 4 tests). The programming model is annotation-driven and, unlike JUnit 4, unconstrained by visibility.

Lifecycle, assertions and the visible-name trick

@Test marks a method; @BeforeEach and @AfterEach run around each test; @BeforeAll and @AfterAll run once per class and must be static unless the class uses @TestInstance(PER_CLASS). @DisplayName replaces the method name in reports, and @Nested groups tests sharing setup. Assertions live in org.junit.jupiter.api.Assertions: assertEquals, assertThrows, assertAll, assertTimeoutPreemptively. A modern matcher library such as AssertJ makes the failure message describe the intent, which matters more than the terseness.

import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;
import static org.assertj.core.api.Assertions.assertThat;

class BankAccountTest {

    private BankAccount account;

    @BeforeEach void openAccount() { account = new BankAccount("Ada", 10_000); }
    @AfterEach  void closeAccount() { account = null; }

    @Test @DisplayName("withdrawing more than the balance changes nothing")
    void rejectsOverdraft() {
        boolean ok = account.withdraw(20_000);
        assertFalse(ok);
        assertAll(
            () -> assertEquals(10_000, account.balanceCents()),
            () -> assertThat(account.toString()).contains("Ada"));
    }

    @Test void depositMustBePositive() {
        var ex = assertThrows(IllegalArgumentException.class, () -> account.deposit(0));
        assertThat(ex).hasMessageContaining("positive");
    }

    @Nested class WhenEmpty {
        @BeforeEach void drain() { account.withdraw(10_000); }
        @Test void refusesAnyWithdrawal() { assertFalse(account.withdraw(1)); }
    }

    // Disable with a reason, and re-enable conditionally.
    @Disabled("covered by the integration suite")
    @Test void slowPath() { }

    @Test @Tag("slow") void numberedAccounts() { }
}

Parameterised tests, extensions and mocking boundaries

A parameterised test runs one method many times with different arguments, and the arguments appear in the report, which removes the test-name inflation of copying a method per case. @CsvSource, @MethodSource, @EnumSource and @ValueSource are the common sources; @ParameterizedTest requires a source and each invocation is reported separately. @ExtendWith registers a Extension — the JUnit 5 replacement for runners and rules — which can inject parameters, manage resources or time out a whole test tree. Mockito is the usual test double library, and the design rule that makes mocking painless is to depend on small interfaces and inject them, so a fake or a mock is a drop-in.

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.*;
import java.util.stream.Stream;

class PricingTest {

    @ParameterizedTest(name = "{0} x {1} = {2}")
    @CsvSource({
        "2,  79.99, 159.98",
        "1,  24.50,  24.50",

8.4 Dependency management, version conflicts and supply-chain hygiene

Most of a modern application is code someone else wrote. Managing that graph is now a build-engineering discipline: pinning, auditing, scanning and replacing.

Conflicting versions and the shading escape hatch

Two libraries depending on different versions of a third produce one winner: Maven takes the nearest to the root, Gradle takes the highest requested version. Both can be wrong, and the resulting NoSuchMethodError or NoClassDefFoundError happens at runtime, not build time. The remedies, in order of preference: import a BOM that fixes the whole family of versions consistently; declare the version explicitly at the root; use an enforced platform. Where two libraries need genuinely incompatible versions of the same package, a shaded (relocated) build of one of them places its classes under a private package name so the two do not collide — this is what many drivers and testing libraries ship by default.

<!-- Maven: enforce a version and fail the build on a conflict -->
<dependencyManagement><dependencies>
  <dependency>
    <groupId>com.google.guava</groupId><artifactId>guava</artifactId>
    <version>33.4.0-jre</version>
  </dependency>
</dependencies></dependencyManagement>

<!-- Gradle equivalent -->
// dependencies {
//   constraints { implementation("com.google.guava:guava:33.4.0-jre") }
// }
// configurations.all { resolutionStrategy.failOnVersionConflict() }

Auditing, pinning and the minimum set

An SBOM (CycloneDX or SPDX) lists every component and version, which is what a vulnerability scanner consumes; OWASP Dependency-Check and the Gradle/Maven OWASP plugin produce one from the resolved graph. Remediation has a cost order: bump a direct dependency, override a transitive one, exclude it and supply a different provider, or accept the risk with a documented exception and an expiry date. Keep the dependency count small — every added library is code you ship but did not review, and a jar per feature is a supply-chain decision. jdeps reports what the code actually uses, which is how you find the dependency that is declared but not needed.

# shell - audit and prune
mvn org.owasp:dependency-check-maven:check
mvn dependency:analyze                 # unused + undeclared dependencies
./gradlew dependencyCheckAnalyze

# What does this jar actually need?
jdeps --multi-release 25 --ignore-missing-deps -summary target/app.jar
jdeps --jdk-internals target/app.jar   # flags use of removed internal APIs

# Generate a CycloneDX SBOM from the build graph.
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
A dependency that is declared but unused is not harmless: it enlarges the attack surface, slows the build, and can pin a version that conflicts later. dependency:analyze and Gradle's dependencyInsight find them, and a periodic prune is cheaper than an emergency upgrade under a disclosure deadline.

A command-line tool is the smallest complete Java program: arguments in, streams out, an exit code, and a jar to ship. It is also where process conventions — exit codes, stdout versus stderr, signals — have to be honoured exactly.

9.1 Arguments, parsing and validation

String[] args is the only interface the launcher gives you, and it is untyped and unvalidated. Everything useful happens in the step that turns those strings into a validated configuration object.

What the shell has already done by the time main sees argv

Quoting, glob expansion and variable substitution happen in the shell, not in Java. By the time main runs, the arguments are a list of already-split strings; on Windows the rules differ from POSIX, which is why quoting a path with spaces behaves inconsistently across platforms. A robust tool therefore parses arguments from the array it is given and never re-splits on whitespace. A common convention is a sub-command word first (git commit), then options, then positionals; another is flags only. Either way, the parse must reject unknown options rather than ignore them, because a silently ignored --dryrun typo is how a dry run turns into a real one.

// Minimal, honest parsing: validate early, fail with a usage message.
public final class Grep {
    record Options(Path file, String pattern, boolean ignoreCase, int context) {}

    static Options parse(String[] args) {
        List<String> positional = new ArrayList<>();
        boolean ignoreCase = false;
        int context = 0;

        for (int i = 0; i < args.length; i++) {
            switch (args[i]) {
                case "-i", "--ignore-case" -> ignoreCase = true;
                case "-C", "--context"      -> context = Integer.parseInt(args[++i]);
                case "-h", "--help"          -> { usage(); System.exit(0); }
                default -> {
                    if (args[i].startsWith("-")) throw new IllegalArgumentException("unknown option " + args[i]);
                    positional.add(args[i]);
                }
            }
        }
        if (positional.size() != 2) throw new IllegalArgumentException("expected PATTERN FILE");
        Path file = Path.of(positional.get(1));
        if (!Files.isReadable(file)) throw new IllegalArgumentException("cannot read " + file);
        return new Options(file, positional.get(0), ignoreCase, context);
    }

    static void usage() { System.err.println("usage: grep [-i] [-C n] PATTERN FILE"); }

    public static void main(String[] args) {
        Options opts;
        try { opts = parse(args); }
        catch (IllegalArgumentException e) {
            System.err.println("error: " + e.getMessage());
            usage();
            System.exit(2);                    // usage error, distinct from failure
        }
    }
}

Where argument validation belongs

Validate at the boundary and construct an immutable options record, so every later method receives a value it can trust. Reproduce shell semantics deliberately: a bare -- ends option processing, - as a file name means standard input, and options may be combined in one token (-iv) if you choose to support that. Reading a value for an option by incrementing the index (args[++i]) must check the index first, or a trailing -C with no value throws ArrayIndexOutOfBoundsException instead of printing a usage error — which is a real bug in a great many hand-written parsers.

// Defensive version of the same parse for a value-taking option.
case "-C", "--context" -> {
    if (i + 1 >= args.length) throw new IllegalArgumentException(args[i] + " requires a number");
    try { context = Integer.parseInt(args[i + 1]); }
    catch (NumberFormatException e) { throw new IllegalArgumentException(args[i] + " needs an integer, got " + args[i + 1]); }
    i++;                                        // consume the value
}

9.2 Standard streams, exit codes and signals

A well-behaved command-line program writes data to stdout, diagnostics to stderr, returns a meaningful exit code, and treats a closed pipe as a normal end of work rather than a crash.

The three streams and why they are separate

System.out is for the program's output — the thing a caller might pipe into another tool. System.err is for progress, warnings and errors, which must not contaminate the data stream. System.in is the input. When stdout is redirected to a file or a pipe, it is block-buffered while a terminal is line-buffered, so a prompt written to stdout may not appear before the program reads from System.in; write prompts to System.err or flush explicitly. A downstream process that exits early closes the pipe, and the next write raises IOException: Broken pipe or delivers SIGPIPE — treat it as "the consumer went away" and exit 0, not as an error.

import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.Scanner;

public final class Cat {
    public static void main(String[] args) {
        // Explicit UTF-8 reader on System.in, not the platform default.
        var in  = new BufferedReader(new InputStreamReader(System.in, StandardCharsets.UTF_8));
        var out = new BufferedWriter(new OutputStreamWriter(System.out, StandardCharsets.UTF_8));
        try {
            String line;
            while ((line = in.readLine()) != null) {
                out.write(line);
                out.newLine();
            }
            out.flush();
        } catch (IOException e) {
            if (e.getMessage() != null && e.getMessage().contains("Broken pipe")) return;  // consumer left
            System.err.println("read error: " + e.getMessage());
            System.exit(1);
        }
    }

    // Interactive prompt: goes to stderr so it never pollutes the data stream.
    static String ask(String question) {
        System.err.print(question + ": ");
        System.err.flush();
        try (var sc = new Scanner(System.in, StandardCharsets.UTF_8)) {
            return sc.hasNextLine() ? sc.nextLine().trim() : "";
        }
    }
}

Exit codes, shutdown hooks and signals

The exit code is the contract with the shell: 0 for success, non-zero for failure, and it is worth choosing a small vocabulary (1 runtime failure, 2 usage error, 3 a specific domain failure) because scripts branch on it. System.exit(n) runs shutdown hooks and then terminates; returning from main is equivalent to exit 0 and also runs hooks. A shutdown hook is a thread registered with Runtime.addShutdownHook that runs on SIGTERM and on normal exit — it is the place to flush a file, close a connection or deregister from a service registry. SIGKILL and SIGSTOP cannot be handled. A hook must be quick and must not wait on a thread that will never finish, because the JVM is already shutting down.

// Exit codes with meaning, and a graceful-stop hook.
public final class Daemon {
    public static void main(String[] args) {
        var running = new java.util.concurrent.atomic.AtomicBoolean(true);

        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.err.println("draining...");
            running.set(false);                 // signal the loop
            try { flushAndClose(); } catch (Exception e) { /* best effort */ }
        }, "shutdown"));

        int code = 0;
        try {
            while (running.get()) { work(); Thread.sleep(100); }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();  // exit 0: a signal asked us to stop
        } catch (Exception e) {
            System.err.println("fatal: " + e);
            code = 1;
        }
        System.exit(code);
    }

    static void work() { }
    static void flushAndClose() { }
}
A CLI tool should work when piped, when redirected, and when its output is a terminal — and it should detect which. System.console() returns a non-null Console only when both stdin and stdout are a terminal, which is the standard way to decide whether to print colour or progress. Under a pipe it returns null, and colour codes and carriage-return progress bars should be suppressed.

9.3 picocli: annotations, help and completion in a single file

picocli turns an annotated class into a complete command-line interface with POSIX option parsing, generated help, ANSI colour, subcommands and shell completion — all in one dependency with no runtime reflection restrictions.

Declaring a command

Annotate fields with @Option and positional parameters with @Parameters, put @Command on the class, and call new CommandLine(new MyApp()).execute(args). The execute return value is the exit code. Types are converted automatically: files, paths, enums, Duration, and anything with a registered converter. mixinStandardHelpOptions = true adds --help and --version for free. versionProvider can read the version from the jar manifest, which removes the drift between the built artifact and what --version claims.

import picocli.CommandLine;
import picocli.CommandLine.*;
import java.nio.file.Path;
import java.util.concurrent.Callable;

@Command(name = "grep", mixinStandardHelpOptions = true, version = "grep 2.1.0",
         description = "Search for PATTERN in FILE.",
         sortOptions = false)
final class GrepCommand implements Callable<Integer> {

    @Parameters(index = "0", description = "Regular expression to find.")
    String pattern;

    @Parameters(index = "1", description = "File to search.", arity = "0..1")
    Path file;

    @Option(names = {"-i", "--ignore-case"}, description = "Case-insensitive match.")
    boolean ignoreCase;

    @Option(names = {"-C", "--context"}, defaultValue = "0",
            description = "Lines of context (default: ${DEFAULT-VALUE}).")
    int context;

    @Option(names = "--color", defaultValue = "auto",
            description = "When to colour: ${COMPLETION-CANDIDATES}.")
    ColorMode color;

    enum ColorMode { auto, always, never }

    @Override public Integer call() throws Exception {
        var flags = ignoreCase ? java.util.regex.Pattern.CASE_INSENSITIVE : 0;
        var re = java.util.regex.Pattern.compile(pattern, flags);
        try (var lines = file == null ? System.in == null ? java.util.stream.Stream.<String>empty()
                                                           : new java.io.BufferedReader(
                                                                 new java.io.InputStreamReader(System.in)).lines()
                                     : java.nio.file.Files.lines(file)) {
            lines.filter(re.asPredicate()).forEach(System.out::println);
        }
        return 0;
    }

    public static void main(String[] args) {
        System.exit(new CommandLine(new GrepCommand()).execute(args));
    }
}

Subcommands, validation and completion

A tool with verbs — init, add, sync — models each as a @Command class and attaches it with addSubcommand, which also gives each subcommand its own help page. @Spec injects the parsed CommandSpec, which is how a command can print its own usage from inside its logic. Exit codes can be aligned with the shell convention by mapping exceptions to codes with an IExitCodeExceptionMapper. Shell completion for bash, zsh and PowerShell is generated by picocli.AutoComplete, and a native image build (GraalVM) works when the annotations are processed at build time.

@Command(name = "acme", mixinStandardHelpOptions = true, version = "acme 1.0",
         subcommands = {InitCmd.class, AddCmd.class, SyncCmd.class})
class Acme implements Runnable {
    @Spec CommandSpec spec;
    public void run() { spec.commandLine().usage(System.out); }
}

@Command(name = "add", description = "Add a dependency.")
class AddCmd implements Callable<Integer> {
    @Parameters(arity = "1..*", description = "Coordinates groupId:artifactId:version")
    List<String> coordinates;

    @Option(names = "--scope", defaultValue = "compile")
    String scope;

    public Integer call() {
        coordinates.forEach(c -> System.out.println("adding " + c + " (" + scope + ")"));
        return 0;
    }
}

public static void main(String[] args) {
    var cli = new CommandLine(new Acme());
    cli.setExecutionExceptionHandler((ex, cmd, parseResult) -> {
        cmd.getErr().println("error: " + ex.getMessage());
        return 1;                         // a single, documented failure code
    });
    System.exit(cli.execute(args));
}

9.4 Packaging a runnable jar and shipping a CLI

The deliverable is usually one file that a user can run with java -jar. Producing that file reproducibly, with the right manifest and no surprises about the classpath, is the last step of the chapter.

The manifest, and why java -cp is not enough

A jar is a zip with a META-INF/MANIFEST.MF. The Main-Class attribute makes it runnable with java -jar; Class-Path names sibling jars relative to the jar itself (fragile, and it does not work for repackaged tools); Multi-Release: true declares that the jar is a multi-release jar containing version-specific classes under META-INF/versions/. java -jar ignores the -cp flag and ignores CLASSPATH, so a jar that needs library jars must either bundle them or be launched with java -cp app.jar:lib/* MainClass. The manifest must be the first entry in the zip and cannot reference a Class-Path that is itself absolute, which is why bundling is the usual answer.

# shell - assemble a runnable jar by hand: classes + libraries + manifest
mkdir -p build/classes build/stage
javac -d build/classes $(find src -name '*.java')
cp -r src/main/resources/. build/classes/
(cd build/classes && jar --create --file ../app.jar .)

# A fat jar: unzip every dependency into the staging directory, merge manifests.
for j in lib/*.jar; do (cd build/stage && jar --extract --file ../../$j); done
cp -r build/classes/. build/stage/
printf 'Main-Class: com.acme.Main\n' > build/manifest.txt
jar --create --file app.jar --manifest build/manifest.txt -C build/stage .
java -jar app.jar --help

# The Spring Boot Maven plugin writes a nested fat jar with its own launcher.
mvn -q clean package
java -jar target/orders-service-1.4.0.jar

# Gradle equivalent: the application plugin builds distributions and scripts.
./gradlew installDist
./build/install/orders-service/bin/orders-service --version

Reproducible builds and shrinking the deliverable

A reproducible jar has identical bytes for identical inputs, which makes a supply-chain signature verifiable and a cache key sound. The pieces are: fix the compiler release, set project.build.outputTimestamp for Maven or Gradle's preserveFileTimestamps = false and reproducibleFileOrder = true, and exclude the manifest entries that record timestamps. The size levers are jlink for a cut-down runtime, jpackage for a native installer, and GraalVM Native Image for a standalone executable. Note that a fat jar flattens every dependency's resources into one namespace, so two libraries with the same service file can clobber each other — Spring Boot's nested-jar layout exists partly to avoid that flattening.

# Gradle: reproducible archives
tasks.withType<AbstractArchiveTask> {
    isPreserveFileTimestamps = false
    isReproducibleFileOrder = true
}

# Maven: a fixed timestamp in the manifest and artifact
// pom.xml: <project.build.outputTimestamp>2026-10-14T00:00:00Z</project.build.outputTimestamp>

# Native executable (needs GraalVM): instant start, no JVM required.
native-image -jar app.jar -o app
./app --help
Prefer the modular route (jlink plus jpackage) for a desktop tool and a container image for a server tool. A fat jar is the simplest thing that works and the right default for a small utility; it is not the right answer for a 300 MB application with a 90-second startup, where native image or a trimmed runtime changes the operational profile completely.

Java ships two desktop toolkits in the JDK era: Swing, which is old, mature and still everywhere in enterprise tools, and JavaFX, which is modern, richer, and distributed separately since JDK 11. Both use an event-dispatch thread and a declarative layout model.

10.1 Swing: components, layout managers and the EDT

Swing is a lightweight, pure-Java component set built on AWT. It has not changed significantly in years, which is exactly why it is a dependable choice for internal tools and why its threading model must be understood precisely.

The thread rule, and what happens when you break it

All Swing component access must happen on the event dispatch thread (EDT). Constructing or mutating a component from another thread is a data race: the symptom is a frozen window, a half-painted frame, or an exception that appears only under load. SwingUtilities.invokeLater queues a task; invokeAndWait queues and blocks the caller (never call it from the EDT — it deadlocks). Background work goes on a worker thread via SwingWorker, whose doInBackground runs off the EDT and whose done and publish/process run on it.

import javax.swing.*;
import java.awt.*;

public class HelloSwing {
    // Always start on the EDT, even for the initial frame.
    public static void main(String[] args) {
        SwingUtilities.invokeLater(HelloSwing::createAndShow);
    }

    private static void createAndShow() {
        var frame = new JFrame("Hello Swing");
        frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

        var label = new JLabel("Press the button");
        var button = new JButton("Count");
        button.addActionListener(e -> label.setText("clicked " + (++clicks)));

        frame.setLayout(new BorderLayout(8, 8));
        frame.add(label, BorderLayout.CENTER);
        frame.add(button, BorderLayout.SOUTH);
        frame.setSize(320, 160);
        frame.setLocationRelativeTo(null);        // centre on screen
        frame.setVisible(true);
    }

    private static int clicks;
}

Layout managers instead of coordinates

Absolute positioning (setBounds) breaks on a different font, a different DPI or a different platform. A layout manager computes positions from preferred sizes: BorderLayout for five regions, FlowLayout for a wrapping row, BoxLayout for one axis, GridLayout for equal cells, GridBagLayout for the flexible cases (powerful and verbose), and CardLayout for swapping panels like pages. Nest panels with simple managers rather than one panel with a complex one; that composition is the whole design idiom. Dialogs and models matter too: JTable reads from a TableModel, JList from a ListModel, so the data and its presentation stay separate and a background thread can update the model safely if it notifies on the EDT.

import javax.swing.*;
import javax.swing.table.AbstractTableModel;
import java.awt.*;
import java.util.List;

class OrdersModel extends AbstractTableModel {
    private final String[] cols = {"SKU", "Qty", "Total"};
    private List<String[]> rows = List.of();

    public void setRows(List<String[]> rows) {
        this.rows = rows;
        fireTableDataChanged();                  // must be on the EDT
    }
    @Override public int getRowCount()    { return rows.size(); }
    @Override public int getColumnCount() { return cols.length; }
    @Override public String getColumnName(int c) { return cols[c]; }
    @Override public Object getValueAt(int r, int c) { return rows.get(r)[c]; }
}

public class OrdersPanel {
    static JPanel build(OrdersModel model) {
        var table = new JTable(model);
        table.setFillsViewportHeight(true);

        var toolbar = new JPanel(new FlowLayout(FlowLayout.RIGHT));
        var refresh = new JButton("Refresh");
        refresh.addActionListener(e -> new SwingWorker<List<String[]>, Void>() {
            @Override protected List<String[]> doInBackground() throws Exception {
                return queryOrders();            // off the EDT
            }
            @Override protected void done() {
                try { model.setRows(get()); }     // back on the EDT
                catch (Exception ex) { JOptionPane.showMessageDialog(null, ex.getMessage()); }
            }
        }.execute());
        toolbar.add(refresh);

        var panel = new JPanel(new BorderLayout());
        panel.add(new JScrollPane(table), BorderLayout.CENTER);
        panel.add(toolbar, BorderLayout.SOUTH);
        return panel;
    }
    static List<String[]> queryOrders() { return List.of(new String[]{"KB-01", "2", "159.98"}); }
}

10.2 JavaFX: the scene graph, controls and layouts

JavaFX is a retained-mode scene graph with hardware-accelerated rendering, CSS styling, FXML and a first-class property/binding system. It is the successor to Swing and is distributed as a separate module set since JDK 11.

The scene graph and the three-part application

A JavaFX application has a Stage (a window), a Scene (its content graph and stylesheets) and a tree of Nodes (Regions that lay out children, and Controls that render something). Application.start runs on the JavaFX Application Thread, and UI updates from elsewhere must go through Platform.runLater. Layout uses panes: BorderPane, HBox/VBox, GridPane, StackPane, FlowPane, AnchorPane. JavaFX 21+ is the current line; the dependency is declared separately from the JDK, and the Maven/Gradle plugin builds a runnable image with the toolkit bundled.

import javafx.application.Application;
import javafx.application.Platform;
import javafx.geometry.Insets;
import javafx.scene.Scene;
import javafx.scene.control.*;
import javafx.scene.layout.*;
import javafx.stage.Stage;

public class OrdersApp extends Application {

    @Override public void start(Stage stage) {
        var search = new TextField();
        search.setPromptText("filter SKUs");

        var table = new TableView<Order>();
        var sku = new TableColumn<Order, String>("SKU");
        sku.setCellValueFactory(c -> c.getValue().skuProperty());
        var qty = new TableColumn<Order, Number>("Qty");
        qty.setCellValueFactory(c -> c.getValue().qtyProperty());
        table.getColumns().addAll(java.util.List.of(sku, qty));

        var filtered = new javafx.collections.transformation.FilteredList<>(
                javafx.collections.FXCollections.observableArrayList(sampleOrders()));
        filtered.predicateProperty().bind(javafx.beans.binding.Bindings.createObjectBinding(
                () -> o -> o.sku().toLowerCase().contains(search.getText().toLowerCase()),
                search.textProperty()));
        table.setItems(filtered);

        var root = new BorderPane(table);
        root.setTop(new VBox(8, new Label("Orders"), search));
        BorderPane.setMargin(root.getTop(), new Insets(8));

        stage.setTitle("Orders");
        stage.setScene(new Scene(root, 520, 360));
        stage.show();
    }

    public static void main(String[] args) { launch(args); }

    static java.util.List<Order> sampleOrders() { return java.util.List.of(); }
    record Order(String sku, int qty) {
        javafx.beans.property.StringProperty skuProperty() { return null; }
        javafx.beans.property.IntegerProperty qtyProperty() { return null; }
        String sku() { return sku; }
    }
}

CSS, modules and the platform decision

JavaFX is styled by CSS on a scene or a parent: scene.getStylesheets().add(getClass().getResource("/app.css").toExternalForm()), with a node's id and style classes as selectors. It supports a useful subset of CSS — colours, fonts, borders, backgrounds, padding, effects, transitions — and the toolkit ships a default stylesheet (modena.css) that can be overridden per control. As a modular toolkit, JavaFX requires the module path (or an explicit --add-modules javafx.controls on the classpath) and is best built with the javafx-maven-plugin or the OpenJFX Gradle plugin, which resolves platform-specific native libraries. Weighing the two toolkits: Swing has no extra dependency and a vast amount of existing code, while JavaFX has better rendering, real CSS, animation, media and a cleaner model — for a new project, JavaFX is the better default unless the environment forbids the extra dependency.

10.3 FXML, controller injection and the view/model split

FXML is an XML description of a scene graph. It lets a designer edit layout without touching Java, and it is loaded by FXMLLoader, which also binds named nodes and event handlers to a controller object.

Wiring a view to a controller

fx:id on a node makes it injectable; the loader assigns it to a @FXML field of the same name in the controller declared by fx:controller. An onAction="#methodName" attribute binds an event to a controller method, and @FXML void handler(ActionEvent e) receives it. 10.4 Properties, binding and reusable controls

The property and binding system is JavaFX's defining difference from Swing: a value is an observable object, and an expression over observable values updates itself. The model does not push updates to the view; the view declares what it depends on.

Properties, bindings and listeners

A Property<T> holds a value, fires change notifications and exposes bind (one-way), bindBidirectional and unbind. A Binding is a derived expression, produced by Bindings.createXxxBinding or by arithmetic on properties. StringProperty, IntegerProperty, BooleanProperty and the SimpleXxxProperty implementations are the concrete classes. Read-only properties are exposed as ReadOnlyXxxProperty with a private SimpleXxxProperty behind them, which is the standard encapsulation idiom for a model class. Add a listener (addListener) only when the reaction is a side effect; use a binding when the reaction is a derived value, because a binding is evaluated lazily on demand and cannot recurse.

import javafx.beans.property.*;
import javafx.beans.binding.Bindings;

public class LineItem {
    private final StringProperty sku   = new SimpleStringProperty(this, "sku", "");
    private final IntegerProperty qty  = new SimpleIntegerProperty(this, "qty", 0);
    private final DoubleProperty price = new SimpleDoubleProperty(this, "price", 0);
    private final DoubleProperty total =
            new SimpleDoubleProperty(this, "total");

    public LineItem(String sku, int qty, double price) {
        this.sku.set(sku);
        this.qty.set(qty);
        this.price.set(price);
        total.bind(qty.multiply(price));                        // derived, always current
    }

    public StringProperty  skuProperty()   { return sku; }
    public IntegerProperty qtyProperty()   { return qty; }
    public DoubleProperty  priceProperty() { return price; }
    public ReadOnlyDoubleProperty totalProperty() { return total; }   // read-only view
}

Computed aggregates and custom controls

An aggregate over a collection of properties uses Bindings.bindContent and a reduction: the sum of all line totals, the count of invalid rows, the enabled state of a button. This is where binding earns its keep, because the alternative is a manual recalculation at every mutation site and a class of stale-value bugs. A reusable control is a subclass of Control or Region with a skin, or more commonly a subclass of an existing layout with a defined public API — a LabeledTextField that exposes a validated value property. For a list, ObservableList with Bindings.bindContent keeps the view in step with the model without a manual refresh call.

11 · JDBC and databases

JDBC is the lowest-level portable database API in Java: four interfaces, a URL, and SQL as strings. Everything higher — JPA, jOOQ, MyBatis — sits on it, so the resource, transaction and type rules it imposes are the rules everything else inherits.

11.1 Drivers, the URL and getting a Connection

A JDBC driver is an implementation of java.sql.Driver that translates the JDBC calls into whatever the database speaks. Since JDBC 4 the driver is discovered automatically from the classpath via a service file, which is why modern code does not call Class.forName.

The four interfaces and one URL format

The contract is Connection (a session, and the transaction scope), Statement/PreparedStatement/CallableStatement (an execution), ResultSet (a cursor over rows) and DatabaseMetaData (capabilities). The URL is jdbc:<subprotocol>:<rest>, and everything after the subprotocol is driver-defined — so there is no portable URL, only a portable shape. A driver jar must be on the classpath (or the module path, as an automatic or named module) and must match the server version's protocol; a driver that is too old to know a newer authentication method is the usual cause of a connection failure that looks like a credentials problem.

import java.sql.*;

// The URL shape, for the databases you are most likely to meet.
String pg     = "jdbc:postgresql://localhost:5432/acme?user=app&password=secret"
              + "&sslmode=require&ApplicationName=orders";
String mysql  = "jdbc:mysql://localhost:3306/acme?useSSL=true&serverTimezone=UTC";
String oracle = "jdbc:oracle:thin:@//db-host:1521/ORCLPDB1";
String mssql  = "jdbc:sqlserver://localhost:1433;databaseName=acme;encrypt=true";
String h2mem  = "jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1";

The cost of opening a connection, and why a DataSource

Opening a connection is expensive: a TCP handshake, authentication, usually TLS, and a server-side session allocation. The legacy DriverManager creates exactly that, per call, and reads credentials from a string — which is why a DataSource is the correct entry point. A DataSource is a factory for connections that can be pooled, configured declaratively, and resolved from JNDI or from a framework's dependency injection. In a modern application the DataSource is a bean (chapter 13) or a servlet context resource (chapter 12), and the connection is borrowed and returned per unit of work, not held for the process lifetime.

Never log, echo or commit a JDBC URL that contains a password. The URL is a string that ends up in a stack trace, a metrics label and a support ticket. Pass the credentials separately, read them from the environment or a secret store, and redact the URL in any diagnostic output.

11.2 PreparedStatement, ResultSet and the SQL injection boundary

The single most important rule in JDBC is that values travel as bound parameters, never as concatenated SQL. That rule is simultaneously a security boundary and a performance feature.

Binding parameters, and why it stops injection

A PreparedStatement is sent to the server once with placeholders, and the server parses, plans and caches it; each execution supplies only the parameter values. Because a parameter can only ever be a value, it cannot change the structure of the statement, which is what makes SQL injection impossible through it. The prepared plan is reused, which is also why a prepared statement in a loop is faster than a concatenated one. A ? in the SQL is a placeholder; the driver's setXxx(index, value) methods bind it, and indices are 1-based. Table and column names cannot be bound — use an allow-list and validate any identifier that must be dynamic.

import java.sql.*;
import java.util.*;

record Customer(long id, String name, String email) {}

class CustomerDao {
    private final DataSource ds;
    CustomerDao(DataSource ds) { this.ds = ds; }

    Optional<Customer> findById(long id) throws SQLException {
        String sql = "SELECT id, name, email FROM customers WHERE id = ?";
        try (Connection con = ds.getConnection();
             PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next()
                        ? Optional.of(map(rs))
                        : Optional.empty();
            }
        }
    }

    List<Customer> search(String fragment, int limit) throws SQLException {
        String sql = """
                SELECT id, name, email
                  FROM customers
                 WHERE name LIKE ?
                 ORDER BY name
                 FETCH FIRST ? ROWS ONLY
                """;
        try (Connection con = ds.getConnection();
             PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setString(1, "%" + fragment + "%");
            ps.setInt(2, limit);
            try (ResultSet rs = ps.executeQuery()) {
                var out = new ArrayList<Customer>();
                while (rs.next()) out.add(map(rs));
                return out;
            }
        }
    }

    // Batch: many rows, one round trip, one plan.
    int[] insertAll(List<Customer> customers) throws SQLException {
        String sql = "INSERT INTO customers (name, email) VALUES (?, ?)";
        try (Connection con = ds.getConnection();
             PreparedStatement ps = con.prepareStatement(sql)) {
            for (Customer c : customers) {
                ps.setString(1, c.name());
                ps.setString(2, c.email());
                ps.addBatch();
            }
            return ps.executeBatch();
        }
    }

    private static Customer map(ResultSet rs) throws SQLException {
        return new Customer(rs.getLong("id"), rs.getString("name"), rs.getString("email"));
    }
}

ResultSet navigation and the type layer

A ResultSet is a forward-only cursor by default; TYPE_SCROLL_INSENSITIVE allows absolute positioning and CONCUR_UPDATABLE allows writing through the cursor, both at a cost. Read by column name rather than index where the query is likely to change, and by index in a hot loop where the cost matters. wasNull() is the only way to distinguish SQL NULL from the Java default after a getLong, so a nullable numeric column needs getObject or a null check. The type mapping is not always obvious: TIMESTAMP WITH TIME ZONE may arrive as Timestamp or OffsetDateTime depending on the driver, NUMERIC should be read as BigDecimal to avoid precision loss, and a large object may need getBinaryStream rather than getBytes. PreparedStatement.setObject plus ResultSet.getObject with a target class is the modern, more reliable pair.

// Null-safe reads and the modern date/time mapping.
String sql = "SELECT id, balance, created_at, notes FROM accounts WHERE id = ?";
try (Connection con = ds.getConnection();
     PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setLong(1, 42L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            long id = rs.getLong("id");

            java.math.BigDecimal balance = rs.getBigDecimal("balance");   // exact
            if (rs.wasNull()) balance = java.math.BigDecimal.ZERO;

            java.time.OffsetDateTime created =
                    rs.getObject("created_at", java.time.OffsetDateTime.class);

            String notes = rs.getString("notes");                          // null when SQL NULL
            System.out.println(id + " " + balance + " " + created + " " + notes);
        }
    }
}

11.3 Transactions, isolation levels and failure handling

A transaction groups statements so they commit or roll back as one unit. JDBC's default is autocommit, which means each statement is its own transaction — correct for a single read, wrong for any business operation that writes more than one row.

Commit, rollback and the resource discipline

Set setAutoCommit(false), do the work, then commit(); on any failure call rollback(). The connection must be returned to the pool in a known state, so the commit-or-rollback belongs in a finally block or, better, a try-with-resources wrapper that rolls back on an exception. A connection that is returned to the pool with an open transaction leaks a lock and can block every subsequent borrower — this is the most common pooling defect in production. After a rollback the connection is usable again; after a fatal error such as a broken connection it is not, and the pool must be told to discard rather than reuse it.

// An explicit transaction with a rollback on any failure.
static void transfer(DataSource ds, long from, long to, java.math.BigDecimal amount)
        throws SQLException {
    try (Connection con = ds.getConnection()) {
        boolean previous = con.getAutoCommit();
        con.setAutoCommit(false);                       // begin
        try {
            try (PreparedStatement debit = con.prepareStatement(
                     "UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?")) {
                debit.setBigDecimal(1, amount);
                debit.setLong(2, from);
                debit.setBigDecimal(3, amount);
                if (debit.executeUpdate() != 1) throw new SQLException("insufficient funds");
            }
            try (PreparedStatement credit = con.prepareStatement(
                     "UPDATE accounts SET balance = balance + ? WHERE id = ?")) {
                credit.setBigDecimal(1, amount);
                credit.setLong(2, to);
                if (credit.executeUpdate() != 1) throw new SQLException("credit account missing");
            }
            con.commit();
        } catch (SQLException | RuntimeException e) {
            con.rollback();                             // the whole transfer is undone
            throw e;
        } finally {
            con.setAutoCommit(previous);                // leave the connection as found
        }
    }
}

The isolation levels and the anomalies they prevent

Isolation trades consistency against concurrency. READ UNCOMMITTED allows dirty reads. READ COMMITTED (the default on PostgreSQL, Oracle and SQL Server) prevents them but allows non-repeatable reads and phantoms. REPEATABLE READ (the MySQL/InnoDB default) prevents non-repeatable reads; with a multi-version store it can still allow phantoms. SERIALIZABLE prevents all three, generally by taking more locks or by aborting and retrying a conflicting transaction. A lost update is the anomaly JDBC does not prevent at any level: two transactions read a balance, both subtract, and one decrement disappears. The fixes are an atomic UPDATE ... SET x = x - ?, a SELECT ... FOR UPDATE row lock, or optimistic concurrency with a version column and a WHERE version = ? clause.

// Pessimistic: lock the row for the duration of the transaction.
try (PreparedStatement ps = con.prepareStatement(
        "SELECT balance FROM accounts WHERE id = ? FOR UPDATE")) { ... }

// Optimistic: read the version, write only if it is unchanged.
int updated;
try (PreparedStatement ps = con.prepareStatement("""
        UPDATE accounts
           SET balance = ?, version = version + 1
         WHERE id = ? AND version = ?
        """)) {
    ps.setBigDecimal(1, newBalance);
    ps.setLong(2, id);
    ps.setInt(3, expectedVersion);
    updated = ps.executeUpdate();
}
if (updated == 0) throw new ConcurrentModificationException("row changed, retry");

// Savepoints: a partial rollback inside a larger transaction.
Savepoint sp = con.setSavepoint("before_audit");
try {
    writeAudit(con);
} catch (SQLException e) {
    con.rollback(sp);            // undo only the audit, keep everything before it
    con.releaseSavepoint(sp);
}
con.commit();

// The level, when the default is not enough.
con.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
A transaction must be short. Holding one open across a network call, a file read or a user interaction holds row locks and database connections for the duration, and the failure mode is a lock wait that cascades into a full outage. Do the external work before the transaction opens, or outside it entirely.

11.4 Connection pools: HikariCP and the sizing rule

A pool keeps a set of open connections and lends them for the duration of a unit of work. Because connections are expensive and the database has a hard limit on concurrency, the pool's size is a capacity decision, not a tuning knob.

Configuration that matters

HikariCP is the default pool in Spring Boot and the recommended standalone choice. The settings that decide behaviour are maximumPoolSize, minimumIdle, connectionTimeout (how long to wait for a connection before failing), idleTimeout and maxLifetime (which must be shorter than the database's own idle timeout, or the server closes a connection the pool believes is alive), and validationTimeout. A maximumPoolSize of ten per instance is usually more than enough; a common production error is setting it to 100 and discovering that the database's connection limit, not the application, becomes the bottleneck.

import com.zaxxer.hikari.HikariDataSource;
import javax.sql.DataSource;

Sizing, and the leak that looks like slowness

Pool size is bounded by the database's ability to serve concurrent queries, not by the application's desire for parallelism. A rough starting point is (cores × 2) + effective_spindle_count for a single database, then measure. If the pool is exhausted, requests queue at connectionTimeout and then fail — and the symptom is a sudden latency cliff, not an error. A leak (a connection borrowed and never closed) reduces the effective pool until the application deadlocks against itself; Hikari's leakDetectionThreshold logs a stack trace for a connection held too long, which names the culprit immediately. Always close the DataSource on shutdown so the pool's threads do not keep the JVM alive.

// Leak detection names the code that forgot to close.
config.setLeakDetectionThreshold(10_000);   // ms; log a stack trace beyond this

// A pool in a shutdown hook, or use try-with-resources on the DataSource.
Runtime.getRuntime().addShutdownHook(new Thread(pool::close));

In a containerised deployment, the number that matters is total connections across all replicas. Ten connections per pod × forty pods is four hundred sessions against one database, which is usually past its limit. Either size the pool per replica from the database's capacity divided by the replica count, or put a proxy such as PgBouncer in front, where a small number of server connections is multiplexed onto many client connections.

12 · The web with servlets and JSP

Before Spring there was the Servlet API, and it is still the contract every Java web framework implements. Understanding the container model — one servlet instance, many request threads, a scoped session — explains the shape of everything built on top of it. The API is jakarta.servlet since Jakarta EE 9; the old javax.servlet namespace is dead.

12.1 The servlet lifecycle and HttpServlet

A servlet is a class the container instantiates once and calls with many concurrent requests. The lifecycle is init, then service many times, then destroy, and the concurrency of the middle phase is the whole design constraint.

One instance, many threads

The container creates a single servlet instance (unless the class is declared SingleThreadModel, which is deprecated and wrong). Requests arrive on container threads, so instance fields are shared mutable state and must be immutable, thread-safe or absent. Everything request-specific belongs in a local variable or the request attributes. HttpServlet.service dispatches by HTTP method to doGet, doPost, doPut, doDelete and the rest, and the default implementations of the less common methods return 405. Since Servlet 3.0 the mapping can be an annotation, @WebServlet("/orders"), or a web.xml entry; mixing both is legal but a duplicate URL pattern is a startup failure.

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.*;
import java.io.IOException;
import java.time.Instant;

@WebServlet(name = "health", urlPatterns = {"/health", "/healthz"}, loadOnStartup = 1)
public class HealthServlet extends HttpServlet {

    // Immutable instance state is safe to share across request threads.
    private final Instant startedAt = Instant.now();

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("application/json");
        resp.setCharacterEncoding("UTF-8");
        resp.setHeader("Cache-Control", "no-store");

        String status = "UP";
        resp.setStatus(HttpServletResponse.SC_OK);
        resp.getWriter().printf(
                "{\"status\":\"%s\",\"uptimeSeconds\":%d}%n",
                status, java.time.Duration.between(startedAt, Instant.now()).toSeconds());
    }
}

Request and response objects

HttpServletRequest exposes parameters (getParameter returns the first value and null when absent), headers, the method, the URI, cookies, the session and a request-scoped attribute map. getParameterMap returns every value for a multi-valued field. The request body is a stream and can be read once, so a filter that consumes it must wrap the request to allow a re-read. HttpServletResponse sets the status, headers and content type before the body is committed; after the first flush the response is committed and a later sendError or sendRedirect throws IllegalStateException. Character encoding must be set before writing text, or the container uses its default and non-ASCII data arrives corrupted.

@WebServlet("/orders/create")
public class CreateOrderServlet extends HttpServlet {

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        // Parameters are request-scoped values, never shared state.
        String sku  = req.getParameter("sku");
        String qty  = req.getParameter("qty");
        String[] tags = req.getParameterValues("tag");

        if (sku == null || sku.isBlank()) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "sku is required");
            return;
        }
        int count;
        try {
            count = Integer.parseInt(qty == null ? "1" : qty);
        } catch (NumberFormatException e) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "qty must be an integer");
            return;
        }

        var created = new OrderService().create(sku, count, tags);
        req.setAttribute("order", created);            // visible to a forward target

        // PRG: redirect after a successful POST so a refresh does not resubmit.
        resp.sendRedirect(req.getContextPath() + "/orders/view?id=" + created.id());
    }
}
A servlet's init runs once and is the place to open expensive shared resources, but you cannot rely on destroy being called on a JVM crash. Close a resource that must not leak with a shutdown hook as well, or use a container-managed DataSource.

12.2 web.xml, the deployment descriptor and packaging a WAR

A web application is packaged as a WAR: a jar-shaped archive with WEB-INF/classes, WEB-INF/lib and a WEB-INF/web.xml. The descriptor configures what annotations cannot easily express.

What the descriptor still owns

Servlet mappings, filters, listeners and context parameters can be annotations, but web.xml remains the place for ordering (which filter runs first when two match), welcome files, error pages, session configuration and security constraints. The filter ordering from @WebFilter is the order the container scans, which is not specified, so a filter chain whose order matters must be declared in web.xml. A <context-param> is application-wide and read with getServletContext().getInitParameter; a <init-param> is servlet-specific and read with getServletConfig().getInitParameter. A <listener> with ServletContextListener is the standard place to start and stop application-scoped resources.

Embedded containers and why they won

A traditional WAR needs a container: Tomcat, Jetty, WildFly or GlassFish, installed separately, with the WAR deployed into it. Since the mid-2010s the dominant model is to embed the container: the application's main method starts an embedded Tomcat or Jetty, which makes the deliverable a single jar and the deployment a process rather than an installation. Spring Boot does exactly this. The embedded model removes the shared-container classloader problems, gives every application its own JVM and its own tuning, and makes the process a first-class citizen for a scheduler. The cost is a bigger artifact and the loss of container-provided services such as JNDI, which must be provided by the application instead.

12.3 JSP, EL and JSTL

A JSP is an HTML template compiled by the container into a servlet on first request. It exists so that markup lives in a file a designer can edit, and its disciplined use is as a pure view over data prepared by a servlet.

The implicit objects and what belongs in a page

A JSP has nine implicit objects, of which the important ones are request, response, session, application, out and pageContext. A scriptlet (<% ... %>) is raw Java in a template and should not be written: it defeats the separation the technology exists for and cannot be tested. The alternatives are Expression Language ${...} for reading values and JSTL tags (<c:forEach>, <c:if>, <c:choose>, <fmt:formatNumber>) for control flow and formatting. Since JSP 2.0 the recommended shape is JSP as template plus a servlet that forwards a prepared model, with <jsp:include> for reusable fragments and a <taglib> for the JSTL prefix.

12.4 Sessions, cookies and filters

HTTP is stateless, so the container supplies a session: a server-side map keyed by an opaque id that travels in a cookie. Filters are the cross-cutting layer that runs before and after every matching request.

How a session is created and found

request.getSession() creates one if absent; getSession(false) returns null rather than creating one, which matters for a health check or a static asset. The id travels in the JSESSIONID cookie, which should be HttpOnly (unreadable from JavaScript), Secure (HTTPS only) and SameSite=Lax (blocks cross-site POST forgery). Session fixation is prevented by calling changeSessionId() at login and again at privilege elevation. Invalidation is session.invalidate(). Attributes in a session must be Serializable if the container may replicate or persist the session. For clustering, either sticky sessions plus replication, or a shared store such as Redis via Spring Session, or a stateless model where the session holds only an id.

@WebServlet("/login")
public class LoginServlet extends HttpServlet {

    @Override protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        String user = req.getParameter("user");
        char[] pass = req.getParameter("password").toCharArray();

        if (!authenticate(user, pass)) {
            // Do not create a session for a failed login.
            resp.sendError(HttpServletResponse.SC_UNAUTHORIZED, "bad credentials");
            return;
        }

        // Fixation defence: a fresh id for the authenticated session.
        HttpSession existing = req.getSession(false);
        if (existing != null) existing.invalidate();
        HttpSession session = req.getSession(true);
        session.setAttribute("user", user);
        session.setMaxInactiveInterval(30 * 60);       // seconds

        resp.sendRedirect(req.getContextPath() + "/orders");
    }

    private boolean authenticate(String user, char[] pass) {
        return user != null && pass.length > 0;       // replace with a real check
    }
}

Filters and the chain

A filter implements Filter and is invoked for every matching request; it calls chain.doFilter(req, resp) to continue, and the code after that call runs on the way out. That symmetric shape is what makes an encoding filter, a logging filter, a rate limiter, a correlation-id filter and an authentication filter all look the same. To change the request or the response, wrap it: a HttpServletRequestWrapper can add a header or allow the body to be re-read, and a HttpServletResponseWrapper can capture output for compression or for a cache. Filters run before servlets and after them, so they are the correct place for anything that applies to a whole path.

import jakarta.servlet.*;
import jakarta.servlet.annotation.WebFilter;
import jakarta.servlet.http.*;
import java.io.IOException;
import java.util.UUID;

@WebFilter(urlPatterns = "/*")
public class CorrelationFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        var req  = (HttpServletRequest) request;
        var resp = (HttpServletResponse) response;

        String id = req.getHeader("X-Request-Id");
        if (id == null || id.isBlank()) id = UUID.randomUUID().toString();
        req.setAttribute("requestId", id);
        resp.setHeader("X-Request-Id", id);

        long start = System.nanoTime();
        try {
            chain.doFilter(request, response);          // the rest of the chain
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            System.out.printf("%s %s -> %d in %d ms [%s]%n",
                    req.getMethod(), req.getRequestURI(), resp.getStatus(), ms, id);
        }
    }
}

// An authentication filter that requests a session but does not create one.
@WebFilter(urlPatterns = "/orders/*")
class AuthFilter implements Filter {
    @Override public void doFilter(ServletRequest rq, ServletResponse rs, FilterChain chain)
            throws IOException, ServletException {
        var req  = (HttpServletRequest) rq;
        var resp = (HttpServletResponse) rs;
        HttpSession session = req.getSession(false);
        if (session == null || session.getAttribute("user") == null) {
            resp.sendRedirect(req.getContextPath() + "/login?next=" + req.getRequestURI());
            return;                                     // do not continue
        }
        chain.doFilter(rq, rs);
    }
}
Keep session attributes few and small, and prefer to store an identifier plus a cache lookup rather than an object graph. A large session makes replication expensive, a schema change in an attribute breaks every active session, and an attribute that references a per-request object leaks memory for the session's lifetime.

13.1 Starters, auto-configuration and the application class

What the annotation does and how auto-configuration decides

13.2 Dependency injection, beans and scopes

The container creates objects, wires their collaborators and manages their lifecycle. Injection is constructor-first, and the design pressure it creates — small classes with explicit dependencies — is the more important benefit.

Stereotypes, constructor injection and the context

@Component, @Service, @Repository and @Controller all register a bean; the specialisations add semantics and, for @Repository, exception translation. Constructor injection is preferred because the dependencies can be final, the object cannot be constructed in an invalid state, and a misplaced dependency is a compile error rather than a NullPointerException. Since Spring 4.3 a single constructor needs no @Autowired. Two beans of the same type are ambiguous: resolve with a @Qualifier, a @Primary, or by naming the parameter after the bean. Configuration classes use @Configuration and @Bean, and a @ConfigurationProperties record binds a group of settings with type checking.

import org.springframework.stereotype.Service;
import org.springframework.context.annotation.*;
import org.springframework.boot.context.properties.ConfigurationProperties;
import java.util.List;

@ConfigurationProperties(prefix = "orders")

Scopes, proxies and the lifecycle

The default scope is singleton: one instance per context. prototype creates a new instance per injection point. request and session are web scopes and, being longer-lived than the singleton that injects them, are provided as a proxy that resolves the real object per call. @PostConstruct and @PreDestroy bracket a bean's life; InitializingBean and DisposableBean are the interface equivalents. Injection into a field of a bean is technically possible and is the wrong default: it hides the dependency list, makes the class impossible to construct in a test without reflection, and permits a circular reference that the container resolves by building a half-initialised object. Circular dependencies are a design smell; break them by extracting a third collaborator.

@Component
class ReportCache {
    private final java.util.Map<String, Report> cache = new java.util.concurrent.ConcurrentHashMap<>();
    private final CaffeineHolder backing;          // whatever backs it

    ReportCache(CaffeineHolder backing) { this.backing = backing; }

    @jakarta.annotation.PostConstruct
    void warmUp() { System.out.println("warming report cache"); }

    @jakarta.annotation.PreDestroy
    void flush() { cache.forEach((k, v) -> backing.write(k, v)); }

    // request-scoped bean injected into a singleton: resolved by proxy per call
    @org.springframework.beans.factory.annotation.Autowired
    private org.springframework.beans.factory.ObjectProvider<RequestContext> ctx;
}
Keep the context small. Every @Component is a bean the container instantiates at startup, and a context with thousands of beans has a measurable start-up cost and a wide tangle of dependencies. Favour explicit configuration for infrastructure and component scanning for the application layer, and never component-scan a package you do not own — you will register a bean the library's author never intended to be a bean.

13.3 REST controllers, content negotiation and error handling

Spring MVC maps HTTP to Java methods with annotations: a URL to a method, a request body to a parameter, a return value to a response body. REST is a style over that mapping, not the mapping itself.

Mapping, binding and validation

@RestController is @Controller plus @ResponseBody, so every return value is serialised. @RequestMapping and its shorthands @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping bind methods, and a class-level prefix composes with them. @PathVariable, @RequestParam, @RequestHeader, @RequestBody and @RequestPart pull the parts of a request into parameters. @Valid triggers Jakarta Bean Validation on an annotated parameter, and a failure throws MethodArgumentNotValidException before the method body runs. Jackson serialises the response; annotate with @JsonIgnore, @JsonProperty or a mixin when the wire format must differ from the class.

import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.http.*;
import java.util.List;

@RestController
@RequestMapping("/api/v1/orders")
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    record CreateOrder(
            @NotBlank String sku,
            @Min(1) @Max(1000) int qty,
            @Email String email) { }

    record OrderView(long id, String sku, int qty, java.math.BigDecimal total) { }

    @GetMapping("/{id}")
    OrderView one(@PathVariable long id) {
        return service.find(id).map(o -> new OrderView(o.id(), o.sku(), o.qty(), o.total()))
                      .orElseThrow(() -> new OrderNotFoundException(id));
    }

    @GetMapping
    List<OrderView> search(@RequestParam(defaultValue = "") String q,
                           @RequestParam(defaultValue = "0") int page,
                           @RequestParam(defaultValue = "20") int size) {
        return service.search(q, page, Math.min(size, 100))
                      .stream().map(o -> new OrderView(o.id(), o.sku(), o.qty(), o.total())).toList();
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    ResponseEntity<OrderView> create(@Valid @RequestBody CreateOrder body) {
        var o = service.create(body.sku(), body.qty());
        var view = new OrderView(o.id(), o.sku(), o.qty(), o.total());
        return ResponseEntity.created(java.net.URI.create("/api/v1/orders/" + o.id())).body(view);

    @DeleteMapping("/{id}")

}

Errors as RFC 9457 problem details

An API must fail predictably. Spring supports the ProblemDetail type, which serialises to application/problem+json with type, title, status, detail and instance — the RFC 9457 shape (the successor to RFC 7807). A @RestControllerAdvice with @ExceptionHandler methods centralises the mapping from domain exception to status and body, so no controller repeats the translation and no stack trace ever reaches a client. Validation failures map to 400 with the field errors included; an unauthenticated request to 401; a missing resource to 404; an unexpected exception to 500 with a correlation id and the detail suppressed.

import org.springframework.web.bind.annotation.*;
import org.springframework.http.*;
import org.springframework.web.context.request.WebRequest;

class OrderNotFoundException extends RuntimeException {
    OrderNotFoundException(long id) { super("order " + id + " not found"); }
}

@RestControllerAdvice
class ApiErrors {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex, WebRequest req) {
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Order not found");
        pd.setType(java.net.URI.create("https://errors.acme.com/order-not-found"));
        pd.setProperty("instance", req.getDescription(false));
        return pd;
    }

    @ExceptionHandler(org.springframework.web.bind.MethodArgumentNotValidException.class)
    ProblemDetail invalid(org.springframework.web.bind.MethodArgumentNotValidException ex) {
        var pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("Validation failed");
        var fields = new java.util.LinkedHashMap<String, String>();
        ex.getBindingResult().getFieldErrors()
          .forEach(fe -> fields.put(fe.getField(), fe.getDefaultMessage()));
        pd.setProperty("errors", fields);
        return pd;
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex) {
        // Log with the stack trace; return nothing sensitive.
        var pd = ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
        pd.setTitle("Internal error");
        pd.setDetail("The request could not be completed");
        return pd;
    }
}
Return a DTO, never the entity. Serialising a JPA entity couples the database schema to the public API, leaks lazy-loading proxies (which throw or fetch the whole graph), and exposes columns that were never meant to be public. A record view type costs one mapping line and buys a stable contract.

13.4 Spring Data JPA, entities and transactions

JPA is the persistence specification; Hibernate is its implementation; Spring Data JPA generates repository implementations from interface declarations. Together they remove most hand-written SQL and introduce a specific set of performance traps.

Entities, repositories and derived queries

An entity is a class annotated @Entity with an @Id; the table name defaults to the class name in snake case and the column names to the field names. Repositories extend JpaRepository<T, ID>, and a method name such as findByEmailAndActiveTrue is parsed into a query — capable, but unpredictable past two or three conditions, so use @Query for anything non-obvious. Transactions are declared with @Transactional; the default is read-write and rolls back on a runtime exception but not on a checked one, which must be requested with rollbackFor. readOnly = true is a real optimisation, not documentation: it skips dirty checking.

import jakarta.persistence.*;
import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;
import org.springframework.transaction.annotation.Transactional;
import java.util.*;

@Entity
@Table(name = "customers", indexes = @Index(name = "ix_customers_email", columnList = "email", unique = true))
class Customer {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    @Enumerated(EnumType.STRING)
    private Tier tier = Tier.STANDARD;

    // Default LAZY: do not fetch the whole graph for a list screen.
    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true, fetch = FetchType.LAZY)
    private List<Order> orders = new ArrayList<>();

    @Version
    private long version;                 // optimistic locking

    protected Customer() { }              // JPA needs a no-arg constructor
    Customer(String name, String email) { this.name = name; this.email = email; }

    // getters/setters omitted
    enum Tier { STANDARD, GOLD }
}

interface CustomerRepository extends JpaRepository<Customer, Long> {

    Optional<Customer> findByEmail(String email);

    List<Customer> findByTierAndNameContainingIgnoreCase(Customer.Tier tier, String fragment);

    // Explicit query with a named parameter: no name parsing, indexable.
    @Query("select c from Customer c where c.tier = :tier and c.orders is not empty")
    List<Customer> payingCustomers(@Param("tier") Customer.Tier tier);

    // Projection: only the columns a screen needs.
    interface NameOnly { String getName(); String getEmail(); }
    List<NameOnly> findAllByTier(Customer.Tier tier);

    @Modifying
    @Transactional
    @Query("update Customer c set c.tier = :tier where c.id = :id")
    int promote(@Param("id") Long id, @Param("tier") Customer.Tier tier);
}

Lazy loading and the N+1 problem

A @OneToMany association is lazy by default, so iterating the children of each parent in a list issues one query per parent — the N+1 problem, which turns a 20 ms screen into a 2-second one. The fixes are a fetch join (join fetch in JPQL, or a @EntityGraph), a batch size (@BatchSize or hibernate.default_batch_fetch_size), or a projection that reads exactly the columns the screen needs. The other trap is that a lazy association accessed outside the transaction throws LazyInitializationException because the session is closed — the fix is to fetch eagerly within the transaction or to map to a DTO inside it, not to disable lazy loading globally.

// N+1: one query for the customers, then one per customer for the orders.
var customers = customerRepository.findByTier(Customer.Tier.GOLD);
customers.forEach(c -> System.out.println(c.getOrders().size()));

// Fix 1: an entity graph forces a single join.
interface CustomerRepository extends JpaRepository<Customer, Long> {
    @org.springframework.data.jpa.repository.EntityGraph(attributePaths = "orders")
    List<Customer> findByTier(Customer.Tier tier);
}

// Fix 2: an explicit fetch join in JPQL, with distinct for duplicates.
interface OrderRepository extends JpaRepository<Order, Long> {
    @Query("select distinct c from Customer c join fetch c.orders where c.tier = :tier")
    List<Customer> withOrders(@Param("tier") Customer.Tier tier);
}

// Fix 3: batch the lazy loads; one extra query per batch, not per row.
// application.yml:
//   spring.jpa.properties.hibernate.default_batch_fetch_size: 50

// A service transaction with read-only fast path and a DTO mapping.
@Service
class CustomerService {
    private final CustomerRepository customers;
    CustomerService(CustomerRepository customers) { this.customers = customers; }

    @Transactional(readOnly = true)
    public List<CustomerView> listGold() {
        return customers.findByTier(Customer.Tier.GOLD).stream()
                .map(c -> new CustomerView(c.getName(), c.getEmail()))   // inside the tx
                .toList();
    }

    @Transactional(rollbackFor = java.io.IOException.class)
    public void promote(Long id) throws java.io.IOException {
        customers.promote(id, Customer.Tier.GOLD);
        audit.record(id);                       // a checked exception can roll back too
    }
}
record CustomerView(String name, String email) { }
Prefer Flyway or Liquibase migrations to spring.jpa.hibernate.ddl-auto=update. Automatic schema update cannot drop or rename a column safely, produces different DDL on different databases, and leaves the production schema with no version history. Set ddl-auto: validate in production so a migration that does not match the entity fails at startup.

13.5 Configuration, profiles, actuator and testing

An application is configured by properties, from several sources with a defined precedence, and verified by a test that starts the real context. Boot gives both a strong default for each.

Properties, profiles and the precedence order

Configuration comes from command-line arguments, then the operating-system environment, then an application-{profile}.yml, then application.yml, then defaults — later sources are overridden by earlier ones, and the environment wins over a file, which is what makes a container override work without rebuilding. Bind a group of properties to a validated record with @ConfigurationProperties and @Validated rather than scattering @Value strings; the record gives completion, type checking and a single place to see the surface. Oracle Database is the enterprise RDBMS with its own SQL dialect, its own procedural language (PL/SQL) and a set of behaviours that differ from the open-source databases. This chapter covers the dialect, the objects Java code interacts with, and the JDBC specifics.

14.1 The Oracle SQL dialect

Oracle SQL is close to standard SQL and diverges in a handful of places that trip up anyone arriving from PostgreSQL or MySQL. The divergences are mostly deliberate, and mostly older than the standard.

DUAL, the empty string and the type system

DUAL is a one-row, one-column table owned by SYS that exists so a SELECT with no FROM has something to select from; SELECT 1 FROM DUAL is the canonical expression query, and it is still valid because a huge amount of Oracle SQL and thousands of tools assume it. The most notorious quirk is that Oracle treats the empty string as NULL: '' is NULL, length('') is NULL and not 0, and WHERE name = '' never matches anything. The type system uses VARCHAR2 (not VARCHAR, which is reserved for a future standard meaning), NUMBER with an optional precision and scale, DATE which always carries a time component, TIMESTAMP with optional time zone, and CLOB/BLOB for large objects. A BOOLEAN type exists in PL/SQL always and in SQL since 23ai; before that, NUMBER(1) with a CHECK (flag IN (0,1)) was the convention.

-- SQL*Plus / SQLcl
SELECT 1 FROM DUAL;
SELECT SYSDATE, SYSTIMESTAMP FROM DUAL;
SELECT USER, SYS_CONTEXT('USERENV', 'DB_NAME') FROM DUAL;

-- The empty string is NULL, and length('') is NULL, not 0.
SELECT CASE WHEN '' IS NULL THEN 'NULL' ELSE 'empty' END FROM DUAL;   -- NULL
SELECT LENGTH('') FROM DUAL;                                          -- (null)
SELECT NVL(LENGTH(''), 0) FROM DUAL;                                  -- 0

-- NVL family and the standard equivalents.
SELECT NVL(comm, 0), COALESCE(bonus, comm, 0), NVL2(comm, 'has', 'none') FROM emp;
SELECT NULLIF(status, 'UNKNOWN') FROM orders;

-- DECODE is Oracle's pre-standard CASE.
SELECT DECODE(tier, 'GOLD', 0.20, 'SILVER', 0.10, 0.05) FROM customers;

-- Row limiting since 12c; ROWNUM is the older idiom.
SELECT * FROM orders ORDER BY created_at DESC FETCH FIRST 10 ROWS ONLY;
SELECT * FROM (SELECT * FROM orders ORDER BY created_at DESC) WHERE ROWNUM <= 10;

-- Date formatting is NLS-dependent; always use an explicit format mask.
SELECT TO_CHAR(created_at, 'YYYY-MM-DD HH24:MI:SS') FROM orders;
SELECT TO_DATE('2026-10-14 09:30:00', 'YYYY-MM-DD HH24:MI:SS') FROM DUAL;
SELECT ADD_MONTHS(SYSDATE, 3), TRUNC(SYSDATE, 'MM'), LAST_DAY(SYSDATE) FROM DUAL;

Escaping, hierarchy and analytic queries

Oracle's identifier quoting is a double quote; a string literal is single-quoted, and an embedded single quote is doubled ('O''Brien'). The q'[...]' syntax removes the doubling for a literal full of quotes. Hierarchical queries use CONNECT BY PRIOR with the pseudo-column LEVEL, and SYS_CONNECT_BY_PATH builds a path string; the standard WITH ... AS (recursive) form is also supported. Analytic functions — ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM() OVER — are the standard way to compute a ranking or a running total without a self-join. The set operators are UNION, UNION ALL, INTERSECT and MINUS, the last standing in for EXCEPT.

-- Quoting and q-literals.
SELECT 'O''Brien' AS name FROM DUAL;
SELECT q'[It's got an apostrophe]' AS phrase FROM DUAL;
SELECT 'He said "hi"' FROM DUAL;

-- CONNECT BY: the management chain below a manager.
SELECT LEVEL AS depth, LPAD(' ', (LEVEL - 1) * 2) || ename AS org
  FROM emp
 START WITH mgr IS NULL
CONNECT BY PRIOR empno = mgr
 ORDER SIBLINGS BY ename;

-- The standard recursive form.
WITH org (empno, ename, mgr, depth) AS (
  SELECT empno, ename, mgr, 1 FROM emp WHERE mgr IS NULL
  UNION ALL
  SELECT e.empno, e.ename, e.mgr, o.depth + 1
    FROM emp e JOIN org o ON e.mgr = o.empno
)
SELECT * FROM org ORDER BY depth, ename;

-- Analytic ranking and a running total.
SELECT ename, deptno, sal,
       ROW_NUMBER() OVER (PARTITION BY deptno ORDER BY sal DESC) AS rn,
       RANK()       OVER (PARTITION BY deptno ORDER BY sal DESC) AS rnk,
       SUM(sal)     OVER (PARTITION BY deptno ORDER BY hiredate
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running
  FROM emp;

-- MERGE: an upsert in one statement.
MERGE INTO customers t
USING (SELECT :id AS id, :name AS name, :email AS email FROM DUAL) s
   ON (t.id = s.id)
WHEN MATCHED THEN UPDATE SET t.name = s.name, t.email = s.email
WHEN NOT MATCHED THEN INSERT (id, name, email) VALUES (s.id, s.name, s.email);

-- MINUS is EXCEPT.
SELECT id FROM current_orders MINUS SELECT id FROM archived_orders;
Never rely on an implicit date format. TO_DATE('01/02/03') depends on NLS_DATE_FORMAT and will silently give a different date on a session with a different locale: the classic bug is a month/day swap that only appears in one country. Always pass a format mask to TO_DATE, and compare a DATE/TIMESTAMP column with a value of the same type, not with a string.

14.2 Sequences, identity and concurrency-safe keys

Oracle generates surrogate keys with a sequence, a server-side counter that is independent of any transaction. Since 12c a column may also be declared as an identity column, which creates and manages a sequence for you.

Sequences and their two number sources

CREATE SEQUENCE with START WITH, INCREMENT BY, CACHE, NOCACHE and CYCLE/NOCYCLE. A sequence is consumed with seq.NEXTVAL and read with seq.CURRVAL; the value is not affected by rollback, so a rolled-back transaction leaves a gap, which is expected and correct — a sequence guarantees uniqueness and ordering, not contiguity. The CACHE setting controls how many values are pre-allocated in memory; a cache of 20 is the default and reduces contention, but a database restart loses the cached range, producing a jump and — for an ordered sequence with NOORDER — a possible out-of-order insert across a RAC cluster. The ORDER option guarantees globally increasing values in a cluster at the cost of inter-instance coordination.

CREATE SEQUENCE orders_seq
  START WITH 1000
  INCREMENT BY 1
  NOCACHE
  NOORDER
  NOCYCLE;

-- Use it, then reference the value in the same session.
INSERT INTO orders (id, sku, qty) VALUES (orders_seq.NEXTVAL, 'KB-01', 2);
INSERT INTO order_lines (order_id, line_no) VALUES (orders_seq.CURRVAL, 1);

-- Identity column (12c+): no explicit sequence, no trigger.
CREATE TABLE customers (
  id      NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name    VARCHAR2(120) NOT NULL,
  email   VARCHAR2(255) NOT NULL,
  CONSTRAINT ux_customers_email UNIQUE (email)
);

-- GENERATED BY DEFAULT allows an explicit id; useful for data migration.
CREATE TABLE legacy_import (
  id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
  payload CLOB
);

Getting a generated key back into Java

An INSERT does not return the new identity value unless you ask for it. JDBC's Connection.prepareStatement(sql, new String[]{"ID"}) plus getGeneratedKeys() is the portable way; Oracle also supports INSERT ... RETURNING id INTO ? with an OraclePreparedStatement register, which avoids the extra fetch. A batch insert of thousands of rows with getGeneratedKeys is measurably slower, so a common pattern is to generate the keys client-side from a sequence or a UUID and insert with batchUpdate. UUID keys avoid the round trip but make an index less cache-friendly; a numeric sequence is usually the better default.

import java.sql.*;

String sql = "INSERT INTO customers (name, email) VALUES (?, ?)";
try (Connection con = ds.getConnection();
     PreparedStatement ps = con.prepareStatement(sql, new String[]{"ID"})) {
    ps.setString(1, "Ada");
    ps.setString(2, "ada@example.com");
    ps.executeUpdate();
    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) System.out.println("new id = " + keys.getLong(1));
    }
}

// RETURNING INTO binds the value directly, without a second round trip.
String withReturning = "INSERT INTO customers (name, email) VALUES (?, ?) RETURNING id INTO ?";
try (var ps = (oracle.jdbc.OraclePreparedStatement) con.prepareStatement(withReturning)) {
    ps.setString(1, "Grace");
    ps.setString(2, "grace@example.com");
    ps.registerReturnParameter(3, oracle.jdbc.OracleTypes.NUMBER);
    ps.executeUpdate();
    try (var rs = ps.getReturnResultSet()) {
        if (rs.next()) System.out.println("new id = " + rs.getLong(1));
    }
}
A gap in a key column is not a bug, so never try to reuse or renumber ids. If business rules require a gapless document number — an invoice sequence, for instance — that is a different problem: it needs a locked row or a dedicated numbering table, because a sequence cannot fill a gap left by a rollback.

14.3 PL/SQL blocks, cursors and exception handling

PL/SQL is Oracle's procedural extension, executed inside the database. A block has three sections — declare, execute, handle — and the language's value is that it keeps a multi-step operation on the server, one round trip from the client.

The block and its variables

The anonymous block is DECLARE ... BEGIN ... EXCEPTION ... END;, with the declare and exception sections optional. Variables use %TYPE to inherit a column's type and %ROWTYPE to inherit a whole row, so a column width change does not break the code; CONSTANT marks a constant and NOT NULL adds a constraint. SELECT ... INTO assigns a single row and raises NO_DATA_FOUND or TOO_MANY_ROWS otherwise. DBMS_OUTPUT.PUT_LINE is the print statement, visible only when the client has enabled the buffer. A transaction is implicit: PL/SQL does not commit unless it is told to, which is what makes it composable from Java.

SET SERVEROUTPUT ON SIZE UNLIMITED

DECLARE
  v_email   customers.email%TYPE;
  v_tier    customers.tier%TYPE := 'GOLD';
  c_vat     CONSTANT NUMBER(4,2) := 0.20;
  v_total   NUMBER(12,2);
BEGIN
  SELECT email, tier
    INTO v_email, v_tier
    FROM customers
   WHERE id = 42;

  v_total := 100 * (1 + c_vat);

  DBMS_OUTPUT.PUT_LINE('customer ' || v_email || ' tier ' || v_tier);
  DBMS_OUTPUT.PUT_LINE('total ' || TO_CHAR(v_total, 'FM999,999.00'));
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('no customer 42');
  WHEN TOO_MANY_ROWS THEN
    DBMS_OUTPUT.PUT_LINE('id is not unique - schema is broken');
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('unexpected: ' || SQLCODE || ' ' || SQLERRM);
    RAISE;                      -- never swallow an unknown error
END;
/

Cursors and bulk operations

A cursor is a handle to a query's result set. An implicit cursor is created for every DML statement and its attributes are read as SQL%ROWCOUNT and SQL%FOUND. An explicit cursor is declared, opened, fetched row by row, and closed; the FOR rec IN cursor LOOP form does all four and is what you should write. A SYS_REFCURSOR is a cursor variable that can be returned to a client, which is how a stored procedure returns a result set to JDBC. BULK COLLECT fetches many rows into a collection in one context switch and FORALL performs many DML statements in one, and both are the difference between a batch job running in seconds and in minutes.

-- Explicit cursor, the readable form.
BEGIN
  FOR rec IN (SELECT id, name FROM customers WHERE tier = 'GOLD' ORDER BY name) LOOP
    DBMS_OUTPUT.PUT_LINE(rec.id || ' ' || rec.name);
  END LOOP;
END;
/

-- Bulk collect and forall: two orders of magnitude fewer context switches.
DECLARE
  TYPE t_ids IS TABLE OF customers.id%TYPE;
  v_ids t_ids;
BEGIN
  SELECT id BULK COLLECT INTO v_ids FROM customers WHERE tier = 'SILVER';

  FORALL i IN 1 .. v_ids.COUNT
    UPDATE customers SET tier = 'GOLD' WHERE id = v_ids(i);

  DBMS_OUTPUT.PUT_LINE('promoted ' || SQL%ROWCOUNT || ' customers');
END;
/

-- A cursor variable returned to the client.
CREATE OR REPLACE PROCEDURE gold_customers(p_cur OUT SYS_REFCURSOR) IS
BEGIN
  OPEN p_cur FOR SELECT id, name, email FROM customers WHERE tier = 'GOLD';
END;
/

-- Named exceptions: a business rule with its own code and message.
DECLARE
  e_insufficient EXCEPTION;
  PRAGMA EXCEPTION_INIT(e_insufficient, -20001);
BEGIN
  RAISE e_insufficient;
EXCEPTION
  WHEN e_insufficient THEN
    DBMS_OUTPUT.PUT_LINE('caught the named condition');
END;
/
Always re-raise an unexpected exception, or at least log SQLCODE and SQLERRM. A WHEN OTHERS THEN NULL; handler is the classic Oracle defect: it converts a real failure into silent data loss and removes the only evidence that anything went wrong.

14.4 Procedures, functions, packages and triggers

A stored subprogram is compiled in the database and called by name. A package groups related subprograms behind one specification, and it is the unit of API design in PL/SQL.

Procedures and functions

A procedure performs an action and returns nothing through the return position; a function returns a value and can be called from SQL. Both support parameters with the modes IN (default), OUT and IN OUT. CREATE OR REPLACE makes redeployment idempotent. A FUNCTION called from a SQL statement must be deterministic or the optimiser may cache a wrong result: declare DETERMINISTIC when that is true, and PARALLEL_ENABLE when it is safe to run in a parallel slave. A RESULT_CACHE clause caches the function's result keyed by its arguments, which is a large win for a lookup that is called per row.

CREATE OR REPLACE FUNCTION tax_amount(
    p_region IN VARCHAR2,
    p_net    IN NUMBER
) RETURN NUMBER DETERMINISTIC IS
    v_rate NUMBER(4,2);
BEGIN
  v_rate := CASE p_region
              WHEN 'EU' THEN 0.20
              WHEN 'UK' THEN 0.20
              WHEN 'US' THEN 0.07
              ELSE 0
            END;
  RETURN ROUND(p_net * v_rate, 2);
END;
/

-- Callable from SQL once compiled.
SELECT id, tax_amount('EU', 100) AS tax FROM orders FETCH FIRST 5 ROWS ONLY;

CREATE OR REPLACE PROCEDURE promote_customer(
    p_id   IN  NUMBER,
    p_tier IN  VARCHAR2 DEFAULT 'GOLD',
    p_rows OUT NUMBER
) IS
BEGIN
  UPDATE customers SET tier = p_tier WHERE id = p_id;
  p_rows := SQL%ROWCOUNT;
END;
/

Packages, package state and triggers

A package has a specification (what is public) and a body (the implementation). Only the specification is referenced by dependents, so changing the body does not invalidate them. Package-level variables have session scope and persist for the life of the session, which makes them a per-session cache and also a per-session memory leak; DBMS_SESSION.MODIFY_PACKAGE_STATE(DBMS_SESSION.REINITIALIZE) resets them. A package can overload a subprogram by parameter type, and it can have an initialisation block at the end of the body that runs once per session. A trigger fires on DML or on a system event; a row-level trigger is the place for an audit row or a derived column, and a statement-level trigger for a bulk rule. Triggers are powerful and hard to debug: a trigger that fires on a table another trigger also touches can produce cascading updates that no application code can see.

-- Specification: the public API.
CREATE OR REPLACE PACKAGE customer_api AS
  FUNCTION  tax(p_region IN VARCHAR2, p_net IN NUMBER) RETURN NUMBER DETERMINISTIC;
  PROCEDURE promote(p_id IN NUMBER, p_tier IN VARCHAR2 DEFAULT 'GOLD');
  PROCEDURE list_gold(p_cur OUT SYS_REFCURSOR);
  c_max_tier CONSTANT VARCHAR2(8) := 'PLATINUM';
END customer_api;
/

-- Body: the implementation, plus a session-scoped counter.
CREATE OR REPLACE PACKAGE BODY customer_api AS
  g_calls PLS_INTEGER := 0;

  FUNCTION tax(p_region IN VARCHAR2, p_net IN NUMBER) RETURN NUMBER IS
  BEGIN
    g_calls := g_calls + 1;
    RETURN ROUND(p_net * CASE p_region WHEN 'EU' THEN 0.20 WHEN 'US' THEN 0.07 ELSE 0 END, 2);
  END tax;

  PROCEDURE promote(p_id IN NUMBER, p_tier IN VARCHAR2 DEFAULT 'GOLD') IS
  BEGIN
    UPDATE customers SET tier = p_tier WHERE id = p_id;
    IF SQL%ROWCOUNT = 0 THEN
      RAISE_APPLICATION_ERROR(-20002, 'no customer ' || p_id);
    END IF;
  END promote;

  PROCEDURE list_gold(p_cur OUT SYS_REFCURSOR) IS
  BEGIN
    OPEN p_cur FOR SELECT id, name FROM customers WHERE tier = 'GOLD';
  END list_gold;
END customer_api;
/

-- An audit trigger: row-level, fires for every changed row.
CREATE OR REPLACE TRIGGER trg_customers_audit
AFTER INSERT OR UPDATE OR DELETE ON customers
FOR EACH ROW
BEGIN
  INSERT INTO customers_audit (changed_at, action, old_tier, new_tier, actor)
  VALUES (SYSTIMESTAMP,
          CASE WHEN INSERTING THEN 'I' WHEN UPDATING THEN 'U' ELSE 'D' END,
          :OLD.tier, :NEW.tier, SYS_CONTEXT('USERENV', 'SESSION_USER'));
END;
/
Package-level variables persist across calls in the same session, so a package used as a cache in a connection-pooled application holds a stale value for as long as the pooled connection lives. Either reset the state per unit of work or move the cache out of the database.

14.5 JDBC with the Oracle driver

The Oracle JDBC driver (ojdbc11.jar, ojdbc17.jar for Java 17 and later) is a thin Java client that speaks Oracle's wire protocol directly. It is not a from-scratch reinvention: it implements the same java.sql interfaces, with a set of Oracle-specific extensions.

Connecting and the extensions worth knowing

The thin URL form is jdbc:oracle:thin:@//host:port/service_name, where the service name (not the SID) is the modern identifier. oracle.jdbc.OracleConnection adds Oracle types and features: createArrayOf for a VARRAY or nested table, createStruct for an object type, and setObject with an OracleType for TIMESTAMP WITH TIME ZONE or INTERVAL. SYS_REFCURSOR is registered as OracleTypes.CURSOR and read as a ResultSet. ARRAY and Struct mappings use java.sql.Array and java.sql.Struct. Fetch size matters more on Oracle than on most databases because the default is small; setting setFetchSize(500) on a statement that returns many rows is a large, free improvement.

import java.sql.*;
import oracle.jdbc.OracleTypes;

String url = "jdbc:oracle:thin:@//db-host:1521/ORCLPDB1";

try (Connection con = DriverManager.getConnection(url, "app", System.getenv("ORA_PASSWORD"))) {

    // Fetch size: the single most effective read tuning knob.
    try (PreparedStatement ps = con.prepareStatement(
             "SELECT id, name FROM customers WHERE tier = ? ORDER BY name")) {
        ps.setFetchSize(500);
        ps.setString(1, "GOLD");
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                System.out.println(rs.getLong("id") + " " + rs.getString("name"));
            }
        }
    }

    // Call a package procedure that returns a cursor.
    try (CallableStatement cs = con.prepareCall("{ call customer_api.list_gold(?) }")) {
        cs.registerOutParameter(1, OracleTypes.CURSOR);
        cs.execute();
        try (ResultSet rs = (ResultSet) cs.getObject(1)) {
            while (rs.next()) System.out.println(rs.getString("name"));
        }
    }

    // An IN OUT parameter of a scalar type.
    try (CallableStatement cs = con.prepareCall("{ call customer_api.promote(?, ?, ?) }")) {
        cs.setLong(1, 42L);
        cs.setString(2, "GOLD");
        cs.registerOutParameter(3, Types.NUMERIC);
        cs.execute();
        System.out.println("rows affected: " + cs.getInt(3));
    }
}

Data types, dates and arrays

Oracle's types do not map one-to-one to Java. NUMBER without a scale may exceed a long, so read it as BigDecimal unless the column is known to be small. DATE carries a time component and maps to java.sql.Timestamp; a TIMESTAMP WITH TIME ZONE should be read with getObject(..., OffsetDateTime.class) so the offset survives. CLOB and BLOB stream with getCharacterStream and getBinaryStream. A nested table or VARRAY is a java.sql.Array whose getArray() returns an Object[], and a user-defined object type is a java.sql.Struct. The oracle.jdbc.OracleTypes constants are the type codes to pass to registerOutParameter for the Oracle-specific cases.

// Exact numerics and time-zone-aware timestamps.
String sql = "SELECT id, balance, created_ts FROM accounts WHERE id = ?";
try (PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setLong(1, 42L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            java.math.BigDecimal balance = rs.getBigDecimal("balance");     // never a double
            java.time.OffsetDateTime created =
                    rs.getObject("created_ts", java.time.OffsetDateTime.class);
            System.out.println(balance + " @ " + created);
        }
    }
}

// A VARRAY column: java.sql.Array wrapping a String[].
try (PreparedStatement ps = con.prepareStatement("SELECT tags FROM products WHERE id = ?")) {
    ps.setLong(1, 7L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            java.sql.Array arr = rs.getArray("tags");
            if (arr != null) {
                String[] tags = (String[]) arr.getArray();
                System.out.println(java.util.Arrays.toString(tags));
            }
        }
    }
}

// Passing an array back into a nested-table parameter.
Object[] region = { "EU", "UK" };
java.sql.Array sqlArray = con.createArrayOf("VARCHAR2", region);
try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO promo_regions (promo_id, regions) VALUES (?, ?)")) {
    ps.setLong(1, 99L);
    ps.setArray(2, sqlArray);
    ps.executeUpdate();
}
Use the thin driver and UCP (Universal Connection Pool) or HikariCP rather than the deprecated OCI driver. Verify the driver's server compatibility matrix before an upgrade: a driver several releases old can fail a new authentication or encryption negotiation in a way that reports as a generic connection error. Keep the driver on the same release train as the database where possible.

A Java program ships as a set of class files plus the runtime that executes them. The choices are how many jars, whether the runtime is shared or bundled, and whether the unit of deployment is a jar, a native installer, a container image or a platform-managed buildpack.

15.1 Jars, fat jars and module jars

A jar is a zip with a manifest. The packaging decision is where the dependencies live: alongside, inside, or resolved at runtime by a module path.

The three shapes

A thin jar contains only the application's classes and names its dependencies in the manifest's Class-Path or expects them on the classpath; it is small and stable but the deployment unit is a directory. A fat or uber jar contains every dependency, unzipped and flattened into one archive; it is a single file and the simplest thing to ship, at the cost of size and of resource-name collisions. A shaded jar goes further and relocates dependency packages under a private prefix, which is how two libraries that need incompatible versions of the same package coexist. A modular jar keeps the dependencies outside and declares them in module-info; it is the smallest runtime and the strongest encapsulation, and the strictest about its dependencies also being modular.

What breaks inside a fat jar

Flattening destroys the META-INF/services service loader files when two dependencies provide the same file name: the second overwrites the first, and a JDBC driver or a JSON provider stops being discovered. Spring Boot's nested-jar layout avoids that by keeping each dependency as its own jar inside. A signed jar also breaks: the manifest digests no longer match after flattening, so a SecurityException or a class-load failure appears out of nowhere. And a resource addressed by a fixed path — getResource("/config.properties") — can shadow another module's file of the same name. These are the reasons a build tool's own packaging plugin is preferable to a hand-rolled unzip-and-rejar.

# Gradle: a fat jar and a shadowed jar
// build.gradle.kts
tasks.jar {
    manifest { attributes("Main-Class" to "com.acme.Main") }
    from({ configurations.runtimeClasspath.get().map { if (it.isDirectory) it else zipTree(it) } })
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
}

// Or use the plugin that gets it right:
// plugins { id("com.github.johnrengelman.shadow") version "8.1.1" }
// tasks.shadowJar { archiveClassifier = "all"; mergeServiceFiles() }
A fat jar built by naive extraction loses service files silently. mergeServiceFiles() in the shadow plugin and Boot's nested layout both solve it; a hand-written unzip -o loop does not. If a dependency becomes invisible only in the packaged artifact and works perfectly in the IDE, this is the first thing to check.

15.2 jlink and custom runtime images

Since JDK 9 the JDK itself is modular, and jlink can assemble a runtime image that contains only the modules an application needs. The output is a directory with its own java launcher.

What goes in and how big it gets

jlink --add-modules takes either an explicit list or the special value ALL-MODULE-PATH, resolves the transitive closure, and writes an image with a bin, conf, lib and legal directory. Flags that matter: --strip-debug removes debug information, --no-header-files and --no-man-pages remove the C headers and manual pages a developer would need but a deployment does not, --compress=zip-6 compresses the image, --include-locales keeps only selected locales, and --vm=server picks the HotSpot variant. A typical server application's image is tens of megabytes rather than the roughly 300 MB of a full JDK, and the win compounds in a container layer.

# shell - the smallest useful server image, and a hello-world one
JMODS="$JAVA_HOME/jmods"

# Which modules does the application actually need?
jdeps --multi-release 25 --ignore-missing-deps --print-module-deps --class-path "lib/*" app.jar
# -> java.base,java.logging,java.sql,java.naming,jdk.crypto.ec

jlink --module-path "$JMODS" \
      --add-modules java.base,java.logging,java.sql,java.naming,jdk.crypto.ec \
      --strip-debug --no-header-files --no-man-pages --compress=zip-6 \
      --output build/runtime

build/runtime/bin/java -version
du -sh build/runtime                 # a fraction of a full JDK

# A one-module image and a launcher script, all in one command.
jlink --add-modules java.base --add-launcher hello=hello.properties --output hello-image

The launcher properties file and constraints

--add-launcher name=file.properties embeds a launcher whose main-class, module, class-path and JVM options are recorded in the image, so the user runs image/bin/name rather than remembering a module path. The constraints are real: an automatic module (a plain jar with only a derived name) can be used on the module path but cannot be jlink'd into a custom image, and a dependency that uses deep reflection on a JDK-internal package needs --add-opens in the launcher's JVM options. For a non-modular application the working combination is jlink for the runtime plus an explicit --class-path in the launcher, or jpackage for the whole thing.

# hello.properties - the launcher embedded in the image
# main-class=com.acme.Main
# class-path=lib/app.jar:lib/postgresql-42.7.4.jar
# java-options=-Xmx512m
# java-options=--add-opens=java.base/java.lang=ALL-UNNAMED

# shell - build a runtime for a non-modular app and launch it
jlink --add-modules ALL-MODULE-PATH --strip-debug --no-header-files --no-man-pages \
      --compress=zip-6 --output build/runtime
build/runtime/bin/java -cp "app.jar:lib/*" com.acme.Main --help
Size the image from jdeps --print-module-deps rather than guessing. Including a module you do not need costs a few megabytes; omitting one costs a NoClassDefFoundError at first use of a rarely exercised path, which is exactly the kind of failure that appears in production and not in a smoke test.

15.3 jpackage, native installers and GraalVM native image

A JDK runtime is not something an end user should have to install. jpackage wraps a runtime image and an application into a platform-native installer; GraalVM Native Image compiles the application ahead of time into a standalone executable with no JVM at all.

jpackage output formats

jpackage --type selects the platform's installer: msi or exe on Windows, dmg or pkg on macOS, deb or rpm on Linux, and app-image for an unpackaged directory. Inputs are --input (the classes and jars), --main-jar and --main-class, --name, --app-version, --icon, and --runtime-image to bundle a custom runtime. The result is a normal installer that registers the application with the operating system and installs a private runtime, so the user needs no JDK. This is the route to a desktop tool that behaves like every other app, and it is the pairing for the JavaFX work in chapter 10.

# shell - a Windows MSI containing a trimmed runtime of its own
jlink --add-modules java.base,java.desktop,javafx.controls --output build/runtime

jpackage --type msi \
         --name "Acme Orders" \
         --app-version 1.4.0 \
         --input build/libs \
         --main-jar orders-desktop.jar \
         --main-class com.acme.OrdersApp \
         --runtime-image build/runtime \
         --icon assets/app.ico \
         --win-menu --win-shortcut \
         --dest build/installers

# A macOS disk image, and a Linux deb, from the same inputs.
jpackage --type dmg --name "Acme Orders" ... --dest build/installers
jpackage --type deb --name acme-orders ... --dest build/installers

Native image and what it changes

GraalVM Native Image does a whole-program static analysis at build time and emits a platform native executable that includes only the reachable code. The results are a startup measured in tens of milliseconds instead of one or more seconds, a much smaller memory footprint, and no JVM at all. The cost is the analysis: reflection, dynamic proxies, JNI and resource loading are invisible to a static analyser, so they need explicit configuration, produced automatically by the tracing agent or supplied by a library's own metadata. Builds are slow (minutes) and the peak throughput of a hot loop can be lower than a warmed-up JIT, which matters for a long-running batch job and not at all for a scale-to-zero function.

# shell - build a native executable, with the tracing agent filling the config
native-image -jar target/app.jar -o build/acme \
             -H:Name=acme -H:+ReportExceptionStackTraces

# Java 24+ moved the entry points into the JDK so no extra toolchain is needed:
# java -agentlib:native-image-agent=config-output-dir=META-INF/native-image -jar app.jar
# (run the app through a representative workload, then build)

# Verify startup time: this is the metric native image changes.
time ./build/acme --version
time java -jar target/app.jar --version
Choose the packaging by the workload. A scale-to-zero serverless function wants native image or a trimmed runtime so cold start is small. A long-running service wants a normal JVM so the JIT can reach its peak and the operator can attach tools. A desktop tool wants jpackage. A batch job wants throughput, so the JVM with a large heap and the Parallel collector.

15.4 Containers, JVM tuning and cloud deployment

A container is how a Java service is normally deployed now. The JVM must be told it is in a container, and the image must be layered so that a code change does not re-download the world.

The image, and why the order matters

Every COPY and RUN instruction is a layer, and Docker caches a layer until its inputs change. Copying the pom and running a dependency download before copying the source means the dependency layer survives a source change, which turns a two-minute rebuild into a few seconds. A multi-stage build compiles in one image and ships only the runtime in the next, which keeps the final image small and free of the build tools.

# Dockerfile - multi-stage, cache-aware, non-root
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -B -q dependency:go-offline          # cached until the pom changes
COPY src src
RUN ./mvnw -B -q clean package -DskipTests      # tests run in CI, not here

FROM eclipse-temurin:25-jre
WORKDIR /app

# Run as a non-root user.
RUN groupadd -r app && useradd -r -g app app
COPY --from=build --chown=app:app /src/target/app.jar app.jar

ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError -XX:+UseG1GC"
USER app
EXPOSE 8080

# exec form, so the JVM is PID 1 and receives SIGTERM directly.
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Container awareness, limits and probes

JDK 10 onwards is container-aware: with no explicit -Xmx, the heap defaults to 25% of the container's memory limit, and the number of GC and JIT threads follows the CPU quota. Set -XX:MaxRAMPercentage and InitialRAMPercentage so the heap is a stated fraction, and leave headroom for thread stacks, metaspace, the JIT code cache and direct buffers — a container sized exactly to the heap is killed by the OOM killer. Use -XX:+ExitOnOutOfMemoryError so a heap exhaustion terminates the process and the platform restarts it, rather than leaving it alive and failing every request. A Kubernetes readiness probe should point at /actuator/health/readiness and a liveness probe at /actuator/health/liveness, so a slow start is not mistaken for a hang and a deadlock is not mistaken for a slow start.

# Kubernetes: resources, probes and a graceful shutdown window
spec:
  containers:
    - name: orders
      image: registry.example.com/acme/orders:1.4.0
      ports: [{ containerPort: 8080 }]
      resources:
        requests: { memory: "512Mi", cpu: "250m" }
        limits:   { memory: "1Gi",   cpu: "1" }
      env:
        - name: JAVA_TOOL_OPTIONS
          value: "-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError"
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }
        initialDelaySeconds: 5
        periodSeconds: 5
      livenessProbe:
        httpGet: { path: /actuator/health/liveness, port: 8080 }
        initialDelaySeconds: 20
        periodSeconds: 10
      lifecycle:
        preStop: { exec: { command: ["sh", "-c", "sleep 5"] } }
  terminationGracePeriodSeconds: 45

# shell - build, run and inspect the container locally
docker build -t acme/orders:1.4.0 .
docker run --rm -p 8080:8080 -e DB_PASSWORD=secret -m 1g acme/orders:1.4.0

# Verify the JVM saw the container limit, not the host's memory.
docker exec <id> java -XshowSettings:system -version 2>&1 | grep -i memory

# Health, liveness and metrics.
curl -s localhost:8080/actuator/health | jq
curl -s localhost:8080/actuator/prometheus | head
Never put -XX:+ExitOnOutOfMemoryError in a single-shot batch job whose output has not been flushed: the process exits without running orderly shutdown code, so any partially written file stays partial. It is the right flag for a stateless server and the wrong one for a job that accumulates work in memory.
For a serverless or scale-to-zero target, choose the packaging by cold-start budget: a trimmed jlink runtime helps, Spring Boot's AOT and CDS support helps more, and GraalVM Native Image helps most — at the cost of build time and reflection configuration. Measure the cold start with the real workload before committing to a route, because the difference between a 300 ms and a 30 ms start is what decides whether a function is viable.
