0.1 What this guide covers

The subject is a single framework — Leaf PHP — examined at the level of the contracts a production application depends on.

Leaf PHP is a small, unopinionated MVC microframework written for PHP 8. This guide documents its runtime behaviour: how requests enter the application, how each layer is expected to interact, and where the framework stops helping and your own code must take over.

It is a vendor document, not a tutorial. Code samples are minimal, complete, and framed as contracts rather than as a build-along project. Where a recommendation is a convention rather than an enforced rule, that is stated explicitly.

Three questions are answered for every subsystem covered:

QuestionMeaning
What does it do?The observable runtime behaviour, in the order it occurs.
Who owns it?Whether the framework, your code, or the PHP runtime is the source of truth.
How does it fail?The failure mode you must design against, and the limit of the framework’s protection.

Version pinning. Every code sample targets PHP 8.3 and Leaf PHP 3.x. Leaf 3.x requires PHP 8.1 or later as a Composer platform constraint; 8.3 is the version this guide assumes for available features such as typed class constants, readonly amendments, and #[\Override]. Where Leaf changed an API between 2.x and 3.x, the 3.x form is shown and the difference is noted.

0.2 What Leaf is, and what it is not

Leaf is a routing and middleware layer with thin conventions for controllers, views, and models. Knowing where it ends is as important as knowing where it begins.

Leaf provides the following, in the order a request encounters them:

// The complete application surface. A Leaf app is four collaborators.
$app = new Leaf\App();

$app->get('/orders/{id}', 'OrderController@show');

// 1. Router        — matches method + path, resolves a handler
// 2. Middleware     — runs before, around, and after the handler
// 3. Controller     — a plain object with methods; no base class needed
// 4. View renderer  — PHP templates rendered into a string

There is no ORM, no dependency injection container, no event bus, no queue, and no form or validation DSL comparable to Laravel. Those concerns belong to the libraries you choose. Leaf’s job is to get a request to a callable and to give you a well-defined interception point on the way in and the way out.

Not a Laravel substitute. Leaf’s controller conventions are far lighter. There is no AppServiceProvider, no facades, no config() global, no Eloquent, and no Blade. If you reach for a Laravel mental model you will write code that does not run. Use Laravel if you want that feature set already integrated and maintained; use Leaf if you want a routing core and nothing else.

What Leaf does give you, and gives you well:

Test the contract, not the implementation. Because Leaf does not own your ORM, your session store, or your auth rules, it cannot protect you from them either. The most common Leaf application defects are not framework defects: they are unprepared statements, unescaped output, and missing authorisation checks that the framework never promised to make.

0.4 Reading conventions

The conventions used in code samples, and the explicit limits of the accuracy of the API references.

Code samples use these conventions throughout:

// Framework surface, abbreviated with __DIR__-relative root
require __DIR__ . '/vendor/autoload.php';

$app = new Leaf\App();

// A route may resolve to 'Controller@method' or to a closure
$app->get('/health', fn() => response()->json(['ok' => true]));

// Grouped routes share a prefix and middleware stack
$app->group('/api/v1', function () {
    $this->get('/orders', 'OrderController@index');
});
  • Real APIs are shown as-is. Where a signature is uncertain for your exact patch release, the sample carries a comment rather than a plausible invention.
  • Ellipses are explicit. // ... marks omission. Nothing is implied that is not written.
  • Ellipsis in paths such as app/{*path} is Leaf’s own syntax, not an omission.
  • Assumed helper availability. request() and response() are the global accessors Leaf registers. Prefer injecting the objects; the globals are shown where a template or a closure makes injection awkward.

Check the installed signature. Leaf’s surface is small but it has moved between minor versions. Before you rely on any method name in this guide, confirm it against the source in vendor/leaf/leaf/ for the version Composer resolved, and prefer the call signature you find there over the one shown here.

1 · The MVC Pattern: Ownership and Failure Modes

1.1 What each layer owns1.2 The request lifecycle1.3 Failure mode: the fat controller1.4 Failure mode: the anemic model1.5 Failure mode: logic in views

Defines the contract of each layer in a Leaf application, then examines the three boundary failures that account for most maintainability problems in MVC codebases.

1.1 What each layer owns

A layer’s responsibility is best expressed as a single question it is allowed to answer, and a set it is not.

MVC is frequently taught as a directory layout. That description is useful for beginners and misleading for everyone else. A useful definition is a set of exclusive questions:

LayerThe one question it answersIt must not answer
RouterWhich callable handles this method and path?Anything about the callable’s internals
MiddlewareMay this request proceed, and with what context attached?What the handler will do with that context
ControllerWhat is the response to this request, given these inputs?How the response is rendered to bytes, or how data is stored
Model / serviceWhat is true about the domain, and what changed?Anything about HTTP
ViewHow is this data presented for this user?Anything about the database or the request’s validity

The exclusion column is the part that matters. MVC degrades not because developers misunderstand the pattern, but because each exclusion is a small convenience that is refused in isolation and accepted as a habit.

In a Leaf application the mapping to these questions is direct, and largely unenforced:

// The router resolves a string handler or a closure. It inspects neither.
$app->get('/orders/{id}', 'OrderController@show');

// The controller is an ordinary class. No base class, no interface required.
class OrderController
{
    public function __construct(private OrderRepository $orders) {}

    public function show(int $id): Response
    {
        // Question answered here: what is the response, given this id?
        $order = $this->orders->find($id);

        return response()->json($order);
    }
}

Nothing is a singleton by default. Leaf resolves the controller class and passes its method arguments through PHP’s ordinary argument resolution. A constructor-promoted dependency is therefore available for injection, but nothing is registered in a container for you. If you need shared instances, own that explicitly rather than assuming the framework caches them.

1.2 The request lifecycle

The exact sequence of frames between the first PHP line executed and the last byte written, which determines where each concern belongs.

A Leaf application’s request passes through a fixed sequence. Knowing the sequence is what lets you place a concern in the correct layer instead of the nearest convenient one.

OrderStageLeaf surfaceFailures surface as
1PHP boots, autoloader runsComposerFatal error, blank page
2App constructednew Leaf\App()Fatal error
3Error handler registered$app->setErrorHandler()Unhandled fatal, stack trace leak
4Global middleware resolved$app->use()500 on every route, including health checks
5Request object built from superglobalsrequest()Empty body, wrong content type
6Router matches method and pathget, post, match404 or 405
7Route middleware, outermost firstuse(middleware: [...])401, 403, 419, redirect
8Handler arguments bound and resolvedPHP reflectionTypeError, 500
9Controller or closure executesYour codeException, wrong status code
10Response normalisedResponseEmpty 200, double-sent headers
11After / around middleware unwindPipelineLate exception, corrupted body
12View rendered, if a view was returnedview()Parse error inside template
13Body written, headers flushedPHP SAPITruncated response

Use the lifecycle to place concerns. Authentication belongs at stage 7 because it must be able to reject the request before the handler runs. Auditing belongs at stage 11 because it needs the final status code. Input validation belongs at stage 9, in the controller, because only the controller knows which fields the action requires. Rendering belongs at stage 12, after every decision has been made.

1.3 Failure mode: the fat controller

The most common MVC defect is a controller that absorbs business rules, persistence, and presentation decisions because no other layer was given permission to hold them.

The fat controller is not primarily a size problem. A 400-line controller whose responsibilities are correctly separated is not the disease. The disease is a method that answers four different questions.

// A handler answering four questions at once.
public function store(Request $request): Response
{
    $data = $request->body();                       // transport concern

    if ($data['quantity'] * $data['unit_price'] > $user->credit_limit) {
        return back()->withErrors(...);              // domain rule + presentation
    }

    $stmt = $this->pdo->prepare('INSERT INTO orders ...');  // persistence
    $stmt->execute([...]);

    Mail::to($user)->send(...);                     // side effect with no owner

    $html = view('orders/created', [...])->render();  // presentation

    return response()->html($html);
}

Three separate defects are present, and it is worth separating them because they are usually confused:

  • Untestable domain logic. The credit limit rule cannot be tested without constructing a request, a PDO connection, and a mail transport. It is a one-line rule that costs a full integration fixture.
  • Undeclared transaction boundary. The insert and the mail send are separate operations with no defined ordering guarantee. A failure after the insert leaves a committed order with no notification, and nothing records that fact.
  • Mixing return shapes. A redirect on validation failure, HTML on success, and an implicit 200 on an exception give a client three different contracts for one action.

The correction is not "add a service layer" mechanically. A service that merely moves the four questions into one class reproduces the problem one level down. Move the domain rule into a value object or a domain service, the persistence into a repository with an explicit interface, and the notification behind an interface the domain depends on. The controller then becomes the composition point — which is the one thing a controller is genuinely good at.

The corrected shape, with ownership visible:

// Owns: a single rule about credit exposure. No HTTP, no persistence.
final readonly class CreditPolicy
{
    public function __construct(private CreditTerms $terms) {}

    public function assertWithinLimit(Account $a, int $cents): void
    {
        if ($a->exposure()->plus($cents)->exceeds($this->terms->limit)) {
            throw new CreditExceeded($a->id(), $cents);
        }
    }
}

// Owns: the order aggregate and its invariant. Depends on an interface.
final class PlaceOrder
{
    public function __construct(
        private OrderRepository $orders,
        private CreditPolicy $credit,
        private Notifier $notifier,     // interface, not a mailer
        private Transaction $tx,
    ) {}

    public function handle(Account $a, DraftOrder $d): Order
    {
        return $this->tx->run(function () use ($a, $d) {
            $this->credit->assertWithinLimit($a, $d->total()->cents());

            $order = $this->orders->save(Order::place($a, $d));

            $this->notifier->orderPlaced($a, $order);

            return $order;
        });
    }
}

Why the transaction encloses the notification. If the notification must not be lost, it belongs inside the transaction with an outbox row. If it may be lost and will be retried, it belongs outside, dispatched after commit. The important part is that the choice is written down in one place instead of emerging from the order two statements happened to appear in.

1.4 Failure mode: the anemic model

The mirror-image failure: a model that holds only properties and getters, pushing every invariant into the controller that reads and writes it.

Overcorrecting from the fat controller produces a different problem. A model with public setters and no behaviour is a data transfer object wearing a database name, and it has moved the invariant problem rather than solved it.

// Anemic: every rule now lives in whatever code happens to hold the object.
class Order
{
    public string $status;
    public int $total_cents;
    public function setStatus(string $s): void { $this->status = $s; }
}

// Callers can now put an order in any state at all.
$order->setStatus('shipped');   // was it paid? cancelled? shipped twice?

There are two valid remedies, and picking the wrong one is its own failure.

RemedyShapeCorrect when
Rich domain modelState transitions are methods; invalid transitions throwThe rules are genuinely about the entity and will be enforced from many call sites
Explicit data + servicePlain readonly DTOs; one application service owns all transitionsThe model is a projection of a table and the rules live across entities

Avoid the middle position. A model with a getter for one field and a setter for another is worse than either extreme, because a reader cannot tell which fields are invariant and which are free. If you are unsure, choose the service and make every transition pass through it.

The rich version makes the illegal state unrepresentable:

// The status is the discriminator; transitions are exhaustive match arms.
enum OrderStatus: string
{
    case Pending    = 'pending';
    case Paid       = 'paid';
    case Shipped    = 'shipped';
    case Cancelled  = 'cancelled';

    public function mayTransitionTo(self $to): bool
    {
        return match ($this) {
            self::Pending   => in_array($to, [self::Paid, self::Cancelled], true),
            self::Paid      => in_array($to, [self::Shipped, self::Cancelled], true),
            self::Shipped   => false,
            self::Cancelled => false,
        };
    }
}

final readonly class Order
{
    public function __construct(
        public string $id,
        public OrderStatus $status,
        public int $total_cents,
    ) {}

    public function markPaid(): self
    {
        if (!$this->status->mayTransitionTo(OrderStatus::Paid)) {
            throw new IllegalTransition($this->id, $this->status, OrderStatus::Paid);
        }

        return new self($this->id, OrderStatus::Paid, $this->total_cents);
    }
}

Note the immutability. readonly plus a method that returns a new instance means a transition cannot be silently discarded. If a caller writes $order->markPaid(); without using the return value, the transition is a no-op and no state changed. That is a real cost, and it is the reason some codebases use a mutable model with assertCanTransitionTo() plus a private setter instead. Both are defensible; mixing them in one codebase is not.

1.5 Failure mode: logic in views

Templates are PHP files, so anything can be written in them. The reason to keep queries out is not purity — it is that templates run at the one moment you can least afford an extra round trip.

Because Leaf templates are plain PHP, there is no compiler to stop a query in a view. This is convenient and dangerous in a specific way: the failure is invisible in review and expensive in production.

// A view that fetches per row. Correct output, quadratic queries.
<?php foreach ($orders as $order): ?>
    <tr>
        <td><?= $this->escape($order->customer_name) ?></td>
        <td>
            <?php foreach (Customer::find($order->customer_id)->orders as $o): ?>
                <?= $o->label() ?>
            <?php endforeach; ?>
        </td>
    </tr>
<?php endforeach; ?>

Chapter 17 covers the mechanics of detecting this. The architectural point is narrower: a view’s only permitted dependency is the data it was given, and the controller or a service is responsible for ensuring that data is complete enough to render without further retrieval.

A useful test. If a view would need to include another view that performs a query, the data is being assembled in the wrong place. A view is a function from already-fetched data to markup; anything that reaches back to the database is a hidden network call inside a rendering function, and it will not appear in your query log if you are not counting them.

The separation of concerns, stated as a checklist you can apply in review:

ConcernBelongs inSymptom when misplaced
Method and path matchingRouterConditional routing inside a handler
Auth, CSRF, rate limitingMiddlewareA guard duplicated in twenty controllers
Input shape and field listController + validatorHand-rolled isset() chains
Business rules and invariantsModel / domain serviceRules that cannot be tested without HTTP
Persistence and queriesRepository over PDOSQL strings appearing outside one directory
External side effectsService behind an interfaceMail or HTTP calls inside a controller
Markup and escapingViewConcatenated HTML in a controller
Status codes and headersResponse objectheader() calls in a template

A note on the "where does it go" question for Leaf specifically. Because Leaf supplies no service container, the composition root is your own bootstrap/app.php. That file is where you decide what a controller receives. Keeping it short and declarative — wiring objects, binding interfaces to implementations, nothing else — is the mechanism by which the ownership table above is actually enforced rather than merely intended.

2.2 The bootstrap file and the application root

The composition root: the single place where every object the application uses is constructed, in one file, with no business logic.

Leaf has no service container, so the composition root is a plain PHP file you write. Its discipline matters more than its content: it should read as a list of objects, and it should be the only file that knows which implementation satisfies which interface.

# public/index.php — the sole entry point for every request.
<?php

declare(strict_types=1);

// 1. Fail loudly on config problems before anything else is attempted.
$app = require __DIR__ . '/../bootstrap/app.php';

// 2. Let the framework send. Do not add echo or var_dump below this line.
$app->run();

The bootstrap file, which is where an entire Leaf application is actually assembled:

# bootstrap/app.php
<?php

declare(strict_types=1);

use Leaf\App;
use Leaf\Router;

require __DIR__ . '/../vendor/autoload.php';

$config = require __DIR__ . '/../config/config.php';

// Database. One connection, created eagerly so a misconfiguration fails now,
// not on the first customer request at 3am.
$pdo = new PDO(
    dsn:      $config['db']['dsn'],
    username: $config['db']['user'],
    password: $config['db']['password'],
    options: [
        PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        PDO::ATTR_EMULATE_PREPARES   => false,
    ],
);

// Leaf configuration. Keys vary by patch release; check yours.
App::configure($config['leaf']);

$app = new App($router ?? new Router());

// Global middleware: order here is the order they wrap every route.
$app->use([
    Leaf\Middlewares\ErrorHandlerMiddleware::class,
    Leaf\Middlewares\SessionMiddleware::class,
]);

// Route files register themselves against $app. Nothing else happens here.
(require __DIR__ . '/../routes/web.php')($app);
(require __DIR__ . '/../routes/api.php')($app);

return $app;

Return the app, do not run it. Having the bootstrap file return $app means a test, a CLI command, or a second mounted app can require it and inspect the route table without sending output. This is also the hook your test harness in chapter 16 uses.

2.5 Configuration without a framework config layer

There is no config() global in Leaf. Configuration is an array returned by a file, read once, and passed explicitly.

Since Leaf supplies no configuration layer, the design decision is entirely yours. The recommendation is an array, returned from one file, read once at boot, and passed to the components that need it.

# config/config.php
<?php

declare(strict_types=1);

// Read once. A dotenv package is fine; the point is that this file
// is the single place that knows where values come from.
$env = static function (string $key, mixed $default = null): mixed {
    $value = $_ENV[$key] ?? getenv($key);

    if ($value === false || $value === '') {
        if ($default === null) {
            throw new RuntimeException("Missing required env: {$key}");
        }

        return $default;
    }

    return match (strtolower((string) $value)) {
        'true', '1', 'yes', 'on'   => true,
        'false', '0', 'no', 'off'  => false,
        default => $value,
    };
};

return [
    'env'      => $env('APP_ENV', 'local'),
    'debug'     => $env('APP_DEBUG', false),
    'url'       => $env('APP_URL', 'http://localhost'),
    'key'       => $env('APP_KEY'),          // no default: fail at boot
    'db'        => [
        'dsn'      => $env('DB_DSN'),          // no default: fail at boot
        'user'     => $env('DB_USER'),
        'password' => $env('DB_PASSWORD', ''),
    ],
    'session'   => [
        'name'     => 'orders_session',
        'lifetime' => 7200,
        'secure'   => $env('SESSION_SECURE', true),
    ],
    'leaf'      => [
        // Keys are patch-version specific — check the installed source.
        'view'      => __DIR__ . '/../resources/views',
        'templates.cache' => $env('APP_ENV') === 'production',
    ],
];

Fail at boot, not at 3am. A configuration key with no default and no environment variable should throw during the bootstrap file, where the error page is still generic and the cause is unambiguous. Reading it lazily inside a controller turns a deployment mistake into a bug report with no stack trace pointing at the cause.

Two things to avoid. Do not read $_ENV or getenv() from anywhere except the config file — the indirection costs nothing and pays for itself the first time a test needs to vary a value. And do not store mutable state in the config array: a config array that is written to after boot is a global variable with extra steps and a misleading name.

3.1 Registering routes

The verb-specific registration methods, the catch-all matcher, and the handler forms each accepts.

Routes are registered on the App instance before run() is called. Leaf exposes one method per HTTP verb and a general match() for any method.

$app = new Leaf\App();

$app->get('/orders',             'OrderController@index');
$app->post('/orders',            'OrderController@store');
$app->put('/orders/{id}',       'OrderController@update');
$app->patch('/orders/{id}',     'OrderController@patch');
$app->delete('/orders/{id}',    'OrderController@destroy');

// Any verb, including WebDAV methods.
$app->match('GET|POST', '/orders/search', 'OrderController@search');

// A closure or invokable, if the action is trivial.
$app->get('/health', fn() => response()->json(['ok' => true]));
MethodAcceptsNotes
get post put patch delete optionsPath, handler, optional route name and middlewarePrimary surface; options is often handled for you at dispatch

A route may carry a name, which is how you generate URLs without hard-coding paths:

$app->get('/orders/{id}', 'OrderController@show')->name('orders.show');

// Later, from a controller or a template:
$url = route('orders.show', ['id' => $order->id]);
$path = path_to('orders.show', ['id' => $order->id]);

Name collisions throw. Registering the same route name twice is a hard error, not an override. This is deliberate: a duplicate name almost always means two route files disagreeing about a URL. Read the name as an assertion you are making about the public interface, not a label.

3.2 Route parameters and constraints

How path segments become typed handler arguments, and why a constraint is a correctness control rather than an optimisation.

A segment wrapped in braces is a parameter. Its value is available in the request and, when the handler declares a matching argument, is bound by position and type.

// /orders/42/edit
$app->get('/orders/{id}/edit', 'OrderController@edit');

class OrderController
{
    // Leaf binds {id} to the first matching argument and coerces to int,
    // so a non-numeric id raises a TypeError rather than reaching SQL.
    public function edit(int $id, Request $request): Response
    {
        return response()->json(['id' => $id]);
    }
}

Constraints narrow what a segment may contain, using the same syntax as a regex. They are checked at match time, so a non-conforming path becomes a 404 rather than a downstream error:

// Only digits, and only a realistic length.
$app->get('/orders/{id:[0-9]+}',  'OrderController@show');
$app->get('/orders/{id:[0-9]{1,19}}', 'OrderController@show');

// Named capture groups propagate into request params.
$app->get('/files/{name:[a-z0-9_-]+\.(?:txt|md)}', 'FileController@show');

Constrain everything. A route like /users/{id} matches /users/-adjacent paths such as /users/../etc only after URL normalisation, but it also matches /users/create if a static route for that path was registered later. Putting a constraint on every parameter is the cheapest way to make the route table self-documenting, and it removes an entire class of shadowing bug. Where an identifier is a UUID, constrain it to the UUID shape rather than accepting any non-slash string.

Reading parameters explicitly, when binding is not what you want:

$request->params['id'];        // All path parameters as an array
$request->param('id');        // Single value by name
$request->params();               // Same data, callable form

// A wildcard stores the remainder under a key of your choosing.
$app->get('/docs/{*path}', 'DocController@show');
$request->param('path');   // 'guides/routing/middleware'

Never interpolate a parameter into a query string or a header. Path parameters are the least trustworthy input in the application: they arrive in a location users can edit freely, they are frequently logged verbatim, and they often bypass the validation you applied to the body. Bind them as prepared statement parameters in chapter 7 and constrain them here, but do not treat a constraint as sanitisation — a constraint limits a character set, it does not make a value safe for a different context.

3.3 Wildcards, optional segments, and fallbacks

The three mechanisms for variable-depth paths, and the ordering rule that decides which of several candidate routes matches.

Leaf supports three forms of variable-depth path, each with distinct semantics.

FormMatchesGreedyTypical use
{param}Exactly one segment, no slashn/aIdentifiers, slugs
{param?}One segment, or nothing at alln/aOptional filters, optional trailing id
{*param}One or more segments, slashes includedYesFile trees, catch-all, 404 handler

$app->get('/orders[/{status}]', 'OrderController@index');

// Wildcard: /assets/img/icons/check.svg
$app->get('/assets/{*path}', 'AssetController@serve');

// A named catch-all as the application's final route.
$app->get('/{*rest}', 'ErrorController@notFound');

Ordering is not a detail in Leaf. Unlike a trie-first router, Leaf’s dispatch is influenced by the order routes were registered, and a greedy wildcard will happily swallow paths that a later, more specific route was meant to handle. Register static and constrained routes before wildcards, and register the catch-all last, unconditionally. If a specific route appears to be ignored, look for a wildcard registered above it.

A dispatch-safe ordering for a typical application:

1Infrastructure that must never be shadowed/health, /metrics
2Fully static paths/orders/new, /orders/search
3Constrained parameters/orders/{id:[0-9]+}
4Optional segments/orders[/{status:[a-z]+}]
5Asset and file trees/assets/{*path}
6Catch-all 404/{*rest}

The 404 route is worth styling carefully, because in a Leaf application the router — not PHP’s built-in server or Apache — is what produces the not-found response:

# Do this once, after every other route is registered.
$app->get('/{*rest}', 'ErrorController@notFound');

class ErrorController
{
    public function notFound(Request $request): Response
    {
        // Distinguish a JSON client from a browser so the two get
        // representations, not different status codes.
        if ($request->wantsJson()) {
            return response()->json([
                'error'   => 'not_found',
                'path'    => $request->url(),
            ], status: 404);
        }

        return response()->html(view('errors/404', [
            'path' => $request->url(),
        ]), status: 404);
    }
}

Add a method-not-found handler too. A 405 is more informative than a 404 for a client, and it lets you emit the Allow header required by RFC 9110. Whether you do this through a dedicated route list or inside the catch-all depends on whether your Leaf patch release exposes the matched-but-wrong-method state — check the router source, and if it is not exposed, derive the allowed set from your own route declarations.

3.4 Route groups and prefixes

Grouping routes by shared prefix, middleware, and namespace, and the scoping rule inside the group callback.

A group applies a prefix and a set of defaults to every route registered inside its callback. Inside that callback, $this is the group instance, which is why $this->get() rather than $app->get() is used.

$app->group('/api/v1', function () {
    // Registers GET /api/v1/orders
    $this->get('/orders', 'Api\V1\OrderController@index');

    $this->group('/admin', function () {
        // Registers POST /api/v1/admin/orders — prefixes compose
        $this->post('/orders', 'Api\V1\AdminOrderController@store')
             ->name('api.admin.orders.store');
    });
});

Grouping by middleware rather than by URL is the more valuable form, because it lets one group carry a whole policy:

# routes/api.php
<?php

declare(strict_types=1);

return function (Leaf\App $app): void {
    $app->group('/api/v1', function () {

        // Public surface. Token auth, no cookies, JSON only.
        $this->group('', function () {
            $this->get('/health', 'Api\V1\HealthController@show')->name('api.health');
        })->middleware([Leaf\Middlewares\ApiMiddleware::class]);

        // Authenticated surface. Two middlewares, in this order:
        // authenticate() runs first and rejects; throttle() only sees
        // requests that reached it, so the rate limit counts real users.
        $this->group('', function () {
            $this->get('/orders',         'Api\V1\OrderController@index')->name('api.orders.index');
            $this->get('/orders/{id:[0-9]+}', 'Api\V1\OrderController@show')->name('api.orders.show');
        })->middleware([
            Leaf\Middlewares\ApiMiddleware::class,
            App\Middleware\AuthenticateToken::class,
            App\Middleware\ThrottleRequests::class,
        ]);
    });
};

Prefer file-scoped groups over deeply nested ones. Three levels of nesting is readable; six is not, and the failure is a route that lands under the wrong prefix because of a misplaced closing brace. A flat file with two groups — public and authenticated — matches how authorisation actually works and is far easier to audit.

Group prefixes compose, but names do not merge implicitly — always give each route an explicit name when it is referenced from a template, and keep names hierarchical so the full set reads as the public API:

PrefixGroupRoute namePath
/api/v1publicapi.health/api/v1/health

/api/v1authapi.orders.show/api/v1/orders/{id}

3.5 Per-route middleware and resolution order

Attaching middleware to a single route or a group, and the exact order in which layers execute when the three sources of middleware combine.

Middleware can be attached globally with $app->use(), to a group with ->middleware(), and to an individual route. The execution order across all three is fixed and must be understood precisely, because most middleware bugs are ordering bugs.

# Global — wraps everything, including routes that reject early.
$app->use([ErrorHandlerMiddleware::class, SessionMiddleware::class]);

# Group — wraps the group's routes only.
$app->group('/admin', function () { ... })
    ->middleware([Authenticate::class, AuthoriseAdmin::class]);

# Single route — innermost, closest to the handler.
$app->get('/orders/{id:[0-9]+}', 'OrderController@show')
    ->middleware(VerifyCsrfToken::class);

Given the three registrations above, a request to /admin/orders/1 with a GET executes in this order:

StepLayerEffect if it rejects
1ErrorHandler (global, first)Would need to run first, or failures are unhandled
2Session (global)No session available to later middleware or the view
3Authenticate (group)401 or redirect to login
4AuthoriseAdmin (group)403
5VerifyCsrfToken (route, GET excluded)419
6HandlerException bubbles to step 1
7VerifyCsrfToken after-phaseToo late to matter for a GET
8AuthoriseAdmin after-phase—
9Authenticate after-phase—
10Session after-phase (writes cookie)—
11ErrorHandler after-phaseLast chance to alter the response

Middleware composes like nested function calls. The first registered layer is the outermost. Each layer’s "before" code runs top to bottom and its "after" code runs bottom to top, so the last-registered middleware sees the final response. This is why the error handler must be first globally — it is the only layer positioned to catch an exception thrown by any layer below it, including the handler.

Short-circuiting stops the unwind, not just the descent. If middleware B rejects a request, middleware A registered before it has already run its before-phase but will not receive a normal after-phase unless the framework guarantees unwinding on early return. Verify this in your Leaf patch release with a test that registers two middleware, has the second one return a response early, and asserts what the first one observed. If the first one’s after-phase is skipped, any cleanup it performs — audit logging, response timing headers — is silently omitted for exactly the requests you most want recorded.

Registering middleware as an array versus a single class is not a style question. An array is the correct form whenever more than one layer applies, because it makes the ordering explicit at the call site rather than relying on an alias to resolve to an ordered list:

# Implicit and easy to get wrong when the alias grows.
$app->get('/orders', 'OrderController@index')->middleware('auth');

# Explicit: the order you read is the order that runs.
$app->get('/orders', 'OrderController@index')
    ->middleware([Authenticate::class, AuthoriseAdmin::class, ThrottleRequests::class]);

4 · Controllers: Conventions, Dependencies, the Handler Contract

Defines the handler contract Leaf expects from a controller method, the four ways to supply dependencies when no container is available, and the correct placement of authorisation checks.

4.1 Controller anatomy and the response contract

A controller is a plain class. What matters is not its base class or shape but the single guarantee its methods must make about their return value.

Leaf imposes no base class, no interface, and no lifecycle hook on controllers. A controller is any class with a public method matching a registered route name. This is a genuine advantage for testing, because a controller can be constructed directly in a unit test with hand-written fakes.

<?php

declare(strict_types=1);

namespace App\Controllers;

use App\Domain\Order;
use App\Services\PlaceOrder;
use Leaf\Http\Request;
use Leaf\Http\Response;

final class OrderController
{
    // Constructor promotion: one line, explicit, and no container needed.
    public function __construct(private PlaceOrder $placeOrder) {}

    // Returns a Response. Always. Every exit path, including the guards.
    public function store(Request $request): Response
    {
        $draft = DraftOrder::fromArray($request->body());

        $order = ($this->placeOrder)($draft);

        return response()->json(OrderResource::from($order), status: 201);
    }
}

The contract has exactly one requirement: every path returns a Response. A method that falls off the end without returning something is the single most common source of confusing behaviour in a Leaf application, because the framework may substitute a default and you will spend an hour looking in the wrong file.

ReturnMeaningUse for
ResponseAn explicit, fully specified responseEverything except the two helpers below
View from view()Render a template; Leaf builds the 200 responseHTML pages with a layout
array or scalarConvenience: JSON-encoded with a 200Small JSON endpoints only

Do not mix the convenience returns with explicit ones. If half your methods return arrays and half return Response objects, the status code policy is no longer visible in any one place and a reviewer cannot tell whether a 200 was chosen or inherited. Pick one style per project; the recommendation is explicit Response for everything that serves an API, and view() for everything that serves a browser.

Setting the status code, headers, and body explicitly, without reaching for global functions:

$response = response()->json(
    data:   $payload,
    status: 201,
);

$response->header('X-Request-Id', $requestId);
$response->header('Location', route('orders.show', ['id' => $order->id]));

return $response;

One resource, one serialiser. If the same entity appears in six responses, the shape of those responses will drift. Extract a small resource class that converts a domain object to an array, and use it everywhere. It costs one file and it turns a data-leak bug — exposing a password hash because someone serialised the model directly — from a plausible incident into an impossible one.

4.2 Dependency injection without a container

Four approaches to supplying constructor dependencies, ordered by how much machinery each requires, and the trade-off each carries.

Leaf has no container, so nothing resolves a controller’s constructor for you. You choose a strategy. There are four that work, and the right one depends on how much your application has grown.

// Strategy 1 — hand-construct at the route. Explicit, no registry, works at any size.
$app->post('/orders', [new OrderController(new PlaceOrder(
    orders:   new PdoOrderRepository($pdo),
    credit:   new CreditPolicy(CreditTerms::standard()),
    notifier: new MailNotifier($mailer),
    tx:       new PdoTransaction($pdo),
)), 'store']);

Strategy 1 is verbose, and the verbosity is the point: every dependency of every handler is visible on the route line. The cost is that a controller with eight dependencies produces an unreadable registration, and the wiring is repeated in tests.

// Strategy 2 — a composition helper of your own. One file, still no framework.
final class Wiring
{
    /** @var array<string, callable> */
    private array $factories = [];

    public function share(string $id, callable $factory): void
    {
        $this->factories[$id] = $factory;
    }

    public function make(string $class): object
    {
        return new $class(...$this->argsFor($class));
    }

    private function argsFor(string $class): array
    {
        // Reflection over the constructor, resolved lazily, cached per request.
        return array_map(
            fn(ReflectionParameter $p) => $this->resolve($p->getType()->getName()),
            (new ReflectionClass($class))->getConstructor()->getParameters() ?? [],
        );
    }

    private function resolve(string $id): mixed
    {
        return $this->instances[$id] ??= ($this->factories[$id])();
    }
}

Strategy 2 is a container, and that is fine. The argument against writing one is not that containers are bad — it is that a poorly built one hides the wiring and couples your domain to a resolver. A 40-line reflection-based helper that only knows factories you registered yourself is a reasonable tool. A general-purpose container injected into the domain is not. If you find yourself adding features to the resolver, that is the signal to stop.

// Strategy 3 — constructor arguments Leaf itself provides.
public function show(Request $request, Response $response): Response

// Strategy 4 — resolve collaborators inside the controller from
// explicit, narrow factories. Use sparingly; see the warning below.
final class OrderController
{
    public function __construct(private OrderRepository $orders) {}

    public function show(int $id): Response
    {
        $order = $this->orders->find($id);
        ...
    }
}

Never use a service locator inside a domain object. Calling app()->make(OrderRepository::class) from inside a domain class makes that class impossible to unit test, because constructing it now requires a booted application. Service location is acceptable in exactly two places: a controller, where the request has already committed to a real environment, and a factory. It is never acceptable in a value object, a policy, or a domain service.

Choosing between the strategies:

StrategyWiring verbosityTestabilityChoose it when
1 · Hand-construct at routeHighBestFew controllers, or you value the explicit route table
2 · Your own wiring helperLowGoodMore than about ten controllers
3 · Framework-provided argsNoneGoodAlways, in addition to the above
4 · Service locatorNonePoorOnly inside controllers and factories

4.3 Handler method resolution and argument binding

How Leaf maps a route’s handler to a method, and the three argument sources it will bind, in priority order.

When a route matches, Leaf locates the handler and calls it. The method is chosen in one of three ways:

Route formMethod selectedNote
'Class@method'The named methodExplicit; the recommended form
'Class' (no @)indexConvenience for a single-action controller; confirm for your patch release
Class implementing __invoke__invokeRoute the class itself

Arguments are bound from three sources, and the fact that all three are attempted in sequence is a frequent source of confusing bugs:

PrioritySourceExample
1Route parameters, by declared type and nameint $id ← {id:[0-9]+}
2Framework objects, by typeRequest, Response
3Default valuesint $page = 1
// GET /orders/42?page=2
public function show(int $id, Request $request, int $page = 1): Response
{
    // $id   ← 42   from the path
    // $request ← the request object, matched by type
    // $page ← 1, its default, because query strings are not
    //        auto-bound. Read them from $request->query().
}

Query and body parameters are never auto-bound. Leaf binds path parameters and framework objects. If your handler expects $page and a client sends ?page=2, you get the default unless you read $request->query('page'). This is a deliberate safety property, not an oversight: silently populating a method’s arguments from arbitrary user input removes any chance of the developer noticing the dependency. Read inputs explicitly, validate them explicitly, and pass the validated value as a separate typed argument.

The pattern this produces, which makes the controller read as a statement of dependencies:

public function index(Request $request, Response $response): Response
{
    $filters = OrderFilters::fromQuery($request->query());   // typed, validated, explicit
    $page    = $filters->page;

    $result  = $this->listOrders->handle($filters, $page);

    return response()->json([
        'data'  => array_map(OrderResource::class . '::from', $result->orders),
        'meta'  => ['page' => $page, 'total' => $result->total],
    ]);
}

When a controller grows past a dozen actions, the more effective response is not to compress the wiring but to split the class. A OrderController that reads, a OrderReportController that exports, and an OrderDraftController that handles unsubmitted carts each have three or four methods, three or four dependencies, and one reason to change.

4.4 One controller per action versus resource controllers

Two organising strategies for controllers, the failure mode of each, and the decision rule that separates them.

There are two defensible ways to organise controllers, and mixing them in one application is the actual mistake.

StrategyShapeStrengthFailure mode
Resource controllerOne class per aggregate, one method per verbMirrors the domain; the route table reads as the APIBecomes a grab bag when unrelated concerns attach to the same aggregate
Single-action controllerOne class per use case, one __invokeEvery class is small and independently testable; dependencies are minimalRoute table becomes a long list of class names with no structure
// Resource style
$app->get('/orders',         'OrderController@index')->name('orders.index');
$app->get('/orders/{id:[0-9]+}', 'OrderController@show')->name('orders.show');
$app->post('/orders',        'OrderController@store')->name('orders.store');
$app->patch('/orders/{id:[0-9]+}', 'OrderController@update')->name('orders.update');
$app->delete('/orders/{id:[0-9]+}', 'OrderController@destroy')->name('orders.destroy');

// Single-action style, named for the use case
$app->post('/orders',         PlaceOrderAction::class)->name('orders.place');
$app->patch('/orders/{id:[0-9]+}', CancelOrderAction::class)->name('orders.cancel');
$app->post('/orders/{id:[0-9]+}/reship', ReshipOrderAction::class)->name('orders.reship');

The decision rule: if a group of actions shares a noun and nothing else, use a resource controller. If two actions in that group need different authorisation, different validation, or different dependencies, they are different use cases and belong in different classes, even though they share the noun.

// A resource controller that has crossed the line. Note the two different
// dependency sets and the inline authorisation in the last method.
final class OrderController
{
    public function __construct(
        private ListOrders $list,
        private PlaceOrder $place,
        private ExportOrders $export,     // unrelated concern
        private RefundPayment $refund,     // different subsystem
    ) {}

    public function index(Request $r): Response { ... }
    public function store(Request $r): Response { ... }
    public function export(Request $r): Response { ... }   // move to ReportController
    public function refund(Request $r): Response { ... }    // move to RefundController
}

A single-action controller is usually a service in disguise. If PlaceOrderAction contains no HTTP concerns at all — no request parsing, no status codes, no headers — then it is a domain service and it belongs in app/Services/, with a thin controller in front of it. Keeping the two distinct is what allows the service to be tested without the framework, which is the whole point of the arrangement.

4.5 Where authorisation checks belong in a controller

Two distinct checks — authentication and resource-level authorisation — and the reason conflating them produces a vulnerability.

Two different questions are routinely collapsed into one. Keeping them separate is a security requirement, not a tidiness preference.

QuestionNameAnswered byFailure status
Who is this?AuthenticationMiddleware, before the controller401, or a redirect to login for a browser
May they do this to this resource?AuthorisationThe controller, because only it knows which resource403

Middleware can establish who the user is. It cannot establish whether that user may modify this particular order, because the order’s id is only known after routing, and in some designs the ownership rule needs data the middleware has no reason to fetch. That check belongs in the controller, immediately before the action:

public function update(Request $request, int $id): Response
{
    $order = $this->orders->findOrFail($id);       // 404 if absent

    // Authorisation: explicit, adjacent to the action, impossible to
    // miss when the method is read. Ownership is a domain rule,
    // so it is asked of the aggregate, not reimplemented here.
    $this->policy->assertMayEdit($request->user(), $order);

    $order = ($this->updateOrder)($order, OrderEdits::fromArray($request->body()));

    return response()->json(OrderResource::from($order));
}

Do not infer ownership from a hidden field. A form that carries <input name="account_id"> and a controller that trusts it will let any authenticated user submit another account’s id. Ownership is read from the loaded record, never from client input. The same applies to role: a role field in a submitted form is an attack, not a request.

The policy is a domain object with no HTTP knowledge, which makes it directly testable and makes the rule visible in one place:

final readonly class OrderPolicy
{
    public function __construct(private bool $allowStaffOverride) {}

    public function assertMayEdit(User $actor, Order $order): void
    {
        if ($actor->isStaff() && $this->allowStaffOverride) {
            return;
        }

        if (!$actor->id()->equals($order->accountId())) {
            throw new AuthorizationException('orders.edit', $actor->id(), $order->id());
        }
    }
}

Chapter 13 builds the middleware half of this arrangement. The point to carry forward is that the authorisation check lives with the action, in a policy, and is exercised by a test that attempts the action as a user who should be refused — not as a user who should be allowed.

5 · The Request and Response Objects

Documents the two objects that carry data across the HTTP boundary: how Leaf normalises superglobals, how responses are constructed and inspected, and the trust assumptions each input source carries.

5.1 The request object

A normalised view of the superglobals. The value is consistency across every input source, not any individual accessor.

The request object wraps PHP’s superglobals so that input is read the same way regardless of source. It is passed to handlers by type, as covered in chapter 4.

$request = request();

$request->url();               // '/orders/42?page=2' — path plus query
$request->method();            // 'POST', normalised to uppercase
$request->body();              // Parsed request body: form fields, or decoded JSON
$request->all();               // Body merged with query parameters
$request->json();              // Decoded JSON body as an array, or null if not JSON
$request->input('status');     // One value from the merged set, or null
$request->params['id'];        // Route parameters, not query
$request->query('page');       // Query string only
$request->files();             // Uploaded files, normalised to $_FILES shape
$request->headers();           // Request headers, case-insensitive access
$request->header('Accept');    // One header value
$request->ip();                // Client address — see the warning below
$request->user();              // The authenticated user, once middleware set it
$request->wantsJson();         // True when Accept prefers JSON

Do not read the superglobals directly in a controller. A handler that reads $_POST['email'] has silently opted out of Leaf’s normalisation, out of any test that fakes the request object, and out of the ability to know whether the value came from the body or the query string. The cost of the accessor over $_POST is one function call; the cost of the superglobal is a code path that only runs in production.

Two properties of the object are worth relying on explicitly, because they are what make it safe to use as a single interface:

// 1. Missing keys return null rather than raising a notice,
//    so optional input needs no isset() guard.
$status = $request->input('status');   // null when absent

// 2. Nested structures are arrays, never objects, so the shape
//    is uniform across form posts and JSON requests.
$items = $request->input('items', []);  // default applies
foreach ($items as $item) {
    $sku = is_array($item) ? ($item['sku'] ?? null) : null;
}

ip() is only as good as the proxy configuration. Behind a reverse proxy the immediate peer is the proxy, so the naive address is the proxy’s. Leaf may read a forwarded header depending on how your server populates the environment; that header is client-controlled unless the proxy overwrites it. If an IP address drives a rate limit, a session binding, or an audit record, resolve it from a header your infrastructure sets and strips from inbound requests, and treat it as untrusted input when you log it.

5.2 Input sources and their trust levels

Five distinct input sources with different meanings. Treating them as interchangeable is the root cause of most injection defects.

A request carries input from several independent sources. They differ in who controls them and in what they are for, which is why treating them as one merged bag — the convenience of $request->all() — is dangerous.

SourceRead asControlled byTrust
Route parameters$request->paramsThe user, via the URLUntrusted; constrained, never interpolated
Query string$request->query()The user, via the link or formUntrusted; often also used for state changes you should not allow
Form body$request->body()The user, via a formUntrusted; the only source a browser form legitimately writes
JSON body$request->json()The user, via an API clientUntrusted; may be arbitrarily nested, unlike a form
Headers$request->header()The user, unless your proxy sets itUntrusted unless infrastructure-owned
CookiesSession and cookie dataThe client, unless signedUntrusted; the signed portion only

The specific hazard of all() is that it merges the query string into the same array as the body. A handler that validates $request->all() and then reads a value from it can be made to accept a field it intended to read only from the form:

// The intent: the client may set a title, never an account id.
public function update(Request $request, int $id): Response
{
    $data = $request->all();   // ← includes the query string

    $order->rename($data['title']);
    $order->moveTo($data['account_id']);  // ← now attacker-controlled
}

// The fix: read the body, and select fields explicitly.
public function update(Request $request, int $id): Response
{
    $data = $request->body();   // form or JSON body only

    $edits = OrderEdits::fromArray([
        'title' => $data['title'] ?? null,
    ]);   // account_id is structurally absent

    ...
}

Mass assignment is the same bug in a different place. Taking an arbitrary input array and applying it to an object with a loop — foreach ($data as $k => $v) $order->$k($$v);, or a mass-update helper — lets the client set any settable field, including account_id, role, or verified_at. In Leaf there is no built-in mass assignment, which is a genuine advantage: the vulnerability has to be written by hand, so a review can see it. Keep it that way by allowing an explicit field list at every boundary.

For GET requests, the presence of body fields is a signal worth rejecting rather than ignoring. A state-changing verb is the only one where a body has meaning:

// In middleware, before the handler. Check the exact method name for
// your patch release; the principle is the constant, not the call.
if (!in_array($request->method(), ['POST', 'PUT', 'PATCH', 'DELETE'], true)) {
    if ($request->body() !== [] && $request->body() !== null) {
        return response()->json([
            'error' => 'unexpected_body',
        ], status: 400);
    }
}

return $next($request);

5.3 JSON bodies and file uploads

Reading structured bodies, the type surprises JSON introduces, and the file upload surface with its own validation requirements.

When the content type is JSON, the body is decoded and the object becomes associative arrays. The accessor you want depends on whether you need the raw string.

$request->header('Content-Type');   // 'application/json'

$request->json();                  // Decoded array, or null if the body is not JSON
$request->rawBody();               // The undecoded string, for signature verification
$request->body();                  // Returns the decoded JSON when the content type says so

JSON decodes to mixed types, and PHP is permissive about the conversion. A field expected to be a string may arrive as a number, a boolean, or null, and it may arrive as an array. Two consequences follow. First, never type-hint a controller parameter as a scalar and rely on the body to satisfy it — the body is not auto-bound (chapter 4). Second, validate structure explicitly before iterating: foreach ($payload['items'] as ...) on a payload where items is a string produces a warning and a wrong result rather than a clean failure.

A defensive read that turns a shape error into a validation failure instead of a warning:

$payload = $request->json();

if (!is_array($payload) || !isset($payload['items']) || !is_array($payload['items'])) {
    return response()->json([
        'error' => 'invalid_payload',
        'detail' => 'items must be an array',
    ], status: 422);
}

$items = array_map(
    fn(mixed $row) => is_array($row) ? $row : throw new UnexpectedValue('row'),
    $payload['items'],
);

File uploads arrive through $request->files(), which normalises the $_FILES structure so that multiple files under one field name are an array of entries rather than a single confusing shape.

$files = $request->files();   // array<string, array> keyed by field name

$upload = $files['avatar'] ?? null;

if ($upload === null) {
    return response()->json(['error' => 'avatar_required'], status: 422);
}

// 1. Did the transfer succeed? A non-OK error code is not an exception.
if (($upload['error'] ?? UPLOAD_ERR_NO_FILE) !== UPLOAD_ERR_OK) {
    throw new UploadFailed((int) $upload['error']);
}

// 2. Check size against your own limit, not only PHP's.
$maxBytes = 2 * 1024 * 1024;

if ((int) $upload['size'] > $maxBytes) {
    return response()->json(['error' => 'too_large'], status: 413);
}

// 3. Check type by inspecting content, never by trusting the name.
$finfo    = new finfo(FILEINFO_MIME_TYPE);
$mime     = $finfo->file($upload['tmp_name']);

if (!in_array($mime, ['image/png', 'image/jpeg', 'image/webp'], true)) {
    return response()->json(['error' => 'unsupported_type'], status: 415);
}

// 4. Generate the stored name yourself. Never reuse tmp_name or the
//    client-supplied name as a path component.
$ext     = match ($mime) {
    'image/png'  => 'png',
    'image/jpeg' => 'jpg',
    default          => 'webp',
};

$stored = 'avatars/' . bin2hex(random_bytes(16)) . '.' . $ext;

Four upload checks, all mandatory, in this order. Transfer status, size, content type by inspection, and a generated destination path. The checks in steps 3 and 4 are the two that are routinely skipped, and they are the two that matter: a file named avatar.png containing PHP source is served as an image by naive validation and executed by a misconfigured handler. Chapter 18 covers the storage-side controls that make the last step effective.

5.4 Building responses

The response object’s factory methods, what each implies about content type and status, and the header rules that apply to all of them.

The response object is immutable in practice: each factory returns a new instance carrying the status, headers, and body you specified. Nothing is sent until the framework writes it.

// JSON. Sets Content-Type: application/json. Escape slashes and unicode
// so payloads are safe to embed and readable in logs.
return response()->json($data, status: 200, flags: JSON_UNESCAPED_SLASHES);

// HTML from an already-rendered string.
return response()->html($html, status: 200);

// Plain text.
return response()->plain('OK', status: 200);

// An empty body with a status. 204 must carry no body at all.
return response()->make(status: 204);

// An existing PSR-7 response, if something upstream produced one.
return $psrResponse;

// A view, built as a Response so status and headers stay explicit.
return response()->view('orders/show', ['order' => $order], status: 200);

Setting headers. The object is chainable and headers accumulate:

$response = response()->json($data);

$response->header('X-Request-Id', $requestId);
$response->header('Cache-Control', 'private, max-age=60', replace: true);
$response->withHeader('ETag', $etag);

return $response;

Check the exact header methods for your patch release. Leaf has carried both mutating header() and immutable withHeader() style methods across versions, and which one exists determines whether a middleware that adds a header must return the object. Read vendor/leaf/leaf/src/Http/Response.php before writing a middleware that modifies a response, because getting this wrong produces a header that is silently absent with no error anywhere.

Cookies are set on the response, not through the global function, so that a test can inspect them:

$response = response()->json($data);

$response->cookie(
    name:     'remember_token',
    value:    $token,           // opaque random value, not a user id
    expire:   time() + 60 * 60 * 24 * 30,
    path:     '/',
    domain:   '',
    secure:   true,             // HTTPS only,
    httpOnly: true,             // not readable by JavaScript,
    // SameSite is the CSRF defence that works when a token is absent.
    sameSite: 'Lax',
);

return $response;

Never set a header value containing unescaped input. A response header value containing a newline is a header injection, and PHP will usually reject it — usually, not always, and the exception is when the value is folded or the check is bypassed. The correct rule is simpler than any mitigation: cast every header value to a string, strip control characters, and never place a user-supplied value in a header without that treatment. Chapter 18 covers the specifics.

5.5 Streaming, redirects, and headers already sent

When to bypass the response object, how to issue a redirect safely, and the single rule that makes a Leaf application misbehave silently.

Most responses are built through the object. Three cases are not.

// 1. A redirect. 303 after a successful POST is the correct semantic:
//    it tells the client to GET the location, so a refresh does not
//    resubmit the form.
return response()->redirect(route('orders.show', ['id' => $order->id]), 303);

// 2. A file download. Content-Disposition carries a filename that may
//    contain characters requiring quoting, so sanitise it.
return response()->download($path, $safeName, 'application/pdf');

// 3. A large body, where buffering would exceed memory_limit.
//    Bypass the object and stream deliberately, with no output before this.
$out = fopen('php://output', 'w');

while (($row = $stmt->fetch()) !== false) {
    fputcsv($out, $row);
}

fclose($out);
exit;

Output before the framework sends is unrecoverable. In Leaf, PHP output that happens before $app->run() returns — a BOM, a stray newline after a closing ?php tag, a var_dump left in a template, or a warning printed by a suppressed check — commits the headers. Every subsequent header() call and the response object’s own header set then fail silently, and the client receives a body with the wrong status code. If a Leaf route is returning 200 with a JSON body prefixed by a space, this is why.

Two defences, both cheap:

// 1. Never close a PHP tag in a template. Leave the file ending mid-tag
//    so the trailing newline is not part of the output.
//    resources/views/partials/row.php ends with:  <?php echo $row['id']; ?>
//    ...and nothing after that. No newline, no blank line, no tag.

// 2. Make display_errors off in every environment except your own.
//    A warning printed to the browser is output, and output is fatal
//    to the response contract.
ini_set('display_errors', '0');
error_reporting(E_ALL);

The rule for the streaming case deserves restating because it is the one that breaks least obviously: once you bypass the response object, you own status codes, headers, and error handling for that response entirely. A database error halfway through a CSV stream has already sent a 200 and part of the body, and no middleware can change it. If the export can fail, either run the query completely before writing anything, or write to a temporary file and send it in one piece.

6.1 Two different things called "model"

A single word covers both a persistence representation and a domain concept. Keeping them distinct is the central discipline of this chapter.

"Model" is used for two unrelated things in PHP codebases. Because Leaf ships no ORM, you will make this decision explicitly rather than inheriting it, which makes this the right place to be precise.

6.2 Value objects and invariants

The most valuable model type in a Leaf application, because it makes an invalid state impossible to construct rather than merely unlikely.

A value object is defined by having no identity: two instances with equal field values are interchangeable, and it is immutable. Its purpose is to make a rule enforceable at construction time, so that no code anywhere can hold an invalid one.

<?php

declare(strict_types=1);

namespace App\Domain\Money;

// Non-negative integer cents. There is no way to hold a negative
// amount, because the constructor refuses to build one.
final readonly class Cents implements \JsonSerializable, \Stringable
{
    private function __construct(public int $amount) {}

    public static function of(int $amount): self
    {
        if ($amount < 0) {
            throw new \InvalidArgumentException('Cents must not be negative');
        }

        return new self($amount);
    }

    public static function fromDecimal(string $input): self
    {
        // Parse explicitly. (float) then * 100 loses precision
        // and turns '8.115' into a wrong amount.
        if (!preg_match('/^(\d+)(?:\.(\d{1,2}))?$/', trim($input), $m)) {
            throw new \InvalidArgumentException('Not a monetary amount');
        }

        $fraction = str_pad($m[2] ?? '', 2, '0');

        return new self(((int) $m[1] * 100) + (int) $fraction);
    }

    public function plus(self $other): self
    {
        return new self($this->amount + $other->amount);
    }

    public function times(int $factor): self
    {
        if ($factor < 0) {
            throw new \InvalidArgumentException('Factor must not be negative');
        }

        return new self($this->amount * $factor);
    }

    public function isGreaterThan(self $other): bool
    {
        return $this->amount > $other->amount;
    }

    public function jsonSerialize(): mixed  { return $this->amount; }
    public function __toString(): string     { return number_format($this->amount / 100, 2, '.', ''); }
}

Use integers for money, always. The float arithmetic in the display method above is acceptable precisely because it is the last operation and the value is never fed back into a computation. Every step before that is integer cents. A rounding error that appears only at the display boundary is a cosmetic issue; one that appears in a tax calculation is a reconciliation problem that surfaces at year end.

The value of this class is not the arithmetic. It is that Cents::of(-5) cannot be constructed, so the bug is impossible rather than merely caught by a test that might be skipped. Compose several of them and the rules compose:

final readonly class Money
{
    public function __construct(
        public Cents $net,
        public Cents $tax,
    ) {}

    public function gross(): Cents
    {
        return $this->net->plus($this->tax);
    }
}

final readonly class OrderLine
{
    /** @param Cents $unitPrice */
    public function __construct(
        public string $sku,
        public int $quantity,      // validated in the constructor, not the database
        public Cents $unitPrice,
    ) {
        if ($quantity < 1) {
            throw new \InvalidArgumentException('Quantity must be at least one');
        }
    }

    public function total(): Cents
    {
        return $this->unitPrice->times($this->quantity);
    }
}

6.3 Entities, identity, and change tracking

An entity is defined by identity rather than value, which changes how it must be persisted and how its state is observed.

An entity has an identity that persists across changes. Two orders with identical contents are still two different orders, and this is the property that makes persistence, change tracking, and concurrency interesting.

final readonly class Order
{
    public function __construct(
        private OrderId $id,        // identity: a typed wrapper, not a bare string
        private AccountId $accountId,
        private OrderStatus $status,
        private Money $totals,
    ) {}

    public function id(): OrderId       { return $this->id; }
    public function status(): OrderStatus { return $this->status; }

    public function markPaid(): self
    {
        if (!$this->status->mayTransitionTo(OrderStatus::Paid)) {
            throw new IllegalTransition($this->id, $this->status, OrderStatus::Paid);
        }

        return new self($this->id, $this->accountId, OrderStatus::Paid, $this->totals);
    }
}

Wrap your identifier types. A method signature of findOrder(int $id) and findAccount(int $id) are indistinguishable to a reader and to a mistyped call. A value object per identifier type — OrderId, AccountId — makes the compiler enforce which belongs where, and gives you one place to attach the parsing rule. The cost is a class per identifier; the benefit is that passing an account id where an order id belongs becomes a type error rather than a data leak.

Change tracking is the substantive problem. With a readonly entity and a method that returns a new instance, you have no dirty state to flush — but you also have no way to save only what changed:

// Immutable: the repository writes the whole aggregate. Correct and simple,
// at the cost of writing every column on every change.
$repository->save($order);

// Mutable alternative: a UnitOfWork that compares snapshots.
final class UnitOfWork
{
    /** @var array<string, array{snapshot: object, current: object}> */
    private array $tracked = [];

    public function track(object $entity): void
    {
        $this->tracked[$this->keyFor($entity)] ??= [
            'snapshot' => clone $entity,
            'current'  => $entity,
        ];
    }

    public function commit(): void
    {
        foreach ($this->tracked as $key => $pair) {
            $changed = $this->diff($pair['snapshot'], $pair['current']);

            if ($changed !== []) {
                $this->sqlFor($key)->update($pair['current'], $changed);
            }
        }

        $this->tracked = [];
    }
}

Read-only models in a write-heavy application will cost you more than the alternative. The immutable approach writes the entire aggregate on every save, which for a large aggregate with a version column becomes an optimistic-locking problem, and for an aggregate with binary or JSON columns means rewriting data you did not touch. Both are correct. The honest statement is that the choice has real costs on both sides, and it should be made per aggregate rather than per application.

The concurrency control that makes this safe under concurrent edits, regardless of which style you choose:

-- The version column is what makes a lost update detectable.
ALTER TABLE orders ADD COLUMN version INT NOT NULL DEFAULT 1;

UPDATE orders
   SET status = ?, version = version + 1
 WHERE id = ? AND version = ?;   -- the version we read

Check affected rows, not exceptions. An update guarded by a version that affects zero rows is not an error condition at the SQL layer — it is a lost update that you must detect. The repository returns false, the service raises a conflict, and the middleware in chapter 13 turns that into a 409. Silently treating a zero-row update as success is one of the most damaging bugs in this area, because the data is now wrong and nothing recorded that it happened.

6.4 Where Active Record should stop

The specific conditions under which an Active Record style abstraction stops paying for itself, stated so the decision can be made on evidence.

Active Record means the model knows its own persistence: it has a connection, a table name, a save(), a delete(), and relationships. It is the dominant style in PHP for good reasons. It also has a boundary, and the boundary is worth being able to name.

SituationActive Record costVerdict
Simple CRUD over one table, few invariantsLow; saves a repository class per entityReasonable
Entities with real invariants, unit testedCannot construct without a database connection; every test is an integration testUse a mapper
Two aggregates must change in one transactionEncourages saving each independently, hiding the boundaryUse explicit repositories

Reporting and exportsObject graph traversal to produce a flat rowRaw queries into DTOs

The tipping point is testing, not design taste. The moment a rule matters enough that you want a fast test asserting it — "a refunded order cannot be shipped", "a credit limit is never exceeded" — Active Record makes that test require a seeded database. A suite of two hundred domain tests that each need a transaction rollback is a suite nobody runs, and rules that are not tested are not enforced. If the answer to "how would I test this?" is "with a fixture", that is a signal to move the rule into a class that needs no fixture.

The compromise most Leaf applications should adopt, which takes the useful half of each style:

// Domain: pure, fast to test, knows nothing about storage.
final class CreditPolicy
{
    public function assertWithinLimit(Exposure $current, Cents $adding): void
    {
        if ($current->total()->plus($adding)->isGreaterThan($this->limit)) {
            throw new CreditExceeded($current, $adding, $this->limit);
        }
    }
}

// Repository interface, declared where the domain needs it.
interface OrderRepository
{
    public function find(OrderId $id): ?Order;
    public function exposureFor(AccountId $account): Exposure;
    public function save(Order $order, int $expectedVersion): bool;
}

// Implementation: the only place SQL exists.
final class PdoOrderRepository implements OrderRepository
{
    public function __construct(private PDO $db) {}

    public function find(OrderId $id): ?Order
    {
        $stmt = $this->db->prepare(
            'SELECT id, account_id, status, net_cents, tax_cents, version
          . '  FROM orders WHERE id = ?'
        );
        $stmt->execute([$id->toString()]);

        $row = $stmt->fetch();

        return $row === false ? null : $this->hydrate($row);
    }
}

The repository interface is declared next to the domain that depends on it, not next to the implementation. That placement is what keeps the dependency arrow pointing inward: the domain names what it needs, and the infrastructure satisfies it. Chapter 7 covers the implementation in detail.

6.5 Hydration and the mapper boundary

The translation layer between rows and objects, where type errors become silent if the mapping is not explicit.

Hydration is the function that turns a database row into a domain object. It is short, it is repeated for every entity, and it is where a type confusion becomes permanent: a string '0' from the driver, or a decimal column that arrived as a float, is captured into the object and then trusted for the rest of the request.

final class OrderHydrator
{
    /** @param array<string, mixed> $row */
    public function hydrate(array $row): Order
    {
        return new Order(
            id:        new OrderId((string) $row['id']),
            accountId: new AccountId((string) $row['account_id']),
            status:    OrderStatus::from((string) $row['status']),   // throws on an unknown value
            totals:    new Money(
                net: Cents::of((int) $row['net_cents']),
                tax: Cents::of((int) $row['tax_cents']),
            ),
        );
    }
}

Column types are the mapper’s responsibility. Define money columns as integers in the schema so no precision is ever lost at the boundary. When a legacy column must be DECIMAL, read it as a string and parse it with Cents::fromDecimal() from section 6.2 — never (int) (float) $row['total'], which rounds twice. The cost of getting the schema right now is a migration; the cost of getting it wrong is a reconciliation that fails silently at year end.

Nullable columns are the second trap. A row where paid_at is NULL must not become a DateTimeImmutable of the epoch, and an optional relation must stay absent rather than becoming an empty collection that reads as "no items" when it means "not loaded":

private function optionalDate(?string $raw): ?DateTimeImmutable
{
    return $raw === null
        ? null
        : new DateTimeImmutable($raw);
}

An explicit hydrator beats a generic one. A reflection-based mapper that maps any object from any array will happily map password_hash into a user object and then serialise it. An explicit hydrator lists the fields it reads, which means a new column is invisible to your code until you decide it should be — precisely the behaviour you want when someone adds a column holding personal data.

For read paths that never mutate, skip the entity entirely and return a purpose-built shape. It is faster, and it makes the endpoint’s contract explicit:

// Read path: no entity, no invariants, no hydration cost.
final class OrderSummaryRow
{
    public function __construct(
        public string $id,
        public string $status,
        public int $totalCents,
        public string $placedAt,
    ) {}
}

// And the query that produces it — no SELECT *, always.
$stmt = $db->prepare(
    'SELECT id, status, (net_cents + tax_cents) AS total_cents,'
  . '       placed_at'
  . '  FROM orders'
  . ' WHERE account_id = ?'
  . ' ORDER BY placed_at DESC'

7.1 Connection management

One connection per request, opened at boot, with a fixed set of attributes that determine whether failures are loud or silent.

Leaf does not provide a database layer. You use PDO, and the first decision is where the connection lives. Because the bootstrap file runs once per request and returns the app, a single connection created there is available to everything for the life of that request.

# bootstrap/app.php — the settings that matter are the attributes, not the DSN.
$pdo = new PDO(
    dsn:     $config['db']['dsn'],
    username: $config['db']['user'],
    password: $config['db']['password'],
    options: [
        // 1. Errors throw. Without this, a failed query returns false and
        //    your code writes an empty page instead of a 500.
        PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,

        // 2. Rows arrive as associative arrays. Cheaper than objects,
        //    and the shape your hydrators expect.
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,

        // 3. Real server-side prepares. See section 7.2 — this one line
        //    is the difference between escaping and parameterisation.
        PDO::ATTR_EMULATE_PREPARES   => false,

        // 4. Real prepared statements reuse connections instead of
        //    reconnecting per statement. A large performance factor on
        //    MySQL for anything chatty.
        PDO::ATTR_PERSISTENT         => false,
    ],
);

Never enable persistent connections without understanding the consequence. A persistent connection survives the request and keeps session state, temporary tables, and transaction state alive. If a request dies mid-transaction, the next request to borrow that connection inherits an open transaction with locks held. It also defeats per-request connection limits in a way that is invisible until you are load testing. Leave it off; the connection cost of a modern local socket is far below the cost of debugging leaked transaction state.

7.2 Prepared statements and the emulation trap

The distinction between escaping and parameterising, and the single PDO setting that determines which one you actually have.

Two superficially similar approaches exist. Only one is correct, and the setting that distinguishes them is often left at a value that silently reduces the safe approach to the unsafe one.

// WRONG. Escaping. The value is turned into a literal, then the statement
// is assembled. If the escaping is wrong for one character class, the
// statement is injectable. This is also why the charset in the DSN
// suddenly becomes a security setting.
$sql = "SELECT * FROM users WHERE email = '"
     . $pdo->quote($email) . "'";
$stmt = $pdo->query($sql);

// RIGHT. Parameterising. The statement is sent to the server with
// placeholders; the values travel separately and the server is
// structurally incapable of executing them as SQL.
$stmt = $pdo->prepare('SELECT * FROM users WHERE email = ?');
$stmt->execute([$email]);
$user = $stmt->fetch();

Check ATTR_EMULATE_PREPARES and know why it matters. When emulation is true — the default on many PDO MySQL installations — the driver does not send a parameterised statement to the server. It interpolates the value into the SQL, quoting it, and sends a complete statement. The result is that you have written parameterised code and received escaped code, with none of the guarantees. Setting it to false forces genuine server-side prepares, at the cost of losing some driver features — notably multi-value INSERT, and integer binding behaves more strictly. The security benefit is not optional.

A small wrapper makes the correct usage the path of least resistance, and gives one place to add the statement log that chapter 17's profiler needs:

final class Database
{
    /** @var list<array{sql: string, ms: float}> */
    private array $log = [];

    public function __construct(private PDO $pdo) {}

    public function select(string $sql, array $bindings = []): array
    {
        return $this->run($sql, $bindings)->fetchAll();
    }

    public function selectOne(string $sql, array $bindings = []): ?array
    {
        $row = $this->run($sql, $bindings)->fetch();

        return $row === false ? null : $row;
    }

    public function scalar(string $sql, array $bindings = []): mixed
    {
        $value = $this->run($sql, $bindings)->fetchColumn();

        return $value === false ? null : $value;
    }

    public function execute(string $sql, array $bindings = []): int
    {
        return $this->run($sql, $bindings)->rowCount();
    }

    private function run(string $sql, array $bindings): PDOStatement
    {
        $started = hrtime(true);

        $stmt = $this->pdo->prepare($sql);

        foreach ($bindings as $key => $value) {
            $param = is_int($key) ? $key + 1 : $key;   // 1-based; named keys pass through

            $stmt->bindValue(
                $param,
                $value,
                match (true) {
                    is_int($value)  => PDO::PARAM_INT,
                    is_bool($value) => PDO::PARAM_BOOL,
                    $value === null => PDO::PARAM_NULL,
                    default         => PDO::PARAM_STR,
                },
            );
        }

        $stmt->execute();

        $this->log[] = [
            'sql' => $sql,
            'ms'  => (hrtime(true) - $started) / 1_000_000,
        ];

        return $stmt;
    }

    public function queries(): array { return $this->log; }
    public function count(): int       { return count($this->log); }
}

Always bind by type, never pass everything as strings. execute([$id]) sends the type PHP infers; binding an int as PARAM_STR makes MySQL compare an integer column against a string, which disables index use and can change comparison semantics. The match above makes the type explicit for every binding, which matters most for the boolean and null cases — a null bound as a string becomes the four-character string "null" in some drivers.

7.3 Binding parameters correctly

Positional versus named placeholders, the values that cannot be bound at all, and the pattern that makes dynamic queries safe.

PlaceholderBound withUse when
?A zero-indexed arrayDefault. Fewer repetitions of the same value
:nameAn associative arrayLong statements where position is hard to verify
Literals in the SQLNothing — validated, not boundTable names, column names, sort direction

Some values cannot be placeholders: an identifier, a keyword, and a limit clause. These must be interpolated from an allow-list, and the allow-list is the security control:

// WRONG. The column name is a placeholder-shaped hole.
$sql = "SELECT * FROM orders ORDER BY {$sort} {$direction}";

// RIGHT. An allow-list turns an injection point into a lookup that
// can only produce a known-safe value or fail.
$sortable = [
    'placed_at' => 'placed_at',
    'total'     => '(net_cents + tax_cents)',
    'status'    => 'status',
];

$column = $sortable[$requested] ?? throw new InvalidArgument('unsupported sort');

$sql = "SELECT id, status, net_cents + tax_cents AS total "
     . "FROM orders WHERE account_id = ? "
     . 'ORDER BY ' . $column . ' '
     . ($direction === 'desc' ? 'DESC' : 'ASC')
     . ' LIMIT ? OFFSET ?';

Note that the direction is resolved by comparison to the literal 'desc' rather than passed through, and the column comes from an array lookup where the user supplies a key, not a fragment. Both techniques are sound; both are easy to get subtly wrong when applied to a value the developer did not consider structural.

A query builder is not automatically a safe query builder. A library that interpolates an identifier it cannot bind will happily produce ORDER BY plus attacker text if you passed the column name through unvalidated. If you adopt a builder, the questions to ask are: which clauses does it parameterise, and which does it interpolate? Then check that every value you pass into the interpolating categories has been allow-listed first. The same question applies to IN clauses, which have no placeholder form at all and therefore must be built from validated values:

// IN clauses: build the placeholders, bind the values, keep the counts equal.
$ids = array_values(array_filter(
    $requested,
    fn(mixed $id) => is_string($id) && preg_match('/^[0-9a-f-]{36}$/', $id) === 1,
));

if ($ids === []) {
    return response()->json(['data' => []], status: 200);
}

$placeholders = implode(', ', array_fill(0, count($ids), '?'));

$stmt = $db->prepare("SELECT id, status FROM orders WHERE id IN ({$placeholders})");
$stmt->execute($ids);

Bind placeholders and values in the same statement, always. The classic bug is implode(', ', $placeholders) where $placeholders is built from the count of the input array, while the values passed to execute() come from a differently filtered array. A mismatch in count produces a false result set, not an error, and the security consequence depends entirely on which array was filtered. Building both from one filtered variable — as above — makes the mismatch impossible.

One last category: values the database itself should produce. Letting the server generate an identifier, timestamp, or checksum avoids a round trip and avoids a clock skew between your application servers:

// Let the database be the source of truth for identity and time.
$db->execute(
    'INSERT INTO orders (account_id, status, net_cents, tax_cents, placed_at)'
  . ' VALUES (?, ?, ?, ?, CURRENT_TIMESTAMP)',
    [$accountId, 'pending', $net, $tax],
);

$id = $db->pdo->lastInsertId();

7.4 Building queries without string concatenation

Composing optional filters safely, and the caching layer that is worth adding only after the query itself is correct.

Dynamic filters are where hand-written SQL becomes dangerous, because each condition is added conditionally. The rule is that WHERE clauses accumulate in an array, joined with AND, and every value is a binding:

final class OrderSearch
{
    public function __construct(private Database $db) {}

    public function find(AccountId $account, OrderFilters $filters): array
    {
        $where  = ['account_id = ?'];
        $bind   = [$account->toString()];

        // Each block appends both a fragment and its values. Keeping
        // them adjacent is what keeps the two in step.
        if ($filters->status !== null) {
            $where[] = 'status = ?';
            $bind[]  = $filters->status->value;
        }

        if ($filters->placedAfter !== null) {
            $where[] = 'placed_at >= ?';
            $bind[]  = $filters->placedAfter->format('Y-m-d H:i:s');
        }

        if ($filters->minimumTotal !== null) {
            $where[] = '(net_cents + tax_cents) >= ?';
            $bind[]  = $filters->minimumTotal->amount;
        }

        $sql = 'SELECT id, status, net_cents, tax_cents, placed_at'
             . '  FROM orders'
             . ' WHERE ' . implode(' AND ', $where)
             . ' ORDER BY placed_at DESC'
             . ' LIMIT ? OFFSET ?';

        $bind[] = $filters->perPage;
        $bind[] = $filters->offset();

        return $this->db->select($sql, $bind);
    }
}

Filter objects are the right place for the rules. Notice that OrderFilters — a plain value object with a validated status, a bounded date, and a computed offset — carries three of the policies that would otherwise be inline conditionals: a maximum page size, a non-negative offset, and an allowed status set. It is testable without a database, which is exactly the property from chapter 6.

Two composition rules that are easy to violate and hard to spot:

RuleReason
Never select *A column added later is silently exposed through your serialiser; chapter 6.5 makes this concrete
Never JOIN a table you do not read fromMultiplies rows, changes aggregate semantics, and defeats a covering index
Prefer a second query to a LEFT JOIN for optional one-to-manyA join with a nullable side duplicates the parent row and forces a GROUP BY
Push filtering into SQL, never into PHP after the fetchFetching 10 000 rows to discard 9 990 of them is the most common performance defect in this layer

Caching a query result is the natural next thought, and it is worth being precise about when. Cache a specific, expensive, frequently repeated read. Do not cache a query whose parameters include anything a user can see and should not see another user’s copy of, and do not add a cache in front of a query you have not yet checked for an index.

7.5 Transactions, migrations, and operational limits

Transaction scope as a design decision, the four properties you need from a migration tool, and the query patterns that break under concurrency.

Since the connection is a single object per request, a transaction is a property of that connection. The discipline that matters is choosing the scope deliberately rather than by habit.

final class Transaction
{
    public function __construct(private PDO $pdo) {}

    // Accepts a callable so the boundary is one statement, and the
    // rollback happens on any Throwable without a catch block.
    public function run(callable $work): mixed
    {
        $this->pdo->beginTransaction();

        try {
            $result = $work();

            $this->pdo->commit();

            return $result;
        } catch (Throwable $e) {
            if ($this->pdo->inTransaction()) {
                $this->pdo->rollBack();
            }

            throw $e;
        }
    }
}
ScopeCorrect forWrong for
One statementNothing — autocommit is correct for a single write—
One use caseMulti-row writes that must agreeWrapping a mail send or an HTTP call
Request-wideRare batch imports where the whole request is one unitAny request that also calls out to a third party

Never hold a transaction open across a network call. An external request inside a transaction holds row locks for the duration of someone else’s latency, which is unbounded from your side. The correct pattern is: commit the state change with an outbox row in the same transaction, then process the outbox after commit. If the notification must be strongly coupled, accept that you have a distributed systems problem and say so in a comment rather than discovering it during an incident.

Migrations: four properties are non-negotiable, whatever tool you choose.

That last property is the one teams discover late. Adding a NOT NULL column with no default breaks the old code still running. The safe sequence is: add the column nullable, deploy code that writes both, backfill, add the constraint, deploy code that requires it. Expanding the schema before contracting the code is the rule.

Three query patterns that fail under concurrency or scale, worth recognising on sight:

// 1. Check-then-act. Two concurrent requests both read "not taken",
//    both proceed. Fix: a single conditional UPDATE, or a unique index
//    whose violation you catch.
$free = $db->selectOne('SELECT * FROM coupons WHERE code = ? AND used_at IS NULL', [$code]);

if ($free !== null) {
    $db->execute('UPDATE coupons SET used_at = ? WHERE code = ?', [now(), $code]);
}

// 2. OFFSET pagination. Row 5000 costs more than row 1, and rows
//    shift between pages, so an item appears twice or vanishes.
//    Fix: keyset pagination on an indexed, ordered column.
$db->select(
    'SELECT id, placed_at FROM orders'
  . ' WHERE (placed_at, id) < (?, ?)'
  . ' ORDER BY placed_at DESC, id DESC LIMIT ?',
    [$cursorDate, $cursorId, 50],
);

// 3. N+1. One query for the list, then one per row. See chapter 17.
$orders = $db->select('SELECT id, customer_id FROM orders LIMIT 50', []);

foreach ($orders as $row) {
    $row['customer'] = $db->selectOne(   // ← 50 extra queries
        'SELECT name FROM customers WHERE id = ?', [$row['customer_id']],
    );
}

On the unique-index fix for check-then-act. A unique constraint on coupons.code plus a plain INSERT is stronger than any amount of application-level checking, because the database is the only component that sees all concurrent writers. Catch the driver-specific duplicate-key exception and translate it to a domain-level AlreadyUsed. This is the general principle: prefer a database constraint over an application check for any invariant that must hold globally.

8 · Middleware: Before, After, Around, Ordering, Short-Circuiting

8.1 Middleware anatomy and the three phases8.2 Before middleware: guarding and enriching8.3 After middleware: observing and modifying8.4 Around middleware: short-circuiting and timing8.5 Ordering, grouping, and termination

Documents the middleware pipeline: the contract a middleware class implements, the before, after, and around phases, the conditions under which a layer may stop a request, and the ordering rules that govern composition.

8.1 Middleware anatomy and the three phases

A middleware is a class with an optional before or after method. Understanding the phases explains every ordering question in this chapter.

A Leaf middleware is a class with a before method, an after method, or both. The framework calls what it finds. There is no base class to extend and no interface to implement, which means a middleware is identified by its method names rather than its type.

<?php

declare(strict_types=1);

namespace App\Middleware;

use Leaf\Http\Request;
use Leaf\Http\Response;

final class RequireApiKey
{
    // before(Request): ?Response — runs on the way in.
    // Returning null continues; returning a Response stops the request.
    public function before(Request $request): ?Response
    {
        $key = $request->header('X-Api-Key');

        if ($key === null || !hash_equals(self::configuredKey(), $key)) {
            return response()->json(['error' => 'unauthorized'], status: 401);
        }

        return null;
    }
}

Three phases, and the distinction between them is the basis of every ordering decision:

PhaseMethodSeesCan
DescentbeforeThe incoming request only; no response existsReject the request, attach data to it, open a resource
Handler———
AscentafterThe final responseAdd or modify headers, log, observe timing

An "around" middleware is not a third method. It is the composition of before and after in one class, distinguished by whether it captures a $next callable and calls it itself. This matters because the two styles have different error-handling consequences, discussed in section 8.4.

// Both phases in one class: the "around" style. Useful for timing and
// for cleanup that must happen whatever the outcome.
final class MeasureResponseTime
{
    public function before(Request $request, callable $next): Response
    {
        $started = hrtime(true);

        // Everything nested inside this call — including every
        // layer below and the handler itself — runs here.
        $response = $next($request);

        $ms = (hrtime(true) - $started) / 1_000_000;

        $response->header('X-Response-Time', sprintf('%.2fms', $ms));

        return $response;
    }
}

Check which signature your Leaf patch release expects. Some versions of the around style pass callable $next as a second argument to before; others use a dedicated handle() method. The framework surface here is small but not uniform across releases. Read vendor/leaf/leaf/src/Middlewares/ and the shipped built-ins — they are working examples of the exact signature your version invokes — and match them.

A middleware that is a class name string must be resolvable. Leaf instantiates middleware by class name, so the class must be autoloadable at the point the route table is built. A middleware defined inside another file, or conditionally declared, will not be found at dispatch time — and because the route table is assembled at boot, the failure may not appear until the first request that traverses the route.

8.2 Before middleware: guarding and enriching

The two legitimate uses of the descent phase — refusing a request and attaching context — and the obligations each carries.

Before middleware does one of two things: it refuses the request, or it attaches something later layers need. Both are legitimate; anything else belongs elsewhere.

<?php

final class AuthenticateSession
{
    public function __construct(private UserRepository $users) {}

    public function before(Request $request): ?Response
    {
        $userId = $_SESSION['user_id'] ?? null;   // via the session layer

        if ($userId === null) {
            // A browser gets a redirect so the flow can continue.
            if ($request->wantsJson()) {
                return response()->json(
                    ['error' => 'unauthenticated'],
                    status: 401,
                );
            }

            session()->set('intended_url', $request->url());

            return response()->redirect(route('login'), 302);
        }

        $user = $this->users->find(new UserId($userId));

        if ($user === null) {
            // The session is valid but the account is gone. Clear it
            // so the user is not redirected back to a loop.
            session()->invalidate();

            return response()->redirect(route('login'), 302);
        }

        $request->user = $user;   // attach for the handler and later layers

        return null;   // null means "continue"
    }
}

The contract a before-phase middleware owes the pipeline:

ObligationReason
Return null to continue, never a falsy valueAny non-null return is treated as a terminal response
Set an accurate status when rejecting401 for unauthenticated, 403 for unauthorised, 419 for a CSRF failure
Be idempotentPreflight requests and probes traverse the same routes
Do not perform the action’s own workIt has not been authorised yet in general
Do not open a transactionIt would hold locks across a request that may not touch the database at all
Do not read the body destructivelyThe handler still needs it; normalise without consuming

Do not read the body in a before-phase middleware. PHP can only populate php://input once. If a middleware calls json_decode(file_get_contents('php://input'), true) on a JSON request, the handler’s later read returns an empty string and every downstream value is missing. This manifests as a validation error that reports every field as absent, which sends people looking at the validator instead of the middleware. If a middleware must inspect the payload, use the request object’s own accessor, and never consume the stream.

The second legitimate use is enrichment — attaching something expensive to compute once, or something every handler in a group needs:

final class AttachLocale
{
    public function before(Request $request): ?Response
    {
        $supported = ['en', 'fr', 'de'];

        $negotiated = $request->header('Accept-Language');

        $locale = $supported[0];

        if ($negotiated !== null) {
            foreach (explode(',', $negotiated) as $part) {
                $tag = strtolower(trim(explode(';', $part)[0]));

                if (in_array($tag, $supported, true)) {
                    $locale = $tag;
                    break;
                }
            }
        }

        $request->locale = $locale;

        return null;
    }
}

Parse the header, do not trust its structure. Accept-Language is attacker-controlled and a naive explode(',')[0] is not a negotiation algorithm. The loop above reads a prefix before the quality value, which is enough to pick a supported language and silently falls back for anything unrecognised. Match the specificity you actually need; more elaborate negotiation is a documentation rabbit hole rather than a security one, as long as an unrecognised value always falls back to a default you control.

8.3 After middleware: observing and modifying

The ascent phase, where the response is complete and its status code and headers are known.

After middleware runs on the way out and has access to the final response. Its uses divide into observation and modification, and the distinction matters because modification is riskier than it looks.

<?php

final class SecurityHeaders
{
    public function after(Request $request, Response $response): Response
    {
        $response->header('X-Content-Type-Options', 'nosniff');
        $response->header('X-Frame-Options',        'DENY');
        $response->header('Referrer-Policy',        'strict-origin-when-cross-origin');
        $response->header('Strict-Transport-Security', 'max-age=31536000; includeSubDomains');

        // CSP is set only on HTML. Sending it on a JSON response is
        // harmless but noisy, and sending a report-only policy in
        // production is worse than sending none.
        if (str_contains((string) $response->header('Content-Type'), 'text/html')) {
            $response->header('Content-Security-Policy', self::policy());
        }

        return $response;
    }
}

Audit logging is the other principal use, and it is where a subtle mistake is common — logging the response but not accounting for responses that never reached this layer:

final class AuditLog
{
    public function __construct(private Logger $log, private Clock $clock) {}

    public function after(Request $request, Response $response): Response
    {
        $this->log->info('request.complete', [
            'method'    => $request->method(),
            'path'      => $request->url(),
            'status'    => $response->status,
            'request_id' => $request->id,
            'user_id'   => $request->user?->id()->toString(),
            'duration_ms' => (int) round((microtime(true) - $request->startedAt) * 1000),
        ]);

        return $response;
    }
}

After middleware does not see every response. If a before-phase middleware above it short-circuited, or an exception propagated past it, this layer’s after-phase may never run — which means the requests you most want recorded are the ones that go missing. Do not rely on after middleware as your only audit trail. Either place the audit layer outermost so it sees everything including failures, or log from the error handler as well, and reconcile the two counts. Chapter 14 covers the error handler’s role in this.

Never log a request body wholesale. A body log records passwords, tokens, and personal data, and it stores them in a log system with different access controls and a longer retention than the application. If you need to debug a payload, log the keys and the types, not the values: ['email' => 'string', 'quantity' => 'int'] is almost always what you actually wanted, and it is safe to keep.

Compressing a response is an after-phase modification, and the ordering requirement is that it runs before any layer that measures the size:

final class CompressResponse
{
    public function after(Request $request, Response $response): Response
    {
        $body = $response->body();

        // Do not compress what is already compressed, and skip tiny
        // payloads where the header costs more than the saving.
        if (strlen($body) < 1024) {
            return $response;
        }

        if (!str_contains((string) $request->header('Accept-Encoding'), 'gzip')) {
            return $response;
        }

        $compressed = gzencode($body, 6);

        if ($compressed === false) {
            return $response;
        }

        return $response
            ->withBody($compressed)
            ->header('Content-Encoding', 'gzip', replace: true)
            ->header('Vary', 'Accept-Encoding', replace: true);
    }
}

8.4 Around middleware: short-circuiting and timing

The around style, the guarantee it gives you about unwinding, and why error handling should use it.

Around middleware wraps the rest of the pipeline. Because it controls the call to $next, it can time the work, retry it, or guarantee cleanup — behaviours that are awkward or impossible when before and after are separate methods.

<?php

final class ErrorHandlerMiddleware
{
    public function before(Request $request, callable $next): Response
    {
        try {
            $response = $next($request);

            return $response;
        } catch (HttpException $e) {
            // Expected, client-caused: map directly, no stack trace.
            return $this->render($request, $e->status, $e->getMessage());
        } catch (ValidationException $e) {
            return $this->render($request, 422, $e->getMessage(), $e->errors());
        } catch (Throwable $e) {
            // Unexpected. Report it, then return something generic.
            $this->report($e, $request);

            return $this->render($request, 500, 'Internal Server Error');
        } finally {
            // Runs on every path, including the throwing one. This is
            // the reason to prefer around for cleanup.
            $this->flush();
        }
    }
}

The guarantee that makes the around style superior for cross-cutting work is that a finally block executes whether the inner pipeline returned normally, returned a short-circuit response, or threw. Separate before and after methods do not give you that unconditionally, as section 3.5 noted.

Put the error handler first, globally, forever. It must be the outermost layer so that it can catch a throw from any layer below it, including the router’s own dispatch. If anything is registered before it — a session layer, a logging layer, a rate limiter — then a failure inside that thing is invisible to your error handling, and the client gets an unhandled fatal with a stack trace in the body.

Retry is the other capability the around style enables, and it is one that is easy to misuse:

final class RetryTransient
{
    public function before(Request $request, callable $next): Response
    {
        $attempt = 0;

        beginning:

        $attempt++;

        try {
            $response = $next($request);
        } catch (Throwable $e) {
            // Only for failures that are genuinely transient, and only
            // for idempotent methods. Retrying a POST that charged a
            // card can charge it twice.
            $transient = $e instanceof TransientUpstreamException;

            $safeMethod = in_array($request->method(), ['GET', 'HEAD', 'PUT', 'DELETE'], true);

            if (!$transient || !$safeMethod || $attempt >= 3) {
                throw $e;
            }

            // Jittered backoff, so a fleet does not retry in lockstep.
            usleep((int) ((2 ** $attempt) * 50_000 + random_int(0, 25_000)));

            goto beginning;
        }

        return $response;
    }
}

A retried request re-runs every layer below the retry point. If the retry middleware sits above the authentication layer, each attempt re-authenticates. If it sits above a layer that opens a transaction, a partial attempt may leave state behind. Place retry as late in the pipeline as possible — immediately around the specific upstream call it protects, which usually means inside a service rather than in the middleware stack at all.

8.5 Ordering, grouping, and termination

The reference ordering for a production application, the rule for deciding it, and the three ways a pipeline ends.

Middleware order is a correctness property, not a preference. The order below is a working default, and the reasoning for each position is what makes it defensible when your application needs something added.

$app = new Leaf\App();

$app->use([
    // 1. Outermost: must catch everything, including the layers below it.
    App\Middleware\ErrorHandlerMiddleware::class,

    // 2. Establish request-scoped context that everything else may need.
    App\Middleware\AssignRequestId::class,
    App\Middleware\StartTimer::class,

    // 3. Infrastructure. Compression before any layer that measures size.
    App\Middleware\CompressResponse::class,

    // 4. Security headers, applied to every response including error pages.
    App\Middleware\SecurityHeaders::class,

    // 5. State. Session must precede auth, which reads the session.
    Leaf\Middlewares\SessionMiddleware::class,

    // 6. Cross-cutting request policies.
    App\Middleware\EnforceHttps::class,
    App\Middleware\ThrottleRequests::class,
]);

// Per-group: state that only some routes need.
$app->group('', function () {
    $this->get('/orders', 'OrderController@index')->middleware([
        App\Middleware\AuthenticateSession::class,
    ]);
});

The rule that generates the order: a layer’s prerequisites must come before it, and its effects must come after anything that observes them. Expressing it that way makes the ordering derivable rather than memorised.

PairWhy the order is fixed
ErrorHandler before everythingIt must enclose the layers that can throw
AssignRequestId before loggingA log line without an id cannot be correlated with anything
Compress before security headersHeaders describe the body that is actually sent
Session before AuthenticateAuthentication reads the session to find the user
Authenticate before AuthoriseYou cannot ask what a user may do before knowing who they are
Throttle before AuthenticateLimiting after authentication means an unauthenticated flood costs a session read per request
CSRF after SessionThe token lives in the session, so the session must exist

Global versus group is a scoping decision, not an importance one. A middleware on $app->use() runs for static asset requests too, if those requests traverse PHP. If compression is registered globally and your server is already serving /assets/ directly, you are paying for a middleware that can never usefully fire. Register the stateful layers globally, and put request policies on the groups that need them.

Three ways a pipeline terminates, and what each owes the client:

TerminationMechanismWho produces the response
NormalHandler returns a ResponseHandler, then after layers may modify it
Short-circuitA before layer returns a non-null responseThe middleware; the handler never runs
ExceptionAny layer or the handler throwsThe error handler, if it is outermost

Whichever way it ends, the after-phase of any layer that has already descended should still be given the chance to clean up. Verify this behaviour in your Leaf patch release rather than assuming it, using the experiment from section 3.5: register a before/after pair, short-circuit inside the inner one, and assert what the outer one observed. If the outer after-phase is skipped, every cleanup it performs — closing a handle, writing a log line, clearing a lock — is omitted precisely for rejected requests, which is the worst possible time to omit it.

9.1 Rendering a view and the variable contract

A template is a PHP file that receives an array of named variables. The contract is small, and its strictness is what makes templates safe to use.

Leaf templates are plain PHP files. Rendering extracts the data array into the template’s scope, includes the file, and captures the output as a string.

// From a controller
return response()->view('orders/show', [
    'order'   => $order,
    'customer' => $customer,
    'canEdit' => $canEdit,
]);

// From a route closure, same call
return view('pages/about', ['year' => date('Y')]);

The template receives exactly the keys you passed, and nothing else. This is the single most important property for security, because it means a template cannot reach the database connection or a service by accident — it has no variable referencing one.

# resources/views/orders/show.php
<?php
/** @var Order $order  @var Customer $customer  @var bool $canEdit */
?>
<h1>Order <?= $this->escape($order->id()) ?></h1>

<table>
    <tr><th>Customer</th><td><?= $this->escape($customer->name()) ?></td></tr>
    <tr><th>Status</th><td><?= $this->escape($order->status()->value) ?></td></tr>
    <tr><th>Gross</th><td><?<=> $order->totals()->gross() ?></td></tr>
</table>

<?php if ($canEdit): ?>
    <a href="<?= $this->escape(route('orders.edit', ['id' => $order->id()])) ?>">Edit</a>
<?php endif; ?>

The template has a $this. It refers to the template context, which is where escape(), include(), section(), and the URL helpers live. If your template needs a helper that is not on that object, pass the value in as a variable from the controller instead of reaching for a global — a template that resolves a service locator is a template you cannot test or reason about.

Naming conventions inside templates are worth adopting, because they make the safe path the obvious one. Variables holding a domain object get escaped through an explicit call; variables proven to contain only your own markup are the only ones printed raw; and the naming signals which is which.

VariableContainsPrinted as
$orderA domain object$this->escape((string) $order->id())
$titleA plain string from the database$this->escape($title)
$classListA string you built from a constant list<?= $classList ?> — see the caveat below
$svgIconMarkup read from resources/ at boot<?= $svgIcon ?>

A variable name is not a proof of safety. $classList reads as safe because it sounds like a list, but if it was built by concatenating a value from a request, it is an injection point into an attribute context. Escaping for HTML text is not escaping for an attribute value, and neither is escaping for a JavaScript string or a URL. Chapter 18 covers context-specific escaping; the rule here is that raw output requires a documented provenance, not a plausible name.

9.2 Layouts and section composition

Wrapping a page in a layout, filling named regions, and the yield mechanism that connects them.

A layout is a template that renders its own chrome and then yields to the page template’s content. Leaf supports this through named sections.

# resources/views/layouts/app.php
<!DOCTYPE html>
<html lang="<?= $this->escape($locale ?? 'en') ?>">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title><?= $this->escape($pageTitle ?? 'Orders') ?></title>
    <?= $this->asset('app.css') ?>
</head>
<body>
    <header>
        <nav><a href="/">Orders</a></nav>
        <?= $this->partial('partials/user-menu', ['user' => $user ?? null]) ?>
    </header>

    <main>
        <?php $this->yieldContent() ?>
    </main>

    <footer><p>&copy; 2026</p></footer>
    <?= $this->asset('app.js', defer: true) ?>
</body>
</html>

# Rendering with a layout. The two supported shapes — use whichever your
# patch release provides; both appear in the shipped templates.
return response()->view('orders/show', $data)->withLayout('layouts/app', [
    'pageTitle' => 'Order ' . $order->id(),
]);

// Or, from the page template itself, if you prefer the relationship
// to be visible in the template rather than at the call site.
$this->layout('layouts/app');

Named sections let a page fill a specific region of the layout rather than only the main content area — the common need for a page-specific script or a page-level banner.

# In the page template
$this->start('head');
?>
    <link rel="stylesheet" href="<?= $this->escape(asset_url('charts.css')) ?>">
<?php $this->end(); ?>

<h1>Revenue</h1>

$this->start('scripts');
?>
    <script>
        window.CHART_ENDPOINT = <?= json_encode(route('api.revenue'), JSON_HEX_TAG | JSON_HEX_APOS | JSON_HEX_QUOT) ?>;
    </script>
<?php $this->end(); ?>

And in the layout, at the point where the region belongs:

<head>
    <title><?= $this->escape($pageTitle ?? 'Orders') ?></title>
    <?= $this->yieldContent() ?>
    <?= $this->section('head') ?>
</head>

<body>
    <main><?= $this->yieldContent() ?></main>
    <?= $this->section('scripts') ?>
</body>

Note the duplicate yieldContent() above is illustrative of a mistake, not a recommendation. The main content region and the named section region are different slots. Put yieldContent() exactly once, in the body, and section('head') in the head. If a page template is rendered without a layout, every section() call must tolerate a missing section — check what your patch release returns and handle the empty case, because an unhandled one is a fatal error on exactly the pages that forgot a layout.

A layout that is itself a template has a practical consequence worth stating: it receives the page’s variables, so it must tolerate their absence when another page uses it. A layout that assumes $user is set will fatal on the login page, which is the one page that has no user.

Pass layout-wide data explicitly. Build a small array of the handful of values every layout needs — the current user, the locale, the navigation entries — and merge it into the page’s data in the controller. This makes the layout’s dependencies visible at the one place they can be satisfied, and it means a missing value is a controller bug with a stack trace rather than a template bug with a fatal on line 41 of a layout.

9.3 Partials and includes

Extracting repeated markup, the rules that keep a partial free of hidden dependencies, and when a partial is the wrong abstraction.

A partial is a template included from another template, rendered with its own data array and returning a string rather than being written directly to the output.

# In a page or another partial
<?= $this->partial('partials/order-row', [
    'order'     => $order,
    'canEdit'  => $canEdit,
    'highlight' => $highlightId === $order->id(),
]) ?>

# resources/views/partials/order-row.php
<?php
/** @var Order $order  @var bool $canEdit  @var bool $highlight */
?>
<tr class="<?= $highlight ? 'row--highlight' : '' ?>">
    <td><?= $this->escape($order->id()) ?></td>
    <td><?= $this->escape($order->status()->value) ?></td>
    <td><?php if ($canEdit): ?>
        <a href="<?= $this->escape(route('orders.edit', ['id' => $order->id()])) ?>">Edit</a>
    <?php endif; ?></td>
</tr>

A partial that keeps its own data array has an important property: it is testable in isolation. Rendering one partial with a synthetic domain object and asserting the output is a fast, valuable test that catches escaping regressions before they reach a page.

A partial must not perform a query. The rule from chapter 1.5 applies with more force here, because a partial is called from inside a loop: one query in a row partial becomes N queries for N rows, and the page’s query count grows with its data rather than staying constant. If a partial needs a related record, either pass it in, or — if the relation is genuinely one-per-row and you cannot batch it — accept the cost deliberately and record why in a comment.

There is also an inclusion trap specific to this design: a partial that includes another partial directly, rather than through the context, may not receive the rendering context and will fail on $this. Prefer one composition mechanism consistently. If your patch release provides partial(), use it everywhere rather than mixing it with raw include.

9.4 Escaping: the default and the exceptions

Context-sensitive escaping, where the default is text, and the small set of cases where raw output is legitimate.

Escaping is not one operation. The transformation that makes a value safe inside a text node is not the one that makes it safe inside an attribute, a URL, a stylesheet, or a script. A single escape() call is therefore a claim about context, and the context is what you must be able to name.

// Text node. htmlspecialchars with ENT_QUOTES covers it.
<p><?= $this->escape($comment->body()) ?></p>

// Attribute value. Same escaping, but the surrounding quotes must be
// real attribute quotes — never unquoted.
<div class="<?= $this->escape($classList) ?>">

// URL. Percent-encode, and verify the scheme. Escaping alone permits
// javascript:alert(1) in an href.
<a href="<?= $this->escapeUrl($user->website()) ?>">site</a>

// JavaScript. json_encode with the hex flags stops </script> and
// quote characters from terminating the surrounding context.
<script>
    const cfg = <?= json_encode($config, JSON_HEX_TAG | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_HEX_AMP) ?>;
</script>

// CSS. Do not build CSS from input at all. Use a class from a
// fixed set; if you must interpolate, escape for CSS, not for HTML.
<div class="bar bar--<?= $this->escape($bucket) ?>">

The URL case is where the standard guidance is insufficient. htmlspecialchars() on a URL leaves javascript: and data: intact, because they contain no characters requiring escaping. If any user-supplied value ends up in an href or src, check the scheme against an allow-list first. A stored link to javascript:alert(document.cookie) is a complete account compromise on click, and it is invisible in a view of the rendered HTML.

Raw output is legitimate in exactly three situations, and each requires knowing the provenance:

SituationRequirement
Markup you wroteIt is a literal in the template. If it is not a literal, it is not a safe case
Markup sanitised at write timeA sanitiser ran on it, the sanitiser is configured to your policy, and the raw form never reaches a context it was not sanitised for
Serialised structured dataPassed through json_encode with the hex flags, inside a script element or a data attribute

Raw HTML from user content is the one that requires the most care, and the recommendation is to keep the sanitisation and the storage together:

// At write time, once, with a known policy and a known library version.
$clean = HtmlSanitizer::sanitize($submitted, [
    'allowed_tags'    => ['p', 'br', 'strong', 'em', 'code', 'ul', 'ol', 'li'],
    'allowed_attributes' => [],   // none, including no href and no style
]);

$comment = new Comment($author, $clean);   // store the clean form, not the raw form

Sanitising at read time is a trap. If the stored value is raw and every render sanitises it, then a change to your sanitiser policy silently reinterprets historical data, and any render path that forgot to sanitise becomes an injection point. Storing the sanitised form means one code path, one policy, and a database whose contents are already safe for their only intended use. If you need the original for any reason — an audit trail, an editorial re-render — store it in a separate, never-rendered location.

Two automatic checks are worth adding to any Leaf application, because escaping is a property of a diff and not of a reviewer’s memory:

# Fail the build on raw output of a variable that is not on the allow-list.
grep -rnE "<\\?=\\s*\\\$" resources/views/ \
  | grep -vE "escape\(|json_encode\(|asset\(|route\(|csrf_field\(|old\(" \
  | grep -vE "^\S+:\s*//"

Chapter 18 develops this into a proper check with an explicit allow-list, and explains why a grep is a useful backstop but not a substitute for context-sensitive output encoding.

9.5 Compiled templates and the filesystem

Where Leaf caches compiled templates, and the two filesystem permissions that separate a working deployment from a broken one.

Templates are plain PHP, so nothing strictly needs compiling. Leaf may still cache resolved or compiled output depending on your configuration and version; treat the cache directory as required rather than optional and configure it deliberately.

# config: a writable directory outside the document root
'templates.cache' => $env('APP_ENV') === 'production',
'templates.path' => __DIR__ . '/../var/cache/templating',

# Create it once, at deploy time — not at runtime.
mkdir -p var/cache/templating
chmod 775 var/cache/templating
chown -R deploy:www-data var/cache

Do not make the web user the owner of the deployment. The classic small-hosting compromise is exactly this: the application runs as a user who can write its own source, so any file-write vulnerability becomes remote code execution immediately, and a compromised dependency can rewrite every file it can reach. Deploy as one user, serve as another, and grant the serving user write access to the cache directory alone. On a shared host you may not have this choice, which is a limitation of that environment rather than a configuration to work around.

Two filesystem permissions cause the majority of Leaf deployment failures, and both present as a 500 with an unhelpful message:

DirectoryRequiredSymptom when wrong
var/cache/Writable by the serving user"Failed to write cache file" or a fatal on first render
storage/Writable by the serving userSession write failure; every login appears to succeed and then forgets
resources/views/Readable, and never writable, by the serving userNothing — until an upload or a template bug writes through it
public/assets/Readable; writable only by the deploy stepStatic files served as empty or 404

Smoke-test these at deploy time, not at first use. A single unauthenticated request to a route that renders a layout and writes a session will exercise the cache directory, the session directory, the template directory, and the autoloader in one go. Add it to your deploy script as a smoke test, and a permission problem surfaces during the deploy rather than on the first customer request.

Finally, keep templates free of anything that is not presentation. The strongest enforcement is structural: templates live in their own directory that nothing else writes to, receive a data array as their only input, and have no mechanism to reach a service. If a template needs a computed value, the controller computes it. This is the constraint from chapter 1.5 restated as a filesystem property, which is far easier to enforce than a code review.

10.1 The form request lifecycle

Six steps from the empty form to the successful redirect, and which component owns each.

A form submission is the one HTTP flow where the server’s failure modes are visible to the user, and the lifecycle below is the sequence that makes it manageable.

StepActionOwner
1Render the form with a CSRF token and values from the modelView
2Client submits, including the tokenBrowser
3Verify the token before anything else touches the inputCSRF middleware
4Validate and coerce; on failure redirect back with input and errorsForm request / validator
5On success, perform the action and redirectController
6Read and clear the flash data on the next renderView

Step 3 before step 4 is not a stylistic preference. A validation routine that echoes an invalid value into a message is, on its own, a reflected cross-site scripting vector, and the token is what stops a third party from causing that request at all.

# The form view
<form method="post" action="<?= $this->escape(route('orders.store')) ?>">
    <?= $this->csrfField() ?>

    <label for="title">Title</label>
    <input
        type="text"
        id="title"
        name="title"
        value="<?= $this->escape(old('title', $order->title())) ?>"
        <?= $errors->has('title') ? 'aria-invalid="true"' : '' ?>
    >
    <?= $errors->first('title') ?>

    <button type="submit">Save</button>
</form>

Always render a token, even for forms whose action looks harmless. The cost of an unnecessary token is one hidden field. The cost of a missing one on a rarely-used form is a vulnerability that a scanner finds and an attacker exploits, on the one endpoint you never tested manually.

10.2 CSRF tokens: generation and verification

The synchroniser token pattern, the comparison that must be constant-time, and why the cookie flags matter even when the token is present.

The defence is a per-session secret that the attacker cannot read and therefore cannot include in their forged request. A token is generated once per session and echoed in every form.

// Generation: once per session, lazily.
$token = $_SESSION['_csrf'] ??= bin2hex(random_bytes(32));

// Rendering.
<input type="hidden" name="_token" value="<?= $token ?>">

// For AJAX, expose it in a header rather than parsing the DOM.
<meta name="csrf-token" content="<?= $token ?>">

Verification compares the submitted value against the session value. Two details are non-negotiable:

<?php

final class VerifyCsrfToken
{
    public function before(Request $request): ?Response
    {
        // 1. Only state-changing verbs need verification. A GET must
        //    never mutate state, so it needs no token.
        if (in_array($request->method(), ['GET', 'HEAD', 'OPTIONS'], true)) {
            return null;
        }

        $expected = $_SESSION['_csrf'] ?? null;
        $given    = $request->input('_token') ?? $request->header('X-CSRF-Token');

        // 2. Constant-time comparison. A short-circuiting === leaks the
        //    token one character at a time to a patient attacker, and
        //    the whole token is 64 hex characters.
        $valid = is_string($given)
            && is_string($expected)
            && hash_equals($expected, $given);

        if (!$valid) {
            // 3. 419, not 403. The request was well-formed and
            //    authenticated, but the token did not validate.
            //    This lets a client distinguish "stale form" from
            //    "you are not allowed to do this".
            if ($request->wantsJson()) {
                return response()->json(
                    ['error' => 'csrf_token_mismatch'],
                    status: 419,
                );
            }

            return response()->redirect(route('session.expired'), 419);
        }

        return null;
    }
}

A token alone is not sufficient, and cookie flags are the reason. SameSite=Lax already blocks the token from being sent on cross-site POSTs in every current browser, which makes CSRF much harder to exploit even if a token check fails. It does not make the token redundant: an older browser without SameSite support, a subdomain you do not control, and a subdomain takeover are all realistic paths to a working exploit. Use both, and treat the token as the primary control with the cookie flags as defence in depth. Chapter 12 covers the flags in full.

Rotating the token at the right moments closes the session-fixation and token-reuse windows:

MomentActionReason
On loginRegenerate the session id and the tokenPrevents fixation, and invalidates tokens minted before authentication
On logoutRegenerate bothPrevents a token from surviving the session it was bound to
On privilege changeRegenerate bothA token issued to a lower-privilege user should not authorise a higher-privilege action
After N minutes or M requestsRegenerate the session id, optionally the tokenLimits the value of a captured token

Keep the token constant within a session unless something security-relevant changed. Regenerating on every request breaks the back button, multi-tab workflows, and any page that holds two forms open — the user submits the second one and receives a 419 with no way to recover except reloading. Rotate on the events in the table above, not on a timer shorter than a working session.

A related token worth having if you serve any HTML on a different origin: a SameSite value of Strict on the session cookie when you have no legitimate cross-site navigation requirement, and a separate short-lived token exchange for the one case you do. The default recommendation for a server-rendered application with no cross-origin surface is SameSite=Lax, which permits top-level GET navigation while blocking cross-site POST.

10.3 Repopulating a failed form

Flashing input and errors across a redirect, and the per-field allow-list that prevents a hidden field from being repopulated.

On validation failure you must show the user what they typed. Doing that in the response body rather than after a redirect breaks the back button and produces a form that cannot be reloaded, and it also means the errors are lost on refresh. The redirect-plus-flash pattern solves all three.

// The controller, on failure. Note the explicit field list.
if (!$validator->passes()) {
    return back()
        ->withInput($request->body())     // everything, filtered below
        ->withErrors($validator->errors());
}

// where "back" is the redirect to the referrer, falling back to a named route
// when no referrer is present.
return back()->withInput($request->body())->withErrors($errors);

Flashing every submitted field is a vulnerability. The hidden role or account_id that a hostile client added is now sitting in your session, and your template repopulates it into a hidden input — where the next honest submission sends it back and your controller, trusting the field, applies it. Two defences, both required: filter the flashed input through an allow-list of the form’s own field names, and never read an ownership or privilege value from input at all, as established in chapter 4.5.

// The filter. A field that is not a form field never reaches the session.
final class SafeOldInput
{
    /** @var list<string> */
    private array $allowed;

    public function __construct(array $allowedFields)
    {
        $this->allowed = $allowedFields;
    }

    public function filter(array $input): array
    {
        return array_intersect_key($input, array_flip($this->allowed));
    }
}

// In the controller
$safe = (new SafeOldInput(['title', 'description', 'quantity']))->filter($request->body());

return back()->withInput($safe)->withErrors($validator->errors());

File inputs and passwords must never be flashed. A password field’s value is stored in the session, on disk, in a file you have been arguing about permissions for, and is then written back into a form. The exclusion is not optional:

Field typeFlash?Reason
passwordNeverSecret at rest in the session store
fileNeverThe browser cannot repopulate it; the value is a path, not content
Card or bank fieldsNeverRegulatory: never store, never log, never echo
Hidden _tokenYes, or regenerateHarmless, and flashing it avoids a 419 on resubmit
Everything else in the allow-listYesThis is the point of the mechanism

Reading the flashed values back, and the two functions every template needs:

// in the view
value="<?= $this->escape(old('title', $order->title())) ?>"

<?= $this->escape(old('description', '')) ?>

// The one place where ordering matters. old() must prefer the
// flashed value and fall back to the model, never the reverse, or a
// failed submission appears to have had no effect at all.

Clear flash data as soon as it is read, and only then. Flash data lives for exactly one subsequent request. If a page that reads it is loaded twice — a prefetch, a link checker, a bot — the second load sees it already gone, and the user who actually arrives sees an empty form with no error explanation. The standard mitigations are a Cache-Control: no-store header on any page rendering flashed state, and a one-time-use marker if the value is genuinely precious enough to protect.

For select and checkbox groups, repopulating needs slightly more care, because a single flash value does not represent a set:

// Checkbox group: the flashed value is an array; test membership.
$selected = (array) old('tags', $order->tagIds());

<?php foreach ($availableTags as $tag): ?>
    <label>
        <input
            type="checkbox"
            name="tags[]"
            value="<?= $this->escape($tag->id()) ?>"
            <?= in_array($tag->id(), $selected, true) ? 'checked' : '' ?>
        >
        <?= $this->escape($tag->name()) ?>
    </label>
<?php endforeach; ?>

Escape on the way out, and use strict comparison on the way in. in_array($tag->id(), $selected, true) without the third argument does loose comparison, and the consequences are not subtle: '0' and 0 match, 'abc' matches 0 in older PHP, and your default selection silently changes. Every in_array over user-influenced data in this codebase needs the strict flag, and the grep is short.

10.4 Post/redirect/get and flash data

Why the redirect after a successful write matters, the status code to use, and how to carry a confirmation message.

After a successful POST, the server redirects. The alternatives are both worse:

ApproachFailure
Render the page directly after POSTA refresh re-submits. A bookmark to that URL re-submits. A crawler following a link re-submits
Redirect without a status codeA 302 after a POST is followed by most clients with a GET, but the historical intent is ambiguous and some clients repeat the POST
303 See OtherExplicitly instructs a GET. The refresh re-fetches a read-only page. This is the correct code after a state change
// Success: 303 to a read-only page, with a one-shot message.
return redirect()
    ->to(route('orders.show', ['id' => $order->id()]), 303)
    ->with('success', 'Order saved.');

// Failure: also a redirect, so the back button and refresh behave.
return back()->withInput($safe)->withErrors($validator->errors());

The message and the errors are the same mechanism — one-shot session data — which is worth knowing because it means the redirect and the flash are not separable features. If you find yourself wanting to flash something that survives two requests, you are describing application state and should store it properly rather than extending the flash lifetime.

Do not put a success message in a query string. ?success=Order+saved is visible in the address bar, in browser history, in the Referer header sent to every subsequent third-party resource on the page, and in your access logs. Flash data stays server-side, which is also why it cannot be forged by a user crafting a link.

For an API, the equivalent pattern is a status code plus a body, with no redirect at all:

// 201 with the canonical URL in Location. No redirect, no flash.
return response()->json(OrderResource::from($order), status: 201)
    ->header('Location', route('api.orders.show', ['id' => $order->id()]));

10.5 Rendering errors accessibly

The three requirements for usable error display, and why a summary at the top and a message at the field are not redundant.

Error display has three requirements, and satisfying only the first is the usual outcome.

RequirementMechanismWithout it
The user can find the errorsA summary block at the top with links to each fieldA form that looks fine and silently did not save
The user can associate a message with a fieldMessage adjacent to the inputA long list with no indication of which field is which
A screen reader announces the changeA container with role="alert" or aria-live, and aria-invalid plus aria-describedby on the inputThe fix is invisible to anyone not looking at the field
# The summary. Rendered only when there are errors.
<?php if ($errors->any()): ?>
    <div role="alert" tabindex="-1" id="form-errors" class="errors">
        <h2><?= count($errors->all()) ?> thing(s) need your attention</h2>
        <ul>
            <?php foreach ($errors->all() as $field => $messages): ?>
                <li><a href="<?= $this->escape($field) ?>"><?= $this->escape($messages[0]) ?></a></li>
            <?php endforeach; ?>
        </ul>
    </div>
<?php endif; ?>

# The field. The id and aria-describedby must match.
<label for="title">Title</label>
<input
    type="text"
    id="title"
    name="title"
    value="<?= $this->escape(old('title', $order->title())) ?>"
    <?= $errors->has('title') ? 'aria-invalid="true" aria-describedby="title-error"' : '' ?>
>
<?php if ($errors->has('title')): ?>
    <p id="title-error" class="field-error"><?= $this->escape($errors->first('title')) ?></p>
<?php endif; ?>

Writing the error text in terms of the fix rather than the rule is what makes the difference between a form a user can recover from and one they abandon:

Instead ofWrite
"Validation failed for field: email""Enter an email address in the form name@example.com"
"Quantity must be greater than 0""Enter a quantity of at least 1"
"This field is required""Enter a delivery address"
"Invalid date""Enter the date as YYYY-MM-DD"

Never echo a submitted value into an error message without escaping. A message like "The value {value} is not a valid SKU" reflects attacker-controlled content into the page. This is the same class of bug as forgetting to escape a field, but it survives code review more often because the surrounding text looks like a developer-authored string. Route every interpolated value through escape(), and prefer not interpolating at all: naming the rule and the format is nearly always more useful.

One last concern for form handling: the double-submit. Two rapid clicks on a submit button produce two POSTs, and for a non-idempotent action that is two orders. The fix is not a JavaScript disable — the client is untrusted. It is a uniqueness constraint at the point of persistence, or an idempotency key the client generates and the server records, checked for uniqueness inside a transaction.

Documents the validator: where it runs, how rule sets are composed, how messages are produced and localised, how custom and conditional rules are written, and the coercion rules that keep validated data trustworthy.

11.1 Where validation runs and what it guarantees

Three places validation can occur, why only one of them counts, and the guarantee a validated value carries.

Validation can appear in three places, and conflating them is the source of most validation defects.

PlaceExampleEnforcedTrustworthy?
Client, in the browserrequired, type="email"No — trivially bypassedNo. UX only
Server, at the request boundaryA form request or a validator call in the controllerYes, if nothing below re-reads the raw inputYes, if the validated value is the one passed on
Domain, at constructionCents::of(), OrderStatus::from()Yes, and applies to every callerYes, structurally

Client-side validation is a usability feature and nothing else. Every rule enforced only in the browser is unenforced. The correct pattern is a mirror: the same rules expressed in HTML attributes for immediate feedback, and in the server validator as the actual control. Where the two disagree — a client that adds a rule the server lacks — the rule does not exist.

The distinction that matters most in practice: validation establishes the shape of the input, and a domain constructor establishes the rules. A validator that checks "quantity is an integer between 1 and 999" is doing its job. A validator that checks "quantity times price does not exceed the credit limit" is doing a domain rule’s job, and doing it in the one place where it can be bypassed — by the other four code paths that create orders.

// Correct division of labour.
//  Boundary: is this a well-formed integer in range?
$quantity = $validator->integer()->min(1)->max(999)->validate('quantity', $data['quantity'] ?? null);

//  Domain: may this account afford it?
$policy->assertWithinLimit($exposure, Cents::of($unitPrice)->times($quantity));

What a validated value guarantees, and the two ways that guarantee is voided:

GuaranteeVoided by
It has the declared typePassing the raw input array to the action instead of the validated one
It satisfies its rulesMutating it afterwards, or validating a copy and using the original
Nothing else was requiredNothing — but note the converse: an unlisted field is not validated and should be ignored
// The bug. Validated, then discarded.
$validator->validate($data);
$action($data);                 // ← the unvalidated array

// The bug. A default applied after validation, bypassing a rule.
$status = $data['status'] ?? 'active';   // 'anything' passes if status was not required

// Correct. The validated output is a separate, typed value.
$command = new CreateOrder(
    accountId: new AccountId($validated['account_id']),
    title:     $validated['title'],
    quantity:  $validated['quantity'],
);

Prefer a validated DTO to an array. An array passes its validation and then loses the guarantee the moment it is copied, merged, or passed to a function that documents no contract. A readonly class with typed constructor properties carries the guarantee in the type system, and the compiler will reject a missing or wrongly-typed field at the point of construction rather than three layers deeper.

11.2 Rule sets and composition

The built-in rule surface, how rules compose into reusable sets, and the two composition errors to avoid.

Leaf ships a validator. Read the shipped implementation for your patch release before relying on a specific method name; the pattern below is the standard fluent surface and the rules are the conventional set.

$v = validator();

$v->required()->email()->maxLength(254);
$v->required()->integer()->min(1)->max(999);
$v->required()->string()->minLength(3)->maxLength(120);
$v->optional()->inArray(['draft', 'published', 'archived']);
$v->required()->confirmed();      // pairs with a 'password_confirmation' field
$v->required()->date()->format('Y-m-d')->afterOrEqual('today');

$v->validate($data);
$v->passes();
$v->errors();      // ['title' => ['Title is required.'], ...]

Rules apply to the value most recently named, or to a field named explicitly. The two composition mistakes worth naming:

MistakeSymptomCorrection
required() after another ruleAn empty value passes email() because a non-value is not a valuePut required() first, and make optional fields explicitly optional
Rules applied to the whole array rather than a fieldErrors reported against a field name that does not existName the field per rule, or use one validator instance per field

Reusable rule sets are the mechanism that stops two forms drifting apart:

final class Rules
{
    // A named set, defined once. The single source of truth for
    // what a valid email address means in this application.
    public static function email(): array
    {
        return ['required', 'email', 'maxLength'];
    }

    public static function moneyInCents(): array
    {
        return ['required', 'integer', 'min'];
    }

    public static function slug(): array
    {
        return ['required', 'string', 'regex'];
    }
}

// Applied to a whole form, as a set of field => rules.
$rules = [
    'email'        => Rules::email(),
    'unit_price'  => Rules::moneyInCents(),
    'slug'        => Rules::slug(),
    'notes'       => ['optional', 'string', 'maxLength'],
];

Express the constraint, not the format. A rule set called slug() documents intent; a rule set called maxLength60RegexLowercaseHyphen() documents implementation and becomes wrong the moment the requirement changes. Naming the constraint means a reader can check it against the product requirement, and a change is a change to one named set rather than a hunt through every form.

Uniqueness and existence are database questions, and this is where a validator’s responsibility ends and a repository’s begins:

$v->validate($data);

if ($v->passes()) {
    // Shape is now known good. Ask the database the questions
    // only it can answer.
    if ($this->orders->slugExists($data['slug'])) {
        $v->addError('slug', 'slug', 'That address is already in use.');
    }
}

if (!$v->passes()) {
    return back()->withInput($safe)->withErrors($v->errors());
}

Uniqueness checked outside the transaction is a race. Two simultaneous submissions both find the slug free, and both insert. The validation gives a good error message for the common case and no guarantee at all under concurrency. The guarantee comes from a unique index plus catching the duplicate-key exception, as in chapter 7.5. Treat the validator check as user experience and the constraint as correctness — and never present the validator check as the reason the operation is safe.

11.3 Messages, attributes, and localisation

Customising the text of a rule, supplying attribute names so messages read as English, and the two-message approach that keeps them consistent.

Default messages are generated from a rule name and an attribute label, so an uncustomised application produces text like "the email field must be a valid email address". Customising means supplying both the attribute label and, where the default is wrong, the message.

$v = validator([
    // Attribute labels. Without these, messages use the raw
    // field name and read as "the email_address must ...".
    'attributes' => [
        'email'       => 'email address',
        'unit_price' => 'unit price',
        'password'    => 'password',
    ],
]);

// Message overrides, keyed by rule. Placeholders are the framework's;
// verify the exact set for your patch release.
$v->messages([
    'required'  => ':attribute is required',
    'email'     => ':attribute must be a valid email address',
    'maxLength' => ':attribute may not be longer than :max characters',
    'min'       => ':attribute must be at least :min',
]);

// Per-field overrides, for the cases the generic text cannot cover.
$v->messages([
    'slug.unique'      => 'That address is already in use.',
    'password.confirmed' => 'The two passwords do not match.',
]);

That makes the set auditable, translatable, and consistent, and it means a copywriter can improve the wording without a deployment. The rule from section 10.5 — describe the fix, not the rule — is a constraint on that file, not on each call site.

Clients branch on the code, and a validator that returns 200 with an error body forces every consumer to inspect the body to learn whether the request worked.

11.4 Custom rules and conditional requirements

Writing a rule that is a domain predicate, expressing requirements that depend on other fields, and keeping both out of the generic layer.

A custom rule is needed when a constraint is not expressible in the built-in set. The discipline is to keep the rule itself in the domain, so that it can be tested and reused outside HTTP.

# app/Domain/Order/Sku.php — the rule as a value object, no validator dependency.
final readonly class Sku
{
    private const PATTERN = '/^[A-Z]{3}-[0-9]{4}$/';

    private function __construct(public string $value) {}

    public static function parse(string $input): self
    {
        $normalised = strtoupper(trim($input));

        if (preg_match(self::PATTERN, $normalised) !== 1) {
            throw new InvalidSku($input);
        }

        return new self($normalised);
    }

    public static function isValid(mixed $input): bool
    {
        return is_string($input) && preg_match(self::PATTERN, strtoupper(trim($input))) === 1;
    }
}

# The validator rule is a thin adapter over it.
$v->addRule('sku', fn(mixed $value): bool => Sku::isValid($value), 'SKU must look like ABC-1234');

Look for the normalisation the rule implies. The SKU example trims and upper-cases before testing, which means the value the application stores and the value the user typed differ. That is correct and it is worth being explicit about: a validation rule that normalises silently is doing two jobs. If the stored form differs from the submitted form, say so in the code and return the normalised value, rather than validating one thing and persisting another.

Conditional requirements — fields required only when another field has a particular value — are where validators are most often misused. The pattern that keeps the rule testable:

final readonly class ShippingRequirement
{
    public function __construct(private array $digitalOnlyStatuses) {}

    public function isShippingAddressRequired(array $data): bool
    {
        $status = $data['fulfilment'] ?? null;

        // The rule is stated once, in a named object, and both the
        // validator and the domain service can ask it.
        return !in_array($status, $this->digitalOnlyStatuses, true);
    }
}

// In the controller
if ($requirement->isShippingAddressRequired($data)) {
    $v->required('shipping_address.line1', 'Delivery address is required for this order');
    $v->required('shipping_address.postcode', 'Postcode is required for this order');
} else {
    $v->optional()->array('shipping_address');
}

A conditional rule in the validator is a rule someone will forget. It applies to this form, on this path, in this branch. The same business rule will also be enforced somewhere else — in a service, in a scheduled job, in an admin tool — and that place has no conditional rule to remind it. Write the conditional in the validator for the form’s convenience, and write it in the domain object for correctness, and let the second one be the authority. Where the two can disagree, add a test that asserts they do not.

Cross-field rules that genuinely need a form-wide view — passwords matching, an end date after a start date, a quantity that is the sum of a breakdown — belong in a rule that takes the whole data array rather than a single value:

$v->addRule(
    'date_range',
    fn(array $data): bool =>
        !isset($data['ends_at'])
        || !isset($data['starts_at'])
        || strtotime($data['ends_at']) >= strtotime($data['starts_at']),
    'The end date must not be before the start date',
);

11.5 Coercion, normalisation, and re-validation

Turning submitted strings into typed values, the transformations that must happen before rules run, and the double-validation trap.

A form submits strings. Your domain needs integers, decimals, dates, and enums. The transformation between them is not optional, and doing it in the wrong order makes rules lie.

$data = $request->body();

// 1. Trim. A required field containing only spaces is present in the
//    request and absent from the domain. Normalise first, or every
//    length and required rule is measuring the wrong thing.
$data = array_map(
    static fn(mixed $v) => is_string($v) ? trim($v) : $v,
    $data,
);

// 2. Empty string is not a value. Convert it to null so 'optional'
//    means what the developer thinks it means.
$data = array_map(
    static fn(mixed $v) => $v === '' ? null : $v,
    $data,
);

// 3. Validate the normalised values.
$v->validate($data);

if (!$v->passes()) {
    return back()->withInput($data)->withErrors($v->errors());
}

// 4. Only now convert to types. A failed conversion here is a
//    programming or normalisation error, not a user error, so it
//    should not be reported as a field error.
$quantity = (int) $data['quantity'];
$notes    = $data['notes'];
$status   = OrderStatus::from((string) $data['status']);

Do not cast before validating. (int) 'abc' is 0, so a quantity of "abc" casts to zero, and if the rule is min:0 it passes. Then the application stores zero and nobody notices. Validate the raw normalised form against the type rule, and only cast once the value is known to be of the right shape. This single ordering error is the most common cause of a validation layer that appears to work and does not.

Date handling deserves separate mention, because it is where silently wrong values come from:

// Require an explicit format. Do not accept 'next tuesday' or '03/04'.
$v->required()->date()->format('Y-m-d');

// Parse strictly, and fail loudly on a value that slips through.
try {
    $placedAt = DateTimeImmutable::createFromFormat(
        '!Y-m-d',          // the '!' resets unparsed fields to the epoch
        $data['placed_at'],
        new DateTimeZone($config['timezone']),
    ) ?: throw new InvalidDate($data['placed_at']);
} catch (ValueError) {
    return back()->withInput($data)->withErrors($v->addError('placed_at', 'date', 'date'));
}

// The epoch prefix is the trap. createFromFormat('Y-m-d', '2026-03-01')
// fills unparsed time fields from "now", and createFromFormat with a
// two-digit year silently resolves 1968 versus 2068 by a rule
// nobody remembers.

Store and compute in UTC; convert only for display. A date-only value has no time and no zone, and the correct representation depends on whether it is a customer’s birthday or a shipment date. The defensible approach is to store the value the domain actually is — a date as a date column, an instant as UTC in a timestamp — and to attach the user’s zone only at the edges. A datetime column holding local time is a bug that surfaces twice a year, at exactly the moment it is most expensive to diagnose.

Finally, the double-validation trap. If you validate a normalised copy and then hand the original array to the action, the guarantee is void, as section 11.1 noted. Building the domain object from the validated data closes it:

// The validated values, and only those, reach the domain.
$command = new CreateOrder(
    accountId: new AccountId($data['account_id']),
    title:     $data['title'],
    quantity:  (int) $data['quantity'],
    placedAt:  $placedAt,
);

($this->placeOrder)($command);

12.1 Session lifecycle and the middleware

Four moments in a session’s life, and the rules that apply at each.

A session is a server-side store keyed by a cookie containing nothing but an identifier. Everything the framework provides is convenience around that arrangement; the security properties come from the identifier, not the data.

MomentActionWhy
Before any outputStart the sessionOnce headers are sent, Set-Cookie is impossible
After privilege changeRegenerate the idPrevents fixation
After a period of inactivityExpire and destroyBounds the value of a stolen cookie
On logoutClear the data, then destroyClearing alone leaves a valid id with no data — harmless but untidy; destroying revokes it
# The middleware that owns the lifecycle. It must be global and early,
# because both the session layer and the authentication layer depend on it.
final class StartSession
{
    public function before(Request $request, callable $next): Response
    {
        // A session cookie has no business on an API response, and
        // starting one per stateless request is pure overhead.
        if ($request->isApi()) {
            return $next($request);
        }

        session()->start();

        $response = $next($request);

        session()->save();

        return $response;
    }
}

Reading and writing, which should go through the session layer rather than the superglobal so that a test can substitute one:

// Write
session()->set('user_id', $user->id()->toString());
session()->set('intended_url', $request->url());

// Read, with a default
$userId = session()->get('user_id');

// Remove one key
session()->remove('intended_url');

// Read and delete in one step — the correct pattern for flash data
// and for one-time tokens, so a second read cannot succeed.
$token = session()->pull('password_reset_token');

// Flash: survives exactly one further request
session()->flash('success', 'Order saved.');
$message = session()->get('success');   // read it, then it is gone

Nothing sensitive belongs in the session. The session store is a file in a directory you have had to make writable, or a row in a table. It is not encrypted, it is not access-controlled with the care an application database receives, and it persists for longer than a request. Store the user identifier and the flags; fetch everything else from the database on demand. A session containing a full user object with a password hash and personal details is a session file that becomes a data breach the moment a directory listing is misconfigured.

Prefer identifiers to objects, always. Storing user_id and loading the user on each request costs one indexed lookup and buys you the fact that a suspended or deleted account takes effect immediately, rather than at the next login. Storing the user object in the session means a change to their permissions or their status does not apply until the session expires, which is a real window of over-permissioned access.

12.2 Cookie flags and what each prevents

The three flags that carry the security properties, the exact configuration that sets them, and the interaction between SameSite and the CSRF token.

Three flags matter, and all three must be set explicitly because PHP’s defaults are permissive or absent.

# The configuration. These must be set before the session starts — PHP
# reads them at start time, so setting them afterwards has no effect
# on the cookie this request is about to send.
session()->configure([
    'cookie_name'     => 'orders_session',
    'cookie_path'     => '/',
    'cookie_domain'   => '',        // host-only: safer than a shared parent domain
    'cookie_secure'   => true,             // HTTPS only
    'cookie_httponly' => true,             // not readable by JS
    'cookie_samesite' => 'Lax',         // permits top-level GET navigation, blocks cross-site POST
    'use_strict_mode' => true,            // reject uninitialised ids — see section 12.3
    'use_only_cookies' => true,           // never accept an id from the query string
    'gc_maxlifetime'   => 7200,           // server-side expiry, in seconds
]);

Set the flags before session_start(), and verify what is actually on the wire. The failure mode is subtle: the session data works, the login works, and the cookie is sent without Secure or HttpOnly because the configuration ran after the session had already started. Assert the flag on the Set-Cookie header in a test rather than trusting the configuration, because a proxy, a PHP build, or a framework default can override what you wrote. One assertion on a header catches all three flags at once.

# Verify the flags on a real response, in a feature test.
$response = $this->get('/login');

$cookie = collect($response->headers->getSetCookie())
    ->firstWhere(fn($c) => str_starts_with($c, 'orders_session='));

$this->assertStringContainsString('HttpOnly', $cookie);
$this->assertStringContainsString('Secure', $cookie);
$this->assertStringContainsString('SameSite=Lax', $cookie);

Choosing a SameSite value, and the one case that complicates it:

ValueSends onUse when
StrictSame-site requests onlyNo legitimate cross-site entry point at all. A user following a link into your app from elsewhere lands logged out
LaxSame-site, plus top-level GET navigationThe default recommendation for a server-rendered app: an emailed link works, cross-site POST does not
NoneEverything, and requires SecureOnly when another origin genuinely needs your cookie — a subdomain app, or a payment provider redirect

The cost of Strict is real and easy to discover late. A user who clicks a link in an email or a chat is not sending a same-site request, so with Strict their session cookie is withheld and they appear logged out on the one screen you spent effort linking them to. Lax solves that case while still blocking the POST vector that CSRF actually exploits. Choose Strict only if you have measured that no such navigation exists, and document that assumption in the configuration.

A separate cookie for a purpose other than the session, with its own rules:

// A long-lived "remember me" token. Not the session id: a distinct,
// revocable, single-purpose credential.
$response->cookie(
    name:     'remember_token',
    value:    $selector . ':' . $validatorHash,   // see below
    expire:   time() + (60 * 60 * 24 * 30),
    path:     '/login',        // narrow: sent only where it is needed
    secure:   true,
    httpOnly: true,
    sameSite: 'Lax',
);

Never set a cookie’s path to '/' when its purpose is narrow. A path=/ cookie is attached to every request to the host, which means it is present in the access logs of every route, included in the request context of any middleware that logs headers, and subject to being sent to third-party resources on the same host. Setting path=/login limits the token to the one endpoint that consumes it, which is both narrower exposure and a smaller blast radius.

12.3 Regeneration and fixation

Session fixation, the attack it enables, the two mitigations, and the strict-mode setting that catches the other half.

Session fixation works like this: the attacker obtains a valid session id, gives it to the victim, and waits. The victim authenticates, and because the id never changed, the attacker’s copy of that id is now an authenticated session.

// The mitigation. Call this immediately after the privilege change,
// before anything else touches the session.
session()->regenerate(deleteOldSession: true);
Privilege changeRegenerate?Also regenerate the CSRF token?
LoginYes, alwaysYes
LogoutYes, and destroy the dataYes
Password changeYesYes
Elevation, such as passing a second factorYesYes
Adding a payment method or changing an emailYesYes
Ordinary navigationNoNo

Regenerate with the old session deleted, and do it before writing new data. regenerate(false) leaves the old id valid, which means an attacker holding it keeps a session that your own code has not revoked. And if you regenerate after setting user_id in the old session, there is a window in which the data is in one session and the id in another. Regenerate first, then write.

The second half of the defence is use_strict_mode, which rejects any session id the server did not issue:

// With strict mode on, PHP ignores an incoming id that matches no
// existing session file and issues a fresh one. An attacker cannot
// plant a chosen id and have it accepted.
session()->configure(['use_strict_mode' => true]);

// And the token cookie must never be read from the URL. PHP will
// accept ?PHPSESSID=... unless you forbid it, and ids in URLs end
// up in logs, in the Referer header, and in browser history.
session()->configure(['use_only_cookies' => true]);

// Defence in depth at the server: refuse the parameter outright.
if (isset($_GET['PHPSESSID']) || isset($_COOKIE['PHPSESSID'])) {
    return response()->json(['error' => 'session_id_in_url'], status: 400);
}

Absolute expiry is the remaining piece. An idle timeout alone is not enough, because a session that is used continuously never idles out:

final class ExpireIdleSessions
{
    public function before(Request $request): ?Response
    {
        $lastSeen = (int) (session()->get('_last_seen') ?? 0);
        $now      = time();

        // Idle timeout: 30 minutes of no activity.
        if ($lastSeen > 0 && ($now - $lastSeen) > 1800) {
            session()->invalidate();
            session()->regenerate(true);

            return $request->wantsJson()
                ? response()->json(['error' => 'session_expired'], status: 401)
                : response()->redirect(route('login'), 302);
        }

        // Absolute lifetime: 12 hours regardless of activity, so a
        // session cannot be held open indefinitely.
        $startedAt = (int) (session()->get('_started_at') ?? 0);

        if ($startedAt === 0) {
            session()->set('_started_at', $now);
        } elseif (($now - $startedAt) > 43200) {
            session()->invalidate();
            session()->regenerate(true);
            ...
        }

        session()->set('_last_seen', $now);

        return null;
    }
}

Regenerate, then write — always in that order. Regeneration changes the identifier; the data lives under whatever identifier is current when it is written. Doing it the other way round leaves the new data in a session the client is no longer presenting, and the user is logged out by a mechanism whose cause is invisible in the log.

12.4 Storage backends and their trade-offs

Where sessions are stored, the properties each backend provides, and the decision that determines which one you need.

PHP’s default is a file per session in a temporary directory. That works, and it fails in specific ways at specific scales. The decision is driven by two questions: how many concurrent sessions, and how many application servers.

BackendGood forFails at
FilesOne server, modest traffic, no shared hostingMany concurrent sessions on one host: a directory with a hundred thousand files is slow to scan and slow to garbage-collect
DatabaseOne server, and you already have a databaseWrite amplification on every request, and the same connection is now a shared bottleneck

Stateless, signed cookieRead-heavy, no server-side state, horizontal scaleAnything larger than a few kilobytes, and anything requiring immediate revocation
# A Redis-backed handler. Implement the SessionHandlerInterface, or use a
# package that does; the interface is the whole contract.
final class RedisSessionHandler implements SessionHandlerInterface
{
    public function __construct(
        private Redis $redis,
        private int $ttl = 7200,
    ) {}

    public function open(string $path, string $name): bool
    {
        return true;
    }

    public function close(): bool
    {
        return true;
    }

    public function read(string $id): string|false
    {
        $data = $this->redis->get("sess:{$id}");

        return $data === false ? '' : (string) $data;
    }

    public function write(string $id, string $data): bool
    {
        // The TTL is the expiry. It is set on every write, which is
        // what makes it an idle timeout rather than an absolute one.
        $this->redis->setex("sess:{$id}", $this->ttl, $data);

        return true;
    }

    public function destroy(string $id): bool
    {
        return $this->redis->del("sess:{$id}") >= 0;
    }

    public function gc(int $max_lifetime): int|false
    {
        // Nothing to collect: the keyspace notification or the TTL
        // does it. Returning 0 tells PHP there is no garbage.
        return 0;
    }
}

session()->setHandler(new RedisSessionHandler($redis));

A Redis session store must be on the same network boundary as your application, with authentication and TLS. A session store is equivalent to a credential store: anyone who can read it holds every logged-in user’s session. An unauthenticated Redis on a shared network is a full account takeover of every user whose session is resident, and it is one of the most common misconfigurations in this layer. If you choose Redis, restrict the bind address, require a password, and decide explicitly whether the connection is encrypted.

With multiple application servers, file sessions are simply wrong: a request that lands on server B cannot see a session written by server A, and the user appears logged out at random. The options are a shared backend, or sticky sessions — and sticky sessions introduce their own failure mode, because a server restart or a rebalance logs out every user pinned to that instance. For an application expected to scale horizontally, choose the shared backend from the start rather than discovering the constraint during an incident.

The stateless option deserves a mention because it inverts the usual trade-off. Signing the session data into the cookie removes the store entirely, which is the fastest possible implementation and scales without limit. The costs are a 4 KB practical ceiling per cookie, and no revocation: a signed cookie remains valid until it expires, so a forced logout cannot take effect and a permission change does not apply until expiry. A hybrid is common and works well: the signed cookie carries the identity, and a Redis entry keyed by the identifier allows immediate revocation.

12.5 Concurrency, locking, and flash data lifetime

The lock file behaviour that serialises concurrent requests on one session, and the failure it causes in a browser.

PHP’s file session handler locks the session file for the duration of the request. Two concurrent requests carrying the same session cookie are therefore serialised: the second waits for the first to finish. This is correct — it prevents one request overwriting another’s session data — and it is a real latency cost under load.

// Releasing the lock early. A long-running request that no longer needs
// the session must not hold it while it talks to a slow API.
session()->writeClose();

$report = $this->expensiveExternalCall();   // now holds no lock

A long request holding a session lock makes the other tab of the same browser appear to hang. The mechanism is worth understanding because it is reported as "the site freezes when I have two tabs open". Request A holds the lock while it does slow work; request B from the second tab blocks until A completes, and if A takes thirty seconds the user sees a spinner. Two mitigations, both worth having: release the lock as soon as the session has been read and any values written, and set a low max_execution_time on handlers that make slow external calls.

Flash data lifetime is a direct consequence of the read path, and the two failure modes are both real:

ImplementationFailure
Read the flash, delete the flashA prefetch, a link checker, or a bot consumes it before the user arrives
Delete the flash at the end of the requestA page that renders in two passes reads a value that has already gone

The workable pattern, and the header that supports it:

// Read-with-deletion, plus a header telling caches and prefetchers to
// leave the page alone.
$success = session()->pull('success');

return response()->view('orders/show', $data)
    ->header('Cache-Control', 'no-store, private', replace: true);

One final item, which belongs here because it is a session-layer concern rather than an auth one: what to do when the session store is unreachable. If the Redis connection fails mid-request, a naive handler returns false from read() and the application continues with an empty session — which logs every user out silently and looks like a mass credential problem. Return an error that the pipeline converts to a 503 rather than a successful request with no session, so the failure is visible in monitoring instead of appearing as a login page.

13.1 Password storage and verification

The hashing parameters to use, the two functions PHP provides, and the constant-time comparison that verification depends on.

Passwords are stored as a hash with a per-password salt, using a memory-hard algorithm. PHP provides the two you need.

// Verification, using the runtime's own parameters. Never hard-code a cost:
// raising it later must not require re-hashing every user at once.
$hash = password_hash($plain, PASSWORD_DEFAULT);

$ok = password_verify($plain, $hash);

// Re-hash transparently when the cost or algorithm has moved on.
if ($ok && password_needs_rehash($hash, PASSWORD_DEFAULT)) {
    $users->updatePasswordHash($userId, password_hash($plain, PASSWORD_DEFAULT));
}
FunctionAlgorithmUse
password_hash with PASSWORD_DEFAULTCurrently Argon2id where available, else bcryptThe only correct choice. It follows the platform when the default changes
password_hash with PASSWORD_ARGON2IDArgon2id, explicitWhen you want to control memory and time cost explicitly and the platform supports it

Never write your own password hashing. The value of a memory-hard function is entirely in its parameters: the memory cost, the iteration count, and the parallelism. A hand-rolled scheme — even one built on a strong primitive — will get one of those wrong, and the error is invisible until someone measures. password_hash also guarantees forward compatibility: when PHP changes the default algorithm, existing hashes continue to verify and are transparently upgraded on the next successful login.

Argon2 parameters, if you set them explicitly, and the reasoning for each:

$hash = password_hash($plain, PASSWORD_ARGON2ID, [
    'memory_cost' => 65536,   // 64 MB. The main defence against GPU and ASIC
    //                      attack: cost that does not parallelise
    //                      well across memory lanes.
    'time_cost'   => 4,       // passes. Multiplies the total work.
    'threads'     => 1,       // parallelism within one hash. 1 or 2.
]);

Calibrate against your own server, not a benchmark article. The correct memory_cost is the highest value your login endpoint can afford while keeping a good user experience under peak load. Measure it: hash a password, time it, and set the parameter so the hash takes roughly 200 to 400 milliseconds on your slowest production machine. Higher is better for security and worse for availability, and the availability failure mode — the login page timing out under a credential-stuffing attack — is worse for the business than a slightly weaker hash.

Two application-level rules that matter as much as the algorithm:

  • Normalise the input before hashing. A password entered with a trailing space on a mobile keyboard, or a password pasted with a non-breaking space, should still work. Trim the ends, and be explicit that you do — a password with meaningful leading whitespace is rarer than the paste accident it protects.
  • Handle the bcrypt 72-byte limit deliberately. bcrypt ignores anything past 72 bytes. Pre-hashing with SHA-256 before bcrypt avoids the truncation, but changes the semantics, so decide once and apply it uniformly. With PASSWORD_DEFAULT on PHP 8.3 the question largely disappears, since Argon2id has no such limit.

13.2 The login flow and its failure modes

The steps of a secure login, the timing attack that makes naive enumeration possible, and the throttling that limits it.

public function store(Request $request): Response
{
    $email    = mb_strtolower(trim((string) $request->input('email')));
    $password = (string) $request->input('password');

    // 1. Throttle before the database is touched, keyed on the
    //    identifier and on the client address separately.
    $throttle->assertNotLocked($email, $request);

    $user = $this->users->findByEmail($email);

    // 2. Hash against a dummy value when the user does not exist, so
    //    the response time does not reveal whether the account is real.
    //    Without this, "no such user" returns in 5ms and "wrong
    //    password" returns in 300ms, and the difference enumerates
    //    your entire user list.
    $hash = $user?->passwordHash() ?? self::DECOY_HASH;

    $valid = password_verify($password, $hash);

    if ($user === null || !$valid) {
        $throttle->recordFailure($email);

        // 3. One message for both causes. "No such user" confirms
    //    //    existence to anyone who asks.
        return back()->withInput($request->except('password'))
            ->withErrors(['email' => 'Those credentials do not match our records.']);
    }

    // 4. An optional check that does not leak through timing either.
    if ($user->isLocked()) {
        $throttle->recordFailure($email);

        return back()->withErrors(['email' => self::GENERIC_FAILURE]);
    }

    // 5. Rehash if the parameters have moved on.
    if (password_needs_rehash($user->passwordHash(), PASSWORD_DEFAULT)) {
        $this->users->updatePasswordHash($user->id(), password_hash($password, PASSWORD_DEFAULT));
    }

    // 6. Regenerate the session id and the CSRF token. See chapter 12.
    session()->regenerate(deleteOldSession: true);
    session()->regenerateToken();

    session()->set('user_id', $user->id()->toString());

    $throttle->clear($email);

    // 7. Honour the intended destination, but only for a path on this
    //    host. See the open-redirect note below.
    return redirect()->to($this->safeRedirectTarget($request), 303);
}

The intended-URL redirect is an open redirect unless it is validated. session()->pull('intended_url') was written by the application, but the value came from a request — and an attacker can arrange for the login form to be submitted from a page of theirs with a crafted referrer or a crafted original path. Redirecting to https://evil.example/login-thank-you after login is a credible phishing primitive, because the redirect comes from your domain. Accept only a path that starts with a single slash and is not protocol-relative, and resolve it against your own base URL before comparing.

private function safeRedirectTarget(Request $request): string
{
    $candidate = session()->pull('intended_url') ?? route('dashboard');

    // Reject absolute URLs, protocol-relative URLs, and anything that
    // does not begin with exactly one slash.
    if (!is_string($candidate) || !str_starts_with($candidate, '/') || str_starts_with($candidate, '//')) {
        return route('dashboard');
    }

    // Belt and braces: confirm the resolved host is ours.
    $resolved = parse_url($candidate, PHP_URL_HOST);

    if ($resolved !== null && $resolved !== parse_url(config('url'), PHP_URL_HOST)) {
        return route('dashboard');
    }

    return $candidate;
}

Throttling, with the two limits that work and the arithmetic behind choosing them:

LimitTypical valueStops
Per account5 failures, then lock for 15 minutes with exponential growthTargeted password guessing against one account
Per address30 failures per hourSpraying across many accounts from one host
GlobalAlert above a baselineCredential stuffing, which is what actually happens

Do not lock an account on failure, and do not reveal whether it exists. Permanent lockout is a denial-of-service tool: an attacker who knows a victim’s email locks them out repeatedly until the victim gives up or calls support. Progressive delay plus a notification to the account owner is both safer for the user and more useful to you, because the notification tells the legitimate owner that something happened.

One more property worth implementing, because it costs almost nothing and closes a whole class of leak: a successful login must invalidate the sessions that preceded it.

// A "session version" on the user. Bump it on password change, on
// forced logout, and on any suspected compromise.
if (!hash_equals((string) $user->sessionVersion(), (string) ($_SESSION['session_version'] ?? ''))) {
    session()->invalidate();

    return response()->json(['error' => 'session_revoked'], status: 401);
}

// And after a password change, every other session is dead within
// one request, with no bookkeeping per session.
$users->bumpSessionVersion($user->id());

13.3 Token authentication for APIs

Opaque tokens versus signed tokens, the storage properties that make revocation possible, and the scopes that limit a token’s damage.

Two designs, with a genuine trade-off between them.

The opaque design, with a selector and validator pair, which makes lookup constant-time and remains safe if the database leaks:

final class ApiToken
{
    private function __construct(
        public string $selector,        // 16 bytes, hex — indexed, safe to log partially
        public string $validatorHash,   // 32 bytes, hashed — never stored raw
        public UserId $userId,
        public array $scopes,            // ['orders:read', 'orders:write']
        public DateTimeImmutable $expiresAt,
        public ?DateTimeImmutable $lastUsedAt,
        public bool $revoked,
    ) {}
}

final class TokenIssuer
{
    public function issue(UserId $userId, array $scopes, int $days): string
    {
        $selector  = bin2hex(random_bytes(16));
        $validator = random_bytes(32);

        $this->tokens->store(new ApiToken(
            selector:       $selector,
            // Hash the validator before storing. A database dump then yields
            // nothing usable, because the raw half exists only in the
            // client's header.
            validatorHash:  hash('sha256', $validator, true),
            userId:         $userId,
            scopes:         $scopes,
            expiresAt:      new DateTimeImmutable("+{$days} days"),
            lastUsedAt:     null,
            revoked:        false,
        ));

        // Returned once. The application never stores or logs it again.
        return "ot_{$selector}_{}" . base64_encode($validator);
    }

    public function verify(string $presented): ?ApiToken
    {
        if (!str_starts_with($presented, 'ot_')) {
            return null;
        }

        [, $selector, $encoded] = explode('_', $presented, 3);

        $token = $this->tokens->findBySelector($selector);

        if ($token === null || $token->revoked) {
            return null;
        }

        if ($token->expiresAt < new DateTimeImmutable()) {
            return null;
        }

        $validator = base64_decode($encoded, true);

        // Constant-time: the selector is not a secret, but the validator is,
        // and a short-circuiting comparison would leak it byte by byte.
        if (!hash_equals($token->validatorHash, hash('sha256', $validator ?: '', true))) {
            return null;
        }

        // A wrong validator against a real selector means the token was
    //    //    guessed or the selector leaked. Revoke the whole family.
        $this->tokens->revokeSelector($selector);

        return null;
    }
}

Never log the Authorization header. A request log that captures headers captures bearer tokens, and a bearer token in a log is a live credential readable by everyone with log access. If you must record that authentication occurred, log the token’s selector — which is why it is a separate, indexed, non-secret half — and never the validator.

The middleware, including the scope check that limits what a token can do:

final class AuthenticateApiToken
{
    public function __construct(private TokenIssuer $tokens) {}

    public function before(Request $request): ?Response
    {
        $header = $request->header('Authorization');

        if ($header === null || !str_starts_with($header, 'Bearer ')) {
            return response()->json(
                ['error' => 'unauthenticated'],
                status: 401,
            )->header('WWW-Authenticate', 'Bearer realm="orders"');
        }

        $token = $this->tokens->verify(trim(substr($header, 7)));

        if ($token === null) {
            return response()->json(['error' => 'invalid_token'], status: 401);
        }

        $request->token = $token;
        $request->user = $this->users->find($token->userId);

        return null;
    }
}

final class RequireScope
{
    public function __construct(private string $scope) {}

    public function before(Request $request): ?Response
    {
        $token = $request->token;

        if ($token === null || !in_array($this->scope, $token->scopes, true)) {
            return response()->json(
                ['error' => 'insufficient_scope'],
                status: 403,
            )->header('WWW-Authenticate', 'Bearer error="insufficient_scope"');
        }

        return null;
    }
}

// Applied per route, next to the route it protects.
$app->get('/orders', 'Api\OrderController@index')->middleware([
    App\Middleware\AuthenticateApiToken::class,
    App\Middleware\RequireScope::class,   // configured with 'orders:read'
]);

Scope checks belong in middleware, and authorisation checks do not. A scope answers "was this token issued for this class of action", which is knowable from the route and the token alone — exactly what middleware is for. "May this user delete this order" requires the record, which is a controller concern, as established in chapter 4.5. Conflating the two produces either an authorisation bug in a layer that cannot see the data, or a middleware that fetches records it has no business touching.

For a short-lived signed token in a multi-service architecture, the properties to get right are narrow in number and unforgiving in practice: an explicit algorithm in the header so the verifier never infers one, a key identifier so rotation does not require a coordinated deploy, an audience claim so a token minted for another service is rejected, an issuer, and an expiry measured in minutes rather than days.

13.4 Authorisation: roles, Policies, and Enforcement

Why role checks in a controller are insufficient, the policy object that replaces them, and the two questions every protected action must answer.

Roles answer the question "what kind of user is this?" Authorisation answers "may this user do this to this record?". Only the second question matters for security, and it cannot be answered from a role alone.

// Wrong: the role grants everything the role can do, to everything
// the role can reach. An admin editing order 1 for a customer they do
// not own is a bug waiting for a support ticket.
if ($user->isAdmin()) {
    $order->rename($data['title']);
}

// Right: a policy, asked two questions.
$this->policy->assertMayEdit($request->user(), $order);

final readonly class OrderPolicy
{
    public function __construct(private StaffOverrides $overrides) {}

    public function assertMayEdit(User $actor, Order $order): void
    {
        // 1. The resource rule: is this actor the owner?
        if ($actor->id()->equals($order->accountId())) {
            return;
        }

        // 2. The override rule: staff may, but only within the
        //    configured scope — same region, not just same role.
        if ($actor->isStaff()
            && $this->overrides->allows($actor, $order, 'edit')) {
            return;
        }

        throw new AuthorizationException(
            ability:  'orders.edit',
            subject:   $order->id()->toString(),
            actor:     $actor->id()->toString(),
        );
    }

    public function assertMayView(User $actor, Order $order): void { ... }
    public function assertMayRefund(User $actor, Order $order): void { ... }
}

A 403 on a resource the user cannot see is an information leak. Returning 403 for order 9 tells an attacker that order 9 exists. For an endpoint where existence itself is sensitive, return 404 — indistinguishable from absence. Choose per resource, write the choice down, and be consistent: an endpoint that returns 403 for one record and 404 for another is telling an attacker exactly which is which.

// The read-side pattern: scope the query, do not filter afterwards.
public function show(Request $request, int $id): Response
{
    $order = $this->orders->findVisibleTo(new OrderId($id), $request->user());

    if ($order === null) {
        // Not "not found" and not "forbidden" — the same response for
        // both, so the endpoint reveals nothing.
        return response()->json(['error' => 'not_found'], status: 404);
    }

    return response()->json(OrderResource::from($order));
}

Make the denied path a test, not a hope. For each protected action, write a test that authenticates a user who is refused and asserts the specific status code. This is the highest-value test in an authorisation suite because it exercises the exact code path an attacker would, and because a missing test is indistinguishable from a missing check. A suite of positive tests only proves the feature works for the owner.

13.5 Password reset, email change, and MFA

The flows that bypass normal authorisation and therefore need the most careful implementation.

Password reset is the flow most often built incorrectly, because it is easy to write and the failure modes are not intuitive.

final class RequestPasswordReset
{
    public function __construct(
        private Users $users,
        private Mailer $mail,
        private Clock $clock,
        private Throttle $throttle,
    ) {}

    public function handle(string $email): void
    {
        $this->throttle->assertNotRateLimited('reset:' . $email);

        $user = $this->users->findByEmail($email);

        // Always the same outward behaviour, whether or not the
        // address exists. The page says "if that address has an
        // //    account, a link is on its way" — unconditionally.
        $this->mail->queuePasswordResetIfUserExists($user, $this->clock->now());

        $this->throttle->record('reset:' . $email);
    }
}

final class CompletePasswordReset
{
    public function handle(string $selector, string $validator, string $newPassword): void
    {
        $record = $this->tokens->findResetBySelector($selector);

        if ($record === null) {
            throw new InvalidResetToken();
        }

        // 1. Constant-time validator comparison — same reason as the
        // //    API token: the selector is guessable, the validator is not.
        if (!hash_equals($record->validatorHash, hash('sha256', $validator, true))) {
            $this->tokens->revokeResetSelector($selector);

            throw new InvalidResetToken();
        }

        // 2. Expiry, and single use. A used token is dead even if it
    //    //    has not expired.
        if ($record->expiresAt < $this->clock->now() || $record->usedAt !== null) {
            throw new InvalidResetToken();
        }

        // 3. Rate limit the completion step separately. Without this, a
        //    //    short token is brute-forceable in a few hours.
        $this->throttle->assertNotRateLimited('reset-complete:' . $selector);

        $this->tokens->markResetUsed($record->id());

        // 4. The password policy is enforced identically to the login
    //    //    form. One implementation, called from both.
        $this->policy->assertAcceptable($newPassword);

        $this->users->setPassword($record->userId, password_hash($newPassword, PASSWORD_DEFAULT));

        // 5. Kill every existing session for that user, including this
    //    //    one. A password reset is a recovery action; if an attacker
    //    //    triggered it, their session must not survive it.
        $this->users->bumpSessionVersion($record->userId);
        $this->tokens->revokeAllForUser($record->userId);
    }
}

Never put the reset token in the query string of a page that loads third-party resources. A link of the form /reset?token=... sends the token in the Referer header to every external script and stylesheet on the landing page, and it lands in browser history and proxy logs. Put the token in a fragment, read it with JavaScript, and post it — or serve a bare page with no external resources. A short-lived POST handoff into your own form field is the simplest correct approach.

Email change deserves the same care, because it changes the address that password reset and MFA recovery depend on — an attacker who changes it first can then take the account permanently.

    userId:      $user->id(),

$this->mail->emailChanged($user->email(), $pending->newEmail);

Multi-factor authentication, when you add it, changes the shape of the session rather than the login logic. The important decisions:

  • Remember-device cookies are credentials. Give them a path of / only if they must accompany every request, a short lifetime, the same three cookie flags, and a stored hash rather than the value. And show the user the list of remembered devices with the ability to revoke each one — a session-management screen is part of MFA, not an optional extra.
  • Recovery codes are single-use and stored hashed. Show them once, at setup, and let the user regenerate the whole set. Never email them.
  • Step-up is a fresh authorisation, not a stored flag. An operation that requires a second factor should verify that factor within a short window, and the window should be minutes rather than hours.

14.1 Registering handlers and converting exceptions

Two separate registrations — one for PHP errors, one for uncaught exceptions — and why converting errors to exceptions matters.

PHP has two error channels and they are not the same thing. A warning, a notice, and a deprecation go through the error handler. A thrown object that nothing catches goes through the exception handler. Both need to be configured, and the first needs converting.

# bootstrap/app.php — both registrations, in this order.

// 1. Convert every PHP error to a Throwable. Without this, a $undefined
// //    variable is a warning, execution continues with a null, and the
// //    failure surfaces three layers away as a type error.
set_error_handler(static function (int $severity, string $message, string $file, int $line): bool {
    // Respect the error_reporting mask: @-suppressed and excluded
    // //    severities must not become exceptions.
    if (!(error_reporting() & $severity)) {
        return false;
    }

    throw new ErrorException($message, 0, $severity, $file, $line);
});

// 2. The framework's handler, which renders the response and reports.
$app->setErrorHandler(function (Throwable $e, Request $request) {
    ...
});

Converting errors to exceptions will surface code that has been silently misbehaving. A project that has been running with notices suppressed will produce a burst of failures the first time this is enabled. That is the point — those notices were real defects whose only visible effect was a wrong value being passed onward. Budget time to fix them, and enable this on a branch rather than during a release.

Exceptions PHP raises itself need no configuration, but two of them are worth distinguishing because they are not your code’s fault:

ExceptionCauseResponse
TypeError, ValueErrorA type declaration failed500 — it is a bug, and it should be loud
ArgumentCountErrorA handler called with the wrong arity500 — a routing or wiring bug
Error (not Exception)A fatal language-level error500 — catch it, report it, do not retry
PDOExceptionThe database refused or failed503 if the connection is down, 500 otherwise
Out of memorymemory_limit reachedNot catchable. Only a shutdown function can log it

Register a shutdown handler for what cannot be caught. An exhausted memory limit, a fatal error from an extension, and a failed session_write_close all terminate the request without an exception. A shutdown function that inspects error_get_last() and logs it is the only way these appear in your logs at all. Without it, the symptom is a blank page or a truncated response with nothing recorded anywhere.

register_shutdown_function(static function (): void {
    $last = error_get_last();

    if ($last === null || !in_array($last['type'], [E_ERROR, E_PARSE, E_CORE_ERROR, E_COMPILE_ERROR], true)) {
        return;
    }

    // Best-effort only. At this point the process is ending; anything
    // //    that throws here is silently discarded, so keep it trivial.
    error_log(sprintf(
        'fatal: %s in %s:%d',
        $last['message'],
        $last['file'],
        $last['line'],
    ));
});

14.2 The exception taxonomy

A small hierarchy where the base class carries the status code, so a handler can map any exception without a chain of instanceof checks.

The design that keeps a handler small: every exception the application throws carries its own HTTP semantics, and the handler reads that property rather than knowing the class hierarchy.

<?php

declare(strict_types=1);

namespace App\Domain\Exception;

use RuntimeException;
use Throwable;

// The base. It knows a status code and whether the failure is the
// //    client's fault or the server's.
abstract class DomainException extends RuntimeException
{
    public function __construct(
        string $message,
        private int $status = 422,
        private bool $reportable = false,
        private array $context = [],
        ?Throwable $previous = null,
    ) {
        parent::__construct($message, 0, $previous);
    }

    public function status(): int      { return $this->status; }
    public function isReportable(): bool { return $this->reportable; }
    public function context(): array    { return $this->context; }
}

// Client errors. Not reportable: they are the caller's problem and
// //    they are not defects.
final class ValidationFailed extends DomainException
{
    public function __construct(private array $errors)
    {
        parent::__construct('Validation failed', status: 422);
    }

    public function errors(): array { return $this->errors; }
}

final class NotFound extends DomainException
{
    public function __construct(string $what, ?string $id = null)
    {
        parent::__construct(
            $id === null ? "{$what} not found" : "{$what} {$id} not found",
            status: 404,
        );
    }
}

final class Unauthorized extends DomainException
{
    public function __construct(string $message = 'Authentication required')
    {
        parent::__construct($message, status: 401);
    }
}

final class Forbidden extends DomainException
{
    public function __construct(string $ability)
    {
        parent::__construct("Not permitted: {$ability}", status: 403);
    }
}

<?php

final class ErrorHandlerMiddleware
{
    public function __construct(
        private LoggerInterface $log,
        private bool $debug,
    ) {}

    public function before(Request $request, callable $next): Response
    {
        try {
            return $next($request);
        } catch (DomainException $e) {
            // Expected. The status comes from the exception, so this
            // //    handler needs no knowledge of the class hierarchy.
            if ($e->isReportable()) {
                $this->log->error($e->getMessage(), $e->context() + [
                    'exception' => $e,
                    'request_id' => $request->id,
                ]);
            }

            return $this->render($request, $e->status(), $e->getMessage());
        } catch (Throwable $e) {
            // Unexpected. Report with the request context, then return
        //    //    something that says nothing about our internals.
            $this->log->error('unhandled', [
                'exception'   => $e,
                'request_id' => $request->id,
                'method'     => $request->method(),
                'path'       => $request->url(),
                'user_id'    => $request->user?->id()->toString(),
                'route'      => $request->route?->name,
            ]);

            $body = $this->debug
                ? ['error' => 'Internal Server Error', 'exception' => $e->getMessage(),
                   'at' => $e->getFile() . ':' . $e->getLine(),
                   'trace' => explode("\n", $e->getTraceAsString())]
                : ['error' => 'Internal Server Error', 'request_id' => $request->id];

            return $this->render($request, 500, $body);
        }
    }
}

One exception type per failure cause, not per call site. An application with OrderNotFound, CustomerNotFound, and ProductNotFound has three types where one would do, and adding a fourth entity means adding a fifth. A single NotFound carrying a what and an id gives an equally good message with one class. The exception taxonomy is a fixed, small set of client-visible outcomes, and it should be enumerable.

Use the previous-exception chain rather than flattening. Passing the underlying PDOException as $previous costs one constructor argument and preserves the entire cause chain for the log. Flattening — catching the driver exception and throwing a new one with only the driver message — produces a log entry that names the symptom and discards the location, which is the part you actually need.

private function render(Request $request, int $status, string|array $body): Response
{
    // A 401 that does not tell the client how to authenticate is a
    //    //    worse 401 than a 403, because the client cannot recover.
    if ($status === 401) {
        $response = $request->wantsJson()
            ? response()->json($body, status: 401)
            : response()->redirect(route('login'), 302);

        return $response->header('WWW-Authenticate', 'Bearer realm="orders"');
    }

    if ($request->wantsJson() || $request->isApi()) {
        return response()->json($body, status: $status);
    }

    return response()->view("errors/{$status}", [
        'message'    => is_string($body) ? $body : null,
        'request_id' => $request->id,
    ], status: $status);
}

An error page must not itself error. The 500 template is the least-exercised template in the application, so it is the one most likely to reference a value that is unavailable precisely because things are broken — a currentUser when the session store is the thing that failed, or an asset() call that depends on configuration loaded before the fault. Keep the error templates free of anything but static markup and a request identifier, and render them without a layout if the layout has dependencies. A blank page in place of an error page tells the user nothing and the log nothing.

Two headers that make a 429 actionable, and one that keeps a 503 from breaking clients:

return response()->json(['error' => 'rate_limited'], status: 429)
    ->header('Retry-After', (string) $retryAfterSeconds)
    ->header('X-RateLimit-Limit',     (string) $limit)
    ->header('X-RateLimit-Remaining', (string) $remaining)
    ->header('X-RateLimit-Reset',     (string) $resetEpoch);

Always include the request identifier in an error response and in the log line for the same failure. It is the only thing that connects a user’s screenshot of "it said 500" to the specific log entry, and it costs a middleware that assigns an id on the way in and adds it as a response header on the way out. Without it, correlating a report to a log entry means searching by timestamp across concurrent requests.

14.4 Logging, context, and what not to log

Structured logging with a fixed context, the fields that must never be written, and the redaction that belongs in the logger rather than at each call site.

Structured means each record is a set of key-value pairs a query engine can filter, not a formatted line a human reads. It is the difference between finding every request from one user in two minutes and in an afternoon.

final class Logger
{
    // Keys whose values are replaced before anything is written.
    // //    A denylist here is a backstop, not the primary control — the
    // //    primary control is not passing the value at all.
    private const REDACTED = [
        'password', 'password_confirmation', 'current_password',
        'token', 'access_token', 'refresh_token',
        'api_key', 'secret', 'authorization',
        'cookie', 'set-cookie', 'card_number', 'cvv',
    ];

    public function __construct(
        private LoggerInterface $inner,
        private string $environment,
    ) {}

    public function error(string $message, array $context = []): void
    {
        $this->write('error', $message, $context);
    }

    public function warning(string $message, array $context = []): void
    {
        $this->write('warning', $message, $context);
    }

    public function info(string $message, array $context = []): void
    {
        $this->write('info', $message, $context);
    }

    private function write(string $level, string $message, array $context): void
    {
        $this->inner->log($level, $message, $this->redact($context) + [
            'env'       => $this->environment,
            'timestamp' => gmdate('c'),
        ]);
    }

    private function redact(array $context): array
    {
        $out = [];

        foreach ($context as $key => $value) {
            if (in_array(strtolower((string) $key), self::REDACTED, true)) {
                $out[$key] = '[redacted]';

                continue;
            }

            $out[$key] = match (true) {
                is_array($value)  => $this->redact($value),
                $value instanceof Throwable => $this->describeThrowable($value),
                is_scalar($value), $value === null => $value,
                default => '[' . get_debug_type($value) . ']',
            };
        }

        return $out;
    }

    private function describeThrowable(Throwable $e): array
    {
        // The chain, so the cause is visible without a separate
    // //    lookup. Each link's file and line, since "somewhere" is useless.
        $chain = [];
        $current = $e;

        while ($current !== null) {
            $chain[] = [
                'class'   => $current::class,
                'message' => $current->getMessage(),
                'file'    => $current->getFile(),
                'line'    => $current->getLine(),
            ];

            $current = $current->getPrevious();
        }

        return [
            'type'     => $e::class,
            'message'  => $e->getMessage(),
            'file'     => $e->getFile() . ':' . $e->getLine(),
            'chain'    => $chain,
            'trace'    => explode("\n", $e->getTraceAsString()),
        ];
    }
}

Never log a request body, a full header set, or a session payload. All three contain credentials in some deployments and personal data in most. Log the shape instead — the field names and their types — which is almost always what you actually needed when you went looking, and it is safe to keep for the lifetime of the log. The exception to a strict body denylist is a deliberate, separately-stored, access-controlled diagnostic capture with a short retention, and that is an incident-response tool rather than application logging.

Authorisation denialwarningAbility, subject id, actor id, route

Log a state change with its before and after values. "Order 42 updated" tells you nothing six weeks later. "Order 42: status pending → paid, total 12500 → 12500, by user 7" is a record you can audit, reconcile, and reverse. It costs two extra reads inside the transaction, and it is the difference between a log that answers questions and one that confirms events happened.

Retention and volume, which are operational rather than code concerns but determine whether the logs are usable:

  • Errors: long. Ninety days minimum, because the failure you need is often the one that precedes a pattern becoming visible.
  • Request logs: short. Seven to fourteen days. They are high volume and low individual value; a sampled subset kept longer serves any analysis that needs it.
  • Audit logs: permanent. Separate storage, append-only, with no application-level deletion path.
  • Log to stderr in a container. Let the platform’s collector handle rotation. A PHP process writing to a file inside the container loses its logs on every deploy.

14.5 Debug mode and the information boundary

What debug mode may reveal, the single configuration key that controls it, and the failure mode of getting that wrong.

Debug mode is a switch between a useful internal error and a deliberately uninformative one. It must be driven by one configuration value read from the environment, and that value must default to off with no way to enable it from a request.

# config/config.php — the only place this is decided.
'debug' => $env('APP_DEBUG', false),

# bootstrap/app.php — a debug mode that fails open is worse than none.
if ($config['debug']) {
    ini_set('display_errors', '1');       // show errors, for the developer
    error_reporting(E_ALL);
} else {
    ini_set('display_errors', '0');       // never, regardless of anything else
    error_reporting(E_ALL);                              // still report, to the log
    ini_set('log_errors', '1');
}

A debug flag left on in production is the most common serious misconfiguration in a PHP application. It exposes absolute file paths, source code excerpts, environment values that leak into messages, database connection details in driver errors, and the full argument list of every function call on the stack. Each of those is a reconnaissance gift, and several of them are credentials. Guard the value: assert in your deploy script that APP_DEBUG is false in production, and add a startup check that refuses to boot if it is not.

# bootstrap/app.php — refuse to start rather than leak.
if (!$config['debug'] && $_SERVER['APP_ENV'] === 'production' && $config['debug']) {
    throw new RuntimeException('Refusing to boot: debug mode in production');
}

# Better: assert the negative directly, so there is no combination
# //    of values that passes.
if ($config['env'] === 'production' && $config['debug'] !== false) {
    throw new RuntimeException('Refusing to boot: APP_DEBUG must be false in production');
}

What the two modes return for the same exception, side by side, because the difference is the whole point:

DebugProduction
BodyMessage, class, file, line, full trace, local variable values where availableGeneric message plus the request id
Status500 with the real status if it is a domain exception500, or the real status for domain exceptions
LogEverything, to stdoutEverything, to the log sink, with a stack trace
Browser consolePHP warnings and notices rendered inlineNothing. Never

Give support a way to debug without shipping debug mode. The request id in the error page plus full detail in the log is the whole mechanism, and it works for the user, for support, and for you. When someone needs more than the request id, the answer is a log query — not a configuration change on a production server.

One related boundary worth stating: the log is not public, but it is not private either. Anyone with log access can read every token, address, and internal identifier you have ever recorded. Treat log access as a privileged capability, restrict it, and audit who has it — the log is the most complete picture of your application’s behaviour that exists, and it is routinely less protected than the database.

The single most important decision in this chapter is that static files are served by the web server, not by PHP. Every other consideration here follows from it.

The nginx equivalent, and the reason the try_files order matters:

server {
    root /var/www/orders/public;
    index index.php;

    location / {
        # A real file is served. A real directory with an index is
    #    //    served. Anything else falls through to PHP.
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        # Only index.php may be executed. Without this, a file
        # //    uploaded into public/ can be run directly.
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_param APP_ENV production;
        fastcgi_read_timeout 30;
    }

    location ~ /\. {
        deny all;          # .env, .git, and dotfiles
    }
}

Restrict which PHP files may execute. try_files alone will happily run any .php file that exists under the document root, including one that arrived through a file upload, a deployment that copied a fixture into the wrong directory, or a dependency with a stray test script. The location block above matches a single filename, or a narrow set of them, and nothing else is ever handed to PHP-FPM. Chapter 18 treats the upload side of this; this is the server side.

Verify the asset path serves no PHP at all. Add a temporary endpoint to a route that returns the process identifier, request a CSS file, and confirm the response does not include it. Or check the access log: a request for /assets/app.css should have a status of 200 from the static handler and no entry in the application’s request log from the audit middleware. The second check is better, because it is continuous rather than a one-time test.

15.2 Content fingerprints and immutable URLs

Filenames derived from content, which turns a cache invalidation problem into a non-problem at the cost of an extra build step.

The core technique: derive the filename from the file’s contents, so a changed file gets a changed name. A URL then identifies a specific version forever, and caching becomes safe to be aggressive about.

# Before
public/assets/app.css
public/assets/app.js

# After a build. The hash is of the file contents, so it changes
# //    only when the file changes.
public/assets/app.9f2c1a4b.css
public/assets/vendor.7d3e88f1.js
public/assets/app.9f2c1a4b.css.gz

Generating the names is a short script, and writing it yourself is often simpler than adopting a build tool for a project this size:

<?php

declare(strict_types=1);

// tools/build-assets.php — run at deploy time, not at request time.
$source = __DIR__ . '/../assets';
$target = __DIR__ . '/../public/assets';

if (!is_dir($target) && !mkdir($target, 0o775, true) && !is_dir($target)) {
    throw new RuntimeException("Cannot create {$target}");
}

// Remove the previous build. Keeping the old directory is what
// //    accumulates, and what makes a rollback unclear.
$iterator = new RecursiveIteratorIterator(
    new RecursiveDirectoryIterator($target, FilesystemIterator::SKIP_DOTS),
    RecursiveIteratorIterator::CHILD_FIRST,
);

foreach ($iterator as $item) {
    $item->isDir() ? rmdir($item->getPathname()) : unlink($item->getPathname());
}

$manifest = [];

foreach (new RecursiveIteratorIterator(new RecursiveDirectoryIterator($source)) as $file) {
    if (!$file->isFile() || !str_ends_with($file->getFilename(), '.css') && !str_ends_with($file->getFilename(), '.js')) {
        continue;
    }

    $contents = file_get_contents($file->getPathname());

    if ($contents === false) {
        throw new RuntimeException("Cannot read {$file->getPathname()}");
    }

    $relative = ltrim(str_replace($source, '', $file->getPathname()), '/\\');

    // The extension must be preserved, or the server serves the file
    // //    with no Content-Type and the browser refuses it.
    $extension = $file->getExtension();
    $stem      = substr($relative, 0, -(strlen($extension) + 1));
    $hash      = substr(hash('sha256', $contents), 0, 12);
    $name      = "{$stem}.{$hash}.{$extension}";

    if (file_put_contents($target . '/' . $name, $contents) === false) {
        throw new RuntimeException("Cannot write {$name}");
    }

    $manifest[$relative] = $name;
}

ksort($manifest);

file_put_contents(
    $target . '/manifest.json',
    json_encode($manifest, JSON_PRETTY_PRINT | JSON_UNESCAPED_SLASHES),
);

echo count($manifest) . " assets built\n";

The extension preservation in the middle of that script is not cosmetic. A file named app.9f2c1a4b with no extension is served as application/octet-stream, and a stylesheet the browser will not apply — a failure that looks exactly like a cache problem and is not one.

Eight to twelve hex characters is enough. The hash is a cache key, not a security control, and a full SHA-256 produces filenames the filesystem and the CDN both handle less efficiently. Sixty-four bits of collision resistance is far beyond what a collision across a few hundred assets requires. Shortening the name also keeps it inside the practical length limit for URLs on older clients and some proxies.

15.3 The build manifest and the asset helper

Mapping an original path to a fingerprinted one, and the helper that makes the mapping impossible to forget.

The manifest maps each source path to its built name. The application reads it once at boot and never guesses a hash.

<?php

declare(strict_types=1);

final class AssetManager
{
    /** @var array<string, string> */
    private array $manifest;
    private string $baseUrl;

    public function __construct(string $publicPath, string $baseUrl)
    {
        $this->baseUrl = rtrim($baseUrl, '/');

        $raw = @file_get_contents($publicPath . '/assets/manifest.json');

        if ($raw === false) {
            // A missing manifest in production is a build failure, and
        //    //    should stop the deploy rather than serve unversioned
    //    //    assets that will be cached forever.
            throw new RuntimeException('Asset manifest missing. Run the asset build.');
        }

        $this->manifest = json_decode($raw, true, 512, JSON_THROW_ON_ERROR);
    }

    // The versioned URL. This is what templates use.
    public function url(string $path): string
    {
        $key = ltrim($path, '/');

        if (!isset($this->manifest[$key])) {
            throw new RuntimeException("Unknown asset: {$key}");
        }

        return $this->baseUrl . '/assets/' . $this->manifest[$key];
    }

    // The original name, for logs and error messages.
    public function logicalName(string $path): string
    {
        return $this->manifest[ltrim($path, '/')] ?? $path;
    }
}

# In the template context, so templates never see the manager.
$this->asset('app.css');
$this->asset('app.js', defer: true);
$this->asset('charts.js', module: true);

<link rel="stylesheet" href="<?= $this->escape($assets->url('app.css')) ?>">

# Produces:
<link rel="stylesheet" href="/assets/app.9f2c1a4b.css">
<script src="/assets/app.7d3e88f1.js" defer></script>

Two properties make this arrangement work, and both are easy to lose. First, the helper throws on an unknown asset rather than falling back to the unhashed path — a silent fallback produces a permanently-cached unversioned file, which is the exact problem fingerprinting was introduced to solve. Second, the manifest is read once, so the URL for a given logical name is stable for the whole request and identical in every template that asks.

# A test that protects the whole mechanism.
public function test_templates_never_reference_an_unversioned_asset(): void
{
    $views = new RecursiveIteratorIterator(
        new RecursiveDirectoryIterator(__DIR__ . '/../resources/views'),
    );

    $failures = [];

    foreach ($views as $file) {
        if (!$file->isFile() || !str_ends_with($file->getFilename(), '.php')) {
            continue;
        }

        $source = (string) file_get_contents($file->getPathname());

        // A literal /assets/ path that is not built from the helper is
        // //    a cache bug waiting to happen.
        if (preg_match('/[\'"]\/assets\/(?!\$\{|<?=)/', $source) === 1) {
            $failures[] = $file->getPathname();
        }
    }

    $this->assertSame([], $failures, 'Unversioned asset references found');
}

15.4 CDNs, browser caching, and the deploy window

The cache headers that pair with fingerprinting, and the deployment race that fingerprinting creates if the files are not ready first.

Fingerprinting makes a long cache lifetime safe, but only if the response says so. Two headers do the work:

# For fingerprinted assets: cache forever, and do not revalidate.
location ~* ^/assets/.+\.[0-9a-f]{8,}\.(css|js|woff2?|png|svg|jpg|webp)$ {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    add_header Vary "Accept-Encoding" always;
    access_log off;
}

# Everything else, including HTML: revalidate every time.
location / {
    add_header Cache-Control "no-cache, must-revalidate" always;
}
Resourcemax-ageWhy
Fingerprinted asset31536000, immutableThe URL is unique to the content, so it can never be stale
HTML page0, must-revalidateIt names the asset URLs; a cached page pins an old asset
Unversioned image referenced by CSS604800, with revalidationHas no fingerprint, so it needs an expiry rather than immutability
API response, authenticatedprivate, no-storeShared caches must not serve one user’s data to another
API response, public60, plus ETagShort, because the data changes independently of deploys

Fingerprinting introduces a deploy race that the unversioned arrangement did not have. The new HTML references app.9f2c1a4b.css, so the new file must be in place and reachable everywhere before any new HTML is served. Deploy the assets first, wait for propagation, then deploy the application. If a request arrives in between — new HTML, old asset set — the page loads with a 404 on its stylesheet, and the cause is invisible in the application log because the 404 came from the static handler, not from Leaf.

Two mitigations, and which to choose:

  • Ordered deploy, with a verification step. Upload the asset directory, then issue a request for a specific fingerprinted URL from outside your network, and only then switch the application. This is the straightforward answer and it works when your infrastructure supports it.
  • Never delete the previous asset set immediately. Keep the last two or three builds and expire them after a day. A request that was in flight during a deploy then still resolves, and a client holding a cached HTML page from yesterday still finds its assets. This costs disk and is far more forgiving than a hard cutover.

With a CDN, purge nothing. The whole point of a content-addressed URL is that a purge is unnecessary: new HTML names new files, and old files remain correct for anyone still holding old HTML. A CDN configured to purge /assets/* on deploy has been set up in a way that discards the benefit, and every purge is a cache stampede. If you need a purge for other resources, scope it to HTML rather than to the asset path.

Third-party assets — a font from a CDN, an analytics script — are a separate question, because you do not control their filenames. Two considerations: pin the version in the URL so a provider’s release does not change what your page loads, and add integrity attributes so a compromised asset cannot execute.

<link
    rel="stylesheet"
    href="https://cdn.example.com/inter/4.1/inter-4.1.css"
    integrity="sha384-...base64hash..."
    crossorigin="anonymous"
>

15.5 Inlining, preloading, and small-asset thresholds

Eliminating a request for a small file, and the two techniques that help the largest asset arrive sooner.

A small critical stylesheet inlined in the document head removes a round trip from the critical path, at the cost of a slightly larger HTML document and no separate caching. The threshold is small: a few kilobytes.

# The build inlines a CSS file below a threshold. Above it, the file
# //    stays external and gets a versioned URL.
$inlineLimit = 4096;

if (str_ends_with($relative, '.css') && strlen($contents) <= $inlineLimit) {
    $inlined[$relative] = $contents;

    continue;
}

file_put_contents($target . '/' . $name, $contents);
$manifest[$relative] = $name;

Preloading the largest stylesheet, and preloading the font that CSS will request, both address the same problem: a request discovered only after a stylesheet has been parsed and applied.

<head>
    <link rel="preload" href="/assets/app.9f2c1a4b.css" as="style">
    <link rel="stylesheet" href="/assets/app.9f2c1a4b.css">

    <link
        rel="preload"
        href="/assets/inter-var.3a1f8c22.woff2"
        as="font"
        type="font/woff2"
        crossorigin
    >
</head>

Preload only what is genuinely used on the page that preloads it. A preloaded resource that is not fetched within a few seconds is logged by the browser as a wasted preload, and it has consumed bandwidth that the page needed. Preloading a stylesheet on a page that then redirects, or a font for a page with no text in that family, actively makes the page slower. The most reliable rule is to preload the critical stylesheet and nothing else until a measurement says otherwise — the classic misuse is preloading every script, which defeats the purpose of the attribute entirely.

And the property that must accompany a preloaded font: font-display. Without it, a font that has been preloaded and then fails to decode blocks the text, because the browser has already committed to showing that face:

@font-face {
    font-family: 'Inter';
    src: url('/assets/inter-var.3a1f8c22.woff2') format('woff2-variations');
    font-weight: 100 900;
    font-display: swap;   // show the fallback immediately, swap when ready
}

Load third-party scripts after your own. An analytics or chat widget loaded in the head blocks parsing on a request you do not control and cannot optimise. Deferring it, or loading it after DOMContentLoaded, keeps it off the critical path while still executing it early enough for its purpose. The measurement to make before and after is time to first interaction, which is what a user actually experiences.

FeatureDoes this request produce this response?The whole applicationUnder 500 ms

The rule for choosing: put the test at the lowest layer that can meaningfully fail. A credit limit rule belongs in a unit test because a unit test can fail on it. A test that exercises the same rule through a full request pass is slower, less precise, and will still pass if the rule is deleted and the test never asserted the failure.

Test the branch, not the whole graph. A feature test that creates an order proves the route exists, the middleware runs, the controller resolves, the repository queries, and the domain accepted the order. It does not prove the credit limit is enforced at the boundary, because a test that never asserts a rejection proves nothing about rejection. Every rule needs a test that asserts the failure path, at the layer where the rule actually lives.

The proportion to aim for, and why the ratio matters more than the count:

SuiteShareConsequence of getting it wrong
Unit70 to 85%Every change is slow to verify, so people batch changes and verify less
Integration10 to 20%Query errors reach production, because nothing exercised the SQL
Feature5 to 15%Wiring errors — a route not registered, middleware in the wrong order — reach production

The test class worth writing most often, and the doubles that make it possible without a mocking framework.

16.3 The feature test harness

A base class that boots the real application, builds a request, and returns a response, without an HTTP server.

A feature test should exercise the real router, the real middleware, the real controller, and the real database. It should not require a web server, a port, or a socket. That is achievable because the pipeline can be invoked in-process.

<?php

declare(strict_types=1);

namespace Tests\Support;

use Leaf\App;
use Leaf\Http\Request;
use Leaf\Http\Response;
use PDO;
use PHPUnit\Framework\TestCase;

abstract class FeatureTestCase extends TestCase
{
    protected App $app;
    protected Database $db;
    protected TestSession $session;

    protected function setUp(): void
    {
        parent::setUp();

        // 1. A fresh in-memory database per test. Not a shared
        //    //    container, not a transaction rollback: a fresh
    //    //    database per test is isolation you can reason about.
        $pdo = new PDO('sqlite::memory:', options: [
            PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        ]);

        $pdo->exec('PRAGMA foreign_keys = ON');

        $this->db = new Database($pdo);

        (new Migrator($pdo))->migrate();

        // 2. The real bootstrap, with the test's PDO and a test
    //    //    environment. Everything under app/ is the same code.
        $this->app = require __DIR__ . '/../../bootstrap/app.php';

        // 3. A substitutable session, so no PHP session is started and
    //    //    no cookie is ever emitted.
        $this->session = new TestSession();

        Session::swap($this->session);
    }

    // The request. A method per verb, mirroring the shape of a
    // //    real request: method, path, body, headers, cookies.
    protected function get(string $uri, array $headers = []): TestResponse
    {
        return $this->request('GET', $uri, [], $headers);
    }

    protected function post(string $uri, array $body = [], array $headers = []): TestResponse
    {
        return $this->request('POST', $uri, $body, $headers);
    }

    protected function postJson(string $uri, array $body, array $headers = []): TestResponse
    {
        return $this->request(
            'POST',
            $uri,
            $body,
            $headers + [
                'CONTENT_TYPE' => 'application/json',
                'HTTP_ACCEPT'   => 'application/json',
            ],
            isJson: true,
        );
    }

    protected function request(
        string $method,
        string $uri,
        array $body = [],
        array $headers = [],
        bool $isJson = false,
    ): TestResponse {
        // Populate the superglobals the request object reads from,
        //    //    then let the framework build its own Request from them.
        $_SERVER = [
            'REQUEST_METHOD' => $method,
            'REQUEST_URI'    => $uri,
            'HTTP_HOST'       => 'localhost',
            'REMOTE_ADDR'    => '203.0.113.10',
            'HTTPS'          => 'on',
        ] + $headers;

        $_GET  = [];
        $_POST = $isJson ? [] : $body;

        parse_str((string) parse_url($uri, PHP_URL_QUERY), $_GET);

        if ($isJson) {
            $rawBody = json_encode($body, JSON_THROW_ON_ERROR);

            $_POST = [];
            file_put_contents('php://memory', $rawBody);
            // Set the stream the request object will read.
            $this->rawBody = $rawBody;
        }

        $_COOKIE = [];

        $response = $this->app->handle(
            Request::createFromGlobals($_SERVER, $_GET, $_POST, $_COOKIE, $_FILES)
                ->withRawBody($this->rawBody ?? ''),
        );

        return new TestResponse($response, $this->session);
    }

    // Helpers for the two things every feature test needs.
    protected function actingAs(User $user): static
    {
        $this->session->set('user_id', $user->id()->toString());
        $this->session->set('session_version', (string) $user->sessionVersion());

        return $this;
    }

    protected function withCsrfToken(): array
    {
        $token = $this->session->get('_csrf') ?? bin2hex(random_bytes(32));

        $this->session->set('_csrf', $token);

        return ['_token' => $token];
    }
}

Read the shipped source for the exact entry point. The precise method — handle(), run(), or a dispatcher you construct yourself — varies across Leaf patch releases, and the way a request is seeded from globals also varies. Look at how the shipped tests or the built-in middleware construct a request, and match that. The architecture above is what matters; the call signature is a version detail to confirm rather than assume.

The response wrapper, which is where most of a feature test’s value is concentrated:

<?php

declare(strict_types=1);

namespace Tests\Support;

use Leaf\Http\Response;

final class TestResponse
{
    public function __construct(
        private Response $response,
        private TestSession $session,
    ) {}

    public function status(): int      { return $this->response->status; }
    public function headers(): array   { return $this->response->headers->all(); }
    public function body(): string     { return (string) $this->response->body; }

    public function header(string $name): ?string
    {
        return $this->response->headers->get($name);
    }

    public function json(?string $key = null): mixed
    {
        $decoded = json_decode($this->body(), true, 512, JSON_THROW_ON_ERROR);

        return $key === null ? $decoded : ($decoded[$key] ?? null);
    }

    // The assertion that catches the silent-output failure from
    //    //    chapter 5: a body that is valid JSON only after trimming.
    public function assertStatus(int $expected): self
    {
        if ($this->status() !== $expected) {
            throw new \RuntimeException(sprintf(
                "Expected %d, got %d.\nHeaders: %s\nBody: %s",
                $expected,
                $this->status(),
                json_encode($this->headers()),
                substr($this->body(), 0, 2000),
            ));
        }

        return $this;
    }

    public function assertJsonPath(string $path, mixed $expected): self
    {
        $actual = $this->json();

        foreach (explode('.', $path) as $segment) {
            $actual = is_array($actual) ? ($actual[$segment] ?? null) : null;
        }

        $this->assertSame($expected, $actual, "JSON path {$path}");

        return $this;
    }

    // Session assertions, so a feature test can verify the
    //    //    authentication side effects it produced.
    public function sessionHas(string $key, mixed $value): self
    {
        $this->assertSame($value, $this->session->get($key));

        return $this;
    }

    public function assertRedirectsTo(string $path): self
    {
        $location = $this->header('Location');

        $this->assertNotNull($location, 'No Location header on a redirect response');
        $this->assertStringEndsWith($path, (string) $location);

        return $this;
    }
}

Use SQLite for tests even when production runs MySQL. A fresh in-memory database per test with no server, no credentials, and no cleanup is dramatically faster. 16.4 Factories, fixtures, and the database

Building valid test data by default, overriding one attribute at a time, and the global-state test that enforces the domain boundary.

A factory produces a valid object with sensible defaults, and a test overrides only what it cares about. This keeps the test’s intent visible and keeps the data valid by construction.

<?php

declare(strict_types=1);

namespace Tests\Support;

use App\Domain\Account\Account;
use App\Domain\Account\AccountId;
use App\Domain\Account\AccountEmail;
use App\Domain\Money\Cents;
use App\Domain\User\User;
use App\Domain\User\UserId;

final class Factory
{
    private static int $sequence = 0;

    public static function account(array $overrides = []): Account
    {
        static $sequence++;

        return new Account(
            id:    $overrides['id'] ?? new AccountId(sprintf('acc_%06d', $sequence)),
            email: $overrides['email'] ?? new AccountEmail(sprintf('a%d@example.test', $sequence)),
        );
    }

    public static function user(array $overrides = []): User
    {
        static $sequence++;

        $account = $overrides['account'] ?? self::account();

        return new User(
            id:             $overrides['id'] ?? new UserId(sprintf('usr_%06d', $sequence)),
            accountId:      $account->id(),
            email:          $overrides['email'] ?? new AccountEmail(sprintf('u%d@example.test', $sequence)),
            passwordHash:   $overrides['password_hash'] ?? password_hash('correct horse battery staple', PASSWORD_DEFAULT),
            sessionVersion: $overrides['session_version'] ?? 1,
            isStaff:        $overrides['is_staff'] ?? false,
            lockedAt:       $overrides['locked_at'] ?? null,
        );
    }

    // A builder for the states that need more than one override.
    public static function lockedUser(): User
    {
        return self::user(['locked_at' => new DateTimeImmutable()]);
    }

    public static function staffUser(): User
    {
        return self::user(['is_staff' => true]);
    }
}

Because the factory builds domain objects rather than inserting rows, a test that needs a user in the database persists the object it made. The distinction matters: a factory that inserted rows directly could produce a user that violates a domain invariant, and the test would pass against impossible data.

ApproachUseProblem
Factory producing domain objectsAlmost everythingNone worth naming
Fixed SQL fixtures loaded per testA known complex state, such as a partially fulfilled order with a historyGoes stale as the schema changes, and hides which columns the test actually depends on
Shared fixture across a suiteRead-only reference data such as a country listCouples tests to each other; a test that mutates it breaks unrelated tests

A test suite that shares mutable state fails in ways that are hard to reproduce. The pattern — tests running in a random order, one test creating a user that another test then counts — produces failures that appear on your machine and not in continuous integration, and only when the suite is slow enough to interleave. A fresh database per test is slower per test and far faster overall, and it is the only approach where a test’s outcome depends on what that test did.

The structural test that keeps the domain free of framework dependencies, which is the automated form of the chapter 6 rule:

<?php

declare(strict_types=1);

namespace Tests\Architecture;

use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

final class DomainIsolationTest extends TestCase
{
    /** @return iterable<string, array{string}> */
    public static function domainFiles(): iterable
    {
        $root = __DIR__ . '/../../app/Domain';

        foreach (new RecursiveIteratorIterator(new RecursiveDirectoryIterator($root)) as $file) {
            if ($file->isFile() && $file->getExtension() === 'php') {
                yield $file->getPathname() => [$file->getPathname()];
            }
        }
    }

    #[DataProvider('domainFiles')]
    public function test_domain_has_no_framework_or_persistence_dependency(string $file): void
    {
        $source = (string) file_get_contents($file);

        $forbidden = [
            // Persistence
            '/\\bPDO\\b/',
            '/\\bPDOException\\b/',
            '/\\bQueryBuilder\\b/',
            // The framework
            '/\\bLeaf\\\\/',
            // Superglobals
            '/\\$_(?:GET|POST|REQUEST|SERVER|COOKIE|SESSION|FILES|ENV)\\b/',
            // Global state
            '/\\b(?:session|response|request|config|view)\\s*\\(\\s*\\)/',
            // Process-level escape hatches
            '/\\b(?:exec|shell_exec|system|passthru|popen|proc_open)\\s*\\(/',
        ];

        foreach ($forbidden as $pattern) {
            $this->assertDoesNotMatchRegularExpression(
                $pattern,
                $source,
                basename($file) . ' contains a forbidden dependency',
            );
        }
    }

    public function test_repositories_are_the_only_place_sql_appears(): void
    {
        $offenders = [];

        foreach (['Controllers', 'Services', 'Domain', 'Middleware'] as $dir) {
            $path = __DIR__ . "/../../app/{$dir}";

            if (!is_dir($path)) {
                continue;
            }

            foreach (new RecursiveIteratorIterator(new RecursiveDirectoryIterator($path)) as $file) {
                if (!$file->isFile() || $file->getExtension() !== 'php') {
                    continue;
                }

                $source = (string) file_get_contents($file->getPathname());

                if (preg_match('/\b(?:SELECT|INSERT\s+INTO|UPDATE|DELETE\s+FROM)\s+/i', $source) === 1) {
                    $offenders[] = $file->getPathname();
                }
            }
        }

        $this->assertSame([], $offenders, 'SQL found outside app/Repositories');
    }
}

Structural tests are cheap insurance against slow architectural decay. Nothing in a code review process reliably catches a $_SESSION read appearing in a domain class, but a regex over the directory catches it immediately, every time. Each assertion here corresponds to a rule stated earlier in this guide, which is what makes them maintainable: the test is not inventing a new standard, it is enforcing one the team already agreed to.

16.5 Architectural tests and coverage honesty

What a coverage number does and does not tell you, and the metrics that are worth watching instead.

Line coverage measures which lines executed. It does not measure whether any assertion was meaningful, whether the test would fail if the code were wrong, or whether the paths nobody covered are the dangerous ones.

MetricWhat it meansHow to read it
Line coverageExecuted lines over totalA floor, not a goal. 80% with meaningful assertions beats 99% of smoke tests
Mutation scoreSurviving mutants over generatedThe only coverage measure that tests assertion strength. Expensive, and worth running occasionally
Test durationWall clock for the suiteThe number that determines whether people run it
Flake rateFailures that do not reproduceTarget zero. One flake per fifty runs trains people to re-run instead of investigate
Slowest testsTop ten by durationAlmost always an accidental network call or a sleep. Both are defects

Set a per-test timeout and fail on a real sleep. A test that takes four seconds is usually a hidden network call, a usleep for a retry, or a loop that should have been a single query. A #[Timeout(5000)] attribute turns a slow suite into a failing one, which is the only version of the problem that gets attention. Any sleep in a test should be replaced with a fake clock — chapter 12's timeout tests are written that way for exactly this reason.

17.1 Opcache and the configuration that matters

Compiled bytecode held in shared memory, and the four settings whose defaults are wrong for a production PHP-FPM deployment.

Without opcache, every request compiles every PHP file it touches from source. On a request that loads a hundred files, that is a hundred parses per request, and it is by a wide margin the largest avoidable cost in a PHP deployment.

# php.ini — production PHP-FPM
opcache.enable=1
opcache.enable_cli=0

// The shared memory pool. This is the number that matters most: it is
// //    the total memory available for all cached scripts, and the
// //    default is small enough to be exhausted by a large application.
opcache.memory_consumption=256

// How many compiled scripts are held. The default is low; raise it to
// //    comfortably exceed your file count.
opcache.max_accelerated_files=20000

// How long to keep a script's bytecode after its source is checked.
// //    revalidate_freq=2 means a stale file can be served for up to
// //    two seconds, which is acceptable and materially faster than
// //    stat-ing every file on every request.
opcache.revalidate_freq=2

// Check the file's timestamp and load it if it changed. Turning this off
// //    is the single biggest speed win — and it means a deploy needs an
// //    opcache reset, or the change has no effect until the next restart.
opcache.validate_timestamps=1

opcache.save_comments=1

In production, turn timestamp validation off and reset opcache at deploy time. Checking a timestamp on every included file is thousands of stat calls per request. With validation off, PHP never asks whether the file changed — and a deploy script issues a reset so the next request recompiles against the new source. The result is faster and, provided the deploy step is not skipped, more correct: there is no window where some workers serve old bytecode and some serve new.

php -r "var_dump(opcache_get_status(true)['scripts']['/var/www/orders/app/Domain/Money/Cents.php']);"

# Reset at deploy time, without restarting PHP.
php -r "opcache_reset();"

# Or, per-pool, over FastCGI.
cgi-fcgi -bind -connect /run/php/php8.3-fpm.sock \
  -data-binary '{"method":"opcache_reset"}' 2>/dev/null

// //    seconds and 32 workers means the 33rd concurrent request
// //    waits for a worker, regardless of the CPU being idle.

Sizing pm.max_children against memory, not against cores. A typical PHP-FPM worker with opcache uses 30 to 60 MB including the opcache allocation. On a 4 GB machine, 32 workers is near the ceiling and 64 will produce out-of-memory failures that look like random 500s. The symptom of oversizing is a server that is fine at low load and falls over under a traffic spike, because the failure mode is allocation failure rather than queueing. Start conservatively, raise under observation, and watch resident memory rather than CPU utilisation.

17.2 The N+1 query problem

The single most common performance defect in a PHP application, why it hides from casual inspection, and the three shapes of fix.

An N+1 is one query to fetch a list, then one more per item to fetch something the list referenced. A page showing fifty orders issues fifty-one queries, and the cost grows with the data rather than staying constant.

// 51 queries for 50 orders.
$orders = $this->db->select(
    'SELECT id, customer_id, status FROM orders WHERE account_id = ? LIMIT 50',
    [$accountId],
);

foreach ($orders as $i => $row) {
    $orders[$i]['customer'] = $this->db->selectOne(   // ← runs 50 times
        'SELECT name, email FROM customers WHERE id = ?',
        [$row['customer_id']],
    );
}

It hides from casual inspection for three reasons. The development machine is fast enough that a page loads in 200 ms with 51 queries. The page looks correct. And the query log shows fifty identical statements, which reads as a repetition rather than as a defect.

Assert the query count in a test. One line — $this->assertLessThan(5, $this->db->count()) after a request that renders fifty rows — turns a silent performance regression into a build failure. This is the highest-leverage performance test available, because it costs nothing to run and it catches the problem at the moment it is introduced rather than after it has been in production for a month.

Three fixes, in order of preference.

// 1. Eager load with a JOIN, when the relation is mandatory.
$rows = $this->db->select(
    'SELECT o.id, o.status, c.name AS customer_name, c.email AS customer_email'
  . '  FROM orders o'
  . '  JOIN customers c ON c.id = o.customer_id'
  . ' WHERE o.account_id = ?'
  . ' ORDER BY o.placed_at DESC'
  . ' LIMIT 50',
    [$accountId],
);

// 2. Batch with an IN clause, when the relation is optional or one-to-many.
$customerIds = array_unique(array_column($rows, 'customer_id'));

$customers = [];

if ($customerIds !== []) {
    $placeholders = implode(', ', array_fill(0, count($customerIds), '?'));

    foreach ($this->db->select(
        "SELECT id, name, email FROM customers WHERE id IN ({$placeholders})",
        array_values($customerIds),
    ) as $customer) {
        $customers[$customer['id']] = $customer;
    }
}

// 3. Precompute in the query, when the value is arithmetic rather than a row.
$rows = $this->db->select(
    'SELECT id, status, (net_cents + tax_cents) AS total_cents, COUNT(*) OVER () AS total_count'
  . '  FROM orders WHERE account_id = ? ORDER BY placed_at DESC LIMIT 50',
    [$accountId],
);

The aggregate case deserves a note, because it produces the other common N+1 — one COUNT(*) per page of results, for pagination:

// A window function gives the unpaginated total alongside the page,
//    //    in the same round trip. The keyset pagination from chapter 7.5
//    //    does not need this at all, which is its other advantage.
$sql = 'SELECT id, status, COUNT(*) OVER () AS total_count'
     . '  FROM orders WHERE account_id = ?'
     . ' ORDER BY placed_at DESC LIMIT ? OFFSET ?';

A JOIN does not fix a one-to-many N+1; it creates a different problem. Joining twenty line items onto three orders returns sixty rows, and the order data is repeated. That is a cartesian multiplication in disguise, and the code that follows must either group — which costs memory and a GROUP BY — or accidentally render each order three times. For a to-many relation, the batch IN approach is correct: one query for the parents, one for the children, and the assembly in PHP where it belongs.

Lazy loading, which is the mechanism that creates N+1 queries, deserves an explicit decision. It is convenient in an ORM and it is a defect in a hand-written repository: an object that fetches data on property access turns a single read into an unpredictable number of queries determined by which code paths touched it.

// Wrong. The query count depends on which properties are read,
//    //    which means it is unknowable from reading the repository.
final class Order
{
    public function customer(): Customer
    {
        return $this->db->selectOne('SELECT * FROM customers WHERE id = ?', [$this->customerId]);
    }
}

// Right. The dependency is explicit in the signature, so the query
//    //    count is visible in the code that triggers it.
final class OrderRepository
{
    public function findWithCustomer(OrderId $id): ?OrderWithCustomer;
    public function findAllWithCustomers(AccountId $account, int $limit): array;
}

// The query-count guard. Put it in the base test case so every
// //    feature test gets it for free.
protected function assertQueryCountAtMost(int $max, string $context = ''): void
{
    $this->assertLessThanOrEqual(
        $max,
        $this->db->count(),
        sprintf('Expected at most %d queries%s, ran %d: %s', $max, $context, $this->db->count(), $this->slowestQueries(3)),
    );
}

17.3 Profiling request execution

Timing the four distinct costs in a request, and the tools that report each one accurately.

A slow request has four separable costs. Measuring which one dominates determines the fix, and the fixes are unrelated to each other.

Network to third parties20 to 2000 msOutbound timing in the loggerCache, batch, or move off the request path

# A minimal timing instrument. Attach to the log context rather than
//    to a response header, so it is queryable.
final class RequestTimer
{
    private array $spans = [];
    private float $startedAt;

    public function start(): void
    {
        $this->startedAt = hrtime(true);
    }

    public function span(string $name, callable $work): mixed
    {
        $from = hrtime(true);

        try {
            return $work();
        } finally {
            $this->spans[$name] = ($this->spans[$name] ?? 0) + (hrtime(true) - $from) / 1_000_000;
        }
    }

    public function report(): array
    {
        $total = (hrtime(true) - $this->startedAt) / 1_000_000;

        return [
            'total_ms'   => round($total, 2),
            'db_ms'       => round($this->spans['db'] ?? 0, 2),
            'db_queries'  => count($this->db->queries()),
            'http_ms'     => round($this->spans['http'] ?? 0, 2),
            'view_ms'     => round($this->spans['view'] ?? 0, 2),
            'spans'       => $this->spans,
        ];
    }
}

The slow query log is the highest-value tool on a PHP-FPM deployment, and it costs nothing to enable:

# MySQL. min_examined_row_ratio catches the queries that examined many
#    rows and returned few, which is where missing indexes show up.
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.2;
SET GLOBAL log_queries_not_using_indexes = 'ON';
SET GLOBAL min_examined_row_limit = 1000;

# Then read the plan for the queries it names.
EXPLAIN SELECT id, status FROM orders WHERE account_id = ? ORDER BY placed_at DESC LIMIT 50;

What a plan tells you, and what each problem looks like:

Plan outputMeaningFix
type: ALLFull table scanAdd an index on the filter or sort column
Using filesortThe sort cannot use an indexIndex the columns in sort order, or sort a smaller set
Using temporaryAn intermediate table, usually for a group or distinctUsually acceptable; check whether the row count justifies it
rows: 48000 on a returning-1-row queryA missing or unusable indexThe single most common cause of a slow endpoint
key: NULLNo index used despite existingUsually a type mismatch: comparing a string column to a number

A function call count is often more actionable than wall time. A wall-clock profile says "40 ms in this method", which invites micro-optimisation. A call count says "this method was called 1 400 times", which usually points at a loop, a repeated computation, or a missing batch. When you find a hot method, ask how many times it is invoked before you ask how long each invocation takes — the first question has a structural answer far more often than the second.

Profiling tools available on PHP 8.3, and what each is actually for:

  • Excimer — sampling, low overhead, shows where wall time goes across the whole request. The right default for a production-shaped profile.
  • Xdebug — full function traces with arguments and memory. Enormously informative and far too slow for anything resembling production; use it locally against a feature test.
  • Blackfire — a commercial continuous profiler that records call graphs in production with low overhead. The right answer at scale, and worth the cost once traffic justifies it.
  • A database-side profiler — for slow query logs, EXPLAIN, and statement-level statistics. Distinct from PHP profiling and often the higher-yield of the two.

17.4 Caching, and when it is the wrong answer

The four cache layers available to a Leaf application, the invalidation problem each one has, and the cases where a cache makes correctness worse.

Four layers exist, and they are not alternatives — a fast application usually uses more than one.

LayerStoresInvalidated byTypical hit rate
OpcacheCompiled bytecodeDeploy, via resetNear 100%
Application cacheComputed values in Redis or the filesystemYour code, explicitlyVariable
HTTP cacheWhole responses at a CDN or a proxyHeaders, or a purgeHigh for static, low for personalised
Database cacheQuery results inside the engineWrite, or a TTLEngine-dependent
# An application cache with an explicit key and a real invalidation path.
final class OrderCache
{
    public function __construct(
        private Redis $redis,
        private Clock $clock,
    ) {}

    public function get(OrderId $id): ?OrderView
    {
        $raw = $this->redis->get($this->key($id));

        if ($raw === null) {
            return null;
        }

        $decoded = json_decode($raw, true);

        // 1. A version and an expiry are both stored. A cache entry
        //    //    without a version cannot be invalidated precisely.
        if ($decoded['v'] !== self::VERSION) {
            return null;
        }

        return OrderView::fromArray($decoded['data']);
    }

    public function put(OrderView $view): void
    {
        $this->redis->setex(
            $this->key($view->id),
            300,
            json_encode(['v' => self::VERSION, 'data' => $view->toArray()]),
        );
    }

    public function forget(OrderId $id): void
    {
        // 2. Explicit invalidation on write. A TTL alone means a stale
        //    //    value for up to its lifetime, which for a status field is
    //    //    long enough to be a support ticket.
        $this->redis->del($this->key($id));
    }

    private function key(OrderId $id): string
    {
        // 3. A namespaced key. An unprefixed key collides with any
    //    //    other application sharing the Redis instance.
        return "orders:v1:order:{$id}";
    }
}

A cache in front of a permissions check is a data leak. The pattern that appears in a hurry: cache the order view, look up the order from the cache, render it. The problem is that the authorisation step now depends on data whose freshness you no longer control, and a permission change does not invalidate the entry. Either authorise before reading the cache — which is the correct order — or include the actor’s identity in the key, which is correct but makes the hit rate depend on the user population. The first option is nearly always better.

// Correct: authorise against the source of truth, then read the cache.
public function show(Request $request, int $id): Response
{
    $order = $this->orders->find(new OrderId($id));   // always fresh

    if ($order === null) {
        return response()->json(['error' => 'not_found'], status: 404);
    }

    $this->policy->assertMayView($request->user(), $order);   // against the real record

    $view = $this->cache->get($order->id()) ?? $this->toView($order);

    return response()->json($view);
}

Where caching is the wrong answer:

SituationWhy caching does not help
The query is fast and indexedA round trip to Redis costs more than the query it replaced
The data is unique per userHit rate collapses to whatever fraction of requests repeat, often under 20%
Invalidation is hard to specifyYou will ship a stale-data bug to save a query that takes 2 ms
Read and write are balancedEvery write needs an invalidation, so the cost is paid constantly for a rare read win
Correctness depends on current dataBalances, permissions, stock levels: a stale value here is a business error, not a slow page

For HTTP caching, the headers are the mechanism and they are worth getting right for anything public:

return response()->json($data)
    ->header('Cache-Control', 'public, max-age=60, s-maxage=300, stale-while-revalidate=600', replace: true)
    ->header('ETag', $etag)
    ->header('Vary', 'Accept-Encoding, Accept', replace: true);

And for anything authenticated, the header that prevents the worst possible caching outcome:

// Without this, a shared cache may store one user's response and
//    //    serve it to the next user. It is the most serious caching bug
//    //    available to a web application.
->header('Cache-Control', 'private, no-store', replace: true)

Set Cache-Control: no-store by default and remove it deliberately. The default in every response should be the safe one, and each place that opts into caching should be a decision someone made on purpose. A blanket public default, or a default that depends on whether the handler remembered to set something, is how one user’s data reaches another user.

17.5 Measuring honestly

Load testing methodology, the three numbers that matter, and the difference between a benchmark and a measurement.

A benchmark measures a thing under ideal conditions. A measurement reflects the conditions your users experience. Confusing the two produces optimisation work that improves a number nobody sees.

NumberDefinitionWhat it tells you
p50 latencyMedian response timeThe experience of a typical request
p95 / p99 latency95th / 99th percentileThe experience of your unluckiest users, and where timeouts and abandonments come from
ThroughputRequests per second at a target latencyCapacity. The number that determines when you scale

An average latency is close to useless for capacity planning. A service with a 20 ms average can have a p99 of four seconds, and four seconds is where users abandon and where your load balancer starts returning 504s. Report p95 and p99, and set your scaling and alerting thresholds on those. If a monitoring dashboard shows only a mean, the number describing your worst experience is one nobody is watching.

# A load test that measures what matters. Note the percentile output
# //    and the explicit target latency assertion.
hey -n 5000 -c 50 -t 5 -m GET,POST,JSON \
    -H "Content-Type: application/json" \
    -D "tests/fixtures/order.json" \
    https://staging.example.com/api/v1/orders

# 50%  23ms
# 75%  41ms
# 90%  88ms
# 95%  134ms
# 99%  612ms     ← the number that explains the support tickets
# 99.9% 1840ms

Methodology points that determine whether a load test is informative:

  • Test against production-shaped data. A table with a thousand rows will never reveal a query that degrades. Seed a realistic volume, and ideally test the query’s plan as the table grows.
  • Run it long enough for the slow paths to appear. Garbage collection, a cache expiring mid-run, and a connection pool filling all show up at minute three and not at second ten.
  • Watch the server, not only the client. A client-side measurement through a saturated connection reports queueing as latency. Record CPU, memory, and — critically — PHP-FPM’s max_children saturation, which is the earliest signal that you are worker-bound rather than CPU-bound.
  • Load-test the read path and the write path separately. They have entirely different characteristics, and a write test at realistic concurrency is where lock contention appears.
# php-fpm status, polled during a run. The queue length is the signal.
curl -s http://127.0.0.1/status?full \
  | grep -E "listen queue|active processes|idle processes|max active processes|max children reached"

Record the baseline before you optimise, and re-measure the same way. A change that improves p50 by 5 ms and worsens p99 by 200 ms has made the application worse for the users who were already struggling. Without a recorded baseline and an identical methodology, the second measurement is not comparable to the first, and the most common outcome of a performance project is a confidently reported number that means nothing.

A closing point on the order of work. Fix queries and indexes before adding caches, because a cache in front of a bad query makes the query bad and the cache complicated. Fix the N+1 before tuning opcache, because the N+1 is measured in round trips and opcache does not affect round trips. Add a cache only after the underlying operation is correct and indexed, and only where the invalidation can be stated in one sentence. In that order, most performance problems are solved before the word "cache" is needed.

18.1 Output encoding by context

Cross-site scripting is a failure of context selection, and each output context requires a different transformation.

Escaping is not one function. The correct transformation depends on where the value lands, and using the wrong one is a vulnerability even though the value was "escaped".

ContextTransformationFailure if wrong
HTML text nodehtmlspecialchars with ENT_QUOTESMarkup injected as content
HTML attributeSame, plus real quotes around the valueBreak out of the attribute, add an event handler
URL in href or srcPercent-encode, and allow-list the schemejavascript: and data: execute
JavaScriptjson_encode with the hex flagsBreak out of the string or the script element

// A single escaping helper, so the context is a required argument and
//    //    not a decision made at each call site.
final class Escaper
{
    public static function html(?string $value): string
    {
        return htmlspecialchars($value ?? '', ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5, 'UTF-8');
    }

    // ENT_SUBSTITUTE replaces invalid byte sequences with a
    //    //    //    replacement character instead of returning an empty
    //    //    //    string. The default behaviour silently blanks the
    //    //    //    output, which hides the bug rather than fixing it.

    public static function attribute(?string $value): string
    {
        return self::html($value);
    }

    public static function url(?string $value): string
    {
        $value = trim($value ?? '');

        if ($value === '') {
            return '#';
        }

        // 1. Scheme allow-list. Escaping does not stop javascript:
        //    //    //    because it contains nothing to escape.
        $scheme = strtolower((string) parse_url($value, PHP_URL_SCHEME));
        $relative = str_starts_with($value, '/') && !str_starts_with($value, '//');

        if (!$relative && !in_array($scheme, ['http', 'https', 'mailto'], true)) {
            return '#';
        }

        // 2. Percent-encode the characters that break out of an
        //    //    attribute, then escape for HTML as well.
        return self::html(rawurlencode($value));
    }

    public static function json(mixed $value): string
    {
        return (string) json_encode(
            $value,
            JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_THROW_ON_ERROR,
        );
    }
}

DOM-based injection defeats server-side escaping entirely. If a template puts a value into a data- attribute and JavaScript later writes it into the DOM with innerHTML, the server escaped it correctly for HTML and the browser still executed it, because innerHTML parses rather than treats text. The rule for the client side is the same as the server side: use textContent rather than innerHTML unless you are inserting markup you generated, and never build a selector or an attribute value by string concatenation from a value the page displays.

// Client side. textContent treats the value as data. innerHTML parses it.
element.textContent = value;                       // safe
element.innerHTML = escapeHtml(value);            // safe, but re-implements a server helper badly
element.innerHTML = value;                         // XSS
element.setAttribute('title', value);          // safe
element.setAttribute('onclick', value);       // XSS — attribute name, not value

Content Security Policy is the structural control that limits the damage when an injection does occur, and the two directives that matter most are script-src and object-src:

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{RANDOM_PER_RESPONSE}';
  style-src 'self';
  img-src 'self' data:;
  font-src 'self';
  connect-src 'self' https://api.example.com;
  object-src 'none';
  base-uri 'none';
  form-action 'self';
  frame-ancestors 'none';
  upgrade-insecure-requests

A nonce or a hash, not 'unsafe-inline'. script-src 'self' 'unsafe-inline' removes most of CSP’s value, because an injected inline script is exactly what it is there to stop. A per-response nonce — random, generated once per response, and applied to every legitimate script tag — is the practical mechanism for a server-rendered application. The equivalent for a stylesheet is a hash of the file, which pairs naturally with the fingerprinting from chapter 15.

// Generate one nonce per response and expose it to templates.
$nonce = base64_encode(random_bytes(16));
$request->cspNonce = $nonce;

// In the layout
<meta http-equiv="Content-Security-Policy" content="script-src 'self' 'nonce-<?= $this->escape($nonce) ?>'">
<script nonce="<?= $this->escape($nonce) ?>" src="/assets/app.7d3e88f1.js" defer></script>

18.2 Header injection and response splitting

The response-splitting attack, why PHP’s protection is not sufficient to rely on, and the sanitising rule for every header value.

A newline in a header value terminates the header and starts a new one. If a request parameter is reflected into a header, an attacker can inject a second header, a whole second response, or a Set-Cookie that fixes a session.

// Vulnerable. A "filename" parameter containing CRLF injects headers.
return response()->download($path, $request->query('filename'));

// Safe. Strip control characters, then constrain the character set.
final class HeaderValue
{
    public static function sanitize(string $value): string
    {
        // 1. Remove every control character, including the ones PHP's
        //    //    own check may not consider a header terminator.
        $clean = preg_replace('/[\x00-\x1F\x7F]/', '', $value) ?? '';

        // 2. Constrain to what a header value may legitimately contain.
        $clean = preg_replace('/[^\x20-\x7E]/', '', $clean) ?? '';

        return $clean;
    }

    public static function filename(string $name): string
    {
        $base = basename($name);            // no path components
        $base = self::sanitize($base);

        // 3. An allow-list of extensions and a bounded length.
        $extension = strtolower(pathinfo($base, PATHINFO_EXTENSION));

        if (!in_array($extension, ['pdf', 'csv', 'png', 'jpg'], true)) {
            throw new InvalidFilename($name);
        }

        return substr($base, 0, 100);
    }
}

Never reflect a request value into a header, even after sanitising. The safe design is that no user-supplied value appears in a response header at all. A Location redirect target built from user input is the usual exception, and it needs a scheme and host allow-list as in chapter 13.2 — sanitising the characters is not sufficient when the value’s meaning is the hazard. Where a value must be echoed, echo it in the body, where escaping applies, and leave the headers to constants.

The related attack on Set-Cookie deserves separate mention, because it is specific to cookies and it is the one that turns a header injection into a session compromise:

// Never build a cookie from a request value.
//    A value containing "; path=/" or a newline can rewrite the
//    //    attributes of the cookie or append a second one.
$response->cookie(name: 'locale', value: $request->query('locale'));

// Safe: an allow-list, and never raw input.
$locale = in_array($requested, ['en', 'fr', 'de'], true) ? $requested : 'en';

$response->cookie(
    name:     'locale',
    value:    $locale,
    path:     '/',
    secure:   true,
    httpOnly: false,   // a locale cookie is read by JavaScript deliberately
    sameSite: 'Lax',
);

PHP raises a warning rather than a fatal for an injected newline, which is the problem. In most configurations header() silently refuses a value containing a newline and emits a warning. If display_errors is off, the request completes with the header missing, and the failure mode depends on which header was dropped. Do not rely on the runtime’s rejection as your control. Sanitise at the point of use so the value is safe by construction, and add a test that submits a value containing "\r\nSet-Cookie: a=b" and asserts the response contains exactly one Set-Cookie header.

18.3 File uploads and storage

The complete control set for accepting a file, the storage location that makes the earlier checks effective, and the parser that undoes all of them.

The four checks from chapter 5.3 are necessary. The storage decision is what makes them sufficient.

final class UploadValidator
{
    private const MAX_BYTES = 5 * 1024 * 1024;

    public function __construct(
        private array $allowedMime,        // ['image/png', 'image/jpeg', 'image/webp']
        private int $maxWidth = 4000,
        private int $maxHeight = 4000,
    ) {}

    /** @return array{name: string, bytes: string, mime: string} */
    public function validate(array $upload): array
    {
        // 1. Transfer status. A partial upload is an error, not a
    //    //    file, and the codes are the only way to tell.
        $error = $upload['error'] ?? UPLOAD_ERR_NO_FILE;

        if ($error !== UPLOAD_ERR_OK) {
            throw new UploadFailed(match ($error) {
                UPLOAD_ERR_INI_SIZE, UPLOAD_ERR_FORM_SIZE => 'too_large',
                UPLOAD_ERR_PARTIAL                        => 'incomplete',
                UPLOAD_ERR_NO_FILE                        => 'required',
                default                                   => 'failed',
            });
        }

        // 2. Size. PHP's own limits are configurable and may be
        //    //    larger than what the application should accept.
        if ((int) $upload['size'] > self::MAX_BYTES) {
            throw new UploadTooLarge(self::MAX_BYTES);
        }

        $bytes = file_get_contents($upload['tmp_name']);

        if ($bytes === false) {
            throw new UploadFailed('unreadable');
        }

        // 3. Type by content inspection. The client-supplied type and
        //    //    the filename are both attacker-controlled.
        $mime = (new finfo(FILEINFO_MIME_TYPE))->buffer($bytes);

        if (!in_array($mime, $this->allowedMime, true)) {
            throw new UnsupportedType($mime);
        }

        // 4. Structure, for images. A valid PNG that is 40000 pixels
        //    //    tall is a decompression bomb: tiny on disk, enormous in
        //    //    memory when decoded.
        if (str_starts_with($mime, 'image/')) {
            $size = @getimagesizefromstring($bytes);

            if ($size === false || $size[0] > $this->maxWidth || $size[1] > $this->maxHeight) {
                throw new InvalidImage($size === false ? 'unreadable' : 'too_large');
            }
        }

        // 5. The stored name is generated, never derived from the
        //    //    client. The extension comes from the inspected type, not
        //    //    from the submitted one.
        $extension = match ($mime) {
            'image/png'  => 'png',
            'image/jpeg' => 'jpg',
            'image/webp' => 'webp',
            default => throw new UnsupportedType($mime),
        };

        return [
            'name'  => bin2hex(random_bytes(16)) . '.' . $extension,
            'bytes' => $bytes,
            'mime'  => $mime,
        ];
    }
}

Store uploads outside the document root and serve them through a handler. A file under public/ is reachable by URL, and if its extension is one the server will execute — or if the server is configured to execute anything under public/ — then a validated image is one misconfiguration away from remote code execution. Storing under storage/uploads/ and serving through a controller removes the class of problem entirely: the web server never maps a request to a file path.

// The serving handler. It knows the id, resolves the path from its own
//    //    mapping, and never takes a path from the request.
final class UploadController
{
    public function show(Request $request, string $id): Response
    {
        if (preg_match('/^[0-9a-f]{32}\.(png|jpg|webp)$/', $id) !== 1) {
            throw new NotFound('file');
        }

        $record = $this->uploads->findById($id);

        if ($record === null || !$this->policy->assertMayView($request->user(), $record)) {
            throw new NotFound('file');
        }

        $path = $this->storage->pathFor($record);   // derived, not from the request

        if (!is_file($path)) {
            throw new NotFound('file');
        }

        return response()->make(
            status: 200,
        )
            ->withBody((string) file_get_contents($path))
            ->header('Content-Type', $record->mime)
            ->header('Content-Length', (string) filesize($path))
            ->header('X-Content-Type-Options', 'nosniff')
            ->header('Content-Disposition', 'inline; filename="' . $record->storedName . '"')
            ->header('Cache-Control', 'private, max-age=86400');
    }
}

Most of these are meaningless over plain HTTP. Secure cookies, HSTS, and the confidentiality of a bearer token all assume the transport is encrypted. Redirecting HTTP to HTTPS is necessary and insufficient: the first request is still exposed, and HSTS is what closes that window — but only once a client has received the header over a secure connection. A deployment that terminates TLS at a load balancer and forwards to PHP over plain HTTP internally is fine, provided the client-facing hop is encrypted and X-Forwarded-Proto is set so the application can tell which it was.

# Middleware that honours the proxy's protocol header. Without this, a
//    //    Secure cookie behind a TLS-terminating proxy is never set,
//    //    because the application believes the request was plain HTTP.
final class TrustProxyProtocol
{
    public function before(Request $request): ?Response
    {
        $forwarded = $_SERVER['HTTP_X_FORWARDED_PROTO'] ?? '';

        if ($forwarded === 'https') {
            $_SERVER['HTTPS']       = 'on';
            $_SERVER['SERVER_PORT'] = '443';
        }

        return null;
    }
}

// And the redirect, for anything that arrives over plain HTTP.
final class EnforceHttps
{
    public function before(Request $request): ?Response
    {
        if (($_SERVER['HTTPS'] ?? '') === 'on') {
            return null;
        }

        $uri = $_SERVER['REQUEST_URI'] ?? '/';

        return response()->redirect('https://' . $_SERVER['HTTP_HOST'] . $uri, 301);
    }
}

Only trust X-Forwarded-* headers from a proxy you control, and strip the inbound ones. These headers are request headers, which means a client can send them. If the application honours X-Forwarded-For to determine the client address and the proxy does not strip it, an attacker sets their apparent address to anything — defeating rate limits, poisoning audit logs, and bypassing an address allow-list. Configure the proxy to overwrite rather than append, and configure the application to trust only known proxy addresses.

19.2 Document root and the rewrite layer

Pointing the server at the right directory, the rewrite that routes everything else to the entry point, and the three misconfigurations that expose the codebase.

The document root is public/. Everything else — application code, configuration, dependencies, logs, sessions — is one level above it and therefore unreachable by URL. This is the single highest-value deployment decision in a PHP application.

# nginx
server {
    listen 80;
    server_name orders.example.com;
    return 301 https://orders.example.com$request_uri;
}

server {
    listen 443 ssl http2;
    server_name orders.example.com;

    root /var/www/orders/current/public;   // current, not the release directory
    index index.php;

    ssl_certificate     /etc/letsencrypt/live/orders.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/orders.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    client_max_body_size 8M;      // must match the upload validator's limit

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ ^/index\.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        fastcgi_param APP_ENV production;
        fastcgi_read_timeout 30s;
    }

    # Any other .php file is not executable. This is the control that
    # //    survives a file being written into public/ by mistake.
    location ~ \.php$ {
        return 404;
    }

    location ~ /\. {
        deny all;
    }

    location ~* ^/assets/.+\.[0-9a-f]{8,}\.(css|js|woff2?|png|svg|jpg|webp)$ {
        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable" always;
        access_log off;
    }
}

<VirtualHost *:443>

Three misconfigurations account for most PHP disclosure incidents. The document root pointing at the project root instead of public/, which serves .env and composer.json. A permissive AllowOverride with a rewrite that matches every request including existing files, which lets a request for app/Domain/Order.php reach the PHP handler. And a php_flag or php_admin_value set in a virtual host that permits .htaccess to be uploaded, at which point an attacker writes their own configuration.

# public/.htaccess — the correct rule, and the subtlety that matters.
<IfModule mod_rewrite.c>
    RewriteEngine On

    # RewriteBase /
    # The -f test is the whole point. Without it, a request for an
    # //    existing file is rewritten to index.php and PHP executes it,
    # //    which means a .php file anywhere under public/ is a
    # //    directly reachable script.
    RewriteCond %{REQUEST_FILENAME} !-f
    RewriteCond %{REQUEST_FILENAME} !-d
    RewriteRule ^ index.php [L]
</IfModule>

<FilesMatch "^\.">
    Require all denied
</FilesMatch>

Verifying the result, rather than assuming it:

# Each of these must return 404, and none may return content.
for path in \
    "/.env" \
    "/composer.json" \
    "/config/config.php" \

The symlink-and-release layout is what makes rollback possible. /var/www/orders/releases/2026-09-29T14-02-11/ holds one immutable deploy, and /var/www/orders/current is a symlink to it. A rollback is ln -sfn to the previous release and a reload — two operations, both reversible, and neither involving a code change. The cost is a few hundred megabytes of disk for retained releases, which is the cheapest possible insurance against a bad deploy.

A hard restart under load is an outage. systemctl restart php8.3-fpm kills in-flight requests, and a deploy that does this during traffic produces a burst of 502s. Use ExecReload with SIGUSR2, which reloads the pool gracefully: the old workers finish their current requests and exit, and new workers pick up the changed configuration. TimeoutStopSec must be longer than the longest request, or systemd kills the workers the graceful shutdown was waiting for.

A health check, which should verify the application and not merely that a port is open:

# The route. Registered first, and excluded from the throttle and the
#    //    session layer, because a health check that creates a session
#    //    file per probe is its own problem.
$app->get('/healthz', function () use ($db, $redis) {
    try {
        $from = hrtime(true);

        $db->selectOne('SELECT 1');
        $dbMs = (hrtime(true) - $from) / 1_000_000;

        $from = hrtime(true);
        $redis->ping();
        $redisMs = (hrtime(true) - $from) / 1_000_000;

        return response()->json([
            'status'   => 'ok',
            'database_ms' => round($dbMs, 2),
            'redis_ms'   => round($redisMs, 2),
        ]);
    } catch (Throwable $e) {
        // 503, so the load balancer removes this instance. A health
        //    //    check that returns 200 while the database is down
        //    //    keeps traffic arriving at a broken instance.
        return response()->json(['status' => 'unhealthy'], status: 503);
    }
})->name('healthz');

Distinguish liveness from readiness. A liveness probe answers "should this process be restarted", and a readiness probe answers "should this instance receive traffic". A database outage should fail readiness and remove the instance from rotation, not fail liveness and trigger a restart loop — restarting every instance because the database is down turns a dependency failure into a full outage plus a thundering herd of reconnect attempts.

19.4 The deploy pipeline and asset ordering

The ordered sequence of a zero-downtime release, and the three ordering constraints that determine whether it works.

A deployment that changes the running code has an order. Three constraints are absolute:

ConstraintReason
Assets before the code that references themChapter 15: a request arriving between the two gets HTML naming a file that does not exist
Additive migrations before the code that needs the columnChapter 7: old code runs against the new schema during the transition
Code before the migration that makes it requiredThe reverse: code that requires a column before it exists

The sequence, for a release that changes both a column and the code that writes it:

#!/usr/bin/env bash
set -euo pipefail

RELEASE=$(date -u +%Y-%m-%dT%H-%M-%S)
BASE=/var/www/orders
TARGET="${BASE}/releases/${RELEASE}"

# 1. Build the release from an immutable artefact. No network, no
#    environment-specific values baked in.
git clone --depth 1 --branch "${GIT_REF}" "${REPO}" "${TARGET}"
cd "${TARGET}"

# 2. Dependencies from the lock file, with the dev requirements omitted.
composer install \
    --no-dev \
    --no-interaction \
    --no-progress \
    --optimize-autoloader \
    --classmap-authoritative

# 3. Build assets. This must complete before the release becomes current.
php tools/build-assets.php

# 4. Writable directories, owned by the application user and not the deploy user.
mkdir -p var/cache var/logs storage/sessions
chown -R app:www-data var storage
chmod -R 775 var storage

# 5. Configuration assertions, before anything is switched.
set -a; . /etc/orders/orders.env; set +a
: "${APP_ENV:?}" "${APP_KEY:?}" "${DB_DSN:?}" "${DB_PASSWORD:?}"
[ "${APP_ENV}" != "production" ] || [ "${APP_DEBUG}" = "false" ] \
    || { echo "APP_DEBUG must be false in production" >&2; exit 1; }

# 6. Smoke test against the new release, on its own port, before the switch.
php -S 127.0.0.1:9099 -t public public/index.php &
SMOKE_PID=$!
trap 'kill ${SMOKE_PID}' EXIT
sleep 1

curl -fsS http://127.0.0.1:9099/healthz | grep -q '"status":"ok"'
kill "${SMOKE_PID}"; trap - EXIT

# 7. Expand-then-contract migrations. Additive first; the contract runs
#    after the new code is live and the old code is gone.
php bin/console migrate --step

# 8. Switch. A symlink change plus a graceful reload.
ln -sfn "${TARGET}" "${BASE}/current.new"
mv -Tf "${BASE}/current.new" "${BASE}/current"
systemctl reload php8.3-fpm

# 9. Verify the switched release. A failed check here rolls back.
sleep 2
if ! curl -fsS https://orders.example.com/healthz | grep -q '"status":"ok"'; then
    echo "Health check failed after switch; rolling back" >&2
    PREVIOUS=$(ls -1dt "${BASE}"/releases/* | sed -n 2p)
    ln -sfn "${PREVIOUS}" "${BASE}/current"
    systemctl reload php8.3-fpm
    exit 1
fi

# 10. Retain the last few releases for rollback; remove the rest.
ls -1dt "${BASE}"/releases/* | tail -n +4 | xargs rm -rf

echo "Deployed ${RELEASE}"

Keep the rollback path in the deploy script. A rollback procedure written down in a wiki is a procedure nobody executes correctly under pressure. Putting the four lines that restore the previous symlink next to the lines that switch forward means the rollback is a tested code path with a known-good command, and step 9 can invoke it automatically without a human deciding anything.

Composer flags, each of which matters for a production deploy:

FlagEffectWhy it matters here
--no-devSkips require-devA smaller attack surface and a smaller image; also catches a missing --no-dev by leaving a test dependency in production
--optimize-autoloaderBuilds an optimised classmapFaster resolution and, with the next flag, no filesystem probing
--classmap-authoritativeDisables PSR-4 fallback entirelyAny class not in the classmap fails immediately rather than probing the filesystem on a request — which also means a missing file is a fast 500, not a slow one
--no-scriptsSkips post-install scriptsArbitrary code from a dependency running as your deploy user. Add it once you have verified which scripts are needed

Composer scripts run with the privileges of whoever ran Composer. A post-install script in a dependency is arbitrary code execution on your build host, with your credentials in the environment. The mitigations are to run the build in a container with no production credentials, to review what scripts your dependencies declare, and to use --no-scripts where the application does not genuinely need them. A build host with production database access is a single point of failure for the whole system.

19.5 Shared hosting, and moving beyond it

What shared hosting forces you to accept, the four constraints that shape your design, and the migration triggers worth watching for.

Shared hosting is a real deployment target for a Leaf application, and the framework’s small footprint suits it. It is also a genuinely constrained environment, and the honest thing is to say which capabilities are unavailable rather than to discover them during an incident.

ConstraintTypical limitConsequence for the application
No process managerShared PHP-FPM poolNo custom opcache, pool, or timeout settings. Sizing is not yours
Document root fixedUsually public_html/You can rename it, and some hosts offer a subdomain pointing elsewhere. Verify before relying on it
No shell or no SSHVaries widelyNo Composer deploy, no migrations, no cron. This is the constraint that shapes everything else
Filesystem writableYour account’s directorySessions, logs, and cache live inside a web-reachable tree. Chapter 18's rules become essential, not optional
No RedisUsuallyFile or database sessions only. Database sessions add write load to the same database the app uses
No reverse proxyUsuallyNo HTTP caching layer, no header rewriting, no request logging you control
# Shared hosting: the document root is fixed, so the application adapts.
#    //    The entry point lives in the document root and reaches up
//    //    for everything else. Verify with a request for /.env and
//    //    for /app/Domain/Money/Cents.php before trusting it.

<?php

declare(strict_types=1);

# public_html/index.php on shared hosting
$root = dirname(__DIR__);   // the directory above public_html

require $root . '/vendor/autoload.php';

$app = require $root . '/bootstrap/app.php';

$app->run();

# .htaccess in public_html — the rewrite, plus the denials that matter
//    //    more when the document root cannot be narrowed.
<IfModule mod_rewrite.c>
    RewriteEngine On

    RewriteCond %{REQUEST_FILENAME} !-f
    RewriteCond %{REQUEST_FILENAME} !-d
    RewriteRule ^ index.php [L]
</IfModule>

# Deny the sensitive files by name, as a second layer in case the
//    //    directory above the document root becomes reachable.
<FilesMatch "^(\.env|\.gitignore|composer\.(json|lock)|.*\.sql|.*\.log|.*\.md)$">
    Require all denied
</FilesMatch>

The compensating controls for a shared document root are necessary, not sufficient. Denying .env by name covers the common case. It does not cover a backup you make with a different name, a log file with an unusual extension, or a file created by a dependency you have not read. If your host will not let you set the document root to a subdirectory containing only the entry point, then the application is running one control layer below where it should, and every other control must be tighter to compensate.

What is achievable on shared hosting, and how:

NeedApproachCaveat
ComposerRun locally, commit vendor/, or upload vendor.zip and have the host extract itCommitting vendor bloats the repository; a build step is better if you have one

CronThe host’s cron, calling a CLI script through the panelTiming is coarse and jobs may be skipped on overloaded hosts

//    web-reachable tree. The file has no PHP opening tag, so a request
//    //    that does reach it returns it as text — which the host's

# var/protected/.htaccess

</FilesMatch>

<IfModule mod_php.c>
    php_flag engine off
</IfModule>

The migration triggers. Shared hosting is a reasonable place to start, and these are the signals that it has become the constraint rather than the context:

TriggerWhy it matters
Deploys take longer than the maintenance window you can justifyUploading files over FTP is the bottleneck, and the risk of a partial upload grows with duration
You cannot run a background workerQueued work has to happen during a request, which means slow responses and a timeout ceiling on any job that takes minutes
Response times vary with other tenantsShared CPU and memory, and no ability to size the process pool
A dependency needs a specific PHP extensionExtension availability is fixed, and a missing one blocks a security upgrade as readily as a feature
You need a second environmentStaging on shared hosting is usually a second plan, and keeping two in sync by hand is how production diverges from what was tested
Log access is a panel and a search boxStructured log queries from chapter 14 are not available, so incident analysis depends on a support ticket

A migration is a change of hosting, not a change of application. If the boundaries from chapter 1 hold — SQL confined to one directory, no framework types in the domain, configuration read from one file, assets served by the web server — then moving to a VM, a container, or a managed platform is a change to the deploy script and nothing else. An application whose conventions were decided against shared hosting is the one that is expensive to move, and the expense shows up in the deploy script rather than in the code.

Write the deploy script before you outgrow shared hosting. Every step in section 19.4 can be run against a local or staging VM today, using the same release directory and symlink structure, with the deploy target being a local path instead of an SFTP upload. When the day comes to move to a proper host, the pipeline is written and the change is a hostname. The alternative is discovering the shape of your deploy process at the moment you are changing hosting, which is the worst possible time.
