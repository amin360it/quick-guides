0 · Orientation

0.1 Three ways to ship an icon0.2 How an icon font actually renders0.3 Choosing per project

Icons are the smallest and most-abused asset class on the web. A single glyph is a few hundred bytes of vector data, yet the decision of how you ship it — a webfont, an inline SVG, or a sprite sheet — determines your page weight, your layout stability, your accessibility story and your build pipeline for the rest of the project. This chapter frames that decision before a single class name is introduced.

The library's two families — Font Awesome and Google Material Symbols — are the most widely deployed icon sets in the world, and both ship in more than one packaging. Understanding the packaging matters more than memorising glyph names, because the packaging is what breaks in production.

0.1 Three ways to ship an icon

There are exactly three delivery mechanisms worth knowing: the icon font, the inline SVG, and the sprite sheet. Each answers the same question — "where does the shape come from at render time?" — with a different answer, and that answer drives everything else.

Icon font: a glyph pretending to be a letter

An icon font is a normal font file whose glyphs happen to be pictures. Each icon sits at a Unicode private-use codepoint, usually in the U+E000–U+F8FF range, so it cannot collide with a real letter. In Font Awesome, fa-house is \f015; in Material Symbols, home is \e88a. You render an icon by asking the browser to draw that codepoint in a font family that has no letters — just picture glyphs.

The consequence is that every icon is text as far as the browser is concerned. It inherits color, font-size, line-height and vertical-align, which makes styling almost free. It also means antialiasing rules, baseline metrics and font smoothing apply, which is where the surprises live: an icon font glyph is positioned on a baseline that was designed for letters, so vertical centring inside a button is never quite exact.

Inline SVG: the shape is shipped per instance

Inline SVG puts the <path d="…"> data directly in your markup. The shape is content, not a font reference, so it renders on the first paint with no network request, never falls back to a box or a stray letter while a font loads, and can be styled per-element with fill, stroke, stroke-width and CSS custom properties.

<!-- Inline SVG: no request, no fallback, per-path styling -->
<svg class="ic" viewBox="0 0 24 24" width="24" height="24"
     fill="none" stroke="currentColor" stroke-width="2"
     stroke-linecap="round" stroke-linejoin="round" aria-hidden="true" focusable="false">
  <path d="M3 10.5 12 3l9 7.5V21H3z"/>
  <path d="M9 21v-6h6v6"/>
</svg>

The obvious cost is repetition. A nav bar with forty icons and twelve inline copies of the same glyph carries twelve copies of the path data. That is why the third option exists.

Sprite sheet: one request, many <use> references

An SVG sprite is a single file containing many <symbol> elements, each with an id. You reference one by name, and the browser paints it. The payload is downloaded once and cached, and per-use markup is tiny.

<!-- icons.svg contains <symbol id="i-home" viewBox="0 0 24 24">…</symbol> -->
<svg class="ic" width="24" height="24" aria-hidden="true">
  <use href="icons.svg#i-home"></use>
</svg>

<!-- Later in the page, the same sprite is already cached -->
<button class="btn" type="button">
  <svg class="ic" width="20" height="20" aria-hidden="true"><use href="icons.svg#i-search"></use></svg>
  <span>Search</span>
</button>

Sprites are the sweet spot for a site with a fixed, curated icon set: you control the payload exactly, there is no font, and there is no runtime library. The cost is process — something must generate and version the sprite — and one real limitation: a cross-document <use> cannot restyle the internals of a symbol from the referencing page in every engine, so a monochrome "currentColor only" design is the safe assumption.

0.2 How an icon font actually renders

Most icon-font bugs are font-loading bugs, not CSS bugs. Knowing the render sequence turns "why did my icons show as empty squares for 300 ms?" into a two-line fix.

Block period, swap period, and the invisible-glyph gap

A webfont goes through three states: block (text is invisible), swap (a fallback font is used), and failure (fallback is permanent). The font-display descriptor decides how long each lasts. For body text you normally want swap; for an icon font you almost never do, because the fallback is a letter. If your icon font is still loading and the fallback applies, there is no tofu box — you get a random character from the fallback font. A \f015 in a fallback font is usually blank or an invisible control glyph, so the icon simply vanishes and the layout shifts.

That is why Font Awesome's stylesheet declares font-display: block for its webfont families: it would rather show nothing for a bounded moment than show the wrong character. The bounded moment is the trade-off. If the font request is slow, "nothing" is what your users look at.

/* What the icon-font family declaration looks like under the hood */
@font-face {
  font-family: "Font Awesome 7 Free";
  font-style: normal;
  font-weight: 900;
  font-display: block; /* not swap: the fallback glyph is meaningless */
  src: url("../webfonts/fa-solid-900.woff2") format("woff2");
}

Why the fallback glyph is the real hazard

Private-use codepoints render as nothing at all in most fallback fonts, which is worse than it sounds: nothing has no width in some engines and a full advance width in others. A row of toolbar icons built from <i> elements therefore collapses, then expands, then settles. Cumulative Layout Shift is measured on exactly this. Inline SVG and sprite icons have no such phase — the shape is in the document from the first frame.

If you self-host an icon font and forget the woff2 file, the entire page does not fail loudly. You get correctly-sized invisible icons, because the CSS loaded and the font did not. Check the Network panel's font requests, not the visual result, when auditing this.

Text-inflation and forced-colour modes

Because an icon font is text, browser text-inflation on mobile can resize it independently of surrounding UI, and Windows High Contrast mode repaints it in a system colour — which is usually what you want for an inline icon and occasionally disastrous for a two-tone or coloured icon. Inline SVG with currentColor and forced-color-adjust gives you explicit control. Icon fonts give you whatever the platform decides.

0.3 Choosing per project

The right answer is a decision about how many distinct icons the project needs and how much of them change at runtime, not about brand preference. Two sets can coexist — a sprite for chrome and a licensed set for content — as long as the system is deliberate.

A decision table

SituationBest choiceWhy
Marketing site, ~20 fixed iconsSVG spriteOne cached request, no font, no library, no layout shift
Admin UI, icons chosen at runtime from a large setIcon font or SVG-with-JSAny glyph is reachable by class name without shipping markup for all of them
Icon colour or shape varies per instanceInline SVGPer-element fill, multi-colour paths, CSS variables
Content authors type icon names in a CMSFont Awesome (CSS)<i class="fa-solid fa-house"> is writable by a non-developer
Strict budget under 100 KB totalHand-picked sprite or subset fontA full icon font is 60–120 KB of woff2 for two or three glyphs
Emails and non-web HTMLRaster PNG onlyMail clients strip webfonts, <style> and often SVG

Mixing sets safely

Font Awesome and Material Symbols can coexist because they are different font families with different class prefixes — .fa-solid versus .material-symbols-outlined — and no selector collides. The real conflicts are load order and size: each family is another blocking font request, and if both are declared with font-display: block you have widened the invisible window.

Write the decision down once, in the project's README, as a sentence: "Icons are an SVG sprite generated from our Figma library; Font Awesome is used only for social brands." Without that sentence, the next developer adds a third system, and you ship all of them.

What this guide assumes

Chapters 1–5 cover Font Awesome in both its packaging modes (CSS webfont and SVG-with-JS), because a real upgrade path has to touch both. Chapter 6 covers Material Symbols and its legacy predecessor. Chapters 7 and 8 are cross-cutting: accessibility and performance apply identically to every approach, and they are where the two libraries differ least and projects fail most.

1 · Font Awesome setup

1.1 The version landscape: 5, 6 and 71.2 CDN versus self-hosting1.3 Kits, Pro, and the JavaScript delivery model

Font Awesome ships in three major generations that are still in production use, in two packaging modes, and through two distribution channels. Which one you pick is decided by three questions: which version, hosted by you or by someone else, and free or paid. This chapter answers all three and gets a working page in front of you.

1.1 The version landscape: 5, 6 and 7

You will meet all three generations. A 2026 project starts on 7, but most tutorials and Stack Overflow answers online describe 5 or 6, and their class names differ. Knowing the deltas prevents you from copying a snippet that silently renders an empty box.

What each generation changed

VersionReleasedStyle prefixesNotes
52017fas, far, fabMagnifying-glass icon is fa-search; 1,500+ free icons
62022fa-solid, fa-regular, fa-brandsSharp family (Pro), duotone colours via CSS variables, legacy name aliases
72025Same as 6Current generation; better tree-shaking, more icons, Sharp in free tier partly

The most disruptive change was not visual. Font Awesome 6 renamed hundreds of icons to descriptive names: fa-search became fa-magnifying-glass, fa-home became fa-house, fa-cog became fa-gear, fa-trash-alt became fa-trash-can. The v6 and v7 stylesheets keep aliases for most v5 names, so old markup usually keeps rendering — but the alias is a compatibility shim, and new code should use the current name.

<!-- v5 markup (still renders in v6/v7 through aliases) -->
<i class="fas fa-search"></i>

<!-- v6 and v7 markup (the documented form) -->
<i class="fa-solid fa-magnifying-glass"></i>

<!-- Keep the old short class off new code: pick one prefix style and stay with it -->

Font family names are version-specific

If you write pseudo-element rules or @font-face overrides, the family name carries the version: "Font Awesome 5 Free", "Font Awesome 6 Free", "Font Awesome 7 Free", plus "…Brands" variants. A rule that names the wrong generation fails silently — the codepoint renders in the fallback font and disappears.

Mixing versions is the classic failure

Because the CSS defines the same class names, loading two generations at once means the later stylesheet wins for every shared class, and the earlier one contributes dead weight plus wrong glyphs for any icon whose codepoint moved. If you must upgrade, remove the old stylesheet in the same commit.

1.2 CDN versus self-hosting

The CDN link is a one-line start and a one-line liability. Self-hosting is more setup and more control. The choice usually comes down to whether you can accept a third-party request on your critical render path.

The CDN link, and what it costs

<!-- Font Awesome 7 free, via jsDelivr (pin the exact version) -->
<link rel="stylesheet"
      href="https://cdn.jsdelivr.net/npm/@fortawesome/fontawesome-free@7/css/all.min.css">

<!-- Or the official CDN -->
<link rel="stylesheet"
      href="https://cdnjs.cloudflare.com/ajax/libs/font-awesome/7.0.0/css/all.min.css"
      integrity="sha512-…" crossorigin="anonymous" referrerpolicy="no-referrer">

The stylesheet itself is small, but it references webfont files on the same host. So a CDN icon is two cross-origin requests on the render path: the CSS, then the woff2 discovered only after the CSS parses. That second round trip cannot be started early, because the URL lives inside the stylesheet. On a cold cache over a slow connection, this is the whole cost of the approach.

The upside is real: the CDN is fast, globally edge-cached, and if several of your projects use the same URL the browser may already have both the CSS and the font in cache.

<!-- Preconnect shortens the handshake, but not the chained request -->
<link rel="preconnect" href="https://cdn.jsdelivr.net" crossorigin>
<link rel="preconnect" href="https://cdnjs.cloudflare.com" crossorigin>

Self-hosting, and why offline libraries prefer it

Self-hosting means copying css/all.min.css and the webfonts/ directory into your project. You get a same-origin request, full control over caching headers and font-display, the ability to subset, and — the reason this guide's library works this way — the ability to run with no network at all.

The trap is the relative path. The shipped CSS points at ../webfonts/, so the directory structure must be preserved:

assets/
  fontawesome/
    css/all.min.css
    webfonts/
      fa-solid-900.woff2
      fa-regular-400.woff2
      fa-brands-400.woff2

<!-- In your document, from the same assets/ root: -->
<link rel="stylesheet" href="assets/fontawesome/css/all.min.css">
If icons render at the correct size but as blank space, the font file 404'd. Open the Network panel, filter by "font", and confirm three 200s. Every self-hosted Font Awesome problem of this shape is a path or a case-sensitivity problem — it works on Windows, then fails on a Linux host because Webfonts and webfonts differ.

1.3 Kits, Pro, and the JavaScript delivery model

A "kit" is Font Awesome's hosted bundle: one script tag that carries your selected icon set, your settings and your optimisation flags. It is the recommended path for Pro and the easiest way to add subsetting without a build step.

What a kit actually is

<!-- Your kit ID is unique per project; this script replaces both the CSS link
     and the SVG-with-JS bundle -->
<script src="https://kit.fontawesome.com/abc123def4.js" crossorigin="anonymous"></script>

The script reads your kit configuration from the server and then either injects a stylesheet (webfont mode), replaces your <i> elements with inline SVG (SVG mode), or both. Because the configuration lives server-side rather than in your repository, changing the icon set does not require a deploy. The cost is the same as any hosted dependency: a third-party script in your critical path, and a document whose behaviour depends on a file you do not version.

Free versus Pro

FeatureFreePro
Solid style~1,600 iconsFull set
Regular style~160 iconsFull set
Brands~500 iconsFull set
Light, Thin, Duotone, SharpNoYes
Icon count~2,000~30,000
Kits, subsetting, custom uploadsLimitedYes

Two practical consequences. First, a Pro-only icon used on a free licence does not throw an error; it renders nothing, and you discover it in review. Second, the free regular style covers only a fraction of the set — fa-regular fa-house exists but most regular icons do not, so a design that assumes "outline version of everything" will not survive contact with the free tier.

<!-- Free tier check: does the regular variant actually exist? -->
<i class="fa-regular fa-heart"></i>        <!-- yes, in free -->
<i class="fa-regular fa-house"></i>        <!-- yes, in free -->
<i class="fa-regular fa-magnifying-glass"></i><!-- no: renders nothing on free -->
Do not load all.min.css and a kit script together. Both install the same class names, both fetch fonts, and the kit's SVG replacement races the CSS rules. Pick one delivery model per project.

2 · Using icons in markup

2.1 Style prefixes: fa-solid, fa-regular, fa-brands2.2 Sizing with the fa-lg through fa-10x scale2.3 Animation: fa-spin, fa-pulse, fa-beat2.4 Rotation, flipping and arbitrary angles

With the stylesheet loaded, an icon is a class name on a disposable element. This chapter covers the three style prefixes that decide which weight of glyph you get, the sizing scale, and the transform and animation utilities that turn a static glyph into a state indicator.

The canonical element is <i>, kept for historical reasons — it is presentational, so screen readers ignore it (which is both the point and, when the icon is meaningful, the problem solved in Chapter 7). A <span> works identically.

2.1 Style prefixes: fa-solid, fa-regular, fa-brands

Font Awesome is not one font, it is several, one per style. The class prefix selects the family and the font weight at once, which is why the prefix is mandatory and why a missing prefix renders a blank icon.

Why two classes are always required

The base .fa rules in pre-v6 markup, and the family rules in v6/v7, only take effect when combined with a style class. A style class alone sets the font family and weight; the icon class alone sets the ::before content and the codepoint. Together they render a glyph. Remove the style class and you have a <span> whose pseudo-element writes a private-use character in an ordinary font — invisible.

<!-- The three free styles -->
<i class="fa-solid fa-house"></i>          <!-- weight 900, filled -->
<i class="fa-regular fa-heart"></i>         <!-- weight 400, outlined -->
<i class="fa-brands fa-github"></i>         <!-- brand logos, own font -->

<!-- Pro-only styles: identical syntax, different family -->
<i class="fa-light fa-house"></i>          <!-- Pro -->
<i class="fa-thin fa-house"></i>           <!-- Pro -->
<i class="fa-duotone fa-house"></i>       <!-- Pro, two-layer -->
<i class="fa-sharp fa-solid fa-house"></i>   <!-- Pro, sharper corners -->

Choosing a style deliberately

Solid reads as UI chrome: toolbars, buttons, navigation. Regular reads as content or as an inactive state, which is why the outline/filled pair is the standard way to show a toggled favourite. Brands are a different font because brand marks are licensed artwork, not icons: they cannot be recoloured into a two-tone scheme, and some are trademark-restricted.

<!-- The conventional toggle: same icon, style changes with state -->
<button class="fav" type="button" aria-pressed="false">
  <i class="fa-regular fa-heart"></i>
  <span class="vh">Add to favourites</span>
</button>

<!-- After a click, swap to the solid weight in JavaScript -->
<script>
  const btn = document.querySelector('.fav .fa-heart');
  // fa-regular -> fa-solid, plus a live announcement
  btn.classList.replace('fa-regular', 'fa-solid');
</script>

Sharps, duotone and the licence boundary

Sharp is a parallel family with lighter strokes that matches a tighter geometric design language; duotone renders a second layer behind the glyph, coloured with --fa-secondary-color and --fa-secondary-opacity. Both are Pro. In a code review, the fastest way to catch a licence violation is to grep for fa-light, fa-thin, fa-duotone and fa-sharp on a project whose kit does not include Pro.

2.2 Sizing with the fa-lg through fa-10x scale

Font Awesome's size utilities multiply the inherited font size. They are convenient and they are also the reason icon alignment drifts, because a multiplier of the parent's text size is not the same as "the right size for this button".

The scale and what it multiplies

fa-xs is 0.75em, fa-sm is 0.875em, fa-lg is 1.333em, and fa-2x through fa-10x are integer multiples. Every one of them sets font-size relative to the inherited size — not to the root. So fa-2x inside a 14 px table cell is 28 px, and the same class inside an 18 px card body is 36 px. That is usually what you want inline with text, and almost never what you want in a component.

<!-- Inline with text: relative sizes track the surrounding copy -->
<p><i class="fa-solid fa-circle-info fa-sm"></i> Small note</p>
<p><i class="fa-solid fa-circle-info"></i> Default</p>
<p><i class="fa-solid fa-circle-info fa-2x"></i> Emphasised</p>

<!-- Component: set the size on the icon itself, not with a multiplier -->
<style>
  .toolbar .fa-solid { font-size: 1.125rem; line-height: 1; }
</style>

Line-height is the alignment bug

Icon glyphs are drawn from the baseline upward, and their advance width comes from the font, not from the drawing. Two icons of different visual width — fa-house and fa-bars — occupy different horizontal space inside the same button, so a row of icon buttons looks ragged. Set line-height: 1 and a fixed width, or use fa-fw (Chapter 3), and give the containing button a grid or flex box that centres it rather than relying on the baseline.

/* Predictable icon button: the box owns the geometry, the glyph is centred */
.icon-btn {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  inline-size: 2.5rem;
  block-size: 2.5rem;
}
.icon-btn .fa-solid { font-size: 1.25rem; line-height: 1; }

2.3 Animation: fa-spin, fa-pulse, fa-beat

Font Awesome's animation utilities are state indicators. They are CSS animations on the glyph, which means they cost GPU work on every frame and they respect neither prefers-reduced-motion nor a background tab's rAF throttling by default.

What each animation means

fa-spinConstant 2 s rotationLoading spinners
fa-spin-pulseRotation in eight discrete stepsRetro or "processing" feel

fa-beat-fadeBeat plus opacitySofter attention

<!-- Spinner: pair the animation with a live-region label -->
<span class="spinner">
  <i class="fa-solid fa-spinner fa-spin" aria-hidden="true"></i>
  <span class="vh" role="status">Loading results</span>
</span>

<!-- Error shake: add the class when validation fails, then remove it -->
<i class="fa-solid fa-triangle-exclamation fa-shake" aria-hidden="true"></i>

Custom speed and steps

Font Awesome exposes CSS variables so you can retune the animation without writing keyframes. This is the supported way to avoid two different spin speeds in the same product.

.spinner-slow .fa-spin {
  --fa-animation-duration: 3s;
  --fa-animation-iteration-count: infinite;
  --fa-animation-timing: linear;
  --fa-animation-delay: 0s;
}

.spinner-steps .fa-spin {
  --fa-animation-duration: 2s;
  --fa-animation-timing: steps(8);
}
A spinning icon is a permanent compositor animation. On a dashboard with twelve polling widgets, twelve fa-spin glyphs will cost measurable battery on mobile. Prefer one shared spinner, or a skeleton placeholder.

Disabling motion honestly

The utilities do not check the user's motion preference. Do it yourself: disable the loop, and provide a static alternative that still communicates "in progress".

@media (prefers-reduced-motion: reduce) {
  .fa-spin, .fa-pulse, .fa-beat, .fa-bounce, .fa-fade, .fa-shake {
    animation: none !important;
  }
  /* Keep the information, drop the motion */
  .spinner .fa-spinner { opacity: .6; }
}

2.4 Rotation, flipping and arbitrary angles

Rotation utilities exist so you do not define seven CSS classes for arrows that point in four directions. They operate on the icon's transform, which is independent of size and colour.

The fixed set

<i class="fa-solid fa-arrow-right fa-rotate-90"></i>       <!-- 90°  clockwise -->
<i class="fa-solid fa-arrow-right fa-rotate-180"></i>      <!-- 180° clockwise -->
<i class="fa-solid fa-arrow-right fa-rotate-270"></i>      <!-- 270° clockwise -->
<i class="fa-solid fa-arrow-right fa-flip-horizontal"></i>  <!-- mirror on X -->
<i class="fa-solid fa-arrow-right fa-flip-vertical"></i>    <!-- mirror on Y -->
<i class="fa-solid fa-arrow-right fa-flip-both"></i>       <!-- 180° mirror -->

<!-- Arbitrary angle through a custom property -->
<i class="fa-solid fa-arrow-right fa-rotate-by" style="--fa-rotate-angle: 45deg"></i>

Rotation versus a second icon

Rotating a chevron to open a disclosure is the standard pattern and it keeps the DOM stable: one element, one class toggle, one transition. The alternative — swapping fa-chevron-down for fa-chevron-up — changes the glyph's bounding drawing and can produce a one-pixel jump, and it also destroys the animation opportunity. Prefer the transform.

<!-- Disclosure: rotate on state, keeping the icon element identity -->
<style>
  .disc .fa-chevron-down { transition: transform .2s ease; }
  .disc[aria-expanded="true"] .fa-chevron-down { transform: rotate(180deg); }
</style>

<button class="disc" type="button" aria-expanded="false" aria-controls="panel">
  Details <i class="fa-solid fa-chevron-down" aria-hidden="true"></i>
</button>
<div id="panel" hidden>…</div>

Where transforms go wrong

A rotation applied to a glyph inside a fixed-width container can clip at the corners, because the rotated bounding box is wider than the original advance width. If overflow: hidden is in play, an fa-rotate-45-style angle will cut the arrow tips off. Set an explicit padding or remove the clip. Also note that combined classes are not additive in a documented order — fa-rotate-90 fa-flip-horizontal resolves through two separate transform declarations, and the last one wins if the stylesheet does not chain them. For anything reliably reproducible, write the transform yourself.

3 · Styling and layout

3.1 Colour and size through inheritance3.2 Fixed width with fa-fw3.3 Stacking icons with fa-stack3.4 Lists, borders and pulled icons

Icon-font CSS is text CSS. Colour, size, weight and spacing are inherited through normal cascade rules, which means the utility classes here are conveniences, not requirements. This chapter covers the utilities worth using — fixed width, stacking, list markers — and the ones whose shorthand behaviour you should replace with plain CSS.

3.1 Colour and size through inheritance

An icon font glyph is drawn with the current text colour, so color on any ancestor reaches it. This is the single biggest advantage of the webfont approach and the reason most projects do not need per-icon CSS at all.

Colour inherits, so style the container

<!-- Bad: per-icon colour, five rules that drift apart -->
<i class="fa-solid fa-circle-info" style="color:#0b5fbf"></i>
<i class="fa-solid fa-triangle-exclamation" style="color:#b45309"></i>

<!-- Good: the container decides, tokens carry the colour -->
<style>
  .alert { color: var(--text); }
  .alert-info  .fa-circle-info       { color: var(--accent); }
  .alert-warn  .fa-triangle-exclamation { color: var(--warn); }
</style>

<div class="alert alert-warn">
  <i class="fa-solid fa-triangle-exclamation" aria-hidden="true"></i>
  Storage is nearly full.
</div>

Size without the multiplier scale

Setting font-size on the icon's own selector is more predictable than a fa-2x class, because it does not compound with a parent that also changed size. Use em when the icon should track the text it labels, and rem when it should be a fixed fixture of the interface.

/* Tracks the label's text size — right for inline icons */
.btn .fa-solid { font-size: 1em; }

/* Fixed size — right for toolbars and standalone icon buttons */
.toolbar .fa-solid { font-size: 1.25rem; }

/* Optical alignment: nudge, then verify in the browser, never guess */
.btn .fa-solid { position: relative; inset-block-start: -1px; }
Set a single anchoring rule early — svg, .fa-solid, .fa-regular, .fa-brands { vertical-align: -0.125em; } — and your icons will sit consistently on the text baseline across the product, instead of being nudged component by component.

3.2 Fixed width with fa-fw

Icons have wildly different advance widths: fa-bars is wide, fa-i-cursor is narrow. In a vertical list they produce a ragged left edge. fa-fw forces every icon to the same 1.25em box.

When it matters most

Three places: menu items with icons stacked vertically, table columns whose cells each start with an icon, and anything that animates between two icons in place. In all three the eye tracks the left edge of the text, and an uneven icon column makes the whole list look misaligned.

<nav class="menu">
  <a href="/"      ><i class="fa-solid fa-house fa-fw" aria-hidden="true"></i> Home</a>
  <a href="/inbox" ><i class="fa-solid fa-inbox fa-fw" aria-hidden="true"></i> Inbox</a>
  <a href="/users" ><i class="fa-solid fa-user fa-fw" aria-hidden="true"></i> People</a>
  <a href="/tags"  ><i class="fa-solid fa-tag fa-fw" aria-hidden="true"></i> Tags</a>
</nav>

What fa-fw does not do

It fixes the width of the glyph box, not the gap to the label, and it does not centre the drawing inside that box — a narrow glyph still sits left-aligned in its 1.25em cell. For precise alignment, use a grid: the icon occupies a fixed track and the label starts at a consistent column.

.menu a {
  display: grid;
  grid-template-columns: 1.75rem 1fr; /* icon track, label track */
  align-items: center;
  gap: .5rem;
  text-align: start;
}
With SVG-with-JS, fa-fw is translated into text-align: center plus a width on the injected <svg>, so the behaviour is equivalent but the underlying mechanism is different — which is why a custom rule targeting i.fa-fw stops matching after the replacement.

3.3 Stacking icons with fa-stack

Stacking places two icons in the same box — a badge over a document, a lock over a cloud. It is the one place where the icon font's fixed box model is genuinely useful, and the pattern predates SVG so it is well supported.

The three-class pattern

fa-stack makes a fixed 2em inline-block. fa-stack-2x fills it, fa-stack-1x occupies half of it, and fa-inverse flips the colour so the overlay reads against the base. The overlay is naturally centred, because both children are absolutely positioned in the same box.

<span class="fa-stack fa-lg" aria-hidden="true">
  <i class="fa-solid fa-camera fa-stack-1x"></i>
  <i class="fa-solid fa-ban fa-stack-2x" style="color:tomato"></i>
</span>

<!-- Badge over a document -->
<span class="fa-stack" aria-hidden="true">
  <i class="fa-solid fa-file fa-stack-2x"></i>
  <i class="fa-solid fa-circle fa-stack-1x fa-inverse"></i>
  <i class="fa-solid fa-check fa-stack-1x" style="font-size:.5em"></i>
</span>

Choosing stack order and font size

The overlay needs help with scale: fa-stack-1x is 50% of the stack box, which is often too small for a check mark inside a badge. Shrink the badge, not the overlay, by overriding font-size on the smaller layer. And remember the stack's total height is fixed at 2em, so a stack inside a line of text will exceed the line box and change the line height of its paragraph.

.fa-stack { line-height: 1; }
.fa-stack .fa-stack-1x.fa-check { font-size: .45em; }
/* Reserve the vertical space so the paragraph does not grow */
.fa-stack { vertical-align: middle; margin-block: -.5em; }
In SVG-with-JS, stacking is not supported by class name alone — the SVG replacement does not understand fa-stack reliably. If you use SVG mode, build the composite with a <span> wrapper and two positioned SVGs, or use the JS icon() API to compose it (Chapter 5).

3.4 Lists, borders and pulled icons

Font Awesome ships a small layout kit for the two most common icon-plus-text patterns: bullet lists whose markers are icons, and icons that sit outside the text block like a figure. These are the last of the utilities and the easiest to replace once you know what they do.

fa-ul and fa-li

fa-ul removes the native list marker and reserves a left indent; fa-li positions an icon in the space the marker would have occupied. The result is a list whose icons align and whose wrapped lines stay aligned with the first line rather than running under the icon.

<ul class="fa-ul">
  <li><span class="fa-li"><i class="fa-solid fa-check"></i></span>
      Ships within 24 hours</li>
  <li><span class="fa-li"><i class="fa-solid fa-check"></i></span>
      Free returns for 30 days, including a longer explanation that wraps
      onto a second line and stays aligned with the first</li>
</ul>

The equivalent CSS is six lines, which is why some teams skip the utility entirely — but it is worth knowing that fa-ul sets list-style-type: none and a margin-inline-start, and that it must wrap <li> elements, not live on them.

fa-border and reading direction

fa-border draws a rounded box with padding around the glyph — useful for a "feature list" of boxed icons, and dated in most other contexts. The pull utilities, fa-pull-left and fa-pull-right, float the icon. They are writing-direction aware inside a stack (the pulled icon is placed at the start of the line in LTR and at the end in RTL), so they are safe in localised layouts.

<!-- Boxed feature icon -->
<p><i class="fa-solid fa-bolt fa-border fa-pull-left fa-2x" aria-hidden="true"></i>
Fast, predictable delivery…</p>

<!-- Modern equivalent, using logical properties -->
<style>
  .feat { display: flex; gap: 1rem; align-items: flex-start; }
  .feat > .fa-solid { font-size: 2rem; color: var(--accent); }
</style>
Floats and fa-pull-* inside a flex or grid container are ignored, because floats do not apply to flex and grid items. That silent no-op is a common "the utility did nothing" report; check the display type of the parent first.

4 · Pseudo-elements and Unicode

4.1 ::before with a codepoint4.2 content values and state4.3 Content and accessibility4.4 Reading a codepoint table

Every Font Awesome icon is, underneath, a ::before pseudo-element with a content codepoint and a font family. Writing that rule yourself is how you put an icon on an element that has no child — a form field marker, a list bullet, a custom checkbox — and how you debug an icon that renders as a blank box.

4.1 ::before with a codepoint

A Font Awesome icon class expands to a single declaration block. Reproducing it by hand gives you three things the class cannot: an icon on an element you cannot edit, an icon whose content varies by state, and a full understanding of what the library is doing.

The generated rule, spelled out

/* What .fa-solid.fa-house compiles to, in essence */
.fa-house::before {
  content: "\f015";
}

/* A hand-written icon: family + weight + content, all three are required */
.field-label::before {
  font-family: "Font Awesome 6 Free";
  font-weight: 900;              /* 900 = solid, 400 = regular/brands */
  content: "\f015";
  margin-inline-end: .4em;
  speak: never;                  /* legacy hint, ignored by modern browsers */
}

Note the escaping in CSS: "\f015" is a hex escape of exactly four digits. A five-digit codepoint such as \1f5d1 needs a trailing space to terminate the escape, and dropping that space is the single most common cause of a wrong glyph:

.trash::before {
  font-family: "Font Awesome 6 Free";
  font-weight: 900;
  content: "\f1f8";   /* fa-trash — four digits, no space needed */
}

.long::before {
  content: "\1f5d1 \fe0f"; /* five-digit escape: the space ends the number */
}

Version-proofing the family name

Because the family name carries the version, a hand-written rule breaks on upgrade unless you route it through one custom property. Declare the family once and use it everywhere.

:root {
  --fa-solid-family: "Font Awesome 7 Free";
  --fa-brands-family: "Font Awesome 7 Brands";
}

.icon-house::before {
  font-family: var(--fa-solid-family);
  font-weight: 900;
  content: "\f015";
}

4.2 content values and state

content can be changed per state, which lets a single element swap its icon without touching the DOM. It is powerful, and it is also invisible to screen readers — which is the subject of the next topic.

Swapping glyphs on state

/* A details/summary marker, done entirely in CSS */
summary::marker { content: ""; }

summary::before {
  font-family: var(--fa-solid-family);
  font-weight: 900;
  content: "\f078"; /* fa-chevron-down */
  display: inline-block;
  margin-inline-end: .5em;
  transition: transform .2s ease;
}

details[open] summary::before {
  content: "\f077"; /* fa-chevron-up */
}

Prefer the transform here rather than the content swap. Two obviously different codepoints are fine, but subtle ones — a caret, a small arrow — jump by a pixel because the two glyphs have different bearings, and the change cannot be animated. Rotating one glyph is smoother and keeps the transition valid.

Combining text and icon in one value

/* Icon plus a nbsp gap, in one declaration */
.badge::before {
  font-family: var(--fa-solid-family);
  font-weight: 900;
  content: "\f058\00a0"; /* fa-circle-check then a non-breaking space */
}

/* Reading a value from a custom property is allowed with counter-less strings */
.qty-marker::after { content: attr(data-unit); }
You cannot interpolate a variable into a hex escape: content: "\f0" var(--n) is not a valid token sequence. Choose the whole escape or nothing. If the glyph has to be dynamic, use JavaScript or a data attribute mapped to a class.

4.3 Content and accessibility

CSS-generated content occupies a strange place in the accessibility tree. It is announced by most screen readers, but it has no semantics, no language, and no relation to the element's role. A private-use codepoint in an announced string is literal nonsense in the speech output.

What screen readers actually do

VoiceOver, NVDA and JAWS generally include ::before and ::after text in the accessible name computation, and a private-use character either produces nothing, produces a generic "object replacement character", or — worst case — leaks the glyph's Unicode name. So a hand-written icon must be treated as decorative by default and made meaningful explicitly.

/* The icon is decoration; the label carries the meaning */
.status--ok::before {
  font-family: var(--fa-solid-family);
  font-weight: 900;
  content: "\f058";
  margin-inline-end: .35em;
}

<!-- Markup: the pseudo-element cannot take aria-hidden, so hide the
     whole decorative span and put the real label in text -->
<p><span class="status--ok" aria-hidden="true"></span>Payment received</p>

When the icon is the only content

If you must have an icon-only control and no text at all, the name has to come from somewhere. On a real button, an aria-label is the answer. On a pseudo-element, the only honest options are a name on the host element or a visually hidden span beside it.

<!-- Icon-only control: name the button, hide the decoration -->
<button class="icon-btn" type="button" aria-label="Search">
  <span class="i-search" aria-hidden="true"></span>
</button>

<style>
  .i-search::before {
    font-family: var(--fa-solid-family); font-weight: 900; content: "\f002";
  }
</style>
Do not put the codepoint in a ::before on the button itself and then label the button with aria-label simultaneously — the label replaces the accessible name wholesale, so it works, but the glyph still contributes to text selection and to copy-paste output. Users selecting a heading sometimes paste invisible private-use characters into a search box, and nothing matches.

4.4 Reading a codepoint table

Every icon has a canonical codepoint, and the codepoint is what a hand-written rule needs. Knowing where to find it — and why Font Awesome's own reference page renders the class approach rather than the codepoint — saves a lot of hunting.

Where the data lives

In the free npm package the mapping is a JSON file, metadata/icons.json, keyed by icon name, with unicode values per style. That file is the authoritative source; a search-and-grep beats a browser tab.

# Find the codepoint for an icon in the published metadata
node -e "const i=require('@fortawesome/free-solid-svg-icons').faHouse;
         console.log(i.iconName, i.icon[3])"

;; Or, from the JSON in @fortawesome/fontawesome-free:
;;   "house": { "unicode": "f015", "styles": ["solid","regular"] }

Anchoring the number to the picture

The reference site shows each glyph next to its name; the codepoint is one click deeper. When you transcribe one by hand, verify it visually immediately — render the glyph in a scratch page and compare. A transposed hex digit still produces a valid glyph from the same private-use block, so a bad codepoint is not a broken character, it is the wrong icon, and it will pass every automated check you have.

<!-- Scratch check: twenty codepoints on one line, eyeball them -->
<p style='font-family:"Font Awesome 7 Free";font-weight:900'>
  \f015 \f007 \f002 \f013 \f0c9 \f00c \f00d \f1f8 \f005 \f004
</p>
Copy codepoints out of the metadata rather than typing them. Private-use blocks are deliberately unsorted and unmemorable, and there is no visual or semantic logic to exploit as a mnemonic.

5 · The Font Awesome JavaScript API

5.1 SVG-with-JS versus the CSS webfont5.2 library.add and the icon registry5.3 icon() and dom.watch()5.4 Tree-shaking and bundle cost

Font Awesome's SVG-with-JS mode replaces each icon element with an inline <svg> at runtime. It removes the font request and the invisible-glyph window, at the cost of a library on the critical path and a DOM that no longer matches your source. This chapter covers when that trade is worth it and how the API actually works.

5.1 SVG-with-JS versus the CSS webfont

These are two different products shipped in one package. The CSS approach is a font; the JS approach is a renderer. Choosing between them is a decision about your build pipeline and your tolerance for a DOM that mutates after load.

The difference in one table

CSS webfontSVG-with-JS
NetworkCSS + woff2 per styleOne JS bundle, inline paths
First paintIcons appear after the font loadsIcons appear after the script runs
DOMStable; your <i> staysReplaced by <svg class="svg-inline--fa">
StylingFont metrics, baseline quirksReal boxes: fill, width, vertical-align
Works with JS offYesNo — the codepoint is in the JS, not your HTML
Tree-shakeableNo, you ship whole fontsYes, with a bundler

The last row is the decisive one for applications. A bundled app that imports four icons from the JS package ships four SVG paths, not four families of fonts. That is a saving of hundreds of kilobytes against a full all.min.css plus its three woff2 files.

// JS mode, front-loaded as a script tag (no bundler needed)
<script defer src="https://kit.fontawesome.com/abc123def4.js" crossorigin="anonymous"></script>

// The replacement your DOM ends up with, in place of <i class="fa-solid fa-house">
// <svg class="svg-inline--fa fa-house" aria-hidden="true" focusable="false"
//      data-prefix="fas" data-icon="house" role="img" viewBox="0 0 576 512">…</svg>

When not to use it

Three cases. Static documentation that must work from the file system, where you cannot rely on a script executing in every reader's browser. Emails, where scripts are stripped. And any page whose Content Security Policy forbids third-party scripts — unless you self-host and bundle it, which brings back the build step you were avoiding.

5.2 library.add and the icon registry

In a bundler, nothing is global. You register the icons you use, and the renderer resolves names against that registry. Registering more than you use is the entire cost of this design.

Registering icons explicitly

// npm i @fortawesome/fontawesome-svg-core \
//        @fortawesome/free-solid-svg-icons \
//        @fortawesome/free-brands-svg-icons
import { library } from '@fortawesome/fontawesome-svg-core';
import { faHouse, faUser, faMagnifyingGlass } from '@fortawesome/free-solid-svg-icons';
import { faGithub, faXTwitter } from '@fortawesome/free-brands-svg-icons';

library.add(faHouse, faUser, faMagnifyingGlass, faGithub, faXTwitter);

// Now any element already in the DOM with these classes is replaced.
// The registry is global to the module instance, so import it once, early.

Aliases and the same icon twice

library.add accepts the icon definition objects, and an icon definition already carries its aliases. Adding an alias name separately is rarely necessary and doubles nothing — the registry is keyed by name, and duplicates are ignored. The one legitimate use is registering your own semantic names over Font Awesome glyphs so design language and code language agree:

import { faTrashCan } from '@fortawesome/free-solid-svg-icons';

// Register a product-specific alias for an existing glyph
library.add({ ...faTrashCan, iconName: 'bin' });

// <i class="fa-solid fa-bin"></i> now resolves, and so does the original name
If you register a name that Font Awesome already defines in another style, the last registration wins and you can silently change the weight of every icon on every page. Keep aliases in one file under version control, and grep it during review.

5.3 icon() and dom.watch()

Two entry points cover almost every runtime need. icon() produces an element or an HTML string you can place yourself; dom.watch() re-scans the document for icon elements that appeared after your initialisation.

icon(): an element or a string

import { icon } from '@fortawesome/fontawesome-svg-core';

// 1) An AbstractElement you can append
const node = icon({ prefix: 'fas', iconName: 'house' });
document.querySelector('.slot').appendChild(node.node[0]);

// 2) A string of HTML, useful for template literals and innerHTML
const html = icon({ prefix: 'fas', iconName: 'user', styles: { color: '#0b5fbf' } }).html;
list.innerHTML = html;

// 3) With transforms, which cannot be expressed as a class in SVG mode
const rotated = icon({
  prefix: 'fas',
  iconName: 'arrow-right',
  transform: { rotate: 90, flipX: false, size: 16 }
});

The transform object is one of the strongest reasons to use the JS API at all: it emits a real SVG transform attribute, so rotation, flipping and scaling compose predictably instead of relying on cascading CSS classes.

dom.watch() for content that arrives late

The initial pass runs once. Anything rendered afterwards — a framework re-render, an AJAX fragment, a modal appended to the body — contains raw <i> elements that nobody replaced. dom.watch() installs a MutationObserver that handles them.

import { dom, config } from '@fortawesome/fontawesome-svg-core';

config.autoReplaceSvg = 'nest';        // wrap instead of replace, keeping the <i>
config.observeMutations = true;        // watch() only needs to be called once

dom.watch({
  autoReplaceSvgRoot: document,        // usually the body
  keepOriginal: false,                 // 'nest' keeps it; true removes it
});
With autoReplaceSvg: 'nest' the original <i> stays in the DOM as a wrapper with the generated <svg> inside it. That preserves any class or ref you had on the element — at the cost of an extra node, which matters if your CSS assumes the icon element is the SVG itself.

Disabling the injected CSS

By default the library injects a <style> element with the base icon rules. In a bundled app that is a surprise runtime mutation and a CSP problem; import the stylesheet instead.

import { config } from '@fortawesome/fontawesome-svg-core';
import '@fortawesome/fontawesome-svg-core/styles.css';
config.autoAddCss = false; // you now own the CSS, and the bundler can hash it

5.4 Tree-shaking and bundle cost

Tree-shaking is the reason a modern app uses the JS API instead of a kit script. It only works when your imports are static and your icon references survive minification, which rules out a few otherwise-natural patterns.

Import per icon, never the barrel

// Good: four icons survive into the bundle, the rest is dropped
import { faHouse, faUser, faCheck, faXmark } from '@fortawesome/free-solid-svg-icons';

// Bad: pulls the whole 1,600-icon module and defeats the shake
import * as solid from '@fortawesome/free-solid-svg-icons';
const name = 'fa' + userInput;               // dynamic — nothing can be shaken
const ic = solid[name];

Each icon definition is roughly 700 bytes to 1.5 KB of path data. Four icons is a few kilobytes; the full solid set is measured in megabytes of JavaScript. A dynamic lookup by name is the single mistake that turns a 4 KB icon budget into a 900 KB one.

What the numbers look like

ApproachWhat shipsRough gutted size
Kit script (all icons)Hosted JS, cachedDepends on kit config
all.min.css + webfontsCSS plus 3 woff2~100 KB woff2 total
solid.min.css subsetCSS plus 1 woff2~60 KB woff2

The core runtime itself is a fixed cost of a few kilobytes. Below roughly ten icons, inline SVG beats it outright. Above about thirty, the JS API plus bundler is the smallest thing you can ship.

Verifying the shake

# Vite / Rollup: name the chunks so you can see the icon chunk
npx vite build --mode production
npx source-map-explorer dist/assets/*.js   # look for free-solid-svg-icons

# Webpack: a stats file is the reliable view of what survived
npx webpack --profile --json > stats.json

If the whole icon module appears in the bundle, one of three things is true: a namespace import leaked in, something used require conditionally, or a plugin forced the module into a "side-effectful" bucket. All three are visible in the stats file, and none of them are visible in the page.

6 · Google Material Symbols and Icons

6.1 Four styles, one family per style6.2 Variable axes: FILL, wght, GRAD, opsz6.3 Sizing, alignment and the server-rendered pattern6.4 The legacy material-icons font

Material Symbols is Google's current icon system and the successor to Material Icons. The critical difference is that Material Symbols is a variable font: one file carries the whole set at four adjustable axes, so weight, fill, grade and optical size are numbers rather than separate files. This chapter covers the current system and the legacy font that still ships in a million themes.

6.1 Four styles, one family per style

Material Symbols comes in four visual styles, and — unusually — each is a separate font family name with its own variable file. You pick the style by choosing a family, and the axes then work the same way in all four.

The families and the span pattern

<!-- Load one style (or several) from Google Fonts -->
<link rel="stylesheet"
  href="https://fonts.googleapis.com/css2?family=Material+Symbols+Outlined:opsz,wght,FILL,GRAD@20..48,100..700,0..1,-50..200&display=block">

<!-- The icon name is the visible text; the font turns it into a picture -->
<span class="material-symbols-outlined">home</span>
<span class="material-symbols-rounded">search</span>
<span class="material-symbols-sharp">settings</span>
<span class="material-symbols-outlined">delete</span>

The class names are: material-symbols-outlined, material-symbols-rounded and material-symbols-sharp. The fourth style — filled — is not a family; it is the FILL axis set to 1 on any of the three. That is an easy thing to get wrong, and there is no material-symbols-filled class.

How the ligature trick works

The font contains ligatures that map the word home to the home glyph. When a browser sees "home" in a font with that ligature, it substitutes the single glyph — no extra markup, no codepoint to look up. The consequence is that the accessible text of that span is literally the word "home", which is sometimes exactly right and sometimes actively misleading (Chapter 7).

/* The minimal CSS you would write if the CDN link only gave you the font */
.material-symbols-outlined {
  font-family: "Material Symbols Outlined";
  font-variation-settings: "FILL" 0, "wght" 400, "GRAD" 0, "opsz" 24;
  font-size: 24px;
  line-height: 1;
  display: inline-block;
  white-space: nowrap;
  direction: ltr;
  font-feature-settings: "liga"; /* the substitution that makes it work */
  -webkit-font-feature-settings: "liga";
}

6.2 Variable axes: FILL, wght, GRAD, opsz

Four axes, all optional, all mechanical once explained. Getting them right is what makes Material Symbols look designed rather than defaulted, and it is the reason the variable file replaces hundreds of individual icon files.

What each axis does

AxisRangeEffect
FILL0 → 1Outline to solid; animated toggles rely on it
wght100 → 700Stroke thickness; must match adjacent text weight
GRAD-50 → 200Optical weight without changing metrics — dark/light backgrounds
opsz20 → 48Optical size: detail at large sizes, legibility when small
<style>
  /* Set the axes per instance, not per family */
  .ic-filled      { font-variation-settings: "FILL" 1, "wght" 400, "GRAD" 0, "opsz" 24; }
  .ic-bold        { font-variation-settings: "FILL" 0, "wght" 700, "GRAD" 0, "opsz" 24; }
  .ic-on-dark     { font-variation-settings: "FILL" 0, "wght" 400, "GRAD" 200, "opsz" 24; }
  .ic-hero        { font-variation-settings: "FILL" 0, "wght" 300, "GRAD" 0, "opsz" 48; }

  /* Animate FILL on a favourite toggle */
  .fav .material-symbols-outlined {
    font-variation-settings: "FILL" 0, "wght" 400, "GRAD" 0, "opsz" 24;
    transition: font-variation-settings .2s ease;
  }
  .fav[aria-pressed="true"] .material-symbols-outlined {
    font-variation-settings: "FILL" 1, "wght" 400, "GRAD" 0, "opsz" 24;
  }
</style>

The rules you cannot break

Four constraints, each of which produces a silent failure. The axis list in the Google Fonts URL must be in alphabetical order, and the value tuples must be in that same order — a mismatched order yields a valid-looking request that returns the default instance. font-variation-settings is not inherited in the way font-weight is, so a child that declares it overrides every axis, not just the one you named: always write all four. Axis values must sit inside the range you requested; asking for "wght" 900 from a file requested as 100..700 clamps silently. And font-variation-settings is a low-level property that resets any high-level font-* property competing in the same declaration — mixing it with font-weight: 700 on the same element is a race.

If your icons suddenly all become identical or all lose their fill, check for a single rule that names only one axis. Because the whole declaration is replaced rather than merged, font-variation-settings: "FILL" 1; resets wght, GRAD and opsz to the font's defaults.

6.3 Sizing, alignment and the server-rendered pattern

Material Symbols defaults to 24 px with a fixed line box that assumes it. In a real design you want the size to come from the layout, and you want the icon to sit on the text baseline without a magic number everywhere.

Sizing and inheriting text styles

.material-symbols-outlined {
  font-size: inherit;          /* track the surrounding text */
  line-height: 1;              /* do not inherit the paragraph's leading */
  vertical-align: -0.15em;     /* sit on the baseline rather than above it */
  font-variation-settings: "FILL" 0, "wght" 400, "GRAD" 0, "opsz" 24;
  user-select: none;           /* the ligature text should not be selectable */
}

/* Offer the size axis only at the sizes where it helps */
.card__icon { font-size: 2.5rem; font-variation-settings: "FILL" 0, "wght" 300, "GRAD" 0, "opsz" 48; }
.btn__icon  { font-size: 1.25rem; font-variation-settings: "FILL" 0, "wght" 400, "GRAD" 0, "opsz" 24; }

user-select: none and direction: ltr are not cosmetic. Without the first, dragging a selection across a row of icons copies the words "home search settings" into the clipboard. Without the second, an RTL layout reverses the ligature and the icon disappears.

Self-hosting and offline use

For an offline library the Google Fonts link is a hard dependency, so download the variable woff2 once and declare it locally. Only the requested instances matter: a full Material Symbols family file is large, so request the axes you need on the CDN, save the returned woff2, and serve that.

@font-face {
  font-family: "Material Symbols Outlined";
  font-style: normal;
  font-weight: 100 700;              /* variable range, not a single weight */
  font-display: block;
  src: url("../fonts/material-symbols-outlined.woff2") format("woff2");
}

<!-- The rule set is identical; only the source changed -->
<span class="material-symbols-outlined" aria-hidden="true">home</span>
Google Fonts serves a different file per User-Agent and per requested axis range. If you vendor a woff2 you requested in a browser, you get the modern format; if you request it with a bare curl, you may get a legacy TTF. Always compare the file size against the browser's Network panel.

6.4 The legacy material-icons font

The pre-2022 Material Icons font is still the most widely deployed icon font in the world, because every Material-UI-era theme and most Bootstrap templates ship it. It is static, not variable, and it uses a different set of class names.

The five legacy classes

<link rel="stylesheet"
  href="https://fonts.googleapis.com/icon?family=Material+Icons|Material+Icons+Outlined|Material+Icons+Round|Material+Icons+Sharp|Material+Icons+Two+Tone">

<i class="material-icons">home</i>
<i class="material-icons-outlined">search</i>
<i class="material-icons-round">settings</i>
<i class="material-icons-sharp">delete</i>
<i class="material-icons-two-tone">favorite</i>

Note that legacy uses <i> by convention while Material Symbols uses <span>. Both are just elements — the font does not care — but copying a snippet across the two systems without changing the class is the usual cause of a blank icon.

Migrating to Material Symbols

The migration is mechanical but not automatic. Icon names are largely unchanged (home, search, settings, delete, favorite), which is why the swap is tempting as a find-and-replace. Three things break:

<!-- Before: static font, one file per style -->
<i class="material-icons-outlined">settings</i>

<!-- After: variable font, FILL replaces the outlined/filled families -->
<span class="material-symbols-outlined" aria-hidden="true">settings</span>

<!-- After, filled: there is no "material-symbols-filled" class -->
<span class="material-symbols-outlined" style='font-variation-settings:"FILL" 1,"wght" 400,"GRAD" 0,"opsz" 24'>settings</span>

First, the codepoints moved: the two families do not share a private-use map, so any hand-written content: "\e8b8" rule must be re-derived. Second, "outlined versus filled" became an axis, so a template that toggled a class now has to toggle a custom property. Third, the set is larger — some legacy names gained a suffix, and a few were replaced outright. Verify each name against the current catalogue rather than trusting that it survived.

Both families are under the Apache 2.0 licence for the code and CC BY 4.0 for the icons, so shipping either in a commercial product is permitted with attribution. The licence is why this guide can embed the fonts — but it is also why the "Google" wordmark and product logos inside the set are not freely usable as brand marks.

7 · Accessibility

7.1 Decorative versus meaningful7.2 Visually hidden labels and icon-only controls7.3 Contrast and non-text criteria7.4 Motion, timing and reduced motion

Icons are the most common accessibility regression in a codebase, because they look finished while being semantically empty. The single question that resolves almost every case is: does this icon carry information, or does it merely decorate text that already carries it? This chapter answers that question, then covers labels, contrast and motion.

7.1 Decorative versus meaningful

Get the classification right and the rest of the work is mechanical. Get it wrong and you either announce noise or hide information.

The rule, and why <i> is not enough

A decorative icon duplicates information already present in text; it must be hidden from assistive technology. A meaningful icon is the information; it must have an accessible name. There is no third category, and "it's obvious" is not a category.

<!-- Decorative: the text says everything the icon shows -->
<button type="button">
  <i class="fa-solid fa-magnifying-glass" aria-hidden="true"></i>
  Search
</button>

<!-- Meaningful: the icon is the only carrier of the message -->
<p class="status status--error">
  <i class="fa-solid fa-circle-xmark" role="img" aria-label="Error"></i>
  <span>Upload failed</span>
</p>

In the second example the label is arguably redundant with the visible text, and that redundancy is usually wrong: a screen reader would read "Error Upload failed". The correct form for that component is aria-hidden="true" on the icon, because the words already say it. Reserve role="img" plus aria-label for icons that stand alone.

SVG-with-JS adds its own attributes

// The generated SVG carries focusable="false" and, depending on config,
// aria-hidden. Verify the output rather than assuming:
document.querySelector('.svg-inline--fa').outerHTML;

// For a meaningful icon in JS mode, pass a title:
icon({ prefix: 'fas', iconName: 'circle-xmark',
       title: 'Error' }).html;
// → <svg … role="img" aria-labelledby="svg-inline--fa-title-1">…
A leftover aria-hidden="true" on a meaningful icon is invisible in every visual test and in every automated audit that only checks for the absence of labels. Review the icon-plus-text pairs by hand once per release.

7.2 Visually hidden labels and icon-only controls

An icon-only button has no accessible name unless you add one, and the two ways to add it — an aria-label and a visually hidden span — are not interchangeable.

The two techniques compared

TechniqueBehaviourWhen to prefer
aria-label="Search"Replaces the accessible name; not visible, not translatable by page tools, not selectableSimple buttons, no text needed
<span class="vh">Search</span>Visible to screen readers as text; selectable and translatable; adds a nodeToolbar buttons, anything localised by a translation file
<span class="fa-sr-only">Search</span>Font Awesome's own visual-hiding utilityWhen you already use Font Awesome utilities
<!-- The visually-hidden pattern, shared by both libraries -->
<style>
  .vh {
    position: absolute;
    inline-size: 1px; block-size: 1px;
    margin: -1px; padding: 0; border: 0;
    overflow: hidden; white-space: nowrap;
    clip-path: inset(50%);
  }
</style>

<button class="icon-btn" type="button">
  <i class="fa-solid fa-gear" aria-hidden="true"></i>
  <span class="vh">Settings</span>
</button>

Name plus state

A toggle needs a name and a state, and the state must be programmatic rather than implied by the glyph. Use aria-pressed for a two-state button and aria-expanded for a disclosure — never a colour change or an icon swap alone.

<button class="fav" type="button" aria-pressed="false">
  <i class="fa-regular fa-heart" aria-hidden="true"></i>
  <span class="vh">Favourite this item</span>
</button>

<script>
  const fav = document.querySelector('.fav');
  fav.addEventListener('click', () => {
    const on = fav.getAttribute('aria-pressed') === 'true';
    fav.setAttribute('aria-pressed', String(!on));
    fav.querySelector('.fa-heart').classList.toggle('fa-regular', on);
    fav.querySelector('.fa-heart').classList.toggle('fa-solid', !on);
  });
</script>

The Material ligature problem

A Material Symbols span has real text inside it, so a screen reader reads the icon name as a word. That is occasionally correct and frequently wrong, and it is also a translation hazard, because "home" in the markup is an icon name rather than English copy. Hide it when the icon decorates, and give the host element a name when it does not.

<!-- Decorative: hide the ligature text from the accessibility tree -->
<a href="/" class="brand">
  <span class="material-symbols-outlined" aria-hidden="true">home</span>
  <span>Dashboard</span>
</a>

<!-- Meaningful: the button owns the name, the ligature stays hidden -->
<button type="button" aria-label="Delete item">
  <span class="material-symbols-outlined" aria-hidden="true">delete</span>
</button>

7.3 Contrast and non-text criteria

Icons are graphics, so they fall under the 3:1 non-text contrast rule when conveying information — a different threshold from the 4.5:1 that body text must clear. Icon fonts sit in an awkward middle, because they are text glyphs painted as graphics.

Thresholds that actually apply

  • Decorative icons — no contrast requirement. A faint watermark arrow is fine.
  • Meaningful icons — 3:1 against the adjacent background (WCAG 1.4.11).
  • Disabled controls — exempt, but keep them distinguishable by shape or label, not colour alone.
  • Text-size icons that label a control — treat as text: 4.5:1.
/* Token-driven icon colour: light and dark both clear 3:1 */
:root             { --icon: #0b5fbf; --icon-on: #ffffff; }
[data-theme=dark] { --icon: #4dd2ff; --icon-on: #04203f; }

.icon-btn { color: var(--icon); }
.icon-btn--on { background: var(--icon); color: var(--icon-on); }

The classic failure is a status icon whose colour carries the meaning — red for error, green for success — with no text or shape difference. A user with a colour vision deficiency cannot tell them apart, and the icons are the only signal. Always pair colour with a different glyph (fa-circle-xmark versus fa-circle-check) or with text.

Icon fonts inherit color, which makes them easy to theme correctly and easy to break: a single opacity: .5 applied for a disabled look can drop a 4.5:1 icon to roughly 2:1. Compute the compounded colour, do not eyeball it.

7.4 Motion, timing and reduced motion

Animation utilities are where accessibility and performance requirements collide, because a spinner is both a necessity and a vestibular hazard.

Why the spinner is the hardest case

A continuous rotation is the archetypal motion that triggers discomfort, and there is no way to communicate "in progress" with a spinner's movement alone — the movement is the message. So the reduced-motion version must keep the information while dropping the motion.

<!-- Markup: one region that announces, one glyph that spins -->
<div class="loader" role="status" aria-live="polite">
  <i class="fa-solid fa-spinner fa-spin" aria-hidden="true"></i>
  <span class="vh">Loading results</span>
</div>

@supports (animation: none) {
  @media (prefers-reduced-motion: reduce) {
    .loader .fa-spin {
      animation: none;
      /* Keep a visible, static progress cue instead of motion */
      opacity: .55;
    }
  }
}

Three motion windows, not one

Reduced motion is not the only threshold. WCAG also limits flashing to three times per second, and any auto-playing movement that lasts longer than five seconds must be pausable. A fa-bounce on a marketing badge therefore has three separate problems: it is not pausable, it ignores the motion preference, and it runs forever.

/* Bound every attention animation: run it, then stop. */
.notice .fa-beat { animation-iteration-count: 3; }

/* Honour the preference globally, once, in a shared sheet */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: .01ms !important;
    scroll-behavior: auto !important;
  }
}
A global reduced-motion override is the only reliable one, because it catches the animations you forgot — including the ones inside third-party widgets. The cost is that it also flattens deliberate, gentle transitions that would have been acceptable. That trade is the right way round.

Loading states beyond the spinner

For lists and tables, a skeleton placeholder conveys "content is coming" with no motion at all, and it avoids the layout shift that a spinner causes when it is replaced by real content. Reserve spinners for indeterminate waits inside a button or a small panel, and keep exactly one per region.

8 · Performance

8.1 Subsetting an icon font8.2 font-display and the invisible window8.3 SVG sprites and tree-shaking as the modern path8.4 Preload, caching and CDN headers

Icon performance is a small set of decisions made once: how much font you download, when it becomes visible, and how it is cached. This chapter covers subsetting, font-display, sprites and the header configuration that makes icons free after the first visit.

8.1 Subsetting an icon font

A full Font Awesome or Material Symbols font carries thousands of glyphs you will never render. Subsetting rewrites the font to contain only the ones in your design — usually a 90%+ saving, at the cost of a build step and a discipline requirement.

The two tools that matter

# 1. Find every icon actually used in the built site
npx glyphhanger --json --files "dist/**/*.html" --selector ".fa-solid, .fa-regular" > used.json

# 2. Subset the woff2 to just those codepoints
npx glyphhanger --subset=webfonts/fa-solid-900.woff2 --unicodes="U+F015,U+F007,U+F002,U+F013" --formats=woff2

# Or with fonttools directly, which is the underlying engine
pip install fonttools brotli
pyftsubset fa-solid-900.woff2 \
  --unicodes="U+F015,U+F007,U+F002,U+F013" \
  --flavor=woff2 --layout-features='' --no-hinting

The output is a tiny woff2 — often under 5 KB for a dozen icons — and a stylesheet that still references the same family name, so no markup changes are required. The font is not a different font, it is a smaller one.

The failure mode: a missing icon on one page

A subset built from the pages that existed last Tuesday will silently lose every icon added since. The glyph is not there, so the codepoint renders as nothing in the fallback font — the same invisible failure as a 404'd font. There is no error, no warning and no visual box.

# Generate the subset inside the build, after the HTML is emitted,
# and fail the build if the font grew or shrank unexpectedly.
node build/subset-icons.js --from dist --font webfonts/fa-solid-900.woff2 --out dist/fonts/
node build/assert-size.js dist/fonts/fa-solid-900.woff2 --min 3000 --max 40000
If your icons are injected by JavaScript rather than present in the HTML — SVG-with-JS, a React component, a CMS field — a scan of the HTML cannot see them. Extract the icon names from the JS bundle with the same tooling, or keep a manifest file listing names as the source of truth and subset from that.

8.2 font-display and the invisible window

For an icon font the choice is genuinely narrow: block or nothing. swap is the one option that must not be used, because the fallback glyph is a wrong picture rather than a wrong letter.

The four values, judged for icons

ValueBlock periodVerdict for an icon font
autoBrowser defaultUnpredictable; avoid
block~3 sCorrect: nothing rather than the wrong glyph
swap0Wrong: shows fallback characters
fallback~100 msRisky: a very short block then a visible swap
optional~100 msUse when inline SVG is not available and icons are decoration
/* Self-hosted override of the library's own declaration */
@font-face {
  font-family: "Font Awesome 7 Free";
  font-style: normal;
  font-weight: 900;
  font-display: block;
  src: url("../webfonts/fa-solid-900.woff2") format("woff2");
}

/* Pair it with a fixed box so the layout cannot shift while blocked */
.fa-solid { display: inline-block; inline-size: 1.25em; text-align: center; }

Why block alone is not enough

Three seconds of invisible icons is a worse experience than a slightly larger first paint, so the real fix is to make the font arrive with the page. Preload it (see 8.4) and, for above-the-fold icons, prefer inline SVG for the handful that the user sees immediately. A hybrid is legitimate and common: inline SVG for the header and primary actions, an icon font for the long tail inside the page.

8.3 SVG sprites and tree-shaking as the modern path

The two approaches that beat a font outright. A sprite removes the font dependency entirely; tree-shaking removes everything you did not import. Both are build-time decisions.

Generating a sprite

# Build a sprite from a folder of individual SVGs (one per icon)
npx svg-sprite --symbol --dest dist/ dist/icons/*.svg
# → dist/sprite/symbol/svg/sprite.symbol.svg + a preview page

<!-- Reference one symbol; the file is fetched once and cached -->
<svg class="ic" width="24" height="24" aria-hidden="true">
  <use href="/img/sprite.svg#house"></use>
</svg>

Two properties make a sprite attractive for a design system: the whole icon set is one cacheable request, and adding an icon does not change the CSS that styles all the others. The limitation, covered in Chapter 0, is styling: assume currentColor only, and treat multi-colour icons as inline SVG.

Tree-shaking the JS API

If you already have a bundler, the JS API with static imports is usually smaller than a subset font, because it ships path data rather than a binary font container, and it compresses well.

// icons.js — one module, the only place icons are imported
export {
  faHouse, faUser, faMagnifyingGlass, faGear, faChevronDown
} from '@fortawesome/free-solid-svg-icons';

// app.js — registered once, watched once
import { library, dom, config } from '@fortawesome/fontawesome-svg-core';
import '@fortawesome/fontawesome-svg-core/styles.css';
import * as icons from './icons.js';
config.autoAddCss = false;
library.add(...Object.values(icons));
dom.watch();
The spread into library.add is safe for tree-shaking because the imports above it are static and named. The shake happens at the module boundary; the runtime spread is just a loop over objects that have already survived.

8.4 Preload, caching and CDN headers

The last mile: get the font on the wire before the CSS asks for it, and make sure it is never downloaded twice.

Preload the woff2, not the CSS

<!-- Order matters: preload as early as possible in the head -->
<link rel="preload" href="assets/fa/webfonts/fa-solid-900.woff2"
      as="font" type="font/woff2" crossorigin>

<link rel="stylesheet" href="assets/fa/css/all.min.css">

<!-- Preconnect only helps a third-party origin; skip it when self-hosting -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

crossorigin is mandatory even when the font is same-origin, because fonts are always fetched in CORS mode. Omitting it produces a second, cache-missing request — the classic "the font downloaded twice" report, visible in the Network panel as two entries for the same URL where the first is marked as a preload that was not used.

Immutable caching for hashed filenames

# Apache: long cache for the font directory
<FilesMatch "\.(woff2|woff|ttf)$">
  Header set Cache-Control "public, max-age=31536000, immutable"
  Header set Access-Control-Allow-Origin "*"
</FilesMatch>

# nginx
location ~* \.(woff2|woff|ttf)$ {
  expires 1y;
  add_header Cache-Control "public, immutable";
  add_header Access-Control-Allow-Origin "*";
}

immutable is only safe when the filename changes whenever the content does — a hash in the name, or a version directory. A font at a fixed path with a one-year immutable header is unfixable without a rename, which is exactly the situation a subset build creates if it overwrites the same filename.

Measuring, not guessing

# What icon assets actually cost, per page, on a cold cache
npx lighthouse http://localhost:4173/ --preset=desktop --output=json --output-path=report.json
node -e "const r=require('./report.json');
  const a=r.audits['network-requests'].details.items
    .filter(i=>/(woff2|\.css$|sprite\.svg)/.test(i.url));
  console.table(a.map(i=>({url:i.url.split('/').pop(),kb:(i.transferSize/1024).toFixed(1)})))"
Track two numbers in CI: total bytes of icon assets, and the count of distinct icon files. A regression in either is usually a new icon library arriving, and both are cheap to assert with a script that reads the build output.
