Welcome — Databases from Basic to Enterprise

How this guide is organisedThe three engines at a glanceClients you will use

This is the welcome module of a hands-on, three-engine course in which you build and query real databases in SQL Server, MySQL and PostgreSQL side by side. Work through the same exercises in each engine so you can compare syntax, output formats and dialect gotchas directly. The practical setup keeps every later chapter testable on your own machine.

A hands-on, comparative course in relational database design and implementation covering the three engines you will meet most in the field: SQL Server Express (T-SQL), MySQL and PostgreSQL. Every topic shows the code and the output for all three.

How this guide is organised

This guide is organised as a straight line: foundations, schema, data work, then enterprise concerns such as scaling, security and backup. Read the chapters in order so each topic builds on the previous ones without gaps. Individual chapters also work standalone as reference when you need to revisit a specific concept later.

  • Foundations (Ch. 1–3) — relational model, installing and connecting, data types across engines.
  • Building schemas (Ch. 4–6) — DDL, constraints, indexes.
  • Working with data (Ch. 7–10) — CRUD, joins and analytics, transactions, programmable objects.
  • Enterprise design (Ch. 11–17) — normalisation, partitioning, replication, tuning, security, JSON, backup and scaling.

1 · Relational Foundations

1.1 Tables, rows and columns1.2 Keys and relationships1.3 ACID

Relational foundations give you the mental model behind every relational database: tables, rows, keys and the ACID guarantees that make transactions trustworthy. Master the mapping between a schema and its data before touching SQL. Getting this right makes every later chapter on queries, joins and design click into place.

1.1 Tables, rows and columns

The core mapping is that a table is a relation, a row is a record and a column is a typed field. Instead of pointers, keys link tables to each other. Model entities and their relationships this way and every query and join you later write follows naturally from the schema.

A relational database stores data in tables (relations). Each row is one record; each column has a type and optional constraints. Relationships are expressed with keys, not pointers.

customers                 orders
+----+--------+          +----+-------------+--------+
| id | name   |          | id | customer_id | total  |
+----+--------+          +----+-------------+--------+
| 1  | Ada    |          | 10 | 1           | 99.90  |
| 2  | Grace  |          | 11 | 1           | 12.00  |
+----+--------+          +----+-------------+--------+
   PK                        FK customer_id -> customers.id

Two ASCII tables show the shape of relational data: customers keys into orders through a foreign key, never a pointer.

1.2 Keys and relationships

Primary keys uniquely identify each row, while foreign keys tie tables together and enforce referential integrity between them. In practice you declare them with PRIMARY KEY and FOREIGN KEY constraints in CREATE TABLE or ALTER TABLE. Understanding keys underlies every join and every index you will build.

KeyPurpose
Primary key (PK)Uniquely identifies each row; cannot be null.
Foreign key (FK)Points to a PK in another table; enforces referential integrity.
Unique keyEnforces uniqueness without being the PK.
Composite keyMade of two or more columns.

1.3 ACID

ACID is the four guarantees that make transactions trustworthy: atomicity, consistency, isolation and durability. Databases that honour these survive crashes and concurrent access without corrupting data. Apply the model when deciding how to batch writes and which isolation level protects a given workload.

  • Atomicity — all or nothing.
  • Consistency — constraints hold before and after.
  • Isolation — concurrent transactions don’t corrupt each other.
  • Durability — committed data survives a crash.

2 · Installing & Connecting

2.1 Install2.2 Connect from the CLI2.3 Verify with a query + output

This chapter is about standing up SQL Server Express, MySQL and PostgreSQL on your own machine and reaching them from their command line clients. Follow the installer defaults, pick one engine to start and add the other two when you want to compare dialects directly. A working setup makes every later chapter testable.

2.1 Install

Getting each engine running is quick with modern installers for Windows and other platforms. Choose one engine to start with, accept sensible defaults for ports and service accounts, then add the other two when you want to compare dialects. Write down the credentials you set because every later chapter connects to these servers.

# SQL Server Express — download installer, choose "Basic"
#   instance name default: .\SQLEXPRESS   (Windows auth by default)
# pick one engine first; SQL Server differs most from the others

# MySQL (Windows / Linux / macOS)
winget install Oracle.MySQL
# or: apt install mysql-server

# PostgreSQL
winget install PostgreSQL.PostgreSQL
# or: apt install postgresql

Covers one-line installers for all three engines on Windows and Linux. Notice the SQL Server instance name .\SQLEXPRESS and the two package managers.

2.2 Connect from the CLI

The CLI is the fastest way to reach a database: run a query, inspect a table or try a syntax variant. Learn the one command per engine, sqlcmd for SQL Server, mysql for MySQL and psql for PostgreSQL, together with the flags for host, user and database. This is the base pattern you will use in almost every chapter.

# SQL Server
sqlcmd -S .\SQLEXPRESS -E            # -E = trusted (Windows) auth

# MySQL
mysql -u root -p
# prompts for the password interactively

# PostgreSQL
psql -U postgres -h localhost
# -h names the host; the default port is 5432

Shows the one command per engine to reach a database from the CLI. The flags -S, -u and -U select server, user and host.

2.3 Verify with a query + output

A one-line version query proves your install and connection work end to end: SELECT VERSION in SQL Server, MySQL and PostgreSQL. Keep it as your first sanity check on any new server. Seeing real output from the engine confirms drivers, authentication and network are all correct.

-- SQL Server
-- @@VERSION returns build, edition and OS
SELECT @@VERSION AS version;
-- Output
-- version
-- Microsoft SQL Server 2022 - 16.0.x (Express Edition) ...

-- MySQL
SELECT VERSION() AS version;
-- the +---+ box is the CLI's result grid
-- +-----------+
-- | version   |
-- +-----------+
-- | 8.4.0     |
-- +-----------+

-- PostgreSQL
SELECT version();
-- psql prints the raw banner text
-- PostgreSQL 16.3 on x86_64-pc-linux-gnu, compiled by gcc ...

Each engine answers the same question, version, with a different function and output shape. Use it as the first smoke test of a fresh install.

SQL Server Express defaults to Windows authentication and disables TCP/IP. For app connections enable TCP and either mixed-mode auth or a dedicated least-privilege login.

3 · Data Types Across Engines

3.1 Numeric types3.2 String and binary types3.3 Date and time3.4 Boolean, JSON and other types

The type system is where the engines differ first, so this chapter maps the numeric, string, datetime and JSON types across SQL Server, MySQL and PostgreSQL. Use the mapping to choose an equivalent type in each engine for the same column. Knowing the differences up front prevents subtle portability bugs later.

3.1 Numeric types

For numbers, choose exact decimal types such as DECIMAL and NUMERIC for money and counts, and reserve floating point types like FLOAT and REAL for scientific data where rounding is acceptable. SQL Server also offers MONEY, MySQL adds scaled DECIMAL and PostgreSQL provides NUMERIC and the integer family. Wrong numeric types are a silent source of rounding bugs.

UseSQL ServerMySQLPostgreSQL
IntegerINT / BIGINTINT / BIGINTINTEGER / BIGINT
Exact decimalDECIMAL(12,2)DECIMAL(12,2)NUMERIC(12,2)
Floating pointFLOATDOUBLEDOUBLE PRECISION
Auto keyIDENTITY(1,1)AUTO_INCREMENTGENERATED ALWAYS AS IDENTITY

Use DECIMAL/NUMERIC for money, never FLOAT. Binary floating point cannot represent 0.10 exactly and rounding errors compound.

3.2 String and binary types

Unicode text, long text, fixed-length char and binary blobs each have an engine-specific spelling: NVARCHAR and VARCHAR(MAX) in SQL Server, CHAR, VARCHAR and TEXT in MySQL, and TEXT and BYTEA in PostgreSQL. Match the right type to your data so international characters and large payloads stay intact. VARCHAR is the usual default for normal strings.

UseSQL ServerMySQLPostgreSQL
Variable textNVARCHAR(n)VARCHAR(n)TEXT / VARCHAR(n)
Long textNVARCHAR(MAX)TEXTTEXT
Fixed lengthCHAR(n)CHAR(n)CHAR(n)

3.3 Date and time

Date and time values carry precision and timezone baggage that differs per engine. The timestamp with time zone type, DATETIMEOFFSET in SQL Server and TIMESTAMP WITH TIME ZONE in PostgreSQL, is usually the safe default. Also store the timezone itself and prefer storing UTC so instants stay unambiguous across servers.

UseSQL ServerMySQLPostgreSQL
Timestamp (tz)DATETIMEOFFSETTIMESTAMPTIMESTAMPTZ
Timestamp (no tz)DATETIME2DATETIMETIMESTAMP
Date onlyDATEDATEDATE
Current timeSYSDATETIME()NOW()NOW()
-- All three return the current instant
SELECT SYSDATETIME();   -- SQL Server  -> 2026-09-17 10:24:31.1234567
-- note: 7 fractional digits, no timezone
SELECT NOW();           -- MySQL       -> 2026-09-17 10:24:31
SELECT NOW();           -- PostgreSQL  -> 2026-09-17 10:24:31.123456+00

All three engines return the current instant, but precision and timezone differ: 7 digits, none, or 6 with UTC. Pick the type that matches your needs.

3.4 Boolean, JSON and other types

Beyond the basics each engine has extras such as boolean, JSON and array types. MySQL has a dedicated JSON type, PostgreSQL offers BOOLEAN, JSONB and ARRAY, and SQL Server supports BIT and JSON text handling. Know where the engines line up and where a type exists in only one of them.

4 · DDL — Databases, Schemas & Tables

4.1 Create a database4.2 Schemas and namespaces4.3 Create a table4.4 Verify the schema + output

DDL, data definition language, is how you define the shape of the database: databases, schemas and the tables inside them using CREATE, ALTER and DROP statements. Precise DDL set before data arrives prevents rework later. This chapter covers creating databases, schemas and tables and verifying the result.

4.1 Create a database

A single CREATE DATABASE statement creates a database everywhere, but MySQL adds CHARSET and COLLATE choices that affect string comparison and correctness. SQL Server and PostgreSQL let you set collation per database too. Decide these defaults up front because changing them later on populated data is painful.

-- SQL Server
CREATE DATABASE shop;
-- the simplest form works in every engine
-- Output: Commands completed successfully.

-- MySQL (charset + collation matter!)
CREATE DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- utf8mb4 covers full Unicode incl. emoji
-- Query OK, 1 row affected (0.01 sec)

-- PostgreSQL
CREATE DATABASE shop;
-- CREATE DATABASE

CREATE DATABASE works in all three, but MySQL asks you to pin down charset and collation. The utf8mb4 choice is the one that prevents mojibake.

4.2 Schemas and namespaces

Schemas are organising layers inside a database that group tables and other objects, though MySQL treats schema as a synonym for database. Use CREATE SCHEMA in SQL Server and PostgreSQL to separate modules or tenants, then qualify objects as schema.table. This keeps a shared database tidy and permissions precise.

-- SQL Server: schemas are containers inside a DB
CREATE SCHEMA sales;
-- MySQL: schema == database (no separate namespace)
CREATE DATABASE sales;
-- PostgreSQL: rich schema support
CREATE SCHEMA sales;
-- search_path sets the default lookup schema
SET search_path TO sales, public;

Two engines put schemas inside databases; MySQL treats schema as a synonym for database. search_path makes PostgreSQL resolve names your way.

4.3 Create a table

The CREATE TABLE statement is where columns, data types and defaults come together in every engine. Notice the small but important identity syntax differences: IDENTITY in SQL Server, AUTO_INCREMENT in MySQL and GENERATED AS IDENTITY in PostgreSQL. Match the identity column style to your engine when defining tables.

-- SQL Server
CREATE TABLE customers (
    id        INT IDENTITY(1,1) PRIMARY KEY,
    -- IDENTITY auto-generates the primary key
    name      NVARCHAR(120) NOT NULL,
    email     NVARCHAR(200) NOT NULL UNIQUE,
    created_at DATETIME2 NOT NULL DEFAULT SYSDATETIME()
);

-- MySQL
CREATE TABLE customers (
    id        BIGINT AUTO_INCREMENT PRIMARY KEY,
    name      VARCHAR(120) NOT NULL,
    email     VARCHAR(200) NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- PostgreSQL
CREATE TABLE customers (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- GENERATED ALWAYS blocks manual key values
    name      VARCHAR(120) NOT NULL,
    email     VARCHAR(200) NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

The same customers table created three ways; identity and autoincrement keywords differ but the pattern is identical. PK, NOT NULL, UNIQUE and defaults appear in all three.

4.4 Verify the schema + output

Describing a table back to yourself is the fastest way to confirm DDL did what you intended. Each engine has its own command: sp_help or the INFORMATION_SCHEMA tables in SQL Server, SHOW CREATE TABLE in MySQL, and backslash d in psql for PostgreSQL. Use these to check columns, types, keys and defaults after creation.

-- SQL Server
-- sp_help reports columns, types, indexes, constraints
EXEC sp_help 'customers';
-- name        type          nullable
-- id          int identity  no
-- name        nvarchar      no
-- email       nvarchar      no
-- created_at  datetime2     no

-- MySQL
-- DESCRIBE is short for SHOW COLUMNS
DESCRIBE customers;
-- +------------+--------------+------+-----+-------------------+--+
-- | Field      | Type         | Null | Key | Default           |  |
-- | id         | bigint       | NO   | PRI | NULL              |  |
-- | name       | varchar(120) | NO   |     | NULL              |  |
-- | email      | varchar(200) | NO   | UNI | NULL              |  |
-- | created_at | timestamp    | NO   |     | CURRENT_TIMESTAMP |  |
-- +------------+--------------+------+-----+-------------------+--+

-- PostgreSQL
-- \d is psql's describe shortcut
\d customers
-- Column     | Type        | Nullable | Default
-- id         | bigint      | not null | generated always as identity
-- name       | varchar(120)| not null |
-- email      | varchar(200)| not null |
-- created_at | timestamptz | not null | now()

Three describe commands confirm the same table definition. Each output is a different CLI grid, but the columns match, which is the real test.

5 · Constraints & Keys

5.1 The constraint family5.2 Foreign keys with actions5.3 What a violation looks like + output

Constraints are the database self-defence mechanism that rejects bad data at the door and keeps a schema trustworthy. PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL and DEFAULT are the tools you declare in CREATE TABLE or ALTER TABLE. Rely on them instead of trusting application code to filter invalid input.

5.1 The constraint family

Six constraint tools keep data honest: PRIMARY KEY for identity, FOREIGN KEY for relationships, UNIQUE for alternatives, CHECK for business rules, NOT NULL for required columns and DEFAULT for fill-in values. Declare each with the matching constraint clause in CREATE TABLE or ALTER TABLE. Know the job of each one before designing a schema.

ConstraintEnforces
PRIMARY KEYUnique + not null identity of a row.
FOREIGN KEYValue must exist in the referenced table.
UNIQUENo duplicate values.
CHECKA boolean rule on the column.
NOT NULLValue is mandatory.
DEFAULTValue used when none supplied.

5.2 Foreign keys with actions

Foreign keys define what happens to dependent rows on update or delete through ON DELETE and ON UPDATE actions. CASCADE carries the deletion to children, RESTRICT or NO ACTION blocks it, and SET NULL clears the reference. Choose deliberately per relationship because the action shapes how data disappears.

-- SQL Server
-- ON DELETE CASCADE removes child rows with the parent
CREATE TABLE orders (
    id          INT IDENTITY(1,1) PRIMARY KEY,
    customer_id INT NOT NULL,
    total       DECIMAL(12,2) NOT NULL CHECK (total >= 0),
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE CASCADE
);

-- MySQL
CREATE TABLE orders (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    total       DECIMAL(12,2) NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE CASCADE,
    CONSTRAINT chk_total CHECK (total >= 0)
);

-- PostgreSQL
-- PostgreSQL allows an inline REFERENCES on the column
CREATE TABLE orders (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
    total       NUMERIC(12,2) NOT NULL CHECK (total >= 0)
);

A foreign key with ON DELETE CASCADE: deleting a customer removes their orders automatically. SQL Server and MySQL name the constraint; PostgreSQL inlines it.

5.3 What a violation looks like + output

When a row breaks a constraint the engines reply with loud, instructive diagnostics: SQL Server names the constraint, MySQL reports the key name and PostgreSQL states the exact check that failed. Use these messages to find which rule rejected the row. They are your feedback loop when debugging bad inserts and updates.

-- customer 999 doesn't exist: FK violation
INSERT INTO orders (customer_id, total) VALUES (999, 10.00);
-- each engine names the constraint it rejected

-- SQL Server
-- Msg 547: The INSERT statement conflicted with the FOREIGN KEY constraint "fk_orders_customer".

-- MySQL
-- ERROR 1452 (23000): Cannot add or update a child row:
--   a foreign key constraint fails (`shop`.`orders`, CONSTRAINT `fk_orders_customer`)

-- PostgreSQL
-- ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
-- DETAIL: Key (customer_id)=(999) is not present in table "customers".

Inserting an order for customer 999 fails in all three engines because no such customer exists. Each engine names the broken constraint, which makes debugging easy.

Prefer ON DELETE RESTRICT (the default) for business data so you cannot silently delete history. Reserve CASCADE for genuinely dependent child rows.

6 · Indexes

6.1 Why indexes exist6.2 Create indexes6.3 Reading a query plan + output6.4 Covering and partial indexes

Indexes are the difference between instant point lookups and full-table scans, and the biggest performance lever in SQL. Learn to create them with CREATE INDEX, use composite and covering variants, and read the query plan that proves they are being used. Index design follows the queries you actually run.

6.1 Why indexes exist

An index trades a little write cost for much faster reads, turning a lookup from a full scan into a log-style search. It is the single biggest lever on query performance. Create indexes on the columns you filter, join or order by, and check the plan to confirm the engine actually uses them.

Without an index, a lookup is a full table scan — O(n). A B-tree index turns it into a logarithmic search — O(log n). Indexes speed reads and slow writes (each insert updates every index).

6.2 Create indexes

Creating an index is one line in any engine: CREATE INDEX on a table and columns. Composite indexes cover several columns, and expression indexes such as PostgreSQL functional indexes go further. Index what your queries actually filter on, and favour fewer, useful indexes over many unused ones.

-- SQL Server
-- index the foreign key you join on
CREATE INDEX ix_orders_customer ON orders(customer_id);
CREATE INDEX ix_orders_customer_total ON orders(customer_id, total DESC);

-- MySQL
CREATE INDEX ix_orders_customer ON orders(customer_id);
CREATE INDEX ix_orders_customer_total ON orders(customer_id, total);

-- PostgreSQL
CREATE INDEX ix_orders_customer ON orders(customer_id);
CREATE INDEX ix_orders_customer_total ON orders(customer_id, total DESC);
CREATE INDEX ix_orders_lower_email ON customers(LOWER(email));  -- expression index

Indexes are created with one statement in each engine. Composite and expression indexes extend the pattern for more targeted lookups.

6.3 Reading a query plan + output

The query plan is the engine explanation of how it will run your SQL, obtained with EXPLAIN in MySQL and PostgreSQL or the estimated execution plan in SQL Server. A good plan shows an index seek; a bad one shows a table scan. Read the plan to verify an index helped and to locate the slowest step.

-- SQL Server
-- showplan_text prints the plan instead of rows
SET SHOWPLAN_TEXT ON;
SELECT * FROM orders WHERE customer_id = 1;
-- Output: Index Seek ... ix_orders_customer   (good: seek, not scan)

-- MySQL
-- EXPLAIN shows the estimated plan and chosen key
EXPLAIN SELECT * FROM orders WHERE customer_id = 1;
-- +----+-------+------+---------------+---------------------+------+-------+
-- | id | table | type | possible_keys | key                 | rows | Extra |
-- | 1  | orders| ref  | ix_orders_c.. | ix_orders_customer  | 3    |       |

-- PostgreSQL
-- ANALYZE runs the query and reports real timings
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 1;
-- Index Scan using ix_orders_customer on orders
--   Index Cond: (customer_id = 1)
--   Planning Time: 0.12 ms  Execution Time: 0.05 ms

Explain tools prove an index is used: the plan shows a seek or an index scan, not a table scan. ANALYZE in PostgreSQL even reports real timings.

6.4 Covering and partial indexes

A covering index answers the query entirely from the index alone, avoiding a round trip to the table, while a partial index with a WHERE clause indexes only a hot subset of rows. Both reduce space and I/O for targeted workloads. Build them when measurements show reads on a narrow, frequently used set of columns.

-- SQL Server: INCLUDE avoids key lookups
CREATE INDEX ix_orders_cust_cover ON orders(customer_id) INCLUDE (total);

-- PostgreSQL: partial index for a hot subset
CREATE INDEX ix_orders_pending ON orders(created_at) WHERE status = 'pending';

-- MySQL: composite index can cover a query when it includes all columns used
CREATE INDEX ix_orders_cust_total ON orders(customer_id, total);

Covering and partial indexes trade space for speed: INCLUDE stores extra columns, and WHERE limits the index to a hot subset.

Column order in a composite index matters. (customer_id, total) helps queries filtering on customer_id, or customer_id+total, but not on total alone. Put equality columns first, range columns last.

7 · DML — Create, Read, Update, Delete

7.1 INSERT + output7.2 SELECT + output7.3 UPDATE + output7.4 DELETE + output7.5 UPSERT — the dialects diverge

This chapter covers the everyday CRUD verbs: INSERT, SELECT, UPDATE and DELETE, with OUTPUT and RETURNING where useful, plus an honest look at how upserts diverge. Run each against your engines and compare the result messages. These statements are the base of almost everything you write in SQL.

7.1 INSERT + output

INSERT adds rows in the same basic form everywhere: INSERT INTO table with column lists and VALUES. Bulk inserts differ slightly, using multi-row VALUES, SELECT-based inserts or the engine bulk tools. Success replies vary, but a message like one row affected or the returned count is the universal confirmation.

-- All three
-- all engines share this basic INSERT form
INSERT INTO customers (name, email) VALUES ('Ada', 'ada@example.com');

-- SQL Server
-- (1 row affected)

-- MySQL
-- Query OK, 1 row affected (0.00 sec)

-- PostgreSQL
-- INSERT 0 1

-- Bulk insert (syntax differs)
INSERT INTO customers (name, email) VALUES
 ('Grace', 'grace@example.com'),
 ('Linus', 'linus@example.com');

The classic insert is identical across engines; only the success message differs. Bulk insert with multi-row VALUES is portable too.

7.2 SELECT + output

SELECT is the read path: choose columns, filter with WHERE, order with ORDER BY and read the result grid. All three engines share the core syntax, with output formatting differing a little. Understand the basics here because joins, grouping and window functions all extend this statement.

-- ORDER BY sorts rows before the grid prints
SELECT id, name, email FROM customers ORDER BY id;
-- the pipe grid repeats across all three CLIs

-- | id | name  | email              |
-- | 1  | Ada   | ada@example.com    |
-- | 2  | Grace | grace@example.com  |
-- | 3  | Linus | linus@example.com  |

The simplest read: pick three columns, order by id, read the grid. Output formatting differs marginally between CLIs, the data does not.

7.3 UPDATE + output

UPDATE changes existing rows: UPDATE table SET column equals a value WHERE condition. Only the rows matched by the WHERE clause change, so scope the condition carefully and preview it with SELECT first. An update without a WHERE clause touches every row in the table.

-- WHERE id = 1 limits the change to a single row
UPDATE customers SET name = 'Ada Lovelace' WHERE id = 1;

-- SQL Server : (1 row affected)
-- MySQL      : Query OK, 1 row affected
-- PostgreSQL : UPDATE 1

Updates a single row by id; the three-verb success line tells you exactly one row changed. Always scope updates with WHERE.

7.4 DELETE + output

DELETE removes rows: DELETE FROM table WHERE condition, where the WHERE clause is your safety net. Run the matching SELECT first to preview exactly what will go before you remove it. Without a WHERE clause the whole table is emptied.

-- only the matching row disappears
DELETE FROM customers WHERE id = 3;
-- SQL Server : (1 row affected)
-- MySQL      : Query OK, 1 row affected
-- PostgreSQL : DELETE 1

-- Safety: always run the SELECT with the same WHERE first.

Deletes one row and each CLI reports its own one-row message. The safety tip is the important part: preview with SELECT first.

7.5 UPSERT — the dialects diverge

Inserting or updating in one shot is genuinely different in each engine: MERGE in SQL Server, INSERT ON DUPLICATE KEY UPDATE in MySQL, and INSERT ON CONFLICT DO UPDATE in PostgreSQL. Pick the dialect of your platform and test the exact conflict rules you need. The same logical operation has very different spelling and semantics.

-- SQL Server: MERGE (or a pattern with IF EXISTS)
-- MERGE matches on email, then inserts or updates
MERGE customers AS t
USING (SELECT 'ada@example.com' AS email, 'Ada L.' AS name) AS s
   ON t.email = s.email
WHEN MATCHED THEN UPDATE SET name = s.name
WHEN NOT MATCHED THEN INSERT (name, email) VALUES (s.name, s.email);
-- (1 row affected)

-- MySQL: ON DUPLICATE KEY UPDATE
-- ON DUPLICATE KEY turns a conflicting insert into an update
INSERT INTO customers (name, email) VALUES ('Ada L.', 'ada@example.com')
ON DUPLICATE KEY UPDATE name = VALUES(name);
-- Query OK, 2 rows affected

-- PostgreSQL: ON CONFLICT
INSERT INTO customers (name, email) VALUES ('Ada L.', 'ada@example.com')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;
-- INSERT 0 1

All three engines support insert-or-update, but the syntax and the row-count replies genuinely diverge. Expect to look up each dialect’s form.

8 · Joins, Aggregates & Analytics

8.1 Joins + output8.2 GROUP BY and HAVING + output8.3 Window functions + output8.4 CTEs and recursion8.5 Pagination — three syntaxes

This chapter is where SQL earns its keep: joining tables, grouping rows, and computing analytics with window functions and recursive CTEs. These patterns answer most real reporting questions engine after engine. Each section runs the same query across all three engines and compares the results.

8.1 Joins + output

Joins combine tables on keys using INNER JOIN to keep only matching rows and LEFT JOIN to keep every row from the left side, with RIGHT and FULL JOIN for the other sides. Write the join condition in the ON clause after the join type. This is the foundation of relational reporting across all three engines.

-- inner join: only rows with a match survive
SELECT c.name, o.id AS order_id, o.total
FROM customers c
JOIN orders o ON o.customer_id = c.id
ORDER BY c.name;

-- | name  | order_id | total |
-- | Ada   | 10       | 99.90 |
-- | Ada   | 11       | 12.00 |
-- | Grace | 12       | 45.00 |

-- LEFT JOIN keeps customers with no orders (NULL order columns):
SELECT c.name, COUNT(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;

-- | name  | orders |
-- | Ada   | 2      |
-- | Grace | 1      |
-- | Linus | 0      |

An inner join pairs matched rows; the left join keeps zero-order customers with NULLs. The row counts per customer are what you notice.

8.2 GROUP BY and HAVING + output

GROUP BY rolls rows into summary groups and HAVING filters the groups that result, applied after aggregation, in contrast to WHERE which filters rows first. Use COUNT, SUM, AVG, MIN and MAX with GROUP BY to produce totals and counts. Together they turn raw rows into summary numbers.

-- one summary row per customer
SELECT customer_id, COUNT(*) AS orders, SUM(total) AS revenue
FROM orders
GROUP BY customer_id
-- HAVING filters groups; WHERE filters rows
HAVING SUM(total) > 50
ORDER BY revenue DESC;

-- | customer_id | orders | revenue |
-- | 1           | 2      | 111.90  |

GROUP BY collapses orders per customer; HAVING keeps only groups above 50. The result is one summary row per customer.

8.3 Window functions + output

Window functions compute per-row values such as RANK, ROW_NUMBER and running totals without collapsing rows into groups. The OVER clause defines the partition and ordering, distinct from GROUP BY. Use them for rankings, cumulative sums and moving averages where GROUP BY cannot keep the detail rows.

SELECT c.name, o.total,
       ROW_NUMBER() OVER (PARTITION BY c.id ORDER BY o.total DESC) AS rn
FROM orders o
-- ranks rows within each customer partition
JOIN customers c ON c.id = o.customer_id;

-- | name  | total | rn |
-- | Ada   | 99.90 | 1  |
-- | Ada   | 12.00 | 2  |
-- | Grace | 45.00 | 1  |

-- Running total
-- sums each row plus all previous rows
SELECT id, total,
       SUM(total) OVER (ORDER BY id) AS running_total
FROM orders;

-- | id | total | running_total |
-- | 10 | 99.90 | 99.90         |
-- | 11 | 12.00 | 111.90        |
-- | 12 | 45.00 | 156.90        |

Window functions rank and total without flattening rows: ROW_NUMBER per customer and a plain running total. No GROUP BY needed.

8.4 CTEs and recursion

A CTE names a subquery with WITH for readability and reuse inside a statement, and the RECURSIVE keyword lets you walk trees like org charts and bill-of-materials data. All three engines support the WITH syntax, with recursion supported in PostgreSQL and SQL Server and available from MySQL 8. Use CTEs for layered, hierarchical or self-referential queries.

-- All three support WITH
WITH big AS (
    SELECT customer_id, SUM(total) AS revenue
    FROM orders GROUP BY customer_id
)
-- big behaves like a read-only table here
SELECT * FROM big WHERE revenue > 100;

-- Recursive CTE: employee hierarchy (PostgreSQL/MySQL 8+/SQL Server)
WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 1 AS depth FROM employees WHERE manager_id IS NULL
    -- base managers, then UNION steps down a level each round
    UNION ALL
    SELECT e.id, e.name, e.manager_id, o.depth + 1
    FROM employees e JOIN org o ON e.manager_id = o.id
)
SELECT * FROM org ORDER BY depth;

A WITH block names a subquery for reuse, and RECURSIVE walks a hierarchy by unioning a base case with a recursive step.

8.5 Pagination — three syntaxes

Paging is OFFSET and FETCH in SQL Server and LIMIT and OFFSET in MySQL and PostgreSQL, all inside ORDER BY queries. Offset paging is simple but slows on deep pages; keyset pagination using a WHERE clause on the last seen key stays fast. Choose based on page depth and data growth.

-- SQL Server
-- OFFSET/FETCH is the SQL Server form
SELECT * FROM orders ORDER BY id OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- MySQL
-- LIMIT...OFFSET is the MySQL/PostgreSQL form
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 20;

-- PostgreSQL
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 20;

-- Tip: keyset pagination (WHERE id > @lastId ORDER BY id LIMIT 10)
-- stays fast at deep offsets where OFFSET 1000000 degrades.

Three pagination spellings do the same thing, and the tip is the real lesson: keyset pagination stays fast where big OFFSET values crawl.

9 · Transactions & Isolation

9.1 Transactions in each engine9.2 Isolation levels9.3 Deadlocks + output

Transactions guarantee that multi-step work is all-or-nothing using BEGIN, COMMIT and ROLLBACK, and this chapter applies them across the engines. Understanding isolation levels and deadlocks keeps concurrent systems correct. Test transaction behaviour per engine because defaults and behaviour differ.

9.1 Transactions in each engine

Begin, change, commit is the transaction shorthand in every engine: BEGIN TRANSACTION in SQL Server, START TRANSACTION in MySQL and BEGIN in PostgreSQL, all ended with COMMIT or ROLLBACK. Wrap multi-step writes so they never half-apply under an error. Keep transactions short to minimise lock time.

-- SQL Server
-- debit then credit must commit together
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT TRANSACTION;

-- MySQL
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- (ROLLBACK instead of COMMIT to undo)

-- PostgreSQL
-- BEGIN/COMMIT is PG's shorthand
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

Wrap a paired debit and credit in BEGIN...COMMIT so they commit as one unit. Only the keyword spelling differs; ROLLBACK works everywhere.

9.2 Isolation levels

Isolation levels trade consistency for concurrency, from READ UNCOMMITTED at the lax end through READ COMMITTED and REPEATABLE READ up to SERIALIZABLE. The engine defaults already protect you from most anomalies: READ COMMITTED in SQL Server and PostgreSQL, REPEATABLE READ in MySQL. Change levels only when you have measured a specific need.

LevelDirty readNon-repeatable readPhantom read
READ UNCOMMITTEDYesYesYes
READ COMMITTEDNoYesYes
REPEATABLE READNoNoYes*
SERIALIZABLENoNoNo
-- Defaults differ:
-- SQL Server : READ COMMITTED
-- MySQL      : REPEATABLE READ   (*InnoDB largely prevents phantoms via gap locks)
-- PostgreSQL : READ COMMITTED

-- SERIALIZABLE is the strictest isolation level
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;   -- SQL Server / PostgreSQL
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- MySQL

Default isolation differs: SQL Server and PostgreSQL use READ COMMITTED, MySQL REPEATABLE READ. Raise the level only when you need stricter guarantees.

9.3 Deadlocks + output

When two sessions hold locks and each waits on the other, one is sacrificed with an error and told to retry. Prevent them with short transactions and a consistent lock ordering across all sessions. The engine error messages name the victim and the resources involved so you can fix the offending access pattern.

-- Session A locks row 1, Session B locks row 2, then each asks for the other's row.
-- SQL Server
-- Msg 1205: Transaction (Process ID 57) was deadlocked on lock resources
--           and has been chosen as the deadlock victim. Rerun the transaction.

-- MySQL
-- ERROR 1213 (40001): Deadlock found when trying to get lock;
--   try restarting transaction

-- PostgreSQL
-- ERROR:  deadlock detected
-- DETAIL: Process 123 waits for ShareLock on transaction 456; blocked by process 789.

-- Mitigations: access tables/rows in a consistent order, keep
-- transactions short, add the right indexes, and retry on deadlock.

Three renderings of the same deadlock error plus the fix list. One victim is chosen and told to retry, which is why retrying is part of the pattern.

10 · Views, Procedures, Functions & Triggers

10.1 Views10.2 Stored procedures — dialects diverge most10.3 Functions10.4 Triggers

Programmable objects let you package SQL for reuse: views simplify and control access, stored procedures and functions encapsulate logic with parameters, and triggers react automatically to changes. Each engine has the full family with dialect differences in syntax. Learn the skeleton of each object type in your platform.

10.1 Views

A view is a saved query you can query like a table, created with CREATE VIEW. It hides joins and complex logic and grants a controlled window onto the data, useful for security and reporting convenience. Materialised views in PostgreSQL and indexed views in SQL Server go further by storing the result.

-- Identical in all three
CREATE VIEW v_customer_revenue AS
-- COALESCE turns NULL into zero for customers with no orders
SELECT c.id, c.name, COALESCE(SUM(o.total), 0) AS revenue
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

SELECT * FROM v_customer_revenue WHERE revenue > 100;
-- | id | name | revenue |
-- | 1  | Ada  | 111.90  |

A view stores a grouped join query you can query like a table. COALESCE turns customers with no orders from NULL into zero.

10.2 Stored procedures — dialects diverge most

Stored procedures encapsulate multi-step SQL with parameters and control flow, and here the dialects diverge most. SQL Server uses CREATE PROCEDURE invoked with EXEC, MySQL uses CREATE PROCEDURE invoked with CALL, and PostgreSQL uses CREATE PROCEDURE or CREATE FUNCTION. Learn the skeleton of each dialect before writing your own.

-- SQL Server
CREATE PROCEDURE usp_AddCustomer @name NVARCHAR(120), @email NVARCHAR(200)
AS
BEGIN
    INSERT INTO customers(name, email) VALUES (@name, @email);
END;
-- EXEC runs the procedure
EXEC usp_AddCustomer 'Ada', 'ada@example.com';

-- MySQL
DELIMITER //
CREATE PROCEDURE usp_AddCustomer(IN p_name VARCHAR(120), IN p_email VARCHAR(200))
BEGIN
    INSERT INTO customers(name, email) VALUES (p_name, p_email);
END //
-- DELIMITER lets the body keep its semicolons
DELIMITER ;
CALL usp_AddCustomer('Ada', 'ada@example.com');

-- PostgreSQL (functions; CALL for procedures since v11)
CREATE PROCEDURE usp_AddCustomer(p_name VARCHAR, p_email VARCHAR)
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO customers(name, email) VALUES (p_name, p_email);
END; $$;
-- CALL runs procedures in all three
CALL usp_AddCustomer('Ada', 'ada@example.com');

The same AddCustomer procedure in three dialects; parameter markers and delimiters differ but the idea is shared. CALL runs it in all three.

10.3 Functions

Functions return a value for use inside SQL expressions, from a scalar tax calculation up to table-returning functions. SQL Server and MySQL define them with CREATE FUNCTION, and PostgreSQL with CREATE FUNCTION in a chosen language. Scalar functions keep logic in one place but can be slow, so test their cost in queries.

-- SQL Server
-- scalar function computes and returns the tax
CREATE FUNCTION dbo.fn_Tax(@amount DECIMAL(12,2)) RETURNS DECIMAL(12,2)
AS BEGIN RETURN @amount * 0.20; END;
SELECT dbo.fn_Tax(100);        -- 20.00

-- MySQL
CREATE FUNCTION fn_Tax(amount DECIMAL(12,2)) RETURNS DECIMAL(12,2)
DETERMINISTIC
RETURN amount * 0.20;
SELECT fn_Tax(100);            -- 20.00

-- PostgreSQL
CREATE FUNCTION fn_tax(amount NUMERIC) RETURNS NUMERIC
LANGUAGE sql IMMUTABLE AS $$ SELECT amount * 0.20 $$;
SELECT fn_tax(100);            -- 20.00

A scalar tax function in each engine; RETURN works everywhere, only the boilerplate differs. DETERMINISTIC and IMMUTABLE allow caching.

10.4 Triggers

Triggers run automatically on INSERT, UPDATE or DELETE on a table, defined with CREATE TRIGGER in every engine, with BEFORE and AFTER timing variants. They are great for auditing and maintaining derived data. Keep them small because hidden logic surprises people and can slow writes.

-- SQL Server (AFTER INSERT audit)
CREATE TRIGGER trg_orders_audit ON orders AFTER INSERT AS
BEGIN
    -- inserted is a virtual table of the new rows
    INSERT INTO order_audit(order_id, action, at)
    SELECT id, 'INSERT', SYSDATETIME() FROM inserted;
END;

-- MySQL
CREATE TRIGGER trg_orders_audit AFTER INSERT ON orders
-- FOR EACH ROW fires once per affected row
FOR EACH ROW
INSERT INTO order_audit(order_id, action, at)
VALUES (NEW.id, 'INSERT', NOW());

-- PostgreSQL (row-level trigger calling a function)
CREATE FUNCTION audit_order() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO order_audit(order_id, action, at)
    VALUES (NEW.id, 'INSERT', NOW());
    RETURN NEW;
END; $$;
CREATE TRIGGER trg_orders_audit AFTER INSERT ON orders
FOR EACH ROW EXECUTE FUNCTION audit_order();

Three audit triggers that log every inserted order. The idea is the same, but each engine exposes the new row differently: inserted, NEW and NEW.

Triggers are powerful but hide logic. Keep them small and single-purpose, and document them — future maintainers will not see them in application code.

11 · Normalisation & Schema Design

11.1 The normal forms11.2 When to denormalise11.3 Naming and modelling conventions

Normalisation removes redundancy so data stays consistent when it changes, and this chapter also covers when to break the rules. Design for third normal form by default, then denormalise deliberately on measured evidence. Good normalisation makes checking, updates and schema evolution predictable.

11.1 The normal forms

The normal forms describe what redundancy to remove at each level, from 1NF about atomic columns up through 2NF and 3NF and into BCNF. Apply them by splitting tables until every non-key column depends on the key, the whole key and nothing but the key. They give you a language for defending schema decisions.

FormRuleFixes
1NFAtomic values, no repeating groupsComma lists in a cell
2NF1NF + no partial dependency on part of a composite keyRedundant attrs
3NF2NF + no transitive dependency (non-key → non-key)Update anomalies
BCNFEvery determinant is a candidate keyRare edge cases
-- Violates 1NF: tags as a comma list
-- posts(id, title, tags)  tags = 'sql,mysql,postgres'

-- 1NF fix: separate table
-- posts(id, title)  tags(id, name)  post_tags(post_id, tag_id)

-- Violates 3NF: city/zip stored on orders -> depends on customer address
-- orders(id, customer_id, city, zip)  -- city, zip transitively depend on customer

-- 3NF fix: keep address on customers; orders keeps customer_id only.

Illustrates a 1NF violation with comma-list tags and a 3NF violation where city and zip depend on the customer, then sketches the fixes.

11.2 When to denormalise

Production schemas routinely bend the rules for performance, duplicating data or adding derived columns to avoid expensive joins. Denormalise deliberately, only when measurements such as query plans and timings justify it, and keep the duplication disciplined. Every copy you add is something you must keep in sync.

  • Read-heavy dashboards where joins dominate cost.
  • Materialised aggregates refreshed on a schedule.
  • Frequently-read derived values stored alongside the source.

Denormalise deliberately, measure the gain, and document the inconsistency window.

11.3 Naming and modelling conventions

Consistent naming and a uniform modelling style make a schema readable by the whole team: singular table names, a clear primary key name such as id, and descriptive foreign key names like user_id. Agree the conventions once and enforce them in reviews and migrations. Every later review gets easier when the shape is predictable.

  • Singular or plural consistently (customers is common).
  • snake_case for objects and columns across all engines.
  • Every table has a surrogate PK; natural keys become unique constraints.
  • Timestamps in UTC; store created_at/updated_at.

12 · Enterprise Design — Partitioning, Replication & HA

12.1 Table partitioning12.2 Replication and read replicas12.3 High availability and failover12.4 Sharding and federation

When one server stops being enough you partition tables, replicate data and add failover, and this chapter maps the enterprise pattern space. Use partitioning to split huge tables, replication for read scaling and HA for automatic failover, and sharding as the last resort. Each pattern adds capacity but also operational cost.

12.1 Table partitioning

Partitioning splits one big table into smaller physical segments by a key such as date using RANGE or LIST partitioning in MySQL and PostgreSQL, or partitioned tables in SQL Server. Queries that filter on the partition key can prune segments, keeping huge tables manageable. Choose the partition key to match your most common WHERE clauses.

-- PostgreSQL: declarative range partitioning
CREATE TABLE orders (id BIGINT, created_at TIMESTAMPTZ NOT NULL, total NUMERIC)
PARTITION BY RANGE (created_at);
-- one partition per month range
CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

-- MySQL: partition by range
ALTER TABLE orders PARTITION BY RANGE (YEAR(created_at)) (
  PARTITION p2026 VALUES LESS THAN (2027),
  PARTITION pmax  VALUES LESS THAN MAXVALUE
);

-- SQL Server: partition function + scheme, then ON the scheme
-- the function maps values, the scheme maps partitions to files
CREATE PARTITION FUNCTION pfYear (int) AS RANGE RIGHT FOR VALUES (2025, 2026);
CREATE PARTITION SCHEME psYear AS PARTITION pfYear ALL TO ([PRIMARY]);
CREATE TABLE orders (id INT, created_at datetime2) ON psYear(YEAR(created_at));

Partitions a table by date range three ways; PostgreSQL is declarative, MySQL uses a range clause, SQL Server a function plus scheme.

12.2 Replication and read replicas

Replication copies data to other servers so reads can scale and failover has somewhere to go. SQL Server uses Always On availability groups, MySQL uses source-replica or group replication, and PostgreSQL uses streaming replication. Accept some lag as you trade a little consistency for capacity.

EngineMechanismTypical use
SQL ServerTransactional / merge replication, Always On AGHA + read scale + DR
MySQLBinlog replication (async/semi-sync), Group ReplicationRead replicas + HA
PostgreSQLStreaming + logical replicationRead replicas + selective sync
-- PostgreSQL: logical replication publication/subscription
-- publisher
CREATE PUBLICATION pub_orders FOR TABLE orders;
-- subscriber
CREATE SUBSCRIPTION sub_orders
  CONNECTION 'host=pub dbname=shop'
  PUBLICATION pub_orders;
-- the subscription pulls and applies published changes

-- Read replica lag is the trade-off; route only
-- tolerant reads there and never rely on a replica for read-after-write.

A publisher/subscription pair streams table changes to a subscriber. The warning is the key part: replicas lag, so never route read-after-write there.

12.3 High availability and failover

High availability means another node can take over automatically when the primary fails, through mechanisms such as SQL Server Always On failover clusters, MySQL Group Replication and PostgreSQL Patroni with streaming replication. Each engine has a supported answer, so plan the configuration and drill failover before you need it. Test recovery as well as replication.

  • SQL Server: Always On Availability Groups with a listener; automatic failover on the sync replica.
  • MySQL: InnoDB Cluster / Group Replication with a router.
  • PostgreSQL: Patroni + etcd/Consul, or managed failover.

12.4 Sharding and federation

Sharding spreads one table across many nodes by a key such as user_id, so writes can scale beyond a single server. It costs you joins across shards, transactions and a rebalance effort when the key distribution changes. Be sure the write volume justifies it before introducing that complexity.

Sharding splits one logical table across nodes by a key (tenant, region, hash). It scales writes but brings cross-shard joins, distributed transactions and rebalancing pain. Exhaust vertical scaling, indexes and caching first.

13 · Performance Tuning

13.1 Index strategy13.2 Reading plans and finding the bottleneck13.3 Statistics and maintenance13.4 Connection pooling

Tuning is measured, not guessed: read the query plan, find the slow statement, then fix the index or query. This chapter gives you the workflow of EXPLAIN plans, index strategy, statistics maintenance and connection pooling rather than magic. Apply it to the slowest queries first for the best returns.

13.1 Index strategy

Index strategy is about matching the engine to the queries you actually run: index the columns in WHERE, JOIN and ORDER BY clauses, and prefer composite indexes whose column order suits the access path. A few well-chosen indexes beat a pile of guesses. Verify each index with EXPLAIN and drop ones the plans never use.

  • Index the columns in WHERE, JOIN and ORDER BY.
  • Composite indexes: equality columns first, range last.
  • Avoid over-indexing — every index taxes writes.
  • Remove unused/duplicate indexes.

13.2 Reading plans and finding the bottleneck

The query plan and its statistics tell you where time actually goes before you touch any code. Use EXPLAIN in MySQL and PostgreSQL and the execution plan in SQL Server, and learn to spot scans, seeks and high logical reads. The most expensive step in the plan is where tuning should start.

-- SQL Server
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
-- every query then reports read counts and elapsed time
-- look for "Scan count", high "logical reads", and Table/Index Scan nodes

Switches on IO and time statistics so every query reports its reads and duration. Learn to watch scan counts and logical reads.

-- MySQL: find slow queries
-- slowest queries by latency come first
SELECT * FROM sys.statement_analysis ORDER BY total_latency DESC LIMIT 5;
EXPLAIN ANALYZE SELECT ... ;   -- MySQL 8.0.18+

-- PostgreSQL: pg_stat_statements
-- aggregates the real statements the app runs
SELECT query, calls, mean_exec_time
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 5;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

Two system views surface the slowest queries: statement_analysis and pg_stat_statements. Pair them with EXPLAIN ANALYZE to see the plan.

13.3 Statistics and maintenance

The optimizer needs fresh statistics to make good plans, so run the maintenance that keeps them current: UPDATE STATISTICS in SQL Server, ANALYZE and VACUUM in PostgreSQL, and ANALYZE TABLE for InnoDB statistics in MySQL. Dead rows and bloat want vacuuming and reorgs. Regular maintenance keeps tables fast as data grows.

-- SQL Server
-- refresh the optimizer's histograms
UPDATE STATISTICS orders;

-- MySQL
ANALYZE TABLE orders;

-- PostgreSQL
ANALYZE orders;
-- reclaims dead tuple space as well
VACUUM (VERBOSE, ANALYZE) orders;   -- reclaim dead tuples

Refreshing optimizer statistics is one command per engine. PostgreSQL’s VACUUM also reclaims space from dead rows.

13.4 Connection pooling

Opening a database connection is expensive, so reuse them through a connection pool in your application. Size the pool to the server and its connection limits, not to the app thread count, to avoid exhausting the database. Pooled connections amortise setup cost and warm up the connection state once.

Opening a connection is expensive. Pool at the app or a proxy (PgBouncer for PostgreSQL, ProxySQL for MySQL, built-in pooling in .NET/Java). Size pools to the DB’s max connections, not to the app’s thread count.

14 · Security

14.1 Users, roles and grants14.2 Row-level security14.3 Encryption and auditing

Security is least privilege applied everywhere: users and roles, grants, row filters and encryption. Create principals as logins and users, grant only what they need and audit what they do. A single bad grant can hand an attacker the whole database, so review privileges regularly.

14.1 Users, roles and grants

Authenticate people and applications as principals, then grant only the privileges they need using CREATE USER and CREATE LOGIN plus GRANT and REVOKE statements. Bundle common rights in roles with CREATE ROLE in every engine. Least privilege is the backbone of database security and keeps a compromise contained.

-- SQL Server
-- login is server-level; user is database-level
CREATE LOGIN app_user WITH PASSWORD = 'Str0ng!Passw0rd';
CREATE USER app_user FOR LOGIN app_user;
GRANT SELECT, INSERT, UPDATE ON dbo.orders TO app_user;

-- MySQL
CREATE USER 'app_user'@'%' IDENTIFIED BY 'Str0ng!Passw0rd';
-- least privilege: SELECT/INSERT/UPDATE only
GRANT SELECT, INSERT, UPDATE ON shop.* TO 'app_user'@'%';
FLUSH PRIVILEGES;

-- PostgreSQL
-- a ROLE with LOGIN is a user in PG
CREATE ROLE app_user LOGIN PASSWORD 'Str0ng!Passw0rd';
GRANT SELECT, INSERT, UPDATE ON orders TO app_user;

Creates a least-privilege app user in each engine: login or role, then selective grants. Never grant more than SELECT, INSERT, UPDATE for an app.

-- Verify grants
-- MySQL
-- shows the exact privileges granted
SHOW GRANTS FOR 'app_user'@'%';
-- +----------------------------------------------------------+
-- | GRANT SELECT, INSERT, UPDATE ON `shop`.* TO `app_user`@% |
-- +----------------------------------------------------------+

-- PostgreSQL
-- \dp lists access privileges per table
\dp orders
-- Access privileges
-- Schema | Name   | Type  | Access privileges
-- public | orders | table | postgres=arwdDxt/postgres,app_user=arw/postgres

Two ways to verify what a user may do: SHOW GRANTS and psql’s \dp. Both confirm the exact privileges you just granted, nothing more.

14.2 Row-level security

Row-level security lets the database hide rows by user or tenant instead of trusting the app to filter, using row security policies in PostgreSQL and security predicates in SQL Server. Define the policy once and it applies to every query that touches the table. It is an extra fence worth having for multi-tenant data.

-- PostgreSQL
-- RLS hides rows the policy rejects
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY owner_only ON documents
  USING (owner_id = current_setting('app.user_id')::bigint);
-- every SELECT must pass the USING predicate

-- SQL Server: RLS via a predicate function + security policy
CREATE FUNCTION dbo.fn_tenant(@tenant int) RETURNS TABLE
WITH SCHEMABINDING AS
RETURN SELECT 1 AS ok WHERE @tenant = CAST(SESSION_CONTEXT(N'tenant') AS int);
CREATE SECURITY POLICY TenantFilter
  ADD FILTER PREDICATE dbo.fn_tenant(tenant_id) ON dbo.orders;

-- MySQL: enforce tenancy in a view or application layer.

Row-level security hides rows that fail the USING predicate. PostgreSQL enables it directly on the table; SQL Server needs a predicate function plus policy.

14.3 Encryption and auditing

Encrypt data in transit with TLS in each engine and at rest with transparent data encryption in SQL Server, tablespace encryption in MySQL and cluster-level encryption in PostgreSQL. Audit who did what through the engine audit logs. Compliance and forensics both start with these basics.

  • In transit: force TLS on every connection.
  • At rest: SQL Server TDE, MySQL InnoDB encryption, PostgreSQL pgcrypto/disk encryption.
  • Column-level: encrypt PII with pgcrypto, Always Encrypted (SQL Server), or app-level.
  • Auditing: SQL Server Audit, MySQL audit plugin, PostgreSQL pgaudit.

Never grant db_owner/ALL PRIVILEGES to an application account. A single SQL-injection then owns the whole database. Grant least privilege only.

15 · JSON & Semi-Structured Data

15.1 Store a JSON document15.2 Query inside JSON + output

Store flexible or sparse data as JSON while still querying it with SQL, and this chapter covers where JSON fits and where a column beats it. Use the JSON column types and the operators each engine provides. The trick is knowing when schema flexibility earns its cost and when a plain relational column is cleaner.

15.1 Store a JSON document

All three engines can hold JSON today: PostgreSQL JSONB gives it real indexing and query semantics, MySQL JSON has validation and generated columns, and SQL Server stores JSON in NVARCHAR with functions. Use them for schemaless payloads that genuinely vary. Prefer a relational column when the shape is stable.

-- SQL Server
-- SQL Server stores JSON as ordinary Unicode text
CREATE TABLE events (id INT IDENTITY PRIMARY KEY, payload NVARCHAR(MAX));
INSERT INTO events(payload) VALUES (N'{"type":"click","x":10,"y":20}');

-- MySQL
-- MySQL validates JSON on insert
CREATE TABLE events (id BIGINT AUTO_INCREMENT PRIMARY KEY, payload JSON);
INSERT INTO events(payload) VALUES ('{"type":"click","x":10,"y":20}');

-- PostgreSQL
CREATE TABLE events (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, payload JSONB);
INSERT INTO events(payload) VALUES ('{"type":"click","x":10,"y":20}');

Three engines store the same JSON payload; PostgreSQL JSONB and MySQL JSON validate and index it. The N prefix marks Unicode in SQL Server.

15.2 Query inside JSON + output

SQL operators reach inside JSON to pull out fields without loading the whole document: the JSONB operators in PostgreSQL, JSON_EXTRACT and the arrow operator in MySQL, and JSON_VALUE and JSON_QUERY in SQL Server. You get SQL filtering and indexing power over flexible data. Query paths let you treat JSON fields like columns.

-- SQL Server: JSON_VALUE / OPENJSON
-- JSON_VALUE extracts a scalar by path
SELECT JSON_VALUE(payload, '$.type') AS type FROM events;
-- type
-- click

-- MySQL: ->> and JSON_EXTRACT
-- ->> returns the value as text from a path
SELECT payload->>'$.type' AS type FROM events;
-- +-------+
-- | type  |
-- +-------+
-- | click |
-- +-------+

-- PostgreSQL: ->> returns text, -> returns json/jsonb
SELECT payload->>'type' AS type FROM events;
--  type
-- -------
--  click

-- Index a JSON field:
-- PostgreSQL: CREATE INDEX ON events ((payload->>'type'));
-- MySQL:      generated column + index
-- a generated column gives MySQL a typed, indexable copy
ALTER TABLE events ADD COLUMN type VARCHAR(32)
  GENERATED ALWAYS AS (payload->>'$.type') STORED, ADD INDEX (type);

SQL reaches inside JSON to pull out the type field using arrow operators. The generated column shows how to index a JSON value for fast lookups.

Use JSON for genuinely schemaless or sparse data. If you always query a field, promote it to a real column with a type — you get constraints, indexes and clarity.

16 · Backup, Restore & Migration

16.1 Backups16.2 Restores16.3 Point-in-time recovery16.4 Schema migrations and cross-engine moves

Backups and restores are the difference between an incident and a disaster, and this chapter covers them across the three engines. Test your restore, automate the backup and keep an eye on point-in-time recovery. A backup you never restored is a backup you cannot trust.

16.1 Backups

A backup is a copy you can restore: full file backups with BACKUP DATABASE in SQL Server, mysqldump or binary snapshots in MySQL, and pg_dump or base backups with WAL archiving in PostgreSQL. Automate the schedule and then prove the restore works. Logical dumps are portable; file backups are faster to restore.

-- SQL Server
-- WITH INIT overwrites the existing backup file
BACKUP DATABASE shop TO DISK = 'C:\backups\shop.bak' WITH INIT;
-- Processed 1234 pages ... BACKUP DATABASE successfully processed.

-- MySQL
-- --single-transaction gives a consistent snapshot
mysqldump -u root -p --single-transaction shop > shop.sql
# mysqldump: [Warning] Using a password on the command line ... (avoid in scripts)

-- PostgreSQL
-- -Fc selects the compressed custom format
pg_dump -Fc shop > shop.dump        # custom format, compressed

Three backup styles: engine file backup, logical dump and compressed custom dump. --single-transaction keeps the MySQL dump consistent.

16.2 Restores

Restoring is the test of a backup and a routine in its own right, using RESTORE DATABASE in SQL Server, mysql or mysqlimport for dumps, and pg_restore or psql in PostgreSQL. Practice it into a scratch database on a schedule so recovery is a rehearsed procedure. A restore you can do quickly makes an incident survivable.

-- SQL Server
-- WITH REPLACE overwrites the existing database
RESTORE DATABASE shop FROM DISK = 'C:\backups\shop.bak' WITH REPLACE;

-- MySQL
-- pipes the SQL file back into the engine
mysql -u root -p shop < shop.sql

-- PostgreSQL
-- -d names the target database
pg_restore -d shop shop.dump

Each backup type has a matching restore command. RESTORE WITH REPLACE overwrites, the mysql CLI replays SQL, and pg_restore reads its own format.

16.3 Point-in-time recovery

Point-in-time recovery replays transaction logs or WAL to recover up to the moment before a mistake, so a full backup plus the archived log stream is required. Enable it with recovery model FULL and transaction log backups in SQL Server, binlog-based recovery in MySQL, and WAL archiving with pg_basebackup in PostgreSQL. It lets you rewind to just before the damaging statement.

Full backup + transaction-log/ WAL archives let you restore to a moment before a mistake. SQL Server uses the transaction log (FULL recovery model); MySQL uses binlogs; PostgreSQL uses WAL archiving + recovery_target_time.

16.4 Schema migrations and cross-engine moves

Schema migrations version your schema like code through tools such as Flyway and Liquibase, applying numbered change files in order. Cross-engine moves export with mysqldump or pg_dump and import into the target after converting types. Planned migrations beat hand-editing production tables.

17 · Scaling & Architecture Patterns

17.1 Scaling the database17.2 Patterns that pay off17.3 Polyglot persistence

Scaling is a ladder: grow the server vertically, add replicas for reads, add caching, and shard last. These architecture patterns are the playbook experienced teams follow. Each rung adds capacity but also operational cost, so climb only as far as the workload requires.

17.1 Scaling the database

Scale vertically first by adding CPU and memory to the existing server, then add read replicas and caching layers, and treat sharding as the last resort. Each rung adds capacity but also operational cost and complexity. Measure utilisation and latency before climbing the ladder.

  • Vertical: more CPU/RAM/fast SSD — always first.
  • Read replicas: offload reporting and read-heavy traffic.
  • Caching: Redis/Memcached in front of hot reads.
  • CQRS: separate read models (often materialised) from writes.
  • Sharding: last resort for write scale.

17.2 Patterns that pay off

A shortlist of repeatable designs that pay off: replica routing for read scaling, materialised views for expensive aggregations, the outbox pattern for reliable events, soft delete instead of hard deletes, and optimistic locking with version columns. Steal them where they fit. Each solves a recurring problem without bespoke architecture.

PatternProblem it solves
Read replica routingReporting load starving transactions
Materialised viewsExpensive aggregates

Soft deleteAudit/history without losing rows
Optimistic concurrency (rowversion)Lost updates without long locks

17.3 Polyglot persistence

One engine can cover most needs, so add a specialist store only for a concrete requirement such as full-text search or analytics. Every extra system adds ops burden, licensing and consistency concerns. Choose a second store only when the primary engine is measurably the wrong tool for the job.

Relational engines handle most needs. Add a specialised store only for a real requirement: a document store for flexible schemas, a search engine (Elasticsearch) for relevance, a time-series DB for metrics, a graph DB for deep relationships. Each adds operational cost.

A.3 Rules of thumb

Six rules that carry most of the value: model first, index for queries, never use floating point for money, parameterise queries, apply least privilege, and scale in order. Follow these as defaults and deviate only with a measured reason. They capture the most reusable judgement from the whole guide.

  • Model first; normalise to 3NF, then denormalise on evidence.
  • Index for your queries; measure, don’t guess.
  • Money is DECIMAL/NUMERIC, never FLOAT.
  • Always parameterise queries — never concatenate user input.
  • Least privilege; backups you have actually restored.
  • Scale up, then out, then shard — in that order.
