1 ▸ Orientation · What Electron Is

1.1 Electron's anatomy: Chromium plus Node1.2 Main, renderer and preload processes1.3 Why the process split exists1.4 When Electron fits — and when it does not

Electron is the framework behind VS Code, Slack and Discord: a Chromium browser engine and a full Node.js runtime fused into one runtime, so one codebase produces a native desktop window with filesystem, network and OS access. This chapter establishes the process model you will live inside for the rest of the guide, and when the framework earns its cost.

1.1 Electron's anatomy: Chromium plus Node

An Electron app is literally two runtimes sharing one process tree. Knowing which runtime is answering a given call explains most of the framework's behaviour.

Two runtimes, one binary

The main process runs Node.js — the same V8-based runtime you use on a server — while each window runs a Chromium tab. Electron rebases its bundled Node against the exact V8 version Chromium ships, so you get one V8, not two. That matters because native modules (.node files) are compiled against the ABI of that V8; a mismatch is why modules break after an Electron upgrade. process.versions in the main process reports all four versions at once.

const { app } = require('electron');

app.whenReady().then(() => {
  console.log('Electron :', process.versions.electron);
  console.log('Chromium :', process.versions.chrome);
  console.log('Node     :', process.versions.node);
  console.log('V8       :', process.versions.v8);
});

The capabilities a browser tab cannot have

Because the main process is Node, it can read and write arbitrary files, bind sockets, spawn processes and call native operating-system APIs. These are the operations you never hand to page code: the renderer sees screens, the main process sees the machine. The classic first example is enumerating the machine the app is running on, which is unremarkable from Node and impossible from a browser.

const { app } = require('electron');
const os = require('os');

app.whenReady().then(() => {
  console.log('Platform :', process.platform);   // win32 | darwin | linux
  console.log('CPU cores:', os.cpus().length);
  console.log('userData :', app.getPath('userData'));
});

1.2 Main, renderer and preload processes

Electron draws a hard line between three worlds. Where a line of JavaScript runs decides which APIs it is allowed to touch, and the file that blurs that line — the preload script — is the most security-sensitive file you will write.

Three process kinds with different privileges

The main process is the entry script in package.json; it owns the app lifecycle and every window. Each BrowserWindow hosts a renderer process, which is a Chromium tab: full DOM, Canvas, WebGL and fetch, but no Node. The preload script runs before the page's own scripts in an isolated world, and is the only renderer-side code that may require() a narrow slice of Electron. process.type tells a shared file where it is running, which is how one utility module can serve all three worlds.

// Run this same file from main, a preload and a page script.
if (process.type === 'browser') {
  console.log('Main process: full Node.js here.');
} else if (process.type === 'renderer') {
  console.log('Renderer: a web page without Node.');
}

The preload bridge

With contextIsolation: true, the preload and the page run in two separate JavaScript worlds that share a DOM but do not share globals. The preload's job is to decide exactly what the page may reach — typically nothing more than a handful of named functions. Exposing the ipcRenderer object itself is the classic mistake; expose capabilities, never transport.

// preload.js — runs before the page in an isolated world.
const { contextBridge } = require('electron');

contextBridge.exposeInMainWorld('env', {
  platform: process.platform,
});

1.3 Why the process split exists

The split is not an accident of history; it is the framework's two design bets: untrusted content must never reach Node, and no single renderer's crash should take the application down.

Untrusted content stays away from Node

A web page is a hostile environment by default — third-party scripts, injected ads, one bad innerHTML. If a renderer had Node, one cross-site scripting bug becomes remote code execution on the user's machine. That is why nodeIntegration has defaulted to false since Electron 5, and why the hardened configuration keeps the renderer sandboxed, with the preload as the only Node-touching entry point.

const { BrowserWindow } = require('electron');
const path = require('path');

const win = new BrowserWindow({
  webPreferences: {
    contextIsolation: true,   // separate the page world from the preload world
    nodeIntegration: false,   // page scripts must never see require()
    sandbox: true,            // renderer runs as a sandboxed Chromium tab
    preload: path.join(__dirname, 'preload.js'),
  },
});

A crashed tab should not take the app down

Because each window is a separate OS process, a renderer that dies — the page ran out of memory, threw somewhere unrecoverable, or was killed by the OS — takes only its tab with it. The main process and every other window survive. The render-process-gone event on app is how you learn about the death and respond by reloading the window or logging diagnostics, rather than losing the whole service.

const { app } = require('electron');

app.on('render-process-gone', (event, webContents, details) => {
  if (details.reason !== 'clean-exit') {
    console.error(`renderer gone: ${details.reason} (code ${details.exitCode})`);
  }
});

1.4 When Electron fits — and when it does not

Electron is a desktop-UI framework with service features, not a service runtime wearing a costume. Matching the tool to the job saves you the two most expensive failure modes: a 200 MB tray icon, and a headless daemon holding a full Chromium in memory for no reason.

The right tool for a web-based desktop UI

Choose Electron when the value is a rich, interactive desktop interface built by people who already know web tech, deployed to Windows, macOS and Linux from one codebase. Code editors, chat clients, DevOps dashboards and internal admin consoles are its home turf: the UI needs the whole web platform, and the app needs filesystem, child_process and native dialogs around it. Before you commit, check what a minimal build actually weighs on disk — the embedded Chromium is not optional, and pretending otherwise only delays the discovery.

# Inspect what a build really ships before calling it small.
du -sh dist/
du -sh node_modules/

Where it strains

Skip Electron for tray-only utilities, pure background daemons and anything whose cardinal virtue is a 10 MB footprint — a windowless main process still boots Node, and any window you create boots a tab. For headless services, plain Node with node-windows or a systemd unit is a fraction of the size. If you do run Electron in a service-ish mode, make the window creation conditional so a daemon start never materialises a hidden browser.

const { app } = require('electron');

// A service-flavoured main: no window unless the user asks for one.
app.whenReady().then(() => {
  if (process.env.SERVICE_MODE === '1') {
    startBackgroundJob();      // headless: no Chromium tab at all
  } else {
    createMainWindow();
  }
});
A windowless Electron process is still around 80–150 MB on disk and boots Node plus part of Chromium. If the deployment target is a true background service — Windows Service or systemd unit with no UI ever — writing it in plain Node typically halves the memory and removes the Chromium attack surface entirely.

2 ▸ Project Setup and App Lifecycle

2.1 Scaffolding with npm2.2 package.json main and starting Electron2.3 The ready lifecycle2.4 Window management with BrowserWindow2.5 Quit and activate conventions

An Electron project is an npm project whose main field points at a Node script. This chapter walks the scaffold, the app lifecycle events, and the window ownership discipline that stops a healthy-looking app from quitting or leaking silently.

2.1 Scaffolding with npm

Electron ships as a normal dev-dependency, and the entire build pipeline hangs off npm scripts — no bespoke toolchain required.

A bare scaffold in four commands

Install electron as a dev dependency: the npm package is a launcher that downloads the platform's prebuilt Chromium+Node binary, so the runtime is not something you require at runtime — it is the runtime. The download comes from GitHub releases by default; teams behind firewalls set the ELECTRON_MIRROR environment variable to an internal mirror. npx electron --version confirms both the install and the binary download completed.

mkdir electron-service-app
cd electron-service-app
npm init -y
npm install --save-dev electron
npx electron --version

The minimal file layout

Three files carry the whole application: main.js (main process), preload.js (the bridge), and a renderer directory that holds the window UI. Keep the renderer in its own folder from day one — a file:// window resolves relative asset paths from the HTML file's own directory, and a flat root gets confusing the moment you add CSS, images or a second page.

electron-service-app/
├── package.json
├── main.js
├── preload.js
└── renderer/
    ├── index.html
    └── renderer.js

2.2 package.json main and starting Electron

The main field names the entry script, and the launch flags you reach for during development are worth knowing before your first bug hunt.

The main field names the entry script

Running electron . makes the CLI read the current directory's package.json, take the main path, and execute it as the main process. If main is missing or mistyped the app opens with a default window and an error in the console — the framework happily shows you a shell even though your code never ran. Put start in scripts so contributors — and CI — never have to remember the incantation.

{
  "name": "electron-service-app",
  "version": "1.0.0",
  "description": "A background service with a control window",
  "main": "main.js",
  "scripts": {
    "start": "electron .",
    "dev": "electron . --inspect=5858"
  }
}

Flags you will use in practice

Three flags pay for themselves quickly: --no-sandbox for Linux CI and root environments where the Chromium sandbox cannot start (development only — never shipped); --inspect=5858 to attach the Chrome DevTools Protocol to the main process, which otherwise has no console you can open; and ELECTRON_ENABLE_LOGGING=1 to surface Chromium's own logging on stderr, which is where a white window's real error message is hiding.

npm start                        # runs: electron .
npx electron . --no-sandbox      # some Linux CI and root environments need this
ELECTRON_ENABLE_LOGGING=1 npm start

2.3 The ready lifecycle

The app object is a state machine, and ready is the gate: anything that touches windows, menus, trays or the OS must wait for it.

The boot order

At launch the framework finishes its own bootstrap — loading Node, starting the browser process — and only then fires ready. Creating a BrowserWindow before ready throws on some platforms and misbehaves silently on others, so every guide's canonical shape is the same: app.whenReady().then(createWindow). On macOS, will-finish-launching fires earlier and is the right place to register Apple Event handlers, but window creation still waits for ready.

const { app, BrowserWindow } = require('electron');

let mainWindow = null;
app.whenReady().then(() => {
  mainWindow = new BrowserWindow({ width: 900, height: 640 });
  mainWindow.loadFile('renderer/index.html');
});

whenReady returns a promise

You are not forced into callbacks: app.whenReady() returns a Promise that resolves exactly once, so it is safe to await from an async bootstrap. The pattern earns its keep in a service app where startup must load configuration, open a database or bind a port before the first window paints — a sequence of awaits reads in order and fails loudly on the first rejection.

const { app, BrowserWindow } = require('electron');

async function bootstrap() {
  await app.whenReady();
  const win = new BrowserWindow({ show: false });
  await win.loadFile('renderer/index.html');
  win.show();
}

bootstrap();
Never create a BrowserWindow at module scope. The top of main.js runs before ready, and a window created there races the browser process bootstrap on every platform.

2.4 Window management with BrowserWindow

A BrowserWindow is a real, resizable OS window backed by a Chromium tab. How you create it and hold onto it decides whether the app flashes white at startup or silently leaks windows.

Creating and painting a window

Two options remove the classic white flash: show: false plus a backgroundColor, then reveal in ready-to-show. The window is fully constructed at that point — the page has rendered its first frame — so users see content, not a blank rectangle. Loading always follows creation, and either loadFile for packaged local content or loadURL for a dev server.

const { BrowserWindow } = require('electron');
const path = require('path');

const win = new BrowserWindow({
  width: 1024,
  height: 700,
  show: false,
  backgroundColor: '#021336',
  webPreferences: {
    preload: path.join(__dirname, 'preload.js'),
  },
});

win.once('ready-to-show', () => win.show());
win.loadFile('renderer/index.html');

Keep a reference, drop it on close

JavaScript cannot garbage-collect an object it can still reach, and a closed window you never null out keeps the renderer process alive without any visible window — a classic leak in an app that opens and closes many windows. Hold the window in a module-level variable and assign null in closed. Note that closed fires only after the window is gone, while close fires before, which is where you veto or persist.

let mainWindow = null;

function createMainWindow() {
  mainWindow = new BrowserWindow({ width: 900, height: 640 });
  mainWindow.loadFile('renderer/index.html');
  mainWindow.on('closed', () => {
    mainWindow = null;          // release so GC can collect the window
  });
}

2.5 Quit and activate conventions

Electron apps must treat "the app is done" differently on macOS than elsewhere. Get this wrong and your app either refuses to die on Windows or becomes unopenable on macOS.

The macOS conventions

On Windows and Linux, closing the last window should quit the app; on macOS, convention says the app keeps running with no windows, and clicking the dock icon recreates one. The canonical pair is window-all-closed (quit unless darwin) plus activate (recreate a window if none exists). The activate handler matters because macOS fires it on every dock click, not just the first.

const { app, BrowserWindow } = require('electron');

app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit();
});

app.on('activate', () => {
  if (BrowserWindow.getAllWindows().length === 0) {
    createMainWindow();
  }
});

The quit order, and vetoing it

Quitting is a three-stage event: before-quit → will-quit → quit. Calling event.preventDefault() in before-quit cancels the quit for that pass — the classic use is flushing state or confirming an unsaved job before actually leaving — and a later app.quit() re-enters the flow. Guard the re-entry with a flag or your save logic runs twice.

let stateSaved = false;

app.on('before-quit', (event) => {
  if (!stateSaved) {
    event.preventDefault();               // cancel this quit pass
    saveState().then(() => {
      stateSaved = true;
      app.quit();                         // re-enter the quit flow
    });
  }
});

3 ▸ The Main Process in Depth

3.1 BrowserWindow options in detail3.2 Loading URLs versus local files3.3 Window and app lifecycle events3.4 Native dialogs and menus3.5 Spawning child processes

Everything a service app does that a web page cannot — native dialogs, application menus, spawning jobs, owning windows — happens in the main process. This chapter goes beyond the ten-line template and covers the options, events and process-spawning APIs you will actually reach for.

3.1 BrowserWindow options in detail

The BrowserWindow constructor takes one options object, and the fifty-odd keys split naturally into geometry, chrome and rendering behaviour.

Geometry and window chrome

Size, position and chrome are plain numbers and booleans, but two deserve attention. autoHideMenuBar: true hides the default application menu until Alt is pressed — normally what a service UI wants — and titleBarStyle: 'hiddenInset' on macOS keeps the traffic lights with a decorated title bar. Remember minWidth/minHeight or a user can shrink a control panel into unusability; remember to persist getBounds() on resize rather than hard-coding x/y.

const win = new BrowserWindow({
  width: 1024,
  height: 700,
  minWidth: 640,
  minHeight: 480,
  x: 80,
  y: 80,
  resizable: true,
  maximizable: true,
  fullscreenable: false,
  autoHideMenuBar: true,
});

Show timing and painting

The paint pipeline is: construct → load → first paint → ready-to-show → show(). Two knobs control the visible result. show: false keeps the window off screen until it has something to paint, and backgroundColor paints behind the page while it parses, so a dark app does not flash white even before the first frame. Together they eliminate the single most reported "ugly" behaviour in Electron apps.

const win = new BrowserWindow({
  show: false,
  backgroundColor: '#021336',
});

win.once('ready-to-show', () => {
  win.show();
  win.focus();
});
Set backgroundColor to match the page's own background colour. On a slow disk the window is visible for the full parse time, and a mismatched colour jars for the whole load.

3.2 Loading URLs versus local files

A window's content comes from either the packaged file:// tree or an HTTP URL. Each has its own rules, and the difference is where most "why is my page broken" mysteries begin.

loadFile and the file:// protocol

loadFile resolves relative to the app root, not the process working directory — a window launched from dist/ vs src/ must not load different files. Always build the path with path.join(__dirname, ...). Under file://, fetch() to other files works in modern Electron, but module scripts and some APIs behave differently than over HTTP; a common shim is loading the same UI from a dev server during development and from disk in production.

const path = require('path');

// Local content: resolve against __dirname, never the cwd.
mainWindow.loadFile(path.join(__dirname, 'renderer', 'index.html'));

// During development a bundler serves the same UI over HTTP:
// mainWindow.loadURL('http://localhost:5173');

loadURL and keeping navigation on a leash

Loading a remote URL is fine when the URL is yours; the danger is where the window can go afterwards. A link, a redirect or a compromised page can navigate the whole window to an attacker's site — complete with your preload bridge attached. Two handlers contain it: will-navigate vetoes main-frame navigations away from your origin, and setWindowOpenHandler intercepts every window.open and target="_blank", where the sane default is denying the popup and handing the URL to the real browser.

const { shell } = require('electron');

mainWindow.webContents.on('will-navigate', (event, url) => {
  if (!url.startsWith('https://app.example.com/')) {
    event.preventDefault();
  }
});

mainWindow.webContents.setWindowOpenHandler(({ url }) => {
  if (url.startsWith('https://')) shell.openExternal(url);
  return { action: 'deny' };
});

3.3 Window and app lifecycle events

Event names on BrowserWindow and app cover the two senses of "lifecycle": the visible life of one window, and the orchestrated life of the whole process.

Window-granular events

Focus, blur, resize, maximize and close are the events a service UI actually listens to: pause heavy work on blur, resume on focus, persist bounds on resize, update menu state on maximize. close fires before destruction and may be prevented; closed fires after, when it is too late to veto and the window object is dead. Most handlers are one-liners that call into your own state helpers.

mainWindow.on('focus', () => { pauseHeavyWork(false); });
mainWindow.on('blur', () => { pauseHeavyWork(true); });
mainWindow.on('resize', () => persistBounds(mainWindow.getBounds()));
mainWindow.on('maximize', () => badge('maximised'));
mainWindow.on('closed', () => { mainWindow = null; });

App-level orchestration events

Alongside the quit trio from chapter 2, app fires browser-window-created for every new window — useful for applying a common policy (same preload, same minimum size) in one place — and web-contents-created for every web contents instance including iframes. A service app that must log its whole life can hook all of them; the ordering is deterministic, which makes the log a reliable chronology.

app.on('browser-window-created', (event, win) => {
  console.log(`window ${win.id} created`);
});
app.on('before-quit', () => console.log('before-quit'));
app.on('will-quit', () => console.log('will-quit'));
app.on('quit', (event, exitCode) => console.log(`quit ${exitCode}`));

3.4 Native dialogs and menus

Dialogs and menus are two main-process APIs that give a window genuine operating-system presence: a real file picker and a real application menu bar.

The native dialog API

dialog.showOpenDialog returns a Promise resolving to { canceled, filePaths } and always checks canceled before touching the paths. properties is where the behaviour is set — 'openFile', 'multiSelections', 'openDirectory', 'createDirectory' — and if you pass a window as the first argument the dialog becomes modal to it, which is what prevents the user from clicking the same window twice. The synchronous variants (showMessageBoxSync) exist for the moments you cannot await, such as the middle of a quit.

const { dialog } = require('electron');

async function pickLog() {
  const result = await dialog.showOpenDialog({
    title: 'Choose a log file',
    properties: ['openFile', 'multiSelections'],
    filters: [{ name: 'Logs', extensions: ['log', 'txt'] }],
  });
  if (!result.canceled) return result.filePaths;
  return [];
}

Building an application menu from a template

Menu.buildFromTemplate takes a declarative array and produces the native menu. Roles (role: 'quit', role: 'copy', …) are the correct way to get standard behaviour — they bind the right accelerator for each platform and exist on macOS only for their Apple menu. Build one template and call Menu.setApplicationMenu once; on Linux the menu is per-window and can be set from browser-window-created.

const { app, Menu } = require('electron');

const template = [
  { label: app.name, submenu: [
      { role: 'about' }, { type: 'separator' }, { role: 'quit' },
  ]},
  { label: 'Edit', submenu: [
      { role: 'undo' }, { role: 'redo' }, { type: 'separator' },
      { role: 'cut' }, { role: 'copy' }, { role: 'paste' },
  ]},
];

Menu.setApplicationMenu(Menu.buildFromTemplate(template));
Not every role exists on every platform. role: 'about' is macOS-only; on Windows and Linux use a click handler with dialog.showMessageBox. Test the built menu on all three targets, or a standard action silently vanishes.

3.5 Spawning child processes

The main process is the only place a service app should spawn external programs. Everything you need is the child_process module you already know from Node, with two Electron-specific habits bolted on.

spawn with detachment

Long-running jobs — transcoders, backups, report generators — want detached: true (the child becomes its own process group leader and outlives the app if it crashes) and stdio: 'ignore' unless you are capturing output. The pairing to remember is detached with unref(): without unref() the parent's event loop stays alive waiting for the child, which is exactly what a service app that should exit quietly must not do.

const { spawn } = require('child_process');

const job = spawn('ffmpeg', ['-i', 'in.mp4', '-c:v', 'libx264', 'out.mp4'], {
  detached: true,
  stdio: 'ignore',
});
job.unref();   // do not keep the app alive just for this child

Streaming output back to a renderer

A job's stdout is a stream, and the renderer wants a live view of it. The clean pattern is ipcMain.handle around the spawn that resolves with the exit code, plus event.sender.send for each stdout chunk so the control panel updates in real time. Keep the stream wiring inside the Promise — the command's error event and its close event are distinct, and only error covers "the binary does not exist".

const { ipcMain } = require('electron');
const { spawn } = require('child_process');

ipcMain.handle('script:run', (event, scriptPath) => {
  return new Promise((resolve, reject) => {
    const child = spawn('node', [scriptPath]);
    child.stdout.on('data', (chunk) => {
      event.sender.send('script:output', chunk.toString());
    });
    child.on('close', (code) => resolve({ code }));
    child.on('error', reject);
  });
});

4 ▸ IPC and Context Isolation

4.1 Channels: ipcMain and ipcRenderer4.2 Request–response with invoke and handle4.3 Preload scripts and contextBridge4.4 contextIsolation and nodeIntegration4.5 The security checklist

Everything a window knows about the machine arrives over IPC — the framework's message bus between renderer and main. This chapter covers the two messaging styles, the preload bridge that gates them, and the security checklist that keeps a web vulnerability from becoming a code-execution one.

4.1 Channels: ipcMain and ipcRenderer

IPC in Electron is a pair of event emitters joined by a channel name. Getting the two styles right — fire-and-forget versus request–response — determines how readable your wiring is.

Fire-and-forget messages

ipcRenderer.send('channel', payload) ships a message to the main process, where ipcMain.on('channel', handler) receives it. The payload is structured-clone serialised, so plain objects, arrays and dates travel fine but functions do not. Fire-and-forget is right for logging, progress ticks and anything where no answer is needed; the moment you want a return value you switch to invoke (section 4.2). In production the renderer never imports electron at all — it calls a bridge function (section 4.3) — shown directly here only to make the transport visible.

// main.js
const { ipcMain } = require('electron');

ipcMain.on('service:log', (event, payload) => {
  console.log(`renderer said: ${JSON.stringify(payload)}`);
});

// page script — in practice reached through the preload bridge
const { ipcRenderer } = require('electron');

ipcRenderer.send('service:log', { text: 'hello from the window' });

Channel hygiene

Channel names are global strings, and a collision silently routes messages to the wrong handler. Adopt a namespaced convention — service:log, store:read, job:run — and keep every channel in one shared constant module so both sides cannot drift. For long-lived listeners, ipcMain keeps the receiving function referenced forever, so remove listeners you no longer need rather than piling handlers on each event.

const onLog = (event, payload) => {
  console.log('log:', payload);
};

ipcMain.on('service:log', onLog);

app.on('will-quit', () => {
  ipcMain.removeListener('service:log', onLog);
});

4.2 Request–response with invoke and handle

When the renderer needs an answer — a file's contents, a computed value, success or failure — invoke/handle turns IPC into a promise call.

Promises across the boundary

ipcMain.handle('channel', asyncFn) registers a handler whose resolved value is returned to the renderer's ipcRenderer.invoke('channel', …) as a promise resolution. The handler and the call are still message-passing under the hood, but to both sides it reads like a normal asynchronous function call — which is exactly why it is the dominant pattern in real apps. It is safe to have the renderer await it; the main-process handler runs on the main thread, so keep it off heavy synchronous work.

// main.js
const { app, ipcMain } = require('electron');
const fs = require('fs/promises');
const path = require('path');

ipcMain.handle('store:read', async (event, key) => {
  const file = path.join(app.getPath('userData'), `${key}.json`);
  const raw = await fs.readFile(file, 'utf8');
  return JSON.parse(raw);
});

// renderer (main world), through the preload bridge:
const settings = await window.api.readStored('settings');
console.log(settings.intervalMs);

Errors cross the bridge sanitised

A thrown Error in an ipcMain.handle rejection reaches the renderer as an "Error invoking remote method" string — Electron strips the stack trace and only the message survives, serialised. Two consequences: never rely on a renderer seeing a full stack (log the real error in main with console.error), and wrap failures in messages that a user-facing panel can actually display. A raw Error: ENOENT is engineering data; could not write "settings" is a sentence.

ipcMain.handle('store:write', async (event, key, value) => {
  try {
    const file = path.join(app.getPath('userData'), `${key}.json`);
    await fs.writeFile(file, JSON.stringify(value));
    return { ok: true };
  } catch (error) {
    // Only this message crosses the bridge; the stack stays in main.
    throw new Error(`could not write "${key}"`);
  }
});

4.3 Preload scripts and contextBridge

The preload runs before the page in an isolated world, and contextBridge is how you hand the page a controlled API — this is the hinge between "renderer is a web page" and "renderer is a privileged shell".

exposeInMainWorld

contextBridge.exposeInMainWorld('api', factory) adds an object to the page's window whose values are snapshot copies — functions are proxied, everything else is frozen. The object should wrap ipcRenderer calls behind intention-named functions and never expose the ipcRenderer object itself, which would let page code send arbitrary channels. For subscriptions, return an unsubscribe function from the exposed API so page code can clean up after itself without touching removeListener.

// preload.js
const { contextBridge, ipcRenderer } = require('electron');

contextBridge.exposeInMainWorld('api', {
  readStored: (key) => ipcRenderer.invoke('store:read', key),
  onJobState: (callback) => {
    const listener = (event, state) => callback(state);
    ipcRenderer.on('job:state', listener);
    return () => ipcRenderer.removeListener('job:state', listener);
  },
});

Using the bridge from page scripts

On the page side the bridge is just a global: window.api.readStored('settings'). The API shape is yours to design — keep it small, promise-returning and JSON-shaped, and you can swap the whole main-process implementation without ever touching the UI. The bridge is also the seam where you can unit-test: a fake window.api with the same shape drives the renderer in isolation.

// renderer.js — the page world, which has no require().
const settings = await window.api.readStored('settings');

const unsubscribe = window.api.onJobState((state) => {
  document.querySelector('#job-state').textContent = state;
});

4.4 contextIsolation and nodeIntegration

These two webPreferences flags are the entire security posture of a renderer. Their defaults are sane only if you never flipped them off to make an old tutorial work.

Two flags, four combinations

nodeIntegration: false removes require, process and friends from the page's world; contextIsolation: true keeps the preload and page worlds separate even though they share a DOM. The two together are the modern default and the only combination you should ship. The dangerous pair is nodeIntegration: true — any XSS in your UI, from a bad innerHTML to an injected ad, becomes arbitrary code execution on the user's machine. There is no mitigation that makes that pairing safe.

const win = new BrowserWindow({
  webPreferences: {
    nodeIntegration: false,   // page scripts must never see require()
    contextIsolation: true,   // preload world and page world stay separate
    sandbox: true,            // renderer without Node, worker or GUI access
    preload: path.join(__dirname, 'preload.js'),
  },
});

What sandbox: true changes

With sandbox: true the renderer runs as a true Chromium sandbox (no Node, no process, no GUI), and the preload script loses access to Node APIs beyond a small allow-list: the electron modules (contextBridge, ipcRenderer), and a handful of Node builtins like events and timers. IPC still works, which covers nearly every real preload. If a preload truly needs fs or path, that is the signal the logic belongs in the main process behind an IPC channel.

// preload.js with sandbox: true — only a limited require() exists.
const { contextBridge, ipcRenderer } = require('electron');

contextBridge.exposeInMainWorld('api', {
  ping: () => ipcRenderer.invoke('svc:ping'),
});
Never set nodeIntegration: true for a window that loads remote or user-provided content. The browser process already treats every renderer as hostile; re-arming Node hands that hostility the keys to the machine.

4.5 The security checklist

The concerns above collapse into a short audit list. Run it against every window factory and every IPC handler before you package anything.

The window factory you audit

Route every window through one factory so the hardened defaults apply to windows you forgot about. The checklist: contextIsolation: true; nodeIntegration: false; sandbox: true; webSecurity: true (never disable it for CORS convenience); allowRunningInsecureContent: false; a preload that exposes only named functions; and navigation/window-open handlers from section 3.2 on every webContents. Centralising means the audit is one function, not a scavenger hunt.

function createHardenedWindow(options = {}) {
  const win = new BrowserWindow({
    ...options,
    webPreferences: {
      nodeIntegration: false,
      contextIsolation: true,
      sandbox: true,
      webSecurity: true,
      allowRunningInsecureContent: false,
      preload: path.join(__dirname, 'preload.js'),
    },
  });
  return win;
}

Validate who is talking to you

Any frame in the window can send on a channel — including a compromised iframe. event.senderFrame.url tells you the actual origin of the message; a handler that accepts a channel from any URL at all is a trust decision you did not mean to make. Gate privileged channels behind an allow-list of the frames you own, and log rejections: a blocked sender at 3 a.m. is far kinder to debug than a mystery backdoor.

const APP_ORIGIN = 'https://app.example.com/';

ipcMain.on('admin:deploy', (event, payload) => {
  const url = event.senderFrame.url;
  const allowed = url.startsWith('file://') || url.startsWith(APP_ORIGIN);
  if (!allowed) {
    console.warn(`blocked IPC from ${url}`);
    return;
  }
  runDeploy(payload);
});
Treat IPC like a public HTTP API: every channel is a route, every handler validates its payload shape before trusting it, and privileged routes check the caller. The disciplines you already know from server code are the right mental model.

5 ▸ The Renderer · Building the Control UI

5.1 The control UI from plain web tech5.2 Constraints of the sandboxed renderer5.3 Remote content at arm's length5.4 Opening external links safely5.5 Desktop notifications

The renderer is a full web page with a job: be the readable face of the service. It builds from plain HTML, CSS and JavaScript, constrained to the web platform, and uses the bridge (chapter 4) for everything privileged. This chapter covers the UI itself, remote-content discipline, external links and notifications.

5.1 The control UI from plain web tech

No framework required — a service control panel is often fewer than a hundred lines of HTML, CSS and vanilla JS.

A minimal index.html

The page is ordinary HTML with one addition that is easy to forget: a Content-Security-Policy meta tag. On file:// there is no server to send headers, so the meta tag is the only way the renderer gets a policy at all. Start with default-src 'self' — it blocks remote scripts immediately — and add back exactly what you need. Everything else in this file is unremarkable web work.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta http-equiv="Content-Security-Policy"
        content="default-src 'self'; style-src 'self' 'unsafe-inline'">
  <title>Service Control</title>
</head>
<body>
  <h1>Service Control</h1>
  <button id="start">Start job</button>
  <pre id="status">idle</pre>
  <script src="renderer.js"></script>
</body>
</html>

CSP rules that matter offline

Two policy details bite most Electron renderers. 'unsafe-inline' is frequently unavoidable for styles but should stay off script-src — move handlers out of attributes into addEventListener. And connect-src governs fetch/WebSocket; a renderer that talks to a local agent over http://127.0.0.1 must list that origin explicitly or every request is silently blocked. Read the warning in the console — Chromium prints the exact directive that rejected the request.

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self';
               connect-src http://127.0.0.1:4100;
               style-src 'self' 'unsafe-inline'">

5.2 Constraints of the sandboxed renderer

The renderer is the web platform, full stop — which is liberating or frustrating depending on what you try to do.

The web platform only

Everything a modern browser page has — DOM, fetch, Canvas, WebSockets, the Notification API, service workers — works. Everything Node has does not: no require, no process, no fs. The correct response to "I want to read that file in the renderer" is never re-enabling Node; it is a bridge function. Feature-detect with in checks exactly as you would in a browser; the window you get half-way through feature detection is the honest one.

// The sandboxed renderer exposes the web platform only.
if ('Notification' in window) console.log('notifications available');
if (!('require' in window)) console.log('no Node: as designed');

// This would throw — the page has no require().
// const fs = require('fs');

Route privileged work through the bridge

The shape of a well-behaved renderer is: UI reads/writes state via window.api functions, and everything else is presentation. Because the bridge returns promises, the page code stays async and readable, and the same UI can run against a mock window.api in a browser during development. The main process holds the actual logic, and the renderer never learns where files live or which port the agent binds.

const result = await window.api.readStored('job');
if (result) {
  renderJobCard(result);
} else {
  renderEmptyState();
}

5.3 Remote content at arm's length

A renderer that can wander the internet is a renderer that can be turned against you. The rule: your window may load your content, and everything else ends up in the system browser.

Navigation and window.open handling, app-wide

Instead of wiring every window, attach the handlers once in web-contents-created so they apply to windows and iframes alike. setWindowOpenHandler answers every window.open and target="_blank" — return { action: 'deny' } and the popup never exists — and will-navigate vetoes main-frame navigations that are not already the current URL (a redirect or a link). Both check the URL scheme before touching shell.

const { app, shell } = require('electron');

app.on('web-contents-created', (event, contents) => {
  contents.setWindowOpenHandler(({ url }) => {
    if (/^https:\/\//.test(url)) shell.openExternal(url);
    return { action: 'deny' };
  });

  contents.on('will-navigate', (event, url) => {
    if (url !== contents.getURL()) event.preventDefault();
  });
});

Sandboxing embedded content

If a feature genuinely needs third-party content inside the window — a widget, a dashboard iframe — the iframe sandbox attribute is the leather leash: without allow-scripts the frame's scripts do not run, and without allow-same-origin it cannot read the parent's DOM. The two flags together are the maximal trust next to no trust at all, so the pair should never appear together for content you do not fully control.

<iframe src="https://stats.example.com/dashboard"
        sandbox="allow-scripts allow-same-origin"></iframe>

5.4 Opening external links safely

A service UI inevitably shows links — documentation, dashboards, your pricing page. Opening them in the user's real browser is the correct behaviour; doing it safely is a scheme check.

shell.openExternal behind an IPC handler

shell.openExternal(url) hands a URL to the operating system's default handler — which means, unguarded, it can hand file:///C:/...something.exe or a custom protocol to whatever registered for it. The handler must validate the scheme before calling out. An /^https?:\/\// test is the entire gate: it admits only what a browser would sensibly open and rejects file:, smb:, and any typosquatted protocol.

const { ipcMain, shell } = require('electron');

const SAFE = /^https?:\/\//;

ipcMain.handle('link:open', (event, rawUrl) => {
  if (!SAFE.test(rawUrl)) {
    throw new Error('only http(s) URLs may be opened');
  }
  return shell.openExternal(rawUrl);
});

The renderer side

In the page, mark external links with a class or data- attribute and intercept them. Prevent the default navigation — otherwise target-less links would replace your own window's content — then hand the href to the bridge and let validation happen in main. If the open fails (no default browser configured), reflecting the failure on the link itself beats a silent dead click.

document.querySelectorAll('a[data-external]').forEach((link) => {
  link.addEventListener('click', async (event) => {
    event.preventDefault();
    const opened = await window.api.openExternal(link.href);
    link.classList.toggle('failed', !opened);
  });
});
Never concatenate user input into a URL before openExternal. A value beginning with file:// or a scheme like ms-/itms- can launch arbitrary registered handlers; validate the completed string, not the user's contribution to it.

5.5 Desktop notifications

A service running in the background should be allowed to say "done" — and both the renderer and the main process can raise a native notification.

The HTML5 Notification API in the renderer

The renderer uses the standard browser API: check support, request permission (a user gesture like a settings toggle is the honest way, not on load), then construct new Notification(title, { body }). Electron routes these to the operating system's notification centre. The permission state persists per origin — here, your file:// or app:// origin — so reflect it in the UI after the first request.

async function notify(title, body) {
  if (!('Notification' in window)) return;

  if (Notification.permission === 'default') {
    const choice = await Notification.requestPermission();
    if (choice !== 'granted') return;
  }
  if (Notification.permission === 'granted') {
    new Notification(title, { body });
  }
}

Notifications from the main process

Background jobs finish in the main process, so the main process frequently raises the notification itself. Electron's Notification class works there too; check Notification.isSupported() first (some Linux desktops lack a notification daemon), and on Windows call app.setAppUserModelId once — without a matching AppUserModelID, Windows silently drops notifications from your app.

const { app, Notification } = require('electron');

app.setAppUserModelId('com.example.service-app');

if (Notification.isSupported()) {
  new Notification({ title: 'Job finished', body: 'The export completed.' }).show();
}
Store the AppUserModelID in the same constant the packaging config uses — Windows matches notifications to installed apps by that exact string, and a mismatch means "works in dev, silent when packaged".

6 ▸ Services and System Integration

6.1 The tray6.2 Global shortcuts6.3 Autostart at login6.4 powerMonitor events6.5 The single-instance lock

Beyond the window, a service app owns a presence: a tray icon, global shortcuts, autostart, power-awareness and single-instance behaviour. These are the APIs that make the app feel like part of the operating system rather than a web page in a chrome.

6.1 The tray

A tray icon keeps the service reachable when every window is closed — the canonical "background with a control panel" pattern.

Tray icon and context menu

Construct a Tray with an image path (16×16 or 32×32 PNG; on Windows a multi-resolution .ico is better), then attach a context menu built from the same template API as the application menu. Keep the tray in a module-level variable — it is an object like any other, and garbage collection silently removes the icon while the app keeps running. role: 'quit' in the menu handles the exit path users expect.

const { Tray, Menu, nativeImage } = require('electron');

const tray = new Tray(nativeImage.createFromPath('assets/tray.png'));
tray.setToolTip('Service App');

tray.setContextMenu(Menu.buildFromTemplate([
  { label: 'Open Control', click: () => showMainWindow() },
  { type: 'separator' },
  { label: 'Paused', type: 'checkbox', checked: false },
  { type: 'separator' },
  { label: 'Quit', role: 'quit' },
]));
Store the Tray in a module-level variable. A tray that goes out of scope is garbage-collected and disappears from the system tray while the app runs on — the classic "my icon vanished" bug.

Click behaviour and live state

Left-click behaviour differs by platform: on Windows and Linux the click event fires, on macOS it only opens the menu — so if you support single-click-to-open, remember it will not work on mac. The tray should reflect live state: setToolTip for hover text, and rebuild or toggle menu items (the checkbox above) when the service pauses, resumes or faults. For macOS, use a template image (filename ending in Template) so the icon adapts to dark mode automatically.

tray.on('click', () => showMainWindow());

function updateTray(statusText) {
  tray.setToolTip(`Service App — ${statusText}`);
}

6.2 Global shortcuts

Global shortcuts trigger your app from anywhere on the desktop — a summon key for a service window deserves exactly that.

Registering a system-wide accelerator

globalShortcut.register(accelerator, callback) works system-wide, unlike in-window accelerators. Use CommandOrControl (not a hard-coded Ctrl or Cmd) so the same accelerator string is right on Windows/Linux and macOS. Registration returns false when the combination is taken by another application — check it, and offer a settings UI rather than silently failing. Call register only after ready: the module needs the browser process up.

const { globalShortcut } = require('electron');

app.whenReady().then(() => {
  const ok = globalShortcut.register('CommandOrControl+Alt+S', () => {
    toggleServiceWindow();
  });
  if (!ok) console.warn('shortcut taken by another app');
});

Releasing them on quit

A registered global shortcut stays registered until it is unregistered — the OS keeps dispensing those key presses to a process that may have forgotten about them. The clean habit is globalShortcut.unregisterAll() in will-quit; for finer control, unregister(accelerator) replaces one at a time (for example, when the user rebinds a key in settings).

const { globalShortcut } = require('electron');

app.on('will-quit', () => {
  globalShortcut.unregisterAll();
});

6.3 Autostart at login

A service that must be running when the machine boots needs to start with the session. Electron covers Windows and macOS natively; Linux is a config file you write.

setLoginItemSettings on Windows and macOS

app.setLoginItemSettings({ openAtLogin }) registers or deregisters the app as a login item, and openAsHidden on Windows starts it without a window — exactly right for a background service. Re-read getLoginItemSettings() to render the current state back into the settings UI; the OS owns the truth and the user may have toggled it elsewhere. There is no Linux equivalent API.

const { app } = require('electron');

function setAutostart(enabled) {
  if (process.platform === 'win32' || process.platform === 'darwin') {
    app.setLoginItemSettings({
      openAtLogin: enabled,
      openAsHidden: enabled,
      args: ['--hidden'],
    });
  }
}

Linux: an autostart desktop entry

On Linux, "start at login" means writing a freedesktop .desktop file into ~/.config/autostart/. The Exec line points at the installed binary (which your package manager installs to e.g. /opt/service-app/), and X-GNOME-Autostart-enabled=true makes it visible in the session's autostart preferences. Writing the file from the main process with fs is fine; keep it to one file, recreated on enable and removed on disable.

[Desktop Entry]
Type=Application
Name=Service App
Exec=/opt/service-app/service-app --hidden
X-GNOME-Autostart-enabled=true
On macOS, a login item registered before the app is in /Applications (running from a build output folder) can silently fail after the user moves the app. Offer the autostart toggle in a packaged build's settings screen, and call it after the app is installed to its final location.

6.4 powerMonitor events

Laptops sleep, lock and run from battery. A service that ignores the power state loses work on suspend and drains batteries on standby.

Suspend, resume and lock

powerMonitor emits suspend (about to sleep — flush pending work, nothing survives RAM loss), resume (cancel timers that assumed the machine never slept), lock-screen and unlock-screen (seal or restore secrets in the UI). The classic failure is a job timer set before suspend firing hours late on resume — arriving "on time" only from the sleeping machine's point of view.

const { powerMonitor } = require('electron');

powerMonitor.on('suspend', () => flushPendingWork());
powerMonitor.on('resume', () => rescheduleJobs());
powerMonitor.on('lock-screen', () => sealSession());
powerMonitor.on('unlock-screen', () => refreshWindows());

Battery- and idle-aware scheduling

Heavy maintenance — indexing, backups, telemetry replay — belongs on desktop power, not on battery. powerMonitor.isOnBatteryPower() plus getSystemIdleTime() (seconds since the last user input) give a two-condition gate: run the expensive pass only when plugged in and idle. Because the idleness signal changes continuously, poll with a modest interval rather than trying to subscribe to state changes.

setInterval(() => {
  const idleSeconds = powerMonitor.getSystemIdleTime();
  const onBattery = powerMonitor.isOnBatteryPower();

  if (idleSeconds > 300 && !onBattery) {
    runHeavyMaintenance();
  } else {
    delayHeavyMaintenance();
  }
}, 60_000);

6.5 The single-instance lock

A service app is, by definition, one app. The single-instance lock makes a second launch a request to the first.

requestSingleInstanceLock

app.requestSingleInstanceLock() returns true for the first process and false for every later one. The loser's correct move is app.quit() immediately — before creating anything — and the survivor listens for second-instance, which carries the second launch's argv and working directory. Called before ready, this is the oldest recommended ordering in the Electron docs, and for good reason.

const { app } = require('electron');

const gotLock = app.requestSingleInstanceLock();

if (!gotLock) {
  app.quit();
} else {
  app.on('second-instance', () => showMainWindow());
  app.whenReady().then(createMainWindow);
}

Acting on the second launch

The best single-instance behaviour turns the second launch into an intent: the user double-clicked a file or a URL and the running app should handle it. second-instance gives you argv, so find the file argument, queue it, and focus the existing window — restore it if minimised, focus if buried. A second launch that does nothing is a bug report; a second launch that opens your control panel is a feature.

app.on('second-instance', (event, argv) => {
  const fileArg = argv.find((arg) => arg.endsWith('.job'));
  if (fileArg) queueJob(fileArg);

  if (mainWindow && !mainWindow.isDestroyed()) {
    if (mainWindow.isMinimized()) mainWindow.restore();
    mainWindow.focus();
  }
});

7 ▸ Persistence, Packaging and Updates

7.1 Storing data in userData7.2 Packaging with electron-builder and Forge7.3 Updates and code signing7.4 Testing and debugging

A service app that cannot remember state, cannot be distributed and cannot update itself has not actually shipped. This chapter covers where data lives, how the app becomes an installer, how it updates, and how you debug all of it.

7.1 Storing data in userData

User data belongs in app.getPath('userData') — the one directory the OS guarantees your app may write, and that survives upgrades.

Where persistent files belong

app.getPath('userData') resolves to %APPDATA% on Windows, ~/Library/Application Support on macOS and ~/.config on Linux, joined with the app name — and the same call always returns the same place, so your code never guesses. The directory may not exist on a first run after a fresh install, so mkdir(..., { recursive: true }) before writing. Never write into the app's install directory: it is read-only when packaged (on macOS, the app bundle is sealed), and anything there is wiped by the next upgrade.

const { app } = require('electron');
const fs = require('fs/promises');
const path = require('path');

async function ensureDataDir() {
  const dir = app.getPath('userData');
  await fs.mkdir(dir, { recursive: true });
  return dir;
}

The electron-store pattern

The electron-store npm package formalises a pattern you can also write by hand: one JSON file per store, read once into memory, written through a temporary file and atomically renamed so a crash mid-write never leaves a truncated store. rename within the same volume is atomic, which is the whole trick. Debounce writes in a real app; the synchronous version below is the readable core.

const fs = require('fs');
const path = require('path');
const { app } = require('electron');

class Store {
  constructor(filename) {
    this.file = path.join(app.getPath('userData'), `${filename}.json`);
    try {
      this.data = JSON.parse(fs.readFileSync(this.file, 'utf8'));
    } catch {
      this.data = {};   // missing or corrupt file: start empty
    }
  }

  get(key, fallback) {
    return this.data[key] ?? fallback;
  }

  set(key, value) {
    this.data[key] = value;
    const tmp = `${this.file}.tmp`;
    fs.writeFileSync(tmp, JSON.stringify(this.data, null, 2));
    fs.renameSync(tmp, this.file);   // atomic replace
  }
}

7.2 Packaging with electron-builder and Forge

Distribution is where "it runs on my machine" becomes an installer for three platforms. Two mainstream tools do the heavy lifting; the choice is which workflow you prefer.

electron-builder targets and config

electron-builder reads a build section in package.json and produces installers: NSIS on Windows, DMG and ZIP on macOS, AppImage and DEB on Linux. The same files allow-list both trims the package (never ship tests or build/) and is an implicit audit of what leaves your machine. appId must be globally unique — it is the identity Windows and the updater use. Run with --publish never until you are genuinely ready to publish.

{
  "scripts": { "dist": "electron-builder --publish never" },
  "build": {
    "appId": "com.example.serviceapp",
    "productName": "Service App",
    "files": ["main.js", "preload.js", "renderer/**", "assets/**"],
    "win": { "target": "nsis" },
    "mac": { "target": ["dmg", "zip"], "category": "public.app-category.utilities" },
    "linux": { "target": ["AppImage", "deb"], "category": "Utility" }
  }
}

electron-forge as the alternative

electron-forge is the Electron team's integrated toolchain: electron-forge make runs packagers (called makers) for each target you declare. Its config lives in forge.config.js; note packagerConfig.asar: true — asar packs your source into a single archive (more on this below). Pick one tool per project; maintainers who swap mid-flight tend to lose their signing and update wiring.

module.exports = {
  packagerConfig: { asar: true },
  makers: [
    { name: '@electron-forge/maker-squirrel', config: {} },
    { name: '@electron-forge/maker-zip', platforms: ['darwin'] },
    { name: '@electron-forge/maker-deb', config: {} },
  ],
};
Package your source into app.asar by default. It is not encryption — the archive format is documented — but it keeps your main.js and renderer out of an unbundled folder tree where users trip over them, and it is the format both packagers expect.

7.3 Updates and code signing

Auto-update is the difference between "users run an old, buggy build forever" and "everyone converges on the fix". Signing makes that possible.

autoUpdater with a feed URL

autoUpdater polls a feed URL for a newer build; when one downloads you ask the user, then quitAndInstall(). The remote side matters as much as the code: the feed must be implemented against the same tool's update server (electron-builder's generic provider, or Forge's S3/GitHub releases), or checkForUpdates fails with a hard-to-read error. Check for updates after ready, not before, and never auto-restart over unsaved work without asking first.

const { app, autoUpdater, dialog } = require('electron');

autoUpdater.setFeedURL({ url: 'https://updates.example.com/ServiceApp' });

autoUpdater.on('update-downloaded', (event, releaseNotes, releaseName) => {
  const choice = dialog.showMessageBoxSync({
    type: 'info',
    buttons: ['Restart now', 'Later'],
    message: `Version ${releaseName} is ready to install.`,
  });
  if (choice === 0) autoUpdater.quitAndInstall();
});

app.whenReady().then(() => autoUpdater.checkForUpdates());

Updates require signed binaries

On macOS, an unsigned app triggers Gatekeeper and autoUpdate silently; on Windows, SmartScreen flags it. Signing configuration lives in the same build block: macOS needs a Developer ID application certificate plus hardenedRuntime: true and notarisation (Team ID in notarize), Windows a code-signing certificate. Keep the private key out of the repo — electron-builder reads the certificate path at build time and the password from the CSC_KEY_PASSWORD environment variable, not from source control.

{
  "build": {
    "mac": {
      "hardenedRuntime": true,
      "identity": "Developer ID Application: Example Ltd (ABCDE12345)",
      "notarize": { "teamId": "ABCDE12345" }
    },
    "win": {
      "certificateFile": "C:/certs/example.pfx"
    }
  }
}
An unsigned autoUpdater build is not merely untrusted — on macOS the update check quietly refuses to apply, which reads as "the updater is broken" in every bug report. Sign and notarise your first release; retrofitting it later means re-distributing everything you shipped before.

7.4 Testing and debugging

Electron's debugging split confuses newcomers more than any other feature: the renderer has DevTools, and the main process needs its own attach ritual.

DevTools and main-process logs

For the renderer, webContents.openDevTools() opens the normal Chromium DevTools. The main process has no DevTools button, so you either pass --inspect=5858 at launch and attach a Chrome DevTools frontend (chrome://inspect), or read its console.log on the terminal where the app started. --inspect-brk pauses on the first line of main — the reliable way to catch a startup crash before it exits. In packaged builds the terminal is gone, so write main-process logs to a file in userData.

# Attach the Chrome DevTools Protocol to the main process:
npx electron . --inspect=5858

# Pause on the very first line of main:
npx electron . --inspect-brk=5858

const { app } = require('electron');

app.whenReady().then(() => {
  const win = createMainWindow();
  if (!app.isPackaged) {
    win.webContents.openDevTools({ mode: 'detach' });
    win.webContents.on('console-message', (event, level, message) => {
      console.log(`[renderer] ${message}`);
    });
  }
});

Automated tests with Playwright

Playwright's Electron support launches your package.json entry as the target and drives windows with the same selectors API as browser tests — the cheapest way to verify "window opens, IPC answers, state renders". Keep fragile timing out of it: toContainText waits instead of sleeping, which is what makes the suite stable. The same tests run in CI on the Electron binary downloaded by the install step.

const { test, expect, _electron: electron } = require('@playwright/test');

test('control window loads and starts a job', async () => {
  const app = await electron.launch({ args: ['.'] });
  const win = await app.firstWindow();

  await win.click('#start');
  await expect(win.locator('#status')).toContainText('running');

  await app.close();
});
Extract main-process logic that deserves tests — the job runner, the store, the scheduling rules — into plain modules that do not require Electron, and unit-test those directly in Node. The Electron-specific layer then becomes a thin shell around logic you have already proven.
