The right mindset

The guide teaches a semantic-first philosophy: use HTML elements for what they mean, then restyle them with CSS. Structure and meaning come before appearance, so you pick heading, article or nav because they describe the content, not because of how they look. This mindset keeps your markup meaningful for every browser and assistive tool.

HTML is not about how a page looks — it is about what a page means. Choose the element that describes the content, and let CSS change its appearance. Browsers, screen readers and search engines all read this structure.

Keep the reference at developer.mozilla.org open beside this guide. This guide explains the why and the sequence; MDN is the exhaustive reference.

1 · Getting Started with HTML5

1.1 What HTML is1.2 The living standard1.3 Your first page1.4 How browsers render

Chapter one explains what HTML actually is, what the HTML5 living standard means in practice, and how to create, save and open your very first web page in a browser. You will see how a minimal document is written and rendered. By the end you have a working page you can build on.

HTML (HyperText Markup Language) is the markup that describes web content. HTML5 is the fifth revision and now simply the baseline of the living standard that browsers ship — it is the skeleton of every web page you have ever visited.

1.1 What HTML is

HTML is a markup language, not a programming language. It has no variables, no loops and no conditions; it describes what a piece of content is, and leaves every question of what should happen with it to CSS and JavaScript. That division is the whole design, and understanding it is what stops people writing JavaScript to solve problems HTML was already solving.

Three languages, three jobs

LanguageAnswersAnswers badly to
HTMLWhat this content is, and how it fits together structurallyHow it should look, or what happens on click
CSSHow it should look, at every size and in every reading modeWhat the content means, or what the state is
JavaScriptWhat happens, in response to an event or over timeDescribing structure, because the parser has to invent it

The practical consequence is that a change of meaning is an HTML change. If a heading stops being a heading because a designer wants it larger, the correct fix is CSS. If a button stops being a button because it needs to look like a link, the correct fix is still a button with different styles — because button comes with keyboard activation, focus behaviour and a role that a div does not.

Markup is tags, attributes and content

An element is written as an opening tag, its content, and a closing tag. The tag name is the element; the key-value pairs inside the opening tag are its attributes. Some elements have no content and no closing tag — the void elements — which is why <img src="a.png" alt="A"> is complete on its own while <p> is not.

<a href="/docs/guide.html" title="The HTML guide" class="nav" id="top-link">
  Read the guide</a>

<img src="logo.svg" alt="Amin360iT">        <!-- void: no closing tag -->
<br>                                       <!-- void as well -->

Attributes come in three flavours, and conflating them causes most of the confusion in a code review. A boolean attribute is present or absent — disabled, required, hidden — and writing disabled="false" does the opposite of what it looks like, because any value at all makes it true. A enumerated attribute accepts one of a fixed set of keywords, such as type="button". A free-form attribute takes text, such as alt.

Boolean attributes are a genuine trap. <input required="false"> is required, because the attribute's presence is the signal and the value is ignored. If you build markup in a template engine, emit the attribute only when it is true or omit it entirely — never render required="false".

Elements are categories, not just names

Every element belongs to one or more content categories, and the parser will not necessarily stop you from violating them. Flow content can go anywhere body content can go. Phrasing content goes inside a sentence. Embedded content includes images, audio, video and canvas. Interactive content is anything a reader can activate. These are the vocabulary behind the nesting rules, and they are why <p><div></div></p> does not produce what you wrote.

<p>Before the div</p>
<div>A div inside a paragraph is not allowed</div>
<p>After</p>

<!-- what the browser actually builds -->
<p>Before the div</p>
<p></p>
<div>A div inside a paragraph is not allowed</div>
<p>After</p>

The parser cannot help you: HTML was designed so that a document with a mistake still renders something rather than showing an error page. That robustness is a genuine strength and the direct cause of most "my CSS does not apply" reports — the element you wrote is not the element in the DOM.

Learn the category each element belongs to, not just its name. It is the smallest piece of knowledge that explains why the document you typed is not the document the browser built, and it makes the nesting rules predictable instead of a list to memorise.

1.2 The living standard

HTML has no versions. There was a 4.0 specification in 1999 and the language has been called HTML5 ever since as a marketing convenience, but what every current browser implements is one continuously updated document called the HTML Living Standard, maintained by the WHATWG. There is no "HTML 6" to wait for, and a feature either ships in browsers or it does not.

Who writes it, and where to read it

BodyWritesRead it for
WHATWGThe HTML Living Standard, together with DOM and URLThe normative answer. If it is not there, it is not HTML
W3CARIA, SVG, and the accessibility guidelinesARIA roles and states, and WCAG itself
MDNReference documentation, not a specificationUnderstandability, worked examples, support data
web.devBaseline, guidance and core web vitalsWhether a feature is safe to use today
caniuse.comAggregated usage dataWhether your actual traffic can run it

The distinction that matters: the specification defines what is correct, MDN explains it in human terms and reports support, and Baseline says whether you can ship it. For "is this valid", the Living Standard is the only authority — and every validator checks against it.

Baseline: the term that settles compatibility questions

Individual features come and go, but a browser set is now formally defined. Baseline is a web.dev designation for a feature supported across all major browsers for thirty consecutive days, or with enough web platform support to be considered safe. It has three levels — newly available, widely available and limited availability — and a feature only climbs, so "widely available" is a promise and "newly available" is a warning.

<!-- Baseline Widely Available — no fallback required -->
<dialog id="baseline-check">
  <form method="dialog">
    <p>Delete this project?</p>
    <menu>
      <button value="cancel">Cancel</button>
      <button value="ok">Delete</button>
    </menu>
  </form>
</dialog>

<script type="module">
  const dlg = document.getElementById("baseline-check");
  dlg.showModal();                 // a Native HTML version is Baseline
</script>

Reading a support table honestly

Support tables need a unit, and "supported" can mean any of five quite different things: it parses, it works, it works correctly, its accessibility behaviour is correct, or it is usable without a flag. A feature can be five years old and still silently broken in one engine's accessibility tree, and for several HTML features that is the actual state rather than a hypothetical.

QuestionWhy it changes what you write
Which engines, which versions?"All browsers" in 2015 and "all browsers" today are different promises
Does it need a flag?A flagged feature is not one you can rely on
Is the accessibility behaviour right?A role that silently does nothing is worse than no role
Is support partial?Partial often means the parse succeeds and the behaviour differs subtly
Which engine added it last?That engine's share of traffic is your real deadline

Detecting a feature, not guessing a version

The reliable test is to ask whether the browser gives you the thing you need, never which version it claims to be. User-agent strings are unreliable by design, they are frequently wrong for privacy reasons, and the browser you are on is not the one you need to know about anyway.

<script>
  // Feature test: does this browser give me the behaviour I need?
  const dialog = document.createElement("dialog");
  const hasDialog = typeof dialog.showModal === "function";

  // Another one, on something genuinely useful to test for
  const hasContainerQueries =
    CSS.supports("container-type: inline-size");

  // In JS, the DOM is the test. In CSS, @supports is.
  if (!hasDialog) {
    // polyfill, or a fallback that does the same job
  }
</script>

<style>
  @supports (container-type: inline-size){
    .card-list{ container-type: inline-size; }
  }
  /* and if it is not supported, this plain rule simply applies instead */
  .card{ display:block; }
</style>

Test for the capability, not the version, and always write the path that works without it first. The version without the new feature is the version you were going to write anyway, so the fallback costs nothing and the enhancement is a single line.

In CSS the equivalent is @supports, which tests a declaration rather than a browser. Use it for anything you are gating on, and keep the ungated rule as the base so an unsupported browser simply skips the enhancement.

There is no version to target and no upgrade cycle. Check the feature rather than the release, ask the browser whether it can do the thing, and keep the fallback for anything not yet Baseline widely available.

1.3 Your first page

The smallest complete HTML document is five lines. Everything else — the metadata, the stylesheet, the script — is added to that skeleton, and every addition is something you can justify. Build it once properly rather than assembling it from a framework template, because the skeleton is the part that has to be right on every page you ever write.

The complete document

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Widget catalogue — Acme</title>
  <link rel="stylesheet" href="/assets/site.css">
</head>
<body>
  <header>
    <a href="/"><img src="/assets/logo.svg" alt="Acme"></a>
  </header>
  <main>
    <h1>Widget catalogue</h1>
    <p>Everything we currently manufacture.</p>
  </main>
  <footer><p>© 2026 Acme Ltd</p></footer>
</body>
</html>

Five elements carry weight. The doctype puts the parser in standards mode; without it you get quirks mode and a page laid out as if it were 1999. The lang attribute on html is what drives hyphenation, font selection for the page's language, and the pronunciation a screen reader uses. The charset must be in the first 1024 bytes, which is why it goes at the very top of head — anywhere later and a mis-declared page decodes mojibake before it corrects itself.

Why lang is not decoration

A single lang attribute changes more than you would expect: it selects the correct font stack, it decides quotation mark direction, it enables hyphenation for that language's rules, it tells a screen reader which pronunciation dictionary to load, and it is what translation tools read to decide whether a segment needs translating. It is also how you mark a single phrase in another language without switching the whole document.

<p lang="en">The German word <span lang="de">Rechtsschutzversicherungsgesellschaft</span>
   is not an English word, whatever the font does to it.</p>

<p dir="rtl" lang="ar">Arabic runs right to left; the layout mirrors
   automatically from this attribute alone.</p>

Required, and what breaks without it

PieceRequired?What goes wrong without it
<!doctype html>Effectively yesQuirks mode: the box model, table sizing and percentage heights all behave differently
langYes, for correctnessWrong pronunciation, wrong hyphenation, wrong font, broken translation
charsetYesAny character above U+007F can be decoded wrongly — mojibake or a parse error that swallows markup
viewportYes in practiceMobiles render a 980px-wide virtual viewport and scale the result down
titleYesThe browser tab, the history entry, the bookmark name and the search result are all blank
mainNot requiredThe page has no main landmark, so skip links and landmark navigation stop working

Serving it correctly

The document itself has one hard requirement from the server: the Content-Type must say text/html, and the charset must match what you declared. A text/plain response renders as source text; a mismatch between a declared and a served charset produces the mojibake that charset was supposed to prevent.

Content-Type: text/html; charset=utf-8

Two caching rules matter more than they look. A 404 or a 500 response should not be cached at all, or a visitor will be shown your error page after you have fixed it. And a redirect must be a real 301 or 302 — a page that redirects via JavaScript has no status code for a crawler or a share preview to read, so the link does not survive being pasted anywhere.

Every page in a site is this skeleton plus content. Get these five things right once and the failure modes they prevent — quirks mode, mojibake, a blank tab title, an unusable mobile zoom — stop being a category of bug you have to think about.

1.4 How browsers render

Between your text and the screen there is an entire pipeline, and almost every "the browser is doing something weird" report becomes obvious once you can name the stage that misbehaved. The path is: bytes arrive, characters are decoded, the HTML is parsed into a tree, CSS is parsed and resolved into a computed style per element, layout assigns boxes, paint fills pixels, and finally composite assembles the layers.

The stages, and what each one decides

StageProducesCommon symptom when it goes wrong
DecodingCharacters from bytesMojibake, or a parse error that eats markup
ParsingThe DOM treeElements nested in ways you did not write; an unclosed tag swallows the rest of the page
Style resolutionComputed styles per elementA declaration that "does nothing" because a more specific rule won
LayoutGeometry: position and sizeOverflow, an element of zero height, a flex item that will not shrink
PaintPixelsSomething invisible because it was painted and then covered
CompositeLayers on screenJank, or a blurred image scaled up

CSS is not applied in the order it appears in your file. The cascade resolves specificity across three origins — author styles, user styles, and the browser's own defaults — and only within an origin does source order break ties. This is why a stylesheet you link second can lose to a rule in the first, and why !important is the last resort rather than a tool.

The waterfall, and why order in your markup is load order

Render-blocking resources are the ones that stop parsing until they arrive. A stylesheet in head is render-blocking, and always will be: a page cannot be painted correctly without knowing the styles, and guessing produces a flash of unstyled content. Scripts are blocking too unless you say otherwise, because a classic script must run to completion before parsing continues.

<!-- blocks rendering AND blocks parsing -->
<script src="/assets/app.js"></script>

<!-- downloads in parallel, executes in order, still blocks parsing -->
<script src="/a.js" defer></script>
<script src="/b.js" defer></script>

<!-- downloads in parallel, executes as soon as it arrives, blocks parsing -->
<script src="/urgent.js" async></script>

<!-- non-blocking CSS: the media query must not match to load at all -->
<link rel="stylesheet" href="/print.css" media="print">

Both defer and async scripts wait for the HTML to be parsed before running, so neither can be trusted to have found the DOM yet unless it also handles the case where the document is still loading. defer preserves execution order among itself, which is why a library and its plugin both belong on it. async guarantees no order at all, which makes it right for analytics and wrong for anything with a dependency.

The DOM is a tree, and it can be inspected

Reading the parsed tree rather than the text you typed is the single most useful debugging skill in front-end work, and every current browser ships the tool for it. If a style "does not apply", the element you styled may not be the element that exists.

<!-- typed by hand -->
<table>
  <p>inside a table, but not in a cell</p>
</table>

<!-- what the parser built, revealed by document.body.innerHTML -->
<table></table>
<p>inside a table, but not in a cell</p>
<p>outside the table entirely</p>
A paragraph is not allowed as a direct child of a table. The parser closes the table and hoists the paragraph out of it, along with everything that followed. This is why a whole page of content can end up below the table instead of inside it, and why the fix is always to use td, th, tbody, caption or colgroup — never to add a container div where a table section belongs.

Layout is also worth understanding as a process, because it explains a specific surprise: reading a geometric property such as offsetHeight from JavaScript forces layout to run immediately, and doing that inside a loop over many elements turns a smooth page into a stuttering one. Batching reads before writes keeps the browser to one layout per frame.

Almost every rendering oddity is a parse error the parser recovered from rather than a bug in the browser. Learning to read the DOM that was actually built turns a two-hour investigation into a one-line check.

Chapter two covers the head of a page: the doctype, the html, head and body skeleton, and every piece of metadata browsers, search engines and social networks read. You will add character encoding, viewport and title declarations that every page needs. Correct metadata makes your pages render well and describe themselves accurately.

Metadata is everything the page knows but the visitor does not see. The head controls character encoding, device scaling, the tab title, stylesheets and the favicon.

2.1 The skeleton: doctype, html, head, body

Every document has the same shape: a doctype, an html element with a language, a head of metadata that renders nothing, and a body of everything that does. The vocabulary is deliberately small. head may only contain a fixed set of elements plus metadata, and knowing which are which is most of what this section is about.

What may go in head

ElementPurposeMay repeat?
titleThe document's name — required, exactly onceNo
metaMachine-readable metadata; the charset one is requiredYes
linkA relationship to an external resource: stylesheet, icon, preload, canonicalYes
baseChanges the base URL all relative URLs resolve against — at most oneNo
styleA block of CSS. Fine for a page-specific rule, wrong for a whole siteYes
scriptA block of JavaScriptYes
noscriptContent shown only when scripting is offYes

Anything else in head is either ignored or moved into body by the parser. A <meta name="description"> is fine; a <form> in head is not, and will turn up in the body where you did not expect it.

html, and the two attributes it should always carry

lang is discussed in section 1.3. The second attribute worth putting on html is dir, which sets the base writing direction for the whole document. Set it and the layout mirrors, quotation marks flip, and punctuation that is directional — brackets, dashes, ellipses — renders on the correct side.

<html lang="en" dir="ltr">
<body>
  <!-- a single phrase in the other direction -->
  <p>Call it <bdi lang="he">חשמל</bdi> — that is the name.</p>

  <!-- bdi isolates direction for a run of mixed text -->
  <p>Price: <bdi>100 ₪</bdi> per unit</p>
</body>

bdi is the element to reach for when text of unknown direction appears inside a sentence. Without it, a neutral character such as a minus sign or a bracket adopts the surrounding direction, and a bidirectional string can reorder itself into something unreadable.

body, and the landmark elements

Inside body you should reach for the element that names what the region is rather than a div plus a class. Six of them create the page's landmark map: header, nav, main, aside, footer, and search. A screen reader user can jump between them directly, which is far faster than scrolling, and this is what a skip link targets.

<body>
  <header>
    <a href="/" class="skip">Skip to content</a>
    <nav aria-label="Primary">...</nav>
  </header>

  <main id="page-main">
    <h1>Widget catalogue</h1>
    <article>
      <h2>Widget A</h2>
      <section>
        <h3>Specification</h3>
      </section>
    </article>
    <aside>Related products</aside>
  </main>

  <search>
    <form role="search"><input name="q" type="search"></form>
  </search>

  <footer>...</footer>
</body>
A page must have exactly one main, and it must not be nested inside an article, aside, header, footer or nav. It is the landmark that means "the content of this page", so two of them leave a reader unable to answer the question, and nesting it defeats the purpose. Give it an id and point the skip link at it.

Metadata that is not content

One head child deserves special care: template holds markup that is parsed but never rendered, which is how a component library stores markup for later use. JavaScript reads its content and clones it. Nothing inside it appears, and nothing in it is fetched — an img inside a template downloads nothing until it is cloned into the document.

<template id="row-template">
  <tr>
    <td></td>
    <td><img src="" alt=""></td>
    <td></td>
  </tr>
</template>

<script type="module">
  const row = document.getElementById("row-template").content
    .querySelector("tr").cloneNode(true);
  // the img above has fetched nothing yet
</script>

The skeleton has about seven elements and they never vary. Choose the landmark that names the region rather than a div with a class, keep one main, and declare the language — and the structure of every page on the site is correct by default.

2.2 meta: charset and viewport

Two meta elements are mandatory in any document you care about, and the rest of the element is a simple grammar: name plus content for the widely understood metadata, or charset, http-equiv or property for everything else. The two required ones are the easiest to get wrong and the most expensive when they are.

charset: one element, placed first

UTF-8 is the only encoding worth using for new work, and the charset declaration must appear within the first 1024 bytes of the document. Anywhere later and the parser has already started decoding with a default, which is how a page ends up displaying a window of mojibake before correcting itself. Place it as the first thing inside head and the question does not arise.

<head>
  <meta charset="utf-8">
  <title>Widget catalogue</title>
</head>

<!-- accepted, but only correct as the first 1024 bytes -->
<meta http-equiv="Content-Type" content="text/html; charset=utf-8">

Both forms declare the same thing, and charset is the one to write because it is a single short attribute, it is limited to 1024 bytes by the specification, and it cannot be malformed. The http-equiv form was needed before UTF-8 could be the default and is obsolete for new documents.

The viewport meta, and what initial-scale actually does

Without a viewport meta, a mobile browser assumes a virtual viewport about 980 CSS pixels wide and scales the result down to fit. Text ends up tiny and the reader has to pinch to read it. The meta element tells the browser to use the real device width instead.

<meta name="viewport" content="width=device-width, initial-scale=1">

<!-- never disable zooming -->
<meta name="viewport"
      content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no">
                            <!-- the last two are an accessibility failure -->
Never set user-scalable=no or maximum-scale=1. They block pinch-zoom for readers who need it, and that is a WCAG 1.4.4 failure. initial-scale=1 is fine — it sets the starting zoom, not the range — but it is also optional, because width=device-width already gives a sensible starting zoom.

viewport-fit=cover is the addition worth knowing, and it is about notches rather than zooming. With it, a page's background can extend under the rounded corners and the sensor bar on a phone; you then keep content clear of the edges using env(safe-area-inset-*).

The named metadata you will actually use

nameEffectNotes
descriptionThe snippet under a search resultNot a ranking factor. It is a click-through decision.
authorIdentifies the authorOne per document is enough
robotsInstructs a crawlernoindex, nofollow, noarchive, index, follow
referrerHow much referrer information to sendno-referrer, same-origin, strict-origin
theme-colorColours the browser chromeOne per colour scheme; see section 8.1
color-schemeTells the UA you support light and darkMakes form controls and scrollbars match before CSS loads

color-scheme is the one with an effect on rendering rather than on a crawler, and it is easy to miss: declaring it makes the browser draw native controls, scrollbars and the default canvas background in the reader's preferred scheme, which removes the flash of a white page in dark mode before your stylesheet has loaded.

http-equiv, and the two that still matter

Most http-equiv values are obsolete. Two survive, and a third is worth knowing even though it is not an equiv.

<meta charset="utf-8">

<!-- still honoured: a refresh, which should almost never be used -->
<meta http-equiv="refresh" content="30">

<!-- not an equiv: conditional loading of a stylesheet -->
<link rel="stylesheet" href="/dark.css" media="(prefers-color-scheme: dark)">
Never use http-equiv="refresh" to redirect. It cannot set a status code, so a search engine cannot tell it from a soft refresh, and it breaks the Back button for anyone who used it by accident. Use a real 301 or 302 from the server, or a link rel="canonical" when the point is to consolidate duplicate URLs.

Two meta elements are load-bearing and take ten seconds to write: charset as the first line of head, and viewport with width=device-width. Everything else is metadata for machines, and adding it is a decision about a specific consumer rather than about the document.

2.3 title, link, base and favicon

Four elements finish the document's identity: title, which is the one piece of metadata a person will see, and link, whose rel value decides what a given link does. The link element is more widely used than most people realise — it is not just for stylesheets, and most of its modern uses are hints rather than downloads.

title: short, unique, and read by people

The title appears in the tab, the window title bar, the history entry, the bookmark dialog and, truncated, as the first line of a search result. That is four audiences and one string, so it has to work in all of them. Keep it under about sixty characters, put the distinguishing part before any site name, and never leave it as the file name — guide.html as a title tells a reader and a crawler nothing.

<title>Native validation and the constraint API — HTML forms</title>

<!-- weak: no word tells a reader or a crawler what this is -->
<title>form.html</title>

<!-- weak: identical on every page, so the tab tells you nothing -->

Icons, and giving the browser real choices

SVG scales to any size, so a single icon.svg with the rel="icon" covers every context the browser chooses. The PNGs remain for the places that still ask for a bitmap — a saved shortcut on iOS in particular, which ignores the SVG. Sizes matter: an unlabelled sizes makes the browser assume the file is 32×32 and pick accordingly.

base: one element, and mostly a reason to avoid it

<base href="/app/"> changes the base URL for every relative reference on the page. It is occasionally necessary when an application is mounted under a path it does not know, and almost always a liability otherwise, because one base in head silently changes the meaning of every relative link, every stylesheet and every form action on the page — including ones you did not write and cannot see.

<!-- with this in head -->
<base href="/app/">

<!-- these now resolve under /app/, not under /docs/ -->
<link rel="stylesheet" href="site.css">
<a href="guide.html">Guide</a>
<form action="submit">
If you must use base, remember it also breaks a fragment-only link. <a href="#install"> resolves against the base URL, so it becomes /app/#install rather than /docs/guide.html#install — and the browser navigates instead of scrolling. Prefer root-relative URLs and no base element.

One more base use that does survive: target sets the default browsing context for links that do not specify one. It is a blunt instrument and there is rarely a good reason for it.

Write the title first, because it is the only head element a person reliably sees. Then add the two link elements that matter for the job — a stylesheet, and an icon — and reach for preload or prefetch only when you can name what you are buying and when it will arrive.

3.1 Headings and paragraphs

HTML gives you six heading levels and one paragraph element. That is the entire vocabulary, and it causes more confusion than anything else in the language because almost nothing about it is enforced — you can nest an h6 inside an h1 and the parser will not complain. What the browser fails to check, your reader pays for. A screen reader user moving through your page by heading builds a mental map from these seven tags and nothing else, and if that map is wrong there is no way for them to recover it.

The heading outline is an outline, not a set of sizes

The reason headings matter is not visual. h1 through h6 are the only elements in HTML that declare structure, so assistive technology builds a navigable list of contents from them. Every current browser ships a rotor, a headings list or an equivalent, and a reader can jump to any heading on the page in document order. That list is generated from the tags, and it inherits every mistake you make in them.

Level is a claim about nesting, not about font size. An h2 is not a smaller h1; it is the top-level division of the region that the h1 introduces. When you want a different type size, that is CSS — and reaching for a different heading level to get it is trading a purely visual problem for a structural one.

<h1>Guide</h1>                      <!-- once per page -->
  <h2>Getting started</h2>         <!-- a top-level division -->
    <h3>Install the toolchain</h3>
      <h4>Windows</h4>
      <h4>macOS</h4>
    <h3>Write your first page</h3>
  <h2>Reference</h2>               <!-- second peer of the first h2 -->
    <h3>Element index</h3>

Read that as a tree. The page has one h1; two h2 divisions sit directly under it; three h3 subsections sit under those; and two h4s sit under the first of those. Every heading is contained by the one above it in the source, not merely somewhere earlier on the page.

Choosing a level

SituationLevelReason
The page's own subject, onceh1The single label this page can be named by in a search result, a bookmark or a citation.
A major division, such as "Getting started" or "Reference"h2Direct children of the h1. These are what a reader scans in a headings list.
A topic within a divisionh3Direct children of the matching h2.
A genuinely distinct subsectionh4Sparingly. If you need four of these, the h3 usually wants to be two sections.
A fifth or sixth levelh5, h6Rare. Depth this far usually means the content wants splitting, not another level.

Skipping a level is what actually breaks outline tools. Going from h1 to h3 claims a level of structure exists that you never labelled, and readers are told about a jump they cannot see.

The one legitimate exception is a component whose heading levels you do not control — a card or widget dropped into someone else's page, where resetting to h2 would be wrong for context. There, prefer keeping the tag shallow and styling it to size. If the level itself must be correct while the tag cannot be, role="heading" aria-level="3" adds an outline entry without adding a document heading.

Paragraphs, and why your line breaks vanish

p is a block element: it begins on a new line and occupies the full width of its container. The browser also gives it margin above and below, and that margin is where a page's vertical rhythm comes from — not from empty lines in your source. Runs of whitespace in HTML source are collapsed to a single space by the parser, so the line breaks and indentation in your editor carry no meaning at all.

<p>One paragraph.</p>

<p>
  This second paragraph is wrapped across three lines in the source
  and still renders as one single line of text in the browser.
</p>

To force a line break inside a paragraph use br. To force a vertical gap between two blocks that belong together, set a margin on the block in CSS — or reach for a div only when there is genuinely no element that means what you mean.

Never separate paragraphs with <br><br>. It produces the vertical rhythm but no structure: to every tool that reads the page this is still one paragraph, so it cannot be restyled, restyled responsively or re-wrapped for translation. It is the most common reason a page looks correct at one width and broken at another, because each manual break lands in a different place once the text reflows.

The four mistakes that break an outline

<!-- 1. styling a heading to look like a different level -->
<h1 class="subtle">Reference</h1>        <!-- still a top-level heading -->

<!-- 2. skipping a level -->
<h1>Guide</h1>
  <h3>Installation</h3>                <!-- nothing at h2 above it -->

<!-- 3. two h1 elements used as banners -->
<h1>Logo</h1>
<h1>Page title</h1>                   <!-- two top-level headings -->

<!-- 4. the fix: one h1, then descend by one -->
<h1>Reference</h1>
  <h2>Elements</h2>
    <h3>Text</h3>

The fix for the second is to insert the missing level rather than renumber downward. The third is usually caused by a large logo wrapped in a heading because it looks like a title; a logo is not a heading, so it belongs outside the outline entirely, as a link with an accessible name or a plain image with alt text.

Headings declare structure and nothing else. Style them freely, but never reach for a different heading level to get a different size — a heading level is a claim about where you are in the document, and it should be the same claim on every page of the site.

3.2 Inline emphasis, line breaks and quotes

Every element in this section is inline: it sits inside a sentence and its box is measured by its text. That single fact explains most of their behaviour, including the ones that surprise people. Inline elements do not start a new line, they cannot be given a width or height, and vertical margins on them are ignored by the layout engine because the line box is sized by the tallest inline box, not by the margins around it.

The inline elements worth knowing

em and strong carry meaning; b and i do not

This is the single most useful distinction in inline markup, and the most often lost. em and strong describe what the text is. b and i only give you a place to hang a style. A screen reader announcing "bold, I ran" and "italic, I ran" conveys nothing, whereas announcing emphasis does — and a stylesheet that sets em to a colour instead of an italic immediately loses the one thing the element was for.

<p>Press <kbd>Ctrl</kbd> + <kbd>S</kbd> to save. <em>Do not</em> press
   <kbd>Ctrl</kbd> + <kbd>Q</kbd> — it <strong>discards</strong> every
   unsaved change without asking.</p>

<!-- the same two words, no meaning either way -->
<p>Press Ctrl + S to save. Do not press Ctrl + Q — it <b>discards</b>
   every unsaved change without asking.</p>
If you want em to look like bold and strong to look like something else, change the CSS. The tags must keep the meaning they were given; the presentation is yours to decide.

br, and the rule about void elements

br is a void element: it has no content and no closing tag. Void elements are area, base, br, col, embed, hr, img, input, link, meta, source, track and wbr. Writing <br></br> is not an error the parser reports — it simply ignores the stray closing tag — so the mistake shows up as a mystery indentation much later.

A line break is a typographic decision, not a structural one. If the text is an address, a poem, or a set of values in a column, you want the line breaks to survive resizing — which means real block elements, not br.

<!-- a break that survives being reflowed -->
<address>
  1 Example Street<br>
  Example City<br>
  EX1 2MP
</address>

<!-- the fragile version: one address broken at one width -->
<p>1 Example Street, Example City, EX1 2MP<br><br>
   Telephone 01234 567890</p>

There is one place br is genuinely right: a line break inside a short run of text where the two halves must stay on separate lines but are the same thought. A postal address in a single-line summary is the usual case.

Quoting: q, blockquote and cite

Three elements, three jobs, and they are routinely confused. q is an inline quotation and marks itself up with the right quotation marks for the document language, so you never write them yourself. blockquote is for a quotation that stands apart, and it is a block element — it can contain several paragraphs, a heading and an image. cite holds the title of the work, not the quotation and not a URL.

<p>She called it a "necessary evil" in her <cite>Designing Data-Intensive
   Applications</cite>, which is a fairer summary than the usual one.</p>

<blockquote>
  <p>Many systems treat naming as a solved problem, which is why so many
     of them are impossible to change later.</p>
  <footer>— Pat Helland, <cite>Designing Data-Intensive Applications</cite></footer>
</blockquote>

When you want to link the source rather than name it, cite takes a URL in its href attribute, and that is the correct use of cite href — a feature that is in the HTML specification and shipped in every current browser.

blockquote does not add quotation marks and is not automatically italic. If you want the visual treatment too, style blockquote in CSS. Quotation marks around a long passage are a typographic error; the indent and the attribution carry the meaning.

Four elements that look the same and are not

All four render in a monospace font by default, which is exactly why they get used interchangeably. They are distinguishable: code is a fragment of source, kbd is something the reader presses, samp is something the program produced, and var is a name the programmer chose.

<p>Set <var>retryCount</var> to 3, then run the command below.</p>
<pre><code>curl -s https://example.test/health</code></pre>
<p>It prints <samp>ok 200</samp> when the service is up. If you see
   <samp>error 503</samp> instead, press <kbd>Ctrl</kbd> + <kbd>C</kbd>
   to stop and retry.</p>
Do not reach for br to lay out a code sample. Inside pre the whitespace is significant and preserved, so indentation is the formatting — a br there adds an extra line and breaks every alignment downstream.

Inline elements describe meaning and formatting is separate. Choosing em over i, strong over b, and kbd over code costs nothing at authoring time and is the difference between a page that reads correctly with a screen reader and one that does not.

3.3 Lists: ul, ol and dl

Three elements cover every kind of set you will write: ul for items where order carries no meaning, ol for items where it does, and dl for term-and-definition pairs. The element you pick is a claim about the content, and a reader who is counting items in an ordered list to find "step 4" is a real use case that ul cannot serve.

Which list to use

dldt then ddNames paired with descriptions or valuesGlossary, API field list, keyboard shortcuts, settings

ul and ol, and the attributes that change the numbering

Both take li children and nothing else. Three attributes are worth knowing: start begins the count at a number other than 1, reversed counts down, and value on an individual li overrides the number for that item and the ones after it.

<ol start="4">
  <li>Fourth</li>
  <li>Fifth</li>
</ol>

<ol reversed start="10">
  <li>Tenth</li>
  <li>Ninth</li>
</ol>

<ol>
  <li>First</li>
  <li value="7">Seventh — everything after follows this</li>
  <li>Eighth</li>
</ol>

None of these change the markup to something else. An ordered list numbered 4, 5, 6 is still one ol; do not write the numbers into the text, or the list stops being a list the moment an item is inserted.

Nesting: the only rule that is not obvious

A nested list must be a child of an li, not of its parent ul or ol. This is the mistake that produces an invisible nested list: put a ul straight inside a ul and the parser closes the first list and starts a new one, so you get two sibling lists where you meant one indented one.

<!-- correct: the inner ul is inside an li -->
<ul>
  <li>Backend
    <ul>
      <li>PHP</li>
      <li>PostgreSQL</li>
    </ul>
  </li>
  <li>Frontend</li>
</ul>

<!-- wrong: a ul directly inside a ul -->
<ul>
  <li>Backend</li>
  <ul>                      <!-- parser ends the first list here -->
    <li>PHP</li>
  </ul>
</ul>

You do not need to nest more than two deep. Three levels is usually a sign that the content is a table or a set of sections rather than a list, and readers using a screen reader have to announce every level on the way down.

Description lists, including the newer grouping form

dl is a term followed by its description, and the pairs are grouped by dt-then-dd order rather than by nesting. The HTML specification added div wrappers so one dt can carry several dds without the association becoming ambiguous.

<dl>
  <dt><code>retryCount</code></dt>
  <dd>How many times a failed request is retried. Default 3.</dd>

  <dt><code>timeoutMs</code></dt>
  <dd>
    <dd>Per-attempt timeout in milliseconds. Default 2000.</dd>
    <dd>Not affected by <code>retryCount</code>.</dd>
  </dd>
</dl>

<!-- the grouped form, one div per pair -->
<dl>
  <div>
    <dt><abbr title="Cascading Style Sheets">CSS</abbr></dt>
    <dd>A language for describing how elements should look.</dd>
  </div>
  <div>
    <dt><abbr title="HyperText Markup Language">HTML</abbr></dt>
    <dd>A language for describing what content means.</dd>
  </div>
</dl>

When a list is the wrong element

Three structures get built as lists and should not be. Navigation is a list of links, which is correct, but a horizontal bar of navigation is better as a nav containing a list — never as a row of divs, because then the count of destinations is invisible to a screen reader. Tabular data is a table. And a set of cards is a ul of lis, which is the one people most often miss: the list is what tells assistive technology "there are six of these".

Never put a heading inside an li to make a card's title look like a title. Use h3 inside the li and style it — an li may contain flow content, and that is the whole point of it. A heading nested inside a list also appears in the page's headings outline at the right level, which a strong or a span never would.

Pick the list by whether order matters, not by how it looks. The visual style — bullets, numbers, spacing, indentation depth — belongs to CSS, and the same ul should be able to render as bullets, as a row, or as a stack of cards without a single change to the markup.

3.4 Links: anchors, relative and absolute URLs

The a element is the most consequential tag you will write, because it is the only one whose behaviour depends on another document's response. It carries a URL, it can be opened in a new tab, it can be a fragment, a telephone number or an email address, and since 2020 it can also trigger a download. Getting its attributes right is a security question, not just a usability one.

How the browser actually resolves a relative URL

This is worth knowing exactly, because it is the source of most "my link works locally and breaks on the server" reports. A relative reference is resolved against the URL of the document, not against the folder on disk, and the part that matters is the directory of that URL. The file name of the current page is discarded; everything before the final slash is kept.

Fragments, and the two ways they behave

A fragment is everything after the #. The browser scrolls to the element whose id matches it, and — this is the part that surprises people — it puts that element in :target, which is a real pseudo-class you can style. Nothing is matched if the id is absent, and the browser will not tell you; the link simply does nothing.

<a href="#install">Jump to installation</a>

<h2 id="install">Installation</h2>

<style>
  :target{ scroll-margin-top: 90px; }   /* clear a fixed header */
  h2:target{ outline: 3px solid var(--accent); }
</style>

JavaScript reads the fragment from location.hash and the hashchange event fires whenever it changes — including when the reader presses Back, which is how in-page navigation survives a refresh. If a page needs to know where the reader jumped from, that event is the mechanism; polling the hash is not.

target and rel: the tabnabbing fix

target="_blank" opens a new browsing context, and by default the new page gets a window.opener reference back to yours. It can then navigate your tab to a page that looks like your site and asks for a password. The fix is rel="noopener", and every current browser now implies it for target="_blank" anyway — but it is still worth writing, because it is explicit, it survives older browsers, and it is checked by linters.

<!-- both together: the safe form -->
<a href="https://example.test/docs"
   target="_blank" rel="noopener noreferrer">Documentation</a>
Never use target="_blank" for a link the reader needs to compare against the current page, such as a search result list or a reference table. Opening a new tab for content the reader is meant to read alongside what they already have is a decision made for your convenience, not theirs. Reserve it for genuinely independent destinations, and tell the reader it happens — a small "opens in a new tab" note, or the external-link icon.

rel="nofollow" asks a search engine not to pass ranking signal to the target. rel="ugc" and rel="sponsored" mark content contributed by users or paid for. None of them restrict what the destination can do to your page; only noopener has any effect on behaviour.

3.5 Images: img, srcset, figure and figcaption

Images are where a page becomes either useful or slow, and most of the decisions are made in the markup rather than in a tool. Four attributes carry almost all of it: alt for meaning, width and height for stability, and loading for when to fetch. The responsive ones — srcset, sizes and picture — decide how much data the reader downloads.

alt: four cases, and only one of them is "description"

CaseWhat to writeExample
The image conveys information the text does notDescribe it, briefly and usefullyalt="Bar chart: revenue doubled between 2023 and 2026"
The image is decorativeEmpty alt, and nothing elsealt=""
The image is inside a link and adds nothingEmpty alt — the link text is the name<a href="/"><img src="logo.svg" alt="">Home</a>
The image is a complex chart or diagramShort alt plus a longer description nearbyalt="Revenue chart" plus a table or caption
The image failed to load and there is no text nearbyDescribe the content, not the failurealt="Company logo" — not "logo broken"

Decorative images are the case people get wrong most often. The correct markup for a decoration is alt="" — present and empty. An omitted alt attribute makes some screen readers announce the file name instead, and alt="decorative" announces the word "decorative", which is worse than either.

Never write alt="image" or alt="picture of". The screen reader already announces that it is a graphic, so the information is spent before the reader learns anything. If a description has genuinely run out, the image is decorative and the attribute should be empty.

width and height, and the layout shift they prevent

Every image reserves its box before it loads when both dimensions are present, because the browser can compute the aspect ratio from them. Without them the box is zero-height until the bytes arrive, and the text underneath jumps down — cumulative layout shift, which is a ranking factor and the single most complained-about symptom of a slow page.

<!-- both attributes present: the space is reserved -->
<img src="chart.png" width="640" height="360"
     alt="Revenue chart: revenue doubled between 2023 and 2026">

<!-- responsive without losing the ratio -->
<img src="chart.png" width="640" height="360"
     style="max-width:100%; height:auto"
     alt="Revenue chart: revenue doubled between 2023 and 2026">

<!-- never scale by only one dimension -->
<img src="chart.png" width="640" alt="Revenue chart">   <!-- 640 by whatever the file happens to be -->

The height="auto" in CSS is the part that is easy to miss: it overrides the attribute's pixel value while the attribute itself still supplies the ratio, so the image scales down on a narrow screen and up on a wide one without ever distorting.

srcset and sizes: choosing a file, not scaling one

width and height reserve space. They do not save bytes. srcset lets the browser download a smaller file when the image is displayed small — which is the normal case on a phone, and the difference between a 40 KB page and a 400 KB one.

<img
  src="photo-800.jpg"
  srcset="photo-400.jpg 400w,
          photo-800.jpg 800w,
          photo-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw,
         (max-width: 1000px) 60vw,
         800px"
  width="1600" height="900"
  alt="A workshop bench with tools laid out in rows">

The w suffix is a real width in pixels. sizes is the space the image will occupy, given as a CSS media-condition list ending in a fallback — and it is the part authors get wrong, because the browser evaluates it before downloading, against the viewport width alone, with no knowledge of your layout. If your image sits in a two-column grid that is 60% of the viewport on desktop, sizes must say 60vw, not 800px. Getting it wrong does not break anything visibly; it just makes the browser pick the wrong file.

Always include a plain src as well. It is the fallback for anything that ignores srcset, and it is what gets requested by clients that send no Accept header at all.

picture, for art direction rather than resolution

srcset chooses between files that show the same picture at different sizes. picture does something different: it lets you choose a completely different image, or a different crop, or a different file type, based on what the browser supports or what the reader has asked for.

<picture>
  <!-- a dark-mode variant, chosen by the reader's preference -->
  <source srcset="hero.avif" media="(prefers-color-scheme: dark)" type="image/avif">
  <source srcset="hero.avif" media="(prefers-color-scheme: light)" type="image/avif">

  <!-- a wide crop for wide viewports, a tall one for phones -->
  <source srcset="hero-wide.avif" media="(min-width: 900px)" type="image/avif">
  <source srcset="hero-tall.avif" media="(max-width: 899px)" type="image/avif">

  <img src="hero.jpg" width="1600" height="900"
       alt="The workshop at dawn, benches in rows">
</picture>

The source elements are tried in order and the first whose media and type both match wins, so order them most-specific-first. The img inside is mandatory and is the fallback for any browser that finds no matching source — put the most universally supported file there. AVIF is around 50% smaller than JPEG at the same quality; WebP is a safe second step.

Both loading="lazy" and decoding="async" are worth setting on anything below the fold. Lazy loading keeps the first paint fast because the browser does not queue dozens of off-screen downloads behind the content the reader is actually looking at. Do not apply it to the image at the top of the page — lazy-loading the largest contentful element delays the thing the page is judged on.

figure and figcaption

When an image needs a caption, a credit or an explanatory paragraph, wrap both in a figure. It is a block element that exists for exactly this and carries no visual style of its own, so nothing looks different until you style it.

<figure>
  <img src="cutaway.png" width="1200" height="700"
       alt="Cross-section of the assembly, showing the rotor inside the housing">
  <figcaption>
    Figure 3. The rotor sits inside the housing. When the housing is removed,
    the retaining clip must be released first or the rotor will bind.
  </figcaption>
</figure>

A figcaption may be the first or the last child, and must be a direct child of the figure. Note that alt and figcaption overlap: if the caption already says everything the alt says, the alt should be shortened or emptied, or the reader hears the same sentence twice.

Every image decision here is a trade between bytes and meaning, and the meanings are the ones worth protecting. Reserve the space, serve a smaller file to a small screen, and describe the image for the reader who cannot see it — the performance cost of the last one is zero.

4 · Tables & Semantic Landmarks

4.1 Table structure4.2 colspan, rowspan and captions4.3 Semantic landmarks

Chapter four covers tables for tabular data and the semantic landmark elements that give a page its outline. You build correct table structure with header and data cells, then map the regions of a page with header, nav, main, aside and footer. Used correctly, both are accessibility wins for every user.

Tables belong to data, not layout. The landmark elements that follow belong on every page — they replace the <div class="header"> stack older sites relied on.

4.1 Table structure

A table is for data that genuinely lives in rows and columns — a schedule, a price list, a specification. It is the one layout technique that HTML refuses to support for layout on principle, and that refusal is the most important thing to know about it. A table carries a two-dimensional relationship between its headers and its cells, and assistive technology exposes that relationship so a reader can move between them; use a table for layout and you hand the reader a grid of meaningless numbers.

The anatomy, and which parts are required

ElementRequiredWhat it means
tableYesThe table itself
captionEffectively yesA title and, importantly, the accessible name of the table
theadWhen there are headersHeader rows, repeated at the top of each printed page
tbodyYes, implicitlyBody rows. The parser inserts one even if you omit it
tfootNoFooter rows, such as totals. May appear before tbody in the source
trYesA row
thWhen there are headersA header cell. Takes scope, colspan, rowspan
tdYesA data cell
col / colgroupNoColumn-wide attributes such as span and a class hook
<table>
  <caption>Delivery times by region</caption>
  <thead>
    <tr>
      <th scope="col">Region</th>
      <th scope="col">Standard</th>
      <th scope="col">Express</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">United Kingdom</th>
      <td>3 days</td>
      <td>Next day</td>
    </tr>
    <tr>
      <th scope="row">Germany</th>
      <td>5 days</td>
      <td>2 days</td>
    </tr>
  </tbody>
  <tfoot>
    <tr>
      <th scope="row">All regions</th>
      <td>4 days mean</td>
      <td>2 days mean</td>
    </tr>
  </tfoot>
</table>

scope is the attribute that does the real work, and it has two values. scope="col" says this cell is a header for its column. scope="row" says it is a header for its row. With both in place a screen reader can announce "United Kingdom, Standard, 3 days" as a coherent triple instead of three disconnected values, which is the difference between a table you can navigate and one you can only read linearly.

Letting the table decide, and stopping CSS breaking it

The one rule that matters for a data table: let it size itself. Setting table-layout: auto — the default — lets content determine widths, which is right for a table whose contents you do not control. Setting table-layout: fixed makes the first row decide, which is what you want when the table sits in a narrow column or must not reflow as data arrives.

.table-scroll{ overflow-x:auto; }

.data-table{
  width:100%;
  border-collapse:collapse;   /* one border per cell edge, not two */
}
.data-table th,
.data-table td{
  padding:.5rem .75rem;
  text-align:left;
  border-bottom:1px solid var(--border);
}
.data-table thead th{
  border-bottom-width:2px;   /* the header reads as a header */
}
/* numeric columns right-aligned so digits line up */
.data-table td[data-numeric]{ text-align:right; font-variant-numeric:tabular-nums; }

/* fixed layout: the first row sets every column width */
.data-table.fixed{ table-layout:fixed; }

The container matters as much as the table. A table with many columns on a phone will overflow its parent, and the failure mode is the whole page scrolling sideways. Wrapping it in a container with overflow-x: auto keeps the overflow inside the component where the reader can scroll it deliberately.

Never use height on a table, row, or any cell. Table layout is special: the height of a row is computed from its cells and the height of the table from its rows, so setting either explicitly is resolved against a value that does not exist yet. Use min-height on the inner content, or a padding on the cell, if you need breathing room.

Reach for a table when the data is genuinely two-dimensional — a relationship between a row label and a column label. Reach for a list of definitions when it is one-dimensional. Most "tables" in ordinary page content are lists, and rendering them as tables gives a screen reader a grid of disconnected values to navigate.

4.2 colspan, rowspan and captions

A simple grid needs only tr, th and td. Real data rarely stays rectangular — a heading spans two columns, a total spans a whole row, a category covers several values — and the three attributes that handle that are colspan, rowspan and headers. All three exist so the relationship survives, not just the look.

colspan and rowspan

colspan makes one cell occupy several columns; rowspan makes it occupy several rows. Both take a count including themselves, so colspan="2" means this cell and the next one. There is a hard limit: a cell cannot extend past the grid, and a rowspan that runs past the last row is clamped by the parser.

<table>
  <thead>
    <tr>
      <th scope="col">Part</th>
      <th scope="colgroup" colspan="2">Cost</th>   <!-- one header over two columns -->
    </tr>
    <tr>
      <th scope="col">Retail</th>
      <th scope="col">Trade</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">Bracket</th>
      <td>12.00</td>
      <td>9.50</td>
    </tr>
    <tr>
      <th scope="row">Fixing kit</th>
      <td>18.00</td>
      <td>14.00</td>
    </tr>
    <tr>
      <th scope="row" colspan="2">Total for two units</th>
      <td>60.00</td>                            <!-- a label across two cells -->
    </tr>
  </tbody>
</table>

Notice the second header row. A colspan does not make the cell below it belong to it automatically — that cell is in a different row. So the "Cost" heading needs a matching row of sub-headings, which is why the example has two <thead> rows. Skipping that second row is the usual cause of a table where the reader can hear "Cost" as a value rather than as a heading.

headers, for the cases scope cannot express

scope handles the regular grid. It cannot describe a cell that refers to a header which is not in a simple row or column relationship — a cell in a row-group layout, or a data cell that belongs to two headers at once. headers takes a space-separated list of header cell ids and states the relationship explicitly, which is what a screen reader will use instead of guessing.

<table>
  <thead>
    <tr>
      <th id="h-day"  scope="col">Day</th>
      <th id="h-am"   scope="col">Morning</th>
      <th id="h-pm"   scope="col">Afternoon</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th id="h-mon" scope="row">Monday</th>
      <td headers="h-mon h-am">Standup 09:15</td>
      <td headers="h-mon h-pm">Review 14:00</td>
    </tr>
    <tr>
      <th id="h-tue" scope="row">Tuesday</th>
      <td headers="h-tue h-am">Review 09:15</td>
      <td headers="h-tue h-pm">Retro 14:00</td>
    </tr>
  </tbody>
</table>

Every id in a headers list must exist and must be a header cell. It is verbose, and it is the correct answer for the irregular cases. Use it when scope genuinely cannot express the relationship — not everywhere, because a table where every cell has a headers list is harder to read and maintain than one that relies on scope alone.

caption and colgroup

caption is the one element in the table that is easy to overlook and easy to regret omitting. It is the table's accessible name, it appears in the accessibility tree as the entry a reader uses to find the right table on a long page, and — being a child of table — it must come first.

<table>
  <caption>
    Delivery times by region. Figures are working days, not calendar days.
  </caption>
  <colgroup>
    <col>
    <col class="numeric">
    <col class="numeric">
  </colgroup>
  <thead>...</thead>
  <tbody>...</tbody>
</table>
A caption can be positioned anywhere visually with CSS, but the sensible default is to keep it first. The common design need — a heading above a table that also explains the units — is best served by the caption itself rather than by an <h2> sitting outside, because the caption travels with the table when it is moved or repeated.

colgroup is a hook for column-wide styling and for span. It is worth using for exactly one thing: giving a class to a numeric column so alignment is decided once in CSS rather than with a class on every cell. A col applies to the column by position, which is brittle if rows are added, so prefer colgroup with a class and let CSS decide alignment from it.

A rowspan that reaches into another tbody or tfoot is not valid, and the parser will move the cell rather than honour it. If your design needs a label that visually spans several rows, keep it inside one row group — split into separate row groups, or use CSS to draw the line rather than spanning cells across a group boundary.

colspan and rowspan change what a cell is attached to, and headers makes that attachment explicit when the grid is irregular. Reach for scope first because it is cheap and correct; add headers only where scope cannot reach.

4.3 Semantic landmarks

A landmark is a region of the page that a reader can jump to directly. Every element that creates one is an ordinary HTML element — header, nav, main, aside, footer, search, plus article and section when they have accessible names. Choosing them is what makes the landmarks list in a screen reader's menu useful rather than a flat list of five identical "banner" entries.

The landmark elements and what each claims

ElementImplicit roleClaims to be
mainmainThe primary content of this document. Exactly one.
navnavigationA collection of navigation links — major, not every group
headerbanner, only when a direct child of bodySite-wide introductory content
footercontentinfo, only as a direct child of bodySite-wide footer content
asidecomplementaryContent tangential to the main content: a sidebar, a pull-quote
searchsearchA search interface. Wraps the form, not a results list
form with an accessible nameformA named region — useful for a long or multi-step form
section with an accessible nameregionA meaningful subsection, named by its heading

The "direct child of body" qualification is not pedantry. A header inside an article is not the page banner — it is a header for that article, and it has no landmark role at all. Putting it inside main or a div likewise means no banner, and the landmarks list silently loses its most useful entry.

Naming landmarks so they can be told apart

Two nav elements produce two identically named "navigation" entries in the landmarks list, which helps nobody. An accessible name — aria-label or aria-labelledby — turns them into "Primary" and "Footer", and that name is what a reader hears when they jump to it.

<header>
  <a href="/"><img src="/logo.svg" alt="Acme"></a>

  <!-- a header INSIDE main is not a banner, and has no role -->
  <nav aria-label="Primary">
    <ul>
      <li><a href="/catalogue" aria-current="page">Catalogue</a></li>
      <li><a href="/support">Support</a></li>
    </ul>
  </nav>
</header>

<main id="doc-main">
  <h1>Catalogue</h1>
  <section aria-labelledby="s-recent">
    <h2 id="s-recent">Recently added</h2>
    <p>...</p>
  </section>
</main>

<footer>
  <nav aria-label="Footer">
    <ul>
      <li><a href="/terms">Terms</a></li>
      <li><a href="/privacy">Privacy</a></li>
    </ul>
  </nav>
</footer>

A section only becomes a landmark when it has an accessible name. Unnamed, it is a plain container with a heading inside it — which is fine, and usually what you want, because a landmark list with thirty entries is as unusable as one with none. Name the handful a reader is likely to want to jump to: the main sections of a long page, and the distinct regions of a complex one.

The skip link, which is what the landmarks are for

A landmarks list is only useful if the reader can get past the header without traversing it. A skip link is the mechanism, and the two details that make it work are usually the two that get missed: it must be the first focusable thing in the document, and the element it targets must be focusable too, which means adding tabindex="-1" to the main.

<a class="skip" href="#cat-main">Skip to main content</a>
<!-- ... header with dozens of links ... -->
<main id="cat-main" tabindex="-1">

.skip{
  position:absolute;
  left:-9999px;              /* off-screen, still focusable */
  top:0;
  padding:.75rem 1rem;
  background:var(--brand);
  color:var(--brand-ink);
  border-radius:var(--radius);
}
.skip:focus{
  left:.5rem;                /* brought into view only on focus */
  z-index:10;
}
/* main must not draw a focus ring when reached by a skip link */
main:focus{ outline:none; }
Moving the element off-screen with left:-9999px rather than display:none or visibility:hidden is deliberate. Both of those remove the element from the accessibility tree and take it out of the tab order, so the skip link stops existing. The tabindex="-1" on the target is equally deliberate: without it the browser scrolls but does not move focus, and the reader's next keystroke continues from the header they just tried to escape.

For a very long page, add a table of contents as a named nav near the top. Combined with one main and a skip link, a reader can reach any chapter of this guide in one keystroke without ever scrolling past the header.

Landmarks are a table of contents that a screen reader builds for you. Choose the element that names the region, give each landmark an accessible name when there is more than one, and make sure a skip link exists — otherwise the landmarks list is an index to a page you cannot get into quickly.

5 · Forms & Native Validation

5.1 The form element and input types5.2 Labels, fieldset and legend5.3 Select, textarea and button5.4 Native validation and the constraint API5.5 autocomplete

Chapter five covers building forms with the correct input types, labelled controls and built-in validation. You will see that most checks run natively in the browser with zero JavaScript. Well-formed forms are faster to fill in, produce better data, and are usable with a keyboard and screen reader.

Forms are how users send data to your server. Modern HTML gives you the input types, validation rules and autocomplete of a full form framework, natively.

5.1 The form element and input types

A form is a set of controls plus a description of where the data should go. The description part is the half that is usually forgotten: a form that does not say where it submits, in what format, and what happens next is a form that works until the day it needs to be changed.

The form element and its three submission attributes

form takes an action — the URL that receives the data — and a method — get or post. They are not interchangeable, and the choice is not a matter of taste.

MethodData travels asGoes in the URL barUse for
getA query stringYesSearching, filtering, anything the reader should be able to bookmark or share
postThe request bodyNoCreating or changing anything, and anything with a password
<!-- bookmarkable, shareable, and safe to be cached -->
<form action="/catalogue" method="get" role="search">
  <label for="q">Search products</label>
  <input id="q" name="q" type="search">
  <button type="submit">Search</button>
</form>

<!-- creates something; never a password in a query string -->
<form action="/accounts" method="post">
  <label for="email">Email</label>
  <input id="email" name="email" type="email" autocomplete="email" required>
  <button type="submit">Create account</button>
</form>
A post form that a reader refreshes will ask them to resubmit, and if the handler is not idempotent that creates a second record. For anything a reader can trigger twice, handle it properly at the server — a token, an idempotency key, or a redirect-after-post. No client-side attribute prevents this.

The third attribute worth knowing is enctype, which controls the format of the body. Its default, application/x-www-form-urlencoded, is fine for ordinary fields. multipart/form-data is required for any file upload, and is also what lets a browser send a form with several files under one name.

input: one element, twenty types

input is a void element whose behaviour comes entirely from type. The type decides the keyboard a mobile device shows, the validation rules applied, the picker that appears, and what the value looks like when submitted. Choosing the right type is the single highest-value decision on a form, because it gets the keyboard, the validation and the accessibility semantics right at once.

emailEmail with @ and .Validates shape onlyAccepts a@b, which has no domain — validate further if it matters

<!-- a reference code with a letters-and-digits keypad -->
<label for="ref">Reference</label>
<input id="ref" name="ref" type="text"
       inputmode="text" pattern="[A-Z]{2}-d{4}"
       maxlength="7" autocapitalize="characters">

<!-- a quantity: the right keyboard and real constraints -->
<label for="qty">Quantity</label>
<input id="qty" name="qty" type="number"
       min="1" max="99" step="1" value="1" required>

The type attribute is not a style choice — it decides the keyboard, the validation and the semantics together. Spending a minute choosing the right type removes most of the JavaScript a hand-validated form would otherwise need.

5.2 Labels, fieldset and legend

Every control needs a label, and the connection between them must be made with for and id. That is not an accessibility nicety: an unlabelled input is announced as "edit text, blank" and a reader has no way to know what to type into it. It also breaks click-to-focus, which is the behaviour people expect from a label.

Three ways to label, and only two are good

<!-- 1. explicit: the only form that survives being moved in the DOM -->
<label for="email">Email address</label>
<input id="email" name="email" type="email">

<!-- 2. wrapping: fine for a checkbox, where the label IS the click target -->
<label>
  <input type="checkbox" name="terms" required>
  I accept the terms of service
</label>

<!-- 3. never: the placeholder is not a label -->
<input type="text" placeholder="Email address">
A placeholder disappears the moment the reader types, it is usually too low in contrast to read, it is announced inconsistently or not at all by screen readers, and browsers do not offer it to a reader who revisits a filled field. Use it only for a format hint that the label cannot express, such as placeholder="dd/mm/yyyy" next to a label that already says "Date of birth".

Groups: fieldset and legend

Related checkboxes and radios go in a fieldset with a legend. The legend is the group's name, and it is what makes the individual labels meaningful — "Allow marketing email" is ambiguous on its own and unambiguous as part of "Email preferences".

<fieldset>
  <legend>Email preferences</legend>

  <label>
    <input type="checkbox" name="pref" value="product">
    Product updates
  </label>
  <label>
    <input type="checkbox" name="pref" value="offers">
    Offers and discounts
  </label>
  <label>
    <input type="checkbox" name="pref" value="security">
    Security alerts   <!-- required, and cannot be opted out of -->
  </label>
</fieldset>

<fieldset>
  <legend>Plan</legend>
  <label>
    <input type="radio" name="plan" value="free" checked>
    Free
  </label>
  <label>
    <input type="radio" name="plan" value="pro">
    Pro
  </label>
</fieldset>

Radios are grouped by a shared name, and that name is what makes them mutually exclusive — two radios with different names are simply two radios. The group needs no JavaScript, and the fieldset plus legend is what tells a screen reader that "Free" and "Pro" are alternatives rather than two unrelated questions.

Making the label connection robust

The for/id pair has one failure mode: the ids must be unique in the document, and forms on the same page easily collide if the id was copied from a template. It is worth having a convention that makes collisions impossible rather than checking by eye.

<form action="/accounts" method="post">
  <label for="acct-name">Full name</label>
  <input id="acct-name" name="name" autocomplete="name" required>

  <label for="acct-email">Email</label>
  <input id="acct-email" name="email" type="email" autocomplete="email" required>

  <label for="acct-pass">Password</label>
  <input id="acct-pass" name="password" type="password"
         autocomplete="new-password" minlength="12" required>
</form>
Prefix the ids with the form's purpose — acct-name rather than name — and the same form can appear twice on a page without either copy breaking. It costs four characters per field and removes an entire class of bug.

Describing a field beyond its label

Three attributes extend a label, and all three should be wired to the control with aria-describedby rather than left floating. A hint, an error message and an example are all content the control needs; putting them in a paragraph next to it does not associate them with it.

<label for="pw">Password</label>
<span id="pw-hint" class="hint">At least 12 characters. A passphrase of four
  unrelated words is stronger than one word with a 9 on the end.</span>
<input id="pw" name="password" type="password"
       aria-describedby="pw-hint" autocomplete="new-password">

<!-- the error is also described by, and referenced with aria-invalid -->
<label for="pw2">Confirm password</label>
<span id="pw2-err" class="error" role="alert">The passwords do not match.</span>
<input id="pw2" name="password2" type="password"
       aria-invalid="true" aria-describedby="pw2-err" autocomplete="new-password">

aria-describedby takes a space-separated list of ids, so a control can be described by a hint and an error at once — which is exactly the state after a failed submission. And the label does not need the hint: it is already the accessible name, and adding the hint to the name would make the reader hear the whole paragraph before they could type.

Label every control with for and id, wrap related checkboxes and radios in a fieldset with a legend, and wire hints and errors through aria-describedby. Those three rules cover most of what a form review finds.

5.3 Select, textarea and button

Three elements cover every choice a form can offer: select for a list of options, textarea for multi-line text, and button for the action. Each has one behaviour that surprises people — what happens on submit, how a selected option is read, and what a button is when it is inside a form.

select: one selection or many

select defaults to a single-choice drop-down. multiple changes it to a list box where the reader holds a modifier to select more than one, and the submitted value is then a list — the server receives repeated parameters, not one joined string.

<label for="country">Country</label>
<select id="country" name="country" required>
  <option value="" selected disabled>Choose one</option>
  <option value="GB">United Kingdom</option>
  <option value="DE">Germany</option>
  <option value="JP">Japan</option>
</select>

<label for="langs">Languages you read</label>
<select id="langs" name="langs" multiple size="4">
  <option value="en">English</option>
  <option value="de">German</option>
  <option value="ja">Japanese</option>
</select>
<!-- submitted as: langs=en&langs=de -->
Attribute on optionMeaningPractical use
valueWhat is submittedAlways set it. The default is the option's text, which changes when you reword it
selectedPreselectedOnly on a single-choice select — with multiple put it on every default
disabledNot selectableFor a "choose one" placeholder, and it stops a default being submitted by accident
labelA different display labelLets you show "Germany (Deutschland)" while submitting DE
optgroupGroups options under a labelEssential for a country list of any length
<label for="place">Delivery address</label>
<select id="place" name="place">
  <optgroup label="United Kingdom">
    <option value="uk-eng-lon">London</option>
    <option value="uk-sct-edi">Edinburgh</option>
  </optgroup>
  <optgroup label="Germany">
    <option value="de-be-ber">Berlin</option>
    <option value="de-by-muc">Munich</option>
  </optgroup>
</select>

textarea and the attributes it needs

textarea takes its initial value as element content rather than an attribute, which is unusual and easy to get wrong. Two consequences follow: the closing tag is mandatory, and any whitespace between the tags becomes part of the value — which is why the opening tag must butt straight up against the first character.

<label for="bio">Short biography</label>
<textarea id="bio" name="bio" rows="5" cols="40"
          maxlength="500" required
          placeholder="Two or three sentences is plenty."></textarea>
<small id="bio-count">0 / 500</small>

<!-- wrong: the newline and the spaces become part of the value -->
<textarea id="x" name="x">
  starts with whitespace
</textarea>

rows and cols set the visible size only; they are presentational, and on a phone the field will grow to fit the viewport regardless. To stop a layout shift while the reader types, set a min-height in CSS and let the field scroll rather than resize.

button, and the three types

A button inside a form submits it by default. That single default is the cause of most unexpected submissions, because a button added for layout quietly becomes the submit button.

<form action="/pay" method="post">
  <button type="submit">Pay now</button>      <!-- sends the form -->

  <button type="reset">Clear</button>          <!-- restores defaults -->

  <!-- type="button": does nothing but what its script does.
       Outside a form this is the default anyway, which is why it must
       be written explicitly inside one. -->
  <button type="button" onclick="preview()">Preview</button>
</form>
Set type explicitly on every button inside a form, including the one you meant to submit. It costs eight characters per button and removes the most common class of "I clicked the wrong thing" bug in forms. Buttons outside a form default to type="submit" too, so they need the attribute just as much.

A button and a link are different things and the difference is not cosmetic. A button performs an action on the current page and is announced as a button; an link navigates and is announced as a link. It is announced because a reader can then predict it: a button does something here, a link takes me somewhere. Making a "Save" button an anchor means adding Enter and Space handling and a role by hand, and it will still be announced as a link.

Never put a <a> with href="#" where a button belongs. It navigates to the top of the page, it is announced as a link, it cannot be triggered with Space, and it puts a real entry in the history. If it goes nowhere, it is a button; if it goes somewhere, it is a link with a real href.

Always submit a stable value from each option, group long option lists with optgroup, and type every button explicitly. Those three habits remove the majority of what goes wrong with form controls.

Browsers can validate a form without a line of JavaScript. The constraint API exposes the same rules the browser uses when it draws the little speech bubble, so a script can read them, add its own, and display the result in your own words without reimplementing any of it.

pattern is anchored for you. A pattern of [A-Z]{2}-d{4} already means "the whole value must match" — you do not write ^ and $, and if you do they are ignored. It is also worth knowing that the browser's built-in message is untranslatable and says nothing useful about why the value was rejected, which is the reason to write your own.

<label for="postcode">Postcode</label>
<input id="postcode" name="postcode" type="text"
       pattern="[A-Z]{1,2}d[A-Zd]? d[A-Z]{2}"
       title="A UK postcode, for example SW1A 1AA"
       autocapitalize="characters" required>

<label for="when">Start date</label>
<input id="when" name="when" type="date"
       min="2026-01-01" max="2026-12-31" required>

<label for="qty">Quantity</label>
<input id="qty" name="qty" type="number" min="1" max="99" step="1" required>

Reading validity from script

Every control is a HTMLInputElement and therefore a ValidityState. The properties are read-only and always present, so you test them rather than checking for undefined, and validationMessage gives the browser's own message for the first failing rule.

<script>
  const form = document.getElementById("signup");

  // checkValidity() reports without showing the browser's bubble
  // reportValidity() shows it as well as reporting
  form.addEventListener("submit", (e) => {
    if (!form.checkValidity()) {
      e.preventDefault();
      const bad = form.querySelector(":invalid");
      if (bad) bad.focus();          // move the reader to the problem
    }
  });

  // per-field, on blur rather than on every keystroke
  const email = form.elements.email;
  const hint  = document.getElementById("email-hint");

  function describe(el) {
    const v = el.validity;
    if (v.valid)  return "";
    if (v.valueMissing) return "An email address is required.";
    if (v.typeMismatch) return "That does not look like an email address.";
    if (v.tooShort)     return "At least " + el.minLength + " characters.";
    return el.validationMessage;      // the browser's own fallback
  }

  email.addEventListener("blur", () => {
    const msg = describe(email);
    hint.textContent = msg;
    email.setAttribute("aria-invalid", msg ? "true" : "false");
  });
</script>
Validate on blur, not on input. Telling someone their email is invalid while they are still typing the first character is noise; validating when they leave a field lets them finish. Re-validate on input only once the field has already been marked invalid, so the error can clear as soon as it is fixed.

Custom messages and the ones you cannot express

setCustomValidity replaces the browser's message with your own, which is how you report a rule the constraint attributes cannot express — an email already registered, a card number that fails a checksum, a date that must be in the future. The browser's bubble then shows your text instead.

<script>
  // A rule no constraint attribute can express
  async function checkEmailTaken(email, taken) {
    if (taken.has(email.trim().toLowerCase())) {
      email.setCustomValidity("That email address is already registered.");
    } else {
      email.setCustomValidity("");   // must be cleared, or it sticks forever
    }
  }

  // setCustomValidity("") is the reset. Forget it and the control stays
  // invalid no matter what the reader types.
  email.addEventListener("input", () => email.setCustomValidity(""));
</script>
Native validation is a convenience, not a control. Every rule must be enforced again on the server, because the request can be replayed with the attributes removed. Treat required and pattern as the first line of a friendly interface, and the server as the only line that matters.

The constraint attributes give you validation with no JavaScript; the ValidityState API lets you read the same rules to display them in your own words; and setCustomValidity covers what no attribute can express. The server still has to check everything.

5.5 autocomplete

autocomplete is a hint that tells the browser which field of a stored profile this control is, so a reader fills in a form they have filled in before. It is one line of markup per field and it removes the largest single source of form abandonment, because typing an address is tedious in a way that typing a password is not.

The tokens, and why the name matters

The value is a space-separated list. The one that matters most is name, and it is what lets the browser fill a shipping address and a billing address separately rather than offering the same value twice.

       autocomplete="one-time-code" pattern="d{6}"
       maxlength="6" required>

<label for="np">New password</label>
<input id="np" name="new_password" type="password"
       autocomplete="new-password" minlength="12" required>

autocomplete="one-time-code" is the highest-value token on this list and the most often left off. Without it the browser treats the field as an ordinary text box, and a reader signing in with two-factor has to read a code off one device and type it on another on every single sign-in. With it, the code is offered directly.

Use autocomplete="off" only where a field genuinely must not be filled — and be suspicious of that. Browsers largely ignore off on login and payment forms now, deliberately, because a form whose fields never fill is a phishing signal. For one-time codes, security questions and similar "must be entered fresh" fields the right token is one-time-code or new-password, which is a request rather than a prohibition.

Two attributes that are not autocomplete but belong with it: autocapitalize="none" and spellcheck="false" on a username field. Without them the browser capitalises the first letter and underlines half the value in red, and a reader who does not notice will submit a username that does not exist.

Name every field with the token that describes it, prefix with a section- token when the same kind of field appears twice, and add one-time-code to your two-factor input. It is the cheapest conversion improvement a form can have.

6.1 audio and video

audio and video are the same element with a different default. Both take src, both can take nested source elements, and both need controls or they render as nothing at all. What differs is what they refuse to do without being asked.

controls is not optional

<video controls width="640" height="360">
  <source src="/media/intro.webm" type="video/webm">
  <source src="/media/intro.mp4" type="video/mp4">
  Your browser cannot play this video.
  <a href="/media/intro.mp4">Download it instead</a>
</video>

<audio controls preload="none" src="/media/theme.mp3"></audio>

Without controls a media element is invisible and has no play button, so the reader needs your own UI and your own keyboard handling. That is a legitimate choice for a background or a custom player, but it is work: Space and the arrow keys, a visible focus state, a transcript, and a way to pause that does not depend on a mouse.

A decorative background video should carry aria-hidden="true" and tabindex="-1". It is announced to a screen reader as a video with no content and sits in the tab order as a focusable stop that does nothing, which is exactly the kind of thing a reader does not need in their way.

Controlling it from script

The JavaScript API is a media element with methods rather than properties, and almost every one of them returns a promise. The pattern that catches people is play(): it rejects if autoplay was blocked, and an unhandled rejection there shows up as a console error on a page that looks fine.

<script>
  const v = document.getElementById("hero");

  // play() rejects when the browser blocks autoplay. Always catch it.
  v.play().catch(() => {
    // blocked: show a poster and a play button instead of failing silently
    v.controls = true;
  });

  // currentTime is writable, so a scrubber is a setter, not an event handler
  slider.addEventListener("input", () => {
    v.currentTime = slider.value;
  });

  // volume is 0 to 1; muted is separate state
  v.volume = 0.4;
  v.muted = false;

  // the events you actually need
  v.addEventListener("timeupdate", () => {
    slider.value = v.currentTime;
  });
  v.addEventListener("ended", () => {
    // loop is false, so the video has stopped for good
  });
</script>

Format order is not arbitrary. List the formats from best to worst and the browser takes the first it can play — the type attribute is what lets it skip the rest without downloading them, so a wrong or missing type makes the browser fetch a file it cannot use. WebM or AVIF for video, WebM or Opus in WebM for audio, with MP4 or AAC as the last entry, covers everything.

Give it controls unless you have built a genuinely accessible player, add preload="none" to anything below the fold, and always catch the rejection from play(). The rest is ordinary media handling.

6.2 source and tracks

The source element looks identical in all three places it appears and behaves completely differently in each. Inside audio and video it is a list of alternative files, tried in order until one plays. Inside picture it is a set of conditions, and the first one that matches wins. Getting that difference right is most of what this section is about.

source inside audio and video

Inside a media element, each source is the same content in a different container. The browser picks the first it can play and stops; the type attribute is what lets it decide without attempting a download.

<audio controls preload="metadata">
  <!-- type is what the browser uses to choose; it must be accurate -->
  <source src="/media/track.ogg"  type="audio/ogg; codecs=opus">
  <source src="/media/track.m4a"  type="audio/mp4; codecs=mp4a.40.2">
  <source src="/media/track.mp3"  type="audio/mpeg">
</audio>

<video controls preload="metadata" width="640" height="360">
  <source src="/media/clip.av1"  type="video/mp4; codecs=av01.0.05M.08">
  <source src="/media/clip.webm" type="video/webm; codecs=vp9,opus">
  <source src="/media/clip.mp4"  type="video/mp4; codecs=avc1.42E01E,mp4a.40.2">
</video>

Including the codec in type is more precise and lets the browser skip more: video/webm alone tells it nothing about which codecs are inside, while video/webm; codecs=vp9,opus tells it whether it can actually decode what it would download. Order them best-first, because the browser will not try a later source if an earlier one parses.

If the media element also has a src attribute, the src wins and every source is ignored. The browser only falls back to the child elements when there is no src. Mixing the two is a common cause of "my second format never gets used".

track: captions and the four kinds

A track element attaches timed text to a media element. It is the difference between a video that is usable and one that is not, and for a video with spoken content it is effectively required.

The NOTE block is a comment for the author, not for the reader, and it is how you record what a line should be describing.

source inside picture, which is a different element entirely

Inside picture, a source is a condition, not an alternative encoding of the same file. Each source has a media query and possibly a type, and the browser picks the first whose condition matches — it does not test whether the file can be decoded.

<picture>
  <!-- conditions, evaluated in order; the FIRST match wins -->
  <source media="(min-width: 900px)" srcset="/img/hero-wide.avif">
  <source media="(min-width: 600px)" srcset="/img/hero-mid.avif">
  <source srcset="/img/hero-small.avif">

  <!-- a different crop for a dark-mode reader -->
  <source media="(prefers-color-scheme: dark)" srcset="/img/hero-dark.avif">

  <!-- the mandatory fallback -->
  <img src="/img/hero.jpg" width="1600" height="700"
       alt="The workshop at dawn">
</picture>
Order matters and the order is counterintuitive. In picture the first matching source wins, so the most specific query must come first and the catch-all last. Putting the generic <source srcset="…"> at the top makes every query below it unreachable, and the page silently serves the wrong image at every width.

In a media element, source is a fallback list and the browser tries each file until one plays. In picture, source is a condition and the first match wins. Same tag, same attributes, opposite selection logic.

6.3 picture: art direction

picture is the one element where you choose the file rather than letting the browser choose. img and srcset present the same picture at different sizes; picture can present a different picture — a different crop, a different colour treatment, a different format entirely — decided by a media query, a format capability, or both.

When to use picture and when to use srcset

A smaller file on a small screensrcset on imgSame image, less data. This is the common case
A different crop at a different aspect ratiopictureThe pixels differ, not just the size
A different image for a dark-mode readerpictureThe content is chosen by preference, not by width

<!-- srcset alone: one picture, several sizes -->
<img src="chart-800.jpg"
     srcset="chart-400.jpg 400w, chart-800.jpg 800w, chart-1600.jpg 1600w"
     sizes="(max-width: 600px) 100vw, 800px"
     width="1600" height="900"
     alt="Revenue chart">

<!-- picture: a genuinely different crop for a wide viewport -->
<picture>
  <source media="(min-width: 900px)" srcset="/img/panorama.avif"
          type="image/avif">
  <source media="(min-width: 900px)" srcset="/img/panorama.jpg"
          type="image/jpeg">
  <source srcset="/img/portrait.avif" type="image/avif">
  <img src="/img/portrait.jpg" width="900" height="1200"
       alt="The bench, photographed from above">
</picture>

Selection order, which is the opposite of what you expect

The browser walks the source children in document order and takes the first one whose media matches and whose type it can decode. It does not pick the best match, and it does not fall through to a later source because the first one was too large. So the most specific condition goes first and the catch-all goes last.

<picture>
  <!-- WRONG: the catch-all matches everything, so nothing below
       it is ever reached -->
  <source srcset="/img/small.jpg">
  <source media="(min-width: 900px)" srcset="/img/large.jpg">

  <!-- RIGHT: most specific first, fallback last -->
  <source media="(min-width: 900px)" srcset="/img/large.jpg">
  <source srcset="/img/small.jpg">
</picture>
A <source> with no media and no type matches every browser, so placing it first makes every condition below it dead. This is the single most common picture bug and it fails silently: the page renders, with the wrong image, at every width.

Format negotiation, and why order it this way

<picture>
  <!-- AVIF first: smallest, and every current browser can decode it -->
  <source srcset="/img/hero.avif" type="image/avif">
  <!-- WebP second: universally supported, larger than AVIF -->
  <source srcset="/img/hero.webp" type="image/webp">
  <!-- the img inside is the mandatory fallback -->
  <img src="/img/hero.jpg" width="1600" height="700"
       alt="The workshop at dawn">
</picture>

There is no need to duplicate a source per format per breakpoint, because srcset works inside a source. One source per format, each carrying its own srcset and sizes, covers every width for that format.

The <img> inside picture is mandatory and is what any browser that matches no source uses — so it must be a file every browser can render, not an experimental format. Putting AVIF only in the sources and a WebP in the img gives you a working fallback with one file rather than two.

Use srcset when it is the same picture at different sizes and picture only when it is a different picture. Inside picture the first matching source wins, so order from most specific to catch-all and keep the img a universally safe file.

6.4 iframe

An iframe embeds a whole separate document. That is why it is powerful and why it is a common source of trouble: you get a document, and with it a viewport, a history entry, a document title, a set of cookies and a script context you did not write.

sandbox: the attribute that matters most

sandbox restricts what the framed document may do. The default value — sandbox with no tokens — is maximally restrictive: no scripts, no forms, no same-origin access. Every token is a capability you deliberately give back, which is the correct order to think in.

TokenGrantsNeeded for
allow-scriptsJavaScript runsAlmost any interactive embed
allow-same-originSame-origin, so it can reach the parent's DOM and storageOnly when the frame and the parent must share state
allow-formsForm submissionAn embedded sign-in
allow-popupsOpening new windowsA payment provider that redirects in a new tab
allow-top-navigationNavigating the parentRarely. Almost always a sign of a redirect you do not control
allow-modalsalert and friendsUsually a sign the framed page is not built for embedding
allow-presentationFullscreenA player the reader may want fullscreen
allow-popups-to-escape-sandboxNew windows are unsandboxedAlmost never
<!-- maximally restrictive: scripts and forms both off -->
<iframe src="/read-only-report" width="100%" height="600"
        title="Quarterly report"></iframe>

<!-- an interactive embed, still without same-origin -->
<iframe src="https://player.example.com/embed/abc"
        title="Installation walkthrough"
        width="640" height="360"
        loading="lazy" referrerpolicy="strict-origin"
        allow="fullscreen; picture-in-picture; encrypted-media"
        allowfullscreen
        sandbox="allow-scripts allow-presentation"></iframe>
allow-scripts together with allow-same-origin on a same-origin frame effectively removes the sandbox, because the framed script can reach the parent DOM and reload itself without the sandbox. If you need both, the framed content must be on a different origin from the parent — the sandbox is a boundary between origins, and same-origin means there is nothing to separate.

title, loading and referrerpolicy

title is mandatory in practice. A frame without one is announced only as "frame", so a reader moving through the page by frame has no idea what they have landed in — and this is one of the most commonly missed attributes in the whole language.

<!-- a payment provider, which needs to redirect the parent -->
<iframe src="https://checkout.example.com/session/abc"
        title="Secure payment"
        width="100%" height="520"
        loading="lazy"
        referrerpolicy="strict-origin-when-cross-origin"
        sandbox="allow-scripts allow-forms allow-same-origin allow-popups"
        allow="payment"></iframe>

<!-- a lazy frame: not fetched until it is near the viewport -->
<iframe src="/map/embed"
        title="Office location map"
        loading="lazy"
        referrerpolicy="no-referrer"
        width="100%" height="300"></iframe>

loading="lazy" is worth setting on any frame that is not above the fold. An embedded map, a video player and a comment widget all cost a document, a set of requests and a JavaScript context, and none of it is needed before the reader scrolls there.

Third-party frames and what they cost

An embedded third-party frame is a separate browsing context: it cannot read your page, but it can see that the reader arrived, take a cookie, run a script and add to the total JavaScript on the page. It also creates a history entry per navigation inside it.

<!-- consent-gated: nothing is requested until the reader agrees -->
<div id="map-consent">
  <p>This map loads from an external service and will set a cookie.</p>
  <button type="button" id="map-accept">Show the map</button>
</div>

<script>
  document.getElementById("map-accept").addEventListener("click", () => {
    const frame = document.createElement("iframe");
    frame.title = "Office location map";
    frame.src = "https://maps.example.com/embed?id=42";
    frame.loading = "lazy";
    frame.referrerPolicy = "strict-origin-when-cross-origin";
    frame.setAttribute("sandbox", "allow-scripts allow-same-origin");
    document.getElementById("map-consent").replaceWith(frame);
  }, { once: true });
</script>

Setting src only after consent is the difference between a consent banner that means something and one that does not — the frame simply is not in the document, so nothing has been requested. Prefer allow="..." over granting blanket permissions, and scope it to the features the embed actually uses.

For an embedded document you control, there is a better answer than sandbox: allow policies narrow what the frame may request — camera, clipboard, geolocation, payment — so an embed that only needs a clipboard cannot escalate to the camera.

Always set title. Start from sandbox with nothing and add back only what the embed needs, add capabilities through allow rather than blanket permissions, and set loading="lazy" on anything below the fold.

6.5 canvas and SVG

Canvas and SVG are two ways to draw, and the choice between them is not about which looks better — it is about whether the result is a picture or a set of objects. That single distinction determines whether it can be styled, scaled, searched, and read by assistive technology.

Canvas, and the accessibility rule that comes with it

A canvas element with fallback content is announced by its contents, and with script enabled those contents are never rendered. So the fallback is invisible to exactly the readers who most need it — which is why a canvas that carries information needs an equivalent in text beside it, not inside it.

<!-- the canvas carries the picture; the table carries the data -->
<figure>
  <canvas id="chart" width="600" height="320"
          role="img"
          aria-label="Bar chart: signups rose from 40 in January to 180 in June">
    Signups by month: January 40, February 55, March 70, April 95,
    May 130, June 180.
  </canvas>
  <figcaption>Monthly signups, January to June.</figcaption>
</figure>

<script>
  const c = document.getElementById("chart");
  const ctx = c.getContext("2d");

  // handle high-density displays, or everything is drawn too small
  const dpr = window.devicePixelRatio || 1;
  c.width  = 600 * dpr;
  c.height = 320 * dpr;
  ctx.scale(dpr, dpr);              // then work in CSS pixels from here

  ctx.fillStyle = "#00d1ff";
  ctx.fillRect(20, 200, 60, 100);
  ctx.fillRect(100, 140, 60, 160);
  ctx.fillRect(180, 60, 60, 240);
</script>
Canvas coordinates are device pixels but your drawing code thinks in CSS pixels, and on a display with a pixel ratio above 1 that makes everything appear at half size or smaller. Set canvas.width and canvas.height to the CSS size multiplied by devicePixelRatio, then call ctx.scale(dpr, dpr) once and draw in CSS pixels. Forgetting this is the most common canvas bug.

Canvas has no accessibility tree of its own. If it draws interactive controls, each one needs a real focusable element positioned over it — which means you have reimplemented HTML, without the semantics. That is the point at which a canvas is the wrong tool.

Reach for SVG when the drawing is made of shapes, styles, scales or needs to be accessible. Reach for canvas when you are drawing thousands of things per frame — a chart with 200 points, a particle field, an image filter — and provide the data in text alongside it.

7.1 Semantic-first, and alt text rules

The accessibility argument for semantic HTML is not that semantic HTML is more accessible. It is that no attribute you can add makes a nameless div into a button a screen reader will announce as a button. Roles can approximate that, they cannot reconstruct the keyboard behaviour, the focus behaviour and the state that come with the real element. Choosing the right tag is nearly all of accessible component work.

Semantic first, ARIA second

The first rule of ARIA is that you should not use ARIA when a native element will do. The rule of thumb behind it: an element's role is its semantics, and ARIA only edits the announcement. Adding role="button" to a div changes what is spoken; it does not make the element focusable, does not respond to Space, does not fire on Enter, does not appear in the form's list of controls, and does not get the disabled, pressed and expanded states a real button has.

<!-- native: everything works, and nothing to keep in sync -->
<button type="button" aria-expanded="false" aria-controls="panel">
  Filters
</button>

<!-- ARIA imitation: focusable by hand, Space and Enter by hand,
     state by hand, and broken the moment any of it is forgotten -->
<div role="button" tabindex="0"
     aria-expanded="false" aria-controls="panel">Filters</div>
The first rule of ARIA is: do not use ARIA if a native element gives you the behaviour you need. The second rule is: if you do use ARIA, take on the behaviour too — a role="button" that ignores Enter and Space is worse than no role, because it has announced itself as a button and then not been one.

The four alt cases, restated as a decision

Deciding alt is a question about what the reader loses if the image is missing. An image carrying information they would otherwise not have needs a description. An image that repeats nearby text needs an empty alt, because a screen reader already read the text. An image inside a link needs an empty alt, because the link text names the destination. A decoration needs an empty alt. Only the first case has content in it, and it is the minority of images on most pages.

<!-- information: describe it -->
<img src="/img/revenue.png" width="640" height="360"
     alt="Bar chart: revenue rises from 12k in 2023 to 47k in 2026">

<!-- decoration: empty alt, NOT a missing alt -->
<img src="/img/divider.svg" alt="">

<!-- repeats text the reader already has -->
<figure>
  <img src="/img/logo.svg" alt="">
  <figcaption>Acme, founded 2011</figcaption>
</figure>

<!-- inside a link: the link text names it -->
<a href="/" aria-label="Acme home">
  <img src="/img/logo.svg" alt="">
</a>

<!-- meaningful: short alt plus the detail in text nearby -->
<img src="/img/assembly.png" width="800" height="500"
     alt="Cutaway diagram of the assembly">
<p>The rotor sits inside the housing; release the retaining clip first.</p>
A missing alt is not the same as an empty one. With no attribute at all, some screen readers fall back to announcing the file name — "revenue-d2f1a3.png" — which is worse than nothing. The attribute should be present on every image, and empty when the image carries no information.

Accessible names, in priority order

A control's accessible name is computed, and the sources are tried in a defined order. Knowing the order explains why two controls with visibly identical labels behave differently.

PrioritySourceExample
1aria-labelledbyPointing at visible text — the name is the visible label, so it always matches
2aria-labelA string that is not visible anywhere
3Native, from content or attributes<label for>, alt, <caption>, <legend>, title
4Content of the elementThe text inside a button or a link
5titleA tooltip, and the last resort — it is unreliable and unavailable on touch
<!-- best: the visible text IS the name -->
<button aria-labelledby="filter-label" aria-expanded="false">
  <span id="filter-label">Filter results</span>
  <svg aria-hidden="true">...</svg>
</button>

<!-- fine when there is no visible label to point at -->
<button aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>

<!-- wrong: a visible "Close" and an unconnected aria-label of "Dismiss" -->
<button aria-label="Dismiss">Close</button>

That last case is the "label in name" requirement: if a control shows visible text, its accessible name must contain that text. Voice control users say what they see, so a button that reads "Close" and is announced as "Dismiss" simply does not respond.

Pick the element that carries the semantics, give every image an alt that is empty unless the image is information, and let the visible text be the accessible name. Those three rules cover most of what an accessibility audit finds.

7.2 Keyboard order and tabindex

A keyboard user reaches every interactive element in an order, and that order is whatever the document says it is. Tab order therefore is not a detail — it is the navigation model. Three attributes affect it, and one of them is a well-intentioned mistake that breaks the page in a way that is hard to see.

What determines the tab order

In a correctly written document the order is simply the order of the markup. That is the whole design: put the header before the main content and the skip link before the header, and the keyboard follows the page.

<!-- the tab order here is: skip link, logo, nav links, main content -->
<body>
  <a class="skip" href="#main">Skip to content</a>
  <header>
    <a href="/"><img src="/logo.svg" alt="Acme"></a>
    <nav><a href="/catalogue">Catalogue</a></nav>
  </header>
  <main id="main" tabindex="-1">...</main>
</body>

tabindex, and the one value that is always safe

tabindex takes a number. Positive values are the source of nearly all keyboard problems: they create a second, higher-priority tab order layered on top of the document, and the result is that Tab jumps around the page in a sequence that matches nothing on screen. Once a positive value exists anywhere on the page, the whole page is affected.

ValueIn the tab order?When to use it
0Yes, in document orderOnly to make a non-focusable element focusable — usually the skip link's target. Rarely needed elsewhere
PositiveYes, but first, before everythingAlmost never. Breaks the relationship between order and position
-1No, but programmatically focusableThe skip link target, a dialog, a menu that is closed. Focusable without being a tab stop
<!-- correct: focusable for script, skipped by Tab -->
<main id="main" tabindex="-1">

<!-- correct: focusable and a tab stop, nothing else needed -->
<div class="roving-tabindex" role="toolbar"
     aria-label="Text formatting">
  <button tabindex="0">Bold</button>
  <button tabindex="-1">Italic</button>
  <button tabindex="-1">Underline</button>
</div>

<!-- wrong: Tab now goes to 1, then 5, then 2, then 3 -->
<button tabindex="1">Bold</button>
<button tabindex="5">Italic</button>
<button tabindex="2">Underline</button>

The roving tabindex in that toolbar is the pattern for any composite widget — toolbars, tab lists, menus, radio groups. The whole group is one tab stop; the arrow keys move within it, and exactly one item holds tabindex="0" at a time. A keyboard user reaches the toolbar in one press instead of four, and the arrow keys are what they expect once inside.

Never use a positive tabindex to fix "the order is wrong". The order is wrong because the markup is in the wrong order, and a positive value hides that by imposing a second order that has to be maintained by hand forever — across every page, every state and every future change.

The keys a custom control must handle

If you build something that behaves like a button, you inherit the keyboard contract. A native button gets it for free; anything else needs all of it.

<div role="button" tabindex="0"
     aria-pressed="false" id="fav">Favourite</div>

<script>
  const fav = document.getElementById("fav");

  function toggle() {
    const on = fav.getAttribute("aria-pressed") === "true";
    fav.setAttribute("aria-pressed", String(!on));
    fav.classList.toggle("is-on", !on);
  }

  // Enter and Space both activate a button. Click alone is not enough.
  fav.addEventListener("keydown", (e) => {
    if (e.key === "Enter" || e.key === " ") {
      e.preventDefault();      // Space would otherwise scroll the page
      toggle();
    }
  });
  fav.addEventListener("click", toggle);
</script>

The missing preventDefault on Space is the classic symptom: the control activates and the page scrolls. And the missing aria-pressed means the toggle never announces its state, so a screen reader user toggles it without learning whether it worked.

Leave the order to the document, use tabindex="-1" for anything script-focusable, never use a positive value, and make a roving tabindex for any composite widget. If a control has a role, it owes the reader the keyboard behaviour that role implies.

Naming, and when not to

Name a landmark when there is more than one of its kind, and leave the rest unnamed. The failure mode in both directions is the same — a list too long to be useful or too short to be useful.

<!-- two of a kind: name both -->

  <h2 id="s-install">Installation</h2>
  ...
</section>

<!-- a container with no reason to jump to: leave it unnamed -->
<section>
  <h2>Notes</h2>
  ...
</section>
Prefer aria-labelledby pointing at the heading that is already visible over aria-label with the same words typed out twice. The visible label then cannot drift out of sync with the name, which is the usual fate of a duplicated string.

The skip link, done properly

<a class="skip" href="#main">Skip to main content</a>

<style>
  .skip{
    position:absolute; left:-9999px;
    padding:.75rem 1rem;
    background:var(--brand); color:var(--brand-ink);
    border-radius:var(--radius); z-index:100;
  }
  .skip:focus{ left:.5rem; top:.5rem; }

  /* suppress the ring when main is reached by script, keep it otherwise */
  main:focus{ outline:none; }
  main:focus-visible{ outline:2px solid var(--accent); }
</style>
Three details decide whether a skip link works, and all three are usually missing. It must be the first focusable thing in the document, or a reader presses Tab once and is still in the header. The target needs tabindex="-1", or the browser scrolls but focus stays behind. And it must be hidden with a position, not with display:none or visibility:hidden, both of which remove it from the tab order entirely — the skip link then cannot be reached at all.

One main, a banner and a contentinfo outside everything else, every repeated landmark named, and a skip link as the document's first focusable element. That is the whole landmark map, and it takes about ten lines of markup.

What it does do is let you communicate state — what is selected, what has expanded, what is in progress, what just changed — in a way that a sighted reader sees from the styling alone.

aria-live, and the timing that makes it usable

aria-live tells assistive technology to announce changes inside a region. The three values are not interchangeable and choosing wrongly is worse than not announcing at all.

<!-- polite: waits for a pause. Use for anything routine -->
<div role="status" aria-live="polite">
  <!-- 3 results -->
</div>

<!-- assertive: interrupts. Use only when the reader must act now -->
<div role="alert" aria-live="assertive">
  <!-- Session expired. Please sign in again. -->
</div>

<!-- log: a running sequence, announced as it accumulates -->
<div role="log" aria-live="polite" aria-relevant="additions">
  <p>Deployed to staging</p>
</div>

Two rules make this usable. A live region must be in the document before the content changes — a region created at the same moment as its message is often missed entirely. And it should only contain the message: if the region holds the whole page and one line changes, some readers announce everything.

When the content of a live region should not be announced — a live search-results counter a reader can see updating — use aria-live="polite" but put the announcement in a separate visually-hidden element, or use aria-live="off" with an aria-label that includes the current count. What matters is that the change is available to a reader who cannot see it, without stealing focus.

aria-hidden and focusable descendants

Never put aria-hidden="true" on an element that contains something focusable. The element disappears from the accessibility tree, so a screen reader user does not know it is there — but a sighted keyboard user can still Tab to it and focus it, which produces the worst possible outcome: focus on an element the reader has no way of discovering what they are on. aria-hidden and tabindex must be applied together, or not at all.
<!-- wrong: focusable, but not in the tree -->
<div aria-hidden="true">
  <button>Invisible to a screen reader, reachable by Tab</button>
</div>

<!-- right: decorative icon, excluded from both -->
<button aria-label="Close">
  <svg aria-hidden="true" focusable="false">...</svg>
</button>

<!-- right for an off-screen menu that is not open -->
<ul class="drawer" hidden>...</ul>

Use roles to name a custom widget, states to say what is true of it, and aria-live to announce what changed. Keep the live region in the document before the change, and never hide an element a reader can still focus.

7.5 Focus management and colour contrast

Focus is the keyboard user's cursor and the screen reader's reading position. Managing it is the difference between a dialog a reader can escape and one they are trapped in, and between a form that moves them forward and one that throws them back to the top on every validation error.

The focus indicator has to be visible

Removing the outline is the single most common accessibility regression, and it is usually done with a one-line rule that looks harmless on the element it was applied to. The outline must stay unless a replacement is drawn, and the replacement must be at least as visible.

<style>
  /* visible by default */
  :focus-visible{
    outline:2px solid var(--accent);
    outline-offset:2px;
    border-radius:var(--radius);
  }

  /* if you keep a custom ring, do not let it be the only change:
     colour alone fails when the reader cannot distinguish it */
  button:focus-visible{
    outline:2px solid var(--accent);
    outline-offset:2px;
  }

  /* a mouse user should not see a ring on every click */
  button:focus:not(:focus-visible){ outline:none; }
</style>
Never write outline: none with nothing in its place. If the indicator must be subtle, use :focus-visible rather than :focus — it shows the ring for keyboard and programmatic focus while keeping it away from a mouse click, which is what stops people from removing it in the first place.

Focus in a modal dialog

A modal dialog must trap focus while it is open and must return it to whatever opened it when it closes. <dialog>'s showModal() does the trapping, the background inertness and the Escape handling; it does not remember what to focus on close, which is your job.

<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete this project?</h2>
  <p>Everything in it will be removed. This cannot be undone.</p>
  <form method="dialog">
    <button value="cancel">Cancel</button>
    <button value="confirm">Delete</button>
  </form>
</dialog>

<button type="button" id="open">Delete project</button>

<script>
  const dlg = document.getElementById("confirm");
  const openBtn = document.getElementById("open");

  openBtn.addEventListener("click", () => dlg.showModal());

  dlg.addEventListener("close", () => {
    // put the reader back where they were
    openBtn.focus();
    if (dlg.returnValue === "confirm") removeProject();
  });
</script>

Without the close handler, dismissing the dialog drops focus onto the body and the reader has to Tab from the top of the document to find where they were. That single missing line is one of the most disorienting things a dialog can do.

Labelling matters too: aria-labelledby pointing at the dialog's own heading makes it announce "Delete this project?, dialog" rather than "dialog". A native <dialog> opened with showModal() is already inert behind it, so focus cannot escape by Tab and no manual trap is needed.

Focus after a validation failure

The rule is simple and almost always broken: move focus to the first field with a problem. Reloading the page, re-rendering the form, or scrolling to an error summary all leave focus at the top, and a screen reader user then has no way to know an error happened at all.

<form id="signup" action="/accounts" method="post" novalidate>
  <div role="alert" id="form-error" hidden>
    <h2>There is a problem</h2>
    <ul><li><a href="#email">Enter a valid email address</a></li></ul>
  </div>

  <label for="email">Email</label>
  <input id="email" name="email" type="email" required>
  <button type="submit">Create account</button>
</form>

<script>
  form.addEventListener("submit", (e) => {
    if (form.checkValidity()) return;
    e.preventDefault();

    const bad = form.querySelector(":invalid");
    if (!bad) return;

    // focus the field, not the summary: the reader can then just correct it
    bad.focus();
    bad.setAttribute("aria-invalid", "true");
  });
</script>

Offering both — an error summary near the top with links to each field, and focus moved to the first bad field — is better than either. The summary tells a screen reader user how many problems there are before they start; the focus move means they do not have to hunt for the first one.

With novalidate on the form, the browser's own bubbles are suppressed and yours are the only errors shown. Without it, the native bubble appears on top of your styling and the two disagree. Pick one: native validation and checkValidity() for the logic, your own markup for the presentation — and that means novalidate.

Contrast, and the AA thresholds that apply

Both are cheap to fix: use a token that has already been solved for contrast, and make the ring an accent colour at a known thickness.

Use :focus-visible so a ring shows for keyboard focus, return focus to the opener when a dialog closes, move focus to the first invalid field on a failed submit, and check placeholder and focus-indicator contrast against the 4.5:1 and 3:1 bars rather than by eye.

8.1 meta description and canonical

On-page metadata decides how a page is described in a search result, whether two URLs are treated as the same page, and what happens when a page is shared. None of it changes the ranking, and all of it changes the click. This library opens from a disk, so none of it has any effect until the site is served from a domain — at which point it is the cheapest work on the page.

The description, and what it is actually for

<head>
  <title>Native validation and the constraint API — HTML forms</title>
  <meta name="description"
        content="How HTML forms validate without JavaScript: the constraint
                 attributes, the ValidityState API, setCustomValidity, and
                 why the server still has to check everything.">
  <link rel="canonical" href="https://example.test/guides/html#forms">
</head>
FieldLimitWhy
titleAround 60 characters before truncationIt is the clickable line, and it is also the tab and the bookmark name
descriptionAround 155 charactersTruncated beyond that; the rest is never read
Title and descriptionUnique per pageTwo pages with the same title is a duplicate-content signal
The description is not a ranking factor and was never intended to be one — Google generated one automatically for years without it. Write it as a sentence that would make you click, not as a keyword list, and put the distinguishing part first, because that is what survives truncation.

canonical, and the duplicate it is for

A canonical URL tells a search engine which of several URLs is the real one. The cases it is genuinely needed for are specific: a page reachable under several URLs, a print or amp variant, a paginated list, and parameters that do not change the content.

<!-- one page, several URLs: point at the preferred one -->
<link rel="canonical" href="https://example.test/guides/css">

<!-- parameters that do not change the content -->
<link rel="canonical" href="https://example.test/catalogue">
<!-- so ?page=2 and ?sort=price point back at the base -->

<!-- a paginated list: each page is its own content, so each is canonical -->
<link rel="canonical" href="https://example.test/catalogue?page=2">

<!-- the earlier and later pages of a guide -->
<link rel="prev" href="https://example.test/guides/css#box-model">
<link rel="next" href="https://example.test/guides/css#selectors">

Two things canonical does not do. It is a hint, not a command — a search engine may ignore it. And it must be self-referential: pointing a page at a different URL is how you consolidate duplicates, and pointing a page at itself is how you confirm the canonical one.

robots, and indexable against index

<!-- a page that should not be in an index -->
<meta name="robots" content="noindex, nofollow">

<!-- readable, but not linked from (some engines honour this, some do not) -->
<meta name="robots" content="index, nofollow">

<!-- a normal page: this is the default, so you rarely need it -->
<meta name="robots" content="index, follow">

<!-- no archive copy, no snippet -->
<meta name="robots" content="noarchive, nosnippet, noimageindex">
noindex is honoured only if a crawler can read the page. A page blocked in robots.txt cannot be fetched, so its noindex is never seen and it may still appear in results as a bare URL. To keep something out of an index, allow crawling and set noindex; to stop crawlers wasting requests on it, block it — but understand that blocking is not removal.

Write a unique title and a description that earns the click, set a self-referential canonical on every page, and use noindex for pages that should stay out rather than blocking them. All of it only matters once the site is served from a domain.

8.2 Open Graph and Twitter Cards

When a page is pasted into a messaging app, the receiving service fetches the page and reads its metadata to build a card: a title, a description and an image. Two independent vocabularies describe the same thing, both needed because neither service implemented the other's.

Open Graph

<head>
  <!-- the four that decide what a card looks like -->

8.3 Structured data with JSON-LD

Structured data is a small JSON document embedded in the page that states what the page is, so a consumer does not have to guess from the prose. It can produce a richer result in a search engine, and it is the only way to describe something that has no visible representation — an author's credentials, a rating, the relationship between two things.

JSON-LD, and why not microdata

There are three ways to put structured data in a page. Microdata puts attributes on the elements themselves. RDFa uses namespaced attributes and XML vocabulary. JSON-LD puts a script block in head containing a JSON object.

The <script> must be JSON on one side and nothing else. Two rules make it maintainable: emit it from the same source as the page rather than writing it by hand, and validate it. A JSON-LD block is the easiest metadata on the page to break with a content edit and the hardest to notice.

Use JSON-LD in head, describe the article and its chapters with hasPart, finish the breadcrumb at the current page, and validate the JSON before shipping — because a malformed block fails silently.

8.4 preload, prefetch and lazy loading

Three link elements tell the browser to fetch something before it is asked to. They sound interchangeable and are not: each is a promise about when you will need a resource and how much you care if it is slow. Getting them the wrong way round costs bandwidth you did not need to spend.

Which one to use

ElementPriorityUse it when
preloadHighYou will need this resource in the next few hundred milliseconds — the font or the hero image above the fold
prefetchLowThe reader is likely to go to the next page. Almost always a next-page link
prerenderVery lowThe next page is very likely. Downloads and parses; a step beyond prefetch
preconnectMediumYou need a connection and a TLS handshake to a specific origin early
dns-prefetchLowYou only need the hostname resolved. A subset of preconnect
modulepreloadHighAn ES module you know is needed. Also fetches its dependency graph
<!-- the hero image: needed now, so high priority and high urgency -->
<link rel="preload" as="image" href="/img/hero.avif"
      type="image/avif" fetchpriority="high">

<!-- a web font, with the crossorigin the fetch will need.
     Omitting crossorigin makes the preload unused, because the
     font request is CORS and this one would not be. -->
<link rel="preload" as="font" type="font/woff2"
      href="/fonts/inter-var.woff2" crossorigin>

<!-- the origin we will certainly need a module from -->
<link rel="preconnect" href="https://cdn.example.test" crossorigin>

<!-- the next page a reader will probably go to -->
<link rel="prefetch" href="/guides/css" as="document">

<!-- a module we know we need before the parser reaches the script -->
<link rel="modulepreload" href="/js/charts.mjs">
The crossorigin on a font preload is the single most common reason a preload does nothing. Fonts are always fetched in CORS mode, so a preload without the attribute is a separate request that the font request then duplicates — you have made the page slower while trying to speed it up. If a preload does not show as used in the network panel, this is why.

The three ways preloading backfires

<!-- 1. preloading something already in the HTML: a duplicate request -->
<link rel="preload" as="style" href="/assets/site.css">
<link rel="stylesheet" href="/assets/site.css">
   <!-- the stylesheet link already fetches it; the preload adds nothing -->

<!-- 2. preloading with the wrong as/type, so it is discarded -->
<link rel="preload" as="font" href="/fonts/inter.woff2">
   <!-- no type, and no crossorigin: fetched, then thrown away -->

<!-- 3. preloading too much: everything is high priority and
        nothing is. The first render is now waiting on the lot. -->
<link rel="preload" as="image" href="/img/1.jpg">
<link rel="preload" as="image" href="/img/2.jpg">
<link rel="preload" as="image" href="/img/3.jpg">
<link rel="preload" as="image" href="/img/4.jpg">
A preload competes with everything else for bandwidth, so it is not free. Preloading four images that are not above the fold means the four images are fetched before the one that is, and the largest contentful element — the thing that decides how the page is judged — arrives last. Preload at most one or two resources, and only ones needed for the first render.

Lazy loading, and the attributes that help the browser decide

<!-- below the fold: do not fetch until it is near the viewport -->
<img src="/img/section-4.png" width="800" height="450"
     loading="lazy" decoding="async"
     alt="...">

<!-- above the fold: say so explicitly, and never make it lazy -->
<img src="/img/hero.avif" width="1600" height="700"
     fetchpriority="high" decoding="async"
     alt="...">

<!-- an iframe below the fold -->
<iframe src="/player" title="Walkthrough" loading="lazy"></iframe>

<!-- a module that is only needed when the reader interacts -->
<button onclick="import('/js/chart.mjs')">Show chart</button>

loading="lazy" does not merely delay the fetch — it also stops the image being downloaded for readers using Data Saver, and it delays layout because the space is not reserved until the element is near the viewport. Pair it with width and height or the shift comes back. Never apply it to the largest contentful element: lazy-loading the thing the page is judged on makes the judgement worse.

For a module or a heavy component that is only needed on interaction, import() inside the handler is better than any hint — nothing is requested until the reader actually asks, and no preload is racing the first render for bandwidth it may never need.

Preload one or two things genuinely needed for the first render, include crossorigin on fonts, prefetch only the next page, lazy-load everything below the fold, and never lazy-load the largest element on the page.

8.5 defer and async scripts

A script in head without attributes stops everything: the parser downloads it, waits, runs it, and only then continues reading the document. The three attributes change that, and choosing between them is a question of order and of when the code can safely assume the DOM exists.

The three attributes

AttributeDownloadsExecutesBlocks parsing
noneImmediately, before continuingBefore anything after it parsesYes
deferIn parallel with the HTMLAfter the document is parsed, in orderNo
asyncIn parallel with the HTMLAs soon as it arrives, any orderNo
type="module"In parallel, always deferredAfter parsing, in orderNo
<!-- classic, blocking, in the head: the parser stops here -->
<script src="/js/legacy.js"></script>

<!-- deferred: parallel download, runs after the DOM exists, in order.
     Use for anything that needs the DOM or has dependencies. -->
<script src="/js/charts.js" defer></script>
<script src="/js/charts-plugin.js" defer></script>

<!-- async: parallel download, runs the moment it lands, in NO order.
     Use only for things independent of everything else. -->
<script src="/js/analytics.js" async></script>
<script src="/js/ads.js" async></script>

<!-- a module is deferred by definition -->
<script type="module" src="/js/app.mjs"></script>
Never put async on a script that has a dependency. With two async scripts and a dependency between them, the execution order is whatever the network happened to deliver, which means the failure is intermittent and only appears on a slow connection — the worst possible bug to reproduce.

Converting a blocking script

The migration is almost always just adding defer, and it is worth doing on any script not needed before the first render. The one thing to check is where the script currently sits: a defer script runs after the document is parsed, so any code that was written to run immediately at the point of inclusion will now find the DOM in a different state.

<!-- before: blocking, and the parser has not reached the footer yet -->
<head>
  <script src="/js/nav.js"></script>
</head>
<body>
  ...
  <nav id="site-nav"></nav>   <!-- did not exist when nav.js ran -->
</body>

<!-- after: parallel download, and the whole document exists first -->
<head>
  <script src="/js/nav.js" defer></script>
</head>
<body>
  ...
  <nav id="site-nav"></nav>
</body>

<!-- nav.js no longer needs to wait, because it now always runs late -->
document.getElementById("site-nav")   // guaranteed to be found

A script placed at the end of body without any attribute is a crude version of the same idea: the parser reaches it only after everything above it, so the DOM exists. It still blocks parsing for whatever remains, and it cannot be parallelised, so defer in head is strictly better.

Modules, and what they fix

<!-- app.mjs -->
import { chart } from "/js/chart.mjs";   // fetched and executed before app.mjs
import "/js/polyfill.mjs";              // for its side effects only

chart(document.querySelector("#results"));

<!-- the browser knows chart.mjs depends on scale.mjs, and fetches
     that too, without either script naming it at the top level -->

<!-- dynamic import: fetched only when this line actually runs -->
document.querySelector("#export").addEventListener("click", async () => {
  const { toCsv } = await import("/js/export.mjs");
  download(toCsv(rows));
});

Modules bring three things that scripts without them lack: they are deferred automatically, so there is no attribute to forget; a static import is always fetched before the importing module runs, which removes every class of "undefined is not a function" caused by load order; and each module has its own scope, so nothing leaks into the global object.

There is one catch with type="module": the file is fetched with CORS semantics, so it cannot be loaded from a file:// page. That matters for a library that is meant to open by double-click — a module-based page works when served and fails silently when opened from disk. Check which you need before converting.

Use defer for anything that needs the DOM or has dependencies, async only for independent scripts like analytics, and type="module" where you can — but remember modules need to be served, not opened from a disk.

9.1 Web Storage: localStorage and sessionStorage

Web Storage is two maps of string keys to string values that outlive the page. It is synchronous, it is limited to a few megabytes, it is shared by every page on your origin, and it is not private. Knowing those four things prevents most of the ways it goes wrong.

The two stores, and what each is for

PropertylocalStoragesessionStorage
LifetimeUntil explicitly clearedUntil the tab closes
Shared between tabsYes, and changes fire a storage event in the othersNo — per tab
Survives a restartYesNo
Typical usePreferences, an offline cache, a draftWizard state, a shopping basket for this visit
<script>
  // Everything is a string. Numbers and objects must be converted on the way
  // in and parsed on the way out.
  localStorage.setItem("theme", "dark");
  localStorage.setItem("cart", JSON.stringify([{ sku: "A1", qty: 2 }]));

  const cart = JSON.parse(localStorage.getItem("cart") || "[]");

  // Namespaced keys, so a shared origin cannot collide with yours
  localStorage.setItem("acme.theme", "dark");

  // Removing a key that is not there is not an error
  localStorage.removeItem("acme.cart");

  // Read every key, which is the only way to enumerate the store
  for (let i = 0; i < localStorage.length; i++) {
    const key = localStorage.key(i);
    console.log(key, localStorage.getItem(key));
  }

  // Or all at once, as an object
  const all = Object.fromEntries(
    Array.from({ length: localStorage.length },
               (_, i) => [localStorage.key(i), localStorage.getItem(localStorage.key(i))])
  );
</script>
Wrap storage in a small module rather than scattering localStorage calls through the code. One place handles JSON, one place handles a full disk, one place handles a browser where storage is disabled because the reader asked for it — which is a real setting, and it throws a SecurityError on access rather than returning null.

The limits, and what happens at them

The quota is roughly 5 MB per origin, and it is shared with everything else on that origin — caches, IndexedDB, and the same site under a different subdomain is a different origin with a different quota. Writing past it throws a QuotaExceededError and, critically, the write does not happen. A quota failure is therefore not a degraded experience; it is a feature that silently stops working.

<script>
  function save(key, value) {
    try {
      localStorage.setItem(key, value);
      return true;
    } catch (err) {
      // QuotaExceededError, or SecurityError where storage is blocked
      console.warn("storage unavailable:", err.name);
      return false;
    }
  }

  // storing something large? check the estimate first
  if (navigator.storage?.estimate) {
    const { usage, quota } = await navigator.storage.estimate();
    console.log(Math.round(usage / 1024) + " KB of " + Math.round(quota / 1024) + " KB");
  }
</script>
localStorage is synchronous and runs on the main thread. Reading or writing a megabyte blocks the main thread for long enough to be visible as a stutter, and doing it in a loop is worse. If you are storing more than a few kilobytes, use IndexedDB — it is asynchronous, transactional and effectively unbounded compared with this.

It is not private, and it is not per-tab

Web Storage is readable by every script on the origin. A third-party script, an injected extension, or an XSS bug can read everything in it, and the contents appear in a plain readable form in the browser's developer tools. Never put a token, a password, or anything personal in it.

<!-- changes in one tab are visible to the others -->
window.addEventListener("storage", (e) => {
  // e.key  null when the whole store was cleared
  // e.newValue null when the key was removed
  if (e.key === "acme.theme") applyTheme(e.newValue);
  if (e.key === null) clearCaches();
});

<!-- the event does NOT fire in the tab that made the change -->
localStorage.setItem("acme.theme", "dark");   // no handler runs here

That asymmetry is the cause of most "my other tab did not update" reports: the handler runs in the receiving tab and not in the one that wrote, so the writing tab must update its own UI directly as well.

Store strings, namespace the keys, catch the quota error, and keep secrets out of it. Use IndexedDB once you are past a few kilobytes, and remember the storage event tells the other tabs rather than this one.

9.2 dialog, details and summary

Three elements handle disclosure: dialog for a window, details for an expand-and-collapse region, and summary for its label. All three do with no JavaScript what would otherwise need a state variable, and all three have accessibility requirements that are easy to get wrong.

dialog, and the two methods that matter

<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete this project?</h2>
  <p>Everything in it will be removed.</p>
  <form method="dialog">
    <button value="cancel">Cancel</button>
    <button value="confirm" class="danger">Delete</button>

  const dlg = document.getElementById("confirm");

  dlg.showModal();     // modal: traps focus, inert behind, Escape closes it
  // dlg.show();        // non-modal: no trap, no inertness

  dlg.addEventListener("close", () => {
    // dlg.returnValue is the value of the button that closed it
    if (dlg.returnValue === "confirm") deleteProject();

Focus is moved into the dialog when it opens, but you still have to put it somewhere sensible — otherwise it goes to the first focusable element, which is usually Cancel, so a reader who presses Enter immediately dismisses the thing they opened to read. details and summary, and the name attribute

<details>
  <summary>Why is my build slower after adding one file?</summary>
  <p>Each module boundary prevents the bundler from joining modules,
     so it cannot tree-shake across one.</p>

  <summary>...</summary>
</details>

<!-- one in a named group open at a time.
     Two open it, and the other closes. -->

The name attribute turns a set of details into an accordion, which is usually what an FAQ actually wants. Without it, a reader can open all twelve at once and lose the ability to find the one they want. With it, opening one closes the rest.

summary must be the first child of details, and only summary is clickable — the rest of the content is not the toggle. Also, styling a summary with display: flex removes the default marker in some browsers, so you must add your own disclosure triangle or the reader is given no indication that it opens anything.

Reading and setting the state

<script>
  const d = document.querySelector("details");

  d.open              // boolean
  d.open = true;      // set
  d.toggle();         // flip
  d.toggle(true);     // open it, whatever its state

  // the open/close event fires for user interaction AND for toggle()
  d.addEventListener("toggle", () => {
    if (d.open) trackExpanded("faq", d.querySelector("summary").textContent);
  });

  // content is not hidden with display:none, so it can be styled
  // and found by find-in-page while collapsed
</script>

Use [open] in CSS to style the open state, and remember that a details can contain flow content including headings. A collapsed section's content is still findable by the browser's find-in-page on most engines, which is often a bonus and occasionally a surprise.

Use showModal() for anything that must be dealt with and return focus to the opener on close; use details for disclosure, with name on a group so it behaves as an accordion.

9.3 template and slot

A template holds markup that is parsed and validated but never rendered. Nothing inside it appears, nothing in it is fetched, and its contents live in a separate document fragment. That separation is what makes it the right container for a reusable piece of markup — and the source of two behaviours that catch people.

Parsed, but inert

<template id="row-template">
  <tr>
    <td class="name"></td>
    <td><img class="thumb" src="" alt=""></td>
    <td class="qty"></td>
  </tr>
</template>

<script>
  const tpl = document.getElementById("row-template");
  console.log(tpl.content);           // a DocumentFragment
  console.log(tpl.innerHTML);         // empty - there is no content attribute

  // the img above fetched nothing: nothing is in the document
</script>

The consequence that matters: an image, a stylesheet or a script inside a template is not loaded and not executed until the fragment is cloned into the document. A component library can ship a hundred templates with a hundred images and the reader downloads one component's image.

Read and write template.content, never the element's children. innerHTML on a template is always empty, because its contents are not children of the element — they are in a fragment. This is a consistent five-minute confusion the first time anyone meets it.

Cloning, and why it must be done per instance

<script>
  const tpl = document.getElementById("row-template");

  function addRow(name, image, qty) {
    // cloneNode(true) is deep, so the fragment's children come too
    const row = tpl.content.cloneNode(true);

    row.querySelector(".name").textContent = name;
    const img = row.querySelector(".thumb");
    img.src = image;
    img.alt = name;                    // the alt is set at the same time
    row.querySelector(".qty").textContent = String(qty);

    document.querySelector("tbody").append(row);
  }
</script>

Each clone needs its own cloneNode. Appending the same fragment twice moves it rather than copying it, so the second row appears empty and the first row is gone from its place. This is the same live-collection behaviour that makes append of several existing nodes surprising.

A template may contain a <tr>, and putting it directly in the document is valid — but a <div> inside a <tr> is not, and the parser hoists it out, which silently restructures the template's content. Templates are parsed with the same rules as the document, so content that is invalid in the target position is invalid in the template too.

slot: letting the user supply the contents

slot is the other half of the pattern. A component declares where its replaceable parts are and what the fallback is, and the user fills them from outside. Named slots go with an slot="name" attribute; the unnamed slot takes everything left over.

<!-- a reusable card component -->
<template id="card-template">
  <article class="card">
    <header>
      <slot name="title">Untitled</slot>
    </header>
    <img slot="media" src="" alt="">
    <div>
      <slot>No summary supplied.</slot>
    </div>
    <footer><slot name="actions"></slot></footer>
  </article>
</template>

<!-- the user fills the slots -->
<div id="card">
  <span slot="title">Native validation</span>
  <img  slot="media" src="/img/forms.png" alt="A form with an error">
  <p>How the constraint API replaces most of a validation library.</p>
  <a slot="actions" href="/guides/html#forms">Read it</a>
</div>
<script>
  // move the user's content into the component's slots
  const card = document.getElementById("card");
  const tpl  = document.getElementById("card-template");
  const instance = tpl.content.cloneNode(true);

  const parts = card.querySelectorAll("[slot]");
  const body  = card.querySelector(":scope > p");

  instance.content.querySelector('[slot="title"]')
    .replaceWith(...parts.map((p) => p.cloneNode(true)));
  instance.content.querySelector("div")
    .replaceWith(body.cloneNode(true));

  card.replaceWith(instance);

  console.log(instance.content.querySelectorAll("[slot]").length);  // 0
</script>

Once the content is in the template's own tree the slot attributes are no longer needed — the element is in the slot. Querying for remaining [slot] elements is therefore a good assertion that the composition succeeded.

A template's contents are parsed but never rendered or fetched until cloned. Use content rather than innerHTML, clone per instance, and pair template with slot for a component whose contents the user supplies.

9.4 data-* attributes and the history API

Two small mechanisms cover most of what used to require a framework. data-* attributes let an element carry structured values that JavaScript can read without a class name convention, and the History API lets a page change its URL without a reload.

data-* attributes

Any attribute whose name starts with data- is valid and is exposed on the element as a key of its dataset object. The name after the prefix is lower-cased, and a hyphen becomes a camelCase boundary.

        data-confirm-message="Delete this user?"
        data-max-length="140">Remove</button>

  btn.dataset.action;          // "delete"

  btn.dataset.missing;         // undefined

  btn.dataset.state = "pending";

  btn.getAttribute("data-user-id");   // "42"

</script>

The History API, without reloading

<script>
  // change the URL without navigating
  history.pushState({ page: 2 }, "", "/catalogue?page=2");

  // replace the current entry, for a filter that is not worth a Back step
  history.replaceState({ page: 2, sort: "price" }, "",
                       "/catalogue?page=2&sort=price");

  // read the state on load - it is null on the first visit
  history.scrollRestoration = "manual";
  const state = history.state || { page: 1 };

  // popstate fires on Back and Forward, NOT on pushState
  window.addEventListener("popstate", (e) => {
    render(e.state?.page ?? 1);
  });
</script>

pushStateYes — Back returns to the previous stateNo

The rule that catches everyone: pushState does not fire popstate, so if you push a new URL you must also render the new state yourself. If you only listen for popstate, the page will appear to change the URL while showing the old content. Handle both: render on push, and render on pop.

Two more constraints. The URL must be same-origin or the call throws, so you cannot push an absolute URL to another domain. And the state object is structured-cloned, so it must be serialisable — a DOM node or a function in there throws.

<!-- a filter that updates the URL, but should not add a Back step -->
const filter = document.querySelector("#category");

filter.addEventListener("change", () => {
  const url = new URL(location.href);
  if (filter.value) url.searchParams.set("category", filter.value);
  else url.searchParams.delete("category");
  history.replaceState({ category: filter.value }, "", url);
  applyFilter(filter.value);
});

// and on load, read it back
applyFilter(new URLSearchParams(location.search).get("category"));

<!-- a step in a wizard: each step SHOULD be a Back step -->
next.addEventListener("click", () => {
  history.pushState({ step: 2 }, "", "/checkout/address");
  showStep(2);
});

Use data-* to attach values to markup and read them through dataset, and use pushState for navigation the reader should be able to go back from and replaceState for adjustments they should not. Render on both push and pop.

9.5 Geolocation and drag and drop

Two APIs that both ask for permission and both fail in ways a user should never be blamed for. Geolocation returns a position, a heading, an accuracy figure and a timestamp — and all four matter, because the first three are meaningless without the last. Drag and drop has three stages and each fires a different event.

Geolocation, and what the error codes mean

<script>
  function locate() {
    if (!navigator.geolocation) return showError("No geolocation");

    navigator.geolocation.getCurrentPosition(
      (pos) => {
        const { latitude, longitude, accuracy, heading, timestamp } = pos.coords;

        // accuracy is a RADIUS in metres, not a precision
        show(`Within ${Math.round(accuracy)} m`,
              latitude, longitude,
              new Date(timestamp).toLocaleTimeString());
      },
      (err) => {
        // each code needs a different message and a different remedy
        switch (err.code) {
          case err.PERMISSION_DENIED:
            return showError("Location is blocked. You can allow it in your browser settings.");
          case err.POSITION_UNAVAILABLE:
            return showError("Your position could not be determined.");
          case err.TIMEOUT:
            return showError("Locating took too long. Try again outdoors.");
        }
      },
      {
        enableHighAccuracy: true,   // GPS; costs battery and time
        timeout: 10000,             // give up after this long
        maximumAge: 30000           // accept a cached fix under 30 s old
      }
    );
  }
</script>
OptionDefaultEffect
enableHighAccuracyfalseUse GPS rather than a network estimate. Slower, more accurate, more battery
timeoutinfiniteWithout it the promise can stay pending for ever indoors
maximumAge0Accept a cached position up to this old. Useful on a page the reader returns to

accuracy is a radius in metres and it is the field that decides whether the answer is worth showing. A 2,000-metre accuracy on a "you are here" map is a lie presented as a dot. When accuracy is poor, either say so or draw a circle of that radius rather than a point — which is what a good mapping interface does and what a lat/lng readout never does.

Permission is asked for in response to a user action, never on page load. A prompt that appears before the reader has seen what is being offered is answered reflexively, and the reflex is "no". Ask when they press "Use my location".

watchPosition, and cleaning up

<script>
  let watchId = null;

  function startTracking() {
    watchId = navigator.geolocation.watchPosition(
      (pos) => render(pos.coords),
      (err) => stopTracking(),       // a hard error ends the watch
      { enableHighAccuracy: true }
    );
  }

  function stopTracking() {
    if (watchId !== null) {
      navigator.geolocation.clearWatch(watchId);
      watchId = null;
    }
  }

  // stop when nobody is looking: a watch left running drains the battery
  document.addEventListener("visibilitychange", () => {
    document.hidden ? stopTracking() : startTracking();
  });
  window.addEventListener("pagehide", stopTracking);
</script>

An unclosed watch is a real cost, not a theoretical one: it keeps the GPS receiver active and fires continuously in the background. Always clear it, and clear it on pagehide as well as on visibilitychange.

Drag and drop, in three stages

<ul id="list">
  <li draggable="true" data-id="a">Apples</li>
  <li draggable="true" data-id="b">Bananas</li>
</ul>

<script>
  const list = document.getElementById("list");

  list.addEventListener("dragstart", (e) => {
    const li = e.target.closest("[draggable]");
    e.dataTransfer.setData("text/plain", li.dataset.id);  // required
    e.dataTransfer.effectAllowed = "move";
  });

  list.addEventListener("dragover", (e) => {
    e.preventDefault();          // without this the drop never fires
    e.dataTransfer.dropEffect = "move";
  });

  list.addEventListener("drop", (e) => {
    e.preventDefault();
    const id = e.dataTransfer.getData("text/plain");
    reorder(id, e.target.closest("li"));
  });

  list.addEventListener("dragend", () => clearDropStyles());
</script>
Two requirements that produce a drop target that silently does nothing. dragover must call preventDefault(), or the browser refuses the drop and drop never fires. And dragstart must call setData, because in most browsers a drag with no data set is not a drag at all — which is why dropping a link or selected text from another window sometimes works and dragging your own element does not.
<!-- dropping a file from the desktop -->
drop.addEventListener("dragover", (e) => {
  e.preventDefault();
  if (e.dataTransfer.types.includes("Files")) e.classList.add("over");
});
drop.addEventListener("drop", async (e) => {
  e.preventDefault();
  e.classList.remove("over");
  for (const file of e.dataTransfer.files) {
    if (file.size > 5 * 1024 * 1024) { reject(file, "too large"); continue; }
    upload(file);
  }
});

Read accuracy before showing a position and say so when it is poor; clear a watchPosition when the page is hidden; and for drag and drop, remember that dragover needs preventDefault and dragstart needs setData or nothing happens at all.

10.1 Write valid, parseable HTML

A validator checks your document against the specification and reports what it finds. It is the only tool that can tell you that your HTML is wrong, because a browser will not: the parser recovers from every error by design, so a page with mistakes still renders and looks fine. Validity is about the document you wrote, not the one the browser built.

Making it part of writing rather than a chore

<!-- in a template, so the invalid HTML never reaches the file -->

  <div class="card">
    <h2>${escapeHtml(title)}</h2>
    <p>${escapeHtml(body)}</p>
  </div>
</template>

Two classes of invalidity are worth separating. A typo — a misspelled tag, a missing alt, an unclosed <div> — is a mistake and should fail the build. An obsolete-but-rendering construct is a trade-off, and belongs in a documented exception rather than in a blanket suppression. The validator that is configured to fail on everything gets disabled; the one that separates the two keeps being run.

There is no such thing as "nearly valid HTML". The parser does not grade correctness — it repairs what it can and discards what it cannot, and which of those happened is invisible in the source. A validator is the only thing that tells you which side of that line your page is on.

Run a validator in the build and treat it as a failure, keep the invalid-markup classes limited to the obsolete constructs you have decided to allow, and validate the rendered DOM as well when a page misbehaves.

A long class list is not a semantic problem, but it is a change-cost problem, and it usually arrives as a symptom of something else. It is normally easier to style the element — with flexbox, a grid, or one modifier class — than to keep twelve utility classes in step with the design system.

Replace a div when the element has a name — a region, a relationship, a unit. Keep it when it exists only to carry a style. And when a heading is rendered as a span, put the heading back.

10.4 Progressive enhancement

Progressive enhancement is the practice of making the useful thing work first and the impressive thing optional. In practice it means the markup contains the content and the function, CSS makes it look right, and JavaScript improves an experience that already exists. The payoff is that every failure mode degrades instead of breaking.

A form that works without script

<!-- works on its own, entirely -->
<form action="/subscribe" method="post">
  <label for="sub-email">Email</label>
  <input id="sub-email" name="email" type="email"
         autocomplete="email" required>
  <button type="submit">Subscribe</button>
</form>

<script>
  // enhancement only: inline validation that adds to what is there
  const form = document.querySelector("form");
  const email = form.elements.email;

  email.addEventListener("blur", () => {
    email.setCustomValidity(email.validity.valid ? ""
      : "Check that address — it is missing an @.");
  });
</script>

With the script blocked, the form still submits to a real endpoint, the browser still validates it, and the reader still gets a result. The script only replaced the browser's bubble with a clearer message. That is the whole pattern: the baseline is complete on its own.

Content first

<!-- not a navigation that happens to be links -->
<nav aria-label="Guide contents">
  <ol>
    <li><a href="#ch1">Getting started</a></li>
    <li><a href="#ch2">Document structure</a></li>
    <li><a href="#ch3">Text, lists, links and images</a></li>
  </ol>
</nav>

<!-- a table that is a table, readable without any styling -->
<table>
  <caption>Delivery times</caption>
  <thead><tr><th scope="col">Region</th><th scope="col">Days</th></tr></thead>
  <tbody><tr><th scope="row">United Kingdom</th><td>3</td></tr></tbody>
</table>

Both of these work, and are navigable and readable, with no CSS at all. That is what makes them progressive: the stylesheet is an enhancement, so a slow stylesheet, a blocked one, or a print stylesheet that hides everything cannot take away the information.

If the content only exists after JavaScript runs, you have an application wearing a document's clothes — which is fine if that is what it is, but it must then be served, not opened from a disk.

Where the line is

Not everything should degrade. A drawing application, a video editor and a spreadsheet are applications, and a document fallback for them is a page saying "please enable JavaScript". The honest test is whether the information is in the document or only in the interface. For a guide, a catalogue or an article, it belongs in the document. For a tool, it belongs in the script, and the fallback should be honest about that.

The common failure is a hybrid: the content is rendered by a script, the script is required, and the only fallback is a spinner. Now the page has a baseline of nothing, so a script error looks identical to a slow connection, and neither is diagnosable from the page. If content is rendered client-side, either accept that it needs the script and say so, or serve it from the server.

Put the content and the function in the markup, style it with CSS and improve it with script. Then check the degradation table honestly: with CSS off the words should still be there, and with script off the form should still submit.

A.3 Global attributes and ARIA landmarks

Two vocabularies meet in this section. The global attributes are the ones any element accepts, and they are how you attach identity, language and behaviour to markup. The landmark roles are the vocabulary assistive technology uses to describe the regions of a page — the map a screen reader builds so a reader can jump between them rather than scroll.

They are listed together because they answer the same question from different directions. A class and an aria-label both say something about an element; the first is for CSS and the second for a reader, and conflating them is how a page ends up with an accessible name that says "button".

An attribute is a claim about an element, and the accessibility attributes are claims a reader relies on. When two disagree — a class that says error and an aria-label that does not — the reader is the one left guessing which was meant.

A.4 Glossary

The glossary defines the terms this guide relies on, from elements and attributes to ARIA, viewport and the DOM. Each definition is short and precise so you can look up a concept mid-task. A term you can name precisely is a bug you can describe precisely when you ask for help.

  • Element — an opening tag, content and a closing tag; the atomic unit of HTML.
  • Attribute — extra information on an opening tag, such as href or required.
  • DOM — the Document Object Model, the live in-memory tree the browser builds from your markup.
  • Semantic HTML — choosing elements for their meaning rather than their appearance.
  • Landmark — a named region of a page, such as banner, main or navigation, that assistive tech navigates.
  • ARIA — the Accessible Rich Internet Applications spec for adding roles, states and properties to widgets.
  • Progressive enhancement — building a fully working baseline, then layering enhancements for capable browsers.
  • Constraint validation — the browser-side rule checks built into forms: required, pattern, min, max, step.
  • Lazy loading — deferring the fetch of off-screen resources until they near the viewport.
  • Cross-origin — content from a different origin (scheme, host and port) than the current page, subject to the same-origin policy.
