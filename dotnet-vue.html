Welcome — Scalable Web Apps with .NET Core + Vue

How this guide is organisedThe stack

This guide maps out a full production-grade system where an ASP.NET Core API in C# talks to a Vue 3 single-page application. Each chapter and subtopic is self-contained, so you can read front to back or jump straight to the part you need. Working through it in order gives you the whole mental model; dipping in still leaves every section meaningful on its own.

A complete guide to building a production-grade, scalable web application with a .NET (ASP.NET Core) backend and a Vue 3 frontend. Single file, offline, progress saved locally.

How this guide is organised

The guide is organised into three arcs: ASP.NET Core backend first, Vue 3 frontend second, then a final arc that integrates and operates the two halves together. Every chapter is written to stand alone, so you can bend the order to your own priorities. Cross-references tell you when a later part depends on an earlier concept.

  • Architecture & backend (Ch. 1–7) — solution structure, minimal APIs, clean architecture, EF Core, auth, API design and background work.
  • Frontend (Ch. 8–11) — Vue 3 + Vite + TypeScript, routing, state with Pinia, forms and the API client.
  • Together (Ch. 12–16) — integration, real-time, testing, observability, deployment and performance.

The backend is the contract; the frontend is a consumer. Design and version the API first, and both halves move independently and safely.

The stack

The stack is the exact technology lineup used in every example: .NET 9 or 10 with EF Core for the API, Vue 3 with Vite and TypeScript for the frontend, and SignalR for realtime messaging. Knowing these names means the patterns you learn transfer directly to your own projects. Nothing else needs installing beyond the standard tooling these frameworks provide.

1 · Architecture Overview

1.1 SPA + API shape1.2 Clean architecture layers1.3 Modular monolith before microservices

Before any code, this chapter explains how the SPA, API and database fit together into one system. It makes the decisions you will see later rational: why the frontend is a separate host, how the API owns the data, and where realtime connections sit. Five minutes here gives every later choice a place to live.

1.1 SPA + API shape

The system is two deployables joined by one contract: the browser speaks HTTPS and JSON to the API, and SignalR handles realtime messages over a WebSocket. This split never changes, so you can develop and test each half independently. The API stays the single source of truth while the SPA remains a purely stateless client.

Browser (Vue SPA)  --HTTPS/JSON-->  ASP.NET Core API  -->  Database
       |                                   |
       +-- SignalR (websockets) -----------+
       +-- CDN (static assets)

Two deployables (or one container serving both), one API contract.

An architecture sketch: the SPA talks HTTPS/JSON to the API, SignalR carries realtime pushes, and a CDN serves static assets — everything behind one API contract.

1.2 Clean architecture layers

Clean architecture organises code into concentric layers with dependencies pointing inward toward the domain. Your domain and application layers know nothing about EF Core, HTTP or Vue, leaving the API layer as the only place framework types appear. That inward flow keeps business rules testable without a database or a server running.

ProjectResponsibilityDepends on
DomainEntities, value objects, rulesNothing
ApplicationUse cases, DTOs, interfacesDomain
InfrastructureEF Core, external servicesApplication
ApiHTTP endpoints, wiringApplication + Infrastructure

1.3 Modular monolith before microservices

Start as one deployable application that is internally divided into clear feature modules, each owning its own routes and data. Microservices are only worth splitting out later when a specific boundary genuinely needs independent scaling or separate ownership. The modular monolith keeps deploys simple while still giving you seams to split along.

Start as a modular monolith with clear boundaries (by feature). Split into services only when a boundary genuinely needs independent scaling or ownership. Premature microservices buy distributed complexity with no payoff.

2 · ASP.NET Core Fundamentals

2.1 Minimal APIs2.2 Dependency injection and configuration2.3 The middleware pipeline

This chapter covers the everyday .NET machinery you touch most: minimal APIs, dependency injection and the middleware pipeline. You learn how to declare endpoints, register services once in the container and inject them where needed, and compose request handling in the correct order. Mastering these makes endpoints quick to write and safe to reason about.

2.1 Minimal APIs

Minimal APIs define HTTP endpoints as small lambda functions with minimal boilerplate, using MapGet, MapPost and related methods on the builder. The guide uses them for the whole API surface because they keep handlers close to their routes. Small surfaces stay readable, and dependency injection arguments are filled automatically from the container.

var builder = WebApplication.CreateBuilder(args); // app host plus config
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddOpenApi();

var app = builder.Build();

var posts = app.MapGroup("/api/posts"); // all post endpoints share this prefix

posts.MapGet("/", async (AppDbContext db) =>
    await db.Posts.OrderByDescending(p => p.CreatedAt).ToListAsync());

posts.MapGet("/{id:int}", async (int id, AppDbContext db) =>
    await db.Posts.FindAsync(id) is Post p ? Results.Ok(p) : Results.NotFound());

posts.MapPost("/", async (CreatePostDto dto, AppDbContext db) =>
{
    var post = new Post { Title = dto.Title, Body = dto.Body };
    db.Posts.Add(post);
    await db.SaveChangesAsync(); // persists the new post
    return Results.Created($"/api/posts/{post.Id}", post);
});

app.Run(); // start listening for requests

A complete minimal API: a lean bootstrap, an /api/posts group for list and detail reads, and a POST that creates a post and returns 201 with its location.

2.2 Dependency injection and configuration

Dependency injection and configuration are built into ASP.NET Core, so you register services once in Program.cs with AddSingleton, AddScoped or AddTransient and inject them anywhere via constructor parameters. Configuration binds from appsettings.json and environment variables through the IConfiguration service. This gives you testability for free because every dependency is explicit.

builder.Services.AddScoped<IPostService, PostService>(); // one instance per request
builder.Services.Configure<JwtOptions>(builder.Configuration.GetSection("Jwt")); // bind the Jwt section

// appsettings.json + environment variables + user-secrets (dev)

Two registration lines: a scoped service per request plus strongly-typed JwtOptions bound from config. Swap either in tests without touching callers.

2.3 The middleware pipeline

Requests flow through a middleware chain in the exact order you register it with Use and Run methods. Ordering is the classic source of bugs, so authentication must run before authorization, and error handling early enough to catch failures. Each middleware can short-circuit the pipeline and hand back a response immediately.

app.UseExceptionHandler("/error"); // outermost, catches everything downstream
app.UseHttpsRedirection();
app.UseCors("spa");
app.UseAuthentication(); // identify the caller
app.UseAuthorization(); // check what the caller may do
app.MapControllers(); // or minimal endpoints

A request pipeline in the right order: exceptions first, then HTTPS and CORS, then authentication before authorization, then the endpoints.

Order matters. Authentication before authorization; exception handling outermost so it can catch everything downstream.

3 · Clean Architecture in .NET

3.1 Use cases3.2 CQRS: commands vs queries3.3 Validation and pipeline behaviors

This chapter keeps business rules independent of the framework by shaping code into use cases. You write the core logic once and then let controllers, HTTP and EF Core hang off the outside. The upfront ceremony pays back in logic you can unit test without a server and can reason about in isolation.

3.1 Use cases

Every command or query becomes a named use case class together with its own handler, typically split by IRequest and IRequestHandler for command-query separation. Controllers shrink to HTTP translation while the real work moves into the handler. Because the use case has no framework dependencies, you can test it in isolation over an in-memory data source.

public sealed record CreatePostCommand(string Title, string Body) : IRequest<int>; // declares the intent

public sealed class CreatePostHandler : IRequestHandler<CreatePostCommand, int>
{
    private readonly AppDbContext _db;
    public CreatePostHandler(AppDbContext db) => _db = db;

    public async Task<int> Handle(CreatePostCommand cmd, CancellationToken ct)
    {
        var post = new Post(cmd.Title, cmd.Body); // map the command to an entity
        _db.Posts.Add(post);
        await _db.SaveChangesAsync(ct); // persist the change
        return post.Id;
    }
}

A command record and its handler: build a Post from the command, save it, return the new id. No HTTP, no framework — just business logic.

MediatR (or a hand-rolled dispatcher) keeps controllers/endpoints thin: they translate HTTP to a command/query and back.

3.2 CQRS: commands vs queries

CQRS separates operations that change state, the commands, from operations that only read it, the queries. Each side is then optimised for its own job: writes stay simple and transactional, reads project exactly what the client needs. You get clear analysis and simpler reasoning about who is allowed to change what.

SidePurposeReturns
CommandChange stateId / void / result
QueryRead stateDTOs

3.3 Validation and pipeline behaviors

Validation rules written with FluentValidation stay attached to the command or query they protect. A pipeline behavior such as the one MediatR provides runs those rules before the handler ever executes, so one policy applies to every request. Fail all requests return consistent validation errors without duplicate code in each handler.

public class CreatePostValidator : AbstractValidator<CreatePostCommand>
{
    public CreatePostValidator()
    {
        RuleFor(x => x.Title).NotEmpty().MaximumLength(200); // required, max 200 chars
        RuleFor(x => x.Body).NotEmpty().MinimumLength(10); // required, min 10 chars
    }
}
// Register a validation behavior so every command is validated before handling.

FluentValidation rules on the command itself: Title required and short, Body required and meaty. A pipeline behavior runs them before any handler.

4 · Data Access with EF Core

4.1 The DbContext and models4.2 Migrations4.3 Efficient querying

This chapter is about sensible data access with EF Core: modelling the schema in code, migrating it safely through environments and querying efficiently. You configure entities and relationships once, generate migrations from the model, and project your queries to exactly the shapes clients need. The goal is that no request ever accidentally scans a whole table.

4.1 The DbContext and models

Your DbContext subclasses DbContext and is the single place that maps entities to tables, keys and relationships using DbSet properties and configuration classes. ModelBuilder configuration in OnModelCreating is the contract your queries depend on, so keeping it explicit matters. One context lifetime maps to one logical unit of work.

public class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options)
{
    public DbSet<Post> Posts => Set<Post>(); // the Posts table
    public DbSet<Tag> Tags => Set<Tag>(); // the Tags table

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Post>().HasIndex(p => p.Slug).IsUnique(); // one slug per post
        b.Entity<Post>().HasOne(p => p.Author).WithMany().HasForeignKey(p => p.AuthorId); // required author
    }
}

The DbContext surfaces Posts and Tags as DbSets and, in OnModelCreating, enforces a unique slug index and the Author relationship.

4.2 Migrations

Migrations turn model changes into reviewable SQL scripts you can run in any environment. The dotnet ef migrations add command generates them and dotnet ef database update applies them locally, while production uses an idempotent script generated with script. Each environment then upgrades deterministically without anyone running handwritten SQL.

dotnet tool install --global dotnet-ef # one-time CLI install
dotnet ef migrations add InitialCreate # scaffold the first migration
dotnet ef database update # apply it locally
dotnet ef migrations script --idempotent   # for CI/CD

The EF Core workflow: install the CLI once, add a migration, update the database, and generate an idempotent script for CI/CD.

4.3 Efficient querying

Efficient querying comes from projecting to DTOs with Select, disabling change tracking on read-only queries with AsNoTracking, and paginating every list with Skip and Take. You must also filter in the database rather than in memory. The difference separates a snappy API from one that scans whole tables per request.

// Project to DTOs -> only needed columns
var list = await db.Posts.AsNoTracking() // read-only, no change tracking
    .Where(p => p.Published)
    .OrderByDescending(p => p.CreatedAt)
    .Select(p => new PostSummary(p.Id, p.Title, p.Author.Name))
    .Skip((page - 1) * size).Take(size) // one page of results
    .ToListAsync();

// Avoid N+1: use Include/ThenInclude or projection; never loop-lazy-load.

A paginated, projected read: no tracking, only published posts, a narrowed column set, and Skip/Take for paging — the antidote to N+1.

AsNoTracking() for reads, projections over full entities, and pagination everywhere. EF Core is powerful but a careless query can scan the whole table.

5 · Authentication & Authorization

5.1 ASP.NET Core Identity5.2 JWT for SPAs5.3 Policies and claims

This chapter covers identity, tokens and permissions, the security layer every real application needs. You register ASP.NET Core Identity for users and password hashes, issue JWTs for the SPA, and protect endpoints with authorization policies. Getting the storage and cookie choices right early avoids painful migrations and security holes later.

5.1 ASP.NET Core Identity

ASP.NET Core Identity provides users, password hashing, roles and token providers straight out of the box. You wire it to EF Core by calling AddIdentity and AddEntityFrameworkStores with your DbContext, then use UserManager and SignInManager for registration, sign-in and password management. It gives you most of a secure auth system without rolling your own hashing.

builder.Services.AddIdentityCore<AppUser>() // registers the identity core
    .AddEntityFrameworkStores<AppDbContext>() // stores users with EF Core
    .AddDefaultTokenProviders();

// Register / login endpoints; password hashing handled for you.

Identity registers the user store in EF Core with default token providers. Hashing, password rules and token generation are handled for you.

5.2 JWT for SPAs

JSON Web Tokens let a stateless SPA authenticate without server-side sessions by validating the token against its issuer, audience and signature on every request. The accepted practice for browser apps is to keep the JWT in a SameSite httpOnly cookie rather than in localStorage. Short expiry times plus a refresh flow limit the damage when a token leaks.

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.TokenValidationParameters = new TokenValidationParameters // what each token must pass
        {
            ValidateIssuer = true, ValidateAudience = true,
            ValidateLifetime = true, ValidateIssuerSigningKey = true,
            IssuerSigningKey = new SymmetricSecurityKey(key) // verify the signature
        };
    });

[Authorize] // on endpoints
// Prefer short-lived access tokens + refresh tokens stored in httpOnly cookies.

JWT bearer auth enforces issuer, audience, lifetime and signature on every request. The closing comment is the real advice: keep tokens in httpOnly cookies.

Never store long-lived JWTs in localStorage in production — XSS turns them into stolen sessions. Use httpOnly, Secure, SameSite cookies or in-memory access tokens with refresh rotation.

5.3 Policies and claims

Authorization is declared at the endpoint with the Authorize attribute tied to a named policy rather than scattered role checks. Policies combine requirements over claims and roles, for example a minimum role or a specific claim value, defined once via AddAuthorization. Endpoints then state what they need and the framework enforces it consistently.

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("CanEditPost", p => p.RequireClaim("permission", "posts.edit")); // claim-based check
    o.AddPolicy("Admin", p => p.RequireRole("Admin")); // role-based check
});

Two policies: a claim-based CanEditPost and a role-based Admin. Endpoints just declare the policy name and the framework enforces it.

6 · API Design & Error Handling

6.1 Resource design6.2 RFC 7807 Problem Details6.3 Versioning strategy

This chapter defines a clean HTTP contract so that failures are as predictable as success. You design consistent resource URLs, return RFC 7807 problem detail bodies for errors, and version the API with a migration path. Consistent problems and versioning keep your clients honest and your documentation truthful.

6.1 Resource design

Resource design gives one URL shape per resource while HTTP verbs cover the actions, and query strings express filtering, sorting and paging. A GET returns a collection or item, POST creates, PUT replaces, PATCH updates and DELETE removes. Predictable REST keeps client code trivial and lets conventions replace per-endpoint documentation.

GET    /api/v1/posts           list (paginated)
GET    /api/v1/posts/{id}      detail
POST   /api/v1/posts           create
PUT    /api/v1/posts/{id}      replace
PATCH  /api/v1/posts/{id}      partial update
DELETE /api/v1/posts/{id}      remove

# Filtering/sorting:  ?page=2&size=20&sort=-createdAt&tag=php

One resource, five verbs, plus pagination, filtering and sorting through the query string. URL versioning keeps v1 stable while v2 evolves.

6.2 RFC 7807 Problem Details

RFC 7807 Problem Details is a standardised JSON body for errors, so every failure looks the same to clients. Implemented with the ProblemDetails class or AddProblemDetails, it carries a type, title, status, detail and instance plus custom fields. Machine-parseable errors let the frontend render failures without special-casing each status code.

builder.Services.AddProblemDetails(); // standard RFC 7807 error output

// Consistent errors:
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Validation failed",
  "status": 400,
  "errors": { "title": ["Title is required"] },
  "traceId": "00-abc..."
}

AddProblemDetails produces standard RFC 7807 bodies with a per-field error map and a traceId — one shape clients everywhere can parse.

6.3 Versioning strategy

URL versioning, such as /api/v1/orders, is simple and impossible for consumers to miss compared to header-based alternatives. The ASP.NET Core versioning packages let you define a deprecation window so past versions keep working for a while after a new one ships. Clear notice plus a removal date protects every client you have published.

  • URL versioning (/api/v1/) is the simplest and most visible.
  • Never break a published contract without a version bump and a deprecation window.
  • Document with OpenAPI/Swagger; generate typed clients for the SPA.

7 · Background Work, Caching & Realtime Backend

7.1 Hosted services and background queues7.2 Caching layers7.3 SignalR hub

This chapter covers work that should not block a request: background jobs, caching hot data and server-initiated push notifications. Together these three make an API feel instant at scale. Each pattern fits a different problem, and the guide shows when to apply which one.

7.1 Hosted services and background queues

A BackgroundService subclass runs long-lived work while your application is up, started and stopped by AddHostedService in configuration. You can pair it with an IBackgroundTaskQueue or a channel that endpoints enqueue work onto, then the service drains it. Perfect for outbox processors, reminders and any work too slow for a request lifetime.

public class OutboxWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested) // loop until shutdown
        {
            using var scope = scopeFactory.CreateScope(); // fresh scoped services each poll
            var handler = scope.ServiceProvider.GetRequiredService<OutboxHandler>();
            await handler.ProcessPendingAsync(ct);
            await Task.Delay(TimeSpan.FromSeconds(5), ct); // wait five seconds between runs
        }
    }
}
builder.Services.AddHostedService<OutboxWorker>();
// For real scale: Hangfire / MassTransit + a broker (RabbitMQ/Azure Service Bus).

A BackgroundService polls an outbox every five seconds using a fresh DI scope per tick, so scoped services stay safe. Registered once, runs for the app’s life.

7.2 Caching layers

The caching layer puts Redis in front of expensive reads with a short time-to-live to cut database load. Cache-Aside is the classic pattern: check the cache, fall through to the database on a miss, then populate the entry for the next request. Keep serialized DTOs in the cache and set a TTL so stale data self-heals.

builder.Services.AddStackExchangeRedisCache(o => // register Redis as the cache
    o.Configuration = builder.Configuration["Redis"]);

var value = await cache.GetOrCreateAsync("stats", async entry => // get or recompute
{
    entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5); // cache for five minutes
    return await ComputeStatsAsync();
});

Redis is registered, then GetOrCreateAsync computes stats once and reuses them for five minutes. The classic cache-aside pattern in four lines.

7.3 SignalR hub

A SignalR hub is the server-side heart of your realtime socket, a class that inherits from Hub and exposes methods clients can invoke. You map it with MapHub, authenticate it like any endpoint, and push messages by calling Clients methods that target connections. The matching Vue client appears in the realtime chapter later in the guide.

public class NotificationsHub : Hub { }

app.MapHub<NotificationsHub>("/hubs/notifications"); // expose the hub endpoint
// Server: await hub.Clients.User(id).SendAsync("postCreated", dto);

An empty hub plus one mapping line exposes /hubs/notifications. Server code pushes to a user with hub.Clients.User(id).SendAsync.

8 · Vue 3 Frontend Foundations

8.1 Project setup8.2 Components with script setup8.3 Props, emits, slots

This chapter spins up a Vue 3 project with Vite and TypeScript and teaches the component model everything else builds on. You write small focused components that communicate through props, events and slots and compose them into screens. Clean building blocks composed deliberately is the pattern the whole frontend follows.

8.1 Project setup

Scaffold a Vue project with the create-vue tool, which offers TypeScript, Vue Router and Pinia as options in one command. The Vite dev server provides a proxy so the browser calls /api and the dev server forwards it to the .NET API. That proxy makes the app behave as if it were same-origin during development.

npm create vue@latest client # scaffold a new Vue 3 app
# choose: TypeScript, Router, Pinia, ESLint, Prettier
cd client && npm install && npm run dev # install deps, start dev server

// vite.config.ts — proxy API in dev
export default defineConfig({
  server: { proxy: { '/api': 'https://localhost:7001' } }, // forward /api to the backend
  plugins: [vue()]
});

Scaffold the client, pick the good options, then point the Vite dev proxy at the API. During development the browser sees no cross-origin calls at all.

8.2 Components with script setup

script setup is the modern component style where the template compiles against the script block directly, giving full TypeScript inference. Combined with Composition API functions like ref and computed, it removes almost all the boilerplate the Options API needed. You get the same power with fewer indent levels and better editor support.

<script setup lang="ts">
import { ref, computed } from 'vue'
const count = ref(0) // reactive state
const doubled = computed(() => count.value * 2) // derived, cached value
function inc() { count.value++ } // the only way to change count
</script>

<template>
  <button @click="inc">{{ count }} ({{ doubled }})</button>
</template>

A tiny script-setup component: ref for state, computed for a derived value, and a click handler updating both. Full TypeScript inference, no boilerplate.

8.3 Props, emits, slots

Props, emits and slots are the three channels of component communication: data flows in through props declared with defineProps, events flow out via defineEmits, and named slots using the well pattern define places where parent content is rendered. Getting these idioms right keeps components composable and reusable. Parents stay the source of truth while children stay dumb.

const props = defineProps<{ post: Post }>() // parent passes a post down
const emit = defineEmits<{ (e: 'select', id: number): void }>() // child announces the event

<article @click="emit('select', props.post.id)">{{ post.title }}</article>

Data flows in through props, events flow out through emits: clicking the article raises select with the post id and the parent owns the response.

Prefer <script setup> + Composition API for new code: it is the modern default and plays best with TypeScript inference.

9 · Routing, State & Data Fetching

9.1 Vue Router9.2 Pinia stores9.3 A typed API client

This chapter covers how a Vue app moves: Vue Router defines the screens for each path, Pinia holds shared state, and a typed API client talks to the backend. Every feature you build ends up touching all three. Together the trio turns a set of components into a navigable, stateful application.

9.1 Vue Router

Vue Router maps each path to a component through the routes array and a router-view placeholder, with navigation guards such as beforeEach checking authentication and redirecting when required. Routes pass params to views as props to keep them decoupled and easy to reuse. Lazy-loaded routes with dynamic imports keep the initial bundle small.

const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', component: HomeView },
    { path: '/posts/:id', component: PostView, props: true }, // id becomes a prop
    { path: '/login', component: LoginView, meta: { public: true } }, // skips the guard
  ],
})

router.beforeEach((to) => {
  if (!to.meta.public && !useAuth().isLoggedIn) return '/login' // redirect guests to login
})

Paths map to components; the login route opts out via meta.public. A beforeEach guard redirects anyone unauthenticated back to /login.

9.2 Pinia stores

Pinia stores central state using setup-style stores defined with defineStore, where plain refs from Composition API become reactive state and functions become actions. Components read state and call actions through the store, never fetching directly from the API themselves. The store stays the single owner of its data, and components stay simple consumers.

export const usePosts = defineStore('posts', () => { // setup-style store
  const items = ref<Post[]>([])
  const loading = ref(false)
  async function fetchAll() {
    loading.value = true
    try { items.value = await api.get('/posts') } // fill state from the API
    finally { loading.value = false }
  }
  return { items, loading, fetchAll }
})

A setup-style Pinia store wraps items and loading, and fetchAll fills them through try/finally. Components subscribe to state instead of fetching directly.

9.3 A typed API client

A typed API client is one axios instance configured once with the base URL, withCredentials for cookies, and interceptors that attach tokens and refresh them on a 401. Response errors are normalised into one shape in the response interceptor, so every caller handles failures the same way. TypeScript types generated from the OpenAPI spec keep payloads aligned with the server.

const api = axios.create({ baseURL: '/api/v1', withCredentials: true }) // shared client with cookies

api.interceptors.response.use(r => r.data, async (err) => {
  if (err.response?.status === 401) await refreshToken() // silent refresh on expiry
  return Promise.reject(err)
})

One axios instance carries the base URL and cookies, an interceptor unwraps response data, and a 401 triggers a silent token refresh before the caller notices.

10 · Forms & UI Patterns in Vue

10.1 Forms and validation10.2 Loading, empty and error states10.3 Component performance

This chapter is the UX plumbing that separates a demo from a product: form validation, loading states and rendering performance. Users feel this chapter on every click, so the patterns here matter as much as the business logic. Handle each case explicitly and your app never leaves the user staring at a blank screen.

10.1 Forms and validation

Client-side validation exists for UX, while server-side validation remains the truth. Mirror the rules in the form with something like VeeValidate or simple computed errors, then map any server error responses back onto the matching field. Both layers end up agreeing on what is valid, and the user gets feedback instantly instead of after a round trip.

const form = reactive({ title: '', body: '' }) // two-way form state
const errors = ref<Record<string, string[]>>({})

async function submit() {
  try { await api.post('/posts', form); router.push('/posts') }
  catch (e) { errors.value = e.response?.data?.errors ?? {} } // surface server errors by field
}

A reactive form posts to the API, navigates on success, and maps server validation errors straight back onto fields on failure — the server stays the source of truth.

Validate on the server (source of truth) and mirror rules on the client (for UX) with libraries like VeeValidate + Zod.

10.2 Loading, empty and error states

Every asynchronous view needs three explicit states plus success: loading, empty, and error, then the data itself. A common approach is a small composable that tracks status along with the data, with a loading skeleton while fetching, an empty message when there is nothing, and an error panel with a retry button on failure. Users are never left staring at a blank screen.

  • Every async view needs three states: loading, empty, error — plus success.
  • Disable submit while in flight; show optimistic updates with rollback.
  • Never leave the user staring at a blank screen.

10.3 Component performance

Component performance work starts with cheap structural wins: lazy-load routes with dynamic imports, virtualise long lists with something like vue-virtual-scroller, and keep v-for keys stable so the renderer can reuse DOM nodes. Cheap changes show up immediately in load time and scrolling smoothness. Measure the impact before reaching for more exotic tinkering.

<!-- lazy-load routes -->
{ path: '/posts', component: () => import('./PostList.vue') }

<!-- virtualise long lists -->
<VirtualList :items="rows" :item-height="48" />

<!-- keep stable keys, avoid v-if/f structural churn -->

Three cheap, high-impact habits: lazy-import routes, virtualise long lists, and keep keys stable. The inline comments are the whole playbook.

11 · Integrating SPA and API

11.1 CORS and cookies11.2 Shared types11.3 One container, both halves

This chapter makes the SPA and API behave like one system by handling CORS, sharing types and shipping a single deployable. You configure CORS on the API, generate TypeScript types from the OpenAPI spec, and publish the Vue build into the API’s static files. Doing this removes entire classes of drift and CORS pain.

11.1 CORS and cookies

The browser blocks cross-origin calls unless the API opts in with the UseCors middleware and a policy that allows the SPA origin. When cookies are involved, the policy must allow credentials and the client must send withCredentials, which makes CORS stricter still. Deploying both halves under the same origin sidesteps the whole problem entirely.

builder.Services.AddCors(o => o.AddPolicy("spa", p => p
    .WithOrigins("https://app.example.com") // only trust the SPA origin
    .AllowAnyHeader().AllowAnyMethod().AllowCredentials())); // credentials allowed

// Same-site deployment (reverse proxy) avoids CORS entirely. Prefer it in prod.

A CORS policy trusts one SPA origin and allows credentials. The trailing note is the real tip: deploy same-origin in production and skip CORS altogether.

11.2 Shared types

Generate TypeScript from the HTTP API’s OpenAPI specification so the contract cannot drift silently. Tools such as openapi-typescript generate types and clients from openapi.json, and you commit the output and regenerate on schema changes. A schema mismatch then fails the build instead of surfacing in production.

Generate TypeScript types from the OpenAPI spec (NSwag / openapi-typescript) so the SPA and API can never silently drift. Commit the generated client.

11.3 One container, both halves

Publish the Vue build into the API’s static folders, typically wwwroot, and ship one container that serves the SPA and the JSON API together. The frame ignores CORS entirely because everything is same-origin. One deployable means simpler operations and a single place to version and roll back.

# Build Vue, copy dist into wwwroot, serve from ASP.NET Core
dotnet publish -c Release # dist lands in wwwroot and is served with the API
# Result: a single deployable that serves the SPA + API with no CORS.

Publish the release build and the Vue dist is served from wwwroot alongside the API. One deployable, no CORS, simplest possible operations.

12 · Real-time with SignalR + Vue

12.1 The Vue client12.2 Groups, presence and scale

This chapter uses SignalR to push updates from server to browser instead of polling for changes. The same hub pattern scales to presence indicators and collaborative features like typing notifications and cursor sharing. You learn the client connection, the wire protocol and how to target the right receivers at scale.

12.1 The Vue client

The Vue client wires the browser to the hub via HubConnectionBuilder with .withUrl to the hub endpoint and .configureLogging for diagnostics. You call server methods with invoke and receive pushes through .on handlers that update Pinia state live. WithAutomaticReconnect restores the connection without a page reload when the network drops.

import { HubConnectionBuilder } from '@microsoft/signalr'
const conn = new HubConnectionBuilder()
  .withUrl('/hubs/notifications', { withCredentials: true }) // connect with cookies
  .withAutomaticReconnect() // survive short drops
  .build()

conn.on('postCreated', (post) => store.items.unshift(post)) // prepend the pushed post
await conn.start()

The browser connects to the hub with cookies and automatic reconnect; on('postCreated') prepends the pushed post to the store so the UI updates live.

12.2 Groups, presence and scale

Instead of broadcasting to every connection, the server adds connections to groups so pushes reach only relevant recipients, using Groups methods and connection identifiers. When the app runs many nodes, the SignalR Redis backplane routes messages across servers, and group membership must be resynced after a reconnect. Clients restore state by pulling the API again after reconnecting.

  • Use groups per topic/user rather than broadcasting everything.
  • For multi-node scale, add the Azure SignalR Service or a Redis backplane.
  • Reconnect + resync: after reconnect, fetch missed state via the API.

13 · Testing the Full Stack

13.1 Backend tests13.2 Frontend tests

This chapter proves the contract works from both sides: integration tests for the API, unit tests for components, and a Playwright journey that runs the whole system end to end. Each layer catches different failures, and together they make changes safe. The frontend and backend tests are cheap once the scaffolding exists.

13.1 Backend tests

Backend tests use WebApplicationFactory to spin up your real application in memory. Integration tests then hit the true HTTP middleware pipeline, controllers and EF Core-backed data against a test database without a live server. That means the tests exercise the same code paths production will use.

public class PostTests(WebApplicationFactory<Program> factory)
    : IClassFixture<WebApplicationFactory<Program>>
{
    [Fact]
    public async Task Creates_post()
    {
        var client = factory.CreateClient(); // in-memory test server
        var res = await client.PostAsJsonAsync("/api/v1/posts", // real HTTP pipeline
            new { title = "Hi", body = "Body text" });
        res.EnsureSuccessStatusCode(); // throws unless 2xx
    }
}

An integration test via WebApplicationFactory: POST to the real HTTP pipeline with a JSON body and assert the 2xx status, no external server needed.

13.2 Frontend tests

Frontend tests split between Vitest for unit-testing components and Playwright for driving a real browser end to end. Vitest mounts single components with @vue/test-utils and mocks Pinia or the API, while Playwright clicks through actual screens against a running backend. Both are cheap to add once the project is scaffolded, and each catches a different failure class.

// Vitest + Vue Test Utils
import { mount } from '@vue/test-utils'
test('increments', async () => {
  const w = mount(Counter) // mount the component
  await w.find('button').trigger('click') // simulate the click
  expect(w.text()).toContain('1') // assert the rendered count
})

// End-to-end: Playwright drives the real app.
test('login flow', async ({ page }) => {
  await page.goto('/login') // start in a real browser
  await page.fill('#email', 'a@b.c')
  await page.click('button[type=submit]')
  await expect(page).toHaveURL('/dashboard') // guard redirected successfully
})

Two layers in one block: Vitest mounts the component, clicks and asserts output; Playwright drives the real login journey in a browser to its destination.

14 · Observability & Operations

14.1 Structured logging and tracing14.2 Health checks14.3 What to watch

This chapter is about knowing what is happening in production: structured logs, distributed tracing, health checks and a few metrics that matter. You can only fix what you can see, so the goal is a system you can interrogate after the fact. Each piece feeds a distinct part of an operations dashboard.

14.1 Structured logging and tracing

Structured logging writes JSON lines with the built-in ILogger support so every event is searchable, and the ASP.NET Core console formatter makes the format consistent out of the box. OpenTelemetry tracing follows a request across services by carrying a trace ID and emitting spans. Correlation IDs in logs and traces thread the pieces back together into one request timeline.

builder.Logging.AddJsonConsole(); // machine-readable output
builder.Services.AddOpenTelemetry() // enable tracing and metrics
    .WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation())
    .WithMetrics(m => m.AddAspNetCoreInstrumentation());

// Correlation IDs flow from the SPA request through the API to the database.

JSON console logging plus OpenTelemetry tracing and metrics instrumentation on the request path. Correlation ids tie the SPA request all the way to the database.

14.2 Health checks

Health checks expose a probe endpoint for load balancers and orchestrators such as Kubernetes. You add checks for critical dependencies like the database or Redis with AddHealthChecks and MapHealthChecks, so the probe verifies more than just that the process is still running. Unhealthy instances then get pulled from rotation.

builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>() // database reachability
    .AddRedis(builder.Configuration["Redis"]!); // cache reachability

app.MapHealthChecks("/healthz"); // orchestration probes this path

Health probes for the database and Redis, exposed at /healthz. Load balancers and Kubernetes check exactly this endpoint before routing traffic.

14.3 What to watch

Pick a few metrics with thresholds instead of trying to watch everything. The useful set on an API is latency percentiles like p95 and p99, error rate, slow database queries and queue depth. Everything else is noise. Monitoring these few numbers tells you whether the app is meeting its service-level objectives.

  • API latency p95/p99, error rate, throughput.
  • Database: slow queries, connection pool saturation.
  • Frontend: Core Web Vitals from real users.
  • Queue depth and background job failures.

15 · Deployment & Scaling

15.1 Containerising15.2 Scaling the API15.3 CI/CD

This chapter ships the system and grows it: one Docker image, stateless replicas and a CI pipeline that makes deploys boring. The same process takes you from one node to many by never storing state in the app process. Deployments become repeatable and rollbacks become a one-command operation.

15.1 Containerising

Containerising uses a multi-stage Dockerfile where a full SDK image builds the app and a slim runtime-only image ships it. The final image is built with dotnet publish, runs the production framework, and is then registered and pushed with the standard docker commands. Small, secure images deploy anywhere that runs a container runtime.

FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build # full SDK for building
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app # compile and package

FROM mcr.microsoft.com/dotnet/aspnet:9.0 # slim runtime image
WORKDIR /app
COPY --from=build /app . # take only the publish output
ENTRYPOINT ["dotnet", "Api.dll"]

A two-stage Dockerfile: the SDK stage builds and publishes, then a slim aspnet image copies only the output. Small, fast, production-shaped.

15.2 Scaling the API

Scaling stays easy when the API remains stateless, so any request can be served by any replica without shared local state. You add replicas behind the load balancer, introduce read replicas for the database, and put caching in front of expensive reads. Horizontal growth then never changes the shape of the code.

  • Stateless API + sticky-free load balancing; sessions in Redis or JWT.
  • Scale horizontally; scale the DB vertically then add read replicas.
  • Cache aggressively in front of expensive reads.
  • Offload CPU work to background workers.
  • Serve the SPA from a CDN.

15.3 CI/CD

A CI/CD pipeline runs tests and publishes a versioned Docker image on every push, triggered by the platform of your choice. The pipeline builds the frontend and backend, runs the suites, and pushes an image that carries a build number. Deploys become repeatable steps and a rollback means promoting the previous image.

- run: dotnet test # fail on regressions
- run: dotnet publish -c Release
- run: docker build -t ghcr.io/acme/app:$GITHUB_SHA . # tag with the commit sha
- run: docker push ghcr.io/acme/app:$GITHUB_SHA # push the image
# then deploy via Argo CD / kubectl set image, with canary + rollback.

A CI pipeline that tests, publishes, builds a SHA-tagged image and pushes it. The trailing line is the key habit: deploy with canary and rollback.

16 · Performance Tuning

16.1 Backend16.2 Frontend

This chapter makes the system measurably faster instead of guessing: query tuning on the backend, bundle splitting on the frontend, and real-user metrics to prove the result. The discipline is always measure, change, re-measure. Most of the wins come from removing work rather than cleverer code.

16.1 Backend

Backend tuning projects queries to DTOs, adds indexes on filter columns and pools database connections. Duplicate or inefficient SQL is found by logging the queries EF Core generates. BenchmarkDotNet measures hot paths carefully before you trust intuition about which change helps.

  • Project queries; avoid SELECT *; use AsNoTracking for reads.
  • Add indexes for filters/joins; watch for full scans.
  • Pool connections; enable response compression and output caching.
  • Use BenchmarkDotNet before optimising by intuition.

16.2 Frontend

Frontend tuning splits the bundle by route with dynamic imports and shrinks what ships by replacing heavy dependencies with lighter ones. Lazy-loaded routes shorten first paint and code-splitting means users download only what the current screen needs. Real-user metrics from the browser prove which optimisations matter.

  • Code-split by route; tree-shake; analyse the bundle.
  • Virtualise long lists; debounce search; abort in-flight requests.
  • Cache API responses client-side; use skeleton loaders.
  • Measure with Lighthouse and real-user metrics.
