0 · Orientation

Spring Boot is production-grade Spring, wired for you. It is not a different framework and it is not a replacement for the Spring Framework — it is a layer of defaults and conventions on top of it, plus an embedded server and an opinionated build plugin. This guide targets Spring Boot 3.5.x, Spring Framework 6.2.x, Jakarta EE 10 (Servlet 6.0), and Java 21 as the baseline, and every code sample compiles and runs as shown.

0.1 What Spring Boot actually is

Spring Boot is a collection of conventions that turn a general-purpose dependency-injection container into a runnable application in three lines. Understanding which layer does what removes most of the confusion people have when something "just works" and they cannot find out why.

The problem it solves

The Spring Framework gave Java a coherent way to assemble objects: declare what a component needs, let the container supply it, and never call new on an infrastructure class again. What it did not give you was a starting point. A 2012-era Spring application needed a web.xml, an external servlet container to deploy into, a DispatcherServlet definition, a transaction manager, a data source, dozens of XML or @Configuration classes, and a war file. All of it was boilerplate that varied only in details, and every team got some of it subtly wrong — a missing @ComponentScan base package, a transaction manager wired to the wrong data source, a Jackson message converter declared after the handler adapter.

Spring Boot answers three questions with defaults rather than configuration. What dependencies do I need? — a starter brings a curated, version-aligned set. How do I wire them together? — auto-configuration inspects the classpath and creates the beans the jars themselves declare they need. How do I run it? — an embedded Tomcat (or Jetty, or Reactor Netty, or Undertow) is started in the same JVM as your main method, producing one executable jar.

The three moving parts

A Spring Boot application is exactly three things working together, and each is separable. The build plugin (spring-boot-maven-plugin or the Gradle org.springframework.boot plugin) repackages the jar with a nested-dependency layout and a launcher. The auto-configuration engine reads condition reports from the classpath and registers beans. The SpringApplication bootstrap creates the ApplicationContext, applies the environment, starts the server, and publishes lifecycle events. Nothing else is magic; everything else is the Spring Framework you already had.

// src/main/java/com/example/demo/DemoApplication.java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication          // = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
@RestController
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @GetMapping("/hello")
    String hello() {
        return "Hello from Spring Boot";
    }
}

What it deliberately does not do

Boot does not choose your architecture. It will happily host a 40 000-line @RestController with a data source injected directly into it. It does not enforce layering, it does not stop you from putting business logic in an entity, and it does not hide the container: every bean Boot registers is visible in the ApplicationContext and overridable. That is the trade-off — the defaults are strong enough to be useful and weak enough to be replaced, which means they are also weak enough to be wrong for your system without the compiler noticing.

The most valuable single debugging technique in Boot is the auto-configuration report. It lists every auto-configuration considered, every one matched, and the exact condition that made an unmatched one fail. Start there before reading any source.

0.2 Auto-configuration and conditional beans

Auto-configuration is not a scanner that guesses. It is a fixed list of ordinary @Configuration classes, each guarded by conditions, shipped inside the Spring Boot jars and evaluated against your classpath at startup.

How the pieces are discovered

Every Boot module that ships auto-configuration contains a file at META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports listing class names, one per line. @EnableAutoConfiguration reads every such file on the classpath and feeds the union into the context. In Spring Boot 2.7 the new imports file was introduced alongside spring.factories; from Boot 3.0 the old EnableAutoConfiguration key in spring.factories is no longer read, so a third-party starter written for Boot 2 that only declares spring.factories will silently stop auto-configuring on upgrade. This is one of the most common migration failures and it produces no error message.

The order in which these configurations apply is not alphabetical and not the order in the file. @AutoConfiguration(before = …, after = …) and the older @AutoConfigureBefore / @AutoConfigureAfter declare dependencies between them, and Boot sorts the graph so an infrastructure bean exists before the thing that consumes it. When you write your own auto-configuration you participate in that ordering; when you write a plain @Configuration in your application it always wins over auto-configuration because user configuration is registered first and @ConditionalOnMissingBean then backs off.

@ConditionalOn… is the whole trick

Conditions are what make a fixed list of configurations adapt to arbitrary applications. The important ones:

ConditionMatches whenTypical use
@ConditionalOnClassA class is on the classpathThe jar that needs the class is present, so wire it up
@ConditionalOnMissingBeanNo bean of that type is already registeredSupply a default that the user can override
@ConditionalOnPropertyA property has (or lacks) a given valueOpt-in features, e.g. spring.hateoas.use-hal-as-default-json-media-type
@ConditionalOnBeanA bean already existsOnly configure a filter if a SecurityFilterChain exists
@ConditionalOnWebApplicationThe application type is SERVLET or REACTIVESkip servlet filters in a batch job
@ConditionalOnResourceA resource path existsOnly read a keystore if the file is present

The asymmetry between @ConditionalOnMissingBean and @ConditionalOnBean matters and is a frequent bug source: missing-bean conditions are only reliable on auto-configuration classes, not on user @Configuration classes. The reason is that auto-configurations are processed last, after all user bean definitions are known, so "what is missing" is a meaningful question. Inside your own configuration the full set is not yet registered and the answer is order-dependent.

// A minimal user-defined auto-configuration.
// File: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
// com.example.greeting.GreetingAutoConfiguration

package com.example.greeting;

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;

@AutoConfiguration
@EnableConfigurationProperties(GreetingProperties.class)
@ConditionalOnProperty(prefix = "app.greeting", name = "enabled")   // (matchIfMissing = false)
public class GreetingAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                 // a user-declared Greeter always wins
    Greeter defaultGreeter(GreetingProperties props) {
        return new Greeter(props.getPrefix(), props.getLocale());
    }
}

Reading the condition report

Run with --debug (or set debug=true in application.properties) and Boot prints three groups to stdout: Positive matches, Negative matches, and Exclusions. Each negative match names the auto-configuration class and the condition that failed — for example DataSourceAutoConfiguration#dataSource did not match: @ConditionalOnMissingBean found beans of type DataSource. That single sentence usually answers "why did Boot not configure X" immediately.

For a machine-readable view use the Actuator conditions endpoint: GET /actuator/conditions returns the same data as JSON, filterable with ?pattern=DataSource. It is safe to enable in a test profile and far easier to diff between two branches than console output.

# shell - the two ways to see why a bean was or was not created
java -jar app.jar --debug | grep -A2 "DataSourceAutoConfiguration"

# or, with the actuator on the classpath and the endpoint exposed:
curl -s localhost:8080/actuator/conditions?pattern=DataSource | jq '.contexts[].negativeMatches'

Excluding and overriding

You can turn an auto-configuration off completely with @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) or the property spring.autoconfigure.exclude=…. Prefer overriding to excluding: declaring your own @Bean of the expected type lets @ConditionalOnMissingBean do the work, keeps the rest of the configuration (health indicators, metrics, JPA integration) intact, and does not need to be revisited when the auto-configuration class is renamed. Exclusion is the right tool only when the auto-configuration does something you cannot neutralise by supplying a bean — for instance when you want no datasource at all in a service that has the JDBC driver on the classpath transitively.

Do not confuse @ConditionalOnMissingBean with bean overriding. If two @Bean methods of the same name are both registered, Boot 2.1 and later fail startup with BeanDefinitionOverrideException rather than silently taking the last one. Set spring.main.allow-bean-definition-overriding=true only if you genuinely need it, and treat its appearance in a codebase as a smell.

0.3 Starters and the dependency model

A starter is a pom with no code. Its entire content is a set of dependencies, chosen so the jars work together. That is both its value and its cost.

One dependency, many jars

spring-boot-starter-web resolves to roughly twenty transitive artifacts: Spring MVC, Jackson databind, the Tomcat embedded jars, spring-boot-starter-json, validation support, logging, and the core spring-boot-starter. Before starters, this list was copied from a tutorial and drifted; the versions of Jackson and Spring were independently chosen, and a Jackson minor bump could change serialisation defaults across the whole application. A starter makes the set a single versioned unit.

The BOM and version alignment

spring-boot-dependencies is a bill of materials: a pom containing dependencyManagement entries for about 1 400 artifacts — Spring Framework, Jackson, Hibernate, Tomcat, Logback, Micrometer, Flyway, Testcontainers, the Kafka and Rabbit clients, and so on. When you use the Maven parent or the Gradle plugin, importing that BOM into your build means you never write a version for a managed dependency. This is the single biggest practical difference between a Boot project and a plain Spring one: the version matrix is tested as a set by the Boot team, and an upgrade is one number in one place.

<!-- pom.xml - the entire inheritance that makes version management work -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.5.6</version>
  <relativePath/>
</parent>

<properties>
  <java.version>21</java.version>
</properties>

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <!-- deliberately no <version>: it comes from the BOM -->
</dependencies>

Escaping the BOM on purpose

The BOM is a default, not a fence. To take a newer library you override the version property the BOM uses — the property names are documented, e.g. <jackson-bom.version>, <hibernate.version>, <testcontainers.version> — rather than pinning the dependency itself. Property overrides keep the transitive set consistent; pinning one artifact often leaves a sibling at the BOM version and produces NoSuchMethodError at runtime. For a genuinely unmanaged library, import its own BOM (<scope>import</scope><type>pom</type>) so its transitive set also stays coherent.

In Gradle the same mechanism is io.spring.dependency-management plus implementation(platform(SpringBootPlugin.BOM_COORDINATES)), or the newer platform("org.springframework.boot:spring-boot-dependencies:3.5.6") with no plugin at all. Gradle's own version catalog (gradle/libs.versions.toml) composes cleanly with a platform and is the current idiomatic choice for multi-module builds.

A starter brings runtime behaviour, not just types. Replacing spring-boot-starter-web with the three jars it contains changes nothing about your code but removes the auto-configuration module — no DispatcherServlet, no embedded server. The starter's transitive closure is the feature.

0.4 Spring Framework vs Spring Boot

"Spring" names two products with the same vocabulary. Knowing the boundary tells you where to look when something is missing, and it tells you which knowledge transfers to Boot 4 and beyond.

What Boot adds, precisely

The Spring Framework provides the container, the programming model (annotations, AOP proxies, transactions, MVC, WebFlux, JdbcClient, RestClient), and the abstractions. Spring Boot provides four things the Framework does not: the auto-configuration catalog, starters, the executable-jar build plugin with an embedded runtime, and externalised configuration — the property system with profiles, relaxed binding and application.yml. Actuator and DevTools are separate Boot modules, not Framework features.

This is why a Boot upgrade is not the same event as a Framework upgrade. Boot 3.5 pins Spring Framework 6.2; Boot 3.4 pinned 6.2; Boot 3.3 pinned 6.1. Spring Framework 6.1 introduced RestClient and JdbcClient; Boot 3.2 was the first release whose managed version included them. The feature exists in the Framework the day the Framework ships, and becomes a one-line dependency the day Boot re-pins it.

What you still must know from the Framework

Everything that actually happens at runtime is Framework behaviour. Bean lifecycle and scoping, proxy semantics for @Transactional and @Cacheable (self-invocation bypasses the proxy), ApplicationEvent propagation, the DispatcherServlet request pipeline, HandlerMethodArgumentResolver ordering, exception resolution. A Boot developer who never reads the Framework docs will be able to start applications quickly and will be unable to explain a self-invocation transaction bug or why @Async on a private method does nothing.

// Plain Spring (no Boot): the wiring Boot would have generated for you.
// ~40 lines to get a web server with Jackson and a datasource.
var ctx = new AnnotationConfigWebApplicationContext();
ctx.register(WebConfig.class);                     // @EnableWebMvc, converters, view resolvers
ctx.register(DataSourceConfig.class);              // DataSource, JdbcTemplate, TransactionManager
ctx.register(ComponentScanConfig.class);           // where to look for @Service/@Repository

var tomcat = new Tomcat();                          // you own the container lifecycle
tomcat.setPort(8080);
tomcat.getConnector();
tomcat.addWebapp("", new File("src/main/webapp").getAbsolutePath());
tomcat.start();

Boot replaces those forty lines with SpringApplication.run(App.class, args), and replaces the external Tomcat with an embedded one started by ServletWebServerApplicationContext. Nothing about the @Service classes in the middle changes.

When to use the Framework without Boot

Boot is the right default for services, APIs and batch jobs. Plain Spring remains reasonable for a library that must not impose a container on its consumers (a Boot auto-configuration is the usual compromise: Framework-only code plus a Boot module that wires it), for a WAR deployed into a shared application server under operations control, and for very small command-line utilities where an embedded container and a 30 MB classpath are unwelcome overhead. In all three cases the cost is the version matrix and the configuration you now own — a cost teams routinely underestimate.

0.5 Prerequisites, versions and the Jakarta namespace

Spring Boot 3 was a deliberately breaking release: the Java baseline moved, the enterprise namespace moved, and several long-deprecated defaults were removed. Getting these three right up front saves a painful migration later.

Java and build tool versions

Spring Boot 3.x requires Java 17 minimum and is tested against 17 through 25. Choose Java 21 LTS for new work: it is the version Boot's own CI exercises hardest after the minimum, it gives you records, sealed types, pattern matching for switch and text blocks as non-preview features, and it gives you virtual threads — which Boot can turn on with one property (see chapter 9). Java 25 LTS is supported by Boot 3.5 and is a reasonable target for a new greenfield service in 2026; the cost is a shorter track record in third-party agents and profilers.

The javax → jakarta rename

In 2017 Oracle donated Java EE to the Eclipse Foundation, but the javax.* package namespace stayed under Oracle's control and could not be used by the new project. Jakarta EE 9 therefore renamed every package: javax.persistence became jakarta.persistence, javax.servlet became jakarta.servlet, javax.validation became jakarta.validation, and so on. Spring Framework 6 / Boot 3 adopted Jakarta EE 9+ wholesale, so everything in the enterprise namespace is jakarta.* in this guide. Framework's own packages are unchanged: org.springframework.*.

This is a mechanical but non-optional migration for any Boot 2 application. Every import changes, and every library that still ships javax.* types — older Hibernate Validator, older springfox, older Jackson modules — is incompatible until it releases a Jakarta build. Spring Boot 3.0 also removed the deprecated SpringFox-style integration and the WebSecurityConfigurerAdapter class, and changed several property names; the Boot 3.0 migration guide enumerates them.

import javax.persistence.Entity;            // import jakarta.persistence.Entity;
import javax.persistence.Id;                // import jakarta.persistence.Id;
import javax.servlet.http.HttpServlet;      // import jakarta.servlet.http.HttpServlet;
import javax.validation.constraints.NotBlank; // import jakarta.validation.constraints.NotBlank;
import javax.annotation.PostConstruct;      // import jakarta.annotation.PostConstruct;

Servlet vs reactive: pick one, knowingly

Boot inspects the classpath to decide the application type. With both spring-boot-starter-web and spring-boot-starter-webflux present it starts a servlet application running Spring MVC and ignores WebFlux's controller layer unless you force it. That behaviour is the source of the common "why is my reactive handler not called" report. The relaxation is deliberate — WebFlux is still used for WebClient and the reactive clients — but the two stacks are different programming models, not a performance option. Choose WebFlux when you have many slow downstream calls and a non-blocking driver for each; choose MVC everywhere else, including when you plan to use virtual threads.

Add spring-boot-starter-validation even in a service that only consumes messages. Bean Validation is not web-specific, and having Validator on the classpath turns a class of silent data-quality bugs into startup-time failures when you annotate @ConfigurationProperties or method parameters.

1 · Project setup

The first twenty minutes of a Spring Boot project decide how painful the next two years will be: how dependencies are managed, how modules are split, how the application is started in a terminal and in a container. Everything in this chapter is the setup Boot generates, plus the reasoning behind each choice it made for you.

1.1 Spring Initializr: what it generates and why

Initializr (start.spring.io) is a project generator, not a runtime dependency. Its output is an ordinary Maven or Gradle project that has no link back to the site — you can regenerate, edit or abandon it without consequence.

The choices that matter

Four fields decide almost everything downstream. Project chooses Maven or Gradle. Language chooses Java, Kotlin or Groovy; Kotlin changes the build file's plugins and adds jackson-module-kotlin plus kotlin-reflect. Spring Boot version selects the Boot line — the four-option list shows only the current GA line and its milestones, deliberately hiding older releases so new projects start current. Java sets java.version, which the Boot parent turns into both maven.compiler.release and the plugin configuration, so the value you pick is the value the compiler enforces.

The Dependencies field is the part people over-fill. Each selection adds one starter. Adding both "Spring Web" and "Spring Reactive Web" produces an application that starts as a servlet one and quietly ignores your reactive handlers — a trap covered in section 1.4. Select the minimum and add later; a starter added by hand is one dependency line.

What the generated project contains

Initializr emits a build file, a wrapper (mvnw, mvnw.cmd, .mvn/wrapper/, or gradlew, gradlew.bat, gradle/wrapper/), the main application class, a single test that only asserts the context loads, application.properties, and a .gitignore. The wrapper is the important one and the one most often deleted by mistake: it pins the build-tool version in-repo, so a machine with no build tool installed can still build, and every developer and the CI runner use the byte-identical build tool. ./mvnw downloads its own Maven distribution on first run and never touches PATH.

# shell - generate a project without opening a browser (-d = dependencies)
curl -s https://start.spring.io/starter.zip \
  -d type=maven-project \
  -d language=java \
  -d bootVersion=3.5.6 \
  -d javaVersion=21 \
  -d groupId=com.example \
  -d artifactId=catalog \
  -d name=Catalog \
  -d packageName=com.example.catalog \
  -d dependencies=web,data-jpa,validation,actuator,postgresql \
  -o catalog.zip

unzip -q catalog.zip -d catalog && cd catalog

# First build downloads the wrapper's own Maven distribution, then the BOM set.
./mvnw -q test
./mvnw spring-boot:run

The generated test is a real test, not filler

@SpringBootTest on an empty test class does more than it looks like. It starts the full ApplicationContext: every auto-configuration is evaluated, every @Bean method runs, the embedded server is created (though not started on a port in the default MOCK web environment), and Bean Validation on @ConfigurationProperties fires. A misconfigured datasource URL, a missing property, a circular dependency between two services — all of these fail this test at build time rather than at 03:00 in production. Keep it, and keep it fast by giving it no conditions that need the network.

Initializr's Explore button (Ctrl+Space in the web UI or curl start.spring.io) prints the exact build file and application skeleton without downloading a zip. It is the fastest way to check the canonical dependency coordinates for a feature before editing a real pom.

1.2 The build file: Maven, Gradle, and plugin configuration

The build file is where a Spring Boot project is actually configured. The plugin on the classpath is what repackages the jar, and the parent or platform is what supplies every version number.

Maven: parent inheritance vs BOM import

Two Maven styles are both supported. The common one inherits from spring-boot-starter-parent, which gives dependency management, sensible plugin configuration, resource filtering with @…@ delimiters, and a default build with the Boot plugin bound to package. The alternative imports spring-boot-dependencies as a BOM and configures the plugin explicitly — necessary when the project already has a corporate parent it must inherit from, since Maven allows only one parent. The BOM import loses the pre-configured plugin behaviour, so the plugin block must be written out.

<!-- pom.xml - BOM-import style, for when another parent is mandatory -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.5.6</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <executions>
        <!-- repackages the jar at package time: nested jars + a Boot launcher -->
        <execution>
          <goals><goal>repackage</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Gradle: the plugin, the platform, and the toolchain

The Gradle plugin (org.springframework.boot) registers the bootJar, bootRun and bootBuildImage tasks, makes bootJar the default assemble output, and — with io.spring.dependency-management applied — imports the BOM automatically. Modern Gradle builds prefer a Java toolchain over a global JDK so the build is reproducible on any machine, and a version catalog over hard-coded strings so versions live in one file.

Choosing between them

Both produce the same artifact and use the same Boot features. Maven's advantage is uniformity: one correct way to write the build, so any Maven-experienced developer can read any project, and enterprise tooling understands it universally. Gradle's advantage is that the build is code — a Kotlin script can express conditional source sets and shared conventions in a buildSrc plugin, and it is measurably faster on large multi-module builds. If neither argument decides it, pick Maven for a small team and Gradle for a large one; the migration cost is real but bounded, and Boot's plugin is the part that does not change.

Never add a dependency version that the BOM already manages just to "make sure". A hard-coded Jackson or Spring version silently overrides the tested matrix and is the most common cause of runtime NoSuchMethodError after a Boot upgrade. To take a newer library, override the BOM's property instead, or import that library's own BOM.

1.3 Project layout and package structure

Boot imposes exactly one structural rule — component scanning starts at the @SpringBootApplication class's package — and leaves everything else to you. The default single-module layout is right far more often than people expect.

The one rule that is enforced

@SpringBootApplication implies @ComponentScan with no basePackages, which means "this package and everything below it". An application class in com.example.catalog scans com.example.catalog.* and nothing above it. Putting the application class in the default package, or in a sibling package to your code, produces the classic "my @Service is not found" NoSuchBeanDefinitionException — with no warning at startup, because scanning an empty or wrong package is not an error.

The layout that avoids the problem permanently is the one Initializr produces: the application class sits at the root of the package, and every feature lives in a subpackage.

src/main/java/com/example/catalog/
├─ CatalogApplication.java          # @SpringBootApplication - the scan root
├─ catalog/                        # feature/package-by-feature
│  ├─ Book.java                    # @Entity
│  ├─ BookRepository.java          # interface extends JpaRepository
│  ├─ CatalogService.java          # @Service - business rules, @Transactional
│  └─ BookController.java          # @RestController - HTTP only
├─ order/
│  ├─ Order.java
│  ├─ OrderRepository.java
│  └─ OrderService.java
└─ config/
   ├─ JacksonConfig.java           # @Configuration
   └─ HttpClientsConfig.java

src/main/resources/
├─ application.yml                 # base config for every profile
├─ application-local.yml           # profile-specific overrides
├─ db/migration/                   # Flyway scripts: V1__init.sql, V2__add_isbn.sql
└─ static/                         # served as-is at "/"

src/test/java/com/example/catalog/
├─ CatalogApplicationTests.java    # context-loads smoke test
├─ catalog/BookControllerTest.java # @WebMvcTest slice
└─ order/OrderRepositoryTest.java  # @DataJpaTest slice

Package by feature beats package by layer

Layering into controller/, service/, repository/, entity/ is the arrangement every tutorial shows and it degrades predictably: adding one feature touches four directories, a refactor of the "order" concept cannot be reviewed as one change, and package-private visibility — the only tool Java has for expressing "this belongs together" — cannot be used because the collaborators are in different packages. Package-by-feature keeps the four classes of a feature adjacent, so the change set is local and visibility can be tightened. Layered packaging is acceptable for genuinely cross-cutting concerns, which is exactly what the config/ package is for.

The test tree mirrors the main tree so that a class and its test are one navigation step apart. Boot's test slices (@WebMvcTest, @DataJpaTest) are selected by annotation rather than location, so there is no framework constraint here — only readability.

When to split into modules

A multi-module build (catalog-api, catalog-core, catalog-web) buys three concrete things: a compile-time dependency graph that prevents the web layer from reaching into internals, per-module test scope, and the ability to deploy two services from one repository. It costs build configuration and friction on every new dependency. Split when you need enforcement, not when the package count feels high. If you do split, keep the @SpringBootApplication class in the module that produces the executable jar and make sure scanning still covers the other modules' packages — either by nesting the packages under the app's root or by adding scanBasePackages.

1.4 Running the application

There are four ways to start a Boot application and they are not equivalent: the packaged jar runs the repackaged classpath, while spring-boot:run and the IDE run your compiled classes with a different class loading order. Most "it worked locally" failures live in that gap.

The four ways, and what each proves

From the IDE — fastest feedback, and how you develop. It uses the IDE's compiled classes, its own resource copying, and (depending on the IDE) a run configuration with environment variables and VM options that exist nowhere else. mvnw spring-boot:run / gradlew bootRun — closest to production classpath while still using exploded classes and your local source tree; the standard way to run against a local database with the local profile active. java -jar target/app.jar — the real artifact: run it before every merge. In a container — the real artifact under the real JVM flags and the real filesystem; the only place a native-image or cgroup-aware memory setting can be validated.

# shell - run, and run the way production will
./mvnw spring-boot:run
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=9090,--logging.level.com.example=DEBUG

./mvnw -DskipTests package          # produces target/catalog-0.0.1-SNAPSHOT.jar
java -jar target/catalog-0.0.1-SNAPSHOT.jar

# Boot's launcher supports extracted/"tools" mode without unzipping by hand:
java -Djarmode=tools -jar target/catalog-0.0.1-SNAPSHOT.jar list
java -Djarmode=tools -jar target/catalog-0.0.1-SNAPSHOT.jar extract --destination app/ && java -jar app/catalog-0.0.1-SNAPSHOT.jar

Precedence: who wins when two places set a value

The property sources are consulted in a fixed order, and later wins. From lowest to highest priority the ones you will actually meet: application.properties inside the jar, then profile-specific files, then application.properties next to the jar in the current directory, then the config/ subdirectory, then environment variables, then SPRING_APPLICATION_JSON, then command-line arguments. Programmatic defaults set with SpringApplication.setDefaultProperties sit below everything.

Two consequences follow. First, an environment variable always beats a file, so a container with SPRING_DATASOURCE_URL set cannot be reconfigured by editing the jar's properties. Second, command-line arguments beat everything except a test's @TestPropertySource, which is why integration tests can force a value that a stray local environment variable would otherwise break.

# shell - the same three settings, four ways, in increasing precedence
java -jar app.jar                                  # 1. application.yml inside the jar
java -jar app.jar --spring.profiles.active=prod     # 2. profile-specific file
SPRING_DATASOURCE_URL=jdbc:... java -jar app.jar    # 3. environment variable (relaxed binding)
java -jar app.jar --server.port=8081               # 4. command-line argument (highest)

# Boot binds all four spellings to the same property:
#   server.port  SERVER_PORT  server_port  SERVER_PORT_8081

Reading the startup log

The banner is noise; the four lines after it are the contract. Profiles tells you which configuration files were considered — if the list lacks the profile you expected, the problem is activation, not content. The Tomcat started on port(s) line confirms the server bound; port 8080 (http) versus nothing tells you whether the binding failed. The startup time from Started Application in 2.431 seconds is your regression signal — a jump means a new auto-configuration or a bean doing network I/O in @PostConstruct. The No active profile set, falling back to default profile: default warning is normal but should never appear for a service you deploy, because it means no profile was set at all.

Bind every deployment to an explicit profile. spring.profiles.active unset means the default profile is used, which is the profile you develop in — so a forgotten configuration is the difference between a local datasource and a local datasource in production.

1.5 DevTools, restart and what "hot reload" really means

DevTools is a development-only module that adds automatic restart, smarter caching defaults, and a browser reload trigger. It is one of the most misused dependencies in Boot because it behaves differently on different classpaths and it must never reach production.

What it actually does

DevTools runs two class loaders: a base loader for everything that changes rarely (the dependencies, the JDK, the Spring Boot jars) and a restart loader for your classes and resources. When a compiled class on the classpath changes, DevTools discards and recreates only the restart loader and then calls SpringApplication.run again inside the same JVM. Dependencies keep their loaded state, the JVM stays warm, and the restart takes roughly a tenth of the time a cold start does. This is why DevTools is dramatically faster than killing and relaunching the process, and also why it is not a hot-swap: the application context is destroyed and rebuilt. Anything held only in memory — an in-flight request, a scheduled task's local state, an in-memory H2 database unless configured otherwise — is lost.

<!-- pom.xml - DevTools is scope=provided so it cannot leak into a packaged jar -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-devtools</artifactId>
  <scope>provided</scope>
  <optional>true</optional>
</dependency>

# Optional: disable restart, keep LiveReload and the dev-only property defaults
# spring.devtools.restart.enabled=false
# Restart only when specific files change (live-reload for static assets instead):
# spring.devtools.restart.additional-exclude=static/**,public/**
# Programmatic form for a multi-module build:
#   System.setProperty("spring.devtools.restart.poll-interval", "1s");

Property and caching defaults that only apply in development

DevTools registers a DevToolsPropertyDefaultsPostProcessor that sets a documented set of properties to development-friendly values unless you override them: template caching off for Thymeleaf, Freemarker and Mustache, spring.mvc.log-resolved-exception=false, and static resource caching disabled. That is why a template edit shows up on refresh during development and why the same edit does not show up for a developer who forgot the dependency — the property defaults, not the restart, are what make the inner loop feel instant.

It also registers a LiveReload server on port 35729. With a browser extension or the IDE's built-in support, a successful restart triggers a page reload. Without the extension nothing listens and nothing happens; the embedded server is harmless but adds a port that some corporate laptops block, producing a startup stack trace that looks alarming and is irrelevant.

Why it must not reach production

The provided (Maven) or developmentOnly (Gradle) scope removes DevTools from the repackaged jar, and Boot additionally disables restart when the application is run from a packed archive. Both guards exist because the consequences of a leak are severe: automatic restarts in response to classpath changes would restart a production service unpredictably, and the dev property defaults would silently disable caching under load. Belt and braces: keep the scope correct and set spring.devtools.restart.enabled=false in every non-dev profile, so a mistaken dependency cannot cause a restart storm.

DevTools does not help in a container. The restart triggers on classpath file changes, and a container's filesystem is read-only after the image is built. For a containerised inner loop, mount your source and use an IDE's debugger, or accept a rebuild — the restart mechanism has nothing to watch.

2 · Dependency injection and beans

Dependency injection is the reason Spring exists and the reason most Spring bugs happen. The container is not opaque — it is a map of bean definitions with a well-defined lifecycle — and almost every surprising behaviour is a consequence of one of its rules about when a bean is created and which instance is handed out.

2.1 The IoC container and the application context

Inversion of control means your classes never construct their collaborators; they declare what they need and something else decides what to pass. The container is the mechanism that makes that decision, and its two phases — registration and instantiation — explain most ordering problems.

Bean definitions, then bean instances

Startup happens in two distinct phases and confusing them is the root of many bugs. In the registration phase, the container reads sources — component-scanned classes, @Bean methods, auto-configuration classes, XML if you have any — and produces a BeanDefinition for each: a recipe holding the class, scope, laziness, and declared dependencies. No object is constructed yet, which is why conditions can be evaluated and why a bean may end up with no definition at all. Only in the instantiation phase are the objects created, their dependencies resolved, and the post-processors run.

This split is why @Conditional works at all: at registration time the container can ask "is a DataSource class on the classpath?" without having built anything. It is also why a circular dependency between two constructors cannot be fixed by reordering declarations — both recipes exist, and each waits for the other.

Lifecycle callbacks in the order they run

A single bean passes through a fixed sequence, and each step is a usable extension point. Knowing the order turns "where do I put this?" into a decision rather than a guess.

Why the injected object is sometimes not your class

Because postProcessAfterInitialization can replace the bean instance, what another bean receives for a @Transactional service is a CGLIB subclass (or a JDK dynamic proxy when the class implements interfaces), not the class you wrote. That proxy is what starts and commits the transaction, and it only intercepts calls made through the proxy reference. Calling this.save(…) inside the same class calls the real object directly, no proxy is involved, and no transaction is started. This is the single most common Spring bug and it belongs to the container's design, not to @Transactional.

A bean whose @PostConstruct performs network I/O makes startup — and every test — depend on an external system. If the call is unavoidable, do it in an ApplicationRunner or after an availability event instead, so the failure is logged and the process can decide to keep running.

2.2 Stereotypes: @Component, @Service, @Repository, @Controller

The four stereotypes are all @Component with a different name. Only two of them carry extra behaviour, and knowing which two is the difference between understanding the framework and cargo-culting annotations.

What actually differs

@Component is the base annotation. @Service and @Controller are pure aliases: they add no processing behaviour whatsoever. @Repository adds one thing — exception translation. A bean annotated @Repository gets a PersistenceExceptionTranslationPostProcessor applied, which converts vendor-specific exceptions (Hibernate's ConstraintViolationException, JDBCException, JPA's PersistenceException) into Spring's DataAccessException hierarchy. That translation is why @Transactional rolls back on DataIntegrityViolationException and why repository code can depend on a stable exception type when the ORM is swapped.

Spring Data repositories get this without the annotation, because the interface is proxied by a factory that installs translation itself. A hand-written class that uses JdbcClient or EntityManager directly does not; annotate it @Repository or the raw driver exception will escape through your service layer.

package com.example.catalog;

import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository                                  // required for exception translation
public class IsbnLookupDao {

    private final JdbcClient jdbc;

    public IsbnLookupDao(JdbcClient jdbc) { this.jdbc = jdbc; }

    public void insert(String isbn, String title) {
        try {
            jdbc.sql("insert into book(isbn, title) values (:isbn, :title)")
                .param("isbn", isbn).param("title", title)
                .update();
        } catch (DataIntegrityViolationException e) {
            // a stable, ORM-independent type - not org.postgresql.util.PSQLException
            throw new DuplicateIsbnException(isbn, e);
        }
    }
}

Choose the name that documents intent

Since @Service and @Controller are aliases, using them is a documentation choice — and a good one. A reader scanning a package sees the role of each class before opening it, and tooling (IDEA, Spring's own AOT hints, JDK Mission Control stack traces) groups them usefully. The convention this guide uses: @RestController/@Controller for the web boundary, @Service for transactional business logic, @Repository for persistence adapters that are not Spring Data interfaces, and plain @Component for utilities, filters, converters, mappers and ApplicationRunners.

The scanning rules people get wrong

Annotation scanning does not follow imports and does not follow the classpath at random: it starts at the base package and walks directories. Three failures follow directly. A class in com.example.other is invisible to an app rooted at com.example.catalog. A class in the default package is never scanned. And a wrapper package such as com.example.catalog.internal is scanned but its annotations may be missed if it contains only a package-info.java and no classes — the scanner historically only walked directories with at least one class.

Auto-configuration classes are not found by scanning at all; they come from the AutoConfiguration.imports files, which is why a starter works regardless of your package layout. That asymmetry is worth remembering: your own components need to be under the scan root, framework beans do not.

2.3 Constructor injection and why it is the default

Spring supports three injection mechanisms. Constructor injection is the recommended one for reasons that are structural rather than stylistic — the other two are supported mainly for legacy code and for framework-internal wiring.

Why the constructor wins

First, it makes dependencies mandatory and visible. A constructor parameter cannot be omitted, so the compiler and the container both refuse to create an object in a half-built state. @Autowired on a field means the container can create the object before assigning the field, so there is a window — exploited by circular dependencies — in which a bean exists with null collaborators. Second, constructor-injected fields can be final, which makes the object safely publishable and immutable; field injection cannot. Third, a constructor-injected class is a plain Java class: tests instantiate it with new and hand-written fakes and never need Spring or Mockito.

Since Spring 4.3 a class with exactly one constructor needs no @Autowired at all. Multiple constructors bring the requirement back, and the idiomatic answer is not to annotate but to have one primary constructor and expose extra construction paths as static factory methods or @Bean methods.

// Idiomatic constructor injection: final fields, no @Autowired, testable with plain new
package com.example.catalog;

import java.util.List;
import java.util.Optional;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CatalogService {

    private final BookRepository books;
    private final List priceProviders;   // all implementations, in @Order order

    public CatalogService(BookRepository books, List<PriceProvider> priceProviders) {
        this.books = books;
        this.priceProviders = List.copyOf(priceProviders);   // defensive copy, immutable
    }

    @Transactional(readOnly = true)
    public Optional<BookView> find(String isbn) {
        return books.findByIsbn(isbn).map(this::toView);
    }

    private BookView toView(Book book) {
        return new BookView(book.getIsbn(), book.getTitle(), book.getPrice());
    }
}

//   var repo = new InMemoryBookRepository();
//   var service = new CatalogService(repo, List.of(new FixedPriceProvider()));
//   assertThat(service.find("978-0-13-235088-4")).isPresent();

Collecting every implementation

Injecting a List<T>, Set<T> or Map<String, T> asks the container for all beans of that type. The list is ordered by @Order or Ordered; an unordered set is not. This is the standard extension-point pattern and it replaces most factories and if/else chains: define an interface, implement it per strategy, and let the container assemble the collection. A Map<String, T> keys by bean name, which is useful when the strategy key is configuration-driven.

The trade-off is that the collection is resolved at startup, so adding a bean silently changes behaviour at every call site that iterates the list. If order matters, declare it explicitly with @Order(10) rather than relying on discovery order, which is undefined for classes found by scanning.

ObjectProvider, @Lazy and optional dependencies

When a dependency genuinely may be absent, or when resolving it at startup would create a cycle, inject an ObjectProvider<T> instead of T. getIfAvailable() returns null when there is no bean, getIfUnique() returns null when there is more than one, and getObject() defers resolution until the call — which is the break-glass fix for a circular dependency, and a design smell worth logging with a TODO.

@Lazy on a constructor parameter injects a proxy that resolves the real bean on first use, and @Lazy on a @Bean or @Configuration class defers creation entirely until the bean is first requested. Both shorten startup; both turn a startup failure ("no such bean") into a runtime failure ("NoSuchBeanDefinitionException on first request"), which is usually a worse trade. Use laziness to break a cycle or to defer a genuinely expensive, rarely used resource — never as a general startup optimisation.

Optional dependencies expressed with Optional<T> as a constructor parameter were never supported for injection and are still not. Use ObjectProvider<T>, or annotate the parameter @Nullable and inject only multiple-constructor beans. The distinction matters because the failure is a startup error that reads as if the type were unknown.

2.4 @Configuration and @Bean: when to write Java configuration

Component scanning handles your own classes. Java configuration handles everything else — third-party types, objects built from other objects, and any bean you want to be able to override from a test or a library consumer.

Why @Configuration is subclassed

@Configuration is itself annotated @Component, but the container does something extra: it creates a CGLIB subclass of the class so that a call to one @Bean method from another returns the same instance rather than a fresh one. Without that, this configuration would create two DataSource objects:

package com.example.config;

import javax.sql.DataSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jdbc.core.simple.JdbcClient;
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;

@Configuration
public class DatabaseConfig {

    @Bean
    DataSource dataSource(DbProperties props) {          // called directly by the method below
        var cfg = new HikariConfig();
        cfg.setJdbcUrl(props.url());
        cfg.setUsername(props.username());
        cfg.setPassword(props.password());
        cfg.setMaximumPoolSize(props.poolSize());
        cfg.setPoolName("catalog-pool");
        return new HikariDataSource(cfg);
    }

    @Bean
    JdbcClient jdbcClient(DataSource dataSource) {         // preferred: ask the container
        return JdbcClient.create(dataSource);
    }
}

The CGLIB subclassing is why a @Configuration class must not be final and must not have only-private constructors, and why proxyBeanMethods = false exists. Setting proxyBeanMethods = false turns off subclassing: the class is instantiated plainly, so inter-method calls create new objects and each method must take its collaborators as parameters. It is faster to start (no CGLIB generation) and is the correct choice for large configuration classes; it is what @AutoConfiguration uses by default for exactly this reason.

When a separate class is right

Three cases justify a dedicated @Configuration class rather than another @Component. The type is third-party and cannot be annotated (RestClient, ObjectMapper with your modules, a TaskExecutor, a caching provider). The construction is conditional on configuration properties. Or you deliberately want a named, overridable bean that a test can replace with @TestConfiguration or a @MockitoBean. If none of those apply and the class is yours, annotate the class itself and let scanning find it.

// proxyBeanMethods = false: no CGLIB, faster startup, explicit dependencies.
// Each @Bean method receives what it needs as a parameter.
@Configuration(proxyBeanMethods = false)
class HttpClientConfig {

    @Bean
    RestClient catalogRestClient(RestClient.Builder builder, CatalogApiProperties props) {
        return builder
            .baseUrl(props.baseUrl())
            .defaultHeader(HttpHeaders.USER_AGENT, "catalog/1.0")
            .requestFactory(new JdkClientHttpRequestFactory(
                HttpClient.newBuilder().connectTimeout(props.connectTimeout()).build()))
            .build();
    }
}

Configuration class ordering pitfalls

Parameter injection between @Bean methods is order-independent: the container resolves the graph. What is not order-independent is anything done in a constructor or @PostConstruct of a configuration class, and anything relying on a BeanFactoryPostProcessor defined in the same class — such a processor must be static, because non-static ones cannot be created before the container that would create them. Both mistakes produce confusing "bean is not yet available" or class-loading errors; both are fixed by making the factory method static or by moving the logic into a BeanPostProcessor-free bean.

Two @Bean methods with the same name in different configuration classes are not merged. Beans are keyed by name, so the second registration overwrites the first or fails with BeanDefinitionOverrideException. Name your beans after their role, and when you intend to replace an auto-configured bean, use the same name Boot uses and rely on @ConditionalOnMissingBean — do not add allow-bean-definition-overriding.

2.5 Scopes, profiles and conditional registration

A scope decides how many instances exist and how long each lives. Profiles and conditions decide whether a definition exists at all. Together they are how one codebase produces a local, a test and a production configuration.

The scopes, and what mismatch looks like

Singleton is the default: one instance per ApplicationContext. Prototype creates a new instance per request, and the container does not manage its destruction — no @PreDestroy, so cleanup is the caller's job. Request, session and application are web scopes bound to the servlet lifecycle, and websocket binds to a WebSocket session. There is also a thread scope available in a Boot web application backed by a SimpleThreadScope, disabled by default.

@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
class RequestContext {
    private final String correlationId = UUID.randomUUID().toString();
    String correlationId() { return correlationId; }
}

// Without proxyMode, injecting a request-scoped bean into a singleton
// is a startup failure: the singleton outlives the request.
// proxyMode makes the injected reference a scoped proxy that resolves
// the real instance from the current request on each method call.

The proxy behaviour is the subtle part. A singleton cannot hold a request-scoped instance, so the container injects a proxy; every call on it looks up the current request's instance. This works with @Transactional and @Async because those are also proxies, and it breaks when code holds a reference to the target — for example by casting the proxy to the concrete class, which fails for a JDK proxy. Prefer interfaces for request-scoped beans, or force TARGET_CLASS.

Profiles: grouping configuration, not code

A profile is a named tag that activates a set of beans and property files. spring.profiles.active names the active profiles; spring.profiles.include adds more without replacing. A profile-specific file (application-prod.yml) is loaded after the base file and its keys win. On beans, @Profile("prod") registers only when that profile is active.

The common mistake is using profiles for environment values when they are better used for environment shapes. Five profiles each differing only in a datasource URL is five files to keep in sync; a single file with SPRING_DATASOURCE_URL supplied by the platform has one place to be wrong. Use profiles for genuine structural differences — an in-memory queue in tests, a real broker in production — and environment variables for values.

@Configuration
class MessagingConfig {

    @Bean
    @Profile("local")                        // in-memory, no broker needed for a laptop run
    MessagePublisher inMemoryPublisher() {
        return new LoggingMessagePublisher();
    }

    @Bean
    @Profile("!local")                       // production-shaped default: everything else
    @ConditionalOnProperty("app.messaging.brokers")
    MessagePublisher kafkaPublisher(KafkaTemplate<String, String> template) {
        return new KafkaMessagePublisher(template);
    }
}

Conditions beyond profiles

@ConditionalOnProperty is the switch that operators can actually flip, because it reads a property that an environment variable can set. @ConditionalOnMissingBean lets a consumer or a test replace a default. @ConditionalOnExpression evaluates a SpEL expression and should be a last resort — it is untyped, unchecked at build time, and easy to get wrong. The three tables in @ConditionalOnProperty — name, havingValue, matchIfMissing — cover almost every real case, and matchIfMissing = false (the default) means the feature is off unless deliberately enabled, which is the safer half of the boolean.

3 · Configuration

Configuration is the seam between one build artifact and every environment it runs in. Spring Boot's model is deliberately simple — a flat set of properties bound with relaxed rules into typed objects — and most production incidents that trace back to configuration are caused by binding that succeeded when it should have failed, or by a value that was read from somewhere the operator did not expect.

3.1 application.properties and application.yml

Both formats are first-class and equivalent; the loader parses whichever it finds. Choose one per repository and stay with it, because a mixed repository makes the effective value of a key impossible to find with a text search.

Format differences that actually bite

Properties files are flat key–value pairs, and every value is a string that Spring converts on demand. YAML is a nested document; the loader flattens it to dotted keys, so server.port: 8080 and server:\n port: 8080 end up identical. YAML's advantages are real for lists of objects — a list of datasources, a list of Kafka topics with per-topic settings — where the properties syntax degenerates into app.topic[0].name. Its disadvantages are also real: indentation is significant, a tab character is a parse error rather than a warning, and a multi-document file (separated by ---) can activate profiles invisibly.

YAML also silently converts some scalars. version: 1.0 is a number, version: "1.0" is a string; on and off are booleans under YAML 1.1 rules (Spring uses a SnakeYAML engine that resolves them as booleans in the standard schema), and port: 080 is a parse error because a leading zero means octal. Quote anything that is an identifier rather than a quantity.

Where the files are searched

The loader looks in four places, in increasing precedence: classpath:/, classpath:/config/, file:./ and file:./config/ and file:./config/*/. The leading optional: prefix is implicit for these locations. The consequence is that a file dropped next to the jar in a config/ directory overrides anything inside the jar with no rebuild — the mechanism behind the classic "twelve-factor" deploy where the artifact is immutable and the environment supplies the difference.

spring.config.import extends the list explicitly: optional:file:./secrets.properties, a Consul/Vault backend, or another profile's file. Imports are processed before the importing document's own keys, and an import without optional: makes a missing source a startup failure — which is usually what you want for a file that is genuinely required.

spring.application.name=catalog

spring.config.import=file:./config/required.properties
# Or opt in to a missing source being acceptable:
spring.config.import=optional:file:./config/overrides.properties,vault://secret/catalog

Placeholders, randomness and property references

Values may reference other properties with ${key} or defaults with ${key:default}. This is resolved in the same pass as binding, so a reference to an undefined key without a default is a startup failure with a clear message — which is a feature: it fails the deploy rather than producing a null. ${random.int}, ${random.uuid} and ${random.long(1,100)} are supported and re-evaluated per resolution, which makes them useful for test fixtures and dangerous for anything persisted.

Turn spring.jpa.open-in-view=false on deliberately and early. Boot warns at startup when it is enabled (the default) because it holds a Hibernate session open for the whole request, making lazy loading "work" on the web thread and masking a missing fetch plan until the day an endpoint is called from a batch job.

3.2 Typed configuration with @ConfigurationProperties

Reading properties with @Value("${…}") works and does not scale. @ConfigurationProperties binds a whole prefix into one object, with type conversion, validation and an IDE-visible contract.

Why the typed object wins

A class bound to a prefix gets five things @Value cannot give. Type conversion for durations, data sizes, enums, URIs and collections, using the same converters everywhere. Relaxed binding, so app.pricing.base-url, app.pricing.baseUrl, APP_PRICING_BASEURL and APP_PRICING_BASE_URL all reach the same field. Validation, via Jakarta Bean Validation annotations on the fields, failing startup when a value is absent or malformed. Metadata, generated by the annotation processor into META-INF/spring-configuration-metadata.json, which is what makes the key autocomplete in an IDE and what a config server can validate. And a single place to see every knob a component has.

@Value is still correct for a single value in a @Bean method or for a SpEL-derived value. It is wrong for anything with more than two related keys, and it is wrong for anything that should be validated, because a typo in a property name produces a null rather than an error.

package com.example.config;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotEmpty;
import java.net.URI;
import java.time.Duration;
import java.util.List;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "app.pricing")
public record PricingProperties(
        @NotEmpty List<@Valid Provider> providers,
        @Min(1) @Max(3) int retries,
        Duration timeout) {

    public record Provider(@NotBlank String name, @NotBlank URI baseUrl, @Min(0) int weight) {}

// Bound from:
//   app.pricing.providers[0].name=primary
//   app.pricing.providers[0].base-url=https://prices.internal/v2
//   app.pricing.retries=2
//   app.pricing.timeout=800ms        -> Duration.ofMillis(800)

Registering a bounded class

Three ways, and they differ in when the class is picked up. @EnableConfigurationProperties(PricingProperties.class) registers it explicitly. @ConfigurationPropertiesScan on the application class scans for @ConfigurationProperties classes in and below the scan root — the least typing and the current recommendation. Annotating the class itself with @Component (or the class being a @Bean) also works but mixes configuration binding with component scanning and makes the prefix harder to find. Constructor binding is the default for records and for classes with a single parameterised constructor, which is why the sample above is an immutable record; for mutable classes the setter-based binding still applies.

Two behaviours are worth knowing precisely. Unknown keys under the prefix are ignored by default; setting spring.config.import… no — setting the property spring.config.… is wrong here: the switch is ignoreUnknownFields = false on the annotation (or spring.config.… is not involved). With ignoreUnknownFields = false a typo such as app.pricing.retrys becomes a startup failure with the unrecognised key named. And ignoreInvalidFields = true suppresses conversion failures, turning a malformed value into a default — almost always the wrong choice, because it hides exactly the mistake validation exists to catch.

// Fail fast on typos and bad values - the whole point of typed configuration.
@SpringBootApplication

public class CatalogApplication { /* ... */ }

//   BindValidationException / ConfigurationPropertiesBindException
//   Failed to bind properties under 'app.pricing' ... Property: app.pricing.retrys
//   Reason: Property 'app.pricing.retrys' is not recognized

Immutable, validated, testable

A record-bound properties object is a plain value: unit tests construct one directly with no container, and code that depends on it depends on an interface-shaped contract rather than on the environment. That testability is the practical reason to prefer records. Where a framework class needs setters — a legacy library, or a class that must be mutable — keep the setters on a separate mutable class and expose an immutable view to your own code.

Durations accept the ISO-8601 form (PT0.8S) and the simple form (800ms, 3s, 2d) with the @DurationUnit fallback. Data sizes accept 10MB, 512KB. Getting these two converters from the framework rather than writing your own parser is one of the quieter wins of typed configuration.

3.3 Profiles and profile groups in depth

Profiles exist to express that the shape of an environment differs. Used that way they are a small, clear tool; used as a place to store per-environment URLs they become a synchronisation problem.

Activation and precedence

spring.profiles.active names profiles; several can be active at once and the last one wins for a conflicting key, because later profile documents are added to the environment after earlier ones. A profile-specific file is loaded after the base file, so application-prod.yml overrides application.yml rather than merging lists — a list under the same key is replaced, not appended. That replacement rule surprises people who add one entry to app.pricing.providers in a profile and lose the rest.

# Case 1: two profiles active, last wins for scalar keys
#   java -jar app.jar --spring.profiles.active=base,prod
# application-base.yml: server.port=8080
# application-prod.yml: server.port=443
# Effective: 443

# Case 2: list keys are REPLACED, not merged
# application.yml:        app.pricing.providers[0]=primary, [1]=fallback
# application-prod.yml:   app.pricing.providers[0]=primary
# Effective in prod: only [0]. Repeat the whole list, or move it out of profiles.

# Case 3: a profile group activates several profiles as one name
# spring.profiles.group.prod[0]=base
# spring.profiles.group.prod[1]=observability
#   --spring.profiles.active=prod   now also activates base and observability

Profile groups and profile expressions

A profile group maps one name to several, so an operator sets prod and gets a coherent bundle instead of remembering three names. Profile expressions (@Profile("prod & !canary"), "cloud | onprem") allow boolean composition on beans and are genuinely useful for the canary case; they are less useful in property files, where a profile-specific document is per-profile and cannot express a union.

The default profile deserves care. When nothing is set, Boot activates default. Naming an environment "default" and shipping it to production by accident is the failure this invites, so the recommended pattern is to make the base file environment-neutral and to require an explicit activation in every deployment: a SPRING_PROFILES_ACTIVE environment variable in the container manifest, and a fail-fast guard bean that refuses to start when no meaningful profile is set.

// Fail fast when nobody chose an environment - cheaper than discovering it in production.
@Component
class ProfileGuard implements ApplicationListener<ApplicationReadyEvent> {

    private static final Set<String> KNOWN = Set.of("local", "test", "staging", "prod");

    ProfileGuard(Environment env) {
        var active = Set.of(env.getActiveProfiles());
        if (active.stream().noneMatch(KNOWN::contains)) {
            throw new IllegalStateException(
                "No known Spring profile active (got " + active + "). "
                + "Set SPRING_PROFILES_ACTIVE to one of " + KNOWN);
        }
    }

    @Override public void onApplicationEvent(ApplicationReadyEvent event) { }
}

What belongs in a profile, and what does not

Put in a profile the things that change the wiring: an in-memory message broker versus Kafka, a stub payment gateway versus a real one, logging levels, actuator exposure, Flyway enabled or not. Keep out of a profile the things that are values: credentials, hostnames, pool sizes, feature flags that operations may need to flip. Values belong in environment variables or a config server, where they can be changed without a new artifact and where the provenance is a deployment manifest rather than a file that might not be on the classpath.

A profile-specific file that exists only inside the jar cannot be changed without a rebuild. If operators must be able to correct a value in a running system, that value must come from an external source — an environment variable, a mounted file, or a config server. Otherwise the recovery path for a bad value is a release.

3.4 Environment variables, relaxed binding and externalised configuration

Relaxed binding is the mechanism that lets an environment variable named in SCREAMING_SNAKE_CASE reach a field called baseUrl. It is also the source of some very confusing misses, because the transformation is not a simple case change.

The binding rules

For a property app.pricing.base-url, the acceptable environment-variable spellings are APP_PRICING_BASEURL and APP_PRICING_BASE_URL. The rule is: remove dashes and dots, upper-case, and use underscores as the separator — but an underscore in the variable also maps to a dash or to nothing, so APP_PRICING_BASE_URL binds while APP_PRICING_BASEURL is the reliable form. A single-value list can be comma-separated in the variable. A numeric index needs the bracket form, which is awkward in a shell and is the reason list-valued configuration usually belongs in a file rather than an environment variable.

SPRING_APPLICATION_JSON and command-line arguments

Two sources accept structured data. SPRING_APPLICATION_JSON holds an inline JSON document that is added at high precedence — useful in a container where the platform can only set environment variables, and a convenient way to set a nested structure that would otherwise need several variables. Command-line arguments (--app.pricing.retries=3) sit at the top of the list, above environment variables, and are the right tool for a one-off run and for integration tests that need to force a value.

# shell - a container-friendly override, no rebuild and no mounted file
SPRING_APPLICATION_JSON='{"app":{"pricing":{"retries":5,"timeout":"1200ms"}},"logging":{"level":{"com.example":"DEBUG"}}}' \
  java -jar catalog.jar

# Same settings as command-line arguments (highest precedence of the property sources):
java -jar catalog.jar --app.pricing.retries=5 --app.pricing.timeout=1200ms --logging.level.com.example=DEBUG

# Prove which source won, without reading any code:
java -jar catalog.jar --debug | grep -i "pricing" || true
# Better: Boot ships an endpoint-free diagnostic - use the actuator /env endpoint (sanitised):
curl -s localhost:8080/actuator/env/app.pricing.retries | jq

Externalising beyond environment variables

Three mechanisms go further than environment variables. A mounted file (file:/etc/catalog/application.yml via spring.config.import or spring.config.additional-location) holds structured configuration that is version-controlled by the deployment system. A config server (chapter 12) centralises configuration across many services and can be refreshed at runtime. A secrets manager (below) supplies credentials with their own access control and audit trail. The property source order means all three compose: the server supplies defaults, the environment overrides them, and an argument wins.

Whichever you choose, add a startup dump. Boot logs the active profiles, the config file names with their resolved locations, and — with logging.level.org.springframework.boot.context.config=DEBUG — each import as it is processed. That log line is the answer to "which file is actually being read" and it costs nothing to enable in a non-production profile.

Property keys are matched case-insensitively in the environment but not in a properties file, and a key set in both an environment variable and a file resolves to the environment variable. When a value seems to be ignored, check the actuator /env endpoint: it lists every source in precedence order with the winning one identified.

3.5 Secrets and configuration hygiene

A secret is configuration with a blast radius. Spring Boot has no secret store of its own; it has good integration with the stores that do, and a set of practices that keep credentials out of artifacts and out of logs.

The four placements, and what each protects against

Plain in application.yml protects against nothing: the value is in the jar, in the git history, and in every developer's checkout. This is the default people fall into and it is the one cause of leaked credentials that never goes away, because removing it from the current revision does not remove it from history. As an environment variable keeps the secret out of the artifact and out of git; it remains visible to anything that can read the process environment (/proc/<pid>/environ, docker inspect, a crash dump) and it is easy to leak into a log by printing System.getenv(). As a mounted file (Docker/Kubernetes secret volume, Vault agent file) has the same trust boundary but a separate lifecycle: it can be rotated without restarting the process if the code re-reads it, and it is not part of the process environment. From a secrets manager — Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager — adds access control, audit logging and rotation, at the cost of an availability dependency that must be handled.

Vault and the Spring Cloud integration

Spring Cloud Vault makes the secrets manager a property source: with the starter on the classpath and spring.config.import=vault:// set, credentials for the configured paths are fetched at startup and merged into the Environment like any other source. The spring-cloud-vault-config-databases module goes further and can request a short-lived database credential from Vault's database secrets engine, so the application never holds a long-lived password at all.

spring:
  config:
    import: vault://
  cloud:
    vault:
      uri: https://vault.internal:8200
      authentication: TOKEN
      token: ${VAULT_TOKEN}                 # itself supplied by the platform
      kv:
        enabled: true
        backend: secret
        default-context: catalog
      database:
        enabled: true
        role: catalog-readwrite             # dynamic, short-lived DB credentials

# Fail fast rather than fetching lazily: a missing secret is a startup error,
# handled by spring.cloud.vault.fail-fast=true.

Keeping secrets out of logs and actuator output

Two leaks are common and both have framework support. First, the actuator /env and /configprops endpoints print property values; Boot sanitises keys matching a documented pattern list (password, secret, token, key, credentials and others) by replacing the value with ******, and you extend that list with management.endpoint.env.show-values and a custom SanitizingFunction. Second, a @ConfigurationProperties object's toString() — and a record's generated one — prints every field, so a properties record holding a password leaks it into any log statement that logs the object. Give such a class an explicit toString() that redacts, or keep the secret in a separate class that is never logged.

// Extend Boot's sanitiser so a custom key is redacted in /env and /configprops.
@Configuration
class SanitisingConfig {

    @Bean
    SanitizingFunction sanitizeApiKeys() {
        return event -> {
            String key = event.getKey();
            if (key != null && (key.contains("apikey") || key.contains("api-key"))) {
                return event.withValue(PropertyValue.of("******"));
            }
            return event;
        };
    }
}

// And never log a properties object that carries a credential:
@ConfigurationProperties("app.payment")
record PaymentProperties(String merchantId, String apiKey) {
    @Override public String toString() {                 // records generate a full one by default
        return "PaymentProperties[merchantId=" + merchantId + ", apiKey=******]";
    }
}
Adding a secret to application.yml "temporarily" is a release-blocking event, not a to-do: the value is then in the git history and in every CI log and artifact cache that touched it. Rotate the credential rather than only deleting the line. For the same reason, do not paste a real value into a test resource file — Testcontainers and random test credentials exist precisely to avoid it.

4 · The web layer

Spring MVC turns an HTTP request into a method call and a return value back into a response. The interesting parts are not the annotations but the pipeline between them: how arguments are resolved, how the body is converted, where validation runs, and how errors become responses. All three of those are extension points, and knowing them is what separates an API that is easy to consume from one that returns stack traces.

4.1 @RestController and request mapping

A controller is a bean whose methods are registered with RequestMappingHandlerMapping at startup. The mapping decision happens once, when the context is built, so an ambiguous mapping is a startup failure rather than a runtime surprise.

How a request finds a method

DispatcherServlet is the front controller: every request enters it, and it asks a chain of HandlerMapping beans which handler should serve it. The one that matters is RequestMappingHandlerMapping, which builds a registry from every @RequestMapping-annotated method in every controller bean at startup. For each request it matches the URL patterns, then the HTTP method, then the consumes and produces conditions, plus any params or headers conditions. The most specific match wins: an exact path beats a path with a variable, and a pattern with fewer wildcard segments beats one with more.

Two consequences follow from "decided at startup". Registering the mapping eagerly means a duplicate route — two controllers declaring GET /books/{isbn} — fails fast with IllegalStateException: Ambiguous mapping naming both methods. And the @RequestMapping conditions are matched against the Accept header, so an API that produces only JSON but is called with Accept: application/xml returns 406 Not Acceptable, not 400 — a distinction clients frequently get wrong.

package com.example.catalog.web;

import java.net.URI;
import java.util.List;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping(path = "/api/books", produces = "application/json")
public class BookController {

    private final CatalogService service;

    public BookController(CatalogService service) { this.service = service; }

    @GetMapping                                        // GET /api/books
    List<BookResponse> list() {
        return service.findAll();
    }

    @GetMapping("/{isbn}")                             // GET /api/books/978-0-13-235088-4
    BookResponse byIsbn(@PathVariable String isbn) {
        return service.find(isbn).orElseThrow(() -> new BookNotFoundException(isbn));
    }

    @PostMapping(consumes = "application/json")        // POST /api/books
    ResponseEntity<Void> create(@RequestBody CreateBookRequest request) {
        BookResponse created = service.create(request);
        return ResponseEntity
                .created(URI.create("/api/books/" + created.isbn()))
                .build();
    }

    @DeleteMapping("/{isbn}")
    ResponseEntity<Void> delete(@PathVariable String isbn) {
        service.delete(isbn);
        return ResponseEntity.noContent().build();      // 204
    }
}

The class-level annotation does two things

@RestController is @Controller plus @ResponseBody. @Controller alone means the return value names a view; on a REST API that produces 500 with a confusing view-resolution error, because Spring tries to resolve a view called BookResponse. @ResponseBody switches the return value to the message-converter path instead: an HttpMessageConverter serialises it and the request is complete. On a REST API you rarely need @Controller — but the moment you want to return a Thymeleaf or JSP view from one method, the answer is to split the controllers rather than to mix @ResponseBody into a view controller.

@RequestMapping at class level sets a prefix and shared conditions; method-level annotations inherit and narrow them. Putting produces at class level and consumes on the write methods is the pattern above: every endpoint in the class speaks JSON, but only the ones that take a body restrict the request media type.

Path patterns: what is allowed and what changed

Spring MVC 6 uses PathPatternParser for MVC request mapping by default (it has been the default for MVC since Framework 6.0). It is a more restrictive language than the older AntPathMatcher, and the differences have caused real behaviour changes. Two patterns are the ones to know: {name} matches exactly one path segment, and {*name} matches the remainder of the path including slashes. The ** pattern is still supported, but the ambiguous combinations — /a/**/b/{x} — now fail at startup with an explicit message rather than matching unpredictably.

4.2 Binding path, query, body and header data

Argument resolution is the pipeline stage that turns a request into method parameters. Spring ships around thirty HandlerMethodArgumentResolvers, and each parameter annotation selects one. Knowing which resolver handles a parameter explains what values are possible — and what conversion errors look like.

Which annotation binds what

@PathVariable reads a named segment from the matched pattern. @RequestParam reads a query parameter or, for a form post, a request parameter; it is required by default, and required = false with @Nullable or a default value is what makes it optional. @RequestBody hands the raw bytes to an HttpMessageConverter and binds the deserialised object; it is required by default, so an empty body is a 400. @RequestHeader reads a header, case-insensitively. @ModelAttribute binds request parameters onto the fields of an object — the classic form-post binding, and the one place where WebDataBinder and custom Converters are configured.

Without an annotation, the resolver falls back on the parameter type: a simple type (String, primitives, enums, Duration) binds like @RequestParam, and a complex type binds like @ModelAttribute. That inference is convenient and worth avoiding in an API controller, because a parameter that was a String and became a record silently changes from a query parameter to a body-bound model attribute.

@GetMapping("/search")
Page<BookSummary> search(
        @RequestParam(required = false) String q,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size,
        @RequestParam(required = false) Sort sort,             // ?sort=title,desc
        @RequestHeader(value = "X-Tenant", required = false) String tenant,
        @RequestHeader("If-None-Match") Optional<String> etag) {
    return service.search(q, PageRequest.of(page, size)).map(BookSummary::from);
}

@PostMapping("/import")
@ResponseStatus(HttpStatus.ACCEPTED)
void importBooks(@RequestBody List<CreateBookRequest> batch,
                 @RequestHeader("Idempotency-Key") String idempotencyKey) {

Conversion, coercion and custom types

Everything arriving in a request is text, so every binding involves a conversion. Spring uses ConversionService for that, and in a Boot MVC application the service includes the application converters, so a custom Converter<String, Isbn> registered as a bean is available to @PathVariable automatically. Registering a converter is the right way to give a value object a text form: it keeps validation of the format in one place and makes the type usable in paths, query parameters and headers alike.

// A value object with one conversion path, reused everywhere a String is bound.
public record Isbn(String value) {
    public Isbn {
        if (!value.matches("(97[89])?[0-9]{9}[0-9X]")) {
            throw new IllegalArgumentException("not a valid ISBN: " + value);
        }
    }
}

@Configuration
class ConversionConfig implements WebMvcConfigurer {
    @Override
    public void addFormatters(FormatterRegistry registry) {
        registry.addConverter(String.class, Isbn.class, Isbn::new);
    }
}

@GetMapping("/by-isbn/{isbn}")     // "978-0-13-235088-4" or "0132350882" both bind
BookResponse byIsbn(@PathVariable Isbn isbn) { return service.get(isbn); }

What a conversion failure returns

A binding failure produces a MethodArgumentTypeMismatchException, which the default error handling renders as 400 Bad Request. The message names the parameter and the value but nothing else, which is fine for a well-designed client and poor for a human. Section 4.5 shows the @ControllerAdvice handler that turns it into a field-addressed payload using ProblemDetail. Note that a failure to bind a simple parameter aborts the request before the method runs, so @Valid never sees it — the two validation paths are separate and both must be handled.

A @RequestBody that fails JSON parsing raises HttpMessageNotReadableException, which by default is also 400 and whose message is often a Jackson parser exception with byte offsets. Turning it into a stable error shape is the single highest-value exception handler in most APIs, because it is the error a client integration hits first.

4.3 Validation with Jakarta Bean Validation

Bean Validation is a specification (Jakarta Validation 3.0 in Boot 3) with a reference implementation, Hibernate Validator. It is declarative, it composes across nested objects, and it is enforced by Spring at the web boundary and on method parameters.

Where the annotations are checked

On a controller method, @Valid or @Validated on a @RequestBody parameter triggers validation after deserialisation and before the method is invoked. On a @ConfigurationProperties class it runs during binding. On a @Service method it is enabled by class-level @Validated and implemented with an AOP proxy — which means it obeys the proxy rules from chapter 2 and is skipped on self-invocation. The three sites share the same constraint annotations, so a constraint written on a record field is enforced everywhere that record is validated.

package com.example.catalog.web;

import jakarta.validation.Valid;
import jakarta.validation.constraints.DecimalMin;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;
import java.math.BigDecimal;
import java.util.List;
import org.springframework.validation.annotation.Validated;

public record CreateBookRequest(
        @NotBlank
        @Pattern(regexp = "(97[89])?[0-9]{9}[0-9X]", message = "must be a valid ISBN-10 or ISBN-13")
        String isbn,

        @NotBlank @Size(max = 200)
        String title,

        @DecimalMin(value = "0.00", inclusive = true)
        BigDecimal price,

        @Size(max = 20)
        List<@NotBlank String> tags,          // validates each element, not just the list

        @Valid                              // recurse into the nested object
        PublisherRequest publisher) {
}

public record PublisherRequest(@NotBlank String name, @Pattern(regexp = "^[A-Z]{2}$") String country) {}

// The controller parameter:
//   ResponseEntity<Void> create(@Valid @RequestBody CreateBookRequest request)

Validation groups and ordering

A constraint can belong to a group, and validation can be limited to a group. The common use is a two-stage create/update distinction: @NotNull(groups = Create.class) for the field that must be present on creation and may be absent on a partial update. Groups are declared on the controller parameter with @Validated(Create.class). @GroupSequence orders groups so cheap checks (format) run before expensive ones (a database uniqueness check implemented as a custom constraint).

Groups are stringently typed and awkward to compose across layers; many teams reach instead for two distinct request records — CreateBookRequest and UpdateBookRequest — which is more code and less machinery. On an API where create and update differ in more than one field, the two-record approach is usually clearer; reserve groups for the case where one DTO genuinely carries both shapes and splitting it would duplicate the schema.

Cross-field and business constraints

Bean Validation expresses per-field and per-object constraints. A rule spanning two fields (an end date after a start date) needs a class-level constraint: an annotation plus a ConstraintValidator that receives the whole object. A rule that needs the database — "this ISBN must not already exist" — is not a good fit: the validator would need a repository, the check races with concurrent inserts, and the real guarantee is the unique index. Implement the database rule as a unique constraint and translate the resulting DataIntegrityViolationException into a 409 in the exception handler.

// Class-level constraint: the annotation lives on the type, the validator sees both fields.
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = DateRangeValidator.class)
public @interface ValidDateRange {
    String message() default "end must be after start";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, PromotionRequest> {
    @Override
    public boolean isValid(PromotionRequest value, ConstraintValidatorContext ctx) {
        if (value == null || value.starts() == null || value.ends() == null) return true;  // @NotNull covers it
        return value.ends().isAfter(value.starts());
    }
}

@ValidDateRange
public record PromotionRequest(@NotNull LocalDate starts, @NotNull LocalDate ends, @DecimalMin("0") BigDecimal pct) {}

Turning violations into a response

Spring raises MethodArgumentNotValidException when an annotated parameter fails, and BindException when a bound model attribute fails. Both expose BindingResult. Since Spring 6.1 a constraint violation on a method parameter that is not a body (a path variable or request parameter, e.g. @PathVariable @Min(1) int n) raises HandlerMethodValidationException instead, and it carries the parameter/message detail under a different accessor. Handling both in one advice method requires reading the exception type — the chapter's last section does exactly this.

Put the human-readable message on the annotation (message = "must be a valid ISBN") and keep it free of the field name. The client already knows which field failed; repeating the name in the message produces strings like "isbn must be a valid isbn". Use a message bundle (ValidationMessages.properties) for localisation rather than embedding text, so one language change is one file.

4.4 Content negotiation and HTTP semantics

The message-converter layer decides which representation is written. Boot configures it for JSON by default, and the right way to add XML, CSV or a versioned media type is to add a converter rather than to special-case a controller.

How the response format is chosen

The Accept header is matched against the produces conditions and the registered converters. If a controller declares produces = "application/json" and the client sends Accept: application/xml, the result is 406 and no converter is consulted. If the controller declares nothing, Spring walks its HttpMessageConverter list in order and picks the first whose canWrite(type, mediaType) is true — with Boot's defaults, Jackson's converter first for a POJO, so JSON wins. The Content-Type header on a request selects the reader the same way, and an unroutable Content-Type is 415 Unsupported Media Type.

Jackson decides what the JSON looks like. Boot auto-configures an ObjectMapper with a documented set of defaults, and any Jackson2ObjectMapperBuilderCustomizer bean adjusts them application-wide. The two settings most worth setting explicitly are the null inclusion policy and the date representation: the defaults write null fields and, for a Java 8 date type, use ISO-8601 strings only after serialization.write-dates-as-timestamps=false (Boot sets this for you by default and it is worth confirming).

// Application-wide JSON policy: one place, no per-field annotations.
@Configuration
class JsonConfig {

    @Bean
    Jackson2ObjectMapperBuilderCustomizer jsonCustomizer() {
        return builder -> builder
                .serializationInclusion(JsonInclude.Include.NON_NULL)
                .featuresToDisable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
                .featuresToDisable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
                .indentOutput(false);
    }
}
// Result: {"isbn":"9780132350884","title":"Effective Java","price":54.99}
// rather than an object with "publisher":null and an epoch-millis date.

Versioning and custom media types

Three versioning strategies are in common use and Spring supports all of them natively. URI versioning (/api/v1/books) is explicit, cache-friendly and trivially debuggable; it also changes the resource identity when the version changes. Media-type versioning (Accept: application/vnd.catalog.v2+json) keeps the URI stable and is the most standards-faithful; it is invisible in a browser address bar and requires clients to set a header. Header versioning (X-API-Version: 2) is explicit but non-standard. All three are implemented the same way: mapping conditions and a converter plus a small RequestCondition or path pattern. What does not work well is branching inside a handler on a version string, because the handler grows two code paths and one of them stops being tested.

@RestController
@RequestMapping(path = "/api", produces = "application/json")
class VersionedBookController {

    @GetMapping(path = "/books/{isbn}", version = "1.0+")   // 6.1+ built-in "version" condition
    BookResponseV1 v1(@PathVariable String isbn) { return service.getV1(isbn); }

    @GetMapping(path = "/books/{isbn}", version = "2.0+")
    BookResponseV2 v2(@PathVariable String isbn) { return service.getV2(isbn); }
}
// Or explicitly, without the built-in condition:
//   @GetMapping(value = "/books/{isbn}", produces = "application/vnd.catalog.v2+json")

HTTP semantics worth getting right

Two design decisions carry more weight than the serialisation format. First, status codes: 201 with a Location header on create, 204 on delete and on a successful update with no body, 200 on a read, 409 on a state conflict, 422 when the body is syntactically fine but semantically rejected. Returning 200 for everything is the single most common API defect and it forces clients to parse a body to know whether the call worked. Second, conditional requests: returning an ETag and honouring If-None-Match lets a client skip the body on an unchanged resource. Spring supports this with ShallowEtagHeaderFilter for the lazy case and explicitly via ResponseEntity.eTag(…) when the entity has a natural version.

@GetMapping("/{isbn}")
ResponseEntity<BookResponse> byIsbn(@PathVariable String isbn,
                                    @RequestHeader(value = "If-None-Match", required = false) String ifNoneMatch) {
    BookResponse body = service.get(isbn);
    String etag = "\"" + body.version() + "\"";           // e.g. a JPA @Version or a content hash
    if (etag.equals(ifNoneMatch)) {
        return ResponseEntity.status(HttpStatus.NOT_MODIFIED).eTag(etag).build();
    }
    return ResponseEntity.ok().eTag(etag).body(body);
}
Boot's default error response is a JSON object with timestamp, status, error, path and optionally message. It is not a standard. Because Spring Framework 6 supports ProblemDetail (RFC 9457, "problem details for HTTP APIs"), setting spring.mvc.problemdetails.enabled=true switches the whole application to that representation — a small, well-specified payload with a stable media type.

4.5 Exception handling with @RestControllerAdvice

One class, one error shape. Centralised handling is what makes an API's errors predictable, and ProblemDetail is the payload that makes them machine-readable.

The resolution order

When a handler throws, DispatcherServlet consults HandlerExceptionResolver beans in order. An @ExceptionHandler in the controller itself wins; then one in a @ControllerAdvice that matches the controller, with more specific basePackages or assignableTypes filters applying before a global advice; then ResponseStatusExceptionResolver (for @ResponseStatus and ResponseStatusException); then DefaultHandlerExceptionResolver, which maps Spring's own exceptions such as MethodArgumentNotValidException and HttpRequestMethodNotSupportedException to statuses. Anything unresolved propagates to the container and becomes a 500 with a servlet error page or Boot's error body.

The practical rule: use @ExceptionHandler for exceptions you own, and let the default resolver handle framework exceptions unless you are replacing the payload globally. Do not catch Exception broadly in a handler for a reason other than "format every unhandled error consistently" — a blanket catch turns a bug into a 200-with-an-apology or a 500 with no log entry.

package com.example.catalog.web;

import java.net.URI;
import java.util.List;
import java.util.Map;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.HandlerMethodValidationException;

@RestControllerAdvice
public class ApiExceptionHandler {

    // --- domain exceptions -------------------------------------------------

    @ExceptionHandler(BookNotFoundException.class)
    ProblemDetail notFound(BookNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Book not found");
        pd.setType(URI.create("https://errors.example.com/book-not-found"));
        pd.setProperty("isbn", ex.getIsbn());
        return pd;                                   // 404, application/problem+json
    }

    @ExceptionHandler(DuplicateIsbnException.class)
    ResponseEntity<ProblemDetail> conflict(DuplicateIsbnException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
                "A book with this ISBN already exists");
        pd.setType(URI.create("https://errors.example.com/duplicate-isbn"));
        pd.setProperty("isbn", ex.getIsbn());
        return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
    }

    // --- framework validation, both paths ----------------------------------

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail onBodyInvalid(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                "Request body failed validation");
        pd.setProperty("errors", fieldErrors(ex.getBindingResult().getFieldErrors()));
        return pd;
    }

    @ExceptionHandler(HandlerMethodValidationException.class)   // @Min/@Pattern on a path or query parameter
    ProblemDetail onParamInvalid(HandlerMethodValidationException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                "Request parameter failed validation");
        pd.setProperty("errors", ex.getAllErrors().stream()
                .map(e -> Map.of("message", String.valueOf(e.getDefaultMessage())))
                .toList());
        return pd;
    }

    private List<Map<String, Object>> fieldErrors(List<? extends org.springframework.validation.FieldError> errors) {
        return errors.stream()
                .map(fe -> Map.<String, Object>of("field", fe.getField(), "message",
                        String.valueOf(fe.getDefaultMessage()),
                        "rejected", String.valueOf(fe.getRejectedValue())))
                .toList();
    }
}

Why ProblemDetail rather than a bespoke shape

RFC 9457 defines five members — type, title, status, detail, instance — and explicitly allows extension members, which is where errors and isbn go above. Using it means the status is in the body as well as the status line, the media type is application/problem+json, and a client library written for one API can parse another. A bespoke {"error": {"code": 1234, "msg": "..."}} shape has to be documented, versioned and reimplemented per client. Spring writes ProblemDetail returns natively, including from an @ExceptionHandler, so the adoption cost is one return type.

Two production details are usually missed. First, log the exception at the right level: a 4xx is a client mistake and belongs at WARN or not at all, while a 5xx is yours and belongs at ERROR with the stack trace; logging every 400 at ERROR makes real errors invisible. Second, never echo a raw exception message for a 5xx — it can contain a SQL fragment, a file path or a class name. Give the client a correlation id and log the pair.

// The two behaviours every API advice needs: right log level, and an
// unhandled-error fallback that leaks nothing.
@ExceptionHandler(Exception.class)
ResponseEntity<ProblemDetail> unexpected(Exception ex, HttpServletRequest request) {
    String correlationId = UUID.randomUUID().toString();
    log.error("Unhandled error [{}] on {} {}", correlationId, request.getMethod(), request.getRequestURI(), ex);

    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
            "An unexpected error occurred. Quote reference " + correlationId + " to support.");
    pd.setType(URI.create("https://errors.example.com/internal"));
    pd.setProperty("correlationId", correlationId);     // nothing else - no class name, no message
    return ResponseEntity.internalServerError().body(pd);
}
Do not return a stack trace or a cause chain to a client, and do not rely on include-message in server.error to describe failures. Both leak internal structure, and the second is a documented source of information disclosure that security scanners flag. Configure server.error.include-message=never and server.error.include-stacktrace=never for any internet-facing service.

5 · Data access

Boot's persistence story is two ladders on the same wall. Spring Data JPA plus Hibernate handles object graphs and lets you write queries in method names; Spring's JDBC support (now JdbcClient) handles rows and SQL and lets you keep total control. Both are transaction-managed by the same infrastructure, both use the same connection pool, and both are wrong for some jobs. This chapter is about choosing, and about the three decisions — fetch strategy, transaction boundary, schema ownership — that determine whether the choice works out.

5.1 Spring Data JPA repositories

A repository interface is a declaration, not an implementation. Spring Data writes the implementation at startup from the method name or the query annotation, and the proxy it produces participates in the surrounding transaction.

What you get without writing a line of code

Extending JpaRepository<Book, Long> provides save, saveAll, findById, findAll (with and without Sort and Pageable), count, existsById, deleteById, deleteAll, flush and findAll(Example). On top of that, the query-method parser derives a query from the method name: findByTitleContainingIgnoreCaseOrderByTitleAsc, findTop5ByPublisher_IdOrderByPublishedDesc, existsByIsbn, countByPublisher_Country. The _ navigates a path; a keyword that the parser does not recognise is a startup failure, so a typo is caught at boot rather than producing a wrong query.

Repository instantiation happens in JpaRepositoryFactoryBean, which decides per method whether to use a declared query (@Query), a derived query from the method name, or one of the built-in implementations. Declared queries are also validated at startup — a JPQL syntax error fails the context, which is one of the strongest reasons to prefer @Query over string-concatenated SQL built in a service.

package com.example.catalog.catalog;

import java.util.List;
import java.util.Optional;
import org.springframework.data.domain.Limit;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface BookRepository extends JpaRepository<Book, Long> {

    Optional<Book> findByIsbn(String isbn);

    List<Book> findByPublisher_NameIgnoreCase(String name);

    // Derived query with an explicit fetch plan - avoids the N+1 in the mapping below.
    @Query("select b from Book b join fetch b.publisher where b.title like :pattern")
    List<Book> findByTitleWithPublisher(@Param("pattern") String pattern);

    // A DTO projection: no managed entity, no accidental lazy load, no dirty checking.
    @Query("""
            select new com.example.catalog.catalog.BookSummary(b.isbn, b.title, b.price)
            from Book b
            where b.publisher.id = :publisherId
            order by b.title
            """)
    List<BookSummary> summariesByPublisher(@Param("publisherId") Long publisherId);

    // Bulk update: bypasses the persistence context, so clear it or the entities stay stale.
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("update Book b set b.price = b.price * :factor where b.publisher.id = :id")
    int repriceByPublisher(@Param("id") Long publisherId, @Param("factor") java.math.BigDecimal factor);
}

Projections are the answer to most "JPA is slow" reports

Returning a managed entity from a read endpoint costs four things: the entity is registered in the persistence context, its dirty state is tracked on flush, its lazy associations may trigger extra queries when serialised, and the SQL selects columns you may not need. A projection — an interface with getters, or a record filled by a constructor expression as above — selects only those columns, produces an immutable value, and cannot trigger a lazy load because it holds no proxy. For anything the API returns directly, use a projection; use the entity when you intend to modify it.

Interface-based projections work by Spring Data generating a proxy from the query result aliases, and they compose with derived queries and with @Query using aliases. Records (class-based projections) need a constructor expression in JPQL, or a native query whose column aliases match the record components exactly. The record form is stronger because the compiler checks the constructor signature and the query fails at startup if it does not match.

Specifications, and when not to use them

A Specification is a predicate builder: repository.findAll(spec, pageable) composes where clauses at runtime from a list of caller-supplied filters. It is the right tool for a search endpoint with twelve optional filters, because the alternative is twelve derived methods or a string-built JPQL. It is the wrong tool for a fixed query, because it moves a query that the database can plan statically into code that plans it per call, and it hides the shape of the SQL from a reviewer. For a small fixed set of filters, prefer a handful of @Query methods; for a genuinely dynamic search, Specification or Querydsl earns its place.

// Composable and testable: each filter is a function of the criteria, not a string.
public final class BookSpecs {
    public static Specification<Book> titleLike(String q) {
        return (root, query, cb) -> q == null ? cb.conjunction()
                : cb.like(cb.lower(root.get("title")), "%" + q.toLowerCase() + "%");
    }

    public static Specification<Book> publishedAfter(LocalDate from) {
        return (root, query, cb) -> from == null ? cb.conjunction()
                : cb.greaterThanOrEqualTo(root.get("published"), from);
    }
}

// In the service:
Specification<Book> spec = Specification.allOf(BookSpecs.titleLike(q), BookSpecs.publishedAfter(from));
Page<Book> page = repository.findAll(spec, PageRequest.of(0, 20, Sort.by("title")));
Repository methods are transactional by default: SimpleJpaRepository is annotated @Transactional(readOnly = true) with mutating methods overriding it. A read method that starts a transaction is cheap but not free, and a repository call made outside any service transaction commits per call — which is correct for a single read and wrong for a sequence that must be consistent.

5.2 Entities, relationships and fetch strategy

An entity is a mapping declaration, and every mapping decision has a runtime cost. The default fetch types are the most consequential defaults in the framework, and they are the opposite of what a web application wants.

Identity, generation and equality

@Id names the identifier and @GeneratedValue chooses how it is produced. IDENTITY (a database sequence or identity column) prevents Hibernate from batching inserts, because it must read the generated key after each statement. SEQUENCE with allocationSize = 50 lets Hibernate pre-fetch key ranges and batch across inserts — the right default on PostgreSQL, Oracle and SQL Server. UUID works everywhere and needs no round trip, at the cost of larger indexes. AUTO picks a strategy per dialect and is fine for development and a hazard in an environment where the dialect differs.

Equality is the other half. An entity's generated id is null until flush, so equals based on id is unstable across the identity-lifecycle. The safe pattern is a business key: a natural unique value the entity already has, used in both equals and hashCode. A @Version column adds optimistic locking — Hibernate appends and version = ? to every update and throws OptimisticLockingFailureException when the row moved underneath you, which is how two concurrent editors are prevented from silently overwriting each other.

package com.example.catalog.catalog;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.SequenceGenerator;
import jakarta.persistence.Table;
import jakarta.persistence.Version;
import java.math.BigDecimal;
import java.util.Objects;

@Entity
@Table(name = "book")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "book_seq")
    @SequenceGenerator(name = "book_seq", sequenceName = "book_seq", allocationSize = 50)
    private Long id;

    @Column(nullable = false, unique = true, length = 20)
    private String isbn;

    @Column(nullable = false, length = 200)
    private String title;

    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal price;

    @ManyToOne(fetch = FetchType.LAZY)                 // default is EAGER - always override
    @JoinColumn(name = "publisher_id", nullable = false)
    private Publisher publisher;

    @Version
    private long version;

    protected Book() { }                               // JPA needs it; keep it non-public

    public Book(String isbn, String title, BigDecimal price, Publisher publisher) {
        this.isbn = isbn; this.title = title; this.price = price; this.publisher = publisher;
    }

    @Override public boolean equals(Object o) {        // business key, stable before insert
        return o instanceof Book b && Objects.equals(isbn, b.isbn);
    }
    @Override public int hashCode() { return Objects.hash(isbn); }

    // getters, domain methods that keep invariants ...
}

The default fetch types are a trap

@ManyToOne and @OneToOne are EAGER by default; @OneToMany and @ManyToMany are LAZY. The result is a mapping that looks harmless and loads half the database: every findById on Book issues a second query for its Publisher, and if Publisher has an eager Country, a third. In a list of twenty books this is forty-one queries — the N+1 problem, and the most common cause of a slow endpoint after a schema change nobody reviewed together.

AssociationDefault fetchWhat to declareWhy
@ManyToOneEAGERLAZYThe parent rarely needs the child graph; fetch it per query when you do
@OneToOneEAGERLAZYSame; note a lazy one-to-one proxy needs the owning side
@OneToManyLAZYKeep LAZYA collection eager-loaded twice causes a MultipleBagFetchException
@ManyToManyLAZYKeep LAZY, model the join table as an entity if it has dataSets cannot be fetched with pagination reliably

Once everything is lazy, the queries that need the graph must say so, and there are two tools. join fetch in JPQL loads it in the same statement; @EntityGraph declares a fetch plan on the repository method, which is the same effect with the query left implicit. Both must be used with pagination carefully: fetching a collection alongside Pageable makes Hibernate paginate in memory unless you supply a count query, which is why the recommended pattern is to fetch the collection with @BatchSize or hibernate.default_batch_fetch_size instead of joining it.

# application.yml - the cheapest global fix for N+1 on collections:
# load lazy collections in batches of 100 instead of one query per entity.
spring:
  jpa:
    open-in-view: false                    # see 5.3
    properties:
      hibernate:
        default_batch_fetch_size: 100
        jdbc:
          batch_size: 50                   # batch inserts/updates
        order_inserts: true
        order_updates: true

// And per query, be explicit about the graph you need:
@EntityGraph(attributePaths = {"publisher"})
Optional<Book> findWithPublisherByIsbn(String isbn);

Cascades, orphans and the owning side

cascade = ALL is a loaded gun aimed at your delete endpoint: removing a publisher removes every book, and if the inverse mapping is missing, the books vanish without a statement. Declare the cascades that are actually part of the aggregate — PERSIST and MERGE on a parent whose children live and die with it, orphanRemoval = true only when removing a child from the collection should delete it. In a bidirectional pair, the mappedBy side is the inverse and does not own the foreign key; forgetting to set the owning side (or to keep the collection in sync with a helper method) produces a mapping that appears to work in memory and writes the wrong foreign key on flush.

Never map a collection of entities that a client may not need to a REST response directly. A @OneToMany on a serialised entity causes both a lazy-loading exception (with no open session) and, if the session is open, an unbounded graph walk. Return a projection, and let the DTO shape decide the fetch plan rather than the mapping.

5.3 Transactions, boundaries and the open-session trap

@Transactional is the most powerful annotation in the framework and the one most often placed incorrectly. It works through a proxy, it is scoped to a method call, and its default rollback rule does not cover checked exceptions.

The rules that decide behaviour

Four properties of the annotation govern almost every real case. Propagation: REQUIRED (default) joins an existing transaction or starts one; REQUIRES_NEW suspends the caller's transaction and commits independently — the mechanism for "audit this failure even though the business transaction rolled back"; SUPPORTS runs without one if none exists; MANDATORY asserts that a caller started one, which is how you make a service unusable without a transaction. Rollback: a transaction rolls back on RuntimeException and Error only, so a checked exception leaves uncommitted work to be committed by the caller — the classic "my partial write survived" bug, fixed with rollbackFor = Exception.class. readOnly: readOnly = true is a hint that lets Hibernate skip dirty-checking and lets the driver use a read-only connection; it is not enforced, and writing in a read-only transaction silently succeeds on most databases. Isolation: leave it at the database default unless you have measured a specific problem; raising it to SERIALIZABLE application-wide converts a throughput issue into a deadlock issue.

@Service
public class ImportService {

    private final BookRepository books;
    private final AuditRepository audit;

    public ImportService(BookRepository books, AuditRepository audit) {
        this.books = books; this.audit = audit;
    }

    // REQUIRES_NEW so the audit row survives whatever happens to the import.
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordAttempt(String isbn) { audit.save(new AuditEntry(isbn, Instant.now())); }

    @Transactional(rollbackFor = Exception.class)          // checked exceptions roll back too
    public ImportResult importBatch(List<CreateBookRequest> batch) throws CsvParseException {
        for (CreateBookRequest r : batch) {
            books.save(toEntity(r));
        }
        if (batch.isEmpty()) throw new CsvParseException("empty batch"); // would otherwise commit
        return new ImportResult(batch.size());
    }

    @Transactional(readOnly = true)                        // no dirty checking, read-only connection
    public List<BookSummary> summaries() { return books.findSummaries(); }
}

Why self-invocation does nothing

The transaction is started by a proxy that wraps the bean (see chapter 2). A call from inside the same class — this.importBatch(…) — reaches the target object directly, so the proxy never sees it and no transaction starts. The symptom is that part of a batch commits and part does not, with no error. The fixes are all structural: move the transactional method to a different bean, inject a self-reference through ObjectProvider<ImportService> or @Lazy, or (worst) enable @EnableAspectJAutoProxy(exposeProxy = true) and call AopContext.currentProxy(). Prefer moving the method.

Open Session in View, and why it is off here

spring.jpa.open-in-view defaults to true and Boot logs a warning about it at startup. With it on, a OpenEntityManagerInViewInterceptor binds an EntityManager for the whole web request, so a lazy association accessed during serialisation triggers a query on the request thread and the N+1 problem is invisible in development — everything works, just slowly and unpredictably. With it off, the session is closed when the service call returns, and an unmapped lazy load raises LazyInitializationException at the point of the bug. That exception is the feature: it forces the fetch plan into the repository instead of leaving it to a serialiser.

# The trade-off in one line, and the setting this guide uses everywhere:
spring.jpa.open-in-view=false

# Symptom with it off (correct, and tells you where the bug is):
#   org.hibernate.LazyInitializationException: could not initialize proxy
#   [com.example.catalog.Publisher#7] - no Session
#   at com.example.catalog.web.BookController.toResponse(BookController.java:41)

# Symptom with it on (looks fine, quietly issues 1 + N extra queries):
#   Hibernate: select ... from book where ...
#   Hibernate: select ... from publisher where id=?      x N
Keep transactions short and free of I/O you do not control. A @Transactional method that calls a payment gateway holds a database connection for the duration of the network call, and under load that exhausts the pool. Split it: do the remote call outside the transaction, then open a short transaction to persist the result.

5.4 JdbcClient and JdbcTemplate

Spring's JDBC support has no session, no dirty checking and no query derivation. You write SQL, you get rows, and the transaction manager treats a JdbcClient call exactly like a repository call. For a read-heavy reporting query or a bulk update over a million rows, that is usually the better tool.

Why JdbcClient replaced the fluent patterns

JdbcTemplate is the original: methods taking a SQL string and a RowMapper, with queryForList, queryForObject, update and batchUpdate. It works and it is not going away. JdbcClient (Spring Framework 6.1, Boot 3.2) keeps the same execution engine and adds a builder-shaped API: sql(…), param(…), params(Map), then a terminal operation query, list, single, optional, update or query(Class). Parameters are bound by position or by name, and the named form is genuinely safer in review because a parameter can be matched to its placeholder by eye.

The query(Optional.class) and query(Class) terminals are what remove most boilerplate: for a record whose component names match the column aliases, Spring binds the row to the record with no mapper at all. That is the fastest path from SQL to a typed result in the framework.

package com.example.catalog.reporting;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.List;
import java.util.Optional;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;

@Repository
public class SalesReportRepository {

    private final JdbcClient jdbc;
    public SalesReportRepository(JdbcClient jdbc) { this.jdbc = jdbc; }

    public record AuthorTotals(String authorName, long titles, BigDecimal revenue) { }

    // SQL for a set-based aggregate; no entity, no session, no N+1 possible.
    public List<AuthorTotals> revenueByAuthor(LocalDate from, LocalDate to) {
        return jdbc.sql("""
                select a.name            as author_name,
                       count(distinct b.id) as titles,
                       coalesce(sum(s.total), 0) as revenue
                from author a
                join book b   on b.author_id = a.id
                left join sale s on s.book_id = b.id and s.sold_on between :from and :to
                group by a.name
                order by revenue desc
                """)
                .param("from", from)
                .param("to", to)
                .query(AuthorTotals.class)          // record binding via column aliases
                .list();
    }

    public Optional<BigDecimal> totalRevenue(LocalDate day) {
        return jdbc.sql("select coalesce(sum(total), 0) from sale where sold_on = :day")
                   .param("day", day)
                   .query(BigDecimal.class)
                   .optional();
    }

    // A single statement that joins the books it modifies: no read-modify-write race.
    @Transactional
    public int applyDiscount(long bookId, BigDecimal pct) {
        return jdbc.sql("""
                update book
                   set price = round(price * (1 - :pct), 2)
                 where id = :id
                   and price > 0
                """)
                .param("pct", pct.movePointLeft(2))     // 10 -> 0.10
                .param("id", bookId)
                .update();
    }
}

Batching, generated keys and large result sets

Three JDBC features have direct JdbcClient/JdbcTemplate support and matter at scale. Batch inserts: sql(…).param(…).update() in a loop is one round trip per row; jdbcTemplate.batchUpdate(sql, batchArgs) or BatchPreparedStatementSetter groups them, and PostgreSQL multiplies the win with reWriteBatchedInserts=true in the JDBC URL. Generated keys: KeyHolder or GeneratedKeyHolder retrieves identity columns without a second query. Streaming: queryForStream with a fetch size, used inside a transaction, lets you process a million rows at constant memory instead of materialising a list — the JDBC counterpart of a database cursor, and the only correct shape for an export job.

5.5 Schema migrations with Flyway and Liquibase

Schema is code. It belongs in version control, it is applied by a tool, and it is never applied by the application's ORM in an environment that matters.

Why not ddl-auto

spring.jpa.hibernate.ddl-auto=update is convenient and unusable in production, for reasons that are structural rather than stylistic. Hibernate's schema updater adds missing columns and tables; it does not drop, does not rename, does not change a type safely, and does not know your data. A rename becomes a new column and an orphaned old one. Two instances starting at once race. Nothing is versioned, so there is no record of what the schema should be, and no way to roll forward in a controlled way. The supported configuration is validate, which starts an instance only if the mapping matches the database and otherwise fails loudly — which is exactly the signal you want after a migration was forgotten.

# application.yml - the production posture
spring:
  jpa:
    hibernate:
      ddl-auto: validate                  # never update/create/create-drop outside tests
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true             # for an existing, unversioned database
    validate-on-migrate: true             # refuse to start if a checksum changed

# Tests use the same migration set, so the schema under test is the schema shipped.
#   src/main/resources/db/migration/V1__init.sql
#   src/main/resources/db/migration/V2__add_book_isbn_unique.sql
#   src/main/resources/db/migration/V3__create_sale_table.sql

Flyway: versioned SQL with a checksum

Files are named V<version>__<description>.sql — two underscores, and the version may be 1, 1.1 or a timestamp. Flyway records each applied migration in a flyway_schema_history table with a checksum of the file, and by default refuses to start if an already-applied file's content changed. That refusal is the feature: a migration is immutable once applied, and a mistake is corrected with a new migration, not by editing the old one. Repeatable migrations (R__views.sql) have no version and are re-applied whenever their checksum changes, which is the right shape for a view, a function or a seed list.

Three operational details are worth setting up front. Flyway runs inside the application's startup by default, which means two replicas starting simultaneously can race; a database-level lock makes this safe on most engines, and an explicit flyway migrate step in the pipeline before the deploy removes the question. baseline-on-migrate exists only for adopting Flyway on a database that already has objects. And a migration that takes a long lock — alter table adding a column with a default on a large table — should be written as an expand/contract pair so no single statement holds a lock for minutes.

-- V4__add_sale_index_and_nullable_discount.sql
-- Expand step: additive and backwards compatible, so old and new code can both run.
alter table sale add column discount_pct numeric(5,2);

-- Concurrent index build outside a transaction (PostgreSQL):
--   create index concurrently if not exists ix_sale_sold_on on sale (sold_on);
-- Additive index creation must not run in the migration transaction for CONCURRENTLY;
-- use spring.flyway.mixed=true with a single-statement script, or run it out of band.

-- V5__backfill_discount.sql
update sale set discount_pct = 0 where discount_pct is null;

-- V6__enforce_discount.sql
-- Contract step: only after every replica writes the column.
alter table sale alter column discount_pct set not null;
alter table sale add constraint ck_discount check (discount_pct between 0 and 100);

Liquibase: a changelog, and why it exists

Liquibase is database-agnostic: a changeset is XML, YAML, JSON or formatted SQL, and the tool generates the dialect-specific SQL. Its advantage over Flyway is portability and rollback — each changeset can declare a rollback block and liquibase rollback undoes a range — and its preConditions let a changeset assert something about the database before running. Its cost is a layer of abstraction between you and the SQL, which makes an unusual migration harder to express and harder to review.

The practical rule: if the team writes SQL comfortably and supports one database, Flyway is simpler and the migration file is exactly what runs. If the product ships on several databases, or if regulated rollback is required, Liquibase's abstraction pays for itself. Both are first-class in Boot — spring-boot-starter-* dependency, auto-configured on startup, controlled by spring.flyway.* or spring.liquibase.* — and neither should be replaced by a hand-rolled runner.

# application.yml - Liquibase instead of Flyway
spring:
  liquibase:
    enabled: true

    contexts: prod                    # only changesets without a context or matching it
    drop-first: false

      ddl-auto: validate

Flyway's checksum validation and Liquibase's checksum on DATABASECHANGELOG will both fail the next start, and the fix — flyway repair or manually updating the history table — is a manual database change performed under pressure. 6 · Security

Spring Security 6 is a filter chain, not an annotation you sprinkle. Every request passes through an ordered list of filters, one of which establishes who the caller is and another of which decides whether they may proceed. Understanding the chain's order and which filters Boot adds by default is what makes a security configuration reviewable instead of superstitious.

6.1 The filter chain, SecurityFilterChain and defaults

Since Spring Security 6.0 the old WebSecurityConfigurerAdapter is gone. Configuration is a bean that returns a SecurityFilterChain, and the lambda DSL replaces the chained methods that were deprecated in 5.x.

What the default chain does

Adding spring-boot-starter-security with no configuration produces a specific, security-first behaviour that surprises people on the first run. All endpoints require authentication. HTTP Basic is enabled. Form login is enabled and served at /login. A user named user is created with a random UUID password printed to the console as Using generated security password: …. CSRF protection is enabled. And several security headers — X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Cache-Control: no-cache, no-store, and on HTTPS, HSTS — are added to every response.

That default is deliberate: the framework starts closed and you open it. The generated user exists so an unconfigured application is not open to the world while a developer wires up real authentication. It disappears as soon as you declare any AuthenticationManager, AuthenticationProvider or UserDetailsService bean.

package com.example.catalog.security;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableMethodSecurity                         // enables @PreAuthorize / @PostAuthorize
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                       // only because this is a stateless token API
            .cors(Customizer.withDefaults())                     // picks up the CorsConfigurationSource bean
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health/**", "/actuator/info").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/books/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers(HttpMethod.POST, "/api/books/**").hasAuthority("SCOPE_books.write")
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));
        return http.build();
    }
}

Filter order, and why it matters

The chain is assembled in a fixed order that is not obvious and is documented in the reference as FilterOrderRegistration. Four positions explain most behaviour. CorsFilter runs early, before authentication, so a preflight OPTIONS request is answered without credentials. CsrfFilter runs before the authentication filters, so a CSRF token is validated before a session is touched. LogoutFilter runs before UsernamePasswordAuthenticationFilter, so /logout is not treated as a login attempt. And AuthorizationFilter runs last, at the end of the chain, so the request is only authorised after identity has been established and security headers have been set.

When you add your own filter, addFilterBefore and addFilterAfter position it relative to a known filter, and addFilterAt replaces one. The mistake to avoid is adding an authentication filter after AuthorizationFilter, where it can never influence the decision. Use OncePerRequestFilter as the base class: a plain Filter may run twice in a forward or an async dispatch.

Multiple chains and @Order

A single application may need two policies: a stateless token API and a session-based admin UI. Declaring two SecurityFilterChain beans with @Order and a securityMatcher on each is the supported answer. The first chain whose matcher matches a request handles it, and the next is not consulted — so the ordering is part of the security model, not an optimisation. Putting the more specific matcher first is the convention, because a broad /api/** chain placed first silently swallows the admin chain.

@Configuration
@EnableMethodSecurity
class TwoPolicies {

    @Bean @Order(1)                       // the token API, matched first
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http.securityMatcher("/api/**")
                   .csrf(csrf -> csrf.disable())
                   .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                   .authorizeHttpRequests(a -> a.anyRequest().authenticated())
                   .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
                   .build();
    }

    @Bean @Order(2)                       // the admin UI: sessions, form login, CSRF on
    SecurityFilterChain adminUi(HttpSecurity http) throws Exception {
        return http.securityMatcher("/admin/**", "/login")
                   .authorizeHttpRequests(a -> a
                       .requestMatchers("/login").permitAll()
                       .anyRequest().hasRole("ADMIN"))
                   .formLogin(Customizer.withDefaults())
                   .build();
    }
}
Do not write permitAll() on "/**" to "get it working". Everything after it in the same chain becomes unreachable, and @PreAuthorize on a service is the only thing left protecting the data. If a proof-of-concept genuinely needs it, mark it with a TODO that has an owner and a date, and keep the actuator endpoints restricted regardless.

6.2 Authentication: UserDetailsService and password encoding

Authentication answers "who is this". Spring Security decomposes it into a manager, one or more providers, a user lookup and a credential check — each replaceable, and one of which (the password encoder) has no safe default other than the one Boot supplies.

The object graph

AuthenticationManager is the entry point; in practice it is a ProviderManager holding an ordered list of AuthenticationProviders and returning the first that can authenticate a given Authentication token. The common provider is DaoAuthenticationProvider, which takes a UserDetailsService to load the user and a PasswordEncoder to compare the presented password with the stored one. When you declare a UserDetailsService bean, Boot's UserDetailsServiceAutoConfiguration backs off and no generated user is created.

UserDetailsService has exactly one method, loadUserByUsername, and it must throw UsernameNotFoundException when the user does not exist. Returning null is treated as "user exists with no authorities" in some versions and is never right. The returned UserDetails carries the username, the encoded password, the authority list and four booleans for account state — expired, locked, credentials expired, enabled — each of which DaoAuthenticationProvider checks and each of which produces a distinct exception (LockedException, DisabledException, …) that a login handler can map to a specific message.

package com.example.catalog.security;

import java.util.List;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
public class JpaUserDetailsService implements UserDetailsService {

    private final AccountRepository accounts;

    public JpaUserDetailsService(AccountRepository accounts) { this.accounts = accounts; }

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        Account account = accounts.findByEmailIgnoreCase(username)
                .orElseThrow(() -> new UsernameNotFoundException("no account for " + username));

        List<SimpleGrantedAuthority> authorities = account.roles().stream()
                .map(role -> new SimpleGrantedAuthority("ROLE_" + role))   // hasRole('ADMIN') needs ROLE_ADMIN
                .collect(java.util.stream.Collectors.toCollection(java.util.ArrayList::new));

        return User.withUsername(account.email())
                .password(account.passwordHash())          // already encoded - see below
                .authorities(authorities)
                .accountLocked(account.isLocked())
                .disabled(!account.isEnabled())
                .build();
    }
}

Password encoding: bcrypt and the delegating encoder

Passwords are never stored in a form that can be reversed, and they are never compared with equals. PasswordEncoder.matches(raw, encoded) exists precisely so that the algorithm can change without changing the calling code. Boot registers PasswordEncoderFactories.createDelegatingPasswordEncoder() when no encoder bean is present, which produces hashes prefixed with their algorithm — {bcrypt}$2a$10$… — and delegates on each check. That prefix is what makes migration possible: existing {noop} or {pbkdf2} hashes keep working while new ones are written with bcrypt.

bcrypt with strength 10 (the default) is the sensible choice: it is deliberately slow, its cost is tunable, it embeds a per-password salt in the output so identical passwords produce different hashes, and the work factor can be raised as hardware improves — new BCryptPasswordEncoder(12) being roughly four times slower than the default. Raising the cost factor invalidates nothing, because each stored hash carries its own cost parameter. Argon2 (Argon2PasswordEncoder) is stronger against GPU attacks and available when spring-security-crypto plus Bouncy Castle are on the classpath; PBKDF2 exists for FIPS-constrained environments.

@Bean
PasswordEncoder passwordEncoder() {
    // Delegating: writes {bcrypt}, reads any registered algorithm - the migration path.
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

// Or explicit bcrypt at a chosen strength:
//   return new BCryptPasswordEncoder(12);

// Hashing a password for a seed script or a test fixture:
//   String hash = passwordEncoder().encode("s3cret");   // -> "{bcrypt}$2a$10$..."
The delegating encoder's default algorithm in Spring Security 6 is bcrypt, and {noop} still exists for tests and legacy rows. Shipping NoOpPasswordEncoder to production is a vulnerability scanner finding and a real one: it stores the password in plain text. If you see {noop} in a live database, that is the incident.

Provider-managed and non-password authentication

Not every authentication is a username and password. A pre-authenticated provider trusts a header or a certificate set by an upstream proxy; an OAuth2 login flow produces an authenticated principal from a third party; a service-to-service call may use mutual TLS or a signed token. All of them plug into the same AuthenticationProvider list and produce the same Authentication object, so authorisation code does not change. That uniformity is the point of the abstraction and the reason to add a provider rather than a bespoke filter whenever the mechanism fits.

6.3 Authorization: request rules, roles and method security

Authorization happens in two places — the URL rule and the method rule — and doing it in only one of them is how an endpoint gets exposed through a path nobody remembered.

Roles are authorities with a prefix

Spring Security has one concept, GrantedAuthority, and one naming convention: hasRole("ADMIN") is exactly hasAuthority("ROLE_ADMIN"). The prefix exists to distinguish a coarse role from a fine-grained permission, and mixing the two up is the most common authorisation bug: storing ADMIN and then checking hasRole("ADMIN") fails silently with a 403 that looks like a configuration problem. Keep roles in the ROLE_ namespace and permissions without a prefix, and prefer the explicit hasAuthority form in code where a reader might not know the convention.

Request rules are prefix-based, and prefixes are order-sensitive

requestMatchers are evaluated top to bottom and the first match wins, so a broad rule placed before a narrow one makes the narrow one dead. Two conventions follow: order from specific to general, and end with a terminal anyRequest() — omitting it means an unmatched request is permitted, which is the opposite of the safe default and is easy to do because the code compiles and runs.

Note that requestMatchers in Security 6 replaced antMatchers, mvcMatchers and regexMatchers with an overload set that resolves the right matcher from the argument type: a string is treated per the configured MvcRequestMatcher (which Boot sets up when Spring MVC is present), a HttpMethod plus string is method-scoped, and PathPatternRequestMatcher handles pattern objects. The MVC-aware matcher is why /api/books/{isbn} style rules are safer in Security 6 than they were with antMatchers: the matching semantics are the same ones the controller used.

@RestController
@RequestMapping("/api/orders")
@PreAuthorize("isAuthenticated()")                 // class level: every method starts closed
class OrderController {

    // Owner-or-admin, expressed against a method argument.
    @GetMapping("/{id}")
    @PreAuthorize("#id == authentication.principal.claims['sub'] or hasRole('ADMIN')")
    OrderView get(@PathVariable String id) { return service.get(id); }

    // Role plus a business permission.
    @DeleteMapping("/{id}")
    @PreAuthorize("hasRole('ADMIN') and hasAuthority('orders.delete')")
    void delete(@PathVariable String id) { service.delete(id); }

    // The principal is injectable - no SecurityContextHolder call in business code.
    @GetMapping("/mine")
    List<OrderView> mine(@AuthenticationPrincipal JwtAccessor principal) {
        return service.byCustomer(principal.subject());
    }
}

Method security and self-invocation

@EnableMethodSecurity creates an AOP advisor, so the same proxy rules as chapter 2 apply: a call from one method of a bean to another method of the same bean does not pass through the advisor, and the annotation is ignored. The default prePostEnabled = true turns on @PreAuthorize and @PostAuthorize; @Secured needs securedEnabled = true and is the older, weaker form (no SpEL). @PreAuthorize is the better default: it composes with and/or and it can read method arguments.

Two operational notes matter. Method security failures raise AccessDeniedException from inside the call, which the servlet layer converts to 403 only if ExceptionTranslationFilter is still on the call stack — that is why a method security check in a scheduled job or an async consumer throws an exception rather than producing an HTTP response, and why such code needs its own handling. And method security on a repository method is a common choice for multi-tenant filters (a @PreAuthorize with a SpEL expression that adds and tenant = ? looks attractive) but it is fragile: the check sees the argument, not the query, so it cannot prevent a caller from reading another tenant's row by id. Tenant isolation belongs in the query.

@PreAuthorize on a controller method is defence in depth, not the primary control. The URL rule is what stops the request from reaching the method, and the method rule is what stops a future caller (a message listener, a scheduled job, another controller) from invoking it unguarded. Keep both, and never remove the URL rule because the method rule "already covers it".

6.4 Form login versus JWT resource server

Boot supports two shapes of OAuth2 out of the box: the application as a resource server that validates tokens issued elsewhere, and the application as a client that logs users in through a provider. Choosing wrongly is expensive, because switching later changes the session model, the CSRF posture and every client integration.

Resource server: validate, do not issue

spring-boot-starter-oauth2-resource-server adds a BearerTokenAuthenticationFilter and a JwtDecoder. Point spring.security.oauth2.resourceserver.jwt.issuer-uri at the authorization server and Boot fetches its OpenID configuration, discovers the JWKS URI, and builds a decoder that verifies the signature, the issuer, the expiry and (if present) the audience. With a symmetric or non-discoverable key you supply jwk-set-uri or public-key-location instead. Crucially, a resource server never issues tokens — that is the authorization server's job — so there is no signing key, no refresh-token table and no revocation list in your application.

The consequence is that revocation is the authorization server's problem and cannot be solved by a JWT alone. Access tokens are short-lived (typically 5–15 minutes) and the resource server trusts them until they expire; a logout that revokes a refresh token does not invalidate an already-issued access token. If instant revocation is a requirement, the answer is token introspection (spring.security.oauth2.resourceserver.opaquetoken.introspection-uri) or a very short token lifetime, not a local denylist.

# application.yml - resource server with issuer discovery
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com/realms/catalog
          audiences: catalog-api          # validated if "aud" is present in the token
server:
  port: 8080

// Map JWT claims onto authorities. Default: the "scope"/"scp" claim becomes
// SCOPE_xxx and nothing else, which surprises people who expect roles.
@Bean
JwtAuthenticationConverter jwtAuthenticationConverter() {
    var granted = new JwtGrantedAuthoritiesConverter();
    granted.setAuthoritiesClaimName("roles");          // our claim is "roles", not "scope"
    granted.setAuthorityPrefix("ROLE_");

    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(granted);
    converter.setPrincipalClaimName("sub");
    return converter;
}

OAuth2 login: the application is a client

When the application is the one authenticating a human — an admin console, a dashboard — the fit is OAuth2 client with OpenID Connect. The user is redirected to the provider, returns with an authorization code, and the code is exchanged for tokens; Spring Security creates a session and an OidcUser principal. Register a client with one property block per provider:

OIDC login keeps a session, so sessions must be managed: a clustered deployment needs spring-session-jdbc or spring-session-data-redis, and logout must reach the provider's end-session endpoint (OidcClientInitiatedLogoutSuccessHandler) or the user is logged back in on the next request.

Form login, and why an API should not use it

.formLogin() with a UserDetailsService and a session is entirely legitimate — for a server-rendered application. It is a poor fit for a JSON API consumed by a single-page app or a mobile client, for three concrete reasons: the session cookie cannot be sent across origins reliably, CSRF protection becomes the client's problem, and horizontal scaling needs sticky sessions or a shared session store. If you must use it for an API, keep CSRF on, expose the token as a cookie a JavaScript client can read, and add server.servlet.session.cookie.same-site=strict.

6.5 CORS, CSRF, headers and hard-won defaults

Three mechanisms cause most Spring Security support tickets. Each has a correct configuration that is short, and an incorrect one that appears to work in a browser.

CORS must be handled twice

Cross-origin resource sharing is a browser enforcement, not a server one: the browser blocks the response unless the server returns an Access-Control-Allow-Origin that matches the page's origin. Spring MVC has @CrossOrigin and WebMvcConfigurer.addCorsMappings; Spring Security has its own CorsFilter in the chain, and a preflight OPTIONS request is rejected by the security chain before MVC can answer it. So both layers must agree, and the reliable pattern is to define a single CorsConfigurationSource bean that Security's .cors(withDefaults()) picks up, and let MVC use it too.

The rule that causes trouble is that allowedOrigins("*") cannot be combined with allowCredentials(true) — the browser rejects the response and the server logs nothing. A credentialed request needs explicit origins. Also, allowedHeaders("*") does not cover the preflight's Access-Control-Request-Headers for every client unless exposedHeaders is considered separately: allowed is what the client may send, exposed is what the client may read.

@Configuration
class CorsConfig {

    @Bean
    CorsConfigurationSource corsConfigurationSource() {
        var cfg = new CorsConfiguration();

CSRF: keep it for cookies, drop it for tokens

Cross-site request forgery works because a browser attaches a session cookie to any request to your origin, including one triggered by a page on another site. CSRF protection is therefore required exactly when the credential is a cookie that the browser sends automatically; it is unnecessary for an Authorization: Bearer token that JavaScript must add explicitly. Disabling it on a cookie-authenticated application is a real vulnerability, not a style choice.

For a single-page application with `SameSite` cookies on `Lax` or `Strict`, the token still has to be available to JavaScript and the response must set the cookie before the token is read. Spring Security 6 uses a deferred CSRF token by default, and a controller that returns before the token is rendered produces an empty cookie. The documented fix is to expose the token via a CsrfTokenRequestAttributeHandler and to force resolution; the older XorCsrfTokenRequestAttributeHandler is the default and adds BREACH protection, which is what you want for a server-rendered form.

// SPA-friendly CSRF: readable cookie plus an eager token so the cookie is set
// before the first JavaScript request reads it.
@Bean
SecurityFilterChain spa(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())  // JS must read it
            .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler()))    // no XOR deferral
        .authorizeHttpRequests(a -> a.anyRequest().authenticated());
    return http.build();
}

// Server-rendered forms: keep the defaults (XorCsrfTokenRequestAttributeHandler)
// and include the token in the form:
//   <input type="hidden" th:name="${_csrf.parameterName}" th:value="${_csrf.token}">

Headers, sessions and the four settings to check

Boot's security headers are on by default and are worth verifying rather than reconfiguring: X-Content-Type-Options: nosniff, X-Frame-Options: DENY (or SAMEORIGIN if you must frame your own pages), a permissive-but-not-too-permissive Referrer-Policy, and Strict-Transport-Security on HTTPS with includeSubDomains and a sensible max-age. A concrete Content-Security-Policy is application-specific and is the one header Boot does not set — a policy that is too strict breaks the UI and one that is too loose is decoration, so it needs real testing.

Session management has two settings that catch people out. server.servlet.session.cookie.same-site should be Lax or Strict unless there is a genuine cross-site flow; unused sessionId handling (sessionFixation().migrateSession()) is a default and should stay on. And on any stateless API, set sessionManagement(s -> s.sessionCreationPolicy(STATELESS)) explicitly: without it Spring Security may still create an empty JSESSIONID, which is a session that exists to be attacked.

Actuator endpoints are a class of endpoint that Boot adds but does not protect by itself. On a Boot 3 application with the actuator starter, /actuator/health and /actuator/info are exposed over HTTP by default and everything else is not — but /actuator/** must still be matched in the security chain, because an endpoint added to the exposure list without a matching rule becomes public. Expose only what you need, and never expose env, configprops or heapdump without authentication.

7 · Testing

The hard part of testing a Boot application is not writing assertions; it is deciding how much of the container to start. Starting all of it is slow and proves little about the specific unit under test; starting none of it misses the wiring bugs that are the reason you chose a framework with auto-configuration. Boot's answer is the test slice: a small, curated slice of auto-configuration per layer.

7.1 JUnit 5 and the shape of a Boot test

spring-boot-starter-test pulls in JUnit 5 (Jupiter), AssertJ, Mockito, Hamcrest, JSONassert and XMLUnit, and configures Surefire or the Gradle test task for the Jupiter engine. No test runner class and no @RunWith is needed.

What the starter actually provides

The dependency set is chosen so tests need no further libraries for ordinary work. JUnit 5 provides the lifecycle and the runner; AssertJ provides the assertion style nearly everyone prefers (assertThat(actual).isEqualTo(expected) with type-aware methods and readable failure messages); Mockito provides doubles; JSONassert and JsonPath assert JSON bodies without deserialising them; XMLUnit does the same for XML. Mixing Hamcrest and AssertJ in one project is a small but real readability cost, so pick AssertJ.

Lifecycle, and the cost of @BeforeEach in a container test

By default JUnit creates a new test-class instance per test method, so instance fields are not shared between tests. @TestInstance(PER_CLASS) changes that and is required for a non-static @BeforeAll; it also means mutable state leaks between methods, so it is a deliberate trade. @Nested classes group tests by scenario and inherit the outer class's state and extensions — which is how a Boot test can share one context across several behaviours and still read as a hierarchy.

The expensive annotation in a container test is @BeforeEach that mutates shared data. Boot caches the ApplicationContext across test classes that declare the same configuration, but it does not roll back your in-memory repository unless the test is transactional. In a @DataJpaTest or a @Transactional @SpringBootTest, each test runs in a transaction that is rolled back at the end, so cleanup is automatic. Outside those, an insert in one test is visible in the next — and the failure appears as a duplicate-key error in an unrelated test.

package com.example.catalog.catalog;

Plain unit tests should not start the container

A test that starts Spring to check a calculation is paying seconds for nothing. The service example in chapter 2 was constructed with new precisely so that it can be tested that way. The rule that keeps the suite fast: use a container test when the thing under test is wiring — a repository's derived query, a controller's mapping and conversion, a filter's order, a properties binding — and a plain unit test when the thing under test is logic. A suite where every test is @SpringBootTest typically runs in minutes and finds few wiring bugs anyway, because the wiring under test is the same in every case.

Always end with a terminal assertion. assertThatThrownBy(…).isInstanceOf(…) passes for the wrong exception unless you also assert the message or a specific subclass; AssertJ's hasMessageContaining is the cheap guard that stops a test from passing when a NullPointerException is thrown for an unrelated reason.

7.2 @SpringBootTest versus test slices

A slice is a Boot test annotation that loads one layer's auto-configuration instead of all of it. The payoff is speed and focus; the cost is that the parts left out are not verified in that test.

What each annotation loads

@SpringBootTest loads the whole context: every auto-configuration, every bean, the embedded server if the web environment is not NONE. It is the only annotation that proves the application starts, and it is the wrong one for a unit-level behaviour test. The slices each load a documented subset:

Two properties decide whether the slice is honest. @WebMvcTest(BookController.class) narrows the loaded controllers; without the argument every controller is loaded, which is slower and, more importantly, means a bean you did not intend to mock can be required. And @DataJpaTest replaces the configured datasource with an embedded one by default — H2 in PostgreSQL compatibility mode — which is fast and is not your database. A query that relies on a PostgreSQL-specific function, a partial index, or a case-sensitivity rule passes on H2 and fails in production. The fix is chapter 7.4's Testcontainers datasource, not a more careful H2 setup.

Choosing the smallest slice that can fail

The discipline that keeps a suite useful is to pick the slice by the failure you want to catch. A mapping typo, a missing @Valid, an exception handler returning the wrong status — @WebMvcTest. A derived query returning the wrong rows because a fetch plan is wrong — @DataJpaTest. A properties record that does not bind because a key is misspelled — @SpringBootTest with a test profile, or better, a plain JUnit test that binds the record through a small ApplicationContextRunner. A class of tests that could be a slice but is written as @SpringBootTest is the single largest source of slow test suites in Boot projects.

Where a slice is not enough — an HTTP contract test that goes through the real server, the real filters and the real database — use @SpringBootTest(webEnvironment = RANDOM_PORT) plus a real client. That combination is genuinely end-to-end and should be a small, deliberate set of tests, because each one starts the server.

// A full-stack test with a real port, real filters and a real database.
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ActiveProfiles("test")
class BookApiIT {

    @Autowired TestRestTemplate rest;              // or RestClient with a base URL from the port

    @Test
    void createThenReadBack() {
        var created = rest.postForEntity("/api/books",
                new CreateBookRequest("9780132350884", "Effective Java", new BigDecimal("54.99"), null),
                Void.class);
        assertThat(created.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        assertThat(created.getHeaders().getLocation()).isNotNull();

        var fetched = rest.getForEntity(created.getHeaders().getLocation(), BookResponse.class);
        assertThat(fetched.getBody().title()).isEqualTo("Effective Java");

Boot caches contexts by configuration, so two slice tests with different @MockitoBean sets have different cache keys and each starts its own context. The cache holds a limited number (32 by default) and evicts the least recently used, which then has to be rebuilt. If a suite is slow, print the context cache statistics with logging.level.org.springframework.test.context.cache=DEBUG — the log shows every context created and every cache hit.

7.3 MockMvc, the request DSL and the current alternatives

MockMvc dispatches a request through the real DispatcherServlet without a network socket. It is fast, it exercises every MVC stage, and it is the right default for controller tests — with two newer APIs worth knowing.

How the request is dispatched

MockMvc holds a DispatcherServlet and a set of filters, and perform(…) builds a MockHttpServletRequest, runs it through the filter chain and the servlet, and returns a ResultActions over a MockHttpServletResponse. Because no container is involved, the request has no real network semantics: Content-Type, Accept and status codes are honoured, but there is no chunked encoding, no real redirect following and no TLS. That is the trade-off — MockMvc proves the application's handling of a request, not the container's handling of a connection.

Filters registered as beans are applied when the context is a WebApplicationContext and the test is configured with @AutoConfigureMockMvc(addFilters = true) (the default). That is what makes @WebMvcTest the right home for a security test: spring-security-test adds SecurityMockMvcRequestPostProcessors such as .with(user("aisha").roles("ADMIN")) and .with(jwt().jwt(j -> j.subject("aisha"))), so an endpoint's authorisation can be tested without a real token.

@WebMvcTest(BookController.class)
@Import(ApiExceptionHandler.class)              // advice is not picked up by the slice automatically
class BookValidationTest {

    @Autowired MockMvc mvc;
    @MockitoBean CatalogService service;

    @Test
    void rejectsBlankIsbnWithFieldErrors() throws Exception {
        String body = """
                {"isbn":"", "title":"", "price":-1}
                """;

        mvc.perform(post("/api/books")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content(body))
           .andExpect(status().isBadRequest())
           .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_PROBLEM_JSON))
           .andExpect(jsonPath("$.errors[?(@.field=='isbn')]").exists())
           .andExpect(jsonPath("$.errors[?(@.field=='title')]").exists());
    }

    @Test
    void unknownBookIs404Problem() throws Exception {
        given(service.find("0000000000")).willReturn(Optional.empty());

        mvc.perform(get("/api/books/0000000000"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.type").value("https://errors.example.com/book-not-found"));
    }

    @Test
    @WithMockUser(roles = "ADMIN")
    void adminCanDelete() throws Exception {
        mvc.perform(delete("/api/books/9780132350884")).andExpect(status().isNoContent());
    }
}

MockMvcTester and why the fluent assert form exists

Spring Framework 6.2 added MockMvcTester, an AssertJ-based façade over the same MockMvc machinery. Instead of the matcher chain it returns an Assert object, so a failure message reads like an AssertJ failure rather than a MockMvc matcher dump, and the IDE completes on the methods. It is opt-in: @AutoConfigureMockMvc plus a MockMvcTester injection, or MockMvcTester.of(mockMvc). Both forms are supported and neither is wrong; the AssertJ one is what this guide prefers for new tests because the failure output is materially better.

@WebMvcTest(BookController.class)
class BookTesterStyleTest {

    @Autowired MockMvcTester mvc;                 // AssertJ-style wrapper, same engine
    @MockitoBean CatalogService service;

    @Test
    void returnsBook() {
        given(service.find("9780132350884")).willReturn(Optional.of(sample()));

        assertThat(mvc.get().uri("/api/books/9780132350884"))
                .hasStatusOk()
                .bodyJson()
                .extractingPath("$.title").isEqualTo("Effective Java");
    }
}

Asserting the parts people skip

Three assertions separate a useful controller test from a smoke test. Content type — contentTypeCompatibleWith(APPLICATION_PROBLEM_JSON) — catches a converter regression that a status-code assertion misses. Headers: Location on a 201, ETag and Cache-Control on a cacheable read; these are part of the contract and are silently removable. A negative case per endpoint: an unauthenticated request is 401, an authenticated but unauthorised request is 403, and a malformed body is 400 — three tests that catch most security and validation regressions and that are almost never written.

@WebMvcTest does not load @ControllerAdvice beans referenced only by type. An advice class is picked up when it is annotated @ControllerAdvice or @RestControllerAdvice and is in the scanned package, but a @Configuration that declares an advice bean is not — hence the @Import(ApiExceptionHandler.class) above. The symptom of forgetting it is a 500 where the test expected a 404.

7.4 Testcontainers: real dependencies, ephemeral

Testcontainers starts a real database, broker or cache in a Docker container for the duration of the test run and throws it away afterwards. It removes the largest source of "works in CI, fails in production" — the test double that behaves differently from the real thing.

Why not H2

An embedded database is a different product. SQL dialect differences are the visible part: window functions, jsonb, on conflict do update, case-insensitive collations, partial indexes, numeric rounding and identifier quoting all differ, and every one of them has produced a production incident that a green test suite did not catch. The invisible part is worse: transaction isolation defaults, the behaviour of a failed unique constraint inside a transaction, and how the driver reports an error. A test that exercises a query whose correctness depends on the database should use that database.

Service connections, and how little configuration they need

Since Boot 3.1 the integration is a single annotation plus a container field. @ServiceConnection on a container field tells Boot to derive the connection properties from the container — spring.datasource.url, username and password from a PostgreSQLContainer, or the bootstrap servers from a KafkaContainer — so no @DynamicPropertySource block, no property plumbing, and it works for JPA, JDBC, Kafka, RabbitMQ, MongoDB, Redis, Elasticsearch, Neo4j, Cassandra and more. Add spring-boot-testcontainers and the Testcontainers BOM (managed by Boot) and the dependency is complete.

Three details make the difference between a fast suite and an unusable one. Start the container once per class, not per test — a static field with @Container and the default per-class lifecycle. Reuse across the whole run with a static singleton container or reusable mode (testcontainers.reuse.enable=true plus withReuse(true)) when the startup cost dominates. Pin the image tag — postgres:17-alpine, never postgres:latest — or the suite changes behaviour without a code change. Guard the environment: @Testcontainers(disabledWithoutDocker = true) skips rather than fails on a laptop without Docker, but that also means the tests do not run. In CI the correct posture is the opposite: run them, and fail the build if Docker is unavailable.

Testcontainers versus Docker Compose versus an external database

Testcontainers is the default choice because each test run is isolated and reproducible. Docker Compose support (spring-boot-docker-compose) is complementary and aimed at development: it starts the services declared in compose.yaml when the application starts, wires the connection details automatically, and stops them on shutdown — a better inner loop than a shared database nobody owns. An externally provisioned database is the right choice only when the schema or data is too large to create per run, and it comes with the usual cost: shared state, flaky tests, and a schema that drifts from the migrations.

7.5 Test doubles, test profiles and context customisation

A test double replaces a collaborator that is slow, external or nondeterministic. Boot's overrides make this a one-annotation change inside a slice, and its profiles make configuration-driven tests explicit.

@MockitoBean and why it replaced @MockBean

@MockBean and @SpyBean were deprecated in Boot 3.4 in favour of @MockitoBean and @MockitoSpyBean, which live in org.springframework.test.context.bean.override.mockito and are framework features rather than Boot ones. The new annotations work at the bean definition level and compose with the override machinery's other implementations (@TestBean, which replaces a bean with a method-provided instance). Practically they behave the same: the named bean is replaced in the test's context, and an unmatched name fails the test with an explicit message rather than being silently ignored — which was the main complaint about the old annotations.

class PaymentServiceTest {

    @MockitoBean PaymentGateway gateway;                 // replaces the bean in this context
    @MockitoSpyBean AuditService audit;                  // real implementation, recorded calls

    @Test
    void retriesOnceOnTimeoutThenFails() {
        given(gateway.charge(any(), any()))
                .willThrow(new GatewayTimeoutException("upstream"))
                .willReturn(new ChargeResult("ok", "tx-1"));

        var result = service.pay(new Payment("order-1", new BigDecimal("19.99")));

        assertThat(result.transactionId()).isEqualTo("tx-1");
        verify(gateway, times(2)).charge(any(), any());
        verify(audit).recordAttempt(anyString());
    }
}

When a double is the wrong answer

Mocking is a design signal. A service that needs six mocks to test one method has six collaborators and probably one too many responsibilities. More concretely, three cases should not be mocked: value objects (make a real one), your own repository against a real database (use Testcontainers — a mocked repository tests the mock), and the class under test (that is a tautology). What is right to mock is a boundary you do not own: an HTTP client, a message publisher, a clock, a random source, a payment gateway. For a clock, prefer injecting java.time.Clock over mocking a static method — it is a one-line change and it removes the mocking entirely.

// Prefer a real collaborator when the collaborator is trivial: no mocking at all.
@Service
class SubscriptionService {

    private final Clock clock;                 // injected; Clock.systemUTC() in production

    SubscriptionService(Clock clock) { this.clock = clock; }

    boolean isActive(Subscription s) { return s.expiresAt().isAfter(clock.instant()); }
}

@Bean Clock clock() { return Clock.systemUTC(); }

// Test: hand it a fixed clock - deterministic, no framework, no mock.
@Test
void inactiveAfterExpiry() {
    var fixed = Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC);
    var svc = new SubscriptionService(fixed);
    assertThat(svc.isActive(new Subscription(Instant.parse("2025-12-31T00:00:00Z")))).isFalse();
}

Test configuration, profiles and property overrides

Four mechanisms cover almost every test-specific wiring need, and they are worth choosing deliberately because each has a different blast radius. @TestConfiguration declares extra beans for one test class only — it is imported, not scanned, so it cannot leak into another test. @ActiveProfiles("test") activates a profile, and a src/test/resources/application-test.yml supplies its values; those values apply to every test annotated with that profile. properties = {…} on the test annotation overrides a single key for that class only. And @DynamicPropertySource registers values computed at runtime — the shape that was needed for Testcontainers before @ServiceConnection, and still the right tool for a value you must compute.

Do not put a real production hostname, credential or API key in src/test/resources/application-test.yml. Test resources are part of the repository and are read by every developer and every CI job. If a test needs a credential, generate one (a random password on a container), mock the boundary, or use a secrets-free fake. A leaked test credential is treated by auditors exactly like a leaked production one.

8 · Actuator, observability and production readiness

An application that cannot be observed cannot be operated. Spring Boot Actuator adds a management surface — health, metrics, configuration introspection, thread dumps — and Micrometer adds the instrumentation that turns application events into metrics and traces. Everything in this chapter is about what to expose, to whom, and what the data actually means when an incident starts.

8.1 Endpoints: what exists and what to expose

Actuator ships around thirty endpoints behind one HTTP base path. Only two are exposed by default, because the surface includes things that leak configuration and things that stop the process.

The endpoints worth knowing

Two families matter in practice: the operational ones you will call during an incident, and the introspection ones you will call when something is misconfigured. Exposure, access and the two switches

Two independent settings control each endpoint, and confusing them is why an endpoint sometimes 404s and sometimes 403s. Exposure (management.endpoints.web.exposure.include) decides whether it is registered on the web at all; an unexposed endpoint is a 404. Access (Boot 3.4's management.endpoints.access.default, or per-endpoint management.endpoint.<id>.access) decides whether the endpoint behaves as enabled, read-only or disabled; an endpoint whose access is NONE returns 404 even when exposed. With Spring Security on the classpath a third layer — the filter chain — decides who may reach it, and that layer is the one that must be configured explicitly, because exposing an endpoint does not authenticate it.

# application.yml - expose a deliberate list, and never "*"
management:
  endpoints:
    web:
      base-path: /actuator
      exposure:
        include: health,info,metrics,prometheus,loggers
        exclude: env,beans,heapdump,shutdown
  endpoint:
    health:
      show-details: when-authorized
      show-components: when-authorized
      probes:
        enabled: true
    loggers:
      access: READ_ONLY            # read levels in prod; write them locally
    shutdown:
      access: NONE                 # keep the endpoint disabled outright
  info:
    env:
      enabled: true                # include keys under "info.*"

The main port then serves only application traffic, and the management port can be bound to a private interface, blocked at the network layer, or omitted from the container's exposed ports entirely. In Kubernetes this is the standard shape — the service selects the application port, and only the kubelet reaches the management port for probes.

Runtime log levels, and why loggers is the most useful endpoint

GET /actuator/loggers/com.example.catalog returns the effective level, and POST with {"configuredLevel":"DEBUG"} changes it live — no restart, no redeploy. On a service that logs at INFO and has a production-only bug, this endpoint is the difference between a deploy cycle and thirty seconds. It is also a production control with a blast radius: setting ROOT or a framework package to TRACE can emit hundreds of megabytes into the log pipeline, so it must be authenticated, rate-limited by policy, and reverted deliberately. Restrict it with access: READ_ONLY in production and enable writes only against the management port.

curl -s -X POST localhost:9090/actuator/loggers/com.example.catalog \

Never set management.endpoints.web.exposure.include=* on an internet-reachable service. It exposes env and configprops (sanitised, but still a map of your infrastructure), heapdump (a full memory image, including any credential the JVM holds) and shutdown. The scanner finding is real and the heap dump is a data breach. Expose a named list and authenticate it.

8.2 Health checks, liveness and readiness

A health check answers a different question in each direction. Liveness asks "should this process be restarted"; readiness asks "should traffic be sent here". Getting them backwards causes outages that a correct deployment would have avoided.

The aggregate, the indicators and the HTTP status

HealthEndpoint polls every registered HealthIndicator bean and reduces their statuses: UP(0), UNKNOWN(1), OUT_OF_SERVICE(2), DOWN(3), and the aggregate is the lowest (worst) of them. The HTTP status code is mapped from that aggregate: UP and UNKNOWN produce 200, everything else produces 503. Boot auto-configures indicators for the datasource, Redis, RabbitMQ, Kafka, Elasticsearch, a disk-space check, a mail server, and the application's own availability, all guarded by @ConditionalOnClass, so installing a starter silently adds a health check that can fail.

That last point is operational, not academic: a Kafka or Redis health indicator that reports DOWN makes /actuator/health return 503, and if a load balancer uses that endpoint to decide routing, a transient broker blip drains every instance at once. Choose deliberately whether each dependency is required for serving traffic; if it is not, exclude its indicator from the readiness group.

package com.example.catalog.health;

import java.math.BigDecimal;
import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.HealthIndicator;
import org.springframework.stereotype.Component;

@Component("pricingFeed")
public class PricingFeedHealthIndicator implements HealthIndicator {

    private final PriceFeed feed;

    public PricingFeedHealthIndicator(PriceFeed feed) { this.feed = feed; }

    @Override
    public Health health() {
        var snapshot = feed.lastSnapshot();
        if (snapshot.age().toMinutes() > 15) {
            // A dependency the service can degrade without: report the detail, keep the service UP.
            return Health.up()
                    .withDetail("age", snapshot.age().toString())
                    .withDetail("stale", true)
                    .build();
        }
        return Health.up()
                .withDetail("age", snapshot.age().toString())
                .withDetail("quotes", snapshot.count())
                .build();
    }
}

Groups and probes

Health groups are named subsets of the indicators, each with its own HTTP path. Boot predefines liveness and readiness when probes are enabled — automatically true inside Kubernetes, or forced with management.endpoint.health.probes.enabled=true. The liveness group contains only the LivenessState contributor by default and must stay that way: including the database would mean a slow database restarts every healthy instance. The readiness group contains ReadinessState and is where dependencies that must be reachable to serve traffic belong.

The state machine is explicit and worth using. ApplicationAvailability has two states: LivenessState.CORRECT/BROKEN and ReadinessState.ACCEPTING_TRAFFIC/REFUSING_TRAFFIC. Boot sets both during startup and shutdown, so an instance that is still initialising reports REFUSING_TRAFFIC and does not receive requests, and a clean shutdown flips readiness first so the load balancer removes the instance before the process exits. Application code can publish a change for a genuine visibility problem — a service that has lost its database connection should report REFUSING_TRAFFIC rather than being restarted.

# application.yml - probes with an explicit readiness composition
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState                 # never add db or broker here
        readiness:
          include: readinessState,db,pricingFeed
          additional-path: /readyz               # alias, alongside /actuator/health/readiness
  health:
    db:
      enabled: true
    diskspace:
      enabled: true
      threshold: 500MB
    rabbit:
      enabled: false                             # broker outage must not drain the pool

// Refuse traffic instead of being restarted when a required dependency is gone.
package com.example.catalog.health;

import org.springframework.boot.availability.AvailabilityChangeEvent;
import org.springframework.boot.availability.ReadinessState;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Component;

@Component
public class ReadinessSwitch {

    private final ApplicationEventPublisher events;

    public ReadinessSwitch(ApplicationEventPublisher events) { this.events = events; }

    // Called from a connection listener: the datasource is unrecoverable here.
    void onDatabaseLost() {
        AvailabilityChangeEvent.publish(events, this, ReadinessState.REFUSING_TRAFFIC);
    }

    void onDatabaseRestored() {
        AvailabilityChangeEvent.publish(events, this, ReadinessState.ACCEPTING_TRAFFIC);
    }
}
// Kubernetes maps these to the /readyz probe, so the pod leaves the Service endpoints
// and stays alive - no restart, no lost in-flight work.

Kubernetes probes, in the right combination

The three probes have different failure consequences and must not point at the same endpoint. livenessProbe should hit /actuator/health/liveness with a generous failureThreshold, because a restart is a heavy action. readinessProbe should hit /actuator/health/readiness with a short period, because the cost of a false negative is only that one instance is skipped. startupProbe exists for a slow start — a native image with a large heap, or an application that loads a cache — and lets liveness be strict without killing an instance that is still starting.

# k8s deployment fragment - distinct probes, distinct endpoints
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 9090 }
  initialDelaySeconds: 20
  periodSeconds: 10
  failureThreshold: 6          # ~60s of real failure before a restart
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 9090 }
  periodSeconds: 5
  failureThreshold: 2
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 9090 }
  failureThreshold: 30
  periodSeconds: 5             # up to 150s to start, liveness deferred until then
Set management.endpoint.health.show-details=when-authorized and require a role for detail, rather than always. An unauthenticated health endpoint that lists every dependency, its version and its connection string is a reconnaissance gift. In Kubernetes, give the probe credential a role with access only to the health group.

8.3 Metrics with Micrometer and Prometheus

Micrometer is a façade over the metric systems: you instrument once against its API, and the registry that is on the classpath decides the output format. Actuator configures the registry and adds JVM, HTTP server, datasource and executor metrics automatically.

The four meter types, and which to reach for

Counter — a monotonically increasing value; use it for events ("requests", "errors", "messages consumed"). Gauge — a value sampled at scrape time; use it for a current quantity ("queue depth", "cache size") and note that it holds a weak reference to the object it observes, so a gauge over something short-lived can vanish. Timer — a duration distribution and a count; use it for any request, call or job length. DistributionSummary — a non-time distribution ("payload bytes"). The rule that avoids most metric mistakes: never use a Gauge to count events, because the intermediate values are lost, and never use a Counter for a value that can go down.

package com.example.catalog.pricing;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import org.springframework.stereotype.Service;

@Service
public class PriceService {

    private final Counter quotes;
    private final Counter failures;
    private final Timer fetchTimer;
    private final PriceFeed feed;

    PriceService(MeterRegistry registry, PriceFeed feed) {
        this.feed = feed;
        // Claim the meters in the constructor - avoids a per-call registry lookup
        // and makes the metric names discoverable in one place.
        this.quotes = Counter.builder("catalog.quotes")
                .description("Quotes requested")
                .register(registry);
        this.failures = Counter.builder("catalog.quotes.failures")
                .description("Quote requests that failed")
                .register(registry);
        this.fetchTimer = Timer.builder("catalog.quotes.fetch")
                .description("Upstream quote fetch duration")
                .publishPercentileHistogram()          // enables histogram_quantile in Prometheus
                .register(registry);
    }

    public Quote quote(String symbol) {
        quotes.increment();
        return fetchTimer.record(() -> {               // times the call, including exceptions
            try {
                return feed.fetch(symbol);
            } catch (RuntimeException e) {
                failures.increment();
                throw e;
            }
        });
    }
}

Tags, cardinality and the one rule that matters

Tags are the dimensions of a metric, and every unique combination becomes a separate time series. High cardinality is the single most common way to make a monitoring system expensive and unusable: tagging an HTTP metric with a raw URL, a user id, an order id or a full exception message creates unbounded series and the storage layer collapses. The discipline is that tags must have a bounded, known set of values — an HTTP status code, a method, a normalised route template, an error type, a tenant tier rather than a tenant id. Route normalisation is why the built-in HTTP server metrics are safe: http_server_requests_seconds is tagged with the mapped pattern (/api/books/{isbn}), not the concrete path.

Observation, and the annotation you should use instead

Micrometer's Observation API is the modern way to instrument: a single observation produces a metric and a span, so an operation is measured once and appears in both systems. @Observed on a method, with @EnableObservedAspect on a configuration class, is the least intrusive form; ObservedAspect is an AOP advisor and therefore obeys the proxy rules from chapter 2. @Timed and @Counted still work and produce metrics only. Boot's own instrumentation — HTTP server, RestClient, JDBC, Kafka, scheduled tasks — already uses observation, which is why a trace and a metric for the same request line up.

@Configuration
@EnableObservedAspect
class ObservabilityConfig {
    @Bean
    ObservedAspect observedAspect(ObservationRegistry registry) {
        return new ObservedAspect(registry);            // wires @Observed to the registry
    }
}

@Service
class CheckoutService {

    @Observed(name = "checkout.submit",
              contextualName = "checkout-submit",
              lowCardinalityKeyValues = {"component", "checkout"})
    Receipt submit(Cart cart) { /* ... */ }
}
// Yields: a timer "checkout.submit" (with the low-cardinality tags)
//         and a span named "checkout-submit" in the active trace.
Do not reach for a monitoring agent to collect what Boot already exposes. Actuator plus micrometer-registry-prometheus gives HTTP, JVM, connection-pool, executor, cache and Kafka consumer metrics with no code. Instrument application-specific things — quotes served, jobs completed, cache hits with your own semantics — and let the framework collect the rest.

8.4 Distributed tracing and structured logs

A request that crosses five services produces five log files. A trace id joins them, and the same id in a log pattern is what makes a log search useful during an incident.

Micrometer Tracing, bridges and exporters

Boot 3's tracing is built on Micrometer Tracing, which is a façade over two implementations: OpenTelemetry (micrometer-tracing-bridge-otel) and Brave (micrometer-tracing-bridge-brave). The bridge provides the API and context propagation; an exporter sends spans somewhere (opentelemetry-exporter-otlp, zipkin-reporter-brave). Choosing OpenTelemetry is the current default for a new system because it is the vendor-neutral format and the OTLP endpoint is understood by every backend; choosing Brave is reasonable when the receiving system is Zipkin.

Propagation is the part that has to be right. The bridge reads incoming context from the W3C traceparent header by default (OpenTelemetry) and injects it into outgoing calls made through instrumented clients — RestClient, RestTemplate, WebClient, Kafka, and the messaging template. A call made through a hand-rolled HttpURLConnection is invisible and breaks the trace at that hop, which is why the instrumented client is worth the small ceremony.

# application.yml - OTLP export, full sampling in dev and 10% in production
management:
  tracing:
    sampling:
      probability: 0.1              # 1.0 locally; 0.1 keeps headroom on a busy service
    propagation:
      type: w3c                     # traceparent/tracestate; also "b3", "b3_multi"
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
      compression: gzip

# Dependencies (versions from the Boot BOM):
#   io.micrometer:micrometer-tracing-bridge-otel

Structured logging

Log lines that are prose are cheap to read and expensive to query: 47ms to fetch book 9780132350884 needs a regular expression to extract the duration. Structured logging writes each event as a JSON object, so the log platform can index fields directly. Boot 3.4 added first-class support with logging.structured.format.console and logging.structured.format.file accepting ecs, logstash or gelf, and merged MDC entries into the output so a trace id becomes a field rather than a substring. Use it for machine consumption — a container's stdout collected by a platform — and keep the human-readable format for local development, where reading JSON is a step backwards.

The correlation between a log line and a trace is the mechanism that makes an incident tractable: given a 500 report, you search the log index for the status and find the trace id, then open the trace and see which downstream call was slow. Without the id in the pattern the two systems are separate and the join is manual.

  # spring.profiles.active=local  with  application-local.yml:

Sampling at 1.0 in production is the most common tracing misconfiguration. Every span is retained and exported, the collector becomes the bottleneck, and the tracing bill is the largest line on the observability invoice. Sample at 0.05–0.1, and use tail-based sampling in the collector if you need every error trace — head-based sampling in the application cannot know that a request will fail.

8.5 Graceful shutdown, info and production readiness checks

The difference between a deploy that drops requests and one that does not is a handful of settings that must all be present. This section is the checklist.

Graceful shutdown means two things at once

server.shutdown=graceful tells the embedded web server to stop accepting new connections and to wait for in-flight requests to finish, up to spring.lifecycle.timeout-per-shutdown-phase. It does not, by itself, remove the instance from a load balancer — that is the readiness probe's job, and the order matters: readiness must flip to REFUSING_TRAFFIC and stay there long enough for the balancer to notice, then the shutdown must wait for the drain. Boot flips readiness as part of the context close sequence, but the balancer's polling interval is what determines how much traffic still arrives after that. A 5–15 second readiness period means a 5–15 second window, so a drain timeout of at least that is the safe pairing.

Beyond HTTP, every long-running component should stop cooperatively. A SmartLifecycle bean with a getPhase() can order itself against the web server's shutdown; a Kafka listener container already implements it and will finish the current record before stopping if spring.kafka.listener.immediate-stop=false (the default). A @Scheduled method cannot be interrupted usefully and should therefore be short and idempotent. And @PreDestroy on a bean that owns a resource is where the final flush goes, with the caveat that the whole shutdown is bounded by the lifecycle timeout, so a @PreDestroy that waits indefinitely will be cut off.

# application.yml - the deploy-safety block
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s      # >= the load balancer's drain window
  kafka:
    listener:
      immediate-stop: false              # finish the in-flight record, then stop

# What a shutdown looks like in the log, in order:
#   Commencing graceful shutdown. Waiting for active requests to complete
#   Graceful shutdown complete
#   Closing ApplicationContext ...

// A lifecycle bean that stops accepting work before the web server drains.
@Component
class JobDispatcher implements SmartLifecycle {

    private final AtomicBoolean running = new AtomicBoolean(false);
    private final ExecutorService workers = Executors.newVirtualThreadPerTaskExecutor();

    @Override public void start() { running.set(true); }

    @Override public void stop() {
        running.set(false);                       // stop taking new work immediately
        try {
            if (!workers.awaitTermination(20, TimeUnit.SECONDS)) {
                workers.shutdownNow();            // bounded wait, then cancel
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            workers.shutdownNow();
        }
    }

    @Override public boolean isRunning() { return running.get(); }

    @Override public int getPhase() { return Integer.MAX_VALUE; }  // stop before the web server
}

9 · Caching, async and scheduling

Three annotations — @Cacheable, @Async and @Scheduled — each look like a one-line change and each work by generating a proxy. Their behaviour is therefore governed by the same rules: the annotation applies only to calls that arrive through the proxy, the thread and transaction context are not what you might assume, and the default concurrency settings are conservative in a way that fails silently under load.

9.1 Caching with @Cacheable and cache providers

The caching abstraction is a map with a key, a value, a policy for filling it and a policy for removing it. Boot auto-configures a provider from what is on the classpath, and the interesting decisions are the key, the eviction and which provider.

The four annotations and what each does

@Cacheable looks in the cache before invoking and stores the return value if it missed — the method body does not run on a hit, so it must be side-effect-free. @CachePut always invokes and stores the result, which is how you refresh an entry after a write. @CacheEvict removes an entry (or, with allEntries = true, the whole cache) and by default does so after the method returns, so a method that throws does not evict; beforeInvocation = true reverses that when a failed method should leave nothing cached. @Caching groups several of the others on one method, which is what a write that touches three caches needs.

package com.example.catalog.catalog;

import java.util.List;
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.cache.annotation.CachePut;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.cache.annotation.Caching;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CatalogService {

    private final BookRepository books;

    public CatalogService(BookRepository books) { this.books = books; }

    // Key defaults to a SimpleKey over all arguments; be explicit instead.
    @Cacheable(cacheNames = "booksByIsbn", key = "#isbn", unless = "#result == null")
    @Transactional(readOnly = true)
    public BookView byIsbn(String isbn) {
        return books.findByIsbn(isbn).map(BookView::from).orElse(null);
    }

    // Spread in the arguments: readable keys in the cache, and no surprise on refactor.
    @Cacheable(cacheNames = "bookSearch", key = "#q + ':' + #page + ':' + #size")
    public List<BookSummary> search(String q, int page, int size) {
        return books.search(q, page, size);
    }

    @CachePut(cacheNames = "booksByIsbn", key = "#result.isbn")
    @Transactional
    public BookView save(CreateBookRequest request) {
        return BookView.from(books.save(toEntity(request)));
    }

    // A write invalidates both the entry and the page of search results it appears in.
    @Caching(evict = {
        @CacheEvict(cacheNames = "booksByIsbn", key = "#isbn"),
        @CacheEvict(cacheNames = "bookSearch", allEntries = true)
    })
    @Transactional
    public void delete(String isbn) { books.deleteByIsbn(isbn); }
}

Keys, conditions and the things that break

The key is generated by a KeyGenerator — SimpleKeyGenerator by default, which combines the arguments into a SimpleKey. That default is fine for one argument and produces a key that changes shape when you add a parameter, so an explicit SpEL key is worth the typing. Two attributes look similar and are not: condition is evaluated before the call and decides whether the cache is consulted at all; unless is evaluated on the result and decides whether it is stored. Checking a value that only exists after the call in condition throws, and checking an argument in unless is legal but pointless.

The failure mode to know is self-invocation, the third time it appears in this guide: this.byIsbn(isbn) from another method of the same bean bypasses the cache interceptor, because the call never crosses the proxy. The result is a cache that appears to have a zero hit rate for one call site — usually the hot internal one. Moving the cached method to its own bean is the fix. sync = true is the second thing to know: it makes concurrent misses for the same key wait for the first computation instead of all executing, which is exactly what you want for an expensive lookup under load — but it is incompatible with unless and with multi-key caches, so it is per-method, not global.

Providers, and the two that are worth using

Boot selects a CacheManager from the classpath: RedisCacheManager if spring-boot-starter-data-redis is present, CaffeineCacheManager if Caffeine is, ConcurrentMapCacheManager otherwise. The last is a plain ConcurrentHashMap with no eviction, no size bound and no TTL — a memory leak with a friendly name, acceptable only in tests. spring.cache.type=none disables caching entirely, which is the correct setting for a test that asserts the underlying call happens.

The choice between Caffeine and Redis is a choice about sharing. Caffeine is in-process: the fastest possible cache (a lookup is a field read), no network, no serialisation, but each instance has its own copy and an eviction on one instance is invisible to the others. Redis is shared: one eviction invalidates every instance immediately, at the cost of a network round trip and a serialisation format per entry. Caffeine is right for data that is expensive to compute and cheap to be slightly stale (reference data, a parsed configuration, a rate-limit window). Redis is right when a write on one instance must invalidate the value on all of them — which is most business data.

Cache and transaction interaction

A cached read inside a transaction is where the two abstractions collide. If the cache advice sits outside the transaction advice, a transaction that rolls back leaves the value in the cache — a stale entry that contradicts the database, and one that no eviction will remove. If it sits inside, the cache is filled before the commit, which has the same problem from the other direction. The durable pattern is to cache read-only lookups on their own bean with no transactional writes nearby, to evict on every write path with @CacheEvict, and to give every entry a TTL so that any residual staleness is bounded rather than permanent. Do not rely on the framework's advice order: both advisors default to Ordered.LOWEST_PRECEDENCE, so set @EnableCaching(order = …) explicitly if the distinction matters to you.

In a clustered deployment, remember that eviction is a message to the provider. A Caffeine eviction reaches one instance; a Redis eviction reaches all of them. Choosing Caffeine for business data and then wondering why one pod serves stale values for five minutes is a design decision, not a bug.

Never cache a value whose correctness depends on the caller's identity without putting that identity in the key. A @Cacheable on a method that returns "the current user's orders" and keys on the order id alone will serve one user's data to another. If the method reads the SecurityContext or a request-scoped bean, the identity must be an explicit part of key — or the method must not be cached at all.

9.2 @Async and thread pool configuration

@Async moves a method call onto another thread. It does not create a queue, it does not propagate the transaction, and its default executor has changed since Boot 2 — three facts that decide whether the feature helps or becomes a silent resource leak.

What the proxy actually does

An @Async method is wrapped by an AsyncExecutionInterceptor, which submits the invocation to an Executor and returns immediately. The return type must therefore be void, Future<T>, CompletableFuture<T> or ListenableFuture<T>; a method returning a plain value is a startup-time configuration error, not a silent bug. Three consequences follow directly. A void method's exception has nowhere to go and is handed to an AsyncUncaughtExceptionHandler, whose default logs it — so a failing fire-and-forget task is a log line and nothing else. A CompletableFuture propagates the exception to the caller when the future is joined. And the security context and the transaction context are both thread-bound, so neither reaches the new thread unless it is propagated deliberately.

package com.example.catalog.imports;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executor;
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class ImportService {

    private final BookRepository books;

    public ImportService(BookRepository books) { this.books = books; }

    // Returns a future so the caller can join, time out and see the failure.
    @Async("importExecutor")
    public CompletableFuture<ImportResult> importBatch(List<Row> rows) {
        int written = 0;
        for (Row r : rows) { books.save(toEntity(r)); written++; }
        return CompletableFuture.completedFuture(new ImportResult(written));
    }

    // Fire and forget: no transaction reaches this thread, so open one here.
    @Async
    @Transactional
    public void reindex(Long bookId) { books.touchIndexedAt(bookId, Instant.now()); }
}

Choosing and configuring the executor

Boot auto-configures a ThreadPoolTaskExecutor named applicationTaskExecutor and uses it for @Async, Spring MVC async requests and several framework features. Its defaults — a core size of 8, a queue of unbounded capacity, a 60-second keep-alive — are tuned for a servlet container at that size, and the unbounded queue is the important part: a saturated pool accepts work indefinitely, latency grows without bound, and nothing reports a problem until the heap fills. Configure the queue explicitly and pair it with a rejection policy, which is the only way the system tells you it is overloaded.

Propagating context, deliberately

Two pieces of context are thread-bound and both are needed by real work. Security: the SecurityContext is stored in a ThreadLocal, so an async method runs as an anonymous user unless the executor is wrapped. Boot does this for the auto-configured executor; for a custom one, wrap it in a DelegatingSecurityContextAsyncTaskExecutor. Request context: a request-scoped bean and MDC log fields are also thread-bound; RequestContextHolder.setRequestAttributes(attrs, true) or a TaskDecorator that copies the MDC map is the fix. A TaskDecorator is the cleanest hook because it runs in the submitting thread, where the context is still correct.

Transactions are the opposite case: they must not be propagated across threads, because a transaction is bound to a connection which is bound to a thread. An @Async method that needs a transaction declares its own; the caller's transaction is unrelated and may already be committed by the time the async work starts.

// Copy the logging context, and the security context, into pool threads.
@Bean("importExecutor")
ThreadPoolTaskExecutor importExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4);
    ex.setMaxPoolSize(8);
    ex.setQueueCapacity(200);
    ex.setThreadNamePrefix("import-");
    ex.setTaskDecorator(runnable -> {                     // runs in the submitting thread
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        return () -> {
            if (mdc != null) MDC.setContextMap(mdc);
            try { runnable.run(); } finally { MDC.clear(); }
        };
    });
    ex.initialize();
    return ex;
}

9.3 @Scheduled and timed work

@Scheduled is the simplest way to run work periodically and it has two defaults that surprise people: the scheduler has a single thread, and every instance of a scaled service runs the job.

The four scheduling forms

fixedRate fires every N milliseconds measured from the start of the previous execution, so a task longer than the interval overlaps or queues. fixedDelay measures from the end, which is what you normally want because it guarantees a gap. initialDelay defers the first run — useful when the application needs a warm cache or a migrated schema. cron uses Spring's six-field format (second, minute, hour, day-of-month, month, day-of-week) with macros such as @daily and @hourly, and supports zone so a business-hours job means business hours where the business is.

package com.example.catalog.jobs;

import java.time.Instant;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@Component
public class MaintenanceJobs {

    private final CacheEvictionService cache;
    private final SalesRollup rollup;

    public MaintenanceJobs(CacheEvictionService cache, SalesRollup rollup) {
        this.cache = cache; this.rollup = rollup;
    }

    @Scheduled(fixedDelayString = "PT15M", initialDelayString = "PT1M")   // ISO-8601 durations
    public void evictStaleCaches() { cache.evictExpired(); }

    @Scheduled(cron = "0 15 2 * * *", zone = "Europe/Berlin")            // 02:15 daily, local time
    public void nightlyRollup() { rollup.forDay(Instant.now().minusSeconds(86_400)); }

    @Scheduled(cron = "0 */5 * * * *")                                    // every five minutes
    public void heartbeat() { log.debug("maintenance heartbeat"); }
}

The single-thread default, and multiple instances

@EnableScheduling creates a ThreadPoolTaskScheduler whose pool size Boot takes from spring.task.scheduling.pool.size, defaulting to 1. With one thread, two jobs scheduled at the same instant run sequentially, and a job that takes longer than its interval delays every other job on the scheduler. The classic symptom is a job that "stopped running" at exactly the time another job got slow. Setting the pool size to at least the number of jobs is a one-line fix; the better fix is to give long jobs their own scheduler or to dispatch them to an async executor so the scheduler thread returns immediately.

The second default is not from the framework at all: every replica of your service runs every scheduled job. On a three-replica deployment, a nightly rollup runs three times, and any job that is not idempotent corrupts data or sends duplicate notifications. Two patterns solve it. Dispatch the job to a single leader chosen by a coordination mechanism — Kubernetes a CronJob, or a Job alongside the deployment — which is the cleanest because the application does not need to know about scale. Or take a distributed lock with ShedLock, which wraps the method so only one instance executes it and the others skip:

// ShedLock: cooperative locking so a scaled deployment runs the job once.
@Configuration
@EnableSchedulerLock(defaultLockAtMostFor = "PT10M")
class ShedLockConfig {
    @Bean
    LockProvider lockProvider(DataSource dataSource) {           // or Redis, Mongo, JDBC
        return new JdbcTemplateLockProvider(
                JdbcTemplateLockProvider.Configuration.builder()
                        .withJdbcTemplate(new JdbcTemplate(dataSource))
                        .usingDbTime()          // the database clock, not the pod clock
                        .build());
    }
}

@Component
class NightlyRollup {
    @Scheduled(cron = "0 15 2 * * *")
    @SchedulerLock(name = "nightlyRollup", lockAtLeastFor = "PT1M", lockAtMostFor = "PT30M")
    void run() { /* exactly one instance executes; the rest skip */ }
}
// Requires the shedlock-spring + shedlock-provider-* jars (not managed by the Boot BOM).

Making a job safe, observable and testable

A scheduled method is production code with no caller, which is why it is so often under-tested. Four practices make the difference. Make it idempotent — a re-run must be harmless, because retries, restarts and overlapping instances all cause re-runs. Give it a bounded scope — "yesterday" from a clock, not "everything since the last run", because the latter grows without limit after an outage. Make it observable — Micrometer instruments @Scheduled methods with spring.task.scheduling.* metrics by default, and a job that has not succeeded is the one alert worth having. And test it: because the job body is an ordinary method, a unit test calls it directly; the @Scheduled annotation only needs verifying when the schedule expression itself is the thing that could be wrong.

# application.yml - more than one scheduler thread, and shutdown that waits
spring:
  task:

      pool:
        size: 4                             # >= number of jobs that may overlap; default 1
      thread-name-prefix: sched-

#   executor.active, executor.completed, executor.queued, executor.pool.size,

Never put an unbounded query or an unbounded fetch behind a scheduled job. "Process every order not yet synced" after a two-day outage is a job that loads a million rows into memory and takes down the service it was meant to help. Bound the batch, page through it, and let the next tick continue — a job that is always behind but never fails is recoverable; one that runs out of heap is not.

9.4 Virtual threads and the concurrency model

Java 21's virtual threads make blocking cheap. Boot 3.2 added a single property that switches the servlet stack and the task executor onto them — and the interesting part is knowing when that helps, when it changes nothing and what it costs.

What a virtual thread is, and what it is not

A virtual thread is a Java object scheduled by the JDK onto a small pool of carrier threads, one per CPU. When a virtual thread blocks on I/O — a socket read, a JDBC call, a LockSupport.park — it is unmounted from its carrier and the carrier is free to run another virtual thread. A platform thread occupying an OS thread while blocked costs around a megabyte of stack and a kernel scheduling slot; a virtual thread costs a few hundred bytes of heap. The consequence is that the thread-per-request model, which had to become reactive to scale past a few thousand concurrent requests, becomes viable again at tens or hundreds of thousands — with plain blocking code that is far easier to read and debug than a chain of reactive operators.

It is not a faster thread. Throughput on CPU-bound work is unchanged, or slightly worse because of the extra indirection. It does not make a slow database faster and it does not increase a connection pool. And it does not remove the need for limits: an unbounded number of virtual threads all contending for a Hikari pool of ten connections is still a queue, just with many more waiting threads.

# application.yml - one switch, supported for servlet stacks and @Async
spring:
  threads:
    virtual:
      enabled: true

# What it changes:
#   - Tomcat's protocol handler uses a virtual-thread executor for requests
#   - the auto-configured applicationTaskExecutor becomes a SimpleAsyncTaskExecutor
#     over virtual threads (one thread per task, no pool to tune)
#   - @Async methods inherit that executor unless they name another
#
# What it does NOT change:
#   - HikariCP still has spring.datasource.hikari.maximum-pool-size connections
#   - @Scheduled still uses a platform-thread scheduler with spring.task.scheduling.pool.size
#   - Reactor/Netty is its own model; WebFlux has no need for virtual threads

Pinning, and the JDK version that fixes it

A virtual thread cannot be unmounted while it holds a monitor. Inside a synchronized block that blocks on I/O, the virtual thread pins its carrier thread, which means that carrier cannot serve any other virtual thread and the scalability win disappears for that call path. On Java 21 the workaround is to replace synchronized with ReentrantLock on the blocking paths; JEP 491, delivered in JDK 24, removes the limitation so synchronized no longer pins. A second pinning source is a native method or a foreign function call, which cannot be avoided and is reported in the JFR event jdk.VirtualThreadPinned — the only reliable way to find pinning is that event, so run with JFR on and look for it rather than guessing.

Deciding, and what to measure

Turn virtual threads on for a servlet application that is I/O-bound and whose concurrency is bounded by blocked threads rather than by a downstream limit. The measurable signal is that throughput rises while the hikari_connections_pending or hikari_connections_active metric stays flat, or that Tomcat's busy-thread count stops being the ceiling. If throughput is unchanged, the bottleneck is elsewhere — a database pool, a downstream rate limit, or a CPU-bound path — and virtual threads have removed a limit that was not the one binding. Keep them off in a WebFlux application and in a CPU-bound batch workload, and remember that a memory-limit increase is usually needed at very high concurrency: a million virtual threads is still a million objects to schedule, and a large number of concurrent in-flight requests means a large number of buffers.

Virtual threads do not change the rule that a blocking call inside a reactive pipeline is wrong. In a WebFlux application, a blocking JDBC call on the event loop stalls every other request on that thread; move it to subscribeOn(Schedulers.boundedElastic()) or use a non-blocking driver. Making the thread virtual does not fix a violation of the model it belongs to.

10 · Messaging and integration

Boot's messaging support is thin in the best sense: it configures the client, gives you a listener annotation and leaves the semantics to the broker. What it does not do is make delivery exactly-once, and the patterns that pretend otherwise — publishing inside a transaction, acknowledging before the work is done, assuming a message arrives once — are the source of the interesting production bugs. This chapter is about the delivery guarantees each piece actually provides.

10.1 Apache Kafka with Spring Kafka

Kafka is a partitioned, replicated log. Consumers read at their own pace, offsets are committed by the consumer group, and the delivery guarantee you get depends entirely on when the offset is committed relative to the work.

Producing, and the guarantees on the write path

KafkaTemplate sends a record asynchronously and returns a CompletableFuture<SendResult>. Three producer settings decide what a successful send means. acks=all waits for the in-sync replicas, so a message survives a broker failure; acks=1 only waits for the leader, so a leader crash loses recent writes. enable.idempotence=true (the default since Kafka 3.0) deduplicates retried batches inside the producer, so a network retry does not double-write — which matters because the producer retries by default. And max.in.flight.requests.per.connection above 1 with idempotence on preserves ordering per partition, which is the common misconfiguration: without idempotence, retries can reorder.

Boot configures these from spring.kafka.producer.* and spring.kafka.producer.properties.*, the second being a pass-through for anything the properties class does not name. Serialisation is Jackson by default for a POJO (spring.kafka.producer.value-serializer=org.springframework.kafka.support.serializer.JsonSerializer) and the type header it writes is what lets the consumer deserialise without knowing the class at compile time.

Consuming, and the acknowledgement decision

@KafkaListener registers a MessageListenerContainer per method. The ack-mode is the single most consequential setting: record commits the offset after the listener returns, which gives at-least-once delivery — a crash between the work and the commit replays the record. batch commits after a poll's worth of records, so a failure replays the entire batch. manual and manual_immediate leave it to you through the injected Acknowledgment, which is the only mode that can give "commit only after the database transaction committed". There is no exactly-once for a side effect outside Kafka: you can have exactly-once between Kafka topics (using transactional producer plus read_committed), but a database write plus a publish is always at-least-once, which is why consumers must be idempotent.

Partition assignment decides ordering and parallelism. Kafka guarantees order within a partition only, so the partition key is the ordering domain: key by order id and every event for an order is strictly ordered, while different orders proceed in parallel. concurrency sets the number of consumer threads and therefore the maximum parallelism per instance; more threads than partitions leaves threads idle. Consumers within a group rebalance when membership changes, and the cooperative-sticky assignor (the default since Kafka 3.0) avoids the stop-the-world rebalance of the eager protocol.

package com.example.catalog.messaging;

import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.messaging.handler.annotation.Payload;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class OrderListener {

    private static final Logger log = LoggerFactory.getLogger(OrderListener.class);
    private final OrderService orders;

    public OrderListener(OrderService orders) { this.orders = orders; }

    @KafkaListener(
            topics = "catalog.orders",
            groupId = "catalog-orders",
            concurrency = "3",
            properties = {"max.poll.records=100", "fetch.min.bytes=1"})
    @Transactional                                   // the work and the offset share the same intent
    public void onOrderPlaced(@Payload OrderPlaced event,
                              @Header(name = "kafka_receivedPartitionId") int partition,
                              @Header(name = "kafka_offset") long offset) {
        log.info("order {} from partition {} offset {}", event.orderId(), partition, offset);
        orders.apply(event);                          // must be idempotent - see 10.4
    }

    // Manual acknowledgement: commit only when the work has definitely succeeded.
    @KafkaListener(topics = "catalog.payments", groupId = "catalog-payments")
    public void onPayment(ConsumerRecord<String, PaymentSettled> record, Acknowledgment ack) {
        orders.settle(record.value());
        ack.acknowledge();                            // after the write, never before
    }
}

Producer transactions, and the one case they solve

spring.kafka.producer.transaction-id-prefix plus KafkaTransactionManager gives a Kafka transaction: a set of produced records is committed atomically, and a consumer with isolation.level=read_committed does not see them until then. KafkaTemplate.executeInTransaction and a consume-transform-produce listener (@KafkaListener with a transactional container) use this to make a Kafka-to-Kafka pipeline exactly-once, which is what a stream processor needs. It does not extend to a database: a Kafka transaction and a database transaction are two resources, and coordination between them needs either a distributed transaction (which no one should want) or the outbox pattern in section 10.4. The value of the setting in a service that also writes to a database is that the produced records are at least all-or-nothing, which is worth having even when the database boundary remains.

// Consume-transform-produce in one Kafka transaction: the offset commit and the
// produced records are atomic together.
@Bean
KafkaTransactionManager<String, String> kafkaTxManager(ProducerFactory<String, String> pf) {
    return new KafkaTransactionManager<>(pf);
}

@KafkaListener(topics = "catalog.orders.raw", groupId = "enricher")
public void enrich(ConsumerRecord<String, String> record) {
    // The container is transactional when it sees a KafkaTransactionManager bean,
    // so the offset for this record and the send below commit together.
    var enriched = enrich(record.value());

}

Set spring.kafka.consumer.value-deserializer=ErrorHandlingDeserializer with the real deserialiser as a delegate class. 10.2 RabbitMQ and AMQP with Spring AMQP

RabbitMQ is a broker with routing rules, not a log. Messages are pushed to consumers, they are removed on acknowledgement, and the exchange-and-binding model is what you configure. The consequence is that history is not replayable and that routing is a first-class feature.

Exchanges, queues and bindings

An exchange receives a message and routing key and decides which queues it goes to. A queue holds messages for consumers. A binding is the rule between them. The four exchange types are what make the model expressive: direct matches the routing key exactly, topic matches patterns with * (one word) and # (zero or more), fanout ignores the key and copies to every bound queue, and headers matches on message headers instead of the key. Queues, exchanges and bindings are server-side objects with their own lifecycle, and declaring them from the application is convenient and dangerous: a declaration that conflicts with an existing object — a different durable or autoDelete — fails with PRECONDITION_FAILED and closes the channel.

package com.example.catalog.messaging;

import org.springframework.amqp.core.Binding;
import org.springframework.amqp.core.BindingBuilder;
import org.springframework.amqp.core.DirectExchange;
import org.springframework.amqp.core.Queue;
import org.springframework.amqp.core.QueueBuilder;
import org.springframework.amqp.core.TopicExchange;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class RabbitTopology {

    static final String ORDERS = "catalog.orders";
    static final String DLX = "catalog.dlx";

    @Bean
    DirectExchange ordersExchange() { return new DirectExchange(ORDERS, true, false); }

    @Bean
    TopicExchange deadLetterExchange() { return new TopicExchange(DLX, true, false); }

    @Bean
    Queue ordersQueue() {
        return QueueBuilder.durable(ORDERS)
                .quorum()                                        // replicated, Raft-backed
                .deadLetterExchange(DLX)                         // where rejects and expiries go
                .deadLetterRoutingKey("orders.dead")
                .messageTtl(java.time.Duration.ofMinutes(30))
                .maxLength(100_000)
                .build();
    }

    @Bean
    Binding ordersBinding(Queue ordersQueue, DirectExchange ordersExchange) {
        return BindingBuilder.bind(ordersQueue).to(ordersExchange).with("orders.placed");
    }

    @Bean
    Queue ordersDeadQueue() { return QueueBuilder.durable("catalog.orders.dead").quorum().build(); }

    @Bean
    Binding deadBinding(Queue ordersDeadQueue, TopicExchange deadLetterExchange) {
        return BindingBuilder.bind(ordersDeadQueue).to(deadLetterExchange).with("orders.#");
    }
}

Listening, acknowledging and converting

@RabbitListener binds a method to one or more queues. Acknowledgement is automatic in the sense that the container acks after the listener returns, unless the method takes an AcknowledgeMode.MANUAL channel and acks itself. The default JSON converter writes a __TypeId__ header with the class name, so the consumer can bind to the right type — which is also a deserialisation-gadget surface, so the allowed packages must be restricted (spring.amqp.deserialization.trust.all=false plus a trusted-package list). A converter configured with a Jackson2JsonMessageConverter of your own, using a fixed target type, avoids the header entirely and is the safer configuration for a message contract you control.

Retries work differently from Kafka, because RabbitMQ has no offsets: on failure the message is requeued, republished or dropped according to the listener's retry configuration. spring.rabbitmq.listener.simple.retry.enabled=true with max-attempts and a backoff — or a stateless RetryTemplate with a RepublishMessageRecoverer — is the shape. Without an explicit retry policy, a listener that throws requeues the message immediately and indefinitely, which is a hot loop that saturates the broker; that is the single most common RabbitMQ misconfiguration.

@Component
class OrderQueueListener {

    private final OrderService orders;

    OrderQueueListener(OrderService orders) { this.orders = orders; }

    }
}

Publishing reliably

A publish to RabbitMQ is fire-and-forget unless publisher confirms are on: the client writes to a socket and assumes the broker queued it. publisher-confirm-type=correlated makes the broker acknowledge the publish, and publisher-returns with mandatory: true tells you when a message was routable to no queue. Handling both is what turns "we sent it" into "the broker has it". The alternative for a durable audit trail is a RabbitTemplate.invoke with a CorrelationData callback that logs the nack — a few lines that remove an entire class of silent message loss.

// Correlated publish: a nack or an unroutable message is a log line, not silence.
@Component
class ReliablePublisher {

    private final RabbitTemplate rabbit;

    ReliablePublisher(RabbitTemplate rabbit) { this.rabbit = rabbit; }

    void publish(String routingKey, OrderPlaced event) {
        var correlation = new CorrelationData(java.util.UUID.randomUUID().toString());
        rabbit.convertAndSend(RabbitTopology.ORDERS, routingKey, event, correlation);
        correlation.getFuture().whenComplete((confirm, ex) -> {
            if (ex != null || confirm == null || !confirm.isAck()) {
                log.error("publish nacked/failed id={} reason={}", correlation.getId(),
                        ex == null ? confirm.getReason() : ex.toString());
            }
        });
    }
}
A queue with no dead-letter configuration and default-requeue-rejected=true turns one bad message into an infinite redelivery loop. The consumer spins, the queue depth climbs, the broker's CPU saturates and healthy messages stop being processed. Configure a dead-letter exchange and default-requeue-rejected: false before the first production deploy, not after the first poison message.

10.3 @TransactionalEventListener and in-process events

Spring's ApplicationEventPublisher is a decoupling tool inside one JVM. Adding @TransactionalEventListener binds the listener to a transaction phase, which is how a service publishes a domain event and knows the notification only happens if the write committed.

The four transaction phases

@TransactionalEventListener extends @EventListener with a phase. The default is AFTER_COMMIT, which is the one people want: publish the event inside the transaction, and let the listener run only once the data is durable. BEFORE_COMMIT runs while the transaction is still open, so the listener can participate in it — the place for a pre-commit consistency check. AFTER_ROLLBACK runs when the transaction failed, useful for releasing a reservation or emitting a failure metric. AFTER_COMPLETION runs in both cases and is what a cleanup should use.

Two behaviours are easy to get wrong. Without a transaction, an AFTER_COMMIT listener is not invoked at all — the event is silently dropped, because the phase it waits for never occurs. That is the correct default and it surprises people testing a listener without @Transactional on the publisher; fallbackExecution = true opts out and runs the listener regardless. And the listener runs synchronously on the committing thread, after the commit: an exception thrown there cannot roll back the transaction, and it propagates to the caller of the transaction. Making the listener @Async moves it off the request thread, which changes the failure mode but not the guarantee.

package com.example.catalog.order;

public record OrderPlaced(String orderId, String customerId, java.math.BigDecimal total) { }

@Service
public class OrderService {

    private final OrderRepository orders;
    private final ApplicationEventPublisher events;

    public OrderService(OrderRepository orders, ApplicationEventPublisher events) {
        this.orders = orders; this.events = events;
    }

    @Transactional
    public Order place(Cart cart) {
        Order order = orders.save(Order.from(cart));
        events.publishEvent(new OrderPlaced(order.id(), order.customerId(), order.total()));
        return order;                                // the listener fires after this commits
    }
}

@Component
class OrderNotifications {

    // Runs only after the transaction that published the event commits.
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void onCommitted(OrderPlaced event) {
        email.send(confirmationFor(event));          // a failure here cannot roll back the order
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
    void onFailed(OrderPlaced event) { metrics.counter("order.rolledback").increment(); }

    // AFTER_COMMIT + @Async: keep the request thread fast; accept at-most-once delivery.
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void auditAsync(OrderPlaced event) { audit.record(event); }
}

Where the in-JVM event boundary stops

An application event is not a message. It has no retry, no delivery guarantee, no durability and no ordering across instances: a crash after the commit and before the listener runs loses the event entirely, and with several replicas the listener runs on whichever instance committed. This is fine for a side effect you can tolerate losing — a cache invalidation, a metric, a best-effort notification whose absence is recoverable. It is not fine for anything that must happen, and the temptation to treat it as a cheap message queue is the trap.

The ordered relationship is worth stating plainly. AFTER_COMMIT is better than publishing before the commit (a rollback then leaves a notification for an order that does not exist) and worse than an outbox (a crash in the gap loses the notice). It is the right tool when the work is idempotent, cheap and non-critical, and the wrong tool when a lost event is a lost business fact.

// The mistake: publish before the write is durable.
@Transactional
public Order place(Cart cart) {
    events.publishEvent(new OrderPlaced("uncommitted", cart.customerId(), cart.total()));
    Order saved = orders.save(Order.from(cart));       // a rollback here sends a false confirmation
    return saved;
}

// The other mistake: an AFTER_COMMIT listener that assumes the transaction is still open.
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
void writeAudit(OrderPlaced event) {
    // There is NO transaction here. This save runs in its own, or with autocommit.
    // Wrap it in its own @Transactional boundary on a different bean if it must be atomic.
    audit.save(new AuditEntry(event.orderId()));
}
Use records for events. They are immutable, they compare by value, they serialise with Jackson without configuration, and — unlike a mutable event class — they cannot be modified by one listener in a way that changes what another listener sees. Name them in the past tense (OrderPlaced, not PlaceOrder): an event is a statement of fact, a command is an instruction, and mixing the two produces listeners with side effects that a future author cannot reason about.

10.4 Integration patterns: outbox, idempotency, retries

Four patterns carry most of the weight in a service that both stores data and publishes messages. Each exists because of one specific failure window, and knowing which window each closes is what makes the choice mechanical.

The dual-write problem and the transactional outbox

A service that writes to a database and then publishes to a broker has two resources and no way to make one commit with the other. If the publish succeeds and the commit fails, consumers act on an order that does not exist. If the commit succeeds and the publish fails, the order exists and nobody knows. The transactional outbox closes the window by removing the second resource from the critical path: the event is written to an outbox table in the same transaction as the business data, and a separate publisher reads the table and sends the messages, marking each as sent. Because both writes are in one database transaction, they succeed or fail together, and the publish becomes a retry problem rather than an atomicity problem.

-- The outbox row is written by the same transaction as the order.
create table outbox (
    id            bigserial primary key,
    aggregate_id  text        not null,
    event_type    text        not null,
    payload       jsonb       not null,
    created_at    timestamptz not null default now(),
    published_at  timestamptz
);
create index ix_outbox_unpublished on outbox (id) where published_at is null;

@Service
public class OrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;

    public OrderService(OrderRepository orders, OutboxRepository outbox) {
        this.orders = orders; this.outbox = outbox;
    }

    @Transactional                                     // one transaction, both writes
    public Order place(Cart cart) {
        Order order = orders.save(Order.from(cart));
        outbox.save(OutboxEntry.of("order", order.id(), "OrderPlaced", toJson(order)));
        return order;
    }
}

// The publisher: poll, send, mark sent. At-least-once - hence 10.4's idempotency.
@Component
class OutboxPublisher {

    @Scheduled(fixedDelayString = "PT1S")
    @Transactional

        for (OutboxEntry entry : outbox.findUnpublished(200)) {

Idempotent consumers, because delivery is at-least-once

Every guarantee on this page is at-least-once: the outbox publisher may send twice after a crash between the send and the mark, Kafka may redeliver after a rebalance, RabbitMQ may redeliver after a lost ack. The consumer therefore must handle seeing the same message twice, and the only reliable way is a durable record of what has already been processed. Two shapes work: a unique constraint on a business key so the second attempt fails harmlessly, or a processed-events table keyed by the message id, checked and inserted in the same transaction as the work.

@Service
public class OrderProjection {

    private final JdbcClient jdbc;

    public OrderProjection(JdbcClient jdbc) { this.jdbc = jdbc; }

    @Transactional
    public void apply(OrderPlaced event, String messageId) {
        int inserted = jdbc.sql("""
                insert into processed_event(message_id, processed_at)
                values (:id, now())
                on conflict (message_id) do nothing
                """)
                .param("id", messageId)
                .update();

        if (inserted == 0) return;                     // already handled - stop here
        jdbc.sql("insert into order_view(order_id, total) values (:id, :total) " +
                 "on conflict (order_id) do update set total = excluded.total")
            .param("id", event.orderId())
            .param("total", event.total())
            .update();
    }
}
// Both statements are in one transaction, so a crash between them rolls both back.

Retries, dead letters and poison messages

A retry policy is a statement about how long a transient failure is worth waiting for, and it must be bounded. Three properties are non-negotiable: exponential backoff with a cap, so a downstream recovering from an outage is not hammered; a maximum attempt count, so a permanent failure reaches a dead letter instead of looping; and a dead-letter destination that someone monitors, because a DLQ nobody reads is a silent data loss. Non-blocking retries — Kafka retry topics via @RetryableTopic, or a Rabbit delayed-exchange — keep the main partition moving instead of blocking it for the length of the backoff, which is the difference between a healthy consumer and a stalled one.

Then make the DLQ actionable. A message in it needs enough context to be understood without the originating database: the payload, the exception type and message, the attempt count, and the time of the last attempt. A replay tool that re-publishes DLQ messages to the original topic after a fix is what closes the loop, and it is worth building before the first incident rather than during it.

// Kafka: blocking retries with backoff, then a dead-letter topic.
@Bean
DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<String, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template,
            (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
    var backOff = new ExponentialBackOffWithMaxRetries(4);     // 1s, 2s, 4s, 8s
    backOff.setInitialInterval(1000L);
    backOff.setMultiplier(2.0);
    var handler = new DefaultErrorHandler(recoverer, backOff);
    handler.addNotRetryableExceptions(IllegalArgumentException.class);   // permanent: go straight to DLT
    return handler;
}

// Kafka 3.2+: non-blocking retries on retry topics, so the main partition keeps moving.

        dltTopicSuffix = ".DLT")
@KafkaListener(topics = "catalog.orders", groupId = "catalog-orders")

11 · Packaging and deployment

A Spring Boot application is a jar with an embedded server, and every deployment target is a variant on running that jar. The choices that matter are not which platform you use but three things: what the artifact contains, how the JVM is configured inside it, and how configuration reaches it. Get those right and moving between a virtual machine, a container and a native image is a build change rather than a rewrite.

11.1 The executable jar and layered extraction

The Boot plugin adds a launcher and a nested-dependency layout to an ordinary jar. Understanding the layout explains why an executable jar behaves differently from a library jar and how to get layer caching for free.

What repackage produces

A plain mvn package produces a jar containing your classes. With the Boot plugin bound to the package phase, repackage takes that jar and rewrites it: your classes move to BOOT-INF/classes/, every dependency jar is embedded verbatim under BOOT-INF/lib/, and a launcher class becomes the Main-Class. Since Boot 3.2 the launcher lives in org.springframework.boot.loader.launch — JarLauncher for a jar, WarLauncher for a war, PropertiesLauncher when you need loader.path. The Start-Class manifest attribute records your main class and is what the launcher invokes.

The nested-jar format is why java -cp app.jar does not work and why java -jar app.jar does: the launcher installs a custom class loader that can read the nested jars without extracting them, and it treats the archive as a directory whose parts are individually addressable. That structure is also what makes it possible to add a dependency at runtime with an external manifest (loader.path) — and it is why a build that transitively pulls a jar with a signed manifest occasionally fails to load it.

Layered extraction, and why it matters for a rebuild

By default the whole application is one layer in a Docker image, so changing a single class invalidates the layer that contains every dependency and the image is rebuilt from scratch — a 200 MB push for a one-line change. The Boot plugin writes a layers.idx file that partitions the jar into ordered layers: dependencies (released dependency jars), spring-boot-loader, snapshot-dependencies, and application (your classes and resources). Extract the layers in that order in the image and the expensive ones are cached across builds, because a changed application class only invalidates the last layer.

A war, and when it is still the right artifact

Setting <packaging>war</packaging> and marking the embedded Tomcat as provided produces a war deployable into a shared servlet container. The entry point changes shape: the application class extends SpringBootServletInitializer and overrides configure(SpringApplicationBuilder), which is how the container invokes your application through the servlet 3.0 SpringBootServletInitializer hook. Choose this only when operations genuinely require a shared container — for a single-application server, an external container is a second thing to version, patch and configure, and it removes Boot's embedded-server defaults from the deployment.

A jar that starts with no JVM flags is a reasonable local convenience and a poor production default; the flags belong in the deployment manifest, not in code.

11.2 Container images: buildpacks and Dockerfiles

Boot can build an OCI image with no Dockerfile at all, and it can supply the layer information that makes a hand-written Dockerfile cache properly. Both paths produce the same runtime; the differences are who chooses the base image and who is responsible for patching it.

Buildpacks: an image from the jar

mvn spring-boot:build-image (or gradlew bootBuildImage) hands the jar to a Cloud Native Buildpack builder, which detects the JVM, installs a JDK and a JRE, builds the layer cache, and produces an image with a non-root user, a configured entrypoint, memory-aware JVM defaults and an SBOM. The default builder is a Paketo Jammy builder and can be overridden with <builder> in the plugin configuration or --builder; the runtime base image can be swapped for a smaller one or a distroless-style base. Because the builder applies memory calculator defaults, the image runs correctly under a container memory limit without any -Xmx tuning — which is the single largest operational win of this path.

The trade-off is control. The base image is chosen by the builder, so patching a CVE means waiting for a new builder or overriding stages. For a regulated environment where the base image is approved centrally, a hand-written Dockerfile using that approved image is the requirement. Boot makes that path cheap with the layer split.

The JVM settings that matter inside a container

Since JDK 10 the JVM is container-aware: UseContainerSupport is on by default and MaxRAMPercentage reads the cgroup limit rather than the host's memory. Four settings are worth being explicit about anyway. -XX:MaxRAMPercentage=75 — the default is 25% of the limit, which wastes three quarters of a generously sized container and is the most common sizing mistake. -XX:+ExitOnOutOfMemoryError — an OOM'd JVM is in an undefined state; exiting lets the orchestrator restart it, rather than surviving in a broken state. CPU awareness — the JVM sizes the JIT compiler threads and the garbage collector from availableProcessors, and a container limited to 0.5 CPU still reports the host's count on older JDKs; on JDK 21 it reads the cgroup quota, but -XX:ActiveProcessorCount=2 remains a useful explicit cap for a latency-sensitive service sharing a node. Heap dumps on OOM — -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dumps to a mounted volume, because a heap dump written to a container's ephemeral filesystem is lost when the container is replaced.

Never build the image with the JDK as the runtime stage. A JDK image is several hundred megabytes larger, and it ships javac, jcmd, jmap, jshell and the src.zip into production — a much larger attack surface and, in a scanned environment, a set of findings you will spend time explaining. Use a fixed JRE base and pin it by digest: eclipse-temurin:21-jre-jammy@sha256:….

11.3 Native images with GraalVM

A native image is a single executable compiled ahead of time: no JVM, no bytecode, no JIT. Startup drops from seconds to tens of milliseconds and memory from hundreds of megabytes to tens — at the cost of a build that takes minutes and a set of constraints that change how you write code.

The build, and what AOT processing does

The Boot plugin has an AOT phase that runs the application's auto-configuration at build time and generates Java source for the bean definitions it would have created reflectively. That generated code replaces the runtime reflection and the CGLIB subclassing of @Configuration classes, which is the difference between a native image that works and one that fails on the first injected bean. The native Maven profile generated by Spring Initializr wires this up: org.graalvm.buildtools:native-maven-plugin plus the AOT phase, driven by mvn -Pnative native:compile. The result is target/catalog — an executable, not a jar.

# shell - build a native executable with the Initializr-generated profile
mvn -Pnative native:compile
./target/catalog              # starts in tens of milliseconds

# The same profile also builds a native image in a container, so no local GraalVM is needed:
mvn -Pnative spring-boot:build-image -Dspring-boot.build-image.imageName=catalog:native
docker run --rm -p 8080:8080 catalog:native

# Inspect the AOT output when something is missing:
mvn -Pnative spring-boot:process-aot
ls target/spring-aot/main/sources        # generated bean definitions
ls target/spring-aot/main/resources      # generated metadata: reflect-config, resource-config

What does not work the way it did

A native image is a closed world. No class can be loaded that was not known at build time, so anything reflective needs a hint, anything needing a proxy needs a proxy registration, and a resource loaded by name must be declared. Boot's AOT engine generates hints for the framework's own usage, and the GraalVM reachability-metadata repository supplies hints for common libraries; your own code must supply the rest. The RuntimeHintsRegistrar interface is the supported place to declare them, and it can be registered with @ImportRuntimeHints or a META-INF/spring/aot.factories entry. For the common case — a DTO you serialise with Jackson — @RegisterReflectionForBinding is a one-annotation answer.

Six other differences are worth knowing before committing to native. Build time is minutes, and it is a full link each time, so the inner loop is a jar run and native is a release-time build. Peak throughput is lower than a warm JIT for long-running CPU-heavy work — native has no JIT, and its AOT-compiled code is not profile-guided; for a request/response service the difference is usually small, for a batch computation it is not. No lazy class loading means the whole class graph must be present at build time; a class only reachable through a configuration string is invisible. Profiles and conditions that depend on runtime property values are a hazard: AOT evaluates conditions during the build, so a property the auto-configuration branches on must be resolvable then — keep profile-specific auto-configuration out of the native path and use plain runtime properties instead. Dynamic agent attachment, JMX and the attach API are unavailable, which removes a class of tooling. And the jcmd/jmap toolkit is gone; diagnostics become JFR and metrics, which is why chapters 8 and 12 matter more, not less, on native.

11.4 Deploying to a platform: configuration and rollout

The artifact is built once and promoted; everything that differs per environment arrives as configuration. This section is the deployment contract: what the platform must set, and what the application must do so that a rollout does not drop requests.

The contract between the application and the platform

Six things every deployment must supply or satisfy. The active profile, explicitly — never rely on the default profile in production. The datasource and broker endpoints as environment variables or mounted files, with credentials from a secret store. The management port reachable by the orchestrator's probe but not by the public internet. Enough memory for the heap at 75% of the limit, and a limit set at all — a container with no limit is the first thing to be evicted. A shutdown grace period longer than the application's drain timeout, or the platform sends SIGKILL mid-drain. And observability wiring — where metrics are scraped from and where traces and logs go.

Why CPU requests matter to a Java service

CPU requests are not just a scheduling hint for a JVM: the JVM reads the cgroup CPU quota and sizes the garbage collector's parallel threads, the JIT compiler threads and the fork-join pool from it. A pod with a 1-CPU limit gets a differently tuned JVM from one with 4, and a service with no CPU request may be scheduled on a busy node and see latency it cannot explain. The practical guidance is to set a request equal to the steady-state usage, allow a burst above it with a limit, and avoid a very small CPU limit on a service that is latency-sensitive — a 200m limit means the JVM believes it has a fifth of a core and it will serialise work accordingly.

Autoscaling follows from the same reasoning. CPU-based horizontal autoscaling works when CPU is the binding constraint; for an I/O-bound service it does not, because the pods are idle-waiting at 10% CPU while latency climbs. The metric to scale on is the one that actually saturates: request queue length (a Tomcat or Hikari pending-connections metric), Kafka consumer lag, or a saturation metric from the gateway. Actuator's Prometheus endpoint plus a custom-metrics adapter is the standard route to scaling on those.

# Horizontal autoscaling on a metric that actually saturates, not on CPU.
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: catalog }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: catalog }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Pods
      pods:
        metric: { name: hikaricp_connections_pending }     # exported by Micrometer
        target: { type: AverageValue, averageValue: "2" }
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 0 }           # react immediately to load
    scaleDown: { stabilizationWindowSeconds: 300 }         # slow down - avoid flapping

Rollout, rollback and feature control

A rolling update with maxUnavailable: 0 plus a readiness probe and graceful shutdown is a zero-downtime deploy, provided the drain window exceeds the load balancer's polling interval — the sequence is: the new pod becomes ready, the old pod's readiness flips during context close, the balancer removes it within a polling period, and the drain waits. Set terminationGracePeriodSeconds above the drain timeout or the platform kills the process mid-drain. Rollback is a redeploy of the previous image tag, which is why the image tag must be immutable and why a schema migration must be backwards compatible for at least one release: the expand/contract pattern from chapter 5 is what makes an immediate rollback possible.

Feature release is a separate axis from deployment. @ConditionalOnProperty plus an environment variable is the cheapest flag and requires a restart; a config server with a refresh (@RefreshScope) or a dedicated feature-flag service allows a change without one. The rule worth holding: never let a flag be the only thing standing between a broken code path and production for longer than the next release. A flag that has been on for three months is a permanent branch that nobody has tested.

# Production configuration that is genuinely per-environment: a mounted file,
# so structured values do not have to be encoded into environment variables.

Do not build a different artifact per environment. The moment application-prod.yml is baked into a prod-only jar, "it worked in staging" stops being evidence and a rollback means a rebuild under pressure. Build once, promote the same digest, and let the environment supply values — that is the whole of the twelve-factor configuration rule, and it is the one most often broken by accident.

12 · Spring Cloud and microservices

Spring Cloud is a set of integrations with the infrastructure a distributed system needs: configuration, service discovery, routing, resilience and tracing. Boot already solved the single-process problem; Spring Cloud solves the many-process one, and it does so by integrating rather than by inventing. Every component here also has a non-Spring answer — Kubernetes has configuration, DNS and probes, an ingress has routing, a service mesh has retries — so the first decision is not which library to use but which problems the platform already solves.

12.1 Centralised configuration with Config Server

A config server turns configuration into a service: one place to change a value for many applications, with the environment and the profile as parameters rather than as files baked into an artifact.

What the server is, and how a client reads it

@EnableConfigServer on a Boot application with spring-cloud-config-server exposes a REST API over a backend — a Git repository, a filesystem, Vault, or JDBC. A client requests configuration for its own {application} name, the active {profile}, and a {label} (a Git branch or tag), and the server returns a property source assembled from files named for those coordinates: catalog.yml, catalog-prod.yml, application.yml, in that precedence. The Git backend is the default and the strongest choice, because configuration gains history, review and rollback for free.

The client side changed shape in Boot 2.4 and the current form is an import rather than a bootstrap context: spring.config.import=configserver: with spring.cloud.config.uri. Making the import non-optional means the application refuses to start when the server is unreachable, which is almost always the behaviour you want — a service that starts with default configuration because the config server was down is worse than one that does not start. spring.cloud.config.fail-fast=true with the spring-retry dependency adds bounded retries during startup, which covers a config server that is still rolling when its clients are.

// Config server: the whole application.
@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
    public static void main(String[] args) { SpringApplication.run(ConfigServerApplication.class, args); }
}

Refresh, and the honest assessment of it

@RefreshScope on a bean makes it re-instantiate when a refresh happens, so a property change can take effect without a restart. The trigger is POST /actuator/refresh on the instance (which requires spring-cloud-context and the actuator), and Spring Cloud Bus broadcasts the refresh across instances through a message broker so one call reconfigures a fleet. Two caveats decide whether this is worth using. The scope re-creates the bean, so anything holding a reference to the old instance — a singleton that injected it, a cached object graph — still holds the old one; and a refresh that changes a property the bean used at construction time can leave the application in a state nobody has tested. The pragmatic position for most teams is: use the config server for delivery, and restart for changes. It is slower, and it is the only path that has been exercised by the test suite.

# Broadcast a refresh to every instance via Spring Cloud Bus (Kafka or Rabbit binding).
curl -X POST http://config-server:8888/actuator/busrefresh
# Or on a single instance:
curl -X POST http://catalog:9090/actuator/refresh

// Only beans that are annotated re-create their state:
@RefreshScope
@Component
class PricingPolicy {
    @Value("${app.pricing.surge-threshold}") private BigDecimal surgeThreshold;
    // On refresh this bean is destroyed and re-created; the new value is bound.
}
A config server is not a secrets manager. It can serve a value, and it can encrypt values with a keystore — an approach that has been superseded in practice by a dedicated secrets store, because the encryption key ends up on every client anyway. Serve non-sensitive configuration from the config server and credentials from Vault, a cloud secret manager or a mounted secret, keeping the two lifecycles separate.

12.2 Service discovery and client-side load balancing

Discovery answers "where is the instance of X right now". A registry holds the answer, a client cache holds a recent copy of it, and the failure modes are all about how stale that copy gets.

Eureka, Consul and the platform

Eureka is the classic Netflix registry and the one most Spring Cloud material describes: a server (@EnableEurekaServer) plus clients that register on startup and send a heartbeat every 30 seconds. Its defaults are deliberately forgiving — a client caches the registry for 30 seconds and the server evicts a silent instance only after about 90 seconds, so a dead instance can receive traffic for up to two minutes. That is a design choice for availability over consistency, and it is the reason Eureka pairs badly with a platform that already knows which pods are alive. Consul is a general service mesh and key-value store with richer health checking, a different operational profile, and its own consistency model.

The decision that matters in 2026 is not Eureka versus Consul but whether you need either. On Kubernetes, a Service is a stable DNS name with the platform's own readiness-gated endpoints, and DNS resolves to the live pods. Spring Cloud Kubernetes provides a DiscoveryClient over the Kubernetes API for the cases where load balancing must be aware of pod metadata, and the k8s profile activates sensible defaults. Adding Eureka to a Kubernetes deployment means running a second registry that disagrees with the first about which pods are healthy.

Client-side load balancing with Spring Cloud LoadBalancer

Spring Cloud LoadBalancer replaced Netflix Ribbon. Its integration point is a @LoadBalanced RestClient.Builder, WebClient.Builder or RestTemplate: the client resolves the service name through the DiscoveryClient, picks an instance with the configured strategy (round-robin by default), and rewrites the URL. Because the resolution happens per call rather than at construction, a pod that disappears is removed on the next refresh of the registry cache — which is the whole benefit and the whole risk, since the staleness window is the registry's, not the client's.

Two properties deserve attention. spring.cloud.loadbalancer.cache.ttl controls how long an instance list is cached locally; shortening it reacts faster to change and increases registry traffic. And the retry integration (spring.cloud.loadbalancer.retry.enabled) retries a failed request on a different instance only when the request is idempotent and the failure was a connection failure rather than a response — retrying a POST on a timeout can duplicate a write, which is the exact behaviour that makes unguarded client-side retries dangerous.

// A load-balanced client: the service name is resolved per call, not at startup.
@Configuration
class CatalogGatewayClient {

    @Bean
    @LoadBalanced
    RestClient.Builder loadBalancedRestClient() { return RestClient.builder(); }

    @Bean
    CatalogApi catalogApi(@LoadBalanced RestClient.Builder builder) {
        var proxy = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(builder.baseUrl("http://catalog-service").build()))
                .build();
        return proxy.createClient(CatalogApi.class);      // declarative HTTP, no Feign needed
    }
}

    @GetExchange("/api/books/{isbn}")

12.3 The API gateway

A gateway is a reverse proxy with a routing model and a filter chain. It centralises cross-cutting concerns — authentication, rate limiting, request shaping — and it is the one component whose outage takes everything with it.

Routes, predicates and filters

Spring Cloud Gateway is built on the reactive stack and its configuration is declarative: a route has an id, a target uri, one or more predicates that decide whether the route matches, and a list of filters that transform the request or the response. A lb:// URI means the target is resolved through the discovery client and load-balanced. Because it runs on Netty with a small event loop, the gateway holds thousands of concurrent proxied connections on a handful of threads — which is the reason it is reactive rather than servlet-based. A servlet-flavoured gateway also exists for teams that want the MVC programming model; the declarative route model is the same.

# Gateway routes: predicates decide the match, filters transform the exchange.
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: catalog
              uri: lb://catalog-service            # resolved + load-balanced
              predicates:
                - Path=/api/books/**
                - Method=GET,POST,PUT,DELETE
              filters:
                - StripPrefix=1                     # /api/books -> /books upstream
                - AddRequestHeader=X-Gateway, spring-cloud-gateway
                - name: Retry
                  args: { retries: 2, methods: GET, series: SERVER_ERROR }
                - name: CircuitBreaker
                  args:
                    name: catalogCb

Where the gateway belongs in the security model

A gateway is the natural place to terminate authentication once and forward identity, which turns every service behind it from "must know how to validate a token" into "trusts a header". Two ways to do it, and the choice matters. Edge token validation: the gateway validates the JWT and forwards the original Authorization header so each service validates it again — defence in depth, at the cost of one verification per hop. Trusted identity headers: the gateway validates once and injects X-User-Id and X-Roles, and services trust them — cheaper, and only safe when the network makes it impossible to reach a service except through the gateway. That is a platform property, not a code property, and a service that is accidentally exposed then accepts forged identity.

Rate limiting is the other cross-cutting concern worth centralising. The RequestRateLimiter filter with a Redis-backed RedisRateLimiter gives per-key limits, where the key resolver decides what to count — a user, an API key, an IP. Because the counter lives in Redis, the limit is enforced across gateway instances rather than per instance, which is the difference between a real limit and one that scales with your replica count.

// Split the incoming token into headers the services can trust, at the edge.
@Configuration
class GatewaySecurity {

    @Bean
    SecurityWebFilterChain gateway(HttpSecurity http) throws Exception {
        return http
            .csrf(ServerHttpSecurity.CsrfSpec::disable)
            .authorizeExchange(a -> a
                .pathMatchers("/actuator/health/**").permitAll()
                .pathMatchers("/api/public/**").permitAll()
                .anyExchange().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))   // validate once, at the edge
            .build();
    }

    @Bean
    GlobalFilter identityHeaders() {
        return (exchange, chain) -> exchange.getPrincipal()
            .cast(Authentication.class)
            .flatMap(auth -> {
                var mut = exchange.getRequest().mutate()
                        .header("X-User-Id", auth.getName())
                        .header("X-Roles", auth.getAuthorities().stream()
                                .map(GrantedAuthority::getAuthority)
                                .collect(Collectors.joining(",")));
                return chain.filter(exchange.mutate().request(mut.build()).build());
            })
            .switchIfEmpty(chain.filter(exchange));
    }

    @Bean
    KeyResolver userKeyResolver() {                  // what the rate limiter counts
        return exchange -> exchange.getPrincipal().cast(Authentication.class)
                .map(Authentication::getName).defaultIfEmpty("anonymous");
    }
}
Strip identity headers a client could have set, at the edge, before adding your own. A gateway that injects X-User-Id without removing an inbound one lets any client choose its own identity — a complete authentication bypass, and one that is invisible unless you look for the header in the incoming request. Configure the trusted-header filter to remove first, then set.

12.4 Resilience and tracing across services

Distributed failure is different in kind from local failure: a dependency can be slow rather than absent, and a slow dependency is more damaging than a missing one because it consumes resources while producing nothing. Resilience4j is the toolset for bounding that damage.

The four decorators, and what each bounds

Circuit breaker — watches calls and stops sending them when the failure or slow-call rate exceeds a threshold, failing fast while the dependency recovers. It converts an overloaded dependency into an immediate error, which is what lets the dependency recover. Retry — re-attempts, with backoff and jitter; it is only safe for idempotent operations and only when the failure is transient. Bulkhead — caps the concurrency of a call so a slow dependency cannot consume every thread in the pool; a semaphore bulkhead bounds concurrent calls, a thread-pool bulkhead isolates them. Rate limiter and time limiter — bound the call rate, and cap the duration (the time limiter needs a CompletableFuture, which is why it pairs with an async client). The decorator order is fixed and documented as Retry outside CircuitBreaker outside RateLimiter outside TimeLimiter outside Bulkhead — with the semantics that the retry sees the whole chain, so a circuit-breaker rejection is retried unless you exclude it.

# application.yml - circuit breakers and bulkheads, with reasoning behind the numbers
resilience4j:
  circuitbreaker:
    configs:
      default:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 50                 # evaluate over the last 50 calls
        minimumNumberOfCalls: 20              # do not trip on a cold service
        failureRateThreshold: 50              # % failures that opens the circuit
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 60
        waitDurationInOpenState: 30s          # how long before a trial call
        permittedNumberOfCallsInHalfOpenState: 5
        automaticTransitionFromOpenToHalfOpenEnabled: true

// A fallback is not a catch-all; it is a defined degraded behaviour.
@Service
class PricingClient {

    private final CatalogApi api;

    PricingClient(CatalogApi api) { this.api = api; }

    @CircuitBreaker(name = "pricing", fallbackMethod = "cachedOrEmpty")
    @Retry(name = "pricing")
    @Bulkhead(name = "pricing")
    Quote quote(String symbol) { return api.quote(symbol); }

    // The fallback must have the SAME signature plus the throwable, and must not
    // call the guarded method - that is an infinite loop the circuit will not stop.
    private Quote cachedOrEmpty(String symbol, Throwable t) {
        log.warn("pricing unavailable for {}: {}", symbol, t.toString());
        metrics.counter("pricing.fallback").increment();
        return lastKnown.getOrDefault(symbol, Quote.stale(symbol));
    }
}

Timeouts, and the discipline that prevents most incidents

A circuit breaker without a timeout measures the wrong thing: a call that hangs for sixty seconds is a failure, but the breaker only sees the failure when it finally returns. The first setting to get right is therefore a connect timeout and a read timeout on every client, set below the caller's own deadline. The second is to make the deadlines a chain rather than a set of independent numbers: if the gateway allows 5 seconds, the service must allow less than 5, and the service's downstream call less than that, or the outer timeout fires and the inner work continues uselessly. Resilience4j's time limiter enforces the local cap; the connect and read timeouts on RestClient, WebClient and the JDBC driver enforce the transport one, and both are needed because a TCP connection can be established and then never respond.

// Timeouts at the transport layer, below the circuit breaker's slow-call threshold.
@Bean
RestClient catalogClient(RestClient.Builder builder, LoadBalancerClientFactory lbf) {
    var factory = new JdkClientHttpRequestFactory(
            HttpClient.newBuilder()
                      .connectTimeout(Duration.ofMillis(500))       // connect: fail fast
                      .build());
    factory.setReadTimeout(Duration.ofSeconds(2));                  // read: bounded response
    return builder.requestFactory(factory).build();
}
// The chain:  gateway 5s  >  this service 2s+overhead  >  downstream 1s
// Each level is shorter than the one above it, so the inner work is always
// cancelled before the outer deadline expires.

Tracing, propagation and the shape of the whole system

Micrometer Tracing propagates the trace context across service boundaries automatically for instrumented clients, so a request through the gateway produces one trace with a span per service. Two additions make it useful in a distributed system. Baggage carries business context — a tenant, a cohort, a request-source — and is propagated explicitly with BaggageInScope; it must be treated as public data at every hop, because it travels in headers a client can see. Sampling has to be consistent across services: a child service inheriting a sampled context keeps it, but a child that starts its own trace samples independently, so a 10% sample at each hop means a complete trace is rare. Sampled-at-the-edge or tail-based sampling in the collector is what makes traces complete.

The last thing worth saying about this chapter is a caution. Every component here — a config server, a registry, a gateway, a circuit breaker — is operational complexity that must be run, upgraded and understood. The pattern that produces the worst systems is a distributed monolith: services that must be deployed together, share a database, and call each other synchronously in a chain. The tests for genuinely independent services are simple: can each be deployed alone, does it own its data, and does a dependency being down degrade one feature rather than the whole product. If the answer to any is no, a modular monolith will outperform the distribution on every axis that matters — latency, debuggability and the operational load on the team.

13.2 Common pitfalls, by symptom

Every entry here is a real failure that recurs across codebases, described by the symptom you will actually observe rather than by the rule you should have followed.

Startup failures

"No qualifying bean of type X" — the bean is outside the component-scan root, its class is in the default package, or it exists only as an interface without a repository or implementation behind it. Check the package of the application class first, then the package of the bean. "A component required a bean of type that could not be found" with an auto-configuration name is the same problem one layer out: a starter is missing its dependency. "BeanDefinitionOverrideException" — two definitions with the same name; do not enable overriding, rename one. "Circular reference" — two constructors each needing the other; the fix is a design change, and @Lazy is a workaround that hides it. "Failed to bind properties under 'app.x'" — a key is misspelled or a value cannot be converted; the message names it, and ignoreUnknownFields = false makes typos fail rather than silently defaulting.

Runs locally, fails in production

Four causes cover most of these. A profile-specific file replaced a list instead of merging it — lists are replaced wholesale, so declare the full list per profile. A property was read from an environment variable whose name did not match the relaxed-binding rule — APP_PRICING_BASEURL, not APP.PRICING.BASE_URL; check /actuator/env for the winner. A migration was forgotten — ddl-auto=validate turns that into a startup failure instead of a runtime error on the first query. The JVM never saw the container's memory limit — heap sized from the host rather than the cgroup, so the process is killed with no OOM log; check with -XX:+PrintFlagsFinal.

Annotations that appear to do nothing

All four of these are the same root cause — a call that never crossed a proxy — and they are worth recognising as one class.

// BROKEN: the annotation is bypassed because the call does not cross the proxy.
@Service
class OrderService {

    @Transactional
    void place(Order o) { /* ... */ }

    void placeMany(List<Order> orders) {
        orders.forEach(this::place);        // this.place -> no proxy -> no transaction, no cache
    }
}

// FIXED: split the guarded method into its own bean so the call is inter-bean.
@Service
class OrderService {
    private final OrderWriter writer;
    OrderService(OrderWriter writer) { this.writer = writer; }

    void placeMany(List<Order> orders) { orders.forEach(writer::place); }   // goes through the proxy
}

@Service
class OrderWriter {
    @Transactional void place(Order o) { /* ... */ }
}
// The same shape fixes @Cacheable, @Async and @PreAuthorize, which are all proxy-based.

The other members of this family are worth listing because the symptom differs while the cause does not: @Async on a private or self-invoked method (no thread is created), @Cacheable on a method called from within the same bean (a permanent cache miss), @PreAuthorize on a method invoked by another method of the same class (no check), and @Transactional on a method that caught its own checked exception (the transaction commits, because the default rollback rule covers unchecked exceptions only).

Performance and data anomalies

An endpoint that issues N+1 queries — an eager @ManyToOne, a lazy collection serialised at the edge, or open-in-view left on so the extra queries happen invisibly. Turn open-in-view off and the failure becomes a visible exception at the point of the bug. Memory growing over days — an unbounded cache (ConcurrentMapCacheManager or Caffeine without maximumSize), an unbounded async queue, or a collection that accumulates. The actuation is a fixed-size cache with a TTL and a bounded queue with a rejection policy. Requests hanging under load — a connection pool smaller than the concurrency it is asked to serve, with no timeout on the acquisition; set spring.datasource.hikari.connection-timeout so the failure is an exception rather than a queue. Cold-start requests timing out — lazy initialisation or a slow first-call JIT path; measure with the startup endpoint and -XX:+PrintCompilation before changing anything.

13.3 Glossary

The vocabulary of the framework, defined in terms of behaviour rather than restated as a synonym.

Container and configuration

ApplicationContext — the container: a registry of bean definitions plus the singleton instances created from them, with an event bus and a resource loader. BeanDefinition — the recipe for a bean: class, scope, lazy flag and declared dependencies, created before any instance exists. BeanPostProcessor — a hook that can modify or replace a bean before and after initialisation; this is what turns a @Transactional service into a proxy. Auto-configuration — a library-supplied @Configuration class guarded by @Conditional annotations, discovered from AutoConfiguration.imports rather than by scanning. Starter — a dependency-only pom that brings a transitive set of jars and therefore their auto-configuration. BOM — a dependencyManagement import that supplies versions, so no dependency declares one.

Request handling and persistence

DispatcherServlet — the front controller of Spring MVC: it resolves a handler for the request, resolves the method arguments, invokes it, converts the return value and resolves any exception. HandlerMethodArgumentResolver — the component that turns one kind of request data into one method parameter, selected by annotation and by type. HttpMessageConverter — the component that serialises and deserialises a request or response body for a given media type. ProblemDetail — an RFC 9457 error payload with type, title, status, detail and extension members. Persistence context — the set of managed entities inside one transaction, tracked for changes and flushed at commit; the thing that makes lazy loading and dirty checking possible, and the reason open-in-view matters. N+1 — one query for a page of rows plus one query per row for an association. Projection — a query result shaped as a type other than the entity, so no persistence context and no lazy loading.

Operations

Actuator — the management surface: health, metrics, configuration introspection and diagnostics. Micrometer — the metrics façade; a registry decides the output format and Boot configures one from the classpath. Observation — the Micrometer API that produces a metric and a span from one instrumentation point. Liveness — should this process be restarted. Readiness — should traffic be routed here. Graceful shutdown — stop accepting new work, finish what is in flight within a bounded time, then close the context. Layered jar — a jar whose content is partitioned into ordered layers so a container image caches dependencies separately from application classes. AOT processing — evaluating auto-configuration at build time and generating the bean definitions as source, which is what makes a GraalVM native image possible. Native image — a closed-world ahead-of-time executable with no JVM, no bytecode and no JIT.

Distributed systems

Service discovery — resolving a logical service name to live instances, with the registry as the source of truth and each client caching a recent copy. Client-side load balancing — the caller chooses the instance, so the choice can account for the registry's health view. Circuit breaker — stop calling a failing dependency so it can recover, and fail fast meanwhile. Bulkhead — cap the resources one dependency can consume. At-least-once — a message is delivered one or more times, never zero; the guarantee every practical broker offers and the reason consumers must be idempotent. Transactional outbox — write the event in the same database transaction as the data, then publish from a separate process, so the two cannot disagree. Idempotent consumer — a consumer that produces the same effect whether it sees a message once or five times. Expanded/contract migration — a schema change split into an additive step, a backfill, and a removal step, so old and new code can run at the same time.

Version discipline without heroics

Four habits keep a project on a supported version. Never pin a managed dependency — override the BOM's property if you must take a newer library, so the transitive set stays coherent. Upgrade on the patch line continuously — a Boot patch release is the supported way to receive a CVE fix, and taking it monthly is a build change rather than a project. Move one minor version at a time — reading one release note and running the suite is a day; skipping three minors is a quarter, because the deprecations accumulate and the migration guides must be applied in order. Watch for deprecation warnings in the build log, which name the replacement class or property and cost nothing to collect.
