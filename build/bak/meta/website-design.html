1 ▸ Orientation — What Website Design Is

1.1 What website design is1.2 Design vs development: the hand-off1.3 The design process1.4 How this guide is organised1.5 Mindset and tools

This chapter establishes what website design actually is — the discipline that sits between the business goal and the browser — then walks through the design process you will use on every project and how this guide is organised around it.

1.1 What website design is

Website design is the craft of shaping a web page so that a real person can reach a real goal. It spans three layers — UX, UI and visual design — and every layer is constrained by the medium: a viewport, a network, a pointer or a keyboard.

Design starts with a brief, not a moodboard

Before any pixel, the design problem must be written down: who the audience is, what they are trying to do, and how success will be measured. A brief is the contract that stops a project drifting into layout opinions. If the goal is "find a café in under 30 seconds", then a hero video that delays that goal is a failure no matter how pretty it is.

# Design brief - one page, agreed before any pixels
Project:    Café finder website
Audience:   remote workers, 25-45, city-centre
Goal:       find a wifi-equipped café in under 30 seconds
Success:    60% of sessions start a search; 20% book a seat
Constraints: mobile-first, works offline, no login required
Out of scope: reviews, loyalty cards, payments

The three layers: UX, UI and visual

User experience (UX) decides what the page contains and in what order; user interface (UI) decides how those contents are arranged and behave; visual design decides how they look. The layers are separable in code: a semantic HTML structure holds the content, CSS holds the arrangement and the skin. Designing with that separation in mind means a badly styled page still works, and a restyle rarely breaks the content.

<body>
  <header>brand and primary navigation</header>
  <main>
    <h1>One page title per page</h1>
    <section>
      <h2>A chapter</h2>
      <p>The content itself.</p>
    </section>
  </main>
  <footer>contact and legal</footer>
</body>

1.2 Design vs development: the hand-off

A design is only real when it is built. The hand-off is the moment the design becomes a specification the developer can implement without guessing — and most hand-offs fail because they deliver pictures instead of decisions.

What a complete hand-off must contain

Every value a developer needs is a decision: the type scale in rem, the spacing scale, the colour roles in both themes, the radius and shadow tokens, the states of every interactive component, and the breakpoints with a reason for each. If the developer has to measure padding off a screenshot, the design is not finished. Ambiguity is the bug: it ships as whatever the developer happened to infer.

# Hand-off checklist - every value a developer needs to build it
# [ ] type scale with sizes in rem and weights
# [ ] spacing scale (8pt) applied as tokens
# [ ] colour palette with semantic roles, both themes
# [ ] radius, shadow and border tokens
# [ ] states for every interactive component
# [ ] breakpoints with the reason each exists
# [ ] asset exports: SVG icons, WebP images
# [ ] behaviour notes: hover, focus, error, empty, loading

Specify one component completely

The fastest way to test whether a hand-off works is to specify a single component — a button — end to end. Its padding, radius, type, states and tokens are the template for every other component in the system. Note that a disabled state is a state of a component, not a colour choice to invent on the spot.

# Button spec - one component, all the decisions
# purpose    primary action, one per view
# padding    8px 16px (2 and 4 units on an 8pt grid)
# radius     4px (--radius token)
# text       16px medium, ink colour on accent fill
# states     hover: one step darker; focus: 2px ring;
#            disabled: grey that still reads 3:1
# tokens     --btn-bg, --btn-fg, --btn-ring

A hand-off lacking states is not "a bit incomplete" — it is a promise that the developer will design the interactions for you, with no access to the research that shaped them.

1.3 The design process

Design is a loop, not a single act: research, define, ideate, prototype, test and refine. Each step narrows the space of choices, and skipping a step does not save time — it moves the cost to a later, more expensive one.

Research to refine: the loop

Most teams over-invest in the middle of the loop (building things) and under-invest in the ends (knowing the problem, checking the result). Research is the cheapest way to avoid building the wrong thing: talk to five people in the target audience before you design. Then write a one-sentence problem statement, sketch many directions, prototype the cheapest version that can be tested, watch real users use it — without coaching them — and refine what the test proved to be broken.

# research  : talk to 5 real users, record their exact words
# define    : one-sentence problem statement
# ideate    : sketch 10 directions, keep the best 2
# prototype : build the cheapest version that can be tested
# test      : watch users complete the task, do not help
# refine    : change only what the test proved to be wrong

Research, personas and journeys

A persona is a compact description of a real user pattern distilled from interviews — name, context, goal, pain — plus, critically, how that information changes the design. A persona without design implications is a poster. The journey is the sequence of steps the user takes; every page in the journey either moves them forward or is dead weight.

Name: Sam K.
Age: 34
Job: Freelance designer
Goal: Find a quiet café with reliable wifi to work from.
Pain: Most listings lack wifi speed or seat availability.

# How this informs design:
# - Show wifi speed prominently on listing pages
# - Add a "seat availability" filter
# - Include quiet hours in the summary

Jobs-to-be-done

Jobs-to-be-done says people "hire" a product to accomplish a job. The site should make the hire obvious and the job easy to finish. Phrase the job in the user's words and let it drive page structure: if the job is "find a café this afternoon", the search affordance and the wifi data must dominate the layout, not the brand story.

# Job: "I need to find a quiet café to work from this afternoon."
#
# The page that serves this job must:
# 1. Be searchable by location or neighbourhood
# 2. Show wifi speed, power outlets, and noise level
# 3. Offer a map view with filters
# 4. Load fast on a mobile device
# 5. Have a clear call to action: "Book a seat"

1.5 Mindset and tools

Good design is invisible: it lets the user accomplish their goal without noticing the interface. That mindset, plus a free tool stack, is all you need to start.

Principles over trends

Trends change; principles do not. A design that follows enduring principles — clear hierarchy, sufficient contrast, consistent spacing — ages well. One that chases the latest style becomes dated in months. Every visual choice should support the user's goal, and a trend applied to a broken principle is still broken.

# Principle                Trend that fades
# hierarchy                glassmorphism
# contrast                 hairline fonts everywhere
# repetition               neon gradients
# alignment                floating blobs
# A trend on top of a broken principle is still broken.

A free design stack

Figma (free tier) or Penpot for wireframes and UI; WebAIM Contrast Checker for colour; Google Fonts for typography; Unsplash for stock imagery; a browser with DevTools for live inspection. All free, all sufficient for most projects. Pair the tool with the stage it supports: wireframes in Figma, colours with the checker, typography from Google Fonts, live CSS in the browser.

# Stage      Tool (free tier)        Output you ship
# wireframe  Figma / Penpot          frames and flows
# colour     WebAIM Contrast Checker verified hex pairs
# type       Google Fonts            woff2 files, stacks
# imagery    Unsplash                webp + srcset
# code       browser DevTools        live CSS

Export assets in your final format: SVG for icons, WebP for photos, CSS or JSON for tokens. Never ship a raw Figma file or a PSD to the browser.

2 ▸ Layout and Visual Hierarchy

2.1 Grids and spacing systems2.2 Visual weight and hierarchy2.3 F/Z patterns and whitespace2.4 Responsive layout principles2.5 Wireframing

Layout gives the page a skeleton and a reading order. This chapter covers the grids and spacing systems that hold content, the hierarchy that tells the eye where to look first, the whitespace that paces reading, the responsive principles that keep the skeleton alive at every width, and the wireframes that test all of it before pixels exist.

2.1 Grids and spacing systems

A grid is a decision made once instead of per-element: how many columns, what gutters, and where content spans. A spacing system turns every distance into a small set of repeatable values, so pages look consistent by construction rather than by effort.

The twelve-column grid

The classic web grid is 12 columns because 12 divides by 1, 2, 3, 4 and 6 — so a layout can split into halves, thirds and quarters without orphan columns. With CSS Grid the columns and gutters are declared once on the container and spans are assigned with grid-column. The gutters carry the spacing: keep them a multiple of the 8pt base so columns and gaps stay on the same rhythm.

.shell {
  display: grid;
  grid-template-columns: repeat(12, 1fr);
  gap: 24px;                 /* 3 x 8px, same rhythm as the spacing scale */
  max-width: 1200px;
  margin-inline: auto;
}
.shell .main { grid-column: span 8; }
.shell .side { grid-column: span 4; }

Spacing scales: the 8-point system

An 8-point scale means every distance is a multiple of 8px (4px allowed for fine nudges). Consecutive values are 4, 8, 16, 24, 48, 96 — each roughly double, so adjacent scale steps are visually distinct yet recognisably related. Declare the steps once as custom properties; if a value that is not on the scale appears in a component, that is a new decision that deserves a token, not a one-off number.

/* 8pt spacing scale - every distance is a multiple of 8 */
:root {
  --space-1: 4px;    /* fine nudges inside components */
  --space-2: 8px;    /* between related items */
  --space-3: 16px;   /* between sibling components */
  --space-4: 24px;   /* between sections */
  --space-5: 48px;   /* between bands and chapters */
  --space-6: 96px;   /* page gutters on wide screens */
}
.card { padding: var(--space-3); gap: var(--space-2); }
.section + .section { margin-top: var(--space-5); }

4px exists for corrections, not as a parallel scale. If you catch yourself spacing cards 20px apart, round to 24px — consistency beats the "perfect" number.

2.2 Visual weight and hierarchy

Visual hierarchy is the order in which the reader notices elements. Gestalt principles explain why the brain groups some elements together and treats others as separate; weight — size, contrast, position — decides which element gets attention first.

Proximity and similarity

Elements that are close together are seen as related; elements that share shape, size or colour are seen as a group. Use generous whitespace between unrelated sections and consistent spacing inside sections. The same CSS rule that groups a card's title and body also separates cards from each other — proximity is expressed as margin and gap, not as lines and boxes.

/* Good hierarchy with grouped elements */
.card {
  padding: 16px;
  border: 1px solid var(--border);
  border-radius: var(--radius);
  margin-bottom: 24px; /* space between unrelated cards */
}
.card .title {
  font-size: 18px;
  font-weight: 700;
  margin-bottom: 8px; /* space between related title and body */
}

Weight: the four principles of design (CRAP)

Contrast, repetition, alignment and proximity — CRAP — form the four-way check every layout should pass. Repetition makes the same component look the same everywhere; alignment gives every element a shared edge; proximity groups related items; contrast lifts what matters off the page. Weight is bought in this order: size first, then colour contrast, then position. Two elements that must compete for attention are a hierarchy failure, not a composition.

/* Repetition: same card style everywhere */
.card {
  border-radius: var(--radius);
  padding: 16px;
  background: var(--panel);
}

/* Alignment: everything lines up to a left edge */
.card { text-align: left; margin-left: 0; }

/* Proximity: related items are close together */
.card .meta { margin-top: 8px; }

/* Contrast: the title stands out from the body */
.card .title { font-weight: 700; color: var(--text); }

2.3 F/Z patterns and whitespace

Eye-tracking research shows reading is not uniform: users scan. The F-pattern describes scanning dense text pages; the Z-pattern describes quick scans of light pages. Whitespace is the tool that steers both.

The F-pattern and Z-pattern

On text-heavy pages users scan an F: the first line is read fully, the next lines less so, and the right edge of lower lines is largely ignored. Put the important words left, early, and bold — a key fact right-aligned at the bottom of a paragraph is invisible. On light pages with few blocks — landing pages, dashboards — users trace a Z: top bar, diagonal sweep, bottom bar. Put the logo top-left and the call to action bottom-right, where the Z ends.

# F-pattern on a text page (eyetracking summary)
#
# Row 1   ████████████░▓▓▓   read fully
# Row 2   ██████░░░░░░░░░░   scan shortens
# Row 3   ███░░░░░░░░░░░░░   scan shortens further
# Right   ░░░░░░░░░░░░▓▓▓░   the lower-right is skipped
#
# Consequence: lead with the answer in the first line.

Whitespace is a layout element

Whitespace does not separate content; it groups it and paces it. The eye should be able to pause between ideas — that pause is margin. Generous whitespace reads as calm and premium; cramped whitespace reads as urgency. The rule that comes out of the spacing scale: related items get small gaps, unrelated items get large gaps, and the difference must be visible at a glance.

/* Whitespace separates, groups, and sets the pace. */
.section { padding-block: var(--space-5); }
.section + .section { border-top: 1px solid var(--border); }

/* Inside a card, small gaps group; between cards, big gaps divide */
.card { gap: var(--space-2); }
.card + .card { margin-top: var(--space-3); }

2.4 Responsive layout principles

A layout that only works at one width is a drawing, not a design. The responsive principles here are the ones that survive without a single breakpoint: fluid columns, flexible media, and a content order that reflows gracefully.

Fluid grids and flexible media

Build the grid from fractions and minmax, not fixed pixel widths, so the layout fills whatever width it gets. repeat(auto-fill, minmax(240px, 1fr)) is a grid that adds columns as space appears — no media query required. A classic one-liner, img { max-width: 100%; height: auto; }, stops images overflowing their container forever. Every fixed width in a stylesheet is a future overflow bug.

/* The grid adapts without a single media query */
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(240px, 1fr));
  gap: var(--space-3);
}
img { max-width: 100%; height: auto; }
video, iframe { max-width: 100%; }

Reordering content for small screens

On a narrow screen a sidebar is usually a burden, not a benefit: the main content should come first, both in the layout and in the reading order. Use order or explicit grid-area assignments so the reflow is intentional, not a cascade accident. Never reorder with order alone in a way that changes the DOM's tab order — the visual order and the keyboard order must agree.

.layout {
  display: grid;
  gap: var(--space-3);
}
.layout .side { order: 2; }   /* content first on mobile */

@media (min-width: 768px) {
  .layout {
    grid-template-columns: 2fr 1fr;
  }
  .layout .side { order: 0; }  /* sidebar back to the right */
}

2.5 Wireframing

A wireframe is a low-fidelity sketch of a page. It defines structure — what is where, in what order — not colour or typography. Wireframes are cheap to change; high-fidelity mockups are expensive. Test structure here, before any pixels are invested.

Low-fi first, in HTML

Wireframes can live in a design tool, but an HTML wireframe is testable: it runs on a phone, it can be linked, and it forces the layout into real semantics. Build the skeleton with semantic tags and placeholder content — the point is the arrangement, not the words.

<section class="hero">
  <h1>Find Your Quiet Café</h1>
  <input type="search" placeholder="Search by neighbourhood...">
  <button>Search</button>
</section>
<section class="cards">
  <div class="card">...</div>
  <div class="card">...</div>
</section>

Grey-box wireframes

A grey-box wireframe is the same sketch with the blocks annotated by role instead of drawn as cards. The annotation is the design decision: this block is the primary action, that one is secondary. If the roles are not assignable, the page has no hierarchy yet, and no amount of styling will manufacture one. Wireframe with real content where possible — realistic lengths change the layout, and "Lorem ipsum" hides that until it is expensive.

# Grey-box wireframe - structure only, no styling decisions
# +----------------------------------------------+
# | [logo]  [nav: Products | Pricing | Support] |
# +----------------------------------------------+
# | H1: "Find Your Quiet Café"                   |
# | [search input............] [Search]         |
# +---------------------------+------------------+
# | card: name / wifi / seats | card: name / ... |
# | card: name / wifi / seats | card: name / ... |
# +---------------------------+------------------+
# | footer: contact, hours, map link             |
# +----------------------------------------------+

3 ▸ Typography

3.1 Type roles and pairing3.2 Modular scales3.3 Readability and legibility3.4 Web fonts vs system fonts3.5 Sizing units: rem and em

Typography carries most of a page's reading — and most of its character. This chapter covers the roles type plays, how to pair families, how to build a modular scale, what makes text readable, when to use web fonts versus system fonts, and why rem beats naked pixel sizes.

3.1 Type roles and pairing

Every piece of text on a page has a job — display, heading, body, label — and each job deserves its own size, weight and family. Pairing is the art of making two families work together without competing.

Roles: display, heading, body, label

Assign each role one rule set and do not drift from it. Display type carries the hero statement; headings announce sections; body does the reading; labels caption controls and metadata. A body font that is also used for labels at a different size blurs what is clickable and what is not. Roles are expressed as CSS custom properties so the scale is a single source of truth.

:root {
  --font-display: "Sora", system-ui, sans-serif;
  --font-body: "Inter", system-ui, sans-serif;
  --font-mono: "JetBrains Mono", ui-monospace, monospace;
  --step-0: 1rem;        /* body */
  --step-1: 1.25rem;     /* h3 / lead */
  --step-2: 1.5625rem;   /* h2 */
  --step-3: 1.9531rem;   /* h1 */
}
body { font-family: var(--font-body); }
h1, h2, h3 { font-family: var(--font-display); }
code, pre { font-family: var(--font-mono); }

Pairing: contrast, and stop at two families

Pair families that differ in structure — a geometric display face with a humanist body face, for example — so the heading visibly hands over to the body. Pair families that are too similar and the difference reads as a mistake. Limit the page to two families, with a third (mono) reserved for code; every additional family doubles the download and halves the coherence. When in doubt, one well-chosen family with strong weight contrast beats two mediocre ones.

/* A high-contrast display face + a quiet body face.
   Two families max; a third, mono, only for code. */
html { font-family: "Inter", system-ui, sans-serif; }
h1, h2, h3 { font-family: "Sora", system-ui, sans-serif; }
code, pre { font-family: "JetBrains Mono", ui-monospace, monospace; }

3.2 Modular scales

A modular scale is a set of type sizes built by multiplying one base size by a ratio. Common ratios are the major third (1.25) and the golden ratio (1.618). The scale makes sizes consistent by construction: every heading is a step, never a guess.

Build the scale

Pick a base — 16px is the browser default and the usual body size — and multiply by the ratio for each step up, divide for each step down. The same ratio applies from caption right up to display, so the whole page shares one visual relationship. A table of the scale is a design artefact worth keeping with the token file.

# Modular scale, ratio 1.25 (major third), base 16px
#  step  size     role
#  -2    10.24px  caption, metadata
#  -1    12.80px  small text, labels
#   0    16.00px  body
#   1    20.00px  lead, h4
#   2    25.00px  h3
#   3    31.25px  h2
#   4    39.06px  h1 / display

Fluid type with clamp()

Handing a fixed step to every viewport makes type either huge on phones or tiny on desktops. clamp() interpolates between a mobile step and a desktop step across the width range, with the middle term in vw driving the curve. The fluid size keeps the scale relationship while removing the breakpoints.

/* One fluid size derived from the scale at both ends */
h2 {
  font-size: clamp(
    1.5625rem,          /* mobile: scale step 2 */
    1rem + 1.5vw,       /* the curve */
    2.4414rem           /* desktop: scale step 3 */
  );
  line-height: 1.15;
}

3.3 Readability and legibility

Legibility is whether a character can be told apart from its neighbours; readability is whether a block of text can be read comfortably. Both are set in CSS: line length, line height, and how lines break.

Line length and leading

The readable line is 45–75 characters — the standard measure — because longer lines make the eye lose the next line and shorter lines make it snap back too often. Set a max-width in ch units so the measure survives font-size changes. Body leading of 1.5–1.65 relative line-height is the comfort zone; display headings tighten to 1.05–1.2 or the descenders collide with the next line.

article p {
  max-width: 65ch;      /* 45-75 characters per line */
  line-height: 1.6;     /* readable body leading */
  margin: 0 0 1rem;
}
h1, h2, h3 { line-height: 1.15; }  /* tight for display */

Alignment and hyphenation

Left-aligned (ragged right) text is the safe default: even spacing, no rivers. Justified text needs hyphenation enabled or the browser stretches word spaces and opens vertical gaps — rivers — that break scanning. hyphens: auto requires a lang attribute to know the language's break rules. Never centre body-length text; centred is for short display lines only.

/* Justified text needs hyphens, or rivers appear */
article.justified {
  text-align: justify;
  hyphens: auto;
  overflow-wrap: break-word;
}
/* Ragged right is the safer default - no hyphens needed */
article.default { text-align: left; }

3.4 Web fonts vs system fonts

A web font is a brand decision with a performance cost; a system font is zero-download consistency with the operating system. The choice is a trade-off, and both have a correct CSS shape.

System font stacks and when they win

A system stack references the fonts every OS ships, so text renders instantly and matches the platform the reader already knows. No download, no layout shift, no licensing. The cost: the design varies by OS, and the stack is hard to make distinctive. Use system fonts when speed and simplicity matter more than brand character — dashboards, docs, tools.

/* System stack: zero download, matches the OS, always available */
html {
  font-family: system-ui, -apple-system, "Segoe UI", Roboto,
    "Helvetica Neue", Arial, sans-serif;
}

Web fonts: @font-face done properly

When a web font is worth the weight, serve WOFF2, subset to the scripts you actually use (Latin only if the content is English), and declare font-display: swap so text renders in a fallback immediately instead of a blank flash. The default block behaviour hides text for up to 3 seconds while the font loads — that is the classic invisible-while-loading failure. Self-host the files rather than hotlinking a CDN, and keep total font payload near 100KB.

@font-face {
  font-family: "Inter";
  font-style: normal;
  font-weight: 400;
  font-display: swap;              /* text first, font later */
  src: url("/fonts/inter-latin-400.woff2") format("woff2");
  unicode-range: U+0000-00FF;      /* latin subset only */
}

The swap doesn't fix layout shift: text reflows when the real font arrives. Declare size-adjust or reserve the metrics so the swap moves nothing the reader is looking at.

3.5 Sizing units: rem and em

rem and em are both relative units, and the difference between them is where they look for their reference: the root for rem, the parent for em. That one difference decides which one composes and which one compounds.

rem for scalable type

1rem always equals the root font-size (16px at default zoom), so type set in rem scales with the root — zoom, user font-size preferences, and a fluid root via clamp() all cascade correctly. This is the accessibility argument: a reader who sets their browser to 20px gets a proportionally larger page. Keep px only for borders and one-pixel lines, where scaling would look wrong.

:root { font-size: 100%; }   /* 16px at default zoom */
html {
  font-size: clamp(1rem, 0.5rem + 0.6vw, 1.125rem);
}
body { font-size: 1rem; }
.card { padding: 1.25rem; }          /* scales with zoom + root */
.card .title { font-size: 1.3125rem; } /* one scale step up */
.card { border: 1px solid var(--border); }  /* px stays for hairline */

em compounds: the nesting trap

1em resolves against the parent's font-size, so nested em values multiply: a card set to 1.25em inside another card set to 1.25em is not 1.25× root but 1.25× the parent — 25px instead of 20px at a 16px root. That compounding is sometimes exactly what you want (scaling a badge with its container), but it surprises everywhere else. Rule of thumb: rem for anything that should respect the user's base size, em for short-scope sizing that must track its own container, px for hairlines.

/* em is relative to the parent - it compounds when nested */
.box { font-size: 1.25em; }        /* 20px inside a 16px parent */
.box .box { font-size: 1.25em; }   /* 25px - compounded again */

/* rem is relative to the root - it never compounds */
.box { font-size: 1.25rem; }       /* 20px at a 16px root, everywhere */

Set margins and padding in em on the element that owns the font-size, and they scale with the text — a button's padding grows when its label grows. Set distances between unrelated things in rem so they ignore the local type size.

4 ▸ Colour

4.1 Colour psychology and the colour model4.2 Palettes and harmonies4.3 Contrast and accessibility4.4 Theming: light and dark4.5 Colour in UI components

Colour is the fastest signal on a page and the easiest to get wrong. This chapter covers what colour means to people, how to build palettes and harmonies, how contrast is calculated and why it is a requirement rather than a taste, how to theme light and dark without duplicating decisions, and how colour behaves inside components.

4.1 Colour psychology and the colour model

Colour carries meaning, but the meaning is cultural, not universal. Before choosing a palette, decide which hue plays which role, then express the palette in a model you can reason about.

Associations are context, not code

The same hue means different things in different places: white is purity in much of Europe and mourning in parts of Asia; red is danger in road signs and luck in China. Even within one culture, the hue's job in the interface beats its dictionary meaning — a red alert needs red, but a brand does not. Choose roles first (brand, accent, success, warning, danger, neutral), then let audience research pick the hues.

# Colour is context. Same hue, different audiences:
#   white: purity (Europe) / mourning (parts of Asia)
#   red:   danger (signs) / luck (China), weddings (India)
# Decide the role first, then the hue:
#   brand    -> the hue you own
#   accent   -> attention, conversion actions
#   semantic -> success / warning / danger / info
#   neutral  -> everything else carries the content

Hue, saturation, lightness: reason in HSL/oklch

Hex is how colours are stored but a poor way to reason about them. The HSL model — hue (0–360°), saturation, lightness — separates what the colour is from how vivid and how light it is, which is exactly the pair of knobs theming needs. oklch() goes further: its lightness axis maps to perceived lightness, so the same L value reads as the same brightness across very different hues — the property that makes ramps for light and dark themes trustworthy.

:root {
  /* hue 214 = blue; the ramp stays on one hue */
  --brand-h: 214;
  --brand-hi: oklch(0.55 0.18 230);   /* bright accent */
  --brand-lo: oklch(0.42 0.14 230);   /* deep navy */
  --neutral-1: oklch(0.2 0 0);        /* near-black text */
  --neutral-9: oklch(0.98 0 0);       /* near-white surface */
}

4.2 Palettes and harmonies

A palette is a plan: a handful of hue positions and a rule for deriving shades from them. Harmonies — complementary, analogous, triadic — are heuristics for placing those hue positions so the palette feels coherent rather than random.

Harmonies, and why one dominates

Complementary pairs sit opposite the colour wheel and maximise tension; analogous groups sit adjacent and feel calm; triadic spreads three evenly and feels playful. All three work only when one hue dominates and the others are accents — three equal hues is noise, not a palette. Any working palette needs neutrals too: grey ramps for text, borders and surfaces outnumber the brand hues by far.

# Complementary: brand blue #034DB8 paired with amber #B87A03
# Analogous:     blues and teals - #012A66, #034DB8, #009CFF
# Triadic:       blue, amber, magenta - evenly spaced
#
# Working palette (one hue dominates, neutrals carry the page):
#   primary   #034DB8   actions, links, active nav
#   accent    #009CFF   highlights, selected states
#   success   #1E7B34   confirmed actions
#   danger    #B3261E   destructive actions
#   neutral   #1A2433   text on light
#   surface   #FFFFFF   page background

The 60-30-10 rule

The 60-30-10 rule allocates the page roughly 60% neutral surfaces, 30% secondary tones (panels, borders), and 10% accent — the accent is what should be scarce, because scarcity is what makes it noticed. Enforce it structurally with tokens: the accent should never be painted with a raw hex inline, because the moment it is, the 10% becomes 50% one paste at a time.

:root {
  /* 60% neutral - the page itself */
  --c-surface: #ffffff;
  --c-text:    #1a2433;
  /* 30% secondary - panels, cards, borders */
  --c-panel:   #f2f5f9;
  --c-border:  #d8dfe8;
  /* 10% accent - buttons, links, active states */
  --c-accent:  #034db8;
  --c-accent-ink: #ffffff;
}

4.3 Contrast and accessibility

Contrast is the measurable difference between foreground and background, and WCAG mandates minimums. It is a requirement with a formula, so it is checked by calculation, not by eye.

WCAG contrast requirements

WCAG 2.2 requires 4.5:1 for body text and 3:1 for large text (≥24px, or ≥18.66px bold) and for the visual boundaries of UI components. The classic failure is light grey text on white: it reads as "designed" in a mockup and as unreadable in production.

/* Accessible contrast: 4.5:1 for body text */
body {
  color: #212529;      /* dark text */
  background: #ffffff; /* light background */
}

/* Too low: white text on light grey */
.bad {
  color: #cccccc;
  background: #ffffff;
}

Calculating the ratio yourself

The WCAG ratio is computed from relative luminance: convert each RGB channel to linear light, weight them 0.2126/0.7152/0.0722, and divide the lighter luminance plus 0.05 by the darker plus 0.05. A ratio of 4.5 passes body text; 3.0 passes large text and UI edges. This is a two-minute script — run it on every colour pair the palette produces, in both themes.

// WCAG relative luminance and contrast ratio
function luminance(r, g, b) {
  const f = (c) => {
    c /= 255;
    return c <= 0.03928 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4);
  };
  return 0.2126 * f(r) + 0.7152 * f(g) + 0.0722 * f(b);
}
function ratio(hexA, hexB) {
  const L = (hex) => luminance(...hex.match(/\w\w/g).map((h) => parseInt(h, 16)));
  const hi = Math.max(L(hexA), L(hexB));
  const lo = Math.min(L(hexA), L(hexB));
  return (hi + 0.05) / (lo + 0.05);
}
// #212529 on #ffffff -> 15.4:1   passes body text
// #767676 on #ffffff -> 4.54:1   passes, barely
// #cccccc on #ffffff -> 1.6:1    fails everything

3:1 is the boundary for UI component edges and large text, not for body text. Grey buttons with 3:1 text and no label fail the moment anyone needs to actually read them.

4.4 Theming: light and dark

Light and dark versions of a design should be the same design. The mechanism is semantic tokens: components reference roles — surface, text, accent — and the theme redefines the roles, never the components.

Semantic tokens, not raw hex, in components

Theming works because components never name a colour, they name a role. --surface can be #ffffff in one theme and #0d1421 in another while the component code stays identical. Raw hex inside a component is a bug: that component now cannot be themed and drifts out of the system. Keep every theme's token block complete — a half-switched theme looks like a rendering glitch and is almost impossible to diagnose later.

:root[data-theme="light"] {
  --bg: #ffffff;
  --surface: #f2f5f9;
  --text: #1a2433;
  --text-dim: #44546a;
  --accent: #034db8;
  --accent-ink: #ffffff;
}
:root[data-theme="dark"] {
  --bg: #0d1421;        /* a deep blue-grey, not pure black */
  --surface: #151e2e;
  --text: #e8eef7;
  --text-dim: #9fb0c4;
  --accent: #4dd2ff;    /* lifted, so it still reads on dark */
  --accent-ink: #03203f;
}
.card { background: var(--surface); color: var(--text); }

Dark mode: elevation without shadows

Pure black backgrounds exaggerate every other colour and glow; the dark palette should sit one step off black. Elevation in dark mode is expressed as lighter surfaces, not shadows — shadows vanish on dark, so the modal goes lighter than the page. And text that passed on white often fails on a dark surface; the darkest text colour is not automatically readable on the darkest background. Re-run contrast for every theme; a palette is not done until both pass.

/* Elevation in dark mode = lighter surfaces, never shadows */
:root[data-theme="dark"] {
  --surface-raised: #1c2740;   /* modal, popover */
  --surface-top:    #243250;   /* toast, floating action */
}
.card  { background: var(--surface); }
.modal { background: var(--surface-raised); }
.toast { background: var(--surface-top); }

4.5 Colour in UI components

Components are where colour becomes a system: every interactive element needs a colour for every state, and every state needs a contrast-verified pair. Semantic colours — success, warning, danger — carry meaning and must never be the only signal.

States: rest, hover, active, focus, disabled

Each interactive component specifies its own state colours, and the states are steps on one hue ramp rather than new hues: hover one step darker, active another, focus a ring. A disabled element must not look like a resting element — its text contrast should drop but stay readable, and it should never look clickable. Deriving states from tokens keeps the whole library's behaviour consistent.

.btn {
  --bg: var(--c-accent);
  --fg: var(--c-accent-ink);
  background: var(--bg);
  color: var(--fg);
  border: 1px solid transparent;
  border-radius: 4px;
  padding: 8px 16px;
  cursor: pointer;
}
.btn:hover { --bg: #0267b2; }
.btn:active { --bg: #012a66; }
.btn:focus-visible {
  outline: 2px solid var(--c-accent);
  outline-offset: 2px;
}
.btn:disabled {
  --bg: #c6cdd6;      /* text still 3:1 against the fill */
  --fg: #5b6673;
  cursor: not-allowed;
}

Semantic colours with a second signal

Success, warning, danger and info each get a background/foreground pair verified for contrast. Colour-blind users cannot rely on hue alone, so every alert also carries an icon and a text label — the colour reinforces meaning, it does not carry it. Define the four pairs once as tokens; an alert that invents its own pastel breaks both the system and, usually, the contrast rule.

:root {
  --ok-bg:   #e6f4ea;  --ok-fg:   #1e4620;  /* success, 10.1:1 */
  --warn-bg: #fef7e0;  --warn-fg: #6a4a00;  /* warning, 8.9:1 */
  --err-bg:  #fdecea;  --err-fg:  #8c1d18;  /* danger,  7.6:1 */
  --info-bg: #e8f1fd;  --info-fg: #0b3d8f;  /* info,    9.8:1 */
}
.alert { border-radius: 4px; padding: 12px 16px; }
.alert.ok   { background: var(--ok-bg);   color: var(--ok-fg); }
.alert.error { background: var(--err-bg); color: var(--err-fg); }

Test the palette once with a simulator (Figma's colour-blind preview, or DevTools' rendering panel) — not because colour-blind users are rare, but because hue-only alerts fail silently: nobody reports a message they cannot see distinguish.

5 ▸ Imagery, Icons and Branding

5.1 Photography5.2 Illustration5.3 Iconography5.4 Favicons, logo marks and brand consistency

Photography, illustration, icons and logo marks carry the emotional layer of a design — and, badly handled, most of its weight. This chapter covers choosing and shipping photography, using illustration and SVG, building an icon family, and keeping the brand lockup consistent across pages.

5.1 Photography

A photograph is the fastest way to set a mood and the fastest way to slow a page. The craft is in the choice of format and crop: right-sized, right-formatted, and framed at its focal point.

Formats and responsive delivery

Ship AVIF or WebP, not giant JPEGs — typically half the bytes at the same quality. srcset with sizes lets the browser pick the right file for the viewport, and the width/height attributes reserve the space so the layout does not jump when the image arrives. A hero that is the page's main content should load eagerly (fetchpriority="high"); everything below the fold should be lazy.

<img
  src="hero-960.webp"
  srcset="hero-480.webp 480w, hero-960.webp 960w, hero-1440.webp 1440w"
  sizes="(min-width: 1024px) 960px, 100vw"
  width="960" height="540"
  alt="A quiet café with laptops on a long wooden table"
  fetchpriority="high"
>

Cropping to the subject: object-fit and object-position

A photo has one focal point — a face, a product, a sign — and the crop should follow it, not the centre. object-fit: cover fills the frame without stretching; object-position pins the focal point inside the crop so it survives every card size. Because the crop target changes with the layout, the position can change with a media query. Never stretch an image to fit a box; that is the fastest way to destroy a photo.

.hero img {
  width: 100%;
  height: clamp(240px, 40vw, 520px);
  object-fit: cover;          /* fill the frame, never stretch */
  object-position: 60% 30%;   /* subject sits upper-right */
}
@media (max-width: 600px) {
  .hero img { object-position: 40% 20%; }  /* reframe for narrow */
}

Stock photos are licences, not downloads. Check the licence before using a service's images commercially — Unsplash's terms changed, and "free" once meant "attribution-free" and now has conditions in some jurisdictions.

5.2 Illustration

Illustration earns its place where photography cannot go: abstract concepts, empty states, onboarding flows, and anything that needs a consistent hand. Inline SVG keeps it crisp at every resolution and themeable.

Inline SVG: crisp, themeable, tiny

An illustration is often a few dozen SVG paths — smaller than the equivalent photo and infinitely scalable. Inline the SVG (rather than an <img> tag) when it must respond to theme colours or hover; use stroke="currentColor" so the illustration inherits the text colour. Name it for assistive tech when it carries meaning (role="img" plus a <title>) and mark it decorative otherwise.

<svg viewBox="0 0 32 32" role="img" aria-labelledby="empty-title">
  <title id="empty-title">An empty inbox</title>
  <rect x="4" y="8" width="24" height="16" rx="2"
        fill="none" stroke="currentColor" stroke-width="2"/>
  <path d="M4 10 L16 18 L28 10" fill="none"
        stroke="currentColor" stroke-width="2"/>
</svg>

One hand: the illustration style spec

The fastest way to make a site look amateurish is two illustration styles side by side — one flat, one shaded, one with outlines. Write the style down as a spec — stroke weight, grid, palette, fill treatment — and hold every new drawing to it. This is the same discipline as a design system, one drawing at a time.

# Illustration style spec - keep one designer's hand
# stroke    2px, rounded caps, drawn on a 24px grid
# palette   three hues from the brand ramp, plus neutral
# fills     flat; no gradients, no shading
# subjects  abstract concepts, empty states, onboarding
# export    inline SVG, stroke="currentColor" aware
# size      keep the path count under 40 per drawing

5.3 Iconography

Icons are a family, not a collection: same grid, same stroke, same optical weight. And they carry a quiet accessibility burden — every icon is either decorative or meaningful, and the markup must say which.

One grid, one stroke, optical alignment

Standardise on a grid — 24×24 with a 2px stroke is the most common — so the whole set reads as one family. Mathematical centring is not visual centring: a circle looks optically smaller than a square of the same box, so pannable shapes get drawn slightly larger. Consistent stroke caps and joins (round at both) are what make a set feel finished rather than drawn by ten people.

<!-- One family: 24x24 grid, 2px stroke, round caps -->
<svg viewBox="0 0 24 24" fill="none" stroke="currentColor"
     stroke-width="2" stroke-linecap="round"
     stroke-linejoin="round">
  <circle cx="12" cy="12" r="9"/>
  <path d="M3 6h18M3 12h18M3 18h18"/>
</svg>

Icon accessibility: aria-hidden or labelled

An icon next to visible text is decoration: hide it with aria-hidden="true" so screen readers do not announce a drawing. An icon that is the only label of a button must be named — either with aria-label on the button or with a visually hidden text span. Never leave a bare icon unlabelled and unhidden: it is either noise or a silence that hides a function.

<!-- Decorative: the text label carries the meaning -->
<button type="button" class="icon-btn">
  <svg aria-hidden="true" viewBox="0 0 24 24">
    <path d="M21 21l-4.3-4.3M17 10a7 7 0 1 1-14 0 7 7 0 0 1 14 0z"/>
  </svg>
  <span>Search</span>
</button>

<!-- Icon only: the button itself carries the name -->
<button type="button" aria-label="Search" class="icon-btn">
  <svg aria-hidden="true" viewBox="0 0 24 24">
    <path d="M21 21l-4.3-4.3M17 10a7 7 0 1 1-14 0 7 7 0 0 1 14 0z"/>
  </svg>
</button>

Draw icons in currentColor and they inherit every state colour — hover, disabled, theme — with zero extra CSS.

5.4 Favicons, logo marks and brand consistency

The brand mark travels farther than the homepage: the favicon in the tab, the touch icon on a phone home screen, and the header lockup on every page. Consistency across all of them is a brand rule, not a decoration.

Favicons and touch icons

A single SVG favicon covers modern browsers, but Safari still wants a PNG touch icon, and some browsers still request an ICO. Declare an SVG icon with a PNG fallback plus the 180×180 apple-touch-icon, and keep the mark simple — at 16 pixels, detail becomes noise. A favicon is also the cheapest recurring brand impression you have; a default globe next to your project name says the project was never finished.

<link rel="icon" type="image/svg+xml" href="/favicon.svg">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32.png">
<link rel="apple-touch-icon" sizes="180x180"
      href="/apple-touch-icon.png">

The lockup: one mark, one rule, every page

The header lockup — logo mark, wordmark, page name — should be byte-identical across the site: same order, same spacing, same typography. Anyone who reassembles it per page creates ten variants of the brand. Theme the mark with a token, never with per-page recolouring, so light and dark themes stay consistent and the mark stays recognisable. The same discipline applies to the wordmark's typeface and to the spacing rhythm around it.

/* One lockup, everywhere: mark + wordmark + page name */
.brand {
  display: flex;
  align-items: center;
  gap: var(--space-2);
}
.brand img { height: 40px; width: auto; }      /* the logo mark */
.brand .wordmark { font-family: var(--font-display); font-weight: 800; }
/* Theme the mark with one token, never per-page recolouring */
.brand img { filter: var(--brand-logo-filter); }

6 ▸ Responsive and Mobile-First Design

6.1 Breakpoints6.2 Fluid layouts6.3 Touch targets and interaction6.4 Navigation patterns6.5 Performance-aware asset choice

Most visitors are on a phone. This chapter covers choosing breakpoints, building fluid layouts that survive unknown widths, sizing touch targets, choosing navigation patterns that fit the viewport, and choosing assets the network can actually deliver.

6.1 Breakpoints

A breakpoint is where the layout changes because the content has stopped working, not where a device "ends". Choose them in a mobile-first direction so the default is the smallest screen and every query adds capability.

Breakpoints are about content, not devices

Naming breakpoints by intent — base, narrow, medium, wide — keeps the CSS honest: a query exists because the layout needs a change at that width, not because an iPhone was 375px in 2023. New devices ship every year; the reasons the layout breaks only change when the content does.

# Breakpoints chosen by content, named by intent, mobile-first
# name      min-width  why the layout changes
# base      0          single column, nav behind a button
# narrow    30rem      two cards fit side by side
# medium    48rem      sidebar appears, nav fits in full
# wide      64rem      content capped at 75rem
# Apply with min-width so the phone is the default, not an override.

Mobile-first: min-width queries

Write the base rules for the narrowest screen, then add capability with min-width queries. Max-width queries double every rule and make the phone a patchwork of overrides; min-width queries keep mobile styles the default and each larger step an additive change. The burger button exists by default and is removed where the full nav fits — not the other way round.

/* Mobile-first: base rules style the phone, then grow */
.nav-list { display: none; }             /* phone: hidden behind */
.btn-menu { display: inline-flex; }      /* phone: burger shown */

@media (min-width: 48rem) {
  .nav-list { display: flex; }           /* grow: full nav */
  .btn-menu { display: none; }           /* burger no longer needed */
}

If you reach for a max-width query, ask what the mobile rule is doing to you — usually the answer is "overriding a desktop default that should not exist".

6.2 Fluid layouts

Fluid layouts respond to the space they are given, not just the viewport. Container queries and clamp() do the work breakpoints used to, with less to maintain.

Container queries: respond to the parent

A card in a two-column grid and the same card full width are different problems, and media queries cannot tell them apart — they answer "how wide is the viewport?", not "how wide is this card?". A container query answers the second: declare container-type on the parent and the component reflows on its own width. This is what makes a component library genuinely reusable.

.card-panel { container-type: inline-size; }

@container (min-width: 32rem) {
  .card-panel {
    display: grid;
    grid-template-columns: 160px 1fr;  /* photo beside text */
  }
}

One clamp does the work of three breakpoints

Continuous sizing with clamp() removes most of the breakpoint scaffolding: padding, gaps and type interpolate smoothly instead of jumping at thresholds. The middle argument in vw scales with the viewport; the two bounds keep it from collapsing on phones or exploding on desktops. Use flow-relative properties (padding-inline, margin-block) so the same rules serve LTR and RTL layouts.

.shell {
  padding-inline: clamp(16px, 4vw, 48px);   /* gutter */
  gap: clamp(16px, 2.5vw, 32px);            /* between blocks */
}
.hero-title {
  font-size: clamp(2rem, 1rem + 4vw, 4rem); /* fluid type */
}

6.3 Touch targets and interaction

On a phone the pointing device is a thumb, and thumbs are imprecise. Touch targets must be big enough to hit without aiming, and the design must not depend on hover — touch has none.

44px targets, 8px gaps

Apple's HIG recommends 44×44 CSS pixels and Material Design 48dp; 44px is the working minimum for any tappable control. Small targets get larger hit areas (padding on the element, not just the visible icon), and targets need clear space between them — 8px — so a miss lands on nothing instead of the wrong action. This is a layout rule, applied in CSS, not a QA afterthought.

button, a.btn, input, select, [role="button"] {
  min-height: 44px;
  min-width: 44px;
}
/* Space the targets; a miss should hit nothing */
.button-group { gap: 8px; }
.nav-item { padding-block: 12px; }

Detecting the input: hover and pointer

A phone has no hover, so anything revealed only on hover is unreachable. The media queries (hover: none) and (pointer: coarse) detect the input type: when they match, show everything by default and skip hover-only affordances. Never guess from touch events or screen size; the media queries are the supported signal, and they also catch hybrids and styluses.

/* Touch devices must not depend on hover to reveal anything */
@media (hover: none) {
  .dropdown { display: block; }     /* always visible */
  .hover-tip { display: none; }     /* hover-only affordance */
}
@media (pointer: coarse) {
  button, a, input, select { min-height: 44px; }
}

6.4 Navigation patterns

Navigation is the pattern that changes most with the viewport. The burger menu, tabs and bottom navigation each answer a different width question — and each has a failure mode to design around.

The burger menu: a disclosure, not a hiding place

The burger works when the menu is genuinely secondary — rarely used items behind a button. It fails when primary navigation is hidden behind it, because discoverability collapses. Mark it up as a real disclosure: a button with aria-expanded and aria-controls pointing at the nav, which starts hidden. The menu must be keyboard-operable, and it must not move content around the page when it opens.

<header>
  <button id="menu" class="burger"
          aria-expanded="false" aria-controls="site-nav">
    Menu
  </button>
  <nav id="site-nav" hidden>
    <a href="/">Home</a>
    <a href="/pricing/">Pricing</a>
    <a href="/support/">Support</a>
  </nav>
</header>

Tabs and bottom navigation

Bottom navigation puts primary destinations under a thumb — the right pattern for apps with four or five top destinations. Tabs suit switching within one section. Both are persistent and visible, which is their strength; both crowd quickly, and the moment a destination does not fit, the answer is a "More" screen, not a menu that wraps. Keep the active tab visibly distinct (colour plus position), never just colour.

<nav class="tabbar" aria-label="Primary">
  <a class="tab is-active" href="/">
    <svg aria-hidden="true"><path d="M3 6h18M3 12h18M3 18h18"/></svg>
    <span>Home</span>
  </a>
  <a class="tab" href="/search/">Search</a>
  <a class="tab" href="/profile/">Profile</a>
</nav>

.tabbar { position: sticky; bottom: 0; }
.tab.is-active { color: var(--accent); border-top: 2px solid var(--accent); }

Hidden navs are the classic keyboard trap: the button opens the menu but focus stays on the button. Move focus into the opened nav, close on Escape, and return focus to the button on close.

6.5 Performance-aware asset choice

Every byte is a UX decision made in advance. The design chooses the images, fonts and scripts; performance decides whether the page is usable on the connection most visitors actually have.

Lazy media, eager hero

Below-the-fold images get loading="lazy" and decoding="async" so the browser skips them until they are near the viewport; the LCP image (usually the hero) loads eagerly and carries width/height or an aspect-ratio to prevent layout shift. Choose formats — AVIF/WebP for photos, SVG for icons — at design time, not in a panic later.

<img src="card-480.webp"
     width="480" height="360"
     loading="lazy" decoding="async"
     alt="Café seating near a window">

<!-- The hero is the LCP element: eager, sized, no shift -->
<img src="hero-1440.webp" width="1440" height="810"
     fetchpriority="high" alt="...">

Budget the page before building it

A performance budget is a design constraint written down: total page weight, JavaScript payload, LCP and CLS targets. Budgets turn performance from an argument into a measurable pass/fail — and they catch creeping growth, which is how sites rot. Check against real network conditions (throttled 4G), not the office fibre, because the office fibre lies.

# Performance budget - decide before you build, then measure
# total page weight  < 1 MB
# main-thread JS     < 170 KB uncompressed
# LCP                < 2.5 s on throttled 4G
# CLS                < 0.1
# hero image         < 100 KB
# card images        < 30 KB each
# fonts              < 2 families, woff2, latin subset

Put the budget in the design hand-off and measure it in CI. A page that grew past its budget is a design regression, reported like any other.

7 ▸ Accessibility, Design Systems and Hand-Off

7.1 WCAG essentials7.2 Design tokens7.3 Component libraries7.4 Developer hand-off7.5 Documentation and definition of done

The final chapter makes the work durable: accessibility turns the design into something everyone can use, design tokens and component libraries turn it into a system, the hand-off turns it into code without guesswork, and documentation keeps the system true after you have moved on.

7.1 WCAG essentials

WCAG 2.2 organises accessibility into four principles — perceivable, operable, understandable, robust (POUR) — and each principle maps to concrete markup and design choices you can verify.

POUR in practice

Perceivable: nothing essential is invisible — images have alt text, information is not colour-only. Operable: everything is reachable by keyboard, focus is visible, touch targets are large enough. Understandable: reading order matches the layout, errors say what to fix. Robust: semantic HTML so assistive tech can parse it, one h1 per page, controls named correctly. Accessibility is not a feature to add at the end; each decision either supports it or costs a fix later.

# WCAG 2.2 essentials - POUR in practice
# Perceivable
#   [ ] every image has alt text; icons are visible or labelled
#   [ ] colour is never the only signal (add an icon or text)
#   [ ] contrast 4.5:1 body text, 3:1 UI edges and large text
# Operable
#   [ ] everything keyboard reachable; focus ring visible
#   [ ] touch targets 44px; no hover-only flows
# Understandable
#   [ ] nav order matches reading order; lang attribute set
#   [ ] error messages say what to fix and how
# Robust
#   [ ] semantic HTML; one h1 per page; names announced correctly

Semantic HTML is the accessibility framework

Landmarks — header, nav, main, footer — are how screen-reader users jump around a page, so a div-only layout strips their navigation to zero. The heading order is the outline: one h1, then h2s that introduce sections. A "skip to content" link at the very top gives keyboard users the same shortcut a mouse user has. These are design decisions, made in the markup.

<a class="skip" href="#main">Skip to content</a>
<header>brand, primary nav, search</header>
<nav aria-label="Primary">...</nav>
<main id="main">
  <h1>Page title - the only h1 on the page</h1>
  <section><h2>Section</h2>...</section>
</main>
<footer>contact and legal</footer>

7.2 Design tokens

Design tokens are the decisions of a design system written as data: colours, spacing, radii, typography and shadows stored once and emitted everywhere. A token is a name with a value and a purpose — and a guarantee that the UI and the design tool agree.

Tokens are data with a source of truth

A token names a decision — color.surface.page, size.space.3 — and the value belongs to the token file, not to any component. Components reference names; themes and platforms swap values. This is the rule that made the colour chapter's theming work, generalised: when a component hard-codes a value, the system has two truths, and they will silently diverge. Structure tokens by function (colour, size, radius, shadow, type) so tools can export them.

{
  "color": {
    "text":    { "primary": { "value": "#1a2433" } },
    "surface": { "page":    { "value": "#ffffff" } },
    "accent":  { "default": { "value": "#034db8" } }
  },
  "size": {
    "space":  { "2": { "value": "8" }, "3": { "value": "16" } },
    "radius": { "default": { "value": "4" } }
  },
  "type": {
    "scale": { "body": { "value": "16" }, "display": { "value": "39" } }
  }
}

Emit tokens to every platform from one file

Transpilers such as Style Dictionary and Token Studio read the token JSON and emit CSS custom properties, Sass maps, iOS and Android constants — one file, N outputs, no drift. CSS variables are the web output; the naming convention maps one-to-one (color.text.primary becomes --color-text-primary). Ratchet check: if someone changes a hex in the CSS instead of the token file, the check that catches it is a diff of the generated file.

/* tokens.json -> :root via a transpiler
   one source of truth, emitted as CSS / iOS / Android */
:root {
  --color-text-primary: #1a2433;
  --color-surface-page: #ffffff;
  --color-accent-default: #034db8;
  --size-space-2: 8px;
  --size-space-3: 16px;
  --size-radius-default: 4px;
  --type-scale-body: 16px;
  --type-scale-display: 39px;
}
/* components use the names; themes and platforms swap values */

7.3 Component libraries

A component library is the design system rendered as code: each component is a contract — anatomy, styles, states, variants, content rules — implemented once and reused everywhere. The library is what makes a 40-page site feel like one product instead of forty.

A component is a contract, not a drawing

Atomic design decomposes interfaces into atoms (tokens, single elements), molecules (small groupings like a search field), organisms (sections), templates and pages. The useful unit for shipping is the molecule: the button, the alert, the card. Each one is specified completely — anatomy, style variants, interaction states, content guidance — so "use the Button component" is a complete instruction and not an invitation to improvise.

# Button - a component is a contract
# anatomy   label + optional leading icon + spinner when busy
# styles    primary, secondary, danger, ghost
# states    rest, hover, active, focus-visible, disabled, loading
# content   real words: "Book a seat", never "Click here"
# variants  size: small / medium / large; full-width option
# tokens    every colour and radius from the token file
# demo      storybook entry + a live page example, in sync

Document states before variants multiply

State matrices are where component libraries earn their keep and where they most often rot. The rule: every state row (rest, hover, active, focus, disabled, loading) is specified, or the component ships half-designed. Disabled is the row people skip — it needs a colour that reads but does not invite, focus is the row that must never be skipped on principle (keyboard users depend on it). Storybook's value is that every state and variant gets a visible, testable slot.

# State matrix - specify every row before the component ships
# state         colour      border  focus  behaviour
# rest          accent      none    --     -
# hover         1 step      none    --     cursor pointer
#               darker
# focus-visible accent      none    2px    keyboard ring,
#                                  offset 2  moved with arrow keys
# active        2 steps     none    --     pressed
#               darker
# disabled      grey 3:1    none    none   not clickable,
#               on fill                     not announced
# loading       accent      none    --     spinner, label kept

7.4 Developer hand-off

The hand-off converts the design into buildable specifications. A good one is boring: complete, unambiguous, and checkable in the browser rather than in the mockup.

The complete spec, so nobody guesses

Figma's Dev Mode and similar tools read measurements straight off the frame, but the artifacts that matter are the ones the tool cannot produce: the spacing scale, the type scale, the token names, the state rules and the asset exports. A hand-off that names tokens (--space-3, --color-accent) instead of raw values lets the developer wire components to the system instead of pasting hex. If a developer has to measure padding off a screenshot, the design still has work left.

# Hand-off is complete when the developer never has to guess
# spacing   8pt rhythm; padding 8/16, gap 8, margin 24
# type      16px body / 20px lead / 25px h3, 1.6 leading
# colour    token names only, never raw hex in the frame
# radius    4px controls, 8px cards, 999px pills
# states    hover / focus / disabled specified per component
# assets    SVG icons + WebP images exported into the repo
# measure   Lighthouse run on the built page vs the budget

Design review runs in the browser

The mockup is a proposal; the browser is where the design is judged. Review at the extreme widths, on keyboard, at 200% zoom, in both themes, on a touch emulator — the states a static frame cannot show. The QA list is the same list every launch: containers do not overflow, focus is visible everywhere, contrast passes on real backgrounds, targets are 44px, and Lighthouse matches the budget.

# Launch QA - the design review that runs in the browser
# [ ] 320px, 768px, 1280px: no overflow, no dead gaps
# [ ] keyboard: tab through; ring visible; no focus traps
# [ ] zoom to 200%: text wraps, controls usable
# [ ] dark and light theme: tokens, not hard hex
# [ ] contrast of every text on its real background
# [ ] 44px targets on a touch emulator
# [ ] Lighthouse against the performance budget
# [ ] alt text on new images; page titles unique

7.5 Documentation and definition of done

A design system without documentation is a rumour: it lives in whichever designer's head knew it last. Documentation lives with the code — versioned, reviewed, generated from the same tree — and a posted definition of done closes the loop on every piece of design work.

Living documentation: versioned with the code

Docs that sit in a separate wiki quietly die; docs that ship in the same repository as the code change together. The token file is documentation. The component markdown is documentation. The changelog that says what changed and why is documentation. When a design line item accompanies its pull request, the docs page is generated from the same tree and cannot lie.

# Documentation lives with the code, or it lies
# /design
#   tokens.json        source of truth
#   components.md      anatomy and states per component
#   patterns.md        page-level recipes
#   changelog.md       what changed and why, dated
# Every design change ships with a PR, and the docs page is
# generated from the same tree as the code.

Definition of done for design work

A definition of done turns "is it done?" into a checklist with no opinions: matches the accepted wireframe, uses tokens, all states specified, both themes pass contrast, assets exported and compressed, documentation updated, reviewed in the browser. Work that clears the list is shippable; work that does not is not "almost done", it is not done. This is the same discipline as the design loop in chapter 1 — the last step of the loop is what makes the first one matter.

# Definition of done for design work
# [ ] matches the accepted wireframe and content plan
# [ ] tokens used; no ad-hoc hex, no ad-hoc spacing
# [ ] all states specified; keyboard and touch verified
# [ ] both themes pass contrast checks
# [ ] assets exported, sized, and compressed
# [ ] documented: components.md updated
# [ ] reviewed in the browser, not the mockup

The checklist is a gate, not a ritual. When a line is skipped, the ticket records the skip and the reason — a deliberate exception is a decision; an unreported one is a hole in the system.
