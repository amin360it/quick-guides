Welcome — How to Use This .NET 10 Desktop Guide

How this guide is organisedWinForms or WPF? Pick the right oneThe tooling you will use all course longWhat a .NET 10 desktop project looks like

Welcome to the C# and .NET 10 desktop guide, a hands-on course through the two Windows UI stacks that ship in the modern .NET SDK: WinForms and WPF. You will build real windows, learn the layout engines of both toolkits, wire up data binding, and finish with a chapter on packaging and deployment. Type out every code sample rather than pasting it; the muscle memory matters more than the copy.

This is a self-paced path through C#, WinForms and WPF on .NET 10. Everything here runs on Windows with the .NET SDK installed — no server, no browser, no internet connection required once the SDK is present.

How this guide is organised

The guide runs in three parts across eleven chapters plus a reference appendix. Modern C# comes first, because both toolkits are the same language. Then WinForms gets three chapters of its own, WPF gets six, and the last chapter covers data, packaging and shipping to real machines.

  • Part I (Ch. 1) — the language: value and reference types, nullable reference types, records, pattern matching, events and disposal.
  • Part II (Ch. 2–4) — WinForms: projects and forms, layout containers, data binding, events and background work.
  • Part III (Ch. 5–10) — WPF: XAML, dependency properties, the layout system, data binding, MVVM, theming, custom controls and animation.
  • Part IV (Ch. 11 + Appendix) — EF Core with SQLite, publishing and installers, diagnostics, plus a full decision table and cheat sheets.
  • Every chapter ends with exercises. Aim to build a small but complete app (a task or contact manager) in each toolkit rather than isolated snippets.

Read the WinForms chapters even if you only plan to ship WPF. WinForms is the yardstick most teams measure against, and knowing why its layout model is fiddly is what makes the WPF layout pass click.

WinForms or WPF? Pick the right one

Both toolkits are first-class in .NET 10 and share the same runtime, NuGet packages and language. They differ in philosophy, not in quality. WinForms is a retained-mode control tree you position in code; WPF is a retained-mode visual composition system you describe declaratively in XAML. The choice usually follows the age of the codebase and the shape of the design you need.

ConsiderationWinFormsWPF
UI definitionDesigners drag controls; XAML-like layout written directly into InitializeComponentHand-written XAML compiled by BAML
Layout modelPixel coordinates plus Dock, Anchor and layout panelsA real layout pass: measure, arrange, validate
StylingOwner-drawn controls and per-control propertiesStyles, templates, triggers, resource dictionaries
Data bindingBindingSource plus INotifyPropertyChangedFirst-class two-way binding with validation and converters
Best forInternal tools, data grids, quick line-of-business screens, existing codeRich, branded, animated, long-lived applications
Learning curveLow to start, high once layouts get complexHigher up front, much better ceiling afterwards

Rule of thumb: if the app is a grid over a database with a toolbar, choose WinForms. If the app needs theming, animation, custom visuals or a designer, choose WPF. If in doubt and the app is new, choose WPF.

Do not mix the two in one process unless you have a specific reason. A WindowsFormsHost inside WPF (or the reverse) is possible, but the two layout and DPI models disagree and every hosting bug costs more than rewriting the screen.

You only need a handful of tools, but you need them configured correctly. Visual Studio remains the best experience for WinForms, WPF and the XAML designer; Visual Studio Code plus the C# Dev Kit covers everything else. Hot Reload shortens the edit-build-run loop dramatically for both toolkits.

What a .NET 10 desktop project looks like

Both toolkits use the modern SDK-style project with a single .csproj file. There is no separate designer project and no COM registration. Target net10.0-windows to opt into the Windows desktop APIs, and set the output type so the SDK knows to produce a windowed executable rather than a console app.

<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>      <!-- WinExe = no console window -->
    <TargetFramework>net10.0-windows</TargetFramework>   <!-- TFM must include -windows -->
    <Nullable>enable</Nullable>                    <!-- nullable reference types on -->
    <ImplicitUsings>enable</ImplicitUsings>    <!-- no using System; boilerplate -->
    <UseWindowsForms>true</UseWindowsForms>      <!-- WinForms only -->
    <UseWPF>true</UseWPF>                            <!-- WPF only -->
  </PropertyGroup>

</Project>

A WinForms project sets UseWindowsForms and a WPF project sets UseWPF; the two can be combined but rarely should be. WinExe suppresses the console window that would otherwise flash on start.

A WPF project additionally produces App.xaml with an ApplicationDefinition entry, which the compiler reads to find the startup object. A WinForms project uses static void Main instead.

Both project types are Windows-only. .NET 10 will happily build them on Linux or macOS, but you cannot run them there. Cross-platform desktop means Avalonia or MAUI, which share some of the C# in this guide but none of the UI frameworks.

1 · C# Refresher for Desktop

Both toolkits are the same language, so chapter one covers the C# that desktop work leans on hardest: how memory is laid out for structs and classes, what nullable reference types actually promise, how records and object initialisers keep UI code short, how pattern matching removes switch sprawl, and how events plus IDisposable tie into component lifetimes.

You do not need to reread the whole language. You do need to reason precisely about value versus reference semantics, because binding, copy semantics and thread affinity all depend on it.

1.1 Value types vs reference types

A struct is copied when it is assigned; a class is referenced. That single difference explains why a struct cannot carry a change notification, why editing a bound property on a struct in a list silently does nothing, and why you should never pass a List<T> item around expecting the callee to mutate it. Structures live on the stack when local, inline in their container when stored in a collection; classes are always on the heap.

// struct = value semantics: assignment copies the bytes
public struct Point { public int X, Y; }

public sealed class Person { public string Name { get; set; } }

static void Demo()
{
    var a = new Point { X = 1, Y = 2 };
    var b = a;      // copy, not alias
    b.X = 99;
    // a.X is still 1

    var p = new Person { Name = "Ada" };
    var q = p;      // both point at one object
    q.Name = "Grace";
    // p.Name is now "Grace" too
}

Structs copy on assignment; classes share. Anything that must notify the UI of a change has to be a class, because a copied struct cannot raise an event back to its owner.

The same rule explains a classic desktop bug. Because a struct item retrieved from a List<T> is a copy, calling a mutating method on it changes nothing:

List<Point> points = [new Point { X = 1, Y = 1 }];

points[0].X = 5;               // compile error: cannot modify the return value
var p = points[0];    // take a copy first
p.X = 5;                      // legal, but the list is unchanged

A struct in a list hands you a copy, so mutations never reach the collection. Store mutable model types as classes and this class of bug disappears.

Default to class for anything bound to a UI, stored in a collection or implementing an interface. Reserve struct for small, immutable-ish value carriers such as a key, a point or a money amount.

1.2 Nullable reference types

With <Nullable>enable</Nullable>, the compiler tracks which reference-typed members may be null and refuses to dereference them without a check. For desktop work this matters more than usual, because half of all "object reference not set" crashes come from a control property, a view-model field or a selected grid row that nobody guarded.

public sealed partial class MainWindow : Window
{
    // non-nullable: caller must supply a value
    public required string Title { get; init; }

    // nullable: null is a legal value you must handle
    private Customer? _customer;

    private void Save()
    {
        if (_customer is null)
        {
            MessageBox.Show("Load a customer first.");
            return;
        }
        SaveCore(_customer);   // flow analysis knows it is not null
    }
}

Nullable reference types are a compile-time contract, not a runtime check. The annotation changes which code compiles; it never changes what the garbage collector does.

Desktop-specific null traps worth guarding explicitly: the SelectedItem of a list or grid before any row is selected, an optional service resolved from the container, a settings value read from disk, and any value returned by a converter.

Suppress warnings with ! only when you can prove the value is present. A null-forgiving operator in a desktop app is a deferred crash report, not a fix. Prefer is null guards or ?. at the call site.

1.3 Records, init and required members

A record is a class with compiler-generated value equality, a ToString, and an immutable-by-default shape. Combined with init accessors and required members, object initialisers become type-safe: the compiler will not let a view-model be constructed without its title. Records are ideal for the immutable DTOs that travel between your data layer and your UI.

// positional record: three properties, all init-only
public sealed record Customer(
    int Id,
    string Name,
    string Email);

// required + init: non-nullable and cannot be skipped
public sealed class EditCustomerViewModel
{
    public required int Id { get; init; }
    public required string Name { get; set; }
    public string Email { get; set; } = "";
}

// with-expression: shallow copy with selected changes
var updated = customer with { Name = "Ada Lovelace" };

Records give value equality and copy-on-change for free, so records are perfect for DTOs. Use ordinary classes for anything the UI binds two-way, because init setters cannot be written by a binding.

A WPF TextBox bound TwoWay to a property with an init accessor will fail at runtime: the binding needs a setter. Use init on records you construct, and plain get/set on anything the UI writes to.

1.4 Pattern matching and switch expressions

Modern C# replaces long if/else chains on typeof and GetType() with type and relational patterns, and replaces statement switches with expression switches. Desktop code is full of is checks on control types, selection states and dialog results, so these patterns shorten real code rather than demo code.

static string Describe(object? item) => item switch
{
    null                            => "nothing selected",
    string { Length: 0 }            => "empty text",
    string s                      => $"text: {s}",
    int i when i < 0                 => "negative number",
    DataGridViewRow row            => $"row {row.Index}",
    _                              => "unsupported"
};

// property patterns nest, so this reads as a shape
bool IsConnected(Socket s) => s is { Connected: true, Available: > 0 };

Pattern arms are evaluated top to bottom, so put the most specific arm first. Order arms from specific to general or the broad arm will swallow the rest.

Pattern matching also works with is not for negative checks, and with when for range logic. A common desktop use is validating a selected row before reading its cells.

// safe read: check the row, then the cell, then cast
if (grid.CurrentRow is not DataGridViewRow row) return;
if (row.Cells["Name"].Value is not string name) return;

Refresh(name);

A pattern is test that also binds a variable both checks and assigns in one pass, which is exactly the shape a validated read wants.

1.5 Events, delegates and IDisposable

Every control raises events, and an event is a multicast delegate: a list of handlers called in subscription order. The two mistakes desktop developers make are leaking handlers by subscribing without unsubscribing, and implementing IDisposable wrongly so that a native or GDI-backed resource is never released. Both show up as a memory leak that only appears after opening and closing a form a few hundred times.

// declare: the event name and delegate type
public event EventHandler<StatusChangedEventArgs>? StatusChanged;

// raise: the ?.Invoke pattern, guarded for null subscribers
protected void RaiseStatusChanged(string message) =>
    StatusChanged?.Invoke(this, new StatusChangedEventArgs(message));

Use ?.Invoke so an event with no subscribers is a no-op, and keep the raise inside a protected method so only the declaring class can fire it.

Because events are strong references, a long-lived subscriber keeps a short-lived publisher alive. The fix is to unsubscribe, or to subscribe weakly:

// pair subscribe and unsubscribe, and make the publisher disposable
public sealed partial class SettingsForm : Form, IDisposable
{
    private readonly AppState _state;

    public SettingsForm(AppState state)
    {
        _state = state;
        _state.ThemeChanged += OnThemeChanged;
    }

    private void OnThemeChanged(object? sender, ThemeEventArgs e) => BackColor = e.Background;

    public void Dispose()
    {
        _state.ThemeChanged -= OnThemeChanged;   // break the reference
        base.Dispose();
    }
}

An event subscription is a strong reference, so an unsubscribed handler keeps both objects alive. Always pair every += with a matching -= in the object’s own lifetime.

Unsubscribe from Form.Shown, TextChanged and static events such as Application.DragDrop in Dispose. Opening and closing a form in a loop is the fastest way to catch a leak you have not fixed.

Anything holding an unmanaged handle — a Graphics, a Font, a FileStream, a database context, a window handle — belongs behind IDisposable. Prefer using for short-lived objects:

using (var brush = new SolidBrush(Color.SteelBlue))
{
    e.Graphics.FillRectangle(brush, ClientRectangle);
}   // brush disposed here, even if FillRectangle throws

A using block disposes deterministically at the closing brace, which matters for GDI objects because the finaliser is too late to prevent a handle exhaustion crash.

Chapter two covers the mechanics of a WinForms application: how the project is created, what a Form really is, the difference between designer-generated code and the code you write, how controls are parented and found, how positioning survives a resize, and what the message loop underneath Application.Run does. Get these right and the rest of the toolkit is detail.

WinForms is a thin, mature wrapper over the Win32 windowing API. It is a retained-mode system: you build a tree of native window handles and the OS redraws them for you. Almost every WinForms design rule follows from that fact.

2.1 Creating a WinForms project

There are two project flavours: the classic Windows Forms App template that opens the visual designer, and the newer template that is designer-optional. Both produce the same files. Creating one takes a single dotnet new command, which is the fastest way to see exactly what the template generates.

# create a WinForms project targeting .NET 10 on Windows
dotnet new winforms -n Inventory.App -f net10.0

# add a companion class library for models and services
dotnet new classlib -n Inventory.Core -f net10.0
dotnet add Inventory.App reference Inventory.Core

# run it
dotnet run --project Inventory.App

The generated project contains a Form1.cs, a Form1.Designer.cs and a Program.cs. Everything the designer draws lands in the .Designer.cs partial.

Start with a three-project layout as soon as the app grows past a couple of screens:

ProjectContainsReferences
Inventory.CoreModels, domain rules, interfacesNothing
Inventory.AppForms, controls, view logic, composition rootCore
Inventory.TestsxUnit or NUnit testsCore

Keeping the UI project free of business rules is what makes the rules testable. A WinForms form is hard to unit test precisely because it drags Win32 and a message loop along with it.

2.2 The Form class and its lifecycle

A Form is a top-level window with a title bar, border and client area. Its lifecycle events fire in a fixed order, and hooking the wrong one is a common source of null-reference crashes. The order below is the single most useful thing to memorise in this chapter.

// order: ctor -> Load -> Shown -> (running) -> FormClosing -> FormClosed -> Dispose
public partial class MainForm : Form
{
    public MainForm()
    {
        InitializeComponent();          // build the control tree, always first
        Load += OnLoad;
        FormClosing += OnFormClosing;
    }

    private void OnLoad(object? sender, EventArgs e)
    {
        // controls exist and the window has a handle: safe to size things
        Width = Math.Max(Width, 900);
    }

    private void OnFormClosing(object? sender, FormClosingEventArgs e)
    {
        // last chance to prompt or cancel the close
        if (_dirty && MessageBox.Show("Discard changes?",
                "Unsaved", MessageBoxButtons.YesNo) != DialogResult.Yes)
        {
            e.Cancel = true;   // veto the close
        }
    }
}

Do real work in Load or Shown, never in the constructor: the client area is not laid out yet and ClientSize is unreliable before the handle exists.

Set StartPosition and MinimumSize in the constructor, not in Load. Window chrome is applied before Load, so these belong to construction time.

2.3 Designer code vs code-behind

Each form is split across two files. Form.Designer.cs is machine-written and regenerated whenever the designer saves; Form.cs is yours. Any logic you put in the designer file is lost the next time the designer rewrites it. Understanding the split is what lets you use the designer for layout and still write clean code.

// MainForm.Designer.cs -- generated, do not edit by hand
private void InitializeComponent()
{
    this.btnSave = new Button();
    // ...
    (this.btnSave).Location = new System.Drawing.Point(12, 12);
    (this.btnSave).Name = "btnSave";
    (this.btnSave).Text = "Save";
    // ...
    (this.btnSave).Click += new System.EventHandler(this.btnSave_Click);
    // ...
    ((System.ComponentModel.ISupportInitialize)(thisgrid)).BeginInit();
    // ...
}

// MainForm.cs -- yours; wire the designer event to a method here
private void btnSave_Click(object sender, EventArgs e) => SaveAll();

The designer wires Click to a method in your file. If you rename that method, the designer will regenerate a stub for you rather than fix the reference.

Never add logic to *.Designer.cs. The designer overwrites the entire file each time you save the form, so a validation routine placed there is deleted without warning.

2.4 The control tree and Controls collection

Every WinForms control has a Parent and a Controls collection; a form is the root of the tree. Children inherit nothing automatically — layout is explicit — so walking the tree by name is how code reaches into a designer-built form. Prefer the generated Fields over Controls.Find, and prefer containers with a Name over raw index access.

// strongly typed: the designer declares private fields for you
private readonly TextBox _nameBox = new() { Name = "nameBox" };

private void BuildUi()
{
    var panel = new TableLayoutPanel { Dock = DockStyle.Fill, ColumnCount = 2 };
    panel.Controls.Add(new Label { Text = "Name", AutoSize = true });
    panel.Controls.Add(_nameBox);
    Controls.Add(panel);
}

// by name: works on a designer-built form, returns null if absent
var grid = (DataGridView?)Controls["grid"];
var found = Controls.Find("grid", true);

// recursive walk: handy for applying a style to a whole form
static void SetTabOrder(Control parent, int next = 0)
{
    foreach Control c in parent.Controls
    {
        c.TabStop = next++ > 0;         // first control keeps no tab stop
        SetTabOrder(c, next);
    }
}

Controls form a tree via Parent/Controls. Use the designer-generated fields where they exist, because Controls.Find returns null and defers the failure to runtime.

Adding a control to a parent automatically removes it from its previous parent, so you never have to call Remove first. To move a control between forms, just re-add it.

2.5 Docking and anchoring

WinForms has no layout algorithm in the WPF sense. A control keeps the pixel rectangle you give it, and Dock and Anchor are the two levers that adjust that rectangle when the parent resizes. Docking is processed in reverse z-order, which makes stacking several docked panels surprising; anchoring is more predictable but requires you to set all four edges deliberately.

// dock: fill the parent, but leave a 60px status strip at the bottom
grid.Dock = DockStyle.Fill;
statusStrip.Dock = DockStyle.Bottom;
statusStrip.Height = 60;

// anchor: pin to all four edges so the box grows with the form
panel.Anchor = AnchorStyles.Top | AnchorStyles.Bottom
             | AnchorStyles.Left | AnchorStyles.Right;

// anchor on two opposite edges: stretches in one direction only
banner.Anchor = AnchorStyles.Left | AnchorStyles.Right;   // full width, fixed height

Docking fills the remaining space in reverse z-order, so the control with the highest z-index index docks first. Anchoring pins edges and preserves the original distance from them.

Order docked controls by sending the fill one to the back: select it in the designer and choose Send to Back. Anything you intend to Fill should be behind the strips that carve space out of it.

Never rely on a single Anchor value alone. If you set only Top | Left, the control floats in the top-left corner forever; the default Anchor is Top | Left, so forgetting to set it is easy.

2.6 Application.Run and the message loop

A WinForms application is a single-threaded message pump. Application.Run creates the main window, then blocks in a loop that pulls messages off a queue: paint, mouse, keyboard, timers and your own custom messages. That loop is why long work on the UI thread freezes the window, and why every blocking operation in chapter 4 must move off it.

internal static class Program
{
    [STAThread]                        // single-threaded apartment, required for OLE
    private static void Main()
    {
        ApplicationConfiguration.Initialize();     // DPI + theme defaults
        Application.Run(new MainForm());          // blocks until the form closes
    }
}

The Main method must be marked [STAThread]. The loop runs on this one thread, so any slow code you write there directly blocks repainting and input.

You can also run a form without blocking, and drive your own loop, which is how a single-process multi-form shell is built:

Application.EnableVisualStyles();
Application.SetCompatibleTextRenderingDefault(false);

var shell = new ShellForm();
shell.Show();                     // non-blocking
Application.Run();                // run with no main form; quit when all forms close

Application.Run(form) exits when that form closes; Application.Run() exits when the last form closes. The second form suits shell applications with several top-level windows.

ApplicationConfiguration.Initialize() is generated by the SDK and enables per-monitor DPI and visual styles correctly. Calling the older EnableVisualStyles by hand as well is redundant and can produce inconsistent results.

Absolute positioning is fine for a dialog and unworkable for a main window. The moment a user drags the edge, everything drifts unless you anchor, dock or place controls in a layout panel.

3.1 TableLayoutPanel

The table layout panel arranges children into a grid of rows and columns, each independently sized by SizeType in pixels, percentages or auto. It is the single most useful WinForms container: a form made of tables resizes cleanly and, critically, stays editable by a designer who did not write the code.

var layout = new TableLayoutPanel
{
    Dock = DockStyle.Fill,
    ColumnCount = 2,
    RowCount = 3,
    Padding = new Padding(8),
};

// two columns: a fixed label column and a star-sized field column
layout.ColumnStyles.Add(new ColumnStyle(SizeType.Absolute, 120));
layout.ColumnStyles.Add(new ColumnStyle(SizeType.Percent, 100));
layout.RowStyles.Add(new RowStyle(SizeType.AutoSize));
layout.RowStyles.Add(new RowStyle(SizeType.AutoSize));
layout.RowStyles.Add(new RowStyle(SizeType.Percent, 100));  // grid takes the rest

{

        AutoSize = true,

3.2 FlowLayoutPanel and SplitContainer

The flow panel lays children out left to right and wraps at the panel edge, which is ideal for a row of buttons that should reflow on narrow windows. 3.5 Dialogs and common windows

A dialog is a form shown with ShowDialog, which blocks the caller until it closes and carries a DialogResult back. There are also four ready-made dialogs that cover most needs — message box, file open, file save and folder browse — and one special case: a form shown with Show, which is modeless and non-blocking.

// the four stock dialogs

        MessageBoxButtons.YesNo, MessageBoxIcon.Question) == DialogResult.Yes) { }

{

    InitialDirectory = Environment.GetFolderPath(Environment.SpecialFolder.MyDocuments)

4.1 BindingSource and simple binding

WinForms binding always goes through a BindingSource, even when you do not know it. The binding source is a currency manager: it tracks the current position, exposes Current, mediates writes, and gives you a place to intercept changes. Binding a control straight to a list skips the current-item concept and breaks editing.

var source = new BindingSource { DataSource = customers };

grid.DataSource = source;                       // grid
nameBox.DataBindings.Add("Text", source, "Name", true);  // text box, two-way

// the current item is the row the user is on
nameBox.Text = ((Customer)source.Current).Name;

// filtering and sorting live on the binding source, not the grid
source.Filter = "IsActive = true";
source.Sort = "Name ASC";

// react to a change of current row
source.CurrentChanged += (object? _, EventArgs __) => ShowDetail((Customer)source.Current);

A BindingSource is the currency layer between your list and the controls. Bind every control that should follow the selected row to the same source, and they stay in step automatically.

DataBindings.Add takes a DataSourceUpdateMode. OnPropertyChanged writes after each keystroke; OnValidation writes when the field loses focus; OnLostFocus writes when focus leaves the control entirely.

4.2 INotifyPropertyChanged in practice

A control bound to a plain auto-property never learns that the property changed, so the screen goes stale. Implementing INotifyPropertyChanged on your model closes that gap. In WinForms the interface matters most for calculated properties and for values changed outside the binding, such as by a timer or a background result.

public sealed class Order : INotifyPropertyChanged
{
    private decimal _net;

    public event PropertyChangedEventHandler? PropertyChanged;

    public decimal Net
    {
        get => _net;
        set
        {
            if (_net == value) return;
            _net = value;
            OnPropertyChanged();                 // raises for "Net"
            OnPropertyChanged(nameof(Tax));       // and anything derived from it
        }
    }

    public decimal Tax => new decimal(Net * 0.2);

    private void OnPropertyChanged([System.Runtime.CompilerServices.CallerMemberName]
                       string? name = null) =>
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}

CallerMemberName supplies the property name automatically, so derived properties only need one extra call to notify their own dependents.

WinForms has a shortcut: DataBindings.Add with DataSourceUpdateMode.OnPropertyChanged pushes control edits into the object, but the object still has to raise the event to update the other controls. Notification is one-directional; you need it in both directions.

4.3 DataGridView editing

Grid editing happens in three phases: begin edit, commit edit, end edit. Each has a matching event, and the value is only written to the row when the cell commits. The trap is reading the cell while the editor is still open, which returns the old value. These events are also where you can reject a value before it lands.

// BEFORE the value reaches the row -- validate and cancel if it is bad
grid.CellValidating += (object? s, DataGridViewCellValidatingEventArgs e) =>
{
    if (grid.Columns[e.ColumnIndex].Name != "Quantity") return;
    if (e.FormattedValue is not string text || !int.TryParse(text, out var q) || q <= 0)
    {
        e.Cancel = true;                       // reject, cell reverts
        grid.Rows[e.RowIndex].ErrorText = "Enter a whole number above zero.";
    }
};

// AFTER the commit -- the new value is live, persist it here
grid.CellValueChanged += (object? s, DataGridViewCellEventArgs e) =>
{
    if (e.RowIndex < 0) return;
    if (grid.Rows[e.RowIndex].DataBoundItem is Order order) Save(order);
};

grid.CurrentCellDirtyStateChanged += (object? _, EventArgs __) =>
{
    if (grid.IsCurrentCellDirty)
        grid.CommitEdit(DataGridViewDataErrorContexts.Commit);
};

Validate in CellValidating and persist in CellValueChanged. Committing the edit explicitly in CurrentCellDirtyStateChanged makes a new row appear as soon as the last cell is filled.

Inside a CellValueChanged handler, DataBoundItem is the row’s model object but the change may not be in the database yet. Batch your saves and wrap them in one transaction rather than writing per keystroke.

4.4 Validating events

WinForms validates at two moments. Control-level events (Validating, Validated) fire when the control loses focus, so the control may still show a rejected value. Form-level Validating fires when validation is requested, which is exactly what the OK button of a dialog should trigger before it closes.

// control level: fires as focus leaves this control
emailBox.Validating += (object? _, CancelEventArgs e) =>
{
    e.Cancel = !MailAddress.TryCreate(emailBox.Text, out var _);   // keep focus here
    emailBox.BackColor = e.Cancel ? Color.MistyRose : SystemColors.Window;
};
emailBox.Validated += (object? _, EventArgs __) =>
    emailBox.BackColor = SystemColors.Window;

// form level: the OK button calls this before it closes
okButton.Click += (object? _, EventArgs __) =>
{
    CancelEventArgs cancel = default;
    ValidateChildren();                        // runs every child Validating handler
    if (!Validate() || string.IsNullOrWhiteSpace(nameBox.Text))
    {
        DialogResult = DialogResult.None;       // do NOT close the dialog
        return;
    }
    DialogResult = DialogResult.OK;            // OK accepts, dialog closes
};

Setting e.Cancel = true in Validating keeps focus in the control. On a dialog’s OK button, set DialogResult = DialogResult.None to veto the close until validation passes.

AutoValidate = AutoValidate.EnableAllowFocusChange makes the form run control validation when focus moves, which is the behaviour users expect. Set it in the designer rather than calling Validate by hand everywhere.

4.5 async/await and the async void trap

The UI thread must return to the message loop frequently, so all slow work belongs on a thread-pool thread. C# gives you await, which resumes on the original synchronisation context, so the part after the await is safely back on the UI thread. But an async void event handler has no caller to return to and no way to await it, which is why it is dangerous.

// DANGEROUS: the compiler cannot track or await this. A thrown exception
// after the first await crashes the process with no stack trace.
private async void btnLoad_Click(object sender, EventArgs e)
{
    UseWaitCursor = true;
    var rows = await _repo.LoadAsync();   // OK
    grid.DataSource = rows;                          // back on the UI thread, OK
    UseWaitCursor = false;                     // never runs if the await throws
}

// SAFE: the handler is synchronous, the work is a task you can await
private async void btnLoad_Click(object sender, EventArgs e) =>
    _ = LoadAsync();                          // fire and forget, but the work is safe

private async Task LoadAsync()
{
    try
    {
        UseWaitCursor = true;
        var rows = await _repo.LoadAsync().ConfigureAwait(false);
        grid.DataSource = rows;               // ConfigureAwait(false) needs an explicit hop back
    }
    catch (Exception ex)
    {
        MessageBox.Show(this, ex.Message, "Load failed",
                        MessageBoxButtons.OK, MessageBoxIcon.Error);
    }
    finally { UseWaitCursor = false; }
}

In WPF you bind a command instead, so the async method is async Task and the framework awaits it. In WinForms an event handler must be void, so wrap the real work in an async Task method and keep the try/catch/finally there.

Never let an exception escape an async void method. It is rethrown on the synchronisation context with no caller to catch it, so it terminates the application. Put the body in an async Task method and handle errors there.

4.6 BackgroundWorker vs Task.Run

Two ways to leave the UI thread. BackgroundWorker is the older WinForms-specific type with explicit DoWork, ProgressChanged and RunWorkerCompleted events, and it marshals progress back to the UI thread for you. Task.Run plus async/await is the modern, general-purpose answer and is what new code should use.

// modern: Task.Run plus IProgress, with real cancellation
private readonly CancellationTokenSource _cts = new();

private async void btnExport_Click(object sender, EventArgs e) =>
{
    var progress = new Progress<int>(p => statusLabel.Text = $"{p}%");
    btnCancel.Enabled = true;

    try
    {
        int written = await Task.Run(() => Export(_rows, progress, _cts.Token));
        statusLabel.Text = $"Wrote {written} rows.";
    }
    catch (OperationCanceledException) { statusLabel.Text = "Cancelled."; }
    finally { btnCancel.Enabled = false; }
}

private static int Export(IEnumerable<Order> rows, IProgress<int> progress, CancellationToken token)
{
    int n = 0, total = rows.Count();
    foreach (var row in rows)
    {
        token.ThrowIfCancellationRequested();
        WriteRow(row);
        progress.Report(++n * 100 / total);
    }
    return n;
}

private void btnCancel_Click(object s, EventArgs e) => _cts.Cancel();

Task.Run moves the work off the UI thread, Progress<T> marshals updates back safely, and a CancellationToken makes cancellation cooperative. All three belong in any long-running desktop operation.

5 · WPF Fundamentals

5.1 XAML syntax and XML namespaces5.2 The visual tree and the logical tree5.3 Application, Window and Page5.4 Why WPF differs from WinForms5.5 The WPF application lifecycle

WPF is a completely different idea from WinForms, and the shift is mostly conceptual rather than syntactic. You stop positioning controls and start describing a visual tree; you stop writing event handlers and start binding properties to data. This chapter establishes the XAML syntax, the two trees WPF maintains, the three application objects, and the lifecycle that replaces Application.Run.

WinForms gives you a window and a bag of controls. WPF gives you a scene graph, a styling system and a binding engine, and the window is just one node in it.

5.1 XAML syntax and XML namespaces

XAML is XML with compiler support: element names resolve to CLR types, attribute names resolve to properties, and the reserved x: prefix reaches language features rather than an object. The default namespace points at the WPF presentation assembly, which is why Button needs no prefix but System.Windows.Controls.Button would.

<Window x:Class="Inventory.App.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:vm="clr-namespace:Inventory.App.ViewModels"
        Title="Inventory" Height="600" Width="900">

    <Grid Margin="12">
        <TextBlock Text="Name" VerticalAlignment="Center" />
        <TextBox   x:Name="nameBox" Height="24" />
        <Button    Content="Save" Click="OnSave" IsDefault="True" />
    </Grid>
</Window>

The default namespace is the WPF presentation assembly, so common controls need no prefix. x:Class links the XAML to its code-behind partial class, and xmlns:vm exposes your own view-models for use as element types.

XAML also has a shorthand for element content and property elements, both of which you meet constantly:

<!-- content property shorthand: Button.Content, TextBlock.Text -->
<Button Content="Save" />
<Button>Save</Button>

<!-- property element syntax: needed for attached properties with dots,
     or any property whose value is a complex object -->
<Grid>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="120" />
        <ColumnDefinition Width="*" />
    </Grid.ColumnDefinitions>
</Grid>

<!-- markup extension: curly-brace syntax, evaluated by the parser -->
<TextBlock Text="{Binding Path=Title}" FontSize="{StaticResource TitleFontSize}" />

<!-- escape a literal brace with ^^ -->
<TextBlock Text="{}{not a binding}" />

Shorthand assigns the type’s content property. Property elements handle collections and dotted attached properties, and curly braces mark a markup extension. Write {} to start a literal string instead.

Every XAML file needs a matching partial class in a code-behind file, and the build fails with a confusing message if the namespace does not match. If a XAML file will not compile, check the x:Class namespace first.

5.2 The visual tree and the logical tree

WPF keeps two trees for every element. The logical tree is the structure you wrote in XAML, the one bindings and resources follow. The visual tree is the expanded render tree including the internal parts of every control template and adorners. Styles, triggers, resources and inheritance walk the logical tree; rendering, hit testing and layout walk the visual tree.

<!-- LOGICAL tree: what you wrote -->
ItemsControl
  ItemTemplate
    TextBlock   (bound to the item)

<!-- VISUAL tree: what WPF actually draws, expanded from the template -->
ItemsControl
  Border        (from the ItemsControl default template)
    ScrollViewer
      Panel
        ContentPresenter
          Border
            Grid
              TextBlock  (your template's leaf)

A single ItemsControl in your XAML becomes a chain of seven or more real elements in the visual tree. The logical tree stays readable; the visual tree is what costs you layout passes.

Use VisualTreeHelper to walk the visual tree when you need a render-level detail such as the actual TextBlock inside a ComboBox. For data questions, walk the logical tree through FrameworkElement.DataContext instead.

5.3 Application, Window and Page

Three objects define the shape of a WPF app. Application is the process-level singleton holding shared resources and the startup URI. Window is a top-level, chrome-bearing window that owns a ContentControl. Page is the same content without chrome, designed to be hosted inside a frame for navigation.

<!-- App.xaml : the process-level resources and startup point -->
<Application x:Class="Inventory.App.App"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             StartupUri="MainWindow.xaml">
    <Application.Resources>
        <ResourceDictionary>
            <ResourceDictionary.MergedDictionaries>
                <ResourceDictionary Source="Themes/Colors.xaml" />
                <ResourceDictionary Source="Themes/Controls.xaml" />
            </ResourceDictionary.MergedDictionaries>
        </ResourceDictionary>
    </Application.Resources>
</Application>

Shared resources belong in App.xaml so every window can reach them. StartupUri names the first window, and merged dictionaries let you split a theme across files.

Hosting pages for navigation is a frame with a content presenter. This is the shell used in chapter 9:

<Window ...>
    <DockPanel>
        <ListBox DockPanel.Dock="Left" Width="180"
                 ItemsSource="{Binding Pages}"
                 SelectedItem="{Binding CurrentPage, Mode=TwoWay}" />
        <Frame Content="{Binding CurrentPage}" />
    </DockPanel>
</Window>

A Frame hosts Page instances and keeps a back-stack journal. Bind its Content to a page object and navigation becomes a property assignment.

5.4 Why WPF differs from WinForms

The same four goals — show text, take input, lay out children, react to user actions — are reached through different abstractions. In WinForms you set properties and handle events; in WPF you set properties that are targeted at other properties and let the binding engine push values. That indirection is the whole reason WPF can theme and animate without your code knowing.

ConcernWinFormsWPF
PositionYou set pixel coordinates or use docking and anchoringYou declare relationships; the layout system computes pixels

5.5 The WPF application lifecycle

There is no Application.Run call to write. The SDK generates the entry point from App.xaml, creates the Application, raises four events and then shows the startup window. The two events you actually use are OnStartup for composition and OnExit for shutdown work.

public partial class App : Application
{
    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);

        // global exception handlers: last line of defence, log then continue
        DispatcherUnhandledException += (object? s, DispatcherUnhandledExceptionEventArgs a) =>
        {
            Log.Fatal(a.Exception);
            MessageBox.Show("An unexpected error occurred. Details were written to the log.",
                            "Error", MessageBoxButton.OK, MessageBoxImage.Error);
            a.Handled = true;      // keep the app alive
        };

        // replace StartupUri with an explicit, testable startup path
        var window = new MainWindow { DataContext = new MainViewModel(AppServices.Build()) };
        MainWindow = window;
        window.Show();
    }

    protected override void OnExit(ExitEventArgs e)
    {
        (_services as IDisposable)?.Dispose();
        base.OnExit(e);
    }
}

Override OnStartup to do work before the window appears, and OnExit to dispose services. Deleting StartupUri and showing the window yourself gives you a composition root you can drive from a test.

6.1 Dependency properties

A dependency property is stored by the WPF property system rather than as a field on the object, and that indirection buys four things: change notification for free, inheritance, styling and animation. A normal CLR property can be animated and styled by wrapping it in a dependency property; if you only need notification, INotifyPropertyChanged is still lighter.

public class Badge : Control
{
    // 1. the metadata that describes the property and its default
    public static readonly DependencyProperty CountProperty =
        DependencyProperty.Register(
            name: "Count",                     // the CLR property name
            propertyType: typeof(int),                 // the value type
            ownerType: typeof(Badge),              // who declares it
            defaultValue: 0,                       // the default
            validateValueCallback: new ValidateValueCallback(IsNonNegative),
            propertyChangedCallback: new OnCountChanged);  // change hook

    // 2. the CLR wrapper that the rest of your code uses
    public int Count
    {
        get => (int)GetValue(CountProperty);
        set => SetValue(CountProperty, value);
    }

    private static bool IsNonNegative(object value) => (int)value >= 0;

    private static void OnCountChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
        => ((Badge)d).OnVisualCountChanged();
}

A dependency property is declared with DependencyProperty.Register and wrapped in a CLR property. The metadata callbacks let you reject bad values and react to changes without a setter body.

Three metadata flags decide how a dependency property behaves, and choosing the wrong one causes subtle bugs:

6.2 Attached properties

An attached property is a dependency property registered by one type but set on another. Grid.Row is declared by Grid and set on a Button; Canvas.Left and TextBlock.Text work the same way. This is how a container decorates its children without those children knowing it exists.

<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto" />
        <RowDefinition Height="*" />
        <RowDefinition Height="Auto" />
    </Grid.RowDefinitions>

    <!-- Grid.Row is a property of Grid, set on a Button -->
    <Button Grid.Row="0" Content="Toolbar" />
    <ListView Grid.Row="1" />
    <StatusBar Grid.Row="2" />
</Grid>

<!-- read one from code: GetValue works on any DependencyObject -->
<int> row = (int)button.GetValue(Grid.RowProperty);

An attached property is registered by one type and set on another, which is how a container positions children that know nothing about it. The dotted XAML syntax resolves to OwnerType.PropertyNameProperty.

This is also the extension point for behaviours. A static helper class that registers an attached property can attach behaviour to any control in XAML without modifying the control itself — the pattern developed in chapter 10.

6.3 Markup extensions

A markup extension is evaluated by the XAML parser rather than stored as a literal. Curly braces mark one, and the two you will use constantly are Binding (re-evaluated when the source changes) and the resource lookups (resolved once). The reserved prefixes below cover almost all real XAML.

<TextBlock Text="{Binding Title}" />                        <!-- live, re-evaluates -->
<TextBlock Text="{Binding Path=Customer.Name, Mode=OneWay}" />
<TextBlock Text="{Binding Title, StringFormat='Total: {0:C}'}" />

<TextBlock Text="{StaticResource BodyFontSize}" />        <!-- resolved once -->
<TextBlock Foreground="{DynamicResource ThemeBrush}" />   <!-- resolved every time -->
<TextBlock Text="{x:Static SystemColors.ControlTextBrush}" />

<Window Title="{Binding RelativeSource={RelativeSource AncestorType=Window},
                        Path=Name}" />
<Slider Value="{Binding Source={x:Reference slider}, Path=Value,
                       Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}" />

<ItemsControl ItemsSource="{Binding Rows}">
    <ItemsControl.Items>
        <x:Array Type="sys:String">
            <sys:String>alpha</sys:String>
            <sys:String>beta</sys:String>
        </x:Array>
    </ItemsControl.Items>
</ItemsControl>

{Binding} tracks its source; {StaticResource} resolves once; {DynamicResource} re-resolves on every change and is what makes runtime theming possible at a small performance cost.

6.4 ResourceDictionary files

Resources are looked up by walking up the element and logical tree, then out to the application and finally the system. A ResourceDictionary is the file-based container, and MergedDictionaries let you compose several at one scope. Splitting a theme by concern keeps each file readable.

<!-- Themes/Colors.xaml -->
<ResourceDictionary xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">

    <SolidColorBrush x:Key="SurfaceBrush"  Color="#FFFFFF" />
    <SolidColorBrush x:Key="TextBrush"     Color="#1A1A1A" />
    <sys:Double x:Key="CornerRadius" xmlns:sys="clr-namespace:System;assembly=System.Runtime">4</sys:Double>
</ResourceDictionary>

<!-- Themes/Controls.xaml : merged dictionaries compose the theme -->

    <ResourceDictionary.MergedDictionaries>
        <ResourceDictionary Source="/Inventory.App;component/Themes/Colors.xaml" />
        <ResourceDictionary Source="Buttons.xaml" />
    </ResourceDictionary.MergedDictionaries>

    <Style x:Key="PrimaryButton" TargetType="Button">
        <Setter Property="Background" Value="{StaticResource AccentBrush}" />
        <Setter Property="Padding" Value="14,6" />
    </Style>

A resource dictionary holds keyed objects such as brushes, styles, geometries and converters. Merged dictionaries compose several files at one scope, which is how a theme stays split by concern.

Lookup order matters: an element’s own resources win, then its ancestors, then the window, then App.xaml, then the theme dictionaries. Define a key once at application level and override it locally when a screen needs something different.

A StaticResource referencing a key defined later in the same dictionary fails at load time, because static lookup is not deferred. If you must forward-reference, use DynamicResource.

6.5 Styles, triggers and ControlTemplate

A Style sets property values for any element of a target type, without touching that element’s own markup. Triggers add conditional behaviour, and a ControlTemplate replaces the visual composition of a control entirely. Together they are the difference between an app you can retheme and one you cannot.

<Style x:Key="CardHeading" TargetType="TextBlock">
    <Setter Property="FontSize" Value="18" />
    <Setter Property="FontWeight" Value="SemiBold" />
    <Setter Property="Foreground" Value="{StaticResource TextBrush}" />
    <Setter Property="Margin" Value="0,0,0,8" />

    <!-- value triggers: fire when a property equals a value -->
    <Style.Triggers>
        <Trigger Property="IsEnabled" Value="False">
            <Setter Property="Opacity" Value="0.5" />
        </Trigger>
        <DataTrigger Binding="{Binding IsOverdue}" Value="True">
            <Setter Property="Foreground" Value="{StaticResource DangerBrush}" />
        </DataTrigger>
        <EventTrigger RoutedEvent="TextBlock.MouseEnter">
            <Setter TargetName="Root" Property="Cursor" Value="Hand" />
        </EventTrigger>
    </Style.Triggers>
</Style>

<!-- implicit style: applies to every element of the type in scope -->
<Style TargetType="TextBox">
    <Setter Property="Padding" Value="6,4" />
    <Setter Property="Margin" Value="0,0,0,8" />
</Style>

<!-- a control template rebuilds the visual tree of a Button -->
<Style TargetType="Button">
    <Setter Property="Template">
        <Setter.Value>
            <ControlTemplate TargetType="Button">
                <Border x:Name="Root" Background="{TemplateBinding Background}"
                        CornerRadius="6" Padding="{TemplateBinding Padding}">

</Style>

A style sets property values, triggers react to conditions and a control template replaces the visual composition. TemplateBinding is what lets a template keep following the control’s own properties.

BasedOn lets a style inherit from another, so you can define a base look and a handful of variations. Combined with implicit styles this keeps a theme DRY without a code-generated theme file.

These three are constantly confused because all three control appearance. 7 · The WPF Layout System

7.1 Measure, arrange and validate7.2 Grid, GridSpan and RowSpan7.3 StackPanel, DockPanel, WrapPanel, Canvas7.4 Star sizing and the Grid choice guide7.5 Margin, padding and layout rounding

WPF runs a two-pass layout algorithm, and once you know the pass names, every layout bug becomes a question you can answer. Grid is the workhorse, star sizing is what makes a window resize sensibly, and the five stock panels each have one situation they are good at. This chapter is the practical layout reference for the rest of the guide.

7.1 Measure, arrange and validate

Layout runs in three stages. Measure asks each element how much space it wants, bottom-up, producing a desired size. Arrange gives each element the space it gets, top-down. Validate re-runs the arrangement of anything that was clipped or invalidated, catching most layout exceptions that would otherwise be silent.

public sealed class Spacer : FrameworkElement
{
    // called bottom-up: report the size you want for the offered space
    protected override Size MeasureOverride(in Size available)
    {
        var desired = new Size(100, 24);
        MeasureOverride(available);                 // measure children yourself
        return desired;
    }

    // called top-down: you are given the final slot; arrange children
    protected override void ArrangeOverride(in Size finalSize)
    {
        ArrangeOverride(finalSize);
        // clip if a child escaped its slot
    }
}

Measure asks bottom-up how much space is wanted; arrange hands out the final rectangles top-down. An infinite available size means "I do not care about your size".

When a custom element misbehaves, the fix is almost always in MeasureOverride. If you return new Size(0,0) the element is invisible; if you return an infinite size the parent will complain. Measure children before you return, or layout silently does nothing.

7.2 Grid, GridSpan and RowSpan

The grid divides its client area into rows and columns you define, then places children into cells by index. Every other panel is a special case of this, which is why Grid is the default answer for anything non-trivial. Spanning lets a cell occupy several rows or columns, which is how you build a form with a label column and a spanning action bar.

<Grid Margin="16">
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto" />          <!-- sized to content -->
        <RowDefinition Height="Auto" />
        <RowDefinition Height="*" />          <!-- takes the leftover space -->
        <RowDefinition Height="Auto" />
    </Grid.RowDefinitions>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="120" />        <!-- fixed pixel width -->
        <ColumnDefinition Width="*" />          <!-- proportional share -->
    </Grid.ColumnDefinitions>

    <TextBlock Grid.Row="0" Grid.Column="0" Text="Customer" VerticalAlignment="Center" />
    <TextBox   Grid.Row="0" Grid.Column="1" Text="{Binding Name, UpdateSourceTrigger=PropertyChanged}" />

    <TextBlock Grid.Row="1" Grid.Column="0" Text="Notes" VerticalAlignment="Top" />
    <TextBox   Grid.Row="1" Grid.Column="1" Text="{Binding Notes}"
               AcceptsReturn="True" Height="80" VerticalContentAlignment="Top" />

    <!-- star row: the list fills the remaining height -->
    <ListView  Grid.Row="2" Grid.ColumnSpan="2" ItemsSource="{Binding Orders}" />

    <!-- spanning action bar across both columns -->
    <StackPanel Grid.Row="3" Grid.ColumnSpan="2" Orientation="Horizontal"
                HorizontalAlignment="Right" Margin="0,12,0,0">
        <Button Content="Cancel" Margin="0,0,8,0" />
        <Button Content="Save" IsDefault="True" Style="{StaticResource PrimaryButton}" />
    </StackPanel>
</Grid>

Rows and columns are sized with pixel, Auto or star values. Grid.ColumnSpan and Grid.RowSpan let one element occupy several cells, and a single star row is how a grid fills the remaining height.

7.3 StackPanel, DockPanel, WrapPanel, Canvas

Four stock panels cover the remaining cases. StackPanel is a single-direction line that never wraps. DockPanel pins children to edges in order, with the last child filling. WrapPanel flows and wraps. Canvas gives absolute positions and ignores layout entirely.

<!-- StackPanel: one axis, no wrapping, infinite measure extent -->
<StackPanel Orientation="Horizontal" Spacing="8">
    <Button Content="Open" />
    <Button Content="Save" />
    <CheckBox Content="Overwrite" />
</StackPanel>

<!-- DockPanel: children dock in declaration order, last child fills -->
<DockPanel LastChildFill="True">
    <Menu DockPanel.Dock="Top" />
    <StatusBar DockPanel.Dock="Bottom" />
    <ListBox DockPanel.Dock="Right" Width="180" />
    <Grid />                                <!-- fills what is left -->
</DockPanel>

<!-- WrapPanel: flows and wraps at the edge -->
<WrapPanel ItemWidth="96" Orientation="Horizontal">
    <RadioButton Content="Day" GroupName="Range" />
    <RadioButton Content="Week" GroupName="Range" />
    <RadioButton Content="Month" GroupName="Range" />
</WrapPanel>

<!-- Canvas: absolute coordinates, never re-laid out -->
<Canvas Height="120">
    <Ellipse Canvas.Left="10" Canvas.Top="10" Width="48" Height="48" Fill="#4C8BF5" />
    <TextBlock Canvas.Left="70" Canvas.Top="24" Text="Overlay" />
</Canvas>

StackPanel is a non-wrapping line, DockPanel pins children in declaration order with the last child filling, WrapPanel flows and wraps, and Canvas ignores layout for absolute positioning.

StackPanel gives its children infinite measure extent along its axis, so a StackPanel inside a horizontally scrolling ScrollViewer works while the same panel vertically will clip rather than scroll. Reach for WrapPanel or a star-sized Grid when the content is variable-length.

7.4 Star sizing and the Grid choice guide

Star sizing is the mechanism that makes WPF layouts resize correctly. A row sized * receives an equal share of whatever space the fixed and auto siblings did not claim. 2* receives twice the share of *. Mixing pixel, auto and star rows is how a window with a fixed toolbar and a filling list is expressed declaratively.

<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="40" />        <!-- fixed toolbar -->
        <RowDefinition Height="Auto" />      <!-- sized to its content -->
        <RowDefinition Height="2*" />        <!-- twice the share of 1* -->
        <RowDefinition Height="1*" MinHeight="80" />
    </Grid.RowDefinitions>
</Grid>

<!-- three equal columns with a proportional middle -->
<Grid>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="1*" MinWidth="120" />
        <ColumnDefinition Width="2*" MinWidth="200" />
        <ColumnDefinition Width="1*" MinWidth="120" />
    </Grid.ColumnDefinitions>
</Grid>

Star rows split the leftover space in proportion, so 2* gets twice what 1* gets. MinHeight and MinWidth keep a pane usable when the window shrinks too far.

7.5 Margin, padding and layout rounding

WPF uses device-independent pixels at 96 DPI by default, so a value of 12 means twelve logical units regardless of the monitor. A one-pixel BorderThickness stays sharp because the system rounds to whole device pixels, and that rounding is why half-pixel values cause fuzzy edges. Margins create space outside an element; padding creates space inside it.

<TextBox Margin="0,0,0,8" Padding="6,4" />              <!-- stack-friendly gaps -->
<Border BorderBrush="#DDDDDD" BorderThickness="1" CornerRadius="4" Padding="12">
    <TextBlock Text="Card body" TextWrapping="Wrap" />
</Border>

<!-- avoid half pixels: they round inconsistently and look blurred -->
<Rectangle Width="100" Height="100" />          <!-- fine -->
<Rectangle Width="100.5" Height="100.5" />      <!-- renders uneven at some scales -->

<!-- uniform margin shorthand -->
<Border Padding="16" Margin="16" />

WPF units are device-independent pixels at 96 DPI by default. Keep to whole numbers, use margin for gaps between elements and padding for space inside them.

Set spacing on the children rather than on the panel. A stack of children each with a bottom margin stays correct when you insert a new child, whereas a panel margin has to be recomputed every time.

Data binding is the mechanism that makes WPF different from WinForms, and this chapter covers all of it. You will raise change notifications, expose behaviour as commands, keep collections live, choose the right binding mode, convert values, validate input and keep the UI responsive with large data sets. 8.1 INotifyPropertyChanged

A binding is a subscription: the target listens to the source for a property-changed notification and updates itself. Without notification, bindings still work once, when the data context is first assigned. Implementing INotifyPropertyChanged on your view-model is what makes them live.

public abstract class ObservableObject : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected bool SetProperty<T>(ref T field, T value, [in System.Runtime.CompilerServices.CallerMemberName] string? name = null)
    {
        if (EqualityComparer<T>.Default.Equals(field, value)) return false;
        field = value;
        OnPropertyChanged(name);
        return true;
    }

    protected void OnPropertyChanged(string? name) =>
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}

public sealed class CustomerViewModel : ObservableObject
{
    private string _name = "";

    public string Name
    {
        get => _name;
        set => SetProperty(ref _name, value);   // also raises "Name"
    }
}

The setter compares first and raises the event only on a real change, which keeps the binding engine from looping. CallerMemberName removes the need to pass the property name by hand.

The DataContext is inherited down the logical tree, so a binding without a path targets the nearest DataContext. This is why a TextBox in a data template binds to the item, and a TextBox in a window binds to the window’s view-model.

<TextBox Text="{Binding}" />                              <!-- binds to the whole DataContext -->
<TextBox Text="{Binding Name}" />                      <!-- Name on the DataContext -->
<TextBox Text="{Binding Customer.Name}" />              <!-- nested path -->
<TextBox Text="{Binding DataContext.Customer.Name,
                  RelativeSource={RelativeSource AncestorType=Window}}" />

A bare {Binding} targets the current DataContext. Paths walk into nested properties, and RelativeSource AncestorType reaches the window when you are several levels down.

8.2 ICommand and button binding

An ICommand pairs a method with the condition that says whether it may run, and WPF queries that condition automatically. A button bound to a command disables itself, blocks double-clicks, and needs no IsEnabled binding. This is how WPF keeps the view declarative instead of drowning in click handlers.

<Button Content="Save" Command="{Binding SaveCommand}" />
<Button Content="Delete" Command="{Binding DeleteCommand}" />

<!-- in the view-model -->
private readonly RelayCommand _saveCommand;
public RelayCommand SaveCommand => _saveCommand;

public CustomerViewModel()
{
    _saveCommand = new RelayCommand(
        execute: Save,                                  // what to do
        canExecute: () => !_isSaving && IsValid);    // may it run right now
}

private void Save()
{
    _isSaving = true;
    SaveCommand.NotifyCanExecuteChanged();    // WPF re-queries the condition
    _repo.Save(_customer);
    _isSaving = false;
    SaveCommand.NotifyCanExecuteChanged();
}

A bound button asks CanExecute whenever it is enabled state could have changed, so you only need NotifyCanExecuteChanged after mutating something the condition depends on.

Call NotifyCanExecuteChanged from inside the property setter of anything the condition reads. Then enabling and disabling is automatic and you never forget the call.

8.3 ObservableCollection

A plain List<T> raises no events when items are added, so an ItemsControl bound to it never updates. ObservableCollection<T> raises collection-changed notifications, and the items control adds and removes rows live. This is the difference between a list that works and one that silently does nothing after the first load.

public sealed class CustomersViewModel : ObservableObject
{
    public ObservableCollection<Customer> Customers { get; } = new();

    private Customer? _selected;
    public Customer? Selected
    {
        get => _selected;
        set { if (SetProperty(ref _selected, value)) OnPropertyChanged(nameof(CanDelete)); }
    }

    public bool CanDelete => Selected is not null;

    public void Add(Customer c) => Customers.Add(c);
    public void RemoveSelected()
    {
        if (Selected is null) return;
        Customers.Remove(Selected);
        Selected = null;
    }
}

ObservableCollection<T> raises notifications on add, remove and replace, so the bound ItemsControl updates itself. Replacing a whole list with a new one requires raising PropertyChanged yourself.

ObservableCollection sends a notification per item, so adding 50,000 rows one at a time re-renders 50,000 times. Add them to a plain List first, assign the list once, or use a bulk-loading collection if the data set is large.

8.4 Binding modes

The binding mode decides which direction values flow. The default for TextBox.Text is two-way; for everything else it is one-way. Getting this wrong is the usual cause of a text box that updates the model but never updates itself, or a slider that snaps back.

<TextBlock Text="{Binding Name}" />                    <!-- OneWay by default -->

Leave UpdateSourceTrigger at its default of LostFocus unless the model genuinely needs per-keystroke validation. Writing the source on every keystroke re-runs validation and conversion on the whole path, and it is the most common cause of a sluggish data form.

8.5 Converters and MultiBinding

A value converter turns a bound value into something the target can display, and back again. IValueConverter handles one value, IMultiValueConverter handles several and returns one, and both are declared in XAML or code and applied with the Converter property. Never put formatting logic in a view-model when a converter will do.

public sealed class InverseBoolConverter : IValueConverter
{
    // Convert: model -> view
    public object? Convert(object value, Type targetType, object? parameter, CultureInfo culture)
        => value is bool b ? !b : false;

    // ConvertBack: view -> model (return Binding.DoNothing to block writes)
    public object? ConvertBack(object value, Type targetType, object? parameter, CultureInfo culture)
        => value is bool b ? !b : false;
}

public sealed class FullNameConverter : IMultiValueConverter
{
    public object Convert(object[] values, Type t, object? p, CultureInfo c)
    {
        var first  = values.ElementAtOrDefault(0) as string;
        var last   = values.ElementAtOrDefault(1) as string;
        return $"{first} {last}".Trim();
    }

    public object[] ConvertBack(object value, Type[] t, object? p, CultureInfo c)
        => throw new NotSupportedException();
}

IValueConverter maps one value both ways; IMultiValueConverter combines several into one. Return Binding.DoNothing from ConvertBack when a target should never write back.

<TextBlock>
    <TextBlock.Resources>
        <conv:InverseBoolConverter x:Key="Inverse" />
        <conv:FullNameConverter    x:Key="FullName" />
    </TextBlock.Resources>

    <CheckBox IsChecked="{Binding IsAdmin, Converter={StaticResource Inverse}}" />

    <StackPanel>
        <TextBlock.Text>
            <MultiBinding StringFormat="{}{0} {1}">
                <Binding Path="FirstName" />
                <Binding Path="LastName" />
            </MultiBinding>
        </TextBlock.Text>
    </StackPanel>

    <!-- or, with a converter instead of a format string -->
    <TextBlock Text="{Binding FirstName, Converter={StaticResource FullName}}" />
</TextBlock>

Declare converters in a resource dictionary and reference them with {StaticResource}. A MultiBinding combines several sources into one target value.

8.6 IDataErrorInfo validation

WPF validation is built into the binding engine. Implement IDataErrorInfo on the view-model, add an ExceptionValidationRules to the binding, and the engine calls into your code, shows the message in the Validation.ErrorTemplate and blocks the invalid value from reaching the source. You style the error; WPF runs the check.

public sealed class CustomerViewModel : ObservableObject, IDataErrorInfo
{
    private string _email = "";

    public string Email
    {
        get => _email;
        set => SetProperty(ref _email, value);
    }

    public string this[string propertyName] => switch (propertyName)
    {
        nameof(Email) when !MailAddress.TryCreate(_email, out var _) =>

8.7 Binding performance and virtualization

WPF is fast until it is not, and the two usual causes are known: an expensive ToString or converter on a value that changes often, and a huge ItemsSource realised all at once. Virtualization is the default for ListBox, ListView and DataGrid, and it only stops working if you give the rows an explicit height.

<!-- BREAKS virtualization: an explicit row height forces a full measure pass -->
<ListView ItemContainerStyle="{StaticResource FixedHeightRow}">      <!-- Height="30" -->
    <ListView.ItemsPanel>
        <ItemsPanelTemplate>
            <VirtualizingStackPanel />
        </ItemsPanelTemplate>
    </ListView.ItemsPanel>
</ListView>

<!-- KEEPS virtualization: the default panel already virtualizes -->
<ListView ItemsSource="{Binding Rows}" />

<!-- ItemsControl does NOT virtualize: only use it for small collections -->
<ItemsControl ItemsSource="{Binding Thousands}" />                 <!-- avoid -->

<!-- ScrollViewer disables virtualization: never wrap an ItemsControl in one -->
<ScrollViewer>
    <ItemsControl ItemsSource="{Binding Rows}" />                  <!-- avoid -->
</ScrollViewer>

Virtualization is on by default for ListView, ListBox and DataGrid. An explicit row height, an ItemsControl, or a wrapping ScrollViewer all disable it.

SymptomLikely causeFix

9.1 A ViewModel base class

Every view-model needs the notification plumbing from chapter 8, plus a lifetime so the shell can dispose it. A small base class removes the repetition and gives every view-model the same IDisposable contract. This is the foundation the rest of the chapter builds on.

public abstract class ViewModelBase : ObservableObject, IDisposable
{
    // true while a long operation is in flight, for the busy overlay
    public bool IsBusy
    {
        get => _isBusy;
        set { if (SetProperty(ref _isBusy, value)) OnPropertyChanged(nameof(IsNotBusy)); }
    }
    private bool _isBusy;

    public bool IsNotBusy => !IsBusy;

    // every view-model in the lifetime list, disposed by the shell
    protected CompositeDisposable Subscriptions { get; } = new();

    public virtual void Dispose()
    {
        Subscriptions.Dispose();
        GC.SuppressFinalize(this);
    }
}

A base class gives every view-model the same notification plumbing, a busy flag for long operations, and a disposal hook so event subscriptions are always released.

9.2 RelayCommand and AsyncRelayCommand

You will write RelayCommand yourself once, then never again. The important detail is the parameter overload: a generic version is type-safe and avoids casting, and the non-generic one rejects the wrong parameter type rather than throwing at run time. AsyncRelayCommand adds a busy state so a command cannot be re-entered while it is running.

public sealed class RelayCommand : ICommand
{
    private readonly Action _execute;
    private readonly Func<bool>? _canExecute;

    public RelayCommand(Action execute, Func<bool>? canExecute = null)
    { _execute = execute; _canExecute = canExecute; }

    public event EventHandler? CanExecuteChanged;
    public bool CanExecute(object? parameter) => _canExecute?.Invoke() ?? true;
    public void Execute(object? parameter) => _execute();
    public void NotifyCanExecuteChanged() => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}

public sealed class RelayCommand<T> : ICommand
{
    private readonly Action<T> _execute;
    private readonly Func<T, bool>? _canExecute;

    public RelayCommand(Action<T> execute, Func<T, bool>? canExecute = null)
    { _execute = execute; _canExecute = canExecute; }

    public event EventHandler? CanExecuteChanged;
    public bool CanExecute(object? p) =>
        p is T typed && (_canExecute?.Invoke(typed) ?? true);
    public void Execute(object? p) { if (p is T typed) _execute(typed); }
    public void NotifyCanExecuteChanged() => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}
public sealed class AsyncRelayCommand : ICommand
{
    private readonly Func<Task> _execute;
    private readonly Func<bool>? _canExecute;
    private bool _isRunning;

    public bool IsRunning
    {
        get => _isRunning;
        private set
        {
            _isRunning = value;
            NotifyCanExecuteChanged();
            CanExecuteChanged?.Invoke(this, EventArgs.Empty);  // blocks re-entry
        }
    }

    public event EventHandler? CanExecuteChanged;
    public bool CanExecute(object? p) => !IsRunning && (_canExecute?.Invoke() ?? true);

    public async void Execute(object? p)
    {
        if (!CanExecute(p)) return;
        IsRunning = true;
        try { await _execute(); }
        finally { IsRunning = false; }
    }

    public void NotifyCanExecuteChanged() => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}

An async command reports IsRunning, which its own CanExecute checks, so a slow operation cannot be started twice. The async void is safe here because it is the command interface, and the try/finally catches the reset.

9.3 Dependency injection into ViewModels

A WPF app can use the same Microsoft.Extensions.DependencyInjection container as an ASP.NET Core app. Register view-models as scoped, views as transient, and resolve each window from the container so its view-model arrives pre-wired. The rule is simple: never use new on a view-model that has dependencies.

// composition root: build once, resolve everything from it
public static class AppServices
{
    public static IServiceProvider Build()
    {
        var services = new ServiceCollection();

        services.AddSingleton<ICustomerRepository, SqliteCustomerRepository>();
        services.AddSingleton<IThemeService, ThemeService>();
        services.AddSingleton<INavigationService, NavigationService>();
        services.AddScoped<MainViewModel>();
        services.AddScoped<CustomerListViewModel>();
        services.AddScoped<CustomerEditViewModel>();
        services.AddTransient<MainWindow>();
        services.AddTransient<CustomerEditView>();

        return services.BuildServiceProvider();
    }
}

// resolve: the view gets its view-model injected, never news one up
protected override void OnStartup(StartupEventArgs e)
{
    var services = AppServices.Build();
    var window = services.GetRequiredService<MainWindow>();
    MainWindow = window;
    window.Show();
}

<Window x:Class="Inventory.App.Views.MainWindow"

Everything in the previous three sections is boilerplate that Microsoft now generates. CommunityToolkit.Mvvm inspects your partial properties at compile time and writes the notification, the backing field and the command for you. The generated code is exactly equivalent to what you wrote by hand, with no run-time reflection.

<ItemGroup>

</ItemGroup>

public partial class CustomerEditViewModel : ObservableRecipient
{

    // [ObservableProperty] generates the field, the property and PropertyChanged
    [ObservableProperty]
    private string _name = "";

    [ObservableProperty]

    [NotifyPropertyChangedFor(nameof(DisplayName))]
    private string _firstName = "";

    NotifyPropertyChangedFor(nameof(DisplayName), nameof(CanSave))]
    [NotifyCanExecuteChangedFor(nameof(SaveCommand))]

    // ...generates the property plus OnSave and OnSaveAsync partial methods
    [RelayCommand]

The generators emit ordinary properties and commands at compile time, so there is no reflection cost at run time. NotifyPropertyChangedFor and NotifyCanExecuteChangedFor wire up the dependencies between properties.

9.5 Navigation between views

Navigation belongs behind a service, not in the code-behind of the window. The view-model asks the service to go somewhere; the service swaps the frame’s content. This keeps views free of each other and means a view-model can be unit tested with a fake navigation service, with no window in sight.

public interface INavigationService
{
    void NavigateTo(string viewName);
    void GoBack();
    bool CanGoBack { get; }
}

public sealed class NavigationService : INavigationService
{
    private readonly IServiceProvider _services;
    private readonly Stack<Page> _backStack = new();

    public NavigationService(IServiceProvider services) => _services = services;

    public Frame? Host { get; set; }      // assigned by the shell at startup

    public bool CanGoBack => _backStack.Count > 0;

    public void NavigateTo(string viewName)
    {
        if (Host is null) throw new InvalidOperationException("No navigation host.");

        if (Host.Content is Page current) _backStack.Push(current);
        Host.Navigate(new Uri(viewName, UriKind.Relative));
    }

    public void GoBack()
    {
        if (_backStack.TryPop(out var page) && Host is not null) Host.Content = page;
    }
}
// the shell owns the Frame and hands it to the service once
public partial class ShellWindow : Window
{
    public ShellWindow(ShellViewModel vm, INavigationService nav)
    {
        InitializeComponent();
        DataContext = vm;
        nav.Host = this.NavFrame;      // the named Frame in XAML
    }
}

// the view-model just asks to navigate
[RelayCommand]
private void EditSelected()
{
    if (Selected is null) return;
    _nav.NavigateTo("Views/CustomerEditView.xaml");
}

A navigation service owns the frame and the back stack, and the shell hands it the frame reference once. View-models then navigate by name and can be tested against a fake.

9.6 Avoiding code-behind

Code-behind is not forbidden; behaviour that genuinely belongs to the view is fine there. The rule is that business behaviour never lives in it. The three things to keep are view construction, a small amount of view-specific wiring, and events the binding engine cannot express, such as a key-down gesture.

Belongs in code-behindBelongs in the view-model
Calling InitializeComponentValidation rules
Assigning the DataContextAll navigation decisions
Wiring a navigation service to the frameSave and delete commands
A KeyDown handler for a shortcutFormatting and conversion rules
Nothing that touches a database or fileEverything that touches a database or file

Keep code-behind to construction, wiring and gestures the binding engine cannot express. If it references a repository or a file, the logic is in the wrong layer.

When a XAML file and its view-model disagree, do not fix it with code-behind. Add the missing property to the view-model, or correct the binding path. The binding engine is the specification; code-behind is the workaround.

10.1 Theming with resource dictionaries

A WPF theme is a set of resource dictionaries holding brushes, styles and control templates, merged into App.xaml. Because brushes are looked up by key, swapping the merged dictionaries at run time retheme the whole application. The keys and styles stay identical; only the values behind them change.

<!-- Themes/Dark.xaml : the same keys, different values -->
<ResourceDictionary xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">
    <SolidColorBrush x:Key="SurfaceBrush"   Color="#1E1E1E" />
    <SolidColorBrush x:Key="TextBrush"      Color="#E6E6E6" />
    <SolidColorBrush x:Key="AccentBrush"    Color="#4C8BF5" />
    <SolidColorBrush x:Key="DangerBrush"    Color="#E5534B" />
</ResourceDictionary>

// swap the theme at run time: the whole app follows
public sealed class ThemeService
{
    private readonly ResourceDictionary _target;

    public ThemeService(ResourceDictionary target) => _target = target;

    public void Apply(string themeName)
    {
        // build the pack URI, e.g. pack://application:,,,/Themes/Dark.xaml
        var uri = new Uri($"pack://application:,,,/Themes/{themeName}.xaml", UriKind.Absolute);
        var theme = new ResourceDictionary { Source = uri };

        _target.MergedDictionaries.Clear();
        _target.MergedDictionaries.Add(theme);

        // notify anything holding a DynamicResource directly
        _target["CurrentTheme"] = themeName;
    }
}
<!-- use DynamicResource so a theme swap is picked up live -->
<Window Background="{DynamicResource SurfaceBrush}"
        Foreground="{DynamicResource TextBrush}">
    <Button Content="Save" Background="{DynamicResource AccentBrush}" />
</Window>

<!-- implicit styles let the whole application restyle from one file -->
<Style TargetType="TextBlock">
    <Setter Property="Foreground" Value="{DynamicResource TextBrush}" />
    <Setter Property="VerticalAlignment" Value="Center" />
</Style>

A theme is a resource dictionary of brushes and styles. Swap the merged dictionary in App.xaml at run time and use DynamicResource everywhere so the change is picked up immediately.

Follow the Material, Fluent or your own design system rather than inventing key names. A theme that uses Background, Surface, OnSurface, Primary, OnPrimary, Error and OnError is far easier to extend than one built around ad-hoc names.

10.3 User controls vs custom controls

A UserControl is a named, reusable piece of XAML with its own code-behind and data context. A custom control is a Control subclass you author in C# with a default style that provides its own template, dependency properties and logic. The rule of thumb: user control for composing existing controls, custom control when you need your own dependency property, automation peer or visual state.

Authored asXAML plus a code-behind partialA C# class plus a default style

// a custom control: the type carries the behaviour and the properties
[TemplatePart(Name = "PART_Bar", Type = typeof(ProgressBar))]
public class CardGauge : Control
{
    public static readonly DependencyProperty ValueProperty =
        DependencyProperty.Register(nameof(Value), typeof(double), typeof(CardGauge),
            new FrameworkPropertyMetadata(0,
                FrameworkPropertyMetadataOptions.AffectsRender | FrameworkPropertyMetadataOptions.AffectsMeasure));

    public double Value
    {
        get => (double)GetValue(ValueProperty);
        set => SetValue(ValueProperty, value);
    }

                </Grid>

    </Setter>

A custom control owns its behaviour and declares dependency properties; a user control is a reusable XAML fragment. TemplatePart declares the named part the control expects its template to provide.

Put a custom control’s default style in a Themes/Generic.xaml resource dictionary inside the control’s assembly. Putting it in the app instead means the control cannot be reused in another application with its own theme.

10.4 Behaviours as attached properties

A behaviour attaches behaviour to an element without modifying that element, and in WPF the natural mechanism is an attached property on a static helper class. This gives you the "attached behaviour" pattern: one reusable behaviour, attached in XAML to any element, that subscribes and unsubscribes automatically.

public static class FocusOnLoad
{
    public static readonly DependencyProperty IsEnabledProperty =
        DependencyProperty.RegisterAttached(
            "IsEnabled", typeof(bool), typeof(FocusOnLoad),
            new PropertyMetadata(false, OnIsEnabledChanged));

    public static void SetIsEnabled(DependencyObject o, bool v) => o.SetValue(IsEnabledProperty, v);
    public static bool GetIsEnabled(DependencyObject o) => (bool)o.GetValue(IsEnabledProperty);

    private static void OnIsEnabledChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not FrameworkElement fe) return;

        if ((bool)e.NewValue) fe.Loaded += OnLoaded;
        else                                 fe.Loaded -= OnLoaded;
    }

    private static void OnLoaded(object sender, RoutedEventArgs e)
    {
        if (sender is FrameworkElement { Focusable: true } fe)
        {
            fe.Focus();
            (as System.Windows.Controls.TextBox)?.SelectAll();
        }
    }
}
<StackPanel>
    <TextBox b:FocusOnLoad.IsEnabled="True" />
    <PasswordBox b:FocusOnLoad.IsEnabled="True" />

    <!-- numeric input without a single line of code-behind -->
    <TextBox b:NumericInput.UpperBound="1000" b:NumericInput.DecimalPlaces="2" />

    <!-- escape closes a dialog, enter confirms -->
    <UserControl b:DialogKeys.Escape="Close" b:DialogKeys.Enter="Save" />
</StackPanel>

An attached property on a static class lets you attach behaviour to any element from XAML. The property-change callback is where you subscribe and unsubscribe, so the behaviour is applied and removed with the property.

The same mechanism powers the popular Microsoft.Xaml.Behaviors package, which gives you EventTrigger, DataTrigger and InvokeCommandAction as XAML elements. Use that package rather than hand-rolling behaviours for anything beyond a single attached property.

10.5 Animations and storyboards

WPF animates any dependency property, not just opacity and position, because a dependency property stores its value in a system that can interpolate over time. A Storyboard groups animations and fires them on triggers such as load, click or a property change. The house rule is that animation should confirm an action, never delay it.

<!-- declarative: a Storyboard triggered by a property change -->
<Storyboard x:Key="GrowStory">
    <DoubleAnimation Storyboard.TargetProperty="(UIElement.Opacity)"
                     From="0" To="1" Duration="0:0:0.2">
        <DoubleAnimation.EasingFunction>
            <QuadraticEase EasingMode="EaseOut" />
        </DoubleAnimation.EasingFunction>
    </DoubleAnimation>
</Storyboard>

<Grid.Triggers>
    <EventTrigger RoutedEvent="Window.Loaded" SourceObject="{Binding RelativeSource={RelativeSource Self}}">
        <BeginStoryboard Storyboard="{StaticResource GrowStory}" />
    </EventTrigger>
    <DataTrigger Binding="{Binding IsError}" Value="True">
        <DataTrigger.EnterActions>
            <BeginStoryboard>
                <Storyboard RepeatBehavior="3" AutoReverse="True">
                    <ColorAnimation Storyboard.TargetProperty="(Control.Background)"
                                    To="#E5534B" Duration="0:0:0.15" />
                </Storyboard>
            </BeginStoryboard>
        </DataTrigger.EnterActions>
    </DataTrigger>
</Grid.Triggers>

// imperative: for durations decided in code
private async void OnPulse(object sender, RoutedEventArgs e)
{
    var animation = new DoubleAnimation
    {
        To = 1.0,
        Duration = new Duration(TimeSpan.FromMilliseconds(150)),
        EasingFunction = new QuadraticEase { EasingMode = EasingMode.EaseOut }
    };
    badge.BeginAnimation(UIElement.OpacityProperty, animation);
    await Task.Delay(150);
    badge.BeginAnimation(UIElement.OpacityProperty, null);   // clear the animation
}

Any dependency property can be animated. BeginStoryboard in an event or data trigger handles most cases; BeginAnimation from code is for durations decided at run time.

An animated property is owned by the animation system until it is removed. If the property must return to XAML control, clear it with BeginAnimation(prop, null) — assigning a new value is silently ignored while an animation is active on that property.

    </Application.Resources>
</Application>

// handle a monitor change: WPF re-scales the logical tree, but any
// value you computed in device pixels must be recomputed yourself
private void OnDpiChanged(object sender, DpiChangedEventArgs e)
{
    double scale = e.NewDpi.DpiScaleX;              // 1.0, 1.25, 1.5, 2.0 ...
    // anything sized in raw pixels: chart margins, image buffers, cursors
    chart.Margin = new Thickness(8 * scale);
    _cachedBitmap = RenderAt(e.NewDpi);
}

Set PerMonitorV2 in the project file and merge XamlControlsResources in App.xaml. WPF rescales the logical tree for you, but values you computed in device pixels must be recomputed in DpiChanged.

WinForms needs the same setting plus an ApplicationConfiguration.Initialize() call, which the SDK template already provides. If your form looks blurry on a high-DPI screen, the awareness mode is almost always the reason.

11.1 EF Core with a local SQLite file

Entity Framework Core works unchanged against SQLite, which makes a local file-backed database the least effort path to persistence in a desktop app. The connection string points at a file under LocalApplicationData, migrations are applied at startup, and a context per operation keeps the lifetime simple.

dotnet add package Microsoft.EntityFrameworkCore.Sqlite
dotnet add package Microsoft.EntityFrameworkCore.Design
public sealed class InventoryDbContext(DbContextOptions<InventoryDbContext> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Customer>(e =>
        {
            e.ToTable("Customers");
            e.HasKey(x => x.Id);
            e.Property(x => x.Name).IsRequired().HasMaxLength(120);
            e.HasIndex(x => x.Email).IsUnique();
        });
    }
}

public static class Db
{
    public static string Path =>
        System.IO.Path.Combine(
            Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
            "Inventory", "inventory.db");

    public static InventoryDbContext Create()
    {
        Directory.CreateDirectory(System.IO.Path.GetDirectoryName(Path)!);
        var options = new DbContextOptionsBuilder<InventoryDbContext>()
            .UseSqlite($"Data Source={Path}")
            .EnableSensitiveDataLogging(false)
            .Options;
        return new InventoryDbContext(options);
    }

    // apply migrations once, at startup
    public static void Migrate()
    {
        using var db = Create();
        db.Database.Migrate();
    }
}

SQLite is a single file under LocalApplicationData, applied with Database.Migrate() at startup. A context per operation keeps lifetimes short and avoids stale reads.

Use AsNoTracking for read-only queries, and project straight to a view-model when the grid only needs a few columns. Both are the difference between an instant list and a visible pause.

db.Customers.AsNoTracking().Where(c => c.IsActive)
  .OrderBy(c => c.Name)
  .Select(c => new CustomerRow { Id = c.Id, Name = c.Name, OrderCount = c.Orders.Count })
  .ToList();

AsNoTracking skips change tracking for read-only data, and a projection to a flat row type avoids loading columns the grid never shows.

SQLite serialises writes. Never hold a write transaction across a UI interaction, and never open two contexts that write the same rows concurrently without retry logic. A "database is locked" error in a desktop app is nearly always a long-running write.

11.2 Data-grid editing patterns

In WPF, grid editing goes through the binding engine, so validation happens as the user types rather than after commit. Add an editable view-model per row, wrap the collection in an observable property that writes through to EF Core, and let the entity itself be the row object so you never hand-copy values.

// the entity is the row: it implements INotifyPropertyChanged itself
[Table("Orders")]
public partial class Order : ObservableObject
{
    [ObservableProperty]
    private string _reference = "";

    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(Total))]
    private decimal _quantity = 1;

    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(Total))]
    private decimal _unitPrice;

    [NotifyPropertyChangedFor(nameof(LineCount))]
    public decimal Total => _quantity * _unitPrice;
    public int LineCount { get; set; } = 1;
}

// the view-model: an observable list, saved explicitly or on a timer
public partial class OrdersViewModel(InventoryDbContext db) : ViewModelBase
{
    [ObservableProperty]
    private ObservableCollection<Order> _orders = new();

    [RelayCommand]
    private void AddRow() => Orders.Add(new Order());

    [RelayCommand]
    private void DeleteSelected()
    {
        if (SelectedOrder is not null) Orders.Remove(SelectedOrder);
    }

    [RelayCommand]
    private void Save()
    {
        // the DbContext is tracking the same instances the grid is editing
        using var context = Db.Create();
        context.Orders.AddRange(Orders);
        context.SaveChanges();
        StatusText = $"Saved {Orders.Count} orders.";
    }
}

Make the entity itself the row view-model so edits are notified automatically, expose an observable list, and call SaveChanges from an explicit command rather than on every keystroke.

Add a CanSave condition based on validation, and show a dirty indicator. A grid that silently loses edits when the window closes is the single most common complaint about an editable desktop grid.

11.3 Async data loading

Loading data is I/O, so it belongs on an async command. In WPF the command is awaited by the framework, which means you do not write the async void pattern from chapter 4 at all. The AsyncRelayCommand generator handles cancellation, and the model property setter that changes the bound list happens on the UI thread after the await.

public partial class OrdersViewModel(InventoryDbContext db) : ViewModelBase
{
    private readonly InventoryDbContext _db = db;

    [ObservableProperty]
    private ObservableCollection<OrderRow> _rows = new();

    [AsyncRelayCommand]
    private async Task LoadAsync(CancellationToken token)
    {
        IsBusy = true;
        try
        {
            // project to a flat row type: no change tracking, no lazy loading
            var data = await _db.Orders.AsNoTracking()
                .Where(o => o.PlacedOn >= DateTime.Today.AddMonths(-1))
                .OrderByDescending(o => o.PlacedOn)
                .Select(o => new OrderRow
                {
                    Id = o.Id,
                    Reference = o.Reference,
                    Customer = o.Customer.Name,
                    Total = o.Total
                })
                .ToListAsync(token);

            Rows = new ObservableCollection<OrderRow>(data);   // one assignment
        }
        catch (OperationCanceledException) { // user cancelled, nothing to do }
        catch (SqliteException ex) { ErrorMessage = ex.Message; }
        finally { IsBusy = false; }
    }
}

An async command is awaited by the binding engine, so the continuation after the await is already on the UI thread. Assign a new collection once rather than adding rows one at a time.

Every AsyncRelayCommand built by the source generator gets a CancellationToken parameter and calls Cancel() automatically when a new execution starts. Pass it to every await and a double-click on a reload button cancels the first load instead of running both.

11.4 dotnet publish options

A desktop app ships as a folder or a single executable. Framework-dependent output is small but needs the runtime installed; self-contained output bundles the runtime and is large but runs anywhere on a matching architecture. Single-file packaging is an option on top of either, not a third choice. Ready-to-run and trimming trade build time and size against startup speed.

# framework-dependent: needs .NET Desktop Runtime on the target machine
dotnet publish -c Release -r win-x64 --self-contained false -o publish/fd

# self-contained single file: nothing to install, ~150 MB
dotnet publish -c Release -r win-x64 --self-contained true \
    -p:PublishSingleFile=true \
    -p:IncludeNativeLibrariesForSelfExtract=true \
    -p:EnableCompressionInSingleFile=true \
    -o publish/single

# self-contained, optimised startup, larger output (no trimming)
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishReadyToRun=true -o publish/r2r

# cross-platform builds from one project
dotnet publish -c Release -r win-arm64 --self-contained true -o publish/arm64
dotnet publish -c Release -r win-x86  --self-contained true -o publish/x86
OptionSizeRequires installStartup
Framework-dependentFew MBYes, .NET Desktop RuntimeFastest
Framework-dependent, single fileFew MBYesFast
Self-containedAbout 150 MBNoModerate
Self-contained, single file, compressedAbout 70 MBNoModerate
Self-contained, ready to runAbout 200 MBNoFast
Self-contained, trimmedVariesNoFastest, but riskier

Framework-dependent output needs the runtime installed and starts fastest. Self-contained bundles the runtime so the app runs on a bare machine; single file and ready-to-run are options layered on top of that choice.

Do not enable PublishTrimmed on a WPF app without thorough testing. Trimming removes code it thinks is unreachable, and WPF resolves types reflectively in several places, so trimming silently breaks styles, converters and data templates at run time.

Build a Windows executable in the SDK rather than shipping the framework-dependent folder. If your users cannot install a runtime, self-contained is the only honest answer, and a PublishProfile in the repository keeps the command reproducible for everyone.

11.5 ClickOnce vs MSIX

ClickOnce updates .NET Framework applications in place and is the older of the two mechanisms. MSIX is a signed package format built on the Windows packaging stack: it installs and uninstalls cleanly, works on Windows 10 and 11, supports per-user and per-machine installs, and does not need the target machine to have a runtime. For a new .NET 10 application, MSIX is the default answer.

AspectClickOnceMSIX
Applies to.NET Framework primarily.NET Framework and modern .NET
SigningOptional, weak trust modelMandatory, certificate-based
Install locationPer-user or per-machine, opaqueStandard Windows app location
UninstallLeaves files behind in some casesClean, via Settings or the store
Runtime dependencyInstall the runtime as a prerequisiteBundle or declare the dependency
Auto-updateBuilt in, with a version checkHandled by the store or your own updater
ToolingVisual Studio publishing wizardMSIX Packaging Project or the Store Developer Center

ClickOnce is for .NET Framework and has a weak trust model. MSIX is the modern choice for .NET 10: mandatory signing, clean install and uninstall, and no runtime prerequisite when bundled.

Whatever you choose, the payload is the same: a publish folder, an application manifest declaring supported OS versions, icons and file associations, and a certificate for signing. Getting the certificate right early is the part projects get stuck on.

An unsigned MSIX package will not install on a standard Windows install. Buy or create a code-signing certificate, keep the private key out of the repository, and store the password in a secret store. Budget for renewal: a desktop app with an expired certificate stops launching for every user.

If the app is going to a managed environment, ask first. Many organisations forbid sideloaded installers entirely and only allow Store, Intune or a specific internal channel, and a signed MSIX package is usually the only thing all three accept.

11.6 Logging and diagnostics

A desktop app has no web request log to lean on, so it has to write its own. Serilog with the file sink is the usual choice: structured events, rolling files, and a sink per environment. Add a crash handler, a diagnostic dump on demand, and a way for the user to open the log folder, and you can support almost any report without asking for a reproduction.

dotnet add package Serilog
dotnet add package Serilog.Sinks.File
dotnet add package Serilog.Sinks.Console
public static class Log
{
    public static readonly Serilog.ILogger Instance = new LoggerConfiguration()
        .MinimumLevel.Information()
        .MinimumLevel.Override("Microsoft", Serilog.Events.LogEventLevel.Warning)
        .Enrich.WithProperty("App", "Inventory")
        .WriteTo.File(new Serilog.Formatting.Json.JsonFormatter(), Path(), rollingInterval: RollingInterval.Day)
        .WriteTo.Console()
        .CreateLogger();

    public static string Path()
    {
        var dir = System.IO.Path.Combine(
            Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData), "Inventory", "logs");
        Directory.CreateDirectory(dir);
        return System.IO.Path.Combine(dir, "app-.log");
    }
}

// last-resort handler: log the crash, then let the app die cleanly
AppDomain.CurrentDomain.UnhandledException += (object? s, UnhandledExceptionEventArgs e) =>
{
    Log.Instance.Fatal(e.ExceptionObject as Exception, "Unhandled crash");
    if e.ExceptionObject is Exception ex)
        MessageBox.Show("The application stopped unexpectedly.&n\n" + ex.Message +
                        $"\n\nA log was written to:{Environment.NewLine}{Log.Path()}",
                        "Fatal error", MessageBoxButton.OK, MessageBoxImage.Error);
};

Log.Instance.Information("Starting {Version}", typeof(App).Assembly.GetName().Version);

Serilog writes structured rolling files under LocalApplicationData. Register an unhandled-exception handler that logs, tells the user where the log is, and then lets the process terminate.

// a diagnostics screen: version, settings path, log path, and a copy button
[RelayCommand]
private void OpenLogFolder()
{
    Process.Start(new ProcessStartInfo("explorer.exe", Log.Path()) { UseShellExecute = true });
}

[RelayCommand]
private void CopyDiagnostics()
{
    var text =
        $"Version: {typeof(App).Assembly.GetName().Version}{Environment.NewLine}" +
        $"OS: {Environment.OSVersion}{Environment.NewLine}" +
        $"Runtime: {Environment.Version}{Environment.NewLine}" +
        $"64-bit process: {Environment.Is64BitProcess}{Environment.NewLine}" +
        $"Data: {Db.Path()}{Environment.NewLine}" +
        $"Log: {Log.Path()}";

    Clipboard.SetText(text);
    StatusText = "Diagnostics copied to the clipboard.";
}

A diagnostics command that copies version, OS, runtime, data path and log path into the clipboard resolves most support requests in one message. Put it on the Help menu.

Log the operation, not the keystroke. Recording which command failed and with which customer id is enough; logging every field of every record is a privacy and storage problem you cannot undo later.
