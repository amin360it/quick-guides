1 · The Android application model

1.1 The four component types

Android's architecture is built on four component types, each with a distinct lifecycle and activation mechanism. Understanding what each one is for — and more importantly, what each one is not for — is the foundation of every architectural decision you will make.

Everything is a component, and the system owns the lifecycle

Android does not have a main() method that you control from start to finish. Instead, the system instantiates components in response to Intent objects and manages their lifecycles according to the device's needs. An Activity is a single screen with a user interface. A Service is a component that runs in the background without a UI. A BroadcastReceiver responds to system-wide broadcast announcements. A ContentProvider manages a structured set of app data that can be shared with other apps. Each is declared in the manifest, and each can be activated independently of the others — the system can start your Service while your Activity is destroyed, or deliver a broadcast to a Receiver in a process that was killed an hour ago. This is the fundamental inversion of control that trips up developers coming from desktop or server frameworks: your code is a collection of entry points that the system calls, not a program that runs top to bottom.

The manifest as component registry

The AndroidManifest.xml is not just a configuration file — it is the registry the system uses to discover and instantiate your components. Every Activity, Service, BroadcastReceiver, and ContentProvider must be declared there with a <activity>, <service>, <receiver>, or <provider> element. The system reads this manifest at install time and builds an internal catalogue; when an Intent naming one of your components arrives, the system knows which process to start and which class to instantiate. The android:name attribute points to the fully-qualified class name. The android:exported attribute (required for all components in targetSdk 31+) controls whether other apps can activate the component. An Activity with android:exported="true" and an <intent-filter> for MAIN/LAUNCHER is the entry point the launcher icon activates. A Service with no intent-filter and exported="false" can only be started by your own app. Getting the exported attribute wrong is both a security vulnerability and a crash waiting to happen.

<!-- android/app/src/main/AndroidManifest.xml -->
<manifest xmlns:android="http://schemas.android.com/apk/res/android">

    <uses-permission android:name="android.permission.INTERNET" />
    <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

    <application
        android:name=".MyApplication"
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:theme="@style/Theme.MyApp">

        <activity
            android:name=".ui.MainActivity"
            android:exported="true"
            android:launchMode="singleTask"
            android:windowSoftInputMode="adjustResize">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>

        <service
            android:name=".service.SyncService"
            android:exported="false"
            android:foregroundServiceType="dataSync" />

        <receiver
            android:name=".receiver.BootReceiver"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.BOOT_COMPLETED" />
            </intent-filter>
        </receiver>

    </application>
</manifest>

Intent-based activation and the decoupling it buys

An Intent is a message object that requests an action from a component. Explicit intents name the target component directly (Intent(this, DetailActivity::class.java)) and are used for internal navigation. Implicit intents declare an action and let the system resolve the best component (Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com"))) and are used for inter-app communication. The decoupling is the point: your app does not need to know which app handles the intent, and the sending app does not need to know the internals of the receiver. When you start a Service with startService(Intent(this, SyncService::class.java)), you are not calling a method — you are handing a message to the system, which will instantiate your Service (starting its process if necessary) and deliver the intent to onStartCommand. The practical consequence is that your component must be able to start fresh at any time, with no in-memory state from a previous run, because the system may have killed and recreated the process between invocations.

// Starting an explicit intent to another activity in the same app
val intent = Intent(this, DetailActivity::class.java).apply {
    putExtra("item_id", itemId)
    putExtra("item_title", title)
}
startActivity(intent)

// Starting a service with work to do
val serviceIntent = Intent(this, SyncService::class.java).apply {
    putExtra("sync_type", SyncService.SYNC_FULL)
}
ContextCompat.startForegroundService(this, serviceIntent)

// Sending an implicit intent and letting the system resolve it
val viewIntent = Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com"))
if (viewIntent.resolveActivity(packageManager) != null) {
    startActivity(viewIntent)
} else {
    // No browser installed — handle gracefully
    Toast.makeText(this, "No browser available", Toast.LENGTH_SHORT).show()
}

The android:exported attribute is mandatory on every component with an intent-filter when targeting API 31+. The build will fail without it. More importantly, leaving a component exported="true" when it should be "false"" is a security hole — any app on the device can activate it. Default to exported="false" and only set "true" when you have a specific reason.

1.2 The activity lifecycle in depth

The activity lifecycle is the most important concept in Android development, and the one most often misunderstood. It is not just a set of callback methods — it is the system's contract for managing memory, resources, and user expectations across configuration changes and process death.

The seven callbacks and what each one is for

An Activity's lifecycle flows through seven primary callbacks: onCreate, onStart, onResume, onPause, onStop, onRestart, and onDestroy. The flow is not strictly linear — an Activity can move from onResume to onPause and back multiple times (when a dialog appears, when the screen turns off, when the user switches apps). The critical insight is the distinction between visible and foreground: onStart/onStop bracket the period when the Activity is visible on screen (even if another activity is on top in multi-window mode), while onResume/onPause bracket the period when the Activity is in the foreground and interactive. Heavy resources — camera, location updates, animation loops — should be acquired in onResume and released in onPause, because those are the callbacks that bound the interactive period. One-time setup that does not need to happen again on every resume — view binding, repository initialisation — belongs in onCreate.

class MainActivity : AppCompatActivity() {

    private lateinit var binding: ActivityMainBinding
    private var locationCallback: LocationCallback? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)

        // Restore transient UI state after process death
        savedInstanceState?.let {
            val query = it.getString("search_query")
            binding.searchInput.setText(query)
        }
    }

    override fun onResume() {
        super.onResume()
        // Start location updates — this is when the user can see the map
        locationCallback = object : LocationCallback() {
            override fun onLocationResult(result: LocationResult) {
                updateMapPosition(result.lastLocation)
            }
        }
        fusedLocationClient.requestLocationUpdates(
            locationRequest,
            locationCallback!!,
            Looper.getMainLooper()
        )
    }

    override fun onPause() {
        super.onPause()
        // Stop location updates — the user can no longer see the map
        locationCallback?.let { fusedLocationClient.removeLocationUpdates(it) }
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        // Save transient UI state for process death or config change
        outState.putString("search_query", binding.searchInput.text.toString())
    }
}

Process death, configuration changes and the saved state bundle

The single most important distinction in Android development is between a configuration change (rotation, locale change, dark mode toggle, font scale change) and process death (the system kills your process to reclaim memory). Both destroy and recreate the Activity, but for different reasons and with different guarantees. A configuration change happens while the user is watching — the system destroys the Activity and immediately recreates it, so onSaveInstanceState is called and the saved state Bundle is available in the new instance's onCreate. Process death happens when the app is in the background — the Activity is destroyed and its state saved, but recreation is deferred until the user navigates back, which may be hours later and may be triggered by a different entry point entirely. The onSaveInstanceState Bundle is not a serialisation mechanism — it is a small, transient store (limited to roughly 1 MB across all saved state) intended for UI state, not for data that belongs in a database or ViewModel. The rule is: if the data can be re-fetched from a repository, let the ViewModel re-fetch it; only save what cannot be reconstructed.

// In a ViewModel — survives configuration changes, dies with the process
class SearchViewModel(
    private val repository: ArticleRepository
) : ViewModel() {

    private val _results = MutableStateFlow<List<Article>>(emptyList())
    val results: StateFlow<List<Article>> = _results.asStateFlow()

    private var searchJob: Job? = null

    fun search(query: String) {
        searchJob?.cancel()
        searchJob = viewModelScope.launch {
            // This survives rotation: the ViewModel is retained
            _results.value = repository.search(query)
        }
    }

    override fun onCleared() {
        super.onCleared()
        searchJob?.cancel()
    }
}

// The ViewModel is scoped to the Activity, so it survives
// configuration changes but not process death
class SearchActivity : AppCompatActivity() {
    private val viewModel: SearchViewModel by viewModels {
        SearchViewModel.Factory(repository)
    }
}

Test process death with the "Don't keep activities" developer option. Enable it in Settings → Developer options, then navigate away from your activity and back. If your UI state does not survive, you have a bug. This single setting catches more lifecycle bugs than any unit test.

1.3 Processes, tasks and the back stack

Android's process and task model governs how your app appears on screen, how the system reclaims memory, and how the back button behaves. Misunderstanding this model is the root cause of duplicate activities, leaked windows, and the infamous "back button exits the app instead of going back."

Process priority and the oom_adj scale

Linux gives every process an OOM (out-of-memory) adjustment score; Android layers its own priority system on top. A foreground process (one with a visible Activity in the foreground, or a foreground Service, or a Service bound by a foreground Activity) is the last to be killed. A visible process (one with an Activity that is visible but not in the foreground — behind a dialog or in multi-window) is killed only under extreme memory pressure. A service process (one hosting a background Service) has lower priority, and a cached process (one with no active components, kept around for faster relaunch) is the first to be killed. This is why your Activity's onStop is the signal to release heavy resources: the moment your Activity leaves the foreground, the process drops in priority and becomes eligible for killing. The system does not guarantee that onDestroy will ever be called — under memory pressure, the process is killed outright. Anything that must survive must be persisted in onStop or earlier.

class MainActivity : AppCompatActivity() {

    override fun onWindowFocusChanged(hasFocus: Boolean) {
        super.onWindowFocusChanged(hasFocus)
        if (hasFocus) {
            // The user is actually interacting — resume video playback,
            // re-enable sensors, restart animations
            videoView.start()
        } else {
            // Another window (dialog, notification shade, split-screen)
            // has taken focus — pause playback to save battery
            videoView.pause()
        }
    }

    // The four launch modes control task membership:
    //
    // standard      — default; a new instance is created every time
    // singleTop     — if an instance is already at the top of the task,
    //                 reuse it instead of creating a new one
    // singleTask    — only one instance exists in the entire system;
    //                 clears activities above it when activated
    // singleInstance— like singleTask but the task holds only this
    //                 activity; other activities started from it go
    //                 to a different task
}

Tasks, task affinity and the back stack

A task is a collection of activities that the user interacts with when performing a certain job — browsing an article, composing an email, checking out. The user perceives a task as an "app," but a task can contain activities from multiple apps. The back stack is the stack of activities within a task, and the back button pops from that stack. When your app starts an Activity, it goes into the task associated with the calling Activity's taskAffinity (by default, the app's package name) unless FLAG_ACTIVITY_NEW_TASK is set, in which case the system finds or creates a matching task. The most common launch-mode bug is using singleTask on a main activity to prevent duplicate instances, not realising that it clears the entire back stack above it — pressing back from a singleTask activity exits the app rather than returning to the previous activity. The fix is almost always to use singleTop instead, which reuses the existing instance at the top of the stack without clearing what is below it.

// The correct way to handle "open this screen" without duplicates
// is singleTop, not singleTask:
//
// AndroidManifest.xml
// <activity
//     android:name=".DetailActivity"
//     android:launchMode="singleTop" />

// singleTop means: if DetailActivity is already at the top of the
// current task, deliver a new intent to it via onNewIntent instead
// of creating a second instance.

class DetailActivity : AppCompatActivity() {
    override fun onNewIntent(intent: Intent) {
        super.onNewIntent(intent)
        setIntent(intent)  // Replace the activity's intent
        val newId = intent.getStringExtra("article_id")
        viewModel.loadArticle(newId)
    }
}

// FLAG_ACTIVITY_NEW_TASK is needed when starting an activity from
// a non-activity context (Service, BroadcastReceiver, Application):
val intent = Intent(this, DetailActivity::class.java).apply {
    putExtra("article_id", id)
    addFlags(Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TOP)
}
startActivity(intent)

1.4 Project structure, Gradle and build variants

A well-structured Android project is not just about file organisation — it is about making the build system, the IDE, and the runtime all agree on where things live. The Gradle build configuration is the contract that ties it all together.

The module layout and source sets

A typical Android project has at least one module: app. The module directory contains src/main/ (production code), src/test/ (unit tests that run on the JVM), and src/androidTest/ (instrumentation tests that run on a device). The src/main/ directory holds java/ (or kotlin/) for source, res/ for resources (layouts, drawables, strings, themes), and AndroidManifest.xml for the module manifest. The manifest merger combines the module manifest with library manifests at build time — this is how a library can contribute a required permission or a Service without the app developer knowing about it. The build.gradle.kts file at the module root declares the Android plugin, SDK versions, dependencies, and build types. For larger projects, feature modules (feature:search, feature:profile) and library modules (core:network, core:ui) break the codebase into independently buildable units with enforced dependency directions.

Why minSdk, targetSdk and compileSdk are three different numbers

compileSdk is the API level your code compiles against — it determines which classes and methods are available at compile time. targetSdk is the API level you have tested against and whose behaviour you opt into — the system uses it to decide whether to apply compatibility behaviours. minSdk is the oldest API level you support — the system will not install your app on a device below it. These three numbers serve completely different purposes and should not be the same. A common mistake is setting compileSdk = 34 and targetSdk = 34 but leaving minSdk = 21, then calling an API introduced in API 26 without a version check — the code compiles fine and crashes on every API 25 device. The rule is: guard every call to an API introduced after your minSdk with if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O), or use the AndroidX backport (which is why the AndroidX libraries exist — NotificationCompat, ContextCompat, and ActivityCompat all handle version checks internally).

// The version-guard pattern
fun setupNotificationChannel(context: Context) {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
        val channel = NotificationChannel(
            CHANNEL_ID,
            "Sync notifications",
            NotificationManager.IMPORTANCE_DEFAULT
        ).apply {
            description = "Shows progress of background sync"
            setShowBadge(false)
        }
        val manager = context.getSystemService(NotificationManager::class.java)
        manager.createNotificationChannel(channel)
    }
    // Below API 26, channels do not exist — notifications are managed
    // at the app level, so there is nothing to set up.
}

// The AndroidX backport pattern — no version check needed
val intent = Intent(this, DetailActivity::class.java)
// ActivityCompat and ContextCompat handle the version differences
// internally, so you call them unconditionally:
ActivityCompat.startActivity(this, intent, null)
val permission = Manifest.permission.ACCESS_FINE_LOCATION
ActivityCompat.requestPermissions(this, arrayOf(permission), REQUEST_CODE)

1.5 Context: the god object

Context is the most-used and most-misused class in Android. It is the gateway to system services, resources, and the application environment — and passing the wrong one is the leading cause of memory leaks and unexpected crashes.

The four Context types and what each one can do

Context is an abstract class; the concrete implementations are Application, Activity, Service, and BroadcastReceiver (which receives a restricted ContextWrapper). The Application context lives for the lifetime of the process and is accessible via applicationContext from any component. The Activity context lives for the lifetime of the Activity and carries the theme, the window, and the task affinity. The Service context is similar to the Application context but is tied to the Service's lifecycle. The critical rule is: use the narrowest Context that works. If you need a system service (getSystemService), a resource, or a database path, the Application context is sufficient and safe — it cannot leak an Activity because it outlives every Activity. If you need to start an Activity, show a dialog, or inflate a layout with the correct theme, you need the Activity context — the Application context cannot start activities (it throws Calling startActivity() from outside of an Activity context requires FLAG_ACTIVITY_NEW_TASK) and does not carry the Activity's theme.

// The leak: storing an Activity context in a long-lived object
class BadRepository(private val context: Context) {
    // If 'context' is an Activity, the Activity cannot be garbage
    // collected even after it is destroyed — the Repository holds
    // a reference to it for the lifetime of the process.
    fun getDb(): SQLiteDatabase {
        return openDatabase(context.getDatabasePath("app.db"))
    }
}

// The fix: use the Application context for anything long-lived
class GoodRepository(private val appContext: Context) {
    // appContext is the Application singleton — it lives as long
    // as the process, so nothing is leaked.
    fun getDb(): SQLiteDatabase {
        return openDatabase(appContext.getDatabasePath("app.db"))
    }
}

// In a ViewModel, inject the Application context via
// AndroidViewModel:
class MyViewModel(application: Application) : AndroidViewModel(application) {
    private val appContext: Context = getApplication<Application>.applicationContext
    // Use appContext for repositories, system services, databases.
    // Never store an Activity reference here.
}

// In an Activity, use 'this' (the Activity context) only for
// UI work — starting activities, showing dialogs, inflating
// layouts with the Activity theme:
class MyActivity : AppCompatActivity() {
    fun showDialog() {
        MaterialAlertDialogBuilder(this)  // needs Activity context
            .setTitle("Confirm")
            .setMessage("Are you sure?")
            .setPositiveButton("Yes") { _, _ -> deleteItem() }
            .show()
    }
}

ContextWrapper and the delegation chain

ContextWrapper delegates all method calls to a wrapped Context instance. Activity, Service, and ThemeWrapper all extend ContextWrapper. This is why you can wrap a Context to modify its behaviour — ContextThemeWrapper applies a different theme, and MutableContextWrapper allows the base context to be replaced. The practical implication is that when you pass a Context around, you may be passing a wrapper that adds behaviour (the Activity's theme, the Service's task affinity) or restricts it (a BroadcastReceiver's Context does not support starting activities). The Context.createPackageContext() method creates a Context for a different package — used to access another app's resources when you have the right permissions. The Context.createConfigurationContext() creates a Context with an overridden configuration (locale, font scale) — used to display content in a language different from the system default without changing the system settings.

A quick heuristic: if you are writing a class that outlives the current screen (Repository, database helper, network client), take the Application context. If you are writing UI code in an Activity or Fragment, use the Activity context. If you are in a Service, use the Service context. When in doubt, pass the Application context and wrap it in a ContextThemeWrapper when you need a theme for inflation.

// ContextThemeWrapper: apply a specific theme without an Activity
fun createThemedContext(context: Context, themeResId: Int): Context {
    return ContextThemeWrapper(context, themeResId)
}

// createConfigurationContext: override the locale
fun createLocalizedContext(context: Context, locale: Locale): Context {
    val config = Configuration(context.resources.configuration)
    config.setLocale(locale)
    return context.createConfigurationContext(config)
}

// Usage: inflate a layout with a custom theme
val themedContext = createThemedContext(appContext, R.style.Theme_MyApp_Dialog)
val themedView = LayoutInflater.from(themedContext)
    .inflate(R.layout.dialog_custom, parent, false)

// Usage: create a notification with a specific locale
val localizedContext = createLocalizedContext(appContext, Locale("ar"))
val localizedTitle = localizedContext.getString(R.string.notification_title)

2 · Building the user interface

2.1 Views, layouts and the ViewGroup tree

The Android UI toolkit is a tree of View objects. Understanding how that tree is measured, laid out, and drawn — and why the three-pass system matters for performance — separates developers who ship smooth apps from developers who ship janky ones.

The View/ViewGroup hierarchy and the three-pass system

Every pixel on an Android screen is drawn by a View. A ViewGroup is a View that contains other Views — it is the container that defines the layout structure. The tree is rooted at a DecorView (the top-level window view), which contains the system UI (status bar background, navigation bar) and a FrameLayout (the android.R.id.content frame) that holds your activity's content view. When the system needs to draw the screen, it calls measure() on the root view, which recursively measures each child; then layout(), which positions each child; then draw(), which renders to the canvas. The measure pass is the expensive one: each ViewGroup must negotiate constraints with its children (via MeasureSpec) and compute its own size. A deeply nested ViewGroup tree means more measure calls, more layout calls, and more chances for a child to trigger a full re-measure of its parent. This is why ConstraintLayout (a flat hierarchy) outperforms nested LinearLayouts (a deep hierarchy) — fewer nodes means fewer measure passes.

// The three-pass system in a custom view
class StatusBarView @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null
) : View(context, attrs) {

    private val paint = Paint(Paint.ANTI_ALIAS_FLAG)

    // Pass 1: measure — how big do we want to be?
    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        val desiredHeight = dp(48)
        val heightMode = MeasureSpec.getMode(heightMeasureSpec)
        val heightSize = MeasureSpec.getSize(heightMeasureSpec)

        val height = when (heightMode) {
            MeasureSpec.EXACTLY -> heightSize
            MeasureSpec.AT_MOST -> minOf(desiredHeight, heightSize)
            else -> desiredHeight  // UNSPECIFIED
        }
        setMeasuredDimension(
            resolveSize(dp(360), widthMeasureSpec),
            height
        )
    }

    // Pass 2: layout — where do our children go?
    // (A leaf view has no children, so this is trivial.)
    override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
        // Leaf view — nothing to layout.
    }

    // Pass 3: draw — render to the canvas
    override fun onDraw(canvas: Canvas) {
        super.onDraw(canvas)
        paint.color = Color.parseColor("#0D47A1")
        canvas.drawRect(0f, 0f, width.toFloat(), height.toFloat(), paint)
    }

    private fun dp(value: Int): Int =
        (value * resources.displayMetrics.density).toInt()
}

requestLayout vs invalidate: two different invalidations

requestLayout() triggers a full measure and layout pass on the view and its ancestors — it is expensive and must be called when the view's size or position might have changed (text content updated, a child added, a constraint changed). invalidate() triggers only a redraw of the view's own bounds — it is cheap and must be called when the view's appearance changed but its size did not (colour, alpha, a progress indicator ticking). The common bug is calling requestLayout() when only invalidate() was needed, forcing the entire tree to re-measure for a colour change. The other common bug is calling invalidate() from a background thread — UI operations must happen on the main thread, and invalidate() is no exception. Use postInvalidate() from a non-UI thread, which posts the invalidation to the main thread's message queue. A View that is not attached to a window (not in the hierarchy) can safely have invalidate() called on it, but the invalidation will be lost — it does not accumulate.

class ProgressCircleView @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null
) : View(context, attrs) {

    private var progress: Float = 0f  // 0.0 to 1.0
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG).apply {
        style = Paint.Style.STROKE
        strokeWidth = 8f
        strokeCap = Paint.Cap.ROUND
        color = Color.parseColor("#1565C0")
    }

    // Called when the progress value changes — the view's size
    // does NOT change, so we only need to redraw, not re-measure.
    fun setProgress(value: Float) {
        progress = value.coerceIn(0f, 1f)
        invalidate()  // cheap: just redraw
    }

    // Called when the stroke width changes — this might affect
    // the view's measured size if it has wrap_content, so we
    // need a full re-measure.
    fun setStrokeWidth(widthDp: Int) {
        paint.strokeWidth = widthDp * resources.displayMetrics.density
        requestLayout()  // expensive: re-measure and re-layout
        invalidate()     // also redraw, since appearance changed
    }

    override fun onDraw(canvas: Canvas) {
        super.onDraw(canvas)
        val padding = paint.strokeWidth / 2
        val rect = RectF(
            padding, padding,
            width - padding, height - padding
        )
        canvas.drawArc(rect, -90f, 360f * progress, false, paint)
    }
}

Never call requestLayout() from within onMeasure, onLayout, or onDraw — it will cause an infinite loop. If you need to trigger a layout change from a layout callback, post it to the next frame with view.post { view.requestLayout() }.

2.2 XML layouts and the resource system

XML is the declarative language of Android UI. It is not just a convenience — it is the mechanism by which the resource qualifier system adapts your UI to different screen sizes, orientations, and configurations without code changes.

LayoutInflater and how XML becomes a View tree

XML layouts are not parsed at runtime from the APK — they are pre-compiled into a binary format at build time and stored in the res/ compiled resources. LayoutInflater.inflate() reads this binary XML and instantiates the corresponding View objects by reflection, calling the two-argument constructor (Context, AttributeSet) for each element. This is why every custom View you define must have that constructor — without it, inflation crashes with InflateException. The attachToRoot parameter controls whether the inflated view is added to the parent ViewGroup immediately (true) or returned for manual addition (false). In practice, ViewBinding replaces manual inflation: it generates a binding class from your layout XML at compile time, giving you type-safe, null-safe references to every view with an android:id. The generated inflate(layoutInflater) method handles the inflation and returns a binding object — no findViewById, no casting, no null checks.

Resource qualifiers and adaptive UI

The resource system selects the best-matching resource at runtime based on the device's configuration. Qualifiers are suffixes on resource directory names: layout-land/ for landscape, layout-sw600dp/ for screens with a smallest width of 600dp (tablets), values-night/ for dark mode, drawable-xhdpi/ for extra-high-density screens. The system matches the device's configuration against all available resource directories and picks the closest match, falling back to the default (no suffix) if nothing matches. This is how one APK serves phones, tablets, foldables, and Chromebooks with a different UI for each form factor. The smallestWidth qualifier (sw<n>dp) is the most reliable for form-factor adaptation because it is based on the smaller screen dimension regardless of orientation — a phone in landscape still has a smallest width of ~360dp, so layout-sw600dp/ will not incorrectly match it.

2.3 RecyclerView: lists done properly

RecyclerView is the most performance-critical widget in Android. It is not just a list — it is a recycling engine that manages view creation, binding, and reuse for datasets that can be arbitrarily large. Getting it right means the difference between 60fps scrolling and a janky mess.

The ViewHolder pattern and why it matters

ListView recycled views, but it forced every row to have the same structure and gave the developer no control over when views were created versus bound. RecyclerView separates the concerns: the RecyclerView owns the recycling pool and decides when to create a new ViewHolder (via onCreateViewHolder) versus reuse an existing one (via onBindViewHolder). The ViewHolder is a cache of view references — it holds the inflated row layout's child views so that findViewById is called once at creation time, not every time a row scrolls on screen. This is the single most important performance pattern in Android UI: without it, a list of 1000 items would call findViewById 1000 times per frame as the user scrolls. The RecyclerView also supports multiple view types (headers, footers, section dividers) through getItemViewType, which creates separate recycling pools for each type.

class ArticleAdapter(
    private val onClick: (Article) -> Unit
) : ListAdapter<Article, ArticleAdapter.ViewHolder>(DiffCallback) {

    // DiffUtil computes the difference between the old and new
    // list and dispatches the minimal set of change notifications.
    // This is far more efficient than notifyDataSetChanged(),
    // which forces a full rebind of every visible row.
    companion object : DiffUtil.ItemCallback<Article>() {
        override fun areItemsTheSame(oldItem: Article, newItem: Article) =
            oldItem.id == newItem.id
        override fun areContentsTheSame(oldItem: Article, newItem: Article) =
            oldItem == newItem
    }

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): ViewHolder {
        val binding = ItemArticleBinding.inflate(
            LayoutInflater.from(parent.context), parent, false
        )
        return ViewHolder(binding, onClick)
    }

    override fun onBindViewHolder(holder: ViewHolder, position: Int) {
        holder.bind(getItem(position))
    }

    class ViewHolder(
        private val binding: ItemArticleBinding,
        private val onClick: (Article) -> Unit
    ) : RecyclerView.ViewHolder(binding.root) {

        fun bind(article: Article) {
            binding.title.text = article.title
            binding.summary.text = article.summary
            binding.date.text = formatDate(article.publishedAt)
            // The entire row is clickable — set the listener once
            // in the ViewHolder, not in onBindViewHolder.
            binding.root.setOnClickListener { onClick(article) }
        }
    }
}

ListAdapter, DiffUtil and the diffing pipeline

ListAdapter (from androidx.recyclerview:recyclerview) wraps AsyncListDiffer, which runs DiffUtil.calculateDiff on a background thread by default. When you submit a new list with submitList(newList), the differ compares it to the current list, computes the minimal set of insertions, deletions, moves, and changes, and dispatches them to the adapter on the main thread. This means you never call notifyDataSetChanged() — the diffing engine handles updates incrementally, which enables item animations (add, remove, move, change) for free. The critical contract is that your DiffUtil.ItemCallback must correctly identify when two items are the same (identity, usually a database ID) and when their contents are equal (for change detection). If areItemsTheSame returns false for items that are actually the same, the adapter will treat them as a removal plus an insertion, losing the view's state and causing flicker.

2.4 Material Components and theming

Material Design 3 (Material You) is Google's design system, and the Material Components library is its Android implementation. It is not just a set of pretty widgets — it is a complete theming system that adapts to the user's dynamic colour preferences on Android 12+.

Theme inheritance and the attribute cascade

Material theming works through a hierarchy of XML theme attributes. Your app theme inherits from Theme.Material3.DayNight.NoActionBar (or Theme.Material3.Light.NoActionBar for light-only). The theme defines colour attributes: colorPrimary (brand colour for app bars, buttons, active states), colorOnPrimary (text/icons on primary), colorSurface (background of cards, sheets, menus), colorOnSurface (primary text), colorError (error states), and the *Variant counterparts for secondary emphasis. Every Material widget reads these attributes at inflation time — MaterialButton uses colorPrimary for its fill, MaterialCardView uses colorSurface for its background, MaterialTextView uses colorOnSurface for its text. This means you change the entire app's appearance by modifying a handful of attributes in values/themes.xml — no widget-level overrides needed. On Android 12+, the system can override your brand colours with the user's wallpaper-derived palette (dynamic colour), and your app should use ?attr/colorPrimary references rather than hardcoded colours to participate.

2.5 ConstraintLayout in depth

ConstraintLayout is the most powerful layout in Android — and the most misunderstood. It is not just a replacement for nested layouts; it is a constraint solver that computes positions from relationships, enabling flat hierarchies that would be impossible with LinearLayout or RelativeLayout.

Constraints as relationships, not positions

In a LinearLayout, you express layout as nesting — a vertical LinearLayout inside a horizontal LinearLayout inside a FrameLayout. In ConstraintLayout, you express layout as constraints — each view declares its relationship to its siblings and the parent. A constraint is a connection: "this view's start edge aligns with that view's end edge, with 16dp margin." The ConstraintLayout solver takes all constraints, builds a system of linear equations, and solves for the positions that satisfy all of them. This means you can express "this view is centred between those two views" or "these two views share the top edge with a 1dp gap between them" — relationships that would require multiple nested containers in LinearLayout. The performance benefit is the flat hierarchy: a ConstraintLayout with 20 views and 40 constraints has one measure pass, whereas the equivalent nested LinearLayout might have 5 levels of nesting and 5 measure passes.

Chains, barriers and guidelines

Chains are a set of views linked bidirectionally — each view constrains to the next, and the first and last constrain to the parent. A barrier references a set of views and computes the maximum (or minimum) edge among them at layout time. Guidelines are invisible positioning aids — vertical or horizontal lines at a fixed position or percentage — that views can constrain to. The common mistake is using ConstraintLayout for simple layouts that would be clearer as a LinearLayout (a single row of equally-weighted views, a vertical stack with no inter-view relationships). ConstraintLayout shines when views have complex, multi-directional relationships; for simple stacks, a LinearLayout with weights is more readable and equally performant.

3.1 Fragments and their lifecycle

Fragments are reusable UI components that live inside an Activity. They were introduced to support tablet layouts, but their real value is in lifecycle-aware UI modules that can be combined and rearranged. The fragment lifecycle is the subtlest in Android because it is tied to both the Activity lifecycle and the fragment's own view lifecycle.

The fragment lifecycle and the view lifecycle split

A fragment has two parallel lifecycles: the fragment lifecycle (onAttach → onCreate → onCreateView → onViewCreated → onStart → onResume → onPause → onStop → onDestroyView → onDestroy → onDetach) and the view lifecycle (onCreateView → onViewCreated → onDestroyView). The critical insight is that onDestroyView is called before onDestroy — the fragment's view is destroyed when the fragment is placed on the back stack (not when the fragment is destroyed). This means you must null out view references in onDestroyView, not onDestroy, and you must not access views after onDestroyView is called. The fragment object itself survives a back-stack transaction; only its view is recreated. The FragmentManager manages the back stack, transactions (add, remove, replace, hide, show), and the fragment result API. A fragment transaction is not executed immediately — it is scheduled via commit() (or commitNow() for synchronous execution, which cannot be used for back-stack transactions).

class ProfileFragment : Fragment() {

    private var _binding: FragmentProfileBinding? = null
    // This getter survives the view lifecycle — it returns null
    // when the view is destroyed (fragment on back stack).
    private val binding get() = _binding!!

    private val viewModel: ProfileViewModel by viewModels()

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        _binding = FragmentProfileBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        // Safe to access views here — the view exists.
        binding.followButton.setOnClickListener { viewModel.toggleFollow() }

        viewLifecycleOwner.lifecycleScope.launch {
            viewModel.user.collect { user ->
                binding.name.text = user.name
                binding.bio.text = user.bio
            }

    }

    // CRITICAL: null out the view binding here, not in onDestroy.
    // The fragment object survives; only the view is destroyed.

        super.onDestroyView()
        _binding = null
    }
}

FragmentManager, back stacks and the transaction API

The FragmentManager is the engine that drives fragment transactions. A transaction is a set of operations (add, remove, replace, hide, show) applied atomically. When you call commit(), the transaction is posted to the main thread's message queue and executed after the current batch of input events and animations. This is why you cannot access the fragment's view immediately after commit() — the transaction has not been executed yet. The back stack is a stack of transactions that the user can reverse with the back button. addToBackStack(null) adds the transaction to the back stack; without it, the back button pops the Activity (exits the app) instead of reversing the transaction. The childFragmentManager is a separate manager for fragments nested inside a fragment — it has its own back stack and lifecycle. The common crash "Fragment already added" happens when you add a fragment in onCreate without checking savedInstanceState == null, causing a duplicate after process death.

class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        // Only add the initial fragment on first creation —
        // after process death, the FragmentManager restores it.
        if (savedInstanceState == null) {
            supportFragmentManager.commit {
                replace(R.id.fragmentContainer, HomeFragment())
                // No addToBackStack — the back button should exit
                // the app from the home screen, not pop a transaction.
            }
        }

            replace(R.id.fragmentContainer, DetailFragment.newInstance(articleId))
            addToBackStack(null)  // back button reverses this navigation
            setReorderingAllowed(true)  // optimises the transition

    // childFragmentManager, not supportFragmentManager:

3.2 The Navigation component

The Navigation component is a library that manages fragment transactions, back stacks, and argument passing through a declarative graph. It replaces manual fragment management with a single source of truth — the navigation graph XML — and eliminates the most common sources of navigation bugs.

The navigation graph and NavController

The navigation graph is an XML file (res/navigation/nav_graph.xml) that declares every destination (fragment, activity, or nested graph) and every action (a named transition between destinations). The NavHostFragment is a special fragment that hosts the navigation graph — it inflates a FragmentManager and a NavController. The NavController is the runtime API: navigate(actionId) performs a transition, popBackStack() reverses one, and currentBackStackEntry gives access to the current destination's arguments. The single-activity pattern — one Activity hosting all fragments via the Navigation component — has become the recommended architecture because it simplifies shared element transitions, deep linking, and the back stack. The NavController manages the fragment back stack automatically: navigate() adds to the back stack, and the back button pops it. You never call FragmentManager.commit() directly.

3.3 Passing data between screens

Navigation requires data to flow between destinations. Android provides three mechanisms — Intent extras, the Fragment Result API, and shared ViewModels — each with a specific scope and lifetime. Choosing the wrong one leads to type-unsafe Bundle lookups, leaked listeners, or state that survives its owner.

Shared ViewModels: the scope-based approach

A shared ViewModel is scoped to a navigation destination's parent — typically the Activity or a parent fragment. When two fragments share the same ViewModelStoreOwner (the Activity), they get the same ViewModel instance and can observe the same state. This is the recommended pattern for passing data between a master and a detail screen: the master fragment writes the selected item ID to the shared ViewModel, and the detail fragment observes it. The ViewModel survives configuration changes but is cleared when the store owner is finished (the Activity is destroyed). The critical rule is that the ViewModel must never hold a reference to a View, Fragment, or Activity context — it holds data and exposes it via LiveData or StateFlow. The by activityViewModels() delegate scopes the ViewModel to the Activity; by viewModels() scopes it to the fragment.

// Shared ViewModel scoped to the Activity
class SharedEditorViewModel : ViewModel() {
    private val _selectedItem = MutableStateFlow<Item?>(null)
    val selectedItem: StateFlow<Item?> = _selectedItem.asStateFlow()

    fun select(item: Item) {
        _selectedItem.value = item
    }
}

    private val sharedViewModel: SharedEditorViewModel by activityViewModels()

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        viewLifecycleOwner.lifecycleScope.launch {
            sharedViewModel.selectedItem
                .filterNotNull()
                .collect { item ->
                    binding.title.text = item.title
                    binding.content.text = item.content
                }
        }
    }
}

The Fragment Result API: the event-based approach

The Fragment Result API (setFragmentResultListener) is the mechanism for a child fragment to send data back to its parent without a shared ViewModel or a direct reference. The parent registers a listener with a string key; the child sets a result with the same key; the system delivers it via a Bundle. The listener is lifecycle-aware — it is removed automatically when the fragment's view is destroyed, so there is no leak. This is the right pattern for a dialog fragment returning a value (a date picker returning a selected date, a filter dialog returning filter criteria). The Bundle is not type-safe — the key is a string and the value must be a Parcelable or Serializable — so the convention is to define the keys as constants and to validate the types when reading.

// Parent fragment: register a listener
class ParentFragment : Fragment() {

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        childFragmentManager.setFragmentResultListener(
            DatePickerFragment.KEY_DATE, viewLifecycleOwner
        ) { _, bundle ->
            val timestamp = bundle.getLong(DatePickerFragment.RESULT_TIMESTAMP)
            val selectedDate = Date(timestamp)
            viewModel.onDateSelected(selectedDate)
        }
    }

    fun openDatePicker() {
        DatePickerFragment().show(childFragmentManager, "datePicker")
    }
}

// Child (dialog) fragment: set a result and dismiss
class DatePickerFragment : DialogFragment() {

    companion object {
        const val KEY_DATE = "date_request"
        const val RESULT_TIMESTAMP = "timestamp"
    }

    override fun onCreateDialog(savedInstanceState: Bundle?): Dialog {
        val calendar = Calendar.getInstance()
        return MaterialDatePicker.Builder.datePicker()
            .setSelection(calendar.timeInMillis)
            .build()
            .apply {
                addOnPositiveButtonClickListener { timestamp ->
                    val result = Bundle().apply {
                        putLong(RESULT_TIMESTAMP, timestamp)
                    }
                    parentFragmentManager.setFragmentResult(KEY_DATE, result)
                    dismiss()
                }
            }.createDialog(requireActivity(), null)
    }
}

3.4 Dialogs, sheets and transient UI

Not every UI interaction is a screen. Dialogs, bottom sheets, and transient overlays are components that float above the content, and each has a lifecycle and a set of constraints that differ from a full Activity.

DialogFragment and why it replaces AlertDialog

A DialogFragment is a Fragment that displays a dialog window. It exists because a plain AlertDialog cannot survive a configuration change — when the device rotates, the Activity is destroyed and recreated, and the dialog is lost (or worse, leaks the old Activity's window). A DialogFragment is managed by the FragmentManager, so it is retained across configuration changes and its lifecycle is tied to the host Activity. The dialog's window is a separate window (with its own WindowManager.LayoutParams) that is attached to the Activity's window token — this is why the dialog dismisses automatically when the Activity is destroyed. The MaterialAlertDialogBuilder provides Material-styled dialogs, and BottomSheetDialogFragment provides a Material bottom sheet (a panel that slides up from the bottom of the screen). The dismiss() method removes the dialog; dismissAllowingStateLoss() is the variant that does not throw if called after onSaveInstanceState (needed when the dialog is dismissed from a background callback).

class ConfirmDeleteDialog : DialogFragment() {

    // Use the factory pattern — never put arguments in a constructor
    companion object {
        fun newInstance(itemId: String) = ConfirmDeleteDialog().apply {
            arguments = Bundle().apply { putString("item_id", itemId) }
        }
    }

    override fun onCreateDialog(savedInstanceState: Bundle?): Dialog {
        val itemId = requireArguments().getString("item_id")!!
        return MaterialAlertDialogBuilder(requireContext())
            .setTitle(R.string.delete_confirmation)
            .setMessage(getString(R.string.delete_confirmation_message, itemId))
            .setPositiveButton(R.string.delete) { _, _ ->
                // Send the result back to the parent
                parentFragmentManager.setFragmentResult(
                    "delete_request",
                    Bundle().apply { putString("item_id", itemId) }
                )
            }
            .setNegativeButton(R.string.cancel, null)
            .create()
    }
}

// Usage from a parent fragment
class ItemListFragment : Fragment() {
    fun onDeleteClick(itemId: String) {
        ConfirmDeleteDialog.newInstance(itemId)
            .show(childFragmentManager, "confirm_delete")
    }
}

4 · Services and background work

4.1 Service types: started vs bound

Services are Android's mechanism for work that must continue when the user is not looking at the screen. The two service types — started and bound — have fundamentally different lifecycles and guarantees, and choosing the wrong type is the most common background-work mistake.

Started services: fire and forget

A started service is created by startService(intent). Once started, it runs indefinitely until it stops itself with stopSelf() or the system stops it. The component that started the service has no further connection to it — the service runs in the background even if the starting Activity is destroyed. The onStartCommand method is called every time startService is called, and its return value controls what happens when the system kills the service under memory pressure: START_STICKY means the system will recreate the service (with a null intent) when memory is available, START_NOT_STICKY means it will not, and START_REDELIVER_INTENT means it will recreate the service and redeliver the last intent. On API 26+, a started service that is not a foreground service is subject to background execution limits: after a few minutes in the background, the system stops it. In practice, this means a started service is only appropriate for short-lived work (a few minutes) or for work that must be a foreground service (a music player, a file download with a notification).

class DownloadService : Service() {

    override fun onBind(intent: Intent?): IBinder? = null

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val url = intent?.getStringExtra("download_url") ?: return START_NOT_STICKY

        // Promote to a foreground service — required on API 26+
        startForeground(NOTIFICATION_ID, createNotification())

        // Do the work on a background thread
        Thread {
            try {
                downloadFile(url)
                // Stop the service when done — this is the contract
                stopSelf(startId)
            } catch (e: IOException) {
                // Notify the user of the failure
                showErrorNotification(url, e)
                stopSelf(startId)
            }
        }.start()

        // If the system kills us, redeliver the intent so the
        // download can be retried.
        return START_REDELIVER_INTENT
    }

    private fun downloadFile(url: String) {
        val connection = URL(url).openConnection() as HttpURLConnection
        connection.connect()
        val input = BufferedInputStream(connection.inputStream)
        val output = FileOutputStream(getExternalFilesDir(null).resolve("download.zip"))
        input.copyTo(output)
        output.close()
        input.close()
    }

    companion object {
        const val NOTIFICATION_ID = 1001
    }
}

Bound services: a client-server connection

A bound service is created by bindService(intent, connection, flags). It provides a client-server interface — the service exposes an IBinder that clients use to call methods on the service. The service lives exactly as long as at least one client is bound: when the first client binds, onBind is called and the service starts; when the last client unbinds, onUnbind is called and the service is destroyed (unless it was also started with startService). The bound service pattern is appropriate for a music player that needs to be controlled by multiple components (the Activity, a notification, a widget) — the Activity binds to control playback, and the notification binds to display the current track. The Binder subclass is the simplest form: it returns the service instance directly, allowing clients to call public methods. For cross-process communication (AIDL), the Messenger or AIDL interfaces are needed, but in-process binding is far more common.

class MusicService : Service() {

    private val binder = MusicBinder()
    private var mediaPlayer: MediaPlayer? = null

    inner class MusicBinder : Binder() {
        fun getService(): MusicService = this@MusicService
    }

    override fun onBind(intent: Intent?): IBinder = binder

    fun play(trackUri: Uri) {
        mediaPlayer?.release()
        mediaPlayer = MediaPlayer().apply {
            setDataSource(this@MusicService, trackUri)
            prepare()
            start()
        }
    }

    fun pause() { mediaPlayer?.pause() }
    fun seekTo(position: Int) { mediaPlayer?.seekTo(position) }
    fun getCurrentPosition(): Int = mediaPlayer?.currentPosition ?: 0
    fun isPlaying(): Boolean = mediaPlayer?.isPlaying ?: false
}

// In the Activity:
class PlayerActivity : AppCompatActivity() {

    private var musicService: MusicService? = null
    private var bound = false

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName?, service: IBinder?) {
            val binder = service as MusicService.MusicBinder
            musicService = binder.getService()
            bound = true
        }

        override fun onServiceDisconnected(name: ComponentName?) {
            bound = false
        }
    }

    override fun onStart() {
        super.onStart()
        Intent(this, MusicService::class.java).also { intent ->
            bindService(intent, connection, Context.BIND_AUTO_CREATE)
        }
    }

    override fun onStop() {
        super.onStop()
        if (bound) {
            unbindService(connection)
            bound = false
        }
    }
}

4.2 Foreground services

A foreground service is a service the user is actively aware of — it must display a persistent notification. This is the only legitimate way to run long-running background work on modern Android, and the system enforces the contract strictly.

The foreground service contract

When you call startForeground(id, notification), you make a promise to the user: "this notification accurately represents the work being done, and it goes away when the work stops." The system enforces this in three ways. First, on API 26+, you must call startForeground within 5 seconds of startForegroundService or the system kills the app with an ANR (Application Not Responding). Second, the notification must be on a notification channel with IMPORTANCE_LOW or higher (low importance is required for the notification to not make a sound). Third, the notification cannot be dismissed while the service is running — the user can only swipe it away if the service is stopped. The foregroundServiceType attribute in the manifest (required on API 34+) declares what the service does: mediaPlayback, dataSync, location, phoneCall, camera, microphone, and others. The type determines which permissions the service needs and what the system allows it to do in the background.

class LocationTrackingService : Service() {

    private lateinit var fusedLocationClient: FusedLocationProviderClient
    private lateinit var locationCallback: LocationCallback

    override fun onCreate() {
        super.onCreate()
        fusedLocationClient = LocationServices.getFusedLocationProviderClient(this)

        locationCallback = object : LocationCallback() {
            override fun onLocationResult(result: LocationResult) {
                val location = result.lastLocation ?: return
                updateNotification(location)
                broadcastLocation(location)
            }
        }
    }

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // MUST call startForeground within 5 seconds
        startForeground(NOTIFICATION_ID, buildNotification("Starting..."))

        val request = LocationRequest.Builder(
            Priority.PRIORITY_HIGH_ACCURACY, 10_000L
        ).build()

        fusedLocationClient.requestLocationUpdates(
            request, locationCallback, Looper.getMainLooper()
        )
        return START_STICKY
    }

    private fun buildNotification(status: String): Notification {
        return NotificationCompat.Builder(this, CHANNEL_ID)
            .setContentTitle("Tracking your run")
            .setContentText(status)
            .setSmallIcon(R.drawable.ic_location)
            .setOngoing(true)  // cannot be dismissed by the user
            .setForegroundServiceBehavior(NotificationCompat.FOREGROUND_SERVICE_IMMEDIATE)
            .build()
    }

    override fun onDestroy() {
        super.onDestroy()
        fusedLocationClient.removeLocationUpdates(locationCallback)
    }

    override fun onBind(intent: Intent?): IBinder? = null

    companion object {
        const val NOTIFICATION_ID = 2001
        const val CHANNEL_ID = "location_tracking"
    }
}

Foreground service types and their constraints

The foregroundServiceType is not just a declaration — it is a contract with the system about what the service is allowed to do. A dataSync type service (file upload, database sync) is allowed to run for a limited time in the background on API 28+ — the system gives it a grace period after the app leaves the foreground, then stops it. A mediaPlayback type service (music, podcast playback) can run indefinitely while playing audio. A location type service (fitness tracking, navigation) can access location in the background, but only if the user has granted ACCESS_FINE_LOCATION or ACCESS_COARSE_LOCATION and the app has a valid use case. A camera type service (video calls) can access the camera while in the foreground. The system enforces these constraints at runtime: if a dataSync service tries to access location, the system throws a SecurityException. On API 34+, you must declare all types the service uses, separated by pipes: android:foregroundServiceType="location|microphone".

Foreground services are the most abused API on Android. The Play Store has strict policies: a foreground service must be user-initiated (the user starts it, not the app), it must show a notification that accurately reflects the work, and it must stop when the work is done. Using a foreground service to keep the app alive or to run invisible work is a policy violation that can get your app removed from the Play Store.

4.3 AlarmManager and exact alarms

AlarmManager is the system service that schedules work to run at a specific time, even if the app is not running. It is the right tool for calendar reminders, medication alarms, and time-sensitive notifications — and the wrong tool for everything else.

Exact vs inexact alarms and the battery tradeoff

An inexact alarm (set, setWindow) is delivered within a time window, and the system batches alarms from multiple apps to minimise wake-ups — this is the battery-friendly option. An exact alarm (setExact, setExactAndAllowWhileIdle) is delivered at the precise millisecond, and on API 31+ requires the SCHEDULE_EXACT_ALARM permission (which the user can revoke at any time) or the USE_EXACT_ALARM permission (which is granted only to apps whose core function is alarms — clocks, calendars, reminders). The battery cost of an exact alarm is real: it wakes the device from Doze mode, and each wake-up costs roughly 30 seconds of battery life. The rule is: use inexact alarms for everything except time-sensitive user-facing actions (a medication reminder that must fire at 8:00 AM, a timer that must beep at exactly 60 seconds). For periodic background work, use WorkManager instead — it batches, respects Doze, and survives process death.

// Scheduling a one-time inexact alarm
val alarmManager = getSystemService(AlarmManager::class.java)

val pendingIntent = PendingIntent.getBroadcast(
    this,
    REQUEST_CODE,
    Intent(this, ReminderReceiver::class.java).apply {
        putExtra("reminder_id", reminderId)
    },
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)

// Inexact — the system batches it with other alarms
alarmManager.set(
    AlarmManager.RTC_WAKEUP,
    triggerTimeMillis,
    pendingIntent
)

// Exact — requires SCHEDULE_EXACT_ALARM permission on API 31+
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
    if (alarmManager.canScheduleExactAlarms()) {
        alarmManager.setExactAndAllowWhileIdle(
            AlarmManager.RTC_WAKEUP,
            triggerTimeMillis,
            pendingIntent
        )
    } else {
        // Direct the user to the settings screen to grant the permission
        startActivity(Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM))
    }
} else {
    alarmManager.setExact(AlarmManager.RTC_WAKEUP, triggerTimeMillis, pendingIntent)
}

// Cancel a scheduled alarm — always cancel in onDestroy
// or when the reminder is dismissed
alarmManager.cancel(pendingIntent)

4.4 Doze, App Standby and battery optimisation

Doze and App Standby are the system's battery-saving mechanisms. They restrict network access, defer jobs, and limit wake locks when the device is idle. Understanding them is essential for any app that needs to do background work reliably.

How Doze works and what it restricts

Doze mode activates when the device is stationary, unplugged, and the screen is off for a period of time (typically 30 minutes to several hours). Once in Doze, the system defers all network access, ignores wake locks, defers standard AlarmManager alarms (but allows setExactAndAllowWhileIdle), and restricts JobScheduler and WorkManager jobs to brief "maintenance windows" (a few minutes every few hours). The device periodically exits Doze for a maintenance window, during which all deferred work is flushed. App Standby is a separate but related mechanism: when the user has not interacted with an app for several days, the app is put on standby — its network access is suspended, its jobs are deferred, and its push messages are deprioritised (still delivered, but may be delayed). The key insight for developers is that no background mechanism works reliably in Doze. The only guaranteed way to deliver a time-critical message is a high-priority FCM push (which wakes the app briefly) or an exact alarm (which the user must permit).

// Testing Doze mode from the command line:
// adb shell dumpsys battery unplug
// adb shell am set-inactive com.acme.app true
// adb shell dumpsys deviceidle force-idle
// (wait for Doze to activate)
// adb shell am set-inactive com.acme.app false
// adb shell dumpsys battery reset

// Requesting a Doze whitelist — only for apps whose core
// function requires background execution (VOIP, home automation)
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.M) {
    val powerManager = getSystemService(PowerManager::class.java)
    if (!powerManager.isIgnoringBatteryOptimizations(packageName)) {
        val intent = Intent(Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS)
        intent.data = Uri.parse("package:$packageName")
        startActivity(intent)
    }
}

// Checking if the app is exempt from battery optimisations
fun isBatteryOptimisationIgnored(context: Context): Boolean {
    val powerManager = context.getSystemService(PowerManager::class.java)
    return powerManager.isIgnoringBatteryOptimizations(context.packageName)
}

The battery optimisation whitelist is not a Get Out of Doze Free card. Apps on the whitelist still have their background work restricted in Doze — the whitelist only exempts the app from App Standby. And the Play Store policy explicitly restricts whitelist requests to apps with a legitimate need (home automation, VOIP, accessibility). Most apps should not request it.
