0.1 The servlet container model

A servlet is not a program. It is a class with a known shape that a container calls on your behalf. Almost every mistake in servlet code — leaked state, deadlocks, mysterious 404s — comes from forgetting which half of that arrangement owns what.

What the container actually does

The container is a Java process that owns a network port, a thread pool, and a class loader per deployed application. When a request arrives it parses the HTTP bytes into a jakarta.servlet.http.HttpServletRequest, matches the request path against the URL patterns declared by your servlets and filters, then invokes your code on a worker thread. After your method returns it serialises the HttpServletResponse, deals with keep-alive, chunked encoding, compression and timeouts, and returns the thread to the pool. It also compiles JSP files to servlets, manages HttpSession objects and their expiry, binds JNDI resources, applies declarative security constraints, and reloads your application when the deployment descriptor or the WAR changes. None of that is code you write; all of it is code you would otherwise write badly.

The request/response contract

There is no main, no socket, and no accept loop in your code. The container calls service() — which for HttpServlet dispatches to doGet, doPost, doPut, doDelete, doHead or doOptions based on the method. Two consequences follow immediately. First, request and response objects are valid only for the duration of that call: caching a HttpServletRequest in a field and reading it on the next request will show the wrong client's data, or throw once the container recycles the object. Second, the response is committed as soon as the buffer flushes — once bytes have left for the client you cannot add a header or call sendRedirect again without an IllegalStateException. Anything you may need to change must be decided before the first flush.

One instance, many threads

The container creates exactly one instance of each servlet per application (per ServletContext) and calls it concurrently from many threads. Instance fields are therefore shared mutable state unless they are immutable and safely published. A field holding a SimpleDateFormat, a Map, or a per-request value is a data race that will surface under load and never reproduce on a developer laptop. Put per-request data in method locals or request attributes; put genuinely shared data behind concurrent collections or, better, in a database or cache. Since Servlet 6.0 the Serializable marker has been dropped from GenericServlet and HttpServlet precisely because a servlet is not a data object — serialising one is meaningless.

// src/main/java/com/example/HelloServlet.java
package com.example;

import java.io.IOException;
import java.time.Instant;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

@WebServlet(name = "hello", urlPatterns = "/hello")
public class HelloServlet extends HttpServlet {

    // Immutable, set once during init: safe to share across threads.
    private String appName;

    @Override
    public void init() {
        appName = getServletContext().getInitParameter("app.name");
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        // Per-request state lives in locals, never in a field.
        String who = req.getParameter("name");
        resp.setContentType("text/plain;charset=UTF-8");
        resp.getWriter().printf("Hello, %s from %s at %s%n",
                who == null ? "world" : who, appName, Instant.now());
    }
}
<!-- The mapping the container builds from @WebServlet above -->
<servlet>
  <servlet-name>hello</servlet-name>
  <servlet-class>com.example.HelloServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>hello</servlet-name>
  <url-pattern>/hello</url-pattern>
</servlet-mapping>
Never store a request, response, session or JDBC Connection in a servlet field. The container pools those objects; holding one pins it, leaks it, or hands it to the wrong thread.

0.2 WAR packaging and the web application layout

A web application is a directory tree with a contract attached. The WAR format is that tree zipped, plus a META-INF/MANIFEST.MF. Learning the tree explains most "my class isn't found" and "my JSP can't see the jar" problems before they happen.

The standard layout

Everything not under WEB-INF is public web content: HTML, CSS, JavaScript, images, and JSP files if you keep them outside the protected directory. WEB-INF is the private half. WEB-INF/web.xml is the deployment descriptor; WEB-INF/classes holds your compiled classes and resources with package directories intact; WEB-INF/lib holds the jars the application needs; WEB-INF/tags and WEB-INF/tlds hold tag files and tag library descriptors. The container builds one class loader per web application whose classpath is those two directories — nothing else on the machine is on it. That isolation is why two applications in the same Tomcat can use incompatible versions of the same library, and why the application must ship every non-container dependency.

What WEB-INF guarantees

The container refuses to serve any URL whose path resolves inside WEB-INF or META-INF; a browser asking for /WEB-INF/web.xml gets 404, not the file. That makes WEB-INF the correct home for JSP fragments, tag files and templates that should only ever be reached through a controller's forward. Code that asks for a JSP under WEB-INF/views must be forwarded server-side — RequestDispatcher or jsp:include — because the client cannot request it directly. That is a feature: it prevents a reader from bypassing the controller and rendering a view with no model attached.

Class loading order and where a jar belongs

Put application libraries in WEB-INF/lib, not in the container's shared lib/. Tomcat's web application class loader searches WEB-INF/classes, then WEB-INF/lib, before delegating for classes it is not allowed to load itself; the JDK and the Jakarta EE API classes always come from the parent so that your jakarta.servlet.* classes are the container's, not a copy you accidentally bundled. Bundling jakarta.servlet-api into a WAR is a classic symptom of "the API is also the implementation" confusion: it must be provided scope in Maven or Gradle, so it compiles but is not packaged.

0.3 Tomcat, Jetty and Undertow

All three implement the same specifications, so your servlets compile and run unchanged against any of them. What differs is the embedding API, the operational surface, and how each project tracks the Jakarta EE release train.

Version alignment is the first thing to check

A container implements a fixed specification version, and the specification is what determines the package names and the available APIs. Tomcat 9 speaks Servlet 4.0 in the javax.servlet namespace and is the last line that does. Tomcat 10.1 speaks Servlet 6.0 and JSP 3.1 in jakarta.servlet. Tomcat 11 speaks Servlet 6.1 and JSP 4.0, the Jakarta EE 11 generation, and requires Java 17 or newer. Jetty and Undertow follow the same rule: Jetty 12 introduced explicit environments — ee8, ee9, ee10, ee11 — so one Jetty installation can host applications from several Jakarta EE generations side by side, which no other container offers as cleanly. Mixing a Servlet 6.0 application with a Servlet 4.0 container produces a ClassNotFoundException for jakarta.servlet.http.HttpServlet the moment deployment starts.

Standalone versus embedded

Standalone means the container is a product you install and configure, and you hand it a WAR. That is the right shape for a shared server, for operations teams who expect a server.xml and a log directory, and for anyone who wants the management story to be someone else's problem. Embedded means the container is a library inside your application, started by a few lines of Java, which is how Spring Boot, Quarkus and most container images work. Embedded gives you reproducible configuration in version control and a single process to monitor; it costs you the ability to deploy a new WAR without restarting the JVM. Production teams commonly run standalone for long-lived shared hosts and embedded for a container-per-application model in Kubernetes. Tomcat supports both from the same jars, so a choice made for development does not have to be the choice made for production.

0.4 JSP, Servlet and the alternatives

JSP is a template language that compiles to a servlet. That single sentence explains both its strengths — it runs on any container with no extra runtime — and its weaknesses, since everything it does is ultimately a Java method writing to a buffer.

What JSP actually becomes

On first request the container translates a .jsp file into a Java class extending HttpJspBase, compiles it, and runs it as a servlet. Template text becomes out.write(...) calls; declarations become instance members; expressions become arguments to out.print(...). The generated class has a _jspService method, a jspInit() and a jspDestroy() that mirror the servlet lifecycle. This is why JSP enjoys the container's threading, session and security models for free, and why the first hit on a page is slower than the rest. The translation is also why WEB-INF/views is the safe place for a view: it compiles and runs exactly like a servlet, but cannot be requested by a client that skips the controller.

The namespace break: javax to jakarta

In 2018 the specification work moved from Oracle to the Eclipse Foundation, and the Jakarta EE project could not take the javax namespace with it. Jakarta EE 9 was therefore a release whose only purpose was the rename: every javax.servlet.* import became jakarta.servlet.*, and the JSTL tag URIs, which had been URLs owned by Oracle, changed from http://java.sun.com/jsp/jstl/core to jakarta.tags.core in JSTL 3.0. Binary compatibility was deliberately sacrificed, because the alternatives were worse: shipping the same package names from two organisations would have made the class path ambiguous forever. The practical effect in 2026 is that a guide, a library or a Stack Overflow answer written before 2020 will hand you a javax import that does not compile against a modern container. The fix is mechanical — rename the package — but the version of the library matters too, because a javax-based JSTL jar will load without error and then silently never match your taglib URI.

// Before Jakarta EE 9 — does not compile on Tomcat 10+ or any EE 9+ container
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.jsp.JspWriter;
import javax.servlet.jsp.tagext.SimpleTagSupport;

// After — Jakarta EE 9 / 10 / 11
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.jsp.JspWriter;
import jakarta.servlet.jsp.tagext.SimpleTagSupport;
<%-- taglib URIs also moved, in JSTL 3.0 (Jakarta EE 11) --%>
<%@ taglib prefix="c" uri="http://java.sun.com/jsp/jstl/core" %>   <%-- JSTL 1.x / 2.x --%>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>                  <%-- JSTL 3.0 --%>

<%-- both URIs are recognised by the JSTL 3.0 implementation,
     so the old spelling keeps working; new code should use jakarta.tags.* --%>

When JSP is still the right tool, and when it is not

Server-rendered HTML with a controller in front remains an excellent fit for form-heavy internal applications, admin screens and content sites, and a JSP plus JSTL stack has no build step and no JavaScript toolchain to keep patched. What JSP is a poor fit for is a client that owns the rendering: if the interface is a single-page application, or the same data must feed a mobile client and a browser, then the server should return JSON and JSP is dead weight. The modern alternatives sit on the same servlet API — Thymeleaf and FreeMarker are template engines with better syntax and no compile step, Spring MVC's DispatcherServlet is a servlet that adds routing and argument binding, and JSF, now Jakarta Faces, wraps the whole component model on top. Learning servlets and JSP first is what makes all of them legible: each is a layer over the request/response contract described in 0.1.

1.1 Lifecycle: instantiation, init, service, destroy

The container decides when your servlet object is created, initialised and thrown away. Knowing the sequence tells you exactly where an expensive resource may be created, and why init is not a constructor.

The three states

A servlet moves through initialised, serving and destroyed. The container instantiates the class with its no-argument constructor, calls init(ServletConfig) exactly once before any request is served, then calls service() any number of times from any number of threads, then calls destroy() once when the application stops or is undeployed. The object is discarded and never reused. A servlet that throws from init fails to load: the container logs the exception and marks the servlet unavailable, and every request to it becomes a 404 or a 500 depending on how the failure is reported. That is why init() is the correct place to fail fast on a missing configuration value — the deployment breaks loudly instead of one request at a time.

Why not use the constructor

The constructor runs before the servlet has a ServletConfig, so getInitParameter, getServletContext and getServletName are not yet available; the spec forbids touching them there, and a container that has not injected the config yet may throw a NullPointerException or behave unpredictably. Use the no-argument constructor for nothing at all, and override init() — the argument-less overload, which the container's own init(ServletConfig) delegates to after storing the config. If you do need to override init(ServletConfig) directly, call super.init(config) first or every getServletContext() call in your code will throw.

Lazy, eager and the load-on-startup promise

By default a servlet is initialised on the first request that maps to it, so the first visitor pays the initialisation cost. @WebServlet(loadOnStartup = 1), or the matching <load-on-startup> element, orders initialisation at application start instead; a lower number starts earlier, and ordering across servlets is by ascending value without any guarantee of relative order among equal values. Use eager initialisation for anything that must exist before traffic arrives — a scheduled job, a warm cache, a pool — and for making a misconfiguration fail at deploy time rather than at 3 a.m. A common pattern is a small "startup" servlet whose only job is to verify configuration and fail the deployment if it is wrong.

@WebServlet(urlPatterns = "/report", loadOnStartup = 1)
public class ReportServlet extends HttpServlet {

    private DataSource pool;          // created once, shared by all threads

    @Override
    public void init() throws ServletException {
        // ServletConfig is available here; init parameters and the
        // ServletContext can be read, and failure aborts deployment.
        String jndi = getInitParameter("dataSource");
        try {
            var ctx = new InitialContext();
            pool = (DataSource) ctx.lookup(jndi);
            pool.getConnection().close();     // verify the pool works now, not later
        } catch (Exception e) {
            throw new ServletException("datasource " + jndi + " unusable", e);
        }
    }

    @Override
    public void destroy() {
        // released automatically when the application stops;
        // close only resources you own, never the container's pool
        pool = null;
    }
}
<!-- web.xml equivalent: eager init and an init parameter -->
<servlet>
  <servlet-name>report</servlet-name>
  <servlet-class>com.example.ReportServlet</servlet-class>
  <init-param>
    <param-name>dataSource</param-name>
    <param-value>java:comp/env/jdbc/app</param-value>
  </init-param>
  <load-on-startup>1</load-on-startup>
</servlet>
destroy() is not guaranteed to run on a kill -9, and it may run while other requests are still in flight during an undeploy. Do not depend on it for durability — commit work as it completes, and let a database transaction be your guarantee.

1.2 HttpServlet: doGet, doPost and safe methods

The HTTP method is a contract about side effects, not a style choice. Getting the mapping wrong produces caching bugs, double-submitted orders and crawlers that delete records.

What each do method means

doGet must be safe and idempotent: it may be cached, prefetched, retried by a proxy, and crawled. doPost is neither, and is therefore the correct verb for anything that changes state. doPut and doDelete are idempotent — repeating the call should leave the same result — and belong to REST-style endpoints. doHead must produce the same headers as doGet with no body; if you override doGet and never override doHead, the default implementation calls doGet through a response wrapper that discards the body, which is correct but still runs your query. doOptions answers the CORS preflight when you are not using a filter for it. The base implementations of all of them return a 405 with an Allow header, so a servlet that only implements doPost correctly rejects a GET rather than silently doing nothing.

Parameter handling and encoding

getParameter reads both the query string and, for application/x-www-form-urlencoded POSTs, the body. It returns null for a missing name and an empty string for a present-but-empty value — a distinction worth preserving, because "not supplied" and "supplied as blank" usually mean different things. For a GET, the container decodes the query string using the connector's URI encoding, which is UTF-8 on Tomcat 10+ by default. For a POST body, decoding uses the request character encoding, which defaults to UTF-8 on the Servlet 6.x containers but must be set before the first getParameter call if you want to force it: calling setCharacterEncoding after parameters have been parsed has no effect at all.

Reading the body exactly once

getParameter consumes the request body, so mixing it with getReader or getInputStream on the same request fails — one of them will get nothing. Pick one style per endpoint: form parameters, or a raw body. If an API accepts JSON, read the stream and parse it yourself or with a library, and do not call getParameter anywhere in that method, including in a helper it calls.

@WebServlet("/search")
public class SearchServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        req.setCharacterEncoding("UTF-8");          // harmless for GET/query, needed for POST
        String q = req.getParameter("q");
        int page = parsePage(req.getParameter("page"));

        if (q == null || q.isBlank()) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "q is required");
            return;                                  // never fall through after sendError
        }
        req.setAttribute("results", service.search(q, page, 20));
        req.setAttribute("query", q);
        req.getRequestDispatcher("/WEB-INF/views/search.jsp").forward(req, resp);
    }

    private int parsePage(String raw) {
        try {
            return Math.max(1, Integer.parseInt(raw));
        } catch (NumberFormatException | NullPointerException e) {
            return 1;                                 // default beats a 500 for a bad query param
        }
    }
}
// POST: the submit endpoint. Never a GET, or a refresh re-orders.
@WebServlet("/orders")
public class CreateOrderServlet extends HttpServlet {

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException, ServletException {
        req.setCharacterEncoding("UTF-8");           // BEFORE any getParameter call
        String sku = req.getParameter("sku");
        String qtyRaw = req.getParameter("qty");

        Map<String, String> errors = new LinkedHashMap<>();
        if (sku == null || !sku.matches("[A-Z0-9-]{3,20}")) errors.put("sku", "Invalid SKU");
        int qty = 0;
        try { qty = Integer.parseInt(qtyRaw); } catch (Exception ignored) { }
        if (qty < 1 || qty > 99) errors.put("qty", "Quantity 1-99");

        if (!errors.isEmpty()) {
            req.setAttribute("errors", errors);
            req.getRequestDispatcher("/WEB-INF/views/order-form.jsp").forward(req, resp);
            return;
        }
        orders.create(sku, qty);
        resp.sendRedirect(req.getContextPath() + "/orders?ok=1");   // POST-redirect-GET
    }
}

1.3 Working with the request and response objects

The two objects mirror the HTTP message. Most of what you will ever need is reading headers, writing headers, and knowing the moment at which the response stops being changeable.

The request in detail

A HttpServletRequest exposes the method, URI, context path, servlet path and path info as separate values, and mixing them up is the most common cause of broken links. For a request to /shop/product/42 mapped to a servlet with context path /shop and pattern /product/*, getRequestURI() returns the whole /shop/product/42, getContextPath() returns /shop, getServletPath() returns /product and getPathInfo() returns /42. Always build outbound URLs from getContextPath() plus a relative path; hard-coding /product/42 works only while the application is deployed as ROOT. Headers are available by name via getHeader and wholly via getHeaderNames, with getIntHeader and getDateHeader for typed access. Since Servlet 3.1 the request also exposes the parsed mapping through getHttpServletMapping(), useful for logging which pattern caught a request.

Building the response

Set setContentType before writing, and prefer the form with the charset attached — text/html;charset=UTF-8 — over a separate setCharacterEncoding call, because it is one decision in one place. Note that setCharacterEncoding called after getWriter is ignored: the writer has already been created with the old encoding, and the response is on its way. Status codes: setStatus sets the code without a body, sendError sets the code and asks the container to render its error page, and sendRedirect sets 302 (or 303) with a Location header. Once the buffer is flushed all three throw IllegalStateException. If you might need to change your mind, keep the default 8 KB buffer, do the risky work first, and only then write.

Caching, streaming and large bodies

Responses that can be cached should say so explicitly: Cache-Control: max-age=3600, public for static content, no-store for anything containing a session token or personal data. For downloads, set Content-Disposition: attachment; filename="...", Content-Length when you know it, and copy the stream in a fixed-size loop rather than reading it entirely into a byte array — the container's thread is a scarce resource and a 200 MB heap allocation per concurrent download ends in an OutOfMemoryError under load.

1.4 URL mapping: annotations versus web.xml

Annotations and web.xml describe the same metadata. Choose one as the source of truth per project, because mixing them makes the effective mapping a join of two files.

The four mapping forms

An exact mapping such as /orders/edit matches one path. A prefix mapping /api/* matches an entire subtree. An extension mapping such as *.jsp matches by suffix but has been forbidden for servlets since Servlet 3.0 — only the container's own JSP servlet uses it, mapped in conf/web.xml. And / is the default servlet mapping, matching everything not matched more specifically; Tomcat reserves it for static content, and replacing it with your own servlet stops the container serving CSS, images and JavaScript. Resolution is longest-prefix-wins, then extension, then default, with an exact match taking priority over any pattern. Two servlets claiming the same pattern is a deployment error that surfaces at startup, which is the good outcome; a pattern that silently shadows static files is the bad one.

@WebServlet and its attributes

The annotation is concise and lives next to the code, and a single class may declare several patterns in one annotation. name defaults to the fully qualified class name; initParams takes an array of @WebInitParam; loadOnStartup, asyncSupported and description map directly to descriptor elements. The trade-off is that an annotation cannot be changed without recompiling and repackaging, it cannot be removed from outside the class, and mapping order relative to other deployments is not expressible.

web.xml, metadata-complete and why large projects still use it

The deployment descriptor is data: operations can patch it in a container image, it can be templated per environment, and it can express ordering with <absolute-ordering> and <ordering> that annotations simply cannot. It also carries the application-wide settings that have no annotation form: error pages, session timeout, welcome files, security constraints, JSP property groups, MIME mappings. Setting metadata-complete="true" on the web-app element tells the container not to scan for annotations at all, which shortens startup and prevents a stray @WebServlet in a dependency jar from mapping itself into your application. That last point is a real production concern: a library shipped with annotations will register its own servlets and filters the moment it lands in WEB-INF/lib unless you either exclude it or set metadata-complete.

2.1 HttpSession: what the container keeps for you

HTTP is stateless; a session is the container's fiction of continuity. Understanding that the session is a server-side map with a client-side key removes the mystery from every "the user got logged out" bug.

The mechanism

The first time your code calls req.getSession(), the container creates an HttpSession — a map of attributes with an id, a creation time, a last-access time and a max-inactive-interval — and asks the client to remember the id. By default that is a JSESSIONID cookie, Path=/ for the context. On each subsequent request the container looks up the existing session and hands you the same object, so session.setAttribute("userId", 42) done in a login servlet is visible in every later request. Calling req.getSession() creates a session if none exists; req.getSession(false) returns null instead, and that is what a filter should use to check whether someone is logged in — asking with the one-argument form turns anonymous visitors into session-holding visitors, which quietly breaks caching and fills your session store with empty rows.

Expiry, invalidation and what happens to attributes

The timeout is a sliding window measured from the last access, not from creation: every request unbound to an existing session resets it. invalidate() ends a session immediately and unbinds its attributes; setMaxInactiveInterval(seconds) overrides the configured default for one session, with a negative value meaning "never expire" — which is almost always the wrong answer, because the container still holds the memory. An attribute bound with setAttribute is kept; one bound with setAttribute followed by none is kept too — there is no difference; only an explicit removeAttribute or the session ending removes it. If the attribute value implements HttpSessionBindingListener, the container calls its valueBound and valueUnbound methods, which is the correct hook for closing a per-session resource. And because the session may be passivated to disk in a clustered container, everything stored in it must be Serializable unless you configure the session manager otherwise.

Configuration

Session policy is declared in web.xml or set programmatically in a ServletContextListener via ServletContext#setSessionTrackingModes and SessionCookieConfig. Two settings matter more than the rest: the cookie's HttpOnly flag, which stops JavaScript from reading the session id, and the cookie's Secure flag, which stops it travelling over plain HTTP. Set both, in every environment that touches a real user, and set the tracking mode to COOKIE so the container never accepts a session id from a URL.

2.2 Cookies, attributes and SameSite

Cookies are the transport for session ids, CSRF tokens, locale preferences and consent flags. Their security properties are decided by four attributes, and three of them are easy to forget.

What a cookie is

A cookie is a name/value pair with a domain, a path, an expiry and flags. The container sends it in a Set-Cookie header; the browser returns it on every matching request. Matching is by domain and path, so a cookie with Path=/shop is not sent for /admin. A session cookie has no Max-Age and lives until the browser closes; a persistent cookie carries Max-Age or Expires. In Jakarta EE the class is jakarta.servlet.http.Cookie; since Servlet 6.0 it has a general setAttribute(String, String) method, which is the portable way to set SameSite and Partitioned rather than reaching into a container-specific API.

Max-Age versus Expires, and locale traps

setMaxAge(int) takes seconds; zero deletes the cookie, and a negative value makes it a browser-session cookie. setMaxAge(0) is the only correct way to log a user out of a cookie, and it must be sent with the same path and domain that created it or the browser keeps two cookies with the same name and sends both. Encoding matters too: RFC 6265 restricts the name and value to a small character set, so a value containing spaces, quotes or commas must be URL-encoded before it is set and decoded after it is read. The Java implementation does not do this for you.

SameSite, and why it is the CSRF control that costs nothing

SameSite=Lax means the cookie is sent on top-level navigations to your origin but not on cross-site form posts or fetches; Strict means it is not sent on cross-site navigation at all, which logs users out when they follow an inbound link; None means it is always sent and requires Secure to be accepted by modern browsers. For a session cookie, Lax is a defensible default and Strict is right for anything transactional. Because a modern browser drops a SameSite=None cookie without Secure, the combination is not a preference — it is a requirement, and forgetting it makes an embedded or cross-origin flow fail in a way that looks like a random logout.

2.3 URL rewriting and tracking modes

Before cookies were universal, the session id travelled in the URL. The specification still supports it, and modern practice is to switch it off — because a session id in a URL leaks through every log, referrer header and shared link.

How it worked and why it is a hazard

With URL tracking enabled, resp.encodeURL("/cart") appends ;jsessionid=... when the container believes the client does not accept cookies. Anyone who copies that URL gives away their session, and anyone who reads the web server's access log sees it. The session id also ends up in a Referer header on every outbound link. Because the container decides per response whether to add the id, a single misconfigured client can produce URLs with the id embedded even in an application that "does not use" URL rewriting. ServletResponse#encodeRedirectURL has the same behaviour for redirect targets. The fix is to declare <tracking-mode>COOKIE</tracking-mode> so the container will not accept a session id from a path parameter at all, and to keep encodeURL calls in templates anyway as harmless no-ops — they are required by the API contract for the case where a container is configured otherwise.

Sessions without cookies, legitimately

Some clients genuinely cannot hold cookies — a transient link in an email, a payment provider's return URL, a health check. The correct answer is not to fall back to URL rewriting but to issue a short-lived, single-purpose token: store the payload server side, put an opaque random id in the link, validate it once, and expire it. That is a signed-link pattern rather than a session, and it avoids the failure mode where a legitimate session id circulates in an inbox.

Distributed sessions

When more than one container instance serves traffic, a session created on instance A must be readable on instance B or the user is bounced back to the login page at random. Three approaches exist. Sticky sessions pin a client to an instance via the load balancer — simplest, and it fails when an instance is removed. Session replication copies sessions between cluster members; Tomcat supports it through the DeltaManager or the more efficient BackupManager, but the cost grows with cluster size and every attribute must be serialisable. A shared session store externalises the map to Redis, a database, or a servlet container-specific store such as Tomcat's PersistentManager; it costs a network hop per request but removes the affinity requirement entirely. For most applications in 2026 the third option — a small cookie holding a signed, encrypted reference to server-side state — is the cleanest, and it is also why stateless tokens for API calls sit alongside cookie sessions for browsers.

2.4 Session id security

A session id is a bearer credential. Anyone holding it is the user. Four attacks follow from that single fact, and each has a specific, cheap defence.

Session fixation

In a fixation attack the attacker obtains a valid session id — by planting it via a URL parameter, a subdomain cookie, or a cross-site request — and then tricks the victim into authenticating with that same id. After login the attacker's browser is already inside the authenticated session. The defence is to change the id at the moment privileges change: req.changeSessionId() (Servlet 3.1) keeps the session object and its attributes but issues a new id, and getSession().invalidate() followed by a fresh getSession() is the older, heavier alternative. Call it on login, on privilege escalation, and on logout; do not call it on every request, because a session id that changes constantly breaks concurrent requests from the same page.

Entropy, id length and the container's defaults

The id must be unguessable, and the container's default is generated with SecureRandom: Tomcat produces a 16-byte hexadecimal id by default and allows a larger one via sessionIdLength in the context. Do not build your own id generator; do not derive an id from a user id, a timestamp or an incrementing counter. If you must generate a token of your own — a CSRF token, a password-reset token — use SecureRandom and encode at least 128 bits of output as base64url or hex, and compare it in constant time when it is a secret.

Transport, logout and timeout

A session id sent over plain HTTP is exposed to anyone on the path. The Secure cookie flag prevents the browser from sending it on a plaintext request, which also means a single http:// link to your site looks like a logout — set up HSTS and a permanent redirect to HTTPS so links never resolve to plaintext. Logout must invalidate the session server-side, not merely clear the cookie: a merely-cleared cookie leaves a live session that an attacker holding the id can still use. Finally, set a timeout that matches the sensitivity of the application — fifteen minutes for banking, hours for a wiki — and remember that the timeout is the only thing limiting how long a stolen id stays useful.

// Login: authenticate, then move to a new session id
@WebServlet("/login")
public class LoginServlet extends HttpServlet {
    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        String user = req.getParameter("user");
        char[] pass = req.getParameter("pass").toCharArray();

            Arrays.fill(pass, '\0');
            resp.sendError(HttpServletResponse.SC_UNAUTHORIZED);

}

3.1 The page directive and what it configures

A JSP file is a translation unit, and the page directive is where the translation is configured. Almost every encoding or session bug in a JSP traces back to an attribute that was left at its default.

The directive syntax and its scope

A directive starts with <%@ and ends with %>, takes a name and a list of name="value" attributes, and produces no output. page directives apply to the whole translation unit, and the specification requires that most attributes appear at most once — import is the exception, because it may be repeated and each occurrence adds to the generated import list. A JSP that includes another file statically shares one translation unit, so a page directive in the included file must not conflict with the including file's: two different contentType values in one translation unit is a translation error, not a silent override.

The attributes that matter

contentType sets the response MIME type and, when it includes a charset, the character encoding the container uses when writing the response and when decoding the page source. pageEncoding sets only the source-file encoding, which is what you need when the file on disk is not UTF-8. session="false" stops the container creating an HttpSession for that page, which matters for cacheable anonymous pages and for error pages, where creating a session in the middle of a failure is unhelpful. isErrorPage="true" exposes the exception implicit object and is required by errorPage on other pages. isELIgnored="true" disables expression language evaluation for the page — dangerous, because it silently turns ${user.name} into literal text rather than an error. trimDirectiveWhitespaces="true" removes the blank lines left behind by directives, which is the difference between tidy HTML and pages with a dozen empty lines at the top. buffer="8kb" and autoFlush="false" are the last pair worth knowing: with auto-flush off, a buffer overflow throws instead of committing, which is a debugging aid rather than a production setting.

Encoding is a two-sided decision

The page's source encoding and the response's output encoding are separate, and getting only one right produces mojibake in one direction or the other. The reliable combination is a UTF-8 file on disk, pageEncoding="UTF-8" to match, and contentType="text/html;charset=UTF-8" so the browser decodes the response correctly. Where the whole application shares one encoding, put it in a JSP property group rather than repeating it on every page — the container then applies it across all matching files, including ones you forget about.

3.2 Scripting elements, expressions and comments

Scriptlets are the oldest part of JSP and the part you should write least. They still matter, because you will read them in legacy code and because declarations remain the only way to add a method to the generated servlet.

The four elements

An expression <%= expr %> prints the value of a Java expression into the response and is exactly equivalent to out.print(expr); a scriptlet <% code %> runs statements inside _jspService; a declaration <%! code %> adds members to the generated class, outside any method, so its variables are instance fields and therefore shared by every thread — the same data race described in 0.1, now hidden in a template. A JSP comment <%-- ... --%> is stripped at translation time and never reaches the browser; an HTML comment <!-- ... --> is emitted verbatim, including anything a scriptlet printed inside it, which is a real information disclosure when the comment contains a developer's note about a query.

Why the style guidance changed

The original JSP design put Java control flow in the page: if blocks, loops, database calls. That works, and it produces views where the HTML skeleton is buried between braces, no designer can edit the file, and a missing brace produces a compilation error with a line number in a file that does not exist on disk. The specification's answer arrived in two stages: the expression language, so that ${user.name} replaces <%= user.getName() %>, and JSTL, so that loop and condition tags replace braces entirely. The modern convention is a strict split — no scriptlets, no expression scriptlets, and declarations only where a genuinely shared helper is unavoidable, which usually means the helper belongs in a Java class instead.

What to keep, and what to read

You will meet scriptlets in every pre-2015 application, and reading them requires knowing the implicit objects and the generated class shape. It is also worth knowing that <%= ... %> does not escape its output: printing a user's name with it is an XSS bug, while <c:out> and ${fn:escapeXml(...)} escape by default. That single difference is why expression scriptlets are the most reliable indicator of an unsafe view.

3.3 Static include, dynamic include and forward

There are three ways to put one file's content into another, and they are not interchangeable: two happen at different times and one is not a composition mechanism at all.

Static include: one translation unit

<%@ include file="header.jsp" %> runs at translation time — the container splices the included file's text into the including file before compiling it. The result is a single generated servlet, so it is fast, and the included file can contribute scriptlets, declarations and even page directives that affect the parent. The price is that the include cannot be dynamic: the file is fixed when the page compiles, a change to the included file requires re-compiling the parent, and the container may or may not notice the dependency depending on configuration, so a stale fragment is a common development surprise. Static includes are right for fragments that are structurally part of a page: a header, a footer, a repeated table header.

Dynamic include: separate servlet, same request

<jsp:include page="banner.jsp" /> runs at request time. The container dispatches to the included resource, which is translated and compiled as its own servlet, and its output is written into the response at that point. Because the include happens during the request, the included page cannot change the parent's response headers or status code after the parent's output has been flushed — headers set inside a dynamic include are ignored. It can read and write request and session attributes, which makes it the correct mechanism for conditionally-present content such as a login box, a cart summary, or a fragment whose visibility depends on the request. <jsp:include> also accepts <jsp:param> elements, which add request parameters visible only to the included page.

Forward is not an include

<jsp:forward page="..." /> and RequestDispatcher#forward abandon the current response and hand the request to another resource entirely. The original page's output is discarded unless it has already been flushed, which is exactly why "forward after write" produces either a blank page or an IllegalStateException. Forward is how a controller hands off to a view (chapter 6); include is how a view assembles itself from parts. Using one where the other belongs is the usual cause of a page that renders half of itself.

3.4 The taglib directive and the generated servlet

The taglib directive is one line, but it is the door to every tag library in the application. Understanding what the container does with the URI explains why a tag sometimes appears as literal text.

Prefix, URI and resolution

<%@ taglib prefix="c" uri="jakarta.tags.core" %> declares that the prefix c refers to the tag library identified by that URI. The container resolves the URI in three ways, in order: an entry in web.xml's <jsp-config><taglib> mapping, a <uri> element in a TLD file under WEB-INF or inside a jar's META-INF, or a container-recognised URI for a library it ships with. The prefix is arbitrary — <%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %> and prefix="f" for the same URI are equivalent — but the URI is not, which is why the java.sun.com to jakarta.tags change in JSTL 3.0 matters: a javax-era JSTL jar on the class path does not advertise the new URI, and the tags then render as literal text in the browser with no error at translation time in some configurations.

What the container generates

For a JSP named list.jsp the container writes a class in the application's temporary directory — work/Catalina/localhost/myapp/org/apache/jsp/WEB_002dINF/views/list_jsp.java on Tomcat — which extends the container's base class, implements jakarta.servlet.jsp.HttpJspPage, and contains one _jspService(HttpServletRequest, HttpServletResponse) method. Reading that file is the fastest way to diagnose a JSP problem: it shows the exact line your exception came from, the imports that were added, and whether your expression was treated as EL or as literal text. The generated source is rewritten on every recompile, so never edit it — the file is a build artefact and the container will overwrite it.

When a tag prints as text

If <c:out> appears in the browser's output, the prefix was not recognised. The four causes, in rough order of frequency: the JSTL jar is missing from WEB-INF/lib (Tomcat does not bundle JSTL); the jar is the javax era and only advertises the old URI; the taglib directive is missing from that particular file, including a statically-included fragment that uses the tag; or isELIgnored was set true by a property group and the page no longer evaluates expressions. All four are visible in one place — the generated servlet will show the tag as an out.write("<c:out ...") call, which is the signature of "treated as literal text".

4.1 The implicit objects

A JSP has nine objects in scope without a single import. They are the container's plumbing, exposed so that a template can reach the request, the session and the response without a scriptlet.

The nine, and what each is for

request is the HttpServletRequest for this request; response is the HttpServletResponse; out is a JspWriter that buffers output and is the object expressions write to; session is the HttpSession, absent when the page declared session="false"; application is the ServletContext, shared by the whole web application; config is the ServletConfig for the generated servlet, which is how a page reads its own init parameters; pageContext is the central object of the JSP API, giving access to all the others, to the four attribute scopes, to the request dispatcher and to the exception; page is the generated servlet instance itself, an alias for this, and is almost never useful; and exception exists only on a page with isErrorPage="true".

pageContext is the useful one

Because pageContext can reach everything, it is the object templates actually use. pageContext.getAttribute(name, scope) and setAttribute read and write the four scopes explicitly; pageContext.findAttribute(name) searches page, then request, then session, then application, and returns the first match, which is exactly what an EL expression does implicitly. pageContext.include(path) and pageContext.forward(path) perform a dispatch from within a page. And since Servlet 3.1/JSP 2.3, pageContext.request also exposes the parsed servlet mapping, so a page can log the pattern that caught it.

Using them from EL and from a tag

EL exposes the same objects as implicit variables: ${requestScope}, ${sessionScope}, ${applicationScope}, ${pageScope}, ${param} for query and form parameters, ${paramValues} for multi-valued ones, ${header} and ${headerValues} for request headers, ${cookie} for cookies, ${initParam} for context init parameters, and ${pageContext} for the object itself. Note that ${param.x} always yields a String — the first value — and never null, giving an empty string for a missing parameter, which is a frequent source of validation bugs: check ${empty param.x} rather than comparing to null. ${paramValues.x[0]} is the explicit form when a parameter repeats.

4.2 The four scopes, and choosing between them

Scope is lifetime plus visibility. Picking the wrong one produces data that vanishes too early, or leaks from one user to another — the latter being the more dangerous mistake.

What each scope means

page is the narrowest: attributes live only for the current generated servlet invocation, and since a forward creates a new page context, page-scoped values do not survive a forward. request lasts from the moment the container accepts the request until the response is complete, surviving forwards and includes — this is where a controller puts model data for a view, and it is the default choice for anything a template needs. session lasts for the life of the HttpSession and is visible to that user across requests, including across contexts? no: a session is per web application, so two applications on the same host do not share session attributes even if cookies would allow it. application is the ServletContext: one per web application, shared by every user and every thread, alive until undeploy. The dangerous one is application — a value written there on behalf of one user is readable by every other user, which turns a convenience cache into a data leak.

Resolution order and shadowing

Both pageContext.findAttribute(name) and a bare EL reference such as ${total} search page, then request, then session, then application, and stop at the first hit. That means an attribute named total in the session silently shadows an application-wide one of the same name. Because the search is silent, a stale session attribute can make a page render yesterday's value; the fix is to namespace attribute names — order.total, cart.total — or to set flash-style attributes and remove them as they are consumed.

Flash messages, and the request-versus-session dance

After a POST-redirect-GET the "saved successfully" message must survive exactly one redirect, so it cannot live in the request scope of the POST and cannot be allowed to show twice. The usual pattern is a session-scoped attribute that the target view reads and immediately removes — a flash message. It is worth writing the removal into the view itself rather than the controller, because a controller that forgets to clean up leaves the message on every subsequent page.

// Controller: request scope for the model, session scope for the flash
req.setAttribute("orders", dao.findRecent(20));           // survives the forward
req.getRequestDispatcher("/WEB-INF/views/orders/list.jsp").forward(req, resp);

getServletContext().setAttribute("buildVersion", "2026.10.1");

// Page scope: a helper object used only inside this view's translation
pageContext.setAttribute("rowClass", "even", PageContext.PAGE_SCOPE);

4.3 EL syntax, operators and null safety

Expression Language is a small language with a large surface of conveniences. Its most valuable property is that it never throws a NullPointerException — a chain of property reads over a null simply yields null.

Delimiters and accessors

Immediate evaluation uses ${...} and is what JSP templates use. Deferred evaluation uses #{...} and is evaluated later by whichever framework owns the expression — that is a Faces and CDI convention, not a JSP one. Property access can be written ${user.name} or ${user['name']}; the bracket form is required when the key is not a valid identifier, computed, or contains a hyphen or dot, as with ${header['user-agent']} and ${order['ship-to']}. For a Map, the dot form looks up the key; for a bean, it calls the getter — which is why ${user.class} resolves to a getter for class rather than the Class object, and why naming a property the same as a forbidden name is a class of bug all its own.

The operator set

Arithmetic uses + - * / % with the word forms div and mod available so that a % inside a JSP attribute is not confused with a directive. Comparison has both symbols and words — ==/eq, !=/ne, </lt, >/gt, <=/le, >=/ge — and inside an XML or JSP attribute you should use the word forms or the symbols must be escaped as entities, which is why word forms are the convention in tag attributes. Logical operators are &&/and, ||/or, !/not. The ternary ?: works as expected. empty is the one to use most: it is true for null, an empty string, an empty collection, an empty map and an empty array, and it is invalid to negate it with ! inside certain XML attribute contexts — write not empty x there instead.

Coercion, null and the famous empty string

EL coerces aggressively: a request parameter, always a String, compares equal to a number if it parses, and ${1 + ''} is 1. A missing property in the middle of a chain yields null and stops the evaluation rather than throwing, so ${order.customer.address.city} is safe even when the order has no customer — it renders an empty string. That behaviour is convenient and it hides bugs: a typo in a property name produces a blank cell, not an error. The practical defence is to render money, counts and totals through typed tags or to validate in the controller, and to treat an unexpectedly empty cell as a possible typo before assuming bad data.

4.4 EL in practice: escaping, locale and errors

EL is safe by default in exactly one respect: it does not throw. It is unsafe in the respect that matters most — it does not escape HTML, so ${x} in a text position is an injection point.

Escaping and the difference from <c:out>

${user.name} prints the string as it is. If that string contains <script>, the browser executes it. <c:out value="${user.name}"/> HTML-escapes the value by default, because its escapeXml attribute defaults to true. ${fn:escapeXml(user.name)} reaches the same result inside an attribute value where you cannot nest a tag. The rule to internalise: any EL expression that prints data which came from a user belongs inside c:out or fn:escapeXml, including inside HTML attributes and textarea content. One nuance that bites people is the difference between escaping categories — HTML escaping prevents markup injection, but a value dropped into a JavaScript string literal or a URL parameter needs a different escape; fn:escapeXml does not make a value safe inside a <script> block.

Locale, formatting and parsing

EL itself has no formatting; numbers and dates are formatted by the fmt tags, which read the request locale and the configured resource bundle. That means the same ${price} renders as $1,234.50 for a US visitor and 1 234,50 € for a French one, provided the locale was resolved — from the Accept-Language header, a fmt:setLocale call, or a session attribute. If you see raw ISO dates in a page, the format tag is missing rather than the locale being wrong.

Silent failures and how to see them

Three silent failures dominate: a misspelled property name yields an empty string; an attribute that was never set yields an empty string; and an EL expression in a context where EL is ignored yields the literal text ${...}. The first two are diagnosed by asking the controller to log the model it set and by rendering with fn:length or a debug fragment when a value is empty; the third is diagnosed by the generated servlet, which will show the expression as a string literal. A debug fragment that dumps the request attributes is one of the highest-value twenty lines in a JSP project, and it should be removed or password-protected before the application is deployed.

<%-- Unsafe: user data printed raw into HTML --%>

5.1 Installing JSTL and understanding the URIs

JSTL is not part of the container. It is a jar you ship in the WAR, which is why the most common JSTL problem is a missing file rather than a syntax error.

The jars and the versions

JSTL 3.0 is the Jakarta EE 11 release: the API jar is jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api version 3.0.0 and the implementation most containers use is org.glassfish.web:jakarta.servlet.jsp.jstl version 3.0.1 or later. Both go into WEB-INF/lib or, in Maven, in compile scope so they are packaged into the WAR. The implementation jar is what actually provides the tag classes; the API jar is what your pages compile against, and shipping only the API produces a page that translates and then fails at request time with a class-not-found for the underlying tag handler. Tomcat 11 does not bundle either, by design, because JSTL is a separate specification from the servlet and JSP specifications.

The URIs, old and new

JSTL 1.x and 2.x identified libraries with URLs under java.sun.com and xmlns.jcp.org. JSTL 3.0 moved to jakarta.tags.*, and the 3.0 implementation recognises both the new names and the legacy ones so that existing pages keep working. The five libraries and their URIs are core (jakarta.tags.core, iteration, conditionals, URL handling), XML (jakarta.tags.xml), internationalisation (jakarta.tags.fmt), SQL (jakarta.tags.sql) and functions (jakarta.tags.functions). New code should use the jakarta.tags form: the JSTL 2.0 URIs are retained for compatibility and will not be extended.

Which JSTL versions work with which container

JSTL 1.2 is the javax generation and works with Servlet 3.x and 4.0 containers — Tomcat 7, 8 and 9. JSTL 2.0 renamed the packages to jakarta while keeping the old URIs, and works with Jakarta EE 9 and 10 containers. JSTL 3.0 is the Jakarta EE 11 generation with the new URIs. The mismatch to watch for is a 2.0 jar on a Tomcat 11 deployment: it usually works, because the packages match, but the URI list it advertises may not include everything a 3.0-era page assumes. The sql and xml libraries deserve a mention of their own: putting SQL in a view was once a teaching convention and is now regarded as an anti-pattern, because it puts database access outside the controller's transaction and error handling. Use JDBC in a DAO (chapter 6) instead.

5.2 The core library: conditionals, iteration and URLs

Core is the library that replaces scriptlets. Five tags cover almost everything a view needs: out, if, choose, forEach and url.

Output, conditionals and the choose ladder

<c:out value="${x}" escapeXml="true" default="n/a"/> escapes by default and renders its default when the value is null or empty, which is how a view states its own fallback instead of leaving a blank cell. <c:if test="${...}" var="flag" scope="request"> has no else branch, by design: when you need one, use <c:choose> with any number of <c:when> tests and exactly one optional <c:otherwise>. Nesting c:if in an c:otherwise to emulate an else-if is the common workaround in older code, and it reads badly; c:choose is the honest construct.

Iteration with forEach

<c:forEach items="${list}" var="item" varStatus="st" begin="0" end="9" step="1"> is the workhorse. items accepts a collection, a map (iterating its entries), an array, an iterator, an enumeration, a comma-separated string, or a ResultSet. begin, end and step give paging and striding without a controller change; varStatus exposes index (zero-based), count (one-based), first, last and current. A very common mistake is iterating a Map and treating the loop variable as the value: with a map, var is the entry, so it is ${entry.key} and ${entry.value}. Another is forgetting that a null items renders nothing at all with no error, so an empty table is indistinguishable from an unset model attribute unless you check ${empty x} first.

URLs and the context path

<c:url value="/orders/list"> prefixes the context path and, unless context is given, adds the session id when tracking requires it — that is the tag's second job and the reason it should be used for links in an application that might be deployed under a non-root context. Nested <c:param> elements add URL-encoded query parameters, which is how you build a link containing a value with a space or an ampersand without hand-encoding it. The result can be stored with var and reused. <c:redirect> performs the redirect with the same encoding rules, and <c:import> fetches another resource — in the same application or a remote URL — into the page, with <c:param> and an optional charEncoding, which is the safe way to embed a remote fragment and the basis of a simple portal composition.

<%-- Conditionals --%>
<c:if test="${empty sessionScope.user}">
  <a href="<c:url value='/login'/>">Sign in</a>
</c:if>

<c:choose>

  </c:when>

    <span class="badge"><c:out value="${order.status}"/></span>
  </c:otherwise>
</c:choose>

<table>

  </c:forEach>
</table>

<%-- A Map iterates entries: key and value --%>
<ul>
  <c:forEach items="${countryNames}" var="e">

  </c:forEach>

5.3 Formatting, messages and string functions

The fmt library turns raw data into something a human in a particular locale expects, and fn gives EL the string operations it otherwise lacks.

Numbers, dates and currency

<fmt:formatNumber> handles three types — number, currency and percent — with pattern for anything bespoke, and its groupingUsed, minFractionDigits and maxFractionDigits attributes control the shape. <fmt:parseNumber> is the inverse, which is how a form field submitted as "1.234,50" becomes a Number in the locale's convention rather than throwing. <fmt:formatDate> takes a java.util.Date and either a type and dateStyle/timeStyle or an explicit pattern; the modern java.time types — LocalDate, Instant — are not supported by JSTL 3.0's formatDate directly, so expose a Date or format in the model layer. This is a real and frequently hit limitation, and it is the main reason projects eventually move to a template engine with java.time support.

Message bundles

<fmt:setBundle basename="messages" var="bundle"/> loads messages.properties and its locale variants from the classpath, and <fmt:message key="cart.title" bundle="${bundle}"/> renders a value. Parameters are passed with nested <fmt:param>, and the bundle value uses {0}, {1} placeholders — the full MessageFormat syntax, including choice formats for plurals. <fmt:setLocale> sets the locale for the page or a scope, and <fmt:requestEncoding value="UTF-8"/> is the tag form of request.setCharacterEncoding, which must appear before any parameter is read — on a page whose form posted UTF-8 data through a container defaulting elsewhere, that single tag is the difference between readable text and question marks.

The functions library

fn is a small, pure set of string helpers callable from EL: length, toUpperCase, toLowerCase, trim, substring, substringAfter, substringBefore, replace, split, join, indexOf, startsWith, endsWith, contains, containsIgnoreCase, escapeXml and startsWith. They are the reason a JSP rarely needs a helper bean for presentation: ${fn:toUpperCase(fn:substring(user.code, 0, 3))} is expressible. Keep them out of business logic — a view that transforms data cannot be tested by calling a method, and a controller that pre-computes a display string can.

5.4 Choosing between tags, EL and helper code

JSTL is a presentation language, not a programming language. The question is always where a given computation belongs, and there are only three defensible answers.

The three-layer rule

Data selection belongs in the controller or DAO: which rows, sorted how, filtered by what. Data shaping that a human will look at belongs in the view, expressed with fmt and fn: currency, dates, capitalisation, pluralisation. Anything with a branch or a loop over a business rule belongs in the model: whether an order is cancellable, what the next status is, whether a user may edit a row. The failure mode is a JSP that computes a discount, and the reason it is a failure is testability — you cannot unit-test a tag, and the same rule will be needed by the API endpoint that is added next quarter. A useful test: if a business analyst could describe the rule in a sentence that mentions a policy rather than a screen, it does not belong in the view.

What JSTL deliberately cannot do

There is no assignment in EL, no mutable accumulator in a forEach, and no way to call a method that has a side effect with fn. That is not an oversight: a view that accumulates is a view that cannot be rendered twice with the same result, which breaks error-page re-rendering and any kind of retry. When you find yourself needing a running total, compute it in the controller, put it on a DTO, and let the tag print it.

Custom tags before a framework

The escape hatch is a tag file or a custom tag handler (chapter 10). Reaching for one is appropriate when a pattern of markup repeats across pages — a data table with sorting, a panel with a title and actions, an input with an error slot — because extraction turns three copies into one place with one set of escaping and accessibility decisions. It is inappropriate as a way to move business logic into the view layer; that just relocates the problem and is harder to test than a plain Java class. A reasonable threshold is the same one used for extracting a function: the third copy, not the second.

6.1 The pattern, and what each part owns

MVC on the servlet API is not a framework feature; it is an arrangement of three things you already have. Getting the boundaries right is what makes a JSP application maintainable for years.

The three parts

The model is the data plus the code that knows how to fetch and change it: DTOs or records for shape, DAOs for persistence, services for rules that span more than one DAO. It knows nothing about HTTP, and nothing about HTML — that is what makes it testable with a plain JUnit test and reusable by a REST endpoint later. The view is a JSP whose only job is to turn model objects into markup; it reads request attributes, formats them, and writes HTML. The controller is a servlet that reads parameters, calls the model, decides which view to render and with what status code, and never emits HTML. A front controller is the variant where a single servlet inspects the request path and dispatches to a per-request Command object, which keeps mapping logic in one place; the per-servlet variant is simpler and is the right starting point for a small application.

Why the boundary is worth defending

The failure mode is a servlet that writes HTML with getWriter and a JSP that queries the database. Both work, and both lock you into an application where no change is local: a copy change requires a Java edit and a redeploy, a query bug cannot be reproduced without a browser, and the same SQL appears in three places with three sets of parameters. The boundary is also what protects against the two most expensive classes of bug in this stack — unescaped output (a view that fetches its own data will eventually print it unwisely) and half-committed state (a controller that renders a view mid-transaction).

A minimal, complete slice

The canonical flow is: the controller validates input, calls the model, puts the result on the request, and forwards to a JSP under WEB-INF/views. The JSP reads the attribute and renders. A failure at any point produces either a forward to a form with error messages and a 400 status, or a throw that the container maps to an error page. Nothing in the view can reach the database, and nothing in the model can reach the response.

6.2 Dispatching: forward, redirect and what each costs

A controller has two ways to hand control on. One keeps the browser where it is and the other changes it, and the difference decides whether a refresh repeats an action.

Forward keeps the request

RequestDispatcher#forward transfers the request and response objects to another resource inside the same application. Request attributes survive, the browser's URL does not change, and the response status stays whatever it was — so a forward after setStatus(400) correctly renders the form with a 400. Neither the status nor the headers can be changed by the target once the first output has been flushed, which is why a forward target must not be written to before the forward. A forward that happens after any bytes were written throws IllegalStateException from the forward call itself.

Redirect ends the request

sendRedirect writes a 302 (or a 303/307 if you set it explicitly) with a Location header and returns. The browser makes a brand-new request, so request attributes are gone, the URL bar updates, and a refresh re-issues a GET rather than the POST. That is the whole point of POST-redirect-GET: the browser's last request is a safe GET, so the back button and the refresh button cannot re-submit an order. The cost is one extra round trip and the loss of request-scoped data, which is what flash attributes in the session exist to bridge.

Choosing, and the tests that catch mistakes

Forward when the URL should stay stable and the response is the result of this request: rendering a list, re-rendering a form with errors, showing a detail page after a lookup. Redirect when the request changed state, when the next step is a different resource, or when the client should be able to bookmark the result. Two mistakes are worth a test each: a successful POST that forwards instead of redirecting, which double-orders on refresh, and a redirect that discards error state, which loses the user's input. Both are caught by an integration test that asserts the status and the Location header.

// Forward: same URL, model preserved, status preserved

6.3 The DAO layer and JDBC done correctly

Most JSP applications talk to a database. Whether that conversation is safe and leak-free is decided by three lines of code you write every time: the try-with-resources, the prepared statement, and the column mapping.

One DAO interface, one JDBC implementation

Define an interface in the model's terms — findRecent(int limit), insert(Order order) — and a JDBC implementation that knows about Connection, PreparedStatement and ResultSet. The interface is what the service and the tests use, so the JDBC implementation can be swapped for an in-memory fake in a unit test without a database. The implementation owns the SQL, which means the SQL exists in exactly one place, is reviewable in isolation, and can be tuned with an index without touching a servlet.

Always a PreparedStatement

A PreparedStatement is not merely faster because some drivers cache the plan; it is the only way to pass a value that cannot change the meaning of the SQL. String concatenation of a parameter produces SQL injection (chapter 9) and a class of bug that is worse than an exploit because it is invisible: an apostrophe in a surname breaks a query that worked in every test. Bind every value with setInt, setString, setTimestamp, including the values in a WHERE clause, in an ORDER BY direction only through a whitelist, and in a LIMIT. Use PreparedStatement's generated-key support when you need the new id back, rather than a second query.

Resources, nulls and result mapping

A ResultSet is a cursor into a live connection: reading a column after the connection closed throws, and leaving a result set unclosed can exhaust the server's cursors. Try-with-resources on the statement closes the result set with it, and on the connection returns the connection to the pool. Read the value, convert it, and store it in a DTO inside the loop so nothing outside the block holds a cursor. Watch two JDBC traps in particular: getInt returns 0 for SQL NULL and its own value is indistinguishable, so use getObject(col, Integer.class) when null matters; and setTimestamp with a java.time value requires the java.sql bridge until a driver supports the JSR-310 types directly, which most now do for setObject.

// dao/OrderDao.java — no JDBC types in the interface
public interface OrderDao {
    List<Order> findRecent(int limit) throws SQLException;
    Optional<Order> findById(long id) throws SQLException;
    long insert(Order order) throws SQLException;
}
// dao/JdbcOrderDao.java — every resource in a try-with-resources
public class JdbcOrderDao implements OrderDao {

    private static final String SQL_RECENT = """
        SELECT id, sku, qty, placed_at, customer_id
          FROM orders
         ORDER BY placed_at DESC
         LIMIT ?
        """;

    private final DataSource ds;
    public JdbcOrderDao(DataSource ds) { this.ds = ds; }

    @Override
    public List<Order> findRecent(int limit) throws SQLException {
        List<Order> out = new ArrayList<>();
        try (Connection c = ds.getConnection();
             PreparedStatement ps = c.prepareStatement(SQL_RECENT)) {
            ps.setInt(1, limit);                       // never concatenated
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    out.add(map(rs));                  // copy out before the cursor closes
                }
            }
        }
        return out;
    }

    @Override
    public long insert(Order o) throws SQLException {
        String sql = "INSERT INTO orders (sku, qty, customer_id) VALUES (?, ?, ?)";
        try (Connection c = ds.getConnection();
             PreparedStatement ps =
                 c.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, o.sku());
            ps.setInt(2, o.qty());
            ps.setLong(3, o.customerId());
            ps.executeUpdate();
            try (ResultSet keys = ps.getGeneratedKeys()) {
                keys.next();
                return keys.getLong(1);
            }
        }
    }

    private Order map(ResultSet rs) throws SQLException {
        // getObject(col, Type.class) preserves SQL NULL; getInt would give 0.
        Integer qty = rs.getObject("qty", Integer.class);
        return new Order(
            rs.getLong("id"),
            rs.getString("sku"),
            qty == null ? 0 : qty,
            rs.getTimestamp("placed_at").toInstant(),
            rs.getLong("customer_id"));
    }
}

public class AppContext implements ServletContextListener {

6.4 Transactions, lazy data and the N+1 trap

JDBC gives you transactions per connection and nothing more. Where a unit of work spans several statements, the boundary has to be drawn deliberately, and the most common performance bug in this stack comes from drawing it in the wrong place.

Transactional boundaries

A single connection with setAutoCommit(false), a sequence of statements, and a commit or rollback in a finally block is the whole mechanism. The boundary belongs in the service layer, not in the DAO: a service that transfers stock between two orders needs one transaction covering both statements, and no DAO method can provide that on its own. Set the isolation level deliberately if a default is not enough — READ_COMMITTED is the usual choice and is what most databases default to, while REPEATABLE_READ prevents a read from seeing a value that changed mid-transaction at the cost of more locking. Set a statement timeout so a lock wait cannot pin a container thread indefinitely: a request that waits forever holds a pooled connection, and enough of those take the application down without any code being wrong.

Never let rows escape into the view

The temptation is a DAO that returns a ResultSet or a lazily-loaded JPA entity so the view can read columns on demand. Both fail: the result set needs a live connection, and the container has already returned the thread to the pool; a lazy entity throws a lazy-initialisation exception once its session closes. The correct shape is a DTO holding plain values, fully populated inside the DAO, safe to put on the request and safe to serialise. That is also what makes a view cacheable and a response testable.

The N+1 query problem

The classic performance bug: a DAO returns twenty orders, and the view (or a lazy mapping) triggers one query per order to fetch the customer name — twenty-one queries where one would do. The symptom is a page that is fast with three rows and takes seconds with three hundred. The fix is always the same shape: fetch what the view needs in one query with a join, and map it into a flat DTO. If the view needs a list per parent, load the children in a single WHERE parent_id IN (...) and group them in Java. Detecting it needs a log line per query rather than a profiler, so enable statement logging in development and count.

// A service-level transaction covering two tables
public void moveStock(long fromOrder, long toOrder, int qty) throws SQLException {
    try (Connection c = ds.getConnection()) {
        boolean previous = c.getAutoCommit();
        c.setAutoCommit(false);                       // transaction starts here
        try (PreparedStatement dec = c.prepareStatement(
                 "UPDATE orders SET qty = qty - ? WHERE id = ? AND qty >= ?");
             PreparedStatement inc = c.prepareStatement(
                 "UPDATE orders SET qty = qty + ? WHERE id = ?")) {

            dec.setInt(1, qty); dec.setLong(2, fromOrder); dec.setInt(3, qty);
            if (dec.executeUpdate() != 1) {
                c.rollback();                         // insufficient stock: no partial move
                throw new IllegalStateException("insufficient stock on " + fromOrder);
            }
            inc.setInt(1, qty); inc.setLong(2, toOrder);
            inc.executeUpdate();
            c.commit();
        } catch (SQLException | RuntimeException e) {
            c.rollback();
            throw e;
        } finally {
            c.setAutoCommit(previous);                // restore before the pool sees it
        }
    }
}

7.1 Binding request parameters to model objects

There is no binding framework here, and that is mostly an advantage: the marshalling is explicit, visible, and testable. It is also where most of the tedium lives, so it is worth doing once in a reusable way.

Reading parameters safely

getParameter returns null for a name that was not submitted and "" for a field submitted empty. A checkbox that is not ticked is simply absent, so getParameter("agree") != null is the test for it. Repeated names — multiple checkboxes, a multi-select — need getParameterValues, which returns an array or null. Values are always strings, so every number, date, boolean and enum needs conversion, and the conversion is where the validation actually happens: a parse failure is the first error to record. Since Servlet 6.x the container's default request encoding is UTF-8, but setCharacterEncoding("UTF-8") before the first read is still correct and still necessary on any container or connector configured otherwise.

A form object, and a single place that builds it

Write one method per form that turns a request into either a validated object or a map of errors. Keeping it in one place means the create and edit paths behave identically, the tests target one function, and the JSP can re-populate its fields from the same object. This is the manual equivalent of what Spring MVC does with @ModelAttribute, and doing it by hand once shows you exactly what the framework is buying.

Sticky forms and the type problem

When validation fails the form must come back with what the user typed, which means the values have to survive the forward. Put the submitted values on the request as strings and read them back in the view with ${fn:escapeXml(param.field)} or a model object; do not read ${param} in the re-rendered view alone, because a subsequent GET has different parameters. For types, keep the raw strings alongside the parsed values so a field that failed to parse can still be re-displayed exactly as typed — otherwise "1,5" becomes an empty box and the user loses their input. Finally, mark every field the server owns as read-only or ignore it on input: a hidden price field is a client-supplied price, and an id field the browser sends is an object reference the client just chose.

7.2 Server-side validation and the error contract

Client-side validation is a courtesy to the user. Server-side validation is the boundary of trust. They are not alternatives, and only one of them is enforced against an attacker.

Validate on the server, always

HTML attributes such as required, pattern and maxlength improve a form's feel and cost nothing, and they are trivially bypassed — a curl command, a modified DOM, or a browser that ignores them. The server-side check is the one that matters, and it must exist for every field, including the ones the UI makes impossible to get wrong. The list to check on every submission: presence, type, length, range, format, allowed values for enumerations, cross-field consistency, and authorisation for the referenced entity. That last one is regularly forgotten: validating that a customerId is a number says nothing about whether the caller may write to that customer's orders.

An error contract the view can render

Return errors as a map from field name to message, plus a form-level list for errors that belong to no single field, and a stable code per error when the message is translated. A map keyed by field is what lets the view place each message beside its input, and a form-level list is where "an order with that SKU already exists" belongs. Do not build messages by concatenating user input — a message that echoes the submitted value is an injection point and a translation problem both. And keep the status code honest: a validation failure on a POST is a 400 with the form re-rendered, while a failure that the user can fix by signing in is a 401 or a redirect to login.

Two-layer rules, and where uniqueness lives

Some rules can be checked in the model and some only in the database. Uniqueness is the canonical example: checking SELECT count(*) and then inserting has a race, so the authoritative check is a unique constraint and the DAO translates the constraint violation into a field error. A validation library such as Jakarta Bean Validation — Hibernate Validator is the reference implementation — gives you @NotNull, @Size, @Pattern, @Email and custom constraints on the form object, and validator.validate(form) returns the violations you then map to field names. It is worth the dependency as soon as the second form appears, because it makes the rules declarative and visible on the object rather than scattered through a binder.

// Jakarta Bean Validation on the form object (Hibernate Validator 9.x)

7.3 Multipart uploads

File upload in the servlet API is one annotation and a handful of methods, plus a set of limits you must configure explicitly or leave your server open to a trivial disk-filling attack.

@MultipartConfig and the API

Annotate the servlet with @MultipartConfig and the container parses multipart/form-data bodies for it; without the annotation, parameters are empty and getPart throws. The same settings exist as elements of the <multipart-config> element for a servlet declared in web.xml. The annotation's attributes are the whole security story: fileSizeThreshold is the size above which a part is written to disk rather than kept in memory, maxFileSize caps a single part, maxRequestSize caps the entire request, and location names the directory used for temporary files. Request parameters can still be read with getParameter when the body is multipart, and text fields arrive as parts, so getParameter("note") keeps working alongside getPart("file").

Storing a file safely

A part's getSubmittedFileName is client-supplied and must never be used as a path. The file should be written under a generated name — a UUID plus an extension validated against an allow-list — inside a directory fixed by the application, and the display name stored in the database as text. Validate the content type from the parsed bytes rather than the Content-Type header, and decide what to do with HTML or SVG uploads because both execute when served from the same origin. Either store uploads outside the web root and stream them through a servlet that sets Content-Disposition: attachment, or serve them from a separate domain; an uploaded .html served from your origin is a persistent XSS. Size limits must exist at three levels — the container's, a reverse proxy's, and an application check — because the proxy is the one that protects against a request large enough to exhaust the container before your code sees it.

Progress, resumability and when not to use this

The servlet multipart API gives no progress events and no resumption: you receive a completed request or an error. For large files that is the wrong tool, and the answer is a direct-to-storage upload — the browser receives a pre-signed URL and uploads straight to object storage, then tells your servlet that the upload finished. That removes the file from the application's memory and disk entirely. Use @MultipartConfig for the case it fits: a modest attachment, a CSV import, an avatar image.

@WebServlet("/upload")
@MultipartConfig(
    fileSizeThreshold = 1024 * 1024,        // 1 MB in memory, then disk
    maxFileSize       = 10L * 1024 * 1024,  // 10 MB per file
    maxRequestSize    = 12L * 1024 * 1024,  // 12 MB for the whole request

    }

public final class FileStore {
    public static String save(InputStream in, String submitted, Set<String> allowed)
            throws IOException {
        byte[] head = in.readNBytes(12);
        String type = sniff(head);                       // magic bytes, not the header
        if (!allowed.contains(type)) {
            throw new IOException("unsupported content type: " + type);
        }
        String ext = switch (type) {
            case "image/png"  -> ".png";
            case "image/jpeg" -> ".jpg";
            case "application/pdf" -> ".pdf";
            default -> throw new IOException("no extension for " + type);
        };
        Path dir = Path.of(System.getProperty("app.storage"), "uploads");
        Files.createDirectories(dir);
        Path target = dir.resolve(UUID.randomUUID() + ext).normalize();
        if (!target.startsWith(dir)) throw new IOException("path escape");   // belt and braces
        try (OutputStream out = Files.newOutputStream(target)) {
            out.write(head);
            in.transferTo(out);
        }
        return target.getFileName().toString();
    }

    private static String sniff(byte[] b) {
        if (b.length >= 8 && (b[0] & 0xFF) == 0x89 && b[1] == 'P') return "image/png";
        if (b.length >= 3 && (b[0] & 0xFF) == 0xFF && (b[1] & 0xFF) == 0xD8) return "image/jpeg";
        if (b.length >= 4 && b[0] == '%' && b[1] == 'P' && b[2] == 'D') return "application/pdf";
        return "application/octet-stream";
    }
}

7.4 Duplicate submits, idempotency and the flow contract

A form is a state machine with a browser on the other end, and the browser will resend, re-post and go back. The submit-once guarantees have to be built, because nothing in HTTP supplies them.

Why duplicates happen

A user double-clicks Submit, the browser's refresh re-posts, a back button restores a cached form, a proxy retries a request that timed out on the wire. Each produces a second POST with an identical body. POST-redirect-GET removes the refresh and back-button cases, because the last request is a GET. It does nothing for the double-click or the retry, which arrive at the server as two separate POSTs before the first response has been seen.

Idempotency tokens

The general fix is a token that identifies the submission rather than the user. The form embeds a hidden field with a random value; the session (or a table) remembers it; the first POST that presents it is processed and the token is consumed; a second POST with the same token is either ignored or answered with the original result. A natural-key alternative applies when the data itself has an identity: a unique constraint on (customer_id, sku, day) makes the second insert fail, and the DAO can then treat the failure as success because the desired state has been reached. Both approaches are legitimate; the token is right when the operation has no natural key, and the constraint is right when it does, because it also protects against a bug in your own token handling.

Making the flow explicit

Write down the transitions: form (GET) to submit (POST) to success (GET). Every mutation is a POST, every POST ends in a redirect, and validations that need to be re-displayed forward with a 400 so the input survives. Then decide what a repeat means for each endpoint and encode it: an order creation token, an UPDATE ... WHERE version = ? optimistic lock for edits, and a client-generated idempotency key for anything that talks to a payment provider. That is the whole contract, and it is worth documenting in the same place as the URL map, because it is the part of a JSP application that is easiest to get subtly wrong.

// A one-shot submit token, checked in the controller
@WebServlet("/orders")

8.1 The filter chain and what belongs in it

A filter wraps the request before a servlet sees it and the response after the servlet has written it. That position — on both sides of every request — is why filters are the right home for policy and the wrong home for business logic.

How the chain works

A filter implements jakarta.servlet.Filter with init, doFilter and destroy. The container builds a chain ordered by the urlPatterns and, when more than one filter matches, by whatever ordering the application declares — for annotations, the order is unspecified, which is the single most important thing to know about @WebFilter. doFilter receives a request, a response and a FilterChain; calling chain.doFilter(req, resp) passes control inward, and the code after the call runs on the way back out, with the response already written. Not calling it is how a filter blocks a request — an authentication check that redirects to login and returns. Anything that must happen after the servlet has produced output, such as a compression or a signing step, belongs after the chain call.

Ordering and the two ways to declare a filter

Because annotation order is undefined, any application where order matters should declare its filters in web.xml with explicit <filter-mapping> blocks, since those are applied in document order per URL pattern. The ordering that matters in practice is: character encoding first, then security headers, then authentication, then authorisation, then CSRF, then logging, then compression. Encoding has to be first because it must be set before anything reads a parameter; compression and logging belong late because they wrap the finished response. Mixing annotation and descriptor declarations for the same filter is an error, so pick one.

Dispatcher types

A filter mapping has a dispatcher list: REQUEST for an ordinary client request, FORWARD for a servlet dispatching to a JSP, INCLUDE for an include, ERROR for a dispatch to an error page, and ASYNC for a re-dispatch after an async operation, which only applies to filters declared with async-supported. The default is REQUEST only, and that default explains a common surprise: a filter that sets an attribute will not have run for the JSP target of a forward unless FORWARD was added, so a view sees nothing. Conversely, adding FORWARD to a filter that increments a counter makes it count once per forward, not once per request.

// An encoding filter has to be the first link in the chain
public class EncodingFilter implements Filter {
    @Override

            resp.setHeader("Location",
                req.getContextPath() + "/login?next=" +
                URLEncoder.encode(req.getRequestURI(), UTF_8));
            return;                                    // chain not called: request ends here
        }
        chain.doFilter(rq, rs);                        // passes inward
        // code here runs on the way back out, after the servlet has written
    }
}
A filter that forgets to call chain.doFilter on the success path produces a blank 200 response with no error — the worst kind of bug to diagnose. Make the single call visible at the end of the method where possible.

8.2 Wrapping requests and responses

The wrapper classes let a filter change what the next link sees or capture what it produced. They are the mechanism behind compression, caching, sanitising and audit logging, and they require care because a wrapper is only as correct as the methods it overrides.

The two wrapper classes

HttpServletRequestWrapper and HttpServletResponseWrapper implement the interfaces by delegating every call to the wrapped object, so a subclass overrides only what it needs. A request wrapper can add a header that is not there, restrict parameters, or substitute a sanitised value for one field. A response wrapper can intercept getWriter and hand out a writer over a buffer, so the filter can inspect or rewrite the whole body at the end of the chain. The classic uses: a response wrapper that captures the HTML so a filter can inject a nonce into every <script>, a request wrapper that overrides getParameter to run an HTML sanitiser over input, and a wrapper that gives a request a different URI so a front controller can dispatch internally.

What to override, and what to leave alone

Override the narrowest set of methods that does the job, and delegate everything else. A request wrapper that overrides getParameter must override getParameterValues and getParameterMap consistently, or the servlet and a JSTL loop will disagree about what was submitted. A response wrapper that substitutes its own writer must also handle getOutputStream, because a servlet that writes bytes will get the wrapped stream, not the wrapped writer. And a wrapper must respect the fact that a response can be committed: buffering the entire body means the response is committed only at the end, which changes the container's behaviour for large responses and can defeat streaming.

Gzip, and why the container may already do it

Compression is the canonical wrapping example and also the case where handwriting is usually a mistake: Tomcat's connector supports compression="on" with a compressibleMimeType list, and a proxy such as nginx or a CDN does it better and earlier. Implement your own only when you need a specific list of content types or a minimum size the container cannot express. If you do, respect Accept-Encoding, skip already-encoded responses, do not compress images or archives, and remember Content-Length must be removed or corrected — a compressed body with the uncompressed length is worse than no compression at all.

// A request wrapper that trims and filters parameters
public class SanitisingRequest extends HttpServletRequestWrapper {

    public SanitisingRequest(HttpServletRequest req) { super(req); }

    @Override
    public String getParameter(String name) {
        return clean(super.getParameter(name));
    }

    @Override
    public String[] getParameterValues(String name) {
        String[] raw = super.getParameterValues(name);
        if (raw == null) return null;
        String[] out = new String[raw.length];
        for (int i = 0; i < raw.length; i++) out[i] = clean(raw[i]);
        return out;
    }

    @Override
    public Map<String, String[]> getParameterMap() {
        Map<String, String[]> out = new LinkedHashMap<>();
        super.getParameterMap().forEach((k, v) -> out.put(k, getParameterValues(k)));
        return Collections.unmodifiableMap(out);       // must agree with the two above
    }

    private static String clean(String v) {
        return v == null ? null : v.strip().replace("\u0000", "");
    }
}

8.3 Listeners: startup, sessions and requests

A listener is a callback the container invokes at a lifecycle event. They are the correct place for wiring a pool, loading configuration, and counting sessions, and they run with no request in sight.

The listener interfaces

ServletContextListener fires contextInitialized when the application starts and contextDestroyed when it stops — the only reliable place to create a thread pool, open a database pool, load a configuration file, or register a scheduled job, and the only reliable place to shut them down. HttpSessionListener fires on session creation and destruction, which is how a "users online" count is maintained; note that destruction is not guaranteed on an abrupt shutdown, so the count is an estimate. ServletContextAttributeListener and the session and request attribute listeners observe attribute changes, which is useful for auditing and for enforcing a maximum size on the session. ServletRequestListener fires at the start and end of every request and is a cheap place for a correlation id or a per-request timer.

Ordering and failure

Listeners are invoked in the order declared for contextInitialized, and in reverse for contextDestroyed, which mirrors the way a resource should be opened before its dependants and closed after them. A ServletContextListener that throws from contextInitialized aborts the deployment, which is exactly the behaviour you want for a missing configuration value: fail at startup, loudly. Keep the work in contextInitialized short — it happens on the deployment thread, and a long operation delays the start of the application.

Sessions, threads and shutdown

Anything a listener starts must be stopped by the same listener, in the matching callback. A ScheduledExecutorService created in contextInitialized and never shut down keeps the JVM alive after undeploy and leaks a thread on every redeploy — after a day of development your server has a hundred of them. A background thread has no request scope, no security context and no session, so it must look up everything it needs from the ServletContext and handle its own errors; a failure there is silent, so log it. And a thread that touches a request or a session must not exist at all, because both are only valid during a request.

// One listener that wires everything, and unwires it in reverse
@WebListener
public class AppLifecycle implements ServletContextListener, HttpSessionListener {

    private HikariDataSource pool;
    private ScheduledExecutorService scheduler;
    private final AtomicInteger online = new AtomicInteger();

    @Override
    public void contextInitialized(ServletContextEvent e) {
        ServletContext ctx = e.getServletContext();
        try {
            pool = Pools.create(ctx.getInitParameter("jdbcUrl"));
            ctx.setAttribute("dataSource", pool);          // visible to DAOs via the context

            scheduler = Executors.newSingleThreadScheduledExecutor(
                r -> { Thread t = new Thread(r, "app-jobs"); t.setDaemon(true); return t; });
            scheduler.scheduleAtFixedRate(
                () -> { try { new CleanupJob(pool).run(); }
                        catch (Exception ex) { ctx.log("cleanup failed", ex); } },
                5, 5, TimeUnit.MINUTES);
        } catch (Exception fatal) {
            throw new IllegalStateException("application failed to start", fatal);
        }
    }

    @Override

        if (scheduler != null) scheduler.shutdownNow();    // or the JVM leaks a thread
        if (pool != null) pool.close();
    }

    @Override public void sessionCreated(HttpSessionEvent e) { online.incrementAndGet(); }
    @Override public void sessionDestroyed(HttpSessionEvent e) { online.decrementAndGet(); }

    public int online() { return online.get(); }
}

8.4 Asynchronous servlets and non-blocking I/O

Async support exists to release the container thread while an operation completes, not to make code faster. Used well it turns a thread-starved application into a concurrent one; used badly it is harder to debug than a thread pool.

startAsync and the AsyncContext

An async-capable servlet calls req.startAsync(), which returns an AsyncContext, returns from doGet, and completes the response later from another thread. The container does not commit or recycle the request and response while the context is open, and its thread goes back to the pool. To be async-capable the servlet must declare asyncSupported = true — either on @WebServlet or in the descriptor — and every filter in the chain must be async-supported too, or startAsync throws an IllegalStateException explaining that the request does not support it. That single sentence is the usual cause of "async does not work in my application": one filter without async-supported silently disables the whole path.

Timeouts, listeners and completion

An AsyncContext has a timeout, defaulting to the container's asyncTimeout, after which the container dispatches to an error page or completes the response. Set it explicitly with setTimeout, and add an AsyncListener to handle onTimeout, onError and onComplete — without the timeout handler a stalled backend leaves the client hanging until the container's default. Completion is asyncContext.complete(), or a dispatch back to a resource that writes the response and completes implicitly. Every path must complete exactly once: completing twice throws, and never completing holds the connection until the timeout.

When async is worth it

Async pays when requests wait on something external and the wait is long enough to exhaust the thread pool: a slow upstream API, a fan-out to several services, a long poll for a notification, an SSE stream. It does not pay when the work is CPU-bound, because there is no thread to release and the executor is just a second pool to tune. A common pattern is a modest pool of async requests with a larger executor, so a hundred concurrent slow requests need a handful of container threads. Non-blocking I/O via ServletInputStream#setReadListener and ServletOutputStream#setWriteListener goes a step further and removes the blocking read too, at the cost of a much more intricate callback structure — use it for high-throughput streaming, not for ordinary endpoints.

@WebServlet(urlPatterns = "/report", asyncSupported = true)
public class ReportServlet extends HttpServlet {

    private ExecutorService workers;

    @Override
    public void init() {
        workers = Executors.newFixedThreadPool(8);
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        AsyncContext ctx = req.startAsync(req, resp);      // release the container thread
        ctx.setTimeout(30_000);                            // 30 seconds, then onTimeout

        ctx.addListener(new AsyncListener() {
            @Override public void onTimeout(AsyncEvent e) throws IOException {
                send(ctx, 504, "report timed out");
            }
            @Override public void onError(AsyncEvent e) throws IOException {
                send(ctx, 500, "report failed");
            }
            @Override public void onComplete(AsyncEvent e) { /* nothing */ }
            @Override public void onStartAsync(AsyncEvent e) { /* re-dispatch */ }
        });

        String account = req.getParameter("account");
        workers.submit(() -> {
            try {
                Report r = reports.build(account);          // slow, off the container thread
                send(ctx, 200, r.toJson());
            } catch (Exception ex) {
                send(ctx, 500, "report failed");
            }
        });
        // doGet returns immediately; the container thread is free
    }

    private static void send(AsyncContext ctx, int status, String body) throws IOException {
        HttpServletResponse r = (HttpServletResponse) ctx.getResponse();
        r.setStatus(status);
        r.setContentType("application/json;charset=UTF-8");
        r.getWriter().write(body);
        ctx.complete();                                    // exactly once, on every path
    }

    @Override
    public void destroy() { workers.shutdownNow(); }
}

Async releases the container thread; it does not create concurrency. If your executor has eight threads and you submit a thousand slow tasks, requests queue exactly as they would have in a thread pool — with the added difficulty that a timeout now fails the response instead of the thread.

9.1 Authentication and authorisation in the container

The servlet specification includes a declarative security model: you say which URL patterns require which roles, and the container enforces it before your code runs. It is worth knowing exactly how far it goes.

Declarative constraints

A <security-constraint> names one or more URL patterns, a set of HTTP methods to protect, and the roles allowed; a <login-config> names the mechanism; and a <security-role> declares the role names the application expects. With that in place the container intercepts a request to a protected path, challenges an unauthenticated user with the configured mechanism, and — crucially — denies access to a role that is not allowed before the servlet is ever invoked. Failing closed is the property that makes declarative security valuable: a missing check in your own code cannot open a URL that has a constraint. The annotation form, @ServletSecurity(@HttpConstraint(rolesAllowed = "admin")), expresses the same thing next to the servlet, and @HttpMethodConstraint lets you protect a single method such as POST while leaving GET public.

The mechanisms, and which ones are worth using

BASIC sends the credentials in a base64 header on every request; it is fine over HTTPS for a CLI or an internal tool and wrong for a browser application. DIGEST avoids sending the password but is obsolete and not recommended for new systems. CLIENT-CERT uses mutual TLS and is the strongest, but the operational cost of issuing and rotating certificates to users is high. FORM is the browser-friendly mechanism: the container serves a login page you supply, the browser posts to the reserved j_security_check action with the reserved j_username and j_password fields, and on success the container redirects to the originally requested resource. The form mechanism is the right default for a JSP application, with one caveat: the reserved field names and check path are fixed, and the login page URL must be reachable without authentication or the container redirects to itself forever. Tomcat also supports SPNEGO and JASPIC; Jakarta Security's annotation-based mechanisms are part of the full platform and are not implemented by Tomcat on its own.

Where the users come from

Authentication needs a realm: a MemoryRealm reading a file, a JDBCRealm or DataSourceRealm reading tables, or JNDIRealm against a directory. Whichever you choose, the passwords must be stored with a strong, salted hash — the container supports digest="SHA-256" with a salt column, and modern deployments often store an Argon2 or bcrypt hash produced by the application and verify it in a custom realm or a login servlet. Roles then come from the same source, and application code asks req.isUserInRole("admin"), req.getRemoteUser() and req.getUserPrincipal() rather than reading a session attribute. Finally, remember the part the container cannot do: role-based access at the row level. "Only a manager may approve an expense" is enforced by the container; "only this manager may approve that expense" is authorisation your service layer must check, and forgetting it is the classic broken-access-control bug.

9.2 Session integrity and cross-site request forgery

Chapter 2 covered what a session is. This section is about the attacks that target it, and the two that reach production most often are a session that survives login unchanged and a state-changing GET.

CSRF: the mechanics that decide the defence

A forged request works because the browser attaches the session cookie automatically to a request it did not initiate — an <img> tag, an auto-submitting form, a fetch. The attacker cannot read the response (the same-origin policy stops that), but for a state-changing request reading is unnecessary. Three controls combine: SameSite=Lax on the session cookie stops the cookie being sent on a cross-site form post in a modern browser; a per-session token in a hidden field and checked server-side stops the request even when the cookie arrives; and Origin or Referer validation catches cases where one mechanism was misconfigured. Use at least two. The token must be compared in constant time only if it is a secret, and it must be per-session rather than per-request on a page with multiple forms — a per-request token breaks a page that submits two forms from two tabs.

Session fixation, replay and the cookie flags

Rotate the session id at every privilege change: req.changeSessionId() on login and on elevation. Set HttpOnly so a cross-site scripting bug cannot read the cookie, Secure so it never travels in plaintext, and a Path that is as narrow as the application allows. Then consider what a stolen id is worth: a session timeout turns a stolen id into a temporary problem rather than a permanent one, and binding a session to a rough client fingerprint — not the IP, which changes on mobile networks, but the User-Agent — makes a stolen cookie harder to use from a different client, at the cost of false logouts when a browser updates.

State-changing requests must not be GETs

The oldest CSRF vector is a link that changes state, because a GET carries the cookie and can be triggered from an image tag. Make every mutation a POST, make the endpoints reject GET with a 405 rather than silently doing nothing, and never accept an action verb as a parameter on a GET — /orders?action=delete&id=42 is an invitation. That also aligns with caching and with the retry behaviour of proxies, which will happily re-issue a GET that changes state.

// A CSRF filter: token in a header or a form field, checked on every mutation
@WebFilter(urlPatterns = "/*")
public class CsrfFilter implements Filter {

    @Override
    public void doFilter(ServletRequest rq, ServletResponse rs, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) rq;
        HttpServletResponse resp = (HttpServletResponse) rs;

        HttpSession session = req.getSession(false);
        if (session != null && !isSafe(req.getMethod())) {
            String expected = (String) session.getAttribute("csrf");
            String given = req.getHeader("X-CSRF-Token");
            if (given == null) given = req.getParameter("_csrf");

            if (expected == null || given == null ||
                !MessageDigest.isEqual(expected.getBytes(UTF_8), given.getBytes(UTF_8))) {
                resp.sendError(HttpServletResponse.SC_FORBIDDEN, "CSRF token mismatch");
                return;
            }
        }
        chain.doFilter(rq, rs);
    }

    private static boolean isSafe(String method) {
        return "GET".equals(method) || "HEAD".equals(method) || "OPTIONS".equals(method);
    }
}

9.3 Output encoding and injection

Two injections account for the majority of application compromises: SQL built by concatenation, and HTML built by pasting user data. Both are prevented in the same place — where the value meets its context.

SQL injection needs no cleverness

Concatenating a parameter into a query means the user supplies SQL. There is no sanitising pass that makes this safe, because the parser decides what is a value and what is syntax only after concatenation — the value has already become part of the program. PreparedStatement is the fix, and it works because the query text is parsed before any value is bound, so a value can never be interpreted as syntax no matter what it contains. Watch the two places a prepared statement does not help: identifiers (a table or column name chosen by the user, and an ORDER BY direction) must be matched against a whitelist and interpolated as a known-safe literal, and stored procedures called with dynamic SQL inside them have exactly the same problem one layer down.

XSS needs the right encoder for the context

The mistake is to think of escaping as one operation. Text placed between tags needs HTML entity encoding; a value inside an HTML attribute also needs entity encoding, but the attribute must be quoted; a value inside a <script> block needs JavaScript string escaping and is best avoided entirely; a value in a URL needs percent encoding; a value in a CSS context needs a different treatment again. HTML entity encoding — what <c:out> and fn:escapeXml do — is correct only for the first two, which is why a value rendered into an inline script is still a vulnerability after escaping. The three robust answers are: never put user data in a script block (pass it through a JSON endpoint or a data-* attribute read by code), enable a Content-Security-Policy with a nonce so injected inline script will not execute, and have a sanitiser such as the OWASP Java HTML Sanitizer clean rich text where the user is allowed to submit markup.

Other injections in the same family

LDAP filters, OS command lines, XML parsers, and template engines all have their own grammars and their own escaping. Log injection is real too: a newline in a user-controlled value forges log entries and can break a log processor, so strip control characters before logging. 9.4 Response headers, transport and the limits of configuration

A handful of headers closes whole classes of browser-side attack, and a filter is the right place to set them, because that is the only place that sees every response including error pages.

The headers worth setting

Content-Security-Policy is the most valuable and the most disruptive: default-src 'self' plus a script-src that uses a per-response nonce is the pattern that makes a stray injected script fail to execute rather than run, and legacy inline handlers and eval must be removed from the code base for it to be enforced without a report-only phase. Strict-Transport-Security with a long max-age and includeSubDomains tells the browser never to attempt plaintext again, and is the reason a single HTTP link stops looking like a logout. X-Content-Type-Options: nosniff stops the browser second-guessing a declared content type — important for anything user-uploaded. Referrer-Policy: strict-origin-when-cross-origin limits what a click on an outbound link discloses. X-Frame-Options: DENY or the CSP frame-ancestors 'none' prevents clickjacking. Tomcat ships a filter that sets several of these, HttpHeaderSecurityFilter, and it is worth using for the ones it covers and adding a filter of your own for the CSP nonce, which has to be generated per response and threaded into the view.

Cookies, transport and TLS

TLS is the precondition for everything above: Secure flags, HSTS and a nonce that an attacker cannot read all assume the connection is confidential. Terminate TLS at the container or at a proxy, redirect all plaintext to HTTPS with a permanent redirect, and make sure the application sees the correct scheme — a proxy that forwards plain HTTP to Tomcat needs RemoteIpValve configured with the trusted proxy list, or req.getScheme(), isSecure() and every generated absolute URL will be wrong, and a redirect loop becomes possible. Also decide which headers your proxy adds and which the application adds, so that neither is duplicated and neither is missing from error responses produced by the proxy itself.

What code must still do

Headers and constraints do not implement authorisation at the object level, do not stop an insecure deserialisation, do not validate a file upload's real type, and do not know that a parameter represents a user id that a different user should not be able to reach. The container is a perimeter; the application is the interior. Assume the perimeter will be perfectly configured and still check, server-side, that the logged-in user owns the row they asked for — that single check, applied consistently, prevents more real breaches than any header. And log the security events that matter: a failed login, a token mismatch, a forbidden access, a validation error that looks like probing. The log is how an incident becomes a diagnosis rather than a mystery.

// A headers filter that also mints a per-response CSP nonce
@WebFilter(urlPatterns = "/*")
public class HeadersFilter implements Filter {

    @Override
    public void doFilter(ServletRequest rq, ServletResponse rs, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) rq;
        HttpServletResponse resp = (HttpServletResponse) rs;

        String nonce = Tokens.newCsrfToken();          // 256 bits, base64url
        req.setAttribute("cspNonce", nonce);           // the view uses it on every script

        resp.setHeader("Content-Security-Policy",
            "default-src 'self'; " +
            "script-src 'self' 'nonce-" + nonce + "'; " +
            "style-src 'self' 'nonce-" + nonce + "'; " +
            "img-src 'self' data:; " +
            "object-src 'none'; base-uri 'none'; frame-ancestors 'none'");
        resp.setHeader("X-Content-Type-Options", "nosniff");
        resp.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
        resp.setHeader("Cross-Origin-Opener-Policy", "same-origin");
        resp.setHeader("Permissions-Policy", "geolocation=(), camera=(), microphone=()");

        if (req.isSecure()) {
            resp.setHeader("Strict-Transport-Security",
                "max-age=31536000; includeSubDomains");
        }
        chain.doFilter(rq, rs);
    }
}

10.1 Tag files: custom tags without Java

A tag file is a JSP fragment with declared attributes that any page can invoke as a tag. It is the cheapest reusable component in this stack: no Java, no compilation step of its own, and no TLD unless you want one.

What a tag file is

A file with the extension .tag under WEB-INF/tags becomes a tag. The directory path after WEB-INF/tags forms the tag's name with colons: WEB-INF/tags/ui/panel.tag is invoked as <ui:panel>. A page makes it available with a taglib directive whose tagdir is the directory, or with a uri pointing at a packaged jar that contains a TLD. Directives inside the tag file are the declaration syntax: <%@ tag body-content="empty" %> declares what the body may contain, and <%@ attribute name="title" required="true" %> declares an attribute. The distinction from a static include is that a tag file has its own declaration boundary: it cannot see the caller's page variables, only what is passed in, which is what stops a fragment from becoming an accidental global.

body-content and the four values

empty means the tag may not have a body; scriptless means the body may contain template text, EL and JSTL, but not scriptlets, and it is the value to use for almost everything; tagdependent means the body is passed through untouched for the tag to interpret itself; and JSP allows scriptlets, which exists for compatibility and should be avoided. Declaring scriptless is a feature, not a restriction: it guarantees that the component cannot smuggle in Java, so a review of the tag file is a complete review of its behaviour.

Passing data in and rendering it out

Declared attributes may be required or optional, may have a default, and their type is String unless type says otherwise, in which case the container coerces the request-time expression. An attribute with rtexprvalue="true" — the default for tag files — accepts a runtime expression such as ${order.total}. Fragments are attributes of type JspFragment invoked with <jsp:invoke>, which is how a tag takes a block of markup as a parameter. Everything a tag file sets as a local variable is local to the tag's own page context and invisible to the caller, so a tag never leaks a variable — and correspondingly, the only way data comes back out is through the body or through an object the caller passed in.

10.2 SimpleTagSupport and a TLD

When a component needs Java — a query, a formatter, a call to a service — a tag file is no longer enough. A SimpleTag handler gives you a class with attributes and a body, packaged with a TLD so it can be used from a jar.

The handler API

Extend SimpleTagSupport and override doTag(). Attributes are plain setter methods: a method named setTitle(String) becomes the title attribute, optionally annotated with @TagAttribute from JSP 3.0 for documentation and metadata. The body, if the TLD declares scriptless, arrives as a JspFragment through setJspBody, and getJspBody().invoke(null) writes it to the current writer; passing a different Writer captures it instead. getJspContext() is the tag's page context, and it is how the tag reads and writes attributes in any scope. This class replaces the older TagSupport and BodyTagSupport API, which used an EVAL_BODY_INCLUDE return-code protocol; the simple API is what you should write in 2026, and the classic API is worth recognising only so you can read older code.

The TLD

A tag library descriptor lives in WEB-INF/tlds/ or in META-INF/ of a jar. It declares the library's uri and, per tag, the name, the handler class, the body content, and each attribute's name, type, required flag and whether it accepts a runtime expression. A jar-packaged library needs the TLD in META-INF so the container finds it by scanning; a web-application-local one can also be mapped in web.xml. The uri is an identifier, not a location, and the convention for a project-local library is a URN such as https://example.com/tags; the old urn:jsptagdir: and urn:jsptld: schemes exist for referencing a directory or a TLD without a URI.

When a handler beats a tag file

Reach for a handler when the component needs to call a service or the database, when the body must be captured and transformed rather than written through, when the same tag must be packaged in a jar for several applications, or when the logic is complex enough to deserve a unit test — a SimpleTag is a plain class, so new MyTag() with setters and a mock JspContext is a test. Stay with a tag file when the component is markup plus EL: a tag file has no build step, is editable by a designer, and cannot hold a database connection open.

10.3 Fragments, dynamic attributes and captured bodies

A fragment turns a block of markup into a first-class value. It is what lets a component place its caller's content in more than one region, or render it only under a condition.

Declaring and invoking a fragment

In a tag file, <%@ attribute name="header" fragment="true" %> declares an attribute whose value is markup. The caller supplies it with <jsp:attribute> rather than a plain attribute, because the value contains tags. Inside the tag, <jsp:invoke fragment="header"/> renders it. Invoking the same fragment twice renders it twice, which is how a component can use one block in two places — and it is also a way to render a fragment whose cost is not obvious, so invoke once unless you mean it. When a fragment is invoked, the EL expressions inside it are evaluated in the tag's page context if it was declared with var, or in the caller's if not, which is the rule that decides whether the fragment can see the caller's variables.

Capturing a body into a variable

<jsp:doBody var="captured" scope="page"/> writes the body into an attribute instead of the response, and the tag can then process it. In a tag file the body arrives as the implicit body variable; in a handler it is getJspBody(). Capturing is how you build a tag that wraps its content — a collapsible region that stores the content, a highlighter that transforms it, an A/B test that discards one variant. The captured value is a string of already-rendered markup, so anything the tag does with it afterwards is post-processing of HTML; treat it as markup, not as data, and do not feed it back into an escape function.

Dynamic attributes

<%@ tag dynamic-attributes="attrs" %> collects every attribute the caller passes that is not declared into a Map<String,String> named attrs. A tag can then emit them straight onto the element it renders, which is how a wrapper passes data-*, aria-* and arbitrary event attributes through without declaring each one. The security caveat is sharp: an attribute map applied verbatim lets a caller inject onclick or a javascript: URL, and with a strict CSP the injected handler will not run — but a href will still be followed. Whitelist the attribute names you forward, and never forward a name that starts with on.

10.4 Layouts and composition without a framework

Most "we need a framework" pressure in a JSP project comes from one real need: a single layout that wraps many pages. Two mechanisms in the specification cover it without adding a dependency.

The tag-file layout

A tag file called layout.tag with a single fragment attribute called body is a complete template-decorator. Each page declares the tag, wraps its content in <jsp:attribute name="body">, and the layout renders the HTML skeleton, the header, the navigation and the footer around it. Because the layout is a tag file, the content is escaped and rendered in the page's own context, and because the layout owns the html, head and body elements, every page is guaranteed to have a meta charset, a title and the same navigation. This is the pattern that replaces Tiles and Sitemesh for most applications, and it has one honest limitation: the layout cannot reorder content that the page has already rendered, so a per-page sidebar must be another fragment.

The two-pass JSP include

JSP 2.0 added the <jsp:output>-era fragment approach more formally, and the two-pass include is its older cousin: a page sets its body content into an attribute, then includes a layout that reads it. It still works and is still found in the wild, but the tag-file version is shorter, typed and easier to read, so new code should use a tag file. The one situation where a two-pass include wins is a layout that must run its own controller-provided logic before rendering, which is better handled by a filter that sets the layout's model attributes before the forward.

Splitting a page into components, and stopping

The rule for extraction is the third repetition, as with any function. In practice a JSP project converges on a small set: a layout, a page header with breadcrumbs, a table with a header row and empty state, a form field with an error slot, a pagination control, a flash-message block. Six components, each a few dozen lines, remove most of the duplication in a JSP application and, more importantly, concentrate the escaping, the accessibility attributes and the ARIA roles in one place each. Beyond that, adding more tags to avoid writing markup generally makes the markup harder to find rather than easier to reuse — and at the point where a component needs its own state and lifecycle, a component framework is the honest answer rather than a seventh tag.

11.1 Error pages: two mechanisms, one result

A stack trace on screen is both an information disclosure and an unprofessional page. The specification gives you two ways to replace it, and they are best used together.

Per-page errorPage and isErrorPage

The errorPage attribute on a page directive names a resource the container dispatches to if that page throws an uncaught exception. The target must declare isErrorPage="true", which makes the exception implicit object available and sets the response status to 500 unless the error page changes it. The attribute is scoped to one translation unit, so in a project with a layout and a dozen pages it means repeating the directive everywhere and forgetting it somewhere. It also only catches exceptions thrown inside that page's own code — a failure in a controller that happens before the forward never reaches the page's error page.

Application-wide error pages in web.xml

<error-page> maps either a status code or an exception type to a location, and it applies to the whole application including failures outside any JSP. The two forms are complementary: <error-code>404</error-code> handles a URL that matched nothing, a sendError(404) from your own code, or a resource the container refused; <exception-type> handles an exception that propagated out of a servlet, with the most specific matching type winning. When both exist the more specific match applies, so a mapping for java.lang.Throwable is a catch-all that should be listed as a fallback, not as the first entry. Since Servlet 3.0 these can also be declared with @WebServlet(...)? no — error pages have no annotation form, and are one of the strongest reasons to keep a web.xml even in an annotation-based application.

Reading the failure from the error page

The container exposes the failure through request attributes under the jakarta.servlet.error prefix: status_code, message, exception, exception_type, request_uri and servlet_name. From EL they are ${requestScope['jakarta.servlet.error.status_code']} and its siblings, and the constants on RequestDispatcher exist so you do not have to spell the string. Three rules make an error page useful: it must set the correct status code itself — a custom 404 page that returns 200 breaks every crawler and every client that checks the status; it must declare isErrorPage="true" if it wants the exception, or reach it through the request attribute if it does not; and it must never print the exception's message, class name or stack trace to the browser, because those disclose file paths, library versions and query fragments. Log the details, show the user an identifier, and make that identifier searchable in the log.

11.2 Handling failures in application code

Which failures you handle and which you let propagate is an architectural decision, and the most common mistake is handling everything, badly, in every place.

Three categories, three responses

Expected outcomes are part of the interface: a missing record, a validation failure, a name already taken. These should be values or a small checked exception, handled where the user can do something about it — re-rendered form, a 404 page, a redirect with a message. Programming errors are bugs: a null dereference, an unchecked cast, a query that returns two rows where one was expected. These should propagate, and be caught once at the edge, logged with full context, and turned into a generic 500, because continuing after one is how a small bug becomes corrupt data. Infrastructure failures — the database is down, the connection pool is exhausted, an upstream service times out — are neither: they need a retry policy, a circuit breaker, and a 503 with a Retry-After rather than a 500, because the honest answer is "try again shortly".

One boundary, one translation

Translate exceptions to HTTP in exactly one place. A filter wrapping the chain turns domain exceptions into statuses, or servlets do it in a small base class, or an <exception-type> mapping does it; what must not happen is every servlet inventing its own mapping, so that the same failure is a 404 in one endpoint and a 500 in another. A useful shape is a base servlet that overrides service and delegates to a handle method inside a try/catch which maps a small, documented set of exception types and rethrows anything else to the container's error page. That keeps the mapping declarative and visible in one file.

Logging that can be acted on

Log once, at the boundary, with the context needed to reproduce: the request id, the method and path, the user, and the exception. Logging the same exception at every layer produces a page of identical stacks and hides the one line that mattered. Do not log secrets, session ids, passwords, tokens or full request bodies; do log the correlation id in the response so a support conversation can find the entry. And make the difference between "handled" and "unhandled" visible — a handled validation failure is a debug line, an unhandled 500 is an error that should page someone. If your logging is not split that way, an alerting rule on "number of errors" will be permanently noisy and permanently ignored.

// A base servlet that maps exceptions to statuses in one place
public abstract class BaseServlet extends HttpServlet {

    @Override
    protected final void service(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        try {
            handle(req, resp);
        } catch (NotFoundException e) {
            req.setAttribute("errorRef", ref());
            req.getRequestDispatcher("/WEB-INF/views/error/404.jsp").forward(req, resp);
        } catch (AccessDeniedException e) {
            resp.sendError(HttpServletResponse.SC_FORBIDDEN);
        } catch (ValidationException e) {
            req.setAttribute("errors", e.errors());
            resp.setStatus(HttpServletResponse.SC_BAD_REQUEST);
            req.getRequestDispatcher("/WEB-INF/views/error/form.jsp").forward(req, resp);
        } catch (SQLException e) {
            // infrastructure: 503 says "try again", 500 says "we are broken"
            log.error("database failure path=" + req.getRequestURI(), e);
            resp.setHeader("Retry-After", "30");
            resp.sendError(HttpServletResponse.SC_SERVICE_UNAVAILABLE);
        }
        // anything else propagates to the container's error page
    }

    protected abstract void handle(HttpServletRequest req, HttpServletResponse resp)
            throws Exception, ServletException, IOException;

    private static String ref() {
        return UUID.randomUUID().toString().substring(0, 8);
    }
}

11.3 Resource bundles, locales and formatting

Internationalisation is mostly a discipline: no user-visible string in Java code or a JSP, nothing concatenated, and a locale decided once per request rather than guessed in a dozen places.

Bundles and locale resolution

A ResourceBundle is a set of property files with a base name: messages.properties, messages_fr.properties, messages_pt_BR.properties. The lookup falls back from the most specific candidate to the base file, so a missing key silently uses the base language rather than failing — which is the right behaviour for production and the reason a missing translation is easy to miss. Resolve the locale once per request, in a filter, and store it on the session or the request: the usual order is an explicit user choice, then a cookie, then Accept-Language, then a default. Accept-Language is a user-controlled header with quality values and, on some browsers, dozens of entries; parse it with a library or with Locale.lookup against your supported set rather than taking the first value, and store the resolved locale so that a change does not alter every link's URL.

At runtime versus at translation time

JSTL's fmt tags resolve the bundle at request time, which means a language switch takes effect without a redeploy — the right default for a JSP application. Load the message keys into Java code through ResourceBundle.getBundle(base, locale) and never through the tags, so that both layers read the same file. Localise the bundle to the message, not to the code: a key named order.created survives a wording change, while click_here_to_submit does not. Avoid the two classic traps — never build a sentence by concatenating fragments ("You have " + n + " items") because word order differs between languages, and never bake text into an image, because it cannot be translated at all.

Formatting and plurals

Numbers and dates are formatted through NumberFormat and DateFormat with the resolved locale, which the fmt tags do automatically; MessageFormat handles parameters and choice formats, giving real plural handling rather than an (s) suffix. Keep the formatted output as text, not as a value fed into arithmetic — parsing a localised number back into a number belongs in the model with an explicit pattern, and doing it by hand is how 1.234,50 becomes 1.234. Finally, remember the layout consequences: German words are longer, Arabic and Hebrew read right to left so the document needs dir, and a fixed-width button sized for English will clip in Finnish.

// A filter that resolves and pins the locale for the request
@WebFilter(urlPatterns = "/*")
public class LocaleFilter implements Filter {

    private static final Set<Locale> SUPPORTED =
        Set.of(Locale.ENGLISH, Locale.FRENCH, Locale.forLanguageTag("pt-BR"));

    @Override
    public void doFilter(ServletRequest rq, ServletResponse rs, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) rq;
        Locale locale = resolve(req);
        req.setAttribute("locale", locale);
        ((HttpServletResponse) rs).setLocale(locale);      // sets Content-Language too

        chain.doFilter(rq, rs);
    }

    private static Locale resolve(HttpServletRequest req) {
        // 1. explicit choice, remembered in the session
        HttpSession s = req.getSession(false);
        if (s != null && s.getAttribute("locale") instanceof Locale chosen) {
            return chosen;
        }
        // 2. the browser's preference, matched against what we translate
        String header = req.getHeader("Accept-Language");
        if (header != null) {
            List<Locale.LanguageRange> ranges = Locale.LanguageRange.parse(header);
            Locale match = Locale.lookup(ranges, new ArrayList<>(SUPPORTED));
            if (match != null) return match;
        }
        // 3. fall back to the container's default locale
        return Locale.getDefault(Locale.Category.DISPLAY);
    }
}

11.4 Character encoding, end to end

Mojibake almost never has a single cause. It has a chain, and the chain has to be UTF-8 at every link from the editor to the database to the browser.

The chain

The source file on disk, the JSP pageEncoding, the response contentType charset, the request character encoding, the URL encoding of the query string, the JDBC connection's client encoding, the database's own encoding, and the HTML meta charset. Each link is independent, and a single mismatch produces a different symptom: a wrong pageEncoding corrupts string literals inside the compiled JSP; a wrong request encoding corrupts form input; a wrong response charset corrupts the output; a wrong database encoding stores the corruption permanently, which is the one that cannot be fixed by a configuration change. Modern defaults help — JDK 18 and later default file.encoding to UTF-8, Servlet 6.x containers default the request encoding to UTF-8, and Tomcat 10+ decodes the URI as UTF-8 — but a deployment should still declare every one of them, because the defaults are the container's to change.

The pieces that need a declaration

In the page, contentType="text/html;charset=UTF-8" and pageEncoding="UTF-8", or a JSP property group covering every JSP. In the filter chain, setCharacterEncoding("UTF-8") first, before anything reads a parameter. On the connector, URIEncoding left at its UTF-8 default and useBodyEncodingForURI left alone. On the database, a UTF-8 database and a connection string that asks the driver for UTF-8 — characterEncoding=UTF-8 for MySQL, client_encoding=UTF8 as a connection parameter for PostgreSQL — with a test that inserts and reads back a four-byte emoji, which is the value that catches every legacy three-byte configuration. In the HTML, <meta charset="UTF-8"> as the first element in head, so the browser does not have to guess before it parses a BOM-less file. And in the file itself, a real UTF-8 encoding with no byte-order mark, saved by an editor that is configured to write UTF-8 rather than the platform default.

Headers, filenames and the awkward cases

HTTP header values are historically ISO-8859-1, so a non-ASCII filename in Content-Disposition has to be encoded per RFC 6266 with filename*=UTF-8''… plus percent encoding, or it will arrive mangled. A cookie value is restricted to ASCII, so it must be percent-encoded on the way out and decoded on the way in. An uploaded file's name arrives in the multipart headers, where the encoding depends on the client; treat it as untrusted and store a generated name. And a query parameter containing a multi-byte character in a URL must be percent-encoded by whoever builds the URL — which is one more reason to build links with <c:url> and <c:param> rather than string concatenation.

12.1 Deploying a WAR to Tomcat

Deployment is a directory, a context path and a set of resources. Getting those three right turns a working application on a laptop into one that survives a restart and a second instance.

The deployment mechanisms

Dropping a WAR into $CATALINA_BASE/webapps is the simplest: the container unpacks it, creates a context whose path is the WAR's name without the extension, and serves it. ROOT.war becomes the default context at /. A Context element in conf/server.xml or conf/Catalina/localhost/<name>.xml gives you an explicit, version-controlled context with a fixed docBase; the second location is preferred, because editing server.xml requires a restart and the per-context file can be reloaded. An exploded directory is a valid deployment and reloads faster. What all three share is that the context path is the identity of the application, so every URL the application generates must be relative to getContextPath() or the application will work at / and break at /shop.

Context configuration and JNDI resources

Everything a single application needs that is not in the WAR belongs in its context file: the session manager, a CookieProcessor, resource definitions, and any Valve. A JNDI DataSource defined there is looked up by the application, which keeps the credentials out of the WAR and lets two deployments of the same artefact point at different databases. The lookup returns a javax.sql.DataSource and the application calls getConnection(), so the pool is the container's and is closed when the context stops. The alternative — a pool created inside a ServletContextListener — is more portable across containers and downloadable from the container's documentation, at the price of the credentials being in the application's configuration. Either is legitimate; mixing them, so that a pool is created per context and per host, is how you end up with three pools where one was intended.

Environment-specific configuration

Never bake a URL, a credential or a feature flag into the WAR: the same artefact should be promoted from staging to production unchanged. The four accepted channels are JNDI resources, JVM system properties set in setenv.sh, environment variables read with System.getenv, and a configuration file mounted outside the application. Read them once, in a listener, validate them, and fail the deployment if one is missing — the alternative is an application that starts happily and fails on the first request with a null URL. Prefer a single typed configuration object created at startup to scattered System.getenv calls, because the object can be validated as a unit and logged without its secrets.

    }
}
reloadable="true" looks convenient in development and leaks a class loader on every change: the container can only reload by discarding the whole class loader, and a thread, a JDBC driver registration or an unclosed pool from the old one keeps it alive. Restart the container instead, and reserve reloadable for a short edit-and-test loop.

12.2 Embedded containers and containers as artefacts

An embedded container is a library in your own main. It buys reproducible configuration, a single process to monitor and an image that carries everything it needs.

Embedding Tomcat, Jetty or Undertow

Embedding Tomcat is a few dozen lines: create a Tomcat, set a base directory and a port, add a context, register servlets and filters, and call start(). The interesting parts are the ones you now control explicitly — a ServletContextListener for the pool, a filter registration with explicit ordering, the error pages and the session configuration that used to be in web.xml. Jetty 12 expresses the same thing with a Server, a ServerConnector and a WebAppContext whose environment selects the Jakarta EE generation, so an ee10 environment serves a Servlet 6.0 application and an ee11 one serves Servlet 6.1. Undertow is built for exactly this and exposes a fluent handler builder. In all three the application's web.xml is still honoured if you point the context at the WAR or the directory, which is the easiest way to reuse existing configuration.

Images and configuration

With an embedded container the application is an executable jar, and the image is FROM eclipse-temurin:21-jre plus that jar and a non-root user. Build the image so that configuration arrives from the environment, the port is configurable, the process handles SIGTERM by shutting down gracefully — the listener's contextDestroyed is where the pool is closed and in-flight requests are allowed to finish — and nothing writes to the container filesystem except a temporary directory that is mounted. A JVM in a container also needs its heap limits derived from the cgroup, which -XX:MaxRAMPercentage does, rather than a fixed -Xmx inherited from a different machine. Session affinity stops being a special case: if the application is stateless apart from a cookie, any replica can serve any request, and the load balancer needs no stickiness at all.

Which one to choose

Standalone is the right answer when someone else operates the server, when the deployment unit is a WAR handed to an operations team, or when the same host runs several applications. Embedded is the right answer when the application is the unit of deployment and already ships as a container image, when configuration must be reviewable in version control, and when startup time and memory matter. The important point is that the choice is reversible at the level of the code: a servlet, a filter and a JSP do not know which one hosts them, so the decision can be revisited without a rewrite — provided nothing depends on a container-specific API. Anything that reaches into Tomcat's internals, a Tomcat Valve, or a Jetty handler from application code is the thing that makes the choice permanent.

12.3 Testing servlets, filters and views

Servlets are testable, and the tests that pay for themselves are the cheap ones: a plain unit test with a mocked request, and one integration test that starts a real container.

JUnit 5 plus Mockito, for the fast majority

A servlet is a class with overridable methods, so a test constructs it, stubs a request, and asserts on the response. Mockito mocks HttpServletRequest and HttpServletResponse; the one piece of setup that is easy to get wrong is the writer, because getWriter() must return a real PrintWriter over a StringWriter so the test can read what was written. Everything after that is an ordinary assertion: the parameter parsing, the attribute set, the status, the redirect target, the error map. The value of these tests is not coverage, it is the boundary conditions — a missing parameter, a negative quantity, a parameter that is present but empty — which is exactly the set that a browser-based smoke test never exercises.

Filter tests are the same shape

A filter test passes a mock FilterChain into doFilter and asserts on what happened to the request and the response plus whether the chain was invoked. That last assertion is the important one: a filter that forwards to login must not call the chain, and a filter that passes through must call it exactly once. A test that counts chain invocations is the guard against the worst filter bug, which is a silent block.

Integration tests with a real container

For the parts a mock cannot prove — the URL mapping, the JSP translation, the filter order, the error page dispatch, the encoding — start an embedded container in a JUnit extension and issue a real HTTP request with the JDK's HttpClient. That verifies the whole chain from mapping to rendered HTML in one test. To assert on HTML, parse it with jsoup rather than matching on a raw string, so the test fails when the content is wrong and not when the whitespace is. Two integration tests that are always worth having: a round trip that posts a form with a non-ASCII value and asserts the same value comes back in the rendered page, which covers the entire encoding chain; and a request to a protected URL that asserts a redirect to login, which covers the filter and the constraint.

12.4 Moving to Spring MVC, and when not to

Every mechanism in this guide has a Spring MVC equivalent that removes boilerplate. The list also shows what you would be giving up, and whether the trade is worth it for your application.

The direct mapping

A servlet becomes a @Controller class with @RequestMapping methods. getParameter plus a binder becomes @RequestParam and @ModelAttribute with Bean Validation. setAttribute plus a forward becomes a returned view name and a Model argument. A filter becomes a HandlerInterceptor or a OncePerRequestFilter. Declarative security becomes Spring Security, which is a far larger surface than the container's model, with session fixation protection, CSRF tokens and header defaults built in. The JSP stays exactly as it is: Spring MVC renders JSP through the same InternalResourceViewResolver and the same /WEB-INF/views convention, so a migration can be incremental — a new controller next to the old servlets, sharing the same JSPs.

What Spring actually buys

Argument binding and validation are the biggest win, because they are the most repetitive part of hand-written servlet code. Dependency injection is the second, because it makes the pool and the DAOs injectable and testable without a service locator. The third is a mature security stack: correct CSRF handling, session fixation protection and a set of security headers that are the product of years of CVE reports. The fourth is ecosystem: @ControllerAdvice for error handling, content negotiation, message converters, and the option of returning JSON from the same methods without a second code path. All of that is real, and it is why most new Java web applications in 2026 start there.

What you would give up, and when to stay

Spring adds a dependency graph, a startup cost, a second configuration model and a large amount of framework-specific knowledge. For a small internal application with a dozen pages, a handful of forms and one database, plain servlets and JSP have no build step beyond mvn package, no version upgrades to chase, and a debugging experience where the stack trace names your code at every frame. The honest decision rule: migrate when the cost of the boilerplate exceeds the cost of the framework — which in practice is when there are several controllers that share cross-cutting concerns, when security requirements go beyond the container's declarative model, or when more than one developer needs a shared convention. If a team of one is maintaining a twenty-page application that works, migrating is a cost with no return.
