This opening chapter explains how to work through the guide offline, chapter by chapter, so you build Nuxt knowledge and muscle memory by typing real code. The right mindset

This section frames Nuxt’s core philosophy of conventions over configuration: folders and file names wire up most behavior automatically. When something appears to be magic, a naming convention or directory layout is behind it, from pages/ routes to auto-imported composables. Adopting that mindset makes Nuxt predictable once you learn the rules.

Nuxt rewards understanding conventions. Drop a file in the right folder and Nuxt wires it up — that is the whole idea. When something feels magical, ask: which folder or naming convention caused this? That one question answers most "how does Nuxt do that?" moments.

Keep the official docs open beside this guide at nuxt.com/docs. This guide explains the why and the sequence; the docs are the exhaustive reference.

1 · Nuxt Fundamentals & Setup

1.1 What Nuxt adds over Vue1.2 Auto-imports: no more import lines1.3 The app structure that matters1.4 Your first project with nuxi1.5 nuxt.config.ts

This chapter boots a working Nuxt application and explains what Nuxt adds on top of plain Vue, such as file-based routing, auto-imports and a built-in server. You scaffold a project with npx nuxi init, start the dev server, and explore the folder layout and nuxt.config.ts. By the end you can navigate and edit a running app confidently.

Nuxt is a meta-framework on top of Vue: it adds file-based routing, SSR and SSG, auto-imports, a server engine and SEO tooling while you keep writing ordinary Vue components. This chapter boots a project and explains the ideas the whole course rests on.

1.1 What Nuxt adds over Vue

This section compares a plain Vue single-page app with a Nuxt application and details what Nuxt enables by default: file-based routing, auto-imports, a Nitro server and SSR. It explains why these defaults remove the manual wiring of build tools and libraries. The main takeaway is that Nuxt provides structure and a server without adding separate frameworks.

Plain Vue is a library you assemble: you choose the router, the state store, the SSR layer and the bundler. Nuxt is a framework with opinions — it brings Vue Router, Nitro, a folder contract and composables, so you skip the plumbing and start shipping pages.

// package.json highlight — one dependency pulls in the whole framework
{
  "name": "my-app",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "nuxt dev",            // HMR dev server on localhost:3000
    "build": "nuxt build",        // production build into .output/
    "preview": "nuxt preview"     // run the built output locally
  },
  "devDependencies": { "nuxt": "^3.14.0" }
}

A Nuxt app needs only the nuxt package and three scripts; the nuxi CLI inside it handles dev, build and preview, and the router and server ship built in.

1.2 Auto-imports: no more import lines

This section covers Nuxt’s auto-import system, where composables, utilities and components resolve by naming convention without import statements. Components in the components/ folder and functions in composables/ and utils/ folders become available automatically across the app. Relying on the convention keeps everyday code short and readable.

// Anywhere in the app — no import statement needed
const count = ref(0)                      // Vue APIs are auto-imported
const router = useRouter()                // as are Nuxt composables
const { data } = await useFetch('/api/posts')

// Only unusual helpers need an explicit import
import { formatDate } from '~/utils/date'

Nuxt auto-imports Vue APIs, Nuxt composables, and files inside composables/ and utils/, so everyday code carries almost no import lines at all.

Auto-import resolves by file name and export name. Name files useMyFeature, MyFeature or formatDate and they become available app-wide.

1.3 The app structure that matters

This section maps the folders Nuxt watches by convention: pages/ for routes, components/ for UI, layouts/ for shared shells, composables/ and utils/ for logic, server/ for API endpoints, and public/ for static assets. Each folder has a defined job, and file names become the URL or tag name. Knowing what each directory does is half of mastering Nuxt.

PathWhat lives there

components/Vue components, auto-imported
layouts/Shared page layouts; default.vue is the base
composables/, utils/Auto-imported functions
assets/, public/Source assets and files served as-is
server/API routes and middleware running in Nitro

1.4 Your first project with nuxi

This section walks through scaffolding a first project with npx nuxi init and starting the development server with npm run dev. It explains the generated file structure and how to open the app in the browser before adding a first page. Within minutes you go from an empty directory to a live, editable Nuxt application.

npx nuxi@latest init my-app --packageManager npm   # scaffold a fresh project
cd my-app
npm install                                          # install the dependencies
npm run dev                                          # dev server with hot reload

# open http://localhost:3000 — edits to pages/ reload instantly

nuxi init scaffolds the whole project, npm install pulls dependencies, and the dev server on localhost:3000 hot-reloads as you edit files.

1.5 nuxt.config.ts

This section introduces nuxt.config.ts, the single config file where most framework tweaks live. Here you set SSR mode, the default app head, favicon, css, modules and route rules using the defineNuxtConfig helper. Most features, including Pinia or Tailwind, are enabled simply by adding a module to the modules array. TypeScript gives autocomplete for every key.

// nuxt.config.ts
export default defineNuxtConfig({
  ssr: true,                    // server-side rendering is on by default
  devtools: { enabled: true },  // in-browser devtools at /_devtools
  app: {
    head: {
      title: 'My App',
      htmlAttrs: { lang: 'en' },   // lang attribute on the root element
    },
  },
  modules: ['@nuxtjs/tailwindcss'],   // add features by listing modules
})

The config turns on devtools, sets global head defaults and registers modules; keeping it small means the framework does more of the work for you.

2 · Pages & File-Based Routing

2.1 Static pages and the router root2.2 Dynamic and catch-all routes2.3 Nested routes with parent/child pages2.4 Navigation, page metadata and middleware

This chapter covers Nuxt’s file-based routing, where every file under pages/ becomes a route whose URL mirrors the file tree. You build static, dynamic and nested routes, navigate with NuxtLink and navigateTo, and attach page metadata and middleware with definePageMeta. The result is zero-config routing that scales naturally with your files.

Nuxt generates its router from the file tree — pages/about.vue becomes /about, and folders nest routes. Combined with auto-imported components, this replaces hundreds of lines of router config with folder names.

2.1 Static pages and the router root

This section shows how a file such as pages/about.vue becomes the about route and how the root component in app.vue hosts pages inside NuxtPage. The mapping is predictable: directory and file names translate directly into URL segments. This convention makes the route table trivial to predict and to extend.

<!-- app.vue — the root component hosting every page -->
<template>
  <div>
    <NuxtPage />   <!-- renders the matched page component -->
  </div>
</template>

<!-- pages/index.vue      → / -->
<!-- pages/about.vue      → /about -->
<!-- pages/blog/index.vue → /blog -->

NuxtPage renders the matched page, and each file under pages/ maps directly to a URL — nested folders become nested URL segments.

2.2 Dynamic and catch-all routes

This section covers dynamic segments written in square brackets, such as pages/[id].vue, and catch-all routes written as [...slug].vue for matching several segments at once. The useRoute() composable reads the current params anywhere in a page, and navigateTo handles movement between dynamic paths. Matchers with no candidate can fall back to a 404 or a designated fallback route.

<script setup lang="ts">
const route = useRoute()               // the current route object, reactive
const id = String(route.params.id)     // from pages/posts/[id].vue

// fetch the post for this id — runs on the server and again on the client
const { data: post } = await useFetch('/api/posts/' + id)
</script>

<template>
  <h1>Post {{ id }}</h1>
  <p>{{ post?.title }}</p>
</template>

<!-- pages/docs/[...slug].vue → matches /docs/a/b/c -->
<!-- params.slug = ['a', 'b', 'c'] -->

Square brackets capture one URL segment, [...] catches everything after it, and useRoute().params hands you those values inside the page.

2.3 Nested routes with parent/child pages

This section builds nested layouts out of the file tree: a folder holds a parent page that includes NuxtPage, and the child page components render inside it. Both levels share route params through useRoute, and the parent state is preserved while children swap. This structure mirrors the filesystem exactly, making complex screens easy to organize.

<!-- pages/users/[id].vue — the parent page -->
<template>
  <div>
    <h1>User {{ $route.params.id }}</h1>
    <NuxtPage />   <!-- child pages render inside here -->
  </div>
</template>

<!-- pages/users/[id]/posts.vue   → /users/7/posts -->
<!-- pages/users/[id]/settings.vue → /users/7/settings -->

A page with its own folder acts as a parent layout: child pages render in its NuxtPage, keeping shared headers and tabs in one file.

2.4 Navigation, page metadata and middleware

This section shows navigation, page metadata and the simplest route middleware. You move between routes with the NuxtLink component or programmatically with navigateTo, publish titles and layouts through definePageMeta, and attach a named middleware to the same meta object. Together these control how users move through the app.

<template>
  <nav>
    <NuxtLink to="/">Home</NuxtLink>
    <NuxtLink to="/blog">Blog</NuxtLink>
    <NuxtLink :to="blogLink">Latest post</NuxtLink>
  </nav>
</template>

<script setup lang="ts">
const blogLink = { path: '/blog', query: { page: 2 } }   // object targets work too

function go() {
  navigateTo('/about')            // programmatic navigation
}

// per-page metadata plus a tiny inline route guard
definePageMeta({
  layout: 'default',
  middleware: defineNuxtRouteMiddleware((to) => {
    if (!to.query.token) return navigateTo('/login')
  }),
})
</script>

NuxtLink renders real prefetching links, navigateTo() moves the app programmatically, and definePageMeta wires a per-page layout plus an inline route guard.

3 · Components, Layouts & SEO

3.1 Auto-imported components3.2 Props, emits and defineModel3.3 Layouts and NuxtLayout3.4 SEO with useHead and useSeoMeta

This chapter turns page code into structured, shareable UI using auto-imported components, typed props and emits, and reusable layouts. It also covers the SEO composables useHead and useSeoMeta for titles, meta tags and Open Graph data. By the end you can build consistent interfaces with centralized head settings.

Any component in components/ is available in every template without an import. Layouts wrap the whole page chrome, and useHead layers per-page titles and meta. Together they replace most of the boilerplate of a hand-built Vue UI.

3.1 Auto-imported components

This section explains that any component placed under components/ is auto-imported, so its tag works anywhere without an import line. Nested folders extend the tag name with a prefix: components/base/Button.vue becomes BaseButton. The lazy option and dynamic imports handle on-demand loading when components grow large.

<!-- components/BaseButton.vue → usable anywhere as <BaseButton> -->
<template>
  <button :class="variant"><slot /></button>
</template>

<!-- components/ui/Card.vue → <UiCard> (the folder becomes a prefix) -->
<template>
  <div class="card"><slot /></div>
</template>

<!-- everywhere else — no import needed -->
<template>
  <UiCard>
    <BaseButton variant="primary">Save</BaseButton>
  </UiCard>
</template>

Components resolve by name from the components/ folder — nesting adds a namespace — and slots let children pass content into the markup.

3.2 Props, emits and defineModel

This section shows the script setup pattern for passing data down and emitting events up. You declare props with defineProps and events with defineEmits using TypeScript types, which are then enforced at compile time. The defineModel macro creates a two-way binding with a single declaration. Typed definitions double as documentation and editor autocomplete.

<script setup lang="ts">
// typed props with defaults
const props = defineProps<{
  title: string
  variant?: 'primary' | 'ghost'      // union type documents the options
}>()

// declared emits — the names a parent can listen for
const emit = defineEmits<{ (e: 'saved', id: number): void }>()

const count = defineModel<number>()   // two-way v-model with the parent
</script>

<template>
  <button @click="emit('saved', 42)">{{ title }} · {{ count }}</button>
</template>

defineProps and defineEmits give typed component contracts, and defineModel wires a v-model pair without hand-written events.

3.3 Layouts and NuxtLayout

This section covers the default layout at layouts/default.vue and how to assign a different one per page with definePageMeta layout: name. NuxtLayout wraps the page inside the matched layout, and the naming convention keeps headers, footers and sidebars out of individual pages. Restructuring shared page chrome becomes a single file change.

<!-- layouts/default.vue — applied when no layout is chosen -->
<template>
  <div>
    <header><SiteNav /></header>
    <main><slot /></main>               <!-- the page content lands in the slot -->
    <footer><SiteFooter /></footer>
  </div>
</template>

<!-- layouts/blank.vue — opt out of the chrome entirely -->
<template><slot /></template>

<!-- pages/login.vue -->
<script setup lang="ts">
definePageMeta({ layout: 'blank' })   // pick a non-default layout per page
</script>

Layouts wrap pages in shared chrome: default.vue applies automatically, pages opt into another layout with definePageMeta, and the page itself lands in the slot.

Layouts stay mounted between navigations, so keep stateful nav UI here instead of app.vue when you want per-path behavior.

3.4 SEO with useHead and useSeoMeta

This section shows per-page SEO with the useHead and useSeoMeta composables in a page script setup. You set the title, description, canonical link and Open Graph tags for each screen, and a global title template in nuxt.config keeps branding consistent. Head values update reactively as users navigate.

<script setup lang="ts">
// per-page head — merges over the global config defaults
useHead({ title: 'About' })

// typed shortcut for the most common SEO fields
useSeoMeta({
  title: 'About — My App',
  ogTitle: 'About — My App',
  description: 'Who we are.',
  ogImage: '/og/about.png',
})
</script>

useHead and useSeoMeta set reactive head tags per component; pairing them with a global title template gives every page a branded title suffix.

// nuxt.config.ts — global defaults and a title template
export default defineNuxtConfig({
  app: {
    head: {
      charset: 'utf-8',
      viewport: 'width=device-width, initial-scale=1',
      titleTemplate: '%s · My App',   // every page title ends with this suffix
      htmlAttrs: { lang: 'en' },
    },
  },
})

The config seeds charset, viewport and a title template; %s is replaced with a page’s own title, giving a consistent brand across every route.

4 · Data Fetching

4.1 useFetch4.2 useAsyncData and $fetch4.3 refresh, watch and cache keys4.4 pending, error and immediate4.5 Parallel and dependent requests

This chapter covers server-safe data fetching with useFetch, useAsyncData and the $fetch helper, whose results are cached and reactive. You load data during SSR so the first HTML already contains the content, then refresh or watch it on the client and render loading and error states. This replaces hand-rolled fetch code across the whole app.

Nuxt’s data layer is built on three pieces: $fetch (the raw HTTP call), useAsyncData (caching, deduplication and SSR) and useFetch (a convenience wrapper around both). The result is data fetched once on the server and reused for the first client render.

4.1 useFetch

This section presents useFetch as the everyday data composable. You pass a URL plus options such as method, params, query and body, and receive data, pending, error and refresh in return. It behaves the same during SSR and on the client and infers the payload type from the endpoint response.

<script setup lang="ts">
// fetches on the server at request time and reuses the data on the client
const { data, pending, error, refresh } = await useFetch('/api/posts')

// with a cache key and a transform — pick only what the page needs
const { data: posts } = await useFetch('/api/posts', {
  key: 'posts',                        // cache key, dedupes parallel calls
  transform: (rows) => rows.slice(0, 10),
})
</script>

<template>
  <p v-if="pending">Loading</p>
  <p v-else-if="error">{{ error.message }}</p>
  <div v-else v-for="post in posts" :key="post.id">{{ post.title }}</div>
</template>

useFetch runs during SSR and hands the page a reactive result; the template branches on pending and error before rendering the loaded posts.

4.2 useAsyncData and $fetch

This section shows useAsyncData, the lower-level composable that wraps any async function, and pairs it with the $fetch helper for full control. You supply a handler that returns the data and options that govern caching and SSR behavior. It is the building block behind useFetch and the right place to add custom logic around a request.

<script setup lang="ts">
const slug = String(useRoute().params.slug)

// $fetch gives you full control of the request
const { data: post } = await useAsyncData('post-' + slug, async () => {
  const all = await $fetch('/api/posts')
  const one = all.find((p) => p.slug === slug)   // pick from the full list
  if (!one) throw createError({ statusCode: 404, message: 'Post missing' })
  return one
})
</script>

useAsyncData runs any async function with the same caching and SSR guarantees, while $fetch handles the HTTP call — the escape hatch for custom data logic.

4.3 refresh, watch and cache keys

This section explains how to re-fetch data and invalidate the cache. A clear key plus calling refresh() covers most stale-data problems, and the watch option refetches automatically when a reactive source changes. Reusing the same key across components shares one cached payload. This keeps fresh data visible after mutations.

const route = useRoute()
const { data: posts, refresh } = await useFetch('/api/posts', {
  key: 'public-posts',                 // explicit key = dedicated cache slot
})

// re-fetch when the page query changes
watch(() => route.query.page, () => refresh())

// evict a cache slot so the next read goes to the network again
clearNuxtData('public-posts')

A stable key makes the same request share one cache slot, watch re-fetches when inputs change, and clearNuxtData evicts a slot so the next read fetches fresh.

4.4 pending, error and immediate

This section shows the status fields returned by the data composables: pending and error tell templates what to render, while the immediate option controls whether fetching starts on mount or when you call execute(). Because the returned data is a ref, mutations update templates reactively with no extra wiring.

const { data, pending, error, execute } = useFetch('/api/search', {
  immediate: false,      // do not fire until execute() is called
  watch: [query],        // auto re-fetch when query changes
})

function search() { execute() }

data.value = []          // mutate to make fallback UI instantly
if (error.value) console.error(error.value.statusCode)

immediate:false defers the request until execute(), watch ties refetching to other reactive values, and data/error are plain reactivity you can read and assign.

4.5 Parallel and dependent requests

This section covers running several independent requests efficiently. Multiple useFetch calls in a page run in parallel and are awaited together before the page renders, and a single useAsyncData can wrap Promise.all for grouped calls. Dependent sequences await the first result before starting the next. Parallel fetching keeps pages fast.

<script setup lang="ts">
// independent calls run in parallel; the await gates render both together
const [profile, { data: posts }] = await Promise.all([
  useAsyncData('profile', () => $fetch('/api/profile')),
  useFetch('/api/posts'),
])

// a dependent call starts once its input value exists
const { data: user } = await useFetch('/api/users/me')
const { data: feed } = await useFetch(() => '/api/feed/' + user.value?.team)
</script>

Promise.all fires independent fetches at the same time, while a dependent fetch only starts once user.value exists — the pattern for building chained requests.

5 · State Management

5.1 useState5.2 Installing and creating Pinia stores5.3 Using stores in pages5.4 Persistence patterns5.5 When to use which

This chapter covers shared reactive state with useState and Pinia for structured application state. You learn to define stores with state, getters and actions and to consume them from pages alongside the data-fetching composables. It also covers persistence patterns and guidance on when each tool is the right fit.

Nuxt has two state layers: the lightweight useState composable for a single shared value, and Pinia (a module) for a full store with state, getters and actions. SSR-safe by default, state created on the server is serialized into the payload so the client keeps the same data.

5.1 useState

This section shows useState, the SSR-safe shared state composable. A value created with the same key on the server and client resolves to one reactively shared ref, so hydrated state survives the transfer. An optional factory function provides the initial value, and TypeScript infers the payload type. State stays globally accessible across components.

<script setup lang="ts">
// shared, SSR-safe counter — the key makes it global across components
const count = useState('counter', () => 0)

function bump() { count.value++ }   // every component using the key sees the change
</script>

<template>
  <button @click="bump">Count: {{ count }}</button>
</template>

useState(key, init) returns one reactive value shared by every component that uses the same key, initialized on the server and hydrated on the client.

Put useState calls inside a composable in composables/ so auto-import works and the key lives in exactly one place.

5.2 Installing and creating Pinia stores

This section adds the Pinia module to nuxt.config, either directly or via @pinia/nuxt, then defines the first store file in the stores/ directory with defineStore. Nuxt auto-imports the store hook from the file name with the use prefix. The module wires the store into the app lifecycle and SSR hydration automatically.

npm install @pinia/nuxt pinia
# then add '@pinia/nuxt' to the modules array in nuxt.config.ts

// stores/cart.ts — any store file is found by the module
export const useCartStore = defineStore('cart', () => {
  const items = ref([])                                  // state
  const total = computed(() =>
    items.value.reduce((sum, item) => sum + item.price, 0))   // getter
  function add(item) { items.value.push(item) }          // action
  return { items, total, add }
})

With the module installed, a store is just defineStore; the setup style returns refs as state, computeds as getters and functions as actions.

5.3 Using stores in pages

This section shows consuming a store from a page with its auto-imported hook and filling it from fetched data. Getters read like computed values and actions are invoked like methods, so stores compose naturally with useFetch and useState. A common first example is a login flow or a shopping cart that needs data on both server and client.

<script setup lang="ts">
const cart = useCartStore()                // auto-imported, shared across the app
const { data } = await useFetch('/api/cart')

// sync server data into the store on load
cart.$patch(data.value ?? { items: [] })

async function checkout() {
  cart.saving = true                       // extra state can live alongside
  await $fetch('/api/checkout', { method: 'POST', body: cart.items })
  cart.saving = false
  cart.items = []
}
</script>

The page reads the shared store, hydrates it from the fetched payload, and calls a store action plus a plain assignment to drive the checkout flow.

5.4 Persistence patterns

This section shows the two common persistence approaches: cookies for values the server must read, handled with the useCookie composable, and localStorage for state needed only by the client. The decision depends on who later consumes the data and how far it must survive reloads. Tokens typically live in cookies so every request carries them.

// server/client-readable: useCookie is a Nuxt composable
const theme = useCookie('theme', { maxAge: 60 * 60 * 24 * 365 })   // lasts one year

// or mirror a client-only store to localStorage with a deep watch
watch(cart.items, (value) => {
  localStorage.setItem('cart', JSON.stringify(value))
}, { deep: true })

// and read it back when the store initializes
const saved = ref(JSON.parse(localStorage.getItem('cart') || '[]'))

Small values the server must see belong in cookies via useCookie, while bulk client-only state can be mirrored to localStorage through a deep watch.

5.5 When to use which

This section decides between useState and Pinia based on the shape of your app. For a few shared values, useState keeps things minimal; Pinia pays off when state gains logic, cross-cutting usage or devtools requirements. The working rule is to start with useState and introduce Pinia as the codebase grows.

SituationReach for
A single shared value across componentsuseState
Per-request values (theme, locale)useCookie or useState
Related values with actions and gettersPinia store
Data shared between server API and clientPinia hydrated from useFetch
Client-only caches and preferenceslocalStorage or IndexedDB via a plugin

6 · Server Routes & Nitro

6.1 The server directory6.2 Params, query and body6.3 Server middleware6.4 Calling your own API with $fetch6.5 Deploying the Nitro server

This chapter covers Nitro, Nuxt’s server engine, where files under server/ become API routes and middleware. You define handlers that read params, query strings and bodies, call the same routes from the client with $fetch, and understand the deployable output. Your API lives beside your application in one codebase and one build.

Every file under server/ runs in Nitro, a compact Node and H3 server bundled with Nuxt. Routes are files, handlers are functions, and the same engine powers dev, preview and most cloud deployments — no separate API project required.

6.1 The server directory

This section maps the server/ folder conventions. Handlers in server/api/ are served under the matching /api path, server/routes/ holds other URL trees, and server/middleware/ runs before every handler. File names translate to URLs exactly like pages do, giving a coherent endpoint map for the whole app.

PathRoutePurpose
server/api/posts/index.get.tsGET /api/postsList posts
server/api/posts/[id].get.tsGET /api/posts/:idOne post
server/api/posts/index.post.tsPOST /api/postsCreate a post
server/middleware/log.tsAll routesRuns before every request
server/utils/db.ts—Auto-imported server helpers
// server/api/posts/index.get.ts
export default defineEventHandler(() => {
  return posts                       // returning a value → JSON response
})

A file in server/api becomes an endpoint and whatever the handler returns is sent as a JSON response — no response object to build by hand.

6.2 Params, query and body

This section explains reading route params, query strings and request bodies from the event object passed to each handler. Every route file exports a default function that receives the event, from which you read the URL params, the query object, and the request body with readBody. Read every input explicitly, mirroring the handler’s path and HTTP method.

// server/api/posts/[id].get.ts
export default defineEventHandler((event) => {
  const id = getRouterParam(event, 'id')     // matches the [id] file segment
  return posts.find((p) => p.id === Number(id))
})

// server/api/posts/index.post.ts
export default defineEventHandler(async (event) => {
  const { title } = await readBody(event)    // parsed JSON body
  const page = getQuery(event).page ?? '1'   // ?page=2 → { page: '2' }
  const post = { id: posts.length + 1, title, author: 'you' }
  posts.push(post)
  return post
})

getRouterParam reads the file-defined segment, readBody parses the JSON body, and getQuery returns the query string — the three standard input channels.

6.3 Server middleware

This section shows server middleware defined in server/middleware/, which runs before every handler, for logging, authentication or early responses. Each middleware file exports a function that receives the event and shares the same event object as handlers. It may also return a response before the handler runs.

// server/middleware/logger.ts — runs for every request to any server route
export default defineEventHandler((event) => {
  console.log(`[server] ${getMethod(event)} ${getRequestURL(event)}`)
})

// server/middleware/auth.ts — short-circuit before the handler runs
export default defineEventHandler((event) => {
  const token = getHeader(event, 'authorization')
  if (!token) throw createError({ statusCode: 401, message: 'Missing token' })
})

Server middleware wraps every handler: the logger observes each request, and the second example aborts with 401 before any handler sees the event.

Do not duplicate work between route and server middleware: route middleware guards the browser UI, server middleware guards the API underneath it.

6.4 Calling your own API with $fetch

This section shows the internal fetch pattern with $fetch used in pages, components and server code alike. During SSR the $fetch request is routed to the same Nitro server without an absolute URL, avoiding an extra network round trip. The unified helper keeps client and server calls identical and typed.

<script setup lang="ts">
// pages/index.vue
const { data: posts } = await useFetch('/api/posts')   // same origin during SSR

async function create() {
  await $fetch('/api/posts', {
    method: 'POST',
    body: { title: 'New post' },   // JSON is serialized automatically
  })
}
</script>

useFetch and $fetch target relative paths that resolve against the current origin — on the server that is Nuxt’s own process, so everything stays internal.

6.5 Deploying the Nitro server

This section explains how nuxi build compiles the app and the server/ tree into one deployable Nitro server. A preset selects the target runtime, such as node-server for a Node host or any of the serverless and edge presets, and the output folder then runs on that platform. Picking the preset is the main packaging decision.

npm run build         # produces .output/ with the bundled server and assets

# .output/server/index.mjs — a single entry point you can run or serve
node .output/server/index.mjs        # works locally on Node

# or target a platform preset instead (nuxt.config.ts)
export default defineNuxtConfig({
  nitro: { preset: 'node-server' }, // or 'vercel', 'netlify', 'cloudflare-pages'
})

nuxt build bundles everything into .output/; the node-server preset runs it with plain Node, while platform presets emit the exact files a host expects.

7 · Middleware, Plugins & Composables

7.1 Named route middleware7.2 Global and anonymous middleware7.3 Plugins and the provide pattern7.4 Writing custom composables

This chapter covers the three extension points of a Nuxt app: route middleware for navigation guards, plugins for app-wide bootstrap code, and custom composables for reusable logic. You write named, global and inline middleware, register plugins either in config or by convention, and author composables in composables/ that auto-import everywhere.

7.1 Named route middleware

This section shows named route middleware stored in the middleware/ directory and activated with the definePageMeta middleware option. A guard runs before the page renders and can redirect with navigateTo or return false to abort navigation. Because it is named, the same file is reusable across many pages.

// middleware/auth.ts
export default defineNuxtRouteMiddleware((to) => {
  const user = useState('user')              // shared auth state from elsewhere
  if (!user.value) {
    // keep the attempted path so login can return the user where they were going
    return navigateTo('/login?redirect=' + to.fullPath)
  }
})

// pages/account.vue — attach the guard to a page
definePageMeta({
  middleware: 'auth',                    // string reference to middleware/auth.ts
  // middleware: ['auth', 'twoFa']       // multiple guards run in order
})

A file in middleware/ becomes a named guard a page opts into; returning navigateTo redirects the navigation instead of rendering the page.

7.2 Global and anonymous middleware

This section covers the remaining two middleware placements. A file named with the .global suffix in middleware/ runs on every navigation, while anonymous middleware can be defined inline within a page’s definePageMeta call. Both receive the to and from route arguments, and global ordering follows file name order.

<script setup lang="ts">
// inline anonymous middleware — defined and applied in the same file
definePageMeta({
  middleware: defineNuxtRouteMiddleware((to) => {
    if (!to.params.id) return navigateTo('/posts', { replace: true })
  }),
})
</script>

// middleware/analytics.global.ts — the .global suffix runs on every navigation
export default defineNuxtRouteMiddleware(() => {
  console.log('navigation started')
})

Anonymous guards are inline in the page, while a file named with the .global suffix runs on every navigation automatically — three placements, one signature.

Server middleware from chapter six runs inside Nitro before an API handler; route middleware runs in the browser (and during SSR) before a page renders. Never reach for one to do the other’s job.

7.3 Plugins and the provide pattern

This section shows plugins in the plugins/ folder that run before the app mounts, useful for bootstrapping third-party libraries or shared instances. Older code injected values with the provide pattern, while modern Nuxt prefers a composable that lazily reads the plugin’s instance. This keeps components clean and avoids polluting global scope.

// plugins/analytics.ts — runs once when the app boots
export default defineNuxtPlugin((nuxtApp) => {
  const analytics = { track(name) { console.log('track: ' + name) } }

  nuxtApp.hook('app:mounted', () => analytics.track('app:ready'))
  return { provide: { analytics } }   // exposes nuxtApp.$analytics
})

// composables/useAnalytics.ts — the recommended doorway to the value
export function useAnalytics() {
  const nuxtApp = useNuxtApp()
  return nuxtApp.$analytics
}

The plugin runs at boot, registers app hooks and exposes analytics through nuxtApp; a thin useAnalytics composable is the clean doorway components use.

7.4 Writing custom composables

This section shows writing custom composables in the composables/ folder that wrap reactive logic and reuse Nuxt hooks such as useState or useNuxtApp. Anything exported from there auto-imports across the app under the use naming convention. This keeps shared logic centralized, type-safe and trivial to reuse between pages and components.

// composables/useDebouncedSearch.ts
export function useDebouncedSearch(fetchFn) {
  const query = ref('')
  const pending = ref(false)
  const results = ref([])
  let timer                             // handle for the pending timeout

  async function search() {
    pending.value = true
    results.value = await fetchFn(query.value)
    pending.value = false
  }

  watch(query, () => {
    clearTimeout(timer)                  // debounce: wait for a pause in typing
    timer = setTimeout(search, 300)
  })

  return { query, results, pending, search }
}

// composables are auto-imported, so a page uses it with no import
const { query, results, pending } =
  useDebouncedSearch(async (q) => $fetch('/api/search?q=' + q))

The composable combines a debounced query with an injected fetcher, and pages auto-import the same reactive, SSR-safe result object Nuxt itself uses.

8 · Rendering Modes & Performance

8.1 SSR by default8.2 Static generation and prerendering8.3 SPA mode8.4 Hybrid rendering with route rules8.5 Payload extraction and image optimization

This chapter covers the rendering modes Nuxt supports: server-side rendering by default, static prerendering and fully client-side SPA mode. Route rules allow hybrid per-route mixing in one app, and performance levers such as payload extraction and the image module trim what ships. You pick a mode per app, then tune.

8.1 SSR by default

This section explains how server-side rendering works. The server renders the full HTML for each request, the client downloads it and hydrates into an interactive Vue application. Benefits include fast first paint and built-in SEO, with the trade-offs of a Node runtime and careful server-safe data fetching. Nuxt runs this mode by default.

// nuxt.config.ts
export default defineNuxtConfig({ ssr: true })   // the default — usually leave it on

// what the browser receives for a page:
// 1. the server runs the setup code, fetches data and renders full HTML
// 2. that HTML arrives immediately: SEO crawlers see real content
// 3. a copy of the data ships in the payload for step 4
// 4. the client hydrates — Vue takes over the DOM and the page goes live

SSR renders full HTML on the server and hydrates it client-side; the first paint is fast for users and readable by search engines, which is why it is the default.

8.2 Static generation and prerendering

This section shows static generation, where the site is prerendered to plain HTML at build time via the static preset or prerender route rules and the nuxi generate command. The output is static files any CDN can serve with no server process at all. Dynamic content then relies on client-side fetching or scheduled regeneration.

// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    prerender: {
      // URLs to bake into static HTML at build time
      routes: ['/', '/about', '/blog/hello-world'],
    },
  },
})

npm run generate     # crawls and prerenders → static HTML in .output/public

nuxt generate builds and prerenders the listed routes to static HTML, producing output a CDN can host with zero runtime computation per request.

8.3 SPA mode

This section shows fully client-side rendering configured with ssr: false. The server sends an empty shell and a loading template, and everything renders in the browser once the JavaScript loads. This suits app-like interfaces where SEO is less important, at the cost of a slower first meaningful paint.

// nuxt.config.ts — turn SSR off entirely
export default defineNuxtConfig({ ssr: false })

// spa-loading-template.html (app/ in Nuxt 4) — shown while the client boots
<div class="loader">Loading application</div>

With ssr:false the app becomes a classic SPA: a tiny shell with a loading screen is sent first, then the client renders everything after boot.

Use SPA mode only for authenticated tools where SEO does not matter; content sites should stay on SSR or SSG.

8.4 Hybrid rendering with route rules

This section shows hybrid rendering with routeRules in nuxt.config. One app can prerender its marketing pages, cache others with a stale-while-revalidate entry, and keep a dynamic dashboard fully live with SSR or CSR. Nitro matches each incoming request to the applicable route rule at runtime.

// nuxt.config.ts — per-route rendering policy
export default defineNuxtConfig({
  routeRules: {
    '/':         { prerender: true },   // bake once at build time
    '/blog/**':  { swr: 3600 },         // serve cached, revalidate hourly
    '/docs/**':  { isr: 3600 },         // incremental: same cache, older pages
    '/admin/**': { ssr: false },        // client-side only (requires auth)
    '/api/**':   { cors: true },        // open the API to other origins
  },
})

routeRules set a policy per URL pattern: pages are separately prerendered, cached or client-rendered, and the API gets CORS — all in one table.

8.5 Payload extraction and image optimization

This section covers the main performance levers available. Payload extraction means transferred fetch data is not duplicated, the image module serves optimized images automatically, and there are config defaults worth verifying. Most speed wins come from not shipping the same data or bytes twice. These levers apply in every rendering mode.

// nuxt.config.ts — performance defaults worth verifying
export default defineNuxtConfig({
  nitro: {
    compressPublicAssets: true,      // gzip and brotli the static files
    minify: true,                    // minify the server bundle
  },
  experimental: {
    payloadExtraction: true,         // ship only the data each page needs
  },
})

// images: swap <img> for NuxtImg (from the @nuxt/image module)
<template>
  <NuxtImg
    src="/img/hero.jpg"
    width="1200"
    height="630"
    loading="lazy"        <!-- defer off-screen images -->
    format="webp"         <!-- served as webp where supported -->
  />
</template>

Payload extraction trims what ships to the browser, compression shrinks the static output, and the Nuxt image component handles resizing, format and laziness for you.

9 · Forms, Errors & Auth Patterns

9.1 Form handling with v-model9.2 Validation9.3 Custom error pages and createError9.4 Cookies and session basics9.5 The auth middleware pattern

This chapter covers form handling with v-model and $fetch, lightweight validation, custom error pages and cookies, plus the classic auth guard pattern. The pieces compose into login, signup and protected-route flows built on the middleware from earlier chapters. By the end you can build real multi-page user workflows end to end.

9.1 Form handling with v-model

This section shows a controlled form wired to reactive state with v-model and submitted with $fetch to a server route. Nuxt adds nothing special here, so the standard Vue patterns carry over directly, with field values read from the reactive object. Server validation errors come back as the response and update the form state.

<script setup lang="ts">
const form = reactive({ title: '', body: '' })
const submitting = ref(false)

async function submit() {
  submitting.value = true
  try {
    await $fetch('/api/posts', { method: 'POST', body: form })  // JSON from state
    await navigateTo('/posts')                                   // success → list page
  } finally {
    submitting.value = false
  }
}
</script>

<template>
  <form @submit.prevent="submit">
    <input v-model="form.title" placeholder="Title" />
    <textarea v-model="form.body" placeholder="Body" />
    <button :disabled="submitting">{{ submitting ? 'Saving' : 'Save' }}</button>
  </form>
</template>

The form binds inputs to a reactive object, submits it as JSON with $fetch, and only navigates after a successful POST — the finally block resets state either way.

9.2 Validation

This section shows a lightweight validation approach that avoids extra libraries. Each field carries an error ref computed from the value or the server response, updated on submit or change, and the messages can be swapped for any validation library later. The pattern keeps forms visibly aligned with the data they guard.

const errors = ref({})

function validate() {
  errors.value = {}
  if (!form.title) errors.value.title = 'Title is required'
  if (form.body.length < 10) errors.value.body = 'Body needs at least 10 characters'
  return Object.keys(errors.value).length === 0
}

async function submit() {
  if (!validate()) return           // stop before any request is sent
  await $fetch('/api/posts', { method: 'POST', body: form })
}

// in the template, print one message per failed field
// <p v-if="errors.title" class="error">{{ errors.title }}</p>

validate() fills a reactive errors object and returns success, letting the submit handler bail early while the template shows one message per field.

9.3 Custom error pages and createError

This section shows Nuxt’s error.vue page, which renders when an error reaches the root, and how code throws one with createError from pages, plugins or server handlers. The error page receives statusCode and statusMessage as props and can dismiss the state with clearError. A custom page turns a crash into a designed experience.

<!-- error.vue — rendered for any unhandled error or failed request -->
<script setup lang="ts">
const props = defineProps({ error: Object })   // { statusCode, statusMessage, ... }
function retry() { clearError({ redirect: '/' }) }   // go home and reset the error
</script>

<template>
  <div>
    <h1>{{ props.error.statusCode }}</h1>
    <p>{{ props.error.statusMessage }}</p>
    <button @click="retry">Back home</button>
  </div>
</template>

// anywhere in a page or server handler:
throw createError({ statusCode: 404, statusMessage: 'Post not found' })

error.vue receives the error as a prop, createError constructs a consistent error from anywhere, and clearError resets the app so a retry walks back home.

9.4 Cookies and session basics

This section shows reading and writing cookies on both server and client with the useCookie composable, plus reading request headers from the event during SSR. Setting the returned ref also updates the cookie automatically in the browser. This is the foundation of stateless auth tokens, since cookies travel with every request.

<script setup lang="ts">
// a cookie shared between server and client — ideal for tokens and prefs
const token = useCookie('token', { maxAge: 60 * 60 * 24 * 7, sameSite: 'lax' })
token.value = 'abc123'       // setting it updates the cookie sent to the browser

// server side: pass browser headers (cookies, user-agent) to an upstream fetch
const headers = useRequestHeaders(['cookie', 'user-agent'])
const { data } = await useFetch('/api/me', { headers })
</script>

useCookie keeps one value in sync between server and client, and useRequestHeaders forwards the browser’s own cookies, keeping server-side calls authenticated.

9.5 The auth middleware pattern

This section assembles cookies, a login handler and route guards into the classic auth flow. The login handler validates credentials and sets a token cookie, the auth middleware reads it and redirects unauthenticated users, and logout clears the cookie. Sessions stay stateless because the token can be validated on each protected request.

// server/api/login.post.ts — verify credentials, hand out a token
export default defineEventHandler(async (event) => {
  const { email, password } = await readBody(event)
  if (email !== 'ada@example.com' || password !== 'secret') {
    throw createError({ statusCode: 401, statusMessage: 'Bad credentials' })
  }
  return { token: 'signed-token-123' }   // in reality: sign a JWT or session id
})

// composables/useAuth.ts — one doorway for login, state and logout
export const useAuth = () => {
  const token = useCookie('token')
  const user = useState('user')

  async function login(email, password) {
    const res = await $fetch('/api/login', { method: 'POST', body: { email, password } })
    token.value = res.token              // cookie set → future requests carry it
    user.value = { email }               // store the identity for guards
  }
  function logout() { token.value = null; user.value = null }
  return { user: readonly(user), login, logout }
}

// middleware/auth.ts — guard protected pages
export default defineNuxtRouteMiddleware(() => {
  const { user } = useAuth()
  if (!user.value) return navigateTo('/login')
})

The login handler returns a token, useAuth stores it in a cookie and exposes login/logout, and the route middleware redirects guests — a complete pattern to extend with a real signing library.

10.3 runtimeConfig and environment

This section shows how runtimeConfig in nuxt.config exposes environment-specific values and secrets, read at runtime through useRuntimeConfig instead of being baked into the build. Public settings live under the public key, private ones stay server-only, and both are read from environment variables at launch. Config changes no longer require a rebuild.

// nuxt.config.ts
export default defineNuxtConfig({
  runtimeConfig: {
    public: {
      siteUrl: process.env.NUXT_PUBLIC_SITE_URL || 'https://example.com',  // client-visible
    },
    apiSecret: process.env.NUXT_API_SECRET,   // server-only, never shipped
  },
})

// server code reads the secret via useRuntimeConfig
const config = useRuntimeConfig()
await $fetch('https://api.example.com', {
  headers: { 'x-key': config.apiSecret },    // only ever used on the server
})

// components read only the public block
const { siteUrl } = useRuntimeConfig().public

runtimeConfig splits client-visible values from server-only secrets, and NUXT_ environment variables override them at runtime without a rebuild.

10.5 Project conventions worth keeping

This section collects the practical conventions that keep Nuxt projects tidy as they grow: keep routes and components close to their usage, prefer small composables, reuse layouts, and keep business logic out of page components. These rules of thumb apply to every app. Following them makes larger codebases readable for the whole team.

  • Let conventions do the wiring — prefer pages/, components/ and composables/ over manual registration.
  • Fetch data with useFetch or useAsyncData, never raw fetch in setup, so SSR and caching keep working.
  • Keep the server API small and single-purpose — each file in server/api answers one question.
  • Type everything with TypeScript; nuxt typegen keeps globals in sync.
  • Pin Node versions and run npm audit before shipping; keep Nuxt updated.
  • Use routeRules over per-page hacks for caching and rendering policy.

This section lists the composables you reach for daily: useState, useFetch, useAsyncData, useRoute, useHead, useSeoMeta, useCookie and useRuntimeConfig, with what each returns or does. It is a quick lookup of signatures and typical return shapes. Keep it open while you build.

ComposableDoes

$fetchRaw HTTP client on server and client

useHead / useSeoMetaPer-page head and SEO tags
useNuxtAppThe app instance: payload, hooks, provides

useRuntimeConfigRuntime configuration and env values

A.2 File-based conventions

This section lists the folders Nuxt wires up by name: pages, components, layouts, composables, utils, middleware, plugins, server and public. Drop a file in the right place and the matching routing, import or runtime behavior starts working. This is the naming key to the whole framework.

FolderConvention
pages/Each file is a route; [param] and [...] capture segments
components/Tag names resolve from file names; folders add prefixes
layouts/default.vue plus per-page choices via definePageMeta
composables/ / utils/Auto-imported functions under use- and $ prefixes
server/api/Handlers; file name and method suffix define the endpoint
middleware/Route guards; the .global suffix runs on every navigation
plugins/Run once at app boot
stores/Pinia stores (with the @pinia/nuxt module)

A.4 Glossary

This section defines the terms used across the guide in one pass, from SSR, SSG and hydration to Nitro, route rules and presets. Skimming it before returning to any chapter anchors the vocabulary the chapters assume. Short definitions keep a line-by-line lookup fast and painless.

  • Nuxi — the Nuxt CLI: scaffolding, dev, build, generate, preview.
  • Nitro — the server engine behind Nuxt: API routes, middleware, presets, deployments.
  • SSR — server-side rendering: HTML rendered on the server before hydration.
  • Hydration — the client attaching Vue reactivity to server-rendered HTML.
  • Prerender / SSG — baking routes to static HTML at build time.
  • Payload — the serialized data shipped from server to client for hydration.
  • Route rules — per-URL-pattern rendering and caching configuration.
  • Auto-imports — resolving functions and components by naming convention with no import lines.
  • Composable — a function using Vue reactivity; Nuxt auto-imports those in composables/ and utils/.
  • Middleware — route middleware guards navigation; server middleware guards API requests.
