Understanding how the pieces fit together is essential before writing code. The .NET 10 stack provides a unified platform for all application types.

1.1 Records and immutability

Records provide value-based semantics for data transfer objects, domain models, and immutable configurations. They are the backbone of clean architecture in .NET.

Value equality, not reference equality

A record gets a compiler-generated implementation of Equals, GetHashCode and == that compares the values of every property rather than object identity. Two separately constructed instances holding the same data are therefore equal — exactly the semantics a DTO crossing a service boundary needs, because caller and callee never share the same instance. The compiler also generates IEquatable<T>, so dictionary and HashSet lookups avoid boxing.

public record Product(int Id, string Name, decimal Price);

// Records have value equality
var p1 = new Product(1, "Laptop", 999.99m);
var p2 = new Product(1, "Laptop", 999.99m);
Console.WriteLine(p1 == p2); // True — value equality
Console.WriteLine(ReferenceEquals(p1, p2)); // False — distinct instances

Non-destructive mutation with with

Because record properties are init-only by default, you cannot mutate an instance after construction. Change is expressed as a new value instead: the with expression clones the instance, applies the listed property values and returns a fresh record. The original object is untouched — a property that makes records safe to share across threads and caches without defensive copies. The sequence below also shows how the source of a record value is preserved while its state evolves.

// with-expressions for non-destructive mutation
var discounted = p1 with { Price = 899.99m };
Console.WriteLine(discounted.Price); // 899.99
Console.WriteLine(p1.Price);        // 999.99 — original unchanged

// with works on record structs too — no heap allocation
public record struct Money(decimal Amount, string Currency);
var total = new Money(12.50m, "GBP");
var refunded = total with { Amount = 0m };

Positional parameters and Deconstruct

A positional record — record Product(int Id, ...) — declares the public properties and a Deconstruct method in one line, so tuples and records interop cleanly. The generated members use init accessors by default. Records also participate in inheritance: a derived record rewrites value equality to include its own members, and positional constructors chain naturally.

// Positional records auto-generate Deconstruct
var (id, name, price) = discounted;

// Inheritance chains positional constructors and equality
public record Product(int Id, string Name, decimal Price);
public record DigitalProduct(int Id, string Name, decimal Price, string DownloadUrl)
    : Product(Id, Name, Price);

Use records for DTOs, domain events, and configuration objects. They eliminate an entire class of bugs related to mutable shared state.

1.2 Pattern matching

C# pattern matching has evolved into a powerful tool for business logic, replacing complex if-else chains with expressive, compiler-checked code.

Switch expressions read like a table

A switch expression turns a ladder of if/else if checks into a single expression whose arms are evaluated in order. The compiler checks two things the old statements never could: if the arms are exhaustive over the input type — the _ discard arm otherwise acts as a fallback — and whether the pattern itself is reachable. Property patterns let you test nested fields in the same arm, so a discount rule that depends on both the tier and the tenure is one readable line instead of three nested conditions.

public decimal CalculateDiscount(Customer customer, Product product) => customer switch
{
    { Tier: CustomerTier.Premium, YearsActive: > 5 } => product.Price * 0.20m,
    { Tier: CustomerTier.Premium }                    => product.Price * 0.15m,
    { Tier: CustomerTier.Standard, YearsActive: > 2 } => product.Price * 0.10m,
    { Tier: CustomerTier.Standard }                    => product.Price * 0.05m,
    _                                                  => 0m
};

Enum and tuple patterns extend the same idea to value combinations — a category of rule that used to produce deeply nested switch statements:

// Tuple pattern: (status, isPriority) combined in one arm
var nextAction = (order.Status, order.IsPriority) switch
{
    (OrderStatus.Paid, true)  => "Dispatch immediately",
    (OrderStatus.Paid, false) => "Dispatch in next batch",
    (OrderStatus.Draft, _)    => "Awaiting submission",
    _                         => "Review required"
};

Property patterns and logical operators

In an is expression, a property pattern { Total: > 1000m, Items.Count: > 5 } is a single test object — no && chains reaching into private fields. Logical operators and, or and not combine patterns, and the relational pattern > handles ranges. The same syntax composes in guards and filters, so the rule set stays centralised rather than scattered across call sites.

// Property patterns with logical operators
if (order is { Total: > 1000m, Items.Count: > 5, Status: OrderStatus.Pending })
{
    order.ApplyBulkDiscount();
}

// `not` and `or` combine freely
if (payment is not { Status: PaymentStatus.Refunded })
{
    await paymentGateway.CaptureAsync(payment);
}

List patterns for sequences

List patterns (C# 11+, extended in C# 12) match a sequence's shape: exact length, a prefix, a slice, or element-wise tests with the .. rest pattern. They replace index-juggling loops when the concern is really "does this start with X", "does this end with Y", or "is every element positive". The slice pattern has a severe edge: it captures a starting position of zero even against a source with no elements — a subtle behaviour worth remembering when a list-pattern guard is used in a hot path.

// List patterns (C# 11+)
int[] numbers = { 1, 2, 3, 4, 5 };
if (numbers is [> 0, > 0, ..])
{
    Console.WriteLine("All positive");
}

// Match first, last and middle independently
if (numbers is [1, .. var rest, 5])
{
    Console.WriteLine($"Middle: {string.Join(", ", rest)}");
}

// Guard an empty sequence explicitly
if (numbers is [] or [0, ..])
{
    Console.WriteLine("Empty or starts with zero");
}

A switch arm that falls through silently is the classic bug here. Keep the _ arm — if the domain later grows a new enum member, the discard is where the missing case becomes visible instead of a null-swallowing default at a call site.

1.3 Nullable reference types

Nullable reference types eliminate null reference exceptions at compile time. Every enterprise project should enable this feature.

Annotations and the compiler's flow analysis

With Nullable enabled, a ? on a reference type means "may be null" and its absence means "assumed non-null". The compiler then tracks the definite-null state of every expression through branches, assignments and calls: dereferencing a possibly-null value produces a warning, and returning a possibly-null value from a method declared non-nullable produces one too. The annotations below declare the contract first; the warning stream then polices it.

<!-- In .csproj -->
<PropertyGroup>
  <Nullable>enable</Nullable>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>

// Code with nullable annotations
public class OrderService
{
    // Non-nullable — must be initialised
    private readonly IOrderRepository _repository;

    // Nullable — may return null
    public Order? FindById(int id) => _repository.FindById(id);

    // Null-forgiving operator — use sparingly
    public Order GetById(int id) => _repository.FindById(id)!;

    // Null-coalescing assignment
    public Customer GetOrCreateCustomer(string email)
    {
        var customer = _repository.FindByEmail(email);
        customer ??= _repository.Create(new Customer(email));
        return customer;
    }
}

Contract attributes refine the analysis

The flow analysis only sees what the signatures tell it. Contract attributes patch the blind spots: [NotNullWhen(true)] teaches the compiler that a successful parse means the out-argument is non-null, [MemberNotNull] declares that a method is guaranteed to initialise a field, and [MaybeNull] weakens a generic that legitimately returns null. With these in place, the ! operator almost disappears from the codebase.

public static class Parsers
{
    // Compiler now knows: when TryParse returns true, value is non-null
    public static bool TryParseId(string input, [NotNullWhen(true)] out int? id)
    {
        return int.TryParse(input, out var parsed) ? (id = parsed) is not null
                                                   : (id = null) is null;
    }
}

// Call site stays clean — no lingering null checks or bangs
if (!Parsers.TryParseId(rawInput, out var id)) return BadRequest("Invalid id");
var order = await _repository.GetByIdAsync(id.Value, ct);

[MemberNotNull(nameof(_connection))]
private void EnsureConnected()
{
    _connection ??= OpenConnection();
    // after this call the compiler treats _connection as non-null
}

Warnings before errors

Flipping a long-lived codebase to enable in one commit produces hundreds of warnings. The designed path is <Nullable>warnings</Nullable> first — analysis on, annotations optional — so you can adopt the ? annotations file by file without a global suppression. The #nullable enable directive switches a single file, which is how you migrate the core of a library first and let the warnings drive the rest.

<!-- Start here on an existing project -->
<PropertyGroup>
  <Nullable>warnings</Nullable>
</PropertyGroup>

// Warnings now appear; annotations are added one file at a time
#nullable enable
public sealed class OrderLine
{
    public required string Sku { get; init; }
    public int Quantity { get; init; }
}
#nullable restore

Enabling nullable reference types in an existing codebase will produce many warnings. Address them incrementally file by file rather than suppressing globally.

1.4 Async / await deep dive

Async is not just about performance — it is about writing correct, scalable I/O-bound code. Understanding the internals prevents deadlocks and thread-pool starvation.

Cancellation is a contract, not an afterthought

Every async method that performs I/O should accept a CancellationToken and pass it down the call chain. The token is how a timeout, a user abort or a shutdown can stop a request mid-flight without leaking the operation to keep running against a dead client. The pattern below combines the caller's token with a hard 30-second deadline by linking two sources: whichever fires first cancels the linked token, so the payment call can never run longer than the timeout regardless of what the client does.

public class OrderProcessingService
{
    private readonly IOrderRepository _repository;
    private readonly IPaymentGateway _payment;
    private readonly ILogger<OrderProcessingService> _logger;

    public async Task<OrderResult> ProcessOrderAsync(Order order, CancellationToken ct = default)
    {
        order.Validate();
        await _repository.AddAsync(order, ct);

        using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
        using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(ct, timeoutCts.Token);

        var payment = await _payment.ChargeAsync(order.Total, linkedCts.Token);

        if (payment.Success)
        {
            order.Complete();
            await _repository.UpdateAsync(order, ct);
            return OrderResult.Success(order.Id);
        }

        order.Fail(payment.ErrorMessage);
        await _repository.UpdateAsync(order, ct);
        return OrderResult.Failure(payment.ErrorMessage);
    }
}
// Throw when either source fires — the observable effect is explicit
try
{
    var payment = await _payment.ChargeAsync(order.Total, linkedCts.Token);
}
catch (OperationCanceledException) when (timeoutCts.IsCancellationRequested)
{
    _logger.LogWarning("Payment timed out for order {OrderId}", order.Id);
    return OrderResult.Failure("Payment gateway timed out");
}

Synchronisation context and sync-over-async

An await resumes on the captured context by default. In a console app or a background service there is no SynchronizationContext, so the resume happens on whatever thread completes the task — which is exactly what you want. In UI or ASP.NET contexts, ConfigureAwait(false) escapes the context capture for continuation work that never touches UI state. The class of bugs to avoid is sync-over-async: calling .Result or .Wait() on a task blocks the current thread while the async chain waits for that thread's context to resume — a guaranteed deadlock on a single-threaded context and a thread-pool stall anywhere else.

// Library code: continuation does not need the captured context
public async Task<decimal> GetOrderTotalAsync(int orderId, CancellationToken ct)
{
    var order = await _repository.GetByIdAsync(orderId, ct).ConfigureAwait(false);
    return order.Items.Sum(i => i.Quantity * i.UnitPrice);
}

// Anti-pattern — blocks a thread AND risks deadlock on a UI context
var total = GetOrderTotalAsync(orderId, ct).Result;      // never do this

ValueTask and batching

ValueTask<T> avoids a heap allocation when the async method completes synchronously — the common case for a cache hit. Because it wraps a value or a task rather than always allocating a Task, it must be awaited once and never stored or awaited twice; libraries that return it on public API surfaces should document that constraint. For fan-out work, Task.WhenAll runs independent calls concurrently instead of serially awaiting each one.

// ValueTask for hot paths that complete synchronously
public async ValueTask<Order?> FindCachedAsync(int id)
{
    if (_cache.TryGetValue(id, out var order))
        return order;

    order = await _repository.FindByIdAsync(id);
    _cache[id] = order;
    return order;
}

// Fan out independent I/O — one round of waits, not N
var orderTasks = ids.Select(id => _repository.GetByIdAsync(id, ct));
var orders = await Task.WhenAll(orderTasks);

Always flow CancellationToken through async call chains. It is the only way to implement proper timeout and cancellation behaviour in enterprise systems.

1.5 LINQ for enterprise data

LINQ is the primary data manipulation tool in C#. Understanding deferred execution, projection, and aggregation is essential for writing efficient data access code.

Deferred execution and when it bites

Most LINQ operators — Where, Select, OrderBy, Take — are deferred: they build a query description and execute nothing until the result is enumerated. The consequence is that the source collection is re-read on every enumeration, and with EF Core the SQL is generated and sent only when a terminal operator (ToListAsync, FirstOrDefaultAsync, CountAsync, SingleAsync) is awaited. Using the same IQueryable twice can therefore execute the database query twice — a classic source of duplicated work that profiling logs expose immediately.

// Deferred execution — query is not executed until enumerated
var query = _context.Orders
    .Where(o => o.Status == OrderStatus.Pending)
    .OrderByDescending(o => o.CreatedAt)
    .Take(100);

// Forces execution — use ToListAsync for EF Core
var results = await query.ToListAsync();
var count = await query.CountAsync();  // executes AGAIN — materialise once

// Guard with Any() rather than Count() > 0 — cheaper, clearer intent
if (await _context.Orders.AnyAsync(o => o.CustomerId == customerId))
{
    // ...
}

Projection narrows what the database returns

A Select that targets a DTO is the single biggest LINQ performance lever: the SQL selects only the mapped columns and EF Core never materialises entities it does not need. Projection also lets you compute totals and counts server-side, keeping the client free of calculated fields that could drift out of sync with the source data.

// Projection — select only needed fields
var dtos = await _context.Orders
    .Where(o => o.CreatedAt > DateTime.UtcNow.AddDays(-30))
    .Select(o => new OrderDto
    {
        Id = o.Id,
        CustomerName = o.Customer.Name,
        Total = o.Items.Sum(i => i.Quantity * i.UnitPrice),
        ItemCount = o.Items.Count
    })
    .ToListAsync();

// SelectMany flattens one-to-many — every order item with its order's id
var orderItemRows = await _context.Orders
    .Where(o => o.Status == OrderStatus.Shipped)
    .SelectMany(o => o.Items, (order, item) => new
    {
        order.Id,
        item.ProductId,
        item.Quantity
    })
    .ToListAsync();

Grouping and aggregation in the database

GroupBy translates to SQL GROUP BY, so aggregation happens on the server rather than in memory. The shape after grouping is a sequence of IGroupings: g.Key is the grouped value and the aggregate operators run per group. Note that the OrderCount below counts distinct order ids inside each group — a naive Count() would count order items instead.

// Grouping and aggregation
var salesByCategory = await _context.OrderItems
    .GroupBy(oi => oi.Product.Category)
    .Select(g => new
    {
        Category = g.Key,
        TotalRevenue = g.Sum(oi => oi.Quantity * oi.UnitPrice),
        OrderCount = g.Select(oi => oi.OrderId).Distinct().Count()
    })
    .ToListAsync();

// Chunk splits a lazy sequence into fixed-size batches for bulk writes
foreach (var batch in allOrderIds.Chunk(500))
{
    await _repository.UpdateStatusesAsync(batch, OrderStatus.Paid, ct);
}

1.6 Generics and constraints

Generics enable type-safe, reusable components. Enterprise applications rely heavily on generic repositories, services, and middleware.

Constraints make the contract explicit

A constraint is a compile-time promise about T that unlocks members which would otherwise be unavailable. where T : Entity lets a repository touch entity.Id; where T : class permits T?; where T : notnull bans nullable type arguments entirely; and where T : new() allows new T(). Constraints are part of the public API — tighten one and every caller must comply, so design them around the operations genuinely shared by all T.

// Restrict a handler to entity types that expose an identity
public interface IEntity { int Id { get; } }

public sealed class Repository<T> where T : class, IEntity, new()
{
    private readonly Dictionary<int, T> _store = new();

    public T Create() => new T();                       // new() constraint

    public T? Find(int id)
        => _store.TryGetValue(id, out var entity) ? entity : null;
}

// where T : notnull rejects nullable annotations outright
public static T Coalesce<T>(T? value, T fallback) where T : notnull
    => value ?? fallback;

One repository, every aggregate root

Because the repository is generic, a single implementation serves every entity: the closed type is chosen at registration time and the DbSet<T> is resolved through context.Set<T>(). The open-generic registration means IRepository<Order>, IRepository<Customer> and every other closure resolve without per-type wiring. The trade-off to guard: a catch-all generic repository exposes every CRUD operation to every consumer, so it pairs naturally with aggregate-specific services that narrow the surface.

public interface IRepository<T> where T : Entity
{
    Task<T?> GetByIdAsync(int id, CancellationToken ct = default);
    Task<IReadOnlyList<T>> ListAsync(CancellationToken ct = default);
    Task<T> AddAsync(T entity, CancellationToken ct = default);
    Task UpdateAsync(T entity, CancellationToken ct = default);
    Task DeleteAsync(int id, CancellationToken ct = default);
}

public class Repository<T> : IRepository<T> where T : Entity
{
    protected readonly AppDbContext _context;
    protected readonly DbSet<T> _dbSet;

    public Repository(AppDbContext context)
    {
        _context = context;
        _dbSet = context.Set<T>();
    }

    public async Task<T?> GetByIdAsync(int id, CancellationToken ct = default)
        => await _dbSet.FindAsync(new object[] { id }, ct);

    public async Task<IReadOnlyList<T>> ListAsync(CancellationToken ct = default)
        => await _dbSet.ToListAsync(ct);

    public async Task<T> AddAsync(T entity, CancellationToken ct = default)
    {
        await _dbSet.AddAsync(entity, ct);
        await _context.SaveChangesAsync(ct);
        return entity;
    }
}
// Open-generic registration — every closed type resolves from this one line
builder.Services.AddScoped(typeof(IRepository<>), typeof(Repository<>));

public class OrderService(IRepository<Order> orders)
{
    public async Task ArchiveAsync(int id, CancellationToken ct)
        => await orders.DeleteAsync(id, ct);
}

Generic math with INumber<T>

Generic math (C# 11+) lets an algorithm operate over any numeric type. Constraining T to INumber<T> gives the operators — +, -, comparisons — a static surface resolved per closed type, so one implementation serves decimal, double and int without overloading every arithmetic operation. It is the cleanest answer to "we need this calculation for both money and quantities".

public static class Totals
{
    public static T GrandTotal<T>(IEnumerable<T> amounts) where T : INumber<T>
        => amounts.Aggregate(T.Zero, (acc, next) => acc + next);
}

decimal revenue = Totals.GrandTotal(new[] { 12.5m, 7.25m, 99m });
double  score   = Totals.GrandTotal(new[] { 1.0, 2.5, 4.0 });
int     units   = Totals.GrandTotal(new[] { 3, 5, 7 });

ASP.NET Core is built on a composable middleware pipeline with first-class dependency injection. Understanding these fundamentals is critical for building maintainable enterprise applications.

2.1 Startup and hosting

The Program.cs file is the entry point. With .NET 10, the minimal hosting model is the recommended approach for new projects.

The minimal hosting model

Since .NET 6 the whole application is expressed in one Program.cs: WebApplication.CreateBuilder(args) builds a WebApplicationBuilder that carries configuration, logging and the service collection; builder.Build() constructs the app with its middleware pipeline; app.Run() starts Kestrel and blocks until shutdown. The builder is a staging area — everything registered on builder.Services becomes the container, and configuration read via builder.Configuration is already layered from providers before your first line of service code runs.

var builder = WebApplication.CreateBuilder(args);

// Register services
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<IOrderRepository, OrderRepository>();

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = builder.Configuration["Auth:Authority"];
        options.Audience = builder.Configuration["Auth:Audience"];
    });

var app = builder.Build();

// Configure middleware pipeline
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();

Service registration happens before Build

Everything on builder.Services is fixed at Build() time. Extensions such as AddDbContext, AddAuthentication and AddScoped are all just methods that append to the collection, so composition is fully additive and testable — an integration test can swap a service by replacing the registration before the container is built. Background workers register the same way with AddHostedService, and the Kestrel endpoint can be overridden at launch or in configuration, keeping the same code path for local dev and production.

// A hosted service starts with the app and lives for its lifetime
builder.Services.AddHostedService<OutboxProcessor>();

public class OutboxProcessor : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await ProcessPendingOutboxAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}

// Override the listening port without touching code:
// ASPNETCORE_URLS=http://0.0.0.0:8080 dotnet run

What happens after Run()

app.Run() blocks the main thread for the lifetime of the process and responds to SIGTERM/Ctrl+C by triggering graceful shutdown: IHostApplicationLifetime fires ApplicationStopping, hosted services receive their CancellationToken, and in-flight requests get a bounded window to complete. In tests and serverless wrappers use await app.StartAsync() instead, which returns once the server is listening and is the method WebApplicationFactory relies on behind the scenes.

// Long-running server: block the main thread
app.Run();

// Hostable / testable: start and keep a handle
await app.StartAsync(ct);
Console.WriteLine("Listening on " + app.Urls.FirstOrDefault());
await app.WaitForShutdownAsync(ct);

2.2 Middleware pipeline

Middleware components form a pipeline that handles each HTTP request. Order matters — each component can short-circuit or pass to the next.

Pipeline order is the security budget

Each registered component is a Russian-doll around the next: a request enters the first middleware, work runs before it calls await _next(context), the pipeline unwinds, and the same component's code after _next runs on the way out. Order therefore decides whether a request is authenticated before it reaches your endpoint, whether static files are served before the auth check, and whether an exception thrown deep in the pipeline can still be turned into a clean response. The canonical order is exception handling first, HTTPS redirection, static files, routing, authentication, then authorization, then endpoints.

var app = builder.Build();

app.UseExceptionHandler("/error");   // outermost: catches everything below
app.UseHttpsRedirection();
app.UseStaticFiles();                // before auth — public assets
app.UseRouting();
app.UseAuthentication();             // establishes identity
app.UseAuthorization();              // enforces policy
app.MapControllers();                // terminal: matches endpoints

Custom middleware as a class

A middleware class receives the RequestDelegate in its constructor — that is the "next" component — and HttpContext per request in InvokeAsync. Anything constructed in the class is shared across requests, so per-request state must be resolved inside InvokeAsync (often via constructor-injected scoped services, which the DI container resolves per request during the call). The timing middleware below logs before and after _next, which is the canonical shape for metrics.

public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        _logger.LogInformation("→ {Method} {Path}", context.Request.Method, context.Request.Path);

        await _next(context);

        sw.Stop();
        _logger.LogInformation("← {StatusCode} {Method} {Path} in {ElapsedMs}ms",
            context.Response.StatusCode, context.Request.Method, context.Request.Path, sw.ElapsedMilliseconds);
    }
}

// Extension method for clean registration
public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder app)
        => app.UseMiddleware<RequestTimingMiddleware>();
}

Inline middleware and short-circuiting

For one-off concerns, app.Use(async (context, next) => ...) avoids a class; app.Run(...) declares a terminal component that never calls next. UseWhen branches conditionally — the branch runs only for matching requests — and returning without calling next anywhere is how you short-circuit, which is what a maintenance-mode flag or a 413 body-size guard relies on.

// Inline maintenance flag — short-circuits before the endpoint layer
app.Use(async (context, next) =>
{
    if (builder.Configuration["MaintenanceMode"] == "true" &&
        context.Request.Path.Value?.StartsWith("/api") == true)
    {
        context.Response.StatusCode = StatusCodes.Status503ServiceUnavailable;
        await context.Response.WriteAsJsonAsync(new { message = "Down for maintenance" });
        return; // do NOT call next — the pipeline ends here
    }

    await next();
});

// UseWhen: branch only for a path prefix, then rejoin the pipeline
app.UseWhen(
    ctx => ctx.Request.Path.StartsWithSegments("/health"),
    branch => branch.UseHealthChecks());

Middleware order is critical: ExceptionHandler → HttpsRedirection → StaticFiles → Routing → Authentication → Authorization → Endpoints. Getting this wrong causes subtle security and routing bugs.

2.3 Dependency injection

ASP.NET Core has a built-in DI container. Understanding service lifetimes is essential for avoiding captive dependencies and memory leaks.

Three lifetimes, three ownership rules

Transient services are constructed per resolution — the cheapest to reason about, the most expensive to allocate. Scoped services live one instance per HTTP request scope, which is why DbContext and per-request unit-of-work services are scoped. Singleton services are created once and shared for the process lifetime, which is where IMemoryCache, HttpClient factories and configuration wrappers belong. A singleton is also the only instance the container disposes at shutdown; transient and scoped instances are disposed when their scope ends — so a service holding an open database connection must not be transient, or connections leak per resolution.

// Service lifetimes
builder.Services.AddTransient<IEmailService, EmailService>();   // New instance every time
builder.Services.AddScoped<IOrderService, OrderService>();       // One per HTTP request
builder.Services.AddSingleton<ICacheService, CacheService>();    // One for app lifetime

// Factory registration: full control over construction and its dependencies
builder.Services.AddScoped<IOrderRepository>(sp =>
{
    var context = sp.GetRequiredService<AppDbContext>();
    var logger = sp.GetRequiredService<ILogger<OrderRepository>>();
    return new OrderRepository(context, logger);
});

Rule of thumb: ask "may this service hold state per request?" If yes, it is scoped; if no, and construction is cheap, transient; if process-wide and thread-safe, singleton.

Keyed services pick an implementation at the call site

Keyed services register several implementations of one abstraction under string keys, and the consumer selects one with [FromKeyedServices] or GetRequiredKeyedService. This is the idiomatic replacement for the old "named instance" containers: the key travels in the registration, the resolution point, and the DI metadata, so the container can validate at startup that every requested key exists.

// Keyed services (.NET 8+)
builder.Services.AddKeyedSingleton<INotificationService, EmailNotificationService>("email");
builder.Services.AddKeyedSingleton<INotificationService, SmsNotificationService>("sms");

// Controller picks the transport per request
[ApiController]
public class NotificationsController(
    [FromKeyedServices("email")] INotificationService email,
    [FromKeyedServices("sms")] INotificationService sms) : ControllerBase
{
    [HttpPost("broadcast")]
    public async Task Broadcast(MessageDto message, CancellationToken ct)
    {
        await email.SendAsync(message, ct);
        await sms.SendAsync(message, ct);
    }
}

The captive dependency trap

Injecting a scoped service into a singleton creates a captive dependency: the singleton resolves its scoped dependency once, at construction, and then holds that instance for the process lifetime — so every later request through the singleton reuses the first request's DbContext and its change tracker, which corrupts data under load. The container cannot detect the mistake at registration time in the general case; it only surfaces in testing or production. The escape hatch is IServiceScopeFactory: create a scope per unit of work, resolve the scoped service inside it, and dispose the scope to release the context.

// Common anti-pattern: captive dependency
// WRONG: Singleton depending on Scoped
builder.Services.AddSingleton<BadService>(); // Depends on IOrderService (scoped) — will cause bugs

// CORRECT: Use IServiceScopeFactory
public class GoodService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public GoodService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task DoWorkAsync()
    {
        using var scope = _scopeFactory.CreateScope();
        var orderService = scope.ServiceProvider.GetRequiredService<IOrderService>();
        await orderService.ProcessPendingOrdersAsync();
    }
}

Never inject Scoped services into Singleton services. This is the most common DI mistake in enterprise applications and causes data corruption under load.

2.4 Configuration

ASP.NET Core uses a layered configuration system with multiple providers. Enterprise apps need strongly-typed configuration with validation.

Providers layer, later wins

Configuration is a dictionary built by stacking providers in order: appsettings.json, then appsettings.{Environment}.json, then environment variables, then command-line arguments. When a key exists in two providers the last one added wins, which is how the same code base gets per-environment values without branching. Hierarchy is expressed with : in JSON keys and __ (double underscore) in environment variables — an unavoidable asymmetry between the providers that ships every clever DevOps script.

{
  "Database": {
    "ConnectionString": "Server=localhost,1433;Database=ShopDb;User Id=sa;Password=DevOnly;",
    "CommandTimeout": 30,
    "EnableRetryOnFailure": true
  }
}
// Same key, two providers — the environment variable overrides the file
// Database__ConnectionString=Server=prod;...   (env var, wins)
// dotnet run --Database:ConnectionString "Server=temp;..."  (CLI, wins again)

// The minimal hosting model already wires JSON + env + CLI for you:
var cs = builder.Configuration.GetConnectionString("Default");
var timeout = builder.Configuration.GetValue<int>("Database:CommandTimeout");

The Options pattern and its three faces

Options bind a configuration section to a strongly typed class, so callers read options.Value.ConnectionString instead of string-key lookups scattered through the codebase. The three consumer interfaces differ in freshness: IOptions<T> is a singleton snapshot fixed at first resolution; IOptionsSnapshot<T> re-binds per request, picking up reloadOnChange edits; IOptionsMonitor<T> is the singleton version that also exposes change notifications — the right choice for feature flags and anything observed by long-lived services.

public class DatabaseOptions
{
    public const string SectionName = "Database";
    public string ConnectionString { get; set; } = string.Empty;
    public int CommandTimeout { get; set; } = 30;
    public bool EnableRetryOnFailure { get; set; } = true;
}

// Registration with validation
builder.Services
    .AddOptions<DatabaseOptions>()
    .BindConfiguration(DatabaseOptions.SectionName)
    .ValidateDataAnnotations()
    .ValidateOnStart();

// Consume via IOptions<T>
public class OrderService
{
    private readonly DatabaseOptions _dbOptions;

    public OrderService(IOptions<DatabaseOptions> options)
    {
        _dbOptions = options.Value;
    }
}

// IOptionsMonitor for reload-on-change
public class FeatureFlagService
{
    private readonly IOptionsMonitor<FeatureOptions> _monitor;

    public FeatureFlagService(IOptionsMonitor<FeatureOptions> monitor)
    {
        _monitor = monitor;
        _monitor.OnChange(opts => Console.WriteLine("Features reloaded!"));
    }

    public bool IsEnabled(string feature) => _monitor.CurrentValue.Features.Contains(feature);
}

Fail fast at startup

ValidateOnStart() moves configuration errors from "works on my machine, 500s in prod" to "refuses to boot". Data annotations cover ranges and requiredness; for business rules use the Validate overload with a callback that returns a boolean plus an error message. A misconfigured deployment then dies in the same way on every environment instead of degrading at first request.

builder.Services.AddOptions<DatabaseOptions>()
    .BindConfiguration("Database")
    .Validate(opts =>
        !string.IsNullOrWhiteSpace(opts.ConnectionString)
        && opts.CommandTimeout is >= 1 and <= 300,
        "Database:ConnectionString is required and CommandTimeout must be 1-300s")
    .ValidateOnStart();

2.5 Environments and secrets

Environment-specific configuration and secret management are non-negotiable in enterprise applications.

Environment-driven behaviour

The environment name (Development, Staging, Production) is set from the ASPNETCORE_ENVIRONMENT variable or launchSettings.json, and it drives both the configuration file that loads and the code branches — IsDevelopment(), IsStaging(), IsProduction(). Keep the branches narrow: a different exception handler and HSTS on/off are legitimate environmental differences; business logic should never read the environment directly, because it makes a behaviour untestable and invisible in the pipeline.

// launchSettings.json — per-profile env vars for local development
"profiles": {
  "Finance.Api": {
    "applicationUrl": "https://localhost:7001;http://localhost:7000",
    "environmentVariables": { "ASPNETCORE_ENVIRONMENT": "Development" }
  }
}
// Environment checks
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();
    app.UseSwagger();
    app.UseSwaggerUI();
}
else
{
    app.UseExceptionHandler("/error");
    app.UseHsts();
}

// Custom checks compose with the profile name
if (app.Environment.IsEnvironment("Staging"))
{
    app.UseStagingRelay();
}

Development secrets never touch appsettings

Connection strings, API keys and signing material have no business in appsettings.json, which is checked into source control. The User Secrets store keeps them in a per-user directory outside the repo, keyed by the project's UserSecretsId. The CLI manages the store, and AddUserSecrets<Program>() only activates in development by default — a same-named environment variable or a production provider always overrides it, so a secret that leaks into the dev store can never leak into production config.

// Program.cs — environment-aware configuration
var builder = WebApplication.CreateBuilder(args);

builder.Configuration
    .AddJsonFile("appsettings.json", optional: false, reloadOnChange: true)
    .AddJsonFile($"appsettings.{builder.Environment.EnvironmentName}.json", optional: true)
    .AddEnvironmentVariables()
    .AddUserSecrets<Program>(optional: true);

// User Secrets CLI
// dotnet user-secrets init
// dotnet user-secrets set "Database:ConnectionString" "Server=..."
// dotnet user-secrets list
// dotnet user-secrets remove "Database:ConnectionString"

Production keeps keys in a vault

Production secrets belong to a purpose-built store: Azure Key Vault (below), AWS Secrets Manager, HashiCorp Vault, or at minimum environment variables populated by the deployment platform. Key Vault's DefaultAzureCredential uses the environment — managed identity in Azure, the logged-in developer locally — so no key material sits in the image or the config files. Secrets referenced from the vault override everything because the vault is added last.

// Azure Key Vault (production)
builder.Configuration.AddAzureKeyVault(
    new Uri($"https://{builder.Configuration["KeyVault:Name"]}.vault.azure.net/"),
    new DefaultAzureCredential());

// Vault keys use double-dash for hierarchy:  Database--ConnectionString
var cs = builder.Configuration["Database:ConnectionString"];

Never commit appsettings.Development.json secrets or a connectionstrings section with real credentials. Rotate anything that has been pushed — the leak is the exposure, not the git history you delete afterwards.

The Model-View-Controller pattern is the foundation of server-rendered web applications in ASP.NET Core. It separates concerns and enables testable, maintainable code.

3.1 Controllers and actions

Controllers handle HTTP requests, orchestrate business logic, and return responses. They should be thin — delegating to services.

Keep the controller thin

A controller's only jobs are to accept the HTTP request, translate it into service calls, and translate the result back into HTTP. Everything else — validation rules, business invariants, persistence — belongs in services and the domain layer, because a controller that computes is a controller that cannot be unit-tested without an HTTP host. The pattern below is the standard enterprise shape: constructor-injected services, CancellationToken flowed from the request, and nothing but translation in the action bodies.

public class ProductsController : ControllerBase
{
    private readonly IProductService _productService;
    private readonly ILogger<ProductsController> _logger;

    public ProductsController(IProductService productService, ILogger<ProductsController> logger)
    {
        _productService = productService;
        _logger = logger;
    }

    [HttpGet]
    [Route("api/[controller]")]
    public async Task<ActionResult<IEnumerable<ProductDto>>> GetAll(
        [FromQuery] ProductSearchRequest request,
        CancellationToken ct)
    {
        _logger.LogInformation("Searching products: {SearchTerm}", request.SearchTerm);
        var products = await _productService.SearchAsync(request, ct);
        return Ok(products);
    }

    [HttpGet("{id:int}")]
    public async Task<ActionResult<ProductDto>> GetById(int id, CancellationToken ct)
    {
        var product = await _productService.GetByIdAsync(id, ct);
        return product == null ? NotFound() : Ok(product);
    }

    [HttpPost]
    [Authorize(Roles = "Admin")]
    public async Task<ActionResult<ProductDto>> Create([FromBody] CreateProductRequest request, CancellationToken ct)
    {
        var product = await _productService.CreateAsync(request, ct);
        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }

    [HttpPut("{id:int}")]
    public async Task<ActionResult<ProductDto>> Update(int id, [FromBody] UpdateProductRequest request, CancellationToken ct)
    {
        var product = await _productService.UpdateAsync(id, request, ct);
        return product == null ? NotFound() : Ok(product);
    }

    [HttpDelete("{id:int}")]
    [Authorize(Roles = "Admin")]
    public async Task<ActionResult> Delete(int id, CancellationToken ct)
    {
        var success = await _productService.DeleteAsync(id, ct);
        return success ? NoContent() : NotFound();
    }
}

Status-code helpers are the contract

Ok, NotFound, NoContent, CreatedAtAction, BadRequest and StatusCode turn service results into the semantic HTTP codes a client can trust. CreatedAtAction is the one most frequently forgotten: a successful POST should return 201 with a Location header — not a bare 200 with a body, which tells the client nothing about how to reach the new resource. ActionResult<T> lets an action return either the value (serialised as 200) or one of the result objects, which is why the ternary over NotFound()/Ok(product) compiles at all.

[HttpPost("transfer")]
public async Task<ActionResult<TransferReceipt>> Transfer(TransferRequest request, CancellationToken ct)
{
    var receipt = await _accountService.TransferAsync(request, ct);

    // Problem Details for RFC 7807 instead of a bare message
    if (receipt.Status == TransferStatus.InsufficientFunds)
    {
        return Problem(
            statusCode: StatusCodes.Status409Conflict,
            title: "Insufficient funds",
            detail: $"Balance {receipt.Balance:C} is below the transfer amount {receipt.Amount:C}.");
    }

    return CreatedAtAction(nameof(GetReceipt), new { id = receipt.Id }, receipt);
}

Binding sources pick where data comes from

Model binding fills action parameters from the request, and the binding source attributes resolve ambiguity: [FromQuery] for query strings, [FromBody] for JSON, [FromRoute] for path segments, [FromHeader] for headers, [FromForm] for multipart/form-data. With the [ApiController] attribute the defaults are inferred — complex types from the body, primitives from the route or query — and an invalid body triggers automatic 400 with validation errors, so a hand-rolled if (ModelState.IsValid) guard is redundant in API controllers.

[HttpPut("{id:int}/stock")]
public async Task<ActionResult> AdjustStock(
    [FromRoute] int id,
    [FromQuery] int delta,
    [FromHeader(Name = "X-Audit-User")] string auditUser,
    CancellationToken ct)
{
    await _productService.AdjustStockAsync(id, delta, auditUser, ct);
    return NoContent();
}

3.2 Routing

ASP.NET Core supports attribute routing, conventional routing, and minimal API routing. Attribute routing is preferred for APIs.

Attribute routing is explicit

Attribute routing declares each endpoint next to the action that serves it, so the URL surface is visible at a glance and cannot silently collide with another controller's convention. The [controller], [action] and [area] tokens substitute the class name, the action name and the area, which keeps the route in sync when you rename the class. The example below also shows version pinning in the route — the :apiVersion constraint comes from the API versioning package and is covered in chapter 4.

// Attribute routing (recommended for APIs)
[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
public class ProductsController : ControllerBase { }

// The verb attributes narrow the same path
[HttpGet]         // GET  /api/v1/products
[HttpPost]        // POST /api/v1/products
[HttpPut("{id}")] // PUT  /api/v1/products/{id}

Route constraints reject bad segments early

A route constraint is a pattern applied to a template parameter during matching: {id:int} only matches numeric segments, {guid:guid} only GUIDs, and :min(1), :max(50) and :alpha narrow the accepted values further. A request that violates a constraint falls through to the next endpoint or yields 404 — it never reaches your action, so the action needs no defensive parsing. Constraints compose left to right, and a regex(...) constraint exists for shape rules that the built-ins do not cover.

// Route constraints
[HttpGet("{id:int:min(1)}")]           // Integer, minimum 1
[HttpGet("{date:datetime}")]          // DateTime
[HttpGet("{guid:guid}")]              // GUID
[HttpGet("{name:alpha:min(2):max(50)}")] // Alpha, 2-50 chars

Conventional routing for MVC views

Conventional routing declares one route table that maps URLs to controllers and actions: the pattern {controller=Home}/{action=Index}/{id?} means /products/edit/5 resolves by convention to ProductsController.Edit(5) with no attributes on the class. It keeps URLs stable when controllers are reorganised — but the mapping is implicit, so rename a controller and the URLs change too. MVC views conventionally use this kind of table; APIs use attribute routing. Areas extend the convention with a leading segment for a sub-application such as an admin console.

// Conventional routing (for MVC views)
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

// Area routing
[Area("Admin")]
[Route("admin/[controller]/[action]")]
public class DashboardController : Controller { }

A request can match both an attribute-route endpoint and a conventional one. Attribute routes match first, so migrating to attribute routing does not require deleting the conventional fallback in the same release.

3.3 Models and validation

Model validation is built into ASP.NET Core via data annotations. Custom validators handle complex business rules.

Data annotations describe shape rules inline

Validation runs after model binding and before the action: the framework walks ModelState, which is populated from your attributes for every bound property. Each failed rule contributes a keyed error ("Name", "Price"), and [ApiController] converts an invalid state into 400 Bad Request automatically — MVC controllers must check ModelState.IsValid themselves. Attributes stay with the model, so the same class validates identically in an API controller, a Razor Page or a Blazor EditForm.

public class CreateProductRequest
{
    [Required]
    [StringLength(200, MinimumLength = 2)]
    public string Name { get; set; } = string.Empty;

    [Required]
    [Range(0.01, 1000000)]
    public decimal Price { get; set; }

    [Required]
    [Range(1, int.MaxValue)]
    public int StockQuantity { get; set; }

    [Url]
    [StringLength(500)]
    public string? ImageUrl { get; set; }

    [Required]
    [StringLength(50)]
    [RegularExpression(@"^[A-Z]{2}-\d{4}$", ErrorMessage = "SKU must be in format XX-0000")]
    public string Sku { get; set; } = string.Empty;
}

// FluentValidation (preferred for complex rules)
public class CreateProductValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Price).GreaterThan(0).LessThanOrEqualTo(1000000);
        RuleFor(x => x.Sku).Matches(@"^[A-Z]{2}-\d{4}$");
        RuleFor(x => x.StockQuantity).GreaterThanOrEqualTo(0);
    }
}

// Register in Program.cs
builder.Services.AddFluentValidationAutoValidation();
builder.Services.AddValidatorsFromAssemblyContaining<CreateProductValidator>();

Cross-field rules with IValidatableObject

Annotations validate one property at a time, which makes rules like "end date must be later than start date" awkward. Implementing IValidatableObject moves validation to the model's Validate method, where all properties are in scope and the return value is a list of ValidationResults keyed to the offending member. The pattern below keeps the declaration local to the model and produces the same ModelState entries the framework emits.

public class DateRangeRequest : IValidatableObject
{
    public DateTime From { get; set; }
    public DateTime To { get; set; }

    public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
    {
        if (To < From)
        {
            yield return new ValidationResult(
                "To must not be earlier than From",
                new[] { nameof(To) });
        }

        if ((To - From) > TimeSpan.FromDays(365))
        {
            yield return new ValidationResult(
                "A booking range may not exceed 365 days",
                new[] { nameof(To) });
        }
    }

3.5 Filters

Filters run before or after action execution. They implement cross-cutting concerns like logging, caching, and error handling.

Action filters wrap the method call

An action filter sees the request before the action binds its arguments (ActionExecutingContext) and again after the action returns (ActionExecutionDelegate → ActionExecutedContext). Setting context.Result without calling next short-circuits the pipeline, which is what makes the validation filter below return 400 before a single service method runs. The asynchronous variant (IAsyncActionFilter) is preferred because it supports await and avoids two parallel class hierarchies.

public class ValidationFilter : IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(ActionExecutingContext context, ActionExecutionDelegate next)
    {
        if (!context.ModelState.IsValid)
        {
            var errors = context.ModelState
                .Where(x => x.Value?.Errors.Count > 0)
                .ToDictionary(
                    x => x.Key,
                    x => x.Value!.Errors.Select(e => e.ErrorMessage).ToArray());

            context.Result = new BadRequestObjectResult(new { Errors = errors });
            return;
        }

        await next();
    }
}

The five filter kinds and their order

Filters are ordered by scope and then by type: authorization filters run first (and only once per request), then resource filters (outermost on the model-binding boundary), then action filters, then exception filters (which catch exceptions from action, result and binding), then result filters, which wrap the execution of the action's result. Setting a result in a resource or action filter short-circuits everything downstream. A filter is just a service — register per-use with [TypeFilter]/[ServiceFilter] when it needs constructor dependencies, or globally with options.Filters.Add when it must apply to every action.

// Global filter registration
builder.Services.AddControllers(options =>
{
    options.Filters.Add<ValidationFilter>();
    options.Filters.Add<ExceptionFilter>();
});

// Per-action registration with dependencies resolved from DI
[ApiController]
[Route("api/[controller]")]
[ServiceFilter(typeof(TenantFilter))]
public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    [TypeFilter(typeof(IdempotencyFilter))]
    public async Task<ActionResult<OrderDto>> Get(int id, CancellationToken ct)
        => Ok(await _orderService.GetByIdAsync(id, ct));
}

Filters are MVC-specific. For Web API-only apps, the same cross-cutting concerns — timing, correlation ids, error mapping — usually belong in middleware or endpoint filters, which run outside the MVC filter chain and are free of the action lifetime.

4.1 REST principles

RESTful APIs use HTTP verbs, status codes, and resource-based URLs. Following REST conventions makes APIs predictable and self-documenting.

Verbs and status codes are the contract

A RESTful surface is a set of resource URLs — /api/products, /api/products/1 — acted on with the HTTP verbs. The semantic payload of each response is its status code: 200 for a successful read or full update, 201 plus a Location header for a creation, 204 for a successful deletion, 400/422 for bad input, 401/403 for missing/inadequate credentials, 404 for an unknown resource. When a client can infer the outcome from the code alone, curl and generated SDKs work without bespoke documentation.

    public DbSet<Order> Orders => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<OrderItem> OrderItems => Set<OrderItem>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);

        // Global query filter for soft delete
        modelBuilder.Entity<Product>().HasQueryFilter(p => !p.IsDeleted);
        modelBuilder.Entity<Order>().HasQueryFilter(o => !o.IsDeleted);
    }

    public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        // Auto-audit
        var entries = ChangeTracker.Entries()
            .Where(e => e.Entity is IAuditable && (e.State == EntityState.Added || e.State == EntityState.Modified));

        foreach (var entry in entries)
        {
            var auditable = (IAuditable)entry.Entity;
            auditable.ModifiedAt = DateTime.UtcNow;

            if (entry.State == EntityState.Added)
                auditable.CreatedAt = DateTime.UtcNow;
        }

        return await base.SaveChangesAsync(ct);
    }
}

public interface IAuditable
{
    DateTime CreatedAt { get; set; }
    DateTime ModifiedAt { get; set; }
    string? CreatedBy { get; set; }
    string? ModifiedBy { get; set; }
}

7.6 Interceptors and auditing

EF Core interceptors allow you to hook into database operations for auditing, logging, and soft delete.

public class AuditInterceptor : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData, InterceptionResult<int> result)
    {
        var entries = eventData.Context!.ChangeTracker.Entries<IAuditable>()
            .Where(e => e.State == EntityState.Added || e.State == EntityState.Modified);

        foreach (var entry in entries)
        {
            entry.Entity.ModifiedAt = DateTime.UtcNow;
            entry.Entity.ModifiedBy = "current-user";

            if (entry.State == EntityState.Added)
            {
                entry.Entity.CreatedAt = DateTime.UtcNow;
                entry.Entity.CreatedBy = "current-user";
            }
        }

        return base.SavingChanges(eventData, result);
    }
}

// Soft delete interceptor
public class SoftDeleteInterceptor : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData, InterceptionResult<int> result)
    {
        var entries = eventData.Context!.ChangeTracker.Entries()
            .Where(e => e.Entity is ISoftDeletable && e.State == EntityState.Deleted);

        foreach (var entry in entries)
        {
            entry.State = EntityState.Modified;
            ((ISoftDeletable)entry.Entity).IsDeleted = true;
            ((ISoftDeletable)entry.Entity).DeletedAt = DateTime.UtcNow;
        }

        return base.SavingChanges(eventData, result);
    }
}

// Register interceptors
builder.Services.AddScoped<AuditInterceptor>();
builder.Services.AddScoped<SoftDeleteInterceptor>();
builder.Services.AddDbContext<AppDbContext>((sp, options) =>
{
    options.UseSqlServer(connectionString)
           .AddInterceptors(
               sp.GetRequiredService<AuditInterceptor>(),
               sp.GetRequiredService<SoftDeleteInterceptor>());
});

8.1 Clean Architecture

Clean Architecture separates concerns into layers with dependencies pointing inward. The domain has no external dependencies.

// Project structure
// MyApp.Domain/          — Entities, value objects, domain events
// MyApp.Application/     — Use cases, DTOs, interfaces
// MyApp.Infrastructure/  — EF Core, external services, email
// MyApp.WebApi/          — Controllers, middleware, configuration

// Domain layer — no dependencies
public class Order : Entity, IAuditable
{
    private readonly List<OrderItem> _items = new();

    public int Id { get; private set; }
    public string OrderNumber { get; private set; } = string.Empty;
    public int CustomerId { get; private set; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyList<OrderItem> Items => _items.AsReadOnly();
    public decimal Total => _items.Sum(i => i.Quantity * i.UnitPrice);

    public void AddItem(Product product, int quantity)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive");
        if (Status != OrderStatus.Draft) throw new DomainException("Cannot modify submitted order");

        var existing = _items.FirstOrDefault(i => i.ProductId == product.Id);
        if (existing != null) existing.IncreaseQuantity(quantity);
        else _items.Add(new OrderItem(product.Id, product.Name, quantity, product.Price));
    }

    public void Submit()
    {
        if (!_items.Any()) throw new DomainException("Order must have at least one item");
        Status = OrderStatus.Submitted;
    }
}

// Application layer — depends only on Domain
public record CreateOrderCommand(int CustomerId, List<OrderItemDto> Items) : IRequest<int>;

public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, int>
{
    private readonly IOrderRepository _orderRepository;
    private readonly IProductRepository _productRepository;

    public CreateOrderHandler(IOrderRepository orderRepository, IProductRepository productRepository)
    {
        _orderRepository = orderRepository;
        _productRepository = productRepository;
    }

    public async Task<int> Handle(CreateOrderCommand request, CancellationToken ct)
    {
        var order = new Order(request.CustomerId);

        foreach (var item in request.Items)
        {
            var product = await _productRepository.GetByIdAsync(item.ProductId, ct)
                ?? throw new NotFoundException($"Product {item.ProductId} not found");
            order.AddItem(product, item.Quantity);
        }

        order.Submit();
        await _orderRepository.AddAsync(order, ct);
        return order.Id;
    }
}

8.2 CQRS with MediatR

CQRS separates reads and writes. MediatR implements the mediator pattern, decoupling controllers from business logic.

// Command (write)
public record UpdateOrderStatusCommand(int OrderId, OrderStatus NewStatus) : IRequest<bool>;

public class UpdateOrderStatusHandler : IRequestHandler<UpdateOrderStatusCommand, bool>
{
    private readonly IOrderRepository _repository;

    public UpdateOrderStatusHandler(IOrderRepository repository) => _repository = repository;

    public async Task<bool> Handle(UpdateOrderStatusCommand request, CancellationToken ct)
    {
        var order = await _repository.GetByIdAsync(request.OrderId, ct);
        if (order == null) return false;

        order.UpdateStatus(request.NewStatus);
        await _repository.UpdateAsync(order, ct);
        return true;
    }
}

// Query (read)
public record GetOrderQuery(int OrderId) : IRequest<OrderDto?>;

public class GetOrderHandler : IRequestHandler<GetOrderQuery, OrderDto?>
{
    private readonly IOrderRepository _repository;

    public GetOrderHandler(IOrderRepository repository) => _repository = repository;

    public async Task<OrderDto?> Handle(GetOrderQuery request, CancellationToken ct)
    {

        return order is null ? null : new OrderDto(order.Id, order.OrderNumber, order.Status.ToString(), order.Total);
    }
}

8.3 FluentValidation pipeline

FluentValidation integrates with MediatR via pipeline behaviors, ensuring all commands are validated before handling.

public class ValidationBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
    where TRequest : IRequest<TResponse>
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public ValidationBehavior(IEnumerable<IValidator<TRequest>> validators)
        => _validators = validators;

    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        if (!_validators.Any()) return await next();

        var context = new ValidationContext<TRequest>(request);
        var results = await Task.WhenAll(_validators.Select(v => v.ValidateAsync(context, ct)));
        var failures = results.SelectMany(r => r.Errors).Where(f => f != null).ToList();

        if (failures.Count != 0)
            throw new ValidationException(failures);

        return await next();
    }
}

8.4 Resilience and Polly

Polly provides retry, circuit breaker, timeout, and fallback policies for resilient distributed systems.

// HttpClient with Polly policies
builder.Services.AddHttpClient<IExternalPaymentService, ExternalPaymentService>(client =>
{
    client.BaseAddress = new Uri(builder.Configuration["ExternalApis:Payment:BaseUrl"]!);
    client.DefaultRequestHeaders.Add("Accept", "application/json");
})
.AddPolicyHandler(Policy.TimeoutAsync<HttpResponseMessage>(TimeSpan.FromSeconds(10)))
.AddPolicyHandler(GetRetryPolicy())
.AddPolicyHandler(GetCircuitBreakerPolicy());

static IAsyncPolicy<HttpResponseMessage> GetRetryPolicy() =>
    Policy.Handle<HttpRequestException>()
        .OrResult<HttpResponseMessage>(r => (int)r.StatusCode >= 500 || r.StatusCode == HttpStatusCode.RequestTimeout)
        .WaitAndRetryAsync(3, retryAttempt =>
            TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)));

static IAsyncPolicy<HttpResponseMessage> GetCircuitBreakerPolicy() =>
    Policy.Handle<HttpRequestException>()
        .OrResult<HttpResponseMessage>(r => (int)r.StatusCode >= 500)
        .CircuitBreakerAsync(5, TimeSpan.FromSeconds(30));

// Resilience pipeline (.NET 8+)
builder.Services.AddResiliencePipeline("payment-pipeline", builder =>
{
    builder.AddRetry(new RetryStrategyOptions
    {
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromSeconds(1),
        BackoffType = DelayBackoffType.Exponential
    })
    .AddTimeout(TimeSpan.FromSeconds(10))
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        FailureRatio = 0.5,
        SamplingDuration = TimeSpan.FromSeconds(30),
        MinimumThroughput = 10,
        BreakDuration = TimeSpan.FromSeconds(30)
    });
});

public class CachedProductService : IProductService
{

    private readonly IDistributedCache _cache;
    private readonly ILogger<CachedProductService> _logger;

    public CachedProductService(
        IProductService inner,

        ILogger<CachedProductService> logger)
    {

        _logger = logger;

    public async Task<ProductDto?> GetByIdAsync(int id, CancellationToken ct)

        var cached = await _cache.GetStringAsync(cacheKey, ct);

        if (cached != null)
        {
            _logger.LogDebug("Cache hit for product {ProductId}", id);
            return JsonSerializer.Deserialize<ProductDto>(cached);

            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10),
                SlidingExpiration = TimeSpan.FromMinutes(2)
            };
            await _cache.SetStringAsync(cacheKey, JsonSerializer.Serialize(product), options, ct);
        }

        return product;
    }
}

// Token generation service
public class TokenService : ITokenService
{
    private readonly IConfiguration _config;

    public TokenService(IConfiguration config) => _config = config;

    public string GenerateToken(User user)
    {
        var claims = new[]
        {
            new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
            new Claim(ClaimTypes.Email, user.Email),
            new Claim(ClaimTypes.Role, user.Role)
        };

        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
        var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        var token = new JwtSecurityToken(
            issuer: _config["Jwt:Issuer"],
            audience: _config["Jwt:Audience"],
            claims: claims,
            expires: DateTime.UtcNow.AddHours(2),
            signingCredentials: creds);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}

public class MinimumYearsHandler : AuthorizationHandler<MinimumYearsRequirement>

        AuthorizationHandlerContext context, MinimumYearsRequirement requirement)

        return Task.CompletedTask;
    }
}

10.1 Unit testing with xUnit

xUnit is the standard testing framework for .NET. It supports facts, theories, and async tests.

public class OrderServiceTests
{
    private readonly Mock<IOrderRepository> _orderRepoMock = new();
    private readonly Mock<IProductRepository> _productRepoMock = new();
    private readonly OrderService _service;

    public OrderServiceTests()
    {
        _service = new OrderService(_orderRepoMock.Object, _productRepoMock.Object);
    }

    [Fact]
    public async Task CreateOrder_WithValidData_ReturnsOrder()
    {
        // Arrange
        var product = new Product { Id = 1, Name = "Laptop", Price = 999.99m, StockQuantity = 10 };
        _productRepoMock.Setup(r => r.GetByIdAsync(1, It.IsAny<CancellationToken>()))
            .ReturnsAsync(product);

        _orderRepoMock.Setup(r => r.AddAsync(It.IsAny<Order>(), It.IsAny<CancellationToken>()))
            .ReturnsAsync((Order o, CancellationToken _) => o);

        // Act
        var result = await _service.CreateAsync(new CreateOrderRequest(1, new() { new OrderItemDto(1, 2) });

        // Assert
        result.Should().NotBeNull();
        result.Id.Should().BeGreaterThan(0);
        _orderRepoMock.Verify(r => r.AddAsync(It.IsAny<Order>(), It.IsAny<CancellationToken>()), Times.Once);
    }

    [Theory]
    [InlineData(0)]
    [InlineData(-1)]
    public async Task CreateOrder_WithInvalidQuantity_ThrowsException(int quantity)
    {
        var product = new Product { Id = 1, Name = "Laptop", Price = 999.99m, StockQuantity = 10 };
        _productRepoMock.Setup(r => r.GetByIdAsync(1, It.IsAny<CancellationToken>()))
            .ReturnsAsync(product);

        var act = () => _service.CreateAsync(new CreateOrderRequest(1, new() { new OrderItemDto(1, quantity) });

        await act.Should().ThrowAsync<ValidationException>();
    }
}

10.2 Integration testing

Integration tests verify the full stack — controllers, services, database, and middleware — working together.

public class OrdersApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;
    private readonly WebApplicationFactory<Program> _factory;

    public OrdersApiTests(WebApplicationFactory<Program> factory)
    {
        _factory = factory.WithWebHostBuilder(builder =>
        {
            builder.ConfigureServices(services =>
            {
                services.Remove<DbContextOptions<AppDbContext>>();
                services.AddDbContext<AppDbContext>(options =>
                    options.UseInMemoryDatabase("TestDb"));
            });
        });
        _client = _factory.CreateClient();
    }

    [Fact]
    public async Task GetOrders_ReturnsSuccessStatusCode()
    {
        var response = await _client.GetAsync("/api/orders");
        response.StatusCode.Should().Be(HttpStatusCode.OK);
    }

    [Fact]
    public async Task CreateOrder_WithValidRequest_ReturnsCreated()
    {
        var request = new CreateOrderRequest(1, new() { new OrderItemDto(1, 2) });
        var response = await _client.PostAsJsonAsync("/api/orders", request);

        response.StatusCode.Should().Be(HttpStatusCode.Created);
        var order = await response.Content.ReadFromJsonAsync<OrderDto>();
        order.Should().NotBeNull();
    }
}

10.3 Docker containerisation

Docker enables consistent deployment across environments. Multi-stage builds keep images small.

# Dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY ["MyApp.WebApi/MyApp.WebApi.csproj", "MyApp.WebApi/"]
RUN dotnet restore "MyApp.WebApi/MyApp.WebApi.csproj"
COPY . .
RUN dotnet build "MyApp.WebApi/MyApp.WebApi.csproj" -c Release -o /app/build

FROM build AS publish
RUN dotnet publish "MyApp.WebApi/MyApp.WebApi.csproj" -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=publish /App/publish .
ENTRYPOINT ["dotnet", "MyApp.WebApi.dll"]
# docker-compose.yml
version: '3.8'
services:
  webapi:
    build: .
    ports:
      - "8080:8080"
    environment:
      - ASPNETCORE_ENVIRONMENT=Production
      - ConnectionStrings__Default=Server=db;Database=MyApp;...
    depends_on:
      - db
      - redis
  db:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment:
      - ACCEPT_EULA=Y
      - SA_PASSWORD=YourStrong@Passw0rd
    ports:
      - "1433:1433"
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

10.4 CI/CD pipeline

GitHub Actions provides a complete CI/CD pipeline for .NET applications with testing, building, and deployment.

# .github/workflows/dotnet.yml
name: .NET CI/CD

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Setup .NET
      uses: actions/setup-dotnet@v4
      with:
        dotnet-version: '10.0.x'
    - name: Restore dependencies
      run: dotnet restore
    - name: Build
      run: dotnet build --no-restore --configuration Release
    - name: Test
      run: dotnet test --no-build --verbosity normal
    - name: Publish
      run: dotnet publish -c Release -o ./publish
