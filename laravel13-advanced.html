Orientation · Scope and version baseline

0.1 What this guide assumes0.2 What "advanced" means here0.3 Version baseline0.4 Directory conventions0.5 Verifying the baseline

Establishes the version baseline and the set of decisions this guide treats as settled, so the chapters that follow can be read as reference material rather than as an introduction.

0.1 What this guide assumes

The reader is already productive on Laravel 11, 12 or an equivalent 10.x codebase and needs precision on behaviour that the basic guides treat as automatic.

This guide covers architectural decisions in a mature Laravel 13 application: how the container resolves objects, how behaviour is registered and booted, how persistence and transport boundaries are drawn, and how the deployed system is observed and maintained. Routing basics, Blade directives, the shape of a CRUD resource controller and the syntax of Eloquent’s basic query builder are assumed knowledge.

Everything here is pinned to a specific runtime. Where a behaviour is specific to Laravel 13 or PHP 8.3 it is called out explicitly, because the framework’s defaults moved in 10.x, 11.x and 12.x and older material found online frequently describes a version that no longer ships.

0.2 What "advanced" means here

Advanced Laravel is a property of the application’s structure, not of the number of abstractions in it.

Three habits separate a maintainable Laravel application from a growing one.

HabitNaive formEngineered form
Dependency acquisitionnew InvoiceService() inside a controllerType-hinted constructor injection resolved through the container
Persistence accessQueries scattered through controllers and viewsQueries behind repositories or query objects, scoped to an aggregate
Side effectsMail and HTTP calls inline in a requestQueued jobs dispatched after the transaction commits

Conversely, none of the following are automatically advanced: repositories over a two-table model, a service class per model method, event sourcing, or hexagonal architecture applied to a CRUD admin panel. Structure should be justified by the complexity of the domain, not by adherence to a pattern.

Over-abstraction warning. Laravel’s own Eloquent Active Record, facades and zero-config container are deliberate simplifications. Introducing an abstraction layer to avoid them is a net cost unless the domain has a specific property — vendor-neutral transport, a legacy data store, or a rule set that changes independently of the schema — that the framework default cannot express.

0.4 Directory conventions

The application skeleton this guide assumes, and the mapping between directories and the boundaries discussed in later chapters.

Laravel 13 ships the slim skeleton first introduced in 11.x: fewer files, more configuration expressed in code. The directories that matter for architectural work are the ones below.

PathResponsibilityChapter
app/ProvidersBinding registration, boot-time configuration1, 2
app/Http/MiddlewareRequest lifecycle interception3, 15
app/ModelsPersistence shapes, casts, relations4, 5
app/DomainAggregates, DTOs, actions, policies8, 9
app/JobsDeferred side effects7, 16
app/Http/ResourcesOutbound payload shaping12
tests/Feature, tests/UnitIntegration and pure-unit suites11

Note that app/Domain is not a Laravel convention. It is used throughout this guide because the alternative — placing domain services in app/Services alongside infrastructure concerns — makes the boundary impossible to enforce with namespace-level test rules. The framework does not care which convention is chosen; the value is that it is one boundary rather than several.

// bootstrap/app.php — Laravel 11+ slim skeleton
return Application::configure(basePath: __DIR__.'/../')
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware) {
        $middleware->alias(['scoped' => ScopedRateLimit::class]);
        $middleware->append(EnsureRequestIsHealthy::class);
        $middleware->validateCsrfTokens(except: ['api/webhooks/*']);
    })
    ->withExceptions(function (Exceptions $exceptions) {
        $exceptions->render(function (LedgerImbalance $e) {
            return response()->json(['code' => 'ledger_imbalance'], 409);
        });
    })
    ->create();

Everything above is configuration, not a bootstrap file. Application::configure() returns an Illuminate\Foundation\Configuration\ApplicationBuilder. Middleware, exception rendering and routing are all composed here, so the classic App\Http\Kernel and Handler base classes no longer exist in a default 13.x install. Code generators and third-party packages that extend those classes need updating; the package ecosystem largely migrated in 11.x.

0.5 Verifying the baseline

How to confirm at runtime that a codebase matches the assumptions made in this guide.

Before applying anything from the following chapters, confirm the actual resolved versions rather than the constraints in composer.json. A constraint of ^13.0 permits any 13.x release, and minor releases occasionally change deprecation timing and config defaults.

php artisan about
# Reports Laravel, PHP, drivers and cache/queue/session configuration

composer show laravel/framework | grep versions
# Confirms the installed patch level, not the constraint

The second command matters for the chapters on queues and caching, where Redis command behaviour and serialized payload handling have changed between patch releases. Pin the framework in a lockfile and review the lockfile diff in the same pull request as any framework bump.

1 · Container resolution, contextual binding and lifetime

1.1 Autowiring and the resolution order1.2 Binding and contextual resolution1.3 Lifetime: singleton, scoped, transient1.4 Extending and decorating1.5 Facades, real-time facades and accessors

How Illuminate\Container\Container decides what to build, how to register alternatives to concrete constructors, and how object lifetime is determined across a request, a job and a queued batch.

1.1 Autowiring and the resolution order

The algorithm the container applies when a type-hinted dependency is unresolvable, and the exceptions that can interrupt it.

The container resolves a class name by consulting four sources in order, and only falls through to the next if the previous throws BindingResolutionException.

  1. An explicit binding — bind(), singleton(), scoped(), instance(), or a binding registered by a service provider.
  2. An alias — alias() or Facade's getFacadeAccessor(), which is resolved first and then re-enters step 1.
  3. build(), which reflects the concrete class. Constructor parameters that are class-typed are resolved recursively; parameters with a default value use the default; untyped or optional-without-default parameters fail unless the class is instantiable with no arguments.
  4. A contextual binding registered with when(...)->needs(...)->give(...), matched on the concrete class currently being built.

Step 4 is applied inside build(), so a contextual binding is consulted per injection site rather than per type. This is the mechanism that makes interface-based dependency injection usable without a single abstract binding.

// A contextual binding applies to one injection site.
final class class BillingServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->when(ProcessInvoice::class)
            ->needs(PaymentGateway::class)
            ->give(StripeGateway::class);

        $this->app->when(SettlePayout::class)
            ->needs(PaymentGateway::class)
            ->give(ManualBankTransferGateway::class);
    }
}

Contextual bindings are resolved per resolution, not per registration. Because a when() block applies to every call to build() for the named class, a class resolved from inside two different consumers can receive two different implementations. That is usually the intent, but it makes the coupling implicit. Prefer a bound implementation when the substitution is global, and contextual binding when it is genuinely local to one consumer.

1.2 Binding and contextual resolution

The binding API surface, what each method does to the resolution algorithm, and how closures versus class strings differ in sharing.

MethodResolves toShared?
bind($abstract, $concrete, $shared = false)Result of build($concrete)No, unless $shared
singleton($abstract, $concrete)One cached instance per containerYes
scoped($abstract, $concrete)One instance per lifecycle scopeYes, per scope
instance($abstract, $instance)The literal object passed inYes
bindIf($abstract, $concrete)Only if not already boundInherits
value($key, $value)A scalar or array on configN/A

A closure binding receives the container and the resolution parameters, which makes it the only way to bind an interface to a closure that itself needs dependencies. A class-string binding is equivalent to fn () => $app->build($class) and is cheaper only in readability.

final class class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Interface to a factory closure with injected dependencies.
        $this->app->singleton(Clock::class, function (Application $app) {
            return SystemClock::class === config('services.clock')
                ? new SystemClock
                : new FrozenClock(new DateTimeImmutable('2026-01-01'));
        });

        // Resolved with constructor parameters available.
        $this->app->bind(ReportBuilder::class, function (Application $app, array $parameters) {
            return new ReportBuilder(
                $app->make(Clock::class),
                $parameters['locale'] ?? app()->getLocale(),
            );
        });
    }
}

Use app() with parameters — app(ReportBuilder::class, ['locale' => 'fr']) — and the parameters are forwarded to the closure as $parameters. This is the supported way to parameterise a resolution; do not read globals inside the binding.

1.3 Lifetime: singleton, scoped, transient

The four object lifetimes the container offers and the failure mode each one produces when chosen incorrectly.

Three lifetimes exist in a web request. Everything else is a variation.

  • Transient — the default for bind() and for any class with no binding. A new instance is built on every make(). This is correct for value objects, DTOs, actions and anything holding per-request state.
  • Singleton — one instance per container instance. The container is created once per PHP process; under php artisan serve or FPM that means one per process, and state leaks between requests handled by the same worker.
  • Scoped — one instance per lifecycle scope, where a scope is a request, a queued job, or a queued batch. This is the correct lifetime for anything that touches the database, the session, or the current authenticated user, because those bindings are also scoped.
use Illuminate\Contracts\Foundation\Application;

final class class CartService
{
    public function __construct(
        private readonly Application $app,
    ) {}

    public function items(): Collection
    {
        // resolve() honours scoped() for the current scope
        return $this->app->make(UserCart::class)->lines();
    }
}

$this->app->scoped(CartService::class);  // one CartService per request

The critical rule: a singleton must never depend on a scoped binding, and never write to scoped state. The reverse is always safe.

Scoped dependency held byOutcome
A singletonFirst request’s user, database connection and tenant leak into every later request in the worker
A scoped bindingSafe — the scoped instance is itself per-scope
A transientSafe, but the work is repeated on every injection

This is the single most common long-lived bug in Laravel production. A singleton ReportService constructed with the current Auth user, injected into a controller, serves user A’s report to user B on the next request in the same FPM worker. The symptom is intermittent and correlates with worker reuse, which is why it frequently escapes staging. Any framework binding that reads request state — auth, session, request, db connection resolvers — is scoped, not singleton.

Illuminate\Container\Container::forgetScopedInstances() is invoked automatically at the start of each request, job and batch by the framework. If you resolve instances yourself inside a long-running process, you are responsible for flushing.

1.4 Extending and decorating

The three idioms for substituting a framework or package implementation, and when each is appropriate.

extend() registers a callback that receives the resolved object and returns a replacement. It is the supported way to swap a third-party implementation while keeping the original as a base class.

$this->app->extend(Illuminate\Notifications\Channels\MailChannel::class,
    function (MailChannel $channel, Application $app) {
        return new InstrumentedMailChannel(
            $channel, $app->make(MetricsRecorder::class)
        );
    });

For interfaces the framework binds internally — Illuminate\Contracts\Auth\Guard, the notification dispatcher, the exception handler — prefer the higher-level hooks over extend(): Auth::provider(), Notification::resolved(), and Application::renderable() in bootstrap/app.php. These survive framework upgrades because the container key is stable, whereas extend() on a concrete class silently stops applying if the framework changes the default binding.

Use bindIf() in package providers. A package that calls $this->app->bind() unconditionally overwrites the host application’s binding, which makes the package impossible to customise. bindIf() and singletonIf() respect an existing binding and turn package configuration into a documented extension point rather than a fight.

1.5 Facades, real-time facades and accessors

How a facade call is turned into a container resolution, and how to replace or trace it.

A facade forwards a static call to the container by string key. Cache::put() becomes app('cache')->put(), where the accessor 'cache' is defined by Cache::getFacadeAccessor() and bound to Illuminate\Cache\CacheManager in CacheServiceProvider.

Two resolution modes matter for debugging. The default resolves the accessor on every call, so rebinding takes effect immediately. Setting a resolved instance on the facade root with Cache::swap($instance) or Cache::clearResolvedInstance('cache') pins or unpins the instance respectively.

// Chapter 14 — bound-instance tracing for facade debugging.
DB::enableQueryLog();
try {
    $orders = Order::query()->where('status', 'open')->get();
} finally {
    foreach (DB::getQueryLog() as $q) {
        logger()->debug('query', ['sql' => $q['query'], 'ms' => $q['time']]);
    }
    DB::disableQueryLog();
}

// Facade: does the container know this class?
echo app()->bound(PaymentGateway::class) ? 'bound' : 'concrete';

Real-time facades — use Illuminate\Support\Facades\Cache; Cache::put() imported into a class rather than referenced as a root namespace — resolve through Facade::__callStatic() identically, but the import makes the dependency greppable and IDE-resolvable. Prefer them in domain and application code; use the full facade name sparingly.

2 · Service providers: registration order, boot and deferred loading

2.1 The two-phase lifecycle2.2 Registration order and why it matters2.3 Boot-time side effects2.4 Deferred providers and their removal2.5 Discovery, publishing and package providers

How the provider list is assembled and executed, why register() must not resolve, and what to do with the deferred-provider mechanism that older codebases still rely on.

2.1 The two-phase lifecycle

What the framework guarantees about ordering within each phase, and the invariant that separates registration from booting.

Every provider implements two optional methods. The framework calls all register() methods across all providers first, then all boot() methods, in the same order.

The invariant is that register() must only declare bindings — it must not resolve them and must not run code that depends on another provider having booted. boot() is where configuration, route registration, view composers and event listeners are set up. This two-phase design is what allows a binding to be overridden by a later provider and still be visible to everything booted afterwards.

use Illuminate\Support\ServiceProvider;

final class class BillingServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Declarations only. No make(), no resolution of other services.
        $this->app->scoped(LedgerService::class);
        $this->app->singleton(ExchangeRateProvider::class, EcbExchangeRateProvider::class);

        $this->app->singleton(BillingSettings::class, function () {
            return new BillingSettings(
                currency: config('billing.currency', 'EUR'),
                graceDays: (int) config('billing.grace_days', 7),
            );
        });

        $this->mergeConfigFrom(__DIR__.'/../config/billing.php', 'billing');
    }

    public function boot(): void
    {
        // Resolving here is safe: every provider has registered.
        $this->app->make(ExchangeRateProvider::class)->warm();

        Model::preventLazyLoading($this->app->environment('production'));
    }
}

mergeConfigFrom is merge-only. It merges the package defaults beneath whatever the application has published, with the application’s values winning. Never use it to overwrite a value the host has explicitly set; that makes the package unconfigurable.

2.2 Registration order and why it matters

The order providers are executed in, and the two mechanisms available to control it.

Order is determined by three sources, applied in this precedence order.

  1. Framework providers, listed in Illuminate\Foundation\Application::DEFAULT_PROVIDERS or its equivalent in 11.x+ builds. These are the package manifest providers first, then the framework’s own.
  2. Application providers from bootstrap/providers.php, in file order. This file replaced config/app.php's providers array in 11.x.
  3. Discovered package providers, appended from bootstrap/cache/packages.php and services.php when package:discover runs.
// bootstrap/providers.php — Laravel 11+
return [
    App\Providers\AppServiceProvider::class,
    App\Providers\BillingServiceProvider::class,
    App\Providers\LegacyImportProvider::class,  // must load after Billing
];

The practical implication: an application provider’s register() runs after every framework and package provider’s register(), but before every one’s boot(). To replace a package binding, register in the application provider — no ordering gymnastics required. To replace a binding another application provider set, order the files.

// config/app.php no longer holds providers in 11+. To force an order
// between two package providers, use Artisan::starting / register events:

final class class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        // Runs after all providers registered, before app is ready.
        Event::listen(Illuminate\Foundation\Http\Events\RequestHandled::class, function () {
            /* per-request teardown work */
        });
    }
}

Verify rather than assume order. php artisan about --only=providers or a temporary listener on Illuminate\Foundation\Events\Booting printing get_class($this) will show the actual execution order on the deployed configuration, including packages that appear only in that environment.

2.3 Boot-time side effects

What legitimately belongs in boot(), what belongs in a command or scheduler, and the cost of booting on every request.

boot() executes once per PHP process, before any request is handled. In FPM that is once per worker, in php artisan serve once per process, and in Octane once per worker that then handles many requests. It is therefore the correct place for work that must happen exactly once per process, and the wrong place for anything that depends on the current request.

WorkWhere it belongsReason
View composers, Blade directivesboot()Registers macros on shared classes
Route model binding customisationRoute::bind() in boot()No database access until a route resolves
Model event listeners via ::observe()boot()Registration only
Cache warm-up, API calls, seedingDeployment script or artisan commandBlocks or fails every request
Reading the current user or requestNeither — use scoped or request-time resolutionWrong in boot, wrong in a singleton
final class class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        // Correct: registration-time only, no I/O.
        Route::bind('invoice', function (string $value) {
            return Invoice::where('public_id', $value)->firstOrFail();
        });

        Schema::defaultStringLength(191);

        RateLimiter::for('api', function (Request $request) {
            return null; // Limit::perMinute(60)->by($request->user()?->id)
        });
    }
}

Never do I/O in boot(). A Http::get() in a provider’s boot method means the application cannot start if the third party is slow, and in a multi-instance deployment it multiplies that call by the instance count. Warm caches in a deploy step that runs before traffic is shifted.

2.4 Deferred providers and their removal

The historical provides()/isDeferred() mechanism, why it no longer applies, and how to migrate off it.

Before 11.x, a provider implementing provides() and setting protected bool $defer = true was loaded on demand when one of its provided services was first resolved. The manifest of deferred services was cached in bootstrap/cache/services.php.

That mechanism is gone. In 11.x the application no longer builds a deferred-provider manifest, and a provider declaring $defer or provides() is simply registered eagerly like any other. The property is retained on the ServiceProvider base class for subclass compatibility but has no runtime effect.

// Legacy code — inert in Laravel 13, remove it.
final class class PdfServiceProvider extends ServiceProvider
{
    protected bool $defer = true;          // remove

    public function provides(): array  // remove
    {
        return [PdfRenderer::class, 'pdf'];
    }
}

// Migration target.
final class class PdfServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->singleton(PdfRenderer::class, DompdfRenderer::class);
    }
}

php artisan optimize:clear   # drops the stale services.php manifest

Performance reality check. Deferring providers saved a small number of register() calls per request. The measurable costs in a modern application are autoloading and booting, and those are unaffected. Optimise by removing I/O from boot() and by running optimize-autoloader and config:cache, not by chasing deferred providers.

2.5 Discovery, publishing and package providers

How third-party providers are discovered, what publishing tags exist, and the contract a package provider should honour.

Package discovery reads each installed package’s composer.json for an extra.laravel.providers array. php artisan package:discover writes the result to bootstrap/cache/packages.php, which is regenerated automatically by composer install via the @php artisan package:discover script.

// A package composer.json
{
    "name": "acme/billing",
    "extra": {
        "laravel": {
            "providers": ["Acme\\Billing\\BillingServiceProvider"],
            "aliases": { "Billing": "Acme\\Billing\\Facades\\Billing" }
        }
    }
}

Publishing is tag-based. A package declares its tag names in provides()... which, after the deferred-provider removal described in 2.4, must be declared explicitly.

public function boot(): void
{
    if ($this->app->runningInConsole()) {
        $this->publishes([__DIR__.'/../config/billing.php' => config_path('billing.php')], 'billing-config');

This is the pragmatic form of the modular boundaries chapter 8 describes.

What happens before the kernel exists, and the operations performed by LoadEnvironmentVariables and LoadConfiguration.

Before Kernel::handle() runs, the front controller has already done the work that determines the entire configuration of the process.

Inside bootstrap/app.php, the ApplicationBuilder composes the kernel and console kernel. LoadEnvironmentVariables reads .env and any .env.{APP_ENV} overlay through Dotenv, populating $_ENV and $_SERVER. LoadConfiguration then loads every file in config/ — unless config:cache has produced bootstrap/cache/config.php, in which case one file is included instead of thirty.

This is why php artisan config:cache is the single highest-value production command: it replaces thirty file reads and thirty array merges with a single var_export include.

Config caching breaks closure-based configuration. Any config/*.php file returning a closure — common for sanctum.php and cors.php in some setups, and always in services.php if written carelessly — will fail at cache time with "Your configuration files are not serializable". Move any closure into a class and reference the class name instead.

Request::capture() builds the Symfony\Component\HttpFoundation\Request instance, which Laravel decorates with Illuminate\Http\Request during the bootstrap phase. A reverse-proxy-aware application must have TrustProxies or its 11.x+ replacement configured before the request is captured, or the client IP, scheme and HTTPS flag will be wrong — which in turn breaks secure-cookie detection, rate limiting by IP and url()->current() generation.

3.3 Middleware ordering and termination

The handle()/$next contract, why order is semantic rather than stylistic, and the first-class termination pattern.

Middleware is a pipeline. Each middleware’s handle() receives the request and a closure representing the rest of the stack. Work before $next($request) runs inbound; work after it runs outbound. The outermost middleware’s post-$next code runs last.

final class class MeasureRequest
{
    public function handle(Request $request, Closure $next): Response
    {
        $start = hrtime(true);

        $response = $next($request);   // inbound work above, outbound below

        $response->headers->set('Server-Timing', sprintf('app;dur=%.1f', (hrtime(true) - $start) / 1e6));

        return $response;
    }
}

Order is semantic because inbound and outbound halves are not interchangeable. A middleware that starts a transaction before $next and commits after it must be outside a middleware that reads the database inside $next; otherwise the reader sees uncommitted state on some paths and committed state on others. Conversely, a middleware that must observe the final response must be inside anything that can short-circuit.

Laravel 13 provides a first-class alternative to the "run after the response is sent" pattern: terminate(). It executes after the response is flushed, outside the try/catch of the pipeline, so a failure there cannot corrupt a delivered response.

final class class RecordOpenApiUsage
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);

        $this->telemetry->record(route: $request->route()?->getName(), status: $response->getStatusCode());

        return $response;
    }

    public function terminate(Request $request, Response $response): void
    {
        // Correct for slow external calls: response already delivered.
        Http::timeout(1)->post(config('telemetry.ingest'), [
            'path' => $request->path(), 'status' => $response->getStatusCode(),
        ]);
    }
}

Middleware must be reusable. The same instance handles every request in a process under classic FPM-per-request, but under Octane the object is re-resolved per request from a scoped binding. Any state stored as a public or instance property on a middleware is therefore safe under FPM and unsafe under Octane unless the middleware is registered as scoped. Chapter 5 of the Octane material covers this; the safe default is to hold no per-request state on the middleware itself.

4 · Eloquent internals: models, casts, accessors and dirty tracking

How Eloquent hydrates, mutates and persists a model instance, and the extension points that let you change behaviour without leaving the Active Record boundary.

4.1 The model as an identity map

What Eloquent keeps in memory per model, and why that changes how you write application code around it.

An Eloquent model instance is a stateful in-memory representation of one row, plus an identity map of the attributes that were read from or written to the database. Three consequences follow, and they account for most of the surprising Eloquent behaviour.

  1. Accessing an attribute that was not in the SELECT list returns null, not a lazy query. This is why Model::select(['id']) followed by $model->name silently yields null.
  2. A model instance does not know it is stale. Two requests, or two queries in one request, produce two independent objects; refreshing one does not affect the other.
  3. Relations are lazy properties. Touching $post->author issues a query and caches the result on the instance for the remainder of its life.
final class class Invoice extends Model
{
    protected fillable = ['customer_id', 'issued_at', 'total_cents'];

    protected function casts(): array
    {
        return [
            'issued_at'    => 'immutable_datetime',
            'due_at'      => 'immutable_datetime',
            'total_cents' => 'integer',
            'meta'        => 'array',
            'is_disputed' => 'boolean',
        ];
    }
}

Overriding casts() as a method rather than declaring a $casts property is the documented Laravel 11+ signature. The property still works and is not deprecated in 13.x, but the method is the form the framework’s own stubs generate and the form the upgrade guide points to.

Store integers, not floats, for money. total_cents as an integer column with an integer cast removes an entire class of rounding bug. If a legacy schema requires decimal, cast to 'decimal:2', which returns a string — never to float, because a float cast will silently lose precision on values above 253 cents.

4.2 Attribute pipeline and casts

The order in which raw attributes are passed through mutators, casts, accessors and relations.

When an attribute is read, Eloquent evaluates in this order: relation check (returns a Relation or its cached result), then a custom accessor, then the registered cast, then the raw attribute. When an attribute is written, the inverse: a custom mutator, then the cast serialiser, then storage.

Two casting styles exist. Array-style $casts entries and class casts implementing CastsAttributes are both first-class in 13.x; the class form is preferred for anything non-trivial because it is type-safe, testable in isolation, and can be reused.

final class class MoneyCast implements CastsAttributes
{
    public function get(Model $model, string $key, mixed $value, array $attributes): mixed
    {
        return $value === null
            ? null
            : Money::fromMinor((int) $value, $attributes['currency'] ?? 'EUR');
    }

    public function set(Model $model, string $key, mixed $value, array $attributes): mixed
    {
        // Return an array to write to additional columns atomically.
        if ($value === null) {
            return ['total_cents' => null];
        }

        $money = $value instanceof Money ? $value : Money::of($value);

        return ['total_cents' => $money->minor, 'currency' => $money->currency->value];
    }
}

Returning an array from a cast’s set() writes multiple columns. The return value is merged into the model’s pending attributes. Returning a bare scalar only sets the single column, which is why a naive Money cast silently stops persisting the currency. Cover multi-column casts with a round-trip assertion in the test suite.

For values that need no database column at all, Attribute accessors let the cast, the accessor and the mutator be declared together and receive the whole attribute array.

4.3 Accessors, mutators and value objects

The modern Attribute declaration form, its caching behaviour, and when to move logic off the model.

use Illuminate\Database\Eloquent\Casts\Attribute;

{
    return Attribute::make(
        get: fn (object $value) => trim(
            (string) ($value->first_name ?? '').' '.($value->last_name ?? '')
        ),
        set: fn (array $value) => [
            'first_name' => $value['first'] ?? null,
            'last_name'  => $value['last']  ?? null,

    )->shouldCache();
}

// Computed attribute with no persisted column.
protected function isOverdue(): Attribute
{
    return Attribute::get(
        fn (): bool => $this->due_at?->isPast() ?? false
    );
}

shouldCache() memoises the computed value in the model’s attribute cache. This is correct for an attribute derived purely from the instance’s own state, and wrong for one that depends on anything mutable — a computed VAT total, a permission check, a stock level. Caching those on the model makes stale data the default.

The discriminator is whether the rule needs persistence state. If it reads only the instance, an accessor is honest. If it queries, if it involves another aggregate, or if it must be testable without a database, it is not model behaviour.

Do not add a relationship accessor that queries inside a loop. An accessor that calls $this->customer->name will lazy-load once per model in a collection. Either add the relation to the eager-load set in the caller, or compute the value in a resource after load().

4.4 Dirty tracking and change detection

How getDirty, isDirty, getOriginal and syncOriginal work, and the save-point semantics that make them correct.

Eloquent keeps two arrays per instance: $attributes (current values) and $original (values as of the last sync). The difference is the dirty set, computed by comparing casted values, not raw ones — which is why changing an attribute and setting it back to its original value correctly reports clean.

$invoice->total_cents = 5000;

$invoice->isDirty();                       // true
$invoice->isDirty('total_cents');           // true
$invoice->getDirty();                     // ['total_cents' => 5000]
$invoice->getOriginal('status');          // 'open'
$invoice->getRawOriginal('total_cents');   // 4500, uncast

$invoice->save();                          // UPDATE only dirty columns; original synced

$invoice->getChanges();                   // ['total_cents' => [4500, 5000]]

$invoice->refresh();                       // reload from DB, discard local changes
$invoice->syncOriginal();                  // treat current state as baseline, no query

Two rules keep this reliable. Never call syncOriginal() immediately after assigning a value — it discards the change and the value will never be persisted. And never build a dirty comparison across models by comparing attributes directly; use getOriginal() against the current value, which respects the cast pipeline.

Conditional updates are available when the change must be atomic against a concurrent writer.

// UPDATE ... SET status='paid' WHERE id=? AND status='open'  — one round trip,
// returns the number of rows actually affected.
$affected = Invoice::whereKey($id)
    ->where('status', 'open')
    ->update(['status' => 'paid']);

if ($affected === 0) {
    throw new InvoiceAlreadyPaid($id);
}

A mass update() bypasses model events, casts' set() for virtual attributes, and observers. It is the right tool for a bulk state change precisely because it is fast; it is the wrong tool if any registered observer must fire. Chapter 14 covers the performance profile of the alternative.

4.5 Model events and observers

The model event hierarchy, when events fire, and the operations that bypass them entirely.

Model events fire from save(), create(), update(), delete() and the corresponding mass operations updateQuietly(), deleteQuietly(), saveQuietly() suppress. The set is: retrieved, creating, created, updating, updated, saving, saved, replicating, deleting, deleted, forceDeleting, forceDeleted, restoring, restored, trashed.

5.1 Local and global scopes

How scopes compose, and the argument-passing convention that makes them chainable.

A local scope is a method whose name begins with scope. The first argument is the builder; the remaining arguments are whatever the caller passes. There is no return-type requirement that the method be a scope — any method named scope* with a leading builder parameter is callable directly as an instance method, which is useful.

final class class Order extends Model
{
    public function scopePlacedBetween(Builder $query, CarbonInterface $from, CarbonInterface $to): void
    {
        $query->whereBetween('placed_at', [$from, $to])
              ->where('status', '!=, 'cancelled');
    }

    public function scopeForCustomer(Builder $query, int $customerId): void
    {
        $query->where('customer_id', $customerId);
    }

    public function scopeOver(Builder $query, int $amountCents): void
    {
        $query->having('total_cents', '>', $amountCents);
    }
}

Order::query()
    ->forCustomer($customer->id)
    ->placedBetween($from, $to)
    ->orderByDesc('placed_at')
    ->paginate(25);

Global scopes are applied on every query for the model and are removed with withoutGlobalScopes(). They compose with orWhere in a way that surprises people: global scopes are parenthesised and OR-ed with the calling constraints. A global tenant scope plus a caller-supplied where() is safe; a global scope plus a caller-supplied orWhere() may widen it to rows outside the tenant. Never expose an orWhere to a scope chain that has a global scope applied.

Return void from scopes that mutate the builder, or return the builder for chaining. Declaring : void and mutating in place is the cleanest convention and it makes the scope impossible to misuse as a query. Declaring a Builder return type allows return $query->where(...);, which reads well. What does not work is returning a different query class and expecting it to be respected — it is, but only if the return type matches.

Named scopes introduced in 11.x compose better than a chain of method calls, because a single named scope is a parameterised, greppable unit in a log of the SQL. Both forms produce identical SQL; the difference is readability at the call site.

// A relation that is not a pure foreign key: correlated by a computed value.
public function recommendedProducts(): HasMany
{
    return $this->hasMany(
        Product::class,
        'id',          // local key on this table
        'category_id',  // foreign key on the related table
    )->where('active', true)
      ->orderBy('popularity_score', 'desc')
      ->limit(3);  // limit + eager load = 1 row per parent
}

// Use a HasManyThrough for a computed join.
public function invoices(): HasManyThrough
{
    return $this->hasManyThrough(
        Invoice::class,
        Subscription::class,
        'customer_id',  // FK on subscriptions
        'customer_id',  // FK on invoices
        'id',             // local key
        'id',             // local key on subscriptions
    );
}

A constraint on a hasMany relation that limits rows breaks eager loading. When a relation carries a limit(), the eager loader issues one whereIn query and then takes the first N rows in the order the database returned them, which is not per-parent. Either accept that the limit is applied per parent in lazy mode and per query in eager mode — a genuine correctness divergence — or use HasMany::limit()'s newer per-parent support where available, or model the relation as a correlated subquery in a resource. Test eager-loaded and lazy-loaded results side by side whenever a relation is constrained.

5.3 Eager loading correctly

The API for eager loading, the loadMissing variant that fixes N+1 in already-loaded graphs, and the strict-mode escape hatch.

with() must be called on the query, before retrieval. load() operates on an existing model or collection, issuing the same additional queries. loadMissing() does the same but skips relations already loaded — it is the correct call inside a service that receives an arbitrary model.

// 1 query for orders + 1 for customers + 1 for items = 3 total.
$orders = Order::query()
    ->with(['customer', 'items.product'])
    ->where('status', 'open')
    ->get();

// Constrained eager load: apply the closure to the eager query only.
$orders->load(['items' => fn (Builder $q) => $q->where('fulfilled', false)->select(['id', 'order_id', 'sku', 'quantity'])]);

// Aggregate count without loading the relation: adds a subselect column.
$orders = Order::withCount(['items as items_count'])
    ->withSum(['items as items_total_cents' => 'unit_price_cents'])
    ->withMax(['shipments as last_shipped_at' => 'shipped_at'])
    ->get();

withCount, withSum, withAvg, withMin, withMax and withExists all compile to a correlated scalar subquery in the SELECT list. They add no query count and avoid the N+1 entirely, which makes them strictly better than eager-loading a relation purely to count it.

preventLazyLoading() turns N+1 into a loud failure. Called in a non-production environment it throws LazyLoadingViolationException instead of issuing the query. Combined with Model::shouldBeStrict(! $this->app->isProduction()) in a test service provider, it makes missing eager loads a test failure rather than a production latency regression. Chapter 14 covers enabling it in production safely.

5.4 Aggregates, subqueries and window functions

Using the query builder for analytical SQL that Eloquent’s aggregates do not cover.

For conditional aggregation, the builder’s selectRaw and selectSub are the tools. Both are driver-portable only if the raw expressions are.

Order::query()
    ->select(['id', 'placed_at'])
    ->selectSub(
        Customer::query()
            ->selectRaw('COUNT(*)')
            ->whereColumn('customers.id', '=', 'orders.customer_id')
            ->where('orders.status', 'open'),
        'customer_open_orders'
    )
    ->selectRaw('COALESCE(SUM(total_cents), 0) AS gross_cents')
    ->where('placed_at', '>=', $since)
    ->groupBy(['id', 'placed_at'])
    ->having('gross_cents', '>=', 10_000)
    ->orderBy('gross_cents', 'desc')
    ->limit(100);

Window functions require selectRaw with a raw OVER clause, because the builder has no first-class API. PostgreSQL and MySQL 8 both support these; SQLite 3.25+ does too. Bind parameters inside selectRaw with the [$binding] array rather than concatenating values.

// Running total, LAG for period-over-period, and a moving average.
$rows = DB::table('daily_revenue')
    ->select(['day', 'revenue_cents'])
    ->selectRaw('SUM(revenue_cents) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total')
    ->selectRaw('LAG(revenue_cents) OVER (ORDER BY day) AS previous_day_cents')
    ->selectRaw('AVG(revenue_cents) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7d')
    ->orderBy('day')
    ->get();

whereColumn() compares two columns without binding the right-hand side as a value, which is the difference between a correlated subquery and a string literal. Using where('id', $customerId) inside a selectSub produces a constant subquery, not a correlated one — a bug that returns plausible-looking numbers.

Group by the full projection, not just the primary key. MySQL in ONLY_FULL_GROUP_BY mode and PostgreSQL both reject a SELECT column that is neither aggregated nor grouped. Listing the primary key alone is not portable if other selected columns are functionally dependent on it; enumerate every non-aggregated column in the groupBy, or let the database accept functional dependency if it can prove it.

5.5 Constraint encapsulation

Separating which rows a view needs from how it filters them, without reintroducing a generic repository.

The failure mode to avoid is a BaseRepository exposing findBy(array $filters) that assembles a query from caller-supplied keys. It moves the query into an object without moving the knowledge of what a valid filter is, and every caller still needs the model.

The alternative is to make the constraint the abstraction: a small, immutable, testable object that returns a configured builder. The model remains accessible to the caller, because Eloquent’s Active Record boundary is a feature, not a leak.

final readonly class class OrderSearch
{
    public function __construct(
        private DateTimeInterface|null $from = null,
        private DateTimeInterface|null $to = null,
        private ?OrderStatus $status = null,
        private ?int $customerId = null,
        private int $perPage = 25,
    ) {}

    public function applyTo(Builder $query): Builder
    {
        return $query
            ->when($this->from, fn (Builder $q, $d) => $q->where('placed_at', '>=', $d))
            ->when($this->to, fn (Builder $q, $d) => $q->where('placed_at', '<=', $d))
            ->when($this->status, fn (Builder $q, $s) => $q->where('status', $s->value))
            ->when($this->customerId, fn (Builder $q, $c) => $q->where('customer_id', $c))
            ->orderByDesc('placed_at');
    }

    public function cursor(): LazyCollection
    {
        return Order::query()->with('customer')->tap(fn (Builder $q) => $this->applyTo($q))
            ->cursor();
    }
}

$paginator = (new OrderSearch(status: OrderStatus::Open))->applyTo(Order::query())->paginate($search->perPage);

Use cursorPaginate() for unbounded traversals. Offset pagination issues LIMIT 50000 OFFSET 100000, which makes the database count and discard 50,000 rows. Cursor pagination keys on the last seen row, is O(limit) regardless of depth, and is stable under concurrent inserts. It has no page numbers, so it belongs in an API or an infinite scroll, not a Blade paginator.

6.1 Schema defaults and portability

The schema API surface, the drivers it generates for, and the defaults that differ between them.

Schema::create() and Schema::table() compile to engine-specific DDL through Illuminate\Database\Schema\Grammars\MySqlGrammar, PostgresGrammar or SQLiteGrammar. The same method call can produce a table copy, an in-place ALTER, or a full schema rebuild depending on the driver — and the rebuild case is why a migration that works locally on SQLite can take an exclusive lock on production MySQL.

Run migrations against the production engine, not SQLite. The SQLite grammar rebuilds the table for almost every alteration, which hides both the locking behaviour and the incompatibility. At minimum, run the full migration set against MySQL in CI, and use --pretend against production to see the exact DDL before applying it.

The Schema::defaultStringLength(191) call historically existed to stay under MySQL’s 767-byte index prefix limit with utf8mb4. MySQL 5.7 with innodb_large_prefix, and every supported version from 5.7.7 onward, support 3072-byte prefixes. If the call is still present in AppServiceProvider::boot() it is dead configuration and can be removed; keep it only if the application genuinely targets an ancient MySQL.

6.2 Online DDL per database engine

Which algorithm each engine chooses for each alteration, and how to force the online one.

Both MySQL and PostgreSQL support non-blocking schema changes, but only if you ask. The framework’s builder does not emit the locking-clause hints, so the decision is made in the session by setting the instance variable or the lock timeout.

EngineSettingEffect
MySQL 8SET SESSION lock_wait_timeout = 5Fail fast rather than queue behind a long-running transaction
MySQL 8ALGORITHM=INPLACE, LOCK=NONEAbort if the change cannot be done in place; forces a maintenance window instead of a silent copy
MySQL 8.0.29+ALGORITHM=INSTANTMetadata-only for supported column operations
PostgreSQL 16SET lock_timeout = '5s'Abort instead of blocking behind a conflicting ACCESS EXCLUSIVE request
PostgreSQL 16SET statement_timeout = '0'Allow a legitimately long index build to run to completion

To emit the MySQL algorithm clause, run raw statements through DB::statement() inside the migration rather than through the builder.

use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Schema;

final class class AddIndexesToOrders extends Migration
{
    public function up(): void
    {
        if (DB::getDriverName() === 'mysql') {
            DB::statement('SET SESSION lock_wait_timeout = 5');
        }

        if (Schema::hasTable('orders') && ! Schema::hasIndex('orders', ['customer_id', 'placed_at'])) {
            if (DB::getDriverName() === 'mysql') {
                // Abort if MySQL would need to copy the table under a lock.
                DB::statement(
                    'ALTER TABLE orders ADD INDEX orders_customer_placed (customer_id, placed_at), ALGORITHM=INPLACE, LOCK=NONE'
                );
            } elseif (DB::getDriverName() === 'pgsql') {
                // CREATE INDEX CONCURRENTLY cannot run inside a transaction.
                DB::statement('SET lock_timeout = "5s"');
                DB::unprepared(
                    'CREATE INDEX CONCURRENTLY orders_customer_placed ON orders (customer_id, placed_at)'
                );
            } else {
                Schema::table('orders', function (Blueprint $table) {
                    $table->index(['customer_id', 'placed_at']);
                });
            }
        }
    }

    public function down(): void
    {
        // Intentionally no-op: dropping an index on a large table locks it.
        // Schedule the drop for a maintenance window instead.
    }
}

CREATE INDEX CONCURRENTLY cannot run inside a transaction, and PostgreSQL migrations are transactional by default. Either set public $withinTransaction = false; on the migration class — supported for MySQL, MariaDB, SQLite and PostgreSQL since 8.x — or accept a blocking index build on a small table. A failed concurrent build also leaves an INVALID index that must be dropped manually.

6.3 The expand/contract sequence

The four-release pattern that keeps a schema change compatible with both the deployed and the incoming version of the code.

The constraint is this: at every moment, the running application and the database schema must agree. A migration that renames a column in the same deploy that changes the code that reads it violates this, because for a window of minutes the old code queries a column that no longer exists and the new code queries one that has not been applied yet.

The pattern splits every change into expand, migrate, contract, with at least one deploy between each phase.

PhaseSchemaCodeDeploys
ExpandAdd the new structure alongside the old. No column dropped, no column renamed.No change, or change reads from the new column if it is already backfilled and defaults correctly1
MigrateBackfill in batches, outside a single long transactionWrite to both columns; read from the new one1
ContractDrop the old columnRead and write only the new column1
// Release 1 — EXPAND. Additive only, safe to run with the old code live.
final class class AddBillingAddressToCustomers extends Migration
{
    public function up(): void
    {
        Schema::table('customers', function (Blueprint $table) {
            // Nullable so existing rows and old INSERT statements both work.
            $table->jsonb('billing_address')->nullable();
        });
    }

    public function down(): void
    {
        Schema::table('customers', function (Blueprint $table) {
            $table->dropColumn('billing_address');  // new column, safe
        });
    }
}

The key discipline: the expand migration must be deployable before any code that depends on it, and must not break the code that is currently running. An additive nullable column satisfies both. A column with a NOT NULL constraint and no default does not, because the deployed version’s inserts will fail the moment the migration runs.

// Release 2 — MIGRATE. Dual-write in application code, backfill in batches.
final class class UpdateCustomerBillingAddress extends Migration
{
    public function up(): void
    {
        // Batched, restartable, and each batch commits independently.
        DB::table('customers')
            ->whereNull('billing_address')
            ->orderBy('id')
            ->chunkById(500, function (Collection $customers) {
                foreach ($customers as $customer) {
                    DB::table('customers')
                        ->where('id', $customer->id)
                        ->update(['billing_address' => json_encode([
                            'line1' => $customer->address_line_1,
                            'city'  => $customer->address_city,
                            'country' => $customer->address_country,
                        ])]);
                }
            });
    }

    public function down(): void
    {
        // Irreversible by design; document it in the class docblock.
    }
}

Never put a large backfill in a migration’s up(). Migrations run inside a transaction on PostgreSQL, so a multi-million-row backfill holds locks for its entire duration and the migrations table row stays uncommitted, which means a second deploy process will try to run it again. A separate, idempotent, resumable command run by the deploy script is the correct home for data work.

6.4 The zero-downtime column pattern

Renaming or retyping a column without a maintenance window, using a shadow column and a view.

Renaming is the operation most often done in a single deploy and most often responsible for an outage. The pattern replaces the rename with an add, a dual-write, a backfill and a final switchover that changes no column name at all.

// Step 1: add the new column, backfilled but nullable.
Schema::table('orders', function (Blueprint $table) {
    $table->unsignedBigInteger('customer_ref')->nullable()->index();
});

// Step 2: dual-write from the model, both directions, for one release.
final class class Order extends Model
{
    protected static function booted(): void
    {
        static::saving(function (Order $order) {
            $order->customer_ref ??= $order->customer_id;
        });
    }
}

// Step 3: switch reads, keep dual-writing. Step 4: drop the old column.

For a type change on a hot table, the same principle applies with a generated column: add a new column of the target type, backfill in batches, add a trigger or dual-write, switch reads, drop the old column and the trigger. The trigger is the only option that also covers writers the application does not control — an ETL job, a manual UPDATE, a second application instance running older code.

Adopt a naming convention for migration phase in the filename. A suffix such as _add_, _backfill_, _drop_ makes the sequence legible in a directory listing and makes it obvious from the filename alone whether a migration is safe to run against a live system. Some teams maintain the convention in a CI check.

6.5 Adding constraints to live tables

Why a foreign key or unique constraint added to a large table is a long-running lock, and the online options.

Adding a foreign key or unique constraint requires the engine to validate every existing row. MySQL 8 supports this online with ALGORITHM=INPLACE, LOCK=NONE for foreign keys, using the online InnoDB log. Unique constraint validation, however, is always performed with a table scan under at least a shared lock in MySQL 8.0; only MySQL 8.0.16+ can add a unique index online, and the constraint check itself still scans.

// Safe pattern: create the index first (online), then add the constraint
// and accept that validation scans the table. Run off-peak.

php artisan tinker
DB::statement('ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
    FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,
    ALGORITHM=INPLACE, LOCK=NONE');

The pragmatic sequence for a large table is: create a unique index concurrently, add the foreign key with the online algorithm, and set lock_wait_timeout low so a contended window aborts the migration and retries rather than queueing every subsequent query behind it. For a truly large table, a hard constraint is often better expressed in application code plus a periodic audit job than applied during a release.

Validate migrations against production-sized data, not production. A migration that takes 200 ms on 500 rows can take 40 minutes and hold a lock on 50 million rows. Test with a table of representative row count and width, and set the lock_wait_timeout in every migration that alters a large table so that a contended deploy fails fast and visibly instead of cascading a queue of blocked queries through the connection pool.

7.1 Events, listeners and discovery

The listener API, the ShouldQueue contract, and how listener discovery reduces boilerplate.

An event is a plain class, usually a readonly DTO describing something that happened. A listener is a class with a handle() method. Adding ShouldQueue moves execution to a worker and requires the job’s properties to be serializable — which is the reason event payloads must be value objects, never Eloquent models.

namespace App\Domain\Billing\Events;

final readonly class class InvoiceIssued
{
    public function __construct(
        public int $invoiceId,
        public int $customerId,
        public int $totalCents,
        public CarbonImmutable $issuedAt,
    ) {}
}

namespace App\Domain\Billing\Listeners;

final class class SendInvoiceEmail implements ShouldQueue
{
    use Dispatchable, InteractsWithSockets, SerializesModels;

    public function __construct(
        public int $batchSize = 100,
    ) {}

    public function handle(InvoiceIssued $event, Mailer $mailer): void
    {
        Invoice::query()
            ->with('customer')
            ->findOrFail($event->invoiceId)
            ->tap(fn (Invoice $i) => $mailer->to($i->customer->email)->send(new InvoiceIssuedMail($i)));
    }
}

// Register the listener. Queued via the interface or the $listen queue arg.
EventServiceProvider::listen(): void
{
    Event::listen(InvoiceIssued::class, SendInvoiceEmail::class)->shouldQueue();
}

Listener auto-discovery in 11.x+ removes the EventServiceProvider for the common case: Laravel scans app/Listeners and matches the type-hinted event in handle(). The generated bootstrap/app.php uses withEvents(discover: [__DIR__.'/../app/Listeners']) when the method is called with no arguments. Auto-discovery is opt-in and does not apply to listeners in other namespaces.

// Explicit discovery path (and where discovery is off by default)
->withEvents(discover: [
    __DIR__.'/../app/Listeners',
    'App\Infrastructure\Listeners' => ['App\Listeners'],  // map namespace
])

// A listener that must not be queued keeps no queue interfaces.
final class class WriteAuditEntry
{
    public function handle(InvoiceIssued $event): void
    {
        AuditLog::create(['event' => 'invoice.issued', 'subject_id' => $event->invoiceId]);
    }
}

Events and commands are different things. A domain event states a fact in the past tense and may have zero, one or many listeners. A command requests an action and has exactly one handler. Dispatching a command as an event makes the "exactly one" guarantee unenforceable, and dispatching an event as a command makes the intent unreadable. Chapter 8 separates them formally.

7.2 Dispatching and the queue contract

The connection, queue and driver configuration hierarchy, and the payload format that crosses the process boundary.

// config/queue.php — precedence is connection, then queue, then the 'default' connection
'default' => env('QUEUE_CONNECTION', 'database'),

'connections' => [
    'redis' => [
        'driver' => 'redis',
        'connection' => 'default',
        'queue' => env('REDIS_QUEUE', 'default'),
        'retry_after' => null,   // defaults to visibility_timeout + 60
        'block_for' => null,
        'after_commit' => false,
        'fail_on_timeout' => false,
    ],
],

retry_after is the single most consequential setting in the file. It is the number of seconds after which a job is considered abandoned and made available to another worker. If a job runs longer than retry_after, a second worker will pick it up while the first is still processing — silently executing the same work twice. The rule is: retry_after must exceed the job’s maximum possible runtime by a wide margin, and the worker’s --timeout must be less than retry_after.

Horizon is not a queue driver; it is a worker manager that uses the Redis driver and overrides retry_after with 90 plus the timeout configured in config/horizon.php. A job that can run for more than 90 seconds will double-execute under Horizon even though config/queue.php says retry_after is 600. Chapter 16 covers Horizon’s timeout model in full.

7.3 After-commit dispatch and transactions

Why a job dispatched inside a transaction may execute before the commit, and the two ways to prevent it.

Without any configuration, a job dispatched inside a database transaction is pushed to Redis immediately. A fast worker can pick it up and query for a row that the transaction has not yet committed — the job throws, retries, and depending on the retry count, may fail permanently. This is the "job dispatched before commit" race, and it is a production-only bug because local queues run synchronously inside the request.

// Option A — global default in config/queue.php
'after_commit' => true,

// Option B — per dispatch, independent of configuration
SendInvoiceEmail::dispatch($invoiceId, $customerId, $total, $issuedAt)
    ->afterCommit();

// Option C — per job class, the most explicit and the recommended default
final class class GenerateInvoicePdf implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public bool $afterCommit = true;
}

Option C is preferred because the guarantee travels with the job rather than depending on an environment variable. A job configured after-commit locally because tests run in transactions and not configured in production is a job that fails only in production.

DB::transaction(function () {
    $invoice = Invoice::create([/* ... */]);

    foreach ($invoice->lines as $line) {
        ReserveStock::dispatch($line->sku, $line->qty);
    }

    InvoiceIssued::dispatch($invoice->id, $invoice->customer_id, $invoice->total_cents, now()->toImmutable());
});
// Every dispatch above fires only after the outer commit succeeds.

If there is no active transaction, afterCommit() dispatches immediately — the callback is invoked synchronously by the transaction manager. This means the same code is correct whether or not the caller happened to wrap it in a transaction, which is why the setting is safe to enable globally.

7.4 Batches, chunks and chains

The three primitives for multi-job work, and what each guarantees about failure.

A batch tracks a set of jobs and reports when all have finished. A chain enforces sequence. A chunk splits a large collection into groups dispatched as a chain or batch. They compose, and choosing the wrong one produces either a memory blowup or an unbounded fan-out.

use Illuminate\Bus\Batch;
use Illuminate\Support\Facades\Bus;

// Chunked: 50k rows become 100 chained jobs, each dispatching the next.
$customers = Customer::query()->select(['id', 'email', 'name']);

$batch = Bus::batch($customers)
    ->allowFailures()
    ->finally(function (Batch $batch) {
        Log::info('import complete', [
            'pending' => $batch->pendingJobs(),
            'failed'  => $batch->failedJobs(),
            'total'   => $batch->totalJobs,
        ]);
    })
    ->name('customer-import-2026-03')
    ->dispatch();

// Manually composed: one job per chunk, chained sequentially.
$jobs = $customers->chunk(500)->map(fn (Collection $rows) => new ImportCustomers($rows->pluck('id')->all()));
Bus::chain($jobs)->dispatch();

// Chain with a conditional stop and a guaranteed cleanup.
Bus::chain([
    new ExtractSourceData,
    new TransformRows,
    new LoadIntoWarehouse,
    new FinalizeImport,
])->name('nightly-etl')->onQueue('low')->dispatch();

A batch’s job list is held in the job_batches table — one row per batch plus one per job — and pruned by queue:prune-batches. A batch of 50,000 jobs therefore writes 50,000 rows. For a large import, either increase the chunk size or use a self-dispatching chain where each job reads the next batch from the database, keeping the batch table to one entry per chunk.

PrimitiveConcurrencyFailure semantics
BatchAll jobs at once, up to the worker poolAll continue unless allowFailures() is absent; batch fails if any job fails
ChainStrictly sequentialStops at the first failure unless catch() is set per link
Chain of batchesSequential batches, parallel jobs withinSame as each batch

Chunks, not all(). Bus::batch(Model::all()) materialises the entire table in memory and then serialises a job per row. Bus::batch($query) accepts a query builder or a lazy collection and chunks it internally, which is the documented approach for anything beyond a few thousand rows.

7.5 Designing for redelivery

The at-least-once delivery guarantee, and the three techniques that make a listener safe to run twice.

Laravel’s queues guarantee at-least-once delivery, not exactly-once. A job can be executed twice if a worker dies after the work completed but before the acknowledgement, if retry_after elapses during a long run, or if a deployment terminates a worker mid-job and the job becomes available again. Every job and every queued listener must be written as if it will run twice, because sometimes it will.

final class class ChargeInvoice implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 5;
    public int $timeout = 60;
    public bool $afterCommit = true;

    public function backoff(): array
    {
        return [10, 60, 300, 900];   // seconds; or [10, 5] means 10, 15, 20
    }

    public function handle(PaymentGateway $gateway, DB $db): void
    {
        // 1. Lock the invoice row. A second execution blocks, then finds it closed.
        $charged = false;

        $db->transaction(function () use (&$charged, $gateway) {
            $invoice = Invoice::query()
                ->whereKey($this->invoiceId)
                ->lockForUpdate()
                ->firstOrFail();

            if ($invoice->status === InvoiceStatus::Paid) {
                $charged = true;

                return;
            }

            $gateway->charge(new ChargeRequest(
                amount: Money::fromMinor($invoice->total_cents, Money::of($invoice->currency)),
                // 2. A stable idempotency key, derived from data, not from a random value.
                idempotencyKey: 'invoice-'.$invoice->id.'-v1',
            ));

            $invoice->forceFill([
                'status'          => InvoiceStatus::Paid,
                'paid_at'         => now(),
                'provider_charge_id' => true,  // placeholder replaced below
            ])->save();
        });

        // 3. Nothing left to do if it was already paid.
        if ($charged) {
            $this->release(5);  // or simply return

            return;
        }
    }

    public function failed(Throwable $e): void
    {
        Alerting::critical('ChargeInvoice permanently failed', [
            'invoice_id' => $this->invoiceId, 'error' => $e->getMessage(),
        ]);
    }
}

The three techniques are: a stable idempotency key passed to any external API, a database unique constraint as the final arbiter, and a row lock or conditional update around the state transition. Used together they make a duplicate execution a no-op rather than a duplicate charge.

A unique constraint beats a firstOrCreate check. firstOrCreate performs a SELECT then an INSERT, which is a race under concurrency — two workers both see no row and both insert. A unique index on the natural key makes the second insert fail deterministically; catch the QueryException and treat it as success. Use upsert() where the semantics allow overwriting.

Retry only transient failures. public function retries(): int overrides the attempt count at runtime, and the ThrottlesExceptions or a catch block that returns without rethrowing ends the attempt chain. Retrying a validation failure 5 times wastes 15 minutes of worker time and tells you nothing. Reserve retries for timeouts, 429s and 5xx responses; send a validation failure to the failed-jobs table immediately.

HTTP is a transport. A controller that contains a business rule has collapsed the first two boundaries. A model that reads an environment variable has collapsed the second and third. Neither is fatal, but both are the point at which a change becomes expensive.

The test that decides: if the rule must be enforced from a console command, a queued job, an Artisan command and an HTTP endpoint, it does not belong in any one of them. It belongs somewhere all four can reach.

8.3 Actions as the transaction boundary

A single-purpose invokable class that owns one use case, one transaction and one set of side effects.

An action is an invokable class with a name that reads as a use case, a single public __invoke, and no interface. It is the unit of work: it opens the transaction, performs the state change, and dispatches the consequences.

namespace App\Domain\Billing\Actions;

final readonly class class IssueInvoice
{
    public function __construct(
        private DB $db,
        private LedgerService $ledger,
        private NumberSequence $numbers,
    ) {}

    public function __invoke(IssueInvoiceData $data): Invoice
    {
        return $this->db->transaction(function () use ($data) {
            $invoice = Invoice::create([
                'number'       => $this->numbers->next('invoice'),
                'customer_id'   => $data->customerId,
                'currency'     => $data->currency->value,
                'subtotal_cents' => $data->subtotal->minor,
                'vat_cents'     => $data->vat->minor,
                'total_cents'    => $data->total->minor,
                'issued_at'     => $data->issuedAt,
                'status'        => InvoiceStatus::Open,
            ]);

            $invoice->lines()->createMany($data->lines);

            // Invariant checked before commit, inside the same transaction.
            $this->ledger->assertBalanced($invoice);

            // afterCommit on the job class means this is safe.
            GenerateInvoicePdf::dispatch($invoice->id);

            return $invoice;
        });
    }
}

The signature is deliberately not the Eloquent model. IssueInvoiceData is a readonly DTO, so the action can be called from a controller, a console command, a queued job or a test with no transport dependency. The action returns a model because the caller frequently needs the identifier and a freshly-loaded relation; that is a pragmatic asymmetry, and it is honest about the Active Record boundary the framework already has.

One action, one transaction. If an action needs a second transaction it needs a second action. Nested transactions in Laravel are savepoints, not independent commits, so a "two-phase" action inside one DB::transaction() does not give the isolation the name implies. Chapters 7 and 8 both depend on this being true.

8.4 When a service layer is justified

The criteria that distinguish a real service from a class that exists to hold methods.

A service earns its name when at least one of these holds.

  • It has state or configuration of its own — a client, a rate limit, a cache, a compiled rule set.
  • It is shared by more than one caller, so that duplicating it would mean duplicating a rule.
  • It is a port to something outside the application — an HTTP API, a queue broker, a payment provider, a filesystem.
  • It exists to be faked in tests, which is only valuable if the real thing is slow, non-deterministic or has side effects.

What does not qualify: a class wrapping one model with pass-through methods; a class constructed only to satisfy a dependency count; a UserService whose only method is getUserById.

final readonly class class StripeGateway implements PaymentGateway
{
    public function __construct(
        private Client $stripe,
        private LoggerInterface $logger,
    ) {}

    public function charge(ChargeRequest $request): ChargeResult
    {
        try {
            $intent = $this->stripe->paymentIntents->create([
                'amount'         => $request->amount->minor,
                'currency'       => $request->amount->currency->value,
                'idempotency_key' => $request->idempotencyKey,
                'metadata'       => ['invoice_id' => $request->reference],
            ], ['idempotency_key' => $request->idempotencyKey]);
        } catch (CardException $e) {
            $this->logger->warning('card declined', ['code' => $e->getStripeCode()]);

            return ChargeResult::declined($e->getStripeCode(), $e->getMessage());
        }

        return ChargeResult::succeeded($intent->id);
    }
}

The PaymentGateway interface is a port; StripeGateway is an adapter. The domain depends on the port. The concrete adapter is bound in a service provider and faked in tests. This is dependency inversion applied to exactly one boundary, which is where it pays for itself.

Register the port binding in a provider, not in the consumer. Binding PaymentGateway to StripeGateway inside IssueInvoice would make the action untestable without a Stripe key and would make the coupling invisible. Binding it in AppServiceProvider::register() with bindIf() makes it a documented, overridable extension point.

8.5 Aggregates and consistency

Choosing the transaction boundary, and what Laravel gives you to enforce a consistency boundary without a full DDD implementation.

An aggregate is a consistency boundary: a set of objects that must change together or not at all. In Laravel the mechanism is a foreign key plus a transaction, and the decision is which child rows belong inside the parent’s boundary.

RelationshipSame aggregate whenSeparate aggregate when
Invoice to InvoiceLineThe line has no meaning without the invoice; the total is derived from themThe line is reused across invoices
Invoice to PaymentAlways separate — a payment is a fact about money moving, made in its own right—
Order to ShipmentSeparate once a shipment can be created by a different actor or on a different dayThe shipment is a status field on the order

What Laravel provides directly: DB::transaction() with retry on deadlock, lockForUpdate() for pessimistic locking, Model::withoutTimestamps() for batch writes, and a migrations table as the sequencing mechanism. What it does not provide and is not worth adding: unit-of-work tracking, identity maps, domain event sourcing. Chapter 5 covers the query performance implications of the choice.

DB::transaction(function () {
    Order::query()
        ->whereKey($orderId)
        ->lockForUpdate()
        ->firstOrFail()
        ->transitionTo(OrderState::Paid, $paymentId);
}, attempts: 3);

// The retry count matters: deadlock is a normal outcome under concurrency,
// and a bare transaction() surfaces it as a user-facing 500.

An aggregate that must be loaded and locked as a unit can become a scalability bottleneck. A single row that every transaction must lock, such as a per-customer balance or a per-SKU stock count, is a serialisation point whose throughput is bounded by the row’s lock hold time. Two mitigations, both worth having: keep the critical section to a single UPDATE ... SET stock = stock - ? statement, which takes the lock and releases it in one round trip, or shard the row by warehouse or bucket so contention is spread.

9.1 DTOs at the transport boundary

What a boundary DTO is for, and why the request array is not an acceptable substitute.

An HTTP request is an untyped bag of strings. Passing that bag into an action makes the action responsible for knowing the shape, which is exactly the coupling the boundary was meant to remove. A DTO at the boundary makes the shape a type: the action’s signature is the contract, and an ArgumentCountError or a TypeError replaces a silent null deep in the call stack.

namespace App\Domain\Billing\Data;

final readonly class class IssueInvoiceData
{
    public function __construct(
        public int $customerId,
        public Money $subtotal,
        public Money $vat,
        public Money $total,
        public CarbonImmutable $issuedAt,
        public Collection $lines,
    ) {}

    public static function fromArray(array $data): self
    {
        $currency = Currency::from($data['currency']);
        $subtotal = Money::fromMinor((int) $data['subtotal_cents'], $currency);
        $vat      = Money::fromMinor((int) $data['vat_cents'], $currency);

        return new self(
            customerId: (int) $data['customer_id'],
            subtotal:    $subtotal,
            vat:         $vat,
            // Derived, never trusted from the client.
            total:       $subtotal->plus($vat),
            issuedAt:    CarbonImmutable::parse($data['issued_at']),
            lines:       Collection(array_map(fn (array $l) => new InvoiceLineData(
                sku:       $l['sku'],
                quantity:  (int) $l['quantity'],
                unitPrice: Money::fromMinor((int) $l['unit_price_cents'], $currency),
            ), $data['lines']),
        );
    }
}

The rule that makes DTOs worth their cost: values the client must not control are derived here, not read. The example above computes total from the components. A DTO that accepts total_cents from the request and passes it to the action has moved the business rule into an attacker-reachable location.

Do not use spatie/laravel-data or a DTO factory in the inner loop. A reflection-based hydrator is convenient and slow, and it works by bypassing the constructor. For a boundary DTO, an explicit fromArray() is faster, greppable and fails loudly on a missing key. In production code, prefer the explicit factory.

9.2 Mapping and hydration

Keeping the mapping in one place, and the two failure modes of an ad-hoc mapper.

Ad-hoc mapping fails in two ways. It leaks types — a method annotated int receives a string, and PHP coerces it silently in non-strict mode. And it duplicates — the same field is mapped differently in a controller, a console command and a seeder, and the three drift.

Declare strict types in every DTO file. This converts every silent coercion into a TypeError at the point of the mistake.

// Declare(strict_types=1); at the top of every DTO and action file.
declare(strict_types: 1);

namespace App\Infrastructure\Persistence\Hydration;

final class class OrderRowHydrator
{
    public function fromRow(object $row): OrderSnapshot
    {
        return new OrderSnapshot(
            id: (int) $row->id,
            placedAt: CarbonImmutable::parse((string) $row->placed_at, 'UTC'),
            total: Money::fromMinor((int) $row->total_cents, Currency::from($row->currency)),
            status: OrderStatus::from($row->status),
        );
    }

    public function manyFromRows(Collection $rows): Collection
    {
        return $rows->map(fn (object $r) => $this->fromRow($r));
    }
}

// Used with the query builder for read models that need no hydration.
$rows = DB::table('orders')->where('id', $id)->first();
$snapshot = $hydrator->fromRow($rows);

A read model that is never written through Eloquent does not need a model class. A plain object hydrated from a DB::table() row is faster, has no events, no accessors and no dirty tracking, and cannot accidentally be saved. This is the appropriate shape for analytics queries, exports and API projections.

9.3 Form requests as a boundary

Authorisation and validation in one authorised, cacheable, testable unit.

A form request extends Illuminate\Foundation\Http\FormRequest. Its rules() method runs before the controller method, and its authorize() method runs before that. Failure produces a 403 or a 422 without the controller ever executing.

namespace App\Http\Requests\Billing;

final class class IssueInvoiceRequest extends FormRequest
{
    public function authorize(): bool
    {
        return $this->user()?->can('issue-invoice') ?? false;
    }

    public function rules(): array
    {
        return [
            'customer_id'          => ['required', 'integer', Rule::exists('customers', 'id')->where('tenant_id', $this->user()->tenant_id)],
            'currency'             => ['required', 'string', 'size:3', Rule::in(['EUR', 'GBP', 'USD'])],
            'issued_at'            => ['required', 'date_format:Y-m-d\TH:i:sP', 'before_or_equal:now'],
            'lines'               => ['required', 'array', 'min:1', 'max:200'],
            'lines.*.sku'          => ['required', 'string', 'max:64', 'regex:/^[A-Z0-9-]+$/'],
            'lines.*.quantity'      => ['required', 'integer', 'min:1', 'max:9999'],
            'lines.*.unit_price_cents' => ['required', 'integer', 'min:0', 'max:100000000'],
            'lines.*.vat_rate'      => ['sometimes', 'numeric', 'between:0,1'],
        ];
    }

    public function withValidator(Validator $validator): void
    {
        $validator->after(function (Validator $validator) {
            $lines = $this->input('lines', []);

            if ($lines !== [] && count(array_unique(array_column($lines, 'sku'))) !== count($lines)) {
                $validator->errors()->add('lines', 'Duplicate SKUs are not allowed in one invoice.');
            }
        });
    }

    public function toIssueInvoiceData(): IssueInvoiceData
    {
        return IssueInvoiceData::fromArray([
            ...$this->validated(),
            'subtotal_cents' => $this->subtotalCents(),
            'vat_cents'      => $this->vatCents(),
        ]);
    }

    private function subtotalCents(): int
    {
        return array_sum(array_map(
            fn (array $l) => $l['unit_price_cents'] * $l['quantity'],
            $this->input('lines'),
        ));
    }

    private function vatCents(): int
    {
        return (int) round($this->subtotalCents() * $this->input('vat_rate', config('billing.default_vat_rate', 0.21)));
    }
}

validated() returns only the keys declared in rules(), which is a real security property: any key not in the rules is not in the validated array, so a client-supplied tenant_id or total_cents cannot reach the DTO even if the controller passes $request->all(). Always pass $request->validated() or the DTO — never $request->all().

exists: rules are queries. A form request with six Rule::exists() rules issues six count queries per request, plus one for any unique rule. They run on every validation attempt including the failing ones. For a hot endpoint, replace with a cached list of valid identifiers or a batched check in an after() hook.

// The three forms of the exists rule that matter in practice.
'customer_id' => ['required', Rule::exists('customers', 'id')->where('tenant_id', $tenantId)],

// Soft-deleted rows are not valid references unless withTrashed().
'parent_id' => ['nullable', Rule::exists('categories', 'id')->whereNull('deleted_at')->where('parent_id', '!=', $this->route('category')?->id)],

// Partial unique: only one open invoice per customer, many historical ones.
'customer_id' => ['required', Rule::unique('invoices', 'customer_id')
    ->where('status', 'open')
    ->ignore($this->route('invoice')?->id)],

// Enum membership without a query.
'status' => ['required', Rule::enum(InvoiceStatus::class)],

// Conditional rules, evaluated only when the field is present.
'vat_number' => ['required_if:country,NL', 'nullable', 'string', Rule::unique('customers')->ignore($this->user()->id)],

A unique rule is advisory, not a guarantee. It is a SELECT performed before the INSERT, so two concurrent requests can both pass it. The database constraint is the only thing that actually guarantees uniqueness. Keep both: the rule produces a 422 with a useful message, the constraint produces the integrity guarantee. Catch the QueryException for the duplicate and translate it to the same 422 so the user sees one consistent failure shape.

9.5 Error responses and failure modes

The exception-to-response pipeline, the 422 shape, and the errors that must never reach a client.

In 11.x and later, exception rendering is configured in bootstrap/app.php through the withExceptions() callback rather than an App\Exceptions\Handler subclass.

->withExceptions(function (Exceptions $exceptions) {
    $exceptions->shouldRenderJsonWhen(
        fn (Request $request, Throwable $e) =>
            $request->is('api/*') || $request->expectsJson()
    );

    $exceptions->render(function (InvoiceAlreadyVoided $e) {
        return response()->json([
            'type'   => 'https://api.example.com/problems/invoice-already-voided',
            'title'  => 'Invoice is already voided',
            'status' => 409,
            'detail' => $e->getMessage(),
            'invoice_id' => $e->invoiceId,
        ], 409, ['Content-Type' => 'application/problem+json']);
    });

    $exceptions->render(function (AuthenticationException $e, Request $request) {
        if ($request->expectsJson()) {
            return response()->json(['message' => 'Unauthenticated.'], 401);
        }

        return null;  // fall through to the default redirect
    });

    $exceptions->dontReport([NotFoundHttpException::class]);
    $exceptions->report(function (Throwable $e) { /* Sentry, Bugsnag */ });
})

The default JSON validation failure is a 422 with message and errors. Three status codes are worth being deliberate about, because clients branch on them.

StatusMeaningClient expectation
400Malformed syntax, unparseable JSONDo not retry unchanged
401No or invalid credentialsRefresh token and retry once
403Authenticated but not permittedDo not retry; surface to user
404Resource does not exist, or the caller may not know it existsStop
409State conflict — duplicate, already transitionedRefetch and reconcile
422Well-formed but semantically invalidShow field errors
429Rate limitedHonour Retry-After

Never surface an exception message to a client without reviewing it. A QueryException message contains the full SQL and its bindings, including the bound values — which for an authentication query is the submitted email and a password hash. Registering a render for QueryException that returns a fixed 500 body, and logging the detail server-side, is not optional. The same applies to HttpException from a third-party SDK, whose bodies can include request headers.

$exceptions->render(function (QueryException $e) {
    Log::error('database error', [
        'sql'       => $e->getSql(),
        'bindings'  => $e->getBindings(),
        'message'   => $e->getMessage(),
        'trace_id'  => Context::get('trace_id'),
    ]);

    return response()->json(['message' => 'A database error occurred.'], 500);
});

Use problem details for anything a client must branch on. The RFC 9457 shape — type, title, status, detail — is stable, machine-readable and self-documenting. A bare {"error": "invalid"} forces every client to hard-code string matching, which breaks silently when the message is reworded.

10.1 Session and token authentication

The default guard, what Laravel 13 ships out of the box, and the setup Laravel Breeze or Fortify adds.

A default 13.x install provides one user model, one guard (web, session-based) and no token support. Session authentication is cookie plus server-side session state; the cookie is signed and encrypted, and the identifier is a 40-character random string. Laravel 11+ ships Sanctum in the default composer.json, so the token guard is available without an additional install.

// config/auth.php — 11+ slim skeleton. Uncomment for a multi-guard setup.
'guards' => [
    'web' => ['driver' => 'session', 'provider' => 'users'],
],
'providers' => [
    'users' => ['driver' => 'eloquent', 'model' => App\Models\User::class],
],
'passwords' => [
    'users' => ['provider' => 'users', 'table' => 'password_reset_tokens', 'expire' => 60, 'throttle' => 60],
],

Hashing uses Hash::make(), which defaults to Bcrypt at cost 12. Argon2id via Hash::argon2id() is the recommended alternative where the PHP extension is available and the deployment is not memory-constrained; Bcrypt’s 72-byte input limit requires pre-hashing if longer passphrases must be supported.

Use Hash::check(), never Hash::make() then a comparison. Comparing hashes directly is both wrong — the salt makes the strings differ every time — and, if done with ===, timing-variable. Hash::check() uses password_verify(), which is constant-time. Rehash transparently on successful login with Hash::needsRehash() when the cost factor changes.

if (Hash::check($plain, $user->password)) {
    if (Hash::needsRehash($user->password)) {
        $user->forceFill(['password' => Hash::make($plain)])->saveQuietly();
    }

    Auth::login($user, remember: true);
    $request->session()->regenerate();  // mandatory: prevents session fixation

    return redirect()->intended(RouteServiceProvider::HOME);
}

RateLimiter::hit($request->ip(), 60);  // or Illuminate\Support\Facades\RateLimiter
throw new ValidationException::withMessages([
    'email' => ['These credentials do not match our records.'],
]);

Regenerate the session identifier on every privilege change. Login, logout and password change must all call $request->session()->regenerate() and invalidate() respectively. Without it, an attacker who obtained a session identifier before authentication retains access after it. This is CWE-384 and it is still found regularly in hand-rolled login code.

10.2 Sanctum: SPA, mobile and API tokens

The three Sanctum token strategies, their storage, and the abilities model.

Sanctum offers three distinct mechanisms. They are not interchangeable, and choosing the wrong one produces a security defect.

MechanismCredentialUse for
SPA cookie authenticationSession cookie plus a first-party XSRF-TOKEN cookieBlade or Inertia applications on the same origin
Personal access tokensAuthorization: Bearer <id|hash>Mobile apps, CLI tools, integrations, long-lived machine access
Ability tokensSame as personal access, with a checked ability listThird-party delegated access, webhooks, read-only keys
// Issuing a token. The plain-text value is shown exactly once.
$token = $user->createToken('cli-tool', ['invoices:read', 'invoices:write'], Carbon::now()->addDays(30));

response()->json([
    'token' => $token->plainTextToken,   // "1|xxxxxxxx..." — never stored, never recoverable
    'expires_at' => $token->accessToken->expires_at,
], 201);

// Consuming: the guard authenticates, the ability check is separate.
$request->user()->tokenCan('invoices:write');   // true
$request->user()->currentAccessToken()->name;         // 'cli-tool'
$request->user()->currentAccessToken()->id;

// Middleware, applied in the api group.
->withMiddleware(function (Middleware $middleware) {
    $middleware->alias(['ability' => CheckAbilities::class]);
})

Route::post('/invoices', IssueInvoiceController::class)
    ->middleware(['auth:sanctum', 'ability:invoices:write']);

Sanctum stores SHA-256 hashes of the token in personal_access_tokens, not the token itself, so a database leak does not yield usable credentials. The |-separated prefix is the token’s numeric identifier, used to look up the correct row before the constant-time hash comparison. Expiry is enforced on the model via 'expiration' => null in config/sanctum.php for permanent tokens, and per-token otherwise.

First-party cookie authentication requires the SPA middleware and stateful domains to be configured exactly. In config/sanctum.php, stateful must list every domain the SPA is served from, and the EnsureFrontendRequestsAreStateful middleware must be in the api group before route-specific middleware. A misconfigured entry does not fail loudly — it fails as a 401 that is very hard to diagnose, because the same 401 also results from a genuinely invalid token.

// config/sanctum.php
'stateful' => explode(',', env('SANCTUM_STATEFUL_DOMAINS', sprintf(
    '%s%s',
    'localhost,localhost:3000,127.0.0.1,127.0.0.1:8000,::1',
    Sanctum::currentApplicationUrlWithPort(),
)),
'expiration' => null,   // non-null forces every token to expire
'token_prefix' => env('SANCTUM_TOKEN_PREFIX', ''),

For third-party delegated access, do not issue a personal access token. Issue an OAuth 2.0 access token from a dedicated authorisation server, or add Passport. Personal access tokens have no consent screen, no redirect allow-list, no refresh and no scopes beyond a flat ability array.

10.3 Guards, providers and multi-tenancy

Multiple guards in one application, and the guard scoping the framework applies per request.

Guards are configured as named entries in config/auth.php; the request selects one with the auth:guard-name middleware. Which guard a user model’s authorization helpers consult is determined by Auth::shouldUse() or the guards property on the model.

// Two audiences, one user table, different session stores.
'guards' => [
    'web'       => ['driver' => 'session', 'provider' => 'users'],
    'admin'     => ['driver' => 'session', 'provider' => 'admins'],
    'api'       => ['driver' => 'sanctum', 'provider' => 'users'],
    'partner-api' => ['driver' => 'sanctum', 'provider' => 'partners'],
],

Route::middleware(['auth:admin'])->group(function () {
    // Auth::user() inside this group is the admin guard's user.
    Route::get('/admin/reports', [ReportController::class, 'index']);
});

Applying auth:api and auth:web in the same request creates an ambiguous user. Auth::user() returns whichever guard was set last via shouldUse(), and code that reads auth()->user() without naming the guard will behave differently depending on middleware order. Name the guard in every authorization call, or enforce a single authenticated guard per route group.

For tenant isolation, a global scope on the tenantable model plus a middleware that resolves the tenant is the standard combination. The scope must be registered in a service provider’s boot() and applied to the query builder, not just the model, or a relationship query will bypass it.

10.4 Policies

The policy API, discovery conventions, and the two ways a policy is silently not applied.

A policy maps a model instance to a set of named abilities. Laravel discovers it by convention: App\Policies\{Model}Policy for App\Models\{Model}. The mapping is registered automatically when the directory is at the default location; a non-default namespace needs explicit registration in a provider’s boot().

namespace App\Policies;

final class class InvoicePolicy
{
    public function viewAny(User $user): bool
    {
        return $user->tenant_id' !== null;
    }

    public function view(User $user, Invoice $invoice): bool
    {
        // Tenant isolation must be part of the policy, not a separate concern.
        return $user->tenant_id' === $invoice->tenant_id';
    }

    public function void(User $user, Invoice $invoice): bool
    {
        return $user->tenant_id' === $invoice->tenant_id'
            && $invoice->status === InvoiceStatus::Open
            && $invoice->issued_at'->isAfter(now()->subDays(config('billing.void_window_days', 7)));
    }

    public function restore(User $user, Invoice $invoice): bool
    {
        return false;
    }
}

// Non-default namespace or a differently named model.
public function boot(): void
{
    Gate::policy(Domain\Billing\Entities\Invoice::class, Domain\Billing\Policies\InvoicePolicy::class);
    Gate::policy(Document::class, DocumentPolicy::class);
}

A policy method may have a nullable user as its first argument, which is how the "guest" case is expressed. The convention Laravel uses for admin guest access is a method named viewAny on a policy bound to a class without a model, or an explicit check in the controller.

// Laravel's own convention for guest access: nullable user + before() hook.
final class class PublicPricingPolicy
{
    public function before(?User $user): ?bool
    {
        return $user?->isSuperAdmin() ? true : null;
    }

    public function view(?User $user, PricingPage $page): bool
    {
        return $page->is_published || $user?->isEditor() === true;
    }
}

A before() that returns true grants everything; returning null defers to the specific method. Returning false from before() denies everything, including abilities a specific method would have allowed. Super-admin checks belong here; tenant checks do not, because they are per-resource.

Two silent failures to check for. A policy that exists but is not registered produces a 403 on everything, not a missing-policy error — unless a Gate::define with the same name exists, in which case that wins. And a policy method invoked through Gate::allows('void', $invoice) resolves to void; invoked through authorize('void', $invoice) in a controller it throws AuthorizationException and renders a 403.

10.5 Gates, abilities and the middleware boundary

When a gate is the right tool, and how the two middleware forms differ.

Gates answer questions that are not about a model: "can this user perform this action in this context", "can this user access a resource of type X in region Y". A closure gate is the fast path; a class-based gate is the testable one.

// Closure gates: fine for a small, stable rule set.
Gate::define('access-admin', fn (User $user) => $user->role === 'admin');

Gate::define('issue-invoice', fn (User $user) =>
    $user->hasPermissionTo('billing.invoices.issue'));

// Class-based gate: injects anything, testable in isolation.
final class class RegionalAccessGate
{
    public function allowsAccess(User $user, string $region): bool
    {
        return in_array($region, $user->regions, strict: true);
    }
}

// Invocation: allow / denies / authorize / inspect — four different contracts.
if (Gate::allows('access-admin')) { /* render */ }
if (Gate::denies('access-admin')) { abort(403); }
$this->authorize('void', $invoice);   // throws on failure
Gate::authorize('access-admin');        // static form, throws
Gate::inspect('access-admin')->allowed();     // tri-state: allowed/denied/null
// @can('void', $invoice) in Blade  — renders or omits, never throws

The two middleware forms differ in what happens on failure. can: on a route aborts with 403 before the controller runs, which is the right place for a coarse check. authorize in the controller throws with a message you control. Neither replaces a policy check on the specific resource, because a coarse check cannot know which resource was loaded.

Authorizing the route does not authorize the resource. Route::middleware('can:update,invoice') authorizes the class invoice for the ability, then the route-model-bound instance is loaded and the controller runs. A can: middleware argument cannot reference a bound route parameter, so the per-instance check must still happen in the controller or a dedicated action. The correct order is: coarse middleware check, then resource check, then action.

11.2 Fakes, mocks and what to fake

The framework’s fakes versus PHPUnit’s mocks, and the rule for choosing.

Two distinct mechanisms exist and they solve different problems. A fake is a working implementation that records calls and returns defaults. A mock is a programmed expectation of interactions. Fakes answer "what happened"; mocks answer "what was called". Preferring fakes is the correct default because a mock encodes the implementation, so refactoring the implementation breaks the test even when the behaviour is unchanged.

// Fake: swap the binding, use the real interface afterwards.
Bus::fake();
Http::fake(['api.stripe.com/*' => Http::response(['id' => 'pi_123'], 200)]);
Event::fake();
Mail::fake();
Notification::fake();
Storage::fake('s3');
Queue::fake();
Cache::fake();
Redis::fake();        // Laravel 11+; flushes the real facade in tearDown
Log::spy();           // facade that still calls through

// Assertions against a fake.
Bus::assertDispatched(GenerateInvoicePdf::class, fn (GenerateInvoicePdf $job) => $job->invoiceId === $invoice->id);
Bus::assertNothingDispatched();
Http::assertSent(function (Request $request) {
    return $request->url() === 'https://api.stripe.com/v1/payment_intents'
        && $request->hasHeader('Idempotency-Key', 'invoice-42-v1');
});

Event::assertDispatched(InvoiceIssued::class, function ($e) { return $e->invoiceId === 42; });

// The critical test: a faked dependency must not make the assertion vacuous.
Bus::assertDispatched(ProcessInvoice::class, function (ProcessInvoice $job) {
    return $job->paymentIntentId === 'pi_123';  // from the faked HTTP response
});

A fake that returns a default makes the assertion meaningless. Always map the specific endpoints a test depends on, and assert on the value that flowed through, not merely that a call was made.

11.3 Factories and states

Factory definitions as documentation, state composition, and the invalid-factory problem.

A factory’s real value is not generating rows; it is expressing the minimum viable shape of a valid entity. A factory that can produce a row violating an invariant will eventually produce one in a test, and the test will fail for the wrong reason.

namespace Database\Factories;

class InvoiceFactory extends Factory
{
    protected $model = Invoice::class;

    public function definition(): array
    {
        return [
            'number'        => fake()->unique()->bothify('INV-####-????'),
            'customer_id'    => Customer::factory(),
            'currency'      => fake()->randomElement(['EUR', 'GBP', 'USD']),
            'subtotal_cents' => fake()->numberBetween(1_000, 500_000),
            'vat_cents'     => fake()->numberBetween(200, 100_000),
            'total_cents'    => fn (array $a) => $a['subtotal_cents'] + $a['vat_cents'],
            'status'        => InvoiceStatus::Open,
            'issued_at'     => now()->subDays(fake()->numberBetween(1, 90)),
            'due_at'        => fn (array $a) => $a['issued_at']->copy()->addDays(14),
        ];
    }

    // States: named, composable, greppable.
    public function paid(): static
    {
        return $this->state(fn (array $a) => [
            'status'  => InvoiceStatus::Paid,
            'paid_at' => now(),
        ]);
    }

    public function overdue(): static
    {
        return $this->state(fn (array $a) => [
            'due_at' => now()->subDay(),
            'status' => InvoiceStatus::Open,
        ]);
    }

    public function forCustomer(Customer $customer): static
    {
        return $this->state(['customer_id' => $customer->id, 'tenant_id' => $customer->tenant_id]);
    }
}

// Usage — reads as a specification.
$invoice = Invoice::factory()
    ->forCustomer($customer)
    ->overdue()
    ->create(['total_cents' => 100_000]);

Use closures for derived attributes, not values. 'total_cents' => fn (array $attributes) => ... receives the already-resolved sibling attributes, so derived fields stay consistent no matter what the caller overrides. Setting a literal and remembering to update it in three places is the alternative, and it is always wrong somewhere.

Seed randomness deterministically for the tests that need reproducibility. fake()->seed(1234) inside a factory definition makes failures reproducible, but a factory used by 200 tests with one global seed means changing the seed breaks unrelated tests. Prefer explicit values at the call site for the attribute the test depends on, and let everything else be random.

11.4 Database tests and transactions

The RefreshDatabase vs DatabaseMigrations choice, and what neither can test.

TraitMechanismSpeedUse for
RefreshDatabaseOne migration, then a transaction per testFastestThe default; the vast majority of tests
DatabaseMigrationsMigrate and roll back per testSlowTests that need real DDL, e.g. index or constraint behaviour
DatabaseTruncationTruncate tables per testMediumMySQL/MariaDB where DDL is implicitly committing

RefreshDatabase migrates once for the whole test run, then begins a transaction in setUp and rolls it back in tearDown. This is the correct default. Two consequences follow that are frequently discovered the hard way.

  • Jobs dispatched with Bus::fake() never run. Their database writes never happen, so a test that dispatches a job and then asserts on its effects must use Queue::fake() plus a manual handle() invocation, or run the job explicitly.
  • An explicit DB::commit() in the test commits the test’s transaction. Assertions after that point see committed data, and the rollback no longer protects isolation. Never commit inside a test that uses RefreshDatabase.
// Executing a queued job's logic without a worker.
$job = new GenerateInvoicePdf($invoice->id);
$job->handle(app(PdfRenderer::class));

// Or, better, test the listener/action the job wraps, not the job.
app(GenerateInvoicePdfAction::class)->__invoke($invoice->id);

// A test that genuinely needs committed state (a second connection).
public function test_cross_tenant_read_is_denied(): void
{
    // Simulate a concurrent committed write from outside the test transaction.
    DB::connection()->statement('SET CONSTRAINTS ALL DEFERRED');
    // ... then assert the global scope still filters it.
}

For asserting that a queued job would work, the highest-value test in the suite is one that dispatches with Bus::fake(), asserts the job was dispatched with the right constructor arguments, and separately tests the class the job delegates to. The job class itself then contains no logic worth testing.

Neither trait can test transactions. MySQL’s DDL statements implicitly commit, so RefreshDatabase is unreliable on MySQL for any test that runs migrations. If a test must verify that a rollback actually undoes a write, it needs a dedicated connection and manual transaction control, or a real integration test against a throwaway database.

11.5 Contract tests and integration boundaries

Testing across a process, a queue, or a third-party API, and the three techniques that work.

An integration boundary is anywhere the code under test cannot reach in-process: a queue worker, an external HTTP service, a scheduled command in a separate process, or a second application instance. Three techniques cover these cases in increasing cost.

// 1. Fake the network. Cheapest, and correct for assertions on the request.
Http::fake(['api.stripe.com/v1/payment_intents' => function () {
    return Http::response(['id' => 'pi_test', 'status' => 'succeeded'], 200);
}]);
Http::fakeSequence()->push(Http::response(['code' => 'rate_limit'], 429))
                 ->push(Http::response(['id' => 'pi_test'], 200));

// 2. Record and replay. Non-deterministic third parties.
VCR::use('stripe');            // records HTTP to tests/fixtures/stripe
Http::fake([]);                      // ... or use php-http/recording-player

// 3. Real infrastructure. Only for contracts you own.
DB::connection('pgsql_test')->statement('SELECT version()');

$redis = Redis::connection('integration');
$redis->flushdb();
$redis->rpush('queue:default', serialize(new ProcessOrder(42)));

For queue integration, the real question is whether the job survives serialisation. That failure mode is invisible to Bus::fake(), which never serialises anything, and invisible to a unit test, which constructs the job directly.

// The test that catches the serialisation bug. No worker required.
it('serialises and restores the job payload identically', function () {
    $job = new ProcessOrder(42, now()->toImmutable(), some: new Money(10_00, Currency::EUR));

    $payload = serialize($job);
    $restored = unserialize($payload);

    expect($restored->orderId)->toBe(42);
    expect($restored->amount)->toEqual($job->amount);
    expect($restored->placedAt->toIso8601String())->toBe($job->placedAt->toIso8601String());
});

// The version of the same test that catches a closure or PDO in a property.
it('has no unserialisable properties', function () {
    $job = new ProcessOrder(42);

    try {
        serialize($job);
    } catch (Throwable $e) {
        expect($e->getMessage())->toContain('Serialization of');
        throw $e;
    }

    expect(true)->toBeTrue();
});

SerializesModels re-queries on deserialisation, which is a hidden I/O in a unit test. A job property typed as a model is stored as its identifier and re-fetched when the worker unserialises it. In a RefreshDatabase test the row still exists, so the test passes while the real worker’s behaviour differs — for example when the row was deleted, the deserialisation throws ModelNotFoundException and the job fails permanently. For anything that must survive its referenced row, store the identifier and query explicitly inside handle(), where a missing row is a handled condition rather than a deserialisation error.

12.1 API resources

The JsonResource contract, conditional fields, and the difference between a resource and a response.

An API resource separates the outbound payload from the model. It is a class with a toArray() method, resolvable through the container, so it may use other resources, formatters and configuration.

namespace App\Http\Resources\Billing;

final class class InvoiceResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id'         => $this->id,
            'number'     => $this->number,
            'status'    => $this->status->value,
            'currency'   => $this->currency,
            'total'     => [
                'amount_minor' => $this->total_cents,
                'currency'     => $this->currency,
            ],
            'customer'   => new CustomerSummaryResource($this->whenLoaded('customer')),
            'lines'      => InvoiceLineResource::collection($this->whenLoaded('lines')),
            'issued_at'  => $this->issued_at?->toIso8601String(),
            'due_at'     => $this->due_at?->toIso8601String(),

            // Only for the owner. Absent, not null, for everyone else.
            $this->mergeWhen($request->user()?->is($this->customer), [
                'internal_cost_cents' => $this->internal_cost_cents,
                'payment_terms'       => $this->payment_terms,
            ]),
        ];
    }
}

whenLoaded() and mergeWhen() are the mechanism that prevents accidental data exposure. A resource that returns $this->customer without whenLoaded will serialise the whole loaded relation graph, including columns the client was never meant to see. The correct discipline: a resource’s toArray() names exactly the fields the client receives, and nothing is included implicitly.

// Instantiation that controls the wrapping and metadata.
return (new InvoiceResource($invoice->loadMissing(['customer', 'lines'])))
    ->response()
    ->header('ETag', '"'.md5($invoice->updated_at->timestamp).'"')
    ->header('Cache-Control', 'private, max-age=0, must-revalidate');

// Single resource: wrapped in "data" by default. Suppress the wrapper.
return (new InvoiceResource($invoice))->withoutWrapping()->response();

// Additional top-level data.
return response()->json([
    'data'  => InvoiceResource::make($invoice)->resolve($request),
    'meta'  => ['generated_at' => now()->toIso8601String()],
]);

Represent money as a minor-unit integer plus a currency. A float in JSON is a rounding bug waiting for a client to multiply it by 100. If an interop constraint requires decimal amounts, emit them as strings, never as JSON numbers.

12.2 Pagination and collection shaping

The metadata each pagination style emits, and the one to use for large traversals.

MethodQuery stringMetadataDeep offset cost
paginate()?page=3&per_page=25current_page, last_page, total, per_page, from, to, path, linksYes — COUNT plus OFFSET
simplePaginate()?page=3Same minus total and last_pageAvoids the COUNT only
cursorPaginate()?cursor=<base64>next_cursor, prev_cursor, per_page, pathNo

paginate() issues two queries: the COUNT(*) and the page. The count is often the expensive one on a wide, filtered table. If the client does not need the total, simplePaginate() removes it. If the client is traversing a large collection, cursorPaginate() removes both the count and the offset cost.

$invoices = Invoice::query()
    ->with('customer:id,name')
    ->tap($search->applyTo(...))
    ->paginate(perPage: min((int) $request->query('per_page', 25), 100));

return InvoiceResource::collection($invoices);   // preserves links and meta

Returning the resource collection rather than wrapping the paginator in ['data' => ...] is what keeps the pagination metadata from being flattened away. A common error is response()->json(['data' => InvoiceResource::collection($paginator)]), which calls toArray() on the paginator and drops the links and metadata.

Clamp per_page from untrusted input. ?per_page=1000000 on an unbounded query is a denial-of-service vector that costs one HTTP request. Read the parameter, clamp it, and reject a value above the maximum with a 422 rather than silently truncating it — silent truncation produces a client that believes it received everything.

12.3 Versioning strategies

The three versioning models, their cost, and the deprecation mechanism that makes them survivable.

StrategyMechanismCostUse when
URL path/api/v2/invoicesLow, explicit, cacheablePublic or third-party APIs

Whatever the mechanism, the durable part is not the version number but the deprecation policy. A version without a stated removal date is a version that never gets removed.

// Version in the path, registered in bootstrap/app.php routing.
->withRouting(
    api: __DIR__.'/../routes/api.php',
    apiPrefix: 'api',
    // routes/api.php then prefixes each group itself:
)

// routes/api.php
foreach (['v2' => __DIR__.'/../routes/api/v2.php'] as $version => $file) {
    Route::prefix($version)->middleware('api')->group($file);
}

// Response headers that make deprecation visible to every client at once.
Route::middleware([function (Request $request, Closure $next) {
    $response = $next($request);

    if ($request->is('api/v1/*')) {
        $response->headers->set('Deprecation', 'true');
        $response->headers->set('Sunset', 'Tue, 30 Jun 2026 00:00:00 GMT');
        $response->headers->set('Link', '</api/v2/invoices>; rel="successor-version"');
    }

    return $response;
})->group(function () {
    require __DIR__.'/../routes/api/v1.php';
});

Deprecation, Sunset and Link rel="successor-version" are the standard headers defined for this purpose. Emitting them is cheap and lets a monitoring system enforce the policy: log every request carrying them, and alert when the daily count has not reached zero by the sunset date.

Prefer additive change to a new version. Adding an optional field, relaxing a validation rule or adding a new endpoint is backward-compatible. Renaming a field, tightening a type, changing a default or removing a field is not. Write the compatibility rule down and require a version bump for anything that fails it — that rule is what makes "additive only" enforceable rather than aspirational.

12.4 Rate limiting

The limiter definitions, the two throttle middleware behaviours, and the Redis-backed implementation.

Rate limiters are defined in a service provider using RateLimiter::for() and consumed by the throttle: middleware with the limiter’s name as the key.

// bootstrap/app.php
->withMiddleware(function (Middleware $middleware) {
    $middleware->throttleApi();   // convenience: RateLimiter::for('api')
})

// A service provider defines the limiters.
final class class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        RateLimiter::for('api', function (Request $request) {
            return Limit::perMinute(60)->by($request->user()?->id ?: $request->ip());
        });

        RateLimiter::for('login', function (Request $request) {
            return [
                Limit::perMinute(5)->by(Str::transliterate(Str::lower($request->input('email')).'|'.$request->ip()),
                Limit::perMinute(20)->by($request->ip()),
            ];
        });

        RateLimiter::for('uploads', function (Request $request) {
            return Limit::perHour(10)->by(Str::lower($request->user()?->email() ?? 'anon'));
        });
    }
}

Route::middleware(['throttle:api'])->group(function () { /* ... */ });
Route::post('/login', function () { /* ... */ })->middleware(['throttle:login']);

Returning an array of limits means every limit must be under its threshold, not any. Returning Limit::none() disables a route’s limiting entirely, which is useful for internal endpoints on a private network — never for a public one.

The middleware sets X-RateLimit-Limit, X-RateLimit-Remaining and Retry-After on a 429. Laravel’s default ThrottleRequests renders an empty 429 body; override the response to include the limit metadata so a client can back off correctly.

$exceptions->render(function (ThrottleRequestsException $e) {
    return response()->json([
        'type'   => 'https://api.example.com/problems/rate-limited',
        'title'  => 'Too Many Requests',
        'status' => 429,
        'retry_after' => $e->getHeaders()['Retry-After'] ?? 60,
    ], 429, $e->getHeaders(), JSON_UNESCAPED_SLASHES);
});

The default cache store determines whether rate limiting is actually distributed. With the database driver the limiter works, but every check is a database write. With the array driver — which is the default when CACHE_STORE is unset in some scaffolds — the limiter is per-process, so a limit of 60 means 60 per worker per minute. Verify php artisan about reports a shared store in production.

12.5 Errors, idempotency and idempotent verbs

Making writes safe to retry, and the three headers an API contract should specify.

An API is a contract about failure as much as about success. Three behaviours must be specified and implemented together: what a retry does, what a duplicate submission does, and what a partial failure looks like.

// Idempotency keys: the server records the outcome and replays it.
final readonly class class IdempotencyStore
{
    public function resolve(string $key, string $fingerprint, callable $operation): mixed
    {
        $existing = IdempotencyKey::query()->where('key', $key)->first();

        if ($existing) {
            // Same key, different payload = client bug, not a replay.
            if ($existing->fingerprint !== $fingerprint) {
                throw new IdempotencyKeyReused($key);
            }

            return $existing->response_body;   // replay verbatim, including status
        }

        return DB::transaction(function () use ($key, $fingerprint, $operation) {
            try {
                $result = $operation();
            } catch (Throwable $e) {
                throw $e;   // rolled back; key not recorded, retry allowed
            }

            IdempotencyKey::create([
                'key' => $key, 'fingerprint' => $fingerprint,
                'response_body' => $result, 'completed_at' => now(),
            ]);

            return $result;
        });
    }
}

// Applied in a middleware or controller.
$key = $request->header('Idempotency-Key');

if (! $key) {
    if (! $request->isMethod('GET')) {
        return response()->json([
            'type' => 'https://api.example.com/problems/idempotency-key-required',
            'title' => 'Idempotency-Key header is required for this endpoint',
            'status' => 400,
        ], 400);
    }
} else {
    $fingerprint = hash('sha256', $request->method().'|'.$request->path().'|'.json_encode($request->all()));
    $body = $store->resolve($key, $fingerprint, fn () => $issueInvoice(...));

    return response()->json($body, 201, ['Idempotency-Key' => $key]);
}

The unique constraint on key is what makes this correct under concurrency: two simultaneous requests with the same key race, one inserts and the other’s insert fails, and the loser re-reads and replays. lockForUpdate() on an existing row is an alternative but does not help when the row does not exist yet.

VerbIdempotent?Contract

POSTNoRequire an Idempotency-Key on any endpoint that charges, sends or creates
PATCHOnly if defined as suchSpecify whether it is a full or partial merge

Use 202 Accepted with a status URL for long operations. An endpoint that takes more than a few seconds should return immediately with a resource identifier, dispatch a job, and let the client poll. A synchronous request held open for a report generation will hit the client or proxy timeout first, and the work may continue server-side invisibly — the worst combination, because the client retries and the work runs twice.

13.2 Cache tags and the stores that support them

The tag API, the implementation detail that makes tag flushing O(1), and the namespace prefix that isolates them.

Redis implements tags with a separate set per tag. A tagged value’s key is suffixed with a versioned identifier, and the tag set holds a reference to that identifier. Flushing a tag increments the identifier — it does not enumerate or delete keys. Flushing is therefore O(1) regardless of how many entries the tag holds, and the old keys expire naturally on their own TTL.

$tagged = Cache::tags(['tenant:7', 'product:991', 'catalog']);

$tagged->put('detail', $product, now()->addHour());
$tagged->remember('related', now()->addHour(), fn () => $product->related()->limit(5)->get());

Cache::tags(['product:991'])->flush();   // O(1), invalidates both keys
Cache::tags(['tenant:7'])->flush();      // O(1), invalidates every product for this tenant

The tag set keys are namespaced with the cache prefix. Two Laravel installations sharing one Redis database must use different prefix values, or a flush in one application will invalidate the other’s tagged entries — a failure that is intermittent, environment-specific, and extremely hard to attribute.

Tag flushing is not atomic with the write that motivated it. A request that reads a value, then a writer updates the row and flushes the tag, then the reader writes its now-stale value into the cache — the classic cache-aside race. It is usually harmless and self-correcting within one TTL. For correctness-critical data, invalidate inside the same transaction as the write and accept that a rollback leaves the cache empty rather than stale, or version the key with the row’s updated_at so a stale write is never served.

13.3 Invalidation patterns that hold

Four invalidation strategies and the conditions under which each one is correct.

StrategyCorrect whenBreaks when
TTL onlyStaleness is bounded and acceptableA stale read is harmful (permissions, pricing, balances)

// Versioned key: correctness without a flush, at the cost of one read.
final readonly class class ProductCache
{
    public function __construct(
        private Redis $redis,
        private ProductRepository $products,
    ) {}

    public function get(int $id): Product
    {
        $version = ((int) $this->redis->get("product:{$id}:v") ?? 1);

        return Cache::remember("product:{$id}:v{$version}", now()->addDay(),
            fn () => $this->products->findOrFail($id));
    }

    public function invalidate(int $id): void
    {
        $this->redis->incr("product:{$id}:v");   // O(1), no enumeration, no tag needed
    }
}

The versioned-key pattern is the most robust of the four because invalidation cannot fail partially. A missed increment leaves the old key readable; it does not leave a tag set containing a dangling reference, and it does not depend on enumerating anything. Its cost is one Redis GET per read, which is roughly a millisecond of network time and is usually cheaper than the alternative.

Invalidate from the model, not from the caller. A model observer that bumps the version counter covers every write path including factories, seeders, queued jobs and artisan commands, because they all go through the model. Chapter 4.5 covers the limits of observers — for a cache version counter the limit does not matter, because a missed invalidation only causes staleness up to the TTL, not a correctness failure.

13.4 Key design and stampede control

Building keys that cannot collide, and the single-flight pattern that stops a cache miss from becoming an outage.

A key must encode every input that changes the result. The most common defect is omitting one, which produces a cache that returns a value computed for different inputs — a correctness bug that is far more damaging than a miss.

final readonly class class CacheKey
{
    public static function report(int $tenantId, OrderSearch $search, string $schemaVersion): string
    {
        // Hash the search object so no filter can be forgotten.
        $filterHash = substr(hash('sha256', serialize([
            $search->from?->format('Y-m-d'),
            $search->to?->format('Y-m-d'),
            $search->status?->value,
            $search->customerId,
            $search->perPage,
        ])), 0, 16);

        // The schema version lets a deploy invalidate everything at once.
        return sprintf('rpt:%s:t%d:%s', $schemaVersion, $tenantId, $filterHash);
    }

    public static function product(int $id, string $locale, int $version): string
    {
        return sprintf('prd:v%d:%d:%s', $version, $id, strtolower($locale));
    }
}

// Bump the schema version to invalidate an entire namespace in one deploy.
config()->set('cache.schema.report', '2026-03-02');

Locale, currency, timezone, feature-flag state and the authenticated user’s effective permissions all change a result and all belong in the key when the result depends on them. A cached permission check for an English locale served to a Dutch one is a bug report, not a curiosity.

A cache stampede is many concurrent requests missing the same key simultaneously and all computing it. The fix is a lock: only the first request computes, the rest wait or serve a stale value.

// Single-flight with a lock, and a stale-while-revalidate fallback.
public function remember(string $key, DateTimeInterface $ttl, int $staleFor, callable $compute): mixed
{
    $value = Cache::get($key);

    if ($value !== null) {
        return $value;
    }

    // Stale-while-revalidate: serve the expired value and refresh in the background.
    $stale = Cache::get("$key:stale");

    if ($stale !== null) {
        Cache::put("$key:refresh", 1, now()->addSeconds(5));

        if (Cache::add("$key:refresh", 1, now()->addSeconds(30))) {
            dispatch(new RefreshCacheEntry($key, $ttl, $staleFor, serialize($compute)));
        }

        return $stale;
    }

    return Cache::lock($key, 10)->block(3, function () use ($key, $ttl, $staleFor, $compute) {
        $value = $compute();

        Cache::put($key, $value, $ttl);
        Cache::put("$key:stale", $value, $ttl->add(DateInterval::createFromDateString("{$staleFor} seconds")));

        return $value;
    });
}

Cache::lock()->block() requires a store that supports atomic locks — Redis, Memcached, database, file. It does not work with the array store, so a test using CACHE_STORE=array exercises a different code path than production. Verify the lock behaviour in a test that uses a real store.

13.5 What not to cache

The data that becomes actively dangerous when cached, and the conditions under which caching is not the fix.

Caching is a trade: latency against correctness under invalidation. Some data has a correctness cost so high that the trade is not worth making at the requested latency.

DataWhy caching is dangerousAlternative
Authorization decisionsA stale grant is a security incident; a stale denial is a support ticketQuery, or cache with a very short TTL keyed on the user’s permission version
Account and inventory balancesTwo writers can both spend the same cached balanceRow lock plus a conditional update; the database is the serialisation point
Payment and idempotency stateA stale record means a duplicate chargeNever cache; use a unique constraint
Session dataTwo nodes disagree about the sessionShared store, not cache
Random or time-dependent outputCaching changes the semantics of the functionCache the input, compute the output
Already fast queriesNetwork round trip to Redis may exceed the query timeMeasure first; an indexed query on a small table is under a millisecond

Caching a query that should be indexed hides a schema problem. A report that takes 900 ms and is then cached for an hour appears to be solved, until the cache is flushed, the deployment happens, or the data grows. The correct order is: add the index, then measure again, then cache only if the result is still too slow. Chapter 14 covers the measurement.

// The pattern that usually replaces a cache: the index and the projection.
Schema::table('orders', function (Blueprint $table) {
    $table->index(['tenant_id', 'placed_at']);              // composite, in filter order
    $table->index(['tenant_id', 'status', 'placed_at']);
});

DB::table('orders')
    ->select(['id', 'total_cents', 'currency'])   // covering index candidate
    ->where('tenant_id', $tenantId)
    ->whereBetween('placed_at', [$from, $to])
    ->groupBy('currency')
    ->get();

Session and cache are different concerns that often share a driver. Pointing SESSION_DRIVER at the redis store is normal, but eviction of a session under memory pressure logs a user out, while eviction of a cached value is invisible. Use separate Redis databases or prefixes for the two, and configure maxmemory-policy deliberately — allkeys-lru will evict sessions under cache pressure.

14.1 Detecting N+1 and query count budgets

Making the query count a testable assertion rather than something noticed in production.

An N+1 is not detectable by looking at code; it is detectable by counting queries. The count belongs in the test suite as an assertion, which converts a performance regression into a test failure.

final class class QueryCountAssertion
{
    public int $count = 0;

    public function start(): void
    {
        $this->count = 0;
        DB::listen(function () { $this->count++; });
    }

    public function assertAtMost(int $expected, string $context = ''): void
    {
        expect($this->count)
            ->toBeLessThanOrEqual($expected, $context);
    }
}

// In a Pest beforeEach/afterEach.
beforeEach(function () {
    $this->queries = new QueryCountAssertion;
    $this->queries->start();
});

it('renders the invoice list in a bounded number of queries', function () {
    Invoice::factory()->count(50)->create();
    $this->queries->count = 0;   // reset after seeding

    $this->get('/invoices')->assertOk();

    $this->queries->assertAtMost(3, 'invoice index');
});

Three production mechanisms, in increasing strictness. Model::preventLazyLoading() in non-production throws on any lazy load. Model::handleLazyLoadingViolationUsing() in production logs and returns the model rather than throwing, so the request succeeds and the violation is observable. A query-count middleware logs the count with the route name on every request, so a regression shows up as a metric rather than as a support ticket.

// AppServiceProvider::boot() — Laravel 11+ style
use Illuminate\Database\Eloquent\LazyLoadingViolationException;

Model::preventLazyLoading(! $this->app->isProduction());
Model::preventSilentlyDiscardingAttributes(! $this->app->isProduction());
Model::preventAccessingMissingAttributes(! $this->app->isProduction());

Model::handleLazyLoadingViolationUsing(function (Model $model, string $relation) {
    Log::warning('lazy load', [
        'model' => $model->getClass(), 'key' => $model->getKey(), 'relation' => $relation,
    ]);

    // Return the model: the request still succeeds, the event is recorded.
    return $model;
});

Do not use preventAccessingMissingAttributes in production without reading what it throws on. It raises on any attribute absent from the SELECT list, including a legitimate access to a column added by a later migration during a rolling deploy. Use it in tests to find projection bugs, and consider it in production only with the violation handler wired to a metric.

A query count budget per route is a design constraint with a real effect: it forces every new relation to be added to an eager-load set, because the alternative is a failing test. Set the budget slightly above the current count, not at it, so a legitimate addition is a deliberate change to the number.

14.2 Bulk operations and chunked writes

Reducing a thousand round trips to three, and the memory cost of the alternative.

The largest single performance win available in a typical Laravel application is replacing a loop of individual writes with a bulk operation. 1,000 INSERT statements is 1,000 network round trips; upsert() is one.

// Bad: 1,001 round trips, and a full model hydration for each row.
foreach ($rows as $row) {
    LedgerEntry::create($row);
}

// Good: one statement. Bypasses events, casts' set(), and observers.
LedgerEntry::upsert(
    $rows,
    ['reference', 'occurred_on'],
    ['amount_cents', 'currency', 'updated_at']
);

// insertOrIgnore: skip rows whose unique key already exists.
DB::table('ledger_entries')->insertOrIgnore($rows);

// For a real UPDATE per row, updateOrInsert still batches into two statements.
DB::table('counters')->upsert($rows, ['key'], ['value', 'updated_at']);

Both methods have a parameter-count limit on the compiled statement. MySQL’s default max_allowed_packet is 64 MB in 8.0, and PostgreSQL has a 1,000-column-per-insert restriction. When a large import fails with a packet or column-count error, the fix is to chunk the input — not to raise the limit.

// Chunked read AND write: bounded memory, one transaction per chunk.
DB::table('legacy_orders')
    ->orderBy('id')
    ->chunkById(500, function (Collection $rows) {
        $payload = $rows->map(fn (object $r) => [
            'id' => $r->id, 'total_cents' => $r->amount, 'placed_at' => $r->date,
        ])->all();

        DB::table('orders')->upsert($payload, ['id'], ['total_cents', 'placed_at']);
    });

// laravel/eloquent-mass-assignment concern: set the fillable list or use forceFill.
// And note chunkById, not chunk — offset-based chunk skips rows when the source mutates.

Run bulk writes in a queued job with a memory limit set explicitly. A job processing a million rows with a 128 MB memory limit will fail at some unpredictable point; with --memory=512 and chunking, it completes. Also set a generous --timeout for such a job and remember from chapter 7.2 that retry_after must exceed it.

14.3 Opcache and the request path

The runtime settings that determine the floor on latency, and why they are deployment configuration rather than application code.

After the application code is correct, the remaining latency is dominated by PHP’s own per-request work: compiling files, initialising the framework, and running the autoloader. Opcache removes the first of these; the second and third are set by how the application is deployed.

// php.ini — production FPM
opcache.enable=1
opcache.enable_cli=0
opcache.memory_consumption=256
opcache.interned_strings_buffer=16
opcache.max_accelerated_files=20000
opcache.validate_timestamps=0
opcache.save_comments=1
opcache.jit=buffer_size=128M,jit_buffer_size=128M,jit=tracing

// Crucial: revalidate_timestamps=0 means new files are NOT picked up.
// FPM must be reloaded after a deploy: systemctl reload php8.3-fpm

// Real production settings

post_max_size=16M
upload_max_filesize=16M

Measure how much of the request is boot. A trivial route that returns immediately still pays the full framework boot. Time it: php artisan tinker with a bare public/index.php request, or compare php artisan about wall time against a no-op. If boot is 40 ms of a 120 ms request, framework-level work is a better investment than the endpoint being optimised.

Three deployment choices reduce boot time measurably. config:cache replaces thirty file includes with one. route:cache and view:cache eliminate the route-file compilation and Blade compilation that otherwise run per request. optimize-autoloader generates a classmap so the autoloader stops scanning directories.

php artisan optimize          # config + route + view + events + cache clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache
composer install --no-dev --optimize-autoloader --classmap-authoritative

# Things that break config:cache — closures, env() outside config files.
# config/*.php must not call env() in a closure body or return a closure.
# php artisan config:cache fails loudly on a closure, which is the desired behaviour.

opcache.validate_timestamps=0 and a deploy that does not reload the FPM pool will serve old code. The symptom is a deploy that reports success and a website that runs the previous version, intermittently, depending on which worker handled the request. The reliable deploy sequence is: warm the cache into a new release directory, switch the symlink, then reload the FPM pool. Without the reload step, opcache keys the compiled script by its real path, so a new release at a new path gets a fresh entry but a deploy.php at the same path does not.

JIT is worth measuring rather than assuming. tracing mode usually helps compute-heavy code and does very little for I/O-bound request handling, where most of the time is spent waiting on the database. Benchmark with and without on the same endpoint before enabling it.

14.4 Queue throughput

The four settings that determine how many jobs a worker fleet processes per second.

Queue throughput is a function of process count, job duration, and the efficiency of the loop between jobs. Nothing else matters at the same order of magnitude.

php artisan queue:work redis --queue=critical,default \
    --sleep=1 --timeout=60 --tries=3 --max-jobs=1000 --max-time=3600 \
    --memory=256 --rest=3 --backoff=5

--memory      exit when above this; requires a supervisor to restart it

// The three real throughput wins, in order of effect.
DB::statement('SET SESSION wait_timeout = 5');   // 1. release the connection fast

// 2. Move I/O out of the job. A job that makes 10 HTTP calls is 10 jobs
//    waiting on a worker for the duration of those calls.
Bus::batch($invoices)->each([NotifyCustomer::class, GeneratePdf::class]);

// 3. Keep the payload small. A job with a 5 MB serialised model is a
//    5 MB Redis write and a 5 MB read per attempt.
ProcessInvoice::dispatch($invoice->id);   // 4 bytes, not 50 KB

Connection exhaustion presents as a queue backlog, not as a database error. 20 workers each holding a connection during a job, plus 20 web requests, plus the scheduler, exceeds a default max_connections of 151 on PostgreSQL or MySQL. The symptom is jobs that time out while waiting for a connection, retried until they fail permanently, with the real error in the PostgreSQL log. Size the pool deliberately, or put PgBouncer in transaction mode in front of it.

// Phase timing that works in production, with no dependency.
final class class PhaseTimer
{
    private array $marks = [];
    private float $startedAt;

    public function start(): void
    {
        $this->startedAt = hrtime(true);

        if (defined('LARAVEL_START')) {
            $this->marks['bootstrap'] = (microtime(true) - LARAVEL_START) * 1000;
        }
    }

    public function mark(string $name): void
    {
        $this->marks[$name] = (hrtime(true) - $this->startedAt) / 1e6;
    }

    public function toServerTiming(): string
    {
        return collect($this->marks)
            ->map(fn ($ms, $name) => sprintf('%s;dur=%.1f', $name, $ms))
            ->implode(', ');
    }
}

    printf("%-6s %7.2fms %s\n", $q['query'][0], $q['time'],

}

# The database's own view of a slow statement.
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE tenant_id = 7 ORDER BY placed_at DESC LIMIT 25;
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE tenant_id = 7;

Never run EXPLAIN ANALYZE on a SELECT * against production. ANALYZE executes the statement and reports the actual time, so a query that scans fifty million rows will take the table offline for the duration. Use plain EXPLAIN to inspect the plan, and reserve ANALYZE for a staging database with production data statistics.

Two query-level details account for a large share of the slow statements found in Laravel applications. A leading % in a LIKE cannot use a B-tree index; the fix is a trigram index on PostgreSQL or a full-text index. And whereIn with a subquery becomes a correlated subquery unless the engine flattens it — verify with EXPLAIN and, where it does not flatten, pass an array of identifiers from an eager-loaded relation instead.

// whereIn with a subquery: check the plan. On PostgreSQL 12+ this is usually
// flattened; on MySQL it depends on the optimiser's subquery materialisation.
$invoices = Invoice::query()
    ->whereIn('customer_id', Customer::query()->select('id')->where('segment', 'enterprise'))
    ->get();

// When the plan is bad, materialise the identifiers — one extra cheap query.
$customerIds = Customer::query()->where('segment', 'enterprise')->pluck('id');
$invoices = Invoice::query()->whereIn('customer_id', $customerIds)->get();

Finally, profile the aggregate rather than the endpoint. A p99 latency that is high while the median is low points at a tail-specific cause: a cache miss, a lock, a connection-pool wait, or garbage collection. A high median with a low p99 points at the common path. The distinction determines which of the four causes to look for, and it is visible in the histogram before any profiler is attached.

15.1 Mass assignment and guarded discipline

How fillable and guarded interact, and where the allow-list fails.

Mass assignment protection has two halves. $guarded = ['*'] prohibits everything by default; $fillable is an allow-list. Models should declare fillable explicitly. The combination that disables protection entirely is $guarded = [], which permits every attribute — the setting used by the default User model in older skeletons and a frequent copy-paste artefact.

final class class Invoice extends Model
{
    protected static $unguarded = false;

    protected fillable = [
        'customer_id',
        'currency',
        'due_at',
        'reference',
    ];

    protected function guarded(): array
    {
        // A second allow-list: attribute must be in BOTH to be mass-assignable.
        return ['id', 'total_cents', 'status', 'tenant_id', 'paid_at'];
    }
}

// Deliberate, narrow, auditable. Never a loop over request data.
$invoice->fill([
    ...$request->validated(),
    'total_cents' => $total->minor,   // computed, not from input
]);

// forceFill bypasses the guard entirely. Correct for a computed value;
// a finding in review if used on request data.
$invoice->forceFill(['total_cents' => $total->minor]);

Guarding is not authorisation. tenant_id in the guarded array stops a client assigning it. It does not stop a controller author from reading tenant_id from a route parameter that the client controls, or from querying a model belonging to another tenant. Every one of those is an insecure direct object reference, and chapter 10's policy is where it is prevented.

Two further surfaces deserve naming. A model’s toArray() is used when a model is returned directly from a controller; returning a model rather than a resource bypasses the resource’s field selection entirely. And a model’s fill() inside an event listener trusts whatever the caller passed, which is why observers should not use mass assignment at all.

15.2 CSRF and cookie configuration

The web group’s CSRF middleware, the stateless alternative, and the cookie flags that matter.

CSRF protection is provided by Illuminate\Foundation\Http\Middleware\ValidateCsrfToken, present in the web group only. Routes outside that group — routes/api.php by default — are not protected, which is correct for a token-authenticated API and a vulnerability for a session-authenticated one.

// The exclusion list is where CSRF protection usually dies by accident.
->withMiddleware(function (Middleware $middleware) {
    $middleware->validateCsrfTokens(except: [
        'api/webhooks/stripe',   // only safe with signature verification
    ]);

    $middleware->validateCsrfTokens(except(function (Request $request) {
        // Narrow, authenticated-header based, and documented.
        return $request->is('api/*') && $request->bearerToken() !== null;
    });
})

A webhook that is excluded from CSRF must verify a signature instead, and the verification must be constant-time and must cover the raw body. Stripe’s scheme is t=timestamp,v1=signature over timestamp.payload, with a 5-minute tolerance to prevent replay.

final class class VerifyStripeSignature
{
    public function handle(Request $request, Closure $next): Response
    {
        $header = null;

        foreach (explode(',', $request->header('Stripe-Signature', '')) as $pair) {
            [$key, $value] = array_pad(explode('=', $pair, 2), 2, null);
            $values[$key] = $value;
        }

        $timestamp = $values['t'] ?? null;
        $signature = $values['v1'] ?? null;

        if (! $timestamp || ! $signature || abs(time() - $timestamp) > 300) {
            abort(400, 'Invalid signature timestamp.');
        }

        $expected = hash_hmac('sha256', $timestamp.'.'.$request->getContent(),
            config('services.stripe.webhook_secret'));

        if (! hash_equals($expected, $signature)) {
            abort(400, 'Invalid signature.');
        }

        return $next($request);
    }
}

Session cookie flags are set by config/session.php and must be correct in production. secure => env('SESSION_SECURE_COOKIE') must be true behind TLS; http_only defaults to true and prevents JavaScript from reading the session identifier; same_site defaults to lax, which blocks cross-site POSTs. Behind a TLS-terminating proxy, secure depends on the request being recognised as HTTPS, which depends on the trusted proxy configuration in chapter 3.2 being correct.

15.3 Output encoding and Blade’s defaults

What Blade escapes by default, the four escape hatches, and where JavaScript context breaks the model.

Blade’s {{ }} compiles to htmlspecialchars($value, ENT_QUOTES, 'UTF-8', true). That is correct for HTML text and attribute context. Everything that deviates from it is a decision to make deliberately.

{{ $user->name }}              escaped — the default, correct for text and attributes
{!! $user->bio !!}            unescaped — only for content you sanitised first
@{{ $literal }}               renders a Blade directive as text
@json($data)                  script-safe JSON with < > & escaped as \u003C etc
@js($var)                     same as @json, for the Alpine/Vue data convention
{!! $html !!}                unescaped — see below

{!! !!} is safe only for output that passed a sanitiser. A rich-text field stored in the database and rendered with {!! !!} is stored XSS: the payload was inserted by any user who can use the field, and it executes for every reader. The correct pattern is to sanitise on input with a maintained library — HTML Purifier or an equivalent — and escape with {{ }} everywhere else. If the sanitiser is not in place, render as escaped text and accept the loss of formatting.

HTML escaping is not sufficient inside a <script> block, an HTML attribute holding a URL, or a CSS value. htmlspecialchars does not prevent </script> termination of a script element, and it does not make javascript: in an href safe.

<!-- Safe: inside a script block, use @json, never {!! !!} -->
<script>
    const config = @json($config);
</script>

<!-- Safe: attribute value, escaped -->
<div data-url="{{ $url }}">

<!-- Unsafe: unescaped URL in href. A javascript: URL executes on click. -->
<a href="{!! $user->website !!}">Link</a>

<!-- Safe: validate the scheme, then escape -->
@php($href = str_starts_with($user->website, ['http://', 'https://']) ? $user->website : '#')
<a href="{{ $href }}" rel="noopener noreferrer" target="_blank">Link</a>

<!-- Inline handler attributes are the classic DOM XSS sink. Avoid entirely. -->
<button onclick="alert('{{ $name }}')">X</button>   {{-- WRONG -->
<button data-name="{{ $name }}" x-on:click="alert($el.dataset.name)">X</button>

// A Blade directive that is safe to reuse, and centralised so it is reviewable once.
Blade::directive('safeUrl', function (string $expression) {
    return "<?php echo e(Str::startsWith(" . $expression . ", ['http://', 'https://', '/', '#']) ? " . $expression . "' : '#'); ?>";
});

<a href="@safeUrl($user->website)">Link</a>

// A sanitiser at the input boundary, so rendering can stay escaped.
use HTMLPurifier\HTMLPurifier;

final class class SanitizedHtml
{
    public static function clean(string $html): string
    {
        static $purifier = null;

        return ($purifier ??= new HTMLPurifier(new HTMLPurifier_Config(create()->set('HTML.Allowed', 'p,a[href],strong,em,ul,ol,li,br')))

Content-Security-Policy is the structural defence. A policy without unsafe-inline in script-src converts XSS from an executable flaw into a blocked report, and the report identifies the source. It is a header set by the web server or a middleware, and it is the single most effective mitigation for an application that must render user-supplied HTML.

15.4 SQL injection and the places it survives

The five code paths in a Laravel application where a binding is not used, and how to close each.

Parameter binding is applied automatically for values passed through where(), orderBy() for simple columns, and whereIn(). Injection survives where the query is assembled as text.

// 1. Raw concatenation — the direct one.
DB::select("SELECT * FROM orders WHERE status = '".$request->input('status')."'");

// 2. Raw without bindings — placeholders are not escaped unless you pass them.
DB::select('SELECT * FROM orders WHERE status = ?');   // no binding passed
DB::select('SELECT * FROM orders WHERE status = ?', [$status]);

// 3. Identifier interpolation — column and table names cannot be bound.
DB::select("SELECT {$request->input('sort')} FROM orders");

// 4. LIKE patterns — % and _ are meaningful, and an escape is needed.
$q->where('name', '%'.$request->input('q').'%');

// 5. Dynamic order/column — must be validated against an allow-list.
$q->orderBy($request->input('sort'), $request->input('dir'));

// Fix 3 and 5: allow-list the identifier. Never escape it, never bind it.
final class class SortSpec
{
    private const COLUMNS = ['placed_at', 'total_cents', 'status', 'number'];
    private const DIRECTIONS = ['asc', 'desc'];

    public static function fromRequest(Request $request): self
    {
        return new self(
            in_array($request->input('sort'), self::COLUMNS, strict: true) ? $request->input('sort') : 'placed_at',
            strtolower((string) $request->input('dir')) === 'asc' ? 'asc' : 'desc',
        );
    }

    public function applyTo(Builder $query): Builder
    {
        return $query->orderBy($this->column, $this->direction);
    }
}

// Fix 4: escape the LIKE metacharacters in the user-supplied part.
$term = str_replace(['\\', '%', '_'], ['\\\\', '\\%', '\\_'], $request->input('q'));
$q->where('name', like, '%'.$term.'%');

// Fix 1: bind, always, including inside selectRaw and whereRaw.
$q->whereRaw('total_cents > ?', [$minCents])
  ->selectRaw('SUM(total_cents) / ? AS avg_cents', [100])
  ->havingRaw('COUNT(*) >= ?', [$minRows]);

whereRaw(), selectRaw() and havingRaw() are the only places a developer writes SQL by hand, and they are where every injection finding in a Laravel codebase originates. A grep for these three method names is a complete audit of the raw-SQL surface. Each occurrence must show a binding array as its second argument unless the interpolated value is a literal or a validated identifier.

15.5 Signed URLs, encryption and secrets

Temporary URLs, encrypted values, and the key management that both depend on.

A signed URL grants access to a resource without an authentication check. The signature is an HMAC over the URL and its parameters, keyed by APP_KEY, which means the URL is tamper-proof but not secret: anyone holding it has access until it expires.

// Generate a temporary download URL valid for five minutes.
return URL::temporarySignedRoute(
    'invoices.download',
    now()->addMinutes(5),
    ['invoice' => $invoice->id]
);

// A signed public URL for a private file, with an absolute path.
URL::signedRoute('exports.view', ['file' => $key]);

// Verification in the route: the middleware aborts with 403 on mismatch.
Route::get('/invoices/{invoice}/download', DownloadInvoice::class)
    ->middleware(['signed'])
    ->name('invoices.download');

// Or in a controller, for a conditional check.
if (! URL::hasValidSignature($request)) {
    abort(403);
}

Signed routes are the right mechanism for a one-shot link in an email: a download, a password reset, a webhook callback with a signature. They are the wrong mechanism for authorisation, because the URL is bearer authority — it forwards, it leaks in a referrer header, and it ends up in a browser history and a mail server’s log.

Encrypted model attributes use the same APP_KEY and are declared as a cast. The value is authenticated, so a tampered ciphertext fails to decrypt rather than returning garbage.

final class class BankAccount extends Model
{
    protected fillable = ['holder', 'iban_encrypted', 'bic_encrypted'];

    protected function casts(): array
    {
        return [
            'iban_encrypted' => 'encrypted',        // APP_KEY, authenticated
            'bic_encrypted'  => 'encrypted:argon2id', // hashed — irreversible
        ];
    }

    public function iban(): string
    {
        // Never in toArray(), never in a resource by default.
        return decrypt($this->iban_encrypted);
    }
}

// encrypt() for reversible, hash() for verification-only.
$account->iban_encrypted = encrypt($iban);
$account->bic_encrypted  = hash('argon2id', $bic);

// Key rotation: the keyring format keeps old keys decryptable.
config()->set('app.previous_keys', [
    base64:encode(old $binaryKey32Bytes),
]);

php artisan key:rotate
# Generates a new key, keeps the previous ones, decrypts and re-encrypts data.
# Available in Laravel 11+; requires APP_PREVIOUS_KEYS to be set before running.

Rotating APP_KEY without APP_PREVIOUS_KEYS destroys every encrypted value, session, signed URL and password reset token in the application. The key is the only thing standing between a database dump and every secret in it. Set APP_PREVIOUS_KEYS before rotating, run key:rotate, and verify the re-encrypted data before removing the old key from the list.

One operational rule: APP_KEY must be identical across every instance and every release. It is the one piece of state that cannot be regenerated per deployment, and a deploy that regenerates it invalidates all sessions simultaneously and every signed URL in flight.

# .env.example must contain the key name with an empty value, never a real key.
APP_KEY=
APP_PREVIOUS_KEYS=

# In production, the key comes from the platform's secret store,
# not from a file in the release directory.

Three timeouts interact and must be ordered. The job’s timeout in the supervisor config is the longest a job may run before the worker kills it. retry_after for the Redis connection is set by Horizon to 90 seconds plus that timeout, and it is what determines when another worker may claim the job. With it off — the default — a timed-out job is retried, which is correct for an idempotent job and dangerous for one that is not.

16.3 Supervisors and balancing

What a supervisor is, how automatic balancing works, and the production process manager setup.

A supervisor is a set of worker processes reading from one or more named queues. Splitting queues across supervisors is the mechanism for protecting latency-sensitive work from bulk work, and it is more effective than raising worker counts.

'balanceMaxShift' => 1,
'balanceCooldown' => 3,  // seconds before rebalancing

// 'jobCount' scales on throughput instead. Pick one; they respond differently.

16.4 Retries, backoff and failure classification

The three retry mechanisms, and the decision of which failures are worth retrying at all.

Laravel offers three distinct mechanisms and they compose in a way that is worth understanding precisely.

MechanismDeclared asSemantics
Attemptspublic int $tries or --triesTotal number of executions, including the first
Delaypublic int $backoff or backoff()Seconds before the next attempt; an array means successive intervals
Release$this->release($seconds)Returns the job to the queue without counting as a failure; tries increments
final class class ChargeInvoice implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 6;
    public int $timeout = 45;
    public bool $failOnTimeout = true;
    public bool $afterCommit = true;

    // Absolute schedule: attempts at 0, 10, 60, 300, 900, 3600 seconds.
    public function backoff(): array
    {
        return [10, 50, 240, 600, 2700];
    }

    public function handle(PaymentGateway $gateway): void
    {
        try {
            $gateway->charge(ChargeRequest::forInvoice($this->invoiceId));
        } catch (RateLimitException $e) {
            // Transient, and the provider told us when to come back. Release without
            // counting a failure, and do not consume a try.
            $this->release($e->retryAfter());

            return;
        } catch (CardDeclined $e) {
            // Permanent. Retrying a declined card wastes 6 attempts and delays the alert.
            $this->fail(new PaymentDeclined($this->invoiceId, $e->reason()));

            return;
        } catch (ValidationException $e) {
            // Permanent and deterministic.
            $this->fail($e);

            return;
        }
    }

    public function failed(Throwable $e): void
    {
        // Called only after the final attempt, with the exception that ended it.
        $this->alerting->critical('ChargeInvoice failed', [
            'invoice_id' => $this->invoiceId,
            'exception'  => $e::class,
            'message'   => $e->getMessage(),
            'attempts'  => $this->attempts(),
        ]);
    }
}

The exception that is not caught propagates to the worker, which records the failure and applies the backoff. release() and fail() are the explicit exits: release() re-queues without a failure record, fail() writes the failed-jobs row immediately and calls failed() without consuming the remaining attempts.

Failure classExamplesAction
TransientConnection refused, 502, 503, 429, deadlockRetry with backoff
Ratelimited429 with a Retry-After headerrelease() at the indicated time
Permanent businessCard declined, account closed, validation failedfail() immediately
Deterministic defectTypeError, undefined method, missing modelfail() immediately; do not retry
Code bugSame exception for the same input, every timeAlert, fail, fix the code

Give the backoff schedule a ceiling that matches the business deadline. An invoice that must be charged within an hour should not have an attempt scheduled at 3,600 seconds. Compute the schedule as a function of the deadline rather than a fixed array, so a job with a short deadline exhausts its attempts and alerts while there is still time to act.

16.5 The failed-jobs table as an operational tool

The schema, the retry mechanics, and the alert that should fire when the table stops being empty.

The failed_jobs table stores the job UUID, the connection, queue, payload, exception and a timestamp. It is the durable record of work that was never completed, and treating it as a queue to be triaged is the difference between an incident and a data-loss event.

// The table, and the two commands that operate on it.
php artisan queue:failed
php artisan queue:retry all
php artisan queue:retry 5e6780e0-8f5f-4a3c-9d1f-2b3c4d5e6f70   # one UUID
php artisan queue:retry --queue=critical
php artisan queue:forget <uuid>

// A daily digest to Slack, and an alert when the count is non-zero.
$count = DB::table('failed_jobs')->count();

if ($count > 0) {
    Alerting::warning("$count failed jobs", [
        'by_queue' => DB::table('failed_jobs')->selectRaw('queue, count(*) as n')->groupBy('queue')->pluck('n', 'queue')->all(),
        'oldest' => DB::table('failed_jobs')->min('failed_at'),
    ]);
}

Two operational practices distinguish a codebase that recovers from one. The first is an alert on the count, not on the rate — a single failure that nobody requeues is worse than a burst of five that are. The second is a scheduled review: the oldest failure’s age is the metric that matters, because it is the time since some piece of work silently stopped happening.

// bootstrap/app.php — the daily triage job
->withSchedule(function (Schedule $schedule) {
    $schedule->command('queue:prune-failed --hours=720')->daily();
    $schedule->command('"report:failed-jobs --older-than=1h')->hourly()->withoutOverlapping();
    $schedule->command('"horizon:snapshot')->everyFiveMinutes();
})

# Scheduler must run every minute. One instance, or onOneServer() for clusters.
* * * * * cd /var/www/app && php artisan schedule:run >> /dev/null 2>&1

Retrying an entire failed batch is a way to cause an incident. queue:retry all replays every failed job, including the ones that failed permanently — the declined cards and the deterministic type errors. They will fail again, filling the table, alerting, and consuming the attempts of jobs that could have succeeded. Requeue by exception class or by queue, in small batches, and confirm the cause is fixed before replaying.

Prune both tables, with retention matched to the debugging horizon. queue:prune-batches and queue:prune-failed keep the tables bounded; a table that has never been pruned is a table that eventually slows down every dashboard query against it. Thirty days is a reasonable default, longer if the release cycle justifies it, and never zero.

17.2 The deploy script, step by step

The correct order of a deploy, and the specific reason each step must precede the next.

The ordering below is not a convention; each position exists because of a specific failure that occurs if it moves.

#!/usr/bin/env bash
set -euo pipefail

APP=/var/www
REPO=$APP/repo
COMMIT=$(git -C $REPO rev-parse --short HEAD)
RELEASE=$APP/releases/$(date -u +%Y-%m-%dT%H-%M-%S)-$COMMIT

# 1. Build the new release WITHOUT touching the current one.
mkdir -p $RELEASE
git -C $REPO archive $COMMIT | tar -x -C $RELEASE
cp -r $REPO/storage $RELEASE/storage            # then replace with the symlink
rm -rf $RELEASE/storage
ln -s $APP/shared/storage $RELEASE/storage
ln -s $APP/shared/.env $RELEASE/.env

cd $RELEASE

# 2. Dependencies. --no-scripts, so migrations do not run here.
composer install --no-dev --optimize-autoloader --classmap-authoritative --no-scripts -q

# 3. Build-time optimisation. Fails loudly rather than at request time.
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache
php artisan storage:link

# 4. Migrations. Additive, backward-compatible, online (chapter 6).
php artisan migrate --force --no-interaction

# 5. Switch traffic. This is the only user-visible instant.
ln -sfn $RELEASE $APP/current.new
mv -T $APP/current.new $APP/current

# 6. Reload long-lived processes so they pick up the new code.
sudo systemctl reload php8.3-fpm
php artisan queue:restart                 # or: horizon:terminate
php artisan horizon:purge

# 7. Prune. Keep the five most recent releases.
cd $APP/releases
ls -1dt */ | tail -n +6 | xargs rm -rf

echo "Deployed $COMMIT to $RELEASE"

Step 2 uses --no-scripts deliberately. Composer’s default post-autoload-dump script runs package:discover, and some packages register a post-autoload-dump hook that runs migrations. Running those against production from inside composer install means the deploy has no clean point at which to inspect what the migration will do.

Step 5 uses mv -T rather than ln -sfn because the latter is not atomic across all shells and follows symlinks in some implementations. mv -T replaces the symlink itself, which is a single atomic rename on the same filesystem.

Step 4 before step 5 means the migration must be compatible with the code that is still running. That is the expand phase of chapter 6, and it is the single constraint that determines the deployment strategy. A deploy script that migrates after switching traffic applies a schema change to a version of the code that has already stopped receiving requests — which is safe, but only for additive changes. For anything else, the expand/migrate/contract sequence with a deploy between each phase is not optional.

17.4 Rollback and the migration problem

Why a code rollback and a schema rollback are separate operations with different guarantees.

Rolling back the code is a symlink change. Rolling back a migration is a data operation with an irreversible step in most cases. The two must be reasoned about separately, because the combination is what breaks.

Change typeCode rollbackSchema rollback
Additive columnSafe — the old code ignores itOptional; the column is unused by the old code
New indexSafeOptional; dropping it locks, so usually leave it
Column renameBreaks immediately unless the expand phase is in placeImpossible to reverse without the data
Column type changeBreaks if the old code expects the old typePossibly lossy
Dropped columnOld code may still read itIrreversible — the data is gone
New NOT NULL column with no defaultOld code’s inserts failMust be dropped to restore, or defaulted
#!/usr/bin/env bash
# Rollback: code only. Never migrate:down as part of a rollback.
ln -sfn /var/www/releases/2026-03-01T09-14-52-3b9d0f4 /var/www/current.new
mv -T /var/www/current.new /var/www/current
sudo systemctl reload php8.3-fpm
php artisan queue:restart
php artisan config:clear && php artisan config:cache

# A "down" method that is safe to run after a rollback.
public function down(): void
{
    // Removing a column the current code needs is worse than leaving it.
    // Document the reason; do not write a destructive down() by reflex.
}

A down() method is not required to be implemented, and a wrong one is worse than a missing one. Laravel allows down() to be empty. For a column rename, a type narrowing or a data backfill, there is no correct automatic reversal. The only safe default is a no-op with an explanatory comment, and the reversal is a forward migration in a new release.

Because of this, the practical rollback strategy is forward-only. If a release causes an incident, the response is to revert the code, restore service, and then either fix forward in the next release or, if the schema itself is the problem, stop all writers and reverse the data operation deliberately with a runbook that was written before it was needed.

18.1 Structured logging and context

The log record format that makes logs aggregatable, and the context that makes one record traceable.

A log line is only useful if it can be found and correlated. Three things achieve that: a channel, a timestamp at a known precision, and a correlation identifier present on every record belonging to one request or one job.

The context is added once, in a middleware, and is then available to every log record, every exception report and every outbound HTTP header for the rest of the request. That is what makes a single user report traceable to the exact request, the queries it issued, the jobs it dispatched, and the third-party calls it made.

final class class EstablishRequestContext
{
    public function handle(Request $request, Closure $next): Response
    {
        $traceId = $request->header('X-Trace-Id') ?? (new Ramsey\Uuid\Uuid)->uuid4()->toString();

        Context::add([
            'trace_id'  => $traceId,
            'request_id' => (string) $request->header('X-Request-Id', $traceId),
            'user_id'   => $request->user()?->id,
            'tenant_id' => $request->user()?->tenant_id,
            'route'     => $request->path(),
        ]);

        $request->headers->set('X-Trace-Id', $traceId);

        try {
            $response = $next($request);
        } finally {
            Context::add(['status' => $response?->getStatusCode() ?? 500]);
        }

        return $response;
    }

    public function terminate(Request $request, Response $response): void
    {
        $response->headers->set('X-Trace-Id', Context::get('trace_id'));
    }
}

// Propagate to outbound calls so a trace spans services.
Http::withHeaders(['X-Trace-Id' => Context::get('trace_id')])->get(...);

Never log a request body, an authorisation header or a card number. The default exception handler does not log them, which is correct. A bespoke "log the request for debugging" middleware is the most common way they enter a log store, and a log store is usually replicated to a third-party aggregator with a much weaker access control than the database it was copied from. If request-level debugging is required, log a hash of the body and a list of its keys.

18.2 Log channels and sampling

Routing log records to different destinations, and controlling volume so the signal survives.

Separating channels is what allows an operational question to be answered without searching everything. Security events, payment events, and application debug output have different retention requirements, different access control, and different audiences.

Log::channel(['security', 'stderr'])->info('auth.login.failed', [
    'email_hash' => hash('sha256', strtolower($email)),
    'ip'         => $request->ip(),
    'ua'         => $request->userAgent(),
    'attempts'   => $attempts,
]);

Log::channel('payments')->critical('payment.failed', $context);

// Sampling: keep 100% of errors and 1% of successes.
Log::channel(['stderr'])->when(function (LogRecord $record) {
    if (in_array($record->level, ['error', 'critical', 'alert', 'emergency'], true)) {
        return true;
    }

    return random_int(1, 100) <= 1;
})->debug('cache.hit', $context);

The volume problem is the reason a log store eventually becomes useless. A busy endpoint at 200 requests per second with five records each produces 1,000 records per second, which exceeds the ingestion budget of most providers and exceeds the review capacity of any human. Three techniques keep it usable: log at info for business events and debug for diagnostics, with LOG_LEVEL=info in production; sample the successful-path records; and never log a record that contains no actionable information.

    public function request(Request $request, Response $response, float $seconds): void

Unbounded label cardinality is the fastest way to take down a metrics backend. A label containing a user id, an order number, a full URL or a bound SQL value multiplies the time series by the number of distinct values — and it is a remote-code-execution vector when the label value reaches a label that the backend evaluates. Queue metrics deserve particular attention, because a queue failure is invisible from the application’s own error rate. The three that matter are depth, wait time and failure count. Horizon’s /api/stats endpoint exposes all three and is designed to be scraped; a scheduled horizon:snapshot writes them to a store for longer retention than a Prometheus scrape interval gives.

18.4 Distributed tracing

What tracing adds over metrics, and the framework integration points.

Metrics tell you that p99 latency on orders.index rose to four seconds. Tracing tells you which of the 240 spans in one of those requests consumed the time. The two are complementary: metrics are cheap and always on, traces are expensive and sampled.

// OpenTelemetry via the automatic Laravel instrumentation in contrib.
// Spans are created for: the request, each DB query, each Redis command,
// each outgoing HTTP call, each queued job, and each Artisan command.

// Manual spans for the parts the automatic instrumentation cannot see.
$span = Tracer::current()->spanBuilder('pricing.calculate')
    ->setAttribute('pricing.rules_evaluated', $rules->count())
    ->setAttribute('pricing.tier', $tier)
    ->startSpan();

try {
    $price = $calculator->calculate($cart, $context);
    $span->setAttribute('pricing.total_minor', $price->minor);

    return $price;
} catch (Throwable $e) {
    $span->recordException($e);
    $span->setStatus(StatusCode::STATUS_ERROR);

    throw $e;
} finally {
    $span->end();
}

// Attributes must be low-cardinality. Never a user id or an amount with cents.

Two propagation details matter. A queued job crosses a process boundary, so the trace context must be serialised into the job and restored on the worker, or a request that dispatches a job produces two unrelated traces. And the trace identifier must be attached to the log context so a log search and a trace search find the same thing — the same trace_id from 18.1 is what joins them.

final class class PropagateTraceContext
{
    public function handle(JobProcessing $event): void
    {
        $payload = $event->job->payload();

        $context = $payload['trace_context'] ?? null;

        if (is_array($context)) {
            GlobalTracer::get()->spanBuilder('queue.process')
                ->setParent(
                    Context::getCurrent()->withRemoteParent(
                        SpanContext::fromTraceParent($context['traceparent')
                    )
                )->startSpan()
                ->activate();
        }

        Context::add(['trace_id' => $context['trace_id'] ?? null]);
    }

    public function handleJobProcessed(JobProcessed $event): void
    {
        Context::forget(['trace_id']);
    }
}

Sample by decision, not uniformly. A trace collector that stores every request for a busy service will exceed its budget; one that samples 1% uniformly will miss the slow requests, which are the ones that matter. Sample all errors, all requests above a latency threshold, and a small percentage of the rest. This requires the sampling decision at the edge, before the application runs.

18.5 Health checks and readiness

The two distinct health checks, and the checks that must not be included in either.

Laravel ships /up through withRouting(health: '/up'). It returns a 200 while the application can serve a request. That is a liveness check, and it is the only one the framework’s built-in route performs.

// bootstrap/app.php — a liveness route. No database, no cache, no queue.
->withRouting(health: '/up', web: ..., api: ...)

// A readiness route that verifies the dependencies actually needed to serve traffic.
final class class ReadinessController extends Controller
{
    public function __invoke(DB $db, Cache $cache, Queue $queue): JsonResponse
    {
        $checks = [];

        $checks['database'] = $this->time(function () use ($db) {
            $db->select('SELECT 1');            // a real round trip, not a config read

            return true;
        });

        $checks['cache'] = $this->time(function () use ($cache) {
            $cache->put('__health', 1, 10);

            if ($cache->get('__health') !== 1) {
                throw new RuntimeException('cache read-after-write failed');
            }

            return true;
        });

        // Do not check the queue: a backlog is not a readiness failure.

        $healthy = ! in_array(false, $checks, strict: true);

        return response()->json([
            'status'     => $healthy ? 'ok' : 'unavailable',
            'version'     => config('app.release'),
            'commit'      => config('app.commit'),
            'checks'     => $checks,
            'queue_depth' => Redis::connection()->llen('queues:default'),
        ], $healthy ? 200 : 503);
    }

    private function time(callable $check): float|false
    {
        $start = hrtime(true);

        try {
            $check();

            return round((hrtime(true) - $start) / 1e6, 1);
        } catch (Throwable $e) {
            Log::error('readiness check failed', ['error' => $e->getMessage()]);

            return false;
        }
    }
}

A readiness check that depends on another service turns that service’s outage into yours. If the health check calls Stripe, then Stripe’s incident page lists every application that checks Stripe. Keep readiness to the dependencies that are strictly required to serve a request, with a short timeout, and report the rest as metrics with alerts instead.

Two operational properties complete the picture. The check must be fast — one second at most, because the orchestrator’s probe interval is the detection latency. And it must not require authentication, or it will fail in exactly the situation where the application is broken, hiding the real cause behind a 401.

Kubernetes readiness and liveness have opposite failure semantics. Readiness failing removes the pod from the load balancer and leaves it running to be fixed. Liveness failing restarts the pod, which is destructive and only appropriate when the process itself is unrecoverable. Point /up at liveness and the dependency check at readiness; never point both at the same URL.

19.2 Reading and tracking deprecations

The deprecation tooling, and the channel configuration that turns deprecations from noise into a work queue.

The framework’s deprecation channel is the single most useful maintenance signal available, and it is off by default beyond a log level. Turning it on in development and CI, and aggregating it in production, converts "this will break in the next major" from a surprise into a tracked item.

// config/logging.php
'deprecations' => [
    'channel' => env('LOG_DEPRECATIONS_CHANNEL', 'null'),
    'trace'   => false,
],

// A dedicated channel, retained longer than the application log.
'deprecations' => [
    'driver' => 'monolog',
    'handler' => Monolog\Handler\StreamHandler::class,
    'with' => ['stream' => 'php://stderr'],
    'formatter' => Monolog\Formatter\JsonFormatter::class,
],

The deprecation:* commands read the cached deprecation reports produced during the test run. The distinction between the three check modes is worth understanding: a typo deprecation is a call to a misspelled method, an internal deprecation is a call to something the framework has marked for removal, and a partner deprecation is a package doing the same. The first is a bug, the second is a scheduled task, the third is a dependency to upgrade.

// In CI, fail the build on framework deprecations. This is the mechanism that
// makes "upgrade before it breaks" the default rather than a project.
- name: Deprecations
  run: |
    php artisan test
    php artisan deprecation:table --stats
    if [ -n "$(php artisan deprecation:check --json | jq -r '.internal_deprecations | length')" ] &&
       [ "$(php artisan deprecation:check --json | jq '.internal_deprecations | length')" -gt 0 ]; then
      echo "::error::Framework deprecations detected. Run deprecation:table."
      exit 1
    fi

Make the deprecation count a metric, not a build failure, and ratchet it. Failing the build on a new deprecation is right, but the existing count must be reduced to zero at least once per major. A ratchet — record the current count, fail only on an increase, and lower the threshold each sprint — turns a number that cannot realistically reach zero into one that can.

19.3 Deleting code, not just adding it

The techniques for finding and removing code that is no longer needed, and the reason deletion is the highest-return maintenance work.

Code that is never used still costs: it is analysed, it is covered by tests that must be maintained, it appears in searches and confuses the next reader, and it constrains refactoring because a change to it might break something that calls it. Deleting it is the only change that reduces all of those costs at once.

// Find definitions with no references anywhere in the codebase.
composer require --dev vimeo/psalm
vendor/bin/psalm --no-cache --threads=8 | grep -i unused

// Or with PHPStan, which reports unused private members.
vendor/bin/phpstan analyse --level=8 app/ --error-format=table

// And the route list, which shows what is actually reachable.
php artisan route:list --except-vendor | grep -c closure
php artisan route:list --json | jq 'length'

// Unused configuration keys: literal strings in config/ vs get() calls.
grep -rhoE "config\('[a-z_]+\." app/ | sort -u

Never delete an applied migration. The migrations table records what has run, and a deleted migration file creates a gap: a fresh environment will never build the schema that production has. To remove a column, add a new migration that drops it, following chapter 6. The old migration file stays forever, because it is the record of how the schema was built.

# A dependency is unused if its namespace is never referenced and it registers
# no service provider. This is a grep, and it is approximate — which is
# why the removal is verified by running the test suite afterwards.
composer show --direct --name-only | while read package; do
  vendor=$(echo "$package" | cut -d/ -f2 | tr '-' '_')
  count=$(grep -rl "$vendor" app/ routes/ config/ 2>/dev/null | wc -l)
  [ "$count" -eq 0 ] && echo "$package: no direct references"
done

The highest-leverage deletion is usually a whole feature. A feature that is no longer used has code, migrations, tests, documentation, configuration, scheduled jobs and monitoring rules attached to it, and removing it produces a larger reduction in total complexity than any refactoring of the code that remains.

19.4 The dependency rotation schedule

A calendar for dependency updates that keeps each one small enough to review.

The reason dependencies are allowed to become stale is that updating a batch of them is unreviewable. The fix is to make each update small and routine, so it is never batched.

Two configuration details carry more weight than the schedule. A committed composer.lock makes the production install reproducible, and the lockfile must be deployed with the code — an application installed with composer update in the deploy script is a different application on every deploy. And roave/security-advisories as a dev dependency blocks any package version with a known advisory, which converts a vulnerability scan into a build failure rather than a report nobody reads.

Pin the PHP version in the lockfile’s platform check. config.platform.php in composer.json makes Composer resolve dependencies as though a specific PHP version were present, which prevents a package being installed on the developer’s 8.4 and then failing on the production 8.3. Set it in the repository, not only in the deploy environment.

19.5 A codebase inventory that stays true

The documentation that remains correct because it is generated, and the review rituals that keep the codebase comprehensible.

Documentation that is written by hand is correct on the day it is written. Documentation that is generated from the code is correct until the code changes. The distinction determines whether a handbook is a maintained asset or an archaeology exercise.

// Command reference, generated from the actual registered commands.
php artisan list --format=md
php artisan list --format=json | jq '.commands | keys'

// Route reference, with middleware and controller.
php artisan route:list --except-vendor
php artisan route:list --except-vendor --json | jq -r '.[] | "\(.method) \(.uri) -> \(.action)"'

// Configuration reference, from the actual config files.
php artisan config:show database
php artisan config:show queue --json

// Scheduled tasks.
php artisan schedule:list
php artisan schedule:list --json

// Event and listener map.
php artisan event:list
php artisan event:list --json | jq -r '.events[].name'

The schema diff is the highest-value of these, because it is the one that fails rather than informs. Generating the schema from a migrated database and diffing it against the last release turns "someone added a column in a migration and did not update the model" into a failing build.

# Generate the schema and diff it in CI.
php artisan schema:dump --prune
mysqldump --no-data --skip-comments --compact app | sed 's/AUTO_INCREMENT=[0-9]* //' > schema.sql

git diff --exit-code schema.sql || {
  echo "::error::Schema changed without a reviewed migration."
  exit 1
}

Two review rituals do more for comprehensability than any document. The first is a small pull request: under roughly 400 changed lines, a review is a real review, and a codebase assembled from small pull requests has uniformly shallow, well-named functions. The second is a quarterly deletion pass, which is the only mechanism that keeps the codebase from accumulating code that is technically live and practically dead.

# The five questions to ask of any module, quarterly.
# 1. Is this reachable?      route:list, grep for the entry point
# 2. Is this still needed?   product usage data, not opinions
# 3. Is this tested?          coverage report, and is the test meaningful
# 4. Does this own a decision?  which rule would change here
# 5. Who knows this?         bus factor; add a second owner or delete it

# Coverage that shows where the risk is.
php artisan test --coverage --min=70
# --min on the changed lines, not the whole codebase, in a large repository.

Give every module one sentence in the README, and keep it to one sentence. A module whose purpose cannot be stated in a sentence usually does not have one. This is the cheapest possible architecture test: if a new engineer cannot say what a directory does after reading one line, the boundary is not a boundary.
