1 ▸ Orientation

This chapter places batch in its environment: what the language actually is, how .bat and .cmd files reach the interpreter, how to create and run a first script, where the built-in help lives, and how scripts report success or failure through exit codes.

1.1 cmd.exe and the batch language

Batch is not a compiled language and has no runtime library. A batch file is a plain-text list of commands that the Windows command interpreter, cmd.exe, reads and executes one line at a time.

What a batch file actually is

Each line of a batch file is handed to cmd.exe, the Windows NT console host, which parses it, expands variables and then runs it. Internal commands such as cd, set, if, for and echo are implemented inside cmd.exe itself, while external tools — findstr.exe, where.exe, robocopy.exe — are separate executables resolved through the PATH environment variable. Because there is no compile step, a mistake on line 20 of a script is only noticed when line 20 runs, which is why careful scripts validate their inputs up front.

.bat and .cmd

Both extensions execute through cmd.exe and behave identically on modern Windows. The distinction is historical: on 16-bit Windows, a .bat file launched from a DOS context ran under COMMAND.COM, which could switch off command extensions mid-import, while .cmd always ran under cmd.exe and preserved them. In practice, prefer .cmd for new scripts so that for, if /i, setlocal and the %~dp0 argument modifiers are guaranteed to be available.

The skeleton every script starts from

Three lines do the heavy lifting in almost every real script. @echo off stops commands being echoed back before they run — the @ suppresses just that one line. setlocal gives the script its own variable scope. enabledelayedexpansion turns on the !var! syntax so a variable inside a loop or parenthesised block is re-read when the line runs, not when it was parsed.

@echo off
setlocal enabledelayedexpansion
rem --- your script body goes here ---
endlocal

:: hello.cmd - greet whoever runs the script
@echo off
setlocal enabledelayedexpansion
set "NAME=%USERNAME%"
echo Hello, %NAME%!
echo We are running from %CD%.
pause
endlocal
The :: double-colon is the traditional comment leader. It is not documented as a comment, so one warning applies: :: can behave oddly inside parenthesised blocks; use rem there.

1.2 Creating and running a script

A script is just a text file that Windows has associated with the interpreter. How you save it and how you launch it change what you see on screen.

Saving the file: encoding and the BOM

Notepad defaults decide the bytes that cmd reads. cmd.exe interprets the file using the console code page, normally 437 or 1252; chcp 65001 switches it to UTF-8 at runtime. Two traps follow: a UTF-8 byte-order mark written at the start of the file becomes part of the first command, so @echo off can fail silently — save without a BOM — and characters outside the active code page are mangled. Either keep files in the legacy code page or switch code page as the first real statement.

:: utf8.cmd - run under UTF-8 after chcp 65001
@echo off
chcp 65001 >nul
echo Café and Zürich now render from a UTF-8 file.
pause

Launching from a prompt or from Explorer

Double-clicking a batch file in Explorer starts it through the registered association, and the console window closes the moment the script ends — the reason scripts end with pause. From within an existing cmd window, typing the file name runs it in the same window; cmd checks the current directory before it searches PATH, so hello.cmd works without a .\ prefix. Dragging a file onto the script in Explorer passes that file's path as the first argument. What you see when echo is left on explains why @echo off is the first line of almost every file:

C:\scripts>hello.cmd

C:\scripts>rem  hello.cmd - greet whoever runs the script
C:\scripts>echo Hello, Amin.
Hello, Amin.
C:\scripts>pause
Press any key to continue . . .

How echo and echo off interact

Echo state is a script property, not a window property. Once a file has run echo off — with or without the @ — the state applies to the rest of that file only. Turning it back on shows exactly why the convention exists:

@echo off
echo one
echo on
echo two
echo off
echo three

Output shows one, then the literal line echo two being printed as C:\>echo two before its output, then the same for echo off, then quietly three. Note that echo on and echo off echo the current state when typed bare, which is how you inspect it.

1.3 Help that ships with Windows

You never need to memorise batch syntax: every command can print its own reference, and the reference lives on the machine you are already using.

The help command

Typing help lists the internal commands. help for, help set and so on print the full syntax page for that command — the same text you get from the command's own /? switch. The pages are terse and assume you know the conventions, but they are complete and authoritative.

help
help for
help setlocal
help call

Every command documents itself with /?

Running command /? displays that command's syntax and, crucially, the exit codes and the modifiers. for /? is the definitive reference for the for syntax including the usebackq and tokens options; set /? documents substring and replacement expansion; cmd /? documents the interpreter's own switches such as /c (run and close) and /k (run and stay open).

for /?
set /?
if /?
cmd /?

Finding the interpreter and the online reference

where resolves where an executable on PATH actually lives, which is the first debugging step when a script works interactively but fails under a service account. ver prints the Windows version. Microsoft's online "Windows Commands" documentation mirrors the /? text and adds examples; it is the reference to reach for when a flag does something surprising.

where cmd
where findstr
ver

1.4 Exit codes: how scripts report success

Every program in a batch script, and the script itself, communicates its outcome through a single integer: the exit code. Reading and returning it correctly is the foundation of every later chapter.

What an exit code is

A finished process hands a 32-bit integer back to its parent. By convention 0 means success and any non-zero value means failure, but the specific numbers are per-command: findstr returns 0 for "match found", 1 for "no match" and 2 for "error"; robocopy returns a bitmask where even success can be a number above zero. The pseudo-variable %errorlevel% holds the code of the last command that ran.

@echo off
dir no-such-folder-xyz
echo The directory check returned %errorlevel%.

Expect 1. A missing argument or bad flag in dir is an error, and the script's own next line sees it.

Returning a code from your own script

exit /b N ends the script and sets its exit code to N without closing the console window — the form to use inside a script launched from a prompt. A bare exit (no /b) also terminates the whole cmd window, which is almost never what a script wants. Scripts called from other scripts read the returned code through %errorlevel% after the call.

@echo off
if "%1"=="--clean" (
  echo leaving with code 5
  exit /b 5
)
echo continuing normally
exit /b 0

Acting on codes without an explicit check

The operators && and || branch on the previous command's exit code directly: && runs the next command only on success (code 0), || only on failure. They are the tersest way to express "do this, and if it worked, do that".

@echo off
dir C:\Windows && echo Windows folder reachable || echo Windows folder missing
dir C:\no-such-folder && echo surprising || echo expected failure
Chaining consumes the exit code: after a && b, %errorlevel% is whatever b (or the skipped command) left, not a's code. If the original code matters, capture it into a variable first.

2 ▸ Commands and Navigation

2.1 The current directory2.2 Listing files with dir2.3 Copying, moving and mirroring files2.4 Deleting and managing files

Chapter two covers the everyday file and directory commands a script is built from: moving around the filesystem, listing files, copying and mirroring trees, and deleting and managing them. These commands are also the raw material the looping constructs in chapter four iterate over.

2.1 The current directory

Batch has a per-process current directory, and most commands interpret relative paths against it. Controlling the current directory precisely is the first habit of robust scripts.

cd and its /d switch

Bare cd prints the current directory; cd path changes it. .. is the parent, \ the root of the current drive, and paths with spaces must be quoted. The one switch that newcomers miss is /d: without it, cd D:\data from C:\ prints the directory but does not leave drive C:. With /d the change is real and stays.

cd
cd C:\Windows\System32
cd ..\..
cd /d D:\data
cd "%USERPROFILE%\Documents\My Projects"

pushd and popd: enter, then always return

pushd path saves the current directory on a stack and changes into path; popd restores the top of the stack. The pair guarantees that a script's working directory ends where it began even if later logic fails — and pushd to a UNC path such as \\server\share temporarily maps a drive letter for it, removing the mapping again on popd. The technique also protects the caller's directory against a buggy script that forgot to cd back.

@echo off
pushd "\\server\share\docs"
echo Now inside %CD%
popd
echo Back in %CD%

%CD% — the directory as a value

%CD% expands to the current directory as a string value, so it can be embedded in variable assignments. %__CD__% is the same value with a trailing backslash. Building absolute paths from %CD% or %~dp0 (chapter three) instead of hard-coding them is what lets a script run identically from anywhere.

@echo off
echo Working in %CD%
set "appdir=%CD%\app"
echo The app directory will be %appdir%
A path containing & — a folder named R&D, say — must always be quoted, or the & will be treated as a command separator.

2.2 Listing files with dir

dir is the workhorse for seeing what exists and, with the right switches, for feeding filenames into other commands.

The core switches every script uses

dir /b prints bare file names only — one per line, no headers, no totals — which is the form designed for piping and for /f parsing. /s recurses into subdirectories, /o:n sorts by name, /p pauses between pages of on-screen output, and /w uses the wide multi-column layout.

dir
dir /b /o:n *.log
dir /s /b C:\Windows\*.ini
dir /p /s C:\Windows

Filtering with attribute letters and wildcards

/a: filters on attributes: /a:d directories only, /a:h files with the hidden attribute, /a:-h everything except hidden, each attribute letter optionally prefixed by - to negate. Wildcards follow the DOS rules: * matches any run of characters, ? exactly one. Note dir *.txt also matches files with a .txtx extension because of how the 8.3 short-name matching works — a classic surprise.

dir /b /a:d
dir /b /a:h "%USERPROFILE%"
dir /b /a:-h *.log
dir /s /b /a:d C:\

Feeding dir output into other commands

Because /b output is one clean name per line, it slots straight into a pipeline: filter with findstr, count lines with find /c, or redirect the whole list to a file that another script consumes later.

dir /b *.log | findstr /i "error"
dir /s /b *.tmp > temp-files.txt
dir /b | find /c /v ""

2.3 Copying, moving and mirroring files

Windows provides three copy commands of increasing power. Choosing between them is choosing how much you trust the destination to match the source.

copy — the everyday file duplicator

copy source dest copies single files or matched sets. /y overwrites existing destinations without prompting (the prompt otherwise appears when stdin is interactive — inside scripts this hangs). The lesser-known form copy a.txt + b.txt combined.txt concatenates files. copy /v verifies each written byte; it is slower but cheap insurance for a one-off critical file.

copy config.ini config.ini.bak /y
copy *.c C:\archive\ /y
copy a.txt + b.txt combined.txt

xcopy — trees, options and exit codes

xcopy copies directory trees: /s copies subdirectories (except empty ones), /e also creates empty subdirectories, /i assumes the destination is a directory, /d copies only files newer than the destination's, and /y suppresses prompts. Its exit codes are meaningful: 0 success, 1 nothing found to copy, 2 aborted by the user, 4 initialisation or permission error, 5 disk-write error.

xcopy C:\app D:\deploy /s /e /i /y
xcopy C:\app D:\deploy /s /e /i /y /d

robocopy — the modern workhorse

robocopy is the reliable choice for real backups. /mir mirrors the tree — deleting files in the destination that no longer exist in the source — while /e alone only adds. /mt:N multithreads the copy, /r:N and /w:N limit retries and the wait between them (the defaults, 1 million retries, will stall a matter of hours), and /log:file writes a transcript. Robocopy's exit code is a bitmask: 0 nothing copied, 1 files copied, 2 extra files, 4 mismatches; any value under 8 is success, 8 or above is a real error.

robocopy C:\data D:\backup /mir /r:2 /w:1 /log:backup.log
robocopy C:\data D:\backup /e /xo /mt:16
Never test robocopy's result with if errorlevel 1 echo failed — a perfect copy with changes returns 1 and you would report the wrong thing. See chapter seven for the correct if errorlevel 8 test.

2.4 Deleting and managing files

Creating, renaming, moving and removing files is the destructive side of the job; these commands are where a wrongly quoted variable costs data, so read the warning at the end of each sample.

del and rmdir / rd

del /s file deletes the file from the current directory and all subdirectories; /q skips the confirm prompt. rmdir /s /q directory removes a directory tree without asking — /s is what lets it delete a non-empty tree, and /q suppresses the prompt. rd is a synonym. Both are silent and permanent: there is no recycle bin. The destructive one-liner del /s /q build\*.o is safe only if build is a variable you proved is set.

del /s /q build\tmp\*.o
rmdir /s /q build\tmp
cd build && rmdir /s /q tmp

mkdir, ren and move

mkdir (or md) creates a directory and, unlike most shells, creates missing intermediate directories in one go: mkdir a\b\c makes all three. ren renames a file or directory without moving it. move relocates a file or directory to another folder and can rename in the same operation when both paths are on the same volume.

mkdir releases\v1\logs
ren config.ini settings.ini
move settings.ini releases\v1
move releases\v1\settings.ini settings-backup.ini

attrib and where

attrib views or sets file attributes — R read-only, H hidden, S system, A archive — with + to set and - to clear. A read-only file cannot be deleted until the flag is cleared, a failure mode that shows up as "Access is denied" in scripts. where searches PATH for an executable and with /r walks a whole tree for any name pattern.

attrib +r notes.txt
attrib -r notes.txt
where python
where /r C:\tools *.exe
Quote every path variable before it reaches del, rmdir or move: an empty variable produces del /s /q \*.o, which attempts to delete from the root of the current drive. Check if defined (chapter four) before any destructive command on a variable-sourced path.

3 ▸ Variables, Arguments and the Environment

3.1 set: creating and reading variables3.2 Expansion timing and the !var! form3.3 Arguments passed to a script3.4 The environment, the clock and keyboard input

Variables are the memory of a batch script. This chapter covers creating and reading them, the delayed-expansion syntax that fixes the language's most confusing parser behaviour, the arguments a script is invoked with, and the environment, clock and keyboard input a script inherits or requests.

3.1 set: creating and reading variables

There is one command for creating a variable, and the difference between its safe and unsafe forms is a trailing-space bug waiting to happen.

Setting values without surprises

set NAME=value creates NAME. Spaces are significant: set NAME = Amin creates a variable literally named NAME (with a trailing space) holding the value Amin, so comparisons later fail invisibly. The robust form is set "NAME=Amin" — the quotes keep stray spaces out of both the name and the value while the value itself may still contain spaces. Never write a space before the =.

@echo off
set "NAME=Amin"
set "MESSAGE=Hello %NAME%"
echo %MESSAGE%

Reading variables and detecting an empty one

%NAME% expands to the value. An undefined variable does not raise an error — it expands to an empty string. That makes an empty-or-missing variable indistinguishable from a set-but-empty one, and the standard test is to compare the quoted expansion against the empty string. set with no arguments lists every variable in the current environment.

@echo off
set "A="
if "%A%"=="" (echo A is set but empty) else (echo A has a value)
if "%NOTSET%"=="" echo NOTSET is missing entirely
set

set /a arithmetic

set /a NAME=expression evaluates an integer expression: + - * / % ( ) with normal precedence, increments via +=, and hexadecimal (0x) and octal (leading 0) literals. The modulo operator uses the double percent in a file — %% — and handing it a number such as 08 fails because that reads as invalid octal, a genuine surprise for anyone writing date math.

@echo off
set /a X = 5 + 3 * 2
echo X is %X%
set /a X += 10
set /a DICE = %RANDOM% %% 6 + 1
echo You rolled %DICE%
set /a HEX = 0x1F
echo 0x1F is %HEX%

3.2 Expansion timing and the !var! form

Batch expands %var% when a line is parsed, not when it runs. Inside a loop or parenthesised block that one fact silently produces wrong values, and !var! exists to fix it.

Why %var% lies inside blocks

cmd reads a whole parenthesised block or for body as one unit, expands every %var% in it at that moment, and only then starts executing lines. A variable changed inside the block therefore still holds its parse-time value everywhere in the block, and even more confusingly, a variable created inside the block is expanded to empty throughout it. The classic symptom:

@echo off
set "N=0"
for %%f in (a b c) do (
  set /a N+=1
  echo file %%f is number %N%
)

Every line prints "number 0": %N% was resolved with the parse-time value and never re-read.

enabledelayedexpansion and !var!

setlocal enabledelayedexpansion switches on a second expansion syntax: !var! is evaluated as each line runs, not when its block was parsed. The same loop written with !N! prints 1, 2, 3. The common convention is to keep using %var% for values fixed at parse time and !var! for anything the script itself changes within a block.

@echo off
setlocal enabledelayedexpansion
set "N=0"
for %%f in (a b c) do (
  set /a N+=1
  echo file %%f is number !N!
)
endlocal

Percent signs in files versus at the prompt

Inside a batch file, for metavariables are written doubled — %%f — while the identical loop typed interactively at a prompt uses %f. The parser itself gives the reason: at the prompt, %f would be interpreted as variable f. The doubling rule extends to any literal percent sign you want echo to print: echo 100%% outputs 100%, and a lone ^% (caret-escaped) outputs a single %.

@echo off
echo 100%% ready
echo The percent sign looks like this: ^%
for %%f in (a b) do echo item %%f

3.3 Arguments passed to a script

Arguments arrive in a fixed set of slots. Understanding the slots — and the modifiers that transform them into full paths — is what turns a script from a one-trick file into a reusable tool.

%0 through %9 and %*

%0 is the script's own name as it was invoked, %1 through %9 the first nine arguments in order, and %* all arguments exactly as typed — a single string that passes through unchanged. A tenth argument is beyond %9; reaching it requires shift.

@echo off
echo Script invoked as: %0
echo First argument:    %1
echo Second argument:   %2
echo Everything passed: %*

shift: walking past nine arguments

shift moves every slot down one: %2 becomes %1, and so on, freeing %9 for a tenth argument. A typical loop consumes arguments until %1 is empty, checking if "%1"=="" to stop. Because shift is destructive, capture what you need into named variables before looping.

@echo off
:next
if "%1"=="" goto :done
echo processing %1
shift
goto :next
:done
echo all arguments consumed

Argument modifiers: %~dp0 and friends

Each %N can be followed by a modifier that expands into a property of the file or directory named by the argument: %~1 strips surrounding quotes, %~f1 a full absolute path, %~d1 the drive, %~p1 the path, %~n1 the name without extension, %~x1 the extension, %~a1 attributes, %~t1 the modification timestamp and %~z1 the size. Combined modifiers such as %~dp1 and %~nx1 compose. Applied to %0, %~dp0 yields the directory containing the script itself — the one modifier every self-contained script uses to find its own files regardless of the current directory.

@echo off
echo This script lives in %~dp0
echo Its own file name is %~nx0
rem pass a file path as the first argument:
echo Full path:  %~f1
echo Size:       %~z1 bytes
echo Modified:   %~t1
echo Name only:  %~n1

3.4 The environment, the clock and keyboard input

Beyond the variables a script defines itself, it inherits a full environment, can read pseudo-variables that change on their own, and can ask the user for input.

The inherited environment

Every script starts with the environment of whatever launched it — the Explorer session, a calling script, or a scheduled task's service context. The useful ones to rely on are %PATH%, %WINDIR%, %USERPROFILE%, %APPDATA%, %TEMP% and %PROGRAMFILES%. A plain set prints them all; never assume a variable exists — a service account's environment is famously leaner than an interactive session's.

@echo off
echo Temp folder:  %TEMP%
echo Profile:      %USERPROFILE%
echo Architecture: %PROCESSOR_ARCHITECTURE%
echo Search path:  %PATH%

%errorlevel%, %date%, %time% and %random%

Four pseudo-variables change on their own. %ERRORLEVEL% holds the last command's exit code (chapter one); %CD% the current directory (chapter two); %DATE% and %TIME% the system clock at expansion time; %RANDOM% a pseudo-random number between 0 and 32767 on every read. Note that %DATE% and %TIME% formats are locale-dependent — slicing them by character position works, but the positions differ on a Dutch or Japanese system.

@echo off
echo Right now: %DATE% at %TIME%
echo A random number: %RANDOM%
findstr /c:"panic" app.log >nul 2>&1
echo The search exited with %errorlevel%

Reading input with set /p

set /p NAME=prompt text prints the prompt (with no newline) and stores one typed line in NAME. Pressing Enter with empty input leaves the variable unchanged rather than clearing it, which is why the reliable pattern assigns a default first, then overwrites: whatever the keypress leaves, the variable is guaranteed set. Guard the prompt text, not the reply — a quote or & inside the prompt string itself breaks the line.

@echo off
set "name=Anonymous"
set /p "name=What is your name? "
echo Hello, %name%!
if "%name%"=="Anonymous" echo (you pressed Enter and kept the default)

4 ▸ Control Flow

4.1 if, else and comparisons4.2 exist, defined and errorlevel tests4.3 for loops: lists, directories, recursion and numbers4.4 goto and labels

Control flow is where a script stops being a list of commands and becomes a program: conditional branches with if, file and variable tests, the for loop in its four forms, and goto with labels. Chapter three's delayed expansion reappears here — blocks are exactly where parse-time expansion bites.

4.1 if, else and comparisons

The if command is the only branching construct. Its quoting habits and its numeric and case-insensitive modes cover most decisions a script makes.

The if statement and its parentheses

if condition (command) else (command) groups multiple commands in parentheses — the multi-line block form used throughout this guide. Two conventions matter. First, quote every operand: if "%var%"=="install", because an empty %var% would otherwise produce if ==install and a syntax error. Second, put the opening parenthesis on the same line as the condition and else on the same line as the closing parenthesis of the first block; a line break in the wrong place splits the structure.

@echo off
if "%1"=="install" (
  echo Installing...
  copy app.dll deploy\
) else (
  echo Usage: %~nx0 install
  exit /b 1
)

Case-insensitive and numeric comparisons

if /i makes string comparison case-insensitive. Comparing numbers with == is wrong — "10"=="2" is false because string comparison is lexical — so numeric tests use the six operators equ, neq, lss, leq, gtr and geq, and these accept either quoted or unquoted operands. Chained else if builds a switch without goto.

@echo off
set /a score=72
if %score% GEQ 90 (
  echo grade A
) else if %score% GEQ 75 (
  echo grade B
) else (
  echo grade C
)
if /i "%1"=="yes" echo affirmative

Blocks are parsed as one unit

A whole parenthesised block is parsed once, and that has consequences: variables changed inside it take their new values only after the block ends, and %var% inside the block holds its pre-block value for all of it. The fix is the !var! form from chapter three, enabled with setlocal enabledelayedexpansion. Any script that assigns variables inside a block should start with that line.

@echo off
setlocal enabledelayedexpansion
set "total=0"
for %%f in (1 2 3) do (
  set /a total+=%%f
  echo after adding %%f total is !total!
)
echo grand total %total%

4.2 exist, defined and errorlevel tests

Three specialised conditions answer the questions a script asks constantly: does this file exist, is this variable set, and did the last command succeed.

if exist: files and folders

if exist path is true when the path exists, and works for both files and folders. Quote the path so a space or & inside it does not end the condition early. A standalone trailing backslash — if exist "C:\Temp\" — is the way to test for a directory specifically, since a file could otherwise match. if not exist is the corresponding guard for creating things idempotently.

@echo off
if exist "config.ini" (
  echo config.ini found
) else (
  echo config.ini missing - writing defaults
  copy default.ini config.ini
)
if exist "C:\Temp\" echo the Temp folder exists
if not exist "logs" mkdir logs

if defined: is the variable set

if defined NAME tests whether a variable exists, without caring about its value. This is the correct gate before a destructive command that uses a variable in its path — see the warning in chapter two — because an unset variable would delete against an empty path. Note that a variable set to an empty value is removed by that assignment, so if defined and "set but empty" are the same thing.

@echo off
set "DEBUG=1"
if defined DEBUG echo Debug mode is on
set "DEBUG="
if not defined DEBUG echo Debug mode has been cleared
set "builddir=%CD%\build"
if defined builddir if exist "%builddir%" rmdir /s /q "%builddir%"

if errorlevel N means "N or greater"

if errorlevel N is true when the last command's exit code is N or higher — a rank test, not an equality test. Because of that, the checks must run highest-first: if errorlevel 2 before if errorlevel 1, or the lower test always wins. This form has one major advantage inside blocks and loops: unlike %errorlevel%, it is re-evaluated at run time, so it does not need delayed expansion.

@echo off
findstr /i "error" app.log
if errorlevel 2 echo input file could not be read
if errorlevel 1 echo no matching lines found
if errorlevel 0 echo search completed normally

4.3 for loops: lists, directories, recursion and numbers

for has four distinct shapes. The metavariable is %%v in a file and %v at a prompt — miss the doubling and the loop body never sees a value.

for over a list of items

for %%v in (a b c) do command iterates the space-separated items. This is the form used to loop over command-line residues after shift, over file wildcards (for %%f in (*.log) do ...), and over literal sets. The loop variable is a single letter, case-insensitive, and its modifiers from chapter three apply directly to it.

@echo off
for %%v in (red green blue) do echo colour: %%v
for %%f in (*.log) do echo log file: %%f
rem one-line form with a body:
for %%i in (1 2 3) do (echo number %%i & echo next)

for /d and for /r

for /d %%d in (paths) do ... iterates directory names instead of files, including matching the wildcard against names only — which is how you loop the subfolders of a project. for /r root %%f in (*.txt) do ... walks the directory tree below root and yields each matching file with its full path, the building block of whole-tree operations such as "delete every .tmp below this folder".

@echo off
for /d %%d in (*) do echo subfolder: %%d
for /r C:\src %%f in (*.cs) do echo source file: %%f
for /r "" %%f in (*.bak) do del /q "%%f"

for /l: counting loops

for /l %%v in (start,step,end) do ... generates a numeric sequence — start, then start+step, and so on until it passes end. A negative step counts down. This is the form for "repeat N times" or index arithmetic; the variable arrives pre-expanded as %%v on each iteration, so delays are needed only for variables you mutate yourself.

@echo off
for /l %%i in (1,1,5) do echo iteration %%i
for /l %%i in (10,-2,2) do echo countdown %%i
rem build a sequence of log files: log1.txt ... log3.txt
for /l %%i in (1,1,3) do echo run %%i > log%%i.txt

4.4 goto and labels

Labels give a script landmarks; goto jumps between them. Modern batch still needs goto for user confirmation loops and for bailing out of the middle of a script.

Labels and unconditional jumps

A label is a line beginning with : followed by a name; the :label line itself does nothing when execution reaches it — it is a marker. goto :label jumps to it. Label names are case-insensitive and may contain letters, digits, underscore and a few symbols. Two labels with the same name are not an error; goto silently takes the first, which makes duplicate names a debugging trap. The special label :eof always means the end of the file.

@echo off
goto :start
echo this line is never reached
:start
echo execution starts here
if "%1"=="" goto :eof
goto :start

goto as the error-exit pattern

Branches fanning out to :ok and :fail labels keep a script readable when the alternative is deeply nested parentheses. Because goto abandons the surrounding block entirely, jumping to a label after a failed step skips every later step cleanly — the primitive version of exception handling available to batch.

@echo off
if not exist "input.csv" goto :missing
if not exist "tool.exe" goto :missing_tool
echo running the tool...
tool.exe input.csv
if errorlevel 1 goto :failed
echo succeeded
exit /b 0

:missing
echo input.csv is absent
exit /b 2

:missing_tool
echo tool.exe is absent
exit /b 3

:failed
echo the tool returned an error
exit /b 1

Structured alternatives to goto spaghetti

Heavy use of goto produces the legendary spaghetti batch file. The structured alternatives are: call :label for reusable code with a return address (chapter six), for /f for iterating data (chapter five), and nested else if chains for decisions. Keep goto for one thing file-level control flow genuinely needs: user loops that must be re-entered, and top-of-script validation that must skip to the end.

@echo off
set /p "again=Loop again? (y/n) "
if /i not "%again%"=="y" exit /b 0
echo looping once
goto :eof

5 ▸ Strings and Text Handling

5.1 find and findstr — searching text5.2 for /f — parsing files, tokens and command output5.3 Substrings and substitution5.4 Escaping metacharacters

Text is the native data format of batch: files arrive as lines, configuration is key-value text, and logs are lines of it. This chapter covers searching text, parsing it into variables with for /f, and the substring and substitution expansion operators that edit a string in place.

5.1 find and findstr — searching text

Two search commands cover the spectrum between literal substrings and full regular expressions; both return codes a script can branch on.

find — literal substring search

find "text" file(s) prints matching lines. The search string is literal — no regex — and must be quoted. Switches: /i case-insensitive, /v the lines that do NOT match, /n prefixes line numbers, /c prints a count instead of lines, /offline searches files with the offline attribute. Exit codes: 0 at least one match, 1 no match, 2 the file could not be opened. The classic line-counting idiom is find /c /v "", which counts non-empty lines.

@echo off
find /i /n "warning" app.log
find /c "ERROR" app.log
find /v "ok" status.txt | find /c /v ""

findstr — regular expressions

findstr is the regex engine: . any character, ^ start of line, $ end, [a-z] classes, \ escaping a literal metacharacter. Switch to literal mode with /c:"exact phrase", which is how spaces survive a search argument. /i ignores case, /m prints only the file name, /v inverts. Its exit codes mirror find: 0 match, 1 no match, 2 a file could not be opened.

@echo off
findstr /i "error pattern" *.log
findstr /c:"not found" *.txt
findstr /r "[0-9][0-9]:[0-9][0-9]" times.log
findstr /m "panic" *.log

Searching inside pipelines

Pipes chain a producer with a filter: list the system folder and keep only DLL files, then count them. find and findstr both read stdin when no file is named, which makes them the natural filter stage. The metacharacter trap to remember is that a literal . in findstr patterns must be written \., or it matches any character including the dot it appears to match.

dir /b C:\Windows\System32 | findstr /r "\.dll$"
dir /b C:\Windows\System32 | findstr /r "\.dll$" | find /c /v ""
type app.log | findstr /i /c:"fatal error"

5.2 for /f — parsing files, tokens and command output

for /f turns external text — a file's lines, a command's standard output, or a string — into loop iterables. It is the single most powerful text tool in the language.

Reading a file line by line

for /f %%i in (file) do ... iterates over the file's lines. With usebackq the file argument is quoted (allowing spaces in the path): for /f "usebackq" %%i in ("names.txt") do .... By default for /f splits each line on spaces and tabs and takes only the first token — the very first thing to override for whole-line handling is delims=, an empty delimiter set meaning "split on nothing". A line that is empty is skipped entirely unless handled specially.

@echo off
for /f "usebackq delims=" %%i in ("names.txt") do (
  echo Hello, %%i
)

Splitting on delimiters and selecting tokens

delims=,; splits each line on any comma or semicolon. tokens=1,3 keeps the first and third pieces, tokens=2-4 a range, and the pieces land in successive metavariables: %%a gets token 1, %%b token 2 if listed, and so on. This makes processing a simple CSV direct: no quotes handling, but perfectly serviceable for square, well-formed files.

@echo off
for /f "tokens=1,2 delims=," %%a in (users.csv) do (
  echo user %%a has email %%b
)
for /f "skip=1 tokens=2 delims==" %%v in (settings.ini) do echo value: %%v

Capturing command output

With a single-quoted argument — for /f "delims=" %%i in ('dir /b') do ... — the loop iterates over the command's output one line at a time, the way to collect a snapshot into variables. Escape characters inside the command for the outer parser: a redirection there needs a caret, as in ('dir /b 2^>nul'). skip=N discards the first N lines, and eol=; treats lines beginning with ; as comments to skip.

@echo off
for /f "delims=" %%i in ('dir /b *.log 2^>nul') do echo log: %%i
for /f "skip=1 delims=" %%i in ('type users.txt') do echo line: %%i

5.3 Substrings and substitution

Variables support two edit operators at expansion time: slicing into substrings and replacing text. Both are pure expansion — the variable itself is unchanged — which makes them safe to chain.

Slicing with %var:~start,length%

%var:~5% takes everything from index 5; %var:~5,3% takes 3 characters starting at index 5; %var:~-3% takes the last 3 characters; %var:~-6,2% the 2 characters 6 from the end. Indices are zero-based. Without delayed expansion these work anywhere, but inside a block the eaten-by-parser rule applies as for any expansion.

@echo off
set "path=C:\data\logs\gamma.log"
echo tail-3:      %path:~-3%
echo char 4-5:    %path:~3,2%
echo without C:\: %path:~3%
set "name=abcdef"
if "%name:~0,1%"=="a" echo name starts with a

Replacing text with %var:old=new%

%var:old=new% replaces every occurrence of old with new. The two sides are literal strings; either may be empty, so %var:.=% strips every dot and %var: =_% turns spaces into underscores. This is the standard way to turn a file name into a variable name or to normalise user input. Replacement happens at parse time like any expansion.

@echo off
set "version=v1.2.3"
echo dots removed: %version:.=%
set "title=My Great Project"
echo sanitised:    %title: =_%
set "ext=docs"
echo joined:       %ext:ocs=OCS%

Stripping and testing strings

Combining slicing with == comparison gives the string tests batch otherwise lacks: a prefix check via %var:~0,N%, an extension check via %~x1 on arguments, and emptiness via quoting. Because substitution does not modify the variable, edits that must stick need a fresh assignment: set "var=%var: =_%".

@echo off
set "file=report-2026.csv"
if /i "%file:~-4%"==".csv" echo a csv file
set "clean=%file:_=-%"
echo cleaned: %clean%
set "text=Hello World"
set "text=%text: =-%"
echo joined: %text%

5.4 Escaping metacharacters

Batch has ten characters with special meaning. Knowing how to print one, pass one, or keep one out of the parser is the difference between a script that runs and one that misbehaves in a way no error message explains.

The metacharacter set and the caret

The specials are & (command separator), | (pipe), < and > (redirection), ^ (escape), % (variable), ! (delayed variable), " (quoting) and the parentheses (grouping). The caret ^ escapes one character, making it literal: echo a ^& b prints a & b instead of running b as a second command. A caret cannot quote a caret at the end of a line comfortably, and inside double quotes most specials are already literal.

@echo off
echo A caret ^^ prints one caret
echo rock ^& roll
echo 50 ^| for the pipe symbol
rem enclosed in quotes the metacharacters are inert:
echo "this & that > nothing" | find /v "nothing"

Printing and echoing special characters

echo has its own peculiarities. A quoted "text" keeps the quotes in the output — quotes are echoed literally. The three characters that defeat echo are a leading < or > at the start of a value (echoed but interpreted as redirection if the parser gets first pick) and a trailing space (dropped, not printed). To print a variable that may contain specials, guard with a nesting technique or accept the limitation — this is honest batch, not a PowerShell escape hatch.

@echo off
echo The redirect symbol ">" prints fine here.
echo Pipe ^| and ampersand ^& must be caret-escaped.
echo 50%% complete

One-liners at the prompt versus files

Interaction between escape layers shows up twice. In for /f ('command') the inner command needs carets for ITS redirection and pipe — ('dir 2^>nul ^| findstr x') — because the outer parser would otherwise consume them. And in a file, % must be doubled where the interpreter expects a variable (%%f in for, %% for a literal percent in echo). Forgetting doubles in the middle of a for /f single-quoted command is the commonest source of "flickering" scripts that work at the prompt but not from a file.

@echo off
rem in a file the loop variable is doubled, the redirection caret-escaped:
for /f "delims=" %%i in ('dir /b *.tmp 2^>nul') do echo found %%i
rem the same command typed interactively uses a single %i:
rem   for /f "delims=" %i in ('dir /b *.tmp 2^>nul') do echo found %i

6 ▸ Subroutines and Functions

6.1 call :label and exit /b6.2 setlocal and endlocal scoping6.3 Macros: named command lines6.4 Return values and errorlevel conventions

Reusable code in batch takes two forms: subroutines reached with call :label, and the variable scoping that keeps them from leaking state into the caller. This chapter covers both, the endlocal & set return-value trick, command-alias macros, and the exit-code conventions that make subroutines composable.

6.1 call :label and exit /b

Unlike goto, which abandons its position, call remembers where it came from. That single difference turns a label into a function.

Calling a label as a subroutine

call :label args... jumps to the label, running it with %1, %2 and so on replaced by the supplied arguments — a fresh argument scope, independent of the caller's. When the subroutine reaches exit /b or goto :eof, control returns to the line after the call. The main body should itself end with exit /b, or it will fall through into the first label below it.

@echo off
call :greet Amin
call :greet Reader
exit /b

:greet
echo Hello, %1!
exit /b

exit /b with a return code

Inside a subroutine, a plain exit /b returns; exit /b N also sets %errorlevel% for the caller to inspect. A subroutine that forgets its exit /b falls through line by line into whatever follows — usually the next label's code or the end of the file — which produces baffling duplicated output. The convention is one exit /b per exit path, each carrying an intent-revealing code.

@echo off
call :check
echo check returned in the main body
exit /b

:check
if exist "flag.txt" exit /b 0
echo flag.txt is missing
exit /b 1

goto :eof and calling other scripts

goto :eof is the predefined label at the end of the file — the idiomatic "return from subroutine" that needs no numbered label. call other.cmd (no colon) runs another script in the same window and returns when it finishes; call without call would transfer control permanently. Batching a sequence of steps as called scripts is the standard way to keep a large build readable.

@echo off
call setup.cmd
if errorlevel 1 goto :eof
call build.cmd
if errorlevel 1 goto :eof
call deploy.cmd

6.2 setlocal and endlocal scoping

Variables set in a script are visible to its caller unless scoping fences them. setlocal and endlocal are those fences, and they are also the mechanism behind a subroutine's private space.

Localising changes with setlocal

setlocal snapshots the entire environment — every variable, not just the ones you name — and endlocal restores it. Between the two, any set is private. Nested pairs nest: each endlocal returns to the snapshot above it. A script that runs setlocal on line two and endlocal on its last line cannot leak variables into whoever called it, which is the difference between a polite utility and one that silently overwrites a caller's TEMP.

@echo off
set "X=outer"
setlocal
set "X=inner"
echo inside the block:  %X%
endlocal
echo after endlocal:    %X%

Options: EnableExtensions and EnableDelayedExpansion

setlocal EnableExtensions guarantees the extended command syntax, and setlocal EnableDelayedExpansion enables !var!. The two combine on one line. Because setlocal resets when the script ends even without a matching endlocal, a subroutine can set up its own delayed expansion without disturbing the caller's — and that independence is what makes the endlocal-boundary tricks in this chapter safe.

@echo off
setlocal EnableExtensions EnableDelayedExpansion
set "i=0"
for %%p in (A B C) do (
  set /a i+=1
  echo !i! - %%p
)
endlocal

Returning values across endlocal

A subroutine that endlocals destroys the variables it set — so returning a value needs the classic one-line trick: endlocal & set "RESULT=%local%" or, better, endlocal & set RESULT=%local% with quotes positioned so the %local% expands before endlocal runs. Both halves of the line are parsed and expanded at the same moment, so the substitution reads the local value just before the restore destroys it, and the restore then happens before the set executes.

@echo off
setlocal
set "value=from-local-scope"
endlocal & set "captured=%value%"
echo captured is "%captured%"
The same mechanism explains a frequent bug: endlocal & exit /b %errorlevel% is correct only because %errorlevel% expands before endlocal resets it. If you need the exit code computed after the restore, capture it into a variable first.

6.3 Macros: named command lines

A macro is a variable whose value is a piece of command line. Batched scripts reuse them the way other languages reuse functions — with the caveat that they expand exactly where they are written, with no call stack.

Alias-style macros

The simplest macro binds a frequently-used line to a short name, and expansion is just variable substitution: %Name% in a command position turns into the stored text, which the parser then executes. Because the expansion happens at parse time, a macro cannot see run-time state without delayed expansion — but for fixed commands like a standard silence or a repeated option set, it removes duplication without ceremony.

@echo off
set "QIET=2^>nul"
set "LIST=dir /b /o:n"
%LIST% *.log %QIET%
%LIST% *.txt %QIET%
echo done listing

Storing a label: function pointers

Because call accepts any expansion in its label position, a variable can name a subroutine: set "HANDLER=:save" then call %HANDLER% %1. This is batch's closest analogue to a function pointer, and it is the mechanism behind dispatch tables — choose which handler to run based on an argument, not an else if ladder. The variable must hold the colon: call distinguishes an external call (no colon) from a label call by that first character.

@echo off
set "op=:save"
call %op% notes.txt
exit /b

:save
echo saving %1
set "copy=%1.safe"
copy "%1" "%copy%" >nul
echo done
exit /b
Real argument-taking macros exist — the delayed-expansion macro idiom bound with ^! — but they are fragile and maintenance-hostile. The robust alternatives are call :label subroutines and variable-held labels; both are debuggable line by line, which a macro that self-escapes is not.

6.4 Return values and errorlevel conventions

Subroutines communicate outward two ways: through a set-after-endlocal variable on the standard one-liner, and through exit codes. Matching Windows conventions keeps your subroutines composable with &&, || and if errorlevel in the caller.

The full return-value pattern

Bundling the endlocal & set trick with a goto :eof produces a complete function: local computing, a result smuggled across the boundary, and a controlled return. The caller reads the result from the named variable. This is how batch implements "functions with return values" without any function machinery at all.

@echo off
setlocal
call :compute 4 5
echo the sum is %SUM%
endlocal & exit /b 0

:compute
set /a SUM=%1+%2
endlocal & set "SUM=%SUM%"
goto :eof

Exit-code conventions

Consistent conventions make code reviewable: 0 success; 1 generic error; 2 bad or missing arguments; 3 missing prerequisites; 4+ command-specific failures, or the documented codes of tools such as xcopy and findstr. The caller's if errorlevel N tests read highest-first. A subroutine that can fail should return a code on every exit path — an unreachable fall-through is how a "success" silently becomes whatever integer was lying around.

@echo off
call :deploy "%1"
if errorlevel 4 echo fatal: deployment aborted
exit /b %errorlevel%

:deploy
if "%1"=="" exit /b 2
if not exist "%1" exit /b 3
echo deploying %~nx1 ...
exit /b 0

Chaining calls with the standard operators

Because every subroutine honours the exit-code contract, callers can use the operators from chapter one: call :step1 && call :step2 || echo step failed. This composes scripts exactly the way tools compose, and it is the reason disciplined batch files are legible even at a hundred lines: each call :label is a sentence, and its exit code is its punctuation.

@echo off
call :step1 && call :step2 && echo both steps ok || echo a step failed
exit /b %errorlevel%

:step1
dir "C:\Windows" >nul
exit /b 0

:step2
exit /b 1

7 ▸ Error Handling and Robust Scripts

7.1 Checking errorlevel correctly7.2 Redirecting and silencing output7.3 Pausing, waiting and reading answers7.4 Verification and logging

A robust batch script assumes every command can fail and every input is hostile. This chapter covers reading exit codes correctly (including inside loops), redirecting and silencing streams, safe user interaction, and the verification and logging patterns that make a script explain itself later.

7.1 Checking errorlevel correctly

Two syntaxes read exit codes — if errorlevel N and %errorlevel% — and each fails differently if misused. Knowing which applies where prevents both silent wrong-branching and the classic %errorlevel%-in-a-loop trap.

if errorlevel N tests "N or higher"

if errorlevel 5 is true for codes 5, 6, 7 and everything above. Two consequences: tests must be ordered from highest to lowest, and a specific code needs the alternative syntax. The high-first order is the one habit to internalise, because the reversed order never looks wrong in testing — the first test just swallows every branch.

@echo off
dir "C:\no-such-folder" >nul 2>&1
if errorlevel 1 (
  echo the folder does not exist
) else (
  echo the folder opened fine
)
xcopy C:\data D:\backup /e /i /y >nul
if errorlevel 5 echo a serious copy error
if errorlevel 1 echo some files were not copied

Inside loops: re-evaluate every iteration

%errorlevel% expands at parse time, so inside a for body or a block it freezes at the value from before the loop started. Two correct forms survive: the if errorlevel rank test, which re-reads at run time, and delayed expansion by assigning set "code=!errorlevel!" after setlocal enabledelayedexpansion. The suppressed-output idiom cmd >nul 2>&1 here uses both stdout and stderr silencing — documented next.

@echo off
setlocal enabledelayedexpansion
set "missing=0"
for %%f in (a.txt b.txt c.txt) do (
  dir "%%f" >nul 2>&1
  if errorlevel 1 (
    echo missing: %%f
    set /a missing+=1
  )
)
echo %missing% files were missing

Exact-value tests with %errorlevel%

When the code must equal one number — never mind higher ones — compare the quoted expansion: if "%errorlevel%"=="1". This is the precise test that the rank form cannot express. Remember the parse-time caveat: on the same line outside a block it is fine; inside a block use !errorlevel! or the rank form.

@echo off
findstr /m "panic" app.log >nul
if "%errorlevel%"=="0" (
  echo matches found
) else (
  echo no matches - continuing
)

7.2 Redirecting and silencing output

Every command has three numbered streams: 0 stdin, 1 stdout, 2 stderr. Redirecting them is how a script runs quietly, keeps a transcript, and stops error text from polluting a result.

>nul 2>&1: the complete mute

command >nul discards stdout; 2>nul discards stderr; >nul 2>&1 discards both — 2>&1 meaning "send stream 2 to wherever stream 1 currently points". Order matters: 2>&1 >nul first points stderr at the console output and only then discards stdout, so error text still reaches the screen. The correct order is >nul 2>&1, and it is one of the most common one-character-class bugs in legacy scripts.

@echo off
dir "C:\no-such-folder" >nul 2>&1
echo quieted dir returned %errorlevel%
copy missing.txt extra.txt >nul 2>&1
echo quieted copy returned %errorlevel%

Writing output into log files

> overwrites a file and >> appends; both create it if absent. A separate 2>errors.log captures only the error stream, and >>build.log 2>&1 merges both streams into one growing log. Every embedded cmd /c or spawned tool writes where its own redirection says; the script's redirection only governs the streams of the command it is attached to.

@echo off
echo build started > build.log
msbuild project.sln >> build.log 2>&1
echo exit code %errorlevel% >> build.log
type build.log

Chaining steps with && and ||

The operators from chapter one support the tersest error handling: step && next || fallback runs next only on success (code 0) and fallback only on failure. A practical pattern is a chain that logs its own failure at the end of the line, so each step's outcome is recorded with the step name. Remember the chain leaves %errorlevel% as the last executed command's code — the fallback's, if the failure branch ran.

@echo off
copy app.dll deploy\ >nul && echo copied ok || echo copy failed
findstr /i "error" app.log >nul && (echo found problems) || echo log is clean

7.3 Pausing, waiting and reading answers

Interaction is where scripts hang or accept garbage: a prompt meant for a person should not read a file line, and a yes/no question should never accept free text.

pause and pause >nul

pause prints "Press any key to continue . . ." and waits for a keypress; pause >nul waits for the keypress without the message, the form used mid-script when the prompt would be noise. Because pause consumes one character from stdin, a script whose stdin is a file will skip a prompt and eat a line of input instead — redirect stdin explicitly to avoid that surprise.

@echo off
echo Review the results above, then continue.
pause
echo Continuing.
pause >nul
echo Done.

timeout — delay with or without a keypress

timeout /t 10 waits ten seconds, counting down on screen, and is interruptible by a keypress; timeout /t 10 /nobreak ignores keys; timeout /t -1 waits indefinitely. Its documented quirk: when stdin is redirected, timeout errors and returns a non-zero code — call it as timeout /t 5 >nul in scripts to both silence the countdown and avoid the redirected-stdin failure.

@echo off
echo waiting 5 seconds...
timeout /t 5 /nobreak >nul
echo done waiting

choice — bounded key selection

choice /c yn /n /m "Continue?" accepts only the listed keys, with /n hiding the list and /m supplying a message. The picked key's position becomes the exit code: y is 1, n is 2, and so on, read with the high-first rank test. Because the input space is bounded, choice cannot be fed a malicious string — the reason it is the right tool for yes/no and menus while set /p is for free text.

@echo off
choice /c yn /m "Backup the database now"
if errorlevel 2 goto :skipped
echo running the backup...
goto :done
:skipped
echo backup skipped
:done

Validating set /p answers

Free-text input needs explicit validation. The pattern is: give the variable a safe default, read the answer, normalise with /i comparison, and treat anything unexpected as the abort path. `set /p` leaves the variable untouched on a bare Enter, so the default survives. This closes the loop chapter three opened.

@echo off
set "answer=no"
set /p "answer=Type yes to continue: "
if /i not "%answer%"=="yes" (
  echo Aborted by the user.
  exit /b 1
)
echo Proceeding...

7.4 Verification and logging

The final layer of robustness is proving the script's own work: check prerequisites before starting, write a log that outlives the run, and verify that the bytes that should have moved really moved.

Checking prerequisites up front

A script fails more legibly when it validates its own guarantees before doing work: required files exist, required tools are on PATH, the destination is writable. Each check exits with a distinct code so a caller can branch on the exact cause rather than a generic 1. where in silent mode with || is the tool test; if not exist the file test.

@echo off
if not exist "input.csv" (
  echo input.csv is required; nothing done.
  exit /b 2
)
where msbuild >nul 2>&1 || (
  echo msbuild is not on PATH.
  exit /b 3
)
echo prerequisites satisfied

Timestamped log files

Logs earn their keep when each run is distinguishable. Build a stamp from %DATE% and %TIME%; the format is locale-dependent, so the robust approach splits the date on its delimiters with for /f. The hour from %TIME:~0,2% can start with a space when the clock is single-digit — sanitise it with substitution before it reaches a file name.

@echo off
for /f "tokens=2-4 delims=/ " %%a in ("%date%") do set "stamp=%%c%%a%%b"
set "log=backup-%stamp%.log"
echo === %date% %time% === > "%log%"
robocopy C:\data D:\backup /mir >> "%log%"
echo finished at %time% >> "%log%"
type "%log%"

Verifying copies and checksums

copy /v verifies every byte it writes; on a flaky disk it is the difference between detecting a bad sector and shipping a corrupt artifact. For absolute certainty, certutil -hashfile file SHA256 prints the hash, and fc compares two files line by line, returning 0 when identical. Backups and deployed binaries deserve at least one of these; the gold standard is hash-before and hash-after.

@echo off
copy /v app.exe deploy\app.exe
certutil -hashfile app.exe SHA256
fc app.exe deploy\app.exe >nul
if errorlevel 1 echo deploy copy differs from source

8 ▸ Automation and Administration

8.1 Scheduled tasks with schtasks8.2 Persisting environment variables with setx8.3 Starting programs with start8.4 Utility scripts worth keeping

The payoff chapter: batch's administrative superpowers. Scheduled tasks run scripts without a user at the keyboard, setx and reg persist configuration machine-wide, start launches applications, and four utility scripts show the patterns from the whole guide assembled into real tools.

8.1 Scheduled tasks with schtasks

schtasks.exe is the Task Scheduler's command-line face. It creates, queries, runs and deletes scheduled tasks — the way batch scripts run on their own long after the console is gone.

Creating a task

schtasks /create /tn name /tr command /sc trigger /st time /f is the minimal form: task name, the command line to run — which should almost always be a batch file rather than a bare EXE when more than one step is needed — the schedule (daily, weekly with /d MON, onlogon, onstart, hourly) and the start time. /f overwrites an existing task of the same name; without it, creating over an existing task errors. The /tr command's executable needs a full path; Task Scheduler does not resolve PATH the way a console does.

schtasks /create /tn "BackupData" /tr "C:\scripts\backup.cmd" /sc daily /st 02:30 /f
schtasks /create /tn "Report" /tr "C:\scripts\report.cmd" /sc weekly /d MON /st 09:00 /f
schtasks /create /tn "OnLogonScan" /tr "C:\scripts\scan.cmd" /sc onlogon /f

Querying, running, changing and deleting

Operational verbs share the shape: /query /tn name prints the task's schedule and state; /run /tn name starts it immediately; /end /tn name stops a running instance; /change /tn name /st 03:00 edits a field in place; /delete /tn name /f removes it. /query /tn name /v /fo LIST gives the verbose per-field listing. A task that errors leaves a %errorlevel% worth checking in the calling script: 0 for success, non-zero for an access or name problem.

@echo off
schtasks /query /tn BackupData /v /fo LIST
schtasks /run /tn BackupData
if errorlevel 1 echo failed to start the task
schtasks /change /tn BackupData /st 03:00
schtasks /delete /tn Report /f

Rights and the SYSTEM account

Creating or changing tasks for other users, and any machine-wide task, requires an elevated console. A non-elevated schtasks /create fails with error 5 (access is denied) — the first thing to check when a task silently never appears. /ru SYSTEM runs the task as the local system account, which has no interactive desktop session — the pause-at-the-end habit from chapter one hangs such a task forever. Give service-scheduled scripts a log file instead of prompts, and give them their own working directory via a pushd "%~dp0" first line.

schtasks /create /tn "CleanTmp" /tr "C:\scripts\clean.cmd" /sc daily /st 04:00 /ru SYSTEM /f
schtasks /query /tn CleanTmp | findstr /i "Status"
A scheduled task runs with the environment of the Task Scheduler service, not the interactive user's. Its PATH is shorter and its %USERPROFILE% is the system profile. Use absolute paths throughout the /tr script and setx-persisted variables (next section) rather than assuming anything inherits.

8.2 Persisting environment variables with setx

Environment variables set with set vanish with the window. setx writes them into the registry so every future process sees them — the difference between today's quick fix and a durable configuration.

setx basics and its limits

setx NAME value stores a user-level variable (under HKCU\Environment) for future processes; setx NAME value /m stores it machine-wide under HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment and needs elevation. Three limits matter: setx does not change the current window — only processes started afterwards see the new value; the stored value is truncated at 1024 characters; and values with spaces must be quoted on the command line but stored without quotes.

setx APP_ENV production
setx APP_ENV production /m
setx "BUILD_ROOT=C:\build tools"

Editing PATH without destroying it

The famous footgun: setx PATH "%PATH%;C:\new" takes the current merged %PATH% — system and user parts combined — and writes the whole merged string into the user variable, cloning every system entry into the user hive. Do it twice and entries duplicate. The safer pattern appends only after checking the target is not already present, and prefers reg add against the user key, or the modern setx /k source-from-registry flag where available.

@echo off
set "tool=C:\tools"
echo %PATH% | findstr /i /c:"%tool%" >nul && echo already on PATH || setx PATH "%PATH%;%tool%"

Reading configuration with reg

reg query "HKCU\Console" /v FontSize prints a registry value in the console; reg add "HKLM\Software\MyApp" /v Mode /t REG_SZ /d auto /f writes one (machine keys need elevation). Dragging a value into a variable needs for /f, iterating the query output lines. Registry access is case-insensitive, and both reg verbs return meaningful errorlevels — 1 for "not found" is the branch a script should consume.

@echo off
reg query "HKCU\Console" /v FontSize
reg add "HKCU\Console" /v FontSize /t REG_DWORD /d 0x00100000 /f
for /f "tokens=3" %%v in ('reg query "HKCU\Environment" /v APP_ENV 2^>nul ^| findstr /i APP_ENV') do set "APP_ENV=%%v"
echo APP_ENV is "%APP_ENV%"

8.3 Starting programs with start

Launching an application, a document or a second console from a script is the domain of start. Its quoting rules are the subtle part — a path is not a title, and a title is not a path.

start: detach, wait or run inline

start launches a program and returns immediately; /wait makes the script pause until the child exits — essential for "install then continue" semantics; /b runs the child in the same console without a new window. The first quoted argument is a TITLE, so launching a quoted path requires an explicit empty title: start "" "C:\Program Files\app.exe". Without the empty pair, the path is consumed as the title and the command silently does nothing. This is the single most common start bug in real scripts.

@echo off
start "" notepad.exe readme.txt
start /wait "" setup.exe /S
start /b "" server.exe
start "" "C:\Program Files\MyApp\app.exe"

Opening by association: assoc and ftype

start "" report.html opens the file with its registered application — the default browser for HTML, the default editor for text. assoc .html reports the file-type key a registered extension maps to, and ftype htmlfile reports the command template that key runs; both take modifiers, so assoc alone lists every mapping. Opening a document by association is the polite way for an installer to show its help without hard-coding a browser path.

@echo off
assoc .html
ftype htmlfile
start "" report.html

Environment and working directory for the child

A child process inherits the script's environment and its current directory. Two consequences: set environment variables before start to configure the child (a server's PORT, a build's CONFIGURATION), and set the working directory with pushd if the child resolves relative paths — a Web server that cannot find its index.html is usually a directories problem, not a code problem. Pair every pushd with the matching popd.

@echo off
pushd "C:\apps\web"
set "PORT=8080"
start /wait "" node server.js
popd

8.4 Utility scripts worth keeping

Four complete scripts tie the guide together. Each is written to run unattended, from a scheduled task or a double-click, and each shows a different combination of the patterns from chapters one through eight.

Timestamped mirror backup

Robocopy mirrors the source into a dated folder and logs every run. The exit-code test below is the one from chapter seven's warning: if errorlevel 8 catches only genuine failures, because robocopy's 1–7 are success. The log path is built with the stamp technique, so no two runs overwrite each other.

@echo off
setlocal
set "src=C:\Projects\myapp"
set "dst=D:\Backup\myapp"
robocopy "%src%" "%dst%" /mir /r:2 /w:1 /log:backup.log
if errorlevel 8 (
  echo FATAL: backup failed with code %errorlevel%
  endlocal
  exit /b 1
)
echo backup finished ok
endlocal

Retention cleanup with forfiles

Deleting logs older than n days is a two-line job with forfiles: /d -30 selects files modified more than 30 days ago, and the /c command deletes each matched @path. The /s flag recurses. This is the classic scheduled-task body: silent, idempotent, and safe because the mask scopes it to one name pattern.

@echo off
forfiles /p "C:\Logs" /s /m *.log /d -30 /c "cmd /c del /q @path"
echo retention cleanup finished

Build, test and deploy in one file

A miniature pipeline proves the patterns compose: cd /d to the source with a || guard, build into a log, branch on the result, copy the artifact out, and report a timestamped outcome. The variable %errorlevel% used here on the final line of a block-free script is safe under the chapter-seven rule; inside the block the rank-form if errorlevel is doing the work instead.

@echo off
setlocal
set "src=C:\src\myapp"
cd /d "%src%" || (echo source folder missing & exit /b 2)
msbuild myapp.sln /p:Configuration=Release /v:m > build.log 2>&1
if errorlevel 1 (
  type build.log
  endlocal
  exit /b 1
)
xcopy "%src%\bin\Release\*.*" "\\deploy\apps\myapp" /e /i /y >nul
echo deployed at %date% %time%
endlocal & exit /b 0

The robust skeleton, complete

Every professional batch file starts from one shape: @echo off, extensions and delayed expansion on, an immediate cd /d "%~dp0" so paths are relative to the script itself no matter where it is launched from, a started-log line, the work, and a single endlocal & exit /b %errorlevel% exit. Because %errorlevel% is expanded before endlocal restores the environment — chapter six's rule — the script exits with the true code of its last real action.

@echo off
setlocal EnableExtensions EnableDelayedExpansion
cd /d "%~dp0"
echo [%date% %time%] script started >> "%~dp0run.log"
rem --- the work, with each step guarded ---
call :do_work
echo [%date% %time%] script finished with %errorlevel% >> "%~dp0run.log"
endlocal & exit /b %errorlevel%

:do_work
echo working...
exit /b 0
