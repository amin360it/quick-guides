This topic contrasts desktop PCs with true servers, showing that servers are engineered for 24x7 uptime, ECC memory, redundant power supplies and remote management capabilities. Understanding them helps you judge whether a given machine is really built to be a server or just a desktop pressed into service.

2 · Server Hardware

It is written so that after reading it you can read a server spec sheet with confidence and tell which components matter for a given workload. Every later decision about sizing and purchasing builds on the basics laid out here.

2.1 CPU

This topic covers the main server CPU families from Intel, AMD and ARM and explains how to match core counts, clock speed and socket features to your workload. Database servers with many concurrent threads and virtualization hosts consolidating many VMs need very different processors than single-application boxes. Knowing the difference keeps you from overbuying or undersizing the compute capacity.

VendorFamiliesNotes
IntelXeon Silver/Gold/PlatinumLarge core counts, ECC
AMDEPYCHigh core/thread density
ARMAmpere/GravitonPower-efficient cloud

Count cores, clock speed, cache, TDP and sockets. Match to workload: single-thread (databases), many-thread (virtualization), or accelerators (GPU).

2.2 Memory

Servers run ECC and registered memory that must be populated evenly across channels to achieve full bandwidth and reliability. Getting the DIMM count, order and speed right is one of the cheapest, most reliable performance wins available, while a misconfigured channel layout silently halves throughput. This topic explains how to read a memory population guideline and apply it.

Types: DDR4 / DDR5, RDIMM (registered) or LRDIMM (load-reduced)
Always ECC on servers. Channels matter: populate evenly
(e.g. 8 DIMM slots -> 2 or 4 or 8 sticks) to get full bandwidth.
Example: 256 GB = 8 x 32 GB DDR5 RDIMM in 8 channels.

This is the memory rule of thumb: use ECC, and populate DIMMs evenly across channels, like eight 32 GB sticks filling all eight channels for 256 GB.

2.3 Storage

This topic describes the storage pyramid from bulk HDDs for archive capacity, through SSD and NVMe for speed, and the RAID arrays that tie disks together. Matching disk type to workload keeps databases fast and archives cheap, because hot and cold data have completely different needs. It also explains how to think about interfaces, capacity and redundancy together.

TypeSpeedUse
HDD (SAS/SATA)SlowBulk, archive, backups
SATA SSDFastBoot, general
NVMe SSDFastestDatabases, high IOPS
RAID arrayVarRedundancy + performance

2.4 Network, power and cooling

This topic covers the supporting infrastructure that decides whether a server survives failures: dual-port NICs for redundancy, hot-swap power supplies on separate feeds, and sensible cooling design. A box with a single NIC or a single PSU has single points of failure at the physical layer. It also covers airflow planning and temperature monitoring as part of a dependable build.

  • NIC: 1/10/25/100 GbE, dual-port for redundancy, iSCSI offload, SR-IOV.
  • PSU: dual redundant, hot-swap, connected to A/B feeds.
  • Cooling: variable-speed fans, airflow direction matched to the rack.
  • RAID controller: battery/cache-backed (BBU), write-back for performance.

3 · Building a Server (Process)

This chapter walks the end-to-end journey of bringing a server into production, from gathering requirements and designing, through firmware, OS installation, hardening and documentation. Following this ordering avoids the classic trap of rebuilding a server within weeks because something was skipped. It is the process layer that turns hardware into a managed service.

3.1 The build process

This topic lays out a 12-step workflow from requirements and design through firmware updates, OS installation, role configuration and hardening, ending with documentation. Treating it as a literal checklist means no step gets skipped under pressure. Each step produces an artifact, such as a bill of materials or a documentation entry, that the next step depends on.

1 Requirements  -> roles, users, growth, budget
2 Design        -> CPU/RAM/storage/network, OS, licensing
3 Procure       -> buy, verify warranty/compatibility
4 Physical build-> rack, rails, PSU, cabling, labels (or order cloud)
5 Firmware      -> update BIOS/RAID/NIC, configure RAID + virtual disks
6 OS install    -> answer file / kickstart / image
7 Drivers       -> chipset, NIC, RAID, GPU
8 Updates       -> OS + firmware baseline
9 Roles         -> install roles (AD, DNS, DHCP, IIS...)
10 Harden       -> baseline, least privilege, firewall
11 Monitor      -> agents, backups, health checks
12 Document     -> asset tag, IP, roles, credentials in vault

A 12-step build checklist that carries a server from requirements to a documented, monitored production box, with firmware and hardening done before any roles are installed.

3.2 Gathering requirements

This topic lists the questions to ask before buying anything: which roles the server will run, how many users it must serve, expected growth, uptime and SLA targets, compliance constraints and licensing costs. Sizing is genuinely about avoiding both waste and regret, and the right questions prevent both. It turns a vague upgrade request into a concrete specification.

3.4 The golden baseline

This topic explains the golden baseline: a patched, hardened, instrumented and documented image that every new server should start from. Building each new machine by cloning this baseline makes rebuilds and displacement nearly free and keeps the estate consistent. It covers what the baseline must contain and how to maintain it as new patches and requirements appear.

  • Standard local admin, monitoring agent, backup agent.
  • Hardened config (see Ch. 28) and a documented build sheet.
  • Image it (or codify it as IaC) so rebuilds are trivial.

5 · Firmware & Out-of-Band Management

5.1 BIOS/UEFI configuration5.2 Remote management controllers5.3 Firmware update discipline

This chapter covers BIOS and UEFI setup, out-of-band management controllers and disciplined firmware update practice. Firmware is the layer people forget until it fails, so this chapter treats it as a first-class part of server management. It gives repeatable procedures for configuring and updating firmware safely across the estate.

5.1 BIOS/UEFI configuration

This topic covers the key BIOS and UEFI settings that quietly control what a server can do: boot order, Secure Boot, Intel VT and AMD-V virtualization extensions, TPM enablement and power profiles. The right settings are needed for virtualization, disk encryption and operating system security features. It explains which settings to change and why each matters.

  • Boot order, Secure Boot, virtualization extensions (VT-x/AMD-V).
  • Hyper-Threading, power profile (performance vs balanced).
  • Memory interleaving and NUMA settings.
  • Disable unused devices and legacy boot where not needed.

5.2 Remote management controllers

This topic covers vendor management controllers such as Dell iDRAC, HPE iLO, Lenovo XCC and baseboard IPMI that let you power on, console in and see hardware health even when the operating system is down. They are effectively a separate, secure management plane and must be treated that way, with dedicated network segments and strong credentials. It covers how to configure and use them.

VendorController
DelliDRAC
HPEiLO
LenovoXClarity / IMM
SupermicroIPMI / Redfish
# Out-of-band lets you power on, console, and reinstall
# even when the OS is down. Put the OOB NIC on a dedicated VLAN.
ipmitool -I lanplus -H 10.0.0.50 -U admin -P **** power status
# Output: Chassis Power is on

This checks power state over IPMI, the out-of-band channel that works even when the OS is down, and the comments remind you to keep its NIC on a dedicated VLAN.

5.3 Firmware update discipline

This topic describes the discipline of baselining firmware at build time, testing updates before rollout and tracking versions across the estate. Firmware regressions are real, so updates belong on a schedule rather than being applied reactively. It covers staging, maintenance windows and keeping an inventory of firmware versions per host model.

  • Baseline all firmware at build; track versions in an inventory.
  • Test updates on one node, then roll out.
  • Schedule with vendor tools (Dell OM, HPE SPP, Lenovo XClarity).
  • Record changes; firmware regressions happen.

Out-of-band controllers are a favourite attack target. Change default credentials, put them on an isolated management VLAN, and never expose them to the internet.

6 · File & Print Servers

6.1 File servers6.2 Print servers6.3 Availability and sharing

This chapter covers the oldest server roles in the book: sharing files and printers across a network. These services are easy to take for granted, but permission design, spooler security and protocol choice still bite organizations that ignore them. It frames file and print services as managed infrastructure with careful planning.

6.1 File servers

This topic covers central file storage over SMB, NFS or object storage, with permissions layered on top. Getting the folder structure and group-based permissions model right before anyone creates a share avoids years of permission sprawl. It covers share creation, NTFS or POSIX permissions, and access controls on both Windows and Linux servers.

Protocols: SMB/CIFS (Windows), NFS (Linux/Unix), AFP (legacy), S3 (object)

# Windows: share + NTFS permissions
New-SmbShare -Name Data -Path D:\Data -FullAccess 'DOMAIN\FileAdmins' `
             -ChangeAccess 'DOMAIN\Staff'
# Linux: NFS export
/data 10.20.0.0/24(rw,sync,no_subtree_check,root_squash)

This creates an SMB share with separate full and change access and an NFS export for Linux clients, so notice how each syntax maps to its platform permission model.

6.2 Print servers

This topic covers centralised print queues using universal drivers, follow-me printing and per-user quotas. Print spooler services have been attacked often, so they must be treated as a security surface rather than a harmless utility. It covers printer deployment, driver management and locking down the spooler service on Windows print servers.

  • Central print queue, universal drivers, deploy via GPO.
  • Follow-me/pull printing, accounting and quotas.
  • Print spooler is a common attack vector — restrict and patch it.

6.3 Availability and sharing

This topic covers the availability extras that turn a plain share into a managed service: Distributed File System namespaces and replication, quotas, shadow copies and access-based enumeration. DFS lets multiple file servers present one namespace and replicate data between sites. Quotas and shadow copies give users self-service recovery while keeping disk growth controlled.

FeaturePurpose
DFS-N / DFS-RNamespace + replication across sites
Quotas / FSRMLimit and screen files
Shadow copiesSelf-service restores
Access-based enumerationHide folders users can’t open

On a file server, plan the folder and permission model before creating shares. Retrofitting NTFS permissions is painful and error-prone.

7.2 Nginx and IIS examples

This topic gives hands-on configuration: a full Nginx site block with server name, proxy and TLS settings, plus a PowerShell-based IIS setup using the WebAdministration module on Windows. These two examples reflect the dominant web platforms seen in production. It works as a reference to adapt for real deployments.

# Nginx site
server {
    # listen for HTTPS with HTTP/2
    listen 443 ssl http2;
    server_name app.example.com;
    ssl_certificate     /etc/ssl/app.crt;
    ssl_certificate_key /etc/ssl/app.key;
    root /var/www/app/public;
    location / { try_files $uri /index.php?$query_string; }
    # PHP requests go to the FPM socket
    location ~ \.php$ { fastcgi_pass unix:/run/php/php8.3-fpm.sock; }
}

This Nginx site serves static files over TLS with PHP handed to FastCGI, and the key detail is the split between the try_files app location and the PHP processing location.

# IIS site
New-WebAppPool -Name app
New-Website -Name app -PhysicalPath C:\inetpub\app -ApplicationPool app -Port 80
# Bind certificate
New-WebBinding -Name app -Protocol https -Port 443
# put the cert into the local machine store
Import-PfxCertificate -FilePath C:\certs\app.pfx -CertStoreLocation Cert:\LocalMachine\My

This stands up an IIS site with its own app pool and binds a certificate for HTTPS, and the detail to notice is that the certificate must land in the machine store before binding.

7.3 TLS and static hosting

This topic explains why modern TLS, HTTP Strict Transport Security and automated certificates are non-negotiable for web serving. A handful of configuration lines, such as enabling TLS 1.2 and 1.3 and setting up Let’s Encrypt style automated issuance, protect every request your site handles. It also covers redirecting HTTP to HTTPS and preloading HSTS.

  • Use TLS 1.2/1.3, modern ciphers, HSTS, and automate certs (Let’s Encrypt/ACME).
  • Compress, cache and serve static assets via a CDN.
  • Run behind a reverse proxy/WAF for apps.

backend app
  # send each new connection to the least busy server

A.4 Rules of thumb

This topic states the guiding rules of thumb: separate roles, build servers from golden images, protect the management plane, patch on a schedule, test backups and watch your fleet with monitoring. These are the habits that keep a server estate healthy over years. It is the distilled wisdom of the whole guide.

  • Separate roles logically; dedicate databases, backups and monitoring.
  • Build from an image or code — no snowflakes.
  • Out-of-band management on an isolated VLAN.
  • Patch OS and firmware on a cadence.
  • Backups tested; at least two of everything critical.
  • Never expose management ports to the internet.
  • Monitor, document, and know your RTO/RPO.
