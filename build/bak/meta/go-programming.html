0.1 Why Go, and what it decided to leave out

Go is a language designed by people who had built large C++ and Java systems and who concluded that the dominant costs in software were not expressiveness but concurrency, testing and tooling — so the language is largely a set of decisions about what to remove.

The seven decisions that make Go what it is

Then the four things that follow, and each is a consequence of those decisions rather than a separate choice. Because there is no inheritance, there is no method resolution order and no virtual dispatch, so behaviour is composed by embedding an interface value rather than by a class hierarchy — and a method set is something you can read. Because there is no null pointer, a nil interface is the absence of a value rather than a pointer that is null, so the failure mode is a panic at a specific point rather than a dereference somewhere later. Because the scheduler and the network poller are in the runtime, a blocking channel operation is cheap and the runtime parks the goroutine — which is why a program with ten thousand goroutines costs kilobytes per goroutine rather than the eight-megabyte stacks a thread would. And Because errors are values, error handling is explicit and visible in the source rather than hidden in a propagation mechanism. Then the three things that go wrong, and each is a mechanism. Starting a goroutine per request and never bounding the count, which is fine until the downstream service slows and the goroutines pile up. Sharing a map between goroutines, which is a data race and which the compiler will not catch because Go's type system has no notion of shared mutable state. And Ignoring the returned error, which the language allows and which is the most common way a Go program fails at run time. Then the two practices, and both are disciplines. Pass values, return interfaces, and make the nil case a defined state rather than an accident, because in Go the distinction between a nil interface and an interface holding a nil pointer is the single most common source of confusion. And Structure concurrent code so the ownership is obvious, because the language gives you channels and the discipline has to come from you.

/* Go is largely a set of decisions about what to REMOVE, made by
   people who had built large C++ and Java systems and concluded
   that the dominant costs were concurrency, testing and tooling. */

/* THE SEVEN DECISIONS.
     1. Garbage collected. Memory is not your problem.
     2. No inheritance. Behaviour is composed, not overridden.
     3. No null. A nil interface is the ABSENCE OF A VALUE.
     4. No exceptions. Errors are values you must handle.
     5. No operator overloading, no generics until 1.18.
     6. One way to do things, enforced by gofmt.
     7. The scheduler, the network poller and the garbage
        collector are in the RUNTIME, not in the application.     */

/* FOUR CONSEQUENCES, each following from the decisions above.

   1. NO INHERITANCE means no method resolution order and no
      virtual dispatch. Behaviour is composed by EMBEDDING an
      interface value, and a method set is something you can read. */
type Reader interface { Read(p []byte) (int, error) }
type Writer interface { Write(p []byte) (int, error) }

/* Embedding an INTERFACE composes behaviour and the method set is
   visible: this type reads AND writes and cannot be closed twice. */
type ReadWriter interface {
    Reader
    Writer
}

/* 2. NO NULL means a nil interface is the absence of a value - and
   the distinction below is the single most common source of
   confusion in Go. */
func describe(r Reader) string {
    if r == nil {
        return "no reader"        /* the interface itself is nil   */
    }
    /* A NON-NIL interface holding a NIL POINTER is not == nil,
       and the check above does not catch it. */
    return fmt.Sprintf("%T", r)
}

type nopReader struct{}
func (nopReader) Read([]byte) (int, error) { return 0, io.EOF }

var typedNil Reader = (*nopReader)(nil)   /* NOT == nil          */
var plainNil Reader                     /* == nil, always       */

/* 3. THE SCHEDULER IS IN THE RUNTIME, so a blocking channel
   operation is cheap: the runtime PARKS the goroutine and resumes
   it when the value arrives. That is why ten thousand goroutines
   cost kilobytes each rather than the eight-megabyte stacks a
   thread would. */
func fan(out chan<- int, jobs <-chan int) {
    for j := range jobs { out <- j * j }  /* blocks cheaply        */
    close(out)
}

/* 4. ERRORS ARE VALUES. Not hidden in a propagation mechanism, not
   in the type - in the source, at the call site. */
func read(path string) ([]byte, error) {
    b, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("read %s: %w", path, err)  /* wrapped */
    }
    return b, nil
}

/* THE THREE FAILURES.
   1. A GOROUTINE PER REQUEST AND NEVER BOUNDED: fine until the
      downstream slows and the goroutines pile up without limit.
   2. A MAP SHARED BETWEEN GOROUTINES: a data race the compiler
      cannot catch, because Go's type system has no notion of
      shared mutable state at all.
   3. AN IGNORED RETURNED ERROR: allowed by the language, and the
      single most common way a Go program fails at run time.       */

/* Two disciplines. PASS VALUES, RETURN INTERFACES, and make the
   nil case a DEFINED STATE rather than an accident - because the
   nil-interface versus nil-pointer distinction above is the most
   common confusion in the language. And STRUCTURE CONCURRENT CODE
   SO THE OWNERSHIP IS OBVIOUS, because the language gives you
   channels and the discipline has to come from you. */

package main

import (
	"errors"
	"fmt"
	"os"
	"strconv"
)

/* THE LEAK, WRITTEN THE WAY THE LANGUAGE PERMITS IT TO BE WRITTEN.
   This compiles, passes go vet, and is the shape that produces the
   out-of-memory report. */
type leaky struct{ items []byte }

func (l *leaky) grow(n int) error {
	l.items = make([]byte, n)   /* the OLD slice is unreachable the
	                                 moment this assignment runs:
	                                 nothing points at it, so the
	                                 garbage collector cannot know
	                                 it was ever live             */
	return nil
}

func (l *leaky) push(b byte) {
	l.items = append(l.items, b)   /* append allocates a NEW array
	                                       and copies when it runs
	                                       out of capacity, which
	                                       is why a slice's length
	                                       and capacity are
	                                       different numbers    */
}

func leakyRun() error {
	l := &leaky{}
	for i := 0; i < 1000000; i++ {
		l.grow(i * 64)   /* each call abandons the previous array */
	}
	return nil
}

/* THE SAME WORK, WRITTEN SO THAT THE GARBAGE COLLECTOR CAN SEE IT. */
type bounded struct{ items []byte }

func (b *bounded) grow(n int) error {
	if n <= cap(b.items) {
		b.items = b.items[:n]   /* REUSE: no allocation at all */
		return nil
	}
	next := make([]byte, n, n*2)   /* grow geometrically so the
	                                  total work is linear rather
	                                  than quadratic: extending
	                                  by one element at a time
	                                  copies the whole array
	                                  every single time          */
	copy(next, b.items)
	b.items = next
	return nil
}

/* THE ERROR PATH, which is the other half of the argument. A
   function that can fail says so in its signature and returns the
   failure rather than printing it and continuing. */
type Config struct {
	Port int
	Addr string
}

func parsePort(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parse port %q: %w", s, err)
	}
	if n < 1 || n > 65535 {
		return 0, fmt.Errorf("port %d out of range", n)
	}
	return n, nil
}

func loadConfig(addr, port string) (Config, error) {
	p, err := parsePort(port)
	if err != nil {
		return Config{}, err     /* WRAP: the caller learns which
	                                  field failed, and errors.Is
	                                  still works on the cause   */
	}
	return Config{Port: p, Addr: addr}, nil
}

/* AND THE THREE WAYS A GO PROGRAM EXITS, which is the other thing
   the language decided rather than inherited. */
func exits() {
	os.Exit(1)                  /* immediate: deferred functions do
	                                 NOT run, so anything holding a
	                                 lock or a temp file is
	                                 abandoned - this is why main
	                                 should return an error and let
	                                 the runtime handle it       */
	panic("unrecoverable")      /* a bug: prints a stack and exits 2 */
	log.Fatal("bad config")     /* log.Fatal is os.Exit(1) in
	                                 disguise, with the same
	                                 consequence               */
}

func main() {
	if err := loadConfig("127.0.0.1", "8080"); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

0.2 The toolchain, and why gofmt is not optional

The Go toolchain is one binary with a fixed set of verbs, and the formatting and vet steps are not style preferences — they are part of the compiler's output being treated as an interface.

Six verbs, and what each guarantees

go build compiles and links; go test compiles and runs tests in the same process model as the code, which is why a race in production is a race in a test. go vet is a static analyser that catches printf mismatches and unreachable code. gofmt rewrites the source to one canonical form. go mod manages the dependency graph. And go run compiles and runs in one step. Then the four things to know, and each is a requirement. Formatting is not optional, because the toolchain rewrites every file and a repository that is not formatted produces a diff on every line somebody touched. go vet runs as part of go test in current versions, which means a printf format mismatch fails the build rather than producing a garbled message. The race detector is a flag, not a default, so a test suite that is run without it has not tested concurrency at all. And Modules replaced the old dependency mechanism entirely, so a module-aware module is the only supported configuration. Then the three things that go wrong, and each is a mechanism. Committing files that are not gofmt-clean, which produces a whole-file diff that hides the real change in a review. Running the tests without -race, which means a data race passes. And Adding a dependency for something the standard library has, which is a supply-chain dependency for a function that already exists in the language. Then the two practices, and both are disciplines. Put gofmt, go vet and go test -race in the pipeline and treat each as a failure, because a tool that is allowed to warn is a tool whose warnings are ignored. And Read the standard library before adding a dependency, because it is unusually complete and because a dependency is a maintenance relationship you cannot see in the import line.

     go build   compile and link

                report

$ gofmt -w .                 # rewrite them
$ gofmt -d file.go           # show the diff without writing it

func logf(name string, n int) {

    log.Printf("%s: %s", name, n)     // vet: format %s has arg n of wrong type int

    /* RIGHT: match the verbs to the arguments, or let vet catch it. */
    log.Printf("%s: %d", name, n)
}

/* THE RACE DETECTOR IS A FLAG, NOT A DEFAULT. A suite run without
   -race has not tested concurrency at all - it has tested the
   interleavings that happened to occur. */
$ go test -race ./...

                                               run proves nothing */

   1. COMMITTING FILES THAT ARE NOT gofmt-clean: a whole-file diff

   2. RUNNING THE TESTS WITHOUT -race: a data race passes.
   3. ADDING A DEPENDENCY FOR SOMETHING the standard library has:
      a supply-chain dependency for a function that already exists
      in the language.                                         */

/* Two disciplines. PUT gofmt, go vet AND go test -race IN THE

   allowed to warn is a tool whose warnings are ignored. And READ
   THE STANDARD LIBRARY before adding a dependency - it is

0.3 What to know before you start

You need one language with interfaces and you need to be willing to learn a memory model where the garbage collector does the work.

What transfers and what does not

Then the three things worth knowing before chapter one, and each is a requirement. Interfaces in Go are satisfied implicitly, so any type with the right methods satisfies the interface without declaring it — which means an interface belongs where the code needs a behaviour, not where the implementer was written. A goroutine is not a thread and has its own stack, so a goroutine that blocks on a channel does not block anything else and the stack grows on demand — the opposite of a thread, where a stack is a fixed cost. And defer runs in reverse order, which makes a sequence of defers the correct way to write cleanup with more than one resource. Then the three things that go wrong, and each is a mechanism. Assuming a goroutine is cheap because it is light, and creating one per item in a million-item list, which is a million stack frames and a scheduler queue. Closing a channel from the sending side, which is a panic when a second sender tries it and the only correct design is one sender or the sending function. And Taking the address of a loop variable and keeping it, which before the language's per-iteration scoping pointed every closure at the same variable. Then the two practices, and both are disciplines. Read the error before you do anything else with the result, because a wrapped error names its cause and a discarded one names nothing. And Start every goroutine with a clear statement of who owns what it reads and writes, because that statement is the only documentation of the concurrency in the program.

/* INTERFACES ARE SATISFIED IMPLICITLY. Any type with the right
   methods satisfies the interface without declaring it - so an
   interface belongs where the code NEEDS a behaviour, not where
   the implementer happened to be written. */
type Store interface {
    Get(key string) ([]byte, error)
    Put(key string, v []byte) error
}

/* Any type with these methods is a Store. No declaration. */
type memStore struct{ m map[string][]byte }
func (s *memStore) Get(k string) ([]byte, error) { v, ok := s.m[k]; if !ok { return nil, ErrMissing }; return v, nil }
func (s *memStore) Put(k string, v []byte) error  { s.m[k] = v; return nil }

/* A GOROUTINE IS NOT A THREAD. It has its own STACK, which grows
   on demand, so a goroutine that blocks on a channel does not
   block anything else - the opposite of a thread, whose stack is a
   fixed cost paid up front. */
/* DEFER RUNS IN REVERSE ORDER, which makes a sequence of defers
   the correct way to write cleanup with more than one resource. */
func process(path string) (err error) {
    f, err := os.Open(path)
    if err != nil { return err }
    defer f.Close()                 /* runs LAST                      */

    lock, err := acquire()
    if err != nil { return err }
    defer lock.release()            /* runs FIRST: unlock, then close */

    return work(f)
}   /* Defers run at RETURN, including on a panic, which is the
     whole reason they exist.                                       */

/* THE THREE FAILURES.
   1. ASSUMING A GOROUTINE IS CHEAP BECAUSE IT IS LIGHT and
      creating one per item in a million-item list: a million stack
      frames and a million scheduler queue entries, and the cost
      is invisible until the machine is out of memory.
   2. CLOSING A CHANNEL FROM THE SENDING SIDE: a panic when a
      second sender tries it. The rule is one sender, or the
      function that owns the channel closes it.
   3. TAKING THE ADDRESS OF A LOOP VARIABLE AND KEEPING IT: before
      the language's per-iteration scoping, every closure captured
      the SAME variable, so a loop appending ten goroutines produced
      ten references to the final value.                             */

/* Two disciplines. READ THE ERROR before you do anything else with
   the result, because a wrapped error names its cause and a
   discarded one names nothing. And START EVERY GOROUTINE with a
   clear statement of who owns what it reads and writes - that
   statement is the only documentation of the concurrency in the
   program, and the race detector tells you about a race you have
   but not about the one you have not hit yet. */

package main

import (
	"errors"
	"fmt"
	"sync"
)

/* FIVE THINGS TO KNOW BEFORE CHAPTER 1, each of them a place where
   a Go program differs from what the same idea looks like in
   another language. */

/* 1. NIL IS AN INTERFACE VALUE, and that is the whole hazard. */
type Reader interface{ Read() []byte }
type T struct{}

func (T) Read() []byte { return nil }

func the_nil_interface()
{
	var r Reader              /* a nil INTERFACE: type is nil,
	                              value is nil, so r == nil is
	                              TRUE                              */
	var t *T
	/* r = t                  ASSIGNING A TYPED NIL: the interface
	                             is now non-nil, because it carries
	                             the type *T. r == nil is FALSE and
	                             calling Read on it may work. This
	                             is the single most common Go bug
	                             and the reason a concrete type is
	                             stored in its own variable
	                             whenever it might be absent. */
	_ = t
	_ = r

	var r2 Reader
	/* r2 = t; if r2 != nil { r2.Read() }
	     r2.Read() PANICS: the interface is not nil, so the guard
	     did not fire, and the method runs with a nil receiver. */
	_ = r2
}

/* 2. A SLICE IS A DESCRIPTOR, not a block. Three words: pointer,
   length, capacity. Passing one copies the descriptor. */
func the_slice()
{
	a := make([]int, 3, 10)
	b := a
	b[0] = 99                  /* SAME backing array: a[0] is also
	                                 99, which is what makes a
	                                 slice cheap to pass           */
	/* b = append(b, 1)      capacity is available, so a is
	                               unchanged and the new element
	                               lives beyond a's length - which
	                               is why a needs to be re-sliced
	                               to see it                     */

	/* b[0] = 1; a[0]        a has length 0, so this PANICS: index
	                          out of range. The element is there;
	                          a cannot address it.            */

	/* c := a[:2] then append to c until it passes 10 and the
	   array is reallocated, and a sees NONE of it. Appending to a
	   sub-slice that shares capacity can silently break the
	   relationship with the parent.                          */
	_ = a
}

/* 3. A MAP IS A REFERENCE, and a nil map is READABLE. */
func the_map()
{
	var m map[string]int
	v, ok := m["missing"]       /* fine: v is 0, ok is false     */
	/* m["k"] = 1              PANICS: assignment to a nil map  */
	_ = v
	_ = ok

	/* ITERATION ORDER IS RANDOM, on purpose, because a stable
	   order would let one package's correctness depend on
	   another's insertion order. */
	counts := map[string]int{"a": 1, "b": 2, "c": 3}
	keys := make([]string, 0, len(counts))
	for k := range counts {
		keys = append(keys, k)
	}
	sortStrings(keys)           /* sort: ALWAYS sort before you
	                                rely on the order, or use an
	                                ordered structure            */
}

/* 4. ERROR IS A VALUE, and wrapping is the reason errors.Is
   works through five frames. */
var ErrNotFound = errors.New("not found")

func find(id string) ([]byte, error) {
	if id == "" {
		return nil, fmt.Errorf("find %q: %w", id, ErrNotFound)
	}
	return []byte(id), nil
}

func the_error_chain()
{
	_, err := find("")
	/* errors.Is(err, ErrNotFound)   TRUE, through the wrap   */
	/* errors.As(err, &pathErr)      works if anything in the
	                                  chain is a *os.PathError    */
	/* err == ErrNotFound            FALSE: the WRAPPED value is
	                                  a different error value.
	                                  == is the wrong operator
	                                  here and this is the trap.  */
	_ = err
}

/* 5. A GOROUTINE LEAKS, and the test that finds it is one line. */
func goroutines(started, finished *sync.WaitGroup) {
	defer finished.Done()
	_ = started
}

func the_leak()
{
	var started, finished sync.WaitGroup
	for i := 0; i < 10; i++ {
		started.Add(1)
		go goroutines(&started, &finished)
	}
	started.Wait()
	finished.Wait()              /* if this never returns, a
	                                 goroutine is blocked forever,
	                                 and the runtime prints EVERY
	                                 goroutine's stack when the
	                                 test times out. That is the
	                                 single most useful property
	                                 the language has.          */
}

func sortStrings(s []string) {
	for i := range s {
		for j := i + 1; j < len(s); j++ {
			if s[j] < s[i] {
				s[i], s[j] = s[j], s[i]
			}
		}
	}
}

func main() {}

0.4 How this guide is organised

The guide moves from the language's two central abstractions — interfaces and concurrency — to the runtime and the tooling, and each chapter's assumptions are the previous chapter's conclusions.

Why this order

Then the three things every chapter has, and each is a property of the writing. A mechanism stated before its consequence, so the consequence is derivable. A list of what goes wrong with the mechanism behind each, because a Go bug is almost never mysterious. And Practices, which are the habits that survive a deadline. 1.1 The type system in one page

Go's type system is small on purpose: eight built-in types, one composite type, named types made from them, and interfaces. What it lacks — generics until recently, no implicit conversions, no operator overloading — is what makes it readable.

What exists, and what the rules are

Go has boolean, integer of several widths, floating point, complex, string, and the byte and rune aliases. Every type has a zero value and every declaration gets one automatically, which is the single most consequential design decision in the language: there is no uninitialised variable, so a struct's zero value is a valid value and a map's is a usable empty map. Types are concrete and conversion is explicit, so a []byte and a string are different types that convert explicitly and cost a copy. Assignment is not free of type rules but there is no implicit numeric promotion across named types, which means a MyInt is not an int until you convert it — and that is why a defined type is a genuine type rather than an alias. Then the four rules that follow, and each is a requirement. Declare a variable with := only when you are creating it, and use = afterwards, because the compiler catches the difference and a mistaken := inside a loop silently shadows. Prefer a defined type over a bare built-in in a structure's fields, because the defined type carries the unit in its name and the compiler then refuses to mix the fields. Use any where the value genuinely has no better type, and a named interface where it has one, because any in a struct field means the field's contract has not been decided. And Remember that a slice is a header, not the data, so copying a slice copies three words and the data is shared. Then the three things that go wrong, and each is a mechanism. := inside a loop body, which creates a new variable each iteration and shadows the outer one — the mechanism behind a loop that appears to do nothing. Appending to a slice whose capacity is shared, which writes into a backing array another slice also sees. And A string built by concatenation in a loop, which is quadratic because each concatenation allocates. Then the two practices, and both are disciplines. Name the unit in the type, so type Millis int64 rather than a comment saying milliseconds, because the compiler cannot read the comment and your reviewer will. And Return concrete types from functions and accept interfaces, because the reverse — accepting a concrete type — makes every caller depend on the implementation and defeats the reason interfaces exist.

/* THE THREE FAILURES, and the mechanism behind each.

   1. := INSIDE A LOOP BODY creates a new variable each iteration
      and SHADOWS the outer one. The code looks correct, the value
      is wrong, and no compiler warning is produced because nothing
      is wrong as far as the language is concerned - you simply
      wrote about a different variable than you meant.

   2. APPENDING TO A SLICE WHOSE CAPACITY IS SHARED writes into a
      BACKING ARRAY another slice also sees. Two slices built from
      one allocation are two windows onto one array, and appending
      to the shorter one can overwrite the longer one's elements. */

/* Two views of one array. Both see the same storage. */
func shared_backing() {
    base := make([]int, 3, 8)       /* len 3, cap 8                  */
    a := base                        /* len 3, cap 8                  */
    b := base                        /* len 3, cap 8 - SAME ARRAY     */

    a = append(a, 1, 2, 3, 4, 5)     /* fits in cap: writes into the  */
                                       /* backing array, at 3..7       */
    /* b still has len 3, so b does not SEE them - but extend b
       and it reads what a wrote:                                   */
    b = b[:cap(b)]                   /* len 8: exposes the shared tail*/
    fmt.Println(b)                   /* [0 0 0 1 2 3 4 5] - a's data */

    /* The fix when the slices must be independent: copy on append,
       or give each its own allocation with a full slice expression. */
    c := base[:3:3]                  /* cap 3: append MUST reallocate */
    c = append(c, 9, 9)
    fmt.Println(b)                   /* unchanged: [0 0 0 1 2 3 4 5]  */
}

/* 3. STRING CONCATENATION IN A LOOP IS QUADRATIC, because each
   concatenation allocates a new string and copies both operands.
   The fix is a strings.Builder, which is amortised linear. */

func concat_loop(parts []string) string {
    var s string
    for _, p := range parts {
        s += p                       /* O(n^2) in total bytes        */
    }
    return s
}

func concat_builder(parts []string) string {
    var sb strings.Builder
    total := 0
    for _, p := range parts {
        total += len(p)               /* know the size, or amortise    */
    }
    sb.Grow(total)
    for _, p := range parts {
        sb.WriteString(p)
    }
    return sb.String()
}

1.2 The zero value is a design, not an absence

Most languages treat the zero value as a lack; Go treats it as a legitimate state, and that is why so little Go code has constructors that do nothing but assign.

What the zero value is for

A type's zero value should be useful without any setup, and most of Go's built-in and standard-library types honour that. A struct's zero value is a valid struct, which is why a large configuration can be returned by value and filled in field by field. A slice's zero value is nil, which ranges and appends handle, so a nil slice behaves as an empty one for every operation that matters. A map's zero value is nil, which reads fine — and which is the asymmetry to remember. An interface's zero value is nil, which means no implementation, and the whole nil-interface discussion in section 1.3 follows from that. Then the four rules that follow, and each is a requirement. Design a type so its zero value is what you want when nobody configured it, because that is the state a caller gets if they declare a variable and forget to initialise it. Lazily initialise a map on first write rather than in a constructor, since a nil map reads correctly and only the write panics. Do not rely on the zero value of a struct field whose zero is a sentinel meaning "unset" unless that sentinel is documented, because it becomes a magic number. And Prefer a constructor that returns a value over one that fills a pointer, because a value cannot be left half-built by a caller who forgets to check. Then the three things that go wrong, and each is a mechanism. A map field written without initialisation, which panics in a code path the author never ran because the map was always populated by a constructor in the tests. A bool field whose zero means false but whose intent was "not specified", which makes it impossible to tell "the user said false" from "the user said nothing". And A struct with a zero value that is expensive to produce, which pushes every caller toward a constructor and the zero value becomes a trap. Then the two practices, and both are disciplines. Write the zero-value test explicitly, — declare the value, use it, assert nothing panics — because it is the state every caller who skips your constructor gets. And Keep the zero value cheap and meaningful, because a type whose zero value allocates is a type every stack frame pays for.

/* THE ZERO VALUE IS A DESIGN, not an absence. A type's zero value
   should be USEFUL without any setup, and most of Go's types honour
   that. This is why so little Go code has a constructor that only
   assigns fields. */

type Config struct {

    Backoff time.Duration    /* zero: no backoff - a real meaning  */

1.3 Nil, the interface trap, and pointers

Go has no null pointer, but it has three things that are nil and they are not the same thing — and the difference between a nil interface and an interface holding a nil pointer causes more confusion than any other feature of the language.

Three nils

A nil pointer is an address of nothing. A nil slice is a header with no data, no length and no capacity, and it ranges, appends and copies correctly. A nil interface is two words — a type and a value — with the type word zero, meaning no method set and therefore no behaviour. Then the four rules that follow, and each is a requirement. Compare an interface to nil only to test whether it has a method set, because that is the only question the comparison answers. When returning an interface, return a literal nil rather than a typed nil pointer, because the literal nil produces a nil interface and the typed pointer produces an interface with a type and a nil value — which is not equal to nil. A pointer is for optionality and for large values, and for nothing else: a pointer to a struct field lets a function mutate the original, which is the actual reason to have one. And Prefer a value receiver unless you must mutate, because the method set differs and a value-receiver method is in the interface while a pointer-receiver method is not. Then the three things that go wrong, and each is a mechanism. Returning a typed nil pointer as an error interface, which is the classic: the interface is non-nil, the caller's err != nil is true, and the failure is silent. Mixed receiver types on one type, which means half the method set is only available through a pointer and the type's own interface assertions silently fail. And A pointer to a loop variable kept in a slice, which — before per-iteration scoping — made every element the same address. Then the two practices, and both are disciplines. Use a sentinel error or a typed nil check rather than a typed nil return, because a typed nil is indistinguishable from success at the call site. And Keep receivers consistent per type, because a mixed method set is a compile error waiting at an interface assertion somebody else writes.

/* THREE NILS, and they are not the same thing.

   nil POINTER    an address of nothing.
   nil SLICE      a header with no data, no length, no capacity. It
                  ranges, appends and copies CORRECTLY.
   nil INTERFACE  TWO WORDS - a type and a value - with the type
                  word zero, meaning NO METHOD SET and therefore NO
                  BEHAVIOUR.

   THE INTERFACE TRAP. An interface value holding a nil *pointer* has
   a NON-ZERO TYPE WORD, so it is NOT equal to nil. */

type Reader interface{ Read() string }
type myReader struct{ s string }
func (m *myReader) Read() string { return m.s }

func typedNil() {
    var p *myReader                       /* nil pointer             */
    var i Reader = p                      /* interface, type set,     */
                                           /* value nil: NOT == nil  */
    fmt.Println(i == nil)                 /* false                    */
    fmt.Println(i.Read())                 /* PANIC, or empty          */
}   /* This is the single most common source of confusion in Go: the
     nil check that does not catch a typed nil, in a function whose
     whole contract is to return nil on failure.                  */

/* THE FIX, which is a sentinel rather than a nil return. */
var ErrNotFound = errors.New("not found")

func lookup(id string) (Reader, error) {
    if id == "" { return nil, ErrNotFound }   /* an UNTYPED nil:    */
    return &myReader{s: id}, nil                /* an interface is nil */
}

/* Compare the interface to nil only to ask whether it has a method
   set - which is the only question the comparison answers. */
func describe(r Reader) string {
    if r == nil { return "no reader" }      /* genuinely no impl   */
    return fmt.Sprintf("%T", r)             /* what did we get      */
}

/* A POINTER IS FOR optionality and for large values, and for mutating
   a caller's value. It is not for "passing efficiently" in general. */
type Big struct{ Buf [1024]byte }

func byValue(b Big)    {}    /* 1 KB copied per call              */
func byPointer(b *Big) {}    /* 8 bytes, and can MUTATE b         */

/* KEEP RECEIVER TYPES CONSISTENT PER TYPE, because the method set
   differs and a value-receiver method is in the interface while a
   pointer-receiver method is NOT. */
type counter struct{ n int }

func (c *counter) Inc() { c.n++ }   /* pointer receiver: MUTATES   */
/* func (c counter) Get() int { return c.n }   value receiver     */

/* The consequence, and it is a compile error somebody else writes:
   counter does NOT satisfy an interface requiring Inc, because Inc
   is on *counter and counter's method set does not include it. */
var _ interface{ Inc() } = (*counter)(nil)   /* the fix: assert the
                                                  POINTER type   */

/* A POINTER TO A LOOP VARIABLE kept in a slice: before the language
   made loop variables per-iteration, every element shared one
   address. The language now allocates per iteration when the
   variable is captured, which costs an allocation per iteration and
   is worth knowing about. */
func capture(ids []int) []*int {
    var out []*int
    for _, id := range ids {
        id := id                    /* explicit copy: no ambiguity */
        out = append(out, &id)      /* a distinct variable         */
    }
    return out
}
/* THE THREE FAILURES, and the mechanism behind each.

   1. RETURNING A TYPED NIL POINTER AS AN ERROR INTERFACE.
        func run() error {
            var p *myError            // typed nil
            return p                  // compiles, warns, WRONGS
        }
        err := run()
        if err != nil { ... }        // ALWAYS TRUE, even on success
      The compiler warns about this exact pattern and the warning is
      easy to ignore. The mechanism is that converting a nil pointer
      to an interface WRITES THE TYPE WORD, and a non-zero type word
      makes the interface non-nil.

   2. MIXED RECEIVER TYPES ON ONE TYPE. Half the method set is only
      available through a pointer, so the type does not satisfy
      interfaces its own methods suggest it should, and the failure
      appears at an interface assertion written in a different file.

   3. A POINTER TO A LOOP VARIABLE kept in a slice. Historically
      every element shared one address and the slice held N copies
      of the final value. The language changed the default; the cost
      is one allocation per iteration when the variable escapes,
      which is invisible until a profile shows it.

/* THE SYSTEMATIC FIX for 2, which costs one line per type. */
type store interface{ Get(string) ([]byte, error) }

type fileStore struct{ root string }

func (f *fileStore) Get(k string) ([]byte, error) { return nil, nil }
func (f *fileStore) Put(k string, v []byte) error  { return nil }

/* Assert at COMPILE TIME that the pointer type satisfies the
   interface. If a method's receiver type changes, this fails to
   compile HERE rather than in the caller that needed it. */
var _ store = (*fileStore)(nil)

/* THE SYSTEMATIC FIX for 3, which is a two-line rule. If a pointer
   to a local escapes, either copy the value into a new variable or
   store the value rather than the address. */
type server struct {
    name  string
    ports []int          /* VALUES, not pointers: no escape, and  */
                         /* no aliasing when the slice grows        */
}

func makeServers(names []string) []server {
    out := make([]server, 0, len(names))
    for _, n := range names {
        out = append(out, server{name: n, ports: []int{80, 443}})
    }
    return out
}

   check rather than a typed nil return, because a typed nil is
   indistinguishable from success at the call site and the compiler's
   warning is not enough.

   And KEEP RECEIVERS CONSISTENT PER TYPE - one type, one receiver
   form - because a mixed method set is a compile error waiting at an
   interface assertion somebody else writes in a different package. */

1.4 Constants, variables and where things live

Go has three levels of storage and each has a rule about initialisation time that is stricter than you would expect, and the strictness is what makes package-level variables safe to use.

Three levels

Constants are compile-time values with no address and no type of their own until used. Package-level variables are initialised before main runs, in dependency order. Function-local variables are initialised when the declaration is reached. Then the four rules that follow, and each is a requirement. Package-level initialisation order is dependency-based, so a variable whose initialiser reads another is initialised after it, and the compiler errors on a cycle rather than picking an order. A constant cannot be a slice, a map or a struct, because it has no address — which means a "constant table" must be a package-level variable. A package-level variable's initialiser may not use another package's variable unless that is also initialised first, and the cycle detection covers that too. And A local variable is initialised when the line executes, so a closure capturing it sees the value at the point of declaration, not the final value. Then the three things that go wrong, and each is a mechanism. A package-level variable initialised by reading a mutable map built in init, which runs in file-name order within a package and is not the order you wrote the lines. A constant used where a variable was meant, which fails with "cannot take the address" and is a sign the design has a hidden invariant. And Building a large package-level table in an init function, which delays every user of the package including those who only wanted a type. Then the two practices, and both are disciplines. Keep package-level variables to configuration the package actually needs, because every one of them is initialised for every importer and a package that reads a file at startup is a package that cannot be tested. And Prefer a function returning a value to an init that fills a package variable, because a function's result is lazy, testable, and cannot be initialised in the wrong order.

/* THREE LEVELS OF STORAGE, each with an initialisation rule that
   is STRICTER than you would expect - and the strictness is what
   makes package-level variables safe to use at all. */

    _ = a
}

/* A CONSTANT CANNOT BE A SLICE, MAP OR STRUCT, because it has no
   address. A "constant table" must therefore be a VARIABLE. */

// WRONG: a slice cannot be constant.
/* const Allowed = []string{"a","b"}    error: invalid array length */

/* RIGHT: a package-level variable, with an explicit type so the
   empty literal is legal. */
var Allowed = []string{"a", "b", "c"}

// 2. PACKAGE-LEVEL VARIABLES: initialised before main, in
//    DEPENDENCY ORDER, and the compiler detects a cycle.
var name     = "service"
var endpoint = "https://" + name + "/v1"    /* depends on name, so
                                                it runs after       */
var a, b     = 1, compute()                  /* a is plain, b is not */

/* A cycle is a COMPILE ERROR, not a runtime surprise:
     var x = y
     var y = x                 // initialization cycle not allowed  */

// 3. FUNCTION-LOCAL: initialised WHEN THE LINE EXECUTES. A closure
//    capturing it sees the value at that point, not the last value.
func closures() []func() int {
    var out []func() int
    for i := 0; i < 3; i++ {
        i := i                    /* a NEW variable each iteration */
        out = append(out, func() int { return i })
    }
    return out                    /* 0, 1, 2                      */
}

/* The value at declaration, not the final value, is what a closure
   sees - so this returns 3, 3, 3 with the outer variable:
     for i := 0; i < 3; i++ {
         out = append(out, func() int { return i })
     }
   ... and it is why i := i inside a loop is an idiom rather than
   an accident.                                                  */

/* THE THREE FAILURES.
   1. A PACKAGE-LEVEL VARIABLE initialised by reading state built in
      an init FUNCTION. init functions run in FILE-NAME order
      within a package - a1.go before z.go - not in the order the
      lines were written, and not in dependency order. The result
      depends on file names.
   2. A CONSTANT used where a variable was meant: "cannot take the
      address", which is the compiler telling you that a hidden
      invariant is being violated.
   3. A LARGE PACKAGE-LEVEL TABLE BUILT IN init, which delays every
      importer of the package including those who only wanted a
      type from it. */

var registry map[string]Handler      /* the bug: nil at init time  */
var config  Config

func init() {                          /* runs in FILE-NAME order   */
    config = loadConfig()              /* may read a nil registry    */
    registry = make(map[string]Handler)
}   /* Read registry before making it, and you get the zero value
     silently - not a panic, because you are READING a nil map. */
/* THE FIXES, and the two disciplines.

   FIX FOR 1 AND 3: a function returning a value, not an init that
   fills a package variable. A function's result is LAZY - nothing
   runs until somebody asks - TESTABLE - you can call it with
   arguments - and cannot be initialised in the wrong order because
   it is initialised nowhere. */

type Registry struct {
    handlers map[string]Handler
    order    []string          /* deterministic listing           */
}

func NewRegistry() *Registry {
    return &Registry{handlers: make(map[string]Handler)}
}

func (r *Registry) Register(name string, h Handler) {
    if _, dup := r.handlers[name]; dup {
        panic("duplicate handler: " + name)   /* fail at STARTUP,  */
    }                                          /* not at 3am         */
    r.handlers[name] = h
    r.order = append(r.order, name)           /* insertion order:  */
}                                              /* reproducible      */

func (r *Registry) Get(name string) (Handler, bool) {
    h, ok := r.handlers[name]
    return h, ok
}

func (r *Registry) Names() []string { return append([]string(nil), r.order...) }

/* The registry is now created by whoever needs it, in the order they
   need it, with no package-level state at all. A test constructs its
   own; two tests cannot interfere; importing the package does not
   read a configuration file. */

/* THE TWO DISCIPLINES.

   KEEP PACKAGE-LEVEL VARIABLES TO CONFIGURATION THE PACKAGE
   ACTUALLY NEEDS. Every one of them is initialised for EVERY
   IMPORTER, and a package that reads a file at startup is a package
   that cannot be unit tested, cannot be imported by a tool without
   side effects, and cannot be used in a serverless function.

   PREFER A FUNCTION RETURNING A VALUE to an init that fills a
   package variable, because a function's result is lazy, testable
   with arguments, and cannot be initialised in the wrong order -
   whereas init is eager, untestable, and ordered by file name. */

2.1 Structs: layout, embedding and the tags

A Go struct is a struct in the C sense with no inheritance, no methods in the declaration sense, and two features with no analogue elsewhere: embedding, which promotes methods rather than members of state, and tags, which are metadata other packages read by reflection.

Layout, embedding, tags

Fields are laid out in declaration order with padding for alignment, so ordering fields largest-first is a real, measurable optimisation for a struct in a large slice. Embedding a type promotes its exported fields and methods to the outer struct, which is composition and inheritance's useful half without the is-a relationship. A struct tag is a string of key-value pairs, read by the encoding packages and by anything else using reflection — which means the schema of a JSON document is a set of strings with no compile-time checking. Then the four rules that follow, and each is a requirement. Order fields largest-alignment-first, because a struct in a slice of a million is a million layouts. Embed a type only when you want its methods promoted, and use a named field when you want the member, because a named field is explicit and an embedded one is invisible at the use site. Always give a tag key that exists in the package you are targeting, since nothing checks it. And Keep unexported fields at the top or the bottom deliberately, because they are padding candidates and their position changes the size. Then the three things that go wrong, and each is a mechanism. Embedding two types that both have a String method, which makes the outer type ambiguous for every interface assertion and the compiler says so — correctly. A JSON tag with a typo in the key, which means the field is silently ignored on marshal and populated with the Go name on unmarshal. And Embedding a mutex, which is correct but means the struct's copy semantics change and any go vet copylocks warning is real. Then the two practices, and both are disciplines. Embed an interface when you want substitutability and a named field when you want a member, because the two produce source that reads identically at the definition and completely differently at the use. And Write a String() method on every type a human will see in a log, because the default formatting of a struct with pointers is unusable.

/* A GO STRUCT is a C struct with no inheritance and two features with
   no real analogue: EMBEDDING, which promotes METHODS rather than
   state, and TAGS, which are metadata read by reflection. */

// 1. LAYOUT. Fields are laid out in declaration order with padding
//    for alignment. Order largest-first is a REAL, MEASURABLE win.
type BadOrder struct {     /* 24 bytes: 1 + 3 pad + 8 + 4 + 4 pad */
    Flag    bool          /* offset 0                                */
    Ptr     *Node         /* needs 8-alignment: 4 bytes of padding    */
    ID      uint32        /* offset 12                               */
    Name    string        /* offset 16, total 24                     */
}

type GoodOrder struct {    /* 24 bytes too, but no interior hole    */
    Ptr     *Node         /* offset 0                                */
    Name    string        /* offset 8                                */
    ID      uint32        /* offset 16                               */
    Flag    bool          /* offset 20                               */
}   /* In THIS example the sizes match. Reorder the fields and the
     interior padding disappears, and the win is per-element in a
     slice of a million. Measure with unsafe.Sizeof; do not guess. */

// 2. EMBEDDING promotes METHODS. It does not create an is-a
//    relationship; it composes behaviour.
type Reader interface{ Read(p []byte) (int, error) }
type Writer interface{ Write(p []byte) (int, error) }
type ReadWriter interface {
    Reader
    Writer
}

type logger struct{ prefix string }
func (l logger) Log(msg string) string { return l.prefix + msg }

type service struct {
    logger                      /* EMBEDDED: service.Log works     */
    ReadWriter                  /* EMBEDDED: promotes Read+Write   */
    Name     string             /* NAMED: service.Name, no promotion*/
}

/* Three DIFFERENT forms of "have a":
     EMBEDDED logger   -> s.Log("x")          substitutable
     EMBEDDED ReadWriter -> s.Read(...)       substitutable
     NAMED   Name     -> s.Name              a member          */
func use(s service) {
    s.Log("start")             /* promoted from the embedded logger*/
    s.Name = "billing"         /* the named field, explicit          */
    var rw ReadWriter = s.ReadWriter
    _ = rw
}   /* An EMBEDDED INTERFACE is the substitution mechanism. An
     embedded CONCRETE TYPE is only method promotion, and the outer
     type then inherits that implementation permanently.         */

// 3. TAGS are metadata read by reflection. Nothing checks them.
type Order struct {
    ID       int64  `json:"id"     db:"id"      validate:"required"`
    Amount   int64  `json:"amount" db:"amount"  validate:"gt=0"`
    Note     string `json:"note,omitempty"`
    internal string `json:"-"`  /* unexported anyway              */
}

/* A typo in a tag key is SILENT. This field marshals as "Amunt"
   because that is the field name, and unmarshals from "amount" into
   nothing - no error, no warning. */
type Typo struct {
    Amunt int64 `json:"amount"`
}

/* THE THREE FAILURES.
   1. EMBEDDING TWO TYPES WITH THE SAME METHOD: ambiguous at every
      use site, and the compiler says so - correctly. "ambiguous
      selector s.String".
   2. A TAG KEY WITH A TYPO: silently ignored on marshal, and on
      unmarshal the field is populated from the GO name.
   3. EMBEDDING A MUTEX: correct, and it changes the struct's copy
      semantics. Any go vet copylocks warning is real, and the
      compiler will not stop you passing the struct by value. */
/* THE FIXES, and the two disciplines.

   FIX FOR 1: give one of them an explicit method that resolves the
   ambiguity, so the intent is written down rather than forced. */
type auditLogger struct{ logger; audit []string }
func (a auditLogger) Log(msg string) string {
    a.audit = append(a.audit, msg)   /* record, then delegate      */
    return a.logger.Log(msg)
}   /* Now service.Log is unambiguous and the audit happens.      */

/* FIX FOR 2: check the tags in a test, against the schema you
   intended. Reflection makes this twenty lines and it catches the
   class of bug that a rename introduces silently. */
func TestTagsMatchFields(t *testing.T) {
    typ := reflect.TypeOf(Order{})
    for i := 0; i < typ.NumField(); i++ {
        f := typ.Field(i)
        tag := f.Tag.Get("json")
        if tag == "" && !f.IsExported() { continue }
        if tag == "" {
            t.Errorf("%s.%s has no json tag; it will marshal under its Go name",
                typ.Name(), f.Name)
        }
        if strings.Contains(tag, "-") && tag != "-" {
            t.Errorf("%s.%s: '-' is only valid alone", typ.Name(), f.Name)
        }
    }
}

/* FIX FOR 3: never embed a sync.Mutex in a type that is passed by
   value. Pass a POINTER, and add a noCopy guard so vet catches a
   future mistake. */
type Guarded struct {
    mu sync.Mutex
    n  int
}

func (g *Guarded) Inc() { g.mu.Lock(); defer g.mu.Unlock(); g.n++ }

/* THE TWO DISCIPLINES.

   EMBED AN INTERFACE WHEN YOU WANT SUBSTITUTABILITY and a NAMED
   FIELD WHEN YOU WANT A MEMBER, because the two produce source that
   reads identically at the definition and completely differently at
   the use: s.ReadWriter is a field either way, and only the
   embedded one also promotes Read and Write onto s.

   WRITE A String() METHOD ON EVERY TYPE A HUMAN WILL SEE IN A LOG,
   because the default formatting of a struct containing pointers is
   a list of hexadecimal addresses, which tells a reader nothing. */

func (o Order) String() string {
    return fmt.Sprintf("order %d: %d cents%s", o.ID, o.Amount,
        map[bool]string{true: "", false: " (unpaid)"}[o.Amount == 0])
}   /* fmt checks for Stringer automatically - so this one method
     fixes the type's appearance in every log line, error message
     and test failure that mentions it.                            */

2.2 Interfaces: small, implicit, and defined by the consumer

An interface in Go is a method set, a type satisfies one by having the methods, and the interface belongs to whoever needs the behaviour rather than to whoever implements it — which is the opposite of most languages and produces better packages.

What an interface is

An interface value is a pair of words: a type and a value, and calling a method means looking up the method in the type's method set at run time. Satisfaction is implicit, so there is no declaration and no inheritance chain — a type satisfies everything it happens to have methods for. An interface is satisfied by anything with the right methods, including a value type and a pointer to it as different things, which is why the receiver type matters. Then the four rules that follow, and each is a requirement. Define the interface where it is used, — in the consuming package — so the provider package needs no knowledge of it and its dependency list stays short. Keep interfaces small, because every method is a promise and an interface with eight methods is eight promises that a test double must keep. Assert interface compliance at compile time with a blank variable, so a method rename fails where it happened. And Accept an interface and return a concrete type, so the caller can use everything the concrete type offers. Then the three things that go wrong, and each is a mechanism. An interface defined in the implementing package, which forces every consumer to import the provider to name the type they pass in. A type satisfying an interface by accident through embedding, which is usually welcome and occasionally means the type grew a method that changes what it can be used for. And A value type where a pointer was needed, which fails to satisfy a mutating interface and is caught at the assertion if you have one. Then the two practices, and both are disciplines. Write the one-method interfaces — reader, writer, closer, clock — and use them, because a function taking a one-method interface can be given a test double in three lines and a real implementation without change. And Put the compile-time assertion next to the type, so the check is a line somebody reads rather than a failure somebody debugs.

/* AN INTERFACE VALUE IS A PAIR OF WORDS: a TYPE and a VALUE.
   Calling a method means looking it up in the type's method set at
   run time. SATISFACTION IS IMPLICIT - there is no declaration, no
   inheritance chain, and no need for the implementer to know the
   interface exists. */

// ---- 1. THE INTERFACE BELONGS TO THE CONSUMER ---------------
package cache   // the consumer defines what it needs

type Store interface {
    Get(key string) ([]byte, bool)
    Put(key string, value []byte)
}
// NOT declared in the memcache package, NOT imported from it.
// That package has no idea this interface exists and its
// dependency list is empty. This is the single most important
// thing about Go interfaces.

// ---- 2. SMALL IS NOT A STYLE RULE --------------------------
// Each method is a PROMISE, and a test double must keep every one.
type Closer interface{ Close() error }              /* 1 method      */
type ReadWriter interface {                         /* 2: io         */
    Read(p []byte) (int, error)
    Write(p []byte) (int, error)
}
type ReadWriteCloser interface {                    /* 3: io         */
    ReadWriter
    Closer
}

/* A function taking a ONE-METHOD interface can be given a real
   implementation and a test double with the same three lines. */
type CloserFunc func() error
func (f CloserFunc) Close() error { return f() }

// ---- 3. ASSERT COMPLIANCE AT COMPILE TIME ------------------
// Next to the TYPE, so a method rename fails where it happened
// rather than in a consumer three packages away.
package store

type File struct{ root string }
func (f *File) Get(key string) ([]byte, bool) { b, err := os.ReadFile(f.root + "/" + key); return b, err == nil }
func (f *File) Put(key string, v []byte)       { _ = os.WriteFile(f.root+"/"+key, v, 0o600) }

var _ cache.Store = (*File)(nil)     // compile-time assertion

// ---- 4. RETURN CONCRETE, ACCEPT INTERFACE -------------------
// The caller gets everything the concrete type offers, and can
// still substitute anything that satisfies the interface.
package cache

type FileCache struct{ dir string; max int }

func Open(dir string) *FileCache {          // returns a CONCRETE type
    return &FileCache{dir: dir, max: 1000}
}

func (c *FileCache) Get(key string) ([]byte, bool) { /* ... */ return nil, false }
func (c *FileCache) Put(key string, v []byte)       { /* ... */ }
func (c *FileCache) Len() int { return 0 }          // NOT in Store

func Serve(s cache.Store) { /* ... */ }              // accepts INTERFACE

func main() {
    c := cache.Open("/tmp")   // a *FileCache: c.Len() works
    Serve(c)                  // passed as an interface
}   /* THE THREE FAILURES.
   1. AN INTERFACE DEFINED IN THE IMPLEMENTING PACKAGE: every
      consumer must import the provider to name the type it passes,
      so the dependency runs the wrong way and a small utility
      library pulls in a large one.
   2. A TYPE SATISFYING AN INTERFACE BY ACCIDENT THROUGH EMBEDDING:
      usually welcome, and occasionally it means the type grew a
      method that silently changed what it can be used for - a
      Bytes() method added for debugging makes a type satisfy
      three interfaces nobody planned.
   3. A VALUE TYPE WHERE A POINTER WAS NEEDED: a mutating method
      has a pointer receiver, so the value type's method set does
      not include it, and the type stops satisfying the interface.
      Caught at compile time IF you have the assertion.          */
/* THE TWO DISCIPLINES, with the shape each produces.

   DISCIPLINE 1: WRITE THE ONE-METHOD INTERFACES and use them.
   reader, writer, closer, clock, notifier - each is three lines
   here and each removes a dependency from a signature. */

package clock

type Clock interface{ Now() time.Time }

type realClock struct{}
func (realClock) Now() time.Time { return time.Now() }

func System() Clock { return realClock{} }

/* A test double costs three lines and needs no library, because
   there is exactly one method to implement. */
type fixedClock struct{ t time.Time }
func (c fixedClock) Now() time.Time { return c.t }
func NewFixed(t time.Time) Clock    { return fixedClock{t} }

/* And this is why the discipline matters: the cache under test now
   takes a Clock, so a test can assert on expiry exactly. */
package cache

type entry struct { value []byte; at time.Time }
type Cache struct {
    c   clock.Clock
    ttl time.Duration
    m   map[string]entry
}

func New(c clock.Clock, ttl time.Duration) *Cache {
    return &Cache{c: c, ttl: ttl, m: make(map[string]entry)}
}

func (c *Cache) Get(key string) ([]byte, bool) {
    e, ok := c.m[key]
    if !ok { return nil, false }
    /* Deterministic expiry. A cache that calls time.Now() itself
       can only be tested by sleeping, and sleeping tests fail on a
       loaded machine and pass on a fast one. */
    if c.c.Now().Sub(e.at) > c.ttl {
        delete(c.m, key)
        return nil, false
    }
    return e.value, true
}

/* A test that asserts real behaviour, not a real duration: */
func TestExpiry(t *testing.T) {
    start := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
    c := New(clock.NewFixed(start), time.Minute)
    c.Put("k", []byte("v"))
    if _, ok := c.Get("k"); !ok { t.Fatal("expired too early") }

    later := New(clock.NewFixed(start.Add(2*time.Minute)), time.Minute)
    later.m = c.m                     /* share the contents         */
    if _, ok := later.Get("k"); ok { t.Fatal("did not expire") }
}

/* DISCIPLINE 2: PUT THE COMPILE-TIME ASSERTION NEXT TO THE TYPE,
   so the check is a line somebody reads. Five lines, once, and it
   turns a rename into a compile error at the rename. */

var (
    _ cache.Store      = (*File)(nil)
    _ cache.Store      = (*Redis)(nil)
    _ clock.Clock      = realClock{}
    _ io.Reader        = (*File)(nil)     /* cross-check stdlib too */
    _ fmt.Stringer     = Order{}
)   /* Five assertions cost nothing at run time, cost one line each
     to maintain, and catch the whole class of "it stopped
     satisfying something after a refactor" bugs - which are
     otherwise found in production, by a consumer.                 */

2.3 Generics: type parameters, constraints, and what they are for

Generics arrived in Go 1.18 and they are deliberately weaker than C++ or Rust templates: no operator overloading on type parameters, no generic methods, and constraints expressed as interface terms rather than as a trait hierarchy.

The design, and the three things it excludes

A type parameter is a parameter of the function or type that declares it, and the type argument is deduced at the call site from the arguments — so most calls need no explicit type argument. A constraint is an interface used only as a type-parameter bound, which means it can have type unions and you can use it for what operations are permitted. Instantiation is by shape, so two different type arguments with the same underlying representation share one instantiation, which is a much smaller code-size cost than a C++ template. Then the four things that follow, and each is a requirement. Define a constraint in terms of an expression — ~int | ~int64, comparable, fmt.Stringer — because that is what makes the body compile. Use a type union with the approximation operator so a defined type whose underlying type is int is included. A generic type cannot have methods with their own type parameters, so a generic container's constructor is a package-level function rather than a method. And Do not reach for generics to avoid an interface, because an interface already gives you polymorphism and generics give you zero-cost dispatch on a concrete type — different tools. Then the three things that go wrong, and each is a mechanism. A constraint with a method plus a type union, which is illegal — the two forms cannot be combined. Comparing two type parameters without a comparable constraint, which is a compile error pointing at the wrong place. And Using generics where a small interface was clearer, which produces a signature with four type parameters where a reader needed to see one method. Then the two practices, and both are disciplines. Use generics for genuinely type-parameterised data structures and algorithms, where the alternative is code duplication per type, and interfaces everywhere else. And Keep constraints minimal, because every method in a constraint is a promise your code makes to callers and a burden every implementation carries.

/* GENERICS IN GO ARE DELIBERATELY WEAKER than C++ templates or Rust
   traits: no operator overloading on type parameters, no generic
   METHODS, and constraints expressed as interface TERMS rather
   than as a trait hierarchy you inherit from.

   A type parameter is a PARAMETER. The type argument is deduced
   from the call arguments, so most calls need no explicit type. */

// ---- 1. CONSTRAINTS ARE INTERFACES USED AS BOUNDS ---------
// Three forms, and they cannot be combined in one constraint.

// (a) a method set: an ordinary interface
type Stringish interface{ String() string }

// (b) a type set: which TYPES are permitted
type Ordered interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64 |
    ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 |
    ~float32 | ~float64 | ~string
}
// The ~ is the APPROXIMATION operator: it includes types whose
// UNDERLYING type is int, so type Meters int satisfies
// Ordered. Without it, only the predeclared int does.

// (c) comparable: a predeclared constraint
func Unique[T comparable](in []T) []T {
    seen := make(map[T]bool, len(in))
    out := make([]T, 0, len(in))
    for _, v := range in {
        if seen[v] { continue }
        seen[v] = true
        out = append(out, v)
    }
    return out
}
// NOTE: no constraint needed for v as a map key, because map[T]
// requires T comparable and the compiler says so - the error names
// the map, not the constraint.

// ---- 2. DEDUCTION AT THE CALL SITE --------------------------
// Generics DO NOT COUNT when deducing, so a type argument is often
// needed. This is the single most common Go generics surprise.
func Keys[K comparable, V any](m map[K]V) []K {
    out := make([]K, 0, len(m))
    for k := range m { out = append(out, k) }
    return out
}

func dedupe[T comparable](in []T) []T { return Unique(in) }

var ages = map[string]int{"a": 1, "b": 2}
ks := Keys(ages)                     // COMPILES: V inferred
bad := dedupe([]any{1, "a"})         // COMPILES: T inferred
alsoBad := Keys[string](ages)        // ERROR: too few type args

// ---- 3. NO GENERIC METHODS ----------------------------------
// A generic type cannot declare a method with its own type
// parameters, so the constructor is a package-level function.
type Stack[T any] struct{ items []T }

func NewStack[T any]() *Stack[T] { return &Stack[T]{} }   /* package-level */
func (s *Stack[T]) Push(v T)     { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 { return zero, false }
    v := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return v, true
}
// func (s *Stack[T]) Map[U any](f func(T) U) *Stack[U]  ILLEGAL
// Write it as a free function instead:
func Map[T, U any](s *Stack[T], f func(T) U) *Stack[U] {
    out := NewStack[U]()
    for _, v := range s.items { out.Push(f(v)) }
    return out
}

// ---- 4. INSTANTIATION IS BY SHAPE, not by type --------------
// Two named types with the same representation share ONE
// instantiation - a much smaller code cost than C++ templates.
type Celsius float64
type Fahrenheit float64
func Add[T ~int | ~float64](a, b T) T { return a + b }
// Add(Celsius(1), Celsius(2)) and Add(Fahrenheit(1), ...)
// are TWO instantiations. Add(MyInt(1), MyInt(2)) and
// Add(1, 2) are ONE - identical shapes, so the linker merges them. 
/* THE THREE FAILURES.

   1. A CONSTRAINT WITH BOTH A METHOD AND A TYPE UNION is illegal:
        type Bad interface { ~int | ~int64; String() string }
                        // "cannot use ~int|~int64 with methods"
      The two forms are alternatives, not combinable. Split into
      two constraints and use both as bounds.

   2. COMPARING TWO TYPE PARAMETERS WITHOUT A COMPARABLE CONSTRAINT
      gives an error that points at the comparison rather than at
      the missing constraint:
        func Bad[T any](a, b T) bool { return a == b }
        // invalid operation: a == b (mismatched types T and T)
      The fix is func Good[T comparable](a, b T) bool.

   3. USING GENERICS WHERE A SMALL INTERFACE WAS CLEARER. A
      signature with four type parameters is harder to read than
      one interface with one method, and it prevents the caller
      from passing any type that does not match exactly - whereas
      an interface accepts everything with the right methods,
      including types that will be written later.

/* So: what do you actually use generics for? The case with no good
   alternative is a DATA STRUCTURE or an ALGORITHM whose code must
   be identical for many types, where duplication is unacceptable
   and a type switch would be worse. */

// GOOD: a generic map, because writing four of them is absurd and
// type-switching in every method is worse.
type OrderedMap[K Ordered, V any] struct {
    keys   []K                 /* insertion order: deterministic  */
    values map[K]V
}

func NewOrderedMap[K Ordered, V any]() *OrderedMap[K, V] {
    return &OrderedMap[K, V]{values: make(map[K]V)}
}

func (m *OrderedMap[K, V]) Set(k K, v V) {
    if _, ok := m.values[k]; !ok { m.keys = append(m.keys, k) }
    m.values[k] = v
}

3.1 Error is an interface, and errors.Is finds the cause

Go has no exceptions because exceptions hide control flow and make it hard to know what a function does on failure — so an error is an ordinary value returned by an ordinary function, and the whole discipline is in what you put in it.

What an error is

error is a one-method interface, so any type with an Error() string method is an error, and there is no base class and no hierarchy to inherit. An error is compared with == against a sentinel or with errors.Is against a wrapped one, and the second is the one that survives a wrapping chain. An error can carry structure, so a custom type with fields survives wrapping and can be extracted with errors.As. Then the four rules that follow, and each is a requirement. Wrap with %w and add context on the way out, because an error message that names the operation and the argument is the difference between a five-minute and a five-hour diagnosis. Check with errors.Is, not ==, because a wrapped error is not equal to its cause. Declare sentinel errors as package-level variables with errors.New, so callers can compare against them without importing a type. And Return the error; do not log it and continue, unless continuing is genuinely safe, because a logged-and-continued error is a program that reports problems it has already decided to ignore. Then the three things that go wrong, and each is a mechanism. Using fmt.Errorf with %v instead of %w, which flattens the chain so the caller can only see the outermost message. Comparing an error with == against something that may have been wrapped, which silently fails and the caller takes the wrong branch. And Defining an error type with an Error() method that captures a formatted string at construction, which is fine, and which makes the error unusable with errors.As for the structured case because the fields are gone. Then the two practices, and both are disciplines. Add context on the way out and never on the way in, so the message reads as a path from the call site to the cause rather than a stack of repetitions. And Have one place that turns an error into a log line, so the format is consistent and the decision about what to log is made once.

3.2 Panic, recover, and the rule about where they belong

A panic is for a situation the program cannot continue in — a bug, an impossible state, a violated invariant — and using it for anything recoverable reintroduces exactly the hidden control flow the language removed.

What panic actually is

A panic unwinds the stack, running every deferred function on the way, and unless something recovers the program exits with a non-zero status and prints the panic value. Recover only works inside a deferred function, because that is the only place the panic is still in flight. The runtime panics on several conditions by itself — a nil dereference, an out-of-range index, a division by zero, a concurrent map write — and none of them are catchable as an error. Then the four rules that follow, and each is a requirement. Panic only at package boundaries for genuine programmer error — an impossible argument, a violated invariant, a nil dependency that must not be nil — and never for an expected outcome. Never recover in library code to paper over a panic, because a library that swallows panics turns a bug into a wrong answer somewhere else. Recover at the top of a request handler or a worker, log it with the stack, and return a 500, which is the one place where the program has a legitimate way to continue. And Remember that a deferred recover changes the function's return values, because the function did not return normally — which is the mechanism behind a handler that returns zero values after a panic. Then the three things that go wrong, and each is a mechanism. Using panic for control flow, which makes the cost of the happy path depend on whether the error occurs and which the compiler cannot check. Recovering and continuing with half-updated state, which is the mechanism behind a corruption that appears much later. And A panic in a goroutine that nobody recovers, which takes down the whole process — there is no equivalent of a handler for a goroutine. Then the two practices, and both are disciplines. Make every index and every map access in a parser defensive by construction, because a panic from the standard library is a runtime failure you did not plan for. And Have exactly one recover site per process, so there is one place that knows a panic happened and every other place lets it propagate.

4.1 Goroutines: cheap concurrency, and what "cheap" means

A goroutine is a function scheduled by the Go runtime rather than by the operating system, and its stack starts at a few kilobytes and grows on demand — which is the single fact that makes high-concurrency Go programs possible.

The model

A goroutine has its own stack that starts at about two kilobytes and grows on demand, so a million of them cost gigabytes of address space rather than the eight-megabyte-per-thread stack a native thread needs. The runtime multiplexes goroutines across operating-system threads and moves a goroutine between them when a system call blocks, which is why a blocking read does not stop the others. Preemption is cooperative at function calls and asynchronous at loop back-edges since 1.14, which is why a tight arithmetic loop no longer starves the scheduler. Then the four rules that follow, and each is a requirement. Never start a goroutine without knowing who will stop it, because a leaked goroutine holds its stack and everything it references for the life of the process. Pass a context.Context to every goroutine that blocks, because it is the only way to abandon a wait. Use a buffered channel or an unbounded worker pool to bound concurrency, because a goroutine per request is fine right up until the downstream slows. And Recover in every goroutine you start that is not a top-level worker, because a panic there takes the whole process down. Then the three things that go wrong, and each is a mechanism. An unreferenced goroutine, which the garbage collector cannot collect — a running goroutine has a stack the collector scans, so a goroutine blocked forever on a channel is a permanent leak. A goroutine per item in a large loop, which is a million stacks and a million scheduler entries. And Ignoring the WaitGroup's counter by adding inside the loop rather than before, which is a race between the loop finishing and the last goroutine starting. Then the two practices, and both are disciplines. Name the goroutine's lifetime in the comment above it, because the code does not say who stops it and only one person knows. And Bound every fan-out, — a semaphore, a fixed worker count, or a buffered channel with a size — because unbounded fan-out is the failure mode that turns a traffic spike into an outage.

// THE SHAPE OF A BOUNDED FAN-OUT. This is the code to copy.
func fetchAll(ctx context.Context, ids []string, limit int) ([]Result, error) {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()                      // released even on success

    jobs := make(chan string)           // UNBUFFERED: a handshake,
    results := make(chan Result, len(ids))  // BUFFERED: the outputs
    var wg sync.WaitGroup

    // BOUND THE CONCURRENCY. Without this line, limit workers is
    // the difference between a spike and an outage.
    sem := make(chan struct{}, limit)
    defer func() { close(sem) }()

    for i := 0; i < limit; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for id := range jobs {
                sem <- struct{}{}       // acquire
                r, err := fetch(ctx, id)
                <-sem                    // release
                if err != nil { continue }
                select {
                case results <- r:
                case <-ctx.Done():
                    return                 // abandon, do not block
                }
            }
        }()
    }

    // Feed from one goroutine so the producer is not racing the
    // consumer's loop.
    go func() {
        defer close(jobs)
        for _, id := range ids {
            select {
            case jobs <- id:
            case <-ctx.Done():
                return
            }
        }
    }()

    // Collect. Note this needs no extra goroutine: closing results
    // after wg.Wait in a helper is the usual shape.
    go func() { wg.Wait(); close(results) }()

    var out []Result
    for r := range results { out = append(out, r) }
    if err := ctx.Err(); err != nil { return nil, err }
    return out, nil
}

4.2 Channels: the type, the rules, and the three ways to get them wrong

A channel is a typed, synchronised queue with a close operation, and almost every channel bug comes from one of three places: closing it twice, closing it from the wrong side, or assuming a receive and a send are a lock.

What a channel is

A channel carries values of one type and is the mechanism for both communication and synchronisation. An unbuffered channel makes a send and a receive a rendezvous: the sender blocks until a receiver takes the value, which is a synchronisation point and a mutual-exclusion guarantee for the code around it. A buffered channel of size n holds n values before a send blocks, which decouples the two sides and is a bounded queue rather than a handshake. Closing a channel is the sender's declaration that no more values will ever be sent, and a receive from a closed channel yields the zero value immediately and forever. Then the four rules that follow, and each is a requirement. Close a channel from exactly one place — the sender, and preferably the function that created it. Never send on a closed channel, which panics. Never close a channel you did not create, because its lifetime is somebody else's decision. And Use the comma-ok form or range when receiving, because a receive on a closed channel is not an error and is indistinguishable from a send of the zero value without the form. Then the three things that go wrong, and each is a mechanism. Closing a channel twice, which panics, and which happens in the deferred cleanup of a function that both owns the channel and inherits it. A defer close(ch) in the function that sends to a channel it received, which closes the sender's channel when the sender is still using it. And Using an unbuffered channel as a queue, which makes the whole thing serial and hides the deadlock until the goroutines are scheduled differently. Then the two practices, and both are disciplines. Size a channel deliberately and document why, because the size is the queue depth and therefore the burst the system absorbs. And Prefer a buffered channel of size one for a request/response pair, because it decouples the sender from the receiver's processing time without unbounded growth.

/* THE FOUR RULES, and each is a mechanism not a convention. */

// 1. CLOSE FROM EXACTLY ONE PLACE: the sender. The function that
//    CREATES a channel usually owns it, and the function that SENDS
//    on it is usually the one that closes it. Pick one and hold to
//    it for the whole package.
func produce(n int) <-chan int {
    out := make(chan int)          // UNBUFFERED: a rendezvous
    go func() {
        defer close(out)           // the creator closes: one place
        for i := 0; i < n; i++ {
            out <- i * i           // blocks until taken
        }
    }()
    return out
}

// 2. NEVER SEND ON A CLOSED CHANNEL. It panics, always, with a
//    message that names the channel and the send.
func wrong() {
    ch := make(chan int)
    close(ch)
    ch <- 1                     // panic: send on closed channel
}

// 3. NEVER CLOSE A CHANNEL YOU DID NOT CREATE. Its lifetime is
//    somebody else's decision, and they may still be sending.
func alsoWrong(in <-chan int) {
    defer close(in)              // panic when the real sender sends
}

// 4. USE COMMA-OK OR range, because a receive on a CLOSED channel
//    is NOT an error: it yields the zero value immediately and
//    forever, and the loop below would spin at full speed.
func drain(ch <-chan int) {
    for {
        v, ok := <-ch            // ok is false once closed
        if !ok { return }
        consume(v)
    }
    // The wrong version, which is a busy loop:
    //   for { consume(<-ch) }        // spins at 100% CPU forever
    // The idiomatic version:
    //   for v := range ch { consume(v) }
}

// AN UNBUFFERED CHANNEL IS A RENDEZVOUS, which means it
// SYNCHRONISES as well as communicates: the send completes only when
// a receiver has taken the value, so everything the sender wrote
// before the send is visible to the receiver after the receive.
func rendezvous() {
    data := make([]byte, 1)
    ready := make(chan struct{})
    go func() {
        data[0] = 'x'             // a WRITE
        close(ready)              // the SYNCHRONISATION POINT
    }()
    <-ready
    _ = data[0]                  // 'x' is GUARANTEED visible
}   /* This is the memory-model guarantee, and it is why the unbuffered
     channel is a correct way to publish data and the buffered one is
     NOT - a buffered send returns before a receiver takes the value,
     so publication through a buffered channel needs the receiver to
     do something else to establish the ordering.                    */

// THE THREE FAILURES.
// 1. CLOSING TWICE: panic. It happens in the deferred cleanup of a
//    function that both owns a channel and inherits it.
// 2. defer close(ch) IN THE FUNCTION THAT RECEIVES ON A CHANNEL IT
//    DID NOT CREATE: closes the sender's channel while the sender
//    is still using it.
// 3. USING AN UNBUFFERED CHANNEL AS A QUEUE: makes the whole
//    pipeline serial and hides the deadlock until the scheduler
//    happens to run the goroutines in a different order. */
/* THE TWO DISCIPLINES, with the shapes they produce.

   DISCIPLINE 1: SIZE A CHANNEL DELIBERATELY AND DOCUMENT WHY,
   because the size IS the queue depth and therefore the burst the
   system can absorb before it blocks. */

func Consumer(ctx context.Context, src <-chan Job, out chan<- Result) {
    // Buffer 100 = ten seconds of burst at the rate we expect.
    // Sized from the ingress rate, not from a round number.
    results := make(chan Result, 100)
    var wg sync.WaitGroup

    for i := 0; i < 8; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range src {
                r, err := handle(ctx, j)
                if err != nil { slog.Error("job failed", "err", err); continue }
                select {
                case results <- r:
                case <-ctx.Done():
                    return
                }
            }
        }()
    }
    go func() { wg.Wait(); close(results) }()
    for r := range results { out <- r }
}

/* DISCIPLINE 2: A BUFFERED CHANNEL OF SIZE ONE FOR A
   REQUEST/RESPONSE PAIR. It decouples the sender from the
   receiver's processing time without unbounded growth, and it
   turns "the caller waits for the answer" into "the caller waits
   for a slot", which is a different and much easier failure. */

type result struct { v any; err error }

func Call(ctx context.Context, fn func(ctx context.Context) (any, error)) (any, error) {
    ch := make(chan result, 1)   // EXACTLY ONE. Not 0, not more.

    go func() {
        // Recovery belongs here: a panic in this goroutine takes
        // the whole process down with no other handler in sight.
        defer func() {
            if r := recover(); r != nil {
                ch <- result{nil, fmt.Errorf("panic: %v", r)}
            }
        }()
        v, err := fn(ctx)
        ch <- result{v, err}
    }()

    select {
    case r := <-ch:
        return r.v, r.err
    case <-ctx.Done():
        // The goroutine may still be running. It will block writing
        // to ch forever - UNLESS the buffer absorbs it. This is the
        // reason the buffer is 1 and not 0: with an UNBUFFERED
        // channel this goroutine leaks on every timeout.
        return nil, ctx.Err()
    }
}

/* WHY SIZE ONE, AND NOT ZERO. With size 0 (unbuffered), the select
   above returns on ctx.Done() and the worker goroutine is then
   blocked forever on its send, holding its stack and its captured
   variables. With size 1, the send completes into the buffer and
   the goroutine exits. The cost is one retained result per
   abandoned call, which is bounded by the timeout rate.           */

/* THE THREE FAILURES, restated with the fix for each.

   1. CLOSING TWICE. Fix: close from the function that created the
      channel, once, in one place. If you cannot name that place,
      you have a design problem, not a bug.

   2. CLOSING AN INHERITED CHANNEL. Fix: pass every channel as
      <-chan T when the callee only receives, and chan<- T when it
      only sends. The compiler then refuses the operations you must
      not perform, which is the whole point of the direction
      arrows.

   3. USING AN UNBUFFERED CHANNEL AS A QUEUE. Fix: buffer it. The
      unbuffered form is for a handshake; the buffered form is for a
      queue; choosing the wrong one is the difference between a
      pipeline and a bottleneck. */

4.3 select, nil channels, and the three ways to shape a pipeline

A select waits on several channel operations at once, and two of its behaviours are so useful they are idioms: a nil channel blocks forever, and a closed channel is always ready.

What select actually does

select blocks until one of its cases is ready, and if several are ready it picks one at random. A nil channel blocks forever, which means a case on a nil channel is a case that never fires — which is how a channel is disabled. A closed channel is always ready, and receiving from it returns immediately with the zero value and a false comma-ok. A default clause makes the whole select non-blocking, which is a poll. Then the four rules that follow, and each is a requirement. Use a nil channel to disable a case, because it is the only way to conditionally include a case without an extra goroutine. Never put a default in a select that is supposed to wait, because it turns a block into a spin. Keep the number of cases small, because a select with eight cases is hard to read and hard to reason about the fairness of. And Prefer a fan-in with a WaitGroup over a select over a hundred channels, because the select has to be rewritten every time the count changes. Then the three things that go wrong, and each is a mechanism. A default in a select meant to block, which is a busy-wait that pins a core. A select reading a closed channel in a loop without the comma-ok, which spins forever consuming a value. And A send on a nil channel, which blocks forever and is the mechanism behind a goroutine that mysteriously never finishes. Then the two practices, and both are disciplines. Use context rather than a done channel for cancellation, because it carries a deadline and a cause and a value, all of which a bare channel cannot. And Structure a pipeline as a chain of stages with one channel between each, because that shape is the one where a backpressure problem is visible as a blocked stage.

/* select BLOCKS until one case is ready, and if several are ready it
   picks ONE AT RANDOM. Two of its behaviours are idioms. */

// A NIL CHANNEL BLOCKS FOREVER, so a case on one never fires: that
// is how a case is DISABLED. This is the idiom the runtime's own
// time.Timer depends on.
func maybeSend(ch chan int, v int, enabled bool) {
    var c chan int
    if enabled { c = ch }        // nil when disabled: never fires
    select {
    case c <- v:                 // blocks FOREVER if c is nil
        // only reached when enabled
    default:
        // enabled but the receiver is not ready: drop it
    }
}

// A CLOSED CHANNEL IS ALWAYS READY and yields the zero value with
// ok == false, immediately and forever.
func drainForever(ch <-chan int) {
    for {
        select {
        case v, ok := <-ch:
            if !ok { return }    // closed: the ONLY way out
            consume(v)
        }
    }
}

// A DEFAULT MAKES THE WHOLE SELECT NON-BLOCKING. That is a poll,
// and a poll in a loop is a spin.
func poll(ch <-chan int) int {
    select {
    case v := <-ch: return v
    default: return -1            // no value RIGHT NOW
    }
}

// THE FOUR RULES.
// 1. USE A NIL CHANNEL TO DISABLE A CASE - the only way to
//    conditionally include one without a second goroutine.
// 2. NEVER PUT default IN A SELECT THAT IS SUPPOSED TO WAIT. It
//    turns a block into a spin that pins a core.
// 3. KEEP THE NUMBER OF CASES SMALL. Eight cases is unreadable and
//    the fairness is not something anybody can reason about.
// 4. PREFER A FAN-IN WITH A WaitGroup over a select over a hundred
//    channels: the WaitGroup does not need rewriting when the count
//    changes, and the select does.

// ---- FAN-IN: many producers, one consumer --------------------
func fanIn(ctx context.Context, inputs ...<-chan string) <-chan string {
    out := make(chan string)
    var wg sync.WaitGroup
    for _, in := range inputs {
        wg.Add(1)
        go func(in <-chan string) {
            defer wg.Done()
            for {
                select {
                case v, ok := <-in:
                    if !ok { return }
                    select {
                    case out <- v:
                    case <-ctx.Done():
                        return
                    }
                case <-ctx.Done():
                    return
                }
            }
        }(in)                      // PASS IT: the direction arrow
    }                               // says receive-only, so a
    go func() { wg.Wait(); close(out) }()   // close cannot happen
    return out                      // before every producer is done

// ---- THE THREE FAILURES -------------------------------------
// 1. default IN A SELECT MEANT TO BLOCK:
//      for {
//          select {
//          case v := <-ch: handle(v)
//          default:            // a SPIN: 100% of one core,
//          }                    // doing nothing, forever
//      }
// 2. READING A CLOSED CHANNEL WITHOUT comma-ok, in a loop: the
//    loop spins at full speed consuming the zero value, and the
//    only symptom is a CPU at 100% and a log filling up.
// 3. A SEND ON A NIL CHANNEL blocks forever and the goroutine
//    NEVER FINISHES - the mechanism behind "one of my goroutines
//    just stopped working" with no error anywhere.             */
/* THE TWO DISCIPLINES.

   DISCIPLINE 1: USE context RATHER THAN A done CHANNEL FOR
   CANCELLATION, because a context carries a deadline, a cause and
   a value, and a bare channel carries none of them. */

func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return                       // ctx.Err() has a CAUSE
        case j, ok := <-jobs:
            if !ok { return }
            if err := handle(ctx, j); err != nil {
                // the error tells you WHOSE deadline it was
                slog.Error("job failed", "job", j.ID, "err", err)
                if errors.Is(err, context.Canceled) { return }
            }
        }
    }
}

// And the value: a deadline you can attach to a request and read
// back out of every layer that receives it.
type ctxKey struct{}
func WithRequestID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, ctxKey{}, id)
}
func RequestID(ctx context.Context) string {
    id, _ := ctx.Value(ctxKey{}).(string)
    return id
}

/* DISCIPLINE 2: STRUCTURE A PIPELINE AS A CHAIN OF STAGES WITH ONE
   CHANNEL BETWEEN EACH, so a backpressure problem is visible as a
   BLOCKED STAGE rather than as a latency number. */

// fetch -> parse -> enrich -> write, four goroutines, three
// channels. Each channel is a BOUNDARY you can measure.
func Pipeline(ctx context.Context, ids []string) error {
    rawCh := make(chan Raw, 64)     // 64 = the burst we absorb
    parsedCh := make(chan Parsed, 64)
    finalCh := make(chan Final, 64)

    var wg sync.WaitGroup
    step := func(in <-chan X, out chan<- Y, f func(context.Context, X) (Y, error)) {
        defer wg.Done()
        for {
            select {
            case x, ok := <-in:
                if !ok { return }
                y, err := f(ctx, x)
                if err != nil { slog.Error("stage failed", "err", err); continue }
                select {
                case out <- y:
                case <-ctx.Done():
                    return
                }
            case <-ctx.Done():
                return
            }
        }
    }

    wg.Add(3)
    go step(rawCh, parsedCh, parse)
    go step(parsedCh, finalCh, enrich)
    go step(finalCh, nil, write)     // a nil out disables the send

    go func() {
        defer close(rawCh)
        for _, id := range ids {
            select {
            case rawCh <- Raw{id: id}:
            case <-ctx.Done():
                return
            }
        }
    }()

    wg.Wait()
    return ctx.Err()
}

/* THE POINT OF THE NIL out. The final stage has nowhere to send, so
   its output channel is nil and the select's send case is disabled -
   which removes the need for a separate code path and a separate
   goroutine per shape. It is the clearest example in the language
   of a nil channel being a FEATURE rather than an oversight.       */

5.1 The five patterns, and the one that is wrong

Concurrent Go reduces to a handful of shapes — pipeline, fan-out/fan-in, worker pool, semaphore, and shared state under a lock — and knowing which one you are writing is most of the design work.

The five shapes

A pipeline is a chain of stages joined by channels, and each stage is a goroutine so each can run at its own rate. Fan-out/fan-in is many producers joined into one consumer, and the joining is what lets the consumer process results as they arrive rather than waiting for the slowest. A worker pool is a fixed set of goroutines sharing one job channel, and it is the shape that bounds concurrency. A semaphore is a buffered channel used as a permit, so it bounds concurrency without bounding queue depth. And shared state under a mutex is the shape with the highest defect rate, because the lock must be held across an invariant rather than around a statement. Then the four rules that follow, and each is a requirement. Prefer passing data to sharing it, because a value sent over a channel cannot be mutated by the receiver. Keep the critical section to the invariant, which usually means copying what you need under the lock, doing the work outside it, and writing back. Use one mutex per resource, never one global mutex, because a global lock is a global serialisation point and every throughput problem eventually becomes one. And Never hold a lock across a channel operation that can block, which is a deadlock waiting for the right interleaving. Then the three things that go wrong, and each is a mechanism. A slice appended to from two goroutines, which is a data race even though each append looks atomic — the race is on the length field. A global var read from a handler and written from a goroutine, which the race detector finds immediately and which is a latent bug in any program run without it. And Copying a struct containing a mutex, which is a race on the lock itself and which go vet's copylocks check reports. Then the two practices, and both are disciplines. Run every test with -race and every soak test without, because the detector finds the race and the soak finds the leak. And Make ownership explicit in the type, — a struct with a mutex is a struct that is not copyable, and saying so costs one comment.

/* FIVE SHAPES, and each is a whole design in miniature. */

// 1. PIPELINE: stages joined by channels, each a goroutine.
func Pipeline(ctx context.Context, n int) int {
    a := make(chan int)
    b := make(chan int)
    go func() { defer close(a); for i := 0; i < n; i++ { a <- i } }()
    go func() { defer close(b); for v := range a { b <- v * v } }()
    total := 0
    for v := range b { total += v }
    return total
}

// 2. FAN-OUT / FAN-IN: many producers, one consumer, results as
//    they arrive rather than after the slowest.
func FanOut(ctx context.Context, urls []string, workers int) []Result {
    jobs := make(chan string, len(urls))
    out := make(chan Result, len(urls))
    for _, u := range urls { jobs <- u }
    close(jobs)

    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for u := range jobs {
                r, err := fetch(ctx, u)
                out <- Result{URL: u, R: r, Err: err}   // never blocks
            }
        }()
    }
    go func() { wg.Wait(); close(out) }()

    var res []Result
    for r := range out { res = append(res, r) }
    return res
}

// 3. WORKER POOL: a fixed set sharing one job channel. This is the
//    shape that BOUNDS concurrency, and bounding is the point.
func WorkerPool(ctx context.Context, jobs <-chan Job, n int) error {
    g, ctx := errgroup.WithContext(ctx)
    g.SetLimit(n)                  // the bound
    for range n {
        g.Go(func() error {
            for j := range jobs {  // one worker, many jobs
                if err := handle(ctx, j); err != nil {
                    return fmt.Errorf("job %s: %w", j.ID, err)
                }
            }
            return nil
        })
    }
    return g.Wait()                // first error; context cancelled
}

// 4. SEMAPHORE: a buffered channel used as a permit. Bounds
//    CONCURRENCY without bounding queue depth, which is the
//    difference from a worker pool and is sometimes exactly right.
func FetchBounded(ctx context.Context, urls []string, maxInFlight int) error {
    sem := make(chan struct{}, maxInFlight)
    g, ctx := errgroup.WithContext(ctx)
    for _, u := range urls {
        u := u
        g.Go(func() error {
            select {
            case sem <- struct{}{}:
                defer func() { <-sem }()      // RELEASE on every path
            case <-ctx.Done():
                return ctx.Err()
            }
            _, err := fetch(ctx, u)
            return err
        })
    }
    return g.Wait()
}

// 5. SHARED STATE UNDER A MUTEX: the highest defect rate, because
//    the lock must cover the INVARIANT, not a statement.
type Counter struct {
    mu sync.Mutex
    n  int
}

func (c *Counter) Inc() { c.mu.Lock(); c.n++; c.mu.Unlock() }
func (c *Counter) Get() int { c.mu.Lock(); defer c.mu.Unlock(); return c.n }

// KEEP THE CRITICAL SECTION TO THE INVARIANT: copy under the lock,
// work outside it, write back. This is the shape to copy.
func (c *Cache) GetAndRefresh(key string) (*Entry, error) {
    c.mu.Lock()
    e, ok := c.m[key]
    c.mu.Unlock()                  // released BEFORE the slow work

    if !ok {
        e, err = c.load(key)      // no lock held: not a convoy
        if err != nil { return nil, err }
        c.mu.Lock()
        c.m[key] = e
        c.mu.Unlock()
    }
    return e, nil
}   /* Holding the lock across c.load would serialise every reader
     behind the slowest network call, and a convoy is how one slow
     dependency becomes a whole service being slow.              */
/* THE THREE FAILURES, each a specific mechanism.

   1. A SLICE APPENDED TO FROM TWO GOROUTINES. The append LOOKS
      atomic and is not: it writes the element and then the length,
      and two goroutines doing that interleave into an index one
      past the end of the allocation. */

// WRONG: this races even though each line looks independent.
func appendConcurrently(jobs []Job, wg *sync.WaitGroup) {
    var out []Result
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(i int) {
            defer wg.Done()
            out = append(out, do(jobs[i]))   // RACE on len(out)
        }(i)
    }
    wg.Wait()
}

// RIGHT: one owner, many senders. The channel IS the mutex for
// this shape, and it is better than one because it does not need a
// critical section around anything.
func appendSafely(jobs []Job) []Result {

    var wg sync.WaitGroup
    for i := range jobs {
        wg.Add(1)
        go func(j Job) { defer wg.Done(); out <- do(j) }(jobs[i])
    }
    wg.Wait()
    close(out)

    var all []Result
    for r := range out { all = append(all, r) }   // ONE appender
    return all
}

// 2. A GLOBAL var READ FROM A HANDLER AND WRITTEN FROM A
//    GOROUTINE. The race detector finds it in one run. Without the
//    detector it is a latent bug that produces a value that is
//    half-written from one side and whole from the other - which on
//    a 64-bit platform cannot happen for a single word, which is
//    why it works in testing, and DOES happen for a struct or a
//    slice header, which is where the corruption is. */

// 3. COPYING A STRUCT CONTAINING A MUTEX. go vet's copylocks check
//    reports this, and it is real: the copy has its own lock word,
//    so two holders of "the same" mutex do not exclude each other.

type BadConfig struct {
    mu      sync.RWMutex
    Timeout time.Duration
}

func (c BadConfig) WithTimeout(d time.Duration) BadConfig {
    c.Timeout = d                 // COPIES THE MUTEX: vet reports it
    return c                      // and two copies do not exclude
}

// RIGHT: the pointer receiver, stated once.
func (c *BadConfig) WithTimeout(d time.Duration) *BadConfig {
    c.Timeout = d
    return c
}

/* THE TWO DISCIPLINES.

   RUN EVERY TEST WITH -race AND EVERY SOAK TEST WITHOUT, because the
   detector finds the race and the soak finds the leak - and they
   find different things. The race detector adds instrumentation
   and changes timing, so it can find a race that never occurs in
   production; and it will not find a goroutine that is blocked
   forever, which only a soak with a goroutine dump will.

   MAKE OWNERSHIP EXPLICIT IN THE TYPE: a struct with a mutex is a
   struct that is not copyable, and saying so costs one comment and
   removes an entire class of defect at review time. */

// The goroutine dump is the other half, and it is the tool for the
// failure the race detector cannot see.
func DumpOnTimeout(limit time.Duration) {
    go func() {
        <-time.After(limit)
        // SIGQUIT on Unix writes every goroutine's stack to stderr:
        // the ONE diagnostic that explains "it just stopped working"
        p, _ := os.FindProcess(os.Getpid())
        _ = p.Signal(syscall.SIGQUIT)
    }()
}   /* A goroutine blocked on a channel appears in this dump with
     the line it is blocked on, and a goroutine blocked on a mutex
     appears holding it. Nine times out of ten the answer to "why is
     this program hanging" is in that dump and nowhere else. */

5.2 Atomics, mutexes, and the rule for choosing

Go's sync/atomic covers a small and specific set of cases, and the rule for choosing between it and a mutex is short enough to state in one sentence — but almost every article about it states the opposite order.

The rule

An atomic protects a single value, and the operations are a load, a store, an add, a compare-and-swap, and a pointer-safe variant of each. A mutex protects an invariant over several values, and it is correct for every case. The atomic operations are sequentially consistent in Go, so there is no memory-ordering argument to have — every atomic operation has a single total order across all goroutines. Then the four rules that follow, and each is a requirement. Use an atomic for a counter, a flag, or a pointer publication, because those are the three cases where a mutex is more than the invariant needs. Use a mutex the moment the invariant involves two fields, because two atomics do not make a pair of reads and writes atomic as a group. Prefer atomic.Pointer[T] and atomic.Value over unsafe.Pointer arithmetic, because the typed versions are correct and readable and the unsafe version is neither. And Never do a read-modify-write as separate atomic operations, because two goroutines doing that lose one update. Then the three things that go wrong, and each is a mechanism. A counter built from a load and a store, which loses updates and is invisible in a single-threaded test. An atomic used where the invariant involves two fields, which gives the appearance of safety and none of it. And A sync.Mutex copied by value, which is a race on the lock and which go vet reports. Then the two practices, and both are disciplines. Reach for a mutex first and drop to an atomic only when you can name the single value it protects, because a mutex is correct in every case and an atomic is correct for a short list. And Keep atomics out of the middle of a data structure, because a lock-free tree or map in Go is a research project and not a Tuesday.

/* THE RULE, in one sentence: use a MUTEX by default, and drop to
   an atomic only when the invariant is about exactly ONE value.
   Almost every article states the opposite order. */

import "sync/atomic"

// 1. A COUNTER. Correct with Add; WRONG with load-then-store.
var hits   atomic.Int64
var misses atomic.Int64

func correct() {
    hits.Add(1)                  // ONE atomic operation: correct
}

func wrong() {
    n := hits.Load()             // two operations, and a LOST
    hits.Store(n + 1)            // UPDATE between them
}   /* The mechanism: another goroutine's Add lands between the Load
     and the Store, and the Store overwrites it. Single-threaded
     this is perfectly correct, which is why the test passes.     */

// 2. A FLAG, and the publication it enables. Sequential consistency
//    means there is no ordering argument to make.
type mailbox struct {
    ready   atomic.Bool
    payload atomic.Pointer[Message]
}

func publish(m *mailbox, msg *Message) {
    m.payload.Store(msg)         // 1. write the data
    m.ready.Store(true)          // 2. then the flag: ordered
}

func consume(m *mailbox) *Message {
    if !m.ready.Load() { return nil }
    return m.payload.Load()       // SEES the store above
}

/* SEQUENTIAL CONSISTENCY IS THE WHOLE REASON THIS IS SHORT. Every
   atomic operation in Go has a single total order across every
   goroutine, so store-then-load cannot observe the flag without the
   payload. C++ and Rust require an explicit memory ordering and
   have a taxonomy of orderings to get wrong; Go does not, and the
   cost is that every atomic operation pays a full memory fence. */

// 3. A POINTER-SAFE CAS, for the rare case you need it.
type config struct { retries int; timeout time.Duration }

func update(cur atomic.Pointer[config], fn func(*config) *config) {
    for {
        old := cur.Load()
        next := fn(old)
        if cur.CompareAndSwap(old, next) { return }   // succeeded
        // else: someone else won the race. old now holds THEIR
        // value, so RETRY with it - do not reload from scratch,
        // which is a livelock under contention
    }
}

/* THE THREE FAILURES.

   1. A COUNTER BUILT FROM LOAD AND STORE: loses updates, invisibly
      in a single-threaded test. The correct form is one operation.

   2. AN ATOMIC WHERE THE INVARIANT INVOLVES TWO FIELDS. Two
      atomics do not make a PAIR of reads and writes atomic as a
      group; they make each field atomic, which is a different and
      weaker property. This is the single most important thing to
      understand about atomics and the reason the rule says mutex
      by default. */

type wrongPair struct {
    inFlight atomic.Int64
    stopped  atomic.Bool
}

// Two goroutines can interleave so that stopped is observed true
// while inFlight is still non-zero, and the shutdown path then
// assumes there is no work in progress. THIS IS A RACE IN THE
// LOGIC, not in the memory model - and no detector finds it,
// because each individual access is atomic and correctly ordered.
type rightPair struct {
    mu       sync.Mutex
    inFlight int
    stopped  bool
}

func (p *rightPair) Begin() bool {
    p.mu.Lock()
    defer p.mu.Unlock()
    if p.stopped { return false }
    p.inFlight++
    return true
}

func (p *rightPair) End() {
    p.mu.Lock()
    defer p.mu.Unlock()
    p.inFlight--
}

// 3. A MUTEX COPIED BY VALUE: a race on the lock word itself. Two
//    holders of the copy do not exclude each other. go vet reports
//    it; the race detector may not, because the copies are in
//    different cache lines and never actually collide in a test. */
/* THE TWO DISCIPLINES, and the shapes they produce.

   DISCIPLINE 1: REACH FOR A MUTEX FIRST, AND DROP TO AN ATOMIC
   ONLY WHEN YOU CAN NAME THE SINGLE VALUE IT PROTECTS. A mutex is
   correct in every case; an atomic is correct for a short list
   (counter, flag, single-word statistics, pointer publication). */

// The shape: a mutex where the invariant spans fields, an atomic
// where it does not. Two of each, in one type, with a comment
// saying which is which.
type Pool struct {
    mu      sync.Mutex      // protects the SLICE - several fields
    entries []*entry
    size    int

    rejected atomic.Int64   // a COUNTER: one value, no invariant
    closed   atomic.Bool    // a FLAG: one value, set once
}

func NewPool(size int) *Pool { return &Pool{entries: make([]*entry, 0, size), size: size} }

func (p *Pool) Get() (*entry, bool) {
    p.mu.Lock()
    defer p.mu.Unlock()
    if p.closed.Load() { return nil, false }   // lock-free read: correct,
    n := len(p.entries)                        // because closed is a
    if n == 0 {                                 // single value with its
        p.rejected.Add(1)                       // own total order
        return nil, false
    }
    e := p.entries[n-1]
    p.entries = p.entries[:n-1]
    return e, true
}

func (p *Pool) Put(e *entry) {
    p.mu.Lock()
    defer p.mu.Unlock()
    if len(p.entries) < p.size {
        p.entries = append(p.entries, e)
        return
    }
    p.rejected.Add(1)
}

func (p *Pool) Close() {
    p.closed.Store(true)     // no lock needed: ONE value
    p.mu.Lock()              // now take the lock to drain, so the
    defer p.mu.Unlock()      // flag and the slice are consistent
    p.entries = nil
}

/* DISCIPLINE 2: KEEP ATOMICS OUT OF THE MIDDLE OF A DATA
   STRUCTURE. A lock-free map or tree in Go is a research project,
   not a Tuesday, for three reasons that are not about Go. */

// (a) The garbage collector has to see every pointer, so a
//     lock-free structure that hides pointers behind unsafe.Pointer
//     and does its own write barriers will interact with the
//     collector in ways the runtime cannot verify. Every real
//     lock-free structure in Go is built on atomic.Pointer, which
//     means the collector sees the head and the structure is only
//     lock-free for the CAS, not for the traversal.
// (b) There is no hazard pointer or epoch scheme in the standard
//     library, so reclamation of a node removed from a lock-free
//     list is the user's problem and getting it wrong is a
//     use-after-free.
// (c) ABA: a node removed and re-added looks unchanged to a
//     compare-and-swap. It requires a version counter or a tagged
//     pointer to fix, and a tagged pointer costs the word you were
//     trying to save.

/* THE PRACTICAL ALTERNATIVE, which is correct and fast enough:
   shard by key and put a mutex in each shard. */
type shardedMap struct {
    shards [256]struct {
        mu sync.RWMutex
        m  map[string]int
    }
}

func (s *shardedMap) shard(k string) int {
    // FNV-1a, so the choice of shard is deterministic rather than
    // randomised - otherwise two lookups of the same key could hit
    // different shards.
    h := uint32(2166136261)
    for i := 0; i < len(k); i++ {
        h ^= uint32(k[i])
        h *= 16777619
    }
    return int(h) % len(s.shards)
}

func (s *shardedMap) Get(k string) (int, bool) {
    sh := &s.shards[s.shard(k)]
    sh.mu.RLock()
    defer sh.mu.RUnlock()
    v, ok := sh.m[k]
    return v, ok
}

func (s *shardedMap) Set(k string, v int) {
    sh := &s.shards[s.shard(k)]
    sh.mu.Lock()
    defer sh.mu.Unlock()
    if sh.m == nil { sh.m = make(map[string]int) }
    sh.m[k] = v
}   /* This scales to a great deal of traffic, it is obviously
     correct, and every line of it can be explained in one sentence.
     The rule is not "do not use lock-free structures"; it is that
     a sharded map costs twenty lines and a lock-free map costs a
     correctness argument about memory reclamation.               */

6.1 Slices: the header, the sharing, and the three ways to surprise yourself

A slice is a three-word header pointing at an array, and every surprising thing about slices follows from that: copying a slice copies the header and shares the data, appending may or may not copy, and a slice returned from a function can be modified by the caller.

The header

A slice is a pointer, a length and a capacity, and the slice itself is a value you can copy cheaply. Appending writes into the spare capacity when there is any and allocates when there is not, so whether an append copies depends on the capacity at the moment of the call. Two slices from one make share a backing array, so a write through one is visible through the other. A sub-slice's capacity extends to the end of the original, which is the mechanism behind the most common Go bug there is. Then the four rules that follow, and each is a requirement. Use the three-index slice to bound the capacity when you hand a sub-slice out, — s[a:b:b] — because it makes an append by the receiver allocate rather than overwrite your data. Never keep a pointer into a slice across an append, because the append may have moved the data. Prefer append(s, x...) to a manual copy loop, because it is correct for a nil destination and it is one line. And Remember that a zero-length slice with capacity is not the same as nil for the purposes of == nil, so test with len when that is what you mean. Then the three things that go wrong, and each is a mechanism. Appending to a sub-slice of another slice, which overwrites the elements after it. A stale pointer after a reallocation, which reads the old array. And Concurrent appends to one slice, which is a race on the length. Then the two practices, and both are disciplines. Pass a slice as a read-only value, — the caller gets a copy of the header and cannot change your length or capacity — and take a pointer to a slice only when you mean to let the caller append. And Use copy and the append form rather than index arithmetic, because both handle the overlapping case that a hand-written loop usually does not.

/* A SLICE IS THREE WORDS: a pointer, a length and a capacity. The
   slice is a VALUE you copy cheaply; the ARRAY it points at is
   shared with every other slice made from it. */

func header() {
    s := make([]int, 2, 10)       // len 2, cap 10
    t := s                        // t's HEADER is a copy
    t[0] = 99                     // visible through s: SAME array
    fmt.Println(s[0])             // 99
    t = append(t, 1, 2)           // fits in cap 10: NO allocation
    fmt.Println(s[2])             // 1: s did not change length,
                                   // but the DATA beyond s's length
                                   // is now written and visible
}

/* THE THREE-ARROW RULE: s[low:high:max]. The third index caps the
   CAPACITY, and it is the only way to hand out a sub-slice that the
   receiver cannot overwrite through. */

func threeIndex() {
    backing := make([]byte, 16)
    fill(backing)

    a := backing[0:8]             // len 8, cap 16 - DANGEROUS
    a = append(a, 'X')            // writes at index 8: OVERWRITES
                                   // backing[8], which b still has
    b := backing[8:16]            // len 8, cap 8
    // b[0] is now 'X' - a corruption caused by an append in
    // a completely different function

    c := backing[0:8:8]           // len 8, cap 8 - SAFE
    c = append(c, 'X')            // cap is full: ALLOCATES instead
    fmt.Println(backing[8])       // untouched: the receiver owns
                                   // its own storage now
}   /* This is the single most common Go bug there is, and the fix
     is one character. Every sub-slice you hand to another package
     or another goroutine should use the three-index form.        */

/* APPENDING MAY OR MAY NOT COPY. It depends on the CAPACITY AT THE
   MOMENT OF THE CALL, not on anything visible at the call site. */
func appendCopies() {
    s := make([]int, 3, 3)        // len == cap
    before := &s[0]
    s = append(s, 4)              // NO spare capacity: ALLOCATES
    after := &s[0]
    // before != after: the old array is still alive, still
    // referenced by before, and still holds {0,1,2}
}   /* This is why a pointer or slice into an array must never
     survive an append. It is also why the escape of before keeps
     the whole old array alive - a four-element slice retains a
     three-element array.                                        */

/* NIL, EMPTY, AND len()==0 ARE THREE DIFFERENT ANSWERS. */
func nils() {
    var a []int                  // nil: len 0, cap 0, a == nil TRUE
    b := []int{}                 // non-nil, len 0, cap 0, == nil FALSE
    c := make([]int, 0, 10)      // non-nil, len 0, cap 10

    fmt.Println(a == nil, b == nil, c == nil)   // true false false
    for _, v := range a { _ = v }               // both range fine
    a = append(a, 1)                             // both append fine
    json.Marshal(a)      // "null"     <- nil marshals as null
    json.Marshal(b)      // "[]"       <- empty marshals as []
}   /* So: test with len(s) == 0 when you mean "is it empty", and
     with s == nil only when you specifically mean "was this never
     initialised". The two mean different things and JSON makes the
     difference visible.                                        */

// THE THREE FAILURES.
// 1. APPENDING TO A SUB-SLICE OF ANOTHER SLICE: overwrites the
//    elements after it. Fix: the three-index form.
// 2. A STALE POINTER AFTER A REALLOCATION: reads the old array.
//    Fix: never keep a pointer into a slice across an append; keep
//    the INDEX and re-slice.
// 3. CONCURRENT APPENDS TO ONE SLICE: a race on the length field
//    even when each element write is independent. Fix: one owner,
//    or a channel.                                              */
/* THE TWO DISCIPLINES.

   DISCIPLINE 1: PASS A SLICE AS A READ-ONLY VALUE, and take a
   pointer to a slice only when you mean to let the caller append.
   The signature is the whole communication. */

// Caller cannot change my length or capacity: I pass a value.
func Sum(values []int) int {
    for i := range values { values[i] = 0 }   // CAN mutate elements
    return 0                                   // CANNOT resize mine
}

// Caller may append, and the append is visible to me: I pass a
// pointer. Note this is the ONLY reason to take *[]T, and it is
// rarely what you want.
func AppendMore(dst *[]int, more ...int) {
    *dst = append(*dst, more...)
}

// The shape to use instead: return the slice.
func WithMore(values []int, more ...int) []int {
    return append(values, more...)
}

// And the difference that matters at the call site:
func caller() {
    a := []int{1, 2, 3}
    AppendMore(&a, 4)             // a is now 1,2,3,4
    b := WithMore(a, 5)            // a is STILL 1,2,3,4 - because the
    _ = b                         // append may have reused capacity
}   /* WithMore can silently write into a's backing array if there
     is spare capacity, which is fine for a caller that does not
     expect a to change but NOT fine for a caller that does. The
     three-index form at the call site removes the doubt:
         b := append(a[:len(a):len(a)], 5)                        */

/* DISCIPLINE 2: USE copy AND THE APPEND FORM RATHER THAN INDEX
   ARITHMETIC, because both handle the overlap that a hand-written
   loop usually does not. */

// The hand-written loop that is wrong half the time:
func wrongCopy(dst, src []byte) {
    for i := range src { dst[i] = src[i] }   // WRONG if they overlap
}

// The two correct forms. copy handles overlap the way memmove does,
// because it is specified as if the source were read first.
func rightCopy(dst, src []byte) int {
    return copy(dst, src)       // min(len(dst), len(src)) bytes
}

func rightAppend(dst, src []byte) []byte {
    return append(dst, src...)  // nil dst works; no size arithmetic
}

// Filter, the idiomatic form. A hand-written filter with an
// in-place compaction is correct and easy to get subtly wrong when
// the predicate has a side effect, because the elements after the
// write index are the ones the predicate will see next.
func keep(s []int, pred func(int) bool) []int {
    out := s[:0]                 // REUSE the backing array: zero
    for _, v := range s {        // allocations. Safe ONLY because we
        if pred(v) {             // never grow past len(s).
            out = append(out, v)
        }
    }
    return out
}

// Note out := s[:0] reuses the caller's memory. That is a
// deliberate, documented, surprising choice - and the reason the
// function is named for what it does rather than returning a new
// slice. A function that silently overwrites its input's array is
// fine as an internal helper and unacceptable as an exported one. */

6.2 Maps, strings, time, and the four traps in each

The standard library's map, string and time packages are unremarkable in interface and each carries one trap that a program will hit in production and not in a test.

Four traps, one per type

A map's iteration order is deliberately unspecified and varies between runs of the same program, which means anything that depends on it is a bug that reproduces on somebody else's machine. A map read of a missing key returns the zero value and a comma-ok, and a write to a nil map panics — the same asymmetry as always. A string is an immutable byte sequence and a for over one yields runes, so indexing gives a byte and iterating gives a character, and the two disagree for any non-ASCII text. And time.Time carries a monotonic reading as well as a wall clock, which is why subtracting two of them is correct even across a clock adjustment and why formatting one loses it. Then the four rules that follow, and each is a requirement. Never depend on map iteration order; sort the keys if you need determinism. Check for a missing key with the comma-ok form rather than comparing to a zero, because zero is a legitimate stored value. Iterate with range rather than by index when the string may be non-ASCII, because the byte length is not the character count. And Measure durations with time.Since on a value from time.Now, never by formatting and re-parsing. Then the three things that go wrong, and each is a mechanism. Relying on map order for a generated document, which produces a different file every run and an unreproducible diff. Slicing a string by byte index to "take the first 10 characters", which splits a multi-byte rune and produces a replacement character in the output. And Parsing a timestamp to measure elapsed time, which is both slower and wrong across a clock adjustment. Then the two practices, and both are disciplines. Sort keys when you need output, and use maps.Keys plus slices.Sorted in current Go, which is two lines. And Keep the zero-value of a struct usable, which for the map case means initialising the map lazily rather than in a constructor nobody calls on the error path.

/* MAP: four behaviours worth stating. */
func maps() {
    m := map[string]int{}

    // 1. ORDER IS UNSPECIFIED and VARIES BETWEEN RUNS. This is
    //    deliberate: it stops code depending on it.
    for k := range m { _ = k }              // not insertion order

    // 2. A MISSING KEY RETURNS THE ZERO and a false comma-ok.
    v, ok := m["absent"]
    fmt.Println(v, ok)                      // 0 false

    // 3. WRITING TO A NIL MAP PANICS; READING DOES NOT.
    var n map[string]int
    _ = n["absent"]                         // fine
    n["x"] = 1                              // PANIC

    // 4. DELETING A MISSING KEY IS FINE and is not an error.
    delete(m, "absent")                      // no-op
}

// The deterministic-order fix, and in current Go it is two lines:
//    keys := slices.Sorted(maps.Keys(m))
import ("maps"; "slices")

func orderedOutput(m map[string]int) []string {
    keys := slices.Sorted(maps.Keys(m))     // Go 1.23+
    out := make([]string, 0, len(keys))
    for _, k := range keys { out = append(out, fmt.Sprintf("%s=%d", k, m[k])) }
    return out
}   /* Without this, a map-driven generator produces a DIFFERENT FILE
     on every run, and the diff is unreviewable. This is the
     mechanism behind "the golden test passed on CI and failed
     locally" more often than anything else.                      */

/* STRING: a byte sequence. Indexing gives a BYTE; range gives a
   RUNE. For ASCII they agree, and for anything else they do not. */
func strings() {
    s := "héllo"                  // 5 runes, 6 BYTES (é is 2)
    fmt.Println(len(s))           // 6 - the BYTE length

    for i, r := range s {         // i is a BYTE offset, r a rune
        fmt.Printf("%d:%c ", i, r)
    }                             // 0:h 1:é 3:l 4:l 5:o - note i=2
                                   // never appears: it is inside é

    fmt.Println(s[0:1])           // "h"
    fmt.Println(s[1:2])           // the FIRST BYTE of é: INVALID
    fmt.Println(s[1:3])           // "é" - correct, but you had to
                                   // know the byte length

/* TIME: a wall clock AND a monotonic reading, and the monotonic
   reading is why Since is correct. */
func times() {
    start := time.Now()
    work()

/* THE THREE FAILURES, each with the mechanism stated.

   1. RELYING ON MAP ORDER FOR GENERATED OUTPUT: a different file on

      randomly. The mechanism is that the runtime deliberately
      randomises the start bucket.

   3. PARSING A TIMESTAMP TO MEASURE ELAPSED TIME: two wall-clock

      negative or wildly wrong duration, and only on a machine with
      NTP or a user changing the clock.

/* THE TWO DISCIPLINES.

   DISCIPLINE 1: SORT KEYS WHEN YOU NEED OUTPUT, and in current Go
   that is two lines rather than a hand-written sort. Do it in the
   function that produces the output, not at every call site. */

func Report(m map[string]int) string {
    keys := slices.Sorted(maps.Keys(m))
    var b strings.Builder
    for i, k := range keys {
        if i > 0 { b.WriteByte('

        fmt.Fprintf(&b, "%-16s %8d", k, m[k])
    }

// And the same discipline for anything derived from a map -
// including a test's want/got comparison, which is the most common
// place it bites.
func assertSameSet(t *testing.T, got, want []string) {
    t.Helper()
    slices.Sort(got)
    slices.Sort(want)
    if !slices.Equal(got, want) {

want %v", got, want)   // both sorted: a
    }                                            // readable diff

/* DISCIPLINE 2: KEEP THE ZERO VALUE OF A STRUCT USABLE - which for
   the map case means initialising lazily rather than in a
   constructor nobody calls on the error path. */

type Registry struct {
    handlers map[string]Handler   // nil until first use
    order    []string
}

// A POINTER receiver throughout, because Register must be able to
// initialise the map. A value receiver could not: it would mutate
// its own copy and the map would be re-allocated per call.
func (r *Registry) Register(name string, h Handler) error {
    if _, dup := r.handlers[name]; dup {
        return fmt.Errorf("duplicate: %s", name)
    }
    if r.handlers == nil {
        r.handlers = make(map[string]Handler)   // lazy: the zero
    }                                           // value is usable
    r.handlers[name] = h
    r.order = append(r.order, name)            // deterministic
    return nil
}

func (r Registry) Get(name string) (Handler, bool) {
    h, ok := r.handlers[name]     // safe on the zero value: reading
    return h, ok                  // a nil map yields the zero
}

func (r Registry) Names() []string {
    // Copy the slice: returning r.order lets a caller append into
    // the registry's own spare capacity and overwrite its elements.
    return append([]string(nil), r.order...)
}   /* The four traps in one type: map order (order, the slice),
     nil-map write (Register), aliasing (Names), and the zero value
     (both are usable). Every one of them is a defect somebody
     will write in the first hour with a map in Go.              */

7.1 net/http: the server, the client, and the three defaults

Go's HTTP support is the reason the language became popular for infrastructure, and it works because the standard library's server is a complete implementation rather than a set of building blocks — which also means its defaults are decisions you inherited.

The server

net/http is a complete server and a complete client, and using it needs no framework. Every request is served on its own goroutine, which is why the concurrency story comes for free and why the connection limits are your problem. The default server has no timeouts, which is the single most consequential default in the package. Then the four rules that follow, and each is a requirement. Always construct an explicit http.Server with all four timeouts set — read, write, idle, and header — because the zero value means "no timeout" and a slow client then holds a goroutine indefinitely. Wrap the mux in middleware rather than checking inside handlers, because a check inside a handler is a line somebody forgets. Always read the request body with a limit, because a client can send as much as it likes. And Serve over TLS with ListenAndServeTLS and let it manage the certificate, because a hand-rolled TLS configuration is a configuration you will get wrong. Then the three things that go wrong, and each is a mechanism. Using http.ListenAndServe with the package-level default server, which cannot be configured and has no timeouts. Reading r.Body with io.ReadAll and no limit, which is a denial of service with one line of client code. And Writing a response header after writing the status, which is a silent no-op and the mechanism behind "my header does not appear". Then the two practices, and both are disciplines. Pass the context from the request to everything downstream, because it carries the deadline, the cancellation and the request's own values — and it is the only way a database query stops when the client disconnects. And Write the handler as if every field of the request is hostile, because it is: the method, the path, the headers, the query, the body and the content type all come from outside.

/* net/http IS A COMPLETE SERVER AND A COMPLETE CLIENT. The reason
   the language became popular for infrastructure is that this is
   one import and one handler, not a framework's worth of pieces. */

// EVERY REQUEST IS SERVED ON ITS OWN GOROUTINE, which is why
// concurrency comes free and why CONNECTION LIMITS ARE YOUR PROBLEM.

func server() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /users/{id}", getUser)   // Go 1.22 patterns
    mux.HandleFunc("POST /users", createUser)

    // RULE 1: ALWAYS CONSTRUCT AN EXPLICIT Server WITH ALL FOUR
    // TIMEOUTS. The zero value means NO TIMEOUT, and a slow client
    // then holds a goroutine and its buffers indefinitely.
    srv := &http.Server{
        Addr:              ":8080",
        Handler:           logRequests(mux),
        ReadHeaderTimeout: 5 * time.Second,   // the slowloris one
        ReadTimeout:       15 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       60 * time.Second,   // keep-alive reuse
        MaxHeaderBytes:    1 << 20,
    }

    // Graceful shutdown: stop accepting, let in-flight finish.
    go func() {
        sig := make(chan os.Signal, 1)
        notify(sig, os.Interrupt, syscall.SIGTERM)
        &lt;-sig
        ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
        defer cancel()
        if err := srv.Shutdown(ctx); err != nil {
            log.Printf("shutdown: %v", err)
        }
    }()

    // TLS managed by the standard library: LoadX509KeyPair reads the
    // files, and the config below is what most services need.
    cert, err := tls.LoadX509KeyPair("cert.pem", "key.pem")
    if err != nil { log.Fatal(err) }
    srv.TLSConfig = &tls.Config{
        Certificates: []tls.Certificate{cert},
        MinVersion:   tls.VersionTLS12,
        ClientAuth:   tls.NoClientCert,   // or RequireAndVerify
    }
    log.Fatal(srv.ListenAndServeTLS("", ""))
}

/* RULE 3: ALWAYS READ THE BODY WITH A LIMIT. io.ReadAll with no
   limit is a denial of service with one line of client code. */
const MaxBody = 1 << 20   // 1 MB

func readBody(w http.ResponseWriter, r *http.Request) ([]byte, error) {
    defer r.Body.Close()
    // http.MaxBytesReader tells the SERVER to stop reading and to
    // tell the client. io.LimitReader alone silently truncates,
    // which is worse: you get a valid-looking partial body.
    r.Body = http.MaxBytesReader(w, r.Body, MaxBody)
    b, err := io.ReadAll(r.Body)
    if err != nil {
        var mbe *http.MaxBytesError
        if errors.As(err, &mbe) {
            return nil, fmt.Errorf("body exceeds %d bytes", MaxBody)
        }
        return nil, err
    }
    return b, nil
}

   1. http.ListenAndServe WITH THE PACKAGE-LEVEL DEFAULT SERVER:

   2. io.ReadAll WITH NO LIMIT: one line of client code and every
      goroutine in the process is consumed.
   3. WRITING A HEADER AFTER WRITING THE STATUS: a silent no-op.
      The mechanism is that the header is flushed with the first

/* THE TWO DISCIPLINES.

   because it carries the deadline, the cancellation and the

func getUser(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()          // CANCELLED when the client leaves

    id := r.PathValue("id")

        // a typed failure, not a string comparison
        httpError(w, http.StatusBadRequest, "id must be an integer")
        return
    }

    // rather than occupying a connection until WriteTimeout.
    var u User
    err := db.QueryRowContext(ctx, "SELECT ... WHERE id=$1", id).Scan(&u)
    switch {
    case errors.Is(err, sql.ErrNoRows):
        httpError(w, http.StatusNotFound, "no such user")
        return
    case errors.Is(err, context.Canceled):
        return                   // nobody is listening any more
    case err != nil:
        log.ErrorContext(ctx, "get user", "id", id, "err", err)
        httpError(w, http.StatusInternalServerError, "internal")
        return
    }

    w.Header().Set("Cache-Control", "private, max-age=60")
    w.WriteHeader(http.StatusOK)
    if err := json.NewEncoder(w).Encode(u); err != nil {
        // the status is already sent, so all you can do is log
        log.ErrorContext(ctx, "encode", "err", err)
    }
}

/* DISCIPLINE 2: WRITE THE HANDLER AS IF EVERY FIELD OF THE REQUEST
   IS HOSTILE, because every one of them is. Here is the whole
   checklist, and each line is a bug somebody writes without it. */

func createUser(w http.ResponseWriter, r *http.Request) {
    // the METHOD is matched by the mux pattern, so a handler
    // registered on "POST /users" cannot be reached by GET
    if ct := r.Header.Get("Content-Type"); ct != "application/json" {
        httpError(w, http.StatusUnsupportedMediaType, "want application/json")
        return
    }
    body, err := readBody(w, r)     // the LIMIT, above
    if err != nil { httpError(w, 400, err.Error()); return }

    var in CreateUserRequest
    dec := json.NewDecoder(bytes.NewReader(body))
    dec.DisallowUnknownFields()      // a typo'd field is an ERROR
    if err := dec.Decode(&in); err != nil {
        httpError(w, http.StatusBadRequest, "malformed JSON")
        return
    }
    if dec.More() {                  // trailing garbage is an ERROR
        httpError(w, http.StatusBadRequest, "one object expected")
        return
    }

    // VALIDATE into a typed result, so the rest of the function
    // works with a value known to be in range.
    v := in.Validate()
    if !v.OK { httpError(w, 422, v.Message); return }

    id, err := insert(r.Context(), v.User)
    if err != nil { log.Error("insert", "err", err); httpError(w, 500, "internal"); return }

    w.Header().Set("Location", "/users/"+strconv.FormatInt(id, 10))
    w.WriteHeader(http.StatusCreated)      // BEFORE the body
    _ = json.NewEncoder(w).Encode(v.User)
}

// The two ordering rules that produce silent failures:
//   1. Every Header().Set BEFORE WriteHeader. After it, they are
//      body bytes.
//   2. WriteHeader BEFORE the body, and only once. A second call
//      logs "superfluous response.WriteHeader call" and is ignored.

// A middleware chain, which is where cross-cutting behaviour goes
// so that no handler can forget it.
func recoverMW(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                slog.Error("panic", "path", r.URL.Path, "panic", rec,
                    "stack", string(debug.Stack()))
                httpError(w, 500, "internal")
            }
        }()
        next.ServeHTTP(w, r)
    })
}

func chain(h http.Handler, mw ...func(http.Handler) http.Handler) http.Handler {
    for i := len(mw) - 1; i >= 0; i-- { h = mw[i](h) }
    return h
}   /* Middleware is not an idiom to be avoided. It is the only
     place a cross-cutting concern can live that EVERY handler gets
     without every handler remembering it.                         */

7.2 Testing: table tests, fakes, and the race detector

Go's testing package is deliberately small — a test is a function whose name says what it is — and the discipline is entirely in how you structure the cases, what you fake, and what you run.

The three tools

A test is a function taking a *testing.T and returning nothing, and a t.Fatal stops it while t.Error continues. A table is the natural shape for cases, because Go has no way to parameterise a test without a table or a subtest. An interface is the natural seam for a fake, because you defined small interfaces on the consumer's side. Then the four rules that follow, and each is a requirement. Name a subtest for the case, so a failure identifies itself without a debugger. Fake at an interface you own, not at a third-party library, because a fake of somebody else's interface breaks when they add a method. Always run with -race, and run the count more than once because a race is probabilistic. And Prefer a fake over a mock for anything with state, because a fake implements behaviour and a mock asserts interactions and the second is a test that breaks on refactoring without finding a defect. Then the three things that go wrong, and each is a mechanism. A test that depends on another's state, which passes alone and fails in a suite and is the reason test order becomes load-bearing. Asserting on a map's output without sorting, which fails randomly. And A mock asserting the exact sequence of calls, which fails on a refactor that changed nothing observable. Then the two practices, and both are disciplines. Make each test's setup explicit and local, so a reader can see what state the assertion depends on without reading another test. And Write the test as the specification first, because a test written after the code tends to assert what the code does rather than what it should do.

/* A TEST IS A FUNCTION taking *testing.T and returning nothing.
   t.Fatal STOPS the test; t.Error CONTINUES and records. Use
   Error for independent assertions and Fatal for the precondition
   everything after depends on. */

// THE TABLE IS THE NATURAL SHAPE, because Go cannot parameterise a
// test any other way.
func TestParse(t *testing.T) {
    tests := []struct {
        name    string
        in      string
        want    entry
        wantErr error
    }{
        {"empty",     "",        entry{},   ErrEmpty},
        {"short",     "F",       entry{},   ErrShort},
        {"file",      "Fa",      entry{"a", 0, 0}, nil},
        {"version",   "Fv2",     entry{"", 2, 0}, nil},
        {"full",      "Fa3.14",  entry{"a", 3, 14}, nil},
        // The boundaries, which are where the bug is:
        {"zero version",    "Fa0",  entry{"a", 0, 0}, nil},
        {"max version",     "Fa255", entry{"a", 255, 0}, nil},
        {"overflow version", "Fa256", entry{}, ErrRange},
        {"unicode name",    "Fé",  entry{"é", 0, 0}, nil},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {     // the subtest NAME
            got, err := Parse(tt.in)
            if !errors.Is(err, tt.wantErr) {    // Is, never ==
                t.Fatalf("Parse(%q) err = %v, want %v", tt.in, err, tt.wantErr)
            }
            if err != nil { return }             // no point comparing
            if got != tt.want {
                t.Errorf("Parse(%q) = %+v, want %+v", tt.in, got, tt.want)
            }
        })
    }
}   /* The subtest name is not decoration: it is what appears in
     go test -run and in the CI output, and it is the difference
     between "TestParse failed" and "TestParse/max_version
     failed".                                                      */

// Fuzzing: Go has it built in, and for a PARSER it is the single
// highest-value test you can write. The seed corpus runs as
// ordinary tests on every run; -fuzz explores.
func FuzzParse(f *testing.F) {
    f.Add("Fa3.14")
    f.Add("")
    f.Add("Fa256")

    f.Fuzz(func(t *testing.T, s string) {
        got, err := Parse(s)
        if err != nil {
            return                    // a documented rejection
        }
        // THE PROPERTY, not the expected value: whatever comes
        // back must RE-PARSE to the same thing. That is true for
        // every input the parser accepts, and it is the property
        // that actually matters.
        got2, err2 := Parse(got.String())
        if err2 != nil {
            t.Fatalf("re-parse of %q failed: %v", s, err2)
        }
        if got != got2 {
            t.Fatalf("not stable: %q -> %+v -> %+v", s, got, got2)
        }
        if got.Version > 255 {
            t.Fatalf("version out of range: %d", got.Version)
        }
    })
}

   the property is checked forever.

   $ go test -race -count=100 ./...

8.1 Modules, builds and cross-compilation

A Go build produces one static binary with the runtime linked in and nothing else required on the target — which is the deployment story, and it is a consequence of the standard library having no C dependencies in the common path.

What a build is

go build compiles and links a single static binary with no shared library requirement, because the garbage collector and the scheduler are part of the binary. Cross-compilation is a single environment variable, because the toolchain is the compiler and there is no C toolchain in the path. A module is a directory with a go.mod declaring a module path and a Go version, and the module path is an identity rather than a location. Then the four rules that follow, and each is a requirement. Set CGO_ENABLED=0 for a fully static binary, unless you genuinely need cgo, because with it on you have a dynamic dependency and a different binary per platform. Pin the Go version in go.mod and in the build image, because the compiler's behaviour changes between releases. Build with trimpath and stripped symbols for a release, which removes absolute paths and shrinks the binary, and keep the unstripped one for the symbol server. And Vendor when the dependency set is large, so the build works offline and the tree is exactly what was tested. Then the three things that go wrong, and each is a mechanism. Shipping with CGO enabled and no libc on the target, which fails at run time with a loader error rather than at build time. Committing a go.sum that does not match, which fails the build on a clean checkout and not on yours. And Vendoring into a directory the tool also scans, which puts a second copy of the standard library into your module. Then the two practices, and both are disciplines. Make the build a single command in a script, so the binary is reproducible by anyone and the flags cannot drift between a laptop and a pipeline. And Keep go.mod tidy as a separate commit, because a dependency bump mixed into a feature change cannot be reviewed and cannot be reverted.

A.1 The idioms worth memorising

A working list of the constructs that solve a recurring problem, with the condition each one requires — because an idiom applied outside its condition is the defect.

The list, with the condition attached

Then the three rules that apply to the whole list, and each is a requirement. Every idiom has a condition, and the condition is the whole content of the entry. Prefer the standard library's version, because it is what the rest of the ecosystem expects. And An idiom that hides an error is a defect, which is the one thing to check about each. Then the two practices, and each is a discipline. Learn the condition with the idiom, because a half-learned idiom is a bug. And Replace an idiom with the standard helper the day one exists, which is more often than people expect.

<p>There is no list of idioms that makes Go programs correct, because the language's hazards are not syntactic either - they are decisions about who cancels a context, who closes a channel, and how many things are allowed to run at once. What a list can do is name those decisions, so that a reader can infer them from a function's signature rather than reconstructing them from its control flow.

<p>Context is first in the list because it is the one convention that has to be followed from the first line of a program to be worth anything. A deadline or a cancellation travels down a call tree only if every function that can block accepts a context as its first parameter and consults it before the expensive part rather than after. The cost of not doing so is a goroutine that outlives its deadline, which is invisible in a test and unbounded in production; the cost of doing so is one parameter and one select statement per function, which is small enough that there is never a good reason to skip it.

<p>Returning an error rather than printing one comes next for the same reason the equivalent C++ rule exists: a function that reports its own failure has taken away the caller's ability to decide what to do about it. The reason the deferred close is worth the three lines it usually takes is that it is the only form where every early return is covered by construction. A program that closes its files, its network connections and its temporary directories in defers has removed an entire class of resource defect - and it has done so without a helper, without a code review checklist, and without the reviewer having to count the return statements.

<p>The concurrency limit is the idiom most often omitted and most often regretted. One goroutine per request is idiomatic Go and it is correct right up to the point where the downstream has a limit of its own: a thousand goroutines each opening a connection against a service that allows ten is an outage caused by a program that is individually correct. The semaphore is three lines, and it converts an unbounded resource question into a configured number that someone chose.

<p>The close discipline deserves a note of its own because it is a rule about ownership rather than about syntax. Closing a channel is the sender's statement that no more values are coming, and only the sender can know that. A receiver that closes a channel is asserting something it cannot possibly know, and the assertion fails as a panic on the next send - in another goroutine, under load, in production. The reason this is worth a rule rather than a convention is that the compiler cannot check it and the failure is not a wrong answer but a crash.

<p>What the list omits is the other kind of advice: package layout, file naming, and where a type should live. Those are matters of taste and of a project's existing structure, and a list that includes them trains the reader to skip the entries that matter. The seven above are the ones where following them removes a class of defect - and removing a class is the only test worth applying to an idiom.

/* THE LIST, WITH THE CONDITION ATTACHED. The condition is the whole
   content of each entry - an idiom applied outside its condition is
   the defect, not the idiom. */

// ERROR AT A BOUNDARY, RETURN INSIDE. Condition: the error adds no
// information. This is the single most important convention in Go.
func b() error {
    if err := check(); err != nil {
        return fmt.Errorf("b: %w", err)   // names the OPERATION
    }
    return nil                           // nil is idiomatic
}

// OPTIONS FUNCTIONS. Condition: more than three optional arguments,
// or any argument a caller will often omit. Returns a value, not a
// pointer, because a half-initialised struct is not constructible.
type Option func(*Server)
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

// COMPOSITION OVER INHERITANCE. Condition: whenever you would
// otherwise write a base class. Embed an interface or a struct.
type Service struct { *Repository; Logger *log.Logger }

// A SENTINEL ERROR. Condition: the caller must BRANCH on the error.
// NOT for a message-only failure - use fmt.Errorf for that.
var ErrNotFound = errors.New("not found")

// A CONSTRUCTOR RETURNING (T, error). Condition: validation, or
// anything that can fail. NOT for a struct with a usable zero value.
func NewClient(u string) (*Client, error) { /* ... */ }

// A FUNCTIONAL OPTION OVER A CONFIG STRUCT passed by pointer.
// Condition: the caller should not be able to see or change the
// whole struct. A config struct is better when it should.

// context.WithValue. Condition: a value that is part of the
// REQUEST, not a parameter - an option, never a required argument.
ctx = context.WithValue(ctx, RequestIDKey, id)

// errgroup. Condition: fan-out where the first error should stop
// the rest. NOT for fan-out where every item must be attempted.
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)

// slices and maps packages. Condition: anything a loop would do.
// slices.Sort, slices.Contains, slices.Compact, maps.Keys.

// THE THREE RULES FOR THE WHOLE LIST.
   // 1. EVERY IDIOM HAS A CONDITION, and the condition is the whole
   //    content of the entry.
   // 2. PREFER THE STANDARD LIBRARY'S VERSION, because it is what
   //    the rest of the ecosystem expects.
   // 3. AN IDIOM THAT HIDES AN ERROR IS A DEFECT - and that is the
   //    one thing to check about each entry above.               */

package main

import (
	"context"
	"errors"
	"fmt"
	"io"
	"os"
	"sync"
)

/* SEVEN IDIOMS, in the order they earn their place. */

/* 1. CONTEXT FIRST, AND FIRST PARAMETER. Context is how a deadline
      and a cancellation travel down a call tree, and it only works
      if every function that can block accepts one. */
func fetch(ctx context.Context, id string) (data []byte, err error) {
	/* Honour it before doing the expensive thing, not after. */
	select {
	case <-ctx.Done():
		return nil, ctx.Err()
	default:
	}
	return doWork(ctx, id)
}

/* 2. RETURN AN ERROR, NEVER PRINT ONE. A function that prints its
      own failure cannot be used by anything that wants to decide
      what to do about it. */
func load(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, fmt.Errorf("open %s: %w", path, err)
	}
	defer f.Close()          /* one line, and every return above it
	                              is covered                       */
	return io.ReadAll(f)
}

/* 3. THE ERROR IS THE LAST RETURN VALUE, and it is named so the
      deferred function can modify it. */
func readThenClose(f *os.File) (data []byte, err error) {
	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = fmt.Errorf("close: %w", cerr)
		}
		/* If err is already set, the close error is DROPPED -
		   which is a choice. The alternative is a joined error,
		   which the caller then has to know how to display.   */
	}()
	return io.ReadAll(f)
}

/* 4. A CONCURRENCY LIMIT, because unbounded goroutines against a
      downstream that has a limit is how one slow dependency
      becomes an outage. */
func fetchAll(ctx context.Context, ids []string, limit int) error {
	sem := make(chan struct{}, limit)   /* a buffered channel as a
	                                       semaphore: this is the
	                                       idiom, not sync.WaitGroup */
	var wg sync.WaitGroup

	for _, id := range ids {
		select {
		case sem <- struct{}{}:      /* acquire */
		case <-ctx.Done():
			wg.Wait()
			return ctx.Err()
		}
		wg.Add(1)
		go func(id string) {
			defer wg.Done()
			defer func() { <-sem }()     /* release: deferred, so it
			                                runs on every path    */
			if _, err := fetch(ctx, id); err != nil {
				log.Printf("fetch %s: %v", id, err)
			}
		}(id)
	}
	wg.Wait()
	return ctx.Err()
}

/* 5. NEVER PASS A NIL CHANNEL OR A CLOSED CHANNEL TO SOMEONE ELSE.
      A nil channel BLOCKS FOREVER; a closed one PANICS on send.
      Both are legal to receive from, which is why the owner is
      the only one who closes. */
func the_close_rule(chan int) {
	defer close(ch)       /* the OWNER closes, exactly once      */
	/* a closed channel yields the zero value on receive,
	   immediately and forever - so "stop when the channel is
	   closed" is written as a range or a comma-ok receive, not a
	   comparison against a sentinel                        */
	_ = chan
}

/* 6. THE WORKER POOL, because a goroutine per item is fine for a
      thousand items and a memory problem for ten million. */
func pool(ctx context.Context, jobs []string, workers int) error {
	in := make(chan string)
	var wg sync.WaitGroup

	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for job := range in {      /* range exits when the
			                              channel is CLOSED - which
			                              is why closing it is the
			                              shutdown signal        */
				if _, err := fetch(ctx, job); err != nil {
					log.Printf("%v", err)
				}
			}
		}()
	}
	for _, j := range jobs {
		select {
		case in <- j:
		case <-ctx.Done():
			close(in)
			wg.Wait()
			return ctx.Err()
		}
	}
	close(in)
	wg.Wait()
	return nil
}

/* 7. STRUCT EMBEDDING for composition, and it is not inheritance:
      the outer type has all the inner type's PROMOTED fields, but
      no implicit conversion to it and no virtual dispatch. */
type Logger struct{ prefix string }

func (l *Logger) logf(format string, args ...any) {}

type Service struct {
	*Logger            /* embedded: l.logf works, and the type is
	                       nil if not initialised - so initialise
	                       it or make it a value, not a pointer  */
	name string
}

A.2 The traps, and what each costs

Nine defects account for most Go bugs found in review, and each has a one-line prevention and a diagnostic that finds it.

The nine

Then the three things that make them hard, and each is a requirement. Most compile, which is why they survive review. Most are correct in a single-threaded test, which is why they survive testing. And Most are silent, which is why they survive to production. Then the two practices, and both are disciplines. Run go vet and -race in the pipeline, because four of the nine have a diagnostic. And Read the nil-interface section once more, because the first trap is the one that costs the most debugging time.

<p>Every trap in this list compiles, passes the vet checks, and produces a wrong answer rather than an error. That is the property they share, and it is why they survive review. A defect a test would catch is not a defect that reaches a customer; these are the ones where the test suite was written against the behaviour the author intended rather than the behaviour the code implements, so the suite reports success on a program that does something else.

<p>The typed nil is the most valuable of the seven, because it is a consequence of a design decision rather than a mistake in the code, and because the fix is a habit rather than a line. An interface value is two words: the dynamic type and the value. A nil interface has neither. Assigning a nil pointer of a concrete type produces an interface that carries that type, so the interface is not nil even though the pointer is, and a guard written as a nil comparison does not fire. The program then calls a method on a nil receiver, which may work - if the method does not dereference the receiver - and may not. The only reliable discipline is to keep a nil interface for absent and never assign a typed nil into one, which means the absence check has to happen where the concrete value is created rather than where it is used.

<p>The loop variable capture is the one that changed under the reader's feet, and the reason it belongs on a list of traps rather than in a migration note. Go 1.22 gave each iteration its own copy of the loop variable, which fixed the closure capture that a decade of advice warned about. Code written for 1.21 and earlier remains correct, because the old behaviour is the conservative one - a goroutine sees the final value rather than its own - so nothing breaks. What changes is that the workaround of copying the variable inside the loop becomes unnecessary and can now be removed, and a codebase that copies it everywhere is carrying code that a reader has to work out the reason for. Version-dependent behaviour that compiles cleanly is the hardest kind of defect to reason about, because the same source has two meanings.

<p>The error comparison and the data race are related in a way worth naming. The comparison trap produces a false answer immediately and is found by reading. The race produces a wrong answer sometimes, which is why it needs a tool: the race detector does not prove anything, it observes an execution and reports what that execution did, which means a race that never fires during a test run is not absent but untriggered. That is the argument for running the suite under the detector many times rather than once, and for having it in continuous integration at all - not because a race will show up, but because the class of defect is invisible to every other method of finding it.

<p>The remaining three - defer argument evaluation, the context that is cancelled but not observed, and the shared slice inside a copied struct - are all the same shape: the code says one thing and the program does another, and the difference is between the value at one moment and the value at another. In each case the fix is to make the moment explicit: a closure when the value at exit is wanted, a context check when a deadline is wanted, and a fresh allocation when a distinct buffer is wanted. Go is unusually good at making that moment explicit elsewhere, so the discipline is worth stating rather than assuming.

/* NINE TRAPS, WHAT EACH COSTS, AND WHAT FINDS IT.

   1. A TYPED NIL RETURNED AS AN ERROR INTERFACE. The caller's
      err != nil is TRUE on success. Cost: a failure path taken on
      every call, or a success path never taken.
      FOUND BY: the compiler, if you read the warning.

   2. A LEAKED GOROUTINE. Blocked on a channel nobody will ever
      use; the collector cannot reclaim it because a running
      goroutine's stack is a GC root. Cost: unbounded memory.
      FOUND BY: a goroutine dump (SIGQUIT) in a soak test.

   3. APPENDING TO A SUB-SLICE. Two slices over one array; the
      append writes past the first one's length and corrupts the
      second. Cost: wrong data, no error, no crash.
      FOUND BY: code review; no tool finds it.

   4. A NIL MAP WRITE. Assigning to a map that was never made.
      Cost: a panic at run time, on a path tests did not reach.
      FOUND BY: reading the code; the compiler cannot.

   5. A LOOP-CAPTURED VARIABLE used without passing it. Cost: every
      iteration used the final value.
      FOUND BY: go vet, since 1.22, for the common shape.

   6. A MISSING CONTEXT in a call that takes one. Cost: an
      operation that cannot be cancelled, and a timeout that is a
      fixed sleep rather than a deadline.
      FOUND BY: nothing. This is a discipline.

   7. AN IGNORED ERROR. Cost: a silent failure that surfaces three
      layers away as a wrong value.
      FOUND BY: errcheck (not in the standard toolchain), or a
      linter, or by writing blank identifiers deliberately.

   8. A MAP ITERATED AND ITS ORDER ASSUMED. Cost: output that
      differs between runs; golden tests that fail randomly.
      FOUND BY: running the test twice.

   9. A MUTEX COPIED BY VALUE. Cost: two holders of the "same"
      lock, so neither excludes the other.
      FOUND BY: go vet's copylocks check.

   THE THREE THINGS THAT MAKE THEM HARD.
   1. MOST COMPILE. A reviewer reads for logic, not for lifetime.
   2. MOST ARE CORRECT IN A SINGLE-THREADED TEST.
   3. MOST ARE SILENT. A crash would have found them.          */

/* TWO PRACTICES. RUN go vet AND -race IN THE PIPELINE, because
   four of the nine have a diagnostic and a diagnostic is free.

   And READ THE NIL-INTERFACE SECTION ONCE MORE, because trap 1 is
   the one that costs the most debugging time: the code looks
   correct, the compiler warns, and the warning is the only thing
   standing between you and an hour.                                 */

package main

import (
	"errors"
	"fmt"
	"os"
	"sync"
	"time"
)

/* SEVEN TRAPS. Each one compiles, passes go vet, and produces a
   wrong answer rather than an error. */

/* 1. THE TYPED NIL IN AN INTERFACE. */
type Reader interface{ Read() []byte }
type File struct{ f *os.File }

func (f *File) Read() []byte { return nil }

func the_typed_nil() error {
	var r Reader
	var f *File
	r = f
	if r != nil {
		r.Read()   /* the guard did NOT fire: the interface
		              carries the type *File, so it is not nil.
		              Reading through it may work here and may
		              not for a type whose method dereferences
		              the receiver - which is why the rule is to
		              store a nil INTERFACE, produced by never
		              assigning to it, rather than a nil pointer
		              assigned into one.                        */
	}
	return nil
}

/* 2. THE LOOP VARIABLE CAPTURED, which is fixed in Go 1.22 and is
   the reason code written for 1.21 must copy it explicitly. */
func the_capture() {
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			/* Go 1.21 and earlier: ALL THREE goroutines see
			   the final value of i, so the loop runs the body
			   once with 3 rather than three times with 0, 1, 2.
			   Go 1.22 onwards: a fresh i per iteration, and
			   the fix is unnecessary. Version-dependent
			   behaviour that COMPILES is the worst kind.   */
			fmt.Println(i)
		}()
	}
	wg.Wait()
}

/* 3. THE ERROR COMPARED WITH ==. */
var ErrTimeout = errors.New("timeout")

func wrap() error { return fmt.Errorf("request: %w", ErrTimeout) }

func the_wrong_comparison() {
	err := wrap()
	/* if err == ErrTimeout       FALSE. %w creates a NEW error
	                                 value whose message is the
	                                 concatenation; the wrapped
	                                 error is reachable only
	                                 through Unwrap.            */
	/* if errors.Is(err, ErrTimeout)   TRUE - the correct form,
	                                       and it works through
	                                       any number of wraps   */
	/* if errors.Is(err, os.ErrNotExist)  TRUE iff something in
	                                         the chain IS that
	                                         sentinel           */
	_ = err
}

/* 4. THE DEFER ARGUMENTS EVALUATED IMMEDIATELY. */
func the_defer_trap() {
	f, _ := os.Open("a.txt")
	name := "a.txt"
	defer f.Close()
	defer fmt.Println("opening", name)   /* the argument is
	                                         evaluated NOW, so it
	                                         prints "a.txt"       */
	name = "b.txt"                       /* too late              */
	defer fmt.Println("opening", name)   /* ... but THIS one
	                                         evaluates at the
	                                         defer, because it is
	                                         a different statement */
	/* Rule: defer f(g()) evaluates g() now. Defer an argument that
	   is a variable and it is the variable's value at defer time
	   that is captured, not the variable. For the value at exit,
	   use a closure. */
}

/* 5. THE RACE THAT ONLY APPEARS UNDER LOAD. */
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) bad() { c.n++ }   /* NOT ATOMIC: read, add,
	                                      write. Two goroutines
	                                      interleave and one
	                                      increment is LOST. go vet
	                                      does not find it; only
	                                      -race does.            */

func (c *Counter) good() { c.mu.Lock(); c.n++; c.mu.Unlock() }

func the_race() {
	c := &Counter{}
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); c.bad() }()
	}
	wg.Wait()   /* the count is less than 100, and it is less by a
	              different amount every run. A nondeterministic
	              result is the SYMPTOM; the fix is -race in CI. */
}

/* 6. THE CONTEXT CANCELLED BUT THE WORK NOT STOPPED. */
func the_ignored_context() {
	ctx, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	go func() {
		/* for { doSlowThing() }  the context is never consulted,
		   so the goroutine outlives the deadline. cancel() is a
		   SIGNAL, not a KILL: it makes the operations that take
		   the context return, and an operation that does not
		   take it is unaffected.                              */
	}()
}

/* 7. THE STRUCTURE RETURNED BY VALUE BUT MUTATED. */
type Buffer struct{ data []byte }

func build() Buffer { return Buffer{data: make([]byte, 0, 16)} }

func the_shared_slice() {
	b := build()
	b.data = append(b.data, 1)   /* fine on its own             */

	bs := []Buffer{build(), build()}
	bs[0].data = append(bs[0].data, 1)
	/* if the two Buffers were built by a loop that reused one
	   make, appending to one appends to the other, because the
	   SLICE HEADER is copied and the ARRAY it points at is
	   shared. Structs containing slices, maps and pointers have
	   this property; passing them "by value" does not copy the
	   contents.                                               */
	_ = bs
}

A.3 Terms, and the four used wrongly

Four words in Go are used more loosely than the specification defines them, and the looseness is where most arguments about the language go wrong.

Four terms, defined and corrected

Then the three conventions worth adopting, and each is a requirement. A goroutine is not a thread, and a "thread-safe" claim about a type means something different in Go. An error returned is not necessarily an error, because nil is a value and a typed nil is a value. Concurrency is not parallelism, because a goroutine is a scheduling decision and a thread is an operating-system object. And Safe means race-free, not correct, because the data-race detector says nothing about logic. Then the two practices, and each is a discipline. Use the specification's word in a comment, so that a reader knows the term means what the language means. And When a comment says the word, check that the code satisfies the definition, because the comment is a claim and the code is the fact.

<p>Four terms in this guide are used precisely and used loosely in roughly equal measure, and in each case the precise meaning carries a consequence the loose one does not. The consequence is what makes the term worth defining: GOMAXPROCS versus the scheduler decides whether a workload can scale, closing a channel versus signalling one decides whether a program crashes under load, the memory model versus sequential consistency decides whether a race is a wrong answer or an undefined one, and idempotence versus safe-to-retry decides whether a timeout causes a duplicate.

<p>The scheduler distinction is the least intuitive, because the loose reading - GOMAXPROCS is how many threads Go runs - is true only in the case nobody is thinking about. A goroutine that blocks on a channel, a mutex or a syscall releases its processor slot, so concurrency above the limit happens anyway. That is why an I/O-bound workload runs perfectly well at GOMAXPROCS of one while a CPU-bound one does not, and why a service that is slow for a reason nobody can find is often a service whose workers are all waiting rather than computing. It also explains why raising the limit on an I/O-bound service changes nothing, which is the observation that makes the distinction memorable.

<p>Closing versus signalling is a rule about ownership, and it is worth stating as one. Close asserts that no more values will ever be sent, which only the sender can know, and it is permanent: a subsequent send panics, in the sender, possibly in another goroutine, possibly only under contention. Sending a sentinel value to mean stop is a different mechanism with different properties - it needs an allocation, it cannot carry a payload, and a receiver cannot distinguish it from a legitimate value without a comparison. Where the exhaustion of a stream is the signal, close is the right answer and ranging over the channel is the idiomatic consumer; where cancellation is the signal, a separate channel or a context is, and the two are not interchangeable.

<p>The memory model distinction is the one that decides how a race is investigated. Sequential consistency is what the synchronisation primitives provide: a mutex, a channel, an atomic operation, each establishing a happens-before relation so that a write before a release is visible after the corresponding acquire. The memory model covers the whole language, including the case where none of those is present - and in that case it says nothing at all. Not that one of the two values will be read, but that the program has no defined behaviour. That is why a race cannot be debugged by reasoning about the two racing lines: there is no guarantee that the value you read is one of the values you wrote, and the only available response is to remove the race.

<p>Idempotence versus safe-to-retry is the distinction most often collapsed, usually by a client retrying an operation the server already performed. Setting a key to a value and deleting a file are idempotent; charging a card is not, which is why the idempotency key exists - and the key is a property of the interaction, not of the operation. A timeout leaves the caller unable to distinguish "did not happen" from "happened and the reply was lost", and the retry is correct only in the second case being harmless. Where it is not, the retry has to be conditional on an identifier the server can recognise, and that is a protocol requirement rather than an implementation detail.

/* 1. "GOROUTINE" and "THREAD". Used interchangeably.

   PRECISE: a goroutine is a FUNCTION SCHEDULED BY THE GO RUNTIME,
   with a stack that starts at ~2 KB and grows. A thread is an
   OPERATING-SYSTEM OBJECT with a stack the OS sizes, and the Go
   runtime multiplexes goroutines across a smaller number of them.

   LOOSE: calling a goroutine "a thread", which leads to a
   thousand OS threads and the memory problem Go exists to solve.

   THE DISTINCTION MATTERS because "thread-safe" is a claim about
   a data race, and a type containing a goroutine-related bug is
   still thread-safe - it just deadlocks.                          */

/* 2. "ERROR". Used loosely to mean "something went wrong".

   PRECISE: an error is a VALUE implementing interface{ Error()
   string }. nil is the absence of an error. A TYPED NIL is the
   PRESENCE of an error whose value is nil, and it is != nil.

   LOOSE: "it returned an error", used for a non-nil value that is
   not necessarily a failure - a sentinel returned deliberately to
   mean "not found" is still an error, and the caller must branch
   on it.

   THE DISTINCTION MATTERS because if err != nil is the most
   common line in Go and it is wrong for a typed nil.            */

/* 3. "CONCURRENCY" and "PARALLELISM". Used interchangeably.

   PRECISE: CONCURRENCY is a STRUCTURE - a program written so its
   parts can be interleaved. PARALLELISM is EXECUTION - those parts
   running at the same instant on different cores.

   LOOSE: "make it parallel", meaning "make it concurrent", which
   produces code where the interleaving is not designed and the
   program is racy.

   THE DISTINCTION MATTERS because a concurrent program can be
   correct on one core and is the ONLY way to write one that is
   correct on eight - and because "I made it parallel" is usually
   a claim about a goroutine count rather than about cores.      */

/* 4. "SAFE". Used loosely to mean "correct".

   PRECISE: in the context of the race detector, "race-free" means
   no two goroutines access the same memory, at least one writing,
   without synchronisation. It says NOTHING about logic, deadlock,
   or a slice shared without a length.

   LOOSE: "the code is safe", meaning correct, which the detector
   will happily confirm about a program that returns the wrong
   answer reliably.

   THE DISTINCTION MATTERS because the detector's silence is
   evidence about ONE property, and the commonest misreading is
   treating it as evidence about all of them.                       */

/* Three conventions worth adopting.
   1. A GOROUTINE IS NOT A THREAD, in every comment that says so.
   2. AN ERROR IS A VALUE, and nil is its absence - say which.
   3. SAFE MEANS RACE-FREE, and nothing more.                        */

/* Two practices. USE THE SPECIFICATION'S WORD in a comment, so a
   reader knows the term means what the language means. And WHEN A
   COMMENT USES THE WORD, check the code satisfies the definition -
   because the comment is a claim and the code is the fact.        */

package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

/* FOUR TERMS USED PRECISELY AND LOOSELY, and the consequence of
   getting the loose version. */

/* 1. "GOMAXPROCS" vs "G".

   GOMAXPROCS is a LIMIT on how many goroutines execute Go code at
      one instant. It is settable at run time, it defaults to the
      number of logical CPUs, and it does not bound the number of
      goroutines.

   G is the scheduler's INTERNAL state: the run queue, the local
      run queues, the garbage collector's pacing, and the channels
      waiting for a receiver. Changing it is only for measurement.

   The loose reading - "GOMAXPROCS is how many threads Go runs" -
   is wrong in a way that matters: GOMAXPROCS == 1 still runs every
   goroutine, one at a time, and a goroutine blocked on a channel
   or a syscall RELEASES ITS P, so blocking work overlaps
   regardless of the value. That is why a CPU-bound workload at
   GOMAXPROCS == 1 does not scale, while an I/O-bound one scales
   perfectly well with GOMAXPROCS == 1.                     */

/* 2. "CLOSE A CHANNEL" vs "SIGNAL".

   Precisely: close makes a channel permanently ready to receive,
      yielding the zero value of the element type forever, and
      PANICS on any subsequent send. The send on a closed channel
      is what panics, and it panics in the SENDER - which is why
      a send on a channel closed by another goroutine is a crash
      that only appears under load.

   Loosely, close is used to mean "no more work" or "we are done",
      which conflates the two directions. Sending a zero value to
      say "stop" costs an allocation for the interface and loses
      the payload; ranging over a channel is the idiomatic way to
      consume until close, and a separate done channel exists for
      the cases where you need cancellation rather than exhaustion.

   So: the SENDER closes, and only the sender. A channel handed to
   another goroutine is never closed by the receiver, ever - the
   receiver cannot tell a close from a value in a select, and
   double-close is a panic rather than a no-op. */

/* 3. "MEMORY MODEL" vs "SEQUENTIAL CONSISTENCY".

   Sequential consistency is what Go's sync package provides for
      the operations it covers: a mutex, a channel send or receive,
      an atomic operation, or the once primitives. All of them
      establish a happens-before relation, so a write before a
      mutex unlock is visible after the corresponding lock.

   The memory model is the complete specification, and it says more
      than that: it also defines the behaviour of a program with
      NO synchronisation at all. Two goroutines reading and
      writing the same variable with no ordering between them is a
      DATA RACE, and the specification does not say what happens -
      not "an arbitrary value", not "one of them", but nothing at
      all.

   That is why "it works on my machine" is not a defence for a
   race: the answer is not guaranteed to be one of the two values
   you wrote, and a program with a data race has no defined
   behaviour to reason about. -race finds these, and it finds them
   by observing the actual execution rather than by proving
   anything - so a race that never occurs during a test run is not
   absent, it is not yet triggered. */

/* 4. "IDEMPOTENT" vs "SAFE TO RETRY".

   Idempotent precisely: performing the operation N times has the
      same effect as performing it once. Deleting a file, setting
      a key to a value, and incrementing a counter with SET rather
      than INCREMENT are idempotent.

   Safe to retry is a property of the SYSTEM around the operation:
      whether repeating it after a TIMEOUT is correct, which also
      requires that the first attempt's effect either did not
      happen or is indistinguishable from the second. Charging a
      card is not idempotent, which is why it needs an idempotency
      key: the key is what makes the retry safe, and it is not a
      property of the charge.

   Conflating them is what produces the retry storm - an operation
   that is safe to retry at the client and unsafe at the server
   being retried by both the client and a load balancer, and the
   failure being a duplicate rather than an absence.
   errors.Is(err, context.Canceled) is the check that decides
   whether a retry is even correct, and it has to be made BEFORE
   the retry, not after the second failure. */
