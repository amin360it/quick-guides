Welcome — IT Infrastructure System Design

How this guide is organisedThe infrastructure stack

This opening section explains what the guide covers: the complete infrastructure stack, from physical facilities up to cloud and SRE practice. It positions the book as both a front-to-back tutorial and a lasting reference. Read it once in order, then return to chapters as needed while you build. The section sets expectations for how each later topic builds on what came before.

A practical guide to designing and operating the foundation layer that everything else runs on: compute, storage, network, identity, monitoring and recovery. Single file, offline, progress saved locally.

How this guide is organised

The guide is organised into four parts: foundations, platform, resilience, and operating at scale. Each chapter is a dependent building block, so the foundations must be understood before the later material makes full sense. Practitioners should follow the suggested reading order the first time, then dip into individual chapters as a reference. The cross-references between chapters are deliberate and carry definitions forward.

  • Foundations (Ch. 1–5) — what infrastructure is, data centres, compute, storage and networking.
  • Platform (Ch. 6–9) — virtualisation/cloud, operating systems, identity, monitoring.
  • Resilience (Ch. 10–12) — backup/DR, high availability, security infrastructure.
  • Operating at scale (Ch. 13–18) — automation/IaC, capacity, cloud/hybrid, FinOps, SRE and a case study.

The infrastructure stack

Every system rests on a stack of layers spanning facilities, network, compute, storage, identity and applications. Each layer is designed to fail independently so a single fault does not take the whole stack down. In practice you work bottom-up, hardening the physical and network base first because everything above depends on it. This stack model is the organising idea behind every chapter.

Applications  (business systems)
Middleware    (web servers, queues, databases)
Platform      (OS, containers, orchestrators, IAM)
Compute       (servers, VMs, cloud instances)
Storage       (SAN/NAS/object, backup)
Network       (switching, routing, firewalls, DNS, LB)
Facilities    (power, cooling, racks, cabling)

The seven-layer stack from facilities up to applications; every layer depends on the ones below it, so lower-layer failures sink everything.

Every layer depends on the one below. Most "application outages" are actually failures in a lower layer. Design each layer to fail without taking the stack down.

1 · What IT Infrastructure Is

1.1 Scope and goals1.2 Infrastructure quality attributes1.3 On-premises, cloud and hybrid

This chapter defines what infrastructure is and separates it from the applications that run on top. It establishes the core vocabulary and the quality attributes that matter, because those definitions reappear in every later chapter. Reader attention here pays off throughout, as terms like availability, scalability and security recur constantly. The goal is shared language before any deeper design work.

1.1 Scope and goals

Infrastructure provides five pillars that everything else depends on: compute, storage, network, identity and management. This section explains what each pillar covers and how they interact, so you can locate where your own system sits in the stack. Knowing the boundaries helps you decide what to own, what to buy, and what to delegate to a provider.

Infrastructure provides the compute, storage, network, identity and management capabilities other systems consume. Its goals are availability, performance, security, scalability and cost-efficiency.

1.2 Infrastructure quality attributes

The quality attributes are the measurable targets a good system is judged against, including availability, RTO and RPO, scalability, security and cost. This section explains what each number means and why agreeing them first shapes every later decision. In practice you set these targets before designing, because capacity, redundancy and budget all follow from them, and undefined attributes get decided by default.

AttributeTypical target
Availability99.9% – 99.99% per service
RTORecovery Time Objective (how long to restore)
RPORecovery Point Objective (how much data may be lost)
ScalabilityElastic with demand
SecurityLeast privilege, defence in depth
ObservabilityKnow before users tell you
CostPredictable, attributable per service

1.3 On-premises, cloud and hybrid

This section compares on-premises, cloud and hybrid deployment, each trading control against operational overhead for different outcomes. On-premise systems let you keep full control of hardware and data but carry power, cooling and maintenance costs, while cloud shifts those burdens to a provider. In practice you choose based on data residency rules, legacy dependencies and the size of the operations team you can staff.

ModelYou manageBest for
On-premEverythingData residency, legacy, predictable heavy load
IaaSOS and aboveLift-and-shift, full control
PaaSApp and dataFast delivery, less ops
SaaSUsageCommodity functions (mail, CRM)
HybridMixCloud burst + on-prem data

2 · Data Centres & Physical Layer

2.1 The facility2.2 Power and redundancy2.3 Racks, cabling and labelling

Data centres are the physical foundation that compute, storage and networking all depend on. This chapter covers the facility itself, power distribution, cooling, fire suppression, racks and cabling, the parts that cannot be patched from software. The guiding rule is that every clever layer above dies the moment the facility does. Practitioners plan redundancy and physical security for the whole site before any server goes in.

2.1 The facility

A data centre facility must guarantee power paths, cooling and physical security for everything inside. This section explains the tiers of facility redundancy from basic to fault tolerant, and how those tiers set the budget and design constraints you build against. In practice you would inspect the power feeds, cooling loop and access control layers and confirm the facility tier matches what the applications running there actually require.

Power:   utility feed -> UPS -> PDU -> rack -> dual-corded servers
Cooling: CRAC/CRAH units, hot/cold aisle containment
Fire:    inert gas / water mist, early detection
Security:badge + biometric access, CCTV, cabinets locked
Tiers:   I (basic) ... IV (fault tolerant, 99.995%)

A quick sketch of the facility essentials from the power path to fire suppression, physical security and the fault-tolerant tier scale.

2.2 Power and redundancy

Power is delivered from the utility feed through uninterruptible supplies, standby generators and distribution units down to each server. Redundancy is typically N+1 or 2N, meaning a spare unit or a fully duplicated path for every component. In practice you trace the whole path from grid to rack and treat any single unprotected fuse or switch as a single point of failure.

ComponentRedundancy
Utility feedsN+1 or 2N
UPSBattery/generator ride-through
PDUsDual A/B power paths
GeneratorsAutomatic transfer + fuel contracts

2.3 Racks, cabling and labelling

Racks are where cabling, power budgets and asset tracking are actually carried out. This section covers planning the power draw per rack, structured cabling between switches and servers, and labelling every cable and asset so failures can be found quickly. In practice good labelling and a current documentation system let a technician trace any circuit in minutes, while a chaotic rack can cost hours of downtime at the least convenient moment.

  • Asset tags and structured cabling with documented patching.
  • Power budget per rack; never exceed the breaker.
  • Dual-network paths (A/B switches) for redundancy.
  • Spare capacity for growth and maintenance windows.

3 · Compute

3.1 Servers and sizing3.2 Virtualisation3.3 Containers and orchestration

Compute is the layer where workloads actually run, in the form of physical servers, virtual machines or containers. This chapter explains how to size those resources and how the abstraction you choose, hypervisor or container runtime, shapes every behaviour above it. In practice you match the compute type to the workload and plan headroom, because getting sizing and the right abstraction right makes everything above behave predictably.

3.1 Servers and sizing

Server sizing balances CPU, memory, disk and network capacity against what the workload actually needs. In practice you measure real utilisation before buying or allocating, because memory is usually the first resource exhausted and the hardest to add later. Plan for headroom and growth while keeping per-host costs reasonable, and favour horizontal patterns that let you add capacity without replacing hardware.

ResourceConsideration
CPUCore count vs clock speed; oversubscription ratios
MemoryUsually the first constraint; reserve host overhead
Local diskOS/scratch; boot devices in RAID 1
Network1/10/25/100 GbE; bonded uplinks
Form factor1U/2U/4U rack, blade, or cloud instance

3.2 Virtualisation

A hypervisor runs many virtual machines on one physical host and isolates each guest operating system from the others. Virtualisation is the foundation of almost every modern data centre because it turns hardware into a pool of allocatable resources. In practice you pick a hypervisor such as VMware or KVM, size the physical hosts for the spread of guests, and rely on live migration and snapshots for maintenance and resilience.

Bare-metal host
  hypervisor (ESXi / Hyper-V / KVM / Proxmox)
    +-- VM (guest OS)   +-- VM   +-- VM
Containers share the host kernel instead of running a full guest OS
and start in milliseconds vs minutes.

VMs get a full guest OS isolated by a hypervisor, while containers share the host kernel and start in milliseconds instead of minutes.

3.3 Containers and orchestration

Containers package an application with its dependencies and share the host operating system kernel, so they start in milliseconds and use far less overhead than a full VM. Orchestrators such as Kubernetes handle scheduling, scaling, networking and self-healing across a cluster of machines. In practice you build immutable images, declare the desired state in manifests, and let the orchestrator keep the running workload matched to it.

  • Containers package app + dependencies into an immutable image.
  • Kubernetes schedules, scales, heals and networks container workloads.
  • Allocate CPU/memory requests and limits to prevent noisy neighbours.
  • Use node pools to separate workload types (system, app, GPU).

CPU oversubscription is normal; memory oversubscription risks the OOM killer and node instability. Budget memory conservatively.

4 · Storage

4.1 Block, file and object4.2 RAID levels4.3 Tiers, snapshots and replication

Storage comes in three models: block, file and object, each with its own access pattern, performance and durability profile. This chapter explains when to use raw volumes, shared file systems or HTTP object stores, and how to protect them with RAID, snapshots and replication. In practice the choice follows the workload: databases like block storage, shared files like NFS or SMB, and backups and archives like object stores.

4.1 Block, file and object

Block storage presents raw volumes to a single host, file storage serves shared folders over NFS or SMB to many clients, and object storage exposes buckets over HTTP with flat namespaces. Each model matches different workloads, from databases and virtual machine disks to shared documents and backup archives. In practice you choose by access pattern and scale, and you mix types within one system where each tier needs a different behaviour.

TypeAccessExamplesUse
BlockRaw volumesSAN, EBS, iSCSIDatabases, VMs
FileShared foldersNAS (NFS/SMB)Shared docs, home dirs
ObjectHTTP APIS3, Azure Blob, GCS, MinIOBackups, media, static assets

4.2 RAID levels

RAID combines multiple disks into one logical volume to improve performance or redundancy. The levels run from simple striping to mirroring to double parity, each trading usable capacity, performance and tolerance for failed disks. In practice you pick a level to match your performance needs and data risk, such as RAID 10 for databases and RAID 5 or 6 for bulk storage, and you always back parity levels with monitored spare disks.

LevelLayoutToleratesNotes
RAID 0Striping0 failuresFast, no protection
RAID 1Mirroring1 diskSimple, 50% usable
RAID 5Stripe + parity1 diskWrite penalty
RAID 6Double parity2 disksLarge arrays
RAID 10Mirror + stripe1 per mirrorPerformance + protection

4.3 Tiers, snapshots and replication

Storage tiering, snapshots and replication manage the trade-off between cost, performance and durability. Tiering moves cold data to cheaper media, snapshots capture fast point-in-time states, and replication keeps copies across systems or sites. In practice you tier by age and access frequency, snapshot on a schedule that matches your recovery point, and note that snapshots are not backups on their own because they live on the same failing storage.

  • Tiering: hot SSD/NVMe, warm SAS, cold archive/object.
  • Snapshots give fast point-in-time copies; they are not backups.
  • Replication (sync/async) protects against array loss; async introduces lag.
  • Thin provisioning saves capacity but risks overcommitment.

5 · Networking for Infrastructure

5.1 Addressing, VLANs and subnets5.2 Core network services5.3 Redundancy and topology

Networking connects every component and carries the most complexity and the most outage blame in infrastructure. This chapter covers addressing, VLANs and subnets, core services like DNS, DHCP and NTP, load balancing, and redundant topologies. In practice you segment networks to limit blast radius, keep names and time consistent, and design every link with a standby so no single switch or cable can take a service down.

5.1 Addressing, VLANs and subnets

VLANs and subnets divide a physical network into separate broadcast domains so that traffic, faults and policies stay contained. Segmentation limits the blast radius of a misconfigured host and makes firewall rules much easier to reason about. In practice you group hosts by role and trust level, assign each group its own subnet, and attach access control lists at the boundaries so a compromise in one lane cannot roam the whole network.

VLAN 10  Management   10.10.0.0/24
VLAN 20  Servers      10.20.0.0/22
VLAN 30  Storage      10.30.0.0/24  (jumbo frames, isolated)
VLAN 40  DMZ          10.40.0.0/24
VLAN 50  Clients      10.50.0.0/22

Segmentation limits blast radius and enables firewall policy.

A sample segmented network with management, servers, storage, DMZ and clients in separate VLANs, each with its own subnet and blast radius.

5.2 Core network services

DNS, DHCP, NTP and load balancers are the quiet core services that everything else quietly depends on. When one drifts or fails, name resolution, addressing, time and traffic distribution break everywhere at once. In practice you run these as redundant pairs, monitor them first, and keep NTP stable because certificate validation and logs depend on accurate time, with load balancers added to spread traffic and detect failing backends.

ServicePurpose
DNSName resolution (internal + external zones)
DHCPAddress assignment (reservations for servers)
NTPTime sync — critical for auth, logs, TLS
Load balancerDistribute traffic, health checks, TLS termination
Reverse proxyRouting, caching, WAF

5.3 Redundancy and topology

Redundant links, switches and out-of-band management remove single points of failure from the network path. The topology is designed for the realistic case where a switch, link or power feed fails at an inconvenient moment. In practice you run protocols such as VRRP or ECMP for failover, keep a management network independent of the production fabric, and test failover regularly because a standby path that has never been exercised usually fails when you need it most.

  • Redundant switches/routers with link aggregation and redundant uplinks.
  • Spanning tree / MLAG to avoid loops and single points of failure.
  • Out-of-band management network for consoles (iDRAC/iLO/IPMI).
  • Uplinks sized for peak + failover (a failed link doubles the load).

6 · Virtualisation, Cloud & Platform Models

6.1 Service models6.2 Regions, zones and edge6.3 Landing zones and guardrails

Virtualisation and cloud both deliver the same compute, storage and network capabilities as a managed service, differing mainly in how much of the stack the provider runs. The model you choose decides how much operational load remains on your team. In practice you compare IaaS, PaaS and managed services by the control you need, then accept and document everything you are delegating. This chapter sets up those decisions.

6.1 Service models

The service models IaaS, PaaS, FaaS and SaaS shift progressively more of the stack to the provider, from raw virtual machines all the way to finished applications. Each step reduces your operational load but also your control and visibility. In practice you take the smallest managed slice that still meets your compliance and customisation needs, and you explicitly accept the shared responsibility for everything the provider now runs.

ModelProvider managesYou manage
IaaSCompute/storage/networkOS, runtime, app
PaaSOS + runtimeApp + data
FaaSScaling + runtimeFunctions
SaaSEverythingConfiguration

6.2 Regions, zones and edge

Cloud resources are organised into regions, each containing availability zones that have independent power, cooling and network. Spreading replicas across zones is the standard way to survive the loss of one facility entirely. In practice you place application instances and data copies in at least two zones within a region, and you keep lower-latency traffic local while accepting that cross-region failover is the next level of resilience.

Region (e.g. eu-west-1)
  +-- Availability Zone A   (independent power/network)
  +-- Availability Zone B
  +-- Availability Zone C
Spread replicas across >= 2 (better 3) AZs for HA.
Multi-region for DR and latency; accept data-replication complexity.

A region contains availability zones with independent power and network; spread replicas across at least two, better three, zones for high availability.

6.3 Landing zones and guardrails

A landing zone is a governed, repeatable starting point that every team or environment gets before they can create resources. It puts network layout, identity, logging and budgets in place by default instead of leaving each team to improvise. In practice you build golden images, baseline subnets and policy guardrails such as IAM roles and resource tagging, so new projects start secure and compliant without bespoke effort.

  • Accounts/subscriptions per environment and per team.
  • Central networking, identity and logging.
  • Policy guardrails (SCPs, Azure Policy) enforcing standards.
  • Golden images / blueprints for repeatable deployments.

7 · Operating Systems & Configuration Management

7.1 Standardisation and patching7.2 Configuration management7.3 Access and remote management

Operating systems stay consistent and patched, or they quietly become the root cause of incidents. This chapter covers standardising the build through golden images, managing configuration after deployment, and controlling remote access. In practice you provision from a known baseline, keep the fleet patched on a fixed cadence, apply configuration with automation, and control remote access through broker gateways.

7.1 Standardisation and patching

Standardisation starts with golden images: a minimal, approved baseline operating system that every host is provisioned from. A fixed patch cadence and a minimal installed footprint keep the fleet consistent and easier to secure, provision and replace. In practice you build the image in a pipeline, scan and patch it on a schedule, and allow service-specific changes only through configuration management so drift never accumulates.

PracticeBenefit
Standard build/golden imageConsistency, faster provisioning
Patch cadenceSecurity, stability
Minimal footprintSmaller attack surface
Immutable infraReplace, don’t mutate

7.2 Configuration management

Configuration management tools declare the state a system should be in and converge the live system toward it, so servers never depend on someone remembering manual steps. Ansible typically manages configuration and ad-hoc tasks on existing servers, while Terraform provisions resources and manages their lifecycle. In practice you store everything as code in version control, run playbooks and plans through review, and let the tools report drift when reality stops matching the declared state.

Ansible   - agentless, YAML playbooks (great for config + patching)
Puppet/Chef - agent-based, continuous convergence
Terraform - provision infrastructure (see Ch. 13)
Desired state: define the target; the tool converges reality to it.

Tool comparison: Ansible is agentless and great for config, Puppet and Chef converge continuously, and Terraform provisions the infrastructure itself.

- hosts: web  # target the web servers
  tasks:
    - name: ensure nginx is present and running
      ansible.builtin.package: { name: nginx, state: present }  # desired package state
    - name: start nginx
      ansible.builtin.service: { name: nginx, state: started, enabled: true }  # run at boot too

A minimal Ansible playbook that installs nginx and starts it as an enabled service on the web hosts, keeping them in the declared state.

7.3 Access and remote management

Remote access to servers and appliances should never be exposed directly to the internet. It goes through a bastion host or session broker that authenticates, logs and forwards connections to the internal network. In practice you use short-lived or certificate-based credentials instead of standing passwords, gate access to a specific SSH port, and record privileged sessions for audit, so every administration action is attributable.

  • SSH/RDP only from a bastion or via a policy broker; never exposed publicly.
  • Certificate-based or short-lived credential auth over passwords.
  • Session recording and full audit of privileged access.

8 · Identity & Access Management

8.1 Directories and SSO8.2 RBAC, ABAC and least privilege8.3 Privileged access management

Identity is the master key to the whole estate, so this chapter treats directories, access models and privileged access as security-critical infrastructure. A broken identity layer breaks authentication everywhere and every system that depends on it. In practice you run a central directory, connect applications to it via single sign-on, and apply least privilege together with strict controls on administrator accounts.

8.1 Directories and SSO

The directory is the single source of truth for users, groups and policies, and everything else authenticates against it. Single sign-on sits on top so a user logs in once, often with MFA, and accesses many systems with that one session. In practice you deploy a directory such as Active Directory or a cloud identity provider, federate the applications to it, and centralise deprovisioning so removing one person revokes access everywhere.

On-prem AD / cloud Entra ID / LDAP
  -> single source of truth for users and groups
SSO via OIDC / SAML / Kerberos
  -> one login, MFA, central deprovisioning

The directory is the single source of truth for users and groups, with SSO providing one login, MFA and central deprovisioning.

8.2 RBAC, ABAC and least privilege

RBAC assigns permissions through roles given to people or groups, while ABAC decides access from attributes such as department, environment and time of day. Just-in-time access adds short-lived elevation for tasks that need more privilege than the day-to-day role. In practice you grant the least access that still gets the work done, review role membership regularly, and prefer temporary elevation over permanently broad roles.

ModelDecision basis
RBACRoles assigned to users
ABACAttributes (dept, location, resource tags)
Just-in-timeElevate temporarily with approval

8.3 Privileged access management

Privileged access management vaults administrator credentials so passwords are rotated, checked out only when needed and individually attributable. It watches the highest-risk accounts that can change configuration, read every secret or delete backups. In practice you route privileged logins through the PAM broker, approve checkouts with workflows, and maintain a sealed break-glass account for emergencies that is monitored the moment it is opened.

  • Vault and rotate privileged credentials.
  • Break-glass accounts, sealed and monitored.
  • Separate admin identities from daily-use accounts.
  • Review access regularly; remove stale entitlements.

Service accounts with standing admin rights are the most common path to a full compromise. Scope them narrowly and rotate their secrets.

9 · Monitoring, Logging & Observability

9.1 The three pillars and a fourth9.2 SLIs, SLOs and error budgets9.3 What infrastructure should monitor

Observability means you find out a problem exists before a user reports it. This chapter covers the three pillars of monitoring, the SLI, SLO and error-budget framework, and the specific infrastructure signals worth watching. In practice you collect metrics, logs and traces into a single platform, define alert rules that page on real user impact, and review trends so capacity exhaustion is caught while it is still a trend rather than an outage.

9.1 The three pillars and a fourth

Metrics, logs and traces answer three different questions: how much, what happened and where the time went. Metrics are numeric counters gathered over time, logs record discrete events, and traces follow a request across services. A fourth pillar, alerting, decides when any of the data is severe enough to page a human. In practice you correlate all three in one tool so one incident can be seen across every dimension.

PillarAnswersExamples
MetricsHow much / how fastPrometheus, Azure Monitor
LogsWhat happenedELK/OpenSearch, Loki
TracesWhere time wentJaeger, Tempo, OTel
AlertsWhen to actAlertmanager, PagerDuty

9.2 SLIs, SLOs and error budgets

SLIs measure how often a service actually delivers good events, such as successful requests over total requests, while SLOs set the target for that ratio over a period. The error budget is the allowed shortfall, and it is spent on releases and changes rather than treated as failure. In practice you alert on burn rate so the budget is spent at a predictable pace, instead of alerting on raw noise that pages people for nothing.

SLI  = fraction of good events (e.g. successful requests under 300ms)
SLO  = target over a window (99.9% / 30 days)
Budget = 100% - SLO; spend it on releases, freeze when exhausted
Alert on burn rate, not on every transient spike

SLIs measure good events, SLOs set a target over a window, and the error budget decides when you freeze releases and alert on burn rate.

9.3 What infrastructure should monitor

Infrastructure monitoring watches the golden signals and the systems underneath them. You collect the same four metrics, latency, traffic, errors and saturation, for each service, and you watch the support infrastructure that hosts it. In practice you set thresholds from capacity models, alert on trends and utilisation approaching the ceiling, and treat capacity exhaustion as a slow and silent outage that is entirely avoidable if watched early.

  • Golden signals per service: latency, traffic, errors, saturation.
  • Infrastructure: CPU, memory, disk, network, power, temperature.
  • Capacity trends to forecast exhaustion.
  • Synthetic checks and real-user monitoring for availability.

10 · Backup, Disaster Recovery & Continuity

10.1 The 3-2-1 rule10.2 DR tiers and RTO/RPO10.3 Business continuity

Backup, disaster recovery and continuity are how you survive the day your primary systems go away. This chapter covers the 3-2-1 rule, DR tiers with their RTO and RPO implications, and the people and process side of business continuity. In practice you treat this spend as insurance, design it into the architecture, and most importantly rehearse restore and failover so the plan works exactly when the primary has already failed.

10.1 The 3-2-1 rule

The 3-2-1 rule says keep at least three copies of your data, on two different media types, with one copy stored off-site. Immutable and air-gapped copies extend this by protecting against ransomware that cannot delete or encrypt them. In practice you automate the copy pipeline, run backups to a separate storage class or cloud availability zone, and test restores on a schedule so the copies are known to be readable.

3 copies of data
2 different media/types
1 off-site (offline/immutable ideally)

Add "0 errors" by TESTING restores and using immutable/air-gapped copies
to defeat ransomware.

The 3-2-1 rule with tested restores and immutable, air-gapped copies added as the defence against ransomware.

10.2 DR tiers and RTO/RPO

DR tiers trade cost against recovery time, from slow backup-and-restore through pilot light and warm standby up to active-active. Each tier delivers a different RTO and RPO at a different price. In practice you work out what each system can tolerate, in downtime and data loss, then buy only the tier it needs, because an active-active tier for everything is unaffordable and a backup tier for everything is not enough.

TierStrategyRTOCost
Backup & restoreRestore from backupsHours–daysLow
Pilot lightCore kept warmHoursMedium
Warm standbyScaled-down live copyMinutesMedium+
Active-activeBoth sites servingSecondsHigh

10.3 Business continuity

Business continuity covers the people and process side that technology alone cannot: documentation, communication and rehearsed responses. It answers who decides what, who talks to whom, and how a team keeps working while systems are down. In practice you write call trees and runbooks, schedule drills and tabletop exercises, and treat an untested plan as a hope rather than a capability.

  • Document dependencies and manual workarounds.
  • Define communication and escalation during an incident.
  • Test failover and restores on a schedule (a DR drill).
  • Review after incidents; update RTO/RPO with real data.

An untested DR plan is a hope. Schedule drills, record actual RTO/RPO, and fix the gaps you find.

11 · High Availability & Clustering

11.1 HA building blocks11.2 Availability maths11.3 Finding and removing SPOFs

High availability is the engineering discipline of removing single points of failure so a system stays up when a component dies. The tools are redundancy, health checks, load balancing and clustering working together. In practice you add redundant components, verify them with automated health checks, and distribute traffic so a failing node is removed automatically, then you test the whole mechanism because unexercised failover is the most common reason high availability quietly fails.

11.1 HA building blocks

Redundant components, load balancing, clustering and multi-zone deployment cover different failure modes, from a failed disk to a lost data centre. Each technique protects a different part of the stack at a different cost. In practice you match the technique to what you are protecting: hardware redundancy for a single server, a load-balanced pool for stateless services, and cluster data replication where state must survive a node loss.

TechniqueProtects against
Redundant components (N+1)Single device failure
Load balancing + health checksNode failure, uneven load
Clustering / quorumServer failure with state
Database failoverDB node failure
Multi-AZ / multi-siteFacility/zone loss

11.2 Availability maths

Availability maths is a simple composition rule: components in series multiply their availability, while redundant components in parallel add to it. Two servers in series can hit two nines, but the moment one is 99 percent, the chain drops to the weaker link. In practice you model the chain, then look past the arithmetic for shared dependencies, since one un-redundant service still caps the availability of everything that uses it.

Serial:   A = A1 * A2        (dependencies multiply -> lower)
Parallel: A = 1 - (1-A1)(1-A2)  (redundancy -> higher)

Example: two 99.9% components in parallel
  = 1 - (0.001 * 0.001) = 99.9999%
But a shared dependency (one DB) still caps the whole chain.

Serial dependencies multiply availability down and redundancy lifts it back up; notice how a single shared dependency still caps the whole chain.

11.3 Finding and removing SPOFs

To find single points of failure you draw every dependency path and circle anything that exists only once on it. Hardware is the obvious case, but shared services, a single firewall, one key and even a team with only one expert who knows a system are points of failure too. In practice you remove or duplicate each one, and where duplication is impossible you at least make the failure fast, visible and recoverable.

  • Walk every path and circle anything with a single instance.
  • Watch shared services: DNS, identity, the load balancer, the database.
  • Remember people and processes: one expert, one runbook, one key.

12 · Security Infrastructure

12.1 Network security controls12.2 Zero trust12.3 Hardening and vulnerability management

Security infrastructure is the layered net around the estate, plus the working assumption that it will be breached. This chapter combines network controls, zero trust and hardening so that no single failure is fatal. In practice you layer firewall and WAF controls at the edges, apply posture checks and software-defined segmentation inside, and harden hosts so the blast radius of any breach stays small.

12.1 Network security controls

Firewalls, web application firewalls, VPNs and intrusion detection shape and monitor traffic where the network meets the outside world. Each control filters or detects a different kind of attack, from port scans to web injection to tunnelled traffic. In practice you layer them on the traffic path, run default-deny rules, analyse logs from all of them together, and remember that the perimeter is only the first line, not the whole defence.

ControlRole
Firewall / security groupsFilter traffic by rule
WAFBlock web attacks (SQLi, XSS)
VPN / ZTNASecure remote access
IDS/IPSDetect/block intrusions
SIEMCorrelate logs and alert
EDREndpoint detection and response

12.2 Zero trust

Zero trust assumes the network is always hostile and that every request must be verified on its own merits, never trusted because of its origin. Identity-aware proxies and mutual TLS verify the caller and the connection, while micro-segmentation isolates workloads so a compromised host cannot roam laterally. In practice you replace the flat trusted LAN with per-request authentication and least-privilege routes between services.

Old: trusted internal network, hard outside.
New: never trust, always verify.
  - identity-aware proxy for every service
  - mTLS between workloads
  - micro-segmentation instead of a flat VLAN
  - least privilege, continuous verification

The shift from a trusted internal network to never trust, always verify, using identity-aware proxies, mTLS and micro-segmentation.

12.3 Hardening and vulnerability management

Hardening shrinks the attack surface by removing unneeded software, applying secure defaults and locking down services on every host. Vulnerability management keeps the surface shrinking as new flaws appear, by scanning, prioritising and patching to an agreed severity SLA. In practice you apply CIS-style baselines, scan images before deployment, patch tracked findings on schedule, and store secrets in a vault instead of config files.

  • Baselines and CIS benchmarks; disable unused services.
  • Patch management with SLAs by severity.
  • Regular vulnerability scanning and penetration tests.
  • Secrets in a vault; never in config files or images.

13 · Automation, IaC & CI/CD for Infrastructure

13.1 Infrastructure as Code13.2 Pipeline for infrastructure13.3 GitOps and drift detection

Automation and infrastructure as code turn design decisions into reviewable, reproducible artifacts instead of manual tribal knowledge. Nothing depends on a human remembering a step, and every change can be peer reviewed and rolled back. In practice you write infrastructure in configuration files, store them in git, and run apply through a pipeline so the same change is made the same way every time.

13.1 Infrastructure as Code

Infrastructure as code declares servers, networks and cloud resources in files that are planned, reviewed and then applied, instead of being clicked together by hand. The state file records what exists and becomes the source of truth for what is live. In practice you write Terraform or equivalent, keep state remotely so a team shares it, and lock state during apply so two changes cannot fight over the same resources.

# one declarative EC2 instance
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.medium"  # small size for a test/example
  subnet_id     = aws_subnet.public.id
  tags          = { Name = "web", Env = "prod" }  # tags drive ownership and cost
}

terraform init / plan / apply  # review the plan before apply
State is the source of truth; keep it remote and locked.

A Terraform block declaring one AWS instance, driven through init, plan and apply, with remote locked state as the source of truth.

13.2 Pipeline for infrastructure

Infrastructure changes should run through the same discipline as code changes: plan, policy check, approval and then apply. This prevents a risky change from being typed directly against a production environment from a laptop. In practice you run the plan step in CI, enforce policies and security scans on the diff, require an approval gate for production, and apply with the same credentials every time so the outcome is reproducible.

fmt -> validate -> plan -> policy check -> approval -> apply
Never `apply` from a laptop on production; run it through CI with
review, state locking and an audit trail.

Run infrastructure changes through CI: format, validate, plan, policy-check, approve, then apply, with review, state locking and an audit trail.

13.3 GitOps and drift detection

GitOps holds the desired state of the entire environment in git and lets controllers continuously reconcile the live systems to match it. Any difference between the repository and reality is drift that the controller either corrects or reports. In practice you store manifests in git, run agents such as Flux or Argo CD in the cluster, merge changes through pull requests, and alert on drift so unauthorised or manual modifications become visible immediately.

  • Declarative desired state in git; controllers reconcile.
  • Detect and alert on drift between declared and actual state.
  • Immutable infrastructure: rebuild rather than patch.

14 · Capacity Planning & Performance

14.1 A capacity method14.2 Key utilisation signals14.3 Performance engineering

Capacity planning is how you run out of headroom on a schedule you control instead of by surprise. It combines measuring utilisation, forecasting growth, modelling headroom and setting trigger points for buying or scaling. In practice you review demand and capacity on a regular cadence, keep forecasts fed by real utilisation data, and act on the agreed triggers before the plateau is reached so users never feel the constraint.

14.1 A capacity method

A capacity method is a repeatable loop: measure current utilisation, forecast future demand, model how much headroom remains, and set triggers for action. The review runs on a schedule, typically monthly, because growth does not stay where you left it. In practice you instrument the infrastructure to capture trends, project several horizons out, and use the modelling to justify when to expand or purchase before supply runs short.

1 Measure current utilisation and growth rate
2 Forecast demand (seasonal + organic)
3 Model headroom: target <= 60-70% steady-state
4 Plan scale-up/scale-out triggers
5 Review monthly; capacities always shift

A five-step capacity method: measure, forecast, model headroom, set triggers, and review monthly since demand always moves.

14.2 Key utilisation signals

The key utilisation signals are the sustained CPU, memory pressure, IOPS and throughput numbers that show when a resource is nearing its ceiling. You watch sustained values and trends rather than peaks, because a slow climb is the signature of approaching exhaustion. In practice you monitor the ratio of demand to capacity, set thresholds on sustained utilisation, and forecast from the trend so you add capacity before the metric flattens against its ceiling.

ResourceWatch
CPUSustained utilisation, run-queue length
MemoryPressure, swap, OOM events
DiskIOPS, latency, free space, queue depth
NetworkThroughput vs link capacity, errors
Power/heatRack and circuit limits

14.3 Performance engineering

Performance engineering finds and removes the constraint that actually limits throughput instead of hiding it behind bigger caches. You load test to find the knee, the point where performance drops sharply as load rises, and you design the scaling levers to respond before it. In practice you profile and benchmark each layer, then set autoscaling on leading indicators so capacity grows ahead of the demand that would push the system past the knee.

  • Little’s Law: concurrency = throughput × latency.
  • Load test to find the knee of the curve before production does.
  • Cache and queue to smooth demand, not to hide a bottleneck.
  • Autoscale on leading indicators, not just CPU.

15 · Cloud & Hybrid Architecture

15.1 Common patterns15.2 Hybrid connectivity15.3 Cloud resilience

Cloud and hybrid architecture moves workloads to wherever they run best, either fully in the cloud or split across cloud and on-premise sites. The chapter covers the migration patterns, connectivity between sites and cloud-specific resilience, including the reality of egress cost. In practice you make the move pattern-explicit, connect sites with VPN or dedicated links, spread across availability zones, and budget for data leaving the cloud.

15.1 Common patterns

The four migration playbooks are lift and shift, re-platform, refactor and hybrid, ordered by depth of change and return. Lift and shift moves workloads as they are, re-platform swaps managed services in, refactor rewrites for the cloud, and hybrid keeps part of the estate on-premise. In practice you match the playbook to the workload’s age, its coupling to old infrastructure and your appetite for change, and you treat the choice as architectural, not cosmetic.

PatternUse
Lift & shiftFast migration, then optimise
Re-platformManaged DB/queue with minor changes
RefactorCloud-native (containers, serverless)
HybridKeep data on-prem, burst to cloud

15.2 Hybrid connectivity

Hybrid connectivity links cloud and on-premise networks across sites, with VPNs being cheap and temperamental and dedicated links such as Direct Connect or ExpressRoute being predictable and pricey. The design must cover routing, DNS resolution and egress cost before the first byte moves. In practice you plan overlapping CIDR avoidance, decide DNS split between the sites, and calculate transfer costs so data-heavy workflows do not surprise the bill.

VPN over internet  - cheap, variable latency
Dedicated link     - ExpressRoute / Direct Connect / Interconnect
                      predictable, higher cost

Design for: routing, DNS resolution across sites, and data egress cost.

VPN is cheap but variable, a dedicated link is predictable and pricier; design routing, DNS and egress cost across sites.

15.3 Cloud resilience

Cloud resilience starts from the fact that regions are made of availability zones and that a whole zone can fail or shed capacity. Workloads should be spread across zones and designed to degrade gracefully when one of them or a quota limit appears. In practice you replicate stateless tiers across zones with load balancing, keep state in replicated services, and deliberately test zone failure with game days so the design is proven rather than assumed.

  • Spread across AZs; test zone-failure scenarios.
  • Automate backup and restore with infrastructure as code.
  • Beware service quotas and regional limits.
  • Design for graceful degradation when a managed service wobbles.

16 · Cost Management (FinOps)

16.1 Visibility and attribution16.2 Optimisation levers

FinOps is cost control that starts in the architecture rather than at the billing report. It adds tagging and attribution first so every cent is accountable, then optimisation with budgets and the right pricing levers. In practice you enforce tagging on everything, run showback to teams, set budgets with anomaly alerts, and review spend with the same regularity you review capacity.

16.1 Visibility and attribution

Visibility starts by tagging every resource with owner, environment and cost centre so the bill can be attributed to whoever created it. Showback shares those numbers with each team, and anomaly alerts flag when spend departs from the expected pattern. In practice you make tagging mandatory at creation time, model the tag hierarchy, and let owners act on their own cost reports before central finance has to intervene.

Tag everything: owner, env, service, cost-centre
Showback/chargeback by team -> behaviour changes
Budgets + anomaly alerts catch runaway spend early

Tag every resource with owner, environment and cost-centre so spend is attributable, then add budgets and anomaly alerts.

16.2 Optimisation levers

Right-sizing matches instance sizes to real utilisation, reservations and commitment discounts buy predictable capacity at lower prices, and spot instances run interruptible workloads on spare provider capacity. Idle resources and over-provisioning are the quiet leaks to find first. In practice you start with a right-sizing review, cover steady-state load with reservations, and leave batch and stateless work on spot, while keeping an eye on egress costs.

LeverTypical saving
Right-sizingLarge — match capacity to demand
Reserved/savings plansLarge — for steady state
Spot/preemptibleLarge — for fault-tolerant work
Storage tiering / lifecycleMedium
Killing idle resourcesMedium–large
Egress reductionVariable

Cost is an architecture concern. A design that replicates everything across three regions for no reason is a permanent bill, not a one-time decision.

17 · Operations, SRE & Runbooks

17.1 SRE practices17.2 Runbooks and on-call17.3 Change and incident management

Operations, SRE and runbooks are how a system stays healthy after it goes live. The SRE practice turns operations into engineering by grounding work in SLOs, reducing toil and making change management blameless. In practice you define error budgets, automate repetitive work, keep tested runbooks for the on-call rotation, and treat every incident as a process improvement opportunity.

17.1 SRE practices

SRE balances the speed of shipping against the reliability of the running service using SLOs and their error budgets. Automating repetitive toil frees engineers to improve the system, and incidents are reviewed without blame so the real causes surface. In practice you set SLO targets with monitoring, spend the error budget deliberately on releases, and measure toil as a metric that drives automation.

PracticePurpose
SLOs + error budgetsBalance reliability and velocity
Toil reductionAutomate repetitive operations
Change managementSafe, observable changes
PostmortemsLearn without blame

17.2 Runbooks and on-call

Runbooks give an on-call engineer a tested, ordered path through a known failure before they touch anything. A good runbook starts with confirming the scope of the incident, works through the likely fixes, and ends with restoring the fixable state. In practice you write runbooks from real incidents, keep them current with the system, and test them so the first time they are followed is not at 3 a.m. during an outage.

Runbook: Database failover
  Trigger: primary unreachable > 60s
  1 Confirm scope (monitoring dashboard link)
  2 Announce in #incident
  3 Promote replica: <exact command>
  4 Verify app health; scale if needed
  5 Post-incident: restore HA, write postmortem

A runbook template for database failover: confirm scope, announce, promote the replica, verify health, then restore HA and write a postmortem.

17.3 Change and incident management

Change and incident management keep operations honest: changes are peer reviewed and reversible, and incidents get defined roles and a clear response structure. You track mean time to repair and repeat incidents as the honest health metrics of the operation. In practice you require review before production changes, standardise incident roles such as incident commander, and review the metrics monthly so the operation improves measurably.

  • Peer-reviewed, reversible changes; feature flags for risk.
  • Incident roles: commander, comms, ops scribe.
  • Blameless reviews that produce system fixes.
  • Track MTTR and repeat incidents as health metrics.

In practice you follow the same order here as in the real world: collect requirements first, design the layers against them, and make every trade-off explicit.

18.1 Requirements

Requirements set the targets for every decision downstream: availability, recovery point and recovery time objectives, data residency, growth expectations and team size. Everything in the design is ultimately a response to one of these numbers or constraints. 18.3 Decisions & trade-offs

Every design decision comes with an explicit trade-off, such as active-passive data replication, a mix of virtual machines and containers, and immutable backups.   • Everything as code — no snowflake servers, full audit.
