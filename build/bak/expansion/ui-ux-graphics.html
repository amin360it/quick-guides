Welcome — How to Use This UI/UX Design Guide

Who this is forWhat a designer needs to know to shipHow the chapters fit togetherTools, and what this guide assumesThe one rule that matters most

This guide is the bridge between designing an interface and building it. It assumes you can already design something you like, and covers the part where a design meets HTML, CSS, a component library, a browser on a slow phone, and a screen reader — and has to survive all of it.

Who this is for

You are a designer, or a developer who has to produce design work, or a developer who has to implement someone else's. All three need the same three things:

  • A vocabulary precise enough to brief a developer. "Make it pop" is not actionable. "Raise the contrast of the secondary text to 4.5:1 and use the 16px type scale" is.
  • The constraints, so you design inside them. Font rendering differs, users override colours, zoom is a feature, and not everyone sees colour the way you do.
  • A system, so a hundred screens stay coherent. Tokens and components, not one-off decisions.

The mindset shift worth making early: a design is not a picture of a screen. It is a specification for behaviour under conditions you cannot fully control. Every value you choose has to survive a 320 px viewport, 200% browser zoom, a colour-blind user, a slow network, a screen reader, and a user who has turned your animations off in the OS settings.

What a designer needs to know to ship

This guide covers the ground between "I have an idea" and "this is in production and correct".

  • Hierarchy and rhythm — how a layout communicates structure before a single word is read.
  • Colour — a system, not a palette, and the rules that keep it accessible.
  • Typography — scale, measure, rhythm, and the line-height maths nobody teaches you.
  • Spacing and layout — the 8-point grid, and why it is not about round numbers.
  • Components — designing the states, not just the picture of the default state.
  • Graphics on the web — SVG, iconography, raster formats, and when each is right.
  • Motion — what to animate, what not to, and the accessibility rules.
  • Accessibility — WCAG, ARIA, and the parts a designer is uniquely responsible for.
  • Responsive design — breakpoints as a consequence of content, not device widths.
  • Handoff — design tokens, specs, and the working relationship with engineering.

How the chapters fit together

  • 1–3 — the foundations. Visual hierarchy, colour, and typography. Nothing else works without these.
  • 4–6 — the system. Spacing and grid, then components and states, then design tokens.
  • 7–9 — the craft. Graphics and SVG, iconography, and motion.
  • 10–12 — the reality. Accessibility, responsive design, and performance as a design constraint.
  • 13–15 — shipping. Handoff, the design review, and building your own process.

Tools, and what this guide assumes

Tooling is discussed where it matters, but nothing here depends on a specific application. Figma is the most common design tool and is used for examples; Sketch, Adobe XD, Penpot and a text editor in your repository all work. The deliverables that matter — tokens, specs, SVGs, component states — are tool-independent.

Design tokens in version control beat any tool's export. A single JSON or YAML file of colour, type, spacing and radius values, committed beside the code, is the thing that actually prevents drift. It can be read by a designer, a developer, and a build step, and it diffs properly. A Figma library is a good authoring tool and a poor source of truth.

The one rule that matters most

If you remember one thing from this guide, remember this.

// Contrast is a hard requirement, not a preference.
//
//   4.5:1  normal text              (WCAG AA)
//   3:1    large text, 18.66px+ bold or 24px+ regular   (WCAG AA)
//   3:1    UI components and their boundaries           (WCAG 1.4.11)
//   7:1    normal text              (WCAG AAA)
//
// check EVERY pair you ship, in EVERY state, in BOTH themes, with
// real content, not placeholder. Grey-on-grey is the single most common
// defect in a "beautiful" design that fails the moment it ships.

1 · Visual Hierarchy and Layout

Before colour or type, a layout tells the user what matters. Get hierarchy right and the rest is decoration; get it wrong and no amount of polish rescues the page.

What hierarchy means on a screen

Hierarchy is the answer to: when someone's eye lands here, what do they read first, and what do they skip? Everything on the page is competing for attention, and hierarchy is how you decide who wins.

// a page has roughly 4-6 levels of importance. name them.
LEVEL 1  the page's single purpose: the main heading, the primary action
LEVEL 2  section headings
LEVEL 3  supporting content, secondary actions
LEVEL 4  metadata: timestamps, counts, helper text
LEVEL 5  chrome: nav, footer, legal

// if you cannot say which level something is, that is the design
// problem. "is this a tertiary button or a link?" means the
// hierarchy has not been decided.

// THE COMMON MISTAKE: too many levels competing
//  three things at LEVEL 1 on one screen. The eye cannot prioritise
//  three things, so it prioritises none of them and the user reads
//  none of it. Pick one.

The signals of importance

Five visual variables carry hierarchy. You can use all of them, but the point is that they should agree.

// 1. SIZE
//    the strongest signal. 32px is read before 16px, always.
//    if two things are the same size, the reader has no basis to
//    choose, so the design has failed to communicate priority.

// 2. WEIGHT
//    700 for headings, 400 for body, 300 for meta. Weight is cheaper
//    than size, so prefer it for sub-levels.
//    CAUTION: variable fonts let you pick any weight, which is a trap.
//    Six weights in one interface is noise. Three is a system.

// 3. COLOUR AND CONTRAST
//    the primary heading at full-contrast text colour; the secondary
//    at a lower one. A large, low-contrast heading reads as an
//    accident rather than a heading.

// 4. SPACE
//    the most underrated. Space around an element says "this is a
//    group, and this group matters". Space is what separates a
//    section from the next one without a line.
//    if two elements are 4px apart they are one group. if 32px
//    apart they are two things.

// 5. POSITION
//    top-left is read first on a left-to-right language. Anything in
//    the top-left region of the viewport gets attention that
//    something in the middle-right does not. Use it.

// THE RULE THAT MATTERS MOST
//    size, weight, colour, space and position must all point the same
//    way. The moment they disagree, the reader gets two conflicting
//    messages and reads neither.
//
//    a 28px light-grey heading with 4px of space above it says
//    "IMPORTANT but not really". That ambiguity is worse than
//    committing to one.

Proximity, grouping and Gestalt

The Gestalt principles are not decoration; they are how the eye segments a page. Use them and the layout explains itself. Ignore them and readers have to work out your structure.

// PROXIMITY: things near each other are perceived as a group
//   the workhorse. it is how you group a label with its input
<label>Email address</label>
<input type="email" name="email">
//   8px between them. 24px between this pair and the next.
//   the reader never has to be told which label belongs to which field.

// SIMILARITY: things that look alike are perceived as related
//   two cards with the same structure read as "the same kind of
//   thing". that is useful, so make all cards in a set look alike.

// CONTINUITY: the eye follows the smoothest path
//   a curved line that suggests a flow is followed. a straight
//   border that stops and starts is not.

// CLOSURE: the eye completes incomplete shapes
//   a circle with a 40px gap reads as "a circle", not "an arc".
//   use it for play buttons, avatars, and any shape that would be
//   expensive to draw completely.

// CONNECTION: connected elements are related
//   the most reliable of all. a line from a label to its control
//   removes all ambiguity. Use it where the association is critical.

// FIGURE AND GROUND: the thing you see depends on what you exclude
//   the most powerful and least used. a modal needs a scrim to
//   separate it from the page behind. A focused task needs
//   everything else visually suppressed.

// COMMON GESTALT MISTAKES
//   - equal spacing everywhere, so nothing groups
//   - a border between two related items, which actively separates them
//   - a container that is 8px from its first child and 40px from its
//     neighbour, so the reader picks the wrong parent

Alignment and the invisible grid

// every element on a page should align to something. almost nothing
// should be "roughly" placed.

// THE COLUMN GRID
//   12 columns, 24px gutters, a max-width container.
//   1200px content + 2 x 24px margins = 1248px page.
//   Components span column counts: a card is 4 columns, a hero is 8.

// WHY 12
//   it divides by 2, 3, 4 and 6, so you can make 2-up, 3-up, 4-up
//   and 6-up layouts with no half columns. 16 would give you powers
//   of two only; 10 is too coarse for a wide screen.

// IN CSS
.container { max-width: 1248px; margin-inline: auto; padding-inline: 24px; }
.grid {
  display: grid;
  grid-template-columns: repeat(12, minmax(0, 1fr));
  gap: 24px;
}
.span-4 { grid-column: span 4; }

// USE GRID OR FLEX, AND KNOW WHICH
//   Grid: two-dimensional. You know the rows AND columns up front.
//         Page layout, card grids, form layouts.
//   Flex: one-dimensional. You have a row or a column and want the
//         items sized to their content.
//         A toolbar of buttons, a row of chips, a centred logo.
//
// the mistake: flex for a page layout. It works until you need a
// second row to align with the first, and then you rewrite it in grid.

// ALIGNMENT AS A DECISION, NOT A DEFAULT
//   left-aligned text is faster to read for long passages. centred
//   text is fine for a headline under 60 characters and terrible for
//   anything longer, because the reader's eye has to find the next
//   line's start every time.
//   rule of thumb: if the text wraps to more than two lines, left it.

Density, and when to give space

// DENSITY is a decision about how much fits, and it should be
// deliberate per screen rather than global.

SPACIOUS   landing pages, marketing, reading, onboarding
           32-48px between sections, generous line-height, lots of air
COMFORTABLE dashboards, settings, most application UI
           16-24px between groups, 1.5 line-height
COMPACT    data tables, admin, IDE-like tools, trading
           8px between rows, 32px row height, tight but not cramped

// THE FAILURE MODE
//   one density for everything. A data table with 48px rows wastes
//   the screen and forces scrolling. A form with 12px rows is
//   unreadable and mis-clickable.
//
//   Set density per context. CSS makes this cheap with a data
//   attribute on a container:
.table[data-density="compact"] td { padding-block: 6px; }
.table td { padding-block: 12px; }

// TOUCH TARGETS
//   44 x 44 CSS pixels is the accepted minimum for anything tappable.
//   This is a hard floor on a phone, and a sensible floor on desktop
//   too. A 24px icon button needs padding, not a smaller hit area:
.icon-btn { width: 44px; height: 44px; display: grid; place-items: center; }
.icon-btn svg { width: 20px; height: 20px; }   // small icon, big target

Balance and visual weight

// visual weight is how "heavy" an element looks: dark, large, dense,
//   detailed, saturated. The page should be balanced overall.

// SYMMETRY
//   symmetric layouts feel stable and formal. Banks, government,
//   anything implying trustworthiness.
//   asymmetric layouts feel modern and dynamic. Editorial, product,
//   anything implying movement or progress.
//   Neither is better. Pick one and be consistent.

// OPTICAL BALANCE, not mathematical
//   a circle's perceived centre is slightly above its geometric
//   centre. a triangle's weight sits below its centroid. Text set in
//   a heavy weight optically overflows its box.
//   the practical rule: when something looks 2px off, nudge it. Do
//   not "fix" it back to the grid.
//
//   letter-spacing, optical:
//     -0.01em  on large display type   (tighten)
//      0.02em  on small caps and tracking (open it)
//     -0.02em  on headings at 24px+
//   This is why two designers using the same font and size produce
//   different-looking headings. The spacing is doing work.

// WEIGHT BALANCE CHECK, a genuinely useful exercise
//   squint at your page until it blurs, or convert it to greyscale.
//   What reads as dark blobs? Those are your focal points. If there
//   are more than two or three, there is no hierarchy and the page
//   has no entry point.
//   Then look at it in greyscale to check that your palette is not
//   doing the work that size and space should be doing.

Focal points and the eye path

// a page should have an entry point, a path, and an exit.

// THE ENTRY POINT
//   top-left by default, in left-to-right languages. top-right in
//   right-to-left. The reader's eye goes there first, so that is
//   where LEVEL 1 content goes.
//   if your most important element is bottom-right, you have a
//   problem. Options: move it, or accept that you need something
//   above it to lead the eye down.

// THE PATH
//   arrange elements so the eye flows: a strong element, space, the
//   next element, space. Avoid two equal-weight elements side by
//   side with nothing leading between them: the reader stops.
//
//   F-pattern for text-dense pages: left-to-right, then down a little,
//   then left-to-right. It happens because the eye returns to the
//   left margin. Design for it: put the important words at line
//   starts, not line ends.
//   Z-pattern for sparse pages: top-left, top-right, bottom-left,
//   bottom-right. It happens only if the elements are visually
//   connected. Without connectors it is just a guess.

// THE EXIT
//   every page needs an obvious next action, and it should be the
//   last thing the eye reaches. A form with a submit button in the
//   top-left, above the fields, makes people hunt.

// TESTING THE PATH
//   the 5-second test: show someone the page for 5 seconds, cover
//   it, and ask what it is for and what the main action is. If they
//   are wrong, your hierarchy is not doing its job. No amount of
//   user research is needed for this and it catches most problems.

Whitespace as a tool

// whitespace is not leftover space. it is the element that groups,
// separates and prioritises. It is the cheapest and most powerful
// tool in a design system.

// SPACE DOES FOUR JOBS
//   1. SEPARATE two unrelated things        24-32px
//   2. GROUP things that belong together   8-16px
//   3. PAD a container's contents          16-24px
//   4. BREATHE at the top of a section      48-64px

// THE INCONSISTENCY THAT MAKES A DESIGN LOOK AMATEUR
//   13px here, 16px there, 11px somewhere else. Nothing is wrong
//   individually and the whole thing feels accidental.
//   the fix is a scale, not a judgement call at each instance.

// A WORKING SCALE (8px base)
  4   micro: icon-to-label, inside a button
  8   tight: label to its control, chips
  16  base:  inside a card, between form fields
  24  group: between cards, between paragraphs
  32  section: between groups within a section
  48  block:  between sections
  64  major:  around major page bands
  96  hero:   above-the-fold breathing room

// THE INCREMENT RULE
//   scale values up, never down. if 24px is too much, use 16px.
//   if 16px is not enough, use 32px. Half-steps produce the noise
//   above, and no design in the history of design has ever needed
//   13px because of a real requirement.

// IF YOUR CONTENT DEMANDS IRREGULAR SPACING
//   a case study with images of different heights may need optical
//   adjustments. Use a small set of overrides (24, 28, 32) rather
//   than arbitrary values, and document them.

Exercises 1

  1. Take a page you designed and label every element with its hierarchy level, 1 to 5. Any element you cannot place is a hierarchy problem. Fix it by removing something, not by adding visual weight.
  2. Convert a design to greyscale. Identify what still reads. If your hierarchy disappears, your colour was doing the work size and space should do.
  3. Rebuild a component layout with a 12-column grid so that every element aligns to a column edge. Record how much time the alignment saved, because it is the argument for the grid.
  4. Run the 5-second test with five people. Record what they say the page is for and what they think the main action is. Where the answer is not unanimous, the hierarchy is ambiguous.
  5. Audit your spacing for arbitrary values. Replace every non-token value with the nearest scale step, and note which changes made it look worse — those are the places needing a scale extension.

2 · Colour Systems

Most colour problems are not "which blue" problems. They are role problems: not knowing which colours are load-bearing, so a designer adds a fifth grey and the interface stops meaning anything.

Colour is a system, not a palette

// A PALETTE is what you picked. A SYSTEM is what each colour DOES.
//
//   A design with 40 hex values in it has a palette and no system.
//   Adding one more button means picking one more hex value, and
//   nothing guarantees the new button matches the old one.
//
//   A system answers: for this job, which colour, and why.
//   Then any new component picks from the roles, and consistency
//   is automatic.

// the shift in practice
//   "use #3B82F6 for the button"      a decision about a component
//   "buttons use the primary role"     a decision about the system
//   the first requires a decision each time. the second does not.

The roles a colour can play

Every colour in a mature interface has one of these jobs. Define each role once.

// SURFACES - the layers things sit on
  surface/base        the page background
  surface/raised      a card, a panel: one step lighter
  surface/sunken      a well, a code block, a disabled field
  surface/overlay     a modal, a popover: above raised, with a scrim

// CONTENT - text and icons. three weights, no more.
  content/primary     headings and body text
  content/secondary   supporting text, labels
  content/disabled    non-interactive text
  content/on-primary  text ON a primary button. a separate role,
                      because it must contrast with the button, not
                      with the page.

// BORDERS
  border/subtle       dividers, table rules
  border/default      input outlines
  border/strong       focused or emphasised edges

// ACCENT - brand and state
  accent/primary      the brand action colour. ONE hue.
  accent/hover        its hover state
  accent/subtle-bg    a tinted background for selected rows and tags

// STATUS - these four are not brand colours and must never be swapped
  status/success      green
  status/warning      amber
  status/error        red
  status/info         blue

// THE RULE THAT PREVENTS MOST DISASTER
//   you have ONE accent colour, and a separate set of four status
//   colours. If your accent is blue and your info is blue, a blue
//   badge is ambiguous: is it your brand or is it informational?
//   Keep the accent visually distinct from the status set, or accept
//   that status always wins and never uses the accent hue.

Building a ramp

// a ramp is 50-950, following the Tailwind convention. it is not
// arbitrary: the steps are perceptually even, so 500 and 600 read as
// the same colour at different intensities.

  50    lightest: tinted backgrounds, dark-mode surfaces
  100   very light backgrounds
  200   disabled borders, subtle dividers
  300   placeholder text on light, disabled icons
  400   disabled content, decorative borders
  500   THE BASE. solid fills on light backgrounds.
  600   hover for a 500 fill. solid fills on dark backgrounds.
  700   text on light backgrounds, active states
  800   hover for a 600 fill
  900   headings on light backgrounds
  950   darkest: dark-mode text

// WHY EVEN STEPS MATTER
//   "brand blue" as a single hex value has to be darkened by hand for
//   hover and lightened for a subtle background, and each of those
//   hand-adjustments drifts. A ramp forces the relationships.

// HSL, and when it is the right tool
//   HSL is intuitive: hue (what colour), saturation (how vivid),
//   lightness (how light).
//   HSL's lightness is NOT perceptual. hsl(210 90% 50%) and
//   hsl(90 90% 50%) have the same L but very different perceived
//   lightness, because yellow is inherently lighter than blue.
//
//   so: HSL to build a ramp by hand, then convert to hex or OKLCH and
//   store THAT. Do not compute hover states with HSL arithmetic in
//   production code; the results will be uneven across hues.

// OKLCH, and why it is the better modern option
//   OKLab is perceptually uniform: equal steps in L look equal to the
//   eye, across every hue.
oklch(0.7 0.15 250)      lightness chroma hue
// L  0 (black) to 1 (white)
// C  0 (grey) to about 0.37 (most vivid hues)
// H  0-360 degrees, same as a colour wheel
// with OKLCH, "5% lighter" looks 5% lighter in yellow and in blue.
// the ramp comes out even by construction.
--brand-500: oklch(0.62 0.19 255);
--brand-600: oklch(0.55 0.19 255);   /* a real 5% step, not a guess */

Naming by role, not by hue

// THIS IS THE SINGLE MOST IMPORTANT DECISION IN A COLOUR SYSTEM
// and it is one every design system gets wrong initially.

BAD
  --blue-500: #3b82f6;
  --gray-100: #f3f4f6;
  .button-primary { background: var(--blue-500); }
  .button-secondary { background: var(--gray-100); }
  // now the brand changes and you are hunting 200 usages

GOOD
  --color-bg: #ffffff;
  --color-surface: #f9fafb;
  --color-text: #0f172a;
  --color-text-muted: #64748b;
  --color-accent: #3b82f6;
  --color-accent-hover: #2563eb;
  --color-border: #e2e8f0;
  .button-primary { background: var(--color-accent); }

// WHY IT IS BETTER, CONCRETELY
//   1. re-theming is a token swap, not a codebase search
//   2. a component cannot misuse a role. If .button-danger uses
//      --color-accent, that is a token change.
//   3. dark mode is a second token file, not a second stylesheet
//   4. roles survive a brand change, hex values do not

// THE THREE-LAYER PATTERN, which is how you get both
//   layer 1  PRIMITIVES: --blue-500, --slate-100. never used directly
//   layer 2  SEMANTIC:   --color-accent, --color-text-muted
//   layer 3  COMPONENT:  --button-bg, --input-border. only if a
//                          component genuinely needs an exception
// components consume layer 2. Primitives are for the token file only.

Contrast, properly

// the ratios that matter (WCAG 2.2)
  4.5:1   body text under 18.66px bold / 24px regular
  3:1     large text at those sizes
  3:1     UI component boundaries, icons that carry meaning
  7:1     AAA for body text

// compute it, never estimate it. your eyes are bad at this and your
// monitor is calibrated differently from your user's.
function contrast(hex1: string, hex2: string): number {
  const L = (hex: string) => {
    const [r, g, b] = [1, 3, 5].map((i) => parseInt(hex.slice(i, i + 2), 16) / 255)
      .map((c) => (c <= 0.03928 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4));
    return 0.2126 * r + 0.7152 * g + 0.0722 * b;
  };
  const a = L(hex1), b = L(hex2);
  return (Math.max(a, b) + 0.05) / (Math.min(a, b) + 0.05);
}
contrast('#64748b', '#ffffff');   // 4.76:1  passes for body text
contrast('#94a3b8', '#ffffff');   // 2.56:1  FAILS. still looks "grey text".

// WHERE CONTRAST FAILS, RANKED BY HOW OFTEN I SEE IT
//   1. MUTED TEXT ON TINTED BACKGROUNDS. light grey on a grey card is
//      usually ~2:1. The card background is not white, so you must
//      check against the card, not the page.
//   2. PLACEHOLDER TEXT. browsers render it at ~54% opacity by
//      default, which lands most designs below 4.5:1. Set it
//      explicitly and often it needs to be darker than you expect.
//   3. DISABLED TEXT. WCAG exempts disabled controls, but users still
//      need to read them. 3:1 is a reasonable floor.
//   4. ICONS WITHOUT LABELS. An icon that is the only way to do
//      something needs 3:1 as a non-text contrast requirement.
//   5. TEXT OVER IMAGES. You cannot check a static ratio; you need a
//      scrim or a gradient. See ch7.

// CHECK ALL OF THEM
//   a contrast checker must run over EVERY token pair, in BOTH
//   themes, in EVERY state including hover and disabled. A single
//   automated pass at build time catches what a manual review misses
//   and what a designer will not catch at all.

Add a contrast check to your build. A script that loads the token file, tests every declared foreground/background pair, and fails CI on a violation. It takes an hour to write and it will catch a contrast regression in a component someone added at 6pm, which no review process reliably does.

Dark mode is a re-design

// the common failure: invert the light theme. this produces
//   pure white text on pure black, which is harsh, and pure black
//   surfaces, which makes elevation impossible to see.

// FOUR THINGS THAT BREAK IN A NAIVE INVERSION

// 1. ELEVATION INVERTS
//   light mode: raised surfaces are LIGHTER than the page, so they
//   appear to come forward.
//   dark mode: raised surfaces must be LIGHTER too, because
//   "closer to the light source" is how we read depth. But the page
//   is already dark, so "lighter" means a lighter dark.
body      { background: oklch(0.16 0.01 250); }   /* not black */
surface   { background: oklch(0.20 0.012 250); }  /* raised: lighter */
overlay   { background: oklch(0.24 0.014 250); }  /* above raised */
scrim     { background: rgb(0 0 0 / 0.6); }      /* darkens, not lightens */

// 2. SHADOWS STOP WORKING
//   there is nothing to cast a shadow onto when everything is dark.
//   depth comes from surface lightness and, optionally, a subtle
//   1px light border on raised surfaces.
.card { box-shadow: none; border: 1px solid var(--color-border); }
/* in dark mode, a light border reads as an edge. that is the
   substitute for the shadow you cannot see */

// 3. SATURATION BLOOMS
//   a colour that looks calm on white looks neon on near-black.
//   the same hex is a different colour perceptually. reduce
//   saturation in dark mode, typically by 10-20%, and use lighter
//   steps of the same ramp:
//   light:  blue-600   dark:  blue-400     (lighter, less saturated)

// 4. PURE BLACK AND PURE WHITE ARE WRONG
//   #000 on #fff is 21:1, which is glare. #fff on #000 is 15:1 in
//   the other direction and is also harsh.
//   cap both ends: text around 87-92% lightness, backgrounds 6-12%.

// THE PRACTICAL RULE
//   do not derive dark mode by transforming light mode in code.
//   write a second token file, deliberately. The mapping is not
//   1:1 and the transform cannot know your intent.
// :root { --color-bg: #fff; --color-accent: oklch(0.55 0.19 255); }
[data-theme="dark"] { --color-bg: oklch(0.16 0.01 250); --color-accent: oklch(0.72 0.14 255); }

Colour vision deficiency

Around 1 in 12 men and 1 in 200 women have some form of colour vision deficiency. Red-green is the common one, and the most common design failure relying on it.

// WHAT YOU CANNOT DO
//   red = error, green = success, with no other difference. to a
//   deuteranope these are the same colour. 8% of men will see a
//   field validation state as neutral.

// WHAT YOU MUST DO: never encode meaning in hue alone
//   the rule is "colour plus something else". The something else
//   can be an icon, a word, a shape, a position or a pattern.

// status indicators, done properly
  error    red    + a warning triangle icon   + the word "Error"
  success  green  + a check icon              + the word "Saved"
  warning  amber  + an exclamation icon       + the word "Pending"

// form validation
  .field--error input { border-color: var(--status-error); }
  .field--error .error-msg::before { content: "!\00a0"; }  /* not colour alone */
  .field--error .error-msg { color: var(--status-error); }
// the red border, the icon and the message. remove the colour and it
// still works.

// CHARTS - the hardest case, because there is no text label
//   - do not use a rainbow. it is unreadable for CVD and bad for
//     greyscale printing
//   - use a sequential ramp for ordered data: light to dark of ONE hue
//   - use a small, CVD-safe categorical set for unordered data
//   - add direct labels on the lines or bars where possible. A legend
//     forces the reader to do arithmetic; a label does not.
//   - add patterns or marker shapes as a second channel:
//     solid line, dashed line, dotted line
//   - test by converting to greyscale. If the series merge, you need
//     labels or patterns.

// TESTING
//   - free browser extensions simulate each deficiency
//   - macOS and iOS have accessibility filters in display settings
//   - Windows has a colour filter setting
//   - most importantly: print it in greyscale. A chart that survives
//     greyscale survives everything.

Exercises 2

  1. Audit a design and list every hex value used. Count how many are load-bearing and how many are one-off accidents. Aim to end with fewer than 30 primitives.
  2. Build a full colour token file with a 950-step ramp and semantic roles, in both light and dark. Verify every declared pair meets 4.5:1 for text and 3:1 for borders, in both themes.
  3. Convert a status-indicator component so it never relies on colour alone. Test it with a colour-vision simulator and in greyscale.
  4. Take a dark theme you produced by inverting a light one and fix the elevation, the saturation and the pure-black problem. Measure the contrast change.
  5. Write a CI script that parses your token file, tests every foreground/background pair, and fails the build on a violation. Add one deliberate violation and confirm it fails.

Type is where most of a design's quality is visible and most of its accessibility lives. The specifics matter more than the taste, and the specs are knowable.

The type scale

// a scale is a set of sizes with a consistent ratio. pick a base and
// a ratio and stop deciding per component.

BASE 16px, RATIO 1.25 (minor third)
  xs    10.24   0.64rem   metadata, legal
  sm    12.80   0.80rem   helper text, captions
  base  16.00   1.00rem   body
  lg    20.00   1.25rem   lead paragraphs, h4
  xl    25.00   1.56rem   h3
  2xl   31.25   1.95rem   h2
  3xl   39.06   2.44rem   h1
  4xl   48.83   3.05rem   display

BASE 16px, RATIO 1.333 (perfect fourth) - bolder, good for dashboards
  sm    12      0.75rem
  base  16      1.00rem
  lg    21.3    1.33rem
  xl    28.4    1.78rem
  2xl   37.9    2.37rem
  3xl   50.6    3.16rem

// THE ROUNDED VERSION, which is what most systems actually ship
// because 1.333 at 16px is 21.3 and nobody types that
  12   14   16   20   24   32   40   48   64

// a workable compromise: a 1.2 ratio, rounded
  12   14   16   19   23   28   34   41   49

// WHY A SCALE MATTERS MORE THAN THE EXACT NUMBERS
//   it makes the page feel systematic. 16/24/32 with consistent 1.5
//   line height reads as designed. 15/22/31 with inconsistent spacing
//   reads as a Word document. Nobody can name the difference; everybody
//   feels it.

// WEIGHT AND THE SHAPE OF A HIERARCHY
//   400 body, 600 h4/h5, 700 h1-h3 is a modern default.
//   300 only for very large display type, never for body.
//   800/900 for hero numbers, sparingly. A fully bold page has no
//   emphasis left to give.

Line height, the real rule

Line height is not a constant. It scales inversely with size, and getting this wrong is the most common typographic error.

// the rule
   large text needs LESS relative leading
   small text needs MORE

  size     line-height    notes
  12px     1.6            small text needs air to be legible
  14px     1.6
  16px     1.5            the workhorse. 1.5-1.7 is the sweet spot
  20px     1.5
  24px     1.4
  32px     1.25           headings want tightness
  48px     1.1
  64px     1.05

// 1.5 with a 16px font is 24px of leading: 16px of glyphs and 8px of
// space, 4px each side. At 48px with 1.5 you get 72px leading, so 24px
// between lines, and the paragraph falls apart into disconnected
// lines. That is why big headings look wrong at a fixed 1.5.

// the summary form: unitless line-height
body    { font-size: 1rem; line-height: 1.5; }     /* 24px */
h1      { font-size: 2.5rem; line-height: 1.15; }  /* 46px */
h2      { font-size: 2rem;   line-height: 1.2; }   /* 38px */
h3      { font-size: 1.5rem; line-height: 1.3; }
// unitless is relative to the element's own font-size, so a heading
// gets correct leading automatically. NEVER use a fixed px line-height
// on a heading: it breaks the moment someone changes the font size.

// LINE HEIGHT AND THE ELEMENT ABOVE
//   the space above a heading should be greater than the space below
//   it, because the heading belongs to what follows. 32px above,
//   16px below. This single rule fixes most "my headings feel wrong"
//   reports, and it is worth more than changing the font.

Measure and line length

// measure is line length: how many characters sit on one line.
// the target is 45-75 characters for body text.

.prose {
  max-width: 65ch;        /* ch is the width of a "0", which is
                             proportional to the font. this is the
                             correct unit for line length, not px. */
}

/* or explicitly, for a two-column page */
.column { max-width: 680px; }

/* WHY ch AND NOT px OR em
   65ch scales with the user's font size. 65em would be 65 times the
   font size, which is absurd. 65px is 65px whatever the font, so a
   user at 200% zoom gets 130 characters per line and cannot read it. */

// WHEN TO BREAK THE RULE
//   - a sidebar or card: 30-45ch is fine
//   - a table cell: one or two lines, and that is acceptable
//   - a UI label: as long as the string needs
//   - a code block: horizontal scroll, never wrap. Wrapping code
//     changes its meaning.
//   - a form label: as long as it needs
//
// full-width body text at 1400px is roughly 180 characters per line.
// That is genuinely hard to read, and it is why a wide container with
// no max-width on the prose looks "cheap" even when nothing else is
// wrong with it.

// READING WIDTH ON MOBILE
//   a phone at 390px with 16px type gives about 45 characters, which
//   is at the bottom of the range. Raising body text to 17-18px on
//   mobile improves it, and is worth doing.

Pairing families

// two families is the practical maximum. three is a curiosity.

// CATEGORY A: a neutral sans for everything
//   Inter, system-ui, -apple-system, "Segoe UI", Roboto, Helvetica
//   + the point: the system stack costs zero bytes and renders
//     natively on every platform
body { font-family: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif; }
//   "font-family: Inter" alone will make macOS and Windows look
//   different, because neither ships Inter. Either bundle it or use
//   the stack. Half-and-half is the worst outcome.

// CATEGORY B: display for headings, neutral for body
//   display   Playfair Display, Fraunces, Source Serif 4, a distinctive sans
//   body      Inter, Source Sans 3, system-ui
//   the rule for success: the two must differ in more than weight.
//   same-family at different weights is a common failure and looks
//   accidental.

// CATEGORY C: serif for body, sans for UI
//   body      Source Serif 4, Literata, Georgia, Charter
//   ui        Inter, system-ui
//   best for: long-form, articles, documentation
//   the risk: serif at 14px in a data table is unreadable. Use the
//   sans for anything dense.

// CATEGORY D: mono as a third voice
//   mono      JetBrains Mono, ui-monospace, SFMono-Regular, Menlo
//   use for: code, ids, versions, anything that is literally data
//   do not use for body. And keep it narrow: a mono used for
//   everything reads as a terminal, not a product.

// MONOSPACE
//   for code and identifiers, not as a design choice
//   code, kbd, samp, pre
code, kbd, samp, pre { font-family: var(--font-mono); font-size: 0.9em; }
// 0.9em because monospace glyphs are visually larger than the same
// point size in a proportional face. At 1em code looks too big.

Web fonts without the cost

A web font is a performance decision as much as a design one. This is the part a designer is uniquely positioned to get right, by specifying subsets and weights.

// the cost of a font
//   a typical family: 4 weights, 2 styles = 8 files, 400KB+ of WOFF2
//   full Latin + Cyrillic + Greek can exceed 1MB
//   on a phone that is several seconds of blocking text

// 1. SUBSET. Most interfaces use 60-80 Latin glyphs. A subset of
//    exactly those is 15-25KB instead of 200KB.
//    do it in the build, per-language: a Japanese site needs a
//    different strategy from an English one.

// 2. LIMIT WEIGHTS. Two is usually enough: 400 and 700.
//    Every weight you add is a file and a request. If your design
//    needs 300/400/500/600/700/800, it needs fewer weights, not more.
//    A variable font is ONE file covering the whole range - the right
//    answer for a modern build.

// 3. PRELOAD THE CRITICAL ONE
//    the weight used above the fold, in the subset actually needed
<link rel="preload" href="/fonts/inter-400.woff2" as="font"
      type="font/woff2" crossorigin>

// 4. USE font-display SWAP, not BLOCK
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-400.woff2') format('woff2');
  font-weight: 400;
  font-display: swap;      /* show fallback immediately, swap in when
                              ready. BLOCK hides text for up to 3s
                              and is the cause of most "the site just
                              sits there" reports */
  size-adjust: 100%;       /* metric override, see below */
}

// 5. MATCH THE FALLBACK, or the swap will jump
@font-face {
  font-family: 'Inter Fallback';
  src: local('Arial');
  size-adjust: 107%;      /* scale the fallback to Inter's metrics */
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}
/* this makes the fallback occupy the same space as Inter, so the swap
   is nearly invisible. It is the single best thing you can do for
   perceived performance */

// 6. SUBSET BY LANGUAGE using unicode-range, so the browser downloads
//    only what the page needs
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-cyrillic.woff2') format('woff2');
  unicode-range: U+0301, U+0400-045F, U+0490-0491, U+04B0-04B1, U+2116;
}

Optical adjustments

// letters are not rectangles. the eye reads them optically, and a
// technically-correct setting can look wrong.

// LETTER-SPACING, by role
   DISPLAY  32px+     -0.02em to -0.03em   tighten; large type sets loose
   HEADING  24-31px   -0.015em
   BODY     16-20px    0                    leave it alone
   SMALL    14px      0                     leave it alone
   CAPS / TRACKING   0.06em to 0.12em      open it up; caps have no
                                           ascender/descender help
   ALL CAPS < 16px    do not use            unreadable

h1 { font-size: 3rem; letter-spacing: -0.025em; }
.eyebrow { text-transform: uppercase; letter-spacing: 0.1em; font-size: 0.75rem; }

// FONT WEIGHT FOR SMALL TEXT
//   400 is too light below 16px. Use 500 for small UI text.
//   .label { font-size: 0.75rem; font-weight: 500; }

// OPTICAL ALIGNMENT
//   text inside a button, badge or pill is rarely optically centred,
//   because glyphs have uneven side bearings. Quote marks, commas and
//   italics stick out. This is why a carefully centred label can look
//   off by a pixel. Nudge it. Optical beats geometric.

// NUMERALS IN TABLES
   font-variant-numeric: tabular-nums;   /* same width per digit, so
                                           columns line up */
   always for anything numeric: tables, prices, counters, timers
   never for running prose

// TUNED FOR NUMBERS
   font-variant-numeric: proportional-nums;  /* in body text, so
                                                 1 does not dwarf 8 */

Fluid type

// fluid type scales with the viewport, with clamp() setting the bounds
h1 {
  /* min | preferred using vw | max */
  font-size: clamp(1.75rem, 1.1rem + 3.2vw, 3.5rem);
}
// 280px viewport -> 1.75rem (28px)
// 1280px viewport -> about 2.9rem
// 1920px viewport -> 3.5rem (56px), capped

// the formula, so you can compute any step
//   preferred = min + (max - min) * (vw - minVw) / (maxVw - minVw)

// THE CRITIQUE, and it is fair
//   pure vw scaling is bad on its own: a 360px phone and a 320px phone
//   get different sizes, so the layout is unpredictable, and a 4K
//   monitor gets enormous text unless capped. clamp() fixes both.

// PREFER THIS INSTEAD for most designs
//   three or four fixed sizes with a breakpoint between them.
//   Predictable, and the designer can see exactly what ships.
//   Fluid is for a marketing page where the payoff is a continuous
//   feel. For an application, fixed steps are more honest.

// AVOID clamp() ON LINE HEIGHT
//   line-height: 1.2 is fine. A fluid line-height produces awkward
//   leading at the extremes. Set the ratio and let the size move.
//   But DO let space-around fluid, using the same clamp formula.

Readability checklist

// run this against any text-heavy design

[ ] body text is at least 16px, 18px is better for long-form
[ ] line length is 45-75 characters (measure with a ch-based max-width)
[ ] line height is 1.5 for body, lower for headings
[ ] body text meets 4.5:1 against its ACTUAL background
    (check tinted cards, not just the page)
[ ] no more than two type families, plus mono for code
[ ] weights limited to 400 and 700, plus 500 for small UI text
[ ] letter-spacing is 0 for body text
[ ] no all-caps below 16px
[ ] font-display: swap, with a metric-matched fallback
[ ] the font is subset, and total font payload is under 150KB
[ ] tabular-nums on any number in a column
[ ] headings have more space above than below
[ ] the type still works at 200% browser zoom
[ ] the type still works in forced-colours / high-contrast mode
[ ] italics work: a real italic face exists, or faked ones are avoided
[ ] line breaks never orphan a single word
    orphans: 2; widows: 2;  /* CSS, worth knowing about */

Test type at 200% zoom before you ship. WCAG 1.4.4 requires text to be resizable to 200% without loss of content or function, and it is the single most common accessibility failure in production. A 16px base with a 65ch measure survives it; a 24px heading with a fixed 600px container does not.

Exercises 3

  1. Build a type scale for a documentation site: base 17px, six steps, a consistent ratio. Apply it to a real page and check the hierarchy reads at a glance in greyscale.
  2. Audit your line heights. Set body to 1.5, headings to 1.15–1.3 by size, and check the space above and below every heading. Note how many layouts improve without touching the font.
  3. Convert a fixed-width text column to a ch max-width. Zoom to 200% and verify the measure stays in the 45–75 range rather than wrapping to four characters.
  4. Implement a metric-matched fallback with size-adjust and ascent-override, then record the CLS from a cold cache with a throttled connection before and after.
  5. Replace a two-weight system with a variable font, or prove your current system needs no more than two weights. Measure the payload either way.
