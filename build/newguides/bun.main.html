0 · Orientation

0.1 What Bun is, and what it replaces

Bun is a single native binary that does four jobs: it runs JavaScript and TypeScript, installs packages, bundles code for a browser or a server, and runs tests. That these are one product rather than four tools glued together explains almost every design decision in the rest of this guide.

Four tools, one process

A conventional JavaScript project has four moving parts that do not know about each other. A runtime executes the code, a package manager resolves the dependency graph, a bundler rewrites the source graph into something a browser can load, and a test runner discovers and executes assertions. Each is installed separately, versioned separately, and — because they do not share a parser, a module resolver or a cache — each re-reads and re-parses the same files. Bun subsumes all four. The module resolver used by bun run is the same resolver used by bun build and by bun test, so a path alias, a package.json condition or an .env file behaves identically in every mode. When a build works but a test does not, the difference is your code, not two divergent toolchains.

What it is not

Bun is not a framework. It has no opinion about UI, routing or state management, and it does not replace React, Vue, Next.js or Express. It is also not a drop-in replacement for every Node.js deployment: the package manager, the bundler and the test runner are Bun-specific, and the runtime is a different engine from Node's. Treat the four capabilities as separable. Many teams adopt only bun install first, because it is fast and reversible, and never run their application under the Bun runtime at all. That is a supported, common path — passing --bun to npm-style scripts is what forces the Bun runtime, and omitting it keeps Node in charge.

Why it is fast

Three things dominate Bun's performance story. First, the engine: Bun embeds WebKit's JavaScriptCore rather than V8, and JSC's start-up cost is substantially lower, which is visible on short-lived scripts and CLI tools where boot time is most of the wall clock. Second, everything is native: the package manager, the bundler and the test runner are compiled Rust, not JavaScript, so they do not pay a JavaScript boot cost before doing any work. Third, the runtime ships implementations of the APIs you reach for most — an HTTP server, SQLite, a shell, hashing — so fewer npm packages have to be downloaded, parsed and initialised before your first line runs. Bun 1.4 (August 2026) replaced the Zig core of the runtime with Rust; the external behaviour is unchanged, but the toolchain and the binary's memory profile are not.

Fast start-up is the reason Bun is pleasant for scripts and tests, but it is not a benchmark of throughput. For a long-running server, engine choice matters far less than your query patterns and I/O handling.

0.2 Installing, pinning and upgrading Bun

Installation is a single binary on your PATH. The interesting part is not the install command — it is pinning a version so that a build that passes locally also passes in CI six weeks later.

Platform installers

On macOS and Linux the installer is a shell script; it needs unzip on the machine. On Windows the equivalent is a PowerShell one-liner that requires Windows 10 version 1809 or newer. Both put bun in a user-level directory and add it to PATH; you may need to restart your shell afterwards. Package managers work too — npm, Homebrew and other registries all carry a Bun package if you prefer a manager you already use.

# macOS / Linux
curl -fsSL https://bun.com/install | bash

# Windows (PowerShell)
powershell -c "irm bun.sh/install.ps1 | iex"

# via npm, if you would rather not use the script
npm install -g bun

Checking and pinning the version

Two commands report version information, and they answer different questions. bun --version prints the semantic version such as 1.4.3; bun --revision prints the exact build revision, which is what you paste into a bug report. In CI, pin the version rather than installing latest, or a release on the morning of a deadline can change your build. The official Docker image tags make this easy: a floating oven/bun:1 tracks the newest 1.x, while oven/bun:1.4.3 is immutable. Applications that ship a compiled binary should pin the exact patch, because the compiled output embeds the runtime.

# shell
bun --version      # 1.4.3
bun --revision     # 1.4.3+abcdef123
bun upgrade        # update to the latest release

Upgrading and rolling back

bun upgrade replaces the binary in place; pass --canary to move to the nightly line when you need a fix that has not shipped yet. Rolling back is deliberately unglamorous: re-run the installer with the version you want, or install a pinned release. This matters when an upgrade changes behaviour. Bun follows semantic versioning but ships substantial features in minor releases — 1.2 added HTML imports and routes, 1.3 rebuilt the dev server and added database clients, 1.4 rewrote the core — so "it is only a minor bump" is not a safe assumption in this project's history.

0.3 Creating a project and running scripts

A Bun project is a normal directory with a package.json. What changes is that you rarely need a separate TypeScript compiler, a bundler config or a test config file.

bun init and what it writes

bun init scaffolds a project: a package.json, a tsconfig.json tuned for Bun, an index.ts entry point and an .gitignore. The tsconfig.json is the part worth reading, because it is what makes bun run file.ts type-check cleanly in your editor without a build step. It targets the latest ECMAScript and enables the module resolution rules Bun uses, so the editor and the runtime agree about where @/lib/db points. Pass --react, --vue or similar flags to pull in the matching template.

# shell
bun init            # interactive scaffold
bun init --yes      # accept defaults, no prompts
bun init --react    # React template

Defining and running scripts

Scripts live in the scripts field exactly as they do under npm, and bun run <name> executes them. Bun runs the named binary from node_modules/.bin when the script names one, and otherwise falls back to the Bun runtime. That fallback is the important detail: "test": "jest" runs Jest under the Bun runtime, which is usually what you want for compatibility, but "dev": "node server.js" will run Node if Node is installed unless you force Bun with --bun. Bun does not require a run keyword for many script names; bun dev is shorthand for bun run dev. Be explicit in CI anyway — ambiguity is cheap to remove and expensive to debug.

// package.json
{
  "name": "my-app",
  "scripts": {
    "dev": "bun --watch src/index.ts",
    "build": "bun build src/index.ts --outdir dist --target bun",
    "test": "bun test"
  }
}
# shell
bun run dev          # run the dev script
bun dev              # shorthand for the same thing
bun --bun run dev    # force the Bun runtime inside the script
bun run src/cli.ts   # run a file directly, no script needed

Environment defaulting

Bun loads .env automatically before your code runs, so Bun.env.DATABASE_URL is populated without a library such as dotenv and without an import. Later chapters cover the exact precedence, but the orientation-level takeaway is that a fresh project usually needs no configuration file at all: no bundler config, no test config, no environment loader. If you are counting lines of configuration you can delete, that is the largest single win.

1 · The runtime

1.1 Running code: bun run

bun run is the entry point for everything. It runs scripts, files and binaries, resolves TypeScript and JSX on the fly, and defaults to a fast start-up without a compile step.

Scripts, files and binaries

bun run does three different things depending on the argument, and knowing which it will pick saves time. Given the name of a script in package.json, it runs that script. Given a path to a file, it executes that file with the Bun runtime — a .ts, .tsx, .jsx or .js file all work without configuration. Given the name of an executable on PATH or in node_modules/.bin, it runs that binary. When a script and a binary share a name, the script wins, because a project's own definition should not be shadowed by a globally installed tool.

# shell
bun run build            # the "build" script from package.json
bun build                # shorthand for the same script
bun run ./src/cli.ts     # execute a TypeScript file directly
bun run --bun vite dev   # run the vite binary under the Bun runtime

Passing arguments and environment

Everything after the script name is forwarded to the script verbatim, which means -- is not required the way it is with npm. Flags that belong to Bun itself must come before the script name. This distinction is a common source of confusion: bun run dev --port 3000 passes --port 3000 to your dev server, while bun --watch run dev tells Bun to watch. Environment variables are inherited from the parent process; anything defined in .env is merged in, and an inline assignment such as NODE_ENV=production bun run start works on Windows as well as POSIX shells, because Bun parses it rather than relying on the shell.

Transactions in a longer pipeline

Sequential steps are usually written as separate entries in scripts and composed with the shell's &&, but that is not portable to Windows cmd. For a cross-platform pipeline that stops on the first failure, write a small TypeScript driver and let Bun run it, or use the Bun shell, which implements &&, || and pipelines itself and therefore behaves identically on every platform. The next chapter covers the shell in detail; the point here is that "just use npm scripts" is not required.

1.2 The engine, globals and TypeScript

Bun runs on JavaScriptCore. The practical consequences of that choice — and of the runtime's built-in TypeScript support — decide what you can delete from a typical project.

JavaScriptCore, not V8

Node.js and Bun share a language but not an engine. Node embeds V8; Bun embeds JavaScriptCore, the engine from WebKit. The visible differences are small at the language level — both implement modern ECMAScript — but they show up in two places. Start-up is markedly faster with JSC, which is why CLI tools feel instant. And occasionally a V8-specific escape hatch is absent or spelled differently, so code that violates a specification but happened to work on V8 can behave differently. Writing to the specification rather than to V8's quirks is the safe rule, and it is also what makes the same file run under both runtimes.

TypeScript and JSX without a build

Bun parses TypeScript and JSX directly. There is no ts-node, no tsx, no esbuild step required to run a .ts file — bun run server.ts simply works. Crucially, Bun does not type-check. It strips types and runs. That is a deliberate speed choice and it means type errors do not stop execution; you still need a checker (the editor's TypeScript service, or bun check in 1.4) for correctness. Configure JSX per file with a pragma comment: @jsxRuntime classic, @jsxRuntime automatic or @jsxImportSource preact at the top of the file selects the transform, and the choice can differ per file, which is useful when a monorepo mixes React and Preact.

// **/*.tsx uses the automatic runtime by default
/** @jsxImportSource preact */
import { render } from "preact";

export function App() {
  return <h1>Hello</h1>;
}

Globals you get for free

Several APIs are available without an import: Bun itself (a namespace holding Bun.serve, Bun.file, Bun.write, Bun.spawn, Bun.password and much more), Bun.env for environment variables, and the web-standard globals fetch, Request, Response, Headers, WebSocket, FormData, URL, TextEncoder and AbortController. A few Node globals are present too, most notably process and Buffer, for compatibility. Preferring the web-standard spellings keeps code portable to browsers, Deno, workers and Node, in roughly that order of likelihood.

Type definitions for the built-ins ship with the runtime package. Add "types": ["bun"] (or a reference directive) to tsconfig.json and your editor will autocomplete Bun.serve and friends in every file.

1.3 Watch mode and hot reload

Bun can restart a process when files change, or reload modules inside a running process without a full restart. Choosing the right one is the difference between a two-second loop and a two-hundred-millisecond loop.

--watch: restart the process

bun --watch src/server.ts watches the files that were imported and restarts the process when one changes. It is the right tool for a server whose start-up is cheap and whose state is disposable. Because it restarts the whole process, everything is reset: caches, connections and in-memory counters. Watch mode is careful about the file graph — it re-runs the import that changed rather than the whole program where it can, and it leaves the terminal history in place so you can scroll back through previous restarts.

# shell
bun --watch src/server.ts     # restart on change
bun --hot src/server.ts       # hot reload without a restart

--hot: reload modules in place

bun --hot keeps the process alive and re-evaluates changed modules, preserving global state between edits. That is a genuine win when start-up is expensive — reading a large file, warming a cache, opening a database pool — but it demands that your code tolerate being re-evaluated. A module-level connection created once at import time will be created again on each reload unless you guard it. The reliable pattern is to store long-lived resources on a global keyed by a stable name, then reuse them across reloads. A module-scoped let will not survive; a property on globalThis will.

// server.ts — survive hot reloads
const key = "__db__";
const pool = (globalThis as any)[key] ??= await createPool();

export function query(sql: string) {
  return pool.query(sql);
}
Hot reload re-runs modules, not the whole program. If two modules capture references to each other at import time, a reload can leave one holding a stale reference. Prefer functions over captured objects, or restart with --watch when in doubt.

1.4 Debugging, inspection and profiling

Because Bun is a normal runtime with an inspector protocol and a rich console, most debugging needs no extra tooling — but the flags are not the ones Node users reach for by reflex.

The inspector and DevTools

bun --inspect src/server.ts starts the process and opens a WebSocket inspector on the standard port. Browsers' DevTools can attach to it, giving you breakpoints, a console, a heap snapshot and a profiler for a server-side process. Pass --inspect-brk to break on the first line, which is what you want for a script that fails immediately or whose input arrives from a pipe. The protocol is Chrome DevTools Protocol, so the tools you already use for front-end debugging work unchanged; only the URL you paste differs from the Node equivalent.

# shell
bun --inspect src/server.ts        # attach DevTools
bun --inspect-brk src/cli.ts       # break before the first statement
bun --inspect-wait src/server.ts   # wait for a debugger to attach

Reading values with console and Bun.inspect

Bun's console.log understands more than primitives: it prints objects with colour and depth, and Bun.inspect(value) returns that formatted string so you can embed it in your own output. Bun.inspect.table(data) renders an array of objects as aligned columns, which is far faster to read than a wall of JSON when you are comparing rows. Error stacks are source-mapped, so a stack from TypeScript points at the .ts line rather than a compiled equivalent. For production, prefer structured logging — write JSON to stdout — because the pretty-printer is for humans, and log collectors are not humans.

// inspect anything, including circular structures
console.log(Bun.inspect({ a: 1, nested: { b: 2 } }));

// render rows as a table
console.table([{ name: "ada", role: "engineer" }]);

// structured logging for a collector
console.log(JSON.stringify({ level: "info", msg: "boot", pid: process.pid }));
console.table and Bun.inspect.table are convenience, not a formatting contract. Column order follows object key order and is not stable across inputs, so never parse your own log output.

2 · The package manager

2.1 Installing dependencies

bun install reads package.json, resolves the graph, writes a lockfile and links node_modules — in one pass, with a cache shared across projects.

What one install actually does

A bare bun install satisfies every dependency class at once: dependencies, devDependencies, optionalDependencies and peerDependencies. That differs from npm, which historically left peer dependencies to the consumer and treats a production install as a separate mode. To skip development dependencies, pass --production; that is the flag a runtime container needs, and forgetting it is the most common reason a production image is hundreds of megabytes larger than the code it runs. The cache lives outside the project, so a second checkout of the same dependency graph does not re-download tarballs — it links from the cache and, on the platforms that support it, hardlinks the files into node_modules.

# shell
bun install                       # install everything from package.json
bun install --frozen-lockfile     # fail if the lockfile would change (CI)
bun install --production          # skip devDependencies
bun add zod                       # add a dependency and install it
bun add -d @types/node            # add a devDependency
bun remove lodash                 # uninstall
bun update --latest               # upgrade within the manifest

Lifecycle scripts and trust

Bun runs your project's own lifecycle scripts — preinstall, install, postinstall, preprepare, postprepare — but by default it does not run the lifecycle scripts of your dependencies. This is a security decision: a postinstall script in a transitive dependency is arbitrary code execution that happens before you have read a single line of it. Dependencies that genuinely need to build native code are listed as trusted, either in the lockfile or via configuration, and only those run their scripts. When a native module fails to load with a "cannot find binding" style error, an untrusted build script is the first thing to check.

If a package ships prebuilt binaries for your platform, extending the trust list is unnecessary — Bun installs the prebuild. Only packages that compile at install time need to be trusted.

Frozen lockfiles in CI

Continuous integration should never resolve a new dependency graph, because a transitive release published this morning is not the graph your tests passed against. bun install --frozen-lockfile installs exactly what the lockfile records and fails loudly if package.json and the lockfile disagree. Use it in CI and in Docker builds. The failure it produces — a mismatch between the manifest and the lock — is the cheapest possible version of the problem it prevents, which is a build that succeeds on a graph nobody reviewed.

2.2 The lockfile

The lockfile records the exact resolved graph. Bun's is a text file, which makes it reviewable in a pull request — a deliberate change from the earlier binary format.

bun.lock is text

Modern Bun writes bun.lock, a human-readable file. Older projects have bun.lockb, the original binary format, which cannot be diffed or merged and therefore caused noisy conflicts whenever two branches touched dependencies. The text format resolves that: a reviewer can see that a patch release moved, and a merge conflict is a normal text conflict. Treat the lockfile as generated: commit it, never hand-edit it, and regenerate it with bun install after changing package.json.

# commit the lockfile; it is generated, not written by hand
git add package.json bun.lock

# migrate an existing project; Bun reads the lockfile from npm, yarn or pnpm
bun install          # recognises package-lock.json / yarn.lock / pnpm-lock.yaml
rm package-lock.json # once bun.lock exists, keep exactly one lockfile

Migrating without rewriting history

Bun reads package-lock.json, yarn.lock and pnpm-lock.yaml, so a migration does not require abandoning a working graph — you run bun install, verify, and then delete the old lockfile so that exactly one source of truth remains. Keeping two lockfiles is worse than either alone: they drift silently, and different contributors install different trees depending on which tool they ran. Before deleting the old file, check that any resolution overrides or patches it contained are represented in package.json, where they belong.

2.3 Workspaces and catalogs

Workspaces let one repository hold several packages that share a single install. Catalogs go one step further and centralise the version numbers themselves.

Declaring workspaces

Add a workspaces array to the root package.json and Bun links the matching directories into the root node_modules, so a package can import a sibling by name rather than by relative path. Patterns are globs and may be negated to exclude a directory. A single install at the root resolves the union of every workspace's dependencies, which means one lockfile, one cache pass and no duplicated trees. Package scripts run in the package that declares them; to run one across every workspace, Bun takes a filter flag rather than a separate orchestration tool for the common case.

// root package.json
{
  "workspaces": ["packages/*", "apps/*", "!packages/legacy-*"]
}

workspace:* and catalogs

Inside a workspace, depend on a sibling with the workspace: protocol so the local package is used instead of a registry copy — "@acme/core": "workspace:*", with ^ and ~ variants to constrain the version. Catalogs solve a different annoyance: the same dependency declared with the same range in a dozen manifests, which drifts. A catalog declares versions once, and members reference the catalog by name, so a bump is a one-line change in one file rather than a search-and-replace across the repository.

// root package.json
{
  "workspaces": { "packages": ["packages/*"], "catalog": { "zod": "^4.0.0" } }
}
// packages/core/package.json
{
  "name": "@acme/core",
  "dependencies": { "zod": "catalog:" }
}
Catalogs are the answer to "which Zod version are we on?". If that question takes more than a second to answer, the repository needs one.

2.4 Global tools and bunx

Not everything belongs in a project manifest. Global installs cover your machine, and bunx runs a package once without installing it at all.

Global installs

bun add --global <name> installs a package into a shared directory and exposes its binaries on PATH. Use it for tools you reach for across projects and rarely pin — a formatter you like, a scaffolding CLI. Anything your build depends on belongs in the manifest instead, because a global is invisible to a colleague's machine and to CI. To list or remove globals, use bun pm ls --global and bun remove -g. Bun keeps global installs isolated so that a global tool's dependencies cannot leak into a project's resolution.

# shell
bun add -g cowsay            # install a global command
bun pm ls --global           # list what is installed globally
bun remove -g cowsay         # uninstall a global command

bunx: run once, install nothing

bunx <package> downloads the package if needed, runs its binary with the arguments you pass, and leaves your project untouched. It is the right way to invoke a one-off generator or a comparison tool without adding a dependency you will never import. bunx is shorthand for bun x; both exist so that muscle memory from npx works. If the package is already a project dependency, prefer a script that calls it, because a bunx call resolves "latest" and therefore is not reproducible.

# shell
bunx create-vite my-app       # scaffold once, no dependency added
bun x cowsay "hello"          # same thing, alternate spelling
bunx --bun some-cli           # run the tool under the Bun runtime
A bare bunx foo fetches the latest version at call time. That is fine in a terminal and wrong in a build: pin the version (bunx foo@3.2.1) or add the tool to devDependencies and call it from a script.

3 · The bundler

3.1 Bundling with bun build

bun build takes an entry point and an output directory and produces a bundle, with no configuration file required. It shares the resolver with the runtime, so a path alias means the same thing in both.

The minimal invocation

A build needs an entry point and a destination. bun build ./src/index.ts --outdir ./dist parses the graph reachable from the entry, applies the same resolution rules the runtime uses, and writes the result. Multi-entry builds are supported by repeating the entry or by passing a glob. Because the resolver understands tsconfig.json paths and package.json export conditions, most projects need no config at all; a plugin is only required for a transform Bun does not already implement, such as a CSS preprocessor or a custom asset type.

# shell
bun build ./src/index.ts --outdir ./dist
bun build ./src/index.ts --outdir ./dist --sourcemap=linked
bun build ./src/index.ts ./src/worker.ts --outdir ./dist --splitting

The JavaScript API

The CLI is a thin wrapper over an exported function, and the function is what a build script or a plugin host should call. Bun.build() returns an object with a success boolean and an outputs array; each output exposes the generated path, the in-memory Blob-like contents and the source map. Checking success before writing anything is the difference between a clear error and a half-written dist. The returned outputs can be written yourself, served directly, or inspected in a test.

// build.ts
const result = await Bun.build({
  entrypoints: ["./src/index.ts"],
  outdir: "./dist",
  target: "bun",
  minify: true,
  sourcemap: "linked",
});

if (!result.success) {
  for (const log of result.logs) console.error(log);
  process.exit(1);
}

console.log(result.outputs.map((o) => o.path));

Watch mode and incremental builds

Add --watch to rebuild when a file in the graph changes. Watch mode keeps the parsed graph in memory and rebuilds only what the change invalidates, so the second build is far cheaper than the first. It is meant for development loops; in production you build once. If a build takes long enough that you want incremental output in CI, that is usually a sign the graph should be split rather than that the build tool is slow.

3.2 Targets, formats and plugins

The target decides which globals and built-ins are assumed present. Choosing the wrong one produces a bundle that builds successfully and fails at runtime, so this is the setting to get right first.

Choosing a target

--target browser assumes a DOM and no Node built-ins; a reference to node:fs is an error rather than a silent shim. --target bun assumes the Bun runtime, so Bun.serve and Bun.file are available and imports of bun:sqlite resolve. --target node assumes Node and its built-ins. The engine also uses the target to decide default output format and which packages to treat as external. Bundling a server entry for browser is the classic mistake: it succeeds because the offending import is tree-shaken out, then fails in the environment where it was supposed to run.

TargetAssumesTypical use
browserDOM, no Node built-insfront-end assets, hydration bundles
bunBun runtime and bun:* modulesBun servers, CLIs run by Bun
nodeNode built-ins and globalslibraries published for Node consumers

Output formats

--format esm is the modern default and the only format you should choose without a specific reason to do otherwise. --format cjs and --format iife exist for compatibility — a CommonJS require-only consumer, or a script tag that expects a global — and are marked experimental, so verify the output rather than assuming equivalence with established bundlers. Set --splitting to share code between multiple entry points; without it, each entry carries its own copy of any shared module, which is correct but larger.

Plugins

A plugin is an object with a name and a setup(build) function that registers callbacks such as onLoad and onResolve. onResolve decides what a specifier points to; onLoad produces the contents for that path. The two are enough to implement a virtual module, a template compiler or an asset pipeline. Keep plugins narrow: a plugin that rewrites every import is a build system you now own, and the reason to use Bun is that you did not want to own one.

// plugin.ts — turn .txt imports into a string export
import type { BunPlugin } from "bun";

export const textPlugin: BunPlugin = {
  name: "text-loader",
  setup(build) {
    build.onLoad({ filter: /\.txt$/ }, async (args) => ({
      contents: `export default ${JSON.stringify(await Bun.file(args.path).text())}`,
      loader: "js",
    }));
  },
};

3.3 The full-stack dev server and HTML imports

Since 1.2 and expanded in 1.3, Bun can serve an HTML entry point directly, bundling the scripts and styles it references on demand and reloading the browser when they change.

HTML as an entry point

Instead of configuring a bundler and a dev server separately, you point Bun.serve at an HTML file. Bun parses the document, finds its <script> and <link> tags, and serves each as a bundled asset with the correct content type. Requesting the page in a browser is enough to build it; there is no separate watcher and no proxy. In production the same entry can be bundled ahead of time, so development and production share one mental model.

// dev-server.ts
const server = Bun.serve({
  port: 3000,
  development: { hmr: true, console: true },
  async fetch(req) {
    const url = new URL(req.url);
    if (url.pathname === "/") return new Response(Bun.file("./index.html"));
    return new Response("Not found", { status: 404 });
  },
});
console.log(server.url);

Routes and development options

The routes option (from 1.2.3) maps URL patterns to handlers more declaratively than a fetch switch. A pattern such as "/users/:id" captures a parameter on req.params.id, and "/api/*" is a wildcard. A route value may be a handler function, a static Response, or a file returned by Bun.file. The development option enables hot module replacement in the browser and forwards browser console.log calls into your terminal — genuinely useful when a client-side error is hard to reproduce. Both are development-only conveniences; disable them in production.

// routes.ts
Bun.serve({
  routes: {
    "/": new Response("home"),
    "/health": () => Response.json({ ok: true }),
    "/users/:id": (req) => Response.json({ id: req.params.id }),
    "/files/*": (req) => Bun.file("./public" + req.params["*"]),
  },
  fetch(req) {
    return new Response("Not found", { status: 404 });
  },
});
routes requires Bun 1.2.3 or newer. On an older runtime the option is ignored and every request falls through to fetch, which presents as "my routes silently do nothing" rather than an error.

3.4 Compiling to a standalone executable

--compile turns a TypeScript entry point into a single native binary that runs on a machine with no Bun and no node_modules. It is the deployment story for CLIs.

Building the binary

bun build ./cli.ts --compile --outfile mycli produces one file that embeds your code and a copy of the runtime. Copy it to a fresh machine and it runs — no interpreter, no dependency install, no package.json. The JavaScript API equivalent sets compile: { outfile } in Bun.build. Because the runtime is embedded, the binary is tens of megabytes rather than a few kilobytes; that is the trade for a self-contained artifact.

# shell
bun build ./cli.ts --compile --outfile mycli
./mycli --help              # runs with no Bun installed

# cross-compile for another platform
bun build ./cli.ts --compile --target=bun-linux-x64 --outfile mycli-linux

Cross-compilation and bytecode

--target selects the platform the binary is for, so one machine can emit builds for Linux, macOS and Windows. That removes the need for a matrix of build runners when you only need to ship an artifact — though you should still test each artifact on a real machine of that platform, because cross-compilation does not exercise the target's quirks. --bytecode pre-compiles your JavaScript into the runtime's bytecode format so the binary does not parse source on start-up; in 1.4 this path is materially faster. Use it for tools where start-up latency is felt.

# shell
bun build ./cli.ts --compile --bytecode --minify --outfile mycli
bun build ./cli.ts --compile --target=bun-windows-x64 --outfile mycli.exe
A compiled binary embeds the runtime version you built it with. Rebuilding after a Bun upgrade is the only way to pick up runtime fixes; a stale binary is a fork you maintain by accident.

4 · The test runner

4.1 Writing and running tests

bun test discovers files matching a fixed set of patterns and runs them with a Jest-compatible API, without a transform step for TypeScript.

Discovery and the API

Bun finds *.test.ts, *.spec.ts and their JavaScript variants anywhere in the project, plus files under a __tests__ directory. Inside a test file, import { test, describe, expect } from "bun:test" gives you the familiar shape. Tests may be synchronous or asynchronous; an async test that returns a promise is awaited, and a test that takes a done callback is supported for callback-style code. Running bun test with no arguments runs everything; passing a path runs one file, and passing a substring filters by name. Because the runner uses the same resolver as the runtime, importing a .ts source file from a test needs no configuration.

// math.test.ts
import { describe, expect, test } from "bun:test";
import { add } from "./math";

describe("add", () => {
  test("sums two numbers", () => {
    expect(add(2, 3)).toBe(5);
  });

  test("resolves async work", async () => {
    expect(await addAsync(2, 3)).toBe(5);
  });

  test("calls back", (done) => {
    addCallback(2, 3, (sum) => {
      expect(sum).toBe(5);
      done();
    });
  });
});
# shell
bun test                # run every test file
bun test math.test.ts   # one file
bun test --grep "sums"  # filter by test name
bun test --bail         # stop at the first failure
bun test --watch        # re-run on change

Assertions and matchers

The matcher set follows Jest closely: toBe for identity, toEqual for deep equality, toThrow, toContain, toMatchObject, toBeCloseTo for floating point, and the not modifier on all of them. expect.assertions(n) guards a test that would otherwise pass vacuously, which is the usual failure mode of a test written around a callback that never fires. For dates and numbers, prefer toBeCloseTo over toBe: exact floating-point equality is a specification of your arithmetic's rounding, not of its correctness.

4.2 Mocks, spies and module mocking

A mock replaces a dependency so a test can observe a call or control a response. Bun follows Jest's vocabulary, so existing tests usually port unchanged.

Mock functions

mock(fn) wraps a function and records its calls; jest.fn() is the same thing under the alias that keeps Jest code working. The recorded state lives on .mock.calls and .mock.results, and you reset it with .mockClear() between tests so one test's calls do not leak into the next. A shared mock created at module scope and never cleared is the most common cause of a test that passes alone and fails in a suite.

import { expect, mock, test } from "bun:test";

test("calls the logger once", () => {
  const log = mock((msg: string) => msg);
  sendReport({ log });

  expect(log).toHaveBeenCalledTimes(1);
  expect(log).toHaveBeenCalledWith("report sent");
  log.mockClear();
});

Controlling a module

For a dependency whose behaviour matters more than its call count, replace the module rather than spying on a function. This is how you make a network call deterministic or force an error branch. Reset the module registry between tests so the replacement does not persist into a test that expects the real implementation. Keep module mocks at the edges of your system — a database client, an HTTP client, the clock — and let internal modules run for real, or the test stops describing your code and starts describing your mocks.

import { expect, mock, test } from "bun:test";
import * as clock from "./clock";

mock.module("./clock", () => ({
  now: () => new Date("2026-01-01T00:00:00Z"),
}));

test("expiry is computed from the injected clock", () => {
  expect(clock.now().getUTCFullYear()).toBe(2026);
});
Mock the clock rather than sleeping. A test that waits three seconds to prove a timeout is a test that will flake on a loaded CI machine and cost three seconds every run.

4.3 Snapshots

A snapshot records the output of an expression once and fails a later run when the output changes. It is powerful and easy to misuse.

Writing and updating snapshots

expect(value).toMatchSnapshot() compares value against a stored serialisation. On the first run, or when --update-snapshots is passed, the snapshot is written instead of compared. Snapshots are stored next to the test in a __snapshots__ directory as .snap files. Commit them: a snapshot is a specification, and a change to one is a deliberate act. In CI, never pass the update flag — an updated snapshot asserts nothing, which is the opposite of what CI is for.

import { expect, test } from "bun:test";
import { renderRow } from "./table";

test("row rendering", () => {
  expect(renderRow({ name: "ada", role: "engineer" })).toMatchSnapshot();
});

When snapshots help and when they hurt

A snapshot earns its place when the output is large, stable and hard to assert field by field — a rendered fragment, a generated configuration, a formatted report. It becomes a liability when the output is large and unstable, because then every unrelated change rewrites the file and reviewers approve it without reading. A one-line object is better asserted with explicit matchers, which document intent and fail with a message a human can act on. When a snapshot does fail, read the diff before updating; the update key is easy to press and impossible to review.

4.4 Coverage, filtering and CI

Coverage reports which lines your tests executed. It is a map of what is untested, not a score of quality.

Generating coverage

bun test --coverage instruments the run and prints a table with per-file percentages for functions and lines. Add --coverage-reporter=lcov to emit a file your CI dashboard can consume, or text for the terminal table. Thresholds can be enforced so a build fails below a floor. Instrumentation costs time, so run coverage on a slower schedule than the main test job if the suite is large.

# shell
bun test --coverage
bun test --coverage --coverage-reporter=lcov
bun test --coverage --coverage-threshold=80

Filtering and isolating

--grep filters by test name, and a path argument runs one file; together they make a tight edit-test loop possible without a separate watch process. Tests run in a fresh module registry, so a module-level variable is not shared between test files — a property you should rely on rather than fight. Mark an individual test or file with skip or todo to exclude it from the run while keeping it visible in the report; a silently deleted test is lost knowledge, a skipped one is a recorded debt.

Coverage counts lines executed, not behaviour verified. A test that calls a function and asserts nothing raises the number and protects nothing. Use the report to find untested branches, then write an assertion about each one.

5 · Built-in APIs

5.1 Files, streams and the shell

Bun ships a file API, a streaming model and a cross-platform shell. Together they replace a surprising amount of NPM surface area.

Bun.file and Bun.write

Bun.file(path) returns a lazy reference to a file — it does not read anything until you ask. The reference exposes .size, .type (a MIME type inferred from the extension) and the reading methods .text(), .json(), .arrayBuffer(), .bytes() and .stream(). Passing a BunFile where a Response or a fetch body is expected works directly, which is why returning a file from a handler needs no read at all. Bun.write(path, data) is the write side; it accepts a string, a typed array, a Blob, a Response or a BunFile, and because it is implemented at the native layer, copying a file into place does not round-trip through JavaScript memory.

// read lazily
const file = Bun.file("./data.json");
console.log(file.size, file.type);      // size, "application/json"
const data = await file.json();

// write several shapes
await Bun.write("./out.txt", "hello");
await Bun.write("./copy.json", file);   // copy without a JS round-trip
await Bun.write("./resp.json", await fetch(url));

Streams

A ReadableStream from file.stream() is the right way to serve a large file: it is sent in chunks, so memory stays flat regardless of file size. The same interface is what fetch bodies and Bun.serve responses use, so the three compose without conversion. When you need line-by-line processing, wrap the stream in a text decoder and split on newlines rather than reading the whole file — a 2 GB log file that fits in no machine's memory is exactly the case streaming exists for.

// stream a file to a response, flat memory
Bun.serve({
  async fetch() {
    return new Response(Bun.file("./big.csv"));
  },
});

// read line by line
const stream = Bun.file("./access.log").stream();
for await (const chunk of stream) {
  for (const line of new TextDecoder().decode(chunk).split("\n")) {
    if (line.includes(" 500 ")) console.warn(line);
  }
}

The Bun shell

import { $ } from "bun" gives a tagged template that runs a command and returns its result, with variable interpolation escaped by default so a value from user input cannot become a shell injection. It implements pipelines, && and || itself rather than delegating to /bin/sh, so the same script runs on Windows, macOS and Linux. Interpolated values may be JavaScript objects: a Response, a Blob, an ArrayBuffer or a BunFile is piped into the command's stdin. This is the API to reach for instead of child_process plus a quoting helper.

import { $ } from "bun";

// escaped by default: fs cannot treat the value as shell syntax
const dir = "my files";
await $`ls ${dir}`;

// pipes, and JS values on stdin
const resp = await fetch("https://example.com");
const bytes = await $`cat < ${resp} | wc -c`;

// capture output and throw on non-zero exit
const { stdout } = await $`git rev-parse HEAD`.quiet();
console.log(stdout.toString().trim());
The shell escapes interpolations, so await $\`rm -rf ${path}\` cannot be turned into an injection by a hostile path. Do not build command strings by concatenation — that discards the guarantee.

5.2 HTTP and WebSockets with Bun.serve

Bun.serve is a web-standard HTTP server built into the runtime. It speaks Request and Response, so handlers are portable to other runtimes.

A server without a framework

The handler receives a standard Request and returns a standard Response. There is no res.end(), no middleware chain and no framework object. Routing is a switch on new URL(req.url).pathname or, from 1.2.3, the declarative routes option. Returning Response.json(data) sets the content type and serialises in one call; returning Bun.file(path) streams a file. Because the interface is the web standard, a handler you write here can be lifted into a worker or a serverless adapter with little change.

// server.ts
const server = Bun.serve({
  port: 3000,
  async fetch(req) {
    const url = new URL(req.url);

    if (req.method === "POST" && url.pathname === "/echo") {
      return Response.json(await req.json(), { status: 201 });
    }
    if (url.pathname === "/") {
      return new Response("<h1>Hello</h1>", {
        headers: { "content-type": "text/html" },
      });
    }
    return new Response("Not found", { status: 404 });
  },
});

console.log(`listening on ${server.url}`);

WebSockets

Add a websocket option with open, message and close callbacks, then upgrade a request by calling server.upgrade(req) from the handler and returning early. Bun maintains the connection and dispatches to your callbacks; ws.send() writes a message and ws.subscribe(topic) participates in the built-in pub/sub, where server.publish(topic, data) broadcasts to every subscriber. That publish path is native, so a chat fan-out does not need a Redis hop merely to reach sockets attached to the same process.

Bun.serve({
  fetch(req, server) {
    if (server.upgrade(req)) return; // handled
    return new Response("upgrade failed", { status: 400 });
  },
  websocket: {
    open(ws) {
      ws.subscribe("room");
      ws.send("welcome");
    },
    message(ws, msg) {
      ws.publish("room", String(msg));
    },
    close(ws) {
      ws.unsubscribe("room");
    },
  },
});

Cookies, TLS and limits

Bun includes a cookie API rather than requiring a parser: Bun.Cookie reads and writes attributes such as HttpOnly, SameSite, Secure, Max-Age and Partitioned explicitly, which keeps those flags visible in review. Pass tls: { cert, key } to serve HTTPS directly, and set maxRequestBodySize to cap uploads so a single request cannot exhaust memory. For a server behind a reverse proxy, remember that client address and scheme come from headers the proxy must set — trust them only from your own proxy.

Bun.serve({
  tls: { cert: Bun.file("./cert.pem"), key: Bun.file("./key.pem") },
  maxRequestBodySize: 10 * 1024 * 1024, // 10 MB
  fetch(req) {
    const jar = new Bun.CookieMap(req.headers.get("cookie") ?? "");
    jar.set("session", "abc", { httpOnly: true, sameSite: "lax", path: "/" });
    return new Response("ok", { headers: { "Set-Cookie": jar.toSetCookieHeaders() } });
  },
});

5.3 SQLite, Postgres, MySQL and Redis

SQLite is built in as bun:sqlite. Postgres, MySQL and Redis clients are built in too, so a service can talk to a database with no driver dependency.

bun:sqlite

import { Database } from "bun:sqlite" gives a synchronous, prepared-statement API with the shape users of better-sqlite3 already know. db.query(sql) prepares once and can be reused; .get() returns one row, .all() returns an array and .run() executes a statement without reading rows. Parameters may be positional (?) or named ($name or :name). Transactions wrap a function so that a throw rolls the whole batch back. BLOB columns arrive as Uint8Array, and .as(MyClass) maps a row onto a class so the result is typed rather than a bare object.

import { Database } from "bun:sqlite";

const db = new Database("app.sqlite", { create: true });
db.run("CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, email TEXT, data BLOB)");

db.run("INSERT INTO users (email) VALUES ($email)", { $email: "ada@example.com" });

const one = db.query("SELECT * FROM users WHERE id = ?").get(1);

const insert = db.transaction((rows) => {
  for (const r of rows) db.run("INSERT INTO users (email) VALUES ($email)", { $email: r.email });
  return rows.length;
});
const count = insert([{ email: "grace@example.com" }, { email: "linus@example.com" }]);

console.log(one, count);

Server databases and Redis

Bun also ships clients for Postgres, MySQL and Redis, so a project can drop the matching npm driver. The Postgres and MySQL clients support tagged-template or parameterised queries and connection pooling; the Redis client speaks the protocol directly with commands such as get, set and publish. Because these are built into the runtime, they are resolved by the same module system as everything else, which means no pg native build step and no redis client version to reconcile. The trade-off is portability: code written against these clients does not run on Node, so keep database access behind a thin module of your own if that matters.

// postgres (built-in)
import { sql } from "bun";
const rows = await sql`SELECT id, email FROM users WHERE id = ${id}`;

// redis (built-in)
import { redis } from "bun";
await redis.set("counter", "1");
const value = await redis.get("counter");
Availability matters here: the SQLite module has been present for several releases, while the Postgres, MySQL and Redis clients arrived in 1.3. Pin your runtime version if you rely on them.

5.4 Hashing, passwords and secrets

Cryptographic primitives you would otherwise fetch from npm are part of the runtime, which removes a dependency and a build step from the security-sensitive part of an application.

Password hashing

Bun.password.hash(password) returns a promise for a hash; pass { algorithm: "argon2id" } (or argon2i/argon2d) with memoryCost and timeCost to tune the work factor, or choose bcrypt for compatibility with an existing database. Bun.password.verify(password, hash) returns a boolean and reads the parameters from the stored hash, so raising the cost later does not invalidate old hashes. Never store a fast hash of a password: the whole point of a slow algorithm is that an attacker with the database must spend the same work you spent at sign-up.

// hash at sign-up (argon2id by default)
const hash = await Bun.password.hash("correct horse battery staple", {
  algorithm: "argon2id",
  memoryCost: 65536, // KiB
  timeCost: 2,
});

// verify at login; parameters come from the hash
const ok = await Bun.password.verify("correct horse battery staple", hash);

General hashing

Bun.hash(data) and the named helpers give non-cryptographic digests for caches and ETags, and Bun.CryptoHasher computes cryptographic digests such as SHA-256 incrementally, which is what you want for a large file or a stream. The distinction matters: use a fast hash to key a cache, and a cryptographic digest anywhere an attacker might try to construct a collision.

// fast, non-cryptographic: cache keys, dedup
const key = Bun.hash("some cache key"); // number

// cryptographic, incremental: files and streams
const hasher = new Bun.CryptoHasher("sha256");
hasher.update("hello ");
hasher.update("world");
const digest = hasher.digest("hex"); // string

Random tokens and comparison

crypto.randomUUID() and crypto.getRandomValues() come from the web platform and are always available; use them for session identifiers and salts, never Math.random(). When comparing a secret you received against one you stored, compare in constant time — the runtime exposes the primitive through the standard WebCrypto surface — so that a timing side channel does not reveal how many leading bytes were correct. These are one-line habits that prevent an entire class of vulnerability.

5.5 Subprocesses and environment

For a program you must run rather than a command you compose, Bun.spawn gives a typed handle on the process, its streams and its exit code.

Spawning and reading

Bun.spawn(["git", "status"], { cwd, env }) returns a Bun.Subprocess with .pid, a promise-like .exited resolving to the exit code, and readable streams on .stdout and .stderr. Reading the streams as they fill is the difference between a tool that works and one that deadlocks: a child that writes more than the pipe buffer holds will block until you drain it, so consume stdout while the process runs rather than awaiting .exited first. Bun.spawnSync is the blocking variant for a short command whose output you need before continuing.

const proc = Bun.spawn(["git", "log", "--oneline", "-5"], {
  cwd: process.cwd(),
  env: { ...process.env, GIT_PAGER: "cat" },
  stdout: "pipe",
});

const text = await new Response(proc.stdout).text();
const code = await proc.exited;
if (code !== 0) throw new Error(`git failed: ${code}`);
console.log(text);

Environment variables

Bun loads .env automatically, then a file selected by NODE_ENV — .env.production, .env.development or .env.test — and finally the *.local variants. .env.local is skipped when NODE_ENV=test, so a test run does not pick up a developer's local overrides. Real environment variables that already exist in the process are not overwritten, which is what lets a deployment platform inject a secret and have it win over a checked-in default. Read values through Bun.env.NAME, or process.env if you need Node compatibility.

# shell — .env
DATABASE_URL=postgres://localhost/app
API_KEY=dev-only
// required secrets should fail loudly at boot
const key = Bun.env.API_KEY;
if (!key) throw new Error("API_KEY is required");

// NODE_ENV selects which .env.* file is loaded
console.log(Bun.env.NODE_ENV ?? "development");
Never commit a real secret in .env. Keep .env in .gitignore, commit a .env.example with placeholder names, and inject production values from the platform that runs the code.

6 · Node.js compatibility

6.1 What "Node.js compatible" actually means

Bun aims to run Node.js code and packages without modification. The claim is behavioural, not aspirational, and it is tracked against a specific Node release — so the useful question is not "is it compatible" but "compatible with which Node, and for what".

Two layers of compatibility

There are two separate promises, and conflating them causes most migration surprises. The first is the module layer: node:fs, node:path, node:crypto, node:stream, node:events, node:http and dozens more are implemented, mostly completely, so an import resolves and behaves as documented. The second is the runtime layer: process, Buffer, global, require, __dirname and the rest of the ambient surface that Node injects into every program. Bun implements both, but the module layer is where the completeness is highest, because it is measurable — each built-in has a documented API you can compare against. Compatibility is tracked against Node.js v26 at the time of writing; consult the version table rather than assuming a method exists just because Node added it recently.

Why the claim is verifiable

Node's own test suite is the strongest available oracle, and the compatibility project runs it. That matters because a hand-written compatibility table tests what someone remembered to list, whereas a suite tests what the ecosystem actually does — including the undocumented behaviours packages depend on. When you find a gap, the productive move is to check whether it is a known difference before rewriting code around it, because a workaround for a gap that is about to close is permanent cost for temporary benefit.

Compatibility is versioned in both directions: the Bun version you run and the Node version it targets. Reading "supports Node" without both numbers tells you almost nothing.

6.2 Built-in modules and the npm ecosystem

Most of the npm ecosystem is pure JavaScript and runs the moment the resolver finds it. The exceptions cluster around native addons and engine-specific behaviour.

Built-ins and interop

Node built-ins are available under both their legacy specifier and the node: prefix, so require("fs") and import "node:fs" both work. Bun also implements the interop rules that make mixed module systems function — a CommonJS module imported from ESM gets a default export and named destructuring where the static analysis supports it, and an ESM module required from CJS is handled where possible. These rules are subtle and were historically a source of breakage; the practical guidance is to write ESM in new code and let the runtime bridge the older packages. Prefer node:-prefixed imports in files you write, because they are unambiguous and portable.

// both spellings resolve
import { readFileSync } from "node:fs";
const fs = require("node:fs");

// CJS package consumed from ESM
import express from "express"; // default interop
import { Router } from "express"; // named, when statically analysable

Native addons

A package with a compiled addon — a .node file or a node-gyp build step — is the main place compatibility can fail, because the addon was compiled against V8's ABI and Bun runs JavaScriptCore. Packages that ship prebuilt binaries for your platform, or that use N-API, generally work. Packages that compile against V8 internals at install time do not, and no amount of resolver work fixes that. When a dependency fails to load with a symbol or ABI error, that is the diagnosis: it is a native addon, and the choice is a pure-JavaScript alternative or running that part under Node.

A dependency whose install step compiles code needs to be trusted before Bun will run that script. A "cannot find binding" error after a fresh install is usually an untrusted build script rather than a missing prebuild — check the trusted list before reaching for a different package.

6.3 Where behaviour differs from Node

The most useful part of a compatibility story is its boundary. These are the places where code that works on Node may behave differently on Bun, and why.

Engine and defaults

JavaScriptCore versus V8 is the root of most subtle differences. Specification-compliant code behaves the same; code that relied on a V8 quirk does not. Beyond the engine, Bun changes several defaults deliberately: it auto-loads .env, it runs TypeScript without a transform step, it resolves dependencies more permissively (installing peers and optional dependencies in one pass), and its HTTP server is a web-standard Request/Response API rather than Node's IncomingMessage/ServerResponse. None of these break Node code, because node:http still exists, but they change what idiomatic code looks like.

Diagnosing a difference

When a file behaves differently under the two runtimes, reduce it to the smallest reproduction and check the compatibility table for that specific API before assuming the runtime is wrong. Then check the version: a difference documented for an older Bun may already be closed, and a difference in a newer Node may simply not be implemented yet. Keep a small script that runs your critical paths under both runtimes in CI if the code must support both — that is a stronger guarantee than any table, and it is cheap because the runtimes can coexist on one machine.

6.4 Type checking with bun check

Running TypeScript without checking it is fast and dangerous. Bun 1.4 added bun check, a built-in type checker aimed at closing that gap.

Why a checker is still needed

Bun strips types; it does not verify them. A file with a type error runs fine until the wrong value reaches a function that assumed otherwise, at which point the failure is a runtime error with a misleading stack. That is a deliberate trade — parsing and erasing types is what makes start-up fast — but it means the type system is only enforced if some tool enforces it. Editors do this live for open files, which is exactly the coverage you do not have in CI, where nobody has the file open.

# shell — type-check the project
bun check
bun run --check src/index.ts   # check before running
bun build ./src/index.ts --check --outdir dist

Fitting it into a pipeline

Because --check can be attached to bun run and bun build, a check does not need its own script entry and the checked output is the output that ships. On large projects the built-in checker is faster than invoking the TypeScript compiler, which matters when a check runs on every commit. Keep the editor's TypeScript integration for the interactive feedback it gives — hover types, go-to-definition, quick fixes — and let bun check be the gate in CI. The two read the same tsconfig.json, so they agree about the code and disagree only about speed.

If you already run tsc --noEmit in CI, bun check is a drop-in replacement for the gate; keep tsc installed if you also publish declaration files, since emitting .d.ts is a separate job from checking.

7 · Migrating from Node.js

7.1 Choosing a migration path

Migration is not one decision. The four Bun capabilities can be adopted independently, and the right first step is usually the one with the smallest blast radius.

Three levels of adoption

The least invasive step is to keep Node as the runtime and adopt only the package manager: replace npm install with bun install and stop there. It is fast, reversible, and touches CI configuration rather than application code. The middle step is to run scripts and tests under Bun while keeping the long-lived server on Node — bun test and --bun for tooling, Node for production. The deepest step is to run the application itself on Bun, which is where the built-in HTTP server and the database clients become available and where the compatibility surface is exercised hardest. There is no prize for reaching the deepest step fastest; each level has a measurable benefit and an independent rollback.

# level 1 — package manager only
bun install

# level 2 — Bun runs the tooling, Node runs the app
bun test
bun --bun run eslint .

# level 3 — Bun runs the app
bun run src/server.ts

Ordering the work

Start with a project whose test suite is green on Node, because that is your safety net. Move the package manager first and confirm CI still passes. Then run the suite under bun test; failures there are usually Jest-API gaps or a reliance on a Node-only global, and each is a small, contained fix. Only then change the runtime for the application, and do it behind a branch with the Node path still available. A migration that changes all four things at once cannot tell you which change broke the build.

7.2 Common failure modes

Almost every migration problem falls into one of a handful of categories. Knowing them turns a baffling error into a two-minute fix.

Native addons and build scripts

The first category is compiled dependencies, covered earlier: a V8-ABI addon cannot load, and a dependency whose install script was skipped cannot build. Check the trusted list first. The second is environment assumptions — a Dockerfile that copied package-lock.json and ran npm ci now has no lockfile the new tool recognises, and a script that assumed NODE_ENV was unset now picks up an auto-loaded .env. Both are configuration, not code.

# a Node-flavoured Dockerfile
FROM node:22-slim
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# the Bun equivalent
FROM oven/bun:1
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production

Test-runner and API gaps

The third category is the test runner: a Jest matcher that Bun has not implemented, a jest.mock call with a factory that behaves slightly differently, or a snapshot format difference. Each has a direct translation, and the failures are loud. The fourth is the HTTP layer: code that reached into req.socket, called res.writeHead() or relied on process.nextTick ordering may need adjustment if it moves off node:http onto Bun.serve. Keeping the framework's own server (Express, Fastify) on node:http and only changing the runtime is the low-risk route until you are ready to adopt the web-standard handler.

// Node style — still works, via node:http
import { createServer } from "node:http";
createServer((req, res) => {
  res.writeHead(200, { "content-type": "text/plain" });
  res.end("ok");
}).listen(3000);
Keep a branch that runs the old command. If the migration stalls, git switch costs a second, whereas reconstructing the working Node configuration costs an afternoon.

7.3 Migrating a server

A web server is the hardest thing to migrate and the most valuable, because it is where the built-in APIs replace the most dependencies.

From framework to handler, or not

You do not have to abandon Express, Fastify or Koa to run on Bun — they run on node:http, which Bun implements, and many teams simply change the runtime and keep the framework. Migrating to Bun.serve is a separate, optional step that trades the framework's middleware ecosystem for a web-standard handler and a much smaller dependency tree. A useful middle path is to adopt Bun.serve for new endpoints while the existing framework serves the old ones, since both can share the same process and port only if one delegates to the other.

// framework on Bun — change nothing but the runtime
import express from "express";
const app = express();
app.get("/health", (_req, res) => res.json({ ok: true }));
app.listen(3000);

What you gain and what you rewrite

Adopting Bun.serve replaces body-parsing middleware with await req.json(), replaces res.json() with Response.json(), and replaces a static-file middleware with Bun.file(). In exchange, middleware that assumed Node's request object — session stores, logging middleware, passport strategies — must be re-evaluated, because a standard Request does not carry the extra properties those packages attach. Migrate endpoint by endpoint behind a test that asserts the response body and status, and move the static files and health check first: they are the least entangled and the quickest to prove.

8 · Production and deployment

8.1 Building for production

Production code should be built once, reproducibly, and run as an artifact — not bundled on the server at start-up.

The build step

Bundle for the target the code actually runs on, set NODE_ENV=production, and fail the build on the first error rather than writing partial output. For a Bun server, --target bun keeps built-ins external and produces a bundle that starts fast; for a library consumed by others, --target node avoids assuming Bun. Emit a source map for the server unless it would leak source you do not want exposed, because an unreadable production stack trace costs more debugging time than the map costs bytes. The build should be a script, not a paragraph in a wiki.

// build.ts — fail fast, write atomically
const result = await Bun.build({
  entrypoints: ["./src/server.ts"],
  outdir: "./dist",
  target: "bun",
  minify: true,
  sourcemap: "linked",
  define: { "process.env.NODE_ENV": JSON.stringify("production") },
});

if (!result.success) {
  console.error(result.logs);
  process.exit(1);
}

Compiled binaries as artifacts

For a CLI, --compile is the whole deployment: one file, no runtime, no node_modules. For a server, a compiled binary is possible but less compelling, because the container already provides isolation and you usually want the ability to patch without a rebuild. If you do compile a server, treat the binary as an immutable release artifact, tag it with the runtime version, and rebuild — never edit in place.

8.2 Containers and CI

Bun publishes an official image, and its install is fast enough that a multi-stage build is straightforward. The details that matter are the lockfile and the production flag.

A reproducible image

Copy the manifest and the lockfile first, install against the frozen lockfile, and only then copy the source. That ordering is what lets Docker cache the dependency layer so a source-only change does not re-install the world. --frozen-lockfile guarantees the image matches the reviewed graph, and --production keeps development dependencies — test runners, type definitions, linters — out of the shipped layer.

# Dockerfile
FROM oven/bun:1 AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build

FROM oven/bun:1-slim
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
EXPOSE 3000
CMD ["bun", "run", "dist/server.js"]

CI structure

A useful pipeline installs with a frozen lockfile, runs the type check, runs the tests with coverage, and builds the artifact — in that order, so the cheapest failure comes first. Pin the Bun version in the workflow rather than installing latest, because a release mid-sprint is not a change anyone reviewed. Cache the install directory keyed on the lockfile hash; Bun's cache is content-addressed, so the key is stable as long as the lockfile is.

# .github/workflows/ci.yml
steps:
  - uses: actions/checkout@v4
  - uses: oven-sh/setup-bun@v2
    with:
      bun-version: 1.4.3
  - run: bun install --frozen-lockfile
  - run: bun check
  - run: bun test --coverage
  - run: bun run build
Run the production build in CI even if the deploy pipeline builds again. It catches a broken build at the point where a reviewer is looking, rather than at the point where a deploy is half-finished.

8.3 Operations: memory, signals and observability

A runtime in production is judged by how it behaves under pressure and in a crash. Bun exposes the knobs and the signals you need.

Memory and process limits

Useful knobs include a heap limit for the JavaScript heap and a maximum body size on the server, both of which convert an unbounded failure into a bounded, observable one. A server process should run under a supervisor or an orchestrator that restarts it; state that matters belongs in a database or Redis, not in a module-level variable, because a restart is not an event you can forbid. Watch resident memory over time: a slow climb is a leak, and the heap snapshot from the inspector is how you find it.

# cap the heap so a leak fails early and visibly
BUN_JSC_forceRAMSize=536870912 bun run dist/server.js

Signals and graceful shutdown

An orchestrator stops a container by sending SIGTERM and killing it after a grace period. The process must, on that signal, stop accepting new connections, finish in-flight requests, close pool connections and exit — otherwise every deploy drops a request. Bun reports the running server's pending request count, so a shutdown routine can drain rather than guess. Keep the handler short and idempotent: a shutdown path that itself hangs is worse than no handler, because it turns a rolling deploy into an outage.

const server = Bun.serve({ port: 3000, fetch: handle });

async function shutdown() {
  await server.stop();          // stop accepting, drain in-flight
  await pool?.close();          // release resources
  process.exit(0);
}
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);

Logging and health

Write structured logs to stdout and let the platform collect them; the terminal pretty-printer is for development. Expose two endpoints rather than one: a liveness check that reports whether the process is running, and a readiness check that reports whether it can serve — a database connection, a required dependency. An orchestrator that treats a failed dependency as a dead process will restart-loop a healthy service, so keep the two signals distinct. Log the request identifier, the status and the duration, and nothing else you cannot query later.

Never log a request body, a token or a password. Structured logs are copied to systems with different access controls than production, and a secret in a log is a secret with a much longer life and a much wider audience.

9.2 Bun and Node at a glance

A summary for choosing between them. Neither column is universally better; the question is which trade-offs your project can absorb.

EngineV8JavaScriptCore

How to decide

Choose Node when you depend on a native addon that only builds against V8, when a package's support matrix explicitly excludes Bun, or when your organisation already has hardened Node operations and no appetite for a new runtime. Choose Bun when you are starting fresh, when start-up latency matters — CLIs, serverless handlers, test suites — or when you want the package manager, bundler and test runner to be one install and one version. The honest answer for most existing applications is a hybrid: Bun for tooling and new services, Node where an ABI-bound dependency holds the line.

9.3 Where to go next

The runtime is large enough that a guide this size is a map, not the territory. These are the edges worth exploring next.

Adjacent guides

Several guides in this library pair with this one. typescript.html covers the type system that Bun erases rather than checks; javascript.html covers the language and the module semantics that the compatibility chapter refers to; react.html, svelte.html and vuejs.html cover the front-ends that bun build and the HTML-import dev server are typically pointed at; and api-design.html covers the HTTP concerns that Bun.serve makes concrete. Read the runtime chapter beside a real project rather than in isolation.

A practice sequence

Work through the topics in the order they appear here, and after each one change something real. Install Bun and pin the version in one project's CI. Swap its install command and confirm the lockfile is the only file that changed. Run its tests under bun test and fix what breaks. Then, in a scratch directory, build a small server with Bun.serve, a SQLite table and a test — the whole stack with no npm dependencies. That exercise touches every chapter of this guide at once, and it usually makes clear which of Bun's four capabilities you want to adopt first.

The quickest way to judge whether Bun fits a codebase is to run bun install and bun test on it and read the output. Dependency-only adoption is reversible in a single command, and the failures it exposes are the failures that matter.
