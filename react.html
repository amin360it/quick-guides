Welcome — How to Use This React Guide

What this guide assumesHow the chapters fit togetherConventions and how to read the codeHow to work through the exercises

React 19 is a library for describing what the screen should look like right now, given some state. Everything else — the build step, the router, the server — is a different tool with a different job. This guide is about the library, deeply, and about the architectural decisions that make a React codebase survive a second year.

What this guide assumes

0.1 JavaScript Prerequisites

You can already write JavaScript and you have seen JSX somewhere. You do not need prior React experience, and if you have used React 17 you will find several things here that have changed: use, actions, the new useOptimistic hook, and the fact that forwardRef is no longer required for most work.

What we assume about your tooling:

  • Node 22 or newer, and a package manager. The examples use npm but nothing here depends on it.
  • TypeScript. React 19's types are far better than they were, and the ecosystem is written in TypeScript. Every example is typed.
  • A modern bundler — Vite, Next.js, or Parcel. The library does not care which, and that is the point.

The one thing to internalise early: React is not a view layer that you poke. It is a function of your state. If you find yourself wanting to "update the UI", you almost certainly have a piece of state in the wrong place. Most of this guide is really about where state lives and who owns it.

How the chapters fit together

0.2 Chapter Structure

The guide is deliberately ordered so that each chapter only depends on the ones before it.

  • Part one (1–5) is the mental model. The render model, elements, reconciliation and the component contract. If you skip this you will write code that works and cannot be explained.
  • Part two (6–10) is state. useState, useReducer, effects, refs, context. This is where most real bugs live.
  • Part three (11–14) is performance and the new features. What re-renders, how to measure it, memoisation done properly, and React 19's use and actions.
  • Part four (15–19) is application architecture. Data fetching, routing, forms, error boundaries, testing, and how to structure a project that ten people can work in.

Conventions and how to read the code

0.3 Code Conventions

Code samples use JSX with TypeScript. Where a type would obscure the idea being taught, it is elided with a comment rather than removed silently.

// a component is a function that returns React elements
// it must be named with a capital letter, because JSX compiles to a call
function SearchBox({ query, onChange }: { query: string; onChange: (q: string) => void }) {
  return (
    <input
      value={query}
      onChange={(e) => onChange(e.target.value)}
      placeholder="Search"
    />
  );
}

// lowercase tags are host elements (div, input, button), capitalised ones
// are your own components. <SearchBox /> calls the function above.

Three conventions worth stating outright:

  • Components are pure functions of their props. They must not mutate props, and they should not read anything that is not passed to them. This is what makes the compiler's automatic memoisation safe in React 19.
  • Effects are for synchronising with the outside world — a network, a timer, a subscription, the DOM. They are not for deriving values, and chapter 9 explains why using an effect to "compute state" is almost always a mistake.
  • Keys are identity. When you render a list, the key tells React which item is which across renders. Chapter 4 covers what happens when you get this wrong, which is subtle and worth reading properly.

How to work through the exercises

0.4 Exercise Format

Every chapter ends with an .ex block. Treat them as the real work; the prose is a summary of what you should already know from doing them. Each one is runnable in a scratch project.

If you get stuck on an exercise, the answer is almost always a smaller component. React's central claim is that a tree of small, pure, well-named functions is easier to reason about than a few large ones with mutable state — and that claim is testable every time you hit a wall.

The declarative model

1.1 Components

You do not tell React what to do. You tell it what the output should be for the current state, and it works out the difference. This sounds like a small change in syntax; it is not, because it moves an entire category of bug out of existence.

// imperative: you own the sequence
const el = document.createElement('button');
el.textContent = 'Click me';
el.addEventListener('click', onClick);
container.appendChild(el);

// later, when state changes, you remember to update it
el.textContent = 'Clicked 3 times';
el.disabled = count >= 3;

// the bug class: a second code path forgets one of these lines.
// the DOM and your intentions drift apart.

// declarative: you describe the result
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)} disabled={count >= 3}>
      Clicked {count} times
    </button>
  );
}
// there is no second code path. count is 0, 1, 2 or 3 and the function
// describes all four states completely.

The trade is real and worth naming: React re-runs your function to discover what changed, so a render is more work than a surgical DOM mutation. That is why "avoid unnecessary renders" is a real concern rather than folklore.

Elements are plain objects

1.2 Rendering

This is the most useful thing to know about React's internals. A React element is not a DOM node, and creating one is not expensive.

// what <div className="x">{1 + 1}</div> actually evaluates to
{
  type: 'div',
  key: null,
  ref: null,
  props: { className: 'x', children: 2 },
  _owner: null
}

// a component element
{
  type: SearchBox,          // the function itself, not a string
  key: null,
  ref: null,
  props: { query: '', onChange: fn },
  _owner: null
}

// this is why they are cheap: a plain object literal
const el = <div />;   // ~50 bytes, no allocation beyond the object

// and why you can pass them around
const row = <td>{cell}</td>;
return <tr>{row}</tr>;   // the same element object appears twice

Because elements are plain data, React can compare two of them with === or Object.is. That is the whole reconciliation strategy: a cheap structural diff of plain objects, then a small number of targeted DOM operations. If you have seen a framework that diffs a virtual DOM node-by-node, this is the same idea with a much cheaper node type.

The fiber tree and why it exists

1.3 Fiber Architecture

A fiber is React's internal unit of work — a plain object holding one component instance, its input, and its output. The tree of fibers mirrors the element tree but carries bookkeeping: which work is pending, what state is, whether it committed.

Fibers exist to make rendering interruptible. Because each fiber is a small serialisable object, React can build a work loop that:

  • yields to the browser between units of work, so a big render does not freeze the tab;
  • can be paused and restarted when a higher-priority update arrives, abandoning low-priority work;
  • lets concurrent features like useTransition and Suspense exist at all.
// the three phases, in order
//
//  1. RENDER phase - pure, interruptible, may be thrown away entirely
//     walks fibers, calls your components, produces an element tree
//     nothing touches the DOM yet
//
//  2. COMMIT phase - synchronous, never interrupted
//     applies the diff to the DOM, runs layout effects, attaches refs
//     this is the only phase that mutates anything
//
//  3. PASSIVE phase - after paint
//     runs useEffect callbacks

// the consequence people get wrong:
// a render that is abandoned in phase 1 still CALLED your component
// function. any side effect inside a component body ran. twice, on a
// strict-mode double render, and possibly again if the render restarts.

// which is the entire reason effects are a separate concept
function Bad() {
  fetch('/api');           // runs on every render, including discarded ones
  return <div />;
}

function Fine() {
  useEffect(() => {      // only after commit
    fetch('/api');
  }, []);
  return <div />;
}

Batching and when a render happens

1.4 batched Updates

React 18 introduced automatic batching everywhere: multiple state updates in the same tick produce one render, not one per update.

function Batch() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);

  const both = () => {
    setA(1);
    setB(1);
    // one render. a === 1 and b === 1 together.
  };

  const stale = () => {
    setA(a + 1);      // a is 0 from this render's closure
    setA(a + 2);      // also uses 0, so the result is 2, not 3
  };

  const functional = () => {
    setA((prev) => prev + 1);   // 1
    setA((prev) => prev + 1);   // 2
  };

  return <button onClick={both}>{a}{b}</button>;
}

Two rules that follow from this:

  • Never rely on a state variable's value in the same tick you set it. Use the updater form when the new value depends on the old.
  • Batching applies to promise callbacks too, since React 18. Three awaits followed by three setters produce one render.
// before React 18, only events inside React handlers were batched
// after: anywhere, including timers and native promise callbacks
async function load() {
  setLoading(true);
  const [users, posts, tags] = await Promise.all([
    fetch('/users').then((r) => r.json()),
    fetch('/posts').then((r) => r.json()),
    fetch('/tags').then((r) => r.json()),
  ]);
  setUsers(users);
  setPosts(posts);
  setTags(tags);
  setLoading(false);
  // one re-render, not five
}

Keys are identity

1.5 Key Identity

When React reconciles a list, it matches old elements to new ones by position unless you give it a key. The key says "this is the same item as before", which is what lets state, focus and DOM identity travel with the data.

function List({ items }) {
  // NO keys: React matches by index
  return (
    <ul>
      {items.map((item) => <li>{item.text}</li>)}
    </ul>
  );
}

// items = ['a', 'b', 'c']  then  ['x', 'a', 'b', 'c']  (prepend)
// index matching says: position 0 changed text a -> x
//                    position 1 changed text b -> a
//                    ...so 3 of 4 DOM nodes are "updated"
// with keys, React sees x as new, a/b/c as unchanged, and appends one node

function Fixed({ items }) {
  return (
    <ul>
      {items.map((item) => <li key={item.id}>{item.text}</li>)}
    </ul>
  );
}

With keys, the state inside each row follows the data. Without them, it follows the position — which is why a delete button in an unkeyed list "deletes the wrong row" when the list changes.

Never use the array index as a key unless the list is static, append-only, and never reordered or filtered. Index keys make state attach to positions, so a filtered list reuses the wrong component state. Keys must be stable, unique among siblings, and derived from the data — item.id, not i.

StrictMode and the double render

1.6 StrictMode Safety

React's StrictMode deliberately renders components twice in development. This is not a bug and not a performance issue; it is a correctness check that surfaces impure components.

// with StrictMode, this component body runs twice per render in dev
function Impure({ user }) {
  console.log('rendered');      // logs twice
  const id = Math.random();    // different id each time - a real bug
  track(user);                 // duplicate analytics - a real bug
  return <div id={id}>{user.name}</div>;
}

// it must be pure: same props in, same output out, no external writes
function Pure({ user }) {
  const [id] = useState(() => crypto.randomUUID());  // once, not per render
  return <div id={id}>{user.name}</div>;
}

// the same applies to the initialiser form, which is exactly why useState
// accepts a function: React calls it once, and StrictMode calls it twice
// and keeps one result, to surface an impure initialiser.
const [rows] = useState(() => buildRows());  // correct: lazy, once
const [rows] = useState(buildRows());          // wrong: runs on every render

StrictMode also mounts, unmounts and remounts effects once in development. If your cleanup function is wrong, you will see the symptom in dev but not in production — which is exactly the point. Treat any effect that misbehaves under StrictMode as a genuine bug rather than a development-mode quirk.

The mechanics of writing components: what JSX becomes, what a component is allowed to return, how composition replaces configuration, and the rules that make a component reusable instead of a liability.

What JSX compiles to

2.1 JSX Elements

JSX is not a templating language. It is a syntax extension that calls a function, which means every JSX quirk follows from being a function call.

// this JSX
<div className="box" onClick={handler}>
  <span>{value}</span>
</div>

// compiles to roughly this
jsx('div', {
  className: 'box',
  onClick: handler,
  children: jsx('span', { children: value }),
});

// note:
// - className, not class, because the compiler passes an object
// - style is an OBJECT, not a string
//   style={{ color: 'red', fontSize: 16 }}      correct
//   style="color: red; font-size: 16px"          wrong, string
// - a single child is not wrapped in an array; several children become one
//   array, so keys matter for lists of them
// - the expression is evaluated, the result is a child

Because JSX is a call, the whole thing is an expression. That is why all of these are valid:

const isWide = useMediaQuery('(min-width: 800px)');
return <Layout sidebar={isWide ? <Nav /> : null}>{content}</Layout>;

return list.map((item) => (
  <li key={item.id}>{item.label}</li>
));

return cond && <Warning />;   // renders nothing when cond is false

The types a component can return

2.2 Return Types

As of React 19 a component may return any of these, and nothing else:

// 1. a React element
return <div />;

// 2. an array of elements
return <><li /><li /></>;   // a fragment is an array of one

// 3. a string or a number
return 'loading...';
return 42;

// 4. null, undefined, true or false - renders NOTHING
if (!user) return null;
return true;   // why you cannot return a bare boolean as output

// 5. a portal - renders elsewhere in the DOM tree but logically here
return createPortal(modals, document.body);

// NOT ALLOWED:
// return undefined   -> runtime error, caught by the type checker
// return a plain object
// return 0 && <Thing /> when 0 is a valid node   -> renders "0"
//   this is the classic bug: use !! or a ternary for boolean state

The a && <b /> trap. If a is the number 0, React renders the text "0", because 0 is a renderable value. This is a real bug in real codebases whenever a count or an index is used in a conditional. Use a ternary — {count > 0 && <Badge />} — or coerce with {Boolean(count) && ...}.

Children and composition

2.3 Children Composition

The most important design decision in React is that components take children instead of configuration props for their internals. A component that accepts slots is flexible; a component that accepts twenty boolean props is a rewrite waiting to happen.

// BAD: configuration. every new layout need is a new prop, and the component
// accumulates conditionals forever.
function Panel({ title, showHeader, showFooter, headerAlign, footerAlign, padded }) {
  return (
    <div className="panel">
      {showHeader && <h2 className={headerAlign}>{title}</h2>}
      {children}
      {showFooter && <div className={footerAlign}>{footer}</div>}
    </div>
  );
}

// GOOD: composition. the caller decides the structure entirely.
function Panel({ header, children, footer }) {
  return (
    <section className="panel">
      {header && <header className="panel-head">{header}</header>}
      <div className="panel-body">{children}</div>
      {footer && <footer className="panel-foot">{footer}</footer>}
    </section>
  );
}

<Panel
  header={<h2>Settings</h2>}
  footer={<button onClick={save}>Save</button>}
>
  <p>Arbitrary content here.</p>
  <Field name="email" />
</Panel>

The rule of thumb: if you find yourself adding a prop that is a JSX element, you probably wanted children or a named slot instead.

Fragments and the extra DOM node

2.4 DOM Structure

A component returns one node, so returning siblings requires a wrapper. A Fragment groups them without adding a DOM element.

// shorthand <> </> when you need no key
return (
  <>
    <dt>{term}</dt>
    <dd>{definition}</dd>
  </>
);

// long form when the list is an array and keys are required
return items.map((item) => (
  <React.Fragment key={item.id}>
    <dt>{item.term}</dt>
    <dd>{item.text}</dd>
  </React.Fragment>
));

A fragment is a real cost: it is a fiber node, it appears in the DevTools tree, and it participates in reconciliation. It is far cheaper than a <div> because there is no DOM node, but it is not free. Prefer a single element unless you genuinely need siblings in two places at once — CSS grid and flex will usually let you avoid the wrapper entirely.

Conditional rendering

2.5 Conditional Forms

There are four common forms, and they differ in what they do to the element tree and to component state.

// 1. ternary - an explicit either/or
{isLoading ? <Spinner /> : <Content data={data} />}

// 2. logical AND - only when you can guarantee a boolean
{hasError && <Error />}     // hasError must be boolean, not 0 or ''

// 3. early return - clearest when there is a lot of the "normal" case
if (!user) return <Skeleton />;
if (error) return <Error error={error} />;
return <Profile user={user} />;

// 4. nothing - when the two branches are siblings in an existing parent
{items.length === 0 ? null : items.map((i) => <Row key={i.id} {...i} />)}

Conditionals change identity. If {cond && <Input />} flips from false to true, a fresh Input mounts with fresh state. If that is not what you want, keep the element mounted and hide it with CSS, or lift the state to the parent so it survives. This matters most for form inputs, media players and anything holding a scroll position.

Lists and stable identity

2.6 List Keys

Rendering a list needs three things, and only the first is obvious.

function Table({ rows, onDelete }) {
  return (
    <table>
      <tbody>
        {rows.map((row) => (
          <tr key={row.id}>
            <td><input defaultValue={row.name} /></td>
            <td>
              <button onClick={() => onDelete(row.id)}>Delete</button>
            </td>
          </tr>
        ))}
      </tbody>
    </table>
  );
}

// 1. key={row.id}       identity follows the data, not the position
// 2. uncontrolled input inside it, so the state is DOM state that must
//    SURVIVE the re-render - which only works because the key is stable
// 3. a closure that captures the right row

// with key={index}, deleting row 1 makes the browser reuse the old row 2's
// DOM for what is now row 1, so the third input keeps the wrong value

Two more list details that cause real bugs:

  • Do not mutate the array you map over. React compares the array reference; mutating in place means no re-render at all. Build a new array.
  • Keys must be unique among siblings only. The same key in two different lists is fine.

Refs as a prop, and forwardRef

2.7 Refs and forwardRef

React 19 lets any component accept a ref as an ordinary prop. forwardRef is no longer needed for function components.

// React 19: ref is just a prop
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}

// the old way, still valid and still needed for class components
const Input = forwardRef(function Input(props, ref) {
  return <input ref={ref} {...props} />;
});

function Form() {
  const emailRef = useRef<HTMLInputElement>(null);

  function focusEmail() {
    emailRef.current?.focus();   // current holds the DOM node
  }

  return (
    <>
      <Input ref={emailRef} type="email" />
      <button onClick={focusEmail}>Focus email</button>
    </>
  );
}

There is also a new useImperativeHandle pattern, but reach for it rarely. Exposing a handle from a component you do not own is often the sign that state should have been lifted instead. A ref that calls focus() or measures a node is legitimate; a ref that mutates something the component does not render is usually a design mistake.

The component contract

2.8 Component Props

A component that obeys all of these is predictable, and predictability is what makes React code reviewable.

// A GOOD COMPONENT
// 1. pure: no side effects in the body, no mutation of props or state
// 2. returns the same output for the same props (memoisation-safe)
// 3. owns its own state, or receives it and treats it as read-only
// 4. does not depend on anything other than its props, context and state
// 5. can be rendered more than once on the same page without colliding
//    (no id="foo" hardcoded, no global singletons, no random on render)
// 6. unmounts cleanly: every effect returns a cleanup
// 7. has one job, and the name says what that job is

function UserBadge({ userId }: { userId: string }) {
  const { data: user } = useUser(userId);
  if (!user) return <Skeleton />;
  return <span title={user.handle}>{user.displayName}</span>;
}

// rule 5 in practice: this is why module-level state is a bug in React
let renderCount = 0;         // shared by every instance on the page
function Bad() {
  renderCount++;             // now it is not a function of props
  return <p>{renderCount}</p>
}

The exact algorithm React uses to turn a new element tree into DOM mutations. Knowing it precisely tells you which code changes are cheap and which cause remounts, which is the difference between a fast and a janky app.

The two things React compares

3.1 Comparison Algorithms

Walking a tree of elements, React asks exactly two questions at each position:

reconcileChildren(returnFiber, oldFirstChild, newChild, lanes)
  │
  ├─ Q1: is the TYPE the same?
  │     string 'div' === string 'div'      → same kind, UPDATE in place
  │     function Foo === function Foo      → same kind, UPDATE in place
  │     anything else                       → DELETE and CREATE a new fiber
  │
  └─ Q2: are the KEYS the same?
        compares the key at each child position
        same key  → UPDATE that child
        key moved → MOVE the existing fiber rather than recreate it
        no key    → fall back to matching by index

Everything else follows. Note what is not on that list: props are compared, but only to decide which host attributes to update. Props are not deeply diffed into a plan — the new props simply replace the old on the fiber, and the commit phase computes the minimal DOM change.

Reconciliation step by step

3.2 Reconciliation Steps

Given an old tree and a new tree, React does this at every level:

1. compare the root types
   differ → throw away the whole subtree, mount fresh
   same  → keep the fiber, continue

2. for each child position, in order:
   a. new has no child here, old does   → delete the old child
   b. old has no child here, new does   → create a new child fiber
   c. same key (or same index)          → recurse into updateChildFiber
   d. key exists elsewhere in the new list
      → mark the old fiber for move, place it here

3. when types match, update the fiber's memoizedProps
   and mark any host instance whose attributes changed

4. commit: walk the effect list in order and apply DOM mutations

Steps 1–3 are the render phase and produce a list of effects — not DOM changes. The commit phase walks that list once. This two-phase split is why a render can be thrown away without side effects: nothing observable happened until commit.

Same type, different props

3.3 Prop Comparison

This is the cheap case and the common one. The fiber is reused, only changed attributes are written to the DOM.

// before
<button className="btn primary" disabled={false} onClick={a}>Save</button>
// after
<button className="btn primary" disabled={true}  onClick={a}>Save</button>

// result: the same <button> DOM node, one attribute written
// state inside is preserved, focus is preserved

// the commit phase diffs host props itself
function updateHostProperties(el, oldProps, newProps) {
  for (const key of newProps) {
    if (key === 'children' || key === 'key') continue;
    if (oldProps[key] !== newProps[key]) {
      setAttribute(el, key, newProps[key]);
    }
  }
  for (const key in oldProps) {
    if (!(key in newProps)) removeAttribute(el, key);
  }
}

Different type, same position

3.4 Re-mount Cost

Here is the one that causes remounts, and it is almost always a mistake rather than a necessity.

function App({ isEditing }) {
  return (
    // when isEditing flips, the span is replaced by an input.
    // different type at the same position -> DELETE span, CREATE input
    // the input mounts with empty state, and any focus is lost
    isEditing ? <input value={name} onChange={setName} /> : <span>{name}</span>
  );
}

// the same UI, with state preserved across the toggle
function App({ isEditing }) {
  const [name, setName] = useState('');
  return isEditing
    ? <input value={name} onChange={(e) => setName(e.target.value)} />
    : <span>{name}</span>;
}
// the state now lives in App, and both branches are pure functions of it.
// nothing is ever destroyed, so nothing needs to be recreated.

// the rule: a component's identity is its POSITION IN THE TREE and its TYPE.
// changing either is a remount. Keys change position-without-destroying,
// which is why keys fix list bugs but not this one.

A common variant of this bug: rendering {loading ? <Spinner /> : content} where content is a large subtree. Every load shows a spinner, so the subtree is destroyed and rebuilt. If that subtree holds state, filter state or a media element, it resets on every refetch. Hoist the state out, or keep both mounted and hide one.

Hydration and the cost of mismatch

3.5 Hydration Cost

Server-rendered HTML has no fibers. React must hydrate: build a fiber tree by walking the existing DOM, claiming nodes as it goes, and attaching listeners. It does not re-render HTML that already matches.

// during hydration React expects the client tree to match the server HTML.
// three common causes of mismatch:

// 1. rendering the current time or a random value
function Stamp() {
  return <time>{new Date().toISOString()}</time>;   // server != client
}

// 2. reading browser-only APIs during render
function Width() {
  const [w] = useState(() => window.innerWidth);      // undefined on server
  return <p>{w}</p>;
}

// 3. invalid HTML nesting that the browser silently repairs
<div>
  <table><tr><div>oops</div></tr></table>   // browser hoists the div
</div>

// the fix pattern for browser-only values: render neutral markup on the
// server, then fill it in after mount
function Width() {
  const [w, setW] = useState<number | null>(null);
  useEffect(() => {
    const on = () => setW(window.innerWidth);
    on();
    window.addEventListener('resize', on);
    return () => window.removeEventListener('resize', on);
  }, []);
  return <p>{w ?? '--'}</p>;   // both server and first client render '--'
}

A hydration mismatch in development throws a warning and falls back to client rendering the whole root, which throws away the server HTML. In production it is silent and can leave event handlers unattached to some nodes. If you see a mismatch warning, the fix is almost always to make the first client render identical to the server render — not to suppress the warning.

What reconciliation actually costs

3.6 Performance Cost

Reconciliation is a tree walk in JavaScript. It is fast, but not free, and it scales with the size of the subtree that re-renders — not with the size of the DOM change.

// a table with 10,000 rows, one cell changes
// React walks 10,000 fibers to find that one change.
// the DOM work is 1 attribute. the JS work is O(rows).

// this is the single most important performance fact in React:
// the cost of a state change is proportional to the size of the subtree
// that re-renders, not to the amount that changes on screen.

// consequences, all of them design constraints:

// 1. state must live as low in the tree as possible
//    typing in an input inside a table cell must not re-render the table
function Bad() {
  const [query, setQuery] = useState('');
  return (
    <table>
      <tbody>
        {rows.map((r) => <Row key={r.id} query={query} onQuery={setQuery} />)}
      </tbody>
    </table>
  );
  // every keystroke re-renders all 10,000 rows
}

function Good() {
  const [query, setQuery] = useState('');
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <table>
        <tbody>
          {rows.map((r) => <Row key={r.id} row={r} />)}
        </tbody>
      </table>
    </>
  );
  // the input is its own component; the table never re-renders
}

Concurrent rendering and interruption

3.7 Concurrency

Because the render phase is pure and produces only a plan, React can stop it. Each fiber carries a lane — a priority bitmask — and the scheduler picks work by lane.

// lanes, in rough priority order
//   SyncLane            discrete input: click, keydown
//   InputContinuousLane continuous input: drag, scroll, hover
//   DefaultLane         setTimeout, promise resolution
//   TransitionLane      startTransition, useDeferredValue
//   IdleLane            anything that can wait

// a click (SyncLane) arrives while a TransitionLane render is halfway done:
//   - the in-progress render is abandoned
//   - its fibers are discarded, nothing was committed
//   - the click renders at high priority
//   - the transition restarts afterwards

function Search({ query }) {
  const [deferred] = useDeferredValue(query);
  const results = useMemo(() => filterHugeList(deferred), [deferred]);

  return (
    <>
      <input value={query} onChange={onQuery} />
      <Results items={results} isStale={deferred !== query} />
    </>
  );
}
// the input stays responsive because the expensive filter runs at low
// priority and can be interrupted. isStale tells the user what happened.

This is why concurrent features are not just an optimisation. useTransition gives you a way to say "this update is allowed to be slow", which is a statement about intent that the old synchronous model could not express. Chapter 14 covers transitions and Suspense in depth.

4 · The Component Lifecycle

What happens to a component between the moment React decides to render it and the moment its memory is reclaimed. The lifecycle is the source of most "this ran twice" and "this ran after unmount" bugs, so it is worth having precisely in your head.

The three phases

4.1 Mount Phase

// MOUNT - the component did not exist before
//   1. the component FUNCTION is called. this is a render.
//      useState initialisers run. (useReducer too.)
//      the returned JSX is reconciled against nothing -> new fibers
//   2. the DOM is created and inserted          (commit)
//   3. refs are attached                        (commit)
//   4. useLayoutEffect callbacks run           (commit, before paint)
//   5. the browser paints
//   6. useEffect callbacks run                  (after paint)

// UPDATE - props, state or context changed
//   1. the component FUNCTION is called again. this is a re-render.
//      useState/useReducer initialisers are NOT run again
//   2. reconciliation against the previous tree
//   3. DOM mutations for changed attributes   (commit)
//   4. useLayoutEffect cleanups, then callbacks, for deps that changed
//   5. paint
//   6. useEffect cleanups, then callbacks, for deps that changed

// UNMOUNT - the component is removed
//   1. useLayoutEffect cleanups run
//   2. DOM nodes are removed
//   3. useEffect cleanups run
//   4. refs are detached
//   5. the fiber is discarded, its state becomes garbage

The detail that surprises everyone: on mount, layout effects run after the DOM is inserted but before the browser paints. Passive effects run after paint. That is the whole reason both exist.

// useLayoutEffect: you must measure or adjust the DOM before the user sees it
function Tooltip({ anchorRef, text }) {
  const [pos, setPos] = useState({ top: 0, left: 0 });
  const tipRef = useRef(null);

  useLayoutEffect(() => {
    // measure the real position, then write it. doing this in useEffect
    // would let the browser paint the tooltip at 0,0 first and then jump.
    const a = anchorRef.current!.getBoundingClientRect();
    const t = tipRef.current!.getBoundingClientRect();
    setPos({ top: a.bottom + 8, left: a.left + (a.width - t.width) / 2 });
  }, [anchorRef, text]);

  return <div ref={tipRef} className="tooltip" style={{ top: pos.top, left: pos.left }}>{text}</div>;
}

// useEffect: everything else. network, subscriptions, timers, logging.
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);

Server-side rendering has no layout phase, so useLayoutEffect does not run there and warns. If you need code that works in both, guard it, or better, isolate the measurement into a child component that only renders on the client.

Rendering twice, in detail

4.2 Why Render Twice

"Why did my component render twice?" has three distinct answers, and they are easy to tell apart.

// cause 1: StrictMode, development only
// React deliberately double-invokes the render phase to expose impurity.
// also double-invokes the initialiser, and mounts+unmounts+remounts effects.
// never happens in a production build.

// cause 2: a discarded concurrent render
// a render at low priority that gets interrupted and restarted will call
// your function again. the first result is thrown away. also development-ish:
// in production you can hit this with a transition that is superseded.

// cause 3: a genuine second update in the same commit
function Form() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);

  useEffect(() => { setB(1); }, [a]);   // sets state
  // a changes -> render 1 (a=1, b=0)
  // the effect fires  -> setB -> render 2 (a=1, b=1)
  // two real renders, both legitimate
}

// the diagnostic: is the second render's output identical?
// if yes, React bails out on the host update even though the function ran
// if no, something actually changed and you want to know what

To find out why a component re-rendered, do not add a log to the component. Wrap the component in React.memo and put the log in a custom comparison function — it only runs when props are compared, which is exactly when you want to know. Or use the DevTools Profiler, which shows the reason for each commit.

What causes a re-render

4.3 Render Triggers

There are only four triggers. Knowing the full list makes most re-render puzzles solvable by inspection.

// 1. the component's own state changed
setCount(1);

// 2. its parent re-rendered
//    this is the big one. nothing about THIS component changed, but its
//    parent rendered, so reconciliation walked down to it and called it
//    again. this is why children re-render, and it is not a bug.

// 3. a context it consumes changed
const theme = useContext(ThemeContext);
// every component reading ThemeContext re-renders when the provider's
// value changes, no matter how far down the tree it is

// 4. it is subscribed to an external store
// useSyncExternalStore: a store outside React that notifies subscribers
// this is how you avoid routing libraries and global-state libraries
// forcing the whole tree to render
// the classic "why does my whole page re-render on every keystroke"
function Page() {
  const [query, setQuery] = useState('');
  const [theme] = useState('dark');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ExpensiveTree />
    </ThemeContext.Provider>
  );
}
// typing re-renders Page, which re-renders ExpensiveTree, because
// reconciliation walks the whole subtree regardless of whether the
// element object for ExpensiveTree changed identity.

// three fixes, in order of preference
// 1. lift the input into its own component so Page does not re-render
// 2. memoize the context value, or split fast-changing and slow-changing
//    values into two contexts
// 3. React.memo(ExpensiveTree) - works, but see chapter 12 for the caveats

The commit phase

4.4 Side Effects

Commit is synchronous and uninterruptible. React walks the effect list in tree order and applies every change. There is no yielding, so a slow commit blocks the main thread — which is why a commit should only do small amounts of DOM work.

// the effect list is built during render, applied during commit
// it includes:
//   - host mutations (set text, set attribute, insert node, remove node)
//   - ref attachment and detachment
//   - useLayoutEffect: cleanup of the previous run, then the new callback
//   - useEffect: queued into a separate passive list, flushed after paint

// cleanup-before-callback is a detail worth knowing:
// when deps change from [a] to [b], React runs
//   cleanup([a])   then   effect([b])
// NOT   effect([b]) then cleanup([a])
// so a cleanup always sees the values it was created with, and a
// subscription is never briefly doubled.

Mount, update and cleanup

4.5 Dependency Arrays

The dependency array is the whole API. There are exactly four forms and they mean different things.

// no array: runs after EVERY render, cleanup after every render
useEffect(() => {
  log('rendered');
});   // effectively what useEffect(fn, [somethingUnstable]) does

// [] : runs once after mount, cleanup on unmount
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);

// [a, b] : when a or b change by Object.is, and on mount
useEffect(() => {
  subscribe(a, b);
  return () => unsubscribe(a, b);
}, [a, b]);

// a function is not a dependency value - inline functions re-create every
// render, so the effect re-runs every render
useEffect(() => {
  doThing(onSave);   // onSave is a new function every render
}, [onSave]);        // so this runs on every render

// if you truly need the latest value without re-running, use a ref
const onSaveRef = useRef(onSave);
useEffect(() => { onSaveRef.current = onSave; });
useEffect(() => {
  const id = setInterval(() => onSaveRef.current(), 1000);
  return () => clearInterval(id);
}, []);   // runs once, but always calls the newest onSave

The StrictMode cleanup rehearsal

4.6 StrictMode Cleanup

In development, React runs every effect's setup, then its cleanup, then its setup again. This is a rehearsal, and it catches the most common class of leak.

// BROKEN: no cleanup, so the second setup doubles the subscription
useEffect(() => {
  const id = setInterval(tick, 1000);
}, []);   // in StrictMode: two intervals. in production: one, until unmount.

// BROKEN: cleanup references a value that is not the one subscribed
useEffect(() => {
  const id = setInterval(() => send(value), 1000);
  return () => clearInterval(id);
}, [channelId]);   // value is used but not a dependency: a stale closure

// CORRECT: cleanup closes over exactly what setup created
useEffect(() => {
  const id = setInterval(() => send(value), 1000);
  return () => clearInterval(id);
}, [channelId, value]);   // re-subscribes when value changes, which is correct

Do not "fix" a StrictMode double-invoke by adding a guard flag inside the effect. That hides a real leak in production. The rehearsal is telling you the truth: the effect is not idempotent, and if it is ever mounted twice — a remount, a route change, a conditional — it will leak. Make setup and cleanup symmetric instead.

Unmounting and its traps

4.7 Unmount Cleanup

Unmount does not interrupt anything. If an async operation started during mount is still in flight when the component unmounts, it will try to set state on a dead component. React 18+ no longer warns, and it is not a memory leak — but the work is wasted and any side effect after the await will still happen.

function User({ id }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    let live = true;
    fetch(`/users/${id}`)
      .then((r) => r.json())
      .then((u) => { if (live) setUser(u); });
    return () => { live = false; };
  }, [id]);

  return user ? <Profile user={user} /> : <Skeleton />;
}

// the flag pattern. abort() is better where available:
useEffect(() => {
  const ac = new AbortController();
  fetch(`/users/${id}`, { signal: ac.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch((e) => { if (e.name !== 'AbortError') throw e; });
  return () => ac.abort();
}, [id]);

// class components get a different hook entirely
class Old extends React.Component {
  componentDidMount()   { this.timer = setInterval(this.tick, 1000); }
  componentWillUnmount() { clearInterval(this.timer); }
  shouldComponentUpdate(next) { return next.id !== this.props.id; }
}

Two things that are fine to leave running past unmount: read-only data fetching with no side effects, and requests you want to finish anyway. Cancelling is only necessary when continuing would cause a visible problem — a stale write, a lost update, a navigation that should abort. It is not free: aborting and retrying can cost more than letting a small request complete.

5 · State and the Mental Model

Two kinds of stateWhere should state live?Derived state, and why it is not stateColocating state with its ownerLifting state up, carefullyShape state as a machineImmutability and why it is requiredChoosing a state library

The reasoning that decides where every piece of state lives. Most React codebases are hard because of this decision, not because of any hook. The goal of this chapter is a repeatable procedure rather than intuition.

Two kinds of state

Every piece of state in a React app is one of two things, and treating them differently is the single highest-leverage habit you can build.

// A. LOCAL / UI STATE
// belongs to one component, cannot be derived, does not need to persist
//   - is the dropdown open
//   - the current text in an input before submit
//   - which tab is selected
//   - a loading flag for one button
// useState, in the component that needs it. usually the default.

// B. SHARED / APPLICATION STATE
// more than one component reads or writes it, or it outlives a route change
//   - the signed-in user
//   - a shopping cart
//   - server data that several screens touch
//   - a feature flag
// belongs higher up, in context, a store, or a cache.

// the diagnostic question, asked until the answer is clear:
//   "who reads this?"
//    exactly one component            -> local
//    more than one, at the same time -> lift to their nearest common parent
//    more than one, in different places -> context or a store
//    nobody, it was a cache           -> it should not be state at all

Shared state is the most common source of over-engineering. If two components in the same file need to agree on something, lift it to the component that renders both — not to a global store. A provider six levels up that two components read is worse than a prop, because you have lost the ability to see the data flow.

Where should state live?

A procedure that works. Start at the component that uses the value and walk up, and stop at the first ancestor that has a reason to know it.

// 1. does anything else read or write it?
//      no  -> keep it here, in this component

// 2. can it be computed from existing state or props?
//      yes -> do not store it. compute during render. (see ch5-derived)

// 3. does it need to survive this component unmounting?
//      yes -> lift to the nearest ancestor that outlives it

// 4. do siblings both need it?
//      yes -> lift to their closest common parent

// 5. do unrelated parts of the app need it?
//      yes -> context, a store, or a server cache

// 6. does it need to survive a page reload?
//      yes -> localStorage, IndexedDB or a cookie, not React state

Step 3 is the one people skip. State that must survive unmount cannot live in the unmounting component. A form on a route, a shopping cart read from three routes, a draft the user should not lose by navigating — all of these need an owner that outlives the screen. Decide where the owner is before writing the form, not after the bug report.

Derived state, and why it is not state

If a value can be computed from other state during render, storing it creates a second source of truth that can disagree with the first. This is the most common avoidable bug class in React.

// WRONG: two sources of truth that can drift
function Cart() {
  const [items, setItems] = useState([]);
  const [total, setTotal] = useState(0);

  function add(item) {
    setItems([...items, item]);
    setTotal(total + item.price);   // now there are two things to update,
  }                                 // and a discounted or refunded item
  return <div>{total}</div>;   // makes them disagree
}

// RIGHT: one source of truth
function Cart() {
  const [items, setItems] = useState([]);
  const total = items.reduce((sum, i) => sum + i.price, 0);
  return <div>{total}</div>;
}

// the tell: you have a useEffect whose whole job is to setState from
// other state. that is derived state wearing a disguise.
useEffect(() => { setTotal(compute(items)); }, [items]);  // delete this

The subtlety is that some values are cheap to compute and some are expensive. Sorting a 10,000-row list on every keystroke is not free, and then useMemo becomes the right tool — but it is still not state, because there is no synchronisation to get wrong.

// cheap: just compute it
const fullName = `${first} ${last}`;
const isEmpty = items.length === 0;
const progress = Math.min(done / total, 1);

// expensive and pure: memoise, still not state
const sorted = useMemo(
  () => [...items].sort((a, b) => a.rank - b.rank),
  [items],
);

// expensive AND has side effects: that is a server cache, not useMemo.
// see chapter 15.

// the test: if you cannot delete the value and compute it in one line,
// it might be state. if you can, it is not.
function Bad() {
  const [filtered, setFiltered] = useState([]);
  useEffect(() => {
    setFiltered(items.filter((i) => i.active));
  }, [items]);
  return <List items={filtered} />;
}

function Good() {
  const filtered = items.filter((i) => i.active);
  return <List items={filtered} />;
}

Colocating state with its owner

Keep state as close to where it is used as possible. Colocation is not just tidiness: it bounds the blast radius of a re-render automatically.

// state in the component that uses it: only that component re-renders
function Row({ item }) {
  const [editing, setEditing] = useState(false);
  const [draft, setDraft] = useState(item.name);

  if (editing) {
    return (
      <>
        <input value={draft} onChange={(e) => setDraft(e.target.value)} />
        <button onClick={() => { save(item.id, draft); setEditing(false); }}>Save</button>
      </>
    );
  }
  return <div onDoubleClick={() => setEditing(true)}>{item.name}</div>
}

// if this state lived in the table, all 10,000 rows would re-render
// on every keystroke. the architecture choice IS the performance choice.

// (a controlled form whose value is submitted by the parent), lift it

Lifting state up, carefully

Lifting is the correct default for shared state, but it costs re-renders and loses locality. Do it when the data genuinely must be shared, and no earlier than necessary.

// lift to the closest common ancestor - not higher
function Accordion() {
  const [open, setOpen] = useState<string | null>(null);
  return (
    <div>
      {sections.map((s) => (
        <Section
          key={s.id}
          section={s}
          isOpen={open === s.id}
          onToggle={() => setOpen(open === s.id ? null : s.id)}
        />
      ))}
    </div>
  );
}

// Accordion needs to know which is open, so it owns the state.
// Section receives a boolean and a callback, so Section owns nothing
// beyond its own transient UI. neither of them re-renders needlessly.

// what lifting costs: every consumer of that state re-renders on change.
// if the value changes often and the tree below is large, consider
// splitting it out of the render path with a store selector (ch5-choices)

Shape state as a machine

When several booleans describe one thing, they will eventually contradict each other. Model the thing, not the flags.

// WRONG: five booleans, no invalid combinations prevented
const [loading, setLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);

Immutability and why it is required

React compares state with Object.is. If you mutate, the comparison says "unchanged" and no re-render happens — a bug with no error message.

// WRONG: mutates. Object.is(oldArray, newArray) is true, so nothing happens
const [rows, setRows] = useState([{ id: 1, done: false }]);

function toggle() {
  rows[0].done = true;
  setRows(rows);              // same reference: React does not re-render
}

// WRONG: mutates a nested object. The top-level reference changed, so React
// re-renders, but the reference passed to memoised children did not.
function rename() {
  user.profile.name = 'New';
  setUser({ ...user });       // user is new, but user.profile is the SAME object
}

// RIGHT
setRows(rows.map((r) => (r.id === 1 ? { ...r, done: true } : r)));
setUser((u) => ({ ...u, profile: { ...u.profile, name: 'New' } }));

// this is why Immer exists: it lets you write mutations and produces
// new references only for what actually changed
import { produce } from 'immer';
setUser(produce(user, (draft) => { draft.profile.name = 'New'; }));

Arrays have traps worth memorising. push, splice, sort and reverse all mutate. Use push into a copy, toSorted / toReversed / toSpliced (ES2023) or [...arr].sort(). sort in particular mutates and is a frequent cause of "the list is in the wrong order" reports that only appear sometimes.

Choosing a state library

For most applications you need none of the big libraries. Here is the order of escalation.

// 1. nothing. useState plus a few lifted values. covers the majority of apps.

// 2. useReducer. when one update touches several fields at once, or the
//    transitions deserve names
function reducer(state, action) {
  switch (action.type) {
    case 'drag/start': return { ...state, dragging: action.id, from: index(state, action.id) };
    case 'drag/move':  return { ...state, to: overIndex(state, action) };
    case 'drag/end':   return reorder(state);
    case 'drag/cancel':return { ...state, dragging: null, to: null };
  }
}
// one action updates dragging, from and to together. three useStates
// would need three setters and an intermediate invalid state where
// dragging is set but to is not.

// 3. a store with selectors, for genuinely global client state.
//    Zustand is the smallest useful option; Jotai is atom-based.
//    useSyncExternalStore under the hood, so it does not force the
//    whole tree to re-render - components subscribe to what they read.
const count = useStore((s) => s.count);   // only re-renders when count changes

// 4. a server cache for data from the network. React Query or SWR.
//    this is not application state - it is a cache of something you do
//    not own. do not copy it into useState; see chapter 15.

// 5. a URL router for navigation state. the location IS the state.
//    a filter page whose state is in the URL is shareable and survives
//    a reload. see chapter 16.

Whatever you pick, the state must be inspectable. Redux DevTools time travel, Zustand's subscribe in the console, React Query's cache inspector — the point is that you can answer "what is the state right now and how did it get here" without adding a console.log. If a tool cannot, it will cost you more than it saves.

The signature and what it returns

const [state, setState] = useState<T>(initialState: T | (() => T)): [T, Dispatch<SetStateAction<T>>];

// the setter is stable for the lifetime of the component. it is safe to
// omit it from dependency arrays, and it is the same function identity
// on every render - which is why passing setState to a memoised child
// does not break its memoisation

// SetStateAction<T> = T | ((prev: T) => T)
// the setter accepts either a new value or a function of the previous

// what it does NOT do
const [count, setCount] = useState(0);
setCount(5);
console.log(count);   // still 0. state updates are queued, not immediate.
console.log(count);   // still 0, even in the same synchronous block.

This is worth internalising as a general fact: your count variable is a snapshot from the render that is currently executing. Mutating it is impossible, and reading it after a setter gives you the old value. Code that reads like imperative code does not work, and that is the design, not a limitation.

Lazy initialisation

Passing a function is not just an optimisation — it is a semantic difference.

// EAGER: runs on every render, and the result is thrown away
const [rows] = useState(buildRows());          // buildRows() called every time
const [config] = useState(JSON.parse(text));   // parse on every render

// LAZY: React calls the function once, on mount, and uses the result
const [rows] = useState(() => buildRows());
const [config] = useState(() => JSON.parse(text));

// the distinction matters when the initialiser is expensive
const [graph] = useState(buildHugeGraph);       // still eager: returns a graph object
const [graph] = useState(() => buildHugeGraph()); // lazy: correct

// also required when the initial value IS a function
const [onClick] = useState(() => () => alert('hi'));
// useState(handleClick) would CALL handleClick and store its return value

Under StrictMode the initialiser runs twice in development and React keeps one result. So an impure initialiser — one that writes to a module variable, generates a random id, or increments a counter — will behave differently in development and production. Treat any such warning as a real bug, and use useState(() => crypto.randomUUID()) rather than a bare random id at mount.

The updater form and stale closures

When the next value depends on the previous, use the updater form. The direct form closes over the value from the current render, so rapid updates lose each other.

function Counter() {
  const [count, setCount] = useState(0);

  // BROKEN: three clicks in quick succession. each handler closes over
  // count === 0 from the render it was created in, so the final value is 1.
  function broken() { setCount(count + 1); setCount(count + 1); setCount(count + 1); }

  // CORRECT: each update receives the latest queued value
  function correct() { setCount((c) => c + 1); setCount((c) => c + 1); setCount((c) => c + 1); }
  // 0 -> 1 -> 2 -> 3, one render
}

// THE REAL-WORLD VERSION: the stale closure in an async callback
function useOnlineUsers(roomId: string) {
  const [users, setUsers] = useState<User[]>([]);

  useEffect(() => {
    const id = setInterval(async () => {
      const fresh = await fetch(`/rooms/${roomId}/online`).then((r) => r.json());
      setUsers(fresh);              // fine: replaces, does not derive
    }, 5000);
    return () => clearInterval(id);
  }, [roomId]);

  function add(user: User) {
    setUsers((prev) => [...prev, user]);   // MUST be updater: prev is latest
  }
  return [users, add] as const;
}

// this render - which is exactly the bug in every "two users clicked
// follow at the same time and only one appears" report
// derived state in a callback: the updater form is also the fix for
// "the count is off by one" in every other framework

//   setX((prev) => compute(prev))   when it does

State identity is per-position

Hooks are matched by their order of call, not by name. This is the single most surprising fact about hooks and it explains an entire class of bug.

// CONDITIONAL HOOKS ARE A BUG, not a style question
function Counter({ enabled }) {
  const [a, setA] = useState(0);
  if (enabled) {
    const [b, setB] = useState(0);   // hook 2 only when enabled
  }
  // when enabled flips, hook 2's slot is now slot 1 - and slot 1 already
  // holds a. React reads the wrong fiber. you get 'b' containing a's value
  // and a's value is lost. this is why the rule exists.
}

// the rule, and it is not negotiable:
// call hooks unconditionally, at the top level of a component or a custom hook

// the correct shape: same hook count in every render
function Counter({ enabled }) {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);      // always called
  useEffect(() => {
    if (enabled) { run(); }           // the CONDITION goes inside
  }, [enabled]);
}

// the same rule applies to loops and early returns
for (const item of items) {
  const [x, setX] = useState(item);  // hook count changes with items.length
}
if (!ready) return <Skeleton />;    // early return skips later hooks

Related: do not call a component like a function (MyComponent(props)). That bypasses React entirely — no hook state, no memoisation, no reconciliation. React needs to own the call. The exception is components that are genuinely just pure functions with no hooks, and even then, avoid it.

Batching and multiple updates in one event

  // is lost. the updater form fixes it:

Writing your own state hook

Once you have the mental model, custom hooks are easy — and worth writing, because they encode a decision once instead of at every call site.

// a toggle with the same semantics everywhere
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  const setTrue = useCallback(() => setOn(true), []);
  const setFalse = useCallback(() => setOn(false), []);
  return { on, toggle, setTrue, setFalse } as const;
}

// a persisted value
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = window.localStorage.getItem(key);
      return raw ? (JSON.parse(raw) as T) : initial;
    } catch {
      return initial;          // private mode, quota, corrupt JSON
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {
      // quota exceeded. state still works, it just will not persist
    }
  }, [key, value]);

  return [value, setValue] as const;
}

// an async request with the states from ch5-shape
function useAsync<T, A extends unknown[]>(fn: (...args: A) => Promise<T>) {
  const [state, setState] = useState<RequestState<T>>({ status: 'idle' });
  const lastArgs = useRef<A | null>(null);

  const run = useCallback(async (...args: A) => {
    lastArgs.current = args;
    setState({ status: 'loading' });
    try {
      const data = await fn(...args);
      setState({ status: 'success', data });
    } catch (e) {
      setState({ status: 'error', error: e as Error });
    }
  }, [fn]);

  // deps on a ref are read during render, not tracked by the dep array,
  // so run() can stay referentially stable
  const retry = useCallback(() => {
    if (lastArgs.current) run(...lastArgs.current);
  }, [run]);

  return [state, run, retry] as const;
}

A reducer is not a more powerful useState. It is a different tool for a different problem: when one logical change must update several fields at once, without passing through an impossible intermediate state.

When to reach for a reducer

Three signals, in rough order of strength.

// SIGNAL 1: one action, several fields. three useStates cannot express
// "these three change together" without an intermediate render where only
// some of them have changed.
const [loading, setLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);
function load() {
  setLoading(true);
  setError(null);      // render 1: loading, data still the OLD data
  fetch(url)
    .then(setData)
    .catch(setError)
    .finally(() => setLoading(false));  // render 2, 3, 4
}

// SIGNAL 2: the transitions have names worth documenting. a drag has
// start, move, end and cancel. four boolean flags and combinations of
// them encode a state machine nobody can read.

// SIGNAL 3: the logic is worth unit-testing in isolation. a reducer is a
// pure function, so you can test it without rendering anything.

// when NOT to use one:
//   - a single independent value (useState)
//   - a derived value (compute it; see ch5-derived)
//   - server data (a cache library owns it; see ch15)

The anatomy of a reducer

import { useReducer } from 'react';

type State = { count: number; step: number };

type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'setStep'; step: number }
  | { type: 'reset' };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'increment': return { ...state, count: state.count + state.step };
    case 'decrement': return { ...state, count: state.count - state.step };
    case 'setStep':   return { ...state, step: action.step };
    case 'reset':     return { count: 0, step: 1 };
    default: {
      // exhaustiveness: remove this and adding a new Action type is a
      // compile error at every place that forgets to handle it
      const _never: never = action;
      return _never;
    }
  }
}

const [state, dispatch] = useReducer(reducer, { count: 0, step: 1 });

// dispatch is STABLE, like a useState setter. safe in dep arrays.
// the initial state can be lazy: useReducer(reducer, initialArg, init)

The default: never branch is the highest-value line in most reducers. It turns "someone added a case and forgot to handle it here" from a silent wrong result at runtime into a compile error. Costs two lines, catches the bug at build time.

Designing actions

The reducer's quality is bounded by its action vocabulary. Design the actions as the domain's vocabulary, not as setter calls.

// BAD: actions named after the implementation
type Action =
  | { type: 'setLoading'; value: boolean }
  | { type: 'setError'; value: Error | null }
  | { type: 'setData'; value: User };

// these encode HOW to change the view, so every caller must know the
// implementation, and impossible combinations are constructible

// GOOD: actions named after what happened in the domain
type Action =
  | { type: 'request/started' }
  | { type: 'request/succeeded'; user: User }
  | { type: 'request/failed'; error: Error }
  | { type: 'request/retried' };

// now 'loading' is not a field at all. it is implied by which action
// produced the current state, so "loading AND has data" is unrepresentable

type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'loaded'; user: User }
  | { status: 'error'; error: Error };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'request/started':  return { status: 'loading' };
    case 'request/succeeded': return { status: 'loaded', user: action.user };
    case 'request/failed':    return { status: 'error', error: action.error };
    case 'request/retried':   return { status: 'loading' };
  }
}

Naming convention that scales well: domain/verb or domain/noun-ed — cart/itemAdded, form/fieldChanged, auth/signedOut. The prefix groups related actions and makes a long switch readable, and it survives a rename of the reducer.

Transitions that must be atomic

This is the core justification. Here is a three-state interaction that is painful with useState and clean with a reducer.

type State =
  | { mode: 'idle' }
  | { mode: 'dragging'; id: string; from: number; x: number }
  | { mode: 'dropping'; id: string; to: number; x: number }
  | { mode: 'reordering'; order: string[] };

type Action =
  | { type: 'grab'; id: string; index: number; x: number }
  | { type: 'move'; x: number }
  | { type: 'hover'; index: number }
  | { type: 'release' }
  | { type: 'cancel' }
  | { type: 'animationEnded' };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'grab':
      return { mode: 'dragging', id: action.id, from: action.index, x: action.x };
    case 'move':
      // only meaningful while dragging
      return state.mode === 'dragging' ? { ...state, x: action.x } : state;
    case 'hover':
      return state.mode === 'dragging' ? { ...state, to: action.index } as State : state;
    case 'release':
      return state.mode === 'dragging' && 'to' in state
        ? { mode: 'dropping', id: state.id, to: state.to, x: state.x }
        : state;
    case 'animationEnded':
      if (state.mode !== 'dropping') return state;
      return { mode: 'reordering', order: reorder(state.from, state.to) };
    case 'cancel':
      return state.mode === 'idle' ? state : { mode: 'idle' };
  }
}

// WHY THIS IS BETTER THAN FOUR useStates
//   - 'to' only exists while dragging or dropping, because it is a field
//     of those variants. there is no 'to' to leave stale.
//   - move() while idle is a no-op by construction, not by a guard in
//     every event handler
//   - the animation completion cannot arrive before release, because
//     release is the only way to reach 'dropping'
//   - the whole interaction is testable as a function with no DOM

Keeping the reducer pure

A reducer must be a pure function: same state and action gives the same result, no side effects, no reading of anything outside its arguments.

// NOT PURE: an async call inside the reducer
function reducer(state, action) {
  switch (action.type) {
    case 'load':
      fetch('/api').then((r) => r.json()).then(setData);
      return { ...state, loading: true };   // the fetch escaped
    default: return state;
  }
}
// the reducer may run twice under StrictMode, may run during a discarded
// concurrent render, and must return synchronously. A promise is not a
// return value, so the result is already wrong before the fetch lands.

// the split: reducer computes, effect performs
function useLoader() {
  const [state, dispatch] = useReducer(reducer, { status: 'idle' as Status });

  useEffect(() => {
    const ac = new AbortController();
    dispatch({ type: 'load/started' });

    fetch('/api', { signal: ac.signal })
      .then((r) => r.json())
      .then((data) => dispatch({ type: 'load/succeeded', data }))
      .catch((e) => {
        if (e.name !== 'AbortError') dispatch({ type: 'load/failed', error: e });
      });

    return () => ac.abort();
  }, []);

  return state;
}

// reducers that need the current time or randomness should receive it
// as part of the action, so the reducer stays pure and testable
type Action = { type: 'item/added'; item: Item; at: number };  // at: Date.now()

Returning the same state object is a deliberate and correct optimisation: React bails out of re-rendering when the new state is Object.is-equal to the old. The move-while-idle case above relies on it. Return the existing state rather than a shallow copy, and the bail-out happens for free.

Composing reducers

For a screen with several independent concerns, one reducer with a growing switch is worse than a small reducer per concern. Compose them with useReducer per slice and combine at the point of use.

// each slice owns its own transitions, and the page owns the coordination
function useCheckout() {
  const [customer, customerDispatch] = useReducer(customerReducer, initialCustomer);
  const [items, itemsDispatch] = useReducer(itemsReducer, initialItems);
  const [payment, paymentDispatch] = useReducer(paymentReducer, initialPayment);

  // cross-slice transitions live here, not inside any one reducer
  function placeOrder() {
    if (items.lines.length === 0) return;
    customerDispatch({ type: 'customer/markedAsNotNew' });
    itemsDispatch({ type: 'items/cleared' });
    paymentDispatch({ type: 'payment/submitted' });
  }

  return { customer, items, payment, dispatch: { customer: customerDispatch, items: itemsDispatch, payment: paymentDispatch } };
}

// and a generic combineReducers, so the top-level reducer stays a list
type ReducerMap<S> = { [K in keyof S]: (state: S[K], action: Action) => S[K] };

function combineReducers<S>(map: ReducerMap<S>, initial: S) {
  return (state: S, action: Action): S => {
    let changed = false;
    const next = {} as S;
    for (const key of Object.keys(map) as (keyof S)[]) {
      const prev = state[key];
      const updated = map[key](prev, action);
      next[key] = updated;
      if (!Object.is(prev, updated)) changed = true;
    }
    return changed ? next : state;   // bail out when nothing moved
  };
}

Testing a reducer

The strongest argument for reducers: the most important logic in a component is a pure function you can test with no DOM, no renderer and no async.

8 · Effects and the Rules That Govern Them

Effects are React's escape hatch for the world outside React, and the source of its most confusing bugs. The dependency array is a claim about your code, and most effect bugs are false claims.

What an effect is for

An effect exists for one job: synchronising with something outside React. Everything else it is used for is a workaround.

// LEGITIMATE USES - all of these involve the outside world
useEffect(() => { const id = setInterval(tick, 1000); return () => clearInterval(id); }, []);
useEffect(() => { const ws = new WebSocket(url); return () => ws.close(); }, [url]);
useEffect(() => { observer.observe(ref.current!); return () => observer.disconnect(); }, []);
useEffect(() => { document.title = title; }, [title]);
useEffect(() => { track('page_view', { id }); }, [id]);

// ILLEGITIMATE USES - all of these are mistakes
useEffect(() => { setTotal(a + b); }, [a, b]);           // derived state
useEffect(() => { document.body.onclick = handler; }, []);  // use a listener, not an effect
useEffect(() => { if (props.onChange) props.onChange(1); }, [props.onChange]); // run in event handler
useEffect(() => { setInterval(tick, 1000); }, []);        // no cleanup: leaks

// the test: name the thing outside React you are synchronising with
//   "a timer"      -> yes
//   "a websocket"  -> yes
//   "the document title" -> yes
//   "nothing, I just want it to happen" -> no, use an event handler

The dependency array, precisely

Every value from the component scope used inside the effect must be in the array. Not "the ones that change", not "the ones that look stateful" — all of them.

function Bad({ userId, onSave }) {
  useEffect(() => {
    fetch(`/users/${userId}`).then((r) => r.json()).then(onSave);
  }, []);   // missing userId AND onSave
  // userId changes and nothing happens. onSave closes over a stale prop.
}

// eslint will offer to "fix" this by adding both. it is right, and the
// result is an effect that re-runs on every userId change, which is
// usually also what you wanted.

function Good({ userId, onSave }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    const ac = new AbortController();
    fetch(`/users/${userId}`, { signal: ac.signal })
      .then((r) => r.json())
      .then(setUser);
    return () => ac.abort();
  }, [userId]);   // onSave is deliberately NOT needed - we do not use it
}

function WithCallback({ userId, onSave }) {
  useEffect(() => {
    const id = setInterval(() => {
      save(userId, onSave);   // both used, so both are dependencies
    }, 1000);
    return () => clearInterval(id);
  }, [userId, onSave]);
  // onSave is often a new function every render, so this re-subscribes
  // every render. the fix is to make onSave stable, not to lie about deps
}

Do not silence the dependency lint by lying. Emptying the array when the linter complains produces exactly the stale-closure bug the linter was warning about. Either include the value, or restructure so the value is not needed — a ref, a useCallback at the parent, or moving the logic into an event handler.

Cleanup is not optional

// EVERY effect that acquires something must release it
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);          // the whole reason this is safe
}, []);

// the four acquisitions, and their release
//   timer        -> clearInterval / clearTimeout
//   listener     -> removeEventListener
//   subscription -> the unsubscribe the API returned
//   connection   -> close / abort / disconnect

// cleanup runs:
//   - before the effect re-runs with changed deps
//   - on unmount
//   - once more in StrictMode development (the rehearsal, ch4-strict-cleanup)

// returning a value that is NOT a function is a common crash
useEffect(() => {
  fetch(url);          // fetch returns a PROMISE
  return fetch(url);   // React tries to call the promise as a cleanup
}, []);                 // -> "destroy is not a function"

// a promise IS a function-like mistake to avoid:
useEffect(() => {
  let ignore = false;
  load().then((d) => { if (!ignore) setData(d); });
  return () => { ignore = true; };   // returns undefined, which is fine
}, []);

The four effect categories

// 1. RUN ONCE, ON MOUNT - setup/teardown of a long-lived resource
useEffect(() => {
  const conn = connect();
  conn.on('message', handle);
  return () => conn.close();
}, []);

// 2. RUN ON CHANGE - resync with a prop or state
useEffect(() => {
  document.title = `${count} items`;
}, [count]);

// 3. RUN EVERY RENDER - almost always a mistake; if you want it, say why
useEffect(() => {
  log('render', count);
});   // in a component with no deps array

// 4. EXTERNAL STORE SYNC - the escape hatch for a non-React source of truth
useEffect(() => {
  return store.subscribe(() => setState(store.getState()));
}, []);

// in practice 1 and 2 are 95% of correct code, and 3 is a bug report
// wearing a costume

Stale closures and the ref fix

Every render creates a new closure over that render's props and state. An effect that runs later still sees the values from the render in which it was created.

// THE BUG: an effect with [] captures the FIRST render's props forever
function Chat({ roomId, onMessage }) {
  useEffect(() => {
    const ws = new WebSocket(`/ws/${roomId}`);
    ws.onmessage = (e) => {
      onMessage(JSON.parse(e.data));   // this is onMessage from the FIRST
    };                                 // render, forever
    return () => ws.close();
  }, [roomId]);
  // if the parent re-creates onMessage, the socket still calls the old one
}

// FIX A: put it in the dependencies. correct, but re-subscribes whenever
// onMessage changes, which for an inline arrow means every render.
useEffect(() => { /* ... */ }, [roomId, onMessage]);

// FIX B: keep the subscription stable, read the latest value from a ref
function useEvent<A extends unknown[], R>(fn: (...args: A) => R) {
  const ref = useRef(fn);
  useEffect(() => { ref.current = fn; });   // no deps: updates every render
  return useCallback((...args: A) => ref.current(...args), []);
}

function Chat({ roomId, onMessage }) {
  const stableOnMessage = useEvent(onMessage);
  useEffect(() => {
    const ws = new WebSocket(`/ws/${roomId}`);
    ws.onmessage = (e) => stableOnMessage(JSON.parse(e.data));
    return () => ws.close();
  }, [roomId]);   // onMessage is NOT a dependency, and never stale
}

// the "latest ref" pattern, spelled out, if you do not want a helper
const onMessageRef = useRef(onMessage);
useEffect(() => { onMessageRef.current = onMessage; });
useEffect(() => {
  const ws = new WebSocket(url);
  ws.onmessage = (e) => onMessageRef.current(parse(e.data));
  return () => ws.close();
}, [url]);

useEffectEvent is being standardised for exactly the useEvent pattern above, and React 19 canary exposes it. Until it is stable, the twenty-line hook is the portable answer, and it makes the intent ("I want the newest value, but I do not want to re-subscribe") explicit at the call site.

Cancellation and races

Effects that start async work must handle the case where the work finishes after the effect has been cleaned up — or after a newer request has started.

// RACE CONDITION: two requests, the second starts later but the first
// finishes later, and the slow stale response overwrites the fresh one
function useSearch(query: string) {
  const [results, setResults] = useState<Result[]>([]);

  useEffect(() => {
    fetch(`/api/search?q=${query}`)
      .then((r) => r.json())
      .then(setResults);      // whichever resolves LAST wins
  }, [query]);
  // type "a", then "ab" quickly. if "ab" responds first, then "a"
  // responds, you see the results for "a" while the box says "ab".

// FIX 1: AbortController - cancels the previous request on cleanup
useEffect(() => {
  const ac = new AbortController();
  fetch(`/api/search?q=${query}`, { signal: ac.signal })
    .then((r) => r.json())
    .then(setResults)
    .catch((e) => { if (e.name !== 'AbortError') throw e; });
  return () => ac.abort();
}, [query]);

// FIX 2: an ignore flag, when you cannot abort
useEffect(() => {
  let live = true;
  load(query).then((d) => { if (live) setResults(d); });
  return () => { live = false; };
}, [query]);

// FIX 3: a request id, when results must not be discarded but must be
// ordered. used by every server-cache library under the hood
let latest = 0;
useEffect(() => {
  const myId = ++latest;
  load(query).then((d) => { if (myId === latest) setResults(d); });
}, [query]);

AbortController is strictly better than the ignore flag: it stops the wasted work, frees the connection for the pool, and the server sees the client hang up. The flag is for APIs you cannot cancel — an image preload, a third-party script tag.

Seven effect traps

// 1. FETCH IN AN EFFECT
// React 19's `use` hook, or a cache library, owns requests. Fetching in
// an effect means hand-managing loading, error, race and cancellation -
// all of which chapter 15 hands you for free.
useEffect(() => { fetch(url).then(r => r.json()).then(setData); }, [url]);   // no

// 2. RESETING STATE ON PROP CHANGE
function List({ userId }) {
  const [items, setItems] = useState([]);
  useEffect(() => { setItems([]); }, [userId]);   // extra render, and a flash
}
// instead: key the component, or derive, or include the id in the state
<List key={userId} userId={userId} />

// 3. AN EFFECT THAT SETS STATE IMMEDIATELY
useEffect(() => { setCount(count + 1); }, []);   // runs twice in StrictMode
// almost always means the value should be computed or useState initialiser

// 4. MANIPULATING THE DOM DIRECTLY
useEffect(() => { ref.current.style.height = h + 'px'; }, [h]);
// usually means a CSS class or a conditional would do. Use layout effect
// and a ref only when there is genuinely no declarative way.

// 5. MANAGING A PROP
useEffect(() => { setValue(props.value); }, [props.value]);
// the parent owns it. call a callback, or lift the state up.

// 6. ASYNC WITHOUT CLEANUP
useEffect(() => { load().then(setData); }, []);   // setState after unmount
// add the guard, every time

// 7. ONE GOD EFFECT
useEffect(() => { fetchA(); fetchB(); subscribeC(); setIntervalD(); return () => {/*...*/}; }, []);
// four unrelated resources, one cleanup, impossible to reason about.
// split it, or abstract each into its own hook

Abstracting effects into hooks

Once the traps are understood, most effects want to become hooks. This is the highest-leverage refactor in a React codebase.

// BEFORE: the same five lines in six components
useEffect(() => {
  const id = setInterval(() => { setNow(new Date()); }, 1000);
  return () => clearInterval(id);
}, []);

// AFTER
function useInterval(callback: () => void, delay: number | null) {
  const saved = useRef(callback);
  useEffect(() => { saved.current = callback; });
  useEffect(() => {
    if (delay === null) return;      // paused
    const id = setInterval(() => saved.current(), delay);
    return () => clearInterval(id);
  }, [delay]);
}

// a document-title hook, with the escape hatch built in
function useTitle(title: string, restore = true) {
  useLayoutEffect(() => {
    const previous = document.title;
    document.title = title;
    return () => { if (restore) document.title = previous; };
  }, [title, restore]);
}

// a media query hook
function useMediaQuery(query: string) {
  const [matches, setMatches] = useState(() =>
    typeof window !== 'undefined' && window.matchMedia(query).matches,
  );
  useEffect(() => {
    const mq = window.matchMedia(query);
    const on = (e: MediaQueryListEvent) => setMatches(e.matches);
    setMatches(mq.matches);
    mq.addEventListener('change', on);
    return () => mq.removeEventListener('change', on);
  }, [query]);
  return matches;
}

9 · Refs, the DOM and Imperative Escape Hatches

Refs are the escape hatch for the cases React cannot express: measuring an element, focusing it, holding a value that must not trigger a render, and integrating with a library that owns its own DOM. Used sparingly they are the right tool.

useRef and the two kinds

A ref holds a mutable box. The critical difference from state: writing to ref.current never causes a render.

const ref = useRef<HTMLInputElement>(null);   // { current: null }
ref.current = node;      // no re-render. the DOM already has it.
ref.current?.focus();    // an action, not a render

// THREE legitimate uses

// 1. reaching the DOM
const inputRef = useRef<HTMLInputElement>(null);
inputRef.current?.focus();

// 2. a mutable value that must NOT trigger a render
//    - "has this mounted once yet"
//    - a timer id
//    - the previous value
//    - a WebSocket instance
const isFirst = useRef(true);
if (isFirst.current) { isFirst.current = false; }   // no render loop

// 3. escaping the closure staleness problem from ch8
const latest = useRef(value);
useEffect(() => { latest.current = value; });

Never write a ref during render for a value the UI shows. The DOM and React's idea of the UI will disagree, and the next render will overwrite it. If a value must be visible, it is state. Refs are for things with no representation.

Reading and measuring the DOM

React does not know the size of anything until you measure it. This is genuinely outside its model, and layout effects are the correct home for it.

// the canonical measure-and-position pattern
function Dropdown({ items }) {
  const [open, setOpen] = useState(false);
  const [pos, setPos] = useState({ top: 0, left: 0 });
  const triggerRef = useRef<HTMLButtonElement>(null);
  const menuRef = useRef<HTMLDivElement>(null);

  useLayoutEffect(() => {
    if (!open) return;
    const t = triggerRef.current!.getBoundingClientRect();
    const m = menuRef.current!.getBoundingClientRect();

    // flip above if there is not enough room below
    const below = window.innerHeight - t.bottom;
    const top = below > m.height + 8 ? t.bottom + 4 : t.top - m.height - 4;

    // shift left if the menu would overflow the viewport
    const maxLeft = window.innerWidth - m.width - 8;
    const left = Math.max(8, Math.min(t.left, maxLeft));

    setPos({ top, left });
  }, [open, items]);   // measure after the menu renders, before paint

  return (
    <>
      <button ref={triggerRef} onClick={() => setOpen((o) => !o)}>Menu</button>
      {open && (
        <div ref={menuRef} className="menu" style={{ top: pos.top, left: pos.left, position: 'fixed' }}>
          {items.map((i) => <button key={i.id} onClick={() => select(i)}>{i.label}</button>)}
        </div>
      )}
    </>
  );
}

// why useLayoutEffect and not useEffect: with useEffect the browser paints
// the menu at top:0 left:0 first, then it jumps. layout effect runs
// before paint, so the user only ever sees the final position.

// infinite scroll: an IntersectionObserver, not a scroll listener
function useInfinite(onHit: () => void) {
  const sentinel = useRef<HTMLDivElement>(null);
  useEffect(() => {
    const io = new IntersectionObserver(([e]) => { if (e.isIntersecting) onHit(); });
    io.observe(sentinel.current!);
    return () => io.disconnect();
  }, [onHit]);
  return sentinel;
}

// scroll restoration for a route
function useScrollRestoration(key: string) {
  useLayoutEffect(() => {
    const y = sessionStorage.getItem('scroll:' + key);
    if (y) window.scrollTo(0, Number(y));
    return () => sessionStorage.setItem('scroll:' + key, String(window.scrollY));
  }, [key]);
}

Prefer scrollIntoView, CSS scroll-margin and scroll-snap over manual scroll arithmetic. Reach for the manual version only when you must preserve a pixel offset across a reorder, which is what block: 'nearest' on a stable anchor handles cleanly.

Focus management

Focus is DOM state, so it is ref territory. Done well it is most of what accessibility requires from a component.

// a dialog: focus moves in on open, and returns to the trigger on close
function Dialog({ open, onClose, children }: Props) {
  const panel = useRef<HTMLDivElement>(null);
  const opener = useRef<Element | null>(null);

  useEffect(() => {
    if (!open) return;
    opener.current = document.activeElement;        // remember where we came from

    // move focus into the panel, preferring the first focusable control
    const first = panel.current?.querySelector<HTMLElement>(
      'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])',
    );
    (first ?? panel.current)?.focus();

    const onKey = (e: KeyboardEvent) => {
      if (e.key === 'Escape') onClose();
      if (e.key === 'Tab') trapFocus(e, panel.current);   // keep focus inside
    };
    document.addEventListener('keydown', onKey);
    return () => {
      document.removeEventListener('keydown', onKey);
      (opener.current as HTMLElement | null)?.focus();   // restore
    };
  }, [open, onClose]);

  if (!open) return null;
  return createPortal(
    <div className="scrim" onClick={onClose}>
      <div ref={panel} role="dialog" aria-modal="true" aria-labelledby="t">{children}</div>
    </div>,
    document.body,
  );
}

// focus management WITHOUT refs, using the browser
//   autofocus attribute works once, on first render
//   the :autofill and :focus-visible pseudo-classes handle the rest
//   never remove an element the user is focused inside - that drops focus
//     to body, and the keyboard user loses their place entirely

The most common a11y bug in a React codebase is a conditional that unmounts the element containing focus. If a button is focused and its parent re-renders to null, focus silently moves to <body> and a screen-reader user is dumped at the top of the page. When a focused element is about to disappear, move focus somewhere deliberate first.

When not to use a ref

// a ref where state would do

// a ref where a reducer would do

// -> useState or useReducer

Effect plus ref patterns

// PATTERN: an event bus between sibling effects
function useEventBus() {
  const handlers = useRef(new Map<string, Set<() => void>>());
  return useMemo(() => ({
    on(evt: string, fn: () => void) {
      if (!handlers.current.has(evt)) handlers.current.set(evt, new Set());
      handlers.current.get(evt)!.add(fn);
      return () => handlers.current.get(evt)!.delete(fn);
    },
    emit(evt: string) {
      handlers.current.get(evt)?.forEach((fn) => fn());
    },
  }), []);
}

// PATTERN: measuring once and re-measuring on change
function useMeasure<T extends HTMLElement>() {
  const ref = useRef<T>(null);
  const [rect, setRect] = useState({ width: 0, height: 0 });

  useLayoutEffect(() => {
    const el = ref.current;
    if (!el) return;
    const ro = new ResizeObserver(([entry]) => {
      const r = entry.contentRect;
      setRect({ width: r.width, height: r.height });
    });
    ro.observe(el);
    return () => ro.disconnect();
  }, []);

  return [ref, rect] as const;
}

function Chart({ data }) {
  const [ref, { width }] = useMeasure<HTMLDivElement>();
  const w = Math.max(0, width - 20);
  return (
    <div ref={ref}>
      <svg viewBox={`0 0 ${w || 1} 200`} width="100%">
        {data.map((d, i) => <rect key={i} x={i * (w / data.length)} width={w / data.length - 2} height={d * 2} />)}
      </svg>
    </div>
  );
}

Context solves one problem — passing a value through many levels without threading props — and creates one big problem: every consumer re-renders when the value changes. Used with the split-and-selector techniques in this chapter, it is excellent.

What context is for

Context is a subscription, not a global variable. When the provider's value changes, React finds every consumer beneath it and re-renders those, regardless of how much of the tree sits between them.

// the case context is genuinely right for
//   - a value many levels need, with no intermediate component caring
//     (theme, locale, current user, a router, a feature-flag set)
//   - a DI mechanism: a component declares what it needs, the tree supplies
//   - breaking a prop-drilling chain through 8 layers of layout

// the case it is wrong for
//   - high-frequency values: a mouse position, a scroll offset, an
//     animation frame, a typing buffer. every consumer re-renders per frame.
//   - anything that is server data. that belongs in a cache library.
//   - a single value two siblings share. lift it to their parent.

// how the lookup works
<ThemeProvider theme="dark">
  <Layout>                 <-- does not consume, does not re-render
    <Header />            <-- consumes: re-renders when theme changes
    <Sidebar>
      <Nav />             <-- consumes: re-renders
    </Sidebar>
  </Layout>
</ThemeProvider>

Always provide a default value

// BAD: createContext(null) gives no type safety and a null crash far from
// the cause. the cast lies to the compiler.
const ThemeContext = createContext<Theme | null>(null);
const theme = useContext(ThemeContext)!;      // the ! is a promise you keep

// GOOD: a real default, so the type is non-nullable and a missing provider
// is a no-op rather than a crash
const ThemeContext = createContext<Theme>({
  theme: 'light',
  setTheme: () => {},          // a no-op, but the type is satisfied
});

// BEST: a hook that throws a useful error, because a missing provider is a
// bug you want to hear about loudly
function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used inside a ThemeProvider');
  return ctx;
}

Make the context value a hook, not a bare useContext call. Two reasons: you get one place to type the value and add the runtime check, and consumers cannot accidentally read a different context. Every context in a codebase should export a hook and nothing else.

The nesting problem

Two failure modes bite almost everyone, and both are fixed by the same technique.

// PROBLEM 1: an object literal recreates on every render, so every consumer
// re-renders on every provider render
const value = { user, theme, dispatch };      // new object every time
return <Ctx.Provider value={value}>{children}</Ctx.Provider>;

// FIX 1: memoise
const value = useMemo(() => ({ user, theme, dispatch }), [user, theme, dispatch]);

// PROBLEM 2: ONE context holding values that change at different rates
const value = { user, cartCount, isDark };
// typing in a search box updates isDark? no. but adding to the cart
// updates cartCount, and now every component reading `user` re-renders
// too, because the value object changed.

// FIX 2: split by update frequency
<UserContext.Provider value={user}>
  <CartContext.Provider value={cart}>
    <ThemeContext.Provider value={theme}>
      {children}
    </ThemeContext.Provider>
  </CartContext.Provider>
</UserContext.Provider>
// a cart update re-renders only the cart consumers. user consumers
// bail out because their value is Object.is-equal.

Split fast and slow context

// the practical pattern: state and actions are different frequencies
//   state changes when the data changes
//   actions are stable forever
//   consumers that only dispatch never re-render

function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  // actions NEVER change, so the object is created once
  const actions = useMemo(
    () => ({
      signIn: async (email: string, password: string) => {
        const user = await api.login(email, password);
        setUser(user);
        return user;
      },
      signOut: () => setUser(null),
      refresh: async () => setUser(await api.me()),

  return (
    <AuthStateContext.Provider value={user}>
      <AuthActionsContext.Provider value={actions}>
        {children}

  );

A typed context hook

// a reusable, fully typed context, so no provider is written twice
import { createContext, useContext, useMemo, useState, type ReactNode } from 'react';

function createRequiredContext<T>(name: string) {
  const Ctx = createContext<T | null>(null);
  const useRequired = () => {
    const v = useContext(Ctx);
    if (v === null) throw new Error(`${name} must be used within its provider`);
    return v;
  };
  return [Ctx, useRequired] as const;
}

// usage
type ThemeValue = { theme: 'light' | 'dark'; setTheme: (t: 'light' | 'dark') => void };
const [ThemeContext, useTheme] = createRequiredContext<ThemeValue>('ThemeContext');

  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

// the value must be referentially stable or every consumer re-renders
// on every provider render, which defeats the point of context

// RIGHT: a primitive needs no memo

Selector subscriptions

Context has no built-in selector. If a value is large and consumers need different parts, either split the context or use a store that supports selectors.

// OPTION A: split contexts (no dependency, always correct)
<UserNameContext.Provider value={user.name}>
  <UserAvatarContext.Provider value={user.avatarUrl}>
    <UserEmailContext.Provider value={user.email}>{children}</UserEmailContext.Provider>
  </UserAvatarContext.Provider>
</UserNameContext.Provider>
// fine for two or three values. unwieldy past that.

// OPTION B: a store with selectors, where each component subscribes to
// only the slice it reads. Zustand is the smallest useful implementation
import { create } from 'zustand';

type Store = {
  user: User | null;
  cart: Item[];
  theme: 'light' | 'dark';
  setUser: (u: User | null) => void;
  addToCart: (i: Item) => void;
};
const useStore = create<Store>((set) => ({
  user: null, cart: [], theme: 'light',
  setUser: (user) => set({ user }),
  addToCart: (i) => set((s) => ({ cart: [...s.cart, i] })),
}));

function CartBadge() {
  // selects only the count, so a user update does not re-render this
  const count = useStore((s) => s.cart.length);
  return <Badge count={count} />;
}

function ThemeToggle() {
  const theme = useStore((s) => s.theme);
  const setTheme = useStore((s) => s.setUser);   // stable, never changes
  return <button onClick={() => setTheme(null)}>{theme}</button>;
}

// useShallow for an object selection, or the default equality will
// re-render every store write
import { useShallow } from 'zustand/react/shallow';
const { name, email } = useStore(useShallow((s) => ({ name: s.user?.name, email: s.user?.email })));

Zustand's useStore(selector) is powered by useSyncExternalStore, the same primitive React uses internally. That is why it does not force the tree to re-render: each component holds its own subscription to the store, and only a change to its selected slice notifies it.

//   - there are few consumers
//   - the tree is small enough that a re-render is cheap
//   - you want zero dependencies

// USE A STORE WHEN
//   - the value changes often
//   - many components read different parts of it
//   - you already have a store and this is just more of it
//   - writes come from outside React (a websocket, a worker)

// USE NEITHER WHEN
//   - the value is local to one component
//   - the value is derived
//   - the value is server data -> a cache library (ch15)
//   - the value is the URL -> the router (ch16)

//   1. split state from actions in existing contexts  (biggest win, no rewrite)

Performance work starts with a measurement, not a memo. This chapter establishes what triggers a re-render, how to observe one with the Profiler, where the real cost lives — the commit and the browser, not your function body — and how to keep a fast app fast with budgets in CI.

What actually re-renders

A render is React calling your component function again with a new set of arguments. It is not a pixel, not a DOM write, and not by itself expensive. The function runs, produces a tree of elements, and React decides what, if anything, to change on screen. Understanding which events cause that function call is the whole of half of performance work, because the other half is measurement and the diagnosis is almost always "component X re-rendered when Y changed, and it did not need to".

There are exactly four triggers. Your component's own state changed to a value that is not Object.is-equal to the previous one. A parent component re-rendered, which re-renders every child unless the child is wrapped in React.memo. A context value changed, which re-renders every consumer of that context. And a state update inside a transition or an action settled, which re-renders the components that read what it changed. Nothing else re-renders: mutating ref.current, changing a value held only in a module variable, calling a callback that React does not know about, or touching the DOM directly cause no render at all.

// every update that bails out, and every update that re-renders
function Counter() {
  const [n, setN] = useState(0);
  const [items, setItems] = useState([]);

  // BAILS OUT: Object.is(1, 1) is true, React throws the update away
  setN(1);                 // when n is already 1

  // RENDERS: new array identity even if the contents are equal
  setItems([...items]);    // spread always allocates

  // OFTEN BAILS OUT: the updater returns the same state, React re-renders
  // once to find that out, then stops - so it is not free, but it converges
  setN((prev) => prev);

  // RENDERS ANYWAY: setState always schedules, even with the identical value
  // of a prop passed back in
  setItems((prev) => prev.concat([]));
}

The subtle case is the updater function. When you pass setN((prev) => prev), React must call your function to learn whether the state changed, so the component renders once more than strictly necessary — but then it stops, because the result is identical. Repeated identical updates therefore converge rather than loop. The dangerous version is not bail-out behaviour, it is the new-identity behaviour: an inline object, array or function passed as a prop is a new value on every render, so a memoised child comparing props shallowly sees a difference every time.

// the re-render you did not ask for: identity, not value
function ProductList({ products }) {
  // this object is new on every render of ProductList
  const ui = { dense: true, showPrice: true };
  return products.map((p) => (
    <ProductRow key={p.id} product={p} ui={ui} />   // memo? wasted - ui differs
  ));
}

// hoist what does not depend on props, pass what does
const DENSE_UI = { dense: true, showPrice: true };
function ProductList({ products }) {
  return products.map((p) => (
    <ProductRow key={p.id} product={p} ui={DENSE_UI} />
  ));
}

The four triggers, stated precisely

Own state that actually changed; a parent re-render; a context value change; a settled transition. Every reported React performance bug is one of these four, and the useful question when a profile looks wrong is never "why is this slow" but "which of the four fired, and did the component need it". Write the trigger down before you change anything — it keeps you from sprinkling memo over components whose re-renders were both correct and cheap.

A component that re-renders is not a component that is slow. Rendering 40 tiny function calls is routinely cheaper than the bookkeeping required to prove they could be skipped. The measurement in the next section is what tells you which situation you are in.

Measuring before you change anything

The React DevTools Profiler records every commit: how long the render phase took, which components rendered, and — critically — which components were skipped because of memo. Two views matter. The flamegraph view shows the tree for one commit, with bar width proportional to time, so the expensive subtree is visually obvious. The ranked chart sorts components by duration across the selected commits, which answers "what is the most expensive thing on this screen" without you guessing.

Three habits make profiles trustworthy. Record a real interaction — a click through the slow path — rather than scrolling idly, because the profiler's flamegraph is per-commit and scrolling produces hundreds of commits nobody reads. Filter by the component you suspect, since an unfiltered profile of a large page is mostly chrome you cannot act on. And always compare against a profile taken in a production build: development React is several times slower, runs double-invoked effects under StrictMode, and carries prop-type style checks, so a dev profile ranks problems that do not exist for users.

// programmatic profiling: wrap only the subtree you care about
import { Profiler } from 'react';

function onRender(id, phase, actualDuration, baseDuration, startTime, commitTime) {
  // actualDuration - time spent rendering THIS update in this build (dev-only,
  //                   near meaningles in production builds)
  // baseDuration    - estimated time to render the whole subtree from scratch
  //                   stable across updates: use it for "is this subtree big"
  if (actualDuration > 16) {
    reportMetric('slow-commit', { id, phase, actualDuration, baseDuration });
  }
}

export function Dashboard() {
  return (
    <Profiler id="Dashboard" onRender={onRender}>
      <Chart />
      <DataTable />
    </Profiler>
  );
}

Use baseDuration for sizing decisions and actualDuration for regression detection. baseDuration is computed from the element tree as if everything rendered from scratch; it changes only when the tree changes, so it is the right number for "how heavy is this screen". actualDuration measures one update and shrinks whenever memoisation or bail-outs skip work, so it is the right number for "did my change help" — but it is only meaningful in development builds, which is exactly where you compare before and after.

Reading a flamegraph honestly

A wide bar high in the tree means a layout component re-rendered and took its children with it — fix the state that woke it. A wide bar low in the tree means one component is doing heavy work inside its own function — fix the work. A wall of equal thin bars means nothing is expensive and the frame budget was simply spent on many small commits in sequence; that is a scheduling problem, not a component problem, and memoisation will not touch it. Match the shape to the category before reaching for a tool.

Never profile a development build and then quote the numbers as user-facing. The ratio between dev and prod cost varies with component shape — heavy prop validation and double-invoked effects distort some screens far more than others — so a dev profile is a map of relative priorities, not a stopwatch.

What a render actually costs

React's render phase is a function call and a diff. Calling your component, running your hooks, building element objects and running the reconciliation algorithm against the previous tree: all of this is JavaScript that usually costs single-digit microseconds per component. The expensive phases are downstream. Commit means writing to the DOM, and the browser then recalculates style, layout and paint. A React app that "feels slow" is almost always blocked in one of three places: a large commit touching many nodes, a layout thrash caused by measuring the DOM and then mutating it repeatedly, or JavaScript occupying the main thread so input events queue behind it.

The distinction matters because the fixes are different. If the render phase is heavy, you are doing too much work in the component body — deriving expensive values on every render, stringifying large objects, sorting thousand-item arrays without memo, or calling APIs like new Date().toLocaleString() inside a loop over rows. If the commit phase is heavy, you are changing too much DOM at once — inserting thousands of nodes, toggling classes on an entire tree, or re-running CSS transitions by removing and re-adding elements. If the main thread is simply busy, the fix is to break the work into slices, which is what transitions in chapter 14 exist for.

// expensive work in the render body - it runs on every keystroke
function FilterableTable({ rows, query }) {
  // this sorts on every render, even when rows and query are unchanged
  const sorted = [...rows]
    .sort((a, b) => b.score - a.score)
    .filter((r) => r.name.includes(query))
    .map((r) => ({ ...r, label: r.name + ' (' + r.score + ')' }));
  return <Table rows={sorted} />;
}

// the same derivation, keyed on its inputs
const selectRows = (rows, query) => { /* pure selector, one line, unit-tested */ };
function FilterableTable({ rows, query }) {
  const sorted = useMemo(() => selectRows(rows, query), [rows, query]);
  return <Table rows={sorted} />;
}

Note that the fix above is not primarily about speed, it is about ownership: the derivation became a pure function with inputs, which is testable, reusable in a loader, and safe to move out of render entirely if it ever grows. Derivations that live inline in JSX accumulate until the component function itself is the bottleneck, and at that point every render of any parent is expensive too, because your component is a child of something. Keep the body of a component boring; push work into named functions that take arguments.

// layout thrash: read-write-read-write forces a reflow per iteration
function measureRows(ref) {
  const nodes = ref.current.children;
  for (let i = 0; i < nodes.length; i++) {
    const h = nodes[i].offsetHeight;          // READ  - forces layout
    nodes[i].style.setProperty('--row-h', h + 'px'); // WRITE - invalidates
  }
}

// batch the reads, then batch the writes
function measureRows(ref) {
  const nodes = ref.current.children;
  const heights = [];
  for (let i = 0; i < nodes.length; i++) heights.push(nodes[i].offsetHeight);
  for (let i = 0; i < nodes.length; i++) {
    nodes[i].style.setProperty('--row-h', heights[i] + 'px');
  }
}

// microtask or the next commit - never interleave reads and writes per node.

Wasted work versus wasted DOM

Wasted work is rendering a component whose output is identical to last time — the cost is JavaScript, and the fix is to skip the render or shrink it. Wasted DOM is committing changes the user cannot perceive — the cost is style and layout, and no amount of memoisation helps because the writes still happen. The Profiler shows you the first; for the second you want the browser's own performance panel, looking at the "Recalculate Style" and "Layout" tracks under the commit you clicked. Two tools, two phases, and using only the React profiler will hide an entire category of slowness.

When a screen feels sluggish but the profiler shows nothing over a few milliseconds, look at frame timing instead: long tasks that begin after the commit — data fan-out, event handlers doing synchronous work, third-party scripts — never appear in React's numbers at all.

Large lists and windowing

Ten thousand rows is not a React problem until it is a browser problem: ten thousand rows means ten thousand rows in the DOM, and the initial commit alone will blow the frame budget regardless of how cheap each component is. Windowing — rendering only the rows inside the viewport plus a small overscan — is the structural fix, and it is worth doing by hand once so you understand what a library like react-window is buying you: a scroll handler, arithmetic, and a container with a fixed height.

Windowing has real costs you must weigh against it. The scroll height must be faked, which breaks simple "scroll to element" logic; keyboard navigation needs explicit management because the focused row can leave the DOM; and screen readers see a shorter list than exists. For a table of 50 rows, do nothing. For a feed that grows without bound, window before you profile — a technique that removes the problem class beats a technique that makes one instance of it cheaper.

// windowing by hand: only rows near the viewport exist in the DOM
function WindowedList({ rows, rowHeight, viewportHeight }) {
  const [scrollTop, setScrollTop] = useState(0);
  const overscan = 4;

  const first = Math.max(0, Math.floor(scrollTop / rowHeight) - overscan);
  const last = Math.min(rows.length, Math.ceil((scrollTop + viewportHeight) / rowHeight) + overscan);
  const visible = rows.slice(first, last);

  return (
    <div style={{ height: viewportHeight, overflow: 'auto' }}
         onScroll={(e) => setScrollTop(e.currentTarget.scrollTop)}>
      <div style={{ height: rows.length * rowHeight, position: 'relative' }}>
        {visible.map((row, i) => (
          <Row key={row.id}
               row={row}
               style={{ position: 'absolute', top: (first + i) * rowHeight, height: rowHeight }} />
        ))}
      </div>
    </div>
  );
}

Two details separate a correct window from a flaky one. Keys must be stable ids, never the visible index: index keys tell React the identity of every row changed when a row is prepended, so it rebuilds the DOM for the whole window instead of moving one node. And the row component must be memoised with props that are stable across scrolls — passing scrollTop or a freshly-built style object into every row turns windowing into a full re-render per scroll frame, which is what you were avoiding. The arithmetic above runs per scroll event and is trivial; the renders it triggers are not, unless the props let React skip them.

// the row must be skippable, and its props must be comparable
const Row = memo(function Row({ row, style }) {
  return <div style={style}>{row.name}</div>;
});

// GOOD: style objects built inside map are new every scroll... which defeats
// memo. build them once per window change instead:
const styles = visible.map((_, i) => ({
  position: 'absolute',
  top: (first + i) * rowHeight,
  height: rowHeight,
}));

// BETTER: let the row compute its own offset from a numeric prop - numbers
// compare by value, so memo actually works:
const Row = memo(function Row({ row, top, height }) {
  return (
    <div style={{ position: 'absolute', top, height }}>{row.name}</div>
  );
});

When not to virtualise

Skip windowing when the list is bounded by the domain — a nav menu, a settings page, a 200-row admin table — because the engineering cost, the accessibility caveats and the print/export edge cases outweigh a commit that costs 30 ms once. Also skip it when rows have variable, unmeasured heights: absolute positioning requires known heights, and measuring every row to discover them reintroduces the layout cost you were removing. Variable-height windowing is a substantially harder problem with its own measurement pass; reach for it only with evidence from the profiler that bounded lists are not your bottleneck.

Windowing hides rows from the DOM, which means find-in-page, anchor scrolling to a row in the middle, and screen-reader row counts all break silently. If the list is a primary navigation surface, budget the accessibility work up front rather than discovering it after release.

Budgets and regression gates

A performance improvement that is not protected by a check is a performance improvement until the next feature lands. Budgets make the cost visible at the same moment the change is made: a maximum bundle size per entry point, a maximum render duration for the screens you care about, and a maximum long-task duration during the interactions that define your product. The point is not precision — a budget that is right within a factor of two beats a number nobody checks.

Three budgets cover most applications. Bundle size is checked in CI against a committed baseline, because it is deterministic and a 20 KB regression is visible long before a user complains. Render cost is checked with the Profiler API inside a component test: render, interact, assert on actualDuration or, better, on how many components rendered, since counts are stable across machines while milliseconds are not. Interaction latency is checked in a real browser against the production build — INP, the web vital that replaced FID, is exactly this measurement aggregated over real sessions, and a synthetic version of it in CI catches the regressions before they reach the field.

// render-count gate: stable across machines, unlike milliseconds
import { render, screen, fireEvent } from '@testing-library/react';
import { Profiler } from 'react';

let rendered = [];
const onRender = (id) => { rendered.push(id); };

test('typing in the search box renders only the results list', () => {
  render(
    <Profiler id="page" onRender={onRender}>
      <SearchPage />
    </Profiler>
  );
  rendered = [];

  fireEvent.change(screen.getByRole('searchbox'), { target: { value: 'ab' } });

  // alphabetical, so the assertion is readable when it fails
  expect([...new Set(rendered)].sort()).toEqual(['ResultsList']);
});

The reason render counts beat timings in tests is variance. A shared CI runner can be interrupted by its neighbour, so a 12 ms assertion flakes and the team learns to ignore red builds — at which point the gate protects nothing. Counts are deterministic: the same interaction over the same tree renders the same set of components every time. When a count assertion fails, it fails for a real reason — someone added a state update to a component that used to be inert — and the failure message names the component.

// bundle budget: fail the build when an entry point grows past its baseline
import { readFileSync, writeFileSync } from 'node:fs';

const BUDGETS = { 'index': 180_000, 'vendor': 320_000, 'dashboard': 90_000 };
const baseline = JSON.parse(readFileSync('bundle-baseline.json', 'utf8'));
let failed = false;

for (const [name, budget] of Object.entries(BUDGETS)) {
  const size = readFileSync('dist/assets/' + name + '.js', 'utf8').length;
  const drift = size - (baseline[name] || 0);
  if (size > budget) { console.error(name + ' over budget: ' + size + ' > ' + budget); failed = true; }
  if (drift > 5_000) { console.error(name + ' grew ' + drift + ' bytes since baseline'); failed = true; }
  baseline[name] = size;
}
if (process.argv.includes('--update')) writeFileSync('bundle-baseline.json', JSON.stringify(baseline, null, 2));
process.exit(failed ? 1 : 0);

Baseline discipline

A budget without a baseline only catches absolute blowouts; the baseline catches the slow creep of one small dependency per sprint. Commit it, update it deliberately with a flag, and require the diff to be reviewed — a PR that raises the baseline by 40 KB is a conversation about why, in the same way a raise in test count is not. The cheapest performance work in any mature application is the regression that never shipped.

Measure the screens users actually open, on the device class they actually use. A budget suite that runs only against a top-end laptop on a fast connection will pass while the app is unusable for everyone on mid-range hardware — throttle the CPU in the browser panel once a sprint and let the flamegraph surprise you.

12 · Memoisation, Done Properly

Measure first, memo secondReact.memo and the props comparisonuseMemo and honest dependency arraysThe React 19 compilerWhen memoisation makes things worse

Memoisation is a trade: memory and comparison cost bought with skipped renders. This chapter covers when the trade pays, what each of the three mechanisms actually guarantees, how the React 19 compiler changes the default, and the failure modes — stale values, dishonest dependency arrays and memoised trees that cost more than they save.

Measure first, memo second

React gives you three memoisation tools and one that arrived with the compiler, and the single most common mistake is applying them in the order the API happens to suggest rather than in the order the profiler justifies. A component that renders 200 microseconds and never appears high in a ranked chart does not need to be skipped; wrapping it in memo adds a shallow comparison on every parent render and a cache entry for a result nobody was waiting on. Memoisation pays when three conditions hold together: the component re-renders often, rendering it is measurably expensive, and its props are usually unchanged between renders. Drop any one condition and the trade goes the other way.

The order of operations is therefore: profile the interaction that feels slow; identify whether the cost is render-phase or commit-phase, because memo only removes render-phase work; check whether the component re-renders for a reason — a parent state change it does not read — and if so, whether that reason can be removed structurally instead. Lifting state down, splitting a component, or moving an unstable value out of render are all fixes that reduce work for everyone. Memoisation does not reduce work; it moves the cost from rendering to comparing and hoping. Sometimes that is exactly right, and the rest of this chapter is about telling the two situations apart.

// the decision, written down, in order
//
// 1. does the component render at all, often?        -> no: stop here
// 2. is rendering it expensive? (profiler, not vibes) -> no: stop here
// 3. are its props usually identical between renders? -> no: memo fails, stop
// 4. can the re-render be removed by moving state?    -> yes: do that instead
// 5. only now: React.memo, and re-measure
//
// steps 1-3 take ten minutes. step 4 takes an hour and usually wins.

export function shouldMemoise(componentName, profile) {
  const c = profile.components[componentName];
  if (!c.renderCount || c.renderCount < 5) return 'infrequent';
  if (c.avgDurationMs < 1) return 'cheap';
  if (c.propStability < 0.5) return 'props-always-change';
  return 'memoise';
}

There is also a structural signal that costs nothing to check. If the expensive component sits under a parent whose state changes on every keystroke of an unrelated input, the right fix is almost always to move that state — a context, a store, or a split component — so the expensive subtree stops being in the render path at all. Chapter 10's split-fast-slow context and chapter 11's trigger analysis are the upstream versions of this fix. Memoisation downstream of a badly-placed state is a patch on a patch: it works, but every new child of the same parent must remember to apply it too.

// structural fix beats memo: the expensive subtree is not in the path
function Page() {
  const [query, setQuery] = useState('');       // changes per keystroke
  return (
    <div>
      <SearchInput value={query} onChange={setQuery} />
      <ExpensiveReport />      {/* re-renders per keystroke - memo hides it */}
    </div>
  );
}

// BETTER: split so the keystroke state lives where it is used
function Page() {
  return (
    <div>
      <SearchPanel />          {/* owns query and SearchInput */}
      <ExpensiveReport />      {/* renders once unless its props change */}
    </div>
  );
}

The profiler-before-memo ritual

Make it a habit with a fixed sequence: record the interaction, note the top three components by actual duration, check their render counts in the same session, and only then decide. Writing the numbers down before the change is what lets you prove afterwards that the change helped — and occasionally you will prove it did not, which is the more valuable outcome, because undoing a wrong memo early is far cheaper than inheriting it later.

Memoisation is not free even when it works: the previous props are retained for comparison, so a tree of memoised components holding large objects pins those objects in memory across renders. On long-lived pages with big data structures, that retention shows up as a slow leak that no render profile will reveal.

React.memo and the props comparison

React.memo wraps a component so that React skips re-rendering it when its props are shallowly equal to the previous ones. Shallow means one level: each prop is compared with Object.is, nested objects are compared by reference, and children — unless you pass a custom comparator — are compared as the children prop like anything else. The comparison runs on every parent render for every memoised child, so a memoised component whose props are new objects on every render pays the comparison and gets no skip: the worst of both worlds, and the most common outcome in codebases where memo was applied before the props were stabilised.

The children case deserves its own rule, because it subverts the usual advice. A memoised component given JSX children re-renders whenever the parent re-renders, since JSX creates new element objects each time and elements are props. The escape hatch is that React treats the children slot specially when you pass them as props from a parent that itself did not re-render — but that parent usually did re-render. The practical pattern is to hoist the JSX for the memoised subtree into a memoised value, or to accept that the boundary belongs higher up the tree, around a component whose props genuinely do not change.

// memo with default shallow comparison: what it actually guarantees
const UserCard = memo(function UserCard({ user, onSelect }) {
  return <button onClick={() => onSelect(user.id)}>{user.name}</button>;
});

// user and onSelect are both new per parent render - memo NEVER skips.
// stabilise both, or the wrapper is pure overhead:
const UserCard = memo(function UserCard({ userId, name, onSelect }) {
  return <button onClick={onSelect} data-id={userId}>{name}</button>;
});
// now: primitives compare by value, and onSelect is a stable dispatch or a
// useCallback from chapter 12's hooks section - the skip can actually fire.

function List({ users, onSelect }) {
  return users.map((u) => (
    <UserCard key={u.id} userId={u.id} name={u.name} onSelect={onSelect} />
  ));
}

The custom comparator parameter — React.memo(Component, areEqual) — is a sharp tool that should stay in its sheath almost always. A comparator that only checks one prop is faster than a full shallow compare, but it silently desynchronises from the component's real inputs: add a second prop later and the component will not re-render when it changes, producing a bug whose symptom is a stale view with no error. If you genuinely need a narrowed comparison, the honest move is to narrow the component's props instead — pass the one value it uses, not the object containing it.

// custom comparator: correct today, a stale-render bug waiting for prop 2
const Chart = memo(function Chart({ data, theme }) { /* ... */ },
  (prev, next) => prev.data === next.data   // ignores theme!
);
// theme changes -> Chart does not re-render -> wrong colours, no error thrown.

// the honest version: make the props match the comparison
const Chart = memo(function Chart({ data, accent }) {
  /* accent is the only visual input I read */
});

// if you must compare deeply, compare the derived value, not the object:
const Chart = memo(function Chart({ data, themeMode }) { /* ... */ },
  (prev, next) => prev.data === next.data && prev.themeMode === next.themeMode
);

Where memo boundaries belong

Put the boundary at the point where a genuinely stable, expensive subtree hangs off an unstable parent — a chart under a form, a read-only table under a toolbar, a static sidebar under page state. Boundaries placed on every leaf of a hot tree turn rendering into a distributed systems problem: thirty shallow comparisons per parent render, each one a place where a future prop can quietly defeat the optimisation. One boundary at a well-chosen seam, with primitive props crossing it, is worth more than thirty with objects crossing them.

Pass primitives across memo boundaries whenever the shape allows it — ids and primitives compare by value and never defeat the check. If the component needs the whole object, pass the object and drop the memo: a boundary that cannot reliably skip is noise in the profile and in the code review.

useMemo and honest dependency arrays

useMemo caches the result of a computation between renders; useCallback caches a function itself — useCallback(fn, deps) is exactly useMemo(() => fn, deps). Both take a dependency array whose contract is precise: React compares it element by element on every render with Object.is, and if anything differs it discards the cache and runs the factory again. There is no deep comparison, no lint-level guarantee that the array is complete, and no consequence for listing a dependency the value does not use beyond extra recomputation. The array is a cache key you write by hand, and honest keys are the entire skill.

Three dishonest shapes cause most bugs. Omitting a dependency, so the memo returns last render's value built from this render's inputs — the classic stale closure, usually surfacing as an effect that "does not update". Listing a dependency that is a new object or function every render, so the cache never hits and the memo does nothing but allocate. And deriving values that could be computed during render without any memo at all — a .filter over a 200-item array costs microseconds, and caching it buys nothing while adding a correctness surface. Use useMemo for genuinely expensive computations and for reference stability other memoisation depends on; skip it for cheap work.

// dishonest: omitted dependency, stale value escapes the memo
function SearchResults({ query, filters }) {
  const results = useMemo(() => filterItems(query, filters), [query]);
  // filters changed -> cache HIT -> stale results, no error, no warning
  return <List items={results} />;
}

// honest: every input the computation reads, in the order it reads them
function SearchResults({ query, filters }) {
  const results = useMemo(() => filterItems(query, filters), [query, filters]);
  return <List items={results} />;
}

// honest AND unnecessary: cheap work, just do it
function SearchResults({ query, filters }) {
  const results = filterItems(query, filters);   // ~50us over 200 items
  return <List items={results} />;               // render cost is elsewhere
}

Dependencies that are themselves functions or objects defeat the memo even when the list is honest, because the identity changes per render. The fix is not a deep comparator — it is to make the value stable: hoist literals out of the component, obtain callbacks from a stable dispatcher like useDispatch, or rebuild the object inside the memo so the cache key is the primitives and the output is the structure. Every stable identity you create is also one that a child wrapped in memo can compare successfully, so the two techniques compound.

// unstable dependency: the array is correct, the cache never hits
function Report({ rows }) {
  const summary = useMemo(() => {
    const config = { currency: 'EUR', locale: 'de-DE' };  // new object... but
    return buildSummary(rows, config);                     // built INSIDE, fine
  }, [rows]);                                              // rows is the only key

  const onExport = useCallback(() => exportSummary(summary), [summary]);
  return <SummaryView summary={summary} onExport={onExport} />;
}

// unstable callback dependency: derived from fresh props every render
function Editor({ doc, onSave }) {
  const save = useCallback(() => onSave(doc.id, editorState), [doc, onSave]);
  // doc is usually a new object from the cache lib per fetch - pass doc.id
  const save2 = useCallback(() => onSave(doc.id, editorState), [doc.id, onSave, editorState]);
}

Rules of thumb that survive contact with real code

Compute during render; add useMemo only when a measurement says the computation is expensive or when a child's memo needs a stable reference. Keep dependency arrays complete rather than clever — a memo that recomputes when it should is a performance note, while one that does not recompute when it should is a bug, and the two are never worth trading. Let the exhaustive-deps lint rule run as an error in CI and treat every suppression comment as a reviewable decision with a written reason next to it.

Suppressing exhaustive-deps and marking the array "correct as-is" is the most common way stale closures reach production. If the rule is genuinely wrong for a case — a stable-by-construction ref, a dispatch — the fix is to make the stability visible in the code, such as an explicit useRef or an eslint-disable with the invariant named, not to silence it silently.

The React 19 compiler

The React compiler — formerly React Forget — memoises for you at build time. It analyses each component and hook, works out which values it reads, and inserts cache-and-invalidate logic so that a component skips rendering when its inputs are unchanged, without you writing memo, useMemo or useCallback anywhere. The mental model it rewards is the one the guide has been building since chapter 1: components as pure functions of their props and state. The compiler can only skip a render it can prove is unnecessary, and it can only prove that when the component does not do things it cannot see.

Two consequences follow for your codebase. First, the manual memoisation tax drops — useCallback wrappers around handlers, useMemo around trivial object literals, memo on leaves — because the compiler emits equivalent or better output and keeps it correct as dependencies change. Second, the correctness rules harden: components must not mutate props or state, must not read write-only values during render, and must keep side effects out of the render body, because these are precisely the patterns that make "did this render need to happen" unanswerable. The compiler is a forcing function for the purity discipline the rest of the guide teaches anyway.

// before the compiler: memoisation you maintain by hand
const TodoItem = memo(function TodoItem({ todo, onToggle }) {
  const label = useMemo(() => formatLabel(todo), [todo]);
  const handle = useCallback(() => onToggle(todo.id), [onToggle, todo.id]);
  return (
    <li>
      <input type="checkbox" checked={todo.done} onChange={handle} />
      {label}
    </li>
  );
});

// after the compiler: the same component, no memo vocabulary at all.
// the compiler caches label on todo, the handler on onToggle + todo.id,
// and skips the render when both are unchanged.
function TodoItem({ todo, onToggle }) {
  const label = formatLabel(todo);
  const handle = () => onToggle(todo.id);
  return (
    <li>
      <input type="checkbox" checked={todo.done} onChange={handle} />
      {label}
    </li>
  );
}

Adoption is a build-plugin change — a Babel or SWC plugin — with an eslint rule set that flags the patterns the compiler cannot optimise. The recommended migration is incremental: enable the plugin, run the compiler's output analysis to see how many components it already handles, fix the blockers the lint rules report, and only then remove hand-written memoisation where the compiler now covers it. Components it cannot optimise are not broken; they simply behave exactly as they did before, which makes partial adoption safe.

What the compiler does not do

It does not fix a bad component boundary — if a component re-renders because its parent passes new children JSX, the compiler can memoise the render but cannot stop the elements from being created. It does not help the commit phase: skipped renders save JavaScript, not DOM writes. And it does not make impure code safe; a component reading Date.now() during render can be skipped at the wrong moment and show the user a stale timestamp. The compiler raises the floor for render-phase cost, and chapters 11, 14 and 18 still own everything downstream of it.

Enable the compiler in development first and keep the render-count tests from chapter 11 running throughout. They are the cheapest way to see whether the compiler is actually skipping the renders you expected — the build succeeds either way, and a silently unoptimised component looks identical to an optimised one in a passing test suite.

When memoisation makes things worse

Every memo is a standing bet that comparison is cheaper than re-rendering. The bet loses in three recurring situations. A memoised component whose props change on most renders pays a full shallow comparison every parent render and still renders — pure overhead added to the hot path. A deeply memoised tree where most comparisons fail early wastes time walking props structures that were never stable, turning a flat render into a tree of partial ones. And memoised closures and objects extend the lifetime of their captured values, which on a long-lived page with large data means memory that a plain re-render would have released with the old tree.

The diagnostic for a losing bet is the same one used everywhere in this chapter: profile with the memo, profile without it, on the real interaction. The ranked chart makes the result legible — if total actual duration is unchanged or worse with the wrapper present, the comparison is not buying anything. There is also a code-level smell worth recognising: a component wrapped in memo whose props are documented as "unstable" or "new object each render" is an optimisation that provably never fires, and the honest fix is to delete it and address the props, not to add a custom comparator and hope.

// a memo that cannot fire: props are rebuilt every render
function Toolbar({ view, onAction, meta }) {
  const actions = { onAction, meta };        // new object each render
  return <MemoBar view={view} actions={actions} />;
}
const MemoBar = memo(Bar);

// deleting the wrapper is correct here - then make the child cheap instead
function Toolbar({ view, onAction, meta }) {
  return <Bar view={view} onAction={onAction} meta={meta} />;
}
// Bar is a thin shell; its children are memoised where they earn it.

// the real optimisation: stable primitives + stable handlers at the source
function Toolbar({ view, dispatch, metaId }) {
  const onAction = useCallback((a) => dispatch({ type: a, metaId }), [dispatch, metaId]);
  return <MemoBar view={view} onAction={onAction} />;   // now it can fire
}

The second failure mode is subtler: memoised components in a list where the key or the props shuffle cause almost all comparisons to fail, so you get the comparison cost for zero skips while the render order churns. This is common with sorted lists — every sort swaps identities, and identity-based comparison correctly concludes that everything changed. Here the structural fix is to memoise the sort itself (chapter 11's derivation rule) so the array of rows is stable between renders, letting the per-row comparisons succeed rather than sorting inside the parent on every keystroke.

// comparison churn: the sort rebuilds every prop, memo skips nothing
function ListView({ items, query }) {
  const sorted = [...items].sort(byScore);           // new array identity
  return sorted.map((it) => <Row key={it.id} item={it} query={query} />);
}
const Row = memo(RowImpl);
// query changes per keystroke -> every Row re-renders AND every Row is
// compared. memo added cost, removed nothing.

// stabilise the expensive input first, then the comparisons succeed
function ListView({ items, query }) {
  const sorted = useMemo(() => [...items].sort(byScore), [items]);
  return sorted.map((it) => <Row key={it.id} item={it} query={query} />);
}
// rows still re-render on query (they display it), but only the render that
// changed query does work - unrelated commits now skip the whole list.

Deleting memoisation is a valid optimisation

In a compiler-enabled codebase, hand-written memoisation is legacy surface: it must be kept correct as props evolve, it hides the real dependency structure behind wrappers, and it occasionally blocks a compiler improvement by wrapping a component in a way the analysis cannot see through. Treat removal as a change to be measured like any other — delete, run the render-count tests, compare profiles, keep the deletion if the numbers hold. Optimisation is a practice, not a possession; code that once earned its place can outlive it.

Never add a custom React.memo comparator to "fix" a memo that is not firing without first asking why the props change. The comparator hides the identity churn from React but not from the code that produces it — and the moment a genuinely new prop arrives, the component will not re-render while its siblings do, which is a data-freshness bug that no test will catch unless you wrote one for exactly that prop.

Reading async values with use

use is a hook you can call conditionally — the first one permitted to break the call-order rule, and for a good reason: its entire purpose is to read a value that may or may not be ready yet. Given a promise, it suspends until the promise resolves, handing control back to the nearest Suspense boundary; given a context, it reads that context from inside a branch, which useContext never allowed because it had to run on every render. The suspending behaviour is what makes it different from await: await blocks a function that is already committed to finishing, while use unwinds to React, which can keep the rest of the screen interactive while the value is pending.

The design implication is that promises become ordinary props. A parent fetches — or receives from a server component — a promise, passes it to three children, and each child calls use(promise). All three suspend on the same promise, React deduplicates the read within one render pass, and the Suspense boundary you placed decides where the fallback appears. Data then flows down the tree as promises and reading is the child's decision, not a refetch the child initiates. This inverts the usual client-fetching shape where every leaf that needs data starts its own request in an effect, which was the source of the request waterfalls chapter 15 exists to eliminate.

// passing a promise down; each reader suspends on it, no refetch
import { use, Suspense } from 'react';

function UserBadge({ userPromise }) {
  const user = use(userPromise);        // suspends until resolved
  return <span>{user.name}</span>;
}

function UserPermissions({ userPromise }) {
  const user = use(userPromise);        // same promise -> same resolution
  return <ul>{user.permissions.map((p) => <li key={p}>{p}</li>)}</ul>;
}

export function Profile({ userPromise }) {
  return (
    <Suspense fallback={<BadgeSkeleton />}>
      <UserBadge userPromise={userPromise} />
      <UserPermissions userPromise={userPromise} />
    </Suspense>
  );
}

Caching is the part you must own yourself. A promise passed as props is only deduplicated within a single render pass — create a new promise on every parent render and every reader suspends again, flashing fallbacks forever with the network happily cooperating. Cache the promise where it is created: a module-level map keyed by id, the framework's data cache, or state updated inside a transition. The rule is the same one chapter 15 states for all data fetching: one owner, one cache, everything else reads through it. A promise is no different from the response body it resolves to, and treating ad-hoc promise creation as harmless is how a Suspense-enabled screen turns into a flicker machine.

// WRONG: a new promise per render -> every reader re-suspends
function Profile() {
  const [user, setUser] = useState(null);
  useEffect(() => { fetch('/api/me').then((r) => r.json()).then(setUser); }, []);
  // passing Promise.resolve(user) as a prop on each render creates a fresh
  // promise identity every time - readers suspend on every parent render.
  return <Badge userPromise={Promise.resolve(user)} />;
}

// RIGHT: cache the promise at its owner, keyed like any other cache
const userCache = new Map();
function getUser(id) {
  if (!userCache.has(id)) {
    userCache.set(id, fetch('/api/users/' + id).then((r) => r.json()));
  }
  return userCache.get(id);              // same promise for every reader
}

function Profile({ userId }) {
  return <Badge userPromise={getUser(userId)} />;
}

use with context: the conditional read

The context form exists because the classic failure was wanting to read a context only when a flag makes it relevant — a conditional read that useContext forbids outright, since the hook must run unconditionally on every render. use(SomeContext) permits the branch. What it still does not permit is a call after an early return that sometimes happens before it: a hook invoked in one render and skipped in the next breaks the hook-order contract, and the error surfaces far from its cause as a mismatched-state crash. Conditionality means inside a branch, not after returning — the distinction trips up nearly everyone on first contact, and the double-invocation StrictMode performs in development makes the failure loud, which is the favour.

// legal: the read is inside a branch that either runs or does not, and
// the hook count stays identical because both paths call the same hooks
function Panel({ mode }) {
  const [open, setOpen] = useState(false);
  if (mode === 'advanced') {
    const theme = use(ThemeContext);     // conditional context read: OK
    if (!open) return <Collapsed theme={theme} />;
    return <Advanced theme={theme} />;
  }
  return <Basic open={open} onToggle={() => setOpen(!open)} />;
}

// still illegal: an early return BEFORE a hook changes the hook order
function Broken() {
  const [a, setA] = useState(0);
  if (a > 10) return <Done />;           // returns before the next hook...
  const theme = use(ThemeContext);        // ...so this run has 2 hooks, not 1
  return <Work theme={theme} />;
}

use suspends, and suspension is contagious: a use inside a subtree with no Suspense boundary above it unwinds the whole render to the nearest boundary, and a React 19 app without one has that boundary at the root — so one pending promise blanks the entire screen. Every promise read through use needs a boundary positioned deliberately, which is chapter 14's subject.

Actions and useActionState

An action is any async function passed to a transition — a form submission, a handler wrapped in startTransition, a framework server action — that React treats as a unit of intent: it may re-render components, suspend, and report its own pending and result state. The React 19 addition is useActionState, which takes such a function and returns three things: the latest state that action returned, the submission function to pass to a form, and a pending boolean. The state returned by the action is the state you render — not the action's raw return value on first render, but whatever the previous invocation left behind, seeded with the initial state you provide.

What it implements is the oldest form state machine there is: idle, submitting, resolved or rejected. What is new is that the library owns the transition. Submitting does not blank the screen — under concurrent rendering the old UI stays interactive while the action runs, and any component reading useFormStatus picks up the pending flag without prop threading. Validation failures return from the action as data rather than thrown exceptions, which is the shape that makes progressive enhancement possible: the same function can run on the server without JavaScript and return the error state in the very first response.

'use client';
import { useActionState } from 'react';

// the action: receives the previous state and the submitted FormData,
// returns the new state. pending and result come from the hook - there is
// no manual isLoading bookkeeping anywhere in this component.
async function subscribe(prevState, formData) {
  const email = String(formData.get('email') || '');
  if (!/^[^@]+@[^@]+\.[^@]+$/.test(email)) {
    return { error: 'Enter a valid email address', email };   // validation as data
  }
  try {
    await api.subscribe(email);
    return { ok: true, email: '' };
  } catch (err) {
    return { error: err.message || 'Subscription failed', email };
  }
}

export function SubscribeForm() {
  const [state, formAction, pending] = useActionState(subscribe, { error: null, email: '' });
  return (
    <form action={formAction}>
      <input name="email" defaultValue={state.email}
             aria-invalid={state.error ? true : undefined}
             aria-describedby={state.error ? 'sub-error' : undefined} />
      {state.error && <p id="sub-error" role="alert">{state.error}</p>}
      <button disabled={pending}>{pending ? 'Subscribing…' : 'Subscribe'}</button>
    </form>
  );
}

Actions also retire the mutation-in-effect pattern that chapter 8 warns about. In React 18 the instinct after a submit was a useEffect watching a submitted flag — an effect that exists only to mirror state the handler set, that races with unmount, and that double-fires under StrictMode. With an action, the mutation is the submit handler: call it, await it, render what it returned. Nothing watches anything and the code reads in the order events happen. If your codebase contains an effect whose dependency array holds a boolean named submit, save or dirty, that is precisely the shape this replaces, and the replacement deletes the effect rather than fixing it.

// BEFORE React 19: the mutation-in-effect anti-pattern from chapter 8
function OldForm() {
  const [email, setEmail] = useState('');
  const [submitted, setSubmitted] = useState(false);
  useEffect(() => {                          // effect exists only to mirror
    if (!submitted) return;                  // state that the handler set
    api.subscribe(email).then(() => setDone(true));   // and races with unmount
  }, [submitted, email]);
  return <form onSubmit={(e) => { e.preventDefault(); setSubmitted(true); }}>/* ... */</form>;
}

// AFTER: the mutation is the handler; the effect is gone entirely
function NewForm() {
  const [email, setEmail] = useState('');
  const [state, action, pending] = useActionState(subscribe, { error: null });
  return (
    <form action={action}>
      <input name="email" value={email} onChange={(e) => setEmail(e.target.value)} />
      <button disabled={pending}>Send</button>
    </form>
  );
}

The action's contract with the server

When a framework offers server actions, the same function is the client/server boundary: the client copy is a stub that starts the transition, the server copy runs with FormData, and its return value crosses back as the new state. Design the contract so the return value is always serialisable data — plain objects, strings, arrays — never a thrown error the client must catch across the wire. Returning an error object rather than throwing means every failure the server can produce arrives in the same channel as success, and one conditional in the JSX covers all of them. Thrown errors, by contrast, take a different path: they land at the nearest error boundary, which is a recovery UI, not a validation message beside a field.

// the same action, two runtimes - the contract is the signature
async function renameProject(prevState, formData) {
  const name = String(formData.get('name') || '').trim();
  const id = String(formData.get('id') || '');
  if (name.length < 3) return { error: 'Name too short', name };
  try {
    const updated = await api.rename(id, name);   // server: the real call
    return { ok: true, name: updated.name };      // serialisable either way
  } catch (err) {
    return { error: 'Rename failed - try again', name };
  }
}

// client: transition + pending state, no fetch, no catch
const [state, action, pending] = useActionState(renameProject, { error: null });
return (
  <form action={action}>
    <input type="hidden" name="id" value={project.id} />
    <input name="name" defaultValue={state.name} />
    {state.error && <p role="alert">{state.error}</p>}
    <button disabled={pending}>Rename</button>
  </form>
);

Keep actions small and single-purpose — one intent, one returned state object. An action that renames, archives and notifies in one call forces the returned state to model three outcomes; three actions composed by the caller each return one outcome, and the JSX that renders them stays a single conditional apiece.

useOptimistic and useFormStatus

useOptimistic gives you a value that shows the intended result immediately while the real one is in flight, then snaps back to reality when the action settles. Its signature is a state plus a setter that behaves like useState, except that React keeps the pre-optimistic value and restores it automatically when the enclosing action completes or fails. You never write the rollback yourself — which is the whole point, because hand-rolled optimistic state is where the bugs live: the update succeeds, the refetch returns stale data, and the UI flickers back to the old value for reasons nobody can name.

The pairing that matters is useOptimistic inside the action's lifecycle: set the optimistic value before the await, let the action's real return value update the underlying state, and React handles the ordering. If the action throws, the optimistic value is discarded and the previous state stands — no error handler needed for the visual rollback, only for the user-facing message. The discipline is that the optimistic value must be derived from the same data the action will finally write; showing an optimistic state you have not designed the server's answer for is how a UI ends up confidently wrong.

'use client';
import { useOptimistic, useActionState } from 'react';

async function sendMessage(text) {
  await api.post('/messages', { text });
  return { ok: true };                    // the action's real result
}

function Thread({ messages }) {
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (current, text) => [...current, { id: 'temp', text, pending: true }]
  );
  const [state, action, pending] = useActionState(sendMessage, null);

  async function submit(formData) {
    const text = String(formData.get('text') || '');
    startTransition(async () => {
      addOptimistic(text);                // shown immediately
      await action(formData);             // when it settles React discards
    });                                   // the optimistic entry itself
  }

  return (
    <>
      <ul>
        {optimistic.map((m) => (
          <li key={m.id} aria-busy={m.pending || undefined}>{m.text}</li>
        ))}
      </ul>
      <form action={submit}><input name="text" /></form>
    </>
  );
}

useFormStatus is the third leg: a hook read by a component inside a form that reports whether the nearest parent form is currently submitting — no prop is passed, because the status lives on the DOM ancestor relationship the browser already knows. It returns pending plus the form's data and method. Its structural rule is easy to state and easy to violate: the hook must run in a descendant of the <form>, never in the component that renders the form itself. The submit button, the fieldset, the progress bar — these are its natural readers, and because it reaches up through the DOM it composes with forms whose action you never see.

// useFormStatus reads the NEAREST parent form - button inside, no props
function SubmitButton() {
  const { pending, data } = useFormStatus();   // from react-dom
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Saving ' + (data.get('title') || '…') + '…' : 'Save'}
    </button>
  );
}

function EditorForm() {
  const [state, action] = useActionState(saveDoc, { error: null });
  return (
    <form action={action}>
      <input name="title" />
      <SubmitButton />         {/* descendant of this form: it sees pending */}
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}

// WRONG: calling it in the component that RENDERS the form
function Wrong() {
  const { pending } = useFormStatus();   // looks at the enclosing form - none
  return <form action={action}>{/* pending is always false here */}</form>;
}

Because useFormStatus reads through the DOM, it works with any submit mechanism — a plain <form> with an action, a server-action form, or a manual requestSubmit(). This is why the pending flag belongs to the DOM tree rather than to React context: the browser already knows which form is submitting, and the hook simply reports it.

Optimistic updates and the rollback contract

The contract to hold in your head: the optimistic value is a promise to the user, and the action's settlement is the moment that promise is kept or withdrawn. Design the action so its return value is what the server really stored — the optimistic entry disappears the instant the real data arrives, which is why an optimistic shape that differs from the real one (a temp id that never gets replaced, a field the server normalises) leaves a visible seam. Keep the optimistic mutation shaped exactly like the real result, and the snap from optimistic to real is invisible.

// the seam: optimistic shape must match what the action returns
async function toggleTodo(prev, formData) {
  const id = String(formData.get('id'));
  const done = formData.get('done') === 'true';
  const saved = await api.patch('/todos/' + id, { done });
  return { id: saved.id, done: saved.done };   // real row, same shape
}

function TodoRow({ todo }) {
  const [done, setDone] = useOptimistic(todo.done, (_, next) => next);
  return (
    <li>
      <form action={toggleTodo}>
        <input type="hidden" name="id" value={todo.id} />
        <input type="hidden" name="done" value={String(!done)} />
        <button onClick={() => setDone(!done)}>{done ? 'Done' : 'Todo'}</button>
      </form>
    </li>
  );
}

An optimistic value is discarded when the action settles — including when it fails. That automatic rollback is the feature, but it means the user sees the old state again with no explanation unless you surface one. Every optimistic path needs a companion error message: the rollback is automatic, the communication is not.

ref as a prop, forwardRef gone

In React 19, ref is an ordinary prop. A function component receives it as props.ref and passes it to whatever element it renders; forwardRef remains supported but is no longer required for any new code, because the compiler and the runtime both treat ref as just another prop that happens to be attached during commit. The visible consequence is a class of wrapper components — the ones that existed only to thread a ref through — collapsing into the components they wrapped. The useImperativeHandle pairing does not change: when a component wants to expose a handle instead of a DOM node, the recipe is identical, only without the wrapping function.

The second ref change is smaller and easier to miss: refs may now take cleanup functions, the same contract effects have. A callback ref that acquires something — an observer, a timer, a canvas context — can return a cleanup that releases it when the ref detaches or its value changes. Before React 19 this required a separate effect watching the ref's current value, which is exactly the pattern chapter 9 warns drifts out of sync with the DOM. The ref's own lifecycle now covers acquire and release in one place.

// React 18: the wrapper existed only to forward the ref
const Input = forwardRef(function Input(props, ref) {
  return <input ref={ref} {...props} />;
});

// React 19: ref is a prop, the wrapper is gone
function Input(props) {
  return <input {...props} />;          // props.ref is spread like any prop
}

// React 18: exposing a handle
const Fancy = forwardRef(function Fancy(props, ref) {
  useImperativeHandle(ref, () => ({ focus: () => inputRef.current.focus() }), []);
  return <input ref={inputRef} />;
});

// React 19: identical, minus the forwardRef ceremony
function Fancy(props) {
  const inputRef = useRef(null);
  props.ref && useImperativeHandle(props.ref, () => ({
    focus: () => inputRef.current.focus(),
  }), []);
  return <input ref={inputRef} />;
}

Callback refs with cleanup close the last gap between refs and effects for DOM-shaped work. Observing an element's size, subscribing to a MutationObserver, attaching a pointer listener to a canvas: each of these wants a function called with the node when it mounts, a different function called when it unmounts, and a re-run when the node is replaced. The callback ref returning its own teardown expresses all three directly, and unlike the effect version it never runs before commit, so the node is guaranteed to exist. Chapter 9's measure-and-resize patterns are the natural place to adopt it.

// callback ref with cleanup: acquire and release in one declaration
function useSize(targetRef) {
  const [size, setSize] = useState({ width: 0, height: 0 });
  return [
    (node) => {                        // called with the node on attach
      if (!node) return;
      const ro = new ResizeObserver((entries) => {
        const r = entries[0].contentRect;
        setSize({ width: r.width, height: r.height });
      });
      ro.observe(node);
      return () => ro.disconnect();    // React 19: cleanup on detach/change
    },
    size,
  ];
}

function Panel() {
  const ref = useRef(null);
  const [setRef, size] = useSize(ref);
  return <div ref={setRef}>{size.width} x {size.height}</div>;
}

// React 18 equivalent needed a useLayoutEffect watching ref.current,
// plus a second effect for the cleanup - two effects, one node.

What still needs forwardRef

Nothing in new code. Existing forwardRef calls keep working — React treats the wrapped component's ref prop the same way — so migration can happen file by file rather than in a flag day, and the compiler will not complain either way. The one subtlety worth knowing: a component that reads props.ref manually and passes it on is behaving like the wrapper it replaced, and if you destructure ref out of props you must remember to spread the rest, or the ref silently stops arriving at the element.

// the destructure trap: ref out of props, then not re-attached
function Field({ label, ref, ...rest }) {   // ref pulled out of props
  return (
    <label>
      {label}
      <input {...rest} />                   {/* ref was NOT spread - lost */}
    </label>
  );
}

// correct: pass it explicitly, or leave it in the spread
function Field({ label, ref, ...rest }) {
  return (
    <label>
      {label}
      <input ref={ref} {...rest} />
    </label>
  );
}

When you delete a forwardRef wrapper, delete the whole indirection: the re-export, the alias, the barrel entry. A file that now only adds a call to the function it wraps is a place where the next reader looks for behaviour that is not there.

Upgrading a React 18 codebase

The migration that matters is behavioural, not package-manager-based. Bumping to 19 while every form still carries its own isLoading state and every component still wraps its children in forwardRef gives you a new version of the old application. The order that keeps a codebase compiling and reviewable at each step: upgrade the toolchain and take the peer-dependency hit first; adopt ref as a prop opportunistically wherever a wrapper exists; replace mutation-in-effect patterns with actions form by form; then add use and Suspense where data flow already passes promises. Each step is independently shippable and independently revertable.

Two upgrades deserve explicit attention because they change runtime behaviour rather than syntax. StrictMode's development double-invocation of effects becomes the norm your code must already satisfy — if an effect double-subscribes or double-fetches without cleanup, the upgrade will surface it, and the fix is cleanup, not disabling StrictMode. And the removal of string refs, defaultProps on function components, and the module-pattern factories means the build will fail loudly rather than quietly; treat every one of those failures as a free report on debt that was invisible before. Nothing in the React 19 upgrade path requires a rewrite of your state model.

// step 1: package.json - the version bump is the easy half
{
  "dependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  },
  "devDependencies": {
    "@types/react": "^19.0.0",
    "@types/react-dom": "^19.0.0",
    "eslint-plugin-react-hooks": "^5.0.0"
  }
}

//   npx react-codemod remove-forward-ref src/
//   npx react-codemod update-react-19 src/
// each codemod leaves a compiling tree; the review decides what to keep

Third-party libraries are the usual source of upgrade stalls: anything that imports react-dom/unstable-render-subtree, patches internals, or peer-pins React 18 will warn or break. Resolve by checking whether the library has a React 19 release, and if not, whether the feature it provides has a React 19 native replacement — several context helpers and ref-forwarding utilities simply became unnecessary. Where no replacement exists, pin that one package and isolate it behind your own module so the rest of the codebase does not import its API directly; the isolation makes the eventual removal a single-file change.

//   import { LegacyChart } from '@/lib/legacy-chart';
// when the lib ships 19 support, only this file changes.

// step 3: verify behaviour, not just compilation
//   - every form still submits, errors render, pending shows
//   - effects clean up (StrictMode on in development is the test)

Verifying the upgrade

A green build after a major React bump proves that the code compiles, not that the app behaves. Three checks catch the classes of regression that actually happen: run the full suite with StrictMode deliberately enabled in development, because double-invoked effects expose every missing cleanup; walk each form through its error path, because action-based forms fail differently than effect-based ones — returned data, not exceptions; and click every ref-dependent interaction (focus rings, scroll-to-row, canvas init) once, because ref threading is where a destructuring mistake hides silently. These are half a day of manual work against a release that took a week, and they cover the three real failure modes.

Keep the old version on a branch until the manual walk-through passes, not merely the test suite. The React 18 to 19 changes that bite hardest — ref handling, action-based form failures, effect timing under StrictMode — are precisely the ones most test suites do not cover, because they were mechanical in the old model.

Suspense and transitions are two answers to the same question: what does the user see while work is still happening. Suspense draws the line on the screen — here is pending, here is content. Transitions draw the line in time — this update can wait so that one cannot. Used together they are what makes a React app feel deliberate rather than jumpy.

Boundaries and where they go

A Suspense boundary is a promise from the layout to the user: everything below this point may be temporarily unavailable, and when it arrives it will appear in place, without moving what is already on screen. The boundary is what makes that promise enforceable — a component below it may suspend (from use, from a framework data hook, from React.lazy) and React replaces only that subtree with the fallback, keeping the rest of the page mounted, interactive and holding its state. Without a boundary the suspension travels to the root, and the whole screen goes to fallback, which is the failure mode people mean when they say Suspense caused flicker.

Placement therefore follows the layout, not the data. Put a boundary around each independently-arriving region — the sidebar, the table, the chart panel — so each one can resolve on its own schedule, and put none around regions that must arrive together or that are above the fold as a unit, because a boundary inside a region that needs all its children at once just moves the wait without shortening it. A useful test: cover the region with your hand and ask whether the rest of the screen is still usable if it is missing. If yes, it wants a boundary. If no, the boundary belongs higher.

// one boundary per independently-arriving region
function Dashboard({ reportPromise, activityPromise }) {
  return (
    <div className="grid">
      <Header />                                   {/* never suspends */}
      <Suspense fallback={<ReportSkeleton />}>
        <Report promise={reportPromise} />        {/* its own boundary */}
      </Suspense>
      <aside>
        <Suspense fallback={<ActivitySkeleton />}>
          <Activity promise={activityPromise} />  {/* resolves independently */}
        </Suspense>
      </aside>
    </div>
  );
}

// WRONG: one boundary at the root -> a pending sidebar blanks the report
function BadDashboard(props) {
  return <Suspense fallback={<PageSkeleton />}><Dashboard {...props} /></Suspense>;
}

Boundaries compose, and nesting them is how you get granularity without losing the coarse safety net: a page-level boundary catches everything, regional boundaries inside it catch their own subtrees first. The innermost boundary wins, so the finer ones should sit lower. One structural rule keeps this maintainable: a boundary should be rendered by the component that owns the region's layout, not by the component that performs the fetch. A boundary embedded deep inside a data-owning component couples fallback presentation to data plumbing, and the moment you want a different skeleton for a different context you have to move it anyway.

// boundaries owned by layout, data owned by leaves
function SettingsPage() {
  return (
    <section>
      <h2>Notifications</h2>
      {/* layout decides this region exists and how it looks while pending */}
      <Suspense fallback={<SettingsRowSkeleton rows={3} />}>
        <NotificationSettings />     {/* leaf decides HOW to fetch */}
      </Suspense>
    </section>
  );
}

function NotificationSettings() {
  const prefs = use(preferencesPromise);   // suspends; the boundary above pays
  return <PreferenceList prefs={prefs} />;
}

The state-preserving property

When a subtree suspends behind an already-mounted boundary, React does not unmount the existing content — it keeps showing the current content while the new data loads, and swaps when ready. That is the behaviour that makes transitions feel smooth, and it only exists if the boundary is already mounted when the suspension happens. A boundary rendered for the first time at the same moment as the suspending child has nothing to keep showing, so its fallback appears: the flicker case. Ensure boundaries mount before the data they guard, which in practice means the boundary lives in the initial render of the region and the fetch is triggered after.

Suspense is a rendering contract, not a loading contract: it says "this subtree is not ready", and whether that means fetching, a slow computation, or a lazy chunk download is the caller's business. This is why the same boundary covers a data hook and a React.lazy import without knowing which is inside.

Fallbacks that do not lie

A fallback is shown for an unknown duration, so its job is to communicate structure and ownership, not progress. The worst fallback is a spinner on an empty page: it says nothing about what is coming, and the moment the content arrives — often at a different height — the entire layout jumps. The second worst is a perfect skeleton of the loaded content, because if the real content differs in shape the skeleton was a promise broken. The right fallback mirrors the structure of the region at roughly its final size, without pretending to know the values.

Layout stability is the measurable part. Give the fallback the same footprint the content will occupy — same grid, same row count where it is predictable, same minimum height — so that arrival causes zero reflow of surrounding regions. The test is a screenshot comparison with the network throttled: a good fallback and the loaded state should differ in texture, not in geometry. Beyond geometry, fallbacks owe the user two things: they must not remove interactive chrome that does not depend on the pending region (a page title, a back button, a search field that searches something else), and they must not trap focus or steal it — a fallback that renders a button the content will not have is a focus trap waiting to snap shut.

// fallback that keeps the geometry: same grid, same row heights
function Panel({ children }) {
  return (
    <div className="panel-grid">
      <Suspense
        fallback={
          <div className="panel-grid" aria-busy="true">
            {/* same class as the loaded content: identical layout box */}
            {Array.from({ length: 6 }, (_, i) => (
              <div key={i} className="panel-cell panel-cell--pending" />
            ))}
          </div>
        }
      >
        {children}
      </Suspense>
    </div>
  );
}

// the loaded content uses the same panel-grid / panel-cell classes,
// so arrival swaps texture, not geometry - zero layout shift.

Announce the pending state to assistive technology without turning every refresh into noise. Marking the region aria-busy="true" while the fallback shows is the structured signal; a live-region announcement ("Loading report") is appropriate the first time a region loads and irritating on every refetch. The distinction mirrors the visual one: a first load is new content appearing, a background refresh is content being maintained. Design the fallback for both cases rather than only the first — a region that goes blank on every refetch teaches users not to trust it.

// announce the first load, stay quiet on background refresh
function AnnouncedRegion({ promise, firstLoad, children }) {
  return (
    <section aria-busy="true"
             aria-live={firstLoad ? 'polite' : 'off'}
             aria-label="Report">
      <Suspense fallback={<ReportSkeleton />}>{children}</Suspense>
    </section>
  );
}

// and never use the fallback for a REFRESH: under a transition, React keeps
// the current content mounted while the new data loads (next section), so
// the skeleton only ever appears once per region, at first mount.

What a fallback must never contain

Interactive controls whose behaviour depends on the pending content — a submit button for a form that has not loaded, a filter for a table that does not exist yet, a link to a detail view you cannot address. Focus can land on these, activation does nothing or throws, and the user has no way to know why. Static presentation, a status message, and the chrome that stands on its own are all fine; anything that accepts input must either work or be visibly disabled with the disabled reason stated.

A fallback rendered by a region that suspends on every keystroke — the anti-pattern of fetching in render without a transition — turns the skeleton into a strobe. If your fallback appears repeatedly rather than once, the fix is not a subtler fallback; it is chapter 14's transitions: the update causing the suspension must be marked as non-urgent.

Transitions: urgent versus predictable

React 18 divided updates into two kinds: urgent, which the user expects to see immediately (typing, clicking, dragging — the element under the pointer must respond in this frame), and transitional, which the user expects to settle rather than instantaneously appear (filtering a large list, opening a detail view whose data is loading, navigating). startTransition marks a state update as the second kind: React may interrupt it, render it at lower priority, and — critically — keep the current content on screen while it completes instead of dropping to a fallback. The API is two lines; the semantics it activates are the whole of concurrent rendering's user-facing value.

The signature behaviour worth internalising: if a transition's render suspends, React keeps showing the old UI until the new one is ready, even though the state has already changed. That is the difference between a search box that blinks a skeleton per keystroke and one that shows results the moment they are ready while you keep typing. And if a newer urgent update arrives mid-transition, React discards the transition's progress and starts again from the new state — transitions are interruptible, which is exactly why typing during a slow filter never feels locked. The rule for when to use one follows from the two categories: wrap the update if the user would accept waiting; do not wrap it if the user would be surprised that nothing happened.

// urgent: the input must repaint THIS frame
function SearchBox({ query, onQuery }) {
  return <input value={query} onChange={(e) => onQuery(e.target.value)} />;
}

function Results({ query }) {
  const [rows, setRows] = useState([]);
  const [pending, startTransition] = useTransition();

  function handleChange(next) {
    // urgent half: the input is controlled by query state in the PARENT,
    // which updates immediately...
    onQuery(next);
    // transitional half: the expensive derived list can wait and be
    // interrupted if the user keeps typing
    startTransition(() => {
      setRows(filterHugeList(next));
    });
  }

  return (
    <>
      <SearchBox query={query} onQuery={handleChange} />
      {pending && <span role="status">Filtering…</span>}
      <List rows={rows} />
    </>
  );
}

Transitions pair with Suspense to produce the behaviour that defines the modern React feel: inside a transition, a suspending render does not show the fallback — it waits. This is the single most useful fact in this chapter, because it converts a design decision (skeleton or keep-current-content?) from a per-component judgement into a property of how the update was scheduled. Refetching a panel after a mutation: transition it, and the panel keeps its old values until the new ones arrive. Navigating to a route whose data is loading: transition it, and the current page stays while the next one prepares.

// refetch under a transition: old content stays until new arrives
function ProjectView({ projectId }) {
  const [project, setProject] = useState(null);
  const [pending, startTransition] = useTransition();

  useEffect(() => {
    startTransition(async () => {           // async transition body
      setProject(await api.getProject(projectId));   // suspends internally
    });                                          // no fallback shown: the
  }, [projectId]);                               // PREVIOUS project stays
                                                 // visible the whole time
  if (!project) return <InitialSkeleton />;   // only for the very first load

  return (
    <>
      {pending && <span role="status">Updating…</span>}
      <Project project={project} />
    </>
  );
}

What not to transition

Do not transition the urgent half of an interaction. A controlled input whose value only updates inside a transition will lag behind the keystrokes, because urgent typing updates must never queue behind a long render — that is precisely the responsiveness guarantee transitions are built to sacrifice for everything else. Likewise, do not transition a state update that toggles something the user is pointing at: a button that goes unpressed after a delay feels broken even when the work behind it succeeds. Split the update: the pointer-visible state updates immediately, the expensive dependent state transitions.

Expose transition pending state to the user as a status, not a blocking overlay. useTransition's pending flag drives a subtle "Filtering…" label or an aria-busy attribute — enough to explain why results lag, never enough to stop the user typing. If your instinct is a spinner over the list during a transition, the update probably should not have been a transition; it should have been urgent.

useDeferredValue and stale input

useDeferredValue is the read-side counterpart of a transition: given a value, it returns that value immediately on the urgent render and a deferred, possibly-stale copy during subsequent low-priority renders. Where startTransition wraps the state update, useDeferredValue wraps the consumption — which makes it the tool for the cases you do not control the update, because it arrives as a prop from a parent, a URL parameter, or a store. The component stays responsive by rendering with last frame's value while the new one catches up.

The comparison that matters: an input with a derived expensive list has two legitimate designs, and both use the same primitive from opposite ends. If you own the state, split it — urgent input state, transitioned derived state, as in the previous section. If you receive the value as a prop, defer it inside the component — render the input from the prop directly and the list from the deferred copy. Both produce the same frame timing: keystroke paints now, expensive subtree reconciles later. The second is often necessary precisely because the parent that owns the value is far away, and threading a transition down to it would couple a leaf's performance needs to an ancestor's API.

// the value arrives from a parent you do not control - defer the read
function BigFilter({ query }) {
  const deferredQuery = useDeferredValue(query);
  const pending = query !== deferredQuery;

  // the input renders from the REAL value: every keystroke paints immediately
  // the expensive subtree renders from the DEFERRED value: it may lag a frame
  const rows = useMemo(() => filterHugeList(deferredQuery), [deferredQuery]);

  return (
    <>
      <input readOnly value={query} />
      {pending && <span role="status">Updating results…</span>}
      <List rows={rows} />
    </>
  );
}

// equivalent timing, opposite control: you own the state, so split it
function OwnsState({ onQuery }) {
  const [query, setQuery] = useState('');
  const [rows, setRows] = useState([]);
  const [, startTransition] = useTransition();
  return <input onChange={(e) => {
    setQuery(e.target.value);                          // urgent
    startTransition(() => setRows(filterHugeList(e.target.value)));
  }} />;
}

Two traps. First, the stale value must be safe to render: if the deferred list is keyed by a value that the urgent render has already moved past — a selected row id that no longer exists in the stale array — you get an index or lookup error precisely during the frames the user is watching. Guard the derived render against staleness (a null check, a "no longer available" state) rather than assuming the two copies agree. Second, using the deferred value as a dependency of anything imperative — an effect that fetches, a subscription that re-registers — reintroduces the lag into a path that cannot skip frames; defer reads for rendering, keep effects on the urgent value.

// staleness is visible: the selection may point outside the deferred list
function Picker({ query }) {
  const deferred = useDeferredValue(query);
  const results = useMemo(() => search(deferred), [deferred]);
  const [selectedId, setSelectedId] = useState(null);

  // results lags query; selectedId may reference a row not in results yet
  const selected = results.find((r) => r.id === selectedId);

  return (
    <>
      <List rows={results} onSelect={setSelectedId} />
      {/* guard the render: do not assume the two copies agree */}
      {selected
        ? <Detail row={selected} />
        : <p role="status">Selecting…</p>}
    </>
  );
}

Measuring the deferral

Confirm the win the same way chapter 11 confirms anything: with the profiler, before and after, on the real interaction. The signature of a correct useDeferredValue adoption is that the urgent input's commit stays under a few milliseconds while the deferred subtree's render moves out of the keystroke's frame — visible as input-handler work shrinking and a second, lower-priority render appearing afterwards. If both renders are still in the same frame, the deferred work is not the bottleneck and the technique bought you an extra render for nothing.

Deferral and transitions are alternatives, not layers: pick one owner for "this update is non-urgent" per interaction. Running both — a transitioned update whose consumer also defers — doubles the lag between what the user did and what they see, and the extra staleness buys no responsiveness the first one did not already provide.

lazy, code splitting and keeping frames

React.lazy takes a function returning a dynamic import and produces a component that suspends until its chunk arrives — which means, with the previous sections in hand, that it is governed by a Suspense boundary like any other pending region. This is the mechanism behind route-level and widget-level code splitting in applications without a framework: the initial payload ships the shell and the first screen, and heavy secondary features — a charting library, a rich-text editor, an admin panel — download only when first rendered. The win is not bytes saved overall; it is bytes moved off the critical path of first interaction.

What makes splitting pay is choosing boundaries that match usage rather than files that match folders. Splitting every component is worse than splitting none: dozens of small requests, a waterfall of chunk discoveries, and worse total latency than one bundle. The right seams are where a usage pattern changes — the detail view behind a list row, the settings modal, anything behind an authenticated area — so that the common path loads one chunk more and the uncommon path loads its cost only when taken. The measurable targets are first-paint and time-to-interactive for the entry route; if a split moves those, it earned its place, and a bundle report in CI (chapter 11's budget) keeps it honest afterwards.

// route-level splitting: the shell never downloads the heavy panels
import { lazy, Suspense } from 'react';

const AdminPanel = lazy(() => import('./AdminPanel'));   // own chunk
const Reports    = lazy(() => import('./Reports'));      // own chunk

function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/" element={<Home />} />            {/* in the shell */}
        <Route path="/admin" element={<AdminPanel />} /> {/* on demand */}
        <Route path="/reports" element={<Reports />} />  {/* on demand */}
      </Routes>
    </Suspense>
  );
}

// WRONG: splitting every component - dozens of round trips, worse than one
const Button   = lazy(() => import('./Button'));
const Badge    = lazy(() => import('./Badge'));
const ListItem = lazy(() => import('./ListItem'));

Prefetching closes the gap between "split" and "split without the user noticing". If the shell can predict the next likely route — the item row that will be clicked, the nav link being hovered — it can start the dynamic import before navigation, so the transition resolves from cache instead of network. This is a small amount of code with a disproportionate effect on perceived speed: the split exists for the rare path, and prefetching makes the common transition to it indistinguishable from an unsplit bundle. React's own examples pair React.lazy with an intersection observer for exactly this, and any router worth using exposes a prefetch option on links.

// prefetch on intent: hover or viewport-entry starts the chunk download
const Reports = lazy(() => import('./Reports'));
let reportsStarted = false;
export function preloadReports() {
  if (reportsStarted) return;
  reportsStarted = true;
  import('./Reports');            // the same specifier -> the same chunk,
}                                 // now cached before anyone navigates

function NavReportsLink() {
  return (
    <Link to="/reports"
          onPointerEnter={preloadReports}
          onFocus={preloadReports}>
      Reports
    </Link>
  );
}

// viewport prefetch for content far down a long list
function useViewportPreload(ref, preload) {
  useEffect(() => {
    const io = new IntersectionObserver((entries) => {
      if (entries.some((e) => e.isIntersecting)) { preload(); io.disconnect(); }
    });
    if (ref.current) io.observe(ref.current);
    return () => io.disconnect();
  }, [ref, preload]);
}

Splitting, boundaries and state — the three regressions

Three ways a splitting pass makes an app worse, each with a distinct symptom. Losing state across a boundary: because a lazy subtree suspends, anything holding local state inside the shell but above the split point survives, while state inside the swapped subtree resets — so a form half-filled in a modal that lazy-loads must live in the store, not the modal. Chunk waterfalls: one lazy component importing another lazily serialises their downloads; check the network panel for chunks arriving in sequence. And duplicate vendors: two chunks each bundling their own copy of a library doubles its bytes across the session — the bundle report from chapter 11 catches this the week it happens, not the quarter after.

Never lazy-load the element that renders the fallback's destination — a lazy component with no Suspense boundary above it, or one placed above a boundary that itself suspends, produces an unhandled suspension that React resolves by unmounting to the root. Every React.lazy call needs a boundary that is guaranteed to be mounted before it, which in practice means the boundary sits in code that was in the initial bundle.

Server data is not component state: it is shared, it arrives out of order, it goes stale while you look at it, and several screens want the same copy at once. This chapter is about handing it to a cache library — the owner chapter 10's decision table names for exactly this value — and designing the query keys, invalidation and mutation flow that make the handoff complete.

Server data has one owner

The distinction the whole chapter rests on: state you own (a draft, a selection, a toggle) originates in the client and the client is its source of truth; state you mirror (a project record, a list of invoices, permissions) originates on the server and the client is a cache of it. Mixing them is the origin of the classic React data bugs — a component fetching into useState so every instance holds its own copy that disagrees with every other's, refetches on mount because nothing else knows the data is already loaded, and cannot be invalidated when a mutation elsewhere changes the record. A cache library exists to be the single place that answers "what is the current value of this server thing", with one entry per query that every component shares.

The decision table in chapter 10 ends with exactly this rule — server data goes to a cache library — and the reason it deserves its own chapter is the breadth of what the cache then handles for you: request de-duplication across components, a single in-flight promise per key, background refetch on window focus or reconnect, stale-while-revalidate rendering, structural sharing so unchanged subtrees keep referential identity, and a mutation flow that can invalidate or patch the affected entries. Writing that yourself is a two-week project that will still be wrong at the edges; using it is a configuration decision you make once per resource type.

// WITHOUT a cache library: every mount is its own request, and the copies lie
function InvoiceList() {
  const [rows, setRows] = useState([]);
  useEffect(() => {
    api.listInvoices().then(setRows);        // fetches on every mount
  }, []);                                     // no dedupe, no invalidation,
  return <Table rows={rows} />;               // two instances = two truths
}

// WITH a cache library: one entry per key, shared by every reader
import { useQuery } from '@tanstack/react-query';

function InvoiceList() {
  const { data: rows = [] } = useQuery({
    queryKey: ['invoices', { status: 'open' }],
    queryFn: () => api.listInvoices({ status: 'open' }),
  });
  return <Table rows={rows} />;
}
// mounting again reuses the cache entry; another screen asking for the
// same invoices gets THE SAME object; a mutation invalidating
// ['invoices'] refetches every reader at once.

What the cache library must never become is a second place where business logic hides. The boundary to enforce: components declare what they read (the key and the fetcher), the library owns when it refetches and how long it keeps it, and mutations decide what is now stale. Application code that reaches around the cache — a direct fetch in an effect, a hand-rolled updatedAt check — reintroduces exactly the split-brain the library exists to prevent. If a piece of code needs the data, it reads the query; if it changes the data, it runs a mutation that tells the cache what changed.

// the boundary: declare reads, declare writes, never fetch behind the cache
// GOOD - a component declares what it reads
function useInvoice(id) {
  return useQuery({
    queryKey: ['invoices', id],
    queryFn: () => api.getInvoice(id),
    enabled: Boolean(id),
  });
}

// BAD - a component fetches behind the cache's back
function Broken({ id }) {
  const [inv, setInv] = useState(null);
  useEffect(() => { api.getInvoice(id).then(setInv); }, [id]);  // second truth
  const { data: cached } = useInvoice(id);                      // first truth
  return <View invoice={inv || cached} />;                      // which wins?
}

Where the library stops

A cache library does not do routing (chapter 16 owns the URL), does not own form state (chapter 17), and does not render — it answers reads and orchestrates writes. Knowing the boundary keeps the architecture legible: the router turns a URL into a set of query keys, the cache turns keys into data, the components turn data into pixels, and mutations turn user intent into new keys' worth of truth. Four owners, four jobs, no overlap.

The server can also be the renderer — React Server Components hand the client a resolved promise instead of a cache entry, which is what use in chapter 13 consumes. That model changes where the fetch happens, not the ownership rule: there is still one owner of the record's value, and if any part of the app mirrors it client-side, the mirror still needs a single shared home.

Query keys and the cache shape

The query key is the cache's primary key and the API's most consequential design decision, because every invalidation, refetch and structural-sharing benefit is expressed in terms of keys. A key must be a deterministic, serialisable description of the data's identity: the resource, its id, and the parameters that change the result — no more. Keys that include incidental state (a sort order that is not part of the request, a component name, a timestamp) fragment the cache into entries that never share; keys that omit parameters that matter (a filter, a page) cause one screen's fetch to poison another's entry with the wrong rows.

The convention that scales is hierarchical arrays: the resource first, then discriminating parameters as an object. Prefix invalidation then reads like SQL — ['invoices'] matches ['invoices', { status }] and ['invoices', id], so marking all invoice queries stale after a create is one call, while ['invoices', 42] precisely targets one record for an optimistic patch. Treat the key structure as a schema: agreed per resource, documented next to the fetchers, reviewed in pull requests. A key format change is a data-identity change and deserves the same scrutiny as a database migration.

// keys as a schema: resource, then discriminating parameters, nothing else
export const invoiceKeys = {
  all:        ['invoices'],
  lists:      () => ['invoices', 'list'],
  list: (f)  => ['invoices', 'list', f],      // f = { status, page, sort }
  detail: (id) => ['invoices', 'detail', id],
  lineItems: (id) => ['invoices', 'detail', id, 'lines'],
};

// GOOD: parameters that change the RESULT are in the key
useQuery({ queryKey: invoiceKeys.list({ status: 'open', page: 1 }),
           queryFn: () => api.listInvoices({ status: 'open', page: 1 }) });

// BAD: key and request disagree - the cache serves page 1's rows for page 2
useQuery({ queryKey: ['invoices', 1],
           queryFn: () => api.listInvoices({ page: 1 }) });

// BAD: key includes state that is not part of the identity - two entries
// for one dataset, invalidated independently, drifting apart
useQuery({ queryKey: ['invoices', { page: 1 }, componentInstanceId], ... });

Aggregating keys into an exported object — the invoiceKeys factory above — is what turns a convention into an invariant. Typo-prone string literals scattered across files are how a cache ends up with two spellings of one query, each invalidated by one code path and refreshed by the other, which presents as "the list updates but the detail page doesn't". With factories, a refactor of the key shape is a one-file edit, and invalidation call sites read as intent (queryClient.invalidateQueries({ queryKey: invoiceKeys.all() })) rather than as pattern matching against strings.

// dependent queries: key B includes the id that key A produces
function useProjectWithTasks(projectId) {
  const project = useQuery({
    queryKey: ['projects', projectId],
    queryFn: () => api.getProject(projectId),
    enabled: Boolean(projectId),
  });

  // the second query waits for the first WITHOUT an effect chain:
  // enabled is the dependency, the cache is the communication channel
  const tasks = useQuery({
    queryKey: ['projects', projectId, 'tasks'],
    queryFn: () => api.listTasks(projectId),
    enabled: project.isSuccess,
  });

  return { project, tasks };
}

// the same relationship expressed as one query with a nested fetcher -
// fewer round trips when the API cannot serve them in parallel:
useQuery({
  queryKey: ['projects', projectId, 'with-tasks'],
  queryFn: async () => {
    const p = await api.getProject(projectId);
    return { ...p, tasks: await api.listTasks(projectId) };
  },
  enabled: Boolean(projectId),
});

Entities versus lists

Model the cache as entities and lists separately, the way a database does. The detail query holds the entity; list queries hold ids (or rows) that reference it. Updating one entity then patches every list that mentions it — a rename changes ['invoices','detail',42] and each list entry with a matching id — instead of invalidating and refetching everything, which is correct but costs a round trip per keystroke of a rename. Invalidation is the reliable default; targeted patches are the optimisation you apply to the hot paths the profiler identifies, with the invariant that a patch must produce exactly the data a refetch would have.

Keep functions and dates out of keys. Keys are serialised for persistence, dedupe and structural comparison, and a Date or a closure in a key either stringifies inconsistently or fails outright — use the epoch number or the id that determined it.

Staleness, refetch and invalidation

Stale-while-revalidate is the lifecycle in one phrase: serve what is cached immediately, then refresh it in the background and swap when the new copy lands. The library expresses it as two numbers — staleTime, how old an entry may be before it is eligible for refresh, and gcTime, how long an unused entry survives in memory — plus a set of triggers (mount, window focus, reconnect, interval) that act only on entries already past staleTime. The defaults are deliberately conservative (stale immediately, refetch often), which is right for a dashboard and wrong for a catalogue: every screen you open refetches what you just navigated away from, and a mobile connection pays for your caution.

Choosing values is a per-resource decision, not a global one, and the question is always "how wrong is a stale copy, and for how long". A user's permissions: staleTime measured in minutes at least, because a wrong-but-fresh copy is worse than an old one the server would correct. An exchange rate: seconds. A published document's body: long, with explicit invalidation on edit, because background swaps under a reader's cursor are a trust violation. The refetch triggers then follow the same logic — refetch-on-focus suits interactive desktop tools and is noise in an embedded kiosk. Configure per query key family, using the defaults as the base and overriding where the staleness question has a different answer.

// staleness declared per resource, from the cost of being wrong
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,          // base: 30s of trusted freshness
      gcTime: 5 * 60_000,         // keep inactive entries 5 minutes
      refetchOnWindowFocus: true, // base: desktop-tool behaviour
      retry: 2,                    // transient network errors: retry twice
    },
  },
});

// permissions: a stale-but-fresh copy is WORSE than an old one the server
// would correct - refetch early, and invalidate on role changes
queryClient.invalidateQueries({ queryKey: ['me', 'permissions'] });

// published documents: background swaps under a reader are a trust
// violation - serve from cache, refresh only on explicit navigation
useQuery({
  queryKey: ['docs', docId],
  queryFn: () => api.getDoc(docId),
  staleTime: 10 * 60_000,
  refetchOnMount: 'never',
  refetchOnWindowFocus: false,
});

// embedded kiosk / TV wall: never refetch on focus, it is not a user signal
useQuery({ queryKey: ['wall'], queryFn: api.getStatus,
           refetchOnWindowFocus: false, refetchInterval: 60_000 });

Invalidation is the load-bearing operation and the one most often avoided for the wrong reason — it refetches, and refetching costs. But invalidation is also the only operation that cannot be wrong: it does not compute what changed, it asks the server what is true. Everything else — optimistic patches, targeted updates, key surgery — is an optimisation layered on top, valid only while it agrees with what a refetch would return. The discipline is therefore: invalidate by default so the data is honest, patch on the paths where the round trip is visible to the user, and keep a manual "invalidate everything" escape hatch for the mutations whose blast radius you cannot enumerate (imports, migrations, permission changes).

// invalidation by default, patching where the user would notice the wait
async function useArchiveInvoice() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id) => api.archiveInvoice(id),

    // 1. optimistic: the row disappears NOW, the server confirms after
    onMutate: async (id) => {
      await qc.cancelQueries({ queryKey: invoiceKeys.all() });
      const previous = qc.getQueriesData({ queryKey: invoiceKeys.lists() });
      qc.setQueriesData({ queryKey: invoiceKeys.lists() }, (old) =>
        Array.isArray(old) ? old.filter((r) => r.id !== id) : old);
      return { previous };                 // the rollback receipt
    },

    // 2. failure: put the world back exactly as it was
    onError: (_err, _id, ctx) => {
      ctx?.previous.forEach(([key, data]) => qc.setQueryData(key, data));
    },

    // 3. success: ask the server what is actually true
    onSettled: () => qc.invalidateQueries({ queryKey: invoiceKeys.all() }),
  });
}

The wrong reasons to skip invalidation

Two excuses surface in review constantly. "The mutation returned the new record, so I'll just write it in" — fine, so long as the write covers every cache entry that mentions it: the detail query, each list containing the row, any aggregate the row participates in. Miss one and a screen shows the old value until a refetch, with no error anywhere. And "invalidating refetches visible queries immediately, which flashes the UI" — that is a rendering problem, not an invalidation one: keep the previous data while refetching (the default), so refetch is invisible unless the data actually changed. The fix belongs in how refetches render, not in whether the truth is re-asked for.

Never call invalidateQueries with a key that does not exist because of a typo — prefix matching means a wrong-but-similar key invalidates the wrong family while the intended one stays stale and silently wrong. Use the key factories from the previous section: a typo in invoiceKeys.lists() is a compile error, a typo in a string literal is a production incident.

Mutations, rollbacks and retries

A mutation is a write plus its cache aftermath, and the aftermath is the part that needs design. The lifecycle hooks each have one job: onMutate captures the world before the write (cancel in-flight queries so they do not overwrite your optimistic state, snapshot the affected entries), onError restores the snapshot, onSuccess writes what the server returned if it is authoritative, and onSettled invalidates regardless of outcome, because even a failed write may have partially applied or raced with another client. Writing all four as one unit — optimistic, snapshot, rollback, reconcile — is the difference between an interface that never lies and one that occasionally strands the user in a state the server does not have.

Retries need their own policy because mutations are not idempotent by default. Retrying a GET is free; retrying a POST that already created a record doubles it, and retrying a payment charges twice. The safe pattern is idempotency keys — a client-generated key the server deduplicates on — combined with a retry policy that only retries the errors that are genuinely transient: network failures and 5xx on a request the server confirmed is safe to repeat. Timeouts are the nastiest class: the write may have succeeded, the client just does not know, so the retry must be keyed or the query must be refetched to learn the outcome rather than assumed.

// idempotency keys: safe to retry when the outcome is unknown
async function createInvoice(payload) {
  const idempotencyKey = crypto.randomUUID();     // one per user intent
  return api.post('/invoices', payload, {
    headers: { 'Idempotency-Key': idempotencyKey },
  });
}

// retry policy: only transient failures, never on unknown-outcome writes
const mutation = useMutation({
  mutationFn: (draft) => api.saveInvoice(draft),
  retry: (failureCount, error) => {
    if (error instanceof TimeoutError) return false;   // outcome unknown -
    return failureCount < 1;                            // REFETCH to learn it
  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: invoiceKeys.all() }),
});

// the unknown-outcome case: ask the server what happened instead of guessing
async function saveWithRecovery(draft) {
  try {
    return await api.saveInvoice(draft);
  } catch (err) {
    if (err instanceof TimeoutError) {
      const current = await api.getInvoice(draft.id);   // did it land?
      if (current && current.updatedAt >= draft.baseVersion) return current;
      throw err;                                        // truly not applied
    }
    throw err;
  }
}

Concurrent writers — two tabs, two users — are where mutation design stops being theoretical. Last-write-wins is a policy, and sometimes the right one, but it must be chosen: version fields or If-Match etags turn a silent overwrite into a 409 the mutation surfaces as a message ("this invoice was changed by Amina — reload") alongside an invalidation that brings both clients to the truth. The optimistic layer matters here too: an optimistic update that shows the user their write succeeded, followed by a conflict error, must roll back visibly and explain. Silent reconciliation — the UI briefly showing a save that never happened — is the failure mode that erodes trust in an application more than any crash.

// conflict handling as a first-class mutation outcome
async function saveInvoice(draft) {
  try {
    return await api.put('/invoices/' + draft.id, draft, {
      headers: { 'If-Match': draft.etag },
    });
  } catch (err) {
    if (err.status === 409) {
      // NOT a retry: the other writer's value is now the truth.
      // surface it, refresh, let the user re-apply their edit deliberately.
      throw new ConflictError('Changed by ' + err.body.changedBy, err.body);
    }
    throw err;
  }
}

// in the mutation: the conflict is data, not an exception to swallow
onError: (err) => {
  if (err instanceof ConflictError) {
    toast.error(err.message);
    queryClient.invalidateQueries({ queryKey: invoiceKeys.detail(err.body.id) });
    return;                       // snapshot rollback already ran above
  }
  toast.error('Save failed - your edits are kept, retry when ready');
}

Queues, offline and the mutation cache

Applications with unreliable connections take the design one step further: mutations queue while offline, replay in order on reconnect, and each queued entry carries the same optimistic-snapshot-rollback machinery. The ordering matters — replaying "archive" before "create" against a server that does not know the row exists fails permanently, so the queue must serialise per entity. And every queued mutation needs its conflict path wired before it ships, because the moment writes can be replayed hours later, a 409 stops being an edge case and becomes a scheduled event. If your application queues writes, budget the conflict UX explicitly; do not discover it in support tickets.

Keep mutation side effects out of components. A mutation that both archives and emails belongs in one function with one rollback story, not in two components each invalidating half the cache — the cache's consistency follows the mutation's atomicity, and a split mutation guarantees a split cache.

Writing queries that components can trust

A query's contract with its consumers is stronger than a promise's: components assume that data, once present, is the current truth and will not vanish under them. Two library features make that assumable. Structural sharing means a refetch that returns equal data gives back the same object reference, so useMemo downstream keeps hitting and re-renders do not cascade for data that did not change. And keeping previous data during refetch means the data field never flickers to undefined on a background update — a refetch that changes nothing is invisible, and one that changes something swaps in a single commit. Design your components on those two guarantees: read data directly, do not defensively clone, and treat a disappearing data as a bug report about how the query is configured.

The loading states deserve the same precision, because "is loading" is three different questions at three different moments: is there no data yet (show the boundary fallback from chapter 14), is there data being refreshed (show nothing, or a subtle status), or is this query waiting for a dependency (render as if empty, quietly). Query libraries surface these as isPending, isFetching and fetchStatus; collapsing them into one boolean is what produces interfaces that flash skeletons on every navigation. Select the state that matches what the user should experience at that moment — and remember the boundary placement rule: only the first of the three deserves a fallback.

// three questions, three states, three UI decisions
function InvoicesPage() {
  const query = useQuery({
    queryKey: invoiceKeys.list({ status: 'open' }),
    queryFn: () => api.listInvoices({ status: 'open' }),
  });

  // 1. no data ever: the region is genuinely unavailable -> Suspense/fallback
  if (query.isPending) return <TableSkeleton rows={6} />;

  // 2. background refresh: data EXISTS -> keep it, mark the region quietly
  return (
    <section aria-busy={query.isFetching}>
      {query.isFetching && <span role="status">Updating…</span>}
      <InvoiceTable rows={query.data} />
      {query.error && <ErrorPanel onRetry={query.refetch} />}
    </section>
  );
}

// WRONG: one boolean for three states -> skeleton on every navigation

The error state completes the contract, and the rule from chapter 18 applies: an error in a background refetch should not unmount content the user is reading. Show the failure alongside the last good data with a retry affordance, because the stale copy is still the best answer the client has, and it is what the user was looking at a second ago. Reserve the full-region error fallback for the first load, where there is no data to preserve — that is also exactly the boundary placement distinction from chapter 14, arriving from the data side rather than the rendering side.

// errors as a spectrum: first load fails loudly, refresh fails quietly
function InvoiceDetail({ id }) {
  const query = useQuery({ queryKey: invoiceKeys.detail(id),

  if (query.isPending) return <DetailSkeleton />;

Selecting, transforming and keeping identity

When a component needs a derivative of query data — a sorted copy, a joined entity, a formatted total — derive it in the component with useMemo over query.data, or select it in the query so the transform runs inside the cache layer and its output participates in structural sharing. What you must not do is transform in an effect and store the result in state: that reintroduces the second-truth problem this chapter removed, complete with its own loading flags and stale closures. The cache holds the raw record; every view-specific shape is a pure function of it, computed where it is read.

// derived in render over stable cache identity - no effect, no second truth
function InvoiceTotal({ id }) {
  const { data: invoice } = useQuery({ queryKey: invoiceKeys.detail(id),
                                       queryFn: () => api.getInvoice(id) });
  const total = useMemo(
    () => invoice.lines.reduce((sum, l) => sum + l.amountCents, 0) / 100,
    [invoice]
  );
  return <Money value={total} currency={invoice.currency} />;
}

// or select at the query layer, so the transform is cached and shared:
const { data: total } = useQuery({
  queryKey: invoiceKeys.detail(id),
  queryFn: () => api.getInvoice(id),
  select: (inv) => inv.lines.reduce((s, l) => s + l.amountCents, 0) / 100,
});
// structural sharing makes the select output stable across unchanged
// refetches - downstream memoisation keeps hitting.

Treat the query cache as the application's read model and mutations as its write path. When a bug appears — a screen out of date, two views disagreeing — the question is never "which component's state is wrong" but "which key was not invalidated or which patch disagrees with a refetch". One owner means one place to look, and that is the entire payoff of chapter 10's decision table.

The URL is application state that the user owns: they can copy it, bookmark it, send it to a colleague, and press back. A router is the component that takes that ownership seriously — turning a string into a render plan, a render plan into data loads, and every in-app decision about "which screen am I on" back into the string. Chapter 10's decision table ends the argument: the value is the URL, the router owns it.

The router owns the URL

The principle in one sentence: no component writes to window.location, keeps a "current page" variable in state, or decides which screen to show on its own. There is exactly one writer — the router, through navigation calls — and exactly one reader of record — the URL, resolved back through the router's route table. Everything else is downstream. When a modal, a tab, a selected row or a filter becomes part of "which screen am I on", it moves into the URL as a parameter, and the router becomes the thing that serialises it. The payoff is that every state the user would want to share now survives a paste into chat, and every back button press does what the label promises.

The failure mode this prevents has a familiar shape: a component holds const [page, setPage] = useState(1), the user filters, clicks into a detail view, presses back, and the list resets to page 1 with cleared filters — because the state lived in a component that unmounted, while the URL, which did survive, said nothing about it. The fix is not a persistence layer for the state; it is recognising that this state was URL-shaped all along. The test for whether something belongs in the URL: would the user be surprised if a bookmark of this screen did not reproduce it? If no, it belongs in the URL. If yes — a half-written draft, a dismissed tooltip — it belongs in component or server-adjacent state.

// WRONG: two sources of truth - the URL says "/", the state says page 3
function Products() {
  const [page, setPage] = useState(1);
  const [category, setCategory] = useState('all');
  // back button: component remounts, state resets, URL unchanged
  // share link: recipient sees page 1, category "all"
  return <ProductList page={page} category={category} />;
}

// RIGHT: the router owns it - navigation IS the state update
import { useSearchParams } from 'react-router';

function Products() {
  const [params, setParams] = useSearchParams();
  const page = Number(params.get('page')) || 1;
  const category = params.get('category') || 'all';

  function go(next) {
    // replace for filter changes (no history spam), push for page turns
    const opts = { replace: next.page === page };
    setParams(toParams(next), opts);
  }
  return <ProductList page={page} category={category} onChange={go} />;
}
// share: ?page=3&category=tools reproduces the screen exactly
// back: the router restores the previous params from history

Draw the line deliberately, because the opposite mistake is real too: stuffing volatile, private state into the URL produces unreadable addresses that leak intent and defeat history. A filter the user set once in a session, a selection that follows the last click, a local sort order — these are legitimately ephemeral. The distinction to hold is reproducible screen identity versus session working state. Screens are URLs; the way you happened to be looking at one is state that may or may not be worth encoding — encode it when sharing it would be useful, leave it out when the parameter would only add noise.

// parse defensively: the URL is user-editable input, not your setter
function useListParams() {
  const [params, setParams] = useSearchParams();
  const page = Math.max(1, Number(params.get('page')) || 1);
  const sort = ['name', 'created', 'status'].includes(params.get('sort'))
    ? params.get('sort')
    : 'name';                       // whitelist beats blacklist for enums
  return { page, sort,
    set: (patch, opts) => setParams(mergeParams(params, patch), opts) };
}

The URL is user input

Every parameter arrives potentially mangled: hand-typed, truncated by a chat client, crafted. Parse into a validated shape at the boundary — numbers coerced and clamped, enums whitelisted, unknown keys dropped — so the components below receive a domain object, never the raw strings. A component that renders params.get('id') directly into a query call turns a typo into an API request; a boundary parser turns it into a redirect to the sane default. The boundary is also where encoding decisions live, so the rest of the application never sees percent-encoding at all.

Never build a URL by string concatenation — '/search?q=' + query breaks on the first ampersand or hash the user types. URLSearchParams and the router's own param helpers encode correctly by construction, and string building is the one place that is not true, which is exactly the place a future change will forget.

Route structure and nesting

Route structure is information architecture expressed as a tree, and the tree should mirror how the product is actually organised: a layout that owns the chrome (nav, sidebar, breadcrumbs), children that own the regions inside it. Nested routes give that structure real mechanics — the layout route stays mounted while children change, so its state and scroll survive navigation, and each child route renders into the parent's outlet rather than remounting the whole page. The corollary that takes teams a while to learn: a route boundary is a remount boundary. State inside a route that unmounts on navigation is gone, which is correct for screen-scoped state and infuriating for state that should have been in the URL or the cache (chapters 15 and 16 respectively).

Flat route tables age badly: twenty sibling routes each repeating the same layout wrapper, guards and loaders, with the relationship between a list and its detail view existing only as a string convention. Nesting makes the relationship structural — the detail route is inside the list route, so the parent can render the list with the selected row highlighted while the child fills the detail pane, both sharing one data load. This is the path-to-layout correspondence worth defending in review: if two screens share chrome, they share a layout route; if one screen has regions that load independently, those regions are child routes, not tabs built from local state.

// route tree mirrors the product's structure
const routes = [

Search params as component state

Search params are where most URL-as-state adoption actually happens, because they are the parameters that change while the user works: filters, sort, page, view mode, a query string, a selected tab. Treat them as the component's state API — read with a hook, written through a setter that knows whether a change deserves a history entry. The distinction between replace and push is the whole of good param UX: typing a search term should replace the history entry (nobody wants fourteen back presses to undo one keystroke), while changing page or opening a record should push (that is a place the user went). A router that defaults to push everywhere produces a back button users learn to avoid; defaulting to replace everywhere produces one that does nothing. Choose per interaction.

The second design question is granularity: one blob parameter versus many. Many small parameters (?q=…&status=…&sort=…) compose — any subset can be shared, a partner team can link to one filter, the URL reads as configuration. One encoded blob (?f=eyJzdGF0dXMiOiJvcGVuIn0=) does not, and it also breaks the moment a user or a mail client mangles it. Keep parameters flat, primitive and named after the user's vocabulary. The one case for encoding is genuinely structured state — a multi-field advanced filter — and even then prefer an editable serialisation (JSON-ish or delimited) over base64, so that a support engineer reading a bug report can see what the URL asked for.

// param updates as the component's state API, with history intent
function useFilterParams() {
  const [params, setParams] = useSearchParams();

  // typing: replace - one history entry for the whole search session
  const setQuery = (q) => setParams(withParam(params, 'q', q), { replace: true });

  // paging: push - going to page 2 is a place the user went
  const setPage = (p) => setParams(withParam(params, 'page', p));

  // opening a filter drawer: replace on commit, not on every toggle
  const setFilters = (f, open) =>
    setParams(withParams(params, encodeFilters(f), { drawer: open ? '1' : null }));

  return {
    q: params.get('q') || '',
    page: Number(params.get('page')) || 1,
    status: params.get('status') || 'all',
    setQuery, setPage, setFilters,
  };
}

// the component consumes plain values - the hook owns serialisation
function OrdersPage() {
  const { q, page, setQuery, setPage } = useFilterParams();
  return <OrderTable query={q} page={page} onQuery={setQuery} onPage={setPage} />;
}

Centralising param handling in one hook per screen is what keeps the serialisation rules in one place: defaults applied in one direction, coercion in the other, history intent declared beside each field. Without it, every component that touches useSearchParams re-implements defaulting and push-versus-replace, and the screen ends up with three fields that push and one that silently replaces, producing an inconsistent back button — an inconsistency no test catches because each call site is locally reasonable. The hook is also where you put the invariant that the params and the UI never disagree: if the component renders from the params and only the params, there is nothing else to sync.

Debouncing and navigation churn

A param that changes per keystroke interacts with everything reading the URL: the query cache keys on it (chapter 15 — fine, that is the point), the router writes history (handled by replace), and any effect watching location re-runs. The remaining question is request volume, and the answer is not to stop writing the URL — it is to let the URL be immediate and the network be patient. The param updates at once, so share and back are always correct; the fetch debounces on top of the param, so the network sees the settled value. Keeping the network fast and the URL honest are separate concerns, and conflating them is how debounces end up hiding state the user cannot see.

// URL immediate, network patient: two clocks, deliberately separated
function SearchBox() {
  const [params, setParams] = useSearchParams();
  const q = params.get('q') || '';

  // the URL updates on every keystroke - history-safe via replace
  function handleChange(next) {
    setParams(withParam(params, 'q', next), { replace: true });
  }

  return <input value={q} onChange={(e) => handleChange(e.target.value)} />;
}

Do not debounce the navigation itself. A navigation guard that waits 300 ms before committing the URL breaks deep links typed into the address bar and makes the back button feel broken. Debounce the expensive follower — the fetch, the autosave — never the state the user believes they already changed.

Loading data with the router

Once routing is the source of screen identity, it is also the natural place to declare what each screen needs: loaders that run before (or alongside) the route rendering, actions that handle its mutations, and an error element per route. The advantage over component-initiated fetching is sequencing — the router can start every loader for the matched branch in parallel, show the navigation's pending state coherently, and let the route render with its data already in hand, which removes the cascade of per-component effects each discovering they needed something. It also unifies failure: a loader that throws lands in the route's error element, giving each screen a recovery UI without wrapping every component in its own boundary.

The composability point is what makes loaders scale: nested routes load nested data in parallel along the matched branch, so /projects/:id/tasks runs the layout's shell loader and the tasks loader together rather than in sequence. The design rule for what goes where mirrors chapter 15's ownership: the layout loader fetches what the branch shares (the project record), a leaf loader fetches what only it shows (the task page), and anything several screens read goes through the cache library keyed identically, so a loader and a component asking for the same record get the same entry. Loaders and cache are not rivals — a loader is one more reader of the key, with the router deciding when it runs.

// loaders along the matched branch, in parallel, keyed into the same cache
const routes = [
  { path: '/projects/:projectId',
    element: <ProjectsLayout />,
    loader: ({ params }) => queryClient.ensureQueryData({
      queryKey: ['projects', params.projectId],
      queryFn: () => api.getProject(params.projectId),
    }),
    children: [
      { path: 'tasks',
        element: <TaskBoard />,
        // sibling-level data: starts WITH the layout loader, not after it
        loader: ({ params }) => queryClient.ensureQueryData({
          queryKey: ['projects', params.projectId, 'tasks'],
          queryFn: () => api.listTasks(params.projectId),
        }),
        errorElement: <TaskLoadError />,   // failure lands HERE, not at root
      },

  },

Two timing patterns to be able to choose between. Blocking loaders hold navigation until data is ready — the outgoing screen stays visible (a transition, per chapter 14) and the new route appears complete; right for screens that are meaningless without their data, wrong when a slow endpoint would make the whole app feel stuck. Non-blocking loaders let the route render immediately and suspend its regions behind Suspense boundaries — right when the shell of the next screen is itself useful, wrong when an empty table flashes before rows arrive. The default to prefer is blocking for the branch's primary data and Suspense for secondary panels within it: navigation feels atomic, and the panels that genuinely arrive later do.

Loaders versus effects: the honest comparison

A component fetching in an effect still works, and for data that exists only while the component is mounted — a typeahead's suggestions, a websocket subscription — it remains correct. The difference appears on navigation: effect fetching begins after the component mounts, renders empty first, and cannot be cancelled by the route change that superseded it, so a fast navigation sequence leaves responses landing out of order. The loader runs as part of navigation, can be aborted when a newer navigation wins, and renders with data present. The rule is ownership again: route-scoped data is declared with the route, component-scoped data lives with the component, and both write into the same cache keyed the same way.

Route errors and render errors are different channels. A loader that throws goes to the nearest errorElement; a component that throws during render goes to the nearest React error boundary (chapter 18). A screen that has both — recovery for load failure, a boundary for render failure — covers the two ways "show this page" fails, and neither substitutes for the other.

Navigation, guards and scroll

Navigation is more than swapping the URL: a real navigation has a pending state, an origin, and a place to land. Use the router's link element rather than an anchor with a click handler for in-app destinations, because it preserves middle-click, ctrl-click, copy-link and right-click — the browser affordances that make a URL feel like a URL — while still participating in client-side transition. Programmatic navigation is for outcomes, not for clicks: after a mutation that renames a record, navigate to the new canonical URL with replace (the old URL no longer resolves, and pushing would put a dead entry in history). The test: if a human clicks it, it should be a link; if the program decides, it is a navigate call.

Guards are where routing meets permissions, and the shape that ages well separates three questions: is the user authenticated (route-level, before load), is this user allowed this record (loader-level, where the 403 arrives with the data request), and is this view permitted by feature flags (render-level, where the flag is read). Collapsing them into one component that checks everything on mount produces the flicker pattern — protected content renders, the check fails, it disappears — and pushes the redirect into an effect that races with the data load. Redirecting in the loader, before the route commits, makes "not allowed" a navigation result the user perceives as one step, not a flash of content.

// guards at the layer that knows: loader-level auth, link-level affordance
function requireSession({ request }) {
  const session = getSession(request);
  if (!session) throw redirect('/login?next=' + encodeURIComponent(new URL(request.url).pathname));
  return session;
}

const routes = [
  { path: '/login', element: <Login /> },
  { path: '/admin',
    loader: requireSession,                 // redirects BEFORE the route renders
    element: <AdminLayout />,
    children: [
      { path: 'users',

];

  isActive ? 'row row--current' : 'row'}>{order.number}</NavLink>

Scroll restoration is the last piece of URL ownership, and it is genuinely part of routing rather than a DOM chore: pressing back should return the user to where they were in the list they left, not to the top of a page they scrolled past twenty rows ago. Routers implement it as position memory keyed per history entry — restore on pop, reset to top on push — with one escape hatch teams always need: a screen where "top" is correct after a filter change even though the entry was pushed. Declare that per route rather than patching it in an effect, because the moment scroll behaviour is computed from component state it disagrees with history entries the component never saw.

    handle: { scrollRestoration: 'position' },

  },

Navigation as an announced event

Client-side navigation is silent by default: no page load, no focus move, no announcement — a screen-reader user activates a link and hears nothing happen, a keyboard user's focus stays on an element that may no longer exist. The fix is small and belongs with routing: after each navigation, move focus to the new screen's main heading and announce the destination through a polite live region. Combined with scroll restoration and pending states, this is what makes a single-page application behave like the document-based web its users already know: focus follows the destination, history means what it says, and the URL is always the thing you could have typed.

// the navigation checklist, as one announcer component
function RouteAnnouncer() {
  const location = useLocation();

    const title = document.querySelector('#content h1')?.textContent || 'Page';

    <div role="status" aria-live="polite"
         style={{ position: 'absolute', width: 1, height: 1, overflow: 'hidden' }}>

    </div>
  );
}

Forms are where React's declarative model meets the browser's oldest, most behaviour-heavy API — native validation, autofill, Enter-to-submit, file inputs — and the design question underneath every other is who owns the field's value. Get that right and validation, submission and error display become data problems; get it wrong and every form in the application accumulates its own collection of state and effects.

Controlled, uncontrolled and when

Two ways to own a value, with a real trade rather than a legacy and a modern. A controlled input's value lives in React state and the DOM mirrors it — every keystroke flows through a change handler and back down. An uncontrolled input's value lives in the DOM and React reads it on demand, via a ref or the FormData handed to a submit handler. Controlled wins when React must react while the user types: enabling a submit button, formatting as they go, showing inline availability, filtering a list above the field. Uncontrolled wins when the form's value matters only at submission — which is most forms — because it removes a state variable and a re-render per keystroke per field, and it gets browser behaviours for free: autofill, spellcheck restoration, and Enter-to-submit that does not depend on your handler wiring.

The pattern that combines both honestly is uncontrolled by default with controlled islands: the form submits through native FormData, and only the fields that need live reactivity get state. This inverts the reflex many teams build — a state variable per field, a handler per field, a controlled input everywhere — which produces forms that re-render the whole subtree on every keystroke of any field and whose submit handler re-reads state that the DOM already holds. The tell that you have over-controlled is a change handler whose body is setState and nothing else on a field nothing else reads.

// uncontrolled form: the DOM owns values until submit
function CreateInvoice() {
  function handleSubmit(formData) {
    // FormData reads the DOM - no state, no per-keystroke render
    const payload = {
      customer: String(formData.get('customer') || ''),
      amountCents: Math.round(Number(formData.get('amount')) * 100),
      due: String(formData.get('due') || ''),
    };
    api.createInvoice(payload);
  }
  return (
    <form action={handleSubmit}>
      <input name="customer" required />
      <input name="amount" type="number" step="0.01" required />
      <input name="due" type="date" required />
      <button type="submit">Create</button>
    </form>
  );
}

// controlled only where React must REACT while typing
function SearchField({ onQuery }) {
  const [q, setQ] = useState('');          // justified: results depend on it
  return (
    <>

Controlled inputs also impose a contract that catches teams out: a controlled input with no change handler is a field the user cannot type in, because React overwrites the DOM after every keystroke with the state that did not move. And when state and DOM disagree — a masked phone formatter that rejects the character the user typed — the cursor jumps to the end, because the browser re-rendered the value wholesale. Both failures are the same root: for a controlled input, React state is the value, and the DOM is display. Accept that for the fields where you need the reaction, and leave the rest uncontrolled.

  return <input value={v} />;
}

Defaults, resets and dirty tracking

Uncontrolled inputs take their initial value from defaultValue — and the moment a server response arrives after mount, the pattern changes: either set a key on the inputs to remount them with the loaded values (the simple, correct move), or read them at submit and let the loader's data sit in a ref. Dirty tracking, similarly, is native rather than React's problem: form elements expose elements and the browser tracks changes — or use a tiny ref-set of initial values compared at submit. Reaching for state to answer "did this change since load" is the sign you are re-implementing form.dirty by hand, with a re-render per keystroke as the price.

// server data arrives late: remount the fields with the new defaults
function EditProfileForm({ profilePromise }) {
  const profile = use(profilePromise);
  return (
    // key change -> inputs remount with fresh defaultValue
    <EditForm key={profile.id} profile={profile} />
  );
}

function EditForm({ profile }) {
  return (
    <form action={saveProfile}>
      <input type="hidden" name="id" value={profile.id} />
      {/* uncontrolled: defaultValue set once at mount, DOM owns it after */}
      <input name="name" defaultValue={profile.name} />
      <input name="email" defaultValue={profile.email} />
      <button type="submit">Save</button>
    </form>
  );
}

Choosing key remount over syncing state is not a shortcut — it is the honest expression of "these fields now describe a different record". State syncing keeps stale cursors and half-typed edits alive across an identity change; remounting makes the identity change mean what it says.

Validation as data, not as panic

Validation answers two different questions at two different times, and conflating them is the source of hostile form UX. During typing, the goal is guidance: format hints, availability, "must be at least 8 characters" — non-blocking, announced politely, never preventing the user from continuing to type. At submit, the goal is rejection: every rule the server enforces, evaluated in one pass, producing a complete map of what is wrong so the user fixes everything at once and resubmits once. Reactive per-keystroke rejection — an error appearing the instant a field is half-filled — optimises for the validator's correctness and against the user, who has not finished the thought.

The structural rule that keeps validation honest: the server is the enforcement point and the client is the courtesy. Every rule runs on the server in the submit action, because the client copy is advisory by definition — it can be bypassed with devtools, skipped by an autofilled payload, or simply stale after a rules change. The client copy exists to save a round trip and to give immediate guidance, and it must be derived from one shared rule description rather than a second, drifting implementation: a schema (Zod, Valibot, your own plain functions) imported by both the client validator and the server action is one source, two call sites, zero drift.

// one schema, two call sites: client courtesy, server enforcement
const signupSchema = {
  email: (v) => (!/^[^@]+@[^@]+\.[^@]+$/.test(v) ? 'Enter a valid email' : null),
  password: (v) => (v.length < 8 ? 'At least 8 characters' : null),
  plan: (v) => (['free', 'team'].includes(v) ? null : 'Choose a plan'),
};

// client: the same functions, run at submit for immediate guidance
function validateSignup(values) {
  return Object.fromEntries(
    Object.entries(signupSchema)
      .map(([field, rule]) => [field, rule(String(values[field] || ''))])
      .filter(([, err]) => err)
  );
}

// server action: the enforcement point - runs regardless of the above
async function signupAction(prev, formData) {
  const values = Object.fromEntries(formData.entries());
  const errors = validateSignup(values);
  if (Object.keys(errors).length) return { errors, values };   // as data
  // ...create the account; a rule the client missed is caught HERE
}

Error display follows the two modes. Inline guidance renders beside its field, tied with aria-describedby so assistive tech reads it when focus lands; submit errors render as a summary at the top with links to each field, because after a failed submit the user's next action is to fix, and a summary turns seven trips into one. The pattern worth copying from server-rendered forms is the error summary's focus behaviour: move focus to the summary on failed submit, so the keyboard and screen-reader user is put exactly where the work is rather than left at the button they just pressed.

// submit errors as a focused summary with links to each field
function ErrorSummary({ errors, idFor }) {
  const ref = useRef(null);
  useEffect(() => { ref.current?.focus(); }, [errors]);   // on failed submit
  if (!errors || !Object.keys(errors).length) return null;

  return (
    <div role="alert" tabIndex={-1} ref={ref} className="error-summary">
      <h2>Fix {Object.keys(errors).length} problems before submitting</h2>
      <ul>
        {Object.entries(errors).map(([field, msg]) => (
          <li key={field}>
            <a href={'#' + idFor(field)} onClick={(e) => {
              e.preventDefault();
              document.getElementById(idFor(field))?.focus();
            }}>{msg}</a>
          </li>
        ))}
      </ul>
    </div>
  );
}

When to validate: blur, change, or submit

A per-field policy beats a global one: validate on blur for format rules (the user has left the field, the hint is no longer interrupting), on submit for cross-field and business rules (they need the whole form), and on change only for cheap, purely-local constraints where the feedback is the input itself — a character counter, a confirm-password match. What all three share is that a rule, once it has failed at submit, re-validates on the next change of that field: a user correcting an error expects the red to clear as they type, not on the following submit. That single re-check is the difference between a form that feels responsive after failure and one that feels stuck.

// per-field timing: blur guides, submit judges, change re-checks failures
function useFieldValidation(name, rule, formState) {
  const [touched, setTouched] = useState(false);
  const failedAtSubmit = Boolean(formState.errors?.[name]);
  const error = touched || failedAtSubmit ? rule(value) : null;

  return {
    'aria-invalid': error ? true : undefined,
    'aria-describedby': error ? name + '-error' : undefined,
    onBlur: () => setTouched(true),
    error,
  };
}

// cross-field rules run once, at submit, against the whole form
function validateAll(values) {
  const errors = {};
  if (values.password !== values.confirm) errors.confirm = 'Passwords must match';
  if (values.startDate > values.endDate) errors.endDate = 'Ends before it starts';
  return errors;                       // complete map: one resubmit, not seven
}

Never clear a field's error only on submit. A user who is told "passwords must match" and watches the red stay while they fix the confirm field has been given a form that appears not to notice them — the correction loop must close on the next keystroke of the offending field, or the guidance reads as a verdict.

Submit flows with useActionState

Chapter 13 introduced actions; this section is about what a production submit flow needs around them. The shape: the action validates first (server rules, as data), then mutates, then returns a state that carries either field errors or a success marker — and the component renders exactly those two outcomes. The pending flag drives the button, and because the action runs as a transition, the rest of the form stays interactive during submission: the user can fix a typo in another field while the first attempt is in flight. What disappears is the entire isLoading choreography — no useState for submission, no effect watching a flag, no manual reset-on-success: the hook's returned state is the flow.

Two behaviours worth designing explicitly, because the default experience omits them. Double submission: the pending flag disables the button, but Enter in a text field can still fire — make the action itself idempotent per submission (a token generated once per form mount, passed through FormData) rather than relying on UI state to serialise network calls. And success versus reset: a create-form that returns a success state should clear the uncontrolled inputs on the next render — either remount the form with a key or, better for a create-then-continue flow, keep the values and show the success inline, because silently wiping a form the user is still adding to is worse than leaving it filled.

// a production submit flow: idempotent action, errors as data, one state
async function createTicket(prevState, formData) {
  const submitToken = String(formData.get('token') || '');
  const title = String(formData.get('title') || '').trim();

  if (title.length < 5) {
    return { errors: { title: 'Give it a real title (5+ characters)' },
             values: Object.fromEntries(formData.entries()) };
  }
  try {
    const ticket = await api.createTicket({ title, submitToken });  // dedupes
    return { ok: true, ticketId: ticket.id };
  } catch (err) {
    return { errors: { form: err.message || 'Could not create the ticket' },
             values: Object.fromEntries(formData.entries()) };
  }
}

The action's returned state should be shaped for rendering, not for transport: field errors keyed by field, the submitted values so the form can re-render filled after a failure, and a discriminated outcome (ok versus errors) the component switches on. What does not belong is transport detail — status codes, response objects, error instances the client would have to interpret. Keep the boundary thin: the action translates the world into renderable state, and the component never learns how the network works. This is also what makes the same action usable from a server submission without JavaScript, since the state shape is already the first response's content.

// state shaped for rendering, not for transport
async function saveSettings(prev, formData) {

Dependent fields and complex forms

Real forms exceed the flat name-value model: fields that appear based on other fields, arrays of rows, groups that validate together, and inputs whose valid values depend on a server-known set. The design axis for all of them is where the shape of the form comes from. If the shape is static, uncontrolled + FormData carries you all the way. If the shape changes with the data — country select feeding state select, plan select revealing seat count — the shape itself becomes derived state, and the honest expression is a schema describing the form, rendered into fields, rather than a nest of conditionals scattered through JSX. A form schema turns "what fields exist" into data that validation, defaults and rendering all read from one place.

Dependent fields specifically: the dependency must flow through a single derived value, not through each field syncing with its neighbour. Country determines the state list — derive the state options from the selected country in render, keep the selected country in state (it is controlled: the second field reacts to it), and clear the state field's value when the country changes, because an inherited value from the previous country is invalid by definition. That clearing rule is the bug teams miss: without it, the form happily submits "California" with country "France", and the server rejects a form the UI showed as valid.

// dependent fields: one derivation, one clearing rule
function AddressFields() {
  const [country, setCountry] = useState('US');
  const [region, setRegion] = useState('');

  // the options are DERIVED from the controlling field, not synced to it
  const regions = REGIONS[country] || [];

  // clearing rule: a value from the previous shape is invalid by definition
  function handleCountry(next) {
    setCountry(next);
    setRegion('');                     // do NOT carry the old region forward
  }

  return (
    <fieldset>
      <label>Country
        <select value={country} onChange={(e) => handleCountry(e.target.value)}>
          {COUNTRIES.map((c) => <option key={c} value={c}>{c}</option>)}
        </select>
      </label>
      <label>State / region
        <select value={region} onChange={(e) => setRegion(e.target.value)}
                disabled={regions.length === 0}>
          {regions.map((r) => <option key={r} value={r}>{r}</option>)}
        </select>
      </label>
      {/* the submit payload reads BOTH - the server re-checks the pair */}
    </fieldset>
  );
}

Array fields — line items, attendees, phone numbers — need three operations (append, remove, reorder) each preserving each row's own field state, and the row identity question from chapter 1 reappears verbatim: rows keyed by a stable id, never by index, or removing row two reassigns every subsequent row's key and React swaps the DOM nodes instead of removing one, carrying any focused input's value into a different row's field. With uncontrolled rows the id is still required for the same reason; with controlled rows the index key produces the classic "deleting a row edits the wrong row" report. Generate the id when the row is created, keep it in the row's data, and the three operations become list transformations with no DOM surprises.

// array fields: stable row ids, not indices
function LineItems({ items, onChange }) {
  function add() {
    onChange([...items, { id: crypto.randomUUID(), desc: '', amount: '' }]);
  }
  function remove(id) {
    onChange(items.filter((r) => r.id !== id));   // keys survive: one removal
  }
  function update(id, patch) {
    onChange(items.map((r) => (r.id === id ? { ...r, ...patch } : r)));
  }

  return (
    <table>
      <tbody>
        {items.map((row) => (
          <tr key={row.id}>   {/* NEVER key={index} - deletion would shift
                                  every field's identity below this row */}
            <td><input value={row.desc}
                       onChange={(e) => update(row.id, { desc: e.target.value })} /></td>
            <td><input value={row.amount}
                       onChange={(e) => update(row.id, { amount: e.target.value })} /></td>
            <td><button type="button" onClick={() => remove(row.id)}>Remove</button></td>
          </tr>
        ))}
      </tbody>
      <tfoot><tr><td colSpan={3}>
        <button type="button" onClick={add}>Add line</button>
      </td></tr></tfoot>
    </table>
  );
}

Server-shaped option sets

When a field's options come from the server — available plans, assignable users, permitted statuses — the option set is data with its own lifecycle, and it needs its own owner. Fetch it through the cache (chapter 15) with a key, not in an effect into local state, so the select renders immediately from cached options on the next form and two forms do not disagree about what the plan list is. Guard the submitted value against the set: if the options loaded after the field was preselected, or another user's plan changed meanwhile, the value in the field may no longer exist server-side — validate membership in the action against a fresh read, because the form's option list is a cache, and caches are exactly what the server does not trust.

// server-owned options: cached, shared, re-validated at submit
function PlanSelect({ value }) {
  const { data: plans = [], isPending } = useQuery({
    queryKey: ['plans'],
    queryFn: () => api.listPlans(),
    staleTime: 5 * 60_000,            // plan lists change rarely
  });
  return (
    <select name="plan" defaultValue={value} disabled={isPending}>
      {plans.map((p) => <option key={p.id} value={p.id}>{p.name}</option>)}
    </select>
  );
}

// the action re-checks membership: the form's list is a cache, and the
// server does not trust caches
async function changePlan(prev, formData) {
  const planId = String(formData.get('plan'));
  const plans = await api.listPlans();               // authoritative
  if (!plans.some((p) => p.id === planId)) {
    return { errors: { plan: 'That plan is no longer available' } };
  }
  await api.changePlan(planId);
  return { ok: true };
}

Long forms deserve persistence beyond the session: a draft written to local storage or the server on an interval, restored on mount, cleared on successful submit. A twenty-field form that loses everything to a tab crash teaches users to write their answers in a text file first — which tells you the form, not the user, is at fault.

Errors, focus and accessibility

Every accessibility rule about forms follows from one fact: a visual user reads an error beside a field and a red border simultaneously, while a screen-reader user encounters them in DOM order, at focus time, if at all. The markup has to carry what the layout shows. Every field gets a real <label> bound by for/id — placeholder is not a label and disappears exactly when the user needs it most. Every error is tied to its field with aria-describedby and announced with role="alert" or a polite live region. Every field exposes aria-invalid while invalid. And required fields are marked with the native required attribute, which the browser's own validation, autofill and screen-reader announcements all understand — the ARIA re-implementation of a native behaviour is always the worse version.

Focus management is the part most often skipped, and it decides whether a failed submit is navigable. Move focus to the error summary; make the summary's links move focus to their fields; on a successful submission that replaces the form, move focus to the confirmation's heading. Without this, a keyboard user presses Submit, hears nothing (unless the alert is live), and must tab from the top to find what failed — while a screen-reader user may never learn the submit failed at all, because nothing received focus or announcement. Chapter 16's route announcer is the same discipline at navigation scope; forms are where it matters most often.

// the accessible field, end to end: label, description, invalid, announce
function Field({ id, label, error, hint, as = 'input', ...rest }) {
  const describedBy = [hint && id + '-hint', error && id + '-error']
    .filter(Boolean).join(' ') || undefined;
  const Input = as;

  return (
    <div className="field">
      <label htmlFor={id}>
        {label}
        {rest.required && <span aria-hidden="true"> *</span>
                          <span className="vh"> (required)</span>}
      </label>
      <Input id={id} aria-invalid={error ? true : undefined}
             aria-describedby={describedBy} {...rest} />
      {hint && <p id={id + '-hint'}>{hint}</p>}
      {error && <p id={id + '-error'} role="alert">{error}</p>}
    </div>
  );
}

Testing the contract

Because the accessibility contract is uniform — label, description, invalid, announcement — it is testable uniformly. A single test that renders a form, submits it empty, and asserts that every error is announced and every field is tied to its message catches the regression class where a developer adds a field and forgets the wiring. Pair it with the keyboard-only pass: tab through the form and submit without a mouse. If the automated assertions pass and the keyboard pass feels natural, the form is accessible in the way that matters: the contract holds for the fields you thought about and the ones you added later.

// one test for the whole accessibility contract of a form

A React application's quality is measured by what it does when things go wrong: a render throws, a request times out, a chunk fails to load, a third-party widget misbehaves. Error boundaries contain the blast radius, resilient design limits how much can go wrong at once, and a testing strategy that mirrors the risk pyramid is what proves both hold after the next change.

What an error boundary catches

An error boundary is a component that catches errors thrown anywhere below it during render, in constructors, lifecycle methods, and effects — and renders a fallback instead of letting the tree unmount to the root. It is a class component with static getDerivedStateFromError (to switch to the fallback state) and optional componentDidCatch (to log). What it does not catch is a category list worth memorising: errors in event handlers (the boundary is not listening when you click), errors in async code after the render committed (a promise rejection in a fetch), errors in setTimeout or scheduled callbacks, errors thrown during server-side rendering, and errors the boundary itself throws. Those five each need their own containment, and confusing them with render errors is how a team concludes "boundaries don't work".

The placement logic is the same as chapter 14's Suspense boundaries but with a harsher default: an error without a boundary above it unmounts the whole application — every piece of state in memory, gone, a blank page. So the root boundary is mandatory, and the useful boundaries are placed by blast radius: one around each screen (a broken screen should not take the shell with it), one around each independently-failing widget (a chart library that throws should cost you the chart), and one around anything third-party, because foreign code has no error discipline you can influence. The test for a proposed boundary: if this throws on a Monday, what should still work on screen? The answer defines the boundary's location.

import { Component } from 'react';

class ErrorBoundary extends Component {
  state = { error: null, key: 0 };

  static getDerivedStateFromError(error) {
    return { error };                 // render the fallback on the next pass
  }

  componentDidCatch(error, info) {
    // logging happens HERE - not in getDerivedStateFromError, which must
    // stay pure: it runs during the render phase
    reportError({ error, info, digest: info.componentStack });
  }

  reset = () => {
    // remount the subtree: clearing the error without a new key just
    // re-throws on the next identical render
    this.setState((s) => ({ error: null, key: s.key + 1 }));
  };

  render() {
    if (this.state.error) {
      return this.props.fallback(this.state.error, this.reset);
    }
    return <Fragment key={this.state.key}>{this.props.children}</Fragment>;
  }
}

// usage: the fallback is a function, so it can show the error and wire reset
<ErrorBoundary
  fallback={(error, reset) => <WidgetFailed error={error} onRetry={reset} />}>
  <RevenueChart />
</ErrorBoundary>

Two implementation details decide whether a boundary is useful in production. The reset must remount: clearing the error state alone re-renders the same component with the same bad props and throws again, which presents as a Retry button that does nothing — one of the most common boundary bugs. And the key subtlety of boundaries as state: the boundary remembers its error until reset, so a sibling update does not clear it, but a parent re-render passing new children re-attempts the render only after you reset. Design the interaction accordingly — Retry re-attempts (right for a transient data problem), Close hides the widget (right for a permanently broken one), and the fallback should say which case it is.

// reset that actually works, and per-case fallback copy
function WidgetBoundary({ children, label }) {
  return (
    <ErrorBoundary
      fallback={(error, reset) => (
        <div role="alert" className="widget-fallback">
          <p>{label} could not load.</p>
          {/* transient? re-attempt. persistent? the error digest says so */}
          <button onClick={reset}>Try again</button>
          <details>
            <summary>Technical detail</summary>
            <pre>{String(error.message)}</pre>
          </details>
        </div>
      )}>
      {children}
    </ErrorBoundary>
  );
}

// the classic bug: retry that clears state but not the failure
function BrokenRetry({ error, onRetry }) {
  return (
    <button onClick={() => { onRetry(); }}>   {/* parent clears error... */}

                                                   remounted: same props, same

Boundary granularity on a real screen

A dashboard assembled from six widgets wants six boundaries, each rendering its own failure state in its own slot — because the failure modes are independent (one chart library, one third-party embed, four own components) and the cost of losing a widget should be proportional to the widget. The pattern composes: each widget boundary sits inside the screen boundary, which sits inside the root. An error that escapes a widget boundary is caught at the screen level with the context intact; an error that escapes the screen is caught at the root, where the fallback can offer navigation home. Three levels is usually the whole structure — root, screen, widget — and deeper nesting buys nothing because the state below a boundary that already caught the error is gone anyway.

// three levels: root, screen, widget - each with its own fallback

      <RouterProvider router={router} />
    </ErrorBoundary>
  );
}

Fallbacks that recover, not just fail

A fallback is a user interface under the worst conditions — the user was mid-task, the data may be half-visible, and the fallback is all they have. The four questions a good fallback answers: what was I trying to do (name the feature, not the error), is anything at risk (state the fate of unsaved work), what can I do now (retry, go back, continue without it), and is this my problem (make clear the fault is the application's). The failure mode to design against is the blank screen with a stack trace: it transfers the entire burden of interpretation to a user who cannot act on any of it. The second failure mode is the opposite overcorrection — a friendly "Something went wrong" with no route forward, which is a dead end with better manners.

Recovery design starts from what the boundary protected. If it wraps a widget, the fallback keeps the rest of the screen and offers widget-scoped retry — the task is intact, only one part failed. If it wraps the screen, offer navigation to a known-good route plus retry, and state explicitly whether in-progress form data survived (it did if the form was above the boundary; it did not if the boundary unmounted it — which is exactly why long forms get their own boundary or their own draft persistence from chapter 17). If it wraps the root, the only honest options are reload and a support path with a correlation id the user can quote. Match the fallback to the blast radius, and make the copy state the actual consequence rather than a generic apology.

// fallback copy that answers the four questions, per blast radius
function WidgetFallback({ label, error, onRetry }) {
  return (
    <div role="alert" className="fallback fallback--widget">
      <p className="fallback-what">{label} failed to load.</p>
      <p className="fallback-risk">The rest of the page is unaffected.</p>
      <div className="fallback-actions">
        <button onClick={onRetry}>Try again</button>
      </div>
      <p className="fallback-ref">Reference: {error.digest || 'local'}</p>
    </div>
  );
}

function ScreenFallback({ error, onRetry }) {
  return (
    <div role="alert" className="fallback fallback--screen">
      <h1>This screen stopped working</h1>
      <p>Your unsaved changes are kept in this browser until you navigate away.</p>
      <div className="fallback-actions">
        <button onClick={onRetry}>Reload this screen</button>
        <Link to="/dashboard">Back to dashboard</Link>

    </div>
  );

The correlation id deserves emphasis because it is the bridge from a user's screenshot to your logs: componentDidCatch logs with a generated digest, the fallback displays the same digest, and the log line carries the component stack and the user's session context. Without a shared id, "it crashed for Amina" is a bug report you investigate by reproducing; with one, it is a log query that returns the exact render path. Generate the id at catch time, show it in the fallback, store it in the log — three lines of code that cut mean-time-to-diagnosis by most of a day.

// the digest is the contract between the fallback and the logs
componentDidCatch(error, info) {
  const digest = hashString(error.message + info.componentStack) & 0xffff;
  console.error('[boundary]', { digest, message: error.message,
                                stack: info.componentStack });
  // ship it: beacon to your logger with the same id the UI shows
  logError({ digest, message: error.message, component: info.componentStack,
             route: window.location.pathname, session: sessionId });
}

// the UI shows the SAME id - one string joins a support ticket to a trace
function Fallback({ error }) {
  return <p>Reference: {error.digest || 'local'}</p>;
}

Retry as a design element

Not every failure deserves a retry button, and the distinction is whether a retry can plausibly succeed. A render error caused by bad data from the server: retry re-runs the same request against the same server and produces the same crash — the right action is navigation or reload, and a Retry button that cannot succeed is worse than no button. A failed chunk load (chapter 14's lazy components): retry genuinely works, the network blip was transient, so offer it. A timeout: retry works but may take time, so offer it with the pending state. Classify your failures into transient and persistent, wire retry only to transient, and give persistent ones a route out — the classification is the entire content of a good recovery design.

// classifying failures: retry where retry can work, route out where it can't
function recoveryFor(error) {
  if (error instanceof ChunkLoadError) {
    return { kind: 'transient', action: 'retry',
             copy: 'The app was updated - reloading picks up the new version.' };
  }
  if (error instanceof TimeoutError) {
    return { kind: 'transient', action: 'retry',
             copy: 'The server took too long. Trying again often works.' };
  }
  if (error.status >= 500) {
    return { kind: 'transient', action: 'retry',
             copy: 'Our side had a problem. Nothing you did caused it.' };
  }
  return { kind: 'persistent', action: 'navigate',
           copy: 'This screen is not working right now. The dashboard is.' };
}

// the fallback renders from the classification, not from the error text
function RecoveryFallback({ error }) {
  const plan = recoveryFor(error);
  return (
    <div role="alert">
      <p>{plan.copy}</p>
      {plan.action === 'retry'
        ? <RetryButton />
        : <Link to="/dashboard">Go to the dashboard</Link>}
    </div>
  );
}

Chunk-load errors change meaning after a deploy: the user's cached app references a hashed file the new deploy deleted, so every retry of import() fails until a reload fetches the new HTML. Detect this case specifically and auto-reload once with a visible "Updating, one moment" message — the one failure where the correct recovery is a page load, not a retry.

Async errors and the rest of the page

Boundaries cover render-phase errors, and the majority of production failures live elsewhere: promise rejections in fetch chains, event handlers that throw after commit, timers, websocket callbacks, third-party scripts. For each category there is a containment that actually works, and the discipline is knowing which channel a given failure travels. Promise rejections are handled where the promise is awaited — in the action or query from chapters 13 and 15, which return errors as data rather than throwing into the void. Event-handler errors are handled by a try/catch in the handler that translates to user-visible state, because by the time it throws, the render is long committed and no boundary is listening. The application-level backstop is the window error and unhandledrejection listeners, which catch what nothing else did and are a reporting channel, not a recovery one — by the time an error reaches them, you cannot render a fallback.

The design rule behind the channels: an error that can be shown to the user must travel as data to a component that is currently rendering; an error that reaches the window has already lost that chance. This is the argument for the shapes chapters 13 and 15 established — actions return error objects, queries surface error state — and against fire-and-forget promises in handlers. A handler that awaits and sets an error state gives the user a message in place; a handler that does not gives you a console line after the user's click silently did nothing. The second silence, the click that did nothing, is the failure users hate most, and no boundary can tell them about it.

// four channels, four containments - pick by where the error travels
function SubmissionPanel() {
  const [state, action, pending] = useActionState(submitAction, { error: null });
  const [handlerError, setHandlerError] = useState(null);

  // channel 1: render errors -> the widget boundary above this panel
  // channel 2: the action's failures -> returned as data, rendered inline
  // channel 3: event-handler errors -> caught HERE, because no boundary is
  //            listening when a click throws after commit
  async function handleExport() {
    try {
      await api.exportReport();
    } catch (err) {
      setHandlerError('Export failed: ' + err.message);   // shown in place
    }
  }

  return (
    <WidgetBoundary label="Submission panel">
      {state.error && <p role="alert">{state.error}</p>}
      {handlerError && <p role="alert">{handlerError}</p>}
      <button onClick={handleExport}>Export</button>
    </WidgetBoundary>
  );
}

// channel 4: the backstop - reporting only, nothing can render from here
window.addEventListener('unhandledrejection', (event) => {
  logError({ kind: 'unhandled-rejection', reason: String(event.reason) });
});
window.addEventListener('error', (event) => {
  logError({ kind: 'global-error', message: event.message });
});

Timeouts, aborts and races deserve their own paragraph because they are errors the application creates for itself. A request that returns after its screen was replaced is not a failure — it is a response nobody asked for any more — and treating it as an error produces spurious failure messages on fast navigation. The containment is cancellation: AbortController wired to the query or effect cleanup (chapter 8's cleanup rule), so superseded requests stop being failures and start being nothing. The same reasoning applies to a retry storm: a flaky endpoint hit by three components at once needs one in-flight request per key (chapter 15's dedupe), not three error toasts teaching users the app is broken when the server is merely busy.

// cancellation instead of failure: superseded requests are not errors
function useSearch(term) {
  return useQuery({
    queryKey: ['search', term],
    queryFn: ({ signal }) => api.search(term, { signal }),  // abort on change
    retry: false,                        // a cancelled request must not retry
    enabled: term.length > 0,
  });
}

// and in a raw effect, the chapter 8 cleanup discipline
useEffect(() => {
  const controller = new AbortController();
  fetch('/api/report', { signal: controller.signal })
    .then((r) => r.json())
    .then(setReport)
    .catch((err) => {
      if (err.name === 'AbortError') return;   // superseded: NOT a failure
      setError(err);
    });
  return () => controller.abort();
}, [reportId]);

Degradation instead of failure

The highest form of resilience is a screen that never fully fails because it was never fully dependent. Render the shell from what you have, then let each region arrive or fail independently — chapter 14's boundaries, chapter 15's per-key queries, chapter 16's per-route loaders are all the same architecture seen from three angles: components own nothing essential, the cache holds what arrived, and one failed key costs one region. A page where the header, list and sidebar can each fail alone has a failure mode measured in widgets; a page that fetches everything in one effect has a failure mode measured in pages. Build from regions, and most errors never reach a boundary at all.

// degradation: three independent regions, three independent fates
function AccountPage() {

What to test, and at which layer

A testing strategy for React is a risk allocation: spend the most tests where changes are most frequent and failures most expensive, and stop where marginal tests become slower than the bugs they miss. The shape that consistently earns its keep is a trophy, not a pyramid: a thin layer of unit tests on genuinely pure logic (validators, formatters, the domain functions from chapters 11 and 15), a broad layer of integration tests that render components with real providers against a mocked network (this is where most assertions belong), and a thin cap of a few end-to-end tests through a real browser for the paths where money or account state moves. Component unit tests — rendering one component in isolation with everything mocked — sit below the trophy: they assert on props and callbacks the integration test would cover anyway, and they break when you refactor the component's internals, which is precisely when you want tests to hold still.

The selection rule for what deserves a test: assertions on behaviour a user could observe (text, roles, network calls, navigation) survive refactors; assertions on internal state, call counts of internal callbacks, and snapshot of intermediate renders do not. Write the test as if describing the feature to someone who has not seen the code — "submitting an invalid form shows the server's message beside the email field" is stable and meaningful; "EmailField calls setErrors with an array of length one" is the same moment encoded as a coupling. The first survives the component being rewritten in a different style, which is when tests are most valuable and most fragile.

// integration over unit: the feature, not the wiring
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

// one harness the whole suite shares: real providers, mocked network
function renderWithProviders(ui) {
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } });
  return render(<QueryClientProvider client={client}>{ui}</QueryClientProvider>);
}

Where each layer sits, concretely. Pure logic — a pricing rule, a slug generator, the key factories from chapter 15 — gets direct unit tests with no DOM at all: fastest, most precise, run on every save. Components and features get integration tests through the shared harness: real providers, mocked network, assertions on roles and text; these carry the bulk of the suite because they test the composition, which is where regressions actually occur. The network mock is the seam that keeps the whole thing deterministic — service-worker or fetch interception replacing the server — so integration tests exercise the real request shapes your API contract specifies without a live backend. End-to-end tests stay few: checkout, sign-up, the one workflow whose failure is a business incident, each asserted at exactly one point in the journey rather than duplicated down the stack.

afterAll(() => server.close());

What not to test

Four categories that cost more than they return: snapshots of whole component trees (they change on every legitimate refactor and reviewers approve them unread), tests of library behaviour already covered by the library's own suite (does React re-render on setState — really), assertions on private state or internal function calls (the coupling that breaks exactly when you improve the code), and tests that require a running backend to be meaningful (they are integration tests of the backend wearing a frontend badge). Every one of these appears in real codebases and each is a maintenance liability disguised as coverage; the discipline is that a test must fail when user-visible behaviour breaks, and never merely when the implementation changes.

Coverage percentage measures lines executed, not behaviour understood — a suite at 90 percent that asserts mocks and internals will pass while a navigation change breaks sign-in. Review tests the way you review features: what user-visible claim does this test make, and would its failure tell someone what to fix?

Testing users, not implementations

The query priority that keeps tests stable and honest: find elements the way a user finds them — by accessible role and visible name first, then by label text, then by placeholder, and never by test id as the first resort. Role queries force the markup to stay accessible (a button that becomes a div with an onClick breaks the query the same way it breaks a screen reader — which is the point: the test fails for the same reason a user would be harmed), and name queries force the visible label to stay attached to its control. Test ids sever both connections: they keep passing when the accessibility regresses, converting a real defect into a silent one. Reserve them for elements with no role and no text — a canvas overlay, a drag handle — where the other two queries genuinely cannot apply.

User events over fireEvent: userEvent types character by character, honours pointer and focus semantics, and produces the sequence the browser produces, which is what makes a form test catch the fact that the submit button never received focus or that a controlled input's onChange did not fire for pasted text. The complementary half is awaiting, and the rule that prevents the classic flake: never wait on time, always wait on the observed outcome — findByRole with a generous timeout instead of sleep, because a fixed sleep is wrong on both sides (too short on slow machines, wasted time on fast ones) and hides the real question, which is not "has enough time passed" but "has the thing appeared".

// query priority: role, then label, then text - test id only as a last resort
test('adding a task puts it in the list and clears the field', async () => {
  renderWithProviders(<TaskApp />);

  // by role + accessible name: fails if the button loses its label OR its
  // role - the same change that would strand a screen-reader user
  const input = screen.getByRole('textbox', { name: /new task/i });
  const add = screen.getByRole('button', { name: /^add$/i });

  await userEvent.type(input, 'Write the release notes');
  await userEvent.click(add);

  // await the OUTCOME, never a duration - no sleep, no arbitrary timeout
  expect(await screen.findByRole('listitem')).toHaveTextContent('Release notes');
  expect(input).toHaveValue('');           // the field cleared, as designed
});

// the flake its replacing: time-based waiting hides the real condition
async function flaky() {
  await userEvent.click(add);
  await new Promise((r) => setTimeout(r, 300));   // wrong on slow AND fast
  expect(screen.getByText('Release notes')).toBeInTheDocument();
}

Interaction-level assertions complete the style. Test the workflow the way a user walks it — land on the screen, fill the form, submit, assert the outcome (a success message, a new row, a navigation) — rather than asserting each intermediate handler fired. This is what makes a test suite read as documentation: a colleague can scan the test names and learn what the application does, because each name is a capability, not an implementation event. And it is what makes the tests resilient: a capability persists through refactors of every kind, while an event fires only as long as the code fires it.

// tests as documentation: capabilities, walked in order
describe('task archive', () => {
  test('archiving a task removes it from the open list', async () => {
    renderWithProviders(<TaskApp />);
    const row = await screen.findByRole('listitem', { name: /write notes/i });
    await userEvent.click(within(row).getByRole('button', { name: /archive/i }));
    expect(screen.queryByRole('listitem', { name: /write notes/i })).toBeNull();
  });

  test('a failed archive keeps the task and explains why', async () => {
    server.use(rest.post('/api/tasks/:id/archive',
      (req, res, ctx) => res(ctx.status(403), ctx.json({ message: 'Read-only member' }))));
    renderWithProviders(<TaskApp />);
    const row = await screen.findByRole('listitem', { name: /write notes/i });
    await userEvent.click(within(row).getByRole('button', { name: /archive/i }));
    // failure path asserted the same way: visible outcome, in place
    expect(await screen.findByRole('alert')).toHaveTextContent('Read-only member');
    expect(screen.getByRole('listitem', { name: /write notes/i })).toBeInTheDocument();
  });
});

The boundary between test kinds

End-to-end tests earn their cost by covering the seams integration tests cannot: real routing with real history, real build output (code splitting, minification, the compiler from chapter 12), real browser form and focus behaviour, and third-party scripts that only exist in a browser. Everything else belongs in integration, which runs in seconds and diagnoses failures precisely, while an end-to-end failure reports only that "the journey broke". Keep the split by what each kind can see: if a test needs a real DOM layout, a real network stack or a real bundle, it is end-to-end; if it needs a mocked fetch and a rendered tree, it is integration; if it needs neither, it is a unit. Following that rule keeps the expensive suite small without leaving the risky paths uncovered.

// the end-to-end suite: the few paths whose failure is an incident
// e2e/checkout.spec.js - real browser, real build, real service worker
test('a customer can complete checkout end to end', async ({ page }) => {
  await page.goto('/products');
  await page.getByRole('link', { name: /watering can/i }).click();
  await page.getByRole('button', { name: /add to cart/i }).click();
  await page.getByRole('link', { name: /cart/i }).click();
  await page.getByRole('button', { name: /checkout/i }).click();

  await page.getByLabel(/card number/i).fill('4242424242424242');
  await page.getByRole('button', { name: /pay/i }).click();

  // exactly one assertion at the end of the journey: the business outcome
  await expect(page.getByRole('heading', { name: /order confirmed/i })).toBeVisible();
});

// everything the journey implies about components is covered faster and
// more precisely in integration - the e2e test asserts only that it ENDS

The failure mode of a growing suite is not slowness but distrust: flakes taught the team to re-run rather than read, at which point red means nothing. Budget for determinism — no real clocks, no shared server state, no test-order dependence — and treat every flake as a defect in the test. A suite that is trusted when it is red is worth more than triple the tests that are only trusted when green.

Folders by feature, not by type

The folder question looks cosmetic and is actually the first architecture decision, because it determines what a change touches. Type-first structure — components/, hooks/, utils/, pages/ — groups by what a file is, which means every feature is scattered across four directories: the page in one, its components in another, its hooks in a third, shared bits in a fourth. A single feature change is therefore four pull requests' worth of files in one diff, every other feature's files sit in the same directories, and ownership is folklore. Feature-first structure — features/projects/, features/billing/ — groups by what a file is for: everything the projects feature needs lives together, a diff for a projects change touches the projects directory, and a new engineer can read one folder to understand one capability.

Feature-first does not mean no shared structure; it means shared structure earns its place explicitly. The shape that holds up at ten people: app/ for composition only (router table, providers, entry point), features/ for capabilities, shared/ for the genuinely cross-cutting (design system, the query client, the key factories, formatters), and routes-and-loaders owned by the feature they serve (chapter 16's route fragments). The rule that keeps it from rotting: a file may import from shared/ and from its own feature, and may import another feature only through that feature's public entry point — which is the next section's subject. Files that violate this start as conveniences and end as the coupling that makes every refactor a cross-team negotiation.

// feature-first: one folder reads as one capability
src/
  app/
    routes.tsx          // composition: imports feature route fragments
    providers.tsx       // query client, theme, error boundaries (root)
    main.tsx            // entry: mount and nothing else
  features/
    projects/
      routes.tsx        // the feature's route fragment (ch16)
      pages/            // screens this feature owns
      components/       // used by nothing outside this folder
      hooks/            // useProject, useProjectTasks
      api.ts            // fetchers + key factories (ch15)
      index.ts          // the PUBLIC surface - the only import path out
    billing/
      routes.tsx pages/ components/ hooks/ api.ts index.ts
  shared/
    ui/                 // design system: Button, Field, Table
    query/              // queryClient, retry policy
    format/             // money, dates, pure and unit-tested
    api/                // the fetch wrapper, auth header

// a type-first counterexample, and the diff it produces
src/components/InvoiceTable.tsx        // touched by billing work
src/hooks/useInvoices.ts               // touched by billing work
src/pages/InvoicesPage.tsx             // touched by billing work
src/utils/invoiceFormat.ts             // touched by billing work
// one feature's change, four directories, no ownership boundary

Two follow-up decisions teams get wrong early. First, pages versus components inside a feature: pages are the route elements — they read loaders and params, compose the screen — while components are the screen's parts; conflating them produces 800-line files where routing concerns and rendering concerns alternate. Second, the size threshold for promoting a folder to a feature: when two features genuinely share a domain concept (a document viewer used by projects and by support), it moves to shared/ or a third feature — it does not live in one feature with the other importing across, because that import is the boundary violation wearing a reasonable name. Move code toward the level where its changes cluster.

// pages compose routes; components render; the feature owns both
features/projects/
  pages/
    ProjectListPage.tsx      // loader data + params -> composes the screen
    ProjectDetailPage.tsx    // <ProjectHeader/> + <TaskBoard/> + outlet panel
  components/
    ProjectHeader.tsx        // pure render of the record - no params, no loader
    TaskBoard.tsx            // columns, drag handling, keyboard moves
    TaskCard.tsx             // one row: could be unit-tested in isolation

// a page reads the routing layer (ch16) and hands components render data:
export function ProjectDetailPage() {
  const { project } = useLoaderData();
  return (
    <>
      <ProjectHeader project={project} />
      <TaskBoard projectId={project.id} tasks={project.tasks} />

The folder test in review

A structural rule is only real if review enforces it, and the fastest enforcement is a question, not a tool: "which folder does this file belong to, and who owns it?" If the answer requires explanation, the structure has an ambiguity the next change will exploit. The heavier version — an import-boundary linter rule — is worth installing once the question starts recurring, because by then the violations are patterned and mechanical to block. Start with the review question; graduate to the rule when you can name the three import patterns it should forbid.

// import boundaries as a lint rule: features reach each other only via index
// .eslintrc.cjs - no-restricted-imports, paths relative to the rule
module.exports = {
  rules: {
    'no-restricted-imports': ['error', {
      patterns: [
        {
          group: ['@/features/projects/components/*'],
          message: 'Import from @/features/projects (its index), not internals.',
        },
        {
          group: ['@/shared/ui/*'],
          message: 'Import from @/shared/ui - the barrel is the contract.',
        },
      ],
    }],
  },
  overrides: [
    // the feature itself may of course import its own internals
    { files: ['src/features/projects/**'], rules: {
        'no-restricted-imports': 'off' } },
  ],
};

The index file of a feature is its API. Keeping it explicit — exporting the pages, the route fragment, and the handful of types other features legitimately need — means an import tells the reader exactly what cross-feature relationship exists, and a change to a feature's internals does not touch its consumers. Internal imports from other features are the single most common way a codebase's boundaries quietly cease to exist.

Module boundaries that hold

A boundary is a promise about the shape of a change: what happens inside a module must be changeable without touching its consumers, and what crosses the boundary must be small, stable and explicit. In React terms the promise has three surfaces. The props a component accepts are its contract — adding an optional prop is compatible, renaming or retyping one is not, and the discipline is to design props as if a stranger's code depends on them, because in a ten-person repo it does. The public entry point of a feature is the second surface: types, route fragments, and the components other features embed, with everything else private by omission rather than by convention. The third is the data contract: the shape returned by a feature's fetchers and actions, which travels through the cache (chapter 15) into other features' renders, and whose evolution needs the same care as an API's.

The failure boundaries cause is ripple, and it has a signature: a change that should be local appears in many directories. Three smells predict it before it arrives. Deep reaching — import { Row } from '@/features/billing/components/Row' — means another feature's internals are load-bearing somewhere, so refactoring Row is no longer billing's decision. Shared state — a context whose value three features write — means they cannot be reasoned about independently, and chapter 10's split-context advice applies at the architecture level: split it by ownership or replace it with the cache. And circular imports — feature A importing B while B imports A — mean the two are one module wearing two names; the fix is to extract what they actually share into shared/ rather than to restructure the imports.

// the three smells, and what each one means
// 1. deep reaching: a refactor in billing now needs projects' review
import { InvoiceRow } from '@/features/billing/components/InvoiceRow';
//    fix: export it from billing/index.ts if it IS a public surface,
//    or stop importing it if it is not.

// 2. shared mutable context: features that write the same value are one
//    feature split across folders (ch10 split fast/slow, or use the cache)
const WorkspaceContext = createContext(null);   // three writers, no owner

// 3. circular imports: A and B are one module with two directories
// features/projects/api.ts   -> import { formatMoney } from '@/features/billing/api'
// features/billing/api.ts    -> import { InvoiceStatus } from '@/features/projects/api'
//    fix: both want shared/format and shared/types - give it to them

// the healthy version: stable props, public entry, one-directional data
// features/projects/index.ts
export { ProjectListPage, ProjectDetailPage } from './pages';
export { projectRoutes } from './routes';
export type { Project, ProjectId } from './types';

Props design is where the boundary is exercised daily, and the pattern that keeps them stable is treating them as a message format: primitives and domain objects the parent already had, callbacks named for the intent they serve (onSelect rather than setSelectedIdFromTable), children for composition slots, and no prop that leaks the component's internal state machine (isOpen plus onToggle plus onOpenChange for one state is a contract with three ways to disagree). The test for a props interface: can a consumer use it correctly without reading the component's source? If not, the interface is describing implementation, and implementation is the thing boundaries exist to hide.

// props as a stable message format
// GOOD: intent-named callbacks, domain data, composition slot
function ProjectRow({ project, onOpen, onDelete, children }) {
  return (
    <li>
      <button onClick={() => onOpen(project.id)}>{project.name}</button>
      <Menu onDelete={() => onDelete(project.id)} />
      {children}
    </li>
  );
}

// BAD: the component's internals leaked into its contract
function ProjectRow({ project, selectedId, onSelectId, onSelectIdChange,
                      hovered, onHoverChange, expanded, onExpandToggle }) {
  // six props, three of which are one piece of state with two spellings -
  // every consumer must know the component's state machine to call it
}

// the boundary test: use it from the public entry, never the internals
import { ProjectRow } from '@/features/projects';    // contract
import ProjectRow from '@/features/projects/components/ProjectRow'; // leak

The same rule separates a folder from a feature. A folder is a place to put files; a boundary is a promise about what may depend on what. Enforce it with a lint rule rather than a code-review habit, because a habit survives one reviewer leaving the team and a lint rule does not.

// eslint-plugin-boundaries: a feature may import its own files and
// shared, and nothing else. App wires features together and may
// import everything. Nothing may import another feature's internals.
{
  "rules": {
    "boundaries/entry-in-dependencies": "error",
    "boundaries/no-unknown": "error",
    "boundaries/no-private": "error",
    "boundaries/element-types": ["error", {
      "default": "disallow",
      "message": "Import across features through app/, never feature to feature.",
      "rules": [
        { "from": "feature", "to": "feature", "when": { "imported": true } }
      ]
    }]
  }
}
Boundaries are cheaper to add at the start than to retrofit. If you are retrofitting anyway, start with the rule that catches the most: no feature imports another feature's internals. Everything else is a refinement of that one.

Versioning a public surface

A shared package used by two teams is a published library, whether or not it reaches a registry. Give it a version, a changelog, and a rule for breaking changes: additive is a minor bump, a changed signature is a major one. Consumers pin a range, so the shared package never forces every feature to change on the same day.

// packages/ui/package.json
{
  "name": "@acme/ui",
  "version": "2.4.1",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./icons": { "default": "./dist/icons.js" }
  },
  "files": ["dist"],
  "scripts": { "build": "tsc -p tsconfig.build.json" }
}

// A breaking change lands as 3.0.0, with a codemod in the changelog.
// Consumers upgrade when they are ready, not when the shared team ships.
Version the export list, not the folder. Deep imports like @acme/ui/dist/internal/Button bypass every guarantee you have made, which is why exports in package.json is worth setting even inside a monorepo.

Shared code and the component contract

Sharing starts the moment two features need the same button. The mistake is treating that as a signal to build a design system; the signal is only that you have written the same button twice. Promote code when the third use is real, and promote it by moving it, not by wrapping it, because a wrapper around a component you do not control becomes a second API you now have to maintain.

// Stage 1: duplication. Correct, and free of decisions.
function SaveButton({ onClick }) {
  return <button className="btn btn-primary" onClick={onClick}>Save</button>;
}

// Stage 2: extract, do not wrap. The props are the ones callers used,
// not the ones the design system happens to offer.
function SaveButton({ onClick, disabled }) {
  return <Button variant="primary" disabled={disabled} onClick={onClick}>
    Save
  </Button>;
}

// Stage 3, and only once three features agree: the vocabulary becomes
// yours. Callers now say intent, not styling.
<SaveButton onClick={save} />
<DeleteButton onClick={remove} confirm />

The test for whether something belongs in shared code is not "is it reusable" — almost everything is reusable under pressure — but "do the consumers agree on what it means". Two teams that want different click behaviour do not have a shared button problem; they have a naming problem, and a shared component would hide the disagreement behind a prop.

// The disagreement, made visible as a prop: a sign the abstraction is wrong.
function Button({ onClick, onPress, onActivate, ...rest }) { /* ... */ }

// The fix is a conversation, then two components with honest names.
function SubmitButton({ onClick })  { /* optimistic, disables itself */ }
function CommandButton({ onClick }) { /* fire and forget, never disables */ }
Shared code carries shared upgrade cost. Every file you move into packages/ui is a file whose changes can break features you have never opened. Keep the shared surface small and boring — tokens, primitives, layout — and keep product logic in the feature that owns it.

The contract is the prop list, not the JSX

When a component crosses a feature boundary, its props stop being an implementation detail and become an interface you have to version. The practical difference is visible in review: an internal component may take whatever is convenient, because its only caller is twenty lines away, while a shared one has to be legible to someone who has never opened its file. That means names that describe intent rather than state (disabled, not isDisabledFromParent), a small number of props with obvious defaults, and — for anything with real behaviour — a controlled form so the caller, not the component, decides when the thing happens. A shared component that reaches for context you did not pass it, or reads a global the caller cannot see, is a boundary that only appears to be one.

// Internal: convenient is fine, the caller is adjacent.
function TaskRowInternal({ task, onDrop, ghost }) {
  return <li className={ghost ? 'row ghost' : 'row'}>{task.title}</li>;
}

// Shared: the same rendering, expressed as a contract a stranger can read.
function TaskRow({ title, state = 'idle', onPick }) {
  return (
    <li data-state={state} onClick={() => onPick?.(title)}>
      {title}
    </li>
  );
}
// state is a closed vocabulary, onPick is optional, and nothing about
// drag-and-drop leaks in — the feature composes those around the row.

Two habits keep the contract honest over time. Document each shared component with one example of real use rather than a table of prop types, because the example is what a consumer scans for; and treat a prop added to a shared component as a design review, asking whether it belongs to every consumer or only to one. If it belongs to one, it belongs in that feature — passed as children, as a render prop, or as a second component built from the first. The moment a shared component accumulates flags for individual callers, it has stopped being shared code and started being two components wearing one name, and the cheapest fix is to separate them again while the split is still obvious.

The pipeline: build, verify, ship

A pipeline is not "CI with tests in it"; it is the sequence of promises a change makes before it can reach a user, and each promise has to be checkable by a machine rather than by whoever reviews the pull request that day. The three that matter for a React codebase: it builds (type errors and bundler failures are caught before merge), it verifies (tests, lint, and the boundary rules from earlier in this chapter run on every push), and it ships the same artifact that was verified — not a second build on the deploy machine, which is how "it passed CI but production broke" happens. If the artifact that was tested is not the artifact that ships, nothing else in the pipeline is evidence.

# .github/workflows/ci.yml — one job per promise, one artifact out
name: ci
on: [push, pull_request]

jobs:
  build:                       # promise 1: it compiles
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run build      # tsc + vite build, no tests yet
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist }

  verify:                      # promise 2: it behaves
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run test:run -- --coverage
      - run: npm run test:e2e   # playwright, against the built app

  ship:                        # promise 3: same bytes, different place
    needs: [build, verify]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: dist, path: dist }
      - run: ./scripts/deploy.sh   # uploads dist/, never rebuilds

Cache strategy is the difference between a four-minute pipeline and a twenty-minute one. Three caches pay for themselves immediately: the package manager's (keyed on the lockfile, so a dependency change invalidates exactly once), the test runner's (Vitest and Jest both keep a transform cache between runs — persist it with actions/cache, keyed on source hash plus lockfile), and the bundler's. The failure mode to avoid is a cache keyed only on branch name: a force-push that rewrites history can silently serve stale output, so the key must include something that changes whenever the inputs change.

- uses: actions/cache@v4
  with:
    path: |
      ~/.npm
      .vitest-cache
    key: ${{ runner.os }}-verify-${{ hashFiles('**/package-lock.json') }}-${{ github.sha }}
    restore-keys: |
      ${{ runner.os }}-verify-${{ hashFiles('**/package-lock.json') }}-

# The restore-keys line is what makes it fast on a miss: an exact-key
# miss falls back to the newest cache with the same lockfile, which is
# correct because the lockfile determines the transform inputs.
Gate on the fastest failure first. Type errors surface in seconds and catch more real bugs per second than any test suite, so tsc --noEmit belongs before tests, not after — and lint rules that encode boundaries (the import rules from 19.2) run in the same window, for the same reason: they are static, so they are nearly free.
A flaky test is a broken build that occasionally lies. Quarantine is acceptable as a temporary state with an owner and a date; a quarantined suite that nobody revisits teaches the team to re-run failures, which is the same as having no suite at all.

Preview deployments: the reviewable build

A preview deployment turns "does this work?" from a question answered in prose on the pull request into a URL a reviewer can open, click through, and form an opinion about — which changes what gets reviewed, because a screenshot invites skim-reading while a running app invites trying the edge case you were hoping nobody would try. The mechanics are cheap once the pipeline emits an artifact: one deploy per branch, named after the PR number so a new push replaces the old one, with the environment URL posted back as a comment. Two rules keep previews trustworthy: they must run the same build command as production (a preview built differently is a demo, not evidence), and they must not touch production data — seeded fixtures or a shadow database, never a copy of the real one.

# previews are the same ship step, a different target
preview:
  needs: [build, verify]
  if: github.event_name == 'pull_request'
  runs-on: ubuntu-latest
  steps:
    - uses: actions/download-artifact@v4
      with: { name: dist, path: dist }
    - run: ./scripts/deploy.sh "pr-${{ github.event.number }}"
    - uses: actions/github-script@v7
      with:
        script: |
          github.rest.issues.createComment({
            owner: context.repo.owner,
            repo: context.repo.repo,
            issue_number: context.issue.number,
            body: `Preview: https://pr-${context.issue.number}.staging.example.com`
          });

Production: deploy, observe, roll back

Deploying a React app is shipping static files plus whatever server renders them, so the interesting decisions are about the boundary between old and new: how a user mid-session is treated when the new version lands, and how fast you can undo it. The boring, correct answer for most teams is immutable deploys — each release is a directory keyed by commit, the server or CDN points at one of them, and rollback is repointing rather than rebuilding. Under that model the browser's cached assets are safe too, because an old HTML file references hashed asset names that still exist in their old directory; the danger case is an in-place overwrite, where the old HTML now points at files that no longer match it and users get a half-old page until their cache expires.

#!/usr/bin/env bash
# deploy.sh — immutable, repointable, reversible in one command
set -euo pipefail

RELEASE="releases/$(git rev-parse --short HEAD)"
mkdir -p "$RELEASE"
cp -r dist/* "$RELEASE/"

ln -sfn "$RELEASE" releases/current          # repoint atomically

Observability for a single-page app cannot be read from server logs, because the failures users see — a blank screen after a deploy, a form that never submits, a route that renders nothing — happen in the browser after the server has already returned 200. Three signals cover most of it: an error tracker with release tagging (so "errors are up" becomes "errors are up since 2.14.0"), web-vitals reporting to catch a bundle-size regression that no test would see, and a synthetic check that walks the login-and-load flow on a schedule from outside your network. Each is keyed to a release, which is what makes the rollback decision a data question rather than a guess.

// main.tsx — attach the release to every report before anything else
import * as Sentry from '@sentry/react';

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_GIT_SHA,   // set by the pipeline
  environment: import.meta.env.MODE,
  tracesSampleRate: 0.1,
});

// web-vitals: the regressions tests cannot see
import { onCLS, onINP, onLCP } from 'web-vitals';
onVitals(({ name, value, id }) => {
  sendToCollector({ name, value, id, release: GIT_SHA, route: location.pathname });
});

// The rule that makes it actionable: a page load with no error and
// INP over 200ms is a real user's bad day, and it aggregates per
// release — so the deploy that caused it shows up without archaeology.
A rollback that has never been rehearsed is a hope. Time it once: from "we are reverting" to "users are on the old version" should be under five minutes and should involve one command. If it is longer than that, fix the deploy model before you need it — the incident is the wrong time to discover that rollback means rebuilding.

Releases, sessions, and the tab that stays open

The hardest moment of a deploy is not the deploy; it is the minutes after it, when tabs opened on the old version keep running against a server that now speaks the new contract. A long-lived tab will fetch chunks that no longer exist at their old hashed paths (the classic "ChunkLoadError" on a route change), and its in-flight mutations may answer against a database the release just migrated. Three defences, in order of how much they cost: keep the previous release's assets served for a grace window rather than deleting them on cutover; have the app poll a version endpoint and prompt a reload when it drifts, so the user decides when to switch rather than meeting an error mid-task; and make migrations additive first — add columns, deploy, backfill, and only then remove the old reads in a later release, so old and new code can run against the same schema at once.

// poll the release, ask for a reload when the tab is stale
let current = window.__RELEASE__;
setInterval(async () => {
  const r = await fetch('/version.json', { cache: 'no-store' });
  const { release } = await r.json();
  if (release !== current && !sessionStorage.getItem('reload-offered')) {
    sessionStorage.setItem('reload-offered', '1');
    toast('A new version is ready — reload', { action: () => location.reload() });
  }
}, 60_000);

// The prompt, not a forced reload: a user mid-form loses nothing,
// and the stale tab never gets far enough to hit a deleted chunk.
