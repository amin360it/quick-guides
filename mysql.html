Orientation — Scope, Version and Method

0.1 Scope and audience0.2 Version target and supported configurations0.3 Storage engine architecture0.4 The concepts that differ from other engines0.5 The reference schema used throughout0.6 Conventions and how to read this guide

MySQL remains the most widely deployed relational database in the world, and the version in production is frequently not the version in any tutorial. This guide is written against MySQL 9.x with InnoDB as the only storage engine under discussion, and it is aimed at engineers who administer or build on MySQL professionally. It assumes SQL fluency and focuses on the places where MySQL’s behaviour is specific, surprising, or the direct opposite of what the SQL standard or another engine would do.

0.1 Scope and audience

What this guide covers and, more usefully, what it deliberately omits.

MySQL has accumulated thirty years of compatibility decisions. Reading its documentation without knowing which of them you are looking at produces advice that is correct for MySQL 4 and wrong for MySQL 9. The most consequential of these are covered in chapter 1: the utf8mb4 default, the strict SQL mode, the removal of implicit type coercion, the deprecation of the query cache, and the move to an instant-DDL model. Where a behaviour changed in a specific version, the version is named.

Out of scope: MyISAM, which is deprecated and present only for upgrade paths; the NDB storage engine, which is a distributed engine with entirely different semantics; and MySQL Replication, which deserves its own treatment. The replication protocol, the SQL thread and the IO thread, GTID versus file-position replication, and the failure modes of a single-threaded applier are all in the MySQL replication chapter of the database design guide and in the system design guide’s replication chapter.

The audience. Someone who has to make a production MySQL faster, safer, or recoverable, and who needs to know why rather than which knob. A developer who will be on call for the schema they designed, and who needs to know what the storage engine does with the constraints they wrote. A reviewer who needs to catch the specific mistakes MySQL permits that other engines do not.

# The three configuration decisions that change behaviour more than any
# schema design decision, and which are already correct by default in 8.0+.
#
# 1. SQL MODE. This is the biggest behavioural difference between a MySQL
#    that silently corrupts data and one that refuses it.
SELECT @@GLOBAL.sql_mode;
#   8.0+ default includes:
#   ONLY_FULL_GROUP_BY              rejects a query whose SELECT list, HAVING and
#                                  WHERE do not collectively determine every selected
#                                  non-aggregated column
#   STRICT_TRANS_TABLES             rejects out-of-range values instead of truncating
#                                  them to the boundary and inserting a warning
#   NO_ZERO_IN_DATE, NO_ZERO_DATE   rejects '0000-00-00', which is not a date
#   ERROR_FOR_DIVISION_BY_ZERO      makes 1/0 an error rather than NULL
#   NO_ENGINE_SUBSTITUTION          refuses to silently fall back to MyISAM
#
#   ONLY_FULL_GROUP_BY is the one that breaks existing application queries on
#   upgrade, and it breaks them correctly. Fix the query; do not disable the mode.
SELECT user_id, MAX(created_at) AS last_seen, email
  FROM sessions
 GROUP BY user_id;
#   ERROR 3064: Expression #3 of SELECT list is not in GROUP BY clause...
#   The query is genuinely ambiguous: which email did you mean, the one from
#   the latest row or the first? The mode is asking a real question.
SELECT user_id, MAX(created_at) AS last_seen, email
  FROM sessions
 GROUP BY user_id
#   Correct: name the row you meant, or aggregate the value too.
SELECT s.user_id, s.created_at AS last_seen, s.email
  FROM sessions s
  JOIN (SELECT user_id, MAX(created_at) AS mx
            FROM sessions GROUP BY user_id) t
    ON t.user_id = s.user_id AND t.mx = s.created_at
#   Or, when you genuinely want an arbitrary one and say so:
SELECT user_id, email, ANY_VALUE(created_at) AS ts
  FROM sessions GROUP BY user_id, email;

# 2. THE TRANSACTION ISOLATION DEFAULT. MySQL's REPEATABLE READ is not the
#    standard's. It is gap-locking, which prevents phantom reads and which
#    produces deadlocks other engines do not have.
SELECT @@GLOBAL.transaction_isolation;
#   REPEATABLE-READ  ← the default, and the source of most deadlock reports
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
#   READ COMMITTED is what PostgreSQL's default is, it does not gap-lock, and it
#   produces fewer deadlocks at the cost of phantom reads. For most OLTP
#   workloads on MySQL, READ COMMITTED is the better default. See chapter 4.

# 3. INNODB_REDO_LOG_CAPACITY, which replaced the two log-file settings in 9.0.
SELECT @@innodb_redo_log_capacity;     # bytes, not files; resizes online
#   This is a capacity decision with a specific consequence: the redo log
#   bounds how much work a crash can lose, and how long a checkpoint can stall.
#   See chapter 4.4 — it is a tuning knob with a correctness dimension.

Never disable ONLY_FULL_GROUP_BY to make a query work. It is the mode that catches a query whose result is not reproducible — one that returns a different email for the same user depending on the execution plan. Turning it off converts a correctness error the database detected into a data error that surfaces in a report months later. There are exactly two legitimate responses to the error: change the query, or use ANY_VALUE to state explicitly that the value does not matter.

0.3 Storage engine architecture

What InnoDB actually stores, and why the buffer pool, the redo log and the change buffer are the three structures that explain almost every performance characteristic.

# The three structures, and what each is for.
#
# 1. THE BUFFER POOL. All InnoDB tables — data and index pages — live in
#    memory in the buffer pool, and the on-disk files are the durable copy.
#    This inverts the intuition from a file-per-table engine: the disk is a
#    backup of memory, not the place data lives.
SELECT @@innodb_buffer_pool_size;            # 128 MB default. Frequently
SELECT @@innodb_buffer_pool_instances;      # far too small. See ch5.5.
SELECT @@innodb_buffer_pool_chunk_size;     # 134217728 = 128 MB
#   Sizing: 60-80% of RAM on a dedicated host, or leave room for the OS and
#   the connection buffers. A buffer pool smaller than the working set is
#   the single most common cause of "MySQL is slow" on a large server.
#   Multiple instances exist only to reduce the mutex contention on the LRU
#   list. If innodb_buffer_pool_size is below about 1 GB, one instance is better.
#
#   The working set that must fit is: the hot data pages PLUS the hot index
#   pages. Indexes frequently dominate, and that is the fact people miss when
#   they size for "the data".
SELECT table_name,
       ROUND(index_length / 1024 / 1024) AS index_mb,
       ROUND(data_length  / 1024 / 1024) AS data_mb
  FROM information_schema.tables
 WHERE table_schema = 'shop'
 ORDER BY index_length DESC LIMIT 10;

# 2. THE REDO LOG. A physical, circular log of every page modification.
#    It is what makes a crash recoverable, and its size sets two things at
#    once: how much work a crash can lose (bounded by checkpoint age, not by
#    capacity) and how long a checkpoint pause can be.
#    Checkpoint age is the number to watch, not the log size:
SELECT page_checkpoint_age,
       ROUND(page_checkpoint_age / 1024 / 1024, -- 2) AS mb_since_checkpoint,
       CASE WHEN page_checkpoint_age > 604800 THEN 'PRESSURE: >7d old, will not advance'
            WHEN page_checkpoint_age > 3600  THEN 'SLOW: >1h since checkpoint'
            ELSE 'ok' END AS health
  FROM information_schema.innodb_metrics
 WHERE name = 'trx_rseg_history_len';   -- different metric, see below
#   A checkpoint that cannot advance — because the oldest active transaction
#   holds a read view — means the redo log fills and every write blocks.
#   That is the mechanism behind "the database hung at 3am". Chapter 4.
#
# 3. THE CHANGE BUFFER. Inserts to a secondary index whose pages are not
#    yet in the buffer pool are accumulated here and merged later, rather
#    than reading the page in. It helps a write-heavy workload on a large
#    table with random primary keys, and it HURTS a read-heavy one and any
#    workload with a high delete rate.
SELECT @@innodb_change_buffering;         # 'all' | 'none' | 'inserts' | 'purges'
#   Sequential primary keys make it nearly useless: the inserts land on the
#   rightmost page, which is the page already being written. If you use
#   AUTO_INCREMENT integers, set this to 'none' and re-measure.
#
# THE TABLESPACE. In MySQL 8.0 a per-table tablespace is the default, so
# each table has an .ibd file. The system tablespace holds the data
# dictionary, the doublewrite buffer and the redo log — and this is why
# ibdata1 no longer grows, which surprises people upgrading from 5.7.
SELECT file_name, file_type, ROUND(extent_size / 1024 / 1024, -- 2) AS extent_mb
  FROM information_schema.innodb_tablespaces
 WHERE file_type LIKE '%TABLESPACE%'
 ORDER BY extent_size DESC LIMIT 10;
#   Move a hot table's tablespace to fast storage, or spread a cold one:
#   ALTER TABLE sales_order TABLESPACE ts_fast;  -- requires DATA DIRECTORY
#   which is disabled by default in 8.0 for security reasons. Prefer LVM or
#   separate schemas on separate instances.

The three structures explain most of what follows. A query that is slow because a page is not in the buffer pool is an I/O problem and is fixed by sizing. A checkpoint that cannot advance is a long-transaction problem and is fixed by finding the transaction. A write that blocks is usually a purge problem, and is fixed by looking at the history list length. Every performance chapter in this guide is an elaboration of one of those three sentences.

-- The coercion trap, demonstrated. This is a real upgrade failure.
--
-- Before 8.0, this matched. After 8.0, it returns nothing:
CREATE TABLE orders (
  order_id   VARCHAR(32) NOT NULL PRIMARY KEY,   -- deliberately wrong
  total_cents BIGINT NOT NULL
);
INSERT INTO orders VALUES ('0042', 1000), ('42', 2000);

SELECT * FROM orders WHERE order_id = 42;
-- MySQL 5.7 and earlier: both rows, because '42' was cast to 42.
-- MySQL 8.0+:           NO rows. The integer is converted to the string
--                         '42', which does not equal '0042' or '42'.
--                         Silent. No error, no warning by default. Zero rows.
--
-- The fix is on the schema side, not the query side:
ALTER TABLE orders MODIFY order_id BIGINT NOT NULL;
-- Or, if the string form is genuinely the domain, quote the parameter
-- in EVERY query and never compare it to a literal number. Fragile.

-- Detect it before it happens. A string PK on a table named orders,
-- invoices, users or products is a schema smell:
SELECT table_name, column_name, column_type
  FROM information_schema.columns
 WHERE table_schema = 'shop'
   AND column_key = 'PRI'
   AND data_type IN ('varchar', 'char', 'text')
 ORDER BY table_name;
-- A UUID or an external reference is a legitimate VARCHAR primary key.
-- An autoincrementing id stored as a string is a bug with extra steps.

0.5 The reference schema used throughout

One schema, used by every example in this guide, so that a chapter can build on the previous one and a reader can follow a single thread.

# The reference schema. Multi-tenant, and the tenant key is in every primary
# key because that is the property that makes the model work. Chapter 4 of
# the database design guide argues it at length; here it is applied.
#
# Deliberate choices, each of which is argued somewhere in this guide:
#   * tenant_id in every PK      → global uniqueness without coordination,
#                                and every FK can be local
#   * money as BIGINT minor units→ no DECIMAL rounding, no FLOAT, section 1.2
#   * timestamps as TIMESTAMP   → stored UTC, converted on display
#   * no ON UPDATE CURRENT_TIMESTAMP → application owns the value, because the
#                                application is the only thing that knows the
#                                semantic time (placed_at, not updated_at)
#   * no foreign key on the hot path → argued in section 2.5, deliberately
#   * a prefix index for lookup by external reference → section 3.4

CREATE DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE shop;

CREATE TABLE tenant (
  tenant_id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  slug         VARCHAR(63)  NOT NULL,
  name         VARCHAR(255) NOT NULL,
  created_at   TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (tenant_id),
  UNIQUE KEY uq_tenant_slug (slug)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE app_user (
  tenant_id      BIGINT UNSIGNED NOT NULL,
  user_id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_slug    VARCHAR(63)  NOT NULL,   -- denormalised, see 3.6
  email          VARCHAR(320) NOT NULL,
  display_name   VARCHAR(255) NOT NULL,
  password_hash  BINARY(32)   NOT NULL,      -- Argon2id, 32 bytes
  is_active      TINYINT(1)   NOT NULL DEFAULT 1,
  created_at     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (tenant_id, user_id),
  UNIQUE KEY uq_app_user_email (tenant_id, email),
  KEY ix_app_user_slug (tenant_id, tenant_slug)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE sales_order (
  tenant_id     BIGINT UNSIGNED NOT NULL,
  order_id      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  customer_id   BIGINT UNSIGNED NOT NULL,
  order_state   ENUM('draft','placed','paid',
                    'shipped','cancelled','refunded') NOT NULL,
  placed_at     TIMESTAMP    NOT NULL,
  total_excl_tax  BIGINT   NOT NULL,
  total_incl_tax  BIGINT   NOT NULL,
  tax_minor       BIGINT   NOT NULL DEFAULT 0,
  currency        CHAR(3)     NOT NULL DEFAULT 'EUR',
  external_ref  VARCHAR(64)  NULL,
  PRIMARY KEY (tenant_id, placed_at, order_id),   -- partitioned, ch4.2
  KEY ix_so_tenant_placed (tenant_id, placed_at DESC),
  KEY ix_so_customer (tenant_id, customer_id),
  KEY ix_so_ref (tenant_id, external_ref(16))   -- prefix, ch3.4
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
PARTITION BY RANGE (placed_at) (
  PARTITION p2026_09 VALUES LESS THAN ('2026-10-01'),
  PARTITION p2026_10 VALUES LESS THAN ('2026-11-01'),
  PARTITION pmax     VALUES LESS THAN (MAXVALUE)
);
#   Note the ORDER of the primary key: the partition key must appear in
#   every unique key, so placed_at is in the PK. That is a consequence, not
#   a preference, and chapter 4.2 explains the trade it forces.

0.6 Conventions and how to read this guide

The conventions, and the six commands that answer most MySQL questions.

# Every command here is real and runnable. Flags are real. Where output is
# shown, it is representative rather than captured, and is labelled as such.
#
# 1. WHAT IS THE SERVER DOING RIGHT NOW?
SHOW FULL PROCESSLIST;
#   Time is in seconds and is the single most useful column. A query with a
#   large Time and State='Sending data' is usually a scan, not a network wait.
#   State='Locked' on a row means waiting on a lock, not holding one — the
#   holder is a different connection and is found with the innodb_lock_waits
#   query in chapter 4.3.
SELECT * FROM information_schema.innodb_trx
 ORDER BY trx_started LIMIT 20;
#   Every open transaction, with its age. A transaction older than a few
#   seconds is the cause of most lock waits and of every stalled purge.

# 2. WHAT IS THE PLAN, AND WHAT DID IT ACTUALLY COST?
EXPLAIN ANALYZE SELECT ...;
#   8.0.18+. Executes the query and reports estimated AND actual row counts
#   and time, in a tree. This is the single most valuable command in MySQL and
#   it is safe for SELECT. It is NOT safe for anything else.
#   Always compare the estimate with the actual. A 100x gap is the finding.

# 3. WHAT IS THE SCHEMA?
SHOW CREATE TABLE sales_order\G
SHOW INDEX FROM sales_order;
#   \G prints vertically. Use it for anything longer than about 80 columns.

# 4. WHAT ARE THE PERSISTENT VARIABLES?
SELECT VARIABLE_NAME, VARIABLE_VALUE
  FROM performance_schema.global_variables
 WHERE VARIABLE_NAME IN (
       'innodb_buffer_pool_size', 'innodb_redo_log_capacity',
       'innodb_flush_log_at_trx_commit', 'sync_binlog',
       'innodb_lock_wait_timeout', 'max_connections',
       'transaction_isolation', 'innodb_change_buffering')
#   performance_schema.global_variables rather than SHOW VARIABLES, because
#   this is queryable and joinable. SHOW VARIABLES is for a human at a prompt.

# 5. WHICH STATEMENTS ARE CUMULATIVELY EXPENSIVE?
SELECT digest_text,
       count_star,
       ROUND(sum_timer_wait / 1000000000000, 2) AS total_s,
       ROUND(avg_timer_wait / 1000000000, 2)    AS avg_ms,
       ROUND(sum_rows_examined / NULLIF(sum_rows_sent, 0), 1) AS examined_ratio
  FROM performance_schema.events_statements_summary_by_digest
 WHERE schema_name = 'shop'
 ORDER BY sum_timer_wait DESC LIMIT 20;
#   examined_ratio is the number to sort on. 1.0 is a perfect index lookup.
#   Above about 10 means rows are being read to be discarded, which is the
#   definition of a missing or wrong index. Chapter 5.

# 6. WHAT ARE THE INNODB STATUS COUNTERS SAYING?
SHOW ENGINE INNODB STATUS\G
#   A ~900-line report. The four sections that matter in an incident are
#   SEMAPHORES (contention), TRANSACTIONS (the history list length),
#   and the FILE I/O and INSERT BUFFER AND ADAPTIVE HASH INDEX sections.
#   Read it before changing anything, because the counter deltas tell you
#   which direction the problem is in.

How to read the diagnostic chapters. Chapters 5 and 6 are reference and work out of order. Chapters 1 through 4 build on each other and are worth reading in sequence the first time, because the type design in chapter 1 constrains the index options in chapter 3. Every chapter has a "diagnose" table in its later sections listing the symptom, the query that confirms it, and the parameter that fixes it — those are the tables to come back to during an incident.

Exercises 0

  1. Print every value of sql_mode on your server and on a target version, and diff them. For each removed or added mode, find a query in your codebase that behaves differently under it, and record the result. This is the highest-value ten minutes of any upgrade assessment.
  2. Measure the working set of your largest table: total data bytes plus total index bytes from information_schema.tables, and compare it to innodb_buffer_pool_size. Compute the ratio and state whether the hot set fits. Most systems discover it does not, and that indexes usually dominate.
  3. Run the string-PK detection query from section 0.4 across your entire schema. For every hit, determine whether the string form is the domain representation or an accident of an early decision, and write down the migration cost of changing it.
  4. Build the reference schema from section 0.5 on a scratch instance. Then run EXPLAIN on a query that filters on a column with no index and count the rows examined. Then add the index and re-run. Record both numbers, and repeat for the partition pruning behaviour.
  5. Set up performance_schema consumers if they are not on, wait for representative traffic, and produce the top-20 list by sum_timer_wait with the examined ratio. Sort by the ratio instead and compare — the two orderings are almost always different, and the second is the one that finds missing indexes.

# The three decisions, and what each one actually costs.
#
# 1. UNSIGNED. It doubles the positive range and has two real costs.
#
#    COST A: no arithmetic between signed and unsigned without a cast, because
#    MySQL will not let a value go silently negative. In a subtraction this
#    surfaces as a runtime error rather than a wrong answer, which is correct
#    but changes your code from "wrong" to "crashes".
SELECT CAST(-1 AS UNSIGNED);   -- 18446744073709551615, the wrap
SELECT BIGINT UNSIGNED col - 100 FROM t;
#   ERROR 1690 (22003): BIGINT value is out of range
#
#    COST B: an AUTO_INCREMENT on an unsigned column tops out at 2^64-1; on a
#    signed one at 2^63-1. In practice neither is reachable.
#
#    The real cost, and it is the reason people regret UNSIGNED:
#    a subtraction that should be negative becomes an error, so a query that
#    worked on a signed column fails. Keep the column signed unless you have
#    a specific reason, and use a CHECK constraint for the domain rule instead.
CREATE TABLE t (
  quantity     INT  NOT NULL DEFAULT 0,
  CONSTRAINT ck_quantity_nonneg CHECK (quantity >= 0)
);
#   The constraint states the domain, the column stays usable in arithmetic,
#   and the intent is readable. This is the better design in almost all cases.
#
#    CHECK constraints are ENFORCED in 8.0.16+. Before that they were parsed
#    and ignored, which is the single most dangerous version difference in the
#    type story: a constraint you believed was protecting data was not.

# 2. DISPLAY WIDTH WAS REMOVED. TINYINT(1) is now TINYINT.
#
#    Integer(N) no longer limits the range, and ZEROFILL was removed entirely.
#    The consequences: a migration that says INT(11) is meaningless, and code that
#    reads information_schema.columns.COLUMN_TYPE will see 'int' not 'int(11)'.
#
#    The one place the notation still carries meaning is TINYINT(1), which the
#    BOOL alias uses. It remains a display width and constrains nothing.
CREATE TABLE flags (is_active BOOLEAN NOT NULL DEFAULT true);
SHOW CREATE TABLE flags;
-- CREATE TABLE `flags` ( `is_active` tinyint(1) NOT NULL DEFAULT '1' )
--   So BOOLEAN is a spelling, not a type. It has no distinct behaviour and
--   no distinct storage. Readability only — which is worth having.

# 3. THE ALLOCATION-FREE CHOICES, which matter at scale.
#
#    A NOT NULL column with no default and no AUTO_INCREMENT is stored in the
#   row with no separate NULL bitmap entry, which is smaller and faster. The
#   rule: every column NOT NULL, always, and let the default live in the DDL.
#
#    Declaring a DEFAULT on a nullable column that is never left NULL buys
#   nothing and costs a byte per row. Declaring NOT NULL on a column that is
#   genuinely nullable costs you the ability to say "not set yet".
#
#    A BIGINT money column is 8 bytes. A DECIMAL(19,4) is a variable-length
#   binary-encoded decimal, roughly 9 bytes, and it is computed in software.
#   For money in minor units, BIGINT is smaller, faster and exact. Section 1.2.

1.2 DECIMAL, FLOAT and money

Three numeric types with genuinely different behaviour, and one of them should almost never be used for a monetary value.

TypeStorageExact?ArithmeticNever use for
FLOAT (4-byte)4 bytes✗ Binary. 0.1 is not representable and neither is 0.5 plus 0.2 exactlyHardware, fastAnything that must be exact. Money, quantities that must sum
DOUBLE (8-byte)8 bytes✗ Same problem at 15–17 significant digitsHardware, fastMoney, IDs, anything compared with = after arithmetic
DECIMAL(M,D)Variable, ~9 bytes for (19,4)✓ Base-10, exactly as writtenSoftware, slowerNothing, but consider BIGINT for minor units
BIGINT minor units8 bytes✓ Integer, exactlyHardware, fast, overflow-checkedAnything needing a fractional minor unit — a currency with 3 decimals, or a tax rate
# The failure, demonstrated rather than asserted.
#
#   With DOUBLE (or a FLOAT), money does not add up:
#     0.1 + 0.2 = 0.30000000000000004
#     19.99 * 100 = 1998.9999999999998
#   A shopping cart that is 0.0000000000004 off is a support ticket and, at scale,
#   a reconciliation failure that nobody can explain.
#
#   The comparison consequence is worse than the arithmetic consequence,
#   because a rounded value stored in a DOUBLE column and compared with =
#   against a literal may not match:
#
#     CREATE TABLE bad (price DOUBLE);
#     INSERT INTO bad VALUES (0.1 + 0.2);
#     SELECT * FROM bad WHERE price = 0.3;   -- returns 0 rows on some builds
#
#   With DECIMAL the same insert is exact and the comparison works, because
#   0.1 + 0.2 in decimal is exactly 0.3.
#
# THE THREE DEFENSIBLE DESIGNS, in order of preference.
#
# 1. BIGINT MINOR UNITS. The right answer for a currency with 2 decimals.
#    Storage 8 bytes, hardware arithmetic, exact, and the unit is in the name.
CREATE TABLE price_a (
  amount_minor  BIGINT  NOT NULL,
  currency      CHAR(3)    NOT NULL DEFAULT 'EUR',
  CONSTRAINT ck_price_a_nonneg CHECK (amount_minor >= 0)
);
INSERT INTO price_a VALUES (1999, 'EUR');      -- €19.99
INSERT INTO price_a VALUES (1999 + 1, 'EUR');  -- €20.00, exactly
#   Only wrong for a currency with 3 or 4 minor units (BHD, KWD, TND have 3;
#   CLF has 4). Store the exponent alongside the amount, or use DECIMAL.
#
# 2. DECIMAL(M,D). Correct for any currency, and for tax rates.
CREATE TABLE price_b (
  amount        DECIMAL(19,4) NOT NULL,
  tax_rate      DECIMAL(7,4)  NOT NULL,  -- 0.2000 = 20%
  CONSTRAINT ck_price_b CHECK (amount >= 0 AND tax_rate >= 0 AND tax_rate <= 1)
);
#   Note tax_rate is a RATE, not an amount, and is also money-ish. Storing
#   it as DECIMAL and enforcing a domain with a CHECK is the correct treatment.
#
#   The M matters: (19,4) allows 15 integer digits and 4 decimals. Sizing M
#   correctly matters because an over-wide DECIMAL wastes a byte per row on
#   every table, and an under-wide one fails on a value you did not predict.
#
# 3. MONEY. Do not use it.
#
#    The type is a locale-dependent, fixed 4-decimal, 64-bit signed integer with
#    a currency symbol for display only. The value is NOT scaled by the
#    currency, so 1.00 EUR and 1.00 USD are the same stored number, and the
#    format follows the lc_time_names session variable. Aggregating across
#    currencies by summing a MONEY column is arithmetically meaningless and
#    MySQL will not stop you.

# THE CALCULATION that makes the difference visible, for a real workload.
#
#   10 million orders, average 3 lines, 2 columns of money per line.
#   DECIMAL(19,4): ~9 bytes × 60 million values = 540 MB of table data, and
#   every SUM is a software loop.
#   BIGINT:        8 bytes × 60 million values = 480 MB, and SUM is a single
#   hardware instruction per row.
#   The 60 MB is not the argument. The SUM is: a nightly reconciliation over
#   DECIMAL can be an order of magnitude slower, and it runs at 3am.

Never use FLOAT or DOUBLE for money, ever, including for intermediate values in a calculation. The failure is silent, it compounds with row count, and it is discovered during a financial reconciliation when the discrepancy is too large to explain. If a library forces a float into your path — a JSON parser, a third-party API, a spreadsheet export — convert at the boundary and never store the float. `CAST(0.1 + 0.2 AS DECIMAL(19,4)) in the insert is the correct place for the conversion.

1.3 Strings, lengths and the utf8mb4 decision

CHAR, VARCHAR and TEXT differ in more than length, and the utf8mb4 decision is irreversible in a way that surprises people who arrive from MySQL 5.5.

CHAR(N)255 charactersFixed, N × charset maxlen, alwaysStripped on RETRIEVE unless PAD_CHAR_TO_FULL_LENGTH in sql_mode. Almost never stripped in practice because that mode is offRarely. Fixed-width codes only: ISO country codes, fixed-hash values
VARCHAR(N)65 535 bytes, i.e. 16 383 utf8mb4 characters1 or 2 length bytes plus the data. Rows may spill off-page at 65535 bytes totalPreserved, and significant to = in a non-_bin collationAlmost everything textual. The default choice
TEXT65 535 bytesOff-page with a 20-byte pointer, alwaysPreservedLarge documents, log bodies, JSON you are not indexing

# WHY VARCHAR(N) IS FASTER THAN TEXT, and when the difference matters.
#
#   VARCHAR(n) stores a 1-byte length prefix when n <= 255 and a 2-byte one
#   above, then the data inline in the row. TEXT stores a 20-byte pointer
#   inline and the data in overflow pages.
#
#   Consequences: a VARCHAR column's data is in the same page as the rest of
#   the row, so reading one column of a row reads the row. A TEXT column's data
#   may be on another page, so selecting it is a second random read.
#
#   For a table that fits in the buffer pool this is invisible. For a table
#   that does not, it is the difference between one I/O and two for every row
#   where the text is not needed. That is the "SELECT * is slow" case, and the
#   fix is to name the columns rather than to change the type.
EXPLAIN ANALYZE
SELECT '*' FROM article WHERE tenant_id = 42 ORDER BY published_at DESC LIMIT 20;
#   Look at 'rows examined' and the actual time. Now:
EXPLAIN ANALYZE
SELECT article_id, title, published_at, author_name
  FROM article WHERE tenant_id = 42 ORDER BY published_at DESC LIMIT 20;
#   The body column is a MEDIUMTEXT and is not in the list. This is usually a
#   5-20x improvement and it costs nothing but discipline.

# THE utf8mb4 DECISION. This is the one that cannot be walked back cheaply.
#
#   "utf8" in MySQL is NOT UTF-8. It is utf8mb3: an alias for a 3-byte-per-
#   character encoding that cannot represent a 4-byte code point. That is every
#   emoji, and it is the entirety of the supplementary planes.
#
#   Column definitions:  utf8mb3 VARCHAR(255) holds 255 CHARACTERS, max 765 bytes
#                         utf8mb4 VARCHAR(255) holds 255 CHARACTERS, max 1020 bytes
#   So converting a table from utf8mb3 to utf8mb4 requires a VARCHAR(255) to
#   become VARCHAR(191) to stay under the 767-byte index limit that applied in
#   5.6. That limit is gone, so in 8.0 you can convert without truncating — but
#   only if the index prefix is in ROW format, or you hit "Specified key was too
#   long; max key length is 3072 bytes".
#
#   The check to run BEFORE the upgrade:
SELECT table_name, column_name, character_set_name
  FROM information_schema.columns
 WHERE table_schema NOT IN ('mysql', 'information_schema', 'performance_schema', 'sys')
   AND character_set_name = 'utf8';
#   Any row returned is a table that will truncate a 4-byte character on insert
#   after the upgrade, and will fail with "Incorrect string value" the first time
#   somebody's name contains one. This is a real incident, not a theoretical one.
#
#   The conversion, per table, and the order matters:
#
#   ALTER TABLE t CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
#   -- rebuilds the table. A 200M-row table takes real time and real disk.
#
#   Set it on the SERVER and the DATABASE too, so new tables inherit it:
#   SET PERSIST character_set_server = 'utf8mb4';
#   SET PERSIST collation_server  = 'utf8mb4_0900_ai_ci';
#   ALTER DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
#
#   The connection charset must also be right, or a round trip through the
#   driver mangles it. Check it from the application, not the server config:
SELECT @@character_set_client, @@character_set_connection, @@character_set_results;
#   All three utf8mb4. If character_set_results is latin1, every string comes
#   back mojibake regardless of what is stored.

Watch the row size when converting to utf8mb4. Every VARCHAR can grow to 4 bytes per character. A table with 20 VARCHAR(255) columns goes from a 5 KB row to a 20 KB row, which exceeds the 65 535-byte row limit and can push a table from compact to DYNAMIC row format with a performance change. Check before you convert, not after: SELECT SUM(data_length) / table_rows FROM information_schema.tables is a good enough proxy, and for a very large table it is worth testing the conversion on a restored copy first.

1.4 Collations, comparison and the utf8mb4_0900 family

A collation decides what = means, which means it decides whether your unique index is correct. This is the most consequential setting in a text-heavy schema and the least examined.

CollationEquality forAccent-insensitiveCase-insensitiveIndex sizeUse

utf8mb4_0900_as_csCase and accent sensitive✗✗Largest — full character definition storedPasswords, exact-match identifiers, codes where case is significant
utf8mb4_0900_binByte-exact, and case-sensitive✗✗LargeHashes, opaque tokens, anything where you compare bytes not letters
utf8mb4_unicode_ciCase-insensitive, more UCA-correct than general_ci✓✓MediumUpgrade path from 5.7. Slower than the 0900 family, no longer the default

# The three collation questions, and the one that causes real bugs.
#
# 1. Does = mean what I think it means?
SELECT 'Straße' = 'STRASSE' COLLATE utf8mb4_0900_ai_ci;    -- 1
SELECT 'Straße' = 'STRASSE' COLLATE utf8mb4_0900_as_cs;    -- 0
SELECT 'ﬁ' = 'fi' COLLATE utf8mb4_0900_ai_ci;   -- 1: the ﬁ ligature
#   matches "fi". Correct for a name field, wrong for a document body.
#
# 2. A UNIQUE INDEX in a CI collation is case-insensitive. This is correct and
#    it is also the single most useful property of the default:
CREATE TABLE app_user (email VARCHAR(320) NOT NULL,
                       UNIQUE KEY uq_email (email));
INSERT INTO app_user VALUES ('Ada@Example.com');
INSERT INTO app_user VALUES ('ada@example.COM');
#   ERROR 1062: Duplicate entry 'ada@example.com' for key 'uq_email'
#   The two addresses are the same address, and the index knows it. This is
#   the behaviour you want for an email column, and it is free.
#
#   ... and the case where you must NOT rely on it:
#
#   Two genuinely different values that a CI collation considers equal. The
#   classic is a product code or an external reference where 'AB-1' and
#   'ab-1' are different products. A unique index will refuse the second one.
#   The fix is a collation on the COLUMN or the INDEX, not a change of the
#   table default:
ALTER TABLE product
  ADD COLUMN external_code VARCHAR(64)
      CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin NULL,
  ADD UNIQUE KEY uq_product_code (external_code);
#   A _bin collation compares bytes. It is also case-sensitive and
#   accent-sensitive, and it sorts in byte order rather than alphabet order.
#   For a password_hash or a token that is exactly the right behaviour.
#
# 3. MIXED COLLUSIONS. This one produces "Illegal mix of collations" and is
#    the most common MySQL error message a developer meets.
#
#    It happens when two columns with different collations are compared, or when
#    a literal takes the connection's default and the column has another.
SELECT * FROM t WHERE a = b;
#   ERROR 1267: Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT)
#                  and (utf8mb4_general_ci,IMPLICIT) for operation '='
#
#   It is a symptom, not a problem. The table was converted column by column
#   and something was missed. The fix is to normalise the schema, not to add
#   COLLATE to the query, which defers the problem and disables the index.
SELECT table_name, column_name, collation_name
  FROM information_schema.columns
 WHERE table_schema = 'shop' AND collation_name IS NOT NULL
 GROUP BY collation_name
 HAVING COUNT(*) > 0;
#   One row per collation used in the schema. More than one is a finding, and it
#   should be one row before the next deploy.
#
# SORTING. An ai_ci collation sorts 'A' before 'a' and 'á' with 'a', which is
# what a user expects from a name list. An _as_cs collation sorts uppercase
# first, because that is the byte order. Both are correct; choose per column.
SELECT display_name FROM app_user ORDER BY display_name;
SELECT display_name FROM app_user ORDER BY display_name COLLATE utf8mb4_0900_as_cs;
#   And the index consequence: ORDER BY a COLLATE expression cannot use the
#   index. If a column is sorted frequently, give the INDEX the collation that
#   the sort uses rather than casting at query time.

1.5 Dates, times, time zones and fractional seconds

MySQL’s temporal types store UTC and convert on display, which is correct and almost entirely unknown. The consequences run through backups, replication, migrations and every cross-timezone report.

TypeRangeFractional precisionAutomatic time-zone conversionUse for
DATE1000-01-01 … 9999-12-31NoneNoBirthdays, invoice dates, calendar dates. A date is not a moment
DATETIME1000 … 99990–6 digitsNo. Stored exactly as writtenAlmost never, which is why it is the source of the classic bug
TIMESTAMP1970-01-01 … 2038-01-190–6 digitsYes. Stored as UTC, converted to the session time_zone on read and on writeEvery moment in time. The right default
# THE DATETIME BUG, and why TIMESTAMP is the default that prevents it.
#
#   DATETIME stores the literal bytes. If your application is in Berlin and
#   your colleague is in Auckland, the two write values 9 hours apart for the
#   same instant, and no comparison ever notices.
#
#   TIMESTAMP stores UTC internally. Both applications write the same bytes for
#   the same instant, and the read is converted to the session time zone, so
#   each user sees local time and every comparison is correct.
>#
#   Set the connection time zone, always, on every connection:
#
#   PHP (PDO, on every connection):
#     $pdo->exec("SET time_zone = '+00:00'");
#   MySQL client / Drizzle / Prisma / Python (mysql-connector):
#     connection option time_zone='+00:00'
#
#   '+00:00' is correct. Naming a zone like 'Europe/Berlin' makes the server do
#   a lookup in the timezone tables, which are not always installed, and it
#   makes the conversion correct only if both ends agree on the name.
#
#   Read it back to prove it is set:
SELECT @@global.time_zone, @@session.time_zone, NOW(), UTC_TIMESTAMP();
#   With time_zone='+00:00', NOW() and UTC_TIMESTAMP() are the same. With a named
#   zone, NOW() is local and they differ by the offset. If they are equal, either
#   the server is UTC or the setting did not apply.
#
#   Load the timezone tables if you need named zones, and the cost is a restart:
#   mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql_tzdata_load;
#
# FRACTIONAL SECONDS. Default precision is 0, which means DATETIME(6) is opt-in.
#
#   Six digits is microseconds, and it costs 3 extra bytes per TIMESTAMP and
#   makes the column 8 bytes instead of 5. Six digits is a real decision: two
#   values that differ only in a microsecond compare as equal under
#   DATETIME(0), which matters for ordering and for a unique constraint.
#
#   For an event log, use DATETIME(6) and accept the size. For a business date,
#   do not: a created_at with microsecond precision is not more accurate, it is
#   only harder to read in a log.
#
# AUTO_UPDATE. Note that it is TIMESTAMP-only in 8.0 (DATETIME gained it in
# 5.6 but the semantics are worse), and that it fires on ANY change to the row:
#
#   UPDATE sales_order SET is_read = 1 WHERE order_id = 42;
#   -- updated_at is now changed, even though the business event was not.
#   -- Every "when did the customer last change anything" query is now wrong.
#   --
#   -- The reference schema therefore declares NO ON UPDATE, and the
#   -- application sets updated_at. It is a line of code in the repository layer
#   -- and it means the timestamp means what the name says.
#
# THE 2038 PROBLEM. TIMESTAMP tops out at 2038-01-19 03:14:07 UTC.
#   That is 12 years away. It is not urgent and it is completely solvable now:
SELECT CREATE TABLE audit (
  at TIMESTAMP(6) NOT NULL,
  event VARCHAR(64) NOT NULL
);
#   For anything that must outlive 2038 — a medical record, a financial
#   audit, an audit log with a retention requirement — use DATETIME(6) with the
#   application disciplined about UTC, or BIGINT microseconds since the epoch,
#   which has no limit and sorts correctly.
SELECT UNIX_TIMESTAMP(NOW(6)) * 1000000 AS micros_since_epoch;

1.6 JSON and generated columns

The native JSON type arrived in 5.7 and became usable in 8.0. It is not a replacement for columns, and generated columns are how you get most of its value without its costs.

# WHAT THE JSON TYPE ACTUALLY DOES.
#
#   • It VALIDATES on insert. Invalid JSON is rejected. That alone justifies it.
#   • It stores a BINARY representation that normalises whitespace and key order,
#     so two documents that differ only in formatting are the same value.
#   • You can index paths with a functional index (5.7+).
#
#   What it does NOT do: give you a schema. Nothing stops a document gaining a key
#   next week that nothing else knows about, and every consumer must handle it.
#
#   The rule: JSON for genuinely variable, genuinely opaque data — a webhook
#   payload, a third-party response, a user-defined settings blob. Columns for
#   anything you query, join, group or sort by.
#
#   The discipline that makes a JSON column work: a CHECK constraint stating the
#   required keys. That converts "every consumer validates" into "the database
#   validates once".
CREATE TABLE webhook_event (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id   BIGINT UNSIGNED NOT NULL,
  source      VARCHAR(64) NOT NULL,
  payload     JSON          NOT NULL,
  received_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY ix_webhook_tenant (tenant_id, received_at),
  #   Required shape, stated once, enforced on every write.
  CONSTRAINT ck_webhook_payload
      CHECK (JSON_CONTAINS_PATH(payload, 'all', '$.type', '$.id', '$.created'))
);
INSERT INTO webhook_event (tenant_id, source, payload) VALUES (
  42, 'github', JSON_OBJECT('type', 'push', 'id', 'abc', 'created', '2026-09-29'));
INSERT INTO webhook_event (tenant_id, source, payload) VALUES (
  42, 'github', JSON_OBJECT('wrong', 'shape'));
#   ERROR 3819: Check constraint 'ck_webhook_payload' is violated.

# GENERATED COLUMNS: the feature that makes JSON queryable at speed.
#
#   A STORED generated column is computed on write and physically stored. It
#   is a real column with a real index and is fast to read.
#   A VIRTUAL generated column is computed on read. It can be indexed, but the
#   index stores the value, so the read still avoids recomputation; the win is
#   that the base column stores nothing extra.
#   A PERSISTENT column is the MySQL 8.0.13+ spelling of STORED.
#   MySQL calls a generated column VIRTUAL by default. The other engines call it
#   GENERATED ALWAYS, and the default is STORED. The inversion surprises people
#   porting a definition between engines.
ALTER TABLE webhook_event
  ADD COLUMN event_type VARCHAR(32)
      GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(payload, '$.type'))) STORED,
  ADD COLUMN source_id VARCHAR(64)
      GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(payload, '$.id'))) STORED,
  ADD UNIQUE KEY uq_webhook_source (source, source_id);
#   Now the same unique constraint a normal column would give, with one source of
#   truth, and no application code that can forget to keep the two in step.
#   This is the pattern to reach for before you reach for denormalising a whole
#   table: promote the two or three JSON paths you actually query to columns.
#
#   One caution: JSON_EXTRACT on a deeply nested path is slow, and the
#   generated column is computed on EVERY insert, including the many that will
#   never be read. Keep the paths shallow and few. Six promoted paths is a
#   reasonable ceiling; thirty means you wanted a schema.
#
#   And a second: a generated column cannot be inserted into or updated, in
#   either form. That is the guarantee that makes it trustworthy, and it is why it
#   is better than a denormalised column an application maintains.

The decision procedure for a new table. For each attribute: is it queried, joined, grouped or sorted? If yes, it is a column. If no, and it is a fixed shape, it is still a column because a fixed shape belongs in the schema. If no, and it is genuinely variable, it is JSON. Then promote any JSON path that turns out to be queried — the promotion is a single ALTER with a generated column, it is online on 8.0, and it is reversible. Starting with everything in JSON and promoting is a valid strategy precisely because the promotion is cheap; starting with a wide table and demoting is not.

2.1 CREATE TABLE, engines and the options that matter

Four table options change behaviour rather than performance, and every one of them is a decision you should make explicitly rather than inherit.

# The four options that are behaviour, not performance.
>#
# 1. ENGINE=InnoDB. The default since 5.5 and the only choice discussed here.
#   Setting it explicitly on every table costs nothing and documents the
#   requirement in a schema dump.
>#
# 2. ROW_FORMAT. DYNAMIC is the 5.7+ default and is what you want. The
#   alternatives matter only for compatibility with a very old server.
#   COMPACT      5.6 default. 8126-byte row limit, no off-page storage for
#     overflow except the 20-byte BLOB/TEXT pointer, no variable-length
#     prefix compression. The limit is the problem: a row of long VARCHARs
#     can fail to insert.
#   REDUNDANT    pre-5.6. Stores every column at its maximum length. Wastes
#     space and is fast for fixed rows. Essentially never correct.
#   COMPRESSED    the row is compressed, tablespace only, needs KEY_BLOCK_SIZE
#     tuning. Saves space, costs CPU, and the benefit shrinks as the buffer
#     pool grows. Not a default choice; a considered one for cold archival data.
#
#   Verify what a table actually has, because it can differ from the server
#   default after an upgrade or a dump restore on an older instance:
SELECT table_name, row_format, engine, table_collation
  FROM information_schema.tables
 WHERE table_schema = 'shop' AND table_name = 'sales_order'\G

# 3. CHARSET and COLLATE. Set them explicitly. The utf8mb4 decision from
#   chapter 1 is made here and nowhere else.
>#
#   Order of precedence, which is worth knowing when a dump round-trips:
#   column > table > database > server
#   A SHOW CREATE TABLE that displays a collation on every single column is
#   telling you the table default is NOT being inherited — check why.
>#
# 4. STATS_PERSISTENT. The default since 8.0 and the correct setting. It keeps
#   index cardinality statistics in the data dictionary, so they survive a
#   restart. Before 8.0 they lived in memory and were lost, which is why a
#   server that had been up for a while and one that had just restarted made
#   different query plans for the same data. If you are debugging "why did the
#   plan change", this was a cause for years and is no longer.
>#
#   For a table with a very skewed distribution, sample pages more often than
#   the default. InnoDB samples 20 pages and extrapolates; on a table where a
#   single tenant is 40% of the rows, that extrapolation is wrong and the planner
#   believes it. One line, and it is the fix for a whole class of "the plan is
#   wrong for one tenant" problems.
ALTER TABLE sales_order STATS_PERSISTENT = 1, STATS_SAMPLE_PAGES = 64;
ANALYZE TABLE sales_order;
#
#   The trigger for doing this: the planner's estimate for a tenant is off by
#   more than an order of magnitude and the plan changes with the tenant. The
#   diagnostic is section 5.4 — compare rows estimated against rows actual in
#   EXPLAIN ANALYZE and check whether the ratio is stable across tenants.

# THE DDL ITSELF, in the order that makes it readable.
CREATE TABLE sales_order (
  tenant_id       BIGINT UNSIGNED  NOT NULL COMMENT 'owning tenant; in every PK',
  order_id        BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT COMMENT 'per-tenant sequence',
  customer_id     BIGINT UNSIGNED  NOT NULL,
  order_state     ENUM('draft','placed','paid',
                          'shipped','cancelled','refunded')  NOT NULL,
  placed_at       TIMESTAMP(3)     NOT NULL,
  total_excl_tax  BIGINT          NOT NULL,
  total_incl_tax  BIGINT          NOT NULL,
  external_ref    VARCHAR(64)     NULL DEFAULT NULL,

  # KEY declarations first, then constraints. This is the mysqlpump
  # order and it is a good one: the reader sees the access paths before
  # the rules.
  PRIMARY KEY (tenant_id, order_id),
  UNIQUE KEY uq_so_external (tenant_id, external_ref),
  KEY ix_so_placed (tenant_id, placed_at DESC),
  KEY ix_so_customer (tenant_id, customer_id),

  # COMMENT on every column is not documentation theatre: SHOW CREATE
  # TABLE, SHOW COLUMNS and every admin tool surface it, so this is the
  # only schema documentation that lives with the schema.
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  ROW_FORMAT=DYNAMIC
  STATS_PERSISTENT=1
  COMMENT='customer orders; partitioned by month, retained 7 years';

Why a MySQL-specific DDL practice differs from other engines. MySQL requires indexes to be declared inside CREATE TABLE (or added by ALTER), has no schema-qualified default like public, uses ENUM as a first-class type, and supports prefix indexes which no other engine does. A schema designed for MySQL and ported to PostgreSQL needs work; the reverse is also true. If a product must run on both, keep the DDL in the migration layer where the dialect can differ, and never assume the two are interchangeable.

Six constraint types, what each one actually does at write time, and the specific failure each one prevents. The cost column is the part that is usually skipped and is the reason constraints get removed under performance pressure.

# CHECK constraints: the ones worth writing, and the one to never write.
>#
#   A CHECK that restates what the column type already guarantees is noise:
#     CONSTRAINT ck_bad CHECK (total_excl_tax >= 0)  -- on an UNSIGNED column
#   The column already refuses a negative. It says nothing and it is checked.
#
#   A CHECK that restates a FOREIGN KEY is worse — it is a second, weaker
#   version of the same rule that will drift from the real one.
#
#   A CHECK that states a rule the database CANNOT otherwise know is valuable:
ALTER TABLE sales_order
  ADD CONSTRAINT ck_so_tax_not_excessive
      CHECK (total_incl_tax >= total_excl_tax),
  ADD CONSTRAINT ck_so_totals_bounded
      CHECK (total_incl_tax <= 1000000000),   -- €10,000,000.00 ceiling
  ADD CONSTRAINT ck_so_external_shape
      CHECK (external_ref IS NULL OR CHAR_LENGTH(external_ref) >= 4);
#   The first is a genuine cross-column invariant that no single column can
#   express. The second is a domain bound that stops a unit error — a value in
#   cents where euros were expected would be a billion and would be caught.
#   The third is a shape rule on a nullable column, which is exactly the case
#   NOT NULL cannot express.

# ENUM: the cost model, which is not obvious and bites on a big table.
>#
#   An ENUM is stored as an index into a list held in the table definition.
#   Storage is 1 byte for up to 255 values, 2 bytes beyond.
#
#   ALTER TABLE ... MODIFY order_state ENUM(...)
#   REWRITES THE WHOLE TABLE if any existing value's index changes.
#   - Appending a value at the END: no existing index changes. INSTANT on 8.0.29+
#     for the metadata, and a fast copy otherwise. Safe.
#   - Inserting in the MIDDLE: every value after it shifts. Full rewrite. On a
#     200M-row table this is an hour and double the disk.
#   - Removing a value: shifts everything after it. Rewrite.
#
#   So: APPEND ONLY, ALWAYS, AND NEVER REORDER. Write your ALTER scripts in
#   chronological order so a new state is appended, not inserted where it would
#   "logically" belong. This is the single most important ENUM rule and it is
#   violated constantly, usually by someone tidying the list.
ALTER TABLE sales_order
  #   MODIFY order_state ENUM('draft','placed','paid','shipped','cancelled',
  #                     'refunded','partially_refunded')   -- appended, not inserted
  #                      , ALGORITHM=INPLACE, LOCK=NONE;
#   ALGORITHM=INPLACE asserts that no copy is needed. If the change would need
#   one, the statement ERRORS instead of silently locking the table. This is
#   the same technique as MySQL 8.0's ALGORITHM assertion and it should be in
#   every production migration. See 2.5.

# ENUM versus a lookup table. The honest comparison.
>#
># ENUM wins when:
#   - the set is genuinely closed and controlled by you
#   - the value is never displayed to a user with a name of their own
#   - the value must be validated, and the validation belongs in the schema
#   order_state: 'paid' is an internal state, has no user-facing name, and must
#   not be misspelled. ENUM is exactly right.
>#
># A lookup table wins when:
#   - the value carries attributes: a label, a sort order, a colour, a colour,
#     a next-state graph, an SLA, or a colour
#   - a user or an admin must be able to add one without a migration
#   - the value must be localised
#   order_state with 'what the customer sees' and 'is it terminal' and 'which
#   state may follow' is a lookup table with a small state-transition table.
>#
># The thing people get wrong: an ENUM that needs a "label" column soon after
# creation. That is the signal it should have been a lookup table. When you
# find yourself writing CASE order_state WHEN 'draft' THEN 'Draft' END,
# convert it before it is in a hundred places.

2.3 Defaults, generated columns and expressions

Defaults are the least-understood part of a schema, and the interaction between a default, a generated column and an application-set value is where timestamps go wrong.

# DEFAULT behaviours, and the two that are not what they look like.
>#
# 1. BLOB/TEXT columns CANNOT have a literal default before 8.0.13. From
# 8.0.13 an expression default is allowed, and the expression is evaluated
#   ONCE AT INSERT unless it is wrapped in parentheses.
#
#   This is the rule that catches everybody:
CREATE TABLE t1 (b BLOB  DEFAULT ('abc'));
#   The parentheses are REQUIRED. Without them, 8.0 accepts the literal but
#   stores the string "abc" as the default, rather than the bytes.
#
#   And for TIMESTAMP, the default-vs-on-update behaviour differs when you
#   add parentheses:
CREATE TABLE t2 (
  a TIMESTAMP NOT NULL DEFAULT (CURRENT_TIMESTAMP),               -- literal, immutable
  b TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP, -- expression, updates
  c TIMESTAMP NOT NULL DEFAULT (CURRENT_TIMESTAMP)
                     ON UPDATE (CURRENT_TIMESTAMP)                 -- expression, updates
);

# 2. NO DEFAULT means the column is implicitly nullable with an implicit
#   NULL default. The word IMPLICIT matters: it is not the same as writing
#   DEFAULT NULL, but it behaves the same for inserts.
>#
#   So `col INT` and `col INT NULL` and `col INT NULL DEFAULT NULL` are
#   equivalent, and all three are a column you forgot to think about. The
#   rule: no column gets a default you did not write down.

# AUTO_INCREMENT, and the three ways it goes wrong.
>#
#   MUST be a key. It may be part of a composite key (the reference schema
#   does this) or the key itself.
ALTER TABLE sales_order MODIFY order_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT;

>#   (a) GAPS ARE PERMANENT. The counter is not rolled back when a transaction
#   fails, because the value was allocated. This is correct and it is required
#   for concurrent insert safety. Never write a schema that assumes contiguity.
#   A migration that inserts 1000 rows "with ids from 1 to 1000" is broken.
#
#   (b) auto_increment_lock_mode. The default since 5.7.8 is 2, which is the
#   simple lock mode: interleaved, maximum throughput, and it burns ids on
#   rollback. Modes 0 and 1 are batch allocations that reduce lock contention at
#   the cost of larger gaps. Do not change this.
SELECT @@innodb_autoinc_lock_mode;
#
#   (c) The per-table counter is exactly why a multi-tenant schema wants a
#   COMPOSITE key with tenant_id first: tenant 42 and tenant 43 each have their
#   own sequence, so order numbers are short (4 digits instead of 12) and a
#   global counter never becomes a contention point on the busiest tenant.

# GENERATED COLUMNS, and the two constraints on them.
>#
>#   Constraint 1: the expression must be IMMUTABLE. A non-deterministic or
#   time-dependent function is refused.
ALTER TABLE sales_order
  ADD COLUMN bad  VARCHAR(32) GENERATED ALWAYS AS (UUID()) STORED;
#   ERROR 3106 (HY000): Expression of generated column contains disallowed
#   function: 'uuid'
#
#   Constraint 2: it cannot be inserted into or updated. That is the point,
span class="c">#   and it is why a generated column beats a denormalised column an application
span class="c">#   maintains — it cannot be wrong.
#
#   The pattern worth standardising: a generated column that carries a sortable,
#   indexable, normalised form of a value you also store in human-readable form.
#   Store the display form for humans, generate the lookup form for machines,
#   and never let an application keep the two in step.
CREATE TABLE app_user (
  tenant_id      BIGINT UNSIGNED NOT NULL,
  user_id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  email          VARCHAR(320) NOT NULL,
  display_name   VARCHAR(255) NOT NULL,
  # Generated: the lower-cased, trimmed form, indexed for the login lookup.
  # Login becomes SELECT ... WHERE email_normalised = ? and an index
  # range scan, instead of a full scan with LOWER() on both sides.
  email_normalised VARCHAR(320)
      GENERATED ALWAYS AS (LOWER(TRIM(email))) STORED,
  is_active      TINYINT(1) NOT NULL DEFAULT 1,
  created_at     TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (tenant_id, user_id),
  UNIQUE KEY uq_user_email (tenant_id, email_normalised),
  KEY ix_user_display (tenant_id, display_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

2.4 Foreign keys: the real cost and when to omit them

A foreign key in InnoDB is not a cheap assertion. It takes a shared lock on the parent row on every child write, it changes the delete semantics of the parent, and it can deadlock. The decision to include one should be made per relationship, and the default should be deliberate.

# WHAT THE CONSTRAINT ACTUALLY DOES, mechanically.
>#
#   ON INSERT/UPDATE OF THE CHILD: InnoDB takes a shared (S) lock on the
#   parent row to prove it exists. An S lock on a row that another transaction
#   holds X on becomes a LOCK WAIT.
#
#   ON DELETE OF THE PARENT: whatever the ON DELETE rule says, and the default
#   is RESTRICT, which means the parent delete FAILS if a child exists.
#
#   That is the shape of the problem: a hot parent row — a customer, an
#   account, a product — becomes a lock that serialises every child write from
#   every transaction that touches it. One customer with a lot of activity is one
#   contended row, and it will show up as a lock-wait timeout at 3am.

# The lock, observed. This is the query you run when you see lock waits.
SELECT r.trx_id            AS waiting_trx,
       r.trx_mysql_thread_id AS waiting_thread,
       r.trx_query          AS waiting_query,
       TIMESTAMPDIFF(SECOND, r.trx_wait_started, NOW()) AS wait_secs,
       b.trx_id            AS blocking_trx,
       b.trx_mysql_thread_id AS blocking_thread,
       b.trx_query          AS blocking_query,
       TIMESTAMPDIFF(SECOND, b.trx_started, NOW()) AS blocking_age,
       # The rows each transaction is holding and waiting for. This is
       # the actual answer to "what is blocking what".
       (SELECT GROUP_CONCAT(locked_table) FROM
          (SELECT CONCAT(object_name) AS locked_table
             FROM performance_schema.data_locks
            WHERE engine_transaction_id = b.trx_id) x) AS held_tables
  FROM information_schema.innodb_trx r
  JOIN information_schema.innodb_lock_waits w
    ON w.requesting_trx_id = r.trx_id
  JOIN information_schema.innodb_trx b
    ON b.trx_id = w.blocking_trx_id
>#
>#   innodb_lock_waits and innodb_lock_waits are deprecated in 8.0 in favour of
#   performance_schema.data_lock_waits, which is more precise and joins cleanly
#   to data_locks. Use performance_schema on 8.0+.

# THE LOCK_WAIT_TIMEOUT IS A SAFETY NET, and it is set per session.
SELECT @@innodb_lock_wait_timeout;      # default 50 seconds
SELECT @@lock_wait_timeout;             # metadata locks, default 31536000 = 1 YEAR
#
#   The second one is the one that causes "the deploy hung". A DDL statement
#   waits for a metadata lock, which any open transaction holding a long-running
#   SELECT prevents. The default is effectively infinite, so an ALTER after a
#   migration blocks forever and looks like a server hang rather than a wait.
#
#   SET SESSION lock_wait_timeout = 5;  before every DDL statement. The statement
#   then fails fast with a clear error, and you retry it when the long
#   transaction has finished. This belongs in every migration script.

# THE THREE OPTIONS, and when each is right.
>#
# 1. KEEP IT. For a low-volume parent whose children must not be orphaned:
#    tenant, address, country, plan, product variant. These tables are small,
#    rarely written, and a wrong row in them corrupts the meaning of many rows
#    elsewhere. The lock cost is on the parent, which is cold. This is the case
#    the constraint was designed for and it is nearly free.
ALTER TABLE sales_order
  ADD CONSTRAINT fk_so_tenant
      FOREIGN KEY (tenant_id) REFERENCES tenant (tenant_id)
      ON DELETE RESTRICT ON UPDATE RESTRICT;

# 2. OMIT IT AND ENFORCE IN THE APPLICATION, DOCUMENTED. For a high-volume
#    parent — customer, order — where the lock cost is real and the orphan risk
#    is low because the parent is only ever soft-deleted:
#    - the FK cannot be expressed anyway, because it would need a composite
#      index on the parent and the parent's PK is on a different column pair
#    - the parent is never hard-deleted, so RESTRICT would never fire anyway
#    - a scheduled reconciliation job finds orphans hourly and the SLA for
#      detecting one is one hour, which is acceptable for a deleted customer
#
#    The discipline that makes this honest: the reconciliation query runs on a
#    schedule, its result is alerted on a non-zero count, and the decision is
#    recorded in the schema COMMENT. An undocumented omission is a defect; a
#    documented one with a detection mechanism is a design.
SELECT COUNT(*) AS orphan_lines
  FROM sales_order_line l
  LEFT JOIN app_user u
    ON u.tenant_id = l.tenant_id AND u.user_id = l.customer_id
 WHERE u.user_id IS NULL AND l.created_at > NOW() - INTERVAL 1 HOUR;
#
# 3. CASCADE. Almost always wrong in an OLTP system. ON DELETE CASCADE on an
#    order deletes its lines, its payments, its shipments and its audit entries,
#    in one transaction, holding locks on all of them for the duration. It is
#    correct for derived rows and catastrophic for anything you would want to
#    keep for an audit. A cascade is irreversible and it is not in the database's
#    backup, because the backup was taken after the cascade.
#
#    For the 1-in-a-million case where a hard delete really is required, do it
#    with a script that DELETEs children in dependency order in batches, takes
#    a verified backup first, and records every id it touched. Slower, and it is
#    possible to observe and reverse. A cascade is none of those things.

2.5 ALTER TABLE and the online DDL matrix

The single most useful MySQL configuration habit, and the matrix that tells you which operations are actually online.

# ALWAYS ASSERT THE ALGORITHM. This is the highest-value habit in this chapter.
>#
#   Without it, MySQL silently picks the safest-for-correctness option, which
#   for most operations means a full table copy with an exclusive metadata lock.
#   With it, MySQL ERRORS if it cannot honour the request. An error in staging
#   at 11:00 is worth an hour of downtime at 03:00.
>#
>#   ALGORITHM=INSTANT   metadata only, no row is read or written. Sub-second on
>#                      a 500M-row table.
>#   ALGORITHM=INPLACE   no table copy, but rows may be rebuilt. Brief exclusive
>#                      metadata lock at the start and at the end.
>#   ALGORITHM=COPY     reads every row, writes a new table, swaps. Exclusive
>#                      metadata lock for the WHOLE duration. On a large table this
>#                      is an outage wearing a disguise.
>#
>#   LOCK=NONE         permits concurrent reads AND writes during INPLACE.
>#   LOCK=SHARED       permits concurrent reads, blocks writes.
>#   LOCK=EXCLUSIVE    blocks everything for the duration. What COPY does by default.
>#
>#   Asserting both is the correct form. The pair is also a tripwire: a change
>#   that silently requires a table copy from now on will fail in CI rather than
>#   in production.
ALTER TABLE sales_order
  ADD COLUMN source_channel VARCHAR(32) NULL,
  ALGORITHM=INSTANT;
>#
>#   The error you get when the assertion fails is explicit and useful:
span class="c">>#     ERROR 1846 (0A000): ALGORITHM=INSTANT is not supported for this operation.
#     Try ALGORITHM=COPY/INPLACE.
#
>#   To find out what an operation WOULD do without doing it:
ALTER TABLE sales_order
  ADD COLUMN test_col TINYINT NULL, ALGORITHM=INPLACE, LOCK=NONE;
SHOW WARNINGS;

# THE MIGRATION FORM. Every production DDL statement gets all four parts.
>#
#   1. SESSION lock_wait_timeout  — fail fast rather than hang on a metadata lock
#   2. lock_wait_timeout           — the one above; the wait is what needs bounding
#   3. ALGORITHM=...               — assert the mechanism
#   4. LOCK=...                    — assert the concurrency guarantee
#
#   Plus a retry loop in the migration runner, because a metadata lock conflict
#   is transient and a lock_wait_timeout failure should be retried, not alerted
#   on. A migration that gives up at the first timeout is worse than one that
#   retries ten times with backoff.
#
#   And the pre-flight check, which is the one that turns a migration from a
#   gamble into a measurement: how big is the table, really, and how long will
#   the copy take at this rate.
SELECT table_name,
       table_rows                                    -- approximate; see note,
       ROUND(data_length  / 1024 / 1024) AS data_mb,
       ROUND(index_length / 1024 / 1024) AS index_mb,
       ROUND((data_length + index_length) / 1024 / 1024) AS total_mb
  FROM information_schema.tables
 WHERE table_schema = 'shop' AND table_name = 'sales_order';
#
#   table_rows is an ESTIMATE from the statistics, and on a table that has never
#   been ANALYZYZEd it can be out by a factor of ten. For a migration, use the
#   exact count on a restored copy, or accept the estimate and add margin. The
#   migration that assumed 2M rows on a 40M-row table is the incident.

>#   The metadata-lock diagnostic, for when a migration IS blocked:
SELECT * FROM performance_schema.metadata_locks
 WHERE OBJECT_SCHEMA = 'shop' AND LOCK_STATUS = 'PENDING'\G
#   PENDING means your ALTER is queued behind something. Find what:
SELECT * FROM performance_schema.metadata_locks WHERE LOCK_STATUS = 'GRANTED'\G
#   Then correlate the blocking thread id with innodb_trx and kill the long
#   transaction. The usual culprit is a reporting query that has been open for
#   two hours, or a replication applier waiting on a lock it will never get.

The failure nobody plans for: DDL is not transactional in MySQL. A multi-statement migration that fails after the third statement leaves the schema partly migrated, and re-running it depends entirely on the statements being idempotent. Write every migration statement to be safely re-runnable — ADD COLUMN IF NOT EXISTS where available, an existence check in a procedure where it is not, and never a bare CREATE TABLE without a guard. And always set lock_wait_timeout, because the default is one year and a hung migration looks exactly like a hung server.

2.6 Views, temporary tables and the rest of the DDL surface

The remaining schema objects, and the one that causes an entire class of performance problem by accident.

# VIEWS: a security boundary with a performance cost that is easy to miss.
>#
#   A MERGE view is folded into the calling query. Fast, and the optimiser can
#   push predicates down into the base table's indexes.
#
#   A TEMPTABLE view is materialised into a temporary table first. The cost is
#   paid on every query, and the materialised result has NO indexes.
#
#   MySQL decides. A view containing GROUP BY, DISTINCT, UNION, aggregate
#   functions, window functions or LIMIT becomes TEMPTABLE. It does not tell you.
#
#   Ask, every time you are about to add a view to a hot path:
#
CREATE VIEW v_order_summary AS
SELECT tenant_id, order_state, COUNT(*) AS n, SUM(total_incl_tax) AS revenue
  FROM sales_order GROUP BY tenant_id, order_state;
EXPLAIN FORMAT=JSON SELECT * FROM v_order_summary WHERE tenant_id = 42\G
#   "materialized_from_subquery" or "MATERIALIZED" in the plan means TEMPTABLE.
#   Every WHERE on a TEMPTABLE view is applied AFTER the aggregation, so the
#   query scans every row of every tenant and then throws most of them away. This
#   is the classic "the report endpoint is slow" and it is invisible without
#   EXPLAIN. Push the tenant predicate INTO the view's own WHERE clause so it
#   participates in the base table scan.
>#
>#   The two view behaviours that are security-relevant:
#
#   DEFINER: a view is executed with the privileges of its DEFINER, not of the
#   invoker, unless it is created SQL SECURITY INVOKER. A view created by root
#   and left as DEFINER gives any account with SELECT on the view full access to
#   everything the definer can see. This is the single most dangerous default in
#   MySQL and it is the reason to ALWAYS write SQL SECURITY INVOKER.
#
#   A view that hides rows based on a session variable is a well-known way to
#   build a broken row-level security layer: the variable is set by the
#   application, so a direct connection with the variable set defeats it. If you
#   need row-level security, use it at the table level where it cannot be
#   set by a client. (MySQL has no native RLS; this is the closest available
#   and it is a mitigation, not a control.)
#
CREATE SQL SECURITY INVOKER VIEW v_active_orders AS
SELECT order_id, customer_id, order_state, placed_at, total_incl_tax
  FROM sales_order
 WHERE tenant_id = @tenant_id
   AND order_state IN ('placed','paid','shipped');
#   Mergeable (no aggregation), so the tenant predicate reaches the index.

>#
># TEMPORARY TABLES, and why they are more dangerous than they look.
#
#   A TEMPORARY table is created in a per-session temporary tablespace and is
#   NOT visible to other sessions. Two consequences that catch people:
#
#   1. You cannot CREATE TEMPORARY TABLE inside a stored routine or a
#   trigger. A migration or a procedure that needs one must create it first.
#
#   2. A table with the SAME NAME in a temporary tablespace SHADOWS the base
#   table for that session. If a session creates TEMPORARY TABLE sales_order
#   and then a trigger fires and references sales_order unqualified, the
#   trigger reads the TEMPORARY table. This is a genuine, hard-to-debug MySQL
#   failure mode, and the fix is to always qualify: shop.sales_order.
#
#   temp_tablespaces controls the default, and the total temp space used is
#   not bounded by any setting you control. A single runaway temporary table
#   can fill the disk, and the error it produces is about the temporary
#   file, not about the real cause. Monitor tmpdir space, not just the data
#   directory.
#
CREATE TEMPORARY TABLE tmp_order_calc (
  order_id  BIGINT UNSIGNED PRIMARY KEY,
  net_cents BIGINT         NOT NULL
) ENGINE=InnoDB;
#   An index on the temp table is not optional. Without it, a join against a
#   500k-row temp table is a full scan per outer row, and the query that was
#   fast in staging is quadratic in production.

A quick schema review that catches most MySQL-specific defects. For every table: is the engine InnoDB; is the charset utf8mb4 with the intended collation; is every column NOT NULL unless nullable is genuinely meaningful; does every column have a COMMENT; are the constraint names present and prefixed; is every ENUM append-only in the migration history; and does every foreign key have a deliberate delete rule. Six questions, about two minutes per table, and it catches the majority of what goes wrong in a schema that grew quickly.

3.1 B-tree indexes and how they are used

The clustered primary key and the secondary indexes built on top of it, and the physical consequence that makes almost every MySQL index fact true.

# THE CLUSTERED INDEX IS THE TABLE. This one fact explains most of InnoDB.
>#
#   Rows are stored in a B-tree keyed by the PRIMARY KEY. There is no other
#   place a row lives. Consequences, in order of how often they bite:
span class="c">#
# 1. THE PK IS THE PHYSICAL ORDER. A range scan on the PK is a sequential read
#    of the pages. The same range on a secondary index is random. This is why
#    "ORDER BY primary_key" is free and everything else sorts.
#
# 2. A WIDE PK MAKES EVERY ROW WIDE. The key is stored in every row AND in
#    every secondary index entry. A 36-byte CHAR(36) UUID primary key costs 36
#    bytes in every row and in every index on the table. This is the strongest
#    argument against UUID primary keys, and it is a physical one, not a taste
#    one. A BIGINT surrogate plus a UNIQUE index on the natural key is faster
#    and about the same size once you count the secondary index.
#
# 3. A SECONDARY INDEX IS NARROWER THAN THE ROW. It contains the indexed
#    columns PLUS the primary key, and nothing else. This is why every secondary
#    index on the table is at least PK-width bytes per entry, and why a table
#    with a UUID PK and six indexes has seven copies of that UUID.
#
# 4. EVERY SECONDARY INDEX IS A BACK MAPPING TO THE CLUSTERED INDEX. A lookup
#    by secondary index finds the PK, then does a second B-tree lookup in the
#    clustered index. This is why a covered query is so much faster, and why
#    "rows examined" in EXPLAIN counts BOTH lookups.
#
# 5. A RANDOM PRIMARY KEY FRAGMENTS THE B-TREE. An AUTO_INCREMENT appends to
#    the rightmost page. A UUID(7) with a timestamp prefix is nearly as good.
#    A UUID(4) is random and splits pages constantly, which is page splits,
#    which is write amplification, which is buffer pool churn. On a write-heavy
#    table this is the difference between a fast insert and a slow one.
#
# 6. WITHOUT A PRIMARY KEY, InnoDB CREATES A HIDDEN 6-BYTE ROW ID. It is
#    monotonic within a table but not guaranteed unique across a restore, and
#    every secondary index still points at it. Never ship a table without a PK.
#

# THE THREE WAYS AN INDEX IS USED. Learning to tell them apart is most of
# the skill.
>#
# 1. REF. A range of key values. `WHERE tenant_id = 42 AND placed_at > X`
#    finds a start and an end in the B-tree. The one to design for.
#
# 2. RANGE SCAN. A contiguous range. `WHERE placed_at BETWEEN X AND Y`. Same
#    mechanism, but if the range is a large fraction of the table the planner
#    will prefer a full table scan, because reading 40% of a table sequentially
#    is genuinely cheaper than 40% of it randomly. The crossover is typically
#    around 20-30% of the table, and it depends entirely on the selectivity.
#
# 3. INDEX SCAN, covering. Every column the query needs is IN the index, so
#    the clustered index is never touched. This is the fastest an InnoDB query
#    can be, and it requires the index to contain the primary key too - which it
#    it does automatically, so a covering index needs no extra declaration.
#

>#   WHERE tenant_id = 42 AND order_state = 'paid'   ← uses ix_so_placed's prefix
#
#   Extra: Using index; Using where                     ← NOT covering
#   Rows examined is higher than rows returned, so a second lookup happened.
#
#   WHERE tenant_id = 42 AND order_id = 8817
#   Extra: Using index                                   ← COVERING. The index
#   contains tenant_id, order_id and implicitly the whole PK, so the row was
#   never read from the clustered index.
#

# THE SARGABILITY RULES, which determine whether an index can be used at all.
>#
#   ✗ Non-sargable: the column is wrapped in a function, so the index value
#     cannot be compared to the transformed value.
#
#     WHERE DATE(placed_at) = '2026-09-29'
#     WHERE YEAR(placed_at) = 2026
#     WHERE total_incl_tax * 1.2 < 10000
#
#     WHERE email LIKE '%@example.com'      ← leading wildcard, always a scan
#     WHERE email LIKE 'ada@%'             ← sargable: a prefix match
#
#
#   ✓ The rewrite for the date case is a RANGE, which is sargable and uses the
#     index perfectly:
#
#     WHERE placed_at >= '2026-09-29 00:00:00'
#       AND placed_at <  '2026-09-30 00:00:00'
#
#
#   The one place a generated column earns its keep, and it is exactly this:
#
#   ALTER TABLE sales_order
#     ADD COLUMN placed_date DATE AS (DATE(placed_at)) STORED,
#     ADD KEY ix_so_placed_date (tenant_id, placed_date);
#
#   Then `WHERE placed_date = '2026-09-29'` uses the index. The comparison on
#   TIMESTAMP(0) is not equivalent — a placed_at of 09:29:47 is not in the
#   range 00:00:00–00:00:00. Write the range predicate, not the equality on a
#   truncated column, and accept that it is correct without a new index.
#
#
#   ✗ Implicit conversion kills an index just as effectively, and this is the
span class="c">#   one from section 0.4 — a VARCHAR compared to an integer. The column is
#   wrapped in a cast, whether you asked for it or not.

How to prove an index is being used, rather than assuming. EXPLAIN shows the plan. EXPLAIN ANALYZE shows the plan and the real numbers, which is strictly better and safe for SELECT. The comparison to make every time is rows examined against rows returned: a ratio of 1.0 is a perfect lookup, 3 is acceptable, and above about 10 means the index is being used for a small part of the row set and the query is still reading far more than it needs. That ratio, not the plan shape, is the finding.

# FULLTEXT, used correctly. The three things that surprise people.
>#
# 1. A MINIMUM LENGTH, default 4. Words shorter than that are not indexed at all,
#    so a search for "ai" or "go" returns nothing unless you configure it.
#
# 2. A STOPWORD LIST, and 50% of a language is stopwords. "the", "and", "of"
#    are not in the index. A search for "the" legitimately returns nothing.
#
# 3. IT CANNOT FIND A PREFIX. A word must be complete, and the match is on a
#    stem. Searching for "data" does not find "database". Searching for a part
#    of a word does not find the word.
#
CREATE FULLTEXT INDEX ft_article_body ON article (title, body)
  WITH PARSER ngram;   -- for CJK and other no-space languages

SELECT article_id, title,
       MATCH(title, body) AGAINST ('synchronisation lag' IN NATURAL LANGUAGE MODE) AS score
  FROM article
 WHERE MATCH(title, body) AGAINST ('synchronisation lag' IN NATURAL LANGUAGE MODE)
 ORDER BY score DESC LIMIT 20;
#   IN NATURAL LANGUAGE MODE  relevance-ranked, 50% of rows ignored (the 50%
#     is deliberate: a term in most documents carries no information)
#   IN BOOLEAN MODE      +, -, *, "exact phrase", (group) and no ranking
#   WITH QUERY EXPANSION auto-adds words found in matching rows. Usually a
#     mistake, because it silently widens every query.
#
#   Test the index rather than trusting it:
SET SESSION innodb_ft_aux_table = 'shop/ft_article_body';
SELECT * FROM information_schema.INNODB_FT_INDEX_TABLE;
#
#   4. FULLTEXT index maintenance is expensive on write. Every insert into a
#   FULLTEXT-indexed column updates the inverted index. On a write-heavy table
#   this dominates the write cost. Measure it before adding one to a hot table.
#

># VECTOR, for embeddings. 9.0+ in InnoDB.
>#
#   The tradeoff is set AT INDEX TIME and cannot be changed without a rebuild:
#     lists = N   how many centroids. More lists = more partitions = better
#   recall, more memory, slower build. Rule of thumb: lists = rows / 1000
#   per dimension, but measure recall rather than trusting the formula.
#
#   The index is HNSW-based, so distance is a graph walk, not a scan. Recall
#   is a function of the M parameter and the data, and the only way to know
#   your recall is to compare against a brute-force search on a sample.
#
CREATE TABLE document_embedding (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    BIGINT UNSIGNED NOT NULL,
  doc_id       BIGINT UNSIGNED NOT NULL,
  model        VARCHAR(64)      NOT NULL,   -- dimension is implied by model
  embedding    VECTOR(768)   NOT NULL,
  PRIMARY KEY (id),
  KEY ix_de_tenant (tenant_id),
  VECTOR INDEX vix_de (embedding) WITH (lists = 50)
) ENGINE=InnoDB;

SELECT doc_id, VEC_DISTANCE_COSINE(embedding, CAST('[0.1, ...]'
       AS VECTOR(768))) AS dist
  FROM document_embedding
 WHERE tenant_id = 42
 ORDER BY dist
 LIMIT 10;

#   cannot use the index and silently does a full scan. Store the model name
#   alongside the vector, because cosine and inner product give different
#   answers and you will eventually need both.

3.3 Multicolumn indexes and column order

The leftmost-prefix rule, the equality-before-range rule, and the two cases where a widely-accepted rule of thumb is wrong.

# THE LEFTMOST PREFIX RULE, stated precisely.
>#
# An index on (a, b, c) can be used for:
#   a                    ← a is a range or a ref, that is all that is used
#   a, b                 ← a ref, b ref or range
#   a, b, c              ← all three
#   a, c                 ← NOT USED as an index range, though MySQL's index
#                       condition pushdown may use c to filter within the a
#                       range, which is a different and much weaker thing
#   b                    ← NOT USED at all
#   b, c                 ← NOT USED at all
#
# So a query filtering only on (b) needs a SEPARATE index on (b), whatever
# else the composite index contains. This is the mistake people make most
# often: one wide composite index and an assumption that it covers everything.
#

# THE EQUALITY-BEFORE-RANGE RULE, and why it is more a guideline than a law.
>#
# The rule: put all equality-matched columns first, then the range column last.
# Because a range ends the usable prefix, (tenant_id, status, placed_at)
# serves "tenant = 42 AND status = 'paid' AND placed_at > X" fully, whereas
# (tenant_id, placed_at, status) stops at placed_at and filters status after.
#
#   WHERE TWO CASES WHERE THE RULE IS WRONG, and both are common:
#
#
#   CASE 1: THE EQUALITY COLUMN IS LOW-CARDINALITY. `status` has six values
#   and 'paid' might be 80% of the rows. Putting it first produces a range
#   that is most of the table, and the following column cannot narrow it. In
#   practice, put the low-cardinality equality column LAST and let the range
#   column lead, so the range is as narrow as possible. Measure, do not reason.
#
#   CASE 2: COVERING CHANGES THE PRIORITY. If including a column in the index
#   lets a query skip the clustered index lookup, that can be worth more than
#   any ordering optimisation. A wider index that is covering beats a narrow one
#   that is not, for a read-heavy query. There is no rule here, only a
#   measurement with EXPLAIN ANALYZE.
#

># The reference schema's access paths, each justified by a real query.
>#
#
#   PRIMARY KEY (tenant_id, order_id)
#   Single-tenant order lookup, and it is the clustered index, so the row is
#   physically adjacent to every other order for that tenant. Point lookups and
#   "my last 20 orders" are both fast because of this.
#
#   ix_so_placed (tenant_id, placed_at DESC)
#   "orders in a date range" and "latest orders" — the single most common query
#   in the product, and DESC lets the planner walk backwards for the "latest".
#
#   ix_so_customer (tenant_id, customer_id)
#   "orders for this customer". customer_id alone is useless — it would match
#   orders across every tenant, so tenant_id must lead. This is why the tenant
#   column is first in EVERY index in a multi-tenant schema, without exception.
#
#   uq_so_external (tenant_id, external_ref)   UNIQUE
#   Idempotency: "have we already imported this external order?" It is a
#   constraint first and an access path second, which is the correct order of
#   importance. Prefix length is 16 — see 3.4.
#
#   The index deliberately MISSING: (tenant_id, order_state). Six values, a
#   very low cardinality, and a "show me all open orders" query is a range
#   scan of the tenant's orders followed by a filter. That is acceptable and
#   an index on it would rarely be chosen. Adding it "just in case" is the
#   most common form of index bloat. See 3.6.
#

# A worked column-ordering decision, with the measurement that settled it.
>#
#   Query: "the 50 most recent orders for a customer in a date window".
#   Two candidate indexes:
#
#     A: (tenant_id, customer_id, placed_at DESC)   equality, equality, range
#     B: (tenant_id, placed_at DESC, customer_id)    equality, range, equality
#
#   The rule of thumb says A. The measurement said otherwise, because the
#   customer has 3,000 orders and the window is 30 days of 400, so the range
#   in B is 400 rows of the whole tenant and customer_id filters within that,
#   while A reads 3,000 rows to find the recent ones. B wins by 7x.
#
EXPLAIN ANALYZE
SELECT order_id, placed_at, total_incl_tax
  FROM sales_order
 WHERE tenant_id = 42
   AND placed_at >= '2026-09-01'
   AND customer_id = 8817
 ORDER BY placed_at DESC LIMIT 50;
#   Look for three things in the output, in this order:
#     1. the index chosen           — did the planner agree with the guess?
#     2. actual rows vs estimate    — a 10x gap means the statistics are wrong
#     3. rows examined vs returned  — the 7x shows up here and nowhere else

3.4 Prefix, functional and invisible indexes

Three MySQL-specific index capabilities that solve problems the standard index cannot, each with a sharp edge that has to be stated.

# PREFIX INDEXES: the MySQL feature no other engine has, and the reason MySQL
># is faster at some string lookups than PostgreSQL.
>#
#   KEY ix (col(16)) indexes only the first 16 CHARACTERS. The index entry is
#   small, so more of them fit on a page, and a lookup is a range scan over
#   16 characters rather than 320.
#
#   THE SHARP EDGE, stated once and clearly: the index can be used to FIND
#   candidate rows, and the full value is then compared. So a prefix index
#   does NOT give you uniqueness.
#
#   MySQL refuses it outright, which is the correct behaviour and the reason
#   the following is an important thing to know rather than an accident:
#
#   UNIQUE KEY uq (col(16))   → ERROR 1170: BLOB/TEXT column used in key
#   specification without a key length
#
#   For the reference schema's external_ref, the requirement is idempotency:
#   "this import must not create a second row". A prefix index cannot enforce
#   that, so the full column is indexed:
#
ALTER TABLE sales_order
  #  For LOOKUP ONLY, where a 16-character prefix is enough to find the
  #  candidate and the rest is compared after. Correct, fast, and honest:
  ADD KEY ix_so_ref_lookup (tenant_id, external_ref(16));
#
  #  For UNIQUENESS, the full column. No prefix allowed:
  ADD UNIQUE KEY uq_so_external (tenant_id, external_ref(64));
#
#  A PREFIX + A UNIQUE INDEX is the correct pattern when you need both and
#  the unique index is too big. The unique index guarantees correctness; the
#  prefix index makes the common lookup fast. The prefix index is pure
#  optimisation and can be dropped at any time with no correctness cost.
#

# FUNCTIONAL INDEXES: index an expression. 8.0.13+.
>#
#   A generated column is a stored functional index. A functional index is the
#   computed-at-read version, which costs nothing to store and more to read.
#
#   Prefer a GENERATED COLUMN. It is visible in SHOW CREATE TABLE, it is
#   queryable directly, and it does not require the exact expression to be
#   written identically in every query — which is the failure mode of a
#   functional index. MySQL matches the expression by exact text, so
#   LOWER(email) and lower(email) are the same function, but LOWER( email )
#   with a space is NOT, and neither is LOWER(CONCAT(email, ' ')).
#
ALTER TABLE sales_order
  ADD KEY ix_so_ref_lower ((LOWER(external_ref)));
#
SELECT order_id FROM sales_order
 WHERE LOWER(external_ref) = 'abc-123';
#   For a column with a collation that is already case-insensitive, this index
#   is pointless — the existing index already matches case-insensitively. Add
#   a functional index for LOWER() only where the column is _bin, and then
#   a case-insensitive SEARCH becomes a sargable indexed lookup that a plain
#   LIKE on a _bin column could never be.
#
#   The pattern for a suffix search, which LIKE '%.pdf' cannot use and which
#   is the only way to do it inside MySQL:
ALTER TABLE document
  ADD KEY ix_doc_ext ((SUBSTRING(file_path, -4)));
SELECT * FROM document WHERE SUBSTRING(file_path, -4) = '.pdf';
#

># INVISIBLE INDEXES: 8.0.0+. The safe way to test an index removal.
>#
#   Making an index INVISIBLE keeps it maintained on write — so the index
#   still costs its full write overhead — but the optimiser ignores it. Read
#   performance is unchanged for every query that did not use it.
#
#   The procedure, which is the correct way to remove an index from production:
#     1. ALTER TABLE ... ALTER INDEX ix_x INVISIBLE;   -- instant, metadata only
#     2. Wait one full business cycle, including a weekly report and a
#        month-end, because those are the queries that use indexes nothing
#        else touches
#     3. Check slow query log and performance_schema for any new bad plan
#     4. Only then DROP the index, which rebuilds nothing but does take the
#        space back
#
#   For a UNIQUE index, making it invisible also removes the uniqueness
#   constraint, so duplicates can be inserted. That is a real behaviour change
#   and it is the one thing to be careful about. Check for duplicates FIRST.
#
#   -- Before hiding a unique index, prove it is currently satisfied:
SELECT external_ref, COUNT(*) AS n
  FROM sales_order
 WHERE external_ref IS NOT NULL
 GROUP BY tenant_id, external_ref HAVING n > 1;   -- must return zero rows

Prefix length is a guess, and a wrong guess is silent. If your external references share a 16-character prefix — and they often do, because they come from one system and share a prefix like ORD-2026-EU — a prefix index of 16 discriminates nothing: every row is a candidate and the index is pure cost. Measure the discrimination before choosing the length, not after: SELECT COUNT(DISTINCT LEFT(col, N)) / COUNT(*) FROM t for a few values of N, and pick the smallest N where the ratio is close to 1. That single query prevents the most common reason a prefix index exists and does not help.

3.5 How the optimizer chooses an index

Cost-based optimisation with cardinality estimates, the three statistics that drive it, and how to make it choose correctly when it does not.

# THE ALGORITHM, in one paragraph: for each candidate plan, estimate the cost
# of every step, sum them, and pick the cheapest. The estimate of "how many
># rows will this step touch" comes from index statistics, and everything wrong
# with a MySQL plan is downstream of a wrong cardinality estimate.
>#
# THE THREE STATISTICS THAT MATTER.
>#
# 1. CARDINALITY PER INDEX PREFIX. InnoDB samples pages and extrapolates,
#    default 20 pages. It stores the number of distinct values per index
#    prefix, and assumes UNIFORM distribution between the distinct values.
#
#    That uniformity assumption is where it breaks. One tenant with 40% of the
#    rows, 4000 tenants with 15% each, and the estimate for every tenant is
#    total_rows / 4001, which is 26x too small for the big one and 26x too
#    large for the small ones. A multi-tenant system is exactly the shape that
#    breaks this assumption, and it is not a rare shape.
#
# 2. HISTOGRAM ESTIMATES. 8.0+. Per-column, per-bucket distributions for
#    skewed columns, which is the correct answer to the problem above.
#
#    ANALYZE TABLE t UPDATE HISTOGRAM ON tenant_id WITH 256 BUCKETS;
#
#    This is the single highest-value tuning command in MySQL 8.0 for a
#    multi-tenant system, and almost nobody uses it. Check whether histograms
#    exist before tuning anything else:
#
#      SELECT table_name, column_name, n_distinct, hist_size, n_bins
#        FROM information_schema.column_statistics;
#
#    A histogram is STATS_SAMPLE_PAGES independent and STATS_PERSISTENT
#    independent, and it is rebuilt by ANALYZE TABLE. It costs disk in the
#    data dictionary and a little time to compute. On a large table the
#    histogram is sampled too, so it is an estimate of a skewed
#    distribution, not a census.
#
# 3. CORRELATION BETWEEN COLUMNS. The planner multiplies marginal
#    selectivities. If tenant_id and order_state are correlated — and in a
#    multi-tenant system they often are, because one tenant may never have
#    'refunded' orders — the product is wrong and there is no fix in MySQL.
#
#    PostgreSQL has CREATE STATISTICS for exactly this. MySQL does not. The
#    workaround is to make the columns correlated in a COMPOSITE INDEX,
#    which stores the joint distribution and fixes the estimate. Section 3.3.
#

># THE THREE HINT VARIABLES. Use them last, and always with a comment saying why.
>#
SELECT * FROM information_schema.optimizer_trace\G
> trace: [ {
  "steps": [ {
    "join_type": "range",
    "rows_estimation": [ {
      "table": "sales_order",
      "possible_keys": [ "PRIMARY", "ix_so_placed" ],
      "chosen_key": "ix_so_placed",
      "access_type": "ref",
      "rows_estimation_per_key": { "tenant_id": "12", "placed_at": "N/A" },
      "filtered": "1.00", // ← 1.00 means no WHERE filtering
      "using_index": null,
      "cost": "3.21"
    } ] } ] } ]
#   THIS IS THE MOST USEFUL SINGLE DIAGNOSTIC IN MySQL. optimizer_trace is
#   enabled per session and off by default because it is expensive and

InnoDB implements multi-version concurrency control: a consistent read is assembled from the undo log rather than blocking a writer, and writers exclude one another with exclusive locks on index records only. That design gives readers the throughput of MVCC and writers the correctness of row-level exclusion, but it makes observable behaviour depend jointly on three things — the isolation level, which index the optimiser chose to reach the row, and the order in which two transactions happen to touch it. This chapter fixes the vocabulary first (lock types, lock modes, deadlock detection) and then works through the three failure modes that account for most production incidents on MySQL: phantom reads and the gap locking that suppresses them, lock wait timeouts and deadlocks, and long-running transactions that pin the undo history. It is written against the InnoDB behaviour of MySQL 9.x, with the places where 8.0 and 8.4 differ called out explicitly.

4.1 The isolation level matrix

Each isolation level is a promise about which anomalies a transaction may observe. The difficulty is that the four level names do not correspond to the same set of anomalies in MySQL as they do in the SQL standard, because MySQL separates the read view used by non-locking reads from the data used by locking reads.

InnoDB never takes a shared lock for a plain SELECT. Instead it reads the newest version of a row whose trx_id is below the current read view, and walks the undo chain to find the version that was current at the moment the read view was taken. The read view is created at the start of the transaction for START TRANSACTION WITH CONSISTENT SNAPSHOT, and otherwise at the first consistent read. Locking reads — SELECT … FOR UPDATE, SELECT … FOR SHARE, and the legacy LOCK IN SHARE MODE — deliberately bypass the read view and read the latest committed version, taking locks as they go. That divergence between snapshot reads and current reads is the single most important fact in this chapter; it is why a transaction at REPEATABLE READ can legitimately update a row that a FOR UPDATE in the same transaction just read at a different value, and why a non-locking read and a locking read in the same statement will not necessarily see the same data.

-- Effective level, session scope wins over global
SELECT @@session.transaction_isolation AS session_level,
       @@global.transaction_isolation  AS global_level,
       @@global.transaction_read_only  AS read_only;

COMMIT;

The difference in observable behaviour is easiest to see with two connections. At REPEATABLE READ, two reads of the same row inside one transaction return the same value regardless of what a concurrent writer committed in between. At READ COMMITTED, each consistent read takes a fresh read view, so the second read sees the new value. Writes are always visible to their own transaction at every level — InnoDB merges the transaction’s own changes into the result rather than presenting a pure snapshot.

SERIALIZABLE deserves a specific warning, because it is rarely what an operator intends when they set it. A plain SELECT that carries no usable index cannot be covered by a next-key lock on a bounded range, so InnoDB locks the entire table and readers serialise behind the writer. On InnoDB the usual way to obtain serialisable behaviour is to write the predicate so that an index bounds it, not to raise the isolation level. Likewise, READ UNCOMMITTED is offered for completeness and is used by reporting replicas that genuinely want last-writer values; on InnoDB it also disables the gap-locking behaviour that REPEATABLE READ provides, so it is not a safe substitute for READ COMMITTED.

Read view lifetime. The read view survives for the whole transaction at REPEATABLE READ, which is exactly why a transaction that stays open for hours holds an increasingly old view: it also keeps the undo versions that view depends on alive. That coupling between isolation level and undo retention is what makes section 4.6 an isolation-level problem as much as a client-behaviour problem.

4.2 Why MySQL’s REPEATABLE READ is not the SQL standard’s

The standard defines REPEATABLE READ so that a re-read of a predicate is evaluated against the current state of the data and phantoms are excluded by blocking the inserter. MySQL excludes phantoms with next-key locks on the same transaction’s locking reads, and with a snapshot for its non-locking reads — which produces the strongest guarantee of the four, and the most contention.

Under the standard’s definition, a transaction that reads WHERE status = 'pending' and re-reads it should see the same result set, and the implementation is expected to prevent new rows matching the predicate from appearing by locking the range. MySQL does the locking part only for locking reads, and does it on index ranges. If the query has no index on status, InnoDB cannot construct a bounded next-key range and instead takes a next-key lock over the whole scanned space — which at REPEATABLE READ means effectively the entire table for that predicate. This is the mechanism behind a class of incident where a single SELECT … FOR UPDATE on an unindexed column serialises an application that otherwise runs concurrently.

The corollary is that the guarantee scales with the quality of the plan. A locking read of the form WHERE tenant_id = ? AND created_at > ? FOR UPDATE with an index on (tenant_id, created_at) locks a bounded interval of records and the gaps around them. The same statement with the index removed locks everything. Tuning the access path is therefore a precondition for the isolation level behaving as designed, and it is the reason a query review that ignores FOR UPDATE is incomplete.

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

   AND  status = 'pending'

Quantifying the switch. The operational result of moving a mixed OLTP workload from REPEATABLE READ to READ COMMITTED is not marginal: where no workload component genuinely requires a long-lived consistent snapshot, the share of statements failing with ERROR 1213 (deadlock) typically falls by around 90%, and the lock waits that remain are row-level rather than range-level, so they clear in milliseconds instead of escalating into whole-transaction rollbacks. Treat that ratio as a prior rather than a result and reproduce it against a copy of production traffic, because a workload that reads a wide range and then writes inside it — report generation, back-office batch edits, ETL checkpointing — loses precisely the protection gap locking was providing. The reduction is a property of the isolation level, not of the release: 8.0, 8.4 and 9.x behave identically here.

What the switch does not break. Two commonly cited guarantees survive a move to READ COMMITTED on MySQL 9.x with the default binlog_format = ROW. Statement atomicity is unaffected: a failed statement is rolled back in full regardless of isolation level. And the statement-level atomicity that row-based replication depends on is unaffected. What does change is the guarantee that two reads of the same predicate agree, so any application logic that reads, decides, and writes across more than one statement must be rewritten to be a single atomic statement — UPDATE … SET col = col + 1 WHERE id = ?, or a compare-and-set with a version column — before the switch is safe. mysqldump --single-transaction is unaffected in practice, because mysqldump sets REPEATABLE READ for its own session and requests START TRANSACTION WITH CONSISTENT SNAPSHOT regardless of the global default.

Replication and READ COMMITTED. With binlog_format = ROW, READ COMMITTED is safe for replication. With STATEMENT it is not: a transaction that reads a row twice can write the two different values to the binary log, and the replica will diverge. MySQL reports this as an unsafe-statement condition rather than silently diverging, but the correct fix is ROW, which is the default from 8.0 onward. On 5.7 hosts being upgraded, check binlog_format before changing transaction_isolation, not after.

4.3 Lock types, modes and the compatibility matrix

InnoDB locks records, the gaps between them, and the boundary between the two, in shared or exclusive mode, and the compatibility matrix across those modes determines whether a statement proceeds or blocks. Intention locks exist so that a table-level reservation can be expressed without touching every row.

Five lock types appear in performance_schema.data_locks and in the deadlock report. Record locks index records, not table rows, so a statement that reaches the same row through a different index takes a lock the previous statement did not take. Gap locks are pure intervals in an index with no record of their own; they are purely inhibitive and never contain data. A next-key lock is the leftmost record of a gap plus the gap itself, and is what a range scan of more than one record actually acquires. Insert intention locks are gap locks with a different purpose: they signal the position at which a new record is about to be inserted, so that two transactions inserting different keys into the same gap do not conflict with one another. The auto-increment lock is not a row lock at all; it protects the counter in AUTO_INCREMENT columns and is governed by innodb_autoinc_lock_mode, which defaults to 1 (consecutive) in MySQL 8.0 and later and was 2 (interleaved) in 5.6 and 5.7.

Intention locks are table-level. IS is recorded when a transaction holds at least one shared row lock, and IX when it holds at least one exclusive one. They exist to answer one question cheaply: may another transaction lock this table exclusively? Without them, a transaction that intends to take an exclusive lock on every row of a table would have to acquire each row lock first and only then discover the conflict — during which time other transactions would have started work it cannot now abort safely.

innodb_lock_wait_timeout governs InnoDB row and index locks only, and is expressed in whole seconds. lock_wait_timeout governs metadata locks — the locks that protect the definition of a table, not its data — and its default is one year, so a blocked ALTER TABLE waits effectively forever. Setting innodb_lock_wait_timeout = 5 therefore has no effect on a DDL statement that appears to hang, and the inverse is equally true. When diagnosing, identify which kind of lock is involved first: a query blocked on rows shows up in data_lock_waits, while a DDL blocked on metadata shows up in performance_schema.metadata_locks with LOCK_STATUS = 'PENDING' and the blocking statement is usually a long-running transaction that is not waiting for anything at all.

The victim is chosen by amount of work undone, not by age or by arrival order: InnoDB rolls back the transaction that has modified the fewest rows, using the number of undo log records as the tie-breaker.        rl.OBJECT_SCHEMA, rl.OBJECT_NAME, rl.INDEX_NAME,
       rl.LOCK_TYPE, rl.LOCK_MODE, rl.LOCK_DATA
FROM   performance_schema.data_lock_waits AS w
JOIN   performance_schema.data_locks AS rl
       ON rl.ENGINE_LOCK_ID = w.ENGINE_REQUESTING_LOCK_ID
JOIN   performance_schema.data_locks AS bl
       ON bl.ENGINE_LOCK_ID = w.ENGINE_BLOCKING_LOCK_ID
JOIN   performance_schema.threads AS rw
       ON rw.THREAD_ID = w.REQUESTING_THREAD_ID
JOIN   performance_schema.threads AS bw
       ON bw.THREAD_ID = w.BLOCKING_THREAD_ID
LEFT JOIN information_schema.INNODB_TRX AS rt
       ON rt.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID
LEFT JOIN information_schema.INNODB_TRX AS bt
       ON bt.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID;

1213 and 1205 are not interchangeable. ERROR 1213 (deadlock) rolls back the entire transaction; the client must replay all of its work, and any work performed outside the database in the same unit — an email sent, a row written to a queue by another system — is not rolled back with it. ERROR 1205 (lock wait timeout) rolls back only the failing statement by default, and the transaction survives; innodb_rollback_on_timeout = ON changes that to a full rollback, but the default remains statement-level. Every retry loop must therefore be written to be safe under both, with a bounded attempt count, exponential backoff and full jitter. A retry loop without jitter synchronises the contending transactions and converts a rare deadlock into a correlated storm.

Metadata locks produce the other blocking class, and it behaves nothing like a deadlock: there is no cycle, so nothing detects it, and a single open SELECT holds a shared metadata lock for the whole of its transaction. A pending ALTER TABLE waiting for an exclusive metadata lock then blocks every new query that touches the same table, behind it, in the metadata lock queue. The application looks entirely dead while the database reports low CPU and no running queries.

SELECT ml.OBJECT_TYPE, ml.OBJECT_SCHEMA, ml.OBJECT_NAME,
       ml.LOCK_TYPE, ml.LOCK_DURATION, ml.LOCK_STATUS,
       t.PROCESSLIST_ID, t.PROCESSLIST_TIME, t.PROCESSLIST_STATE
FROM   performance_schema.metadata_locks AS ml
JOIN   performance_schema.threads AS t
       ON t.THREAD_ID = ml.OBJECT_INSTANCE_BEGIN
WHERE  ml.LOCK_STATUS = 'PENDING'
ORDER  BY ml.LOCK_STATUS, t.PROCESSLIST_TIME DESC;

When a DDL is the blocker, kill the DDL. A pending DDL holds the queue and stalls new traffic, whereas the long-running transaction that holds the shared metadata lock is usually a background job whose work is idempotent. Cancelling the DDL releases the queue immediately; the transaction can be left alone or killed and retried later. Setting lock_wait_timeout on the DDL session so it gives up on its own is the more disciplined variant, and LOCK TABLES … NOWAIT plus ALTER TABLE … ALGORITHM=INSTANT remove the class of incident entirely. Note that innodb_lock_wait_timeout has no effect on any of this — it does not apply to metadata locks.

4.5 Savepoints, nested rollback and statement atomicity

A savepoint is a marker inside an open transaction that allows a partial rollback without discarding the work done before it. It is the only way to undo part of a unit of work in MySQL, and its two limitations — locks are not released, and non-transactional engines are not rewound — are what separate it from a savepoint in some other systems.

START TRANSACTION;

INSERT INTO ledger (tenant_id, entry_id, delta_cents)
VALUES (42, 1, -19900);
SAVEPOINT after_debit;

INSERT INTO ledger (tenant_id, entry_id, delta_cents)
VALUES (42, 2,  19900);
SAVEPOINT after_credit;

INSERT INTO ledger (tenant_id, entry_id, delta_cents)
VALUES (42, 3,    500);

ROLLBACK TO SAVEPOINT after_credit;

SELECT COUNT(*) AS rows_after_credit FROM ledger
 WHERE tenant_id = 42 AND entry_id = 3;
-- 0    the third entry never happened

COMMIT;
SELECT entry_id, delta_cents FROM ledger
 WHERE tenant_id = 42 ORDER BY entry_id;
-- 1 | -19900
-- 2 |  19900

ROLLBACK TO SAVEPOINT rewinds the transaction to the named marker and leaves the transaction open. It does not release row locks acquired after that marker, it does not reset auto-increment counters, it does not undo changes made to non-transactional tables such as MyISAM or to tables in the NDB engine under some configurations, and it cannot undo the effects of a statement that modified a non-transactional table. RELEASE SAVEPOINT only removes the marker; it commits nothing and releases no locks. After a savepoint rollback the transaction remains read-write and may be rolled back to an earlier savepoint, or to the start of the transaction with a bare ROLLBACK.

SET autocommit = 0;
SELECT @@autocommit;    -- 0, the transaction is now open

INSERT INTO tenants (id, slug) VALUES (42, 'acme');
INSERT INTO tenant_keys (tenant_id, k_id, k_secret)
VALUES (42, 1, 'k-7f3a');
ROLLBACK;              -- both statements are discarded

-- A single statement is atomic regardless of level
INSERT INTO tenant_keys (tenant_id, k_id, k_secret)
VALUES (42, 1, NULL);  -- ERROR 1048 (23000): Column 'k_secret'
-- cannot be null. Nothing was inserted.

Two related semantics trip up code that assumes transactional defaults. First, with autocommit = 0, ROLLBACK discards the work of the open transaction and ends it, but a subsequent COMMIT then commits an empty transaction — the statements are not deferred. Second, MySQL commits implicitly at points where other systems do not: before and after every DDL statement, when START TRANSACTION is issued while a transaction is already open, and when an autocommit = 1 statement begins a new transaction. A stored procedure containing a CREATE TABLE in the middle of a batch therefore commits everything that preceded it, and no amount of ROLLBACK recovers it.

Where savepoints earn their keep. Batch loads are the standard case: a job that must either apply 200 000 rows or apply nothing is best expressed as one transaction, and a failure at row 199 000 should not force a re-run from the beginning. Wrapping each chunk in a savepoint, and rolling back to the last good marker on a per-row error, converts a total loss into a bounded one. The cost is that InnoDB cannot free the undo for a savepoint rollback until the transaction commits, so a long-running batch with many savepoints holds a long undo history — the same problem as section 4.6, in a different costume. On non-transactional engines the pattern is not safe at all: ROLLBACK TO SAVEPOINT will not undo a MyISAM or Aria write, so the “bounded loss” becomes a partial write plus a reported success.

4.6 The long-running transaction problem

A transaction that stays open does more than hold its own locks. It pins the undo history, which prevents purge from reclaiming space, lengthens every version-chain traversal in the instance, and turns the history list length into a proxy for how far behind the oldest reader is. On a write-heavy table this is the failure mode that produces disk exhaustion under no obvious load.

The diagnostic question is always the same — how old is the oldest open transaction, and what is it doing — and the answer is usually surprising, because an idle-in-transaction session has no statement running and therefore no visible query. information_schema.INNODB_TRX.trx_query is NULL for such a session, which is the field most monitoring rules check and most alerting rules then discard as empty. Age must be computed from trx_started, and the connection id from trx_mysql_thread_id.

SELECT trx.trx_id,
       trx.trx_state,
       TIMESTAMPDIFF(SECOND, trx.trx_started, NOW()) AS age_s,
       TIMESTAMPDIFF(MINUTE, trx.trx_started, NOW()) AS age_min,
       trx.trx_mysql_thread_id                      AS conn_id,
       trx.trx_isolation_level,
       trx.trx_rows_locked,
       trx.trx_rows_modified,
       trx.trx_is_read_only,
       LEFT(COALESCE(trx.trx_query, '<idle>'), 100) AS query,
       p.PROCESSLIST_USER, p.PROCESSLIST_TIME, p.PROCESSLIST_STATE
FROM   information_schema.INNODB_TRX AS trx
LEFT JOIN information_schema.PROCESSLIST AS p
       ON p.ID = trx.trx_mysql_thread_id
ORDER  BY trx.trx_started
LIMIT  50;

Read-only transactions deserve separate attention because they are the easiest to overlook and the most damaging. A transaction that only runs SELECT statements takes no row locks, so it never appears in data_lock_waits and never causes a deadlock, yet it holds a read view and therefore prevents purge from advancing past its start time. A report endpoint that opens a transaction, streams a large result, and then holds the connection in a pool is the canonical instance of this. The mitigation is structural rather than tuning: release the read view promptly by completing the transaction, and if streaming must be long-lived, read from a replica.

-- Before killing anything: what is this transaction blocking?
SELECT w.BLOCKING_ENGINE_TRANSACTION_ID AS blocking_trx,
       COUNT(*)                          AS blocked_locks,
       MAX(TIMESTAMPDIFF(SECOND, t.trx_started, NOW())) AS age_s
FROM   performance_schema.data_lock_waits AS w
JOIN   information_schema.INNODB_TRX AS t
       ON t.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID
GROUP  BY w.BLOCKING_ENGINE_TRANSACTION_ID;

-- KILL issues ROLLBACK. A 40 GB rollback is not instant,
-- and the connection stays in "Rolling back" until done.
KILL 4471;

-- History depth: the direct cost of the open transaction
SELECT NAME, COUNT AS trx_rseg_history_len
FROM   information_schema.INNODB_METRICS
WHERE  NAME = 'trx_rseg_history_len';

trx_rseg_history_len is the number of undo records that purge has not yet been able to discard. Its practical value is that it converts a qualitative complaint — “transactions are too long” — into a number with a unit, a baseline and an alert threshold. Sample it on a fixed interval and plot it; a history length that grows monotonically has identified an open transaction that is not closing, and the corresponding trx_started in INNODB_TRX has identified which one.

Prevention is mostly a client-side contract. Three server settings bound the damage: wait_timeout closes a connection that has been idle, and an idle connection with an open transaction is killed and rolled back when it fires; MAX_EXECUTION_TIME (8.0 and later, milliseconds, SELECT only) bounds a single read; and a per-transaction statement budget enforced in the application layer bounds the rest, since no server variable can interrupt a transaction that keeps issuing statements. On the application side, the durable fix is to make read-modify-write sequences a single statement — UPDATE … SET counter = counter + 1 WHERE id = ?, or an optimistic compare-and-set on a version column that returns zero affected rows, which the caller then retries with backoff. This removes the window in which the deadlock exists at all, rather than making the deadlock cheaper to recover from.

KILL is not free. Killing a connection issues a rollback, and a rollback of a large transaction takes time proportional to the work it has done, during which the connection remains visible in PROCESSLIST as “Rolling back” and continues to hold its locks. The uninformed reflex — kill the oldest transaction — will therefore sometimes convert a slow purge problem into a second, larger stall. Check trx_rows_modified first, prefer killing the transaction with the fewest rows if several candidates exist, and remember that an XA transaction prepared with XA PREPARE survives the disconnect entirely: it is listed by XA RECOVER, and until it is committed or rolled back with XA COMMIT or XA ROLLBACK it continues to hold locks and hold the transaction slot open.

5 · Query Tuning and the Optimizer in Practice

Query tuning in MySQL is a measurement discipline, not a catalogue of index rules. The tools divide cleanly into two families: sources that tell you which statements cost what — the slow query log for durability, performance_schema digests for aggregation — and instruments that tell you why one statement costs what it does: EXPLAIN, EXPLAIN FORMAT=JSON, EXPLAIN ANALYZE and the optimizer trace. This chapter walks the order in which those tools are applied, because applying them out of order is the most common way tuning projects fail: changing an index before establishing a baseline produces a change that cannot be evaluated and will not be kept. It is written against MySQL 9.x, noting where 8.0 and 8.4 differ, and covers the planner controls MySQL provides — and, just as importantly, the ones it does not.

5.1 The tuning method, in order

Five steps, executed in this sequence for every tuning task. The order is not stylistic: each step produces the input the next one requires, and skipping a step is the most frequent cause of an optimisation that helps locally and regresses globally.

Step 1 — Measure. Establish a number before touching anything. The number must be a global one, because the usual failure is optimising the query a human noticed rather than the query that consumed the resource. Suitable baselines are total statement time over a fixed window, p95 and p99 latency for a named endpoint, rows examined per second, or the count of statements exceeding a latency threshold. Record the window, the traffic source and the server configuration alongside the number, because a baseline without those three is not comparable to anything measured later.

Step 2 — Find. Attribute the baseline to specific statements. This is where the slow query log and performance_schema digests are used, and the choice between them is a question of durability rather than quality. The slow log persists to a file, survives restarts, and can be shipped; performance_schema is in-memory, cumulative since the last reset, and is destroyed by a restart. Use both: the digest to get the ranked shortlist, the slow log to recover the literal text and the timestamp for a specific incident.

-- Step 1: a baseline you can hold in your head
SELECT NOW()                                        AS window_start,
       COUNT(DISTINCT USER)                          AS distinct_users,
       VARIANCE(HOST)                                AS host_spread;

-- Step 2: the shortlist, ranked by total time not by count
SELECT LEFT(DIGEST_TEXT, 64)                         AS digest,
       COUNT_STAR                                    AS executions,
       ROUND(SUM_TIMER_WAIT / 1000000000000, 2)      AS total_seconds,
       ROUND(AVG_TIMER_WAIT / 1000000000, 2)         AS avg_ms,
       ROUND(SUM_ROWS_EXAMINED / NULLIF(SUM_ROWS_SENT,0), 1)
                                                     AS examined_per_sent
FROM   performance_schema.events_statements_summary_by_digest
WHERE  SCHEMA_NAME IS NOT NULL
ORDER  BY SUM_TIMER_WAIT DESC
LIMIT  5;

Step 3 — Explain. Take the single most expensive statement and obtain a plan for the actual production shape of the query, with realistic bind values, against a copy of production data. A plan obtained against a freshly created table with ten thousand identical rows will be wrong in a way that has nothing to do with the query, because it is a plan for the statistics rather than for the data. The output of this step is a specific diagnosis: a wrong access type, a missing covering index, a sort or temporary table where none should be, a cardinality estimate off by orders of magnitude, or a join order that starts from the wrong table.

Step 4 — Change one thing. Exactly one: an index, a rewritten predicate, a hint, a session variable, or a schema change. Single-variable discipline is not superstition. Any change that alters an index or a plan also alters row counts, statistics, buffer residency and the plans of every other statement touching the same table, so a combined change that improves the target query tells you nothing about which half worked and gives you no way to attribute a regression elsewhere.

Step 5 — Re-measure. Return to step 1 and compute the same number over the same window. If the baseline did not move, the diagnosis in step 3 was wrong; do not accumulate a second change on top of the first. A tuning project that never returns to step 1 is not a tuning project, it is a collection of changes.

-- Step 3: a plan for the real shape, not for an empty table
EXPLAIN FORMAT=JSON
SELECT o.id, o.total_cents, u.email
FROM   orders AS o
JOIN   users AS u ON u.id = o.user_id
WHERE  o.tenant_id = 42
  AND  o.created_at >= '2026-02-01'
ORDER  BY o.total_cents DESC
LIMIT  50\G

-- Step 4: one change
ALTER TABLE orders
  ADD INDEX idx_tenant_created_total (tenant_id, created_at, total_cents);

-- Step 5: the same number again, same window
SELECT ROUND(SUM(SUM_TIMER_WAIT)/1000000000000, 2) AS total_seconds
FROM   performance_schema.events_statements_summary_by_digest;

The workload includes the maintenance tools. On a busy host the largest single consumer of rows examined is frequently not application traffic. mysqldump --single-transaction reads an entire consistent snapshot; in 8.0 and later it defaults to --single-transaction for InnoDB, sets the isolation level for its own session, and issues FLUSH TABLES WITH READ LOCK only when combined with --master-data/--source-data and --lock-all-tables is not in effect. Percona XtraBackup 9.x streams a physical copy without a long-lived read lock, taking a brief backup lock for DDL metadata, but it still generates substantial redo and I/O that competes with foreground queries. Any measurement window that includes a backup, a statistics run, or a schema migration is measuring the backup, not the application.

5.2 The slow query log

The slow query log is the only built-in source of statement text that survives a restart. It is the right instrument for post-incident forensics and for hosts where performance_schema is not retained, and the wrong instrument for ranking statements across an arbitrary window.

The log is controlled by a small set of variables, and the interaction between them causes more operational confusion than any other part of the MySQL configuration surface. The essential one is long_query_time: a statement is logged when its execution time exceeds it, measured from the start of the statement to the moment the last row is returned to the client. The consequence worth internalising is that a statement which is never logged at long_query_time = 1 can still dominate the server’s total cost if it runs four million times. The log ranks by individual latency; the server is burdened by aggregate time. Those are different questions, and neither instrument answers the other’s question.

# /etc/my.cnf  —  MySQL 9.x

-- measuring. Both exist only in 8.0 and later.
performance_schema              = ON

Two of these deserve their own treatment. min_examined_row_limit sets a floor on Rows_examined below which a statement is not logged, which is how the log is kept usable when long_query_time is set aggressively low; a statement that examined four hundred rows in eight milliseconds is not a tuning target, and without the floor it is logged. log_queries_not_using_indexes is a separate, noisier stream: it logs statements whose plan contains no index, regardless of latency, and on a schema with an unindexed foreign key or a text search column it can generate thousands of entries per minute. log_throttle_queries_not_using_indexes exists specifically to bound that, defaulting to one entry per minute per statement pattern.

5.3 Digest-level aggregation

A digest is a normalised form of a statement: literals replaced by ?, whitespace collapsed, so that every execution of the same statement text shares one row with cumulative counters. This is the instrument that answers “where did the time go” over an arbitrary window.

The normalisation is what makes digests valuable and also what makes them lossy. Two statements that differ only in a literal aggregate into one row, so a pathological WHERE tenant_id = 42 and a well-behaved WHERE tenant_id = 7 are indistinguishable. Where that matters, the per-instance performance schema views (events_statements_history_long and events_statements_current) retain the literal text, and the slow log retains it permanently. Digests are for ranking; history and the slow log are for forensics, and the workflow moves from one to the other the moment a digest identifies a suspect.

The counters that matter for ranking are COUNT_STAR, SUM_TIMER_WAIT, SUM_ROWS_SENT and SUM_ROWS_EXAMINED. The derived metric that separates a real tuning target from a merely loud statement is the ratio of rows examined to rows sent. A ratio near 1.0 means the server read what it needed. A ratio of 900 means it read nine hundred rows to return one, and no amount of latency tuning will fix it — only access path and index coverage will. Sorting by SUM_TIMER_WAIT alone reliably puts full table scans of tiny tables at the top of a busy instance, because they are numerous and each is individually cheap.

-- The workhorse ranking query for a 9.x host
SELECT SCHEMA_NAME,
       LEFT(DIGEST_TEXT, 90)                            AS statement,
       COUNT_STAR                                       AS n,
       ROUND(SUM_TIMER_WAIT/1000000000000, 2)            AS total_s,
       ROUND(AVG_TIMER_WAIT/1000000000, 2)                AS avg_ms,
       ROUND(MAX_TIMER_WAIT/1000000000, 2)                AS max_ms,
       SUM_ROWS_EXAMINED                                AS examined,
       SUM_ROWS_SENT                                    AS sent,
       ROUND(SUM_ROWS_EXAMINED
             / NULLIF(SUM_ROWS_SENT, 0), 1)              AS exam_per_sent,
       SUM_NO_INDEX_USED                                AS no_index,
       SUM_CREATED_TMP_DISK_TABLES                      AS tmp_disk,
       SUM_SORT_MERGE_PASSES                            AS sort_merge
FROM   performance_schema.events_statements_summary_by_digest
WHERE  SCHEMA_NAME NOT IN ('mysql','performance_schema','sys')
ORDER  BY SUM_TIMER_WAIT DESC
LIMIT  20;

Three practical notes on reading those numbers. First, SUM_TIMER_WAIT and every other TIMER_WAIT column is in picoseconds; dividing by 1012 yields seconds and by 109 yields milliseconds. Second, the table is cumulative from the last reset, so a ranking taken an hour after a previous ranking is not comparable to it — either reset the counters and re-measure over a known window, or compute deltas from two saved snapshots. Third, the table has a fixed capacity (performance_schema_digests_size, default 10 000) and evicts entries by age when it fills, so a host with a highly variable statement mix silently loses its oldest digests. sys.statement_analysis wraps this query with the same caveat, adds the literal QUERY text, and is the convenient starting point.

-- Before measuring: reset, or the window is unknowable

TRUNCATE performance_schema.events_statements_summary_global_by_event_name;
TRUNCATE performance_schema.events_statements_summary_by_thread_by_event_name;

-- After the window: the sys view carries the
-- literal text alongside the digest counters
SELECT query, db, exec_count, total_latency,
       rows_examined_avg, rows_sent_avg,
       ROUND(rows_examined_avg
             / NULLIF(rows_sent_avg, 0), 1) AS exam_per_sent,
       tmp_tables_on_disk, rows_sorted,
       rows_affected_avg
FROM   sys.statement_analysis
ORDER  BY total_latency DESC
LIMIT  10\G

-- Statements with no index, straight from sys
SELECT db, query, exec_count, total_latency
FROM   sys.statements_with_full_table_scans
ORDER  BY total_latency DESC
LIMIT  10;

What is not in the digest table. Digests cover statements that reached the server. They do not cover time spent in the network, in the client, or in a connection pool waiting for a connection — the single largest component of perceived latency in a well-tuned OLTP system, and entirely invisible here. They also exclude statements executed inside a stored program as separate entries: the call to the procedure is recorded, and the statements inside it are recorded separately with their own digests, so a procedure called from ten places produces eleven rows rather than one. Before concluding from a digest table that the database is fast, confirm that application latency and database latency are the same number; if they are not, the problem is upstream of the server and no query change will move it.

5.4 EXPLAIN and EXPLAIN FORMAT=JSON

EXPLAIN reports the plan the optimiser chose, together with its cost estimate for every step. It does not execute the statement, it does not report actual timings, and it is only as good as the statistics behind it — which means a plan is a statement about the optimiser’s model of the data, not about the data.

The tabular form is compact and lossy. Read it in this order: the type column, which is the access method and the single most informative field; the key column, which names the index actually chosen and not merely the one considered; the rows and filtered pair, which together give the estimated number of rows that reach the next stage; and finally the Extra column, which names the operations that cost real time. Using filesort and Using temporary are the two entries that most often identify the actual cost, because they mean a sort or a materialised intermediate that has to be written somewhere.

Two columns are routinely misread. rows is the estimate, not the count; it is derived from index cardinality, and it compounds multiplicatively as a plan goes deeper, so an estimate that is wrong by a factor of ten at one level becomes wrong by a hundred at the next. filtered is the percentage of the estimated rows that survive the WHERE clause, so rows × filtered / 100 is the estimated output of that step. A filtered of 0.5 on an index scan of four million rows is the statement that the optimiser expects to discard half of a full table scan — an estimate usually produced by a missing or unselective index rather than by a bad statistic.

EXPLAIN estimates, it does not measure. When the plan disagrees with observed behaviour, the first question is whether the statistics are stale, not whether the optimiser is defective. 5.5 EXPLAIN ANALYZE and the optimizer trace

Both instruments answer questions EXPLAIN cannot. EXPLAIN ANALYZE executes the statement and reports what happened next to what was predicted; the optimizer trace records every candidate the optimiser considered, in order, with the cost that eliminated each one.

EXPLAIN ANALYZE (8.0.18 and later, present throughout the 8.4 and 9.x lines) produces a tree of iterators, each annotated with the estimated cost and row count in parentheses and the measured time and row count after it. The format is the point: read the estimate and the actual side by side, and the first node where they diverge is the node to investigate. actual time=A..B rows=N loops=L means the iterator’s first row arrived at A milliseconds and its last at B, and the totals are per-loop, so multiply by loops before comparing against anything else in the tree.

mysql> EXPLAIN ANALYZE
    -> SELECT o.id, COUNT(*) AS n
    -> FROM   orders AS o
    -> WHERE  o.tenant_id = 42
    ->   AND  o.created_at >= '2026-02-01'
    -> GROUP BY o.id\G
-> Aggregate: count(*)  (actual time=0.281..1844.902
    ->   rows=18422 loops=1)
    -> Sort: o.id  (cost=18422.00..18844.00 rows=18422)
        (actual time=0.109..912.774 rows=18422 loops=1)
        -> Index range scan on o using idx_tenant_created
            (cost=41203.10 rows=18422)
            (actual time=0.048..741.201 rows=18422 loops=1)
            -> Index condition: (o.created_at >= '2026-02-01')
                (cost=41203.10 rows=18422)
                (actual time=0.041..88.113 rows=0 loops=1)
            -> Filter: (o.tenant_id = 42)
                (cost=41203.10 rows=18422)
                (actual time=0.041..610.442 rows=18422 loops=1)

That output is a diagnosis in itself. The index range scan estimated 18 422 rows and delivered 18 422, so the cardinality estimate is right; the sort estimated and delivered the same; the divergence is the 1.3 seconds spent in the Filter node, which is the tenant predicate being evaluated 18 422 times on rows the index range already fetched. The index range on created_at — visible in the key condition — is being used because the optimiser evaluated the created_at predicate as the more selective, and the tenant predicate, which is the genuinely selective one, is left to be checked row by row. That is a composite index-order problem with a specific fix, and it was invisible in the tabular EXPLAIN.

Two cautions. EXPLAIN ANALYZE executes the statement, so it must not be run against a mutating statement inside a transaction you intend to roll back — the UPDATE and DELETE forms are supported, and their effects are real and immediate. And the timing it reports includes the time to read rows that were already in the buffer pool, so the absolute numbers are not a benchmark; the ratio between nodes, and between estimate and actual, is the information.

The optimizer trace answers a different question: not what happened, but what else was considered. It is enabled per session, writes to a ring buffer per session, and is retrieved from information_schema.OPTIMIZER_TRACE as JSON. Enable it, run exactly one statement, then read the trace; leaving it enabled across a workload adds measurable overhead and produces a trace too large to read.

SET SESSION optimizer_trace = 'enabled=on';
SET SESSION optimizer_trace_max_mem_size = 1048576;
SET SESSION optimizer_trace_offset = -1;
SET SESSION optimizer_trace_limit = 1;

SELECT o.id, COUNT(*) FROM orders AS o
 WHERE o.tenant_id = 42 GROUP BY o.id;

SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G
SET SESSION optimizer_trace = 'enabled=off';

The JSON is a list of steps, and the entries worth reading are the ones under best_access_path and considered_execution_plans. Each candidate carries a cost, the access_type that produced it, and for range scans a condition. The chosen flag marks the winner; the candidates that were not chosen are listed with their costs, and comparing the winner’s cost against the cheapest rejected candidate is the fastest way to see that the optimiser was right on its own terms and the statistics were wrong. A plan where a full scan cost 91 000 and an index range scan cost 412 03 — with no tie, no warning and no range_optimizer_max_mem_size message in the error log — is a statistics problem, and the fix is in section 5.4 rather than in a hint.

When to reach for EXPLAIN FOR CONNECTION (8.0.28 and later). EXPLAIN on a running statement gives the plan the optimiser would produce now, for literal values you supply — which is not necessarily the plan the long-running statement actually obtained, because the literals it received may have selected differently. EXPLAIN FOR CONNECTION <id> reports the plan of a statement currently executing on that connection. It is the correct tool for a query that is stuck right now, and it requires no privileges beyond those already needed to see the connection.

5.6 Join order, optimizer_switch and missing planner guards

MySQL explores join orders and access paths under a cost model with a small set of binary switches, and it provides no session-level boolean to veto an individual join algorithm. That absence is the most consequential difference from PostgreSQL for anyone porting a tuning playbook.

MySQL’s join execution is nested-loop: for each row of the outer table it looks up matching rows in the inner table through whatever access path the optimiser selected. There is no hash join in the classical sense and no sort-merge join; what appear in EXPLAIN as Using join buffer are materialised inner relations re-read per outer row, and in 8.0.20 and later that buffer can be used for a hash join, which is why the same plan can be described as Using join buffer (hash join) on a modern server and simply Using join buffer on an older one. The consequence for tuning is direct: the cost of a join is dominated by the access path of the inner table multiplied by the number of outer rows, and the two things that reduce it are a covering or highly selective index on the inner table and an outer table that yields few rows. Join order follows from those, and the optimiser generally gets it right when the statistics are right.

optimizer_switch is the control surface, a comma-separated set of flag=on|off pairs scoped to a session. It is worth knowing precisely which flags exist and what the risky ones do, because several of them change semantics rather than merely cost.

The absence of planner guards is the operational point. PostgreSQL exposes enable_hashjoin, enable_nestloop, enable_mergejoin, join_collapse_limit and from_collapse_limit as ordinary session variables: a DBA can set enable_hashjoin = off on a connection and watch the next query take a different plan, iteratively, without touching application code. MySQL has no equivalent. The nearest equivalents are session-scoped (SET SESSION optimizer_switch, which does not survive a reconnect and is invisible to the application’s connection pool) and per-statement optimizer hints in a /*+ … */ comment, which are durable, travel with the statement, and can be scoped to a single table in a single query block.

-- Per-statement, durable, connection-pool safe
SELECT /*+ JOIN_ORDER(u, o) BKA(u) NO_HASH_JOIN(o) */
       o.id, o.total_cents
FROM   orders AS o
JOIN   users AS u ON u.id = o.user_id
WHERE  o.tenant_id = 42
  AND  o.created_at >= '2026-02-01'
ORDER  BY o.total_cents DESC
LIMIT  50;

-- A hint that does not apply is a warning, not an error
EXPLAIN FORMAT=JSON
SELECT /*+ JOIN_ORDER(u, o) THIS_IS_NOT_A_HINT */
       o.id FROM orders AS o WHERE o.tenant_id = 42;
SHOW WARNINGS;
-- Warning 3126: Unresolved name ... for optimizer hint

This has a direct consequence for a team porting a PostgreSQL tuning runbook. A PG playbook whose first step is “disable hash join on the reporting replica” has no MySQL equivalent that can be applied to a fleet from configuration alone. The MySQL sequence is: reproduce the statement against production-shaped data, confirm the plan with EXPLAIN FORMAT=JSON, compare the alternative with the optimizer trace, ship a hint or a schema change with the statement, and re-measure the same baseline. That sequence ends at EXPLAIN and at a change that is under version control — which is the correct place for it to end. A SET GLOBAL optimizer_switch applied from a change window and never revisited is a guess that happens to be load-bearing.

Two supporting controls complete the picture. join_buffer_size (default 256 KiB, maximum 1 GiB) sizes the buffer used by the materialised inner relation in a nested-loop join and by the hash join added in 8.0.20; a Using join buffer node whose actual time is dominated by buffer re-reads rather than by the inner lookup is a candidate for a larger value, scoped per session rather than globally. optimizer_search_depth (default 62) bounds how many permutations the optimiser considers, and lowering it makes planning faster and plans more predictable on queries with many tables, at the cost of possibly missing the best order — a trade worth making on a system where planning time, not execution time, is the constraint.

-- Session-scoped, reversible, and worth measuring twice
SELECT @@join_buffer_size, @@optimizer_search_depth,
       @@optimizer_prune_level, @@tmp_table_size,
       @@sort_buffer_size, @@read_rnd_buffer_size;

Make the temporary table a decision, not an accident. Using temporary and Using filesort are not defects in themselves; they are correct answers to queries that genuinely require a sort or a materialisation. What matters is whether the amount being sorted is close to the amount being returned. When a LIMIT 50 is preceded by a sort of 18 000 estimated rows, the plan is spending two orders of magnitude more work than the result requires, and that is the finding. When the sort handles 60 rows to return 50, it is the cheapest possible plan. Judge the Extra column against rows, not against a rule of thumb.

A query that is slow is a performance problem. A schema change that is slow is an availability problem, because the server holds metadata locks that block every query touching the table, including plain reads. This chapter treats DDL as an operational change with a lock budget rather than as a statement typed into a console.

6.1 Why schema change is a different problem from query change

A SELECT competes for resources with other queries and degrades gracefully. A ALTER TABLE takes a metadata lock at the start and holds it until the statement finishes. While that lock is held, every other statement that needs the same metadata waits, regardless of whether it reads or writes, and the default lock_wait_timeout is one year. A table copy on a large table therefore becomes a site-wide outage rather than a slow query.

-- The three clocks that govern a migration.
SELECT @@lock_wait_timeout   AS meta_lock_timeout,   -- default 31536000 (1 year)
       @@innodb_lock_wait_timeout AS row_lock_timeout,  -- default 50 seconds
       @@max_execution_time    AS stmt_timeout;        -- default 0 (unlimited) for DDL

-- Watch for metadata locks in real time while a migration runs.
SELECT * FROM performance_schema.metadata_locks
WHERE object_schema = 'shop' AND object_name = 'order_line';

-- See who is blocked, and who is blocking them.
SELECT waiting_pid, waiting_query, blocking_pid, blocking_query
FROM sys.innodb_lock_waits;

Set lock_wait_timeout to a few seconds for the duration of any DDL you run in production. The default of one year means a migration blocked behind a long-running query will sit there holding nothing, appearing to hang, while every subsequent query on that table queues behind it. A short timeout converts that silent hang into a clear error you can retry deliberately.

6.2 The ALTER TABLE algorithms and what each one costs

6.3 Metadata locks, waiting and the lock queue

A metadata lock is not a row lock and does not appear in SHOW PROCESSLIST as "Locked". It appears as a query in the Waiting for table metadata lock state, and the query that holds it may look completely idle from the outside because it is frequently a long-running SELECT that started before the DDL arrived.

-- Who holds and who waits for metadata locks right now.
SELECT ml.OBJECT_NAME, ml.LOCK_TYPE, ml.LOCK_DURATION, ml.LOCK_STATUS,
       t.PROCESSLIST_ID, t.PROCESSLIST_TIME, t.PROCESSLIST_STATE,
       t.PROCESSLIST_INFO
FROM performance_schema.metadata_locks ml
JOIN performance_schema.threads t
  ON t.THREAD_ID = ml.OWNER_THREAD_ID
WHERE ml.OBJECT_SCHEMA = 'shop'
ORDER BY ml.LOCK_STATUS, t.PROCESSLIST_TIME DESC;

-- Kill a specific blocking session if the business allows it.
KILL 41207;

-- Or roll back the waiter; the holder keeps running.
ROLLBACK TO SAVEPOINT migration_sp;

The dangerous property is the queue order. Metadata locks are granted roughly in request order, so a single long-running transaction that acquired a read lock early can block a DDL, and that DDL then blocks every new query behind it. One stale transaction from a reporting script can therefore stall a whole table.

-- Find idle-in-transaction sessions: the usual culprits.
SELECT trx_mysql_thread_id AS conn_id, trx_state,
       trx_started, trx_rows_locked, trx_rows_modified,
       LEFT(trx_query, 80) AS query
FROM information_schema.innodb_trx
ORDER BY trx_started;

-- Bound how long a transaction may sit open. Four hours is generous.
SET GLOBAL innodb_lock_wait_timeout = 20;
SET GLOBAL lock_wait_timeout = 10;

Run DDL in a dedicated session with a short lock_wait_timeout, and retry in a loop with jitter. A migration that fails immediately and retries in thirty seconds is far less disruptive than one that queues behind a five-minute report and takes the application down with it.

6.4 Online DDL in practice: safe recipes

The recipes below are the changes that account for almost all production schema migration. Each states the algorithm it requires and the operation to take if the statement is refused.

-- 1. Add a nullable column, backfill, then add the constraint separately.
ALTER TABLE customer ADD COLUMN phone_e164 VARCHAR(16) NULL,
  ALGORITHM=INSTANT;

-- Backfill in small batches so you never hold a long transaction.
UPDATE customer
   SET phone_e164 = CONCAT('+', country_code, phone)
 WHERE phone_e164 IS NULL
   AND id BETWEEN 1000 AND 5000;

-- 2. Then tighten it. NOT NULL forces a validation scan; do it deliberately.
ALTER TABLE customer
  MODIFY COLUMN phone_e164 VARCHAR(16) NOT NULL,
  ALGORITHM=INPLACE, LOCK=NONE;

-- 3. Drop a redundant index first; this is the cheapest change available.
ALTER TABLE order_line DROP INDEX ix_sku, ALGORITHM=INPLACE;

-- 4. A foreign key needs validated existing data first.
ALTER TABLE order_line
  ADD CONSTRAINT fk_line_order
  FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE,
  ALGORITHM=INPLACE, LOCK=NONE;

Adding a foreign key validates every existing row. If any row violates the constraint the statement fails, and if the table is large the validation itself is expensive. Check for violations first with a LEFT JOIN that counts orphans, and fix the data before attempting the constraint rather than after.

6.5 The expand/contract migration pattern

Some changes cannot be made online at all: renaming a column, splitting one column into two, changing a type, or narrowing a column. The answer is not to endure the lock but to stop needing the change to be atomic. Expand/contract turns one breaking change into four non-breaking ones, spread across multiple deploys.

PhaseActionCompatible withReversible
1. ExpandAdd the new column, nullable, no constraintOld code that ignores itYes, drop the column
2. BackfillPopulate it in batches, dual-writing from the applicationOld code, because it still reads the old columnYes, stop and drop
3. Switch readsDeploy code that reads the new column, falling back to the oldData in both columnsYes, revert the deploy
4. Switch writesDeploy code that writes only the new columnReaders of the new columnNo, once old data stops being maintained
5. ContractDrop the old columnNothing references itNo
-- Renaming order.total to order.total_cents without a blocking change.

-- Phase 1: expand.
ALTER TABLE orders
  ADD COLUMN total_cents BIGINT NULL, ALGORITHM=INSTANT;

-- Phase 2: backfill in batches, online.
UPDATE orders
   SET total_cents = ROUND(total * 100)
 WHERE total_cents IS NULL AND id > 0 ORDER BY id LIMIT 10000;
-- repeat until zero rows remain

-- Phase 5: contract, only after every reader and writer has moved.
ALTER TABLE orders DROP COLUMN total, ALGORITHM=INPLACE;

// The application side of phase 3: read new, fall back to old.
$row = $db->query("SELECT total_cents, total FROM orders WHERE id = ?", [$id]);

if ($row['total_cents'] !== null) {
    $cents = (int) $row['total_cents'];
} else {
    $cents = (int) round($row['total'] * 100);   // pre-migration rows
}

// Phase 4 writes. Dual-write during the overlap so no reader sees a gap.
$db->execute(
    "UPDATE orders SET total_cents = ?, total = ? WHERE id = ?",
    [$cents, $cents / 100, $id]
);

The cost of expand/contract is that two columns exist at once and the application must be correct in both states. That is a real cost and it is worth paying for any change that would otherwise block a table. For a column rename on a table with a few thousand rows, ignore it and just do the rename; for a rename on a hundred-million-row table, plan a week.

6.6 Migration tooling, ordering and rollback

A migration system earns its place by enforcing discipline that a person cannot hold in their head: versioned files, a single ordering, a recorded state, and a reversible plan. The tool is secondary; the invariants are not.

ToolLanguageStrengthConsider
FlywaySQL, with JVM or nativeStrong validation and historyVendor binary, licensing on some editions
LiquibaseXML, YAML, SQL or formatted JavaChangeSets with checksums and context filteringXML is verbose; Java changesets are slow to review
AtlasGo, declarative schemaDiff-based, works well with expand/contractRequires schema introspection discipline
golang-migrateSQL files, Go binaryDeliberately minimalNo checksums; you track drift yourself
Django, AlembicPythonAutogenerate plus hand-written opsOnly if you are already in Django
-- V014__add_total_cents.sql — ordered, named, one concern per file.
ALTER TABLE orders
  ADD COLUMN total_cents BIGINT NULL, ALGORITHM=INSTANT;

-- The matching down migration. Write it now, not when you need it.
-- V014__add_total_cents.down.sql
ALTER TABLE orders DROP COLUMN total_cents, ALGORITHM=INPLACE;

Three rules prevent most migration incidents. One schema change per file, so a failure has one cause. Never edit an applied migration, because tools that checksum files will refuse to run, and tools that do not will leave environments divergent. And never put a data backfill inside a schema migration that also changes structure, because the two have different runtimes and the data one is the one that will be slow.

-- The one migration that is genuinely not transactional: a large backfill.
-- Run it as a resumable job, outside the migration transaction.
CREATE TABLE backfill_job (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  label       VARCHAR(64)  NOT NULL,
  cursor      BIGINT UNSIGNED NOT NULL DEFAULT 0,
  finished_at DATETIME     NULL,
  KEY ix_label_cursor (label, cursor)
) ENGINE=InnoDB;

DDL in MySQL causes an implicit commit. There is no wrapping an ALTER TABLE and the application change in one transaction, so the deploy that runs the migration and the deploy that changes the code must be separate and ordered. This is a property of the engine, not a tooling limitation, and it is the strongest technical reason to prefer expand/contract over clever single-step migrations.

Availability and durability are different properties, and MySQL gives you independent mechanisms for each. This chapter separates replication, which copies changes for availability, from backup, which copies data for recovery, and explains the single mechanism — the binary log — that both depend on.

7.1 The four layers of copying, and which one you need

A database that runs on one machine has one failure domain: that machine. There are four distinct ways to remove it, and they solve different problems at different costs.

LayerWhat it copiesRecovers fromData loss on failureComplexity
BackupA consistent snapshot, on a scheduleCorruption, accidental deletion, ransomwareUp to the interval since the last backupLow
Point-in-time recoveryBackups plus the full binary logAny error that happened at a known timeSeconds, if the log is intactMedium
Asynchronous replicaEvery change, continuouslyServer or disk failureTypically zero to a few secondsMedium
Synchronous / group replicationEvery change, with a quorumAny single node failure, with no data lossNone on single-node failureHigh

Replication is not a backup. A replica faithfully reproduces every mistake, including DROP TABLE, a bad UPDATE without a WHERE clause, and an accidental data deletion. If the mistake is made on the primary it reaches every replica within the replication delay, and you now have N copies of the damage. Backups must be on a separate system, and they must be restorable.

7.2 The binary log and its three formats

The binary log is the server’s record of every change to data. It underpins replication, point-in-time recovery, and most change-data-capture pipelines, so enabling it is a prerequisite for almost everything in this chapter.

-- Server configuration. Requires a restart; put it in my.cnf, not at runtime.
[mysqld]
server_id                = 1
log_bin                  = /var/lib/mysql/mysql-bin
binlog_format            = ROW
binlog_row_image         = FULL
binlog_expire_logs_seconds = 604800
sync_binlog              = 1
SettingValuesConsequence
binlog_formatROW, STATEMENT, MIXEDROW records the changed rows and is deterministic; use it
binlog_row_imageFULL, MINIMAL, NOBLOBFULL records every column, so replay is exact; MINIMAL breaks tools that need the old values
sync_binlog0, 1, or an integer1 fsyncs the log for every commit, which is what makes the log trustworthy for recovery
expire_logs_secondsSecondsHow long logs are kept; must exceed your longest recovery window

Binary log files are numbered. A single logical log is a sequence of files, and the current one grows until it is rotated and closed.

-- Inspect the log inventory and which is currently being written.
SHOW BINARY LOGS;
SHOW MASTER STATUS;

-- Read what is in it. mysqlbinlog can replay a log without a server.
mysqlbinlog --base64-output=DECODE-ROWS --verbose /var/lib/mysql/mysql-bin.000042 \
  | grep -A3 -E "^(###|INSERT INTO|DELETE FROM|UPDATE)" | head -40

-- Replay a specific time window into a scratch instance for testing.
mysqlbinlog --start-datetime="2026-09-01 10:00:00" \
            --stop-datetime="2026-09-01 10:15:00" \
            /var/lib/mysql/mysql-bin.000042 | mysql -u root -p

7.3 Asynchronous replication and the replication lag problem

Asynchronous replication is the default and the most common topology: one primary accepts writes and sends its binary log to one or more replicas that apply it independently. The primary does not wait for acknowledgement, which is fast and cheap, and which creates the central problem of this section — the replicas are behind by an amount you must measure and reason about.

-- Create a replica. On MySQL 8.0.23+ the syntax was renamed from
-- CHANGE MASTER TO to CHANGE REPLICATION SOURCE TO.
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST        = 'db-primary.internal',
  SOURCE_PORT        = 3306,
  SOURCE_USER       = 'repl',
  SOURCE_PASSWORD   = '...from the secret store...',
  SOURCE_AUTO_POSITION = 1,
  GET_SOURCE_PUBLIC_KEY = 1;

START REPLICA;
SHOW REPLICA STATUS\G

SOURCE_AUTO_POSITION enables GTID-based positioning, which is what you should use. File and position offsets break the moment a replica is re-seeded or a failover occurs, because the file numbering diverges. GTIDs identify a change by its origin server and sequence number, so a replica can be positioned regardless of which physical log file it happens to be reading.

Status fieldMeaningHealthy value
Replica_IO_RunningIs the replica receiving the logYes
Replica_SQL_RunningIs the replica applying the logYes
Seconds_Behind_SourceApparent lag in secondsNear zero
Last_ErrorThe last failure messageEmpty
Last_IO_ErrorThe last network or auth failureEmpty

Failures are split between the two threads, and the distinction matters. If the I/O thread stopped, the replica is not receiving the log and will fall further behind until it reconnects. If the SQL thread stopped, it received an event it cannot apply — usually a duplicate key or a missing row from a DELETE — and it will stay stopped until a human intervenes.

-- The standard diagnostic: is it connected, is it applying, how far behind?
SELECT @@gtid_executed AS this_replica,
       @@gtid_purged  AS already_purged;

-- Find the GTID gap: what the primary has that the replica does not.
mysqlbinlog --read-from-remote-server --raw --stop-never-slave-server-id=999999 \
            --host=db-primary.internal | head -50

-- Restart a stopped SQL thread after fixing the cause.
SET GLOBAL replica_sql_thread_state = 'RUNNING';

Seconds_Behind_Source is an estimate computed from event timestamps, and it is frequently zero when the replica is genuinely stuck, because the last event it processed had a recent timestamp. Never alert on this field alone. The reliable signal is a growing gtid_executed gap between the primary and the replica measured over time, or Replica_SQL_Running = No persisting.

7.4 Group replication and MySQL InnoDB Cluster

Group replication is a multi-primary topology in which each node replicates the others through a distributed group communication layer, and a transaction commits only when a quorum of nodes has accepted it. The cost is latency on every write; the benefit is that a single node failure loses nothing and can be replaced without a failover procedure.

PropertyAsynchronous replicaGroup replication
Writable nodesOneAll
Commit requiresLocal disk onlyQuorum acknowledgement
Data loss on single-node failurePossibly, up to the lagNone
Write latencySub-millisecondRoughly the network round trip to a quorum
Conflict detectionNot applicableCertifies against concurrent transactions; aborts conflicting ones
Operational complexityLowHigh; requires a consensus plugin and careful quorum sizing
-- Each node needs a unique server_id and a group UUID shared by all members.
[mysqld]
server_id                        = 11
group_replication_group_name     = 8d1b0a1c-4b6e-11ef-9c3a-0242ac110002
group_replication_start_on_boot  = ON
group_replication_local_address  = 10.0.2.11:33061
group_replication_group_seeds    = 10.0.2.11:33061,10.0.2.12:33061,10.0.2.13:33061
group_replication_single_primary_mode = ON

With single_primary_mode = ON the group still elects one writer, but a failover is automatic and takes a few seconds, where an asynchronous topology needs a manual or orchestrated promotion. With it off, every node accepts writes and conflicts are detected and aborted, which requires application-level retry logic and is genuinely difficult to get right.

-- Operational surface of the group.
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_PORT, MEMBER_STATE,
       MEMBER_ROLE, MEMBER_VERSION
FROM performance_schema.replication_group_members;

-- On a single-primary group, this is the node currently accepting writes.
SELECT CHANNEL_NAME, MEMBER_ID, MEMBER_HOST, MEMBER_ROLE
FROM performance_schema.replication_group_channels;

-- Bootstrap a new cluster on the first node only, then add the others.
SET GLOBAL group_replication_bootstrap_group = ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group = OFF;

MySQL InnoDB Cluster and MySQL Shell wrap this topology in a management layer: they configure group replication, maintain a distributed metadata table, and provide mysqlsh commands for adding, restarting and diagnosing members. For anything beyond a three-node production cluster, use the tooling rather than configuring replication by hand.

Always use an odd number of voting members. A two-node group cannot achieve a quorum if one node fails, so a second node failure is a total outage. Three or five nodes tolerate one or two failures respectively. If you need more capacity, add read replicas outside the group rather than growing the voting set.

7.5 Backup types and what each actually protects you from

"Backup" covers three quite different things. A physical backup copies data files, is fast on large instances and is typically server-version-locked. A logical backup produces SQL statements, is portable across versions and servers, and is slow to restore on a large instance. A snapshot is a block-level copy taken by the storage layer, which is fast but only consistent if the database coordinates it.

mysqldump --single-transaction \
          --quick \
          --routines \
          --triggers \
          --events \
          --set-gtid-purged=OFF \
          --source-data=OFF \
          --hex-blob \
          --default-character-set=utf8mb4 \
          --databases shop \
  | gzip -1 > shop-$(date +%Y%m%d-%H%M).sql.gz

-- --single-transaction gives a consistent snapshot for InnoDB without locking.
-- It does NOT protect MyISAM tables, and it is incompatible with
-- --lock-all-tables. Never use the latter on a live system.

A storage snapshot taken without flushing InnoDB buffers and locking is crash-consistent at best. MySQL will usually recover to a consistent state on startup, but a snapshot of a running instance can also produce a usable but out-of-date image that silently loses the last few seconds of committed transactions. For a database that matters, either use a tool that coordinates the flush, or stop the instance, snapshot, and start it.

-- Physical backup with a tool that coordinates the flush.
xtrabackup --backup --target-dir=/backup/full \
           --user=backup --password --host=127.0.0.1
xtrabackup --prepare --target-dir=/backup/full

-- Incremental on top of the full, then prepare both in order.
xtrabackup --backup --target-dir=/backup/inc1 \
           --incremental-basedir=/backup/full
xtrabackup --prepare --target-dir=/backup/inc1

-- Restore: copy files, prepare, then start. Never start before prepare.
rsync -a /backup/full/ /var/lib/mysql/
xtrabackup --prepare --target-dir=/var/lib/mysql/
chown -R mysql:mysql /var/lib/mysql

Test that a logical dump actually loads before you rely on it. A dump of a database with foreign keys often fails to restore because the child rows are inserted before the parents. Dump with --foreign-key-checks=0 and restore the session variable, or use --single-transaction together with --set-gtid-purged=OFF and load in the order the tool produced.

7.6 Point-in-time recovery, step by step

Point-in-time recovery restores a backup and then replays binary logs up to the moment immediately before a mistake. It is the only mechanism that recovers from a mistake made ten minutes ago on a live system, and it depends entirely on having retained both the backup and a continuous, complete archive of the binary log.

-- 1. Archive the binary log continuously, off the server. Losing the server
--    must not mean losing the means of recovery.
mysqlbinlog --read-from-remote-server --raw --stop-never \
            --host=db-primary.internal --result-file=/archive/binlog/ \
  > /archive/stream.log 2>&1 &

-- 2. Record the exact binary log position immediately before the mistake.
SHOW MASTER STATUS;
-- File: mysql-bin.000117   Position: 8842136   GTID: 3E11FA47-...:1-99887766

-- 3. Restore the most recent full backup into a clean instance.
gunzip -c /backup/full-20260901.sql.gz | mysql -u root -p

-- 4. Replay the logs from the backup point to just before the error.
mysqlbinlog --start-position=4791932 \
            --stop-position=8842136 \
            --stop-never-slave-server-id=999999 \
            /archive/binlog/mysql-bin.00011{5,6,7} \
  | mysql -u root -p

-- 5. Verify, then reopen for application traffic.
mysql -u root -p -e "SELECT COUNT(*) AS orders FROM orders; SHOW ENGINE INNODB STATUS\G"

Recovering to a point in time means choosing a position slightly before the damaging statement, not at it. If the bad UPDATE began at position 8842136, replay to 8842136 exclusive. When using GTIDs, express the boundary as an explicit set: --exclude-gtids='3E11FA47-71CA-11e1-9E33-C80AA9429562:1-99887766' stops immediately before that transaction.

Replaying a binary log against a schema that has drifted from the one in effect when the log was written will fail at the first DDL-derived statement, or worse, will succeed while corrupting data. Record every schema change with its timestamp and its binary log coordinates, and restore to a point that respects the migration order.

7.7 Restoring and verifying: the untested backup is not a backup

A backup is a hypothesis about recoverability. Only a restore proves it, and a restore drill on a schedule converts an untested claim into a measured recovery time objective. The discipline matters more than the tooling, and it is the one thing on this list that is almost always missing.

PropertyQuestion it answersHow to measure
RTO — recovery time objectiveHow long can we be down?Wall-clock time of a full restore drill, end to end
RPO — recovery point objectiveHow much data can we lose?Time since the most recent backup plus log replay latency
Restore correctnessIs the data actually intact?Row counts, checksums, and application-level smoke tests
Backup completenessDoes the dump contain everything?Compare table and row counts against the source
-- A verification script worth running on every restore.
SELECT table_name, table_rows,
       ROUND((data_length + index_length) / 1048576, 1) AS mb
FROM information_schema.tables
WHERE table_schema = 'shop'
ORDER BY table_rows DESC LIMIT 20;

-- Referential integrity after a restore. Empty result is the goal.
SELECT ol.id
FROM order_line ol
LEFT JOIN orders o ON o.id = ol.order_id
WHERE o.id IS NULL LIMIT 10;

-- And that replication is actually running afterwards.
SHOW REPLICA STATUS\G

# A monthly drill that measures the objective rather than assuming it.
#!/usr/bin/env bash
set -euo pipefail

START=$(date +%s)
LATEST=$(ls -t /backup/full-*.sql.gz | head -1)
TARGET="drill-$(date +%Y%m%d)"

docker run -d --name "$TARGET" \
  -e MYSQL_ROOT_PASSWORD=drill -e MYSQL_DATABASE=shop \
  -p 3399:3306 mysql:8.4 >/dev/null

until docker exec "$TARGET" mysqladmin ping -uroot -pdrill --silent 2>/dev/null; do sleep 2; done

gunzip -c "$LATEST" | docker exec -i "$TARGET" mysql -uroot -pdrill
END=$(date +%s)

ROWS=$(docker exec "$TARGET" mysql -uroot -pdrill -Nse \
       "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='shop'")

echo "restore_seconds=$((END - START)) tables=$ROWS source=$LATEST"
docker rm -f "$TARGET" >/dev/null

Measure the restore, not the backup. A backup that completes in one hour and has never been restored may take four hours to load, which invalidates the RTO. Put the measured number in the same place as the target so the two are compared every time, and treat a regression as a real finding rather than a curiosity.
