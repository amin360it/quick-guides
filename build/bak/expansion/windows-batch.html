0.1 What cmd.exe and .bat files are

Windows Batch Scripting runs the cmd.exe interpreter on .bat or .cmd files. It predates PowerShell and survives because it is already on every Windows box: login scripts, legacy installers, and CI steps that call older tools.

The brief history

Batch was introduced with DOS 1.0 in 1981 when Microsoft shipped the first COMMAND.COM. Its entire model was “interpret lines one at a time” and never throw. That model shaped the language: there is no parser, no compiler during execution, and error handling is the return code of the last run program.

Why it still exists

On modern Windows, PowerShell is the default for new automation, but Batch is still embedded in: 1) embedded systems and old industrial gear where COMMAND.COM is the only shell; 2) massive installers and build systems that ship a .cmd wrapper around a .NET exe; 3) Group Policy startup/shutdown scripts, Group Policy Preferences, and the Windows Terminal Service.

Where it breaks

A batch file cannot parse JSON/XML safely, cannot hold multi-line command lines across continuations without effort, and has no built-in awareness of encoding (UTF-8 vs. ANSI) — so any path with Unicode outside the active code page breaks.

A minimal skeleton

@echo off
setlocal enabledelayedexpansion
rem --- your code goes here ---
endlocal

The @echo off stops commands from being echoed. setlocal creates a local variable scope. enabledelayedexpansion lets you use !var! to expand the current runtime value of a variable rather than the parse-time value. Without it, !var! is just literal text.

:: batch-demo.bat
@echo off
setlocal enabledelayedexpansion
set NAME=World
echo Hello, %NAME%!
set /a X=5
echo X is %X%
endlocal
