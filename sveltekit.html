Welcome — How to Use This SvelteKit Guide

How this guide is organisedThe right mindset: one framework for client and serverTools you will use all course long

This guide walks you through building a complete SvelteKit application from your first route to a deployed full-stack site, fully offline. It is organised into chapters and exercises that build on one another and that you type out yourself. Work chapter by chapter and write the code to build muscle memory as you go.

This is a complete, self-paced path through SvelteKit, from your first route to streaming data, sessions, and deployment. SvelteKit is the application framework for Svelte: file-based routing, server rendering, form actions, API endpoints, and adapters for every host — all with one language and one component model. Everything runs in a single HTML file — no internet required, progress is saved in your browser.

How this guide is organised

Explains the three-part structure of the guide, which spans ten chapters plus exercises and an appendix. Each chapter ends with copy-ready code you should type out yourself, and later chapters build on earlier ones. Skim the appendix any time you forget a convention or a command.

  • Part I (Ch. 1–3) — foundations: routing, layouts, pages, and loading data.
  • Part II (Ch. 4–6) — real applications: form actions, API routes, and hooks.
  • Part III (Ch. 7–10) — advanced and scale: state, auth and sessions, adapters and deployment, streaming and testing.
  • Every chapter ends with exercises. Code is copy-ready; type it rather than pasting to build muscle memory.

The right mindset: one framework for client and server

Explains the SvelteKit philosophy that one component model serves both client and server, so a component can render on either side. Because SvelteKit uses plain files and conventions you already know, most questions answer themselves once you learn the file naming rules. Keep that mental model and the rest of the guide follows naturally.

SvelteKit is built on file conventions: a page is always +page.svelte, its layout is +layout.svelte, and an API endpoint is +server.js. Almost every "how do I…" is answered by "create a file with the right prefix." The same component runs on the server for rendering, then hydrates in the browser — you write it once.

Keep the official docs open beside this guide at svelte.dev/docs. This guide explains the why and the sequence; the docs are the exhaustive reference.

1 · SvelteKit Fundamentals & Routing

1.1 Scaffolding a project1.2 File-based routes: +page.svelte1.3 Dynamic routes: [param]1.4 Rest [...rest] and optional [[param]] routes1.5 Navigation and route groups

Builds your first pages with file-based routing and explains the project skeleton. A route is simply a folder under src/routes containing a +page.svelte component, and the folder path becomes the URL. This chapter lays the foundation that every later feature builds on.

SvelteKit’s routing is filesystem-based: a folder inside src/routes becomes a URL, and the file that renders it is always named +page.svelte. This chapter maps the scaffold and every route shape you will use for the rest of the guide.

1.1 Scaffolding a project

Creates a new SvelteKit project with the create command and explains what the generated folders do. The interactive CLI asks whether you want TypeScript, ESLint, Prettier, or Playwright before writing any files. It then walks through src/routes, src/lib, and the static directory so you know what each one is for.

# create a new project with the official scaffold
npm create svelte@latest my-app
cd my-app
npm install
npm run dev          # start Vite at http://localhost:5173
npm run build        # build the app for your chosen adapter

The scaffold answers a few prompts, installs dependencies, and npm run dev boots a dev server with instant reload on port 5173.

The parts of the skeleton that matter most: src/routes/ holds every page, src/app.html is the single HTML shell, and svelte.config.js points at the adapter that publishes your app.

1.2 File-based routes: +page.svelte

Shows the core rule of SvelteKit routing: a folder under src/routes maps to a URL, and its +page.svelte file renders that page. The file name is the API, so adding a folder with the right file is all it takes to add a route. The page component receives its data through props supplied by its load functions.

<!-- src/routes/about/+page.svelte -->
<script>
  let founded = 2019;
</script>

<h1>About us</h1>
<p>We have existed since {founded}.</p>

Creating src/routes/about/+page.svelte makes /about a real page served and hydrating on request — nested folders become nested URL paths automatically.

1.3 Dynamic routes: [param]

Covers square-bracket parameters for per-item URLs. A folder named [slug] matches any single segment, and the captured value is exposed through params, which load functions and pages can read. This is how product pages, post pages, and other dynamic resources are built.

// src/routes/blog/[slug]/+page.server.js
import { error } from '@sveltejs/kit';
import { getPost } from '$lib/server/posts';

export function load({ params }) {
  const post = getPost(params.slug);   // "hello-world" for /blog/hello-world
  if (!post) throw error(404, 'Post not found');
  return { post };
}

The [slug] folder captures one URL segment into params, and the server load looks the post up and returns it, throwing a 404 when it is missing.

1.4 Rest [...rest] and optional [[param]] routes

Shows how rest parameters with three dots inside square brackets catch multiple segments, and how optional parameters inside double brackets let a segment disappear. Together they cover documentation trees, deep URL structures, and i18n paths. Both work with load functions and server files the same way.

<!-- src/routes/docs/[...slug]/+page.svelte -->
<script>
  import { page } from '$app/stores';
  let parts = $page.params.slug || [];   // [] for /docs, ['a','b'] for /docs/a/b
</script>

<h1>Docs</h1>
<p>Path: {parts.join(' / ')}</p>

A [...slug] folder catches zero or more segments as an array, while an [[lang]] folder makes /about and /en/about both resolve to the same page.

1.5 Navigation and route groups

Shows client-side navigation with plain anchor tags plus the goto helper from the navigation module. Links to internal routes are intercepted by the router so navigation happens without full page reloads. It also explains that parentheses group folders to organise the route tree without adding URL segments.

<script>
  import { goto } from '$app/navigation';
</script>

<!-- plain links are intercepted: no full page reload -->
<a href="/blog">Blog</a>
<a href="/blog/{slug}">Open post</a>

<button on:click={() => goto('/checkout')}>Checkout</button>

SvelteKit prefetches and navigates plain links client-side, and goto() does the same from code, keeping the page alive instead of reloading.

src/routes/
  (marketing)/                  # parentheses: groups only, no URL part
    about/+page.svelte          # still served at /about
  account/
    profile/+page.svelte        # served at /account/profile

Route groups wrap folders in parentheses to organise code or attach a layout without changing the URL, which matters when you meet layout resets in Chapter 2.

2 · Layouts, Pages & Head

2.1 Nested layouts and the slot2.2 Layout reset and groups2.3 +page.js vs +page.svelte2.4 Page options: prerender, ssr, csr2.5 Head management with <svelte:head>

Covers layouts, page options, and the svelte:head API for managing the document head. Layouts give every route a shared shell such as a header and footer without repeating markup a single time. Page options and head management then let each route control its own rendering and metadata.

2.1 Nested layouts and the slot

Shows how a +layout.svelte file wraps every page beneath it in the route tree. Nested layouts compose like matryoshka templates, so each level adds its own shell around the content below it. A page renders inside its nearest layout, which itself renders inside the layout above it.

<!-- src/routes/+layout.svelte -->
<nav>
  <a href="/">Home</a>
  <a href="/blog">Blog</a>
</nav>

<main>
  <slot />    <!-- the child page renders here -->
</main>

The root layout renders once for the whole app, and the slot is replaced by whichever page or child layout matches the current route.

2.2 Layout reset and groups

Explains how route groups let different pages use different layouts, and how +layout@.svelte resets to a specific parent layout. The @ selector names the parent whose shell you want to escape. This is how login and error pages break out of the main app shell.

src/routes/
  (app)/
    +layout.svelte          # sidebar layout for the app
    dashboard/+page.svelte
  (auth)/
    +layout@.svelte         # resets to the root layout — bare screen
    login/+page.svelte

Both groups live at the same depth, so none adds a URL segment, and the @. reset drops the sidebar layout so login renders on a bare canvas.

2.3 +page.js vs +page.svelte

Separates the module scripts that run first from the component that renders. The +page.js file exports load and the page options while +page.svelte holds the markup. Keeping logic in the module file keeps components simple and lets data arrive before render.

// src/routes/posts/+page.js
export const load = ({ url }) => {
  const q = url.searchParams.get('q');
  return {
    title: q ? `Results for "${q}"` : 'All posts',
    page: Number(url.searchParams.get('page')) || 1,
  };
};

The +page.js module exports a load function that runs before render and returns data; the sibling +page.svelte receives it through the data prop.

<!-- src/routes/posts/+page.svelte -->
<script>
  export let data;   // what load() returned becomes {data.title}
</script>

<h1>{data.title}</h1>
<p>Page {data.page}</p>

The component exports a data prop that the framework fills from load, keeping the script that fetches strictly separate from the markup that shows it.

2.4 Page options: prerender, ssr, csr

Introduces the prerender, ssr, and csr page options that control how a page is produced. Prerender builds static HTML at build time, ssr renders on every request, and csr off emits a shell that fills in later. They are plain exports from the page module.

// src/routes/landing/+page.js
export const prerender = true;   // bake to static HTML at build time
export const ssr = true;         // server-render each request (default)

// src/routes/analytics/+page.js
export const ssr = false;        // client-only: no server render at all
export const csr = true;         // hydrate in the browser (default)

Prerender turns a route into a static file, and ssr:false skips server rendering for pages that only make sense after the browser loads.

2.5 Head management with <svelte:head>

Shows per-page title, description, and meta tags using the svelte:head element. Anything inside it is rendered into the document head on both server and client. This is the standard way to set SEO metadata and dynamic titles per route.

<!-- src/routes/blog/[slug]/+page.svelte -->
<script>
  export let data;
</script>

<svelte:head>
  <title>{data.post.title} | my-blog</title>
  <meta name="description" content={data.post.excerpt} />
</svelte:head>

<h1>{data.post.title}</h1>

svelte:head injects title and meta tags right from the page component, so every route controls its own document head without touching the shell.

3 · Loading Data

3.1 Universal load vs server load3.2 Using fetch and auth in +page.server.js3.3 Parent data, depends and invalidate3.4 Streaming promises and fetch in load

Explains how data reaches your pages through load functions, from universal load that runs everywhere to server-only streams. Load functions run before the component renders and supply its data prop. Load is where SvelteKit does most of its heavy lifting.

3.1 Universal load vs server load

Distinguishes +page.js universal load, which runs during SSR and again on the client, from +page.server.js server load, which runs only on the server. Server load can read cookies, headers, and private secrets, while universal load is limited to public code. The choice is about what data you trust and where it can run.

// +page.js — universal: SSR first, then runs again on the client
export function load({ url }) {
  return { path: url.pathname };   // fine for public, shared data
}

// +page.server.js — server only: never shipped to the browser
export async function load() {
  const secret = await db.query(...);   // safe: the browser never sees this file
  return { secret };
}

Universal load runs during server render and again on navigation, while server load runs only where the server exists — which is where secrets, cookies, and the database belong.

3.2 Using fetch and auth in +page.server.js

Shows a realistic server load function that talks to an API and guards access. The function receives cookies, fetch, params, url, and locals through its event argument. Fetching from the server lets you forward cookies and keep credentials off the client.

// src/routes/account/+page.server.js
import { error, redirect } from '@sveltejs/kit';

export async function load({ locals, fetch }) {
  if (!locals.user) throw redirect(302, '/login');   // bounce guests early

  const res = await fetch(`/api/orders?user=${locals.user.id}`);
  if (!res.ok) throw error(502, 'Order service failed');

  return { orders: await res.json() };
}

The server load checks auth first, calls the internal API with a server-side fetch, and turns a bad response into a readable 502 error.

3.3 Parent data, depends and invalidate

Shows how child loads merge with the parent layout’s data and how depends and invalidate re-run loads on demand. Returning a promise that awaits parent data merges the two results. Call invalidate with the matching dependency string to refresh data when the underlying source changes.

// src/routes/+layout.server.js
export function load() {
  return { settings: await getSettings(), user: await getCurrentUser() };
}

// src/routes/+page.server.js — a child of the same layout
export async function load({ parent }) {
  const { user, settings } = await parent();   // merge parent data in
  return { greeting: `Hello, ${user.name}`, theme: settings.theme };
}

await parent() pulls the layout’s data into the page load, so layout-level work is loaded once and reused rather than repeated per route.

// src/routes/orders/+page.server.js
export async function load({ depends }) {
  depends('app:orders');                       // tag this load's data
  return { orders: await getOrders() };
}

// anywhere after a mutation:
import { invalidate } from '$app/navigation';
await invalidate('app:orders');   // re-run every load that depends on the tag

depends tags data with a name so a later invalidate() call re-runs only the loads that declared they depend on it — a targeted refresh after a mutation.

3.4 Streaming promises and fetch in load

Shows how returning a promise from server load streams its resolution to the browser. The page shell renders instantly while slow data arrives later in chunks. This keeps the first paint fast even when some queries take a while.

// src/routes/report/+page.server.js
import { slowStats } from '$lib/server/stats';

export function load() {
  return {
    quick: { name: 'Summary' },   // sent with the first pass of the response
    stats: slowStats(),           // a promise: streamed when it resolves
  };
}

Server load can return unresolved promises, and SvelteKit streams each one to the client as it completes instead of holding the whole page hostage.

<!-- src/routes/report/+page.svelte -->
<script>
  export let data;
</script>

<h1>Report</h1>
<p>{data.quick.name}</p>

{#await data.stats}
  <p class="muted">Calculating…</p>
{:then stats}
  <table><tr><th>Total</th><td>{stats.total}</td></tr></table>
{/await}

The page renders the sync data immediately and uses svelte’s {#await} blocks to swap in the streamed stats the moment the promise resolves.

4 · Form Actions

4.1 The default action4.2 Named actions and redirect() after writes4.3 Validation with fail()4.4 Progressive enhancement with use:enhance4.5 Handling uploaded files

Shows the SvelteKit answer to forms: actions defined in +page.server.js that handle form submissions. Validation uses fail() to return errors together with the submitted values, and progressive enhancement is added with use:enhance. File uploads are handled through formData file objects as well.

4.1 The default action

Introduces the actions export in +page.server.js and a plain form posting to it. Submitting sets form props on the page in return, so the page re-renders with the result. No client-side JavaScript is required for the basic flow to work.

// src/routes/todos/+page.server.js
export const actions = {
  default: async ({ request }) => {
    const form = await request.formData();
    const title = form.get('title');

    if (!title || !String(title).trim()) {
      return fail(400, { missing: true });   // same page, error state
    }
    await createTodo(String(title));
    return { created: String(title) };       // becomes the {form} prop
  },
};

The default action reads the posted form data, rejects empty titles with fail(400), and otherwise creates the todo and returns data that becomes the page’s form prop.

<!-- src/routes/todos/+page.svelte -->
<script>
  export let form;   // whatever the last action returned
</script>

<form method="POST" action="?/create">
  <input name="title" placeholder="New todo" />
  <button>Add</button>
</form>

{#if form?.missing}<p class="error">A title is required.</p>{/if}

A plain HTML form posts to the action, and the returned object arrives as the form prop so the page can show validation messages without any custom JS.

4.2 Named actions and redirect() after writes

Shows the ?/action selector that lets a form choose a named action, and the redirect() helper for after successful writes. Named actions let one page handle many intents such as create, update, and delete. Return a redirect after a write so refreshing the page does not resubmit.

// src/routes/todos/+page.server.js
import { fail, redirect } from '@sveltejs/kit';

export const actions = {
  create: async ({ request }) => { /* as before */ },
  toggle: async ({ request }) => {
    const done = Boolean((await request.formData()).get('done'));
    await setDone(params.id, done);
  },
  delete: async ({ params }) => {
    await deleteTodo(params.id);
    throw redirect(303, '/todos');   // stop here and bounce to a fresh page
  },
};

Forms address named actions with action="?/delete", and throw redirect(303) after a write to apply the Post/Redirect/Get pattern and refresh the data.

4.3 Validation with fail()

Shows field-level validation errors collected in one pass with fail(). Each failed field keeps its submitted value so the user can correct it without retyping. Read the returned errors and data in the page component to display the messages inline.

// src/routes/register/+page.server.js
import { fail, redirect } from '@sveltejs/kit';

export const actions = {
  register: async ({ request, cookies }) => {
    const data = Object.fromEntries(await request.formData());
    const errors = {};

    if (!data.name) errors.name = 'Name is required.';
    if (!data.email || !String(data.email).includes('@')) errors.email = 'Invalid email.';
    if (String(data.password).length < 8) errors.password = 'Use 8+ characters.';

    if (Object.keys(errors).length) {
      return fail(400, { errors, data });   // keep input, show every error
    }
    const user = await createUser(data);
    cookies.set('session', user.sessionId, { path: '/' });
    throw redirect(303, '/account');
  },
};

Validation runs server-side, every bad field is collected into errors, and fail(400) returns them with the original values so the form repopulates.

4.4 Progressive enhancement with use:enhance

Adds use:enhance to the form element so the same form submits as a fetch under the hood. Without JavaScript it falls back to a plain POST, and with it the page updates without a full reload. Extra options can show pending states and reset the form after success.

<script>
  import { enhance } from '$app/forms';
  export let form;
  let saving = false;
</script>

<form method="POST" use:enhance={() => {
  saving = true;                    // show a spinner while submitting
  return async ({ result }) => {    // receives update, result, formElement
    saving = false;
    if (result.type === 'error') alert('Something went wrong');
  };
}}>
  <input name="title" placeholder="New todo" />
  <button disabled={saving}>{saving ? 'Saving…' : 'Add'}</button>
</form>

use:enhance submits the form with fetch, applies the action’s returned form prop, and runs your callback — so the same form works with or without JavaScript.

4.5 Handling uploaded files

Handles multipart uploads inside an action. The formData file field arrives as a File object whose buffer you write to disk or remote storage. Always validate the filename and content type, and never trust the submitted name directly.

// src/routes/upload/+page.server.js
import { fail } from '@sveltejs/kit';
import { writeFile } from 'node:fs/promises';
import { randomUUID } from 'node:crypto';

export const actions = {
  upload: async ({ request }) => {
    const form = await request.formData();
    const file = form.get('avatar');

    if (!file || !(file instanceof File)) return fail(400, { noFile: true });

    const bytes = new Uint8Array(await file.arrayBuffer());
    const name = `${randomUUID()}.${file.name.split('.').pop()}`;   // safe name
    await writeFile(`static/uploads/${name}`, bytes);

    return { uploaded: name };
  },
};

The action reads the File, writes its bytes to disk under a server-generated name, and returns the safe filename — client filenames are never trusted or reused.

5 · API Routes

5.1 A +server.js GET endpoint5.2 POST, PUT and DELETE handlers5.3 Request and Response, and the json helper5.4 Endpoint params and error handling

Covers +server.js endpoints that speak JSON through GET, POST, PUT, and DELETE handlers. The exported functions handle each HTTP verb for the same URL, and the json helper builds responses cleanly. Consistent error responses keep API clients predictable across every endpoint.

5.1 A +server.js GET endpoint

Shows the file convention for API routes and the simplest JSON response. Exporting a GET function from +server.js is all it takes to expose an endpoint. Every function you export corresponds to the HTTP verb it handles.

// src/routes/api/posts/+server.js
import { json } from '@sveltejs/kit';
import { listPosts } from '$lib/server/posts';

export async function GET() {
  const posts = await listPosts();
  return json(posts);                    // 200 with Content-Type: application/json
}

A +server.js file under src/routes/api/posts maps to GET /api/posts and returns the post list as JSON via the json helper.

5.2 POST, PUT and DELETE handlers

Shows a full CRUD endpoint for one resource using separate exported handlers. Each exported method handles one HTTP verb for the same URL. Read the request body or params to identify the resource, then respond with the appropriate status code.

// src/routes/api/posts/[id]/+server.js
import { json, error } from '@sveltejs/kit';

export async function GET({ params }) {
  const post = await findPost(params.id);
  if (!post) throw error(404, 'Post not found');
  return json(post);
}

export async function PUT({ params, request }) {
  const body = await request.json();
  const updated = await updatePost(params.id, body);   // params works here too
  return json(updated);
}

export async function DELETE({ params }) {
  await removePost(params.id);
  return new Response(null, { status: 204 });   // 204 = no content
}

The same +server.js exports a handler per HTTP verb, sharing the [id] param, so /api/posts/42 supports GET, PUT, and DELETE with one file.

5.3 Request and Response, and the json helper

Shows how handlers read query strings and JSON bodies, and how to build responses. Handlers are plain Web-standard functions that receive a Request and return a Response. The json helper serialises data and sets an appropriate content type for you.

// src/routes/api/search/+server.js
import { json } from '@sveltejs/kit';

export async function POST({ request, url }) {
  const q = url.searchParams.get('q');      // GET-style query: ?q=hello
  const body = await request.json();          // parsed POST body
  const results = await search(String(q).trim(), body.limit ?? 10);

  // status codes and headers ride along with the data
  return json({ q, results }, { status: 200 });
}

Handlers receive the standard Request with query string, headers, and body, and json() packages a Response with the right content type and status.

5.4 Endpoint params and error handling

Combines params, validation, and error() so clients always get a structured failure. Use params to identify the resource, validate the request, then throw error() with a status and message, and SvelteKit shapes the JSON response. This keeps error handling consistent across the whole API.

// src/routes/api/posts/+server.js
import { json, error } from '@sveltejs/kit';

export async function POST({ request }) {
  const { title } = await request.json();

  if (!title || String(title).length < 3) {
    throw error(422, 'Title must be at least 3 characters');   // Unprocessable Entity
  }

  const post = await createPost(String(title));
  return json(post, { status: 201 });       // 201 = Created
}

// throw error() with your own code for the client:
export function GET({ url }) {
  if (!url.searchParams.get('key')) {
    throw error(403, { message: 'API key missing', code: 'NO_KEY' });
  }
  return json({ ok: true });
}

throw error() produces a JSON error body with the status and message, so validation failures and auth problems reach API clients in a consistent shape.

6 · Hooks & Middleware

6.1 The handle hook and event.locals6.2 Composing hooks with sequence6.3 handleFetch6.4 handleError and an authorization pattern

Covers the server hooks that run around every request: handle, sequence, handleFetch, and handleError. Hooks are where cross-cutting concerns such as auth, logging, and header manipulation live. They run at the edge of every request, before and after the routes themselves execute.

6.1 The handle hook and event.locals

Shows the entry point for server requests. The handle hook runs before any route and can inspect and modify the request or resolve a response directly. event.locals carries per-request data through the whole stack, from hooks down to load functions and components.

// src/hooks.server.js
import { getUserFromToken } from '$lib/server/session';

export async function handle({ event, resolve }) {
  const token = event.cookies.get('session');
  event.locals.user = token ? await getUserFromToken(token) : null;
  // locals is per-request: safe for any load or action to read
  return resolve(event);      // hand the request to the router
}

handle reads the session cookie, attaches the user to event.locals before the route runs, and every load function in the app can read locals user.

6.2 Composing hooks with sequence

Chains multiple handle hooks in order with sequence from the SvelteKit module. Each hook stays small and does exactly one thing, such as parsing a cookie or setting a header. The first hook receives the raw request and the last one resolves the final response.

// src/hooks.server.js
import { sequence } from '@sveltejs/kit/hooks';

async function logging({ event, resolve }) {
  const start = Date.now();
  const response = await resolve(event);
  console.log(`${event.request.method} ${event.url.pathname} ${Date.now() - start}ms`);
  return response;
}

async function auth({ event, resolve }) {
  event.locals.user = await loadUser(event.cookies.get('session'));
  return resolve(event);
}

export const handle = sequence(logging, auth);   // run in listed order

sequence runs logging first and auth second, each wrapping resolve, so hooks stay composable and additive instead of one giant function.

6.3 handleFetch

Shows how to intercept fetch calls made by load functions and forward credentials. This closes the classic internal-API auth gap by baking cookies or tokens into the outgoing request. The hook returns a modified fetch, or falls back to the original one.

// src/hooks.server.js
export async function handleFetch({ request, fetch, event }) {
  if (request.url.startsWith('http://api.internal/')) {
    // forward the user's session cookie to the internal API
    request.headers.set('cookie', event.request.headers.get('cookie') ?? '');
  }
  return fetch(request);   // otherwise, fetch normally
}

handleFetch rewrites every fetch your load functions make, forwarding the visitor’s cookies to an internal API so it sees the same user.

6.4 handleError and an authorization pattern

Centralises unexpected error logging in one place. The handleError hook receives the error and the event that caused it on the server, while a client-side variant handles browser errors. It also demonstrates the guard pattern that protects whole subtrees from a hook or layout.

// src/hooks.server.js
export function handleError({ error, event }) {
  console.error('Unhandled error on', event.url.pathname, error);
  // never leak stack traces or DB details to the client
  return { message: 'Something went wrong. Please retry.' };
}

handleError captures unexpected errors once, logs them server-side, and returns a safe message the error page is allowed to show.

// src/routes/admin/+layout.server.js
import { redirect } from '@sveltejs/kit';

export function load({ locals }) {
  if (!locals.user) throw redirect(302, '/login');        // guests out
  if (!locals.user.isAdmin) throw redirect(302, '/');     // members out
  return { user: locals.user };
}

A layout server load running for /admin and every route beneath it enforces authorization in one place, short-circuiting before any page renders.

7 · State, Stores & Context

7.1 The page and navigating stores7.2 Store SSR caveats7.3 setContext and getContext7.4 Sharing load data with components

Covers the built-in stores from the app stores module, the server-side pitfalls of module stores, and how setContext and getContext share state down a component tree. Together they give you safe, scoped state across pages and components. This is the chapter that makes your state behave correctly under SSR.

7.1 The page and navigating stores

Introduces the page and navigating stores from the app stores module. They expose URL, params, data, and the in-flight navigation state anywhere in your components. Reading them auto-subscribes and updates reactively as navigation happens.

<script>
  import { page, navigating } from '$app/stores';
</script>

{#if $navigating}
  <div class="loader">Loading {$navigating.to?.url.pathname}…</div>
{/if}

<p>You are on <code>{$page.url.pathname}</code></p>

$page gives any component the current URL, params, and rendered data, while $navigating goes truthy during a client-side navigation and names the target.

7.2 Store SSR caveats

Warns about module-level stores holding shared state across requests. Because SSR renders many requests in one server process, a module store would leak one user’s state to another. Importable stores must be created outside components and kept request-neutral, or created fresh per request with context.

// src/lib/stores/counter.js — NOT inside a .svelte file
import { writable } from 'svelte/store';

export const count = writable(0);   // importable from any component

// Dangerous pattern: this store is shared across ALL requests during SSR
// export const currentUser = writable(null);  // do not do this with user data

// Safe: derive state from $page.data instead
import { page } from '$app/stores';
export const currentUser = derived(page, ($p) => $p.data.user);

svelte/store is safe for counters and theme, but per-user data belongs in load results or context — a module store shared in SSR would leak across requests.

7.3 setContext and getContext

Shares objects with descendants without prop drilling. A parent calls setContext to offer an object, and any child in that tree calls getContext to read it. Context is scoped to the component tree, so per-user state stays isolated between requests.

<!-- src/routes/+layout.svelte -->
<script>
  import { setContext } from 'svelte';
  import { writable } from 'svelte/store';

  // one store per request, handed to every descendant below this slot
  setContext('user', writable($page.data.user));
</script>

<slot />

The layout creates a per-request store and registers it as 'user' context, so every component below inherits it without prop drilling.

<!-- any descendant component -->
<script>
  import { getContext } from 'svelte';
  import { page } from '$app/stores';

  const user = getContext('user');   // the store created by the nearest ancestor

  $: greeting = $user?.name && `Hi, ${$user.name}`;
</script>
<p>{greeting}</p>

getContext pulls the store back out in the child, and because context matches the tree, server rendering keeps each request’s state separate.

7.4 Sharing load data with components

Shows the cleanest sharing mechanism: load returns data that flows through the page store’s data property. Components read that property reactively with zero plumbing. This works identically for both universal and server load results.

// src/routes/+layout.server.js
export function load() {
  return { workspace: await getWorkspace() };
}

// any component anywhere in the app:
import { page } from '$app/stores';

// $page.data.workspace is reactive and SSR-safe
const workspace = $page.data.workspace;

Returning data from a layout load merges it into $page.data, giving every component under the layout reactive, server-safe access by default.

8 · Errors, Auth & Sessions

8.1 The error page: expected vs unexpected8.2 Session cookies with the cookies API8.3 Auth guards with redirect8.4 A complete session flow

Covers the error page, expected versus unexpected failures, session cookies, and authorization guards. Together they complete the auth story that began with event.locals in an earlier chapter. You learn to build a login, protect routes, and handle failures gracefully.

8.1 The error page: expected vs unexpected

Shows +error.svelte and the two failure channels. Throwing error() is an expected failure, and its message reaches the page for rendering. Anything else is unexpected and is filtered by handleError so internal details never leak to users.

<!-- src/routes/+error.svelte -->
<script>
  import { page } from '$app/stores';
</script>

<h1>{$page.status}</h1>
<p>{$page.error.message}</p>
<a href="/">Back home</a>

+error.svelte renders for any failed navigation or render, reading status and message from $page so expected throw error(...) messages show and internals never do.

8.2 Session cookies with the cookies API

Sets a secure session cookie from an action and reads it later with the cookies API. Options such as httpOnly, sameSite, and secure are non-negotiable for web auth. Set and delete cookies from hooks, actions, load functions, and server endpoints.

// src/routes/login/+page.server.js
import { fail, redirect } from '@sveltejs/kit';

export const actions = {
  default: async ({ request, cookies }) => {
    const data = Object.fromEntries(await request.formData());
    const user = await verifyLogin(data.email, data.password);

    if (!user) return fail(401, { email: data.email });

    cookies.set('session', user.sessionId, {
      path: '/',                // send it for every route
      httpOnly: true,           // invisible to JavaScript in the browser
      secure: true,             // HTTPS only in production
      sameSite: 'lax',          // CSRF mitigation
      maxAge: 60 * 60 * 24 * 7, // one week
    });

    throw redirect(303, '/account');
  },
};

The action verifies credentials, writes an httpOnly same-site cookie for the path, and redirects — the cookie then rides on every subsequent request.

8.3 Auth guards with redirect

Reads the session cookie in hooks and bounces unauthenticated visitors with redirect(). The cookie value is the only proof of identity the server needs to trust. A guard placed in a hook or layout protects every route beneath it.

// src/hooks.server.js
import { redirect } from '@sveltejs/kit';
import { userFromSession } from '$lib/server/session';
import { protectedPaths } from '$lib/server/routes';

export async function handle({ event, resolve }) {
  const sessionId = event.cookies.get('session');
  event.locals.user = sessionId ? await userFromSession(sessionId) : null;

  // catch protected prefixes before the router resolves anything
  if (protectedPaths.some((p) => event.url.pathname.startsWith(p)) && !event.locals.user) {
    throw redirect(302, `/login?next=${encodeURIComponent(event.url.pathname)}`);
  }

  return resolve(event);
}

The hook resolves the session into locals.user and short-circuits protected prefixes with a redirect that remembers where the visitor was headed.

8.4 A complete session flow

Ties login, guard, and logout into one loop. Session creation happens on a successful login action, verification runs per request in a hook, and deletion happens on logout. This is the complete, working auth lifecycle you can carry into any app.

// src/routes/logout/+page.server.js
export const actions = {
  default: async ({ cookies }) => {
    cookies.delete('session', { path: '/' });   // drop it client-side too
    return { loggedOut: true };
  },
};

// src/routes/account/+layout.server.js — the guard side
export function load({ locals }) {
  if (!locals.user) throw redirect(302, '/login');
  return { user: locals.user };
}

Logout deletes the session cookie, and the account layout guard only lets locals.user through — the complete create-verify-delete session loop.

Use httpOnly and sameSite together, never stash secrets in localStorage, and rotate session IDs on login to defeat fixation.

9 · Adapters & Deployment

9.1 adapter-auto and adapter-node9.2 adapter-static and prerendering9.3 $env modules and environment variables9.4 build, preview and the production checklist

Covers adapters, prerendering, and the environment-variable modules. An adapter is the only thing that changes when you move hosts, reshaping the build for a target platform. With the right adapter your app runs on Node servers, CDNs, or serverless platforms.

9.1 adapter-auto and adapter-node

Shows the default auto adapter and the Node server adapter for baremetal hosts. adapter-node builds a standalone Node server with no port assumptions and reads its configuration from environment variables at runtime. The result is a single build that runs anywhere you run Node.

npm add -D @sveltejs/adapter-node

// svelte.config.js
import adapter from '@sveltejs/adapter-node';

export default {
  kit: {
    adapter: adapter({ out: 'build' }),
  },
};

// then
npm run build          # produces build/ with a server and prerendered assets
PORT=3000 node build   # run the server anywhere Node.js exists

Swapping the adapter changes the build output, and adapter-node produces a tiny Node server you can run with node build on any host or container.

9.2 adapter-static and prerendering

Builds the entire app as plain static files for CDN hosting. Every route must be prerendered or marked csr-only for this to work. The result is a folder of HTML, CSS, and JavaScript you can serve from any static host or file server.

npm add -D @sveltejs/adapter-static

// svelte.config.js
import adapter from '@sveltejs/adapter-static';

export default {
  kit: {
    adapter: adapter({ pages: 'build', assets: 'build', fallback: null }),
  },
};

// src/routes/+layout.js — every route must agree to be static
export const prerender = true;

With the static adapter the build emits only HTML, JS, and assets — deployable to any CDN or static host, provided every route is prerenderable.

9.3 $env modules and environment variables

Shows which environment-variable module fits each variable. Public variables come from the env static or dynamic public modules and are compiled into the client bundle. The private and dynamic private modules keep secrets and runtime values on the server forever.

# .env
PUBLIC_API_URL=https://api.example.com    # PUBLIC_ prefix: safe for browsers
DATABASE_URL=postgres://user:pass@localhost/db

// src/routes/+page.server.js
import { DATABASE_URL } from '$env/dynamic/private';     // read at runtime, server only
export async function load() {
  return { db: DATABASE_URL };   // safe: this file never ships to the client
}

// src/routes/+page.js
import { PUBLIC_API_URL } from '$env/static/public';     // compiled into the bundle
export function load({ fetch }) {
  return { api: `${PUBLIC_API_URL}/posts` };
}

PUBLIC_-prefixed variables are safe to compile into client code, while $env/dynamic/private variables exist only on the server and refresh without a rebuild.

9.4 build, preview and the production checklist

Lists the commands that complete a release and the checks to run before you ship. Build produces the final output, preview serves it locally, and svelte-kit sync keeps the generated types honest after config changes. Walk the checklist before every deployment.

npx svelte-kit sync          # regenerate route types after changing files
npm run build                # adapt the app for the target host
npm run preview              # serve the production build locally

# production checklist
# - set a strong COOKIE_SECRET and rotate on deploy
# - pin the SvelteKit and adapter versions
# - assert directives for the document head in app.html
# - confirm PRERENDERED routes in the build output

Build then preview reproduces the production server locally, and the checklist pins secrets, versions, and security headers before the deploy.

Prefer adapter-auto while developing and only pin a specific adapter when you commit to a host — the app code never changes.

10 · Advanced Patterns

10.1 Streaming data and progressive resolution10.2 Snapshots10.3 Service workers for offline apps10.4 Testing with Playwright and Vitest10.5 Performance levers

Covers streaming, snapshots, service workers, testing, and the performance levers SvelteKit gives you. These advanced techniques take a good app and make it polished. Each pattern builds on the fundamentals covered in the earlier chapters.

10.1 Streaming data and progressive resolution

Streams independent server queries to the client as they finish. The page paints instantly and each chunk of data arrives when it is ready. This keeps the first paint fast without waiting on the slowest query.

// src/routes/report/[id]/+page.server.js
export function load() {
  return {
    meta: getMeta(),           // fast: blocks nothing
    chart: slowChart(),        // promise: streams in when resolved
    table: slowerTable(),      // another independent promise
  };
}

// limit what streams to specific clients if needed
export const config = { ssr: true };

Returning several promises from server load lets each resolve on its own timeline, and SvelteKit streams each chunk to the browser as it completes.

<!-- src/routes/report/[id]/+page.svelte -->
<script>
  export let data;
  let { meta } = data;   // already available at first paint
</script>

<h1>{meta.title}</h1>

{#await data.chart}
  <p>Chart loading…</p>
{:then chart}
  <img alt="chart" src={chart.src} />
{/await}

The page renders the resolved meta immediately and each {#await} block swaps in its own data the moment its promise resolves — progressive enhancement of rendering.

10.2 Snapshots

Preserves ephemeral component state across client-side navigations. The snapshot module registers capture and restore functions so a partially-filled form survives leaving and returning to a page. SvelteKit saves and restores the returned state hash on each navigation automatically.

<!-- src/routes/search/+page.svelte -->
<script>
  let query = '';
  let results = [];
  let loading = false;

  // exported from the instance script: SvelteKit wires it up automatically
  export const snapshot = {
    capture: () => ({ query, results }),   // saved when you navigate away
    restore: (value) => {                   // replayed when you come back
      query = value.query;
      results = value.results;
    },
  };
</script>

<input bind:value={query} placeholder="Search…" />

The snapshot export saves the search state before the Svelte component is destroyed and restores it on return, so back-navigation keeps your query and results.

Do not put secrets or large blobs in snapshots — the value lives in history.state and is visible in the browser.

10.3 Service workers for offline apps

Adds an offline layer with the service-worker module. The worker caches the app shell and static assets, and only revalidates on new builds based on the version string. This is how you build apps that keep working without a connection.

// src/service-worker.js — automatically wired up and registered in production
import { build, files, version } from '$service-worker';

const CACHE = `static-${version}`;   // version changes on every build

self.addEventListener('install', () => {
  caches.open(CACHE).then((c) => c.addAll(build));   // cache the app shell
  self.skipWaiting();
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys()
      .then((keys) => Promise.all(keys
        .filter((k) => k !== CACHE)
        .map((k) => caches.delete(k))))   // purge stale caches
  );
});

The service worker caches the built app shell under a versioned key, and activate purges old versions, so updates arrive without stale assets.

Covers end-to-end browser tests and fast unit tests. Playwright drives a real browser against the built app, while Vitest covers functions and components in isolation. Both were offered by the scaffolder and run as scripts in your project.

npm create svelte@latest my-app      # pick "Playwright" and "Vitest" options

10.5 Performance levers

Lists the highest-impact performance levers: prerendering static routes, prefetching link data, splitting bundles, and streaming. Measure with an audit or a profiler before you optimise so you fix real bottlenecks. Small, targeted changes give the biggest wins.
