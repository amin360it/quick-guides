0.1 What an Electron service app is, and the four deployment targets

An Electron service app is an application built with the Electron framework — the same framework as VS Code, Slack, and Discord — and deployed to one of four targets: a Linux desktop application, a Windows Service (a background process managed by the Service Control Manager), a Linux Service (a background systemd unit), or a Linux CLI tool.

Why Electron, and what it costs

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

Electron bundles the Chromium rendering engine and the Node.js runtime into one process. The result is an app that can render a web UI and access the local filesystem, network, and native OS APIs — the same technology as a browser tab, with access that a browser cannot have. Then the four deployment targets, and each is a different package. Linux GUI, — a .desktop entry pointing at an Electron-built binary wrapped in a shell script. Windows Service, — a Win32 Service registered with the Service Control Manager via a native module or the node-windows library. Linux Service, — a systemd unit file pointing at the Electron-built binary. Linux CLI, — the same Electron process with a --headless flag, or a plain Node.js script compiled with electron-builder. Then the three things Electron costs you. At minimum, the Electron binary is 150 MB, because it embeds Chromium. A simple app can easily become 200 MB on disk. Memory is similarly large, because the Chromium renderer in each window is a full browser tab. Then the two practices. Minimise the renderer process footprint — use a single renderer window and embed the heavier UI elements in the main process when possible. Use electron-builder for deployment artifacts — it produces the .deb for Linux, the .msi for Windows, and the .dmg for macOS by reading the package.json's build section. Then the one security rule. Never enable nodeIntegration in a renderer exposed to untrusted content, because it gives the renderer, and any injected script inside it, the ability to write files and spawn processes. Use a preload script with contextBridge to expose only the specific APIs the renderer needs.

/* Electron main process: index.js.
   IMPORTANT: the main process is the only one that can use the
   full Node.js API and the BrowserWindow. All other windows and
   web pages are renderer processes — they get a subset. */

const { app, BrowserWindow, ipcMain } = require('electron');

let mainWindow;

function createWindow() {
  mainWindow = new BrowserWindow({
    width: 800,
    height: 600,
    webPreferences: {
      // SECURITY: keep nodeIntegration off and use a preload script
      nodeIntegration: false,
      contextIsolation: true,
      preload: './preload.js',
      sandbox: true,
    },
  });

  mainWindow.loadFile('index.html');
}

app.whenReady().then(createWindow);

app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit();
});

/* package.json build config for electron-builder.
   This is the part that makes the binaries downloadable. */

{
  "name": "my-service-app",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "start": "electron .",
    "dist": "electron-builder --publish=never"
  },
  "build": {
    "appId": "com.mycompany.serviceapp",
    "productName": "Service App",
    "linux": {
      "target": "AppImage"
    },
    "win": {
      "target": "nsis"
    },
    "mac": {
      "target": "dmg"
    }
  }
}

/* electron-builder reads this section and produces:
   dist/Service App-1.0.0.AppImage  (Linux portable)
   dist/Setup Service App 1.0.0.exe (Windows installer)
   dist/Service App-1.0.0.dmg       (macOS disk image)
   Run: npm run dist */
