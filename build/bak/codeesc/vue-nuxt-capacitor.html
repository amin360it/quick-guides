Welcome - How to Use This Guide

0.1 How this guide is organised0.2 The right mindset0.3 Tools and prerequisites

This guide takes a Vue or Nuxt codebase and turns it into a shipped iOS and Android app with Capacitor. It assumes you already know Vue and is explicit about the decisions that are specific to running inside a native web view.

There are three things that make a Capacitor app different from the same code in a browser, and they run through every chapter:

  • You do not control the origin. The app loads over capacitor://localhost or https://localhost, not a real domain. That affects routing, cookies, storage and CORS.
  • You do not control the device's clock or network. The app is suspended in the background, offline on trains, and the battery is not yours.
  • You do not control the release cadence. Native binaries are gated by two stores, so anything that must change often belongs in the web layer and needs a path to ship without a review.

0.1 How this guide is organised

Maps the three parts of the guide so you can jump straight to the decision you need to make.

  • Part I (Ch. 1-5) - foundations: choosing between a Vue SPA and a Nuxt app, project setup, reactivity inside a web view, Nuxt's rendering modes on native, and routing.
  • Part II (Ch. 6-10) - building: state with Pinia, an offline-first data layer, safe-area-aware styling, deep links, and wrapping the Capacitor plugin layer so the rest of the app never imports it directly.
  • Part III (Ch. 11-14) - shipping: performance measured on a real device, testing with a mocked native layer, the release pipeline, and a reference appendix.

0.2 The right mindset

Four beliefs that keep a Vue app from becoming a slow, fragile one inside a native shell.

  1. Keep the native boundary in one folder. Nothing outside src/native/ may import @capacitor/*. Everything else asks a service. This is what makes the app testable and the web build possible.
  2. Never assume the network. Design the data layer so the first render reads from local storage and the network is an enhancement. This is not optional on mobile.
  3. Treat the frame budget as a hard limit. A Vue app that is smooth on a laptop can drop frames badly on a phone. Measure on the device.
  4. Design the failure state first. No permission, offline, slow network, and a killed background task are not edge cases. They are the normal states of a mobile app.

0.3 Tools and prerequisites

The toolchain, and the two platform facts that constrain your whole plan.

// core
node 18+
vue 3.4+          (reactive core)
vue-router 4
pinia 2+          (state)
vite 5+           (build)
@capacitor/core, @capacitor/cli
@capacitor/android, @capacitor/ios

// optional
nuxt 3            (only if you chose the Nuxt path, chapter 4)
@pinia/nuxt
vitest            (testing)
@vue/test-utils

// native toolchain
Android Studio + JDK 17  (Android builds)
Xcode 15+ + CocoaPods    (iOS builds, macOS only)

iOS builds require macOS. There is no workaround and no way around it: the iOS SDK, the codesign tool and the simulator only exist on macOS. If your team is Windows or Linux, plan for a macOS CI runner (GitHub Actions macos-latest is the standard answer) and keep the local iOS iteration optional.

Exercises 1

  1. Install the toolchain and run npx cap --version. Create a Vue 3 + Vite project and add the Android platform.
  2. Write down, for your own app, which of the three realities from the opening list you are most likely to get wrong. You will revisit it at the end of the guide.
  3. Read the four mindset points and check them against a codebase you have shipped before. Note which ones you violated.

1.1 Vue SPA with Vite

What you get, what it costs, and the one config line people forget.

Why a SPA works inside a web view

A Vue single-page app is the simplest thing that works. Vite builds it to static files, Capacitor copies them into the app, and Vue Router runs entirely client-side. No server exists at runtime, so there is nothing to configure for the native origin. That absence of a server is a feature, not a limitation: no CORS headers to negotiate, no SSR hydration mismatch to debug, no server process to keep alive. The entire app is a folder of files the web view reads from disk.

The trade-off is that everything client-side means everything lives in the JavaScript bundle. Components, router state, Pinia stores — all of it downloads, parses and executes on the first launch. On a phone with a slower CPU and no warm cache, that cold start is the thing users notice most, which is why the build pipeline matters more here than it does on the web.

// vite.config.js - the one line that matters for Capacitor
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  base: './',                 // RELATIVE paths, because there is no server root
  plugins: [vue()],
  build: {
    target: 'es2019',         // matches the oldest web view you support
    sourcemap: true,          // essential: the error overlay in production
    rollupOptions: {
      output: {
        // keep the first chunk small; split the heavy views
        manualChunks: {
          vendor: ['vue', 'vue-router', 'pinia'],
        },
      },
    },
  },
});

The base path and the blank-screen trap

base: './' is the setting that turns a blank white screen into a working app. Vite defaults base to '/', which produces absolute asset paths like /assets/index.js. On a web server those resolve correctly because the server root is /. Inside a Capacitor app there is no server root — the web view reads from capacitor://localhost or https://localhost — so every absolute asset request 404s and the page renders nothing.

The failure is silent in the worst way: the app launches, shows a blank screen, and the only symptom in the console is a series of failed asset requests. The fix is one line, but it is the line everyone forgets because it is invisible during web development where base: '/' is correct.

// the wrong config, and what it produces
export default defineConfig({
  base: '/',     // WRONG: absolute paths 404 inside the app
});

// the right config
export default defineConfig({
  base: './',    // RIGHT: relative paths resolve against the app origin
});
