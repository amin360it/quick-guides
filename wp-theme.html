Orientation - Scope, Baseline and the Theme Contract

0.1 Scope and exclusions0.2 Version and platform baseline0.3 The theme contract0.4 How WordPress loads a theme0.5 How to read this guide

Establishes what a WordPress theme is responsible for, what it is not, and the version baseline every example in this guide targets. It also documents the contract WordPress enforces when it loads a theme, because nearly every production theme defect traces back to a misunderstanding of that contract.

0.1 Scope and exclusions

Defines the boundary of theme development and names the adjacent systems a theme integrates with rather than reimplements.

A theme is a PHP and asset bundle that renders the public-facing surface of a WordPress site. It owns presentation, not content. The database schema, the role system, the REST API and the plugin architecture are core responsibilities. A theme that creates tables, provisions users or proxies third-party services has crossed the line and will fail theme review.

Four areas are deliberately excluded. Plugin architecture appears only where a theme must declare an extension point for plugins. Schema design is out of scope: themes read and write rows, they do not create tables. Server configuration is limited to the wp-config.php constants that change theme behaviour. Multisite is out of scope except where is_multisite() changes a documented decision.

0.2 Version and platform baseline

Pins the platform versions every code sample in this guide is written against.

ComponentBaselineConsequence for theme code
WordPress6.7Script Modules are stable; wp_get_global_settings() is available; theme.json version 3 is current.
PHP8.3Typed properties, readonly, enums, first-class callable syntax, json_validate(), and strict undefined-key notices are all fair game.
MySQL / MariaDB8.0 / 10.6Assume 5.7+ semantics only. Avoid window functions and CTEs.
EditorsGutenberg 20.xBlock APIs in the 6.x generation are stable.

The declared headers matter. A theme distributed through the directory declares Requires at least: 6.7, Tested up to: 6.7 and Requires PHP: 8.0 or higher. Claiming a Tested up to value beyond what you have actually run is a review rejection, not a technical shortcut.

PHP 8 raises the bar. Undefined array keys, undefined properties and null passed to a string parameter are now notices or TypeError fatals rather than silent coercion. Code that ran on PHP 7.4 will crash on PHP 8.3. Audit every $value['key'] and every strlen( $maybe_null ) before shipping.

0.3 The theme contract

Enumerates the guarantees WordPress makes to a theme, and the guarantees a theme must make in return.

WordPress guarantees a theme a defined directory, a registered stylesheet, a working query object before any template is parsed, and a complete set of core template functions. A theme guarantees the reciprocal: templates parse without side effects, templates do not assume a query, and every value echoed into HTML is escaped for its exact output context.

Guaranteed by coreRequired of the theme
Filesystem path via get_template_directory()Resolve all asset URLs through get_template_directory_uri() or get_stylesheet_directory_uri().
Global $wp_query is populated before index.php runsNever mutate $wp_query or $post in a template without restoring it.
Core template functions exist in every themeDo not redeclare a core function name, including in functions.php.
Output buffering around template partsEmit balanced HTML in every template fragment.

Plugin priority. Plugins run their code first. A theme that assumes exclusive control of an action, filter or global state is a theme that will break on a real site. Register at the default priority unless a documented conflict requires otherwise.

0.4 How WordPress loads a theme

Traces the request from bootstrap to template parse, and marks the exact points at which theme code first executes.

For a front-end request, wp-blog-header.php sets WP_USE_THEMES, loads wp-load.php, and the bootstrap chain reaches wp-settings.php. WordPress reads the active_theme option, locates the theme root, registers its stylesheet with register_theme_directory() semantics, and then loads functions.php if present. Only after that does it fire after_setup_theme, load plugins, fire init, fire wp_loaded, and dispatch the request to a template.

// Order of first execution. Registering on a later hook than the
// one that consumes your data is the single most common cause of
// "my theme support is not showing up".
add_action( 'after_setup_theme', mytheme_setup );   // theme supports, menus, image sizes
add_action( 'init',           mytheme_content_types ); // CPTs, taxonomies, post meta
add_action( 'widgets_init',  mytheme_widgets );      // sidebars and widget areas
add_action( 'wp_enqueue_scripts', mytheme_assets ); // styles and scripts

Two consequences follow. First, functions.php is included exactly once per request, before init, so anything that depends on a post type must run on init. Second, the admin request lifecycle differs: admin.php never loads a front-end template, so a template file that calls wp_head() unconditionally will emit a notice when loaded in an admin context. Guard with is_admin() or, better, with an explicit hook.

0.5 How to read this guide

Describes the reference conventions used throughout: code fidelity, escaping expectations and the exercise loop.

Every code sample is production-shaped: real hook names, real function names, real argument keys. Where a sample elides work, the elision is marked with a comment rather than an ellipsis. Escaping is not optional in any sample containing output; if a sample prints a value without an escaping call, that omission is itself the subject of the surrounding prose.

Each chapter ends with a set of exercises. Treat them as verification, not reading. A theme is a system that is validated by executing it, and reading about esc_attr() teaches less than one deliberately broken template that proves the escaping was load-bearing.

1 · The Anatomy of a Classic Theme

Defines the three files WordPress requires before it will recognise a classic theme, the exact header keys those files must carry, and the structure a production theme grows into. Read this chapter before touching any other chapter: everything later assumes the layout established here.

1.1 style.css and the theme header

Documents the theme manifest, which WordPress parses as plain CSS comments, and the keys required for directory distribution.

A directory becomes a theme the moment it contains a style.css whose first comment block declares Theme Name. That block is the only file the database stores anything about. WordPress re-parses it on every admin theme screen, which is why editing the header has an immediate visible effect but renaming the directory does not.

/*
Theme Name: Meridian
Theme URI: https://example.com/meridian
Author: Example Studio
Author URI: https://example.com
Description: A production classic theme with full block-editor support.
Version: 2.4.1
Requires at least: 6.7
Tested up to: 6.7
Requires PHP: 8.0
License: GNU General Public License v2 or later
License URI: https://www.gnu.org/licenses/gpl-2.0.html
Text Domain: meridian
Tags: block-styles, wide-blocks, custom-menu, custom-logo, featured-images, translation-ready
Requires PHP: 8.0
*/
KeyRequiredNotes
Theme NameYesPlain text. Must not contain markup.
VersionYesUsed by the updater and by child-theme cache busting.
LicenseYesMust be GPL-compatible. The directory rejects anything else.
Text DomainDirectoryMust match the theme folder slug exactly.
Requires PHPRecommendedPrevents activation on incompatible hosts.
Requires blocksBlock themesComma-separated minimum core block versions.

The header is CSS, not a config file. Any character that breaks the comment block breaks discovery. Never place a literal */ inside a description, and never nest block comments.

1.2 index.php as the universal fallback

Explains why the least specific template is the most important one, and how it behaves when queried.

index.php is the last template WordPress looks for. Every request that matches no more specific template lands here, and a theme without it is treated as broken. Many commercial themes ship a index.php that is a bare get_header(); while ( have_posts() ) : the_post(); get_template_part(); endwhile; get_footer(); sequence precisely so the site keeps rendering while a more specific template is being written.

index.php is not the home page. The home page is resolved through front-page.php then home.php. Naming a template index.php and expecting it to be the blog index is the most common beginner misconception, and it is harmless once stated once.

For static front pages, WordPress uses front-page.php for both the static page and the posts page when one is defined. When a static page is set, is_home() and is_front_page() are both true for the posts page and only is_front_page() is true for the static page. Templates that branch on these two conditionals must handle all three combinations or they will render the wrong layout.

1.3 functions.php and load order

Establishes functions.php as a plain include with no namespace, no autoloader guarantee, and a load order that precedes init.

functions.php is included with a plain include inside an anonymous function scope, which means it shares the global namespace. It is not namespaced, not autoloaded, and executed exactly once per request before init. It must therefore be defensive about the order in which it registers things.

if ( ! defined( 'ABSPATH' ) ) {
    exit;
}
define( 'MERIDIAN_VERSION', '2.4.1' );
define( 'MERIDIAN_DIR',    get_template_directory() );
define( 'MERIDIAN_URI',    get_template_directory_uri() );

The ABSPATH guard is the convention that permits a theme to be required by a plugin without executing over HTTP. Split the file so that the declarations run unconditionally but the hook registrations sit behind function definitions; the split keeps the file testable and keeps side effects in one place.

Do not return early from functions.php. A return at file scope inside the theme bootstrap has bitten themes that are loaded through a child theme, because the include is expected to complete. Structure the file with functions, and let the hook callbacks be the only executable statements.

1.4 A complete minimal classic theme

Shows the smallest classic theme that satisfies review, with the header, footer, content and search templates fully formed.

The following is the complete file set of an acceptable classic theme. The header.php calls wp_head() inside wp_body_open() and wp_footer() in the footer, which is the non-negotiable contract for assets and admin bar injection.

// header.php
<!DOCTYPE html>
<html <?php language_attributes(); ?>>
<head>
    <meta charset="<?php bloginfo( 'charset' ); ?>">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <?php wp_head(); ?>
</head>
<body <?php body_class(); ?>>
<?php wp_body_open(); ?>
<a class="skip-link" href="#primary"><?php esc_html_e( 'Skip to content', 'meridian' ); ?></a>
<header class="site-header">...</header>

// index.php
<?php get_header(); ?>
<main id="primary" class="site-main">
    <?php if ( have_posts() ) : // phpcs:ignore WordPress.WP.AlternativeFunctions
        <?php while ( have_posts() ) : the_post(); ?>
            <?php get_template_part( 'template-parts/content', get_post_type() ); ?>
        <?php endwhile; ?>
        <?php the_posts_pagination(); ?>
    <?php else : ?>
        <?php get_template_part( 'template-parts/content', 'none' ); ?>
    <?php endif; ?>
</main>
<?php get_footer(); ?>

1.5 screenshot.png and readme.txt

Covers the two non-code files that determine whether a theme is usable by an administrator choosing between it and nine others.

screenshot.png is displayed at 1200 by 900 pixels in the theme picker. A screenshot that is a raw page capture of unstyled content will not be approved; the reviewer requires a composed representation of the finished design. Keep it under 1 MB so the picker stays responsive across a hundred themes.

readme.txt is the parser. It follows the same field format as a plugin readme, and the description is used verbatim on the directory page. Keep the short description to 150 characters or fewer, and put installation steps under == Installation == as a numbered list. Anything that requires a paid add-on must be stated in the description, not discovered after activation.

2 · Block Themes: theme.json, Templates, Parts and Patterns

Describes the block theme architecture introduced in WordPress 5.9 and stabilised through 6.7: declarative templates, the theme.json schema, and patterns. This is the architecture new themes are reviewed against, and the direction block themes will develop in.

2.1 The block theme file model

Enumerates the directory layout WordPress recognises and the conditions that make a theme a block theme.

A theme is a block theme if it contains a templates/index.html file. That single file is the discriminator; everything else follows from the presence of the templates directory and, usually, a root theme.json.

PathPurpose
templates/index.htmlPresence marks the theme as a block theme. Universal fallback template.
templates/single.htmlSingle post, all post types.
templates/page.htmlStatic page.
templates/home.htmlPosts index.
templates/front-page.htmlStatic front page.
templates/archive.html, category.html, tag.html, taxonomy.html, author.html, date.html, search.html, 404.htmlContextual templates mirroring the classic hierarchy.
parts/header.html, parts/footer.htmlTemplate parts referenced with <!-- wp:template-part {"slug":"header","tagName":"header"} /-->.
patterns/*.phpPHP files that return block markup and register as patterns.
theme.jsonDesign tokens, global styles, block style overrides.
functions.phpStill supported for enqueues, patterns registration, editor styles and block style registration.

WordPress reads these files directly from disk. Templates are not PHP and are not rendered by PHP; the block renderer converts the comment-delimited markup into a stored post or a rendered output. A PHP error cannot occur inside a templates/ file, which removes an entire category of theme failure.

2.2 theme.json and the versioned schema

Defines the layered settings model and the exact top-level keys a version 3 file accepts.

theme.json merges with core defaults and with user customisations through a three-layer cascade. Later layers win, which is why a user who changes a colour in the Site Editor sees their value survive a theme update.

{
  "$schema": "https://schemas.wp.org/trunk/theme.json",
  "version": 3,
  "settings": {
    "appearanceTools": true,
    "useRootPaddingAwareAlignments": true,
    "color": {
      "palette": [
        { "slug": "base",   "color": "#ffffff", "name": "Base" },
        { "slug": "contrast", "color": "#101418", "name": "Contrast" },
        { "slug": "accent",  "color": "#2b5cd9", "name": "Accent" }
      ],
      "gradients": [],
      "custom": false,
      "defaultPalette": false
    },
    "typography": {
      "fluid": true,
      "fontSizes": [
        { "slug": "small",  "size": "0.875rem",  "name": "Small" },
        { "slug": "medium", "size": "1rem",     "name": "Medium" },
        { "slug": "large",  "size": "clamp(1.5rem, 1.2rem + 1.5vw, 2.25rem)", "name": "Large" }
      ]
    },
    "spacing": { "units": [ "px", "rem", "%", "vw" ], "defaultSpacingSizes": false },
    "layout": { "contentSize": "48rem", "wideSize": "72rem" },
    "blocks": {
      "core/button": { "border": { "radius": true } },
      "core/site-title": { "typography": { "fontSize": "large" } }
    }
  },
  "styles": {
    "color": { "background": "var(--wp--preset--color--base)", "text": "var(--wp--preset--color--contrast)" },
    "spacing": { "blockGap": "1.5rem", "padding": { "left": "clamp(1rem, 4vw, 4rem)", "right": "clamp(1rem, 4vw, 4rem)" } },
    "typography": { "fontFamily": "var(--wp--preset--font-family--body)", "lineHeight": "1.6" },
    "elements": {
      "link": { "color": { "text": { "color": "var(--wp--preset--color--accent)" } } },
      "button": { "color": { "background": "var(--wp--preset--color--accent)", "text": "var(--wp--preset--color--base)" } }
    },
    "blocks": {
      "core/site-title": { "color": { "text": "var(--wp--preset--color--contrast)" } },
      "core/post-title": { "typography": { "fontSize": "large", "lineHeight": "1.15" } }
    }
  },
  "templateParts": [
    { "name": "header", "title": "Header", "area": "header" },
    { "name": "footer", "title": "Footer", "area": "footer" }
  ],
  "customTemplates": [
    { "name": "template-full-width", "title": "Full width, no sidebar", "postTypes": [ "page" ] }
  ]
}

Version is not optional and not decorative. "version": 3 enables root padding-aware alignments, fluid typography and the 6.7 defaults. Omitting the key makes WordPress treat the file as version 1, silently discarding settings it does not recognise in that generation. Set it explicitly to 3.

Prefer presets over raw values. Referencing var(--wp--preset--color--accent) rather than a hex literal means a user who edits the palette in the Site Editor changes your design everywhere at once. Raw hex in styles is the single most common reason a block theme "does not respond to the editor".

2.3 HTML templates and template parts

Shows the block markup that constitutes a template, and how parts are composed and overridden.

<!-- wp:template-part {"slug":"header","tagName":"header","className":"site-header"} /-->

<!-- wp:group {"tagName":"main","layout":{"type":"constrained"},"className":"site-main"} -->
    <!-- wp:group {"layout":{"type":"constrained"},"style":{"spacing":{"blockGap":"var:preset|spacing|50"}}} -->
        <!-- wp:post-title {"level":1,"isLink":true,"style":{"spacing":{"margin":{"bottom":"var:preset|spacing|40"}}}} /-->
        <!-- wp:post-date {"fontSize":"small"} /-->
    <!-- /wp:group -->

    <!-- wp:post-featured-image {"align":"wide","style":{"border":{"width":"1px"}}} /-->

    <!-- wp:post-content {"layout":{"type":"constrained","contentSize":"48rem"}} /-->

Templates in the Site Editor are post objects of type wp_template once a user edits them, held in the database and overriding the file on disk. A user change therefore survives a theme update, which is the correct behaviour and also the reason themes must not assume the file version is what is being rendered. Use get_block_template() if you need to know which source won.

2.4 Block patterns and their front matter

Documents pattern registration, the PHP docblock header, and the correct way to ship patterns in a theme.

Since WordPress 6.0 a theme or plugin can drop PHP files into a patterns/ directory and WordPress registers them automatically if the file returns block markup preceded by a specific docblock. No register_block_pattern() call is required for that path, and the file must not echo.

// patterns/hero-home.php
<?php
/**
 * Title: Home hero with call to action
 * Slug: meridian/home-hero
 * Categories: featured, banner
 * Description: Full-width hero with heading, text and two buttons.
 * Keywords: hero, cta, banner
 * Viewport Width: 1440
 * Block Types: core/group
 * Inserter: yes
 */
?>
<!-- wp:group {"align":"full","layout":{"type":"constrained"},"style":{"spacing":{"padding":...}}} -->
    <!-- wp:heading {"level":1,"fontSize":"large"} -->
        <!-- wp:heading-content -->Ship faster<!-- /wp:heading-content -->
    <!-- /wp:heading -->
    <!-- wp:paragraph --><!-- wp:paragraph-content -->Built for agencies.<!-- /wp:paragraph-content --> -->
    <!-- wp:buttons -->
        <!-- wp:button --><!-- wp:button-content -->Read the docs<!-- /wp:button-content --><!-- /wp:button -->
    <!-- /wp:buttons -->

Categories and keywords drive discovery. A pattern in the featured category appears in the inserter’s front row. An uncategorised pattern is effectively invisible. Also add Viewport Width so the inserter preview matches real rendering, and Inserter: no for parts that only make sense inside a template.

2.5 Hybrid themes and phased templates

Explains running classic templates alongside block templates so one theme can support both rendering engines.

A hybrid theme registers a block type that renders through PHP while keeping index.php and friends for the rest of the site. Core ships three: core/query, core/post-content and core/post-template, each filterable with render_block_{$block_name}. This is the supported migration path for a mature classic theme that cannot be rewritten wholesale.

add_filter( 'render_block_core/post-content', 'meridian_post_content', 10, 2 );
function meridian_post_content( $block_content, $block ) {
    if ( ! isset( $block['attrs']['legacy'] ) ) {
        return $block_content;
    }
    ob_start();
    while ( have_posts() ) {
        the_post();
        the_content();
    }
    return ob_get_clean();
}

Phased templates are the transition mechanism, not the destination. Each phased template you add is a fallback path you must test on every update. Prefer a clean classic theme with add_theme_support( 'align-wide' ) and good block support if you are shipping today; it is far simpler to maintain than a dual-engine theme.

Documents the exact algorithm WordPress uses to choose a template, the conditional tags that describe the current query, and the filters that let plugins and child themes override the outcome. Template bugs are hierarchy bugs; this chapter is the reference you will return to.

3.1 The full resolution order

Presents the resolution order for the most commonly confused request types.

WordPress builds an ordered list of candidate filenames, walks it from the top, and uses the first file that exists in the child theme, then the parent theme, then the active theme directory. The search is not recursive: only files at the theme root are considered unless the query is a custom post type with a {custom}-{plural}.php convention.

3.2 Conditional tags as query facets

Explains that conditional tags read the main query, not the current post, and how to test a secondary query correctly.

Conditional tags inspect the global $wp_query. A template that has started a WP_Query loop of its own will still report is_home() as true unless the global query was changed. Where a template needs to know what the current object is, use the function form with an explicit query object rather than a template-level branch.

// Correct: inspect the loop WordPress is actually running.
while ( have_posts() ) {
    the_post();
    if ( is_singular( 'book' ) ) {
        echo get_the_title();
    }
}

// Wrong: is_singular() ignores $post entirely.
// $post tells you the object; the conditional tells you the query.

For a secondary query, call is_singular( 'book' ) is not valid; the correct approach is to test the post type directly, or to inspect the WP_Query instance you constructed. Do not swap the global query with $GLOBALS['wp_query'] to make conditionals work; use wp_reset_postdata() and test the object.

3.3 get_template_part and the part cascade

Documents part resolution, the arguments parameter, and the get_template_part_{$slug} filter.

// 1st arg: base name in template-parts/. 2nd: specific variant.
// 3rd: array of variables extracted into the part's scope.
get_template_part( 'template-parts/content', get_post_type(), array(
    'show_thumbnail' => true,
    'heading_level' => 'h2',
) );

Part lookup is template-parts/{slug}-{name}.php then template-parts/{slug}.php, searched in the child theme before the parent. Because the slug and name are concatenated into a path, always pass values that are internal to the theme. Passing user-controlled data into get_template_part() is a local file inclusion vector; the sanitising helper sanitize_file_name() does not make it safe, because a valid sanitised name still lets an attacker include an unintended file.

Never build part slugs from request data. get_template_part( 'content-' . $query ) where $query comes from a URL is a file inclusion bug. Map input to a closed set of allowed slugs with a match or an array_intersect_key against a whitelist.

4 · The Loop, the Global $post and Why It Is Dangerous

4.1 Loop anatomy4.2 The global $post and its aliases4.3 Nested loops and wp_reset_postdata4.4 Template tags that depend on the loop4.5 Secondary queries done correctly

Explains the loop’s internals, why it mutates global state, and the two failure modes that account for most theme bugs: forgotten loop resets and reliance on $post after the loop has advanced. Every template you write after this chapter should be written with these constraints in mind.

4.1 Loop anatomy

Decomposes the three functions that constitute the loop and the cursor each one advances.

The loop is not a language construct. It is three global functions reading and writing a shared iterator, plus a stack for the data they read.

while ( have_posts() ) :   // Moves $wp_query->current_post forward. Returns false when exhausted.
    the_post();              // Copies the current row into global $post and $authordata.
    <?php // Template output using the current $post. ?>
endwhile;
rewind_posts();          // Resets the cursor. Required before a second loop over the same query.

have_posts() reads the post_count and current_post properties of the main WP_Query. the_post() calls WP_Query::the_post(), which calls setup_postdata() after assigning $GLOBALS['post']. That is why template tags that take no arguments can read from a global: they are shorthand for methods on the current row, and they work only while the loop is positioned on it.

have_posts() is a main-query function. It has no query argument. A secondary query is iterated with its own object’s methods, not with have_posts(). Passing arguments to have_posts() is a common and silently ignored mistake.

4.2 The global $post and its aliases

Catalogues the globals the loop sets and the exact failure that occurs when a template reads them at the wrong time.

the_post() sets $GLOBALS['post'] and a $GLOBALS['more'] flag, calls setup_postdata() to populate a set of extractor variables, and fires the the_post action. The extractor variables are the ones template tags read.

These variables are only meaningful between the_post() and the next the_post(). After the loop ends, $post refers to the last post in the query, not to the post the template is conceptually "about". Any function that accepts no post argument and is called after the loop therefore reads the wrong row. This is the mechanism behind the classic bug where a byline on the last article in an archive shows the first author’s name.

4.3 Nested loops and wp_reset_postdata

Shows the correct nested loop pattern and the precise corruption that omitting the reset causes.

<?php while ( have_posts() ) :
    the_post();
    // 1. Save the outer loop's cursor and post object.
    wp_reset_postdata();

    // 2. Build a secondary query.
    $related = new WP_Query( array(
        'post_type'              => 'post',
        'posts_per_page'         => 3,
        'post__not_in'           => array( get_the_ID() ),
        'ignore_sticky_posts'    => true,
        'no_found_rows'          => true,
        'update_post_meta_cache'  => false,
        'update_post_term_cache'  => false,
    ) );

    // 3. Iterate the secondary query WITHOUT have_posts()/the_post().
    foreach ( $related->posts as $related_post ) {
        setup_postdata( $related_post );
        echo get_the_title( $related_post ) . '<br>';
    }

    // 4. Restore the outer loop before continuing.
    wp_reset_postdata();
endwhile;

Steps 2 and 4 matter. If step 4 is omitted, the outer loop’s $wp_query cursor is untouched but the global $post now points at the last related post, so every subsequent call to the_title() in the outer loop prints the wrong title. If a secondary query is iterated with $secondary->have_posts() and $secondary->the_post(), the global $post is clobbered the same way; the reset is still required.

Symmetry is the rule. Every setup_postdata() needs a matching wp_reset_postdata() on every exit path, including early returns and exceptions. A helper that calls setup_postdata() and returns early without resetting will corrupt the caller’s loop in a way that is extremely hard to trace.

4.5 Secondary queries done correctly

Covers the arguments that distinguish a cheap secondary query from an expensive one, and the caching consequences.

A secondary query is a real database query. On an archive of twenty posts, each with a three-post related list and no caching flags, a page issues twenty-one queries. The four flags that change this are set out below, and their omission is the most common performance defect in commercial themes.

5 · Escaping: Output Contexts and Sanitisation

5.1 The five output contexts5.2 The escaping function for each context5.3 wp_kses and allowed HTML5.4 Sanitisation on input versus escaping on output5.5 Defensive patterns and audits

Establishes the non-negotiable rule of theme output: every value reaching HTML is escaped for the context it lands in. This chapter maps each context to its function, distinguishes escaping from sanitisation, and gives the audit procedure for an existing codebase.

5.1 The five output contexts

Names the distinct HTML contexts a theme can emit into and why one escaping function cannot serve all of them.

An escaping function is correct only for the sink it targets. Using esc_html() inside a src attribute blocks exploitation but also blocks legitimate URLs containing &, because the ampersand is double-encoded. The contexts a theme actually produces are these five.

ContextSinkFunction
HTML text node<p>VALUE</p>esc_html()
Attribute valuetitle="VALUE"esc_attr()
URL in href/srchref="VALUE"esc_url()
Raw HTML fragment<div>VALUE</div>wp_kses_post() or wp_kses( $v, $allowed )
JavaScript stringvar x = "VALUE";wp_json_encode() then escape the surrounding script

Two additional contexts matter in practice. Inside a <script> block, a </script> sequence inside a string literal terminates the block, which is why wp_json_encode() alone is insufficient for HTML-embedded scripts and wp_add_inline_script() should be preferred. Inside a CSS value, use wp_strip_all_tags() plus a numeric or colour whitelist; there is no general CSS escaper in core.

5.2 The escaping function for each context

Provides the canonical call for each sink, including the two-argument forms and the raw variants.

// HTML text node.
<h2><?php echo esc_html( get_the_title() ); ?></h2>

// Attribute value, including array keys built from data.
<section id="<?php echo esc_attr( $section_id ); ?>" class="panel">

// URL in href. Display and stored forms differ.
<a href="<?php echo esc_url( get_permalink() ); ?>">
    <?php echo esc_html( get_the_title() ); ?>
</a>

// esc_url for output, esc_url_raw for a value going to the database
// or to wp_redirect(). The raw form does not HTML-encode.
wp_safe_redirect( esc_url_raw( $target ) );

// Textarea content. esc_textarea() is esc_html() with newlines preserved.
<textarea><?php echo esc_textarea( $value ); ?></textarea>

// Translated and escaped in one call.
<?php esc_html_e( 'Read more', 'meridian' ); ?>

// JSON into a script block, escaped for the script context.
<script>
    const config = <?php echo wp_json_encode( $config ) | wp_kses_no_null( $x, array() ) | esc_js(); ?>;
</script>

Translated text still needs escaping. __() returns a string and stops there. Use esc_html__(), esc_attr__() or esc_html_e() so the escaping happens after translation. A translator in a language you do not read can otherwise inject a script into your layout.

Double escaping is a real failure mode. Calling esc_attr( esc_html( $v ) ) produces visible &amp; in output. Apply exactly one escaping function at the point of output, to the raw value.

5.3 wp_kses and allowed HTML

Distinguishes the three wp_kses variants and shows how to build a constrained allowlist.

// Post content: uses the post-context allowlist. This is the default for
// the_content() and is almost always what you want.
echo wp_kses_post( $post->post_content );

// A custom context. Start from a known list and add deliberately.
$allowed = array(
    'strong'   => array(),
    'em'       => array(),
    'a'        => array( 'href', 'title', 'target', 'rel' ),
    'br'       => array(),
    'code'     => array(),
    'span'     => array( 'class' ),
);
echo wp_kses( $excerpt, $allowed );

// Reading the allowlist, then extending it, is the documented pattern
// for a shortcode that must accept a subset of post HTML.
$allowed = array_merge( wp_kses_allowed_html( 'post' ), array(
    'iframe' => array( 'src', 'width', 'height', 'allowfullscreen' ),
) );

wp_kses_allowed_html( 'post' ) returns the filtered allowlist, which plugins have already modified. Building an allowlist from scratch instead of extending the filtered one will strip markup that plugins depend on, and will do so silently.

Do not use wp_kses as a substitute for escaping the surrounding attribute. wp_kses( $url, array( 'a' => array( 'href' ) ) ) validates tags, not URL schemes. For a URL sink, esc_url() is the correct function because it enforces the protocol allowlist.

5.4 Sanitisation on input versus escaping on output

States the core rule and provides the sanitisation function for each data type.

Escape late, sanitise early, and do both. Sanitising on input is a user-experience measure that produces a predictable stored value; it is not a security control, because the stored value can be modified by direct database access, by REST, by XML-RPC, or by another plugin. Escaping at output is the security control. A theme that sanitises on input and does not escape on output is exploitable; a theme that escapes on output and does not sanitise on input is merely ugly.

5.5 Defensive patterns and audits

Provides the audit procedure and the helper patterns that make correct escaping the default.

Auditing an existing theme for escaping is tractable. Search for echo and print in template files, then classify each occurrence by sink. Any echo of a variable with no escaping call and no preceding wp_kses is a finding. A useful intermediate step is to make the omission loud rather than silent: install the escaping_linter development dependency, or run a PHPCS ruleset that includes WordPress.Security.EscapeOutput, and treat every reported line as a defect.

<?php
/**
 * Render a term list without exposing raw slugs to markup.
 * @param int    $post_id Post ID.
 * @param string $taxonomy Taxonomy name.
 * @return string Safe HTML.
 */
function meridian_term_list( int $post_id, string $taxonomy ): string {
    $terms = get_the_terms( $post_id, $taxonomy );
    if ( is_wp_error( $terms ) || empty( $terms ) ) {
        return '';
    }

    $items = array();
    foreach ( $terms as $term ) {
        $items[] = sprintf(
            '<li class="term term--%1$s"><a href="%2$s">%3$s</a></li>',
            esc_attr( sanitize_html_class( $term->slug ) ),
            esc_url( get_term_link( $term ) ),
            esc_html( $term->name )
        );
    }

    return wp_kses_post( '<ul class="terms">' . implode( '', $items ) . '</ul>' );
}

Note the deliberate use of int and string parameter types under PHP 8.3. Typed parameters turn an entire class of argument error into a TypeError at the call site, where the stack trace names the offending file, instead of a silent coercion that produces wrong output three layers away.

6.1 Register then enqueue

Explains why handle uniqueness across the whole site matters and how a duplicate handle silently drops an asset.

WordPress keys every registered asset by handle. Enqueuing an already-registered handle does nothing; the previously registered src and dependencies win. Two plugins or a theme and a plugin that both use the handle jquery-ui produce one script, not two, and the loser gets no warning. 6.3 Dependencies, versions and cache busting

Explains dependency arrays, why the version must not be a build hash on a CDN-backed asset, and how filemtime() interacts with caching plugins.

The dependencies array is a declaration of load order, not a bundler. WordPress performs a topological sort, handles the jquery handle alias, and prints scripts in dependency order in the footer. Declaring a dependency you do not actually need creates a hard coupling that will break if the provider is ever deactivated.

// Version from the theme header. One number, bumped per release,
// serves as the cache key for every asset in the theme.
$version = wp_get_theme()->get( 'Version' );

// filemtime() busts the cache per file without a release, which is
// convenient in development and wrong in production: it defeats
// far-future caching and leaks the file system layout.
$dev_version = filemtime( MERIDIAN_DIR . '/assets/js/navigation.js' );

A null version means no cache busting at all. Passing null as the version makes WordPress print the bare file URL. Combined with a page cache that serves the same URL indefinitely, a deploy becomes invisible to every returning visitor until they hard refresh. Always pass a real version.

Do not add a query-string version manually. Appending ?ver=1.2.3 to the src yourself defeats any CDN rewriting, breaks SCRIPT_DEBUG unpacking and duplicates what the version parameter already does. Pass the version as the fifth argument and let core build the URL.

6.4 Passing data: localize, inline, script modules

Compares the three data-passing mechanisms and shows the Script Modules path available in WordPress 6.7.

wp_localize_script() prints var objectName = {...} before the script. It JSON-encodes values but does not escape the surrounding script context, and the object is emitted as a bare global. wp_add_inline_script() prints arbitrary code adjacent to the handle and is the safer general option for theme code. For ES module semantics, WordPress 6.7 stabilised wp_register_script_module() and wp_enqueue_script_module(), which print <script type="module"> tags and resolve an import graph for you.

// Preferred for theme data: inline JSON before the handle's tag.
wp_add_inline_script(
    'meridian-navigation',
    'window.meridianConfig = ' . wp_json_encode(
        array(
            'restUrl'   => esc_url_raw( rest_url( 'meridian/v1/' ) ),
            'nonce'     => wp_create_nonce( 'wp_rest' ),
            'locale'    => get_locale(),
            'isRtl'    => is_rtl(),
        )
    ) . ';',
    'before'
);

// 6.7: module registration and enqueue. The src must be in the theme
// or a directory registered for module resolution.
wp_register_script_module(
    '@meridian/gallery',
    MERIDIAN_URI . '/assets/js/gallery/index.js',
    array( '@wordpress/interactivity' )
);
wp_enqueue_script_module( '@meridian/gallery' );

Never build a nonce for output. A nonce generated for a page’s HTML is valid for that page’s session and is exactly what you want on the front end for an authenticated AJAX call. What you must not do is reuse a REST wp_rest nonce in a way that suggests it is a capability check; it is a CSRF token, and a capability check is still required server-side.

7.1 Registering and rendering navigation

Defines location registration, the theme_location indirection, and the arguments that determine accessible markup.

7.2 Custom walkers and the markup contract

Explains when a walker is warranted, the method signature it must implement, and why the default classes are already sufficient for most themes.

A Walker_Nav_Menu subclass is a way to change the emitted HTML of wp_nav_menu(). The class is invoked by wp_nav_menu() with start_lvl, end_lvl, start_el and end_el. Because the default implementation already emits current-menu-item, current_page_item, current_page_ancestor and submenu classes, a theme that rewrites the walker to add a flyout arrow must re-add all of them or lose current-item indication entirely.

class Meridian_Nav_Walker extends Walker_Nav_Menu {
    public function start_el( &$output, $item, $depth = 0, $args = null, $id = 0 ) {
        $classes   = empty( $item->classes ) ? array() : (array) $item->classes;
        $classes[] = 'menu-item-' . $item->ID;
        $has_kids  = in_array( 'menu-item-has-children', $classes, true );

        $attr = array(
            'href'   => ! empty( $item->url ) ? $item->url : '',
            'class'  => implode( ' ', array_filter( $classes ) ),
            'rel'    => ! empty( $item->xfn ) ? $item->xfn : '',
        );
        if ( $has_kids ) {
            $attr['aria-haspopup'] = 'true';
            $attr['data-toggle']  = 'dropdown';
        }
        if ( in_array( 'current-menu-item', $classes, true ) ) {
            $attr['aria-current'] = 'page';
        }

        $output .= sprintf(
            '<li %1$s><a %2$s>%3$s</a>',
            esc_attr( implode( ' ', $classes ) ),
            esc_attr( wp_json_encode( $attr ) ),
            esc_html( $item->title )
        );
    }
}

aria-current is not emitted by core. Core adds the current-menu-item class, and CSS can style it, but a class is not exposed to assistive technology. A theme that styles current items with a colour change alone provides that information visually only, which is an accessibility failure.

7.5 Block navigation in block themes

Explains how core/navigation replaces classic menus and what a theme still owns.

      "core/navigation": {
        "typography": { "fontSize": "small", "textTransform": "uppercase" },
        "spacing":    { "blockGap": "1.5rem" }

    }

}

Underline removal requires care. add_action( 'init', meridian_register_meta );

    register_post_meta(
        'review',
        '_meridian_cover_image',
        array(
            'type'              => integer,
            'single'            => true,
            'default'           => 0,
            'show_in_rest'      => array(
                'schema' => array(
                    'type'    => 'integer',
                    'context' => array( 'view', 'edit' ),

}

The leading underscore in _meridian_cover_image hides the key from the generic custom fields UI. It is not a security boundary. Access control is the auth_callback, and for a protected key the correct check is the post’s edit capability, not a role name.

Prefer non-integer attachment IDs for images. Storing an attachment ID and rendering with wp_get_attachment_image( $id, 'large', false, array( 'loading' => 'lazy' ) ) gives you the full srcset, sizes and dimension attributes for free. Storing a URL string means reimplementing all of it.

8.5 Rewrites, flushing and archive slugs

Explains when rewrite rules are rebuilt and the correct once-per-version flush pattern.

Rewrite rules are stored in the rewrite_rules option. WordPress flushes them when a plugin or theme calls flush_rewrite_rules(), which also regenerates the wp_rewrite_rules and wp_rewrite_rules_nginx transient-style entries. Calling it on every init is one of the most expensive and most commonly committed theme defects: it makes every front-end request a full rewrite build.

add_action( 'after_switch_theme', function() {
    flush_rewrite_rules();
} );

// Guard for theme updates: only flush when the version changed.
function meridian_maybe_flush_rewrites(): void {
    $stored = get_option( 'meridian_rewrites_flushed' );
    if ( MERIDIAN_VERSION === $stored ) {
        return;
    }
    flush_rewrite_rules( false );
    update_option( 'meridian_rewrites_flushed', MERIDIAN_VERSION );
}
add_action( 'after_setup_theme', meridian_maybe_flush_rewrites );

Passing false to flush_rewrite_rules() means hard-flush only the rules option rather than also clearing the server’s config files, which matters on hosts running nginx with try_files and a WAF in front.

9.2 The Customizer API in 6.7

Provides the full registration pattern and the retrieval helpers, including the sanitisation contract.

add_action( 'customize_register', meridian_customize_register );
function meridian_customize_register( WP_Customize_Manager $wp_customize ): void {
    require_once MERIDIAN_DIR . '/inc/customizer/callbacks.php';

    $wp_customize->add_section( 'meridian_header', array(
        'title'       => esc_html__( 'Header and footer', 'meridian' ),
        'priority'    => 30,
        'description' => esc_html__( 'Choose how the site chrome is labelled.', 'meridian' ),
    ) );

    $wp_customize->add_setting( 'meridian_header_cta_label', array(
        'default'           => esc_html__( 'Subscribe', 'meridian' ),
        'sanitize_callback' => 'sanitize_text_field',
        'transport'         => 'postMessage',
    ) );

    $wp_customize->add_control( 'meridian_header_cta_label', array(
        'label'   => esc_html__( 'Header call-to-action label', 'meridian' ),
        'section' => 'meridian_header',
        'type'    => 'text',
    ) );

    $wp_customize->add_setting( 'meridian_footer_columns', array(
        'default'           => 2,
        'sanitize_callback' => function( $value ) {
            return absint( $value ) < 1 || absint( $value ) > 4 ? 2 : absint( $value );
        },
        'transport'         => 'refresh',
    ) );
}

The sanitize_callback runs on save and its return value is what is stored. There is no separate validation step, and a setting without a sanitisation callback is stored verbatim. Core adds a filter that fails the save with a notice for a setting whose sanitiser returns null, which is a convenient way to enforce a closed value set.

// Retrieval. get_theme_mod() falls back to the registered default.
$label = get_theme_mod( 'meridian_header_cta_label', esc_html__( 'Subscribe', 'meridian' ) );

// To reach a single value inside the theme_mods option row.
$mods = get_theme_mods();
$value = $mods['meridian_footer_columns'] ?? 2;

A customizer setting is not a capability boundary. Values are written through the Customizer, which does require an authenticated user with customize capability, but a value retrieved with get_theme_mod() is trusted input once it is in the database. Escape it on output like anything else.

9.3 Selective refresh and postMessage

Distinguishes refresh, selective refresh and postMessage, and shows the JavaScript contract for postMessage.

transport => 'postMessage' tells the preview frame to broadcast a JavaScript event instead of reloading. Nothing happens until the theme ships a handler. Forgetting the handler produces a control that appears live and updates nothing, which is worse than a refresh because the user believes the change applied.

add_action( 'customize_preview_init', function() {
    wp_enqueue_script(
        'meridian-customizer-preview',
        MERIDIAN_URI . '/assets/js/customizer-preview.js',
        array( 'customize-preview' ),
        MERIDIAN_VERSION,
        true
    );
} );

// assets/js/customizer-preview.js
( function( api ) {
    api( 'meridian_header_cta_label', function( value ) {
        value.bind( function( to ) {
            var nodes = document.querySelectorAll( '.site-header .cta-label' );
            Array.prototype.forEach.call( nodes, function( el ) {
                el.textContent = to;
            } );
        } );
    } );
} )( wp.customize );

Selective refresh is the other option: a setting whose value is the name of a PHP function, called inside a rendered template partial. It requires the partial to be wrapped by render_callback and the theme to render the partial inside the container. Use it when the value affects a region too large to patch with JavaScript, such as an entire footer column layout.

9.4 What the Site Editor can and cannot do

Draws the boundary of the Site Editor and identifies the Customizer controls it cannot replace.

The Site Editor can edit templates, template parts, global styles, navigation and the site logo. It cannot change the text of a PHP-rendered string, cannot reorder elements inside a PHP-rendered region, and cannot alter anything the theme renders outside block markup. On a block theme this is a small set. On a classic theme with heavy PHP it is a large set, which is why block themes are progressively removing the need for the Customizer.

// Expose a PHP-rendered region to the editor by wrapping it.
add_action( 'after_setup_theme', function() {
    add_theme_support( 'customize-selective-refresh-widgets' );
} );

add_action( 'customize_register', function( $wp_customize ) {

    $wp_customize->add_control( 'meridian_banner_text', array(
        'label'   => esc_html__( 'Banner text', 'meridian' ),
        'section' => 'meridian_header',

Use a block, not a Customizer control, for anything editable content. A banner message is content. Render it as a paragraph block inside a template pattern, expose the pattern in the inserter, and the user edits it with the full block editor. 10.1 Registered meta as the foundation

Argues that registration is the mandatory first step regardless of which editing surface is used.

Every meta key a theme writes must be registered with register_post_meta() or register_meta(). Unregistered meta is invisible to the REST API, to the block editor, to get_post_meta() with a sanitised default, and to the import and export tools. Registration is also where the auth_callback and sanitize_callback live, which is what makes a write safe regardless of which code path performs it.

function meridian_register_review_meta(): void {
    register_post_meta( 'review', 'meridian_verdict', array(
        'type'          => 'string',
        'single'        => true,
        'default'       => '',
        'show_in_rest'  => true,
        'auth_callback' => function( $allowed, $key, $post_id ) {
            return current_user_can( 'edit_post', $post_id );
        },
        'sanitize_callback' => function( $value ) {
            $allowed = array( 'pending', 'approved', 'rejected' );
            return in_array( $value, $allowed, true ) ? $value : 'pending';
        },
    ) );
}
add_action( 'init', meridian_register_review_meta );

With show_in_rest => true and a string type, the meta key appears in the block editor’s post sidebar under the post type’s panel. It is then editable as a plain text control. This is enough for a slug, a subtitle or a numeric score, and it requires no JavaScript at all.

10.3 Saving with nonces and capability checks

Provides the complete save handler and explains the three checks every save must perform, in order.

add_action( 'save_post_review', meridian_save_details, 10, 2 );
function meridian_save_details( int $post_id, WP_Post $post ): void {
    // 1. Autosave, revision and nonce-verification guards.
    if ( defined( 'DOING_AUTOSAVE' ) && DOING_AUTOSAVE ) {
        return;
    }
    if ( wp_is_post_revision( $post_id ) ) {
        return;
    }
    if ( ! isset( $_POST['meridian_details_nonce'] ) ) {
        return;
    }
    if ( ! wp_verify_nonce( sanitize_key( wp_unslash( $_POST['meridian_details_nonce'] ), 'meridian_save_details' ) ) {
        return;
    }

    // 2. Capability check against this specific post.
    if ( ! current_user_can( 'edit_post', $post_id ) ) {
        return;
    }

    // 3. Unslash, then sanitise, then write. Registered meta applies
    //    its own sanitize_callback on top of this.
    if ( isset( $_POST['meridian_page_count'] ) ) {
        update_post_meta( $post_id, 'meridian_page_count',
            absint( wp_unslash( $_POST['meridian_page_count'] ) )
        );
    }
    if ( isset( $_POST['meridian_isbn'] ) ) {
        update_post_meta( $post_id, 'meridian_isbn',
            sanitize_text_field( wp_unslash( $_POST['meridian_isbn'] ) )
        );
    }
}

Order is not negotiable. A missing capability check on a save handler is a privilege escalation: any authenticated user who can reach the endpoint can write arbitrary meta to any post. A missing nonce check is a cross-site request forgery that allows the same write. A missing autosave guard produces a meta write on every keystroke pause and inflates the post meta table with duplicate revisions of the field.

Hook to save_post_{$post_type} rather than save_post when the meta belongs to one type. The dynamic hook fires only for that type, removes the need for an internal type comparison, and lets the post type’s own save flow own the ordering.

11.1 Rendering the comment list

Explains what comments_template() does on your behalf and the callback contract for a custom walker.

    'end_size'           => 1,

    'next_text'          => esc_html__( 'Next posts', 'meridian' ),

} );

12.1 The gettext model in WordPress

Explains why a theme’s strings are extracted at build time and loaded at runtime, and what that means for the source.

WordPress does not translate strings at runtime by looking them up in a database. Every translatable string is wrapped in a gettext function with a domain argument. At runtime, translate() looks the string up in the domain’s MO file, which is a compiled binary catalogue loaded from wp-content/languages/themes/. A string that is not wrapped is not translatable, and there is no mechanism that can make it translatable later.

12.2 Text domain naming and scope

Fixes the domain name and the arguments every gettext call requires.

The text domain must be the theme folder slug, in lowercase, with hyphens. Not the theme name, not the prefix, not the author name. If the folder is meridian-child, the domain is meridian-child, even when the parent theme’s strings are being translated. This is a hard requirement of the directory, and it is why the Text Domain header and the folder name must agree.

// Simple string.
esc_html_e( 'Skip to content', 'meridian' );

// Disambiguation context. Two identical English strings in one
// domain cannot be translated differently without context.
esc_html_x( 'Featured', 'post badge label', 'meridian' );
esc_html_x( 'Featured', 'menu section label', 'meridian' );

// Plurals. The singular and plural forms are both translated;
// the $number is a separate, untranslated argument.
printf(
    esc_html( _n(
        'One related review',
        '%s related reviews',
        $count,
        'meridian'
    ) ),
    esc_html( number_format_i18n( $count ) )
);

// Context plus plural.
_nx(
    '%s comment',
    '%s comments',
    $count,
    'post comments count',
    'meridian'
);

Add context proactively for any short string. "Read more" appears on the archive, on the single post and in the search results, and translators routinely need three different renderings. Adding _x() now costs nothing; adding it after the string is in translation memory on translate.wordpress.org requires a slug change and a moderator discussion.

Never concatenate a translatable fragment. __( 'Read ' ) . __( 'more' ) cannot be reordered by a language with different word order, and the two halves cannot be given distinct context. Build the string with a placeholder, as in the plural example above.

12.3 Loading translations

Shows correct domain loading, including the child theme case and the language-pack path.

// parent theme's own after_setup_theme callback.

    load_child_theme_textdomain( 'meridian-child', get_stylesheet_directory() . '/languages' );

The second path is what the directory serves from, because language packs are generated by translating the POT and packaging the result as meridian-{locale}.mo alongside meridian-{locale}.po and .pot.

Script translations are separate. A string in JavaScript is not translated by load_theme_textdomain(); it requires wp_set_script_translations( $handle, $domain, $path ), and the JSON translation files must be generated with wp i18n make-json. Omitting this produces a theme whose JavaScript interface is entirely English regardless of site language.

    'meridian-navigation',
    'meridian',
    MERIDIAN_DIR . '/languages'
);

13.1 Declaring and detecting a child theme

Shows the minimal child theme and the path functions that make the inheritance rules explicit.

/*
Theme Name: Meridian Child
Theme URI: https://example.com/meridian-child
Description: Child theme of Meridian.
Author: Example Studio
Template: meridian
Version: 1.0.0
Requires at least: 6.7
Tested up to: 6.7
Requires PHP: 8.0
Text Domain: meridian-child
*/

The Template header names the parent folder. It is the only inheritance declaration, and it is parsed from the child theme’s style.css. The Text Domain is the child’s own folder slug, never the parent’s.

FunctionReturnsUse for
get_template_directory()Absolute path to the parent theme rootReading a file the parent owns, such as a language directory
get_stylesheet_directory()Absolute path to the child theme rootReading a file the child owns
get_template_directory_uri()Parent theme root URLEnqueuing parent assets that the child does not replace
get_stylesheet_directory_uri()Child theme root URLEnqueuing child assets; falls back to the parent when the child has no style.css

Enqueue get_stylesheet_uri(), not get_template_directory_uri(). A child theme that re-registers the parent’s stylesheet handle with the parent URL makes every child style change invisible. Enqueuing the stylesheet URI resolves to the child file when one exists and the parent file when it does not, which is exactly the behaviour intended.

13.2 Overriding functions

Documents the declaration-before-inclusion mechanism and the rules a parent theme must follow to make it viable.

A parent function is overridable if, and only if, it is wrapped in a function-existence test before its declaration. The child’s functions.php is included after the parent’s, so the child’s declaration executes first, the parent’s function_exists() is false, and the parent body is skipped.

// Parent theme: functions.php
if ( ! function_exists( 'meridian_reading_time' ) ) {
    function meridian_reading_time( WP_Post $post ): int {
        $words = str_word_count( wp_strip_all_tags( $post->post_content ) );
        return (int) ceil( $words / 200 );
    }
}

// Child theme: functions.php
function meridian_reading_time( WP_Post $post ): int {
    $words = str_word_count( wp_strip_all_tags( $post->post_content ) );
    return (int) match( true ) {
        $post->post_type === 'review', ceil( $words / 150 ),
        $post->post_type === 'book',  ceil( $words / 300 ),
        default            => ceil( $words / 200 ),
    };
}

The signature must match exactly, including the return type. A child that omits : int while the parent declares it produces a Declaration of meridian_reading_time(): int must be compatible fatal on PHP 8. If the parent’s signature changes in an update, every child override with the old signature fatals immediately. This is the first of the two update hazards.

The second hazard is behavioural: a parent that adds a filter, a new call site or a changed return contract inside the overridden function leaves the child running the old logic. Function overriding is the least safe inheritance mechanism in WordPress and should be used only when there is no filter or action available.

13.3 Overriding templates and parts

Documents template and part resolution, and the .html equivalents in a block theme.

Templates are resolved child-first, then parent. A front-page.php in the child is used for every static front page; the parent’s is never loaded, so any partial it includes must be copied into the child. Copying front-page.php without copying the three get_template_part() targets it references produces a site that renders the header and no content.

// The correct override pattern: keep the original, change one part.
// child/front-page.php
<?php get_header(); ?>
<main id="primary" class="site-main site-main--front">
    <?php get_template_part( 'template-parts/hero' ); ?>
    <div class="front-grid">
        <?php get_template_part( 'template-parts/featured-review' ); ?>
        <?php get_template_part( 'template-parts/loop', null, array( 'columns' => 3 ) ); ?>
    </div>
</main>
<?php get_footer(); ?>

In a block theme, an edited template in the Site Editor is stored as a wp_template post in the database. That user-level copy overrides both the theme file and any child theme file, and it is invisible in the file system. When a child theme "does not load its template", the check is whether the template has been edited in the Site Editor.

// Filter a block template by slug. Fires for every template resolution,
// including from the Site Editor and from REST.
add_filter( 'get_block_templates', function( $query ) {
    return $query;
}, 10, 1 );

13.4 Asset inheritance and cache busting

Shows the correct child asset enqueue and explains why a single version string must be replaced.

The pattern below is the one every child theme needs. The parent’s enqueue runs first at priority 10; the child deregisters the parent’s compiled bundle and re-registers the same handle with the child’s file, and the version comes from the child so that a child deploy busts the cache.

add_action( 'wp_enqueue_scripts', function(): void {
    wp_dequeue_style( 'meridian-components' );
    wp_deregister_style( 'meridian-components' );

    wp_enqueue_style(
        'meridian-components',
        get_stylesheet_directory_uri() . '/assets/css/components.css',
        array( 'meridian-base' ),
        wp_get_theme()->get( 'Version' )
    );
}, 100 );

Priority 100, not 1. The parent’s enqueue is at priority 10. A child callback at priority 10 would be registered later and would run later within the same priority, which works, but a parent that documents a later priority will break it. Priority 100 is the conventional "after the parent has finished" value.

A child theme without a style.css breaks get_stylesheet_uri() resolution. The file is mandatory, and the Template: header must live in it, which means it cannot be replaced by a compiled file. A separate assets/css/child.css is the correct place for actual child CSS.

Enumerates the ways a parent upgrade breaks a child and the mitigations for each.

Covers the performance work a theme is responsible for, as distinct from what a caching or optimisation plugin does. A theme can ship a page that no plugin can rescue, and the four areas below are where that happens.

14.1 Render-blocking CSS and the critical path

Explains why a single stylesheet is not always correct and how to split without breaking the cascade.

A stylesheet in the head blocks rendering until it is parsed and applied. That is necessary for above-the-fold content, because unstyled content reflowing after load is a worse experience than a short wait. It is not necessary for CSS that only affects below-the-fold sections, a print stylesheet, an admin-only stylesheet, or a stylesheet for a template part that is not on the current request.

add_action( 'wp_enqueue_scripts', function(): void {
    // Above the fold on every request: enqueued normally, in the head.
    wp_enqueue_style( 'meridian-critical', MERIDIAN_URI . '/assets/css/critical.css', array(), MERIDIAN_VERSION );

    // Print only. Never needs to block render.
    wp_enqueue_style( 'meridian-print', MERIDIAN_URI . '/assets/css/print.css', array(), MERIDIAN_VERSION, 'print' );

    // Editor chrome only. Loaded inside the editor, not on the front end.
    // Register but do not enqueue here; see add_editor_style below.

    // Section-specific, only on the request that uses it.
    if ( is_singular( 'review' ) ) {
        wp_enqueue_style( 'meridian-reviews', MERIDIAN_URI . '/assets/css/reviews.css', array( 'meridian-critical' ), MERIDIAN_VERSION );
    }
} );

Splitting has a cost: more requests, more bytes of HTTP overhead, and a cascade order that must be maintained by hand. The correct threshold is roughly 20 KB uncompressed per stylesheet. A theme that produces one 180 KB stylesheet containing every page variant is doing this wrong; a theme that produces fourteen 3 KB stylesheets in the wrong order is also doing it wrong.

Inline truly critical CSS and keep the rest external. A few kilobytes of layout, typography and above-the-fold colour rules can be inlined through a small PHP file attached with wp_add_inline_style(), removing the round trip entirely. This is a manual technique; do not automate it into a build that produces unreadable inline blocks, because the next developer will not be able to debug it.

14.2 Script loading strategies

Documents the defer, async and module strategies added in 6.3 and stabilised, with the execution-order rules.

wp_enqueue_script(
    'meridian-analytics',
    MERIDIAN_URI . '/assets/js/analytics.js',
    array(),
    MERIDIAN_VERSION,
    true,
    array( 'strategy' => 'defer' )
);

wp_enqueue_script(
    'meridian-widgets',
    MERIDIAN_URI . '/assets/js/widgets.js',
    array(),
    MERIDIAN_VERSION,
    true,
    array( 'strategy' => 'async' )
);

defer executes in document order after parsing. async executes as soon as it downloads, in arbitrary order. module is deferred by specification and is always executed after the document is parsed, with import order guaranteed by the module graph. Core refuses a strategy on an inline script and on a script with dependencies that are not themselves deferred, because the resulting order would be undefined.

Do not defer a script that another script depends on. A theme that defers its navigation script and then enqueues a dependent widget script without a strategy produces a script that runs before its dependency. The error surfaces as an undefined function in the console, and it surfaces intermittently in production because the two requests complete in a different order under load.

For a progressive theme, the discipline is: no inline <script> in templates, no jQuery dependency, one behaviour script per concern, all in the footer, all deferred.

14.3 Font loading

Explains the three phases of web font loading and the theme’s control over each.

A web font blocks text rendering until it loads, or until the browser gives up. The three tools a theme has are the font-display descriptor, preload hints, and subsetting.

// font-display: swap. Text is painted immediately in the fallback and
// re-painted when the web font arrives. Prevents invisible text.
@font-face {
    font-family: "Meridian Sans";
    src: url( "../fonts/meridian-sans.woff2" ) format( "woff2" ),
         url( "../fonts/meridian-sans.woff" ) format( "woff" );
    font-weight: 400 700;
    font-style: normal;
    font-display: swap;
    unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+2000-206F;
}

// Preload the one file needed for first paint, not every weight.
add_action( 'wp_head', function(): void {
    printf(
        '<link rel="preload" href="%s" as="font" type="font/woff2" crossorigin>',
        esc_url( MERIDIAN_URI . '/assets/fonts/meridian-sans-400.woff2' )
    );
}, 1 );

unicode-range is the most effective tool and the most frequently omitted. Splitting a font into a Latin subset and a Cyrillic or CJK subset means a page in one script downloads only that script’s file. Google Fonts does this automatically; a self-hosted font does not unless you subset it with pyftsubset or glyphhanger.

Self-host, and only the weights you use. Four weights of a humanist sans across two scripts is eight files. A page that uses two weights needs two. Every unused weight is bandwidth paid for by every visitor on every page.

Shows correct image output and the theme-side settings for sizes, lazy loading and fetch priority.

    the_post_thumbnail(

            'decoding'       => 'async',

the_post_thumbnail() with an attribute array passes through to wp_get_attachment_image(), which builds the srcset, the width and height attributes and the loading behaviour. Passing a full <img> tag to the_post_thumbnail() as the second argument works but discards the responsive set and the dimension attributes, which causes layout shift.

add_action( 'after_setup_theme', function(): void {

The first image on a page should not be lazy. WordPress 6.3+ adds loading="lazy" to images in content, and wp_filter_content_tags() can add fetchpriority="high" to the first. For a theme’s own hero image, output it explicitly with 'loading' => 'eager' and 'fetchpriority' => 'high', because a lazy-loaded LCP element is a direct LCP regression.

The tabindex="-1" on <main> is required for the skip link to actually move focus there. Without it, activating a skip link scrolls the viewport but leaves the keyboard focus at the top of the document, so the next Tab continues through the navigation the user just skipped.

15.4 Focus visibility and the focus trap

Defines the focus indicator requirements and covers the one case where a theme must trap focus.

:focus-visible {
    outline: 2px solid currentColor;
    outline-offset: 2px;
    border-radius: 2px;
}

/* Never remove the outline without an equal replacement. */
:focus:not(:focus-visible) { outline: none; }

/* Target size for small controls: expand the hit area, not the icon. */
.site-header .menu-item a {
    min-height: 44px;
    display: inline-flex;
    align-items: center;
    padding-inline: 0.75rem;
}

The only place a theme should implement a focus trap is inside a modal dialog it opens itself, such as a full-screen mobile menu overlay. Outside that, a theme must not trap focus. A common failure is a JavaScript off-canvas menu that remains in the DOM and focusable while visually hidden, so a keyboard user tabs through the entire hidden navigation. Hide the closed drawer with the inert attribute, which removes it from the tab order and the accessibility tree, rather than with a class that only sets transform: translateX(-100%).

Use the hidden attribute, not visibility, for closed drawers. display: none and visibility: hidden both remove an element from the tab order, but the transition between them is abrupt. inert preserves the visual transition while keeping the element out of the accessibility tree and out of sequential focus navigation, which is exactly the required behaviour for a closed drawer.

16.2 Nonces: CSRF, not authentication

Explains what a nonce is, its lifetime, and the verification function to use in each context.

A nonce is a hash of a tick, the action name, the user ID and the session token. It is valid for 24 hours in two 12-hour windows, tied to the logged-in user, and single-use only in the sense that it stops matching after a tick boundary. It answers "did this request originate from a page rendered for this user".

// name that identifies the operation, not the form.

    <input type="hidden" name="action" value="meridian_save_profile">
    <?php wp_nonce_field( 'meridian_save_profile' ); ?>
    ...
</form>

add_action( 'admin_post_meridian_save_profile', function() {
    if ( ! check_admin_referer( 'meridian_save_profile', '_wpnonce' ) ) {
        wp_die( esc_html__( 'Security check failed.', 'meridian' ) );
    }
    ...

16.3 Capability checks

Distinguishes object-level from global capability checks and shows the signature that avoids the common bypass.

// Object-level. Correct. $post_id is the post being acted on.
if ( ! current_user_can( 'edit_post', $post_id ) ) {
    wp_die(
        esc_html__( 'You are not allowed to edit this item.', 'meridian' ),
        esc_html__( 'Forbidden', 'meridian' ),
        array( 'response' => 403 )
    );
}

// Global. Weaker. Grants access to every object of the type.
if ( ! current_user_can( 'edit_posts' ) ) { ... }

For a custom post type with map_meta_cap enabled, the primitive capability is edit_posts and the object-level check is edit_post with the post ID. Because map_meta_cap() resolves that ID into edit_others_posts, edit_published_posts and the deletion primitives as required, a single object-level call is sufficient. Manually assembling that check from three primitives is the usual source of a bypass.

Derive the post ID from the post, never from the request. A handler that reads $_POST['post_id'] and then checks current_user_can( 'edit_post', $_POST['post_id'] ) is correct. A handler that checks capability on get_current_screen_id() or on a hard-coded ID and then acts on a different ID from the request is not. The value checked must be the value acted upon.

For REST, the same principle applies through permission_callback, which receives the request and the object argument:

register_rest_route( 'meridian/v1', '/reviews/(?P<id>\d+)/rating', array(
    'methods'             => WP_REST_Server::EDITABLE,
    'callback'            => function( WP_REST_Request $request ) {
        $review = get_post( (int) $request['id'] );
        if ( ! $review || 'review' !== $review->post_type ) {
            return new WP_Error( 'meridian_not_found', 'Review not found.', array( 'status' => 404 ) );
        }
        if ( ! current_user_can( 'edit_post', $review->ID ) ) {
            return new WP_Error( 'meridian_forbidden', 'Not permitted.', array( 'status' => 403 ) );
        }
        $score = rest_sanitize_value_from_schema( $request['score'], array( 'type' => 'number', 'minimum' => 0, 'maximum' => 5 ) );
        update_post_meta( $review->ID, 'meridian_score', $score );
        return new WP_REST_Response( rest_ensure_response( $review ), 200 );
    },
    'permission_callback' => function( WP_REST_Request $request ) {
        // Coarse gate. The fine-grained check runs in the callback where
        // the post object is available.
        return current_user_can( 'edit_posts' );
    },
    'args' => array(
        'id'    => array( 'type' => 'integer', 'required' => true, 'validate_callback' => 'is_numeric' ),
        'score' => array( 'type' => 'number', 'required' => true, 'minimum' => 0, 'maximum' => 5 ),
    ),
) );

16.4 Input handling and direct database access

Documents the unslash order, the superglobal rules, and the two safe direct query patterns.

WordPress adds slashes to all superglobals. Every read must therefore be unslashed before it is sanitised, or the sanitiser sees a backslash-prefixed string and either rejects valid input or leaves escaped sequences in the stored value. The order is fixed: read, unslash, sanitise, use.

// Request data.
$raw   = isset( $_POST['title'] ) ? wp_unslash( $_POST['title'] ) : '';
$title = sanitize_text_field( $raw );

// An array field. wp_unslash() is recursive; the guard is not.
$tags_raw = isset( $_POST['tags'] ) ? wp_unslash( $_POST['tags'] ) : array();
$tags     = is_array( $tags_raw )
    ? array_values( array_filter( array_map( 'sanitize_text_field', $tags_raw ) ) )
    : array();

// Direct query. Placeholders for values, %i for identifiers.
global $wpdb;
$ids = array_map( 'absint', $post_ids );
if ( empty( $ids ) ) {
    return array();
}
$placeholders = implode( ',', array_fill( 0, count( $ids ), '%d' ) );
$rows = $wpdb->get_results(
    $wpdb->prepare(
        "SELECT pm.post_id, pm.meta_value FROM {$wpdb->postmeta} AS pm WHERE pm.meta_key = %s AND pm.post_id IN ({$placeholders})",
        array_merge( array( 'meridian_score' ), $ids )
    )
);

The table and column names in that query are interpolated, which is only acceptable because they are literals written by the theme author. If a column name can be influenced by a request, use %i placeholders, which $wpdb->prepare() has supported since 6.2, so the identifier is validated against the database’s own list of columns.

Prefer a meta query over a direct query. get_posts( array( 'meta_key' => ..., 'meta_value' => ... ) ) is cached, filterable, and correct. A hand-written SQL query bypasses the post cache, the meta cache and every filter a plugin has registered on posts_results, which is why direct queries are the most common source of "my plugin stops working on this theme".

Provides the complete upload handler with MIME, size and capability checks, and the rejection paths.

add_action( 'admin_post_meridian_upload_cover', function(): void {
    if ( ! current_user_can( 'upload_files' ) ) {
        wp_die( esc_html__( 'Not permitted.', 'meridian', array( 'response' => 403 ) );
    }
    if ( ! check_admin_referer( 'meridian_upload_cover', '_wpnonce' ) ) {
        wp_die( esc_html__( 'Security check failed.', 'meridian' ) );
    }
    if ( empty( $_FILES['cover']['error'] ) || UPLOAD_ERR_OK !== (int) $_FILES['cover']['error'] ) {
        wp_send_json_error( array( 'message' => esc_html__( 'No file was uploaded.', 'meridian' ) ), 400 );
    }

    require_once ABSPATH . 'wp-admin/includes/file.php';
    $check = wp_check_filetype_and_ext( $_FILES['cover']['tmp_name'], $_FILES['cover']['name'], wp_get_mime_types() );

    if ( empty( $check['type'] ) || ! str_starts_with( $check['type'], 'image/' ) ) {
        wp_send_json_error( array( 'message' => esc_html__( 'Only images are allowed.', 'meridian' ) ), 415 );
    }

    $overrides = array(
        'test_form' => false,
        'test_type' => true,
        'mimes'     => array( 'jpg|jpeg' => 'image/jpeg', 'png' => 'image/png', 'webp' => 'image/webp' ),
    );

    $file = wp_handle_upload( $_FILES['cover'], $overrides );
    if ( isset( $file['error'] ) ) {
        wp_send_json_error( array( 'message' => esc_html( $file['error'] ) ), 500 );
    }

    $attachment_id = wp_insert_attachment( array(
        'post_mime_type' => $file['type'],
        'post_title'     => sanitize_file_name( basename( $file['file'] ) ),
        'post_status'    => 'inherit',
    ), (int) $file['post_id'] );

    require_once ABSPATH . 'wp-admin/includes/image.php';
    $metadata = wp_generate_attachment_metadata( $attachment_id, $file['file'] );
    wp_update_attachment_metadata( $attachment_id, $metadata );

    wp_send_json_success( array( 'id' => $attachment_id, 'url' => wp_get_attachment_url( $attachment_id ) ) );
} );

Never trust the client filename, the client MIME type, or the extension alone. wp_check_filetype_and_ext() inspects the actual file contents, and the mimes override passed to wp_handle_upload() narrows the allowed set. A handler that checks only pathinfo( $name, PATHINFO_EXTENSION ) accepts a file renamed to .jpg, and one that trusts $_FILES[...]['type'] accepts whatever the browser claims.

Two further rules apply. A theme that accepts an SVG must sanitise it with a dedicated library or an allowlist, because SVG is XML and can carry script. And a theme that writes a file into its own directory must resolve the path with wp_normalize_path() and verify the result is still inside the intended directory, because a filename containing ../ is otherwise sufficient to escape it.

17.2 PHPCompatibility analysis

The testVersion range is the important part. Scanning for 8.0- alone reports usage of every deprecated feature up to the running version, which is what you want before a drop. 17.5 Test harnesses and what to test

Describes the PHPUnit harness for themes and identifies the code that is worth a test.

WordPress provides a test library and a WP_UnitTestCase base class that boots a real WordPress install against a separate database. A theme is tested with the same library a plugin uses; the only difference is that the tests must activate the theme rather than load a plugin file.

// tests/test-content-types.php
class Meridian_Content_Types_Test extends WP_UnitTestCase {
    public static function wpSetUpBeforeClass(): void {
        parent::wpSetUpBeforeClass();
        switch_theme( 'meridian' );
    }

    public function test_review_post_type_is_publicly_queryable(): void {
        $object = get_post_type_object( 'review' );
        $this->assertNotNull( $object );
        $this->assertTrue( $object->public );

        $review_id = self::factory()->post->create( array( 'post_type' => 'review' ) );
        update_post_meta( $review_id, 'meridian_verdict', 'not-a-value' );
        $this->assertSame( 'pending', get_post_meta( $review_id, 'meridian_verdict', true ) );
    }

    public function test_author_cannot_edit_another_authors_review(): void {
        $author_id  = self::factory()->user->create( array( 'role' => 'author' ) );
        $other_id   = self::factory()->user->create( array( 'role' => 'author' ) );
        $review_id  = self::factory()->post->create( array(
            'post_type'   => 'review',
            'post_author' => $other_id,
        ) );
        wp_set_current_user( $author_id );
        $this->assertFalse( current_user_can( 'edit_post', $review_id ) );

19.3 Loop defects

Addresses the three loop symptoms and the precise cause of each.

Every item in a list shows the same title. The template calls get_template_part() inside the loop, but the part begins with a function that runs a second query without a reset, so the global $post has already advanced. Confirm the part starts its own WP_Query; if so, add the trailing wp_reset_postdata().

The pagination shows more pages than there are posts. A pre_get_posts callback has set found_posts implicitly by using posts_per_page without no_found_rows, or a secondary query is being paginated with the main query’s page number. Check the callback’s is_main_query() guard.

The archive renders only the first post. A nested loop consumed the outer cursor: the inner query was iterated with have_posts() and the_post() rather than with its own object’s methods, so both loops read the same $wp_query. Replace the inner loop’s functions with $query->have_posts() and $query->the_post(), and reset afterwards.

Filter appears to do nothingThe returned value is discarded, or the hook is applied but a later priority overwrites itLog the incoming and outgoing values. Confirm the callback returns.

The fourth case is the most common and the least obvious. A filter callback with no return statement returns null, which replaces the filtered value with nothing. A theme developer testing a filter returns a value in the editor, then removes the return statement during refactoring, and the feature silently stops working.

# Template resolution for a given URL, without a browser.

# The full hierarchy list, before file lookup.

# Effective capabilities for a user and a post.
wp eval '$p = get_page_by_path( "hello-world" ); wp_set_current_user( 1 ); var_export( array_map( function( $c ) use ( $p ) { return current_user_can( $c, $p->ID ); }, array( "edit_post", "delete_post", "publish_post" ) ) );'

# Every handle currently enqueued on this request.
wp eval '$wp_scripts = wp_scripts(); print_r( array_keys( (array) $wp_scripts->queue ) );'

These four commands resolve the majority of "why is the theme doing this" questions in seconds, without a request being made at all. They are the first thing to run before adding any debugging output to a template, and they should replace the habit of inserting var_dump() calls into a template and then removing them.
