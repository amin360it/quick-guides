    Introduction

    1 · How CSS Works

    1.1 Anatomy of a rule1.2 The cascade and origin1.3 Specificity, inheritance and importance1.4 Cascade layers and @layer

    Chapter one explains the mechanics behind every stylesheet: rule anatomy, the cascade, specificity, inheritance, importance and cascade layers. You write a selector plus a declaration block of property and value pairs, and the browser picks the winner using origin, specificity, order and important flags. Understanding these rules makes browser behaviour predictable instead of mysterious, and it becomes the foundation for everything later in the guide.

    CSS is declarative: you describe what elements look like, and the browser figures out how. The engine resolves every element’s final styles through a well-defined process, so before writing rules you should understand the rules of the rules — the cascade, specificity and inheritance.

    1.1 Anatomy of a rule

    A CSS rule is a selector, a declaration block, and a set of declarations. That is the whole grammar, and everything difficult about CSS is a consequence of what happens when several rules match the same element. The syntax is trivial; the resolution is not.

    Anatomy, including what the parser silently discards

    /* comment */
.card > p {            /* selector */
  color: var(--text);    /* declaration: property : value ; */
  margin-block: 0.5rem;
}

@media (min-width: 60rem){      /* at-rule */
  .card p { font-size: 1.125rem; }
}

:root { --brand: #00d1ff; }     /* a custom property, read like a value */

    A declaration is a property, a colon, and a value. Two things catch everyone: the last declaration in a block wins over earlier ones for the same property, and a declaration whose value the parser cannot understand is **discarded silently** — not passed down, not inherited, just gone, with no error anywhere.

    .a{
  colour: red;        /* discarded: misspelled property */
  color: red;         /* this one applies */
  margin: 12px 8px    /* discarded: missing final semicolon is tolerated,
                         but a missing VALUE here would drop it */
}
.b{
  width: calc(100% -; /* invalid: the value does not parse */
  height: 10px;       /* height still applies */
}
    A typo produces no error, no warning and no visible message — the declaration is simply not there. This is why a rule "not working" is so often a misspelling rather than a cascade problem, and it is why the browser's dev tools show struck-through declarations in the styles pane: the strikethrough is the parser telling you it rejected that one.

    At-rules, and which ones wrap other rules

    At-ruleContainsPurpose
    @mediaRulesApply them conditionally on a media feature
    @supportsRulesApply them only if a declaration is supported
    @containerRulesApply them based on an ancestor's size, not the viewport
    @layerRulesName a cascade layer and order the layers themselves
    @importA stylesheetFetch another sheet. Blocks rendering; avoid it
    @keyframesKeyframe blocksDescribe an animation's steps
    @font-faceDescriptorsDeclare a font and where to fetch it
    @propertyDescriptorsRegister a custom property with a type and an initial value
    @pageDescriptorsStyle paged media — margins, size, counters
    @starting-styleRulesGive an entering element a from-state, for transitions

    Nesting a plain rule inside an at-rule is legal, and that is what makes container queries and @supports readable. Nesting a declaration inside an at-rule without its own block is not, and was a legacy parsing quirk worth knowing about only so you recognise it in old code.

    Custom properties are values, not declarations

    :root{
  --space-2: 0.5rem;
  --brand: #00d1ff;
}

.card{
  padding: var(--space-2);
  border: 1px solid var(--brand);
  /* NOT valid: a custom property cannot be part of a keyword */
  animation: slide var(--dur) ease;   /* --dur undefined -> whole rule dropped */
}

    A custom property holds a token stream, not a typed value, and it is substituted exactly where it appears. That is why it cannot be concatenated into a keyword: animation: slide var(--dur) would need --dur to be the literal text ease, not the value 200ms. When the substitution produces something invalid, the declaration using it is dropped.

    The grammar is small: selector, block, declarations, and at-rules that group other rules. Almost every surprise in CSS comes from the parser discarding a declaration it cannot parse without telling you.

    1.2 The cascade and origin

    The cascade is the algorithm that decides which declaration wins when several match the same property. It has a fixed order of steps, and almost every "why is not my rule applying" question is answered by walking them.

    The algorithm, in order

    StepQuestionNotes
    1Which declarations match this element, for this property?Origin and importance filter first
    2Which are in a later @layer?Unlayered styles beat layered ones — the reverse of what people expect
    3Which are from a later origin?Author beats user-behaviour; user beats browser
    4Which is more specific?Compared as three numbers
    5Which comes later in the source?The final tiebreak

    Importance is folded into step 1 and it inverts the order it sits next to. Within the author origin, an !important declaration beats every normal author declaration regardless of specificity. Across origins, importance flips the order entirely, so a normal user declaration beats an important author one.

    OriginNormalWith !important
    TransitionHighest—
    User agent !important—Highest
    User !important—Overrides author
    Author !important—Overrides user
    AuthorOverrides user—
    UserOverrides browser—
    Browser defaultLowest—

    The four origins, and which ones you can see

    /* 1. browser default - the UA stylesheet.
      You can read it in dev tools; overriding it is normal. */
button{ background: ButtonFace; }

/* 2. author - your stylesheets and inline styles. This is 99% of CSS. */
.btn{ background: var(--brand); }

/* 3. user - reader settings and extensions.
      "Always use my reader stylesheet" is a real origin, and it beats you. */
@media (prefers-contrast: more){ ... }

/* 4. user-agent !important - browser accessibility defaults.
      Usually accessibility-related, and should not be fought. */
@media (prefers-reduced-motion: reduce){ ... }
    An !important in a UA stylesheet exists so that browser accessibility behaviour — visible focus, forced colours in high-contrast mode — cannot be accidentally overridden by a page. If your rule needs !important to beat one of those, the fix is usually to stop resetting something you should not have reset.

    Inline styles, and the attribute that is easy to forget

    <div style="color: red">inline</div>
<div style="color: red !important">inline important</div>

    An inline style attribute is treated as a separate origin that beats any selector in a stylesheet, and adding !important inside it beats everything else. It also cannot be overridden without an equally specific inline rule or !important — which is why a stray style attribute in a template becomes the hardest bug in a file.

    In a loop that sets styles from JavaScript, use el.style.setProperty(name, value, priority) rather than building the cssText string, and pass a priority only when you have a specific reason. It keeps the specificity model intact instead of quietly escalating.

    Origin, then layer, then specificity, then source order — with importance inverting the origin comparison. Most cascade surprises are one of those five steps being skipped, and the dev tools styles pane shows you exactly which declaration won.

    1.3 Specificity, inheritance and importance

    Specificity is three numbers compared left to right, and it exists for one reason: so that a more specific selector wins without the author having to know what order the stylesheet will be concatenated in. Understanding it as a tiebreaker in a designed system — rather than as a number to inflate — is what keeps stylesheets maintainable.

    How the three numbers are counted

    ColumnCountsExample
    IDsEach #id#header → 1
    Classes, attributes, pseudo-classesEach .class, [attr], :hover.btn.is-open → 2
    Elements and pseudo-elementsEach tag name, ::before, ::afterdiv p → 0,0,2
    Negated selectorsThe :not() argument does count:not(#x) → 1 ID
    CombinatorsNever count>, +, ~ → 0
    The universal selectorNever counts* → 0
    /*                    id  class  element   written as 0-x-y-z */
p                             0  0     1        (0,0,0,1)
.card p                       0  1     1        (0,0,1,1)
#app .card p                 1  1     1        (0,1,1,1)
#app                          1  0     0        (0,1,0,0)
a:hover                       0  1     1        (0,0,1,1)
ul li                         0  0     2        (0,0,0,2)
[data-open]                   0  1     0        (0,0,1,0)
::before                      0  0     1        (0,0,0,1)
.card:not(#x)                 1  1     0        (0,1,1,0)
    The most counter-intuitive rule: a pseudo-class counts as a class, so :hover and :focus-visible are worth as much as a class. That is deliberate — a state needs to be able to beat a plain styling rule without an id — but it means a and a:hover differ by only one column.

    Inheritance is not specificity

    Inheritance is a separate mechanism and it interacts with the cascade in a way that produces a specific surprise: a property set directly on an element always beats an inherited value, no matter how specific the selector that set the inherited value was.

    body{ color: rebeccapurple; }   /* specificity (0,0,0,1) */
#app p{ color: teal; }         /* specificity (0,1,0,1) - but on the parent */

#app p{ color: teal; }         /* inherited by the p */
p{ color: black; }             /* specificity (0,0,0,1) - set directly on the p */
<!-- the p is BLACK, not teal.
     A declaration on the element always beats an inherited one. -->

    This is why setting a colour on body and then finding that a <a> inside it keeps the browser's link colour is not a bug: the UA stylesheet sets a link colour on the link, and a directly-set value beats an inherited one regardless of origin.

    /* Properties that do NOT inherit, by default */
color, background, border, margin, padding, font-size, width, height,
display, position, top/right/bottom/left, transform, overflow, z-index

/* Properties that DO inherit */
color, font, font-family, font-weight, line-height, letter-spacing,
text-align, text-transform, white-space, visibility, list-style,
cursor, border-collapse, border-spacing, orphans, widows

/* make others inherit, deliberately and reversibly */
.panel, .panel *{ box-sizing: border-box; }
input, button, textarea{ font: inherit; }   /* stop controls using their own font */

    !important, and the one thing it is for

    /* the normal case: a utility that must beat component CSS */
.is-hidden{ display: none !important; }

/* the legitimate case: overriding a third-party or inline style */
.vendor-widget button{ all: unset !important; }
    A specificity war is a structural problem wearing a CSS costume, and !important guarantees you lose it later. The correct escalation is not !important — it is @layer. Put the component in a layer and the override in a later one, and the override wins regardless of selector, with no escalation and no global registry of important declarations.

    Three columns: ids, then classes/attributes/pseudo-classes, then elements/pseudo-elements. Compare left to right. Inheritance is separate — a value set directly on an element always beats an inherited one, whatever the selector's specificity.

    1.4 Cascade layers and @layer

    Cascade layers solve the problem specificity was invented to solve, and they do it properly: they order whole groups of styles, so an override does not need a heavier selector, and the specificity of the selectors inside each layer becomes irrelevant between layers.

    The problem they remove

    /* WITHOUT layers: three ways to fight, in escalating order */

/* 1. accept the problem */
.card__title{ font-size: 1rem; }
.card--featured .card__title{ font-size: 1.5rem; }   /* heavier */

/* 2. add an id */
#featured .card__title{ font-size: 1.5rem; }        /* heavier still */

/* 3. escalate to !important */
.card--featured .card__title{ font-size: 1.5rem !important; }
.card--featured .card__title{ font-size: 1.5rem !important; } /* and now they collide */

    Every one of those steps is a compromise, and step 3 has no step 4. The specificity numbers become a load-bearing part of the system's design, and the only way to know what wins is to compute three numbers for every rule that might conflict.

    Declaring and ordering layers

    /* declare the order ONCE, up front. This is the entire mechanism. */
@layer reset, base, layout, components, utilities;

/* then use them */
@layer reset{
  *, *::before, *::after{ box-sizing: border-box; }
  body{ margin: 0; }
}

@layer base{
  body{ font: 1rem/1.5 var(--font-sans); color: var(--text); }
}

@layer components{
  .btn{ background: var(--brand); }
  .card{ border: 1px solid var(--border); }
}

@layer utilities{
  .u-hidden{ display: none; }
}

    The first rule — the bare list of layer names with no braces — establishes the order. Later layers beat earlier ones. A name not in that list is appended to the end, and a @layer block that appears before the declaration is still ordered by the declaration.

    Declare the layer order in one file that is loaded first, and never declare layer order anywhere else. Two competing order declarations is the same class of bug as two competing specificity escalations, one level up.

    The rule that surprises people

    @layer reset, base, utilities;

@layer base{ .btn{ color: black; } }
@layer utilities{ .btn{ color: white; } }   /* utilities wins: later layer */

/* unlayered styles BEAT every layered one, regardless of specificity */
.btn{ color: red; }
/* ^ this red wins over the white above, even though red is (0,1,0)
   and white is (0,1,0) inside a later layer.

   So an unlayered stylesheet is a nuclear option: it beats your
   entire layer architecture. */
    Unlayered styles take priority over all layered styles. That is deliberate — it means a third-party stylesheet you did not layer cannot accidentally beat your carefully ordered system — but it also means one forgotten <link> outside any @layer overrides everything. If you adopt layers, put every one of your own rules inside a layer.

    Nesting layers, and anonymous layers

    /* a named layer inside a layer: the inner one is added to the
   stack when first encountered, and after the outer one */
@layer reset, base, theme, layout;
@layer base{
  @layer theme{ ... }
}

/* an unnamed @layer block is ANONYMOUS and sorts by first appearance,
   which makes the order depend on which stylesheet loaded first.
   Avoid anonymous layers entirely. */
@layer{ .x{ color: red } }   /* do not do this */

    Declare the layer order once, at the top, in the layer statement itself. Later layers win, unlayered rules win over all layers, and an anonymous layer orders itself by load order — which is the behaviour you are trying to escape.

    2 · Selectors & Combinators

    2.1 Type, class, id and attribute selectors2.2 Pseudo-classes and pseudo-elements2.3 Combinators2.4 :is, :where, :not and specificity maths

    This chapter packs the selector toolbox: type, class, id and attribute selectors, pseudo-classes and pseudo-elements, combinators, and the modern forgiving selectors like is, where and not. Selectors define which elements a rule targets, and combinators express relationships such as descendant, child and sibling. It also works through the specificity maths that let you predict exactly which rule wins.

    Selectors are the targeting system of CSS. The more precisely you can name what you want to style, the less code you write. This chapter walks the full toolbox, from the everyday class to the modern forgiving selectors.

    2.1 Type, class, id and attribute selectors

    A selector is a pattern that matches elements. The four basic kinds — type, class, id, attribute — cover most markup, and everything else is a variation on them. What matters beyond the syntax is the specificity each one costs, because that number follows the selector into every conflict it will ever have.

    The four kinds, with their specificity

    SelectorMatchesSpecificityNotes
    pAny p element(0,0,0,1)The lowest useful weight
    *Everything(0,0,0,0)Counts nothing. Useful in a reset
    .btnAny element with class="btn"(0,0,1,0)The workhorse
    .a.bBoth classes present(0,0,2,0)Two classes, not one
    #appThe element with that id(0,1,0,0)Higher than any number of classes
    [type="email"]By attribute value(0,0,1,0)Exact match
    [type^="ema"]Value begins with(0,0,1,0)Prefix
    [type$="ail"]Value ends with(0,0,1,0)Suffix
    [type*="mai"]Value contains(0,0,1,0)Substring
    [type~="email"]One of a space-separated list(0,0,1,0)Matches the class list, not a substring
    [lang|="en"]en or en-GB(0,0,1,0)Language subtags
    a[href^="http"]External links(0,0,1,1)The usual way to mark them
    /* chaining classes is a specificity decision, not a style choice */
.card{}                    /* (0,0,1,0) */
.card.is-open{}            /* (0,0,2,0) */
.card.is-open.is-featured{} /* (0,0,3,0) */

/* and attribute selectors are how you style by state or by data,
   without inventing classes for it */
tr[data-status="failed"]{ color: var(--danger); }
input:required:not(:placeholder-shown){ border-color: var(--ok); }
[data-density="compact"] .card{ padding: .25rem; }

    Attribute selectors, in detail

    All eight operators exist and three of them cause real bugs. ~= matches a whole word in a space-separated list, so [class~="btn"] matches an element whose class attribute contains btn among others — that is different from [class*="btn"], which matches btn-primary too.

    <span class="btn btn-primary">...

[class*="btn"]{ }    /* matches: btn-primary, btn-large, unbtn */
[class~="btn"]{ }    /* matches: only when btn is a whole word */
    Never style on class="btn" with =. An element almost always carries more than one class, and an exact match silently stops applying the moment a second class is added — which is usually in a different file, by a different person, months later.

    What to select on

    The hierarchy of what makes a stable selector, best to worst: the element, then a class you control, then an attribute you control, then a structural position, and last an id. Structural selectors are the fragile ones because they break the moment someone inserts an element, and they are usually written by someone trying to reach a specific node rather than a component.

    /* fragile: breaks if a wrapper is added anywhere above */
.card > div > p > span{ }

/* fragile in a different way: breaks if the order changes */
.card p:nth-of-type(2){ }

/* stable: a class or a hook you control */
.card__text{ }
.card p{ }
.card > p{ }

    Type is (0,0,0,1), class and attribute and pseudo-class are (0,0,1,0), id is (0,1,0,0) and outranks any number of classes. Match whole words with ~=, select on something you control, and treat nth-of-type and long descendant chains as a last resort.

    2.2 Pseudo-classes and pseudo-elements

    A pseudo-class selects by state — what is true of an element right now — and a pseudo-element selects a part of one. Both are counted in specificity, both add markup the author never wrote, and both have states that are surprisingly hard to observe.

    Pseudo-classes worth knowing by heart

    Pseudo-classTrue when
    :hoverA pointer is over it. Not usable on touch
    :focus-visibleFocused in a way that should show a ring. The one to use
    :focus-withinIt or a descendant has focus. Good for a form group
    :activeBeing pressed right now
    :targetIts URL fragment matches its id
    :checkedA checkbox, radio or option is selected
    :indeterminateA checkbox is partly checked
    :disabled, :enabledWhether the control accepts input
    :required, :optionalWhether the attribute is present
    :valid, :invalidConstraint validation state
    :in-range, :out-of-rangeFor min/max
    :placeholder-shownAn input still showing its placeholder
    :first-child, :last-childPosition among siblings. Not the same as :first-of-type
    :only-child, :emptyOnly sibling; has no children at all
    :nth-child(2n+1)Position among siblings, odd here
    :has()Any descendant matches the argument. The relational one
    :is(), :where(), :not()Matching against a selector list
    /* the three states worth styling together */
:focus-visible{ outline: 2px solid var(--accent); outline-offset: 2px; }
:focus:not(:focus-visible){ outline: none; }
:hover{ background: var(--surface-hover); }

/* form state, with no JavaScript at all */
.field:invalid:not(:placeholder-shown){ border-color: var(--danger); }
.field:valid:not(:placeholder-shown){ border-color: var(--ok); }

/* a control that has content, selected or not */
.option:has(input:checked){ background: var(--accent-soft); }

/* first-child counts ALL siblings; first-of-type counts only the same tag */
li:first-child{ color: red; }      /* first li if it is the first child */
li:first-of-type{ color: red; }     /* first li among the li siblings */
    :hover does not exist on a touch device, and it sticks after a tap: the element stays hovered until something else is touched, which is why a tapped card stays highlighted. Never put information that only appears on :hover behind an action that can be tapped.

    /* the old way: depends on a placeholder being present */
.field:not(:placeholder-shown):invalid{ border-color: var(--danger); }

/* the current way: no placeholder needed, and it clears as they fix it */
.field:user-invalid{ border-color: var(--danger); }

Pair them as :focus:not(:focus-visible){ outline:none } and the ring appears exactly when it should.

    A pseudo-class is a state and costs a class of specificity; a pseudo-element is a part and costs an element. Style :focus-visible rather than :focus, remember :hover is sticky on touch, and keep meaningful text out of ::before and ::after entirely.

    2.3 Combinators

    Four combinators join selectors into a relationship, and a fifth joins them inside a selector list. None of them add specificity, which is convenient and occasionally surprising: > is free, but it also means you cannot use it to escalate.

    The four, and what each one asserts

    CombinatorMeaningSpecificityFails when
    a bDescendant, at any depthAdds nothingNever fails, which is the problem
    a > bDirect childAdds nothingA wrapper element is added
    a + bImmediately following siblingAdds nothingAny element sits between them
    a ~ bAny following siblingAdds nothingThey are not siblings
    a, bEither — a selector LISTHighest of the twoNothing. It is the one that surprises
    /* descendant: matches at any depth, which is why it over-matches */
.card p{ color: var(--text); }
/* this also hits a <p> inside a nested blockquote inside the card */

/* child: precise, and breaks if anyone inserts a wrapper */
.card > p{ }

/* adjacent sibling: the classic "spacing between items" pattern */
h2 + p{ margin-block-start: 0; }     /* only the first p after an h2 */

/* general sibling: everything after */
h2 ~ p{ color: var(--muted); }        /* every following p */

    The list, and why it is the dangerous one

    /* What specificity does .a, .b .c have? Not 0,1,0 and not 0,1,1.
   It has the specificity of its most specific selector: (0,0,1,1). */

.a{ color: red }        /* (0,0,1,0) */
.b .c{ color: blue }    /* (0,0,1,1) */

/* so this one rule beats .a, not because .a is weak but because
   .b .c is heavier - and you wrote them expecting them unrelated. */
.a, .b .c{ }

/* the rule that surprises: adding a selector to a list can LOWER it */
.x, #y .z{ }            /* (0,1,1,0) - the ID dominates the whole list */
#y .z{ }                /* (0,1,0,1) - same visible result, lighter */
    A selector list takes the specificity of its most specific member for every branch. So .a, .b .c makes plain .a as specific as .b .c. This is why adding a selector to a comma-separated list can change which rule wins somewhere else entirely, and why h1, h2, h3 behaves differently from three separate rules.

    nth-child, and the four functions

    ExpressionSelects

   argument, so use nth-last-child for this */
li:last-child{ border-block-end: 0; }
li:nth-last-child(2){ border-block-end: 0; }   /* the other one too */

    Choosing between descendant and child

    The default should be the descendant selector, and the reason is the wrapper problem. A > selector is a claim that nothing will ever be inserted between two elements — and wrappers get inserted. A framework adds a div, a print stylesheet adds one, and a designer adds one to apply a background.

    <!-- as written -->
<div class="card"><p class="card__text">...</p></div>

<!-- someone adds a wrapper. The child selector dies. -->
<div class="card"><div class="card__inner"><p class="card__text">...</p></div></div>

.card > p{ }        /* BROKEN */
.card p{ }            /* still works */
.card .card__text{ }  /* still works, and is the best of the three */

    The > is worth using in exactly two situations: when the extra levels genuinely must not be styled — a reset where you are establishing that a heading is a direct child of a section, for instance — and in :nth-child arithmetic, where it removes the need to count.

    Sibling combinators, and the spacing pattern they enable

    The + combinator solves a real layout problem that is otherwise solved with JavaScript or with margin-top on every element except the first. h2 + p removes the top margin from the paragraph that directly follows a heading — the one case where that margin is visually wrong — without touching any other paragraph on the page.

    /* the general problem: spacing between siblings without touching the first */
.stack > * + *{ margin-block-start: 1rem; }
/* the specific fix: only the paragraph right after a heading */
h2 + p{ margin-block-start: 0; }
/* and the general sibling version, for every following paragraph */
h2 ~ p + p{ margin-block-start: 2rem; }
    /* two sibling hooks at once, in a form */
.form__field + .form__field{ margin-block-start: 1.25rem; }
.form__field:has(:user-invalid){ border-inline-start: 3px solid var(--danger); }
.form__field + .form__field:has(:user-invalid){ margin-block-start: 1.5rem; }

    One thing + and ~ cannot do is look backwards. There is no previous-sibling combinator, so x + y always means "y immediately after x", and anything needing the element before a given one has to be written as y:has(+ x) — :has(+ p) on an h2 selects a heading followed by a paragraph.

    Because there is no previous-sibling combinator, the workaround reads backwards and is easy to get wrong: p:has(+ p) selects a paragraph followed by another paragraph, not one preceded by one. Whenever a layout depends on what came before, write the rule as that thing :has(+ what you were given), and check it against real markup rather than reasoning about it in the abstract.

    Descendant by default, child only when you mean it, and never a deep descendant chain. Sibling combinators are the cleanest available fix for spacing between elements, with the caveat that they only ever point forwards.

    Descendant, child, adjacent sibling, general sibling — none of which add specificity. A selector list does, taking the heaviest member for every branch, which is why editing a comma-separated list can change a rule's weight somewhere else.

    2.4 :is, :where, :not and specificity maths

    Four functional pseudo-classes take a selector as an argument, and they differ in a way that matters more than it looks: three of them take their specificity from their argument, and one deliberately takes none. That one choice is what makes :where() the right tool for a default.

    :is, :where, :not, :has

    FunctionMatches whenSpecificity
    :is(a, b, c)Any argument matchesThe heaviest argument
    :where(a, b, c)Any argument matchesAlways zero
    :not(a, b)No argument matchesThe heaviest argument
    :has(a)A relative selector matchesThe heaviest argument
    :is(h2, h3, h4){ margin-block-start: 2rem; }
/* specificity is that of h4 - (0,0,0,1) */

:where(h2, h3, h4){ margin-block-start: 2rem; }
/* specificity is 0,0,0,0 - it loses to almost anything */
    This pairing is the mechanism that replaces specificity wars. Write the default with :where() so it carries no weight, then override it with a class or an id. The default can never win an argument it should lose, and you never have to think about it again.

    :has, and why it changed CSS

    :has() matches an element based on its descendants or siblings — the parent selector CSS never had. It is the reason "style a form when it contains an invalid field" went from a JavaScript classList to one line.

    /* style the FIELD LABEL, based on what the input contains */
.field:has(input:invalid:not(:placeholder-shown)) .field__label{
  color: var(--danger);
}

/* style a CARD based on its state */
.card:has(.card__badge){ border-color: var(--accent); }
.card:has(> img){ grid-template-columns: 8rem 1fr; }

/* style the PARENT list when any item is selected */
ul:has(li[aria-current="page"]) ul{ background: var(--accent-soft); }

/* :has is not restricted to descendants - it takes a full relative
   selector, so siblings work too */
.box:has(+ .box:hover){ background: var(--surface-alt); }

/* and it can nest, which is where it becomes genuinely powerful
   without JavaScript */
.card:has(.card__title:focus-visible){
  outline: 2px solid var(--accent);
}
    :has() invalidates styles for siblings and ancestors of the match, so a very broad one — body:has(*) — can force the engine to re-evaluate a large part of the tree on every change. Narrow the argument to the smallest thing that answers the question, and prefer body:has(.modal-open) to body:has(*).

    The zero-specificity pattern, in full

    /* 1. a defensible default, with no weight */
:where(.btn){
  background: var(--surface);
  color: var(--text);
  padding: .5rem 1rem;
  border-radius: var(--radius);
}

/* 2. variants override with a plain class, however they like */
.btn--primary{ background: var(--brand); color: var(--brand-ink); }
.btn--ghost{ background: transparent; border: 1px solid var(--border); }

/* 3. a state still needs one class of weight, because :where() gave none */
.btn:is(:hover, :focus-visible){ background: var(--surface-hover); }

/* Nothing in this needs !important, an id, or a doubled class,
   because the default was written to be beatable. */

    Using :where to make a system order-independent

    The pattern only pays off if it is applied consistently, and the reason is worth stating precisely. A stylesheet that mixes weights is a stylesheet where every conflict has to be decided by counting; one where all defaults are :where() is a stylesheet where the only conflicts that matter are the ones you wrote deliberately.

    /* Reset, base, layout, components, utilities - all zero-specificity */
@layer reset, base, layout, components, utilities;

@layer base{
  /* every default is written so it can be beaten by one class */
  :where(a){ color: var(--accent); }
  :where(button){ font: inherit; }
  :where(h1, h2, h3){ margin-block: 0 0.5em; }
  :where(img){ max-width: 100%; height: auto; }
}

@layer components{
  /* components set their own weights freely, because nothing else
     in this layer is competing for the same property */
  .btn{ font-weight: 600; }
  .btn--lg{ font-size: 1.125rem; padding: .75rem 1.5rem; }
}

@layer utilities{
  /* one utility, deliberately able to beat any component */
  .u-hidden{ display: none; }
  .u-mt-4{ margin-block-start: 1rem; }
}
    With layers doing the ordering, utilities no longer need !important. That is the practical payoff: the one place a codebase accumulates important declarations is the place that becomes hardest to change, and layers delete it.

    What is safe to rely on

    FeatureStatusSafe without a fallback?
    :where(), :is()Baseline widely availableYes — use freely
    :has()Baseline widely available since 2023Yes, but scope the argument — see 8.3 for the cost
    :not() with a selector listWidely availableYes. A single simple argument is much older
    Native CSS nestingBaseline widely availableYes. Check the & rules below first
    @layerBaseline widely availableYes — layers that a browser ignores still cascade by source order
    Type selectors inside :is()Widely availableYes

/* and the reverse: the base rule, enhanced upward */

}

    Write every default with :where() and every override with an ordinary class, and specificity stops being something you compute and becomes something you choose once. Combine that with @layer and the whole question of which rule wins is answered by the layer statement.

    :is(), :not() and :has() take the heaviest argument's specificity; :where() takes none. That is the whole reason to use them: write defaults with :where() so they never win an argument they should lose.

    3.1 The box model and box-sizing

    Every element is a box, and CSS gives you four properties that describe it: content, padding, border and margin. Two of those are inside the border and two are outside it, which is the whole distinction that makes the model click. Almost every layout bug in CSS comes from not knowing which is which.

    The four parts, inside out

            margin
     ┌───────────────────────┐   <- outer: transparent, never painted
     │        border         │   <- painted
     │  ┌─────────────────┐  │
     │  │     padding     │  │   <- painted, part of the element's background
     │  │  ┌───────────┐  │  │
     │  │  │  content  │  │  │   <- the text, and width/height size this
     │  │  └───────────┘  │  │
     │  └─────────────────┘  │
     └───────────────────────┘
    PropertyApplies toBackground paints over it?
    marginEverything except replaced and inline elementsNo — it is outside the element entirely
    borderEverythingYes, under the background
    paddingEverythingYes — padding is inside the background
    width / heightEverything except inline and non-replaced inlineSets the content box, unless box-sizing says otherwise

    box-sizing, which should be global

    The default is content-box: width sets the content box, and padding and border are added on top. That is almost never what anyone means, and it is why width: 100% plus padding overflows its parent.

    /* content-box (the default): the element ends up WIDER than 240px */
.box{ box-sizing: content-box; width: 200px; padding: 20px; border: 1px solid; }
/* total = 200 + 40 + 2 = 242px */

/* border-box: width includes padding and border */
.box{ box-sizing: border-box; width: 200px; padding: 20px; border: 1px solid; }
/* total = 200px */

/* apply it everywhere, including on pseudo-elements */
*, *::before, *::after{ box-sizing: border-box; }
    Setting box-sizing: border-box on * only is not enough. Pseudo-elements are separate boxes with their own box-sizing, and they are exactly where an icon::before with padding and a width ends up twice as wide as intended. The declaration must include *::before and *::after.

    Sizing, and the three things that do not work

    width and height set the content box, and three values are worth knowing: auto for the intrinsic size, min-content for the narrowest it can be without overflowing, and max-content for the width it would take on one line.

    /* auto: as wide as the content needs, up to the container */
.card{ width: auto; }

/* min-content: the narrowest possible - where the longest word fits */
.film-strip img{ width: min-content; }

/* max-content: one line, however long. Useful in a grid track */
.tooltip{ width: max-content; max-width: 30ch; }

/* the three that do NOT work on a normal block */
.wrong1{ width: 100%; padding: 2rem; }          /* overflows, see above */
.wrong2{ height: 100%; }                        /* percentage of what? parent needs a height */
.wrong3{ margin-top: -100%; }                  /* percentage margins resolve against the
                                                   container's INLINE size, not its height */
    Percentage margins and padding resolve against the inline size of the containing block — its width, even for margin-top. So margin-top: 10% on a wide-but-short container is a large value, and this surprises people once per career. Use viewport or container units when you want a value that scales with a dimension.

    Logical properties, and why they are the default now

    /* physical */
.card{ margin-top: 1rem; margin-right: 2rem;
       margin-bottom: 1rem; margin-left: 2rem; }
.card{ padding: 1rem 2rem; }
.card{ border-left: 3px solid var(--accent); }
.card{ width: 40ch; }

/* logical - the same intent, and it follows the writing mode */
.card{ margin-block: 1rem; margin-inline: 2rem; }
.card{ padding-block: 1rem; padding-inline: 2rem; }
.card{ border-inline-start: 3px solid var(--accent); }
.card{ inline-size: 40ch; }

    Logical properties map to the writing mode rather than to the screen. In a horizontal left-to-right language, block-start is the top and inline-start is the left — so margin-inline-start is exactly margin-left. In Arabic, with dir="rtl", it becomes the right, and the whole layout mirrors with no second stylesheet.

    Use the shorthand for the two axes where you can — margin-inline instead of margin-left and margin-right, inset-inline instead of left and right — and write inline-size and block-size rather than width and height. The physical names still exist and are correct for the 95% case, but the logical ones compose better and are what the rest of this guide uses.

    Margin is outside and never painted, padding is inside and is. Set box-sizing: border-box on * and both pseudo-elements, and prefer logical properties so the box follows the writing mode rather than the viewport.

    3.2 Padding, border, margin and collapse

    Padding and border are simple — they add to the element. Margin is where the complexity lives, because margins between two elements collapse into one, and the result is almost never what the arithmetic suggests. Margin collapsing is the cause of most "my margin does nothing" reports.

    Margin collapsing, in three cases

    Two vertical margins collapse when there is nothing between them to separate them. The value that survives is the larger of the two, not the sum and not the smaller.

    <!-- 16px above, 24px below -->
<h2>One</h2>
<p>...</p>

<!-- the gap between them is 24px, not 40px -->
/*   ^^^^^^^^ 16   */
/*          ^^^^^^^^ 24   -> collapses to max(16,24) = 24 */

    Collapsing happens in three situations, and knowing which one you are in explains most of it.

    CaseRuleConsequence
    Adjacent siblingsBottom margin of one and top margin of the next collapseSpace between blocks is max(a,b)
    Parent and first childA top margin on the first child collapses through the parent's top edge if the parent has no padding, border or overflow setThe child appears to escape the parent. "Why is my card's heading outside it?"
    Parent and last childSame, with bottom margins, unless the parent has height, min-height, padding, border or overflow other than visibleThe parent's background stops short of its content
    /* the classic escape: margin-top on the first child collapses out */
.card{ background: var(--panel); }
.card__title{ margin-block-start: 1rem; }
/* the panel starts BELOW the margin - the title is outside it */

/* three fixes, pick by intent */
.card{ display: flow-root; }                    /* establish a block formatting
                                                   context, nothing else changes */
.card{ padding-block-start: .1px; }             /* the classic hack, and it is ugly */
.card{ overflow: auto; }                        /* also works, also has side effects */

/* or use the child's margin-inline and padding on the parent instead */
.card{ padding-block-start: 1rem; }             /* the honest fix */
.card__title{ margin-block-start: 0; }
    display: flow-root is the correct fix when the parent should contain its children's margins and you have no opinion about anything else changing. It creates a block formatting context, which stops the collapse, and it does nothing to layout besides that. overflow: hidden also works and additionally clips overflow, which is usually not wanted.

    Margin and padding, written well

    ShorthandExpands toTypical use
    margin: 1rem 2rem1rem top and bottom, 2rem left and rightThe common case
    margin: 1remAll fourReset, spacing scale
    margin-inline: 2remStart and end of the inline axisFollows writing mode
    margin-block-start: 1remTop, in horizontal writingPrecise overrides
    padding: 1rem 2remSame as marginContent inside a card
    padding-inline: 2remStart and end of inline axisWriting-mode aware

/* and do not apply to flex or grid items in the collapsing sense -
   adjacent margins there do NOT collapse */
.flex{ display: flex; }
.flex > *{ margin-block-start: 1rem; }   /* each is 1rem below the last */

    Negative margins, and auto centring

    /* negative margin: pulls an element outward. Useful for a full-bleed
   child inside a padded parent, without touching the parent's padding */
.page{ padding-inline: 2rem; }
.page__bleed{ margin-inline: -2rem; }

/* the classic centring trick, still the right answer in a grid cell */
.container{
  display: grid;
  place-items: center;
}
/* or, without grid */
.centre{
  display: flex;
  align-items: center;
  justify-content: center;
  min-height: 100dvh;
}
/* and the block-level one that works without flex or grid */
.centre-old{
  width: fit-content;
  margin-inline: auto;
}
    A negative margin is not a hack; it is the only way to cancel a parent's padding without restructuring the DOM, and full-bleed content inside a padded container is a genuine layout requirement. It is a hack when it is used to undo a margin that was a mistake.

    Adjacent vertical margins collapse to the larger of the two, and a first child's top margin collapses through its parent unless the parent has padding, a border, a height or display: flow-root. Padding and border are inside the element and never collapse.

    3.3 Units: px, rem, em, %, vw, vh, ch

    CSS has two kinds of length: absolute, which do not respond to anything, and relative, which respond to the reader's font size or to the viewport. Choosing wrong is not a matter of taste — using px for body text makes a page unreadable for a reader who has turned up their default font size, and that setting exists because they had to.

    The units, and what each responds to

    UnitRelative toTypical use
    pxNothingBorders, shadows, anything that must not scale with text
    remThe root font sizeType scale, spacing. The default choice
    emThe element's own font sizePaddings that should grow with their own text
    %The parent's matching dimensionWidths. Never a height unless the parent has one
    chThe width of 0 in the current fontA max-width on prose — near-perfect for measure
    exThe height of xRarely. Superscript alignment
    lhThe computed line-heightScaling spacing with the type scale
    vw, vh1% of the viewportHero sizing. Beware the mobile bars
    vmin, vmaxSmaller / larger viewport axisFull-screen layouts that must fit either way
    dvh, svh, lvhDynamic / small / large viewport heightAnything full-height on a phone
    svw, lvw, dvwSame, for widthRarely needed
    /* em compounds, and that is the thing to know */
.btn{ font-size: 1rem; padding: .5em 1em; }
/* padding is 0.5rem/1rem now - it follows the element's own font-size */

.card__body{
  font-size: 1.25em;          /* 20px, and this element is now 1.25em-based */
  padding: 1em;              /* 20px, not 16px - it follows the NEW size */
  border-radius: .25em;      /* 5px */
}

/* which is why nesting em-based sizing multiplies:
   1.25 * 1.25 * 1.25 = 1.95x after three levels */
    That compounding is why em is dangerous inside nested components and why rem is usually safer. An em-based padding on an element that is itself em-sized multiplies at every level, and the result drifts far from the value you wrote. Use em where the padding genuinely must track its own text size — an icon in a label — and rem everywhere else.

    Viewport units, and the mobile browser bars

    100vh is the viewport height with the browser's own chrome excluded, and on a phone that height changes as the bars hide and show. A section sized 100vh is taller than the screen when the bars are visible, so it can never be seen in full.

    /* broken on mobile: taller than the visible area */
.hero{ min-height: 100vh; }

/* the three dynamic viewport units, and what each measures */
.hero{ min-height: 100svh; }   /* small: bars always shown. Stable, no jump */
.hero{ min-height: 100lvh; }   /* large: bars hidden. Tallest possible */
.hero{ min-height: 100dvh; }   /* dynamic: current. Resizes as bars move */

/* the practical combination: fit the small viewport, grow to the large */
.hero{ min-height: 100svh; }
@supports (min-height: 100lvh){
  .hero{ min-height: 100lvh; }
}
/* that never causes a resize mid-scroll on a phone */

    calc, clamp and container query units

    /* calc: mixed units in one value */
.card{ width: calc(100% - 2rem); margin-inline: auto; }
.card{ width: min(100% - 2rem, 40rem); }      /* no calc needed here */
.card{ font-size: clamp(1rem, 0.9rem + 0.5vw, 1.25rem); }

/* cqi / cqw: relative to the nearest query container, not the viewport */
.panel{ container-type: inline-size; }
.panel__title{ font-size: clamp(1rem, 4cqi, 1.5rem); }

    min(), max() and clamp() take the same arguments as calc(), and where a calc wraps a single subtraction you can usually write min() instead — min(100% - 2rem, 40rem) is shorter and clearer. clamp(min, preferred, max) is the fluid-value workhorse and is covered properly in section 4.4.

    Set the reader's base size in rem and never in px, and the browser default at 16px applies. html{ font-size: 62.5% } is a widespread convention that makes 1rem equal 10px — which makes the arithmetic easier to read and makes the font-size control on body stop working, since it is in rem and so changes with the root.

    Use rem for type and spacing, ch for prose measure, viewport units only with svh/lvh on mobile, and remember em compounds through nesting while rem does not.

    3.4 Color notation and gradients

    Colour has five notations in modern CSS and three colour spaces, and the space matters more than the notation. oklch() was added so that a colour could be defined by the lightness and hue a designer actually chose, with the browser resolving it into a displayable colour rather than the numbers falling outside the gamut.

    The notations

    NotationWritten asNotes
    Namedrebeccapurple147 of them. Inconsistent naming, and some are surprising
    Hex#1a73e8, #1a73e880Universal. The alpha form is 8 digits, RRGGBBAA
    rgb() / rgba()rgb(26 115 232 / 50%)Space-separated. Slash before alpha
    hsl() / hsla()hsl(212 80% 51%)Hue, saturation, lightness. Perceptually uneven
    oklch()oklch(0.65 0.19 250)Lightness, chroma, hue. Perceptually even. The one to learn
    color()color(display-p3 1 0 0)Wide-gamut, where the display supports it
    color-mix()color-mix(in oklab, red 30%, transparent)Derived from two existing colours. Avoids new tokens
    :root{
  /* oklch: L is 0 to 1, C is roughly 0 to 0.4, H is degrees */
  --brand:   oklch(0.78 0.15 205);
  --accent:  oklch(0.62 0.19 250);
  --danger:  oklch(0.58 0.21 25);

  /* the same colour expressed four ways */
  --a: #1a73e8;
  --b: rgb(26 115 232);
  --c: hsl(212 80% 51%);
  --d: oklch(0.58 0.19 255);
  /* all four render identically; oklch is the one that scales sensibly */
}
    In oklch, two colours with the same L look equally bright regardless of hue — which is not true in HSL. That property is why it is the right space for a palette: you can set a lightness ramp and every step will look one step brighter, instead of yellow being brighter than blue at the same number.

    color-mix, and why it beats a new token

    color-mix() takes two colours and a proportion, in a space you choose. Its value here is that it derives a colour from tokens that already exist, so it adapts to every theme and every mode without a single new declaration — which is exactly the kind of thing that otherwise requires a token in each palette block.

    /* a hover tint, derived, with no new token */
.btn{
  background: var(--brand);
  color: var(--brand-ink);
}
.btn:hover{
  background: color-mix(in oklab, var(--brand) 85%, black);
}

/* a translucent version. Mixing with the keyword transparent gives real
   alpha, because color-mix premultiplies - a fade, not a mix toward black */
.overlay{ background: color-mix(in oklab, var(--text) 20%, transparent); }

/* mixing in oklab avoids the muddy midpoint that srgb gives you */
.card{ border: 1px solid color-mix(in oklab, var(--accent) 30%, var(--border)); }

/* a two-axis ramp from one hue */
:root{
  --brand-l: oklch(0.78 0.15 205);
  --hover:   oklch(0.72 0.16 205);
}
    Mix in oklab, not in srgb. An srgb midpoint between two colours passes through a dull, desaturated region — mixing blue and yellow in srgb gives you a grey-ish mud, while the same mix in oklab gives you a clean green. This is the single most important argument for using oklab for any derived colour.

    Gradients

    /* linear-gradient: an angle plus colour stops */
.hero{
  background: linear-gradient(160deg,
    var(--brand) 0%,
    color-mix(in oklab, var(--brand) 60%, var(--accent)) 55%,
    var(--accent) 100%);
}

/* radial-gradient: a shape, a size, and a position */
.badge{
  background: radial-gradient(circle at 30% 30%,
    white, color-mix(in oklab, white 60%, var(--accent)));
}

/* conic-gradient: an angle sweep. Used for progress rings */
.ring{
  background: conic-gradient(var(--accent) 0turn var(--p, 0.25turn),
                              var(--border) 0turn);
  border-radius: 50%;
}

/* hard stops make a stripe rather than a blend */
.stripes{
  background: repeating-linear-gradient(45deg,
    var(--accent) 0 8px,
    transparent 8px 16px);
}

    Every gradient takes a direction and a list of stops, and stops do not have to be percentages — two colours with no positions produce a hard edge. in oklab as the interpolation space gives a more even blend than the default srgb, which matters on long ramps where srgb produces a visible band through the middle.

    A gradient is not accessible text. Text on a gradient has to clear 4.5:1 against the least favourable part of it, not against a representative colour — which is why a dark scrim over a gradient is usually needed for a heading placed on one. Test the worst stop, not the average.

    Use oklch for a perceptually even ramp, color-mix() in oklab to derive tints from tokens you already have, and remember that mixing with transparent yields real alpha while an srgb mix does not.

    4.1 Font stacks and web fonts

    A font stack is an ordered list of families with the generic last. The list exists because no font is available everywhere, and the order is the fallback strategy: the browser walks it and uses the first family it can resolve. Getting the order right is what makes a page look the same on a machine you do not control.

    How the stack is resolved

    body{
  font-family:
    "Inter Variable",        /* your web font, exact match first */
    Inter,                   /* the same family, installed locally */
    system-ui,               /* the OS's UI face: the safest sans */
    -apple-system,           /* explicit vendor faces, older approach */
    "Segoe UI",
    Roboto,
    "Helvetica Neue",
    Arial,
    sans-serif;              /* the generic. ALWAYS last */
}

/* local() picks an installed font rather than downloading one */
p{ font-family: local("Inter"), sans-serif; }
    Generic familyWhat it meansUsual result
    serifAny serifTimes New Roman on Windows, Georgia on macOS
    sans-serifAny sansArial, Helvetica, the OS default
    monospaceAny fixed-pitchConsolas, Menlo, DejaVu Sans Mono
    system-uiThe OS's own interface faceBest-looking on every platform, and it differs per OS
    ui-monospaceThe OS's code faceMatches the OS rather than a code font you chose
    cursive, fantasyScript, decorativeUnpredictable. Rarely what you want
    math, emojiMath and colour glyphsUsed in a stack for specific spans, not for body
    system-ui is the closest thing to "the right font on every device" that CSS offers. It resolves to San Francisco on macOS, Segoe UI Variable on Windows, Roboto on Android — each the platform's intended face. A stack that starts system-ui looks native everywhere without shipping a single byte.

    Loading a web font properly

    @font-face{
  font-family: "Inter Variable";
  src: url("/fonts/inter-var.woff2") format("woff2-variations");
  font-weight: 100 900;          /* the variable axis range */
  font-style: normal;
  font-display: swap;            /* show the fallback immediately */
  unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+2000-206F;
}

/* and with two subsets, so Latin readers do not download Arabic */
@font-face{
  font-family: "Inter Variable";
  src: url("/fonts/inter-var-arabic.woff2") format("woff2-variations");
  font-weight: 100 900;
  unicode-range: U+0600-06FF, U+0750-077F, U+08A0-08FF;
}
    /* the metrics that stop the page reflowing when the font arrives */
@font-face{
  font-family: "Inter Fallback";
  src: local("Arial");
  size-adjust: 107%;
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}
/* then declare it BEFORE the real font, so the swap is metric-compatible */
body{ font-family: "Inter Fallback", "Inter Variable", system-ui, sans-serif; }
    Without size-adjust and the ascent/descent overrides, font-display: swap causes a visible reflow: text renders in the fallback at the wrong size, then jumps when the web font arrives. With them, the fallback is scaled to match, and the swap is close to invisible. This is the single biggest quality difference between a site that loads a web font well and one that does not.

    Variable fonts

    :root{
  --wght: 400;
  --wdth: 100;
  --slnt: 0;
}

body{
  font-family: "Inter Variable", system-ui, sans-serif;
  font-variation-settings:
    "wght" var(--wght),
    "wdth" var(--wdth),
    "slnt" var(--slnt);
  transition: font-variation-settings .2s ease;
}
body:has(input#bold:checked){ --wght: 700; }

/* the animatable properties - preferred over font-variation-settings,
   because font-variation-settings cannot be transitioned */
body{
  font-weight: var(--wght);
  font-stretch: var(--wdth);
  font-style: oblique var(--slnt);
  transition: font-weight .2s ease, font-stretch .2s ease;
}

    The three mappings are the ones worth knowing: wght to font-weight, wdth to font-stretch, and slnt to font-style: oblique. Using the real properties rather than font-variation-settings matters because they can be transitioned, while font-variation-settings is not animatable.

    /* numerals that line up in a table */
.nums{ font-variant-numeric: tabular-nums; }
.caps{ font-variant-caps: all-small-caps; }
.oldstyle{ font-variant-numeric: oldstyle-nums; }
.liga{ font-variant-ligatures: common-ligatures; }   /* usually the default */

    Always end the stack with a generic family, put system-ui early if you do not need a specific face, split web fonts by unicode-range, and pair font-display: swap with a size-adjust fallback so nothing jumps.

    4.2 Size, weight, line-height and spacing

    Four properties set type: size, weight, line height, and the two that space individual lines. They interact — line height is inherited as a number and multiplies against whatever size the element ends up with, which is why changing a parent's font size moves all its spacing at once.

    Size, and the relationship between the properties

    PropertyAcceptsInherited as
    font-sizeLength, percentage, keywordsThe computed length
    font-weight100–900 in stepsThe number
    line-heightNumber, length, percentageA number stays a number
    letter-spacingLengthThe computed length
    word-spacingLengthThe computed length
    text-transformKeywordThe keyword
    /* the difference that matters */
body{ font-size: 1rem; line-height: 1.5; }
/* a child at 2rem gets 3rem of line height: 2 * 1.5 */

body{ font-size: 1rem; line-height: 150%; }
/* a child at 2rem gets 2rem of line height: 150% of its OWN size,
   and 150% of 1rem = 1.5rem for body. They agree at body size
   and diverge everywhere below it. */

body{ font-size: 1rem; line-height: 24px; }
/* a child at 2rem STILL gets 24px - and the lines will overlap. */
    Use a unitless line-height, always. It is the only form that scales correctly when a descendant changes its own font size, and a fixed length or percentage silently breaks the moment any text in the page is resized independently.

    A scale that holds up

    :root{
  --text-sm:   0.875rem;  /* 14px */

  --text-lg:   1.25rem;
  --text-xl:   1.5rem;
  --text-2xl:  2rem;
  --text-3xl:  2.5rem;

  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-6: 1.5rem;

h2{ line-height: 1.2; }
h3{ line-height: 1.3; }

/* measure: the length of a line, in characters. 60-75 for prose */

}

   a big heading needs to look right */

    Every type property inherits, so the scale belongs on body and every heading needs its size, weight, line height and tracking set deliberately. A unitless line-height on the root makes all of that scaling correct without further work.

    4.4 Fluid type with clamp

    Fluid type is one expression that produces a size between a minimum and a maximum, growing with the viewport rather than jumping at breakpoints. It removes the media queries from a type scale entirely, and it makes the scale continuous instead of stepped.

    clamp, and what the three arguments mean

    /* clamp(MIN, PREFERRED, MAX) */
h1{ font-size: clamp(2rem, 1.2rem + 3vw, 3.5rem); }
/*          ^min  ^grows with the viewport      ^max

/* the middle argument must contain a viewport unit, or it is constant
   and you have written min() by accident */

/* simpler forms of the same idea */
.card{ font-size: min(1.125rem, 2.5vw); }        /* shrinks only */
.hero{ font-size: max(1rem, 4vw); }              /* grows only */

/* the full version, with a preferred step */
h1{
  font-size: clamp(2rem, 1rem + 2.5vw + 0.5rem, 3.5rem);
}

    The arithmetic that makes it readable: the middle term is preferred, not a target. It is what the size would be at a viewport of zero if the rem part were its only component, and the vw part is the slope. Adding a rem term means the type still has a sensible size if the viewport unit is ignored, which is what happens when a reader has a minimum font size set.

    The rem in the middle term is not decoration. A reader who has set a minimum font size in their browser will have your vw term ignored or clamped, and the rem term is what keeps the heading legible at that point. Without it, a large heading can end up smaller than the body text.

    Fluid spacing, and where to stop

    :root{
  /* one fluid step between two fixed ones */
  --space-fluid: clamp(1rem, 0.5rem + 2vw, 2rem);

  /* a scale where the middle steps are fluid and the ends are fixed */
  --space-4:  1rem;
  --space-6:  clamp(1.25rem, 0.9rem + 1.5vw, 1.75rem);
  --space-8:  clamp(1.5rem, 1rem + 2.5vw, 2.5rem);
  --space-12: clamp(2rem, 1rem + 5vw, 4rem);
}

/* section spacing is where fluid is most valuable: it is the
   difference between "somewhere between" and a media query */
.section{ padding-block: var(--space-12); }
.section + .section{ padding-block-start: var(--space-8); }
    Fluid everything produces a page with no rhythm at the extremes. On a very wide display the type stops growing at the clamp's maximum while the columns keep widening, and the reading experience degrades — long lines, wide margins, and type that looks small on a large screen. Fluid the type scale and the section spacing; keep component padding fixed.

    Container query units, and when they are better

    /* a component that responds to ITS OWN width, wherever it lands */
.card{ container-type: inline-size; }

.card__title{
  font-size: 1rem;
  font-size: clamp(1rem, 8cqi, 2rem);
}
/* cqi is 1% of the container's inline size */

@container (min-width: 30rem){
  .card{ grid-template-columns: 8rem 1fr; }
  .card__title{ font-size: 1.5rem; }
}
    This is the case viewport units cannot handle. A card in a sidebar and the same card in a main column want different internal type sizes, and both are on the same page at the same viewport width — so vw gives them the same answer, wrongly. Container query units give each one an answer based on its own width, which is the correct question.
    /* a complete fluid type scale, no media queries */
:root{
  --step--1: clamp(0.833rem, 0.8rem + 0.16vw, 0.9rem);
  --step-0:  clamp(1rem,     0.95rem + 0.25vw, 1.125rem);
  --step-1:  clamp(1.2rem,   1.1rem + 0.5vw,   1.5rem);
  --step-2:  clamp(1.44rem,  1.25rem + 0.95vw, 2rem);
  --step-3:  clamp(1.728rem, 1.4rem + 1.6vw,  2.75rem);
  --step-4:  clamp(2.074rem, 1.6rem + 2.4vw,  3.5rem);
}

    clamp() with a viewport unit in the middle and a rem alongside it gives a fluid size that still survives a reader's minimum-font setting. Fluid the type scale and section spacing, keep component padding fixed, and use container query units for anything that has to respond to its own width.

You create a flex container with the display property set to flex, then control the main and cross axes with flex-direction, alignment and distribution. Flex items stretch or shrink according to the flex shorthand, and the reusable layouts such as media objects and sticky footers are built from these few tools.

    Flexbox lays out children along a single line, distributing space and aligning items automatically. It is the right tool for rows, columns, toolbars, ranking lists and centring. When layout needs two independent dimensions, you will reach for the Grid in the next chapter.

    5.1 The container and the two axes

    Flexbox lays out a row or a column and distributes space along it. You choose the direction once on the container, and every axis question afterwards follows from it: the main axis is the one items flow along, the cross axis is perpendicular, and they swap when you switch direction.

    The one declaration that matters

    .row{ display: flex; }
.column{ display: flex; flex-direction: column; }

/* and the two that make it a wrapping container */
.wrap{
  display: flex;
  flex-wrap: wrap;
  gap: 1rem;          /* the modern shorthand for row-gap and column-gap */
}

    row (default)HorizontalVerticalLeft to right
    row-reverseHorizontal, reversedVerticalRight to left
    columnVerticalHorizontalTop to bottom
    column-reverseVertical, reversedHorizontalBottom to top

    Because the axes are named rather than fixed, most flexbox properties are relative to them. flex-grow distributes along the main axis; align-items works across the cross axis. When you switch to column, both swap — and any code that hardcoded the word "width" instead of "main axis" is now wrong in a way that is invisible until you run it.

    /* this works in BOTH directions, because the properties are logical */
.container{

  flex-direction: var(--dir, row);
  gap: 1rem;
}
.container > *{

  min-inline-size: 0;             /* or, in a column: min-block-size */
}
.container[style*="column"] > *{ min-inline-size: 0; min-block-size: 0; }

The old .item + .item { margin-left } pattern adds space before the first item and needs the sibling selector, which gap does not.

    5.3 Flex items: grow, shrink, basis and order

    The three item properties — flex-grow, flex-shrink, flex-basis — describe how an item responds to leftover or missing space. They are almost always set through the flex shorthand, and the values you choose are a decision about whether the container is distributing surplus or dividing scarcity.

    The flex shorthand, decoded

    ShorthandgrowshrinkbasisMeans
    flex: 1110%Equal share of the container, ignoring content size
    flex: 1 1 0110%The explicit form of flex: 1
    flex: auto11autoContent size, then grows into leftover space
    flex: auto 111autoSame. An explicit-looking variant
    flex: initial01autoNever grows, shrinks if needed
    flex: none00autoFixed at content size. Neither grows nor shrinks
    flex: 2210%Twice the share of a flex: 1 sibling
    flex: 0 0 12rem0012remExactly 12rem, rigid
    flex: 1 1 0%110%Identical to flex: 1
    flex: 1 is shorthand for flex: 1 1 0%, not flex: 1 1 auto. The basis is zero, which means items with a lot of content and items with very little end up exactly the same width. Almost every time someone wants "equal width but sized by content", they want flex: auto, and almost every time something overflows unexpectedly it is because they wrote flex: 1 and got a zero basis.

    The sizing algorithm, in order

    Flexbox is a single-pass algorithm, and knowing the order is the only reliable way to predict it.

    /* 1. Determine the flex base size for each item
      = flex-basis, or 0 if flex-basis:auto and width is not auto,
      or the content size otherwise

   2. Sum the hypothetical main sizes.
      If the total is SMALLER than the container, distribute the surplus
      by flex-grow, in proportion.
      If the total is LARGER, shrink by flex-shrink, in proportion.

   3. Clamp each item by its min and max sizes.
      THIS is why "the maths says it should fit" and it does not. */

.card{ display: flex; }
.card__img{ flex: 0 0 8rem; }
.card__body{ flex: 1 1 auto; min-inline-size: 0; }
    Step 3 is the whole explanation for the most common flexbox bug. An item's used size is clamped by min-width and max-width after the grow and shrink arithmetic. So an item with a long unbreakable word and the default min-width: auto refuses to shrink below its content, the row overflows, and no amount of flex-shrink fixes it.
    /* THE most common flexbox fix: min-width: 0 */
/* without it, an item's automatic minimum size is its min-content
   size, so long text and overflow: hidden children refuse to shrink */

.card__body{
  flex: 1 1 auto;
  min-inline-size: 0;      /* or min-width: 0 - the logical form */
}
.card__body img{ max-inline-size: 100%; }

/* in a column, the equivalent trap is on the block axis */
.stack{ display: flex; flex-direction: column; }
.stack > *{ min-block-size: 0; }

    order, and why it is a last resort

    /* visual order without changing the DOM order */
.card__actions{ order: 1; }
.card__title{ order: -1; }

/* the gap in the DOM order, which matters for a screen reader,
   for find-in-page, and for tab order */
<div class="card">
  <h3 class="card__title">Title</h3>
  <p class="card__body">Body</p>
  <div class="card__actions"><button>Go</button></div>
</div>
    order changes what a reader sees and not what a screen reader announces or what find-in-page finds, because both use the DOM. A visual reorder that differs from the DOM is one of the most common ways a page looks fine and reads wrongly, and no accessibility tool will flag it — the two orders are simply different.

    flex: 1 means a zero basis, so items are equal regardless of content — use flex: auto when content should matter. Add min-inline-size: 0 or long content will not shrink, and reach for order only when you have checked the DOM order still makes sense.

    5.4 Common flexbox layouts

    Flexbox solves one-dimensional distribution. The layouts below are the ones it is genuinely better at than any alternative, and knowing which are which prevents a lot of grid being used for things flexbox does more simply.

    The three centring problems, and which solves which

    /* 1. one element in a known-size parent */
.parent{ display: grid; place-items: center; }

/* 2. one element in an unknown-size parent */
.parent{ display: grid; place-items: center; }
.child{ width: fit-content; margin-inline: auto; }

/* 3. vertically AND horizontally in the viewport, which is where
      flexbox beats grid because it needs no wrapper */

  min-height: 100dvh;
  display: flex;
  align-items: center;
  justify-content: center;
}

   add flex: 1 0 auto or min-height: max-content */

.nav{
  display: flex;
  align-items: center;
  gap: 1.5rem;
}

.nav__links{ flex: 1 1 auto; display: flex; gap: 1rem; }

.spacer{ flex: 1 1 auto; }

/* and the reverse, an element pinned to the start */
.push-right{ margin-inline-start: auto; }

    The truncating row, where flexbox earns its place

    This is the layout that is genuinely hard without flexbox, because it requires a flex item to shrink below its content size while a sibling stays fixed — and that is precisely what the automatic minimum size prevents.

    .row{
  display: flex;
  align-items: center;
  gap: .75rem;
}

.row__icon{ flex: 0 0 auto; }

.row__label{

  min-inline-size: 0;              /* without this, it refuses to shrink */
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
}

.row__action{ flex: 0 0 auto; margin-inline-start: auto; }
    flex: 0 1 auto plus min-inline-size: 0 is the pair for "shrink to fit but never grow". Adding overflow: hidden or overflow-wrap: anywhere on a child achieves the same effect without reaching outside, because any overflow other than visible makes the automatic minimum size zero.

    Switching orientation without a media query

    /* a component that is a row until it runs out of room, then a column.
   Flex-wrap plus a min basis does this with no breakpoint at all. */

.cards{

  flex-wrap: wrap;
  gap: 1rem;
}

}
/* narrow: one per line.  wide: as many as fit. No media query. */

/* the same for a nav */

  flex-wrap: wrap;
  gap: .5rem 1.5rem;
}

It responds to how much room there is rather than to a device width, so it works in a sidebar, in a main column and at 400px, all without a media query. This is the strongest single argument for flexbox over a fixed breakpoint.

   align-items: stretch (the default) makes every item in a line
   as tall as the tallest, and the card's own flex column
   distributes the space inside it */
.card{

  flex-direction: column;
  gap: .5rem;

.card__body{ flex: 1 1 auto; }   /* absorbs the leftover */
.card__actions{ margin-block-start: auto; }  /* pins to the bottom */

    Equal-height cards without grid

    Flexbox gives cards equal height in a wrapped row because align-items: stretch is the default: every item in a line is made as tall as the tallest. That single default is what makes a wrapping flex row behave like a card grid, and it is why the internal layout matters.

    This chapter masters truly two-dimensional layout with CSS grid. You define tracks with the fr unit, repeat and minmax in the grid-template-columns and grid-template-rows properties, then place items by line number or named areas. The implicit grid grows automatically for unplaced items, and auto-fit with minmax builds responsive card grids that reflow with the viewport.

    Where Flexbox lays out a line, Grid lays out a plane. Define the columns and rows, then drop items into lines, areas, or let the browser auto-place them. Grid shines for page skeletons and for collections of cards that must align in both directions.

    6.1 Tracks: fr, repeat and minmax

    A grid is defined by its tracks. Track sizing is an algorithm with a defined order — intrinsic content sizes first, then flexible tracks divided into what is left — and almost every "why is my column the wrong width" question is answered by knowing which step produced the result.

    The sizing algorithm

    1. Size anything with an intrinsic size: auto, min-content, max-content, a length, or a percentage against a definite size.
    2. Distribute remaining space to flexible tracks — those sized in fr. In equal proportion.
    3. If the free space is negative, every fr track is sized to zero and the overflow is distributed to the minmax() minimums instead.
    /* step 1 gives the fixed track its width; step 2 splits the rest */
.grid{
  display: grid;
  grid-template-columns: 16rem 1fr;   /* 16rem fixed, the rest flexible */
}

/* minmax with a definite minimum keeps the track from vanishing */
.grid{
  grid-template-columns:
    minmax(0, 16rem)   /* never below 0, never above 16rem */
    minmax(20rem, 1fr) /* never below 20rem, takes the rest */
    auto;              /* sized by content */
}

/* the shorthand form of minmax(0, 1fr), which is what you almost always want */
.columns{ grid-template-columns: repeat(3, 1fr); }
/* 1fr alone means minmax(auto, 1fr), and auto as a MINIMUM
   prevents the track from ever shrinking below its content */
    This is the most consequential detail in grid. 1fr is shorthand for minmax(auto, 1fr), and that auto minimum means the track cannot shrink below the largest unbreakable thing inside it. A long URL in one cell therefore widens the whole column and the overflow step never runs. Write minmax(0, 1fr) — or repeat(auto-fit, minmax(min(20rem, 100%), 1fr)), which handles it — whenever a cell can contain anything.

    repeat, auto-fit and auto-fill

    /* a fixed number of equal columns */
grid-template-columns: repeat(4, 1fr);

/* as many as fit, at least 20rem each, never overflowing */
grid-template-columns:
  repeat(auto-fit, minmax(min(20rem, 100%), 1fr));
/* the min() is essential: without it a 20rem minimum overflows a
   15rem phone. It says "20rem, or the container if that is smaller". */

/* repeat with a pattern, which needs no track names at all */
grid-template-columns: repeat(auto-fill, minmax(12rem, 1fr));
    FunctionWhen there is more room than columnsWhen there is less
    auto-fitExisting tracks stretch to fillTracks shrink to the minimum
    auto-fillEmpty tracks are kept, so items stay narrowSame as auto-fit

    The difference only shows when the container is wider than the tracks need. auto-fit collapses the empty tracks and stretches the real ones — which is what you want for a card grid of two items on a wide screen. auto-fill keeps the empty ones, so two cards stay half-width. For most grids auto-fit is the right default.

    fr, and what it does not do

    /* fr divides the space that is LEFT after everything else */
grid-template-columns: 1fr 200px;      /* 1fr takes what remains after 200px */

/* and it is not a percentage */
grid-template-columns: 1fr 1fr;        /* two equal halves of the container */
grid-template-columns: 50% 50%;        /* also two halves, but gaps can overflow:
                                         50% + 50% + a gap is more than 100% */

/* a gap is outside the tracks, so fr math is on the container minus the gaps */
.grid{ gap: 1rem; grid-template-columns: repeat(3, 1fr); }
/* each track is (100% - 2rem) / 3 - not 100% / 3 */

/* proportional fr */
grid-template-columns: 2fr 1fr;       /* a two-to-one split */
    Percentage columns plus a gap overflow, because percentages are of the container and the gap is on top. Fr tracks are sized from what remains after the gaps, which is why 1fr 1fr behaves correctly with a gap and 50% 50% does not. This is the reason fr became the default unit the moment it existed.
    /* the responsive grid pattern, complete */
.cards{
  display: grid;
  gap: 1rem;
  grid-template-columns:
    repeat(auto-fit, minmax(min(18rem, 100%), 1fr));
}
/* one column on a phone, as many as fit above that, no breakpoints,
   no overflow, and it works inside a sidebar as well as a page */

    Grid is intrinsic sizes first, then fr for the remainder. Write minmax(0, 1fr) rather than 1fr in anything whose content you do not control, and always put min() inside auto-fit so the minimum cannot overflow a narrow container.

    6.2 Grid lines, named areas and placement

    Grid lines are numbered from 1 at the start edge, and the negative indices count back from the end — which is what makes layouts that stretch to the container's edges possible without knowing how many columns there are.

    Lines, spans and the negative indices

    .grid{
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  /* lines:  -3  -2  -1   1   2   3   4
     cols:   c1  c2  c3  c1  c2  c3  (c4 == c1) */
}

/* place by line numbers: start line, end line, and the end is EXCLUSIVE */
.header{ grid-column: 1 / -1; }   /* the whole width, whatever the count */
.sidebar{ grid-column: 1 / 3; }   /* columns 1 and 2 */
.main{ grid-column: 3 / -1; }    /* the last column only */

/* the -1 is what makes this responsive: it means "the end" */
.full-bleed{ grid-column: 1 / -1; }
    /* span is shorthand for a start line and an end line */
.grid-col-2{ grid-column: span 2; }
.grid-row-3{ grid-row: span 3; }

/* place with auto, which is where automatic placement picks up */
.card{ grid-column: auto; grid-row: auto; }

/* explicit, and then the rest auto-fill around it */
.intro{ grid-column: 1 / -1; grid-row: 1; }
.body{ grid-column: 2 / 4; grid-row: 2; }

    Named areas, and why they are worth the verbosity

    With grid-template-areas the whole layout becomes a diagram in CSS, and the placement is then named rather than counted. The cost is that every cell in the map must be filled, which is exactly the constraint that makes a layout diagram readable.

    .layout{
  display: grid;
  grid-template-columns: 16rem 1fr;
  grid-template-areas:
    "sidebar header"
    "sidebar main"
    "footer  footer";
}
.layout > *{ margin: 0; }
.sidebar{ grid-area: sidebar; }
.header{ grid-area: header; }
.main{ grid-area: main; }
.footer{ grid-area: footer; }

/* each cell must be filled or become a dot: "." means empty */
grid-template-areas:
  ".     header"
  "sidebar main"
  "footer  footer";

/* responsive, and only the changed cells need restating */
@media (min-width: 60rem){
  .layout{ grid-template-areas:
    "sidebar header"
    "sidebar main"
    "sidebar footer"; }
}
    Named areas are the only way to make a two-dimensional layout legible to the next person, and the diagram costs about the same number of characters as the line numbers do. They also make it impossible to place an item outside the map, which is a class of bug that line arithmetic allows silently.

    Spanning, and what it does to placement

    An item that spans several columns or rows changes where auto-placement resumes afterwards, and this is the part of line-based placement that produces the "there is a gap in my grid" report. The algorithm fills in order and an item that spans forces the cursor past everything it covers.

    .grid{
  display: grid;
  grid-template-columns: repeat(4, 1fr);
  grid-auto-flow: row dense;   /* dense closes the holes */
}
.featured{
  grid-column: span 2;         /* occupies two columns */
  grid-row: span 2;           /* and two rows */
}
/* without dense, auto-placed items flow around it and leave
   holes rather than backtracking to fill them */
    The cursor after a spanning item moves to the next cell that does not overlap it, not to the cell immediately after it. So a two-column span at position 1 resumes at column 4, and columns 3 and 4 of that row are skipped. dense is what recovers them, at the cost of visual reordering.

    6.3 The implicit grid and auto-placement

    Defining tracks creates an explicit grid. Anything that does not fit creates an implicit grid, whose tracks are sized automatically. This is the mechanism behind every layout that appears to work until the content grows.

    Implicit tracks, and sizing them

    /* two explicit columns, and the third item overflows into an
   implicit third column that is sized auto - narrow and content-based */
.grid{
  display: grid;
  grid-template-columns: 1fr 1fr;
}
/* item 3, 4, 5 land in auto-sized implicit columns */

.grid{ grid-auto-rows: minmax(0, auto); }        /* the default */
.grid{ grid-auto-columns: minmax(0, 1fr); }     /* implicit columns match */
/* the usual fix: make implicit tracks match explicit ones */
    Implicit tracks are the cause of "one row is a different height" and "the last column is narrower". Because they are sized by auto rather than by your fr definition, an item that spills into one gets content-based sizing and stops matching the rest. Set grid-auto-rows and grid-auto-columns explicitly whenever items can exceed your defined tracks.

   grid where the rest flow around it */

    dense reorders items relative to the DOM to fill gaps, so the visual order can differ from the reading order. On a grid of related cards that is acceptable; on anything where order means something, it is not.

    The full-bleed problem, and its solution

    A constrained column that needs one child to break out to the container's full width is the classic grid problem. The solution is a full-bleed element that uses negative margins to cancel the parent's padding — and it works because the padding, not the width, is what confines the content.

    .prose{
  max-width: 70ch;
  margin-inline: auto;
  padding-inline: 1.5rem;
}

.prose > .full-bleed{
  margin-inline: calc(50% - 50vw);
}
/* 50% of the parent's content box, minus half the viewport */

/* a full-bleed that must not cause a horizontal scrollbar */
:root{ scrollbar-gutter: stable; }
.full-bleed{
  margin-inline: calc(50% - 50vw);
  max-inline-size: 100vw;
  padding-inline: 1.5rem;      /* re-apply the prose padding inside */
}
/* and the modern, scrollbar-aware version: */
.full-bleed{
  width: 100dvw;
  margin-inline: calc(50% - 50dvw);
}
    100vw includes the scrollbar, so a full-bleed element computed from it produces roughly 15 pixels of horizontal scroll on a page with a classic scrollbar. scrollbar-gutter: stable reserves the space permanently and removes the shift; 100dvw has the same problem. Where the browser supports it, using the parent's own padding as the breakout width avoids the arithmetic entirely.

    Implicit tracks are sized auto, so define grid-auto-rows and grid-auto-columns when items can exceed your tracks. Use dense only where visual reordering is harmless, and break out of a constrained column with negative margins rather than a second wrapper.

    6.5 Named lines and subgrid

    Subgrid lets a grid item's tracks be defined by its parent's grid rather than its own. It is the answer to the problem that a card component cannot align its header, body and footer with its neighbours', which until now required either a flat DOM or duplicate markup.

    The problem subgrid solves

    <!-- WITHOUT subgrid: every card lays itself out internally, so
     the headers and footers end up at different heights -->
.cards{ display: grid; grid-template-columns: repeat(3, 1fr); gap: 1rem; }
.card{ display: grid; grid-template-rows: auto 1fr auto; gap: .5rem; }
<!-- card 1's body is short, so its footer sits high.
     card 2's body is long, so its footer sits low. -->

<!-- WITH subgrid: the parent owns the rows, and every card's
     internal rows line up across the whole row of cards -->
.cards{
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 1rem;
  /* every card spans one row of the PARENT grid, and its own rows
     are the parent's rows */
  grid-template-rows: auto 1fr auto;
}
.card{
  display: grid;
  grid-row: span 3;              /* occupy all three parent rows */
  grid-template-rows: subgrid;   /* adopt the parent's row tracks */
  gap: .5rem;
}
/* now every title is on row 1, every body on row 2, every footer
   on row 3 - across all three cards */
    subgrid requires the item to be a grid or flex item. Setting grid-template-rows: subgrid on an element that is not itself a grid item has no effect, and it fails silently — no error, just no alignment. The child must also span the parent's rows for the tracks to line up, which is why the example spans three.

    Named lines, which subgrid also inherits

    .form{
  display: grid;
  grid-template-columns:
    [label-start] 8rem [label-end input-start] 1fr [input-end];
  gap: .5rem 1rem;
}
.form > label{ grid-column: label; }    /* the named AREA shorthand */
.form > label{ grid-column: label-start / label-end; }
.form > input{ grid-column: input-start / input-end; }

/* the same names exist on EVERY row, so this aligns the third
   input with the first without counting lines */
.form > input:last-of-type{ grid-column: input-start / input-end; }

/* subgrid inherits the names too */
.form > fieldset{
  display: grid;
  grid-template-columns: subgrid;   /* same columns, same names */
}
    /* the practical case: a list where every row's second cell
   aligns, without a table */
.rows{
  display: grid;
  grid-template-columns: [key] 12rem [value] 1fr;
  column-gap: 1rem;
}
.rows > dt{ grid-column: key; }
.rows > dd{ grid-column: value; }

/* subgrid lets a nested component inherit those columns */
.rows > .group{
  grid-column: 1 / -1;
  display: grid;
  grid-template-columns: subgrid;
}
.group > dt{ grid-column: key; }   /* the names came from the parent */
    Named lines plus subgrid is the combination that removes most of the remaining reasons to use a table for layout-adjacent content. A description list where every value column lines up, with grouping that still aligns, is two declarations and no table semantics to argue about.
    /* subgrid with a breakpoint, which is where it pays most */
.cards{
  display: grid;
  grid-template-columns: 1fr;
  grid-template-rows: auto auto auto auto;
}

  grid-template-rows: subgrid;

  }

   and the DOM never changes */

}

  /* all three are required, and only the third is obvious */
  display: grid;                  /* must be a grid */

    The gaps are the detail that catches everyone. Subgrid inherits the parent's track sizes and its named lines, but not its gap. A card using subgrid without its own gap has its rows meeting at the parent's gap boundaries only, and any internal spacing has to be declared on the item. The alignment still works; the rhythm does not.

    Whether it is worth it

    /* WITHOUT subgrid: the flatten-and-reorder trick, which needs the
   DOM restructured to match the visual order, and breaks as soon as
   the visual order changes */
.cards > .card:nth-child(1) .title{ grid-row: 1; }
.cards > .card:nth-child(1) .body{ grid-row: 2; }
.cards > .card:nth-child(1) .actions{ grid-row: 3; }
.cards > .card:nth-child(2) .title{ grid-row: 4; }
.cards > .card:nth-child(2) .body{ grid-row: 5; }
.cards > .card:nth-child(2) .actions{ grid-row: 6; }
/* nine rules per card, and the order is now load-bearing */

/* WITH subgrid: two rules, and the DOM order is free */

  display: grid;
  grid-template-columns: repeat(3, 1fr);
  grid-template-rows: auto 1fr auto;
  gap: 1rem;
}
.card{ grid-row: span 3; grid-template-rows: subgrid; }
    The decision is usually straightforward. If the alignment across items matters — card headers and footers lining up, a set of forms sharing column positions — subgrid replaces structural work with two declarations. If it does not matter, the flat markup with each item laying itself out is simpler and has nothing to go wrong.

    subgrid inherits track sizes and named lines but not gaps, and the item must be a grid item that spans the parent's rows. Where alignment across a row matters it replaces a page of nth-child rules; where it does not, it is not worth the requirement.

    grid-template-rows: subgrid makes a grid item adopt its parent's row tracks, so card headers and footers line up across a row without duplicating markup. The element must be a grid item and must span the parent's rows, and subgrid inherits named lines as well as tracks.

    8.1 Mobile-first and breakpoints

    Mobile-first is not a moral position. It is a consequence of how specificity works: a base rule that applies at every width needs no override, and an override in a media query is one more rule competing for the cascade. Writing the base first means the common case is never the one paying.

    The mechanism, not the slogan

    /* DESKTOP-FIRST: every rule needs an override, and the override
   has to be as specific as the rule it replaces */
.card-grid{ display: grid; grid-template-columns: repeat(3, 1fr); }
@media (max-width: 60rem){ .card-grid{ grid-template-columns: 1fr; } }
/*                              ^ same specificity, later in the file,
                                so it wins. But only because it is later. */

/* MOBILE-FIRST: the base is the narrow case, and the enhancement
   only has to add what the wide case needs */
.card-grid{ display: grid; grid-template-columns: 1fr; gap: 1rem; }
@media (min-width: 40rem){
  .card-grid{ grid-template-columns: repeat(2, 1fr); }
}
@media (min-width: 64rem){
  .card-grid{ grid-template-columns: repeat(3, 1fr); }
}
/* no overrides, no equal-specificity races, and the base rule
   works with the media queries deleted */

    Rules at the narrow widthInside a queryAt the top level, no query
    Rules at the wide widthAt the top levelInside a query

    Breakpoints should come from where the content stops fitting, not from a list of device widths.     8.2 Media features and the range syntax

    A media query tests a feature, and the modern range syntax expresses a condition as a range rather than as two separate keywords. The range form is not only shorter — it excludes a boundary that the keyword form includes, and that off-by-one is a real source of a rule applying one pixel too early.

    The range syntax, and the boundary it fixes

    /* legacy: two features, one meaning */
@media (min-width: 40rem){ }
/* range: one expression */
@media (width >= 40rem){ }

/* the difference is at the boundary */
@media (max-width: 40rem){ }        /* matches AT 40rem too */
@media (width < 40rem){ }           /* does not */

/* so the two idioms that used to double up do not now */
@media (min-width: 40rem) and (max-width: 60rem){ }   /* 40 to 60, both ends */
@media (40rem <= width < 60rem){ }                     /* 40 to just under 60 */

/* the rule: never hide anything behind :hover alone */
.card__actions{ opacity: 0; }
.card:hover .card__actions{ opacity: 1; }
/* unreachable by keyboard, invisible on touch, and gone for
   anyone who scrolled past. Always pair. */
    Anything that appears only on :hover is unavailable to a keyboard user and to every touch user, and it is invisible to a mouse user who has scrolled. If content appears on hover it must also appear on :focus-within, and be permanently visible under (hover: none). The capability query is how you handle all three cases with three lines rather than a redesign.

    The accessibility queries, treated as requirements

    QueryWhat the reader is telling youThe required response
    prefers-reduced-motion: reduceLarge motion causes me discomfortStop animating position and scale. Opacity and colour are usually fine
    forced-colors: activeMy OS is replacing your colours with its ownStop expressing meaning in colour. Use SystemColor keywords and borders
    prefers-contrast: moreI need more contrast than you choseIncrease it. Token overrides are enough
    prefers-transparency: reduceTranslucency is hard for me to readOpaque backgrounds instead of rgba

   your carefully-chosen borders and shadows will not appear */

  .card{ border: 1px solid CanvasText; }
  .btn{ border: 2px solid ButtonText; }
  .accent-bar{ background: Highlight; forced-color-adjust: none; }

  .brand-mark{

  }
}

    prefers-reduced-motion does not mean "no animation". Vestibular triggers are large, fast, moving things — parallax, scaling, sliding. A 150ms opacity fade is usually still fine, and removing it entirely can make a state change feel abrupt rather than calm. Reduce the motion; do not delete it.

    Prefer (width >= 40rem), which excludes the boundary that the keyword form includes. Treat prefers-reduced-motion, forced-colors and prefers-contrast as requirements rather than preferences, and use (hover: none) so nothing depends on hover alone.

    Prefer (width >= 40rem) over (min-width: 40rem) — it is shorter and the boundary is exclusive.     8.3 Container queries

    A container query asks how wide this component's container is, rather than how wide the window is. That is the correct question for any component that appears in more than one place, and it is the difference between a card that works in a sidebar and one that does not.

    The declaration, and what it costs

    .panel{
  container-type: inline-size;   /* queries on the INLINE axis */
  container-name: panel;         /* optional, for named queries */
}
@container panel (min-width: 30rem){
  .panel__body{ grid-template-columns: 8rem 1fr; }
}
/* unnamed: @container (min-width: 30rem){ ... } queries the
   nearest ancestor container */

/* and the fallback: unstyled below the threshold */
.panel__body{ display: block; }
    container-typeQueries onContainsUse for
    normalNothingNothingThe default
    inline-sizeInline axis onlyInline axisAlmost always this
    sizeBoth axesBoth axesOnly when the height is already fixed
    scroll-stateScroll position—Animating on scroll
    container-type: size applies size containment on both axes, which means the element's height no longer comes from its content. Apply it to an element whose height you set explicitly, or it collapses to nothing. inline-size contains only the inline axis and leaves the block axis alone, which is why it is the right default.

    The three rules that surprise people

    RuleWhy
    A container cannot query itselfThe query looks at the element's ancestor containers. It is not its own ancestor
    A container query cannot change the container's own stylesSame reason. Wrap the component and query from a child
    Size queries cannot be used in the same query as a style queryThey are different query types and cannot be combined
    /* the wrapper pattern that resolves both of the first rules */
.card{ display: grid; }               /* the container is the OUTER */

.card__inner{
  container-type: inline-size;       /* the query target's wrapper */
}
@container (min-width: 24rem){
  .card{ grid-template-columns: 8rem 1fr; }
}
/* .card is a child of .card__inner, so the query reaches it */

/* the style query, and its values are compared as custom properties */
.group{ --layout: stacked; }
.group[data-layout="wide"]{ --layout: wide; }

@container style(--layout: wide){
  .card{ grid-template-columns: 8rem 1fr; }
}
/* the queried element must be an ancestor, and the property must
   be REGISTERED with @property for the comparison to be reliable
   in every browser */
@property --layout{
  syntax: "wide | stacked";
  inherits: true;
  initial-value: stacked;
}
    /* container query units: relative to the nearest query container */
.card{ container-type: inline-size; }
.card__title{ font-size: clamp(1rem, 7cqi, 2rem); }  /* 7% of container */
.card__body{ padding-inline: clamp(1rem, 5cqi, 3rem); }

/* cqmin, cqmax, cqh, cqb also exist */

/* the case media queries cannot handle: the same card in a
   sidebar and in a main column, on one page, at one viewport */
.sidebar .card{ container-type: inline-size; }
.main .card{ container-type: inline-size; }
/* identical markup, different internal layout, because each
   measures itself */

    The component pattern that makes them worthwhile

    <!-- a card that works in a sidebar, a main column and a modal,
     from one set of markup and no media queries -->
<article class="card">
  <img class="card__media" src="/img/panel.avif"
       width="800" height="450" alt="">
  <div class="card__body">
    <h3 class="card__title">...</h3>
    <p class="card__text">...</p>
  </div>
</article>

/* the card is the CONTAINER: it declares the query context */
.card{
  container-type: inline-size;
  container-name: card;
}

/* narrow: stacked, text only */
.card__media{ display: none; }
.card{ display: block; }

/* wide enough for a side-by-side: show the media column */
@container card (min-width: 24rem){
  .card{
    display: grid;
    grid-template-columns: 10rem 1fr;
    gap: 1rem;
    align-items: start;
  }
  .card__media{ display: block; inline-size: 100%; block-size: auto; }
}

/* wide enough for the text to be measured, so drop the measure */
@container card (min-width: 45rem){
  .card{ grid-template-columns: 14rem minmax(0, 1fr); }
  .card__body{ max-inline-size: none; }
}
    The rule that makes this pattern safe: the container is the component's own root, and every rule inside a @container block targets its descendants — never the container itself. That is not a style preference; the container cannot be affected by its own query, so a rule like @container (…) { .card { … } } inside .card silently never applies.
    /* the wrapper pattern, for the case where the container must
   itself be styled by the query */
.section{ container-type: inline-size; }

.section__inner{
  display: block;
}
@container (min-width: 40rem){
  .section__inner{ display: grid; grid-template-columns: 1fr 2fr; }
}
/* the inner is a child of the container, so it can be styled.
   Put the container-type on the same element you want to style
   and the query will not apply to it. */

/* nesting containers: the inner one wins for its own subtree */
.card{ container: card / inline-size; }
.card__quote{ container: quote / inline-size; }
/* a query inside .card__quote uses quote, not card,
   because the nearest ancestor container is the quote */

    Declare the container on the component's root and style only its descendants inside the query. Use inline-size rather than size unless the height is already fixed. Nested containers use the nearest one, so name them if the nesting is deep.

    Set container-type: inline-size on a wrapper, never on the element being queried — a container cannot query itself. Register custom properties with @property before using them in a style query, and use cqi for type that should follow the component rather than the viewport.

    8.4 Responsive images and fluid layout strategies

    Images are where a page becomes either useful or slow, and the decisions are made in markup and CSS rather than in a tool. Four properties carry most of it: intrinsic size for stability, srcset for bytes, sizes for choosing correctly, and lazy loading for when to fetch.

    The two that must be right every time

    /* dimensions: both attributes, so the box is reserved */
img{
  max-inline-size: 100%;
  block-size: auto;         /* overrides the height attribute while
                               keeping its ratio */
}
/* height:auto is what makes it responsive; the height attribute
   still supplies the aspect ratio the browser needs to reserve space */

/* never scale by one dimension only - this distorts */
img.bad{ width: 640px; }              /* height comes from the file */

/* object-fit and object-position for a fixed-ratio frame */
.thumb{
  aspect-ratio: 16 / 9;
  object-fit: cover;
  object-position: center;
  inline-size: 100%;
}
.thumb img{
  inline-size: 100%;
  block-size: 100%;
  object-fit: cover;
}
    A container with a fixed aspect-ratio and an image inside it needs both dimensions on the image plus object-fit. Without them the image overflows or the container is ignored. This is the combination behind every cropped-thumbnail layout that has to be fixed one at a time.

    srcset and sizes, and the part everyone gets wrong

    <img
  src="photo-800.jpg"
  srcset="photo-400.jpg 400w,
          photo-800.jpg 800w,
          photo-1600.jpg 1600w"
  sizes="(max-width: 40rem) 100vw,
         (max-width: 70rem) 50vw,
         700px"
  width="1600" height="900" loading="lazy" decoding="async"
  alt="A workshop bench with tools laid out in rows">

    The w suffix is a real pixel width. sizes is the space the image will occupy — evaluated before downloading, against the viewport width alone, with no knowledge of your layout. If the image sits in a two-column grid that is 60% of the viewport, sizes must say 60vw. Getting it wrong breaks nothing visibly; it just makes the browser pick the wrong file.

    /* a full-bleed hero: 100vw, and no gap for the scrollbar
   matters because there is no padding */
.hero img{ sizes: 100vw; }

/* an image in a sidebar on one side and a main column on the
   other: a media query, because sizes is viewport-only */
sizes="(max-width: 60rem) 100vw, 400px"

/* CSS has no srcset equivalent, but the pattern is the same:
   let the browser choose */
.card-grid img{
  inline-size: 100%;
  block-size: auto;
  loading: lazy;
}
/* with srcset on the img, which CSS cannot supply */
    Always keep a plain src alongside srcset. It is the fallback for anything that ignores srcset, and it is what gets requested by clients sending no Accept header at all.

    picture, for format rather than size

    <picture>
  <source type="image/avif" srcset="hero.avif">
  <source type="image/webp" srcset="hero.webp">
  <img src="hero.jpg" width="1600" height="700"
       alt="The workshop at dawn, benches in rows">
</picture>

/* each source can carry its own srcset and sizes */
<source type="image/avif"
        srcset="hero-800.avif 800w, hero-1600.avif 1600w"
        sizes="(max-width: 40rem) 100vw, 800px">

/* and a different crop per width */
<source media="(min-width: 60rem)" srcset="hero-wide.avif">

/* the img is mandatory and is the fallback for every browser
   that matches no source, so it must be a safe format */
    Inside picture the first matching source wins, so order from most specific to the catch-all img. That is the opposite of srcset, where the browser picks the best candidate. Putting a generic source first makes every condition below it unreachable and fails silently.
    /* loading: never lazy-load the largest contentful element */
img.hero{ fetchpriority: high; loading: eager; }
/* everything else */
img{ loading: lazy; decoding: async; }

/* a background-image in CSS has no srcset, so it is fetched at one
   size. Use an image-set() when it must be responsive: */
.hero{
  background-image: image-set(
    url(hero.avif) type("image/avif"),
    url(hero.webp) type("image/webp"),
    url(hero.jpg)  type("image/jpeg"));
}

/* and never lazy-load a print stylesheet's background */
@media print{
  *{ background-image: none !important; }
}

    Both width and height plus block-size: auto in CSS, and that combination is what prevents layout shift. sizes must describe your actual layout in viewport units because it is evaluated before download. picture takes the first match; srcset takes the best.

    This chapter covers transitions with their timing functions, 2D and 3D transforms, and keyframe animations, along with the performance discipline that keeps motion smooth. Transitions interpolate between property states on hover or class changes, transforms move and scale without reflow, and keyframes drive repeated animation. The chapter closes with rules for animating only cheap properties.

    Motion guides attention: a button that responds, a card that lifts, a toast that fades in. CSS gives you three layers — transitions for property changes, transforms for geometry, animations for full choreography. This chapter teaches all three plus when to leave them alone.

    9.1 Transitions and timing functions

    A transition interpolates between two computed values of a property over a duration. It needs three things — a property, a duration and a change of state — and it only runs when the value changes as a result of something other than the transition itself.

    The four properties, and which is which

    PropertySetsNotes
    transition-propertyWhich propertiesDefaults to all, which is usually wrong
    transition-durationHow longDefaults to 0s, so nothing happens without it
    transition-timing-functionThe curve between the valuesDefaults to ease
    transition-delayWait before startingThe only way to stagger a list
    .btn{
  background: var(--surface);
  transition: background-color .18s ease-out,
              border-color .18s ease-out,
              color .18s ease-out,
              transform .18s ease-out;
  /* named properties, not all - all will transition properties
     you did not intend, including ones a future engine adds */
}
.btn:hover{ background: var(--brand); transform: translateY(-1px); }
.btn:active{ transform: translateY(0) scale(.98); }
.btn:focus-visible{ outline: 2px solid var(--accent); }
/* set every transition on the BASE state, never on :hover.
   A transition only exists if the element already had it when
   the value changed. */
    Setting the transition on the hover state rather than the base is the most common reason a transition "does nothing" or "jumps". The transition must be present on the element before the value changes, because it describes how to get to the new value — and it must be present in the state it was in when the change happened, which for a hover in is the base state.

    Timing functions

    FunctionShapeFeels like
    easeDefault cubic bezierEverything. The unremarkable choice
    linearConstant rateSpinners, progress, anything continuous
    ease-inSlow startSomething accelerating away
    ease-outSlow finishSomething arriving. Usually what you want for a UI
    ease-in-outSlow both endsSomething leaving and arriving
    cubic-bezier(.2, .8, .2, 1)CustomA quick, confident response
    steps(n)Discrete jumpsSprites, typewriter effects
    linear()A sampled springReal physical motion, no overshoot to tune

   immediately and settles, which reads as responsive */

   for a small element. Big things can take longer. */

/* staggering a list, with no extra classes */

   nothing - which is why display: none cannot be transitioned
   and why height: auto needs @starting-style or a JS shim */

    What actually starts a transition

    A transition runs when a property's computed value changes between two styles, and nothing else. There are three ways that happens, and the third is the one people forget.

    TriggerExampleNotes
    A pseudo-class:hover, :focus-visible, :checkedThe most common
    A class or attribute change.is-open, [aria-expanded="true"]The right choice for anything a script controls
    A change of custom property:root{ --brand: red } with var(--brand) in a propertyWorks for ordinary properties, because substitution happens before computation
    Not a triggerThe element being added to the DOMIt appears already at its final value. This is what @starting-style is for
    Not a triggerA resize, if the value is identicalNo value change, no transition

   already "arrived", so there is nothing to transition from */

   the list order is irrelevant, only the duration differs */

    A transition fires on a computed-value change and on nothing else — including not on an element being inserted into the DOM, which is what @starting-style exists to solve.     UseBecause
    TransitionThe change comes from a state change — a hover, a class, an attribute. The browser knows both ends and interpolates
    KeyframesThe motion is the point, not a response to anything. It runs, repeats, or is driven by a scroll timeline

    9.2 Transforms: translate, scale, rotate and 3D

    Transforms change the visual representation of an element without affecting layout. Nothing else on the page moves, nothing reflows, and nothing is recalculated — which is why a transform is cheap and an animated top is not.

    The 2D functions

    FunctionDoesOrder matters?
    translate(x, y)Moves. Accepts lengths and percentagesYes
    scale(x, y)Scales. One value means both axesYes
    rotate(angle)Rotates, clockwise, around the centre by defaultYes
    skew(x, y)Slants. Rarely what you wantYes
    matrix(a,b,c,d,e,f)All of the above at once—

.a{ transform: translateX(1rem) rotate(45deg); }
/* with the longhands, which are individually animatable and
   do NOT combine - each is a separate property */
.b{
  translate: 1rem 0;
  rotate: 45deg;
  scale: 1 1;
}
/* the longhands are composited in a FIXED order:
   translate, then rotate, then scale - regardless of the order
   you write them in. The shorthands apply in the order written. */

    centerThe middleThe default

   animating box-shadow is also on the compositor in most engines
   only when it is a shadow on a composited layer */

    3D, and perspective

    /* perspective on the PARENT, rotateX on the child.
   Perspective does not inherit, which is why it goes on the
   wrapper rather than on the element being tilted. */

  transition: transform .3s ease-out;

    The individual properties, in detail

    PropertyEquivalent shorthandAnimatable

    rotatetransform: rotate()Yes, including 3-axis with three values
    scaletransform: scale()Yes

   translate, then rotate, then scale. Writing them in a
   different order in CSS has no effect. */

.cube{ rotate: 30deg 40deg 0deg; }

   hover scale of 1.05 and a -5% translate stay proportional */
.card:hover{ scale: 1.05; translate: 0 -5%; }

   rather than by coordinates, and it needs no JS */

    9.3 Keyframes and animation properties

    A keyframe animation moves through a set of keyframes on its own timeline, without needing a state to change. Beyond that it is the same idea as a transition, and the shorthand has enough options that most of them are never needed.

    Writing and attaching

    /* declare, then attach */
@keyframes slide-in{
  from{ translate: 0 0; opacity: 0; }
  to  { translate: 0 -1rem; opacity: 1; }
}
.panel{ animation: slide-in .25s ease-out both; }

/* the shorthand, in order:
   name | duration | timing-function | delay | iteration-count

    11.1 Cascade layers as architecture

    Cascade layers, used as an architecture rather than as a trick, are the answer to a problem specificity cannot solve well: making an override win without making it heavier. A layer orders whole groups of rules, so "this should beat that" is decided once in a list rather than four hundred times in selectors.

    Layering a whole stylesheet

    /* one statement, first thing in the whole build, and the
   entire ordering decision for the project */
@layer reset, tokens, base, layout, components, utilities;

/* reset - lowest. Normalises what the browser did, and nothing else */
@layer reset{
  *, *::before, *::after{ box-sizing: border-box; }
  body{ margin: 0; }
  h1, h2, h3, h4, p, ul, ol{ margin: 0; }
  img{ max-inline-size: 100%; block-size: auto; display: block; }
}

/* tokens - the custom properties. No rules, only declarations */
@layer tokens{
  :root{
    --brand: oklch(0.78 0.15 205);
    --text: oklch(0.22 0.06 258);
  }
}

/* base - element defaults and typographic scale */
@layer base{
  body{ font: 1rem/1.6 var(--font-sans); color: var(--text); }
}

/* layout - page structure: grid, containers, regions */
@layer layout{
  .shell{ inline-size: min(100% - 2rem, 72rem); margin-inline: auto; }
}

/* components - reusable pieces. These may set any weight they like,
   because nothing inside this layer competes with them */
@layer components{
  .btn{ background: var(--brand); padding: .5rem 1rem; }
}

/* utilities - last, and deliberately able to beat anything */
@layer utilities{
  .u-hidden{ display: none; }
  .u-mt-4{ margin-block-start: 1rem; }
}

    The duplication that layers let you delete

  .btn{ background: var(--brand); padding: .5rem 1rem; }
  .card{ border: 1px solid var(--border); padding: 1rem; }

    11.3 Nesting and the modern functions

    Native nesting removes the need for a preprocessor, or at least the need for the nesting part of one. It is already what most preprocessors did, with two differences that matter: the nesting selector is optional, and there is a specificity change that catches everyone once.

    Nesting, and the & rules

    /* native nesting, no preprocessor */
.card{
  padding: 1rem;

  & .title{ font-size: 1.25rem; }        /* the & is the nesting
                                               selector and is OPTIONAL */
  .title{ font-size: 1.25rem; }             /* same thing */
  > .media{ inline-size: 8rem; }          /* > behaves as expected */
  + .card{ margin-block-start: 1rem; }      /* so do the combinators */
  .card & .title{ }                      /* & works mid-selector */
}

/* compiled equivalent:
   .card .title { }
   .card > .media { }
   .card + .card { }
   .card .card .title { }          <- note: this compounds */

/* nesting a nesting */
.card{
  & .title{
    font-size: 1.25rem;
    & em{ font-style: normal; }          /* .card .title em */
  }
}
    Nesting is desugared, and the specificity of the resulting selector is that of the largest selector in the whole nested chain — not of the innermost one. So .card{ & .title{ } } gives .card .title a specificity of (0,0,1,1), not (0,0,1,0). Nest deeply and specificity grows at every level, which is the opposite of what most preprocessors do and the opposite of what the syntax suggests.

el.scrollIntoView({ behavior: "smooth" });
/* so prefer it for anchors, and use scrollIntoView only when you
   genuinely need the element, with the matchMedia guard */

    What to use where, and the fallback

    FeatureSinceFallback needed?
    Logical propertiesBroad for yearsNo. The physical names remain valid and equivalent in LTR
    accent-colorBroadNo — it is an enhancement; the control just uses the platform default
    scroll-snap-typeBroadNo — without it the container simply scrolls freely
    scroll-behavior: smoothBroadNo — falls back to an instant jump, which is what most readers prefer
    field-sizing: contentNewerYes, if a textarea must size itself — feature-detect
    Anchor positioning (position-area)NewerYes. Feature-detect and fall back to a fixed position
    /* logical properties: safe to write today, because in a
   horizontal LTR document they are the same as the physical
   names. The upside only appears in a translated or RTL one. */
.card{
  margin-block-end: 1rem;            /* not margin-bottom */
  padding-inline-start: 1rem;        /* not padding-left */
  inset-inline-start: 0;             /* not left */
  text-align: start;                 /* not left */
  float: inline-start;               /* not left */
}

/* accent-color: one declaration, every native control */
:root{
  color-scheme: light dark;
  accent-color: var(--accent);
}
/* no image, no JavaScript, and it follows the platform's own
   hover and focus rendering in each theme */

/* field-sizing, feature-detected, with a JS shim as the fallback */
textarea{
  field-sizing: content;
  min-block-size: 3lh;
  max-block-size: 30lh;
}
@supports not (field-sizing: content){
  /* a tiny observer, or accept the fixed rows attribute */
  textarea{ resize: vertical; }
}

/* anchor positioning, the first layout primitive driven by the DOM */
.popover{
  position-anchor: --trigger;
  position-area: block-end span-inline-end;
  margin-block-start: .25rem;
}
@supports not (position-area: block-end){
  .popover{ inset-block-start: anchor(--trigger block-end); }
}
    Logical properties cost nothing and are already the better default: in a horizontal left-to-right document margin-block-end and margin-bottom are the same declaration, and the moment a reader's page is translated or dir is set to rtl, only one of them still means what you meant. There is no compatibility reason to write the physical names for anything except width, height and the top/left pairs where the logical form is genuinely awkward.

    Logical properties are already safe to write everywhere — they are identical to the physical names in horizontal LTR and correct everywhere else. accent-color themes every native control in one declaration. Scroll snap needs scroll-snap-align on the children, and mandatory is wrong where content heights vary.

    Use logical properties throughout so a component mirrors from the document's dir with no second rule. accent-color themes every native form control in one declaration. Scroll snap needs scroll-snap-align on the children, and mandatory is wrong anywhere content heights vary.

    11.5 Architecture: reset, naming and files

    CSS architecture is three questions: what resets, what is named, and what is imported. Cascade layers now answer the ordering question better than any preprocessor did, so the file structure can be simple and the naming can be decided on other grounds.

    The reset, and how much of one you need

    /* the modern minimum, in the reset layer */
@layer reset{
  *, *::before, *::after{ box-sizing: border-box; }

  *{ margin: 0; }                       /* removes every default margin */

  html{ -webkit-text-size-adjust: 100%; }

  body{
    min-block-size: 100dvh;
    line-height: 1.6;
    -webkit-font-smoothing: antialiased;
  }

  img, picture, video, canvas, svg{
    display: block;
    max-inline-size: 100%;
  }

  input, button, textarea, select{ font: inherit; color: inherit; }
  /* controls do NOT inherit font by default, which is why every
     form looks different from every other site */

  p, h1, h2, h3, h4, h5, h6{ overflow-wrap: break-word; }
  h1, h2, h3, h4{ text-wrap: balance; }
  p{ text-wrap: pretty; }

  /* and only these: */
  ul[role="list"], ol[role="list"]{ list-style: none; padding: 0; }
  /* because a list-style: none removes the list semantics in Safari
     VoiceOver, and role="list" restores them */
}
    list-style: none on a ul removes its list semantics in Safari's VoiceOver — the reader stops announcing "list, 5 items". Adding role="list" restores it. It is the one place where a purely visual change alters what is announced, and it is why the rule above is written as an attribute selector rather than a blanket reset.

    Naming, and what the block-class argument actually is

    PatternShapeCost
    Block-element — .card__titleNests under a blockRequires one class per element. Two elements cannot share a name
    BEM — .card__title--lgAdds modifiersLong, verbose, easy to get subtly wrong
    Utility — .u-mt-4Single purposeMany classes per element; needs layers to stay safe
    Component + descendant.card .titleLeaks into nested components of the same name
    Component + element, no block.card-titleNo nesting semantics. Simple, flat
    Container queries—Removes most of the need to scope by name
    /* with container queries and layers, the argument is mostly gone:
   components cannot reach each other, so names need only be unique */

@layer components{
  .card{ display: flex; flex-direction: column; container-type: inline-size; }
  .card__title{ font-size: var(--text-lg); }
  .card__title--lg{ font-size: var(--text-2xl); }
  .card__body{ flex: 1; }

  /* a DIFFERENT component with its own .card__title- is a
     different class, and they cannot collide because the layer
     and the container boundary keep them apart */
  .panel__title{ font-size: var(--text-md); }
}

@layer utilities{
  .u-mt-4{ margin-block-start: var(--space-4); }
  .card{ padding: 1rem; }
  /* beats every component, no !important, no id, no doubled class */
    Container queries remove the reason BEM had for being strict: once a component cannot see its neighbours' internals, a name only needs to be unique within that component. Two components can both have a __title with no relationship between them, which is the case BEM's two-part naming was designed to prevent and no longer needs preventing.

    Files, and what a build needs at all

    /* assets/
   tokens.css      @layer tokens { :root { ... } }
   reset.css       @layer reset  { ... }
   base.css        @layer base   { ... }
   layout.css      @layer layout { ... }
   components.css  @layer components { ... }
   utilities.css   @layer utilities { ... }        */

/* one file that establishes the order, loaded first */
@layer reset, tokens, base, layout, components, utilities;
@import url("assets/reset.css")       layer(reset);
@import url("assets/tokens.css")      layer(tokens);
@import url("assets/base.css")        layer(base);
@import url("assets/layout.css")      layer(layout);
@import url("assets/components.css")  layer(components);
@import url("assets/utilities.css")   layer(utilities);
    @import blocks rendering: the browser must fetch and parse each sheet before continuing, and a chain of them is serialised. Use @import … layer() only in a single entry file during development, and a <link> per file in production so they fetch in parallel. The layer names mean the load order of the links no longer matters — which is exactly what makes that safe.
    /* production: parallel links, order irrelevant because of layers */
<link rel="stylesheet" href="/assets/utilities.css">
<link rel="stylesheet" href="/assets/components.css">
<link rel="stylesheet" href="/assets/layout.css">
<link rel="stylesheet" href="/assets/base.css">
<link rel="stylesheet" href="/assets/tokens.css">
<link rel="stylesheet" href="/assets/reset.css">
/* links in any order, and the layer statement in one of them
   decides the cascade. This is the payoff of layers: file order
   stops being load-bearing. */

    Order with a layer statement and file order stops mattering. Reset the things that actually need resetting — including font: inherit on controls — and add role="list" where you remove list markers. Container queries plus layers mean naming needs uniqueness within a component, not a strict two-part convention.

    A.4 Glossary

    This glossary defines the terms used across the guide in one alphabetical list. If a word confused you in a chapter, you will find a plain definition here, from cascade and specificity to custom properties and subgrid. Keep it open next to you while you read so no term slows you down.

    • Cascade — the process that merges all stylesheets and picks the winning rule.
    • Specificity — the (ids, classes, elements) score that breaks ties inside a layer.
    • Inheritance — properties flowing from a parent to its descendants.
    • Origin — where a style came from: user-agent, user, or author.
    • @layer — a named bucket of styles compared before specificity.
    • Box model — content, padding, border and margin around every element.
    • Containing block — the box that sizing percentages and absolute offsets are relative to.
    • Stacking context — the isolated z-order world created by position, transform, filter and more.
    • Flex item — a direct child of a flex container, laid out along the main axis.
    • Grid track — a column or row between two grid lines.
    • Implicit grid — the extra tracks the browser creates beyond your declared ones.
    • Media query — a rule applied only when a device feature (width, color scheme, motion) matches.
    • Container query — like a media query, but sized against a component rather than the viewport.
    • Custom property — a user-defined token read with var().
    • clamp() — fluid sizing between a minimum, a preferred value and a maximum.
