Microservices are a deployment topology, not a virtue. This chapter places the monolith, the modular monolith and the distributed system on one spectrum, explains the scale cube that most "split the service" advice is really about, and sets out the cases where distributing a system makes it measurably worse.

0.1 The architecture spectrum

Monolith, modular monolith and microservices differ in kind, not degree: the first two are separated by discipline, the third by a network.

Three shapes, one continuum

A monolith is a single deployable artifact containing all of the system's behaviour: one process, one release cadence, one database schema. A modular monolith is the same single deployable, but with internal boundaries enforced by the build rather than by convention: modules own their own tables, communicate through explicit interfaces, and a static-analysis rule fails the build when one module reaches into another's internals. Microservices keep those same boundaries but insert a network between them, so each boundary becomes a process with its own pipeline, its own datastore and its own failure mode.

The key observation is that the first two differ only in discipline, while the third differs in kind. Moving from a monolith to a modular monolith is refactoring, done entirely inside a compiler and a test suite. Moving from a modular monolith to microservices is distribution, which replaces in-process function calls with network calls that can time out, arrive twice, arrive out of order, or not arrive at all. Nearly everything difficult about microservices follows from that one substitution, and teams that skip the modular stage tend to discover the costs without ever having enjoyed the benefit of enforced boundaries.

What actually changes when you split

Inside a process, a call either returns or throws; partial failure does not exist, and a rollback is a rollback of the whole unit of work. Across the network, a call can succeed on the server and fail on the response path, so the caller genuinely cannot tell whether the work happened. Latency stops being measured in nanoseconds and starts at single-digit milliseconds per hop. Transactions stop spanning the boundary, so consistency has to be re-established with sagas, outbox tables and reconciliation jobs. Versioning becomes permanent, because producer and consumer can no longer be deployed together. Memory becomes per-service, so caching that used to be a hash map is now a distributed cache with its own failure modes.

None of this is an argument against distribution. It is a list of costs that must be paid deliberately, with an owner and a budget, rather than discovered during an incident. A modular monolith lets you defer payment on all of them while still building the domain model and the seams you would later split along, which is why it is the recommended starting point for almost every new system.

Choosing on evidence, not fashion

The decision that matters is never "monolith or microservices" in the abstract. It is "which subsystem has a requirement the rest of the system does not have" — an independent release cadence, an independent scaling profile, an independent compliance boundary, or an independent failure domain. A payments path that must scale on its own and be audited separately justifies a separate deployable; a settings screen does not. Record the forces you observed in an architecture decision record, because the same question will be reopened in eighteen months and the recorded context is the only thing that prevents it being re-litigated from scratch by people who never saw the original constraints.

0.2 The scale cube

Most "we need microservices" pressure is actually pressure to scale, and scaling has three independent axes. Only one of them is microservices.

Three axes, not one decision

The scale cube describes three orthogonal ways to make a system handle more work. The X axis is horizontal duplication: run N identical copies of the whole application behind a load balancer. It is cheap, requires no code change, and is limited only by whether instances share state — sessions in memory or a local cache break it immediately. The Y axis is functional decomposition: split the application by what it does, so each function becomes a separately deployable, separately scalable unit. This is the microservice axis, and it is the only one that changes the code's shape and the org's shape. The Z axis is data partitioning: keep the code the same but split the data, so tenant A's requests always go to shard 1. It scales writes and dataset size, at the cost of cross-shard queries and rebalancing.

AxisWhat changesSolvesCosts
X — cloneInstance countThroughput, redundancyRequires statelessness; shared DB remains a bottleneck
Y — decomposeCode and team boundariesIndependent deploy, independent scaling, failure isolationNetwork failure modes, eventual consistency, platform effort
Z — partitionData placementDataset size, write throughput, tenant isolationCross-shard joins, rebalancing, hot shards

Choosing an axis

Diagnose first. If one endpoint saturates while the rest of the system is idle, that is a Y-axis problem: the hot function needs to scale and deploy independently. If every endpoint saturates together, that is usually an X-axis problem — add replicas and remove the shared state that prevents it. If the database is the bottleneck, or the dataset no longer fits comfortably on one primary, that is a Z-axis problem, and decomposing the application will not help because all the new services still hammer the same primary.

The order matters because the costs escalate. X is a deployment change. Z is a data-model change plus an operational discipline for rebalancing. Y is a redesign of the code, the data ownership, the release process, the testing strategy and the on-call structure simultaneously. Teams routinely reach for Y when X or Z would have been sufficient, and then spend two years paying for a decomposition that solved nothing the load balancer could not.

Why the Y axis costs the most

Decomposition is the only axis that converts a local function call into a network call, and every consequence in this guide follows from that: partial failure, eventual consistency, idempotency, contract versioning, distributed tracing, service discovery, mTLS. It also breaks the assumption that a deploy is atomic, which means every change now needs a rollout plan and a rollback plan rather than a single revert. A team that cannot yet practise trunk-based development with a fast pipeline gains nothing from per-service deploys, because the per-service pipeline is only valuable when it is genuinely independent.

0.3 When not to use microservices

The honest answer for most teams in their first three years: build a modular monolith, enforce the boundaries, and split only when a specific, named force demands it.

Signals that you should not split yet

Do not decompose when the domain model is still in flux, because the service boundaries you draw will be wrong and moving a boundary after it has its own database, its own repository and its own release cadence is an order of magnitude harder than moving a package. Do not decompose when a single team owns the whole system: the main benefit of microservices is independent deployment by independent teams, and with one team you pay all the costs and collect none of the benefit. Do not decompose when the workload is uniformly low and there is no per-function scaling need. Do not decompose a reporting-heavy system whose value comes from joining data across the whole domain, because that join survives decomposition only as a data pipeline you now have to build and operate.

Also do not decompose as a substitute for fixing what is actually broken. Slow delivery is usually caused by a missing pipeline, manual QA gates and a release process requiring three approvals — not by the code being in one repository. Instability is usually caused by missing observability and no SLO, not by the process boundary. Solve the real bottleneck; a distributed version of a broken delivery process is slower and harder to debug.

The hidden tax: platform capability

Microservices are cheap to draw and expensive to run, and the expense is concentrated in platform capability that a monolith does not need. Before the first split, the following should already exist and be boring, because building them concurrently with an active decomposition is how migrations stall.

A defensible default

For a new system in 2026, the defensible default is a modular monolith deployed as a handful of horizontally scaled replicas, with modules that own their tables and communicate through published interfaces; one pipeline; one database with clearly separated schemas; and a written list of the forces that would justify extraction. Extract a module into a service when one of those forces actually arrives — a scaling profile nobody else shares, a compliance boundary, a team that needs its own release cadence, or a failure domain that must be isolated — and extract it one at a time, with the seam already enforced.

If you cannot articulate, in one sentence, the force that requires a separate deployable, you are not ready to split. "It is more modern" is not a force; "pricing must deploy daily while catalog deploys monthly, and they are owned by different teams" is.

0.4 What distribution actually costs

A realistic bill of materials: the recurring operational and cognitive costs of running N services, and the organisational preconditions that decide whether independent deployment is real or nominal.

Recurring operational costs

The first cost is multiplicity. Each service carries its own pipeline, its own dashboards, its own alerts, its own dependency tree, its own base image and its own runbook. Patching a base image vulnerability that appears in every service becomes N pull requests, N pipelines and N deploys — teams that ran this once report it taking days, and the realistic target is to automate it or accept that some services stay behind. The second cost is the platform itself: an event broker, a tracing collector, a service registry or mesh, a secret store, a container registry and a schema registry are all things a monolith does not run, and each one is a system with its own upgrade path, capacity limits and failure modes.

The third cost is latency and ambiguity. Every synchronous hop adds milliseconds to the critical path, and every cross-service write introduces a window in which the system is in a legitimate intermediate state. That window is where support tickets come from: "I paid and the order is missing" is usually eventual consistency with a UI that does not admit it. Designing for those states — showing "processing", polling, or returning a pending resource rather than a 404 — is work that no diagram shows.

Cognitive and organisational preconditions

Conway's law is not a suggestion: the system will mirror the communication structure of the teams that build it. If one team owns five services, they will be deployed together and become a distributed monolith with extra latency. Independent deployment requires a stream-aligned team per service or per small group of services, with a platform team providing the paved road and enabling teams helping others adopt it. A service without a single owning team drifts: nobody owns its alerts, its upgrades stall, and its interface is changed by whoever needs it changed.

The second precondition is local knowledge. Debugging a distributed request means reading a trace spanning four services, none of which the engineer wrote. That is only tractable if tracing, correlation IDs and structured logs are standard from the beginning, so the debugging skill and the tooling arrive together. Attempting distribution first and observability later reliably produces long incidents, because the data required to diagnose them was never emitted.

1.1 Domain-driven design and bounded contexts

A bounded context is the largest boundary inside which one model and one vocabulary are consistently true — the tool that turns "we disagree about what a customer is" into an explicit, ownable seam.

Ubiquitous language and where it stops applying

The word "customer" means a billing entity with a credit limit to Finance, a contact with ticket history to Support, and an authentication principal with credentials to Identity. None of those models is wrong; they are each correct inside their own context. A bounded context makes that explicit rather than collapsing all three into one bloated Customer table that every team edits and no team owns, which is where the classic failures come from: a column added for billing that breaks reporting, a nullable field that three teams interpret differently, a status enum whose values have drifted.

The practical test for a boundary is linguistic. If two areas assign incompatible meanings to the same word, or the word has to be qualified every time it is spoken ("billing customer" versus "auth customer"), they are separate contexts and are candidates for separate services. If they share a single meaning with a single source of truth, splitting them buys you latency and a distributed transaction and nothing else. Domain experts settle this question faster than architects do, because they feel the ambiguity in conversation long before it appears in a schema.

Contexts are not services

A bounded context is a modelling boundary; a service is a deployment boundary. Treating them as one-to-one is a common and expensive mistake made at the point of maximum ignorance, because the model is least understood exactly when the architectural commitments are largest. A first cut that gives three related contexts one deployable with enforced internal modules keeps the option to split later; a first cut that gives them three services commits to network protocols, idempotency and versioning before anyone knows what the query patterns are.

What should be one-to-one is context to ownership. A context sized so that exactly one team owns it end to end — its schema, its API, its on-call rotation, its roadmap — is a context that can evolve. Two teams editing one context's tables is the organisational defect that later surfaces as constant merge conflicts and as "independent" services that always get deployed together.

Core, supporting and generic subdomains

Not every part of the domain deserves the same investment. A core subdomain is where the business actually competes — pricing, matching, risk scoring, routing — and it deserves bespoke code owned in-house by the strongest engineers. Supporting subdomains are necessary but not differentiating; they can be built cheaply, modelled loosely, and changed without ceremony. Generic subdomains — identity, email delivery, payment rails, search, notifications — should be bought, rented or adopted as off-the-shelf products rather than written.

Applying microservice discipline evenly across all three is how teams end up with a beautifully decomposed system that contains no competitive advantage, having spent their best people on an authorisation service they could have purchased. Classify first, then allocate effort: core gets custom services and custom models, generic gets a managed product behind a thin adapter that you control so the vendor can be replaced.

1.2 Decomposition by business capability

Capabilities answer "what does the business do", which is a more stable boundary than "what data does it hold" — and far more stable than the technical layers most systems are first split along.

Capability versus technical layer

Decomposing by technical layer produces a service that owns "all database access", another that owns "all business logic" and another that owns "the API". Every user action then traverses all three, so the system is chatty by construction, every feature touches every service, and no single team can ship anything alone. This is the shape that earns distributed systems their bad reputation, and it happens whenever the split follows the stack rather than the domain.

A business capability is something the organisation does to create value: take payment, reserve stock, dispatch a parcel, price a basket, assess risk. Capabilities are comparatively stable — pricing rules change constantly inside the pricing capability, but the capability itself has existed for decades. That stability is exactly what a boundary needs, because a boundary drawn along a stable capability absorbs change internally instead of propagating it across the network to every consumer.

Deriving the capability map

Start from the revenue path and the org chart, then refine. Ask what has to happen for money to come in and for the promise to be kept, and list the verbs: quote, accept, reserve, authorise, fulfil, invoice, refund, reconcile. Each verb that has its own rules, its own data and (ideally) its own team is a capability candidate. Then check each candidate against the org: if two capabilities are staffed by one team working in one backlog, they will be released together and are candidates for one deployable with enforced modules.

The map is a living document, not a pre-commitment to services. Write it as a table of capability, owning team, key data, input events and output events. That table then answers the boundary questions for you: two capabilities that share a table need either a shared-kernel decision or a split of the table, and both are cheaper to decide on paper than in production.

# capabilities.yaml - one row per capability, reviewed with the domain experts
capabilities:
  pricing:
    owner: payments-team
    outcome: "a price for a basket, including promotions and tax"
    owns_data: [price_list, promotion, tax_rule]
    consumes: [basket.updated, promotion.activated]
    publishes: [price.calculated]

  checkout:
    owner: shopping-team
    outcome: "a confirmed order with a captured payment"
    owns_data: [order, order_line, payment_intent]
    consumes: [price.calculated, stock.reserved]
    publishes: [order.placed, order.cancelled]

  fulfilment:
    owner: logistics-team
    outcome: "goods handed to a carrier and visible to the customer"
    owns_data: [shipment, parcel, tracking_event]
    consumes: [order.placed]
    publishes: [shipment.dispatched, shipment.delivered]

Capability services, not entity services

The most common decomposition mistake is the entity service: a CustomerService, a ProductService, an OrderService that are each a thin CRUD wrapper over one table. They share nothing conceptually but end up sharing a database because callers need joins, and their interfaces become "get me all the fields of the row". Every consumer then depends on every field, so the schema can never change, and each service is owned by nobody.

The alternative is to make each service responsible for a capability and to expose intent-level operations: reserveStock(sku, qty, holdId) rather than updateInventoryRow, authorisePayment(intent, amount) rather than insertPayment. Intent-level interfaces are stable while the storage behind them is free to change, they make authorisation rules enforceable at the boundary, and they give the service a reason to exist beyond ownership of a table.

// Weak: an entity service whose interface mirrors its table
POST /customers/{id}       // body = the row
PUT  /customers/{id}       // whole-row replace
GET  /customers/{id}/orders?expand=lines,payments

// Stronger: a capability service whose interface mirrors intent
POST /checkout/sessions/{sid}/price      -> PriceBreakdown
POST /reservations                        -> ReservationId   (hold stock, expires)
POST /payments/authorisations             -> AuthId           (idempotent by key)

1.3 Event storming and context mapping

Event storming is the cheapest way to discover boundaries because it extracts the domain's own timeline from the people who run it, and context mapping then turns that timeline into interfaces between teams.

The timeline and its stickies

A storm is run with the people who operate the business — not only engineers — and a wall (or a large shared board) on which coloured notes are placed in time order. Orange notes are domain events, written in the past tense: OrderPlaced, PaymentAuthorised, StockReserved, ShipmentDispatched. Blue notes are commands: the intent that precedes an event (PlaceOrder, AuthorisePayment). Yellow notes are actors, purple notes are policies (the rules that say "when this event happens, that command follows"), and pale notes are read models — the data someone needs in order to issue a command.

The exercise starts deliberately chaotic: everyone writes every event they can think of, without order, duplicates welcome. Only then is the timeline arranged, and only then are policies and read models added. The order matters because a room told to "draw the process" produces the official process; a room free-associating events produces the real one, including the exceptions, the reversals and the manual workarounds that the official diagram omits.

From storm to context map

The boundaries fall out of the timeline at pivots: events that mark a genuine change of actor, of vocabulary or of pace. Where the same event name means subtly different things on either side, the language has changed, so a bounded context boundary belongs there. Where a policy fires across a long gap — "three days after OrderPlaced, if no ShipmentDispatched, raise a chase" — there is usually a separate context, because the participants, the timing and the data are all different from the checkout flow.

Once contexts are drawn, record how each pair relates. Those relationships are not neutral: a downstream context that must conform to an upstream model is permanently constrained by it, and the choice between conforming and translating is a cost decision that should be explicit.

Remote and follow-up sessions

Distributed storms work when the board is a shared canvas with strict notation and one facilitator, and when the session is short — ninety minutes with a specific slice of the domain, not a two-day attempt to model the company. The artefact that matters is not the wall; it is the structured list of events, pivots, hotspots and open questions, committed to the repository next to the code. A storm whose output was only a photograph is a meeting, not a model.

Follow up within a week by walking the hotspots with the people who raised them, because the questions found in a storm are the specification work that would otherwise be done as bugs. The most valuable output is usually the list of places where two parts of the business disagree about a word, since each of those is a boundary that would otherwise be discovered by a failed migration.

1.4 Seams, decomposition patterns and service sizing

Where a cut is safe, which pattern to use for the cut, and how to tell whether the result is the right size — judged by change rate, ownership and data, never by line count.

Kinds of seam

A seam is a place where the system can be cut with the least resistance, and there are four kinds worth distinguishing. A code seam is a module whose internals are already hidden behind an interface. A data seam is a set of tables that only one module writes. A temporal seam is a step that already happens asynchronously — a batch job, a queue worker — so moving it behind a network adds no new failure mode to the user-visible path. A team seam is a boundary that already matches who owns what and who is on call. The strongest extraction candidate is one that is all four; the weakest is a class at the centre of a web of joins with three teams editing it.

Data is usually the binding constraint. If a candidate module reads another module's tables, the extraction must first break that read, either by duplicating the data via events or by calling an interface. Doing that work inside the monolith — where it costs a refactor and a pull request — is dramatically cheaper than doing it across two databases and a message broker after extraction, which is why the first three steps of any strangler migration are internal.

Decomposition patterns

Several patterns coexist and each answers a different question. Decompose by business capability answers "what does the business do". Decompose by subdomain answers "where is the model different". Decompose by transaction boundary asks which writes must be atomic together and keeps them in one service, because a boundary that splits an atomic write creates a saga. Decompose by rate of change groups the volatile code separately from the stable code so releases are independent. Decompose by scaling profile isolates the component with a radically different resource shape. Strangler and branch by abstraction are migration patterns rather than boundary patterns: one peels functionality out of a live system, the other hides a replacement behind an existing interface so both implementations can run side by side.

Service sizing heuristics

Size by ownership and change rate, not by size of code. A service should have one owning team and fit inside that team's head — the working test is whether a new engineer can understand it and ship a change in their first week, and whether the team could rewrite it in two weeks if needed. A second test is coupling in the release process: if two services are always deployed together, they are one service and should be merged, because the coordination cost of two pipelines with one cadence is pure overhead. A third test is the count of synchronous dependencies: a service that calls six others synchronously on its happy path is a distributed monolith component and should probably be folded together with its tightest partner.

In the other direction, watch for services that are too small. A service with one endpoint and no invariants of its own is usually a library or a module, and extracting it converts a function call into a network call and an on-call rota. The tell-tale is a service whose entire contents could be an object inside a sibling service without that sibling becoming incoherent.

Choosing between synchronous and asynchronous interaction: REST, gRPC and GraphQL for request-response work, messaging and event streaming for decoupling, and the delivery semantics and idempotency discipline that make at-least-once messaging safe.

2.1 Synchronous communication: REST, gRPC and GraphQL

Synchronous calls are correct when the caller cannot complete its own work without the answer — and they multiply availability, so every one of them needs conscious justification.

When a caller genuinely needs an answer now

A synchronous call is right when the response is an input to the caller's own transaction: "is this card authorised?", "does this SKU exist?", "is this user allowed to see this document?". It is also the easiest interaction to reason about, which is why it dominates the first version of every distributed system and why review boards rarely push back on it. The cost is temporal coupling: the caller's latency is at least the callee's, and their availability multiplies rather than staying independent.

The arithmetic is unforgiving. Three dependencies at 99.9% each give a caller that needs all three 99.7%; ten give 99.0%, which is roughly 3.6 days of degradation a year assembled entirely from flawless components. This is why the count of synchronous hops on a critical path is itself an architectural metric, and why shaving a hop with a cache, a local replica or an event is often worth more than any amount of optimisation inside a service.

REST, gRPC and GraphQL are different shapes of coupling

REST over HTTP/JSON is the default for public and cross-team boundaries: human-readable, cacheable with standard semantics, debuggable with curl, and understood by every client and every intermediary. Its weakness is chatty resource modelling, where one screen needs six round trips because each resource is fetched separately, and the fix (a bespoke aggregate endpoint) is how gateways and BFFs get introduced.

gRPC is the default for internal, high-volume, strongly typed calls. Protobuf schemas generate clients, evolve compatibly by field number, support streaming in all four directions, and cost materially less CPU and bandwidth to serialise than JSON. The trade-offs are concrete: browsers need gRPC-Web and a proxy, binary payloads are harder to inspect by eye, and a strict IDL makes casual evolution feel heavier — which is the point.

GraphQL inverts the shape: one endpoint, a client-specified query, and a schema describing the whole graph. It solves over-fetching for varied clients and is a strong fit at the edge, which is why federated GraphQL appears in chapter 3. It does not eliminate the N+1 problem, it relocates it into resolvers; and it makes HTTP caching and per-endpoint rate limiting harder because every request is a POST to the same URL with an opaque body.

Versioning and evolution across a network

Because a service's clients are never deployed with it, every change is a compatibility question with an unknown audience. The safe discipline is tolerant-reader expansion: add a field, deploy all readers so they already ignore fields they do not know, then begin writing it; remove a field only after every reader has stopped reading it. Protobuf supports this natively through field numbers and reserved ranges, and tooling can enforce it — buf breaking --against '.git#branch=main' fails a pull request that removes or renumbers a field.

JSON APIs need the same discipline without the compiler's help, which usually means never removing a field and never changing its meaning. A field whose type changes is indistinguishable from a new field to a lenient parser, so a client keeps reading the old shape and silently produces wrong values rather than failing loudly. Publish the schema, run a compatibility checker in CI, and treat any narrowing as a breaking change that needs a new version.

A JSON field that changes from "amount": "12.50" to "amount": 12.50 breaks every strict deserialiser in the fleet and looks like a harmless cleanup in review. Add amount_minor and an explicit currency, deprecate the string field, and delete it only in a later major version.

2.2 Asynchronous messaging and events

Asynchronous messaging decouples services in time: the producer does not wait, the broker buffers, and the consumer may be down without the producer noticing. That independence is bought with duplication, ordering and observability problems.

Decoupling in time

A synchronous call couples availability and latency: if the callee is down, the caller fails, and the caller's response time includes the callee's. A message flips that relationship. The producer writes to a durable log or queue and returns as soon as the broker has acknowledged, so a burst becomes a backlog rather than a timeout, a restart becomes a pause rather than an outage, and a new consumer can be added without touching the producer. This is the property that makes event-driven systems absorb traffic spikes that would flatten a chain of synchronous calls.

The price is that the producer no longer knows the outcome. Failures arrive later and elsewhere: a malformed message may be rejected ten minutes after the user was told "done", a downstream rule may reject the work, and the user interface has to represent a state between "accepted" and "completed". Ordering is no longer guaranteed unless the broker is explicitly configured for it, and duplication is now normal rather than exceptional — which is why the idempotency discipline in section 2.4 is not optional.

Three event styles, and two kinds of event

An event notification carries an identifier and a hint, and consumers call back for detail. It minimises coupling in the schema but reintroduces a synchronous call, so use it when the payload is large or genuinely sensitive. An event-carried state transfer event carries the full state the consumer needs, so consumers can keep their own replica without calling back — the right choice for read models, search indexes and caches. A command message is not a fact but an instruction addressed to one handler, and it belongs on a queue rather than a topic.

Separately, distinguish the domain event from the integration event. The domain event is the internal record of something that happened, in the service's own language and with its own field names; the integration event is the published contract, deliberately shaped for external consumers and versioned independently. Publishing internal domain events directly to a shared topic is how a private refactor becomes a breaking change for four other teams.

Queue or log: the choice that shapes everything else

2.3 Request-reply, pub/sub and delivery guarantees

The four topologies worth knowing, the three delivery guarantees and what each actually promises, and the retry, dead-letter and backoff machinery every consumer needs.

Topologies and their semantics

A point-to-point queue distributes work: several workers compete, each message is processed once by one of them, and adding workers increases throughput. A publish/subscribe topic fans out: every subscriber receives its own copy, so adding a subscriber never slows the others — and a slow subscriber cannot block anybody, which is exactly why unread backlogs are easy to miss. Competing consumers within a group combines the two: within one consumer group messages are distributed, but each group gets its own copy of the stream. Request-reply over messaging uses a correlation id and a reply queue; it is legitimate for long-running work, but it re-creates coupling in time and should not be used to avoid designing the asynchronous flow properly.

Ordering deserves care in all four. A log orders per partition, so messages about the same entity must share a partition key — usually an aggregate id such as orderId. A queue orders per queue, which means concurrency and ordering are in direct conflict: two workers on one queue can process two messages about the same order simultaneously, in either order. Where order matters, either use a single consumer, or use the entity id as a routing key so that all messages for one entity land on the same worker, or make the handler tolerate any arrival order.

Delivery guarantees, stated precisely

At-most-once acknowledges before processing, so a crash loses the message. It is appropriate for telemetry and for work whose loss is cheaper than its duplication. At-least-once acknowledges after processing succeeds; a crash between processing and acknowledgement redelivers the message, so the effect may happen twice. This is the practical default, and it is safe only when the handler is idempotent. Exactly-once is achievable only inside a single system boundary: Kafka's idempotent producer plus transactions can make "consume, transform, produce" atomic across Kafka topics, and a database can make "apply and record the offset" atomic in one local transaction. End-to-end exactly-once across Kafka and Postgres does not exist, because the two systems cannot share a commit. In practice you build at-least-once delivery plus an idempotent sink, and call the composition effectively-once.

Poison messages, retries and dead letters

A message that always fails — a malformed payload, a reference to an entity deleted years ago — will be redelivered forever unless the design stops it. Three mechanisms matter. A delivery limit (RabbitMQ's x-delivery-limit, SQS's maxReceiveCount, Kafka's retry topic chain) moves a repeatedly failing message out of the hot queue. A backoff ladder delays each retry so a transient dependency outage does not burn the retry budget in milliseconds; the usual shape is retry at 30s, 2m, 10m, then dead-letter. A dead-letter queue preserves the message with its headers and failure reason so a human can inspect and replay it after the bug is fixed. Without a DLQ, "at-least-once" quietly becomes "at-least-once, forever, in a loop", and the queue depth graph becomes the only symptom.

2.4 Idempotency and message deduplication

Every retry, redelivery and consumer rebalance will replay work. Idempotency is the property that makes replay harmless, and it is cheaper to design in than to repair.

Why at-least-once forces idempotency

Consider the window between "the handler did the work" and "the broker recorded the acknowledgement". A crash, a network partition or a consumer group rebalance inside that window causes redelivery, so the work runs twice. The same window exists one level up: a caller that times out does not know whether the server processed the request, so a sensible caller retries, and the server sees the same request twice. Neither of these is a bug in the broker or the client; they are inherent in not being able to commit across two systems atomically. The only defence is to make the handler's effect independent of how many times it runs.

Note that "we use a transactional producer" does not remove the need. Transactions make the consume-transform-produce step atomic within Kafka; the external side effect — charging a card, sending an email, writing to Postgres — is not part of that transaction. Any handler that touches a system outside the broker needs its own idempotency mechanism.

Implementing an idempotency key

The standard approach is a table keyed by a caller-supplied identifier, written in the same transaction as the effect. Insert first: if the insert conflicts, the request has been seen before and the stored response is returned instead of the work being repeated. Store a hash of the request body as well, so that a client reusing a key with different content is rejected with a 409 rather than silently receiving the first request's answer — that mismatch is a client bug and must be loud. Expire keys after a defined window (24 hours is typical) so the table does not grow forever, and make the window longer than any possible retry, which is bounded by the delivery limit and backoff ladder.

-- Postgres: the key, the request hash and the cached response in one table
CREATE TABLE idempotency_key (
  key            text PRIMARY KEY,
  request_hash   text        NOT NULL,
  status_code    int,
  response_body  jsonb,
  state          text        NOT NULL DEFAULT 'in_progress',  -- in_progress | done
  created_at     timestamptz NOT NULL DEFAULT now(),
  expires_at     timestamptz NOT NULL DEFAULT now() + interval '24 hours'
);
CREATE INDEX idempotency_key_expiry_idx ON idempotency_key (expires_at);

-- claim the key and apply the effect atomically
BEGIN;
WITH claimed AS (
  INSERT INTO idempotency_key (key, request_hash)
  VALUES ($1, $2)
  ON CONFLICT (key) DO NOTHING
  RETURNING key
)
INSERT INTO payment (id, order_id, amount_minor, currency, intent_key)
SELECT $3, $4, $5, $6, $1
WHERE EXISTS (SELECT 1 FROM claimed)
RETURNING id;
-- 0 rows = key already used; compare request_hash, then return the cached response
COMMIT;

Idempotency without keys

Where a caller cannot supply a key, design the operation so repetition is naturally harmless. Upserts keyed by a natural identifier (INSERT ... ON CONFLICT (order_id, line_no) DO UPDATE) are idempotent by construction. Conditional state transitions are idempotent when they include the expected current state: UPDATE order SET status='CONFIRMED' WHERE id=$1 AND status='PENDING' affects one row the first time and zero rows on replay, and the handler can treat zero rows as "already done". Monotonic comparisons protect against out-of-order redelivery: ignore an update whose revision or occurredAt is older than what is stored. And sequence numbers let a consumer skip anything it has already processed, which is how compacted log topics are consumed safely.

-- Conditional transition: exactly one of these two statements ever changes the row
UPDATE "order"
   SET status = 'CONFIRMED', confirmed_at = now(), revision = revision + 1
 WHERE id = $1 AND status = 'PENDING' AND revision = $2
RETURNING id, revision;

-- 0 rows affected? Either it is already CONFIRMED (fine, treat as success)
-- or the revision is stale (drop the stale event and log it as a metric).

-- Monotonic guard for carried-state events
INSERT INTO product_projection (sku, title, price_minor, revision, updated_at)
VALUES ($1, $2, $3, $4, now())
ON CONFLICT (sku) DO UPDATE
   SET title = EXCLUDED.title,
       price_minor = EXCLUDED.price_minor,

The edge of a distributed system: what a gateway should and should not do, why a backend-for-frontend exists and who owns it, how GraphQL federation composes many services into one graph, and the anti-patterns that quietly turn an edge proxy into a second monolith.

3.1 What an API gateway actually does

A reverse proxy with policy: routing, TLS, authentication, rate limits, observability headers — the concerns every service needs and none should reimplement.

Cross-cutting concerns belong at the edge

Every service needs the same handful of things applied before its own logic runs: terminate TLS, authenticate the caller, resolve the tenant and its quota, route by path, host or header, stamp tracing headers, apply compression, CORS and request size limits. Implementing that five times produces five subtly different definitions of "authenticated", and the differences are only discovered during a security review or an incident. A gateway centralises the concerns so each service can assume a routed, authenticated request with a stable header contract.

In 2026 the mainstream options split into Envoy-derived proxies (Envoy itself, Istio's ingress gateway, Emissary), nginx/OpenResty, managed cloud gateways, and Kubernetes Gateway API implementations such as Cilium, Contour and Kong. The Gateway API has largely displaced the older Ingress resource for new work because it separates infrastructure ownership — the GatewayClass and Gateway, owned by a platform team — from application routing, expressed as HTTPRoute objects owned by the teams that own the services. That split is what stops every new route becoming a platform ticket.

What the gateway must not become

A gateway should hold no business rules. The moment it decides whether an order is refundable or which discount applies, it has become a service with logic, state and an on-call rota — carrying all the coupling of everything it fronts with none of the isolation. Keep it to routing, policy, protocol translation and light, stateless payload transformation. If a route needs to ask a question about domain state, that question belongs in a service that owns the answer.

Two further failure modes deserve design attention. The gateway is a single point of failure even when replicated, because it concentrates the blast radius of misconfiguration; keep its configuration declarative and versioned, and rehearse restoring it from source, because the fastest way to take a fleet down is a bad route pushed everywhere at once. And an overloaded gateway adds a hop to every external call — measure the added p50 and p99 rather than assuming it is free, and use a service mesh for east-west traffic instead of routing internal calls back out through the edge.

Ingress north-south versus east-west

Gateway traffic is north-south: from outside the cluster to a service. Service-to-service traffic is east-west, and pushing it through the same edge proxy adds latency, doubles the failure surface and turns your public entry point into a dependency of internal calls. East-west policy — mTLS, retries, traffic splitting, telemetry — belongs either in the client library or in a sidecar or node-level mesh, which chapter 9 covers. Keeping the two planes distinct also means the public gateway can be locked down hard while internal traffic keeps its own, looser, expiry-driven policy.

3.2 Backend for frontend

A BFF is a client-shaped aggregation layer owned by the team that owns the client, so that mobile, web and partner needs stop competing for space in one general-purpose API.

Why per-client BFFs exist

A mobile app and a browser have genuinely different shapes of demand. The browser can fetch five resources and render progressively; the phone wants one payload sized for a flaky connection, with images and fields it will actually show. A partner API wants stable, coarse, versioned endpoints with generous limits. When all three are served by one general-purpose API, every client's requirement becomes an option on a shared endpoint: the payload grows monotonically, fields are added and never removed, and one team's release is gated on another team's review. The BFF splits that argument: each client experience gets its own thin layer with its own payload shape and its own release cadence, while the domain services keep their clean, client-agnostic interfaces.

The organisational effect is the real point. A BFF is owned by the client team, so the team that feels the latency and sees the screens owns the code that aggregates. That removes the hand-off that otherwise turns every UI change into a ticket against a backend team's backlog.

Aggregation, not business logic

A BFF's job is fetch, join, project and cache. It must not own invariants: if the BFF decides whether an order is cancellable, the rule now exists in two places and they will disagree. Aggregation is nevertheless more than a Promise.all — the interesting part is what happens when one dependency fails. A page that needs a product, its reviews and its delivery estimate should render without the reviews if reviews are down, so calls are issued in parallel, individually timed out, and the failures are absorbed into a partial response the client can handle. Falling back to a cached value, and marking it as stale, beats failing the whole page.

// Node BFF: parallel fetch, per-call deadline, partial failure, short cache
import express from "express";

const app = express();
const cache = new Map();          // in production: Redis with a 30s TTL

async function get(url, timeoutMs) {
  const started = Date.now();
  try {
    const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });
    if (!res.ok) throw new Error("status " + res.status);
    return { ok: true, data: await res.json(), ms: Date.now() - started };
  } catch (err) {
    return { ok: false, error: String(err), ms: Date.now() - started };
  }
}

How many BFFs, and who owns them

Split by client experience, not by screen or by platform. One BFF for the customer web app, one for the mobile apps (iOS and Android usually share it), one for the partner API, and possibly one for internal tooling. Two weeks after creating a BFF per screen you have a monolith with worse tooling; one BFF for everything is just the general-purpose API again. The workable rule is that a BFF exists where a distinct client population has a distinct payload, cadence and failure tolerance.

Two recurring failure modes are worth designing against. First, aggregation logic duplicated across BFFs: extract the shared upstream client and the response models into a library both consume rather than a third shared service, which would become the general-purpose API you were avoiding. Second, the BFF accumulating writes. A BFF should orchestrate reads generously and writes sparingly, because a write endpoint in a BFF is an invariant in the wrong service and a second place where authorisation must be correct.

If several BFFs need to compose the same set of domain services with the same joins, that is a signal the domain services are missing a coherent interface — or a good case for a federated GraphQL edge, which gives each client flexible queries over one graph without a bespoke aggregator per client.

3.3 GraphQL federation

Federation composes independently deployed services into one graph, so clients query across boundaries without a per-client aggregator — at the cost of a query planner, entity resolution and query cost control.

Subgraphs, composition and the router

In a federated graph, each team runs a subgraph: an ordinary GraphQL service that extends types it does not own by declaring a @key. The subgraph that defines a type owns its primary fields; another subgraph that needs to add fields declares the same type, identifies it by key, and marks the fields it does not own as @external. A composition step validates those declarations across all subgraphs and produces a supergraph schema, which a router (Apollo Router, Cosmo Router, GraphQL Mesh) uses to plan queries. Clients see one endpoint; the router splits each query by which subgraph can resolve each field, fans out, and stitches the results back together.

Entity resolution is the mechanism that makes cross-service joins work without a shared database: a subgraph may implement a reference resolver that fetches an entity by key, so the products subgraph can be asked for price for a set of SKUs that the reviews subgraph enumerated. The keys are therefore a real schema commitment — changing them is a breaking change across the graph — and every resolver becomes a fan-out point that needs batching.

extend schema @link(url: "https://specs.apollo.dev/federation/v2.9",

  sku: ID!

Query planning, N+1 and cost control

A federated query is not a database query with a nice syntax in front of it. The router builds a plan: fetch products by SKU, then batch the review lookups for those SKUs, then merge. If the resolver for reviews loads them one SKU at a time, the router's fan-out becomes an N+1 storm across services, which is why every entity resolver must batch — a DataLoader keyed by entity id, or a bulk endpoint such as getProductsBySkus([...]). Instrument the subgraph side of every plan step; the router's own trace shows the shape, but only the subgraph's spans reveal the query count.

Cost control is mandatory at an edge that accepts arbitrary queries, because a client can ask for a deep, wide, self-referential selection that no REST endpoint would ever expose. Three controls are standard: a static complexity limit (assign a cost per field and per list depth, reject above a threshold), a depth limit, and a timeout on the whole plan with per-subgraph deadlines. Add persisted or allow-listed queries for first-party clients, which converts the edge from "any query" to "these 40 known queries" and makes cost predictable and cacheable.

When federation is the wrong tool

Federation pays off when many teams own parts of one connected domain and clients need to ask questions the API designers did not anticipate. It is a poor fit when the graph is small and stable, where a handful of REST endpoints behind a BFF is far less machinery; when consumers are machine-to-machine with fixed needs, where gRPC or REST is a better contract; and when the organisation cannot staff the router as a supported platform component, because the router is a hard dependency of every client and its composition failures are total.

3.4 Rate limiting, auth offload and edge anti-patterns

The two jobs a gateway does better than anything behind it — turning away excess traffic early and verifying identity once — plus the failure modes that turn an edge proxy into a liability.

Rate limiting: algorithms and placement

A fixed window counter is trivial but allows double the limit across a boundary: 100 requests at 00:59 and 100 more at 01:00. A sliding window log stores timestamps and is exact but memory-heavy per key. A sliding window counter interpolates between two fixed windows and is the usual production compromise. A token bucket permits short bursts while enforcing an average rate, which is what interactive clients actually need, while a leaky bucket smooths traffic to a constant output rate and is the right shape when the thing behind the limiter cannot handle bursts at all. Whichever you choose, the enforcement key matters more than the algorithm: limits per API key or per tenant protect the system from one customer, while limits per IP protect against anonymous abuse, and limits per user protect against one account's runaway script.

Placement is layered. The edge rejects cheaply, before TLS termination cost and application work; a local in-process limiter (Envoy's local rate limit, nginx's shared-memory zones) catches bursts without a network hop but is per-instance, so the effective limit is the limit times the instance count. A global limiter using Redis gives an accurate cluster-wide number at the cost of a round trip and a new dependency on the request path. Run both: a generous global limit and a tight per-instance one, so a single hot instance cannot exhaust the fleet. Always return 429 with Retry-After and a machine-readable error body, because clients that cannot tell the difference between "slow down" and "you are broken" retry immediately.

limit_req_zone $binary_remote_addr zone=perip:20m rate=20r/s;

Auth offload: what the edge can and cannot decide

The gateway is the right place to establish who the caller is: terminate TLS, verify the token's signature against the issuer's JWKS, check exp, iss and aud, and reject the request if anything fails. It should also normalise the identity into a small set of forwarded headers with a trusted naming scheme, and strip any client-supplied copies of those headers so a caller cannot forge them. What it should not do is decide what the caller may do. Fine-grained authorisation depends on resource state — is this order mine, is this account suspended, does this tenant's plan include exports — and that state lives in services. Enforcing coarse rules at the edge is good defence in depth; enforcing them only at the edge is a vulnerability, because service-to-service calls and internal paths bypass it.

Where tokens must cross a boundary with a different audience, use token exchange rather than forwarding the user's token unchanged. A gateway can accept a user token addressed to the edge and obtain a narrowly scoped token for the specific downstream service, so a compromised service cannot replay the user's full authority against other services. Keep token lifetimes short, and make the identity provider's JWKS caching explicit — a five or ten minute cache with a refresh on unknown kid avoids both an outage when keys rotate and a stampede against the issuer.

Edge anti-patterns

Business logic in the gateway. Rules that reference domain state turn the shared edge into the most coupled service in the system, deployed by everyone and owned by no one. One global config with no ownership. A single file that every team edits becomes a merge bottleneck and a shared blast radius; use per-team route objects with a platform-owned gateway, which is the Gateway API design. Retries at the edge. A gateway that retries 5xx responses multiplies load during an incident, turning a slow dependency into an outage — retries belong in the caller, where the semantics of the operation are known. Long-lived credentials in the proxy. A static service token in the edge config cannot be rotated per service and is a single credential with fleet-wide authority. Buffering large uploads. A proxy that buffers whole bodies exhausts memory on a single large request; stream them, or route them directly to object storage with a pre-signed URL. Timeouts left at defaults. Unbounded proxy timeouts hold connections until a dependency recovers, which is how one slow service takes down every route through the shared edge.

The hardest part of microservices is not the code but the data: ownership per service, transactions that span services, and the consistency models that replace a single ACID commit.

4.1 Database per service

The database is the real boundary. A service that shares tables with another cannot be deployed, scaled or changed independently, whatever its API claims.

Why the datastore decides independence

Two services that read one another's tables are coupled through the most volatile artefact in the system. Every schema change is a coordinated release; every index added for one workload slows the other; a lock held by one team's bulk update blocks the other's checkout path; and neither service can be scaled to a different database size. The coupling is also invisible to the compiler and the API documentation, because it lives in SQL that nobody reviews as an interface. This is why shared-database microservices (chapter 14) behave exactly like a monolith while costing more to operate.

Ownership does not require a separate database server per service. It requires that a service is the only writer of its schema, that no other service can read it, and that no query joins across the boundary. Separate schemas with separate roles achieves the logical boundary on one cluster; separate databases or instances add failure isolation and independent tuning. Start with separate schemas and private credentials, and split hosts when a service needs its own resource profile, its own upgrade window or its own blast radius. Polyglot persistence — a document store for a catalogue, a relational store for orders, a search index for query — follows naturally once each service owns its own storage.

-- One schema and one login role per service; the boundary is enforced, not agreed.
CREATE ROLE svc_orders   LOGIN PASSWORD :'orders_pw';
CREATE SCHEMA orders AUTHORIZATION svc_orders;
CREATE ROLE svc_catalogue LOGIN PASSWORD :'catalogue_pw';
CREATE SCHEMA catalogue AUTHORIZATION svc_catalogue;

GRANT USAGE ON SCHEMA catalogue TO svc_catalogue;   -- not to svc_orders

The joins you lose

A join that crossed a module boundary inside the monolith becomes, after extraction, one of four things. API composition calls both services and joins in memory: simple, correct, and expensive when the result set is large, because it becomes N+1 calls or one very wide request. An event-fed projection keeps a local copy of the fields the service needs, updated from the owning service's events: fast and available when the owner is down, at the cost of replication lag and a rebuild path. A CQRS read model maintains a purpose-built denormalised table that many services and clients query, which is the standard answer for cross-domain list pages. A data warehouse or lakehouse handles analytics, where joining across every domain is the whole point and a few hours of staleness is acceptable.

The decision is driven by size and freshness. Joining two records is an API call. Joining two hundred thousand for a report is a projection or a warehouse. Anything on the interactive path that needs low latency and joins more than a handful of rows should be a projection, because API composition on a hot path multiplies latency and availability risk with every additional service it touches.

Cross-service reads must be explicitly allowed

Removing the ability to join is as much an organisational change as a technical one, and it will be resisted by whoever owns the report that used to be one query. The productive response is to make the allowed paths first-class: publish a data product from the owning service, give it a documented contract and a freshness guarantee, and treat consumers of it as you would treat API consumers. What must not happen is a private read-only replica of someone else's schema, granted "temporarily", because that is a shared database wearing a disguise and the owning team can no longer change a column without breaking an unpredictable consumer.

4.2 Local transactions and compensating actions

A saga is a sequence of local transactions, each with a compensating action that undoes its effect semantically rather than physically.

What a saga actually guarantees

A saga is a business process implemented as N local transactions across N services, where each step either completes or is compensated by a previously registered action. It does not provide atomicity or isolation; it provides eventual consistency plus a recorded history of what was done. The intermediate states are visible to other readers, so a saga must be designed so that a partially completed order is a legitimate state rather than a corrupt one: PENDING with a reservation held is fine, "order exists but no payment and no stock" is a state somebody will eventually ship.

Two properties make sagas workable. Every step must be idempotent, because the saga may retry a step after a crash and at-least-once delivery is the norm. Every compensation must be semantically valid even if it arrives late or twice: a refund that runs twice is a real problem, so compensation records its own key and checks whether it has already run. The classic failure is a compensation that cannot undo the original — you cannot un-send a confirmation email — which is why the ordering of steps matters. Put irreversible steps last, after every compensatable step has succeeded.

Semantic locks and isolation loss

Because there is no global lock, sagas use semantic locks: a reservation flag, a pending payment, a hold with an expiry. The lock is visible to other transactions, which must know to respect it — an inventory service that counts reserved stock as available will oversell the moment a saga is in flight. Where a conflicting saga is detected, the standard responses are to fail fast and compensate the later saga, or to wait with a bounded retry. Expiring holds matter as much as the hold itself: a saga that crashes permanently must not lock stock forever, so every semantic lock needs a TTL and a reconciliation job that sweeps expired holds and compensates or completes them.

-- Saga state in a table: durable, inspectable, and resumable after a crash
CREATE TABLE saga_instance (
  id             uuid PRIMARY KEY,
  saga_type      text        NOT NULL,
  state          text        NOT NULL,   -- STARTED | RESERVED | PAID | COMPENSATING | DONE | FAILED
  payload        jsonb       NOT NULL,
  attempts       int         NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX saga_due_idx ON saga_instance (next_attempt_at) WHERE state NOT IN ('DONE','FAILED');

-- the worker claims work without two pods processing the same saga
WITH due AS (
  SELECT id FROM saga_instance
   WHERE state NOT IN ('DONE','FAILED') AND next_attempt_at <= now()
   ORDER BY next_attempt_at
   FOR UPDATE SKIP LOCKED
   LIMIT 20
)
UPDATE saga_instance s
   SET attempts = attempts + 1, next_attempt_at = now() + interval '2 seconds'
  FROM due
 WHERE s.id = due.id
RETURNING s.id, s.saga_type, s.state, s.payload, s.attempts;

Writing compensations without a workflow engine

You can hand-roll a saga, and many teams do, but the code you write is a durable state machine with retries, timers, idempotency keys and crash recovery — which is a substantial fraction of a workflow engine. If your platform already runs one — Temporal, Cadence, AWS Step Functions, Camunda, or a database-backed queue with a state table — it is usually cheaper to express the process there. The benefit is that the compensating logic sits next to the forward logic in the same function, ordered by ordinary control flow, while the engine handles persistence, retries and timers.

// Temporal TypeScript: the saga is an ordinary function; the engine persists
// every activity result, so a worker crash resumes rather than restarts.
import { proxyActivities, ApplicationFailure } from "@temporalio/workflow";

const { reserveStock, releaseStock, authorisePayment, refundPayment } =
  proxyActivities<ShopActivities>({
    startToCloseTimeout: "10s",
    retry: { maximumAttempts: 5, initialInterval: "200ms",
             backoffCoefficient: 2, maximumInterval: "10s" },
  });

export async function placeOrder(order: Order): Promise<string> {
  const reservation = await reserveStock({ sku: order.sku, qty: order.qty,
                                           idempotencyKey: order.id });

  let authRef: string | undefined;
  try {
    authRef = await authorisePayment({ orderId: order.id,
                                       amountMinor: order.totalMinor,
                                       idempotencyKey: order.id });
  } catch (err) {
    // compensate the forward step before failing; compensation is retryable
    await releaseStock({ reservationId: reservation.id,
                         idempotencyKey: reservation.id });
    throw ApplicationFailure.nonRetryable("payment_declined");
  }

  // irreversible work goes last, once nothing left can fail
  await sendOrderConfirmation({ orderId: order.id });
  return authRef;
}

4.3 Choreography versus orchestration

The same process, two shapes: services reacting to each other's events with no central brain, or one coordinator that calls each step and owns the state machine.

Choreography: events, no coordinator

In choreography each service subscribes to the events it cares about and publishes its own, so the process exists only as an emergent property of the subscriptions. It is maximally decoupled at the point of addition — a new service can join the flow by subscribing, without touching anybody else — and it has no single point of failure or bottleneck. The costs appear as the process grows. There is no artefact anywhere that says what the whole flow is, so answering "what happens after payment is authorised?" requires walking every consumer's code. Debugging a stuck order means correlating events across five services. Cyclic event flows are easy to create accidentally, and there is no place to enforce a timeout or a cancellation policy.

Orchestration: one coordinator owns the state

In orchestration a coordinator issues commands and tracks the outcome, holding the state machine in its own store. The process is explicit: one artefact describes the steps, the retries, the timeouts and the compensations, and a single dashboard shows every in-flight instance and where each is stuck. It is easier to test, easier to reason about, and the natural fit for processes with many steps, deep branching or a regulatory requirement to show what happened. The costs are real too: the orchestrator is a component everyone depends on, it can become a coupling point where every team's rules accumulate, and the coordinated commands reintroduce a degree of temporal coupling between steps.

Choosing, and the hybrid that usually wins

Use choreography when the process is short, the reactions are genuinely independent and nobody needs a global view — notifications, index updates, audit trails, cache invalidation. Use orchestration when the process is long-running, has compensation, has branching or needs an auditable trace — checkout, onboarding, claims, migrations. Most real systems end up hybrid: choreography for the fan-out after a business fact, orchestration for a linear process that must be tracked and interrupted.

The pragmatic boundary is the number of steps and the number of teams. Below roughly four steps with one owning team, choreography is less machinery and less to break. Above that, or as soon as two teams must agree on the order of steps, write the process down in an orchestrator where the sequence is a reviewable artefact. A useful intermediate is a saga orchestrated by a component inside one service — the order service coordinates stock and payment — which keeps the state machine explicit without introducing a platform-wide workflow engine.

4.4 Transactional outbox

The dual-write problem and its standard fix: record the state change and the message in one local transaction, then let a relay publish it — so a message can never be lost or invented relative to the data.

The dual-write problem

Almost every correctness bug in an event-driven system descends from a service doing two things that cannot be committed together: writing to its database and publishing to a broker. Committing the database first and then publishing means a crash in between loses the event permanently — the order exists and nobody was told. Publishing first and then committing means the event can describe a change that never happened, and downstream services act on a phantom. Wrapping the publish in a Kafka transaction does not help across the boundary either, because the database commit is not part of the broker's transaction. There is no ordering of the two writes that is safe on its own.

The outbox: one transaction, two tables

Write the event into an outbox table in the same local transaction as the state change. Now the decision is atomic by construction: either both rows exist or neither does. A separate relay process reads unpublished rows and publishes them to the broker, then marks them published. This is at-least-once: if the relay publishes and crashes before marking, the message is published again, so consumers must be idempotent. An ordering_key column — the aggregate id — lets the relay preserve per-aggregate order by publishing all rows for one key through a single ordered path, which is what makes the outbox safe for state-transfer events where order matters.

-- The state change and the event commit together, or not at all.
BEGIN;

INSERT INTO "order" (id, customer_id, total_minor, currency, status)
VALUES ($1, $2, $3, $4, 'PLACED');

INSERT INTO outbox (aggregate_id, aggregate_type, event_type, payload, ordering_key)
VALUES ($1, 'order', 'order.placed.v1', $5, $1);

COMMIT;   -- after this, the event WILL be published (at least once)

-- outbox table
CREATE TABLE outbox (
  id            bigserial PRIMARY KEY,
  aggregate_id  text        NOT NULL,
  aggregate_type text       NOT NULL,
  event_type    text        NOT NULL,
  payload       jsonb       NOT NULL,
  ordering_key  text        NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);
CREATE INDEX outbox_unpublished_idx ON outbox (ordering_key, id)
  WHERE published_at IS NULL;
-- housekeeping: delete published rows older than 7 days in a nightly job

Relay implementations

Three relay designs are in common use. A polling publisher runs inside the service, claims a batch with FOR UPDATE SKIP LOCKED, publishes it and marks it done: no extra infrastructure, easy to reason about, and its throughput is bounded by the poll interval, which is fine for most business events but not for high-volume streams. A change data capture pipeline — Debezium on the database's write-ahead log — publishes outbox rows with no polling and no publisher code, at the cost of running and monitoring a connector. A broker-side transaction log (Kafka transactions plus an idempotent producer, or a database with a built-in outbox like some managed offerings) removes the relay but only works when the database and the broker are willing to cooperate.

Whichever you choose, make the relay observable: an unpublished-row age metric is the single most useful alarm in an event-driven system, because it catches a stalled relay before consumers notice missing data. Give the relay a poison-row policy too, since a row that cannot be published — a malformed payload, a topic that no longer exists — otherwise blocks the queue behind it forever.

Changing your mind after publishing

An event that has been published cannot be recalled, which shifts the burden onto the new event that corrects it. If an order is cancelled, you publish order.cancelled.v1; consumers must handle a cancel that arrives without a preceding place if they started from an offset after the place. This is why streams are retained and replayable, and why consumers are built to tolerate any arrival order — a new consumer group bootstrapping from the earliest offset will see the whole history, in order, and must converge on the same state as one that started late. Test that convergence explicitly: replay a day of events into a fresh projection and compare it with the live one.

4.5 CQRS and event sourcing

Separating the write model from the read model, and optionally making the event log itself the source of truth. Powerful, and frequently applied to problems that do not need it.

CQRS: two models, one domain

Command Query Responsibility Segregation means the path that changes state and the path that reads state are allowed to use different models, stores and scaling profiles. It is worth the cost when reads and writes genuinely differ: a write path that enforces invariants over a normalised aggregate, and a read path that serves a denormalised, indexed list view with different query patterns and ten times the volume. The read model is maintained by consuming the write side's events, so it lags by milliseconds to seconds, and the UI must represent that: return the write response with a location or a pending status, then let the client poll or receive a push when the projection catches up.

The costs are concrete. A projection is another moving part with its own lag, its own rebuild and its own bug surface. Writes that must be immediately visible to the writer — "create then immediately list" — need care, either by reading through to the write model for that user or by returning a version token the client can wait on. And every projection must be reproducible: keep the events, keep the checkpoint offsets, and rehearse a full rebuild, because a projection whose only copy is live production data cannot be corrected when a bug is found.

Event sourcing: the log is the truth

In an event-sourced system the state of an aggregate is derived by replaying its events, and the events are the system of record. That gives a complete audit trail by construction, the ability to rebuild any projection, and a natural fit with event-driven integration. It also imposes real constraints. Every event is permanent, so event schemas must be versioned and evolved with care; a long-lived aggregate accumulates many events, so snapshots are needed to bound replay time; and the many questions the business asks that are not "what happened" — "what is the value now" — are answered by projections, which must exist before any query can be served.

Event sourcing is the wrong choice when you need flexible ad-hoc querying (a projection per query is not sustainable), when there is no business requirement for a full audit history, or when the team has no experience with eventual consistency and versioned event schemas. The deletion problem also needs a plan: a GDPR erasure request cannot rewrite an immutable log, so either store personal data by reference to a crypto-shredded key, or keep personal data outside the event store and hold only identifiers in events.

Putting the three together

A common, defensible combination is: domain state in ordinary normalised tables for the write model, an outbox for reliable publication, and event-fed projections for the read shapes that queries actually need — with event sourcing reserved for the few aggregates where an audit trail is a requirement rather than a nicety (ledgers, entitlements, approvals). That keeps the permanent-schema commitment of event sourcing narrow, while still getting eventual consistency and replay where they pay for themselves. Adopt full event sourcing across a whole domain only when the audit value is genuinely the product, as in finance or regulated records.

Distributed systems fail partially and slowly. This chapter covers the mechanisms that keep a partial failure from becoming a total one: timeouts and retries, circuit breakers, bulkheads, load shedding, backpressure and deliberate fault injection.

5.1 Timeouts and retries

A timeout is the only defence against a dependency that never answers; a retry is a bet that the failure was transient. Both must be sized from a budget, not chosen by feel.

Timeouts are a latency budget, not a safety net

Start at the user-visible requirement and subtract. If a page must render within 1,000 ms and the edge may spend 100 ms, a request that fans out to three services in parallel can give each 600 ms; a service that then calls two dependencies in sequence can give each 200 ms. Every hop inherits a smaller number, and that number must be attached to the request so the callee can see how much time remains rather than starting its own fresh clock. Without deadline propagation, a chain of 5-second timeouts means a request can occupy threads for 25 seconds while the client gave up after 2 — the classic situation where the load spike has already passed but the system is still stuck draining work nobody is waiting for.

The failure mode when timeouts are missing or too long is not "slow responses". It is resource exhaustion: request threads or connections are held, pools fill, health checks start failing, and the orchestrator restarts a service that was only waiting. A missing timeout converts a slow dependency into an outage of the caller. Set a connect timeout shorter than the read timeout, since a refused connection is immediate while a slow server needs room, and always set a client-side timeout on every HTTP client, database pool, cache client and message consumer — including the ones created by libraries with generous defaults. Infinite and 30-second defaults are the most common configuration defect in production traffic paths.

Retry with exponential backoff and jitter

A retry helps only when the failure is transient, the operation is idempotent, and the retry happens at exactly one layer. Retrying a non-idempotent write duplicates it; retrying a permanent error (400, validation failure, unknown entity) wastes the budget and hides the bug behind latency. Retrying at several layers is the classic amplification bug: three layers each retrying three times turns one logical request into twenty-seven requests, which is why an overloaded service stays overloaded — the retries are the traffic. Pick one layer, usually the caller closest to the dependency, and make every layer above it fail fast.

Backoff without jitter does not work, because synchronized clients retry in lockstep: if 2,000 requests time out together, they all come back 100 ms later and the second wave is as damaging as the first. Full jitter — sleeping a uniformly random duration between zero and the exponential bound — spreads the wave. Cap the number of attempts and the total time, and add a retry budget (for example, retries may not exceed 10% of successful requests over a window) so that a partial outage does not become a self-inflicted denial of service.

// Go: capped exponential backoff with full jitter, deadline-aware
func callWithRetry(ctx context.Context, fn func(context.Context) error) error {
	const maxAttempts = 4
	base := 50 * time.Millisecond

	for attempt := 1; ; attempt++ {
		err := fn(ctx)
		if err == nil || attempt == maxAttempts || !isTransient(err) {
			return err
		}
		// full jitter: uniform in [0, base*2^(attempt-1))
		bound := base * time.Duration(1<<(attempt-1))
		sleep := time.Duration(rand.Int63n(int64(bound)))

		select {
		case <-time.After(sleep):
		case <-ctx.Done():          // caller's deadline wins over our backoff
			return ctx.Err()
		}
	}
}

func isTransient(err error) bool {
	var se *ServiceUnavailable
	var to net.Error
	return errors.As(err, &se) || (errors.As(err, &to) && to.Timeout())
}
// gRPC: propagate a deadline and fail fast instead of queueing forever
ctx, cancel := context.WithTimeout(parentCtx, 1200*time.Millisecond)
defer cancel()

// WaitForReady(false) means a call to an unready backend fails immediately
// rather than blocking until the connection is healthy.
resp, err := client.GetQuote(ctx, req,

	grpc.MaxCallRecvMsgSize(1<<20))

// Server side: the handler must respect the remaining budget
func (s *server) GetQuote(ctx context.Context, req *pb.QuoteRequest) (*pb.Quote, error) {
	deadline, ok := ctx.Deadline()
	if !ok {
		return nil, status.Error(codes.InvalidArgument, "no deadline set")
	}
	if time.Until(deadline) < 20*time.Millisecond {
		return nil, status.Error(codes.DeadlineExceeded, "budget exhausted")

}

Idempotency is the precondition

Retrying a POST that creates an order needs a key the server can deduplicate on, or the retry creates a second order. The HTTP convention is an Idempotency-Key header (Stripe's approach, now widely copied): the client generates a UUID per logical operation, reuses it across retries, and the server stores it with the response so a repeat returns the original result rather than performing the work again. The safe HTTP verbs — GET, PUT, DELETE — are naturally idempotent because they express desired state rather than an increment. Where the API cannot be made idempotent, retries must move to a layer that can guarantee deduplication, which usually means a queue with a deduplication id rather than an HTTP client.

5.2 Circuit breakers and bulkheads

A breaker stops sending traffic to something that is failing, so the failing dependency gets room to recover. A bulkhead stops one failing dependency from consuming every resource in the caller.

States, thresholds and what a breaker buys

A circuit breaker is a state machine over a rolling window of calls. In closed state it passes traffic and records outcomes. When the failure ratio (or the slow-call ratio) crosses a threshold with enough volume to be statistically meaningful, it moves to open and fails immediately without calling the dependency. After a wait it moves to half-open and admits a small number of probes; if they succeed, it closes, and if they fail, it reopens for a longer period. The parameters that matter are the window (count-based or time-based), the minimum number of calls before a decision — which prevents a single failure at low traffic from tripping the breaker — the failure rate threshold, the slow-call threshold, and the wait duration before probing.

The value over a bare timeout is that a timeout spends the full budget on every call while the dependency is down, which keeps both the caller and the callee saturated. A breaker fails in microseconds, sheds the load from the failing dependency, and turns a slow degradation into a fast, explicit error that the caller can handle. It also makes the failure visible in one place: breaker state is a metric that says "this dependency is unhealthy right now" without any log archaeology.

Bulkheads: isolating pools per dependency

A bulkhead partitions resources so that exhaustion in one partition cannot consume the others. Without it, one slow dependency is enough to take down every endpoint: threads block on the slow call, the shared thread pool fills, and endpoints that never touch that dependency start failing too. The fix is a separate concurrency limit per dependency — a semaphore or its own thread pool — sized so that the worst case of all dependencies still leaves the process able to serve health checks and unaffected routes.

Semaphore-based bulkheads (limit the number of concurrent calls) are usually preferable to thread-pool bulkheads (limit the number of threads) in asynchronous stacks, because a thread pool imposes context-switch and queueing costs that a semaphore avoids. The same concept applies above the process: separate node pools for CPU-bound and memory-bound workloads, separate consumer groups for a high-volume topic so one poison partition cannot stall everything, and a dedicated connection pool per database so a reporting query cannot starve the transactional path. Kubernetes resource requests and limits are bulkheads too — they bound the blast radius of a runaway replica — and they fail loudly by killing the container rather than silently by degrading the node.

Timeouts, retries and breakers as one system

These three mechanisms are usually configured independently and then interact badly. The workable ordering is: an inner deadline on each call, a retry policy around it with jitter and a small attempt cap, a breaker that observes the outcomes of attempts, and a bulkhead around everything that caps in-flight work. Two rules prevent the common failures. First, retries must never cross a bulkhead that is already saturated, or the retry queue becomes an unbounded buffer. Second, a breaker must count the final outcome per logical operation, not each attempt, or a single operation that retries three times and fails will triple-count and trip the breaker far earlier than intended.

Finally, share the failure signal. A per-instance breaker learns slowly and only about the traffic it happens to receive; a mesh-level outlier ejection removes an unhealthy endpoint for every caller, and a service-level health signal in the registry stops new traffic arriving at all. All three levels are complementary: the registry decides who is a candidate, the mesh decides which candidates are currently bad, and the client breaker decides whether the whole dependency is worth calling.

5.3 Rate limiting, load shedding and backpressure

Near saturation, latency rises without bound and every additional request makes the system worse. Shedding load deliberately is how a service stays useful instead of collapsing.

Why queueing destroys latency near saturation

A single-server queue's response time grows as 1 / (1 - utilisation). At 50% utilisation a small burst is absorbed invisibly; at 80% the queue is noticeable; at 95% the same burst multiplies latency by tens; at 99% it multiplies it by a hundred. The practical consequence is that a service running at high utilisation has no headroom for the burst that always arrives, and its p99 degrades long before its average does. This is why scaling on average CPU is misleading and why the useful signal is queue depth, in-flight requests or p99 latency against the SLO.

It also means "keep accepting everything" is not a kindness. Accepting a request that will time out wastes the capacity that could have served ten requests that would have succeeded, so the system serves fewer users well. Shedding early — at the edge and at admission control — is how a service preserves the requests it can complete. A useful mental model is that overload is managed by choosing which requests to lose, and the only choice is whether that decision is made deliberately by your code or accidentally by a timeout.

Admission control, priority and load shedding

Admission control decides before doing work: check the in-flight count, the queue length and the caller's class, and reject with 429 or 503 plus a Retry-After when the budget is exhausted. Rejecting at the front is cheap; rejecting after three downstream calls is expensive. Priority makes the shedding intelligent: interactive requests for paying tenants survive a burst that sheds batch jobs and free-tier traffic, which is the difference between a degraded service and a broken one.

Which requests to drop is a design question, not a detail. Under overload, dropping the oldest queued work is usually better than dropping the newest, because the newest is most likely to be for a user still waiting, while the oldest is likely to be abandoned — this is the LIFO argument. And shedding must be visible: a load_shed_total counter by reason and caller class is what distinguishes "we protected ourselves successfully" from "we silently dropped 12% of revenue".

// Node: admission control with priority classes, shed before doing work
const LIMITS = { interactive: 120, standard: 60, batch: 10 };
const inflight = { interactive: 0, standard: 0, batch: 0 };

function admissionClass(req) {
  if (req.headers["x-job-type"] === "batch") return "batch";
  if (req.tenant?.plan === "enterprise" && req.method !== "GET") return "interactive";
  return "standard";
}

app.use((req, res, next) => {
  const cls = admissionClass(req);
  if (inflight[cls] >= LIMITS[cls]) {
    res.set("Retry-After", "2");
    loadShed.inc({ class: cls, reason: "inflight" });
    return res.status(503).json({ error: "overloaded", retryAfterMs: 2000 });
  }
  inflight[cls]++;
  res.on("finish", () => { inflight[cls]--; });
  next();
});

// memory leak with extra steps, and it converts overload into a crash.

Backpressure end to end

Backpressure is the property that a slow consumer causes the producer to slow down rather than the buffers to grow. It has to exist at every hop, or the slow hop simply moves. In a message-driven system the signals are consumer lag and broker flow control: a consumer that limits max.poll.records and pauses partitions when its internal queue is full keeps memory bounded and lag visible, while a consumer that reads as fast as it can and buffers in memory eventually dies with an out-of-memory kill and redelivers everything. On Kafka, lag per partition is the backpressure metric and the autoscaling trigger; on HTTP/2 interfaces, flow-control windows and request concurrency limits are the mechanism.

The ultimate limiter is the database connection pool, and it is usually where backpressure is lost: application threads queue in front of a pool of twenty connections with no timeout, so the queue grows to thousands and every request waits minutes. Cap the pool, set a bounded acquisition timeout, and let the rejection propagate upward as a 503. Then scale the pool deliberately and watch the database's own metrics, because a larger pool on a saturated database makes throughput worse, not better.

5.4 Chaos engineering

Deliberately breaking a system in a controlled way is the only reliable way to find out whether its fallbacks, timeouts and alerts actually work — because the failure mode you have never exercised is the one that will surprise you.

Hypothesis, steady state and abort conditions

A chaos experiment is a scientific experiment, not a stunt. Define the steady state first, in metrics that already exist: checkout success rate above 99.5%, p99 below 900 ms, consumer lag under 500. Then state a hypothesis about the injected fault: "if pricing adds 800 ms of latency, checkout p99 stays under 1.5 s because the pricing call has a 400 ms deadline and falls back to the cached price". Then choose a blast radius — one pod, one availability zone, one tenant class, 1% of traffic — and define abort conditions that stop the experiment immediately, such as error rate above 5% for two minutes or the SLO burn rate crossing a threshold. Finally, write down what would prove the hypothesis false and watch for it; an experiment with no falsifiable outcome is just a random outage.

Notification matters as much as the technical setup. Tell the on-call engineers, put a marker in the deploy timeline, and keep the experiment inside working hours with someone watching the dashboards. The point of the exercise is to discover missing fallbacks, misconfigured timeouts and alerts that never fire — not to test whether the incident process works under real pressure, which a scheduled game day can do later with a much wider blast radius.

A failure catalogue worth rehearsing

Certain failures recur in every distributed system and each one exercises a different defence. A pod kill tests restart speed, graceful shutdown and connection draining. Added latency tests timeouts, deadlines and cache fallbacks. Packet loss and partition test retry budgets, idempotency and duplicate handling. A DNS failure tests whether the client caches addresses and whether the failure is fast or a 5-second resolver timeout. A broker slowdown tests lag metrics, consumer backpressure and load shedding. A zone failure tests replica balance and topology spread — and reveals when every replica happens to be in one zone. Certificate expiry tests rotation and the health of the trust chain. Clock skew tests token validation, lease renewals and any logic that depends on now() matching across hosts.

The most valuable experiments are usually the least dramatic: not "kill the whole cluster" but "make one dependency 800 ms slower for a single tenant" and then observe whether the p99 stays inside the SLO, whether the fallback served the user, and whether an alert fired with the right routing. Every such run should end with an updated runbook or a fixed timeout, otherwise the experiment produced no change.

Tooling and safety rails

In Kubernetes, Chaos Mesh and LitmusChaos express faults as custom resources, which means experiments live in Git, run on a schedule and can be reviewed like any other configuration. Measure the experiment, not the injection. The useful outputs are the alerts that fired (and the ones that should have and did not), the fallbacks that worked, the metrics that showed the fault, the runbook steps that turned out to be wrong, and the configuration changes that follow. A team that runs one well-scoped experiment a month and fixes what it finds will out-perform a team that plans a heroic annual game day, because resilience is a property of many small, verified defences rather than one big rehearsal.

6.1 Service discovery

Client-side discovery, server-side discovery and DNS are three answers to the same question, with different trade-offs in coupling, latency and blast radius.

The problem discovery solves

In a platform where instances are created and destroyed by a scheduler, an IP address is not an identity. A caller needs a stable name, a current list of healthy endpoints, and a way to be told when that list changes. Hard-coded addresses or an entries file in a load balancer both fail as soon as the fleet becomes elastic: a rolling deploy replaces every address within minutes, and an autoscaler changes the count constantly. Discovery replaces configuration with a registry that is continuously reconciled against the actual state of the platform.

Client-side versus server-side

With server-side discovery, the caller talks to a stable virtual address and something in front — a Kubernetes Service with kube-proxy or an eBPF dataplane, a cloud load balancer, an Envoy fleet — resolves and balances on its behalf. The client knows nothing about instances, which keeps it simple and language-agnostic; the cost is an extra hop, a component with its own capacity limits, and policy (retries, circuit breaking, mTLS) that must live in the proxy. With client-side discovery, the caller fetches the instance list from a registry and balances locally. There is no extra hop and the client can make smarter decisions — locality-aware routing, per-instance circuit breaking — but every client must implement the logic, and a stale list becomes a client-specific outage. Modern gRPC and Envoy's xDS protocol blur the line: the client is a thin data plane that receives its endpoint list and policy from a control plane.

DNS sits between the two. It is universal and needs no library, which makes it excellent for coarse discovery and terrible for fast failover: records are cached for their TTL, so a dead instance can keep receiving traffic for as long as the resolver caches it. Treat DNS as a level of indirection to a stable name, and use a data plane — a service mesh, an Envoy sidecar, kube-proxy — for the per-request decision.

Health, readiness and the difference that causes outages

Liveness and readiness answer different questions and are frequently confused. A liveness probe asks "is this process beyond recovery, and should it be restarted?"; a readiness probe asks "should traffic be sent here right now?". Making liveness depend on a downstream dependency is a well-known way to convert a dependency outage into a rolling crash loop, because every replica restarts together and the fleet returns cold and unprimed. Readiness, by contrast, may legitimately reflect dependency state — but a readiness probe that requires a dependency means a dependency outage removes all replicas from the load balancer, turning a degraded service into an unavailable one. The usual guidance: liveness checks the process only, readiness checks the service's own ability to serve (warm caches, migrated schema, subscribed consumer) and treats a downstream failure as a reason to serve degraded responses, not to disappear.

Startup also needs care. A service that takes 40 seconds to warm a cache will fail a 5-second readiness probe and be killed repeatedly; a startupProbe with a generous failure threshold covers the cold start, after which the tighter readiness check takes over. Equally, a consumer that is ready to serve reads but has not yet joined its consumer group is a common source of "the deploy lost messages" — subscribe, then become ready.

6.2 Load balancing at layer 4 and layer 7

Which layer balances decides whether you can route by request, retry intelligently, and distribute long-lived HTTP/2 connections — the last of which breaks naive setups badly.

Layer 4 versus layer 7

A layer-4 balancer forwards TCP or UDP connections without interpreting them. It is cheap, protocol-agnostic and adds almost no latency, which makes it the right choice at the very front of a system. But it decides once per connection, so it cannot route by path or header, cannot retry a failed request without re-establishing the connection, and cannot apply per-request policy. A layer-7 balancer terminates or decrypts the request, sees the method, path, headers and protocol, and can therefore route by version, retry a specific request, split traffic by weight, and balance per request rather than per connection. The cost is more CPU, more memory, TLS handling and a component that must be updated.

The gRPC case is where choosing the wrong layer is most damaging. gRPC runs over HTTP/2, which multiplexes many concurrent streams over one long-lived connection, so a layer-4 balancer pins each client to a single backend for the life of that connection. A fleet of twenty replicas can end up with all traffic on one pod while the other nineteen idle, and the golden metrics look bizarre until someone notices that the connection count is 12 and the request count is 80,000 per second. The fixes are all layer-7 or client-side: put an Envoy-family proxy in front (so balancing happens per stream), use a headless service with client-side round-robin, or enable the mesh's per-request balancing. This is also why maxRequestsPerConnection and periodic connection recycling matter for HTTP/2 clients.

Algorithms and their failure modes

Round robin assumes every request costs the same and every instance is equally fast; it is fine for uniform stateless work and poor when some requests take 500 ms and others 5 ms, because queues build unevenly. Least request (or power-of-two-choices, which samples two instances and picks the less loaded) adapts to that variance and is the better default for request-response traffic. Consistent hashing (ring hash, maglev) pins a key to an instance, giving cache locality and session affinity, at the cost of uneven load when the key distribution is skewed and of reshuffling when instances change unless the implementation is designed for it. Locality-aware balancing prefers instances in the same zone or region and spills over only when local capacity is exhausted; it saves cross-zone latency and data-transfer cost, but a poorly configured version can fill one zone and leave the others idle. Slow start ramps traffic to a new instance so a cold JVM or an empty cache is not immediately handed a full share, and connection draining on shutdown is the counterpart that stops in-flight requests being cut off during a deploy.

Health checking is the other half. Active health checks probe an endpoint on an interval and remove failures; passive checks (outlier ejection) observe real request outcomes and eject endpoints producing errors. Both are needed: active checks find dead instances quickly, passive checks find instances that answer health checks but fail real requests. The panic threshold is the safety valve — if too few instances are considered healthy, the balancer resumes sending traffic to all of them, because serving from an unhealthy instance is better than refusing every request.

Balancing during deploys

A rolling update is a load-balancing event, and most "deploy caused a spike of 502s" incidents are a race between the process exiting and the load balancer noticing. The remedy is a graceful shutdown sequence: mark the pod not-ready, wait long enough for the balancer to remove it (a preStop sleep of a few seconds covers propagation in most data planes), then request shutdown inside terminationGracePeriodSeconds, stop accepting new work, drain in-flight requests, and exit. Clients need the same courtesy, which is why HTTP/2 clients should recycle connections and why long-poll or streaming endpoints need an explicit end-of-stream signal rather than a socket close.

6.3 Configuration and dynamic configuration

Three kinds of configuration with three different lifetimes: values baked into the image, values set per environment, and values changed at runtime without a restart. Mixing them up is how a limit ends up needing a deploy.

Image, environment, runtime: where a value belongs

A useful rule is that the image contains everything that is the same everywhere — code, dependencies, default timeouts, schema, and the default value for every tunable — while the environment supplies what differs between deployments: database hosts, credentials, log level, replica counts, feature availability. The image must never contain environment-specific values, because a promoted artefact then behaves differently in each environment and the artefact you tested is not the artefact you shipped. Baking configuration into the image also makes a rollback impossible without a rebuild, and rebuilds are where "we rolled back but it still fails" comes from.

Environment variables are the portable form of per-environment configuration, and they are not sufficient on their own: changing one requires restarting or redeploying, which is a slow path for a value that needs to change during an incident. That is what runtime configuration is for — the small set of values that must change in seconds and that are read continuously: rate limits, circuit-breaker thresholds, feature flags, kill switches, log verbosity for a specific package. Splitting the three deliberately, and stating which category each value belongs to, prevents both extremes: secrets baked into images and timeouts that need a release train to adjust.

Stores and their trade-offs

Where the configuration lives decides how it is reviewed, versioned and rolled out. Kubernetes ConfigMap and Secret objects are the default in-cluster choice, and their critical property is how updates reach the process: a mounted volume is rewritten in place (the kubelet syncs on a delay of up to about a minute), an environment variable never changes without a restart, and a versioned immutable ConfigMap referenced by name is the safest because it makes the change atomic with a new ReplicaSet. Consul KV and etcd support watches, so a process can be notified within milliseconds. Managed stores — AWS AppConfig, Parameter Store, Azure App Configuration, Google Runtime Configurator — add validation, staged rollouts and audit trails. Spring Cloud Config, or any Git-backed config service, adds versioning and review at the cost of another service to run.

Dynamic configuration without an outage

Dynamic configuration is a distributed system in miniature, and it must be treated as untrusted input: parse it, validate it against a schema, and reject anything that fails rather than applying it half-way. A malformed document that sets a concurrency limit to null or zero can take a service down as effectively as a code bug, and the failure appears at the moment of change, which makes it look like a deploy. Validate first, apply atomically (swap the whole configuration object rather than mutating fields one at a time), and keep the last known good copy so a failed refresh is a no-op rather than an outage.

The second discipline is a default that works when the config service is unreachable. A service that refuses to start because the configuration endpoint is down has made configuration a hard dependency of availability, and a service that starts with a wrong default can fail worse. The workable pattern is a compiled-in default for every tunable, an override loaded at startup, and a runtime refresh that must pass validation before it takes effect; the service then behaves correctly at reduced functionality with no configuration service at all. Finally, record every configuration change with who, when and why, and make it as visible as a deploy, because "someone changed a flag" is otherwise indistinguishable from a mysterious behaviour change during an incident.

6.4 Secrets management and rotation

The one value every service needs and none should store: where secrets live, how they reach a process, and how they are rotated without a restart or an outage.

What counts as a secret, and where it must never be

A secret is any value whose disclosure grants access: database passwords, API keys, private keys, tokens, webhook signing secrets and connection strings that contain any of those. They must never appear in the repository (including history), the image layers, a build log, an environment dump, a stack trace, a bug report or a metrics label. A Kubernetes Secret is base64-encoded, not encrypted, so it is only as safe as the etcd encryption configuration and the RBAC around it; that is usually acceptable in-cluster and never acceptable as a portable file checked into Git.

The bootstrap problem is real: a process needs one credential to fetch all the others. The strong answer is to avoid a static bootstrap secret entirely by authenticating the workload with a platform identity — a Kubernetes service-account token projected into the pod, an instance profile, a workload identity federation — which Vault or the cloud provider exchanges for a short-lived, narrowly scoped credential. Where that is not possible, the bootstrap secret is the single value to protect hardest: scoped to one namespace and one role, injected at deploy time, never in the image, and rotated on a schedule short enough that a leak has a bounded lifetime.

Rotation without downtime

Rotation fails when the new credential and the old one cannot coexist. Three properties make it safe. First, overlap: the verifier accepts both the current and the previous version for a period longer than the maximum token or certificate lifetime, so a rotation does not invalidate anything in flight. Second, propagation order: issue the new credential, roll it to consumers, confirm they are using it, and only then revoke the old one — revoking first guarantees an outage. Third, short lifetimes for generated credentials: dynamic database users that live for an hour and are renewed automatically remove the rotation problem for that class of secret entirely, because there is nothing long-lived to leak or forget to change.

Credentials with cryptographic verification need one extra step. A JSON Web Key set is fetched and cached by every verifier, so a new signing key must be published in the JWKS before anything is signed with it, and the old key must remain published until every access token signed with it has expired. A verifier that sees an unknown kid should refresh the key set once and then reject, rather than trusting an unverified key. Certificate rotation follows the same shape, and automation that renews at a third of the lifetime — renewBefore in cert-manager, ACME renewal in the usual automation — removes the class of outage that used to happen every year at the same time.

Findings that recur in reviews

Three patterns account for most API security findings in a microservice estate. First, secrets in environment variables that are logged or echoed by a diagnostics endpoint or a crash handler; the fix is a secret store with a template that injects files rather than environment, plus log scrubbing as a backstop. Second, long-lived tokens with fleet-wide scope, so that one leaked value opens every service; the fix is audience-scoped tokens, per-service identities and short lifetimes. Third, a scanner that finds secrets in the repository only after they were committed, with no rotation in response; the fix is pre-commit and CI scanning (gitleaks, trufflehog) plus a documented rotation runbook that is exercised, because a secret that was merely deleted from the latest commit is still compromised.

7.1 Logs, metrics and traces

Three signals, three costs. Each answers a question the others cannot, and using the wrong one is why an incident takes an hour instead of five minutes.

What each signal is for

Metrics are cheap numeric aggregates sampled at fixed intervals: counters, gauges, histograms. They are the only signal that is affordable to keep for months and the only one that answers "is this normal, and is it getting worse" in under a second. Their weakness is aggregation: a latency histogram tells you that p99 tripled, not which tenant or which endpoint caused it. Traces are the causal structure of one request across services, with a span per operation and its duration. They answer "where did this request spend 4 seconds" and are the single most valuable signal in a distributed system — but only if they are sampled, because storing every span of every request is prohibitive at scale. Logs are discrete events with arbitrary detail. They are the most expensive per byte, the most useful for exact diagnosis ("the request was rejected because the tenant's plan expired"), and useless at scale unless every line is structured and correlated to a trace.

The practical division of labour: metrics to detect and to size, traces to localise, logs to explain. A team that instruments only logs discovers incidents when a customer calls; a team that instruments only metrics cannot explain the spike; a team with traces and no metrics cannot see the spike at all.

Correlation: the thing that turns three signals into one

Correlation is what makes the signals usable together, and it comes from propagating two identifiers on every hop: a trace_id for the trace and a business correlation id where one exists (an order id, a claim reference). Every log line includes both, every metric that can be labelled by a bounded dimension includes the route and the tenant class, and every trace span carries the identifiers so a slow trace can be found from a log line. The boundary that breaks most often is the asynchronous one: a message is published with the current trace context in its headers, a consumer starts a new span linked to that context, and the trace survives a five-minute queue delay. Without that, the consumer's work appears as an unrelated root span and the end-to-end picture disappears.

Cardinality is the constraint to respect. A label with unbounded values — user id, request id, raw URL, free-form error message — destroys the metric backend's memory and query performance. Keep labels to a fixed, small set, and put the unbounded detail in traces and logs, which are built for it.

// Node: one JSON log line per event, carrying trace and business ids
import { trace, context } from "@opentelemetry/api";

function log(level, msg, fields = {}) {
  const span = trace.getSpan(context.active());
  process.stdout.write(JSON.stringify({
    ts: new Date().toISOString(),
    level,
    msg,
    service: process.env.OTEL_SERVICE_NAME,
    trace_id: span?.spanContext().traceId,
    span_id: span?.spanContext().spanId,
    ...fields,                       // bounded, structured, never a raw body
  }) + "\n");
}

Where to send the data

Instrument with an open API and forward through a collector, so the backend is a configuration decision rather than a code change. A collector — OpenTelemetry Collector, Fluent Bit, Vector, Promtail — can batch, redact, sample and route: tail-based sampling decisions happen there, personal data is scrubbed before it leaves the cluster, and the same pipeline can mirror traffic to a second backend during a migration. This indirection is also the cheapest way to control cost, because sampling and retention are configuration rather than re-instrumentation, and cost control in observability is almost entirely about what you choose not to store.

7.2 OpenTelemetry instrumentation

One vendor-neutral API for traces, metrics and logs; automatic instrumentation where it exists, manual spans where it does not, and context propagation that survives asynchronous hops.

The API, the SDK and the protocol

OpenTelemetry separates three layers. The API is what application and library code calls; it is stable and vendor-neutral, so instrumentation written today survives a change of backend. The SDK implements the API and is configured per process: exporters, sampling, resource attributes, batch sizes. OTLP is the wire protocol that carries telemetry to a collector or a backend. The practical consequence is that a library can emit telemetry without knowing where it goes, and the operator decides the destination in configuration — which is the property that finally ended the era of one instrumentation package per vendor.

Auto-instrumentation covers HTTP clients and servers, gRPC, database drivers, Kafka and Redis clients, and most web frameworks, and it is worth enabling because it produces the spans you would otherwise forget (the actual SQL, the actual broker call). Manual instrumentation then covers what only the application knows: business operations with meaningful names and attributes, the steps inside a long operation, and the points where an asynchronous boundary would otherwise break the trace. Name manual spans after the operation in the domain's language — checkout.price_basket rather than compute() — and attach bounded, useful attributes such as tenant_class, route and item_count.

Propagating context across boundaries

Context propagation is the mechanism that makes a trace a trace rather than a collection of unrelated spans. For HTTP and gRPC it is the traceparent header (W3C Trace Context), injected by the client instrumentation and extracted by the server. For messaging it is the message headers, and a Kafka producer must inject them explicitly; the consumer then extracts and starts a new trace segment. The subtlety is that a message may be consumed minutes later by a different process, so the relationship is not parent-child across time but a link: a span that references the producing span while remaining the root of its own trace. That distinction keeps a queue from producing traces that never end while preserving the ability to jump from the consumer to the producer.

Inside a process, propagation is equally easy to lose. Work handed to a thread pool, a callback without context capture, a setTimeout, or a promise chain created outside the active context will start a span with no parent, and the trace silently splits in two. The remedy is the runtime's context-propagation mechanism: Node's AsyncLocalStorage, Java's Context.current().wrap() around submitted tasks, Go's explicit context.Context parameter. Where a library cannot be made to propagate, wrap the entry point of that work in a span whose parent is captured explicitly.

Sampling: head, tail and parent-based

Sampling decides which traces are kept, and it is the only lever that materially controls cost. Head sampling decides at the root, before the trace exists; it is cheap and predictable but blind, so it keeps 1% of everything, including 1% of the errors — usually the 1% you have the least of. Tail sampling buffers spans in the collector until the trace is complete, then applies policies: keep every trace with an error status, keep every trace slower than 800 ms, sample the rest at a low rate. That gives you all the interesting traces and a representative sample of the normal ones, at the cost of buffering memory and a decision delay of several seconds.

Parent-based sampling is the rule that keeps traces whole: a service honours the sampling decision already recorded in the incoming context rather than making its own. Without it, a 100% sampled front end that calls a 1% sampled back end produces traces that are missing most of their spans, which look like slow services that are actually just unobserved. Configure parent-based sampling everywhere, set the base ratio low, and let tail policies do the intelligent selection.

7.3 SLI, SLO and error budgets

Service level indicators measured from the user's side, objectives that define "good enough", and the error budget that converts reliability into a number a product team can spend.

Choosing SLIs users can feel

An SLI is a ratio of good events to valid events, measured where the user experiences the system: at the load balancer or gateway for user-facing journeys, and at the caller for internal ones. The four families that cover most targets are availability (the proportion of requests that succeeded), latency (the proportion that completed under a threshold — always a proportion, never an average), quality (the proportion of responses that were correct or complete, such as a search that returned results), and freshness (the proportion of reads served from data no more than N seconds old, which is the right SLI for a projection-fed read model).

Two definitional traps account for most useless SLOs. First, averaging hides the tail: "average latency 120 ms" is compatible with 5% of users waiting eight seconds, so latency SLIs are always expressed as a proportion under a threshold. Second, the valid-event denominator matters: client errors (4xx caused by the caller) usually should not count against the service's target, but they must not be used to make the numbers look good either — a service that returns 400 for requests it cannot handle has an availability of 100% and no users. Write the SLI's query down, review it with the consuming team, and version it, because an SLI that changes silently invalidates every historical comparison.

Budgets, burn rates and when to page

An objective turns the SLI into a decision: 99.9% availability allows 43 minutes of unavailability per 30-day month. The complement is the error budget, and it is the mechanism that makes reliability a shared concern with the product organisation. A burn rate of 1 means the budget will be exhausted exactly at the end of the window; a burn rate of 14.4 exhausts a 30-day budget in about two days. Alerting on burn rate rather than on instantaneous error rate is what separates a useful page from noise, because a brief spike that consumes almost no budget should not wake anyone.

The standard multi-window scheme uses a fast window and a slow window together to require both a sudden and a sustained problem: 2% of the budget in one hour (burn rate 14.4 sustained over both 5m and 1h) pages, 5% in six hours (burn rate 6 sustained over 30m and 6h) opens a ticket, and 10% in three days (burn rate 1) opens a lower-priority ticket. Requiring both windows to agree filters out the single-minute blip while still catching a slow leak.

Keeping the policy honest

An SLO with no consequences is a dashboard. The budget policy is the part that gives it teeth: when the month's budget for a service is exhausted, feature work pauses and reliability work takes priority until it recovers; when the budget is healthy, shipping aggressively is the correct behaviour, because unused reliability is a cost with no benefit. That policy has to be agreed with the product owner in advance and written down, because the moment it is invoked is the worst possible time to negotiate it.

Internal dependencies need SLOs too, but their consequences are different: an internal service's objective should be at least as strict as what its consumers promise their users, or the arithmetic at the edge will not add up. Where a service is the sole provider of a capability, publish the objective and the current budget status so consumers can decide whether to invest in a fallback, cache or a queue. The final discipline is review: recompute SLO attainment from real data monthly, and change the objective deliberately — either because the user-visible requirement changed, or because the system genuinely cannot meet it — rather than silently lowering it during an incident.

7.4 Dashboards, alerting and runbooks

What to display, what to wake someone for, how to route it to a team that owns the service, and the document that turns a page at 03:00 into a five-minute fix.

Four dashboards per service

A service needs a small, stable set of views rather than a wall of graphs. The overview shows the four golden signals — traffic, errors, latency (as a distribution, not an average) and saturation — plus the SLO status for the current window; it is the first tab anyone opens during an incident. The dependencies view shows, per downstream call, the request rate, error rate, latency and breaker or outlier-ejection state, because most incidents start one hop away. The resources view shows CPU, memory, GC pauses, thread and connection pool utilisation, and file descriptors — the causes rather than the symptoms. A business view shows orders per minute, conversion and payment success, which is what tells you whether the technical incident matters.

Build these as templates parameterised by service name rather than one hand-made dashboard per service, or they will drift: some services will have the new panel, most will not, and the one you need during an incident will be the one without it. Every panel should answer a question someone has actually asked, and any panel nobody has looked at in a quarter should be deleted — an unread dashboard is a maintenance cost and a distraction.

Alert routing, deduplication and ownership

Alerts should page on user-visible symptoms — SLO budget burn, error rate, latency — and ticket on causes such as disk pressure or a certificate expiring in fourteen days. Routing then depends on two pieces of metadata that every alert must carry: the owning team and the service, so the notification reaches people who can act. Grouping by service and alert name prevents one broken dependency from generating eighty separate pages, and inhibition rules suppress the downstream noise: if the payments dependency is down, then the five services reporting elevated errors because of it produce a single actionable page rather than six.

Ownership is not decoration. An alert without an owner is dropped by whoever receives it, and a service without an owner accumulates unactioned alerts until the alerting channel is muted — after which nothing is trusted. Keep the ownership metadata in the repository next to the service definition, generate the routes from it, and treat "this alert has no owner" as a configuration error that fails CI. Measure alert quality with the proportion that were actionable, the acknowledgement time and the fraction of pages that led to a change; an alert that nobody acts on is a defect to be deleted or its threshold fixed.

Runbooks and production readiness

A runbook is written for a tired engineer who did not build the service and is holding a phone. The useful structure is short: what the alert means, the likely user impact, the three queries that narrow the cause, a decision tree (roll back, scale out, fail over, disable a feature flag, escalate), how to verify recovery, and who to escalate to. The alert itself should link to it via an annotation, so the document is one click from the page rather than buried in a wiki. Writing a runbook is also the cheapest review of a system's debuggability: if the first diagnostic query does not exist, that is a missing metric or an unlabelled log, and fixing it takes minutes compared with discovering the gap during an incident.

The last piece is a production readiness review before a service takes real traffic. The checklist is deliberately boring and mechanical: an SLO with dashboards, alerts with owners and runbooks, a rollback path that has been executed at least once, timeouts and retries on every dependency, a bulkhead per dependency, dashboards showing consumer lag, a documented data model and migration path, secrets in a managed store with rotation, and a load test that shows the known capacity limit. Reviewing this before launch is an order of magnitude cheaper than retrofitting it, and every item on the list has an obvious failure mode attached: services without a rollback path stay broken during incidents, and services without dependency timeouts take their callers down with them.

8.1 OAuth 2.1, OIDC and token flows

Delegated authorisation for users: which flow to use in 2026, how tokens are audience-scoped, and why the implicit and password grants are gone.

The flows that survive

OAuth 2.1 consolidates a decade of security guidance into one document, and the practical effect is that three patterns remain. Authorization Code with PKCE is the only flow for user-facing applications, browser or native: the client generates a code verifier, sends its hash with the authorisation request, and proves possession when redeeming the code, which defeats code interception. Client Credentials is for machine-to-machine calls with no user present. Token Exchange (RFC 8693) is for the case where a service holds a token and needs a differently scoped token for a downstream service. The implicit grant is gone because tokens in URLs leak through history, logs and referrers; the resource owner password grant is gone because it trains users to hand passwords to third parties and makes MFA impossible.

OpenID Connect is the identity layer on top: it adds the ID token, a signed JWT that asserts who the user is, and the UserInfo endpoint for profile data. Keep the separation clear — OIDC answers "who is this", OAuth answers "what may this client do on behalf of whom" — because conflating the two is how an ID token ends up being used as an API access token, and an audience that was never intended to accept it does so anyway.

Audience, scope and least authority

Every access token should name the resource it is for in its aud claim, and every resource server should check that claim. Without it, a token minted for one service is a skeleton key for the fleet: any service that can be reached with a stolen or leaked token will accept it, which is exactly the confused-deputy problem. Scope should be coarse enough to remain stable and specific enough to be meaningful (orders:read, orders:write, payments:authorise), and the resource server must enforce it, never the client. A gateway checking scopes is defence in depth; the service checking them is the control.

Token lifetime is the other lever. Short-lived access tokens (5-15 minutes) with a refresh token that rotates on use limit the value of a leaked token and make revocation practical. Refresh token rotation with reuse detection — a rotated token that is presented again means theft, so the whole chain is revoked — is the standard mechanism for exactly this. Long-lived bearer tokens with no rotation are the single most common finding in API security reviews.

Where tokens live, and what that costs

In a browser, the safest place for a refresh token is an httpOnly, Secure, SameSite cookie scoped to the API's domain, with the access token held in memory for the life of the page — the BFF pattern makes this straightforward, because the browser talks only to the BFF and the tokens never touch JavaScript. In a native app the equivalent is the platform keychain. On Android and iOS, PKCE with an app-claimed redirect scheme plus the platform browser is the supported pattern, and embedded web views are explicitly discouraged because the app can read the user's credentials.

8.2 JWT validation, claims and pitfalls

A JSON Web Token is a signed statement, not an authorisation. What the signature proves, which claims must be checked, and the mistakes that turn a convenient token into a skeleton key.

What a signature proves, and what it does not

A JWT is three base64url segments: a header naming the algorithm and key id, a payload of claims, and a signature over the first two. The signature proves that the holder of the signing key issued exactly this payload and that it has not been modified. It proves nothing about whether the token is still valid, whether the subject still has the claimed rights, or whether the presenting party is the legitimate owner — a bearer token is valid for whoever holds it, which is why transport security and short lifetimes matter.

The payload is encoded, not encrypted, so anyone who can see the token can read every claim; personal data, internal identifiers and permission names are all public to whoever intercepts it. Storing a token in localStorage turns any cross-site scripting flaw into full session theft, and putting one in a URL leaks it into history, access logs and referrer headers. Where a token is genuinely needed in a browser, the safer shape is a same-site, httpOnly cookie holding a short-lived session and an access token obtained per request by the backend.

The validation checklist

Verification is a list of checks that all have to pass, in this order: the header's algorithm must be one the service explicitly allows (never trust the header's value, and never accept none), the key must be resolved from the issuer's JWKS by kid with the key type matching, the signature must verify, and then the claims must be checked — iss equal to the expected issuer, aud containing this resource, exp in the future and nbf in the past with a small clock-skew tolerance (60 seconds is typical), and iat not implausibly older than the token's permitted maximum age. Only then are scope, roles or groups read for authorisation. Skipping any single item is enough to defeat the whole scheme, and the classic attacks target exactly the ones people omit: a resource server that never checks aud accepts any token from the same issuer, including one minted for a different service.

// Node with jose: explicit algorithm, issuer, audience, clock tolerance
import { createRemoteJWKSet, jwtVerify } from "jose";

const JWKS = createRemoteJWKSet(new URL("https://id.example.com/.well-known/jwks.json"), {
  cacheMaxAge: 300_000,          // 5 minutes; refresh sooner on unknown kid
  cooldownDuration: 30_000,      // do not stampede the issuer on a bad kid
});

export async function authenticate(req, res, next) {
  const header = req.get("authorization") || "";
  if (!header.startsWith("Bearer ")) return res.status(401).json({ error: "no_token" });

  try {
    const { payload, protectedHeader } = await jwtVerify(header.slice(7), JWKS, {
      algorithms: ["RS256", "ES256"],          // allow-list, never "none"
      issuer: "https://id.example.com/",
      audience: "https://api.example.com",     // rejects other services' tokens
      clockTolerance: "60s",
      maxTokenAge: "15m",
    });

    // authorisation, not authentication: the scope must cover this route
    const scopes = String(payload.scope || "").split(" ");
    if (!scopes.includes(req.requiredScope)) {
      return res.status(403).json({ error: "insufficient_scope" });
    }

    req.identity = {
      subject: payload.sub,
      tenant: payload.tenant_id,       // still verify object ownership later
      scopes,
      keyId: protectedHeader.kid,
    };
    next();
  } catch (err) {
    return res.status(401).json({ error: "invalid_token" });   // never echo err
  }
}

Revocation, key rotation and lifetime

Statelessness is the point of JWTs and also their weakness: a token that has been issued stays valid until it expires, so revocation needs help. Three mechanisms cover most cases. Short access-token lifetimes (5-15 minutes) bound the damage and make revocation a matter of waiting. A deny-list keyed by jti or subject, checked by services that need immediate revocation, handles the emergency case at the cost of a lookup. Refresh token rotation with reuse detection kills the whole family when a stolen refresh token is presented twice. Treat a leaked token like a leaked password: rotate the signing key if it was a compromise of the issuer, and revoke the subject's sessions if it was a compromise of the user.

Key rotation is the other half. Publish a new key in the JWKS with a new kid before signing anything with it, sign new tokens with the new key, and keep the old key published until the longest possible access-token lifetime has elapsed. On the verifier side, cache the JWKS for minutes rather than seconds, and on an unknown kid refresh once with a cooldown before rejecting — a naive implementation that fetches the JWKS on every request turns every verification into a call to the identity provider, and a naive implementation that never refreshes cannot survive a rotation.

8.3 mTLS, service identity and zero trust

Inside the perimeter there is no perimeter: every call is authenticated, encrypted and authorised on its own merits, using workload identities that are issued, rotated and verified automatically.

Zero trust in practice

Perimeter security assumed that anything inside the network could be trusted, which fails the moment one workload is compromised, a contractor has VPN access, or a pod is co-scheduled with someone else's. Zero trust removes network position from the trust decision: every request carries a verifiable identity, is encrypted in transit, and is authorised against a policy that names the caller. The unit of identity is the workload, not the host or the IP — a SPIFFE ID such as spiffe://shop.example.com/ns/shop/sa/orders, derived from the platform's own identity system, or a mesh-issued certificate whose subject encodes the same thing.

Two properties make this practical rather than aspirational. Identities are short-lived and issued automatically, so there is no long-lived key to distribute or forget to rotate; and the cryptography is mutual, so the server verifies the client as well as the other way round, which prevents an attacker who has network access from simply talking to a database port. The mesh or the platform implements it once, in the data plane, so application code does not carry a TLS configuration that only some services get right.

What mTLS buys and what it does not

Mutual TLS gives confidentiality and integrity in transit, and authenticity of both ends of the connection — no impersonation by IP address or DNS name, and no passive reading of service-to-service traffic. It does not authorise: an identity proves who is calling, and a policy still has to decide whether that caller may perform the operation. It does not protect against a compromised service using its own legitimate identity, so least-privilege policies per workload matter as much as the transport. And it stops at your boundary: calls to a third-party API need TLS with certificate validation on the client side (plus an egress control so a compromised workload cannot reach arbitrary hosts), which is the SSRF class of failure covered in 8.4.

The usual implementation shape is that transport identity and application authorisation are separate layers. The data plane enforces STRICT mutual TLS for all in-cluster traffic and rejects plaintext, and an authorisation policy names the allowed principal — for example, only cluster.local/ns/shop/sa/orders may call the pricing service's /v1/quote method. The application then receives a verified identity it can use for finer decisions, such as checking that the caller is allowed to act for the tenant in the request. In a mesh, this is configuration; without one, it is a certificate authority plus per-service TLS configuration, which is exactly the work a mesh automates.

Authorisation is a separate decision

Once identity is solved, authorisation becomes the interesting problem. Role-based checks are enough for coarse functions, but object-level rules dominate real APIs: this order belongs to this customer, this document is in this project, this invoice is for this tenant. Enforce those in the service that owns the data, using the verified identity rather than a user-supplied identifier, and centralise the policy so it can be reviewed and tested — Open Policy Agent, Cedar or an equivalent policy engine evaluated in-process, or a shared library that implements one decision function. The gateway's checks are then a fast pre-filter, not the control, and the failure mode of a bypassed route is a rejected request rather than an unauthorised read.

8.4 The OWASP API Top 10 in a microservice estate

API-specific failure modes, in the order they are actually found in reviews, and the controls that address each — most of which are authorisation and inventory problems rather than cryptography.

The failure modes, in order of frequency

Broken object level authorisation is the most common serious finding: the endpoint checks that the caller is authenticated and that the token has the right scope, then loads order by an id from the path without checking that the order belongs to the caller's tenant. It is trivially exploited by incrementing an identifier, and it is invisible to a unit test that only exercises the happy path. Broken authentication covers everything from accepting tokens from the wrong audience to weak password reset flows to API keys committed in a mobile app. Broken object property level authorisation is the "mass assignment" and "excessive data exposure" pair: an endpoint that binds the request body onto an entity lets a caller set role: admin or isVerified: true, and an endpoint that returns the whole entity leaks fields the client was never meant to see — the fact that the UI hides them is not a control.

Unrestricted resource consumption is any endpoint where cost is attacker-controlled: unbounded pagination, a search endpoint that can trigger hundreds of downstream calls, image resizing without pixel caps, an export that reads a whole table. Broken function level authorisation is the equivalent of object-level but for operations: an internal admin endpoint reachable with a normal user token because only the UI hid the button. Unrestricted access to sensitive business flows covers abusable flows — bulk account creation, referral farming, scraping via the search API, ticket scalping — which are business rules rather than vulnerabilities, so they need detection and throttling rather than a patch. Server-side request forgery appears wherever a service fetches a URL a user supplied, including webhooks, image imports and PDF renderers, and in a microservice estate it is especially dangerous because the service can reach the internal network. Security misconfiguration, improper inventory management (shadow APIs, forgotten versions, an old gateway route pointing at a decommissioned service) and unsafe consumption of third-party APIs complete the list.

Making the controls testable

The reason broken object authorisation survives so long is that it is only detectable by trying to do the wrong thing. Write tests that attempt it: for each endpoint that takes an identifier, call it as a user from tenant A with tenant B's identifier and assert a 404 (not a 403, which confirms existence) — parametrised over every route, generated from the API schema so a new route cannot be added without the test. Do the same for property-level rules by sending extra fields and asserting they are ignored, and for function-level rules by calling every route with a token that has no scopes and asserting rejection. A contract test that asserts the required scope per operation, run in CI, is what keeps the policy from drifting as the API grows.

Then watch production for the patterns a scanner cannot see: a single subject reading objects for many tenants, a burst of 404s on identifier-shaped paths (enumeration), a client whose request rate is orders of magnitude above the median, an egress destination never seen before. These are cheap to compute from the telemetry in chapter 7 and are the difference between finding a leak from an alert and finding it from a customer report. Keep the response for the incident ready too: revoke the credential or session, rotate the signing key or secret, determine the window of exposure from the access logs, and notify per the applicable regime — decided in advance, because deciding it during the incident is how notifications become late.

Secrets, rotation and the incident that follows a leak

A leaked credential is the most likely way an attacker enters an estate that has otherwise correct authorisation, so the rotation machinery in 6.4 is a security control, not hygiene. Keep lifetimes short, keep scopes narrow, and make the runbook for a suspected leak concrete: identify which credential and which scope, revoke it, rotate the replacement, search the access logs for the credential's use from unexpected sources, and confirm that no privileged action was performed in the window. If the credential is a signing key, revoke the tokens signed with it by rotating the key set rather than waiting for expiry; if it is a database password, the credential's grant should be narrow enough that the blast radius is a single schema.

9.1 Containers and Kubernetes

A container image is the unit of deployment; Kubernetes is the reconciler that keeps the running system equal to the declared one. Both have constraints a microservice must respect.

An image is an interface, not a snapshot

The point of a container image is that it is immutable, content-addressed and identical everywhere, which removes "works on my machine" from the class of possible failures. Three disciplines make that true in practice. Pin base images by digest rather than a mutable tag, so a rebuild does not silently pick up a different base. Build a single process per container and run it as a non-root user with a read-only root filesystem where possible, so a compromised process has nowhere to write. Keep the image minimal — a distroless or slim base reduces the CVE surface more than any scanner — and keep the build reproducible: same input, same digest, so a rebuild of an unchanged commit produces the artefact already tested.

The container also imposes the first real constraint on a microservice: it must start fast, it must shut down gracefully on SIGTERM, and it must not hold state in the filesystem. A service that takes two minutes to warm a cache makes every deploy a two-minute availability dip; a service that ignores SIGTERM makes every deploy drop in-flight requests; a service that writes to its own filesystem loses that data on the next scheduling event.

What Kubernetes actually guarantees

Kubernetes is a reconciliation loop: you declare the desired state and controllers work continuously to make the world match it. It does not guarantee ordering, exactly-once delivery of events, or that a pod lives long. It guarantees that if you ask for three replicas, it will keep trying to have three. That is a meaningful and limited promise, and most operational surprises come from assuming more: within a single Deployment, replicas are interchangeable and unordered, a pod's IP changes on restart, and process restarts are normal rather than exceptional.

The objects that matter day to day are few. A Deployment for stateless services; a StatefulSet where stable network identity or ordered startup is required; a Service for a stable virtual address; a ConfigMap and Secret for configuration; an Ingress or Gateway API resource for external traffic; a PodDisruptionBudget to stop a voluntary disruption from taking out the whole fleet; and topology spread constraints or anti-affinity so replicas are not all on one node or in one zone. Resource requests and limits are not optional: without requests the scheduler packs pods blindly, and without limits one service can consume a node's memory and take its neighbours down with it.

Shared infrastructure you no longer control

Once services run on a shared cluster, the cluster itself is a dependency with its own failure modes: the API server's availability during a control-plane upgrade, the CNI's capacity for concurrent connections, the ingress controller's reload behaviour, the node autoscaler's latency when the last pending pod needs a new node. Capacity has to account for the fact that a new replica may take a minute to arrive, which is why minReplicas is a resilience setting rather than a cost setting. And a cluster upgrade is a maintenance window in disguise: node drains, DaemonSet restarts and a temporary capacity dip in every service at once, which is worth rehearsing in staging before the control plane forces it.

9.2 Service mesh

A data plane per workload plus a control plane that configures it: mutual TLS, per-request balancing, retries and telemetry applied uniformly without touching application code.

What a mesh does, and where the value actually is

A mesh moves the cross-cutting concerns of chapter 5 and 8 out of libraries and into the platform: STRICT mutual TLS with automatic certificate issuance and rotation, per-request load balancing for HTTP/2 and gRPC, timeouts, retries, outlier ejection, traffic shifting by weight, fault injection, and uniform request metrics and traces for every call. The value is greatest in a polyglot estate, where a Java library, an Node library and a Go library would otherwise each implement these differently and drift; with a mesh, one configuration applies to all of them, and the policy is reviewable in one place.

Two deployment models dominate in 2026. The sidecar model injects a proxy container into every pod, which gives full L7 policy for every protocol but costs memory and CPU per pod and requires pod restarts to add or upgrade. The ambient model splits the data plane: a per-node proxy handles mTLS and L4 policy for everything, and an L7 proxy is deployed only where a workload needs L7 features. That removes the per-pod overhead and the restart requirement for most workloads, which for many teams is what makes adopting a mesh practical rather than aspirational. Linkerd takes the opposite design bet — a small, fast Rust micro-proxy with a deliberately narrow feature set — and its simplicity is a feature: fewer knobs, less to operate, fewer ways to misconfigure the data plane.

When a mesh is the wrong answer

A mesh is infrastructure, and it is worth its cost only when the concerns it centralises are otherwise paid repeatedly. If the estate is one language with a good, already-adopted client library, the library may be sufficient: client-side load balancing, retries and metrics from a well-maintained SDK cover the same ground with no extra hop and no control plane. If the workloads speak protocols that are not HTTP, gRPC or TCP with a known framing, the mesh can provide mTLS and little else. And if nobody can operate it — upgrade the control plane, roll the data plane, debug a rejected request — a mesh will be installed, misconfigured, frozen at an old version and eventually removed, taking its security properties with it.

Where the estate is heterogeneous, large, or has a compliance requirement for uniform transport security, the mesh earns its keep quickly, and the deciding factor is usually the mTLS story rather than traffic shifting. The pragmatic adoption path is to enable mutual TLS first, watch it for a release cycle, then add traffic policy, and only then use features like fault injection in a controlled namespace. This order matters because mTLS either works everywhere or produces an intermittent class of failure that is hard to attribute.

Operating a mesh

The mesh is a dependency with its own upgrade path, and the data plane must be upgraded progressively: control plane first (which is usually backward compatible with the previous data plane version), then the workloads, namespace by namespace, while watching the error rate. A frozen data plane becomes a security problem, because certificate rotation, protocol fixes and CVEs in the proxy all require it to move. Give the proxies explicit resource requests and limits — an unbounded sidecar can starve the application after a traffic spike — and decide deliberately whether the sidecar should be included in the workload's readiness or its resource budget.

Observe the mesh itself, not only what flows through it: certificate expiry and rotation failures, control-plane configuration push errors, rejected requests by policy, and the difference between connection-level and request-level metrics (a healthy TCP connection to an unhealthy service shows as zero requests, which looks like no traffic at all). The failure mode that surprises teams most is the mesh becoming a silent traffic cop — a policy pushed to all namespaces that denies a legitimate internal call produces 403s that look like application authorisation bugs. Version the policy, review it like code, and keep a break-glass path to relax a policy in production, with the change logged like any other.

9.3 Blue/green, canary and progressive delivery

Reducing the blast radius of a release: two environments and an instant cutover, a small percentage of live traffic, or a deploy that is not a release at all because a flag decides.

Strategies and what each one costs

A rolling update replaces instances gradually within one environment. It is cheap and needs no extra capacity, and its rollback is another rollout, which takes as long as the first. Blue/green keeps two complete environments: traffic switches from blue to green in one step, so rollback is a switch back and takes seconds, at the cost of double capacity and the risk that a single cutover moves all traffic onto an unproven version at once. A canary sends a small percentage — 1%, then 5%, then 25% — to the new version and compares it with the old on live traffic, which catches problems that only appear under real load and real data; it requires traffic splitting, a metric comparison and an automated decision. Shadow or mirror traffic sends copies of live requests to the new version while discarding its responses, which validates read paths and performance without affecting users, provided the new version's side effects are suppressed. Feature flags separate deployment from release: the code is running in production, dark, and a configuration change turns it on for a cohort. That is the fastest rollback available (a flag flip, no deploy) and the hardest to keep clean, because flags accumulate and stale flags become dead code with a configuration surface.

Reading the signals during a rollout

A canary is only as good as its analysis. Compare the cohorts on the same window and the same traffic mix: error ratio, p99 latency, saturation, plus at least one business metric (checkout completions, payment authorisations) because a technically healthy release can still be wrong. Require enough data before deciding — a 1% canary needs thousands of requests before an error-rate difference is meaningful — and stop the rollout automatically on a threshold breach rather than waiting for a human to notice. Tools such as Argo Rollouts and Flagger implement exactly this loop: weight the new version, query a metrics provider, and promote or roll back based on the result.

Schema compatibility is the part that most teams miss. While two versions receive traffic at once, both must work against one database schema, so a migration must be backward compatible in both directions: add a nullable column, backfill, switch reads and writes to the new column, then remove the old one in a later release (the expand/contract pattern). A destructive migration executed during a canary will break the old version that is still serving 95% of traffic, and the rollback will then fail because the data is gone. Treat every schema change as a multi-release programme rather than a single step, and gate the migration with a check that the previous version's queries still run.

Deploy is not release

Splitting deployment from release is the most valuable discipline in this chapter. Deploying code that is inert behind a flag removes the deployment risk from the release decision: the risky moment becomes a flag flip that can be reversed in seconds, and the release can be staged by cohort — internal users, then 1% of customers, then everyone. Two rules make flags safe. Every flag has an owner and an expiry date, and stale flags are deleted on schedule, because a feature flag that has been on at 100% for nine months is dead code multiplied by a configuration surface. And every flag has a kill switch, a documented way to disable the feature completely without a deploy, tested at least once before it is needed.

Blue/green remains the right answer when the change is infrastructural rather than behavioural — a new runtime version, a new database engine, a change to the mesh or the ingress — because it makes the unit of rollback the environment itself. The combination that covers most estates is: rolling or blue/green for the deployment, a canary with automated analysis for anything risky on the request path, and feature flags for behaviour. Each additional mechanism costs configuration and discipline, so adopt them in that order as the cost of a failed release grows.

9.4 GitOps

The desired state of every environment lives in Git, and a controller continuously reconciles the cluster to match it. The pull request becomes the change-management record.

The reconciliation model

GitOps inverts the direction of deployment: instead of a pipeline pushing manifests into a cluster, an agent in the cluster pulls the desired state from a repository and applies it, repeatedly, forever. The controller's continuous reconciliation is the important part, because it also detects drift — a manual kubectl edit, a deleted resource, a value changed by a mutating webhook — and corrects it back to the committed state. That makes Git the single source of truth not by convention but by enforcement, and it makes "what is deployed in production" answerable by reading a commit rather than by querying the cluster and hoping the answer is complete.

Argo CD and Flux are the two dominant implementations, with largely equivalent capability and different emphasis: Argo CD has a rich UI and an application-centric model, Flux is a set of composable controllers with an emphasis on automation and image-update workflows. Both support pull-based sync from a Git repository, health assessment before a sync is considered complete, hooks for ordering, and notifications. CI's job in this model becomes narrow and clear: build the image, run the tests, push the artefact, and open a pull request that changes the image digest in the environment's manifests. Deployment authority lives with the repository, not the pipeline.

Repository structure and promotion

Two layouts are common. A single repository per application, containing the manifests for all its environments, keeps an application's changes together and makes ownership obvious. A monorepo containing every application and the platform configuration makes cross-cutting changes atomic and dependency visible, at the cost of a busier review queue and more access control. Either way, environments are directories or overlays, not branches: a long-lived branch per environment produces merge conflicts and divergent histories, and it hides what differs between environments. Kustomize overlays or Helm values files per environment express the differences, and a promotion is a pull request that changes the image digest in the next environment's overlay — reviewed, and auditable in one place.

Secrets never live in the manifests. The pattern that works is a secret manager plus a controller: either a sealed-secret tool that encrypts values for one cluster's key (SOPS with age, Sealed Secrets), or an external-secrets controller that syncs from Vault or the cloud provider at runtime. The first makes the encrypted value reviewable in Git; the second keeps the plaintext out of Git and out of etcd. Either way, the bootstrap credential for the controller is the one secret to protect hardest, because it is what lets the cluster decrypt everything else.

Guardrails and failure modes

The most common operational surprise is auto-sync undoing an emergency change: an engineer scales a deployment or edits a ConfigMap to relieve an incident, the controller reconciles it back within a minute, and the incident worsens. The remedies are procedural rather than clever — pause auto-sync for the application as an explicit, logged action, or make the fix in the repository first and let the controller apply it, which is slower but leaves a record. Disable auto-prune in production until the ownership and labelling are right, because prune with a misconfigured path deletes real resources, and set ignoreDifferences deliberately for fields another controller legitimately owns, such as the HPA's replica count.

Be equally clear about what GitOps is not. It is not a backup: the cluster's persistent data, its certificates, and its etcd contents are not in the repository, so a disaster recovery plan still needs etcd snapshots and data backups with tested restores. It is not a substitute for access control, because a repository that anyone can merge to is a production credential. And it does not eliminate the need for a break-glass path: keep a documented, audited procedure for changing production when the controller or the Git provider is unavailable, and rehearse it, because the moment you need it is the moment you least want to improvise.

10.1 Vertical, horizontal and statelessness

Growing up is simpler than growing out, but it has a ceiling and a cost curve. Growing out requires the state to live somewhere other than the process.

Vertical first, then horizontal

Vertical scaling — a bigger machine — is the cheapest change available: no code change, no distributed failure modes, no consistency problem, and it buys time to find the real bottleneck. Its limits are the instance size the provider offers, the price curve, which is super-linear at the top end, and the fact that a single machine is a single failure domain. Upgrading in place also usually requires downtime unless the platform supports live migration, so the practical use of vertical scaling is as a deliberate stopgap with a date attached.

Horizontal scaling — more instances — removes the failure-domain problem and in principle has no ceiling, but only for work that can be partitioned. The three things that block it are state in the process, ordering requirements and shared resources. A service that keeps sessions in memory cannot be scaled safely without sticky routing; a consumer that must process events in order is limited by the partition count; and any component with a single shared instance, usually the database, becomes the bottleneck that more application replicas only make worse by adding contention. That last point is why adding replicas sometimes reduces throughput: more concurrent connections to one saturated primary means more lock waits and context switching, not more useful work.

Where state hides

Statelessness is not a property a service has; it is a property maintained by moving every piece of state to a component that is designed to be shared. The common hiding places are obvious and not: HTTP sessions, in-memory caches that are assumed to be complete, local rate-limit counters, scheduled jobs that assume exactly one instance runs, in-flight file uploads written to a container filesystem, WebSocket connections pinned to a pod, and sequence numbers generated from a local counter. Each of these works perfectly on one instance and breaks subtly on two: duplicate emails, a rate limit multiplied by the replica count, a scheduled job running four times.

The standard remedies are a shared session store, a distributed cache, a shared rate-limit counter or a deliberate per-instance limit, leader election or a database advisory lock for scheduled work, object storage for uploads, and an external pub/sub fan-out for socket notifications. Each introduces a dependency with its own latency and failure mode, so the honest trade-off is that horizontal scaling converts in-process state into a network call: fast, simple and fragile becomes slower, more complex and survivable. Where a service genuinely cannot be made stateless, sticky sessions are acceptable for a bounded period, provided the loss of a pod is understood as a lost session rather than a data-loss incident.

10.2 The cache hierarchy

Each layer absorbs a different kind of traffic: the edge absorbs repeatable public reads, the application layer absorbs hot keys, the database absorbs sequential access through its own buffers.

What each layer is for

A CDN or edge cache removes traffic from the origin entirely, which is the cheapest scale available because it costs nothing per request at the origin. It suits immutable assets, public content, and cacheable API reads — a product page, a catalogue listing, a public profile — with a TTL measured in seconds to hours depending on how much staleness the business tolerates. Application-level caches come in two forms: an in-process cache (fast, free, but per-replica and therefore inconsistent across replicas and cold after every deploy) and a distributed cache such as Redis or Memcached (shared, consistent, at the cost of a network round trip and another dependency). Database caches are mostly invisible: the buffer pool, the query plan cache, materialised views and covering indexes. They are not an alternative to the layers above, but they are why a warm database is dramatically faster than a cold one, and why a restart during high load produces a latency cliff.

The layering rule is to cache as close to the client as possible and as coarsely as correctness allows. Caching inside one service helps that service only; caching at the edge helps every service behind it. The cost of a layer is proportional to its invalidation difficulty, and staleness tolerance is what decides where a value belongs: a price that must be exact in a checkout flow belongs in the request path, while the same price on a marketing page can be five minutes old.

Invalidation, TTLs and stampedes

Every cache has one of two invalidation strategies: expire by time, or invalidate explicitly when the source changes. TTLs are simple and self-healing but always stale by up to the TTL; explicit invalidation is fresh but requires every writer to remember to do it, and the writer that forgets is the bug that ships. The pragmatic pattern combines them — a short TTL as the safety net, plus explicit invalidation from the events that change the data — so a missed invalidation degrades to a short staleness window instead of a permanent inconsistency. Where reads are far more common than writes, invalidation by publishing an event that deletes the key is usually cheaper than recomputing on write.

The failure that takes systems down is the stampede: a popular key expires and every concurrent request misses at once, so the origin receives N simultaneous identical queries. The remedies are a lock or single-flight so that one request recomputes while the others wait, stale-while-revalidate so an expired value is served while a refresh happens in the background, jittered TTLs so keys do not expire in lockstep, and a small negative cache for misses to stop a flood of lookups for something that does not exist. A related failure is the cold start: after a deploy or a cache restart, every replica misses everything, which can be more traffic than the origin has ever seen — a reason to keep cache TTLs long, warm critical keys deliberately, and rate-limit the refill.

const redis = createClient({ url: process.env.REDIS_URL });
const inflight = new Map();          // key -> Promise

async function cachedProduct(sku) {
  const key = "product:v3:" + sku;
  const hit = await redis.get(key);
  if (hit === "__miss__") return null;             // negative cache
  if (hit) return JSON.parse(hit);

  if (inflight.has(key)) return inflight.get(key);  // stampede protection

  const p = (async () => {
    const product = await db.findProduct(sku);
    if (!product) {
      await redis.set(key, "__miss__", { EX: 5 });       // short negative TTL
      return null;
    }
    const ttl = 60 + Math.floor(Math.random() * 30);      // jitter: no lockstep
    await redis.set(key, JSON.stringify(product), { EX: ttl });
    return product;
  })().finally(() => inflight.delete(key));

  inflight.set(key, p);
  return p;
}

// Invalidate from the event stream, not from the write path, so a writer
// that forgets cannot leave a key stale forever; the TTL is the backstop.

  await redis.del("product:v3:" + evt.sku);
}

What must never be cached

Anything whose correctness depends on who is asking is a security trap. A response that varies by authorisation must either be excluded from shared caches or be keyed on something that cannot be spoofed — and keying a CDN on an Authorization header usually produces the worst of both worlds: a near-zero hit ratio plus a class of cache-poisoning bugs where one user's response is served to another. The same applies to Vary headers taken from client input, cache keys built from unvalidated paths, and any cache shared between tenants. The safe default is that shared caches hold only public, identical-for-everyone data; anything authenticated is either uncacheable or cached in a store the caller cannot reach.

10.3 Read replicas, sharding and partitioning

Replicas multiply read throughput at the cost of a consistency gap; shards multiply write throughput at the cost of cross-shard queries and a rebalancing problem.

Read replicas and the consistency gap

A read replica is a continuously applied copy of the primary that serves reads. It scales read throughput, and it also moves the read workload away from the primary's CPU and locks, which helps writes as a side effect. The gap is replication lag: with asynchronous replication the replica is behind by milliseconds under calm conditions and by seconds or minutes under load, during a bulk backfill, or after a network hiccup. Applications that are not designed for that produce the classic support ticket — a customer saves a change, reloads, and sees the old value, then reloads again and sees the new one.

The standard remedy is a bounded read-your-writes guarantee: after a write, either read from the primary for a short window, or record a token (a log position, a monotonic version, a timestamp) and route the request to a replica that has caught up past it, falling back to the primary if none has. Lag must be monitored per replica and used as a routing input, because a replica that is an hour behind should be taken out of rotation rather than serving stale data silently. The other caveats are capacity and failure: replicas add read capacity but their promotion on primary failure takes time and may lose the last transactions with asynchronous replication, which is exactly the trade-off chapter 10.4 formalises.

Sharding: choosing the key

Sharding splits the data itself, so each shard holds a subset of rows and each node handles a fraction of the writes. Everything depends on the shard key. A tenant or customer id gives natural isolation, keeps each tenant's data together, and makes most queries single-shard — until one enormous tenant creates a hot shard. A time-based key gives excellent write distribution for append-heavy data but makes recent data a hotspot and queries that span time ranges fan out. A hash of a synthetic id distributes evenly but destroys range queries and locality. There is no key that is good at everything, so the decision must come from the dominant query pattern, and where two patterns conflict, a directory-based approach (a separate lookup that maps an entity to a shard) allows remapping individual hot entities without a full resharding.

Two operational realities decide whether sharding is viable. First, cross-shard queries stop being free: a join across shards becomes an application-side merge or a denormalised read model built by consuming events. Second, resharding must be planned from the beginning, because the original shard count becomes a ceiling — the standard mitigation is to shard into many more logical partitions (virtual nodes) than physical nodes, so partitions can be moved between nodes as the fleet grows. Managed distributed databases — Vitess, Citus, MongoDB's sharded clusters, CockroachDB, Spanner and its analogues — implement this machinery, and adopting one is usually cheaper than writing it, provided the query patterns suit the engine's constraints.

Scaling the write path before sharding

Sharding is the last resort, because it constrains every future query. Several cheaper steps usually come first. Batch and coalesce writes — accumulate increments in the application and flush them, which turns thousands of row updates into a handful, and is the standard technique for counters and view counts. Shorten transactions so row locks are held for microseconds rather than seconds; long transactions are the most common cause of write throughput collapse. Move expensive work out of the transaction: compute and validate before opening it, and emit events rather than performing cross-aggregate updates inside it. Use the fastest storage available for the write-ahead log — an NVMe device or provisioned IOPS changes the ceiling dramatically. Where the workload is append-heavy, an event log or an append-only table can replace in-place updates entirely, with the current state derived into a projection.

What is left after those steps is usually a genuine volume problem, and then the question is whether to shard the data or to shard the responsibility: splitting one overloaded service into two that write to separate databases (which is a decomposition decision, chapter 1) is often cheaper than sharding one table, because it does not constrain query patterns across the whole domain.

10.4 CAP, PACELC and consistency choices

CAP names a real trade-off but is widely misquoted: it applies during a partition, and the choice is made per operation rather than per system.

What CAP actually says

Consistency, availability and partition tolerance cannot all hold simultaneously. Since every distributed system experiences partitions — a slow network, a lost packet, a garbage-collected pause long enough to look like a failure — partition tolerance is not optional, so the real choice during a partition is between refusing to answer (consistency) and answering with the possibility of divergence (availability). This is a per-operation decision, not an architectural label: a single system can be consistent for a payment authorisation and available for a product listing, because the first is worth failing and the second is worth serving slightly stale. Calling a system "CP" or "AP" at the level of the whole architecture is what makes the framework useless.

PACELC extends it to the normal case: if there is a partition, trade availability against consistency (the CAP part), else trade latency against consistency. Even with no failure, a strongly consistent write that must be acknowledged by a quorum or replicated synchronously across regions costs latency, while an asynchronously replicated write is fast and may be lost on failover. That "else" branch is where most real design decisions live, because partitions are rare and latency is constant.

Consistency models you can use

Between "linearizable" and "eventually consistent" there is a spectrum of models that are cheap to implement and match what users actually notice. Read-your-writes guarantees that a user sees their own change, which is the property that turns a support ticket into a non-event. Monotonic reads guarantee that a user does not go backwards in time, observed as a counter that decreases or a list that loses an item just added. Causal consistency guarantees that a reply never appears before the message it answers. Bounded staleness quantifies the window ("reads are at most five seconds old") and can be enforced by refusing to serve data older than the bound. Session guarantees such as these are far more achievable than global ordering and cover the overwhelming majority of user-visible complaints.

Deciding per operation

The workable process is to name the consistency requirement of each operation explicitly, in the API contract: a payment authorisation is linearizable, a balance check is read-your-writes, a product listing is bounded-stale at five seconds, and a recommendation is eventually consistent with no visible promise. That declaration then drives the implementation — quorum reads, primary routing, cached reads, replicas — and it gives you something to test and to alert on. Where the choice cannot be made now, default to read-your-writes for anything a user just changed, because it removes the most damaging class of perceived bugs at a small cost in latency.

11.1 The event backbone

One broker, many producers, an operational contract between teams. The choices that are hard to reverse are partitioning, retention and topic naming.

Log-based brokers and why they won

A partitioned log keeps messages after they are consumed and lets each consumer group track its own position. That single property — retention plus independent offsets — is what makes the pattern work at the scale of an organisation: a new consumer can be added and process the entire history without asking anybody to republish, a bug fix can be deployed and the affected window replayed, and consumer groups do not interfere with each other. It also means the broker is a system of record for a period of time, which is a responsibility that a queue does not carry: retention is a policy decision that determines how far back a replay can go, and it costs storage that must be budgeted.

The price is operational weight. Log brokers require careful capacity planning for disk, sensible partition counts, rebalance behaviour that does not stall consumers, and an understanding of how replication, in-sync replicas and acks interact with durability. Managed offerings remove much of that, at the cost of less control over retention and partition placement.

Choosing a backbone

The choice is usually made once for the whole organisation, because running two backbones means two sets of tooling, two operating models and a permanent bridge between them. The selection criteria that matter in practice are throughput per partition, the retention and tiered-storage model, ordering and delivery semantics, the connector ecosystem, multi-tenancy isolation, and the operational burden the team can actually absorb.

Name events for the fact, not the consumer: shop.orders.order.placed.v1, following a domain.aggregate.event.version convention (or the CloudEvents type field with the reverse-domain form). Partition count is the parallelism ceiling for a consumer group, and it can be increased but never decreased, so a topic created with one partition becomes a single-threaded consumer until someone migrates it. A practical rule is to start with enough partitions for the expected consumer fleet multiplied by a small factor, sized so that one partition's throughput stays comfortably inside what a single consumer can handle. The partition key decides ordering and distribution at once: key by aggregate id for per-entity order, key by tenant for locality — and check the distribution, because a low-cardinality or skewed key produces a hot partition that throttles the entire topic. Compaction is the other per-topic policy worth deciding early: a compacted topic retains the latest record per key, which makes it suitable as a state store or a materialised view (11.4), while a delete policy by time is the right default for event streams.

11.2 Schemas, contracts and governance

An event's schema is a public interface with unknown consumers. A registry turns "we think nobody reads that field" into an enforced, testable rule.

Why schemas must be managed

Any topic that more than one team consumes has a contract, whether or not it is written down. Without a registry the contract is discovered the hard way: a producer removes a field that "nothing uses", a consumer's deserialiser starts throwing at 02:00, and the event is stuck in a retry loop. A schema registry makes the contract explicit and, more importantly, a durable artefact that production and consumption can be checked against — the schema is stored per subject (usually topic-value and topic-key) and referenced by an id embedded in each message, so a consumer can deserialise even after the subject's latest version has changed.

The registry's useful feature is compatibility enforcement. Backward compatibility lets new consumers read data written with the previous schema (adding a field with a default, removing an optional field). Forward compatibility lets old consumers read data written with the new schema (removing a field, adding an optional one). Full requires both, which is the correct setting for a topic with consumers you do not control and is slightly more restrictive to evolve. Compatibility must be configured deliberately per subject, because the default varies by deployment and a permissive setting on a shared topic is an incident waiting for a quiet afternoon.

Evolving an event safely

Most evolution is additive and can be done without ceremony: add a field with a default, deploy consumers first, then start populating it. The changes that must never be made silently are removing a field in use, renaming one, changing a type, tightening validation, changing a field's semantics while keeping its name, and reordering fields in a positional format such as Avro's binary encoding or Protobuf's field order — the last of which is why Protobuf numbers its fields and reserves retired ones. Where a genuinely incompatible change is required, the escape hatch is a new event version: a new topic (...placed.v2) or a new type, published alongside the old one for one migration window, with consumers moving over deliberately and the old topic retired on a date.

Two disciplines keep this from drifting. First, an event carries an envelope with metadata — id, type, version, source, occurred-at, trace id, correlation id — separate from the domain payload, so the transport-level concerns can evolve without touching the business fields. Second, publishing is governed: a topic has an owner, a published schema and a documented meaning, and publishing to it is a change that goes through review like any other interface. AsyncAPI can express this as a machine-readable document, which gives the same benefits the OpenAPI document gives for REST: generated documentation, validation and drift detection.

Enforcing the contract in CI

A registry is only useful if nothing can bypass it, so the checks belong in the pipeline: every producer's pull request runs a compatibility check against the latest registered version and fails on an incompatible change, and every consumer's test suite deserialises a corpus of recorded events from the previous version. That corpus is the cheap part that pays for itself — a fixture directory of real events, one per version ever published, replayed through the consumer in tests. It catches the exact class of failure that registries miss: a field that is compatible at the schema level but whose meaning changed, or a consumer that assumed a value would never be null.

Keep the governance light enough to survive. One owner per topic, one published schema, a compatibility mode chosen on purpose, an AsyncAPI document where consumers need it, and a rule that a breaking change requires a new topic rather than a negotiation. Teams that attempt a heavyweight event-governance board usually end up with shadow topics that bypass it entirely, which is a worse outcome than a convention enforced by a CI check.

11.3 Delivery, ordering and replay

A log gives per-partition order and at-least-once delivery. Replay is the superpower and the hazard: reprocessing history is only safe when effects are idempotent by design.

What a log guarantees, precisely

Order is per partition, so two events about the same order are ordered only if they share a key and therefore a partition; nothing guarantees ordering across keys, and nothing guarantees it at all once a consumer processes messages in parallel. Delivery is at-least-once by default: a consumer that crashes after applying a record and before committing its offset reprocesses that record on restart, and a rebalance that moves a partition to another consumer causes the records already fetched but not committed to be redelivered. The idempotent producer removes broker-side duplicates caused by retries, and transactions extend that into exactly-once semantics within Kafka: a consumer can apply its work and commit its offsets in the same transaction, so the pair is atomic. What transactions cannot do is make an external side effect — a database write, a payment, an email — part of that atomic unit, which is why the handler still has to be idempotent (chapter 2.4).

Consumer group mechanics deserve attention because they are the most common source of mysterious duplicates. A group with more consumers than partitions leaves some consumers idle. A consumer that exceeds max.poll.interval.ms while processing stops being considered alive, so the group rebalances and its partition moves to a peer, which then reprocesses from the last committed offset. That is why long per-record work should be handed to a worker with its own queue, or why the consumer should poll with fewer records and commit more often — the trade-off being more commits, which is cheaper than repeated rebalances.

Replay and reprocessing

Replay is the reason to keep a log: a bug is fixed, the affected window is reprocessed, and the projection converges without asking anybody to republish. Doing it safely needs four things. Retention must cover the window you intend to replay — 7 days of retention cannot fix a bug that ran for 30. The consumer must be reset explicitly and per group, never by wiping a shared topic. Side effects must be suppressed or idempotent, because a replay will re-send emails, re-charge cards and re-emit notifications if the handler does them unconditionally; the standard mitigations are an idempotency key derived from the event id and a rule that a replay runs against a projection-only consumer or with outbound effects disabled by a flag. And the replay must be rate-limited, because a consumer that catches up from zero as fast as it can will overload the database it writes to; a deliberately throttled replay that takes four hours is better than one that takes twenty minutes and takes the production database with it.

A useful discipline is to rehearse this before you need it: replay a day of events into a fresh projection, compare it row by row with the live one, and record the difference. That single exercise validates retention, idempotency, throughput and the correctness of the projection, and it is the same test that chapter 4.4 recommends for the convergence question.

Poison events without blocking the partition

Ordering and error handling are in direct conflict. A consumer that stops on a bad record to preserve order blocks every subsequent event for that key, which for a high-volume topic means the whole partition stalls and lag grows without bound. The usual resolution is a retry ladder with increasing delays — immediate, then 30 seconds, then minutes, then hours — followed by a dead-letter topic, all of which keeps the partition moving while giving transient failures time to clear. The trade-off, stated plainly, is that strict ordering is temporarily broken for the key whose event failed: the later events for that aggregate may be processed first. Where that is unacceptable, the aggregate must carry a version and the consumer must reject stale or out-of-order updates (the monotonic guard in chapter 2.4) rather than relying on arrival order.

Whatever scheme is chosen, the dead-letter topic is only useful if someone looks at it: alert on its depth and on its rate, include the original topic, key, offset and failure reason in the headers so a replay is possible, and document the replay procedure. A DLQ that nobody monitors becomes a graveyard where failed business events accumulate silently until a customer notices that their order never shipped.

11.4 Stream processing and materialised views

Turning an event stream into continuously maintained state: stateful operators, event-time windows and watermarks, and the decision between streaming and batch.

Stateful stream processing

Stateless processing (map, filter, route) is easy and covers a surprising amount of integration work. Stateful processing is what enables counting, joining and aggregating across a stream, and it introduces the hard parts: state must be persisted and recovered, results depend on time, and events arrive late. Frameworks such as Kafka Streams, Flink, Spark Structured Streaming and Pulsar Functions solve this by keeping operator state in a local store backed by a changelog topic, so a failed task can restore its state from the log; windowing is expressed explicitly, and the framework handles the bookkeeping. Kafka Streams additionally supports exactly-once semantics by tying state updates and offset commits into one Kafka transaction.

Time is the concept that surprises newcomers. Processing time is when the event was handled; event time is when it happened, and it is the one business reports care about. Event-time windows need a watermark: an estimate of how far behind the stream currently is, used to decide when a window can emit and be forgotten. Late events then fall into a defined category — with a grace period they update the window, after which they are dropped or routed to a side output. Choosing a grace period is choosing how long you are willing to hold a window open, which trades completeness against state size and result latency; two hours is common for operational aggregates, while financial aggregates often need a day or more and sometimes a reconciliation job instead.

Materialised views as read models

A stream processor that maintains an aggregate is a projection builder that happens to be always-on, and its output — a compacted topic or a table in the serving database — is a read model of the same kind as chapter 4.5 describes. Two properties make it useful. First, because the view is derived from a log, it can be rebuilt from scratch by starting a new consumer group at the earliest offset, which is the recovery path when a bug corrupts it. Second, the same mechanism can serve the view locally: an interactive-query service can load a compacted topic into a local store (Kafka Streams' global store, or an in-process cache) and answer queries at memory speed with no database round trip, at the cost of holding a copy of the data in every instance.

Operationally, the questions are rebuild time, state size and cost. A rebuild that takes eleven hours is a real recovery-time objective, so a large projection is often backed by a periodic snapshot plus a tail of events, so a rebuild starts from the snapshot rather than the beginning. State size caps how large a single processor's store can grow, which drives partition counts and instance sizing. And the compute cost of an always-on processor is paid whether or not anything is happening — a real bill, and the main reason to keep a small, purposeful set of stream processors rather than turning the backbone into a general-purpose compute platform.

// Kafka Streams: a windowed, event-time aggregate with grace and final emission
StreamsBuilder builder = new StreamsBuilder();

KStream<String, OrderPlaced> placed = builder.stream("shop.orders.order.placed.v1",

When batch is still the right tool

Streaming is not automatically better than batch. Batch is cheaper per record, deterministic on rerun (no dependence on arrival order or processing time), easier to reason about, and simpler to operate for anything that is not needed within minutes. A nightly job that reconciles payments, computes tax summaries or refreshes a warehouse does not need a stateful cluster running continuously, and making it streaming usually adds cost and a new failure mode in exchange for nothing. The honest split is by freshness requirement: operational counters and fraud signals need streaming; analytics, finance and reporting usually need a scheduled job plus a warehouse, where the joins that were destroyed by decomposition can be performed across all domains at once.

The pragmatic architecture most organisations settle on keeps both: a backbone with a small number of stream processors for low-latency projections, and a batch or lakehouse layer that consumes the same topics (or their compacted snapshots) for anything analytical. The important thing is that both derive from the same events, so the two views cannot disagree about what happened — only about how fresh they are.

12.1 The test portfolio

Unit, component, contract and end-to-end tests each prove something the others cannot. The failure mode is investing in the wrong layer and paying for it in build time and flakiness.

What each layer proves

A unit test exercises pure logic in memory in milliseconds: pricing rules, state machines, validation, mapping. It is the cheapest place to test the combinatorial surface of business rules, and it should be the majority of the count. A component test runs one service with its real dependencies — a database in a container, a broker, an in-memory queue — and asserts its behaviour through its own API. It catches the failures unit tests cannot: SQL that does not parse, a transaction that does not commit, a serialisation mismatch, a migration that breaks the repository layer. A contract test asserts that two independently deployed services agree on their interface, and it is the layer that replaces a combinatorial explosion of integration tests. An end-to-end test drives a real deployment through a user journey and proves the wiring: authentication, routing, configuration, the mesh, the database, everything at once.

What only end-to-end can prove

No amount of unit testing proves that the token issued by the identity provider is accepted by the gateway and forwarded in a form the service's authorisation policy understands; that the secret was mounted; that the migration ran before the new pods started; that the mesh's mutual TLS is enforced rather than merely configured; or that the message published in one cluster reaches the consumer subscribed in another. Those are facts about an assembled system, and they can only be established by running one. The corollary is that end-to-end tests must be few, chosen for the journeys whose failure is unacceptable, and run on the merge path only for those; everything else can run nightly or before a release, where a fifteen-minute suite is acceptable.

Where no environment is production-like, the value of end-to-end tests collapses and the honest response is to invest in the layers below plus production verification: synthetic transactions that exercise the critical journey against the live system on a schedule, canary analysis that compares cohorts on real traffic, and alerts on the business metrics that reveal a broken journey before a customer reports it. A test environment that shares a database with staging and has no realistic data will produce false confidence and constant flakiness.

Keeping the suite fast and trustworthy

Test duration is a product decision, because it sets how often change can be integrated. Three techniques keep a suite inside a few minutes: run tests that share a dependency set in one container (start Postgres once per worker, not once per test), parallelise by test file with a per-worker schema or database so tests cannot collide, and make the deterministic things deterministic — inject a clock instead of reading the system time, generate ids from a seeded factory, and never depend on the order of a test run. An ephemeral environment per pull request, created from the same manifests production uses, gives real topology without shared mutable state, and its tearing down is part of the pipeline's cost model.

Flakiness must be treated as a defect with an owner, not tolerated with retries. A retry policy hides a real race or a real ordering assumption, and it teaches the team that red is negotiable. The workable policy is to quarantine a flaky test automatically (move it to a nightly-only set), raise a ticket, and require a fix or a deletion within a short window — a quarantined test that is never fixed is deleted after two weeks, because a permanently skipped test is just a comment.

// Component test: the service, its real database, and its real HTTP API

Coverage, in the only sense that matters

Line coverage measures which statements were executed, not which behaviours were checked, and it is trivially gamed by asserting nothing. The coverage questions worth asking about a microservice are behavioural and countable: does every route have an authorisation test that tries the wrong tenant, does every event type have a consumer that handles a duplicate and a stale version, does every dependency have a test that simulates its failure and asserts the fallback, and does every migration have a test that runs it against the previous release's schema. Those lists are short, verifiable and directly connected to the incidents the system has actually had. Keep them as a checklist per service and review them at the readiness review described in 7.4.

12.2 Consumer-driven contract testing

A contract test replaces the N-squared integration matrix with a per-edge assertion: each consumer declares what it needs, the provider proves it still delivers it, and the pipeline refuses a deploy that would break a known consumer.

Why the integration matrix collapses

With eight services each calling three others, a full pair-wise integration suite is twenty-four combinations to build, run and keep current, and every new consumer multiplies the cost. A contract test inverts the direction: the consumer writes a test against a mock that records the exact requests it makes and the responses it expects, producing a machine-readable contract; the provider replays those recorded interactions against its real running code and fails if the response no longer matches. The matrix becomes one contract per edge, owned by the team that depends on it, and the provider learns about a breaking change in its own pipeline instead of in someone else's production.

The recorded interaction is deliberately shallow — a status code, a few chosen fields, a shape — because a contract asserts compatibility, not behaviour. Asserting an entire response body turns the contract into a snapshot that every irrelevant field change invalidates, and a contract that fails for irrelevant reasons gets disabled, which is worse than not having one.

Writing the consumer side

The consumer test runs entirely in memory against a mock server that Pact (or Spring Cloud Contract, or the provider's own recorded-fixture tool) starts for it. No broker is needed and no provider is running, so the test is milliseconds fast and can run on every commit.

// JS — the consumer's half of the contract for a pricing call
import { PactV3, MatchersV3 } from "@pact-foundation/pact";
const { like, decimal, string } = MatchersV3;

const provider = new PactV3({
  consumer: "order-service",
  provider: "pricing-service",
  dir: "pacts",
});

test("order-service asks pricing for a quote", async () => {
  provider
    .given("sku-1 exists with a base price")
    .uponReceiving("a quote request for two units")
    .withRequest({
      method: "POST",
      path: "/v1/quotes",
      headers: { "Content-Type": "application/json" },
      body: { sku: "sku-1", qty: 2, currency: "USD" },
    })
    .willRespondWith({
      status: 200,
      body: {
        quoteId: string("q_9f"),
        total: decimal(19.98),          // matches any decimal, not this value
        currency: like("USD"),
        expiresAt: string("2026-10-15T12:00:00Z"),
      },
    });

  await provider.executeTest(async (mock) => {
    const client = new PricingClient(mock.url);
    const quote = await client.quote("sku-1", 2);
    expect(quote.total).toBeGreaterThan(0);
  });
});

Verifying the provider and gating the deploy

The provider pipeline runs the recorded interactions against a real instance — an in-process server or a live test environment — and publishes the verification result to a broker alongside the provider's version. can-i-deploy then asks the broker whether the version about to ship satisfies every contract that a currently deployed consumer expects. That query is the whole point: it turns "is this change safe to release" from a human judgement into a lookup, and it has to gate the deploy step rather than sit in a dashboard.

# shell — provider verifies every contract, then asks the broker
pact-verifier \
  --provider-base-url http://localhost:8081 \
  --pact-broker-base-url https://broker.internal \
  --provider-app-version "$(git rev-parse --short HEAD)"

# gate: nothing ships unless every deployed consumer is satisfied
pact-broker can-i-deploy \
  --pacticipant order-service \
  --version  "$(git rev-parse --short HEAD)" \
  --to-environment production

Where contracts break down

Three failure modes recur. First, a contract that asserts too much becomes brittle, so keep matchers loose and assert only the fields the consumer reads. Second, a broker left un-pruned accumulates thousands of obsolete versions and can-i-deploy starts returning verdicts about consumers that no longer run; configure a retention policy and delete the contracts of decommissioned consumers. Third, a provider that verifies only at release time discovers a break weeks after a consumer merged, so verification must run on every provider build. Contracts are the wrong tool for a consumer that genuinely needs the provider's full semantics — a GraphQL gateway or a reporting export — because those are contracts of convenience rather than of interface; model them as an explicit, versioned API instead.

12.3 Integration testing with real dependencies

Mocks assert what you believe a database does; a container asserts what it does. Testcontainers puts the real engine, broker and cache in the test process without a shared environment.

Why an in-memory substitute lies

SQLite in place of Postgres accepts a schema Postgres rejects, ignores isolation behaviour, and has no JSONB, window functions or SKIP LOCKED. An in-memory broker has no persistence, no consumer groups and no ordering guarantees, so a test that passes proves the handler is wired, not that the message will arrive. The defects that reach production in a distributed system are overwhelmingly of this class: a column type that truncates, a transaction that does not isolate, a requeue that loops, a charset that mangles an emoji. A container costs a few seconds per suite and removes an entire category of false confidence, which is why Testcontainers — a library that manages real Docker containers from the test process — has become the default for component tests.

Lifecycle and reuse

Starting Postgres per test is far too slow, so start one per test file or per worker, migrate it once, and hand each test either a transaction it rolls back or a schema it drops. Reuse across files only works while nothing is shared: the moment two suites write to the same database, the suite becomes order-dependent and flaky, and order-dependent failures are the hardest kind to diagnose.

A realistic component test needs the service plus its database plus the broker and sometimes the identity provider. Compose them the way production does, but let the test framework own the network: Testcontainers puts every container on a shared network and exposes a dynamic port, so nothing is pinned to 5432 and parallel suites cannot collide. Where the topology is already described in a compose file, point the library at that file rather than duplicating it, so the test environment and the local developer environment cannot drift apart.

# shell — one throwaway stack per test run, torn down after
docker compose -f docker-compose.test.yml up -d --wait
trap 'docker compose -f docker-compose.test.yml down -v' EXIT

# the same compose file a developer runs locally
export DATABASE_URL="postgres://app:pw@localhost:55432/orders?sslmode=disable"
export KAFKA_BOOTSTRAP="localhost:59092"
npm run test:component
Never point a test suite at a shared team database. A test that truncates a table is one careless filter away from destroying a colleague's fixture data, and the resulting rule — "do not run this suite" — removes it from the pipeline within a month.

Fixtures, migrations and teardown

Run the application's real migrations rather than restoring a dump, because a dump stops tracking the schema the moment it is taken and the migration is itself on the critical path to a deploy. Seed data through the public API or through small, explicit factories so the fixture exercises the same validation production does. Guarantee teardown: containers leak volumes and ports when a suite crashes, so wire cleanup to the test runner's exit hook and reclaim orphans at the start of the next run. Assert on observable state — rows that exist, messages on a topic — rather than on which methods were called, because a test coupled to implementation calls fails on every refactor and is eventually rewritten to assert nothing.

12.4 Performance, soak and chaos in the pipeline

Load tests answer "how fast" and "how far"; soak tests answer "what leaks"; fault injection answers "what happens when it breaks". All three are only useful when they have a budget to fail against.

Load, stress and spike ask different questions

A load test drives the expected peak to establish headroom and to catch the regression a large code change introduced. A stress test keeps increasing until something breaks, and the interesting output is which thing broke first — the connection pool, the database's write lock, the sidecar's memory — because that is the capacity limit to plan against. A spike test jumps to peak instantly rather than ramping, which is the only way to see whether autoscaling reacts before the queue drains into a timeout cascade. A soak test runs at a moderate rate for hours to expose the slow defects: a growing cache, a subscription that is never closed, a file handle per request, a leak that only appears after ten thousand messages.

None of it is meaningful without a budget. Fix an SLI first — p99 latency under a stated load and error rate below a stated percentage — and make the run fail when the budget is missed, otherwise the report is a chart nobody reads. Run the same script against every release so the result is comparable over time, and record the software version alongside each result.

// JS — k6: a ramping load profile with SLO thresholds
import http from "k6/http";
import { check } from "k6";

export const options = {
  scenarios: {
    peak: {
      executor: "ramping-arrival-rate",
      startRate: 20,
      timeUnit: "1s",
      preAllocatedVUs: 50,
      stages: [
        { target: 200, duration: "2m" },   // ramp to peak
        { target: 200, duration: "5m" },   // hold
        { target: 0,   duration: "1m" },   // ramp down
      ],
    },
  },
  thresholds: {
    http_req_failed:   ["rate<0.01"],     // under 1% errors
    http_req_duration: ["p(99)<300"],     // p99 under 300 ms
  },
};

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/v1/catalogue?limit=20`);
  check(res, { "status is 200": (r) => r.status === 200 });
}

Soak and leak detection

A soak test is a load test with a long tail and a memory assertion. Watch resident memory and goroutine or thread count across the whole run; a staircase that never comes back down is a leak, and it will surface in production as a restart every few days that everyone has learned to ignore. Point the run at a container with a realistic memory limit rather than a laptop, because a leak that matters is one that crosses the limit, and the limit is what the orchestrator enforces. Feed the soak from a queue that is never fully drained so backpressure accumulates, and assert that the service sheds load rather than growing its in-flight count without bound.

Fault injection as a gate, not a rehearsal

Chaos engineering is only engineering when the experiment has a hypothesis, a steady-state measurement and a pass/fail result. In the pipeline the cheap version is a fault proxy in front of a dependency during a component test: inject latency, drop the connection mid-response, or return a 503 for ten seconds, and assert that the caller's circuit breaker opened and its fallback produced an acceptable response.

# YAML — a bounded fault-injection step in a build pipeline
- name: dependency failure drills
  run: |
    toxiproxy-cli create pricing --listen 0.0.0.0:9001 --upstream pricing:8080
    for model in latency timeout reset; do
      toxiproxy-cli toxic add pricing --type "$model" --attribute latency=2000
      npm run test:resilience -- --only pricing || exit 1
      toxiproxy-cli toxic remove pricing --toxicName "$model"
    done

In production the same idea runs as a scheduled experiment with a blast-radius limit and an abort condition: kill one replica of the recommendation service during business hours, with a dashboard open and a rollback command ready, and watch whether the system degrades gracefully or the error budget burns. Start with a dependency that is genuinely optional and non-transactional; injecting a fault into the payment path before retry and idempotency behaviour is proven is how a drill becomes an incident. Every experiment should end by either hardening the system or recording why the failure is acceptable — an experiment that changes nothing was a rehearsal.

13 · Migration and evolution

13.1 The strangler fig13.2 The anticorruption layer and seam symmetry13.3 Versioning APIs and events13.4 An incremental migration playbook

Greenfield descriptions stop before the hard part: moving a working monolith to services without a rewrite, and evolving interfaces that consumers you do not control already depend on.

13.1 The strangler fig

Route traffic to the old system until a slice of behaviour is reimplemented behind the same edge, then flip that slice and delete the old code. The router, not the rewrite, is the mechanism.

Why a big-bang rewrite loses

A rewrite has to reach feature parity before it can take a single real request, so it delivers no value for the whole duration, and the requirements move while it is being written. A strangler fig does the opposite: the existing system keeps serving, one capability at a time is built alongside it, and a routing layer decides which requests go where. The old system shrinks until nothing calls it and it can be deleted. The invariant that makes this safe is that the edge contract does not change — consumers keep the same URLs and payloads while the implementation behind them is replaced, so no client is forced to migrate on the same day.

The name comes from the vine that grows around a host tree and gradually replaces it. The property that matters is reversibility at every step: at no point is the old system switched off before the new one has proven itself on real traffic, and every step can be undone by changing a route rather than by restoring a database.

Choosing the seam and the router

The first slice should be the capability with the cleanest boundary, the fewest inbound dependencies and a real reason to exist separately: a search path, a notification fan-out, a reporting read model. Put the router where one already exists if possible — an API gateway, a reverse proxy, an edge load balancer that can route by path. Reaching into the monolith to branch on a feature flag is a fallback, not a design, because it couples old and new code in one process and one deploy.

# nginx — split by path: search to the new service, everything else to the monolith
upstream monolith { server monolith:8080; }
upstream searchsvc { server search-service:8080; }

server {
  listen 80;

  location /v1/search {
    proxy_pass http://searchsvc;
    proxy_set_header X-Request-Id $request_id;
    proxy_next_upstream error timeout http_502 http_503;   # bounded failover
    proxy_connect_timeout 1s;
    proxy_read_timeout 3s;
  }

  location / {
    proxy_pass http://monolith;
    proxy_set_header X-Request-Id $request_id;
  }
}

Routing at the data layer, and the fallback

Writes are harder than reads because two stores now hold the same truth. The workable pattern is one writer at a time: either the old system owns the write until cutover and the new service keeps a projection current from the old system's change log, or the new service owns the write and dual-writes into the old schema while it is still authoritative. Whichever direction, there must be a single owner at any instant and a reconciliation job that compares the two and reports drift; a divergence found three weeks later is the failure that ends these projects.

Leave the old path runnable for rollback. A cutover that cannot be reverted by one routing change will not be attempted on a Friday, and the freeze that follows is its own cost. Write the removal criterion down before the work starts — zero requests on the old path for fourteen consecutive days — or the "temporary" branch outlives the team that wrote it.

-- SQL — nightly reconciliation: count and sample the rows the two stores disagree on
WITH differences AS (
  SELECT o.id
  FROM   orders_legacy  o
  FULL JOIN orders_new  n USING (id)
  WHERE  o.id IS NULL
      OR n.id IS NULL
      OR o.status      IS DISTINCT FROM n.status
      OR o.total_cents IS DISTINCT FROM n.total_cents
)
SELECT count(*) AS drifted_rows FROM differences;

-- the migration is only done when this count is stable and explainable
SELECT id, status, total_cents FROM differences ORDER BY id LIMIT 20;

13.2 The anticorruption layer and seam symmetry

A boundary that is never translated leaks the other model's vocabulary into your domain until the two are one system again. The anticorruption layer is the code that stops that, and it needs to exist on both sides of an edge.

What an anticorruption layer translates

An anticorruption layer (ACL) is an adapter that converts a foreign model into your own at the boundary: transport shapes, field names, enums, error codes, identifier formats and, above all, concepts. The simple case is a field named customer_id becoming a typed CustomerId. The valuable case is a legacy status column carrying eleven values that mean four things; the ACL is the single place that decides the mapping, so when the legacy system changes an enum your domain is untouched and the compiler points at the one adapter to update. Without it, the legacy vocabulary spreads through your entities, and every future change to either side becomes a change to both.

// TypeScript — the ACL is the only file that knows the legacy shape
type LegacyStatus = "A" | "P" | "S" | "X" | "D";     // the provider's vocabulary

export interface Order {
  id: OrderId;
  state: "open" | "paid" | "shipped" | "cancelled";  // our vocabulary
  total: Money;
}

export function fromLegacy(row: LegacyOrder): Order {
  return {
    id: new OrderId(row.order_no),
    state: mapState(row.status),
    total: Money.fromMinorUnits(row.amount_cents, row.currency),
  };
}

function mapState(s: LegacyStatus): Order["state"] {
  switch (s) {
    case "A": case "P": return "open";
    case "S":           return "paid";
    case "X":           return "shipped";
    case "D":           return "cancelled";
    default: throw new UnmappedStatusError(s);   // fail loudly, never guess
  }
}

Where it lives and who owns it

Place the ACL at the edge of the consumer, in the consumer's repository, because the consumer is the party that cares about the translation and must be free to deploy it. A shared integration library sounds efficient but recreates the coupling it was meant to remove: two teams editing one import, one version to bump, a release train instead of a boundary. Duplicate the small amount of mapping code rather than sharing it — a forty-line adapter copied into two services is cheaper than a library with two owners and three versions in production.

Seam symmetry and the cost of a thin seam

A boundary has two directions, and translating only inbound is the common half-measure: requests are mapped, but the service returns its own internal DTO, so the caller must understand the provider's model anyway. Symmetry means the provider publishes a deliberate contract — its own versioned schema, not a serialisation of an internal class — and the consumer translates in both directions. The test of a good seam is that the shared vocabulary is a small, explicit, versioned artefact and nothing else. If two services share an entity class from a common library, they are not separated by a seam; they are separated by a compile-time dependency and a release schedule.

asyncapi: 3.0.0

13.3 Versioning APIs and events

A version is not a number in a URL; it is a promise about what will not change. Decide which changes are compatible, then pick the cheapest mechanism that enforces the promise.

Compatible and breaking changes

Adding an optional response field, adding an optional request field, and adding an endpoint are backward compatible. Removing or renaming a field, changing a type, tightening validation, making an optional field required, changing a default, and changing status codes or error shapes are breaking. Protobuf has a decidable vocabulary for this: sequential field numbers, reserved ranges, optional and repeated fields, and preservation of unknown fields. The discipline is to treat the wire format as a schema with rules, not as whatever the current language happens to serialise — a class rename can become a field rename on the wire without anyone intending it.

# shell — a breaking change should fail the pull request, not production
oasdiff breaking api/openapi.yaml api/openapi.main.yaml \
  --fail-on ERR \
  --format text

# examples it flags: removed field, type change, new required parameter,
# enum value removed, response code removed.
# Exit code 1 stops the build; the author fixes the contract or writes the
# expand/contract migration instead.

Mechanisms, cheapest first

Prefer, in order: make the change compatible; use expand/contract, where the new field ships first, consumers migrate, and the old field is removed after a deprecation window; version the media type or the path only when a change genuinely cannot be made compatible. Path versioning (/v2/) is the bluntest tool and multiplies the surface that must be maintained, so reserve it for a break worth two parallel systems. Never change the meaning of an existing field in place: consumers silently apply the old meaning, and the resulting data corruption is discovered by accounting, not by a test.

-- SQL — expand/contract in three releases, never one
-- Release 1: expand. Both columns exist; writes fill both, reads use old.
ALTER TABLE orders ADD COLUMN total_minor bigint;
UPDATE orders SET total_minor = round(total * 100) WHERE total_minor IS NULL;

-- Release 2: migrate readers to total_minor, backfill any stragglers,
-- add a constraint once the values agree.
ALTER TABLE orders ALTER COLUMN total_minor SET NOT NULL;

-- Release 3 (after the deprecation window): contract.
ALTER TABLE orders DROP COLUMN total;

Versioning events, where there is no request to negotiate

An event is a stored, replayable fact, so its version must be carried in the payload rather than inferred from an endpoint, and old events stay in the topic forever. Keep a schema registry as the source of truth and set compatibility per subject: BACKWARD for events a consumer replays from the beginning of a topic, FULL where producers and consumers deploy independently and either upgrade order must work. The registry is what turns "do not break consumers" from a rule in a wiki into a check that rejects a bad schema at the producer's build rather than at 2 a.m.

# shell — the registry refuses an incompatible schema at build time
curl -s -X POST "$REGISTRY/subjects/order-value/versions" \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data @schema.json

# 409 Conflict → the change is incompatible with BACKWARD mode.
# The valid moves: add an optional field, add a default, or
# create a new subject (order-value-v2) and run both during migration.

13.4 An incremental migration playbook

The order of operations decides whether a migration is reversible. Parallel-run, shadow traffic, cutover and decommission are separate steps, each with its own exit criterion.

The sequence, and why shadowing comes before cutover

First freeze the seam: write the contract the new service must satisfy and confirm it against real production traffic. Then build the new service behind a disabled route. Then shadow: mirror a copy of live requests to the new service and compare responses while discarding its writes; disagreements are the specification. Then parallel-run for writes, with the new service writing to a shadow store that a reconciler compares. Then canary a small percentage of real traffic, then cut over with a rollback that is one routing change, and finally decommission — remove the old path, the dual-write, the comparison job and, last, the old code.

The step most often skipped is shadow comparison, because it is work with no visible feature — and it is exactly the step that finds the twenty differences between the old and new implementations before a customer does.

# shell — shadow comparison: replay a real request to both, diff the essential fields
REQ='{"customerId":"cus_1","sku":"sku-1","qty":2}'

old=$(curl -s -X POST http://monolith/v1/quotes -d "$REQ")
new=$(curl -s -X POST http://pricing-new/v1/quotes -d "$REQ")

# compare only what the consumer reads: total and currency
diff <(echo "$old" | jq -S '{total,currency}') \
     <(echo "$new" | jq -S '{total,currency}') \
  || echo "MISMATCH for $REQ"   # collect, then triage as a specification gap

Measuring progress and deciding when to stop

A migration needs a progress measure that is not "story points closed": the share of traffic served by the new path, the number of remaining call sites in the monolith, and the count of reconciler differences trending to zero. Set a deadline for the decommission step and make it someone's explicit task, because the last five percent — the batch job, the admin screen, the report — has no customer asking for it and will otherwise be maintained in two places indefinitely.

Keeping the old system honest

The monolith cannot keep changing underneath a migration, or the target moves faster than the work. The practical rule is a change freeze on the migrating capability: new behaviour is built in the new service, and the monolith receives only fixes. Publish that rule to the whole team, because a single feature merged into the old path during a cutover resets the shadow comparison and can invalidate a week of verification. Where a change is unavoidable, land it in both implementations in the same change and note it in the migration log, so the reconciler's difference count stays meaningful.

14 · Anti-patterns and pitfalls

14.1 The distributed monolith14.2 The shared database14.3 Nano-services14.4 Cycles and unclear ownership

Most failed microservice programmes do not fail because a pattern was wrong; they fail because a pattern was applied without the discipline that made it work. These are the recurring shapes of that failure.

14.1 The distributed monolith

Everything is deployed in its own container, but every release requires four services to ship together. The topology is distributed; the coupling is not.

The symptoms

A distributed monolith has all the operational cost of microservices and none of the independence. The tell-tale signs are a release train that deploys several services at once, a shared library whose version bump forces a coordinated release, synchronous chains of four or five calls per request, and a "deploy everything" pipeline because the services inherit each other's schemas. Another sign is a team that cannot answer "what can I deploy on its own today?" without looking at a spreadsheet. The architecture diagram shows boundaries; the deployment graph shows one unit.

The root cause is almost always decomposition by layer or by technical function rather than by business capability. A user-service, an order-service and an inventory-service are capabilities only if each owns its data and can change independently; if the order flow calls all three synchronously and each mutates the others' tables, splitting them into processes removed nothing but the local function call.

The chatty interface

Distribution makes an N-call interface expensive: each hop adds latency, a failure mode and an entry in the trace. A screen that needs customer, orders and inventory should not fan out from the client or the gateway through three services one field at a time; a backend-for-frontend or an aggregation endpoint should compose them, and the read model should be shaped for the screen rather than for the database. A useful measurement is fan-out per request: if a single page view produces more than a handful of synchronous service calls, the boundary is in the wrong place or a read model is missing.

# shell — find the chatty paths: count spans per trace, worst first
# (requires a tracing backend; here, a local Jaeger query)
curl -s "http://jaeger:16686/api/traces?service=gateway&limit=200" \
  | jq -r '.data[]
      | [ .traceID,
          (.spans | length),
          ([.spans[].process.serviceName] | unique | join(","))
        ] | @tsv' \
  | sort -k2,2nr \
  | head -20

# A trace with 40 spans for one page view is the signature of a
# synchronous chain that should be an aggregated read model.

What to change

Convert a synchronous chain into an asynchronous one where the result is not needed in the response, and into an aggregated read model where it is. Move ownership so each service writes only its own data and other services react to its events. Then break the coordination itself: replace the shared entity library with published contracts, and require every service to be deployable on its own with only backward-compatible changes. If a genuine atomic operation spans two capabilities, that is a sign they are one service, not two — merging them back is the correct and often avoided fix.

14.2 The shared database

Two services reading and writing the same tables are one service with two deployables. The schema becomes an undeclared, unversioned public API, and every migration is a cross-team event.

Why it defeats the point

A shared database couples the services at the strongest possible point: the schema. Every team can break every other team by changing a column, and no one can migrate without coordinating. It also prevents the freedom to pick a storage engine for the access pattern — a key-value store for sessions, a relational store for ledger data, a search index for the catalogue — because there is one database and it must serve all of them. The immediate symptom is deploy-time coupling; the latent one is that no service can be tested in isolation, so component tests become integration tests against a shared environment.

Incremental extraction

You do not need to migrate the data in one weekend. Start by making one service the sole writer of a table and having it publish changes as events; other services build their own projections from those events and read their projection instead of the table. Then revoke the read grants, one consumer at a time. A change-data-capture connector can publish changes from the existing table while the new owner is built, so the old readers keep working during the transition. Finish by moving the table to its owner's own store and deleting the grants.

-- SQL — the transition, without a big bang
-- 1. One writer. Every other service loses INSERT/UPDATE/DELETE.
REVOKE INSERT, UPDATE, DELETE ON orders FROM analytics_svc;
GRANT  SELECT ON orders TO analytics_svc;   -- reads still allowed, temporarily

-- 2. The owner publishes changes; consumers build projections.
--    (Debezium/CDC reads the write-ahead log and emits to the bus.)

-- 3. Revoke the reads once each consumer has a live projection.
REVOKE SELECT ON orders FROM analytics_svc;

-- 4. Drop the cross-schema foreign keys that encode the old coupling.
ALTER TABLE analytics_events DROP CONSTRAINT analytics_events_order_fk;

Exceptions that are not exceptions

Three cases are often cited as needing a shared database and two of them are not. A read-only analytics replica is a legitimate exception if it is fed by replication and no service writes to it for its own operation, but it is a coupling of convenience and must be treated as one. Reference data — country codes, currency tables — is better served by a versioned dataset each service loads than by a shared table. The genuinely shared thing is usually the concept, and the fix is a contract: publish the reference data as a versioned artefact, and let each service own a copy.

14.3 Nano-services

Splitting until each service is one operation multiplies operational and cognitive cost without removing coupling. The network does not make a function cheap; it makes it expensive, remote and unreliable.

The arithmetic of over-splitting

Every service is a deployable, a pipeline, a dashboard, an on-call surface, a set of credentials, a schema and a version. At thirty services those costs are real but manageable; at three hundred, a platform team is needed just to keep the machinery running, and the human cost of a change rises because the number of edges grows faster than the number of nodes. A service that performs a single database call is not simpler than a module in a larger service — it is the same logic with a network hop, a timeout, a retry policy and a new failure mode attached.

The correct granularity is the smallest unit that can be owned by one team and deployed without coordinating with another. That is a business capability, not an operation. A good service is small enough to hold in one's head and large enough that its transactions are local.

Telling genuine decomposition from fragmentation

Two services should be separate if they have genuinely different scaling profiles, different lifecycles, different data or different compliance boundaries — a bursty image encoder and a steady billing ledger belong apart. They should be merged if they share a transaction, always deploy together, are changed by the same person, and have the same scaling profile. A useful diagnostic is the commit log: if the same people always change two services in the same pull request, the boundary is drawn inside a single team's work and is a candidate for merging.

# shell — services that always change together are probably one service
# list each service's recent commits, then find files that co-occur
git log --since="3 months ago" --name-only --pretty=format:'--- %h' -- services \
  | awk '/^---/{c=$2; next} NF{print c, $1}' \
  | sort -u > /tmp/cochange.txt

# count pairs that appear in the same commit
awk '{print $1}' /tmp/cochange.txt | uniq -c | sort -nr | head

# a high co-change rate between two service directories is a strong hint
# that the boundary is real on the diagram and fictional in practice.

Conway's law as a design input

System structure tends to mirror the communication structure of the organisation that builds it, so a boundary that cuts across a team's responsibilities will be crossed in code regardless of how it is drawn. Design the boundary and the team together: one capability, one team, one service, with the team owning the pipeline and on-call. Where a single team owns five tiny services, expect them to be deployed together and eventually to be merged, and prefer to merge them deliberately rather than discovering the coupling as an incident.

14.4 Cycles and unclear ownership

A call or event cycle between services means no service can be deployed, scaled or understood independently. Cycles are almost always an ownership problem wearing an architecture costume.

Why cycles are fatal

If A calls B and B calls A, a change to either can break the other, a failure in either can take down the pair, and there is no order in which they can be upgraded without a compatibility dance. During a cycle, scaling one service increases load on the other, so a capacity plan becomes a mutual recursion. Cycles are also the strongest predictor of a distributed monolith: they make independent deployability impossible by construction, regardless of how the code is organised.

Breaking a cycle

Four moves break most cycles without new infrastructure. Move the shared behaviour into one of the two services and invert the direction of the remaining call. Introduce an event so one direction becomes asynchronous — A publishes, B subscribes, and B no longer calls A. Extract the shared capability into a third service that both call, so neither calls the other. Or merge the two, which is the honest fix when the cycle exists because the split was wrong. A dependency graph is a directed graph and should be acyclic; wire a check into the build so a new edge cannot be added silently.

# shell — fail the build if the service dependency graph contains a cycle
# adjacency file: one "caller -> callee" edge per line
python - <<'PY'
import sys
from collections import defaultdict

edges = defaultdict(list)
for line in open("deps.txt"):
    if "->" in line:
        a, b = (p.strip() for p in line.split("->"))
        edges[a].append(b)

WHITE, GREY, BLACK = 0, 1, 2
colour = defaultdict(int)
stack, cycles = [], []

def visit(n):
    colour[n] = GREY
    stack.append(n)
    for m in edges[n]:
        if colour[m] == GREY:
            cycles.append(" -> ".join(stack + [m]))
        elif colour[m] == WHITE:
            visit(m)
    stack.pop()
    colour[n] = BLACK

for n in list(edges):
    if colour[n] == WHITE:
        visit(n)

if cycles:
    print("dependency cycles found:")
    print("\n".join(cycles))
    sys.exit(1)
PY

Ownership and the escalation path

Every service needs exactly one owning team, named in the repository and in the catalogue, and that team is accountable for its interfaces, its data and its on-call. Ownership by committee reproduces the cycle in human form: two teams each half-own two services, and every change needs both. When two capabilities genuinely share a model, the answer is a published contract with a named owner, not joint custody of a class. Unclear ownership also shows up as an unowned service discovered during an incident; the register that answers "who do I page for this" is as much a part of the architecture as the dependency graph.

Publish a service catalogue — name, owner, on-call rotation, tier, repository, dependencies — and generate the dependency graph from it. An architecture diagram that is not generated from the code it describes is accurate only on the day it was drawn.

15.1 The production-readiness gate

"It works" is not a definition of done. A service is ready when it can be operated by someone who did not write it, in an incident that happens while they are asleep.

What the gate covers

A readiness review is a short, written checklist that the owning team answers before a service takes production traffic, and again whenever its tier changes. It is not a ceremony: each item corresponds to a failure that has ended a real system. The categories are stable across stacks — observability, resilience, security, data, deployment, and ownership — and the specifics can be made machine-checkable. A service that cannot be operated includes one with no logs correlated by request id, no health endpoint the orchestrator can act on, no documented fallback when its database is unavailable, and no named owner.

# YAML — a service manifest that doubles as a readiness gate in CI
apiVersion: platform.internal/v1
kind: Service
metadata:
  name: pricing-service
  owner: team-pricing
spec:
  tier: 1                        # 1 = customer-facing; drives the checks below
  slo:
    availability: "99.9%"        # error budget: ~43m per month
    latency:  { p99: "300ms", at: "200 rps" }
  observability:
    traces:   otel               # emits spans; required for tier <= 2
    metrics:  prometheus
    logCorrelation: requestId
  resilience:
    timeouts:  { default: 1s, dependencies: { catalogue: 800ms } }
    retries:   { max: 2, backoff: exponential, jitter: true }
    breaker:   { failureRatio: 0.5, minRequests: 20 }
  data:
    ownership: exclusive         # this service is the only writer
    backups:   { schedule: "0 */6 * * *", restoreTestedAt: "2026-09-30" }
  deploy:
    strategy: canary             # progressive, automatic rollback on SLO burn
    rollback: single-command
  oncall: pricing-primary

A maturity ladder, not a certification

Treat the gate as a ladder rather than a pass/fail exam, so a team knows what to improve next instead of defending what it has. Each rung is useful on its own; skipping a rung is what produces the incidents.

LevelWhat existsWhat it buys
1 — RunningContainer, health check, structured logs, one ownerSomeone can find and restart it
2 — ObservableTraces, metrics, SLOs against error budgetsYou know before customers do
3 — ResilientTimeouts, idempotency, breakers, load sheddingOne dependency's failure does not cascade
4 — Independently deployableContracted interfaces, backwards-compatible changes, contract testsYou ship alone, on your schedule
5 — EvolvableVersioned events, tested restores, rehearsed failureYou change the model without breaking the estate

Where the gate belongs in the pipeline

Make the checkable items checkable by a machine, so the human review is reserved for judgement: that the SLO exists in the manifest, that a health endpoint answers, that the OpenAPI document is present and diffed for breaking changes, that a restore has been tested within the retention window, that the manifest names an owner and a tier. Wire those to a pipeline step that fails the pull request, and keep the review for the parts that cannot be expressed as a rule — whether the boundary is right, whether the data ownership is genuinely exclusive, whether on-call has the runbook. Encode what can be encoded; review what must be judged.

15.2 Should this be a separate service?

The default answer is no, and the burden of proof sits with the split. This section gives the questions, the alternative first, and the record to leave behind.

Ask these before splitting

Write the answers down; a split justified in someone's head is a split nobody can review. The questions that actually discriminate are: does it need an independent scaling profile; does it need an independent release cadence; does it have a distinct lifecycle or compliance boundary; can it own its data exclusively; can it be operated by one team; and does the business capability map to a stable boundary or a moving one? If none of these is clearly yes, a module inside the current service is the cheaper and more reversible answer.

  • Scaling — does this part need materially different CPU, memory or concurrency?
  • Cadence — does it change on a different schedule, by a different team?
  • Data — can it own its store with no shared tables and no distributed transaction?
  • Lifecycle — is there a distinct debut, deprecation or compliance scope?
  • Operability — is a team ready to run it, page for it and pay its pipeline cost?
  • Reversibility — if the split is wrong, how expensive is merging it back?

The alternatives to splitting

Reach for the cheaper boundary first. A module with a published interface inside one deployable gives most of the design benefit with none of the operational cost. A separate release train in the same repository and pipeline gives cadence independence without a new runtime. A read replica or a materialised view gives scaling for reads without a new service. A background worker in the same codebase gives isolated resource consumption without a network boundary. Splitting is justified when these are exhausted, not before.

# ADR-014: extract pricing from the order service

Status:   accepted
Context:  quote recalculation is CPU-bound, peaks 20x the order path,
          and ships weekly while orders ship hourly.
Decision: extract pricing-service owning its own schema (pricing.*);
          order-service calls it synchronously for a quote and consumes
          pricing.changed for cache invalidation.
Alternatives considered:
  - in-process module (rejected: cannot scale the burst independently)

Recording the decision

An architecture decision record is one file, a paragraph of context, the decision, the alternatives and the consequence, kept in the team's repository and never edited after acceptance — a superseding record is written instead. The value is not the record's formality; it is that the reasoning survives the people. It also creates the honest question that prevents most bad splits: "what would have to be true for us to merge this back?", written at the moment of greatest optimism.

15.3 Glossary of terms used here

The vocabulary is dense and some pairs sound interchangeable while meaning opposite things. These are the definitions this guide uses.

Core terms

TermMeaning
Bounded contextA boundary within which a domain model is consistent and a term has exactly one meaning.
Anticorruption layerAdapter code that translates a foreign model into the local one at a boundary.
Consumer-driven contractAn interface agreement written by the consumer and verified by the provider in its own build.
Transactional outboxWriting the state change and the message in one local transaction, then publishing from the outbox table.
Idempotency keyA caller-supplied identity that lets a service recognise a retried operation and not repeat its effect.
Circuit breakerA stateful proxy that stops calling a failing dependency to let it recover and fail fast.
BulkheadAn isolated resource pool per dependency so one slow dependency cannot exhaust all capacity.
SagaA long-running business transaction implemented as local steps with compensations.
BackpressureSignalling from a consumer to a producer to slow down when the consumer cannot keep up.
Strangler figIncremental replacement of a system behind an unchanged edge, route by route.
Anti-entropy / reconciliationA job that compares two stores holding the same truth and reports or repairs drift.

Pairs that are easy to confuse

Orchestration vs choreography: an orchestrator tells participants what to do next; choreography is participants reacting to each other's events with no central brain. Event vs command: an event states a fact in the past tense and may have many consumers; a command is addressed to one handler and expects an effect. Idempotent vs exactly-once: idempotency is a property of the operation's effect under repetition; exactly-once is a claim about a delivery pipeline and is only ever "effectively once" with deduplication. Availability vs consistency in CAP: the choice only exists during a network partition, and PACELC adds the latency/consistency choice that applies the rest of the time. SLO vs SLA: an SLO is your internal target with an error budget; an SLA is a contractual commitment with a remedy, and it is always looser than the SLO.

Terms this guide deliberately avoids

"Microservice" is used only as shorthand for the architecture, never as a claim about size — the size is a consequence of the boundary, not a target. "Serverless microservice" and "distributed monolith" are both contradictions that name a topology and a coupling respectively. "Cloud-native" is omitted because it describes nothing testable. Where a term has a precise older meaning — "service", "component", "module" — the guide uses it in that sense and says so, because the failure to distinguish a module from a service is the first step toward two deployables sharing one database.

15.4 Further reading and how to verify

Everything above is checkable. This section lists the references worth keeping and the habit of confirming a claim against a running system rather than a slide.

Foundational references

The idea of decomposing by bounded context, and the vocabulary of aggregates, context maps and anticorruption layers, comes from Eric Evans's Domain-Driven Design. Sam Newman's Monolith to Microservices is the detailed treatment of the migration patterns in chapter 13, and Building Microservices covers the operating concerns. Chris Richardson's Microservices Patterns is the canonical source for the saga, outbox and CQRS patterns in chapter 4, and his pattern catalogue online is kept current. For reliability, Release It! (Nygard) is where circuit breakers, bulkheads and timeouts were named, and Google's SRE book is the reference for SLIs, error budgets and progressive rollout. On distributed-systems theory, Kleppmann's Designing Data-Intensive Applications explains replication, consensus and the consistency models that chapters 10 and 11 depend on.

Verify, do not assume

Every claim in this guide is falsifiable against a running system. The trade-off between an orchestrator and choreography is visible in a trace's span count. Whether a broker guarantees ordering is a property to test with a producer and two partitions, not to read from a brochure. The latency cost of one hop is a measurement, not an estimate. The habit worth keeping is small: for each architectural claim, name the observation that would prove it false, then make that observation. A latency budget asserted in a design review and never measured is a guess with a unit attached.

Tools that make the claims observable

OpenTelemetry for traces and metrics; Prometheus and Grafana for time series and dashboards; Jaeger or Tempo for trace storage; k6 or Gatling for load, soak and spike; Testcontainers for component tests; Toxiproxy or Chaos Mesh for fault injection; a schema registry for event compatibility; Pact for consumer-driven contracts; a service catalogue and generated dependency graph for ownership and cycles. The list is deliberately tool-agnostic — each entry could be replaced — because the pattern matters more than the vendor, and a pattern implemented with the wrong tool is still diagnosable, whereas a pattern that was never implemented is not.
