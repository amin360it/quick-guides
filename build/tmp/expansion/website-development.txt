<section class="chapter">
<h2 id="ch1" data-toc>1 ▸ Orientation: How the Web Works</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Before you write a single tag, understand what happens between typing a URL and seeing a page. This chapter walks the request → server → response → render journey end to end, maps the full stack and the roles that build it, and explains how the rest of this guide is organised.</p>

<h3 id="ch1-1" data-toc>1.1 The request–response cycle</h3>
<p class="topic-desc">The web is a request-response system: a client (usually a browser) asks a server for a resource, and the server answers with bytes. Nothing renders until that exchange completes.</p>

<h4 id="ch1-1-lifecycle">A full request, from keystroke to paint</h4>
<p>Every page load is a pipeline of discrete steps. The browser must resolve the hostname, establish a connection, negotiate encryption, send an HTTP request, receive a response, and only then can it parse and render. Failure at any step produces a different symptom — a DNS failure gives "server not found", a TLS failure gives a certificate warning, and a slow server shows a blank tab while you wait.</p>

<div class="codeWrap"><pre><code>1. DNS lookup:      example.com → 93.184.216.34
2. TCP connection:  open a socket to 93.184.216.34:443
3. TLS handshake:   agree keys, verify the certificate
4. HTTP request:    GET /page HTTP/1.1  (or HTTP/2 / HTTP/3)
5. Server work:     route, query, assemble → bytes
6. HTTP response:   200 OK + headers + body
7. Browser parse:   HTML → tokeniser → DOM tree
8. Render:          CSSOM + layout + paint → pixels</code></pre></div>

<h4 id="ch1-1-render">From response bytes to painted pixels</h4>
<p>The browser does not wait for the whole HTML file to arrive before it starts working. The HTML parser streams: as soon as it sees a <code>&lt;link rel="stylesheet"&gt;</code> it opens a parallel request for the CSS, pauses script execution when it meets a <code>&lt;script&gt;</code> (unless the script has <code>defer</code> or <code>async</code>), and builds the DOM incrementally. CSS and JS files block rendering in different ways, which is why the classic render-blocking audit asks you to inline critical CSS and defer non-critical scripts.</p>

<div class="codeWrap"><pre><code>// bytes → text → tokens → nodes → layout → paint
Response bytes
  → charset decoding   (UTF-8)
  → tokeniser           (tags and text)
  → tree construction   (DOM nodes, one per element)
  → style calculation   (CSSOM: which rules match which nodes)
  → layout / reflow     (boxes get sizes and positions)
  → paint               (pixels to the compositor)</code></pre></div>
<div class="tip"><p>Open DevTools → Network and look at the waterfall; you can see the whole cycle per resource: DNS, connect, TLS, wait, download. A page that is slow is usually slow at exactly one of those phases.</p></div>

<h3 id="ch1-2" data-toc>1.2 URLs, domains and DNS</h3>
<p class="topic-desc">A URL is the address the browser reads; DNS is the phonebook that turns a human-friendly name into the machine address a server actually listens on.</p>

<h4 id="ch1-2-url">Anatomy of a URL</h4>
<p>A URL decomposes into a protocol, an authority (host and optional port) and a path with optional query and fragment. The fragment never leaves the browser — it is handled entirely client-side — while the query string is sent to the server. Getting the parts straight matters when you debug: a 404 on the path is a server problem; a broken anchor on the fragment is a page problem.</p>

<div class="codeWrap"><pre><code>https://www.example.com:443/docs/getting-started?id=123#setup
|      |                  |    |                  |     |
protocol  hostname        port  path              query  fragment
|                                                  |       |
https://        domain + subdomain                  sent    never sent
                to the server                      to the server</code></pre></div>

<h4 id="ch1-2-dns">What DNS actually returns</h4>
<p>A single name is backed by several record types. <code>A</code> records map a name to an IPv4 address, <code>AAAA</code> to IPv6, <code>CNAME</code> aliases one name to another, and <code>MX</code> points at mail servers. The browser needs an <code>A</code> or <code>AAAA</code> (or a <code>CNAME</code> chain that ends in one) before it can open a connection. Caching happens at every level — your OS, your router, your ISP, and the TTL the record declares — which is why DNS changes can take "up to 48 hours" to propagate.</p>

<div class="codeWrap"><pre><code>$ dig +short example.com A
93.184.216.34

$ dig +short example.com AAAA
2606:2800:21f:cb07:6820:80da:af6b:8b2c

$ dig +short www.example.com CNAME
example.com.</code></pre></div>
<div class="note"><p>When you change hosting, you move records, not names: the domain stays, the <code>A</code> / <code>CNAME</code> values point elsewhere. Keep the registrar and the DNS hosting separate from the web host so a host migration never touches your domain registration.</p></div>

<h3 id="ch1-3" data-toc>1.3 Static and dynamic rendering</h3>
<p class="topic-desc">A static site is a folder of finished HTML files; a dynamic site builds HTML on the server per request. The choice drives your hosting, your costs and your architecture.</p>

<h4 id="ch1-3-static">Static: pre-built files, served anywhere</h4>
<p>Static pages are rendered once, at build time, and the results are plain files on disk. Requests never touch application code, so throughput is limited only by the CDN or web server, and there is no database and no secret to leak. This is why marketing sites, docs and blogs are static-first: it is the fastest, cheapest, most secure option that exists, and every static host (Netlify, GitHub Pages, Cloudflare Pages) will publish it in one command.</p>

<div class="codeWrap"><pre><code>// static — one HTML file, no server needed
File:     dist/index.html
Request:  GET /index.html
Origin:   a CDN edge near the visitor
Response: the same bytes for every visitor</code></pre></div>

<h4 id="ch1-3-dynamic">Dynamic: assembled per request</h4>
<p>Dynamic rendering queries a database, runs server logic and personalises the response. It is the right tool when the content changes faster than you can rebuild, when it depends on who is asking, or when it must come from a database the public never touches. The cost is a running server, an attack surface, and complexity — so the rule of thumb is to make as much of the site static as you can and reserve dynamic paths for the data that is genuinely per-request.</p>

<div class="codeWrap"><pre><code>// dynamic — server generates HTML per request
Request:  GET /news/article/123
Server:   query article 123 from the database
Response: HTML built specially for this request

// middle ground: hybrid
Most pages:  static files, rebuilt when content changes
/user/feed:  dynamic, rendered on request</code></pre></div>
<div class="note"><p>Static is faster, cheaper and more secure; choose dynamic only where you need real-time data or server-side logic that cannot run at build time. The two are not mutually exclusive — most production sites are a mixture.</p></div>

<h3 id="ch1-4" data-toc>1.4 The full stack, roles and tooling</h3>
<p class="topic-desc">Web development is a stack of layers, and each layer maps to a job title and a toolchain. You do not need to master all of them to ship, but you need to know where the boundaries are.</p>

<h4 id="ch1-4-layers">The layers, top to bottom</h4>
<p>From the user's screen down: the browser runs the front end; a build step compiles the source into what the browser can run; an API or server processes requests; a database stores the truth; hosting, DNS and a CDN deliver it all. A "full-stack" developer can work across the whole chain; a specialist owns one layer and knows enough about its neighbours to integrate.</p>

<div class="codeWrap"><pre><code>// seven layers every project touches
1. Browser (client)      requests, renders, runs JS
2. Front-end code        HTML, CSS, JS (maybe a framework)
3. Build step            bundles, minifies, optimises
4. API / server          routes, logic, joins data
5. Database              the source of truth
6. Hosting + DNS         serves files, maps names to IPs
7. HTTPS + CDN           encrypts traffic, caches responses</code></pre></div>

<h4 id="ch1-4-roles">Who builds what</h4>
<p>Front-end engineers own layers 1–3: semantics, styling, behaviour, and increasingly the render strategy. Backend engineers own 4–5: APIs, business logic, authentication and data modelling. DevOps/platform engineers own 6–7: infrastructure, deployments, monitoring and security hygiene. The boundaries blur in small teams — a solo developer is every role at once — but the responsibilities remain distinct enough that the terminology carries across companies.</p>

<h4 id="ch1-4-tools">The toolchain you need, all free</h4>
<p>Everything in this guide runs on free tooling: VS Code as the editor, Git for version control, Node.js as the runtime and package ecosystem, a local dev server for preview, and a static host or small VPS to deploy to. No paid tool is required anywhere; paid tiers only buy convenience, scale and support.</p>

<div class="codeWrap"><pre><code>$ code .                          # open the project in VS Code
$ python -m http.server 8000      # serve the current folder locally
$ git add .                       # stage your work
$ git commit -m "Homepage copy"   # record a snapshot</code></pre></div>

<h3 id="ch1-5" data-toc>1.5 How this guide is organised</h3>
<p class="topic-desc">The seven chapters follow the real delivery sequence: understand the wire, build the front end, adopt tooling, reach for frameworks, add a backend, deploy, then keep it healthy.</p>

<h4 id="ch1-5-structure">The arc of the book</h4>
<p>Each chapter is an h2; each topic inside it is an h3; each h3 is a self-contained unit with an intro, prose, at least two runnable code samples and a callout that flags the most common mistake. Chapters 1–2 build foundations, 3–4 are about how you build, 5–6 are about what you run, and 7 is the ongoing cost of running it.</p>

<div class="codeWrap"><pre><code>// build in this order, not in parallel
ch1  orientation:  what happens on the wire
ch2  front end:    HTML, CSS and JS in the browser
ch3  tooling:      editors, Git, npm, build tools
ch4  frameworks:   components, state, rendering strategies
ch5  backend:      servers, APIs, auth, databases, migrations
ch6  deployment:   hosting, DNS, HTTPS, pipelines, config
ch7  upkeep:       security, performance, monitoring, backups</code></pre></div>

<h4 id="ch1-5-sequence">The mindset: users first, then code</h4>
<p>Fast, accessible and maintainable: those three goals never conflict when you work in the right order. Structure first, behaviour second, polish third. Do not build the backend before the API contract is clear; do not write CSS before the HTML is semantic; do not optimise images before the page even loads. Every chapter ends with a check against the same three questions — does it work on a phone, on a slow network, with a screen reader?</p>

<div class="codeWrap"><pre><code>1. structure:  semantic HTML alone, no styling
2. behaviour:  JS that works from keyboard and screen reader
3. polish:     responsive layout, images, performance
4. verify:     phone, slow network, screen reader → then ship</code></pre></div>

<h4 id="ch1-5-verify">Verify before you deploy</h4>
<p>A build that passes on your machine and fails for your users is not done. Treat the browser's DevTools and an auditing tool like Lighthouse as part of the writing loop, not a final gate. If a check fails, fix it before moving on — the cost of a fix grows with every layer you build on top of it.</p>

<div class="codeWrap"><pre><code>const checklist = [
  'works on a phone',
  'works on a slow network',
  'reads aloud well (screen reader)',
  'passes Lighthouse accessibility',
];
checklist.forEach((item) =&gt; console.log(item));</code></pre></div>
<div class="tip"><p>Start with plain HTML, CSS and JS. Add a framework, a build tool or a database only after you have hit a real problem that it solves — chapter 4 shows how to recognise that moment.</p></div>

<section class="chapter">
<h2 id="ch2" data-toc>2 ▸ The Front End</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">The front end is everything the browser runs: semantic HTML for structure, CSS for layout and styling, JavaScript for behaviour, the DOM as the live tree they all share, and DevTools as the observability layer on top. Master these four files' worth of fundamentals before any framework.</p>

<h3 id="ch2-1" data-toc>2.1 Semantic HTML structure</h3>
<p class="topic-desc">Semantic HTML uses elements for their meaning, not their appearance. A <code>&lt;header&gt;</code> means "page header", not "a div styled like a header" — meaning is what screen readers, search engines and future maintainers rely on.</p>

<h4 id="ch2-1-skeleton">The document skeleton</h4>
<p>Every page starts with the same five parts: the <code>&lt;!DOCTYPE html&gt;</code> declaration, an <code>&lt;html lang="en"&gt;</code> root whose <code>lang</code> attribute drives pronunciation and translation, a <code>&lt;head&gt;</code> for metadata, and a <code>&lt;body&gt;</code> split into landmarks. The <code>lang</code> attribute is not decorative — a screen reader will pronounce English text with a German voice if you leave it out.</p>

<div class="codeWrap"><pre><code>&lt;!DOCTYPE html&gt;
&lt;html lang="en"&gt;
&lt;head&gt;
  &lt;meta charset="utf-8"&gt;
  &lt;meta name="viewport" content="width=device-width, initial-scale=1"&gt;
  &lt;title&gt;A semantic page&lt;/title&gt;
&lt;/head&gt;
&lt;body&gt;
  &lt;header&gt;Site name and main navigation&lt;/header&gt;
  &lt;main&gt;
    &lt;article&gt;…&lt;/article&gt;
    &lt;aside&gt;Related links&lt;/aside&gt;
  &lt;/main&gt;
  &lt;footer&gt;Copyright and contact&lt;/footer&gt;
&lt;/body&gt;
&lt;/html&gt;</code></pre></div>

<h4 id="ch2-1-landmarks">Landmarks, navigation and articles</h4>
<p>Landmark elements (<code>header</code>, <code>nav</code>, <code>main</code>, <code>aside</code>, <code>footer</code>) give assistive technology a page map, exactly as headings give it an outline. Keep exactly one <code>main</code>, label navigation with <code>aria-label</code> when there is more than one <code>nav</code>, and let <code>article</code> own self-contained content so browsers can reuse it in readers and search results.</p>

<div class="codeWrap"><pre><code>&lt;nav aria-label="Main"&gt;
  &lt;ul&gt;
    &lt;li&gt;&lt;a href="/"&gt;Home&lt;/a&gt;&lt;/li&gt;
    &lt;li&gt;&lt;a href="/docs"&gt;Docs&lt;/a&gt;&lt;/li&gt;
    &lt;li&gt;&lt;a href="/about"&gt;About&lt;/a&gt;&lt;/li&gt;
  &lt;/ul&gt;
&lt;/nav&gt;

&lt;article&gt;
  &lt;h1&gt;Launching the redesign&lt;/h1&gt;
  &lt;p&gt;Published &lt;time datetime="2026-10-01"&gt;1 October 2026&lt;/time&gt;.&lt;/p&gt;
&lt;/article&gt;</code></pre></div>

<h4 id="ch2-1-forms">Forms: labels, types and autocomplete</h4>
<p>A form field without a <code>&lt;label&gt;</code> is invisible to assistive technology, and a field with the wrong <code>type</code> gets the wrong keyboard on mobile. Choosing <code>type="email"</code>, <code>type="tel"</code> or <code>type="number"</code> changes both validation and the on-screen keyboard. <code>autocomplete</code> lets the browser prefill real values — name, email, postal code — which is worth more to users than any styling.</p>

<div class="codeWrap"><pre><code>&lt;form action="/subscribe" method="post"&gt;
  &lt;label for="email"&gt;Email address&lt;/label&gt;
  &lt;input id="email" name="email" type="email"
         required autocomplete="email"&gt;

  &lt;label for="plan"&gt;Plan&lt;/label&gt;
  &lt;select id="plan" name="plan"&gt;
    &lt;option value="free"&gt;Free&lt;/option&gt;
    &lt;option value="pro"&gt;Pro&lt;/option&gt;
  &lt;/select&gt;

  &lt;button type="submit"&gt;Subscribe&lt;/button&gt;
&lt;/form&gt;</code></pre></div>
<div class="warn"><p>Do not build "div soup" — ten nested <code>&lt;div&gt;</code>s carry zero meaning and force every consumer (search engine, screen reader, maintainer) to guess. If an element already exists for the job, use it.</p></div>

<h3 id="ch2-2" data-toc>2.2 CSS layout: box model and flex/grid</h3>
<p class="topic-desc">Every element on the page is a rectangle. Padding is inside the border, margin is outside it, and flexbox and grid are the two modern engines for arranging those rectangles.</p>

<h4 id="ch2-2-box">The box model, and box-sizing</h4>
<p>An element's rendered width is content + padding + border (by default, <code>content-box</code>), which makes percentage widths lie: a <code>width: 50%</code> card with padding actually exceeds half the container. The one-line fix is <code>box-sizing: border-box</code> on everything, so declared width includes padding and border. This single reset prevents more layout bugs than any other rule.</p>

<div class="codeWrap"><pre><code>*,
*::before,
*::after {
  box-sizing: border-box;
}

.card {
  width: 100%;          /* border-box: this is the full rendered width */
  padding: 1rem;        /* space inside the border */
  border: 1px solid #ccc;
  margin-bottom: 1rem;  /* space outside the border */
}</code></pre></div>

<h4 id="ch2-2-flex">Flexbox: one dimension at a time</h4>
<p>Flexbox lays out children along one axis — row or column — and is the right tool for a header, a toolbar or a card body. <code>justify-content</code> positions along the main axis, <code>align-items</code> along the cross axis, and <code>gap</code> replaces the old margin-hacks for spacing between siblings. Give the container a direction and the children get aligned for free.</p>

<div class="codeWrap"><pre><code>header.top {
  display: flex;
  justify-content: space-between; /* main axis: spread the ends */
  align-items: center;            /* cross axis: vertical centre */
  padding: 12px 20px;
}

header.top nav ul {
  display: flex;
  gap: 16px;          /* spacing between nav items, no margins */
  list-style: none;
}</code></pre></div>

<h4 id="ch2-2-grid">Grid: two dimensions, explicit placement</h4>
<p>Grid places items in rows and columns at once — the tool for a card wall, a dashboard or a page frame. The magic combination is <code>repeat(auto-fit, minmax(240px, 1fr))</code>: the browser decides how many equal columns fit at the current width, so the layout adapts with zero media queries. Give grid a track definition and the rows fall out of the content flow.</p>

<div class="codeWrap"><pre><code>.card-wall {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 1rem;
}

.dashboard {
  display: grid;
  grid-template-columns: 220px 1fr;
  grid-template-rows: auto 1fr;
  gap: 1rem;
}</code></pre></div>

<h4 id="ch2-2-responsive">Responsive values: media queries, clamp and custom properties</h4>
<p>Modern responsive CSS is mostly "fluid by default, breakpoints for behaviour". <code>clamp()</code> makes a value fluid between a minimum and maximum, custom properties (<code>--space</code>, <code>--accent</code>) keep the palette in one place, and media queries are reserved for genuine layout changes — hiding a sidebar, stacking a nav — rather than rescaling text. Prefer <code>vw</code> units inside <code>clamp()</code> over fixed pixel type sizes.</p>

<div class="codeWrap"><pre><code>:root {
  --space: clamp(0.5rem, 1vw + 0.5rem, 1.5rem);
  --radius: 4px;
}

.card {
  padding: var(--space);
  border-radius: var(--radius);
}

@media (max-width: 640px) {
  .sidebar { display: none; }        /* layout change, not a font tweak */
  nav ul   { flex-direction: column; }
}</code></pre></div>
<div class="note"><p>Design mobile-first in CSS: write the single-column base, then use <code>min-width</code> media queries to add complexity as the viewport widens. It is one code path instead of two, and the phone layout is never an afterthought.</p></div>

<h3 id="ch2-3" data-toc>2.3 JavaScript behaviour</h3>
<p class="topic-desc">JavaScript is the behaviour layer: it selects elements, reacts to user actions, talks to servers and keeps the UI in sync with state. It runs last, after the document exists.</p>

<h4 id="ch2-3-basics">Variables, functions and template literals</h4>
<p>Declare with <code>const</code> by default and <code>let</code> only when a value is reassigned; <code>var</code> has function rather than block scoping and causes subtle bugs. Functions are first-class: you pass them around as values, which is the entire basis of event handling. Template literals (backticks with <code>${}</code>) interpolate safely and read better than string concatenation.</p>

<div class="codeWrap"><pre><code>const title = 'Quick Guides';
const pages = 78;

function describe(prefix) {
  return `${prefix}: ${pages} offline pages`;
}

console.log(describe(title));
// → Quick Guides: 78 offline pages</code></pre></div>

<h4 id="ch2-3-events">Handling events: clicks, submits, keys</h4>
<p>Events are how the user talks to the script. <code>addEventListener</code> is preferred over inline <code>onclick</code> attributes because a page can attach many listeners and keep markup clean. A submit handler must call <code>preventDefault()</code> or the page reloads and loses your state. Read the input's <code>value</code> at event time — the DOM is the live current state, not a snapshot.</p>

<div class="codeWrap"><pre><code>const form = document.querySelector('#search-form');

form.addEventListener('submit', (event) =&gt; {
  event.preventDefault();               // stop the full page reload
  const input = document.querySelector('#search');
  const query = input.value.trim();
  if (query.length === 0) return;
  console.log('Searching for:', query);
});</code></pre></div>
<div class="warn"><p>Inline <code>onclick="…"</code> attributes run in a messy scope, cannot be removed in code, and mix behaviour into markup. Keep all behaviour in <code>&lt;script&gt;</code> files and attach it with <code>addEventListener</code>.</p></div>

<h3 id="ch2-4" data-toc>2.4 The DOM and events in depth</h3>
<p class="topic-desc">The DOM is the live, in-memory tree of the page. HTML is its source, DevTools shows its current state, and JavaScript edits it. Understanding the tree model turns "make the page do things" into a few predictable operations.</p>

<h4 id="ch2-4-dom">What the DOM is</h4>
<p>When the parser finishes, every element, attribute and text node exists in a tree: <code>document</code> at the root, then <code>html</code>, then <code>head</code> and <code>body</code>, then their children. <code>document.querySelector</code> finds one node by selector; <code>querySelectorAll</code> returns a static <code>NodeList</code> you can spread or loop. Text inside a node is a child <em>text node</em>, which is why <code>innerHTML</code> and <code>textContent</code> behave so differently.</p>

<div class="codeWrap"><pre><code>&lt;!-- the source --&gt;
&lt;ul id="tags"&gt;
  &lt;li&gt;HTML&lt;/li&gt;
  &lt;li&gt;CSS&lt;/li&gt;
&lt;/ul&gt;

// the tree it produces
document
└─ ul#tags
   ├─ li  → "HTML"
   └─ li  → "CSS"</code></pre></div>

<h4 id="ch2-4-build">Creating and inserting nodes</h4>
<p>Build new nodes with <code>document.createElement</code>, fill them with <code>textContent</code> (never <code>innerHTML</code> for user data), and attach them with <code>appendChild</code> or <code>append</code>. This is exactly what rendering libraries do internally — a framework is a smarter version of this loop, with diffing on top.</p>

<div class="codeWrap"><pre><code>const list = document.createElement('ul');

['HTML', 'CSS', 'JS'].forEach((item) =&gt; {
  const li = document.createElement('li');
  li.textContent = item;          // text node: no markup is parsed
  list.appendChild(li);
});

document.querySelector('#tags').after(list);</code></pre></div>

<h4 id="ch2-4-delegate">Event bubbling and delegation</h4>
<p>Events bubble: a click on a list item travels up through every ancestor. Instead of attaching a listener to hundreds of rows, attach one to the container and read the actual target with <code>event.target.closest()</code>. This works for rows added later — vital because nodes you create after page load never had the chance to receive their own listeners.</p>

<div class="codeWrap"><pre><code>document.querySelector('#todo-list').addEventListener('click', (event) =&gt; {
  const row = event.target.closest('li[data-id]');
  if (!row) return;                       // clicked padding, not a row
  console.log('Clicked todo', row.dataset.id);
  row.classList.toggle('done');
});</code></pre></div>
<div class="note"><p>Use <code>closest()</code> rather than checking <code>event.target</code> directly — the target can be a text node or a nested <code>&lt;span&gt;</code> inside the row, and <code>closest()</code> walks up for you.</p></div>

<h3 id="ch2-5" data-toc>2.5 Browser developer tools</h3>
<p class="topic-desc">DevTools is the debugger, inspector, network analyser and performance profiler all in one. Every claim in this guide can be verified in it, and most front-end bugs are found in its first three panels.</p>

<h4 id="ch2-5-inspect">Elements and Console</h4>
<p>The Elements panel shows the live DOM and the computed styles — right-click any element, and you see exactly which CSS rules apply and which one wins the cascade. The Console runs JavaScript against the live page: you can query the DOM, call your functions, and inspect values with <code>console.table</code> for arrays of objects. The console evaluates in the page's context, so a typo there costs nothing but a re-run.</p>

<div class="codeWrap"><pre><code>// paste into the Console against the running page
const cards = [...document.querySelectorAll('.card')];
console.table(
  cards.map((card) =&gt; ({
    text: card.textContent.trim().slice(0, 40),
    visible: card.getBoundingClientRect().width &gt; 0,
  })),
);</code></pre></div>

<h4 id="ch2-5-network">The Network panel and the request waterfall</h4>
<p>The Network panel records every request: status code, size, timing, and the waterfall that shows DNS, connect, TLS, wait and download for each one. Filter by <code>Fetch/XHR</code> to watch API calls, and read the <em>Initiator</em> column to find which script started a request. A request stuck on "wait" is a server problem; a request that downloads slowly is a payload problem; either way the panel names it.</p>

<div class="codeWrap"><pre><code>// trigger an API call, then watch it in Network → Fetch/XHR
fetch('/api/products', { headers: { Accept: 'application/json' } })
  .then((res) =&gt; res.json())
  .then((data) =&gt; console.table(data.slice(0, 5)));</code></pre></div>

<h4 id="ch2-5-lighthouse">Lighthouse: an automated audit</h4>
<p>Lighthouse runs a headless pass over your page and scores performance, accessibility, best practices and SEO, each with a list of concrete failing opportunities. It is the fastest way to find the first five real problems on any page, and it is scriptable — run it in CI so a performance regression fails the build instead of surprising you in production.</p>

<div class="codeWrap"><pre><code>$ npx lighthouse https://example.com --view
$ npx lighthouse https://example.com \
    --output=json --output-path=report.json \
    --only-categories=performance,accessibility</code></pre></div>
<div class="tip"><p>Lighthouse scores are thresholds, not marketing: a 95 performance score still fails Core Web Vitals if LCP is over 2.5 s. Read the "opportunities" section, not just the number.</p></div>
</section>

<section class="chapter">
<h2 id="ch3" data-toc>3 ▸ Tooling and Workflow</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Tools amplify or waste your time. A sane setup — a good editor, Git, a package manager, a build tool and a local server — is the difference between shipping weekly and debugging your own machine. This chapter builds that setup from zero, free.</p>

<h3 id="ch3-1" data-toc>3.1 Editors and IDEs</h3>
<p class="topic-desc">Choose one editor and learn it deeply. VS Code is the default recommendation because it is free, cross-platform and extendable; the principles transfer to any editor.</p>

<h4 id="ch3-1-choice">What to look for in an editor</h4>
<p>An editor earns its keep through syntax highlighting, IntelliSense, a built-in terminal, and a debugger you can actually step through. VS Code stores your configuration as JSON (<code>settings.json</code>) and per-project settings in a <code>.vscode</code> folder, so a team's editor behaviour becomes part of the repository. Commit that folder and every teammate gets the same formatting, linting and file handling without reading a README.</p>

<div class="codeWrap"><pre><code>{
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "always"
  },
  "files.eol": "\n",
  "files.trimTrailingWhitespace": true,
  "terminal.integrated.defaultProfile.windows": "Git Bash"
}</code></pre></div>

<h4 id="ch3-1-extensions">The handful of extensions that matter</h4>
<p>Keep extensions purposeful: Prettier for consistent formatting, ESLint for catching mistakes before they run, and a live-reload server. Language servers — the engines behind IntelliSense — give you what editors used to charge for: hover documentation, go-to-definition and rename-across-files. Recommending them in <code>.vscode/extensions.json</code> makes setup one click for anyone who clones the repo.</p>

<div class="codeWrap"><pre><code>{
  "recommendations": [
    "dbaeumer.vscode-eslint",
    "esbenp.prettier-vscode",
    "ritwickdey.LiveServer"
  ]
}</code></pre></div>
<div class="warn"><p>Do not install the whole marketplace. Every extension is code running with your permissions: the fewer you have, the smaller the attack surface and the fewer "why is my editor slow" mysteries.</p></div>

<h3 id="ch3-2" data-toc>3.2 Git version control</h3>
<p class="topic-desc">Git records snapshots of your project so you can experiment freely, compare versions and collaborate. Every worthwhile mistake is undone with one command — if you commit as you go.</p>

<h4 id="ch3-2-basics">Initialise, stage, commit</h4>
<p>A commit is a snapshot of the staged tree, and the message explains <em>why</em> the change exists. The loop is: edit, <code>git status</code> to see what changed, <code>git add</code> to stage, <code>git commit</code> to snapshot. <code>.gitignore</code> keeps generated and secret files out of the repository — committing <code>node_modules</code> or a <code>.env</code> file is the classic beginner disaster.</p>

<div class="codeWrap"><pre><code>$ git init
$ git status                    # what has changed?
$ git add index.html styles.css
$ git commit -m "Add landing page"

# .gitignore — never commit these
node_modules/
dist/
.env
*.log</code></pre></div>

<h4 id="ch3-2-branch">Branches: working without fear</h4>
<p>A branch is a movable pointer to a commit. Create one per feature, work there, then merge it back to <code>main</code>. This keeps <code>main</code> deployable at all times and makes a half-finished feature invisible to everyone else. <code>git diff</code> shows exactly what a change will do before you commit it — read it, always.</p>

<div class="codeWrap"><pre><code>$ git switch -c feature/nav       # new branch, checked out
$ git diff --stat                 # summary of pending changes
$ git add .
$ git commit -m "Add responsive nav"
$ git switch main                 # back to the stable line
$ git merge --no-ff feature/nav   # merge as explicit history</code></pre></div>

<h4 id="ch3-2-remote">Remotes: pushing and pulling</h4>
<p>A remote is a copy of the repository somewhere else — GitHub, GitLab, Bitbucket. <code>git push</code> sends your commits, <code>git pull</code> brings theirs, and a pull request is a proposal to merge a branch that everyone can review before it lands. Keep commits small and messages specific; a future you debugging a regression reads them like a diary.</p>

<div class="codeWrap"><pre><code>$ git remote add origin https://github.com/you/site.git
$ git push -u origin main        # -u remembers the branch
$ git pull --rebase              # replay local work on top of remote
$ git log --oneline -5
f3c9a21 Add responsive nav
b17e04f Fix checkout form validation
a8d110c Add landing page</code></pre></div>
<div class="tip"><p>Commit early and often — a commit a minute is fine while you experiment. The recap (<code>git log --oneline</code>) is your safety net; you can always <code>git revert</code> a commit you regret but never one you did not make.</p></div>

<h3 id="ch3-3" data-toc>3.3 Package managers</h3>
<p class="topic-desc">A package manager installs, versions and scripts the libraries your project depends on. npm ships with Node.js; pnpm and Yarn are faster alternatives using the same registry and the same <code>package.json</code>.</p>

<h4 id="ch3-3-npm">npm: install, save, run</h4>
<p><code>npm install &lt;name&gt;</code> fetches a package and records it in <code>dependencies</code>; <code>--save-dev</code> puts build-time tools in <code>devDependencies</code> so production installs stay lean. <code>npx</code> runs a package without installing it permanently — the standard way to run one-off tools. The <code>scripts</code> block is your project's command line: <code>npm run dev</code>, <code>npm run build</code> and <code>npm test</code> mean the same thing for every project you open.</p>

<div class="codeWrap"><pre><code>$ npm init -y               # create package.json
$ npm install express        # runtime dependency
$ npm install --save-dev vitest   # dev-only dependency
$ npx prettier --check src/  # run a tool without saving it
$ npm run                   # list the available scripts</code></pre></div>

<h4 id="ch3-3-versioning">Semantic versioning</h4>
<p>Versions are <code>major.minor.patch</code>: a change to major can break you, minor adds features without breaking, patch fixes bugs. In <code>package.json</code>, <code>^1.4.0</code> means "1.4.0 or any newer minor up to but not including 2.0.0" — safe in-range updates happen automatically. That optimism is why the audited, exact state of every dependency lives in <code>package-lock.json</code>.</p>

<div class="codeWrap"><pre><code>{
  "name": "my-site",
  "version": "1.0.0",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  },
  "dependencies": {
    "express": "^4.21.0"
  },
  "devDependencies": {
    "vite": "^6.0.0"
  }
}</code></pre></div>

<h4 id="ch3-3-lockfile">The lockfile and reproducible installs</h4>
<p><code>package.json</code> declares ranges; <code>package-lock.json</code> pins exact versions. <code>npm install</code> may change the lockfile, so CI and teammates must use <code>npm ci</code>, which installs exactly the locked tree and fails if the two files disagree. A lockfile is the only reason "works on my machine" stops being an excuse, and it must be committed.</p>

<div class="codeWrap"><pre><code>$ npm ci        # exact install from the lockfile — use this in CI
$ npm install   # may move the lockfile — use this when adding packages

# in CI, e.g. GitHub Actions
- run: npm ci
- run: npm run build</code></pre></div>
<div class="warn"><p>Never delete the lockfile to "fix" an install problem. The lockfile is the reproducible ground truth; deleting it silently upgrades every dependency at once, and a major-version bump in one of them will take your build down in production.</p></div>

<h3 id="ch3-4" data-toc>3.4 Build tools</h3>
<p class="topic-desc">A build tool compiles and bundles what you write into what browsers run: modern syntax to widely supported syntax, dozens of modules into a few files, and readable names into fingerprinted assets.</p>

<h4 id="ch3-4-why">Why a build step exists</h4>
<p>Browsers can run ES modules natively, but production wants a handful of small files, not hundreds of network round trips. The build step bundles modules, minifies identifiers, compiles JSX/TypeScript/Sass, and hashes filenames so a deployed change busts the cache (<code>site-a1c3d.css</code> is a different URL from yesterday's build). The dev and production shapes differ on purpose.</p>

<div class="codeWrap"><pre><code>$ npm run dev      # dev server: instant reload, no build output
$ npm run build    # production: bundle + minify + fingerprint
$ ls dist
index.html  assets/index-B7x2f9.js  assets/site-a1c3d.css</code></pre></div>

<h4 id="ch3-4-vite">Vite: the modern default</h4>
<p>Vite serves source modules directly in dev (no bundling wait, via native ES modules) and switches to Rollup bundling for production. Its on-demand compilation and hot module replacement make the feedback loop close to instant. The config file is a plain ES module — every option is discoverable and typed.</p>

<div class="codeWrap"><pre><code>// vite.config.js
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  plugins: [vue()],
  build: {
    outDir: 'dist',
    sourcemap: true,          // readable stacks in production too
    target: 'es2020',
  },
});</code></pre></div>
<div class="note"><p>Never hand-edit the files in <code>dist/</code> — they are build output. Configure the source and the build tool; a hand-edited bundle is exactly one deploy away from being silently overwritten.</p></div>

<h3 id="ch3-5" data-toc>3.5 Local development servers</h3>
<p class="topic-desc">A local server serves files over <code>http://localhost</code> with the same rules as production — modules, fetch and service workers refuse to work from <code>file://</code>. You need one from day one.</p>

<h4 id="ch3-5-static">A zero-dependency static server</h4>
<p>Python ships with <code>http.server</code>, which serves a folder over HTTP in one command with correct MIME types. It is enough for plain sites and for testing that a build output actually works. Anything that depends on a real HTTP origin — fetch to relative URLs, ES module imports, cookies — behaves correctly here where double-clicking the file does not.</p>

<div class="codeWrap"><pre><code>$ python -m http.server 8000
Serving HTTP on :: port 8000 (http://[::]:8000/)

# alternatives, same idea
$ php -S localhost:8000          # PHP built-in server
$ npx serve dist                 # static server for a build output</code></pre></div>

<h4 id="ch3-5-live">Live reload and hot module replacement</h4>
<p>The VS Code Live Server extension injects a script that reloads the page whenever a file changes — pure static convenience. A framework dev server goes further with hot module replacement: it re-executes only the module you changed and patches the running page, preserving state you would lose to a reload. Either way the loop is edit → see it instantly → repeat, and the faster that loop, the more iterations you actually do.</p>

<div class="codeWrap"><pre><code>// two ways to see changes instantly
1. VS Code + Live Server   static files, full reload on save
2. Vite dev server          HMR: only the changed module re-runs

// what breaks on file:// that works on http://localhost
fetch('/api/data')            → CORS / relative-path errors
import { x } from './m.js'    → blocked
service worker registration   → refuses non-HTTP origins
cookies and caching           → keyed to the file path</code></pre></div>
<div class="warn"><p>If a feature "works offline in your editor" but misbehaves on the web host, check you are testing over <code>http://localhost</code> — half of all "works on my machine" front-end bugs vanish with a real server.</p></div>
</section>

<section class="chapter">
<h2 id="ch4" data-toc>4 ▸ Frontend Frameworks</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">A framework gives you components, state and rendering so the UI stays in sync with data by construction. The cost is size, a build step and a mental model to debug. This chapter covers when the cost is worth it and how the ideas look in React, Vue and Svelte.</p>

<h3 id="ch4-1" data-toc>4.1 When to use a framework</h3>
<p class="topic-desc">The right question is not "which framework" but "do I need one at all". Frameworks earn their keep when state and UI must stay synchronised across many elements.</p>

<h4 id="ch4-1-signals">Signals you have outgrown vanilla JS</h4>
<p>The turning point is when several independent widgets must stay in sync — a counter, a filter, a cart, and the "total" line that all depend on the same data. Without a framework you write the same update in four places and the copies drift. With one, you declare what the data is and the framework re-renders the parts that changed. The baseline tool is event handlers updating the DOM by hand, and it is worth writing once to feel the ceiling.</p>

<div class="codeWrap"><pre><code>&lt;button id="count"&gt;0&lt;/button&gt;

&lt;script&gt;
  let n = 0;
  const btn = document.querySelector('#count');
  btn.addEventListener('click', () =&gt; {
    btn.textContent = ++n;      // manual: state + DOM in one step
  });
&lt;/script&gt;

// fine for one button; copy-paste it for twenty widgets and
// you now maintain twenty pairs of state + DOM updates</code></pre></div>

<h4 id="ch4-1-compare">The real cost of adopting one</h4>
<p>A framework adds framework code to the bundle (React and its DOM renderer are roughly 120 KB minified, without your components), a mandatory build step, and a reactivity model you must learn to debug. For a marketing page that renders once, that is pure tax. For an app where state changes constantly, it buys you correctness the hand-written version will not have. The honest test is a prototype: if the vanilla version stays clean past a few screens of real state, you may not need one.</p>

<div class="codeWrap"><pre><code>// deciding checklist — mostly "yes" means adopt
[ ] several widgets share the same changing data
[ ] the UI must re-render when data changes
[ ] you manage lists: add, edit, reorder, delete
[ ] the app has distinct routes and views
[ ] a team will maintain it for more than a few months

// mostly "no" → plain HTML/CSS/JS is the better tool</code></pre></div>
<div class="warn"><p>Do not adopt a framework because it is popular. The maintenance cost is paid by your team, forever, in a language the framework's maintainers decide. A 20 KB page that loads in 400 ms beats a 200 KB SPA that loads in 2 s, when the content is the same.</p></div>

<h3 id="ch4-2" data-toc>4.2 Components and props</h3>
<p class="topic-desc">A component is a reusable, self-contained unit of UI with a name. Props are its inputs — data passed from the parent — and in all three frameworks a component is a pure function of its props plus state.</p>

<h4 id="ch4-2-react">React: components as functions</h4>
<p>In React a component is a JavaScript function returning JSX, and props arrive as a single object. One-way data flow means a child never changes its own props — it asks the parent, who owns the data. The same concept appears in Vue and Svelte with different syntax.</p>

<div class="codeWrap"><pre><code>// Greeting.jsx
export default function Greeting({ name }) {
  return &lt;p&gt;Hello, {name}!&lt;/p&gt;;
}

// parent usage
import Greeting from './Greeting.jsx';
export default function App() {
  return &lt;Greeting name="Ada" /&gt;;
}</code></pre></div>

<h4 id="ch4-2-vue">Vue: single-file components</h4>
<p>Vue's single-file component puts template, script and style in one <code>.vue</code> file. Props are declared explicitly with <code>defineProps</code>, which doubles as documentation, and the template is HTML you can read at a glance. <code>{{ name }}</code> interpolation escapes by default — it can never inject HTML.</p>

<div class="codeWrap"><pre><code>&lt;!-- Greeting.vue --&gt;
&lt;script setup&gt;
defineProps({ name: String });
&lt;/script&gt;

&lt;template&gt;
  &lt;p&gt;Hello, {{ name }}!&lt;/p&gt;
&lt;/template&gt;</code></pre></div>

<h4 id="ch4-2-svelte">Svelte: compile-time components</h4>
<p>Svelte compiles components away at build time — there is no virtual DOM and almost no runtime, so the shipped JS is smaller. Props are declared with <code>export let</code>, a quirk of the compiler, and reactivity is language-level rather than an API you call.</p>

<div class="codeWrap"><pre><code>&lt;!-- Greeting.svelte --&gt;
&lt;script&gt;
  export let name;
&lt;/script&gt;

&lt;p&gt;Hello, {name}!&lt;/p&gt;</code></pre></div>
<div class="note"><p>Learning one framework transfers to the others: all three are components + props + state, and the syntax differences are a weekend, not a career. The concepts in the next two topics are framework-neutral.</p></div>

<h3 id="ch4-3" data-toc>4.3 State and reactivity</h3>
<p class="topic-desc">State is the data that changes over the life of the app; reactivity is the framework noticing the change and re-rendering. Where and how you store state decides how many bugs you get.</p>

<h4 id="ch4-3-usestate">Declaring and updating state</h4>
<p>With React's <code>useState</code>, the state variable and its setter come back from the hook, and updating is always an assignment <em>through the setter</em> — mutating the old value directly does nothing, because React compares references to decide what changed. The setter takes the new value, or a function of the previous one when the update depends on it.</p>

<div class="codeWrap"><pre><code>import { useState } from 'react';

function Counter() {
  const [n, setN] = useState(0);
  return (
    &lt;button onClick={() =&gt; setN((prev) =&gt; prev + 1)}&gt;
      Clicked {n} times
    &lt;/button&gt;
  );
}</code></pre></div>

<h4 id="ch4-3-derived">Derived state: compute, don't store</h4>
<p>The most common state bug is storing what you can compute. If <code>total</code> and <code>inStock</code> already follow from <code>items</code>, storing them invites them to disagree. Derive instead: compute them in the render, and the framework keeps them correct for free. Every extra piece of stored state is another invariant you must maintain by hand.</p>

<div class="codeWrap"><pre><code>// store one thing
const [items, setItems] = useState([]);

// derive everything else at render time
const total = items.reduce((sum, item) =&gt; sum + item.price, 0);
const inStock = items.filter((item) =&gt; item.qty &gt; 0);
const isEmpty = items.length === 0;</code></pre></div>

<h4 id="ch4-3-lifting">Lifting state to the nearest common parent</h4>
<p>When two components need the same data, the data lives in their nearest common ancestor and flows down as props. The child fires a callback (<code>onChange</code>) when its input changes; the parent owns the value. This keeps each component's data in one place — the upside of the one-way flow is that you always know where a value came from.</p>

<div class="codeWrap"><pre><code>function App() {
  const [query, setQuery] = useState('');
  return (
    &lt;div&gt;
      &lt;SearchInput value={query} onChange={setQuery} /&gt;
      &lt;Results query={query} /&gt;
    &lt;/div&gt;
  );
}

function SearchInput({ value, onChange }) {
  return &lt;input value={value}
    onChange={(e) =&gt; onChange(e.target.value)} /&gt;;
}</code></pre></div>
<div class="tip"><p>If you ever find yourself copying state into two components "so both can read it", stop — that is the exact moment to lift it. One source of truth beats two synced copies every time.</p></div>

<h3 id="ch4-4" data-toc>4.4 Client vs server rendering</h3>
<p class="topic-desc">The same components can be rendered in two places: in the browser (client-side rendering, CSR) or on a server (SSR), or pre-built (SSG). Where you render decides your first-load performance and your SEO story.</p>

<h4 id="ch4-4-csr">Client-side rendering</h4>
<p>A CSR app ships a small HTML shell and a JS bundle; the browser runs the bundle and builds the page in the DOM. Subsequent navigation swaps views client-side with no full reload — the app feels instant once loaded. The trade-off is that the very first load ships nothing but a shell until the JS downloads and executes, which shows up directly in LCP and time-to-interactive. Use CSR for app-heavy UIs behind a login where the first paint is not the moment of truth.</p>

<div class="codeWrap"><pre><code>// client-side rendering
1. server returns a small HTML shell + JS bundles
2. browser downloads and executes the JS
3. JS builds the whole page in the DOM
4. later routes: JS swaps views, no full page reload

// cost: HTML is empty until the bundle runs</code></pre></div>

<h4 id="ch4-4-ssr">Server-side rendering and hydration</h4>
<p>SSR runs the same components on a server, emits finished HTML, and ships that — the browser paints content immediately. Then the framework re-runs on the client in a phase called hydration, attaching event handlers to the existing DOM instead of building it again. The cost is a server that can render your UI and double work: the components run on the server <em>and</em> on the client for every page load.</p>

<div class="codeWrap"><pre><code>// server-side rendering (Next.js, Nuxt, SvelteKit)
1. server runs the same components → finished HTML
2. browser paints that HTML immediately
3. JS hydrates: attaches events to the existing DOM

// cost: components run twice per load, and a server is involved</code></pre></div>

<h4 id="ch4-4-ssg">Static generation and islands</h4>
<p>Static generation is SSR at build time: every route is rendered once during <code>npm run build</code> and deployed as files, so you get SSR-quality HTML with no server at runtime. Islands architecture — the framework-rendered shell with only interactive parts hydrated — is how marketing sites get the best of both: real HTML and working widgets. Prefer SSG for anything whose content changes slower than your builds.</p>

<div class="codeWrap"><pre><code>// static generation: React, run once, at build time
HTML:   emitted per route during `npm run build`
Deploy: files on a CDN — no server at runtime
Update: rebuild to publish new content

// islands: render the static shell, hydrate only widgets
&lt;div class="product-card"&gt;
  &lt;h2&gt;…&lt;/h2&gt;                     &lt;!-- static, no JS --&gt;
  &lt;button id="buy"&gt;Add to cart&lt;/button&gt; &lt;!-- hydrated --&gt;
&lt;/div&gt;</code></pre></div>
<div class="warn"><p>Do not let a framework decide your render strategy for you: a static content site rendered client-side is slow for everyone and unreadable without JS. Pick rendering by content type, not by which framework is fashionable.</p></div>
</section>

<section class="chapter">
<h2 id="ch5" data-toc>5 ▸ Backend and Data</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">The backend receives requests, runs your logic, talks to the database and answers with data. This chapter covers the server fundamentals, HTTP and APIs, authentication, databases with CRUD, and migrations — the five things every backend does in some order.</p>

<h3 id="ch5-1" data-toc>5.1 Server-side fundamentals</h3>
<p class="topic-desc">The foundation of every backend is an HTTP server: something that listens on a port, reads requests and writes responses. Node's built-in server shows the shape; Express turns it into something pleasant to build on.</p>

<h4 id="ch5-1-node">A server with no dependencies</h4>
<p>Node's <code>node:http</code> module gives you a callback per request. You read the method and URL, write a status and headers, and end the response. It is deliberately low-level — path routing, bodies and JSON are all your problem — which makes it an excellent way to see what Express does for you. Note the callback's <code>res.end()</code>: a handler that forgets to end an async response leaves the browser waiting until the timeout.</p>

<div class="codeWrap"><pre><code>const http = require('node:http');

const server = http.createServer((req, res) =&gt; {
  const body = '&lt;h1&gt;Hello from Node&lt;/h1&gt;';
  res.writeHead(200, {
    'Content-Type': 'text/html; charset=utf-8',
    'Content-Length': Buffer.byteLength(body),
  });
  res.end(body);
});

server.listen(3000, () =&gt; console.log('listening on :3000'));</code></pre></div>

<h4 id="ch5-1-express">Express: routing and middleware</h4>
<p>Express layers routes and middleware over the same foundation. Middleware is a function that runs between the request arriving and the handler answering — parsing JSON bodies, logging, checking auth — each calling <code>next()</code> to pass control along. Route order matters: middleware registered before a route runs first, and a handler that neither answers nor calls <code>next()</code> hangs the request.</p>

<div class="codeWrap"><pre><code>const express = require('express');
const app = express();

app.use(express.json());                    // parse JSON request bodies

app.use((req, res, next) =&gt; {               // logging middleware
  console.log(req.method, req.url);
  next();
});

app.get('/api/health', (req, res) =&gt; {
  res.json({ ok: true, uptime: process.uptime() });
});

app.post('/api/todos', (req, res) =&gt; {
  const { title } = req.body;
  if (!title) return res.status(400).json({ error: 'title required' });
  res.status(201).json({ id: 42, title });
});

app.listen(3000);</code></pre></div>
<div class="tip"><p>Use <code>res.status(400)</code> for bad input, <code>401</code> for missing credentials, <code>403</code> for insufficient permission, <code>404</code> for unknown routes and <code>500</code> only for genuine server faults. Correct status codes are the API's error contract; clients branch on them.</p></div>

<h3 id="ch5-2" data-toc>5.2 HTTP methods, APIs and REST</h3>
<p class="topic-desc">An API is an HTTP interface: methods describe the intent, status codes describe the outcome, and JSON carries the payload. REST is a discipline for arranging those nouns and verbs.</p>

<h4 id="ch5-2-methods">Verbs and their meanings</h4>
<p>Each method has a contract. <code>GET</code> must not change state and is cacheable; <code>POST</code> creates and is not idempotent; <code>PUT</code> replaces a whole resource and <code>DELETE</code> removes it. <code>PATCH</code> applies a partial update. The corresponding status codes make the contract self-describing: <code>201</code> for created resources with a <code>Location</code> header, <code>204</code> for deletes that return no body.</p>

<div class="codeWrap"><pre><code>GET    /todos         → 200 list, 404 missing resource
POST   /todos         → 201 created + Location header
PUT    /todos/42      → 200 replaced (whole resource)
PATCH  /todos/42      → 200 partial update
DELETE /todos/42      → 204 no content

// idempotent: repeat the call, same outcome
GET, PUT, DELETE     safe to retry after a network blip
POST                 NOT safe to retry — you may create two</code></pre></div>

<h4 id="ch5-2-rest">REST: nouns for resources, verbs for intent</h4>
<p>REST models your domain as resources addressed by URL (<code>/todos/42</code>) and operated on with the standard verbs. Nested resources express ownership (<code>/users/7/todos</code>), and collections are named in the plural. The pay-off is predictability: a developer who has seen any REST API can guess this one. The discipline matters more than the letter — the point is that the URL identifies <em>what</em> and the method says <em>what to do</em>.</p>

<div class="codeWrap"><pre><code>// resource design, collection + item
GET    /users
GET    /users/7            single resource
POST   /users              create
PATCH  /users/7            update fields
DELETE /users/7

// ownership as nesting
GET /users/7/todos         "the todos belonging to user 7"

// never: verbs in URLs such as /getTodos or /deleteTodo?id=7</code></pre></div>

<h4 id="ch5-2-client">Calling the API from the browser</h4>
<p><code>fetch</code> returns a promise for the <em>response</em>; the JSON body is a second await. A fetch that returns <code>404</code> does not throw — <code>res.ok</code> is the flag to check, then read <code>res.status</code>. Handle the error branches explicitly, or your UI will cheerfully render "undefined" when the server says no.</p>

<div class="codeWrap"><pre><code>const res = await fetch('/api/todos', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: 'Publish the guide' }),
});

if (!res.ok) {
  throw new Error(`POST /api/todos failed: ${res.status}`);
}

const created = await res.json();
console.log('Created todo', created.id);</code></pre></div>
<div class="warn"><p>Always set <code>'Content-Type': 'application/json'</code> when sending JSON, and always check <code>res.ok</code>. The two most common API bugs in new code are the missing header and trusting a <code>fetch</code> that resolved with a 4xx body.</p></div>

<h3 id="ch5-3" data-toc>5.3 Authentication and authorisation</h3>
<p class="topic-desc">Authentication proves who you are; authorisation decides what you may do. The two classic mechanisms are server-held sessions and signed tokens (JWTs), and both start with the same non-negotiable rule: never store a plaintext password.</p>

<h4 id="ch5-3-hashing">Password storage: hash, salt, compare</h4>
<p>A password is stored as a salted, slow hash — slow is a feature, because it makes brute force expensive. <code>bcrypt</code> embeds its salt in the output, so each hash is unique even for identical passwords. Never write your own hash, never use <code>sha256</code> "plus salt" (it is far too fast to brute-force), and treat the hash field as a delay, not a lock: the defence is that attackers cannot reverse it cheaply.</p>

<div class="codeWrap"><pre><code>const bcrypt = require('bcryptjs');

// signup: hash before you store
const hash = await bcrypt.hash(password, 12);   // 12 = cost factor

// login: compare with the stored hash — never hash the attempt
const ok = await bcrypt.compare(attempt, user.passwordHash);
if (!ok) return res.status(401).json({ error: 'bad credentials' });</code></pre></div>

<h4 id="ch5-3-sessions">Sessions vs tokens</h4>
<p>Sessions store the login state on the server and hand the browser a cookie id; revocation is instant — delete the server record and the session dies. Tokens (JWTs) are self-contained: the server signs the claims, the client keeps the token, and any server with the secret can verify it without a store — ideal across many services, but revocation is impossible until expiry, which is why real implementations add denylists or short expiries. For a solo service, sessions are the simpler, safer default.</p>

<div class="codeWrap"><pre><code>// session auth — server holds the state
login      → server stores a session, sends a session cookie
each visit → cookie → server looks up the session → user record

// token auth — stateless
login      → server signs a JWT, client stores it
each visit → Authorization: Bearer &lt;token&gt; → server verifies signature
// revoke a session: delete the record (instant)
// revoke a JWT:     impossible before expiry, by design</code></pre></div>

<h4 id="ch5-3-jwt">A minimal JWT flow</h4>
<p>Issue the token only after the password check passes, sign it with a long random secret from the environment — never committed — and set a short expiry. Verification is the mirror operation: decode, check the signature and expiry, then trust the claims in <code>payload</code> for this request. The secret is the crown jewels; if it leaks, anyone can mint tokens for any user.</p>

<div class="codeWrap"><pre><code>const jwt = require('jsonwebtoken');

// issue, after the password compared ok
const token = jwt.sign(
  { sub: user.id, role: user.role },
  process.env.SECRET_KEY,          // never hard-code it
  { expiresIn: '1h' },
);

// verify, on every protected route
try {
  const payload = jwt.verify(token, process.env.SECRET_KEY);
  req.user = { id: payload.sub, role: payload.role };
} catch {
  res.status(401).json({ error: 'session expired' });
}</code></pre></div>
<div class="warn"><p>Authorisation is not authentication. Signing someone in does not tell you what they may do — a user who can read their own profile must not read other profiles. Check <code>role</code> and resource ownership on every protected route, not just at the login screen.</p></div>

<h3 id="ch5-4" data-toc>5.4 Databases and CRUD</h3>
<p class="topic-desc">A database is the source of truth: structured, indexed and transactional. CRUD — create, read, update, delete — is the alphabet every application is built from.</p>

<h4 id="ch5-4-schema">Designing the schema</h4>
<p>Tables describe entities; columns declare their types and constraints. A primary key uniquely identifies a row, a foreign key expresses ownership, and constraints (<code>NOT NULL</code>, <code>UNIQUE</code>) are the database's data validation — cheaper and more reliable than the application's. Indexes are the read-acceleration layer: they make lookups fast at the cost of slower writes and disk space.</p>

<div class="codeWrap"><pre><code>CREATE TABLE users (
  id            INTEGER PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,
  display_name  TEXT NOT NULL,
  password_hash TEXT NOT NULL
);

CREATE TABLE posts (
  id      INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  title   TEXT NOT NULL,
  body    TEXT
);

CREATE INDEX idx_posts_user ON posts(user_id);</code></pre></div>

<h4 id="ch5-4-crud">CRUD with a parameterised driver</h4>
<p>Drivers like <code>better-sqlite3</code> expose prepared statements: you write the SQL once with <code>?</code> placeholders and bind values per call. Prepared statements are both faster (the plan is cached) and safe (values are bound, never interpolated into SQL — the injection defence from chapter 7).</p>

<div class="codeWrap"><pre><code>const db = require('better-sqlite3')('app.db');

// create
db.prepare(
  'INSERT INTO posts (user_id, title, body) VALUES (?, ?, ?)',
).run(1, 'Hello', 'First post');

// read
const rows = db.prepare(
  'SELECT * FROM posts WHERE user_id = ?',
).all(1);

// update
db.prepare('UPDATE posts SET title = ? WHERE id = ?')
  .run('Hello again', rows[0].id);

// delete
db.prepare('DELETE FROM posts WHERE id = ?').run(rows[0].id);</code></pre></div>

<h4 id="ch5-4-indexes">Indexes and query plans</h4>
<p>An index is a sorted structure over a column (or columns) that lets the database find rows by key instead of scanning the table. The query planner decides; you can read its decision with <code>EXPLAIN QUERY PLAN</code>. Index what you actually filter on — foreign keys and login usernames are the classic two — and measure: an index on a column you never query is pure write overhead.</p>

<div class="codeWrap"><pre><code>EXPLAIN QUERY PLAN
SELECT * FROM posts WHERE user_id = 1;

-- with the index:    SEARCH posts USING INDEX idx_posts_user
-- without the index: SCAN posts        ← every row, every time

-- composite indexes follow column order
CREATE INDEX idx_posts_user_created
  ON posts(user_id, created_at);</code></pre></div>
<div class="note"><p>Start without indexes except primary/foreign keys, profile the slow queries, then add exactly the indexes the slow ones need. Indexing everything "to be safe" is how small databases grow into slow ones.</p></div>

<h3 id="ch5-5" data-toc>5.5 Migrations</h3>
<p class="topic-desc">A migration is a versioned, ordered script that changes the schema. Migrations turn "alter the table in production by hand" from a risky improvisation into a reviewed, repeatable deployment step.</p>

<h4 id="ch5-5-why">Why hand-editing the schema is a trap</h4>
<p>The moment a database is shared, ad-hoc <code>ALTER TABLE</code> statements diverge: your laptop has column X, production does not, and the deploy fails in the middle. Migrations fix this by making schema changes part of version control — same files, same order, applied everywhere. A migration framework tracks which ones have run, so each runs exactly once against each database.</p>

<div class="codeWrap"><pre><code>// migrations live in the repo, numbered and ordered
001_create_users.sql
002_create_posts.sql
003_add_posts_tags.sql

// applied once each, in order, on every environment
laptop:   001 → 002 → 003
staging:  001 → 002 → 003
production: 001 → 002 → 003   ← same state, provably</code></pre></div>

<h4 id="ch5-5-sample">Up and down in one script</h4>
<p>Each migration pairs a forward step with a backward one, so a bad release can be rolled back without archaeology. The forward step must be additive where possible — adding a nullable column and backfilling is safer than a destructive rewrite — and the down step should restore the previous shape. Test both directions before you deploy, not after.</p>

<div class="codeWrap"><pre><code>-- 003_add_posts_tags.sql (up)
ALTER TABLE posts
  ADD COLUMN tags TEXT NOT NULL DEFAULT '';

-- rollback (down)
ALTER TABLE posts
  DROP COLUMN tags;

-- contentious but unavoidable: destructive changes
-- go through two migrations: add new → copy → drop old</code></pre></div>

<h4 id="ch5-5-drift">Running and checking migrations</h4>
<p>Environments drift the same way schemas used to: a migration applies in staging, then someone runs a quick <code>ALTER</code> in production "to save time", and the two histories diverge permanently. Apply migrations through the same pipeline everywhere, check status before deploy, and treat a manual schema edit in production as an incident to record, not a shortcut to take.</p>

<div class="codeWrap"><pre><code>$ npm run migrate status      # what is applied where
$ npm run migrate up          # apply everything pending
$ npm run migrate down 1      # roll back the most recent one

# rule: never edit an already-applied migration
# edit → the file hash changes → environments diverge
# fix forward instead: 004_repair_posts_tags.sql</code></pre></div>
<div class="warn"><p>Never rewrite a migration that has already been applied anywhere. The fix for a bad migration is a new migration, not an edit to history — a rewritten old migration applies differently on the databases that already ran it, and "should be the same everywhere" is the entire point.</p></div>
</section>

<section class="chapter">
<h2 id="ch6" data-toc>6 ▸ Hosting and Deployment</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Deployment is where your code meets users: a host to run on, a domain to reach it, HTTPS to secure it, and a pipeline that ships changes without fear. This chapter covers the options from static hosting to containers, plus the DNS, TLS and environment-config details that break more deploys than code ever does.</p>

<h3 id="ch6-1" data-toc>6.1 Static hosting</h3>
<p class="topic-desc">Static hosting serves built files from a CDN edge — no application server, no database, nothing to patch. It is the default home for anything that can be built ahead of time.</p>

<h4 id="ch6-1-static">Publishing the build output</h4>
<p>A static host (Netlify, Cloudflare Pages, GitHub Pages) takes your <code>dist/</code> folder and serves it from dozens of edge locations with caching headers you would otherwise configure by hand. Deployment is atomic: one folder replaces the previous one, so a bad build never leaves the site half-updated. Connect the repo, point the host at the build command, and every push to <code>main</code> publishes the new site automatically.</p>

<div class="codeWrap"><pre><code>$ npm run build
# deploy dist/ to Netlify / Cloudflare Pages / GitHub Pages
# every deploy is atomic: one folder replaces the previous one
# a failed build never publishes: the old site stays live

# local preview of the exact build output
$ npx serve dist</code></pre></div>

<h4 id="ch6-1-config">Configuration: redirects and SPA fallback</h4>
<p>A single-page app routes client-side, so a request for <code>/docs/setup</code> must return the app shell for the router to run — the "SPA fallback" rule. Static hosts express this as a redirects file, and most also let you set cache headers per path. The classic mistake is the opposite rule for hashed assets: those <em>should</em> be cached forever, because a content hash means the URL changes when the content does.</p>

<div class="codeWrap"><pre><code># netlify.toml
[build]
  command = "npm run build"
  publish = "dist"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200              # SPA fallback: serve the shell, let JS route

# asset cache: hashed files never change, so cache them long
/assets/*
  Cache-Control: public, max-age=31536000, immutable</code></pre></div>
<div class="note"><p>Cache long only what is hashed or truly immutable. Caching <code>/index.html</code> for a year is how "users can't see the new deploy" happens: the browser reuses yesterday's document without asking.</p></div>

<h3 id="ch6-2" data-toc>6.2 Servers and PaaS</h3>
<p class="topic-desc">When you need code running continuously — an API, a database, background jobs — you need a server. The spectrum runs from a raw VPS you manage entirely, to a platform (PaaS) that takes the server away from you.</p>

<h4 id="ch6-2-paas">Platform as a service: no servers to babysit</h4>
<p>PaaS hosts (Render, Railway, Fly.io, Heroku-style platforms) run your process for you: you declare the start command, they provide networking, restart-on-crash, logs and scaling. The bargain is set in <code>Procfile</code>-style config — one line saying what to run — and you lose low-level control in exchange for not patching operating systems at 2 a.m. Start here; graduate to a VPS only when a concrete need (custom kernel, unusual ports) appears.</p>

<div class="codeWrap"><pre><code># Procfile — how the platform starts your web process
web: node server/index.js

# environment, not config, for secrets
DATABASE_URL=postgres://app:pass@db.internal:5432/app
PORT=8080</code></pre></div>

<h4 id="ch6-2-containers">Containers: the same app anywhere</h4>
<p>A container packages your app, its runtime and its dependencies into one image that runs identically on a laptop, CI or a cloud server. The <code>Dockerfile</code> is a build recipe, and the discipline — immutable images, declared dependencies, <code>npm ci</code> for reproducibility — is a direct extension of the lockfile work from chapter 3. The image you test is byte-for-byte the image you deploy, which kills an entire class of "works here" bugs.</p>

<div class="codeWrap"><pre><code># Dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev          # exact deps from the lockfile
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "server/index.js"]</code></pre></div>
<div class="warn"><p>Do not copy source before installing dependencies — a change to one source file then invalidates the entire dependency layer of the image cache and every build re-downloads everything. Copy the manifests first, install, then copy source.</p></div>

<h3 id="ch6-3" data-toc>6.3 Domains and DNS</h3>
<p class="topic-desc">A domain is a name you rent; DNS is the system that points it at your host. Getting the records right connects the two, and record types trip up everyone at least once.</p>

<h4 id="ch6-3-records">The record types that matter</h4>
<p>An <code>A</code> record maps a name to an IPv4 address; <code>AAAA</code> does the same for IPv6. A <code>CNAME</code> aliases one name to another — its value must be another name, not an IP — and is how <code>www</code> is pointed at a host like Netlify without knowing its addresses. The rule that catches everyone: <code>CNAME</code> cannot coexist with other records on the same name, so the bare domain often uses <code>A</code>/<code>ALIAS</code> while <code>www</code> uses <code>CNAME</code>.</p>

<div class="codeWrap"><pre><code># a typical zone (DNS records, not config)
example.com.     3600  IN  A       93.184.216.34
example.com.     3600  IN  AAAA    2606:2800:21f:cb07:6820:80da:af6b:8b2c
www.example.com. 3600  IN  CNAME   example.com.
mail.example.com. 3600 IN  MX 10   mail.example.net.

# A / AAAA : a name → an address
# CNAME    : a name → another name (follow the chain to an A)
# MX       : mail routing, unrelated to web hosting</code></pre></div>

<h4 id="ch6-3-verify">Verifying before you wait</h4>
<p>DNS changes propagate according to each record's TTL, and caching happens at every resolver between you and the zone. Use <code>dig</code> against the authoritative server to see a change that your local cache is hiding, and lower the TTL on a record a day before a migration so the old value expires quickly on the day itself.</p>

<div class="codeWrap"><pre><code>$ dig +short example.com                 # what your resolver sees
$ dig @dns1.registrar.com example.com    # what the authority says
$ dig +short www.example.com CNAME

# TTL: how long resolvers may cache — a plan, not a knob
# lower it before a migration, restore it after
example.com.  300  IN  A  203.0.113.10     # 5-minute TTL during switch</code></pre></div>
<div class="tip"><p>Verify HTTPS <em>after</em> the switch, not before: a certificate covers a specific name, and the classic outage is a domain pointing at the new host while the old certificate still names the old one. Certificates and DNS both have propagations — do DNS first, then issue, then switch.</p></div>

<h3 id="ch6-4" data-toc>6.4 HTTPS and SSL</h3>
<p class="topic-desc">HTTPS encrypts the connection and authenticates the server. Certificates are free and automated now — there is no legitimate reason for a public site to run plain HTTP.</p>

<h4 id="ch6-4-cert">Free certificates and renewal</h4>
<p>Let's Encrypt issues certificates automatically via the ACME protocol: your server proves it owns the domain (by serving a token over HTTP or DNS), and the certificate is granted, typically for 90 days. <code>certbot</code> automates both issuance and renewal, and platforms (Netlify, PaaS hosts, managed hosting) run the whole dance invisibly. The 90-day lifetime is a feature: automation is the only reliable way to renew, so short lifetimes force it and prevent the "certificate expired because Bob left the company" class of outage.</p>

<div class="codeWrap"><pre><code>$ sudo certbot certonly --nginx \
    -d example.com -d www.example.com

$ sudo certbot renew --dry-run
# renewal is a systemd timer or cron job — not a manual task
# check it: a certificate that cannot renew is a week-long outage waiting</code></pre></div>

<h4 id="ch6-4-force">Redirecting HTTP to HTTPS</h4>
<p>Once the certificate is live, every HTTP request should bounce to HTTPS with a <code>301</code> — browsers learn the rule and skip the extra round trip on later visits. The redirect must preserve the host and path (<code>$host$request_uri</code>), and HSTS then tells browsers to refuse plain HTTP entirely for your domain. Test the redirect with curl; the two most common failures are redirecting to the wrong host and forgetting www.</p>

<div class="codeWrap"><pre><code># nginx: force HTTPS, keep host and path
server {
  listen 80;
  server_name example.com www.example.com;
  return 301 https://$host$request_uri;
}

$ curl -I http://example.com
HTTP/1.1 301 Moved Permanently
Location: https://example.com/</code></pre></div>
<div class="note"><p>Only enable HSTS (<code>Strict-Transport-Security</code>) once HTTPS is working for every subdomain you own — the header tells browsers "never connect over HTTP for this long", and there is no safe way for a browser to undo a preloaded domain. Start with <code>max-age=86400</code> and raise it after a month of clean logs.</p></div>

<h3 id="ch6-5" data-toc>6.5 Deployment pipelines and environment configuration</h3>
<p class="topic-desc">A pipeline makes deploys boring: the same commands run in CI, the tests gate the release, and the artifact is identical to what you tested. Environment configuration keeps secrets out of the repository and settings out of the code.</p>

<h4 id="ch6-5-ci">Continuous deployment with GitHub Actions</h4>
<p>CI runs your build and tests on every push; CD deploys the artifact when the tests pass. The workflow file declares the trigger, the runner, and the steps — checkout, install, build, deploy. Failures happen in CI, not on your users. The deploy step typically pushes the build output to the static host or builds a container image on a PaaS — either way, the pipeline, not the developer, decides when the world sees the code.</p>

<div class="codeWrap"><pre><code># .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm run build
      - uses: peaceiris/actions-gh-pages@v4
        with:
          publish_dir: ./dist</code></pre></div>

<h4 id="ch6-5-env">Separating config from code</h4>
<p>The twelve-factor principle: configuration lives in the environment, not in source. Secrets like <code>DATABASE_URL</code> and <code>SECRET_KEY</code> are injected by the platform (or a local <code>.env</code> file), and a committed <code>.env.example</code> documents the keys without exposing the values. The moment a real secret is committed, consider it leaked — rotate it, don't just delete the line</p>

<div class="codeWrap"><pre><code># .env                ← never commit this (it is in .gitignore)
DATABASE_URL=postgres://app:secret@db.internal:5432/app
SECRET_KEY=replace-me-with-a-long-random-string

# .env.example        ← commit this: the documentation of keys
DATABASE_URL=
SECRET_KEY=

// read it, never hard-code it
const dbUrl = process.env.DATABASE_URL;
const secret = process.env.SECRET_KEY;</code></pre></div>

<h4 id="ch6-5-rollback">Rollbacks: make them boring</h4>
<p>A deploy you cannot undo is a gamble. The cheap version of a rollback is re-running the previous build — which is why build-once-promote-same-artifact matters: redploying the exact prior image is not "rebuilding in a panic", it is pointing the router at a known-good state. Keep the last successful artifact, tag releases, and practise the rollback procedure on staging before you need it in production.</p>

<div class="codeWrap"><pre><code># deploy = promote an artifact, never "rebuild and hope"
build:    npm run build     → artifact v123
promote:  point the host at v123
rollback: point the host at v122   (seconds, no rebuild)

# a release tag per deploy makes "what is live?" answerable
$ git tag deploy-2026-10-11 &amp;&amp; git push origin --tags
$ git log --oneline --decorate -3</code></pre></div>
<div class="warn"><p>If a deploy fails, resist the reflex to "fix it live" in production. Roll back, reproduce the failure on staging, fix and redeploy through the pipeline. A hotfix applied to production is a fix that CI never tested and staging never saw — you have just reintroduced the human-failure mode you built CI to remove.</p></div>
</section>

<section class="chapter">
<h2 id="ch7" data-toc>7 ▸ Security, Performance and Maintenance</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">A site is never "done": it is attacked, it gets slow as it grows, and it must be kept running. This chapter covers the security flaws that actually hit websites, the headers that shut doors, the performance budgets that keep it fast, and the monitoring and update hygiene that keep it alive.</p>

<h3 id="ch7-1" data-toc>7.1 OWASP Top 10 highlights</h3>
<p class="topic-desc">The OWASP Top 10 is the consensus ranking of the most dangerous web application risks. Four of them — injection, XSS, broken access control and misconfiguration — cause the majority of real breaches.</p>

<h4 id="ch7-1-injection">SQL injection and its fix</h4>
<p>SQL injection happens when untrusted input is concatenated into a query, so a crafted string <em>becomes</em> SQL. The canonical exploit is a <code>' OR '1'='1'</code> in a login field; the fix is never concatenation. Parameterised queries bind values separately from the statement, so the input is data no matter what it contains — and that is true for every database driver worth using.</p>

<div class="codeWrap"><pre><code>// vulnerable: the input becomes part of the program
const query =
  "SELECT * FROM users WHERE email = '" + email + "'";
//  email = "' OR '1'='1' --"  →  returns every row

// fixed: placeholders bind values; input stays data
const row = db.prepare(
  'SELECT * FROM users WHERE email = ?',
).get(email);</code></pre></div>

<h4 id="ch7-1-xss">Cross-site scripting (XSS)</h4>
<p>XSS injects markup into your page: a comment field rendered with <code>innerHTML</code> becomes script running in your users' sessions. The rule is binary — <code>textContent</code> and DOM methods can never execute markup; <code>innerHTML</code> reparses it every time. Sanitising user HTML is a library's job (DOMPurify), not yours; most of the time you should not render user HTML at all. Framework templates interpolate and escape by default, which is exactly why they are safer than string-built markup.</p>

<div class="codeWrap"><pre><code>// vulnerable: user input reparsed as markup → script runs
comments.innerHTML = userComment;

// fixed: build nodes, never render strings
const li = document.createElement('li');
li.textContent = userComment;      // a text node: markup is inert
comments.appendChild(li);

// frameworks do this for you: {{ value }} / {value} escape by default</code></pre></div>

<h4 id="ch7-1-owasp">The list that matters for a typical site</h4>
<p>Beyond injection and XSS: broken access control (a user reading another user's data because the route checks login but not ownership), cryptographic failures (stealing session cookies over plain HTTP, weak hashing), and security misconfiguration (default credentials, verbose error pages, missing headers). None of these are exotic — each is a checkbox, and each shows up in an automated scanner the day after launch.</p>

<div class="codeWrap"><pre><code>// the ones that hit websites most often
A01  broken access control      owner checks missing on routes
A02  cryptographic failures     HTTP instead of HTTPS, weak hashes
A03  injection                  SQL / NoSQL / template injection
A05  security misconfiguration  defaults, verbose errors, no headers
A07  cross-site scripting       stored, reflected, DOM-based XSS

// owning data: check identity AND ownership, on every route</code></pre></div>
<div class="warn"><p>Testing <code>is the user logged in?</code> is not access control. The cheapest real exploit is <code>/invoices/42</code> returning 42's invoice to whoever guessed the URL — resource ownership must be checked against the logged-in user on every handler, not just at the login gate.</p></div>

<h3 id="ch7-2" data-toc>7.2 Security headers</h3>
<p class="topic-desc">Security headers are HTTP response headers that instruct the browser in defensive behaviour. They cost a few lines of configuration and close entire classes of attack.</p>

<h4 id="ch7-2-headers">The five headers that matter</h4>
<p><code>Content-Security-Policy</code> restricts what the page may load and execute — a strict one can neuter XSS even if a script slips through. <code>Strict-Transport-Security</code> (HSTS) forces HTTPS for the domain. <code>X-Content-Type-Options: nosniff</code> stops MIME sniffing; <code>Referrer-Policy</code> limits what URLs you leak to other sites; <code>Permissions-Policy</code> switches off camera, microphone and geolocation you do not use. Set all five, and let a scanner verify them.</p>

<div class="codeWrap"><pre><code>Content-Security-Policy: default-src 'self'; img-src 'self' https://cdn.example.com
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()</code></pre></div>

<h4 id="ch7-2-frame">Setting them without typos</h4>
<p>Hand-writing header strings invites a typo that silently disables the protection. <code>helmet</code> for Express sets the sensible set in one line (configurable per header), and static hosts and CDNs support header rules in config. Go live with <code>default-src 'self'</code> first, then loosen specific directives only where the audit proves you need them — a CSP that blocks your own scripts breaks the site, which is why it ships in report-only mode first.</p>

<div class="codeWrap"><pre><code>const helmet = require('helmet');
app.use(helmet());   // CSP, HSTS, nosniff, referrer-policy and more

// roll out a new CSP in report-only mode first
app.use(
  helmet.contentSecurityPolicy({
    useDefaults: true,
    directives: { scriptSrc: ["'self'"] },
    reportOnly: true,          // log violations, do not block
  }),
);</code></pre></div>
<div class="note"><p>Inline <code>onclick</code> attributes and inline <code>&lt;script&gt;</code> blocks violate a strict CSP — the header is a structural forcing function for the same "behaviour in files" rule from chapter 2, which is why adopting both together is easy.</p></div>

<h3 id="ch7-3" data-toc>7.3 Performance budgets and Core Web Vitals</h3>
<p class="topic-desc">Performance is a budget, not a hope. Core Web Vitals name the three user-visible metrics that matter, and a budget makes regressions fail the build instead of surprising real users.</p>

<h4 id="ch7-3-vitals">The three Core Web Vitals</h4>
<p>LCP (Largest Contentful Paint) measures when the main content appears — good under 2.5 s, and it is dominated by the server, the first HTML bytes and the hero image. INP (Interaction to Next Paint) measures how quickly the page responds to clicks and keys — the event-handler and layout work from chapters 2 and 4. CLS (Cumulative Layout Shift) measures unexpected movement: images and embeds without reserved space cause it, and the fix is <code>width</code>/<code>height</code> attributes so the layout does not jump when media loads.</p>

<div class="codeWrap"><pre><code>// the three numbers, and what moves them
LCP  ≤ 2.5 s   Largest Contentful Paint  → first paint, hero image, server
INP  ≤ 200 ms  Interaction to Next Paint  → JS handlers, layout thrash
CLS  ≤ 0.1     Cumulative Layout Shift    → un-sized images/ads/fonts

// measure in the field, not just DevTools
$ npx lighthouse https://example.com --only-categories=performance</code></pre></div>

<h4 id="ch7-3-budget">Codifying the budget</h4>
<p>A performance budget is a number your build must not exceed: a byte budget for JS, a request budget, a LCP budget. Put it in CI — Lighthouse budget assertions, or a simple script — so a dependency bump that adds 300 KB fails the deploy with a readable message instead of becoming a tweet about slow sites. A budget nobody checks is a wish; a budget in CI is a policy.</p>

<div class="codeWrap"><pre><code>// budget.json — the numbers the build must respect
{
  "LCP": 2500,
  "INP": 200,
  "CLS": 0.1,
  "mainJsBytes": 170000,
  "imageBytes": 500000,
  "requests": 60
}

// check in CI
$ npx lighthouse-budget budget.json</code></pre></div>

<h4 id="ch7-3-media">Images: the usual suspect</h4>
<p>Images are routinely half a page's weight. Serve responsive sizes with <code>srcset</code> (the browser picks by viewport and density), declare <code>width</code>/<code>height</code> to stop CLS, add <code>loading="lazy"</code> to below-fold images, and ship modern formats — WebP/AVIF — generated by your build tool, not by hand. The `loading="lazy"` attribute alone often halves initial bytes on content pages.</p>

<div class="codeWrap"><pre><code>&lt;img
  src="photo-small.jpg"
  srcset="photo-small.jpg 480w, photo-large.jpg 1200w"
  sizes="(max-width: 600px) 100vw, 50vw"
  loading="lazy"        &lt;!-- below-fold images load when near viewport --&gt;
  width="1200"
  height="800"
  alt="The finished site"&gt;</code></pre></div>
<div class="tip"><p>Run the image audit first: compress, size correctly, then lazy-load. In the typical content page, responsible image handling beats every other optimisation combined — but only once the server actually sends them fast, which is the LCP half.</p></div>

<h3 id="ch7-4" data-toc>7.4 Monitoring</h3>
<p class="topic-desc">Monitoring is how a problem tells you before your users do: uptime checks for "is it alive", structured logs for "what happened", and error tracking for "where". All three are cheap to start.</p>

<h4 id="ch7-4-logs">Structured logs you can actually search</h4>
<p>Text logs are archaeology; structured logs are queryable data. Emit JSON lines with a timestamp, method, URL, status and duration, and the platform's log search answers "how many 500s in the last hour?" in one query. Add a per-request correlation id so you can follow one user's path across services — impossible with free-form logging and the single most useful habit in distributed debugging.</p>

<div class="codeWrap"><pre><code>import { createServer } from 'node:http';

createServer((req, res) =&gt; {
  const start = Date.now();
  res.on('finish', () =&gt; {
    console.log(JSON.stringify({
      time: new Date().toISOString(),
      method: req.method,
      path: req.url,
      status: res.statusCode,
      ms: Date.now() - start,
    }));
  });
  res.end('ok');
}).listen(3000);</code></pre></div>

<h4 id="ch7-4-checks">Uptime checks and alerting</h4>
<p>An uptime check hits a health endpoint on a schedule and alerts when the answer is not 200. Alerts must be actionable and rare: an alert every visit is noise and teaches everyone to mute it; an alert you act on once a quarter is the right shape. Monitor the endpoint that exercises the whole path (server + database), not just the static host responding to a ping.</p>

<div class="codeWrap"><pre><code># cron-based health check; alert if it fails three times in a row
* * * * * curl -fsS https://example.com/api/health \
  | grep '"ok":true' || curl -fsS -X POST https://alerts.internal/basic

# a health endpoint that proves the whole path works
GET /api/health →
{ "ok": true, "db": "up", "uptime": 120963 }</code></pre></div>
<div class="note"><p>An error tracker (Sentry-style) captures exceptions with stack traces and groups duplicates — worth adding from the first deploy, because "it worked in my terminal" is not observability, and the first bug your monitoring catches pays for the whole setup.</p></div>

<h3 id="ch7-5" data-toc>7.5 Backups and update hygiene</h3>
<p class="topic-desc">The two maintenance habits that separate professional sites from abandoned ones: backups you have actually restored, and dependencies that are never more than a sprint behind.</p>

<h4 id="ch7-5-backups">The 3-2-1 rule, and practising restores</h4>
<p>Back up to three copies, on two media, one off-site. For a database that means the platform's snapshots <em>plus</em> an export to object storage the platform cannot delete (a platform outage taking both copies down is the 3-2-1 failure). The backup that is never restored is a rumour: schedule a monthly restore into a scratch database and verify the data is there. A two-year-old backup format that tooling no longer reads is not a backup.</p>

<div class="codeWrap"><pre><code># nightly at 02:30 UTC, keep 14 daily copies, off-site
30 2 * * * pg_dump -Fc app_db \
  | aws s3 cp - s3://backups/app-$(date +%F).dump

# the monthly test: restore into a scratch database, not production
$ createdb restore-test
$ pg_restore -d restore-test backup-2026-10-11.dump
$ psql restore-test -c "SELECT count(*) FROM posts;"</code></pre></div>

<h4 id="ch7-5-updates">Update hygiene: small, often, checked</h4>
<p>Dependency updates are a maintenance treadmill with a rhythm: <code>npm outdated</code> to see what drifted, <code>npm audit</code> for known vulnerabilities, <code>npm update</code> for safe in-range bumps, and a scheduled job (Dependabot-style) opening a PR per dependency group so a major bump is a reviewed change, not an emergency. The danger is the opposite rhythm — updating nothing for six months, then absorbing a year of breaking changes in a panic during an incident.</p>

<div class="codeWrap"><pre><code>$ npm outdated          # what is behind, and by how much
$ npm audit             # known vulnerabilities in the lockfile
$ npm update            # safe in-range updates only
$ npx npm-check-updates -u   # bump the manifest to the latest
$ npm ci &amp;&amp; npm run build    # prove the bump builds, then ship it

# cadence matters more than timing
minor/patch:  merge within a week of release
major:        a planned, tested migration — not an incident</code></pre></div>
<div class="warn"><p>An automated "update everything" button is how dependency hygiene becomes a disaster. Each automated PR must be small enough to review, and the version pinning from chapter 3 is what keeps a bad release out of everyone's build at once. Boring, reviewed, frequent updates beat exciting, rare, panicked ones.</p></div>
