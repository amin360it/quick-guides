Orientation — Scope, the Two Halves, and the Boundary Between Them

0.1 Scope and target version0.2 The two halves of the stack0.3 How the halves meet0.4 Reference layers and their order0.5 Conventions used in this guide

This guide treats object-oriented PHP and MySQL as one subject rather than two. It fixes the version target, names the reference layers a persistence stack is built from, and identifies the single boundary at which object identity stops and row identity begins. Every later chapter assumes the vocabulary established here.

0.1 Scope and target version

0.1.1 Visibility and Scope

The exact language and server releases described, and what is deliberately excluded.

The language target is PHP 8.3, the branch released on 23 November 2023 and receiving security patches until 31 December 2027. The server target is MySQL 8.4, the long-term-support innovation release of 8 April 2024. Where a construct is available in 8.2 but not 8.3, the guide says so; where a construct exists only in 8.4 or later, the guide marks it >= 8.4 and treats it as an upgrade target rather than as available syntax.

ComponentVersionWhy it matters here
PHP8.3.xTyped class constants, #[\Override], json_validate(), dynamic class constant fetch
MySQL8.4 LTSRemoves the mysql_native_password plugin; deprecates utf8mb3 aliases; improves the optimiser
InnoDB8.4 defaultTransactions, foreign keys, clustered primary keys, online DDL
PDOMysql driver 8.3+ATTR_EMULATE_PREPARES must be false for server-side prepare

MySQL 8.4 removes mysql_native_password as a default plugin and downgrades connections from accounts still using it to caching_sha2_password on a best-effort basis. A driver older than 8.0.34 cannot complete that handshake. On an 8.4 server, verify the client library version before diagnosing anything else about authentication.

0.2 The two halves of the stack

0.2.1 Definition and Purpose

What PHP gives you for free, what MySQL gives you for free, and which responsibilities belong to neither.

The language half supplies value semantics through readonly properties and final classes, identity through the object handle, substitutability through interfaces, and laziness through generators. It does not supply persistence, identity mapping, change tracking, or any guarantee that a value read from the database is valid. The database half supplies durability, atomicity, isolation, referential integrity, concurrent access control, and query planning. It does not supply behaviour; a CHECK constraint can reject a value but it cannot normalise one or invoke a method on it.

The responsibilities that belong to neither half — mapping rows to objects, deciding when a write is a write, and translating database failures into domain failures — are exactly the ones teams get wrong, and they are the reason this guide exists.

// The same three facts, expressed on each side of the boundary.
// PHP says: an Email is a valid, immutable value. MySQL says: the
// column is unique, indexed, and NOT NULL. Neither statement is enough.

<?php

final readonly class Email {
    public function __construct(private string $value) {
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('malformed email');
        }
        $this->value = strtolower($value);
    }

    public function value(): string { return $this->value; }
    public function __toString(): string { return $this->value; }
}

0.3 How the halves meet

0.3.1 Hydration Flow

The hydration boundary, the direction of flow, and the single rule that keeps it clean.

Data crosses the boundary in exactly one direction at a time. Inbound, a row is a array<string, mixed> and is converted by a mapper into an object graph; no constructor that touches the database is ever called. Outbound, an object is converted by the same mapper into a parameterised statement; no object holds a PDO reference. The rule that follows is narrow and worth stating verbatim: an object never learns the shape of a row, and a row never learns the shape of an object.

Resist the temptation to give entities a save() method, a setConnection() setter, or a static find() on the model. Each of them looks like convenience and each of them destroys the testability that 17.1 and 17.2 depend on: a class that can open its own connection cannot be exercised without a live server.

Two consequences follow, and both are load-bearing. First, a mapper is a real component with real failure modes — a column rename is a mapper change — so it gets its own tests. Second, the set of SQL statements the application can execute is finite and can be enumerated, which is what makes the security argument in 16.1 auditable rather than aspirational.

0.4 Reference layers and their order

0.4.1 Layer Order

The dependency direction for the whole guide, and why the domain layer is allowed to know nothing about PDO.

Every chapter in this guide is written against a fixed four-layer arrangement. Dependencies point inward only: the domain layer knows nothing; the application layer knows domain; the infrastructure layer knows domain and application; the composition root knows all three and wires them together. This is ports and adapters with a persistence emphasis, and it is not a stylistic preference — it is the only arrangement in which the domain chapter can be unit-tested without a database.

LayerHoldsMay referenceTested with
DomainValue objects, entities, domain exceptions, repository interfacesNothing but the languagePlain unit tests
ApplicationUse cases, transactions, orchestrationDomainUnit tests with in-memory fakes
InfrastructurePDO repositories, mappers, container bindingsDomain, applicationIntegration tests on real MySQL
CompositionWiring, configuration, entry pointsAll threeSmoke test

The practical test for the boundary is a grep. If a file under src/Domain mentions PDO, MySQL, or a column name, the layering is broken and no amount of naming discipline elsewhere will compensate.

0.5 Conventions used in this guide

0.5.1 Naming Conventions

Code formatting, namespace layout, error handling policy, and how to read the examples.

All examples assume declare(strict_types=1); as the first statement after the opening tag, PSR-12 formatting, and a PSR-4 root of Acme\ mapped to src/. Example schemas use the same three tables throughout — customers, orders, order_lines — so that DDL, mapping, and query chapters describe one coherent database rather than twenty unrelated ones.

// composer.json — the four fields that determine autoloading
{
    "name": "acme/billing",
    "require": {
        "php": "^8.3",
        "ext-pdo": "*",
        "ext-json": "*"
    },
    "autoload": {
        "psr-4": { "Acme\\": "src/" }
    }
}

Errors are never suppressed. No example in this guide uses @, and no example catches a Throwable in order to log it and continue, because that pattern converts a crash into a corrupted row. The one place a broad catch appears is a process boundary, and it is always accompanied by a rethrow policy or an explicit exit code.

Token colouring in code samples is applied manually and is therefore indicative rather than exhaustive. Where a sample is long enough to matter — the container in 9.3, the migration runner in 13.4, the query builder in 14.1 — it is written to be copied into a file and run, not read as pseudocode.

1 · The PHP 8.3 Object Model

1.1 Class declaration, visibility and typed properties1.2 Constructor promotion and named arguments1.3 readonly properties and readonly classes1.4 final, abstract and closing hierarchies1.5 Enums as first-class types

This chapter fixes the declaration vocabulary for the rest of the guide. It covers what PHP 8.3 offers on a class, why readonly is shallow, what final actually costs and buys, and how enums replace runtime string validation with a type the engine can check. The recurring theme is closure: a design is better when the set of possible runtime types is known at compile time.

1.1 Class declaration, visibility and typed properties

1.1.1 Property Types

The declaration surface PHP 8.3 offers and the visibility model that makes state changes auditable.

A class is a namespace for behaviour plus a record of state. PHP 8.0 made every property typed, and PHP 8.3 added typed class constants, which closes the last gap in the declaration surface: constants are now part of the type contract rather than untyped values that vary silently between subclasses.

// 1.1 Typed properties and typed constants (PHP 8.3).

<?php

final class Money {
    public const string CURRENCY_LENGTH = 3;

    private readonly int $amountMinor;
    private readonly string $currency;

    public function __construct(int $amountMinor, string $currency) {
        $this->amountMinor = $amountMinor;
        $this->currency = strtoupper($currency);
    }
}

Three visibility levels are available — public, protected, private — and they are not a documentation convention but a compile-time contract. A property declared without a visibility is public; a property without a type is an untyped bag that the engine will accept anything into. Both defaults are legal and both are almost always wrong in application code.

Prefer private over protected as a default. protected hands every subclass write access to a property it did not declare, which means an invariant established in the parent can be invalidated by code three levels down. When a subclass genuinely needs access, expose a protected function that returns the value and performs the check; this keeps the invariant in one place.

Declare a class final unless you have a named subclass in production. The engine short-circuits dispatch for final methods, and more importantly it makes the type hierarchy closed: a reader of the code knows the complete set of possible runtime types, which is the precondition for the exhaustive match patterns used throughout this guide.

1.2 Constructor promotion and named arguments

1.2.1 Named Arguments

Reducing a constructor to a declaration, and the coupling that promotion introduces between parameter names and the API.

Constructor promotion, introduced in PHP 8.0, replaces the boilerplate of declaring a property and assigning it in the body with a visibility modifier and a type on the parameter itself. The result is a constructor that carries no logic, which is the correct shape for a data-carrying object.

// 1.2 Promotion, then validation. The check is the invariant,
// and the invariant belongs where the object is born.

<?php

final readonly class OrderLine {
    public function __construct(
        public string $sku,
        public int $quantity,
        public Money $unitPrice,
    ) {
        if ($quantity < 1) {
            throw new InvalidArgumentException('quantity must be positive');
        }
    }

    public function subtotal(): Money {
        return new Money(
            $this->unitPrice->amountMinor() * $this->quantity,
            $this->unitPrice->currency(),
        );
    }
}

$line = new OrderLine(sku: 'A-1', quantity: 2, unitPrice: $price);

Promotion makes the constructor parameter names part of the public API. Because PHP 8.0 supports named arguments, a caller may write new OrderLine(sku: 'A-1', quantity: 2, unitPrice: $p), and renaming a promoted property is therefore a breaking change to that call site. This is a real cost of promotion and it is worth paying deliberately: it is far cheaper than the alternative, in which a property is declared private and exposed through a getter, and the getter name — not the property name — is the API.

Do not use constructor promotion to expose a PDO, a container, a request object, or a clock. Promoting a service dependency publishes it as part of the value the object claims to be, and every consumer of that object can then reach through it to the database. Take services as ordinary constructor parameters; they are collaborators, not data.

1.3 readonly properties and readonly classes

1.3.1 Initialization

What readonly enforces, and the shallow-versus-deep distinction that determines whether immutability is real.

A readonly property may be initialised once, from inside the declaring class’s scope, and never modified again. PHP 8.2 extends the modifier to the whole class: a readonly class has every property readonly by default, and every property must have a declared type. A readonly class is implicitly final — the engine rejects an attempt to extend it — which removes the entire category of bug where a subclass reopens a supposedly immutable object.

The guarantee is shallow. Marking a property readonly prevents reassignment of the reference, not mutation of the object the reference points to. This is the most common misunderstanding in PHP 8.2 and 8.3 code, and it is exactly analogous to what final does not do for a Java collection.

// 1.3 Deep immutability is a design constraint, not a language feature.

<?php

final readonly class Invoice {
    public function __construct(
        public int $id,
        public DateTimeImmutable $issuedAt,
        public array $lines, // copy-on-write: safe to append to
    ) {}
}

// Legal, and a design error:
//   $invoice->lines[] = $other;
//   $invoice->lines[0]->quantity = 9;   // reaches through the array.

// The rule: promote only final readonly classes, DateTimeImmutable,
// scalars, and arrays whose elements are themselves those.

Arrays are the exception that proves the rule: PHP arrays have copy-on-write semantics, so an array property cannot be mutated through a shared reference the way an object property can. Object properties can. The practical rule for a genuinely immutable aggregate is therefore to promote only final readonly classes, DateTimeImmutable, scalars, and arrays of exactly those.

1.4 final, abstract and closing hierarchies

1.4.1 Hierarchy Closure

Using final as a design decision rather than a defensive reflex.

final has two distinct meanings worth separating. A final class cannot be extended at all. A final method cannot be overridden, but its declaring class can still be extended — and it is precisely the final methods that make a partially open class safe, because they fix the behaviour subclasses are allowed to vary around.

Applied to a template method, final public function run() wrapping non-final hooks gives a guaranteed call sequence with a single extension point. PHP 8.3 adds #[\Override], which makes the intent checkable at compile time: omitting the attribute on a method that does override a parent is a fatal error.

// 1.4 Template method with a single closed entry point.

<?php

abstract class ImportJob {
    final public function run(): int {
        $batch = $this->fetchBatch();
        if ($batch === []) {
            return 0;
        }
        $written = 0;
        foreach ($batch as $row) {
            $written += $this->persist($row);
        }
        $this->afterBatch();
        return $written;
    }

    abstract protected function fetchBatch(): array;
    abstract protected function persist(array $row): int;
    protected function afterBatch(): void {}
}

final class CustomerImport extends ImportJob {
    protected function fetchBatch(): array { return []; }
    protected function #[\Override] public function persist(array $row): int { return 1; }
}

Marking a method final costs nothing at runtime beyond skipping a dispatch check, and #[\Override] turns an omission into a compile-time error rather than a review comment. Enable the attribute throughout a codebase and most final decisions become mechanical.

1.5 Enums as first-class types

1.5.1 Backed Enums

Backed and pure enums, why they belong in the type system rather than in a validation list, and their storage representation.

Enumerations arrived in PHP 8.1 and are the correct replacement for a class of string constants validated at runtime. A backed enum has an associated scalar value, which is what makes it storable: the backed value goes into the column and the bound parameter, and the enum case is what appears in a type declaration.

// 1.5 Backed enum with domain behaviour attached to the type.

<?php

enum OrderStatus: string {
    case Pending   = 'pending';
    case Paid      = 'paid';
    case Shipped   = 'shipped';
    case Cancelled = 'cancelled';

    public function isTerminal(): bool {
        return match($this) {
            self::Shipped, self::Cancelled => true,
            default => false,
        };
    }
}

$status = OrderStatus::from('paid');      // ValueError if absent
$status = OrderStatus::tryFrom($dbValue); // ?OrderStatus, null if absent
$status->value;  // 'paid'  — persist this
$status->name;   // 'Paid'   — never persist this

Three operational rules follow. Persist ->value, never ->name, because renaming a case is a non-breaking refactor in PHP but a data-corruption event if names are in the database. Use tryFrom() at every hydration boundary, because a value written by an older or newer application version will not exist in the current enum. And never add a method that performs a database round trip to an enum — an enum must stay a pure value type, or the layering established in 0.4 has been breached.

MySQL 8.4 can enforce enum integrity directly with CHECK (status IN ('pending','paid','shipped','cancelled')) over a VARCHAR, or with a native ENUM column. Prefer the CHECK constraint: a native ENUM is compact, but adding a value requires an ALTER TABLE, and it hides ordering semantics inside the schema where a reader of a query cannot see them.

2 · Interfaces, Abstract Classes, and the Difference That Matters

2.1 Interfaces as narrow contracts2.2 Abstract classes and shared state2.3 The difference that matters2.4 Sealing hierarchies with a private constructor2.5 Contract tests for every implementation

An interface states what can be done to an object; an abstract class states how a family of objects shares state and code. This chapter makes that distinction operational, shows how to close a hierarchy once its set of implementations is fixed, and introduces the contract test that keeps every implementation of an interface substitutable for every other.

2.1 Interfaces as narrow contracts

2.1.1 Contract Methods

Defining repository and collaborator interfaces in the domain layer, and the argument for one-method interfaces.

An interface is a promise about capability. It carries no state and, since PHP 8.0, may carry constants, but its value is that it can be implemented by a class that shares no inheritance with anything else. This is why the domain layer in 0.4 can declare a repository it never implements.

// 2.1 Domain-layer contract. No PDO, no SQL, no infrastructure knowledge.

<?php

namespace Acme\Billing\Domain\Repository;

use Acme\Billing\Domain\Order;
use Acme\Billing\Domain\CustomerId;

interface OrderRepository {
    public function add(Order $order): void;
    public function get(int $id): ?Order;
    public function findByCustomer(CustomerId $id, int $limit): array;
    public function nextNumber(): string;
}

The test for whether an interface is too fat is substitutability with a hand-written fake. If you cannot write an in-memory implementation of the interface in under a screen, the interface is coupled to something the domain does not require — most often to the query shape or to a paging strategy. Splitting findByCustomer into a countByCustomer and a searchByCustomer interface is usually the correction.

Interfaces with exactly one method need no method name in their own vocabulary. Name them for the role, not the action: Clock rather than GetTime, Mailer rather than SendMail. The name is what appears in a constructor signature, and a noun reads correctly in every position a type can appear.

2.2 Abstract classes and shared state

2.2.1 State Management

When code and data genuinely must be shared, and the price of taking that option.

An abstract class differs from an interface in that it can supply state and implementation. That capability is exactly what makes it the right tool for a family of objects that share a representation, and exactly what makes it the wrong tool for a family that merely share a capability.

// 2.2 Shared representation: every event has a name and an occurred-at.

<?php

abstract readonly class DomainEvent {
    public function __construct(
        public string $name,
        public DateTimeImmutable $occurredAt,
    ) {}

    abstract public function payload(): array;
}

final class OrderPaid extends DomainEvent {
    public function __construct(
        public int $orderId,
        DateTimeImmutable $occurredAt,
    ) {
        parent::__construct('order.paid', $occurredAt);
    }

    public function payload(): array {
        return ['order_id' => $this->orderId];
    }
}

An abstract class may not implement an interface partially and defer the remainder to a further subclass indefinitely — the compiler requires every concrete class to be complete. The common workaround, an abstract method that returns null by default, reintroduces the nullable-everywhere problem that the type system was supposed to remove. If two of three subclasses share behaviour and one does not, the behaviour belongs in a trait (3.1) or in composition.

2.3 The difference that matters

2.3.1 Polymorphism

A decision procedure that picks the right one of the two, stated so it can be applied under time pressure.

The distinction is not "abstract is bad, interface is good". It is about what varies. If implementations share a representation — the same fields, the same serialisation, the same equality rule — abstract is correct. If they share only a capability — the ability to be saved, clocked, or dispatched — interface is correct. Multiple inheritance of implementation is not available in PHP, so two families with shared state and different families with shared capability cannot both be expressed by a single hierarchy; attempting it produces the diamond the language is designed to prevent.

QuestionAnswerChoose
Do all implementations carry the same fields?Yesabstract class
Do all implementations serialise the same way?Yesabstract class
Do all implementations need a database?Yesinterface, implemented by the repository
Can a fake with no database be written?Yesinterface
Do I need a base type for a match in the domain?YesEither, plus an enum of concrete types

The last row is the practical resolution for the common "I need a closed set of types" requirement. Model the closed set as an enum of cases plus a match in the domain, and let each case be a final class implementing a shared interface. You get exhaustiveness from the enum and substitutability from the interface, without a deep hierarchy.

2.4 Sealing hierarchies with a private constructor

2.4.1 Inheritance Control

Restricting a base class to its own subclasses, which PHP does not offer natively.

PHP has no sealed keyword equivalent to C#'s. The idiomatic substitute is a private constructor, which prevents the base from being instantiated and — more importantly — makes the hierarchy closed to external extension, because an outside class cannot satisfy the private constructor it would need to call.

// 2.4 A sealed base: only these two subclasses may ever exist.

<?php

abstract class PaymentMethod {
    private function __construct(
        protected readonly string $reference,
    ) {}

    final public function reference(): string {
        return $this->reference;
    }

    abstract public function authorize(Money $amount): void;
}

final class CardPayment extends PaymentMethod {
    public function __construct(string $reference, private readonly int $lastFour) {
        parent::__construct($reference);
    }

    public function authorize(Money $amount): void { /* gateway call */ }
}

// new PaymentMethod('x');        // Error: private constructor
// class BankTransfer extends PaymentMethod {}  // Error: cannot extend

Two costs are worth naming. A sealed base makes the set of implementations part of the class’s public contract, so adding a third implementation is a deliberate change to that contract — which is usually the point, but occasionally a constraint you will resent. And a private constructor interacts awkwardly with unserialize() and with ORM proxies, both of which need to construct instances reflectively; the workaround is a static named-constructor factory such as PaymentMethod::card(...), which is better API design in any case.

2.5 Contract tests for every implementation

2.5.1 Testing Contracts

Proving substitutability mechanically rather than by inspection.

An interface is only as good as its implementations' agreement on unspecified behaviour. Three questions recur: does a not-found lookup return null or throw; does a duplicate insert throw or silently update; and is ordering guaranteed? Answer them once in an abstract test case and run it against every implementation, including the in-memory fake.

// 2.5 One contract, run against PDO and against the fake.

<?php

use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

abstract class OrderRepositoryContract extends TestCase {
    abstract protected function repository(): OrderRepository;
    abstract protected function seed(): void;

    public function testMissingOrderReturnsNull(): void {
        $this->seed();
        $this->assertNull($this->repository()->get(999_999));
    }

    public function testDuplicateNumberIsRejected(): void {
        $this->seed();
        $this->expectException(DuplicateOrderNumber::class);
        $this->repository()->add($this->existingOrder());
    }
}

Two repositories implementing one interface will drift if you do not run both through the same contract suite. The concrete test class needs no test methods of its own — it supplies the factory and the fixture. When a new implementation is added, extending the contract class is the entire test-writing effort, which is the payoff for keeping the interface narrow in 2.1.

3 · Traits, Composition, and When Inheritance Is the Wrong Tool

3.1 Trait mechanics3.2 Conflict resolution and precedence3.3 Composition over inheritance3.4 When inheritance is the wrong tool3.5 Collaborators, aggregates and identity

PHP offers traits as horizontal reuse, but a trait is a language feature rather than a design tool, and its cost is deferred. This chapter explains what traits actually do to the class table, when they are defensible, and how to recognise the four situations in which composition is the correct answer — including the one that dominates persistence code, where the type hierarchy of a database schema is not the type hierarchy of a program.

3.1 Trait mechanics

3.1.1 Trait Methods

What use does at compile time and why that matters for reflection and for method overriding.

A trait is not a type. Using one copies its members into the consuming class at compile time, exactly as if they had been written there. The trait does not appear in the class’s parent chain, does not appear in its class_implements() result, and is invisible to ReflectionClass::getParentClass() — which is precisely the property that makes traits useful and precisely the property that makes them dangerous.

// 3.1 A trait supplying a constructor. The consuming class is
// still standalone: it has no parent and declares no interface.

<?php

trait ClockAware {
    private Clock $clock;

    public function setClock(Clock $clock): void {
        $this->clock = $clock;
    }

    protected function now(): DateTimeImmutable {
        return $this->clock->now();
    }
}

final class ExpireRule {
    use ClockAware;

    public function expiresAt(): DateTimeImmutable {
        return $this->now()->modify('+30 days');
    }
}

// get_parent_class(ExpireRule::class) === false
// class_uses(ExpireRule::class) === ['ClockAware' => 'ClockAware']

The setter is the weakest part of this design and it is there only to demonstrate the mechanics. In production code, take the clock as a promoted constructor parameter instead. Traits that require post-construction injection are a strong signal that the shared code wanted to be composition all along.

3.2 Conflict resolution and precedence

3.2.1 Resolution Strategy

The three mechanisms for resolving collisions, and the diagnostics you should read when a collision appears.

When two traits used by the same class declare the same member, the class is a fatal error at compile time with a message naming both traits and the member. There are three resolutions, and they are not equivalent in quality.

// 3.2 Three resolutions, worst to best.

<?php

trait Audits {
    public function label(): string { return 'audit'; }
}

trait Labels {
    public function label(): string { return 'label'; }
}

final class Record {
    use Audits, Labels {
        Audits::label insteadof Labels;   // 1. pick one
        Labels::label as secondaryLabel; // 2. keep both
    }

    public function label(): string {   // 3. class wins outright
        return parent::label() . '/overridden';
    }
}

Option 1, insteadof, silently discards code. Option 2, as, preserves it under a new name. Option 3, a class member, overrides both but may not call parent:: when there is no parent, so the example above is in fact an error and the correct form is a use-level insteadof followed by an alias. The diagnostic to read is not the fatal error but the resolution: if you needed option 2 to keep both behaviours alive, the two traits were not independent and one of them should have been a collaborator object.

Trait precedence also interacts with inheritance in a way that surprises people. A method defined in the class body always beats a trait method, and a trait method always beats an inherited parent method — but a trait used in a parent class is inherited by children and can then be overridden by a trait used in the child. The effective precedence is class, then trait of the class, then trait of the parent, then the parent’s own method. Document any trait that is designed to be overridden, or make it final in the trait, which is legal and removes the ambiguity.

3.3 Composition over inheritance

3.3.1 Composition Patterns

Replacing an is-a relationship with a has-a relationship, and the interface that makes the switch safe.

Composition is the default recommendation, but it is worth being concrete about the mechanical transformation. An is-a relationship becomes a constructor parameter typed by an interface; the child method that called parent:: becomes a method call on the collaborator; and the shared state becomes collaborator state. The transformation is mechanical enough to script, which is how large hierarchies are usually unwound without a rewrite.

// 3.3 Before: DiscountedOrder is-a PricedOrder is-a Order.
// After:  Pricer is a collaborator; Order holds one.

<?php

interface Pricer {
    public function priceFor(Order $order): Money;
}

final class VolumePricer implements Pricer {
    public function priceFor(Order $order): Money {
        $lines = $order->lines();
        return $lines === [] ? new Money(0, 'EUR') : $lines[0]->subtotal();
    }
}

final class Order {
    public function __construct(private array $lines, private Pricer $pricer) {}

    public function total(): Money {
        return $this->pricer->priceFor($this);
    }
}

The gain is not aesthetic. With an interface-typed collaborator, a test substitutes an in-memory pricer, and a second production pricer can be introduced without touching Order at all. With a subclass, adding a second pricer required a sibling subclass, and the two subclasses could not be combined. That combinatorial property — can this object be both a volume pricer and a loyalty pricer? — is the practical test, and hierarchy answers no.

3.4 When inheritance is the wrong tool

3.4.1 Alternative Example

Four failure modes, each with the concrete symptom it produces in a persistence codebase.

Inheritance is the right tool when the relationship is genuine and permanent, when the base class has no dependency on its children, and when the hierarchy is closed. It is the wrong tool in four distinguishable situations, and each produces a symptom you can look for in an existing codebase.

SituationSymptom in the codeCorrect structure
Sharing code, not a conceptA base class named BaseModel with no domain meaningTrait, or a collaborator
Reuse across unrelated domainsTwo aggregates sharing a common ancestorComposition with a shared interface
Many-axis variationClass explosion: CardDiscountedPriorityOrderStrategy objects injected at runtime
Mirroring a database tableOne subclass per table, no polymorphism usedOne class per aggregate; tables are an implementation detail

The fourth row deserves emphasis because it is the most common in PHP codebases that grew alongside a relational schema. If a class hierarchy has exactly one subclass per table and no caller ever substitutes polymorphically, the hierarchy is a copy of the schema. It adds an indirection without adding a substitution, and it guarantees that a schema change becomes a class-hierarchy change. The correct move is to let the mapper own the relationship between tables and classes, and keep the class hierarchy flat.

A useful mechanical test: search for a class that has exactly one subclass and no interface. In most application codebases this finds a schema mirror. Deleting the subclass and promoting its methods into the parent is almost always a net improvement, because the class count drops and the indirection disappears with it.

3.5 Collaborators, aggregates and identity

3.5.1 Identity Preservation

Choosing the aggregate boundary, which determines what a transaction must cover.

An aggregate is a cluster of objects treated as one consistency boundary: a set of invariants is enforced inside it, and it is loaded and saved as a unit. In a relational schema the boundary is usually drawn at the foreign key that has an ON DELETE RESTRICT or NO ACTION constraint, because that constraint is the database’s statement of the same boundary.

// 3.5 Order is the aggregate root; OrderLine is inside it and has
// no repository, no identity, and no static finders.

<?php

final class Order {
    private array $lines = [];

    public function addLine(OrderLine $line): void {
        foreach ($this->lines as $existing) {
            if ($existing->sku === $line->sku) {
                throw new DomainException('duplicate sku in order');
            }
        }
        $this->lines[] = $line;
    }

    public function lines(): array { return $this->lines; }
    public function total(): Money { /* folds sub-totals */ }
}

The corollary is the rule that governs 12.4: a transaction scope must be at least as wide as the aggregate. If an invariant spans two aggregates — "an order cannot be created unless the customer is not already over their credit limit", where credit limit lives on the customer — then the two aggregates are either one aggregate, or the invariant is enforced in the application layer and the transaction spans both. It cannot be enforced by a sequence of independent saves, because another transaction can interleave between them.

Order lines have no identity outside their order, so the table needs a composite primary key of (order_id, position) or (order_id, sku) rather than a surrogate id. A surrogate key on a dependent row invites code to treat it as an identity, which then breaks the moment the row is copied between orders. The schema argument in 13.2 and the object argument here are the same argument.

4 · Union Types, Intersection Types, Generics in Practice, and Variance

4.1 Union types and DNF types4.2 Intersection types4.3 Generics in practice4.4 Variance and substitutability4.5 strict_types and the coercion boundary

PHP’s type system is sound but not gradual, and it has no user-defined generics. This chapter works with what exists: union and intersection types including the DNF form added in 8.2, docblock generics as a static-analysis contract rather than a runtime one, the variance rules that decide whether a signature is legal, and the file-level declare that determines whether a mismatched argument throws or is coerced.

4.1 Union types and DNF types

4.1.1 Express Unions

Expressing a genuinely multi-typed input without reaching for mixed, and the redundancy rules the compiler enforces.

A union type names the set of types a value may have. Since PHP 8.0 unions are accepted on parameters, properties and return types; since 8.1 false may be written as a pseudo-type; since 8.2 null and true are standalone types and disjunctive normal form types are accepted.

// 4.1 DNF types: (A|B)&Countable, valid since PHP 8.2.

<?php

final class Cart {
    public function merge(self|GuestCart $other, int|null $ttl = null): void {}

    public function basket(): (Traversable|array)&Countable {
        return $this->lines;
    }
}

// Rejected at compile time:
//   int|positive-int      redundant subset
//   Countable|array       array is already Countable in PHP 8
//   ?string|null           ?string already includes null
//   bool                   use true|false, never bool, in a union

PHP 8.2 made every array Countable and every object Traversable, which removes a large class of unions from the type vocabulary. The corollary is that iterable means array|Traversable and is genuinely equivalent to writing that union; prefer it, because it says what the code consumes rather than what it happens to accept.

A union type on a return is a design smell unless the caller genuinely branches on it, and a match with no default arm will fatal at runtime if a new case appears. If callers always do the same thing for all members of the union, the function should return the common supertype — a Money, not a Money|string — or should be split into two functions.

4.2 Intersection types

4.2.1 Type Narrowing

Narrowing a parameter to a type that is genuinely more than one thing.

An intersection type accepts a value only if it satisfies every named type. Pure intersection types arrived in PHP 8.1, meaning a class type may be combined with an interface type; mixing an intersection with a union — DNF — arrived in 8.2. The canonical use is a function that genuinely requires two capabilities and cannot do anything useful with either alone.

// 4.2 A repository that must be both flushable and countable.

<?php

interface UnitOfWork {
    public function commit(): void;
    public function rollback(): void;
}

final class BatchFlusher {
    public function flush(UnitOfWork&Countable $work): int {
        $count = count($work); // valid, but only because of Countable
        if ($count > 0) {
            $work->commit();
        }
        return $count;
    }
}

An intersection is a stronger guarantee than a union and is far less often appropriate. Two failure modes dominate. Writing a class type into an intersection (A&B where both are classes) is legal in 8.1+ and almost always a mistake, because PHP has no multiple inheritance and no class can satisfy it; a static analyser will report the intersection as impossible. And an intersection used purely to accumulate requirements — "I need it to be A and B and C and D" — is a type that no production class will ever satisfy, which makes the parameter unusable.

4.3 Generics in practice

4.3.1 Docblock Usage

What docblock generics buy you, what they cannot buy you, and how to make them pay.

PHP has no user-defined generics. The convention is a docblock annotation understood by PHPStan and Psalm, and the two forms that matter in persistence code are list<T> and array<K, V>. These are checked at analysis time only; nothing enforces them at runtime, and a list<Order> return that actually returns an array with a gap in its keys will pass every test and fail a level-8 static analysis run.

// 4.3 Generics are a static-analysis contract. list<T> is not array<T>.

<?php

namespace Acme\Billing\Domain\Repository;

use Acme\Billing\Domain\Order;

/**
 * @return list<Order>                       zero-indexed, no gaps
 */
interface OrderRepository {
    public function get(int $id): ?Order;

    public function search(CustomerId $id): array;
    /** @return list<Order> */
    public function recentFor(CustomerId $id, int $limit): array;
}

The distinction between list and array is the one that pays for itself in database code. A PDOStatement::fetchAll() result is a list. An array keyed by primary key — the natural output of an eager-loading mapper — is not. If a function is annotated list<Order> and its caller relies on foreach plus a numeric index, annotating it array<int, Order> instead converts a real production bug into an analysis error. The cost is one word; the benefit is the elimination of an entire class of "undefined offset 3" failures.

Do not write @template annotations on a class in application code and then rely on them. Generic classes in a domain model usually indicate that the class is doing too much: a Repository<T> with a T constraint you have to describe in prose is a repository with two methods. Reserve @template for genuinely type-parameterised infrastructure — a collection, a mapper, a cache adapter — where the constraint can be written in a single line.

4.4 Variance and substitutability

4.4.1 Covariance and Contravariance

The engine’s rules for narrowing and widening parameter and return types, and how to read a fatal error about them.

PHP enforces variance at class declaration time. A parameter type may only be widened — contravariant — and a return type may only narrow — covariant. A child that narrows a parameter type or widens a return type is a fatal error at compile time, which is the correct implementation of the Liskov substitution principle for a language with nominal subtyping.

// 4.4 Legal: contravariant parameter, covariant return.

<?php

interface Reader {
    public function read(string $key): mixed;
}

final class OrderReader implements Reader {
    public function read(OrderId $key): ?Order { /* narrower in, narrower out */ }
}

// Illegal: the parameter was narrowed.
//   public function read(OrderId $key): Order {}
// Fatal error: Declaration must be compatible with Reader::read()
// 
// Also illegal: the return was widened.
//   public function read(string $key): Order|string {}

A property behaves as if it declared both a getter and a setter, so a property must be invariant — the same type in the parent and the child, with no narrowing and no widening. This is stricter than a method and catches a class of bug that methods allow: a parent with a Animal property and a child with a Dog property is rejected, because a caller holding the parent type could read a value that is not an Animal.

Variance violations surface as fatal errors at class-load time, not as test failures, which means they cannot reach production through a code path that loads the class. The practical consequence for a persistence codebase is that an interface may be broadened safely — replacing a concrete return type with an interface it implements — but never narrowed in a way that removes cases a caller depends on. Design repository interfaces from the caller’s side, not from the implementation’s side.

4.5 strict_types and the coercion boundary

4.5.1 Coercion Boundary

Which file decides whether a mismatched argument throws, and the arguments for per-file rather than per-project strictness.

Type checking mode is a property of the calling file, not the declaring file. A file with declare(strict_types=1); refuses a coerced argument; a file without it accepts a numeric string where an int is declared, silently converting it. This is the single most surprising rule in the type system and it is why a strict project still receives TypeError exceptions from third-party code that makes loose calls.

// 4.5 The caller's file decides. Strict in, weak out.

<?php
// strict-file.php
declare(strict_types=1);

function takesInt(int $n): int { return $n; }

takesInt('42');   // TypeError: must be of type int, string given
takesInt(42.0);    // TypeError under strict mode

function looseCaller(): void {
    takesInt('42'); // accepted: the caller is weak
}

// Parameters from $_GET, $_POST and json_decode() are
// strings, arrays and mixed. Under strict_types the boundary
// where a type error occurs is the call, not the coercion.

Per-file declaration is the right granularity because the strictness a file needs is a property of its inputs. A controller parsing a query string should be strict, because it must validate before constructing a typed value; a value object that receives an already-validated scalar does not need to be strict about anything. Applying the declaration to every file is harmless and is what most projects do, and the only real risk is a library file left without it, which silently accepts whatever the caller sends.

For database results, the equivalent decision is whether to trust the driver’s typing. PDO::ATTR_EMULATE_PREPARES => false with MySQL 8.4 returns native types for INT, BIGINT, DECIMAL and DATE columns. With emulation on, every value comes back as a string, and a strict parameter type will reject a COUNT(*) result the moment you forget to cast it. Decide this once, in the connection factory (11.2), not per query.

5 · Value Objects, Entities, and the Anemic Domain Model Trap

5.1 Value objects and their equality5.2 Entities and identity5.3 The mapper and the hydration boundary5.4 The anemic domain model trap5.5 Where invariants belong

The distinction that decides whether a class is a value or an entity determines its equality semantics, its persistence strategy, and whether two loaded instances are the same thing. This chapter defines both, implements the mapper that translates between row and object, and argues that the anemic domain model is a legitimate choice in a CRUD application — provided you know that is the choice you have made and know what you have given up.

5.1 Value objects and their equality

5.1.1 Equality Rules

Defining a value object, and the two equality rules that make it a value rather than a bag.

A value object has no identity: two instances holding equal components are interchangeable, and swapping one for the other changes nothing about the system state. The consequence is that value objects must override == to compare components, and — because PHP’s === compares identity and is not overridable — must never be compared with === or used as an array key.

// 5.1 Equality by component, not by identity.

<?php

final readonly class Email {
    public function __construct(public string $value) {
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('malformed email');
        }
    }

    public function equals(self $other): bool {
        return $this->value === $other->value;
    }

    public function __toString(): string { return $this->value; }
}

$a = new Email('a@example.com');
$$b = new Email('a@example.com');

$$a === $$b;                     // false — identity
$$a == $$b;                      // true  — components, because both are scalar-promoted
$$a->equals($$b);             // true  — explicit, always correct

For a value object with only scalar components, the engine’s default == already compares by component, which is convenient and frequently relied upon by accident. For one with an object component — a Money holding a DateTimeImmutable, or a Period holding two Date objects — == compares object components with === and therefore compares by identity, giving the wrong answer. Always provide an explicit equals() for any value object with a non-scalar component, and never rely on == for one.

Normalise in the constructor, then equality is free. A value object that lowercases and trims on construction has exactly one representation per semantic value, which means the database can hold a UNIQUE constraint on it and the domain can rely on it. A value object that stores the raw input has as many representations as the callers happen to produce, and every uniqueness check becomes a comparison with case folding and whitespace stripping that somebody has to remember to write.

5.2 Entities and identity

5.2.1 Lifecycle Methods

What an entity is, why it cannot be readonly, and how identity survives a round trip.

An entity has identity that is independent of its attributes: the customer with id 417 is the same customer even after the name changes. Identity must be assigned once and must never change, while the rest of the state may. This is why an entity cannot be a readonly class — a readonly entity is indistinguishable from a value object, and the database’s AUTO_INCREMENT key is then a value that must be known at construction time, which it cannot be before the insert.

// 5.2 Identity is readonly; everything else is not.

<?php

final class Customer {
    private ?int $id = null;
    public function __construct(
        private Email $email,
        private string $name,
        private DateTimeImmutable $createdAt,
    ) {}

    public function id(): ?int { return $this->id; }
    public function renameTo(string $name): void { $this->name = $name; }
    public function email(): Email { return $this->email; }

    // Called by the infrastructure layer once, after INSERT.
    public function assignId(int $id): void {
        if ($this->id !== null) {
            throw new LogicException('identity is assigned once');
        }
        $this->id = $id;
    }
}

The assignId() method is the seam through which the database reaches the domain, and it is a genuine compromise: it is the one place where an infrastructure concern appears in a domain class. The alternative is a second hydration constructor, which duplicates the constructor signature and doubles the maintenance. A third alternative is to generate the key in the application — a UUIDv7, or a Snowflake-style identifier — which removes the seam entirely at the cost of a wider index, since a random 16-byte primary key fragments the clustered index and defeats InnoDB’s sequential insert pattern. For a table under a few million rows, the application-generated key is usually the better trade; above that, AUTO_INCREMENT wins on index locality.

Never compare entities with ==. Two Customer instances with the same id and different names are the same customer; with == the engine compares all properties and answers false, and a foreach over two lists of the same customer will produce duplicates. Compare id(), and give the entity a sameIdentityAs() method so the comparison is named rather than repeated.

5.3 The mapper and the hydration boundary

5.3.1 Hydration Logic

Converting a row into an object graph without a constructor that touches the database.

The mapper is the only place in the system that knows both shapes. Its input is a row array keyed by column name; its output is a fully constructed object graph. Because it is the only place that knows both, it is also the only place that must change when a column is renamed — which is the correct and unavoidable coupling.

// 5.3 The mapper owns every column-to-property decision.

<?php

namespace Acme\Billing\Infrastructure\Persistence;

final class CustomerMapper {
    public function hydrate(array $row): Customer {
        return new Customer(
            new Email($row['email']),
            $row['name'],
            new DateTimeImmutable($row['created_at']),
        );
    }

    public function extract(Customer $c): array {
        return [
            'email'      => $c->email()->value,
            'name'       => $c->name(),
            'created_at' => $c->createdAt()->format('Y-m-d H:i:s'),
        ];
    }
}

Two implementation details are non-negotiable. First, the mapper must never call a query; it is a pure function of its arguments, and the moment it fetches something it becomes untestable in isolation and a source of hidden N+1 queries (14.3). Second, the mapper must be total: it either returns a valid object or throws. A ?? null in a mapper that silently produces a Customer with a null email turns a data integrity problem into a type error three layers away.

5.4 The anemic domain model trap

5.4.1 Rich Model Alternative

The legitimate CRUD architecture, the version of it that is a failure, and how to tell them apart.

An anemic domain model is one in which entities hold data and no behaviour, and all logic lives in service classes that read and write their properties. For a system whose use cases are create, read, update and delete, this is a defensible architecture: the service is a use case, the entity is a typed record, and the complexity lives in the database, which is very good at filtering and aggregation.

The trap is the version of this where the service classes are not use cases but property bags of setters. The symptom is a CustomerService with setName, setEmail, setStatus and no validation anywhere except a validator class that is invoked by the controller, which means the invariant holds only for the one entry point that remembered to call it.

SignalReading
Every entity property is public or has a bare getter and setterBehaviour has leaked into services; invariants are unenforceable
A validator class exists and is called from the controllerValidation is an entry-point concern, not a domain one
Services take scalars and return scalarsLikely correct: the use case is the service
Services take entities, mutate them and save themAmbiguous: decide which of the two you are
Domain classes contain no database typesCorrect under either architecture

The decision criterion is not purity, it is where the invariant lives. If a rule — "an order with no lines cannot be marked paid" — holds regardless of which code path is used, it belongs on the entity. If it holds only in the HTTP request path, it belongs in the application layer, and the database is the backstop. A rule that exists in one of these three places is enforced; a rule that exists in documentation is not.

5.5 Where invariants belong

5.5.1 Enforcing Invariants

The three enforcement points, and the cost of each.

Every invariant should be enforced in as few places as possible and at the lowest layer that can see all the facts required to check it. There are three candidate layers, and they are not equivalent in cost.

The database is the cheapest and the most authoritative, because it is the only layer that cannot be bypassed. A NOT NULL, a CHECK, a UNIQUE or a foreign key is enforced for every writer, including the one you forgot about, the migration script, and the analyst running a query at midnight. The cost is a constraint that fires as a driver error rather than as a domain exception, which is why it is the backstop and not the primary.

The entity is where a rule belongs when the rule needs more than one field, or a value object, or an external condition that has already been fetched. A rule the database can check with a CHECK should still be written here as well, so that a caller gets a precise exception rather than a driver error code.

The application layer is the only layer that can see other aggregates, so a cross-aggregate invariant belongs there and must be covered by a transaction wide enough to make the check meaningful (12.1).

Write each invariant once, as an executable test, and record which of the three layers enforces it. An invariant that appears in no layer is a comment; an invariant that appears in all three with slightly different logic is a future inconsistency. The target is one authoritative check per invariant plus a database backstop, with the two kept in agreement by a test that asserts the constraint exists in the schema.

6 · Exceptions, Error Handling, and Why finally Alone Is Not Enough

6.1 The Throwable hierarchy6.2 Designing a domain exception hierarchy6.3 Why finally alone is not enough6.4 Translating exceptions at the boundary6.5 Error handling without suppression

PHP separates recoverable conditions from engine faults, and a design that conflates the two produces code that catches too much. This chapter establishes the hierarchy as the engine defines it, argues for exceptions that name a domain condition rather than a message, shows why finally releases resources but does not restore state, and gives the translation layer that turns a driver exception into a domain one at exactly one place in the system.

6.1 The Throwable hierarchy

6.1.1 Exception Classes

The engine’s error model, and which branch a given condition belongs to.

Everything that can be thrown implements Throwable, which has two direct children. Exception is the base for conditions a program is expected to handle: a failed query, a malformed record, a rejected argument. Error is the base for conditions that indicate a programming fault: a type mismatch, an undefined method, an exhausted memory limit, a failed assertion.

Catching Exception is normal. Catching Error is a statement that a programming fault is expected at this point, and it is almost always a mistake — with two defensible exceptions. The first is a top-level handler that must convert an uncaught fault into a 500 response and a log entry rather than a blank page. The second is a batch or queue worker, which must record the failure and continue with the next item instead of dying on a single malformed record.

// 6.1 The hierarchy, as the engine defines it.

<?php

interface Throwable {}
class Exception implements Throwable {}
class Error implements Throwable {}

// Exception subtree: all recoverable.
Exception            LogicException          RuntimeException
  BadFunctionCallException                    PDOException
    BadMethodCallException                    UnexpectedValueException
  InvalidArgumentException                    OutOfRangeException
  DomainException        // the root of your own hierarchy

// Error subtree: all programming faults.
Error                TypeError              ValueError
  ArgumentCountError    DivisionByZeroError   UnhandledMatchError
  ArithmeticError       ParseError            AssertionError

Two members of this tree carry more weight than the rest. TypeError is thrown when a strict declaration rejects a value, and it is the mechanism by which 4.5 is enforced. ValueError is distinct from InvalidArgumentException and is thrown by engine functions when a value is well-typed but outside the permitted domain — Enum::from('nope') throws ValueError, not InvalidArgumentException, and a catch (InvalidArgumentException) will not catch it. Any mapper that hydrates an enum must handle ValueError explicitly or use tryFrom(), which returns null instead of throwing.

PDOException derives from RuntimeException, not from a persistence-specific class, which means a broad catch (RuntimeException) in a service will swallow database failures along with everything else. If your application catches RuntimeException anywhere, the next bug report will be a generic 500 with no indication that a query failed. Narrow the catch to the exception types you actually intend to handle.

6.2 Designing a domain exception hierarchy

6.2.1 Hierarchy Design

Exceptions that name a condition rather than a message, and the cost of a deep hierarchy.

A domain exception should be catchable without parsing its message. If the only way for a caller to distinguish "the order is already paid" from "the order does not exist" is to match on a string, then the exception is a data structure with a bad accessor and the caller is doing the dispatch the hierarchy should have done.

// 6.2 A shallow hierarchy with machine-readable context.

<?php

namespace Acme\Billing\Domain\Exception;

final class DomainException extends \DomainException {}

final class OrderNotFound extends DomainException {
    public function __construct(public readonly int $orderId) {
        parent::__construct(sprintf('order %d does not exist', $orderId));
    }
}

final class OrderAlreadyPaid extends DomainException {
    public function __construct(public readonly int $orderId) {
        parent::__construct(sprintf('order %d is already paid', $orderId));
    }
}

try {
    $this->orders->markPaid($id);
} catch (OrderNotFound $e) {
    throw new NotFoundHttpException($sprintf('/orders/%d', $e->orderId));
} catch (OrderAlreadyPaid $e) {
    return new JsonResponse(['error' => 'already_paid'], 409);
}

Keep the hierarchy shallow — a base class plus one level of concrete leaves — because every additional level is a decision about which catch clauses are correct, and a deep tree produces a combinatorial problem. Carry structured data as promoted readonly properties rather than as message text, so a caller can branch on $e->orderId without parsing. And prefer one exception per condition to one exception per class of failure: an OrderAlreadyPaid that is also a NotFound is two exceptions, and the caller must be able to catch either.

Extend \DomainException or \RuntimeException, never Exception directly. A caller that wants to catch "anything this domain considers invalid" catches the base, and it works for every future leaf without modification. Also: do not use exceptions for control flow that happens routinely. A find() that returns null and a get() that throws OrderNotFound is the correct pair; a find() that throws is not.

6.3 Why finally alone is not enough

6.3.1 Lifecycle Handling

What finally guarantees, and the two things it does not.

finally runs unconditionally on both the normal and the exceptional path, and it is the correct construct for releasing a resource. It does not do two things. It does not restore state: a transaction left open by an exception is still open when finally completes, and the next statement in the same request will run inside a transaction it does not know about. And it does not decide outcome: a finally block that logs and continues lets the original exception propagate, which is right, but a finally that returns a value silently discards the in-flight exception, which is catastrophic and is legal PHP.

// 6.3 finally releases; it does not restore state or decide outcome.

<?php

$pdo->beginTransaction();
try {
    $repo->add($order);
    $mailer->send($message);   // throws
    $pdo->commit();
} catch (Throwable $e) {
    $pdo->rollBack();          // restores state
    throw $e;
} finally {
    $$stmt->closeCursor();          // releases a resource
}

// Legal PHP, and a data-loss bug: the exception is discarded.
function broken(): int {
    try {
        throw new RuntimeException('boom');
    } finally {
        return 0;   // the throw never happens
    }
}

The rule that avoids both problems: finally releases resources only, and state restoration belongs in catch with an explicit rethrow. This is why the transaction wrapper in 12.1 is a separate class rather than a base class with a template method — it must be able to guarantee that the rollback happens and that the original exception, not a wrapper, reaches the caller.

Resource release is easier in PHP 8 than it was in 7 because try-with-resources is unnecessary: an object with a destructor releases its handle, and a generator abandoned mid-iteration is closed when it goes out of scope. The cases that still need finally are the ones with no destructor — a PDOStatement cursor held across a long loop, and a temporary file handle. Do not write finally blocks for objects; write them for cursors and handles.

6.4 Translating exceptions at the boundary

6.4.1 Exception Translation

The single place a PDOException becomes a domain exception.

The layering established in 0.4 requires that no domain or application class imports PDOException. That is achieved by translating once, inside the repository, using the driver error code and SQLSTATE rather than the message text. MySQL exposes a numeric error code and a five-character SQLSTATE, and both are stable and documented.

// 6.4 One translation point. Nothing else in the app sees PDOException.

<?php

namespace Acme\Billing\Infrastructure\Persistence;

final readonly class DriverErrorMap {
    public const int DUPLICATE_KEY      = 1062;
    public const int NO_REFERENCED_ROW = 1452;
    public const int ROW_IS_REFERENCED = 1451;
    public const int CHECK_VIOLATED    = 3819;
    public const int LOCK_DEADLOCK      = 1213;
    public const int LOCK_TIMEOUT       = 1205;
}

final class PdoExceptionTranslator {
    public function translate(\PDOException $e): DomainException {
        $sqlstate = $e->getCode();
        $driver    = $e->errorInfo[1] ?? null;

        return match (true) {
            $driver === DriverErrorMap::DUPLICATE_KEY
                => new DuplicateIdentifier($e->getMessage(), 0, $e),
            $driver === DriverErrorMap::NO_REFERENCED_ROW
                => new UnknownReference($e->getMessage(), 0, $e),
            $sqlstate === '40001'
                => new ConcurrentModification($e->getMessage(), 0, $e),
            default => new StorageFailure($e->getMessage(), 0, $e),
        };
    }
}

Passing the original PDOException as the third constructor argument sets getPrevious(), so the full driver context — including the SQLSTATE and the driver code — survives into the log without appearing in the domain type. This is the mechanism that lets a domain exception stay domain-shaped while a log entry remains diagnosable. Note that getCode() on PDOException returns the SQLSTATE string, while errorInfo[1] holds the MySQL numeric code; both are needed because different conditions are distinguishable on one axis and not the other.

6.5 Error handling without suppression

6.5.1 Handling Strategies

A review checklist for exception handling, and the three patterns that are always wrong.

Three patterns account for most of the exception-handling defects in production PHP. The first is the empty catch: catch (Throwable $e) {}, which converts a failure into a silent wrong answer. The second is the log-and-continue catch, which converts a failure into a partially written state — worse than a crash, because the process continues. The third is catch (Exception $e) around a block that includes database writes, which catches a constraint violation and continues with a transaction that must now be rolled back.

// 6.5 The three shapes that survive review.

// 1. Handle and recover: the caller has a better answer.
try {
    return new JsonResponse($$this->orders->get($id));
} catch (OrderNotFound $e) {
    return new JsonResponse(['error' => 'not_found'], 404);
}

// 2. Translate and rethrow: the layer changes, the fact does not.
catch (\PDOException $e) {
    throw $this->translator->translate($e);
}

// 3. Boundary: log once, convert to a response, stop.
catch (Throwable $e) {
    $this->log->error('unhandled', ['exception' => $e]);
    return new JsonResponse(['error' => 'server_error'], 500);
}

The review question for every catch block is: after this block, what does the system believe? If the answer is "the same thing, plus a log line", the block is doing nothing and should be removed or the underlying operation should be made idempotent and retried — which is a real strategy for deadlock and lock-timeout errors, and a fabrication for a constraint violation. Retrying a duplicate-key insert will never succeed; retrying a deadlock usually will, within a bounded attempt count and with jittered backoff.

One exception to "never catch Error" is worth stating precisely: an out-of-memory condition in a long-running worker. Error for memory exhaustion leaves the request or job in an unknown state, and the only safe response is to log, mark the current unit of work as failed, and let the supervisor restart the process. Catching it and continuing in the same process is not safe, because the allocator state is not guaranteed to be consistent.

7 · Iterators, Generators and Lazy Evaluation in PHP

7.1 The iterator contract7.2 Generators and yield7.3 Lazy evaluation and the cursor7.4 Pipelines, delegation and keys7.5 Materialisation and memory

Lazy evaluation is not a stylistic preference in a persistence stack — it is the difference between streaming a entire result set and running out of memory on it. This chapter covers the iterator interfaces PHP provides, the generator semantics that differ from a hand-written iterator in ways that matter, the unbuffered MySQL cursor, and the delegation pattern that composes generators into pipelines.

7.1 The iterator contract

7.1.1 Iterator Methods

Which interface to implement, and the difference between the aggregate and the cursor interfaces.

PHP defines a family of iterator interfaces. Iterator requires four methods plus a count(). IteratorAggregate requires one method, getIterator(), returning any Traversable — and this is the interface to implement in application code, because a generator returned from getIterator() satisfies it in one line. SeekableIterator adds seek(), which a database cursor cannot honour, and ArrayAccess adds offset access, which forces materialisation.

// 7.1 IteratorAggregate: one method, no state to keep consistent.

<?php

namespace Acme\Billing\Domain;

final readonly class OrderLines implements \IteratorAggregate, \Countable {
    public function __construct(private array $items) {}

    public function getIterator(): \Traversable {
        yield from $this->items;
    }

    public function count(): int { return count($this->items); }
}

foreach ($$lines as $$line) { /* works; getIterator() is called implicitly */ }
count($$lines);              // works; Countable is implemented

Do not implement Iterator directly unless you are building a cursor abstraction that must be resumable and inspectable. A hand-written Iterator has an internal position that must be kept consistent with the underlying data across valid(), current(), next(), key() and rewind(), and every one of those is a place to introduce a bug. A generator receives all five from the engine and cannot get them wrong.

Because PHP 8.1 made every object Traversable, a foreach over a plain object iterates its public properties, not its accessors. An entity with public properties therefore leaks its internal representation into every foreach in the codebase. This is the practical reason to prefer private properties with explicit accessors for anything that is not a value object, and it composes with the IteratorAggregate decision above.

7.2 Generators and yield

7.2.1 Yield Details

The four generator operations, the send-and-return protocol, and the two behaviours that surprise newcomers.

A function containing yield returns a Generator and does not execute its body until iteration begins. The generator is single-use: once iteration finishes or the generator is closed, it cannot be restarted, and a second foreach over the same variable produces nothing and raises a warning. yield from delegates to another iterable and, since PHP 7.0, forwards send(), throw() and getReturn() as well as values and keys.

// 7.2 Keys are yours to choose; a generator is single-use.

<?php

function bySku(Order $order): \Generator {
    foreach ($order->lines() as $line) {
        yield $line->sku => $line;   // string key, not an index
    }
}

$$gen = bySku($order);
foreach ($$gen as $sku => $line) { /* $sku is 'A-1', 'B-2', ... */ }
foreach ($$gen as $x) { }   // no iterations: already consumed

// array_key_exists() and isset() do not work on a Generator —
// it has no key index. Use iterator_to_array() if you need one.

Two features are used constantly in production code and are rarely explained. $generator->send($value) passes a value into the suspended yield expression, which is how a coroutine receives input. $generator->getReturn() returns the value of the eventual return statement, which runs only after the generator is exhausted — a convenient way to compute a summary while streaming, such as the row count or a running total, without buffering.

Use yield to stream, not to be clever. A generator that yields inside a loop over a database cursor holds one database connection open for the whole iteration, and a second query on that connection while the cursor is open is a protocol error under the unbuffered mode described in 7.3. If a pipeline needs two streams at once, materialise one of them with iterator_to_array() and stream the other.

7.3 Lazy evaluation and the cursor

7.3.1 Configuration

Configuring PDO for unbuffered reads and knowing exactly when the buffer ends.

By default, PDO::query() on MySQL buffers the entire result set in client memory before returning a statement. This is invisible for small results and fatal for large ones, and the option that changes it is PDO::ATTR_USE_BUFFERED_QUERY. With it set to false, rows arrive from the wire as they are consumed.

// 7.3 Unbuffered: one row in memory at a time.

<?php

$pdo = new \PDO($dsn, $user, $password, [
    \PDO::ATTR_ERRMODE            => \PDO::ERRMODE_EXCEPTION,
    \PDO::ATTR_EMULATE_PREPARES   => false,
    \PDO::ATTR_USE_BUFFERED_QUERY => false,   // no client-side buffer
    \PDO::ATTR_STRINGIFY_FETCHES  => false,
]);

$$stmt = $$pdo->query('SELECT id, email FROM customers ORDER BY id', \PDO::FETCH_ASSOC);

while ($$row = $$stmt->fetch()) {
    // exactly one row is resident. The server holds the rest
    // in its own buffers, subject to net_buffer_length and
    // max_allowed_packet.
    process($row);
}

// Unbuffered mode forbids a second statement on the same
// connection while the cursor is open:
//   $pdo->query('SELECT ...');   // MySQL server has gone away

The critical constraint is that unbuffered mode holds the connection exclusively until the cursor is exhausted or closed. Running a second query on the same PDO instance before finishing the first raises a protocol error, and calling $stmt->fetchAll() on an unbuffered statement is legal only because it drains the cursor first. The solution used throughout this guide is one connection per unit of work (15.1), which makes the restriction harmless because there is never a second statement to run.

Unbuffered mode also changes what query() returns: the statement is active from the moment it is created, so a slow consumer holds a server-side cursor and a connection. A cursor left open while a SELECT is being streamed from a table that another transaction is updating will hold locks on the rows it has read, and in InnoDB a streaming read under REPEATABLE READ holds a read view open for the duration. Prefer unbuffered mode for exports and batch jobs, and buffered mode for request-scoped queries with a LIMIT.

7.4 Pipelines, delegation and keys

7.4.1 Delegation Pattern

Composing generators with yield from, and the key-collapsing behaviour to watch for.

Because a generator is just an iterable, transformations are ordinary functions. Composing them with yield from produces a pipeline in which only one element is live at a time, and the intermediate collections never exist. This is the correct shape for a large export and the incorrect shape for anything that needs random access.

// 7.4 A streaming pipeline over an unbuffered cursor.

<?php

function filterRows(\Traversable $rows, callable $p): \Generator {
    foreach ($$rows as $key => $row) {
        if ($p($row)) { yield $key => $row; }
    }
}

function mapRows(\Traversable $rows, callable $f): \Generator {
    foreach ($$rows as $key => $row) { yield $key => $f($row); }
}

function batch(\Traversable $$rows, int $size): \Generator {
    $chunk = [];
    foreach ($$rows as $row) {
        $chunk[] = $row;
        if (count($chunk) >= $size) { yield $chunk; $chunk = []; }
    }
    if ($chunk !== []) { yield $chunk; }
}

$$pipeline = batch(
    mapRows(filterRows($$stmt, fn(array $r) => $r['status'] === 'paid'), fn(array $r) => $r['email']),
    1000,
);

Two details decide whether this is correct. Keys are preserved by mapRows and filterRows, so the batch numbers reflect original row positions rather than a dense re-index — usually what you want in an audit trail, occasionally a surprise. And yield from on a Traversable that is a PDOStatement is the delegation that makes the whole thing work: the pipeline never materialises the result set, and each batch is the largest object that exists at any moment.

Do not use array_map(), array_filter() or array_column() inside a pipeline intended to stream. They take and return arrays, so the moment one appears in the chain the entire input is materialised and the memory profile of the pipeline is the memory profile of the largest array. Use array_map() only after an explicit iterator_to_array(), where materialisation is the intent.

7.5 Materialisation and memory

7.5.1 Memory Management

Choosing the point at which a stream becomes an array, and the arithmetic that decides it.

Materialisation converts a stream into an array and is the point at which memory becomes proportional to row count rather than to one row. The decision is arithmetic: a row of 400 bytes at 1 million rows is roughly 400 MB, plus PHP’s per-element hash overhead, which for a typical associative row is closer to 900 bytes. The default memory_limit for a CLI process is often unlimited and for FPM is commonly 128M or 256M, so the threshold at which a naive fetchAll() fails is far lower than intuition suggests.

// 7.5 Batching with a prepared statement and bound LIMIT.

<?php

final class CustomerStream {
    public function stream(\PDO $pdo, int $batchSize = 500): \Generator {
        $$lastId = 0;
        do {
            $$stmt = $$pdo->prepare(
                'SELECT id, email, name FROM customers WHERE id > :after ORDER BY id LIMIT :n'
            );
            $$stmt->bindValue(':after', $$lastId, \PDO::PARAM_INT);
            $$stmt->bindValue(':n', $$batchSize,  \PDO::PARAM_INT);
            $$stmt->execute();

            $$rows = $$stmt->fetchAll(\PDO::FETCH_ASSOC);
            foreach ($$rows as $$row) {
                $$lastId = $$row['id'];
                yield $$row;
            }
        } while (count($$rows) === $$batchSize);
    }
}

Keyset pagination — WHERE id > :after ORDER BY id LIMIT :n — is used here rather than OFFSET because offset pagination makes the server read and discard every skipped row, so the cost of page 9000 is 9000 times the cost of page 1. It is also stable: rows inserted while the scan is running do not cause an item to be skipped, which is exactly the bug that OFFSET pagination has. The cost is that the caller must know the sort column, which means a repository method designed for streaming must be documented in terms of its ordering.

Where materialisation is correct, do it deliberately and with a limit. A screen listing 25 rows should have a LIMIT 25 in the statement rather than a fetchAll() followed by array_slice() in PHP — the second form transfers the entire table across the network in order to discard all but 25 rows. Reserve iterator_to_array() for pipelines that will be traversed more than once, since a generator is single-use.

8 · Attributes, Reflection, and Code That Reads Its Own Metadata

8.1 Attribute syntax and targets8.2 Reading attributes at runtime8.3 Reflection over types and signatures8.4 Metadata-driven behaviour8.5 The limits worth respecting

Attributes put machine-readable metadata in the source without a runtime cost and without a docblock parser. They are only worth using where the metadata is genuinely consumed at runtime, and this chapter is specific about which those cases are: routing, validation, ORM mapping and framework-free dependency injection. It also covers the reflection APIs that make the metadata actionable, and the costs that appear once a system reads its own declarations.

8.1 Attribute syntax and targets

Declaring an attribute, constraining where it may be applied, and passing constructor arguments.

An attribute is a class. Declaring one uses the #[] syntax at the point of use and the #[Attribute] marker on the class itself, which declares the target flags. The default target is TARGET_ALL, which is almost never what you want; constraining the target turns an accidental misapplication into a fatal error at the point of the mistake.

// 8.1 A class-attribute with named constructor arguments.

<?php

use Attribute;

#[Attribute(Attribute::TARGET_CLASS | Attribute::TARGET_IS_REPEATABLE)]
final class Route {
    public function __construct(
        public readonly string $method,
        public readonly string $pattern,
        public readonly string $name = '',
    ) {}
}

#[Route(method: 'GET',  pattern: '/orders/{id}')]
#[Route(method: 'POST', pattern: '/orders')]
final class OrderController {}

Attribute arguments must be constant expressions, so literals, class constants and enum cases are permitted while variables and function calls are not. Named arguments are supported and are strongly preferred, because positional arguments in an attribute are unreadable at the call site — nothing tells you that the second string is the pattern and not the name. new in initialisers, added in PHP 8.1, permits an object as an attribute argument as long as its constructor arguments are themselves constant expressions.

Mark a metadata class final readonly and give every property a type. The engine instantiates the attribute object for you, and a mutable attribute class is a class whose contents can change between the declaration site and the point of use — a bug that only appears when the same attribute is read in two different orders.

8.2 Reading attributes at runtime

The three reflection methods that read attributes, their caching cost, and the failure mode of an unchecked read.

ReflectionClass::getAttributes() returns attribute instances without constructing their arguments, which is the cheap path and the one to use for filtering by class name. ReflectionAttribute::newInstance()ReflectionAttribute::getArguments() returns the raw constant-expression arguments, which is cheaper still and sufficient when only a scalar is needed. Passing ReflectionAttribute::IS_INSTANCEOF as the second argument to getAttributes() filters by interface or parent class and avoids loading unrelated attribute classes.

// 8.2 Filtering without instantiating, then instantiating one.

<?php

final class Router {
    /** @var list<array{method:string,pattern:string,class:string}> */
    private array $$routes = [];

    public function scan(string $directory): void {
        foreach (glob($directory . '/*Controller.php') as $$file) {
            $$fqcn = basename($$file, '.php');
            $$rc   = new \ReflectionClass('App\\Controller\\' . $$fqcn);

            foreach ($$rc->getAttributes(Route::class) as $$attr) {
                $$route      = $$attr->newInstance();
                $$this->$routes[] = [
                    'method'  => $$route->method,
                    'pattern' => $$route->pattern,
                    'class'   => $$fqcn,
                ];
            }
        }
    }
}

Every attribute read is a cache miss on the first call and a cache hit afterwards, but the set of attributes for a class is cached per reflection object, not globally. A router that scans several hundred controllers therefore pays several hundred attribute constructions per request unless the resulting route table is built once and cached — which is a generated-file or a serialised-array problem, not a reflection problem. A second failure mode is an unchecked read: newInstance() on an attribute whose constructor throws propagates that exception into the scanner, and a single malformed controller then makes the entire application unroutable.

Never eval or otherwise execute a string derived from an attribute argument. An attribute is not a sandbox: it is arbitrary constant expressions evaluated at scan time, and routing to a class named in an attribute means the scanner is willing to load any class the attribute mentions. Restrict the scanned directory and validate the class exists with class_exists() before reflecting on it.

8.3 Reflection over types and signatures

Reading parameter and return types, resolving names, and why the container in chapter 9 needs all of it.

Reflection over a method’s signature yields ReflectionParameter and ReflectionType objects. The three cases a resolver must handle are a named type — which may be a class, an interface, or a builtin — a union type, and an intersection type. A nullable named type is reported as a ReflectionNamedType whose allowsNull() returns true, not as a union with null, and confusing the two is a common source of nulls being injected where an object was required.

// 8.3 Resolving a signature into a list of class names.

<?php

final class SignatureReader {
    /** @return list<class-string> */
    public static function classNames(\ReflectionType $type): array {
        if ($type instanceof \ReflectionIntersectionType) {
            return array_map(
                static fn(\ReflectionType $t) => self::nameOf($t),
                $type->getTypes(),
            );
        }

        if ($type instanceof \ReflectionUnionType) {
            return array_map(
                static fn(\ReflectionType $t) => self::nameOf($t),
                $type->getTypes(),
            );
        }

        return [self::nameOf($type)];
    }

    private static function nameOf(\ReflectionType $t): string {
        if (!$t instanceof \ReflectionNamedType) { return ''; }
        if ($t->isBuiltin()) { return ''; }
        return $t->getName();   // already FQCN
    }
}

Two details matter for the container in 9.3. A class name obtained from reflection is already fully qualified, resolved against the file’s use statements, so no namespace prefixing is required — but only if the class or interface has actually been autoloaded when reflection ran. And a default value is available on the ReflectionParameter, so a scalar with a default needs no resolution at all: pass the default. This is what makes a container able to construct a class with four scalars and one service without any registration for the class at all.

8.4 Metadata-driven behaviour

The four uses of attributes that genuinely pay, and the SQL that one of them generates.

Attributes pay for themselves where the same information is needed in two places and would otherwise drift. The canonical case is a column mapping: the PHP property name and the SQL column name must agree, and if they are stated twice a rename breaks one of them silently.

// 8.4 Column metadata, consumed by the mapper and by the migrator.

<?php

#[Attribute(Attribute::TARGET_PROPERTY)]
final class Column {
    public function __construct(
        public readonly string $name,
        public readonly string $type = 'VARCHAR(255)',
        public readonly bool $nullable = false,
    ) {}
}

final class Customer {
    private readonly int $id;

    #[Column(name: 'email',       type: 'VARCHAR(320)')]
    private readonly Email $email;

    #[Column(name: 'name',        type: 'VARCHAR(120)')]
    private readonly string $name;

    #[Column(name: 'created_at',  type: 'DATETIME(6)')]
    private readonly DateTimeImmutable $createdAt;
}

// The migrator reads the same metadata to emit DDL, so the
// schema and the mapper cannot disagree about a column name.

The value here is the second consumer. A single source of column names drives the mapper, the migrator, and any export or import tooling, and a rename becomes a single edit. The risk is that the metadata becomes a schema in disguise — an attribute carrying a nullable flag, a default, an index and a foreign key is a migration file expressed in PHP, at which point you have gained reflection cost and lost the ability to read the schema with SHOW CREATE TABLE. Keep attributes to the mapping, and keep the constraints in the migration.

Attributes are evaluated lazily and cached, but reading them is still an order of magnitude more expensive than reading a constant. In a request-scoped path, the cost is irrelevant because the scan happens once at boot. In a CLI worker that processes ten million rows, a per-row attribute read is a measurable regression; read the metadata into a typed structure once and pass the structure into the loop.

8.5 The limits worth respecting

Four situations in which a docblock, a config file, or plain code is the better instrument.

Attributes are not universally the right instrument, and the cases where they are wrong are recognisable. When the metadata is needed by a static analyser rather than at runtime — a @param annotation, a return type for inference, a @var on a property — a docblock is the correct form, because a static analyser reads docblocks and ignores attributes except where explicitly supported. When the metadata must be read by a non-PHP tool, a docblock is again correct, and this is the entire reason the generic annotations in 4.3 remain docblocks.

When the metadata describes something that is not attached to a declaration — a global setting, a retry policy, a feature flag — there is nowhere to put it, and a configuration file is clearer. And when the relationship is one-to-many with a value — "this property maps to this column with this converter" — a small explicit mapper is more readable than five nested attributes, because a reader can see the whole mapping in one screen instead of navigating to each property.

A useful test before adding an attribute: ask what happens when it is wrong. If a wrong value produces a wrong query, a wrong route or a wrong file path, the attribute is worth its cost because the failure is loud and immediate. If a wrong value produces subtly incorrect behaviour three layers away, prefer a construct the reader can evaluate at a glance — usually a method call in the code that uses it.

9 · Dependency Injection Without a Framework: A Workable Container

9.1 Constructor injection and the null object9.2 Registrations and the object graph9.3 Resolution, autowiring and singletons9.4 Scopes and lifecycle9.5 Factories as the escape hatch

A dependency injection container is a service locator with a cache in front of it, and about 150 lines of PHP is enough to build one that satisfies PSR-11 and autowires a graph by reflection. This chapter builds that container: registrations, resolution with cycle detection, singleton and transient scopes, and the factory registrations that cover everything autowiring cannot express. The point is not to replace a framework but to make the framework’s behaviour legible.

9.1 Constructor injection and the null object

Why every collaborator arrives through the constructor, and what to do when there is genuinely none.

Constructor injection has one property that matters more than the others: it makes the dependency graph explicit and finite. Every edge in the graph is visible on a class declaration, which means the graph can be read, tested and reasoned about without executing anything. Setter injection, property injection and static access all break that property in different ways — a service locator in particular makes the graph infinite and unnameable, because any class can reach any other at any point.

The problem constructor injection creates is optional dependencies. A logger that is only used on a rare path, a clock that a test wants to replace, a mailer that a dry-run mode disables — a nullable type pushes the null check onto every call site, and a call site that forgets the check produces a TypeError or a fatal on a null method call.

// 9.1 The null object removes the null check from every call site.

<?php

interface Mailer {
    public function send(Message $m): void;
}

final class NullMailer implements Mailer {
    public function send(Message $m): void {
        // deliberately does nothing
    }
}

final class OrderNotifier {
    public function __construct(private Mailer $mailer) {}  // not ?Mailer

    public function paid(Order $o): void {
        $this->mailer->send(new Message($o));  // no guard needed
    }
}

A null object is not the same as a fake. A fake is a test double with observable behaviour a test asserts on; a null object is a production implementation that intentionally does nothing, used for dry runs and for the case where the dependency genuinely does not apply. The discipline that matters is that the null object must implement the full interface, so that promoting it to a real implementation later is a container change and not a code change.

9.2 Registrations and the object graph

The three registration forms and the data structure that holds them.

Every container reduces to one map from string identifier to one of three things: a class name to instantiate, a closure to call, or an already-constructed instance to return. Binding by interface name is what makes the container useful, because the interface is the type the consumer depends on. Binding the same identifier to a different class is the entire mechanism by which a production database is replaced with an in-memory array in a test.

// 9.2 Registrations: shared instances, factories, and values.

<?php

final class Container implements \Psr\Container\ContainerInterface {
    /** @var array<string, \Closure(\Psr\Container\ContainerInterface):mixed> */
    private array $$factories = [];

    /** @var array<string, mixed> */
    private array $$shared = [];

    public function singleton(string $id, \Closure $factory): void {
        $$this->$factories[$id] = $factory;
        unset($$this->$shared[$id]);
    }

    public function instance(string $id, mixed $value): void {
        $$this->$shared[$id] = $$value;
    }

    public function get(string $id): mixed {
        if (array_key_exists($id, $$this->$shared)) {
            return $$this->$shared[$id];
        }
        if (!isset($$this->$factories[$id])) {
            $$this->$factories[$id] = fn(ContainerInterface $$c) => $$c->get($id);  // autowire
        }
        $$value = ($$this->$factories[$id])($$this);
        $$this->$shared[$id] = $$value;
        return $$value;
    }

    public function has(string $id): bool {
        return isset($$this->$shared[$id]) || isset($$this->$factories[$id]) || class_exists($id);
    }
}

Note that the fall-through registration in get() makes every class name autowirable with no explicit entry, which is what keeps the registration list short: only interfaces and classes needing arguments are registered. The PSR-11 has() contract requires a return of false rather than an exception for an unknown identifier, and get() must throw NotFoundExceptionInterface for the same identifier — the two methods have deliberately different failure modes and a container that conflates them is not PSR-11 compliant.

9.3 Resolution, autowiring and singletons

Constructing an object from its signature, and the three conditions that must be detected rather than attempted.

Autowiring means constructing a class by reading its constructor with reflection and resolving each parameter: a class or interface type is requested from the container recursively, a builtin with a default uses the default, a builtin without a default is an unresolvable registration error, and a variadic is skipped. The implementation is short, and the three failure conditions it must detect are the difference between a useful error message and a fatal.

// 9.3 Reflection-based construction with cycle detection.

<?php

private array $$resolving = [];

private function build(string $class): object {
    if (isset($$this->$resolving[$class])) {
        throw new \RuntimeException(sprintf(
            'circular dependency: %s', implode(' -> ', [...array_keys($$this->$resolving), $class]),
        ));
    }

    $$ctor = (new \ReflectionClass($class))->getConstructor();
    if ($$ctor === null) { return new $class(); }

    $$this->$resolving[$class] = true;
    try {
        $$args = [];
        foreach ($$ctor->getParameters() as $$param) {
            $$type = $$param->getType();

            if (!$$type instanceof \ReflectionNamedType || $$type->isBuiltin()) {
                if ($$param->isDefaultValueAvailable()) {
                    $$args[] = $$param->getDefaultValue();
                    continue;
                }
                throw new \RuntimeException(sprintf(
                    'unresolvable parameter $%s of %s: register it explicitly',
                    $$param->getName(), $class,
                ));
            }

            $$name = $$type->getName();
            $$args[] = $$type->allowsNull() && !$$this->has($$name)
                ? null
                : $$this->get($$name);
        }

        return new $$class(...$$args);
    } finally {
        unset($$this->$resolving[$class]);
    }
}

The three conditions are: a circular dependency, a builtin without a default, and a non-class type. Detecting all three explicitly turns a stack overflow, a TypeError at construction, and a silently ignored parameter into three messages that name the class and the parameter. The finally is not optional here — without it, one failed resolution leaves the class marked as resolving and every subsequent request for it reports a circular dependency that does not exist.

Autowiring a class whose constructor takes a union or an intersection type is a known limitation of this implementation and of most lightweight containers. The resolver above only handles ReflectionNamedType; a union falls into the unresolvable branch and produces a message telling you to register explicitly. This is a feature, not a defect: a union-typed dependency is a design signal that the class does too much.

9.4 Scopes and lifecycle

Choosing the scope of each service, and the one service that must never be a singleton across requests.

A singleton is shared for the lifetime of the container; a transient is constructed per resolution. Scope must be decided per service, and the decision follows from what state the service holds. A stateless repository is a candidate for either. A unit of work, a transaction, a request-scoped cache and anything holding an open cursor must be transient or explicitly request-scoped, because sharing one across two units of work means the second inherits the first’s open transaction.

// 9.4 One connection per unit of work — never shared process-wide.

<?php

$$container->singleton(OrderRepository::class, static fn(ContainerInterface $$c) =>
    new PdoOrderRepository($$c->get(PDO::class)));

// The PDO itself is a shared instance, but the container that
// holds it is created fresh per request, so "shared" means
// "shared for this request", not "shared forever".
$$container->instance(PDO::class, ConnectionFactory::create($$dsn, $$user, $$pass));

// In a long-running worker, replace the PDO instance at the end
// of every job. A pooled worker that reuses a connection across
// jobs inherits another job's session variables and temp tables.
//   $container->instance(PDO::class, ConnectionFactory::create(...));

The distinction that trips teams up is between a container per request and a container per process. In PHP-FPM, a request-scoped container is free — the process does not outlive the request, so "singleton" and "request-scoped" are the same thing. In a queue worker or a long-running consumer, they diverge: a process-scoped container holding a PDO singleton will hand a connection to job 4000 that job 1 opened, with job 1's @@session.sql_mode, its temporary tables and its uncommitted state if the previous job failed. The fix is either a container per job, or an explicit reset of the shared state at the job boundary.

Because PDO is stateful, it is the correct singleton within a request and the incorrect singleton across a worker’s job loop. The general rule: a singleton may hold only state that is valid for the whole of its lifetime. Configuration read once is valid; a transaction, a cursor, a session variable and an identity-map cache are not.

9.5 Factories as the escape hatch

The four things autowiring cannot do, and the registrations that cover them.

Autowiring fails in four predictable situations, and each has a registration that resolves it without changing any class. A scalar argument that varies per call site, a variadic, a class needing a named argument, and a factory that builds a configured instance — all four are expressed as closures in the registration file, which means the composition root is the only place that knows the concrete implementations.

// 9.5 The composition root. The only file that knows which is which.

<?php

// config/services.php — returns a configured Container.

$dsn  = sprintf('mysql:host=%s;port=%d;dbname=%s;charset=utf8mb4',
    $getenv('DB_HOST'), 3306, getenv('DB_NAME'));
$$debug = $getenv('APP_DEBUG') === '1';

$$container = new Container();

// Infrastructure bindings.
$$container->instance(PDO::class, ConnectionFactory::create($$dsn, $$config['db']['user'], $$config['db']['password']));
$$container->singleton(LoggerInterface::class, static fn() => new StreamLogger($$debug ? 'php://stderr' : '/var/log/app.log'));
$$container->singleton(ClockInterface::class, static fn() => new SystemClock());

// Environment-dependent substitutes, decided in one place.
$$container->singleton(Mailer::class, static fn() =>
    $$_ENV['MAIL_DRIVER'] === 'null'
        ? new NullMailer()
        : new SmtpMailer($$_ENV['SMTP_HOST'], 587, $$_ENV['SMTP_USER']));

// A scalar the autowirer cannot supply.
$$container->singleton(InvoiceNumberPolicy::class, static fn(ContainerInterface $$c) =>
    new SequenceNumberPolicy($$c->get(PDO::class), 'ORD-2026-', 6));

return $$container;

Two properties of this file are worth protecting. It is the only place that imports both the domain interfaces and the infrastructure implementations, so the dependency graph has exactly one root and the direction test in 0.4 has a single place to fail. And it is the only file that reads environment variables for the composition of the object graph, so a test can substitute the entire configuration by passing a different container to the same entry point.

Do not let the container reach into itself for configuration. A registration that calls $c->get(Config::class) to obtain a string is a registration that should have taken a value. Configuration belongs in an array read once at boot, and the registrations close over it — which makes the whole graph inspectable by printing the registration list in a test.

10 · PSR Standards: PSR-1, PSR-4, PSR-7, PSR-11, PSR-3 and PSR-12

10.1 PSR-1 and PSR-12: basic and extended style10.2 PSR-4: autoloading and directory layout10.3 PSR-7 messages and PSR-15 handlers10.4 PSR-11 containers and PSR-17 factories10.5 PSR-3 logging and the others that matter

The PSR family is a set of interfaces agreed between independent projects, and it is the only interoperability mechanism PHP has. This chapter covers the six standards that a persistence codebase actually depends on: two style standards, autoloading, HTTP messages, containers and log records. The recurring point is that a PSR is an interface, not an implementation — adopting one costs nothing and makes your components replaceable by anybody else’s.

10.1 PSR-1 and PSR-12: basic and extended style

The minimum and the practical rules, and what each buys beyond consistency.

PSR-1 is a very short document: files declare symbols in one namespace, classes are named in StudlyCaps, constants in UPPER_SNAKE_CASE, methods in camelCase, and a file contains either a side-effect-free symbol declaration or executable code, never both. PSR-12 extends it into a full formatting standard and is what a linter should enforce.

The rules that matter beyond tidiness are the two structural ones. The "one symbol per file" rule combined with PSR-4 (10.2) means the autoloader can find any class from its name alone, with no class map, no configuration, and no risk of a file declaring a class the autoloader does not expect. And the "no side effects in a declaration file" rule is what makes an autoloaded file safe to require from anywhere: including it twice is harmless, and including it never emits output, defines a constant unexpectedly, or starts work.

// 10.1 A PSR-12 compliant declaration file. Note: no closing ?>,
// no side effects, one class, blank line after the namespace block.

<?php

declare(strict_types=1);

namespace Acme\Billing\Domain\Repository;

use Acme\Billing\Domain\Order;
use Acme\Billing\Domain\CustomerId;

interface OrderRepository
{
    public const string DEFAULT_LIMIT = 50;

    public function add(Order $order): void;

    public function get(int $id): ?Order;

    public function recentFor(CustomerId $customerId, int $limit = self::DEFAULT_LIMIT): array;
}

Two PSR-12 details are worth naming because tools disagree about them if they are not configured. The closing ?> must be omitted from a file containing only PHP, since a trailing newline after it is emitted as output. And a multi-line method signature uses one parameter per line, indented by four spaces, with the closing parenthesis on its own line aligned to the declaration.

Adopt declare(strict_types=1); as the first statement in every file, which PSR-12 permits and which makes the type system mean what it says. Add a linter to CI with the PSR-12 ruleset and fail the build on violations; a style standard that is not enforced decays within one sprint, and the cost of the debate is larger than the cost of the rule.

10.2 PSR-4: autoloading and directory layout

The prefix-to-directory mapping, the file-name rule, and the cases PSR-4 does not cover.

PSR-4 defines exactly one thing: a fully-qualified class name maps to a file path by removing a configured namespace prefix and appending .php to each remaining segment. Acme\Billing\Domain\Order under the prefix Acme\ mapped to src/ resolves to src/Billing/Domain/Order.php. Nothing else is configurable and nothing else is needed.

// 10.2 Two prefixes, one for production code and one for tests.

{
    "autoload": {
        "psr-4": {
            "Acme\\Billing\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "Acme\\Billing\\Tests\\": "tests/"
        }
    }
}

// -> Acme\Billing\Domain\Order        resolves to src/Domain/Order.php
// -> Acme\Billing\Tests\Unit\OrderTest resolves to tests/Unit/OrderTest.php
//
// vendor/bin/phpunit  — uses autoload-dev
// composer install --no-dev — production ships without tests/

Four cases fall outside PSR-4 and each needs an explicit decision. Classes whose name does not match the file name — the classic offenders are a class implementing IteratorAggregate for a collection, or a Clock implementation named SystemClock when the interface lives elsewhere — must either be renamed or registered in a classmap section. Functions and constants are not covered by PSR-4 at all and belong in files autoloading. And a PSR-4 violation in a dependency is the single most common cause of a class that exists but cannot be found, so composer dump-autoload --optimise in CI surfaces it immediately.

A PSR-4 prefix must not be a prefix of another registered prefix without care, because resolution stops at the longest match only in some autoloaders. Registering both Acme\ and Acme\Billing\ in the same project is legal and Composer handles it, but registering a vendor prefix that overlaps yours is not. Check composer show --tree when a class from a dependency is unexpectedly not found.

10.3 PSR-7 messages and PSR-15 handlers

Immutable message objects, why immutability is the standard’s central requirement, and the handler contract.

PSR-7 defines MessageInterface, RequestInterface and ResponseInterface, and the standard’s most consequential decision is that message objects are immutable: every with* method returns a new instance rather than modifying the receiver. That is a deliberate choice, and it is what allows a middleware to pass a request down a pipeline without any component being able to alter it for every other component.

// 10.3 PSR-15 handler middleware. No framework required.

<?php

final readonly class TransactionMiddleware implements \Psr\Http\Server\MiddlewareInterface {
    public function __construct(private UnitOfWork $$uow) {}

    public function process(
        \Psr\Http\Message\ServerRequestInterface $$request,
        \Psr\Http\Server\RequestHandlerInterface $$handler,
    ): \Psr\Http\Message\ResponseInterface {
        $$this->$uow->begin();
        try {
            $$response = $$handler->handle($$request);
            $$this->$uow->commit();
            return $$response;
        } catch (\Throwable $e) {
            $$this->$uow->rollback();
            throw $e;
        }
    }
}

PSR-15 separates the two concerns cleanly: a RequestHandlerInterface handles a request and returns a response, and a MiddlewareInterface receives a request and the next handler and returns a response. The transaction middleware above is a complete, framework-independent implementation of a cross-cutting concern that in most applications is implemented by framework configuration instead. PSR-17 then supplies the factories — ServerRequestFactoryInterface, ResponseFactoryInterface, StreamFactoryInterface, UploadedFileFactoryInterface — which is what makes the message objects constructible in a test without a server.

Note the ordering constraint that a framework’s middleware stack usually hides: the transaction middleware must be the outermost layer, because a handler that commits before an outer middleware has finished means a failure in that outer middleware cannot roll anything back. When composing middleware by hand, order is the design decision and it should be written down where it is configured.

10.4 PSR-11 containers and PSR-17 factories

The two-method container contract and the factory interfaces that keep objects constructable outside a container.

PSR-11 defines a container as a class with exactly two public methods: get(string $id): mixed and has(string $id): bool. The standard is deliberately thin, and the two requirements it does state are the ones that matter: has() must return true only for identifiers the container can actually return, and get() for an unknown identifier must throw something implementing NotFoundExceptionInterface. A container that throws a bare RuntimeException is not PSR-11 compliant, and a test asserting compliance is worth writing.

PSR-17 is the more consequential of the two for a persistence codebase, because it solves a problem that is usually solved badly: how do you create a PSR-7 object, or a PSR-3 logger, or a DateTimeImmutable, in a unit test where there is no container and no server. The answer is to inject the factory. A class that needs a response takes a ResponseFactoryInterface; a class that needs a clock takes a PSR-20 ClockInterface; neither requires anything from the framework.

// 10.4 A class that needs nothing but factories.

<?php

final readonly class JsonResponder {
    public function __construct(
        private \Psr\Http\Message\ResponseFactoryInterface $$responses,
        private \Psr\Http\Message\StreamFactoryInterface $$streams,
    ) {}

    public function respond(array $payload, int $status = 200): \Psr\Http\Message\ResponseInterface {
        $$body = $$this->streams->createStream(
            $json_encode($payload, \JSON_THROW_ON_ERROR | \JSON_UNESCAPED_SLASHES),
        );
        return $$this->$responses->createResponse($status)->withHeader('Content-Type', 'application/json')->withBody($$body);
    }
}

Use JSON_THROW_ON_ERROR with json_encode() in every production call site. Without it, encoding failure returns false, which is falsy, which is a value that reaches a json_encode of its own or a database write as a legitimate payload. With it, an unencodable value — a resource, a malformed UTF-8 string, a recursive structure — raises JsonException at the point of the mistake.

10.5 PSR-3 logging and the others that matter

The nine-method logger, structured context, and the standards most applications never need.

PSR-3 defines a logger with nine level methods and a log() method that takes an arbitrary level string. The nine levels are the interface’s substance: adopting them means a consumer can suppress debug in production by configuration rather than by editing code, and the levels are a shared vocabulary that every backend already understands.

// 10.5 Context is the payload; the message is for humans.

<?php

$this->log->warning(
    'order.total.recalculated',
    [
        'order_id'   => $order->id(),
        'was'       => $previousTotal->amountMinor(),
        'now'       => $$this->total(&$order)->amountMinor(),
        'reason'    => 'late_discount',
        'correlation' => $$this->correlationId,
    ],
);

// Never this:
$this->log->error(sprintf('order %d total changed from %d to %d', $id, $a, $b));

// Exception objects are interpolated by compliant loggers.
$this->log->error('db.write.failed', ['exception' => $e, 'table' => 'order_lines']);

The rest of the family is smaller and easier to place. PSR-14 is an event dispatcher with a well-defined listener priority, and it is what replaces a static event bus. PSR-16 is a simple request-handler clock with a single now() method, which is the right way to inject time. PSR-18 is a client-side HTTP client and is worth adopting only if the application makes outbound HTTP calls. PSR-6 is a caching interface that is largely superseded by PSR-16 plus a cache component of your own, and PSR-10 is a process-management interface of niche use.

Log at the boundary of a failure, not at every layer it passes through. A PDOException translated in a repository and then logged in a controller and then logged again in a front controller produces three log lines for one failure, and the first two are noise that trains operators to ignore the log. Log once, at the outermost handler, with the translated exception as the previous — the translator in 6.4 already attaches it via the third constructor argument.

11.1 The DSN and the connection factory

The connection string, the session initialisation that must happen on every connection, and why it belongs in one place.

The MySQL DSN is a semicolon-delimited string passed to the PDO constructor. The characters that matter are charset, which must be utf8mb4 and not utf8 — the latter is a three-byte alias in MySQL and will silently truncate or reject a four-byte character — and init_command, which executes a statement on connection and is the correct place for session settings that must be identical on every connection in the application.

// 11.1 One factory. Every connection in the application is made here.

<?php

final class ConnectionFactory {
    public static function create(array $$config): \PDO {
        $$dsn = sprintf(
            'mysql:host=%s;port=%d;dbname=%s;charset=utf8mb4',
            $$config['host'], $$config['port'], $$config['database'],
        );

        $$pdo = new \PDO($$dsn, $$config['user'], $$config['password'], [
            \PDO::ATTR_ERRMODE            => \PDO::ERRMODE_EXCEPTION,
            \PDO::ATTR_DEFAULT_FETCH_MODE => \PDO::FETCH_ASSOC,
            \PDO::ATTR_EMULATE_PREPARES   => false,
            \PDO::ATTR_STRINGIFY_FETCHES  => false,
            \PDO::ATTR_TIMEOUT            => 5,
        ]);

        // The same session state on every connection, everywhere.
        foreach ([
            'SET SESSION sql_mode = STRICT_ALL_TABLES,NO_ZERO_DATE,NO_ZERO_IN_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION',
            'SET SESSION time_zone = "+00:00"',
            'SET SESSION innodb_lock_wait_timeout = 10',
            'SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED',
        ] as $$sql) {
            $$pdo->exec($$sql);
        }

        return $$pdo;
    }
}

Two of these settings are load-bearing. sql_mode containing STRICT_ALL_TABLES converts a silent truncation into an error, which is the difference between a data-integrity failure and a corrupted value nobody notices. time_zone = '+00:00' makes the server’s clock arithmetic and PHP’s agree, so a TIMESTAMP column written by a migration script and one written by the application are comparable. The isolation level is a per-request decision discussed in 12.2; setting it in the factory makes it explicit rather than a server-wide default nobody remembers.

Never connect as root and never grant a wide set of global privileges to the application account. A dedicated account with SELECT, INSERT, UPDATE, DELETE on the application schema and CREATE, ALTER, INDEX, DROP, REFERENCES on a separate account used only by migrations is the arrangement that turns a SQL injection from a breach into an incident (16.5).

11.2 Attributes that change behaviour

The five attributes worth setting, and the two whose default costs more than they appear to.

ATTR_ERRMODE defaults to ERRMODE_SILENT in PHP 8, which means a failed query returns false and nothing else. Every application should set ERRMODE_EXCEPTION, because a silent failure is checked for by nobody. ATTR_DEFAULT_FETCH_MODE defaults to FETCH_BOTH, which returns each column twice — once indexed numerically and once by name — and doubles the memory of every row. Setting FETCH_ASSOC or FETCH_OBJ removes that entirely.

With ATTR_EMULATE_PREPARES => true, PDO interpolates the parameters into the SQL string in the client and sends a plain COM_QUERY; the server never sees a prepared statement, PDOStatement::debugDumpParams() shows the real values, and integers and booleans arrive as strings. 11.3 Prepared statements and binding

Placeholder syntax, the three binding methods, and the parameter types that matter.

MySQL’s native prepared statements use positional ? placeholders. PDO supports named :name placeholders as a client-side convenience even with emulation off, and a named parameter may be bound more than once if you disable PDO::ATTR_EMULATE_PREPARES — repeated named placeholders in one statement are only permitted when emulation is on, so the portable choice is one distinct name per placeholder.

// 11.3 Bind every parameter. Do not interpolate, ever.

<?php

final class CustomerRepository {
    public function __construct(private readonly \PDO $$pdo) {}

    public function findByEmail(Email $email): ?array {
        $$stmt = $$this->$pdo->prepare('SELECT id, email, name, created_at FROM customers WHERE email = :email LIMIT 1');
        $$stmt->bindValue(':email', $email->value, \PDO::PARAM_STR);
        $$stmt->execute();

        $$row = $$stmt->fetch(\PDO::FETCH_ASSOC);
        return $$row === false ? null : $$row;
    }

    public function search(string $name, int $limit): array {
        $$stmt = $$this->$pdo->prepare(
            'SELECT id, email FROM customers WHERE name LIKE :q ORDER BY id LIMIT :lim'
        );
        $$stmt->bindValue(':q',  $$name . '%', \PDO::PARAM_STR);
        $$stmt->bindValue(':lim', $$limit,          \PDO::PARAM_INT);  // quoted: LIMIT ?
        $$stmt->execute();
        return $$stmt->fetchAll(\PDO::FETCH_ASSOC);
    }
}

Three binding methods exist and the differences are practical. execute(array) binds everything as PARAM_STR, which is wrong for a LIMIT, a boolean or a NULL, and it will be silently wrong rather than an error. bindValue() binds one parameter by reference to a PHP variable and is what the example above uses; the reference means the variable must not be reassigned before execute() runs. bindParam() also binds by reference, is marginally faster for repeated execution, and is the one to use for a statement executed in a loop with different values.

Bind null with PDO::PARAM_NULL explicitly, and bind booleans with PDO::PARAM_BOOL. A WHERE deleted_at = NULL never matches, which is almost always a bug, and the correct SQL for that intent is WHERE deleted_at IS NULL — the two forms are not interchangeable and the first looks plausible enough to survive review.

11.4 Fetch modes and row shape

The four modes, the duplicate-column problem, and the decision between associative rows and objects.

FETCH_ASSOC returns string-keyed arrays, FETCH_NUM numeric-indexed, FETCH_OBJ stdClass objects, and FETCH_BOTH both. FETCH_KEY_PAIR is a special mode that returns a two-column result as a key-to-value map and is the most efficient way to load an id-to-value lookup. The choice for application code is FETCH_ASSOC, because the mapper then receives an array it can pass to a constructor, and because a typo in a column name is a runtime Undefined array key rather than a silent property that does not exist on stdClass.

// 11.4 Duplicate column names must be aliased, or one silently wins.

<?php

// Wrong: both 'id' columns exist; the second overwrites the first
// under FETCH_ASSOC, and under FETCH_NUM you get two entries.
$$bad  = $$pdo->query('SELECT c.id, o.id FROM customers c JOIN orders o ON o.customer_id = c.id');

// Right: distinct, predictable keys that the mapper can rely on.
$$good = $$pdo->query('SELECT c.id AS customer_id, o.id AS order_id, o.total_minor AS total
                     . ' FROM customers c JOIN orders o ON o.customer_id = c.id', \PDO::FETCH_ASSOC);

// FETCH_KEY_PAIR: the cheapest id-to-value map available.
$$totals = $$pdo->query('SELECT customer_id, SUM(total_minor) FROM orders GROUP BY customer_id')
    ?->fetchAll(\PDO::FETCH_KEY_PAIR);

Native typing, enabled by ATTR_EMULATE_PREPARES => false, is what makes the row shape predictable: an INT column yields an int, a BIGINT yields an int on a 64-bit build and a string on a 32-bit one, a DECIMAL yields a string because PHP has no decimal type, and DATE, DATETIME and TIMESTAMP yield strings unless PDO::ATTR_STRINGIFY_FETCHES is off and the native prepared statement is in use. The BIGINT caveat is the one that bites: a BIGINT primary key above 263 is returned as a string, and a mapper that declares the id as int will reject it under strict_types.

Write the mapper to accept the row as it is and convert explicitly — (int) $row['id'], new DateTimeImmutable($row['created_at']) — rather than trusting the driver’s typing. A mapper with explicit conversions behaves identically with emulation on and off, which means the codebase’s test suite does not silently depend on a connection attribute that a hosting provider may override.

11.5 Query, exec and the single-value helpers

Which PDO method to call for which statement, and the four helpers worth writing once.

PDO::query() executes a statement that takes no parameters and returns a statement or false; with ERRMODE_EXCEPTION it throws instead. PDO::exec() executes a statement and returns the affected row count, which makes it right for INSERT, UPDATE and DELETE that take no parameters. PDO::prepare() is for everything else. lastInsertId() returns the generated key for the current connection — and the current connection is the qualifier that matters, since it is meaningless if another statement has run on a different connection in between.

// 11.5 Four helpers that remove most repetition from a repository.

<?php

final class Db {
    public function __construct(private readonly \PDO $$pdo) {}

    /** @param array<string,mixed> $params @return list<array<string,mixed>> */
    public function all(string $sql, array $params = []): array {
        $$stmt = $$this->prepare($sql, $params);
        return $$stmt->fetchAll(\PDO::FETCH_ASSOC);
    }

    /** @return array<string,mixed>|null */
    public function one(string $sql, array $params = []): ?array {
        $$row = $$this->all($sql, $params)[0] ?? null;
        return $$row;
    }

    public function value(string $sql, array $params = []): mixed {
        $$row = $$this->one($sql, $params);
        return $$row === null ? null : reset($$row);
    }

    public function execute(string $sql, array $params = []): int {
        $$stmt = $$this->prepare($sql, $params);
        return $$stmt->rowCount();
    }

    private function prepare(string $sql, array $params): \PDOStatement {
        $$stmt = $$this->$pdo->prepare($sql);
        foreach ($$params as $$key => $$value) {
            $$type = match (true) {
                $$value === null     => \PDO::PARAM_NULL,
                is_bool($$value)    => \PDO::PARAM_BOOL,
                is_int($$value)     => \PDO::PARAM_INT,
                default                => \PDO::PARAM_STR,
            };
            $$stmt->bindValue($$key, $$value, $$type);
        }
        $$stmt->execute();
        return $$stmt;
    }
}

The type-dispatch match in prepare() is the piece that makes the helper worth having: it is the only place in a codebase that has to know that a null bound as a string is not the same as a NULL literal, and centralising it means a repository author cannot get it wrong. Note also that value() uses reset() on the fetched row, which is why the SQL for a value query must select exactly one column; selecting two and calling value() is a bug that returns the first column silently.

rowCount() is not a count of matched rows for every statement. For an UPDATE MySQL returns the number of rows changed by default, not the number matched, so an UPDATE that sets a column to the value it already holds reports zero. Set PDO::MYSQL_ATTR_FOUND_ROWS => true if you need matched-row semantics, and remember that it applies to the whole connection. The reliable alternative is a SELECT ROW_COUNT() immediately after, or a separate SELECT EXISTS(...).

12 · Transactions, Isolation and the Repository Pattern

12.1 Transaction control in PDO12.2 Isolation levels in MySQL 8.412.3 Anomalies and what InnoDB actually does12.4 The repository pattern12.5 Unit of work and identity map

A transaction is the only mechanism by which a relational database offers atomicity, and using it correctly requires knowing what it does not protect you from. This chapter covers PDO’s transaction API and its nested-transaction limitation, the four isolation levels with the anomaly each one permits, the repository as a collection abstraction, and the unit of work that makes a multi-entity write atomic.

12.1 Transaction control in PDO

The three transaction methods, why nesting is not supported, and the wrapper that makes nesting safe.

PDO exposes beginTransaction(), commit() and rollBack(), plus inTransaction() to test. A committed transaction cannot be rolled back, and a transaction cannot be nested: calling beginTransaction() while one is open throws, and a service that assumes it owns the transaction will fail when called from another service that already opened one.

// 12.1 Savepoints emulate nesting where nesting is required.

<?php

final readonly class UnitOfWork {
    public function __construct(private \PDO $$pdo, private int $$depth = 0) {}

    public function begin(): void {
        if ($$this->depth++ === 0) {
            $$this->$pdo->beginTransaction();
        } else {
            $$this->$pdo->exec(sprintf('SAVEPOINT sp_%d', $$this->depth));
        }
    }

    public function commit(): void {
        if (--$$this->depth === 0) {
            $$this->$pdo->commit();
        } else {
            $$this->$pdo->exec(sprintf('RELEASE SAVEPOINT sp_%d', $$this->depth + 1));
        }
    }

    public function rollback(): void {
        $--$this->depth;
        if ($$this->depth === 0) {
            $$this->$pdo->rollBack();
        } else {
            $$this->$pdo->exec(sprintf('ROLLBACK TO SAVEPOINT sp_%d', $$this->depth + 1));
        }
    }
}

The depth counter makes composition safe: an inner service that begins, commits and rolls back affects only its own savepoint, and the outer transaction is unaffected unless it too rolls back. The alternative — a flag that ignores a nested begin() — is simpler but wrong in one important respect: an inner rollback would be indistinguishable from a successful inner commit, so a partially failed operation would appear to succeed. Savepoints make the two distinguishable, and the cost is one SAVEPOINT statement per nesting level.

DDL causes an implicit commit. Any CREATE TABLE, ALTER TABLE, DROP or TRUNCATE inside a transaction commits everything before it and starts a new implicit transaction afterwards. A migration that runs inside the request’s transaction therefore has no rollback, and a migration that fails halfway leaves the schema partially migrated with no record in the migrations table. This is the strongest practical argument for running migrations as a separate process (19.4) rather than from application code.

12.2 Isolation levels in MySQL 8.4

The four levels, the anomalies each permits, and the default this guide recommends.

The SQL standard defines four isolation levels; InnoDB implements all four and defaults to REPEATABLE READ, which is a deliberate choice optimised for the workload MySQL was designed for rather than the strictest reading of the standard. Each level is characterised by the anomalies it permits.

LevelDirty readNon-repeatablePhantomGap locks
READ UNCOMMITTEDYesYesYesNo
READ COMMITTEDNoYesYesNo
REPEATABLE READNoNoMostlyYes
SERIALIZABLENoNoNoAll rows

Two of these deserve a note. READ COMMITTED is what most application developers mean by "a transaction sees a consistent state": it takes a new read view at each statement rather than holding one for the whole transaction, which means it does not accumulate locks over a long-running transaction and it does not produce the gap-lock contention that makes REPEATABLE READ prone to deadlocks on range scans. REPEATABLE READ in InnoDB is not the standard’s REPEATABLE READ in full: it prevents non-repeatable reads within a transaction but still permits phantoms for locking reads and for UPDATE statements, because a current read sees the latest committed version.

// 12.2 Set the level for the session, or per transaction.

$pdo->exec('SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED');

// Or per transaction, which allows different levels per
// operation: an inventory decrement can be stricter than
// a reporting read.
$$pdo->exec('SET TRANSACTION ISOLATION LEVEL SERIALIZABLE');
$$pdo->beginTransaction();
/* ... */
$$pdo->commit();  // level resets for the next transaction

The recommendation for a web application is READ COMMITTED set in the connection factory, with the reasoning stated rather than assumed: it prevents dirty reads, it does not hold a read view open for the lifetime of the request, it avoids the gap locks that REPEATABLE READ takes on range scans and that produce deadlock spikes under load, and it makes the lock-holding window of a transaction roughly equal to the time taken by its statements. Where strict consistency is genuinely required for a specific operation, escalate that one transaction to SERIALIZABLE and keep everything else at the cheaper level.

12.3 Anomalies and what InnoDB actually does

Write skew, lost updates, and the locking reads that detect them.

Two anomalies matter in practice and neither is prevented by REPEATABLE READ. Write skew occurs when two transactions each read a state that satisfies a condition, each inserts a row that violates the condition jointly, and neither sees the other’s uncommitted row — the classic example being two concurrent bookings of the last seat. Lost update occurs when two transactions read the same row, compute different values from it, and write both, with the second overwriting the first.

// 12.3 Lost update: the fix is one statement, not a lock.

<?php

// Wrong: read, compute in PHP, write. Two transactions interleave
// and one increment is lost.
$$row = $$db->one('SELECT stock FROM items WHERE id = ?', [$id]);
$$db->execute('UPDATE items SET stock = ? WHERE id = ?', [$$row['stock'] - 1, $$id]);

// Right: let the database apply the operation atomically.
$$db->execute('UPDATE items SET stock = stock - 1 WHERE id = ? AND stock > 0', [$id]);

// For write skew, a locking read (FOR UPDATE) takes the range
// lock the other transaction needs, forcing serialisation.
$$db->all('SELECT id FROM seats WHERE event_id = ? AND status = ? FOR UPDATE', [$$eventId, 'free']);

The AND stock > 0 predicate is the second half of the fix: it turns the check and the decrement into a single atomic statement and makes the row count meaningful, so a zero return tells the caller the item was unavailable rather than that the write happened. This is a general pattern — push the invariant into the WHERE clause and let the affected-row count be the assertion.

SELECT ... FOR UPDATE is the tool for write skew, and it is also the tool most often misused. It takes an exclusive next-key lock on every row the query scans, including rows that do not satisfy the predicate, so a FOR UPDATE over an unindexed predicate locks the whole table and serialises every writer. Always pair it with an index that covers the predicate, and keep the locked set as small as the query permits.

Deadlock is not an error to be eliminated; it is the database’s way of detecting an unorderable pair of lock requests. InnoDB picks a victim, rolls it back, and reports error 1213 with SQLSTATE 40001. The correct response is a bounded retry with randomised backoff around the whole transaction — not a longer lock timeout, and not a narrower query, both of which usually increase the deadlock rate. Lock timeouts, error 1205, are the same condition reached by a different mechanism and deserve the same retry.

12.4 The repository pattern

A repository as a typed collection, what it must not do, and the query methods it should expose.

A repository is a typed collection of one aggregate plus the queries that aggregate legitimately needs. Its value is that the domain never names a table and never names a query, and that the SQL for an aggregate is in one file. Its cost, when misused, is a repository that has become a second service layer with findByXAndYAndZNotDeletedSortedBySomething methods.

// 12.4 A repository that stays inside its aggregate's boundary.

<?php

final readonly class PdoOrderRepository implements OrderRepository {
    public function __construct(
        private \PDO $$pdo,
        private OrderMapper $$mapper,
    ) {}

    public function get(int $id): ?Order {
        // Two queries, not N+1: lines are loaded for the
        // aggregate root in one statement.
        $$row = $$this->$pdo->prepare('SELECT id, number, status, customer_id, total_minor FROM orders WHERE id = ?');
        $$row->execute([$id]);
        $$head = $$row->fetch(\PDO::FETCH_ASSOC);
        if ($$head === false) { return null; }

        $$lines = $$this->$pdo->prepare('SELECT sku, quantity, unit_price_minor, currency FROM order_lines WHERE order_id = ? ORDER BY position');
        $$lines->execute([$id]);

        return $$this->$mapper->hydrate($$head, $$lines->fetchAll(\PDO::FETCH_ASSOC));
    }

    public function add(Order $order): void {
        $$this->$pdo->prepare('INSERT INTO orders (number, status, customer_id, total_minor) VALUES (?, ?, ?, ?)')
            ->execute([$order->number(), $order->status()->value(), $$order->customerId()->value(), $$order->total()->amountMinor()]);
        $$id = (int)$$this->$pdo->lastInsertId();
        $$order->assignId($$id);

        $$line = $$this->$pdo->prepare('INSERT INTO order_lines (order_id, position, sku, quantity, unit_price_minor, currency) VALUES (?, ?, ?, ?, ?, ?)');
        foreach ($$order->lines() as $position => $l) {
            $$line->execute([$$id, $$position, $$l->sku, $$l->quantity, $$l->unitPrice->amountMinor(), $$l->unitPrice->currency()]);
        }
    }
}

Three rules keep a repository from becoming a service. It performs no branching on business state — no if ($order->isPaid()). It starts no transaction — the unit of work does that, so a use case composing three repositories is atomic. And it exposes queries in domain terms — recentFor(), not findByCreatedAtGreaterThan() — because a method named after a column will be requested with a different column by a caller who has read the schema.

When a use case genuinely needs a query that no repository owns — a report, a search, a cross-aggregate read — do not add it to a repository. Create a read model class in the application layer that depends on PDO directly, and be explicit that it is a query, not a domain operation. Mixing the two produces a repository that knows about reporting joins it has no business knowing.

12.5 Unit of work and identity map

Grouping writes into one commit and guaranteeing one instance per identity.

The unit of work tracks the entities touched during an operation and commits them together. The identity map guarantees that within one unit of work, a given identity yields the same object instance — which is what makes $a->customer() === $b->customer() true, and which makes the mutated state of a shared child visible through every parent that references it.

// 12.5 Identity map + deferred persistence, inside one transaction.

<?php

final class UnitOfWork {
    /** @var array<class-string, array<int|string, object>> */
    private array $$identityMap = [];

    public function get(string $class, int $id): mixed {
        $$key = $$class . '#' . $$id;
        if (!isset($$this->$identityMap[$$key])) {
            throw new RuntimeException(sprintf('%s not loaded in this unit of work', $$key));
        }
        return $$this->$identityMap[$$key];
    }

    public function add(object $entity, int $id): void {
        $$this->$identityMap[get_class($entity) . '#' . $id] = $$entity;
    }

    public function clear(): void { $$this->$identityMap = []; }
}

The identity map has a cost that must be stated: an entity loaded through it cannot see a change another transaction commits, because the cached instance is the one the rest of the unit of work will use. For a read-heavy request that is correct and fast. For a request that must observe the latest committed state of a row it has already loaded — a balance check, a queue worker retrying a job — the map must be bypassable, and the honest design is a separate repository method that goes to the database deliberately. A unit of work that silently serves stale state is worse than no unit of work at all.

Clear the identity map at the end of every request. In FPM the process dies and the map is collected, so a request-scoped container (9.4) is sufficient. In a long-running worker an uncleared map is a memory leak whose growth rate is the entity load rate, and it will hold every entity the worker has ever loaded until the process is restarted.

The schema is the durable expression of the domain model, and the only layer that cannot be bypassed. This chapter writes the DDL for the example schema, argues the column-type choices against storage and semantics, places every invariant that can be placed in a constraint, and builds a migration runner that is safe to run repeatedly, records its own state, and separates the operations that cannot run inside a transaction from those that can.

13.1 The core DDL

The three tables used throughout this guide, with the engine, charset and options stated explicitly.

Every table in an InnoDB schema should state its engine, its character set and its collation. MySQL 8.4's server defaults are reasonable but not guaranteed, and a table created on a server whose default charset is utf8mb3 will silently reject four-byte characters. State the charset on the database and on every table so the schema is portable between environments.

-- 13.1 customers
CREATE TABLE customers (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email       VARCHAR(320) NOT NULL,
    name        VARCHAR(120) NOT NULL,
    status      VARCHAR(16) NOT NULL DEFAULT 'active',
    created_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    UNIQUE KEY uq_customers_email (email),
    CONSTRAINT ck_customers_status CHECK (status IN ('active','suspended','closed')),
    KEY ix_customers_status_created (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

-- 13.1 orders
CREATE TABLE orders (
    id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    number       VARCHAR(32) NOT NULL,
    customer_id  BIGINT UNSIGNED NOT NULL,
    status       VARCHAR(16) NOT NULL,
    total_minor  BIGINT NOT NULL,
    currency     CHAR(3) NOT NULL,
    placed_at    DATETIME(6) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_orders_number (number),
    KEY ix_orders_customer_placed (customer_id, placed_at),
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
        REFERENCES customers (id) ON DELETE RESTRICT ON UPDATE RESTRICT,
    CONSTRAINT ck_orders_total_nonneg CHECK (total_minor >= 0),
    CONSTRAINT ck_orders_status CHECK (status IN ('pending','paid','shipped','cancelled'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

Four decisions in this DDL are deliberate and each has a cost. BIGINT UNSIGNED for the primary key gives 264 values, which is far more than any application will reach, and unsigned halves the index key size compared with a signed BIGINT because the sign bit is not needed. The UNIQUE on email rather than a UNIQUE INDEX with a name chosen by convention is the same thing; the name matters only when you must drop the constraint. ON DELETE RESTRICT is the default and is stated explicitly because it is the aggregate boundary from 3.5 — the database is being told that an order cannot outlive its customer. And ON UPDATE RESTRICT on a surrogate key is a formality that documents intent: nothing should ever change a primary key, and if something tries, it should fail.

Name every constraint explicitly. MySQL 8.0.16 and later enforce CHECK constraints, and an unnamed check appears in SHOW CREATE TABLE as CONSTRAINT table_chk_1 CHECK (...) — a name that tells you nothing when you need to drop exactly that one. A naming convention such as fk_<child>_<parent>, uq_<table>_<columns> and ck_<table>_<rule> costs nothing at creation and pays at the first incident.

13.2 Choosing column types

The type decisions that affect correctness, then the ones that affect only storage.

Two type choices affect correctness rather than efficiency. Storing money as DECIMAL(12,2) with arithmetic in SQL is correct only if every value is a monetary amount; storing it as BIGINT of minor units is correct always, because the integer is the canonical representation and the scale is a property of the currency, not of the amount. The example schema uses BIGINT minor units with a separate CHAR(3) currency, which is why a Money value object in 1.1 stores an int.

Timestamps deserve a decision as well. DATETIME stores a wall-clock time with no zone and is unaffected by session or server time-zone changes; TIMESTAMP stores a UTC instant converted on read and write, is limited to the range 1970 to 2038, and changes the value it returns when the session time zone changes. For a distributed system in which multiple applications write the same table, DATETIME(6) with the convention that every value is UTC is the more predictable choice, and it removes the @@time_zone dependency established in 11.1.

For storage, two facts govern the choice. InnoDB stores variable-length columns off-page when the row exceeds roughly half a page, and a VARCHAR prefix is stored inline, so a wide VARCHAR in a frequently read table increases the number of pages touched. And a utf8mb4 character can occupy up to four bytes, so VARCHAR(320) requires 1280 bytes of storage — which is why 320, the RFC 5321 maximum for an email address, is the correct width and 255 is a habit rather than a standard.

Every index entry in a secondary index stores the primary key columns as well, to locate the row in the clustered index. A secondary index on a VARCHAR(320) therefore carries 1280 bytes of key plus 8 bytes of primary key, and MySQL’s index key length limit of 3072 bytes for DYNAMIC row format means roughly two such columns exhausts the budget. If a text column must be indexed, index a prefix — KEY ix_name (name(64)) — or a hash of it, and state in the schema that the index is prefix-based.

13.3 Constraints as the last line of defence

Placing every invariant that the database can enforce, and the two it cannot.

A constraint is the only enforcement point that cannot be bypassed by a code path, a migration script, a manual fix, or a second application written in another language. That makes it the last line of defence and, in the ordering recommended in 5.5, the authoritative one. The rule to apply is: if the database can express the rule without executing code, it should.

-- 13.3 order_lines: dependent rows, composite key, no surrogate id.
CREATE TABLE order_lines (
    order_id         BIGINT UNSIGNED NOT NULL,
    position         SMALLINT UNSIGNED NOT NULL,
    sku              VARCHAR(64) NOT NULL,
    quantity         INT UNSIGNED NOT NULL,
    unit_price_minor BIGINT NOT NULL,
    currency         CHAR(3) NOT NULL,
    PRIMARY KEY (order_id, position),
    UNIQUE KEY uq_order_lines_sku (order_id, sku),
    CONSTRAINT fk_order_lines_order FOREIGN KEY (order_id)
        REFERENCES orders (id) ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT ck_order_lines_qty CHECK (quantity > 0),
    CONSTRAINT ck_order_lines_price CHECK (unit_price_minor >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

The composite primary key (order_id, position) follows directly from the aggregate argument in 3.5: a line has no identity outside its order, and the position is the ordering the domain already requires. ON DELETE CASCADE here and ON DELETE RESTRICT on the order’s customer encode two different intentions — a line cannot exist without its order, and an order cannot exist without its customer — and the difference between them is the whole content of the aggregate boundary.

Two invariants cannot be expressed as constraints and are worth naming so that nobody attempts it. A constraint cannot reference another table’s column, so "a line’s currency must equal its order’s currency" requires either a trigger or a denormalised check at write time in the application. And a constraint cannot count rows, so "an order must have at least one line" is not expressible; the nearest available approximation is a deferred check, which MySQL does not support. Both belong in the entity, with the database covering the parts it can.

MySQL 8.0.16 onward enforces CHECK constraints, and 8.4 continues to do so. Before 8.0.16 the syntax parsed and the constraint was ignored silently, which means a schema carried forward from an older server may contain check constraints that are not enforcing anything. Verify with SHOW CREATE TABLE and confirm the server version before relying on one.

13.4 A migration runner

Recording applied migrations, executing them in order, and separating transactional from non-transactional operations.

A migration runner needs a table recording what has run, a deterministic ordering, and an honest account of the fact that most MySQL DDL is not transactional. The runner below distinguishes two classes of statement: those that InnoDB can roll back — data changes and most constraint operations — and those that cause an implicit commit — CREATE, ALTER, DROP, TRUNCATE, RENAME.

-- 13.4 The migrations table
CREATE TABLE schema_migrations (
    version     VARCHAR(64) NOT NULL,
    applied_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    duration_ms INT UNSIGNED NOT NULL,
    checksum    CHAR(64) NOT NULL,   -- sha256 of the file
    PRIMARY KEY (version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
<?php

final readonly class Migrator {
    public function __construct(private \PDO $$pdo, private string $$path) {}

    public function migrate(\Psr\Log\LoggerInterface $log): int {
        // A named lock makes concurrent deploys safe: the second
        // runner waits rather than racing on the same DDL.
        $$name = sprintf('%s_migrate', $$this->$pdo->getAttribute(\PDO::ATTR_CONNECTION_STATUS));
        $this->$pdo->exec(sprintf('SELECT GET_LOCK(%s, 30)', $$pdo->quote('acme_migrate')));

        $applied = [];
        foreach ($$this->$pdo->query('SELECT version, checksum FROM schema_migrations')->fetchAll(\PDO::FETCH_KEY_PAIR) as [$$version, $$checksum]) {
            $$applied[$$version] = $$checksum;
        }

        $$count = 0;
        foreach ($$this->pending() as [$$version, $$file]) {
            $$sql      = file_get_contents($$file);
            $$checksum = hash('sha256', $$sql);

            if (isset($$applied[$$version]) && $$applied[$$version] !== $$checksum) {
                throw new RuntimeException(sprintf('migration %s changed after being applied', $$version));
            }
            if (isset($$applied[$$version])) { continue; }

            $$start = hrtime(true);
            $this->executeFile($$sql);
            $$ms = (int)((hrtime(true) - $$start) / 1_000_000);

            $$stmt = $$this->$pdo->prepare('INSERT INTO schema_migrations (version, duration_ms, checksum) VALUES (?, ?, ?)');
            $$stmt->execute([$$version, $$ms, $$checksum]);
            $$log->info('migration.applied', ['version' => $$version, 'ms' => $$ms]);
            ++$$count;
        }

        $$this->$pdo->exec('SELECT RELEASE_LOCK(' . $$pdo->quote('acme_migrate') . ')');
        return $$count;
    }
}

Three details make this safe in production. The GET_LOCK prevents two deploys from migrating the same schema simultaneously, which on a large table means two ALTER operations contending for the same metadata lock and one of them timing out. The checksum comparison turns a silent divergence into a hard failure: an edited migration file is a mistake that is otherwise undetectable until a fresh environment is created and behaves differently from production. And the duration is recorded so that a deploy which is slow because of a migration is visible in the log rather than appearing as a general latency increase.

Do not wrap the whole migration run in a transaction. Because ALTER TABLE commits implicitly, a wrapping transaction gives the false impression of atomicity while providing none: a failure on the third of five statements leaves the first two applied and nothing recorded. Record each migration in its own insert immediately after it succeeds, and treat the file list as the source of truth for ordering.

13.5 Zero-downtime schema change

The expand-contract sequence, the algorithm options, and the operations that still take a lock.

Adding a NOT NULL column with a default, changing a column type, or dropping a column all rewrite or scan the table. The expand-contract sequence avoids the downtime by never requiring both application versions to work against the old schema: expand with the new structure, deploy code that tolerates both, backfill, then contract by removing the old structure. The window during which both structures exist is the whole point.

-- 13.5 Renaming a column without a rename and without downtime.

-- 1. EXPAND: add the new column, nullable, with no default rewrite.
ALTER TABLE orders
    ADD COLUMN total_cents BIGINT NULL AFTER total_minor,
    ALGORITHM=INSTANT;

-- 2. Deploy code that writes both and reads the new one when
--    present. Both application versions now work.

-- 3. BACKFILL in batches, so no single transaction is long.
UPDATE orders SET total_cents = total_minor
 WHERE total_cents IS NULL AND id > ? ORDER BY id LIMIT 5000;

-- 4. CONTRACT, after every row is backfilled and no code reads
--    the old column. Use ALGORITHM=INPLACE, LOCK=NONE.
ALTER TABLE orders
    CHANGE COLUMN total_cents total_minor BIGINT NOT NULL,
    ALGORITHM=INPLACE, LOCK=NONE;

The algorithm and lock clauses are the mechanism that turns a hope into a guarantee. ALGORITHM=INSTANT is available for adding a column at the end of the row, for 8.0.12 onward at any position with AFTER, and for several other operations; it modifies the metadata only and takes no row lock. ALGORITHM=INPLACE rebuilds the table without blocking concurrent DML, and adding LOCK=NONE makes the server fail rather than silently fall back to a blocking copy — which is exactly what you want in a deploy pipeline, because a silent fallback becomes an incident at 3am.

This is why lock_wait_timeout and max_statement_time should be set deliberately on long-running sessions, and why a deploy pipeline that applies migrations should be willing to fail and retry rather than wait indefinitely.

14 · Query Construction, N+1 Elimination and the Mapper

14.1 A small, safe query builder14.2 Joins and eager loading14.3 Eliminating N+114.4 The row mapper14.5 Pagination that does not degrade

Query construction in PHP has one non-negotiable safety property: no user-supplied value may ever reach the SQL text unescaped. This chapter builds a builder that guarantees that by construction, uses it for the two queries that account for most application load, and covers the three techniques that eliminate N+1 — joined eager loading, a second-batch query, and a deliberate identity map.

14.1 A small, safe query builder

Building SELECT statements with bound parameters, and where a builder must refuse to operate.

A builder earns its place only if it makes unsafe SQL impossible rather than merely discouraged. The design below has one rule: every value goes through bindValue, and only identifiers — table names, column names, sort direction — are interpolated, and those are validated against a whitelist before they are used. A builder that offers a whereRaw() method has given that property away.

// 14.1 Values bind; identifiers are whitelisted. There is no raw().

<?php

final class Select {
    /** @var list<string> */
    private array $columns = ['*'];
    /** @var list<string> */
    private array $wheres  = [];
    /** @var array<string,mixed> */
    private array $params  = [];
    /** @var list<string> */
    private array $joins   = [];
    /** @var list<string> */
    private array $orderBy = [];
    private ?int $limit = null;
    private int $$offset = 0;

    private const SORTABLE = ['id', 'placed_at', 'total_minor', 'number'];

    public function columns(string ...$cols): self {
        foreach ($$cols as $$c) {
            if (!preg_match('/^[a-z_][a-z0-9_]*(\.[a-z_][a-z0-9_]*)?$/', $$c)) {
                throw new InvalidArgumentException(sprintf('illegal column %s', $$c));
            }
            $$this->columns[] = $$c;
        }
        return $$this;
    }

    public function where(string $$col, string $$op, mixed $$value): self {
        if (!in_array($$op, ['=', '<>', '<', '>', '<=', '>=', 'LIKE'], true)) {
            throw new InvalidArgumentException(sprintf('illegal operator %s', $$op));
        }
        $$placeholder = ':w' . count($$this->params);
        $$this->wheres[] = sprintf('%s %s %s', $$this->ident($$col), $$op, $$placeholder);
        $$this->params[$$placeholder] = $$value;
        return $$this;
    }

    public function orderBy(string $$col, string $$dir = 'ASC'): self {
        if (!in_array($$col, self::SORTABLE, true)) {
            throw new InvalidArgumentException('column is not sortable');
        }
        $$this->orderBy[] = $$col . ' ' . (strtoupper($$dir) === 'DESC' ? 'DESC' : 'ASC');
        return $$this;
    }
}

The in_array checks are the whole safety argument. An operator and a sort direction are the two places where a caller is most likely to pass something derived from user input, and both are validated against a fixed list. The column-name check is a regular expression rather than a whitelist because column names in a fixed set of tables are developer-chosen; if a query is genuinely dynamic over a schema the caller does not control, the column must be whitelisted instead.

Refuse OFFSET without a ORDER BY. A statement with a limit and no ordering has no defined page, so two pages may overlap or skip rows, and the bug appears as "a record was missing from the list". Enforcing it in the builder costs one comparison and removes a class of support ticket.

14.2 Joins and eager loading

A left join that multiplies rows, and the two-query alternative that does not.

A join between an aggregate root and its children multiplies rows: three orders with five lines each return fifteen rows, not eight. That is correct for a query and wrong for hydration, and it is why a mapper fed a joined result set must group by the root’s identity before constructing children. The grouping is the join’s cost, paid in mapper complexity and in memory.

// 14.2a Joined eager loading: one query, N x M rows to group.

<?php

$sql = 'SELECT o.id AS o_id, o.number AS o_number, o.total_minor AS o_total,
     . '       l.position AS l_pos, l.sku AS l_sku, l.quantity AS l_qty'
     . '  FROM orders o'
     . '  LEFT JOIN order_lines l ON l.order_id = o.id'
     . ' WHERE o.customer_id = :customer'
     . ' ORDER BY o.id, l.position';

// 14.2b Batch eager loading: two queries, 1 + M rows.

$sql = 'SELECT id, position, order_id, sku, quantity FROM order_lines'
     . ' WHERE order_id IN (' . implode(',', array_map(static fn(int $$id) => sprintf('%d', $$id), $$ids)) . ')'
     . ' ORDER BY order_id, position';

The second form is almost always the better one for a page of results. It returns one row per order in the first query and one row per line in the second, so the total row count is M plus N rather than M times N, the mapper’s grouping step disappears for the children, and the two statements can be explained independently in EXPLAIN. Its cost is the second round trip, which is small — well under a millisecond on a local socket — and the need to pass an id list, which is safe here only because the ids come from the database and are cast to int before interpolation. Interpolating an id that originated from user input would be the injection described in 16.3.

An IN list has a practical ceiling. The server parses each element, and a list of several thousand integers produces a statement that must be parsed every time it is prepared. If the set of parents routinely exceeds a few hundred, the correct move is a JOIN against a derived table of the same ids, or a temporary table, or keyset pagination that limits how many parents exist in the first place.

14.3 Eliminating N+1

Detecting the problem, the three fixes, and the only reliable detection method.

N+1 is a loop that performs a query per item: one query to fetch 100 customers, then 100 queries to fetch each customer’s last order. The total is 101 round trips, the latency is the sum rather than the maximum, and on a remote database it is the difference between 5 ms and 400 ms. It survives code review because the code is short and the query is correct.

// 14.3 The defect, then the fix: one IN query instead of N.

<?php

// Defect: 1 + N queries.
$$lastOrders = [];
foreach ($$customers as $$customer) {
    $$lastOrders[$$customer->id] = $$this->orders->latestFor($$customer->id());
}

// Fix: one query, grouped by customer_id in PHP.
$rows = $$this->$db->all(
    'SELECT customer_id, id, number, total_minor FROM orders'
    . ' WHERE customer_id IN (' . implode(',', $$ids) . ')'
    . ' ORDER BY customer_id, placed_at DESC',
);

$latest = [];
foreach ($$rows as $$row) {
    $$latest[$$row['customer_id']] ??= $$row;  // first per group wins
}

The three fixes, in order of preference: batch into one query with an IN list, as above; join and group, as in 14.2; or denormalise the value into a column maintained on write, which is the right answer when the read is in the hot path of a high-traffic page and the write is rare. The fourth option — caching each lookup individually — is the worst of the four, because it produces a cache with an unbounded key space and a hit rate that degrades exactly when traffic is highest.

Detection is the part teams skip. Static analysis will not find it, because a repository method is individually correct. What finds it is a query counter: wrap the connection, increment a counter on every execute(), and assert in a test that rendering a page of 100 rows issues fewer than ten statements. That single assertion converts N+1 from a code-review concern into a test failure, and it is the highest-value assertion in a persistence test suite.

Make the query count part of the integration test, not a production metric. A test that renders a list of 100 fixtures and asserts $counter->value() <= 5 takes no more than a millisecond to run and permanently prevents the regression. A production dashboard that shows queries-per-request does not prevent anything; it reports the problem after the incident.

14.4 The row mapper

Grouping a joined result set into an object graph without constructing anything twice.

The mapper’s hardest job is not conversion but grouping. Given a result set with a parent and a child in the same rows, it must construct one parent object, construct each child exactly once, attach them to the right parent, and emit a list of parents in a deterministic order. Two performance details matter: key the parents by identity in an array so the second row with the same parent id is a lookup rather than a construction, and construct the value objects — the Money, the DateTimeImmutable — once per distinct value rather than per row.

// 14.4 Grouping a joined result set into a graph.

<?php

final class OrderHydrator {
    /** @return list<Order> */
    public function hydrate(array $rows): array {
        /** @var array<int, Order> $orders */
        $$orders = [];

        foreach ($$rows as $$row) {
            $$id = (int)$$row['o_id'];

            $orders[$$id] ??= new Order(
                (int)$$row['o_id'],
                $$row['o_number'],
                OrderStatus::tryFrom($$row['o_status']),
                new Money((int)$$row['o_total'], $$row['o_currency']),
            );

            if ($$row['l_sku'] === null) {
                continue;   // LEFT JOIN with no line
            }

            $$orders[$$id]->attachLine(new OrderLine(
                $$row['l_sku'],
                (int)$$row['l_qty'],
                new Money((int)$$row['l_price'], $$row['l_currency']),
            ));
        }

        return array_values($$orders);
    }
}

Three failure modes are specific to this function and all three are silent. A LEFT JOIN produces a row with NULL in every child column when the parent has no children, so the null check is required and must test the child key, not the parent. A parent that appears with different aggregate values on two rows — which happens when a second join multiplies rows and the aggregate is not grouped — is silently overwritten by the later row, so the aggregate must be in the GROUP BY or selected from a derived table. And an enum hydration using tryFrom() returns null for a value written by a newer application version, so the null must either be rejected or surfaced, never passed into a constructor that expects the enum.

Do not return the array keyed by id from a public repository method. The keys are an implementation detail of the grouping, and a caller that iterates with foreach ($orders as $order) is unaffected while a caller that calls count() or serialises the result is surprised by the shape. array_values() at the boundary costs nothing and produces a list, which is what the list<Order> annotation in 4.3 promises.

14.5 Pagination that does not degrade

Why offset pagination is quadratic in the offset, and the three alternatives.

An OFFSET n clause makes the server locate the first matching row and then discard n rows. The cost is proportional to n, so page 1 is cheap, page 1000 is a thousand times more expensive, and a crawler that walks every page degrades quadratically. There is a second, worse property: OFFSET pagination is not stable under concurrent writes, because a row inserted before the current page’s first row shifts everything down by one and a row is skipped.

// 14.5 Keyset pagination: stable, O(log n) per page, no discarded rows.

<?php

// Page after (placed_at, id) of the last row on the previous page.
$sql = 'SELECT id, placed_at, number, total_minor FROM orders'
     . ' WHERE customer_id = :customer'
     . '   AND (placed_at, id) > (:ts, :id)'   -- row-value comparison
     . ' ORDER BY placed_at, id'
     . ' LIMIT 50';

// MySQL 8.0.16+ optimises a row-value comparison into an index
// range scan. Confirm it with EXPLAIN rather than assuming.

The row-value comparison is the detail that makes keyset pagination usable: comparing placed_at alone is ambiguous when two rows share a timestamp, and the id tiebreaker requires the tuple form. The index that supports it is a composite index on the filter columns followed by the sort columns — here (customer_id, placed_at, id) — which is exactly the index recommended in 18.2. Without that index, keyset pagination is no better than offset, because the server still scans.

What keyset pagination costs is the ability to jump to an arbitrary page number, and a total count. Both are real product requirements sometimes. The resolution is to be explicit about which mode serves which screen: a search results screen that needs "page 47 of 92" uses offset with a cached count, and a feed or an export uses keyset. Trying to serve both from one query is how applications end up with a page number that does not correspond to a stable set of rows.

For a count on a large table, SELECT COUNT(*) scans the index. If the exact number is only needed for a display string, estimate it: EXPLAIN reports rows for the query, and MySQL 8.0 exposes the optimiser’s estimate through EXPLAIN FORMAT=JSON. An estimate that is occasionally off by a few percent is preferable to a scan that adds 400 ms to a page load, and the requirement should be written as "approximately N results", not "exactly N results".

15 · Connection Pooling, Persistent Connections and Deployment

15.1 Connection lifecycle and the connection budget15.2 Persistent connections in PDO15.3 A bounded pool for long-running processes15.4 The server-side limits that bite15.5 Deployment topology

The number of database connections an application opens is a function of its concurrency, and the server’s limit is a hard number. This chapter covers the connection budget and how to compute it, what ATTR_PERSISTENT actually does and when it is the wrong choice, the pool a long-running process needs, the four server variables that end production incidents, and the deployment topologies that keep the arithmetic correct.

15.1 Connection lifecycle and the connection budget

Computing the maximum number of connections before writing any pooling code.

Under PHP-FPM, connections are opened and closed with the request, so the peak number of concurrent connections equals the peak number of concurrent requests. The arithmetic is then simple and must be done before anything is deployed: workers × PHP-FPM processes per worker = peak requests in flight, and each of those holds at most one connection if the design in 9.4 is followed.

-- 15.1 The budget, computed rather than guessed.

--   8 application servers
-- x 12 FPM processes each   (pm.max_children)
-- = 96 concurrent requests
-- + 4 workers x 2 connections = 8
-- = 104 peak connections, plus headroom for admin and CI
--
-- max_connections must therefore be at least ~150, and the
-- pooler, if any, must be configured to accept 150.

SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Max_used_connections';   -- the number that matters

Max_used_connections is the value to monitor, and it is the number that is checked after an incident rather than before one. Note that the default max_connections of 151 is a shared resource: every other client — the migration runner, a monitoring agent, a developer at a console, a backup process — consumes from the same pool, and a burst that opens 96 application connections can starve all of them. This is the single most common cause of "the application cannot connect but the database is not overloaded", and the fix is a max_connections that accounts for everything.

Keep the per-process connection count at one. Two connections per FPM process doubles the peak for no benefit, and the second connection almost always exists because a repository took a PDO as a constructor argument while the service layer also held one. Injecting the connection rather than the factory is what keeps it at one.

15.2 Persistent connections in PDO

What ATTR_PERSISTENT returns to the pool, and the three reasons to avoid it.

With PDO::ATTR_PERSISTENT => true, the connection is not closed when the PHP script ends; it is returned to a per-process pool and reused by the next request on that worker. The saving is the cost of the TCP handshake, the authentication round trip, and the session initialisation from 11.1 — typically 1 to 3 ms on a local socket, more over a network.

-- 15.2 Persistent connections are reused; session state is NOT reset.

<?php

$options = [
    \PDO::ATTR_ERRMODE            => \PDO::ERRMODE_EXCEPTION,
    \PDO::ATTR_EMULATE_PREPARES   => false,
    \PDO::ATTR_PERSISTENT         => true,
];

// A pooled connection inherits everything the previous request set:
//   SET SESSION sql_mode, transaction isolation, user variables,
//   temporary tables, LAST_INSERT_ID(), and any open transaction.
//
// The factory MUST re-apply session state on every checkout,
// or a later request inherits an earlier request's settings.

Three problems make persistence a poor default. The session state problem above is the serious one: a persistent connection is not reset when it is returned, so SET SESSION from request 1 is still in effect in request 400, and if request 1 left a transaction open, request 400 runs inside it and cannot commit. The second is that a persistent connection pins server resources — an open transaction holds locks, a temporary table holds memory — for as long as the process lives, even while no request is running. The third is that it interacts badly with rolling deploys: a connection established to a database that is then restarted or fail-overed is a stale connection that the application keeps using until the query fails.

Persistent connections and unbuffered queries do not combine. An unbuffered PDOStatement holds a server-side cursor, and a persistent connection returned to the pool with a cursor still open leaves that cursor occupying the connection indefinitely. MySQL will not release it until the client consumes or closes it, so a single aborted request can leak a cursor per worker. If a long-running process must stream, give it its own dedicated non-persistent connection.

15.3 A bounded pool for long-running processes

A pool for workers and daemons, with checkout, validation and guaranteed return.

A long-running PHP process — a queue worker, a scheduler, a websocket daemon — opens one connection and holds it for the life of the process, which is simple and correct for a single connection per process. It becomes a problem when the process is multi-threaded through an extension, or when several logical units of work need isolation from each other’s transaction state. In that case a bounded pool with explicit checkout is required, and the essential property is that a connection is always returned even on the exceptional path.

// 15.3 A bounded pool with a finally that always returns.

<?php

final class ConnectionPool {
    /** @var list<\PDO> */
    private array $$idle = [];
    private int $$leased = 0;

    public function __construct(
        private readonly int $$max,
        private readonly string $$dsn,
        private readonly string $$user,
        private readonly string $$pass,
    ) {}

    public function checkout(int $$timeoutSeconds = 5): \PDO {
        $$deadline = microtime(true) + $$timeoutSeconds;

        do {
            $$pdo = array_pop($$this->$idle);
            if ($$pdo instanceof \PDO) {
                if ($$pdo->ping()) { return $$pdo; }  // discard a dead one
                continue;
            }
            if ($$this->leased < $$this->$max) {
                ++$this->$leased;
                return new \PDO($$this->$dsn, $$this->$user, $$this->$pass);
            }
            usleep(10000);
        } while (microtime(true) < $$deadline);

        throw new RuntimeException('connection pool exhausted');
    }

    public function checkin(\PDO $$pdo): void {
        // A connection with an open transaction or a live cursor must
        // not go back into the pool.
        if ($$pdo->inTransaction()) { $$pdo->rollBack(); }
        $$this->$idle[] = $$pdo;
    }
}

Two details make the pool usable. The ping() on checkout exists because a connection idle for longer than wait_timeout is dead, and using one produces "MySQL server has gone away" — so the checkout must validate and discard. And the checkin() that rolls back before returning exists because a connection returned with an open transaction is a correctness bug, not a resource leak: the next user of that connection will either commit the previous user’s work or be blocked by its locks.

Always return the connection in a finally. A lease without a guaranteed return is a leak that only manifests under error, and the manifestation is pool exhaustion in a worker that was healthy when it started. The shape is: $pdo = $pool->checkout(); try { ... } finally { $pool->checkin($pdo); }, in every call site, without exception.

Five variables, what each of them fails with, and the symptom to look for.

Five server variables account for most connection-related incidents, and each has a distinct failure signature. Knowing the signature is worth more than knowing the value, because the value is configuration and the signature is what appears in a log at 3am.

The two that catch experienced teams out. wait_timeout applies to idle non-interactive connections, so a connection left in a pool overnight is terminated by the server while the pool still believes it is valid — which is exactly the case the ping() in 15.3 handles, and an application that is not using a pool must handle it by retrying once on a connection-level error and reconnecting. innodb_lock_wait_timeout defaults to 50 seconds, which is far longer than any web request may wait; lowering it to something matching the request timeout converts a 50-second request that times out at the proxy into a fast, clean failure the application can handle.

Raising max_connections is not a capacity strategy. Each connection has a per-thread memory cost, and past a few hundred the scheduler overhead degrades throughput even though the limit has not been reached. If the arithmetic in 15.1 demands more connections than the server should serve, the answer is a connection pooler in front — ProxySQL, MySQL Router, or PgBouncer’s MySQL-protocol mode is not applicable, so a MySQL-aware pooler or a proxy is — or a reduction in pm.max_children with a queue in front of FPM.

15.5 Deployment topology

Where the database sits relative to the application, and the three failure modes of each choice.

Placement determines the round-trip time that appears in every query, and that number is the multiplier for everything in 18. A Unix socket to a database on the same host removes the network stack entirely and is the fastest option available. A private network between hosts adds roughly 0.1 to 0.5 ms per round trip, which a request issuing 30 queries pays 30 times. A managed database service across the internet adds an order of magnitude more and makes N+1 (14.3) catastrophic rather than merely slow.

-- 15.5 Same host: a Unix socket, no TCP, no DNS.
$dsn = 'mysql:unix_socket=/run/mysqld/mysqld.sock;dbname=acme;charset=utf8mb4';

-- Different host: TCP, with the connection timeout that bounds
-- the failure when the database host is unreachable.
$dsn = 'mysql:host=db.internal;port=3306;dbname=acme;charset=utf8mb4';

-- Verify which path the driver actually took.
--
-- SELECT id, email FROM customers WHERE email = ?
-- SHOW SESSION STATUS LIKE 'Ssl_cipher';
-- SELECT @@socket;   -- the server-side socket path

Three failure modes recur regardless of placement. During a rolling deploy, the old and new application versions are both live, so the schema must satisfy both — which is the expand-contract sequence from 13.5, applied to the application rather than the schema. During a database failover, every existing connection dies at once, and a request that was mid-transaction sees error 2006 or 2013; the application must reconnect and, for a transaction, roll back rather than retry the statement in place, because the transaction is gone. And during a network partition, connections appear alive because the TCP socket is not yet closed, so a write appears to succeed and the data is lost; this is why a read that must be authoritative goes to a replica with an explicit "read your own writes" path, or to the primary.

Reconnect on a connection-level failure, and only there. Distinguishing a connection failure from a statement failure is done by error code: 2006, 2013, 2003 and 08001 are connection-level and justify a reconnect; 1062, 1452 and 3819 are statement-level and must not be retried. Retrying a statement inside a transaction that has already failed server-side will fail again, and retrying a non-idempotent statement can double-write.

16 · Security: Injection, Binding, Mass Assignment and Least Privilege

16.1 SQL injection and why prepared statements are the whole answer16.2 The three PDO binding modes and their sharp edges16.3 Identifiers cannot be parameters: the allowlist pattern16.4 Mass assignment and object hydration16.5 Database users, least privilege and connection identity

The overwhelming majority of PHP and MySQL application vulnerabilities come from one category: untrusted input reaching a place that gives it meaning. This chapter covers the four places that matters — the query string, the column list, the object graph and the privilege grant — and the specific mechanism that closes each one in PHP 8.3 with MySQL 8.4.

16.1 SQL injection and why prepared statements are the whole answer

SQL injection occurs when a value is concatenated into a statement, so the value can change the statement’s meaning. Prepared statements eliminate it structurally, because the SQL text and the values travel separately and the server never parses a value as SQL.

// Vulnerable. The value can terminate the literal and append a second statement.
$sql = "SELECT * FROM customer WHERE email = '" . $_POST['email'] . "'";
$rows = $pdo->query($sql)->fetchAll();

// An attacker sends:
//   email = a@b.com' UNION SELECT password,email,3 FROM admin_user -- 
// The trailing comment discards the rest; the UNION returns the admin table.

// Correct. The value never enters the SQL text at any point.
$st = $pdo->prepare('SELECT * FROM customer WHERE email = :email');
$st->execute(['email' => $_POST['email']]);
$rows = $st->fetchAll();

Prepared statements protect values only. They do nothing for identifiers. A query built as ORDER BY $column cannot be parameterised, because ? ORDER BY ? is a syntax error — a parameter is a value, and a column name is a name. Every dynamic identifier therefore has to be validated against an allowlist, and this is the single most common surviving injection point in otherwise well-written PHP.

// A second-order injection: the value came from the database, not the request,
// so it feels safe. It is not. Assume every string in the database is hostile.
$column = $row['sort_field'];   // stored earlier, from a form
$sql = "SELECT * FROM customer ORDER BY {$column}";   // injectable

16.2 The three PDO binding modes and their sharp edges

PDO can bind a value four ways, and they are not interchangeable. The default silently converts types, which is the source of a family of bugs where a boolean becomes 1 and a zero becomes an empty string.

$st = $pdo->prepare('INSERT INTO customer (name, email) VALUES (:name, :email)');
$st->execute(['name' => 'Ada', 'email' => null]);

// depending on the driver - never SQL NULL. A UNIQUE index then
// collides on the first row that omits an email.

// Explicit and correct:
$st->bindValue(':name', $name, PDO::PARAM_STR);
$st->bindValue(':email', $email, $email === null ? PDO::PARAM_NULL : PDO::PARAM_STR);
$st->execute();

Turn off PDO::ATTR_EMULATE_PREPARES. With emulation on, the driver builds the SQL string itself and quotes values, which reintroduces exactly the escaping problem prepared statements exist to remove. With it off, the statement is compiled once by the server and the values travel as typed protocol parameters — the correct behaviour, and the reason IN (...) placeholders work at all.

16.3 Identifiers cannot be parameters: the allowlist pattern

Wherever a column, table or sort direction comes from outside the code, it must be checked against a list the developer wrote. The allowlist is not a heuristic; it is the complete answer, because a name that is not on the list is a name the application will never use.

// The allowlist. Every value is a literal the developer typed.
final class readonly class CustomerSort {
    private function __construct(
        public string $column,
        public string $direction,
    ) {}

    private const SORTABLE = ['name', 'email', 'created_at', 'lifetime_value'];

    public static function fromRequest(string $field, ?string $dir): self {
        $column = in_array($field, self::SORTABLE, true) ? $field : 'created_at';
        $direction = (strtoupper($dir ?? '') === 'ASC') ? 'ASC' : 'DESC';
        return new self($column, $direction);
    }
}

// Usage. The string is now provably one of five literals.
$sort = CustomerSort::fromRequest($_GET['sort'] ?? '', $_GET['dir'] ?? null);
$sql = sprintf('SELECT id, name, email FROM customer ORDER BY %s %s LIMIT :lim',
               $sort->column, $sort->direction);

Notice that LIMIT is a parameter even though the offset is often dynamic. MySQL and PostgreSQL both accept a bound value for LIMIT because the driver sends it as a typed integer, and this is the correct way to paginate. Only identifiers — names, not values — need the allowlist.

16.4 Mass assignment and object hydration

Mass assignment is the PHP equivalent of the same class of bug: taking an array of client-supplied data and applying every key to an object, including the keys the client should not control. A request that includes role=admin sets the role, and the vulnerability is identical to an injection even though the SQL is perfectly parameterised.

// Vulnerable. Every key in the payload becomes a property.
$customer = new Customer();
foreach ($_POST as $k => $v) { $customer->$k = $v; }
$repo->save($customer);

// An attacker adds: customer_id=9, credit_limit=999999, deleted_at=...

// Correct: an explicit list, and a constructor that decides what it takes.
$customer = Customer::change(
    id: new CustomerId($pathId),
    name: trim((string) $input['name']),
    email: Email::parse((string) $input['email']),
    // credit_limit is not settable from this endpoint at all.
);

credit_limitNeverFinanceSeparate method with an audit row

Constructor promotion with readonly is the structural fix. If a property is declared public readonly and set once in the constructor from a named argument, there is no setter for a request payload to reach, and the mass-assignment vulnerability is not patched — it is unrepresentable. The allowlist above is a mitigation; the immutable property is the design.

16.5 Database users, least privilege and connection identity

The final layer is the database’s own view of what the application may do. An application that connects as a user with only the privileges it needs converts a whole class of bug — including any injection that survives the layers above — from a full compromise into a bounded one.

-- One user per application role. Never one user for everything.
CREATE USER 'acme_web'@'10.0.2.15' IDENTIFIED BY '...from the secret store...';
GRANT SELECT, INSERT, UPDATE, DELETE ON 'acme_shop'.* TO 'acme_web'@'10.0.2.15';
-- No CREATE, no DROP, no ALTER, no FILE, no SUPER, no GRANT OPTION.

-- A separate identity for migrations, used only from CI.
CREATE USER 'acme_migrate'@'10.0.3.%' IDENTIFIED BY '...';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX
      ON 'acme_shop'.* TO 'acme_migrate'@'10.0.3.%';

-- Confirm what the web user can actually do. This is the audit, not the grant.
SHOW GRANTS FOR 'acme_web'@'10.0.2.15';

// Prove the privilege boundary holds, from the application's own credentials.
$db = ConnectionFactory::create(ROLE: ConnectionFactory::WEB);

try {
    $db->exec('DROP TABLE customer');
    throw new RuntimeException('SECURITY: web user can DROP');
} catch (PDOException $e) {
    // Expected. In CI this is a passing test, not a comment.
    if (!str_contains($e->getMessage(), 'denied')
     && !str_contains($e->getMessage(), 'command denied')) {
        throw $e;   // a different failure is a real failure
    }
}

This last test is worth writing once and keeping. It converts "the web user has no DROP privilege" from a claim in a design document into an assertion that fails the build if someone later grants it for convenience. Privilege creep is almost always an accident committed under time pressure, and it is invisible until a test asserts against it.

The layering in 0.4 exists partly so that this chapter is possible: a domain layer that mentions no database is testable without one, and an infrastructure layer that mentions nothing else is testable only with one. This chapter covers the PHPUnit 11 attribute-based configuration, what to double and what to run against a real server, and the fixture and isolation strategy that makes a MySQL-backed suite fast and deterministic.

17.1 Unit tests and the PHPUnit 11 attributes

The configuration style PHP 8.3 codebases should use, and the assertions worth making.

PHPUnit 11 replaced annotations with attributes throughout, and the change is worth making because the attributes are checked by the engine and the annotations were checked by a parser. The common ones are #[Test] on a method whose name does not start with test, #[DataProvider] supplying cases, #[CoversClass] restricting coverage accounting, and #[Group] for selection.

<?php

declare(strict_types=1);

namespace Acme\Billing\Tests\Domain;

use PHPUnit\Framework\Attributes\CoversClass;
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\TestCase;

#[CoversClass(Order::class)]
final class OrderTest extends TestCase {
    #[Test]
    public function rejectsAnOrderWithNoLines(): void {
        $$order = new Order(1, new Money(0, 'EUR'), new DateTimeImmutable());

        $$this->expectException(NoLinesException::class);
        $$order->markPaid();
    }

    #[Test]
    #[DataProvider('currencyMismatches')]
    public function refusesToAddAcrossCurrencies(string $$a, string $$b): void {
        $$this->expectException(CurrencyMismatch::class);
        $$this->orderWith($$a)->addLine($$this->lineWith($$b));
    }

    public static function currencyMismatches(): iterable {
        yield 'eur against usd' => ['EUR', 'USD'];
        yield 'gbp against eur' => ['GBP', 'EUR'];
    }
}

Three practices distinguish a suite that finds bugs from one that documents them. Assert on the exception type and, where the type carries data, on that data — expectExceptionObject() rather than expectException() alone, so a test fails if the wrong condition is raised. Use a data provider for the variations of one behaviour, because a foreach inside a test reports only the first failure and the remaining cases are untested. And prefer asserting on observable behaviour to asserting on internals, which is why #[CoversClass] matters: a test that asserts a private method was called is a test that fails when the implementation changes and passes when the behaviour breaks.

Test the invariant, not the implementation of the invariant. "An order with no lines cannot be marked paid" is one test that survives any refactoring of how the check is performed. "Calling assertHasLines() invokes the private method" is zero tests. When a bug is found, the regression test should fail against the old code and pass against the new, for the reason stated in the requirement rather than the reason stated in the diff.

17.2 Test doubles and what to double

Mock, stub, spy and fake, and the decision about which collaborator gets which.

Four kinds of double are available and they are not interchangeable. A stub returns prepared values and asserts nothing. A mock returns prepared values and asserts that a call happened with specific arguments — the assertion is the point, so a mock is really an expectation. A spy records calls for later assertion. A fake is a working implementation with a simplified behaviour, which is what an in-memory repository is.

// 17.2 Prefer a fake repository over a mocked interface.

<?php

final class InMemoryOrderRepository implements OrderRepository {
    /** @var array<int, Order> */
    private array $$orders = [];

    public function add(Order $$order): void {
        $$id = $$order->id() ?? (count($$this->$orders) + 1);
        $$order->assignId($$id);
        $$this->$orders[$$id] = $$order;
    }

    public function get(int $$id): ?Order { return $$this->$orders[$$id] ?? null; }

    public function recentFor(CustomerId $$id, int $$limit = 50): array {
        return array_slice(array_values($$this->$orders), 0, $$limit);
    }
}

// A mock, for the interaction that is genuinely the behaviour:
$$mailer = $$this->createMock(Mailer::class);
$$mailer->expects($$this->once())->method('send')->with(
    $$this->callback(static fn(Message $$m) => $$m->to()->value() === 'ops@example.com'),
);

The rule is that a fake substitutes for a dependency with behaviour the test does not need to be real about, and a mock substitutes for a dependency where the interaction itself is the requirement. Repositories get fakes, because a test that asserts "the order was saved" is satisfied by a real save and by a fake one, and the fake version runs in microseconds. Mailers, notifiers and clocks get mocks or stubs, because for those the fact of the call is the behaviour.

Never mock the type you are testing, and never mock a value object. A mocked Money that returns 0 from amountMinor() tests nothing except that the mock was configured. Value objects are cheap, deterministic and have no collaborators, so there is no reason to substitute them; their correctness is covered directly by their own tests. Mocks should be reserved for the boundary — I/O, clocks, randomness, message queues — and for nothing else.

17.3 Integration tests against real MySQL

Why a mocked database is not a test, and the minimum viable integration harness.

An integration test against a real server is the only thing that verifies the SQL, the schema and the driver behaviour. A suite that mocks the connection verifies that the code calls the methods the test expected, which is a weaker and largely circular claim. The objection is usually speed, and the answer is that a MySQL-backed test on a Unix socket runs in single-digit milliseconds per test and a thousand tests take seconds.

// 17.3 A base test case that owns one connection and truncates.

<?php

abstract class IntegrationTestCase extends \PHPUnit\Framework\TestCase {
    protected static \PDO $$pdo;

    public static function setUpBeforeClass(): void {
        self::$$pdo = ConnectionFactory::create([
            'host'     => $_ENV['DB_TEST_HOST'],
            'port'     => 3306,
            'database' => $_ENV['DB_TEST_NAME'],
            'user'     => $_ENV['DB_TEST_USER'],
            'password' => $_ENV['DB_TEST_PASSWORD'],
        ]);
        // self::$pdo->exec('SET SESSION sql_mode = STRICT_ALL_TABLES');
    }

    protected function setUp(): void {
        // TRUNCATE resets AUTO_INCREMENT and is faster than DELETE.
        // FK checks are disabled for the duration of the truncate.
        self::$$pdo->exec('SET FOREIGN_KEY_CHECKS = 0');
        foreach (['order_lines', 'orders', 'customers'] as $$table) {
            self::$$pdo->exec(sprintf('TRUNCATE TABLE %s', $$table));
        }
        self::$$pdo->exec('SET FOREIGN_KEY_CHECKS = 1');
    }
}

TRUNCATE rather than DELETE is correct for two reasons: it does not leave the table’s pages fragmented, and it resets the AUTO_INCREMENT counter, so an id asserted in one test is the same id in the next. The foreign-key checks are disabled because the truncation order cannot always satisfy a RESTRICT constraint without knowing the data, and because a test that truncates in reverse dependency order is a test that breaks whenever a foreign key is added.

Run the migrations against the test database as part of the suite’s setup, not as a separate manual step. The test schema and the production schema must be the same schema, and the only way to guarantee that is for CI to create an empty database and run the identical migration set. A test database provisioned once and left to drift is a fixture that will eventually disagree with the code and produce failures that look like application bugs.

17.4 Fixtures, truncation and isolation

Fixture strategies, the shared-database problem, and the test that asserts query count.

Fixtures come in three forms, and the choice is mostly about volume. A hard-coded small set — three customers, two orders — is best for domain tests, because the expected values can be written literally in the assertion. A factory builds on demand and is best when a test needs a specific shape. Bulk loaders exist for performance tests and are the only strategy that should be used when seeding thousands of rows.

// 17.4 A factory that returns the created entity, not a void.

<?php

final class CustomerFactory {
    public function create(string $$email = null, string $$status = 'active'): Customer {
        $$customer = new Customer(
            new Email($$email ?? 'u' . bin2hex(random_bytes(4)) . '@example.com'),
            'Test Customer',
            new \DateTimeImmutable('2026-01-01 00:00:00'),
        );
        (new CustomerRepository(self::$$pdo))->add($$customer);
        return $$customer;   // the id is now populated
    }
}

//
// $counter = new QueryCountingConnection(self::$pdo);
// $html  = $this->renderCustomerList();
// $this->assertLessThanOrEqual(5, $counter->count());

The query-count assertion deserves a place in every suite that renders a list. It is the only test that detects the N+1 described in 14.3, it costs microseconds, and it fails loudly and specifically when a mapper is changed to call a repository in a loop. Wrapping the connection in a counting decorator is a small class: a trait that increments a counter on prepare() and query(), applied to the PDO instance the test owns.

Do not run a parallel test suite against one database. Two processes truncating the same tables produce failures that are not reproducible in isolation and are extremely expensive to diagnose. If the suite must run in parallel, each process needs its own database — acme_test_1 through acme_test_N, created by the CI job and selected by an environment variable — or its own schema, which is simpler and faster to set up than a per-worker pool.

17.5 Wiring the suite into CI

The three jobs, the migration step, and the services a CI runner needs.

A persistence-backed project needs three CI jobs and they should be separate so that a slow integration job does not block the fast feedback of a unit job. The unit job runs the domain and application suites with no database and completes in seconds. The integration job provisions MySQL 8.4, runs the migrations, then runs the infrastructure suite. The static analysis job runs PHPStan at level 8 or 9 with the MySQL extension stubs enabled.

# 17.5 A CI job, in the shape most providers express.

services:
  mysql:
    image: mysql:8.4
    env:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: acme_test
    options: >-
      --health-cmd="mysqladmin ping -h 127.0.0.1 -proot"
      --health-interval=5s --health-timeout=5s --health-retries=20
    ports: ["3306"]

steps:
  - run: php -v && php -m | grep -i pdo
  - run: composer install --no-interaction --prefer-dist
  - run: vendor/bin/phpunit --testsuite=unit
  - run: php bin/console migrate --force     # identical to production
  - run: vendor/bin/phpunit --testsuite=integration
  - run: vendor/bin/phpstan analyse --level=8 --no-progress

Two details distinguish a CI configuration that works from one that is intermittently red. Pin the MySQL image to a minor version — mysql:8.4, not mysql:latest — because a major or minor upgrade changes the optimiser, the defaults and occasionally the authentication plugin, and a test that passes locally fails in CI for reasons unrelated to the code. And run the migration step as its own command in the pipeline, so a migration that fails to apply stops the build before 300 tests run and each of them reports the same missing-table error.

Add a test that runs the migrations against an empty database and then asserts the resulting schema matches a committed snapshot, taken with SHOW CREATE TABLE for every table and normalised. This catches an accidental manual ALTER on a developer’s machine, a migration that is not idempotent, and a migration whose file was edited after being applied — the checksum check in 13.4 catches the third only on servers that run the migrator.

18 · Performance: Profiling, Indexes, Opcache and Measuring Properly

Performance work is measurement or it is guessing, and the two halves of a PHP request fail in different ways — the language half through compilation and function calls, the database half through plans and I/O. This chapter covers profiling each layer with the right tool, index design and how to read an execution plan, opcache configuration for a real deployment, the slow query log as the single most useful diagnostic, and the discipline required to make a number mean something.

18.1 Profiling the right layer

Two profilers, two questions, and the order in which to run them.

A slow request has two candidate explanations and they are diagnosed with different tools. If time is spent in PHP — compilation, autoloading, a function called a million times — a PHP profiler shows it. If time is spent waiting for the database — a round trip, a lock, a scan — the answer is in the server’s own instrumentation, because the PHP profiler will show a long PDO::query() call and nothing more.

The order matters. Measure the request’s total time, then its SQL time, then its PHP time. If SQL dominates, index and query work in 18.2 will move the number; if PHP dominates, opcache (18.3) and algorithmic fixes in the PHP layer are where the win is. A team that profiles the PHP layer first on a request whose time is 90% SQL will find nothing and conclude there is no problem.

// 18.1 Two timers, printed as one line per request.

<?php

$t0 = hrtime(true);
// ... handle the request ...
$$totalUs = (hrtime(true) - $$t0) / 1000;

$log->info('request.completed', [
    'route'         => $$route,
    'total_us'     => round($$totalUs),
    'sql_us'        => $$sqlCounter->us(),
    'sql_count'     => $$sqlCounter->count(),
    'peak_mem_bytes' => memory_get_peak_usage(true),
]);

// A PHP profiler (Xdebug, or Blackfire for sampling) is a
// development tool. Never enable Xdebug in production: it
// changes the timing of everything it measures.

Xdebug’s profiler output is a cachegrind file readable by QCacheGrind or a web viewer, and it answers "which function consumed the time" with call counts and inclusive and exclusive time per function. Blackfire samples instead of instrumenting, which makes its overhead low enough to run against a staging environment that mirrors production. Either is a development tool; neither belongs in a production request path, and the decision to disable Xdebug in production should be enforced by the deployment rather than by a configuration file somebody remembers.

18.2 Index design and reading EXPLAIN

Composite index column order, covering indexes, and the four things an execution plan tells you.

InnoDB stores data in the clustered index, which is the primary key; every secondary index entry stores the indexed columns plus the primary key, and reaching the row requires a second lookup. This has one design consequence that is not obvious: an index that covers the columns a query needs — a covering index — is served entirely from the index with no clustered lookup at all, and on a large table that is the difference between a sequential scan of an index and random reads across the table.

-- 18.2 Equality columns first, then the range, then the sort.

CREATE INDEX ix_orders_customer_placed
    ON orders (customer_id, placed_at, id);

-- Serves: WHERE customer_id = ? ORDER BY placed_at, id
-- Fully covering once the remaining columns are added:
CREATE INDEX ix_orders_cover
    ON orders (customer_id, placed_at, id, number, total_minor, currency);

The ordering rule for a composite index is: equality predicates first, then one range predicate, then the sort columns. A range predicate stops the index from being used for the columns after it, so WHERE a = 1 AND b > 2 ORDER BY c is best served by (a, b, c) — but the ORDER BY c cannot use the index for ordering because b is a range in between. Moving c before b gives up the ability to seek on b. This is a real trade-off, and EXPLAIN is how you settle it rather than reasoning from first principles.

-- 18.2 The four fields that matter in a plan.

EXPLAIN ANALYZE
SELECT id, number, total_minor FROM orders
WHERE customer_id = 417 AND placed_at >= '2026-01-01'
ORDER BY placed_at LIMIT 50;

-- -> Nested loop inner join (cost=1.05 rows=50) (actual time=0.4..0.6 rows=50 loops=1)
--     -> Index range scan on ix_orders_customer_placed
--            using index; rows=50 (actual time=0.3..0.5 rows=50)
--
-- type:  ALL is a full scan, ref is an index lookup by value,
--        range is an index range, index is a full index scan
-- key:   the index chosen — NULL means none was used
-- rows:  the ESTIMATE. Compare it with actual; a large gap means
--        stale statistics and ANALYZE TABLE will help
-- Extra: "Using index" is a covering index — no table access at all

EXPLAIN ANALYZE executes the statement and reports actual timings, which is what makes it valuable and what makes it risky: it runs the query, so on an UPDATE or an INSERT it changes data. Use plain EXPLAIN for anything that is not a SELECT, and EXPLAIN ANALYZE for the select that is actually slow. The most useful diagnostic in the output is the gap between the estimated and the actual row count; a tenfold gap means the optimiser chose a plan based on a cardinality estimate that is wrong, and the fix is either better statistics or an index whose leading columns give the optimiser a usable range.

Every index is paid for on every write: an INSERT must update each secondary index, and an UPDATE to an indexed column must delete the old entry and insert a new one. A table with twelve indexes on a hot path has a write cost that no plan will show, because the cost is in the index maintenance rather than in the query. Audit indexes against the queries that are actually issued — performance_schema.table_io_waits_summary_by_index_usage counts reads per index, and an index with zero reads is a write tax with no benefit.

18.3 Opcache and the request path

The shared memory cache that makes PHP requests affordable, and the settings that matter.

Without opcache, every request compiles every included file from source. With it, compilation happens once per server lifetime and the result is held in shared memory. On a codebase of a few hundred files the difference is large enough to change the shape of a deployment: it is frequently the difference between one application server and two.

; 18.3 php.ini — the settings that are worth changing.
opcache.enable=1
opcache.enable_cli=0
opcache.memory_consumption=256          ; MB; raises the limit on cached scripts
opcache.max_accelerated_files=20000      ; count Composer's autoloader files too
opcache.validate_timestamps=1        ; 1 in dev, 0 in production
opcache.revalidate_freq=2            ; seconds between stat() checks
opcache.save_comments=1             ; required by some docblock readers
opcache.jit_buffer_size=0            ; JIT off by default in 8.3
opcache.interned_strings_buffer=16

; Measure the hit rate before tuning further:
;   opcache.hit_rate below ~95% means scripts are not cached.

The two settings that decide the deployment story are opcache.validate_timestamps and opcache.revalidate_freq. With validation on, opcache stat()s each cached file every revalidate_freq seconds and recompiles it if the modification time changed, which is what makes a development reload work without restarting anything. With validation off, a changed file is not picked up until opcache is reset, and the reset must be part of the deploy — a file write and a opcache_reset() or a process restart. Production should have validation off, because a stat() per file per request is real work multiplied by the number of files.

On the JIT, the honest position for PHP 8.3 is that it is off by default and enabling it rarely helps a request that is dominated by I/O. It helps compute-bound loops that do not call out to the database, which in a web application is a small minority of the work. Measure with a representative request before turning it on, and measure with opcache.jit=disable as the control.

opcache.max_accelerated_files defaults to 10000 and a modern Composer project with a framework generates several thousand files of its own before any application code. When the cache fills, opcache silently stops caching new files, and the symptom is a small number of files that are recompiled on every request while everything else is fast — which is very hard to diagnose from timing alone. Check the count against opcache_get_status(true) in a deployment smoke test.

18.4 The slow query log and pt-query-digest

The one diagnostic that requires no application change, and how to read its output.

The slow query log is configured on the server and requires nothing from the application, which makes it the highest-value diagnostic available. In MySQL 8.4 it is available through a table — performance_schema.events_statements_summary_by_digest — or through the file-based log, and the table form is preferable because it is queryable and survives restarts.

-- 18.4 Top queries by total time. Run it against production.

SELECT
    DIGEST_TEXT                                    AS query,
    COUNT_STAR                                   AS calls,
    ROUND(SUM_TIMER_WAIT/1000000000000, 2) AS total_s,
    ROUND(AVG_TIMER_WAIT/1000000000, 2)   AS avg_ms,
    ROUND(SUM_ROWS_EXAMINED/GREATEST(SUM_ROWS_SENT,1), 0) AS examined_per_sent,
    SUM_ROWS_EXAMINED                             AS rows_examined,
    SUM_CREATED_TMP_DISK_TABLES                  AS tmp_disk
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'acme'
GROUP BY DIGEST
HAVING SUM_TIMER_WAIT > 10000000000
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;

Order by total time, not by average. A query averaging 800 ms that runs once a month is not an incident; a query averaging 0.4 ms that runs 400 000 times an hour is, because it is 44 seconds of database time per hour and it competes with everything else. The examined_per_sent column is the single most diagnostic number in the table: a value of 1 means the query is reading only the rows it returns and the index is doing its job, while a value in the hundreds or thousands means rows are being read and discarded, which is a missing or wrong index and a fixable query.

tmp_disk counts sorts and joins that spilled to disk because they exceeded tmp_table_size or max_heap_table_size. A query that sorts a large result set without an index falls into this column, and the fix is usually an index that supplies the ordering rather than a larger tmp_table_size — which treats the symptom and costs memory on every connection.

Normalise before you optimise. pt-query-digest from Percona Toolkit reads the slow log or the digest table, replaces literals with ?, and groups by fingerprint, which turns a thousand one-off slow queries into a ranked list of five patterns. It is the fastest route from "the database is slow" to the two or three statements responsible, and it runs against a log file on a machine that never touched production.

18.5 Measuring properly

Baseline, one change, one measurement, and the benchmarks that mislead.

A performance measurement is only meaningful with a baseline, a single change and a repeat. The discipline is short: record the number, make exactly one change, record it again with the same method, and keep the change if it improved. Measurements taken with different data volumes, different cache states or a different machine are not comparable, and a benchmark that reports a single run is reporting noise.

// 18.5 A benchmark that measures the wrong thing.

// This says nothing useful: 1000 iterations against a table of
// 12 rows, all in the buffer pool, all on one connection.
for ($$i = 0; $$i < 1000; $$i++) { $$pdo->query('SELECT * FROM customers WHERE id = 1')->fetchAll(); }

// This measures three things: the query, the round trip, and the
// buffer pool. To separate them, measure each on its own:
--   (a) server-side:  EXPLAIN ANALYZE -> actual time of the plan
--   (b) round trip:    a SELECT 1 on the same connection
--   (c) total:        the application timer from 18.1
--
-- (c) - (b) - (a) is the PHP overhead, which is what opcache
-- and a profiler actually address.

Three benchmarks mislead systematically. A micro-benchmark on a table of twelve rows measures the buffer pool, not the query. A benchmark that runs against a freshly restored copy measures the disk, not the steady state that production spends 99% of its time in. And a benchmark that compares against an unindexed schema measures the absence of an index rather than the presence of one — which is why an index benchmark should compare two indexed variants, one of which is the one you believe is right.

The measurement that matters most is the p95 and p99 of a real endpoint under representative load, not the mean. A mean is insensitive to exactly the requests that users complain about; a p99 is dominated by them and is the number that correlates with support tickets. Capture it with a load generator that is not the same machine as the application, and record the database’s own counters — Threads_running, Questions, Innodb_buffer_pool_read_requests — at the same time, so the two sides of the system can be correlated.

Warm the caches before measuring and state that you did. A benchmark run immediately after a deploy has a cold opcache, a cold buffer pool and cold connection state, and it will show a regression that is not one. Conversely, a benchmark run against a table that has been queried ten thousand times in a loop measures a warm buffer pool that production reaches only for its hottest pages. Report the cache state with the number, or the number is not comparable with anything.

19.1 Structured logging and correlation

What a log line must contain to be useful, and what must never appear in one.

A log line that cannot be queried is a line that will not be read. Three properties make structured logs worth the effort: a stable event name that is the same string in every occurrence, a context object whose keys are consistent across occurrences, and a correlation identifier that ties a request’s lines together and links them to a database statement.

// 19.1 Request-scoped context attached to every entry for its duration.

<?php

final readonly class ContextLogger implements \Psr\Log\LoggerInterface {
    public function __construct(
        private \Psr\Log\LoggerInterface $$inner,
        private array $$context = [],
    ) {}

    public function withContext(array $$extra): self {
        return new self($$this->$inner, $$this->$context + $$extra);
    }

    public function error(\Stringable|string $$message, array $$context = []): void {
        $$this->$inner->error($$message, $$this->$context + $$context);
    }

    // The remaining eight levels are identical in shape.
}

// Never log these, at any level:
//   a password, a token, a session id, a full card number,
//   a request body containing any of the above, or a value
//   object rendered with print_r / var_dump.

The exception context is the one that pays. A PDOException interpolated into a log entry includes the full driver message, the SQLSTATE, the driver error code and — because the translator in 6.4 attached it as the previous exception — the original query’s shape, without any of it appearing in the domain type. That is the difference between an actionable log line and "database error".

Redaction has to be systematic rather than remembered. Two approaches work: a list of context keys the logger removes, applied centrally so no call site can bypass it; or a value object per sensitive field whose __toString() returns a masked form and whose jsonSerialize() does the same, so it cannot be logged accidentally. The second is stronger because it survives the field being passed somewhere the logger’s key list does not cover.

Log the decision, not the datum. "Order 417 marked paid, previously pending" is a line that answers a question during an incident. "Order status updated" is not. When in doubt, log the identifiers and the before-and-after values of the fields that changed, because the field an engineer will want is the one nobody predicted they would need.

19.2 Health, readiness and dependency checks

Liveness, readiness and startup as three distinct questions, and what a database check should do.

Three checks answer three different questions and conflating them causes outages. Liveness asks whether the process should be restarted; it must not depend on the database, because a database outage that triggers a restart loop turns a degradation into an outage. Readiness asks whether this instance should receive traffic, and it should check the database because an instance that cannot serve requests should not be sent any. Startup asks whether initialisation has finished, which matters for a process that runs migrations or warms a cache at boot.

// 19.2 Three endpoints with three different questions.

<?php

final readonly class HealthController {
    public function live(): \Psr\Http\Message\ResponseInterface {
        // No dependency checks. If this fails, restart the process.
        return $$this->json(['status' => 'ok'], 200);
    }

    public function ready(): \Psr\Http\Message\ResponseInterface {
        try {
            // Cheap, bounded, and it proves the connection works.
            $$this->$pdo->query('SELECT 1')->fetchColumn();
        } catch (\PDOException $$e) {
            // No connection: stop sending traffic here, but do not
            // restart the process.
            return $$this->json(['status' => 'degraded', 'database' => 'unavailable'], 503);
        }

        return $$this->json(['status' => 'ok'], 200);
    }
}

The readiness check must be bounded, and PDO::ATTR_TIMEOUT is not enough because it covers the connect phase rather than the query. A readiness probe that hangs for 30 seconds while the database is unreachable occupies a probe slot, delays the orchestrator’s decision and produces a timeout that is indistinguishable from a hung process. Wrap the check in a short SET SESSION max_execution_time or issue it against a connection with a one-second connect timeout, so a failing check fails in one second rather than in thirty.

Do not run a full query in the readiness check. A probe running every five seconds from every instance multiplies into a real load against the database, and a check that exercises a complex query is a check that will eventually fail because of a table lock rather than because the service is unhealthy. SELECT 1 proves the connection is alive, which is the only thing a readiness check needs to prove; deeper verification belongs in a separate, human-triggered diagnostic endpoint.

19.3 Deployment and rollback

The expand-contract discipline applied to the application, and a rollback that is actually reversible.

A release is safe when the previous version and the new version can both run correctly against the current schema for the duration of the deploy. That is achieved by the same expand-contract sequence used for the schema in 13.5: deploy code that tolerates both structures, then change the structure, then remove the tolerance. A release that is not reversible in one step is not a release; it is an incident waiting for a cause.

// 19.3 Backward-compatible reads during a rolling deploy.

<?php

final class PdoCustomerRepository implements CustomerRepository {
    public function get(int $$id): ?Customer {
        // The new column may not be populated on every row yet.
        // That is normal during a deploy, not exceptional.
        $$row = $$this->$db->one(
            'SELECT id, email, name, display_name FROM customers WHERE id = :id',
            [':id' => $$id],
        );
        if ($$row === null) { return null; }

        return new Customer(
            new Email($$row['email']),
            $$row['display_name'] ?? $$row['name'],
            new \DateTimeImmutable($row['created_at']),
        );
    }
}

Two properties make a rollback work. The previous artifact must remain available and runnable, which means the deploy is additive — a new release identifier, not a mutated one in place — and the database must still accept what the previous version writes, which is the expand half. A destructive schema change in the same deploy as the code that stops using it removes both properties at once, and that is the release that cannot be rolled back.

Forward-only fixes are usually faster than rollbacks during an incident, and a rollback that reintroduces a bug fixed two hours ago produces a second incident. The discipline is to know both: the rollback command and how long it takes, decided before the deploy rather than during the incident. A deploy that cannot be reversed in under five minutes should not ship on a Friday afternoon.

19.4 Migrations as a pipeline stage

Where migrations run, the locking that makes concurrency safe, and the stage that must precede the deploy.

Migrations run as their own pipeline stage, with their own credentials, and never from application start-up. The reasons are operational rather than technical: a migration that fails must fail the pipeline and stop the deploy, which is impossible when it runs on application boot; a migration needs privileges the application account deliberately does not have (16.5); and a migration on every instance during a rolling deploy runs the same DDL many times concurrently.

# 19.4 The pipeline order. Migrations before deploy, always.

stages:
  - name: test
    script:
      - vendor/bin/phpunit --testsuite=unit
      - vendor/bin/phpunit --testsuite=integration   # against a real 8.4
      - vendor/bin/phpstan analyse --level=8

  - name: migrate-expand
    script:
      - php bin/console migrate --force            # additive only
      - php bin/console wait-for-replication       # if replicas exist

  - name: deploy
    script:
      - ./scripts/rolling-restart.sh               # old and new coexist

  - name: backfill
    when: manual                    # not automatic, not urgent
    script:
      - php bin/console backfill:display-name --batch=5000

  - name: migrate-contract
    when: manual                    # a later release, not this one
    script:
      - php bin/console migrate --force

The separation of the migrate and contract stages is the whole point. The expand migration runs automatically before the deploy and must be additive and fast — an added nullable column, an added index built with LOCK=NONE. The backfill runs separately, is restartable, processes in batches with a bounded transaction per batch, and is triggered by a human once the new code is confirmed to be writing correctly. The contract migration runs in a later release, after the old code is gone, and is the only one that can be destructive.

The batching rule for a backfill is not optional. A single UPDATE over ten million rows holds locks for the duration of the statement, generates a huge undo log, and can exceed innodb_lock_wait_timeout for every other writer. Batching by primary key range, committing each batch, and pacing between batches keeps the transaction short and the impact bounded. The batch also makes the job restartable, because it records the last processed id.

Set an upper bound on how long the expand migration may take and fail the pipeline if it exceeds it. An ALTER TABLE that was expected to be INSTANT and is instead rebuilding a 200-million-row table will hold a metadata lock and block every query in the application, and the pipeline should stop rather than let it run. The ALGORITHM and LOCK clauses from 13.5 turn that silent downgrade into an immediate error, which is the behaviour you want in a pipeline.

19.5 The runbook and the closing checklist

The three queries to run first, and the checklist that ties the guide together.

Three queries answer most database incidents, in this order. SHOW FULL PROCESSLIST shows what is running and what is locked. SELECT * FROM information_schema.INNODB_TRX joined to INNODB_LOCKS shows the transactions holding and requesting locks, with their age — a transaction older than a few seconds holding a lock is the cause of most lock-wait cascades. And SHOW ENGINE INNODB STATUS, specifically the TRANSACTIONS section, shows the current deadlock count and the most recent deadlock’s SQL, which is frequently the answer to a question the log did not record.

-- 19.5 The three queries, in the order to run them.

-- 1. What is running, and what has been running for too long.
SELECT id, user, db, command, time, state, info
  FROM information_schema.processlist
 ORDER BY time DESC LIMIT 20;

-- 2. Long-running transactions: the usual cause of a stall.
SELECT trx.trx_id, trx.trx_state, trx.trx_started,
       TIMESTAMPDIFF(SECOND, trx.trx_started, NOW()) AS age_s,
       trx.trx_mysql_thread_id, trx.trx_query
  FROM information_schema.innodb_trx trx
 ORDER BY trx.trx_started
 LIMIT 20;

-- 3. Deadlock count and the most recent victim's statements.
SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks';
-- SHOW ENGINE INNODB STATUS  -> LATEST DETECTED DEADLOCK

The most useful habit in the set is reading age_s rather than the query text. A transaction open for 300 seconds is the problem regardless of what it is doing, and killing it by thread id is usually the correct first action. The query text matters afterwards, for the fix.

Kill the transaction, not the query. KILL a statement and MySQL rolls back only that statement, leaving the transaction and its locks in place; KILL the connection id and the entire transaction rolls back, releasing every lock it holds. For a stalled system the second is what is wanted, and the first looks like it worked and changes nothing.

Keep this list where it can be pasted at 3am. The value of a runbook is not the explanation it contains but the elimination of decisions: the first query to run, the first thing to look at in the output, the first action to take. A document that requires judgement is not a runbook.
