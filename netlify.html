Orientation — Scope, Model and Conventions

0.1 Scope of this guide0.2 The Netlify platform model0.3 Core concepts and vocabulary0.4 Plan limits and quotas0.5 Pricing mechanics0.6 Conventions, versions and tooling

This guide describes the Netlify platform as an engineering system rather than as a product surface: what the network, the build system and the serverless runtimes actually guarantee, where the boundaries of those guarantees end, and which values you must look up rather than assume. It assumes you can already ship a production application and that what you need is the exact configuration surface, the real limits, the billing mechanics, the failure modes and the escape hatches. Every code block is intended to be pasted into a real repository and executed; every table is either a hard platform limit or a decision matrix. Nothing here is a tutorial. Behaviour is stated as of 2026 and the version baseline is pinned at the top of the file so that a reader can tell immediately whether the advice applies to their stack.

0.1 Scope of this guide

Establishes which platform surfaces are covered, which are deliberately excluded, and the exact framework and runtime versions every example targets.

Netlify is four systems sharing one control plane and one configuration file. The first is a global reverse proxy and content delivery network that terminates TLS, applies redirect and header rules, and serves an immutable deploy from the nearest edge point. The second is a container-based build system that clones your repository, resolves dependencies inside a hermetic build image, runs your build command, and publishes the resulting directory. The third is a serverless compute plane offering a Lambda-compatible runtime, a Deno runtime that executes at the edge, and a background execution mode for long jobs. The fourth is the control plane: the API, the CLI, the Git provider integrations, branch and deploy-preview automation, and the billing meters that measure the other three.

Understanding which system owns a given behaviour is the single most useful heuristic for debugging. If a route returns stale content, that is the CDN and the caching headers in netlify.toml, not the build. If a build behaves differently in CI than it does on a developer machine, that is the build image and the pinned language versions, not the framework. If a request times out at 12 seconds and not 10, that is the function timeout tier, which is a plan property. Each chapter in this guide is organised around one system so that the owner of a failure mode is always unambiguous.

Out of scope: the drag-and-drop deploy UI, form handling, the CMS and its editor, split testing, and the analytics surface, unless a specific runtime or proxy behaviour depends on them. Also out of scope: Netlify Connect (the identity provider) beyond the practical note that JWT validation in functions needs a real JWKS fetch, and Netlify Image CDN beyond its role as a resizing proxy. Topics such as data stores, queues and payment processing are out of scope because Netlify does not provide them; where a design in this guide requires durable state, an external dependency is named explicitly rather than implied.

On plan-dependent numbers. Quotas, timeouts and concurrency ceilings are properties of the plan, not of the product version, and Netlify changes them more often than it changes its changelog. Every such value in this guide is marked as published and points at docs.netlify.com/plans/limits/ and docs.netlify.com/pricing/. When a number matters for a design decision, read it from your own account rather than from a document: netlify api getSite and the usage endpoints in section 0.5 return the values your organisation is actually bound by.

Read the whole orientation before touching configuration. Sections 0.2 and 0.3 introduce terms that the later chapters use without redefinition, in particular deploy versus site, context, and the distinction between the build output directory and the published directory. Skipping them produces configuration that looks correct and behaves in ways that are impossible to reason about from the file alone.

0.2 The Netlify platform model

Explains the atomic-deploy and immutable-asset model that the CDN, the build system and the rollback tooling all depend on.

Netlify does not mutate a site. It publishes deploys, and a site is a pointer to exactly one of them at a time. A deploy is an immutable, content-addressed tree of files plus an immutable set of function bundles. When you push to a production branch, the build system produces a new deploy, and only after the build succeeds does the production domain’s pointer move. If the build fails, the pointer does not move, the previous deploy keeps serving, and nothing about the live site changes. This is why a failed build is a non-event operationally, and why a successful build is the only moment at which a rollback target becomes permanently unreachable by accident.

The atomic property extends to function code. A deploy that routes /api/* to functions carries its own function bundles, so you cannot end up in the state where the new HTML references a route that the old function set does not expose. The same deploy also carries a snapshot of the published directory, so index.html and the hashed JavaScript it references are always from the same build. Both properties are worth stating explicitly because most competing hosts mutate in place, and debugging a partial rollout on those platforms costs far more than Netlify’s occasional stale-cache behaviour costs here.

Serving works by TLS termination at the edge, then a lookup of the domain to a deploy, then rule evaluation, then either a cached asset read, a proxy, or a function invocation. The response carries Netlify-specific headers that tell you which of those happened. Reading them is the fastest way to establish what you are actually looking at, and the command below is worth memorising.

The x-nf-deploy-id header is the highest-value diagnostic in the list. Every response, whether it came from the CDN, a rewrite, or a function, carries the deploy that produced it. When an operator reports that production is serving the previous release, comparing that header against the expected deploy ID settles the question in one request, without a cache purge and without a deploy.

Rollback is a pointer move, not a rebuild. Netlify retains prior deploys, and the UI and API can promote any retained deploy to production. Because a deploy is immutable, the rollback restores the exact bytes that were serving before, including the function bundles, not a rebuild of the same source. The consequence is that a rollback does not reintroduce the bug you were trying to fix if the bug was introduced by a rebuild rather than by a commit; the honest practice is to roll back for containment and then forward-fix.

Environment changes are not retroactive. A function instance that is already warm continues to run with the environment it was initialised with; a build that already completed keeps the environment it used. Changing a secret therefore takes effect on the next cold start or the next deploy, which under low traffic can be a matter of minutes. If a credential rotation is a security requirement rather than a preference, follow it with a deploy, or accept a deliberate cache purge of function instances via the API, and document which mechanism you used.

Use immutable, content-addressed filenames. Because a deploy is a new tree rather than a mutated tree, you can safely set a one-year immutable cache header on anything whose name contains a content hash. If your static assets are named app.js rather than app.9f2c1d.js, you have given up the one optimisation the immutable-deploy model exists to enable, and you are also making every release a full-bust for the whole asset directory. Chapter 2.3 covers the header side of this.

0.3 Core concepts and vocabulary

Defines the terms the rest of the guide relies on: site, deploy, context, branch deploy, deploy preview, build image, publish directory, and the environment variables that encode all of them.

A site is the durable object: a set of domains, a set of Git connections, environment variables, build settings, and deploy history. A deploy is one immutable artefact in that history. The two are not interchangeable in tooling: netlify sites:create and netlify link operate on the site, while netlify deploy and netlify functions:invoke operate on a deploy. A context is the execution environment a build or a function runs in, and there are exactly four: production, branch-deploy, deploy-preview, and dev. The context determines which environment variable set is visible, which [context.*] block in netlify.toml applies, and which quota meter the usage is billed to.

A branch deploy is a deploy of a branch that is not the production branch, on a shared branch subdomain. A deploy preview is a deploy created for a pull request or a commit, on a unique per-deploy URL. Both are branch-deploy-like in that they use the branch-deploy or deploy-preview context, and the distinction matters because the UI and the config treat them separately: a branch deploy is addressed by branch name and is stable, a deploy preview is addressed by deploy ID and is disposable.

The environment variables below are the canonical encoding of these concepts. They are set by the platform in every build and every function, cannot be overridden from the UI, and are the supported way to make a build command behave differently per context without parsing netlify.toml yourself.

Two variables cause disproportionate confusion. BRANCH is the branch name for a production deploy and for previews alike, which means a build command that branches on BRANCH alone will apply production behaviour to every pull request. The correct discriminator is CONTEXT. Separately, CACHED_COMMIT_REF is empty on the first deploy and on any deploy where the previous build failed, so the ignore command in section 1.5 must treat empty as "always build" rather than "never build".

The build image is the container definition the build runs inside: base distribution, architecture, and the preinstalled versions of Node, Python, Ruby, Go, Java and PHP. Sites inherit a default image that the platform chooses. You override it with the NETLIFY_BUILD_IMAGE variable in [build.environment]. The image tag is a triple of distribution, release and architecture, for example amazonlinux-2022-x64 or amazonlinux-2022-arm64. The current list is published in the build image documentation; do not hard-code a tag from memory, because images are added and retired.

Deploy previews are not environments. A deploy preview is a deploy. It shares nothing with the production data stores unless you explicitly point it at them, it expires on the site’s cleanup policy, and its URL changes on every commit. Treat it as a fast, disposable rendering of a commit on the real platform, and treat it as the only place where the build, the edge rules and the functions of a pull request are exercised together. That makes it the correct first integration test and the wrong place to store anything.

Never let a deploy preview reach a production datastore. A preview runs your real build command and your real function code, including migrations, seed scripts and third-party writes. Point previews at a disposable database by branching on CONTEXT in environment configuration, not inside application logic, so that a mis-set variable fails loudly at build time instead of quietly at runtime. Section 1.6 and section 2.6 give the concrete mechanism.

0.4 Plan limits and quotas

Collects the hard ceilings that shape architecture, separates them from soft accounting limits, and states where each authoritative value is published.

There are two different kinds of number, and conflating them is a common source of wasted design effort. A hard limit is a technical ceiling that produces an error: a function that exceeds its memory limit is terminated, a request body over the cap is rejected, a redirect chain deeper than the documented maximum is refused. A soft limit is an accounting boundary: exceeding it produces charges, throttling on the next build, or a plan upgrade prompt, but nothing fails immediately. Only hard limits belong in your architecture; soft limits belong in your budgeting.

The table below lists the hard limits that most often shape a design. The values are those published for 2026. Because Netlify revises them per plan and occasionally mid-cycle, treat the third column as the thing to check before you commit to a design, not as a permanent fact. Where the ceiling is enforced by the underlying provider rather than by Netlify, that is noted, because it changes what happens on failure: a Lambda memory ceiling kills the process without a Netlify-generated error page, whereas a Netlify-enforced payload limit returns a structured rejection.

Where this guide and those pages disagree, those pages are correct. The one thing this guide adds is the failure shape, which the tables do not.

Read the enforcement column as a description of what you will observe. An out-of-memory Lambda is terminated mid-invocation; if the client has already received response headers from a streaming handler, the client sees a truncated body rather than an error, which is a genuinely hard failure to attribute. A function that exceeds its timeout is killed and the client receives a gateway error from the edge. An oversized request body is rejected before your handler runs, so an explicit content-length guard in your code never fires and you must handle the edge’s error shape. An edge function that exceeds its CPU budget is terminated with no chance for a finally block to complete.

Silent out-of-memory is the most under-diagnosed Netlify failure. Because a Lambda that exceeds its memory ceiling is terminated without a Netlify-generated response, the client typically sees a connection reset or a truncated stream, and the deploy log shows only that the invocation started. If you are seeing intermittent 502s on endpoints that are memory-shaped rather than CPU-shaped, raise memory and re-measure before you start optimising code. Chapter 3.4 covers the diagnostic sequence.

Assert your limits in CI. Because the bundle-size and function-count ceilings are enforced at deploy time, not build time, a build can be green and a deploy can still be rejected. Add a post-build check that inspects .netlify/functions and fails the pipeline before the deploy step runs. The size assertion is four lines and it converts an intermittent deploy failure into a deterministic build failure with a useful message.

0.5 Pricing mechanics

Explains the credit-based meter that replaced per-unit quotas, which activities are metered, which are not, and how to observe consumption before it becomes a bill.

Netlify’s commercial plans are organised around a monthly pool of credits rather than around per-unit quotas with hard ceilings. A fixed subscription grants a pool; every metered activity draws down that pool at a published per-unit rate; the pool resets each billing period; consumption above the pool is charged as overage. The consequence for architecture is that most of the things that are expensive are cheap per invocation and expensive in aggregate, so the units you monitor are not the ones you would guess. Bandwidth and build minutes dominate for a content-heavy site; function duration dominates for a compute-heavy API; the combination of many small previews is a build-minute problem, not a function problem.

The metered activities are: build minutes, by plan rate and by build image family; bandwidth, by egress tier; function invocations and function GB-seconds; edge function invocations; and seats, which is a separate subscription dimension from usage. Deploys, previews and custom domains are not individually metered on the plans where they are unlimited; deploy previews consume build minutes, which is the cost people most often fail to attribute correctly, because a pull-request-heavy workflow is a build-minute workload wearing a CI costume.

Rates, pool sizes and the overage policy are published at docs.netlify.com/pricing/ and are specific to each plan and each billing period. The pool is not a bank: credits granted in one period are not carried into the next beyond whatever the current terms state, and a site that is idle for a month still expires its allocation. If you are modelling cost for a seasonal business, model it as a monthly re-purchase, not as an annual budget you can average across.

The observability path matters more than the rates. Netlify exposes usage through the account-level usage API and through the UI’s usage view, and both report consumption by site and by meter. The pattern below is the one to put in a monthly job: query usage, compare against the pool, alert on a projected overrun, and fail loudly rather than quietly accruing overage across many sites.

#!/usr/bin/env bash
# Report metered usage for a month and project the end-of-period total.
set -euo pipefail

ORG_ID="${NETLIFY_TEAM_ID:?}"
MONTH="$(date -u +%Y-%m)"
TOKEN="${NETLIFY_AUTH_TOKEN:?}"

usage() {
  curl -sS -H "Authorization: Bearer ${TOKEN}" \
    -H "Content-Type: application/json" \
    "https://api.netlify.com/api/v1/accounts/${ORG_ID}/api/billing/usage?period=${MONTH}"
}

usage | jq -r '
  [ .usage | to_entries[] | { meter: .key, value: .value } ]
  | ("{:<28}{:>12}{:>10}", "METER", "USED", "UNIT"),
    ( .[] | "{:<28}{:>12}{:>10}", .meter, (.value|tostring), "" )
  | .[]
'

# Project: if the month is half elapsed, double the observed draw.
DAYS_IN_MONTH=30
DAYS_ELAPSED=$(( 10#$(date -u +%d) ))
PROJECTED=$(usage | jq --argjson factor "$(( DAYS_IN_MONTH / DAYS_ELAPSED ))" \
  '[ .usage | to_entries[] | .value * $factor ] | add | floor')

echo "projected period total: ${PROJECTED}"
if [ "${PROJECTED}" -gt "${POOL_WARN:-8000}" ]; then
  echo "WARN: projected draw exceeds ${POOL_WARN} threshold" >&2
  exit 1
fi

Bandwidth is billed on egress, and previews are public. A deploy preview URL is unauthenticated and unlisted, not private. If a preview exposes a large dataset, or if your traffic source is a crawler that fans out across preview hosts, that traffic is egress from your account. If your data is sensitive enough that this matters, the setting to change is whether pull-request builds are created at all, not a firewall rule you can add later.

Model build minutes before you model anything else. For the majority of teams, build minutes dominate the first year of Netlify cost, and the ratio is driven by one variable: how many pull requests create a full deploy. Netlify’s selective build optimisation skips work for pull requests that touch no deployable path. Configuring it is a five-minute change and it is the highest-leverage billing action available to most teams.

0.6 Conventions, versions and tooling

Fixes the conventions used throughout: how the CLI is pinned, how local development achieves parity, and which commands are safe to automate.

The netlify CLI is a development dependency, not a global install. Pin it in devDependencies at an exact version and invoke it through the package manager, so that CI, laptops and build agents all execute the same binary. A floating global CLI is the most common cause of the class of incident where a build works for one developer and fails for everyone else, because the CLI rewrites netlify.toml, changes function bundling defaults and changes local dev-server behaviour between minor versions.

Three commands carry most of the day-to-day weight. netlify dev is the local emulation of the whole platform: it serves publish content, applies redirect and header rules in file order, runs functions, and runs edge functions on the real Deno runtime rather than an approximation. netlify build runs the build exactly as the build system will, including the same base directory semantics and the same bundling, without publishing anything. netlify deploy publishes the output of the preceding build, and takes flags that select the context. Learn the difference between netlify deploy and netlify deploy --build: the first is the correct command in CI where the build has already run and its artefacts are wanted, and the second is the correct command interactively where you want the whole cycle.

Pin the CLI, pin the language version, pin the build image, and commit the lockfile. Those four together are what make a Netlify build reproducible, and every reproducibility problem you will meet in practice traces back to one of them being unpinned. A useful smoke test is to run netlify build on a machine that has never run the project, in a container with no global tooling, and confirm the output directory is byte-identical to CI. If it is not, the difference is almost always an unpinned image or an implicit framework default that a plugin is supplying.

Two commands exist specifically for constrained environments and are worth knowing before you start writing custom build scripts. netlify build --offline reuses the cached build output from a prior build in the same working tree instead of re-running the build, which makes it possible to deploy from an air-gapped or partially available runner. netlify dev --offline does the analogous thing for local development, serving the previously built function bundles instead of rebuilding them, which turns a four-second local loop into an instant one when you are iterating on application code rather than on function code.

1.1 Sites and Git integration

Establishes the durable object: how a site is created, how a local directory is bound to it, and how Git providers drive the pipeline.

A site is created once and then outlives every repository arrangement you might have. The three creation paths are equivalent in outcome and differ only in where the configuration lives. The UI path creates a site and pushes a starter repository, and is appropriate for a first deploy and for handing a site to a team. The API and CLI paths create a site without touching Git, and are the correct choice when the pipeline is driven from your own CI, because the Git integration is then not a dependency of the deployment path and cannot become a single point of failure during an outage of the provider.

Linking a directory to a site is a local, persistent operation: it writes a .netlify/state.json file containing the site ID. That file must be committed for teams that deploy from CI, and must be git-ignored for workflows where a single checkout is deliberately bound to different sites per environment, because binding is per working tree, not per repository. Confirming which site you are bound to before every publish, rather than after, is the cheapest insurance available.

1.2 Build configuration and build images

Defines every key in the [build] table, the build image selection mechanism, framework detection, and the publish directory per framework.

The [build] table is the contract between your repository and the build system. Five keys matter. command is the shell command that produces the output; an empty value means "no build", which is correct for a site of prebuilt files or for a repository whose CI already produced artefacts. publish is the directory whose contents become the deploy, relative to the base directory; it is the only directory that is served. base is the directory the build runs in and that paths in the other keys resolve against. functions is the source directory of Netlify Functions. edge_functions is the source directory of edge functions. ignore is a shell command whose exit status suppresses the build entirely, which section 1.5 covers in detail.

The build image is a container image that fixes the operating system, the architecture and the set of preinstalled language runtimes. If you set nothing, the site uses the platform default, and the platform default is chosen by Netlify and can change. The consequence is that an unpinned build is not a build you can reproduce or debug: a change in the default image alters the Node version, the glibc version, the available native build tooling and the CPU architecture under which your native modules were compiled, with no commit and no changelog entry on your side. Pin it, and treat an image upgrade as a deliberate, tested change.

1.3 Monorepo builds

Covers the two viable monorepo strategies, the base-directory mechanics that make one of them work, and the cache behaviour specific to workspace roots.

There are exactly two correct monorepo arrangements on Netlify, and choosing between them is mostly a question of how much you want to deploy per push. The first is a single site that builds the whole workspace, publishing one app and using redirects or functions to serve the others. The second is one site per deployable app, each with its own base, its own build cache and its own deploy cadence, sharing a repository. The first is simpler; the second scales. A hybrid is common and legitimate: a marketing site plus a functions-only API, where the API site builds from a subdirectory and does not publish any static assets at all.

The mechanics of base are the part that generates confusion. Setting base = "apps/web" makes the build run with that directory as the working directory, and makes publish, functions and command resolve relative to it. Paths are therefore not relative to the repository root, and the common mistake is a publish of apps/web/dist in a file that also sets base to apps/web, which resolves to apps/web/apps/web/dist and produces a build that finds nothing.

# apps/web/netlify.toml   -   the site that serves the storefront
[build]
  base    = "apps/web"
  publish = "dist"                       # relative to base, not to repo root
  command = "npm ci && npm run build"

[build.environment]
  NODE_VERSION        = "24"
  NETLIFY_BUILD_IMAGE = "amazonlinux-2022-arm64"
  NPM_FLAGS           = "--no-audit --no-fund --include-workspace-root"

# apps/api/netlify.toml   -   the site that serves only functions
[build]
  base       = "apps/api"
  functions  = "src/functions"
  publish    = "public"                  # must exist, may be empty of assets
  command    = "npm ci && npm run build:functions"

[functions]
  directory = "src/functions"
  node_bundler = "esbuild"

[build.environment]
  NODE_VERSION        = "24"
  NETLIFY_BUILD_IMAGE = "amazonlinux-2022-arm64"

# Root netlify.toml   -   only if you want a single site for the whole repo
[build]
  base    = "."
  publish = "apps/web/dist"
  command = "npm ci && npm run build --workspace=@acme/web"

[build.environment]
  NODE_VERSION        = "24"
  NETLIFY_BUILD_IMAGE = "amazonlinux-2022-arm64"
  # npm does not install workspace dev deps at the root by default
  NPM_FLAGS           = "--include-workspace-root"

Workspace dependency installation at a non-root base directory is the second mechanical trap. If base is apps/web and that package depends on @acme/shared declared in the root workspace, a plain npm ci in the base directory fails because there is no root lockfile in scope. The remedies are to set the base to the repository root and build with a workspace flag, or to keep the base at the app and use a package manager whose workspace root can be found from a subdirectory, which npm’s --prefix flag approximates but does not fully replicate. Pick the arrangement that keeps the build command a single readable line, because the alternative is a build command full of cd steps that break on the first path containing a space.

Task-graph tooling interacts well with this. If the repository already uses a task runner with its own cache, keep it: Netlify’s build cache and the task runner’s cache are complementary, and layering them correctly is a matter of ensuring the lockfile-derived key is stable and the task runner’s output directory is inside the publish directory. Layering them incorrectly, which usually means the task runner skips work because it sees a warm cache from a different commit, produces stale output that no amount of Netlify cache invalidation will fix.

One site per app means N build caches, and they fill up. A monorepo with a dozen sites consumes a per-site cache allowance that you sized for one site. When the allowance is exceeded, Netlify evicts cache entries, build times climb without any code change, and the cause is invisible in the deploy log because the build still succeeds. Monitor build duration per site over time rather than per deploy; a monotonic rise is the signature of cache eviction pressure.

Keep one canonical lockfile at the repository root. Every site in a monorepo should install from the same lockfile, even at a non-root base. Divergent lockfiles in a monorepo mean the same package resolves to different versions in production than in a local clone of another app, which is the worst class of monorepo bug because it is order-dependent and passes every individual test.

1.4 Ignore rules and dependency installation

Distinguishes the three exclusion mechanisms, explains what each one actually excludes, and pins the dependency-install inputs that determine what gets built.

There are three distinct exclusion mechanisms and confusing them produces builds that are simultaneously too slow and, in one specific case, missing files. .gitignore controls what Git checks out, so anything ignored is absent from the build entirely. .netlifyignore controls what the deploy uploads; ignored files are present during the build and absent from the deploy, which is the correct tool for excluding source files, lockfiles, tests and screenshots from a static upload. The ignore build key controls whether the build runs at all, and is discussed in section 1.5 because its correct implementation is subtle.

The consequence worth internalising is that .netlifyignore does not reduce build time. It reduces deploy upload time and deploy size. If your problem is a slow build, the levers are the build cache, the dependency install and the build command. If your problem is a slow deploy or an inflated function bundle, the lever is .netlifyignore and the function bundler configuration from chapter 3.

1.5 Build caching and reproducibility

Explains what the build cache stores, when it is invalidated, how the ignore key suppresses builds safely, and what "reproducible" requires beyond a warm cache.

The build cache stores two things: the dependency tree, keyed on the lockfile and the package manager, and a compiled output cache for frameworks and task runners that support one. The dependency cache is the one that matters most: a hit turns a two-minute install into a fifteen-second no-op. The cache key is derived from the lockfile hash, the build image, the language version and the base directory, so changing any of those correctly invalidates it. Deploy previews and branch deploys maintain caches separately from production, which is why a preview can be slow while production is fast and why preview build times are the leading indicator of cache pressure.

Reproducibility is a stronger property than a warm cache, and a warm cache actively conceals its absence. A build is reproducible if the same source, the same lockfile, the same language version and the same build image produce byte-identical publish output on any machine at any time. Timestamps in generated files, absolute paths embedded in source maps, locale-dependent sorting, and non-deterministic ordering from concurrent bundlers are the usual causes. The check is cheap and belongs in CI.

# Reproducibility gate: build twice from clean state, compare manifests.
$ build_and_manifest() {
  rm -rf dist .netlify
  CI=1 TZ=UTC LANG=C.UTF-8 LC_ALL=C.UTF-8 SOURCE_DATE_EPOCH=1700000000 \
    npm ci --include-workspace-root && npm run build --workspace=@acme/web
  find dist -type f -print0 | sort -z | xargs -0 sha256sum
}

build_and_manifest > /tmp/a.txt
rm -rf node_modules apps/web/node_modules
build_and_manifest > /tmp/b.txt

if diff -u /tmp/a.txt /tmp/b.txt; then
  echo "REPRODUCIBLE: $(wc -l < /tmp/a.txt) files identical"
else
  echo "NOT REPRODUCIBLE" >&2; exit 1
fi

The ignore build key is a shell command that runs before the build. If it exits zero, the build is skipped and Netlify reports the deploy as ignored; if it exits non-zero, the build proceeds. The canonical implementation diffs the incoming commit against the last successful production commit and skips the build when nothing deployable changed. The subtlety is the empty case: CACHED_COMMIT_REF is empty on a first deploy, on a fresh branch, and after a failed build, and an implementation that treats empty as "nothing changed" silently skips the first deploy of every new branch.

  # Exit 0 to SKIP the build, non-zero to run it. This inverts the intuition of
  # most CI skip-directives, so it must be documented in the repository.
  ignore = """
    if [ -z "$CACHED_COMMIT_REF" ]; then
      echo "no cached ref; building"; exit 1
    fi
    if git diff --quiet "$CACHED_COMMIT_REF" "$COMMIT_REF" -- \
         netlify.toml package.json package-lock.json apps/ public/; then
      echo "no deployable changes since $CACHED_COMMIT_REF"; exit 0
    fi
    echo "deployable changes detected"; exit 1
  """

There is a second, separate cache concept that is routinely confused with the build cache: the CDN cache of published assets. A new deploy invalidates the CDN cache for the paths it replaces, not for the whole site, which is the behaviour you want and which is the reason immutable filenames are safe. The build cache and the CDN cache have different keys, different lifetimes and different invalidation triggers, and a page that is slow to build is unrelated to a page that is slow to serve.

Pinning the build image is a reproducibility requirement, not an optimisation. 1.6 Deploy previews and branch deploys

Compares the two non-production deployment types, their configuration surface, their isolation guarantees, and the cost and retention characteristics of each.

Both non-production deploy types run a real build and produce a real deploy, addressed by different means. A branch deploy is reached at a stable, branch-derived subdomain and is the right choice for a shared environment that a team points at repeatedly. A deploy preview is reached at a unique URL containing the deploy ID and is the right choice for reviewing a pull request, because many previews can coexist for the same branch and each corresponds to exactly one commit.

Neither is an isolated environment by default. They share your repository, your build image, your build cache, and whatever environment variables their context exposes. What they do not share is the production data stores, unless you point them at the same ones. The context is the mechanism for making that separation real, and it must be used in the environment configuration rather than in application code, because environment configuration fails at deploy time and application code fails at request time, usually in production.

Selective build optimisation is the feature that makes previews affordable and is configured per site rather than per repository. When enabled, Netlify determines the set of files a pull request touches, compares it against the paths that affect the deploy, and skips the build entirely for pull requests that touch none of them. Because the cost model from section 0.5 makes previews a build-minute problem, this is the highest-leverage billing configuration available to a pull-request-heavy team.

Anything you need to keep should live in a branch deploy on a branch you maintain, or in an artefact store, or in production. 2.1 netlify.toml structure and precedence

Fixes the file location, the full table structure, and the precedence order between the file, the control panel and framework detection.

netlify.toml is the only place configuration should live for anything you need to be able to diff, review and reproduce. It is looked for at the base directory, not at the repository root, which means a site whose base is apps/web reads apps/web/netlify.toml. A file at the repository root is ignored for that site, with no warning, and the site silently falls back to whatever the control panel or framework detection supplies. This is the first thing to check when a site ignores your configuration.

The file is parsed as TOML and the tables are positional in meaning, not in syntax: every [[array-of-tables]] entry is independent and there is no inheritance between them. The top-level tables you will use are [build], [functions], [context.*], [[plugins]], [[redirects]], [[headers]], [[edge_functions]] and, in newer configurations, [[transforms]]. Order in the file does not matter for TOML semantics, with exactly one exception that will be covered in section 2.2: the order of [[redirects]] entries is significant.

2.2 Redirects: rewrites, proxies and ordering

Explains the evaluation order, the role of force, the status-code semantics, splat placeholders, conditional matching, and the three mistakes that account for most broken routing.

The redirect engine is a first-match-wins evaluator over an ordered list. Rules are evaluated top to bottom in file order, the first rule whose source matches the request wins, and evaluation stops. There is no specificity ordering, no longest-match preference and no reordering by path length. A catch-all placed anywhere other than the last position makes every rule beneath it unreachable, and a specific rule placed beneath a catch-all is silently dead configuration. This single property explains the majority of Netlify routing bugs, and it is why the ordering of [[redirects]] entries is semantically significant even though TOML itself is unordered.

Each rule has a source, a target, a status and an optional force flag. The status selects the mechanism. 200 is a server-side rewrite: the client is not told, the URL in the browser does not change, and the origin path is replaced before the file lookup. 301 and 302 are client-side redirects: the browser is instructed to make a new request, the URL visibly changes, and the query string of the original request is carried unless the rule overrides it. 404 and 410 are terminal responses with no target, used to deliberately retire a path.

# ---------------------------------------------------------------------------
# Ordered, first-match-wins.  The SPA fallback MUST be last.
# ---------------------------------------------------------------------------

# 1. Terminal responses: retired paths, no target.
[[redirects]]
  from   = "/wp-admin"
  status = 410
[[redirects]]
  from   = "/legacy/*"
  status = 404

# 2. Host-level canonicalisation to HTTPS, before anything else is considered.
[[redirects]]
  from     = "http://acme.example/*"
  to       = "https://acme.example/:splat"
  status   = 301
  force    = true
  [redirects.conditions]
    protocol = "http"

# 3. Domain migration, one rule per legacy host.
[[redirects]]
  from   = "https://old.example/*"
  to     = "https://acme.example/:splat"
  status = 301
  force  = true

# 4. API routing to functions. force is REQUIRED: without it a static file at
#    /api/anything in the publish directory would win over the rule.
[[redirects]]
  from   = "/api/*"
  to     = "/.netlify/functions/:splat"
  status = 200
  force  = true

# 5. Specific path rules BEFORE any wildcard that could shadow them.
[[redirects]]
  from   = "/pricing"
  to     = "/plans"
  status = 301
[[redirects]]
  from   = "/docs/latest/*"
  to     = "/docs/v2/:splat"
  status = 301

# 6. Conditional variants: country, query, language, signed access.
[[redirects]]
  from   = "/campaign/*"
  to     = "/eu/:splat"
  status = 302
  [redirects.conditions]
    country = ["GB", "IE", "FR", "DE"]

[[redirects]]
  from   = "/preview/*"
  to     = "/preview/:splat"
  status = 200
  force  = true
  [redirects.conditions]
    signed = true

# 7. SPA fallback. MUST be the final rule in the file. No rule may follow it.
[[redirects]]
  from   = "/*"
  to     = "/index.html"
  status = 200

The second rule that must be stated explicitly is that force = true shadows the published file system. Without force, the engine first checks whether a real file exists at from in the publish directory and serves it if it does, applying the rule only on a miss. With force = true, the rule is applied unconditionally, and a file that exists at from becomes unreachable. This is the mechanism behind "my new build overwrote my hand-written 404.html", and it is also the mechanism that lets a rule route a path that deliberately collides with a file. Decide which of those two behaviours you want, per rule, and write the decision down; the default, no force, is correct for a site whose content is all files, and force = true is correct for anything routing to functions or to an external origin.

The third rule is the consequence of the first: a single-page-application fallback of /* → /index.html rewrites every unmatched path to the application shell, so it must be the final rule or it will shadow every legitimate rule after it. If you have a /* rule at line 5 and a /api/* rule at line 40, the API rule is dead and the failure presents as a routing problem where every API request returns HTML, which then fails in the client as a JSON parse error rather than as a 404. The diagnostic for this is always the same: read the file top to bottom and check where the wildcard sits.

Rules may be declared in TOML, in a _redirects file in the publish directory, or in both. When both exist, the file-based rules are appended to the TOML rules and the combined list is evaluated in that order, which means TOML rules take precedence and file rules are evaluated last. This is the correct arrangement for the SPA fallback, and it is also a trap if you maintain both files: a catch-all in the publish directory is evaluated after every TOML rule, so anything in _redirects that you expected to run first will not.

# _redirects  -  plain-text form. No comments-with-hash are supported in some
# versions; the "!" prefix is the conventional comment marker.
! SPA fallback last, always.
/api/*    /.netlify/functions/:splat   200
/assets/* /build/:splat                200
/*        /index.html                  200

# netlify.toml  -  placeholders and splats
[[redirects]]
  from   = "/files/*"
  to     = "/uploads/:splat"
  status = 200
  force  = true

[[redirects]]
  from   = "/p/:id-:slug"

[[redirects]]
  from   = "/tenants/:tenant/invoices/:invoice"

    /pricing:301|/api/orders:200|/files/report.pdf:200) : ;;

  esac

The SPA fallback shadows everything below it. This is the single most common Netlify routing defect and it is invisible on the home page, so it usually reaches production. Symptom to recognise: API routes return 200 with an HTML body, and the client reports a JSON parse error rather than a 404. The fix is to move the /* rule to the last line of the file, and then add the check in the block above to CI so that it cannot regress silently.

301 responses are cached by browsers indefinitely. A 301 that ships with a mistake is effectively permanent from the client’s perspective, and clearing it requires the user to act. Ship a 302 while validating a rule against real traffic, promote it to 301 once the hit rate looks right, and remember that a 301 also tells crawlers the move is permanent, which is a one-way door for search indexing.

2.3 Headers and caching policy

Covers response header rules, the caching defaults you are actually relying on, the invalidation model, and how to set and verify headers correctly.

Header rules are declared in [[headers]] with a for pattern and a values table. Unlike redirects they are not first-match-wins: all matching rules are applied, and where two rules set the same header the result is implementation-defined, so you must not set the same header from two rules. The for pattern supports splats and named placeholders, and rules can carry a query condition to apply only when specific parameters are present.

The caching point is the one that surprises people. Netlify’s CDN does cache your published content, but it does not invent a Cache-Control policy for you. In the absence of a header you set, the response is served with validators and the browser applies heuristic freshness, which for HTML with a recent Last-Modified means a surprising number of users get a cached document for a while, and for large unversioned assets means a large fraction of your bandwidth is spent re-fetching bytes the CDN already has. The fix is to set an explicit policy, and the correct policy differs by class of file.

# ---------------------------------------------------------------------------
# Headers: security, CORS, and an explicit cache policy per asset class.
# ---------------------------------------------------------------------------

# Content-hashed assets: immutable, one year. Safe because the filename changes
# whenever the bytes change, and because a deploy is immutable.
[[headers]]
  for = "/assets/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"
    X-Content-Type-Options = "nosniff"

[[headers]]
  for = "/_app/immutable/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

# Content-hashed images and fonts.
[[headers]]
  for = "/fonts/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"
    Access-Control-Allow-Origin = "*"

# HTML entrypoints: revalidate every time, never serve a stale shell.
[[headers]]
  for = "/*"
  [headers.values]
    Cache-Control = "public, max-age=0, must-revalidate"
    X-Frame-Options        = "DENY"
    X-Content-Type-Options = "nosniff"
    Referrer-Policy        = "strict-origin-when-cross-origin"
    Strict-Transport-Security = "max-age=63072000; includeSubDomains; preload"
    Permissions-Policy     = "camera=(), microphone=(), geolocation=()"
    Content-Security-Policy = "default-src 'self'; img-src 'self' data: https:; \
script-src 'self' 'nonce-{CSP_NONCE}'; style-src 'self' 'unsafe-inline'; \
frame-ancestors 'none'; base-uri 'self'; form-action 'self'"

# API responses: no caching of dynamic data.
[[headers]]
  for = "/api/*"
  [headers.values]
    Cache-Control = "no-store"
    Access-Control-Allow-Origin = "https://acme.example"
    Access-Control-Allow-Methods = "GET, POST, PATCH, DELETE, OPTIONS"
    Access-Control-Allow-Headers = "Content-Type, Authorization, Idempotency-Key"

# Conditional: only when a query parameter is present.
[[headers]]
  for = "/api/*"
  [headers.values]
    Cache-Control = "private, max-age=60"
  [headers.query]
    embed = "true"

Invalidation is per path and happens on deploy. Publishing a new deploy invalidates the CDN cache for the paths whose content changed, which is exactly the behaviour that makes content-hashed filenames safe and unversioned filenames expensive. For the cases that deploy cannot cover, such as a third-party response you proxy, or an emergency invalidation of a path that has not changed, the purge API accepts a list of paths for a site and removes them from the cache on demand. Purge is rate-limited and should be treated as an operational tool rather than as something to call on every content update.

One caution about security headers. Content-Security-Policy with a nonce requires the nonce to be generated per request and injected, which a static build cannot do, and a policy that hard-codes a hash or allows 'unsafe-inline' is weaker than it appears in the configuration. For a static site the honest options are a hash-based policy generated at build time, or a report-only policy deployed first to learn what the application actually needs, or an edge function that generates a per-request nonce. 2.4 Proxies to external origins

Describes proxying to origins outside Netlify, the semantics of path and query forwarding, host and TLS behaviour, and the cases where a proxy is the wrong tool.

A redirect rule with status = 200 and an external target is a proxy: the request is terminated at the edge, the path is rewritten, and the edge makes the outbound request on your behalf. The browser’s URL does not change, so the proxy is invisible to the client apart from latency. This is the mechanism for putting an origin you do not want to expose directly behind Netlify, for splitting a hostname across a static site and a legacy application, and for adding edge logic in front of a third-party service you cannot configure.

Three semantics must be understood before you rely on it. First, force = true is required for any external target, because a 200 rule without force that happens to collide with a published file will serve the local file instead, and a proxy that silently serves local content half the time is worse than no proxy. Second, the path is mapped by the placeholder, and :splat is the entire remainder including nested segments, so /legacy/* to https://origin.internal/app/:splat maps /legacy/a/b to https://origin.internal/app/a/b. Third, the outbound request’s Host header and the protocol seen by the origin are determined by the target, and the original values are available to the origin through forwarded headers; if your origin performs host-based virtual-host routing or issues absolute URLs from configuration, this is where it breaks.

# Proxy a path prefix to an internal origin, invisible to the client.
[[redirects]]
  from   = "/legacy/*"
  to     = "https://origin.internal.svc.cluster.local/app/:splat"
  status = 200
  force  = true

# Map several public prefixes onto distinct origin paths. Order matters: put
# the more specific prefixes first.
[[redirects]]

[[redirects]]

# incoming query; replacing with ?name= discards it.
[[redirects]]

# API gateway in front of a third party you do not control.

There are limits that come from the nature of the mechanism rather than from configuration. A redirect-based proxy is a request-response proxy, so a long-lived streaming response holds the connection for its full duration, and a WebSocket upgrade does not survive it; WebSockets require a function or an edge function. Header manipulation on the inbound request is limited to what the redirect and header rules can express, and anything that requires a body rewrite, a header signature or a token exchange belongs in code. If the transformation is a simple header addition or a URL substitution, the newer [[transforms]] facility is the lighter-weight mechanism and avoids an invocation from your code entirely.

Because the origin never sees the client, it sees the edge. Anything at the origin that depends on the client address, the original host, or the original protocol is a behaviour change introduced by the proxy, and it must be handled deliberately. Audit the origin for getRemoteAddr, absolute URL generation from the request host, IP allow-lists, and TLS-terminated-in-origin assumptions, before the first deploy rather than after the first incident.

2.5 Edge functions in configuration

Declares edge functions in netlify.toml, resolves the conflict between path and excluded, and positions edge functions relative to redirects and transforms.

An edge function is Deno code that runs at the CDN edge before a request is served from the published content. It is declared either inside the file with an exported config object, or in netlify.toml with an [[edge_functions]] entry. The TOML form is preferable for anything that is reviewed, because the routing table is then visible in the same place as the redirect table and the two can be checked against each other.

The two keys are path, which selects the requests the function sees, and excluded, which removes paths from that selection. The relationship is subtraction: the function runs on path minus excluded. Because a function that calls context.next() hands control onward to the rest of the pipeline, an over-broad path is usually harmless but costs an invocation on every request; an over-broad excluded is always a defect because it means your function silently does not run where you expect.

# netlify.toml - edge function routing
[[edge_functions]]
  # Everything except what is excluded below.
  path     = "/*"
  excluded = [
    "/assets/*",
    "/_app/*",
    "/favicon.ico",
    "/robots.txt",
    "/sitemap.xml",
    "/api/*",              # API traffic is handled by Lambda functions
    "/well-known/*"
  ]

# A second function on a narrower path, declared independently.
[[edge_functions]]
  path     = "/geo/*"
  excluded = ["/geo/legacy/*"]

# netlify/edge-functions/a-b-test.ts
#   export const config = { path: "/pricing" }   overrides the TOML path

# netlify/edge-functions/security-headers.ts
export default async (request: Request, context: any) => {
  const response = await context.next();
  const headers = new Headers(response.headers);
  headers.set("X-Frame-Options", "DENY");
  headers.set("X-Content-Type-Options", "nosniff");
  headers.set("Referrer-Policy", "strict-origin-when-cross-origin");
  // Strip anything the origin set that contradicts our policy.
  headers.delete("X-Powered-By");
  headers.delete("Server");
  return new Response(response.body, {
    status: response.status,
    statusText: response.statusText,
    headers
  });
};

Three placement decisions matter. Edge functions run before redirect evaluation for a matching request, so an edge function that intercepts a path and returns without calling context.next() prevents the redirect rules on that path from ever being evaluated. A request for a legacy path that you intend to 301 therefore needs either an exclusion or a deliberate pass-through. Conversely, if you need a redirect to win over an edge function, express the redirect inside the edge function and exclude the path from the TOML entry, rather than relying on ordering between two independent subsystems.

Order among multiple edge functions is by the specificity of their paths, with the more specific path running first, and this differs from the strict file-order semantics of redirects. That asymmetry is a genuine trap: developers learn the redirect rule, generalise it to edge functions, and get different behaviour. The safe practice is to keep the set of edge function paths non-overlapping so that ordering is irrelevant, and to reserve overlap for cases where you have an explicit reason and a test.

Where the transformation is a simple header addition or a URL substitution, [[transforms]] is the mechanism to prefer over an edge function: it is declarative, it runs in the same place as the other rules, and it does not consume an invocation from your own code. Reserve edge functions for logic that needs a conditional, a token, a body read or a stream.

# Declarative transform: same outcome as an edge function, no code, no invocation

      X-Frame-Options = "DENY"
      X-Content-Type-Options = "nosniff"

  [transforms.redirects]
    from = "/pricing"
    to   = "/plans"

An edge function that never calls context.next() makes the request a hard stop. Run edge functions locally with the real Deno runtime. netlify dev executes your edge functions on the same Deno runtime the edge uses, not on a Node approximation, which means Deno-specific APIs work locally and Node-specific ones fail locally. 2.6 Environment variables and build environment

Defines the scopes available for environment variables, the precedence between the file, the CLI and the panel, and how secrets should reach builds and functions.

Environment variables exist in the site configuration, not in the repository, and each carries a scope that determines where it is visible: build is available to the build command only, functions to Netlify Functions and background functions, runtime to functions of all kinds including edge functions, ui to the deploy UI so a comment can reference a deploy ID, and build,functions to both. The scope is a real access-control boundary and choosing the narrowest one that works is the cheapest security improvement available to a Netlify site.

There are three ways to set a variable and their precedence is worth stating: the CLI and the API write to the site configuration, and the panel displays and edits the same configuration. All three therefore write to the same place, and there is no meaningful precedence between them, only an audit trail of who changed what and when. The one genuine precedence relationship is between [build.environment] in netlify.toml and the site environment: values in the file win for the build, and the file value is visible in the build log’s environment listing, so a variable that appears in both places will resolve to the file value. That is a useful escape hatch for pinning non-secret values and a hazard for secrets, because a secret in netlify.toml is in version control.

This chapter covers the three ways to run code on Netlify, honestly and in the terms an engineer has to make decisions in. Netlify Functions are Lambda-compatible, bundle your dependencies, run on Node 24 or on the Deno 2.x runtime, and are bounded by a synchronous timeout of 10 seconds on the entry-level plans and 26 seconds on paid tiers. Background Functions are for work that takes minutes rather than seconds: they are capped at 15 minutes, they are not guaranteed to start immediately, and any design that depends on a background function running promptly is a design that needs a durable queue. Each of the three has a real cost and a real failure mode, and choosing the wrong one is the most common architectural error on the platform.

3.1 Netlify Functions and runtimes

Covers the function source directory, the two runtimes and their differences, the bundling rules, and the manifest that tells you what was actually shipped.

A Netlify Function is one exported handler that receives a request and returns a response. The source directory defaults to netlify/functions and is set with [build] functions. Every file in that directory that exports a handler becomes a function whose name is derived from the filename, with the extension and the language suffix removed, so process-order.ts becomes process-order. The build bundles each function into a single self-contained artefact under .netlify/functions, and the deploy uploads that directory rather than your source.

There are two runtimes. The Lambda runtime is Node 24, provided by the underlying provider, and is the runtime for the common case: full Node API access, npm dependency resolution, native modules, and the standard synchronous timeout tiers. The Deno runtime runs functions on Deno 2.x with npm compatibility, which gives you a modern standard library and Deno’s permissions model while still resolving npm packages. The choice is per function and is made by the file extension and, in some cases, by explicit configuration, so a repository can legitimately contain both. What the Deno runtime does not give you is the Node API surface that many libraries assume; the honest framing is that it is a different runtime with a compatibility layer, not a faster Node.

// netlify/functions/process-order.ts
//   Lambda runtime, TypeScript, Web-standard handler signature.
import type { Context } from "@netlify/functions";
import { z } from "zod";

Bundling is the part of the function story that has the most operational consequence and the least documentation in application codebases. The default bundler is esbuild, and it follows relative imports into your source, resolving node_modules dependencies and inlining them into a single file per function. Two consequences follow. First, a function that imports your application graph can pull the entire graph into the bundle, so the function directory should be a thin adapter layer over your domain code and not a place where application code is written. Second, because dependencies are inlined, a function has no node_modules directory at runtime, so anything that resolves paths relative to the module tree at runtime will behave differently than it did locally. The external_node_modules key excludes specific packages from inlining, and included_files copies non-JavaScript assets into the bundle; both are escape hatches and both reduce the reliability of the local-to-production equivalence, so use them with a recorded reason.

3.2 Edge Functions on the Deno runtime

Describes the edge execution model, the Deno standard library you can rely on, the handler contract, and the workloads that genuinely benefit.

An Edge Function runs in a Deno 2.x isolate at the CDN edge point that received the request. Startup is sub-millisecond, which is the whole point: the function is already running in the same machine as the request, so the request pays dispatch rather than a cold start. That property is why edge functions can be used for request-time logic on every request to a site, which a Lambda cannot be because its cold start is measured in hundreds of milliseconds to seconds and its regional placement means a request from another continent pays a network round trip before your code runs.

The constraints follow directly from the runtime. There is no Node API: no fs, no net, no child_process, no npm package that assumes one. The Deno standard library is available, so Deno.serve-era web APIs, fetch, crypto, TextEncoder, streams and the Web platform types are all there, and Deno’s own APIs such as Deno.env and Deno.readTextFile exist in the type surface but file access is not what you want to depend on in a function that runs on every request. The practical consequence is that edge functions can do network calls, cryptographic work, parsing and transformation, and cannot do anything that requires a filesystem or a long-lived process.

Execution is bounded by a CPU budget rather than a wall-clock timeout, on the order of tens of milliseconds. The distinction matters: a function that awaits a slow fetch is not consuming CPU budget while it waits, so a network call is affordable, whereas a synchronous cryptographic loop or a large JSON parse is entirely CPU and will exhaust the budget immediately. A function that exceeds the budget is terminated with no opportunity for a finally block to complete cleanly, so you must budget for it rather than discover it.

// netlify/edge-functions/geo-route.ts
//   Runs on Deno 2.x at the edge. Node APIs are not available; the Web platform
//   APIs and the Deno standard library are.
export default async (request: Request, context: any) => {
  const url = new URL(request.url);

  // A-B split, keyed on a signed cookie, with a stable allocation.

// Persistent binding: a Deno KV or platform binding, not a module-level cache.
async function edgeSplit(key: string, req: Request, ctx: any): Promise<"a" | "b"> {
  const cookie = req.headers.get("cookie")?.match(new RegExp(`${key}=([ab])`))?.[1];
  if (cookie === "a" || cookie === "b") return cookie;
  const assign = (crypto.getRandomValues(new Uint8Array(1))[0] & 1) === 0 ? "a" : "b";
  const res = await ctx.next();
  const h = new Headers(res.headers);
  h.append("Set-Cookie", `${key}=${assign}; Path=/; Max-Age=31536000; SameSite=Lax`);
  return assign;
}

The handler contract is deliberately small. context.next() continues the pipeline and returns the response that the rest of the platform would have produced, whether that is a published file, the result of a redirect rule, or a Lambda function. context.next(url) continues with a modified URL, which is the idiomatic way to do a rewrite from the edge. context.geo, context.ip, context.requestId and context.log give you request metadata and logging. If you do not call context.next(), the pipeline stops and your return value is the response, which is how you short-circuit a request entirely.

State is the constraint that decides whether a workload belongs here. There is no in-process state that survives between requests, because the isolate is disposable, so an edge function that needs a session, a rate-limit counter or a cached lookup needs somewhere to put it. Platform bindings, an HTTP call to a key-value store, or a signed stateless token in a cookie are the options, and the last of those is the most elegant: encode the state in a signed value the client returns, verify it at the edge in microseconds, and pay no storage at all. When you find yourself reaching for a network call on every request to hold a counter, that is the signal that the logic belongs in a Lambda with a real datastore, or in a set of conditional rules that need no code.

3.3 Background Functions

Section 3.3 has no topic description element; the following paragraphs establish what background execution is, when it is appropriate, and what it does not guarantee.

A Background Function is a Netlify Function with a wall-clock limit of 15 minutes instead of the synchronous limit, and a contract that does not include the request. You get it by naming the file with a background suffix or by exporting the appropriate configuration, and you use it by returning a response immediately and doing the work through context.waitUntil(). The 15 minutes is the total wall clock for the invocation, not an idle timeout and not a per-request allowance: work that is waiting on a slow third party is consuming that budget whether or not it is consuming CPU.

The second property, and the one that matters for design, is that a background function is not guaranteed to run promptly. A request that triggers background work returns immediately; the work is scheduled on the platform and starts when capacity is available. Under bursty load, a sudden queue of a thousand triggers will not start a thousand invocations at once, and the latency between the request and the start of the work is unbounded from the caller’s perspective. This means a background function is the wrong tool for anything the user is waiting on, and the right tool only for work whose completion is not part of any user-visible interaction.

The third property is that there is no retry. A background function that throws is finished, and nothing re-invokes it. The platform’s job queue is not a durable message queue and does not provide the delivery guarantees that a queue implies. Any design in which losing a job is unacceptable therefore requires an external durable queue, with the background function acting as the consumer that pulls from it, so that a failure leaves the message available for redelivery. A common and sound architecture is: an external queue as the source of truth, a background function per message, and idempotency in the handler so that a redelivered message is harmless.

// netlify/functions/sync-customer-background.ts
// The "background" suffix grants the 15-minute wall clock and the waitUntil
// contract. The caller gets 202 immediately; the work happens after.
import type { Context } from "@netlify/functions";
import { syncCustomer } from "../src/domain/sync";
import { logger } from "../src/observability/logger";

export default async (req: Request, { waitUntil, log }: Context) => {
  if (req.method !== "POST") {
    return Response.json({ error: "method_not_allowed" }, { status: 405 });
  }
  const { customerId } = await req.json() as { customerId: string };

  waitUntil(
    (async () => {
      // Idempotency is not optional here. A redelivered trigger, a manual
      // re-invocation, and a retry from your own queue can all run this twice.
      const claimed = await claimOnce("sync-customer", customerId);
      if (!claimed) { log.info("already claimed", { customerId }); return; }

      try {
        const result = await syncCustomer(customerId);
        await markDone("sync-customer", customerId, result);
      } catch (err) {
        // A throw ends the invocation. Nothing retries. The durable queue, not
        // this function, is what guarantees eventual completion.
        await markFailed("sync-customer", customerId, err);
        logger.error("sync.failed", { customerId, err });
        throw err;
      }
    })(),
  );

  return Response.json(
    { status: "accepted", customerId },
    { status: 202, headers: { Location: `/ops/sync/${customerId}` } },
  );
};

Idempotency in a background handler is the difference between a design that survives a redelivery and one that silently double-charges a customer. The pattern is a claim: before doing work, take a unique key representing the logical operation and insert it into a table with a unique constraint. If the insert succeeds, you own the work. If it fails on the constraint, someone else owns it and you return immediately. Release the claim on completion, and set a lease expiry so that a crashed worker’s claim becomes reclaimable. This is the same pattern you would use with any queue, and it is the reason a durable queue is worth the operational cost even when the trigger is a background function.

On the naming of the suffix, be careful: the convention that matters is that the function name ends with a recognisable marker, and the exact spelling is validated at build time with a build error rather than a silent downgrade. If your function is not being given the background treatment, the build log will say so, and the symptom in production is a job that dies at the synchronous timeout with no other explanation. Assert the timeout you expect in the deploy check rather than assuming it.

3.4 Timeouts, memory and payload limits

Enumerates the enforced ceilings, distinguishes the ones that produce clean errors from the ones that produce truncated output, and gives the diagnostic sequence for each.

Three limits produce failures that are hard to attribute, and each has a distinctive signature. The memory limit is enforced by the underlying Lambda runtime, which terminates the process without generating a response. If your handler has already written response headers, the client observes a truncated body or a connection reset rather than an error status, and the deploy log shows only that the invocation started. The wall-clock timeout is enforced by the platform, which kills the invocation and returns a gateway error to the client. The request payload limit is enforced at the edge, before your handler runs, so a guard in your code never fires and you must handle the edge’s error shape instead of your own.

Memory is the one to instrument first. Because out-of-memory is silent, the only reliable detection is measurement: record peak memory per invocation, alert on a trend rather than a threshold, and when you see intermittent resets on a memory-shaped handler, raise memory before you optimise code. Halving memory usually improves cold start and throughput, so the correct first response to a reset is to measure rather than to increase, unless the handler genuinely needs the memory.

// netlify/functions/upload-document.ts
// Enforce the payload limit explicitly and return a shape the client expects.
// The edge also enforces it, but only if your own guard has not already
// produced a better error.
const MAX_BYTES = 5 * 1024 * 1024;   // stay under the 6 MB platform cap
const ALLOWED  = new Set([
  "application/pdf",
  "image/png",
  "image/jpeg",
  "text/csv",
]);

export default async (req: Request) => {
  if (req.method !== "POST") {
    return Response.json({ error: "method_not_allowed" }, { status: 405 });
  }

  const declared = Number(req.headers.get("content-length") ?? "0");
  if (declared > MAX_BYTES) {
    return Response.json(
      { error: "payload_too_large", maxBytes: MAX_BYTES },
      { status: 413, headers: { "Retry-After": "0" } },
    );
  }

  const type = req.headers.get("content-type")?.split(";")[0] ?? "";
  if (!ALLOWED.has(type)) {
    return Response.json({ error: "unsupported_media_type" }, { status: 415 });
  }

  // Read with a hard cap so a lying content-length cannot exhaust memory.
  const reader = req.body?.getReader();
  if (!reader) return Response.json({ error: "empty_body" }, { status: 400 });

  let total = 0;
  const chunks: Uint8Array[] = [];
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    total += value.byteLength;
    if (total > MAX_BYTES) {
      await reader.cancel();
      return Response.json({ error: "payload_too_large" }, { status: 413 });
    }
    chunks.push(value);
  }
  const buf = new Uint8Array(total);
  let off = 0;
  for (const c of chunks) { buf.set(c, off); off += c.byteLength; }

  const doc = await store(buf, type, total);
  return Response.json({ id: doc.id, bytes: total }, { status: 201 });
};

3.5 Concurrency, streaming and connection behaviour

Explains what happens above the concurrency ceiling, how streaming changes both memory and timeout behaviour, and what does and does not happen when a client disconnects.

Each plan provides a number of concurrent function executions per site. Requests above that number are not rejected; they wait, and the queue is the only backpressure you have. This has three practical consequences. First, a concurrency ceiling of one means a single slow request blocks every other request to that function, which makes per-function concurrency the right unit for capacity planning and makes separate functions the unit for isolation. Second, a synchronous endpoint that fans out internally multiplies its concurrency consumption, because each concurrent invocation may hold several connections at once, so a handler with a four-way fan-out effectively has a quarter of the stated capacity. Third, a queued request is consuming the client’s timeout budget while it waits, so a function with a 26-second ceiling can still return 504 to a client whose own timeout is 10 seconds.

Streaming changes the shape of a request in three ways. Memory falls, because you no longer need to materialise the whole response. The timeout semantics change, because a streamed response’s headers reach the client immediately, so a stream that stalls midway produces a client that has already received a 200 and then observes a truncated body. And the failure mode becomes harder to attribute, because the client reports a parse error at an arbitrary offset rather than a status code. Streaming is correct for large or slow-to-produce responses and is the wrong choice when a failure after the headers is likely, because you cannot retract a 200.

Connection behaviour has one rule that surprises people: a client disconnect does not reliably stop your function. The invocation continues until it finishes or hits its timeout, and you continue to pay for it. For a handler doing expensive work on behalf of a user who has navigated away, that is wasted spend. Cancelling on abort is worth doing explicitly by passing the request signal through to your own downstream calls, which at least stops the network cost, and is worth doing whenever your handler does more than one round trip.

// netlify/functions/export-report.ts
// Streamed response: headers flush immediately, body is produced lazily.
// Memory stays flat regardless of export size.
export default async (req: Request, context: any) => {
  const started = Date.now();
  const budget  = 20_000;                 // leave headroom under the 26 s ceiling
  const rows    = await queryRows(req, { signal: req.signal });

  const encoder = new TextEncoder();

      controller.enqueue(encoder.encode("id,total,created_at\n"));
      let sent = 0;

        for await (const row of rows) {
          if (Date.now() - started > budget) {
            // We are already committed to a 200. Say so in-band and stop
            // cleanly rather than being terminated mid-stream.
            controller.enqueue(encoder.encode(
              `\n# TRUNCATED at ${sent} rows; narrow the filter and retry\n`));
            break;
          }
          controller.enqueue(encoder.encode(
            `${row.id},${row.total},${row.created_at}\n`));
          sent++;
        }
        controller.close();
      } catch (err) {
        controller.enqueue(encoder.encode(`\n# ERROR ${(err as Error).message}\n`));
        controller.close();               // in-band error, still a valid CSV
      }
    },
  });

// cannot consume the whole site allowance.
const LIMIT = 4;
async function mapLimit<T, R>(items: T[], fn: (t: T) => Promise<R>): Promise<R[]> {
  const out: R[] = new Array(items.length);
  let next = 0;
  await Promise.all(
    Array.from({ length: Math.min(LIMIT, items.length) }, async () => {
      while (next < items.length) {
        const i = next++;
        out[i] = await fn(items[i]);
      }
    }),
  );
  return out;
}

A streamed 200 cannot be taken back. Once your handler returns a response with status 200 and the first bytes, the client has committed to success. 3.6 Cold starts and local parity with the edge runtime

Explains what determines cold start cost, which levers actually reduce it, and how to achieve real local parity for both function types.

Cold start cost is the time between a request arriving at a function with no warm instance and the first byte of the response. It decomposes into container start, runtime initialisation, module loading, and your own top-level work, and the last of those is the only one entirely under your control. The most common cause of a slow top-level contribution is initialising a client at module scope: a database pool, an HTTP agent, a large JSON import, or a crypto library. Those initialisation costs are paid on every cold start and are pure overhead if the instance then serves a handful of requests before going idle.

The levers, in order of value per effort: reduce bundle size, since a smaller archive loads faster; move initialisation into the first request rather than into module scope, and pay it once per container instead of conceptually per process; avoid top-level await of network resources, since a module that awaits a fetch at import time is a container that cannot serve a request until that fetch completes; and keep dependencies shallow, since a wide import graph is slower to evaluate than a narrow one even at equal size. What does not help is warming instances you do not control and code that optimises for the warm path, which is already fast.

// Good: lazy, single-flight initialisation. Cost paid once per container,
// concurrently rather than serially across cold starts.
let clientPromise: Promise<Database> | null = null;

function getDb(): Promise<Database> {
  if (!clientPromise) {
    clientPromise = (async () => {
      const [primary, replica] = await Promise.all([
        connect(process.env.DATABASE_URL!,   { pool: { min: 1, max: 4 } }),
        connect(process.env.READ_REPLICA_URL!, { pool: { min: 1, max: 8 } }),
      ]);
      return { primary, replica };
    })().catch((err) => { clientPromise = null; throw err; });
  }
  return clientPromise;
}

// into the bundle. Keep the import surface to the domain module you need.
import { everything } from "../src/index";    // do not do this in a function

Local parity is the other half of the problem, and Netlify’s development server is better here than most platforms because it runs both runtimes for real. netlify dev serves the publish directory, applies your header and redirect rules in the same order the edge will, runs Lambda functions with the bundler the build uses, and runs edge functions on the actual Deno runtime rather than emulating them. That last point is what makes it a genuine safety net for edge work, because the Deno-versus-Node divergence is exactly the class of bug that survives a Node-based local shim and fails in production.

Use the offline modes deliberately. netlify dev --offline serves the previously built function bundles instead of rebuilding them, which turns a multi-second loop into an instant one when you are changing application code rather than function code; it is the right default once the function layer is stable. netlify dev --edge narrows the server to edge functions and their configuration, which is a faster and less noisy loop when you are working on request-time logic specifically. And netlify functions:invoke <name> runs a single function with a constructed event, which is the fastest way to test a handler’s error paths without constructing a full request.

The verification that matters is the one you cannot do locally: measure cold start in production, per function, continuously, and watch the distribution rather than the mean. A function whose p99 cold start is an order of magnitude above its p50 is almost always initialising something at module scope that occasionally blocks, most often a network call or a large parse. Instrument the container, not the request, because the request timer does not start until after the container is ready, which means the metric you would naturally reach for does not contain the cost you are trying to reduce.

4 · Forms, Identity and Access Control

Netlify’s built-in form handling and Identity service remove most of the boilerplate from a small application, but both sit on a simple model that becomes surprising the moment a site grows past a handful of users. This chapter explains exactly what the platform guarantees, where the guarantees stop, and how to keep authorization decisions on the server rather than in the browser.

4.1 The form pipeline and what Netlify actually runs

A static site has no application server, so a traditional <form action="/api/contact"> has nothing to post to. Netlify solves this by parsing the HTML at deploy time, extracting every form element, and registering a submission endpoint in the platform’s form backend. Nothing about the site changes at runtime; the work happened during the build.

The form element needs almost nothing beyond the standard attributes. The name attribute becomes the field key in the submission payload, and it is the only part that carries meaning.

<!-- public/contact.html -->
<form name="contact" method="POST" data-netlify="true" netlify-honeypot="bot-field">
  <input type="text" name="name" required>
  <input type="email" name="email" required>
  <select name="topic">
    <option value="sales">Sales</option>
    <option value="support">Support</option>
  </select>
  <textarea name="message" required></textarea>

  <!-- rendered to humans, ignored by people. Bots fill it in. -->
  <p class="hp"><label>Do not fill this in</label>
     <input name="bot-field"></label></p>

  <button type="submit">Send</button>
</form>

Three attributes do the work. data-netlify="true" marks the form for registration; it is what the build-time parser looks for, and omitting it is the single most common reason a form silently does nothing. name supplies the field keys. netlify-honeypot="bot-field" points at the decoy input.

Forms in a JavaScript-rendered page are invisible to the parser. If the form is produced by React, Vue or Svelte at runtime, the build-time HTML never contains it and no endpoint is created. The fix is to declare the form in a static file that ships in the build output, hidden or not, so the parser can see it, while your client code handles submission. Many teams keep an invisible forms.html that lists every dynamic form.

4.2 Reading submissions: API, dashboard and webhooks

Submissions are stored by Netlify and are queryable through the REST API. The API is the only durable record: the dashboard is a view over it, and deleting a site deletes its submissions. Anything you intend to keep must be copied out.

# List submissions for one form (API v1, form-scoped)
curl -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     "https://api.netlify.com/api/v1/forms/contact"

# Filter by site, then read one submission's fields
curl -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     "https://api.netlify.com/api/v1/sites/$SITE_ID/forms?form_id=contact"

# Decode the base64 form_data payload
curl -s -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     "https://api.netlify.com/api/v1/forms/$FORM_ID/submissions/$SUBMISSION_ID" \
  | jq -r '.form_data' | base64 -d | jq .

The form_data field is base64-encoded JSON, which makes bulk export awkward but keeps the API opaque to clients that should not be introspecting it. A common operational pattern is a scheduled drain that writes each submission to durable storage and then deletes it from Netlify, so the platform is used as a queue rather than a database.

Rate limits, retention and per-plan submission quotas are all plan-dependent and subject to change. Treat the numbers in the dashboard as authoritative rather than hard-coding them, and always implement your own throttling in a Netlify Function if the form is public-facing.

4.3 Spam protection, honeypots and bot filtering

A publicly hosted form with no throttling will be found and abused. Netlify applies a baseline spam score to each submission and drops submissions above a threshold, but the exact scoring is opaque and the coverage is not a substitute for your own controls.

The time-to-submit check is underused and needs no third party. Record a timestamp when the form renders and compare it at submission.

// public/contact.html

  <!-- ...fields... -->
</form>

</script>

// Reject anything submitted implausibly fast.
export default async (request) => {
  const form = await request.formData();
  const openedAt = Number(form.get('ts'));
  if (!openedAt || Date.now() - openedAt < 2000) {
    return new Response('Too fast', { status: 400 });
  }
  return new Response(JSON.stringify({ ok: true }), {
    headers: { 'content-type': 'application/json' },
  });
};

Rejecting a submission should be indistinguishable to the client from accepting it. A bot that receives a 400 learns it was detected; one that receives a cheerful success page does not. Return 200 with a neutral body and discard the payload quietly in the background.

4.4 Netlify Identity: users, registration and the widget

Netlify Identity is a hosted user store. It provides registration, confirmation, password recovery and a set of OpenID Connect endpoints, and it can be enabled per site or per team. The identity data lives with Netlify, not in your application, which is the central architectural decision.

Enabling it is a toggle, not a code change. The endpoints appear immediately at https://<site>.netlify.app/.netlify/identity, and the service supports the standard OIDC discovery document, so any compliant client library can discover the issuer, authorisation and token endpoints automatically.

// netlify.toml
[build]
  publish = "dist"
  command = "npm run build"
  functions = "netlify/functions"

[build.environment]
  # Public, non-secret. This is the site URL, not an API token.
  IDENTITY_URL = "https://example.netlify.app/.netlify/identity"

The simplest integration is the widget. It is a single script that renders a complete login form, and it ships as a Web Component so it does not require a build step or a framework.

<!-- public/account.html -->
<div id="user"></div>
<script src="https://identity.netlify.com/v1/netlify-identity-widget.js"></script>
<script>
  const identity = window.netlifyIdentity;
  identity.on('init', user => {
    if (user) {
      document.getElementById('user').textContent = user.email;
    } else {
      document.getElementById('user').textContent = 'signed out';
    }
  });
  identity.on('login',  () => { window.location.href = '/app/'; });
  identity.on('logout', () => { window.location.href = '/'; });
</script>

Identity is not an application database. The user object carries id, email, confirmed, created_at, app_metadata and user_metadata. Anything else you need — a subscription tier, a billing identifier, a permission list — you must store yourself and associate with user.id. Treat Netlify as the authentication authority and your own store as the system of record for everything else.

4.5 Authentication flows: email, OAuth, SSO and tokens

Identity supports several ways for a person to prove who they are, and they all converge on the same artifact: a signed JWT that the browser stores and a Function can verify. Understanding what that token contains, and what it does not, is what separates a working auth system from a broken one.

// netlify/functions/me.js — verify the caller, read claims, decide.
import jwt from 'jsonwebtoken';

const AUTH0_DOMAIN = process.env.IDENTITY_DOMAIN;   // e.g. example.netlify.app
const JWKS_URL = `https://${AUTH0_DOMAIN}/.netlify/identity/.well-known/jwks.json`;

function bearer(req) {
  const h = req.headers.get('authorization') || '';
  return h.startsWith('Bearer ') ? h.slice(7) : null;
}

export default async (request) => {
  const token = bearer(request);
  if (!token) return new Response('unauthorized', { status: 401 });

  try {
    // Verify signature, issuer and expiry against the published JWKS.
    const claims = jwt.verify(token, JWKS_URL, {
      issuer: `https://${AUTH0_DOMAIN}/.netlify/identity`,
      audience: 'app',
      algorithms: ['RS256'],
    });
    return new Response(JSON.stringify({
      sub: claims.sub,
      email: claims.email,
      roles: claims.app_metadata?.roles ?? [],
    }), { headers: { 'content-type': 'application/json' } });
  } catch {
    return new Response('unauthorized', { status: 401 });
  }
};

Never decode a JWT without verifying it. Calling jwt.decode() or JSON.parse(atob(...)) and then branching on the result is the most common authentication bypass in serverless applications, because the payload is trivially forgeable. Only the signature check makes a token trustworthy, and only the signature check is slow enough to matter.

Put Netlify Identity intest mode while developing. In test mode the widget accepts any password, which removes a whole class of confusing failures during integration work. Turn it off before the site is public.

4.6 Authorization: roles, gated sites and server-side checks

Authentication answers "who is this". Authorization answers "may they do this". Netlify gives you two coarse mechanisms for the second question — a site password, and per-user roles in the token — and a third pattern you have to build yourself: gating a whole path prefix behind a Function that redirects unauthenticated visitors.

A site password is a single shared secret set in the Netlify UI or API. It guards the entire site behind a browser prompt. It is useful for staging sites and for client review builds, and it should never protect production, because it has no user identity, no revocation and no audit trail beyond Netlify’s own logs.

// Set or clear the site password (Basic auth at the edge).
curl -X PUT \
  -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"password":"a-long-unique-secret"}' \
  "https://api.netlify.com/api/v1/sites/$SITE_ID/password"

curl -X DELETE \
  -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
  "https://api.netlify.com/api/v1/sites/$SITE_ID/password"

For anything with real users, keep a role list in the token’s app_metadata. The Admin API is the only supported way to set it, and it requires a personal access token, so it belongs in a script or a CI job rather than in a request handler.

// scripts/grant-role.mjs — run from CI, never from a Function.
const userId = process.argv[2];
const role   = process.argv[3] || 'editor';

const res = await fetch(`https://api.netlify.com/api/v1/users/${userId}`, {
  method: 'PUT',
  headers: {
    Authorization: `Bearer ${process.env.NETLIFY_AUTH_TOKEN}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ app_metadata: { roles: [role] } }),
});

if (!res.ok) { console.error(res.status, await res.text()); process.exit(1); }
console.log(`granted ${role} to ${userId}`);

Roles live in app_metadata, which is only writable by the API, and user_metadata, which the user can write themselves. Anything a user must not be able to grant to themselves belongs in app_metadata. Confusing the two is the most common privilege-escalation bug in this stack.

4.7 Enforcing access control in functions

Static assets are, by construction, public. Anyone who knows the URL can fetch a file from the CDN, and Netlify does not apply per-user authorization to published assets. Therefore: anything that must be private cannot be a static file. It has to be a Function that authenticates the caller and streams the bytes.

// netlify/functions/report.js — a gated download, not a static asset.
import jwt from 'jsonwebtoken';
import { S3Client, GetObjectCommand } from '@aws-sdk/client-s3';

const s3 = new S3Client({ region: process.env.AWS_REGION });

async function authorize(request) {
  const h = request.headers.get('authorization') || '';
  if (!h.startsWith('Bearer ')) return null;
  try {
    return jwt.verify(h.slice(7), process.env.JWKS_URL, {
      issuer: process.env.IDENTITY_ISSUER, audience: 'app',
    });
  } catch { return null; }
}

export default async (request) => {
  const claims = await authorize(request);
  if (!claims) return new Response('unauthorized', { status: 401 });

  // Authorization is a separate decision. Verify, then check the claim.
  const roles = claims.app_metadata?.roles ?? [];
  if (!roles.includes('analyst')) {
    return new Response('forbidden', { status: 403 });
  }

  const key = `private/${claims.sub}/report.csv`;
  const obj = await s3.send(new GetObjectCommand({ Bucket: process.env.BUCKET, Key: key }));
  return new Response(obj.Body, {
    headers: {
      'content-type': 'text/csv',
      'cache-control': 'private, no-store',
    },
  });
};

Three decisions in that handler matter more than the rest. The object key is derived from the verified subject, never from a request parameter, so one user cannot read another user’s file by editing a URL. The response carries no-store, so a shared cache does not retain private content. And the role check runs on the server, where the client cannot influence it.

ControlWhere it belongsReason
Hiding a nav linkClient, cosmetic onlyNot a control; the endpoint is still callable
Disabling a buttonClient, cosmetic onlySame; trivially bypassed by calling the API
Validating the tokenFunction, mandatoryThe only place the caller is untrusted
Checking the role claimFunction, mandatoryAuthentication is not authorization
Scoping the object key by subjectFunction, mandatoryPrevents horizontal access across users
no-store on private responsesFunction, mandatoryStops CDN and browser caching of secrets

Netlify Functions can be invoked from anywhere by default, so a Function holding privileged logic is reachable from any origin unless you restrict it. For admin-only endpoints, check an allowlist of origins or require a separate secret header that is never present in client code, and treat CORS as a browser convenience rather than a security control.

5 · The Edge Network, CDN and Caching

A static site is fast for reasons that are almost entirely about caching, and caching is where most of the achievable performance lives. This chapter covers the request path, how to set cache policy that survives a deploy, what invalidation actually costs, and the transport-layer and privacy characteristics of Netlify’s edge.

5.1 How a request reaches the edge

Netlify runs a content delivery network built on Cloudflare’s infrastructure, with published points of presence in roughly 300 metropolitan areas. The path from a browser to your bytes is short, and understanding its stages explains most of the headers you will end up writing.

Redirects are evaluated at the edge before a Function is considered, which matters when both could match a path. A redirect rule for /old always wins over a Function at /.netlify/functions/old, and the specificity rules among redirect rules themselves are documented but worth confirming against the current documentation for any rule set you depend on.

Because the edge serves from a distributed cache, the first request after a deploy to a given path may still be answered by a stale entry on a PoP that has not yet been told the object changed. For content that must be absolutely current, either send Cache-Control: no-cache or accept the small propagation window, which is normally a few seconds.

5.2 Cache-Control, immutable assets and content hashing

Two categories of file on a static site want opposite cache policies. Fingerprinted build output should be cached essentially forever, because its URL changes whenever its content changes. The HTML that references it should be revalidated on every visit, because it is the only thing that points at the new filenames.

Content hashing is the mechanism that makes this safe. The build tool writes a file, hashes its contents, and puts the hash in the filename. A change produces a new URL, so no cache anywhere holds a stale copy, and the old file can be left in place for as long as any browser might still request it.

# vite.config.js
export default {
  build: {
    // app.a1b2c3d4.js - changes only when the contents change
    assetsDir: 'assets',
    rollupOptions: {
      output: {
        entryFileNames: 'assets/app.[hash].js',
        chunkFileNames: 'assets/[name].[hash].js',
        assetFileNames: 'assets/[name].[hash][extname]',
      },
    },
  },
};

Now the headers. The correct policy is: HTML short-lived or revalidating, hashed assets immutable for a year, and anything under assets/ treated as immutable even if the filename is not hashed, provided it changes name when it changes.

# _headers file at the publish root
/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'

# Hashed build output: never revalidate, it cannot change.
/assets/*
  Cache-Control: public, max-age=31536000, immutable

# HTML must be revalidated so it points at the current asset names.
/index.html
  Cache-Control: public, max-age=0, must-revalidate

/*.html
  Cache-Control: public, max-age=0, must-revalidate

Applying immutable to HTML is the most damaging header mistake on a static site. Because the HTML is what names the assets, an immutable cached index.html will keep pointing at asset files that may have been replaced, and visitors will load a page referencing JavaScript that no longer exists. Immutable belongs on the fingerprinted files and nowhere else.

Netlify offers three equivalent places to declare headers. They are merged, with later sources taking precedence, and using more than one is a common source of confusion when a rule appears not to apply.

5.4 Purge, cache tags and cache invalidation

Invalidation is the escape hatch for when content is not fingerprinted and you cannot wait for a natural expiry. Netlify offers three mechanisms, and choosing between them comes down to how much of the site you are willing to evict.

MechanismGranularityCost and limitsUse when

Cache tags are the useful one. You declare which tags a response belongs to, and then evict every object carrying a tag in a single call. The pattern that pays for itself is a shared navigation or footer fragment: one change invalidates every page that includes it, with one request.

# Tag a response so it can be purged as a group.
export default async () => {
  const body = await renderNav();
  return new Response(body, {
    headers: {
      'content-type': 'text/html',
      'cache-control': 'public, max-age=300, stale-while-revalidate=86400',
      'netlify-cache-tag': 'nav,shared',
    },
  });
};

# Purge every object tagged "nav" (or one specific path).
curl -X POST -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"tags":["nav"]}' \
     "https://api.netlify.com/api/v1/cache/tags/purge"

curl -X POST -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"paths":["/pricing","/pricing/enterprise"]}' \
     "https://api.netlify.com/api/v1/cache/purge"

Aggressive purging is self-defeating. Every purge forces the next visitor to be a cache miss and a slow origin fetch, and repeated purging will keep your origin warm path hot and your perceived performance poor. The correct steady state for a static site is that almost nothing needs purging at all, because the deploy already replaced the content and the fingerprints already changed the URLs. Reach for a purge only for content changed outside the deploy pipeline.

5.5 IPv6, HTTP versions and custom domains

Netlify serves IPv4 and IPv6, and supports HTTP/2 and HTTP/3 without configuration. A custom domain is attached through DNS, and the certificate is issued and renewed automatically once the domain resolves correctly.

# 1. Add the domain to the site (this returns the required DNS values)
curl -X POST -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"site_id":"'"$SITE_ID"'","custom_domain":"www.example.com"}' \
     "https://api.netlify.com/api/v1/domains"

# 2. Confirm the site is served correctly before the certificate issues
curl -sI https://www.example.com | head -20

DNS is where custom domains usually go wrong, and the failure modes are worth memorising because they look identical from the browser.

DNS recordPurposeConsequence of getting it wrong

If a CAA record exists on the parent zone, it must permit the actual issuer. A CAA record left over from a previous host is a frequent cause of a domain that resolves correctly and never receives a certificate.

5.6 Privacy, data residency and the DPA

A static site stores no personal data of its own, but the platform you host it on does: request logs, IP addresses, account details, form submissions and any analytics you enable. If your visitors are in the European Economic Area, the transfer of that data outside the EEA needs a lawful basis, and for many organisations that basis is the vendor’s standard contractual clauses plus a signed data processing agreement.

Where is request data processed?Determines whether a transfer mechanism is requiredNetlify’s trust centre and subprocessor list

These are contractual and organisational questions, not technical configuration. The practical engineering consequence is smaller than it looks: keep personal data out of the static build output, keep it out of repository history, and confine it to a Function that talks to a database you control. A static site that holds no user data is far easier to make compliant than one whose build folder is full of generated personal reports.

Add a privacy notice that names the actual processors, including the CDN and any analytics, and link it from the footer of every page. It is a small amount of work that resolves a surprising number of compliance questions before they are asked.

This chapter describes general practice, not legal advice. Data protection obligations vary by jurisdiction and by sector, and the specifics should come from whoever is responsible for compliance in your organisation.

6 · Environments, Contexts, Deploy Previews and Branch Subdomains

6.1 Contexts: the four environments and how they differ6.2 Environment variables, scopes and the precedence trap6.3 Deploy Previews and their lifecycle6.4 Branch subdomains and deployment behaviour rules6.5 Promoting a deploy without rebuilding6.6 Secrets handling and what must never be a build variable

Netlify’s environment model has four contexts rather than the three that most teams assume, and the differences between them are the source of most "it worked in production" incidents. This chapter defines each context, explains the variable precedence that catches people out, and covers the branch and preview machinery in enough detail to build a release process on top of it.

6.1 Contexts: the four environments and how they differ

A context is a build environment with its own variables, its own build command and its own deploy. There are four: production, deploy preview, branch deploy and branch review. They are not equally featured, and the gaps matter.

ContextTriggered byURL shapeNotable differences
ProductionMerge to the production branch, or a manual deployThe apex or custom domainFull access to production variables; the only context that serves the primary domain
Deploy previewAny pull request or any branch not marked as a production branchA unique per-deploy URLPreview variables plus shared variables; never gets production secrets
Branch deployPush to a branch marked "branch deploy" in the UIbranchname--sitename.netlify.appPersistent URL; good for staging that should not vanish
Branch reviewA push, reviewed in the interface before it is publishedNot published until acceptedThe deploy is held; used for design review and QA

The production context is not merely a name. It is the only context where the variables you have not explicitly marked as shared are visible, and the only one whose deploy can take over the site’s custom domain. A deploy preview that appears to work but reads undefined for a production-only variable is behaving correctly.

Branch deploys are not production and must never be treated as such. A common failure is a team that configures the production branch correctly, assumes a staging branch is equivalent, and discovers at release time that the staging build was assembled from preview variables and silently omitted a feature flag. Verify which context a deploy ran in before trusting it.

6.2 Environment variables, scopes and the precedence trap

A variable can be scoped in three ways: to a single context, to all deploys, or to a specific branch or deploy. These compose, and the composition order is what surprises people — a value set for a single deploy beats everything, which is convenient for testing and dangerous if a deploy is ever triggered by hand in the wrong context.

# Declarative variables, version-controlled, no secrets here.
# netlify.toml
[build.environment]
  NODE_VERSION = "24"
  PUBLIC_SITE_URL = "https://example.com"

[context.production.environment]
  PUBLIC_API_URL = "https://api.example.com"

[context.deploy-preview.environment]
  PUBLIC_API_URL = "https://staging-api.example.com"

[context.branch-deploy.environment]
  PUBLIC_API_URL = "https://staging-api.example.com"

Anything in [build.environment] is available to the build in every context. Anything under a [context.*] block is only available in that context. The API can then apply additional overrides, and those are applied after the file, which is why a value can differ between two runs of the same commit.

Precedence (highest first)SourceTypical use
1. Per-deploy overrideSet on a single deploy through the API or the UIReproducing a production failure with production secrets
2. Per-branch overrideSet on a branch, applies to that branch’s deploysGiving main-staging a distinct database
3. Context scopeSet for production, deploy preview, or branch deployThe ordinary arrangement
4. Shared variablesVisible to all deploysA build token, a read-only API key
5. [build.environment] in netlify.tomlCommitted to the repositoryVersions, flags, public URLs

# Set a variable for one context only, via the API.

     -H "Content-Type: application/json" \

     "https://api.netlify.com/api/v1/accounts/$ACCOUNT_ID/env"

# Set one for every deploy (treat as a shared secret).
curl -X PUT -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"key":"NPM_TOKEN","value":"npm_...","context":"*"}' \
     "https://api.netlify.com/api/v1/accounts/$ACCOUNT_ID/env"

# Set one for a single branch, above the context scope.
curl -X PUT -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"key":"PUBLIC_API_URL","value":"https://qa.example.com","context":"branch:qa-staging","branch_deploys":true}' \
     "https://api.netlify.com/api/v1/accounts/$ACCOUNT_ID/env"

Log the effective configuration at the top of every build, with values redacted. A one-line env dump naming each variable and printing only whether it is set turns a two-hour environment debugging session into a two-minute one, and costs nothing.

6.3 Deploy Previews and their lifecycle

Every pull request gets its own build and its own URL. The URL contains a random token and does not change when the pull request is updated, so a link shared in review continues to work across commits. The preview is destroyed when the pull request is closed or merged, unless it is explicitly retained.

# List recent deploys, newest first, with their state and context.
curl -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
  "https://api.netlify.com/api/v1/sites/$SITE_ID/deploys?per_page=10" \
  | jq '.[] | {id, state, context, branch, deploy_url, created_at}'
Deploy stateMeaningWhat to do
newQueued, build not startedWait
buildingBuild in progressWatch the log
uploadingAssets being written to the deploy storeWait
readyLive and servingNone
errorBuild or deploy failedRead the log; the exit code is the useful part
retryingTemporary infrastructure failure, being retriedWait; escalate if it persists

Because previews are destroyed on merge, any external system that needs to reach a preview has to do so while the pull request is open. For a database migration under test this is usually fine, because the migration is applied once against a shared test database rather than against a preview-specific one.

To keep a preview alive after merge, call the restore endpoint on the deploy. Retained previews accumulate, and each one still occupies a slot against plan limits, so prune them deliberately rather than leaving them to accumulate.

6.4 Branch subdomains and deployment behaviour rules

Netlify can assign a stable subdomain to a branch, which turns a long-lived staging environment into something with a predictable address. Which branches get one is controlled by deployment behaviour rules, which are evaluated in order and where the first match wins.

# A stable subdomain per long-lived branch. Order matters: first match wins.
curl -X POST -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
  "rules": [
    { "type": "branch-deploy", "branch": "staging" },
    { "type": "branch-deploy", "branch": "qa" }
  ]
}' \
     "https://api.netlify.com/api/v1/sites/$SITE_ID/deploy-settings"
Rule typeMatchesEffect
production-branchThe configured production branchDeploys take over the primary domain
branch-deployNamed branchesGets a stable branch--site subdomain and branch-scoped variables
all-branchesEvery branch with a deployEach branch gets a persistent subdomain; useful for permanent demo sites
deploy-previewPull requestsPreviews are generated; the only way to turn them off
ignoreNamed branchesNo deploy at all; the usual treatment for dependabot/*

Ignoring automation branches is worth configuring from the start. Each merge from a dependency bot produces a build, and a repository with a dozen active bots spends a meaningful part of its build minutes on pull requests nobody will review.

Keep the number of branch deploys small. Each persistent subdomain is a separate deployed site consuming plan slots, and each one is a URL that will eventually be indexed by a search engine unless it is protected with a site password. Two or three long-lived environments is usually the right number.

6.5 Promoting a deploy without rebuilding

A rebuild is not always the same artifact. The build is not perfectly hermetic: a base image can change underneath you, a dependency registry can serve a different tarball, and a build that reads the current time embeds that time. Promoting an existing deploy sidesteps all of it, and is the right way to make a release decision you can point at afterwards.

# Promote an existing deploy to production. No rebuild occurs.
curl -X POST -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"deploy_id":"'"$DEPLOY_ID"'"}' \
     "https://api.netlify.com/api/v1/sites/$SITE_ID/deploys/$DEPLOY_ID/promote"

# Roll back is the same operation pointed at the previous deploy.
curl -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
  "https://api.netlify.com/api/v1/sites/$SITE_ID/deploys?per_page=5" \
  | jq '.[] | {id, created_at, state}'

Promotion carries the build environment of the source deploy, not of production. A preview promoted to production will be built from preview variables, so the promoted site will read PUBLIC_API_URL from the preview context and point at staging. Always confirm the variable set of the deploy you are about to promote, or promote a production-built deploy only.

A production promotion is instantaneous and needs no build minutes, which makes rollback as cheap as a promotion. That is the strongest argument for a release process that always knows the previous deploy identifier: keep it in the release record so the rollback command needs no lookup.

# A minimal release script that records both ids for rollback.
const prev = await netlify('/sites/'" + SITE + '/deploys?per_page=1').then(r => r.json());
const next = await netlify('/sites/'" + SITE + '/deploys', {
  method: 'POST',
  body: JSON.stringify({ branch: 'main', dir: './dist' }),
});
await netlify(`/sites/${SITE}/deploys/${next.id}/promote`, { method: 'POST' });
console.log(JSON.stringify({ deployed: next.id, rollbackTo: prev[0].id }));

6.6 Secrets handling and what must never be a build variable

Netlify distinguishes two kinds of secret, and confusing them is the single most damaging mistake in this chapter’s area. A build variable is available to your build command and therefore to any code the build runs. A runtime secret is encrypted at rest and served to a Function as an environment variable at invocation. A value that is available at build time must be treated as published.

PropertyBuild variableRuntime secret (Function)
Visible to the build commandYesNo
Visible in the deployed JavaScript bundleYes, if the code inlines itNo
Visible in the build logOnly if the build prints itNo
Rotatable without a rebuildNo, requires a new deployYes, takes effect on the next invocation
Suitable forPublic URLs, build flags, registry read tokensAPI keys, database passwords, signing secrets
# WRONG: a secret handed to the build ends up in the client bundle.
# Vite inlines any PUBLIC_ variable referenced in client code.
PUBLIC_STRIPE_SECRET_KEY = "sk_live_..."
# ...and `import.meta.env.PUBLIC_STRIPE_SECRET_KEY` is now in the shipped JS.

# RIGHT: keep it out of the build entirely, declare it as a Function secret.
# netlify/functions/charge.js
import Stripe from 'stripe';
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);

Any variable prefixed with a framework’s public prefix (VITE_, PUBLIC_, REACT_APP_, NEXT_PUBLIC_) is bundled into client code by design. Prefixing a secret is not a way to hide it; it is a way to publish it. The name is a contract with the bundler, and the bundler keeps it.

# Manage a Function secret through the API (values are write-only).
curl -X PUT -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"key":"STRIPE_SECRET_KEY","value":"sk_live_...","context":"production"}' \
     "https://api.netlify.com/api/v1/accounts/$ACCOUNT_ID/env"

# Secrets are decryptable to the runtime, but the API never returns them.
curl -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     "https://api.netlify.com/api/v1/accounts/$ACCOUNT_ID/env" \
  | jq '.[] | {key, scopes, context}'

Add a lint step that fails the build if a known secret name appears in the committed netlify.toml or in any file under public/. A short list of forbidden names is enough, and it converts the most catastrophic class of mistake in this stack from an incident into a failed pull request.

7.1 Log drains, scopes and the Functions log API

Netlify captures the output of a Function’s console and exposes it in the dashboard, but that store is for reading during development. For production you configure a log drain that streams every invocation to a destination you control, which is the only way to retain logs past the dashboard’s window or to alert on them.

# Configure a log drain to an S3 bucket (also: Datadog, New Relic,
# Honeycomb, Splunk, Azure Blob, Google Cloud Logging).
curl -X POST -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
  "site_id": "'"$SITE_ID"'",
  "type": "s3",
  "config": {
    "bucket_name": "acme-netlify-logs",
    "path": "functions/",
    "region": "eu-west-1",
    "access_key_id": "'"$AWS_KEY"'",
    "secret_access_key": "'"$AWS_SECRET"'"
  }
}' \
     "https://api.netlify.com/api/v1/log_drains"

// Structured output, not string concatenation. A log drain can parse this.
export default async (request, context) => {
  const start = Date.now();
  let status = 200;

  try {
    const order = await loadOrder(context.clientContext.user?.sub);
    if (!order) { status = 404; return new Response('not found', { status }); }
    return new Response(JSON.stringify(order), { status });
  } catch (err) {
    status = 500;
    // Log the detail; the client gets a correlation id and nothing else.
    const incident = context.randomUUID;
    console.error(JSON.stringify({
      level: 'error', msg: 'order load failed',
      incident, user: context.clientContext.user?.sub ?? null,
      err: String(err), stack: err?.stack,
    }));
    return new Response(JSON.stringify({ error: 'internal', incident }), { status });
  } finally {
    console.log(JSON.stringify({
      level: 'info', msg: 'request',
      path: new URL(request.url).pathname, status,
      ms: Date.now() - start,
    }));
  }
};

Emit one JSON object per line rather than formatted prose. A drain can then index fields, so you can alert on status >= 500 or on ms > 3000 without regular expressions. The context.randomUUID property is generated per invocation — use it as the correlation identifier you return to the client, and the two become joinable during an investigation.

7.2 Web Analytics and what it does not tell you

Netlify’s built-in analytics is a privacy-respecting, cookieless counter: no cross-site identifier, no personal data, and no script served to the visitor beyond Netlify’s own. 7.3 Error tracking and source maps

A minified production bundle reports a stack trace full of column offsets that correspond to nothing in your source. Source maps are the mapping that makes a production stack trace readable, and getting them to reach your error tracker requires configuring the build rather than the tracker.

// Vite: emit source maps, and hide the .map files from the public edge.
// vite.config.js
export default {
  build: {
    sourcemap: 'hidden',     // generates .map, no //# comment in the bundle
    rollupOptions: {
      output: { manualChunks: { vendor: ['react', 'react-dom'] } },
    },
  },
};

# Upload maps at build time, then strip them from the deploy.
# package.json
"scripts": {
  "build": "vite build",
  "build:release": "vite build && npm run maps:upload && npm run maps:clean",
  "maps:upload": "sentry-cli sourcemaps upload --release $RELEASE_ID dist/assets",
  "maps:clean": "rimraf dist/assets/*.map"
}

# Belt and braces: even without the clean step, never serve maps.
# _headers
/assets/*.map
  X-Robots-Tag: noindex
  Cache-Control: public, max-age=0, must-revalidate

Publishing source maps to a public CDN hands an attacker your original, unminified, un-obfuscated source. Many teams intend to upload maps to their tracker and forget to delete the local copies, and the deployment then serves the entire application logic to anyone who guesses the filename. Treat "are the maps gone from the deploy" as a release check, not a preference.

7.4 Measuring real performance, not synthetic scores

A synthetic score measures a machine in a data centre loading a cold cache. What matters is the time for a real visitor on a real network to see a usable page. These are different measurements, and conflating them leads to optimising the wrong thing.

# What a returning visitor actually experiences, from their machine.
curl -o /dev/null -s -w 'dns %{time_namelookup}s  tcp %{time_connect}s  tls %{time_appconnect}s\n' \
     -w 'ttfb %{time_starttransfer}s  total %{time_total}s  bytes %{size_download}\n' \
     https://example.com/

# The headers that decide how much of that is cache.
curl -sI https://example.com/assets/app.a1b2c3d4.js | grep -iE 'cache-control|age|etag|content-encoding'

# Is compression actually on?
curl -sI -H 'Accept-Encoding: gzip, br' https://example.com/ | grep -i 'content-encoding'
MetricWhere it comes fromGood valueWhat it tells you
TTFBReal user monitoring, or curl from a cold cache< 300 ms warmEdge and Function cost
LCPField data, not lab< 2.5 s at p75When the page became usable
CLSField data< 0.1Whether the layout jumped
INPField data< 200 msWhether the page responded to input

Core Web Vitals are defined against the 75th percentile of real visits, not the median and not the average, because a site that is fast for most people and unusable for a quarter of them has an INP problem. Any measurement reporting only a mean is reporting the number that hides the problem.

# Field data collection, the part that is actually hard to fake.
addEventListener('load', () => {
  const nav = performance.getEntriesByType('navigation')[0];
  const lcp  = performance.getEntriesByType('largest-contentful-paint').pop();

  navigator.sendBeacon('/api/vitals', JSON.stringify({
    path: location.pathname,
    ttfb: Math.round(nav.responseStart),
    domContentLoaded: Math.round(nav.domContentLoadedEventEnd),
    load: Math.round(nav.loadEventEnd),
    lcp: lcp ? Math.round(lcp.startTime) : null,
    connection: navigator.connection?.effectiveType ?? null,
  }));
});

# Step 6: does the HTML reference files the deploy actually has?
curl -s https://example.com/ | grep -oE '/assets/[^"]+' | sort -u | while read -r a; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "https://example.com$a")
  [ "$code" != "200" ] && echo "$code $a"
done

Roll back first, investigate second. If the previous deploy was healthy, promotion is instant, costs nothing, and stops the bleeding while you read logs at a human pace. Rolling back before you understand the cause is not malpractice — it is the first thing you do, and the investigation is far more productive against a site that is serving again.

7.6 Deploy notifications and third-party integrations

A deploy is the moment most incidents begin, so the deploy event is the moment worth notifying on. Netlify emits deploy events to any number of integrations, and the useful ones are the ones that put the build result where the team already looks.
