Welcome — How to Use This Alpine.js Guide

How this guide is organisedThe right mindsetTools you will use all course long

This opening section explains how to work through the guide most effectively. It sets the expectation that you should move chapter by chapter and type every snippet yourself rather than skim. The goal is a practical, hands-on grounding in Alpine.js so the concepts become automatic as you build.

Alpine.js is a tiny JavaScript framework for adding behaviour directly to your HTML. Everything in this guide runs in a single HTML file — no internet, no build step, no dependencies beyond a CDN script tag. Progress lives in your browser.

How this guide is organised

Describes the three-part structure of the guide spanning ten chapters, hands-on exercises, and a reference appendix. Chapters build one idea on top of another, and each ends with code snippets you should type out yourself. Knowing the path lets you locate any topic quickly and revisit the appendix for lookup tables.

  • Part I (Ch. 1–5) — the core: what Alpine is, state with x-data, the core directives, reactivity, and the magics that reach into the DOM.
  • Part II (Ch. 6–8) — real apps: fetching data, components and stores, and the official plugin fleet.
  • Part III (Ch. 9–10) — shipping: Alpine inside server-rendered apps such as Laravel Blade, Django and Rails, plus best practices and testing.
  • The appendix consolidates quick-reference tables for directives, magics, plugins and modifiers. Keep it open while you build.

The right mindset

Covers the philosophy that sets Alpine apart: behaviour lives in your markup rather than in a separate JavaScript layer. You write declarative expressions directly in attributes and let Alpine handle the imperative work. Thinking in terms of state and its reactions keeps components small and obvious.

Alpine is often called "the Tailwind of JavaScript": it borrows Tailwind’s philosophy of small, composable utilities living in your markup. You write x-show, x-bind and x-on as attributes directly on elements — there is no separate controller file, no virtual DOM, and no build step.

There is no state fetched from a server and no node list to reconcile: Alpine reads your attributes, sees the state you declared, and updates the DOM when that state changes. Type the snippets rather than pasting them — muscle memory matters.

1 · Alpine Fundamentals & Setup

1.1 What Alpine is and where it came from1.2 Installing Alpine with one script tag1.3 Your first x-data component1.4 Alpine vs Vue, jQuery, and when to use it

Introduces Alpine.js, how to load it via CDN, and how to build a first component with x-data. You create state and wire it to the page with directives to produce a working interactive element. By the end you can read Alpine markup fluently and understand the vocabulary used throughout the rest of the guide.

Alpine is a collection of attributes that turn ordinary HTML into reactive UI, weighing about 16 KB minified. This chapter establishes the baseline: where it came from, how to install it, and the single entry point everything else hangs off — x-data.

1.1 What Alpine is and where it came from

Places Alpine in the history of frontend tooling, tracing the ideas that run from jQuery through Vue and into Alpine’s deliberately small footprint. Alpine is an enhancement layer that sprinkles behaviour onto your existing HTML rather than an application framework. You add directives where you need them and leave the rest of the page alone.

Alpine was created by Caleb Porzio, the author of Tailwind CSS, as an answer to "how do I add a splash of interactivity without pulling in Vue or React?" Each directive does one small thing, and complex UI is composed from simple attribute combinations rather than a component tree backed by a diffing engine.

<!-- Compare: the same button in vanilla JS and in Alpine -->
<!-- Vanilla: find the node, attach a listener, mutate the DOM -->
<button id="btn">Click</button>
<script>
  let clicks = 0;
  document.getElementById('btn').addEventListener('click', () => {
    clicks++;
    document.getElementById('btn').textContent = 'Clicked ' + clicks;
  });
</script>

<!-- Alpine: declare the state and what should happen -->
<div x-data="{ clicks: 0 }">
  <button @click="clicks++" x-text="'Clicked ' + clicks">Click</button>
</div>

Alpine keeps the state and the event logic inside the markup itself, so a reader sees the whole behaviour in one small block instead of code scattered across a script tag.

1.2 Installing Alpine with one script tag

Shows the one-tag CDN installation used by most projects, with the defer attribute so the script boots after the DOM is ready. You verify Alpine actually loaded, usually by checking that an x-data component reacts. This single script tag is the entire installation for typical work.

<!-- Put this in the <head> of every page that needs Alpine -->
<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js"></script>

<!-- Verify it booted: open the console and evaluate -->
// typeof Alpine  →  "object" if the script loaded correctly
document.querySelectorAll('[x-data]').length;   // count of live components

The defer attribute makes the browser download Alpine while it parses the page and run it only after the DOM is ready, so Alpine sees every element it needs to initialise.

With the script in place, any element carrying an x-data attribute becomes a live component. If you already use a bundler, the same package also installs through npm — the CDN is simply the fastest path.

1.3 Your first x-data component

Builds the classic toggle component, which introduces the three ideas that cover most UI. One x-data attribute declares the state, an x-on handler responds to a click, and x-show or x-text reflects that state in the page. Combining declare, respond, and reflect is the core mental model.

<div x-data="{ open: false }">                <!-- state object -->
  <button @click="open = !open">Toggle</button> <!-- flip it -->
  <p x-show="open">Hello from Alpine!</p>      <!-- react to it -->
</div>

x-data creates a component owning the open property, @click assigns a new value, and x-show hides or shows the paragraph whenever open changes.

Compare this with the mindset from 1.1: the state, the trigger and the effect sit on the same three lines. There is no request, no reload, and nothing to re-render by hand.

1.4 Alpine vs Vue, jQuery, and when to use it

Weighs Alpine against Vue and jQuery while also judging when neither is the right call. Alpine trades the full power of a framework for a dramatically smaller mental load, making it best for server-rendered pages that want interactivity. The comparison helps you recognise when plain JavaScript or a full framework is the better tool.

OptionBest forTrade-off
Plain JS / jQueryTiny one-off interactionsState management is manual and easy to get wrong
AlpineDeclarative widgets on server-rendered pagesNot built for complex component trees
Vue / React / SvelteSPAs with rich client-side stateBuild step, tooling, and a steeper learning curve

The rule of thumb: if a page is mostly server-rendered and needs a pinch of interactivity — menus, toggles, filters, inline forms — Alpine is the sweet spot. If you find yourself writing dozens of components with a cross-cutting data model, move up to Vue, Svelte or React (chapter 10).

2 · State with x-data

2.1 Declaring state as an object2.2 Nested components and scope2.3 Getters and methods2.4 Reusable components with Alpine.data

Treats x-data as the single most important concept in Alpine, the place where all state is declared, scoped, and structured. The rest of the framework is essentially a reaction layer over this data: directives read it, events change it, and the DOM updates to match. Getting state right makes everything else fall into place.

In Alpine, x-data is the entry point of every component. Its value is a JavaScript object (or an expression returning one), and every property in that object is reactive state available to the directives inside the element. Master this chapter and the rest of the guide becomes vocabulary.

2.1 Declaring state as an object

Shows how to declare primitives, strings, and booleans inside an x-data expression and bind them to the page with x-text and x-model. The resulting object is readable by every directive nested below the component. Keeping the data flat and obvious makes expressions easy to reason about.

<div x-data="{ count: 0, name: 'Ada', ready: false }">
  <p x-text="count"></p>                      <!-- renders the current value -->
  <button @click="count++">Increment</button>
  <input x-model="name">                     <!-- two-way binding to state -->
  <p x-show="ready">Ready when the box is checked</p>
  <input type="checkbox" x-model="ready">
</div>

The component state object lives in x-data; x-text renders a value, x-model reads and writes it, and @click mutates it through a small expression.

2.2 Nested components and scope

Explains how x-data components can nest, creating a scope chain of parent and child objects. A child scope can read a parent’s properties but should write to its own, reserving a mutable piece of state for each level. Scoping keeps collisions and unintended coupling under control.

<div x-data="{ saved: false }">                        <!-- parent scope -->
  <form x-data="{ email: '' }" @submit="saved = true">  <!-- child reads parent -->
    <input x-model="email">
    <button type="submit">Save</button>
  </form>
  <p x-show="saved">Saved. Child scopes can see parent properties.</p>
</div>

The inner form adds its own email property while still reading and writing saved from the parent, because an expression resolves up the scope chain until it finds a property.

This scope chain is one of Alpine’s most used features — it is how a list of items and each item’s own state (such as an open menu) live together on one page.

2.3 Getters and methods

Shows how to add computed values and functions to the x-data object. Getters produce derived values that update when their dependencies change, while methods execute in expressions and event handlers. Moving logic into named methods keeps directives short and makes behaviour reusable across the component.

<div x-data="{
  items: [3, 7, 9],
  total() {
    return this.items.reduce((sum, n) => sum + n, 0);
  },
  label: 'Total',
  summary() {
    return this.label + ': ' + this.total();
  }
}">
  <p x-text="summary()"></p>                    <!-- prints "Total: 19" -->
</div>

Functions defined in state act like methods: this refers to the component, so total() and summary() are called from directives just like any other helper.

Because x-data is plain JavaScript, everything you already know — array methods, destructuring, ternaries — works inside it. Reach for a method once an expression grows longer than one line.

2.4 Reusable components with Alpine.data

Introduces Alpine.data as the mechanism for defining a named, reusable data factory. You register a function under a name and instantiate it with x-data, and each instance receives its own fresh state. One definition can therefore power many independent widgets on the same page.

<script>
  document.addEventListener('alpine:init', () => {   // fires once, before components boot
    Alpine.data('counter', () => ({
      count: 0,
      inc() { this.count++; },
      dec() { this.count--; },
    }));
  });
</script>

<div x-data="counter">                             <!-- a fresh instance -->
  <button @click="dec()">-</button>
  <span x-text="count"></span>
  <button @click="inc()">+</button>
</div>

Alpine.data registers the counter factory on the alpine:init event, and x-data="counter" instantiates it with a fresh state object — two counters on the page never share state.

3 · Core Directives

3.1 Conditionals: x-show and x-if3.2 Loops with x-for and :key3.3 Binding attributes with x-bind3.4 Events, text and HTML with x-on, x-text, x-html3.5 Two-way binding with x-model and its modifiers

Covers the core directives that express almost any UI behaviour: conditionals, loops, attribute binding, events, text binding, and two-way form binding. Each directive is a small declarative tool, and most interactions combine a few of them together. Mastering this chapter gives you a complete toolkit for day-to-day markup.

Directives are Alpine’s verbs. They share one shape — x-directive:modifier="expression" — and they all react to state changes. This chapter works through them one by one, from the commonest to the most specialised.

3.1 Conditionals: x-show and x-if

Explains the difference between x-show and x-if for conditional rendering. x-show toggles the display style and leaves the element permanently in the DOM, which is fast for frequent toggling, while x-if destroys and recreates the subtree and must live on a template tag. Choose based on whether the element’s presence matters.

<div x-data="{ open: false }">
  <button @click="open = !open">Menu</button>
  <nav x-show="open" x-transition>        <!-- fade + slide while toggling -->
    <a href="#">Home</a>
    <a href="#">About</a>
  </nav>
</div>

x-show flips between display:none and the element’s natural display, so the nav keeps its state and layout; x-transition adds a smooth fade and slide.

<div x-data="{ loading: true, posts: [] }">
  <template x-if="loading">                     <!-- branch disappears when false -->
    <p>Loading posts…</p>
  </template>
  <template x-if="!loading && posts.length === 0">
    <p>No posts yet.</p>
  </template>
  <template x-if="posts.length > 0">
    <ul><template x-for="p in posts" :key="p.id"><li x-text="p.title"></li></template></ul>
  </template>
</div>

x-if must wrap its content in a template tag and fully removes or inserts the subtree, which is right for expensive branches that should not exist until needed.

3.2 Loops with x-for and :key

Shows how to iterate over arrays and objects with x-for, binding a stable key through the :key attribute. Keys let Alpine track which items moved, were added, or were removed, so the DOM updates efficiently and correctly. Without a stable key, reordering rows can produce wrong data binding.

<div x-data="{
  todos: [
    { id: 1, text: 'Write the guide' },
    { id: 2, text: 'Escape angle brackets' }
  ]
}">
  <ul>
    <template x-for="todo in todos" :key="todo.id">
      <li x-text="todo.text"></li>
    </template>
  </ul>
</div>

x-for also lives on a template element; :key binds a unique identifier per item so Alpine patches lists correctly when items are reordered.

Bind a key whenever your list items can change order or identity. A static list works without one, but the habit keeps lists predictable when they grow.

3.3 Binding attributes with x-bind

Covers x-bind and its : shorthand for setting attributes, classes, and styles from state. Beyond plain values, class and style accept object and array syntax, so you can toggle individual classes based on conditions. Binding keeps the DOM in sync without imperative DOM manipulation.

<div x-data="{ disabled: true, theme: 'dark', id: 7 }">
  <button :disabled="disabled">Save</button>
  <img :src="'photos/' + id + '.jpg'" alt="Preview">
  <div :class="{ 'bg-black': theme === 'dark', 'bg-white': theme !== 'dark' }">...</div>
  <div :style="{ color: theme === 'dark' ? 'white' : 'black' }">Themed text</div>
</div>

:src builds an attribute from an expression, while :class and :style accept object syntax where each key applies only when its boolean value is true.

A bare disabled="..." attribute is always treated as present and truthy in HTML. Bind it as :disabled="false" to actually remove it from the element.

3.4 Events, text and HTML with x-on, x-text, x-html

Explains x-on and its @ shorthand for listening to events, with modifiers for stopping propagation, preventing default, and running once. It also contrasts x-text with x-html for filling element content: x-text always escapes its input and is the safe default, while x-html renders raw HTML and should be used rarely.

<div x-data="{ count: 0, html: '<strong>bold text</strong>' }">
  <button @click="count++">Clicked <span x-text="count"></span> time(s)</button>
  <button @mouseenter.once="count = 0">Reset (only on first hover)</button>
  <p x-text="count"></p>            <!-- text is always escaped -->
  <p x-html="html"></p>             <!-- renders real HTML -->
</div>

@ handles events and modifiers like .once, while x-text writes text safely and x-html injects raw markup — use x-html only with content you control or trust.

x-html injects whatever the expression produces into the page. Never point it at user input — that is how XSS happens. Default to x-text.

3.5 Two-way binding with x-model and its modifiers

Covers x-model for two-way binding on inputs, selects, and textareas, syncing the element’s value with component state in both directions. Modifiers tune when and how values sync, such as number conversion, trimming whitespace, or lazy updates on change instead of input. Most forms are built with this single directive.

<div x-data="{ q: '', agree: false, tags: [], age: '' }">
  <input x-model="q" placeholder="Search">                 <!-- text -->
  <input type="checkbox" x-model="agree">                  <!-- boolean -->
  <select x-model="tags" multiple>                          <!-- multi-select array -->
    <option>html</option><option>css</option><option>js</option>
  </select>
  <input x-model.number="age">                             <!-- coerces to a number -->
  <input x-model.lazy="q">                                 <!-- syncs on change, not input -->
  <input x-model.debounce.300ms="q">                       <!-- waits 300ms of quiet -->
</div>

x-model reads the element type — text, checkbox, select, radio — and writes the matching kind of value, while .number, .lazy and .debounce adjust coercion and sync timing.

4 · Reactivity & Watchers

4.1 Reacting with x-effect4.2 Watching state with $watch and $nextTick4.3 Reactivity caveats: mutating vs replacing4.4 Skipping work with x-ignore

Explains the automatic reactivity engine that powers the whole framework. When state referenced inside directives or effects changes, Alpine re-runs the affected parts of the page automatically. The chapter teaches you to declare effects, watch specific properties, and avoid the small set of caveats that catch newcomers.

Reactivity is the property that makes directives fire automatically when state changes. Alpine 3 implements it with JavaScript Proxies: when a directive reads a property, Alpine notes the dependency; when that property later changes, only the affected directives re-run.

4.1 Reacting with x-effect

Introduces x-effect for registering a side effect that runs whenever any of its dependencies change. The directive evaluates its expression once immediately on boot, then re-runs it each time a referenced property updates. It is the foundation for anything that must react without a button or event.

<div x-data="{ count: 0 }" x-effect="console.log('count is now', count)">
  <button @click="count++">Increment</button>
</div>

<!-- console output on load:  count is now 0 -->
<!-- then after clicks:       count is now 1, 2, 3, ... -->

x-effect records count as a dependency during its first run and re-executes only when that property changes — a tiny, declarative version of an observer.

4.2 Watching state with $watch and $nextTick

Shows how to react to a single property changing using the $watch magic, and how to coordinate with the DOM using $nextTick. $watch fires a callback whenever the chosen expression changes, while $nextTick runs code after Alpine has applied the latest DOM update. Together they give you precise control over timing.

<div x-data="{
  query: '',
  menuOpen: false,
  init() {
    this.$watch('query', (value) => console.log('search:', value));
  },
  focus() {
    this.menuOpen = true;
    this.$nextTick(() => this.$refs.input.focus());  // wait for the DOM to update
  }
}">
  <input x-model="query" x-ref="input">
  <button @click="focus()">Edit</button>
</div>

$watch subscribes to one property and hands you its new value, while $nextTick defers a callback until Alpine has applied the pending DOM changes.

4.3 Reactivity caveats: mutating vs replacing

Explains the one case where reactivity is not automatic: mutating arrays and objects in place is not always tracked. The safe pattern is to replace the value with a fresh reference, assigning a new array or object instead of pushing or modifying properties. This simple habit prevents the majority of stale-UI bugs.

<div x-data="{
  user: { name: 'Ada', hits: 0 },
  items: [1, 2, 3]
}">
  <p x-text="user.hits"></p>

  <!-- Replace with a new object (spread keeps it immutable and obvious) -->
  <button @click="user = { ...user, hits: user.hits + 1 }">Increment hit</button>

  <!-- Reassign the array with a new array each time -->
  <button @click="items = [...items, 4]">Append 4</button>

  <!-- Filter into a fresh array to remove items reactively -->
  <button @click="items = items.filter(n => n !== 4)">Remove 4s</button>
</div>

Replacing the object or array with a fresh reference is the pattern Alpine documents for certainty: every directive that read the property re-evaluates against the new value.

Alpine 3's Proxy also makes adding a brand-new property later fully reactive — a real upgrade over Alpine 2. The remaining caveat is timing: assign the whole new reference when you want a change to be unmistakable, and reach for $nextTick when code must run after the DOM reflects state.

4.4 Skipping work with x-ignore

Shows x-ignore, which tells Alpine to skip a whole subtree and never initialise or re-render the components inside it. Use it around third-party embeds and any pre-rendered content that must be left untouched. The ignored region stays exactly as the server wrote it.

<div x-data>
  <!-- Everything between the x-ignore markers stays untouched by Alpine -->
  <div x-ignore>
    <!-- A widget injected by a third-party script that manages its own DOM -->
    <div id="chat-embed">...</div>
  </div>

  <p x-text="new Date().toLocaleTimeString()"></p>  <!-- still reactive -->
</div>

x-ignore stops Alpine from initialising or re-rendering anything inside the element, protecting third-party widgets that would otherwise fight Alpine’s updates.

5 · Magics, DOM Access & Lifecycle

5.1 Meet the magics: $el, $root and $data5.2 Grabbing elements with $refs and x-ref5.3 Talking upwards with $dispatch5.4 Running code at boot with x-init5.5 Hiding the pre-javascript flash with x-cloak

Covers the $ magics that reach outside the component into the browser, along with the setup attributes that tie components together. Magics expose the current element, the root, raw data, refs, events, timing, and the store, while x-init, x-cloak, and x-ref wire up lifecycle and structure. Together they handle almost every escape hatch you need.

Magics are properties prefixed with $ that Alpine exposes inside expressions, such as $refs or $nextTick. They are the bridge between your declarative state and the imperative browser around you.

5.1 Meet the magics: $el, $root and $data

Introduces the main introspection magics: $el points at the current element, $root at the outermost component element, and $data at the raw state object. These are invaluable for inspecting values during development and for the occasional imperative tweak. Reading them never creates a new dependency, so using them in expressions is always safe.

<div x-data="{ name: 'Alpine' }" data-id="root-1">
  <!-- $el is the element the expression lives on -->
  <p x-text="$el.tagName + ' (my tag)'"></p>
  <!-- $root is the nearest x-data element -->
  <p x-text="$root.dataset.id"></p>
  <!-- $data is the raw component state -->
  <pre x-text="JSON.stringify($data, null, 2)"></pre>
</div>

$el, $root and $data give expressions a mirror of the live DOM and state around them, handy for logging, measuring or reading arbitrary attributes.

5.2 Grabbing elements with $refs and x-ref

Shows how to name elements with x-ref and then reach them from anywhere in the same component using $refs. This is the reliable way to focus an input or measure a node’s dimensions when directives alone are not enough. The ref lookup is scoped to the current component’s subtree.

<div x-data="{
  open: false,
  focusNote() {
    this.open = true;
    this.$nextTick(() => this.$refs.note.focus());
  }
}">
  <textarea x-show="open" x-ref="note"></textarea>
  <button @click="focusNote()">Write a note</button>
</div>

x-ref tags the textarea with the name note, and $refs.note returns it after $nextTick guarantees the element is visible and laid out.

5.3 Talking upwards with $dispatch

Explains how to communicate upwards using custom events created with $dispatch. The method fires an event on the current element, parents listen with the x-on shorthand such as @name, and the payload arrives in $event.detail. It is the Alpine-native alternative to calling parent methods directly.

<div x-data="{ total: 0 }" @add-to-cart="total += $event.detail.qty">
  <p x-text="'Cart: ' + total"></p>
  <button @click="$dispatch('add-to-cart', { qty: 2 })">Add 2</button>
</div>

<!-- The event bubbles to the window by default, so siblings can listen too:
<script>
  window.addEventListener('add-to-cart', (e) => console.log(e.detail.qty));
</script> -->

$dispatch fires a custom DOM event carrying a payload; the parent picks it up with @add-to-cart and reads $event.detail, and bubbling lets unrelated code listen on window.

5.4 Running code at boot with x-init

Shows the two ways to run code when a component boots: the x-init attribute and the init() method inside the data object. The chapter covers the boot order and when the DOM is considered ready so initialisation can safely measure or query elements. Knowing this timing prevents the classic cannot-read-document errors on load.

<div x-data="{
  posts: [],
  init() {                     // runs once, before children initialise
    this.posts = ['first'];
  }
}">
  <p x-text="'Loaded ' + posts.length + ' post(s)'"></p>
</div>

<!-- Equivalent single-expression form for small components -->
<div x-data="{ ready: false }" x-init="ready = true">...</div>

An init() method on the state object runs once when the component boots, and x-init is the attribute shortcut; both run before child components, so $nextTick is how you wait for the whole DOM.

5.5 Hiding the pre-javascript flash with x-cloak

Covers x-cloak, the standard guard against a visible flash of uninitialised markup before Alpine loads. Combined with one CSS rule that hides any element carrying the attribute until Alpine removes it, the fix costs a single attribute and a few lines of style. It is an essential polish for any public page.

<div x-data="{ open: false }" x-cloak>
  <button @click="open = !open">Toggle</button>
  <p x-show="open">This content never flashes before Alpine boots.</p>
</div>

<!-- Add this one rule to your own stylesheet, not inside the page: -->
/* [x-cloak] { display: none; } */

x-cloak hides the element until Alpine initialises it and removes the attribute, so users never see raw, unreacted markup during the script-load window.

6 · Data Fetching & Async

6.1 One-line JSON with $fetch6.2 Loading, success and error states6.3 Submitting forms with x-model and fetch6.4 Composing requests against JSON APIs

Teaches everything needed to talk to a backend from Alpine components. It introduces $fetch for one-line JSON reads, async initialisers for work at load time, a repeated three-phase pattern for loading and error states, and full form submission without a page refresh. The chapter keeps network requests explicit and readable.

Alpine components often need live data — search results, comments, dashboards. Alpine gives you async/await everywhere, and the $fetch magic removes the ceremony around reading JSON.

6.1 One-line JSON with $fetch

Introduces $fetch, a thin convenience wrapper around the native fetch API that resolves to parsed JSON. It turns the usual fetch boilerplate into a single expression you can assign directly to state. For anything beyond a simple JSON read, the plain fetch API remains available.

<div x-data="{
  posts: [],
  async init() {
    this.posts = await $fetch('/api/posts');   // fetch + .json() in one call
  }
}">
  <template x-for="post in posts" :key="post.id">
    <article>
      <h2 x-text="post.title"></h2>
      <p x-text="post.body"></p>
    </article>
  </template>
</div>

$fetch('/api/posts') replaces the usual fetch().then(r => r.json()) pair, so the init method resolves directly to the array of posts.

6.2 Loading, success and error states

Shows the three-phase async pattern used every time you load remote data: a loading flag that drives an indicator, a results slot for the success case, and an error branch for failures. You set the flag before the request and flip it in the then and catch handlers. Reaching for this shape consistently keeps every request understandable.

<div x-data="{
  posts: [],
  loading: true,
  error: null,
  async load() {
    try {
      this.posts = await $fetch('/api/posts');
    } catch (err) {
      this.error = 'Could not load posts';
    } finally {
      this.loading = false;
    }
  }
}" x-init="load()">
  <p x-show="loading">Loading…</p>
  <p x-show="error" x-text="error"></p>
  <ul x-show="!loading && !error">
    <template x-for="post in posts" :key="post.id">
      <li x-text="post.title"></li>
    </template>
  </ul>
</div>

load() runs from x-init, and the finally block clears the spinner whether the call succeeded or failed, leaving error to choose the message shown.

6.3 Submitting forms with x-model and fetch

Builds a form whose field values live in component state through x-model and are submitted with an Alpine fetch call. The @submit.prevent modifier blocks the browser’s default page reload and lets your handler take over. The response is then written back into the page with standard binding.

<form x-data="{
  data: { name: '', email: '' },
  sent: false,
  async submit() {
    const res = await fetch('/api/contact', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(this.data)
    });
    if (res.ok) this.sent = true;
  }
}" @submit.prevent="submit()">
  <input x-model="data.name" placeholder="Name">
  <input type="email" x-model="data.email" placeholder="Email">
  <button type="submit">Send</button>
  <p x-show="sent">Thanks — we will reply shortly.</p>
</form>

The form’s inputs live in the reactive data object, and @submit.prevent stops the native reload so submit() can send JSON and flip the sent flag on success.

6.4 Composing requests against JSON APIs

Covers composing requests against JSON APIs, including running parallel calls with Promise.all and caching fetched results in component state. $fetch is a shortcut, and the plain fetch API is always there when you need headers, methods, or custom handling. This section shows how to stay in control of the network layer.

<div x-data="{
  stats: { users: 0, posts: 0 },
  async init() {
    const [users, posts] = await Promise.all([
      $fetch('/api/stats/users'),
      $fetch('/api/stats/posts')
    ]);
    this.stats = { users, posts };
  }
}">
  <p>Users: <span x-text="stats.users"></span></p>
  <p>Posts: <span x-text="stats.posts"></span></p>
</div>

Promise.all runs both requests concurrently, and the whole batch is reassigned to stats at once so the two figures render together.

When you need headers, credentials, aborting or error status codes, fall back to the native fetch() call — $fetch stays a convenience layer, not a replacement for fetch.

7 · Stores, Components & Communication

7.1 Global state with Alpine.store7.2 Reusable components with Alpine.data7.3 Communicating between components with events7.4 Cross-component state and persistence

Moves from isolated components to a whole application: global stores for shared state, reusable Alpine.data factories for repeated widgets, and event-driven communication that connects them. It also covers persisting that state across reloads. The result is a repeatable architecture rather than a pile of independent pieces.

Single components are fine for a widget, but real pages have a header, a cart, a search box and a footer that must stay in sync. This chapter introduces the two Alpine primitives that make shared state and reuse painless.

7.1 Global state with Alpine.store

Introduces Alpine.store for global state shared by every component on the page. You register a store once and any component reads and writes it through the $store magic, giving you cross-component data without prop drilling or long event chains. Stores stay reactive, so updates re-render every component that observes them.

<script>
  document.addEventListener('alpine:init', () => {
    Alpine.store('cart', {
      items: [],
      total() { return this.items.reduce((s, i) => s + i.price, 0); },
      add(item) { this.items.push(item); }
    });
  });
</script>

<!-- Header reads the store -->
<p x-text="'Items: ' + $store.cart.items.length"></p>

<!-- Any component writes to it -->
<button @click="$store.cart.add({ name: 'Guide', price: 19 })">Buy the guide</button>

Alpine.store creates a global reactive singleton; $store.cart works in every component on the page, and its methods and total are reactive just like local state.

7.2 Reusable components with Alpine.data

Deepens the Alpine.data pattern introduced in chapter 2, covering parameters, scope isolation, and organising factories across the codebase. Treating each factory as a tiny class for one UI widget keeps definitions small and reusable. Parameters let the same factory be configured differently at each usage site.

<script>
  document.addEventListener('alpine:init', () => {
    Alpine.data('dropdown', (label = 'Menu') => ({
      label,
      open: false,
      toggle() { this.open = !this.open; },
      close() { this.open = false; }
    }));
  });
</script>

<div x-data="dropdown('Options')">
  <button @click="toggle()" x-text="label"></button>
  <ul x-show="open" @click.outside="close()">
    <li><a href="#">Edit</a></li>
    <li><a href="#">Delete</a></li>
  </ul>
</div>

The dropdown factory accepts a label parameter and returns fresh state per instance, and @click.outside closes the menu when the user clicks anywhere else.

7.3 Communicating between components with events

Shows the event pattern for communicating between nested and sibling components. Components bubble custom events upwards with $dispatch, parents listen with the @ shorthand, and the payload is read from $event.detail. For components that share no ancestor relationship, window-level listeners provide loose coupling.

<div x-data="{ cart: 0 }" @bought="cart += $event.detail.qty">
  <p x-text="'Cart total: ' + cart"></p>

  <div x-data>                                  <!-- an unrelated subtree -->
    <button @click="$dispatch('bought', { qty: 1 })">Buy one</button>
  </div>
</div>

<!-- Loose coupling to anything on the page:
<script>
  window.addEventListener('bought', (e) => console.log(e.detail.qty));
</script> -->

The inner button dispatches a bought event that bubbles up to the parent’s @bought listener, and window-level listeners let entirely separate components collaborate.

7.4 Cross-component state and persistence

Combines Alpine.store and Alpine.data components into a single coherent pattern, then adds the persist plugin so shared state survives page reloads. The store remains the single source of truth while components act as the visual faces over it. Reloading the page restores saved values instantly.

<!-- Start from store registered in 7.1: Alpine.store('cart', { count: 0 }) -->
<p x-data x-text="'Count in store: ' + $store.cart.count"></p>
<button x-data @click="$store.cart.count++">Increment global count</button>

<!-- Persist a component property across reloads (needs the persist plugin) -->
<div x-data="{ theme: Alpine.$persist('light') }">
  <select x-model="theme">
    <option value="light">Light</option>
    <option value="dark">Dark</option>
  </select>
</div>

Every component reads and writes the same reactive store, while Alpine.$persist keeps the theme in localStorage so the choice survives a page reload.

8 · The Plugin Fleet

Covers the eight official plugins: mask, persist, collapse, focus, intersect, resize, sort, and anchor. Each adds either a directive or a helper, and the chapter explains how to register them and when each earns its place. Loading plugins independently keeps the core lean.

Plugins extend Alpine with new directives and magics. Each ships as its own script loaded after the core script, and each is entirely optional. This chapter is the tour.

8.1 Registering the plugin fleet

Shows the CDN registration pattern shared by all eight plugins: one additional defer script tag per plugin, loaded after Alpine itself. You register only the plugins you actually use rather than pulling the whole fleet, which keeps the page lean. The same pattern works regardless of which plugin you add.

PluginAddsCDN package

Loading a plugin’s CDN script after the core script registers its directives and magics automatically, so you only load what a page actually uses.

8.2 Entering formatted input with mask

Shows x-mask for formatting input as the user types, supporting fixed patterns such as phone numbers and dynamic masks such as money values. The stored value stays plain while the display is formatted, so the backend still receives raw digits or numbers. Masking reduces validation errors without altering your data.

<form x-data>
  <!-- Fixed pattern: parens, space and dash are inserted as you type -->
  <input x-mask="(99) 999-9999" placeholder="(555) 123-4567">

  <!-- Dynamic mask: changes shape based on what you type -->
  <input x-mask:dynamic="$money($input, ',', 2)" placeholder="0,00">
</form>

Static masks force a fixed pattern, while x-mask:dynamic re-selects the mask as input grows and the $money helper formats a currency value live.

8.3 Remembering state with persist

Covers the persist plugin’s Alpine.$persist helper for backing a property with localStorage. A single function call makes a property survive page reloads, with options for custom keys and for persisting whole objects. Restoring happens automatically so state feels continuous across sessions.

<div x-data="{
  count: Alpine.$persist(0),
  prefs: Alpine.$persist({ theme: 'light' })
}">
  <button @click="count++">Visits: <span x-text="count"></span></button>
  <select x-model="prefs.theme">
    <option value="light">Light</option>
    <option value="dark">Dark</option>
  </select>
</div>

<!-- Custom storage key, so the value does not collide with another -->
<div x-data="{ colour: Alpine.$persist('blue').as('preferred-colour') }">
  <input type="color" x-model="colour">
</div>

Alpine.$persist wraps a property so every change writes to localStorage and every page load restores the saved value; .as('key') customises the storage slot.

8.4 Animating and trapping with collapse and focus

Pairs x-collapse, which animates height smoothly when an element is shown or hidden, with x-trap, which captures keyboard focus inside a modal or menu. The combination makes accessible expandable panels and dialogs straightforward to build. Both react to the element’s current state rather than fighting it.

<div x-data="{ expanded: false }">
  <button @click="expanded = !expanded">Toggle</button>
  <div x-show="expanded" x-collapse>
    <p>This panel animates open and closed; x-collapse measures the height for you.</p>
  </div>
</div>

<div x-data="{ open: false }">
  <button @click="open = true">Open dialog</button>
  <div x-show="open" x-trap="open" role="dialog" aria-modal="true">
    <input placeholder="Tab stays inside the dialog">
    <button @click="open = false">Close</button>
  </div>
</div>

x-collapse animates the height transition for you, while x-trap locks keyboard focus inside the dialog until open is false again — modal accessibility in two attributes.

8.5 Intersect, resize, sort and anchor

Covers the remaining four plugins. x-intersect fires when an element scrolls into view, x-resize watches an element’s size, x-sort enables drag-and-drop reordering of a list, and x-anchor positions a floating element relative to its trigger. Each handles a common interactive need that would otherwise become custom JavaScript.

<!-- intersect: run once when an element scrolls into view -->
<div x-data="{ seen: false }"
     x-intersect.once="seen = true"
     x-text="seen ? 'Now visible' : 'Scroll down'">
</div>

<!-- resize: react when the element's size changes -->
<div x-data="{ w: 0 }" x-resize="w = $event.detail.width" x-text="w + 'px wide'"></div>

<!-- sort: drag-and-drop reordering of a list -->
<ul x-data="{ todos: ['a', 'b', 'c'] }" x-sort:group="todos">
  <template x-for="t in todos" :key="t">
    <li x-sort:item x-text="t"></li>
  </template>
</ul>

<!-- anchor: keep a popover pinned to its button -->
<div x-data="{ open: false }">
  <button @click="open = !open" x-ref="trigger">Actions</button>
  <div x-show="open" x-anchor="$refs.trigger">A positioned popover</div>
</div>

Each plugin contributes one focused capability: intersect for scroll reveals, resize for layout-dependent UI, sort for drag reordering, and anchor for popover placement.

9 · Alpine in Server-Rendered Apps

9.1 Progressive enhancement in Laravel Blade9.2 The same trick in Django and Rails9.3 CSRF-safe POST and PUT with the right headers9.4 Avoiding hydration conflicts and staying fast

Shows how Alpine extends pages that a backend already rendered, whether Laravel Blade, Django, or Rails. The chapter covers progressive enhancement, carrying CSRF tokens into fetch calls, and avoiding hydration conflicts. The goal is interactivity layered on server markup without turning the stack into a single-page application.

Alpine’s sweet spot is server-rendered apps. The backend builds the HTML; Alpine sprinkles behaviour onto it. That division of labour respects the islands architecture and keeps first paint fast.

9.1 Progressive enhancement in Laravel Blade

Shows a Blade nav component that works as a plain menu before Alpine loads and gains toggle behaviour the moment it boots. Because the link markup is always present, the content stays crawlable and usable without JavaScript. Alpine only wires the enhancement over what the server already outputs.

{{-- resources/views/components/nav.blade.php --}}
<nav x-data="{ open: false }">
  <button @click="open = !open" aria-expanded="false">Menu</button>
  <ul x-show="open" @click.outside="open = false">
    <li><a href="{{ route('home') }}">Home</a></li>
    <li><a href="{{ route('posts.index') }}">Posts</a></li>
  </ul>
</nav>

{{-- layouts/app.blade.php — load Alpine once, in the head --}}
<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js"></script>

Blade renders the menu links server-side and Alpine adds the toggle; a default closed state keeps the page orderly even if JavaScript never loads.

9.2 The same trick in Django and Rails

Repeats the progressive-enhancement pattern with Django template tags and a Rails helper. The idiom is identical in every framework: the server renders the full markup and Alpine adds behaviour on top. Knowing this shape once lets you apply it anywhere.

{# Django template #}
<div x-data="{ q: '' }">
  <input x-model="q" placeholder="Filter posts">
  <ul>
    {% for post in posts %}
      <li x-show="!q || '{{ post.title|lower }}'.includes(q.toLowerCase())">
        {{ post.title }}
      </li>
    {% endfor %}
  </ul>
</div>

<!-- Rails — the same Alpine, served by an ERB helper in the layout -->
<%= javascript_include_tag "https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js", defer: true %>

The Django filter box embeds each server-rendered title into an Alpine expression, and the Rails helper adds the same Alpine script to every page.

9.3 CSRF-safe POST and PUT with the right headers

Shows how to carry the CSRF token from your server-rendered template into Alpine fetch calls. Because every modern framework double-submits the token, you must match its exact shape and expected header name. A small inline value or data attribute supplies the token to your request headers.

{{-- Laravel: publish a token your JavaScript can read --}}
<meta name="csrf-token" content="{{ csrf_token() }}">

<form x-data="{
  body: '',
  async submit() {
    const res = await fetch('/comments', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-CSRF-TOKEN': document.querySelector('meta[name=csrf-token]').content
      },
      body: JSON.stringify({ body: this.body })
    });
    if (res.ok) this.$root.reset();
  }
}" @submit.prevent="submit()">
  <textarea x-model="body"></textarea>
  <button>Post comment</button>
</form>

<!-- Django reads the token from the csrftoken cookie instead of a meta tag:
// headers: { 'X-CSRFToken': getCookie('csrftoken') } -->

The server’s CSRF token travels from Blade into a meta tag, and Alpine’s fetch sends it back in the X-CSRF-TOKEN header so the request passes the middleware.

9.4 Avoiding hydration conflicts and staying fast

Lists the gotchas that appear when Alpine meets server markup, such as duplicate element ids, re-rendered third-party embeds, and oversized x-data objects. The fixes are cheap once known: namespace ids, wrap embeds in x-ignore, and keep data factories small. Avoiding these upfront keeps server-rendered pages fast.

  • No duplicate ids. Alpine does not virtualise the DOM; a repeated id confuses getElementById and your CSS selectors.
  • Let the server render once. If the backend already printed a list, do not also loop it with x-for — pick one source of truth.
  • Isolate third-party widgets with x-ignore so their scripts do not fight Alpine’s DOM updates.
  • Keep islands small. A page with fifty small x-data islands is fine; one island holding thousands of rows is not.
  • Load Alpine with defer and stream the HTML first — first paint stays server-fast.
<div x-data="{ expanded: false }">
  <button @click="expanded = !expanded" aria-expanded="false">
    Reveal the server-printed body
  </button>
  <p x-show="expanded">{{ $post->body }}</p>   <!-- the server already printed the body -->
</div>

The server owns the markup and Alpine only wires one toggle per element — no x-for, no duplicate render, and the fully rendered HTML arrives before any JavaScript runs.

10.1 Keeping state small and readable

Shows the refactoring pattern for oversized x-data objects: split definitions into named Alpine.data factories, extract small methods, and keep the remaining state obvious. Complexity hides in unusable one-line objects filled with co-opted expression logic. Readable state makes every later change safer.

<!-- Messy: one giant object with duplicated logic -->
<div x-data="{ a: 0, b: 0, total() { return this.a + this.b; }, ... }">...</div>

<!-- Clean: a named component that reads like a class -->
<div x-data="calculator">
  <input type="number" x-model.number="a">
  <input type="number" x-model.number="b">

</div>

<script>

    Alpine.data('calculator', () => ({
      a: 0, b: 0,
      total() { return this.a + this.b; }
    }));
  });
</script>

Extracting the same logic into Alpine.data keeps the markup declarative and the behaviour testable, which is exactly where maintainability comes from.

10.2 Accessibility and flash prevention

Covers the accessibility defaults to bake in from the start: aria-expanded and aria-controls on toggles, sensible focus behaviour for menus and dialogs, and full keyboard support. It also stresses x-cloak so nobody sees unstyled pre-boot markup. Small consistent choices cover most audit requirements.

<div x-data="{ open: false }" x-cloak>
  <button
    @click="open = !open"
    :aria-expanded="open"
    aria-controls="menu"
    id="menu-btn"
  >Menu</button>

  <ul id="menu" role="menu"

  </ul>
</div>

10.3 Debugging Alpine components

Shows the fastest debugging loop for a stale or silent component. Temporary x-effect logging surfaces what changes, the $watch magic traces a single property, and the Alpine DevTools extension inspects live state and the DOM. When a directive silently ignores you, check scope first, then how your expressions were written.

<!-- Tune in to the component's state changes -->
<div x-data="{ count: 0 }" x-effect="console.log({ count })">...</div>

<!-- Watch a specific property from init -->

  q: '',

</div>

<!-- In the browser devtools -->
// typeof Alpine    →  "object" means the CDN script loaded
// Alpine.store('cart')   prints a store you registered
// x-text showing nothing usually means a misspelled property name

10.4 Testing Alpine with Playwright and Cypress

Shows end-to-end tests using Playwright or Cypress that drive a real browser against your components. Because Alpine lives in the DOM, browser automation is the natural test harness rather than unit-level mocks. Tests click, type, and assert on visible markup exactly as a user would.

// Playwright test — menu opens on click and closes on Escape
await page.goto('/');
await page.getByRole('button', { name: 'Menu' }).click();
await expect(page.getByRole('menu')).toBeVisible();

// Cypress test — counter increments after each click
cy.visit('/');
cy.contains('button', '+1').click();
cy.contains('p', 'Count: 1').should('be.visible');
cy.contains('button', '+1').click();
cy.contains('p', 'Count: 2').should('be.visible');

Both tools click real DOM nodes and assert on real rendered text, which is exactly what matters for interactivity built from attributes rather than a framework API.

For remote data, wait for the network response — page.waitForResponse in Playwright or cy.intercept in Cypress — so assertions run after your Alpine fetch settles, not before.

10.5 Growing out of Alpine: Vue and Svelte

Gives an honest exit strategy for when a project outgrows Alpine. It lists the warning signs, such as deeply nested cross-component state or heavy custom plumbing, and recommends the successor with the smallest behavioural jump. Because Alpine markup already reads almost like Vue templates, Vue is often the cleanest step.

Signal to growWhat it looks like
Shared data everywhereYou lean on $store plus events for logic that wants a state library
Deep component treesTwenty nested x-data scopes instead of composed components
Heavy client renderingMost of the page now renders from state rather than from the server
A team of manyMarkup-in-attributes stops scaling past two or three developers

Vue is the gentlest climb: directives like v-if, v-for and v-model map almost one-to-one onto Alpine’s x-*. Svelte fits if you value reactivity by assignment and compile-time size. Either way, the components you wrote in chapters 1–8 carry over as mental models.

A.4 Glossary

Defines the vocabulary used through the guide in one place, from directives and magics to stores and plugins. Skim it before asking how to express an idea, because the term you are looking for usually sits here. Entries are short and cross-referenced.

  • Component — one x-data element plus everything its value scopes over.
  • Directive — an x- attribute that attaches behaviour, such as x-show or x-for.
  • Magic — a $ property available in expressions, like $refs or $nextTick.
  • State — the reactive object declared by x-data that directives read and write.
  • Reactivity — the mechanism that re-runs a directive when a property it read changes.
  • Scope — the set of properties available to expressions, chained up through nested x-data.
  • Store — global reactive state shared across components via Alpine.store.
  • Plugin — a separate script that adds directives or magics to Alpine.
  • Islands architecture — server-rendered HTML with small interactive regions around it.
  • Progressive enhancement — behaviour layered on markup that works without JavaScript.
  • Hydration conflict — a fight between server markup and client re-rendering, avoided with x-ignore.
