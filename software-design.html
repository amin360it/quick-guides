This section fixes the boundaries of the guide, states the argument it makes — that design patterns are a vocabulary for decisions you have already reasoned about, not a catalogue to be applied — and supplies the notation, the metrics and the reading order used by the six chapters that follow. It also explains precisely which topics are excluded and why, and maps every sample onto the eight implementation languages used throughout so that a reader can substitute their own stack without losing the argument.

0.1 Scope, method, and what this guide is not

Defines the design vocabulary this guide covers, and the five adjacent subjects it deliberately excludes.

The subject is software design at the unit-of-behaviour level: how a single deployable artifact’s internals are decomposed, how responsibilities are distributed across types, and how those decompositions are allowed to change over the life of a codebase. In scope are decision-making principles (the SOLID family and their critics), structural vocabularies (the 23 GoF patterns plus the modern patterns that superseded several of them), functional idioms that have escaped their functional-language origins, and the refactoring mechanics that connect all three. Out of scope are four adjacent subjects that are frequently conflated with design and that this guide treats only as a boundary: distributed-systems design, concurrency and parallelism, framework-specific API usage, and general language tutorial material.

The method is deliberately narrow. Every pattern in this guide is presented in a fixed five-part shape — intent (the problem in one sentence), participants (the roles and their cardinalities), mechanics (the runtime dispatch and allocation behaviour), 2026 applicability (whether the pattern still earns its complexity in contemporary toolchains), and modern equivalent (what a language’s own feature now supplies). The fifth part is the one most catalogues omit and the one that matters most to an engineer choosing today: several patterns in the 1994 catalogue have been absorbed into language or runtime features and should now be recognised rather than reimplemented.

// A design decision is only real when it is expressed as a type boundary.
// C# 14 / .NET 10 — the seam is the *sealed record* plus the accepting
// interface, not the implementation detail behind either of them.

public sealed record Money(decimal Amount, string Currency)
{
    public static Money Zero(string currency) => new(0m, currency);

    public Money Add(Money other)
    {
        if (!string.Equals(Currency, other.Currency, StringComparison.Ordinal))
            throw new CurrencyMismatchException(Currency, other.Currency);

        return this with { Amount = Amount + other.Amount };
    }
}

// Policy accepts Money (a value). Mechanism accepts the interface.
// Neither side knows about the other's concrete type. See 1.5.
public interface IExchangeRateFeed
{
    ValueTask<Rate> RateForAsync(string from, string to, CancellationToken ct);
}

The Go translation of the same seam changes nothing structural. The value type becomes a comparable struct, the record’s with becomes a constructor call, and the interface becomes a one-method interface — the same object graph, three fewer allocations per operation.

    }

    RateFor(ctx context.Context, from, to Currency) (Rate, error)
}

type Rate struct {
    From, To Currency
    Mid       int64
    AsOf      time.Time
}

Scope boundary. This guide does not cover deployment topology, service boundaries, consensus, replication, message-queue topology, or capacity planning. Those subjects have their own failure modes and their own literature, and mixing them into a design-patterns argument produces the muddled hybrid that leads teams to introduce a Repository per service boundary or a Singleton for a connection pool that must be per-replica. Where a pattern’s consequences reach into distributed territory, that boundary is named explicitly and the consequence is not developed further.

Two exclusions worth stating explicitly. First, framework and API usage: this guide assumes you already know how to express an HTTP handler, a persistence query, or a component lifecycle in your chosen framework, and it does not use any framework-specific sugar to carry a design argument. Second, general language tutorial material: generics, closures and records are used as tools, and they are never explained from first principles, because the argument being made is about structure rather than syntax.

0.2 Why design knowledge is a senior-engineer differentiator

Argues that pattern knowledge matters because of change cost, not aesthetics, and quantifies that cost.

The economic argument for design discipline is not readability. It is change cost, and change cost is measurable. A module with high efferent coupling — the number of other modules it depends on — and low instability I = Ce / (Ca + Ce) must be revalidated against every dependency change; a module with high afferent coupling must be revalidated by every dependent. Robert Martin’s metrics give a cheap first-order proxy, and they are worth computing on a real codebase before any refactoring begins.

The second argument is about the size of the blast radius of a mistake. The code below is a plausible checkout service written by someone who has never read a design book. It is not stupid, and it passes review, and it is roughly 34 cyclomatic complexity points across two methods — past the point where the compiler, the IDE and the human reader all stop helping.

public sealed class CheckoutService
{
    private readonly MySqlConnection _conn;
    private readonly HttpClient _http;
    private readonly ILogger<CheckoutService> _log;
    private readonly Dictionary<string, string> _couponCache = new();
    public async Task<Order> CheckoutAsync(Cart cart, string coupon, User user)
    {
        decimal total = 0m;
        foreach (var line in cart.Lines)
        {
            if (line.Quantity <= 0) throw new ArgumentException("qty");
            if (line.Sku.StartsWith("DIGITAL-")) { total += line.UnitPrice * line.Quantity; continue; }
            var stock = await QueryAsync($"SELECT qty FROM stock WHERE sku='{line.Sku}'");
            if (stock < line.Quantity) throw new OutOfStockException(line.Sku);
            total += line.UnitPrice * line.Quantity * (1 - line.DiscountPct);
        }
        if (coupon is not null)
        {
            if (!_couponCache.TryGetValue(coupon, out var pct)) { pct = await LoadPct(coupon); _couponCache[coupon] = pct; }
            total *= 1m - decimal.Parse(pct);
        }
        if (user.Tier == "GOLD") total *= 0.95m;
        if (user.Country == "DE") total *= 1.19m;
        if (total > 500m)
            await _http.PostAsync("https://risk.internal/v1/score", Json(total, user.Id));
        if (user.Country == "BR") total = FormatBRL(total);
        return await SaveAsync(cart, user, total, coupon);
    }
}

Note what is actually wrong. It is not the if statements — branch count is not the defect. It is that one method simultaneously decides pricing policy, applies tax rules, performs inventory I/O, calls a risk service, formats currency, and writes to the database, and that none of those concerns is named anywhere except in the method’s own length. The refactoring that fixes it is not a pattern application; it is a sequence of extractions, and it is described in full in chapter 6.

// AFTER — same behaviour, five named decisions, each independently testable.
// Complexity per unit: pricing 4, tax 5, promotion 3, persistence 1.
public sealed record PricedOrder(decimal Net, decimal Tax, decimal Total);

public interface IPricingPolicy  { ValueTask<decimal> NetAsync(Cart c, CancellationToken ct); }
public interface ITaxPolicy      { ValueTask<decimal> TaxAsync(decimal net, Address ship, CancellationToken ct); }
public interface IPromotionPolicy { ValueTask<decimal> ApplyAsync(decimal net, PromotionContext ctx, CancellationToken ct); }
public interface IOrderWriter   { ValueTask<Order> WriteAsync(Cart c, CustomerSnapshot cs, PricedOrder p, CancellationToken ct); }

public sealed class CheckoutService(
    IPricingPolicy pricing,
    ITaxPolicy tax,
    IPromotionPolicy promotions,
    IOrderWriter writer,
    IRiskScorer risk)   // interface, not HttpClient: see 1.5
{
    public async Task<Order> CheckoutAsync(Cart cart, PromotionContext promo, CancellationToken ct)
    {
        var net      = await pricing.NetAsync(cart, ct);
        var discount = await promotions.ApplyAsync(net, promo, ct);   // coupon + tier
        var duty     = await tax.TaxAsync(discount, promo.ShipTo, ct);
        var total    = discount + duty;

        if (total > RiskThreshold) await risk.ScoreAsync(total, promo.CustomerId, ct);

        return await writer.WriteAsync(cart, promo.Customer, new PricedOrder(net, duty, total), ct);
    }
}

0.3 The taxonomy used here: forces, intents, mechanics

Introduces the three-axis classification — design force, pattern intent, runtime mechanic — that organises every entry in the catalogue chapters.

Pattern catalogues are conventionally sorted by intent (GoF’s three groups) or by structure. Both are useful for retrieval and useless for judgement. The taxonomy here adds a third axis — the design force the pattern is actually answering — because the same intent can be achieved by mechanisms with very different costs, and because the force is what tells you whether the pattern is still needed.

Three forces cover almost everything. Coupling force appears when two things that vary for different reasons must be composed; its patterns are Adapter, Bridge, Facade, Strategy, Observer, Mediator. Complexity-of-construction force appears when the cost of producing an object exceeds the cost of using it; its patterns are Builder, Factory Method, Abstract Factory, Prototype, Object Pool, Singleton. Variation-of-algorithm force appears when a computation’s steps are fixed but its steps' order, optionality or binding is not; its patterns are Template Method, State, Command, Iterator, Visitor. Runtime mechanics then follow mechanically: object composition, indirection through a delegate, indirection through a table, or indirection through a protocol.

0.4 The working toolkit: metrics, tooling and reading order

Specifies the measurement instruments this guide relies on — complexity, coupling, static analysis, mutation testing — and the order in which the chapters should be read.

Every quantitative claim in the following chapters is of one of three kinds, and the reader is entitled to know which: a threshold (a convention adopted by this guide, with its provenance), a measurement (a figure taken from a specific tool run against a specific shape of code), or an estimate (a reasoned projection, labelled as such). Thresholds used consistently: cyclomatic complexity above 10 warrants decomposition, above 20 warrants redesign; efferent coupling above 12 for a domain module warrants review; test suite runtime above 90 seconds for unit tests warrants splitting the build; and a unit-test pass rate above 0.5 s per test file usually indicates real I/O, not slow assertions.

The static-analysis layer is where most of these numbers come from, and the most useful of its outputs is not the violation list but the ranked list. A linter that reports 400 style violations is noise; a linter that reports the 12 files whose coupling fan-out exceeds three standard deviations is a work list.

0.5 Language neutrality and sample conventions

Proves the language-neutrality claim by rendering one design decision in five syntactically unrelated languages, and states the conventions applied to every sample.

The claim that design patterns are language-independent is usually asserted and rarely demonstrated. Here is the demonstration: a bounded retry policy with exponential backoff and jitter rendered in five languages whose paradigms barely overlap. The policy, its participants and its runtime behaviour are identical; what changes is how each language pays for indirection. Read the five blocks and you will see that the design is the same object graph and the cost model is the only thing the language decides.

// Elixir 1.19 — policy is a struct; behaviour is a function value.
defmodule Retry do
  @moduledoc "Exponential backoff with full jitter. Attempts are 0-based."

  @spec run((0..7 -> result), keyword) :: {:ok, result} | {:error, term}
        when result: term
  def run(fun, opts \\ []) do
    max = Keyword.get(opts, :max, 5)
    base = Keyword.get(opts, :base_ms, 50)
    do_run(fun, 0, max, base, [])
  end

  defp do_run(_fun, attempt, max, _base, _hist) when attempt >= max,
    do: {:error, :exhausted}

  defp do_run(fun, attempt, max, base, hist) do
    case safe_apply(fun, attempt) do
      {:ok, value} -> {:ok, value, hist}
      {:error, reason} when attempt == max - 1 -> {:error, reason, hist}
      {:error, reason} ->
        Process.sleep(jitter(:math.pow(2, attempt) * base))
        do_run(fun, attempt + 1, max, base, [{attempt, reason} | hist])
    end
  end

  defp jitter(span), do: :rand.uniform() * span
  defp safe_apply(fun, a), do: (try do {:ok, fun.(a)} rescue e -> {:error, e} end)
end
// PHP 8.5 — same policy. In PHP the "policy" is a first-class callable and
final readonly class RetryPolicy
{
    public function __construct(
        private int $maxAttempts = 5,
        private int $baseMicroseconds = 50_000,
        private int $jitterPermille = 1000,
    ) {}
    public function execute(callable $operation): mixed
    {
        $hist = [];
        for ($attempt = 0; $attempt < $this->maxAttempts; $attempt++) {
            try {
                return ['ok' => true, 'value' => $operation($attempt), 'hist' => $hist];
            } catch (TransientFailure $e) {
                $hist[] = ['attempt' => $attempt, 'why' => $e->getMessage()];
                if ($attempt === $this->maxAttempts - 1) {
                    return ['ok' => false, 'error' => $e, 'hist' => $hist];
                }
                usleep($this->backoffMicroseconds($attempt));
            }
        }
        throw new LogicException('unreachable');
    }
    private function backoffMicroseconds(int $attempt): int
    {
        $span = (int) (($this->baseMicroseconds << $attempt) * ($this->jitterPermille / 1000));
        return random_int(0, max(1, $span));
    }
}
public record Attempt<T>(int number, Outcome outcome, T value, Throwable failure) {
    public sealed interface Outcome permits Ok, Transient, Fatal {}
    public record Ok() implements Outcome {}
    public record Transient(String code) implements Outcome {}
    public record Fatal(String code) implements Outcome {}
    public static <T> Attempt<T> ok(int n, T v)      { return new Attempt<>(n, new Ok(), v, null); }
    public static <T> Attempt<T> tr(int n, String c)  { return new Attempt<>(n, new Transient(c), null, null); }
    public static <T> Attempt<T> fa(int n, String c)  { return new Attempt<>(n, new Fatal(c), null, null); }
}
public final class RetryPolicy {
    private final int max;
    private final long baseMillis;
    public RetryPolicy(int max, long baseMillis) { this.max = max; this.baseMillis = baseMillis; }
    public <T> Result<T, List<Attempt<T>>> run(CheckedSupplier<T> op) {
        var hist = new ArrayList<Attempt<T>>();
        for (int i = 0; i < max; i++) {
            try {
                var v = op.get();
                hist.add(Attempt.ok(i, v));
                return Result.success(v, List.copyOf(hist));
            } catch (TransientException e) {
                hist.add(Attempt.tr(i, e.code()));
                if (i == max - 1) return Result.failure(List.copyOf(hist));
                Sleeper.sleep(backoff(i));
            } catch (RuntimeException e) {
                hist.add(Attempt.fa(i, e.getClass().getSimpleName()));
                return Result.failure(List.copyOf(hist));
            }
        }
        throw new AssertionError("loop invariant");
    }
    private long backoff(int i) {
        long span = baseMillis << i;
        return ThreadLocalRandom.current().nextLong(span + 1);   // full jitter
    }
}

Compare the three. In Elixir the policy is data plus a private recursive loop, and the client supplies an anonymous function. In PHP the policy is a class holding three scalars, and the client supplies a first-class callable — PHP has no need for a strategy interface because closures are ordinary values. In Java the policy is a class, the operation is a functional interface, and the interesting extra work is the sealed result hierarchy that makes the three failure kinds un-extensible on purpose. The design is identical; the bill is different.

use std::time::Duration;
pub enum Attempt<T> {
    Ok { attempt: u32, value: T },
    Transient { attempt: u32, code: &'static str },
    Fatal { attempt: u32, code: &'static str },
}
pub trait Operation {
    type Output;
    fn call(&mut self, attempt: u32) -> Result<Self::Output, &'static str>;
}
pub struct RetryPolicy { pub max: u32, pub base: Duration }
impl RetryPolicy {
    pub fn run<O: Operation>(&self, mut op: O, rng: &mut impl RngLike) -> Result<O::Output, Vec<String>> {
        let mut hist = Vec::with_capacity(self.max as usize);
        for i in 0..self.max {
            match op.call(i) {
                Ok(v) => return Ok(v),
                Err(code) => {
                    hist.push(code.to_string());
                    if i == self.max - 1 { return Err(hist); }
                    std::thread::sleep(self.backoff(i, rng));
                }
            }
        }
        unreachable!("loop invariant is checked by the compiler here")
    }
    fn backoff(&self, i: u32, rng: &mut impl RngLike) -> Duration {
        let span = self.base.saturating_mul(1u32 << i.min(16));
        Duration::from_micros(rng.below_us(span.as_micros() as u64 + 1))
    }
}

0.6 Notation, typography and cross-references

Defines the symbols, the cross-reference format and the severity markers used consistently across all forty-two subsections.

Symbols carry meaning that would otherwise require a sentence each. ✓ marks a use for which the pattern or practice is appropriate; ✗ marks one for which it is not. 1.1 Single responsibility, precisely defined

Replaces the "one reason to change" slogan with an enumerable, testable definition based on distinct axes of change and a call-graph argument.

The most quoted definition of single responsibility — "a class should have only one reason to change" — is a symptom description masquerading as a definition, and it fails under examination. Every class has infinitely many reasons to change; what it has is a number of independent reasons, and the useful question is how many. The defensible formulation is this: a unit has a single responsibility if there is exactly one axis of change along which its public contract would have to be revised, and that axis is nameable in a short noun phrase.

Three corollaries make the definition operable. First, the axis must be a property of the contract, not of the implementation: adding a field to a private helper is a change in implementation, not a change in responsibility. Second, the axis must be independent — a unit that must change when the tax rate changes and when the payment provider changes has two axes, and the two axes vary for different business reasons at different rates, typically annually and quarterly respectively. Third, the axis must be countable from the outside: a reviewer should be able to name the axes from the public surface alone, without reading the body.

Robert Martin’s contribution was to note that responsibility is about actors. A responsibility is assigned to an actor — the finance team, the fraud team, the operations team — and the single-responsibility principle holds when each actor has exactly one reason to require a change. This reframing is what makes the definition testable: ask who asked for the last three changes, and the answer is a list of actors, and the count of distinct actors is the count of responsibilities.

1.2 Open/closed

Argues that the open/closed principle is about enumerated, named axes of variation, and that its cost is paid in indirection whether or not the axis materialises.

Open/closed is routinely quoted as "open for extension, closed for modification", which is a slogan that describes no testable property at all — every object is technically open for extension by subclassing and nothing is closed for modification in any meaningful sense. The operable content of the principle is narrower: a system is open along an axis if adding a member of that axis requires no modification of the code that already handles the existing members. That is measurable, and the measurement is files touched per added member.

Two facts make the principle a weak architectural tool on its own. The first is the prediction problem: you can only be open along axes you predicted, and prediction has a poor hit rate. A codebase opened for five axes that never materialise has paid five indirections for nothing; a codebase that closed itself for all axes and needed a sixth has paid a switch edit across N sites. The second is that the indirection cost is paid immediately and the benefit is paid contingently. A strategy table with one entry is strictly worse code than a switch with one branch, at every level: it is longer, it allocates, it loses exhaustiveness checking, and it has no place for a comment. The principle is therefore a bet, and the correct engineering response is to size the bet — open along axes that are already varying, and stay closed along axes that are not.

1.3 Liskov substitution

Restates Liskov substitution behaviourally, demonstrates that the canonical Rectangle/Square example does not actually violate it, and identifies the violations that occur in production code.

The 1973 formulation — "every operation on a base class should behave the same way for objects of its subclasses" — is a statement about observable behaviour, and it is one of the few principles in the literature with an unambiguous meaning. Its value is not that it forbids inheritance; it is that it makes inheritance auditable, and it does so by identifying the specific behaviours a client is entitled to rely upon: preconditions, postconditions, and class invariants.

The canonical counterexample is usually presented as follows, and the analysis matters because the example is widely cited and widely misread. A Square inherits from Rectangle. Rectangle.SetWidthAndHeight(w, h) is inherited, and calling it on a square violates the invariant width equals height. Therefore substitutability fails. This is correct — and the conclusion usually drawn, that the design is wrong, is not. The design is wrong for a different and more interesting reason: the inheritance is semantically false. A square is not a rectangle that happens to be constrained; the two are sibling concepts in the same taxonomy, and no client that treats a Rectangle generically can be trusted to treat a Square correctly. The correct refactoring is to model the invariant, not to delete Square.

// Java 25 — the canonical example, and the diagnosis that actually holds.
record Rectangle(double width, double height) {
    // Precondition:  width > 0 && height > 0   (enforced in ctor)
    // Invariant:     none
    void setSize(double w, double h) { throw new UnsupportedOperationException(); }
}

// Square's inherited setSize can only be honoured by ignoring one argument.
// Postcondition of setSize(w, h) is "both fields hold the given values".
// Square can satisfy it only for w == h.  => LSP VIOLATION, correctly diagnosed.
//
// BUT the true defect is upstream: `Square IS-A Rectangle` is a false claim.
// The honest model carries the invariant, and no violation is possible.

sealed interface Shape permits Rect, Square {
    double area();
}

record Rect(double w, double h) implements Shape {
    public double area() { return w * h; }
}

record Square(double side) implements Shape {
    // Invariant side > 0 is enforced here and cannot be broken by any
    // inherited method, because Shape declares no mutators at all.
    Rect asRect() { return new Rect(side, side); }
    public double area() { return side * side; }
}

1.4 Interface segregation, and its degeneration into one-method interfaces

Reformulates interface segregation as a constraint on client-visible coupling, shows how literal application produces single-method interfaces with negative returns, and identifies the real fault line.

Interface segregation is usually stated as "clients should not be forced to depend on methods they do not use", which is correct, and applied as "split every interface that has more than one method", which is wrong and produces a measurable pathology. The pathology is real and worth naming precisely, because it is now the dominant style in several popular codebases: the one-method interface.

The cost of the one-method interface is not aesthetic. It is that the interface has no name. A type called IShippingQuoteSource communicates the domain concept; a type called IShippingQuoteSourcePort communicates an architectural layer; a type called ShippingQuoteSourcePortAdapterPort communicates that a code generator was run. When the abstraction is one method wide, there is no domain vocabulary in it, so the actual domain concept must live somewhere else — usually as a record with a one-field wrapper, or as a type alias, or as a comment. The result is a codebase with twice as many types and half the vocabulary.

The deeper cost is that single-method interfaces are unusually LSP-sensitive and unusually substitutable, which means they quietly convert a design decision into a Dictionary lookup. If a class has two unrelated operations and you split them, the caller now holds two independently-implementable capabilities, and there is no longer any type in the system that says "these two things are one object with one lifecycle". The lifetime relationship — the thing that actually needed expressing — has been deleted by an over-literal reading of a principle about interface size.

1.5 Dependency inversion, misapplied to framework code

Separates the dependency inversion principle from dependency injection, and shows where abstracting over a framework inverts the dependency in the wrong direction and costs more than it returns.

Two distinct claims are routinely conflated. Dependency inversion is a statement about which direction information flows: high-level policy should not depend on low-level detail, both should depend on abstractions, and the abstractions should not depend on the details. Dependency injection is a statement about how an object receives its collaborators: through a constructor, a property or a method parameter, rather than by constructing them itself. Injection is the mechanism that makes inversion possible; it is not the principle, and a container that resolves dependencies from a global registry is injection without inversion — it merely moves the coupling from a new expression to a service locator.

Where this is most often misapplied is framework code. The canonical mistake is to define ISessionFactory, IMessagePump, IHttpTransport and ITransactionScope in the domain layer in order to "decouple from the framework", producing a domain that cannot use a transaction, cannot stream a response, and cannot be run by the framework’s own tooling. This is not dependency inversion, it is dependency obfuscation: the domain now depends on an abstraction whose only implementation is the framework adapter, so the dependency count is unchanged and the vocabulary is destroyed.

The distinguishing test is whether the abstraction has a second, genuinely different implementation that exists for a reason other than testing. If the only implementations are the real one and a mock, the abstraction has no reason to exist at the layer where it was declared; it belongs in the test, not in the production type system.

Do not invert toward your own framework wrappers. A wrapping interface is justified when (a) the concept is a domain concept the framework happens to implement, and (b) you can name a second implementation that is not a test double — an in-memory implementation used by a CLI tool, a cached implementation used by a hot read path, a deterministic implementation used by a batch job. The worked example that follows violates four of the five principles simultaneously and is the correct design for its problem. It is a hot read path in a reporting service: 4 100 requests per second at peak, a 12 ms p99 budget, and a data model that changes twice a year. 2.1 Adapter

Two variants of the same idea, the mechanics and cost of each, and the rule for deciding which to write.

Intent. Convert the interface of a class into something a client expects. Participants: Target (the interface the client speaks, 1), Adaptee (the foreign class, 1–N), Adapter (the translator, 1–N), Client (1–N). The pattern is trivially correct and almost never wrong, which is why it is under-taught: it has no controversial mechanics and no serious failure mode other than the accumulation of adapters that each add a layer until nobody can find the real implementation.

Two variants exist and they are not interchangeable. The object adapter holds a reference to the adaptee and delegates; it composes, so the adaptee’s lifetime is independent and the adapter can be created long after the adaptee. The class adapter inherits from the adaptee, which in most languages is now both unnecessary and harmful — it forces multiple inheritance or a language-specific trait, it makes the adaptee’s protected members visible, and it prevents the adapter from being used with a type that merely conforms structurally. The object adapter is correct in 2026 in every language in this guide; Go’s structural typing means the two are the same construct, and Rust’s trait objects make the class adapter unrepresentable.

2.2 Decorator

The pattern’s single hardest invariant — ordering — plus the measured cost of the wrapping chain and the closure-based alternative that removes it.

Intent. Attach additional responsibility to an object without subclassing. Participants: Component (1 abstraction), ConcreteComponent (1–N), Decorator (1–N, holds a Component), Client (1–N). The structural requirement is that a decorator implements the component’s interface exactly and forwards everything — any method a decorator does not override is a contract violation, because a caller holding the component type will call it and silently get nothing.

The invariant that separates competent decorator use from the widely-cited failure is ordering. A chain of decorators composes behaviour in an order that is determined by construction order, and the two plausible orders are not the same. In an outermost-first chain, caching outside timing outside retry; in an innermost-first chain, retry outside caching outside timing. Only one of these is correct for a given requirement, and in a codebase with 5 decorators the combinatorial count is 120 orderings, none of which is visible in the type system. Every serious implementation of a decorator chain therefore makes the composition explicit and named rather than letting the DI container assemble it in registration order.

  const t0 = performance.now();

  return async (u) => {
    for (let i = 0; i < attempts; i++) {
      try { return await next(u); }
      catch (e) {
        if (i === attempts - 1 || !isTransient(e)) throw e;
        const span = baseMs * 2 ** i;
        await sleep(Math.random() * span);          // full jitter
      }
    }
    throw new Error("unreachable");
  };
};

  const hit = store.get(u);
  if (hit) return hit;
  const body = await next(u);                      // inner: sees only misses
  store.set(u, body);
  return body;
};

2.3 Facade

The only structural pattern that reduces rather than increases the number of types, its three required properties, and the cost when it becomes a god object.

Intent. Provide a single, stable entry point to a subsystem whose real interface is wide and whose usage is narrow. Participants: Facade (1), Subsystem classes (3–30), Client (1–N). The pattern’s distinguishing property is that it has no participants of its own: it defines no interface of its own, holds no state worth naming, and is free to be replaced. This is why it is the least structural of the six and the most frequently correct.

Three properties distinguish a real facade from a helper class. It must be thin: it orchestrates calls and returns a result, and it does not implement policy, because policy in a facade cannot be tested independently of the subsystem. It must be complete for its use cases: a facade that exposes one method per use case is correct, and a facade that merely forwards all subsystem methods is a pointless layer with a 1:1 mapping and a maintenance cost of one extra hop. And it must be open behind: the subsystem must remain directly reachable for the cases the facade does not cover, or the facade becomes a gate that must be extended for every new requirement.

2.4 Composite

Uniformity versus type safety in a tree, the three costs of composite’s ambiguity, and the 2026 default of an explicit closed hierarchy.

Intent. Compose objects in tree structures so that clients treat individual elements and compositions identically. Participants: Component (1 abstraction declaring operation()), Composite (1–N, holds a collection of Components), Leaf (1–N, no children), Client (1–N). The pattern’s entire value is the claim that a client cannot tell a leaf from a branch, and its entire cost is that this uniformity is achieved by a shared interface that both kinds must implement, which means operations valid for a branch are exposed on a leaf.

The two costs follow directly. First, type safety is traded for uniformity: RemoveChild(Composite c) is on the Component interface and throws or no-ops on a leaf. Second, dispatch becomes a runtime branch at every node, and in a tree of depth 6 with 10 000 nodes a naive recursive walk performs 10 000 type tests. Both costs are avoidable in a modern type system, and the alternative is usually better: a sealed hierarchy with one abstract accept or a sum type with a fold, where the compiler can prove exhaustiveness and where the branch is erased.

2.5 Proxy

The pattern’s four variants, the confusion between a proxy and its two cousins, and the two correctness traps that produce silent data corruption.

Intent. Provide a surrogate that controls access to another object. Participants: Proxy (1–N, holds a reference to the real subject), RealSubject (1), Subject (1 interface shared by both), Client (1–N). The pattern has four well-distinguished variants, and the literature’s habit of listing them without saying they have different failure modes is the main practical problem with it.

Virtual proxy defers construction until a method is called. Remote proxy makes an in-process object look like a remote one. Protection proxy enforces access control. Caching proxy — which is a Decorator (2.2) with a storage concern, and should be named as such. The two traps are specific and both are silent. The first is identity: a proxy that wraps a mutable subject and is compared with == or used as a dictionary key does not compare equal to the subject unless the proxy deliberately forwards equality, and the failure is a duplicated cache entry or an infinite retry loop. The second is partial state: a caching or lazy proxy that returns a default-constructed value while loading fails turns a network error into a plausible-looking zero, which is far more expensive to diagnose than a crash.

2.6 Flyweight

The only GoF pattern whose primary beneficiary is the garbage collector, its 2026 relevance after value types, and the invariant that makes it unsafe to get wrong.

Intent. Share fine-grained objects to support large numbers of clients efficiently. Participants: Flyweight (1–N, intrinsic state only), FlyweightFactory (1, owns the pool and the intrinsic state), Client (1–N, holds extrinsic state). The pattern’s entire purpose is to move state out of objects that are numerous into objects that are few, so that memory scales with the number of distinct values rather than the number of occurrences.

The pattern’s 2026 status is genuinely different from the other five, and the change is caused by the widespread availability of value types. In languages with cheap value semantics — Rust, Go, C# structs, Kotlin data classes, Python with __slots__ — the flyweight is the default and the pattern is unnecessary: a 24-byte glyph struct copied by value costs nothing and cannot be accidentally shared, which is the flyweight’s chief hazard. The pattern is still needed in three situations: the shared object is expensive to construct rather than expensive to store, the shared object owns an external resource, or the intrinsic state is genuinely large (a 4 KB font glyph raster). The pattern is actively harmful when used to reduce object count for its own sake.

The invariant that makes it unsafe: a flyweight must hold intrinsic state only. If any per-occurrence state is stored on the shared instance, two occurrences of the same value become indistinguishable and the bug is a data race or a lost update, both of which are silent and both of which are expensive to reproduce.

How to know whether you have a flyweight problem. Not by object count — by duplicate intrinsic state. Three measurements, in order: allocation profile showing the same immutable payload allocated repeatedly; retained heap divided by distinct values, which should be a small integer and in a healthy system is 1; and the time spent in constructors that perform pure computation. The first two identify the opportunity; the third tells you the size of it. In the glyph case the ratio was 1 000 000 : 8, which is unmistakable. In a case where the ratio is 4 000 : 3 800, the flyweight will not pay for the lock.

3.1 Builder

Distinguishes the telescoping-constructor problem from the staged-construction problem, and shows why named factories now cover most Builder uses.

Intent. Construct a complex object step by step, separating specification from realisation. Participants: Builder (1 interface, stages the construction), ConcreteBuilder (1–N, assembles a product), Director (0–1, sequences the stages — usually unnecessary in modern code), Product (1–N). The pattern exists for one specific problem: an object with so many valid configurations that a constructor cannot express them, and so many optional parameters that the constructor’s signature is unreadable.

Two different problems get conflated under this name, and they need different answers. The telescoping constructor problem is solved by any of the three: optional parameters, a builder, or — best — a record with named fields, because a record’s constructor call is self-documenting at the call site. The staged construction problem is different: the object cannot be built in one expression because step 3's inputs depend on step 1's output, or because the object must be validated between stages, or because a stage is expensive and should be deferred. Only a genuine staging requirement justifies a Builder class; a record does not stage anything.

3.2 Factory Method

Separates the decision of what to construct from the construction itself, and shows that in most languages a function and a table replace the class entirely.

Intent. Define an interface for creating an object, and let subclasses or registrations decide which concrete type to instantiate. Participants: Product (1–N), Creator (1 abstract, declares the factory method), ConcreteCreator (1–N), Client (1). The pattern’s value is one thing: it moves a single decision — "which concrete type" — out of the client and into a place where it can be changed without touching the client.

The 1994 implementation used subclassing, and that is now the worst available implementation, because each new product type requires a new subclass whether or not the subclass has any behaviour beyond construction. The 2026 implementations, in ascending order of machinery, are: a free function returning a value; a lookup table from key to function; a registry passed into a function; and — only if the decision must vary by context object at runtime — a class with a virtual method. The table is worth stating because most of the cost difference is invisible until a codebase has 30 product types.

The class-based version of the pattern survives only when the factory method must be overridden polymorphically by a subclass, which in practice means only when you are designing a framework for third parties — and frameworks built on Factory Method have a well-earned reputation for being harder to extend than frameworks built on registration.

Factory Method versus dependency injection. These are frequently treated as alternatives and are not. A DI container resolves a requested type; a factory decides which type is correct given a run-time key. In a container world the factory’s job shrinks to exactly the part the container cannot do — the conditional — and that job is usually 3 lines. Writing a factory that only forwards to a container registration has produced no benefit; writing a factory that encodes a real decision has produced most of the benefit of the pattern in 6 lines.

3.3 Abstract Factory

The pattern with the highest ratio of machinery to benefit, and the conditions under which a family of products is a real concept rather than a coincidence.

Intent. Provide an interface for creating related objects without specifying their concrete classes. Participants: AbstractFactory (1 interface, 3–8 creation methods), ConcreteFactory (1–N), Product (1–N interfaces), ConcreteProduct (1–N per product), Client (1–N). The pattern’s distinguishing property is that the factory’s methods are correlated: they must all produce products from the same family, and the client relies on that correlation without being able to express it.

This is the least-used and most-misunder pattern in the catalogue, and the reason is visible in the participants list. An abstract factory with 5 creation methods needs 5 product interfaces and, for N families, N concrete factories and up to 5N concrete products — a 5-product, 3-family configuration is 19 types to construct 3 objects. The correlation the pattern guarantees is real, but in most codebases the family is a runtime data question ("which theme, which locale, which tenant configuration") rather than a type question, and runtime data is better expressed as a value.

3.4 Singleton, the module registry, and explicit lifecycle

The pattern with the worst name-to-value ratio in the catalogue, and the four things it is genuinely used for once the global-state objection is separated out.

Intent. Ensure a class has exactly one instance and provide a global point of access. Participants: Singleton (1, with a private constructor and a static accessor). The pattern’s stated intent is a guarantee about identity — exactly one instance — and its unstated, and much more consequential, effect is to make a global variable with lazy initialisation, a global namespace and a hidden dependency.

The identity guarantee is almost never the requirement. What is actually required, in the four cases that survive scrutiny, is: (a) one shared expensive resource per process, such as a connection pool or a compiled regex set; (b) one authoritative configuration snapshot per process; (c) an idempotent, process-wide identity source, such as a request counter; and (d) a runtime registry keyed by name, which is not a singleton at all but a module table. The other 90 % of singleton usage — "so I can call it from anywhere" — is a dependency-injection defect that the pattern conceals by making the dependency invisible.

The test for a legitimate process-wide singleton. Answer all four with yes: (1) does it own an external resource whose acquisition is expensive and whose release must happen exactly once — a socket, a file handle, a native library, a timer wheel; (2) is it immutable, or thread-safe by construction; (3) can a test construct a second, differently-configured instance and get different behaviour; (4) does the application genuinely have one, rather than one per tenant, per request or per shard. 3.5 Object Pool

The one creational pattern the garbage collector cannot replace, its measured break-even, and the precondition that makes it unsafe.

Intent. Reuse objects of the same kind rather than creating and destroying them. Participants: Pool (1, owns the free list and the factory), PooledObject (1–N, must support reset), Client (1–N). The pattern’s purpose is to avoid the cost of acquisition — allocation, OS resource acquisition, or expensive initialisation — and the modern version also targets latency predictability, which is often the stronger reason.

Pooled objects are reused mutable state, and that is exactly what a garbage-collected language spent two decades teaching you not to do. The pattern is correct precisely when the pool owns the object’s lifecycle completely, and the failure mode is a leaked reference: a caller retains a pooled object past its return, and the pool hands the same object to a second caller, and the first caller’s mutation appears in the second caller’s data. This is the most severe class of bug in this chapter because it is silent, it is data-dependent, and it reproduces at production load rather than in a test.

public sealed class BufferPool
{
    private readonly Stack<RentedBuffer> _free = new(capacity: 64);
    private readonly Func<int, RentedBuffer> _create;
    private int _live;                                  // for the leak detector
    public RentedBuffer Rent(int n)
    {
        lock (_free)
        {
            while (_free.Count > 0)
            {
                var b = _free.Pop();
                if (b.Length >= n) { b.Reset(); Interlocked.Increment(ref _live); return b; }
                b.Dispose();                            // too small: genuinely free it
            }
        }
        var made = _create(n);                         // 40 µs, the cost we avoid
        Interlocked.Increment(ref _live);
        return made;
    }
    public void Return(RentedBuffer b)
    {
        Interlocked.Decrement(ref _live);
        b.Reset();                                     // PRECONDITION of the pattern
        lock (_free) { if (_free.Count < 64) _free.Push(b); else b.Dispose(); }
    }
    public int Live => Volatile.Read(ref _live);       // MUST return to 0 at quiescence
}

3.6 Prototype and the immutability dividend

Copy construction, the hidden cost of a shallow copy, and why immutability makes the pattern disappear into a language feature.

Intent. Specify the kind of an object by creating a prototype and making copies of it. Participants: Prototype (1–N, itself an instance that can clone), ConcretePrototype (1–N), Client (1–N). The pattern’s 1994 purpose was to avoid the cost of construction for expensive objects in languages where object initialisation was costly, and that purpose has largely evaporated: copying an object is no cheaper than initialising one in any language in this guide except C++, and in C++ the pattern was never the answer either.

What survives is copy construction as a defaulting mechanism: a builder or configuration object that is copied and then modified. This is genuinely useful and is used constantly, but it is a language feature in all eight languages here — with in C#, spread in TypeScript, dataclasses.replace and copy.replace in Python, clone in PHP, record copy in Java, struct copy in Go, #[derive(Clone)] in Rust, and struct copy in Elixir. The pattern is worth discussing mainly for its hazard, which is the same hazard in every language: the copy is shallow unless someone thought about it.

The six behavioural patterns, with particular attention to the one structural question that unites half of them: whether the variation axis belongs in a type or in a value. Strategy, State and Command are all ways of binding a decision at run time, and the differences between them are entirely about how long the decision lives — per call, per object lifetime, or per transaction. 4.1 Strategy

The decision-scoping axis, the four implementations ranked by cost, and the reason the modern answer is almost never a class.

Intent. Define a family of algorithms, encapsulate each one, and make them interchangeable at run time. Participants: Strategy (1 interface, 1–5 methods), ConcreteStrategy (1–N), Context (1, holds a Strategy and delegates). The pattern’s value is precisely one thing: it moves a conditional from the middle of a method to a binding at the edge, which makes the conditional nameable, testable and replaceable.

Because the value is that small, the cost of the machinery must also be small, and in most languages it is not: an interface, a family of classes, and a registration. The four implementations in ascending cost — a switch expression, a first-class function, a table of functions, and a strategy interface — are separated by nanoseconds and by dozens of lines, and the choice should be made by counting the variants, not by the pattern’s name.

The choice is not aesthetic. It is determined by the arity of the decision and the lifecycle of its inputs. A one-method decision taken per call should be a function or a switch. A multi-method decision that should be named in the domain’s vocabulary should be an interface. A decision that must be selected once at startup and held should be a bound strategy object, not a per-call lookup.

// The bound-strategy form, which is the genuinely distinct third lifecycle:
// chosen ONCE at construction, invoked MANY times. This is what a
// Strategy interface is actually for, and it is where it pays.
public sealed class FreightSurcharge
{
    private readonly IFreightRate[] _rates;
    private readonly Dictionary<Region, IFreightRate> _primary;

    public FreightSurcharge(IEnumerable<IFreightRate> rates)   // built once, at startup
    {
        _rates = rates.ToArray();
        _primary = _rates.ToDictionary(r => r.Coverage);
    }

    // Called 2.4 M times a day. The dispatch is a dictionary lookup plus
    // 1-2 interface calls, not a linear scan and not a switch.
    public Money For(Shipment s, Weather w)
    {
        var carrier = _primary[s.Region];
        Money total = carrier.BaseCharge(s);
        foreach (var extra in _rates)                  // surcharges are COMPOSABLE
            if (!ReferenceEquals(extra, carrier) && extra.Applies(s))
                total += extra.SurchargeFor(s, w);
        return total;
    }
}

Choosing the strategy representation in one question. Would you accept a bug report phrased as "tenant 47 gets the wrong freight rate"? If yes, the strategy must be a value — a table row, a config entry, a database record — because that is the only representation you can change without a deployment. If no, because the set of algorithms genuinely is fixed and small, use a switch and keep the exhaustiveness check the compiler gives you for free. The question is not about extensibility in the abstract; it is about who is allowed to change the decision and how fast.

4.2 Template Method

Inversion of control applied to an algorithm’s skeleton, and why its modern form is composition rather than inheritance.

Intent. Define the skeleton of an algorithm in a base class, deferring specific steps to subclasses. Participants: AbstractClass (1, declares the template method and abstract hooks), ConcreteClass (1–N, implements the hooks), Client (1–N). The pattern is a controlled inversion of control: the algorithm’s author owns the order and the control flow, and the subclass author owns only the leaves. This is the same relationship that a callback chain, an event handler or a map/filter/reduce expresses — the pattern’s historical distinction is that it uses inheritance to express it.

In 2026 the pattern survives in three forms and is wrong in one. It is right when the steps must be enumerated in one place and the order is the specification — a validation pipeline, an export format, a state-transition reducer. It is right as a final method over abstract methods in a language with no other way to express a fixed pipeline. It is right as composition — a list of functions, a chain of middleware (2.2). It is wrong as a general subclassing idiom, because it makes the algorithm’s control flow part of the type’s public surface, which means a caller holding the base type cannot know which steps will run.

4.3 Observer

Push versus pull, the three ordering and re-entrancy hazards, and the observation that an event emitter is an Observer whose subscribers the type system cannot see.

Intent. Define a one-to-many dependency so that when one object changes state, all its dependents are notified automatically. Participants: Subject (1, holds observers), Observer (1 interface, 1 method), ConcreteObserver (1–N), Client (1–N). The pattern is the most widely implemented pattern in the catalogue, because essentially every event system, signal, listener registry and pub-sub client in every language is one.

The single design decision that determines the correctness of an observer implementation is push or pull. A pushed observer receives the changed value and has everything it needs, at the cost of constructing a payload object per event even if no observer uses most of it. A pulled observer receives a reference to the subject and reads what it needs, at the cost of exposing the subject’s mutability and creating a race between the notification and the read. The correct default is push with a typed payload, and the reason is that pulling turns every observer into a place where the subject’s internal state is observable, which is precisely the coupling the pattern is supposed to remove.

4.4 Command

The pattern that turns an intention into a value, its three genuine uses, and the accounting system it becomes when the queue is durable.

Intent. Encapsulate a request as an object, thereby parameterising clients with the requests, queuing, logging and undoing them. Participants: Command (1 interface: execute() and usually undo()), ConcreteCommand (1–N), Invoker (1, decides when to execute), Receiver (1–N, the thing that does the work). The pattern’s defining property is that a request becomes a value: it can be stored, compared, logged, retried, scheduled and reversed, none of which a method call can do.

Three uses are genuine. Reversible operations — an editor, a transaction log, a compensation in a saga. Queued and retried work — the request outlives the process that created it. Auditable intent — the command is a description of what was asked for, and the log is a log of decisions rather than a log of calls. One use is usually a mistake: wrapping a synchronous call in a Command object in the hope of gaining extensibility. If nothing stores, schedules, reverses or logs the command, it is a class with one method and no reason to exist.

4.5 State, and the state machine as data

The pattern that replaces a boolean with a structure, the three ways to represent a state machine, and the rule for choosing between them.

Intent. Allow an object to alter its behaviour when its internal state changes, so that it appears to change its class. Participants: Context (1, holds a current state and delegates), State (1 interface, 1–4 methods), ConcreteState (1–N), Client (1–N). The pattern’s argument is that behaviour which depends on state belongs with the state, and that a switch over an enum is a State pattern that has been flattened back into a method — usually a method that has grown past 150 lines.

There are three representations, and choosing among them is the entire practical content of the pattern. The enum plus switch is correct for 2–5 states with 1–2 behaviours and no per-state data. The class per state is correct when each state has substantial distinct behaviour, because it lets the compiler reject an operation a state does not support — at the cost of a class per state and a virtual call per transition. The state machine as data — a transition table plus a reducer — is correct when the state graph is large, when it must be inspectable, when it must be persisted and reloaded, or when a non-programmer needs to reason about it. A 14-state order lifecycle with 41 legal transitions is 14 classes and 41 virtual calls in the object form, and a table with 41 rows in the data form; the data form is the one that can be drawn on a whiteboard, reviewed by a domain expert, and tested by a single parameterised test that walks every edge.

Two properties of the data form are worth stating because they are not obvious. The transition table is exhaustively testable: one parameterised test walks all 19 edges and asserts each produces the expected state, and a second test asserts that every state is reachable from Draft and that every state has a path to a terminal state. Both are 20 lines and both find real defects. 4.6 Visitor, and the two-intersection problem

The pattern’s actual counting rule, the modern form that replaces it, and the honest comparison against a sealed hierarchy with a fold.

Intent. Define a new operation over a set of classes without changing those classes, by moving the operation into a visitor that is dispatched by the classes. Participants: Element (1 interface, 1–N), ConcreteElement (1–N), Visitor (1 interface, 1 method per element type), ConcreteVisitor (1–N), Client (1). The pattern exists to add operations without adding methods, and its cost is that it inverts the dependency: the visitor needs to know every element type, so adding an element requires editing every visitor.

The counting rule that decides whether the pattern is worth it is the two-intersection count: multiply the number of element types by the number of operation types. Below roughly 10, a switch in each operation is smaller, faster, and the compiler enforces exhaustiveness for free — which is a benefit the Visitor pattern cannot match at all, since adding a tenth element type silently breaks every visitor. Above 20, the pattern starts to justify itself, because the alternative is 20 switches each of 10 arms. And in every language in this guide with algebraic data types, the answer is neither: it is a sum type with a fold, which achieves the Visitor’s goal — operations added without touching the type definitions — with the exhaustiveness check the Visitor pattern lacks.

5.1 Purity and referential transparency

Defines purity precisely, separates it from the two properties it is usually confused with, and shows what it is actually good for.

A function is pure if its return value depends only on its arguments and it performs no observable effect: no mutation of state visible to the caller, no I/O, no reading of ambient state such as a clock or an environment variable, and no non-determinism. A function is referentially transparent if it can be replaced by its value in any expression without changing the program’s meaning — which is a strictly stronger property, because it additionally permits common-subexpression elimination and reordering. Pure functions are referentially transparent, but not conversely: Math.random() is referentially transparent only under an interpretation where its value has already been fixed.

The two properties most often confused with purity are immutability (a function may be pure while operating on mutable data it does not own) and determinism (a function may be deterministic and pure but depend on an injected clock, which is still impure in the strict sense and still perfectly testable). The practical distinction matters because the reason to care about purity is not philosophical: it is that a pure function can be tested with input-output pairs, reasoned about locally, memoised, run in parallel, and composed without the reader needing to hold the program’s state in their head.

Purity’s practical value is concentrated in three places, and it is worth being precise about which is which. The first is property-based testing, which is impossible without it, because a property must hold for a stated domain and an impure function’s domain changes between runs. The third is concurrency safety, which is a corollary rather than a cause: pure functions are trivially thread-safe, but thread-safety can also be achieved by other means, and immutability plus careful publication usually suffices.

5.2 Immutability and persistent data structures

The difference between immutable values and persistent data structures, structural sharing, and the measured cost of both.

Immutable means an object’s state cannot change after construction, so every reference to it is a valid description of it forever. Persistent means an update returns a new version that shares unchanged structure with the old one, so a sequence of 1 000 updates costs O(1) new memory per update rather than O(n) copying. The two are separate: an immutable array that copies all 1 000 elements on every append is immutable and not persistent, and costs O(n²) over 1 000 appends.

The practical argument for immutability in a mutable-runtime language is not memory — it is that immutability converts a whole class of concurrency and aliasing defects into compile errors or impossible states, and that it enables structural sharing which is what makes undo, snapshots, caching and time-travel cheap. The cost is real and measurable: a persistent update in a language without built-in support typically costs one small object plus a path copy, and the languages that provide it natively make the same operation free or nearly so.

// C# 14 / .NET 10 — persistence provided by the runtime. `ImmutableArray<T>`

Immutability does not mean everything is immutable. The practical discipline in a garbage-collected language is a boundary rule: values below the I/O line are immutable, state above it is owned by exactly one component. The I/O line is the point where a call can block, fail, or observe the world. Above it you have ports and services; below it you have pure computation. This rule is what makes the discipline affordable, because it does not require the whole system to be functional — only the part where reasoning is hard, and which is worth property-testing, to be free of effect.

5.3 Monads, explained through Option, Result, Promise, Stream and Parser

Defines a monad by its two operations and its two laws, then shows the same shape in five types a working engineer will actually write, with no category theory.

A monad is a type constructor M together with two operations: a unit (also called return or lift) that puts a value into the context, and a bind that composes a computation producing an M with a function from the underlying value to another M. Two laws constrain them: left identity, unit(a).bind(f) == f(a), and right identity, m.bind(unit) == m. That is the whole definition. Everything else — the category theory, the monadic composition laws in Haskell’s do notation — follows from these and is not needed to use any of the five types below.

The reason this matters to a professional engineer is that Option, Result, Task, Stream and Parser are all the same structure with different bind semantics, and recognising the shape means you can transfer a technique from one to another. Option.bind short-circuits on absence. Result.bind short-circuits on failure and accumulates the first reason. Task.bind does not short-circuit at all; it sequences asynchronous effects and guarantees the second does not start before the first completes. Stream.bind flattens a stream of streams and lets you implement infinite pipelines with finite memory. Parser.bind threads a position through a grammar, which is what makes backtracking correct rather than a hand-rolled mess.

public readonly struct Option<T>
{
    private readonly T? _value;
    private Option(T v) => _value = v;
    public static Option<T> Some(T v) => new(v);
    public static Option<T> None  => new();
    public bool IsSome => _value is not null;

public readonly struct Result<T, E>
{
    private readonly T? _ok; private readonly E? _err;

    public static Result<T, E> Err(E e) => new(default, e);
    public Result<U, E> Bind<U>(Func<T, Result<U, E>> f) =>

public readonly struct Task<T>
{
    private readonly Func<CancellationToken, ValueTask<T>> _run;
    public Task(Func<CancellationToken, ValueTask<T>> run) => _run = run;
    public Task<U> Bind<U>(Func<T, Task<U>> f) =>
        new(ct => _run(ct).ContinueWith(t => t.IsCompletedSuccessfully
            ? f(t.Result).RunAsync(ct)
            : ValueTask.FromResult(default!), ct).Unwrap());
}
public readonly struct Stream<T>
{
    private readonly Func<CancellationToken, IAsyncEnumerable<T>> _run;
    public Stream(Func<CancellationToken, IAsyncEnumerable<T>> run) => _run = run;
    public Stream<U> Bind<U>(Func<T, Stream<U>> f) =>
        new(ct => Flatten(_run(ct), f, ct));
}
public readonly struct Parser<T>
{
    private readonly Func<string, int, ParseResult<T>> _run;
    public Parser(Func<string, int, ParseResult<T>> run) => _run = run;
    public Parser<U> Bind<U>(Func<T, Parser<U>> f) =>
        new((s, p) => _run(s, p) switch
        {
            ParseResult.Ok(var v, var np) => f(v)._run(s, np),
            ParseResult.Fail e              => e,
        });
}

The practical payoff is that a chain of binds reads left to right, top to bottom, with no nesting and no early returns, and every failure mode is represented as a value rather than as a control-flow exception. The costs are equally concrete: the Result chain requires error-type unification, so heterogeneous errors need either an enum or a boxed error; the Task chain allocates a continuation per bind; and the Stream chain requires a disciplined await foreach to avoid accidental buffering.

Error accumulation is a choice, and the default is wrong often enough to matter. Result.bind short-circuits, which means a 40-step validation pipeline reports the first failure and the user fixes it, submits again, and discovers the second. In a 6-field form, first-failure reporting produces a median of 2.4 submission round trips against 1.0 for accumulation, and each round trip is a network call from a phone on a poor connection. The fix is not to abandon Result but to use a third type: Validation<T, E> whose bind concatenates errors rather than short-circuiting, and to apply the first-failure semantics only to sequences that genuinely must not proceed — anything with a side effect, anything expensive, anything order-dependent. The distinction is not stylistic; using first-failure semantics on a pure validation chain is a measurable product defect.

5.4 Algebraic data types, product and sum

Two constructors, one modelling rule — make illegal states unrepresentable — and the conversion table from class hierarchies to algebraic types.

An algebraic data type is built from two constructors and nothing else. A product constructor combines a fixed set of fields into a value that has all of them: Product<A, B, C> is the cartesian product, and it corresponds to a record or a plain class. A sum constructor chooses exactly one of several alternatives: Sum<A, B, C> is the disjoint union, and it corresponds to a sealed class, an interface with a closed set of implementations, or a tagged union. Every type in a well-modelled system is built from these two operations, and the entire benefit of the discipline is in the sum constructor, because a sum has an exhaustive set of cases and the compiler can therefore enforce that every one is handled.

The modelling rule that follows is worth stating as a single sentence: represent the states your domain can be in, and nothing else. A class hierarchy with 4 subclasses and 6 nullable fields can express 2⁶ × 4 = 256 states, of which perhaps 9 are legal. A sum type over 4 alternatives with 6 total fields expresses 4. The gain is not elegance — it is that the 247 illegal states cannot be constructed, so the 247 corresponding tests do not need to exist, and the 9 illegal transitions that a real system will attempt become compile errors rather than production incidents.

5.5 Effect handling: where effects live in an object-oriented codebase

A concrete placement rule for effects — below the port boundary they are absent, above it they are explicit — and three mechanisms for handling them without a functional core in the strict sense.

The question this section answers is practical: in a codebase built from classes, ports and a DI container, where do effects go, and how are they handled? The answer that has held up across several large systems is a two-region architecture. In the inner region — domain logic, calculation, validation, state transition — there are no effects at all: no I/O, no clock, no randomness, no logging, no environment. In the outer region — controllers, handlers, adapters, composition roots — every effect happens, and each is either performed directly or captured in a type that makes it a value.

This is not the "functional core, imperative shell" formulation exactly, because a strict functional core requires that the core return descriptions of effects rather than performing them, which requires an interpreter and adds a layer that most OOP systems do not earn. The weaker and usually sufficient version is that the core is pure — no ambient effect — while the shell both performs effects and interprets a small number of effect descriptions where sequencing matters.

Three mechanisms exist for handling effects more explicitly than this, and it is worth knowing all three even if you use only the first. Free-monad or interpreter style: the core returns a data structure describing effects, and an interpreter performs them. Maximum purity and maximum testability; maximum indirection and a new vocabulary for the team to learn. Reader-writer in a single monad: the core runs in Task<Result<T,E>, Env>, threading the environment and accumulating effects. Cleaner than free-monad for most systems; the type signatures become long. Effect handlers as an explicit queue: the core returns IReadOnlyList<Effect> and the shell executes them in order with a failure policy. This is the middle ground and it is what the example above is doing implicitly.

from __future__ import annotations

5.6 When is this idiomatic? An honest answer for OOP codebases

Gives the decision criteria, the three situations where introducing these idioms is a net loss, and a staged adoption path that does not require rewriting anything.

The honest answer has two halves. These idioms are idiomatic — meaning the cost they charge is smaller than the value they return — in four identifiable situations, and they are a liability in three. The four situations are: the code is a calculation whose correctness matters and which has no effects to begin with, such as pricing, tax, scheduling and state-transition logic; the type is a closed set of states and the exhaustiveness property is worth enforcing; the operation is a chain of four or more steps where the imperative form nests; and the value must be shared across threads or retained as a snapshot.

The three liabilities are equally identifiable. They are a liability when the team does not share the vocabulary, because an Option that half the team treats as nullable and half treats as an error will produce defects that are harder to diagnose than the null it replaced. They are a liability when the abstraction is applied at a layer where a runtime dispatch already exists and the performance matters — an Option<T> monad in a per-pixel inner loop in a language without inlining is a 14× slowdown. And they are a liability when the cost is paid in a codebase that will not be maintained by people who know the idioms, which is the situation in most enterprise codebases and the one that should govern the decision.

The adoption path that worked across all three audits was staged and incremental, and never involved a rewrite. Introduce one type in one module, in the place where the pain is highest, and let the rest of the codebase continue in its existing style until a specific change requires otherwise. A codebase that adopts Result at one boundary and uses exceptions everywhere else is not inconsistent in a harmful way; it is a codebase with a well-defined edge, and the edge is where the design question actually lives.

How to tell whether a team can carry these idioms. Three signals, and all three must be present. The team can state the two monad laws without looking them up, which means the vocabulary is internalised rather than copied. The team uses the idioms in review comments to explain a design rather than to win an argument, which means they have moved from advocacy to description. And at least one person has migrated a module away from the idioms and been asked why, which means the choice is understood to be a choice. When any of the three is absent, the correct adoption is smaller: one type, one module, one boundary, and a re-evaluation after six months rather than a migration.

The three ways this goes wrong in practice. Heterogeneous vocabulary: two teams in the same repository use Result with incompatible error conventions, and a caller that assumes one gets the other’s semantics — the worst outcome, because it is type-compatible and semantically wrong. The defence is a single shared error module per bounded context and a review rule that forbids ad-hoc error enums. Leakage into the shell: the core is pure for three months and then someone adds a DateTime.UtcNow because a deadline check "has to be there", and purity is lost in a way nobody notices because nothing tests for it. The defence is the design-lint rule from section 0.4, which is a 4-line static check. Allocation regression: the idioms are adopted in a hot path and the p99 moves from 8 ms to 41 ms, and the change is reverted under deadline pressure with a comment reading "premature optimisation", which is a misdiagnosis that will be repeated at the next opportunity.

6.1 The Fowler smell catalogue, annotated with a response policy

Twenty Fowler refactorings, each with the symptom to look for, the measured cost of leaving it, and an explicit policy for when to act.

A smell is a surface symptom that correlates with a structural cause. The correlation is not deterministic — a 200-line method can be a linear algorithm that happens to be long, and a 6-line method can contain the worst decision in a system — which is why the useful property of a smell catalogue is not the list but the response policy: for each entry, the condition under which acting is worth the cost, and the condition under which it is not. The three policy categories are act now (the smell is on a change path and the cost of leaving it is compounding), act on touch (the smell is real but not currently costing anything, so fix it when you are editing that code anyway), and leave it (the "smell" is a false positive for this code’s purpose).

6.2 The four safe mechanics

The four operations that account for most productive refactoring, why they are safe, and the two structural edits that are not on the list.

Martin Fowler’s second edition reduces twenty refactorings to a small set of mechanics — the low-level, semantically unambiguous edits from which the named refactorings are composed. Four of them account for the overwhelming majority of productive work: extract function, extract variable, move function (move method, in the object-oriented spelling), and replace temporary with query. Each is safe in a specific and important sense: each has no decision in it. The engineer chooses a name and a boundary, and the compiler verifies the rest. That is the property that distinguishes them from design changes, and it is the property that makes them applicable in a codebase nobody understands completely.

The two structural edits that are not on that list are worth naming, because they are the ones people reach for first and the ones that break things. Change signature alters a contract and therefore every caller, and it is safe only when the compiler finds all of them — which it does in most languages and does not in Python, Ruby, JavaScript or any language with structural typing and no whole-program name resolution. Inline is the reverse and has the same property. The practical consequence is that in a dynamically typed or weakly typed codebase the four safe mechanics remain safe and the two structural ones require a search that may be incomplete.

6.3 Origin-introducing smells and how they compound

The distinction between smells that persist and smells that reproduce, and the four that generate others at a measurable rate.

Most smell catalogues treat all smells as equivalent: things to be cleaned up. That framing misses the important distinction between a smell that persists — a long method that stays long because nobody has needed to change it — and a smell that reproduces, a structure that generates new instances of itself every time it is extended. Origin-introducing smells are the second kind, and they are the only ones that justify architectural work, because they predict future cost rather than describing present cost.

Four reproduce reliably, and each has a characteristic signature: how many new instances it generates per change, and what it generates them into. The practical value of identifying them is that a reproducing smell is an argument for a structural change at a specific point, and a persisting smell is not an argument for anything at all.

The final line is the one most catalogues omit, and it is the reason a response policy is necessary. A codebase with 14 long methods and no reproduction is not a codebase with a problem; it is a codebase where the long methods are stable and the risk of change is low. Cleaning them up would consume 3 weeks, introduce 61 opportunities for a regression, and produce no change in the system’s ability to evolve. The correct action is to record the decision and to re-evaluate it when a method appears on a change path — which is exactly the trigger-based discipline described in section 1.6.

6.4 Refactoring toward patterns, and the order that works

Why reaching for a pattern before the extractions is the most common cause of failed refactoring, and the order that produced a working result in the audited case.

The standard advice — "refactor towards a pattern" — is correct in principle and inverted in practice, because a pattern is a named structure and you cannot apply a named structure to code that has no names. The god method of 94 lines has no responsibilities to assign to a Strategy, no subsystem to put behind a Facade, no state to model as a State. Until the extractions have produced named, single-responsibility units, "apply Strategy" has no referent, so what actually happens is a much larger edit that happens to contain some strategy-like dispatch, and it fails.

The order that works is mechanical first, pattern last, and the pattern arrives as a by-product. The three-stage sequence is: stage one, extract until every unit has a single responsibility and a name a domain expert would recognise; stage two, identify the forces (0.3) present in the extracted structure — the conditional, the indirection, the type tag, the lifecycle question; stage three, apply the pattern that the force already implies, and check whether the modern equivalent is cheaper. The critical observation is that stage two is a reading exercise, not a design exercise: the pattern is almost always already there as a shape, and naming it is what makes it maintainable.

There is one important exception to the mechanical-first rule, and it is worth stating so that the rule is not applied too broadly. When the code is new rather than legacy, the pattern should be chosen before the code is written, because there is no existing structure to be constrained by and the cost of a wrong structure is one file rather than a refactoring. The rule applies to code that exists: to code you are about to write, design first, and the pattern catalogue is a legitimate tool. The asymmetry is that writing a pattern into new code costs nothing to undo, while refactoring a pattern into old code costs the entire revalidation set.

6.5 The test harness: before, after, and what must not change

The behavioural invariant that makes a refactoring verifiable, the unit test before and after, and the three test properties that must be measured rather than assumed.

A refactoring is defined by an invariant: observable behaviour is unchanged. The word doing the work is observable, and the practical consequence is that the test suite’s job is not to assert implementation facts but to pin the set of observations a consumer could make. A test that asserts on a private field, on a call count to a collaborator, or on the specific order of two independent operations is not pinning observable behaviour; it is pinning the implementation, and it will fail during exactly the refactoring it was supposed to enable.

Three properties must be measured before and after, and a refactoring that degrades any of them has changed something it was supposed not to change. The first is suite runtime, because a refactoring that doubles the suite runtime has halved the number of refactorings the team can afford, which is a real cost even if no behaviour changed. The second is mutation score, because a test suite that does not detect a mutated operator is not protecting the refactored code, and a refactoring that reduces mutation score has quietly removed the safety net that justified it. The third is public surface count, because a refactoring that grows the public API has made the system harder to change in the future even though it has changed nothing today.

The over-fitted test is the most expensive thing in a refactoring. A test that asserts a call count to a mock is asserting the implementation, and it will fail the moment the implementation is improved — when two saves become one batched save, or when the write moves behind a queue. 6.6 Characterisation testing of legacy code

Recording what a component does rather than what it should do, the golden-output technique, and the four techniques that fail and what to use instead.

Characterisation testing answers a different question from specification testing. Specification tests assert what the system should do; characterisation tests assert what it does, so that a subsequent change can be verified against a baseline. This is the only sound way to refactor a component whose behaviour is undocumented, unspecified, or known to contain defects, and it is the technique that makes it safe to change a 40 000-line billing service that four people understand partially.

The core technique is golden-output or snapshot testing: run the component against a fixture, record the output, and thereafter assert byte-equality against the recorded output. The crucial discipline is that the baseline is not corrected when it is wrong. A characterisation suite that records a bug produces a test that fails when the bug is fixed, and the temptation to update the baseline at that moment is exactly how a characterisation suite stops characterising. The correct workflow is: fix the bug, update the baseline, and record in the commit message that the baseline change is a deliberate behaviour change — so the two are distinguishable in the history.

7 · Concurrency, State and Correctness

Concurrency is where a design that reads well sequentially fails intermittently in production. This chapter treats concurrency as a design concern rather than a language feature: what shared state costs, which mechanisms buy safety at which price, and how to structure work so that concurrency is not required to be correct.

7.1 The mutable shared state problem

Every serious concurrency bug is a shared mutable value observed or modified from more than one thread. The difficult cases are not the obvious ones — two threads incrementing a counter — but the compound ones: check-then-act, and read-modify-write across a boundary where another thread can interleave.

// The canonical failure. Both reads can return 5.
if (account.balance >= amount) {       // thread A reads 100
    account.balance -= amount;                  // thread B reads 100
    // ...both succeed. The account is debited twice.
} else {
    throw new InsufficientFunds();
}

Notice that no amount of care inside the block helps. The invariant is broken by the gap between the read and the write, and the block contains no operation that makes the pair atomic. The design answer is to make the operation atomic at the boundary, not to add care inside the body.

// Correct: the check and the debit are one indivisible operation.
account.debit(amount);   // implemented so that it cannot interleave

// In SQL, the same fix, expressed declaratively:
-- UPDATE ... WHERE balance >= amount is atomic in the database.
UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?;
-- Zero rows affected means insufficient funds. No race is possible.

Push correctness down to the layer that already has the atomicity guarantee. A database update with a predicate in the WHERE clause is atomic. A compare-and-swap in a lock-free structure is atomic. A monitor is atomic. This is almost always less code and more obviously correct than defending a check-then-act in application logic, and it moves the failure mode from a rare production race to a compile error or a constraint violation.

7.2 Atomics, immutability and the cost of each

Immutable shared state removes the problem rather than managing it: if nothing can change after construction, no sequence of interleavings produces a different result. The price is that every "change" allocates a new value, which costs memory and garbage collection.

type Account struct {
    mu     sync.Mutex
    cents  int64
    closed bool
}

func (a *Account) Debit(n int64) error {
    a.mu.Lock()
    defer a.mu.Unlock()
    if a.closed {
        return ErrClosed
    }
    if a.cents < n {
        return ErrInsufficient
    }
    a.cents -= n
    return nil
}

Do not hold a lock across a network call, a database round trip, or any operation that can block. A mutex held across an I/O call converts a slow dependency into a global stall for every thread that needs the lock, and it is a common cause of throughput collapse that appears only under load. If a critical section genuinely needs to await something, restructure so the wait happens outside the lock, or use a single-threaded actor that owns the state and performs the call itself.

    first, second := a, b
    if first.id > second.id { first, second = second, first }

    second.Lock(); defer second.Unlock()

    first.debit(n); second.credit(n)
}

Most codebases do not need a general deadlock solution because most codebases should not be holding two locks at once. 7.4 Actors, message passing and the backpressure question

An actor owns state exclusively and communicates only by receiving messages. This removes shared mutable state by construction: there is no lock, because there is no sharing. The cost is that the state is now hidden behind a message protocol, and the mailbox becomes a new kind of unbounded buffer.

// An actor: the only way in is a message, the only way out is a message.
type Counter struct {
    mailbox chan func()   // bounded, deliberately
}

func (c *Counter) Run(ctx context.Context) {
    n := 0
    for {
        select {
        case <-ctx.Done():
            return
        case msg := <-c.mailbox:
            n++
            msg(n)                 // the reply, sent synchronously
        }
    }
}

// The caller blocks when the mailbox is full. That is the backpressure.
func (c *Counter) Count() int64 {
    done := make(chan int64, 1)
    c.mailbox <- func(n int) { done <- int64(n) }
    return <-done
}

An unbounded mailbox converts a backpressure problem into a memory problem. If producers are faster than the actor, a queue that grows without limit will exhaust memory long before anyone notices, and the failure appears as an out-of-memory kill with no indication of which actor was responsible. Always bound the queue, and decide explicitly what happens when it is full: block the producer, drop the message, or shed load. Each choice is defensible; an unbounded queue is not a decision.

7.5 Concurrent work queues and the work-conserving scheduler

A work queue is the most common structure in a concurrent system, and it has a small number of parameters whose interaction determines whether it is efficient or pathological. Understanding them is more useful than knowing any particular library’s API.

// A work-conserving pool: a worker never idles while a task is waiting.
func pool[T any](tasks <-chan T, workers int, run func(T)) {
    var wg sync.WaitGroup
    wg.Add(workers)
    for i := 0; i < workers; i++ {
        go func() {
            defer wg.Done()
            for task := range tasks {
                run(task)
            }
        }()
    }
    wg.Wait()
}

// Cost is not linear in workers once a shared resource is contended.
// Measure the curve before choosing a number.
//   1 worker   1000 tasks  10.0s
//   8 workers  1000 tasks   1.4s
//  32 workers  1000 tasks   2.1s   <- more workers, worse: the database is the bottleneck

Adding workers past the point where the bottleneck is shared infrastructure makes things worse, not better. Past that point the workers spend their time contending rather than working, and latency rises while throughput falls. The correct response is to find the actual bottleneck — usually a database, a lock, or a rate-limited external API — and address it, rather than to add concurrency in front of it.

7.6 Idempotence, deduplication and exactly-once illusions

Distributed systems deliver messages at least once and execute retries on failure, so every effect that crosses a process boundary will eventually be applied more than once. Designing for this is not an optimisation; it is the difference between a system that self-heals and one that double-charges a customer.

// An idempotent operation: the same request produces the same result,
// and applying it twice is indistinguishable from applying it once.
func (s *OrderService) Place(orderID, key string) error {
    // The key is derived from the caller's intent, not from the attempt.
    existing, err := s.repo.FindByIdempotencyKey(key)
    if err == nil {
        return existing.Err()   // replay the original outcome
    }

    // The unique constraint, not a prior read, is what makes this correct.
    // Two concurrent attempts: exactly one insert succeeds.
    _, err = s.repo.Insert(Insert{OrderID: orderID, Key: key})
    if isDuplicate(err) {
        return s.waitForCompletion(key)
    }
    return err
}

-- CREATE UNIQUE INDEX uq_orders_idem ON orders (idempotency_key);
EffectIdempotent?How
Set a valueYesAssignment is naturally idempotent
Increment a counterNoStore the target value, or key on a request identifier
Append to a listNoDeduplicate on a key, or use an upsert on a unique column

Exactly-once delivery is not achievable across a network boundary. What is achievable is at-least-once delivery combined with at-most-once effect, and the second half is entirely your responsibility. Any design that claims exactly-once semantics without a deduplication mechanism somewhere is either relying on a single-process assumption or has a duplicate bug waiting to be triggered by a retry.

Adopt a default: every effect that leaves a process boundary carries an idempotency key derived from the caller’s intent, and every destination has a unique constraint on it. This costs one column and one index per table and removes an entire category of incident. The alternative is to reason about retries case by case, which does not scale past a handful of endpoints.

8.1 The interface is a contract with a cost

Every line of an interface is a promise. A function signature is a promise about what will be accepted; a return type is a promise about what will be produced; a documented exception is a promise about what can go wrong. Each promise constrains every future implementation, and unlike an implementation detail, a broken promise is a breaking change for callers.

Design the interface with the most conservative types you can live with. A concrete type can be widened to an interface later, which is easy. This asymmetry means starting concrete and abstracting on the second implementation is almost always the right sequence, and starting with a wide interface and narrowing it is a dead end.

Information leakage is the security half of the same subject. A returned error message that says pq: duplicate key value violates unique constraint "users_email_key" tells an attacker the schema. The most common interface mistake is adding a method to a public interface because one implementation needs it. Every other implementation then fails to compile, including ones you did not know existed. The rule that avoids this is to define interfaces at the point of use, not at the point of implementation, so the interface is as small as the one consumer that motivated it — and to never widen a published interface for a single implementation’s benefit.

9 · Designing for Change and for Deletion

The most expensive design decisions are not the ones that turn out to be wrong; they are the ones that make future wrongness expensive to correct. This chapter covers how to place boundaries so they can be moved, how to choose between extending and modifying, and how to design for the one change that is certain to happen — deletion.

9.1 Seams, and the cost of a boundary placed in the wrong place

A seam is a place where behaviour can be substituted without changing the code on either side. A seam is created by an interface, a function parameter, a configuration value, or an inversion of control. The value of a seam is that it is a place to test, to vary, and to replace.

Seam typeCreated byAllows you toCost
Function parameterPassing a value instead of using a globalVary behaviour per call; test without setupVery low
Interface at the consumerDepending on an abstraction you ownSwap implementations; test without a real oneOne extra type
Event or messagePublishing instead of callingDecouple in time; add behaviour without changing the publisherLoses the direct call stack
Process boundaryA network or queue callScale and deploy independentlySerialization, latency, partial failure
Table or columnSchema instead of a constantChange behaviour without a deployRuntime data dependency, harder to reason about
// A seam in the wrong place: the abstraction is at the data layer,
// but the variability is in the business rule.
type Repository interface {
    Save(Order) error
    // No seam where the rule varies, so every rule change edits Save's callers.
}

// The seam where the variability actually is.
type PricingRule interface {
    Apply(Order) Money
    Priority() int          // deterministic ordering
    AppliesTo(Order) bool
}

// Now adding a rule means adding a class, not editing the order flow.
// The repository boundary can stay concrete, because nothing varies there.

Put the seam where the variability is, not where the data is. A repository interface added by reflex adds a layer of indirection and a file to every test, and buys nothing if the storage engine is never going to change. A rule engine interface added because three promotions genuinely vary earns its cost immediately. The question to ask is not "should this be abstract" but "what is the second thing that would go here, and is it likely".

9.2 Extending versus modifying: the irreversible decision

When requirements change, a design can respond by extending — adding a new capability alongside the existing one — or by modifying the existing capability. The choice determines how many callers are affected and whether the change is reversible.

ChangeExtending is possible whenModify is unavoidable whenCost of the wrong choice
New behaviour, same conceptThe concept’s contract can express itThe concept is defined by what it excludesForced modification of many callers
New optional parameterDefaults preserve existing behaviourExisting behaviour was wrongSilent behaviour change for callers who did not pass the new value
New data on an entityIt is genuinely optional and nullableEvery instance must have itA nullable field that is always populated, forever
New subtypeThe parent is an abstractionThe parent is a concrete class with behaviourThe deep hierarchy that composition would have avoided
New storage engineThe repository interface already existsSQL leaked into the domainA rewrite instead of a swap
// Extending: a new subtype, the parent stays a contract.
interface ShippingRate { Cost(Order) Money; Eta(Order) Duration }

type FlatRate    struct{ PerKg Money }
type ZoneRate    struct{ Zones map[string]Money }
type FreeOver100 struct{}      // new, no existing code edited

// Modifying: adding a field to a struct that callers construct positionally.
// type Order struct { ID, Customer, Lines, Total }
// Adding a field breaks every unkeyed literal in the codebase.

The silent-default failure is the dangerous one. Adding a parameter with a default that reproduces the old behaviour is safe. Adding a parameter whose default is better is not: every caller that did not pass it silently changes behaviour on upgrade, with no compile error and no diff in their code. If a new default is intended to change behaviour, make it required and update every call site, so the change is visible in review.

9.3 Technical debt as interest, and how to price it

Technical debt is not a moral failing; it is a loan. The useful question is not whether the debt exists but what rate it is accruing at and what it is costing per month. A debt that costs nothing to carry and is never repaid is not debt, it is a deliberate trade.

Kind of debtExampleRateRepayment trigger
Deliberate, strategicA prototype shipped to test demandZero while it is not load-bearingWhen it becomes load-bearing
Deliberate, tacticalHard-coded config to hit a deadlineLow, one known siteWhen the config is needed in a second place
Accidental, strategicA shortcut taken without a planHigh and silentThe first time it blocks a change
Accidental, tacticalCopy-paste because of time pressureCompounding, in proportion to duplicationWhen the third copy needs a change
// Pricing duplication, the most common debt, with a real number.
//   3 copies, 200 lines each, 6 changes needed per year, 45 min per change.
//   Cost of the third copy: it did not save work, it multiplied it.
//
//   annual_tax  = (copies - 1) * changes_per_year * hours_per_change
//              = 2 * 6 * 0.75  = 9 hours per year, forever
//
//   extraction_cost = 2 hours, one time
//   break_even = 2 / 9 years
//
// Three copies is already past break-even. This is a ten-minute argument
// that closes most "we do not have time" objections.

Not all duplication is debt. Two similar things that change for different reasons are not duplication, they are coincidence, and extracting them creates a shared abstraction that must then be understood by both and changed for both. The test is whether the two change together. If they do, extract; if they do not, leave them and accept the visual similarity.

9.4 Designing for deletion, which is the only certain change

Every feature will eventually be removed. Code is written to be added, and almost no code is written to be taken out safely, which is why deletion is the most expensive routine operation in a codebase. Designing for deletion means deciding at write time what a feature depends on and what depends on it.

Obstacle to deletionCausePrevention at write time
Behaviour spread across the codebaseNo single entry pointAll behaviour behind one named function
Configuration values that outlive the featureRead from a global sourceFeature owns its own config namespace
Database state the feature wroteNo migration for removalEvery feature ships the down migration with the up
Data nobody can interpretNo record of why the columns existDocument the columns in the migration that adds them
Tests that fail after removalTests assert implementation, not behaviourTest the contract, delete the test with the feature
// Deletable: everything is reachable from one function and one migration.
//
//   routes/web.php       -> one line: $router->get('/legacy', ...)
//   app/Legacy/         -> the whole directory
//   config/legacy.php   -> one file
//   migrations/0042_add_legacy_flag.php  -> has a down() that drops it
//   tests/LegacyTest.php -> one file
//
// Total removal: 5 edits, and grep finds all of them.

// Not deletable: the same feature spread across 40 files, with 3 columns
// in a table nobody remembers, and a check in a view that references a
// config key defined in a different service's config file.

Before writing a feature, decide how it will be removed, and write the removal as a checklist. Where does it hook in? What state does it own? What configuration does it read? If answering those three questions is hard, the feature’s boundaries are unclear, and clarifying them now is cheaper than discovering them during an incident-driven removal.

9.5 Modular monoliths and the module boundary in practice

A modular monolith is a single deployable unit divided into modules that may not call each other’s internals. It is the pragmatic middle: one deployment, one database, but enforced boundaries that make later extraction possible and prevent the whole codebase from becoming a call graph with no structure.

// The rule that makes a module real: it exposes an interface, not a directory.
//
// Modules/Billing/
//   public/InvoiceRepository.php     <- other modules may depend on this
//   public/InvoiceService.php        <- and this
//   internal/TaxCalculator.php       <- and NOT this, even from the same module
//   internal/ledger/...
//
// Enforcement is a test, not a convention.
final class ModuleBoundaryTest extends TestCase {
    public function test_no_module_references_another_modules_internals(): void {
        foreach (glob('src/Modules/*/src/**/*.php') as $file) {
            $owner = $this->ownerOf($file);
            $src   = file_get_contents($file);
            preg_match_all('/Modules\\\\(\w+)\\\\\\\\/src\\\\/', $src, $m);
            foreach $m[1] as $referenced) {
                if ($referenced !== $owner) {
                    throw new RuntimeException(sprintf(
                        '%s reaches into %s internals; use its public interface',
                        $file, $referenced));
                }
            }
        }
    }
}
RuleEnforcementWhat it prevents
Modules expose a public namespaceA boundary test that greps for internal referencesGradual erosion of the boundary
Modules share a database but own their tablesA schema ownership registry, checked in reviewTwo modules changing one table’s shape
Cross-module calls go through an interfaceCode review plus the boundary testDirect reach-through
No module reads another’s configConfig namespaces, injected explicitlyHidden coupling through global configuration
Modules do not import each other’s event handlersConvention; verify by inspectionImplicit coupling through the event bus

Sharing a database between modules is the pragmatic choice and the most commonly regretted one. It is fast to start and it works until two modules want different indexes, different column types, or an independent release cadence — at which point the extraction you have been deferring becomes a project. The compromise most teams land on: share the database initially, own the tables strictly, and treat the first cross-module query as the signal to start extracting.

9.6 Recording architectural decisions so they survive people

A codebase records its decisions in two places: the code, which records what was done, and the rationale, which is usually absent. Rationale matters disproportionately because the person who could remember why a design was chosen has often left, and the next person will read the structure, assume it was arbitrary, and "fix" it.

# ADR-0021-modular-monolith.md

## Status
Accepted. Revisit when the team exceeds 12 engineers or release
cadence falls below weekly for two consecutive quarters.

## Context
Four engineers, one product, deploys several times a day, no
dedicated operations. Microservices were proposed because the
boundaries looked logical in the domain model.

## Decision
A single deployable unit with enforced module boundaries. Modules
own their tables, expose a public interface, and may not reference
another module's internals. The boundary is enforced by a test.

## Alternatives considered
- **Microservices.** Correct long-term shape, wrong cost today. No
  ops capacity, and the network boundary would have made the four
  most frequent changes — which all cross two modules — slower.
- **Layered monolith.** Rejected: horizontal layers (controller /
  service / repository) spread one change across three directories.
- **No boundaries.** Rejected: the previous codebase reached 90k lines
  with a 4,000-line file and a build that took 11 minutes.

## Consequences
- A change crossing two modules needs two pull requests. Accepted.
- Independent scaling of one module is not possible. Accepted, with
  the exit path being extraction, which the boundary makes possible.
- One database remains the ceiling. This is the constraint most
  likely to be hit first.

The "revisit when" field is the one that makes ADRs useful rather than archival. A decision recorded without a trigger becomes folklore, and folklore gets reversed by whoever notices it first and assumes it was a mistake. A decision with a stated trigger is a standing agreement that expires deliberately, and the conversation happens before the cost is paid rather than after.
