0.1 What Node.js actually is

Node.js is not a language and not a framework. It is a JavaScript runtime: one executable that embeds the V8 engine, adds a standard library, and drives all I/O through a single-threaded event loop. Every "Node feature" you meet is one of those three layers showing through.

A runtime, not a language

Node adds no syntax. The JavaScript you write in Node is the JavaScript V8 supports, which is why Node shipped optional chaining, top-level await in modules and Array.prototype.at on the same day V8 did. What Node adds is capability: objects that only make sense outside a browser. process, Buffer, require, module, fs, net, and in modern releases the fetch and WebSocket globals. It also removes things: there is no window, no document, no localStorage, and no DOM at all unless you install one.

That subtraction is the source of most beginner friction. A snippet copied from an MDN page frequently does not run, and the error is not "this is browser code" — it is ReferenceError: document is not defined. The rule to internalise early: if it touches the page, it is browser code; if it touches a socket, a file or a process, it is Node code.

What it is good at, and what it is not

Node was designed for I/O-bound concurrency: many connections or many files in flight at once, each one mostly waiting. A single process holds thousands of open sockets cheaply because a waiting socket costs a few kilobytes of state rather than an OS thread. It is not a parallel compute engine. One Node process runs your JavaScript on one thread, so a handler that spends 400 ms in a tight numeric loop stalls every other request for those 400 ms.

The classic comparison is with a process-per-request server such as PHP-FPM behind Apache. There, ten concurrent requests mean ten workers, and the OS scheduler switches between them. In Node, ten concurrent requests mean one handler function suspended ten times at its await points, resumed as their I/O completes. The first model scales with RAM and processes; the second scales with the number of pending operations, and only as long as none of them is CPU-heavy.

// smallest-useful.js - one process, many connections, no dependencies
import { createServer } from 'node:http';

const server = createServer(async (req, res) => {
  // "await" yields the event loop back to every other in-flight request
  const payload = { ok: true, method: req.method, url: req.url };
  res.writeHead(200, { 'content-type': 'application/json' });
  res.end(JSON.stringify(payload));
});

server.listen(3000, () => console.log('listening on http://localhost:3000'));

The process model in one paragraph

Each node process gets its own V8 heap, its own libuv loop, and its own four-thread libuv pool for the jobs the kernel cannot do asynchronously. Because a process cannot share that heap with another, horizontal scaling in Node means either several processes behind a load balancer (the cluster module or a process manager) or several threads inside one process for compute (worker_threads with message passing). The first chapters of this guide build the mental model, and chapter 3 makes the loop's phases concrete enough to reason about why code is slow.

A quick sanity check on any Node install: node -p "process.versions" prints the V8, libuv and OpenSSL versions Node was linked against. Two machines on the same Node major can still differ there, which is why bug reports should include it.

0.2 V8 and libuv: the two halves

Node is a C++ program that glues two large libraries together. V8 evaluates JavaScript; libuv supplies everything asynchronous the language itself does not have. Knowing which one owns a given problem explains most of Node's performance characteristics.

V8: the JavaScript half

V8 parses your source, compiles it first with the Ignition interpreter for fast startup, and promotes hot functions to machine code with the Turbofan optimising compiler. It keeps objects fast using hidden classes (shapes) and inline caches, which is why object literals with a consistent shape outperform objects whose properties are added and deleted in different orders. Its garbage collector, Orinoco, is generational: a young generation collected often and cheaply (the scavenger), and an old generation collected rarely and more expensively (mark-compact).

V8 knows nothing about files, sockets, timers or the process. It exposes one entry point into the runtime and one out, and the rest of Node is a set of C++ bindings that expose native capability as JavaScript objects. That boundary is why a blocking native call is catastrophic in a way a slow pure-JS function is not: it blocks the only thread that could have run V8's microtask queue.

libuv: the asynchronous half

libuv is a portable C library that presents one event-loop API over the platform's native mechanism — epoll on Linux, kqueue on macOS and the BSDs, IOCP on Windows, and increasingly io_uring on modern Linux kernels. It owns timers, TCP and UDP sockets, pipes, TTYs, signals, child processes and the file-system interface.

It also owns a thread pool, and the pool is the part people forget. The kernel can wait on a socket asynchronously, but a plain read(2) on a file cannot be waited on in the same way on every platform, and neither can getaddrinfo. So libuv runs those on a small fixed pool of threads — four by default — set with the UV_THREADPOOL_SIZE environment variable. Everything on that pool is still async to your JavaScript, but they compete for four slots.

# shell - raise the libuv pool before Node starts; it is read once, at init.
# Useful when a process does many concurrent fs or dns operations.
UV_THREADPOOL_SIZE=16 node server.js

# prove the pool size from inside a running process
node -p "process.env.UV_THREADPOOL_SIZE ?? 'default (4)'"
The thread pool is not a licence to parallelise CPU work. Cryptography tasks such as pbkdf2 or scrypt do run on the pool, so an authentication endpoint under load can exhaust its four threads and queue every other file read behind it. Watch for this pattern: slow logins together with slow static file serving almost always means a saturated pool, and the fix is either an async-friendly alternative or a larger UV_THREADPOOL_SIZE.

How the halves meet

Trace one call. JavaScript reaches fs.promises.readFile, which lands in a C++ binding, which asks libuv to read the file. libuv either submits to the thread pool or registers interest with the kernel, and returns immediately; the JavaScript stack unwinds and V8 goes back to the loop. When the bytes arrive, libuv signals the loop, the loop runs the completion, and the binding resolves the promise, which schedules a microtask. V8 then runs that microtask — on the event-loop thread, in the correct order — and your .then body finally executes.

Every asynchronous API in Node follows that shape. The differences between them are only which libuv subsystem handles the wait, and whether the completion is delivered as a callback, a promise or an event.

0.3 Installing Node: nvm, fnm and Corepack

Install Node once per version, not once per machine. A version manager lets a project pin the exact runtime it was written for; Corepack does the same job for the package manager.

Version policy: what a number means

Node releases a new major every six months, in April and October. Odd majors are Current for their six-month life and are then abandoned. Even majors graduate to Active LTS and are supported for roughly thirty months, with security-only Maintenance at the end. In autumn 2026 the Active LTS line is Node 24 and Node 26 has just become Current; Node 22 is in Maintenance.

Production should run an even major. Libraries should test the current LTS and the one before it, because that is the range your users install. New language features — native TypeScript type stripping, the stable test runner, require() of ES modules — arrive on Current first and become safe to rely on when they reach LTS.

0.4 The REPL and the command-line flags

The node binary is both an interpreter and a task runner. Knowing a dozen flags turns it into a competent replacement for a small build script.

The REPL is a real terminal app

Run node with no arguments and you get a read-eval-print loop with tab completion, a history file, and a _ variable holding the last result. It supports top-level await, which makes it the fastest way to test an API call or a promise chain. .editor switches to multi-line input until you press Ctrl+D, and .load ./scratch.js evaluates a file into the current session so its bindings are available afterwards.

Scripts with shebangs

A file beginning #!/usr/bin/env node and marked executable runs as a command on Unix, and on Windows it runs as long as the extension is associated with Node. A CLI is then just a bin entry in package.json. Because the interpreter is chosen by env, the shebang respects whatever node is first on the user's PATH — one more reason to pin the version in the manifest rather than in the script.

// bin/count.js
#!/usr/bin/env node
// process.argv[0] is the node binary, [1] is this file, [2..] are the args
import { readdir } from 'node:fs/promises';

const dir = process.argv[2] ?? '.';
const entries = await readdir(dir);
console.log(`${entries.length} entries in ${dir}`);
Node 24 strips TypeScript types natively: it will run app.ts directly as long as the file uses only erasable syntax — no enum, no namespace, no parameter properties. Erased types are gone before evaluation, so there is no type checking; run tsc --noEmit separately for that.

0.5 Package managers: npm, pnpm, yarn and Bun

All four read the same registry and the same package.json. They differ in how they lay files on disk, which determines install speed, disk usage and — crucially — which dependencies your code is allowed to import.

npm and the lockfile

npm is bundled with Node. npm install resolves the version ranges in package.json, writes package-lock.json, and installs a mostly flat tree into node_modules. The lockfile is the contract: npm ci deletes node_modules and installs exactly what the lockfile records, failing if the manifest and lockfile disagree. CI and Docker builds should always use ci, never install, so that two builds of the same commit cannot pick up different transitive versions.

pnpm: content-addressed and strict

pnpm keeps one copy of every package version in a global content-addressed store and hard-links it into each project's node_modules/.pnpm. Because files are linked rather than copied, ten projects using the same React version consume the disk once. It also does not hoist: your code can import only what your own package.json declares, which surfaces "phantom dependencies" — packages that happened to be installed because a dependency needed them — as a MODULE_NOT_FOUND error at development time instead of a production incident.

# shell
pnpm add express fastify           # runtime deps
pnpm add -D vitest typescript      # dev deps
pnpm run -r build                  # run "build" in every workspace package
pnpm --filter @acme/api test       # run "test" in one package only
pnpm dlx create-vite@latest        # one-shot fetch (like npx)

Yarn and Bun

Yarn 4 modernised the toolchain: yarn dlx for one-shot binaries, Yarn PnP to resolve from a zip cache with no node_modules at all, and yarn constraints to enforce consistent versions across a monorepo. Bun bundles a runtime, a package manager, a test runner and a bundler; its own test runner and HTTP server are fast, but "works with Bun" and "works under Node" are different claims, so a library targeting Node should still be tested on Node.

Running npm install in a pnpm workspace deletes the symlink farm and rewrites the lockfile, and the resulting node_modules has a different resolution shape than every other machine. Commit exactly one lockfile, delete the others, and let the packageManager field enforce the choice.

1.1 CommonJS: require and module.exports

CommonJS is Node's original module system. It is synchronous, cached, and evaluated as a plain function body, and understanding the wrapper function explains __dirname, the cache and the circular-import behaviour at once.

Every file is wrapped in a function

Before evaluating a file, Node wraps its source in a function call. That is why top-level var and function declarations never leak onto the global object, and why __filename and __dirname exist without being declared anywhere: they are parameters. The wrapper is effectively:

// what Node conceptually runs for every .cjs file
(function (exports, require, module, __filename, __dirname) {
  // ...your file, verbatim...
});
// invoked as: fn.call(module.exports, module.exports, require, module, filename, dirname)

Two consequences fall out of that single line. First, this at the top level of a CommonJS module is module.exports, not the global object. Second, because the wrapper is a normal function call, require can be used anywhere — inside an if, inside a loop, inside a handler — with no hoisting of any kind.

The require cache is the module's identity

require() resolves the specifier to an absolute path, and checks require.cache[absolutePath]. A hit returns the cached exports object and skips evaluation entirely. A miss creates a fresh Module, inserts it into the cache before running the body — the crucial detail — and then runs the wrapper. Inserting first is what makes circular imports terminate rather than loop forever: the second module sees a partial exports object instead of recursing.

// a.js
exports.name = 'a';          // visible to b.js, which is required next
const b = require('./b');    // b.js has already run its own top half
exports.friend = b.name;     // 'b'

// b.js
exports.name = 'b';
const a = require('./a');    // cache hit: gets a's PARTIAL exports
console.log(a.name);         // 'a'  - exported before the require
console.log(a.friend);       // undefined - assigned after the cycle

// app.js
const a = require('./a');
console.log(a.friend);       // 'b'
console.log(require.cache[require.resolve('./a')] === require.cache[require.resolve('./a')]); // true
A circular dependency almost never throws. It silently hands one side a half-populated object, and the failure appears far from the cause as undefined is not a function. Fix it by moving the shared value into a third module, or by requiring lazily inside the function that needs it rather than at the top of the file.

module.exports versus exports

exports is just a local alias initialised to the same object as module.exports. Mutating it works, because it changes the shared object. Reassigning it does not, because the alias now points somewhere else and Node still returns module.exports. Mixing the two styles in one file is the classic way to lose an export.

// works: mutating the shared object
exports.add = (a, b) => a + b;

// breaks: rebinds the local alias, Node ignores it
exports = { add: (a, b) => a + b };

// works: assigning the module's real export
module.exports = { add: (a, b) => a + b };

// also works, and is what most authors mean
module.exports.add = (a, b) => a + b;

// lesson: use ONE style per file. Either always "module.exports =" for a
// single value, or always "exports.name =" for a namespace of named exports.

1.2 ES modules in Node

ES modules are the language's own module system, and Node supports them natively. The two systems interoperate, but at specific and learnable boundaries — and the differences that matter are semantic, not just syntactic.

How Node decides which system a file uses

The extension is the first signal: .mjs is always an ES module and .cjs is always CommonJS, regardless of any manifest. For a .js file, Node walks up from the file to the nearest package.json and reads its type field — "module" makes .js an ES module, the default ("commonjs" or absent) keeps it CommonJS. Code passed with -e or over stdin is CommonJS unless --input-type=module is given. Dynamic import() is available from CommonJS, so a CommonJS file can always reach an ES module; the reverse is not true of require in every case.

// package.json - the switch that redefines every .js file in the tree
{ "type": "module" }

// then, in the same directory:
//   index.js   -> ES module  (import / export)
//   legacy.cjs -> CommonJS   (require / module.exports), always
//   helper.mjs -> ES module, always, even in a CommonJS package

// a CommonJS file can always reach an ES module dynamically
const { default: chalk } = await import('chalk');   // top-level await? no ->
(async () => { const m = await import('./esm-only.mjs'); m.run(); })();

What actually differs, beyond the syntax

An ES module is parsed and its import graph resolved before any of it runs, so imports are hoisted — a binding is available above the line that names it, and a module cannot be conditionally imported at the top level. Bindings are live: an importer sees the exporter's current value, not a copy taken at import time, which also means it cannot assign to it. Strict mode is always on and this at the top level is undefined, not module.exports. There is no require, __dirname or __filename; the equivalents are import.meta.url, import.meta.dirname and import.meta.filename.

// live bindings: the importer tracks the exporter, it does not snapshot it
// counter.mjs
export let count = 0;
export function bump() { count++; }
// app.mjs
import { count, bump } from './counter.mjs';
bump();
console.log(count);          // 1 - a live view, not a stale copy

// the __dirname replacements
import { fileURLToPath } from 'node:url';
console.log(import.meta.dirname);                    // Node 21.2+
const here = fileURLToPath(new URL('.', import.meta.url));  // portable form

// when you genuinely need require() from an ES module
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const legacy = require('./legacy.cjs');

Interop in both directions

Importing CommonJS from ESM always works: the default export is that module's module.exports, and named exports are offered when a static analyser can find them — which it can for the common patterns exports.foo = ... and module.exports = { foo }, and cannot for a computed assignment. The other direction, require() of an ES module, became available once the module graph contains no top-level await; a module that does use top-level await cannot be required synchronously and fails with a distinct error rather than hanging.

1.3 package.json and the resolution algorithm

A specifier like './utils' or 'lodash/fp' is resolved by a fixed sequence of rules. Knowing the sequence is what turns "module not found" from a mystery into a lookup.

The fields that change behaviour

FieldEffect
name, versionIdentity, and the self-reference key for import 'my-pkg/x' inside the package
type"module" makes .js an ES module; absent means CommonJS
exportsPublic subpaths and the conditions under which each is chosen; everything else becomes unreachable
importsPrivate aliases beginning with #, usable only inside the package
mainLegacy entry point, still the fallback when there is no exports

enginesAdvisory Node version constraint; enforced only if the installer is told to enforce it
binCommand name to file path; the file needs a shebang and, on Unix, an executable bit

The resolution walk

A specifier is classified first. A node: prefix or a bare builtin name resolves to the runtime itself. A URL, or a specifier beginning with ./, ../ or /, resolves as a path relative to the importing file. Anything else is a bare specifier, and Node searches node_modules starting in the importing file's directory and walking up through every parent — which is why a nested node_modules can shadow the root one, and why a phantom dependency works on one machine and not another.

// resolve without executing, to see exactly which file wins
node -e "console.log(require.resolve('express'))"
// -> /srv/app/node_modules/express/index.js

// from an ES module, using the standard API
import { createRequire } from 'node:module';
createRequire(import.meta.url).resolve('express');

// the resolution order for a bare specifier, in plain terms:
//   1. node_modules/express/package.json  "exports"
//   2. node_modules/express/package.json  "main"
//   3. node_modules/express/index.js
//   4. repeat the whole thing in the parent directory, up to the filesystem root

The exports map is a contract, in both directions

When a package declares exports, that map becomes the complete public surface: a file that exists on disk but is not listed is unreachable, and the error is an explicit ERR_PACKAGE_PATH_NOT_EXPORTED rather than a silent success. Keys must start with ./, wildcards cover whole directories, and conditions are evaluated in the order they are written, so default must come last or it swallows everything after it.

// exports: separate the ESM and CommonJS entries, and hide the internals
{
  "name": "acme-utils",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",   // first: type resolution for TS
      "import": "./dist/index.js",    // ESM consumers
      "require": "./dist/index.cjs",  // CommonJS consumers
      "default": "./dist/index.js"    // last resort - keep it last
    },
    "./math/*": "./dist/math/*.js",   // subpath pattern
    "./package.json": "./package.json" // many tools still ask for this
  },
  "imports": { "#internal/*": "./src/internal/*.js" },
  "files": ["dist", "README.md"]
}
Without an exports map, every file in the package is importable, so an internal helper becomes de-facto public API and cannot be moved without breaking someone. Add exports deliberately, and include "./package.json" because a surprising number of tools read it at runtime.

1.4 Workspaces and monorepos

A workspace is a package developed in place rather than fetched from a registry. The manager links it into the root install, so an edit in one package is visible to another with no publish step.

npm workspaces

Listing globs under workspaces in the root manifest is the whole setup. npm then installs a single lockfile at the root and hoists shared dependencies into the root node_modules, linking each workspace by its package name. Every command can be scoped to one workspace with -w or to all of them with --workspaces. Hoisting is convenient and slightly dishonest: since dependencies are usually reachable from the root, a package can import something it never declared, and the mistake surfaces only when the package is used outside the monorepo.

// root package.json
{
  "name": "acme",
  "private": true,
  "workspaces": ["packages/*", "apps/*"],
  "scripts": {
    "build": "npm run build --workspaces --if-present",
    "test": "npm run test --workspaces --if-present"
  }
}

# shell
npm install                              # one root lockfile, all workspaces linked
npm install zod -w @acme/api             # add a dep to one workspace
npm run build -w @acme/api               # run a script in one workspace
npm run test --workspaces --if-present   # every workspace that defines "test"
npm ls --workspaces --depth=0            # see the tree per workspace

pnpm workspaces and the version problem

pnpm declares its workspace through pnpm-workspace.yaml and does not hoist by default, so a workspace can import only what it declares — the phantom-dependency class disappears. It also adds two things npm lacks: the workspace:* protocol, which expresses "use the local copy, whatever its version", and catalogues, which pin one version per dependency across every workspace so react or typescript cannot drift between packages.

# pnpm-workspace.yaml

Versioning and releasing

Independent versions per package are the honest model for a monorepo, and automation is what makes them survivable. A changeset workflow records a human intent — "this is a patch to @acme/api, a minor to @acme/web" — in a committed file, and a release job consumes the accumulated intents to bump versions, write changelogs and publish. When CI publishes, request provenance so the registry records which workflow and commit produced the artefact; it is the one supply-chain control that a consumer can verify without trusting you.

# shell - changesets, the common monorepo release flow

1.5 SemVer and version ranges

Semantic versioning is a compatibility contract: the numbers promise what is safe to upgrade. Ranges are the expression of that trust, and the lockfile is what keeps an expressed range from changing under your feet.

What the three numbers promise

A version is major.minor.patch. A patch release fixes a defect without changing the API, a minor release adds functionality without breaking it, and a major release may break anything. Those are promises about the public API, and here is the catch: a package that does not declare an exports map has no defined public API, so any internal change can be a breaking one. A version below 1.0.0 is explicitly exempt — semver makes no promise about stability there, which is why depending on a 0.x package at a caret range is genuinely risky.

2.1 Callbacks and the error-first convention

The callback is Node's original async API shape and it is still underneath everything: promises, streams and events all resolve into callbacks eventually. Knowing why the convention looks the way it does explains the promise APIs built on top of it.

The Node callback style

Every core callback receives the error as its first argument and the result as its second. The error is null when there is no error. The ordering is not cosmetic: it makes the "did it fail?" check the first thing in the body, and it lets the caller distinguish a failure from a legitimate falsy result such as 0, '' or false.

// error-first, in its natural habitat
import { readFile } from 'node:fs';

readFile('./config.json', 'utf8', (err, text) => {
  if (err) {
    // ALWAYS return after calling back with an error, or the handler
    // continues with an undefined "text"
    return console.error('read failed:', err.message);
  }
  console.log(JSON.parse(text).port);
});

Why "call back exactly once" is a real rule

A callback is a continuation, and calling it twice means the rest of the program runs twice. Libraries that guard against this use a flag, and the standard pattern is to check it at the top of every exit path. This is also why a thrown exception inside an asynchronous callback cannot be caught by the caller's try: by the time the callback runs, the caller's stack is long gone. Node reports such a throw as an uncaught exception and terminates the process unless a handler is installed.

// a defensive "once" wrapper, the pattern the core modules use internally
function once(fn) {
  let called = false;
  return (...args) => {
    if (called) return;
    called = true;
    fn(...args);
  };
}

// the caller's try/catch cannot see an async throw
try {
  setTimeout(() => { throw new Error('boom'); }, 0); // NOT caught here
} catch (err) {
  console.log('never runs');
}
// instead, handle it at the top level
process.on('uncaughtException', (err) => {
  console.error('fatal:', err);
  process.exitCode = 1;   // let in-flight I/O finish, then exit
});
Prefer node:util's promisify over hand-wrapping core callbacks: const read = promisify(fs.readFile) produces a promise-returning function with correct rejection semantics, including the util.promisify.custom symbol that a library can use to expose a better promise API than a mechanical wrap.

Callback APIs that are still worth knowing

Promises did not replace every callback. fs.watch takes a listener, sockets and servers are event emitters, and child_process reports through events with no promise form. util.promisify converts error-first callback functions only — it cannot promisify an emitter, and wrapping one by hand is a common source of a promise that never settles. The skill worth developing is recognising which style an API uses before writing the call, rather than after a test hangs.

2.2 Promises and the microtask queue

A promise is a placeholder for a future value that has three states and one-way transitions. The mechanics matter because then callbacks never run synchronously — they are always queued as microtasks, which is why ordering surprises appear in real code.

States, and the two things you can attach

A promise starts pending, then becomes either fulfilled with a value or rejected with a reason, and never changes again. Attaching handlers after settlement still works: the callbacks are queued immediately. The executor function you pass to new Promise runs synchronously, so anything before its first await inside it happens before the constructor returns.

const p = new Promise((resolve, reject) => {
  console.log('1 executor runs immediately');
  resolve('done');
});

p.then(v => console.log('3 handler:', v));
console.log('2 synchronous code after construction');
// prints 1, 2, 3 - the handler is always a microtask, never inline

Combinators choose a failure policy

There are four combinators and they differ only in how they treat rejection and how they collect results. Picking the wrong one is the most common promise bug in server code.

CombinatorResolves withOn first rejection
Promise.allArray of values, input orderRejects immediately; other work continues but is unobserved
Promise.allSettledArray of {status, value|reason}Never rejects
Promise.raceFirst settled, fulfilled or rejectedRejects if that first one rejected
Promise.anyFirst fulfilledRejects with AggregateError only if all fail
// fan-out with a partial-failure policy that matches the business rule
const tasks = ['a', 'b', 'c'].map(name => fetch(`https://api.example.com/${name}`));

const results = await Promise.allSettled(tasks);
const ok = results.filter(r => r.status === 'fulfilled').map(r => r.value);
const failed = results.filter(r => r.status === 'rejected').map(r => r.reason);

if (failed.length && ok.length === 0) throw new AggregateError(failed, 'all upstreams down');
console.log(`${ok.length} ok, ${failed.length} failed`);
A rejected promise with no handler is reported as unhandledRejection. In Node 15 and later the default is to terminate the process, which is deliberate: a silent swallowed failure is worse than a crash. Always attach a .catch to fire-and-forget promises, and at minimum log it.

2.3 async/await without the traps

async/await is promise syntax that reads like synchronous code. It does not make anything faster, and two mistakes make it dramatically slower: awaiting inside a loop, and forgetting that a function declared async always returns a promise.

What the keywords actually do

An async function always returns a promise; a returned value is wrapped with Promise.resolve and a thrown value becomes a rejection. await suspends the function, schedules the remainder as a microtask once the awaited promise settles, and yields control back to the event loop in the meantime. That last part is the whole benefit: other work runs while this function waits.

// sequential - correct when each step needs the previous result
async function slow() {
  const user = await getUser(id);         // ~50ms
  const orders = await getOrders(user.id); // ~50ms
  return orders;                            // ~100ms total
}

// concurrent - correct when the calls are independent
async function fast() {
  const [user, config] = await Promise.all([getUser(id), getConfig()]);
  return user;                              // ~50ms total
}

Awaiting in a loop

An await inside a for loop runs the iterations strictly one after another. When the iterations are independent, that costs the sum of all latencies instead of the maximum. The fix is to start the work concurrently and then await it together, but the naive version has a second bug: mapping to promises inside Promise.all starts every request at once, which can exhaust sockets or a rate limit.

// a small concurrency limiter - run at most N at a time, in order
async function mapLimit(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;
  async function run() {
    while (next < items.length) {
      const i = next++;
      results[i] = await worker(items[i], i);
    }
  }
  const pool = Array.from({ length: Math.min(limit, items.length) }, run);
  await Promise.all(pool);
  return results;
}

await mapLimit(urls, 8, url => fetch(url).then(r => r.json()));
return await promise inside a try is intentionally different from return promise. The await version catches a rejection in the local catch; the plain version lets it escape and skips the finally. Outside a try, the await only adds a tick and is noise — which is why linters flag it in one place and require it in the other.

Async generators and for await

An async generator is a pull-based sequence: the consumer asks for the next value and the producer resumes, which gives consumer-driven flow control with no library. for await (const x of gen()) consumes one value at a time and applies back-pressure naturally by simply not asking for more. When the loop exits early, the runtime calls the generator's return(), so a finally block inside it runs — the correct place to release a lock or close a cursor. Async iterables interoperate with streams both ways, which makes them the bridge between ordinary async code and a streaming pipeline.

2.4 Timers, immediacy and ordering

Node has four scheduling primitives, and they do not fire in the order their names suggest. Two of them do not belong to the event loop's timer phase at all.

The four primitives

APIRunsBelongs to
process.nextTick(fn)Before any other I/O, after the current operationNot a timer; a per-operation microtask-like queue
queueMicrotask(fn)After the current stack, with promise callbacksThe V8 microtask queue
setImmediate(fn)In the check phase, after poll completesThe event loop
setTimeout(fn, 0)In the timers phase, clamped to ~1msThe event loop

process.nextTick is misnamed and predates microtasks. Its queue is drained after the current JavaScript operation and before the loop continues, and it is drained completely — a nextTick that schedules another nextTick defers all pending I/O indefinitely. Use it to let a caller attach handlers before you call them, and use queueMicrotask when you mean "as soon as possible" without starving I/O.

// ordering demonstration - run it, the result is stable across platforms
setTimeout(() => console.log('setTimeout'));
setImmediate(() => console.log('setImmediate'));
queueMicrotask(() => console.log('queueMicrotask'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise.then'));
console.log('sync');
// sync, nextTick, promise.then, queueMicrotask, then setTimeout/setImmediate
// (the last two swap only when the loop starts inside an I/O callback)

Cancelling and ref-ing timers

A pending timer keeps the event loop alive, so a server that sets a repeating timer never exits on its own. timer.unref() detaches it from the loop's liveness count without cancelling it; ref() reattaches. For repeated work, setInterval drifts because it schedules the next call from the start of the previous one; a self-rescheduling setTimeout keeps a fixed gap and lets you cancel cleanly.

// a drift-free repeating task that can be stopped, plus a self-expiring guard
function every(ms, fn) {
  let timer;
  const tick = async () => {
    try { await fn(); } finally { timer = setTimeout(tick, ms); }
  };
  timer = setTimeout(tick, ms);
  return () => clearTimeout(timer);
}

const stop = every(1000, async () => {
  const res = await fetch('https://example.com/health');
  if (!res.ok) throw new Error(`health ${res.status}`);
});

// keep the process exit-able while this job is only a background nicety
setTimeout(stop, 30_000).unref();
Timer callbacks with a large numeric delay overflow the 32-bit signed millisecond counter and fire after roughly 1 ms. Cap long waits explicitly, and for delays beyond the maximum of about 24.8 days chain several timers instead of passing one enormous value.

2.5 AbortController: cancelling anything

Cancellation used to be per-API. Since the AbortSignal interface was adopted across the platform, one controller can cancel a fetch, a stream read, a database driver and a custom job — and the standard reason distinguishes a timeout from a user abort.

One signal, many consumers

Create a controller, pass controller.signal to everything cancellable, and call controller.abort(reason) once. Every consumer rejects with the same reason — or, in well-behaved APIs, throws or emits it. AbortSignal.timeout(ms) builds a signal that aborts itself, and AbortSignal.any([...]) merges several so a request can be cancelled by either a client disconnect or a deadline.

// cancel a slow dependency when the caller has already given up
async function fetchDigest(url, { timeoutMs = 2000 } = {}) {
  const signal = AbortSignal.any([
    AbortSignal.timeout(timeoutMs),
    incomingRequest.signal,   // aborts when the client disconnects
  ]);

  const res = await fetch(url, { signal });
  if (!res.ok) throw new Error(`upstream ${res.status}`);
  return res.json();
}

// abort() carries a reason, which is exactly the place to say WHY
const ctrl = new AbortController();
setTimeout(() => ctrl.abort(new Error('deadline exceeded')), 500);
try {
  await fetchDigest('https://api.example.com/slow', { signal: ctrl.signal });
} catch (err) {
  // err is the abort reason, not a generic AbortError
  console.error(err.message); // "deadline exceeded"
}

Making your own code cancellable

A well-behaved async function accepts an optional signal, checks it before starting expensive work, and wires an abort listener to whatever it must tear down. This is the single most valuable interface contract to copy across a codebase: a caller that can cancel is a caller that can enforce a timeout, and unenforced timeouts are how request queues become outages.

// the shape to copy: check early, listen, clean up, rethrow the reason
function delay(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);
    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);
    function onAbort() {
      clearTimeout(timer);
      reject(signal.reason);
    }
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

await delay(5000, { signal: AbortSignal.timeout(100) }); // rejects quickly
Hand the same signal to every layer — HTTP client, database driver, stream — and a single abort() unwinds the whole call tree. This is far more reliable than timeout logic duplicated at each hop, because the layers that never received a signal are exactly the ones that keep working after everyone stopped caring.

Signals reach more than fetch

AbortSignal is not a fetch feature; it is a convention that the core modules have adopted widely. fs.promises operations accept a signal, the promise-based timers accept one, stream/promises' pipeline and finished accept one, and most database and queue clients accept one on every call. A service that threads a single signal from the HTTP request down through every layer gets request cancellation and timeouts for free, and the layers that were left unwired are exactly the ones that keep working after the client has gone away.

3.1 The phases of one loop iteration

The event loop is not a queue of callbacks. It is a small state machine that cycles through named phases, and each phase drains its own queue before the loop moves on. Which phase a callback is queued in is what explains the ordering you observe.

The six phases in order

PhaseWhat runs
timerssetTimeout and setInterval callbacks whose deadline has passed
pending callbacksDeferred system-level callbacks, such as a TCP error delivered late
idle, prepareInternal to libuv; not used by ordinary JavaScript
pollRetrieves new I/O events and runs most I/O callbacks; blocks here when idle
checksetImmediate callbacks, immediately after poll
close callbacksclose events on sockets and handles

The poll phase is where the loop spends most of its time, and it is the only phase that may block. If there are no pending timers, no setImmediate callbacks and nothing else to do, libuv waits there for I/O to arrive rather than spinning. That is why a Node process sits at 0% CPU while holding a thousand idle sockets.

Why the order is not the order you wrote

Each phase drains its own queue completely before handing over to the next, so a callback that schedules another callback of the same kind runs both in the same phase. Between one callback and the next inside a phase, and again between phases, Node drains the two microtask queues: first process.nextTick, then promise callbacks. Nothing from the next phase runs until both are empty.

// the classic ordering puzzle, explained by the phase table
const { readFile } = require('node:fs');

setTimeout(() => console.log('timers'), 0);
setImmediate(() => console.log('check'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('microtask'));

readFile(__filename, () => {
  // we are now INSIDE the poll phase, so the check phase is next
  setTimeout(() => console.log('timers (from I/O)'), 0);
  setImmediate(() => console.log('check (from I/O)'));
});
// nextTick, microtask, then timers/check (order may swap at startup),
// then "check (from I/O)" before "timers (from I/O)" - deterministically
The setTimeout(fn, 0) versus setImmediate order is non-deterministic when scheduled from the main module, because the process may reach the timer phase before or after the poll phase depending on how long the module took to load. Inside an I/O callback it is fully determinate: setImmediate always wins.

What keeps the loop alive

The loop exits when there is nothing left to wait for: no active timers, no listening servers, no open handles, no pending requests, and no work on the microtask queues. A promise alone does not keep the process alive — a promise awaiting a timer does, because the timer is the handle. Diagnosing "my process will not exit" is always the same question: which handle is still referenced? process.getActiveResourcesInfo() answers it directly.

// find out exactly what is holding the process open
console.log(process.getActiveResourcesInfo());
// e.g. [ 'TCPServerWrap', 'Timeout' ]

const server = require('node:http').createServer();
server.listen(0);
console.log(process.getActiveResourcesInfo()); // [ ..., 'TCPServerWrap' ]
server.unref();                                 // stop counting it as liveness
server.close();                                 // and then release it for real

3.2 nextTick, microtasks and starvation

Two queues run outside the phases, both drained to empty before anything else happens. The distinction between them is small in API terms and enormous in failure modes, because a queue that is drained to empty can be kept non-empty forever.

Two queues, strict priority

After every callback and at every phase boundary Node runs the process.nextTick queue to exhaustion, then the V8 microtask queue — which holds promise reactions, queueMicrotask callbacks, and await resumptions. Only then does the loop advance. The ordering is not "approximately"; it is checked at every yield point in the loop.

// nextTick always beats a promise microtask queued in the same turn,
// regardless of which line comes first
Promise.resolve().then(() => console.log('microtask'));
process.nextTick(() => console.log('nextTick'));
// nextTick, microtask

// but a promise reaction queued from inside nextTick runs after the whole
// nextTick queue has drained - the queues are not interleaved
process.nextTick(() => Promise.resolve().then(() => console.log('from nextTick')));
process.nextTick(() => console.log('second nextTick'));
// second nextTick, from nextTick

Starvation is the failure mode

Because both queues are drained to empty, a self-scheduling microtask never lets the loop proceed. Timers never fire, sockets are never read, and the process appears hung at 100% CPU while continuing to answer nothing. The same bug in the I/O phase merely makes the program busy; in the microtask queue it makes the program permanently deaf.

// this process never handles a request, and never exits
function spin() {
  process.nextTick(spin);
}
spin();
//  also fatal as a promise chain:
//  (function loop() { Promise.resolve().then(loop); })();

// the correct shape: yield to the loop periodically in long computations
async function chunkedWork(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    if (i % 500 === 0) await new Promise(r => setImmediate(r)); // real break
  }
}
Reach for setImmediate, not setTimeout(fn, 0), when you need the loop to advance. setImmediate is guaranteed to run in the check phase of the current iteration; a zero-delay timeout is clamped to about a millisecond and may be deferred by one full loop. In a large library setImmediate is also substantially cheaper.

Measuring a runaway microtask loop

A recursive process.nextTick does not overflow the stack the way recursive function calls do, because each turn unwinds before the next is scheduled. There is no RangeError and no warning — only a process that answers nothing while burning a core. The practical guard is a counter in the loop itself: after a few tens of thousands of turns, throw, because a legitimate deferred chain is never that long. Pair it with the event-loop delay histogram, which is the only signal that distinguishes a microtask spin from a genuinely large computation.

3.3 Detecting and fixing a blocked loop

Blocking the loop is Node's defining performance failure: one slow synchronous operation degrades every concurrent request because there is only one thread to run them on. The fix is always either to make the work asynchronous or to move it off the loop entirely.

What "blocked" means in numbers

A function that takes 80 ms of CPU on a server handling 1,000 requests per second adds 80 ms of latency to every request that arrives during it — not just its own. At scale, the queue grows faster than it drains and latency becomes unbounded. The right measurement is event-loop delay: how late the loop is compared with its schedule, sampled continuously.

// monitor event-loop delay, exported for scraping, negligible overhead
import { monitorEventLoopDelay } from 'node:perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  const p99 = histogram.percentile(99) / 1e6; // nanoseconds -> ms
  if (p99 > 100) console.warn(`event loop p99 delay: ${p99.toFixed(1)}ms`);
  histogram.reset();
}, 10_000).unref();

The usual culprits

Four patterns account for the overwhelming majority of blocked loops. JSON.parse and JSON.stringify on multi-megabyte payloads, which are synchronous and proportional to size. Catastrophic regex backtracking, where a pattern such as /(a+)+$/ explodes exponentially on input that nearly matches. Synchronous filesystem calls — any *Sync method — inside a request. And large numeric or crypto work such as pbkdf2 with a very high iteration count or image decoding.

// the same validation written so a hostile string cannot hang the process
const BAD = /^(a+)+$/;                    // exponential on "aaaaaaaaaaaaaaaaaaaaaaaaX"
const GOOD = /^a+$/;                      // linear

BAD.test('a'.repeat(30) + 'X');           // effectively never returns

// bound the input BEFORE the pattern sees it, whatever the pattern is
function safeTest(re, value, maxLen = 64) {
  if (typeof value !== 'string' || value.length > maxLen) return false;
  return re.test(value);
}

Getting the work off the thread

Use the async form for anything the kernel or libuv can wait on: fs.promises.readFile instead of fs.readFileSync, crypto.randomBytes instead of randomBytesSync. For genuine CPU work — parsing large documents, resizing images, computing hashes over megabytes — no async API exists, because the work is computation rather than waiting. That is the case for a worker thread, covered next, or for a separate service reached over HTTP.

3.4 worker_threads: real parallelism

A worker is a separate V8 isolate on a separate OS thread inside the same process. It has its own heap and its own event loop, so it can burn CPU without touching the main thread's latency — at the cost of message-passing instead of shared variables.

The model

Start a worker from a file or with eval: true for a string. Data crosses the boundary by structured clone: objects, arrays, typed arrays and Maps survive, but functions, class prototypes and DOM-like objects do not. Expensive buffers can be moved rather than copied by listing them in the transfer list, after which the sender's ArrayBuffer is detached. Genuine sharing is possible through SharedArrayBuffer plus Atomics, and only there.

// hash-worker.js
import { parentPort, workerData } from 'node:worker_threads';
import { createHash } from 'node:crypto';

parentPort.on('message', ({ id, buffer }) => {
  const digest = createHash('sha256').update(buffer).digest('hex');
  // transfer the buffer back instead of copying it
  parentPort.postMessage({ id, digest }, [buffer.buffer]);
});

// main.js
import { Worker } from 'node:worker_threads';

const worker = new Worker(new URL('./hash-worker.js', import.meta.url), {
  workerData: { algo: 'sha256' },
});

function hash(buf) {
  return new Promise((resolve, reject) => {
    const onMessage = ({ id, digest }) => { cleanup(); resolve(digest); };
    const onError = (err) => { cleanup(); reject(err); };
    function cleanup() {
      worker.off('message', onMessage);
      worker.off('error', onError);
    }
    worker.on('message', onMessage);
    worker.on('error', onError);
    worker.postMessage({ id: 1, buffer: buf }, [buf.buffer]);
  });
}

const hex = await hash(Buffer.alloc(64 * 1024 * 1024, 7));

Costs and when not to use them

A worker costs roughly 20–40 ms to start and several megabytes of memory, because V8 must be initialised a second time and given its own heap. Spawning one per request is slower than doing the work inline. The correct pattern is a fixed pool created at boot and reused, sized to os.availableParallelism() minus one reserved for the main thread.

Workers are also the wrong tool for I/O. A worker waiting on a socket gives nothing that the main loop did not already give, and it adds serialisation on every hop. Use them for pure computation whose result is small relative to its cost: compression, cryptography over large inputs, parsing, image transforms, and CPU-heavy machine learning inference.

Workers do not inherit the parent's listeners, timers or open handles, and an unhandled error inside a worker does not crash the parent — it arrives as an 'error' event. If you never listen for it, the failure is invisible. Always attach 'error' and 'exit' handlers, and always call worker.terminate() on shutdown, or the process will not exit.

4.1 Files and paths: fs/promises and path

The filesystem module ships in three flavours — callback, synchronous and promise — and the promise API is the default choice in modern code. Path handling is the half that fails silently on the wrong platform, so it belongs beside it.

Prefer fs/promises

node:fs/promises exposes the same operations as the callback module but returns promises, so it composes with async/await and with Promise.all. The synchronous variants exist for genuine startup work — reading a config file before the server listens — and are a defect inside a request handler. The promise API also gives you a FileHandle from open(), which supports positional reads and must be closed, ideally with await using where the runtime supports explicit resource management.

// a config loader that behaves on first run and on corrupt input
import { readFile, writeFile, mkdir, rm, copyFile } from 'node:fs/promises';
import { dirname, join } from 'node:path';

async function loadConfig(file) {
  try {
    return JSON.parse(await readFile(file, 'utf8'));
  } catch (err) {
    if (err.code === 'ENOENT') return {};          // absent: defaults
    if (err instanceof SyntaxError) {               // present but broken
      await copyFile(file, `${file}.corrupt`);
      return {};
    }
    throw err;                                      // EACCES, EMFILE: real
  }
}

const target = join(process.cwd(), 'data', 'config.json');
await mkdir(dirname(target), { recursive: true });
await writeFile(target, JSON.stringify({ port: 3000 }, null, 2));
await rm('old-cache', { recursive: true, force: true });   // no throw if absent

Path rules that survive a platform change

Never build a path with string concatenation. path.join normalises and inserts the correct separator; path.resolve additionally makes the result absolute against the working directory. path.relative is the safe way to express "inside this directory". On Windows paths may contain backslashes and drive letters, and path.win32 and path.posix let you parse the other flavour explicitly when a tool must understand a foreign path.

import path from 'node:path';
import { fileURLToPath } from 'node:url';

// in an ES module there is no __dirname; use import.meta.dirname (Node 21+)
path.join(import.meta.dirname, 'assets', 'logo.png');

// the portable fallback for older runtimes
const here = path.dirname(fileURLToPath(import.meta.url));

// traversal guard: prove a requested file is inside the root before serving it
function safeJoin(root, untrusted) {
  const full = path.resolve(root, '.' + path.sep + untrusted);
  const rel = path.relative(root, full);
  if (rel.startsWith('..') || path.isAbsolute(rel)) throw new Error('path traversal');
  return full;
}
safeJoin('/srv/www', '../../etc/passwd');  // throws
fs.readdir returns names only; to distinguish files from directories without an extra stat call per entry, pass { withFileTypes: true } and test entry.isDirectory(). Also watch EMFILE: a directory with tens of thousands of entries read as individual promises can exhaust the process file-descriptor limit. For large trees, iterate rather than fan out, or use fs.glob.

4.2 os, process and url

These three modules are how a Node program asks about its environment and presents itself to the rest of the world. Most of what debugging and deployment need lives here, and the legacy string-based URL parsing must be avoided.

Asking the machine

node:os exposes the host it is running on. os.availableParallelism() is the modern answer for "how many workers should I start" — it respects cgroup limits in containers, where os.cpus().length reports the host's core count and over-schedules badly. os.totalmem and os.freemem are useful for capacity logging, and os.tmpdir and os.homedir keep you from hard-coding a platform path.

import os from 'node:os';

console.log({
  host: os.hostname(),
  platform: `${os.platform()} ${os.release()} (${os.arch()})`,
  cores: os.availableParallelism(),   // container-aware; prefer over cpus().length
  memGB: (os.totalmem() / 1024 ** 3).toFixed(1),
});

// sensible default: leave one core for the main thread and for libuv
const poolSize = Math.max(1, os.availableParallelism() - 1);

process is the running program

process.env is the environment, always strings — parse explicitly. process.argv is the raw argument vector. process.exitCode is the polite way to set a status: it lets in-flight I/O flush before the loop empties, unlike process.exit() which terminates immediately and can truncate output. process.memoryUsage() and process.hrtime.bigint() are the primitives for monitoring and benchmarking, and process.cwd() is the directory the command was launched from, which is not the directory of the script.

// a portable, dependency-free argument parser
import { parseArgs } from 'node:util';

const { values, positionals } = parseArgs({
  allowPositionals: true,
  options: {
    port:  { type: 'string', short: 'p', default: '3000' },
    watch: { type: 'boolean', default: false },
    log:   { type: 'string', multiple: true },
  },
});
console.log(Number(values.port), positionals);

// graceful shutdown: finish work, then let the process end naturally
process.on('SIGINT', async () => {
  await server.close();
  process.exitCode = 0;
});
console.log(`pid ${process.pid} started in ${process.cwd()}`);

URL, never url.parse

The WHATWG URL class and URLSearchParams are globals and are the only correct way to build or read a URL now. The legacy url.parse() is deprecated: it does not know about IPv6 literals, does not validate, and mishandles many real-world inputs. Always construct with a base when the input may be relative.

// parse, mutate and rebuild with the WHATWG API
const u = new URL('../api/v2/items?page=2&limit=10', 'https://example.com/shop/');
u.pathname;                       // '/api/v2/items'
u.searchParams.get('limit');      // '10'
u.searchParams.set('page', '3');
u.toString();                     // 'https://example.com/api/v2/items?page=3&limit=10'

// convert between a file URL and an OS path - the half people get wrong
import { fileURLToPath, pathToFileURL } from 'node:url';
fileURLToPath('file:///C:/tmp/a.txt');   // 'C:\\tmp\\a.txt' on Windows
pathToFileURL('/srv/app/index.js').href; // 'file:///srv/app/index.js'

4.3 Events and EventEmitter

EventEmitter is Node's in-process publish/subscribe primitive and the base class of servers, streams and sockets. One special rule for 'error' handles more bugs than any other convention in the runtime.

The contract

Listeners are stored in insertion order and invoked synchronously when emit is called, in that order, with the emitted arguments. once removes the listener before calling it — so a listener that emits the same event recursively does not re-enter itself. The emitter has no back-pressure and no delivery guarantee after the fact: if nobody is listening at the instant of the emit, the event is simply gone.

import { EventEmitter } from 'node:events';

class JobQueue extends EventEmitter {
  #queue = [];
  add(job) {
    this.#queue.push(job);
    this.emit('added', job, this.#queue.length);   // metadata as extra args
  }
}

const q = new JobQueue();
q.on('added', (job, depth) => console.log(`+${job.id} (depth ${depth})`));
q.once('added', () => console.log('first add only'));
q.add({ id: 1 });   // "+1 (depth 1)" then "first add only"
q.add({ id: 2 });   // "+2 (depth 2)"

The 'error' event is special

If an emitter has no 'error' listener and you emit one, Node throws the error out of emit — unlike every other event, which is silently discarded. This is deliberate, and it means an unhandled error on a stream or server becomes an uncaught exception. Attach a listener to every emitter you create, or accept that a remote peer can terminate your process.

// promise-based waiting for an event, with a built-in timeout
import { once } from 'node:events';
import { createServer } from 'node:http';

const server = createServer();
server.listen(0);
await once(server, 'listening');
console.log('port', server.address().port);
server.close();

// an async iterator consumes events in order, and stops on a terminal event
import { on } from 'node:events';
async function watch(emitter) {
  for await (const [payload] of on(emitter, 'message', { signal: AbortSignal.timeout(5000) })) {
    console.log('got', payload);
  }
}
Node warns about emitters with more than ten listeners on one event (a likely leak). That warning is per event name on a single emitter, not global. For a legitimately fan-out emitter, raise it explicitly with setMaxListeners(0) — passing zero disables the check — rather than ignoring the warning.

EventEmitter or EventTarget?

Node ships both, and they are not interchangeable. EventEmitter supports emit with arbitrary arguments, captureRejections, and is what every stream and server in the runtime uses. EventTarget is the web standard: it accepts an AbortSignal in addEventListener, supports once declaratively, and is what fetch and WebSocket return. For a public API that also has to run in a browser, choose EventTarget; for anything internal and Node-only, EventEmitter is the idiomatic choice.

4.4 crypto: hashing, secrets and random values

The node:crypto module covers random generation, digests, keyed authentication, symmetric encryption and password hashing. The failure mode it guards against is not a crash but a silently weak system, so the defaults matter.

Randomness and digests

Anything that must be unpredictable — session identifiers, tokens, salts, nonces — comes from crypto.randomBytes or crypto.randomUUID. Math.random is a deterministic generator seeded for speed and is never acceptable for a secret. Digests are one-way: createHash for integrity, createHmac when the digest must be verifiable only by a party holding the key, which is the right primitive for signing a cookie or a webhook payload.

import { randomUUID, randomBytes, createHash, createHmac, timingSafeEqual } from 'node:crypto';

randomUUID();                       // '2f6b...' - v4, 122 bits of randomness
randomBytes(32).toString('base64url');  // a 256-bit session token

// content integrity
createHash('sha256').update('the file contents').digest('hex');

// signing a webhook body so the receiver can verify the sender
const sig = createHmac('sha256', process.env.WEBHOOK_SECRET).update(body).digest();

// compare secrets in constant time, or the response time leaks the prefix
function safeEqual(a, b) {
  const A = Buffer.from(a), B = Buffer.from(b);
  return A.length === B.length && timingSafeEqual(A, B);
}

Storing passwords

A password is not a secret to be decrypted; it is a value to be verified, so it needs a deliberately slow, salted, memory-hard function. Use crypto.scrypt (built in) or Argon2 from a native package; never a bare SHA-256 digest, which a modern GPU enumerates by the billion. The salt is unique per password and stored beside the hash, and the work factors must be stored too so they can be raised later without invalidating existing hashes.

import { scrypt, randomBytes, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';

const scryptAsync = promisify(scrypt);
const OPTS = { N: 2 ** 16, r: 8, p: 1, maxmem: 128 * 1024 * 1024 };

async function hashPassword(plain) {
  const salt = randomBytes(16);
  const dk = await scryptAsync(plain, salt, 32, OPTS);
  // store the parameters WITH the hash so they can be upgraded later
  return `scrypt$${OPTS.N}$${OPTS.r}$${OPTS.p}$${salt.toString('base64')}$${dk.toString('base64')}`;
}

async function verifyPassword(plain, stored) {
  const [scheme, N, r, p, saltB64, hashB64] = stored.split('$');
  if (scheme !== 'scrypt') return false;
  const dk = await scryptAsync(plain, Buffer.from(saltB64, 'base64'), 32,
    { N: +N, r: +r, p: +p, maxmem: 128 * 1024 * 1024 });
  const expected = Buffer.from(hashB64, 'base64');
  return dk.length === expected.length && timingSafeEqual(dk, expected);
}

Symmetric encryption, done without inventing things

For data you must recover, use an AEAD mode — AES-256-GCM is the standard choice — which provides confidentiality and detects tampering. A unique random IV per message is mandatory: reusing an IV under the same key destroys both properties, and with GCM it leaks the authentication key outright. The Web Crypto API is available globally as crypto.subtle and is the better choice when the code must also run in a browser or a worker without Node's module system.

import { createCipheriv, createDecipheriv, randomBytes } from 'node:crypto';

const key = randomBytes(32);                 // keep this in a secret manager
function seal(plaintext) {
  const iv = randomBytes(12);                // 96-bit IV, unique per message
  const cipher = createCipheriv('aes-256-gcm', key, iv);
  const ct = Buffer.concat([cipher.update(plaintext), cipher.final()]);
  return Buffer.concat([iv, cipher.getAuthTag(), ct]);  // store all three
}
function open(sealed) {
  const iv = sealed.subarray(0, 12);
  const tag = sealed.subarray(12, 28);
  const decipher = createDecipheriv('aes-256-gcm', key, iv);
  decipher.setAuthTag(tag);                  // throws if the ciphertext changed
  return Buffer.concat([decipher.update(sealed.subarray(28)), decipher.final()]);
}
createCipheriv requires a key of exactly the right length, and passing a passphrase where a key belongs fails loudly. Never derive a key from a password with a bare hash — use scrypt or hkdf. And never commit the key: the difference between encryption and obfuscation is who can read it.

4.5 util and the modern globals

node:util is the drawer of small, stable helpers, and several features that once required it are now globals. Knowing which is which avoids importing something the runtime already provides.

The helpers worth importing

util.parseArgs is a small, spec-compliant argument parser with no dependency. util.promisify converts an error-first callback function into a promise, respecting a custom symbol so a library can supply a better promise form. util.inspect is what console.log uses; calling it directly lets you set depth, colours and a maximum string length for a log line. util.deprecate wraps a function so the first call emits a one-time warning to stderr.

import { promisify, inspect, deprecate, types } from 'node:util';
import { gzip } from 'node:zlib';

const gzipAsync = promisify(gzip);
console.log(inspect({ nested: { deep: { more: [1, 2, 3] } } }, { depth: 4, colors: false }));

const oldFn = deprecate((x) => x * 2, 'oldFn() is deprecated; use newFn()');
oldFn(2);  // prints a one-time DeprecationWarning to stderr

types.isDate(new Date());      // true, and works across realms
types.isPromise(Promise.resolve()); // true

Text, now global

TextEncoder and TextDecoder are globals in Node and are the correct way to move between strings and bytes when the encoding is UTF-8, which it almost always is. Buffer.from is the idiomatic Node equivalent and is faster, but it silently substitutes malformed input; TextDecoder with fatal: true throws instead, which is what you want when validating untrusted bytes.

// strict decoding: reject invalid UTF-8 instead of mangling it
const dec = new TextDecoder('utf-8', { fatal: true });
try {
  dec.decode(Buffer.from([0xff, 0xfe]));  // throws: not valid UTF-8
} catch {
  console.log('rejected malformed input');
}

// strings are UTF-16; byte length and string length are different numbers
const s = 'héllo 🙂';
s.length;                  // UTF-16 code units
Buffer.byteLength(s, 'utf8'); // bytes on the wire - always validate against THIS
new TextEncoder().encode(s).byteLength === Buffer.byteLength(s); // true
util.styleText, added in Node 22, is the supported way to colour terminal output — it respects NO_COLOR, FORCE_COLOR and whether stdout is a TTY, so a log pipeline that writes to a file does not receive escape sequences.

Know which of these are globals and which are modules

The web-standard APIs are globals: fetch, WebSocket, URL, URLSearchParams, AbortController, structuredClone, TextEncoder, crypto, performance and the timers all exist without an import. Everything specific to Node is a module — fs, path, events, util, os, child_process. Importing those through the node: prefix is deliberate and worth adopting: it makes the core-module intent unmistakable and, unlike a bare specifier, cannot be shadowed by a userland package of the same name in a future release.

5.1 Buffer: bytes in a fixed block

A Buffer is a fixed-length view over raw memory outside V8's heap. It is a subclass of Uint8Array, which is why modern code can often be written against either, and it is the unit of every stream and socket in Node.

Allocating

Buffer.alloc(n) returns a zero-filled block. Buffer.allocUnsafe(n) skips the fill and is faster, but the memory it hands back is whatever was previously in the pool, which may be another request's data. That is a real information-disclosure bug when the buffer is sent before being fully written, so allocUnsafe is only acceptable when you overwrite every byte before use.

// safe default, and the fast path when you control every byte
const zeroed = Buffer.alloc(1024);              // all zeros
const fromStr = Buffer.from('héllo', 'utf8');   // encode
fromStr.toString('hex');                        // 68c3a96c6c6f (6 bytes, not 5)
Buffer.byteLength('héllo', 'utf8');             // 6 - always measure in bytes

// allocUnsafe: only when you are certain to fill it completely
const scratch = Buffer.allocUnsafe(4);
scratch.writeUInt32BE(0xdeadbeef, 0);           // every byte written before use

// concatenation copies; subarray does NOT - it is a view sharing memory
const a = Buffer.from('foo'), b = Buffer.from('bar');
const joined = Buffer.concat([a, b]);           // new 6-byte buffer
const view = joined.subarray(0, 3);
view[0] = 0x58;                                 // mutates "joined" too!
buf.length is bytes, not characters, and buf[i] returns a number while buf.toString() may produce replacement characters for a multi-byte sequence cut in the middle. Slicing a UTF-8 buffer at an arbitrary offset is the most common way to corrupt text: always split on a protocol boundary you control, or accumulate until the sequence is complete.

Sizes, views and safety

The maximum buffer length, buffer.constants.MAX_LENGTH, is roughly 4 GB on 64-bit systems and much smaller on some others; a request that claims a 10 GB body must be rejected before any buffer is allocated for it. buf.subarray and new Uint8Array(buf.buffer, offset, len) both create views, so a "small" slice can keep an enormous allocation alive — the classic memory leak of holding a 2-byte header view into a 64 MB body.

// copy out the bytes you intend to keep, so the big buffer can be collected
const big = await readFile('huge.bin');
const header = Buffer.from(big.subarray(0, 16));   // copies 16 bytes only

// size ceilings, checked before allocating
if (Number(req.headers['content-length'] ?? 0) > 2 * 1024 * 1024) {
  res.writeHead(413).end();                        // 413 Payload Too Large
}

Encoding is not the same as character set

Base64 and hex are ways of writing bytes as text; they are not text encodings and they are not interchangeable with UTF-8. Round-tripping binary data through base64 is safe and lossless, but decoding base64 into a string and then treating that string as UTF-8 is not, because the bytes were never text to begin with. Buffer.from(value, 'base64') also ignores characters outside the base64 alphabet without complaint, so validating the input shape beforehand is the only way to tell a truncated payload from a valid one.

5.2 Readable and Writable streams

A stream is a sequence of chunks delivered over time. Two modes read a Readable, and they cannot both be used casually; the choice determines whether you control the pace or the stream ignores your concerns.

Flowing versus paused

Attaching a 'data' listener switches a readable to flowing mode: chunks are pushed at whatever rate the source produces them. Not attaching one, and instead calling read() or using for await, keeps it paused: chunks are pulled when you ask. Flowing mode is convenient and dangerous, because the source keeps going whether or not you finished handling the previous chunk.

// pulling: the loop applies back-pressure automatically
import { createReadStream } from 'node:fs';

const stream = createReadStream('big.log', { encoding: 'utf8' });
let lines = 0;
for await (const chunk of stream) {
  lines += chunk.split('\n').length - 1;
}
console.log({ lines });

// pushing: simple, and unpaced - fine for small, fast sources
stream.on('data', (chunk) => process.stdout.write(chunk));
stream.on('end', () => console.error('done'));

The lifecycle events

EventOnMeaning
'data'ReadableA chunk is available (flowing mode)
'end'ReadableNo more data will be produced
'error'BothFailed; no further events follow
'finish'WritableAll data has been flushed to the underlying resource
'close'BothThe underlying resource is closed

Writing is pull-aware: writable.write(chunk) returns false when the internal buffer has crossed its high-water mark, meaning "stop until 'drain'". Ignoring the return value is the single most common cause of uncontrolled memory growth in a Node service, because the stream keeps accepting data it cannot deliver.

import { createWriteStream } from 'node:fs';
import { once } from 'node:events';

const out = createWriteStream('audit.log');
async function writeAll(chunks) {
  for (const chunk of chunks) {
    if (!out.write(chunk)) await once(out, 'drain');   // honour the signal
  }
  out.end();
  await once(out, 'finish');                            // flushed, not just queued
}
Readable.from(asyncIterable) turns any async generator into a readable stream, and Readable.fromWeb adapts a WHATWG ReadableStream. Both let you stay in ordinary async code until the last moment, which is usually clearer than subclassing.

Interop with web streams

Node streams and the web ReadableStream standard are two different models, and both are now everywhere: fetch bodies are web streams, most Node APIs are not. Readable.fromWeb and Readable.toWeb convert in both directions, as do their Writable counterparts, which is how you feed a fetch response into pipeline or wrap an existing Node stream to hand it to a Response. Convert once at the boundary rather than mixing the two models inside one pipeline, because their error and cancellation semantics differ and a mixed chain loses errors.

5.3 Transform streams and pipeline

A transform reads, modifies and writes. Composing several of them into a pipeline is the readable way to express a data flow, and stream/promises' pipeline() is the only version that gets error propagation and cleanup right.

Writing a transform

A transform subclass implements _transform(chunk, encoding, callback) and calls the callback with the transformed chunk, or with an error. The object-mode option lets the chunks be JavaScript values rather than bytes, which turns a pipeline into a processing queue. Do not buffer the entire stream inside a transform unless that is genuinely the operation — it defeats the purpose of streaming.

// a transform that redacts a token wherever it appears, bytes or strings
import { Transform } from 'node:stream';

class Redact extends Transform {
  #secret;
  #tail = '';                       // hold back a partial match split across chunks
  constructor(secret) {
    super({ decodeStrings: false });
    this.#secret = secret;
  }
  _transform(chunk, _enc, cb) {
    const text = this.#tail + chunk;
    const cut = Math.max(0, text.length - this.#secret.length);
    this.#tail = text.slice(cut);
    cb(null, text.slice(0, cut).replaceAll(this.#secret, '[REDACTED]'));
  }
  _flush(cb) {
    cb(null, this.#tail.replaceAll(this.#secret, '[REDACTED]'));
  }
}

pipeline is the only correct composition

pipeline(source, ...transforms, destination) returns a promise, forwards an error from any stage to all of them, and destroys the whole chain so nothing is left half-open. The old pattern of chaining .pipe() calls and attaching listeners by hand leaks file descriptors on failure, because a .pipe() destination is never automatically destroyed when an upstream source errors.

import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { setTimeout as delay } from 'node:timers/promises';

await pipeline(
  createReadStream('access.log'),
  new Redact(process.env.API_TOKEN),
  createGzip(),
  createWriteStream('access.log.gz'),
);
console.log('compressed');     // only reached on complete success

// inject a stage with no library: an async generator is a transform
async function* throttled(source) {
  for await (const chunk of source) {
    yield chunk;
    await delay(5);            // pace the producer
  }
}
await pipeline(createReadStream('in.bin'), throttled, createWriteStream('out.bin'));
A stream that is neither consumed nor destroyed holds its file descriptor open forever. Every branch that creates a stream — including the error path — must either finish the pipeline or destroy the stream. This is the origin of the EMFILE: too many open files error under load, which appears minutes after the real mistake.

objectMode: a pipeline of values, not bytes

An object-mode stream carries JavaScript values instead of buffers, which turns a pipeline of transforms into a bounded, back-pressured work queue. The default high-water mark is sixteen objects rather than sixteen kilobytes, and that mismatch is worth remembering: a stage that holds a large object reports a comfortable depth in objects while consuming a great deal of memory, so in object mode the count is not a memory bound. Set an explicit limit and treat the pipeline as a queue with a capacity, not as a stream with a buffer size.

5.4 Backpressure, concretely

Backpressure is a producer slowing down because a consumer cannot keep up. Streams expose it as a boolean and a 'drain' event; the watermark that triggers it is configurable and is the knob that trades memory for throughput.

The high-water mark

Both sides have a highWaterMark: the number of bytes (or objects) buffered before the stream signals that it is full. It defaults to 16 KB for binary streams in modern Node, 16 objects in object mode, and the exact value is a heuristic rather than a limit — the buffer may overshoot by one chunk. Raising it improves throughput for large sequential transfers; lowering it reduces peak memory. Neither changes correctness.

import { createWriteStream, createReadStream } from 'node:fs';

// an 8 MB write buffer: fewer syscalls, more resident memory
const sink = createWriteStream('dump.bin', { highWaterMark: 8 * 1024 * 1024 });

// observe the signal directly, to see it work
const src = createReadStream('dump.bin', { highWaterMark: 64 * 1024 });
src.on('data', (chunk) => {
  const ok = sink.write(chunk);
  if (!ok) {
    src.pause();                          // stop producing
    sink.once('drain', () => src.resume()); // resume when the consumer caught up
  }
});
src.on('end', () => sink.end());

When the producer cannot be paused

An HTTP upload, a socket and a child process's stdout are all sources that will not wait. The answer there is not to buffer without limit; it is to cap the buffering and fail fast. A queue with a maximum depth that rejects new work is strictly better than a queue that grows until the process is killed by the OOM reaper, because rejection is a decision the application can make and an OOM kill is not.

// a bounded buffer: over-limit input is a 503, not a memory leak
class BoundedSink {
  #queue = [];
  #limit;
  constructor(limit = 1_000) { this.#limit = limit; }
  push(item) {
    if (this.#queue.length >= this.#limit) {
      throw Object.assign(new Error('busy'), { statusCode: 503 });
    }
    this.#queue.push(item);
  }
}

// and when the source is a socket, pause it explicitly
import { createServer } from 'node:net';
const srv = createServer((socket) => {
  socket.pause();                  // stop reading at the OS level
  ready().then(() => socket.resume());
});
Rule of thumb: if you cannot name where a stream's back-pressure signal ends up, the buffer is unbounded in practice. pipeline() is the easy way to be sure, because it wires the signal for you and refuses to leave a stage dangling.

Measuring buffer growth directly

A stream exposes the depth of its internal buffer as readableLength and writableLength, and this is the number to watch rather than the process's total memory, which is noisy and lagging. A writable whose writableLength climbs while its source keeps producing is the exact signature of ignored back-pressure, and writableNeedDrain tells you whether a 'drain' is still outstanding. Exporting these two gauges per stream in a busy service turns an unexplained memory graph into a single named culprit.

6.1 The node:http module

A Node HTTP server is a function called with a request stream and a response stream. Every framework in the ecosystem is a layer over that function, so understanding the raw shape is what makes framework behaviour predictable rather than magical.

The request and the response are streams

createServer(handler) registers the handler and returns a Server. The handler receives an IncomingMessage (readable) and a ServerResponse (writable). req.url is the request target — path plus query, never the full URL — and req.method and req.headers are already parsed. Header names are lower-cased in that object, which is why req.headers['Content-Type'] is always undefined.

Because the body is a stream, nothing reads it for you. A handler that ignores the body and responds immediately leaves unread bytes in the socket, which for a request with a body means the connection cannot be reused and, depending on the framing, the next request on that connection can be misparsed. Either consume the body or explicitly end the request.

// raw-http.js - everything a server must do, with no framework
import { createServer } from 'node:http';

const server = createServer((req, res) => {
  // never trust req.url as a path; it may be absolute-form or contain a query
  const url = new URL(req.url, `http://${req.headers.host ?? 'localhost'}`);

  if (req.method === 'GET' && url.pathname === '/health') {
    res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
    return res.end(JSON.stringify({ status: 'ok', uptime: process.uptime() }));
  }

  // 405 with the correct Allow header beats a bare 404
  res.writeHead(405, { allow: 'GET', 'content-type': 'text/plain' });
  res.end('method not allowed');
});

server.listen({ port: 3000, host: '127.0.0.1' });
server.on('error', (err) => {
  if (err.code === 'EADDRINUSE') console.error('port 3000 already in use');
  else throw err;
});

Default headers, and the ones Node sets for you

Node sends Date, Connection and Transfer-Encoding or Content-Length automatically. If you call res.write without a Content-Length, Node switches to chunked encoding, which is correct and slightly larger on the wire. Call res.writeHead(status, headers) once — a second call throws ERR_HTTP_HEADERS_SENT — and after that use res.setHeader before the first write. res.writeHead also works without a reason phrase, in which case Node supplies the standard one.

6.2 Routing by hand

Routing is matching a method and a path to a handler. A hand-written router is twenty lines and is genuinely sufficient for internal services; it is also the clearest way to see what a framework adds.

A route table instead of an if-chain

Match on the pair (method, pathname). Parameterised routes need a pattern, and the smallest useful one is to split the path into segments and compare segment by segment, treating a leading colon as a capture. A linear scan of a few dozen routes costs nothing measurable; a long list should be keyed by first segment to avoid a full scan per request.

// a 30-line router: method + path -> handler, with :params
function compile(pattern) {
  const keys = [];
  const rx = new RegExp('^' + pattern
    .split('/')
    .map(seg => {
      if (!seg) return '';
      if (seg.startsWith(':')) { keys.push(seg.slice(1)); return '/([^/]+)'; }
      return '/' + seg.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
    })
    .join('') + '/?$');
  return { rx, keys };
}

const routes = [];
const route = (method, pattern, handler) => {
  routes.push({ method, ...compile(pattern), handler });
};

route('GET', '/users', () => ({ body: [] }));
route('GET', '/users/:id', (req, { id }) => ({ body: { id } }));

function match(method, pathname) {
  for (const r of routes) {
    if (r.method !== method) continue;
    const m = r.rx.exec(pathname);
    if (!m) continue;
    const params = Object.fromEntries(r.keys.map((k, i) => [k, decodeURIComponent(m[i + 1])]));
    return { handler: r.handler, params };
  }
  return null;
}

The rules a router should not break

Decode percent-escapes only after matching, never before — decoding first lets %2F become a slash and collapse two routes into one, which is a genuine security bug in naive routers. Return a real 405 with an Allow header when the path matches but the method does not, which is both friendlier and required by the specification. Normalise trailing slashes and repeated / once, at the boundary, rather than in every handler.

// dispatch: turn a match into a response, and distinguish 404 from 405
function dispatch(req, res) {
  const url = new URL(req.url, 'http://localhost');
  // collapse '//', remove a trailing slash (except the root) ONCE
  const pathname = url.pathname.replace(/\/{2,}/g, '/').replace(/(.+)\/$/, '$1');

  const hit = match(req.method, pathname);
  if (hit) return respond(res, hit.handler(req, hit.params));

  const allowed = [...new Set(routes
    .filter(r => r.rx.test(pathname))
    .map(r => r.method))];
  if (allowed.length) {
    res.writeHead(405, { allow: allowed.join(', ') });
    return res.end();
  }
  res.writeHead(404, { 'content-type': 'application/json' });
  res.end(JSON.stringify({ error: 'not found' }));
}

function respond(res, { status = 200, headers = {}, body = '' } = {}) {
  const text = typeof body === 'string' ? body : JSON.stringify(body);
  res.writeHead(status, { 'content-type': 'application/json', ...headers });
  res.end(text);
}
Hand-rolled routers are the right answer for a service with a handful of routes and no middleware. The moment you need parameter validation, content negotiation, CORS and error mapping, each of which is a hundred lines to do well, a framework is cheaper than the code you would write.

HEAD and OPTIONS are part of the contract

A HEAD request must return exactly the headers a GET would, with no body. Frameworks that route by method often handle this for you, and a hand-written router must do it explicitly, because crawlers, proxies and health checkers use it to test availability without transferring a payload. OPTIONS answers what a client may do to a resource, and it is what a browser sends before a cross-origin request that uses a non-simple method or header. Answering both is a few lines and prevents a category of bug that only appears behind a proxy or in a browser.

6.3 Serving static files safely

Static serving looks trivial and contains three real traps: path traversal, missing cache validators, and reading whole files into memory. A correct implementation is short, and every line of it is load-bearing.

Resolve, then verify

Build the absolute path with path.resolve, then confirm the result is still inside the root before opening anything. Comparing strings for .. is not enough: percent-encoded traversal, absolute paths, Windows drive letters and symlinks all defeat naive checks. The reliable test is path.relative(root, resolved) not starting with .. and not being absolute.

import { createReadStream } from 'node:fs';
import { stat } from 'node:fs/promises';
import { extname, resolve, relative, isAbsolute, sep } from 'node:path';
import { createHash } from 'node:crypto';

const MIME = new Map(Object.entries({
  '.html': 'text/html; charset=utf-8', '.css': 'text/css; charset=utf-8',
  '.js': 'text/javascript; charset=utf-8', '.json': 'application/json',
  '.png': 'image/png', '.jpg': 'image/jpeg', '.svg': 'image/svg+xml',
  '.woff2': 'font/woff2', '.wasm': 'application/wasm',
}));

async function serveFile(root, urlPath, req, res) {
  const target = resolve(root, '.' + sep + decodeURIComponent(urlPath));
  const rel = relative(root, target);
  if (rel.startsWith('..') || isAbsolute(rel)) return notFound(res);

  let info;
  try { info = await stat(target); } catch { return notFound(res); }
  if (info.isDirectory()) return notFound(res);

  // a weak validator from size + mtime: cheap and good enough for static assets
  const etag = `W/"${info.size.toString(16)}-${info.mtimeMs.toString(16)}"`;
  if (req.headers['if-none-match'] === etag) {
    res.writeHead(304, { etag });
    return res.end();
  }

  res.writeHead(200, {
    'content-type': MIME.get(extname(target).toLowerCase()) ?? 'application/octet-stream',
    'content-length': info.size,
    etag,
    'cache-control': 'public, max-age=0, must-revalidate',
  });
  if (req.method === 'HEAD') return res.end();
  createReadStream(target).pipe(res);      // streams: constant memory for any size
}

Set a cache policy on purpose

An ETag or Last-Modified header lets a client revalidate with a cheap 304 instead of re-downloading. Content-hashed filenames — app.9f2c1a.js — are the only case where immutable, max-age=31536000 is safe, because a new build produces a new name. For everything else use max-age=0, must-revalidate so a stale copy is never served without asking.

// in production, hash the filename at build time and cache it forever
const name = `app.${createHash('sha256').update(source).digest('hex').slice(0, 8)}.js`;
// then: Cache-Control: public, max-age=31536000, immutable
// and for index.html, which names the hashed files: no-store

// Range requests matter for video and large downloads
const range = req.headers.range;                 // "bytes=0-1023"
if (range) {
  const [start, end] = range.replace('bytes=', '').split('-').map(Number);
  const last = Number.isFinite(end) ? end : info.size - 1;
  res.writeHead(206, {
    'content-range': `bytes ${start}-${last}/${info.size}`,
    'accept-ranges': 'bytes',
    'content-length': last - start + 1,
  });
  return createReadStream(target, { start, end: last }).pipe(res);
}
Serve static assets from a CDN, a reverse proxy such as nginx, or a dedicated library. Node is perfectly capable of serving files, but when it is also running your application, a few large downloads can consume the entire libuv thread pool and starve every database call. Keep the two workloads apart.

Why the Content-Type of a static file is a security boundary

The browser decides how to treat a response from its Content-Type, not from the file extension. Serving an uploaded file with a sniffable or wrong type lets it execute in your origin: an SVG is a document, and an HTML file served from /uploads/ runs script with your cookies and your session. That is why X-Content-Type-Options: nosniff belongs on every response, and why user-uploaded content should be served from a separate origin with a restrictive content type rather than from the application host.

6.4 JSON APIs: reading bodies and answering well

A JSON handler is a body reader plus a body writer, and both have a failure mode. Correct framing, a size limit and a consistent error shape are what separate an API that is pleasant to integrate from one that is not.

Reading a body with a limit

Never accumulate an unbounded request body. Check content-length first for a fast rejection, then enforce a limit while streaming, because the header can lie or be absent under chunked encoding. Reject a wrong content type with 415 rather than attempting a parse, and treat malformed JSON as 400, not 500 — the client is at fault.

const LIMIT = 1 * 1024 * 1024;   // 1 MB

async function readJson(req) {
  if (!(req.headers['content-type'] ?? '').includes('application/json')) {
    throw Object.assign(new Error('expected application/json'), { statusCode: 415 });
  }
  const declared = Number(req.headers['content-length'] ?? 0);
  if (declared > LIMIT) {
    req.destroy();                            // stop reading; do not buffer
    throw Object.assign(new Error('payload too large'), { statusCode: 413 });
  }

  const chunks = [];
  let size = 0;
  for await (const chunk of req) {
    size += chunk.length;
    if (size > LIMIT) {
      req.destroy();
      throw Object.assign(new Error('payload too large'), { statusCode: 413 });
    }
    chunks.push(chunk);
  }
  if (!size) return null;
  try {
    return JSON.parse(Buffer.concat(chunks).toString('utf8'));
  } catch {
    throw Object.assign(new Error('invalid JSON'), { statusCode: 400 });
  }
}

An error shape, decided once

Pick a single JSON error envelope and never deviate from it. Include a stable machine-readable code, a human message and, for validation failures, a list of field-level problems. Do not leak stack traces or internal messages: log the detailed error against a request id, return the id to the client, and let an engineer reconstruct the failure from the logs without exposing anything.

// one place that turns any thrown value into an HTTP response
function sendError(res, err, requestId) {
  const status = err.statusCode ?? 500;
  if (status >= 500) console.error({ requestId, err });   // full detail, server-side
  res.writeHead(status, { 'content-type': 'application/problem+json' });
  res.end(JSON.stringify({
    type: `https://errors.example.com/${err.code ?? 'internal'}`,
    title: status >= 500 ? 'Internal Server Error' : err.message,
    status,
    requestId,                                              // safe to expose
    details: err.details ?? undefined,
  }));
}

// handlers stay thin and throw typed errors
async function createUser(req, res) {
  const body = await readJson(req);
  if (!body?.email) {
    throw Object.assign(new Error('email is required'),
      { statusCode: 422, code: 'validation', details: [{ field: 'email' }] });
  }
  res.writeHead(201, { location: `/users/${body.email}` }).end();
}
Always set content-type: application/json; charset=utf-8 and send a Content-Length when you have the whole body in hand. A missing charset is fine for JSON in practice, but it is required for text responses that contain anything outside ASCII, and getting it wrong produces mojibake in terminals and browsers.

Streaming a response instead of assembling it

A handler that loads a hundred thousand rows and calls JSON.stringify on the array holds the whole result in memory twice over. For large result sets, write incrementally: emit each record as it is produced, wrapping the output in an array or using newline-delimited JSON, and call res.end() when the source is exhausted. Nothing about the client changes if it is written to parse a stream, and the server's peak memory becomes a constant instead of a function of the data set.

6.5 HTTPS, keep-alive and graceful shutdown

A server that runs is not the same as a server that stops. In an environment where deploys and scale events happen continuously, shutdown has to be as deliberate as startup, and TLS has to be terminated somewhere explicitly chosen.

TLS terminated here, or in front

node:https takes a key and certificate and otherwise behaves exactly like node:http. In practice TLS is usually terminated by a load balancer or ingress, and Node receives plain HTTP from a trusted private network. If so, configure the server to trust exactly the proxy's certificate or address, and read the real client address from X-Forwarded-For only when the request came from that trusted hop — otherwise any client can forge its own address.

// direct TLS termination
import { createServer } from 'node:https';
import { readFileSync } from 'node:fs';

const server = createServer({
  key: readFileSync('/etc/tls/tls.key'),
  cert: readFileSync('/etc/tls/tls.crt'),
  minVersion: 'TLSv1.2',             // refuse TLS 1.0/1.1
  keepAliveTimeout: 65_000,          // above a typical proxy's 60 s idle timeout
}, handler);

// behind a proxy: express the trust boundary, and get the client IP from it
function clientIp(req) {
  const remote = req.socket.remoteAddress;
  const trusted = remote === '10.0.0.10' || remote?.startsWith('10.0.0.');
  if (!trusted) return remote;                       // never trust a stranger
  return (req.headers['x-forwarded-for'] ?? '').split(',')[0].trim() || remote;
}

Shutdown in the right order

Graceful shutdown means: stop accepting new connections, keep serving in-flight requests, tell the load balancer you are going away, and only then exit. A zero-downtime deploy depends on all four. server.close() stops listening and calls back once existing connections end — but idle keep-alive sockets keep it open indefinitely, so closeIdleConnections() is not optional, and a hard deadline is what guarantees the process eventually dies.

import { once } from 'node:events';

let shuttingDown = false;
async function shutdown(signal) {
  if (shuttingDown) return;             // SIGTERM twice must not run twice
  shuttingDown = true;
  console.log(`${signal}: draining`);

  // 1. fail readiness so the load balancer stops sending new work
  ready = false;

  // 2. wait for in-flight requests, bounded
  const deadline = new Promise(r => setTimeout(r, 15_000).unref());
  server.close();                       // callback fires when all are done
  server.closeIdleConnections();        // release keep-alive sockets now

  await Promise.race([once(server, 'close'), deadline]);

  // 3. close the things the server depended on
  await Promise.allSettled([db.end(), redis.quit(), workerPool.close()]);
  // 4. default busy sockets, so the process can actually exit
  server.closeAllConnections();
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));
A Kubernetes pod is sent SIGTERM and then killed after terminationGracePeriodSeconds, which defaults to 30 seconds. A shutdown that waits longer than that is killed mid-flight, and the requests it was draining produce connection resets. Make the application's own deadline several seconds shorter than the platform's.

7.1 Express 5

Express is the oldest and most widely deployed Node web framework. Version 5 finally removes the legacy callback plumbing that made v4 error handling awkward, and it is a thin, unopinionated layer that stays out of your way.

The shape of an Express app

An app is a router plus a stack of middleware. express.json() parses bodies, express.static() serves files, and everything else is a function that takes (req, res, next). When a handler returns without calling res-ending method, the request hangs — the most common Express bug, and the reason the response must always be ended on every path.

// Express 5 - promise rejections now reach the error handler automatically
import express from 'express';

const app = express();
app.use(express.json({ limit: '1mb' }));
app.use(express.static('public', { maxAge: '1h' }));

app.get('/users/:id', async (req, res) => {
  const user = await repo.find(req.params.id);
  if (!user) return res.status(404).json({ error: 'not found' });
  res.json(user);
  // in v5 a rejected promise here is forwarded to the error middleware;
  // in v4 you had to wrap it yourself with try/catch or next(err)
});

// an error handler is identified by its FOUR parameters - this is the contract
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);        // cannot fix a partial response
  res.status(err.status ?? 500).json({ error: err.message });
});

Mount the catch-all 404 handler after all routes and the error handler after that. Express walks the stack in registration order, so a 404 middleware registered early shadows every route defined later — a mistake whose symptom is "all my routes return 404" with correct-looking route definitions.

When Express is the wrong tool

Express is deliberately unopinionated, which is its strength for a small service and its weakness for a large one. It has no built-in request validation, no response serialisation contract, no request-id propagation and no structured logger, so every team invents all four — usually differently in each router. Middleware ordering is the API and is invisible in the route definitions, so an authentication gap is a reordering away. Once the surface has dozens of endpoints and more than one team touching it, a framework that makes validation and serialisation part of the route definition pays for the learning curve quickly.

7.2 Fastify

Fastify is the modern alternative, built around validation and serialisation driven by JSON Schema. The schema is not decoration: Fastify compiles it into a fast validating function and uses the response schema to serialise output safely.

Schemas do three jobs

A route schema declares the body, the querystring, the params and the response. Fastify validates the input before your handler runs and returns a structured 400 if it fails, and it compiles the response schema with fast-json-stringify so the serialiser emits only declared fields — which both speeds up output and prevents accidentally leaking an internal field such as a password hash.

// Fastify 5 - validation, serialisation and typed handlers from one schema
import Fastify from 'fastify';

const fastify = Fastify({ logger: true });

const UserBody = {
  type: 'object',
  required: ['email'],
  additionalProperties: false,          // reject unknown fields outright
  properties: {
    email: { type: 'string', format: 'email' },
    name:  { type: 'string', minLength: 1, maxLength: 80 },
  },
};

fastify.post('/users', {
  schema: {
    body: UserBody,
    response: {
      201: {
        type: 'object',
        properties: { id: { type: 'string' }, email: { type: 'string' } },
        // "passwordHash" is simply never serialised, because it is not listed
      },
    },
  },
}, async (request, reply) => {
  const user = await repo.create(request.body);
  reply.code(201).send(user);
});

await fastify.listen({ port: 3000, host: '0.0.0.0' });

Encapsulation instead of a global stack

fastify.register(plugin) creates a new scope. Hooks added inside a plugin apply only to that plugin's routes, so a preHandler that requires authentication can be registered on the API subtree without affecting public routes. Decorators add values to the instance within that scope, which is Fastify's answer to attaching things to req.

// a plugin that adds an authenticated sub-tree, scoped cleanly
import fp from 'fastify-plugin';

async function auth(app) {
  app.decorate('currentUser', null);
  app.addHook('preHandler', async (req, reply) => {
    const token = req.headers.authorization?.replace(/^Bearer /, '');
    if (!token) return reply.code(401).send({ error: 'unauthorized' });
    req.currentUser = await verify(token);       // scoped to this subtree
  });
}

export default fp(async function api(app) {
  await app.register(auth);
  app.get('/me', async (req) => req.currentUser);
}, { name: 'api', dependencies: ['database'] });
Choose Express when you want the largest pool of existing middleware and examples; choose Fastify when throughput, schema validation and a structured logger matter more than middleware breadth. Benchmarks favour Fastify by a wide margin on JSON routes, but the schema-first discipline it requires is the real difference in day-to-day code.

The request lifecycle as an ordered set of hooks

Fastify exposes a precise pipeline: onRequest before routing, preParsing and preValidation around body handling, preHandler just before the handler, then preSerialization, onSend, onResponse and onError. Choosing the right hook is mostly a question of what the hook must see: authentication belongs in preHandler when it needs the parsed body, and in onRequest when it only needs the headers. A hook registered inside a plugin applies to that plugin's routes only, which is how an authenticated subtree is expressed without global middleware and without exceptions to it.

7.3 Routing patterns that scale

Routing decisions are structural, not stylistic. The route layout, the versioning strategy and the pipeline between request and handler determine how hard the codebase is to change two years later.

Version, and never break a client

URL-prefix versioning — /api/v1/… — is the simplest strategy that actually works, because it is visible in logs and can be routed by a proxy. Header-based versioning is more elegant in theory and much harder to operate, because the version is not in the access log. Whichever you choose, additively evolve within a version: a new optional field is safe, a renamed one is not.

// one file per resource, mounted twice, so v1 can freeze
import { Router } from 'express';
import { usersV1 } from './users.v1.js';
import { usersV2 } from './users.v2.js';
import { deprecate } from './middleware/deprecate.js';

const app = express();
app.use('/api/v1/users', deprecate('2027-01-01'), usersV1);
app.use('/api/v2/users', usersV2);

Resource-shaped routes

Keep verbs out of the URL and let the method carry the intent: POST /orders creates, GET /orders/:id reads, PATCH /orders/:id updates. Actions that are genuinely not a resource — POST /orders/:id/refund — are acceptable as a sub-resource rather than a verb on the resource itself. Route ordering matters in frameworks that match first-wins, so register a literal segment such as /orders/stats before the parameterised /orders/:id, or stats becomes an order id.

// literal-before-parameter is a real bug source, not a style preference
app.get('/orders/stats', getOrderStats);   // must be first
app.get('/orders/:id', getOrder);          // otherwise this matches /orders/stats

// and validate the parameter BEFORE it reaches the data layer
app.param('id', (req, res, next, raw) => {
  if (!/^[0-9a-f]{24}$/.test(raw)) {
    return res.status(400).json({ error: 'invalid id' });
  }
  next();
});
A useful rule: the route table should read like the API documentation. If you cannot tell from the routes what resources exist and what may be done to them, the endpoints are doing too much and should be split.

Pagination, filtering and the query contract

Two pagination styles cover nearly every case. Offset paging — ?page=2&per_page=50 — is simple and lets a client jump to any page, but it drifts and gets slower as the offset grows. Cursor paging — ?after=eyJpZCI6ImFiYyJ9 — is stable under insertion and stays fast, at the cost of being forward-only. Whichever you choose, cap the page size server-side rather than trusting the client's limit, and define a total order on the sort key, or two identical requests can return the same row twice and never return another.

7.4 Middleware and the request pipeline

Middleware is a function in a chain that may end the request, pass it on, or fail it. Order is the API, and the common defects are all ordering defects: a parser after the route, an authenticator after the handler, a CORS header after the response.

What good middleware does — and does not do

A middleware should do exactly one job, be idempotent about the response, and call next() exactly once. It should not swallow errors, mutate the request in ways that surprise later stages, or perform work that belongs to a single route. Anything that runs on every request must be cheap, because it is multiplied by traffic: a synchronous filesystem read in a global middleware is a scalability decision, whether or not it was intended as one.

// the canonical global order, and why each position is fixed
app.use(requestId);            // 1. everything after can log the id
app.use(logRequests);          // 2. now logs can include the id
app.use(securityHeaders);      // 3. applies to every response, including errors
app.use(cors({ origin: allowlist }));
app.use(express.json({ limit: '1mb' }));   // 4. before any handler reads a body
app.use('/api', apiRouter);    // 5. routes
app.use(notFound);             // 6. only reached if no route matched
app.use(errorHandler);         // 7. LAST, and it takes four arguments

function requestId(req, res, next) {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  res.setHeader('x-request-id', req.id);
  next();
}

Composing safely

A middleware that needs the response finished — for timing, for metrics — must hook the finish, not assume the work happened when next() returns. Wrap res.end, or listen for 'finish' and 'close', and be aware that a client disconnect fires 'close' without 'finish'. Distinguishing the two is how you tell a slow response from an abandoned one.

// a correct metrics middleware: measures the response, not the handler call
function metrics(req, res, next) {
  const start = process.hrtime.bigint();
  res.on('finish', () => {
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    histogram.observe({ method: req.method, status: res.statusCode }, ms);
  });
  res.on('close', () => {
    if (!res.writableEnded) abandoned.inc({ route: req.route?.path ?? 'unknown' });
  });
  next();
}
A middleware that calls next() and then also writes to the response produces ERR_HTTP_HEADERS_SENT the moment the route handler responds, and the error appears to come from the handler rather than the middleware. Guard every branch: exactly one of "end the response" or "call next" per execution path.

Register a middleware once

Middleware that runs twice is a real defect with a boring cause: registering it both on the app and on a router mounted into that app. The symptom depends on what the middleware does — two request ids, a double-counted metric, a rate limit that fires at half the intended threshold, or a body parsed twice. Give every cross-cutting middleware exactly one registration point near the top of the application and keep routes free of it, so the question "how many times does this run" has a one-line answer.

7.5 Error handling across a framework

Error handling is a design decision about who knows what. The handler knows the business context; the framework knows the transport; the logger knows the audience. A good design keeps those roles separate instead of scattering res.status(500) through business code.

Typed errors, translated once

Define a small hierarchy — a base AppError carrying status, code and optional details, and subclasses for validation, not-found and conflict. Business code throws; a single translator at the edge converts a typed error into a response, and an untyped error into a logged 500 with a generic message. Nothing else in the codebase should know about HTTP status codes.

// errors.js - the whole vocabulary the application needs
export class AppError extends Error {
  constructor(message, { status = 500, code = 'internal', details } = {}) {
    super(message, { cause: undefined });
    this.name = new.target.name;
    this.status = status;
    this.code = code;
    this.details = details;
    Error.captureStackTrace?.(this, new.target);   // V8: drop the constructor
  }
}
export class ValidationError extends AppError {
  constructor(details) { super('validation failed', { status: 422, code: 'validation', details }); }
}
export class NotFoundError extends AppError {
  constructor(what) { super(`${what} not found`, { status: 404, code: 'not_found' }); }
}
export class ConflictError extends AppError {
  constructor(what) { super(`${what} already exists`, { status: 409, code: 'conflict' }); }
}

Transport failures are not application failures

A database connection reset, a DNS failure and a zero-byte response are infrastructure problems, not business outcomes, and lumping them into the same Error object destroys the information needed to alert on them. Tag them — an isOperational flag, or a separate DependencyError class — so an operator can distinguish "the user typed bad input" from "the payments provider is down". Only the second should page anyone.

// the single translator, in both frameworks
function toResponse(err) {
  if (err instanceof AppError && err.status < 500) {
    return { status: err.status, body: { code: err.code, message: err.message, details: err.details } };
  }
  return { status: 500, body: { code: 'internal', message: 'Internal Server Error' } };
}

// Express
app.use((err, req, res, _next) => {
  const { status, body } = toResponse(err);
  if (status === 500) req.log.error({ err, requestId: req.id }, 'unhandled');
  res.status(status).json(body);
});

// Fastify
fastify.setErrorHandler((err, req, reply) => {
  const { status, body } = toResponse(err);
  if (status === 500) req.log.error({ err }, 'unhandled');
  reply.code(status).send(body);
});
Set process.on('unhandledRejection') and process.on('uncaughtException') to log and then exit with a non-zero code. Continuing after an uncaught exception leaves the process in an unknown state; a supervisor or orchestrator restarting a clean process is the only reliable recovery, and a loud crash is what makes it happen.

8.1 child_process: spawn, exec and fork

Some work is not JavaScript and does not belong in a worker thread: a compiler, an image tool, a shell command, another Node program. The four APIs differ mainly in whether they go through a shell and whether they buffer output.

The four APIs

APIShellOutputUse when
spawnNoStreamedAnything long-running or large; the default choice
execYesBuffered, cappedA short command needing shell features or a pipe
execFileNoBuffered, cappedA known binary with a fixed argument list
forkNoIPC channelAnother Node module, communicating by messages

spawn never involves a shell, so arguments are passed as an array and are not reinterpreted. That is the whole security argument: exec('convert ' + filename) with a filename containing a semicolon runs a second command, while spawn('convert', [filename]) cannot. If you need a shell for a pipe or a wildcard, pass the assembled string deliberately and validate every interpolated value first.

import { spawn } from 'node:child_process';

// streaming: the child's stdout arrives chunk by chunk, memory stays flat
const ffmpeg = spawn('ffmpeg', ['-i', input, '-f', 'mp4', '-movflags', 'frag_keyframe', 'pipe:1'],
  { stdio: ['ignore', 'pipe', 'pipe'] });

ffmpeg.stdout.pipe(res);                 // stream straight to the HTTP client

let stderr = '';
ffmpeg.stderr.on('data', (b) => { stderr += b; if (stderr.length > 64_000) stderr = stderr.slice(-64_000); });
ffmpeg.on('error', (err) => { /* ENOENT: binary not found */ });
ffmpeg.on('close', (code, signal) => {
  if (code !== 0) console.error({ code, signal, stderr });
});

Timeouts, cancellation and zombie processes

A child process is a resource. It must be given a deadline, killed if it exceeds it, and reaped. Signal the whole process group where possible, because a shell child spawns grandchildren that survive a kill aimed only at the direct child. Never interpolate untrusted input into an argument that a tool treats as a filename or a URL; treat the child as an untrusted component and validate what comes back.

// wrapping spawn with a deadline and full cleanup
import { once } from 'node:events';

async function run(command, args, { timeoutMs = 10_000, input } = {}) {
  const child = spawn(command, args, { stdio: ['pipe', 'pipe', 'pipe'] });
  const out = [], err = [];
  child.stdout.on('data', (c) => out.push(c));
  child.stderr.on('data', (c) => err.push(c));
  if (input) child.stdin.end(input); else child.stdin.end();

  const timer = setTimeout(() => child.kill('SIGKILL'), timeoutMs);
  const [code, signal] = await once(child, 'close');   // 'exit' may precede output flush
  clearTimeout(timer);

  if (signal) throw new Error(`${command} killed by ${signal}`);
  if (code !== 0) throw new Error(`${command} exited ${code}: ${Buffer.concat(err)}`);
  return Buffer.concat(out);
}
exec buffers all output and enforces a default maxBuffer of 1 MB, at which point it kills the child with an ERR_CHILD_PROCESS_STDIO_MAXBUFFER error. A command whose output grows with input data — a recursive listing, a database dump — silently fails at exactly the wrong moment. Either raise the limit deliberately or use spawn.

8.2 cluster: one port, many processes

A Node process uses one CPU core for JavaScript. The cluster module runs several copies of the same program, one per core, with the primary accepting connections and distributing them to the workers.

How the port is shared

The primary process opens the listening socket and does the accept(), then hands each connection to a worker over an IPC channel. Round-robin is the default distribution policy on all platforms now; the operating-system default sharing mode is available but spreads unevenly under bursty load. Because workers are separate processes, a crash in one does not affect the others, and the primary can restart it.

// graceful cluster: survive a worker crash, and replace it
import cluster from 'node:cluster';
import os from 'node:os';

if (cluster.isPrimary) {
  const n = os.availableParallelism();
  for (let i = 0; i < n; i++) cluster.fork();

  cluster.on('exit', (worker, code, signal) => {
    console.error(`worker ${worker.process.pid} died (${signal ?? code})`);
    if (!shuttingDown) cluster.fork();     // keep the pool at full size
  });

  let shuttingDown = false;
  process.on('SIGTERM', () => {
    shuttingDown = true;
    for (const w of Object.values(cluster.workers)) w.send('shutdown');
    // then let each worker exit; the primary exits when the pool is empty
  });
} else {
  // every worker runs the same server on port 3000 - no conflict, no proxy
  startServer();
  process.on('message', (msg) => { if (msg === 'shutdown') shutdown(); });
}

Why clustering is not free

Sessions, caches and rate-limit counters that used to live in a process-local Map now exist once per worker, so a user's next request may hit a worker that has never seen them. Anything shared moves to Redis or a database, and anything sticky requires either a central store or a load balancer that respects a cookie. Memory is multiplied by the worker count, and a hard crash-loop now produces a periodic flapping log rather than a single failure.

ConcernSingle processCluster of N
CPU-bound throughput1 coreUp to N cores
In-process stateShared and simplePer-worker; must move to a store
Memory floorOne heapN heaps
Crash blast radiusEverythingOne in-flight request set
Deploy complexityLowNeeds coordinated shutdown

Sticky sessions and the shared-state trap

Once a request may land on any of several workers, every value that used to be a process-local variable becomes a distributed-systems question. Caches, rate-limit counters, in-flight job maps and session objects must move to a shared store such as Redis, or a user's next request hits a worker that has never seen them. Long-lived connections — WebSockets, server-sent events, long polling — are pinned to one worker for their whole life, so a broadcast has to go through the shared store rather than through the process that happens to hold that socket.

8.3 Choosing between threads, processes and services

There are three ways to use more of a machine, and they solve different problems. Mixing them up is why "we added workers" sometimes makes a service slower.

The decision

Use a worker thread when the work is CPU-bound, the input and output are small relative to the computation, and sharing the process's lifecycle is acceptable. Use a child process or cluster when you need a crash to be isolated, when the work is a foreign binary, or when you want to use all cores for the whole application. Use a separate service when the work has a different scaling profile, a different release cadence, or different hardware needs — a model server on GPUs, an image pipeline with large memory.

// a small, reusable worker pool - the pattern that avoids spawn-per-request
import { Worker } from 'node:worker_threads';
import { cpus } from 'node:os';

class Pool {
  #workers = []; #queue = []; #idle = [];
  constructor(size = Math.max(1, cpus().length - 1), file) {
    for (let i = 0; i < size; i++) {
      const w = new Worker(file);
      w.on('message', (msg) => {
        const job = w._job; w._job = null;
        job.resolve(msg);
        this.#idle.push(w);
        this.#drain();
      });
      w.on('error', (err) => { w._job?.reject(err); });
      this.#workers.push(w); this.#idle.push(w);
    }
  }
  run(payload) {
    return new Promise((resolve, reject) => {
      this.#queue.push({ payload, resolve, reject });
      this.#drain();
    });
  }
  #drain() {
    while (this.#queue.length && this.#idle.length) {
      const w = this.#idle.pop();
      const job = this.#queue.shift();
      w._job = job;
      w.postMessage(job.payload);
    }
  }
  async close() { await Promise.all(this.#workers.map(w => w.terminate())); }
}

Sizing the pool

The honest answer is measured, but the starting point is availableParallelism() - 1: one core reserved for the event loop, so a parallelism of one leaves none for I/O bookkeeping. If the work is partly I/O, a larger pool helps; if it saturates memory bandwidth, more workers hurt. Instrument queue depth and job latency, and scale the pool to keep depth near zero without leaving cores idle.

Node's own webworker-style pools exist in libraries such as piscina, and they handle the details this example omits: worker recycling, task transfer lists, per-task abort signals and queue statistics. Writing the pool yourself is worthwhile once, to see the moving parts; after that, use the library.

Autoscale on the right signal

CPU utilisation is a poor autoscaling signal for a Node service, because a process waiting on a database, a queue or an upstream API sits at low CPU while every request is already slow. By the time CPU rises, the service is saturated. Scale on a signal that rises before that: in-flight requests, event-loop delay, queue depth or the age of the oldest item in a work queue. These measure the thing users actually experience, and they start moving while there is still capacity to add.

8.4 Signals, shutdown and supervisors

Deployment is a stream of starts and stops, so shutdown correctness determines availability more than throughput does. This section is the operational counterpart to the graceful-shutdown code in chapter 6.

The signals that matter

SignalMeaningCorrect response
SIGTERMTerminate politelyDrain, then exit 0
SIGINTCtrl+C / dev interruptSame, usually faster
SIGHUPTerminal closed on LinuxIn containers, often used to mean "reload config"
SIGUSR2Convention: restart workersRoll workers one at a time
SIGKILLUncatchableNothing; the process dies mid-write

A default SIGTERM handler already terminates the process, so installing one replaces that default. If your handler forgets to exit, the platform eventually sends SIGKILL and every in-flight request is reset. Always include a fallback timer that exits with a non-zero code if draining did not finish in time.

// the deadline that makes a shutdown handler safe to trust
const HARD_EXIT_MS = 20_000;

['SIGTERM', 'SIGINT'].forEach((sig) => {
  process.once(sig, async () => {
    const killer = setTimeout(() => {
      console.error('shutdown timed out; forcing exit');
      process.exit(1);
    }, HARD_EXIT_MS);
    killer.unref();                       // never keep the loop alive for this

    try {
      await shutdown();                   // drain from section 6.5
      clearTimeout(killer);
      process.exit(0);
    } catch (err) {
      console.error('shutdown failed', err);
      process.exit(1);
    }
  });
});

What a supervisor expects

A process manager, systemd unit or container orchestrator makes three assumptions: the process stays in the foreground, it logs to stdout and stderr rather than to a file, and its exit code means something. Exit 0 for a requested stop, 1 for a fatal error, so the supervisor distinguishes "we asked it to stop" from "it broke". Never fork a background daemon from inside the process — the supervisor then supervises the wrong thing.

# systemd unit: the four lines that matter most
[Service]
ExecStart=/usr/bin/node /srv/app/dist/server.js
Restart=on-failure
RestartSec=2
KillSignal=SIGTERM
TimeoutStopSec=25            # longer than the app's 20 s drain deadline
StandardOutput=journal
StandardError=journal
Do not call process.exit() in a normal request path. It terminates immediately, discarding buffered stdout and any pending write, so the very log line that would explain the failure is the one most likely to be lost. Set process.exitCode and return instead, and reserve exit() for the end of a deliberate shutdown.

9.1 Error classes and error chaining

A JavaScript Error is an ordinary object with a name, a message and a stack. Everything useful about error handling follows from treating it as data you can attach to, rather than a string you throw away.

What the runtime gives you

error.message is the human text, error.name is the constructor name, error.stack is a lazily-formatted string that includes frames from the throw site, and error.cause links to the error that provoked this one. The cause option, standardised with ES2022, is what turns a chain of wrapped failures into a readable tree instead of a single opaque message.

// chaining preserves both layers: what you were doing, and why it failed
try {
  await db.query('SELECT * FROM users WHERE id = $1', [id]);
} catch (cause) {
  throw new Error(`loading user ${id} failed`, { cause });
}

// the full tree prints from the outer throw, including the inner stack
// Error: loading user 42 failed
//     at loadUser (repo.js:12:11)
//   [cause]: Error: connect ECONNREFUSED 127.0.0.1:5432
//     at TCPConnectWrap.afterConnect [as oncomplete] (net.js:1141:16)

Adding fields, without breaking instanceof

Subclass Error, set this.name to the subclass name so logs are readable, and attach the fields the transport needs. This works natively in modern JavaScript; remember only that instanceof comparisons cross module boundaries badly when two copies of a package are installed, so a plain discriminated field such as code is more robust than a class check for anything that must survive serialisation.

class HttpError extends Error {
  constructor(message, { status, code, details, cause } = {}) {
    super(message, { cause });
    this.name = 'HttpError';
    this.status = status ?? 500;
    this.code = code ?? 'internal';
    this.details = details;
    Error.captureStackTrace?.(this, HttpError);  // hide the constructor frame
  }
  // a structured, serialisable view for logs and API responses
  toJSON() {
    return { name: this.name, message: this.message, status: this.status,
             code: this.code, details: this.details, cause: this.cause?.message };
  }
}

// special-cased aggregation, for when several operations failed
throw new AggregateError([err1, err2], 'all upstreams failed');
Never throw a string or a plain object. throw 'not found' loses the stack, breaks every instanceof Error check, and produces undefined for err.message in a logger that assumes an Error. The linter rule that bans it exists because the resulting debugging session is long and avoidable.

Where to catch, and where not to

Catch where you can add information or make a decision. Wrapping an error adds context; swallowing it removes a fact. A catch block that logs and returns a default silently converts a bug into a wrong answer, and the wrong answer is discovered weeks later by a customer. The correct shape is usually: catch, annotate, rethrow — and let one handler at the boundary decide what the user sees.

// annotating rather than swallowing
async function withRetry(fn, { attempts = 3, baseMs = 100 } = {}) {
  let lastErr;
  for (let i = 0; i < attempts; i++) {
    try { return await fn(); }
    catch (err) {
      lastErr = err;
      if (!isTransient(err)) throw err;              // do not retry a 400
      await delay(baseMs * 2 ** i + Math.random() * 50); // jittered backoff
    }
  }
  throw new Error(`retries exhausted`, { cause: lastErr });
}

const isTransient = (e) => e.code === 'ECONNRESET' || e.code === 'ETIMEDOUT' || e.status >= 500;

9.2 Errors in async code

Asynchrony breaks the stack-based intuition of try/catch. A rejection is a value, not a control-flow transfer, so an unobserved rejection is invisible until Node reports it and, by default, exits.

The three ways a rejection escapes

First, a .then without a following .catch. Second, an await inside a try in a different function from the catch — the rejection travels the promise chain, not the call stack. Third, a fire-and-forget call: doWork() on its own line with no await and no handler. The third is the dangerous one in a long-lived server, because the request that triggered it has already been answered.

// NEVER leave a promise unattended - attach a handler at the call site
saveAudit(event).catch((err) => logger.error({ err }, 'audit write failed'));

// or make the intent explicit with a helper that cannot be forgotten
function detach(promise, context) {
  promise.catch((err) => logger.error({ err, ...context }, 'background task failed'));
  return promise;                      // still awaitable where it matters
}

// a loop of independent awaits: one failure must not hide the others
const results = await Promise.allSettled(ids.map(id => syncOne(id)));
for (const r of results) {
  if (r.status === 'rejected') logger.warn({ err: r.reason }, 'sync failed');
}

Node's last line of defence

'unhandledRejection' fires for a rejected promise that was garbage-collected without a handler; 'uncaughtException' fires for a synchronous throw that escaped every frame. Node 15 and later terminate the process on an unhandled rejection, which is a deliberate hardening: a process that continues after an unknown failure is more dangerous than one that restarts. Install handlers to log enough to diagnose, then exit non-zero and let a supervisor restart cleanly.

// log loudly, then exit - do NOT continue serving after an unknown fault
process.on('uncaughtException', (err) => {
  logger.fatal({ err, kind: 'uncaughtException' }, 'fatal');
  // flush logs asynchronously, then die
  flushLogs().finally(() => process.exit(1));
});

process.on('unhandledRejection', (reason) => {
  logger.fatal({ err: reason, kind: 'unhandledRejection' }, 'fatal');
  flushLogs().finally(() => process.exit(1));
});

// async context lets a log line name the request that caused it
import { AsyncLocalStorage } from 'node:async_hooks';
const ctx = new AsyncLocalStorage();
export const logger = {
  info(fields, msg) { console.log(JSON.stringify({ ...ctx.getStore(), ...fields, msg })); },
};
app.use((req, _res, next) => ctx.run({ requestId: req.id }, next));
AsyncLocalStorage is the supported way to carry a request id through an async call chain without threading a parameter through every function. It costs less than the older async_hooks API it builds on, and the main caution is that a long-lived object created inside the context will keep that context reachable.

Per-request isolation without the old domain module

Node removed domain because it could not reliably attribute an asynchronous error to a request. AsyncLocalStorage is the supported replacement for the parts of that job that were sound: it carries the request id and any per-request logger down every await, so a stray rejection can be logged against the request that caused it. It cannot, and should not, swallow an error — a genuine unhandled rejection still needs to be logged and the process still needs to exit, because a service that continues after an unknown fault is serving answers nobody can trust.

9.3 The inspector and the profiler

Console logging finds out what happened; the inspector finds out why. Node exposes the same debugging protocol Chrome uses, so the DevTools front-end can attach directly to a running process.

Attaching a debugger

node --inspect file.js opens a WebSocket on port 9229 and prints a URL. Pasting that URL into Chrome's dedicated DevTools for Node gives breakpoints, a live scope inspector, a call stack and a heap view. --inspect-brk pauses on the first line, which is the only reliable way to debug module-level initialisation. In a container, bind the inspector to 0.0.0.0 and forward the port, and never expose it publicly — it is remote code execution by design.

# shell
node --inspect app.js                  # attach whenever you like
node --inspect-brk=0.0.0.0:9229 app.js # pause before the first line, all interfaces
node inspect app.js                    # the built-in CLI debugger instead

# a long-running production process: signal it to open the inspector
kill -USR1 $PID                        # Node listens on 9229 without --inspect

# let code decide when to break, in a REPL-like pause
node -e "setTimeout(() => { debugger; }, 1000)"

Profiling without a debugger

Two profiling modes ship with the runtime. --cpu-prof writes a sampling profile that Chrome DevTools can open as a flame graph, showing exactly which function consumed the time. --heap-prof shows where memory was allocated. For a live process, the inspector protocol exposes the same profilers over CDP, and --diagnostic-report-on-fatalerror writes a JSON report — stack, handles, memory, environment — at the moment of a fatal fault.

# shell - capture a 30-second CPU profile of a real workload
node --cpu-prof --cpu-prof-dir=./profiles --cpu-prof-interval=500 app.js
# -> profiles/CPU.20261014.101500.12345.0.001.cpuprofile, open in DevTools

# heap sampling, useful for finding allocation hot spots rather than leaks
node --heap-prof --heap-prof-dir=./profiles app.js

# write a diagnostic report on demand, from inside the process
node -e "process.report.writeReport('./report.json'); console.log('written')"

# and automatically, when the process dies badly
node --report-on-fatalerror --report-directory=./reports app.js
A production memory leak is usually diagnosed as a heap snapshot difference: take one snapshot, exercise the suspected path a few thousand times, take a second, and look at objects that grew. --heapsnapshot-signal=SIGUSR2 makes a running process dump one on command, without a restart.

Debugging a container or a remote host

Start the process with the inspector bound to all interfaces, --inspect=0.0.0.0:9229, and reach the port through a tunnel — kubectl port-forward, an SSH local forward, or the platform's equivalent. Never publish 9229 beyond the pod or the host, because the inspector protocol can evaluate arbitrary code in the process; exposing it is a remote code execution vulnerability with a friendly user interface. For a one-off look at a production pod, prefer a diagnostic report or a CPU profile over an interactive debugger, since both are read-only and neither pauses the process for other users.

9.4 Structured logging

A log line is an event record, not a sentence. Writing JSON gives you fields you can filter, aggregate and alert on; writing prose gives you text you can only grep, which fails exactly when volume is high and the question is specific.

Log to stdout, in JSON, with a level

The container or supervisor collects stdout; the application should not decide where logs go. Emit one JSON object per line with a timestamp, a level, a message and contextual fields. Use a numeric level so ordering is trivial, and route by level rather than mixing everything into one stream. Pino is the common library because it serialises to a stream without allocating an intermediate string, but the shape below is the part that matters.

// a minimal structured logger with levels and redaction
const LEVELS = { trace: 10, debug: 20, info: 30, warn: 40, error: 50, fatal: 60 };
const MIN = LEVELS[process.env.LOG_LEVEL ?? 'info'] ?? 30;
const REDACT = new Set(['password', 'token', 'authorization', 'cookie', 'secret']);

function redact(obj, depth = 0) {
  if (depth > 6 || obj === null || typeof obj !== 'object') return obj;
  if (Array.isArray(obj)) return obj.map((v) => redact(v, depth + 1));
  return Object.fromEntries(Object.entries(obj).map(([k, v]) =>
    [k, REDACT.has(k.toLowerCase()) ? '[redacted]' : redact(v, depth + 1)]));
}

function log(level, fields, msg) {
  if (LEVELS[level] < MIN) return;                 // cheap early exit
  const line = JSON.stringify({ time: new Date().toISOString(), level, msg, ...redact(fields) });
  (level === 'error' || level === 'fatal' ? process.stderr : process.stdout).write(line + '\n');
}
export const logger = Object.fromEntries(
  Object.keys(LEVELS).map((l) => [l, (fields, msg) => log(l, fields, msg)]));

What to log, and what never to

Log the decision boundary: the request id, the route, the status, the duration, and the outcome. Log every dependency call with its latency, because that is where outages start. Log at error level only for conditions a human must act on — if everything is an error, the alert is useless. Never log credentials, session tokens, full request bodies, personal data or anything from an Authorization header, because logs are copied, shipped to third-party aggregators, kept for months, and read by a wider audience than the database.

// request logging: one line in, one line out, correlated by id
app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  logger.info({ requestId: req.id, method: req.method, path: req.path }, 'request');
  res.on('finish', () => {
    logger.info({
      requestId: req.id, method: req.method, path: req.path,
      status: res.statusCode,
      ms: Number(process.hrtime.bigint() - start) / 1e6,
    }, 'response');
  });
  next();
});

// ERROR logs carry the exception; INFO logs carry the fact
logger.error({ err, requestId: req.id, userId: req.user?.id }, 'payment failed');
logger.info({ orderId, amount, requestId: req.id }, 'order created');
Synchronous console writes in a hot path are a performance problem: console.log to a pipe is synchronous on Unix, so a high-volume debug line can dominate request latency. Gate verbose logging behind a level check that the logger performs before formatting, and never build a large object purely to pass it to a disabled log call.

10.1 The built-in test runner

Since Node 20 the test runner is part of the runtime and stable: no framework, no transpiler, no configuration file. It covers the whole common case — discovery, grouping, hooks, subtests, watch mode and reporting.

Anatomy of a test file

Import test from node:test and call it with a name and a function. The function may be async; returning a promise makes the runner wait. Group related cases with describe and it if you prefer that vocabulary, and use hooks for setup and teardown. A test that creates a resource must release it in after, or the runner will keep a handle open and the process will not exit cleanly.

// test/sum.test.js - run with: node --test
import { test, describe, before, after, beforeEach } from 'node:test';
import assert from 'node:assert/strict';

describe('sum', () => {
  let calls = 0;
  beforeEach(() => { calls++; });

  test('adds numbers', () => {
    assert.equal(sum(2, 3), 5);
  });

  test('is async-aware', async () => {
    assert.equal(await sumAsync(2, 3), 5);
  });

  test('rejects non-numbers', () => {
    assert.throws(() => sum('2', 3), /must be a number/);
  });

  test('skipped with a reason', { skip: 'not implemented yet' }, () => {});
  test('a planned failure is allowed', { todo: true }, () => { assert.fail('later'); });
});

Subtests and the runner's CLI

Passing a callback argument to test gives you a TestContext, whose t.test() creates a subtest that runs in sequence and whose failure is attributed to the parent. The point is granularity: one subtest failing should not invalidate its siblings. Concurrency, filtering, reporters and isolation are all flags on the runner rather than code you write.

# shell

node --test --watch                  # re-run on change; combine with --test-only
node --test --test-name-pattern="auth"
node --test --test-concurrency=4
node --test --test-reporter=spec     # or tap, dot, junit
node --test --test-reporter=junit --test-reporter-destination=report.xml
node --test --test-isolation=none    # faster, but tests share one process
node --run test                      # run the package.json script without npm
// subtests: independent failures, one shared fixture
test('parser', async (t) => {
  const parser = await createParser();

  await t.test('accepts integers', () => {
    assert.equal(parser.parse('42'), 42);
  });
  await t.test('rejects trailing text', () => {
    assert.throws(() => parser.parse('42abc'), /unexpected input/);
  });
});

// a failing subtest must not leak: register teardown on the context
test('with a server', async (t) => {
  const server = createServer().listen(0);
  t.after(() => server.close());           // always runs, pass or fail
  await once(server, 'listening');

Name a file so discovery finds it: *.test.js, *-test.js, *_test.js, test.js, test-*.js, or anything under a test/ directory. A test file that is never discovered is a test that passes forever and proves nothing, so print the runner's file count in CI at least once.

Test files are part of the build, not an afterthought

The runner discovers files by name, so a test that is never found passes forever and proves nothing. Keep tests beside the code they cover or under a top-level test/ directory, and name them so discovery is obvious. By default each file runs in a separate child process, which gives every file a clean module registry and its own globals — slow, but the reason one file's side effects cannot corrupt another's. --test-isolation=none shares a single process and is noticeably faster for a large suite, at the cost of any shared state between files becoming a real hazard.

Testing asynchronous behaviour deterministically

Timers, retries and timeouts make tests slow and flaky. The runner can replace the timer functions inside a test so time advances only when you say so, which turns a 30-second backoff into a microsecond assertion. Where the runner's fake timers do not fit, inject the clock: pass a now function or a delay function into the code under test, and pass a controllable one in the test.

// fake timers: the retry logic is exercised without waiting for it
test('retries with backoff', async (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] });
  let attempts = 0;
  const job = withRetry(() => { attempts++; return Promise.reject(new Error('flaky')); }, { attempts: 3 });

  t.mock.timers.tick(0);
  t.mock.timers.tick(100);
  t.mock.timers.tick(250);
  await assert.rejects(job);
  assert.equal(attempts, 3);
});

// dependency injection, the version with no mocking library at all
export function createUserService({ now = Date.now, id = () => crypto.randomUUID() } = {}) {
  return { create: (email) => ({ id: id(), email, createdAt: now() }) };
}
test('stamps the id and time from the injected clock', () => {
  const svc = createUserService({ now: () => 1_700_000_000_000, id: () => 'fixed' });
  assert.deepStrictEqual(svc.create('a@b.c'), { id: 'fixed', email: 'a@b.c', createdAt: 1_700_000_000_000 });
});
Avoid asserting on wall-clock durations in tests. assert.ok(elapsed < 100) passes on a developer laptop and fails on a loaded CI runner, producing a flaky test that everyone learns to re-run. 10.3 Mocking without a framework

A mock is a stand-in whose behaviour you control. The runner's built-in mocking covers functions, methods, timers and modules, which is enough for most services — and preferring real objects with injected seams over mocks keeps most tests honest.

Spies, stubs and the context object

Each test receives a TestContext whose t.mock is automatically restored afterwards, so a mock cannot leak into a sibling test. mock.fn wraps a function and records calls; mock.method replaces a method on an object. Both expose mock.calls and mock.callCount(), so you can assert on how something was used rather than only on what it returned.

test('emails the owner once per order', (t) => {
  const send = t.mock.fn(async () => ({ id: 'msg_1' }));
  const svc = createOrderService({ mailer: { send } });

  await svc.place({ id: 'o1', owner: 'a@b.c', total: 10 });

  assert.equal(send.mock.callCount(), 1);
  assert.deepStrictEqual(send.mock.calls[0].arguments, [{ to: 'a@b.c', template: 'order' }]);
});

test('retries the mailer on a 503', async (t) => {
  const send = t.mock.fn()
    .mock.mockImplementationOnce(async () => { throw Object.assign(new Error(), { status: 503 }); })
    .mock.mockImplementationOnce(async () => ({ id: 'msg_2' }));
  // ...
});

Should you mock the module or inject the dependency?

Module mocking replaces an import for the duration of a test, which is convenient for a hard-wired third-party client and a trap when used as the default strategy: the test then asserts that your code calls the mock the way the mock expects, rather than that the behaviour is correct. Prefer constructor or argument injection — it is plain JavaScript, works with any runner, and makes the seam visible in the production code.

// injection: no mocking library, no module interception
export function createRepo({ db }) {         // db is passed in
  return { findUser: (id) => db.query('SELECT ... WHERE id = $1', [id]) };
}
test('propagates a database error', async () => {
  const repo = createRepo({ db: { query: async () => { throw new Error('down'); } } });
  await assert.rejects(repo.findUser('1'), /down/);
});

// module mocking is still the tool when the import is not yours to change
// (Node supports it via the test runner's module mocking hooks)
Test doubles are ranked by fidelity: a real object beats an in-process fake, a fake beats a stub, and a stub beats a deep mock of an internal collaborator. Reach down that list only as far as you must. Tests that mock the database tend to pass while production is down, because they test the mock.

Test data should be built, not pasted

A fixed fixture object quietly drifts away from the shape the production code actually expects: a field is added, the fixture is not updated, and the test keeps passing because nothing exercises the new field. A factory function with per-test overrides solves this. It builds a valid value by default, accepts only the fields a given test cares about, and — most usefully — can be asserted against the same schema the API validates with, so a schema change breaks the factory once instead of surprising every test.

10.4 Coverage and what it does not tell you

Coverage measures which lines, branches and functions executed. It is a useful signal about untested code and a poor signal about test quality, because a line can be executed without any assertion being checked.

Running the built-in coverage collector

The runner collects coverage itself, using the V8 coverage data, so no instrumentation step and no transform is required. Point it at the source directory, exclude test files, and — in CI — set thresholds so the build fails when coverage drops rather than after the fact.

# shell
node --test --experimental-test-coverage
# Node 24 also accepts explicit thresholds and include/exclude globs:
node --test \
  --experimental-test-coverage \
  --test-coverage-lines=85 \
  --test-coverage-branches=75 \
  --test-coverage-functions=90 \
  --test-coverage-exclude='**/*.test.js' \
  --test-coverage-include='src/**/*.js'

Reading the numbers correctly

Function coverage is usually the most actionable: an entire function that never ran is either dead code or an untested path. Line coverage flatters uninformative tests, because a line inside a loop is counted once no matter how many iterations matter. Branch coverage is where the real defects hide — the else of a validation check, the catch of a network call, the default arm of a switch. Set a threshold you will actually defend, and refuse to game it with assertion-free tests.

MetricAnswersBlind spot
LineWas this statement reached?Says nothing about which path or with what data
FunctionDid this function ever run?A called function may be called only with a trivial input
BranchWas each decision outcome taken?Does not check that the outcome was correct
Do not chase a coverage number as a target. A team measured on line coverage writes tests that execute lines, and the resulting suite is large, slow and unable to catch a regression — the worst combination, because it looks like safety while providing none. Measure coverage to find gaps, not to certify quality.

11.1 Input validation and injection

Every vulnerability begins with data you did not author arriving somewhere that assumed you did. Validation at the boundary converts an untrusted blob into a typed value, and every layer after it can then assume the value is well formed.

Allowlist, type, bound — in that order

Decide what is permitted rather than what is forbidden, because a denylist is always incomplete: it misses encodings, case variants and new syntax. Validate the type, then the shape, then the bounds — length, range, cardinality. Reject unknown fields instead of ignoring them, which is what turns a mass-assignment bug into a validation error. Reject an oversized array before iterating it.

// a validator written by hand: explicit, dependency-free, and complete
function parseCreateUser(input) {
  const errors = [];
  if (typeof input !== 'object' || input === null || Array.isArray(input)) {
    throw new ValidationError([{ field: '$', message: 'body must be an object' }]);
  }
  const allowed = new Set(['email', 'name', 'age']);
  for (const key of Object.keys(input)) {
    if (!allowed.has(key)) errors.push({ field: key, message: 'unknown field' });
  }
  const email = input.email;
  if (typeof email !== 'string' || email.length > 254 || !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email)) {
    errors.push({ field: 'email', message: 'invalid email' });
  }
  const age = input.age;
  if (age !== undefined && (!Number.isInteger(age) || age < 13 || age > 130)) {
    errors.push({ field: 'age', message: 'must be an integer 13..130' });
  }
  if (errors.length) throw new ValidationError(errors);
  return { email: email.toLowerCase(), name: String(input.name ?? '').slice(0, 80), age };
}

Prototype pollution, and other object-shaped attacks

A recursive merge that copies untrusted keys onto a target can write __proto__, constructor or prototype and alter behaviour for every object in the process. The defence is not a regex on the key; it is to avoid merging untrusted objects into prototypes at all — build the result explicitly, or use Object.create(null) and skip these keys. The same discipline applies to querystring-style parsers that produce nested objects from bracket notation.

// the shape of the bug, and the shape of the fix
const payload = JSON.parse('{"__proto__":{"isAdmin":true}}');
const user = {};
Object.assign(user, payload);      // does NOT pollute in modern engines...
function unsafeMerge(target, src) {
  for (const k of Object.keys(src)) {
    if (src[k] && typeof src[k] === 'object') unsafeMerge(target[k] ??= {}, src[k]);
    else target[k] = src[k];       // ...but a recursive merge WILL
  }
}
unsafeMerge({}, { constructor: { prototype: { isAdmin: true } } });  // dangerous

// typed request surfaces are regression-safe, and serialisable
// Zod / Ajv / TypeBox: declare once, get a parsed value AND a 422 response
const CreateUser = z.object({
  email: z.string().email().max(254),
  name: z.string().max(80).optional(),
}).strict();                        // .strict() rejects unknown keys

Regex denial of service is the most under-rated of these, because the vulnerable pattern looks innocent and the input that triggers it is one crafted string. A pattern with nested quantifiers over overlapping alternatives — (a+)+, (\w+\s?)* — is exponential. Give every regex that sees user input a length cap on the input, and prefer simple patterns wherever a parser would do.

11.2 Secrets and configuration

A secret is any value whose disclosure grants access. The goal is not to hide it well but to ensure it exists in as few places as possible, for as short a time as possible, and can be rotated without a deploy.

Loading configuration

Node reads .env files natively with --env-file, which keeps the file-walking and quoting out of application code. The file must be in .gitignore, and a committed .env.example should list the keys with placeholder values so a new environment can be set up from the repository alone. Validate the environment at startup and fail immediately on a missing or malformed value, because a process that boots with an undefined secret fails later, less clearly.

# shell
node --env-file=.env app.js
node --env-file-if-exists=.env.local app.js   # tolerate absence in CI
node -p "process.env.DATABASE_URL ? 'set' : 'MISSING'"

// config.js - parse once at boot, validate loudly, export typed values
function required(key) {
  const value = process.env[key];
  if (!value) throw new Error(`missing required env var: ${key}`);
  return value;
}
export const config = Object.freeze({
  env: process.env.NODE_ENV ?? 'development',
  port: Number(process.env.PORT ?? 3000),

  jwtSecret: required('JWT_SECRET'),

Where secrets should live in production

Environment variables are the common default and are readable by anything that can read /proc/<pid>/environ or a crash dump on the same host, and they are inherited by every child process. A mounted file with restrictive permissions is safer when the platform supports it, and a secret manager — Vault, AWS Secrets Manager, a Kubernetes Secret mounted as a volume — is safer still because access is auditable and rotation is central. Whatever the mechanism, keep the secret out of the image, out of the repository and out of the logs.

// never put a secret in a URL or a log field — rotate-on-leak becomes urgent
logger.info({ url: req.url }, 'request');         // ?token=... ends up in logs
logger.info({ url: req.url.replace(/token=[^&]+/, 'token=[redacted]') }, 'request');

// prefer short-lived credentials: assume a role, fetch a token, refresh it
let cached;
async function getDbPassword() {
  if (cached && cached.expiresAt > Date.now() + 60_000) return cached.value;
  const res = await fetch(process.env.SECRET_ARN);   // instance/task identity
  const { SecretString, Expiration } = await res.json();
  cached = { value: JSON.parse(SecretString).password, expiresAt: Date.parse(Expiration) };
  return cached.value;
}
Rotation is the property that matters most. A secret that requires a code change and a redeploy to replace is a secret nobody replaces under pressure. Design the read path so the value is fetched or refreshed at runtime, so rotation is an operational action rather than an engineering project.

CORS, cookies and rate limits

CORS is a browser-enforced response policy, not a server-side access control, so it protects users from a site they visit and never protects your API from a program. Reflect an explicit allowlist, never the request origin, and if you send credentials the wildcard origin is rejected by the browser anyway. Cookies carrying a session need HttpOnly, Secure and SameSite set deliberately: Lax stops cross-site form posts, and Strict additionally stops top-level navigations from carrying the cookie.

// explicit CORS: allowlist, credentials, and a preflight that actually answers
const allowed = new Set(['https://app.example.com', 'https://admin.example.com']);
app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (origin && allowed.has(origin)) {
    res.setHeader('access-control-allow-origin', origin);
    res.setHeader('vary', 'Origin');                     // cache correctness
    res.setHeader('access-control-allow-credentials', 'true');
    res.setHeader('access-control-allow-methods', 'GET,POST,PATCH,DELETE');
    res.setHeader('access-control-allow-headers', 'content-type,authorization');
  }
  if (req.method === 'OPTIONS') return res.writeHead(204).end();
  next();
});

// session cookie flags that are not optional
res.cookie('sid', token, {
  httpOnly: true,          // unreachable from JavaScript - blocks XSS theft
  secure: true,            // HTTPS only
  sameSite: 'lax',         // blocks cross-site POST; use 'strict' where possible
  maxAge: 1000 * 60 * 60,  // bounded lifetime
  path: '/',
});
Rate limiting is a correctness requirement, not a nicety: login, password reset, OTP verification and any endpoint that touches an external paid service must be limited per account and per IP. In a clustered deployment the counter must live in a shared store, or each worker permits the full quota and the effective limit is multiplied by the worker count.

11.4 Dependencies and the supply chain

A modern Node service has hundreds of transitive dependencies, each able to run code at install time and at require time. Supply-chain hygiene is therefore part of the application's security surface, not a separate concern.

Install-time safety

package-lock.json or pnpm-lock.yaml records an integrity hash per tarball, so a substituted package fails verification. npm ci installs strictly from the lockfile and never rewrites it. Lifecycle scripts — preinstall, postinstall — run arbitrary code as your user, which is the primary vector for a compromised dependency, so --ignore-scripts is worth enabling where the dependency graph tolerates it.

# shell - the defaults worth changing

npm audit --audit-level=high    # fail the build on a high or critical advisory
npm audit signatures            # verify registry signatures and attestations

Choosing and governing dependencies

Every dependency is a permanent liability, so the gate should be "is this worth it". Check the maintenance signal — recent releases, responsive issues, a security policy, more than one maintainer. 12.1 Finding the bottleneck before fixing it

Performance work without measurement produces changes that are hard to justify, easy to revert and occasionally harmful. The discipline is to reproduce the problem, locate it, change one thing, and re-measure with the same method.

Measure at the boundary, not by intuition

A load tool generates traffic and reports latency percentiles and throughput; the runtime's own profiler says which function consumed the CPU. Averages hide the problem, so always look at p95 and p99 — the users who matter are in the tail, and a service whose mean is 20 ms but whose p99 is 4 seconds is broken for one percent of requests. Record the event-loop delay alongside, because a rising p99 with a flat CPU trace usually means waiting on a dependency rather than burning cycles.

# -> Latency p50/p97.5/p99, Req/Sec, non-2xx count

# run the load, stop the process, open the .cpuprofile in DevTools

  try { return await fn(); }
  finally {
    performance.mark(`${label}:end`);
    performance.measure(label, `${label}:start`, `${label}:end`);
  }
}

await timed('db.listItems', () => db.query(/* ... */));
Beware optimisation that only moves the cost. Caching a query makes the endpoint faster and the cache a new dependency with its own failure mode; pushing work to a worker makes the main thread responsive and adds serialisation. Every change should state which metric it improves and which one it degrades, or it is not a trade-off but a hope.

12.2 Configuration, environment and runtime flags

The environment decides how the process behaves before a line of your code runs. Getting flags and memory settings right prevents an entire class of production incident, most of all the container OOM kill.

NODE_ENV and the flags worth setting

NODE_ENV=production is read by many libraries to disable development conveniences: Express caches views, some ORMs skip query logging, and several caches enable themselves. NODE_OPTIONS injects flags into a process you do not launch directly, which is exactly what a platform or a systemd unit needs — and precisely why the platform restricts which options it will accept from an inherited environment.

# shell / Dockerfile ENV
NODE_ENV=production
NODE_OPTIONS="--max-old-space-size=1536 --enable-source-maps"
UV_THREADPOOL_SIZE=8
LOG_LEVEL=info

# enable source maps so stack traces name TypeScript sources, not dist output
node --enable-source-maps dist/server.js

# cap the V8 heap BELOW the container limit, so GC runs before the OOM killer
# container memory limit 2 GiB -> heap limit ~1.5 GiB leaves room for
# buffers (allocated outside the V8 heap) and native memory

Memory in containers is the subtle part

Buffers, streams' internal pools and native allocations live outside the V8 heap, so a process well inside its heap limit can still exceed a container's memory limit and be killed without a JavaScript error — the classic silent OOMKilled with no stack trace. Leave real headroom between --max-old-space-size and the container limit, and remember that concurrency multiplies the buffer side: a thousand in-flight requests each holding a 1 MB buffer is a gigabyte regardless of what V8 thinks its heap is.

# Kubernetes: an explicit limit, matching Node flags, and a JVM-style ratio
resources:
  requests: { memory: "512Mi", cpu: "250m" }
  limits:   { memory: "2Gi",   cpu: "2000m" }
env:
  - name: NODE_OPTIONS
    value: "--max-old-space-size=1536"   # ~75% of the limit

# and a readiness/liveness split, so a slow dependency never restarts a
# process that is merely waiting on it
readinessProbe: { httpGet: { path: /ready, port: 3000 }, periodSeconds: 5 }
livenessProbe:  { httpGet: { path: /live,  port: 3000 }, periodSeconds: 20, failureThreshold: 3 }
Separate /live from /ready. Liveness answers "is this process wedged and should be restarted", so it must not touch a dependency. Readiness answers "should traffic be sent here", so it may check the database. Wiring liveness to the database turns a brief outage of a dependency into a fleet-wide restart storm.

12.3 Packaging with Docker

The image is the deployment artefact: it should contain the application and its runtime, nothing else, and be reproducible from the lockfile. Multi-stage builds make that possible without shipping a compiler or the dev dependencies.

A multi-stage, non-root image

Build in one stage with the full toolchain and install production dependencies in another, then copy only the output and the production modules into the final layer. Pin the base image to a major version so builds are consistent, use a minimal base, run as a non-root user, and set the entrypoint to the server directly so signals reach the process.

# Dockerfile
# ---- deps: install exactly what the lockfile records ----
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile --prod=false

# ---- build: compile, run tests, produce dist/ ----
FROM node:24-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN pnpm run build

# ---- runtime: the smallest layer that can serve ----
FROM node:24-alpine AS runtime
ENV NODE_ENV=production NODE_OPTIONS=--max-old-space-size=1024
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile --prod && pnpm store prune
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
# exec form, so SIGTERM reaches node directly rather than a shell
CMD ["node", "dist/server.js"]

Signals, PID 1 and cache hygiene

PID 1 in a container has different signal semantics from an ordinary process: a shell that does not forward signals is why a container ignores SIGTERM and is killed after the grace period every single time. Using the exec form of CMD avoids a shell entirely; if an init is needed to reap zombies, add CMD ["node", "--run", "start"] style direct invocations or docker run --init. A .dockerignore keeps node_modules, .git and test fixtures out of the build context, which both speeds the build and shrinks what a layer can leak.

Layers are content-addressed and retained: deleting a file in a later RUN removes it from the final filesystem but not from the image history, where anyone with the image can recover it. Pass secrets at run time through the orchestrator's secret mechanism, never through ENV or a committed .env.

Something has to start the process, restart it when it dies, and put it behind TLS and a stable address. Which component owns that responsibility depends on where the application runs — but not on whether the job is done.

pm2 start dist/server.js -i max --max-memory-restart 1G --time

What the reverse proxy must set

A proxy terminates TLS, compresses, caches, and forwards a few headers the application needs. The two that are most often missing are Host, without which every absolute URL your app generates is wrong, and the forwarding headers that identify the original client — which must be trusted only from the proxy's own address. Upstream keep-alive must be enabled, or every request pays a fresh TCP handshake.

# nginx: proxy to a Node app, with keep-alive upstream and correct timeouts
upstream app {
  server 127.0.0.1:3000;
  keepalive 64;                     # reuse upstream connections
}
server {
  listen 443 ssl http2;
  server_name app.example.com;

  location / {
    proxy_pass http://app;
    proxy_http_version 1.1;         # required for upstream keepalive
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # keep this BELOW the app's server.keepAliveTimeout (e.g. 65s)
    proxy_read_timeout 60s;
    proxy_connect_timeout 5s;
    client_max_body_size 10m;       # reject huge uploads before Node sees them
  }
}
The rule that keeps a deployment boring: one component decides where traffic goes, one decides when the process restarts, and the application decides only how to shut down. When a PaaS, a proxy and a local process manager all try to own restarts, the result is duplicate process trees, double-started ports and an outage that is nobody's fault.

Rolling deploys and the in-flight request

A rolling deploy replaces instances one at a time, and correctness depends on the load balancer, not on the application alone. The instance must fail readiness first, wait long enough for the balancer to stop sending new connections, then receive SIGTERM and drain. Clients that reuse connections — proxies, HTTP/2 pools, keep-alive clients — can hold a socket open to an instance that is already draining, which is why the shutdown deadline must exceed the longest plausible request and why idle connections are closed explicitly. Getting the order wrong produces intermittent 502s during every deploy, a symptom that never reproduces in development.

How to practise

Five exercises, roughly in order of difficulty, each producing something you keep. Build a static file server from node:http with ETags and range support, then rewrite it on top of Express and compare the line counts. Write a stream pipeline that reads a CSVs of logs, filters rows, redacts a token and writes gzip output, using only stream/promises. Turn a CPU-heavy function into a fixed worker pool and measure p99 latency under load before and after. Write a JSON API with no framework, including request-id correlation, structured logging, a typed error hierarchy and a bounded body reader. Finally, containerise it, add a readiness endpoint, and confirm that SIGTERM drains in-flight requests before the process exits.

// the smallest possible end-to-end check of the whole toolchain
// 1. server.js writes a JSON response; 2. probe.js asserts it; 3. run both
// server.js
import { createServer } from 'node:http';
export const server = createServer((req, res) => {
  res.writeHead(200, { 'content-type': 'application/json' });
  res.end(JSON.stringify({ ok: true, pid: process.pid }));
});

// probe.test.js - node --test probe.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { once } from 'node:events';
import { server } from './server.js';

test('responds with JSON', async (t) => {
  server.listen(0);
  t.after(() => server.close());          // no leaked handle, no hung runner
  await once(server, 'listening');
  const res = await fetch(`http://127.0.0.1:${server.address().port}/`);
  assert.equal(res.status, 200);
  assert.equal(res.headers.get('content-type'), 'application/json');
  assert.equal((await res.json()).ok, true);
});
