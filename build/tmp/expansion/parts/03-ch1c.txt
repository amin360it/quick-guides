<h3 id="ch1-3" data-toc>1.3 Hello, world — and the compiler as teacher</h3>
<p class="topic-desc">Your first Rust program is also your first real interaction with the compiler, and the compiler is deliberately talkative. Learning to read its diagnostics — location, cause, then a concrete suggested fix — is the fastest skill you can acquire in this language.</p>

<h4 id="ch1-3-new">cargo new and the standard layout</h4>
<p><code>cargo new hello</code> creates <code>src/main.rs</code> and a <code>Cargo.toml</code>, and initialises git. The layout is the contract: every cargo project looks the same, so tooling and other engineers do not need to learn per-project structure. The binary's entry point is the <code>main</code> function in <code>src/main.rs</code>; <code>println!</code> writes a line to standard output.</p>
<div class="codeWrap"><pre><code>$ cargo new hello
$ cd hello
# src/main.rs  — the file cargo created for you:
fn main() {
    println!("Hello, world!");
}

# $ cargo run
# Hello, world!
# the result is a native binary in target/debug/hello.exe
# (or target/debug/hello on Linux/macOS)</code></pre></div>

<h4 id="ch1-3-errors">Reading a compiler error</h4>
<p>Every rustc diagnostic names the error code, points at the offending line with a caret, and — crucially — usually suggests the fix. Do not fear the red text; it is a code review that runs at every build. The error below is the first one most people meet: variables are immutable by default, so assigning twice to <code>answer</code> is rejected before the program ever runs.</p>
<div class="codeWrap"><pre><code>fn main() {
    let answer = 40;
    answer += 2;   // error[E0384]: cannot assign twice to
}                  // immutable variable `answer`
//   |
// 2 |     let answer = 40;
//   |         ------ first assignment to `answer`
// 3 |     answer += 2;
//   |     ^^^^^^^^^^ cannot assign twice to immutable variable
//   |
// help: consider making this binding mutable: `mut answer`</code></pre></div>

<h4 id="ch1-3-fix">Taking the suggestion</h4>
<p>Notice what the compiler asked for: not a change of value, but a change of <em>intent</em>. <code>mut</code> says the binding is meant to change. That is the pattern of every Rust fix — the compiler is usually right about the mechanics, and the suggestion is a good first move. When the fix is structural rather than cosmetic, the diagnostic will say so and point you at the documentation for the rule.</p>
<div class="codeWrap"><pre><code>fn main() {
    let mut answer = 40;   // the compiler's own suggestion
    answer += 2;
    println!("{answer}");  // 42
}</code></pre></div>

<h3 id="ch1-4" data-toc>1.4 Where Rust fits, and where it does not</h3>
<p class="topic-desc">Rust shines where a wrong pointer, a data race or an unsafe buffer is expensive: network services, embedded and real-time code, CLI tools, parsers and anything that must run for years. It is a poor fit where iteration speed and your own thinking time dominate — that is the territory of dynamic languages, and choosing the right tool is part of the job.</p>

<h4 id="ch1-4-fits">The territory: services, CLIs, embedded, parsers</h4>
<p>A web service holding connection state and parsing untrusted input is classic Rust ground: every potential buffer overflow and race is a compile error, and the release binary is small and starts fast. The same loop that a dynamic language runs through an interpreter runs as native arithmetic here — but only if you actually build with <code>--release</code>, because the debug binary is unoptimised by design.</p>
<div class="codeWrap"><pre><code>fn main() {
    // The same loop a dynamic language runs in its interpreter
    // runs as native arithmetic here. Compile with --release or
    // the timings mean nothing.
    let total: u64 = (0..10_000_000).map(|n| n * n).sum();
    println!("{total}");
}</code></pre></div>

<h4 id="ch1-4-not">Where Rust is the wrong tool</h4>
<p>Rapid-prototyping glue code, one-off scripts, data exploration — anywhere the bottleneck is your own thinking rather than the machine — is dynamic-language territory. Rust makes you decide ownership early, and paying that tax on a program that will be rewritten tomorrow is wasted effort. The signal to watch is allocation patterns: a loop churning out formatted strings is fine in a script and the wrong shape for a hot path in Rust, where the fix is restructuring, not more memory.</p>
<div class="codeWrap"><pre><code>fn main() {
    let mut events: Vec&lt;String&gt; = Vec::new();
    for i in 0..1000 {
        events.push(format!("event-{i}"));   // one allocation each
    }                                        // fine at 1,000, not 10M
    println!("{} events", events.len());
}</code></pre></div>

<h4 id="ch1-4-deploy">The deployment story: one static binary</h4>
<p>Rust's other unfair advantage is the artifact. Because rustc is the entire compiler, cross-compiling needs no toolchain packages — just a target added via rustup — and the musl target produces a statically linked binary with no glibc version dependency. That one file runs on any Linux distribution and inside the smallest scratch container, which makes packaging and container images dramatically simpler than for a language with a shared runtime.</p>
<div class="codeWrap"><pre><code>$ rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl

$ cargo build --release --target x86_64-unknown-linux-musl
$ file target/x86_64-unknown-linux-musl/release/billing
# ELF 64-bit LSB pie executable, x86-64, statically linked

# no dynamic linker, no shared libraries to install: copy the file
# onto any Linux host (or into a scratch container) and run it.</code></pre></div>

<div class="tip">Run <code>cargo doc --open</code> on a project you did not write. The documentation is built from the source comments, and browsing it is the fastest way to learn how a crate actually wants to be used.</div>
<div class="warn">Never ship the debug build. It has no optimisation, keeps overflow checks — good for finding bugs, wrong for serving traffic — and its timings are meaningless. <code>cargo build --release</code> is the artifact.</div></section>
