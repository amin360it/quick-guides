The classic three-tier design

The core, distribution and access split separates high-speed transport from policy and user attachment. Core switches carry the aggregated traffic between distribution nodes, distribution applies routing and policy such as access lists, and access switches connect end devices. It remains the mental model most enterprise networks are measured against, even when it is scaled down to a collapsed-core two-tier design or translated into spine-leaf fabrics.

        Core (fast, redundant backbone)
        /            |            \
   Distribution  Distribution  Distribution
      |              |              |
  Access         Access         Access
   |  |            |  |           |  |
 end hosts     end hosts      end hosts

Rules: access connects devices, distribution applies policy,
core moves packets as fast as possible. Keep policy out of the core.

The three-tier hierarchy: access connects devices, distribution applies policy, and the core transports packets. Keep policy out of the core so it stays fast.

1 · Network Design Fundamentals

1.1 What a network design must achieve1.2 Topologies1.3 Hierarchy, modularity and summarisation

This chapter frames the constraints every sound design must balance: availability, scalability, performance, security, manageability and cost. It defines what each means in practice, such as uptime percentages, throughput budgets and recovery time objectives, and shows how they trade off against one another. Requirements gathering, traffic analysis and clear documentation turn these constraints into the measurable targets that drive every later decision.

1.1 What a network design must achieve

Design work should start from explicit, agreed goals rather than vendor defaults or habit. Each goal maps to a measurable requirement, such as availability expressed as a percentage of uptime, performance as latency and throughput, and security as permitted zones and identity rules. Every topology and technology choice should be traceable to one of these goals, so the design can be defended in review and rechecked as traffic grows.

GoalDesign implication
AvailabilityRedundant links/devices, no single points of failure
ScalabilityHierarchy, summarisation, spare capacity
PerformanceLow latency, adequate bandwidth, QoS for real-time
SecuritySegmentation, least privilege, inspection points
ManageabilityConsistent addressing, naming, monitoring, automation
CostRight-sized links and hardware

1.2 Topologies

The physical or logical shape of a network determines its cost, resilience, latency and ease of growth. Common shapes include bus, ring, star, full and partial mesh, hierarchical and leaf-spine layouts, with hub-and-spoke giving cheap centralised control and mesh giving redundant paths at higher cost. Choose the topology that matches the traffic pattern you actually have, using measured bandwidth and failure requirements rather than preferring a shape automatically.

TopologyCharacteristicUse
Star / hub-and-spokeCentral deviceSmall sites, WAN spokes
Mesh (full/partial)Every node to manyWAN core, data centre
Tree / hierarchicalLayeredEnterprise campus
Spine-leafFlat, predictableModern data centres
RingSurvives single link breakMetro, legacy

1.3 Hierarchy, modularity and summarisation

Layering a network into hierarchies of tiers, modules and functional blocks keeps it understandable as it grows. Modular design isolates failure domains so one outage cannot cascade past its boundary, and route summarisation at each tier shrinks routing tables and dampens link flaps. Implementation uses distribution and core tiers per location, collapsed cores for small sites, and prefix aggregation with summarised routes toward the core.

  • Build in modules (per building/floor/rack) that can be replicated.
  • Assign addresses so each module can be summarised into one route.
  • Apply policy at distribution; keep the core simple and fast.

2 · The Network Model

2.1 OSI and TCP/IP in practice2.2 Encapsulation2.3 TCP vs UDP

OSI and TCP/IP give a shared language for describing every hop a packet takes, from the physical signal to the application payload. OSI defines seven layers while the practical TCP/IP model collapses them into a four-layer stack of link, internet, transport and application. Understanding which layer a device or protocol operates at makes troubleshooting systematic, because you can isolate symptoms, test layer by layer and interpret protocol behaviour correctly.

2.1 OSI and TCP/IP in practice

Real networks are mapped onto the seven OSI layers through TCP/IP’s simpler model of link, internet, transport and application. Ethernet and Wi-Fi occupy layers 1 and 2, IP sits at layer 3, TCP and UDP at layer 4, and DNS, HTTP and TLS at layer 7. Knowing which layer a device or protocol lives at tells you what it can inspect and control, for example switching at layer 2 versus routing at layer 3.

7 ApplicationApplicationHTTP, DNS, SMTPNames/URLs
6 PresentationTLS, encoding—
5 SessionSessions, RPC—
4 TransportTransportTCP, UDP, QUICPorts
3 NetworkInternetIP, ICMP, routingIP addresses
2 Data linkLinkEthernet, 802.11, ARPMAC addresses
1 PhysicalCables, fibre, radio—

2.2 Encapsulation

Encapsulation wraps each protocol data unit with the header of the layer below as data travels down the stack, so TCP or UDP data becomes an IP packet and then an Ethernet frame. Receivers strip the headers in reverse order, called de-encapsulation, until the original payload is handed to the application. Tracing this wrapping with packet captures is the core of packet-level diagnosis, because it reveals MTU issues, VLAN tags and tunnel headers.

Data
  + TCP header  = Segment
  + IP header   = Packet
  + Eth header  = Frame
  + preamble    = Bits on the wire

Each layer adds its header; each layer on the receiver removes it.

Each protocol layer adds its own header, and the receiver strips them in reverse order. This wrapping is encapsulation.

2.3 TCP vs UDP

TCP provides reliable, ordered, connection-oriented delivery with acknowledgements, retransmission, windowing and flow control, while UDP is a lightweight best-effort transport with only ports and a checksum. TCP suits web, file transfer and mail where loss matters most, so applications such as HTTP, SMTP and SSH use it. UDP suits real-time and query workloads such as DNS, VoIP and video, where latency matters more than an occasional lost packet.

TCPUDP
ConnectionHandshake, statefulConnectionless
ReliabilityRetransmits, orderingBest effort
SpeedSlower start (congestion control)Low overhead
UseWeb, DB, file transferDNS, voice/video, games
# Watch a TCP handshake
tcpdump -n 'tcp port 443 and tcp[tcpflags] & tcp-syn != 0'  # capture SYNs on https
# SYN -> SYN,ACK -> ACK   (connection established)

Captures the SYN packets of a TCP handshake on port 443 so you can watch a connection open in real time.

3 · IP Addressing & Subnetting

3.1 IPv4 and CIDR3.2 Subnetting example + output3.3 VLSM and address planning3.4 IPv6 essentials

Subnetting is the arithmetic behind every scalable address plan, letting one prefix be divided into smaller networks with their own host ranges. Engineers allocate blocks using CIDR and VLSM, compute usable hosts as two to the power of the host bits minus two, and document subnets so DHCP scopes and routes stay aligned. A solid, documented scheme now saves painful renumbering later, so plan the whole hierarchy before configuring anything.

3.1 IPv4 and CIDR

CIDR notation packs a network and its subnet mask into one slash form such as 192.168.10.0/24, where the prefix length states how many leading bits are the network part. It is the quick math of address planning, so memorising powers of two and common prefixes such as /24, /30 and /31 is worth the effort. Engineers use it to describe routes, calculate address budgets and design summarised blocks for the routing protocol.

Address  192.168.10.0/24
         |-- network --|host|
Subnet mask 255.255.255.0
Hosts: 2^(32-24) - 2 = 254 usable (network + broadcast reserved)

CIDR cheat sheet
/24 = 256 addresses   /25 = 128   /26 = 64   /27 = 32
/28 = 16             /29 = 8     /30 = 4 (2 usable, point-to-point)

CIDR shorthand: the slash tells you how many addresses the network holds. Remember the friendly sizes from /24 down to /30.

3.2 Subnetting example + output

A worked subnetting example shows how a real block such as 192.168.10.0/24 divides into smaller subnets, listing the network address, broadcast address and usable host range for each piece. You can recreate the calculation with a tool such as ipcalc, whose command-line output prints the network, broadcast, mask and host list for each subnet. Checking your own plans this way exposes overlaps and wasted space before they reach production configuration.

Split 10.0.0.0/24 into four subnets:
  10.0.0.0/26    10.0.0.64/26    10.0.0.128/26    10.0.0.192/26

# Verify with classic tools
$ ipcalc 10.0.0.0/26  # print usable range and broadcast
Network:   10.0.0.0/26
HostMin:   10.0.0.1
HostMax:   10.0.0.62
Broadcast: 10.0.0.63
Hosts/Net: 62

Splits a /24 into four /26 subnets, then uses ipcalc to print the exact usable range. A handy sanity check before assigning addresses.

3.3 VLSM and address planning

Variable Length Subnet Masks give each segment exactly the addresses it needs by allowing different prefix lengths on different subnets inside one block. A /24 can therefore be split into a mix of /26, /27 and /30 segments, so a point-to-point link wastes none of the space. Practise by ordering subnets from largest to smallest before assigning them, then document the plan so future engineers can extend it without renumbering.

3.4 IPv6 essentials

IPv6 removes the need for NAT and makes address space effectively infinite, giving every device globally routable addresses. The essentials are prefix notation such as a /64 per subnet, hexadecimal addresses compressed in the canonical RFC 5952 form, and neighbour discovery replacing ARP. Engineers plan one /64 per LAN segment, use DHCPv6 or SLAAC for configuration, and keep track of the shorter practical prefixes for point-to-point links.

2001:db8:acad:1::/64
 |global routing prefix|subnet|
Addresses are 128-bit; a /64 has 2^64 host addresses.
No NAT required; use unique-local (fc00::/7) internally.
Shorten by removing leading zeros and one run of zeros (::) per address.

IPv6 addresses are 128-bit with a fixed subnet structure, so NAT is unnecessary. Compression removes leading zeros and one run of zeros.

Bad addressing plans are expensive to fix. Design a scheme that maps to sites/buildings/floors/VLANs from day one, and reserve blocks for growth.

4 · Routing

4.1 Static routing4.2 Dynamic routing protocols4.3 OSPF in practice4.4 BGP and route policy

Routing decides how packets travel beyond a single link, using forwarding tables to pick the next hop toward each destination. Static routes suit simple, fixed cases such as default routes and stub networks, while dynamic protocols such as OSPF and BGP share reachability so the network reconverges when links change. Choose the approach by scale: start with static entries for a handful of routes and move to a protocol as the topology grows and gains redundancy.

4.1 Static routing

Static routes are manually configured next-hop or exit-interface entries, simple, predictable and cheap, but they do not adapt when a link changes. Use them for defaults, stubs and small fixed networks where the topology rarely changes, and always include a default route where one is needed. When the network grows or gains redundant paths, switch to a dynamic protocol, because static routes cannot heal themselves.

# Simple, predictable, no overhead — but manual
ip route 10.20.0.0 255.255.0.0 10.0.0.2                    ! next hop on the LAN
# Default route: send everything unknown to the edge
ip route 0.0.0.0 0.0.0.0 203.0.113.1                       ! everything else to the ISP

Two static routes: one to a specific destination network, and a default route sending everything else to the ISP router.

4.2 Dynamic routing protocols

Dynamic protocols exchange reachability information so routers build forwarding tables automatically and reconverge when links or routes change. Link-state protocols such as OSPF and IS-IS fit enterprise interiors, distance-vector protocols such as RIP suit small networks, and path-vector BGP connects autonomous systems. Pick the protocol by scale and design, using interior protocols within the organisation and BGP for Internet and multi-cloud policy.

ProtocolTypeScaleMetric
RIPDistance vectorSmallHops
OSPFLink stateEnterpriseCost (bandwidth)
EIGRPHybrid (Cisco)EnterpriseComposite
IS-ISLink stateCarrier/DCCost
BGPPath vectorInternet/DCPath attributes

4.3 OSPF in practice

OSPF is the workhorse enterprise interior protocol, flooding link-state advertisements across an area so every router builds the same shortest-path view of the network. Design areas to limit flooding, make area 0 the backbone, and summarise at area boundaries to shrink tables. Verify neighbours with commands such as show ip ospf neighbor rather than assuming adjacency is up, then check reachability with show ip route ospf.

router ospf 1
 network 10.0.0.0 0.0.255.255 area 0    ! core area
 network 10.20.0.0 0.0.255.255 area 1   ! branch area
! Areas limit flooding; ABRs summarise between areas.

# Verify
show ip ospf neighbor
show ip route ospf

Neighbor ID     Pri State      Dead Time  Address
10.0.0.2          1 FULL/DR    00:00:36   10.0.0.2

Activates OSPF on two networks and verifies the neighbour reaches FULL. A FULL/DR neighbour means the adjacency is healthy.

4.4 BGP and route policy

BGP carries routes between autonomous systems and applies policy rather than simple shortest-path math, using attributes such as local preference, AS path and communities. Engineers filter with prefix lists, route maps and community-based policies, and advertise only what they intend to accept. Filtering incoming and outgoing prefixes plus RPKI validation keep those routes safe from hijacks and from overloading neighbours.

  • EGP that exchanges routes between autonomous systems.
  • Choose paths by policy (local pref, AS-path, MED), not just speed.
  • Use prefix filters and RPKI to prevent route leaks/hijacks.
  • In the data centre, BGP is often used at the leaf/spine layer too.

5 · Switching & VLANs

5.1 Ethernet switching and MAC tables5.2 VLANs and trunking5.3 STP, link aggregation and stacking

Switches learn from source MAC addresses and forward by destination MAC, shaping everything inside your LAN, while VLANs split one physical network into many logical broadcast domains. Trunk links carry tagged frames, so one cable serves many VLANs between switches. Together they segment traffic, contain broadcast storms and give each department or security zone a clean boundary.

5.1 Ethernet switching and MAC tables

An Ethernet switch learns the source MAC address and port of every incoming frame and forwards subsequent frames to the correct port by looking up the destination MAC in its MAC address table. Unknown destinations are flooded out, and ageing timers remove stale entries automatically. When frames go astray, inspect the address table first, using show mac address-table to verify where each address is learned.

The switch learns source MACs and forwards by destination MAC.
Unknown unicast -> flood; broadcast -> flood within the VLAN.
Loop prevention: Spanning Tree Protocol (STP).

# Show what the switch has learned: MAC, VLAN and port
show mac address-table
Vlan  Mac Address         Type      Ports
10    aabb.cc00.0100      DYNAMIC   Gi0/1

The one command that reveals what a switch has learned. A dynamic MAC entry maps a VLAN, address and port.

5.2 VLANs and trunking

VLANs isolate traffic logically, so devices in different VLANs cannot communicate without a routed hop, and VLAN trunk links carry many VLANs between switches using 802.1Q tags. Each frame on a trunk carries a VLAN identifier so switches keep traffic on the right segment. In practice configure access ports for end devices, tag trunks between switches, and provide an inter-VLAN router or Layer 3 switch to cross boundaries.

vlan 10                      ! user segment
 name USERS
vlan 20                      ! voice segment
 name VOICE

interface Gi0/1
 switchport mode access
 switchport access vlan 10   ! puts this port on the user VLAN

interface Gi0/24            ! uplink to switch/AP
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30   ! which VLANs ride the trunk

Defines two VLANs, assigns an access port to VLAN 10, and makes an uplink a trunk carrying the VLANs to the next switch.

5.3 STP, link aggregation and stacking

Redundancy needs loop prevention, and spanning tree protocol blocks redundant paths until a link fails and then reconverges to keep the LAN loop-free. Link aggregation groups parallel links into one logical bundle using LACP, and stacking makes several switches behave as a single device. Use RSTP or MSTP, enable portfast on access ports, and bundle uplinks to raise both bandwidth and resilience in the access layer.

FeaturePurpose
STP / RSTP / MSTPPrevent loops; fast reconvergence
PortFast / BPDU guardProtect edge ports
LACP / EtherChannelAggregate links for bandwidth + redundancy
Stacking / MLAGTwo switches appear as one

Never create a physical loop without STP (or a routed design). A broadcast storm can saturate a network in seconds.

6 · Core Network Services

6.1 DNS6.2 DHCP6.3 NAT and PAT

DNS, DHCP and NAT are the plumbing every user and device touches. DNS resolves names to addresses, DHCP configures addresses and options automatically, and NAT translates between private and public address space. Get them right and the network feels like magic; get them wrong and nothing works, so run them with redundancy and watch scope pools and translation tables for exhaustion.

6.1 DNS

DNS turns names into addresses and is often the first suspect in outages, so engineers must know the record types and how to query them. A records map names to IPv4, AAAA to IPv6, MX to mail, CNAME to aliases, and SRV for services, with tools such as nslookup and dig for testing. Check TTLs, forwarding and caching behaviour, and confirm that both forward and reverse zones resolve before blaming the network.

Records: A (IPv4)  AAAA (IPv6)  CNAME (alias)  MX (mail)
         TXT (verification/SPF)  SRV (service)  PTR (reverse)

# Query + output
$ dig example.com A +short  # show only the IPv4 address
93.184.216.34

$ nslookup -type=MX example.com  # query the mail servers
example.com  MX preference = 10, mail exchanger = mail.example.com

Lists the DNS record types, then shows dig resolving an A record and nslookup pulling the MX record. Both are standard ways to test resolution.

6.2 DHCP

DHCP hands out addresses and configuration options automatically, saving thousands of manual configurations and avoiding conflicts. A server manages a scope per subnet, offering IP address, mask, gateway, DNS and lease time, while DHCP relay agents forward client requests from other subnets so one server serves many. Plan pools from the addressing scheme, reserve addresses for servers and printers, and monitor lease utilisation before it exhausts.

DORA: Discover -> Offer -> Request -> Acknowledge
Lease with scope, options (gateway, DNS, NTP) and reservations.
Use DHCP relay where the server is on another subnet.

# Linux client
$ sudo dhclient -v eth0  # verbose lease request on eth0
DHCPDISCOVER ... DHCPOFFER ... DHCPREQUEST ... DHCPACK

The DORA exchange, then a Linux client that requests a lease and prints each phase. The four messages map exactly to the states in the diagram.

6.3 NAT and PAT

NAT lets private addresses reach the internet by translating between inside and outside addresses, while PAT maps many clients to one public address using different source ports. In practice configure inside and outside interfaces, add static entries for inbound services and pools for outbound traffic, then inspect translations when flows fail. Watch the translation table and pool sizes, because both can quietly exhaust under heavy load.

TypeMapping
Static NATOne private ⇄ one public
Dynamic NATPrivate pool ⇄ public pool
PAT / NAT overloadMany private → one public (by port)
# Cisco PAT to the internet
ip nat inside source list 1 interface Gi0/0 overload
access-list 1 permit 10.0.0.0 0.0.255.255   ! which source range to translate
# If the NAT table fills, new connections fail — monitor it.

PAT overloads one public interface for many private clients. The access-list defines which source addresses get translated, so monitor table usage.

7 · Wireless Design

7.1 Wi-Fi generations7.2 Coverage and capacity design7.3 Wireless security

Wireless is the access layer users actually feel, and coverage, capacity and security decide whether Wi-Fi feels great or terrible. Engineers plan by surveying the site, choosing access point placement based on the 802.11 standard and channel reuse, and sizing for client density rather than range alone. A controller or cloud management platform then handles radios, roaming and policies across the whole fleet.

7.1 Wi-Fi generations

Each IEEE 802.11 generation adds speed and manages denser client environments better, from 802.11n and 802.11ac on 5 GHz through 802.11ax Wi-Fi 6 and 6E to 802.11be Wi-Fi 7. The 5 and 6 GHz bands do the heavy lifting, with 6E bringing wider channels and less interference to the spectrum. Match the standard to your device mix and available spectrum, because legacy clients cap the negotiated shared rate.

StandardBandTypical speed
802.11n (Wi-Fi 4)2.4/5 GHzUp to 600 Mbps
802.11ac (Wi-Fi 5)5 GHzUp to ~1.3 Gbps
802.11ax (Wi-Fi 6/6E)2.4/5/6 GHzMulti-Gbps, high density
802.11be (Wi-Fi 7)2.4/5/6 GHzVery high throughput, low latency

7.2 Coverage and capacity design

Coverage and capacity design sizes the wireless network for the number of clients that will connect, not just how far the signal reaches. A predictive or active site survey maps signal strength, roaming behaviour and channel use, and access point density is chosen for real throughput per user. A controller manages channel and transmit power settings centrally, with fast roaming mechanisms such as 802.11r and 802.11k enabled for mobile devices.

  • Site survey (or predictive modelling) before mounting APs.
  • Plan for capacity (clients/second), not just coverage.
  • Keep 2.4 GHz for range, 5/6 GHz for throughput; avoid co-channel overlap.
  • Use a wireless controller for central management and roaming.

7.3 Wireless security

Enterprise Wi-Fi should use WPA3 with many deployments, or WPA2 with 802.1X and a RADIUS server to verify user identity per session. Guests get an isolated SSID on a separate VLAN with its own internet-only policy and rate limits. Configure pre-shared keys only for small personal networks, disable WEP and WPA1 entirely, and rotate credentials regularly.

WPA3-Enterprise  - strongest, 802.1X + RADIUS, per-user credentials
WPA2-Enterprise  - common fallback
WPA2/WPA3-Personal - pre-shared key, for guest/home
Guest network    - isolated VLAN, captive portal, rate limits

Never use WEP or open networks for anything sensitive.

A quick ranking of wireless security modes, from WPA3-Enterprise down. Guests get isolated networks; WEP and open networks are never for sensitive traffic.

8 · Load Balancing, Proxies & CDN

8.1 Load balancing8.2 Forward and reverse proxies8.3 CDN and edge

Load balancers, proxies and CDNs sit between users and servers to add scale, control and speed. A load balancer distributes client requests across a server pool, a proxy adds caching, filtering and TLS termination, and a CDN caches content at edge locations close to users. Together they are how web services survive traffic spikes with predictable latency and availability.

8.1 Load balancing

A load balancer spreads requests across a group of servers and automatically removes failed or unhealthy ones, using a virtual IP and health checks to keep the pool consistent. Choose the algorithm to match the application: round-robin for stateless workloads, least connections for uneven request sizes, and persistent source affinity for stateful sessions. Implement TLS termination and key decisions about layer 4 versus layer 7 operation when you deploy it.

AlgorithmBehaviour
Round robinIn turn
Least connectionsTo the least busy
WeightedBy capacity
IP hashSticky by client
L4 (TCP)   - fast, no content awareness
L7 (HTTP)  - routes by path/host/header, TLS termination, WAF

Health checks remove failed nodes automatically.
Session state must be shared (Redis) or sticky to survive failover.

Load balancing works at Layer 4 for speed or Layer 7 for smart routing. Health checks and shared session state keep failover clean.

8.2 Forward and reverse proxies

Forward proxies send client traffic outbound, while reverse proxies accept traffic on behalf of back-end servers, and both add caching, filtering and TLS control. A forward proxy on the LAN edge enforces URL policy, identity and egress filtering, whereas a reverse proxy fronts web applications for certificate termination and load sharing. Deploy them in front of application tiers and tune caching rules and health checks as part of the rollout.

  • Forward proxy — clients' proxy to the internet (filtering, caching).
  • Reverse proxy — sits in front of servers (TLS, routing, caching, WAF).

8.3 CDN and edge

A CDN caches content at edge points of presence close to users, cutting latency and shifting load off the origin servers. Versioned URLs are the key to safe cache invalidation, because immutable content can be cached aggressively and updated simply by changing the URL. Plan cache rules that keep dynamic traffic fresh, purge on demand and monitor the hit ratio to confirm the CDN is actually working.

Client -> nearest edge POP -> origin (on cache miss)
Cache static assets and, increasingly, dynamic/API responses.
Invalidate carefully; version asset URLs to avoid stale content.

Traffic flows client to edge node first and only hits the origin on a cache miss. Versioned URLs make invalidation safe and predictable.

9 · WAN & Connectivity

9.1 WAN options9.2 SD-WAN9.3 VPN types

The WAN is how sites and clouds talk over long distances, with options ranging from MPLS to internet VPN, SD-WAN and dedicated cloud links. Each choice trades cost, quality, capacity and control differently, and the terms below explain what they are for. Engineers typically combine a primary transport with a backup, or a circuit mix that SD-WAN manages by policy.

9.1 WAN options

MPLS, internet VPN, SD-WAN and 5G each trade cost, quality and control differently. MPLS offers quality of service and SLA-backed performance, IPsec VPN over the internet is cheap and flexible, SD-WAN steers traffic across multiple circuits per application, and 5G provides quick wireless access for new sites. Pick what your applications actually need in latency, jitter and availability, and layer redundancy on top rather than betting on one transport.

OptionCharacteristic
MPLSPrivate, deterministic, costly
Internet + VPNCheap, variable quality
SD-WANPolicy-driven over any links, app-aware
Dedicated cloud linkPredictable to a cloud provider
5G / LTEFast to deploy, good for backup

9.2 SD-WAN

SD-WAN steers traffic per application across the links you have, turning cheaper internet circuits into a resilient, policy-driven WAN. It builds an overlay with IPsec tunnels under centralised control, measures each path continuously and chooses the best one for voice or business-critical traffic, failing over automatically. Implement it as a hub-and-spoke or full-mesh overlay under central orchestration, with application-aware routing and underlay independence.

Central policy -> steer traffic by application:
  - voice/video over the low-latency link
  - bulk backup over the cheap link
  - automatic failover between links
Encryption (IPsec) over every transport; zero-touch provisioning.

SD-WAN steers each application onto the link that suits it and encrypts every transport. Policy lives centrally while branches provision themselves.

9.3 VPN types

VPNs create private paths over shared networks, and the right type depends on the scenario. Site-to-site IPsec tunnels connect whole offices into one private network, remote access VPNs such as IPsec or WireGuard admit individual users, and TLS-based browser VPNs work from anywhere. Match the encryption and authentication to the risk of the traffic, and route split tunnelling deliberately rather than by default.

  • Site-to-site IPsec — connect branch offices.
  • Remote-access VPN / ZTNA — individual users, now often identity-aware.
  • SSL/TLS VPN — browser-based access.

10 · Network Security

10.1 Segmentation and zones10.2 Firewalls and inspection10.3 Zero trust networking

Design security in from the start rather than bolting it on afterwards, using segmentation, firewalls and zero trust to shrink the blast radius of any compromise. Engineers divide the network into zones with least-privilege boundaries, enforce explicit allow policies at chokepoints, and verify identity continuously rather than trusting the inside. This layered approach limits how far an attacker can move and makes incidents much more containable.

10.1 Segmentation and zones

Dividing the network into zones such as trusted internal, demilitarised zone, guests and management gives each workload a least-privilege boundary. Firewalls, access lists and VLAN-based separation enforce what is allowed to cross between zones, with routing restricted to explicit allow statements. This is the highest-value control in most networks, because a compromise in one zone cannot walk freely into the rest.

ZoneContentsAccess
InternetUntrustedDeny inbound by default
DMZPublic servicesLimited to specific ports
InternalUsers, appsEast-west controlled
ManagementDevicesOnly from admin network
Critical/dataDatabasesLeast privilege, monitored

10.2 Firewalls and inspection

Firewalls enforce what is explicitly allowed and inspect the traffic that crosses them, from stateful filtering at layer 4 to next-generation inspection at the application layer. Modern ones add intrusion prevention, application awareness and web-application protection, often with TLS inspection so threats cannot hide in encrypted traffic. Deploy them at internet edges and zone boundaries, keep rule sets to least privilege and test every change before it goes live.

Default deny; allow only what is documented.
Stateful firewall tracks connections.
NGFW adds app awareness + IPS; WAF protects web apps.

# Example rule intent
permit tcp 10.20.0.0/24 -> 10.30.0.0/24 port 5432   (app -> db)
deny   ip  any -> any   log

Default-deny plus explicit permits, with a logged catch-all trailing rule. The example allows only app-to-database traffic on the DB port.

10.3 Zero trust networking

Zero trust stops assuming the inside is safe and verifies identity on every request, no matter where it comes from. It uses continuous authentication, device posture checks and per-application access controls instead of implicit network trust, often through identity-aware proxies and micro-segmentation of workloads. Implement it gradually, starting with the most sensitive applications and adding identity verification and segmentation in phases.

  • Identity-aware access proxies instead of a flat trusted LAN.
  • Micro-segmentation between workloads; mTLS for service-to-service.
  • Continuous verification, least privilege, assume breach.
  • Monitor east-west traffic, not just the perimeter.

A flat internal network means one compromised laptop can reach every server. Segmentation is the single highest-value network security control.

11 · QoS & Traffic Engineering

11.1 Why QoS11.2 Classification and marking11.3 Queuing and shaping

When links congest, QoS decides who suffers, so classified traffic is shaped and queued to protect the real-time classes users notice most. Engineers mark packets with DSCP, map the markings to queues on each interface and police or shape the rest. Apply the policy consistently along the entire path, because a single unmarked hop can undo the whole end-to-end treatment.

11.1 Why QoS

Congestion without QoS is unfair by default, because scheduling is first-in first-out and all traffic is treated alike. Voice and video need low jitter, bounded delay and adequate bandwidth, which only queuing and priority treatment can guarantee. QoS is justified whenever real-time traffic shares links with bulk transfers, such as VoIP or video running over WAN circuits.

When a link is congested, everything suffers. QoS classifies traffic and guarantees service for what matters — usually voice and video, which need low jitter and latency.

11.2 Classification and marking

Mark packets at the edge with DSCP so every hop downstream knows their priority without re-classifying them. Classify on source, destination, port or application, set the differential services code point such as EF for voice and AF for video, and trust markings only from known boundary devices. Consistent markings are what make end-to-end QoS possible across the whole network.

Trust DSCP markings at the edge; classify by app/ACL.
EF (46)   - voice        (highest, low latency)
AF41 (34) - video
AF21 (18) - transactional
CS1 (8)   - scavenger / bulk (lowest)

DSCP values encode service priority, from EF for voice down to CS1 for bulk. Mark at the edge; every hop trusts and acts on the value.

11.3 Queuing and shaping

Queues give priority classes guaranteed treatment so voice and video move while bulk traffic waits, and shaping smooths bursts down to a configurable rate. Implement class-based weighted fair queueing or strict priority queues matched to DSCP, and add policing with parameters such as committed information rate and burst size. Together these turn markings into enforced behaviour on every interface they cross.

ToolPurpose
Priority queue / LLQVoice gets strict priority
CBWFQGuaranteed bandwidth per class
Shaping / policingSmooth or cap traffic
WREDDrop early to avoid tail-drop sync

12 · Redundancy & High Availability

12.1 Layer 2/3 redundancy12.2 Designing for no SPOFs12.3 Testing failover

High availability comes from removing single points of failure and then proving the design recovers. Engineers duplicate power, links, gateways and devices in separate failure domains, and use protocols such as STP, LACP and VRRP so failover is automatic. None of it counts until reconvergence has been tested against the service level agreement.

12.1 Layer 2/3 redundancy

Redundant gateways and links need protocols to keep them loop-free and to fail over automatically. At layer 2, spanning tree prevents loops and link aggregation bundles redundant paths, while at layer 3, first-hop redundancy protocols such as VRRP or HSRP share a virtual gateway IP between routers. Configure pre-emption and link monitoring so the backup takes over only when the primary really fails.

TechniqueProvides
STP/RSTPLoop-free redundant L2 paths
LACP bundlesLink redundancy + bandwidth
VRRP / HSRP / GLBPRedundant default gateways
Routing convergenceAutomatic path failover (OSPF/BGP)

12.2 Designing for no SPOFs

A single point of failure is anything whose loss ends a service, so engineers dual everything and keep failure domains clean. Redundant uplinks, dual power feeds, N plus one devices and independent paths between tiers are standard practice. Apply this within budget, because duplicating everything is rarely realistic, and document whatever remains intentionally shared so it is a known, accepted risk.

Dual core switches, dual uplinks, dual power, dual ISPs.
Failure domains: don't let one failure take out both paths.
Sub-second failover via routing protocols + tuned timers/BFD.

High availability is redundancy of every critical component plus clean failure domains. Routing protocols and BFD make failover sub-second.

12.3 Testing failover

Failover that is never tested is only hope, so engineers deliberately pull links and power to verify reconvergence. Each test should measure how long the service is interrupted, compare it to the recovery time objective and check that routes, address tables and sessions rebuild cleanly. Script the tests, run them at a safe time and re-run them after every topology change.

# Common checks
show standby brief          # HSRP/VRRP state
show ip ospf neighbor       # reconvergence
traceroute 8.8.8.8          # path after a link down
# Schedule link-pull tests; validate reconvergence time against SLA.

A failover checkpost: gateway state, routing adjacency and the actual path. Deliberate link-pull tests prove reconvergence meets the SLA.

13 · Network Automation & Monitoring

13.1 Automation13.2 Monitoring protocols13.3 What to watch

Config as code and consistent monitoring turn networks into manageable systems. Automation relies on templates, a source of truth and validation in the CI pipeline, while monitoring combines SNMP, syslog, flow records and telemetry for a complete picture. If something is not automated and monitored, it is not really managed.

13.1 Automation

Automation replaces hand-typed configuration with templates and a declared source of truth, so the same base configuration is generated consistently across every device. Engineers store configs in version control, render them through templating such as Jinja2 and deliver them to devices over the network, validating in the CI pipeline before any change reaches a switch or router. This catches mistakes early and makes rollback trivial.

Templates + variables (Jinja2) -> consistent config
Ansible / Nornir / Terraform for network devices
Source of truth (NetBox) drives addressing and documentation
CI pipeline validates config before pushing to devices

Config as code: templates and a source of truth produce consistent configs, and CI validates before devices ever see them.

13.2 Monitoring protocols

SNMP, syslog, flow records and telemetry each answer a different question about the network. SNMP polls counters and sends traps for device health, syslog collects device and application events, NetFlow or sFlow give per-flow traffic insight, and streaming telemetry pushes continuous data over gRPC. Use them all together for a complete picture instead of relying on any single one.

ProtocolUse
SNMPDevice metrics, traps
SyslogEvent logging to a central collector
NetFlow / IPFIX / sFlowTraffic flow analysis
Streaming telemetryHigh-frequency push metrics
Synthetic probesEnd-to-end availability

13.3 What to watch

Watch utilisation, errors, device health and routing stability, because these reveal failures before users notice them. Track CPU and memory, link utilisation and error counters, temperature, and protocol adjacency changes, with alerts that point to a cause rather than just a symptom. Baselines and trends let you spot slow degradation early and link a change to its effect.

  • Link utilisation, errors/discards, and latency per path.
  • Device CPU/memory, temperature, power, fans.
  • Routing adjacency changes and flapping.
  • Config change audit and drift.

14 · Data Centre Network Design

14.1 Spine-leaf14.2 Overlays: VXLAN and EVPN14.3 Storage and convergence

Data centres need flat, predictable fabrics that scale with east-west traffic, not the tree shapes of a campus LAN. Spine-leaf topologies with equal-cost paths and overlay technologies provide this, keeping latency predictable as the fabric grows. Design for low oversubscription, consistent one or two hop latency and the ability to expand by adding spine and leaf switches.

14.1 Spine-leaf

In a spine-leaf fabric every leaf switch connects to every spine switch, giving equal-cost paths and predictable latency between any pair of server ports. The fabric scales simply by adding spines for capacity and leaves for ports, and equal-cost multipathing spreads traffic across all of them. It suits the east-west traffic of modern data centres far better than a legacy three-tier design.

        Spine1      Spine2
        /  \        /  \
   Leaf1   Leaf2  Leaf3  Leaf4
    |         |      |      |
  servers  servers servers servers

Every leaf connects to every spine (equal-cost paths).
East-west traffic is the norm; predictable, low latency, easy to scale.

Every leaf stretches to every spine, giving equal-cost paths and flat predictable latency. Scale by adding more spines or leaves.

14.2 Overlays: VXLAN and EVPN

VXLAN encapsulates Layer 2 frames in UDP over an IP fabric, letting virtual segments span any topology, and EVPN gives them a control plane. EVPN distributes MAC and IP reachability through BGP so the data plane stays simple while operators get the full view. Together they enable workload mobility and multi-tenancy across a common physical network.

  • VXLAN extends L2 over an L3 fabric (24-bit VNI = millions of segments).
  • EVPN provides control-plane learning and multi-tenancy.
  • Enables workload mobility and large tenant separation.

14.3 Storage and convergence

Storage traffic has its own rules: isolation from noisy workloads, jumbo frames, low loss and predictable low latency. Engineers match these with dedicated VLANs or fabrics, the correct frame size, and lossless Ethernet or Fibre Channel transport as the workload needs. A converged fabric such as FCoE or NVMe over TCP trades complexity for fewer cables and shared infrastructure.

NetworkPurpose
Front-endClient/app traffic
Storage (SAN)iSCSI/Fibre Channel, isolated, jumbo frames
ManagementDevice OOB access
Converged (FCoE/RoCE)One fabric for LAN + SAN

15 · Cloud Networking

15.1 VPCs, subnets and routing15.2 Security groups vs NACLs15.3 Connecting clouds and on-prem

Cloud networks are software-defined and self-service, with subnets, route tables and policies replacing boxes and cables. The design principles still hold, so plan address space, segmentation and redundancy as carefully as on premises. Build and manage everything through the provider’s API, console or infrastructure-as-code tooling rather than by hand.

15.1 VPCs, subnets and routing

A VPC is your private slice of a cloud provider, defined by its own CIDR blocks, subnets and route tables. Distribute application tiers across subnets and spread them over multiple availability zones for resilience, letting route tables steer traffic between subnets, internet gateways and transit gateways. Choose non-overlapping CIDRs, keep some headroom for growth and size each subnet ahead of time.

VPC 10.0.0.0/16
  public subnets  10.0.0.0/24, 10.0.1.0/24   -> route to Internet GW
  private subnets 10.0.10.0/24, 10.0.11.0/24 -> route via NAT GW
Spread subnets across AZs; one route table per tier.

A VPC split into public and private subnets, each with its own route table. Spreading tiers across availability zones is what buys resilience.

15.2 Security groups vs NACLs

Security groups filter traffic at the instance or interface level and are stateful, while network access control lists filter at the subnet boundary and are stateless. Combine both for defence in depth, using NACLs as a coarse allowance at the subnet and security groups as precise per-instance rules. Remember that the stateless NACL must explicitly permit return traffic, which is a common source of failures.

Security groupNACL
Applies toInstance/ENISubnet
StatefulYesNo
RulesAllow onlyAllow + deny
OrderAll evaluatedNumbered, first match

15.3 Connecting clouds and on-prem

Peering, VPNs and private endpoints stitch clouds together and back to your on-premises network. VPC peering connects cloud networks cheaply, site-to-site IPsec VPNs link offices into the cloud, and private endpoints such as Private Link keep traffic off the public internet. Route advertising, transit gateways and NAT gateways then tie the whole hybrid environment into one reachable space.

  • VPC peering / transit gateway for many VPCs.
  • Site-to-site VPN or dedicated link to on-prem.
  • Private endpoints so services never traverse the internet.
  • Centralised egress and inspection for consistent policy.

17 · Troubleshooting Methodology

17.1 A layered method17.2 The toolbelt17.3 Common failure patterns

A repeatable method beats raw intuition for finding faults, because it keeps the search structured and every step testable. Engineers form a hypothesis, isolate the affected layer, change one thing at a time and measure the result before moving on. Structured hunting solves cases faster and leaves behind a documented understanding of the network.

17.1 A layered method

Work the model bottom-up or top-down and change exactly one thing at a time, measuring after each step. Bottom-up fits total outages, checking cable and link status before routing, while top-down fits application complaints, working from the application toward the wire. This discipline separates guesses from fixes and keeps every attempt testable and reversible.

1 Define the problem precisely (who/what/where/when)
2 Work bottom-up or top-down through the layers
3 Compare a working vs broken path
4 Divide and conquer (test from the middle)
5 Form/hold one hypothesis at a time; change one thing
6 Document and fix the root cause

A six-step troubleshooting loop that keeps the hunt structured. One hypothesis at a time is what turns guesses into fixes.

17.2 The toolbelt

The standard command-line tools each answer one class of question. ipconfig or ip shows local addressing, ping tests reachability, traceroute or tracert reveals the path, arp and ip neighbour inspect layer 2, nslookup or dig query DNS, and captures such as tcpdump or Wireshark give ground truth. Match the tool to what you still do not know, and verify rather than assume.

ToolAnswers
ping / tracertReachability and path
ipconfig / ifconfigAddress, gateway, DNS
nslookup / digName resolution
arp -aL2 mapping
netstat / ssOpen ports and connections
tcpdump / WiresharkActual packets
curl / openssl s_clientApp/TLS issues

17.3 Common failure patterns

DNS, asymmetric routing, MTU, VLAN and NAT issues account for most real outages, so recognise the pattern and you halve the diagnostic time. A site that loads small pages but fails on large downloads points at MTU, and failures after a renumbering exercise point at DNS or NAT. Turn these signatures into checklists and runbooks, then confirm each with the right tools before escalating.

  • "It’s DNS." Can’t resolve → check records, forwarders, split-horizon.
  • Asymmetric routing → stateful firewalls drop return traffic.
  • MTU/PMTUD black holes → small packets work, large ones hang.
  • Wrong VLAN / native VLAN mismatch → no L2 reachability.
  • Exhausted NAT/connection table → intermittent failures at scale.
# MTU test: 1472 + 28 = 1500
ping -f -l 1472 8.8.8.8      # Windows
ping -M do -s 1472 8.8.8.8   # Linux

Pings with 1472 bytes of payload test for MTU black holes. If these fail but smaller pings work, you have a path MTU problem.
