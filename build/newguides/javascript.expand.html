13 · Web Storage and IndexedDB

13.1 localStorage and sessionStorage

Both are synchronous key/value stores that persist strings for one origin. They are simple, fast for small payloads, and the source of a surprising number of performance and correctness bugs.

What the two stores actually give you

localStorage keeps data until the user or the app removes it. sessionStorage is scoped to a single top-level browsing context and is discarded when that tab closes. Neither is shared with a different origin, and neither is sent to the server on every request the way a cookie is. That last property is why they replaced cookies for caching user preferences and drafts: a 40 KB preference blob in localStorage costs nothing on the network, whereas the same blob as a cookie would ride along on every image and stylesheet request.

The API is deliberately tiny: getItem, setItem, removeItem, clear and the length property. Values are coerced to strings, so anything you store that is not a string either silently becomes one or, for objects, becomes the useless "[object Object]". Wrapping every write in a small typed helper is the difference between a store you can reason about and one that returns "undefined" strings forever.

// A minimal, safe wrapper. Every value round-trips through JSON.
const store = {
  get(key, fallback = null) {
    try {
      const raw = localStorage.getItem(key);
      return raw === null ? fallback : JSON.parse(raw);
    } catch (err) {
      return fallback; // corrupt entry or storage blocked
    }
  },
  set(key, value) {
    try {
      localStorage.setItem(key, JSON.stringify(value));
      return true;
    } catch (err) {
      // QuotaExceededError or a privacy setting that denies writes
      console.warn('persist failed', key, err.name);
      return false;
    }
  },
  remove(key) {
    localStorage.removeItem(key);
  }
};

store.set('theme', { name: 'nord', density: 'compact' });
console.log(store.get('theme').name); // "nord"

Storage is synchronous, and that is the real cost

Reads and writes block the main thread. A single getItem returning a few hundred bytes is measured in microseconds and is invisible. Storing a 2 MB JSON document and parsing it on every keystroke is a different animal: the stringify, the write, and the subsequent parse all happen on the thread that is trying to paint the page. The classic symptom is a text editor that stutters when it autosaves a large draft.

The fix is not to abandon the API but to bound it. Keep hot state in memory and write to storage on a debounce, store a compact representation rather than a pretty one, and move anything genuinely large to IndexedDB, which is asynchronous by design. sessionStorage has the same synchronous cost, so it is not a performance escape hatch; it is a lifetime escape hatch.

localStorage is unavailable, or throws, when the user has blocked cookies in some browsers, when the page is embedded in a sandboxed iframe without allow-same-origin, or in some private-browsing modes. Always read through a try/catch and degrade to an in-memory object rather than assuming a successful write.

The storage event, and where it does not fire

When one tab changes a key, every other same-origin tab receives a storage event. The tab that made the change does not. The event carries key, oldValue, newValue, url and storageArea, which makes it a workable poor-man's broadcast channel for things like "the user logged out" or "the theme changed".

It is not a reliable synchronization primitive. The event fires after the fact, there is no ordering guarantee across many writers, and a burst of writes produces a burst of events. Use it to invalidate a cache or to nudge other tabs to re-read, never as the primary source of truth.

// Every other tab on this origin hears this.
window.addEventListener('storage', (event) => {
  if (event.storageArea !== localStorage) return; // ignore sessionStorage
  if (event.key === 'auth') {
    if (event.newValue === null) location.reload();
  }
});

// Broadcast a logout to sibling tabs.
localStorage.setItem('auth', JSON.stringify({ user: null, at: Date.now() }));
Storage is per origin, and origin means scheme plus host plus port. https://app.example.com and http://app.example.com are different stores, as are two ports on the same host. Moving a site from one hostname to another leaves the old store behind and users see their settings reset.

13.2 Quotas, serialization and structured clone

Storage limits are not a single number, they are a per-origin budget shared with IndexedDB and the Cache API. Knowing the rules prevents both silent data loss and the quota crashes that come with it.

The quota model in current browsers

Modern engines give each origin a share of the disk rather than a fixed 5 MB. The practical ceiling is typically around 60 percent of total disk for a given origin, with the whole browser capped so one origin cannot fill the drive. Quotas are shared across localStorage, sessionStorage, IndexedDB and the Cache API, so a service worker that caches 300 MB of media is eating the same budget as your database.

Browsers also enforce eviction. Under storage pressure a browser may clear the whole origin's bucket without asking, which is why anything users would be upset to lose must either be small, re-syncable from the server, or protected by navigator.storage.persist(). Persistent storage is granted heuristically, based on site engagement and whether the app is installed, and the call can simply return false.

// How much room is there, and how much is already used?
async function reportStorage() {
  if (!navigator.storage) return null;
  const { usage = 0, quota = 0 } = await navigator.storage.estimate();
  const megabytes = (bytes) => Math.round(bytes / (1024 * 1024));
  console.log(megabytes(usage) + ' MB used of ' + megabytes(quota) + ' MB');
  return { usage, quota };
}

// Ask the browser to exempt this origin from eviction.
const persisted = await navigator.storage.persist();
console.log('exempt from eviction:', persisted);

Structured clone is not JSON

postMessage, IndexedDB and structuredClone all use the structured clone algorithm rather than JSON. Structured clone understands Map, Set, Date, RegExp, ArrayBuffer, typed arrays, Blob, File and even circular references. JSON understands none of those and will happily turn a Date into a string and a Map into {}.

What structured clone cannot carry: functions, DOM nodes, class prototypes, symbols and getters that are not enumerable data. Cloning an instance of a class gives you a plain object with the same fields, not an instance, so a toJSON or an explicit rehydrate step is usually the honest choice. The practical rule is that localStorage is JSON, while IndexedDB and workers are structured clone, and mixing the two mental models produces bugs where a Date mysteriously becomes a string after a save and reload.

const original = {
  when: new Date('2026-01-01T00:00:00Z'),
  tags: new Set(['a', 'b']),
  board: new Map([['r1', 7]]),
  buffer: new Uint8Array([1, 2, 3])
};
original.self = original; // circular reference is fine

const copy = structuredClone(original);
console.log(copy.when instanceof Date); // true
console.log(copy.tags instanceof Set);  // true
console.log(copy.self === copy);        // true

// JSON, by contrast, mangles almost everything:
const json = JSON.parse(JSON.stringify(original)); // throws on circular refs
Structured clone has no size limit of its own, but it is not free: cloning a large typed array copies the bytes. When the goal is moving data to a worker rather than duplicating it, mark the buffer as transferable so ownership moves instead of being copied.

13.3 IndexedDB object stores and transactions

IndexedDB is the browser's real database: asynchronous, transactional, able to hold hundreds of megabytes of structured data, and cursed with an event-based API that predates promises.

The model: databases, object stores, records

An IndexedDB database contains named object stores, and an object store holds records keyed by a key path or by an out-of-line key. A store is roughly a table, a record is roughly a row, and a record's value can be any structured-cloneable object. The schema — the set of stores and indexes — is only changeable inside an upgrade transaction that the browser opens for you when it sees a version number higher than the stored one.

Everything happens in a transaction. A transaction is scoped to one or more stores, has a mode of readonly, readwrite or versionchange, and commits automatically when the microtask queue drains without new requests being issued. That auto-commit is the single most common surprise: if you await a fetch or a timer in the middle of a transaction, the transaction closes and the next request throws TransactionInactiveError. Keep transactions synchronous and short; do the network work outside, then open a fresh transaction to write.

// Open (or create) the database and declare its schema.
function openDb() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open('notes-db', 2);

    request.onupgradeneeded = (event) => {
      const db = request.result;
      const oldVersion = event.oldVersion;

      if (oldVersion < 1) {
        const notes = db.createObjectStore('notes', { keyPath: 'id', autoIncrement: true });
        notes.createIndex('by_updated', 'updatedAt');
      }
      if (oldVersion < 2) {
        const tags = db.createObjectStore('tags', { keyPath: 'name' });
        tags.createIndex('by_count', 'count');
      }
    };

    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
    request.onblocked = () => reject(new Error('another tab holds an old version'));
  });
}

const db = await openDb();
console.log(db.objectStoreNames);

Promisifying requests without breaking transactions

A request is a one-shot event emitter: it fires success or error exactly once. Wrapping each request in a promise is fine, because the request is issued inside the transaction and the promise settles on the same turn. What is not fine is awaiting something unrelated between two requests. A helper that resolves on onsuccess and rejects on onerror, plus a separate helper that resolves on the transaction's oncomplete, gives you both a usable value and a durable commit signal.

const ask = (request) => new Promise((resolve, reject) => {
  request.onsuccess = () => resolve(request.result);
  request.onerror = () => reject(request.error);
});

const done = (tx) => new Promise((resolve, reject) => {
  tx.oncomplete = () => resolve();
  tx.onerror = () => reject(tx.error);
  tx.onabort = () => reject(tx.error);
});

async function addNote(db, note) {
  const tx = db.transaction('notes', 'readwrite');
  const record = { ...note, updatedAt: Date.now() };
  const key = await ask(tx.objectStore('notes').add(record));
  await done(tx); // wait for the durable commit
  return key;
}

const id = await addNote(db, { title: 'Storage', body: 'IndexedDB basics' });
console.log('stored with key', id);
Do not await fetch() or setTimeout inside an open IndexedDB transaction. The transaction auto-commits as soon as the request queue empties and the microtask checkpoint passes, and every later request throws. Fetch first, then open the transaction.

Versioning and the blocked event

Bumping the version forces the browser to run your upgrade callback in every tab that has the database open. If a tab is still holding an old connection, the upgrade is blocked and the new tab waits. The standard remedy is to close idle connections when a versionchange event arrives on the old connection, then reload, so a deploy is not held hostage by a tab someone left open overnight.

// On the old connection: yield when a newer page wants to upgrade.
db.onversionchange = () => {
  db.close();
  console.info('A newer version of the app is open; close this tab or reload.');
};

// Detect connections held by other tabs during an upgrade.
request.onblocked = () => {
  console.warn('Upgrade blocked: another tab still has version ' + request.result.version);
};

13.4 Indexes, cursors and range queries

A store answers lookups by primary key. Everything else — "notes updated this week", "tags starting with c" — needs an index, and index lookups are what separate a query that scans ten thousand records from one that touches three.

Indexes over a key path

An index is created inside the upgrade transaction with createIndex(name, keyPath, options). Options matter: unique rejects duplicate index keys, and multiEntry indexes each element of an array value separately, which turns a tags: ['js', 'web'] array into two index entries. A record can appear under several index keys, so a store with three useful indexes can be answered in three different ways without any additional storage of the full record.

The index key is derived from the record at write time, so a compound key path such as ['status', 'updatedAt'] produces a key that sorts by status first and by timestamp second. That ordering is what makes a range query over the second component usable only when the first is pinned with an exact value.

// Inside onupgradeneeded
const notes = db.createObjectStore('notes', { keyPath: 'id' });
notes.createIndex('by_updated', 'updatedAt');
notes.createIndex('by_status_updated', ['status', 'updatedAt']);
notes.createIndex('by_tag', 'tags', { multiEntry: true });
notes.createIndex('by_slug', 'slug', { unique: true });

Cursors and key ranges

An IDBKeyRange describes a contiguous slice: only for an exact match, lowerBound, upperBound, and bound for both, each with an open flag for exclusive ends. A cursor walks the range in key order and fires once per record, which lets you stream a large result set without materialising it all in one array.

Direction is set at open time: next, prev, nextunique and prevunique. The unique variants skip records that share an index key, which is exactly what you want when you only need one example per tag. IndexedDB gives no ordering guarantee across different indexes, but within one index the order is always by key, so pagination by storing the last seen key is stable and cheap.

// Stream every note updated in the last 24 hours, newest first.
async function recentNotes(db, since) {
  const range = IDBKeyRange.lowerBound(since);
  const tx = db.transaction('notes', 'readonly');
  const index = tx.objectStore('notes').index('by_updated');
  const out = [];

  return new Promise((resolve, reject) => {
    const cursor = index.openCursor(range, 'prev');
    cursor.onsuccess = () => {
      const c = cursor.result;
      if (!c) return resolve(out);
      out.push(c.value);
      c.continue();
    };
    cursor.onerror = () => reject(cursor.error);
  });
}

// One note per tag, using the unique cursor direction.
function firstPerTag(db) {
  const tx = db.transaction('notes', 'readonly');
  const rows = [];
  const cursor = tx.objectStore('notes').index('by_tag').openCursor(null, 'nextunique');
  cursor.onsuccess = () => {
    const c = cursor.result;
    if (!c) return rows;
    rows.push({ tag: c.key, id: c.primaryKey });
    c.continue();
  };
  return rows;
}
Deleting or updating a record inside a cursor fires another cursor event for the mutated key in some implementations, because the index is being rewritten while you walk it. Collect keys first, then act on them in a separate transaction, whenever the operation changes an indexed field.

Counting and existence without reading values

count() over a range uses the index and returns a number, not records, so a "how many failed jobs today" badge costs almost nothing. For existence, open a cursor with a range of exactly the value you care about and stop after the first hit rather than loading all matches. Both patterns keep the amount of structured-cloned data crossing the transaction boundary to a minimum, which is where most of the time in a large query actually goes.

13.5 When to choose which store

Five storage mechanisms coexist in a modern browser, and picking the wrong one is a decision that is expensive to reverse. The choice follows from three questions: how much data, how is it queried, and who is allowed to lose it.

The decision in one table

The table below is the whole argument. Cookies are for the server; sessionStorage is for a tab's lifetime; localStorage is for small preferences; IndexedDB is for anything with structure or volume; the Cache API belongs to the service worker and is addressed by request.

StoreCapacityAccessBest for
Cookieabout 4 KB eachsent on every requestsession identity the server must see
sessionStoragea few MBsynchronouswizard state, per-tab drafts
localStoragea few MBsynchronoustheme, language, tiny preferences

Cache APIlarge, shared origin budgetasynchronousHTTP responses for a service worker

Four rules of thumb

First, if the server needs the value on each request, it is a cookie and nothing else will do, because no other store is transmitted. Second, if the value is under a few kilobytes and is read on startup, localStorage is the least code for the job. Third, if the value is large, structured, or something you need to query by more than its identity, it is IndexedDB. Fourth, if the value is an HTTP response you want to replay offline, it is the Cache API, ideally written by a service worker rather than by page code.

Two failure modes are worth naming. Writing a large dataset into localStorage and parsing it on every render is the most common performance bug in this area, because it is the path of least resistance. Treating localStorage as durable is the other: clients clear it, browsers evict it under pressure, and a user moving to a new laptop loses it. Anything that matters must exist on the server or be reconstructable, with local storage acting as a cache rather than the system of record.

// Choose a backend once, then hide the choice behind one interface.
async function createStore() {
  if (navigator.storage && navigator.storage.getDirectory) {
    return { kind: 'indexeddb', read: idbRead, write: idbWrite };
  }
  const probe = '__probe__';
  try {
    localStorage.setItem(probe, '1');
    localStorage.removeItem(probe);
    return { kind: 'localstorage', read: lsRead, write: lsWrite };
  } catch (err) {
    return { kind: 'memory', read: memRead, write: memWrite };
  }
}
Because the quota is shared, a service worker cache can starve your IndexedDB writes. If a feature stores media offline, cap the cache size deliberately in the worker and evict oldest-first rather than letting the browser decide which technology loses its data.

14 · Web Workers and concurrency

14.1 Dedicated, shared and service workers

JavaScript has one call stack per agent, so long work blocks paint and input. Workers put extra call stacks beside the main one, each with its own global scope and no DOM access.

Three worker kinds, three lifetimes

A dedicated worker is created by one page with new Worker(url) and dies with that page. It is the general tool for offloading computation: parsing, image processing, sorting, encryption. A shared worker is reachable from any same-origin page through a MessagePort, so several tabs share one instance — useful for a single websocket multiplexed across tabs, though support is uneven and most teams use BroadcastChannel instead.

A service worker is a different beast: it is an event-driven proxy sitting between the page and the network, with no page attached, and it is covered in the next chapter. It is not a place to run CPU work, because the browser will terminate it when it goes idle.

// main.js — a module worker; note the trailing comma in the options object
const worker = new Worker('./heavy.js', { type: 'module' });

worker.postMessage({ job: 'sort', rows: 500000 });
worker.addEventListener('message', (event) => {
  console.log('worker replied with', event.data);
});

// heavy.js
self.addEventListener('message', (event) => {
  const { rows } = event.data;
  const numbers = Array.from({ length: rows }, () => Math.random());
  numbers.sort((a, b) => a - b);
  self.postMessage({ median: numbers[Math.floor(rows / 2)] });
});

The worker global scope

Inside a worker you have self rather than window: timers, fetch, indexedDB, crypto, WebSocket, TextEncoder and the Cache API are available. There is no document, no localStorage, no direct DOM access, and no layout. Any result that must reach the screen comes back as a message.

That separation is the feature. It means a worker cannot accidentally touch shared DOM state, which removes a whole category of race conditions. It also means the boundary crossing is the only thing you have to reason about, and the next sub-topic is entirely about making that crossing cheap.

// feature-detect inside a worker
const caps = {
  canvas: typeof OffscreenCanvas !== 'undefined',
  storage: typeof indexedDB !== 'undefined',
  net: typeof fetch === 'function',
  wasm: typeof WebAssembly === 'object'
};
self.postMessage({ caps });

// An inline worker from a Blob avoids a second network request.
const source = 'self.onmessage = (e) => self.postMessage(e.data * 2);';
const blobUrl = URL.createObjectURL(new Blob([source], { type: 'text/javascript' }));
const inline = new Worker(blobUrl);
Workers do not have access to document, and that includes document.cookie and localStorage. If a worker needs a value from page storage, read it on the main thread and pass it in the first message rather than trying to reach for it on the worker side.

14.2 postMessage, structured clone and transferable objects

Everything that crosses a worker boundary is a message, and every message pays a cost. Structured clone copies; transfer moves. Knowing which one you triggered is the difference between a fast app and one that stalls on large payloads.

What a message round trip involves

postMessage(data) serialises data with the structured clone algorithm, queues it on the receiving agent, deserialises it there, and dispatches a message event. Functions, DOM nodes and class prototypes do not survive. Circular references do. For a small object the whole thing is sub-millisecond; for a 50 MB typed array it is a full copy of those bytes, and the copy happens on the sender's thread before the message is even queued, so a naive large postMessage blocks exactly the thread you were trying to unblock.

The transferable list, passed as the second argument, fixes that. It lists objects whose ownership moves rather than being copied: the sender's reference is neutered — its byteLength becomes 0 — and the receiver gets the actual memory. ArrayBuffer and its views, MessagePort, ImageBitmap, OffscreenCanvas and streams are transferable. The pattern for a repeated job is to keep one buffer, transfer it to the worker, let the worker write the result in place, and transfer it back. Zero copies, constant cost.

// Copying: the whole buffer is duplicated before the event is queued.
const pixels = new Uint8ClampedArray(width * height * 4);
worker.postMessage({ pixels });

// Transferring: ownership moves, the sender is left with a neutered buffer.
const buffer = pixels.buffer;
worker.postMessage({ pixels, width, height }, [buffer]);
console.log(pixels.byteLength); // 0 — do not use it again

// The worker can transfer it back when it is finished.
self.onmessage = ({ data }) => {
  const view = new Uint8ClampedArray(data.pixels.buffer ?? data.pixels);
  // ... mutate view in place ...
  self.postMessage({ pixels: view, width: data.width }, [view.buffer]);
};

Typed-array views must be transferred, not their views

The transferable is the underlying ArrayBuffer, not the Uint8Array that views it. Transferring a buffer that has other views alive leaves those views detached, which is why the pattern above re-wraps the incoming buffer in a fresh view on the worker side. Also note that a subarray shares its parent's buffer: transferring the parent to a worker detaches the subarray too, silently. Slice first if both sides need the bytes.

// A round trip that preserves one buffer instead of allocating per job.
worker.onmessage = ({ data }) => {
  const next = new Uint8Array(data.buffer);
  // reuse `next` for the next frame
};

function sendFrame(buffer) {
  transferInFlight = true;
  worker.postMessage({ buffer }, [buffer]);
}

// Guard against sending while a previous transfer is still out.
let transferInFlight = false;
A transferred buffer is not usable on the sending side. Reusing it, or a view over it, after the postMessage gives you a zero-length array and a bug that only appears under load. Ping-pong the same buffer back and forth, and never keep a second reference to a buffer you transferred.

MessagePort: a private, directed channel

For anything more complex than one request/response pair, create an explicit channel with new MessageChannel(). The two ends are port1 and port2; transfer one end and the two sides now have a dedicated pipe that no other message can be confused with. Ports must be start()ed or have an onmessage handler attached, otherwise queued messages never wake the receiver.

const channel = new MessageChannel();
const worker = new Worker('./stream.js', { type: 'module' });

worker.postMessage({ port: channel.port1 }, [channel.port1]);
channel.port2.onmessage = (event) => console.log('progress', event.data);

// stream.js
self.onmessage = ({ data: { port } }) => {
  let i = 0;
  const timer = setInterval(() => {
    port.postMessage({ done: i += 5 });
    if (i >= 100) clearInterval(timer);
  }, 20);
};

14.3 SharedArrayBuffer and Atomics

Everything so far moved data by copying or by handing ownership over. A shared buffer is different: two agents read and write the same bytes, which enables real parallelism and the entire class of race conditions that comes with it.

Why sharing needs cross-origin isolation

SharedArrayBuffer was removed from browsers in 2018 because it enabled timing attacks such as Spectre. It is now available only to cross-origin isolated documents, which means every response must carry Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp. Until both headers are present, crossOriginIsolated is false and the constructor throws. That is why a shared-memory feature must be guarded and, in most codebases, wrapped behind a fallback that copies instead.

if (crossOriginIsolated) {
  const shared = new SharedArrayBuffer(1024 * 1024); // 1 MB, no transfer needed
  const view = new Int32Array(shared);
  worker.postMessage({ shared, count: 4 });
} else {
  console.warn('SharedArrayBuffer unavailable: enable COOP and COEP');
}

Atomics: the only safe way to touch it

Ordinary reads and writes to a shared buffer are not synchronized, and the compiler is free to cache a value in a register so a polling loop never observes a change. Atomics provides the primitives: load, store, add, sub, exchange, compareExchange, plus wait and notify for blocking and waking. A worker pool usually combines an atomic counter used as a job index with a control word used as a sleep/wake signal.

// worker.js — take the next index atomically, so two workers never collide.
self.onmessage = ({ data: { shared, total, done } }) => {
  const index = new Int32Array(shared);
  const results = new Float64Array(shared, 64);
  const flag = new Int32Array(done);

  for (;;) {
    const job = Atomics.add(index, 0, 1);
    if (job >= total) break;
    results[job] = Math.sqrt(job) * Math.PI;
  }
  Atomics.add(flag, 0, 1);          // report completion
  Atomics.notify(flag, 0);          // wake the main thread if it is waiting
};

// main.js — block until every worker has finished.
const flag = new Int32Array(new SharedArrayBuffer(4));
while (Atomics.load(flag, 0) < workerCount) {
  Atomics.wait(flag, 0, Atomics.load(flag, 0), 1000); // timeout in ms
}
Atomics.wait is not allowed on the main thread of a browser, because blocking the UI is precisely what it prevents. Main-thread coordination uses Atomics.waitAsync, which returns a promise, or simply polls with a timeout while yielding to the event loop.

When sharing is worth the complexity

Shared memory pays for itself when the data is large and the access pattern is fine-grained and concurrent: a growth simulation, a physics grid updated by several workers, an audio processing graph, a WASM module with threads. For a one-shot sort or a JSON parse, the extra headers, the fallback path and the atomic discipline cost far more than the copy they avoid. Reach for it only when profiling shows memory bandwidth is the bottleneck, not when it merely looks impressive on a diagram.

14.4 Worker pools and offloading heavy work

One worker is a thread; several workers behind a queue are a scheduler. A pool bounds concurrency to the number of hardware threads, reuses expensive instances, and keeps a burst of jobs from spawning a worker per task.

Sizing a pool

Spawn roughly navigator.hardwareConcurrency workers, clamped to a sane range such as two to eight. Below that you leave cores idle; above it, context switching and duplicated per-worker startup cost dominate. A worker also has a fixed memory cost of several megabytes, so a 32-worker pool on a small laptop is worse than four. If jobs are heterogeneous, keep one small dedicated worker for latency-sensitive work and a larger pool for batch work rather than sharing a single queue.

Startup is not free either. Compiling a large module worker can take tens of milliseconds, so create the pool lazily on first use and keep it warm. The pool should also be the owner of the transferable buffers, recycling them between jobs so steady-state usage allocates nothing.

class WorkerPool {
  constructor(url, size) {
    const cores = navigator.hardwareConcurrency || 4;
    this.size = Math.max(2, Math.min(size ?? cores, 8));
    this.url = url;
    this.idle = [];
    this.queue = [];
    this.pending = new Map();
    this.started = false;
  }

  start() {
    if (this.started) return;
    this.started = true;
    for (let i = 0; i < this.size; i += 1) {
      const worker = new Worker(this.url, { type: 'module' });
      worker.onmessage = (event) => this.settle(worker, event.data);
      worker.onerror = (event) => this.fail(worker, event.message);
      this.idle.push(worker);
    }
  }

  run(payload, transfer = []) {
    this.start();
    return new Promise((resolve, reject) => {
      this.queue.push({ payload, transfer, resolve, reject });
      this.drain();
    });
  }

  drain() {
    while (this.idle.length > 0 && this.queue.length > 0) {
      const worker = this.idle.pop();
      const job = this.queue.shift();
      this.pending.set(worker, job);
      worker.postMessage(job.payload, job.transfer);
    }
  }

  settle(worker, data) {
    const job = this.pending.get(worker);
    this.pending.delete(worker);
    if (job) job.resolve(data);
    this.idle.push(worker);
    this.drain();
  }

  fail(worker, message) {
    const job = this.pending.get(worker);
    this.pending.delete(worker);
    if (job) job.reject(new Error(message));
    worker.terminate();
    const replacement = new Worker(this.url, { type: 'module' });
    replacement.onmessage = (event) => this.settle(replacement, event.data);
    this.idle.push(replacement);
    this.drain();
  }
}

const pool = new WorkerPool('./tile-worker.js');
const tiles = await Promise.all(chunks.map((c) => pool.run({ chunk: c })));

Progress, cancellation and errors

A pool needs a correlation id on every message if a worker can be running more than one logical job, and it needs a defined behaviour for cancellation: either terminate the worker and replace it — expensive but immediate — or set a shared flag the job checks between units of work. Errors do not cross the boundary as exceptions; a thrown error inside a worker fires onerror on the page with a message and a filename, and the pool must reject the corresponding promise and replace the dead worker or future jobs will queue forever.

// Report progress without finishing the job.
self.onmessage = ({ data }) => {
  const { id, rows } = data;
  const out = new Float32Array(rows);
  for (let i = 0; i < rows; i += 1) {
    out[i] = Math.sin(i / 100);
    if (i % 20000 === 0) {
      self.postMessage({ id, type: 'progress', done: i, total: rows });
    }
  }
  self.postMessage({ id, type: 'done', out }, [out.buffer]);
};
OffscreenCanvas is the clean way to run rendering in a worker: transfer the canvas once, then draw frames off the main thread. Combine it with requestAnimationFrame in the worker and the page's main thread never touches a single pixel.

15 · Service Workers and Progressive Web Apps

15.1 Lifecycle: install, activate, fetch

A service worker is a script the browser runs independently of any page, intercepting network requests for its scope. Its lifecycle is deliberately conservative so that one bad deploy cannot brick every open tab.

Registration and scope

The page registers a worker with navigator.serviceWorker.register(url, { scope }). The scope defaults to the worker's own directory and cannot be widened without a Service-Worker-Allowed response header, which is why a worker served from /js/sw.js can only control /js/ by default. Register from the top level of the app and serve the script from the root if you want to control every navigation.

The worker runs only on HTTPS, or on localhost, because a cached response from an untrusted origin is a security problem. It has no DOM, no window and no localStorage; it has self, caches, fetch, indexedDB, clients and an event-driven lifetime. The browser starts it when an event arrives and terminates it when idle, so module-level state does not survive; anything that must persist goes in IndexedDB or the Cache API.

// Page code: register once, at the top level of the app.
if ('serviceWorker' in navigator) {
  window.addEventListener('load', async () => {
    const reg = await navigator.serviceWorker.register('/sw.js', { scope: '/' });
    console.log('scope', reg.scope);
    reg.addEventListener('updatefound', () => console.log('new worker installing'));
  });
}

The three phases and the third one that is not install or activate

Install fires once per version. It is the place to pre-cache the shell: open the cache, add the URLs, and fail loudly if any of them 404s, because a failed install aborts the whole thing. Activate fires once after install, and is the place to delete caches from previous versions and to take control of open pages. Fetch fires for every controlled request, for the lifetime of the version, and is where the caching strategy lives.

A newly installed worker does not control the page that registered it until that page reloads, unless it calls clients.claim() during activation. That is intentional: swapping the network layer under a running app mid-session can break in-flight state. It is also why a first visit frequently appears to ignore the worker until the second navigation.

// sw.js
const VERSION = 'v7';
const SHELL = ['/', '/index.html', '/app.css', '/app.js', '/offline.html'];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(VERSION).then((cache) => cache.addAll(SHELL))
  );
});

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const keys = await caches.keys();
    await Promise.all(keys.filter((k) => k !== VERSION).map((k) => caches.delete(k)));
    await self.clients.claim(); // take over pages that are already open
  })());
});

self.addEventListener('fetch', (event) => {
  event.respondWith(route(event.request));
});

async function route(request) {
  const cached = await caches.match(request);
  return cached || fetch(request);
}
A service worker is torn down between events to save memory, so event.waitUntil(promise) is not optional when your handler does asynchronous work. Return the promise and the browser keeps the worker alive until it settles; leave it out and the worker may be killed mid-write.

15.2 Caching strategies

A caching strategy is a statement about which of two sources wins and what happens when one of them fails. There are five that cover almost every case, and most apps should use different ones per request type.

The five strategies

Cache first answers from the cache and only goes to the network on a miss. It is the fastest option for versioned, immutable assets such as hashed bundles and fonts, and the wrong choice for anything that changes, because the user sees a stale copy until the cache is versioned out. Network first tries the network and falls back to the cache, which is right for API data the user expects to be fresh, at the cost of a slow first byte when the network is poor.

Stale while revalidate returns the cached copy immediately and refreshes the cache in the background. It gives a fast response and eventual freshness, which is ideal for headlines, avatars and non-critical lists. Cache only and network only are for the two extremes: precached shell files that must never hit the network, and requests that must never be cached at all, such as authenticated POSTs or analytics beacons.

// Cache first, with a network fallback and an offline page.
async function cacheFirst(request, cacheName) {
  const cache = await caches.open(cacheName);
  const hit = await cache.match(request);
  if (hit) return hit;
  try {
    const response = await fetch(request);
    if (response.ok) cache.put(request, response.clone());
    return response;
  } catch (err) {
    return caches.match('/offline.html');
  }
}

// Stale while revalidate: answer now, refresh in the background.
async function staleWhileRevalidate(request, cacheName) {
  const cache = await caches.open(cacheName);
  const hit = await cache.match(request);
  const update = fetch(request)
    .then((response) => {
      if (response.ok) cache.put(request, response.clone());
      return response;
    })
    .catch(() => hit);
  return hit || update;
}

Routing by request type

A real worker decides per request. Navigations get network first with an offline fallback so a deploy is visible immediately; hashed static assets get cache first because their URL changes when their content does; images get stale while revalidate; API calls get network first with a short timeout and a cached fallback for the offline case. Only same-origin, GET requests should be cached — a cross-origin POST or an OAuth redirect must pass straight through.

self.addEventListener('fetch', (event) => {
  const { request } = event;
  if (request.method !== 'GET') return; // never cache mutations
  const url = new URL(request.url);
  if (url.origin !== self.location.origin) return;

  if (request.mode === 'navigate') {
    event.respondWith(networkFirst(request));
  } else if (url.pathname.startsWith('/assets/')) {
    event.respondWith(cacheFirst(request, 'v7'));
  } else if (url.pathname.startsWith('/api/')) {
    event.respondWith(networkFirst(request, 3000));
  } else {
    event.respondWith(staleWhileRevalidate(request, 'v7'));
  }
});
Never cache a response to an authenticated API call in a shared cache without varying on the credential, or one user's data can be served to another. If a response depends on a cookie or an Authorization header, either leave it uncached or store it in a per-user cache name.

Partial content and opaque responses

Range requests — 206 Partial Content — cannot be cached and replayed as if they were complete; a cached 206 served to a request expecting the whole file produces a truncated media element. Cross-origin requests made without CORS produce an opaque response whose status the worker cannot read, so response.ok is always false for them and a size check is impossible. If you must cache them, cache them deliberately and account for the padding browsers report as quota usage.

15.3 The web app manifest and installability

A service worker makes an app work offline; a manifest makes it installable. Installability is a browser-defined bar: the app is served over HTTPS, has a worker with a fetch handler, and has a manifest with a name, icons and a start URL.

The required fields

15.4 Push notifications and background sync

Two capabilities let a worker act with no page open: push wakes it from the server, and background sync wakes it from a failed request. Both run in the worker's event loop, with all the lifetime rules that implies.

Subscriptions and the push message

Push requires permission, a PushManager subscription and a server that holds the endpoint and the keys. registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey }) returns an object whose endpoint is a capability URL — anyone who has it can push to that user, so it must be stored server-side, not in page code. The server encrypts the payload, the browser decrypts it and fires a push event in the worker, and the handler has a hard deadline of a few seconds to display a notification or the browser may show nothing at all.

Every push must produce a visible notification on most platforms, which is why userVisibleOnly is mandatory in Chrome: silent push is a spamming vector. Notifications are also the only click target while the app is closed, so the notificationclick handler decides whether to focus an existing client or open a new window.

// Page: ask, then subscribe.
const registration = await navigator.serviceWorker.ready;
const permission = await Notification.requestPermission();
if (permission === 'granted') {
  const subscription = await registration.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(VAPID_PUBLIC_KEY)
  });
  await fetch('/api/push/subscribe', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify(subscription)
  });
}

// sw.js
self.addEventListener('push', (event) => {
  const data = event.data ? event.data.json() : { title: 'Update', body: 'New content' };
  event.waitUntil(self.registration.showNotification(data.title, {
    body: data.body,
    tag: data.tag,        // replaces a previous notification with the same tag
    data: { url: data.url },
    icon: '/icons/icon-192.png'
  }));
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  const target = event.notification.data.url || '/';
  event.waitUntil((async () => {
    const list = await self.clients.matchAll({ type: 'window' });
    const existing = list.find((c) => c.url.includes(target));
    if (existing) return existing.focus();
    return self.clients.openWindow(target);
  })());
});

Background sync and periodic sync

SyncManager retries a named task when connectivity returns, which turns "the user hit save while offline" into a durable queue rather than a lost write. The page calls registration.sync.register('outbox'); the worker listens for sync, drains an IndexedDB queue, and rethrows if it should be retried. periodicsync adds a coarse interval, but it requires an installed app and a high site engagement score, so it cannot be relied on for correctness — only for prefetching.

self.addEventListener('sync', (event) => {
  if (event.tag !== 'outbox') return;
  event.waitUntil(flushOutbox());
});

async function flushOutbox() {
  const pending = await readQueue('outbox');
  for (const item of pending) {
    const response = await fetch(item.url, item.init);
    if (!response.ok) throw new Error('retry later'); // fails the sync, browser retries
    await removeFromQueue('outbox', item.id);
  }
}

// Page side: queue the write, then ask the browser to retry when online.
await enqueue('outbox', { url: '/api/notes', init: { method: 'POST', body: body } });
await navigator.serviceWorker.ready.then((reg) => reg.sync.register('outbox'));
A failing sync event is retried by the browser with its own backoff, but a bug that always throws will retry forever. Count attempts on the queued item and drop or park anything that has failed more than a handful of times.

15.5 Update flow and cache versioning

A service worker sits between the user and the server, so it can serve a deploy the user never sees. An update flow is the set of decisions that make a new version arrive, arrive atomically, and not break a running session.

When the browser checks for a new worker

The browser bypasses the HTTP cache for the worker script — modern engines cap that at 24 hours regardless of headers — and starts an update check on navigation, on functional events, and when registration.update() is called. If the script's bytes differ, the new worker installs in parallel and waits. The old worker keeps serving until every client using it is gone or the new one calls skipWaiting().

That "waiting" state is the crux. Auto-skipping gives users the new version immediately but can swap the network layer while a page holds in-flight state. Never auto-skipping means a long-lived tab pins an old version indefinitely. The usual compromise is to prompt: the page watches updatefound and statechange, shows a "reload to update" banner, and on confirmation sends skipWaiting to the waiting worker and reloads after controllerchange. Guard the reload so it fires once, not on every claim.

// Page: offer an update instead of applying it silently.
const registration = await navigator.serviceWorker.register('/sw.js');
let reloading = false;

registration.addEventListener('updatefound', () => {
  const installing = registration.installing;
  installing.addEventListener('statechange', () => {
    if (installing.state === 'installed' && navigator.serviceWorker.controller) {
      showUpdateBanner(() => installing.postMessage({ type: 'SKIP_WAITING' }));
    }
  });
});

navigator.serviceWorker.addEventListener('controllerchange', () => {
  if (reloading) return; // statechange fires more than once
  reloading = true;
  location.reload();
});
// sw.js
self.addEventListener('message', (event) => {
  if (event.data?.type === 'SKIP_WAITING') self.skipWaiting();
});

// Version the cache by build id so a deploy cannot collide with the old one.
const BUILD = '2026-10-15T09';
const SHELL_CACHE = 'shell-' + BUILD;
const DATA_CACHE = 'data-' + BUILD;

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const keys = await caches.keys();
    const keep = [SHELL_CACHE, DATA_CACHE];
    await Promise.all(keys.filter((k) => !keep.includes(k)).map((k) => caches.delete(k)));
    await self.clients.claim();
  })());
});

Atomic updates and the cache name is the version

Because the cache name encodes the build, activation deletes exactly the previous generation, and there is no window in which half the assets come from the new version and half from the old. Precaching during install is what makes the switch atomic: either every shell file is present in the new cache, or the install fails and the old worker keeps running. Never write cache names by hand in two places; derive them from one constant, and never reuse a name across builds, because a stale entry with the same name is invisible to every deletion routine.

A worker that fails to install leaves a broken app for anyone who only ever gets the new version, so test the offline path explicitly: load once online, then stop the server and reload. If the shell is not cached before activation, the user sees the browser's offline error rather than your page.

16 · Real-time browser communication

16.1 WebSocket

The WebSocket API is a single bidirectional connection that begins as an HTTP request and then upgrades. It is the default transport whenever the client and server both need to send at any time.

How the connection is established

The client sends an HTTP request with Upgrade: websocket and a base64 nonce. A server that agrees answers 101 Switching Protocols, and from that point the TCP connection carries framed messages in both directions with no further HTTP overhead. The handshake is a normal HTTP request, so cookies, subprotocols and an Origin header all travel with it, which is what lets your existing session authentication work without a separate token exchange — and what makes an origin check on the server essential, since browsers do not apply the same-origin policy to WebSocket connections the way they do to fetches.

A message can be a string or binary. Strings are UTF-8; binary arrives as a Blob by default, or as an ArrayBuffer if you set binaryType = 'arraybuffer'. There is no request/response correlation in the protocol itself, so an application-level id is needed the moment two operations can be in flight at once.

const socket = new WebSocket('wss://api.example.com/live', ['app.v2']);
socket.binaryType = 'arraybuffer';

socket.addEventListener('open', () => {
  socket.send(JSON.stringify({ type: 'hello', at: Date.now() }));
});

socket.addEventListener('message', (event) => {
  if (typeof event.data === 'string') {
    const message = JSON.parse(event.data);
    handle(message);
  } else {
    renderFrame(new Uint8Array(event.data));
  }
});

socket.addEventListener('close', (event) => {
  console.log('closed', event.code, event.reason, 'clean:', event.wasClean);
});

socket.addEventListener('error', () => console.warn('socket error'));

// Backpressure: bufferedAmount grows if you send faster than the link drains.
function sendSafely(payload) {
  if (socket.bufferedAmount > 1024 * 1024) {
    console.warn('dropping frame, buffer is full');
    return false;
  }
  socket.send(payload);
  return true;
}

Close codes, backpressure and the half-open problem

bufferedAmount is the only flow-control signal the API exposes. Sending a stream of frames faster than the network drains queues them in memory and grows without bound, which is the usual cause of a tab allocating gigabytes during a video call. Watch the value and drop or coalesce frames rather than accumulating them.

A connection can also die without a close frame — a dropped cell connection, a suspended laptop, a NAT table expiry. No close event fires until TCP eventually times out, which can be minutes, so an application-level heartbeat is mandatory for anything that must be known to be alive. That is covered in 16.4.

A WebSocket connection does not survive the page entering the back-forward cache in a usable state, and mobile browsers terminate sockets aggressively on background. Treat every disconnect as normal and design the UI to resync from a server cursor rather than assuming a continuous stream.

16.2 Server-Sent Events

SSE is a one-way stream over ordinary HTTP where the server keeps the response open and writes text frames. It is far simpler than WebSocket and, for notifications and live feeds, usually the better choice.

The wire format and the client API

A response with Content-Type: text/event-stream stays open and carries named fields separated by blank lines: event for the type, data for the payload, id for the last event identifier, and retry for the reconnection delay in milliseconds. The EventSource object reconnects on its own and, crucially, sends Last-Event-ID on the next request so the server can replay what was missed. That automatic resumption with replay is the feature WebSocket makes you build yourself.

The cost is direction: the client cannot push. A typical design pairs a read-only SSE stream with normal POSTs for writes, which is enough for dashboards, chat read receipts, build logs, notification bells and price tickers.

// Client
const stream = new EventSource('/api/events', { withCredentials: true });

stream.addEventListener('message', (event) => append(JSON.parse(event.data)));
stream.addEventListener('build', (event) => updateBuild(JSON.parse(event.data)));
stream.addEventListener('open', () => setStatus('live'));
stream.addEventListener('error', () => {
  // EventSource retries automatically; readyState 2 means it gave up.
  if (stream.readyState === 2) scheduleManualRetry();
});

// Server (Node) — one event with an id so a reconnect can resume.
res.writeHead(200, {
  'content-type': 'text/event-stream',
  'cache-control': 'no-cache',
  connection: 'keep-alive'
});
let id = 0;
setInterval(() => {
  id += 1;
  res.write('id: ' + id + '\n');
  res.write('event: build\n');
  res.write('data: ' + JSON.stringify({ id, state: 'running' }) + '\n\n');
}, 1000);

Buffering, proxies and connection limits

The usual reason an SSE stream "does not work in production" is an intermediary that buffers the response. Nginx needs proxy_buffering off and X-Accel-Buffering: no; a CDN may need explicit configuration; and a compression middleware can hold the whole stream until a flush. Sending an initial comment line of a few kilobytes of padding forces early flushes in some stacks and is a common workaround.

The other limit is per-origin connection count. Under HTTP/1.1 a browser allows about six connections per origin, and an SSE stream occupies one permanently, which can starve ordinary requests. Under HTTP/2 or HTTP/3 the limit is far higher and multiplexed, so serve SSE over HTTP/2 and keep a comment heartbeat flowing every 15 to 30 seconds so idle proxies do not close the pipe.

# nginx: disable buffering for the event stream route
location /api/events {
  proxy_pass http://app;
  proxy_http_version 1.1;
  proxy_set_header Connection '';
  proxy_buffering off;
  proxy_cache off;
  chunked_transfer_encoding off;
  add_header X-Accel-Buffering no;
  proxy_read_timeout 1h;
}
Because EventSource reconnects automatically, server-side replay support is what makes the stream correct rather than merely available. Keep a short ring buffer of recent events keyed by id, and honour Last-Event-ID on the reconnect request.

16.3 WebRTC data channels

WebRTC connects two browsers directly, so the data does not traverse your server in steady state. The data channel is the part of that stack you can use without any media, and it is the only browser transport that can be unreliable and unordered on purpose.

Peer connections, ICE and SDP

Two peers exchange session descriptions through a signalling channel of your own choosing — usually your WebSocket — then probe for a working network path using ICE candidates gathered from STUN and, when a direct path is impossible, relayed through TURN. STUN is cheap and works for most home networks; TURN relays all traffic through your server and is the reason a working WebRTC deployment still needs bandwidth. Roughly one in five connections needs TURN, and shipping without it produces intermittent, geography-dependent failures that are miserable to debug.

The security model matters too. RTCPeerConnection is DTLS-encrypted and requires a secure context; media access needs user permission; and ICE candidates can leak local IP addresses unless an iceTransportPolicy of relay is set. Everything is authenticated by fingerprint in the SDP, so the signalling channel must itself be trusted — an attacker who can tamper with signalling can substitute a peer.

const pc = new RTCPeerConnection({
  iceServers: [{ urls: 'stun:stun.example.com' }]
});

const channel = pc.createDataChannel('chat', { ordered: true });
channel.onopen = () => channel.send(JSON.stringify({ type: 'ping' }));
channel.onmessage = (event) => console.log('peer said', event.data);

pc.onicecandidate = (event) => {
  if (event.candidate) signal.send({ candidate: event.candidate });
};

pc.ondatachannel = (event) => {
  event.channel.onmessage = (e) => console.log('incoming', e.data);
};

// Offerer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
signal.send({ sdp: pc.localDescription });

// Answerer
pc.ondatachannel = (event) => attach(event.channel);
await pc.setRemoteDescription(offer);
const answer = await pc.createAnswer();
await pc.setLocalDescription(answer);
signal.send({ sdp: pc.localDescription });

Ordering and reliability are configurable

A data channel has three knobs that HTTP and WebSocket do not expose. ordered: false lets messages arrive out of order, which removes head-of-line blocking at the cost of application complexity. maxRetransmits limits retries and maxPacketLifeTime limits the retry window, so a stale position update can be dropped rather than delivered late. Setting either of those makes the channel unreliable, which is the right choice for game state, cursor positions and live annotations, and the wrong choice for chat or file transfer.

Bandwidth estimation is automatic but coarse: there is no direct throughput API, so senders must adapt using bufferedAmount and application-level acknowledgements, exactly as with WebSocket. Large payloads must be chunked with a chunk size under about 16 KB and, on unreliable channels, with a header so a lost chunk does not corrupt the file.

// A lossy channel for state that is worthless once superseded.
const cursor = pc.createDataChannel('cursor', {
  ordered: false,
  maxRetransmits: 0
});

cursor.send(JSON.stringify({ x, y, t: Date.now() }));

// Chunked transfer for anything larger than a packet or two.
const CHUNK = 16 * 1024;
const bytes = new Uint8Array(await file.arrayBuffer());
for (let offset = 0; offset < bytes.length; offset += CHUNK) {
  const slice = bytes.subarray(offset, offset + CHUNK);
  transfer.send(JSON.stringify({ id, offset, total: bytes.length, data: slice }));
}
Do not build a small WebRTC data channel that carries JSON between two tabs and expect WebSocket-level ergonomics. Signalling, TURN, permission prompts and per-browser quirks make it heavier than a server relay; choose it when latency or privacy genuinely requires a direct path, or when the payload is media.

16.4 Reconnection, backoff and heartbeats

Real networks drop. A transport that has no reconnection policy is a feature that works on a desk and fails in a lift. This sub-topic is the small amount of code that makes all three transports dependable.

Exponential backoff with jitter

Retrying immediately after a failure hammers a server that is probably already struggling, and a thousand clients doing it in lockstep produce a thundering herd on recovery. The fix is exponential backoff with full jitter: delay is a random value between zero and a ceiling that doubles each attempt, capped at some maximum such as 30 seconds. The cap matters — without it, a client that slept through a long outage takes hours to notice it is back.

Reset the attempt counter only on evidence of health, not on a successful TCP connect. A socket that opens and closes repeatedly is a server that is failing, and treating each open as success produces a fast reconnect loop that looks exactly like an attack.

function backoffDelay(attempt, base = 800, cap = 30000) {
  const ceiling = Math.min(cap, base * 2 ** attempt);
  return Math.random() * ceiling; // full jitter
}

class ReliableSocket {
  constructor(url, onMessage) {
    this.url = url;
    this.onMessage = onMessage;
    this.attempt = 0;
    this.healthy = false;
    this.connect();
  }

  connect() {
    this.socket = new WebSocket(this.url);
    this.socket.addEventListener('open', () => {
      this.healthy = false;      // only a heartbeat confirms health
      this.startHeartbeat();
    });
    this.socket.addEventListener('message', (event) => {
      const message = JSON.parse(event.data);
      if (message.type === 'pong') { this.noteHealthy(); return; }
      this.onMessage(message);
    });
    this.socket.addEventListener('close', () => {
      this.stopHeartbeat();
      const delay = backoffDelay(this.attempt);
      this.attempt = Math.min(this.attempt + 1, 10);
      setTimeout(() => this.connect(), delay);
    });
  }

  noteHealthy() {
    this.healthy = true;
    this.attempt = 0;
  }

  startHeartbeat() {
    this.timer = setInterval(() => {
      if (this.socket.readyState !== WebSocket.OPEN) return;
      if (!this.healthy) this.socket.close(); // missed the last pong
      this.healthy = false;
      this.socket.send(JSON.stringify({ type: 'ping', at: Date.now() }));
    }, 15000);
  }

  stopHeartbeat() {
    clearInterval(this.timer);
  }
}

Heartbeats, resume tokens and offline awareness

A heartbeat is a small message sent on a fixed interval with a deadline for the reply. If the reply does not come, the connection is treated as dead and closed deliberately — which is what turns a silent, half-open socket into a close event the backoff logic can act on. Servers often do the same from their side, so pick an interval below the proxy's idle timeout; 15 to 30 seconds is typical.

Reconnecting is only half the job. The client also needs to know what it missed, which means the server must expose a monotonic cursor — a sequence number, an event id or a timestamp — and the client must send the last one it processed. On resume, the server replays from that cursor. Store the cursor in IndexedDB or localStorage before acknowledging the message so a crash cannot lose it. Finally, listen to online, offline and visibilitychange: reconnecting on a phone that has been asleep for an hour is usually better done on the next visible frame than on a timer that fired while the tab was frozen.

// Resume from the last processed cursor instead of starting over.
const cursorKey = 'events.cursor';

async function openWithResume() {
  const lastId = localStorage.getItem(cursorKey) || '0';
  const url = '/api/events?since=' + encodeURIComponent(lastId);
  const response = await fetch(url, { headers: { accept: 'text/event-stream' } });
  consume(response.body);
}

window.addEventListener('online', () => console.log('network back, retry now'));
window.addEventListener('offline', () => console.log('network gone, pause retries'));
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') socket.close(); // trigger a fresh connect
});
Page unload is not a reliable place to persist a cursor — beforeunload may not run on mobile. Write the cursor as each batch is acknowledged, not when the tab closes.

16.5 Choosing a transport

Four mechanisms look similar from a diagram and behave very differently in production. The choice is driven by direction, fan-out, latency budget and how much infrastructure you are prepared to operate.

The comparison that decides it

TransportDirectionReconnectBest for
Pollingclient pulltrivial, nothing to reconnectslow-changing data, simple deploys
SSEserver to clientautomatic with Last-Event-IDfeeds, notifications, logs, read-only streams
WebSocketbidirectionalyou write itchat, collaboration, games, presence
WebRTC data channelpeer to peeryou write it, plus ICE restartmedia, privacy-sensitive or ultra-low latency paths

Start at the top of that table and move down only when the row above cannot do the job. Polling with a sensible interval handles more "real-time" requirements than teams admit, and it needs no new server infrastructure, survives every proxy, and reconnects by definition. SSE is the right answer for the very common case of updates that flow one way; it is a few lines on both sides and the browser does the hard part. WebSocket earns its complexity when the client genuinely pushes at the same rate, or when fan-out per message is small and volume is high. WebRTC is the last resort, justified by latency or by a requirement that traffic not pass through your server at all.

// A polling loop that adapts instead of hammering the server.
async function poll(cursor, { min = 2000, max = 60000 } = {}) {
  let interval = min;
  for (;;) {
    const response = await fetch('/api/changes?since=' + cursor);
    if (response.status === 429) {
      interval = Math.min(max, interval * 2); // server is unhappy, back off
    } else {
      const body = await response.json();
      cursor = body.cursor;
      if (body.changes.length > 0) {
        apply(body.changes);
        interval = min;
      } else {
        interval = Math.min(max, interval * 1.5); // idle, slow down
      }
    }
    await new Promise((resolve) => setTimeout(resolve, interval));
  }
}

Operational realities

Every long-lived connection consumes a server file descriptor and a slot in your reverse proxy's worker pool, so ten thousand idle sockets is a capacity decision, not a free upgrade. Sticky sessions, graceful restarts and horizontal scaling all interact badly with long connections: a deploy drains and closes every socket, and each client must reconnect with jitter to avoid a synchronised stampede against the new instances. Load balancers must be configured with read timeouts above your heartbeat interval, and a CDN in front of a streaming endpoint needs explicit buffering disabled.

Whatever you choose, put it behind one interface in the client — subscribe(topic, handler) — so the transport is an implementation detail. Swapping SSE for WebSocket later should be a change inside that module, not a change in every component that listens for updates.

17.1 Canvas 2D and requestAnimationFrame

Canvas is an immediate-mode drawing surface: you issue draw calls and the pixels persist until you draw over them. It is the right tool for charts, games, image editing and any visual that DOM elements cannot express.

The drawing model and the device pixel ratio trap

A canvas has two sizes. Its CSS size is the layout box, and its width and height attributes are the backing store. If the two disagree, the browser scales the bitmap and everything is blurry on a high-density display. The fix is to set the attributes to the CSS size multiplied by devicePixelRatio, then scale the context by the same factor so your drawing code can keep using CSS units. Re-read the ratio on every resize, because dragging a window between monitors changes it.

function fitCanvas(canvas) {
  const ratio = window.devicePixelRatio || 1;
  const rect = canvas.getBoundingClientRect();
  canvas.width = Math.round(rect.width * ratio);
  canvas.height = Math.round(rect.height * ratio);
  const ctx = canvas.getContext('2d');
  ctx.setTransform(ratio, 0, 0, ratio, 0, 0); // draw in CSS pixels
  return ctx;
}

const ctx = fitCanvas(document.querySelector('#chart'));
ctx.fillStyle = '#03122f';
ctx.fillRect(0, 0, 300, 160);
ctx.strokeStyle = '#00d1ff';
ctx.lineWidth = 2;
ctx.beginPath();
ctx.moveTo(0, 120);
ctx.lineTo(150, 40);
ctx.lineTo(300, 90);
ctx.stroke();

The animation loop

requestAnimationFrame schedules a callback before the next paint and passes a high-resolution timestamp. It pauses when the tab is hidden, which is a feature: a background animation costs nothing. Never animate with setInterval, and never use the timestamp as a delta without clamping it — a tab that was hidden for a minute resumes with a delta of 60,000 ms, and any physics stepping that far will teleport everything off screen. Always clear the frame first, draw from state, and keep the state update independent of the frame rate by multiplying by an elapsed-time factor.

const state = { x: 20, y: 80, vx: 90, last: 0 };

function frame(now) {
  const dt = state.last ? Math.min((now - state.last) / 1000, 0.05) : 0;
  state.last = now;

  state.x += state.vx * dt;
  if (state.x > 300 || state.x < 10) state.vx *= -1;

  ctx.clearRect(0, 0, 320, 200);
  ctx.fillStyle = '#00d1ff';
  ctx.beginPath();
  ctx.arc(state.x, state.y, 10, 0, Math.PI * 2);
  ctx.fill();

  requestAnimationFrame(frame);
}

requestAnimationFrame(frame);
Reading a layout value such as getBoundingClientRect between draw calls forces a synchronous reflow and can cut the frame rate in half. Read all geometry once per frame, before drawing anything, and write to the DOM only outside the loop.

Beyond pixels: transforms, filters and the offscreen path

The 2D context exposes save and restore around transform stacks, which is how you draw a rotated object without recomputing every coordinate. setTransform with a matrix handles scale and translate together; globalCompositeOperation gives you blend modes; ctx.filter accepts CSS filter syntax for blur and saturation. For heavy scenes, an OffscreenCanvas transferred to a worker keeps the main thread free, and an ImageBitmap decoded off-thread with createImageBitmap avoids the main-thread decode cost of new Image().

const bitmap = await createImageBitmap(file); // decoded off the main thread
const off = document.createElement('canvas');
off.width = bitmap.width;
off.height = bitmap.height;
off.getContext('2d').drawImage(bitmap, 0, 0);

const offscreen = off.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]);

17.2 Web Audio

Web Audio is a graph of nodes processed by the audio thread. You connect sources to effects to a destination, schedule events against a sample clock, and the browser handles the timing.

Graphs, nodes and the audio clock

An AudioContext is the container. Sources include OscillatorNode, AudioBufferSourceNode for decoded samples, MediaElementAudioSourceNode for a video or audio element, and MediaStreamAudioSourceNode for a microphone. Effects include GainNode, BiquadFilterNode, DelayNode, ConvolverNode and DynamicsCompressorNode. Everything ends at context.destination, or at a MediaStreamAudioDestinationNode when you want to send the result elsewhere.

The reason not to use it as a glorified audio element is the scheduling model. Every automation call takes a time in context.currentTime, a monotonically increasing value in seconds, which lets you schedule a note or a fade to land on an exact sample rather than "as soon as the main thread gets around to it". That precision is what makes Web Audio usable for music, games and metronomes; it is useless for anything that must be triggered by a DOM event with jitter.

// A short percussive blip with an exponential decay envelope.
function blip(context, frequency = 440, when = context.currentTime) {
  const osc = context.createOscillator();
  const gain = context.createGain();

  osc.type = 'triangle';
  osc.frequency.setValueAtTime(frequency, when);

  gain.gain.setValueAtTime(0.0001, when);
  gain.gain.exponentialRampToValueAtTime(0.4, when + 0.01);
  gain.gain.exponentialRampToValueAtTime(0.0001, when + 0.3);

  osc.connect(gain).connect(context.destination);
  osc.start(when);
  osc.stop(when + 0.32);
}

const context = new AudioContext();
blip(context, 660);
blip(context, 990, context.currentTime + 0.15);

Autoplay policy and user-gesture unlocking

An AudioContext created without a user gesture starts suspended, and resuming it later requires a gesture too. The reliable pattern is to create the context lazily on the first click or keypress, call resume(), and check context.state before assuming sound will play. Any audio graph built before the gesture still works, it is simply silent until resumed — which produces the classic bug where a game is mute for its first minute with no error anywhere.

let context = null;

async function unlockAudio() {
  if (!context) context = new AudioContext();
  if (context.state === 'suspended') await context.resume();
  console.log('audio state:', context.state);
  return context;
}

document.addEventListener('pointerdown', unlockAudio, { once: true });

// Decoding a file into a reusable buffer, once.
async function loadSample(url) {
  const bytes = await (await fetch(url)).arrayBuffer();
  return context.decodeAudioData(bytes); // context must exist and be unlocked
}
A GainNode between the graph and the destination is the standard master volume: automate its gain for fades, and ramp rather than assign to avoid clicks. An abrupt gain change from 0.8 to 0 is a step discontinuity and is audible as a pop.

17.3 File and Clipboard APIs

Reading a file the user picked, dragging one in, and putting something on the clipboard are three small APIs that most apps need and most implementations get subtly wrong.

Reading a picked file

An <input type="file"> gives you a FileList of File objects, which are Blobs with a name and a last-modified date. They can be read with text(), arrayBuffer() or stream(), and the stream form is what allows progressive parsing of a multi-gigabyte file without holding it in memory. A File from an input has no real path: browsers deliberately hide it, so anything that needs a path must go through a picker API and a handle instead.

Drag and drop is the second entry point. A drop target must call preventDefault on both dragover and drop, or the browser navigates away from your app and opens the file. The drop event carries dataTransfer.files for real files and dataTransfer.items when you want directory entries; getAsFileSystemHandle is the modern path that also works for folders.

// Streaming read: constant memory, even for a huge file.
async function parseLargeTsv(file) {
  const reader = file.stream().getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop(); // keep the incomplete tail
    for (const line of lines) handleRow(line.split('\t'));
  }
}

dropZone.addEventListener('dragover', (event) => event.preventDefault());
dropZone.addEventListener('drop', async (event) => {
  event.preventDefault(); // without this the browser opens the file
  for (const file of event.dataTransfer.files) {
    await parseLargeTsv(file);
  }
});

Clipboard: permission, focus and formats

The async Clipboard API is restricted to secure contexts and requires the document to be focused and usually a transient user activation. writeText and readText are widely supported; rich formats go through ClipboardItem with a map of MIME types to blobs, and only a few types are permitted. Reading the clipboard is much more restricted than writing it, because clipboard contents are frequently sensitive: Safari prompts, Firefox has limited support for images, and any of these can fail for reasons a web page cannot see.

// Write plain and rich text together, so the target picks the best it understands.
async function copyResult(markdown, html) {
  try {
    const item = new ClipboardItem({
      'text/plain': new Blob([markdown], { type: 'text/plain' }),
      'text/html': new Blob([html], { type: 'text/html' })
    });
    await navigator.clipboard.write([item]);
    return true;
  } catch (err) {
    // Fall back to the legacy selection trick for older engines.
    console.warn('clipboard write failed', err.name);
    return false;
  }
}

document.querySelector('#copy').addEventListener('click', () => {
  copyResult('# Title', '<h1>Title</h1>');
});
Never read the clipboard on load, and never write to it without the user asking. Both are privacy-sensitive and both fail without a user gesture in current browsers, so a "copy to clipboard" button that works when clicked will silently do nothing if it is triggered from a timer.

Persistent handles and download links

showOpenFilePicker and showSaveFilePicker return a FileSystemFileHandle that can be retained across sessions in IndexedDB and re-authorised with requestPermission(), which is how a web editor offers "reopen my project". For the write-back case that does not need a handle, URL.createObjectURL(blob) on an anchor's href with a download attribute triggers a save without any server round trip. Revoke the object URL when you are done, or the blob stays alive for the lifetime of the document.

17.4 IntersectionObserver, MutationObserver, ResizeObserver

These three APIs replace the classic loops — scroll handlers, polling for element changes and window resize listeners — with asynchronous callbacks that the browser schedules efficiently and off the critical path.

IntersectionObserver: visibility without scroll math

An observer watches an element against a root, by default the viewport, and reports when the intersection crosses a threshold. The callback fires asynchronously after layout, gives you the ratio and the bounding rectangles, and never runs on the scroll thread. That is what makes lazy-loading images, infinite-scroll sentinels, sticky header detection and impression tracking cheap instead of janky. rootMargin lets you preload before an element is truly visible, which is how a gallery starts fetching one screenful early.

The canonical use is an image whose real source lives in data-src. Swap it on first intersection, then unobserve, because a one-shot observation costs nothing after it has fired. For a continuously tracked element, keep observing and read isIntersecting each time.

const lazy = new IntersectionObserver((entries, observer) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    const img = entry.target;
    img.src = img.dataset.src;
    img.removeAttribute('data-src');
    observer.unobserve(img); // one shot
  }
}, { rootMargin: '600px 0px', threshold: 0.01 });

document.querySelectorAll('img[data-src]').forEach((img) => lazy.observe(img));

// A sentinel at the bottom of a list, for infinite scroll.
const sentinel = new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting) loadNextPage();
}, { root: null, threshold: 0 });
sentinel.observe(document.querySelector('#end-of-list'));

ResizeObserver and MutationObserver

ResizeObserver reports an element's content box changing, including changes caused by its parent rather than the viewport — the case a window resize listener cannot see, such as a sidebar being collapsed by a sibling. Callbacks run before paint, so writing layout-affecting styles inside one can trigger the "ResizeObserver loop completed with undelivered notifications" error; schedule the write in requestAnimationFrame instead.

MutationObserver batches DOM changes into records with childList, attributes and characterData flags, and delivers them as a microtask. It is the correct replacement for polling for third-party widgets and for detecting content injected by an extension, but it is not a rendering hook and it will happily fire thousands of times for a chatty framework. Filter with attributeFilter and subtree and disconnect when you no longer need it.

const sizeWatch = new ResizeObserver((entries) => {
  for (const entry of entries) {
    const width = entry.contentRect.width;
    requestAnimationFrame(() => layoutChart(width)); // never write layout here directly
  }
});
sizeWatch.observe(document.querySelector('#panel'));

const domWatch = new MutationObserver((records) => {
  for (const record of records) {
    if (record.type === 'attributes' && record.attributeName === 'class') {
      syncThemeFrom(record.target);
    }
  }
});
domWatch.observe(document.body, {
  attributes: true,
  attributeFilter: ['class'],
  subtree: true
});
All three observers deliver an array of entries, not a single element, and several records can arrive in one batch. Iterate the array every time; code that reads only entries[0] works in testing and drops updates under load.

17.5 Geolocation, Notifications, Performance and Page Visibility

The remaining platform APIs share a theme: they are permission-gated, they can fail for reasons the page cannot observe, and each has a legitimate reason to be denied. Handle the failure path first.

Geolocation, notifications and their permission model

navigator.geolocation.getCurrentPosition is one-shot and watchPosition streams updates until you clear the watch id; both take a success callback, an error callback and options for accuracy and timeout. The error code distinguishes a denied permission from a position the device simply could not fix, so the two must be handled differently — retrying a denied request annoys the user without ever succeeding. Always pass a timeout and maximumAge, because without them a request can hang indefinitely on a desktop with no GPS and no network location service.

Notification.requestPermission() must be called from a user gesture in current browsers, and once denied it cannot be requested again — the origin has to be changed. That makes the decision to prompt effectively permanent, so prompt at a moment of clear value rather than on first load. As a complement, the Permissions API reports state through navigator.permissions.query({ name: 'geolocation' }) so you can adapt the UI without triggering a request.

function locate({ timeout = 8000, highAccuracy = false } = {}) {
  return new Promise((resolve, reject) => {
    if (!navigator.geolocation) return reject(new Error('unsupported'));
    navigator.geolocation.getCurrentPosition(
      (pos) => resolve({ lat: pos.coords.latitude, lon: pos.coords.longitude, acc: pos.coords.accuracy }),
      (err) => reject(new Error(err.code === 1 ? 'denied' : 'unavailable')),
      { enableHighAccuracy: highAccuracy, timeout, maximumAge: 30000 }
    );
  });
}

locate().then(showOnMap).catch((err) => {
  if (err.message === 'denied') showManualEntry();
});

Performance measurement and page visibility

The Performance API is how you find out what the user actually experienced. performance.now() gives a monotonic clock for spans; performance.mark and measure record them for devtools; PerformanceObserver reports largest-contentful-paint, layout-shift, longtask and navigation timing as they happen, which is the only way to observe field data rather than a lab run. The most useful entry for real apps is longtask: any task over 50 ms is visible to the user as input latency, and its attribution points at the script that caused it.

document.visibilityState tells you whether the tab is visible, and visibilitychange is the hook that should drive nearly every background behaviour: pause animations and game loops, stop polling and timers, flush a pending autosave, and resume with a fresh connection instead of trusting a socket that has been idle. The pagehide and pageshow events cover the back-forward cache, where a page is frozen rather than unloaded and unload may never fire.

// Field measurement for the two metrics users feel most.
new PerformanceObserver((list) => {
  const last = list.getEntries().at(-1);
  report('lcp', Math.round(last.startTime));
}).observe({ type: 'largest-contentful-paint', buffered: true });

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report('longtask', { ms: Math.round(entry.duration), name: entry.name });
  }
}).observe({ type: 'longtask', buffered: true });

// One hook to pause and resume everything background-related.
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    pauseLoops();
    flushAutosave();
    socket.close();
  } else {
    resumeLoops();
    socket.reconnectNow();
  }
});
Measurement must never itself be the bottleneck: a performance reporter that sends an HTTP request per entry produces more long tasks than it finds. Batch entries and flush on visibilitychange, when the page is going away anyway and the work cannot hurt the frame rate.
