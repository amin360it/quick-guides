Orientation — Scope, Model and Conventions

Orientation.1 Scope and version pinningOrientation.2 The deployment modelOrientation.3 Core concepts and object modelOrientation.4 Limits by planOrientation.5 Pricing mechanicsOrientation.6 Documentation conventions

This guide documents Vercel as a deployment platform rather than as a tutorial for a first deployment. It fixes the versions of the frameworks and runtimes it describes, states the limits and costs that change per plan, and describes failure modes precisely, because those are the details that determine whether a production system behaves as designed. Where Vercel changes behaviour without notice, the guide says so and names the surface to read.

Orientation.1 Scope and version pinning

Establishes which framework versions, runtimes and platform behaviours this document describes and where to verify anything that has since changed.

The framework surface Vercel supports is versioned against the frameworks, not against Vercel. This guide describes Next.js 16 with the App Router, Vite 7, Astro 6, Nuxt 4, React Router 7 in framework mode, SvelteKit 2 with the adapter-auto or adapter-vercel output, and Node.js 24 as the current Node LTS line. Where a framework changed a build-output contract — SvelteKit moved from a server directory to adapter output, Astro moved to static-first with per-route prerender flags, Nuxt moved its default output to the Nitro preset — those changes are stated explicitly, because they alter what outputDirectory and buildCommand must contain.

Vercel itself is a moving target. There is no single versioned API surface; the platform ships continuous changes and the product is described by its own documentation. Treat any specific number in this guide as pinned to the state of the platform as of 2026 and verify before relying on it. The two authoritative sources are the Limits page under Platform Documentation, which tabulates every limit by plan, and the Functions Limits and Build Steps pages, which are generated from the same internal configuration the runtime uses.

Where to read current values. Limits are not published as an API. Read vercel.com/docs/limits for the plan matrix, vercel.com/docs/functions/limitations for runtime ceilings, and the pricing page for the per-plan allowance figures. Do not treat third-party summaries, including this guide, as authoritative for anything that would fail a load test.

Two further conventions. First, this guide describes the platform behaviour of a project with a vercel.json present and the behaviour of a project without one, because the difference is the single most common source of production incidents. Second, all limits are quoted per plan — Hobby, Pro, Enterprise — since Hobby is not a production tier and several limits are structurally absent there rather than merely lower.

Orientation.2 The deployment model

Explains the build-and-serve separation, why the same repository produces different artefacts per target, and what a deployment actually is.

Vercel separates build from serve. The build phase runs in a Linux container, inside a Vercel-provided Build Image pinned to a dated release. The build phase has no access to production data stores, no long-lived filesystem, and a wall-clock ceiling. What it produces — a set of static files, a serverless function bundle, or both — is uploaded to the edge storage layer. The serve phase is a globally distributed request router with a CDN in front of it. Nothing from the build container survives into the request path.

That separation is why a successful build followed by 404s is a normal and predictable outcome rather than a contradiction. A build that writes to the wrong directory exits zero. Vercel uploads whatever is in the configured outputDirectory. If that directory does not contain the index document, the CDN has nothing to serve and returns 404 for every path. The build log is green. This is the single most important mental model in the platform: a green build asserts that a command succeeded, not that an artefact exists at the path the router will read.

A deployment is the immutable pair of artefacts plus the configuration snapshot taken at build time. It receives a unique, non-deterministic URL such as https://my-app-git-feature-x-user.vercel.app. Production traffic moves by promoting a deployment’s immutable hash to the production alias — an atomic pointer change, not a copy. Rollback is the reverse pointer change and takes effect in the same order of magnitude as a cache purge, which is single-digit seconds for the routing layer and longer for browser caches you do not control.

Reproduce locally. npx vercel build plus npx vercel dev runs the same build container logic against the local project and serves the produced output. It is not a full emulator — it does not reproduce Fluid Compute concurrency behaviour or the edge cache — but it does reproduce output-directory mistakes, which is the failure you will actually hit.

Orientation.3 Core concepts and object model

Defines Project, Deployment, Domain, Environment, Team, Git repository connection, Build and the alias graph, and states which are mutable and which are immutable.

The object graph is small and worth fixing in memory because configuration errors usually trace back to picking the wrong level of it. A Team or Personal Account owns Projects and holds Domains and Integration credentials. A Project has one Git repository connection, any number of branches mapped to environments, and a set of Deployments. A Deployment is immutable once created and has exactly one alias set: preview aliases, the production alias, and custom-domain aliases.

Environments are the most misunderstood object. There are three named targets — production, preview and development — and each is a separate environment variable scope with separate settings and separate a non-production or production protection policy. A preview deployment reads the preview scope, never production. Deployment protection is attached to the environment, not to the domain, which is why a preview alias can be password-protected while a production alias on the same project is not.

Aliases are mutable pointers to immutable deployments, and a single deployment can hold several aliases simultaneously — that is exactly how a custom domain can serve a production deployment while also being pointed at a preview for a staged rollout.

Values below the ceiling are not free. A maxDuration is the runtime’s patience, not your budget. A function that reliably runs 280 s on Pro consumes concurrency and invocation time for 280 s, and a single long request pins a Fluid Compute instance for that whole window. Set maxDuration to the p99 of real behaviour plus headroom, not to the maximum the plan allows.

Orientation.5 Pricing mechanics

Explains the four billable dimensions, why bandwidth egress dominates real invoices, and how the included allowances interact with overage.

Vercel bills on four independent dimensions: build minutes, function invocations, function execution time and bandwidth egress. On top of those sit metered products — Postgres compute and storage, KV operations, Blob storage and egress, Fluid Compute provisioned concurrency, WAF and Firewall Rules, and Observability retention — which are billed separately from the platform allowance.

The platform plan bundles a small allowance of each dimension. The allowance is a monthly reset, not a rollover, and once exceeded, usage is billed at the plan’s per-unit rate. On Hobby the platform allowance exists but commercial use is prohibited, and concurrent build capacity is 1, which alone disqualifies the plan for a team.

# Billable dimensions, in the order they usually surprise people:
#  1. Bandwidth egress        — usually the largest line item
#  2. Function execution time — scales with duration, not just count
#  3. Fluid provisioned conc. — billed as provisioned capacity
#  4. Build minutes            — cheapest, but multiplied by PR churn

Two cost mechanics deserve emphasis. First, egress is metered at the CDN on the bytes actually served, so an unoptimised image route, an un-cached API response returning large JSON, or a websocket reconnect storm will dominate an invoice while the invocation count looks trivial. Second, because a request that is aborted mid-flight has already consumed execution time and its function has already been invoked, a client-side retry storm amplifies cost multiplicatively without a corresponding increase in successful work.

Watch the multiplier, not the total. Execution-time cost is memory × duration × invocations. A route that allocates 2 GB of memory to shave 200 ms is frequently a net loss. Set memory to what the runtime profiling shows, and use --cpu-boost only for genuinely CPU-bound short tasks.

Orientation.6 Documentation conventions

Fixes notation for version pinning, plan-conditional statements, config precedence and the way escape hatches are described throughout the guide.

Throughout, plan-conditional behaviour is stated as a table rather than a sentence, because a sentence tends to be misremembered as universal. Configuration precedence is always given in the order the platform applies it, and when two sources conflict the guide names the winner explicitly. An escape hatch is any mechanism that exits the managed path: a self-hosted runtime, a functions entry overriding a framework default, a custom build command that bypasses the framework preset, an external database reached over a public endpoint, or a vercel.json property that disables an optimisation.

Configuration sources in Vercel are, in increasing precedence: framework-preset defaults, then framework-native config files such as next.config.js or astro.config.mjs, then project settings in the dashboard, then vercel.json. This ordering surprises people because the dashboard sits above the framework file but below vercel.json — so a setting you can see and edit in the UI can still be silently overridden by a committed file. Chapter 1 develops this in full.

//  3. Project settings in dashboard

//  5. CLI flags                   (--prod, --target, --prebuilt)

Finally, a note on what this guide deliberately omits. It does not cover the legacy build system, the now v2 platform alias, or the deprecated runtime: experimental-edge key. It does not cover Deployment Environments (the per-branch environment feature) except where it changes scoping semantics, and it does not treat Fluid concurrency autoscaling as a substitute for capacity planning. Where a feature is on a deprecation path, the guide says so in the relevant callout and gives the migration target.

1.1 Projects and Git integration

Defines the project object, how a Git repository is connected, and the two distinct paths by which a deployment is created.

A Project binds a Git repository, a build configuration, three environment scopes and a set of deployments. A project is created either by importing a repository through the Git provider integration or by running vercel in a local directory and linking it with vercel link. A project is scoped to a team: creating a project with the same name under a different team yields an entirely separate object with its own domains, environment variables and deployment history.

There are two deployment paths and they are not equivalent. A Git push creates a deployment through the integration, which reads the repository, the configured branch mapping and the environment scopes from the dashboard, then runs the build in Vercel-managed infrastructure. A CLI deploy uploads local files and runs a build from those files. The consequences are concrete: a Git deploy can reach private package registries and Git submodules through the provider’s token, can set commit metadata as build environment variables, and can trigger automatic deploys; a CLI deploy uploads only what the local filesystem contains, so a file you forgot to commit or gitignore is simply absent, and the commit SHA variables will describe whatever the local branch pointed at, which may be nothing.

// Git push path — the integration owns branch → environment mapping.
$ git push origin feature/checkout-v2
# GitHub → Vercel webhook → build → deployment
# All other branches: preview. main: production (if mapped).

// CLI path — you own what is uploaded.
$ npx vercel link
  ↳ Linking to project storefront under my-org  (scope: my-org)
  ↳ No Project Settings found locally. Run `vercel pull` first.
$ npx vercel pull --yes --environment=production
  Downloading `production` settings  [====================]  done
  ✔ Created .vercel/project.json
$ npx vercel deploy --prod --yes
  Running "installCommand" (npm ci)
  Running "buildCommand" (npm run build)
  Running "build" (next build)
  ✔ Compiled in 38.9s
  Vercel CLI 48.2.1
  Deploying storefront-7Qf2mKp9xT…
  ✔ Production: https://storefront-abc123-user.vercel.app  [dpl_7Qf2mKp9xT]
  ✔ Aliased:    https://storefront.example.com

Running vercel pull before a CLI deploy is not optional. It writes .vercel/project.json and, for a linked project, the resolved project settings you want to preview. Without it, the CLI creates a new project rather than deploying to the existing one, and the deployment lands in a project with no domains and no environment variables.

1.2 The build pipeline and vercel.json

Specifies each build phase, the properties that control it, the precedence order that resolves conflicts, and why a wrong output directory yields a green build and a 404.

The build pipeline has up to four phases: install (installCommand), pre-build (buildCommand when it differs from the framework default), build (the framework build), and post-build. Additional files can be injected with build.env for build-time-only variables and includeFiles/excludeFiles for lambda bundling, which are not the same mechanism as build input filtering.

Framework auto-detection runs first. If vercel.json omits framework, Vercel inspects the dependency manifest and lockfile and matches a preset — package.json dependencies plus the presence of next.config.*, vite.config.*, astro.config.*, nuxt.config.* and so on. Detection sets defaults for buildCommand, outputDirectory, installCommand and the function bundler. A monorepo with several framework packages, or a repository whose root has a vite.config.ts only for tooling, is where detection goes wrong.

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "vite",
  "installCommand": "npm ci",
  "buildCommand": "npm run build:web",
  "outputDirectory": "apps/web/dist",
  "build": {
    "env": {
      "NEXT_TELEMETRY_DISABLED": "1",
      "VITE_API_ORIGIN": "https://api.example.com"
    }
  },
  "functions": {
    "api/**/*.ts": {
      "runtime": "nodejs24.x",
      "memory": 1024,
      "maxDuration": 30
    }
  },
  "regions": ["iad1", "fra1"],
  "cleanUrls": true,
  "trailingSlash": false
}

Precedence, lowest to highest: framework preset defaults; framework-native config (next.config.js, astro.config.mjs, nuxt.config.ts); project settings in the dashboard; vercel.json; CLI flags. A practical consequence is that editing the build command in the dashboard is a fragile way to configure a repository, because the first person to commit a vercel.json with a buildCommand key silently overrides the dashboard and the change is invisible in the UI.

// Next.js 16 — framework-native config. `output` is the decisive key.
// "standalone" is required for a custom server; the preset ignores it.
// next.config.mjs
import { defineConfig } from 'next/config';

export default defineConfig({
  output: 'standalone',
  outputFileTracingIncludes: {
    '/api/**/*': ['./node_modules/sharp/**/*']
  },
  experimental: {
    ppr: true,          // partial prerendering
    staleTimes: { dynamic: 30, static: 1800 }
  },
  async headers() {
    return [{
      source: '/:path*',
      headers: [{ key: 'X-Frame-Options', value: 'DENY' }]
    }];
  }
});

The outputDirectory failure mode deserves an explicit description because the diagnostic is counter-intuitive. Vercel uploads the contents of outputDirectory to the CDN and registers the function entries it finds. If the directory is wrong, the upload is of the wrong files — a directory that exists but is empty, or one containing only source maps. The build command exited zero, so the build step is recorded as successful, the deployment is created, the alias is assigned. Only when a request arrives does the router find no matching static asset and no matching function, and return its 404 template. There is no build error to grep for.

Diagnose by inspecting the upload, not the log. When a green build 404s, read the deployment’s file list in the dashboard or run vercel inspect <deployment-url> --logs and look for the uploaded path list. Compare it against what the framework’s build log printed as its output directory. For Vite the expected value is dist; for Astro with output: "static" it is dist and for output: "server" it is dist/server with the function alongside; for Nuxt 4 with the Nitro preset it is .output/public; for a SvelteKit adapter-vercel build it is .vercel/output/static. A relative path in outputDirectory is resolved against the Root Directory, not the repository root — a monorepo mistake that produces exactly this symptom.

# Astro 6 — output mode changes the contract.
# astro.config.mjs
import { defineConfig } from 'astro/config';
import vercel from '@astrojs/vercel';

export default defineConfig({
  output: 'static',                       // or 'server'
  adapter: vercel({ webAnalytics: { enabled: false } }),
  build: { format: 'directory' },
  prefetch: { prefetchAll: true }
});

// vercel.json for Astro — Root Directory is the Astro project.
{ "framework": "astro", "outputDirectory": "dist" }

// Nuxt 4 — Nitro produces .output/public plus a server entry.
// nuxt.config.ts
export default defineNuxtConfig({
  compatibilityDate: '2026-01-15',
  nitro: { preset: 'vercel' },
  routeRules: {
    '/':            { prerender: true },
    '/blog/**':     { swr: 600 },
    '/api/**':      { cors: true, headers: { 'x-robots-tag': 'noindex' } }
  }
});

1.3 Monorepos and Root Directory

Explains Root Directory scoping, the project-per-package deployment model, include/exclude build filters, and the orchestration problem this creates for cross-package changes.

rootDirectory is a project setting, stored in .vercel/project.json for CLI projects and in the dashboard for Git projects, that scopes the build to a subdirectory of the repository. It affects path resolution for buildCommand, outputDirectory and every functions glob. It is not a working-directory change for the whole repository — files outside the root are still available on the build container’s filesystem, but the build command executes with the root as its base.

The common monorepo shapes are: one project per package with a root directory each, which gives independent previews and independent environment scopes; one project for the whole monorepo with a build command that produces a single artefact; and a hybrid where a shared library is built once and consumed by several projects, which requires a build order guarantee that a parallel CI scheduler will not provide for free.

├── packages/
│   ├── ui/           ← built by its consumers, not deployed alone
│   └── sdk/          ← built by its consumers

├── turbo.json
└── pnpm-workspace.yaml

1.4 .vercelignore and build inputs

Distinguishes the four distinct filtering mechanisms, states which one controls the build context, and gives the patterns that reliably exclude large or sensitive trees.

Four separate mechanisms reduce what the build sees, and confusing them causes both wasted build minutes and accidental exposure. .vercelignore at the repository root controls the build input — the files uploaded for a CLI deploy and the files present in the Git build context. .gitignore also matters, because the Git path clones the repository and then applies the ignore logic. excludeFiles in a functions entry prunes the function bundle. skipLibCheck and bundler tree-shaking affect module inclusion, not files.

1.5 Build caching and cache keys

Describes what is cached across builds, how the cache key is derived, how to read cache status from logs, and the trade-offs of turning the cache off.

The build cache covers three things: the package manager’s download store, the framework build cache, and the general dependency cache. The cache key is derived from more than the lockfile — it incorporates the Root Directory, the Node version, the runtime configuration, the environment scope and the build command. A change to any of those produces a cache miss, which is why a maxDuration bump can cost every project a full cold build.

Cache status is reported per build in the logs. Cache Hit, Cache Miss, Cache Skipped and Cache Invalidation are distinct states, and they mean different things: skipped usually indicates a configuration that opted out, invalidation indicates a declared cache scope that changed. The distinction matters when diagnosing a build that got slower, because a skip and a miss have the same wall-clock effect and different causes.

1.6 Preview deployments and pull requests

Defines preview deployment generation, per-branch and per-commit controls, data isolation, and the cost and hygiene implications of an unbounded preview policy.

A preview deployment is a full build and a full function bundle, served at a unique alias, with the preview environment scope. Every push to a non-production branch that has previews enabled produces one. There is no sampling, no automatic expiry and, by default, no cap. A repository with active long-lived branches therefore accumulates deployments and, more importantly, keeps them invocable — which is a security consideration before it is a cost consideration.

Controls are layered. Per-branch toggles enable or disable previews for named branches. Deploy hooks let an external system request a deployment, which is how you build the same commit twice with different environment variable sets. Git settings allow forking behaviour and commit-message control. Deployment protection gates access to the alias at the routing layer, and it is the only control that works when the environment variable scope is shared by hundreds of deployments.

// Namespacing by environment, enforced at the data layer.
const PREFIX = process.env.VERCEL_ENV === 'production' ? 'prod' : 'preview';

  const full = `${PREFIX}:${key}`;
  const hit = await redis.get(full);
  if (hit) return JSON.parse(hit) as T;
  const value = await fn();
  await redis.set(full, JSON.stringify(value), { EX: 300 });
  return value;
}

// POSTGRES_URL differs per scope; DATABASE_SCHEMA selects the schema.

This chapter describes the order in which Vercel resolves a request and where each configuration surface sits in that order. The central fact is that the filesystem is consulted before rewrites, which makes rewrites a fallback mechanism rather than an override, and which determines whether a rewrite can shadow a static file. 2.1 The routing pipeline

Orders the request resolution steps and names the configuration key that participates at each stage.

A request to a Vercel deployment is resolved in a fixed sequence. The platform matches the hostname to a domain and then an alias, which selects a deployment. It applies the redirect rules configured for that domain. It normalises the path according to cleanUrls and trailingSlash. It then checks the filesystem — static assets, prerendered HTML, and function routes — and only if nothing matches does it evaluate framework-level rewrites and then vercel.json rewrites. If still nothing matches, it falls through to a 404, which for a framework deployment is the framework’s own not-found route rather than a platform error page.

Headers are applied at the response stage, after the handler runs, and can be declared in three places: vercel.json headers, a framework’s native header configuration, and the handler itself. The three are additive, and the handler’s own setHeader wins for any key it sets itself, because it runs last.

       ─▶ 2. cleanUrls / trailingSlash normalisation
       ─▶ 3. FILESYSTEM CHECK
              ├─ static asset / prerendered HTML  → serve
              ├─ matching function route         → invoke

       ─▶ 4. rewrites[] (vercel.json)           → re-enter at step 3
       ─▶ 5. framework rewrites (next.config)  → re-enter at step 3
       ─▶ 6. platform 404

In SvelteKit, routing is entirely framework-owned; the rewrites array is the right tool for redirecting legacy paths into the app, not for adding application routes. 2.2 Rewrites and filesystem precedence

Documents the rewrites schema, explains precisely why a rewrite cannot shadow a static file, and gives the correct technique when a rewrite must take precedence.

A rewrite is an internal mapping applied when nothing else matched. It returns the target’s response under the original URL, without a redirect, and without the browser learning about the change. That is exactly what you want for a legacy path mapping to a new one and exactly what you do not want for security enforcement, because the URL in the address bar will not reflect the mapping.

Because the filesystem is checked first, a rewrite from /about to /pages/about is silently ignored if a file or prerendered route already exists at /about. The platform does not warn. The first rule of debugging a "broken rewrite" is to request the target path directly and confirm the source path does not resolve.

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    { "source": "/api/:path*",     "destination": "/backend/:path*" },
    { "source": "/docs/:slug",     "destination": "/kb/:slug" },
    { "source": "/old-blog/:p*",   "destination": "/blog/:p*" }
  ]
}
// Evaluated top to bottom, first match wins, and only after the
// filesystem has already failed to match. Ordering matters: a
// broad "/:path*" catch-all must be last.

To make a mapping take precedence over an existing file, you must remove the file or change the target. The practical patterns are: rename the file so nothing occupies the source path; use a redirect instead of a rewrite when you are willing to expose the new URL; or handle the collision inside the framework, where the route file itself owns the resolution. There is no force flag on a rewrite.

// next.config.mjs — framework rewrites live INSIDE the router and
// therefore DO beat the filesystem, because they define routes.
import { defineConfig } from 'next/config';

export default defineConfig({
  async rewrites() {
    return {
      beforeFiles: [
        { source: '/legacy/pricing', destination: '/pricing' }
      ],
      afterFiles: [
        { source: '/u/:handle', destination: '/profile/[handle]' }
      ],
      fallback: [
        { source: '/:path+/', destination: '/blog/:path+' }
      ]
    };
  }
});
// beforeFiles  → evaluated before the filesystem (can shadow)
// afterFiles   → evaluated after static + dynamic routes
// fallback     → evaluated last, when nothing else matched

Wildcard rewrites and cache keys. A catch-all rewrite like /:path* collapses many URLs onto one target. If the target is a dynamic function, every distinct source URL produces a separate cache entry unless you set an explicit Cache-Control, which is how a single high-traffic alias turns into an unbounded cache-key space and a large egress bill. Scope wildcards as narrowly as the routing model allows.

{
  "rewrites": [
    { "source": "/embed/:widget", "destination": "https://cdn.example.com/embed/:widget" }
  ],
  "headers": [
    {
      "source": "/embed/:path*",
      "headers": [
        { "key": "Cache-Control", "value": "public, s-maxage=3600, stale-while-revalidate=86400" },
        { "key": "X-Frame-Options", "value": "SAMEORIGIN" }
      ]
    }
  ]
}
// A rewrite to an absolute URL is a proxy, not a redirect: the
// response is served from Vercel's edge, and egress is billed.

Prefer the framework’s own phase control. When the routing question is "should this beat the file system", you are asking a beforeFiles question in Next.js, a middleware matcher question in SvelteKit, and a middleware.ts matcher question in Nuxt. vercel.json rewrites are for the boundary — legacy hosts, vanity paths, mounts that predate the app — not for intra-app routing.

2.3 Redirects and status codes

Compares 307, 308, 302 and 301 for routing migrations, documents the permanent flag and status override, and covers the proxy pattern with its caching and header consequences.

Vercel emits 308 by default for redirects entries and 307 when permanent is false. Both preserve the request method and body, which is what an API route needs. A 301 or 302 is a browser-level redirect: browsers and many HTTP clients convert a POST to a GET and drop the body. Using 301 for an API migration silently converts writes into reads, and the symptom appears in the client logs as a 404 or 405 on a route that demonstrably exists.

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "redirects": [
    { "source": "/old-blog/:slug", "destination": "/blog/:slug", "permanent": true },
    { "source": "/api/v1/users",  "destination": "/api/v2/users",  "permanent": false },
    {
      "source": "/geo",
      "destination": "https://edge.example.com/geo",
      "status": 302
    },
    { "source": "/maintenance",   "destination": "/status",     "permanent": false }
  ]
}
// 308 + permanent:true  → cached indefinitely by browsers
// 307 + permanent:false → not cached, method preserved
// 302 + status          → method may downgrade to GET

A rewrite whose destination is an absolute external URL is a proxy: Vercel fetches the origin and returns the body, adding x-vercel-proxy and forwarding the original host in x-forwarded-host. Proxies are useful for consolidating origins under one hostname and for terminating TLS in one place, and they are expensive and easy to leak. The origin sees Vercel’s egress addresses unless you have configured the firewall, and every response passes through the metered bandwidth path even if the origin itself is free.

2.4 Headers and security policy

Documents the headers schema, header size limits, how to compute a strong Subresource Integrity hash, and how security headers interact with the image optimizer and the edge.

The headers array matches on source using path-to-regexp syntax with the same parameter tokens as rewrites. Matches are cumulative: a request to /assets/app.js that matches both /:path* and /assets/:path* receives both sets. When the same key appears twice, the last one wins, so ordering specific before general produces the specific value surviving.

There is a hard ceiling on total response header size — 16 KB on standard plans. Exceed it and the edge returns a 500 rather than truncating, which presents as an intermittent failure under load because short responses succeed and only responses carrying many cookies, many origins or a long CSP succeed. A Content-Security-Policy with four domains of script sources plus nonces plus a long report-to list is a realistic way to hit it.

{
  "headers": [
    {
      "source": "/:path*",
      "headers": [
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        { "key": "Permissions-Policy", "value": "camera=(), microphone=(), geolocation=()" },
        { "key": "Strict-Transport-Security", "value": "max-age=63072000; includeSubDomains; preload" }
      ]
    },
    {
      "source": "/assets/:path*",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" },
        { "key": "Cross-Origin-Resource-Policy", "value": "same-origin" }
      ]
    }
  ]
}
// "immutable" is correct only for content-hashed filenames.
// Next.js emits /_next/static/** with a content hash in the path.

Subresource Integrity requires computing a hash at build time, not at runtime. Vercel does not compute SRI for you; the value must be generated by the build and injected. The standard approach is a small post-build step that walks the output directory, hashes each file with the SRI algorithm, and writes a manifest the HTML or server template consumes. A CSP that uses 'strict-dynamic' with a per-request nonce is easier to deploy and stronger in practice than an SRI manifest, provided the nonce is generated in middleware where every response can carry it.

// next.config.mjs — nonce in middleware covers every dynamic response
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(req: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');
  const csp = [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`,
    "style-src 'self' 'unsafe-inline'",
    "img-src 'self' data: blob: https://images.example.com",
    "connect-src 'self'",
    "frame-ancestors 'none'",
    "upgrade-insecure-requests"
  ].join('; ');

  const res = NextResponse.next();
  res.headers.set('Content-Security-Policy', csp);
  res.headers.set('x-nonce', nonce);
  return res;
}

export const config = {
  matcher: [
    { source: '/((?!api/health|_next/static|_next/image|favicon.ico).*)',
      missing: [ { type: 'header', key: 'next-router-prefetch' } ] }
  ]
};

Never blanket-disable framing. X-Frame-Options: DENY on /:path* also blocks your own marketing site from embedding an interactive demo, and blocks OAuth providers that render inside a frame. Use frame-ancestors in CSP with an explicit allowlist, and set X-Frame-Options only on paths that must never be framed. The two coexist; the browser honours the more specific of the two in practice, which is another reason to keep the allowlist correct.

2.5 cleanUrls and trailingSlash

Explains the interaction between cleanUrls, trailingSlash and framework output format, and how mismatched settings produce redirect loops and cache fragmentation.

cleanUrls: true removes .html from static file extensions: /about.html is served at /about. trailingSlash controls whether directory paths carry a trailing slash. The two interact with the framework’s own output format, and Astro makes the interaction explicit with build.format set to file or directory.

Setting them in conflict with the framework produces a redirect on every request, and in the worst case a loop. If a framework emits /about/index.html and the platform is configured to prefer /about.html, the two normalise to the same resource by different rules and each canonicalises to the other. The symptom is a 310 or an infinite redirect reported by the browser, or — more quietly — two cache entries per page, halving your effective hit rate.

{
  "cleanUrls": true,
  "trailingSlash": false
}
// Canonical form: /about  →  200
// /about/               →  308 to /about
// /about.html           →  308 to /about

// astro.config.mjs must agree with the platform setting:
export default defineConfig({
  build: { format: 'file' },      // emits about.html, no dir index
  trailingSlash: 'never'
});

// Nuxt 4 / Nitro: the preset owns this.
export default defineNuxtConfig({
  nitro: { preset: 'vercel' },
  router: { options: { strict: true } }
});

Next.js declares its own trailing-slash policy in next.config.js and it is authoritative for Next.js routes; setting trailingSlash in vercel.json for a Next.js project mostly affects static files under public/. 2.6 Proxy and external routing

Covers external rewrites, multi-domain routing, path-to-domain mounts, the origin firewall consequence of proxying, and the practical reasons to accept or refuse a proxy.

Multiple domains on one project route independently to the same deployment, which is how a marketing site, an app and a legacy host can share one build. When they need to serve different content, a path-to-domain rewrite such as /app/:path* → https://app.example.com/:path* acts as a proxy for that subtree only, leaving the rest local. This is the standard consolidation pattern and it works well when the target is a fast origin and the subtree is not the bulk of your traffic.

Proxying has three costs that are not always obvious. The response traverses Vercel’s metered egress, so a proxied file store turns into a bill. The origin’s firewall must permit Vercel’s egress ranges, which is a standing operational dependency. And proxied responses are not cached by default in a way you control — you must set Cache-Control explicitly, and if you do, you have moved caching responsibility out of the origin and into a layer whose cache key you do not fully model.

Proxy and cache interact with stale-while-revalidate. If you cache a proxied response with s-maxage=300, stale-while-revalidate=86400, the origin can be unreachable for a day without user-visible failure, and a bad origin deploy can persist for the entire SWR window. During a migration, cap stale-while-revalidate at minutes and purge deliberately rather than inheriting a day-long tolerance by accident.

This chapter distinguishes the four rendering strategies available on the platform, gives the cache-key semantics for each, and is explicit about the costs. Two claims deserve emphasis before the detail: incremental regeneration across many distinct paths carries a per-revalidation cost proportional to path count, and the revalidate value is a path-level TTL applied to whatever is cached at that path — not a page-level switch that governs the whole route.

3.1 Static generation

Describes build-time prerendering, the constraints it imposes on data access, and the failure mode where a build-time fetch silently freezes a value.

Static generation runs at build time in the build container. The render function executes once per path, its output is written to the output directory, and the request path never executes application code. This gives the best cacheability, the lowest latency, zero function invocations, and a hard requirement: everything the page needs must be resolvable at build time, from either a committed data source, a build-time API call, or a value embedded at compile time.

The failure mode is silent. A page that reads new Date().toISOString() at module scope, or that fetches a value the build container’s egress policy silently returned an empty body for, prerenders successfully and serves a permanently stale value with no error anywhere. There is no runtime to throw in. The mitigation is to assert freshness externally: a synthetic check that compares a rendered timestamp against wall clock, and a build-time failure when a required upstream returns non-2xx.

// app/(marketing)/page.tsx — Next.js 16, statically prerendered
export const dynamic = 'force-static';
export const revalidate = false;      // never revalidate; serve from CDN

export default async function Home() {
  // Build-time only. If this throws, the BUILD fails — which is

  const res = await fetch('https://api.example.com/releases/latest', {

  if (!res.ok) {
    throw new Error(`upstream ${res.status} during prerender`);
  }
  const release = await res.json();

}

3.2 Incremental static regeneration

Defines revalidation as a path-level TTL, quantifies its cost on large path sets, and explains the staleness window honestly.

Incremental static regeneration caches a rendered page at the edge and regenerates it in the background when the entry is stale. Two distinct knobs exist and they are routinely confused. revalidate is a path-level TTL: it sets how long the cache entry at that path may be served before it is considered stale. It is not a page-level directive, it does not "refresh the page", and it does not guarantee the content is younger than the TTL — a regeneration that takes four minutes produces entries up to TTL plus four minutes old.

The second knob is on-demand revalidation, which purges a specific path or a tag from outside the request path. That is the mechanism to use when you know the moment something changed, and the TTL is the fallback for when you do not. Setting revalidate to a long value and relying only on the TTL is the wrong default for content that must be current; setting it to a short value on a large path set is the wrong default for content that is not.

// app/products/[slug]/page.tsx — path-level TTL
export const revalidate = 300;              // this path, 5 min
export const dynamicParams = true;           // generate unseen slugs

export default async function Product({ params }) {
  const { slug } = await params;
  const product = await fetch(`${process.env.API}/products/${slug}`, {
    next: { tags: [`product:${slug}`, 'catalog'], revalidate: 300 }
  });
  if (!product.ok) notFound();
  return <ProductView product={await product.json()} />;
}

// The same route with a per-tag freshness contract instead:
export const revalidate = 86400;             // long safety-net TTL
export async function generateStaticParams() {
  const rows = await db.product.findMany({ select: { slug: true }, take: 500 });
  return rows.map(({ slug }) => ({ slug }));
}

The cost statement needs precision. Every distinct cached path is a separate cache entry with its own revalidation event. On a catalogue of 50,000 product pages at a 300-second TTL, that is roughly 50,000 regenerations per 5 minutes, or about 167 per second spread across regions — each of which executes your render function, which means function invocations and execution time billed at the same rate as a live request. ISR is cheap when the path set is small and the TTL is long. It is not cheap when the path set is large and the TTL is short, and in that regime a static build with a webhook-driven rebuild is frequently cheaper.

Stale-while-revalidate can exceed your TTL by a wide margin. Cache-Control: s-maxage=60, stale-while-revalidate=86400 means the edge may serve content a full day old while regenerating. If the regeneration is failing, the platform will keep serving stale content rather than erroring, so an outage in your data source looks like "content is a bit old" rather than like an incident. Alert on regeneration errors, not on user-visible staleness.

3.3 Edge runtime rendering

Documents the Web API-based edge runtime, its genuine constraints, the TCP restriction that rules out most database drivers, and the honest assessment of when it is the right choice.

The edge runtime executes JavaScript in V8 isolates behind the CDN, using Web-standard APIs — fetch, Request, Response, Headers, URL, Web Streams, crypto, TextEncoder, and atob/btoa. It does not have Node built-in modules. There is no fs, no net, no child_process, and no raw TCP. This is not a policy restriction that can be relaxed; it follows from the runtime substrate.

The TCP restriction has a concrete consequence that decides architecture: most Postgres and MySQL drivers open a socket, so they do not work on the edge. HTTP-based clients work, which is why Prisma Accelerate, Neon over HTTP, PlanetScale’s HTTP interface, Upstash Redis and Vercel KV’s HTTP client are all edge-compatible while pg and mysql2 are not. A hand-written Postgres wire-protocol client over a raw socket is possible on some edge runtimes with TCP support and is not something to design a production system around.

// api/geo.ts — edge function, Vercel KV over HTTP
export const config = { runtime: 'edge' };

type GeoRow = { country: string; city: string | null };

export default async function handler(req: Request): Promise<Response> {
  const country =
    req.headers.get('x-vercel-ip-country') ??
    req.headers.get('x-vercel-ip-country-region') ??
    'XX';

  if (country === 'XX') {
    return new Response(JSON.stringify({ error: 'country unknown' }), {
      status: 400, headers: { 'content-type': 'application/json' }
    });
  }

  const res = await fetch(
    `https://kv.vercel-storage.com/v1/geo/${country}`,
    { headers: { authorization: `Bearer ${process.env.KV_REST_API_TOKEN}` } }
  );

  if (res.status === 404) {
    return Response.json({ country, city: null, source: 'default' });
  }
  if (!res.ok) {
    return Response.json({ error: 'lookup failed' }, { status: 502 });
  }

  const row = (await res.json()) as GeoRow;
  return Response.json(
    { ...row, source: 'kv' },
    { headers: { 'cache-control': 'public, s-maxage=86400, stale-while-revalidate=604800' } }
  );
}

Beyond the API surface, edge functions are limited in duration to a shorter ceiling than Fluid functions, and their memory is fixed rather than configurable, which means a large in-memory operation is not an option. The win is real for the workloads the model suits: geolocation and locale selection, A/B and feature-flag evaluation, token verification and rate limiting, response and request rewriting at the CDN layer, and small read-only lookups against an HTTP data store. For anything CPU-bound, anything using a native module, and anything that opens a connection, the Node runtime is the correct answer and pretending otherwise produces a rewrite.

// Edge + Vercel KV SDK — available, uses the HTTP transport
import { createClient } from '@vercel/kv';
import { jwtVerify } from 'jose';

                         token: process.env.KV_REST_API_TOKEN! });

  const token = req.headers.get('authorization')?.replace(/^Bearer /, '');
  if (!token) return new Response('missing token', { status: 401 });

  try {
    const { payload } = await jwtVerify(token, secret, { issuer: 'api.example.com' });
    const hits = await kv.incr(`rl:${payload.sub}`);
    if (hits === 1) await kv.expire(`rl:${payload.sub}`, 60);
    if (hits > 120) return new Response('rate limited', { status: 429 });
  } catch {
    return new Response('invalid token', { status: 401 });
  }

  const res = await fetch(req.url, { headers: { 'x-authenticated': '1' } });
  res.headers.set('x-cache-layer', 'edge');
  return res;
}

An edge function that needs a database will be rewritten. Adding a join, a transaction or a WHERE clause to an edge handler is the moment to move it to the Node runtime with a pooled connection. The migration is mechanical — the handler body is identical, the imports change — and doing it early costs an hour. Doing it after the data layer has been abstracted around HTTP primitives costs a week.

3.4 Fluid Compute rendering

Describes Fluid Compute’s instance-based concurrency model, what it changes about connection and cold-start behaviour, and how provisioned versus on-demand concurrency trade off latency against cost.

Fluid Compute replaces the older model in which each concurrent request received its own function instance with a model in which a bounded number of long-lived instances serve many concurrent requests. The older model scaled concurrency with traffic and had no floor; Fluid scales concurrency with traffic and has a configurable floor. The floor is the entire point: an instance that is already warm when a request arrives eliminates the cold start, and a set of already-connected instances eliminates the connection-storm problem.

Fluid is billed in two modes. On-demand bills execution time with no reserved capacity and is closest to the older economics. Provisioned concurrency reserves a number of instances that stay warm, billed as reserved capacity plus execution, and it is the mode that makes cold starts disappear. Provisioned concurrency is priced per instance-hour, so the decision is arithmetic: what is a cold start costing you in added latency and dropped requests, and what would the same traffic cost in reserved capacity.

A function that opens a database connection on each invocation, under the legacy model, opens one connection per concurrent request. 3.5 Cache keys and variants

Specifies what constitutes the cache key for each rendering strategy, how Vary interacts with the key, and how uncontrolled variation multiplies entries and cost.

For a static page, the cache key is the URL plus the deployment identity. Two deployments of the same URL are distinct entries, which is what makes atomic promotion and instant rollback correct. For ISR, the key is the URL plus the deployment, with the revalidate TTL and tag set as metadata controlling invalidation rather than key derivation. For edge and Fluid functions, the key is the URL plus the deployment plus every dimension named in the response’s Vary header.

This is where cost surprises originate. A handler that sets Vary: Accept-Encoding, Cookie on a response that does not actually depend on the cookie will create one cache entry per distinct cookie value in the wild, which is one per user, which is a cache hit rate of approximately zero and a memory footprint you cannot bound. Every Vary dimension multiplies the key space. The rule is to declare exactly the dimensions the response body depends on and no others.

// app/api/search/route.ts — deliberate, minimal Vary
export async function GET(req: Request) {
  const url = new URL(req.url);
  const q = url.searchParams.get('q') ?? '';

  // The body depends on the query string and on encoding only.
  // It does NOT depend on Cookie, even though the request has one.
  return NextResponse.json({ q, results: await search(q) }, {
    headers: {
      'cache-control': 'public, s-maxage=60, stale-while-revalidate=300',
      'vary': 'Accept-Encoding'
    }
  });
}

// For genuinely per-user content, do not use Vary: Cookie.
// Use a private response so it is never stored at the edge:
return NextResponse.json(await personalise(userId), {
  headers: { 'cache-control': 'private, no-store' }
});

Framework-level caching adds its own key dimensions. Next.js caches fetch results with a key derived from the URL, the method, the body, and the next-option configuration, and the framework adds framework headers to the Vary value for RSC payloads — RSC, Next-Router-State-Tree, Next-Router-Prefetch. That is correct behaviour and it multiplies entries by the number of navigation states, which is why router prefetching on a link-heavy page is a measurable cache and egress cost rather than a free optimisation.

3.6 Revalidation and tags

Distinguishes TTL expiry, tag purges, path purges and deployment promotion, gives the framework equivalents, and states the ordering guarantees you can rely on.

There are four ways a cache entry stops being served, and they have different latency and different guarantees. TTL expiry is probabilistic: the entry is served stale and regenerated in the background. A tag purge marks every entry carrying that tag stale immediately, with the same background regeneration — it is also not a synchronous read-your-writes operation. A path purge does the same for one path. Deployment promotion is the only one that is atomic and complete, because it changes the deployment component of the cache key for every path simultaneously.

That last point is the reason deploy-based invalidation is the safest strategy. If a content change ships through the same commit that changes the code, promotion invalidates everything at once and the question of tag hygiene never arises. Tag-based revalidation is the right tool for content that changes without a deploy, and it carries a discipline cost: a tag that is not attached to every entry that should be invalidated produces stale content that no amount of re-purging the correct tag will fix.

// app/api/webhooks/cms/route.ts — verified, then purge by tag
import { revalidateTag, revalidatePath } from 'next/cache';
import { createHmac, timingSafeEqual } from 'node:crypto';

export async function POST(req: Request) {
  const raw = await req.text();
  const sig = req.headers.get('x-cms-signature') ?? '';
  const expected = createHmac('sha256', process.env.CMS_WEBHOOK_SECRET!)
    .update(raw).digest('hex');
  if (sig.length !== expected.length ||
      !timingSafeEqual(Buffer.from(sig), Buffer.from(expected))) {
    return new Response('bad signature', { status: 401 });
  }

  const event = JSON.parse(raw) as { type: string; slug: string; id: string };
  switch (event.type) {
    case 'entry.publish':
      revalidateTag(`product:${event.slug}`, 'max');
      revalidateTag('catalog', 'max');
      return Response.json({ ok: true, purged: [`product:${event.slug}`, 'catalog'] });
    case 'entry.delete':
      revalidatePath(`/products/${event.slug}`);
      return Response.json({ ok: true, purged: [`/products/${event.slug}`] });
    default:
      return Response.json({ ok: true, ignored: event.type });
  }
}

Purge is not read-your-writes. After a purge returns, the next request still receives the stale body, because regeneration is asynchronous and the purge only marks the entry. If a user must see their own write immediately, do not route that read through a cached path — either bypass the cache for the mutation response, or include a client-side optimistic update and accept eventual consistency. Designing an admin workflow on the assumption that purge is synchronous is a reliable way to ship a confusing bug.

4.1 Function configuration

Documents the functions map, its glob resolution rules, the per-function keys, and the relationship between vercel.json and framework route config.

The functions key maps glob patterns to per-function configuration. Patterns are matched against the function’s path relative to the project root, and the first matching pattern wins, so ordering is significant and a specific pattern must precede a general one. The keys available are runtime, memory, maxDuration, includeFiles, excludeFiles, minify, bundle and, on some plans, cpu and architecture.

Only vercel.json configures the function’s execution environment. Framework route configuration — a Next.js route segment’s export const runtime, a SvelteKit export const config, a Nuxt route rule — configures framework behaviour and in some cases maps to the same underlying setting. Memory is the lever people under-use. Function execution cost is billed as a product of memory and duration, so doubling memory doubles the cost of the same work. 4.2 Runtimes and the runtime floor

Enumerates the available runtimes, explains how the default Node version is chosen and pinned, and documents the compatibility consequences of raising it.

Two runtimes cover effectively all production use: the Node runtime, pinned by a major version string such as nodejs24.x, and the edge runtime. Bun and Deno have been offered as runtimes on Vercel; treat their current availability and plan restrictions as items to verify on the runtimes page rather than assuming parity, because their feature coverage, particularly around native modules and the bundler, has not matched the Node runtime consistently.

The safe practice is to declare runtime explicitly on every function, to pin a major version rather than an exact one, and to set engines.node in package.json so the build container and the runtime agree. A mismatch between the Node version used to compile native modules at build time and the version used to run them produces an ABI error at first invocation, not at build time.

4.3 Timeouts and what happens at the ceiling

Gives the maxDuration ceiling by plan, describes the client’s experience at the limit, and explains why long-running work belongs in a queue.

maxDuration is the wall-clock ceiling for a single function invocation, enforced by the runtime. Its maximum is plan-dependent and is clamped rather than rejected when you configure a higher value — the build succeeds and the request dies at the clamped value, which is why a misconfiguration here presents as a runtime timeout rather than a build error.

At the ceiling the runtime terminates the invocation and the client receives a platform-generated error. With streaming already committed, the stream is closed mid-body, which the browser reports as a network error and the client library as an incomplete read. Without streaming, the response is a 504 or the platform’s equivalent, and any work already performed — a database write, a third-party call, a charged payment — is not rolled back. This is the single most important thing to understand about the ceiling: it is a resource limit, not a transaction boundary.

Long work does not belong in a function invocation regardless of how high the ceiling is. A four-minute job holds an instance for four minutes, consumes execution time proportional to memory, and fails irrecoverably if it exceeds the ceiling no matter how far along it was. The correct shape is: accept the request, validate, enqueue to a queue or a table with a status column, return 202 with an identifier, and process in a separate loop or worker triggered by a cron or a queue consumer. The user-visible contract becomes "poll this identifier", which is honest about the latency.

// api/export.ts — 202 immediately, work continues outside the request
import { db } from '@/lib/db';
import { enqueue } from '@/lib/queue';

export async function POST(req: Request) {
  const { dataset, format } = await req.json();
  const job = await db.exportJob.create({
    data: { dataset, format, status: 'queued', requestedBy: req.headers.get('x-user-id') }
  });

  await enqueue('export', { jobId: job.id });
  return Response.json(
    { jobId: job.id, status: job.status, poll: `/api/export/${job.id}` },
    { status: 202, headers: { 'location': `/api/export/${job.id}` } }
  );
}

// Poll endpoint — cached off, cheap, honest
export async function GET(_req: Request, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const job = await db.exportJob.findUnique({ where: { id } });
  if (!job) return Response.json({ error: 'not found' }, { status: 404 });
  return Response.json(
    { jobId: job.id, status: job.status, url: job.resultUrl ?? null },
    { headers: { 'cache-control': 'private, no-store' } }
  );
}

Timeout is not rollback. A handler that charges a card, writes a row and then blocks on a third-party call can be killed between the write and the call, leaving money taken and no order. Make each handler idempotent with a key, do the irreversible operation last, and record intent before performing it. Then a retry is safe and the timeout becomes a recoverable condition rather than a reconciliation problem.

// Idempotent by construction: intent first, effect second,
// and a unique constraint as the final arbiter.
import { PrismaClient } from '@prisma/client';
import { createHmac } from 'node:crypto';
const db = new PrismaClient();

export async function POST(req: Request) {
  const key = req.headers.get('idempotency-key');
  if (!key) return Response.json({ error: 'idempotency-key required' }, { status: 400 });

  const digest = createHmac('sha256', process.env.IDEMPOTENCY_SECRET!)
    .update(await req.text()).digest('hex');

  const existing = await db.idempotency.findUnique({ where: { key } });
  if (existing?.digest !== digest) {
    return Response.json({ error: 'key reused with different payload' }, { status: 409 });
  }
  if (existing) return Response.json(existing.response, { status: 200 });

  const order = await db.order.create({ data: { key, status: 'pending' } });
  try {
    await db.payment.charge({ orderId: order.id });
    await db.order.update({ where: { id: order.id }, data: { status: 'paid' } });
    const response = { orderId: order.id, status: 'paid' };
    await db.idempotency.update({ where: { key }, data: { response, digest } });
    return Response.json(response, { status: 201 });
  } catch (err) {
    await db.order.update({ where: { id: order.id }, data: { status: 'failed' } });
    throw err;   // retry is safe: the key is the guard
  }
}

4.4 Concurrency models

Contrasts per-request and Fluid Compute allocation, states the database connection consequences of each, and explains how concurrency is bounded and what happens when it saturates.

Under the older per-request model, concurrency equals the number of in-flight requests. Each request gets an instance; an instance that opens a database connection holds it for the request’s duration. A 500-request-per-second endpoint with 200 ms duration produces roughly 100 concurrent instances and, if each opens a connection, 100 database connections from a burst that may last two seconds. That is a connection storm, and it is why serverless functions exhausting a database’s connection limit is one of the most common production incidents on this platform.

Under Fluid Compute, concurrency is served by a bounded number of instances, each handling multiple in-flight requests. The connection count is therefore bounded by the instance count rather than by the request rate, which is a qualitative change: you can size the database connection limit against a number you configure and observe, instead of against a traffic spike.

Two properties survive both models and are worth stating because code written against a long-lived server breaks on both. There is no guaranteed instance affinity, so an in-process cache, a rate-limit counter or a warm socket cannot be assumed to be there on the next invocation. And there is no shared memory between instances, so anything that must be consistent must live in an external store or in a database with a constraint.

// Broken under both models — module scope is per instance, and
// instances are replaced, scaled out and moved between regions.
const rate = new Map<string, number>();

export async function POST(req: Request) {
  const ip = req.headers.get('x-forwarded-for') ?? 'anon';
  const n = (rate.get(ip) ?? 0) + 1;
  rate.set(ip, n);
  if (n > 100) return new Response('rate limited', { status: 429 });
  return Response.json({ ok: true, count: n });
}

// Correct: an external store, with a TTL so it self-expires.
import { createClient } from '@vercel/kv';
const kv = createClient({
  url: process.env.KV_REST_API_URL!, token: process.env.KV_REST_API_TOKEN!
});

export async function POST(req: Request) {
  const ip = req.headers.get('x-forwarded-for')?.split(',')[0] ?? 'anon';
  const key = `rl:${ip}`;
  const n = await kv.incr(key);
  if (n === 1) await kv.expire(key, 60);
  const ttl = await kv.ttl(key);
  return Response.json({ ok: n <= 100, count: n, ttl }, {
    status: n > 100 ? 429 : 200,
    headers: { 'x-ratelimit-limit': '100', 'x-ratelimit-remaining': String(Math.max(0, 100 - n)) }
  });
}

Concurrency is bounded by the plan, not only by your settings. There is a per-deployment concurrency ceiling and, on plans without Fluid Compute, no meaningful floor. When a deployment saturates, requests queue and then receive a 429 or a platform error rather than hanging indefinitely — but the client-visible behaviour is a hard failure, so the queue depth is a capacity-planning input, not an implementation detail. Read the current ceiling from the limits page for the plan you run.

Bound your own work explicitly. Use a semaphore of one in a handler that does non-idempotent work, or route writes through a single-writer design. Under Fluid, an instance handling 32 concurrent requests means 32 interleaved executions in one process — a module-level variable mutated between awaits is a data race that reproduces only under load. Treat the instance as shared memory and use external coordination for anything that matters.

4.5 Streaming responses

Documents streaming from both the Node and edge runtimes, its interaction with the duration ceiling and with CDN buffering, and the buffering pitfalls that make it appear not to work.

Streaming lets a handler emit bytes before the response is complete. It changes perceived latency rather than total duration: a token-by-token LLM response, a progressive CSV export, a chunked server-rendered page. Both runtimes support it — the edge runtime through Web Streams natively, the Node runtime through Readable adapted to the response body, and both through async iterables that the runtime converts.

Three things interfere. The duration ceiling still applies to the whole stream, not to the time between chunks. CDN and proxy buffering defeats the benefit if a layer between you and the client accumulates the body — which you can detect by measuring time-to-first-byte rather than total time. And error handling changes: once the first byte is committed, a mid-stream error cannot become a 500, so failures must be encoded in-band.

// app/api/chat/route.ts — streaming from a Node runtime handler
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';

export const maxDuration = 60;

export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = streamText({
    model: openai('gpt-4.1-mini'),
    system: 'You are a concise storefront assistant. No preamble.',
    messages,
    maxTokens: 500
  });

  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    async start(controller) {
      try {
        for await (const delta of result.textStream) {
          controller.enqueue(encoder.encode(delta));
        }
        controller.enqueue(encoder.encode('\n'));
      } catch (err) {
        // Headers are already sent. Encode the failure in-band
        // rather than throwing, which would truncate silently.
        controller.enqueue(encoder.encode(
          `\n[error] ${err instanceof Error ? err.message : 'upstream failed'}\n`
        ));
      } finally {
        controller.close();
      }
    }
  });

  return new Response(stream, {
    headers: {
      'content-type': 'text/plain; charset=utf-8',
      'cache-control': 'no-store',
      'x-accel-buffering': 'no',      // defeat proxy buffering
      'transfer-encoding': 'chunked'
    }
  });
}

Streaming and caching are in tension. A response with Content-Type: text/event-stream must not be cached, and setting a positive s-maxage on a stream produces an entry that is a truncated first chunk. If the stream is a live event feed, use no-store; if it is a progressive render of content that is identical for every user, generate it fully and cache the result rather than streaming it.

A client disconnect is not a server-side cancel. When a streaming client goes away, the runtime signals the request as aborted and the platform reclaims the instance — but any work already dispatched to a third party keeps running and keeps costing. For LLM calls, pass an abort signal through to the provider SDK. For anything billed per call, this is the difference between a client closing a tab costing a fraction of a cent and costing a full completion.

4.6 Cold starts and minimum concurrency

Explains the components of a cold start, the mitigations available, and how to size a minimum-concurrency setting from measured traffic.

A cold start is the interval between a request arriving at an instance with no prior work and that instance being able to respond. It has three components: the time to obtain an instance, the time to load and execute the module bundle, and the time for the application’s own initialisation — which includes any top-level await, any SDK client construction, and, critically, any connection acquisition if the module opens one at import time. The third component is the one you control, and it is frequently the largest.

Module-level initialisation is a mistake in a serverless runtime. A database pool created at module scope, a schema validation compiled at import, a large JSON file parsed at import, a crypto key derived at import — all of these execute on every instance creation and are pure latency added to every cold start. Move them behind a lazy initialiser so the work happens on first real use, and cache the result on the instance for subsequent invocations.

// Cold-start-hostile: three expensive things at module scope.
import { PrismaClient } from '@prisma/client';
import { schema } from '@/generated/schema';
import { privateKeyPem } from '@/certs/private.pem';

const prisma = new PrismaClient();          // TCP + handshake
const compiled = JSON.parse(schema);         // megabytes of JSON
const key = privateKeyPem.toString('base64'); // fs read + encode

// Cold-start-friendly: nothing happens until it is needed, and
// the result is reused for the life of the instance.
import type { PrismaClient } from '@prisma/client';

let _prisma: PrismaClient | undefined;
let _schema: unknown;
let _key: string | undefined;

export const db = new Proxy({} as PrismaClient, {
  get(_t, prop) {
    if (!_prisma) {
      const { PrismaClient } = require('@prisma/client') as typeof import('@prisma/client');
      _prisma = new PrismaClient();
    }
    return Reflect.get(_prisma, prop);
  }
});

export const getSchema = () => (_schema ??= require('@/generated/schema').default);
export const getKey = () => (_key ??= Buffer.from(process.env.SIGNING_KEY!, 'base64').toString('base64'));

Minimum concurrency is the direct mitigation: keep N instances warm and ready so requests never wait for scale-up. Sizing it is arithmetic against your own traffic, not against the plan maximum. Compute the expected concurrent requests from Little’s law — concurrency equals arrival rate times average duration — and set the minimum above the p95 concurrency, not the mean. A minimum of one keeps a single instance warm and removes the worst tail; a minimum matching p95 concurrency removes the tail entirely and costs reserved capacity continuously.

5.1 Managed Postgres

Describes the managed Postgres model, the connection-string contract, pooled versus direct strings, regions and branching, and the limits that determine when to move off it.

Vercel Postgres is a managed Postgres service integrated through the storage marketplace, provisioned in a region, and exposed to your project through environment variables. The integration produces at least a direct connection string and, on plans that support it, a pooled string backed by a pooler. Those two strings are different in kind, not merely in host, and using the wrong one is the root of the connection-exhaustion problem in the next-but-one section.

Region selection is fixed at creation and is coupled to your function regions. A database in iad1 and functions executing in fra1 pay cross-region latency on every query, and the latency is charged to your function’s duration budget rather than billed separately. Match the database region to the region serving the majority of traffic, and pin the function with preferredRegion in the route or the regions array in vercel.json.

5.2 Vercel KV

Describes the KV product, its Redis-compatible command surface, the two access transports, the operations-based billing, and the constraints that distinguish it from a general-purpose cache.

Vercel KV is a managed key-value store with a Redis-compatible command surface, accessible over TLS with a long-lived connection or over HTTP with a stateless request. The HTTP transport is what makes it usable from the edge runtime and from anywhere a TCP socket is unavailable; the TCP transport is lower-latency from the Node runtime. Both present the same commands, and the SDK picks one based on which environment variables are present.

It is a cache and a small durable store, not a primary database. It has no transactions beyond single-command atomicity, no secondary indexes, no joins, and no relational constraints. Values are limited in size, keys are limited in count per database, and eviction is policy-driven rather than under your control. The right uses are caching, rate limiting, counters, session and token blocklists, feature flags, and idempotency records with a TTL.

// Two transports, one API. The SDK selects based on which
// environment variables the integration provisioned.
import { createClient } from '@vercel/kv';

const kv = createClient({
  url:     process.env.KV_REST_API_URL,      // HTTP transport
  token:   process.env.KV_REST_API_TOKEN,    // for edge + REST
  url_tcp: process.env.KV_URL,               // TLS transport
  token_tcp: process.env.KV_REST_API_TOKEN,
  automaticDeserialization: true
});

// Cache-aside with a stampede guard.
const inflight = new Map<string, Promise<unknown>>();

export async function cached<T>(key: string, ttl: number, fn: () => Promise<T>): Promise<T> {
  const hit = await kv.get<T>(key);
  if (hit !== null) return hit;

  // A per-instance guard. Not a distributed lock — for a true
  // distributed guard use SET NX with a short TTL below.
  const existing = inflight.get(key);
  if (existing) return existing as Promise<T>;

  const p = fn()
    .then(async (v) => { await kv.set(key, v, { EX: ttl }); return v; })
    .finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}

// Distributed stampede guard for high-traffic keys.
export async function acquire(key: string, ttl: number): Promise<boolean> {
  const res = await kv.set(`lock:${key}`, '1', { NX: true, EX: ttl });
  return res === 'OK';
}

KV is billed on operations and on storage, with commands priced differently: a read is cheaper than a write, a scan is expensive and is not a substitute for a known key, and deleting by prefix requires a scan. A cache with a low hit rate can therefore be a net cost rather than a saving, because you are paying for the writes and the misses and getting nothing back. Measure the hit rate before expanding a KV deployment.

// Hit-rate instrumentation worth having from day one.
import { createClient } from '@vercel/kv';
const kv = createClient({
  url: process.env.KV_REST_API_URL!, token: process.env.KV_REST_API_TOKEN!
});

export async function instrumented<T>(
  key: string, ttl: number, fn: () => Promise<T>
): Promise<T> {
  const hit = await kv.get<T>(key);
  if (hit !== null) {
    await kv.hincrby('metrics:kv', 'hit', 1);
    return hit;
  }
  await kv.hincrby('metrics:kv', 'miss', 1);
  const value = await fn();
  await kv.set(key, value, { EX: ttl });
  return value;
}

// Report:
// > hgetall metrics:kv
// { hit: "918273", miss: "81642" }   → 91.8% hit rate, healthy
// { hit: "104", miss: "99896" }     → 0.1% hit rate, delete it

// Rate-limit counters with a fixed window and a hard cap.
export async function rateLimit(id: string, limit: number, window: number) {
  const k = `rl:${id}:${Math.floor(Date.now() / 1000 / window)}`;
  const n = await kv.incr(k);
  if (n === 1) await kv.expire(k, window + 1);
  return { allowed: n <= limit, remaining: Math.max(0, limit - n) };
}

TTL on every key. KV has no automatic expiry policy you should rely on, and an unbounded keyspace is both a storage cost and a latency cost as the store grows. Make EX a required argument in your wrapper rather than an optional one — the type signature is a better enforcement mechanism than a code review comment, and it is the kind of invariant that survives staff turnover.

5.3 Vercel Blob

Documents the Blob API, access control models, multipart and streaming uploads, the read-path integration with the image optimizer, and the egress implications of serving user uploads.

Blob is object storage with a thin HTTP API and a token-based access model. Content is addressed by pathname, which makes it a poor fit for frequently-replaced content under the same path and a good fit for immutable, content-identified content. Uploads are made from a route handler using a token generated server-side; the token’s access level is the security boundary, so generating a public token for user content publishes it.

The access levels are the design decision. public content is served without a token and can be cached aggressively at the CDN. private content requires a token on every read, which means every read is an authenticated HTTP request to the store and cannot be cached at the edge. Serving private content through a proxying function — the function checks authorisation and then fetches from Blob — restores cacheability at the cost of metering that traffic through your bandwidth.

// api/uploads/sign.ts — server-side token generation
import { handleUpload } from '@vercel/blob/client';

export async function POST(req: Request) {
  const session = await requireSession(req);            // your auth
  const body = await req.json();

  const jsonResponse = await handleUpload({
    body: {
      access: 'private',             // never 'public' for user uploads
      allowedContentTypes: ['image/jpeg', 'image/png', 'image/webp', 'application/pdf'],
      maximumSizeInBytes: 25 * 1024 * 1024,
      addRandomSuffix: true,          // prevents path guessing
      tokenPayload: JSON.stringify({ userId: session.user.id })
    },
    request: req,
    onBeforeGenerateToken: async (pathname, clientPayload) => {
      if (!canUpload(session.user, clientPayload.userId)) {
        throw new Error('forbidden');
      }
      return { allowedContentTypes: ['image/*'], maximumSizeInBytes: 25 * 1024 * 1024 };
    }
  });

Serving user uploads through a function rather than directly is the pattern to reach for when the content is private or when you need transformation. It costs an invocation and metered egress per read, and it gives you a place to enforce authorisation, apply a watermark, redirect to a resized variant, or return a signed URL with a short lifetime. For public, immutable content, serving the Blob URL directly is strictly better because the CDN serves it without invoking you.

Egress is where Blob bills you back. A 2 GB dataset download, a video asset served without a CDN cache policy, or a container image layer pulled repeatedly will all show up as bandwidth. 5.4 Storage integrations and marketplace

Covers the integration model, environment variable contracts, access control, the OIDC identity used by cloud integrations, and the operational consequences of a marketplace resource being regional or plan-gated.

Storage and database integrations are installed from the marketplace into a specific environment scope. Installing into production only is the common configuration and the correct default; installing into all environments gives every preview deployment a real database and bills you for it, whether or not a preview exists. Each integration provisions its own variables, and the variable names are integration-specific, which is why reading what your project actually has is more reliable than assuming a naming convention.

Cloud provider integrations — S3-compatible storage, a managed database on AWS or GCP — authenticate with OIDC rather than static keys. Vercel presents a signed identity token to the provider, the provider trusts it under a configured role, and no long-lived credential exists in your project’s environment at all. This is a genuine security improvement over an access key, and it has a cost: a misconfigured trust policy produces an authorisation error that surfaces as a 500 with a provider message, and debugging it means reading the provider’s CloudTrail, not your application’s logs.

5.5 Connection pooling

Explains why serverless functions exhaust database connections, and gives the three required mitigations: an external pooler, the pooled connection string, or a driver pooler with a maximum of one connection per instance.

The mechanism is simple and the numbers make it unavoidable. A database has a hard connection limit — often 100 for a modest instance, lower on serverless Postgres plans. A serverless function opens a connection when it starts doing work and holds it for the instance’s lifetime. Under the per-request concurrency model, N concurrent requests means up to N connections. A deployment that receives a 200-request burst with a 500 ms handler duration reaches 100 concurrent connections in half a second and the database begins refusing new ones. The application then returns 500s, which causes retries, which causes more connections, which deepens the failure.

There are three correct mitigations and you need at least one of them. A pooler in front of the database multiplexes many client connections onto a small number of database connections; use the pooled connection string the integration provisions. A driver-level pooler with max: 1 caps each instance at one connection, which combined with Fluid Compute bounds the total to the instance count; this works because an instance multiplexes many requests over its single connection. A HTTP-native driver avoids TCP entirely and is the only option on the edge runtime.

// The problem, in numbers. Direct string, no pooler.
// 200 rps burst, 500 ms handler, 100-connection database limit:
//   concurrency = 200 * 0.5 = 100 connections at t=0.5s  → REFUSED
// Retries multiply it. This is not a slow-database problem.

// Mitigation A — use the pooled connection string. Same code.
const url = process.env.DATABASE_URL;          // pooled, points at pooler
// NOT process.env.DIRECT_DATABASE_URL, NOT the raw host:5432

// Mitigation B — driver pooler, max 1 per instance.
import { Pool } from 'pg';
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 1,                     // ONE connection per instance
  idleTimeoutMillis: 30_000,  // let it close when idle
  connectionTimeoutMillis: 3_000,
  allowExitOnIdle: false
});
// With Fluid Compute at 20 instances → at most 20 connections.
// Pool wait is the queue; it is visible and it is bounded.

Each mitigation has a characteristic cost that determines which to choose. An external pooler adds a network hop and a small per-query overhead, and it caps total database concurrency at the pooler’s pool size, which becomes a throughput ceiling for the whole application. A driver pooler with max: 1 adds queueing inside the instance under load and serialises queries that could have run in parallel, which matters for a request doing two independent queries. An HTTP driver removes pooling from the problem entirely and adds a serialisation round trip per query.

5.6 Migrations in a deployment pipeline

Describes running migrations in the build, the expand-contract pattern, the ordering hazard between migration and deploy, and the rollback implications of each.

A migration that runs in the build phase executes before the new code is serving traffic, which means it is running while the previous deployment is live. Any migration that is not backward-compatible with the running version will break production during the build window. This is the ordering hazard, and it is why the expand-contract pattern exists.

Expand-contract makes every migration safe to deploy while the old code is still running. Expand: add the new column as nullable, or add the new table, without removing or renaming anything. Deploy code that writes to both shapes and reads from the old. Migrate: backfill in batches, from a separate job, not from the deploy. Contract: in a later deploy, after the backfill is verified and the old code is fully retired, stop reading the old shape and drop it. Each deploy is independently safe and independently reversible.

// Phase 1 — expand. Safe while old code is serving.
// migrations/20260114_add_customer_email_verified/migration.sql
ALTER TABLE "Customer" ADD COLUMN "emailVerifiedAt" TIMESTAMP(3);
CREATE INDEX CONCURRENTLY "Customer_emailVerifiedAt_idx"
  ON "Customer" ("emailVerifiedAt") WHERE "emailVerifiedAt" IS NOT NULL;

// Phase 2 — deploy code that tolerates both shapes.
// src/server/customer.ts
export function isVerified(c: Customer): boolean {
  // Reads the new column when present, falls back when not.
  return c.emailVerifiedAt !== null && c.emailVerifiedAt !== undefined;
}
// Writes both during the transition window.
export async function verifyEmail(id: string) {
  const at = new Date();
  await db.customer.update({ where: { id }, data: {
    emailVerified: true,
    emailVerifiedAt: at,
    legacyVerifiedFlag: 'Y'          // still required by v_old
  }});
}

// Phase 3 — backfill, batched, outside the deploy.
// scripts/backfill.mjs — run as a one-off job, not in build
const BATCH = 500;
for (;;) {
  const { rows } = await db.$queryRaw`
    UPDATE "Customer" SET "emailVerifiedAt" = "updatedAt"
     WHERE "emailVerifiedAt" IS NULL
       AND id IN (SELECT id FROM "Customer"
                   WHERE "emailVerifiedAt" IS NULL LIMIT ${BATCH})
    RETURNING id`;
  if (rows.length === 0) break;
  await new Promise((r) => setTimeout(r, 200));   // be gentle
}

Running migrations in the build has one advantage and several costs. The advantage is that a failing migration fails the deploy rather than the application, which is the right failure ordering. The costs are: the migration runs concurrently with production traffic against the same database, so a lock on a hot table blocks live writes; the migration has the build duration ceiling, which a large backfill will exceed; and the build may be retried, so the migration must be idempotent or transactional.

Rollback asymmetry. A deployment can be rolled back by repointing an alias in seconds. A migration cannot, because the database has moved on. This is the strongest argument for expand-contract: after a phase-1 expand migration, rolling back the code is completely safe, because the new nullable column and the concurrent index are inert. After a contract migration, it is not.

Do not run migrations from preview builds against production. A preview build inherits its environment from the preview scope, and a misconfigured preview scope with a production connection string will apply every migration to production on every pull request. This is the exact failure that environment scoping exists to prevent, and it is worth a CI check that asserts the production connection string’s host never appears in a preview build’s resolved configuration.

6.1 Environment variables and scoping

Documents the three environment scopes, their precedence and their propagation into build and runtime, and the rule that a preview must never read production secrets.

Every project has three environment scopes. Production applies to deployments targeting the production environment. Preview applies to every other deployment, with no per-branch sub-scope by default. Development applies to vercel dev and is populated by vercel env pull or a .env.local file. Variables are plaintext values; the distinction between a variable and a secret is metadata, not a different storage mechanism.

Precedence at runtime is: value set for the specific deployment (deploy-hook or CLI override) beats the environment scope, which beats process.env inherited from the platform. At build time, the same scope resolution applies, plus build.env in vercel.json, which is build-only and invisible to the function. The failure this causes — a value present during the build and absent at runtime — is one of the most common production incidents and has a one-line diagnosis: grep the runtime for the variable name.

The invariant that matters most is that a preview build must never read production secrets. It is violated in three ordinary ways. First, a variable is added with the target "all" when it was only intended for production. Second, a third-party marketplace integration is installed into all scopes, so previews receive production credentials for the same database or bucket. Third, a CI job uses a production token to run a preview build, which is the same violation with extra steps.

The consequence is not hypothetical. A preview deployment with a production Stripe key can create real charges. A preview with a production database URL can apply migrations to production, as covered in chapter 5. A preview with a production email credential can send mail to real people. Every one of these is prevented by scoping, and none of them is prevented by a convention you intend to follow.

6.2 Secrets and credential types

Distinguishes dashboard access tokens, CLI tokens, personal account tokens, service account tokens and OIDC federation, and states which belongs in CI.

There are four credential types and conflating them is a common source of both privilege excess and CI fragility. Dashboard access tokens are created per user for programmatic access to the dashboard’s own API surface — the endpoints behind the settings pages. They are a human’s credentials and should not be in CI. Personal CLI tokens are created by a person and act as that person: they inherit their role, they appear in the audit log as that person, and they stop working when the person leaves.

Team service account tokens act as a non-human principal with an explicitly assigned role and an explicit expiry. These belong in CI. OIDC federation to AWS, GCP or another provider is a different mechanism entirely: your CI provider presents a signed identity token, Vercel exchanges it for a short-lived credential scoped to the project, and nothing long-lived exists anywhere. Where OIDC is offered, it is strictly better than any static token.

// Preferred: OIDC to AWS. No static key exists in CI or in Vercel.
// .github/workflows/deploy.yml
permissions:
  id-token: write          // required to mint the OIDC token
  contents: read
  aws-actions/configure-aws-credentials: no
env:
  VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
  VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}
  AWS_ROLE_ARN: arn:aws:iam::123456789012:role/vercel-deploy
steps:
  - uses: actions/checkout@v4
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: ${{ env.AWS_ROLE_ARN }}
      aws-region: us-east-1
  - run: npx vercel pull --yes --environment=production --token=${{ secrets.VERCEL_TOKEN }}
  - run: npx vercel build --prod
  - run: npx vercel deploy --prebuilt --prod --token=${{ secrets.VERCEL_TOKEN }}
// VERCEL_TOKEN here is a SHORT-LIVED, project-scoped token
// minted by the OIDC exchange, not a stored secret.

Service account tokens should have a role, an expiry and a defined scope. A token that can deploy and delete projects and never expires is a permanent, unrecoverable liability: anyone who obtains it can remove production. The expiry on a deploy token should be measured in hours or days, rotated by the pipeline that uses it, and stored in the CI provider’s secret store with rotation notifications.

6.3 Deployment protection and security

Documents password and SSO protection, standard and preview protection, the WAF and Firewall Rules, rate limiting, and how protection interacts with bots, health checks and automated checks.

Deployment protection sits in front of the routing layer and gates access to an environment’s deployments before any application code executes. Two mechanisms exist: a password, which is a shared secret protecting a whole environment, and SSO, which requires team membership and can be restricted by group or role. Both can be applied to previews and to standard deployments independently, and the two settings are separate toggles that are easy to confuse.

Protecting previews is the highest-value configuration in this chapter, because preview URLs are unguessable but not secret — they leak through commit references in public pull requests, through browser history on shared machines, through error reporters and through screenshots. An unlisted URL is obscurity, not access control.

// Automated checks must pass protection. Configure a bypass
// header, and keep its value in the CI secret store only.
// .github/workflows/smoke.yml
- name: Smoke test the production deployment
  run: |
    curl -fsS -o /dev/null -w '%{http_code}\n' \
      -H "x-vercel-protection-bypass: ${{ secrets.VERCEL_PROTECTION_BYPASS }}" \
      -H "x-vercel-set-bypass-cookie: true" \
      https://storefront.example.com/healthz

// Never put the bypass value in a URL query string: it lands in
// access logs, Referer headers and browser history.
// Never commit it. Never expose it to the client bundle.

WAF and Firewall Rules are configured at the edge, ahead of the application, and operate on request attributes: IP, geography, user agent, path, method, headers, and for Enterprise, bot categories and rate limits. They are the right place for denials that should not consume a function invocation, and the right place for geographic and reputation rules. They are the wrong place for application authorization, which must live in the application because the edge does not know who the user is.

// Firewall rules: JSON, evaluated top to bottom, first match wins.
{
  "version": "1",
  "rules": [
    { "if": "req.ip.ver", "then": { "action": "rate_limit",
        "rate_limit": { "limit": 600, "interval": 60, "key": "ip" } } },
    { "if": "geoip.country == 'RU' and not req.path.path.startsWith('/legal')",
      "then": { "action": "deny" } },
    { "if": "req.method == 'POST' and req.path.path.startsWith('/api/auth')",
      "then": { "action": "challenge", "challenge": { "type": "js" } } },
    { "if": "http.user_agent matches '^curl|wget|python-requests'",
      "then": { "action": "deny" } },
    { "if": "req.path.path matches '^/api/(admin|internal)/' and not ip.is_in_vercel()",
      "then": { "action": "deny" } }
  ],
  "default_action": "allow"
}

Security headers were covered in chapter 2. The remaining operational items are the ones teams forget: a Content-Security-Policy that is deployed and then never tested against a real login flow; frame-ancestors set without checking whether a legitimate partner embeds the product; rate limiting applied at the edge for high-volume routes and in the application for per-user quotas; and a response to a compromised third-party script that assumes a third-party script is compromised, which means a remote kill switch.

// A remote kill switch for a third-party script, evaluated per
// request and cached briefly so it costs one KV read at most.
import { createClient } from '@vercel/kv';
const kv = createClient({ url: process.env.KV_REST_API_URL!,
                         token: process.env.KV_REST_API_TOKEN! });

export async function middleware(req: Request & { next: () => Promise<Response> }) {
  const flag = await kv.get<string>('flags:analytics').catch(() => 'on');
  const html = await req.next();
  const res = new Response(html.body, html);

  if (flag !== 'on') {
    res.headers.set('content-security-policy',
      "default-src 'self'; script-src 'self'; img-src 'self' data:");
  }
  return res;
}
// Flip flags:analytics to "off". Every route is protected within
// the KV read TTL. No redeploy, no rollback.

Protection applies per environment, not per deployment. Turning on protection for previews protects every current and future preview, which is what you want, but it also means your team can no longer click a preview link without credentials — including from a phone. Set the SSO group to include everyone who reviews, and set the bypass for automated checks before you enable it, or you will spend the first ten minutes of a release blocked on your own password.

6.4 Domains, apex and wildcards

Covers domain assignment, apex and subdomain DNS records, wildcard certificates, domain-level headers and redirects, and the geo and platform request headers available for routing.

A domain added to a team is assigned to a project, and it serves whichever deployment currently holds the production alias for that project. Apex domains cannot be served by a CNAME at the DNS root, so they require the platform’s A and ALIAS records or a CNAME flattening provider; subdomains use a CNAME to the platform’s assigned target. Verification is a TXT record proving control, and it is one-way — once verified, the domain can be pointed at any project in the team without re-verification.

Wildcard domains are supported and are the correct configuration for a platform serving many customer hostnames. A wildcard *.example.com requires a CNAME covering all subdomains and yields a certificate covering the wildcard and the apex. The consequence is that a request to any unmatched subdomain is served by your production deployment and runs your application, so the application must handle an unknown host deliberately — resolve tenant by hostname, return 404 for an unknown tenant, and never let an unrecognised host fall through to a default tenant with production data.

// Wildcard  *.example.com

// Verification, TXT on the root

// Multi-tenant host resolution, framework-level.
// middleware.ts — runs before routing, sees the raw Host
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(req: NextRequest) {
  const host = (req.headers.get('x-forwarded-host') ?? req.headers.get('host') ?? '')
    .split(':')[0].toLowerCase();
  const apex = process.env.APEX_DOMAIN ?? 'example.com';
  const sub = host.endsWith(`.${apex}`) ? host.slice(0, -(apex.length + 1)) : null;

  if (host !== apex && !sub) {
    return new NextResponse('unknown host', { status: 404 });
  }
  if (sub && !/^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$/.test(sub)) {
    return new NextResponse('invalid host', { status: 400 });
  }

  const url = req.nextUrl.clone();
  if (sub) url.searchParams.set('__tenant', sub);
  return NextResponse.rewrite(url);
}

export const config = { matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'] };

Domain-level headers and redirects apply only to requests arriving on that domain, which is what makes multi-domain hosting with a single project tractable. The canonical host gets the security headers; a legacy host gets a 308 to the canonical host; an apex-plus-www arrangement gets the 308 on the non-canonical side with no chain. Getting this wrong produces the most common domain incident: a redirect loop, because both hosts redirect to each other, or because the canonical redirect and the trailing-slash redirect disagree.

// per-domain configuration
{
  "redirects": [
    { "source": "/:path*", "destination": "https://www.example.com/:path*",
      "permanent": true }
  ],
  "headers": [
    { "source": "/:path*",
      "headers": [{ "key": "Strict-Transport-Security",
                    "value": "max-age=63072000; includeSubDomains; preload" }] }
  ]
}
// Applied to legacy.example.com only, as a domain-level setting.
// The canonical host must NOT redirect to itself.

Two request headers carry the geo and platform context that routing and rate limiting depend on. x-vercel-ip-country is the ISO 3166-1 alpha-2 country derived from the client address, and x-vercel-ip-country-region gives the subdivision. Both can be XX when the address cannot be geolocated — which happens for private ranges, some VPNs and some proxies — so any logic that branches on country must have a defined behaviour for XX rather than treating it as a valid country. x-vercel-ip-city and x-vercel-ip-latitude / x-vercel-ip-longitude are available where the edge can determine them.

// Edge function using geo headers, with an explicit XX branch
export const config = { runtime: 'edge' };

const COUNTRY_TO_LOCALE: Record<string, string> = {
  US: 'en-US', CA: 'en-CA', GB: 'en-GB', DE: 'de-DE', JP: 'ja-JP'
};

export default function handler(req: Request) {
  const country = req.headers.get('x-vercel-ip-country') ?? 'XX';
  const region  = req.headers.get('x-vercel-ip-country-region') ?? 'XX';

  const locale = COUNTRY_TO_LOCALE[country] ?? 'en-US';   // defined default
  const known  = country !== 'XX';

  return Response.json({
    country, region, locale,
    geolocationReliable: known,
    // Never infer currency or tax jurisdiction from these
    // alone — a VPN in DE is not a buyer in DE.
    pricingCurrency: process.env.DEFAULT_CURRENCY
  }, {
    headers: {
      'cache-control': 'public, s-maxage=300, stale-while-revalidate=86400',
      'vary': 'x-vercel-ip-country, x-vercel-ip-country-region',
      'x-geo-reliable': known ? '1' : '0'
    }
  });
}

Certificate provisioning takes time; plan for it. A newly added domain is served over HTTP before its certificate is issued, and automated checks that require TLS will fail for a period measured in minutes and occasionally longer. Add the domain, verify DNS, then wait for issuance before pointing traffic at it. For a migration, add the domain to the project first, confirm it serves the expected deployment, and only then cut DNS — otherwise the cutover window is a certificate window.

A wildcard domain is a large attack surface. Any subdomain a visitor guesses is served by your production application, your production cookies are scoped to the parent domain, and your application must resolve every host. Do not use a wildcard unless the product is genuinely multi-tenant, and if you do, set the cookie domain to the specific host rather than the parent, or one tenant’s session is readable on another’s subdomain.

6.5 Preview hygiene and access

Covers preview access control, retention and pruning, indexing prevention, per-branch controls, and the review workflow that makes previews useful rather than merely present.

Preview access has three layers and all three should be on: deployment protection for authentication, a noindex response header for discoverability, and a retention policy for existence. The header is set in the preview environment scope so it applies to every preview without touching production.

// vercel.json — but a scope override is cleaner, because this
// applies only to previews and cannot accidentally hit prod.
{
  "headers": [
    { "source": "/:path*",
      "headers": [
        { "key": "X-Robots-Tag", "value": "noindex, nofollow, noarchive" },
        { "key": "X-Robots-Preview", "value": "true" }
      ] }
  ]
}
// Prefer: Project Settings → Preview → Headers, scoped to
// the preview environment only.

// Prune previews for merged branches.
$ npx vercel ls storefront --yes | head -20
# List previews, filter by branch, remove all but the newest N.
$ for url in $(npx vercel ls storefront --json | jq -r '.[].url'); do
    npx vercel rm "$url" --yes
  done

Per-branch controls keep the preview population bounded. Branch-level toggles disable previews for branches that never need one — dependabot branches, long-lived experiment branches, release branches that duplicate production. A path filter in the Ignored Build Step keeps documentation-only changes from producing a deployment at all. Together these two controls typically reduce preview count by an order of magnitude without affecting any review workflow.

What makes a preview useful is review instrumentation: a comment bot that posts the preview URL, a status check that re-runs when the head commit changes, and a smoke test that runs against the preview with the protection bypass. Use concurrency with cancellation. A pull request with 40 pushes produces 40 builds and 40 deployments, of which 39 are useless. Cancelling in-progress runs bounds the count at one live preview per PR and cuts build minutes proportionally, with no effect on the reviewer’s experience.

6.6 Teams, roles and workflow

Documents team roles and their effective permissions, the access model for production, promotion and rollback, required checks on Enterprise, and the operational practices that keep deployments auditable.

Roles are assigned at the team level and there are fewer of them than the dashboard implies. Owner has full control including billing, team deletion and member management. Member can create and manage projects and deploy. Developer can work within projects they are granted access to. The distinction that matters operationally is that only Owner can change billing or delete the team, and only Owner or Member can add a project — so the practical question for an organisation is who holds Owner, and how many.

Access to a specific production deployment is mediated by the environment, not by the project. That means a person with full project access can still be blocked from production by deployment protection, and that protection can require SSO plus a group membership. On Enterprise, required reviews and a deployment gate can require a second approver before a production promotion completes, which converts a two-person rule from a convention into a platform-enforced control.

Three practices separate a team whose deployments are auditable from one whose are not. No production deploys from a laptop. Every production change flows through CI, so the actor in the audit log is the pipeline and the commit is traceable. Branch protection with required checks. A production branch whose only gate is human review will receive a direct push. Deployment annotation. Recording the change reference on the deployment makes the rollback decision a lookup rather than an investigation.

// CI: build once, deploy the same artefact, annotate it.

      --meta githubCommitRef=${{ github.sha }} \

    VERCEL_TOKEN: ${{ secrets.VERCEL_TOKEN }}

    pnpm exec vercel annotate \
      "$(pnpm exec vercel ls storefront --json | jq -r '.[0].uid')" \

// Observability setup that makes a rollback decision fast
// instrumentation.ts — registered at the top of the file
export async function register() {
  const { NodeSDK } = await import('@vercel/observability');
  await new NodeSDK({ serviceName: 'storefront-api' }).start();
}

Owner concentration is a single point of failure. If the only Owner leaves or their account is locked, billing changes, member management and team deletion become unreachable, and in the worst case the whole team is unrecoverable. Maintain at least two Owners, keep the list in a place that is not the platform itself, and review membership on a schedule so that people who left a project three months ago do not still hold access to it.
