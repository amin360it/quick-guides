1 ▸ Orientation: Why Rust

1.1 Why Rust, and what it guarantees1.2 Cargo, rustup and the edition system1.3 Hello, world — and the compiler as teacher1.4 Where Rust fits, and where it does not

Rust is a systems language that guarantees memory safety and thread safety at compile time, without a garbage collector, by enforcing ownership rules in the type system. This chapter orients you: what Rust promises, how the toolchain is organised, and the territory — and the non-territory — where it earns its keep.

1.1 Why Rust, and what it guarantees

Every shortcoming that Rust removes comes from one of two places: a tool that makes a promise it does not keep, or a process that is not checking the promise at the boundary. Rust fixes the silence first, which makes the debugging much quieter.

The three pillars

Ownership means every value has exactly one owner, and the value is dropped when that owner goes out of scope. Borrowing means you can pass a reference to a value without giving up ownership, but the reference cannot outlive the owner. Lifetimes are the compile-time proof that borrowing is safe. The three ideas are one mechanism with three names: the compiler can prove a program is memory-safe because it can see, at every point, who owns what and which references are still valid.

fn sum(xs: &[i32]) -> i32 {
    xs.iter().sum()
}

fn main() {
    let xs = vec![1, 2, 3];
    println!("{}", sum(&xs));   // 6
}

What the compiler promises — and what it does not

The guarantee is narrow and strong: no dangling pointers, no use-after-free, no data races, no buffer overflows. Rust will not stop you from leaking memory deliberately with std::mem::forget, and it will not catch logical errors — you can still return the wrong sum, or dead-lock a mutex. It is a memory-safety guarantee, not a correctness guarantee. When several places genuinely need to share one value, the normal answer is a reference-counted handle: Rc on one thread, Arc across threads, both cloning by bumping a counter rather than copying the data.

use std::rc::Rc;

fn main() {
    let a = Rc::new(vec![1, 2, 3]);
    let b = a.clone();                // cheap: bumps the refcount
    println!("a and b share {:?}", a);
    println!("strong refs: {}", Rc::strong_count(&a));   // 2
}

The one leak Rust allows on purpose

std::mem::forget takes a value and declares it unreachable: the destructor never runs, so the memory is never returned. It is there for genuinely exotic cases — embedding a value into a lifetime-managed runtime, or handing a buffer to C code that takes over ownership. Because it compiles without complaint, the line is the documentation: a deliberate leak is visible, a buggy one is not.

use std::mem::forget;

fn main() {
    let s = String::from("leak me");
    forget(s);   // compiles and runs: the buffer is never freed.
                 // Rust stops accidents, not deliberate decisions.
}

1.2 Cargo, rustup and the edition system

Rust's toolchain is two programs and one file. cargo builds, tests, documents, publishes and resolves dependencies; rustc is the compiler underneath; and Cargo.toml is where the package's identity, its edition and its dependency versions live. Nearly every confusing thing about a Rust project traces back to a value in that file.

Six verbs, and what each guarantees

cargo new creates a project with a standard layout. cargo build compiles; adding --release turns on optimisation and is the difference between a development binary and a production one. cargo run builds and runs in one step. cargo test compiles and runs the unit tests, the integration tests and the documentation tests. cargo clippy is the linter, and cargo fmt rewrites the source to one canonical form. Everything else in the ecosystem hangs off those six.

$ cargo new hello        # a new binary crate, git already initialised
$ cd hello
$ cargo build            # debug profile: fast to compile, slow to run
$ cargo build --release  # optimised. THIS is what you deploy
$ cargo run              # build (if stale) and execute
$ cargo test             # unit, integration and doc tests
$ cargo fmt -- --check   # fail CI on unformatted code
$ cargo clippy           # 500+ extra lints on top of rustc
$ cargo doc --open       # build and open the API docs
$ cargo add serde        # add a dependency, editing Cargo.toml
$ cargo tree             # the full transitive dependency graph

Why the edition matters more than it looks

An edition is a set of language rules versioned separately from the compiler. A crate declaring edition = "2021" compiles with today's rustc under 2021 semantics, so it keeps working when the language changes underneath it. Omitting the field defaults to 2015, which disables every post-2015 feature in your code — no async/await, no dyn Trait, no 2018 module paths. Editions in order are 2015, 2018, 2021 and 2024; the field is the only place a whole language generation is switched on.

# Cargo.toml
[package]
name    = "billing"
version = "1.4.0"
edition = "2021"     # NEVER omit this. The 2015 default disables
                     # async, dyn Trait, the 2018 module paths and more.

[dependencies]
serde      = { version = "1", features = ["derive"] }
tokio      = { version = "1", features = ["full"] }
anyhow     = "1"

[dev-dependencies]
criterion  = "0.5"   # test-only: never in the shipped binary

[profile.release]
lto         = true   # link-time optimisation
codegen-units = 1
opt-level   = 3

The debug profile is not just slower

The debug profile enables debug_assertions and integer overflow checks, both of which are removed in release — so an arithmetic bug that panics in development silently wraps in production. The debug profile also generates no inlining and no optimisation, so debug timings are meaningless. This is the single most common way a Rust service passes its tests and fails in production, and the fix is a test suite that also runs against a release build.

fn main() {
    let x: u8 = 255;
    println!("{}", x + 1);
    // debug build:   panics — overflow checks are on
    // release build: prints 0 — it wraps, silently
}

// catch it in CI, not in production:
//   cargo test            (debug profile of the tests)
//   cargo test --release  (the run that matters)

What rustup manages, and what cargo does not

rustup manages toolchains: which compiler versions are installed, which is the default, and which targets are available for each. cargo manages one project: its dependencies, its profiles, its build script, and its output. The frequent confusion is looking for cargo subcommands that are actually rustup commands — installing a toolchain is rustup toolchain install, not a cargo operation at all. A team should pin one toolchain via rust-toolchain.toml so every checkout builds identically.

$ rustup show
active toolchain
stable-x86_64-pc-windows-msvc (default)
stable-x86_64-unknown-linux-musl

$ rustup toolchain install 1.78.0
$ cargo +1.78.0 build          # one project, one pinned toolchain
$ rustup component add clippy rustfmt
$ rustup target add wasm32-unknown-unknown

1.3 Hello, world — and the compiler as teacher

Your first Rust program is also your first real interaction with the compiler, and the compiler is deliberately talkative. Learning to read its diagnostics — location, cause, then a concrete suggested fix — is the fastest skill you can acquire in this language.

cargo new and the standard layout

cargo new hello creates src/main.rs and a Cargo.toml, and initialises git. The layout is the contract: every cargo project looks the same, so tooling and other engineers do not need to learn per-project structure. The binary's entry point is the main function in src/main.rs; println! writes a line to standard output.

$ cargo new hello
$ cd hello
# src/main.rs  — the file cargo created for you:
fn main() {
    println!("Hello, world!");
}

# $ cargo run
# Hello, world!
# the result is a native binary in target/debug/hello.exe
# (or target/debug/hello on Linux/macOS)

Reading a compiler error

Every rustc diagnostic names the error code, points at the offending line with a caret, and — crucially — usually suggests the fix. Do not fear the red text; it is a code review that runs at every build. The error below is the first one most people meet: variables are immutable by default, so assigning twice to answer is rejected before the program ever runs.

fn main() {
    let answer = 40;
    answer += 2;   // error[E0384]: cannot assign twice to
}                  // immutable variable `answer`
//   |
// 2 |     let answer = 40;
//   |         ------ first assignment to `answer`
// 3 |     answer += 2;
//   |     ^^^^^^^^^^ cannot assign twice to immutable variable
//   |
// help: consider making this binding mutable: `mut answer`

Taking the suggestion

Notice what the compiler asked for: not a change of value, but a change of intent. mut says the binding is meant to change. That is the pattern of every Rust fix — the compiler is usually right about the mechanics, and the suggestion is a good first move. When the fix is structural rather than cosmetic, the diagnostic will say so and point you at the documentation for the rule.

fn main() {
    let mut answer = 40;   // the compiler's own suggestion
    answer += 2;
    println!("{answer}");  // 42
}

1.4 Where Rust fits, and where it does not

Rust shines where a wrong pointer, a data race or an unsafe buffer is expensive: network services, embedded and real-time code, CLI tools, parsers and anything that must run for years. It is a poor fit where iteration speed and your own thinking time dominate — that is the territory of dynamic languages, and choosing the right tool is part of the job.

The territory: services, CLIs, embedded, parsers

A web service holding connection state and parsing untrusted input is classic Rust ground: every potential buffer overflow and race is a compile error, and the release binary is small and starts fast. The same loop that a dynamic language runs through an interpreter runs as native arithmetic here — but only if you actually build with --release, because the debug binary is unoptimised by design.

fn main() {
    // The same loop a dynamic language runs in its interpreter
    // runs as native arithmetic here. Compile with --release or
    // the timings mean nothing.
    let total: u64 = (0..10_000_000).map(|n| n * n).sum();
    println!("{total}");
}

Where Rust is the wrong tool

Rapid-prototyping glue code, one-off scripts, data exploration — anywhere the bottleneck is your own thinking rather than the machine — is dynamic-language territory. Rust makes you decide ownership early, and paying that tax on a program that will be rewritten tomorrow is wasted effort. The signal to watch is allocation patterns: a loop churning out formatted strings is fine in a script and the wrong shape for a hot path in Rust, where the fix is restructuring, not more memory.

fn main() {
    let mut events: Vec<String> = Vec::new();
    for i in 0..1000 {
        events.push(format!("event-{i}"));   // one allocation each
    }                                        // fine at 1,000, not 10M
    println!("{} events", events.len());
}

The deployment story: one static binary

Rust's other unfair advantage is the artifact. Because rustc is the entire compiler, cross-compiling needs no toolchain packages — just a target added via rustup — and the musl target produces a statically linked binary with no glibc version dependency. That one file runs on any Linux distribution and inside the smallest scratch container, which makes packaging and container images dramatically simpler than for a language with a shared runtime.

$ rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl

$ cargo build --release --target x86_64-unknown-linux-musl
$ file target/x86_64-unknown-linux-musl/release/billing
# ELF 64-bit LSB pie executable, x86-64, statically linked

# no dynamic linker, no shared libraries to install: copy the file
# onto any Linux host (or into a scratch container) and run it.
Run cargo doc --open on a project you did not write. The documentation is built from the source comments, and browsing it is the fastest way to learn how a crate actually wants to be used.
Never ship the debug build. It has no optimisation, keeps overflow checks — good for finding bugs, wrong for serving traffic — and its timings are meaningless. cargo build --release is the artifact.

2 ▸ Ownership, Borrowing and Lifetimes

Ownership is the rule system that lets Rust deallocate memory automatically without a garbage collector. This chapter explains the three ownership rules, the borrow rules that follow from them, slices as the canonical borrow, and lifetimes — the annotations that prove a reference stays valid.

2.1 Ownership: the three rules every type obeys

Every value in Rust is owned by exactly one variable, and when that variable goes out of scope the value is dropped. Assignment moves ownership, and no other mainstream language has this exact semantics.

The three rules, and the tree they build

Rule one: each value has exactly one owner. Rule two: when the owner goes out of scope, the value is dropped. Rule three: ownership can be transferred — moved — but there is never more than one binding holding the value. Together the rules make ownership a tree: one root, no sharing at the leaves, and drop order decided by the braces at compile time. That determinism is why Rust needs no garbage collector at all.

// Ownership is a tree: one owner per value, drop order decided by
// the scopes, no collector needed.

fn main() {
    let s1 = String::from("hello");   // s1 owns the heap buffer
    let s2 = s1;                      // ownership MOVES to s2
    // println!("{s1}");              // ERROR: use of moved value
    println!("{s2}");                 // s2 is the owner now
}

Move, clone and copy

Move is the default for heap types — String, Vec, Box, Rc. Clone is deep and explicit — s.clone() duplicates the buffer, and the name is always written out because it can be expensive. Copy types are bitwise-copied — integers, bools, chars, arrays and tuples of Copy types — and for them assignment behaves the way it does in C. The distinction is not memory layout; it is whether the type owns a resource that must be freed exactly once.

fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone();          // DEEP copy: a fresh buffer
    println!("{s1} {s2}");        // both valid, both own their own

    let x = 42;                   // i32 is Copy: assignment copies
    let y = x;
    println!("{x} {y}");          // both still valid
}

Which types are Copy, and how to ask the compiler

A type is Copy when it has no Drop implementation and no interior pointers — the compiler proves it, and you can ask the proof. std::mem::needs_drop reports whether a type's deallocation is mandatory; std::mem::size_of reports the stack size. The litmus test that matters is simpler: if a type would be broken by a bitwise copy, it is not Copy — a String copied bitwise would leave two owners of one buffer, so it is moved instead.

use std::mem::{needs_drop, size_of};

fn main() {
    println!("i64:    needs_drop={} size={}", needs_drop::<i64>(), size_of::<i64>());
    println!("String: needs_drop={} size={}", needs_drop::<String>(), size_of::<String>());
}

2.2 References and the borrow rules

A reference lets code read — or with &mut, write — a value without taking ownership. The two borrow rules make the system safe: you may have any number of shared borrows or one exclusive borrow, and a borrow must not outlive its referent.

References borrow without taking

Passing &s to a function hands it a read-only view; the function promises not to keep it beyond the call, and the caller keeps ownership. The signature &String is self-documenting — the function reads, it does not consume. This is the workhorse pattern of the whole language, and it is what lets a function compute a length without the caller losing the string.

fn calculate_length(s: &String) -> usize {
    s.len()     // read through the reference
}

fn main() {
    let s = String::from("hello");
    let len = calculate_length(&s);   // borrow: s keeps ownership
    println!("{s} has {len} chars");  // 5 — s is still usable
}

One mutable or many immutable

The second borrow rule, in one sentence: either any number of shared (&T) borrows or one exclusive (&mut T) borrow — never both at the same time. The rule exists because two readers can race nothing, while a reader plus a writer can read garbage mid-write. Modern Rust also uses non-lexical lifetimes: a borrow ends at its last use, not at the end of its scope, so the sequence below compiles because the shared borrow is already finished when the mutable one starts.

fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];            // shared borrow
    println!("{first}");          // last use: the borrow ends here

    let last = &mut v[2];         // exclusive borrow, later
    *last *= 10;
    println!("{:?}", v);          // [1, 2, 30]
}

The three failures, all caught at compile time

Each of these is silent undefined behaviour in C++ and a compile error in Rust: using a value after it has been moved; letting a reference outlive the value it points at; and mutating through one path while a shared borrow is alive. The borrow checker is never wrong about the mechanics. When it rejects your code, the correct response is to restructure — pass an index, return an owned value, or reorder the operations — rather than to fight it.

// 1) Use after move
//    let s = String::from("hi");
//    let t = s;               // s is moved into t
//    println!("{s}");         // ERROR: use of moved value
//
// 2) A reference outliving its referent
//    let r;
//    {
//        let s = String::from("hi");
//        r = &s;               // s dies here: r would dangle
//    }
//    println!("{r}");         // ERROR: does not live long enough
//
// 3) Mutating while borrowed
//    let mut v = vec![1, 2, 3];
//    let first = &v[0];
//    v.push(4);               // ERROR: cannot borrow as mutable
//    println!("{first}");
//
// The discipline: if the checker says no, restructure. Do not reach
// for unsafe, Rc<RefCell<T>>, or a clone in a hot loop as the first
// response.
Rc<RefCell<T>> is the classic escape hatch — and it moves the safety check from compile time to runtime, where a violation is a panic, not an error message. Use it for legitimate interior mutability with shared ownership, never as a way to silence the borrow checker.

2.3 Slices: a borrow that sees a run of elements

A slice is a reference to a contiguous run of elements — a pointer plus a length, with no ownership of the underlying storage. Slices are the standard way to look at a substring or a sub-vector without copying, and they come with bounds checked at runtime.

String slices

&str is the immutable view over a String's buffer, and string literals are &str pointing into the compiled binary. Slicing uses half-open ranges: &s[0..5] is characters at indexes 0, 1, 2, 3 and 4. The range index is a byte offset, and slicing panic guards it: cutting through the middle of a multi-byte UTF-8 character is an error, not silent corruption.

fn main() {
    let s = String::from("hello world");
    let hello = &s[0..5];     // half-open range: 0..=4
    let world = &s[6..11];
    println!("{hello} {world}");

    let whole: &str = &s;     // borrow the entire string
    println!("{whole}");
}

Array and vector slices

The same slice type works for arrays and vectors: &xs[1..4] and &v[2..] are both &[T]. A slice carries its length with it, so unlike a raw pointer it can never overrun — bounds are checked at access time. That is why so many functions take &[T] rather than a specific collection: any contiguous sequence of T qualifies.

fn main() {
    let xs = [10, 20, 30, 40, 50];
    let mid = &xs[1..4];         // [20, 30, 40]

    let v = vec![1, 2, 3, 4];
    let tail = &v[2..];          // [3, 4]

    println!("{mid:?} {tail:?}");
}

The slice borrow freezes its source

A slice is a borrow, so while it is alive the source cannot be mutated — mutation could invalidate the slice's assumption about the data. The compiler enforces it, which is exactly what prevents the classic vector-reallocation bug of other languages. When you genuinely need to mutate, end the borrow first (or let it end at its last use) and then change the collection.

fn main() {
    let mut v = vec![1, 2, 3];
    let slice = &v[..];          // the whole vector, borrowed
    println!("{slice:?}");
    // v.push(4);                // ERROR: cannot borrow as mutable
    //                           // while the slice borrow is alive
    drop(slice);                 // end the borrow explicitly
    v.push(4);                   // now allowed
    println!("{:?}", v);
}

2.4 Lifetimes, and when the borrow checker fights

A lifetime is a name for the scope in which a reference is valid. The compiler infers lifetimes in most cases; you annotate them when a function returns a reference derived from a parameter, or when a struct stores one.

Why most functions need no annotation

Three elision rules cover the common cases: each reference parameter gets its own lifetime; with exactly one input lifetime, every output reference inherits it; and with several inputs, an output borrows from &self. The rules are chosen so that the obvious reading — a function that takes one reference and returns one reference is borrowing from its input — never needs to be spelled out.

fn first_char(s: &str) -> &str {   // elided: the compiler infers
    s.get(..1).unwrap_or("")
}

fn main() {
    let w = first_char("hello");
    println!("{w}");               // h
}

Two inputs, one output: the annotation is required

When a function takes two reference parameters and returns a reference, elision cannot decide which one the result borrows from — so you say so: 'a ties the output to the shorter of the two inputs, and the compiler checks the guarantee at every call site. The same lifetime appears on structs holding references: Excerpt<'a> promises the struct does not outlive the string it borrows.

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

struct Excerpt<'a> {
    part: &'a str,
}

fn main() {
    let novel = String::from("Call me Ishmael.");
    let e = Excerpt { part: &novel[..4] };   // "Call"
    println!(
        "{} {}",
        longest(&novel, "Ishmael"),
        e.part
    );
}

The most common lifetime error

Returning a reference to a local — fn bad() -> &String building a String inside — is the error most people meet first, and the one the compiler explains best: "borrowed value does not live long enough". The fix is structural, not a cleverer annotation: return the owned value and let the caller own the result. A reference into a function's own locals can never be valid after the function returns, no matter how the lifetimes are written.

// The classic lifetime error: a reference to a local.
fn bad() -> &String {
    let s = String::from("hello");
    &s     // ERROR: `s` does not live long enough
}

// The fix: return the owned value, and the ownership moves out.
fn good() -> String {
    String::from("hello")   // the caller owns it now
}

Name lifetimes for their role; restructure when they fight

'a says nothing; 'input says what is being borrowed. Naming lifetimes for their role turns a wall of annotations into readable documentation, and it matters because lifetimes are not exotic — they appear in every function that returns a slice of a parameter. If the annotations keep fighting you, the fix is usually to change the shape: return an owned value, return an index or a key instead of a reference, or take the reference as a parameter and write through it. The borrow checker reflects structure; it does not invent it.

fn trimmed_len<'input>(text: &'input str) -> usize {
    text.trim().len()
}

fn main() {
    let s = String::from("  pad  ");
    println!("{}", trimmed_len(&s));   // 3
}
Lifetimes are a compile-time construct: no runtime metadata, no cost, no effect on the compiled code. They exist purely to give the checker the information it needs to prove your references are valid.

Rust's type system is where most of its safety lives. This chapter covers the scalar primitives, the two workhorse composite types — structs and enums — the Option and Result types that replace null and exceptions, pattern matching with match, and the conversion traits that move data between representations.

3.1 Primitives and scalar types

The scalar types are integers, floats, booleans, characters and the unit type. Their sizes are explicit in the type name, and — unlike C — Rust never chooses a width for you silently.

Integer widths and the default

Every integer type names its width and signedness: u8, i8, u16, i32, u64, i64, u128, isize and usize. The default for an unsuffixed literal is i32 — the deliberate choice of a size that fits the common case. Underscores in literals (1_000_000) are purely visual; overflow panics in debug builds and wraps in release, so pick a width that cannot overflow rather than relying on the wrap.

fn main() {
    let a: u8 = 255;                  // unsigned, 0..=255
    let b: i8 = -128;                 // signed, -128..=127
    let big: u64 = 18_446_744_073_709_551_615;  // max u64
    let x = 42;                       // inferred as i32
    println!("{a} {b} {big} {x}");
}

Floats, bool and char

There are two float types, f32 and f64, and the default is f64 — double precision, matching the IEEE 754 double. bool is true or false, and in arithmetic contexts it is not a number; conversions are explicit. char is a Unicode scalar value: four bytes wide, able to hold any single code point, and never half a character — which is why string indexing uses bytes and why char cannot be used to split a string by position blindly.

fn main() {
    let pi: f64 = 3.141_592_653_589_793;
    let e: f32 = 2.718_282;
    let done = true;                  // bool
    let heart = '♥';                  // char: a Unicode scalar value
    println!("{pi} {e} {done} {heart}");
}

Tuples, arrays and the unit

A tuple groups values of any types — ("rust", 2024) is a (&str, i32) — and destructures positionally. An array is a fixed-length run of one type, sized at compile time; the vector in chapter 5 is the growable version. The unit type () is the type with exactly one value, and it is the return type of functions that return nothing — which, in Rust, means they return ().

fn main() {
    let pair = ("rust", 2024);        // a tuple of (&str, i32)
    let (name, year) = pair;          // destructure positionally
    println!("{name} {year}");

    let xs = [1, 2, 3, 4, 5];         // array: fixed length, one type
    println!("{} items", xs.len());

    let unit = ();                    // the unit type: "no value here"
    println!("{unit:?}");
}

3.2 Structs and enums

Structs group named fields into one type; enums enumerate a closed set of variants, each of which may carry its own data. Together they give Rust algebraic data types: composition by naming, and choice by exhaustion.

Structs: named fields

A struct is declared with struct and constructed with field names, so field order never matters and a missing field is a compile error. Fields are independently mutable through the owning variable, and the struct update syntax ..u copies the untouched fields from another instance. A struct without fields is a unit struct — useful as a marker for traits- and type-level dispatch.

#[derive(Debug)]
struct User {
    name: String,
    age: u8,
    active: bool,
}

fn main() {
    let mut u = User {
        name: String::from("Amin"),
        age: 30,
        active: true,
    };
    u.active = false;                      // fields are independently mutable

    let younger = User { age: 29, ..u };   // struct update syntax
    println!("{:?}", younger);
}

Enums: closed sets of variants

An enum declares every value the type can hold, and the compiler knows all of them — that is what makes exhaustiveness checking possible. Each variant can carry different data: V4(u8, u8, u8, u8) carries four octets, V6(String) carries one string. This is how Rust models things that other languages model with class hierarchies or tagged unions, and the matching code is forced to handle every case.

// An enum is a closed set: the compiler knows every possible value.
enum IpAddr {
    V4(u8, u8, u8, u8),
    V6(String),
}

fn main() {
    let home = IpAddr::V4(127, 0, 0, 1);
    match home {
        IpAddr::V4(a, b, c, d) => println!("{a}.{b}.{c}.{d}"),
        IpAddr::V6(addr) => println!("{addr}"),
    }
}

Deriving behaviour instead of writing it

Traits like Debug, Clone and PartialEq have one canonical implementation per type, so the compiler generates it on request via #[derive(...)]. Deriving is not magic — a macro writes the same impl you would — but it is the difference between one line and twenty, and it is the fastest way to get printing, cloning and equality on your own types before you write the traits that are genuinely yours.

#[derive(Debug, Clone, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let a = Point { x: 1, y: 2 };
    let b = a.clone();           // from Clone
    println!("{:?}", a);         // from Debug
    assert_eq!(a, b);            // from PartialEq
}

3.3 Option and Result

Rust has no null and no exceptions. Absence is Option<T> — a value or nothing — and failure is Result<T, E> — a value or an error. Both are enums, so the compiler forces you to handle both cases wherever you use them.

Option: presence or absence

Option<T> is either Some(value) or None. Because it is a regular enum, there is no way to read a value that might be absent without acknowledging the possibility — the None case must be handled or explicitly ignored. Functions like Vec::get and str::find return Option specifically so that "not there" is a value you can branch on, not a crash.

fn first_word(s: &str) -> Option<&str> {
    for (i, &byte) in s.as_bytes().iter().enumerate() {
        if byte == b' ' {
            return Some(&s[..i]);
        }
    }
    Some(s)
}

fn main() {
    match first_word("hello world") {
        Some(w) => println!("first word: {w}"),
        None => println!("no space at all"),
    }
}

Result: success or error

Result<T, E> is Ok(value) or Err(error). It carries the failure reason with it, so the error type is part of the function's signature — the caller can see, before calling, exactly which failure modes exist. The exhaustive match below is the honest way to handle it; chapter 4 builds the ergonomics on top with the ? operator.

use std::fs;

fn main() {
    match fs::read_to_string("Cargo.toml") {
        Ok(text) => println!("{} lines", text.lines().count()),
        Err(e) => eprintln!("could not read file: {e}"),
    }
}

Combining them without panicking

map transforms the success case and leaves the failure untouched; unwrap_or supplies a default for absence; filter_map skips None values entirely. These combinators let you compose fallible steps into a pipeline where the failure policy is a single decision at the end, rather than a ladder of nested matches.

fn main() {
    // map + unwrap_or: turn a fallible step into a plain value
    let doubled = "42".parse::<i32>().map(|n| n * 2).unwrap_or(0);
    println!("{doubled}");   // 84

    // filter_map: skip the values that fail to parse
    let nums = ["1", "two", "3"];
    let sum: i32 = nums.iter().filter_map(|s| s.parse().ok()).sum();
    println!("{sum}");       // 4: "two" contributes nothing
}
The combinators (map, and_then, unwrap_or_else) are the same names on Option and Result. Learn them once with Option and the Result versions are a free upgrade.

3.4 Match and destructuring

match is the switch statement done properly: exhaustive, expression-valued, and able to pull data out of what it matches. Destructuring is the same mechanism applied to structs, tuples and enums.

match must be exhaustive

A match must cover every possible value — the compiler refuses to compile a non-exhaustive one — so adding a variant to an enum forces every site that matches on it to be revisited. Arms can combine values with |, match ranges with ..=, and fall back with the wildcard _. Because match is an expression, it returns a value, which is how branching becomes data.

fn classify(n: i32) -> &'static str {
    match n {
        0 => "zero",
        1 | 2 => "tiny",
        3..=9 => "small",
        _ => "big",        // the wildcard satisfies exhaustiveness
    }
}

fn main() {
    for n in [0, 2, 5, 42] {
        println!("{n}: {}", classify(n));
    }
}

Destructuring structs, tuples and enums

Patterns can reach into values: let Point { x, y } = p pulls the fields out, Shape::Rect { w, h } extracts the variant's data, and tuple patterns destructure positionally. Destructuring by reference keeps the original usable; destructuring by value moves the pieces out. The same pattern syntax works in match arms, if let, and let else.

struct Point {
    x: i32,
    y: i32,
}

enum Shape {
    Circle { r: f64 },
    Rect { w: f64, h: f64 },
}

fn main() {
    let p = Point { x: 10, y: 20 };
    let Point { x, y } = p;              // destructure the struct
    println!("{x} {y}");

    let s = Shape::Rect { w: 2.0, h: 3.0 };
    match s {
        Shape::Circle { r } => println!("circle radius {r}"),
        Shape::Rect { w, h } => println!("rect area {}", w * h),
    }
}

Guards and @ bindings

A guard, x if condition, adds a boolean test to an arm without changing what the pattern binds. The @ binding captures a value and checks a pattern on it at the same time — n @ 1..=9 both matches the range and binds the value so the arm can use it. Guards are evaluated in order top to bottom, so put the most specific conditions first.

fn main() {
    for n in 1..=15 {
        match n {
            x if x % 15 == 0 => println!("fizzbuzz"),
            x if x % 3 == 0 => println!("fizz"),
            x if x % 5 == 0 => println!("buzz"),
            x @ 1..=9 => println!("single digit {x}"),
            x => println!("{x}"),
        }
    }
}

3.5 Type conversions: From, Into and as

Rust converts between types in three deliberately different ways: as for lossy numeric casts, From/Into for infallible conversions you design, and parse for fallible string conversion. The distinction between them is the difference between "I know this is safe" and "the compiler knows".

as casts, and where they truncate

as is the blunt instrument: narrowing an integer wraps modulo the target width, casting a float to an integer truncates toward zero, and char to u8 gives the code point. Rust makes these explicit so the loss is visible at the call site — but as never checks, so prefer conversions that can fail (try_from) when the input is not a literal you control.

fn main() {
    let big: i64 = 300;
    let small = big as u8;        // 300 -> 44: wraps modulo 256
    println!("{small}");

    let x = 3.9_f64 as i32;       // truncates toward zero: 3
    println!("{x}");

    let c = 'A' as u8;            // 65: the code point
    println!("{c}");
}

From and Into

From<T> for U is the authoritative conversion: implement it once, and Into<U> arrives for free — every U::from(t) can be written t.into(). The direction matters: implement From for the target type you want to be able to construct from others. The std library ships hundreds of these, so String::from, Vec::from and friends are already in scope for most ordinary conversions.

struct Celsius(f64);

impl From<f64> for Celsius {
    fn from(c: f64) -> Self {
        Celsius(c)
    }
}

fn main() {
    let temp = Celsius::from(21.5);
    let temp2: Celsius = 18.0.into();   // Into comes free with From
    println!("{} {}", temp.0, temp2.0);
}

Parsing strings: FromStr and parse

"42".parse() implements FromStr, converting a string into a target type if the text is well formed — and failing with a descriptive error if it is not. The target type is almost always written on the left: let n: i32 = "42".parse(). Numbers, booleans, chars and SocketAddr all implement FromStr, as can your own types via impl FromStr for MyType.

fn main() {
    let n: i32 = "42".parse().unwrap();
    let f: f64 = "3.14".parse().unwrap();
    let flag: bool = "true".parse().unwrap();
    let port: u16 = "8080".parse().unwrap();

    // a failed parse returns an Err, never a crash:
    let bad: i32 = "not a number".parse().unwrap_or(-1);
    println!("{n} {f} {flag} {port} {bad}");
}
The error type of a failed parse is nearly always std::num::ParseIntError (or an equivalent). Its Display message names the offending string, which is exactly what you want to log.

4 ▸ Error Handling

4.1 Result and the ? operator4.2 unwrap, expect and when they are acceptable4.3 Custom error types4.4 Panic vs error, and adding context

Rust has no exceptions: recoverable failure is a returned value (Result), and unrecoverable failure is a panic. This chapter covers the ? operator that threads errors through a call stack, the panicking accessors and when they are justified, hand-written and derived error types, and the distinction between an error and a panic.

4.1 Result and the ? operator

The return type is the function's contract: Result<T, E> says this call may fail, and the ? operator converts failure into an early return without obscuring the happy path.

The Result type is the function's contract

Because failure is encoded in the return type, a caller can see, before calling, what can go wrong and what the error values are. There is no hidden control flow and no exception to forget to catch. The cost is that every fallible call must be acknowledged — which is why libraries carefully choose which operations return Result and which are infallible by construction.

use std::fs;

// The contract: either produce a String or report why not.
fn read_input(path: &str) -> Result<String, std::io::Error> {
    fs::read_to_string(path)
}

fn main() {
    match read_input("input.txt") {
        Ok(text) => println!("{} chars", text.len()),
        Err(e) => eprintln!("failed: {e}"),
    }
}

The ? operator

Hand-written matches on every Result would bury the logic in boilerplate, so ? does the obvious thing: on Ok(v) it yields v; on Err(e) it returns Err(e.into()) from the current function. The into() is the interesting part — it converts the error into whatever the function's return type demands, provided a From implementation exists (chapter 4.3 shows how to build one). A function that uses ? must itself return a Result (or Option).

use std::fs;

fn first_line(path: &str) -> Result<String, std::io::Error> {
    let text = fs::read_to_string(path)?;   // early return on Err
    Ok(text.lines().next().unwrap_or("").to_string())
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let line = first_line("Cargo.toml")?;
    println!("{line}");
    Ok(())
}

? in main: Box<dyn Error>

main may return a Result too, and when it does, the error is printed and the process exits with a non-zero code. The conventional catch-all type is Box<dyn std::error::Error> — a trait object that can hold any error — which is exactly right for a binary that just wants to report failure and stop. When you need to distinguish errors for exit codes or continued execution, return a concrete error type instead.

use std::env;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let args: Vec<String> = env::args().collect();
    if args.len() < 2 {
        eprintln!("usage: {} <file>", args[0]);
        std::process::exit(2);       // usage error, not a Result
    }
    let text = std::fs::read_to_string(&args[1])?;
    println!("{} lines", text.lines().count());
    Ok(())
}

4.2 unwrap, expect and when they are acceptable

unwrap and expect are the panicking accessors: they return the Ok/Some value and panic on the error case. They are not wrong — but they are only right where failure is genuinely impossible.

unwrap: panic on error

unwrap says "I am certain this cannot fail", and when the certainty is wrong it aborts with a generic message naming the operation. That is perfect for literals and invariants, and fatal for anything user-controlled — a malformed file name becomes a crash instead of a handled error. The rule of thumb: unwrap on values that come from your own code's constants, never on values that crossed a trust boundary.

fn main() {
    // "10" is a literal: the parse cannot fail, unwrap is honest
    let n: i32 = "10".parse().unwrap();
    println!("{n}");

    // a user-supplied string would deserve a Result instead
    let raw = std::env::args().nth(1).unwrap_or_else(|| "10".into());
    let m: i32 = raw.parse().unwrap_or(0);   // fall back, don't panic
    println!("{m}");
}

expect: the message that survives

expect is unwrap with a caller-written message that appears in the panic output — the difference between "called Option::unwrap() on a None value" and "server requires a port argument". The message is your future self's debugging context, so it should state the invariant, not the panic: "port must be a number in 0..=65535" beats "parse failed". It still panics; it just explains better.

fn main() {
    let raw = std::env::args().nth(1);
    let port: u16 = raw
        .expect("usage: server <port>")        // None: custom message
        .parse()
        .expect("port must be a number 0-65535");
    println!("listening on {port}");
}

Graceful fallbacks before you panic

Most "unwrap" sites are really asking for a policy: a default, a skip, a retry. unwrap_or supplies a default value, unwrap_or_else computes one lazily, ok/err convert to Option, and unwrap_or_default leans on the type's Default. Reaching for these first — and keeping unwrap for true invariants — makes the crate's panic sites countable on one hand.

fn main() {
    let port: u16 = "8080".parse().unwrap_or(8080);   // fallback default
    let home = std::env::var("HOME")
        .ok()                                          // Result -> Option
        .unwrap_or_else(|| "/home/guest".to_string());
    let jobs: usize = std::env::var("JOBS")
        .ok()
        .and_then(|s| s.parse().ok())
        .unwrap_or(4);
    println!("{port} {home} {jobs}");
}

4.3 Custom error types

A hand-written error type is an enum whose variants name every way the operation can fail. It is matchable, testable, and — with From impls — the thing the ? operator converts into.

An error enum with Display and Error

The two implementations a custom error needs are Display — the human-readable message, used by println! and logging — and std::error::Error, the marker that lets the type be used as Box<dyn Error> and that provides source() for error chaining. The enum's variants document the failure modes in the code itself: reading them is reading the function's failure contract.

use std::fmt;

#[derive(Debug)]
enum CliError {
    Io(std::io::Error),
    Parse(std::num::ParseIntError),
    Empty,
}

impl fmt::Display for CliError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            CliError::Io(e) => write!(f, "io error: {e}"),
            CliError::Parse(e) => write!(f, "parse error: {e}"),
            CliError::Empty => write!(f, "no input given"),
        }
    }
}

impl std::error::Error for CliError {}

fn main() {
    println!("{}", CliError::Empty);
}

From impls let ? convert between errors

Once From<std::io::Error> for AppError exists, every ? in the function converts an underlying error into your error type automatically. This is how a function that touches both the filesystem and the parser can return one error type while ? handles both conversions inline. Without the From impl, the same code needs explicit map_err at every call site.

use std::fmt;

#[derive(Debug)]
enum AppError {
    Io(std::io::Error),
    Parse(std::num::ParseIntError),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AppError::Io(e) => write!(f, "io: {e}"),
            AppError::Parse(e) => write!(f, "parse: {e}"),
        }
    }
}

impl std::error::Error for AppError {}

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> Self {
        AppError::Io(e)
    }
}

impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> Self {
        AppError::Parse(e)
    }
}

fn load() -> Result<i32, AppError> {
    let raw = std::fs::read_to_string("n.txt")?;   // io::Error -> AppError
    let n: i32 = raw.trim().parse()?;              // ParseIntError too
    Ok(n)
}

fn main() {
    println!("{:?}", load());
}

thiserror: derive the boilerplate

The thiserror crate derives Display, Error and From from declarative annotations, collapsing the three impls above into a derive. The #[error(...)] attribute is the Display message with field interpolation; #[from] generates the From impl; #[error(transparent)] delegates for wrapper variants. This is the standard choice for library error types — the kind callers will match on.

use thiserror::Error;

#[derive(Debug, Error)]
enum ConfigError {
    #[error("missing key `{key}`")]
    Missing { key: String },

    #[error("invalid value for `{key}`: {value}")]
    Invalid { key: String, value: String },

    #[error(transparent)]
    Io(#[from] std::io::Error),
}

fn main() {
    let err = ConfigError::Missing { key: "host".into() };
    println!("{err}");     // missing key `host`
}

4.4 Panic vs error, and adding context

The dividing line is simple: if the program can recover, return a Result; if the program's own invariant is broken and continuing would be wrong, panic. Panics are for programmer errors; Result is for user errors.

panic!, unreachable! and assert!

panic! aborts execution with a message; unreachable!() documents a branch the logic says can never happen (a bug if it is reached); assert! and assert_eq! verify invariants and panic with the failing values when they break. All three are how you encode "this state is impossible" so that a future refactor that makes it possible fails loudly instead of corrupting data.

fn main() {
    let xs = [1, 2, 3];
    let i = 5;
    if i >= xs.len() {
        // a programmer error: an invariant WE broke, not the user
        panic!("index {i} out of bounds (len {})", xs.len());
    }
    println!("{}", xs[i]);
}

// assert! is the same idea in testable form:
fn main2() {
    let total: i32 = (1..=5).sum();
    assert_eq!(total, 15, "1+2+3+4+5 must equal 15");
    println!("{total}");
}

anyhow and context for application errors

Binaries do not match on their own errors nearly as often as libraries do — they report them. anyhow::Result<T> wraps an arbitrary error, and .context("...") attaches a human explanation to the chain: failed to load config: could not read data/config.toml: No such file or directory. The context is the layer's story of what it was doing; the chain beneath it is the low-level cause. Libraries use thiserror; applications use anyhow — that division is the ecosystem convention.

use anyhow::{Context, Result};

fn load() -> Result<String> {
    let path = "data/config.toml";
    let raw = std::fs::read_to_string(path)
        .with_context(|| format!("could not read {path}"))?;
    Ok(raw)
}

fn main() -> Result<()> {
    let cfg = load()?;
    println!("{} bytes", cfg.len());
    Ok(())
}

Choosing panic or Result

Two questions decide it. First: did the caller pass in bad data? Then it is a Result — the caller should be able to recover, retry or show a message. Second: did your own code violate a contract — an index that is out of range for data you control, a None where the logic says Some? Then panic, because the correct response is a fix, not handling. The pattern to avoid is panicking on ordinary user input, which turns every bad file into a crash and every crash into lost work.

// A library boundary: bad input is Err, not a panic.
fn divide(a: i64, b: i64) -> Result<i64, String> {
    if b == 0 {
        return Err("division by zero".into());
    }
    Ok(a / b)
}

fn main() {
    match divide(10, 0) {
        Ok(q) => println!("{q}"),
        Err(e) => eprintln!("{e}"),   // recovered: no crash
    }
}
A panic in a spawned thread does not abort the process — join() returns an Err, and everything else keeps running. If a panic must stop the whole service, propagate it back through join and exit deliberately; do not assume a thread panic is process-wide.

Most programs are plumbing: data in, data transformed, data out. This chapter covers the standard collections — Vec, HashMap, HashSet — the owned vs borrowed string distinction, and the iterator pipeline that turns collections into transformations without the intermediate allocations of imperative code.

5.1 Vec: the growable sequence

Vec<T> is a contiguous, growable buffer of T — the array you can resize. It is the default sequence type, and most iteration in Rust starts from one.

Creating and indexing

vec![1, 2, 3] is the idiomatic constructor; vec![0; 5] repeats a value five times; Vec::new() starts empty. Indexing with v[i] reads from the buffer directly, and slicing &v[1..3] borrows a run of elements. The capacity is distinct from the length: the buffer may hold more than the logical length, which is what makes push cheap on average.

fn main() {
    let mut v: Vec<i32> = Vec::new();
    v.push(1);
    v.push(2);

    let zeros = vec![0; 5];          // five zeroes
    let ab = vec![1, 2, 3];
    println!("{} {} {:?}", v.len(), zeros.len(), &ab[1..3]);
}

push, pop, insert, remove, extend

push appends and pop removes from the end — both O(1) amortised. insert and remove work at any position by shifting the following elements, so they are O(n): use them when the vector is small or the position genuinely matters. extend appends a whole iterator, which is how you concatenate collections without a loop.

fn main() {
    let mut v = vec![10, 20, 30];
    v.push(40);                 // [10, 20, 30, 40]
    v.insert(1, 15);            // [10, 15, 20, 30, 40]
    let last = v.pop().unwrap();// 40
    v.remove(0);                // drop the first element
    v.extend([50, 60]);
    v.sort();
    println!("{last} {v:?}");   // 40 [15, 20, 30, 50, 60]
}

Indexing vs get: panic versus Option

v[i] with an out-of-range index panics; v.get(i) returns Option instead. The choice is the same policy as chapter 4: use the panicking form when the index is an invariant, the checked form when it crosses a boundary. first and last return Options for the endpoints, and iter, iter_mut and into_iter give borrow, mutable borrow and owned iteration respectively.

fn main() {
    let v = vec![10, 20, 30];

    match v.get(9) {
        Some(x) => println!("{x}"),
        None => println!("index 9 out of bounds — no panic"),
    }

    let first = v.first().copied().unwrap_or(0);
    let last = v.last().copied().unwrap_or(0);
    println!("{first} {last}");
}
Never reach for insert(0, ...) or remove(0) in a hot path on a big vector — every call shifts every element. If the front matters, consider VecDeque, which is the ring buffer type made for exactly that.

5.2 HashMap and HashSet

A HashMap<K, V> maps keys to values with average O(1) lookup; a HashSet<T> is a HashMap whose values are the unit type — membership is the whole value.

HashMap basics

insert overwrites an existing key; get returns Option<&V> — the Option again, so absence is a handled possibility, and copied turns the borrowed value into an owned V when V: Copy. contains_key is the pure membership test. Iteration visits in hash order, which is deliberate and non-deterministic, so anything that must print stably should collect and sort first.

use std::collections::HashMap;

fn main() {
    let mut scores = HashMap::new();
    scores.insert("blue", 10);
    scores.insert("red", 5);
    scores.insert("blue", 12);       // overwrites the earlier blue

    for (team, pts) in &scores {
        println!("{team}: {pts}");
    }

    let blue = scores.get("blue").copied().unwrap_or(0);
    println!("blue has {blue}");
}

The entry API: read-modify-write in one step

The classic counting bug — if let Some(v) = map.get_mut(k) { *v += 1 } else { map.insert(k, 1) } — does two lookups and a lot of noise. entry(k) borrows a slot once: or_insert(0) returns a &mut V that is either the existing value or a freshly inserted default, and the += 1 writes through it. One lookup, one mutation, no duplicated logic.

use std::collections::HashMap;

fn main() {
    let mut counts = HashMap::new();
    for word in "the cat and the dog and the bird".split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }
    println!("the={} dog={}", counts["the"], counts["dog"]);
}
entry(k).or_insert_with(|| expensive_default()) computes the default lazily, only when the key is absent — the map version of unwrap_or_else.

HashSet: uniqueness and set maths

A HashSet rejects duplicates on insert — a second insert of an equal value is a no-op — and that single property makes it the tool of choice for deduplication and membership checks. The set operations union, intersection and difference return iterators, which is why the sample collects them into vectors for printing. Filtering a stream by "seen before?" is the canonical use.

use std::collections::HashSet;

fn main() {
    let a: HashSet<i32> = [1, 2, 3].into_iter().collect();
    let b: HashSet<i32> = [2, 3, 4].into_iter().collect();

    let all: Vec<i32> = a.union(&b).copied().collect();
    let common: Vec<i32> = a.intersection(&b).copied().collect();
    let only_in_a: Vec<i32> = a.difference(&b).copied().collect();
    println!("{all:?} {common:?} {only_in_a:?}");
}

5.3 String vs &str

Rust has two string types and the difference is ownership: String owns a growable heap buffer; &str is an immutable view into a buffer owned by someone else. Getting the boundary right is most of the story.

The difference is ownership

String owns; &str borrows. String literals are &str baked into the binary, and &s on a String gives a &str view of its buffer. Functions therefore take &str when they only need to read text — that is what most functions should do — and return String when they must produce text the caller will own. Converting between them is cheap in the borrowing direction and an allocation in the owning direction.

fn main() {
    let owned = String::from("hello");   // owns a heap buffer
    let borrowed: &str = &owned;         // a view; no allocation
    let literal: &str = "hello";         // points into the binary
    println!("{borrowed} {literal}");
}

Building strings efficiently

push_str appends a slice and push appends a single char; format! is the convenient one-shot builder; and joining an iterator of owned strings via collect then join is the idiomatic way to build a delimited list. None of this is slow in absolute terms — a String grows geometrically, so appending is amortised O(1) — but a format! inside a hot loop allocates every iteration, which is where the "one pass, then join" shape wins.

fn main() {
    let mut out = String::new();
    for i in 0..10 {
        out.push_str(&format!("{i} "));   // 10 small allocations
    }
    out.push('!');

    // one pass, one allocation, then a single join:
    let joined = (0..10)
        .map(|i| i.to_string())
        .collect::<Vec<_>>()
        .join(", ");

    println!("{out}");
    println!("{joined}");
}

UTF-8: bytes versus chars

A String is UTF-8, so s.len() counts bytes, not characters — "héllo" is 6 bytes and 5 chars because é is two bytes. s.chars() iterates code points and s.char_indices() gives the byte offset of each. Direct indexing s[0] is a compile-time-ish runtime error, because byte 0 might land inside a multi-byte character; slicing must fall on a character boundary, which is what s.get(..n) checks safely.

fn main() {
    let s = "héllo";
    println!("bytes: {}", s.len());            // 6: é is two bytes
    println!("chars: {}", s.chars().count());  // 5
    for (i, ch) in s.char_indices() {
        println!("byte {i}: {ch}");
    }
    // s[0] would be an error: indexing must land on a char boundary.
    // s.get(..2) returns Some("hé") — the checked alternative.
}

5.4 Iterators, adaptors and closures

Iterators are the engine of idiomatic Rust: a lazy sequence of items, a set of adaptors that transform the sequence, and collect that turns the result back into a concrete collection. Closures are the small anonymous functions the adaptors take.

Iterators are lazy; next advances

Creating an iterator — v.iter(), s.chars(), 1..=10 — runs nothing. Values are produced one at a time as the iterator is consumed, by calling next() until it returns None. That laziness is what makes infinite iterators like (0..) safe to construct: nothing is generated until an adaptor pulls, and take(3) pulls exactly three times.

fn main() {
    let v = vec![1, 2, 3];
    let it = v.iter();                 // lazy: nothing has run yet
    for n in it {                      // iterating pulls the values
        println!("{n}");
    }

    let mut it2 = [10, 20].iter();     // drive it manually:
    println!("{:?}", it2.next());      // Some(10)
    println!("{:?}", it2.next());      // Some(20)
    println!("{:?}", it2.next());      // None — the iterator is spent
}

map, filter, fold, take

Adaptors (map, filter, fold, take, skip, enumerate, zip) take one iterator and return another, and they chain naturally. map transforms each item, filter keeps items passing a predicate, fold accumulates a state across the sequence — the general form of sums and products — and take truncates. Each adaptor is a small struct that implements Iterator, so the whole chain compiles to a single fused loop with no intermediate collections.

fn main() {
    let evens: Vec<i32> = (1..=10).filter(|n| n % 2 == 0).collect();
    let sum: i32 = (1..=100).map(|n| n * n).sum();
    let product: i32 = (1..=5).fold(1, |acc, n| acc * n);
    let first: Vec<i32> = (0..).take(3).collect();
    println!("{evens:?} {sum} {product} {first:?}");
}

Collecting and consuming

Adaptors are lazy; collect is where the pipeline becomes data. Its target type is inferred from the binding: collect::<Vec<_>>() is the explicitness you need when inference cannot see the collection type. The consuming methods (sum, product, min, max, count, any, all) pull the whole iterator to produce one value. The iterator pipeline exists so that filter, map and sum describe a transformation without building the intermediate vectors a naive imperative version would.

fn main() {
    let chars: Vec<char> = "hello".chars().collect();
    let words: Vec<String> =
        "a b c".split_whitespace().map(String::from).collect();
    let total: i32 = [1, 2, 3].into_iter().sum();
    let max = [4, 9, 1].into_iter().max();
    let has_big = [4, 9, 1].iter().any(|n| *n > 5);

    println!("{chars:?} {words:?} {total} {max:?} {has_big}");
}

Closures: capture, borrow, move

A closure is an anonymous function that can capture variables from its environment. By default it borrows them; move makes it take ownership — mandatory when the closure outlives the scope, as with threads in chapter 7. A closure's capture style is inferred from its body: reading base borrows it, and that borrowed value is held for as long as the closure lives. Closures that capture nothing are usable anywhere a function pointer is.

fn main() {
    let base = 10;                    // captured by reference
    let add_base = |n: i32| n + base;
    println!("{}", add_base(5));      // 15

    let text = String::from("data");  // moved in, not borrowed
    let take = move || println!("{text}");
    take();
    // println!("{text}");            // ERROR: moved into the closure
}
The pipeline looks like it allocates a list per step; it does not. map(...).filter(...).sum() compiles to one loop over the source — the iterator types are erased to a single fused state machine.

Programs grow by being split. This chapter covers the module system that splits a crate into files, the impl blocks that attach behaviour to types, and the trait system that provides polymorphism without inheritance — with generics for the statically dispatched case and dyn Trait for the dynamically dispatched one.

6.1 Modules and visibility

A module is a namespace with a privacy boundary. The module tree mirrors the directory layout, and pub is the only way to let the outside world see what is inside.

A module tree mirrors the filesystem

The crate root is src/main.rs (a binary) or src/lib.rs (a library). A pub mod db; declaration in the root pulls in src/db.rs, and a nested pub mod pool; inside it pulls in src/db/pool.rs — or the directory form src/db/mod.rs. The path mylib::db::pool::connect is the same name written down as nested modules; there is no other lookup step. Modest crates can skip files entirely with inline mod blocks; files are for the ones that grow.

// A module tree mirrors the filesystem, but inline modules compile
// in one file — handy for sketching before you split files out.
mod db {
    pub mod pool {
        pub fn connect(conn: &str) -> bool {
            !conn.is_empty()
        }
    }
}

fn main() {
    println!("{}", db::pool::connect("postgres://db"));   // true
}

// With real files the same path is:  src/db.rs  +  src/db/pool.rs
//   // src/lib.rs
//   pub mod db;      // src/db.rs (or src/db/mod.rs)
//   pub mod http;

pub gates what the outside sees

Privacy in Rust is item-level: everything is private to its module unless marked pub, and a private item is invisible to every module that is not its descendant. That means a module's internals — helper functions, implementation details, intermediate types — can change freely without breaking callers, because callers cannot name them at all. The public surface of a module is exactly its pub items, and that surface is the module's contract.

mod secret {                // private: invisible outside this crate
    pub fn hidden() -> i32 { 1 }
}

pub mod math {
    pub fn double(x: i32) -> i32 { x * 2 }
    fn helper(x: i32) -> i32 { x + 1 }   // private to math
}

fn main() {
    // use mylib::math::double; // OK (a sibling crate)
    // use mylib::secret;       // ERROR: module `secret` is private
    println!("{}", math::double(21));    // 42
    // println!("{}", math::helper(1));  // ERROR: private function
}

use, as, and re-exports

use brings a path into scope; as renames it to avoid collisions or shorten it; pub use imports and re-exports — the classic pattern of a library exposing its façade: pub use db::pool::Pool; lets users write my_lib::Pool and keeps the internal path private. The prelude is a fixed set of uses the compiler applies to every file, which is why Option, Result, String and Vec need no import.

use std::collections::HashMap as Map;   // rename on import

fn main() {
    let mut m = Map::new();
    m.insert("k", 1);
    println!("{}", m.len());
}

// re-export (typically in src/lib.rs):
//   pub use db::pool::Pool;
// then users write Pool, never the private full path.

6.2 impl blocks: methods and associated functions

An impl block attaches functions to a type. Methods take self in one of three forms; associated functions take no self and are called on the type itself.

Methods take self

A method is a function whose first parameter is self, and Rust's method-call syntax r.area() automatically borrows or moves the receiver to match the self form. Methods live in the impl block, so the type's behaviour is written next to its data. The &self receiver is the common case: the method reads the instance and leaves it in place.

struct Rectangle {
    w: f64,
    h: f64,
}

impl Rectangle {
    fn area(&self) -> f64 {          // &self: read-only method
        self.w * self.h
    }

    fn scale(&mut self, factor: f64) {   // &mut self: mutating method
        self.w *= factor;
        self.h *= factor;
    }
}

fn main() {
    let mut r = Rectangle { w: 3.0, h: 4.0 };
    println!("{}", r.area());       // 12
    r.scale(2.0);
    println!("{}", r.area());       // 48
}

Associated functions: new and Self

An associated function has no self and is called on the type: Circle::new(2.0). The conventional one is new, a constructor that returns Self — the type name spelled generically, so it stays correct if the type is renamed. Self in an impl block always means "the type this block is for".

struct Circle {
    r: f64,
}

impl Circle {
    fn new(r: f64) -> Self {        // constructor: no self
        Circle { r }
    }

    fn pi() -> f64 {
        std::f64::consts::PI
    }
}

fn main() {
    let c = Circle::new(2.0);
    println!("r={} area={}", c.r, Circle::pi() * c.r * c.r);
}

self, &self and &mut self

The three receivers encode the effect on the instance: &self reads, &mut self mutates in place, self consumes — the method takes ownership and the instance is gone afterwards, which is how builders and into_* conversions work. Choosing the receiver is part of the API design: a consuming method is a promise that the caller will not need the value again.

struct Counter {
    n: i32,
}

impl Counter {
    fn new() -> Self { Counter { n: 0 } }
    fn get(&self) -> i32 { self.n }         // read
    fn bump(&mut self) { self.n += 1; }     // write in place
    fn into_parts(self) -> i32 { self.n }   // consume
}

fn main() {
    let mut c = Counter::new();
    c.bump();
    c.bump();
    println!("{}", c.get());        // 2
    let n = c.into_parts();         // c is moved, gone for good
    println!("{n}");
}

6.3 Traits: definition and implementation

A trait is a collection of methods that a type can implement — shared behaviour without a base class. A type can implement any number of traits, and a trait can require other traits.

Defining a trait, with defaults

A trait declaration lists the method signatures implementors must provide. Methods with a body are defaults: implementors inherit them and may override. This is how a library ships one canonical behaviour while letting specialised types replace it. Trait methods take &self like regular methods, which is what lets them read the implementing instance.

// A trait is a contract: implementors must provide these methods.
trait Draw {
    fn draw(&self);

    // A default implementation: implementors may inherit or override.
    fn bounding_box(&self) -> (f64, f64, f64, f64) {
        (0.0, 0.0, 100.0, 100.0)
    }
}

Implementing a trait for your type

impl Draw for Circle is explicit: there is no implicit trait satisfaction like Go's interfaces — a type is opted in by writing the block. The compiler checks the signatures against the trait declaration, so a wrong parameter type is a compile error at the impl, not a surprise at the call site. A type can implement many traits, and overriding only the methods that need customising is fine — the rest stay default.

struct Circle {
    x: f64,
    y: f64,
    r: f64,
}

impl Draw for Circle {
    fn draw(&self) {
        println!("circle at ({}, {}) radius {}", self.x, self.y, self.r);
    }
    // bounding_box stays default
}

fn main() {
    let c = Circle { x: 1.0, y: 1.0, r: 5.0 };
    c.draw();
}

The orphan rule and the newtype wrapper

You may implement your trait for their type, or their trait for your type — but not their trait for their type, because then two crates could implement the same pair differently and the compiler could not choose. The workaround for "I want Display on Vec<i32>" is the newtype: a one-field struct that wraps the foreign type, making it yours. The wrapper costs nothing at runtime; the field access self.0 is the price you pay.

// The orphan rule: YOUR trait for THEIR type, or THEIR trait for
// YOUR type — but never their trait for their type.
//
// impl std::fmt::Display for Vec<i32>   // ERROR: both foreign
//
// The newtype wrapper makes a foreign type YOUR type:
struct MyVec(Vec<i32>);

impl std::fmt::Display for MyVec {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        let inner = self.0
            .iter()
            .map(|x| x.to_string())
            .collect::<Vec<_>>()
            .join(", ");
        write!(f, "[{inner}]")
    }
}

fn main() {
    println!("{}", MyVec(vec![1, 2, 3]));   // [1, 2, 3]
}

6.4 Generic bounds and trait objects

A generic function with a trait bound is monomorphised at compile time — one specialised copy per concrete type, no runtime cost. dyn Trait is the dynamically dispatched alternative, stored behind a pointer, for when the concrete types cannot be known in advance.

Generic functions with trait bounds

fn render<T: Draw>(item: &T) accepts any type that implements Draw. The compiler generates a specialised version for each type that satisfies the bound — render(&circle) becomes render_Circle with Circle::draw inlined — which is why generics have no runtime overhead. The cost is code size: N concrete types mean N specialised copies of the function. For closed sets of types, generics are always the right call.

fn render<T: Draw>(item: &T) {
    item.draw();
}

fn main() {
    let c = Circle { x: 0.0, y: 0.0, r: 2.0 };
    render(&c);   // monomorphised to render_Circle
}
Prefer generics with bounds for closed sets of types (you know every implementor) and dyn Trait for open sets (plugins, user-registered types). A generic version is always faster because it is monomorphised.

where clauses keep readable bounds

Multiple bounds quickly overflow the signature line — <T: Clone + Debug + PartialEq, U: Display> is hard to scan. A where clause moves the bounds below the signature, lines them up, and reads like a constraint list, which is exactly what it is. The compiler treats both spellings identically; the choice is readability.

use std::fmt::Display;

fn announce<T>(msg: &str, value: &T)
where
    T: Display,
{
    println!("{msg}: {value}");
}

fn main() {
    announce("score", &99_u32);
    announce("name", &String::from("Amin"));
}

dyn Trait: the trait object

Sometimes the concrete types genuinely cannot be a closed set — a collection of shapes, a registry of handlers — and the answer is a trait object: a pointer to a value plus a pointer to its implementation's method table. &dyn Draw borrows one; Box<dyn Draw> owns one. A trait object can only hold the methods of one trait, so the collection needs the trait, not the type — and the price of the flexibility is a virtual call per method plus an allocation for the Box.

fn describe(item: &dyn Draw) {
    item.draw();
    println!("box: {:?}", item.bounding_box());
}

fn main() {
    // different concrete types behind one trait-object type
    let shapes: Vec<Box<dyn Draw>> = vec![
        Box::new(Circle { x: 0.0, y: 0.0, r: 1.0 }),
        Box::new(Circle { x: 3.0, y: 0.0, r: 2.0 }),
    ];
    for s in &shapes {
        describe(s.as_ref());
    }
}

// Without the Box the compiler says "the size for values of type
// `dyn Draw` cannot be known at compile time" — that is the error
// that tells you to put the trait object behind a pointer.
A Vec<dyn Draw> without Box is the trait-object beginner error: trait objects have unknown size, so they must live behind a pointer. The compiler's message names exactly that — read the whole diagnostic before reacting.

7.1 Threads

Rust's threads are OS threads — no green threading by default — and the borrow checker applies across thread boundaries, which is the whole safety story: a data race is a compile error, not a heisenbug.

thread::spawn and the move closure

std::thread::spawn takes a closure and runs it on a new OS thread. The closure must own everything it uses — the thread may outlive the caller's scope — which is why move appears on almost every spawn: it forces the captured values inside the closure. The spawned thread runs concurrently with the caller, and there is no automatic wait; if the main thread ends first, the process exits and the spawned threads are cut off.

use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=5 {
            println!("worker: {i}");
        }
    });
    for i in 1..=3 {
        println!("main: {i}");
    }
    handle.join().unwrap();   // wait for the worker to finish
}

join returns the thread's result

handle.join() blocks until the thread completes and returns Result<T> — the closure's return value, or an Err if the thread panicked. So a thread is not just fire-and-forget; it is a unit of work with a result you collect. Moving an owned vector in and getting a computed total back is the canonical pattern: values cross the thread boundary in both directions, with the move guaranteeing no aliasing on the way.

use std::thread;

fn main() {
    let v = vec![10, 20, 30];           // the closure must own v
    let handle = thread::spawn(move || {
        v.into_iter().sum::<i32>()      // the thread's return value
    });
    let total = handle.join().unwrap(); // join hands it back
    println!("total: {total}");
}

Scoped threads borrow instead of moving

When the threads are guaranteed to finish before the caller continues — the common case in parallel processing — thread::scope is the better tool: its threads may borrow surrounding variables, and the scope joins all of them before returning. That removes the move and the Arc boilerplate entirely. If your threads only need to read shared data, start here.

use std::thread;

fn main() {
    let s = String::from("hello");
    thread::scope(|scope| {
        // scoped threads may BORROW surrounding variables
        scope.spawn(|| println!("len: {}", s.len()));
        scope.spawn(|| println!("{s}"));
    });                       // all threads joined before scope ends
    println!("{s}");          // still ours afterwards
}

7.2 Channels and shared state

Threads communicate two ways: message passing through channels, or shared state behind a mutex. Rust's standard library ships both — mpsc for channels, Mutex for shared state.

mpsc: multiple producers, one consumer

mpsc::channel() returns a sender and a receiver. The sender's send places a value into the channel; the receiver's recv blocks until a value arrives, and iterating the receiver yields values until every sender is dropped — the channel closes when its last sender goes away. Multiple threads can hold cloned senders; only the receiver side is single. This is the actor-style pattern: workers send results back to one coordinator.

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for i in 0..3 {
        let tx = tx.clone();          // a sender clone per thread
        thread::spawn(move || {
            tx.send(i * 10).unwrap();
        });
    }
    drop(tx);                          // close the ORIGINAL sender
    for received in rx {               // ends when all senders drop
        println!("{received}");
    }
}

Mutex: interior mutability with a lock

Mutex<T> gives safe mutation of a T shared through a reference: lock() returns a guard that derefs to &mut T, and the lock is released when the guard drops — automatically, even if the scope exits early. The guard is the token of permission: while it lives, no other thread can touch the value. A second thread calling lock() blocks until the first releases. The price of this safety is the lock itself, which is why the guard scope should be as short as possible.

use std::sync::Mutex;

fn main() {
    let m = Mutex::new(0);
    {
        let mut guard = m.lock().unwrap();
        *guard += 1;                 // deref through the guard
    }                                // guard dropped: lock released
    println!("{:?}", m);             // Mutex { data: 1 }
}

Arc<Mutex<T>>: share across threads

The combination that actually gets shared between threads is Arc<Mutex<T>>: Arc gives each thread a reference-counted handle (atomics included, unlike Rc), and the Mutex inside serialises access to the T. Ten threads each incrementing one counter is the hello-world of shared state — and the answer to why Rc will not do: its count is not atomic, so two threads cloning it would race on the refcount itself.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut n = c.lock().unwrap();
            *n += 1;
        }));
    }

    for h in handles {
        h.join().unwrap();
    }
    println!("counter = {}", *counter.lock().unwrap());   // 10
}
Holding a MutexGuard across a blocking call or an await is a dead-lock and a performance bug respectively: the lock stays held while other threads wait. Scope the guard tightly — acquire, mutate, drop.

7.3 Send and Sync

Send and Sync are the marker traits that encode thread-safety into the type system: Send means the value may move to another thread, Sync means &T may be shared across threads. The compiler derives them automatically, so most types are both without you writing anything.

Send: the value may cross threads

A type is Send if moving it to another thread cannot cause unsafety. String, Vec, numbers, Arc are all Send; Rc is not, because its reference count is a plain integer that two threads would race. thread::spawn` requires its closure to be Send, so trying to move an Rc into a thread is a compile error with the exact type in the message — the check happens before the race can. The fix is either Arc (atomic counting) or not sharing at all.

use std::rc::Rc;

fn main() {
    let rc = Rc::new(5);         // reference-counted, thread-UNSAFE
    // thread::spawn(move || println!("{rc}"));
    // ERROR: `Rc<i32>` cannot be sent between threads safely
    //        (Rc counts refs without atomics; another thread could
    //         race the count). Use Arc, or move an owned value.
    println!("{rc}");
}

Sync: &T may be shared across threads

Sync means a shared reference to the type can be sent between threads, which is what lets several threads read one value safely. Arc<String> is Send and Sync, so cloning the handle in each thread and printing through it is safe — every Arc::clone bumps an atomic count, and each thread reads through its own Arc. The rule of thumb: a type is Sync when &T cannot observe mutation; interior mutability types like Mutex<T> are Sync precisely because they make mutation exclusive.

use std::sync::Arc;
use std::thread;

fn main() {
    let name = Arc::new(String::from("shared"));
    let mut handles = vec![];
    for _ in 0..4 {
        let n = Arc::clone(&name);     // atomic refcount bump
        handles.push(thread::spawn(move || println!("{n}")));
    }
    for h in handles {
        h.join().unwrap();
    }
    // Arc<String> is Send + Sync: sharing reads is safe by design
}

7.4 Unit and integration tests

Testing ships with cargo: unit tests beside the code, integration tests in tests/, and documentation tests inside doc comments — all run by the one command cargo test.

Unit tests with #[cfg(test)]

A unit test is a #[test]-marked function in a mod tests block annotated #[cfg(test)]. The attribute means the module compiles only when testing, so the test helpers never ship. assert! and assert_eq! fail the test with the differing values; #[should_panic] asserts that a panic happens — the way you test a contract violation. cargo test runs them, and the convention of use super::*; imports the module under test.

pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn adds_two_numbers() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    fn addition_is_commutative() {
        assert_eq!(add(3, 2), add(2, 3));
    }

    #[test]
    #[should_panic(expected = "assertion failed")]
    fn failing_assert_panics() {
        assert!(add(1, 1) == 3);
    }
}

fn main() {
    println!("{}", add(1, 2));
}

Integration tests in tests/

Integration tests live in tests/, outside src/, and each file compiles as its own crate that links the library — so they can only use the public API, exactly like a real consumer. That is their whole job: to fail if the public surface is broken or the pieces do not fit together, even when every unit test passes. A binary crate cannot be integration-tested this way without also having a library, which is why the pattern is a thin src/main.rs over a fat src/lib.rs.

// tests/cli.rs — integration tests live in tests/, can touch only
// the crate's PUBLIC API — exactly what a real user sees.
use mylib::parse_port;

#[test]
fn parses_a_valid_port() {
    assert_eq!(parse_port("8080").unwrap(), 8080);
}

#[test]
fn rejects_an_out_of_range_port() {
    assert!(parse_port("99999").is_err());
}

// src/lib.rs must expose it:
//   pub fn parse_port(s: &str) -> Result<u16, std::num::ParseIntError> {
//       s.parse()
//   }

Doc tests: examples that cannot lie

Code fences inside /// doc comments are compiled and executed by cargo test. A doc example that no longer compiles, or whose assertions fail, fails the test run — so the documentation cannot drift from the code. This is the most undervalued testing surface in the language: every example you write for humans is also a running test, and #[should_panic]-style expectations work there too via the should_panic attribute in the fence.

/// Adds two numbers together.
///
/// # Examples
///
/// ```
/// let n = mylib::add(1, 2);
/// assert_eq!(n, 3);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

// The `rust` fence above is compiled and RUN by `cargo test`.
// A doc example that lies about the API is a failing test.

7.5 The ecosystem: serde, clap, tokio and cargo tooling

Three crates carry a large share of real Rust programs: serde for serialisation, clap for command-line parsing, and tokio for asynchronous I/O. Around them, the cargo tooling — linting, formatting, docs, dependency inspection — is what makes a project shippable.

serde: serialise and deserialise anything

serde is a framework: derive Serialize/Deserialize on your struct, and a companion crate (serde_json, toml, yaml, bincode…) moves it in and out of that format. Field names become keys by default; #[serde(rename = "...")] and #[serde(default)] bend it to match existing schemas. Because the derive is checked at compile time, a struct with a field serde cannot serialise is a compile error, not a runtime surprise.

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Server {
    host: String,
    port: u16,
    tls: bool,
}

fn main() {
    let server = Server {
        host: "db.internal".into(),
        port: 5432,
        tls: true,
    };

    let json = serde_json::to_string(&server).unwrap();
    println!("{json}");

    let back: Server = serde_json::from_str(&json).unwrap();
    println!("{}:{}", back.host, back.port);
}

clap: command-line parsing from a struct

clap's derive mode turns a struct into your CLI: fields are arguments, doc comments become help text, #[arg(short, long)] toggles flags, and --version/--help come from the #[command] attribute. Args::parse() reads std::env::args(), validates types and requiredness, and prints usage and exits on a bad invocation — which is exactly the behaviour a well-behaved tool should have, and a dozen lines of hand-written parsing you no longer maintain.

use clap::Parser;

/// Count lines in a file.
#[derive(Parser)]
#[command(version, about = "counts lines in files")]
struct Args {
    /// the file to read
    path: String,

    /// print extra diagnostics
    #[arg(short, long)]
    verbose: bool,
}

fn main() {
    let args = Args::parse();          // parses std::env::args()
    let text = std::fs::read_to_string(&args.path).unwrap();
    println!("{} lines", text.lines().count());
    if args.verbose {
        println!("reading {}", args.path);
    }
}

tokio: the async runtime

async fn returns a future, and a future does nothing until it is awaited — the compiler turns each async body into a state machine with one struct per await point, which is why an unawaited future costs nothing. tokio is the executor that polls futures: an async runtime with a multithreaded work-stealing scheduler and OS-level I/O events (epoll on Linux, kqueue on macOS, IOCP on Windows). #[tokio::main] initialises it, tokio::spawn runs tasks concurrently, and tokio::join! awaits several futures at once. Three failures dominate beginners' async: holding a std::sync::MutexGuard across an await (not Send — the compiler rejects it), calling a blocking function inside async (it freezes the executor thread — use tokio::time::sleep), and never awaiting a future at all.

use tokio::time::{Duration, sleep};

// async fn returns a Future: the body does nothing until awaited.
async fn wait_and_say(secs: u64, msg: &str) {
    sleep(Duration::from_secs(secs)).await;
    println!("{msg}");
}

#[tokio::main]
async fn main() {
    // sequential awaits would take 3 seconds; join! runs concurrently
    tokio::join!(
        wait_and_say(1, "first done"),
        wait_and_say(2, "second done"),
    );
}

// The three async pitfalls:
//   1. a std::sync::MutexGuard held across .await is not Send —
//      the compiler rejects it; use tokio::sync::Mutex
//   2. std::thread::sleep inside async blocks the executor thread —
//      use tokio::time::sleep
//   3. a future never awaited is just a value — silently inert

Cargo tooling and the pre-merge checklist

The command set that turns working code into shippable code: cargo fmt reformats, cargo clippy adds several hundred lints over rustc's, cargo test --release runs the suite with optimisations and without the debug-only checks (the profile that matters), cargo doc builds the docs, cargo tree answers "why is this dependency here" transitively, and cargo audit scans the resolved tree for known vulnerabilities. Wire the first three into CI with -- --check / -D warnings and formatting drift, lint regressions and release-only failures all stop arriving by pull request.

# The pre-merge checklist, in order:
$ cargo fmt -- --check       # fail CI on unformatted code
$ cargo clippy -- -D warnings
$ cargo test
$ cargo test --release       # debug assertions are off out there
$ cargo doc --open           # docs for the version you are shipping
$ cargo tree -i tokio        # who pulls tokio in, transitively?
$ cargo add serde_json       # dependencies are a one-line command
$ cargo audit                # known-vulnerability scan of the tree
Async is not faster than threads by magic: it overlaps I/O waits. CPU-bound work gains nothing from async — keep that on plain threads, and use tokio for the I/O-heavy service in between.
