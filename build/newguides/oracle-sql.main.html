0 · Orientation

Oracle Database is the server that stores and guards your data; Oracle SQL is the language you use to reach it. This guide is written against Oracle Database 23ai, the current Long Term Support release, and marks where something needs 19c or 21c or exists only in 23ai. Every example is real SQL or PL/SQL that runs in SQLcl, SQL*Plus or SQL Developer.

0.1 The database, the instance, and the language

Three words get used interchangeably and they are not the same thing. Knowing which one is broken is most of the difference between a five-minute incident and a five-hour one.

Database versus instance

The database is the durable artefact on disk: the data files, the control file, the online redo log and the parameter file. It survives a power cut. The instance is the volatile machinery that gives access to those files: the background processes (DBWn, LGWR, CKPT, SMON, PMON, MMON) plus the System Global Area, a shared pool of buffers and cursors. A normal server has one instance per database; Real Application Clusters runs one database across several instances on different hosts, which is why RAC problems are usually interconnect or cache-fusion problems rather than SQL problems.

Operationally this split explains several things. SHUTDOWN IMMEDIATE ends an instance; opening the files again with STARTUP brings it back with the same data. ORA-01034: ORACLE not available means no instance is listening, not that data is lost. And because the SGA is per-instance, anything cached in memory — parsed cursors, result cache, sequences' cached values — is not shared between RAC nodes, so a number that looks monotonic on one node can look gappy from another.

Where SQL ends and Oracle begins

Oracle SQL is close to ANSI SQL, but the interesting parts are the extensions. Oracle has had MERGE, analytic functions, MODEL, hierarchical CONNECT BY, PIVOT and the (+) outer-join operator for years before the standards caught up, and it has its own spelling of several standard constructs. The product also owns a large procedural language, PL/SQL, which is not SQL at all and runs inside the server. The practical consequence: code written for PostgreSQL will mostly parse, then behave differently at the edges — date arithmetic, implicit string-to-number conversion, and NULL ordering all differ.

0.2 Versions in 2026: 19c, 21c and 23ai

Oracle's release numbering is not sequential in the way most people expect: the last digit is the patch set, the middle digit groups new features, and the trailing letter marks a generational change.

Which release you are actually on

Oracle Database 19c has been the workhorse since 2019 and is still deployed widely. 21c was an innovation release — new features, no long support commitment. 23ai (originally numbered 23c, renamed when Oracle put AI features in the core) is the current long-term-support line; it is the sensible target for new work in 2026. Before you trust any documentation or bug number, ask the database what it is, because the marketing name and the patch level routinely disagree.

-- SQL - the version, the patch level and the container you landed in
SELECT banner_full FROM v$version;

SELECT version_full AS db_version
FROM   product_component_version
WHERE  product LIKE 'Oracle Database%';

-- 19c and later are always multitenant: are we in the CDB or a PDB?
SELECT name, cdb, con_id FROM v$database;
SELECT sys_context('USERENV','CON_NAME') AS current_container FROM dual;

What 23ai added that changes how you write SQL

The features people reach for on day one are: the VECTOR data type with vector indexes and VECTOR_DISTANCE, which makes similarity search a SQL operation rather than an external service call; JSON-relational duality views, which expose relational tables as a JSON document without duplicating data; a real SQL BOOLEAN type (usable in tables, not just PL/SQL); table-less SELECT, so SELECT 1 no longer needs FROM DUAL; the SELECT ... QUALIFY clause that filters on a window function directly; and the IF [NOT] EXISTS clause on DDL. On the JSON side, JSON_TRANSFORM and dot-notation access mean many transformations no longer need JSON_TABLE, and SQL GROUP BY accepts a select-list alias.

0.3 Connecting: SQLcl, SQL*Plus, SQL Developer

Three clients ship with or alongside Oracle, and they are not interchangeable. SQL*Plus is the oldest and the one every server has; SQLcl is its Java replacement; SQL Developer is the graphical one.

Easy Connect or a TNS alias

An Easy Connect string packs everything into one token: //host:port/service_name. It needs no configuration file and is what you want for a one-off. A TNS alias names an entry in tnsnames.ora and is what you want for anything permanent, because it keeps the host name out of scripts, lets you switch between a direct connect and an SCAN listener for RAC, and holds the connection-timeout, retry and failover parameters. Both files are found through TNS_ADMIN; if a client cannot see your alias, that environment variable is the first thing to check on Windows, where multiple Oracle homes each pretend to own %ORACLE_HOME%\network\admin.

# shell - SQLcl / SQL*Plus, Easy Connect then a named alias
sql user/pass@//dbhost:1521/FREEPDB1
sql user/pass@ORCLPDB1
sql /nolog                      # connect later with CONNECT

# SQLcl extras that SQL*Plus lacks:
sql -name prod user/pass@prod   # saved, reusable named connection

-- SQL - useful session settings, identical in both clients
SET LINESIZE 200
SET PAGESIZE 100
SET LONG 100000
SET TIMING ON
SET DEFINE OFF          -- stop treating & as a substitution variable
SET SERVEROUTPUT ON SIZE UNLIMITED

SELECT sys_context('USERENV','SESSION_USER') AS me,
       sys_context('USERENV','DB_NAME')      AS db,
       sys_context('USERENV','CON_NAME')     AS container
FROM   dual;

The three clients compared

SQL*Plus is a thin C client that is always present on a server and is the safest thing to put in a cron job or a shell script, because its output formatting has been stable for decades. SQLcl is Java, connects over JDBC, and adds the things SQL*Plus never had: history, tab completion, INFO on tables and views, SET SQLFORMAT json|csv|ansiconsole, and LOAD/UNLOAD for bulk data. SQL Developer is the GUI: good for browsing the dictionary, running the debugger, and producing diagrams; poor for automation, because anything you can do there you should be able to do in a script.

0.4 Schemas, users, and the privilege model

Oracle merges "user" and "schema" into one object, and that single fact explains most of the privilege surprises people hit in their first week.

A schema is a user is a namespace

When you write CREATE USER app IDENTIFIED BY ... you have created an account and an empty namespace called APP. Every table, index, view, sequence, type and PL/SQL unit that account creates lives inside that namespace and is addressed as app.orders. There is no separate CREATE SCHEMA step as in PostgreSQL; the schema appears when the user appears and disappears when the user is dropped with CASCADE. A consequence worth internalising: two users can each own a table named orders, and which one a query means depends entirely on the parsing schema — normally the connected user, changed with ALTER SESSION SET CURRENT_SCHEMA.

-- SQL - the smallest useful grant set (run as a DBA)
CREATE USER app IDENTIFIED BY "S3cret!" QUOTA UNLIMITED ON users;
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE, CREATE VIEW TO app;
GRANT CREATE PROCEDURE, CREATE TRIGGER TO app;

-- 23ai shortcut: a curated developer role for hands-on work
GRANT DB_DEVELOPER_ROLE TO app;

-- Let another schema read one table, and nothing else
GRANT SELECT ON app.orders TO reporting;
CREATE SYNONYM reporting.orders FOR app.orders;   -- optional shorthand

Privileges: system and object

Oracle distinguishes system privileges, which allow a class of action anywhere (CREATE TABLE, SELECT ANY TABLE, CREATE SESSION), from object privileges, which allow an action on one named object (SELECT ON app.orders). SELECT ANY TABLE is a blunt instrument that defeats row-level security and auditing; grant the object privilege or a role instead. Roles are collections of privileges that can be granted to users — with one important trap: a role is not enabled inside a definer's-rights PL/SQL unit by default, so a procedure that runs as its owner will fail with ORA-00942 even though your interactive session can see the table. Grant the privilege directly to the owner, or use AUTHID CURRENT_USER, rather than blaming the SQL.

-- SQL - see what the current session can actually do
SELECT privilege FROM user_sys_privs ORDER BY privilege;
SELECT owner, table_name, privilege FROM user_tab_privs_recd;

-- Who am I, what schema am I parsing in, which roles are on?
SELECT sys_context('USERENV','SESSION_USER')  AS connected_as,
       sys_context('USERENV','CURRENT_SCHEMA') AS parsing_schema
FROM   dual;
SELECT role FROM session_roles;
The HR, OE, SH, PM and CO sample schemas are the fastest teaching data set. On 23ai they are installed into a pluggable database and reachable once DB_DEVELOPER_ROLE (or an explicit object grant) is in place, so connect to the PDB before hunting for HR.EMPLOYEES.

0.5 DUAL, the data dictionary, and your first query

Two things make Oracle feel unfamiliar at first: a one-row table used to evaluate expressions, and a large family of read-only views that describe the database itself.

DUAL and the table-less SELECT

DUAL is a one-row, one-column table (DUMMY VARCHAR2(1) holding 'X') that exists so you can evaluate an expression without touching real data: SELECT SYSDATE FROM DUAL. It is not a quirk to be worked around — historically Oracle required a FROM clause, and DUAL supplied one with a guaranteed single row. Oracle 23ai finally allows SELECT 1 with no FROM at all, and PL/SQL blocks have always allowed bare assignment. When portability matters, keep writing FROM DUAL: it is still valid everywhere.

-- SQL - expressions with and without a table
SELECT 1 + 1 AS two, SYSDATE AS now, USER AS me FROM dual;

-- 23ai only: FROM is optional
SELECT 1 + 1 AS two;

-- DUAL in a query generator: build ten rows with no table scan
SELECT LEVEL AS n FROM dual CONNECT BY LEVEL <= 10;

The data dictionary is just tables

Everything Oracle knows about itself is queryable. The dictionary comes in three flavours: USER_* views are the objects you own, ALL_* views are the objects you own plus those you have been granted, and DBA_* views are everything and require a privileged role. Underneath them are the SYS-owned base tables (OBJ$, COL$, TAB$) and the dynamic performance views V$..., which are not tables at all but windows onto instance memory. This is the single most valuable habit to build: instead of guessing a name, ask USER_TAB_COLUMNS for column types, USER_CONSTRAINTS for the rules, and USER_IND_COLUMNS for what is indexed.

-- SQL - orientation queries you will run on every new system
SELECT table_name FROM user_tables ORDER BY table_name FETCH FIRST 20 ROWS ONLY;

SELECT column_name, data_type, nullable
FROM   user_tab_columns
WHERE  table_name = 'EMPLOYEES'
ORDER  BY column_id;

-- Search the dictionary by meaning, not by name
SELECT table_name, comments FROM dict WHERE LOWER(comments) LIKE '%sequence%';
Write SELECT ... FROM user_objects WHERE object_name = 'MY_PROC' before concluding a procedure is missing. An object compiled with errors has a row with status = 'INVALID', and many "not found" errors are really "found but invalid" — SHOW ERRORS PROCEDURE my_proc in SQLcl or SQL*Plus tells you which.

1 · SQL fundamentals

Every query, from a two-column lookup to a fifty-line analytic report, is built from the same clauses. This chapter works through them in the order the optimizer evaluates them, not the order you type them, because that order explains most of the surprises.

1.1 SELECT and FROM: projection and the logical order

The clauses you type are not executed left to right. Understanding the real order is what makes aliases, window functions and ROWNUM behave predictably.

The logical order of evaluation

A query is evaluated roughly as: FROM and joins first, then WHERE, then GROUP BY and aggregates, then HAVING, then window functions, then SELECT (so column aliases do not exist yet in WHERE), then DISTINCT, then ORDER BY, and finally row limiting. This is why you cannot filter on a column alias in WHERE — the alias is defined after the filter runs — while you can use it in ORDER BY. It also explains why a window function cannot appear in WHERE: it is computed after filtering, in a separate pass, so the filter must be pushed into an inline view.

The optimizer is free to reorder physically as long as the result is the same, which is the whole point of the cost-based optimizer. Your job is to describe the result; the plan is the database's job. The exceptions where you must care about order are the ones where the language pins it: ROWNUM is assigned before ORDER BY in the same block, and analytic functions can see row order only through their own ORDER BY.

-- SQL - projection, aliases and expressions
SELECT e.employee_id                AS id,
       e.first_name || ' ' || e.last_name AS full_name,
       e.salary,
       e.salary * 12                AS annual,
       ROUND(e.salary / 12, 2)      AS monthly
FROM   hr.employees e
WHERE  e.department_id = 50
ORDER  BY annual DESC;

Qualifying columns is not optional at scale

Always qualify a column with its table alias, even when the query is unambiguous today. A schema change that adds a same-named column to a second table in the FROM clause turns a working query into ORA-00918: column ambiguously defined — at deploy time, in production. Using an alias also documents which table a column came from, and lets the optimizer's plan be read alongside the SQL without a lookup. The * shorthand is fine for interactive poking and dangerous in application code, because a column added to the table silently changes the result set shape your client parses.

-- SQL - the two ways to rename the result, and why one is safer
SELECT salary AS basic_pay FROM hr.employees;   -- alias in the projection

-- Bad idea in application code: a new column changes the contract
SELECT * FROM hr.employees;
An unquoted alias is folded to upper case, exactly like an unquoted identifier. SELECT 1 AS total returns a column named TOTAL. If a case-sensitive API needs total, write AS "total" — and then remember that every later reference must quote it too.

1.2 WHERE and the three-valued logic of NULL

NULL is not zero and not the empty string; it is "unknown", and it propagates through comparisons in a way that quietly removes rows from your result.

Why NULL breaks the obvious filters

SQL uses three-valued logic: a comparison evaluates to TRUE, FALSE or UNKNOWN, and WHERE keeps only rows where the predicate is TRUE. salary <> 5000 is UNKNOWN for a row where salary is NULL, so that row disappears — and so does it from salary = 5000. The only predicates that survive are IS NULL and IS NOT NULL. This is the single most common source of "the report is missing rows" bugs, and it bites hardest with NOT IN: x NOT IN (1, 2, NULL) is never true for any x, because the implicit equality with NULL is unknown. Use NOT EXISTS instead, which is null-safe by construction.

-- SQL - the NULL traps, side by side
SELECT COUNT(*) AS all_rows,
       COUNT(commission_pct)              AS non_null_comm,
       COUNT(*) - COUNT(commission_pct)    AS null_comm
FROM   hr.employees;

-- This returns nothing at all, and it is NOT a bug
SELECT * FROM hr.employees WHERE commission_pct NOT IN (0.1, 0.2, NULL);

-- The only predicates that survive a NULL: IS NULL and IS NOT NULL
SELECT * FROM hr.employees WHERE commission_pct IS NULL;

Safe comparisons and the empty string

Oracle is unusual in treating the empty string as NULL: '' IS NULL is true, and inserting '' into a VARCHAR2 stores NULL. That is why WHERE name = '' never matches anything, and why concatenating 'a' || NULL gives 'a' — concatenation deliberately treats null as empty. To compare two possibly-null values in a meaningful way, use DECODE(a, b, 1, 0), which considers two nulls equal, or the SYS_OP_MAP_NONNULL trick that the optimizer itself uses. For a readable query, NVL(a, sentinel) = NVL(b, sentinel) with a sentinel that cannot occur in the data is easier to explain to the next reader.

-- SQL - comparing values that may be null
SELECT e.employee_id,
       e.commission_pct,
       e.manager_id,
       CASE WHEN NVL(e.commission_pct, -1) = NVL(e.manager_id, -1)
            THEN 'same' ELSE 'different' END AS note
FROM   hr.employees e
WHERE  e.department_id = 80;
An index on a nullable column does not store rows where every indexed value is null, so WHERE col IS NULL can force a full table scan even though an index exists. If null-hunting is a real access path, build a function-based index on NVL(col, '<none>'), or make the column NOT NULL and stop needing the question answered.

1.3 ORDER BY: deterministic output and NULL placement

A query without ORDER BY has no defined order — full stop. Rows that happen to come back sorted today come back differently after a plan change, a statistics refresh or a parallel degree bump.

The default, and how to override it

Ascending order places NULL last; descending places it first. That is Oracle's convention and it is the opposite of PostgreSQL's, which is why a ported query can silently change where the blanks appear. The fix is explicit: NULLS FIRST or NULLS LAST on each sort key. Because the null-handling is per key, a multi-column sort can put nulls at the top of one column and the bottom of another, which is often exactly what a report needs.

Sorting is not free. Unless an index already returns rows in the required order and the optimizer chooses to use it, the sort becomes a SORT ORDER BY operation with its own memory grant (the PGA work area). A sort too large for its memory spills to a temporary tablespace file and the plan shows it as SORT ORDER BY ... (Temp). That is not an error, but it is the difference between a report that returns in two seconds and one that returns in two minutes.

-- SQL - explicit null placement, per key
SELECT department_id, commission_pct, salary
FROM   hr.employees
ORDER  BY commission_pct DESC NULLS LAST,
          salary         ASC  NULLS FIRST;

-- Sort by something not in the projection (allowed, unlike GROUP BY)
SELECT first_name, last_name FROM hr.employees
ORDER  BY hire_date DESC FETCH FIRST 5 ROWS ONLY;

Expression sorts, case-insensitive sorts and stability

You can sort by an expression, which lets you do a case-insensitive collation without changing the data: ORDER BY UPPER(last_name). On a large table that expression sort cannot use a plain B-tree index, so if it is on a hot path, index the expression itself. When two rows tie on every sort key their relative order is unspecified; if a caller needs it to be stable, add a unique tiebreaker such as the primary key. The NLSSORT function with an explicit collation name does linguistic sorting properly — the affected sort columns must be NLS_SORT-aware by declaration or the index will not be used.

-- SQL - case-insensitive and linguistically-aware ordering
SELECT last_name FROM hr.employees ORDER BY UPPER(last_name) FETCH FIRST 5 ROWS ONLY;

SELECT last_name FROM hr.employees
ORDER  BY NLSSORT(last_name, 'NLS_SORT=GENERIC_M_CI') FETCH FIRST 5 ROWS ONLY;
From 12.2 Oracle supports a column-level COLLATE clause, so a column declared VARCHAR2(100 CHAR) COLLATE BINARY_CI sorts and compares case-insensitively without any UPPER() call or function-based index. If case-insensitive matching is pervasive, fixing it in DDL is far cheaper than wrapping every predicate.

1.4 DISTINCT and row limiting with FETCH FIRST

Deduplication and "give me the top N" are both scans over a result set, and both have an efficient form and a form that quietly ruins performance.

DISTINCT is a sort or hash, not magic

DISTINCT applies to the whole projection, not to a chosen column, so asking for two columns "distinct" returns distinct combinations. Under the hood it is a SORT UNIQUE or HASH UNIQUE step, which means it costs either a sort or a hash table sized to the cardinality. On a large fact table SELECT DISTINCT over ten columns is often a worse way to get a subscriber list than a purpose-built query over a smaller table. When you genuinely want one row per key from unequal rows, that is a ranking problem, not a deduplication problem — reach for ROW_NUMBER, which lets you decide which row survives.

-- SQL - distinct combinations, and one-row-per-key the honest way
SELECT DISTINCT department_id, job_id FROM hr.employees;

SELECT department_id, job_id, salary
FROM  (SELECT department_id, job_id, salary,
              ROW_NUMBER() OVER (PARTITION BY department_id, job_id
                                 ORDER BY salary DESC) AS rn
       FROM   hr.employees)
WHERE  rn = 1;

Row limiting, and why ROWNUM is a trap

FETCH FIRST n ROWS ONLY (12c and later) is the standard row-limiting clause and it is what you should write. It is applied after ORDER BY, so it really does give you the top N by your sort. ROWNUM is the older mechanism and it is assigned as rows are produced, before ORDER BY — so WHERE ROWNUM <= 10 ORDER BY salary DESC returns ten arbitrary rows, sorted. To use ROWNUM correctly you must nest it: the inner query sorts, the outer query applies the rownum.

FETCH FIRST ... WITH TIES is the piece people forget. If the tenth and eleventh rows tie on the sort key, plain ROWS ONLY picks one arbitrarily; WITH TIES returns both, which is what a "top 10 salespeople" report actually means. There is also OFFSET n ROWS for pagination — but be aware that deep offsets still produce and discard the skipped rows, so paginating a million-row report with OFFSET 900000 is inherently slow. Keyset pagination, asking for rows after the last key you saw, scales; offsets do not.

-- SQL - correct row limiting
SELECT first_name, salary
FROM   hr.employees
ORDER  BY salary DESC
FETCH  FIRST 5 ROWS ONLY;

-- Ties included: maybe more than 5 rows, never an arbitrary cut
SELECT first_name, salary
FROM   hr.employees
ORDER  BY salary DESC
FETCH  FIRST 5 ROWS WITH TIES;

-- Pagination: rows 21-30
SELECT first_name, salary
FROM   hr.employees
ORDER  BY salary DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- The old way: correct only when ROWNUM is applied in an outer query
SELECT * FROM (
  SELECT first_name, salary FROM hr.employees ORDER BY salary DESC
) WHERE ROWNUM <= 5;
FETCH FIRST with no ORDER BY is legal and meaningless — it returns an arbitrary subset. The optimizer is allowed to use it to speed things up (it can stop after N rows, which is often a huge win), but only a sort makes the choice of those N rows reproducible.

1.5 Literals, operators and expressions

Oracle's operators look familiar but the precedence, the implicit conversions and the character-set rules all have sharp edges.

Operator precedence and comparison behaviour

AND binds tighter than OR, so a = 1 AND b = 2 OR c = 3 means (a = 1 AND b = 2) OR c = 3. Parenthesise whenever a reader might hesitate; it costs nothing and prevents a predicate that silently matches far more rows than intended. Oracle has two inequality spellings, <> and !=, which are synonyms; <=, >= and ^= (also a not-equal) are all accepted. String comparison uses the column's collation — binary by default, so 'A' sorts before 'a' and comparison is case- and accent-sensitive.

-- SQL - precedence made explicit, and both inequalities
SELECT * FROM hr.employees
WHERE  (department_id = 50 AND salary > 5000)
   OR  (department_id = 80 AND commission_pct IS NOT NULL);

SELECT * FROM hr.employees WHERE job_id <> 'SA_REP' AND ROWNUM <= 3;
SELECT * FROM hr.employees WHERE job_id != 'SA_REP' AND ROWNUM <= 3;   -- same

Literals, and the conversion you did not ask for

A string literal is single-quoted; two adjacent single quotes inside it represent one apostrophe (O''Brien). Numeric literals may use scientific notation and the f/d suffixes for BINARY_FLOAT/BINARY_DOUBLE; date and timestamp literals use the ANSI forms DATE '2026-10-15' and TIMESTAMP '2026-10-15 09:30:00', which need no format mask and must be written in that exact order. Preferring them over TO_DATE('15/10/2026','DD/MM/YYYY') removes a whole class of ORA-01843: not a valid month bugs caused by a session whose NLS_DATE_FORMAT is not what you assumed.

Oracle will implicitly convert a string to a number or a date when the context demands it. That is convenient and occasionally catastrophic: an implicit TO_NUMBER on a VARCHAR2 column disables the index, and a comparison against a session-dependent NLS_DATE_FORMAT can fail for one user and succeed for another on the same data. Write the explicit conversion, or use the ANSI literal; on 12.2+ you can also make the failure graceful with TO_DATE(x DEFAULT NULL ON CONVERSION ERROR, ...).

-- SQL - literals that need no session settings
SELECT DATE '2026-10-15'                      AS a_date,
       TIMESTAMP '2026-10-15 09:30:00.123456'  AS a_ts,
       INTERVAL '2' DAY                       AS two_days,
       INTERVAL '3-6' YEAR TO MONTH            AS three_years_six_months
FROM   dual;

-- Explicit conversion, and a graceful failure mode
SELECT TO_NUMBER('12,345.67', '99G999D99',
                 'NLS_NUMERIC_CHARACTERS=''.,''') AS n,
       TO_DATE('02/30/2026' DEFAULT NULL ON CONVERSION ERROR, 'MM/DD/YYYY') AS bad
FROM   dual;
Oracle has no bare boolean literal in SQL before 23ai: you cannot write WHERE is_active = TRUE on 19c, and SELECT 1 = 1 is not a query. Use CASE WHEN x THEN 1 ELSE 0 END to turn a predicate into a value. On 23ai the BOOLEAN type is available in tables and expressions, so the pattern finally has a native spelling.

2 · Data types, DDL and DML

Choosing the wrong type is a decision you pay for on every query for the life of the table. This chapter covers the type family, the DDL that creates and evolves objects, the DML that moves rows, and the constraints that make invalid data impossible rather than merely unlikely.

2.1 Choosing a data type: NUMBER, VARCHAR2, DATE, LOBs

Oracle's type system is small and old, and most of its surprises come from types that look standard but are not.

The core scalar types

NUMBER(p, s) stores exact decimal values; p is the total number of significant digits and s the digits after the decimal point, so NUMBER(10,2) holds up to 99,999,999.99. Without a precision it is a variable-length exact number, which is convenient and slower to process than a fixed one. NUMBER(10,2) is the right type for money — never BINARY_FLOAT or BINARY_DOUBLE, which are IEEE 754 binary types and cannot represent 0.10 exactly. Reach for BINARY_DOUBLE only for scientific computation where the exact decimal value is irrelevant.

Strings are VARCHAR2(n) — variable length, up to 4000 bytes by default, or 32,767 bytes if the database was created with MAX_STRING_SIZE=EXTENDED. The length unit matters: VARCHAR2(50 BYTE) counts bytes in the database character set, so a column that holds 50 ASCII characters holds only 12 four-byte emoji. Declare VARCHAR2(50 CHAR) when the limit is about characters to a human. CHAR(n) is blank-padded to a fixed length and should be reserved for genuinely fixed-length codes; comparing a CHAR with a VARCHAR2 forces padding rules on you.

Dates, timestamps and the timezone question

DATE always contains a time, down to the second, and never a timezone. TIMESTAMP WITH TIME ZONE stores the value together with the offset that was supplied, so two rows can show the same instant with different offsets. TIMESTAMP WITH LOCAL TIME ZONE normalises on insert to the database time zone and converts back to the session's on retrieval, which is the type most applications actually want: store once, display in the viewer's zone, compare without thoughts about offset. Mixing the two is the classic source of an off-by-hours bug that only appears for users in one region.

-- SQL - one instant, four representations
SELECT SESSIONTIMEZONE                                AS session_tz,
       SYSTIMESTAMP                                   AS db_ts,
       CAST(SYSTIMESTAMP AT TIME ZONE 'UTC' AS TIMESTAMP WITH TIME ZONE) AS utc_ts,
       SYSTIMESTAMP AT TIME ZONE 'America/New_York'   AS ny_ts
FROM   dual;

-- Storage cost is per row and per column: check before you guess
SELECT column_name, data_type, data_length, char_used
FROM   user_tab_columns WHERE table_name = 'EMPLOYEES' ORDER BY column_id;
VARCHAR2 column names are stored from 1 byte per character upward depending on the character set, and any value over 4000 bytes cannot live in a VARCHAR2 without extended string sizes. If the field might grow past a page of text, declare it CLOB from the start — converting a populated VARCHAR2 to CLOB later is an ALTER TABLE that rewrites the table.

ROWID, RAW and the identity of a row

ROWID is a physical address: it encodes the data file, block and slot. It is the fastest way to reach a row and it is what an index leaf points at. It is not stable — a row movement (partition move, table rebuild, some updates) changes it — so never store it as a permanent key. UROWID is the logical-ish variant for index-organized tables. RAW(n) holds bytes with no character-set conversion, which is what you want for hashes, UUIDs and encryption output; a UUID stored as RAW(16) takes a quarter of the space of its 36-character text form and indexes much better.

-- SQL - a UUID as bytes, and a rowid lookup
CREATE TABLE api_keys (
  key_id      RAW(16)  DEFAULT SYS_GUID() PRIMARY KEY,
  owner_name  VARCHAR2(100 CHAR) NOT NULL,
  created_at  TIMESTAMP WITH LOCAL TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL
);

INSERT INTO api_keys (owner_name) VALUES ('billing-service');

SELECT RAWTOHEX(key_id) AS key_hex, owner_name FROM api_keys;

-- ROWID is an access path, not a key
SELECT rowid, employee_id FROM hr.employees WHERE employee_id = 100;

2.2 CREATE, ALTER, DROP: evolving a live schema

DDL in Oracle is transactional at the statement level: it commits implicitly, and it takes a library-cache latch while it runs. Both facts constrain how you change a busy schema.

CREATE TABLE and its storage clauses

A basic CREATE TABLE is portable; the clauses that follow the closing parenthesis are where Oracle-specific tuning lives. PCTFREE reserves space in each block for row growth from updates; INITRANS sets the number of concurrent transaction slots in the block header and is raised for hot rows; COMPRESS enables basic or advanced compression. CREATE TABLE AS SELECT (CTAS) is the fastest way to materialise a result, and it copies data but not constraints, defaults or indexes — a common surprise when a test table created with CTAS silently allows duplicates.

-- SQL - a table with the settings that matter
CREATE TABLE order_events (
  event_id    NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id    NUMBER(12)      NOT NULL,
  event_type  VARCHAR2(30 CHAR) NOT NULL,
  payload     JSON,
  created_at  TIMESTAMP WITH LOCAL TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT chk_event_type CHECK (event_type IN ('CREATED','PAID','SHIPPED','CANCELLED'))
)
PCTFREE 10
TABLESPACE users;

-- CTAS: data only, no constraints, no indexes
CREATE TABLE order_events_snapshot AS SELECT * FROM order_events WHERE 1 = 0;

ALTER TABLE without an outage

Most modern ALTER TABLE operations are metadata-only and return in milliseconds however large the table: adding a nullable column with a default (11g+ stores the default in the dictionary rather than rewriting rows), adding a NOT NULL constraint where the data already satisfies it, renaming a column, and SET UNUSED. Others rewrite every row and need a maintenance window: changing a column's type, shrinking a VARCHAR2, converting to or from CLOB, and MOVE. Column renames are metadata-only but they immediately break every non-validated dependency — and a view or PL/SQL unit that referenced the old name goes INVALID and recompiles on next use, sometimes successfully, sometimes not.

-- SQL - evolve a table; the first three are instant, the last is not
ALTER TABLE order_events ADD (region_code VARCHAR2(10 CHAR));
ALTER TABLE order_events ADD (channel VARCHAR2(20) DEFAULT 'WEB' NOT NULL);
ALTER TABLE order_events RENAME COLUMN payload TO body;

-- Slow: narrowing a column rewrites every block and invalidates dependents
ALTER TABLE order_events MODIFY (region_code VARCHAR2(4 CHAR));

-- Destructive and irreversible: the space is not reclaimed until a MOVE
ALTER TABLE order_events DROP COLUMN channel;
ALTER TABLE order_events SET UNUSED COLUMN region_code;
DDL commits first and asks questions later. If you are halfway through a batch of INSERTs and issue an ALTER, your uncommitted work is committed by the DDL. That means a failed migration step can leave a partially-applied change that no ROLLBACK can undo — plan the DDL, take a backup or use flashback, then run it.

DROP, TRUNCATE and the recycle bin

DROP TABLE does not delete the data; it renames the segment into the recycle bin, from which FLASHBACK TABLE x TO BEFORE DROP restores it in seconds. TRUNCATE TABLE genuinely removes every row, keeps the segment, resets the high-water mark and is DDL, so it commits — but it can be ROLLBACK-ed only in the sense that it is already done. TRUNCATE is the fastest way to empty a staging table and the most dangerous single word in a script; guard it with an explicit schema and, for partitioned tables, TRUNCATE PARTITION rather than a delete.

-- SQL - recovery is a query away, before you purge
SELECT object_name, original_name, droptime
FROM   user_recyclebin ORDER BY droptime DESC;

FLASHBACK TABLE order_events_snapshot TO BEFORE DROP;

-- Permanently bypass the bin (default in 10g+ was ON; PURGE is explicit)
DROP TABLE order_events_snapshot PURGE;

2.3 INSERT, UPDATE, DELETE and the RETURNING clause

DML is where correctness and cost meet. A multi-row UPDATE is one statement with one plan and, crucially, one undo stream.

Single statement, single unit of work

Oracle has no multi-row VALUES on classic INSERT; you either use INSERT ... SELECT, INSERT ALL, or INSERT ... VALUES in a loop (which is slow unless you use FORALL). The good news is that a set-based UPDATE or DELETE is far faster than row-by-row PL/SQL: the whole statement runs inside the SQL engine. The cost is that it holds undo for every changed row, so a ten-million-row delete should be batched to keep undo growth and lock duration bounded.

RETURNING is the feature that lets you avoid a second query: the DML statement returns column values, either into PL/SQL variables or — since 12c — to a client as a result set. It reads the post-update row for UPDATE and INSERT, and the pre-delete row for DELETE. Using it removes the round trip and the race where another session changes the row between the write and the read-back.

-- SQL - set-based DML, and seeing what you changed
INSERT INTO order_events (order_id, event_type)
SELECT order_id, 'CREATED' FROM orders WHERE status = 'NEW';

UPDATE hr.employees
SET    salary = salary * 1.05
WHERE  department_id = 50;

DELETE FROM order_events
WHERE  created_at < SYSTIMESTAMP - INTERVAL '180' DAY;

-- RETURNING into PL/SQL (works in SQL*Plus / SQLcl too)
UPDATE hr.employees SET salary = salary * 1.10 WHERE employee_id = 100
RETURNING salary INTO :new_salary;

Careful with correlated updates

A correlated UPDATE ... SET (a,b) = (SELECT ...) sets the columns to NULL when the subquery finds no row, silently wiping data. The safe patterns are MERGE (next topic), an EXISTS guard on the UPDATE, or an updatable join. This is one of the few places where writing more SQL prevents a data-loss bug rather than merely documenting intent.

-- SQL - the trap, then the guard
-- Wipes salary to NULL where no band matches (and cannot use an alias in SET).
UPDATE hr.employees e
SET    salary = (SELECT g.low FROM salary_bands g WHERE g.job_id = e.job_id);

-- Only touch rows that actually match
UPDATE hr.employees e
SET    salary = (SELECT g.low FROM salary_bands g WHERE g.job_id = e.job_id)
WHERE  EXISTS (SELECT 1 FROM salary_bands g WHERE g.job_id = e.job_id);
Every DML statement has an implicit cursor you can inspect: SQL%ROWCOUNT gives the number of rows affected, and SQL%FOUND/SQL%NOTFOUND tell you whether it touched anything. Check SQL%ROWCOUNT = 0 after an UPDATE that was supposed to match exactly one row; an unguarded zero is how a "successful" deployment quietly does nothing.

2.4 MERGE: upsert in one pass

MERGE is Oracle's single-statement upsert and it is usually the right tool for ETL, but its join is not null-safe and its behaviour on duplicate source rows is not obvious.

Anatomy of a MERGE

The shape is: MERGE INTO target USING source ON (condition), then WHEN MATCHED THEN UPDATE and/or WHEN NOT MATCHED THEN INSERT. The ON condition is a join, not a filter, and only rows that satisfy it are considered "matched". Both branches are optional, so a MERGE can be a pure update or a pure insert-if-absent. The unmatched-insert branch cannot reference target columns, because there is no target row. A WHEN MATCHED THEN UPDATE ... DELETE WHERE (predicate) clause deletes matched rows that satisfy the predicate after the update, which removes stale rows in the same pass.

-- SQL - classic upsert from a staging table
MERGE INTO products t
USING (SELECT product_code, product_name, list_price, loaded_at
       FROM   products_stage) s
ON    (t.product_code = s.product_code)
WHEN MATCHED THEN
  UPDATE SET t.product_name = s.product_name,
             t.list_price   = s.list_price,
             t.updated_at   = s.loaded_at
  DELETE WHERE s.list_price = 0            -- drop discontinued rows
WHEN NOT MATCHED THEN
  INSERT (product_code, product_name, list_price, created_at, updated_at)
  VALUES (s.product_code, s.product_name, s.list_price, s.loaded_at, s.loaded_at);

The two failure modes to design around

First, NULL: an ON (t.k = s.k) does not match when either side is null, so source rows keyed by NULL fall through to the insert branch and duplicate forever. Guard the source with WHERE k IS NOT NULL or use DECODE/NVL in the join. Second, duplicate source rows: if two source rows match the same target row, the statement fails at runtime with ORA-30926: unable to get a stable set of rows in the source tables. That is a genuine data problem, not a syntax one; deduplicate the source with a ROW_NUMBER filter before merging.

-- SQL - make the source unique so MERGE cannot see a moving target
MERGE INTO products t
USING (
  SELECT product_code, product_name, list_price, loaded_at
  FROM  (SELECT s.*,
                ROW_NUMBER() OVER (PARTITION BY product_code
                                   ORDER BY loaded_at DESC) AS rn
         FROM   products_stage s
         WHERE  product_code IS NOT NULL)
  WHERE rn = 1
) s
ON   (t.product_code = s.product_code)
WHEN NOT MATCHED THEN
  INSERT (product_code, product_name, list_price, created_at)
  VALUES (s.product_code, s.product_name, s.list_price, s.loaded_at);
MERGE reads the target with a consistent-read query and locks the matched rows as it updates them; on a heavily concurrent table this can serialise on a hot key. A short transaction and a small batch (a few thousand rows) keeps the lock footprint bounded. Where the source is huge, merge in slices by a monotonic key rather than all at once.

2.5 Constraints: making bad data impossible

A constraint is enforced for every writer, forever, including the loading script someone writes in three years. An application-side check is enforced only by the code that remembers it.

The five constraint kinds

NOT NULL forbids missing values, UNIQUE forbids duplicates (and is implemented by a unique index), PRIMARY KEY is a NOT NULL plus UNIQUE and identifies the row, CHECK enforces an arbitrary boolean predicate, and FOREIGN KEY requires a matching key in another table and, on delete, can CASCADE, SET NULL or refuse. All of them except NOT NULL can be declared DEFERRABLE, which postpones the check until COMMIT — essential when rows must be inserted in an order that is temporarily inconsistent, such as a parent pointing at a child that does not exist yet.

The integrity cost is real but bounded: a unique constraint is one index probe, and a foreign key is one index lookup on the parent unless the child column is indexed, which is why unindexed foreign keys cause full scans on parent deletes and lock the whole child table. Index your foreign-key columns; it is the cheapest performance work in the chapter.

-- SQL - constraints that describe the business rules
CREATE TABLE order_items (
  order_id    NUMBER(12) NOT NULL,
  line_no     NUMBER(4)  NOT NULL,
  product_id  NUMBER(12) NOT NULL,
  quantity    NUMBER(6)  NOT NULL,
  unit_price  NUMBER(10,2) NOT NULL,
  CONSTRAINT pk_order_items PRIMARY KEY (order_id, line_no),
  CONSTRAINT fk_items_order   FOREIGN KEY (order_id)
              REFERENCES orders (order_id) ON DELETE CASCADE,
  CONSTRAINT fk_items_product FOREIGN KEY (product_id)
              REFERENCES products (product_id),
  CONSTRAINT chk_qty    CHECK (quantity > 0),
  CONSTRAINT chk_price  CHECK (unit_price >= 0)
);

-- The supporting index for the foreign key: do not skip it
CREATE INDEX ix_order_items_product ON order_items (product_id);

NOVALIDATE, ENABLE and cleaning up legacy data

Adding a constraint to a table with existing rows validates every row and takes a table lock; on a large table that is a long window. ENABLE NOVALIDATE enforces the rule for all new and changed rows immediately while asserting nothing about the past, which is the standard online technique: add it as no-validate, then validate in a separate step, optionally at low priority. DISABLE stops enforcement entirely, which is occasionally needed for a bulk load but leaves a period in which the database holds data the constraint claims is impossible.

-- SQL - add and enforce without a long exclusive lock
ALTER TABLE orders ADD CONSTRAINT chk_status
  CHECK (status IN ('NEW','PAID','SHIPPED','CANCELLED')) ENABLE NOVALIDATE;

-- Later, in a quiet window or with low priority
ALTER TABLE orders ENABLE VALIDATE CONSTRAINT chk_status;

-- What is enforced right now?
SELECT constraint_name, constraint_type, status, validated, deferrable
FROM   user_constraints WHERE table_name = 'ORDERS';
DBMS_ERRLOG.CREATE_ERROR_LOG plus the LOG ERRORS INTO clause turns a constraint violation during a bulk insert from a failed statement into a logged rejected row, with the offending values captured. That is how you load a dirty feed without either losing the good rows or switching the constraint off.

3 · Joins

A join is where a query's cost is decided. The shape of the join — which table drives, how many rows each step produces — matters far more than the syntax used to express it, but the syntax is what the optimizer must interpret, so both matter.

3.1 Inner joins: the rows that match on both sides

An inner join keeps a combination only when the join condition is true. It is the default, and the most common reason a rowcount comes back lower than expected.

What the join condition actually is

A join is a filter over the Cartesian product: every row of the left table paired with every row of the right table, then reduced by the ON predicate. No engine builds the product, of course — the optimizer chooses a physical algorithm (nested loops, hash join, sort-merge) — but thinking of it as a product makes the arithmetic obvious: a missing match on either side removes the pair. If one side has three matching rows and the other has two, you get six rows, not three. That fan-out is the normal case, not a bug, and it is why a "slightly wrong" total usually means a join hit a one-to-many relationship it was not told about.

-- SQL - inner join: employees who have a department
SELECT d.department_name, e.last_name, e.salary
FROM   hr.employees   e
JOIN   hr.departments d ON d.department_id = e.department_id
WHERE  e.salary > 10000
ORDER  BY d.department_name, e.salary DESC;

-- Rows on either side that do NOT match (the negative space)
SELECT COUNT(*) AS unmatched_employees
FROM   hr.employees e
WHERE  NOT EXISTS (SELECT 1 FROM hr.departments d
                   WHERE d.department_id = e.department_id);

The join key must be the right key

Joining on a column that is not unique on one side multiplies rows silently. Joining on a column that is nullable drops rows, because NULL = NULL is unknown. Joining two columns of different types forces implicit conversion, which can prevent an index from being used and occasionally produces ORA-01722: invalid number when a stray non-numeric value appears. Good practice, in order: join on declared foreign keys, make keys NOT NULL where the business allows it, and keep numeric keys numeric end to end rather than comparing NUMBER to VARCHAR2.

-- SQL - detect the fan-out before it reaches a report
SELECT e.employee_id, COUNT(*) AS rows_produced
FROM   hr.employees   e
JOIN   hr.job_history jh ON jh.employee_id = e.employee_id
GROUP  BY e.employee_id
HAVING COUNT(*) > 1
ORDER  BY rows_produced DESC FETCH FIRST 10 ROWS ONLY;
There is no performance difference between JOIN ... ON and comma-join with the condition in WHERE. The difference is readability and risk: mixing the two styles in one query is how a missing join predicate becomes a runaway Cartesian product that runs for hours.

3.2 Outer joins: LEFT, RIGHT, FULL

An outer join keeps unmatched rows from one or both sides and fills the missing columns with NULL. Almost every bug with outer joins comes from a predicate in the wrong place.

Which side is preserved

LEFT JOIN preserves every row from the table written first; RIGHT JOIN preserves the second; FULL JOIN preserves both. For a LEFT JOIN, columns from the right table are NULL exactly when no match exists, which makes IS NULL on a right-side column the standard way to find orphans — but only on a column that is otherwise NOT NULL, or a real null cannot be told apart from a missing match.

-- SQL - all employees, with or without a department
SELECT e.last_name, d.department_name
FROM   hr.employees   e
LEFT   JOIN hr.departments d ON d.department_id = e.department_id
ORDER  BY d.department_name NULLS FIRST, e.last_name;

-- Orphans: departments with no employees. The FK makes e.department_id
-- trustworthy for this purpose.
SELECT d.department_id, d.department_name
FROM   hr.departments d
LEFT   JOIN hr.employees e ON e.department_id = d.department_id
WHERE  e.employee_id IS NULL;          -- a NOT NULL column on the optional side

The predicate-placement trap

This is the rule to memorise. A condition in the ON clause filters the right-hand rows before the outer join fills nulls, so unmatched left rows survive. The same condition in WHERE filters after the join, and since the right side is null for unmatched rows, it removes them — silently turning your outer join back into an inner one. If the filter is genuinely optional, put it in ON; if it is mandatory, it belongs in WHERE and you probably want an inner join.

-- SQL - same words, opposite results
-- Keeps every employee; only the DEPARTMENT data is filtered.
SELECT e.last_name, d.department_name
FROM   hr.employees   e
LEFT   JOIN hr.departments d
       ON d.department_id = e.department_id
      AND d.location_id  = 1700;

-- Contradicts the outer join: drops every employee without a match.
SELECT e.last_name, d.department_name
FROM   hr.employees   e
LEFT   JOIN hr.departments d ON d.department_id = e.department_id
WHERE  d.location_id = 1700;

FULL OUTER JOIN and anti-joins

FULL OUTER JOIN is the set union of left-outer and right-outer; it is the right tool for reconciliation, where you want rows present on either side plus rows that disagree. It is also the slowest of the three, because both sides must be preserved, so the optimizer cannot simply pick a driving table and probe. For "find differences between two tables" it is clearer than two anti-joins and one UNION ALL.

-- SQL - reconcile two versions of a feed
SELECT NVL(a.id, b.id)              AS id,
       a.amount                      AS legacy_amount,
       b.amount                      AS new_amount,
       CASE WHEN a.id IS NULL THEN 'only in NEW'
            WHEN b.id IS NULL THEN 'only in LEGACY'
            WHEN a.amount <> b.amount THEN 'amount differs'
            ELSE 'match' END         AS verdict
FROM   legacy_amounts a
FULL   OUTER JOIN new_amounts b ON b.id = a.id
WHERE  a.id IS NULL OR b.id IS NULL OR a.amount <> b.amount;

3.3 Cross joins and self joins

Two special shapes: one deliberately produces every combination, the other reads a table twice to answer a relationship between its own rows.

CROSS JOIN is multiplication, on purpose

CROSS JOIN returns every pairing; with m and n rows it produces m × n. Used deliberately it is a row generator: a handful of seed rows times a handful of dates times a handful of categories gives a dense grid for a report that must show zeros. The danger is the same operation happening by accident, which is what a forgotten join predicate produces; the classic symptom is a query that ran in a second yesterday and will not finish today because a dimension table grew.

-- SQL - a dense calendar grid: every location, every month
WITH months AS (
  SELECT ADD_MONTHS(DATE '2026-01-01', LEVEL - 1) AS month_start
  FROM   dual CONNECT BY LEVEL <= 12
),
locations AS (SELECT location_id FROM hr.locations WHERE country_id = 'US')
SELECT l.location_id, m.month_start
FROM   locations l
CROSS  JOIN months m
ORDER  BY l.location_id, m.month_start;

Self joins and the aliasing discipline

A self join needs two aliases; without them every column reference is ambiguous. The common shapes are the manager relationship (employee.manager_id = manager.employee_id) and the comparison-within-a-group shape where a row is compared to its siblings. Because the two references resolve to the same table, the optimizer reads the same blocks twice but usually only materialises the needed columns, so a self join is not automatically a double scan. An OUTER self join is what you need for a hierarchy's top node, whose manager is NULL.

-- SQL - the manager relationship, top node included
SELECT e.last_name  AS employee,
       m.last_name  AS manager
FROM   hr.employees e
LEFT   JOIN hr.employees m ON m.employee_id = e.manager_id
ORDER  BY manager NULLS FIRST, employee;

-- Compare a row with the highest salary in its own department
SELECT e.last_name, e.department_id, e.salary
FROM   hr.employees e
WHERE  e.salary = (SELECT MAX(x.salary) FROM hr.employees x
                   WHERE x.department_id = e.department_id);
When you self-join and the same table appears twice, the optimizer's row estimates for the second reference come from the same statistics, so both copies are assumed equally selective. When the two roles have very different cardinalities — a small manager set and a large employee set — the plan can be badly skewed. Create a VIEW with its own stats, or a materialised view, if the asymmetry is persistent.

3.4 ANSI joins versus Oracle's (+) operator

Oracle predates the ANSI join syntax and still accepts its own: a (+) suffix on every column of the optional side. Both are supported in 23ai, and both produce the same plans in almost every case.

Reading and writing (+)

The rule is mechanical: put (+) on the columns of the table whose rows may be missing — that is, the table that would be null-supplied. WHERE d.department_id = e.department_id (+) means "preserve employees", because the department side is optional. Getting it backwards is a silent logic error: the query still runs and still returns rows, just the wrong ones. With three or more tables the number of (+) marks needed grows and it becomes possible to write contradictions that Oracle rejects with ORA-01468.

-- SQL - the same left outer join, two ways
SELECT e.last_name, d.department_name
FROM   hr.employees e LEFT JOIN hr.departments d
       ON d.department_id = e.department_id;

SELECT e.last_name, d.department_name
FROM   hr.employees e, hr.departments d
WHERE  d.department_id (+) = e.department_id;

Why the ANSI form is the better default

The (+) syntax cannot express a FULL OUTER JOIN at all — there is no way to mark both sides. It cannot express an outer join whose ON predicate contains extra non-join conditions without moving them into a subquery, because there is no separate ON clause. And it silently converts an outer join into an inner one when you add a filter on the optional side, exactly like the WHERE-placement trap above. The ANSI form has none of these limits and is what the standard and every other database use.

-- SQL - the plus-syntax accident: this is an INNER join
SELECT e.last_name, d.department_name
FROM   hr.employees e, hr.departments d
WHERE  d.department_id (+) = e.department_id
AND    d.location_id = 1700;             -- kills the outer join

-- The intent, expressed unambiguously
SELECT e.last_name, d.department_name
FROM   hr.employees e
LEFT   JOIN hr.departments d
       ON d.department_id = e.department_id AND d.location_id = 1700;
There is no performance penalty for the ANSI syntax; the parser normalises both forms to the same internal representation and the optimizer sees one query. Convert to ANSI during normal maintenance rather than in a mass rewrite, so that each change can be tested.

3.5 How the optimizer actually joins: access paths

The join method is chosen from row estimates and access paths. Knowing the three algorithms tells you which statistic, index or rewrite will change the plan.

Nested loops, hash join, sort-merge

Nested loops reads a few rows from the driving table and probes the second table once per row — perfect when the outer set is small and the inner lookup is a unique or range index scan. Cost grows linearly with the outer row count, so a nested loop over a ten-million-row driver is a disaster. Hash joins build an in-memory hash table from the smaller input and stream the larger one through it — the workhorse for large equality joins, and happy without any index at all. It needs a memory grant; if the build side does not fit, it spills to TEMP and the plan says HASH JOIN (Temp). Sort-merge joins sort both inputs on the join key and merge; they are the right choice when the join is a range or inequality rather than an equality, and when both inputs are already sorted by the key because of an index.

MethodBest whenFails whenPlan marker
Nested loopsSmall driving set, indexed inner tableLarge driver, no usable indexNESTED LOOPS
Hash joinLarge sets, equality join, no useful indexTiny tables (build overhead dominates)HASH JOIN
Sort-mergeRange or inequality join, pre-sorted inputsInputs need expensive sortsMERGE JOIN

Making the plan you want reachable

You influence the join method indirectly: accurate statistics, a usable index on the inner table's join column, and a predicate that lets the optimizer estimate the driving cardinality. Hints exist (/*+ USE_HASH(t s) */, /*+ LEADING(s t) */, /*+ USE_NL(t) */) but a hint that depends on today's data distribution becomes tomorrow's regression, because it overrides the estimate. Fix the statistics or the index first; hint only where the optimizer cannot know something you do, and document why.

-- SQL - ask for the plan (does not execute the query)
EXPLAIN PLAN FOR
SELECT d.department_name, e.last_name
FROM   hr.departments d
JOIN   hr.employees   e ON e.department_id = d.department_id
WHERE  d.location_id = 1700;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY(format => 'BASIC +ROWS +PREDICATE'));

-- The access path on the inner table is what decides the method
SELECT index_name, column_name, column_position
FROM   user_ind_columns WHERE table_name = 'EMPLOYEES' ORDER BY index_name, column_position;
In SQLcl there is no GUI, but there is a much better plan than EXPLAIN PLAN: run the query with /*+ GATHER_PLAN_STATISTICS */ and then DBMS_XPLAN.DISPLAY_CURSOR(format => 'ALLSTATS LAST'). That shows actual rows (A-Rows) beside estimates (E-Rows), and a large gap is the diagnosis. EXPLAIN PLAN alone never runs the query and can therefore be wrong about runtime filters.

4 · Subqueries and set operators

A query inside a query is how SQL composes. The two things to get right are whether the inner query runs once or once per outer row, and whether you meant a filter or a set operation.

4.1 Scalar subqueries and inline views

A scalar subquery returns at most one row and one column and can be used anywhere an expression is allowed; an inline view is a subquery in FROM and behaves like a table.

Scalar subqueries behave like expressions

Because the result is a single value, a scalar subquery can appear in the SELECT list, in WHERE, and even in ORDER BY. If it returns zero rows the value is NULL; if it returns more than one row the statement fails with ORA-01427: single-row subquery returns more than one row. That failure is a feature — it tells you the data does not match your assumption — but it means you should never write one against a column you have not proven unique. The optimizer may evaluate a correlated scalar subquery once per row or transform it into an outer join; the SELECT-list version is frequently rewritten to an outer join automatically, which is why it can be surprisingly fast.

-- SQL - scalar subqueries as values
SELECT e.last_name,
       e.salary,
       (SELECT ROUND(AVG(x.salary)) FROM hr.employees x
        WHERE x.department_id = e.department_id)     AS dept_avg,
       e.salary - (SELECT ROUND(AVG(x.salary)) FROM hr.employees x
                   WHERE x.department_id = e.department_id) AS diff
FROM   hr.employees e
WHERE  e.department_id = 50
ORDER  BY diff DESC;

An inline view is a named intermediate result

Anything the language forbids at one level can be done in an inline view and filtered at the next: window functions cannot be filtered in the same SELECT, so you compute them inside and filter outside. The optimizer can usually merge or push predicates through the view (view merging), so an inline view is not automatically materialised — but it can be, and when it is, the plan shows VIEW followed by TABLE ACCESS FULL. If you need the intermediate result guaranteed, WITH ... AS MATERIALIZED, or the MATERIALIZE hint, settles it.

-- SQL - an inline view is the only way to filter a window function
SELECT department_id, last_name, salary, rn
FROM  (SELECT department_id, last_name, salary,
              ROW_NUMBER() OVER (PARTITION BY department_id
                                 ORDER BY salary DESC) AS rn
       FROM   hr.employees)
WHERE  rn <= 3
ORDER  BY department_id, rn;
A subquery in the FROM clause must have an alias, or you get ORA-00933 or ORA-00918 depending on the version. Always alias it and always name its columns; a view named x with column_1 tells the next reader nothing.

4.2 Correlated subqueries, IN and EXISTS

A correlated subquery references a column of the outer query, so conceptually it runs once per outer row. Whether it actually does is an optimizer decision, and it is usually the decision that matters.

Correlation is semantics, not a loop

Writing WHERE EXISTS (SELECT 1 FROM t2 WHERE t2.k = t1.k) describes a semi-join: keep outer rows for which at least one inner row matches. The optimizer is free to implement that as a nested-loop probe, a hash semi-join, or anything else — and it stops looking as soon as it finds a match, which is a real advantage over a join that would materialise every match. A correlated scalar subquery, by contrast, must produce a value, so it is fundamentally a per-row lookup unless rewritten.

IN versus EXISTS is the classic comparison. EXISTS is a predicate: it never duplicates outer rows and it is null-safe, because a missing match is simply false. IN is a set membership test whose semantics break when the list contains NULL. On modern versions the optimizer unnests both into semi-joins and picks the same plan, so the deciding factor should be correctness and clarity: prefer EXISTS/NOT EXISTS, and reserve IN for a small literal list.

-- SQL - all three, and the one that is a landmine
SELECT * FROM hr.employees e
WHERE  EXISTS (SELECT 1 FROM hr.departments d
               WHERE d.department_id = e.department_id);         -- semi-join

SELECT * FROM hr.employees e
WHERE  e.department_id IN (SELECT d.department_id FROM hr.departments d);

-- NOT IN with a nullable inner column: silently returns nothing
SELECT * FROM hr.employees e
WHERE  e.department_id NOT IN (SELECT d.department_id FROM hr.departments d);

-- NOT EXISTS: correct and null-safe
SELECT * FROM hr.employees e
WHERE  NOT EXISTS (SELECT 1 FROM hr.departments d
                   WHERE d.department_id = e.department_id);

Unnesting and when it does not happen

Unnesting a correlated subquery into a join is a transformation with rules: it needs the correlated column to be equality-comparable, no ROWNUM in the subquery, no aggregate that cannot be pushed, and the tables to be joinable. When it cannot unnest, the plan shows a filter applied inside a nested loop and runtime grows with the outer row count. That is the case to watch for in production: a query that is fine at a thousand rows and fatal at a million. The fix is usually to rewrite the correlation as an explicit join with a GROUP BY, or to use an analytic function instead.

-- SQL - unnestable correlation, rewritten as a join
-- Per-row lookup version:
SELECT e.last_name, e.salary
FROM   hr.employees e
WHERE  e.salary > (SELECT AVG(x.salary) FROM hr.employees x
                   WHERE x.department_id = e.department_id);

-- Same result with one hash group-by and one hash join:
SELECT e.last_name, e.salary, a.dept_avg
FROM   hr.employees e
JOIN  (SELECT department_id, AVG(salary) AS dept_avg
       FROM   hr.employees GROUP BY department_id) a
  ON   a.department_id = e.department_id
WHERE  e.salary > a.dept_avg;
A correlated subquery in the SELECT list of a query that also has GROUP BY can be evaluated at the wrong level and return ORA-00979: not a GROUP BY expression, or worse, an answer that is technically legal and subtly wrong. When the subquery depends on a grouping key, join to a grouped inline view instead of correlating to the base table.

4.3 WITH: common table expressions

A WITH clause — subquery factoring — names a subquery and lets the rest of the statement refer to it multiple times. In Oracle it is less a performance tool than a readability one, but it has real optimiser interactions.

Naming intermediate results

A query with four levels of nesting becomes unreadable; the same query written as four named CTEs reads top to bottom. That alone is worth the syntax, because the reader sees each transformation once instead of guessing which inner alias means what. Beyond readability, a CTE referenced twice gives the optimizer the choice of materialising it once or inlining it both times: if the result is small and expensive, materialising is a large win; if it is large and cheap, inlining is. The MATERIALIZE and INLINE hints decide it explicitly, and 12.2 and later accept the SQL-standard AS MATERIALIZED spelling.

-- SQL - a linear pipeline is easier to read as CTEs than as nesting
WITH recent AS (
  SELECT employee_id, department_id, salary, hire_date
  FROM   hr.employees
  WHERE  hire_date >= ADD_MONTHS(SYSDATE, -60)
),
dept_totals AS (
  SELECT department_id, COUNT(*) AS headcount, AVG(salary) AS avg_salary
  FROM   recent GROUP BY department_id
)
SELECT r.employee_id, r.salary, t.headcount, t.avg_salary
FROM   recent r
JOIN   dept_totals t ON t.department_id = r.department_id
WHERE  r.salary > t.avg_salary;

Recursion and inline PL/SQL

WITH is also the host for the recursive form covered in the hierarchical chapter, and since 12c it can declare a PL/SQL function in the with clause: WITH FUNCTION f(x NUMBER) RETURN NUMBER IS ... END;. That is a surprisingly powerful feature — it lets you put a small function beside the query that uses it, instead of in a package — but it is compiled and cached per statement, so it must be deterministic and it will not be found by a PL/SQL profiler.

-- SQL - an inline function defined next to its query (12c and later)
WITH FUNCTION band(p_salary NUMBER) RETURN VARCHAR2 IS
BEGIN
  RETURN CASE WHEN p_salary <  5000 THEN 'LOW'
              WHEN p_salary < 12000 THEN 'MID'
              ELSE 'HIGH' END;
END;
SELECT band(salary) AS pay_band, COUNT(*) AS n
FROM   hr.employees
GROUP  BY band(salary)
ORDER  BY 1;
A CTE is not a temporary table and does not persist between statements. If a set of rows is genuinely reused by several statements — a filtered extract, a calculated cohort — a global temporary table (ON COMMIT PRESERVE ROWS) or a materialized view is the honest tool; forcing a CTE to be materialised for one statement does not share anything.

4.4 Set operators: UNION, UNION ALL, INTERSECT, MINUS

Set operators combine two result sets column-by-column by position, not by name. That single rule explains most of the errors people hit with them.

Named by position, deduplicated unless you say otherwise

UNION merges and removes duplicates, UNION ALL merges and keeps them, INTERSECT keeps rows in both, and MINUS (spelled EXCEPT since 21c) keeps rows in the first query that are absent from the second. Duplicate removal means a sort or hash, so UNION ALL is almost always faster and is the right default when the two branches cannot overlap — a partitioned archive plus a current table, for example. If they can overlap, deduplication is the point and you pay for it once.

The column count and the type of each position must be compatible. Oracle uses the first query's column names for the result and takes the widest type, converting as needed. It does not match by name, so a UNION of two six-column queries with the columns in a different order produces garbage without a single warning — always list columns explicitly and keep the order identical.

-- SQL - set operators, with the duplicate question answered deliberately
SELECT employee_id FROM hr.employees WHERE department_id = 50
UNION ALL
SELECT employee_id FROM hr.employees WHERE department_id = 80;

-- Rows in one table and not the other: data-drift detection
SELECT product_id FROM products_legacy
MINUS
SELECT product_id FROM products;

-- Since 21c, EXCEPT is a synonym for MINUS
SELECT product_id FROM products
EXCEPT
SELECT product_id FROM products_archive;

Precedence, ORDER BY and the NULL question

Set operators have equal precedence and are evaluated left to right, unlike the arithmetic operators; parenthesise when mixing three or more. ORDER BY applies to the whole combined result, must appear once, at the end, and may only use column names or positions from the first query. Finally, duplicate detection treats two NULLs as equal — set semantics are not three-valued — so INTERSECT and MINUS do match null to null even though = does not. That is the behaviour you want for comparing two tables, and it is different from what WHERE a = b would do.

-- SQL - one ORDER BY for the whole union, and explicit grouping
(SELECT 'employee' AS src, employee_id AS id FROM hr.employees)
UNION ALL
(SELECT 'manager', manager_id FROM hr.employees WHERE manager_id IS NOT NULL)
ORDER BY src, id;
A UNION of two queries that each scan the same large table is often a sign that one SELECT with an OR, or a CASE, would do — and the single-scan version lets the optimizer choose one access path instead of two. Reach for set operators when the sources are genuinely different, not to express a filter.

5 · Aggregation and grouping

Aggregation collapses many rows into one. The mechanics are simple; the subtleties are all about NULL, about which rows are in the group, and about where the totals come from.

5.1 Aggregate functions and the NULL they ignore

Every aggregate except COUNT(*) skips nulls. That is the single fact behind most wrong averages ever published.

The core set, and what each one does with nulls

COUNT(*) counts rows; COUNT(expr) counts non-null values of the expression; the difference between them is the number of rows where the expression is null. SUM, AVG, MIN and MAX all ignore null inputs, which means AVG(commission_pct) averages only the employees who earn commission, not all employees — a materially different number, and the one a business reader usually does not expect. If you want nulls to count as zero, write AVG(NVL(x,0)) and accept that you have changed the definition.

An aggregate over zero rows is a special case: SUM, AVG, MIN and MAX return NULL, while COUNT returns 0. That is why a report showing a blank total usually means "no rows matched", not "the total failed to compute", and why wrapping the total in NVL(..., 0) hides a genuine empty-selection bug.

-- SQL - the two averages, both correct, both different
SELECT COUNT(*)                       AS employees,
       COUNT(commission_pct)          AS commissioned,
       ROUND(AVG(commission_pct), 4)  AS avg_over_commissioned,
       ROUND(AVG(NVL(commission_pct,0)), 4) AS avg_over_all
FROM   hr.employees;

-- Aggregates over zero rows: SUM is null, COUNT is zero
SELECT COUNT(*) AS c, SUM(salary) AS s
FROM   hr.employees WHERE department_id = -1;

DISTINCT inside an aggregate, and the statistical family

COUNT(DISTINCT x) is supported and is usually a sort or hash over the values; SUM(DISTINCT x) is legal but rarely what anyone means, so if you write it, be sure. Beyond the core set, Oracle ships the statistics (STDDEV, VARIANCE, MEDIAN, CORR, REGR_*), which all ignore nulls in the same way. MEDIAN is not a percentile shorthand — it is the actual median, and it is far more robust than a mean for anything with a long tail, such as time-to-resolve or transaction size.

-- SQL - distinct counting and dispersion
SELECT department_id,
       COUNT(*)                              AS n,
       COUNT(DISTINCT job_id)                AS distinct_jobs,
       ROUND(AVG(salary))                    AS mean_pay,
       MEDIAN(salary)                        AS median_pay,
       ROUND(STDDEV(salary))                 AS sd
FROM   hr.employees
WHERE  department_id IS NOT NULL
GROUP  BY department_id
ORDER  BY n DESC;
When a mean and a median disagree strongly, the distribution has a tail and the mean is the wrong summary to publish. Reporting both, with the row count, costs nothing and prevents the "average handle time is four minutes, but nobody's call took four minutes" conversation.

5.2 GROUP BY, HAVING and the shape of the result

Everything in the SELECT list must be either an aggregate or a grouping key. That rule is the whole design of GROUP BY, and the optimizer's main grouping strategies follow from it.

Every non-aggregated column must be grouped

If you select a column that is neither aggregated nor listed in GROUP BY, Oracle raises ORA-00979. This is not pedantry: a group of many rows has no single value for that column, so the database would have to pick one arbitrarily. The corollary is that grouping by a high-cardinality column (a VARCHAR2 timestamp, an unnormalised description) makes groups of size one and produces a result indistinguishable from the ungrouped table, at the cost of a sort. Group by keys, not by everything.

Grouping keys can be expressions, and the expression must match the one in the select list or the group key is a different value. Since Oracle 23ai you may also GROUP BY a column alias from the select list, which removes the duplicate-expression annoyance; on older releases repeat the expression or wrap the whole thing in an inline view.

-- SQL - grouping on an expression, keeping the two identical
SELECT TRUNC(hire_date, 'YYYY') AS hire_year,
       COUNT(*)                 AS hires,
       MIN(salary)              AS lowest
FROM   hr.employees
GROUP  BY TRUNC(hire_date, 'YYYY')      -- must match the SELECT expression
ORDER  BY hire_year;

-- 23ai: GROUP BY can use the select-list alias
SELECT TRUNC(hire_date, 'YYYY') AS hire_year, COUNT(*) AS hires
FROM   hr.employees
GROUP  BY hire_year
ORDER  BY hire_year;

HAVING filters groups, WHERE filters rows

WHERE runs before grouping and removes rows; HAVING runs after grouping and removes whole groups. Putting a row filter in HAVING is legal when it references only grouped columns, but it is a performance mistake: the database builds groups for rows it will then discard. Push every predicate that does not mention an aggregate into WHERE, and keep HAVING for aggregate conditions such as HAVING COUNT(*) > 5 or HAVING SUM(amount) > 100000.

-- SQL - filter rows early, filter groups late
SELECT department_id,
       COUNT(*)      AS headcount,
       SUM(salary)   AS payroll
FROM   hr.employees
WHERE  hire_date >= DATE '2015-01-01'          -- rows: cheap, uses the plan
GROUP  BY department_id
HAVING SUM(salary) > 100000                     -- groups: after aggregation
ORDER  BY payroll DESC;
Two rows that look identical can belong to different groups if the group key differs only in how it is stored — a trailing space in a CHAR, a different case, a different timezone offset in a timestamp column. Group by a normalised value (UPPER(TRIM(code))) when the source data may vary, and expect that expression to need a function-based index if it is on a hot path.

5.3 Subtotals with ROLLUP, CUBE and GROUPING SETS

These three extensions produce multiple grouping levels in one pass, replacing the UNION ALL of several grouped queries that people used to write.

ROLLUP is hierarchical, CUBE is exhaustive

GROUP BY ROLLUP(a, b, c) produces the detail rows, then subtotals dropping c, then dropping b as well, then the grand total — the collapsed levels of a report. GROUP BY CUBE(a, b, c) produces every combination, eight grouping sets from three columns, which is 2n and grows fast enough to be a problem at five or six columns. GROUPING SETS is the explicit form: list only the combinations you actually need, so a three-way report can be three grouping sets instead of eight.

Because these produce several grouping levels in a single pass, the optimizer can share one sort or hash across them, which is why a ROLLUP is usually far cheaper than the equivalent UNION ALL of four grouped queries — it reads the base table once instead of four times. The trade is that the result contains levels of differing granularity, so any consumer that simply sums a column without checking GROUPING will double-count the subtotals. Expose the levels explicitly, or filter the query to the one level the consumer wants.

-- SQL - one pass, four levels of totals
SELECT d.department_id,
       j.job_id,
       SUM(e.salary)                       AS payroll,
       GROUPING_ID(d.department_id, j.job_id) AS gid
FROM   hr.employees   e
JOIN   hr.departments d ON d.department_id = e.department_id
JOIN   hr.jobs        j ON j.job_id        = e.job_id
GROUP  BY ROLLUP(d.department_id, j.job_id)
ORDER  BY d.department_id NULLS LAST, j.job_id NULLS LAST;

Telling a real null from a subtotal null

In a ROLLUP result, NULL means "this level was rolled up" — but a genuine NULL in the data looks identical. The GROUPING(expr) function returns 1 for a rolled-up level and 0 for a real value; GROUPING_ID(...) packs the bits into one number so you can order and filter by level. Without it, a subtotal row and a group whose key is genuinely null are indistinguishable, which is a correctness bug, not a cosmetic one.

-- SQL - label the levels so subtotals are never mistaken for data
SELECT CASE GROUPING(d.department_id)
         WHEN 1 THEN 'ALL DEPARTMENTS'
         ELSE TO_CHAR(d.department_id)
       END                                  AS dept,
       CASE GROUPING(j.job_id)
         WHEN 1 THEN 'ALL JOBS'
         ELSE j.job_id
       END                                  AS job,
       SUM(e.salary)                        AS payroll
FROM   hr.employees   e
JOIN   hr.departments d ON d.department_id = e.department_id
JOIN   hr.jobs        j ON j.job_id        = e.job_id
GROUP  BY ROLLUP(d.department_id, j.job_id)
HAVING GROUPING_ID(d.department_id, j.job_id) IN (0, 3)  -- detail + grand total
ORDER  BY GROUPING_ID(d.department_id, j.job_id);
GROUPING SETS is also the cleanest way to compute several independent aggregates in one scan, because Oracle can share the sort or hash between sets. Compare the plan of a UNION ALL of three grouped queries with the single GROUP BY GROUPING SETS version; the one that reads the base table once is usually the winner.

5.4 PIVOT and UNPIVOT: reshaping rows and columns

PIVOT turns distinct values of one column into columns; UNPIVOT does the reverse. Both are pure syntactic sugar over conditional aggregation, and the plan is usually the same.

PIVOT replaces the CASE-with-SUM pattern

Before PIVOT existed, a cross-tab was written as SUM(CASE WHEN month = 1 THEN amount END) repeated twelve times. PIVOT states the operation once and generates those expressions, which makes the intent visible and the wide result set mechanical. The catch is that the pivot values must be literals known at parse time: you cannot pivot on the distinct values of a column discovered at runtime. A dynamic cross-tab whose column set changes monthly needs dynamic SQL (DBMS_SQL or EXECUTE IMMEDIATE), or a client-side pivot.

-- SQL - quarterly payroll per department, as columns
SELECT *
FROM  (SELECT d.department_name AS dept,
              TO_CHAR(e.hire_date,'Q') AS qtr,
              e.salary
       FROM   hr.employees e
       JOIN   hr.departments d ON d.department_id = e.department_id)
PIVOT (SUM(salary) FOR qtr IN ('1' AS q1, '2' AS q2, '3' AS q3, '4' AS q4))
ORDER  BY dept;

UNPIVOT is for feeding a reporting tool

The reverse direction is common when a legacy table has one column per period and a modern tool expects one row per period. UNPIVOT names the source columns explicitly and produces a key/value pair per row. INCLUDE NULLS is a deliberate choice: by default null columns are dropped, which is usually right for a sparse table and wrong when a missing reading is itself the signal.

-- SQL - wide to long, keeping the nulls so gaps are visible
WITH quarterly AS (
  SELECT 50 AS dept_id, 1000 AS q1, 1200 AS q2, NULL AS q3, 900 AS q4 FROM dual
)
SELECT dept_id, quarter, amount
FROM   quarterly
UNPIVOT INCLUDE NULLS (amount FOR quarter IN (q1 AS 'Q1', q2 AS 'Q2', q3 AS 'Q3', q4 AS 'Q4'))
ORDER  BY dept_id, quarter;
A PIVOT over a column with many distinct values produces a very wide result, and every column has to be named in the IN list. If that list is generated, it becomes a SQL-text-generation problem with the usual injection and hard-parse concerns. Generate the list from the dictionary, validate it, and keep the number of pivoted columns bounded.

5.5 LISTAGG and string aggregation

Collapsing many strings into one delimited string is a request that arrives constantly and has a hard limit that people discover in production.

Ordering and overflow

LISTAGG(col, ',') WITHIN GROUP (ORDER BY col) concatenates the values in the group in the given order. The order is mandatory, because concatenation is not commutative and a report that changes delimiter order between runs is not reproducible. The result is a VARCHAR2 and is capped at the 4000-byte (or 32,767-byte with extended string sizes) SQL limit, which a real group of a few hundred values will exceed, producing ORA-01489: result of string concatenation is too long. Since 12.2 the standard fix is ON OVERFLOW TRUNCATE, optionally with a marker and a count.

-- SQL - a delimited list, with a defined order and a defined overflow
SELECT department_id,
       LISTAGG(last_name, ', ' ON OVERFLOW TRUNCATE '...' WITH COUNT)
         WITHIN GROUP (ORDER BY last_name) AS members
FROM   hr.employees
WHERE  department_id IN (50, 80)
GROUP  BY department_id;

Distinct values, and the alternatives

LISTAGG(DISTINCT col, ',') works and internally sorts and deduplicates, which is a real cost on a large group. The historical alternative is XMLAGG with XMLElement, which escapes and returns an XMLTYPE that must be cast back; its advantage was never running out of string space, and it is now mostly of archaeological interest. In 19c and later, if the values are numeric or you need a nested structure, JSON_ARRAYAGG and JSON_OBJECTAGG produce JSON directly and remove the delimiter-escaping problem entirely — a value containing the delimiter cannot corrupt the result.

-- SQL - JSON aggregation: no delimiter can break the output
SELECT department_id,
       JSON_ARRAYAGG(last_name ORDER BY last_name RETURNING CLOB) AS members_json
FROM   hr.employees
WHERE  department_id = 50
GROUP  BY department_id;

-- Distinct members with the legacy XMLAGG technique (no length limit)
SELECT department_id,
       RTRIM(XMLCAST(XMLAGG(XMLELEMENT(e, job_id || ',') ORDER BY job_id) AS CLOB), ',') AS job_list
FROM   hr.employees
GROUP  BY department_id;
If the consumer is going to split the string again, you have chosen the wrong transport. JSON arrays survive embedded commas, quotes and newlines; a comma-delimited string does not, and the escaping rules for CSV are more subtle than they look. Use LISTAGG for a human-readable summary and JSON for a machine-readable one.

6 · Analytic (window) functions

Analytic functions compute a value across a set of rows related to the current row, without collapsing those rows. They are the single most useful part of modern SQL and the hardest to reason about until the window frame clicks.

6.1 The OVER clause: partitioning and ordering

OVER defines the window. PARTITION BY splits the rows into independent groups; the optional ORDER BY within the window makes positions and running values meaningful.

What the window is

A window function is evaluated after WHERE, GROUP BY and HAVING, and before ORDER BY and DISTINCT — but it sees the rows of the result set, not the rows of the base table when a GROUP BY has already run. Each PARTITION BY value is an independent window; the function restarts for each. No PARTITION BY means one window over the whole result, which is exactly what you want for "share of the total". Mixing a regular aggregate and a window in the same query is legal and useful: the aggregate collapses the group, and the window then operates over the collapsed rows.

-- SQL - a plain aggregate beside a window over the same rows
SELECT department_id,
       SUM(salary)                              AS dept_payroll,
       salary,
       ROUND(salary / SUM(salary) OVER (PARTITION BY department_id) * 100, 1)
                                                AS pct_of_dept
FROM   hr.employees
WHERE  department_id = 50
ORDER  BY salary DESC;

Named windows save repetition and prevent drift

When several analytic functions share the same partition and order, an inline WINDOW clause gives that specification a name — WINDOW w AS (PARTITION BY a ORDER BY b) — and every function refers to OVER w. This is worth doing for more than brevity: a copy-pasted window that differs in one word produces two functions that silently disagree, and naming the window makes that disagreement impossible. Named windows are available in 21c and later.

-- SQL - one window, several functions, no chance of drift
SELECT last_name,
       department_id,
       salary,
       ROW_NUMBER() OVER w AS seq,
       RANK()       OVER w AS rnk,
       AVG(salary)  OVER w AS running_avg
FROM   hr.employees
WHERE  department_id IN (50, 60)
WINDOW w AS (PARTITION BY department_id ORDER BY salary DESC)
ORDER  BY department_id, seq;
A window function is not allowed in WHERE, GROUP BY or HAVING. The reason is the evaluation order: those clauses run before the window exists. Put the function in an inline view or a CTE and filter in the outer query. On 23ai, QUALIFY is the standard clause that lets you filter on a window function directly; on 19c you must nest.

6.2 ROW_NUMBER, RANK and DENSE_RANK

Three functions answer three different questions about "position", and choosing the wrong one gives a plausible wrong number rather than an error.

The difference in one example

ROW_NUMBER gives a strict 1, 2, 3, 4 sequence and never repeats or skips, breaking ties arbitrarily (or by whatever ORDER BY you supplied). RANK gives equal values the same rank and then skips: two rows tied at 1 are followed by a rank of 3. DENSE_RANK also gives ties the same rank but does not skip: two rows at 1 are followed by 2. So if the question is "which row is the latest per key", use ROW_NUMBER; if it is "what is this employee's rank in the pay scale", use RANK because the next distinct salary really is two places down; if it is "how many distinct pay levels are there", use DENSE_RANK.

-- SQL - the three side by side, deliberately with ties
WITH pay(id, name, salary) AS (
  SELECT 1, 'Ada',   9000 FROM dual UNION ALL
  SELECT 2, 'Grace', 9000 FROM dual UNION ALL
  SELECT 3, 'Linus', 8000 FROM dual UNION ALL
  SELECT 4, 'Barbara', 7000 FROM dual
)
SELECT id, name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn,
       RANK()       OVER (ORDER BY salary DESC) AS rk,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS dr
FROM   pay
ORDER  BY salary DESC, id;

The top-N-per-group pattern

This is the canonical use: rank rows within each partition and keep the ones you want. The tie-breaking decision is the whole design. If you rank by salary DESC alone, ties are broken arbitrarily and the result can differ between runs; add a unique column such as employee_id to the ORDER BY to make the result reproducible. If ties should all survive — "everyone in the top three salaries" — rank with DENSE_RANK and filter <= 3, which correctly returns four rows when the third and fourth tie.

-- SQL - top two earners per department, deterministic
SELECT department_id, last_name, salary, rn
FROM  (SELECT department_id, last_name, salary,
              ROW_NUMBER() OVER (PARTITION BY department_id
                                 ORDER BY salary DESC, employee_id) AS rn
       FROM   hr.employees
       WHERE  department_id IS NOT NULL)
WHERE  rn <= 2
ORDER  BY department_id, rn;
ROW_NUMBER plus WHERE rn <= n is usually faster than a correlated TOP-N subquery and always faster than DISTINCT plus a self join. Optimizers recognise the pattern and can stop the sort early; the reason to prefer it is as much about the plan as about the syntax.

6.3 LAG, LEAD, FIRST_VALUE and LAST_VALUE

These functions read another row of the same window without a self join. They are how you compute deltas, gaps and change flags in one pass.

Reading the previous and next row

LAG(expr, offset, default) returns expr from the row offset rows before the current one in window order; LEAD looks forward. The offset defaults to 1 and the default to NULL, which is why the first row of each partition has a NULL previous value and why a diff column is blank on the first row. Supplying an explicit default — a zero, or the current row's own value — is what turns the output into something a chart can plot. Both functions accept multiple expressions in one call in 21c and later, which removes the need to list them twice.

-- SQL - month-over-month movement, with an explicit first value
WITH monthly AS (
  SELECT TRUNC(hire_date,'MM') AS mth, COUNT(*) AS hires
  FROM   hr.employees GROUP BY TRUNC(hire_date,'MM')
)
SELECT mth,
       hires,
       LAG(hires, 1, 0) OVER (ORDER BY mth)              AS prev_hires,
       hires - LAG(hires, 1, 0) OVER (ORDER BY mth)      AS change,
       ROUND((hires - LAG(hires) OVER (ORDER BY mth))
             / NULLIF(LAG(hires) OVER (ORDER BY mth), 0) * 100, 1) AS pct_change
FROM   monthly
ORDER  BY mth;

FIRST_VALUE, LAST_VALUE and the frame that explains them

FIRST_VALUE returns the first row of the window; LAST_VALUE returns the last row of the current frame, which is not the same thing. With the default frame for an ordered window — RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — the "last value" is the current row, so LAST_VALUE appears to do nothing. The fix is to widen the frame explicitly: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. This behaviour surprises almost everyone once; understanding it once explains the whole notion of a frame.

-- SQL - first hire and most recent hire, on every row
SELECT department_id, last_name, hire_date,
       FIRST_VALUE(last_name) OVER (PARTITION BY department_id
                                    ORDER BY hire_date
                                    ROWS BETWEEN UNBOUNDED PRECEDING
                                             AND UNBOUNDED FOLLOWING) AS first_hired,
       LAST_VALUE(last_name)  OVER (PARTITION BY department_id
                                    ORDER BY hire_date
                                    ROWS BETWEEN UNBOUNDED PRECEDING
                                             AND UNBOUNDED FOLLOWING) AS last_hired
FROM   hr.employees
WHERE  department_id IN (50, 60)
ORDER  BY department_id, hire_date;
NTH_VALUE(expr, n) returns the nth row of the frame and has the same frame sensitivity as LAST_VALUE. It also accepts FROM FIRST or FROM LAST, which decides whether n counts up from the start of the frame or down from its end — a distinction that only matters once IGNORE NULLS enters the picture, which it can.

6.4 Running totals and window frames

A frame is the subset of the window that a function actually sees. It is optional for ranking functions and essential for any cumulative or moving calculation.

ROWS, RANGE and GROUPS

ROWS counts physical rows: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW is exactly three rows. RANGE counts by value: with RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW every row with the same sort value as the current row is included, so ties all see the same cumulative total — a real difference for a running total over a date with duplicate dates. GROUPS, added in 21c, counts peer groups: GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW means the current run of equal values plus the previous run. When in doubt for a running total, ROWS is the safer default because it depends on nothing but position, and the result is stable even if another row with the same key is inserted.

-- SQL - running total, three-row moving average, and a full-window average
SELECT last_name, hire_date, salary,
       SUM(salary) OVER (ORDER BY hire_date, employee_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_pay,
       ROUND(AVG(salary) OVER (ORDER BY hire_date, employee_id
                               ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)) AS moving_avg3,
       ROUND(AVG(salary) OVER ()) AS overall_avg
FROM   hr.employees
WHERE  department_id = 50
ORDER  BY hire_date, employee_id;

The default frame and the omission that bites

If you write OVER (ORDER BY x) with no frame and the function is an aggregate such as SUM, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — a running total by value. If you write OVER () with no ORDER BY at all, the frame is the whole partition, so SUM(salary) OVER () is the grand total on every row. The same function name therefore means three different things depending on two optional words, which is why every production analytic query should state its frame explicitly even when the default would do.

-- SQL - the same SUM, three frames, three answers
WITH t(d, amt) AS (
  SELECT DATE '2026-01-01', 100 FROM dual UNION ALL
  SELECT DATE '2026-01-01', 200 FROM dual UNION ALL
  SELECT DATE '2026-01-02',  50 FROM dual
)
SELECT d, amt,
       SUM(amt) OVER (ORDER BY d)                                   AS by_value_default,
       SUM(amt) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING
                                          AND CURRENT ROW)         AS by_row,
       SUM(amt) OVER ()                                             AS grand_total
FROM   t
ORDER  BY d, amt;
Frames can also exclude rows. 21c added EXCLUDE CURRENT ROW, EXCLUDE GROUP, EXCLUDE TIES and EXCLUDE NO OTHERS, which makes leave-one-out statistics trivial — a moving average that excludes the value being judged, or a department average that excludes the employee under review, without a self join.

6.5 Reporting aggregates: RATIO_TO_REPORT, NTILE and pivot-free shares

The remaining reporting functions turn a flat result into a report. Each replaces a self join you would otherwise write.

Shares and buckets

RATIO_TO_REPORT(x) OVER (PARTITION BY p) is x / SUM(x) over the partition, expressed once. It is convenient, and it is the classic way to divide by zero when a partition sums to zero — the function returns NULL in that case rather than raising ORA-01476, which is a defensible choice and worth knowing. NTILE(n) divides an ordered partition into n roughly equal buckets, useful for quartile or decile analysis: NTILE(4) labels every row 1 to 4, with the larger buckets first when the count does not divide evenly.

-- SQL - department share and pay quartile in one pass
SELECT last_name, department_id, salary,
       ROUND(RATIO_TO_REPORT(salary) OVER (PARTITION BY department_id) * 100, 2) AS pct_of_dept,
       NTILE(4) OVER (ORDER BY salary) AS pay_quartile
FROM   hr.employees
WHERE  department_id IN (50, 60)
ORDER  BY department_id, salary DESC;

KEEP (DENSE_RANK FIRST/LAST) and the aggregate-within-a-rank

Sometimes you want an aggregate of the rows that hold the extreme value of another column: "the highest salary in the department, and the job title of the person who earns it". MIN(salary) KEEP (DENSE_RANK FIRST ORDER BY salary) returns that; combine with MAX(...) and KEEP (DENSE_RANK LAST ...) to get the extremes and their attributes together. It has no exact equivalent in most other databases and it removes a self join from a very common report.

-- SQL - the top earner's job title, per department, in one row
SELECT department_id,
       MAX(salary)                                                   AS top_salary,
       MAX(job_id) KEEP (DENSE_RANK FIRST ORDER BY salary DESC, employee_id) AS top_job,
       COUNT(DISTINCT job_id)                                        AS distinct_jobs
FROM   hr.employees
WHERE  department_id IS NOT NULL
GROUP  BY department_id
ORDER  BY top_salary DESC;
Analytic functions force a sort (or two) over the partitioned input, and the sort is often the dominant cost of the query. When the OVER matches an existing index — the same leading columns, the same direction — the optimizer can read the index in order and skip the sort entirely. If a window function is the hottest part of a report, check whether an index on (partition_col, order_col) turns a SORT ORDER BY into a WINDOW SORT PUSHED RANK or removes the step altogether.

7 · Hierarchical and recursive queries

Oracle has two ways to walk a tree: its own CONNECT BY syntax, which predates the standard by twenty years, and the ANSI recursive WITH, which every other database also understands.

7.1 CONNECT BY PRIOR: walking a hierarchy

Hierarchical queries iterate the table against itself, using a PRIOR operator to say which side of the condition refers to the parent row.

START WITH, CONNECT BY and the direction of PRIOR

START WITH selects the roots; CONNECT BY PRIOR child_col = parent_col says how to get from one level to the next. The position of PRIOR is the entire syntax: PRIOR employee_id = manager_id walks downward from manager to reports, while PRIOR manager_id = employee_id walks upward from report to manager. Reading it as "the PRIOR side is the row I already have" makes it memorable. If you start from a leaf and walk up, you get the ancestor path; if you start from the root and walk down, you get the subtree.

Oracle evaluates this as a row-source that loops, either by index lookup per level or, when the tree is large and the connection has no usable index, by a sort-based algorithm that is considerably slower. The manager_id column should therefore be indexed; without one, each level can scan the whole table.

-- SQL - the organisation chart, top down from the CEO
SELECT LEVEL        AS depth,
       LPAD(' ', (LEVEL - 1) * 2) || last_name AS org_tree,
       employee_id, manager_id
FROM   hr.employees
START  WITH manager_id IS NULL
CONNECT BY PRIOR employee_id = manager_id
ORDER  SIBLINGS BY last_name;

Cycle protection and the pseudocolumns

Real data has cycles — a manager chain that loops because of a bad import — and an unguarded CONNECT BY on a cycle runs until it runs out of memory, with ORA-01436: CONNECT BY loop in user data as the friendly outcome. CONNECT BY NOCYCLE tells Oracle to stop when it reaches a row it has already seen on the current path, and the CONNECT_BY_ISCYCLE pseudocolumn then flags the row that closed the loop so you can report it. LEVEL is the depth (1 for the root), and CONNECT_BY_ISLEAF is 1 for a node with no children, which is the standard way to select only the leaves of a tree.

-- SQL - find the cycles instead of crashing on them
SELECT employee_id, manager_id, LEVEL, CONNECT_BY_ISCYCLE AS cycle_here
FROM   org_nodes
START  WITH manager_id IS NULL
CONNECT BY NOCYCLE PRIOR employee_id = manager_id
AND    CONNECT_BY_ISCYCLE = 1;

-- Leaves only
SELECT employee_id, last_name FROM hr.employees
WHERE  CONNECT_BY_ISLEAF = 1
START  WITH manager_id IS NULL
CONNECT BY PRIOR employee_id = manager_id;
LEVEL and the other pseudocolumns exist only in the SELECT list of the hierarchical query itself; you cannot refer to them in an enclosing view without re-exposing them. If a report needs depth as a normal column, that is one more argument for the recursive WITH form, where the depth is an ordinary column you define.

7.2 SYS_CONNECT_BY_PATH, CONNECT_BY_ROOT and ordering

Three features turn a hierarchy query into something a human can read: the full path, the root of each branch, and siblings sorted at every level.

The path string and the root value

SYS_CONNECT_BY_PATH(column, delimiter) accumulates the value of column from the root to the current row. The delimiter must be a character that cannot appear in the data, or the path is ambiguous — use '/' for paths and something like '|' for free text. CONNECT_BY_ROOT column returns the root row's value on every descendant row, which is the cheapest way to tag a whole subtree with the branch it belongs to; it is far clearer than joining back to a WHERE pid IS NULL query. ORDER SIBLINGS BY sorts each level independently while preserving the tree structure, which is the only ordering that produces correct indentation.

-- SQL - full path, root tag, and per-level ordering
SELECT LEVEL   AS depth,
       CONNECT_BY_ROOT last_name                       AS branch_root,
       SYS_CONNECT_BY_PATH(last_name, '/')             AS full_path,
       last_name,
       CONNECT_BY_ISLEAF                               AS is_leaf
FROM   hr.employees
START  WITH manager_id IS NULL
CONNECT BY PRIOR employee_id = manager_id
ORDER  SIBLINGS BY last_name;

The limitations to plan around

A path string is capped by the SQL string limit, so a very deep tree can overflow it with ORA-01489 just as LISTAGG can. Both path functions are also only available in the CONNECT BY form, so code that must run on another database cannot use them. And an incremental update is not possible: changing a node's parent moves its whole subtree, and any materialised path column kept in the table must be recomputed for every descendant. If you are storing paths as data, keep them consistent with a trigger or a package, or derive them on read and accept the cost.

-- SQL - which departments sit under each manager, as a path
SELECT manager_path, COUNT(*) AS reports
FROM  (SELECT SYS_CONNECT_BY_PATH(last_name,' / ') AS manager_path, employee_id
       FROM   hr.employees
       START  WITH manager_id IS NULL
       CONNECT BY PRIOR employee_id = manager_id)
GROUP  BY manager_path
ORDER  BY reports DESC FETCH FIRST 10 ROWS ONLY;
Indentation built with LPAD of a multiplied level number only looks right in a fixed-width font. For anything a user will see, emit LEVEL as a plain number and let the presentation layer indent — a client can then collapse branches, which a string of spaces can never support.

7.3 Recursive WITH: the standard alternative

A recursive CTE has an anchor member and a recursive member joined with UNION ALL. It is more verbose than CONNECT BY and considerably more flexible.

The shape, and why the column list is mandatory

WITH t (id, parent_id, lvl) AS ( ... anchor ... UNION ALL ... recursive ... ) requires the column list, because a recursive member cannot be named if the anchor has not been read. The anchor selects the roots; the recursive member joins the CTE to the base table and increments the depth, and UNION ALL (never UNION) feeds the result back in. Oracle evaluates it by repeatedly running the recursive member against the rows produced in the previous iteration, which is how it terminates naturally on a regular tree. Unlike CONNECT BY, the recursion can involve more than one table, can aggregate inside the step, and can carry a cumulative total.

-- SQL - the same tree, recursively, with an explicit depth
WITH org (employee_id, manager_id, last_name, lvl) AS (
  SELECT employee_id, manager_id, last_name, 1
  FROM   hr.employees
  WHERE  manager_id IS NULL
  UNION ALL
  SELECT e.employee_id, e.manager_id, e.last_name, o.lvl + 1
  FROM   hr.employees e
  JOIN   org o ON o.employee_id = e.manager_id
)
SELECT lvl, LPAD(' ', (lvl - 1) * 2) || last_name AS indented, employee_id
FROM   org
ORDER  BY lvl, last_name;

Cycle handling and breadth-versus-depth order

Because the recursion is a query you control, you can break cycles by carrying the visited set: accumulate the ids in a VARCHAR2 path column and add AND INSTR(path, '/' || to_char(e.employee_id) || '/') = 0 to the recursive member. More formally, Oracle 11g R2 and later support the SQL-standard clauses SEARCH DEPTH FIRST BY ... SET order_col and SEARCH BREADTH FIRST BY ... SET order_col, plus CYCLE col SET is_cycle TO 1 DEFAULT 0, which does the same bookkeeping declaratively. Compare with the NOCYCLE approach: the standard clause is portable and gives you a marking column rather than just suppressing rows.

-- SQL - depth-first ordering and cycle detection, standard syntax
WITH org (employee_id, manager_id, last_name, path) AS (
  SELECT employee_id, manager_id, last_name, '/' || employee_id || '/'
  FROM   hr.employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.employee_id, e.manager_id, e.last_name,
         o.path || e.employee_id || '/'
  FROM   hr.employees e
  JOIN   org o ON o.employee_id = e.manager_id
  WHERE  INSTR(o.path, '/' || e.employee_id || '/') = 0
)
SEARCH DEPTH FIRST BY last_name SET sort_key
SELECT last_name, path
FROM   org
ORDER  BY sort_key;
A recursive CTE will happily run forever if the data has a cycle and the termination condition never becomes true. Always carry either a visited-value test or a depth ceiling — WHERE lvl < 50 in the recursive member — while developing. In production, a runaway recursion consumes a temporary tablespace and a session's PGA until it is killed.

7.4 Trees and bills of materials in practice

The textbook example is an employee hierarchy; the commercially important one is a bill of materials, where each node has a quantity and the totals must be computed along the path.

Rolling quantities up a BOM

In a BOM, an assembly contains components, each of which may itself be an assembly. The quantity of a leaf needed to build one unit of the root is the product of the quantities along the path — which is exactly what a recursive query computed with a multiplication per step produces. This is where the recursive form earns its keep: the accumulator is a running product, not just a level number, and it is an ordinary expression in the recursive member.

-- SQL - how much of each part is needed for one unit of 'BIKE-100'
WITH bom_expand (part_id, parent_id, qty_per, total_qty, lvl) AS (
  SELECT part_id, parent_id, qty_per, qty_per, 1
  FROM   bom
  WHERE  parent_id = 'BIKE-100'
  UNION ALL
  SELECT b.part_id, b.parent_id, b.qty_per,
         ROUND(e.total_qty * b.qty_per, 4),
         e.lvl + 1
  FROM   bom b
  JOIN   bom_expand e ON e.part_id = b.parent_id
)
SELECT part_id, lvl, total_qty
FROM   bom_expand
ORDER  BY part_id;

Where the path column earns its place

Keeping a materialised path such as /ROOT/ENGINE/PISTON/ in the table makes subtree queries trivial and fast: WHERE path LIKE '/ROOT/ENGINE/%' is a range scan on an index over the path column, with none of the per-level lookups of a recursive query. The cost is maintenance on move: changing a node's parent requires rewriting the path of every descendant, which is an update touching the whole subtree. The pragmatic split is to store the path where reads dominate and nodes rarely move — category trees, document folders, geographic hierarchies — and to compute it on read where the tree is volatile.

-- SQL - subtree query against a stored path column: one index range scan
SELECT id, name, path
FROM   categories
WHERE  path LIKE '/ROOT/ENGINE/%'                 -- descendants only
ORDER  BY path;

-- Descendants only, excluding the node itself
SELECT id, name FROM categories
WHERE  path LIKE '/ROOT/ENGINE/%'
AND    path <> '/ROOT/ENGINE/';
An ORDER BY over a path string sorts lexicographically, so sibling names with digits sort 'item10' before 'item2'. Zero-pad the numeric segments to a fixed width when you build the path, or the report will look wrong in a way that no amount of tuning fixes.

8 · Functions and expressions

Oracle's built-in function library is large and uneven: some functions are standard, some are Oracle-only, and a few have subtle behaviour that a namesake in another database does not share.

8.1 String functions

Text handling in Oracle is byte- or character-aware depending on the function, and the distinction matters the moment non-ASCII data appears.

Substrings, searching and padding

SUBSTR(s, start, len) counts from 1, and a negative start counts from the end; a len longer than the remainder is not an error, it just returns what is there. INSTR(s, sub, start, nth) returns the position of the nth occurrence and 0 when it is absent — so INSTR(...) > 0 is the membership test, and 0 is a value you must handle rather than an exception. LPAD/RPAD pad to an exact width, which is how you build fixed-width files and zero-padded keys. All of these count characters in a character-semantics column and bytes in a byte-semantics one; LENGTHB versus LENGTH makes the difference visible.

-- SQL - the workhorses
SELECT SUBSTR('Oracle Database 23ai', 8, 8)        AS sub,      -- Database
       INSTR('a-b-c-d', '-', 1, 2)                 AS third,    -- 4
       LPAD(TO_CHAR(42), 6, '0')                   AS padded,   -- 000042
       LPAD('Total', 20, '.')                      AS dotted,
       TRIM(BOTH ' ' FROM '  padded  ')            AS trimmed,
       LENGTH('caf' || UNISTR('\00E9'))            AS chars_,
       LENGTHB('caf' || UNISTR('\00E9'))           AS bytes_
FROM   dual;

Replacement, translation and the concatenation trap

REPLACE substitutes a substring; TRANSLATE substitutes characters one-for-one, which is the right tool for stripping punctuation or normalising digits, because it takes a from-set and a to-set positionally. REGEXP_REPLACE is more powerful and far more expensive; use REPLACE when the pattern is literal. Concatenation with || treats NULL as an empty string, so first || ' ' || last silently loses a separator when one part is null — the fix is NVL, COALESCE, or the format function that knows about optional parts.

-- SQL - character-level versus substring replacement
SELECT REPLACE('2026-10-15', '-', '/')                    AS rep,
       TRANSLATE('(555) 123-4567', '()-. ', '+')          AS keep_digits,
       TRANSLATE('abc123', 'abc', 'xyz')                  AS transl,
       'Mr' || ' ' || NULL || ' Smith'                    AS null_hole
FROM   dual;
Oracle has no CONCAT_WS; the idiomatic guard is first || CASE WHEN first IS NOT NULL AND last IS NOT NULL THEN ' ' END || last, or TRIM(BOTH ' ' FROM first || ' ' || last) which is shorter and correct because trimming collapses the extra space. Prefer the explicit form; the trim version still collapses intentional internal whitespace at the edges.

8.2 Numeric and date/time functions

Date arithmetic has one rule — a day is the unit — and everything else follows from it. Currency-scale arithmetic has one rule too, and it is about rounding.

Rounding, and rounding money correctly

ROUND(x, n) rounds half away from zero, TRUNC(x, n) truncates toward zero, CEIL and FLOOR round up and down to integers, and MOD returns the remainder. Because NUMBER is decimal, ROUND(2.675, 2) gives the result a human expects rather than the binary-float surprise a BINARY_DOUBLE would produce. This is the single strongest argument for storing money as NUMBER. For a total that must equal the sum of displayed line items, round at the point of display and nowhere else; rounding per line and then summing is how a penny goes missing.

-- SQL - numeric functions, and why the type matters
SELECT ROUND(2.675, 2)        AS rounded,
       TRUNC(9.999, 2)        AS truncated,
       CEIL(-2.1)             AS ceil_up,     -- -2
       FLOOR(-2.1)            AS floor_down,  -- -3
       MOD(17, 5)             AS remainder,   -- 2
       ROUND(1234.5678, -2)   AS round_hundreds
FROM   dual;

-- Deterministic money: round once, at the end
SELECT ROUND(SUM(unit_price * quantity), 2) AS invoice_total
FROM   order_items WHERE order_id = 1;

Dates: a day is a number

date + 1 is tomorrow; date - 7 is a week ago; date2 - date1 is a number of days, fractional because DATE holds a time. ADD_MONTHS and MONTHS_BETWEEN are the calendar-aware pair — ADD_MONTHS(DATE '2026-01-31', 1) is 28 or 29 February, not 31 March, and MONTHS_BETWEEN accounts for partial months, which is why it returns a fraction. TRUNC(date, 'MM') gives the first of the month, the standard grouping key for a monthly report; LAST_DAY gives the last day; NEXT_DAY gives the next given weekday. For timestamps, INTERVAL arithmetic is type-correct where adding a number would be rejected.

-- SQL - the date functions you will actually use
SELECT SYSDATE                                        AS now,
       SYSDATE + 1                                    AS tomorrow,
       ADD_MONTHS(DATE '2026-01-31', 1)               AS feb_end,
       ROUND(MONTHS_BETWEEN(DATE '2026-12-31',
                            DATE '2026-01-01'), 2)    AS months,
       TRUNC(SYSDATE, 'MM')                           AS month_start,
       LAST_DAY(SYSDATE)                              AS month_end,
       NEXT_DAY(SYSDATE, 'MONDAY')                    AS next_monday,
       EXTRACT(YEAR FROM SYSDATE)                     AS yr,
       SYSTIMESTAMP + INTERVAL '90' MINUTE            AS ninety_on
FROM   dual;
Never compare a DATE to a string without an explicit mask. WHERE hire_date > '01/01/2026' depends on the session's NLS_DATE_FORMAT, so it works for you and raises ORA-01843 for a colleague whose client is configured for a different format. Write DATE '2026-01-01' or TO_DATE('01/01/2026','DD/MM/YYYY'). This is the most common portability bug in Oracle SQL.

8.3 Conversion, NVL, COALESCE, NULLIF, CASE and DECODE

Explicit conversion is a correctness habit; null-handling functions are the vocabulary of every real query.

Conversion with a format model

TO_CHAR with a format model is how you produce a report string; the model elements are case-sensitive (MM is month, MI is minutes, HH24 is 24-hour) and the wrong case is a silent wrong answer rather than an error. TO_NUMBER accepts the group and decimal separators from the session unless you override them, which is why parsing a formatted number from an English-formatted file fails on a session set to another NLS_NUMERIC_CHARACTERS. Since 12.2, DEFAULT ... ON CONVERSION ERROR turns a bad value into a default instead of ORA-01722 — invaluable when loading an external feed you cannot clean first.

-- SQL - format models, including the case-sensitivity trap
SELECT TO_CHAR(SYSDATE, 'YYYY-MM-DD HH24:MI:SS')        AS stamp,
       TO_CHAR(1234567.891, '9G999G999D99')            AS grouped,
       TO_CHAR(DATE '2026-10-15', 'FMMonth DD, YYYY')  AS pretty,
       TO_NUMBER('1.234,56', '9G999D99',
                 'NLS_NUMERIC_CHARACTERS=''.,''')      AS european,
       TO_DATE('not a date' DEFAULT NULL ON CONVERSION ERROR,
               'YYYY-MM-DD')                           AS safe
FROM   dual;

Null substitution and conditional expressions

NVL(a, b) replaces null with b and always evaluates b, even when it is not needed. COALESCE(a, b, c) returns the first non-null and, importantly, short-circuits, so an expensive later argument is not evaluated once an earlier one is non-null — the standard advice is to prefer COALESCE for that reason. NULLIF(a, b) returns null when the two are equal, which is the idiomatic way to avoid dividing by zero: x / NULLIF(y, 0) yields null instead of ORA-01476. CASE is the standard conditional expression and short-circuits; DECODE is Oracle's older equivalent, uses equality only, treats two nulls as equal, and cannot contain a comparison operator.

-- SQL - the null toolkit
SELECT NVL(commission_pct, 0)                       AS nvl_,
       COALESCE(commission_pct, bonus, 0)           AS first_present,
       NULLIF(quantity, 0)                          AS null_if_zero,
       100 / NULLIF(quantity, 0)                    AS safe_ratio,
       CASE WHEN salary >= 15000 THEN 'HIGH'
            WHEN salary >= 8000  THEN 'MID'
            ELSE 'LOW' END                          AS band,
       DECODE(job_id, 'SA_REP', 'Sales', 'IT_PROG', 'Engineering', 'Other') AS dept_name
FROM   hr.employees
WHERE  employee_id < 110
ORDER  BY employee_id;
CASE is an expression, so it can be nested inside an aggregate, an ORDER BY or a window function. That is how conditional aggregation is written: SUM(CASE WHEN status = 'PAID' THEN amount ELSE 0 END) sums one subset while the same query sums another with a second CASE, reading the table once.

8.4 Regular expressions

Oracle's REGEXP_* family implements POSIX extended regular expressions, with some Oracle-specific options. They are powerful and they are expensive; the cost is proportional to input length and pattern complexity.

Match, extract, replace, count

REGEXP_LIKE is the predicate, REGEXP_SUBSTR extracts a match, REGEXP_REPLACE substitutes, REGEXP_INSTR locates, and REGEXP_COUNT counts. All accept match parameters: 'i' for case-insensitivity, 'c' for sensitivity, 'm' for multi-line so ^ and $ match at line breaks, 'n' to let . match a newline, and 'x' to ignore whitespace in the pattern. Defaults inherit from NLS_SORT and NLS_UPPER, so a case-insensitive database behaves differently from a case-sensitive one unless you pass 'c' or 'i' explicitly — which is exactly the kind of environment-dependent behaviour worth pinning down.

-- SQL - validation, extraction and replacement
SELECT REGEXP_LIKE('ABC-123', '^[A-Z]{3}-[0-9]{3}$')            AS valid_code,
       REGEXP_SUBSTR('order: 4711, qty: 12', '[0-9]+', 1, 1)    AS order_no,
       REGEXP_SUBSTR('order: 4711, qty: 12', '[0-9]+', 1, 2)    AS qty,
       REGEXP_REPLACE('2026 10 15', '\s+', '-')                 AS dashes,
       REGEXP_COUNT('banana', 'an')                             AS occurrences,
       REGEXP_SUBSTR('a,b,,c', '[^,]*', 1, 3)                   AS third_field
FROM   dual;

The performance rule

A regular expression predicate cannot use a normal B-tree index on the column, because the index stores the value and the predicate is on the value's shape. If the pattern is anchored at the start and the query is hot, a function-based index on REGEXP_SUBSTR(col, ...) can be used only when the query repeats the exact same expression with the same NLS settings. For fixed-position extraction, SUBSTR plus INSTR is several times faster and easier to index. Reach for REGEXP_* for validation and one-off cleanup; avoid it in the predicate of a query that runs a million times a day.

-- SQL - fixed positions with SUBSTR, which an index can help
SELECT SUBSTR(code, 1, 3) AS dept_code,
       SUBSTR(code, 5)     AS serial
FROM   products
WHERE  code LIKE 'ENG-%';          -- prefix LIKE can use an index

-- Regex backreference in a replacement: swap first and last name
SELECT REGEXP_REPLACE('Smith, John', '(\w+),\s*(\w+)', '\2 \1') AS flipped
FROM   dual;
Catastrophic backtracking exists in Oracle too. A pattern with nested quantifiers such as (a+)+$ against a long non-matching string can consume a session's CPU for minutes. When a regex is applied to user-supplied text, keep it simple and consider a length guard — CASE WHEN LENGTH(s) <= 400 THEN REGEXP_LIKE(s, ...) ELSE 'N' END.

8.5 JSON functions and SQL/JSON

Oracle treats JSON as a first-class type rather than a string, and the SQL/JSON function family lets you query it without a procedural parser.

Storing JSON, and querying it

On 21c and later the native JSON data type stores the document in the binary OSON format, which validates on insert and parses far faster than a CLOB holding text. On older releases use CLOB with IS JSON in a CHECK constraint. Once stored, JSON_VALUE(t.doc, '$.customer.name') extracts a scalar, JSON_QUERY extracts an object or array, JSON_EXISTS tests for a path, and dot notation (t.doc.customer.name) works directly in the query on 21c and later. JSON_TABLE is the general tool for turning an array into rows.

-- SQL - a JSON column, an index, and three ways to read it
CREATE TABLE events (
  event_id  NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload   JSON
);

INSERT INTO events (payload)
VALUES ('{"kind":"order","customer":{"id":42,"name":"Ada"},"items":[{"sku":"A1","qty":2}]}');

SELECT JSON_VALUE(payload, '$.customer.name')  AS customer,
       JSON_VALUE(payload, '$.items[0].sku')   AS first_sku,
       JSON_QUERY(payload, '$.items')          AS items_array
FROM   events
WHERE  JSON_EXISTS(payload, '$.items[*]?(@.qty > 1)');

Generating JSON and reshaping it

The generation side is JSON_OBJECT, JSON_ARRAY and their aggregate cousins JSON_OBJECTAGG and JSON_ARRAYAGG, which build a document from rows — the standard way to serialise a result set without string concatenation. JSON_TRANSFORM (21c and later) applies a list of operations to a document in one pass: SET, INSERT, REMOVE, APPEND, RENAME. It replaces a chain of JSON_MERGEPATCH calls and, crucially, does not read-modify-write the column in three separate statements.

-- SQL - query result as JSON, and an in-place edit
SELECT JSON_OBJECT('dept'  VALUE d.department_name,
                   'staff' VALUE JSON_ARRAYAGG(e.last_name ORDER BY e.last_name)
                   RETURNING CLOB) AS dept_json
FROM   hr.departments d
JOIN   hr.employees   e ON e.department_id = d.department_id
GROUP  BY d.department_name;

UPDATE events
SET    payload = JSON_TRANSFORM(payload,
                       SET '$.status' = 'PROCESSED',
                       SET '$.audit.at' = SYSTIMESTAMP FORMAT JSON,
                       REMOVE '$.items[0].internal')
WHERE  event_id = 1;
Index JSON when you query it. On 21c and later, CREATE INDEX ... ON t (JSON_VALUE(doc, '$.customer.id' RETURNING NUMBER)) gives a function-based index the optimizer can use for a specific path, and a SEARCH INDEX ON t (doc) covers arbitrary paths at the cost of a second data structure to maintain. Query a JSON path in a WHERE clause without an index and you are scanning and parsing every document.

9 · PL/SQL basics

PL/SQL is Oracle's procedural language, executed inside the database. It is the right tool when logic must live next to the data; it is the wrong tool when a single SQL statement would do.

9.1 Anonymous blocks, variables and anchoring to the schema

Every PL/SQL program is a block. The structure is fixed, and the declaration section is where you prevent most runtime errors.

The block and the declare section

A block is [DECLARE ...] BEGIN ... [EXCEPTION ...] END;. The declaration section is optional for an anonymous block and mandatory in the sense that any variable used must be declared there. In SQL*Plus and SQLcl a trailing / on its own line executes the block; without it the client just buffers the text. Variables declared at the top of a package persist for the life of the session, which is convenient and, under connection pooling, a source of state that leaks from one HTTP request to the next.

%TYPE anchors a variable to a column's type, and %ROWTYPE anchors it to an entire row. This is not merely tidiness: if the column is widened from NUMBER(6) to NUMBER(10), an anchored variable follows automatically, while a hand-typed PLS_INTEGER keeps working and silently truncates. Anchor everything that mirrors the schema.

-- PL/SQL - a block with anchored variables
SET SERVEROUTPUT ON SIZE UNLIMITED
DECLARE
  v_emp_id     hr.employees.employee_id%TYPE := 100;
  v_row        hr.employees%ROWTYPE;
  v_salary     hr.employees.salary%TYPE;
  v_raise_pct  CONSTANT NUMBER := 0.05;
BEGIN
  SELECT * INTO v_row FROM hr.employees WHERE employee_id = v_emp_id;
  DBMS_OUTPUT.PUT_LINE('Before: ' || v_row.salary);

  UPDATE hr.employees
  SET    salary = salary * (1 + v_raise_pct)
  WHERE  employee_id = v_emp_id
  RETURNING salary INTO v_salary;

  DBMS_OUTPUT.PUT_LINE('After:  ' || v_salary);
  DBMS_OUTPUT.PUT_LINE('Rows:   ' || SQL%ROWCOUNT);
END;
/

Binding is what keeps a program fast

A PL/SQL variable used in a SQL statement is a bind variable, and that is the whole reason a loop over PL/SQL can outperform a loop over dynamically-built SQL. The statement is parsed once and the plan is reused, so the shared pool holds one cursor instead of a thousand near-identical ones. Concatenating values into SQL — EXECUTE IMMEDIATE '... WHERE id = ' || v_id — throws that away and is also the classic SQL-injection hole. Use USING and RETURNING INTO, always.

-- PL/SQL - binds, not concatenation
DECLARE
  v_id      NUMBER := 101;
  v_name    VARCHAR2(100);
  v_sql     VARCHAR2(200) := 'SELECT last_name FROM hr.employees WHERE employee_id = :id';
BEGIN
  EXECUTE IMMEDIATE v_sql INTO v_name USING v_id;
  DBMS_OUTPUT.PUT_LINE('Name: ' || v_name);

  -- Injecting the value would be both slow and unsafe:
  -- '... WHERE employee_id = ' || v_id
END;
/
Never store a value in a package global to pass it between requests. In a shared-server or connection-pooled deployment the package state belongs to the session, which is reused. The symptom is an intermittently wrong value under load that disappears in testing. Pass parameters explicitly, or store in a table if the value must persist.

9.2 Control flow: IF, CASE, loops

PL/SQL's control structures are conventional; the interesting decisions are which loop to use and when a loop is the wrong answer entirely.

Loops, and the one that is usually wrong

LOOP is infinite until EXIT or EXIT WHEN; WHILE cond LOOP tests first; FOR i IN 1..n LOOP iterates a range; FOR r IN cursor LOOP iterates a cursor and auto-opens, fetches and closes it. A cursor FOR loop is the shortest correct form and fetches in batches internally, so it is not the disaster people assume. What is a disaster is a cursor FOR loop that runs one UPDATE per iteration over a million rows: that is a million statement executions where one set-based UPDATE would do the same work in a single pass. Use a loop for control flow; use SQL for bulk data movement.

-- PL/SQL - all four loop shapes, one a time
DECLARE
  v_sum NUMBER := 0;
BEGIN
  FOR i IN 1 .. 5 LOOP                       -- range loop
    v_sum := v_sum + i;
  END LOOP;

  WHILE v_sum > 0 LOOP                       -- guarded loop
    v_sum := v_sum - 3;
    EXIT WHEN v_sum < 5;                     -- explicit exit
  END LOOP;

  FOR r IN (SELECT last_name, salary FROM hr.employees
            WHERE department_id = 50 ORDER BY salary DESC) LOOP
    DBMS_OUTPUT.PUT_LINE(RPAD(r.last_name, 15) || r.salary);   -- cursor FOR loop
    EXIT WHEN ROWNUM > 3;
  END LOOP;
END;
/

CASE as a statement, and the form that raises

PL/SQL has both an IF/ELSIF/ELSE chain and a CASE statement. The important distinction is between the two CASE statement forms: the simple form (CASE expr WHEN v THEN ...) raises CASE_NOT_FOUND when no branch matches and there is no ELSE, whereas the searched form (CASE WHEN cond THEN ...) does nothing when no branch matches. That asymmetry has bitten every PL/SQL developer at least once. Inside SQL, the CASE expression returns NULL when nothing matches, in both forms.

-- PL/SQL - searched CASE (safe) and the simple form's trap
DECLARE
  v_score NUMBER := 87;
  v_grade VARCHAR2(1);
BEGIN
  -- Searched form: no match simply does nothing.
  CASE
    WHEN v_score >= 90 THEN v_grade := 'A';
    WHEN v_score >= 80 THEN v_grade := 'B';
    WHEN v_score >= 70 THEN v_grade := 'C';
    ELSE v_grade := 'F';
  END CASE;

  DBMS_OUTPUT.PUT_LINE('Grade ' || v_grade);
END;
/
An IF chain that tests the same expression over and over is a CASE; a CASE inside a loop is usually a lookup table that should be read once into a collection, or better, joined in SQL. Moving branch logic into a join with a small reference table removes the procedural loop and lets the optimizer do the work.

9.3 Cursors: explicit, implicit and REF CURSOR

A cursor is a handle to a result set. SQL statements get one automatically; when you need to control fetching, you declare one.

Explicit versus implicit, and the attributes

Every DML statement and every single-row SELECT INTO uses an implicit cursor whose attributes you read as SQL%ROWCOUNT, SQL%FOUND and SQL%NOTFOUND. An explicit cursor is declared, then OPENed, FETCHed and CLOSED; its attributes are cursor%ROWCOUNT, %FOUND, %NOTFOUND and %ISOPEN. A cursor FOR loop hides all of that and is what you should normally write. Explicit cursors with declared names and parameters are worth it when the query is reused with different arguments.

Parameters matter: a parameterised cursor is bound, so opening it a thousand times with different values reuses one parsed plan. Building the SQL text per call does not.

-- PL/SQL - a parameterised explicit cursor
DECLARE
  CURSOR c_dept (p_dept_id hr.employees.department_id%TYPE,
                 p_min_sal hr.employees.salary%TYPE) IS
    SELECT last_name, salary FROM hr.employees
    WHERE  department_id = p_dept_id AND salary >= p_min_sal
    ORDER  BY salary DESC;

  v_name hr.employees.last_name%TYPE;
  v_sal  hr.employees.salary%TYPE;
BEGIN
  OPEN c_dept(50, 6000);
  LOOP
    FETCH c_dept INTO v_name, v_sal;
    EXIT WHEN c_dept%NOTFOUND;
    DBMS_OUTPUT.PUT_LINE(RPAD(v_name, 15) || v_sal);
  END LOOP;
  DBMS_OUTPUT.PUT_LINE('Fetched ' || c_dept%ROWCOUNT || ' rows');
  CLOSE c_dept;
END;
/

REF CURSOR: passing a result set back to the caller

A SYS_REFCURSOR (the built-in weakly-typed REF CURSOR) lets a PL/SQL program hand a query result to a client, another program, or another schema without materialising it. This is how a third-party reporting tool or a microservice consumes a stored procedure. The trade-offs are real: the cursor holds a snapshot, so an open REF CURSOR returned across a network keeps the transaction's read consistency alive and can produce ORA-01555 if the consumer is slow. Close it as soon as the consumer has read the last row.

-- PL/SQL - a function that returns a result set to any caller
CREATE OR REPLACE FUNCTION employees_by_dept (p_dept_id NUMBER)
  RETURN SYS_REFCURSOR
IS
  v_rc SYS_REFCURSOR;
BEGIN
  OPEN v_rc FOR
    SELECT employee_id, last_name, salary
    FROM   hr.employees
    WHERE  department_id = p_dept_id
    ORDER  BY salary DESC;
  RETURN v_rc;
END;
/

-- Consume it from SQL*Plus / SQLcl directly:
SELECT employees_by_dept(50) FROM dual;
A cursor is a session resource with a limit (OPEN_CURSORS). Leaking an open SYS_REFCURSOR in a long-lived connection eventually produces ORA-01000: maximum open cursors exceeded. The cursor FOR loop and the implicit cursor both close automatically; only explicit OPEN requires a matching CLOSE, and a RETURN or an exception before it skips it unless you use a FINALLY-like pattern or let the exception handler close it.

9.4 Exceptions: handling and propagating

An exception changes control flow, not the transaction. Understanding exactly what is and is not rolled back is the difference between a safe handler and a silent data corruption.

What the engine actually rolls back

When a statement inside a block raises, Oracle rolls back the effects of that statement, not the transaction. Work committed earlier stands; work done earlier in the same transaction stands. The exception handler runs and, if it does not RAISE or call ROLLBACK, execution continues and the caller may COMMIT — committing a transaction that contains the successful part of a partially failed operation. That is exactly what you usually do not want. Either let the exception propagate to a boundary that rolls back and decides, or have the handler do the compensation explicitly.

-- PL/SQL - a handler that decides, rather than one that swallows
DECLARE
  v_id hr.employees.employee_id%TYPE := 9999;
  v_name hr.employees.last_name%TYPE;
BEGIN
  SELECT last_name INTO v_name FROM hr.employees WHERE employee_id = v_id;
  DBMS_OUTPUT.PUT_LINE('Found ' || v_name);
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('No employee ' || v_id);
    -- No ROLLBACK needed: the failed SELECT changed nothing.
  WHEN TOO_MANY_ROWS THEN
    DBMS_OUTPUT.PUT_LINE('Duplicate employee_id - check the data');
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('Unexpected: ' || SQLCODE || ' ' || SQLERRM);
    DBMS_OUTPUT.PUT_LINE(DBMS_UTILITY.FORMAT_ERROR_BACKTRACE);
    RAISE;                       -- never swallow what you cannot explain
END;
/

Named, user-defined and re-raised exceptions

Oracle's predefined exceptions (NO_DATA_FOUND, TOO_MANY_ROWS, VALUE_ERROR, ZERO_DIVIDE, DUP_VAL_ON_INDEX) cover the common ones. For a business rule you want to name, declare your own and attach an error number with PRAGMA EXCEPTION_INIT, or simply raise RAISE_APPLICATION_ERROR(-20001, 'message'), which propagates a custom number and message to the caller. Two numbers are reserved: -20000 to -20999 is the user range, and everything else belongs to Oracle. FORMAT_ERROR_BACKTRACE gives the line where the exception was raised, where FORMAT_ERROR_STACK gives the message; the backtrace is almost always the more useful of the two.

-- PL/SQL - a named business exception
DECLARE
  e_insufficient_stock EXCEPTION;
  PRAGMA EXCEPTION_INIT(e_insufficient_stock, -20010);
  v_on_hand NUMBER := 2;
  v_wanted  NUMBER := 5;
BEGIN
  IF v_wanted > v_on_hand THEN
    RAISE_APPLICATION_ERROR(-20010,
      'Insufficient stock: requested ' || v_wanted || ', on hand ' || v_on_hand);
  END IF;
EXCEPTION
  WHEN e_insufficient_stock THEN
    DBMS_OUTPUT.PUT_LINE('Business rule hit: ' || SQLERRM);
    RAISE;
END;
/
A bare WHEN OTHERS THEN NULL; is the most expensive line of code in a PL/SQL codebase. It converts every failure — a bad date, a broken constraint, a lost connection — into "the procedure completed", and the error surfaces days later in the data. If you truly must ignore a specific failure, catch that exception by name; never the generic one.

9.5 Records, collections and dynamic SQL

Collections let a PL/SQL program hold a working set in memory; dynamic SQL lets it build a statement it could not write in advance. Both are places where correctness is easy and performance is easy to lose.

Associative arrays, nested tables and varrays

An associative array (INDEX BY PLS_INTEGER) is a sparse in-memory map and, being PL/SQL-only, cannot be stored in a column. A nested table is a persistent collection type that can be stored in a column or bound to SQL; it has no guaranteed order. A varray is bounded and ordered. The practical distinction for day-to-day work is that an associative array can be indexed by a string as well as an integer, which makes it a natural in-memory lookup table for a small reference set read once at the start of a batch.

-- PL/SQL - an associative array as an in-memory lookup
DECLARE
  TYPE t_rate IS TABLE OF NUMBER INDEX BY VARCHAR2(3);
  v_rates t_rate;
  v_code  VARCHAR2(3);
BEGIN
  v_rates('USD') := 1.00;
  v_rates('EUR') := 1.09;
  v_rates('GBP') := 1.27;

  v_code := v_rates.FIRST;
  WHILE v_code IS NOT NULL LOOP
    DBMS_OUTPUT.PUT_LINE(v_code || ' = ' || v_rates(v_code));
    v_code := v_rates.NEXT(v_code);   -- sparse-safe iteration
  END LOOP;
END;
/

Dynamic SQL, and the two kinds

EXECUTE IMMEDIATE handles a single statement whose text is built at runtime and whose shape is known: DDL, a statement with a variable IN list, or a query returning a known set of columns. DBMS_SQL handles the harder case where you do not know the number or types of the columns, or the number of binds, until runtime — and it is the only way to describe and fetch an arbitrary query. The rule that applies to both: bind every value, and interpolate only identifiers you have validated against the data dictionary. DBMS_ASSERT.SIMPLE_SQL_NAME is the standard check when a caller supplies an object name.

-- PL/SQL - EXECUTE IMMEDIATE with binds, and DDL
DECLARE
  v_tbl   VARCHAR2(30) := 'STG_ORDERS';
  v_cnt   NUMBER;
  v_sql   VARCHAR2(4000);
BEGIN
  -- Identifiers cannot be bound. Validate, then interpolate.
  DBMS_ASSERT.SIMPLE_SQL_NAME(v_tbl);

  EXECUTE IMMEDIATE 'TRUNCATE TABLE ' || v_tbl;

  v_sql := 'INSERT INTO ' || v_tbl || ' (order_id, amount) VALUES (:1, :2)';
  EXECUTE IMMEDIATE v_sql USING 4711, 99.95;
  EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM ' || v_tbl INTO v_cnt;
  DBMS_OUTPUT.PUT_LINE(v_tbl || ' now has ' || v_cnt || ' row(s)');
END;
/
Dynamic SQL is a hard parse every time the text differs. If a loop builds a slightly different string per row, you have replaced one reusable cursor with thousands. Move the variable part into a bind; if the variable part is a table name or column list, restructure so that it is not — very often a partitioned table or a CASE expression removes the need for dynamic SQL entirely.

10 · Stored program units

Procedures, functions, packages and triggers put logic in the database. That is a genuine architectural choice with real advantages and real costs, and this chapter treats it as one.

10.1 Procedures and functions

A procedure does something; a function returns something and can be called from SQL. That one difference drives every other decision about them.

The calling contract

A procedure is invoked as a statement (BEGIN my_proc(1); END;), a function inside an expression. A function called from a SQL statement must obey a stricter rule: it may not modify database state unless it is declared PRAGMA AUTONOMOUS_TRANSACTION and is called from PL/SQL, because a SQL statement cannot have side effects on the rows it is reading. It must also be DETERMINISTIC if the optimizer is to cache its results within a query — without that promise, a call in a WHERE clause is evaluated per row. RESULT_CACHE goes further and caches the return value across executions in the SGA, keyed on the arguments, which is a large win for an expensive lookup on a small dimension and a large risk if the underlying table changes and the invalidation is not triggered.

Parameter modes are IN (read-only, default), OUT and IN OUT. NOCOPY on an OUT parameter avoids copying a large collection out of the procedure, which matters when the collection is a thousand elements or more — and is unsafe if the procedure raises, because the caller may see a partially-modified value.

-- SQL - a deterministic function that SQL is allowed to use
CREATE OR REPLACE FUNCTION tax_rate (p_country_id CHAR)
  RETURN NUMBER DETERMINISTIC
IS
  v_rate NUMBER;
BEGIN
  SELECT rate INTO v_rate FROM tax_rates WHERE country_id = p_country_id;
  RETURN v_rate;
EXCEPTION
  WHEN NO_DATA_FOUND THEN RETURN 0;
END;
/

-- Usable in a WHERE clause and in the projection
SELECT country_id, tax_rate(country_id) AS rate
FROM   customers
WHERE  tax_rate(country_id) > 0.20;

When a function in SQL is the wrong answer

A PL/SQL function called per row has a context switch between the SQL engine and the PL/SQL engine. For a million rows that is a million switches, and it can dominate the runtime even when the function itself is trivial. The fix is almost always to express the same logic as a join, a CASE, or an inline view — the SQL engine can hash-join a small reference table in one pass, which no per-row function call can match. Keep functions in SQL for genuinely procedural work with no set-based equivalent, and measure before committing to the pattern.

-- SLOW: a context switch per row
SELECT c.customer_id, tax_rate(c.country_id) FROM customers c;

-- FAST: one hash join against a tiny table, no context switches
SELECT c.customer_id, COALESCE(r.rate, 0) AS rate
FROM   customers c
LEFT   JOIN tax_rates r ON r.country_id = c.country_id;
Use PRAGMA UDF on a function that is only ever called from SQL. It tells the compiler to optimise for the SQL-to-PL/SQL boundary rather than for PL/SQL use, which commonly halves the per-call overhead. It costs nothing and changes no semantics.

10.2 Packages: interface, body and state

A package is a namespace with a public specification and a private body. It is the unit of design in PL/SQL, not the procedure.

Spec and body: what is public and what is not

The specification declares what callers can see: procedure and function signatures, constants, types, cursors. The body implements them and may contain anything else the caller must not know about. Everything in the spec is a contract you are promising to keep; everything in the body can be rewritten at will. That split is why packages are better than a folder of loose procedures: you can refactor the body of a package without breaking a single caller, and you cannot do that with a standalone procedure whose name is the interface.

Overloading is allowed inside a package — two procedures can share a name if their parameter types differ — and the spec can forward-declare so that two procedures can call each other. The package also has an initialisation section at the end of the body, which runs once per session on first use; it is where you populate a cache table or register a session.

-- SQL - the specification is the contract; the body is the implementation
CREATE OR REPLACE PACKAGE hr_util AS
  c_high_pay CONSTANT NUMBER := 15000;

  FUNCTION  annual (p_salary NUMBER) RETURN NUMBER;
  PROCEDURE give_raise (p_emp_id NUMBER, p_pct NUMBER DEFAULT 0.03);

END hr_util;
/

CREATE OR REPLACE PACKAGE BODY hr_util AS
  -- Private helper: visible only inside this package body
  FUNCTION capped (p_salary NUMBER) RETURN NUMBER IS
  BEGIN
    RETURN LEAST(GREATEST(p_salary, 0), 999999);
  END capped;

  FUNCTION annual (p_salary NUMBER) RETURN NUMBER IS
  BEGIN
    RETURN capped(p_salary) * 12;
  END annual;

  PROCEDURE give_raise (p_emp_id NUMBER, p_pct NUMBER DEFAULT 0.03) IS
  BEGIN
    UPDATE hr.employees SET salary = capped(salary * (1 + p_pct))
    WHERE  employee_id = p_emp_id;
  END give_raise;
END hr_util;
/

Package state and the pooling trap

A package-level variable lives for the lifetime of the session, not the statement. In a dedicated-connection world that is just a cache. In a connection-pooled application — anything from a web framework to a mid-tier connection cache — a session outlives the request, so a package global set during request A is still there during request B if B happens to reuse the session. The bug is intermittent, load-dependent, and invisible in a single-user test. If state must persist, put it in a table; if it must not, make it a parameter. PRAGMA SERIALLY_REUSABLE makes the package state reset at the end of each call, at the cost of re-initialising on each use.

-- PL/SQL - state resets per call, so it cannot leak across pooled requests
CREATE OR REPLACE PACKAGE session_ctx AS
  PRAGMA SERIALLY_REUSABLE;
  g_request_id VARCHAR2(64);
END session_ctx;
/

-- In a pooled environment, check whether you are reusing a session:
SELECT sid, serial#, server, logon_time, program
FROM   v$session
WHERE  audsid = SYS_CONTEXT('USERENV','SESSIONID');
Editing a package body invalidates dependent objects just like editing a procedure, but because a package is compiled as a unit, a change to the spec invalidates every caller of every subprogram in the package — a much wider blast radius. Add to a spec rarely; refactor the body freely.

10.3 Triggers: firing rules and the mutating-table problem

A trigger is code the database runs for you, invisibly, whether or not the caller knows it exists. That is its value and its danger.

Timing, granularity and pseudo-records

A trigger is BEFORE, AFTER or INSTEAD OF, and either row-level (FOR EACH ROW) or statement-level. Row-level triggers read and modify the row being processed through the :NEW and :OLD pseudo-records; a BEFORE ... FOR EACH ROW trigger can assign to :NEW.col and thereby change the value that gets written, which is how audit columns, normalisation and defaults that need logic are implemented. A statement-level trigger cannot see individual rows but can fire once around a large operation, which is where a cheap guard belongs. INSTEAD OF triggers are what make a view updatable when a table's own rules cannot express the mapping.

-- SQL - audit columns, filled without asking the application
CREATE OR REPLACE TRIGGER biu_orders
  BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW
BEGIN
  IF INSERTING THEN
    :NEW.created_at := SYSTIMESTAMP;
    :NEW.created_by := SYS_CONTEXT('USERENV','SESSION_USER');
  END IF;
  :NEW.updated_at := SYSTIMESTAMP;
  :NEW.updated_by := SYS_CONTEXT('USERENV','SESSION_USER');
END;
/

The mutating-table error and the compound trigger

A row-level trigger cannot read or modify the table it is defined on — the table is being modified, so its contents are undefined mid-statement — and attempting it raises ORA-04091: table is mutating, trigger/function may not see it. The traditional workaround is a package collection that a row-level trigger fills and an after-statement trigger processes. From 11g onward the compound trigger does this in one object with timing sections: a BEFORE STATEMENT block to reset state, a FOR EACH ROW block to collect, and an AFTER STATEMENT block to act on the collected set. When several triggers exist on one table, FOLLOWS and PRECEDES (12c and later) fix the firing order, which is otherwise not guaranteed to match the order in which they were created.

-- SQL - a compound trigger that computes a statement-wide total
CREATE OR REPLACE TRIGGER trg_order_totals
  FOR INSERT ON order_items
  COMPOUND TRIGGER
    TYPE t_ids IS TABLE OF orders.order_id%TYPE;   -- must be a SQL-visible type
    v_ids t_ids := t_ids();

    BEFORE STATEMENT IS
    BEGIN
      v_ids.DELETE;              -- reusable, and still initialised
    END BEFORE STATEMENT;

    AFTER EACH ROW IS
    BEGIN
      v_ids.EXTEND;
      v_ids(v_ids.COUNT) := :NEW.order_id;
    END AFTER EACH ROW;

    AFTER STATEMENT IS
    BEGIN
      FOR r IN (SELECT DISTINCT COLUMN_VALUE AS order_id FROM TABLE(v_ids)) LOOP
        UPDATE orders o
        SET    o.item_total = (SELECT SUM(i.quantity * i.unit_price)
                               FROM   order_items i
                               WHERE  i.order_id = r.order_id)
        WHERE  o.order_id = r.order_id;
      END LOOP;
    END AFTER STATEMENT;
  END trg_order_totals;
/
Every row-level trigger is code that runs inside the user's transaction, and it runs once per row. A trigger that does a query per row multiplies the cost of a bulk load by the row count, and a trigger that raises an unhandled exception aborts the whole statement. Keep triggers small, keep them free of queries where possible, and never let one hide a business rule that a caller ought to know about — a CHECK constraint expresses the same rule far more cheaply and visibly.

10.4 Privileges, definer's rights and autonomous transactions

Who a stored unit runs as is decided at compile time, and the choice has security and correctness consequences that are easy to get backwards.

Definer's rights versus invoker's rights

By default a unit runs with definer's rights: it executes with the privileges of the schema that owns it, so a user granted EXECUTE on a procedure can do through the procedure what they cannot do directly. That is how a controlled data-access layer is built, and it is also how a privilege escalation is built if the procedure is careless — it must validate its inputs and never accept an object name or SQL text from the caller. Invoker's rights (AUTHID CURRENT_USER) makes the unit run with the caller's privileges, so the object names must be qualified with the caller's schema and the caller must hold the object privileges. Roles are not enabled inside a definer's-rights unit, which is why a procedure that works from SQL Developer fails with ORA-00942 when called by an application: grant the object privilege directly to the owner rather than relying on a role.

-- SQL - a controlled access layer: definer's rights, explicit grants
CREATE OR REPLACE PROCEDURE get_my_salary (p_emp_id NUMBER, p_sal OUT NUMBER)
AUTHID DEFINER
IS
BEGIN
  SELECT salary INTO p_sal FROM hr.employees WHERE employee_id = p_emp_id;
END;
/

GRANT EXECUTE ON get_my_salary TO reporting_app;
-- reporting_app never gets SELECT on hr.employees itself

Autonomous transactions: deliberate, not accidental

PRAGMA AUTONOMOUS_TRANSACTION starts a separate transaction inside the current one. Committing in the inner transaction does not commit the outer one, and rolling back the outer one does not undo the inner. This is exactly right for logging: a log row must survive even when the operation it describes fails and is rolled back. It is exactly wrong as a way to get around a rollback you do not like, because it breaks atomicity — the database now contains a row describing work that never happened. Every autonomous transaction must end with an explicit COMMIT or ROLLBACK; leaving it open holds a lock and produces ORA-06519: active autonomous transaction detected and rolled back when the block ends.

-- SQL - audit logging that survives the rollback it is recording
CREATE OR REPLACE PROCEDURE log_attempt (p_action VARCHAR2, p_ok NUMBER)
IS
  PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
  INSERT INTO audit_log (action, succeeded, logged_at)
  VALUES (p_action, p_ok, SYSTIMESTAMP);
  COMMIT;                       -- mandatory in an autonomous transaction
END;
/

BEGIN
  log_attempt('DELETE_BATCH', 0);
  ROLLBACK;                     -- the log row is already committed and stays
END;
/
Grant EXECUTE on the package, never on individual procedures inside it. Package-level grants are simpler to audit, and revoking a subprogram's grant does not take effect until the package is recompiled — a trap that has caused more than one security review to pass wrongly.

10.5 Bulk operations: BULK COLLECT and FORALL

Row-by-row PL/SQL is the single most common performance mistake in Oracle code. Bulk binding is the cure, and it is a mechanical change rather than a redesign.

The context switch, quantified

Each SQL statement executed from PL/SQL crosses between the PL/SQL engine and the SQL engine. A loop that runs a statement per iteration pays that cost per iteration. BULK COLLECT fetches many rows into a collection in one crossing, and FORALL sends many DML operations to the SQL engine in one crossing. Limits of a few hundred to a few thousand are the sweet spot: the limit bounds the PGA a single fetch consumes, which matters when the rows are wide or the collection is of records. A FORALL is not a loop — it is a single statement with a collection of binds — and it does not allow a COMMIT inside it for that reason.

-- PL/SQL - the row-by-row version, then the same work done in bulk
DECLARE
  CURSOR c IS SELECT employee_id, salary FROM hr.employees WHERE department_id = 50;
  TYPE t_ids IS TABLE OF hr.employees.employee_id%TYPE;
  TYPE t_sal IS TABLE OF hr.employees.salary%TYPE;
  v_ids t_ids;
  v_sal t_sal;
  c_limit CONSTANT PLS_INTEGER := 500;
BEGIN
  OPEN c;
  LOOP
    FETCH c BULK COLLECT INTO v_ids, v_sal LIMIT c_limit;
    EXIT WHEN v_ids.COUNT = 0;

    -- One context switch for the whole batch
    FORALL i IN 1 .. v_ids.COUNT
      UPDATE hr.employees
      SET    salary = v_sal(i) * 1.05
      WHERE  employee_id = v_ids(i);
  END LOOP;
  CLOSE c;
  COMMIT;
END;
/

SAVE EXCEPTIONS: partial success, reported properly

A FORALL fails as a whole by default: one bad row aborts the entire statement, and because it is one statement there is nothing to roll back to. FORALL ... SAVE EXCEPTIONS changes that — it processes every element, collects the failures into SQL%BULK_EXCEPTIONS, and raises ORA-24381 at the end if anything failed. The collection then tells you which index failed and with which error code, so a loader can write the bad rows to an error table and keep the good ones. SQL%BULK_ROWCOUNT(i) reports how many rows each DML affected, which is the only way to know that a particular bind updated nothing.

-- PL/SQL - keep the good rows, report the bad ones
DECLARE
  TYPE t_row IS RECORD (id NUMBER, amt NUMBER(10,2));
  TYPE t_tab IS TABLE OF t_row;
  v_rows t_tab := t_tab(t_row(1, 10.00), t_row(2, -5.00), t_row(3, 99.99));
BEGIN
  FORALL i IN 1 .. v_rows.COUNT SAVE EXCEPTIONS
    INSERT INTO staged_amounts (id, amount) VALUES (v_rows(i).id, v_rows(i).amt);
EXCEPTION
  WHEN OTHERS THEN
    IF SQLCODE = -24381 THEN
      FOR i IN 1 .. SQL%BULK_EXCEPTIONS.COUNT LOOP
        DBMS_OUTPUT.PUT_LINE(
          'Row ' || SQL%BULK_EXCEPTIONS(i).ERROR_INDEX ||
          ' failed: ORA-' || SQL%BULK_EXCEPTIONS(i).ERROR_CODE);
      END LOOP;
      COMMIT;   -- the successful inserts are still pending
    ELSE
      RAISE;
    END IF;
END;
/
Never mix BULK COLLECT with an unbounded FETCH into a collection when the row count is unknown. Fetching a ten-million-row table into a single collection consumes the session's PGA until the process dies with ORA-04030: out of process memory. The LIMIT clause is not optional good practice; it is the thing that makes the pattern safe.

11 · Indexes and query performance

An index trades write cost and space for read speed, and the choice of index is decided by the shape of the query, not by the column name. This chapter covers the index types, how to read a plan, and how statistics drive the decision.

11.1 B-tree indexes: the default and what it can do

A B-tree index is a balanced tree of key values with row identifiers at the leaves. It answers equality, range and prefix queries, and — as a bonus — can sometimes answer a query without touching the table at all.

When a B-tree can be used

An index is usable when the predicate is col = v, col BETWEEN a AND b, col > v, col LIKE 'prefix%' (a leading wildcard breaks it), or col IS NOT NULL, and when the column is functionally unmodified by a function or an expression. A composite index (a, b, c) can be used for predicates on a, on a, b, or on all three, but not on b alone — the leftmost-prefix rule. A query that needs only indexed columns can be served by an index-only scan (INDEX FAST FULL SCAN or INDEX FULL SCAN with the plan showing no table access), which is a large win for a covering index on a wide table.

The cost of an index is paid on write: every INSERT, DELETE and any UPDATE that changes an indexed column must maintain it. Five indexes on a table mean six structures to update for each inserted row, plus the undo and redo those changes generate. That is why a table in a write-heavy load path should carry the indexes the queries actually need and no more.

-- SQL - composite index, and the queries it can and cannot serve
CREATE INDEX ix_emp_dept_job ON hr.employees (department_id, job_id, last_name);

SELECT * FROM hr.employees WHERE department_id = 50;                 -- used
SELECT * FROM hr.employees WHERE department_id = 50 AND job_id = 'ST_CLERK';  -- used
SELECT * FROM hr.employees WHERE job_id = 'ST_CLERK';                 -- NOT usable
SELECT * FROM hr.employees WHERE department_id = 50
AND   UPPER(last_name) = 'SMITH';                                     -- NOT usable

Ordering, compression and visibility

An index stores keys in ascending order by default; DESC on a column makes it descending, which matters for ORDER BY col DESC and for the range in which the index is scanned. COMPRESS n removes repeated prefixes from a composite key, shrinking the index considerably when the leading columns have few distinct values — a range that primes/job_id would compress well. INVISIBLE (11g and later) creates a fully maintained index the optimizer ignores, so you can add it in production, verify its size and build cost, then make it VISIBLE without a second build; use it also to retire an index gradually by making it invisible first and dropping it a release later.

-- SQL - a covering index, and the invisible-then-visible technique
CREATE INDEX ix_emp_cover ON hr.employees (department_id, last_name, salary)
  COMPRESS 1;

-- Add online, verify, then expose. Building ONLINE does not block DML.
CREATE INDEX ix_emp_hire ON hr.employees (hire_date) ONLINE INVISIBLE;

SELECT index_name, visibility, compression, num_rows, leaf_blocks
FROM   user_indexes WHERE table_name = 'EMPLOYEES';

ALTER INDEX ix_emp_hire VISIBLE;
An index on a UNIQUE or PRIMARY KEY constraint is created automatically; do not create a second one on the same columns. Check USER_IND_COLUMNS against USER_CONSTRAINTS before adding anything, because redundant indexes cost write throughput and are invisible in a query review.

11.2 Bitmap, function-based, and index-organized tables

Three specialised structures answer questions a plain B-tree cannot, or answer them far more cheaply. Each has a condition under which it is the wrong choice.

Bitmap indexes: for low cardinality and read-mostly data

A bitmap index stores one bit per row per distinct key value, so a predicate on a low-cardinality column such as a status or a region becomes a bitwise AND across several indexes — extremely fast for warehouse-style queries that combine several such filters. The cost is concurrency: a DML operation on one row must lock the bitmap segment covering the value, which locks every row with that value. On an OLTP table that turns into serialised writes and deadlocks. The rule is therefore firm: bitmap indexes belong on read-mostly or batch-loaded columns in a data warehouse, never on a table that many sessions insert into concurrently.

-- SQL - the classic star-schema bitmap set
CREATE BITMAP INDEX bx_sales_channel ON sales (channel_id);
CREATE BITMAP INDEX bx_sales_region  ON sales (region_id);
CREATE BITMAP INDEX bx_sales_status  ON sales (status);

SELECT region_id, SUM(amount)
FROM   sales
WHERE  channel_id = 3 AND status = 'PAID'       -- two bitmaps ANDed
GROUP  BY region_id;

Function-based indexes and index-organized tables

A function-based index indexes the result of an expression rather than the column, which is the only way to index UPPER(name) or TO_CHAR(order_date,'YYYY'). It is used only when the query repeats the expression exactly, and creating one requires the QUERY REWRITE system privilege as well as CREATE INDEX; the expression must be deterministic, so a function that reads the clock cannot be indexed. An index-organized table stores the table's rows inside the B-tree itself, ordered by the primary key, so a key lookup reaches the data in one structure instead of two. That is ideal for narrow lookup tables read by key, and it has real limits: a large key makes the whole structure larger, secondary indexes store the primary key as their row identifier and are therefore less efficient, and a full scan reads in key order rather than in physical order.

-- SQL - a function-based index used by an exactly-matching predicate
CREATE INDEX ix_emp_upper_name ON hr.employees (UPPER(last_name));

SELECT * FROM hr.employees WHERE UPPER(last_name) = 'KING';   -- index used
SELECT * FROM hr.employees WHERE last_name = 'KING';          -- index NOT used

-- A narrow lookup table stored inside its own index
CREATE TABLE country_codes (
  country_id CHAR(2)     NOT NULL PRIMARY KEY,
  name       VARCHAR2(60) NOT NULL,
  region_id  NUMBER(3)    NOT NULL
) ORGANIZATION INDEX;

CREATE INDEX ix_country_region ON country_codes (region_id);
An index-organized table with an OVERFLOW clause keeps only the key and the leading part of each row in the B-tree and pushes the rest to a second segment. The threshold is PCTTHRESHOLD. That recovers much of the benefit for slightly wider tables, at the cost of a second segment to manage and a chance of a second I/O per fetch.

11.3 EXPLAIN PLAN and reading an execution plan

A plan is a tree read from the inside out: the most-indented operation runs first and feeds its parent. Everything else about reading plans follows from that.

Getting a plan

EXPLAIN PLAN FOR writes an estimate to PLAN_TABLE without running the query; DBMS_XPLAN.DISPLAY prints it. That is fast and often wrong, because it cannot know the runtime effect of bind values, adaptive plans or bind peeking. The accurate method is to run the query with /*+ GATHER_PLAN_STATISTICS */ and print DBMS_XPLAN.DISPLAY_CURSOR(..., 'ALLSTATS LAST'), which shows actual rows per operation beside the estimate. The ratio between E-Rows and A-Rows is the single most useful number in the output: when the estimate is out by an order of magnitude, the optimizer chose a join method for the wrong cardinality, and the fix is statistics or a rewrite rather than a hint.

-- SQL - the estimated plan, then the real one
EXPLAIN PLAN SET STATEMENT_ID 'emp' FOR
SELECT d.department_name, COUNT(*)
FROM   hr.employees e JOIN hr.departments d ON d.department_id = e.department_id
GROUP  BY d.department_name;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY('PLAN_TABLE','emp','BASIC +ROWS +PREDICATE'));

-- The plan the query actually used, with runtime rows
SELECT /*+ GATHER_PLAN_STATISTICS */ d.department_name, COUNT(*)
FROM   hr.employees e JOIN hr.departments d ON d.department_id = e.department_id
GROUP  BY d.department_name;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(format => 'ALLSTATS LAST'));

The operations worth recognising

TABLE ACCESS FULL reads every block — correct for a small table or a query needing most rows, wrong for a selective lookup. INDEX RANGE SCAN walks part of an index; INDEX UNIQUE SCAN is a single descent; INDEX SKIP SCAN can use a composite index when the leading column is not in the predicate, at the cost of many more probes. TABLE ACCESS BY INDEX ROWID is the second step after an index scan and is where random single-block reads happen, so a plan that does it a million times is usually worse than a full scan. For joins, the plan reads inside-out: the innermost line is the driving row source. A SORT ORDER BY that is not eliminated by an index means the sort is real work, and (Temp) beside any operation means it spilled to disk.

An EXPLAIN PLAN that shows a join you did not write — a semi-join, an anti-join, a VIEW with a pushed predicate — is normal. The optimizer transforms queries before planning. Read the plan's row estimates and operations, not its textual resemblance to your SQL.

11.4 Optimizer statistics and hints

The cost-based optimizer chooses a plan from statistics. Wrong statistics produce the wrong plan regardless of how well the SQL is written, and no hint compensates for a table whose row count is stale by three orders of magnitude.

What statistics are collected

Table statistics give the row count and average row length; column statistics give the number of distinct values, the density and — where a histogram exists — the distribution. Histograms matter when the data is skewed: a status column that is 99% 'CLOSED' needs a histogram for the optimizer to know that status = 'PENDING' is highly selective, or the row estimate will be off by the whole table. Oracle gathers statistics automatically in a nightly maintenance window on the default maintenance task, using an adaptive sample size. That is adequate for a database that changes slowly and inadequate for a table that grows by a million rows overnight; for the hot tables, gather deliberately.

-- SQL - gather statistics for one table, with a histogram where it matters
EXEC DBMS_STATS.GATHER_TABLE_STATS(
       ownname     => 'HR',
       tabname     => 'EMPLOYEES',
       cascade     => TRUE,
       method_opt  => 'FOR COLUMNS SIZE AUTO department_id, job_id, salary',
       degree      => 4);

-- Is a histogram present, and does it look useful?
SELECT column_name, num_distinct, density, histogram, last_analyzed
FROM   user_tab_col_statistics WHERE table_name = 'EMPLOYEES';

-- Stale statistics are the usual cause of a plan flip
SELECT table_name, num_rows, stale_stats, last_analyzed
FROM   user_tab_statistics WHERE stale_stats = 'YES';

When to hint, and which hints to avoid

A hint is a directive in a /*+ ... */ comment directly after SELECT. It should be the last resort, because it freezes a decision that the optimizer would otherwise revisit as the data changes; a hint that is right today is a latent regression. The disciplined sequence is: fix the statistics, check for a missing index, rewrite the SQL, and only then hint — with a comment naming the reason and the date. SQL Plan Management is the mechanism for the genuinely hard case, where a good plan must be preserved: DBMS_SPM stores a SQL plan baseline for a SQL_ID and the optimizer will not deviate from it without an accepted new plan.

-- SQL - a hint with a reason, and a plan baseline for a critical statement
SELECT /*+ INDEX(e ix_emp_dept_job) LEADING(d e) USE_NL(e)
           Because: d has 27 rows, e is 100k; verified 2026-10-15 */ *
FROM   hr.departments d
JOIN   hr.employees   e ON e.department_id = d.department_id
WHERE  d.location_id = 1700;

-- Freeze the plan the optimizer picked for a known-good statement
DECLARE
  v_plan PLS_INTEGER;
BEGIN
  v_plan := DBMS_SPM.LOAD_PLANS_FROM_CURSOR_CACHE(sql_id => 'abc123xyz');
  DBMS_OUTPUT.PUT_LINE('Baselines loaded: ' || v_plan);
END;
/
DBMS_STATS.GATHER_SCHEMA_STATS with CASCADE => TRUE on a large schema is I/O heavy and can change many plans at once. Gather on a representative schedule, keep a copy of the previous statistics (DBMS_STATS.RESTORE_TABLE_STATS can undo a bad gather), and never gather statistics on a system table.

11.5 The performance pitfalls that recur

Most production slow queries are one of a handful of mistakes. Recognising the pattern is faster than reading the plan from scratch.

Implicit conversion, functions on columns, and bind peeking

A predicate that wraps the indexed column in a function — WHERE TO_CHAR(order_date,'YYYY') = '2026', or the implicit WHERE order_id = '4711' against a NUMBER column — cannot use the column's index. The rewrite is almost always better anyway: order_date >= DATE '2026-01-01' AND order_date < DATE '2027-01-01' is a clean range that can use the index and is more obviously correct. Bind peeking is a different flavour of the same problem: the optimizer chooses a plan using the first bind value it sees, and if that first value is atypical, a later execution with a selective value can inherit a full-scan plan. Adaptive cursor sharing (11g and later) detects that the same SQL_ID would benefit from different plans and creates additional child cursors, which is why V$SQL has several rows for one statement text and why V$SQL_SHARED_CURSOR explains why a cursor was not reused.

-- SQL - the rewrite that restores index access
-- Bad: a function on the column defeats the index
SELECT * FROM orders WHERE TO_CHAR(order_date,'YYYY') = '2026';

-- Good: an index-friendly range
SELECT * FROM orders
WHERE  order_date >= DATE '2026-01-01'
AND    order_date <  DATE '2027-01-01';

-- Check the type mismatch that causes the implicit conversion
SELECT column_name, data_type FROM user_tab_columns
WHERE  table_name = 'ORDERS' AND column_name IN ('ORDER_ID','ORDER_DATE');

Row estimates that collapse, and the not-quite-indexed column

A WHERE clause on a column with no index and no histogram gets the default density estimate, which is a guess. So does a join whose filtered column has a handful of distinct values. The symptom in the plan is E-Rows of 1 followed by A-Rows in the millions, and a nested loop that should have been a hash join. The other recurring pattern is a near-miss index: a composite index on (a, b) and a query that filters on a with an equality and b with a range, which works; or filters on b alone, which does not. Before adding an index, check what exists — USER_IND_COLUMNS lists every indexed column in order, and an index whose leading column does not appear in the query is dead weight.

-- SQL - find the SQL that is actually costing you time
SELECT sql_id, child_number, executions,
       ROUND(elapsed_time/1e6, 1)          AS total_sec,
       ROUND(elapsed_time/GREATEST(executions,1)/1e3, 2) AS avg_ms,
       buffer_gets, rows_processed, sql_text
FROM   v$sql
WHERE  executions > 0
ORDER  BY elapsed_time DESC
FETCH  FIRST 10 ROWS ONLY;
Measure before you tune. The expensive query is not always the one you suspect: V$SQL ordered by total elapsed time, restricted to the last hour, finds the real culprit in seconds. Tuning a query that costs 50 ms a hundred times a day is wasted effort compared with the one that costs four seconds twice a day.

12 · Transactions and concurrency

Oracle's concurrency model is unusual: readers never block writers and writers never block readers, because a reader reconstructs a consistent version of each block from undo. That one design decision explains most of its behaviour.

12.1 Transactions and the implicit boundary

Oracle has no BEGIN TRANSACTION. A transaction begins with the first DML statement and ends with a COMMIT, a ROLLBACK, or any DDL — and that surprise is the thing to internalise first.

What implicitly commits

Every DDL statement (CREATE, ALTER, DROP, TRUNCATE, GRANT, COMMENT) commits the transaction before and after it runs. So do EXIT from SQL*Plus without ROLLBACK — normal exit commits. Losing the connection rolls back. Because DDL commits, a script that does DML, then an ALTER, then fails is left with the DML already durable and no way to undo it; that is why long migration scripts are designed to fail at harmless points. The other boundary is the database itself: a session that disconnects cleanly commits only if the client asked it to, and an abnormal termination leaves the transaction for PMON to roll back.

-- SQL - the boundary you did not ask for
INSERT INTO audit_log (action) VALUES ('step 1');

ALTER TABLE audit_log ADD (detail VARCHAR2(200));   -- COMMIT happens here

ROLLBACK;                                            -- step 1 is already durable

-- Control the client's exit semantics explicitly
-- SQL*Plus:  EXIT COMMIT   or   EXIT ROLLBACK
-- SQLcl:     SET AUTOCOMMIT OFF   (default)

Autocommit, and why to leave it off

SQLcl and SQL*Plus default to AUTOCOMMIT OFF; JDBC and most drivers default to on. That difference is why a bug reproduces in an application and not in a console session, and vice versa: with autocommit, each statement is its own transaction and there is no way to roll back a partially applied batch. For any multi-statement unit of work, run with autocommit off and commit once, at the end, deliberately. The transaction's size then becomes a decision you make, which is what it should be.

-- SQL - one transaction, one commit, bounded work
SET AUTOCOMMIT OFF

INSERT INTO staging (id, payload) SELECT id, payload FROM feed_batch_1;

UPDATE accounts SET balance = balance - 250.00 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 250.00 WHERE account_id = 2;

COMMIT;   -- both or neither; a crash before this rolls back everything
Oracle's ACID guarantee means a committed transaction is durable even if the host loses power on the next instruction, because LGWR wrote the redo to disk before COMMIT returned. The performance implication is real: the commit is a synchronous I/O, which is why a loop that commits per row is slow and why batching commits is the single largest speed-up available in a PL/SQL loader.

12.2 COMMIT, ROLLBACK and SAVEPOINT

A commit is not just a flag: it flushes redo, releases locks and makes the changes visible. All three effects are what make batching decisions matter.

What a commit actually does

COMMIT assigns the transaction a System Change Number, writes the commit record to the online redo log and waits for LGWR to confirm it is on durable storage, releases the row locks, and makes the transaction's changes visible to new queries. It does not write the changed blocks to the data files — that is DBWn's job, later and asynchronously — which is why a commit is fast for a small transaction and why recovery after a crash replays redo to bring the data files forward. COMMIT WRITE NOWAIT returns without waiting for the redo write, which is faster and can lose the transaction in a total failure; it exists for bulk loads where a lost batch can be re-run.

-- SQL - a batched loader: commit per chunk, not per row
BEGIN
  FOR i IN 1 .. 20 LOOP
    INSERT INTO big_staging (id, payload, n)
    SELECT id, payload, i FROM source_view
    WHERE  MOD(id, 20) = MOD(i, 20);

    COMMIT;                      -- ~5% of the rows each time
  END LOOP;
END;
/

-- The redo cost of a single huge transaction is not free either:
SELECT name, value FROM v$sysstat WHERE name LIKE 'redo%';

Savepoints and partial rollback

A SAVEPOINT name marks a position inside the transaction; ROLLBACK TO SAVEPOINT name undoes everything after the mark and keeps everything before it, leaving the transaction open. That is how a batch job keeps the rows it has already validated and discards only the failing segment, without abandoning the whole run. Savepoints do not release locks taken before the mark, and they disappear when the transaction ends. In a loop, reusing the same savepoint name on each iteration is the normal pattern — but remember that each savepoint consumes undo, so a loop with a savepoint on every one of a million rows builds a large transaction history.

-- PL/SQL - validate groups; keep the good groups, drop the bad ones
BEGIN
  FOR r IN (SELECT DISTINCT batch_id FROM incoming_rows) LOOP
    SAVEPOINT before_batch;
    BEGIN
      INSERT INTO accepted_rows
      SELECT * FROM incoming_rows WHERE batch_id = r.batch_id;

      IF SQL%ROWCOUNT = 0 THEN
        RAISE_APPLICATION_ERROR(-20050, 'Empty batch ' || r.batch_id);
      END IF;
    EXCEPTION
      WHEN OTHERS THEN
        ROLLBACK TO SAVEPOINT before_batch;
        INSERT INTO rejected_batches (batch_id, reason)
        VALUES (r.batch_id, SQLERRM);
    END;
  END LOOP;
  COMMIT;
END;
/
Keep transactions short and put the slow part outside them. A transaction that holds row locks while it calls a web service and waits for the response blocks every other writer on those rows. Read the data, close the transaction, call the service, then open a new transaction to write — accepting that the row may have changed and must be re-read or version-checked.

12.3 Isolation levels and read consistency

Oracle offers three isolation levels, not four, and it has never supported READ UNCOMMITTED. The reason is the undo-based consistency model.

Read committed is the default

At read committed, each statement sees a consistent snapshot of the data as of the moment the statement began. Dirty reads are impossible — a reader never sees uncommitted data, because the writer's changes live in undo until commit. Non-repeatable reads are possible: two statements in the same transaction can see different values if someone commits in between. That is a deliberate choice in favour of concurrency. The mechanism is that when a query finds a block too new for its snapshot, it walks the undo chain backwards to reconstruct the version it should see, using the block's ITL entries and the undo segment. This is also the source of ORA-01555: snapshot too old: if the undo needed for that reconstruction has been overwritten, the consistent read fails, and no amount of retrying brings it back.

-- SQL - two statements, one transaction, and the gap between them
SELECT salary FROM hr.employees WHERE employee_id = 100;   -- snapshot S1

-- another session commits a raise here

SELECT salary FROM hr.employees WHERE employee_id = 100;   -- snapshot S2 (new)

-- Force transaction-level consistency instead: no changes are visible
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

Serializable and read-only

Serializable gives the whole transaction one snapshot, so every statement sees the same data and the result is as if the transaction ran alone. Oracle implements it optimistically: a write that would have been based on a version of a row that has since changed raises ORA-08177: can't serialize access for this transaction, and the application must roll back and retry the whole transaction. That retry loop is not optional — a serializable application that does not handle ORA-08177 will fail under load. Read-only (SET TRANSACTION READ ONLY) gives the same transaction-level snapshot but forbids any DML, which is what a long report should use when it must not see the world change halfway through.

-- SQL - a serializable transaction with the retry it requires
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

BEGIN
  UPDATE inventory SET qty = qty - 1 WHERE sku = 'A1' AND qty > 0;
  IF SQL%ROWCOUNT = 0 THEN
    ROLLBACK;
    RAISE_APPLICATION_ERROR(-20060, 'Out of stock');
  END IF;
  COMMIT;
EXCEPTION
  WHEN OTHERS THEN
    IF SQLCODE = -8177 THEN       -- ORA-08177: retry the whole transaction
      ROLLBACK;
      RAISE_APPLICATION_ERROR(-20061, 'Serialization conflict, retry');
    ELSE
      RAISE;
    END IF;
END;
/
A long-running query is the classic ORA-01555 victim: it needs undo from the moment it started, and if the undo tablespace is small or the transaction volume high, that undo is overwritten by the time the query reaches the relevant block. The fix is more undo space, a longer UNDO_RETENTION, or a shorter query — and the last one is usually the honest answer, because a report that needs an hour of undo is a report that should be reading a materialized view.

12.4 Locking and deadlocks

Oracle locks rows, not tables, and only for writes. Two sessions can update different rows of the same table all day; they collide only when they want the same row.

Row locks, and the queue behind them

An UPDATE or DELETE locks the affected rows until the transaction commits or rolls back; an INSERT takes a lock on the new row. A second session that wants the same row waits, and the wait is visible as an enq: TX - row lock contention event. Oracle queues waiters in request order — no fairness games, no timeout by default, so a session that never commits can block its colleagues indefinitely. SELECT ... FOR UPDATE takes the same lock explicitly, which is how you read-then-write safely, and it accepts NOWAIT (ORA-00054 immediately) or WAIT n (give up after n seconds). It also accepts SKIP LOCKED, which is the correct primitive for a job queue: each worker claims a different free row instead of contending for the same one.

-- SQL - a job queue worked by many sessions without contention
DECLARE
  v_id NUMBER;
BEGIN
  SELECT job_id INTO v_id
  FROM   job_queue
  WHERE  status = 'READY'
  ORDER  BY priority, created_at
  FETCH  FIRST 1 ROWS ONLY
  FOR    UPDATE SKIP LOCKED;

  UPDATE job_queue SET status = 'RUNNING', started_at = SYSTIMESTAMP
  WHERE  job_id = v_id;
  COMMIT;                       -- release the row immediately
END;
/

Deadlocks: detection and prevention

A deadlock is a cycle in the wait-for graph: session A holds row 1 and wants row 2, session B holds row 2 and wants row 1. Oracle's MMON-assisted deadlock detector notices within about three seconds, rolls back the last statement of one victim (which gets ORA-00060) and lets the other proceed. The failure is a statement, not a transaction — but the statement was almost certainly part of a unit of work the application must restart. The trace contains the full deadlock graph, and it is the only place the two statements appear together. The fix is never to retry blindly: it is to make every transaction acquire the same rows in the same order, usually by sorting the keys before processing them.

-- SQL - find what is blocking what
SELECT s.sid, s.serial#, s.username, s.status, s.seconds_in_wait,
       s.blocking_session, s.event, s.sql_id
FROM   v$session s
WHERE  s.blocking_session IS NOT NULL
ORDER  BY s.seconds_in_wait DESC;

-- The lock a session holds, and the object behind it
SELECT l.sid, l.type, l.lmode, l.request, l.id1, l.id2, o.object_name
FROM   v$lock l
LEFT   JOIN dba_objects o ON o.object_id = l.id1
WHERE  l.type = 'TX' OR l.block = 1;
Process multi-row updates in a deterministic order. If every transaction that touches accounts 1 and 2 sorts them and updates 1 first, the cycle that causes a deadlock cannot form — this turns a hard concurrency problem into a one-line ORDER BY in the cursor that builds the batch.

12.5 Flashback: querying and recovering the past

Because Oracle keeps undo and, optionally, a flashback archive, it can show you what the data looked like at a past time without restoring a backup.

Flashback Query

SELECT ... AS OF TIMESTAMP or AS OF SCN runs the query against a consistent version of the data as of that moment, reconstructing old block versions from undo exactly as a consistent read does. For a series of versions, VERSIONS BETWEEN adds VERSIONS_STARTTIME, VERSIONS_ENDTIME, VERSIONS_OPERATION and VERSIONS_XID columns to each row, which answers "who changed this and when" without any auditing trigger. The window is bounded by UNDO_RETENTION and by whether the undo still exists; asking for a timestamp older than that returns ORA-01555. AS OF can also be used inside an insert, making "copy the state from before the bad deployment" a single statement.

-- SQL - what did this row look like 30 minutes ago, and by whom?
SELECT employee_id, salary,
       versions_starttime, versions_endtime,
       versions_operation, versions_xid
FROM   hr.employees
VERSIONS BETWEEN TIMESTAMP (SYSTIMESTAMP - INTERVAL '30' MINUTE) AND SYSTIMESTAMP
WHERE  employee_id = 100
ORDER  BY versions_starttime;

-- Repair by copying the old value forward
UPDATE hr.employees e
SET    salary = (SELECT salary FROM hr.employees
                 AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '30' MINUTE)
                 WHERE employee_id = 100)
WHERE  e.employee_id = 100;

Flashback Table, Drop and Data Archive

FLASHBACK TABLE t TO TIMESTAMP ... reverts a whole table and requires ROW MOVEMENT to be enabled, because the undo must be applied as new DML. FLASHBACK TABLE t TO BEFORE DROP restores a dropped table from the recycle bin. Both are bounded by undo. For retention measured in years rather than hours, a Flashback Data Archive (Total Recall) keeps every version in a separate tablespace with its own quota and retention, so a table can be queried as of any time within its retention period regardless of how much DML has happened since — and that is how you satisfy an auditor without a hand-built history table.

-- SQL - a long-retention archive, and a table-level revert
CREATE FLASHBACK ARCHIVE fla_ledger
  TABLESPACE fla_ts QUOTA 20G RETENTION 5 YEAR;

ALTER TABLE ledger FLASHBACK ARCHIVE fla_ledger;

ALTER TABLE ledger ENABLE ROW MOVEMENT;
FLASHBACK TABLE ledger TO TIMESTAMP (SYSTIMESTAMP - INTERVAL '2' HOUR);

SELECT table_name, flashback_archive_name
FROM   user_flashback_archive_tables;
Flashback is not a backup. It cannot recover a dropped tablespace, a corrupted data file or a damaged control file, and it is bounded by undo or by a configured archive. Use it for the common case — a bad deployment, a mistaken update, an over-eager delete — and keep real backups for the rest. The two are complementary, and the recovery time difference is enormous.

The features that define Oracle 23ai as a modern database: documents without a second store, large objects, partitioned tables, and precomputed results.

13.1 JSON and JSON-relational duality views

A duality view exposes relational tables as a JSON document and accepts JSON updates that are decomposed back into the tables. It is not a copy and not a cache; it is a projection that is written through.

What a duality view is

A JSON RELATIONAL DUALITY VIEW is defined once, in SQL, and provides two interfaces to the same rows: the tables for set-based processing, and the view for document-shaped access. There is no duplication, no change-data-capture pipeline, and no divergence to reconcile. The definition uses the new JSON { } constructor with an optional nested subquery for a child array, and each SELECT in the definition carries annotations — WITH INSERT UPDATE DELETE — that say which operations the view permits on that object. Reading is an ordinary query against the data column; writing is an UPDATE of that column, an INSERT into the view, or a DELETE, and Oracle decomposes the JSON into row operations with all the usual constraint checking.

-- SQL - one definition, two interfaces
CREATE OR REPLACE JSON RELATIONAL DUALITY VIEW dept_dv AS
  SELECT JSON {'_id'        : d.department_id,
               'name'       : d.department_name,
               'location_id': d.location_id,
               'employees'  :
                 [ SELECT JSON {'_id'  : e.employee_id,
                                'first': e.first_name,
                                'last' : e.last_name,
                                'pay'  : e.salary}
                   FROM hr.employees e WITH INSERT UPDATE
                   WHERE e.department_id = d.department_id ] }
  FROM hr.departments d WITH INSERT UPDATE DELETE;

Reading and writing the document

The view is queried like any other. JSON_SERIALIZE turns the stored JSON value into readable text, and JSON_TRANSFORM edits it in place. Because the view is a projection, an update through it is immediately visible in the base tables and vice versa — which is what makes it safe to mix a document-oriented API with reporting SQL over the same data. The read-modify-write sequence should be conscious of concurrency; duality views support ETags for optimistic locking so a client can detect that a document changed between its read and its write.

-- SQL - read a document, then change one field
SELECT JSON_SERIALIZE(data PRETTY) AS doc
FROM   dept_dv
WHERE  JSON_VALUE(data, '$._id') = 50;

UPDATE dept_dv d
SET    d.data = JSON_TRANSFORM(d.data, SET '$.name' = 'Research and Development')
WHERE  JSON_VALUE(d.data, '$._id') = 50;
COMMIT;

-- A new department, and a nested employee, in one insert
INSERT INTO dept_dv VALUES (
  JSON {'name': 'Analytics',
        'location_id': 1700,
        'employees': [JSON {'first': 'Ada', 'last': 'Lovelace', 'pay': 12000}]});
COMMIT;
Duality views are the right answer when an application wants documents and an analytics team wants tables over the same entities. They are the wrong answer when the document shape is genuinely different from the relational shape — a free-form event log with no fixed schema is better as a plain JSON column, because forcing it into a view buys nothing and constrains the documents.

13.2 XML and XMLType

Oracle has supported XML natively for decades. It remains the right tool for standards-driven interchange — invoices, tax filings, industry schemas — even where JSON has taken over internal APIs.

XMLType, XMLQuery and XMLTable

XMLType is a native type: it can be stored in a column, and the storage model can be object-relational (shredded into columns, fast but rigid) or binary XML, or a CLOB. XMLQUERY evaluates an XQuery expression and returns a fragment; XMLEXISTS is the predicate; XMLTABLE is the one that matters most, because it turns an XPath expression into a virtual table, letting you join against a document's repeating elements as if they were rows. Combined with XMLCAST to coerce values to SQL types, XMLTABLE is how a document becomes relational data in one statement.

-- SQL - shred a document into rows with XMLTABLE
SELECT x.emp_name, x.salary
FROM   employee_docs d,
       XMLTABLE('/employees/employee'
                PASSING d.doc
                COLUMNS emp_name VARCHAR2(50) PATH 'name',
                        salary   NUMBER       PATH 'salary') x
WHERE  x.salary > 10000;

-- Build XML from relational data
SELECT XMLELEMENT("Employee",
         XMLATTRIBUTES(e.employee_id AS "id"),
         XMLFOREST(e.last_name AS "name", e.salary AS "pay")) AS xml_row
FROM   hr.employees e
WHERE  e.employee_id < 103;

Indexing and the storage choice

An XMLIndex is a specialised index over a document's structure that makes path predicates efficient; a function-based B-tree index on XMLCAST(XMLQUERY(...)) handles a single hot path more cheaply. The storage model is the more consequential decision: binary XML stores the parsed tree so queries do not re-parse, but it is larger on disk; object-relational shredding is smallest and fastest but requires the schema to be known when the table is created and is painful to evolve. CLOB storage parses on every access and should only be used for archival content that is rarely queried.

-- SQL - a hot path indexed exactly, and structural search if needed
CREATE INDEX ix_doc_empno ON employee_docs
  (XMLCAST(XMLQUERY('/employee/@id' PASSING doc RETURNING CONTENT) AS NUMBER));

CREATE INDEX ix_doc_struct ON employee_docs (doc)
  INDEXTYPE IS XDB.XMLINDEX;

SELECT COUNT(*) FROM employee_docs d WHERE XMLEXISTS('/employees/employee' PASSING d.doc);
XML has real overheads — parsing, character-set handling and namespace complexity — so do not choose it for a new internal interface in 2026 unless an external standard demands it. When you must consume XML, shred it at the boundary with XMLTABLE into relational rows for everything downstream; querying inside documents on every report is both slower and harder to reason about.

13.3 LOBs: CLOB, BLOB and SecureFile storage

A LOB column holds up to 128 TB per row. The storage and buffering decisions around it decide whether the application streams or chokes.

SecureFile versus BasicFile

Since 12c, SECUREFILE is the default and the better choice: it supports compression (which can shrink text and scans dramatically), deduplication of identical LOBs, encryption, and a configurable CHUNK size, all of which BASICFILE cannot do. SecureFile LOBs also perform far better for concurrent writes and small reads. The one setting whose default must be considered is ENABLE STORAGE IN ROW: values under roughly 4000 bytes are stored inline in the table's row, so a small LOB costs nothing extra to read, while a large one moves out to a separate segment. Do not turn this off unless the average LOB is genuinely large, because inline storage avoids a second I/O.

-- SQL - SecureFile with compression, and the size threshold made explicit
CREATE TABLE documents (
  doc_id     NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title      VARCHAR2(200 CHAR) NOT NULL,
  body       CLOB,
  scan       BLOB
)
LOB (body) STORE AS SECUREFILE doc_body (COMPRESS HIGH CACHE ENABLE STORAGE IN ROW)
LOB (scan) STORE AS SECUREFILE doc_scan (COMPRESS MEDIUM NOCACHE CHUNK 32768);

-- Is the LOB inline or out of line, and how big is it really?
SELECT table_name, column_name, segment_name, in_row, chunk, cache, compression
FROM   user_lobs WHERE table_name = 'DOCUMENTS';

Streaming with DBMS_LOB

Reading a LOB means deciding how much of it to move. DBMS_LOB.SUBSTR and DBMS_LOB.INSTR work on pieces; DBMS_LOB.WRITEAPPEND and DBMS_LOB.WRITE build one; DBMS_LOB.LOADFROMFILE, LOADCLOBFROMFILE and LOADBLOBFROMFILE stream a server-side file directly into a LOB without crossing the client boundary, which is how a bulk document import should be done. A BFILE is a read-only pointer to a file in a database directory, useful for import when the file is already on the server. The one pattern to avoid is selecting a whole CLOB into a VARCHAR2 variable: on a multi-megabyte document that fails or exhausts memory, and the client should be reading a substring or a stream.

-- SQL - writing a LOB in pieces, and reading one in pieces
DECLARE
  v_body CLOB;
BEGIN
  INSERT INTO documents (title, body) VALUES ('Release note', EMPTY_CLOB())
  RETURNING body INTO v_body;

  DBMS_LOB.WRITEAPPEND(v_body, 13, 'Release note:');
  DBMS_LOB.WRITEAPPEND(v_body, 20, ' version 2.0 shipped');
  COMMIT;
END;
/

SELECT DBMS_LOB.GETLENGTH(body)          AS bytes_,
       DBMS_LOB.SUBSTR(body, 40, 1)      AS head
FROM   documents
WHERE  title = 'Release note';
Every LOB write generates undo and redo for the changed chunks, so a bulk load of large documents can fill a small undo tablespace very quickly. Where the load is a one-off and the data is recreatable, NOLOGGING plus a backup afterwards is the standard trade; never use it for data you cannot regenerate. Also note that a LOB column's segment can be many times the size of the table row data, so space planning must count it separately.

13.4 Partitioning basics

Partitioning splits one logical table into many segments, so that maintenance acts on a piece and queries can skip pieces they do not need. The benefit is entirely downstream of whether the queries filter on the partition key.

Strategies, and picking one

Range partitioning splits on value ranges — dates almost always — and is the default for anything time-series. Interval partitioning extends range partitioning so that Oracle creates a new partition automatically when a row arrives beyond the current high value, which removes the "the loader failed because the partition did not exist" class of incident. List partitioning splits on discrete values, which suits a region or a tenant. Hash partitioning spreads rows over a fixed number of partitions and is used to break a hot segment into many, without any pruning benefit. Composite partitioning applies one method inside another, typically range then hash, to get pruning and distribution at the same time. In 23ai, automatic partitioning can partition by any of several columns without an explicit strategy, which is convenient and, like all automatic features, something to verify against the workload before trusting.

-- SQL - interval range partitioning, one partition per month, self-managing
CREATE TABLE sales (
  sale_id   NUMBER GENERATED ALWAYS AS IDENTITY,
  sale_date DATE   NOT NULL,
  region_id NUMBER(3) NOT NULL,
  amount    NUMBER(12,2) NOT NULL
)
PARTITION BY RANGE (sale_date)
INTERVAL (NUMTOYMINTERVAL(1,'MONTH'))
( PARTITION p0 VALUES LESS THAN (DATE '2026-01-01') );

-- Local indexes are maintained per partition, so a drop is metadata-only
CREATE INDEX sx_sales_date ON sales (sale_date) LOCAL;
CREATE INDEX sx_sales_region ON sales (region_id) LOCAL;

Pruning, maintenance and the wrong-key trap

Partition pruning is the optimizer eliminating partitions whose ranges cannot contain a matching row, which requires the predicate to be on the partition key without a function around it. WHERE TRUNC(sale_date) = DATE '2026-06-01' defeats pruning; WHERE sale_date >= DATE '2026-06-01' AND sale_date < DATE '2026-06-02' does not. Maintenance is where partitioning pays for itself: dropping a month of history is ALTER TABLE ... DROP PARTITION, an instant metadata operation, instead of a huge DELETE with all the undo, redo and index maintenance it implies. Global indexes must be rebuilt or updated when a partition is dropped; local indexes are maintained with the partition and disappear with it, which is why local indexes are the norm on partitioned tables. The exception is a unique constraint that does not include the partition key — that needs a global index, and a global index over a table whose partitions are frequently dropped is an ongoing cost.

-- SQL - prove that pruning happens, and retire a month in one step
EXPLAIN PLAN FOR
SELECT SUM(amount) FROM sales
WHERE  sale_date >= DATE '2026-06-01' AND sale_date < DATE '2026-07-01';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
-- Look for PARTITION RANGE ITERATOR and PSTART/PSTOP in the plan.

SELECT partition_name, high_value, num_rows, last_analyzed
FROM   user_tab_partitions
WHERE  table_name = 'SALES'
ORDER  BY partition_position;

ALTER TABLE sales DROP PARTITION p0;   -- decommission an old month instantly
Partitioning is not a substitute for an index. A query that filters on a column other than the partition key still scans every partition, and the segments are smaller but not fewer. Choose the partition key from the workload's most common range predicate, and remember that a partitioned table's statistics should be gathered incrementally on large systems, or every gather becomes a full scan of the whole table.

13.5 Materialized views and query rewrite

A materialized view stores the result of a query as a table and refreshes it from the sources. It is the standard way to make an expensive aggregate cheap without changing the application's SQL.

Refresh strategy and the materialized view log

A fast refresh applies only the changes since the last refresh and needs a materialized view log on each base table to record them; a complete refresh re-runs the query and replaces the contents. ON COMMIT refreshes as part of the transaction that changed the base table — which makes the view current but adds latency to every DML statement on it — while ON DEMAND refreshes when you ask, which is what a nightly batch wants. For a fast refresh of an aggregate, the view log must include the sequence and rowid and record new values so deltas can be applied; not every query is fast-refreshable, and DBMS_MVIEW.EXPLAIN_MVIEW says why not rather than leaving you to guess.

-- SQL - the log, then a fast-refreshable aggregate
CREATE MATERIALIZED VIEW LOG ON sales
  WITH ROWID, SEQUENCE (product_id, qty, amount) INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW sales_monthly_mv
  BUILD IMMEDIATE
  REFRESH FAST ON COMMIT
  ENABLE QUERY REWRITE
AS
SELECT product_id,
       TRUNC(sale_date,'MM') AS mth,
       SUM(amount)           AS total_amount,
       COUNT(*)              AS sale_count
FROM   sales
GROUP  BY product_id, TRUNC(sale_date,'MM');

Query rewrite: when the application does not change

With ENABLE QUERY REWRITE, the optimizer can transparently replace a query over the base tables with one over the materialized view, so an existing report gets faster without a single line of application change. This is powerful and it must be verified: the rewrite only happens when the optimizer can prove the result is identical, which requires the right join and group-by structure, a suitable QUERY_REWRITE_INTEGRITY setting, and current statistics on the view. Rewrite against a stale view with STALE_TOLERATED returns stale answers quickly, which is a business decision, not a technical one. Check what the optimizer is doing with DBMS_MVIEW.EXPLAIN_REWRITE rather than assuming.

-- SQL - refresh control, and why a view cannot be fast-refreshed
DECLARE
  v_fail PLS_INTEGER;
BEGIN
  DBMS_MVIEW.REFRESH_DEPENDENT(number_of_failures => v_fail, list => 'SALES');
  DBMS_MVIEW.REFRESH(list => 'SALES_MONTHLY_MV', method => 'C');
END;
/

SELECT mview_name, refresh_mode, refresh_method, staleness, last_refresh_date
FROM   user_mviews;

-- If it will not fast-refresh, ask why instead of guessing
EXEC DBMS_MVIEW.EXPLAIN_MVIEW('SALES_MONTHLY_MV');
SELECT capability_name, possible, msgtxt FROM mv_capabilities_table;
A materialized view on commit adds work to the transaction that changed the base table, and a heavily refreshed view can become the bottleneck it was meant to remove. Prefer ON DEMAND refreshes on a schedule, inside a maintenance window, and measure the refresh as part of the batch's duration. A materialized view that is refreshed hourly but read by a report that needs per-minute freshness is a correctness problem disguised as a performance feature.
