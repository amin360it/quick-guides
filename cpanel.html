Orientation — Scope, Layers and Method

This guide treats cPanel &WHM 11.x as the administrative substrate of a Linux shared and reseller hosting platform rather than as a web application. It fixes the vocabulary, the on-disk layout and the privilege model that every later chapter depends on, and it states plainly what the software does not isolate. The intended reader already administers Linux hosts and can read a MySQL grant table or an Exim router without a primer.

Scope of this guide

What this document covers, what it deliberately excludes, and the hardware and software envelope it assumes.

The scope is a single cPanel &WHM server: a host running CloudLinux or AlmaLinux with WHM, Litespeed Enterprise — or Apache 2.4 on hosts where Litespeed is not licensed — PHP 8.5 with PHP-FPM, MySQL 8.0/9.x, Exim 4.97 and Dovecot 2.4. It does not cover cPanel on Windows, the mail-only or WebHosting Builder product lines, WHMCS or any other billing front end, and multi-server clustering beyond the point where a single host’s configuration has to be reasoned about. Where a feature genuinely differs on those platforms, that difference is stated rather than assumed away, because "it depends on the platform" is the most common way a cPanel document becomes useless to the person holding it.

Excluded, deliberately: application-level deployment — Composer, Node process management, queue workers beyond cPanel’s own cron — plus DDoS and edge protection, and any form of high availability. These are separate disciplines with their own failure vocabularies, and blending them into a control-panel guide produces advice that is either too shallow to act on or too broad to verify. What is included instead is the layer that everything above eventually breaks through: the web server’s override rules, the FPM pool that governs memory exhaustion, the grant tables that define who can read which database, the DNS records that determine whether mail is accepted at all, and the queue behaviour that determines whether an accepted message is ever delivered.

Hardware envelope. WHM’s own minimums are conservative and irrelevant to a production decision. The practical floor for a host running Litespeed Enterprise, PHP-FPM, MySQL and Exim is 4 GB of RAM and 2 vCPU; below that, pool sizing and the InnoDB buffer pool start competing within days. Treat anything below 8 GB as a shared host with narrow headroom and size pools conservatively rather than generously — a generous pool on a small host does not become available memory, it becomes swap.

The layer map and the request path

The directory layout cPanel owns, where it diverges from distribution defaults, and the order a request traverses the stack.

cPanel installs almost nothing in the distribution’s namespace. It prefixes its own tree with /usr/local/cpanel, its own Apache-compatible tree with /usr/local/apache, and it leaves the distribution’s /etc/httpd effectively irrelevant. This is the single largest source of confusion for administrators arriving from RHEL documentation, and it produces a characteristic failure: an engineer tunes /etc/httpd/conf/httpd.conf, sees no change, concludes the change failed, and escalates. The live configuration is /usr/local/cpanel/var/apache/conf/httpd.conf; /usr/local/apache/conf/httpd.conf exists as a near-duplicate that exists to satisfy the binary’s compiled-in include path and that you should leave alone. Per-account virtual hosts live under /usr/local/cpanel/var/apache/conf/userconf/DOMAIN/userdata_TIMESTAMP/ and are regenerated on every domain edit, with a timestamped directory retained so the swap is atomic.

A request for https://www.example.com/index.php traverses the stack in a fixed order, and knowing the order turns most incidents from a search into a lookup. The listener accepts on 443; mod_lsapi or mod_proxy_fcgi selects an FPM pool named for the account; the account’s .htaccess in the document root is evaluated subject to AllowOverride; the request is handed to an FPM worker; PHP opens the session, reads its configuration from the pool and the account ini, and resolves whatever credentials the application holds — typically from /home/USER/.my.cnf or a file one level above the document root; and the response is filtered on the way out. Mail traverses an entirely separate stack — Exim accepting on 25, routing through routers into transports, Dovecot delivering on 993, the local router writing into /home/USER/mail/DOMAIN/ Maildir — and the two stacks share only the account, the domain registry and the system limits.

Do not treat cPanel as configuration management. A hand edit to any file cPanel regenerates is lost at the next domain edit, PHP handler change, upcp or reboot — and in the interim can leave the server in a state where a routine operation fails outright. Worse, the failure is non-deterministic: the edit appears to work until the next cPanel operation, which may be a customer pressing Save in the interface. Express required changes through the WHM interface or the matching whm command. If neither can express it, escalate to cPanel support rather than editing the generated file.

Account roles: root, reseller, account owner

The privilege ladder inside WHM, and — more importantly — what it does not protect against.

WHM models privilege as a set of metadata files under /var/cpanel/users/ keyed by Unix UID, with the values root, reseller, user and UNKNOWN. The reseller file grants a named account a bounded subset of WHM operations, normally scoped by a reseller resource name limiting that account to its own users and domains. This is a user-interface and API authorisation layer. It is not a security boundary between the root account and the hosting accounts, and that distinction governs every incident-response decision in the rest of this guide.

On a conventional shared host there is no kernel-level isolation between cPanel accounts. A hosting user’s /home/USER/public_html files are owned by USER:USER with mode 0644 and directories 0755 — readable by every process on the box, including root and every other cPanel user, regardless of what any cPanel setting claims. The reseller role can read them. So can a shell user, a cron job, a compromised application and a support agent with WHM access. Isolation between tenants on a cPanel host is contractual — it is what the acceptable use policy and the control panel’s own permissions promise — and not technical. The separation that does hold is between unprivileged processes and root, and between what the ACL layer exposes through cPanel’s interface and what it does not.

# This is the whole privilege model, and it is worth reading as plain text.
cat /var/cpanel/users/root

The consequences deserve to be stated without euphemism, because they are routinely discovered only during an incident. Database credentials stored inside public_html are readable by every tenant. A PHP script running as one account can read another’s source, including API keys embedded in it. /home/ is on the same filesystem with the same permission model as /var/www; cPanel’s use of /home/USER/public_html is a convention inherited from the control panel’s original design, not a chroot. If genuine technical isolation is a requirement — regulated data, mutually distrusting tenants, a multi-tenant SaaS — then shared cPanel hosting is the wrong substrate and the honest answer is separate VMs per tenant with a hard kernel boundary. CloudLinux’s CageFS and Lightweight Virtual Environment place each account in a cgroup with score limits on CPU, IO, memory and process count. LVE is a resource-control and accounting mechanism; it bounds consumption, and it is frequently mistaken in incident write-ups for a security boundary, which it is not.

Multi-tenancy risk. If your threat model includes a hostile tenant, the per-file permission model of a cPanel host is insufficient no matter what cPanel’s ACL files say. Budget for separate VMs with a hard kernel boundary rather than for ACL tuning, and record the decision explicitly in the host’s documentation so that the next administrator does not "fix" it by trusting the control panel’s own interface. A reseller account with shell access is the case to document most carefully, because the reseller is a business partner who will read it as an accusation.

Licensing, entitlements and feature availability

How cPanel’s licence gates features, why a reseller sees fewer menu items, and how to diagnose an absent one.

cPanel’s licensing model determines which features exist on a host at all, independently of what is installed. A Web Hosting Starter licence carries no reseller support, no plugin installation and no WHMCS integration. Web Hosting Pro adds API tokens and some extension points. Cloud and Enterprise tiers add the ContactPartner tooling, deeper CageFS integration and additional plugin slots. Litespeed Enterprise is licensed separately again, bound by default to the server’s IP address and, with a purchased key, to a hardware hash. Three independent licences therefore have to line up for a given capability to exist, and the usual cause of "the menu item has gone" is a lapsed tier rather than a misconfiguration.

# Installed plugins are a separate thing from available entitlements.

# CloudLinux and LVE entitlements - required for LVE scoring to bind.

One recurring operational point: the ACL name in /var/cpanel/users/USER refers to a privilege set in /var/cpanel/userdata/, and that set encodes which WHM API functions the role may call. The defaults are broad by design, because cPanel assumes the reseller is a business partner rather than a suspect. Many hosts define several tighter ones and assign them deliberately. Choosing a narrower ACL than the default is one of the few genuinely effective permission reductions available inside the product, and it is worth doing on every delegated account rather than only on the ones that have complained. Paired with a reseller resource limit on account count and disk, it produces a delegation model that survives a staff turnover without anyone having to remember which resellers were trusted.

Terminology and naming conventions

cPanel’s vocabulary distinguished from general hosting vocabulary, and the on-disk naming rules that follow from it.

Several cPanel terms have a more specific meaning than their common usage suggests, and mixing them produces configuration errors that are hard to see. A main domain is the domain created with the account; it is not special to the web server, only to the control panel’s interface and to default mail routing. An addon domain is a second domain added to an existing account, and it is not a subdomain in the DNS sense. A parked domain is a domain whose content is served from the main domain’s root, typically for a name acquired before the site is ready. A subdomain is a label beneath a domain the account already owns, and it gets its own document root. A domain alias — a canonical name in older interfaces — points an additional hostname at an existing vhost so both serve identical content.

The naming rules on disk follow directly from that vocabulary and are worth memorising, because nearly every path in this guide derives from them. Accounts live in /home/USER. Document roots are /home/USER/public_html for the main domain, /home/USER/public_html/SUBDOMAIN for subdomains, and — this is the detail that catches people out when restoring sites — /home/USER/DOMAIN for addon domains and /home/USER/PARKED for parked domains, both siblings of public_html rather than children of it. Mail is stored in /home/USER/mail/DOMAIN/ as Maildir, with the primary mailbox at /home/USER/mail/DOMAIN/ACCOUNTNAME and virtual mailboxes alongside. Logs are in /home/USER/logs/, one directory per vhost.

Command and file conventions in this guide

How to read the commands, paths and escaping in the examples that follow, and which API surface to reach for.

All shell examples assume a root shell on a cPanel host with a PATH that includes /usr/local/cpanel/bin, /usr/local/cpanel/exbin and /usr/local/sbin. Where a command is cPanel-specific it is invoked as whm or cpanel; both are Perl dispatchers that translate a friendly name into a call against the underlying module. The whm command executes as root. The cpanel command is impersonated: it requires an explicit --user unless the account is root, and it will not escalate. Three API surfaces are used throughout and they are not interchangeable.

uapi is the modern cPanel API, invoked as uapi --user=USER Module::Function argument=value, and it is the correct choice for new automation because its output format is documented and stable and it returns an exit status. The WHM API 1 is legacy, verb-based, and returns anonymous hashes on some endpoints. API 2 is the older WHM interface with typed output, and it remains necessary for operations uapi does not cover — reseller and package management, for instance. Where a task can be expressed in uapi, this guide uses uapi, and where it cannot, it says so rather than reaching for a shell loop over whm that will be slow and fragile on a host with thousands of accounts.

# uapi: documented, machine-readable, correct first choice.
uapi --user=example Domains list_data | head -40
uapi --user=example Email list_pops
uapi --user=example Modules list_enabled
# Check the exit status in scripts rather than parsing human-readable text.
uapi --user=example Email list_forwarders; echo "status=$?"

# WHM API 1: legacy verb interface. Verbose; rarely the right answer.
whm API1 Emails listpops account=example

# WHM API 2: older interface, typed output, still required for some calls.
whm API2 Email listpops user=example
whm API2 Resellers list

# The WHM CLI wraps both plus the administrative shell operations.
whm --help | head -20
whm --version
whm lldiag > /root/lldiag-$(date +%F).txt 2>&1

# Redirection, heredocs and pipes appear throughout. In the rendered HTML
# the shell metacharacters are escaped for display only; in your terminal
# they are ordinary characters.
cat > /root/reset-cpanel-user.sh <<'EOF'
#!/bin/bash
# Force every cPanel session for an account to be invalidated.
set -euo pipefail
TARGET="$1"
[ -d "/var/cpanel/users/${TARGET}" ] || { echo "no such account" >&2; exit 1; }
uapi --user="${TARGET}" Sessions clear
whm passwd --user="${TARGET}" "$(openssl rand -base64 18)"
EOF
chmod 700 /root/reset-cpanel-user.sh
bash -n /root/reset-cpanel-user.sh && echo "syntax ok"

Four locations will be used constantly in this guide and are worth internalising now: /var/log/maillog for Exim and Dovecot, /usr/local/cpanel/logs/ for control-plane actions, /var/log/messages for the service manager and kernel, and /usr/local/lsws/logs/ or /usr/local/apache/logs/ for the web server. Per-account web logs are at /home/USER/logs/, and per-mailbox delivery logs are a separate switch under Email → Track Delivery that is off by default. The first habit worth forming is running one of those tails before restarting anything, not after.

1.1 WHM and the root account

WHM is the administrative plane, root is the only identity that uses it, and root can read every account’s data. That last fact is contractual isolation, not technical isolation.

WHM is a web front end over a set of Perl modules and a store of state, and every privileged operation on a cPanel host is either a call into /usr/local/cpanel/bin/whm or an edit of a file cPanel considers it owns. There is no third path, and that is the single most useful thing to know about the product. It is reached over https://HOST:2087 and it is the most valuable target on the host, which is why the hardening baseline matters: two-factor authentication for every privileged account including root; the WHM port restricted at the firewall to an office or VPN range; PermitRootLogin set to prohibit-password with key authentication for day-to-day work; and fail2ban integration with whm login so that automated credential stuffing against 2087 is throttled at the edge.

The question of what root can reach has an unambiguous answer, and it should be stated in any security documentation you produce for a hosting service. The root account can read every cPanel account’s files, including database credentials, SSH keys, stored mail and TLS private keys. It can read them because those files are mode 0644 or 0600 owned by the account user, and root is not bound by file mode. It can read them through WHM, through the shell, through the /scripts/ utilities and through any installed plugin. A reseller role can also read them, because cPanel’s ACL layer restricts operations and not file access. None of this is a defect: cPanel is a shared-hosting platform designed for the case where the operator is the hosting provider and tenants are customers with contractual obligations. But it does mean that a claim of "isolated shared hosting" in a proposal or a compliance document is a claim about policy and about the honesty of tenants, not about technical enforcement, and it has to be written that way.

Two-factor is not optional at this layer. WHM on 2087 is full root over the host, and credential stuffing against it is routine and automated. If a second factor cannot be deployed, restrict the port to a source range, alert on repeated failures, and treat the absence of 2FA as a finding rather than a backlog item. Audit every privileged account including resellers' parent accounts, and fail the audit if any lacks it — the reseller account is the one that gets forgotten, and it is often the one with the broadest practical reach.

1.2 cPanel &WHM Web Interface

The end-user interface, its state files, session handling, and the plugin allow-list that is a real security control.

cPanel is served on https://HOST:2083 and is a genuinely separate application from WHM: different port, different session store, different API, and an account-bound view that cannot see the host. Its value is exposing operations to non-administrators safely — creating a database, installing an application, editing an .htaccess — but each of those operations eventually calls a root-privileged module with an impersonated identity. That is why /var/cpanel/userdata/USERNAME/main matters when troubleshooting access: it records the ACL, the features and the resource limits cPanel will honour for that session, and a mismatch between it and /var/cpanel/users/USERNAME produces the class of ticket where a user can log in successfully and sees an empty menu.

Authentication in current releases is layered: the cPanel password, the two-factor token, and optionally the WHM two-factor device trust record. Sessions live server-side under /var/cpanel/sessions/ and are invalidated aggressively — on IP change, on passwd, and when the per-account session limit is reached. The most common confusing support case is an account locked out of cPanel but working perfectly over SSH. The cause is almost always a session limit or an IP mismatch rather than the password, and both are cleared with one uapi Sessions clear instead of resetting credentials, which destroys the customer’s mail client configuration and generates a support ticket about Thunderbird as a side effect.

1.3 Web server: Litespeed Enterprise vs Apache 2.4

Which server is running, where its configuration actually lives, and how .htaccess behaves differently between the two.

cPanel 11.x ships with Litespeed Enterprise as the default and supports Apache 2.4 on hosts where Litespeed is not licensed. Behind cPanel’s abstraction the two are not interchangeable, and the differences that matter operationally concentrate in three places: the process model, the behaviour of .htaccess evaluation, and the location of the effective configuration. Apache runs as httpd from /usr/local/apache/bin/httpd with a prefork or event MPM depending on the install. Litespeed runs as lsws from /usr/local/lsws/bin/lsws as a single root process that forks workers, which is why it handles high static-file concurrency with a fraction of the memory: there is no process per connection.

The configuration location is the same for both and it is not /etc/httpd. cPanel writes /usr/local/cpanel/var/apache/conf/httpd.conf and the binary reads it via its compiled-in ServerRoot. /usr/local/apache/conf/httpd.conf exists as a near-duplicate that exists to satisfy that include path; leave it alone. Per-account vhosts live under /usr/local/cpanel/var/apache/conf/userconf/DOMAIN/userdata_TIMESTAMP/ and are regenerated on every domain edit, with a timestamped directory retained so the swap is atomic. A stale userdata_* directory surviving a failed upgrade is a real and recurring problem, and it is diagnosed by listing the directory and noticing more than one timestamped entry where there should be one current entry plus the _bdy fragment.

1.4 PHP-FPM and per-pool configuration

Pool sizing, why pm must be ondemand or dynamic, and the ini relationship that silently breaks uploads.

PHP-FPM in cPanel is a per-account process pool. Each account with PHP enabled has a pool file under /opt/cpanel/php-fpm/pools.d/ named for the account, listening on a Unix socket under /opt/cpanel/php-fpm/var/run/, and the web server routes that account’s vhosts to the pool by name. Pool sizing is the most consequential tuning decision on a shared host, because the number of worker processes multiplied by memory_limit is the memory an account can consume before the kernel intervenes. On a 40-account host, a naive per-account allocation of even ten workers at 512M implies a 200 GB theoretical footprint. That is survivable only because ondemand and LVE keep actual usage far below the theoretical maximum, which is precisely why the mode setting is not a detail.

The pm setting should be ondemand or dynamic and never static. static forks pm.max_children processes at start-up and keeps them all for the life of the pool, so an account with max_children=30 consumes roughly thirty times memory_limit in resident memory the moment PHP-FPM starts, on a host with dozens of accounts. dynamic starts few, grows toward max_children under load and reaps idle workers back to min_spare_servers. ondemand keeps only idle spares and forks on demand, which is correct for a multi-tenant host where most accounts are quiet and a burst in one account must not be paid for by every other account’s idle workers.

# Every pool on the host, and its key sizing parameters.
ls -1 /opt/cpanel/php-fpm/pools.d/
grep -H -E "^(pm|max_children|start_servers|min_spare|max_spare|max_requests)" \
  /opt/cpanel/php-fpm/pools.d/*.pool
# A correct host produces no line matching the next command.
grep -H "^pm *= *static" /opt/cpanel/php-fpm/pools.d/*.pool || echo "none - good"

# One account's pool, as cPanel writes it. Read-only inspection.

Worked sizing: on a 16 GB host with 40 accounts, do not divide total memory evenly per account, because accounts are not uniformly active. Reserve roughly 40% of RAM for MySQL, the web server, mail and the OS; divide the remainder by the number of accounts that have actually served traffic in the last 30 days, not the number that exist; set pm.max_children to that quotient, floored at four and capped at thirty. Then adjust per account using LVE’s memory score and observed peak. The interaction to watch is the one that kills hosts: at 512M and twelve children, one account can legitimately allocate 6 GB. LVE’s mem limit stops that at the cgroup level, and the OOM killer stops it when LVE is not configured — and the OOM killer selects its victim by a size-and-age heuristic that frequently chooses a different account’s MySQL or Dovecot process, taking an unrelated site down with it and giving the affected customer no diagnostic whatsoever.

Change pools through the interface — WHM → MultiPHP Manager for version and handler, WHM → PHP Selector for extensions, WHM → Adjust Compile Time for base values, and the account’s Select PHP Version page for per-domain ini overrides. Editing the pool file by hand produces a configuration that survives only until the next MultiPHP Manager operation, and the symptom is an ini value that reverts "on its own" after a day or two, usually blamed first on a caching layer and then on a customer’s browser. Set pm.max_requests explicitly at around 500: it recycles workers after that many requests, which bounds the effect of any leak in a long-lived PHP process and stops a slow leak accumulating across a day’s traffic. 500 is a good shared-hosting default; 10,000 is defensible for a single high-traffic site with a well-tested runtime, and a poor choice for a host of many accounts.

Never set pm = static on a multi-account host. This is the most damaging single change available to an administrator of a shared cPanel server, because its cost is paid at PHP-FPM start-up for every pool simultaneously and is not released until restart. On a 100-account host with static and max_children=20, expect several gigabytes of idle resident memory and swap thrash under ordinary load. If it is already set, revert it and restart with /scripts/restartsrv_apache_php_fpm, then confirm the worker count has actually fallen rather than assuming it has.

1.5 MySQL 8.0/9.x: users, grants, my.cnf

cPanel’s database model, the grants it emits, the my.cnf settings that matter on a shared host, and how to audit privilege creep.

MySQL 8.0 and 9.x removed several behaviours that older cPanel documentation still describes. utf8 is an alias for utf8mb3 and is deprecated; use utf8mb4 on every table and set character-set-server and collation-server to utf8mb4 and utf8mb4_unicode_ci. The older single-process --skip-grant-tables form no longer works. validate_password and its default policy interact with cPanel’s own password policy, and a mismatch produces resets that fail with a message the account owner cannot interpret. cPanel maintains its configuration in /etc/my.cnf with included fragments under /etc/my.cnf.d/; a /etc/my.cnf edited directly may be overwritten on upgrade, so the correct place for local changes is a fragment in the included directory.

1.6 Process model, restart scope and resource limits

What restarts what, what LVE actually limits, and how to find the process that killed the site before you restart it.

Every service restarts in a different scope, and choosing the wrong one is both disruptive and occasionally destructive. The web server restarts per-server, dropping in-flight requests under Apache and idling gracefully under Litespeed. PHP-FPM restarts per-server, unless you reload a single pool, in which case only that pool’s workers are recycled and no other account notices. MySQL restarts per-server and takes every site’s database with it. Exim and Dovecot restart per-service, and a Dovecot restart drops every IMAP session on the host. /scripts/restartsrv_apache_php_fpm is the correct cPanel-aware way to restart the web tier and is safe at any hour; service mysqld restart is not, during business hours, on a host with paying customers.

LVE sits above all of it. Each cPanel account has a user ID inside the lve hierarchy and a set of limits expressed as scores — cpu out of 400, mem in kilobytes or unlimited, io, maxproc and nproc — enforced by the LVE kernel module. These are what make CloudLinux’s oversubscription claims true, and they bound consumption rather than guaranteeing correctness. A mem limit of 1G means a runaway script is killed at 1G, but it is killed by the kernel rather than by PHP raising memory_limit cleanly, so the customer sees a 502 and an empty error page rather than a PHP fatal error naming the real problem. That difference in observability is worth remembering when a support conversation turns into an argument about whose fault the 502 is: from the customer’s side the two are indistinguishable, and only the LVE log distinguishes them.

  FROM information_schema.processlist ORDER BY time DESC LIMIT 20;"

# The three logs that answer "why did that site go down".

tail -50 /opt/cpanel/php-fpm/logs/error.log
tail -50 /usr/local/cpanel/logs/error_log
grep -i -E "killed process|out of memory" /var/log/messages | tail -20

Resident memory is the failure mode that recurs on shared hosts. The sum of all pools' max_children × memory_limit is a number far larger than physical RAM, and it is only safe because ondemand and LVE keep actual usage bounded. It stops being safe the moment a static pool appears, a memory_limit is raised host-wide instead of per account, or an application keeps a process resident through a pm.max_requests set too high. When swap usage climbs on a host showing no load, look for idle FPM workers first and for a single account whose LVE memory limit is unlimited second. Both are one command to confirm and one interface change to fix, and both are invisible in the cPanel interface, which is why they belong in a monitoring check rather than in a periodic manual review.

Alert on ratios, not absolutes. Useful low-noise checks for a shared host: swap above 20% of RAM, MySQL Max_used_connections above  % of max_connections, root disk above 80%, any single account’s LVE memory above 90% of its limit, Exim queue depth above 500, and any account’s FPM worker count above 30. Each corresponds to a failure that becomes an outage if it runs for an hour. Alerting on host CPU alone produces constant noise and catches none of them, because on a correctly oversubscribed host high CPU is the normal state rather than a symptom.

cPanel’s domain model is three types with materially different on-disk consequences, and every one of them begins and ends with DNS. This chapter works from the records that must be correct, through subdomain, addon and parked domain creation, to canonical aliases and TLS issuance. The recurring theme is that cPanel writes its own state — /etc/userdomains, the vhost fragments, the mail routing tables — and that a DNS change made outside the control panel’s expectations is the most common cause of a domain that works for everyone except the person reporting the problem.

2.1 DNS records that matter

The record set a cPanel domain needs, why Zone Manager edits are silent no-ops on externally hosted DNS, and how to tell the two situations apart.

A domain added in cPanel must resolve to the server’s IP before the operation completes, because cPanel performs an A lookup against the authoritative nameservers. This is why a domain added before its A record is live fails with a DNS error rather than a configuration error, and why the Status column reading Pending or Review not needed is a DNS problem and not a web-server problem. The records that actually matter are a small set: an A record for the apex, an A or AAAA for www, MX for mail, TXT for SPF, one for DKIM and one for DMARC, and — if you want the convenience hosts to resolve — CNAME records for autodiscover, autoconfig and webmail. Everything else is optional and is frequently set anyway, which is its own problem.

cPanel maintains a local zone cache under /var/cpanel/dns/, and WHM → DNS Zone Manager edits the zone on the server’s own nameserver if the domain uses it. A zone edited in cPanel and a zone edited at the registrar or at a third-party DNS host are two different zones, and cPanel’s resolver consults the authoritative one. This dual-source confusion produces the most common DNS incident on a cPanel host: an administrator adds an MX in Zone Manager, the authoritative nameservers are elsewhere, and the record does nothing at all while appearing perfectly correct in cPanel. The failure is silent, the interface confirms the record exists, and time is lost before anyone checks which nameservers actually answer.

# What cPanel believes it sees, versus what the world sees.
dig +short example.com A @1.1.1.1
dig +short example.com A @8.8.8.8
dig +short example.com MX @1.1.1.1
# Trace the authority chain. cPanel's resolver is never authoritative.
dig +trace example.com A | tail -20
dig +short example.com NS

# The zone cPanel is editing locally, if it is editing one at all.
cat /var/cpanel/dns/example.com
ls -l /var/cpanel/dns/example.com
cat /var/cpanel/bind/zonefiles/example.com 2>/dev/null | head -40

# Does this server serve DNS for the domain, or only cache it?
grep -n "example.com" /usr/local/cpanel/var/named/zone.conf 2>/dev/null
whm dns loadzone example.com
dig +short @127.0.0.1 example.com A

# The three deliverability records, through a public resolver.
dig +short example.com TXT @1.1.1.1
dig +short mail._domainkey.example.com TXT @1.1.1.1
dig +short _dmarc.example.com TXT @1.1.1.1

TTLs are a lead-time problem, not a setting. Lowering a TTL thirty seconds before a migration accomplishes nothing for resolvers that already cached the old value. The correct sequence is: reduce the TTL, wait at least one full previous TTL, make the change, then restore the TTL. Do the same for MX before any mail migration and for CNAME before any cutover, and remember that the wait is measured from the moment the lower TTL was published, not from the moment you started the change.

2.2 Subdomains and document roots

The cheapest domain type: a new vhost and a new document root nested inside the main one, with no new delegation.

A subdomain is a label beneath a domain the account already owns. It requires no new A record if the zone has a wildcard or an explicit record for that name, and cPanel creates it without any DNS check, which is why a subdomain succeeds in situations where an addon domain would fail outright. The on-disk consequence is precise: blog on account example gets the document root /home/example/public_html/blog, its own timestamped vhost fragment, its own access log directory, its own .htaccess chain and its own entry in /etc/userdomains. The vhost is a genuine independent virtual host, which is why a subdomain can carry a different PHP version, a different certificate and different rewrite rules from its parent.

Because the document root is nested inside public_html, two things follow. The parent site can reach the subdomain’s files by relative path, and the subdomain inherits the parent’s .htaccess directives from every directory above it unless it overrides them. The second point is a genuine source of mysterious behaviour: a rewrite rule, an AuthUserFile or an Options directive in the parent applies to subdomain requests, and the subdomain’s own file never mentions it. When someone reports that a subdomain is running the parent site’s rules, the answer is almost always inheritance up the directory tree, not a misconfiguration in either file. Test for it by temporarily moving the parent’s .htaccess aside rather than by reading the subdomain’s rules in isolation.

# Create a subdomain through the API. No DNS lookup is performed.
uapi --user=example SubDomain create_subdomain \
  subdomain=blog domain=example.com \
  document_root=/home/example/public_html/blog

# cPanel's registry gains a line and ownership stays unambiguous.
cat /etc/userdomains
#   example:example.com
#   example:blog.example.com
uapi --user=example SubDomain list_sub_domains

# Document root on disk, vhost fragment alongside, logs separate.
ls -ld /home/example/public_html/blog
ls -1 /usr/local/cpanel/var/apache/conf/userconf/blog.example.com/
ls -1 /home/example/logs/blog.example.com/

# The generated vhost: names, document root, log paths.
grep -n -E "DocumentRoot|ServerName|ErrorLog|CustomLog" \
  /usr/local/cpanel/var/apache/conf/userconf/blog.example.com/userdata_bdy/main.conf

# External DNS: a wildcard, or an explicit A record per subdomain.
dig +short example.com A
dig +short blog.example.com A
# If the account uses cPanel's nameservers, add it in Zone Manager and
# load the zone. If DNS is external, the account owner must add it.
whm dns loadzone example.com
dig +short @127.0.0.1 blog.example.com A

# Prove it is served as its own vhost, not as a directory of the parent.
curl -sI https://blog.example.com/ | head -8
curl -s https://blog.example.com/ | head -5

# Inheritance check: the parent's .htaccess governs unless overridden.
grep -n -E "RewriteEngine|AuthUserFile|Options" /home/example/public_html/.htaccess
cat /home/example/public_html/blog/.htaccess

# Deleting a subdomain removes the vhost, NOT the directory.
uapi --user=example SubDomain delete_subdomain subdomain=blog domain=example.com

Path traversal upward. Because a subdomain’s document root sits inside public_html, a script that trusts a user-supplied path can read the parent domain’s .env, wp-config.php or configuration.php. That is not a cPanel defect — it is what nesting means — but it converts a compromise of one application into a compromise of every application in the account, and the blast radius is invisible from inside the compromised application. Where that matters, use addon domains for genuinely independent codebases rather than subdomains, and treat a subdomain as a second name for the same application rather than as a new site.

2.3 Addon domains

A second independent site in the same account, rooted outside public_html, with its own vhost and its own mail decision.

An addon domain is a domain not already served by cPanel that is added to an existing account. It gets a top-level entry, its own vhost, its own document root at /home/USER/DOMAIN and its own mail routing decision — the last of which administrators most often miss, because the choice between Share an IP with, DNS to route email to and the local mail server determines whether mail for that domain is delivered by Exim at all. A domain with a vhost and no mail configuration delivers nothing and bounces nothing. A domain with Exim enabled but no MX record advertises a capability it cannot deliver on. Both are common, and both surface to the customer as the single sentence "mail doesn’t work".

# Create an addon domain, with mail explicitly disabled until decided.
uapi --user=example Domain create_addon_domain \
  domain=shop.example.com \
  document_root=/home/example/shop.example.com \
  description="Shop - separate codebase" \
  username=example
cat /etc/userdomains
#   example:shop.example.com
uapi --user=example Domain list_addon_domains

# On disk: a sibling of public_html, with its own logs and vhost.
ls -ld /home/example/shop.example.com
ls -1 /usr/local/cpanel/var/apache/conf/userconf/shop.example.com/
ls -1 /home/example/logs/shop.example.com/

# Which pool serves it? The account's, not one of its own.
grep -rn -E "lsapi|proxy_fcgi|SetHandler" \
  /usr/local/cpanel/var/apache/conf/userconf/shop.example.com/userdata_bdy/main.conf

# Mail for an addon domain is a separate decision, and it is silent by default.
uapi --user=example Email list_mail_domains
uapi --user=example Email add_mail_domain domain=shop.example.com
ls -1 /home/example/mail/shop.example.com/ 2>/dev/null
# Adding the mail domain creates the Maildir tree. Creating the first
# mailbox is a separate step; until it exists, mail is accepted and bounced.
uapi --user=example Email add_mailbox domain=shop.example.com \
  mailbox=shop password="$(openssl rand -base64 16)"

# DNS: the addon domain needs a real A or CNAME at the registrar.
dig +short shop.example.com A @1.1.1.1
curl -sI https://shop.example.com/ | head -6
# With no record the vhost never matches and you get a 404, or a
# redirect to the main domain if ForceHTTPS Redirect is enabled.

# Migrating existing content in, with ownership and modes preserved.
rsync -aHAX --numeric-ids /root/staging/shop/ /home/example/shop.example.com/
chown -R example:example /home/example/shop.example.com
find /home/example/shop.example.com -type d -exec chmod 755 {} \;
find /home/example/shop.example.com -type f -exec chmod 644 {} \;
grep -rn "/var/www/html\|/home/olduser" /home/example/shop.example.com/ | head

2.4 Parked domains and redirects

Two names serving one document root, the redirect status that matters, and the cPanel limitation that catches people.

A parked domain shares the main domain’s content, and cPanel’s default behaviour is a temporary redirect to the main domain. That is the correct choice for a domain acquired before its site is ready and the wrong choice for a domain meant to serve content in its own right. The distinction is not cosmetic: a 302 preserves the request URL in the browser and in search-engine indexing, whereas a 301 is cached aggressively and permanently by clients, so choosing wrongly in either direction has consequences that are painful and slow to reverse. Parked domains are genuinely useful for defensive registration — typo domains, alternative spellings, common misspellings of a brand — where serving a redirect to the real site is the entire point.

There is a cPanel limitation here worth knowing before you promise something to a customer. A parked domain has no configurable document root: it either redirects to the main domain, or it serves whatever the main domain serves. If you need the same content under two apex names with full vhost features — its own certificate, its own logs, its own PHP version — the supported workaround is an addon domain pointed at the main domain’s root, not a parked domain. Similarly, per-domain redirect logic with an arbitrary target is not expressible through the parked-domain interface; it requires either that addon-domain approach or a rewrite rule in the main domain’s .htaccess keyed on HTTP_HOST. Both work; neither is discoverable from the interface, which is why it belongs in your onboarding documentation rather than in the customer’s.

# Create a parked domain. document_root is the MAIN domain's root.
uapi --user=example Domain create_parked_domain \
  domain=example.net document_root=/home/example/public_html \
  forward_parked_to=example.com
cat /etc/userdomains
#   example:example.net
uapi --user=example Domain list_parked_domains

# The generated vhost shows the redirect target explicitly.
grep -n -E "DocumentRoot|Redirect|ServerName" \
  /usr/local/cpanel/var/apache/conf/userconf/example.net/userdata_bdy/main.conf

# Confirm the status code the client actually receives.
curl -sI http://example.net/ | head -6
#   HTTP/1.1 302 Found
#   Location: http://example.com/
curl -sIL https://example.net/ | grep -iE "^(HTTP|location)"

# To serve content from the parked name with full vhost features, use
# an addon domain sharing the main root instead.
uapi --user=example Domain delete_parked_domain domain=example.net
uapi --user=example Domain create_addon_domain \
  domain=example.net document_root=/home/example/public_html \
  description="Mirror of main domain" username=example

# Per-hostname logic, when the target genuinely differs from the main domain.
cat /home/example/public_html/.htaccess
# RewriteEngine On
# RewriteCond %{HTTP_HOST} ^www\.example\.com$ [NC]
# RewriteRule ^(.*)$ https://example.com/$1 [R=301,L]
# RewriteCond %{HTTP_HOST} ^example\.net$ [NC]
# RewriteRule ^(.*)$ https://example.com/$1 [R=301,L]

# Diagnose a redirect loop without following it first.
curl -sIL --max-redirs 0 http://example.net/
curl -sIL https://example.net/
grep -n -i "redirect" \
  /usr/local/cpanel/var/apache/conf/userconf/example.net/userdata_bdy/main.conf

# HSTS: a parked domain serving the main root inherits its headers.
curl -sI https://example.com/ | grep -i strict-transport
curl -sI https://example.net/ | grep -i strict-transport
# The target must not itself redirect, or you have built a loop.
curl -sIL https://example.com/ | grep -c "^HTTP"

Decide the redirect status when you create the domain. A 302 preserves the URL, which is correct while a site is in progress. Converting it to a 301 months later, after clients have cached the 302, produces inconsistent behaviour across user agents for weeks, and search engines read the accumulated redirect history as a signal that the site is unstable. If the parked name will eventually be a separate brand, create it as an addon domain from the start rather than parking it and converting later, and record the intended status in your account notes so the next administrator does not have to infer it.

2.5 Domain aliases and canonical names

A second hostname for an existing vhost — same content, same status code — and the canonical signal it requires.

A domain alias, called a canonical name in some cPanel interfaces, maps an additional hostname onto an existing vhost so both serve identical content with a 200. This is materially different from a parked domain’s redirect and from a DNS-level CNAME: the alias is a server-side vhost addition, which means the application must be aware it is being served under the alias and must nominate one canonical URL, or it will serve duplicate content under two names with no signal to any consumer about which is authoritative. The alias mechanism adds a name; it does not add a redirect, and expecting it to is the most common misunderstanding about the feature.

Aliases are the right tool for two situations: staging environments that must share the production codebase, and multi-brand hosting where the same application serves several names with per-domain configuration read from HTTP_HOST. They are the wrong tool for anything where a redirect would be acceptable, because a 200 on two names splits link equity and confuses analytics for the life of the deployment. Choose the redirect when the names are meant to be one identity; choose the alias only when they genuinely are two identities served by the same code. That distinction is worth writing into your onboarding guidance, because customers reach for aliases when they want canonical behaviour and get exactly the opposite.

# Add an alias. The API name differs from the UI name; check both.
uapi --user=example Domains add_domain_alias \
  alias=staging.example.com domain=example.com
cat /etc/userdomains
#   example:staging.example.com
uapi --user=example Domains list_aliases
whm --help | grep -i -E "alias|canonical"

# Both names now answer 200 from the same document root.
curl -sI https://example.com/         | head -3
curl -sI https://staging.example.com/ | head -3

# The vhost fragment lists both names - this is the evidence.
grep -n -E "ServerName|ServerAlias" \
  /usr/local/cpanel/var/apache/conf/userconf/example.com/userdata_bdy/main.conf

# Certificates: an alias is covered only if the SAN list includes it.
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \

uapi --user=example SSL installed_host_data host=example.com

curl -s https://staging.example.com/ | grep -i "rel=\"canonical\""

uapi --user=example Domains delete_domain_alias alias=staging.example.com

2.6 SSL/TLS activation, AutoSSL and hostname verification

How cPanel issues, stores and renews certificates, and why a domain that works over HTTP fails over HTTPS.

cPanel supports three sources of TLS material: a certificate the account owner uploads, a certificate AutoSSL obtains and renews automatically, and a Let’s Encrypt certificate requested through SSL → Let’s Encrypt where the account’s plan permits it. All three converge on the same storage layout. The key and certificate are copied to /var/cpanel/ssl/keys/DOMAIN.key and /var/cpanel/ssl/certs/DOMAIN.pem, the vhost is regenerated with a userdata_ssl_ fragment referencing them, and the web server is reloaded. A fourth path — the server’s own hostname certificate, managed through WHM — covers the control panel interfaces and the default virtual host, and its validity is what determines whether a browser shows a warning on the cPanel login page. A browser warning on port 2087 is the most visible and most avoidable misconfiguration on a cPanel host, and it is entirely under the root account’s control.

# Where certificates live, and what cPanel thinks it is serving.
ls -l /var/cpanel/ssl/keys/  | head -20
ls -l /var/cpanel/ssl/certs/ | head -20
uapi --user=example SSL installed_hosts
uapi --user=example SSL installed_host_data host=example.com

# AutoSSL status per domain, with the reason when not eligible.
uapi --user=example SSL autossl_status host=example.com
whm --help | grep -i -E "autossl|ssl"

# The vhost's TLS fragment - read it, never write it.
ls -1 /usr/local/cpanel/var/apache/conf/userconf/example.com/
#   userdata_1723498800  ssl_2  userdata_bdy  userdata_ssl_2
cat /usr/local/cpanel/var/apache/conf/userconf/example.com/ssl_2/main.conf | head -40

# Certificate hygiene: expiry, SAN coverage, and shared certificates.
for f in /var/cpanel/ssl/certs/*.pem; do
  d=$(basename "$f" .pem)
  exp=$(openssl x509 -in "$f" -noout -enddate 2>/dev/null | cut -d= -f2)
  n=$(openssl x509 -in "$f" -noout -ext subjectAltName 2>/dev/null | tr ',' '\n' | grep -c "DNS:")
  printf "%-32s %-30s SANs=%s\n" "$d" "$exp" "$n"
done | sort -k2 | head -30
ls -l /var/cpanel/ssl/keys/ | awk '{print $1, $3}' | sort | uniq -c

# Verify what is actually presented, from outside, by SNI name.
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# Expiry as plain arithmetic - this belongs in a monitoring check.
end=$(echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -enddate | cut -d= -f2)
echo "$end -> $(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 )) days remaining"

# Protocol posture. TLS 1.0 and 1.1 must be refused.
curl -sI --tlsv1.2 --tls-max 1.2 https://example.com/ >/dev/null && echo "1.2 ok"
curl -sI --tlsv1.3 --tls-max 1.3 https://example.com/ >/dev/null && echo "1.3 ok"
curl -sI --tlsv1.1 --tls-max 1.1 https://example.com/ >/dev/null || echo "1.1 refused - good"

# Redirect HTTP to HTTPS per vhost, through the supported switch.
uapi --user=example Domain toggle_force_https_redirect domain=example.com
curl -sI http://example.com/ | head -4

Certificate hygiene on a real cPanel host produces findings worth auditing rather than assuming. Keys in /var/cpanel/ssl/keys/ should be 0600 and root-owned. cPanel also keeps a per-account copy under /home/USER/ssl/ when the account uploaded a certificate, and that copy is readable by the account user — which is correct, because the account’s own web server may need it, and which also means a compromised account is a compromised private key. A single certificate covering dozens of unrelated customers is a shared-compromise risk: rotate it once and you affect every one of them, and one customer with read access to the key can sign as all of them. Inventory the SAN counts on every certificate on the host and investigate anything unusually large, because a healthy cPanel host issues one certificate per domain or per small alias set, and a large SAN count is a strong signal of a legacy or shared certificate that should be replaced.

Let’s Encrypt rate limits are shared across the host. The limit is 50 certificates per registered domain per week, and every cPanel domain under the same registered domain consumes from the same allowance. A provisioning script that retries on failure, or a host with many aliases and subdomains, can exhaust it for every customer at once, after which AutoSSL fails for days. Treat repeated validation failures as a host-level incident rather than a per-customer ticket, and add the failure count across all domains to the expiry monitoring rather than watching them one at a time. Also remember that a rate-limited host cannot recover faster than the limit resets, so the mitigation is to stop the retry loop rather than to keep clicking.

3.1 Exim 4.97 architecture on cPanel

The routers, transports and ACLs cPanel builds, the two supported extension points, and why verify = sender exists.

cPanel generates and owns Exim’s configuration. The live file is /etc/exim4/exim.conf, assembled from fragments under /var/cpanel/exim/ by /scripts/rebuildeximconf on every mail-configuration change. It runs to several thousand lines and divides into named sections — BEGIN ACL, ROUTERS, TRANSPORTS, RETRY and begin authenticators — and each cPanel feature that touches mail adds a router: domainloop, forwardfile, autorespond, maildirhome, localuser, checkloa and the verify = sender check in the ACL. The lists that drive routing are plain text under /var/cpanel/exim/, principally local_domains and local_recipient, and they are regenerated as domains and mailboxes change.

# The generated file, its size, and the sections cPanel maintains.
wc -l /etc/exim4/exim.conf
grep -n -E "^(BEGIN|begin|ROUTERS|TRANSPORTS|RETRY)" /etc/exim4/exim.conf | head -30
ls -1 /var/cpanel/exim/
#   acl/  local_domains  local_recipient  main_log  main_log_sql

head -5 /var/cpanel/exim/local_domains

# local_part_suffix: how an unadorned local part expands into an address.
# With "+" present, user+tag@domain resolves to the underlying mailbox,
# which is what makes plus-addressing work for filters and SaaS senders.

Understanding verify = sender is worth the time, because it is the single mechanism that prevents a class of incident that takes a shared IP out of rotation for weeks. Without it, any mail server in the world can connect to port 25 and claim to be sending as postmaster@somebank.com. You accept the message, you bounce it because no such mailbox exists, the bounce goes to somebank.com, their server receives a message from your IP that it never sent, it generates its own bounce, and the cycle runs until rate-limiting systems on both sides blacklist you. With verify = sender, Exim checks the claimed sender’s domain against the local domain list at accept time and rejects anything that is not yours, so the loop never starts. On a shared host this single setting is the difference between one account’s misconfiguration and a hundred accounts losing their mail, and it is worth confirming explicitly during every host build rather than assuming it is present.

3.2 Mailboxes, Dovecot 2.4 and quotas

Maildir layout, IMAP and POP3 access, how quota is enforced, and why an over-full mailbox is a deliverability problem.

Mail is stored in Maildir format under /home/USER/mail/DOMAIN/. The account’s primary mailbox is the directory named for the cPanel username — /home/example/mail/example.com/example for account example on example.com — with additional virtual mailboxes as siblings and the special-use folders .sent, .spam and .trash alongside. Inside each mailbox sit the standard Maildir triads cur/, new/ and tmp/. This layout is why mail counts against cPanel’s disk quota and why a mailbox problem is simultaneously a disk problem on a small-volume host — a customer who reports that email has stopped is frequently reporting a full disk, and the web site going down at the same time is not a coincidence.

# The mailbox tree, and disk usage per mailbox.

Never restore a Maildir with cp -r from an untrusted source. Maildir files are written by arbitrary senders and are a well-known route for getting code onto a hosting account. A naive restore script that sets 0755 on everything, or an over-permissive .forward or filter configuration, will happily execute a script that arrived as mail. When restoring mail, preserve modes exactly, keep files 0600 or 0640, and never create executable files under a mail directory. Use rsync -aHAX for the same reason as everywhere else on this platform: -a for ownership and modes, -A for ACLs, -X for extended attributes and SELinux contexts.

3.3 Forwarders

Server-side redirection with no local copy, the free-mailbox trap, and how forwarders differ from filters and aliases.

A forwarder redirects mail arriving for a local address to one or more external addresses without keeping a copy locally. It is implemented as a line in /home/USER/.forward together with the corresponding Exim forwardfile router, which means the forwarding address becomes the domain of record for the delivered message. That single property is the source of the most common deliverability failure on cPanel hosting. Two characteristics are worth stating plainly: a forwarder stores nothing locally, so a customer who adds one and later removes it has lost the history of everything that arrived in between; and the original From: header is preserved, because altering it would break the sender’s mail client and the recipient’s expectations.

# Create a forwarder through the API - address first, destination second.
uapi --user=example Email add_forwarder \
  address=sales@example.com destination=owner@realcompany.net
uapi --user=example Email list_forwarders domain=example.com
uapi --user=example Email delete_forwarder address=sales@example.com

# On disk this is a plain text file. Read it, and look for cycles.
cat /home/example/.forward
# sales@example.com   owner@realcompany.net
# "|/home/example/hooks/notify.sh"

# matching message. It must not be world-writable.
ls -l /home/example/hooks/notify.sh
# -rwxr-x--- 1 example example 412 Aug 30 14:02

dig +short example.com TXT @1.1.1.1 | grep spf

Why forwarding to a free mailbox domain gets an account blocked deserves a direct explanation rather than a warning label. When your server forwards, the Received: chain shows your IP as the originating hop and the final delivery is made by a consumer provider into a mailbox on a domain with aggressive DMARC policy. The message arrives with your IP in the trace. The visible sender is the original correspondent, whose domain will not authorise your IP in its SPF record, because it has no idea your server exists. The receiving provider therefore sees a message whose visible sender domain is unrelated to the domain that authenticated it, and applies its heuristics accordingly. Repeat that across a few hundred customers and the shared IP accumulates enough of those signals to be rate-limited or blocked — after which legitimate mail from every account on the host is degraded. The customers who pay are the ones who suffer, for the behaviour of people they will never meet, which is why this belongs in your onboarding documentation as a technical requirement rather than as a support topic.

3.4 Autoresponders and vacation

The mechanism, the delay that prevents loops, and the one setting that can damage a whole host.

A cPanel autoresponder writes a generated script and a vacation database into the mailbox, and adds a line to /home/USER/.forward invoking it. The generated script uses a SQLite database under /home/USER/.vacation/ to record which senders have already received a reply, and it enforces a delay before responding to the first message from any given sender. That delay is what stops the classic autoresponder loop: two people each on holiday, each auto-replying to the other’s mail, would otherwise generate replies until both mailboxes filled and receiving servers classified the traffic as a loop. The recommended range is five to fifteen minutes, and the setting is exposed as a single field with no warning attached to it.

Setting that delay to zero is the most damaging configuration change an account owner can make on a shared host. With zero delay, an autoresponder on a mailing list address — or on an address that receives automated mail from a CRM, a monitoring system, a ticketing system or a password reset flow — produces a reply to every single automated message, and those replies originate from your IP. A modest misconfiguration can therefore generate tens of thousands of messages an hour from your host, which ends in a blocklisting that affects every account on it. This is the failure to check first whenever a shared host’s sending reputation degrades, because it is the one that scales fastest and the one entirely within a customer’s control. A secondary trap is leaving the end date unset: cPanel’s default window is long enough that a forgotten vacation reply is still answering mail six months later, quietly and indefinitely.

# Create an autoresponder with a sane delay and a bounded end date.

3.5 SPF, DKIM and DMARC

The three records that must be right, the order to fix them in, and how to test each one independently.

Deliverability on shared hosting rests on three DNS records, and they are not equal in importance. SPF authorises which hosts may send for a domain. DKIM signs the message content and headers with a private key, so the receiving server can verify that a specific domain authorised the exact bytes it received — and unlike SPF, that verification survives forwarding, because the signature covers the content rather than the sending host. DMARC tells the receiving server what to do when both fail, and where to send aggregate reports. In practice DKIM does most of the work, SPF is checked first and fails most often, and DMARC is the enforcement layer that makes the other two matter rather than being advisory.

On cPanel, DKIM keys are generated per domain through Email → Authentication Results or WHM’s DKIM manager, and cPanel installs a Milter that signs outbound mail. The public key is a TXT record at the selector cPanel chose — current builds use a deployment identifier rather than the default selector, so verify the exact name before publishing — and the private key lives in /var/cpanel/dkim_keys/ with mode 0600. SPF must be created manually: cPanel tells you the value to publish and does not write your DNS. That asymmetry is the source of most "cPanel says DKIM is enabled but mail is still rejected" tickets, because the DKIM record was added and the SPF record was not, and the receiving provider fails on SPF before it ever evaluates the signature that would have passed.

# The three records, exactly as cPanel expects them. Publish these.
dig +short example.com TXT @1.1.1.1 | grep spf
#   "v=spf1 +a +mx +ip4:203.0.113.10 ~all"
dig +short mail._domainkey.example.com TXT @1.1.1.1
#   "v=DKIM1; h=sha256; k=rsa; p=MIGfMA0GCSqGSIb3DQEB..."
dig +short _dmarc.example.com TXT @1.1.1.1
#   "v=DMARC1; p=none; rua=mailto:dmarc@example.com; fo=1"

# What cPanel believes it has configured, per account.
uapi --user=example Email list_dkim_keys
whm --help | grep -i -E "dkim|spf"
ls -l /var/cpanel/dkim_keys/ | head -20

  --to deliver@dmarc-reporter.org --timeout 20
tail -60 /var/log/maillog | grep -iE "dkim|spf|dmarc|align"

# The line that decides whether mail reaches the inbox, as the receiver
# sees it after their MTA has added it:
#   Authentication-Results: mx.google.com;
#     dkim=pass header.i=@example.com header.s=mail
#     spf=pass (google.com: domain of sales@example.com designates ...)

# Count SPF DNS lookups. Ten is the limit; beyond it is a permerror.
python3 - <<'PY'
import subprocess, re
domain = "example.com"
txt = subprocess.run(["dig","+short",domain,"TXT","@1.1.1.1"],
                     capture_output=True, text=True).stdout
spf = [l for l in txt.splitlines() if "v=spf1" in l]
if not spf:
    raise SystemExit("no SPF record found")
record = spf[0].strip('" ')
lookups = sum(2 if m == "mx" else 1
              for m in re.findall(r"\b(include|a|mx|ptr|exists)\b[^ ]*", record))
print("record :", record)
print("lookups:", lookups, "(limit 10)")
PY

SPF has a hard limit of ten DNS lookups, and cPanel’s own suggested +a +mx form consumes several before the ip4: is reached. A domain with several MX records pointing at providers that in turn have include: chains will exceed ten and produce a permerror, which is treated as a failure and which several receivers treat as grounds for outright rejection. When writing SPF, prefer explicit ip4: entries for the server and for any receiving provider over include: chains, and count the lookups. ~all is correct during migration; -all is correct once everything has been verified. Publishing -all before verification is one of the more expensive mistakes available, because it authorises nothing else to send and every other legitimate tool stops working silently.

DKIM private keys are per-domain, and they are shared files. The key in /var/cpanel/dkim_keys/ is 0600 and root-owned, but a misconfigured permission on a parent directory or a compromised root-adjacent process can expose it, and anyone who reads it can sign mail as that domain. Rotate a key immediately after any account compromise involving shell access, because the key signs for the domain and not for the account, and one compromised customer therefore compromises every domain they can reach through it. Rotation is a cPanel operation followed by a DNS change, and the new public key must be published before the old one is disabled, or sending breaks in the interim. Add a CAA record while the records are healthy: it restricts which authorities may issue for the domain, is cheap now, and is awkward to add after a mis-issuance has been recorded against it.

3.6 SpamAssassin, RBLs and reading maillog

How mail is rejected before it reaches a mailbox, how to read /var/log/maillog, and how to find the account behind an outbreak.

cPanel runs SpamAssassin as an Exim Milter and consults external DNS blocklists during the SMTP transaction. The order of operations determines how you read a rejection. A connection-level RBL check happens first and rejects before any content is transferred, so a 550 at connection time carrying a blocklist reference has nothing to do with SpamAssassin and nothing to do with the customer’s message. A message accepted and then rejected at DATA with a spam score has passed the blocklists and failed content scoring. A message accepted and delivered into .spam has passed everything and was kept. A message held in /var/spool/exim/incoming/ was quarantined by SpamAssassin Extra Checks or by a router you added yourself. Reading a rejection without knowing which of those four things happened is how people spend an afternoon tuning a filter that was never involved in the failure.

Reading /var/log/maillog is a learnable skill and the highest-leverage one in this chapter. Every Exim event produces a line with a timestamp, the Exim process ID, a message ID, the sender, the recipient and an outcome, and Dovecot’s lines are interleaved into the same file with a different prefix. The two techniques that make the file usable are filtering by message ID to reconstruct one message’s complete life, and filtering by a specific address to see everything about one account. The first takes about three minutes to learn and it eliminates the majority of "where did my email go" questions without any further tooling. Add the send-volume query from below and the same file answers the second question that always follows: whose mail is this, and how much of it is there?

# One message, end to end. Start from the ID in the bounce report.
ID=1xYz3Ab-00042F-9T
grep "$ID" /var/log/maillog

# The lines that matter, from one delivery chain:
# H=mail.remote.example (1.2.3.4) ESMTP id abc123
#   <= sender@remote.example H=(...) P=esmtp S=512 id=abc123
#   => sales@example.com R=dovecot_user T=remote_smtp H=mail.remote.example
#   Completed
# "<=" is SMTP IN (accepted from the world), "=>" is SMTP OUT (we
# relay onward), "==" is local delivery, and H= always names the
# previous hop. Deferrals append "defer" and a reason to the same line.

# Outbreak detection: who is sending the most, right now. The top sender
# is usually the compromised account, and the volume tells you whether
# to suspend the account or to suspend the host.
grep "=>" /var/log/maillog | tail -20000 \
  | sed -E 's/.*<= ([^ ]+) .*/\1/' | sort | uniq -c | sort -nr | head -20

# Everything about one account, in both directions.
grep "sales@example.com" /var/log/maillog | tail -20

# RBL, SpamAssassin and quarantine outcomes - different causes, fixes.
grep -iE "listed at|blocked using|zen\.spamhaus" /var/log/maillog | tail -20
grep -iE "spam score|reject message" /var/log/maillog | tail -20
grep -iE "quarantine|held|defer_hold" /var/log/maillog | tail -20
ls -lh /var/spool/exim/incoming/ 2>/dev/null | head
# "Greylisted" self-resolves. "timeout" does not - it needs a route fix.
grep -E "(defer|timeout|connection failed|greylisted)" /var/log/maillog | tail -30

Deliverability on a shared IP is a function of the least behaved account. If one of two hundred accounts is compromised and sends a million messages, the blocklists record the IP, the major providers rate-limit it, and every other account’s legitimate mail is degraded — customers who pay, suffering for the behaviour of someone they will never meet. This is the core operational argument for per-account sending rate limits in Exim, for monitoring outbound volume per account, and for an abuse policy with a fast suspension path, and it is why the local_custom_router rate-limit extension is worth configuring rather than leaving at its default. It is equally the argument for understanding autoresponder delays and forwarder destinations, because those two features account for a disproportionate share of these incidents and neither of them looks like abuse to the person who configured it. Set the limit high enough that legitimate high-volume senders are unaffected, and low enough that a compromise cannot consume the host’s entire budget in an hour. When mail is going to spam, check in this order: send a test message to an address whose receiving MTA publishes an Authentication-Results header and read it; if SPF or DKIM fails, no volume heuristic and no reputation improvement will save the mail, and tuning a content filter is wasted effort. Only if authentication passes, check the IP’s blocklist status and the per-account sending volume, then confirm the domain has not inherited a DMARC record from a previous provider and that the visible From: domain matches the authenticated domain. That ordering resolves the overwhelming majority of deliverability tickets in three commands, and it is worth training support staff to follow it rather than reaching for the spam score first.

4.2 Databases, users and the privilege model

The cPanel model is deliberately narrow. Each account gets databases and users of its own, and privileges are granted only on that account’s databases. There is no global grant, no SUPER, no ability to create a new user, and no access to the server’s other accounts. Anything requiring those powers is a WHM operation performed by the server administrator.

-- What cPanel actually grants, and nothing more.
CREATE DATABASE 'cpanelacct_shop';
CREATE USER 'cpanelacct_shop'@'localhost' IDENTIFIED BY '...';
GRANT ALL PRIVILEGES ON 'cpanelacct_shop'.* TO 'cpanelacct_shop'@'localhost';
FLUSH PRIVILEGES;

-- Note the host component. cPanel creates a user per host pattern.
SELECT user, host FROM mysql.user
WHERE user LIKE 'cpanelacct%';

4.3 Remote access, whitelisting and the database host

Connecting to a database from outside the server is the most commonly misconfigured part of shared hosting, and it is also the part most often left wide open. The correct path is: add the remote host to the account’s allowlist, create a user with the appropriate host pattern, and connect over TCP to the server’s own address.

# 1. Whitelist the source IP. This is a cPanel API call.
curl -H "Authorization: Bearer $CPANEL_TOKEN" \
  "https://server.example.com:2083/external/mysql/remote/mysql_list"

# 2. Add the developer's address. Never 0.0.0.0/0.
curl -H "Authorization: Bearer $CPANEL_TOKEN" \
  "https://server.example.com:2083/external/mysql/set_remote_mysql" \
  -d 'host=203.0.113.24'

# 3. A user whose host is the specific address, not '%'.
CREATE USER 'joesmith_app'@'203.0.113.24' IDENTIFIED BY 'strong-password';
GRANT SELECT, INSERT, UPDATE, DELETE ON 'joesmith_shop'.* TO 'joesmith_app'@'203.0.113.24';

# 4. Connect to the server, not to localhost.
mysql -h server.example.com -P 3306 -u joesmith_app -p joesmith_shop

Whitelisting the source address is the control that matters. The host pattern on the MySQL user is a second, weaker layer: it is enforced by MySQL but it is matched after a TCP connection has already been accepted, so it does not stop connection attempts from reaching the port at all. Use both, and treat the allowlist as the real boundary.

For a production application, a database connection from outside the server is a liability regardless of how good the password is. Use the application server’s own address in the allowlist and nothing else, and remove the entry the moment a contractor’s access ends. Remote access is a debugging tool with a short shelf life.

4.4 Importing, exporting and repairing through the panel

phpMyAdmin is the panel’s database interface, and the three operations that matter on a shared host are import, export and repair. Each has a failure mode that is specific to shared hosting, because the account lacks privileges that would make the operation trivial elsewhere.

# Import via the command line: faster and more reliable than the web UI,
# and it survives a PHP upload limit.

4.5 Character sets, collation and the utf8mb4 migration

MySQL’s utf8 is not UTF-8. It is utf8mb3, an implementation that cannot store four-byte characters, which includes every emoji and some historic scripts. The consequence appears years later, as an Incorrect string value error on a table that has been working perfectly since it was created.

-- What is actually in use across every database on the server.
mysql -e "
  SELECT DEFAULT_CHARACTER_SET_NAME cs, DEFAULT_COLLATION_NAME coll,
         COUNT(*) dbs
  FROM information_schema.SCHEMATA GROUP BY 1,2 ORDER BY 3 DESC;"

-- Per-table, which is where a partial migration shows up.
mysql -e "
  SELECT table_schema, table_name, table_collation
  FROM information_schema.tables
  WHERE table_schema NOT IN ('mysql','information_schema','performance_schema','sys')
    AND table_collation NOT LIKE 'utf8mb4%'
  ORDER BY table_schema, table_name;"

-- Columns still on the old character set.
mysql -e "
  SELECT table_schema, table_name, column_name, character_set_name
  FROM information_schema.columns
  WHERE character_set_name IS NOT NULL
    AND character_set_name NOT LIKE 'utf8mb4%';"
NameWhat it actually isMax charactersVerdict
utf8 / utf8mb3Three-byte UTF-8BMP only, no emojiDo not use for new work
utf8mb4Full four-byte UTF-8All of UnicodeCorrect choice
latin1ISO-8859-1One byte per characterLegacy; migrate away
ascii7-bit ASCII128 charactersLegitimate for enum-like columns

The subtlety with collation is that in the utf8mb4 family, the default is utf8mb4_0900_ai_ci in MySQL 8 and utf8mb4_unicode_ci in MySQL 5.7 and MariaDB. The two sort differently, so a table converted under one and queried under the other can return rows in a different order and behave differently for LIKE and GROUP BY.

-- Convert a whole table. This rewrites every row, so it is a blocking operation.
ALTER TABLE post
  CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- Check for data that cannot survive the conversion: 4-byte characters in a
-- utf8mb3 column will fail, and MySQL will tell you only on the first one.
SELECT id FROM post
WHERE CHAR_LENGTH(title) > CHAR_LENGTH(CAST(title AS BINARY))
LIMIT 20;

Use utf8mb4_0900_ai_ci for new MySQL 8 work. It is faster, uses the Unicode 9.0 algorithm, and treats emoji as characters rather than as multiple code points. If the server also runs MariaDB, or if clients connect with libraries that predate MySQL 8, use utf8mb4_unicode_ci instead — the connection collation mismatch is a common and confusing source of "illegal mix of collations" errors.

4.6 The command line: UAPI and WHM for database work

Every cPanel action is available through two authenticated APIs, and both are worth preferring over the web interface for anything scripted. UAPI is scoped to a single account; WHM API is scoped to the server and requires a WHM administrator token.

# UAPI: list databases for one account. Port 2083 is cPanel.
curl -H "Authorization: Bearer $CPANEL_USER_TOKEN" \
  "https://server.example.com:2083/external/mysql/list_databases"

# UAPI: create a database, a user, and grant in three calls.
curl -H "Authorization: Bearer $CPANEL_USER_TOKEN" \
     "https://server.example.com:2083/external/mysql/create_database" \
     -d 'database=shop'

curl -H "Authorization: Bearer $CPANEL_USER_TOKEN" \
     "https://server.example.com:2083/external/mysql/create_user" \
     -d 'user=app&password=STRONG&database=shop'

curl -H "Authorization: Bearer $CPANEL_USER_TOKEN" \
     "https://server.example.com:2083/external/mysql/set_privileges_on_database" \
     -d 'user=app&database=shop&privileges=ALL PRIVILEGES'

# WHM API: server-wide. Port 2087. Needs an admin token, not a user token.
curl -H "Authorization: whm $WHM_ROOT_USER:$(cat /root/.whm/whm.json | grep api_token | cut -d'"' -f4)" \
  "https://server.example.com:2087/json-api/list_databases?user=joesmith"

Note that the user parameter in the UAPI calls above is the unprefixed local name; cPanel adds the account prefix itself. Passing an already-prefixed name produces cpanelacct_cpanelacct_shop, which is the most common cause of a "database created but inaccessible" report. The WHM API is different: it requires the fully qualified cPanel username.

5 · Security, TLS and Hardening

A shared cPanel server hosts code from hundreds of mutually distrusting accounts on one kernel. Its security model is therefore mostly about containment: making sure one account cannot read another’s files, exhaust the server, or reach the network in a way that harms everyone else. 5.1 The trust model on a shared server

Every account runs as its own unprivileged Unix user, typically joesmith, in its own home directory. The web server user must be able to serve those files, which cPanel solves with a two-group arrangement: the file owner is the account, and the serving group is nobody or apache. This is the single most important structural fact on the server.

The correct response to a permissions error is to find the actual cause in the application or in open_basedir, never to widen the mode.

5.2 TLS: AutoSSL, certificates and the ACME dance

cPanel manages certificates through AutoSSL, which uses the ACME protocol to obtain and renew a certificate for every domain and subdomain in an account. It is reliable, and it fails in a small number of specific ways that are worth recognising on sight.

whmapi1 autossl_check user=joesmith

  if [ "$days" -lt 21 ]; then echo "WARN $host expires in $days days"; fi
done

5.3 ModSecurity and how to not fight it

ModSecurity is a web application firewall that inspects requests before they reach PHP. cPanel ships it with the OWASP rule set, which is aggressive enough to produce false positives on ordinary application traffic — particularly JSON APIs, and particularly anything containing SQL-like or script-like strings in a legitimate payload.

# Turn it on for a domain, and choose a mode.
whmapi1 security_set_vhost_security vhost=example.com \
        enabled=1 servernames=example.com docroot=/home/joesmith/public_html

# Two exclude files, one for the Apache layer and one for nginx.
ls -l /usr/local/apache/conf/domcom/example.com/user_rules/
ls -l /etc/nginx/conf.d/domains/example.com/

# A targeted exclusion, not a global disable. Scope it to one rule and one path.
# /usr/local/apache/conf/domcom/example.com/user_rules/modsec.conf
<IfModule mod_security.c>
  SecRuleEngine On
  SecRequestBodyAccess On

  <LocationMatch "^/api/v2/report$">
    SecRuleRemoveById 942100 942190 942260 942370
  </LocationMatch>
</IfModule>

Turn the rules off, reproduce the block, turn them back on, and read the error message. The message names the rule id that fired, and the id is a direct link to documentation explaining what pattern matched. Disable that specific rule for that specific path, note the date and the reason beside it, and review the exclusions on a schedule. A blanket SecRuleEngine Off is not a decision, it is the removal of the control.

ModSecurity in DetectionOnly mode logs matches without blocking. Running a new application in that mode for a few days before enabling enforcement produces a clean list of false positives and is far less disruptive than discovering them in production.

5.6 Responding to a compromised account

On a shared server, one compromised account is an operational emergency rather than only a customer problem: the same server has to stay up for everyone else. The response has a fixed order, and the order matters more than the speed.

# 1. Suspend first. This stops execution without destroying evidence.
whmapi1 suspendacct user=joesmith reason=Suspended pending security investigation

# 2. Preserve evidence before changing anything.
tar czf /root/incidents/joesmith-$(date +%F).tar.gz \
    -C /home joesmith 2>/dev/null
cp -a /var/log/auditor.log /root/incidents/ 2>/dev/null || true

# 3. Look for what the account actually did.
echo "== recently modified files =="
find /home/joesmith -mtime -7 -type f -newermt '-7 days' \
  -not -path '*/mail/*' -printf '%TY-%Tm-%Td %p\n' 2>/dev/null | sort -r | head -40

echo "== PHP files changed recently =="
find /home/joesmith -name '*.php' -mtime -7 -printf '%TY-%Tm-%Td %p\n' 2>/dev/null | sort -r | head -40

echo "== outbound connections from this account =="
ss -tnp 2>/dev/null | grep -E '(php|joesmith)' | head -20

Suspending rather than deleting is deliberate. If you delete the web shell and restore the site, the attacker still has the entry point that let them create it, and it returns. Find the vector — an outdated plugin, a weak password, an exposed backup file, an unpatched CMS — and fix that, or the incident repeats within days. Restoring from a known-good backup is part of the response, but it is not the response.

# 4. Rotate everything the account could have read, from a clean session.

         reason=Restored and patched email=1

A cPanel backup does not contain your DNS, and DNS is what makes email work. Restoring a mailbox onto a new server while the MX records still point at the old one produces a mailbox that is restored and unreachable. When planning any migration, treat the DNS zone as a separate artifact to be captured and applied, and treat DKIM private keys as the single most commonly forgotten item.

# What a restore archive actually contains. Check before relying on it.
tar tzf /home/joesmith/backup-2026-09-28.tar.gz | sed 's|/[^/]*$||' | sort -u | head -30

# The email authentication records, which are not in the cPanel backup.
dig +short TXT _dmarc.example.com
dig +short TXT default._domainkey.example.com
# The DKIM private key must be exported separately before any migration.
cat /home/joesmith/var/spool/dkim/default._domainkey.example.com.privatekey

6.2 Configuring backup destinations and retention

The default configuration backs up daily to the server’s own /home partition, which is the same disk the site is served from. That configuration survives a deleted file and survives a bad migration, and it does not survive disk failure.

# Point backups at remote storage. Ports: 2086 WHM, 2087 WHM over TLS.
whmapi1 backup_configure_multiple_destinations \
   id=1 name="Offsite S3" \
   type="s3" bucket="acme-backups" region="eu-west-1" \
   access_id="AKIA..." secret_key="..." \
   save=1

# Enable daily backups for an account, keeping two weeks.
whmapi1 savepopt user=joesmith \
   "backup"=1 "freq_daily"=1 "freq_weekly"=1 \
   "freq_monthly"=1 "days"=7 "destinations"=1

# Run one now and confirm it actually produced a file.
whmapi1 backup_run user=joesmith
ls -lh /home/joesmith/backup-$(date +%F).tar.gz

Use the 3-2-1 shape even here: three copies, on two media types, one of them off-site. cPanel’s scheduler gives you copy one and copy two within the same disk; the S3 or FTP destination is the third. Retention costs storage linearly, so a daily-and-weekly schedule for fourteen days is usually the best value on a shared host.

6.3 Restoring a site, a database, a mailbox and an account

Four restore operations, four different tools, and one shared warning: each of them overwrites the current state without asking twice. Take a copy of what you are about to replace.

# --- 1. A single account. Recreates files, databases, mail, cron and config. ---
whmapi1 restoreacct user=joesmith dir=/home/joesmith/backup-2026-09-28

# --- 2. A single database. ---
whmapi1 restoremysql user=joesmith db=joesmith_shop \
         dir=/home/joesmith/backup-2026-09-28

# --- 3. A single file or directory, from the UI or by hand. ---
#    Extract the archive and copy over the top; rsync is safer than cp.

6.4 Migrating a site between servers without downtime

A migration has two independent halves: moving the data and moving the traffic. Do the data first, cut over, then move what changed during the gap. Everything below follows from that ordering.

# --- Phase 1: copy the account to the new server, without moving traffic. ---
whmapi1 transferacct user=joesmith \
   desthost=newserver.example.com destport=2087 \
   destusr=root live=0     # live=0 means copy only

# --- Phase 2: freeze writes, copy the final delta, unfreeze. ---
# Put the old site into maintenance mode. Everything after this is quick.
cp index.php index.php.bak
cat > .maintenance <<'EOF'
<!doctype html><title>Brief maintenance</title><p>Back in a few minutes.
EOF

# Re-sync only the changed files and the databases.
rsync -az --delete /home/joesmith/ root@newserver:/home/joesmith/
mysqldump -u joesmith_shop -p --single-transaction --routines --triggers joesmith_shop \
  | ssh root@newserver 'mysql -u joesmith_shop -p joesmith_shop'

# --- Phase 3: lower the DNS TTL at least 24 hours BEFORE phase 2. ---
# dig example.com MX   and   dig example.com A

# --- Phase 4: point DNS, verify, then keep the old server warm for 48 hours. ---

The single most common cause of a failed migration is forgetting that DNS was cached. A record with a 3600-second TTL cached aggressively by resolvers and browsers can keep traffic arriving at the old server for hours after the change, and those requests are then answered by a site whose files were already moved. Lower the TTL a full day ahead, and leave the old server serving read-only for two days after cutover.

7.1 Finding the slow request, not guessing at it

On a shared server you do not have a profiler, but you do have the access log, and the access log contains a response time on most Apache and LiteSpeed configurations. The first step is always to establish whether the site is slow, and for whom.

# Slowest requests in the current access log, by total time.
awk '{print $NF, $0}' /var/log/apache2/access.log \
  | sort -rn | head -20 \
  | awk '{printf "%8.3fs  %s  %s\n", $1, $6, $7}'

# Same, but grouped: which URL is responsible for the most total time.
awk '{print $NF, $7}' /var/log/apache2/access.log \
  | awk '{t[$2]+=$1; n[$2]++} END {for (u in t) printf "%9.1fs %6d  %s\n", t[u], n[u], u}' \
  | sort -rn | head -20

# Error rate by status, for the last hour.
awk '$9 ~ /^5/ {print $9}' /var/log/apache2/access.log | sort | uniq -c
awk '$9 ~ /^4/ {print $9}' /var/log/apache2/access.log | sort | uniq -c

The second query is usually the more useful one. One request taking thirty seconds is an incident; a thousand requests taking one second each is a design problem, and only the grouped view shows the second kind. Always ask which URL is consuming the most total time before deciding what to optimise.

# Per-account view, so one noisy customer does not hide a platform problem.
whmapi1 --output=jsonpretty apache_status | head -40

# Top IPs by requests in the last 2000 lines - a crude but effective
# way to spot a scraper or a loop.
tail -2000 /var/log/apache2/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -15

7.3 Diagnosing a slow site through MySQL

A slow website on shared hosting is usually a slow query. The slow query log is often disabled by default, which means the first action is to turn it on, wait, and then look.

# Enable the slow log. Everything after 1 second is recorded.
whmapi1 --output=json set_mysql_config \
   'setting_name'=slow_query_log 'value'=1
whmapi1 --output=json set_mysql_config \
   'setting_name'=long_query_time 'value'=1

# What is running right now, and what is it waiting on?
mysql -e "
  SELECT id, user, db, command, time, state,
         LEFT(info, 120) AS sql_text
  FROM information_schema.processlist
  WHERE command <> 'Sleep'
  ORDER BY time DESC LIMIT 20;"

# Which statement shape is slowest on average? The digest view is
# aggregated, so one bad loop cannot hide behind 500 identical calls.
mysql -e "
  SELECT LEFT(digest_text, 90) AS statement,
         COUNT_STAR        AS calls,
         ROUND(SUM_TIMER_WAIT/1e12, 2) AS total_s,
         ROUND(AVG_TIMER_WAIT/1e9, 1)  AS avg_ms,
         SUM_ROWS_EXAMINED AS rows_scanned
  FROM performance_schema.events_statements_summary_by_digest
  ORDER BY SUM_TIMER_WAIT DESC LIMIT 15;"

# Is it the database at all? Compare against a static file on the same account.
for i in 1 2 3; do
  printf "static : "; curl -s -o /dev/null -w "%{time_starttransfer}s\n" https://example.com/robots.txt
  printf "dynamic: "; curl -s -o /dev/null -w "%{time_starttransfer}s\n" https://example.com/search?q=x
done

# If static is fast and dynamic is slow, it is PHP or MySQL, not the server.
# If both are slow, it is the server, the network, or the customer's code
# is including a remote resource on every request.

Compare a static file against a dynamic one. It is the fastest way to halve the search space: if robots.txt returns in 40 ms and search?q=x takes four seconds, the problem is in PHP or MySQL on that account, and the server’s general health is irrelevant. If both are slow, the problem is above the application and you should look at load and the other accounts.

7.4 Diagnosing mail delivery failures

Mail problems on cPanel are almost always a deliverability or configuration problem rather than an Exim problem. Exim does its job; the message is rejected downstream, or the sending IP has no reputation.

# Was the message accepted by Exim at all?
grep "joesmith@example.com" /var/log/exim_mainlog | tail -20

# The disposition line tells you what happened next. Read it literally.
#   => 250 2.0.0 Ok: queued            - accepted, we are done
#   <= 550 5.7.1 Message refused       - rejected, do not retry
#   == 550 5.7.1 ... (timeout)         - deferred, will retry
#   Completed                            - delivered successfully

# The queue, and what is stuck in it.
mailq | tail -20
exim -bpc          # messages in the queue
exim -bp | wc -l

# Every recipient that hard-failed, with the remote reason.
awk '/Completed|Completed/' /var/log/exim_mainlog | tail -5
grep '<=' /var/log/exim_mainlog | tail -20

7.5 Load, processes and resource exhaustion

On a shared server, one account’s runaway process degrades everyone. The tools are standard Linux; what differs is knowing which process belongs to which account and what the acceptable ceiling is.

# The three numbers that matter, and their acceptable values on shared hardware.
uptime                                  # load average; 1.0 per core is saturated
free -m                                 # available memory, not free; watch 'available'
df -h                                   # root and /home separately, plus inode use
df -i                                   # inodes run out before bytes on small accounts

# Who is consuming CPU right now.
top -b -n1 | head -15
ps -eo user,pid,pcpu,pmem,etime,comm --sort=-pcpu | head -20

# Which account owns which process, and how long has it been running.
ps -eo user,pid,etime,args --sort=-etime | grep -vE 'grep|CRON|^\s*USER' | head -20

# Open files, for the account hitting the limit.
ls /proc/$(pgrep -u joesmith -f php-fpm | head -1)/fd 2>/dev/null | wc -l

# The three failures that generate support tickets on shared hosting.
mysql -e "SHOW VARIABLES LIKE 'max_connections'"
mysql -e "SHOW STATUS LIKE 'Threads_connected'"
mysql -e "SHOW STATUS LIKE 'Max_used_connections'"
# Max_used approaching max_connections is why a new account's site
# suddenly cannot connect at all, despite nothing being wrong with it.

# CloudLinux CageFS: which account is using how much, and is it jailed.
cagefsctl --list
lveinfo --user=joesmith --list
lveps --user=joesmith

# Account disk usage, which is where "my site disappeared" usually starts.
du -sh /home/* 2>/dev/null | sort -rh | head -15
quota -vs * 2>/dev/null | grep -E 'joesmith|Block limits' | head -10

Check inodes before you check bytes when a site has stopped working. A customer with 40,000 small files in a cache directory can exhaust the inode count while using almost no space, and the symptom is a site that cannot create a single new file while the disk report shows plenty free. df -i is the command that finds this in one second.

7.6 A diagnostic checklist that works at 3am

The order below is deliberate. Each step is cheap, each one eliminates a large class of causes, and none of them changes anything. Run it top to bottom and you will have the answer before you change a single setting.

# 1. Is the account suspended? The most common "site is down" report.
whmapi1 --output=jsonpretty list_suspended | grep -A2 -i "joesmith"

# 2. Is the domain resolving to this server at all?
dig +short "example.com" @1.1.1.1
grep -E '"'"'example\.com'"'"' /var/named/example.com.db | grep -v ';'

# 3. Does the server answer for that host, and with what status?
curl -sI -H '"'"'Host: example.com'"'"' http://127.0.0.1/ | head -3

# 4. Does the document root exist, and is it readable?
ls -ld /home/joesmith/public_html
ls -l  /home/joesmith/public_html/index.php
sudo -u joesmith test -r /home/joesmith/public_html/index.php && echo readable || echo NOT-readable

# 5. What is the actual error in the log for a real request?
curl -s -o /dev/null -w '"'"'%{http_code}\n'"'"' -H '"'"'Host: example.com'"'"' http://127.0.0.1/
tail -5 /var/log/apache2/error.log

# 6. PHP: is the selected version even running, and is opcache failing?
ls /opt/cpanel/ea-php/
grep -iE '"'"'fatal|parse error|allowed memory'"'"' /var/log/apache2/error.log | tail -5

# 7. Database: can PHP connect?
mysql -u joesmith_shop -p -e '"'"'SELECT 1'"'"' joesmith_shop
mysql -e '"'"'SELECT COUNT(*) FROM information_schema.processlist'"'"'

# 8. Resources: is this account the one causing the pressure?
lveinfo --user=joesmith --list
du -sh /home/joesmith
ps -u joesmith -o pid,pcpu,pmem,etime,args --sort=-pcpu | head

# 9. What did the user change most recently?
grep '"'"'joesmith'"'"' /var/log/auditor.log | tail -20

Step 9 is the one that ends most investigations. A surprising share of "the site is down" reports are the result of something the account owner did minutes earlier — a bad .htaccess, a moved file, a changed database password, a deleted cron. The auditor log answers the question in one command, and asking it early turns a long investigation into a single lookup.

Change one thing at a time and re-test after each. The instinct under pressure is to adjust three settings at once, which produces an uninterpretable result and, if the site recovers, no knowledge of what actually fixed it. The checklist above is read-only by design, which is a deliberate property.
