Welcome — How to Use This Next.js Guide

What this guide assumesHow the chapters fit togetherThe mental model you need firstConventions and how to read the codeWorking through the exercises

Next.js is a React framework, and almost every confusion with it comes from not knowing which of your code runs on the server and which runs in the browser. This guide is organised around making that boundary explicit, because once you can state where a piece of code runs, every Next.js decision becomes obvious.

What this guide assumes

You know React — the component model, hooks, effects and state from a React guide at this level. You do not need Node.js server experience; where it matters, it is explained.

  • Node.js 20 or newer. Next.js 15 requires it.
  • TypeScript. Next.js has first-class types and the type-level route helpers are worth learning.
  • A hosted platform is optional. Everything here works with next dev and next build locally, and deploys to Vercel, Netlify, a container, or a VM.

Versions used here: Next.js 15 with the App Router, React 19, and Turbopack as the default dev bundler. The App Router replaced the Pages Router in 13.4 and is the recommended default; the Pages Router is covered in one chapter for migrating existing projects.

How the chapters fit together

  • Part one (1–4): the two runtimes. Server Components, the client boundary, data fetching and the request lifecycle. This is the part that changes how you write React.
  • Part two (5–8): routing and rendering. The file system router, layouts, streaming, caching and revalidation.
  • Part three (9–13): the platform. Server Actions, middleware, forms, images, fonts and metadata.
  • Part four (14–19): production. Auth, performance, testing, deployment, the Pages Router migration, and architecture.

The mental model you need first

Hold this one idea and most of the framework stops being surprising.

// Next.js renders your React tree in TWO places, and a component belongs
// to one of them permanently.
//
//   SERVER                          BROWSER
//   runs Node.js                    runs JS
//   has the filesystem, the         has no filesystem, no secrets,
//   database, the network            can be called directly by anyone
//   renders to HTML                 hydrates the HTML
//   cannot use useState, useEffect  cannot read the database
//
// THE DEFAULT is the server. A component is a Server Component unless it
// says otherwise. 'use client' is an opt-in, not a starting point.
//
// this is the opposite of what most tutorials lead with, and it is the
// single most important fact in the framework.

// 'use client' marks the BOUNDARY. Everything imported into a client
// component becomes client code too, transitively.
'use client';
import Counter from './Counter';   // Counter is now a Client Component
// and if Counter imports a big library, that library is in the bundle

// you do NOT need 'use client' on a component that only renders other
// server components and has no interactivity. Most of your app should
// not have it.

Two consequences follow immediately:

// 1. you cannot import a server-only thing into a client component
//    this is a build error, and it is a feature:
//      import { db } from '@/lib/db';        in a client component
//      -> "You're importing a component that needs db. That React hook
//          only works in a Server Component"

//    the fix is to pass the DATA down as a prop, not the client

// 2. the client boundary is a one-way street
//    a Server Component can render a Client Component and pass it
//    serialisable props. It cannot receive a function from one.
<SearchBox
  results={results}            // data: fine
  onSelect={() => ...}       // function: not serialisable
/>                            // -> "Functions cannot be passed to Client
                               //     Components" - use a Server Action

Conventions and how to read the code

File names in the App Router are meaningful, and the examples use the standard conventions:

  • page.tsx — a route. Its presence in a folder creates the URL.
  • layout.tsx — shared UI wrapping this route and everything under it.
  • loading.tsx — a loading UI, streamed automatically.
  • error.tsx — an error boundary for this segment.
  • not-found.tsx — the 404 UI for this segment.
  • template.tsx — like a layout, but remounts on navigation.
  • route.ts — a custom HTTP handler, no UI.
  • Anything prefixed _ is excluded from routing. _components/ and _lib/ are the conventional homes for helpers.
// the shape of an app
app/
  layout.tsx           root layout: html, body, global nav
  page.tsx             /
  globals.css
  (marketing)/         a group: no URL segment, purely organisational
    layout.tsx
    page.tsx           /
    pricing/page.tsx   /pricing
  products/
    layout.tsx
    page.tsx           /products
    [id]/              a dynamic segment
      page.tsx         /products/123
      loading.tsx
      error.tsx
  api/
    route.ts           /api - a POST handler, no UI
  _components/         excluded from routing
    CartButton.tsx     'use client'
  _lib/
    db.ts              server-only, never imported by a client component

// the URL is the folder path. (marketing) contributes nothing.

Working through the exercises

Every chapter ends with exercises. Run them in a real project — npx create-next-app@latest — because the build errors described in chapters 1 and 2 are the whole point and they only appear in a real build.

One habit that pays for itself immediately: open the browser devtools Network panel and keep it visible while developing. Click a server component and you will see an HTML document, not a JS bundle. That one observation explains more about Next.js than any diagram.

1 · The Two Runtimes

What actually happens on a requestTwo environments, two globalsMarking code server-onlyEnvironment variablesNode versus Edge runtimesWhat each choice costs

A single page request in Next.js passes through several environments with different capabilities and different security properties. Knowing which is which is the foundation for every decision that follows.

What actually happens on a request

// GET /products/42
//
//  1. the request hits your server (or the edge, or a CDN)
//
//  2. Next.js matches the URL against the app/ tree
//     /products/[id]/page.tsx  with  id = "42"
//     and collects every layout.tsx on the path:
//       app/layout.tsx          root
//       app/products/layout.tsx products
//       app/products/[id]/page.tsx
//
//  3. layouts render TOP DOWN, page LAST
//     each is a React tree, so this is a normal render
//
//  4. Server Components run HERE, on the server
//     they can await, read the database, read env vars
//     their output is HTML plus a serialised RSC payload
//
//  5. the HTML response is streamed to the browser as it renders
//     (this is why loading.tsx and Suspense work - see ch6)
//
//  6. the browser downloads the JS chunks for the Client Components
//
//  7. the browser hydrates those components and takes over the DOM
//
//  8. from then on, navigation is client-side
//     the RSC payload for the next route is fetched, no full page load
//
// Server Components do NOT run in steps 6-8. They ran once, on the server.
// They are not re-run on the client. If a Server Component's output is
// not there, re-rendering in the browser is not going to produce it.

This is why a Server Component cannot have useState. There is no client instance of it to hold state — the component executed, produced a description, and that is the end of it. The state would have nowhere to live between interactions.

Two environments, two globals

//                    Server            Browser
// process.env        YES               bundled at build - only NEXT_PUBLIC_*
// fs                 YES               no
// path/child_process YES               no
// Buffer             YES               no (unless polyfilled)
// window/document    no                YES
// localStorage       no                YES
// navigator          no                YES
// fetch              full              browser fetch, no caching rules
// setTimeout         yes               yes
// WebSocket          yes               yes
// Deno / Bun globals yes (node runtime) no

// consequences that surprise people
// 1. an object with methods cannot cross the boundary
//   pass plain data: strings, numbers, booleans, null, undefined,
//   Date (yes, serialised), plain objects, arrays, Map, Set,
//   typed arrays, Promise, and JSX elements

// 2. a class instance cannot cross
//   class Money { constructor(c) { this.c = c } }
//   <Price money={new Money(100)} />      Error
//   <Price cents={100} />                  fine

// 3. a function cannot cross
//   <Form onSubmit={() => save()} />     Error
//   <Form action={saveAction} />           fine (ch9)

Marking code server-only

There is a package for this, and it should be used on every module that touches secrets or a database.

// lib/db.ts
import 'server-only';          // npm i server-only
import { Pool } from 'pg';

export const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// what it does: if ANY client component, anywhere in the dependency
// graph, imports this module, the BUILD FAILS with a clear message.
// without it, the mistake is a runtime error in the browser - or worse,
// a successful build with your connection string in the bundle.

// the reverse: client-only modules
'use client';
import { Chart } from './Chart';   // everything imported is client code
// use 'client' on the LEAF that needs interactivity, not at the top of
// your tree. 'use client' at the root turns your entire app into a SPA
// and throws away most of what Next.js does for you.

process.env.SECRET in a client component is a real leak, not a type error. A non-NEXT_PUBLIC_ variable referenced in client code is replaced with undefined at build time — safe but silently broken. Referenced in a module that reaches the bundle by accident, older tooling inlined it. Always add 'server-only' and always check what you import into a client component.

Environment variables

// .env.local        not committed, your machine
// .env              committed defaults, safe to share
// .env.production   production values, committed, no secrets
//
// the rule
//   NEXT_PUBLIC_FOO   -> inlined into the client bundle at build time.
//                       public. treat as broadcast.
//   EVERYTHING_ELSE   -> server only. read in server components, route
//                       handlers, server actions and middleware.

// reading them
const url = process.env.DATABASE_URL;            // server only
const version = process.env.NEXT_PUBLIC_VERSION; // any

// a typed accessor, so a missing variable fails at boot not at 3am
// lib/env.ts
import 'server-only';

function required(name: string): string {
  const v = process.env[name];
  if (!v) throw new Error(`Missing required environment variable: ${name}`);
  return v;
}

export const env = {
  DATABASE_URL: required('DATABASE_URL'),
  SESSION_SECRET: required('SESSION_SECRET'),
  STRIPE_SECRET_KEY: required('STRIPE_SECRET_KEY'),
};

// and validate the PUBLIC ones too
if (!/^\d+\.\d+\.\d+$/.test(process.env.NEXT_PUBLIC_VERSION ?? '')) {
  throw new Error('NEXT_PUBLIC_VERSION must look like 1.2.3');
}

Because NEXT_PUBLIC_ variables are inlined at build time, changing one requires a rebuild, not just a restart. This surprises people deploying to a platform that restarts containers. Treat a public env var as part of the build, not the runtime.

Node versus Edge runtimes

Next.js can run your code in two very different runtimes, and the choice is per-route or per-page.

// DEFAULT: the Node.js runtime. full Node APIs, no artificial limits.
export const runtime = 'nodejs';     // this is the default; no need to say it

// EDGE: a V8 isolate at the CDN's edge. starts in ~1ms instead of ~300ms,
// but NO Node built-ins.
export const runtime = 'edge';

// what you lose on the edge
//   fs, path, child_process, Buffer
//   most npm packages that depend on them
//   native addons
//   long-lived in-process caches (a new isolate per request in some
//     platforms, so a module-level Map is not a cache)
//
// what you keep
//   fetch, Web Streams, the standard Web APIs
//   crypto.subtle
//   most of the Web platform

// the real trade-off
//   edge  = faster cold start, less CPU per request, global distribution
//   node  = everything works, longer cold start
//
// a pragmatic rule: put edge on middleware and on genuinely
// request-scoped, read-only, latency-sensitive routes. Put a database
// anywhere else - a TCP connection to Postgres is not available on the
// edge, and a proxy through an HTTP data API adds latency and a failure
// mode that a direct connection does not have.
// where you declare it
// app/api/geo/route.ts
export const runtime = 'edge';
export async function GET(req: Request) {
  const ip = req.headers.get('x-forwarded-for');
  return Response.json(await lookup(ip));    // fetch-based, fine on edge
}

// app/products/page.tsx
export const runtime = 'nodejs';             // default; reads the DB directly
export default async function Page() {
  const rows = await pool.query('SELECT * FROM products');
  return <List rows={rows.rows} />;
}

// a third option, the most capable one
export const runtime = 'nodejs';
export const preferredRegion = 'home';       // keep compute near the DB
// a Node serverless function with a full filesystem and a warm-ish start,
// deployed close to your database. often the right answer for anything
// data-heavy

What each choice costs

// SERVER COMPONENT
//   pros: reads the DB, no client JS shipped, secrets stay server,
//         no data-fetching waterfall, the HTML is complete for crawlers
//   cons: no interactivity, runs on every request unless cached (ch7),
//         must return serialisable output

// CLIENT COMPONENT
//   pros: state, effects, event handlers, browser APIs
//   cons: shipped to the browser, so its imports are too, re-renders,
//         its markup arrives in the HTML but its behaviour needs JS

// THE PRACTICAL DIVISION
//   server: fetch data, format it, decide what to render
//   client: everything the user can do to it
//   the boundary should be as low in the tree as possible, and as small
//   as possible. A 4 KB client component that owns a dropdown is a good
//   design. 'use client' on your layout is not.

Exercises 1

  1. Create a project and add lib/db.ts with import 'server-only'. Import it from a client component and confirm the build fails, not just the dev server.
  2. Add lib/env.ts with a required() helper. Delete one variable and confirm the app fails at boot with a readable message rather than at first query.
  3. Write a route.ts that returns the current runtime and the region, declared on the edge, and another on Node. Note the cold-start difference in the response headers your platform sets.
  4. Take an existing client component and move its data fetching up into a server parent, passing only serialisable props down. Measure the client bundle before and after.
  5. Deliberately pass a Date, a Map, a class instance and a function from a server component to a client one. Record the exact error for each, then explain which of the four is legal and why.

2 · Server and Client Components

The mechanics of the client boundary: what each kind of component can do, what may be passed between them, and the composition patterns that keep a mostly-server application from turning into a mostly-client one.

Writing a Server Component

A Server Component is just an async function with no 'use client' directive. There is nothing else to declare.

// app/products/[id]/page.tsx
import { db } from '@/lib/db';            // server-only
import { notFound } from 'next/navigation';
import AddToCart from './AddToCart';       // 'use client' inside

export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>;     // async in Next 15
}) {
  const { id } = await params;             // must await

  const product = await db.product.findUnique({ where: { id } });
  if (!product) notFound();                // renders not-found.tsx, 404

  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.description}</p>

      {/* data crosses as a plain object: fine */}
      <AddToCart productId={product.id} price={product.price} available={product.stock > 0} />
    </main>
  );
}

// no 'use client', no useState, no useEffect, no event handler.
// params and searchParams are Promises in Next 15 - a real change that
// catches people upgrading.

Async components and Suspense

A Server Component may be async. That is the mechanism behind streaming, and it is why a slow query does not block a fast one.

// a page with two independent slow sections
export default async function Page() {
  // NOT this - the whole page waits for the slower of the two
  const [reviews, recommendations] = await Promise.all([
    getReviews(),          // 800ms
    getRecommendations(),  // 1200ms
  ]);
  return <Layout reviews={reviews} recs={recommendations} />;
}

// THIS - each streams in as it resolves
export default function Page() {
  return (
    <Layout>
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews />                {/* async server component */}
      </Suspense>
      <Suspense fallback={<RecsSkeleton />}>
        <Recommendations />
      </Suspense>
    </Layout>
  );
}

async function Reviews() {
  const reviews = await getReviews();       // 800ms
  return <ReviewList reviews={reviews} />;
}

// the shell arrives immediately, ReviewsSkeleton streams, then Reviews
// replaces it. total time to first byte is roughly zero in both cases -
// what changes is when the CONTENT arrives.

// layout.tsx is a natural Suspense boundary: it is the shell
// loading.tsx wraps the page in its segment automatically, which is
// shorthand for exactly this

You cannot put a useState in a server component, so the skeleton is a static component. The one place this becomes awkward is a skeleton that needs to match real content dimensions — pass the shape in from the parent as plain data, or use CSS aspect-ratio so the placeholder occupies the space the real content will.

Writing a Client Component

// app/products/AddToCart.tsx
'use client';

import { useState, useTransition } from 'react';
import { addToCart } from './actions';       // a server action, ch9

export default function AddToCart({
  productId, price, available,
}: { productId: string; price: number; available: boolean }) {
  const [quantity, setQuantity] = useState(1);
  const [pending, startTransition] = useTransition();

  return (
    <div>
      <label>
        Quantity
        <input
          type="number"
          min={1}
          value={quantity}
          onChange={(e) => setQuantity(Number(e.target.value))}
        />
      </label>

      <button
        disabled={!available}
        onClick={() => startTransition(() => addToCart(productId, quantity))}
      &>
        {pending ? 'Adding...' : 'Add to cart'}
      </button>
    </div>
  );
}

// the component is small, it owns only quantity, and the price prop is
// data it does not need to fetch. the server did the fetching.

// 'use client' is transitive: everything AddToCart imports ships too
import { motion } from 'framer-motion';   // 40KB in the bundle
// import what you need, or move the animation into its own leaf component

What can cross the boundary

// ALLOWED as props from server to client
string, number, boolean, null, undefined
bigint
plain object / array of allowed values
Date                       serialised to an ISO string, arrives as a string
Map, Set                    serialised to {} and {} - LOSSY
typed arrays                Buffer, Uint8Array - pass as-is, Node only
Promise                     a promise prop, then await in a client component
JSX elements                a server-rendered child, not re-rendered client-side
Server Action references    the only way to pass behaviour

// NOT ALLOWED
() => {}                          function
class instances                     anything with a prototype
Symbol, WeakMap, WeakSet
DOM nodes
getters and setters are lost
class Foo { get x() { return 1 } }  <Foo />  -> x is gone
non-plain objects (URL, Headers)    use toJSON at the boundary

// the Date trap, in full
// server: <Client date={new Date()} />
// client receives a STRING. new Date(str) works, but date.getMonth()
// throws. if you need a Date on the client, construct it there, or send
// a timestamp and document the conversion.

// the JSX-element exception, and why it matters
// server: <ClientLayout><ServerHeavyThing /></ClientLayout>
// the child was rendered on the SERVER. its HTML is in the response and
// its JS is not shipped, but the client component can receive it as
// children and place it. this is the main way to have interactivity
// without losing server rendering.

A Map or Set passed from a server component arrives as an empty object. This fails silently — no error, just missing data. If you need a set-like structure across the boundary, pass an array and rebuild it in the client component, or pass a plain object keyed by id.

Where to put the boundary

// the WRONG boundary: as high as possible
'use client';
// app/layout.tsx
export default function RootLayout({ children }) {
  const [theme, setTheme] = useState('light');
  return (
    <html>
      <body>
        <ThemeToggle theme={theme} onChange={setTheme} />
        {children}
        </body>
    </html>
  );
}
// now EVERYTHING below is a client component. The database import that
// worked yesterday fails to build. Your static page ships as JS.

// the RIGHT boundary: as low as possible, one per interactive island
// app/layout.tsx - server
export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Header />               {/* server, renders children slots */}
        {children}
        <Footer />
      </body>
    </html>
  );
}

// app/components/ThemeToggle.tsx - client, 30 lines
'use client';
export function ThemeToggle() { /* ... */ }

// the rule of thumb: one 'use client' per interactive leaf. A page
// should typically contain three to eight of them, not one at the top.

// a test: if a component has no state, no effect, no event handler and
// no browser API, it does not need 'use client'. Delete the directive
// and see if the build still passes. It almost always does.

Context across the boundary

// a Server Component can PROVIDE to a Client Component
// app/providers.tsx  - server
import { ThemeProvider } from './ThemeProviderClient';

export default function Providers({ children }: { children: React.ReactNode }) {
  return (
    <ThemeProvider theme="dark">
      {children}          {/* client children passed through, fine */}
    </ThemeProvider>
  );
}

// a Client Component canNOT provide a context to a Server Component
// because the provider's children would have to be rendered by the
// client, and the point is that they are not.

// the practical pattern for shared state
//   server: read the data, pass it down as props
//   client: a provider near the top of the CLIENT tree holds the
//           interactive state
//   the two never have to share a context

// reading cookies/session in a server component and passing it down
import { cookies } from 'next/headers';

export default async function Shell({ children }) {
  const session = await getSession();     // reads cookies() internally
  return (
    <ClientShell user={session?.user ?? null}>
      {children}
    </ClientShell>
  );
}

Composition patterns that work

// PATTERN 1: server parent, client leaf, server children
// layout.tsx (server)
export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <div className="shell">
      <Sidebar user={user} />        {/* client, interactive */}
      <main>{children}</main>    {/* server children, untouched */}
    </div>
  );
}

// PATTERN 2: render a client component FROM a server component with
// server-rendered children - the "children as a prop" trick
// app/comments/page.tsx (server)
export default async function Page() {
  const comments = await getComments();
  return (
    <CommentList comments={comments}>
      {/* this is server-rendered and passed as children */}
      {comments.map((c) => (
        <CommentRow key={c.id} comment={c} />   {/* server */}
      ))}
    </CommentList>
  );
}
// CommentList is 'use client' and handles the sort control. The rows
// are server components: their data fetching and rendering happen on the
// server, and only the control is interactive.

// PATTERN 3: an interactive wrapper around server content
// 'use client'
export function Disclosure({ summary, children }: {
  summary: React.ReactNode;
  children: React.ReactNode;
}) {
  const [open, setOpen] = useState(false);
  return (
    <details open={open} onToggle={(e) => setOpen(e.currentTarget.open)}>
      &ltsummary>{summary}</summary>      {/* server-rendered summary */}
      {open && children}                  {/* server-rendered content */}
    </details>
  );
}

// PATTERN 4: passing a server action as a prop
// <DeleteButton action={deleteProduct.bind(null, id)} />
//   server action, so the client can pass it to onClick
// <ClientRow onDelete={deleteProduct.bind(null, row.id)} row={row} />
//   both are a function and a plain object: one legal, one not

  4. Implement the children-as-a-prop pattern: a client SortableList receiving server-rendered rows as children. Verify the rows are not in the client bundle by searching for their text in the built JS.

3 · The Rendering Lifecycle

Every Next.js page is rendered in one of a small number of ways, and the choice is made for you unless you make it. This chapter is about knowing which one you got, and about the two functions that make the choice explicit.

A request end to end

// GET /dashboard  (signed in)

//  1. CDN edge. is this URL in the cache?
//     no, and this is a dynamic route with a session cookie

//  2. Next.js server. run middleware first (ch8):
//     rewrite? redirect? authenticate? add a header?

//  3. Resolve the route to a React tree.
//     app/dashboard/layout.tsx
//     app/dashboard/page.tsx

//  4. Collect what each component needs.
//     layouts render top-down; the page renders last.

//  5. Each Server Component executes on the server.
//     this is where 'await' happens, where the DB is read, where
//     fetch calls are made. Some results are cached (ch7).

//  6. React renders the tree to a stream.
//     - already-resolved parts flush immediately
//     - pending parts inside a Suspense boundary flush a fallback
//     - the RSC payload is interleaved with the HTML

//  7. Response streams to the browser. TTFB is low even if the page
//     takes 2 seconds, because the shell goes out first.

//  8. Browser parses the HTML. Content is visible and indexable now.

//  9. Browser downloads client chunks for the Client Components only.

// 10. Hydration. Only the interactive parts become live.

// 11. Later navigations: the router fetches the RSC payload for the
//     next route and swaps the tree. No document reload, no full
//     page data refetch, and the server components on that route
//     execute on the server again.

Step 6 is the one people miss. Next.js streams by default, which is why a slow query degrades gracefully instead of showing a spinner for the whole page.

Static, dynamic, and how Next decides

// A STATIC route
//   rendered ONCE at build time. The HTML file is what gets served.
//   Every request gets the same bytes.
//
//   Used when the output is the same for everyone: a blog post,
//   a product page for a slow-changing catalogue, a docs page.
//
//   revalidated in the background every N seconds (ISR, ch7), or
//   never, or on demand via revalidatePath / revalidateTag.
//
// a page is STATIC if none of these appear in its render:
//   - cookies(), headers(), draftMode()
//   - searchParams (dynamic, see below)
//   - a route or segment marked dynamic
//   - an uncached fetch of a non-static source
//   - uncached DB queries (a non-static API, or a dynamic data source)

// A DYNAMIC route
//   rendered per request on the server. Can read the session, the
//   user's cookies, the current time, anything.
//
//   the response is not cached by the CDN unless you say so
//
// A PARTIALLY STATIC route
//   the shell is static, and the parts that need the request are
//   streamed in behind Suspense. This is Partial Prerendering and
//   it is the interesting middle case.
// you can see which it is
//   next build prints a route table:
//
//   ○  (Static)    prerendered as static content
//   ●  (SSG)       prerendered as static HTML (uses generateStaticParams)
//   ƒ  (Dynamic)   server-rendered on demand
//   ◐  (Partial)   prerendered with dynamic holes (PPR)
//
//   this table is the single most useful diagnostic in Next.js. If a
//   page you expected to be static is marked ƒ, something is reading
//   the request. `next build` will often name the culprit.

// forcing a choice
export const dynamic = 'force-static';    // never dynamic
export const dynamic = 'force-dynamic';  // always dynamic
export const revalidate = 3600;          // ISR: at most 1 hour stale
export const dynamicParams = true;       // allow unknown params to render

// a route can only be one of these. If a page reads headers() and you
// set force-static, the read returns empty rather than erroring, and
// you get a page that silently lacks what it needed.

Opting into dynamic rendering

// WHY a page becomes dynamic, and how to control it

// 1. an uncached fetch with a dynamic source
//    a fetch with no-store, or with cache: 'no-store', is dynamic
//    a fetch to an authenticated URL is dynamic by default
const data = await fetch('https://api.internal/me', { cache: 'no-store' });

// 2. request APIs
const cookieHeader = (await cookies()).get('session');
const ua = (await headers()).get('user-agent');

// 3. searchParams
//    a page that reads searchParams is dynamic, because the URL is
//    part of the request identity
export default async function Page({
  searchParams,
}: { searchParams: Promise<{ q?: string }> }) {
  const { q } = await searchParams;
  return <SearchResults query={q} />;
}

// 4. uncached database access
const rows = await db.query.someCmsTable();   // no cache tag

// opting out, deliberately
//   wrap the dynamic part in a Suspense boundary, and make the rest
//   static. This is Partial Prerendering (next section).

// opting in, deliberately
export const dynamic = 'force-dynamic';
//   when the page genuinely needs per-request data AND you have no
//   useful static shell to cache around it

Partial prerendering

PPR splits a route into a static shell, cached at build, and dynamic holes, filled per request. It is the answer to "this page is mostly the same for everyone but has a personalised corner".

// next.config.ts
const nextConfig = {
  experimental: { ppr: 'incremental' },   // or true for the whole app
};

// a route with a static shell and a dynamic hole
// app/dashboard/page.tsx
import { Suspense } from 'react';

export default function Page() {
  // everything outside the Suspense boundary is prerendered at build time
  return (
    <div className="dashboard">
      <h1>Dashboard</h1>
      <Nav />                        {/* static */}
      <Suspense fallback={<FeedSkeleton />}>
        <PersonalFeed />              {/* dynamic, per request */}
      </Suspense>
    </div>
  );
}

async function PersonalFeed() {
  const user = await getSession();          // cookies() -> dynamic
  const feed = await getFeed(user.id);      // no-store -> dynamic
  return <Feed items={feed} />;
}

// the shell is served from cache instantly, everywhere, forever.
// only the hole is rendered per request.
// this turns "my dashboard is slow" into "the shell is cached and the
// feed streams in", with no per-user shell cache explosion.

PPR is still experimental, but the mental model it teaches is the one you need regardless: separate what is the same for everyone from what is specific to this request, and cache the first. Even without PPR you can achieve most of it with loading.tsx and a well-placed Suspense boundary.

Reading headers and cookies

// both are ASYNC in Next 15, and they are DYNAMIC APIs:
// calling either makes the route dynamic.

import { cookies, headers } from 'next/headers';

export default async function Page() {
  const cookieStore = await cookies();
  const session = cookieStore.get('session')?.value;
  const theme = cookieStore.get('theme')?.value ?? 'light';

  const headersList = await headers();
  const ua = headersList.get('user-agent');
  const lang = headersList.get('accept-language')?.slice(0, 2);

  return <Dashboard theme={theme} lang={lang} ua={ua} />;
}

// in a Server Action the cookieStore is also writable
'use server';
export async function setTheme(theme: string) {
  (await cookies()).set('theme', theme, { httpOnly: true, sameSite: 'lax' });
}

// in MIDDLEWARE, they are not async (it is not a component)
import { NextRequest } from 'next/server';
export function middleware(req: NextRequest) {
  const token = req.cookies.get('session');
}

// in a ROUTE HANDLER, the NextRequest carries them
export async function GET(req: NextRequest) {
  const session = req.cookies.get('session');
  return Response.json({ ok: !!session });
}

Reading a cookie to vary content means the page cannot be cached for everyone. For "one small personalised corner of a large page", the fix is usually: read the cookie inside a small child component wrapped in Suspense, so only that child is dynamic. Reading it in the page's top level makes the whole page dynamic, which is a heavy price for one value.

The render cache and a nonce

Next.js keeps a per-request cache so that if a layout and a page both fetch the same thing, it happens once. Understanding it explains some otherwise-baffling behaviour.

// the render cache: a Map that lives for the duration of one request
// and is shared by everything rendered in it.

export default async function Layout({ children }) {
  const user = await getUser();     // hits the DB
  return <Shell user={user}>{children}</Shell>;
}

export default async function Page() {
  const user = await getUser();     // SAME request, so the cache returns
  // the first result. one DB query, not two.
  return <Profile user={user} />;
}

// IMPORTANT: a client component in between BREAKS the render cache,
// because the client component does not execute on the server, so the
// value has to be serialised and passed across the boundary.
export default async function Page() {
  const user = await getUser();
  return <ClientProfile user={user} />;   // serialised now
}

// if the cache is disabled, or you cross a client boundary, or you use
// a non-cached fetch, you get N queries instead of 1. The fix is
// React.cache(), which deduplicates across the whole request even
// across client boundaries.

// a nonce is how a Server Component claims it was rendered on the server
// when the output is not HTML
const nonce = (await headers()).get('x-nonce');
// rendered into the RSC payload. If you ever find yourself checking
// this in a client component, you are working around a design problem,
// not solving one.

Seeing what happened

// 1. next build prints the route table with ○ ● ƒ ◐ per route.
//    read it every build. it is the fastest way to know whether your
//    change to a fetch or a cookie read silently made a static page
//    dynamic.

// 2. DevTools, the Next.js tab
//    shows which parts of the tree are server and which are client,
//    and highlights the client boundary visually.

// 3. console.log runs once, on the server
//    in a Server Component it prints in the terminal. If it prints
//    twice, you are in a cached route being revalidated, or in dev's
//    double render.

// 4. A deliberate marker
//    put a unique token in the markup and look for it in the HTML
//    response vs the JS bundles. If it is in the HTML but not in the
//    JS, that component is server-only and will not re-render client
//    side. This is the fastest way to verify your mental model.

Try this on any page: view source, then search the HTML for a string that only appears in a Server Component's output. Then look at the JS bundle for the same string. Its absence from the bundle is the proof that it rendered on the server. Ten minutes with this habit resolves most "is this running on the server?" confusion permanently.

4 · Data Fetching and Mutations

Where to fetchParallel and dependent fetchesFetching with SuspenseCascades and how to flatten themMutations and the client cacheRevalidating after a mutationError handling per fetchA complete data flow

Fetching in the App Router is easier than it was in the Pages Router, mostly because there is one obvious place to do it. This chapter is about doing it well: in parallel, without waterfalls, with errors that are contained, and with a cache you can reason about.

Where to fetch

// DEFAULT AND USUALLY CORRECT: in the Server Component, at the top level,
// not in an effect, not in a client hook.

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await db.product.findUnique({ where: { id } });
  return <ProductView product={product} />;
}

// WHY this is better than the alternatives
//   - it runs before anything is sent, so the HTML is complete
//   - there is no loading state to manage: either the component renders
//     with data, or it throws
//   - no waterfall: the component does not mount before fetching
//   - no cache library required
//   - the data is not in the client bundle

// the rule: fetch in a Server Component. Put the fetch in a client
// effect only when the request genuinely depends on user interaction
// that happens after hydration.

// WHERE NOT TO FETCH
//   - in useEffect        (waterfall, loading state, double-fetch risk)
//   - in a layout          (blocks every page beneath it)
//   - in a Client Component (ships your data-access code to the browser)

Parallel and dependent fetches

// DEPENDENT: b needs a's result, so they must be sequential
const user = await getUser(session.userId);
const orders = await getOrders(user.id);        // must wait

// INDEPENDENT: three of these, so run them at once
const [a, b, c] = await Promise.all([
  getProducts(),
  getCategories(),
  getReviews(),
]);
// three sequential awaits = 300 + 200 + 150 = 650ms
// Promise.all        = max(300, 200, 150) = 300ms

// "waterfall" means dependent requests stacked on top of each other. The
// most common cause in Next.js is a parent awaiting before a child starts.
//
// BAD: layout awaits, so every page under it waits
// app/dashboard/layout.tsx
export default async function Layout({ children }) {
  const user = await getUser();          // 400ms, always
  return <Shell user={user}>{children}</Shell>;
}
// app/dashboard/page.tsx
export default async function Page() {
  const stats = await getStats();        // 300ms, starts AFTER the layout
  return <Stats stats={stats} />;      // total 700ms
}

// GOOD: the layout does not fetch, the page fetches in parallel, and the
// parts that need the user sit behind their own Suspense boundary
// app/dashboard/layout.tsx - server, no await
export default function Layout({ children }) {
  return <Shell>{children}</Shell>;
}

// app/dashboard/page.tsx
export default async function Page() {
  const stats = await getStats();        // starts immediately
  return (
    <>
      <Suspense fallback={<NavSkeleton />}>
        <UserNav />                   {/* awaits the user itself */}
      </Suspense>
      <Stats stats={stats} />
    </>
  );
}
// shell + stats stream together; the nav fills in when the user arrives

The practical rule: fetch as close to where the data is used as possible. A layout that fetches forces every page beneath it to wait for data most of them do not need. It is the most common cause of a slow dashboard.

Fetching with Suspense

// make a data-fetching component itself async, and let Suspense handle it
// the parent does NOT await it

// app/products/page.tsx
export default function Page() {
  return (
    <div>
      <h1>Products</h1>
      <Suspense fallback={<GridSkeleton />}>
        <ProductGrid />                {/* async, fetches its own data */}
      </Suspense>
    </div>
  );
}

async function ProductGrid() {
  const products = await db.product.findMany();
  return <Grid products={products} />;
}

// the page function must NOT be async here, or it awaits everything
// and the streaming benefit is lost. This is the pattern to remember:

//   async parent  -> awaits everything, one slow thing blocks all
//   sync parent + async children behind Suspense -> streams

// the fetches run in PARALLEL even though they are sequential in the file
// because each component starts independently
export default function Dashboard() {
  return (
    <>
      <Suspense fallback={<A />}><WidgetA /></Suspense>   {/* 200ms */}
      <Suspense fallback={<B />}><WidgetB /></Suspense>   {/* 900ms */}
      <Suspense fallback={<C />}><WidgetC /></Suspense>   {/* 100ms */}
    </>
  );
}
// A and C are visible almost immediately, B arrives last. No waterfall,
// no whole-page spinner.

Cascades and how to flatten them

A cascade is a request that cannot start until an earlier one finishes. It is the root cause of most slow pages.

// THE CASCADE, UNFLATTENED
// app/orders/[id]/page.tsx
const order = await getOrder(id);          // 100ms
const customer = await getCustomer(order.customerId);   // 120ms, after
const items = await getItems(order.id);                // 80ms, after
const productDetails = await Promise.all(
  items.map((i) => getProduct(i.productId)),         // 150ms, after
);
const reviews = await getReviews(productDetails.map((p) => p.id)); // 200ms, after
// total: 650ms, strictly sequential

// FLATTENED
// step 1: what is known at the start? just the id
const order = await getOrder(id);          // 100ms, unavoidable

// step 2: everything now computable runs together
const [customer, items] = await Promise.all([
  getCustomer(order.customerId),
  getItems(order.id),
]);                                        // max(120, 80) = 120ms

// step 3: and the next layer together
const products = await db.product.findMany({
  where: { id: { in: items.map((i) => i.productId) } },
});                                        // ONE query, not N
const reviews = products.length
  ? await getReviews(products.map((p) => p.id))
  : [];
// total: ~370ms, and one round trip instead of N

// THE BIGGEST WIN: batch the N+1
// BAD: 50 products, 50 queries
for (const p of products) p.category = await getCategory(p.categoryId);

// GOOD: one query
const categories = await db.category.findMany({
  where: { id: { in: [...new Set(products.map((p) => p.categoryId))] } },
});
const byId = new Map(categories.map((c) => [c.id, c]));
products.forEach((p) => { p.category = byId.get(p.categoryId); });

// or use a data loader, which batches across an entire render
const getUser = dataLoader(async (id) => {
  return db.user.findUnique({ where: { id } });
});
// 10 components ask for users 1, 2, 3... Next.js issues ONE query with
// an IN clause, and caches it for the request

When profiling, look at the shape of the waterfall in the Network panel, not just the slowest request. Ten requests that each take 50 ms but run in sequence cost 500 ms; one request that takes 120 ms costs 120 ms. The waterfall, not the latency, is usually the problem.

Mutations and the client cache

Reads in the App Router are server-side and cached. That means a mutation must tell the server cache what changed, or the user will see stale data on their next navigation.

// the core tension
//   reads:  happen on the server, and the RESULT is cached
//   writes: happen via a server action, on the server
//   the client router has its OWN cache of the last-visited pages

// so after a write you must invalidate, or the user navigates back to
// the old data. Three mechanisms exist:

// 1. revalidatePath - drop a route from the server cache
// 2. revalidateTag  - drop anything fetched under a tag (ch7)
// 3. router.refresh() - re-fetch the current route's RSC payload

// 'use server'
import { revalidatePath, revalidateTag } from 'next/cache';

export async function updateProduct(id: string, form: FormData) {
  await requireUser();                        // ALWAYS authorise
  const data = validate(form);                // ALWAYS validate
  await db.product.update({ where: { id }, data });

  revalidateTag('products');                  // the list
  revalidatePath(`/products/${id}`);           // the detail page
  // both. the list and the detail are different cache entries.
}

// 3. client-side, when you want a transition
'use client';
const router = useRouter();
const [pending, startTransition] = useTransition();

function onSaved() {
  startTransition(() => {
    router.refresh();       // re-fetch this route's payload, show it
                          // without a loading state
  });
}

Every server action needs both an authorisation check and a validation step, and they are not optional. A server action is a public HTTP endpoint. Anyone can call it with any argument, including an id belonging to another user. Treat every action as untrusted input: check who is calling, check what they are allowed to touch, and validate every field.

Revalidating after a mutation

// choosing the right invalidation

// revalidateTag - precise, survives as long as the data is fetched with
// the tag
export async function createPost(form: FormData) {
  const post = await db.post.create({ data: parse(form) });
  revalidateTag('posts');                 // matches fetch(url, { next: { tags: ['posts'] } })
  revalidateTag(`post:${post.id}`);
  return post;
}

// revalidatePath - path-based, simpler, coarser
revalidatePath('/blog');                 // the list
revalidatePath(`/blog/${slug}`);          // one post

// router.refresh() - client-side, re-fetches the current route only,
// and does not touch the server cache. Good for a form that updates
// what is on screen right now.

// router.push(href) - for a redirect after a create. Navigating to the
// new page fetches it fresh (or from cache, if still valid).

// the ordering that avoids a flash of stale data
'use client';
async function onSubmit(form: FormData) {
  const action = useActionState(updateProfile, null);
  // ...
  // the component receives the new value as props after revalidation,
  // so there is no window where the old data is shown
}

// what NOT to do
// 'use client'; useEffect(() => { fetch('/api/products').then(setProducts) }, [])
// this bypasses the server cache entirely, gives you no streaming, and
// duplicates the data-fetching logic the framework already does

Error handling per fetch

// three layers, and you want all three

// 1. a thrown error is caught by the nearest error.tsx (ch16)
//    this is the default and it is correct
async function Widget() {
  const data = await getData();   // throws on failure
  return <Chart data={data} />;
}

// 2. error.tsx catches it for the segment. Note it must be a client
//    component, because it needs useEffect for the reset button
'use client';
export default function Error({ error, reset }: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong</h2>
      <p>{error.message}</p>
      <button onClick={reset}>Try again</button>
    </div>
  );
}

// 3. graceful degradation, when one failure should not blank the page
async function Widget() {
  const data = await getData().catch(() => null);
  if (data === null) return <WidgetUnavailable />;
  return <Chart data={data} />;
}

// the two rules
//   - a failed fetch inside a Suspense boundary triggers the boundary's
//     error handler, NOT the whole page
//   - never catch an error and show nothing. an empty region with no
//     explanation is worse than an error message

Next.js redacts server error messages in production before sending them to the client, and shows a digest instead. That is deliberate: stack traces and database errors leak schema and file paths. Use the digest in logs to find the real error.

A complete data flow

// the full pattern: server component reads, form posts to a server action,
// validation and authorisation on the server, cache invalidated, UI
// updates without a manual refetch.

// app/products/[id]/edit/page.tsx - server
import { requireUser } from '@/lib/auth';
import { canEdit } from '@/lib/permissions';
import { updateProduct } from './actions';
import { notFound } from 'next/navigation';

export default async function EditPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const user = await requireUser();                  // redirects if not signed in
  const product = await db.product.findUnique({ where: { id } });
  if (!product) notFound();
  if (!canEdit(user, product)) notFound();           // do not leak existence

  return (
    <ProductForm
      product={product}                              {/* plain, serialisable */}
      action={updateProduct}                         {/* a server action */}
    />
  );
}

// app/products/[id]/edit/actions.ts
'use server';
import { revalidatePath, revalidateTag } from 'next/cache';
import { z } from 'zod';

const Schema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1).max(200),
  price: z.coerce.number().positive(),
});

export type State = { errors?: Record<string, string[]>; message?: string } | null;

export async function updateProduct(
  _prev: State,
  form: FormData,
): Promise<State> {
  const session = await requireUser();

  const parsed = Schema.safeParse(Object.fromEntries(form));
  if (!parsed.success) {
    return { errors: parsed.error.flatten().fieldErrors };
  }

  const { id, ...fields } = parsed.data;
  const existing = await db.product.findUnique({ where: { id } });
  if (!existing || !canEdit(session.user, existing)) {
    return { message: 'Not found' };
  }

  await db.product.update({ where: { id }, data: fields });

  revalidateTag('products');
  revalidatePath(`/products/${id}`);
  revalidatePath('/products');
  return null;                                       // success: no error state
}

// app/products/[id]/edit/ProductForm.tsx - client
'use client';
import { useActionState } from 'react';

export function ProductForm({ product, action }: {
  product: Product;
  action: (prev: State, form: FormData) => Promise<State>;
}) {
  const [state, formAction, pending] = useActionState(action, null);

  return (
    <form action={formAction}>
      <input name="id" type="hidden" value={product.id} />

      <label>
        Name
        <input name="name" defaultValue={product.name}
          aria-invalid={!!state?.errors?.name} />
        {state?.errors?.name?.map((e) => <span key={e} role="alert">{e}</span>)}
      </label>

      <label>
        Price
        <input name="price" type="number" step="0.01" defaultValue={product.price} />
        {state?.errors?.price?.map((e) => <span key={e} role="alert">{e}</span>)}
      </label>

      {state?.message && <p role="alert">{state.message}</p>}

      <button disabled={pending}>{pending ? 'Saving...' : 'Save'}</button>
    </form>
  );
}

Note what is not in there: no useEffect, no useState for the field values, no fetch, no loading boolean, no refetch after submit. The form is progressive — it works without JavaScript, because a plain <form action> posts to the server and the server re-renders.

5 · The File System Router

The App Router derives your URL structure from the folder tree. Almost every routing question — nesting, layouts, parallel routes, modals — is answered by knowing the file conventions.

File conventions

// these filenames have meaning. Nothing else in app/ is special.
app/
  layout.tsx        wraps its segment and all children; ONE root, renders html+body
  page.tsx          makes the segment a route
  loading.tsx       Suspense fallback for this segment, automatic
  error.tsx         error boundary for this segment; MUST be 'use client'
  global-error.tsx  catches root layout errors; replaces the root layout
  not-found.tsx     404 UI, used by notFound()
  template.tsx      like layout.tsx but REMOUNTS on navigation
  route.ts          an HTTP endpoint, no UI
  default.tsx       fallback for parallel routes
  redirect.ts       a redirect, server-side
  middleware.ts     runs before routing

// the four you will use daily
layout.tsx  page.tsx  loading.tsx  error.tsx

One rule about nesting worth internalising: layout.tsx does not re-render on navigation. It renders once and persists. That is why a layout must not hold per-page state, and why state in a layout survives navigation — a feature for a cart, a bug for a form.

// [id] matches one segment
// app/blog/[slug]/page.tsx   ->  /blog/anything-here

Catch-all and optional segments

<
// [slug]      one segment       /blog/a
// [...slug]   one or more        /blog/a/b/c
// [[...slug]] zero or more       /blog  and  /blog/a/b

// app/docs/[...path]/page.tsx
export default async function Page({ params }: { params: Promise<{ path: string[] }> }) {
  const { path } = await params;
  // /docs            -> not matched
  // /docs/getting-started       -> path = ['getting-started']
  // /docs/guides/routing/layouts -> path = ['guides','routing','layouts']
  return <Doc path={path.join('/')} />;
}

// app/shop/[[...filters]]/page.tsx
// /shop                     -> filters = undefined
// /shop/colour/red/size/l   -> filters = ['colour','red','size','l']

// the practical use: a docs site where content lives in the filesystem
// or a CMS that maps a path to a document
const doc = await fs.readFile(`content/docs/${path.join('/')}.mdx`, 'utf8');

// SECURITY: never interpolate a path segment into a file path without
// validating it. path.join('../..') escapes the directory.
if (path.some((seg) => seg === '..' || seg.includes('/'))) notFound();
const file = path.join(DOCS_ROOT, ...path);
if (!file.startsWith(DOCS_ROOT)) notFound();   // belt and braces

Path traversal in a dynamic route is a real vulnerability, not a theoretical one. A segment of ..%2F..%2Fetc%2Fpasswd or a decoded .. in the array can escape the intended directory. Always resolve and then assert the result is still inside the root.

Parallel routes and slots

Parallel routes let one URL render several independent segments at once, and give you named slots to place them.

// the motivating case: a dashboard with a persistent sidebar that does not
// re-render on navigation, plus a content area that does.

app/dashboard/
  layout.tsx                 the shell: sidebar + {children} + {modal}
  @sidebar/
    layout.tsx               persists across navigation
    default.tsx              shown when no match
    (withNav)/page.tsx       /dashboard       -> with the nav
    (withoutNav)/page.tsx    /dashboard/full  -> without it
  @modal/
    default.tsx              nothing by default
    login/page.tsx           /dashboard/login -> modal
    photo/[id]/page.tsx      /dashboard/photo/1 -> modal
  page.tsx                   /dashboard

// a real modal: the page underneath keeps its state, the modal overlays it
// app/layout.tsx
export default function RootLayout({ children, modal }: {
  children: React.ReactNode;
  modal: React.ReactNode;        // the @modal slot
}) {
  return (
    <html>
      <body>
        {children}
        {modal}                    {/* renders on top, same URL */}
      </body>
    </html>
  );
}

// navigating to /dashboard/photo/1 does NOT change the URL you see, does
// NOT unmount the dashboard behind it, and the dashboard's state survives

// on hard refresh of /dashboard/photo/1, only the @modal slot matches, so
// the @sidebar default.tsx is used. this is why default.tsx exists in
// every parallel slot: without it, a hard refresh 404s or errors

default.tsx is the file everyone forgets. A parallel slot needs one for the cases where only some slots match a URL — a hard refresh, a direct link, a back navigation. Without it Next.js renders a 404 that makes no sense from the user's point of view.

Intercepting routes

// (...)folder means "this segment, but only in this situation".
// The classic use: a photo URL that shows a MODAL when navigated to
// client-side, and a full page when loaded directly.

// app/feed/page.tsx                    the feed
// app/feed/[id]/page.tsx               the photo, full page
// app/@modal/(.)feed/[id]/page.tsx     the SAME photo, as a modal
//   the (.) matches one segment level: app/@modal/feed/[id]

// /photos/1 typed or pasted  -> app/photos/[id]/page.tsx, full page
// clicking a link in the feed -> app/@modal/(.)photos/[id]/page.tsx
// the modal, the feed stays mounted behind it
// pressing Escape or backdrop  -> router.back(), the feed is still there

// matcher reference
//   (.)   same level
//   (..)  one level above
//   (..)(..) two levels above
//   (...) catch-all, from the app root

// the rule: interception only applies to CLIENT-SIDE navigation. A hard
// refresh always resolves to the real route. This is the behaviour you
// want — a shared link should not open a modal over nothing.
// the full modal example
// app/photos/[id]/page.tsx - server, the standalone page
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  return <PhotoPage id={id} />;      // full page, chrome included
}

// app/@modal/(.)photos/[id]/page.tsx - server, the intercepted version
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  return (
    <div className="modal-backdrop" onClick={close}>
      <div className="modal" onClick={(e) => e.stopPropagation()}>
        <PhotoPage id={id} />
        <button onClick={close} aria-label="Close">×</button>
      </div>
    </div>
  );
  function close() { /* a client component or a form action */ }
}

'use client';
import { useRouter, usePathname, useSearchParams, useParams } from 'next/navigation';

function Examples() {
  const router = useRouter();
  const pathname = usePathname();          // '/dashboard'
  const search = useSearchParams();        // ?tab=stats
  const params = useParams();              // { id: '1' } from [id]

  router.push('/dashboard');               // adds a history entry
  router.replace('/dashboard');            // does not
  router.back();
  router.forward();
  router.refresh();                        // re-fetch the RSC payload
  router.prefetch('/products');            // warm the cache

  return (
    <>
      <p>{pathname}</p>
      <p>{search.get('tab')}</p>
    </>
  );
}

Link prefetching

// <Link> prefetches automatically when it enters the viewport. For
// static routes that is the full HTML; for dynamic routes it is the
// RSC payload up to the nearest loading.tsx boundary, split into a
// static shell and a dynamic part.

<Link href="/about">Static page</Link>        {/* prefetched fully */}

export const dynamic = 'force-dynamic';
// app/reports/page.tsx
<Link href="/reports">Dynamic page</Link>      {/* partially prefetched */}

// the "partial" bit is the loading.tsx shell. without it, Next.js
// prefetches nothing for a dynamic route, because it cannot know how
// much of the payload is reusable.

export const dynamic = 'force-dynamic';
// app/reports/loading.tsx
export default function Loading() {
  return <ReportSkeleton />;          // now this IS prefetched
}

// when to opt out
//   - a link inside a list of 1,000 items: 1,000 prefetches
//   - a link behind a paywall or to an admin area
//   - a link you never expect a user to follow
<Link href="/report" prefetch={false}>Generate report</Link>

// prefetching on demand instead
'use client';
const router = useRouter();
<button onMouseEnter={() => router.prefetch('/report')}>
  Generate report
</button>

If a navigation feels slow and the Network panel shows no request, the route's RSC payload was already prefetched and it is rendering on the client — the cost is then a client render, not a round trip. If you see a request, it was not prefetched. That distinction tells you which problem you have.

// middleware.ts - dynamic, runs on every matching request, and is where
// auth lives
import { NextResponse, type NextRequest } from 'next/server';

export function middleware(req: NextRequest) {
  const { pathname } = req.nextUrl;
  const token = req.cookies.get('session')?.value;

  if (!token && pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login?next=' + pathname, req.url));
  }
  if (token && pathname === '/login') {
    return NextResponse.redirect(new URL('/dashboard', req.url));
  }

  // a request header the server can read
  const headers = new Headers(req.headers);
  headers.set('x-pathname', pathname);
  return NextResponse.next({ request: { headers } });
}

export const config = {
  // exclude static assets and the API routes you do not want to guard.
  // matchers are an optimisation AND a correctness tool.
  matcher: ['/((?!_next/static|_next/image|favicon.ico|api/health).*)'],
};

// middleware runs on the EDGE runtime by default, so no Node APIs.
// it is not a place for database queries or slow crypto.

// order of operations
//   1. headers   (next.config)
//   2. redirects (next.config)
//   3. middleware
//   4. beforeFiles rewrites
//   5. filesystem routes (public/, _next/static, pages, app)
//   6. afterFiles rewrites
//   7. dynamic routes
//   8. fallback rewrites
//   9. 404

Middleware runs on every matched request including static assets, unless your matcher excludes them. A matcher that does not exclude _next/static can add latency to every page load in your app and, on some platforms, count against a request quota. Always exclude _next/static, _next/image and your own static files.
