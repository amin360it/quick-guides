0.1 Why Rust, and what it guarantees

Rust is a systems language that guarantees memory safety and thread safety at compile time, without a garbage collector, by enforcing ownership rules in the type system.

The three pillars

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

Ownership means every value has exactly one owner, and the value is dropped when that owner goes out of scope. Borrowing means you can pass a reference to a value without giving up ownership, but the reference cannot outlive the owner. Lifetimes are the compile-time proof that borrowing is safe.

What Rust cannot do for you

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

Rust will not stop you from leaking memory explicitly with std::mem::forget, and it will not stop logical errors: you can still return the wrong sum, or dead-lock a mutex. The guarantee is narrow and strong: no dangling pointers, no use-after-free, no data races, no buffer overflows.

fn sum(xs: &[i32]) -> i32 {

fn main() {
    let xs = vec![1, 2, 3];

}

0.2 The toolchain: cargo, rustc, and the edition system

Rust's toolchain is two programs and one file. cargo builds, tests, documents, publishes and resolves dependencies; rustc is the compiler underneath; and Cargo.toml is where the package's identity, its edition and its dependency versions live. Nearly every confusing thing about a Rust project traces back to a value in that file.

Six verbs, and what each guarantees

cargo new creates a project with a standard layout. cargo build compiles; adding --release turns on optimisation and is the difference between a development binary and a production one. cargo run builds and runs in one step. cargo test compiles and runs the unit tests, the integration tests and the documentation tests. cargo clippy is the linter. cargo fmt rewrites the source to one canonical form.

$ cargo new hello
$ cd hello
$ cargo build            # debug profile: fast to build, slow to run
$ cargo build --release  # optimised. THIS is what you deploy
$ cargo run
$ cargo test
$ cargo clippy
$ cargo fmt
$ cargo doc --open
$ cargo add serde        # adds a dependency and edits Cargo.toml
$ cargo tree             # the full dependency graph, transitive

Why the edition matters more than it looks

An edition is a set of language rules versioned separately from the compiler. A crate declaring edition = "2018" compiles with today's rustc under 2018 semantics, so it keeps working when the language changes underneath it. Omitting the field defaults to 2015, which disables every post-2015 feature in your code. Editions in order are 2015, 2018 (module system rework, async/await, dyn Trait), 2021 (closures capturing disjoint fields, prelude additions) and 2024.

# Cargo.toml
[package]
name    = "billing"
version = "1.4.0"
edition = "2021"     # NEVER omit this. The 2015 default disables
                     # async, dyn, the 2018 module paths, and more.

[dependencies]
serde      = { version = "1", features = ["derive"] }
tokio      = { version = "1", features = ["full"] }
anyhow     = "1"

[dev-dependencies]
criterion  = "0.5"   # only for tests, not in the shipped binary

[profile.release]
lto         = true   # link-time optimisation
codegen-units = 1
opt-level   = 3
panic       = "abort"  # smaller binary, no unwinding. NOT if you
                       # catch panics for a graceful shutdown

The profiles, and why a debug binary is not just slower

Cargo has four built-in profiles and they differ in more than speed. The debug profile enables debug_assertions and integer overflow checks, both of which are removed in release — so an arithmetic bug that panics in development silently wraps in production. It also generates no inlining and no optimisation, so debug timings are meaningless. This is the single most common way a Rust service passes its tests and fails in production, and the fix is a test suite that also runs against a release build.

fn main() {
    let x: u8 = 255;
    println!("{}", x + 1);   // debug: panics. overflow detected.
                             // release: prints 0. wraps silently.
}

// catch it in CI, not in production:
$ cargo test                                    # debug only
$ cargo test --release                          # the one that matters
$ cargo clippy -- -D warnings
$ cargo fmt -- --check                          # fails if unformatted

Cross-compilation and musl

Cross-compiling needs no toolchain packages, because rustc is the whole compiler. The target is selected by --target, and for Linux you will almost always want x86_64-unknown-linux-musl rather than the gnu target, because musl produces a statically linked binary with no glibc version dependency — which is what makes a single artifact portable across distributions and inside a minimal container.

$ rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl

$ cargo build --release --target x86_64-unknown-linux-musl
$ file target/x86_64-unknown-linux-musl/release/billing
# ELF 64-bit LSB pie executable, x86-64, statically linked

$ ls -lh target/*/release/billing
# one binary per target, no separate runtime, no shared libraries
# to install. Copy it to the host and run it.

What rustup manages, and what cargo does not

There are two tools and the division is easy to state. rustup manages toolchains: which compiler versions are installed, which is the default, and which targets are available for each. cargo manages one project: its dependencies, its profiles, its build script, and its output. A common confusion is looking for cargo subcommands that are actually rustup commands — installing a toolchain is rustup toolchain install nightly, not a cargo operation at all.

$ rustup show                       # active toolchain and targets
active toolchain
stable-x86_64-pc-windows-msvc (default)
stable-x86_64-unknown-linux-gnu
stable-x86_64-unknown-linux-musl

$ rustup toolchain install 1.78.0
$ cargo +1.78.0 build               # build with that specific toolchain
$ rustup component add clippy rustfmt
$ rustup default nightly             # a team should pin ONE version

Three disciplines: always set edition in Cargo.toml, because the 2015 default silently disables most of the language and produces error messages that assume you know things you have no way to know; run cargo test --release as well as the debug suite, because debug assertions and overflow checks are removed in release and the bug they catch is the one that reaches users; and build Linux binaries against musl, because a statically linked artifact is the difference between one file and a dependency on the host's glibc version.

1.1 Ownership: the three rules every Rust type obeys

Every value in Rust is owned by exactly one variable, and when that variable goes out of scope the value is dropped. Assignment moves ownership; no other language has this exact semantics.

What move means, and what clone means

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

Move is the default for heap types — String, Vec, Box, Rc. Clone is deep and explicit — s.clone() copies the buffer. Copy types are bitwise-copied — integers, bools, chars, tuples of Copy types. Then the four rules that follow, and each is a requirement. A function parameter of type String consumes the string, so the caller loses the value. Returning a value moves ownership back to the caller, so a function can hand back what it took. A struct's fields are moved independently, so you can move one field out of a struct and keep the others. And Destructuring a value moves all of its fields — which is why pattern matching on a String is destructive unless you borrow first. Then the three things that go wrong, and each is a mechanism. Using a value after passing it to a function, which is the move error. Forgetting that reborrowing a mutable reference splits it, so both the old and new reference cannot be used. And Cloning in a hot loop to satisfy the borrow checker, which allocates every iteration when a restructure would have cost nothing. Then the two practices, and both are disciplines. Design ownership so that lifetimes are scopes, not scopes with exceptions, because the compiler proves it from the braces. And Prefer reading the ownership docs over fighting the borrow checker, because it is always right about the mechanics if not always about the ergonomics.

/* OWNERSHIP IS TREE-STRUCTURED. One owner, and every value is a
   node in the tree that gets dropped when its owner drops.
   This is why Rust can deallocate memory automatically without
   a garbage collector: the drop order is deterministic from the
   scopes. */

fn ownership() {
    let s1 = String::from("hello");  // s1 owns the heap buffer
    let s2 = s1;                      // s1's ownership MOVES to s2
    // println!("{}", s1);           // ERROR: use of moved value
    println!("{}", s2);               // OK: s2 is the owner now
}

fn clone_needed() {
    let s1 = String::from("hello");
    let s2 = s1.clone();              // DEEP copy: allocates new
    println!("{} {}", s1, s2);        // both valid, both own theirs
}

/* Copy types: integers, bools, chars, fixed-size arrays of Copy,
   tuples of Copy types. Assigning them SHAlLOWS: both variables
   remain valid because both have their own copy. */

fn copy_types() {
    let x = 42;
    let y = x;                        // x is COPIED, not moved
    println!("{} {}", x, y);          // both valid
}

/* Which types are Copy? Ask the compiler:
   std::mem::needs_drop::<T>() tells you if Drop is needed.
   std::mem::size_of::<T>() tells you the stack size.
   A type without Drop and without interior pointers is Copy. */

fn works() {
    let s = String::from("hello");
    let len = calculate_length(&s);     // BORROW: pass a reference
    println!("{} has {} chars", s, len);  // s is still valid
}

fn calculate_length(s: &String) -> usize {
    s.len()                             // reads through the ref
}

/* A function taking &String does NOT consume the string.
   The reference is a borrow, the function promises not to
   keep it past the call, and the caller keeps ownership. */

/* THE THREE FAILURES, each invisible in C++ and caught in Rust.

   1. Use after move:
      let s = String::from("hi");
      let t = s;
      println!("{}", s);   // ERROR: use of moved value

   2. A reference that outlives its referent:
      let r;
      {
          let s = String::from("hi");
          r = &s;           // s dies here, r is dangling
      }
      println!("{}", r);   // ERROR: borrowed value does not live
                            // long enough

   3. Mutating while borrowing immutably:
      let mut v = vec![1, 2, 3];
      let first = &v[0];
      v.push(4);            // ERROR: cannot borrow as mutable
      println!("{}", first);

/* THE TWO DISCIPLINES.
   1. If the borrow checker says no, restructure. Do not reach
      for unsafe, Rc>, or a clone in a loop as the
      first response. Usually the right move is passing an index
      or a key rather than a reference, so the borrow is released
      before the mutation.
   2. Use &mut for mutating parameters and &T for read-only. The
      signature is the documentation: a &mut parameter promises
      the function will change the value, and the caller is
      prepared for that. */

1.2 Lifetimes: the annotation that proves a reference is valid

A lifetime is a name for the scope a reference is valid, and the compiler infers lifetimes in most cases — but when a function returns a reference derived from a parameter, the compiler needs an annotation to know which parameter's lifetime the result inherits.

When the compiler needs you to say it

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

Lifetime elision covers most cases, so a function taking one reference parameter and returning a reference has its lifetime inferred. But if a function takes two reference parameters, the compiler cannot know which one the result borrows from, so you must annotate it. Then the two rules that follow, and each is a requirement. The result of a function that returns a reference must be valid for at least as long as every input reference it borrows from, and the lifetime parameter links them. A struct holding a reference must carry the same lifetime. Then the three things that go wrong, and each is a mechanism. Omitting lifetimes on a struct with a reference field, which the compiler rejects. Using a shared reference after a mutable one exists, which is a compile error. And Returning a reference to a temporary, which is the most common lifetime error and the one the compiler explains well: "borrowed value does not live long enough". Then the two practices, and both are disciplines. Name the lifetime for what it is, — 'buffer, 'row, 'text — rather than 'a, 'b. And If you find yourself fighting to make the lifetimes work, the fix is usually to restructure so the reference is not returned — return an owned value, an index, or a key.

/* Lifetime elision rules, in order:
   1. Each reference parameter gets its own lifetime.
   2. If there is exactly one input lifetime, it is given to all
      output references.
   3. If there are multiple input lifetimes but one is &self or
      &mut self, the output gets self's lifetime.

   When none of these apply, the compiler requires an annotation.
   This happens when a function takes two reference parameters and
   returns a reference. */

// ELIDED: one input, one output — the compiler infers.
fn longest(x: &str) -> &str {
    x   // elided lifetime: &str with the same lifetime as x
}

// ANNOTATION REQUIRED: two inputs, the compiler cannot decide.
fn longest_annotated<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}   // The 'a means: the returned reference is valid for at most
   // as long as BOTH x and y are valid.

/* A struct holding a reference MUST declare the lifetime:
   struct ImportantExcerpt<'a> {
       part: &'a str,
   }
   The 'a is a promise: ImportantExcerpt does not outlive the
   string it borrows from.                                   */

/* The most common lifetime error: returning a reference to a
   temporary. */
fn bad() -> &String {
    let s = String::from("hello");
    &s                    // ERROR: borrowed value does not live
}                         // long enough — s drops here, &s dangles

/* The fix: return the owned value. The caller does not need a
   reference into your locals. */
fn good() -> String {
    String::from("hello")   // moved to caller, alive there
}
/* THE THREE FAILURES, restated.
   1. Struct holding a reference without a lifetime parameter:
      struct Bad { part: &str }   // ERROR: missing lifetime
   2. A shared borrow after a mutable borrow exists:
      let r1 = &mut x;
      let r2 = &x;                // ERROR: cannot borrow as immutable
   3. Returning a reference to a local:
      fn bad() -> &T { &T{} }      // ERROR

/* THE TWO DISCIPLINES.
   1. Name the lifetime for its role, not its position:
      fn parse<'input>(text: &'input str) -> &'input str { ... }
      fn first<'buffer>(b: &'buffer Buffer) -> &'buffer Row { ... }
   2. If the lifetimes are fighting you, restructure. The typical
      fixes, in order of how often they work:
      - return an owned value (clone)
      - return an index or key instead of a reference
      - take the reference as a parameter and write through it
      - split the function so the reference does not cross the
        function boundary                             */

2.1 Traits: shared behaviour without inheritance

A trait in Rust is a collection of methods that a type can implement, and it is the mechanism for polymorphism without a base class. A type can implement any number of traits, and a trait can require other traits.

What a trait is, and what dyn Trait is

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

A trait defines a set of methods that a type must provide, and a type can implement many traits. impl Trait for Type is explicit, — there is no implicit trait satisfaction like Go's interfaces. A generic function with a trait bound is monomorphized at compile time, — the compiler generates a specialised version for each type that satisfies the bound, which is why it has no runtime cost. dyn Trait is the dynamically-dispatched version, stored behind a pointer, and it exists when you need to hold several different implementations of the same trait in one collection. Then the three rules that follow, and each is a requirement. A trait object — Box<dyn Trait> — can only hold the methods of one trait, so a collection needs the trait, not the type. Implementing a trait for a type you do not own requires a wrapper, unless the trait is one you define — the orphan rule. And A where clause keeps complex bounds readable, and it is not optional once you have more than two bounds. Then the three things that go wrong, and each is a mechanism. Forgetting the dyn keyword and trying to store a trait in a Vec, which the compiler rejects. Not implementing Send or Sync on a type used across threads, which the compiler rejects when you spawn a thread. And Using a where clause with Self in the bound, which the compiler sometimes cannot resolve and which usually means the bound should be on the function's generics rather than the trait. Then the two practices, and both are disciplines. Define traits in the module that owns the behaviour, not in the module that implements it, so the dependency arrow points from the implementer to the trait. And Use dyn Trait only when the set of types is genuinely open, and generics when it is not.

/* A TRAIT is like a Go interface but explicit: a type says it
   implements a trait, and the compiler checks. */

trait Draw {
    fn draw(&self);
    fn bounding_box(&self) -> (f64, f64, f64, f64) {
        // default method: implementors may override
        (0.0, 0.0, 100.0, 100.0)
    }
}

struct Circle { x: f64, y: f64, r: f64 }

impl Draw for Circle {
    fn draw(&self) {
        println!("Drawing a circle at ({}, {}) with radius {}", self.x, self.y, self.r);
    }
}

/* GENERIC with a trait bound: monomorphized per type. */
fn render&lt;T: Draw&gt;(item: &T) {
    item.draw();
}

/* DYNAMIC with dyn Trait: stored behind a pointer. */
fn render_dyn(item: &dyn Draw) {
    item.draw();
}

/* Why monomorphization matters:
   render(&circle)  →  the compiler generates fn render_Circle() with
                      Circle's draw() inlined. No virtual table, no
                      indirection. The cost is code size: N types
                      → N specialised copies of the function.  */

/* The orphan rule: you can implement YOUR trait for THEIR type, or
   THEIR trait for YOUR type, but NOT their trait for their type.
   fn impl Display for Vec&lt;i32&gt;  →  ERROR: Display and Vec are
   both foreign. The workaround is a newtype: */
struct MyVec(Vec&lt;i32&gt;);
impl std::fmt::Display for MyVec {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "{:?}", self.0)
    }
}
/* THE THREE FAILURES.
   1. Vec&lt;Box&lt;dyn Draw&gt;&gt; without Box: the compiler says "the size
      of dyn Draw cannot be known at compile time", and a Box is
      the usual fix.
   2. Spawning a thread with a non-Send closure:
      std::thread::spawn(|| { let rc = Rc::new(5); });
      // ERROR: Rc&lt;i32&gt; is not Send.
      Use Arc&lt;Mutex&lt;T&gt;&gt; instead.
   3. A trait bound with Self where the compiler cannot infer it.

/* THE TWO DISCIPLINES.
   1. Define the trait where the BEHAVIOUR lives, not where the
      TYPE lives. Otherwise the dependency arrow goes backwards.
   2. Use generics with trait bounds for closed sets of types,
      dyn Trait for open sets. A generic version is always faster
      because it is monomorphized. */

2.2 Async: the future, the executor, and the await point

Async Rust uses the async keyword to mark functions that return futures, an executor to poll those futures, and the await keyword to yield control at points where the result is not ready.

The three pieces

Every shortcoming in this area comes from one of two places: the tool being used makes a promise it does not keep, or the surrounding process is not checking that promise at the boundary. Both are the same mistake in different clothes — treating a silent tool as an honest one. Fix the silence first, and the debugging gets much quieter.

async fn returns a Future, and the future does nothing until it is awaited. An executor polls futures, — tokio is the most common one — and spawns tasks that map onto OS threads. await is the yield point, where the task gives up its thread and the executor runs another ready task. Then the three rules that follow, and each is a requirement. Hold no non-Send data across an await, because the task may move to a different thread. Use tokio::spawn for concurrent work and tokio::join! for waiting on both, because a sequential await is a blocking await. Never call a blocking function inside an async block, because it blocks the executor thread for every other task on that thread. Then the three things that go wrong, and each is a mechanism. A lock guard held across an await, which is not Send and which the compiler rejects. Calling std::thread::sleep inside an async function, which blocks the executor. And Not awaiting a future, which means it never runs. Then the one discipline. The executor is what makes async real, and without one the futures are a pile of state machines that never get polled. Tokio is the standard choice, and its runtime must be initialised with #[tokio::main].

/* async fn returns an impl Future. The function body does NOT
   execute until awaited. */

async fn fetch_data(url: &str) -> Result&lt;String, std::io::Error&gt; {
    let resp = reqwest::get(url).await?;
    resp.text().await
}

/* The compiler transforms this into a state machine:
   - initial state: not started
   - after first await: waiting on reqwest::get
   - after second await: waiting on resp.text
   - final: done, returns Result
  
   Each state is a struct. The enum of states becomes the Future.
   This is WHY Rust async has no runtime cost when not awaited:
   polling an unpolled future is just a match on the state. */

/* The three pieces:
   1. async fn     → returns Future
   2. executor     → polls Future (tokio)
   3. await        → yield point
   
   #[tokio::main] initialises the runtime. */

#[tokio::main]
async fn main() {
    let data = fetch_data("https://example.com").await;
    match data {
        Ok(text) => println!("{}", text),
        Err(e) => eprintln!("Error: {}", e),
    }
}

/* The three rules.
   1. HOLD NO NON-SEND ACROSS await. This is not a suggestion:
      the compiler rejects it. A MutexGuard is the classic case.
   2. tokio::spawn for concurrent, tokio::join! for both. */
use tokio;
async fn concurrent() {
    let fut1 = fetch_data("url1");
    let fut2 = fetch_data("url2");

    // BAD: sequential — awaits one, then the other
    let r1 = fut1.await;
    let r2 = fut2.await;

    // GOOD: concurrent — both run, await waits for both
    let (r1, r2) = tokio::join!(fut1, fut2);
}
/* 3. NEVER BLOCK INSIDE ASYNC. std::thread::sleep blocks the
   executor thread, freezing every other task on that thread.
   Use tokio::time::sleep instead: it yields the executor on
   await. */
/* THE THREE FAILURES.
   1. MutexGuard held across await:
      let mut guard = mutex.lock().unwrap();
      some_async_fn().await;     // ERROR: guard is not Send
      drop(guard);
   Fix: drop the guard BEFORE the await, or use tokio::sync::Mutex.

   2. Blocking inside async:
      async fn bad() {
          std::thread::sleep(Duration::from_secs(1));  // blocks
      }
   Use tokio::time::sleep(Duration::from_secs(1)).await.

   3. Not awaiting a future:
      fetch_data("url");      // future never polled, never runs
   The compiler does not warn because futures are just values.
   Use let _ = or await it.

/* THE DISCIPLINE.
   An executor makes async real. Tokio is the convention. The
   runtime initialises with #[tokio::main], spawns tasks with
   tokio::spawn, and its reactor maps I/O events to futures via
   epoll (Linux), kqueue (macOS), IOCP (Windows). */
