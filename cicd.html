1 · Why CI/CD Exists

1.1 The problem with manual releases1.2 CI vs CD vs CD1.3 What good CI/CD buys you

Explains the problems that continuous integration and continuous delivery solve: late integration bugs, manual release steps, and deployments that depend on one person knowing the drill. CI merges and verifies changes often, while CD ships small verified increments. The chapter frames these pains so the automation patterns later in the guide have a clear reason to exist.

Integration used to happen once every few weeks, in a painful "merge week". CI/CD replaces big risky releases with small, verified, frequent ones.

1.1 The problem with manual releases

Describes the failure modes of hand-run releases: undocumented steps, environment drift, conflicting changes, and a single person who holds the expertise. Because the procedure lives in someone’s head, rebuilds and rollbacks are slow and inconsistent. Automation exists to turn this personal ritual into a repeatable, recorded process, which justifies everything the rest of the guide covers.

  • Long-lived branches drift and conflict painfully.
  • Manual steps are undocumented and non-repeatable.
  • Bugs are found late, when they are most expensive.
  • Only one person knows how to deploy — a bus-factor of one.

1.2 CI vs CD vs CD

Distinguishes continuous integration, continuous delivery and continuous deployment by how far automation reaches. Continuous integration merges and tests every change, continuous delivery leaves a human gate before production, and continuous deployment releases automatically when the pipeline passes. The comparison helps you decide where your own automation should stop and where humans should stay in charge.

TermMeaning
Continuous IntegrationEvery change is merged to trunk and automatically built + tested.
Continuous DeliveryEvery passing build is deployable to production; release is a business decision.
Continuous DeploymentEvery passing build goes to production automatically, no human gate.

1.3 What good CI/CD buys you

Summarizes the payoff of good CI/CD: a smaller blast radius, faster feedback and releases that repeat exactly the same way every time. Teams gain the confidence to ship frequently because a red pipeline catches problems early while they are cheap to fix. Frequent small releases reduce risk, and that confidence is the real currency the practice buys.

  • Smaller changes → smaller blast radius → easier rollback.
  • Fast feedback: catch defects minutes after writing them.
  • Repeatable, auditable releases.
  • Developer confidence to refactor and improve.

  1. List every manual step in your current release and mark which could be automated.
  2. Decide where you sit between Delivery and Deployment, and why.

2 · Version Control Workflows

2.1 Branching strategies2.2 Pull requests and protected branches2.3 Commit hygiene and conventions

Covers how your branching model shapes integration pain, including strategies such as trunk-based development, GitHub Flow and GitFlow, plus pull requests and commit conventions. It explains how protected branches, code review and Conventional Commits rules combine with CI to keep the main branch green. This workflow is the foundation every later pipeline job assumes.

2.1 Branching strategies

Compares trunk-based development, GitHub Flow and GitFlow in terms of integration effort versus release control. Trunk-based keeps branches short and merges frequent, which suits continuous delivery, while GitFlow adds release and hotfix branches for scheduled releases. The trade-off decides how painful each integration feels, and teams shipping continuously tend to favor short-lived branches.

StrategyShapeFits
Trunk-basedShort-lived branches merged to main dailyHigh-performing CI/CD teams
GitHub FlowFeature branch → PR → mainMost web teams
GitFlowdevelop/release/hotfix branchesVersioned/enterprise releases

The more branches that live long, the more integration pain you manufacture. Prefer short branches and feature flags over long-lived branches.

2.2 Pull requests and protected branches

Explains how protected branches enforce reviews and a green CI run before anything lands. Branch protection rules in repository settings require pull requests, at least one approving review, and passing status checks, so main cannot be pushed directly. The pull request becomes the front door of a disciplined pipeline where every change is examined and verified before merging.

# Protect main:
#  - require a PR before merging
#  - require status checks (CI) to pass
#  - require at least one review
#  - require branch up to date before merge
#  - disallow force-push and deletion

A checklist of branch-protection rules that force every change through a reviewed, green-CI pull request to main.

2.3 Commit hygiene and conventions

Introduces Conventional Commits, where message prefixes such as fix, feat and BREAKING CHANGE drive generated changelogs and automatic versioning. Tools like commitlint enforce the format and semantic-release parses messages to decide the next SemVer version. Consistent messages make history readable and automatable instead of a tangle of free-text summaries.

feat(auth): add refresh-token rotation
fix(cart): prevent negative quantities
chore(deps): bump framework to 13.1

# Conventional Commits enable automated changelogs + semantic versioning.

Conventional Commits format messages as type(scope): description, which unlocks automated changelogs and semantic versioning.

3 · Build Automation & Artifacts

3.1 What "build" means3.2 Build once, deploy many3.3 Multi-stage Docker builds3.4 Reproducible builds

Explains that building turns source into a versioned, immutable artifact you can promote through every environment. The chapter covers compilation, bundling, packaging and containerisation, and argues for building once and reusing the result instead of rebuilding per environment. Artifacts are tagged with versions and commit SHAs so every deployment stays traceable to its source.

3.1 What "build" means

Defines build as compiling, bundling, packaging or containerising source into a single deployable unit. The output, called the artifact, is the thing you test, promote and deploy everywhere. Naming each build stage and recording its inputs makes results reproducible and traceable back to the exact commit that produced them.

Building transforms source into a runnable/deployable unit: compile, bundle, package, containerise. The output is an artifact — a versioned, immutable file you can promote through environments.

3.2 Build once, deploy many

Argues that rebuilding the same source per environment causes drift and works-in-staging surprises. Instead, the pipeline builds one immutable artifact once, then varies only injected configuration for each target. Promote that same artifact through test, staging and production so the bits you tested are exactly the bits that reach users.

# Anti-pattern: rebuild per environment (drift, "works in staging")
# Pattern: build once -> promote the identical artifact
build  -> image:v42  (tested)
promote-> staging     (image:v42)
promote-> production  (image:v42)

# Environment differences come from CONFIG, never from recompiling.

Promote the exact same tested image through staging into production; only config differs at deploy time, never the build.

3.3 Multi-stage Docker builds

Shows how a Dockerfile with multiple FROM stages separates the build toolchain from the runtime image. Early stages compile or bundle with full toolchains, and later stages copy only the output into a slim final image. The result is small, reproducible images that never ship compilers or build dependencies, with BuildKit providing layer and dependency caching.

FROM node:22 AS build  # compile stage
WORKDIR /app
COPY package*.json ./
RUN npm ci  # install from lockfile
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html  # keep final image small
# tiny, reproducible final image with no build tooling inside

A two-stage Dockerfile keeps the npm toolchain out of the final nginx image, shrinking it and leaving no build secrets behind.

3.4 Reproducible builds

Explains pinning package lockfiles and image digests so the same source always yields the same artifact. Dependency resolution is fixed to exact versions rather than ranges, and base images are referenced by SHA instead of mutable tags. Reproducibility is what makes rollbacks trustworthy, because you can rebuild exactly the thing that once worked in production.

  • Pin dependency versions (lockfiles committed).
  • Pin base images by digest, not floating tags.
  • Same inputs → same artifact; cache safely and hermetically.

4 · Testing in the Pipeline

4.1 The test pyramid4.2 Quality gates4.3 Flaky tests are the enemy4.4 Parallelism and caching

Lays out the testing strategy CI uses as its eyes: many fast unit tests, a smaller set of focused integration tests, and a few end-to-end checks. The chapter explains how to place each test type at the right pipeline stage and keep CI fast and honest. Tests run on every push so failures surface in minutes instead of at deploy time.

4.1 The test pyramid

Presents the classic test pyramid: many fast unit tests at the base, some integration tests in the middle, and few slow end-to-end tests at the top. Inverting that shape makes feedback slow and brittle, so the guide recommends writing mostly small isolated tests. Following the pyramid keeps pipeline minutes low while coverage stays meaningful.

LayerSpeedConfidenceCount
UnitMillisecondsLogicMany
IntegrationSecondsComponents talkSome
End-to-endMinutesWhole systemFew

4.2 Quality gates

Describes gates that stop the pipeline on lint, coverage or type errors, defined as commands or jobs in the workflow. A lint job runs a tool such as ESLint or flake8, a test job enforces coverage thresholds, and a type-check job catches type errors before deploy. Fail fast so developers hear about problems within minutes of pushing.

- run: npm run lint
- run: npm test -- --coverage  # coverage gate
- run: npm run test:e2e
- run: npx tsc --noEmit  # type check
# Fail fast: lint first, expensive e2e last.

Quality-gate steps run cheap checks first and the expensive end-to-end suite last so the pipeline fails fast on simple errors.

4.3 Flaky tests are the enemy

Warns that tests which pass and fail without any code change poison trust in a red pipeline that everyone learns to ignore. The advice is to quarantine flaky tests immediately, investigate the root cause, and fix or delete them rather than silently retrying. A reliably green pipeline is the only signal a team can learn to trust.

  • Quarantine flaky tests immediately; a red pipeline everyone ignores is worse than no pipeline.
  • Sources of flakiness: timing/races, shared state, ordering, network, clock/timezone.
  • Retry once for insight, but fix the root cause.

4.4 Parallelism and caching

Explains strategies for keeping CI wall-clock time low as the test suite grows. Jobs split test files across multiple runners using matrix or shard configuration, and dependency caches restore package installs on each run. Cache keys tie to lockfile digests so caching stays correct while total minutes stay affordable.

# Split tests across runners to cut wall-clock time
strategy:  # one matrix row per shard
  matrix: { shard: [1, 2, 3, 4] }
- run: npm test -- --shard=${{ matrix.shard }}/4  # run this shard's slice

# Cache dependencies
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}  # bust on lockfile change

A four-way shard matrix spreads tests across runners, and a lockfile-keyed cache keeps npm installs fast.

  1. Classify your existing tests into the pyramid.
  2. Add a coverage threshold gate to a pipeline.
  3. Find the flakiest test you have and diagnose it.

5 · Pipeline as Code

5.1 GitHub Actions5.2 GitLab CI5.3 Designing a pipeline

Explains that a pipeline becomes code the moment it lives in the repository, reviewed and versioned like any other file. The chapter shows GitHub Actions and GitLab CI side by side so you can read one workflow format and translate it into the other. Pipeline changes go through the same pull request review process as application code.

5.1 GitHub Actions

Describes how GitHub Actions defines workflows in YAML files under .github/workflows, using triggers, jobs and steps. A workflow triggers on events such as push, pull request or schedule, then runs steps inside jobs on hosted or self-hosted runners. Every push or pull request can run a full quality gate without extra infrastructure.

name: pipeline
on:
  push: { branches: [main] }  # CI on main pushes
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4  # fetch the repo
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm test

A minimal GitHub Actions pipeline that runs on every push and PR, installing dependencies then linting and testing on ubuntu.

5.2 GitLab CI

Explains how GitLab CI structures work in stages and jobs inside a single YAML file at the repository root. Stages such as build, test and deploy run in order, while jobs in one stage run in parallel, with artifacts flowing to later stages automatically. Each job can restrict the branches or tags that trigger it.

stages: [test, build, deploy]  # run in order
test:
  stage: test
  image: node:22  # per-job runner image
  script:
    - npm ci
    - npm test
  artifacts:
    reports: { junit: junit.xml }

GitLab CI splits work into ordered stages, runs npm install and tests in one job, and publishes a JUnit report for the UI.

5.3 Designing a pipeline

Advises designing stages, gates and reusable pieces before writing a single line of YAML. Break the flow into validate, test, build and deploy stages, and make each job rerunnable without side effects so pipelines are idempotent and safe to rerun. Shared templates and reusable jobs avoid duplication across workflows.

  • Stages: validate → test → build → scan → deploy.
  • Gates: stop the line on failure; no manual overrides without record.
  • Reuse: composite actions / reusable workflows / templates.
  • Idempotent: running twice must be safe.

6 · Artifacts, Registries & Versioning

6.1 Passing artifacts between jobs6.2 Container and package registries6.3 Versioning schemes

Explains that artifacts need a home, a version and a traceable link to their source. The chapter covers passing build outputs between CI jobs, storing images and packages in registries, and choosing a versioning scheme. Every artifact records the commit SHA that produced it so deployments can be audited and rolled back confidently.

6.1 Passing artifacts between jobs

Describes how CI systems upload build outputs in one job so later jobs can download them without rebuilding. GitHub Actions uses actions/upload-artifact and actions/download-artifact, while GitLab CI passes artifacts between stages automatically. The artifact you test is the same one you deploy, so nothing drifts between jobs or environments.

- run: npm run build  # produce dist/
- uses: actions/upload-artifact@v4  # stash for later jobs
  with: { name: dist, path: dist/ }
# later job
- uses: actions/download-artifact@v4  # restore in deploy job
  with: { name: dist }

The build job uploads dist as a named artifact that a later job downloads unchanged, avoiding a rebuild.

6.2 Container and package registries

Explains how registries such as GHCR, Docker Hub and package managers store versioned images and packages with access control. Pushing from the pipeline lets you tag each image or package with both a semantic version and the immutable git commit SHA. That dual tagging supports rollback and keeps the deployment audit trail intact.

docker build -t ghcr.io/acme/api:1.4.2 .  # tag image with version
docker push ghcr.io/acme/api:1.4.2  # publish to registry
# tag by semantic version + immutable git SHA for traceability

Build and push tag the image with a semantic version so every environment pulls the identical, traceable artifact.

6.3 Versioning schemes

Contrasts SemVer for libraries and API consumers with CalVer and plain build numbers for continuously deployed services. SemVer communicates breaking changes through major, minor and patch numbers, while CalVer encodes the date. Whatever scheme you pick, record the git SHA alongside the version so operations can always identify the exact source of a release.

  • SemVer (MAJOR.MINOR.PATCH) for libraries.
  • CalVer or build numbers for continuously deployed services.
  • Always record the commit SHA in the artifact metadata — it is your audit trail.

7 · Environments & Configuration

7.1 Environment tiers7.2 Configuration vs code7.3 Preview environments

Explains how code flows through local, CI, staging and production while configuration is injected separately for each environment. The chapter covers environment tiers, why configuration belongs outside the artifact, and preview environments created per pull request. Keeping the artifact byte-identical across environments is what prevents drift.

7.1 Environment tiers

Describes the tiers from local and CI through staging to production, each existing to catch problems before the next one sees them. Staging approximates production with realistic data and traffic, and preview environments catch issues even earlier per branch. The point is that code never reaches production without first proving itself in a lower tier.

Typical progression: local → CI → staging/pre-prod → production, plus ephemeral preview environments per pull request.

7.2 Configuration vs code

Explains the rule that configuration lives in the environment, never baked into the image. Secrets, URLs and feature values are injected as environment variables or resolved at runtime by a secrets manager, so the same artifact behaves differently only through those injected values. That is what makes one build deployable to many environments safely.

# Same artifact, different config injected at deploy time:
APP_ENV=production  # injected at deploy time
DATABASE_URL=postgres://...
FEATURE_NEW_CHECKOUT=true  # flag rides the same artifact

12-factor rule: store config in the environment, never baked into the image.

These environment variables are injected at deploy time, keeping one artifact identical and valid across every environment.

7.3 Preview environments

Describes preview environments that spin up a production-like space for each pull request and tear it down on merge. Platforms such as Vercel, Netlify or Kubernetes namespaces keyed to the branch deploy the artifact under a unique URL. They dramatically shorten UI reviews, API contract checks and database migration review.

  • Spin up an isolated, prod-like environment per PR (namespace + DB schema).
  • Tear it down on merge/close to control cost.
  • Massively shortens review of UI and migrations.

  1. List config values that differ per environment.

8 · Deployment Strategies

8.1 The menu8.2 Canary by the numbers

Explains the choices for how new code reaches users and how fast you can undo it. The chapter compares recreate, rolling, blue-green, canary and feature flags, weighing downtime, speed and rollback complexity for each. Choosing the right strategy depends on your service’s statefulness and tolerance for risk.

8.1 The menu

Compares the deployment strategy menu and the trade-offs each one makes. Recreate is simplest but causes downtime, rolling replaces instances gradually with zero downtime, blue-green flips traffic between two identical environments, canary shifts small percentages, and feature flags gate code at runtime. Pick based on how stateful your service is and how much risk you will tolerate.

StrategyIdeaRollback
RecreateStop old, start newSlow, downtime
RollingReplace instances graduallyRoll back the wave
Blue-greenTwo full environments, switch trafficInstant switch back
CanarySmall % of traffic firstDrop canary
Feature flagsDeploy dark, enable per userFlip flag off

8.2 Canary by the numbers

Explains how canary deploys shift small traffic percentages, such as five or ten percent, while watching error rate and latency for the new version. Orchestrators like Argo Rollouts promote or roll back automatically when health signals dip. Automatic rollback triggers protect users because a bad release never reaches everyone.

# Progressive delivery
5% traffic  -> watch error rate/latency 5 min
25% traffic -> watch 10 min
100%        -> done

# Automatic rollback triggers on an error-budget burn:
#   errors > 1% OR p95 latency > 500ms  => abort and shift back

A progressive canary steps traffic up while error-budget thresholds act as triggers for automatic rollback.

Combine canary with feature flags: the flag controls exposure, the canary controls infrastructure risk. They answer different questions.

9 · Database Changes in CI/CD

9.1 Migrations as code9.2 Backward-compatible migrations9.3 Rolling back data changes

Explains why schema changes are the hardest part of continuous delivery: data cannot roll back the way code can. The chapter covers versioned migrations, backward compatibility and safe rollback strategies. Every migration is versioned in the repo and runs through the pipeline before it touches production data.

9.1 Migrations as code

Describes keeping migration scripts versioned in the repository and running them as pipeline or deploy steps with tools such as Flyway, Alembic or Prisma Migrate. Never rewrite or edit a migration that has already shipped; add a new one instead so history stays intact. Each migration produces a schema that is reproducible from the repo alone.

# Version migrations in the repo; run them in the pipeline:
php artisan migrate --force      # Laravel
dotnet ef database update        # EF Core
npx prisma migrate deploy        # Prisma

# Never edit history: add a NEW migration to change things.

Each framework runs its versioned migration inside the pipeline; change history by adding, never by editing.

9.2 Backward-compatible migrations

Presents the expand, deploy, backfill, contract dance for zero-downtime schema changes. First add the new column or table, deploy code that tolerates the old shape, backfill data, then stop using the old structure and finally drop it. Renames and NOT NULL constraints must be staged across releases or old code breaks.

# "Expand / contract" for zero-downtime:
# 1 EXPAND: add nullable column / new table (old code ignores it)
# 2 DEPLOY: code writes to both old + new
# 3 BACKFILL: job fills historical rows
# 4 CONTRACT: stop using old, drop it in a later release

# DANGER (breaks during the window): rename column, drop column, NOT NULL without default

Expand, deploy, backfill, contract keeps schema changes safe; renames, drops and bare NOT NULL are the listed traps.

9.3 Rolling back data changes

Explains that code rolls back quickly but data does not, so destructive schema changes need special care. Prefer additive changes that both old and new code can tolerate, and take snapshots or backups before any destructive operation. That snapshot becomes the recovery path if a release goes wrong.

Code rollback is easy; data rollback is hard. Prefer additive changes, take backups/snapshots before destructive ones, and separate schema migration from data migration.

Exercises 9

  1. Convert a "rename column" into an expand/contract sequence.
  2. Add a migration step to a deployment pipeline.
  3. Explain why dropping a column is rarely a safe rollback target.

10 · Secrets Management

10.1 Rules that never bend10.2 Secret stores and OIDC

Explains that secrets such as API keys and cloud credentials are the crown jewels a pipeline carries. The chapter covers the rules for never storing them in code, injecting them at deploy time, and rotating them the moment they leak. Least privilege keeps the blast radius small whenever something does go wrong.

10.1 Rules that never bend

Sets the non-negotiable rules of secret handling: never commit secrets to the repository, inject them only at deploy or run time, and rotate them the moment they leak. Restrict each credential to the minimum scope and permissions the pipeline actually needs. Least privilege keeps the blast radius small whenever a secret is exposed.

  • Never commit secrets; scan for them in pre-commit and CI.
  • Inject at deploy time from a secret store.
  • Rotate on exposure, immediately, and assume compromise.
  • Least privilege: a pipeline gets only what it needs.

10.2 Secret stores and OIDC

Explains how secret managers such as HashiCorp Vault, AWS Secrets Manager and GitHub encrypted secrets hold credentials outside the repository. OpenID Connect lets a workflow exchange a short-lived token for cloud credentials without storing long-lived keys anywhere. That removes permanent secrets from the pipeline environment entirely.

# Prefer short-lived credentials via OIDC over static keys:
permissions:
  id-token: write  # OIDC token for AWS
  contents: read
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123:role/ci  # short-lived, no static keys
    aws-region: eu-west-1
# No long-lived AWS keys stored anywhere.

OIDC grants the workflow a short-lived role via id-token, so no static cloud keys ever exist in the repo.

Secrets leaked in logs, PR comments or build artifacts are extremely common. Mask them, avoid printing env, and rotate anything that touches a log.

Exercises 10

  1. Add a secret-scanning step to CI.
  2. Replace a static cloud key with OIDC federation.
  3. Document a rotation procedure for one secret.

11 · Observability & Release Health

11.1 The three signals11.2 SLOs and error budgets11.3 Automated rollback

Argues that you cannot safely deploy what you cannot watch. The chapter connects metrics, logs and traces to release gates and rollback decisions, so health data becomes part of the pipeline itself. Deployments get gated on real signals instead of on faith that everything is fine.

11.1 The three signals

Describes the three observability signals and the job each one does: metrics measure rates and counts, logs explain events with detail, and traces locate latency across services. Tools like Prometheus, Grafana, OpenTelemetry and Jaeger provide them. Together they tell you whether a release is healthy enough to keep moving forward.

SignalAnswers
MetricsHow much / how fast (error rate, latency, throughput)
LogsWhat happened for this request
TracesWhere time went across services

11.2 SLOs and error budgets

Explains how service level objectives translate customer happiness into concrete numbers, measured with service level indicators such as availability or latency. The error budget, the allowed slack over a period, tells you how much risk remains before you must stop shipping. Rapid budget burns freeze risky changes until reliability recovers.

SLI: fraction of requests served successfully under 300ms
SLO: 99.9% over 30 days
Error budget: 0.1% = ~43 minutes/month
If the budget burns fast -> freeze risky changes and stabilise.
Deploy health gates compare the canary's SLI against the baseline.

The SLO defines the target, the error budget quantifies allowed failure, and a burned budget freezes risky changes.

11.3 Automated rollback

Describes wiring rollback directly to an SLI so a bad rollout reverts itself automatically. The pipeline or orchestrator watches signals such as error rate and latency and, when thresholds break, swaps back to the previous artifact. The previous artifact is usually the fastest fix because it restores known-good code immediately.

Wire the deployment controller to the SLI: if error rate or latency crosses a threshold during rollout, shift traffic back automatically. The fastest fix is usually the previous artifact.

12.2 Supply-chain integrity

Explains how to make an artifact’s history trustworthy: sign artifacts and images with cosign, ship a software bill of materials, and pin third-party actions to full commit SHAs instead of tags.   • Sign artifacts and images; verify signatures before deploy.
  • Generate an SBOM (Software Bill of Materials) per release.
  • Pin and review third-party actions; prefer trusted publishers.
  • Follow SLSA-style provenance: know exactly how an artifact was built.

CI runners are high-value targets: they hold credentials and can deploy. Treat pipeline config changes like production changes — reviewed and protected.

13.1 Kubernetes with GitOps

Explains how Git becomes the single source of truth in a GitOps setup, with Argo CD or Flux continuously reconciling the cluster to the state declared in the repository. CI builds and pushes the image, then the CD tool watches Git, applies the manifest and reports drift. Rollbacks are simply a git revert.

# Desired state lives in git; a controller reconciles the cluster.
# CI builds + pushes an image; CD updates the manifest; Argo CD applies it.
apiVersion: apps/v1
kind: Deployment
metadata: { name: api }

  replicas: 3

14 · Toolchain Deep Dive: GitHub Actions

14.1 Anatomy of a workflow14.2 Reusable workflows and matrix

A focused dissection of GitHub Actions so the earlier concepts stick. The chapter examines workflow anatomy, reusable workflows and the matrix strategy in detail. It reads the real YAML syntax for triggers, jobs and steps, and for passing values between jobs.

14.1 Anatomy of a workflow

Describes a workflow file as a name, triggers set with the on keyword, concurrency, and jobs, each declaring runs-on and a list of steps. Jobs run in parallel on runners and exchange values through needs dependencies and the outputs property. Permissions and environment define which secrets and scopes each job can use.

name: release
on:
  push:
    tags: ['v*']  # version tags trigger release
concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false
jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    outputs: { tag: ${{ steps.meta.outputs.tag }} }
    steps:
      - uses: actions/checkout@v4
      - id: meta
        run: echo "tag=${GITHUB_REF_NAME}" >> "$GITHUB_OUTPUT"
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production  # gate this deploy job
    steps:
      - run: echo deploying ${{ needs.build.outputs.tag }}

A tag-triggered release workflow with concurrency control; the build job hands its tag output to a gated production deploy.

14.2 Reusable workflows and matrix

Explains how the matrix strategy fans one job out across combinations of operating systems, runtimes and other variables, and how reusable workflows let teams call a centrally maintained workflow from many repositories with the uses keyword. A path filters which combinations run. Both keep duplication low and test coverage wide.

jobs:
  test:
    strategy:
      matrix:  # test matrix combos
        os: [ubuntu-latest, windows-latest]
        node: [20, 22]  # two Node majors
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }

The matrix fans the same test job across two OSes and two Node majors, with setup-node caching dependencies per run.

Use concurrency to cancel superseded PR runs and to serialise production deploys. It prevents "two deploys racing" bugs.

16 · Culture, Failure & Continuous Improvement

16.1 Blameless culture16.2 A postmortem template16.3 Practices that keep pipelines healthy

Argues that the best tooling fails without the right culture around it. The chapter covers blameless postmortems, a practical postmortem template, and the practices that keep pipelines healthy. Culture is treated as part of the system, not a soft afterthought bolted onto the tooling.

16.1 Blameless culture

Explains that blameless postmortems chase how the system allowed the failure to happen, not who caused it. Incident reviews focus on process, tooling and automation gaps rather than individual mistakes. Psychological safety is what keeps people shipping and reporting problems early instead of hiding them.

If a deploy fails and the response is "who did it?", people hide mistakes and stop deploying. Blameless postmortems ask how the system allowed it and produce fixes, not culprits.

16.2 A postmortem template

Gives a structured template for writing incident reviews: impact summary, timeline, root cause, what worked, and action items each with an owner and a date. Keep the narrative short and the fixes concrete, with one clear owner per action. Concrete improvements matter far more than a perfect story.

Title: Checkout 5xx during release v42
Impact: 12 min, 3% of checkouts failed
Timeline: (UTC, what happened, who noticed, actions)
Root cause: canary health check missed a downstream timeout
What went well: automatic rollback triggered in 40s
Action items: (owner, due date) tighten canary thresholds
Lessons: (small, concrete)

A compact postmortem structure: impact, timeline, root cause, what went well, then owner-and-deadline action items.

16.3 Practices that keep pipelines healthy

Lists the habits that keep delivery on rails: fast pipelines so feedback arrives quickly, loud failures nobody can ignore, zero flaky tests, and an owner for each pipeline. Treat the pipeline as a product with a maintainer and a backlog, improved and refactored like any other application code.

  • Keep the pipeline fast (target < 10 min for PR checks).
  • Make failures loud, specific and actionable.
  • Delete or fix flaky tests the day they appear.
  • Own the pipeline as a product with a maintainer.
