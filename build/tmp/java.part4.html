12 · The web with servlets and JSP

Before Spring there was the Servlet API, and it is still the contract every Java web framework implements. Understanding the container model — one servlet instance, many request threads, a scoped session — explains the shape of everything built on top of it. The API is jakarta.servlet since Jakarta EE 9; the old javax.servlet namespace is dead.

12.1 The servlet lifecycle and HttpServlet

A servlet is a class the container instantiates once and calls with many concurrent requests. The lifecycle is init, then service many times, then destroy, and the concurrency of the middle phase is the whole design constraint.

One instance, many threads

The container creates a single servlet instance (unless the class is declared SingleThreadModel, which is deprecated and wrong). Requests arrive on container threads, so instance fields are shared mutable state and must be immutable, thread-safe or absent. Everything request-specific belongs in a local variable or the request attributes. HttpServlet.service dispatches by HTTP method to doGet, doPost, doPut, doDelete and the rest, and the default implementations of the less common methods return 405. Since Servlet 3.0 the mapping can be an annotation, @WebServlet("/orders"), or a web.xml entry; mixing both is legal but a duplicate URL pattern is a startup failure.

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.*;
import java.io.IOException;
import java.time.Instant;

@WebServlet(name = "health", urlPatterns = {"/health", "/healthz"}, loadOnStartup = 1)
public class HealthServlet extends HttpServlet {

    // Immutable instance state is safe to share across request threads.
    private final Instant startedAt = Instant.now();

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("application/json");
        resp.setCharacterEncoding("UTF-8");
        resp.setHeader("Cache-Control", "no-store");

        String status = "UP";
        resp.setStatus(HttpServletResponse.SC_OK);
        resp.getWriter().printf(
                "{\"status\":\"%s\",\"uptimeSeconds\":%d}%n",
                status, java.time.Duration.between(startedAt, Instant.now()).toSeconds());
    }
}

Request and response objects

HttpServletRequest exposes parameters (getParameter returns the first value and null when absent), headers, the method, the URI, cookies, the session and a request-scoped attribute map. getParameterMap returns every value for a multi-valued field. The request body is a stream and can be read once, so a filter that consumes it must wrap the request to allow a re-read. HttpServletResponse sets the status, headers and content type before the body is committed; after the first flush the response is committed and a later sendError or sendRedirect throws IllegalStateException. Character encoding must be set before writing text, or the container uses its default and non-ASCII data arrives corrupted.

@WebServlet("/orders/create")
public class CreateOrderServlet extends HttpServlet {

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        // Parameters are request-scoped values, never shared state.
        String sku  = req.getParameter("sku");
        String qty  = req.getParameter("qty");
        String[] tags = req.getParameterValues("tag");

        if (sku == null || sku.isBlank()) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "sku is required");
            return;
        }
        int count;
        try {
            count = Integer.parseInt(qty == null ? "1" : qty);
        } catch (NumberFormatException e) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "qty must be an integer");
            return;
        }

        var created = new OrderService().create(sku, count, tags);
        req.setAttribute("order", created);            // visible to a forward target

        // PRG: redirect after a successful POST so a refresh does not resubmit.
        resp.sendRedirect(req.getContextPath() + "/orders/view?id=" + created.id());
    }
}
A servlet's init runs once and is the place to open expensive shared resources, but you cannot rely on destroy being called on a JVM crash. Close a resource that must not leak with a shutdown hook as well, or use a container-managed DataSource.

12.2 web.xml, the deployment descriptor and packaging a WAR

A web application is packaged as a WAR: a jar-shaped archive with WEB-INF/classes, WEB-INF/lib and a WEB-INF/web.xml. The descriptor configures what annotations cannot easily express.

What the descriptor still owns

Servlet mappings, filters, listeners and context parameters can be annotations, but web.xml remains the place for ordering (which filter runs first when two match), welcome files, error pages, session configuration and security constraints. The filter ordering from @WebFilter is the order the container scans, which is not specified, so a filter chain whose order matters must be declared in web.xml. A <context-param> is application-wide and read with getServletContext().getInitParameter; a <init-param> is servlet-specific and read with getServletConfig().getInitParameter. A <listener> with ServletContextListener is the standard place to start and stop application-scoped resources.

Embedded containers and why they won

A traditional WAR needs a container: Tomcat, Jetty, WildFly or GlassFish, installed separately, with the WAR deployed into it. Since the mid-2010s the dominant model is to embed the container: the application's main method starts an embedded Tomcat or Jetty, which makes the deliverable a single jar and the deployment a process rather than an installation. Spring Boot does exactly this. The embedded model removes the shared-container classloader problems, gives every application its own JVM and its own tuning, and makes the process a first-class citizen for a scheduler. The cost is a bigger artifact and the loss of container-provided services such as JNDI, which must be provided by the application instead.

import org.apache.catalina.startup.Tomcat;
import java.nio.file.Files;

public class EmbeddedTomcat {
    public static void main(String[] args) throws Exception {
        var tomcat = new Tomcat();
        tomcat.setPort(8080);
        tomcat.getConnector();                       // must be called to create it

        var ctx = tomcat.addContext("", Files.createTempDirectory("tomcat").toString());
        Tomcat.addServlet(ctx, "health", new HealthServlet());
        ctx.addServletMappingDecoded("/health", "health");

        tomcat.start();
        tomcat.getServer().await();                  // block until shutdown
    }
}

12.3 JSP, EL and JSTL

A JSP is an HTML template compiled by the container into a servlet on first request. It exists so that markup lives in a file a designer can edit, and its disciplined use is as a pure view over data prepared by a servlet.

The implicit objects and what belongs in a page

A JSP has nine implicit objects, of which the important ones are request, response, session, application, out and pageContext. A scriptlet (<% ... %>) is raw Java in a template and should not be written: it defeats the separation the technology exists for and cannot be tested. The alternatives are Expression Language ${...} for reading values and JSTL tags (<c:forEach>, <c:if>, <c:choose>, <fmt:formatNumber>) for control flow and formatting. Since JSP 2.0 the recommended shape is JSP as template plus a servlet that forwards a prepared model, with <jsp:include> for reusable fragments and a <taglib> for the JSTL prefix.

<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c"   uri="jakarta.tags.core" %>
<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
<!DOCTYPE html>
<html lang="en">
<head><meta charset="UTF-8"><title>Orders</title></head>
<body>

  <c:choose>

12.4 Sessions, cookies and filters

HTTP is stateless, so the container supplies a session: a server-side map keyed by an opaque id that travels in a cookie. Filters are the cross-cutting layer that runs before and after every matching request.

How a session is created and found

request.getSession() creates one if absent; getSession(false) returns null rather than creating one, which matters for a health check or a static asset. The id travels in the JSESSIONID cookie, which should be HttpOnly (unreadable from JavaScript), Secure (HTTPS only) and SameSite=Lax (blocks cross-site POST forgery). Session fixation is prevented by calling changeSessionId() at login and again at privilege elevation. Invalidation is session.invalidate(). Attributes in a session must be Serializable if the container may replicate or persist the session. For clustering, either sticky sessions plus replication, or a shared store such as Redis via Spring Session, or a stateless model where the session holds only an id.

@WebServlet("/login")
public class LoginServlet extends HttpServlet {

    @Override protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        String user = req.getParameter("user");
        char[] pass = req.getParameter("password").toCharArray();

        if (!authenticate(user, pass)) {
            // Do not create a session for a failed login.
            resp.sendError(HttpServletResponse.SC_UNAUTHORIZED, "bad credentials");
            return;
        }

        // Fixation defence: a fresh id for the authenticated session.
        HttpSession existing = req.getSession(false);
        if (existing != null) existing.invalidate();
        HttpSession session = req.getSession(true);
        session.setAttribute("user", user);
        session.setMaxInactiveInterval(30 * 60);       // seconds

        resp.sendRedirect(req.getContextPath() + "/orders");
    }

    private boolean authenticate(String user, char[] pass) {
        return user != null && pass.length > 0;       // replace with a real check
    }
}

Filters and the chain

A filter implements Filter and is invoked for every matching request; it calls chain.doFilter(req, resp) to continue, and the code after that call runs on the way out. That symmetric shape is what makes an encoding filter, a logging filter, a rate limiter, a correlation-id filter and an authentication filter all look the same. To change the request or the response, wrap it: a HttpServletRequestWrapper can add a header or allow the body to be re-read, and a HttpServletResponseWrapper can capture output for compression or for a cache. Filters run before servlets and after them, so they are the correct place for anything that applies to a whole path.

import jakarta.servlet.*;
import jakarta.servlet.annotation.WebFilter;
import jakarta.servlet.http.*;
import java.io.IOException;
import java.util.UUID;

@WebFilter(urlPatterns = "/*")
public class CorrelationFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        var req  = (HttpServletRequest) request;
        var resp = (HttpServletResponse) response;

        String id = req.getHeader("X-Request-Id");
        if (id == null || id.isBlank()) id = UUID.randomUUID().toString();
        req.setAttribute("requestId", id);
        resp.setHeader("X-Request-Id", id);

        long start = System.nanoTime();
        try {
            chain.doFilter(request, response);          // the rest of the chain
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            System.out.printf("%s %s -> %d in %d ms [%s]%n",
                    req.getMethod(), req.getRequestURI(), resp.getStatus(), ms, id);
        }
    }
}

// An authentication filter that requests a session but does not create one.
@WebFilter(urlPatterns = "/orders/*")
class AuthFilter implements Filter {
    @Override public void doFilter(ServletRequest rq, ServletResponse rs, FilterChain chain)
            throws IOException, ServletException {
        var req  = (HttpServletRequest) rq;
        var resp = (HttpServletResponse) rs;
        HttpSession session = req.getSession(false);
        if (session == null || session.getAttribute("user") == null) {
            resp.sendRedirect(req.getContextPath() + "/login?next=" + req.getRequestURI());
            return;                                     // do not continue
        }
        chain.doFilter(rq, rs);
    }
}
Keep session attributes few and small, and prefer to store an identifier plus a cache lookup rather than an object graph. A large session makes replication expensive, a schema change in an attribute breaks every active session, and an attribute that references a per-request object leaks memory for the session's lifetime.

13 · Spring Boot

Spring Boot is the dominant Java application framework: a container for dependency injection over the Spring Framework, plus auto-configuration, an embedded server, an opinionated set of starters and production endpoints. Spring Boot 3.x requires Java 17 and uses the jakarta namespace; Spring Boot 4.0 followed in November 2025.

13.1 Starters, auto-configuration and the application class

A Boot application is a main method annotated @SpringBootApplication. Everything else — the server, the datasource, the JSON mapper, the security filter chain — is auto-configuration driven by what is on the classpath.

What the annotation does and how auto-configuration decides

@SpringBootApplication is three annotations in one: @SpringBootConfiguration (a specialisation of @Configuration), @ComponentScan over the package of the class and everything below it, and @EnableAutoConfiguration. Auto-configuration classes are @Conditional: they apply only when a class is present on the classpath, a bean of a type is missing, a property is set, or the application is not a web application. That is why adding spring-boot-starter-data-jpa and a JDBC URL produces a working EntityManagerFactory with no configuration, and why adding nothing produces none. The condition report (--debug) prints every auto-configuration and the exact condition that decided it.

package com.acme.orders;

import org.springframework.boot.SpringApplication;

@SpringBootApplication
public class OrdersApplication {
    public static void main(String[] args) {

13.2 Dependency injection, beans and scopes

The container creates objects, wires their collaborators and manages their lifecycle. Injection is constructor-first, and the design pressure it creates — small classes with explicit dependencies — is the more important benefit.

Stereotypes, constructor injection and the context

@Component, @Service, @Repository and @Controller all register a bean; the specialisations add semantics and, for @Repository, exception translation. Constructor injection is preferred because the dependencies can be final, the object cannot be constructed in an invalid state, and a misplaced dependency is a compile error rather than a NullPointerException. Since Spring 4.3 a single constructor needs no @Autowired. Two beans of the same type are ambiguous: resolve with a @Qualifier, a @Primary, or by naming the parameter after the bean. Configuration classes use @Configuration and @Bean, and a @ConfigurationProperties record binds a group of settings with type checking.

import org.springframework.stereotype.Service;
import org.springframework.context.annotation.*;
import org.springframework.boot.context.properties.ConfigurationProperties;
import java.util.List;

@ConfigurationProperties(prefix = "orders")
record OrdersProperties(int maxLines, List<String> allowedRegions) { }

@Service
class PricingService {
    private final TaxClient tax;

    // Constructor injection: final field, no @Autowired needed, testable.
    PricingService(TaxClient tax) { this.tax = tax; }

    java.math.BigDecimal priceWithTax(String region, java.math.BigDecimal net) {
        return net.add(tax.rate(region).multiply(net));
    }
}

interface TaxClient { java.math.BigDecimal rate(String region); }

@Configuration
class AppConfig {
    @Bean
    TaxClient taxClient(OrdersProperties props) {
        // A bean method can take other beans as parameters and can be conditional.
        return region -> props.allowedRegions().contains(region)
                ? new java.math.BigDecimal("0.20")
                : java.math.BigDecimal.ZERO;
    }
}

Scopes, proxies and the lifecycle

The default scope is singleton: one instance per context. prototype creates a new instance per injection point. request and session are web scopes and, being longer-lived than the singleton that injects them, are provided as a proxy that resolves the real object per call. @PostConstruct and @PreDestroy bracket a bean's life; InitializingBean and DisposableBean are the interface equivalents. Injection into a field of a bean is technically possible and is the wrong default: it hides the dependency list, makes the class impossible to construct in a test without reflection, and permits a circular reference that the container resolves by building a half-initialised object. Circular dependencies are a design smell; break them by extracting a third collaborator.

@Component
class ReportCache {
    private final java.util.Map<String, Report> cache = new java.util.concurrent.ConcurrentHashMap<>();
    private final CaffeineHolder backing;          // whatever backs it

    ReportCache(CaffeineHolder backing) { this.backing = backing; }

    @jakarta.annotation.PostConstruct
    void warmUp() { System.out.println("warming report cache"); }

    @jakarta.annotation.PreDestroy
    void flush() { cache.forEach((k, v) -> backing.write(k, v)); }

    // request-scoped bean injected into a singleton: resolved by proxy per call
    @org.springframework.beans.factory.annotation.Autowired
    private org.springframework.beans.factory.ObjectProvider<RequestContext> ctx;
}
Keep the context small. Every @Component is a bean the container instantiates at startup, and a context with thousands of beans has a measurable start-up cost and a wide tangle of dependencies. Favour explicit configuration for infrastructure and component scanning for the application layer, and never component-scan a package you do not own — you will register a bean the library's author never intended to be a bean.

13.3 REST controllers, content negotiation and error handling

Spring MVC maps HTTP to Java methods with annotations: a URL to a method, a request body to a parameter, a return value to a response body. REST is a style over that mapping, not the mapping itself.

Mapping, binding and validation

@RestController is @Controller plus @ResponseBody, so every return value is serialised. @RequestMapping and its shorthands @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping bind methods, and a class-level prefix composes with them. @PathVariable, @RequestParam, @RequestHeader, @RequestBody and @RequestPart pull the parts of a request into parameters. @Valid triggers Jakarta Bean Validation on an annotated parameter, and a failure throws MethodArgumentNotValidException before the method body runs. Jackson serialises the response; annotate with @JsonIgnore, @JsonProperty or a mixin when the wire format must differ from the class.

import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.http.*;
import java.util.List;

@RestController
@RequestMapping("/api/v1/orders")
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    record CreateOrder(
            @NotBlank String sku,
            @Min(1) @Max(1000) int qty,
            @Email String email) { }

    record OrderView(long id, String sku, int qty, java.math.BigDecimal total) { }

    @GetMapping("/{id}")
    OrderView one(@PathVariable long id) {
        return service.find(id).map(o -> new OrderView(o.id(), o.sku(), o.qty(), o.total()))
                      .orElseThrow(() -> new OrderNotFoundException(id));
    }

    @GetMapping
    List<OrderView> search(@RequestParam(defaultValue = "") String q,
                           @RequestParam(defaultValue = "0") int page,
                           @RequestParam(defaultValue = "20") int size) {
        return service.search(q, page, Math.min(size, 100))
                      .stream().map(o -> new OrderView(o.id(), o.sku(), o.qty(), o.total())).toList();
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    ResponseEntity<OrderView> create(@Valid @RequestBody CreateOrder body) {
        var o = service.create(body.sku(), body.qty());
        var view = new OrderView(o.id(), o.sku(), o.qty(), o.total());
        return ResponseEntity.created(java.net.URI.create("/api/v1/orders/" + o.id())).body(view);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void delete(@PathVariable long id) { service.delete(id); }
}

Errors as RFC 9457 problem details

An API must fail predictably. Spring supports the ProblemDetail type, which serialises to application/problem+json with type, title, status, detail and instance — the RFC 9457 shape (the successor to RFC 7807). A @RestControllerAdvice with @ExceptionHandler methods centralises the mapping from domain exception to status and body, so no controller repeats the translation and no stack trace ever reaches a client. Validation failures map to 400 with the field errors included; an unauthenticated request to 401; a missing resource to 404; an unexpected exception to 500 with a correlation id and the detail suppressed.

import org.springframework.web.bind.annotation.*;
import org.springframework.http.*;
import org.springframework.web.context.request.WebRequest;

class OrderNotFoundException extends RuntimeException {
    OrderNotFoundException(long id) { super("order " + id + " not found"); }
}

@RestControllerAdvice
class ApiErrors {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex, WebRequest req) {
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Order not found");
        pd.setType(java.net.URI.create("https://errors.acme.com/order-not-found"));
        pd.setProperty("instance", req.getDescription(false));
        return pd;
    }

    @ExceptionHandler(org.springframework.web.bind.MethodArgumentNotValidException.class)
    ProblemDetail invalid(org.springframework.web.bind.MethodArgumentNotValidException ex) {
        var pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("Validation failed");
        var fields = new java.util.LinkedHashMap<String, String>();
        ex.getBindingResult().getFieldErrors()
          .forEach(fe -> fields.put(fe.getField(), fe.getDefaultMessage()));
        pd.setProperty("errors", fields);
        return pd;
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex) {
        // Log with the stack trace; return nothing sensitive.
        var pd = ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
        pd.setTitle("Internal error");
        pd.setDetail("The request could not be completed");
        return pd;
    }
}
Return a DTO, never the entity. Serialising a JPA entity couples the database schema to the public API, leaks lazy-loading proxies (which throw or fetch the whole graph), and exposes columns that were never meant to be public. A record view type costs one mapping line and buys a stable contract.

13.4 Spring Data JPA, entities and transactions

JPA is the persistence specification; Hibernate is its implementation; Spring Data JPA generates repository implementations from interface declarations. Together they remove most hand-written SQL and introduce a specific set of performance traps.

Entities, repositories and derived queries

An entity is a class annotated @Entity with an @Id; the table name defaults to the class name in snake case and the column names to the field names. Repositories extend JpaRepository<T, ID>, and a method name such as findByEmailAndActiveTrue is parsed into a query — capable, but unpredictable past two or three conditions, so use @Query for anything non-obvious. Transactions are declared with @Transactional; the default is read-write and rolls back on a runtime exception but not on a checked one, which must be requested with rollbackFor. readOnly = true is a real optimisation, not documentation: it skips dirty checking.

import jakarta.persistence.*;
import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;
import org.springframework.transaction.annotation.Transactional;
import java.util.*;

Lazy loading and the N+1 problem

A @OneToMany association is lazy by default, so iterating the children of each parent in a list issues one query per parent — the N+1 problem, which turns a 20 ms screen into a 2-second one. The fixes are a fetch join (join fetch in JPQL, or a @EntityGraph), a batch size (@BatchSize or hibernate.default_batch_fetch_size), or a projection that reads exactly the columns the screen needs. The other trap is that a lazy association accessed outside the transaction throws LazyInitializationException because the session is closed — the fix is to fetch eagerly within the transaction or to map to a DTO inside it, not to disable lazy loading globally.

// N+1: one query for the customers, then one per customer for the orders.
var customers = customerRepository.findByTier(Customer.Tier.GOLD);
customers.forEach(c -> System.out.println(c.getOrders().size()));

// Fix 1: an entity graph forces a single join.
interface CustomerRepository extends JpaRepository<Customer, Long> {
    @org.springframework.data.jpa.repository.EntityGraph(attributePaths = "orders")
    List<Customer> findByTier(Customer.Tier tier);
}

// Fix 2: an explicit fetch join in JPQL, with distinct for duplicates.
interface OrderRepository extends JpaRepository<Order, Long> {

14 · Oracle SQL and Oracle Database

Oracle Database is the enterprise RDBMS with its own SQL dialect, its own procedural language (PL/SQL) and a set of behaviours that differ from the open-source databases. This chapter covers the dialect, the objects Java code interacts with, and the JDBC specifics.

14.1 The Oracle SQL dialect

Oracle SQL is close to standard SQL and diverges in a handful of places that trip up anyone arriving from PostgreSQL or MySQL. The divergences are mostly deliberate, and mostly older than the standard.

DUAL, the empty string and the type system

DUAL is a one-row, one-column table owned by SYS that exists so a SELECT with no FROM has something to select from; SELECT 1 FROM DUAL is the canonical expression query, and it is still valid because a huge amount of Oracle SQL and thousands of tools assume it. The most notorious quirk is that Oracle treats the empty string as NULL: '' is NULL, length('') is NULL and not 0, and WHERE name = '' never matches anything. The type system uses VARCHAR2 (not VARCHAR, which is reserved for a future standard meaning), NUMBER with an optional precision and scale, DATE which always carries a time component, TIMESTAMP with optional time zone, and CLOB/BLOB for large objects. A BOOLEAN type exists in PL/SQL always and in SQL since 23ai; before that, NUMBER(1) with a CHECK (flag IN (0,1)) was the convention.

-- SQL*Plus / SQLcl
SELECT 1 FROM DUAL;
SELECT SYSDATE, SYSTIMESTAMP FROM DUAL;
SELECT USER, SYS_CONTEXT('USERENV', 'DB_NAME') FROM DUAL;

-- The empty string is NULL, and length('') is NULL, not 0.
SELECT CASE WHEN '' IS NULL THEN 'NULL' ELSE 'empty' END FROM DUAL;   -- NULL
SELECT LENGTH('') FROM DUAL;                                          -- (null)
SELECT NVL(LENGTH(''), 0) FROM DUAL;                                  -- 0

-- NVL family and the standard equivalents.
SELECT NVL(comm, 0), COALESCE(bonus, comm, 0), NVL2(comm, 'has', 'none') FROM emp;
SELECT NULLIF(status, 'UNKNOWN') FROM orders;

-- DECODE is Oracle's pre-standard CASE.
SELECT DECODE(tier, 'GOLD', 0.20, 'SILVER', 0.10, 0.05) FROM customers;

-- Row limiting since 12c; ROWNUM is the older idiom.
SELECT * FROM orders ORDER BY created_at DESC FETCH FIRST 10 ROWS ONLY;
SELECT * FROM (SELECT * FROM orders ORDER BY created_at DESC) WHERE ROWNUM <= 10;

-- Date formatting is NLS-dependent; always use an explicit format mask.
SELECT TO_CHAR(created_at, 'YYYY-MM-DD HH24:MI:SS') FROM orders;
SELECT TO_DATE('2026-10-14 09:30:00', 'YYYY-MM-DD HH24:MI:SS') FROM DUAL;
SELECT ADD_MONTHS(SYSDATE, 3), TRUNC(SYSDATE, 'MM'), LAST_DAY(SYSDATE) FROM DUAL;

Escaping, hierarchy and analytic queries

Oracle's identifier quoting is a double quote; a string literal is single-quoted, and an embedded single quote is doubled ('O''Brien'). The q'[...]' syntax removes the doubling for a literal full of quotes. Hierarchical queries use CONNECT BY PRIOR with the pseudo-column LEVEL, and SYS_CONNECT_BY_PATH builds a path string; the standard WITH ... AS (recursive) form is also supported. Analytic functions — ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM() OVER — are the standard way to compute a ranking or a running total without a self-join. The set operators are UNION, UNION ALL, INTERSECT and MINUS, the last standing in for EXCEPT.

-- Quoting and q-literals.
SELECT 'O''Brien' AS name FROM DUAL;
SELECT q'[It's got an apostrophe]' AS phrase FROM DUAL;
SELECT 'He said "hi"' FROM DUAL;

-- CONNECT BY: the management chain below a manager.
SELECT LEVEL AS depth, LPAD(' ', (LEVEL - 1) * 2) || ename AS org
  FROM emp
 START WITH mgr IS NULL
CONNECT BY PRIOR empno = mgr
 ORDER SIBLINGS BY ename;

-- The standard recursive form.
WITH org (empno, ename, mgr, depth) AS (
  SELECT empno, ename, mgr, 1 FROM emp WHERE mgr IS NULL
  UNION ALL
  SELECT e.empno, e.ename, e.mgr, o.depth + 1
    FROM emp e JOIN org o ON e.mgr = o.empno
)
SELECT * FROM org ORDER BY depth, ename;

-- Analytic ranking and a running total.
SELECT ename, deptno, sal,
       ROW_NUMBER() OVER (PARTITION BY deptno ORDER BY sal DESC) AS rn,
       RANK()       OVER (PARTITION BY deptno ORDER BY sal DESC) AS rnk,
       SUM(sal)     OVER (PARTITION BY deptno ORDER BY hiredate
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running
  FROM emp;

-- MERGE: an upsert in one statement.
MERGE INTO customers t
USING (SELECT :id AS id, :name AS name, :email AS email FROM DUAL) s
   ON (t.id = s.id)
WHEN MATCHED THEN UPDATE SET t.name = s.name, t.email = s.email
WHEN NOT MATCHED THEN INSERT (id, name, email) VALUES (s.id, s.name, s.email);

-- MINUS is EXCEPT.
SELECT id FROM current_orders MINUS SELECT id FROM archived_orders;
Never rely on an implicit date format. TO_DATE('01/02/03') depends on NLS_DATE_FORMAT and will silently give a different date on a session with a different locale: the classic bug is a month/day swap that only appears in one country. Always pass a format mask to TO_DATE, and compare a DATE/TIMESTAMP column with a value of the same type, not with a string.

14.2 Sequences, identity and concurrency-safe keys

Oracle generates surrogate keys with a sequence, a server-side counter that is independent of any transaction. Since 12c a column may also be declared as an identity column, which creates and manages a sequence for you.

Sequences and their two number sources

CREATE SEQUENCE with START WITH, INCREMENT BY, CACHE, NOCACHE and CYCLE/NOCYCLE. A sequence is consumed with seq.NEXTVAL and read with seq.CURRVAL; the value is not affected by rollback, so a rolled-back transaction leaves a gap, which is expected and correct — a sequence guarantees uniqueness and ordering, not contiguity. The CACHE setting controls how many values are pre-allocated in memory; a cache of 20 is the default and reduces contention, but a database restart loses the cached range, producing a jump and — for an ordered sequence with NOORDER — a possible out-of-order insert across a RAC cluster. The ORDER option guarantees globally increasing values in a cluster at the cost of inter-instance coordination.

CREATE SEQUENCE orders_seq
  START WITH 1000
  INCREMENT BY 1
  NOCACHE
  NOORDER
  NOCYCLE;

-- Use it, then reference the value in the same session.
INSERT INTO orders (id, sku, qty) VALUES (orders_seq.NEXTVAL, 'KB-01', 2);
INSERT INTO order_lines (order_id, line_no) VALUES (orders_seq.CURRVAL, 1);

-- Identity column (12c+): no explicit sequence, no trigger.
CREATE TABLE customers (
  id      NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name    VARCHAR2(120) NOT NULL,
  email   VARCHAR2(255) NOT NULL,
  CONSTRAINT ux_customers_email UNIQUE (email)
);

-- GENERATED BY DEFAULT allows an explicit id; useful for data migration.
CREATE TABLE legacy_import (
  id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
  payload CLOB
);

Getting a generated key back into Java

An INSERT does not return the new identity value unless you ask for it. JDBC's Connection.prepareStatement(sql, new String[]{"ID"}) plus getGeneratedKeys() is the portable way; Oracle also supports INSERT ... RETURNING id INTO ? with an OraclePreparedStatement register, which avoids the extra fetch. A batch insert of thousands of rows with getGeneratedKeys is measurably slower, so a common pattern is to generate the keys client-side from a sequence or a UUID and insert with batchUpdate. UUID keys avoid the round trip but make an index less cache-friendly; a numeric sequence is usually the better default.

import java.sql.*;

String sql = "INSERT INTO customers (name, email) VALUES (?, ?)";
try (Connection con = ds.getConnection();
     PreparedStatement ps = con.prepareStatement(sql, new String[]{"ID"})) {
    ps.setString(1, "Ada");
    ps.setString(2, "ada@example.com");
    ps.executeUpdate();
    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) System.out.println("new id = " + keys.getLong(1));
    }
}

// RETURNING INTO binds the value directly, without a second round trip.
String withReturning = "INSERT INTO customers (name, email) VALUES (?, ?) RETURNING id INTO ?";
try (var ps = (oracle.jdbc.OraclePreparedStatement) con.prepareStatement(withReturning)) {
    ps.setString(1, "Grace");
    ps.setString(2, "grace@example.com");
    ps.registerReturnParameter(3, oracle.jdbc.OracleTypes.NUMBER);
    ps.executeUpdate();
    try (var rs = ps.getReturnResultSet()) {
        if (rs.next()) System.out.println("new id = " + rs.getLong(1));
    }
}
A gap in a key column is not a bug, so never try to reuse or renumber ids. If business rules require a gapless document number — an invoice sequence, for instance — that is a different problem: it needs a locked row or a dedicated numbering table, because a sequence cannot fill a gap left by a rollback.

14.3 PL/SQL blocks, cursors and exception handling

PL/SQL is Oracle's procedural extension, executed inside the database. A block has three sections — declare, execute, handle — and the language's value is that it keeps a multi-step operation on the server, one round trip from the client.

The block and its variables

The anonymous block is DECLARE ... BEGIN ... EXCEPTION ... END;, with the declare and exception sections optional. Variables use %TYPE to inherit a column's type and %ROWTYPE to inherit a whole row, so a column width change does not break the code; CONSTANT marks a constant and NOT NULL adds a constraint. SELECT ... INTO assigns a single row and raises NO_DATA_FOUND or TOO_MANY_ROWS otherwise. DBMS_OUTPUT.PUT_LINE is the print statement, visible only when the client has enabled the buffer. A transaction is implicit: PL/SQL does not commit unless it is told to, which is what makes it composable from Java.

SET SERVEROUTPUT ON SIZE UNLIMITED

DECLARE
  v_email   customers.email%TYPE;
  v_tier    customers.tier%TYPE := 'GOLD';
  c_vat     CONSTANT NUMBER(4,2) := 0.20;
  v_total   NUMBER(12,2);
BEGIN
  SELECT email, tier
    INTO v_email, v_tier
    FROM customers
   WHERE id = 42;

  v_total := 100 * (1 + c_vat);

  DBMS_OUTPUT.PUT_LINE('customer ' || v_email || ' tier ' || v_tier);
  DBMS_OUTPUT.PUT_LINE('total ' || TO_CHAR(v_total, 'FM999,999.00'));
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('no customer 42');
  WHEN TOO_MANY_ROWS THEN
    DBMS_OUTPUT.PUT_LINE('id is not unique - schema is broken');
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('unexpected: ' || SQLCODE || ' ' || SQLERRM);
    RAISE;                      -- never swallow an unknown error
END;
/

Cursors and bulk operations

A cursor is a handle to a query's result set. An implicit cursor is created for every DML statement and its attributes are read as SQL%ROWCOUNT and SQL%FOUND. An explicit cursor is declared, opened, fetched row by row, and closed; the FOR rec IN cursor LOOP form does all four and is what you should write. A SYS_REFCURSOR is a cursor variable that can be returned to a client, which is how a stored procedure returns a result set to JDBC. BULK COLLECT fetches many rows into a collection in one context switch and FORALL performs many DML statements in one, and both are the difference between a batch job running in seconds and in minutes.

-- Explicit cursor, the readable form.
BEGIN
  FOR rec IN (SELECT id, name FROM customers WHERE tier = 'GOLD' ORDER BY name) LOOP
    DBMS_OUTPUT.PUT_LINE(rec.id || ' ' || rec.name);
  END LOOP;
END;
/

-- Bulk collect and forall: two orders of magnitude fewer context switches.
DECLARE
  TYPE t_ids IS TABLE OF customers.id%TYPE;
  v_ids t_ids;
BEGIN
  SELECT id BULK COLLECT INTO v_ids FROM customers WHERE tier = 'SILVER';

  FORALL i IN 1 .. v_ids.COUNT
    UPDATE customers SET tier = 'GOLD' WHERE id = v_ids(i);

  DBMS_OUTPUT.PUT_LINE('promoted ' || SQL%ROWCOUNT || ' customers');
END;
/

-- A cursor variable returned to the client.
CREATE OR REPLACE PROCEDURE gold_customers(p_cur OUT SYS_REFCURSOR) IS
BEGIN
  OPEN p_cur FOR SELECT id, name, email FROM customers WHERE tier = 'GOLD';
END;
/

-- Named exceptions: a business rule with its own code and message.
DECLARE
  e_insufficient EXCEPTION;
  PRAGMA EXCEPTION_INIT(e_insufficient, -20001);
BEGIN
  RAISE e_insufficient;
EXCEPTION
  WHEN e_insufficient THEN
    DBMS_OUTPUT.PUT_LINE('caught the named condition');
END;
/
Always re-raise an unexpected exception, or at least log SQLCODE and SQLERRM. A WHEN OTHERS THEN NULL; handler is the classic Oracle defect: it converts a real failure into silent data loss and removes the only evidence that anything went wrong.

14.4 Procedures, functions, packages and triggers

A stored subprogram is compiled in the database and called by name. A package groups related subprograms behind one specification, and it is the unit of API design in PL/SQL.

Procedures and functions

A procedure performs an action and returns nothing through the return position; a function returns a value and can be called from SQL. Both support parameters with the modes IN (default), OUT and IN OUT. CREATE OR REPLACE makes redeployment idempotent. A FUNCTION called from a SQL statement must be deterministic or the optimiser may cache a wrong result: declare DETERMINISTIC when that is true, and PARALLEL_ENABLE when it is safe to run in a parallel slave. A RESULT_CACHE clause caches the function's result keyed by its arguments, which is a large win for a lookup that is called per row.

CREATE OR REPLACE FUNCTION tax_amount(
    p_region IN VARCHAR2,
    p_net    IN NUMBER
) RETURN NUMBER DETERMINISTIC IS
    v_rate NUMBER(4,2);
BEGIN
  v_rate := CASE p_region
              WHEN 'EU' THEN 0.20
              WHEN 'UK' THEN 0.20
              WHEN 'US' THEN 0.07
              ELSE 0
            END;
  RETURN ROUND(p_net * v_rate, 2);
END;
/

-- Callable from SQL once compiled.
SELECT id, tax_amount('EU', 100) AS tax FROM orders FETCH FIRST 5 ROWS ONLY;

CREATE OR REPLACE PROCEDURE promote_customer(
    p_id   IN  NUMBER,
    p_tier IN  VARCHAR2 DEFAULT 'GOLD',
    p_rows OUT NUMBER
) IS
BEGIN
  UPDATE customers SET tier = p_tier WHERE id = p_id;
  p_rows := SQL%ROWCOUNT;
END;
/

Packages, package state and triggers

A package has a specification (what is public) and a body (the implementation). Only the specification is referenced by dependents, so changing the body does not invalidate them. Package-level variables have session scope and persist for the life of the session, which makes them a per-session cache and also a per-session memory leak; DBMS_SESSION.MODIFY_PACKAGE_STATE(DBMS_SESSION.REINITIALIZE) resets them. A package can overload a subprogram by parameter type, and it can have an initialisation block at the end of the body that runs once per session. A trigger fires on DML or on a system event; a row-level trigger is the place for an audit row or a derived column, and a statement-level trigger for a bulk rule. Triggers are powerful and hard to debug: a trigger that fires on a table another trigger also touches can produce cascading updates that no application code can see.

-- Specification: the public API.
CREATE OR REPLACE PACKAGE customer_api AS
  FUNCTION  tax(p_region IN VARCHAR2, p_net IN NUMBER) RETURN NUMBER DETERMINISTIC;
  PROCEDURE promote(p_id IN NUMBER, p_tier IN VARCHAR2 DEFAULT 'GOLD');
  PROCEDURE list_gold(p_cur OUT SYS_REFCURSOR);
  c_max_tier CONSTANT VARCHAR2(8) := 'PLATINUM';
END customer_api;
/

-- Body: the implementation, plus a session-scoped counter.
CREATE OR REPLACE PACKAGE BODY customer_api AS
  g_calls PLS_INTEGER := 0;

  FUNCTION tax(p_region IN VARCHAR2, p_net IN NUMBER) RETURN NUMBER IS
  BEGIN
    g_calls := g_calls + 1;
    RETURN ROUND(p_net * CASE p_region WHEN 'EU' THEN 0.20 WHEN 'US' THEN 0.07 ELSE 0 END, 2);
  END tax;

  PROCEDURE promote(p_id IN NUMBER, p_tier IN VARCHAR2 DEFAULT 'GOLD') IS
  BEGIN
    UPDATE customers SET tier = p_tier WHERE id = p_id;
    IF SQL%ROWCOUNT = 0 THEN
      RAISE_APPLICATION_ERROR(-20002, 'no customer ' || p_id);
    END IF;
  END promote;

  PROCEDURE list_gold(p_cur OUT SYS_REFCURSOR) IS
  BEGIN
    OPEN p_cur FOR SELECT id, name FROM customers WHERE tier = 'GOLD';
  END list_gold;
END customer_api;
/

-- An audit trigger: row-level, fires for every changed row.
CREATE OR REPLACE TRIGGER trg_customers_audit
AFTER INSERT OR UPDATE OR DELETE ON customers
FOR EACH ROW
BEGIN
  INSERT INTO customers_audit (changed_at, action, old_tier, new_tier, actor)
  VALUES (SYSTIMESTAMP,
          CASE WHEN INSERTING THEN 'I' WHEN UPDATING THEN 'U' ELSE 'D' END,
          :OLD.tier, :NEW.tier, SYS_CONTEXT('USERENV', 'SESSION_USER'));
END;
/
Package-level variables persist across calls in the same session, so a package used as a cache in a connection-pooled application holds a stale value for as long as the pooled connection lives. Either reset the state per unit of work or move the cache out of the database.

14.5 JDBC with the Oracle driver

The Oracle JDBC driver (ojdbc11.jar, ojdbc17.jar for Java 17 and later) is a thin Java client that speaks Oracle's wire protocol directly. It is not a from-scratch reinvention: it implements the same java.sql interfaces, with a set of Oracle-specific extensions.

Connecting and the extensions worth knowing

The thin URL form is jdbc:oracle:thin:@//host:port/service_name, where the service name (not the SID) is the modern identifier. oracle.jdbc.OracleConnection adds Oracle types and features: createArrayOf for a VARRAY or nested table, createStruct for an object type, and setObject with an OracleType for TIMESTAMP WITH TIME ZONE or INTERVAL. SYS_REFCURSOR is registered as OracleTypes.CURSOR and read as a ResultSet. ARRAY and Struct mappings use java.sql.Array and java.sql.Struct. Fetch size matters more on Oracle than on most databases because the default is small; setting setFetchSize(500) on a statement that returns many rows is a large, free improvement.

import java.sql.*;
import oracle.jdbc.OracleTypes;

String url = "jdbc:oracle:thin:@//db-host:1521/ORCLPDB1";

try (Connection con = DriverManager.getConnection(url, "app", System.getenv("ORA_PASSWORD"))) {

    // Fetch size: the single most effective read tuning knob.
    try (PreparedStatement ps = con.prepareStatement(
             "SELECT id, name FROM customers WHERE tier = ? ORDER BY name")) {
        ps.setFetchSize(500);
        ps.setString(1, "GOLD");
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                System.out.println(rs.getLong("id") + " " + rs.getString("name"));
            }
        }
    }

    // Call a package procedure that returns a cursor.
    try (CallableStatement cs = con.prepareCall("{ call customer_api.list_gold(?) }")) {
        cs.registerOutParameter(1, OracleTypes.CURSOR);
        cs.execute();
        try (ResultSet rs = (ResultSet) cs.getObject(1)) {
            while (rs.next()) System.out.println(rs.getString("name"));
        }
    }

    // An IN OUT parameter of a scalar type.
    try (CallableStatement cs = con.prepareCall("{ call customer_api.promote(?, ?, ?) }")) {
        cs.setLong(1, 42L);
        cs.setString(2, "GOLD");
        cs.registerOutParameter(3, Types.NUMERIC);
        cs.execute();
        System.out.println("rows affected: " + cs.getInt(3));
    }
}

Data types, dates and arrays

Oracle's types do not map one-to-one to Java. NUMBER without a scale may exceed a long, so read it as BigDecimal unless the column is known to be small. DATE carries a time component and maps to java.sql.Timestamp; a TIMESTAMP WITH TIME ZONE should be read with getObject(..., OffsetDateTime.class) so the offset survives. CLOB and BLOB stream with getCharacterStream and getBinaryStream. A nested table or VARRAY is a java.sql.Array whose getArray() returns an Object[], and a user-defined object type is a java.sql.Struct. The oracle.jdbc.OracleTypes constants are the type codes to pass to registerOutParameter for the Oracle-specific cases.

// Exact numerics and time-zone-aware timestamps.
String sql = "SELECT id, balance, created_ts FROM accounts WHERE id = ?";
try (PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setLong(1, 42L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            java.math.BigDecimal balance = rs.getBigDecimal("balance");     // never a double
            java.time.OffsetDateTime created =
                    rs.getObject("created_ts", java.time.OffsetDateTime.class);
            System.out.println(balance + " @ " + created);
        }
    }
}

// A VARRAY column: java.sql.Array wrapping a String[].
try (PreparedStatement ps = con.prepareStatement("SELECT tags FROM products WHERE id = ?")) {
    ps.setLong(1, 7L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            java.sql.Array arr = rs.getArray("tags");
            if (arr != null) {
                String[] tags = (String[]) arr.getArray();
                System.out.println(java.util.Arrays.toString(tags));
            }
        }
    }
}

// Passing an array back into a nested-table parameter.
Object[] region = { "EU", "UK" };
java.sql.Array sqlArray = con.createArrayOf("VARCHAR2", region);
try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO promo_regions (promo_id, regions) VALUES (?, ?)")) {
    ps.setLong(1, 99L);
    ps.setArray(2, sqlArray);
    ps.executeUpdate();
}
Use the thin driver and UCP (Universal Connection Pool) or HikariCP rather than the deprecated OCI driver. Verify the driver's server compatibility matrix before an upgrade: a driver several releases old can fail a new authentication or encryption negotiation in a way that reports as a generic connection error. Keep the driver on the same release train as the database where possible.

15 · Packaging and deployment

A Java program ships as a set of class files plus the runtime that executes them. The choices are how many jars, whether the runtime is shared or bundled, and whether the unit of deployment is a jar, a native installer, a container image or a platform-managed buildpack.

15.1 Jars, fat jars and module jars

A jar is a zip with a manifest. The packaging decision is where the dependencies live: alongside, inside, or resolved at runtime by a module path.

The three shapes

A thin jar contains only the application's classes and names its dependencies in the manifest's Class-Path or expects them on the classpath; it is small and stable but the deployment unit is a directory. A fat or uber jar contains every dependency, unzipped and flattened into one archive; it is a single file and the simplest thing to ship, at the cost of size and of resource-name collisions. A shaded jar goes further and relocates dependency packages under a private prefix, which is how two libraries that need incompatible versions of the same package coexist. A modular jar keeps the dependencies outside and declares them in module-info; it is the smallest runtime and the strongest encapsulation, and the strictest about its dependencies also being modular.

What breaks inside a fat jar

Flattening destroys the META-INF/services service loader files when two dependencies provide the same file name: the second overwrites the first, and a JDBC driver or a JSON provider stops being discovered. Spring Boot's nested-jar layout avoids that by keeping each dependency as its own jar inside. A signed jar also breaks: the manifest digests no longer match after flattening, so a SecurityException or a class-load failure appears out of nowhere. And a resource addressed by a fixed path — getResource("/config.properties") — can shadow another module's file of the same name. These are the reasons a build tool's own packaging plugin is preferable to a hand-rolled unzip-and-rejar.

# Gradle: a fat jar and a shadowed jar
// build.gradle.kts
tasks.jar {
    manifest { attributes("Main-Class" to "com.acme.Main") }
    from({ configurations.runtimeClasspath.get().map { if (it.isDirectory) it else zipTree(it) } })
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
}

// Or use the plugin that gets it right:
// plugins { id("com.github.johnrengelman.shadow") version "8.1.1" }
// tasks.shadowJar { archiveClassifier = "all"; mergeServiceFiles() }
A fat jar built by naive extraction loses service files silently. mergeServiceFiles() in the shadow plugin and Boot's nested layout both solve it; a hand-written unzip -o loop does not. If a dependency becomes invisible only in the packaged artifact and works perfectly in the IDE, this is the first thing to check.

15.2 jlink and custom runtime images

Since JDK 9 the JDK itself is modular, and jlink can assemble a runtime image that contains only the modules an application needs. The output is a directory with its own java launcher.

What goes in and how big it gets

jlink --add-modules takes either an explicit list or the special value ALL-MODULE-PATH, resolves the transitive closure, and writes an image with a bin, conf, lib and legal directory. Flags that matter: --strip-debug removes debug information, --no-header-files and --no-man-pages remove the C headers and manual pages a developer would need but a deployment does not, --compress=zip-6 compresses the image, --include-locales keeps only selected locales, and --vm=server picks the HotSpot variant. A typical server application's image is tens of megabytes rather than the roughly 300 MB of a full JDK, and the win compounds in a container layer.

# shell - the smallest useful server image, and a hello-world one
JMODS="$JAVA_HOME/jmods"

# Which modules does the application actually need?
jdeps --multi-release 25 --ignore-missing-deps --print-module-deps --class-path "lib/*" app.jar
# -> java.base,java.logging,java.sql,java.naming,jdk.crypto.ec

jlink --module-path "$JMODS" \
      --add-modules java.base,java.logging,java.sql,java.naming,jdk.crypto.ec \
      --strip-debug --no-header-files --no-man-pages --compress=zip-6 \
      --output build/runtime

build/runtime/bin/java -version
du -sh build/runtime                 # a fraction of a full JDK

# A one-module image and a launcher script, all in one command.
jlink --add-modules java.base --add-launcher hello=hello.properties --output hello-image

The launcher properties file and constraints

--add-launcher name=file.properties embeds a launcher whose main-class, module, class-path and JVM options are recorded in the image, so the user runs image/bin/name rather than remembering a module path. The constraints are real: an automatic module (a plain jar with only a derived name) can be used on the module path but cannot be jlink'd into a custom image, and a dependency that uses deep reflection on a JDK-internal package needs --add-opens in the launcher's JVM options. For a non-modular application the working combination is jlink for the runtime plus an explicit --class-path in the launcher, or jpackage for the whole thing.

# hello.properties - the launcher embedded in the image
# main-class=com.acme.Main
# class-path=lib/app.jar:lib/postgresql-42.7.4.jar
# java-options=-Xmx512m
# java-options=--add-opens=java.base/java.lang=ALL-UNNAMED

# shell - build a runtime for a non-modular app and launch it
jlink --add-modules ALL-MODULE-PATH --strip-debug --no-header-files --no-man-pages \
      --compress=zip-6 --output build/runtime
build/runtime/bin/java -cp "app.jar:lib/*" com.acme.Main --help
Size the image from jdeps --print-module-deps rather than guessing. Including a module you do not need costs a few megabytes; omitting one costs a NoClassDefFoundError at first use of a rarely exercised path, which is exactly the kind of failure that appears in production and not in a smoke test.

15.3 jpackage, native installers and GraalVM native image

A JDK runtime is not something an end user should have to install. jpackage wraps a runtime image and an application into a platform-native installer; GraalVM Native Image compiles the application ahead of time into a standalone executable with no JVM at all.

jpackage output formats

jpackage --type selects the platform's installer: msi or exe on Windows, dmg or pkg on macOS, deb or rpm on Linux, and app-image for an unpackaged directory. Inputs are --input (the classes and jars), --main-jar and --main-class, --name, --app-version, --icon, and --runtime-image to bundle a custom runtime. The result is a normal installer that registers the application with the operating system and installs a private runtime, so the user needs no JDK. This is the route to a desktop tool that behaves like every other app, and it is the pairing for the JavaFX work in chapter 10.

# shell - a Windows MSI containing a trimmed runtime of its own
jlink --add-modules java.base,java.desktop,javafx.controls --output build/runtime

jpackage --type msi \
         --name "Acme Orders" \
         --app-version 1.4.0 \
         --input build/libs \
         --main-jar orders-desktop.jar \
         --main-class com.acme.OrdersApp \
         --runtime-image build/runtime \
         --icon assets/app.ico \
         --win-menu --win-shortcut \
         --dest build/installers

# A macOS disk image, and a Linux deb, from the same inputs.
jpackage --type dmg --name "Acme Orders" ... --dest build/installers
jpackage --type deb --name acme-orders ... --dest build/installers

Native image and what it changes

GraalVM Native Image does a whole-program static analysis at build time and emits a platform native executable that includes only the reachable code. The results are a startup measured in tens of milliseconds instead of one or more seconds, a much smaller memory footprint, and no JVM at all. The cost is the analysis: reflection, dynamic proxies, JNI and resource loading are invisible to a static analyser, so they need explicit configuration, produced automatically by the tracing agent or supplied by a library's own metadata. Builds are slow (minutes) and the peak throughput of a hot loop can be lower than a warmed-up JIT, which matters for a long-running batch job and not at all for a scale-to-zero function.

# shell - build a native executable, with the tracing agent filling the config
native-image -jar target/app.jar -o build/acme \
             -H:Name=acme -H:+ReportExceptionStackTraces

# Java 24+ moved the entry points into the JDK so no extra toolchain is needed:
# java -agentlib:native-image-agent=config-output-dir=META-INF/native-image -jar app.jar
# (run the app through a representative workload, then build)

# Verify startup time: this is the metric native image changes.
time ./build/acme --version
time java -jar target/app.jar --version
Choose the packaging by the workload. A scale-to-zero serverless function wants native image or a trimmed runtime so cold start is small. A long-running service wants a normal JVM so the JIT can reach its peak and the operator can attach tools. A desktop tool wants jpackage. A batch job wants throughput, so the JVM with a large heap and the Parallel collector.

15.4 Containers, JVM tuning and cloud deployment

A container is how a Java service is normally deployed now. The JVM must be told it is in a container, and the image must be layered so that a code change does not re-download the world.

The image, and why the order matters

Every COPY and RUN instruction is a layer, and Docker caches a layer until its inputs change. Copying the pom and running a dependency download before copying the source means the dependency layer survives a source change, which turns a two-minute rebuild into a few seconds. A multi-stage build compiles in one image and ships only the runtime in the next, which keeps the final image small and free of the build tools.

# Dockerfile - multi-stage, cache-aware, non-root
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -B -q dependency:go-offline          # cached until the pom changes
COPY src src
RUN ./mvnw -B -q clean package -DskipTests      # tests run in CI, not here

FROM eclipse-temurin:25-jre
WORKDIR /app

# Run as a non-root user.
RUN groupadd -r app && useradd -r -g app app
COPY --from=build --chown=app:app /src/target/app.jar app.jar

ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError -XX:+UseG1GC"
USER app
EXPOSE 8080

# exec form, so the JVM is PID 1 and receives SIGTERM directly.
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Container awareness, limits and probes

JDK 10 onwards is container-aware: with no explicit -Xmx, the heap defaults to 25% of the container's memory limit, and the number of GC and JIT threads follows the CPU quota. Set -XX:MaxRAMPercentage and InitialRAMPercentage so the heap is a stated fraction, and leave headroom for thread stacks, metaspace, the JIT code cache and direct buffers — a container sized exactly to the heap is killed by the OOM killer. Use -XX:+ExitOnOutOfMemoryError so a heap exhaustion terminates the process and the platform restarts it, rather than leaving it alive and failing every request. A Kubernetes readiness probe should point at /actuator/health/readiness and a liveness probe at /actuator/health/liveness, so a slow start is not mistaken for a hang and a deadlock is not mistaken for a slow start.

# Kubernetes: resources, probes and a graceful shutdown window
spec:
  containers:
    - name: orders
      image: registry.example.com/acme/orders:1.4.0
      ports: [{ containerPort: 8080 }]
      resources:
        requests: { memory: "512Mi", cpu: "250m" }
        limits:   { memory: "1Gi",   cpu: "1" }
      env:
        - name: JAVA_TOOL_OPTIONS
          value: "-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError"
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }
        initialDelaySeconds: 5
        periodSeconds: 5
      livenessProbe:
        httpGet: { path: /actuator/health/liveness, port: 8080 }
        initialDelaySeconds: 20
        periodSeconds: 10
      lifecycle:
        preStop: { exec: { command: ["sh", "-c", "sleep 5"] } }
  terminationGracePeriodSeconds: 45

# shell - build, run and inspect the container locally
docker build -t acme/orders:1.4.0 .
docker run --rm -p 8080:8080 -e DB_PASSWORD=secret -m 1g acme/orders:1.4.0

# Verify the JVM saw the container limit, not the host's memory.
docker exec <id> java -XshowSettings:system -version 2>&1 | grep -i memory

# Health, liveness and metrics.
curl -s localhost:8080/actuator/health | jq
curl -s localhost:8080/actuator/prometheus | head
Never put -XX:+ExitOnOutOfMemoryError in a single-shot batch job whose output has not been flushed: the process exits without running orderly shutdown code, so any partially written file stays partial. It is the right flag for a stateless server and the wrong one for a job that accumulates work in memory.
For a serverless or scale-to-zero target, choose the packaging by cold-start budget: a trimmed jlink runtime helps, Spring Boot's AOT and CDS support helps more, and GraalVM Native Image helps most — at the cost of build time and reflection configuration. Measure the cold start with the real workload before committing to a route, because the difference between a 300 ms and a 30 ms start is what decides whether a function is viable.
