0 · Orientation

What Docker Compose actually is, why the file format is now the Compose Specification rather than a vendor format, how the modern docker compose plugin differs from the retired Python docker-compose tool, and how to install and verify the current release.

Docker Compose is the declarative front end to the Docker engine for anything larger than a single container. Instead of remembering a wall of docker run flags — networks, volumes, environment variables, restart policy — you describe the desired end state in one YAML document and let Compose reconcile it.

0.1 What Docker Compose is

A description of desired state, not a script

Compose is not a shell script in YAML clothing. You declare what the finished system looks like — three services, two networks, one named volume, a handful of environment variables — and Compose decides the order of operations: create networks, pull or build images, create volumes, start containers, attach them. Because the document describes state rather than steps, running up twice is safe and idempotent: the second run finds most objects already correct and changes only what drifted.

The unit of work is the project. A project is a set of services that live and die together, get a shared network namespace, and share a name prefix on every object they create. By default the project name is the basename of the directory holding the compose file, so ~/code/shop/compose.yaml produces a project called shop, a network called shop_default, and containers named shop-web-1, shop-db-1 and so on.

That shared network is the quietly important part. Every service in a project joins the same user-defined bridge network automatically, and Docker's embedded DNS server resolves each service's name to the right container. That single design decision is why a service can connect to db:5432 instead of chasing an IP address: the name db is a DNS record that Compose maintains for you.

Where Compose stops and orchestration begins

Compose runs containers on one Docker host. It has no scheduler, no multi-node placement, no self-healing reconciliation loop that keeps a desired replica count alive across a cluster. That is a deliberate boundary, not a gap. Compose is the right tool for local development, CI test environments, single-host deployments and edge boxes; Kubernetes or a managed orchestrator is the right tool once you need many machines.

In practice the two are complementary: the same service definitions you use locally often get translated into a deployment manifest later, and the discipline of writing a precise compose.yaml forces you to make container boundaries, data volumes and wiring explicit long before production.

If a task needs two hosts, Compose is the wrong answer. If it needs one host with several coordinating containers, Compose will usually save you an afternoon.

0.2 Compose v2 versus v1

The command changed shape

The original Compose was a standalone Python program invoked as docker-compose with a hyphen. Since Compose v2 it is a Docker CLI plugin, and the command is docker compose with a space. The plugin ships with Docker Desktop and with the docker-compose-plugin package on Linux, so on any current install it is already there. The old Python tool reached end of life in July 2023 and should not be used for new work.

The practical differences are worth knowing because they show up in tutorials that predate 2023. v2 is written in Go, starts noticeably faster (no Python interpreter to boot), and runs natively on every platform the Docker CLI supports. It also removed the split between "build info" and "run info" ordering quirks, and it uses BuildKit by default for builds, which gives you multi-platform builds, better caching and secrets-aware Dockerfiles without extra setup.

# v1 (retired): a separate binary
docker-compose up -d

# v2 (current): a Docker CLI plugin
docker compose up -d

# both can coexist if the old binary is still on PATH,
# but only `docker compose` gets new features

The Compose Specification

The other half of the v2 story is standardization. The file format is no longer owned by a single product: it is the Compose Specification, an open document maintained under the compose-spec umbrella. Docker Compose implements it, and other tooling reads the same schema. That is why the file is now simply a Compose file, and why the filename preference moved to compose.yaml.

The specification also stopped the older custom extension keys from being declared at the top level. Everything user-defined now belongs under the x- prefix, which the tooling is required to ignore, and every top-level key has a defined meaning.

0.3 Installing and verifying

Confirming you have the plugin

Before writing anything, confirm which command your machine answers to. Running docker compose version should print a v2 version string and mention the plugin. If it errors with "docker: 'compose' is not a docker command", the plugin is missing and you should install it from Docker's package repository rather than reaching for the legacy binary.

# shell - verify the plugin is present and current
docker compose version
# Docker Compose version v2.32.x

docker info --format '{{.ServerVersion}}'
# 27.x - the engine Compose talks to

# list the compose files Compose would use, in priority order
ls compose.yaml compose.yml docker-compose.yml docker-compose.yaml 2>/dev/null

The filename Compose looks for

If you do not pass -f, Compose searches the current directory for a file in a fixed order: compose.yaml, then compose.yml, then the legacy docker-compose.yml, then docker-compose.yaml. The first one found is used. New projects should prefer compose.yaml; the hyphenated forms remain supported so that repositories written before 2023 keep working unchanged.

On Windows and macOS the plugin arrives with Docker Desktop and needs no extra step. On Linux, install the engine first, then the plugin package, and make sure the Compose CLI plugin directory is on DOCKER_CONFIG or the default ~/.docker/cli-plugins.

# Debian/Ubuntu - plugin from Docker's own repository
sudo apt-get update
sudo apt-get install docker-compose-plugin

# verify, then run a one-shot smoke test
docker compose version
mkdir -p /tmp/scaffold && cd /tmp/scaffold
docker compose init  # or write the file by hand
A minimal smoke test is worth doing once per machine: bring a two-service stack up, confirm it is healthy, then bring it down with -v. That proves networking, DNS and volume mounts all work before you debug them inside a real project.

1 · Anatomy of compose.yaml

The top-level keys, the project name, why the version key is obsolete and should be deleted, and how variable interpolation resolves a value from four different sources in a defined order.

1.1 Top-level keys

The small set that matters

A Compose file is a mapping with a handful of recognized top-level keys. services is the only required one; every other key is optional and exists to declare shared resources that services reference by name.

KeyPurpose
servicesThe containers to run. Required.
networksNamed networks services can join.
volumesNamed volumes that survive down.
secretsSecret values mounted under /run/secrets.
configsNon-secret configuration files mounted into services.
nameOverrides the project name.
includePulls in other Compose files as reusable units.
x-*Extension fields; ignored by Compose but usable via YAML anchors.

Two rules catch people out. First, a network or volume referenced by a service does not have to be declared at the top level — using it implicitly creates it with project defaults — but declaring it is how you attach options such as driver, external or driver_opts. Second, an external: true resource must already exist; Compose will not create it and will fail loudly if it is missing.

A skeleton with every key

# compose.yaml
name: shop               # project name; everything is prefixed with it

x-common: &common        # reusable block, referenced with *common
  restart: unless-stopped
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "3" }

services:
  web:
    image: ghcr.io/acme/shop-web:1.4.2
    <<: *common
    networks: [frontend, backend]
  db:
    image: postgres:17
    <<: *common
    networks: [backend]

networks:
  frontend: {}
  backend: {}

volumes:
  pgdata: {}
YAML merge keys (<<) plus an x- extension field are the idiomatic way to share a block of settings without editing generated files. In the real YAML file it is literally two less-than signs.

1.2 The name key and project identity

Why the project name matters more than it looks

The project name is a namespace prefix applied to every object Compose creates: networks, volumes, and the default container names. If you run two checkouts of the same repository on one machine without changing the name, their containers collide on names and their published ports collide on the host. Setting an explicit name, or passing -p, is how you run a second instance side by side.

# shell - three ways to control the project name
docker compose -p shop-staging up -d        # CLI flag wins
COMPOSE_PROJECT_NAME=shop-ci docker compose up -d   # env var
# or declare it in the file itself:
# name: shop

Resolution order

Compose resolves the project name in a fixed precedence. The -p flag on the command line beats the COMPOSE_PROJECT_NAME environment variable, which beats the name key in the Compose file, which beats the name from any included file. If none of those are set, Compose derives the name from the directory containing the first Compose file, sanitizing it to lowercase letters, digits, dashes and underscores.

That last fallback is why a project moved from ~/proj to ~/proj-v2 suddenly grows a second set of volumes named proj-v2_pgdata and appears to have lost its data. The data is still there under the old prefix; the new project simply does not see it. Pin name explicitly whenever data persistence matters.

1.3 The obsolete version key

Delete it

Older files began with version: "3.9". That key is obsolete in the Compose Specification. It no longer selects a schema and cannot enable or disable features; modern Compose reads the whole document and warns that the key is meaningless. The single most common cleanup in a 2026 repository is deleting that line.

# legacy - produces a warning on current Compose
version: "3.9"
services:
  web:
    image: nginx:1.27

# current - no version key at all
services:
  web:
    image: nginx:1.27

What replaced the schema split

Before the specification existed, the major version number gated which features were legal — for example, deploy was only meaningful in the swarm-oriented version 3. The specification folded all of that into one schema: every key has a defined meaning, features that only apply to a scheduler are documented as such, and Compose implements the ones that make sense on a single host. The result is that you can use a health check, a deploy block and a profile in the same file without declaring a version that claims you can.

If a tutorial tells you to add version: "3.8" to fix a parse error, the tutorial is out of date. The fix is almost always a typo in the YAML, not a missing version key.

1.4 Variable interpolation

Substituting values at parse time

Compose interpolates ${VARIABLE} references before it validates the document, using a small but expressive syntax. A bare reference substitutes the empty string when unset, and each modifier changes what happens in that case.

SyntaxBehaviour when the variable is unset
${VAR}Substitutes empty string
${VAR:-def}Uses def when unset or empty
${VAR-def}Uses def only when unset
${VAR:?err}Fails with the message err when unset or empty
${VAR:+alt}Uses alt only when set
$$A literal $, not interpolated
# compose.yaml
services:
  api:
    image: ghcr.io/acme/api:${TAG:-latest}
    environment:
      DATABASE_URL: "postgres://app:${DB_PASS:?DB_PASS must be set}@db:5432/app"
    command: ["sh", "-c", "echo cost is $$5 and stay"]

Where values come from

Interpolation reads from the shell environment first, then from the project's .env file (or the file named by --env-file). That order matters: a value exported in your shell silently overrides the .env file, which is exactly what you want on CI and exactly what fools you when a stale export lingers in a terminal. Use :? for anything the stack cannot sensibly guess, so a missing password stops the run instead of producing a broken container that fails ten seconds later.

Keep interpolation and environment: straight. Interpolation happens in the file before Compose ever starts a container; environment: sets variables inside the container. A common bug is writing PASSWORD: ${PASSWORD} and expecting the container to expand it — the container only ever sees the already-substituted literal value.

# shell - inspect what interpolation produced, safely
docker compose config          # fully resolved, all ${} replaced
docker compose config --quiet  # validates and prints nothing on success

2 · Services, Images and Builds

Choosing between image and build, wiring the build context and Dockerfile, passing build arguments, selecting a stage from a multi-stage Dockerfile, and controlling when Compose is allowed to pull a newer image.

2.1 image versus build

Two ways to get a container

Every service needs an image. You either name a prebuilt one with image: or ask Compose to build one with build:. You may specify both: build tells Compose how to produce the image, and image gives that built result a local tag so pushes and references stay stable.

# pull-only service
services:
  db:
    image: postgres:17.2

# build-only service: Compose tags it project-service automatically
  api:
    build: ./api

# build-and-tag: the recommended shape for anything you push
  worker:
    build:
      context: ./worker
      dockerfile: Dockerfile
    image: ghcr.io/acme/worker:${TAG:-dev}

Which to reach for

Use image alone for off-the-shelf software — databases, caches, proxies — where you want a specific published artifact and nothing more. Use build for your own code. When you set both, remember that docker compose up will build the image but will not push it; pushing is a separate docker compose push step, and in a CI pipeline you usually build and push with docker buildx bake or the plain docker build so the same artifact can be promoted unchanged.

A subtle trap: if a service declares both image and build and the local tag already exists, Compose may skip rebuilding, so you keep running yesterday's code after editing the source. docker compose up --build forces a rebuild, and docker compose build does it explicitly.

2.2 Build context, Dockerfile and args

The three knobs that decide what gets built

context is the directory sent to the builder. It defines the boundaries of what the Dockerfile can COPY. Send the smallest context that contains what the build needs; a context of the repository root quietly uploads the entire tree, including node_modules and .git, unless a .dockerignore excludes it. dockerfile names the file to use when it is not literally Dockerfile. args supplies values for the Dockerfile's ARG instructions.

services:
  web:
    build:
      context: .
      dockerfile: docker/web.Dockerfile
      args:
        NODE_VERSION: "22"
        BUILD_ENV: production
      # BuildKit cache mount reuse across builds
      cache_from:
        - ghcr.io/acme/web:cache
      target: runtime
# docker/web.Dockerfile
ARG NODE_VERSION=22
FROM node:${NODE_VERSION} AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM deps AS build
COPY . .
ARG BUILD_ENV=production
RUN npm run build -- --mode "$BUILD_ENV"

FROM node:${NODE_VERSION}-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY package*.json ./
RUN npm ci --omit=dev
USER node
CMD ["node", "dist/server.js"]

Arguments versus environment

Build arguments are visible in image history and are not a place for secrets; use them for version pins and build modes. They are also not environment variables inside the running container — an ARG that is not promoted with ENV disappears once the layer is built. For values that must not leak into a layer, BuildKit's --mount=type=secret or a Compose secrets: block is the correct mechanism, and the classic mistake is baking a token into an image with an ARG.

2.3 Multi-stage targets

One Dockerfile, several usable images

Multi-stage Dockerfiles produce more than one image; the final stage is what you get by default, but target lets a service stop at an earlier stage. This is extremely useful for development: the deps stage has everything installed, the build stage has tooling, and the runtime stage is slim. A development service can target a stage that includes dev dependencies and a shell, while the production profile targets runtime.

# compose.yaml - develop against a fat stage, ship the slim one
services:
  web:
    build:
      context: .
      target: deps      # includes devDependencies and ts-node
    command: npm run dev
    volumes:
      - ./src:/app/src
    ports: ["3000:3000"]

  web-prod:
    profiles: ["prod"]
    build:
      context: .
      target: runtime   # slim, no toolchain
    ports: ["8080:3000"]

Why this beats maintaining two Dockerfiles

A single multi-stage Dockerfile guarantees the base image, the language version and the system packages are identical across the stages you ship and the stages you develop against. Two separate Dockerfiles drift, and the drift is invisible until a production-only bug appears. The trade-off is that a target earlier than the last still builds every stage it depends on, so targeting deps does not avoid the cost of the base layers — it only avoids the final assembly.

2.4 pull_policy

Controlling when an image is fetched

By default Compose uses a local image if one exists and only pulls when it is missing — which is why postgres:17 can silently mean a months-old local copy. pull_policy makes that decision explicit and is one of the highest-value lines in a Compose file for reproducibility.

ValueBehaviour
alwaysPull on every up; fail if the pull fails.
neverNever pull; use only local images.
missingPull only if not present locally (the default).
buildBuild if the image is absent; never pull.
if_not_presentLegacy spelling of missing.
daily, weeklyPull if the local copy is older than that.
services:
  db:
    image: postgres:17.2
    pull_policy: always      # never accidentally run a stale local copy

  api:
    image: ghcr.io/acme/api:1.4.2
    pull_policy: missing

# shell equivalents for a one-off run
docker compose pull            # update every image
docker compose up -d --pull always

Pinning beats pulling

Pulling often is a mitigation; pinning is the cure. A tag such as 17 or latest is a moving pointer, so the container you tested and the container that restarts tomorrow are not guaranteed to be the same bytes. Pin a full version, and for anything security-sensitive pin the digest: postgres:17.2@sha256:.... The digest cannot change, so pull_policy becomes a performance question rather than a correctness one.

3 · Ports, Volumes and Bind Mounts

Publishing container ports with the short and long syntax, binding host addresses, the difference between named volumes and host bind mounts, and the read-only and tmpfs options that keep a container's filesystem honest.

3.1 Publishing ports

Short syntax and what it hides

The short form is [HOST_IP:][HOST_PORT:]CONTAINER_PORT[/PROTOCOL]. Compose fills in the missing pieces: no host IP means bind on all interfaces, no host port means publish a random free port, and no protocol means TCP. The short form is compact and covers ninety percent of cases, but it cannot express two things you sometimes need — a specific host IP and a port range mapped to a different range.

services:
  web:
    image: nginx:1.27
    ports:
      - "8080:80"                 # host 8080 -> container 80
      - "127.0.0.1:8081:80"       # loopback only, not the LAN
      - "8443:443/tcp"
      - "53:53/udp"
      - "9090-9091:8080-8081"     # ranges, mapped one-to-one
      - "80"                      # random free host port

Long syntax and the mode you almost never need

The long form names each field, which removes ambiguity and lets you set mode. On a single host mode: host is what actually happens; mode: ingress belongs to swarm's routing mesh and has no effect under plain Compose, so declaring it is a sign of a file copied from a swarm deployment.

services:
  web:
    image: nginx:1.27
    ports:
      - target: 80          # inside the container
        published: "8080"   # on the host
        host_ip: 0.0.0.0    # which interface to bind
        protocol: tcp
        app_protocol: http  # hint for tooling
        mode: host
Two containers cannot publish the same host port. This is the single most common reason --scale fails for a service with a fixed published port. Give the service an unpublished port and put a proxy in front, or publish a range.

3.2 Named volumes versus bind mounts

Two very different things wearing one syntax

Both write as source:target, but they are not interchangeable. A bind mount maps a path on the host into the container: the source is a real host path, your editor edits the files directly, and the container sees your latest save. A named volume is storage that Docker manages in its own area — the source is just a name, the path on the host is an implementation detail, and the data is created and owned by Docker.

Bind mountNamed volume
SourceHost filesystem pathDocker-managed name
Lives in the repoYes, it is your filesNo
Survives down -vYesNo, it is deleted
Portable across hostsNoYes
Typical useSource code, configDatabase data
services:
  api:
    build: .
    volumes:
      - ./src:/app/src          # bind: live code, edit and rerun
      - ./config/app.yml:/app/config/app.yml:ro

  db:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data   # named: persistent data

volumes:
  pgdata: {}   # declared, so it survives `docker compose down`

The long syntax and the empty-directory catch

The long form adds type, read_only and per-type options such as bind.propagation and volume.nocopy. One behaviour to internalize: when Docker mounts a named volume onto a container path that already contains files from the image, it copies those files into the fresh volume on first use. That is how a Postgres image initializes its data directory — and why a bind mount over that same path can appear to "lose" the image's files, because a bind mount never copies first.

volumes:
  - type: volume
    source: pgdata
    target: /var/lib/postgresql/data
    volume:
      nocopy: true          # skip the initial copy from the image
  - type: bind
    source: ./backups
    target: /backups
    read_only: true
    bind:
      create_host_path: true   # make the dir if missing (the default)

3.3 Read-only, tmpfs and mount options

Closing the writable surface

Most containers never need to write outside a few explicit locations. Mounting config as :ro and running the root filesystem read-only shrinks the blast radius of a compromised process and makes accidental writes fail loudly instead of persisting. The short syntax accepts a comma-separated option list after the target.

services:
  web:
    image: nginx:1.27
    read_only: true               # root filesystem is immutable
    tmpfs:
      - /var/cache/nginx
      - /run
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./html:/usr/share/nginx/html:ro
      - nginx-logs:/var/log/nginx:rw

tmpfs and SELinux sharing

A tmpfs mount is memory-backed and disappears with the container, which is perfect for socket directories, PID files and caches that must not touch disk. On SELinux hosts the :z and :Z options relabel the host path so the container is allowed to read it: :z shares one label across containers, :Z gives a private label to a single container. Omitting them on RHEL-family hosts produces a permission denied that looks like a filesystem bug.

volumes:
  - ./data:/data:z          # shared label, multiple containers
  - ./private:/private:Z    # private label, one container only
  - /tmp/sock:/var/run/app.sock:rw
If a container cannot see files it obviously should, check permissions and SELinux before checking your paths. On Docker Desktop the file-sharing settings for the drive can also silently drop a bind mount.

4 · Environment, Secrets and Profiles

Setting container environment variables, sourcing them from files, understanding the precedence order that decides who wins, mounting real secrets instead of baking passwords into env, and using profiles to keep optional services out of the default start.

4.1 environment

Mapping or list

environment accepts either a mapping or a list of KEY=value strings. The mapping form is clearer for fixed values; the list form with a bare key passes the value through from Compose's own environment, which is a shorthand you should use deliberately rather than by accident.

services:
  api:
    image: acme/api:1.4.2
    environment:
      NODE_ENV: production
      LOG_LEVEL: info
      CACHE_TTL: "300"          # quote numbers? YAML is fine, but quote to be safe
      # bare key: take the value from the shell/.env when Compose runs
      DATABASE_URL:
      FEATURE_FLAGS: "a,b,c"

Values are strings

Environment variables are always strings inside the container. YAML will happily parse CACHE_TTL: 300 as a number and Compose will coerce it, but a leading zero or a value like yes can be reinterpreted by YAML in surprising ways. Quoting anything that looks numeric or boolean is cheap insurance. An unset bare key resolves to an empty string rather than an error, which is why ${VAR:?} in the value is the better pattern when a variable is mandatory.

Do not confuse the two layers again: ${VAR} is interpolation performed by Compose on the file, while environment: is what the process inside the container reads via getenv. Interpolation happens once, at parse time, and the container never sees the original reference.

4.2 env_file and .env

Two files with confusingly similar names

These are different features and the names trip people up. The .env file at the project root is read by Compose to interpolate ${} references in the Compose file — it is Compose's own input. An env_file: entry on a service is read by Compose and handed to that container as its environment — it is the container's input. A value can appear in both, and it serves two different purposes.

# .env (project root) - feeds ${} interpolation in the file
TAG=1.4.2
DB_PASS=devpassword

# services/api.env - feeds container environment only
NODE_ENV=production
PORT=3000

# compose.yaml
services:
  api:
    image: ghcr.io/acme/api:${TAG}
    env_file:
      - services/api.env
      - path: services/api.local.env   # optional, ignored if absent
        required: false
    environment:
      PORT: "8080"                     # overrides the env_file value

Choosing env_file in v2

Newer Compose versions support the long form of env_file with path, required and format. That optional-file form is far better than committing a placeholder file just to satisfy a missing-file error. Keep secret values out of any env_file that is committed — use .env.local and a .gitignore entry, or move the truth into secrets:.

4.3 Precedence

Who wins inside the container

When the same key arrives from several places, the highest source in this list wins:

  1. docker compose run -e KEY=value on the command line.
  2. environment: in the Compose file (including a pass-through shell value).
  3. The env_file: files, in the order listed, later files overriding earlier ones.
  4. ENV instructions baked into the image by its Dockerfile.

The container's CMD and ENTRYPOINT do not read any of this until the process asks; a shell that refuses to inherit variables is a separate bug from this ordering.

Who wins inside the Compose file

Separately, interpolation (${}) reads from the shell environment, then from --env-file or the default .env. A shell export beats the file. On CI this is usually what you want — the pipeline exports TAG and it wins — but the same behaviour means a leftover export DB_PASS=old in a terminal quietly overrides your .env. Run docker compose config to see the resolved truth rather than the source files.

# shell - prove what actually won
docker compose config | grep -A5 environment
docker compose run --rm api env | sort

4.4 secrets and profiles

Secrets: files by default

A Compose secret is mounted as a file under /run/secrets/<name>, not exported as an environment variable. That matters because environment variables leak into docker inspect, crash reports and child processes far more readily than a file does. The source can be a host file or the value of an environment variable.

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
  api_token:
    environment: API_TOKEN        # read from Compose's environment

# Inside the container the value is at:
#   /run/secrets/db_password

Profiles: optional services, off by default

A service that declares profiles: does not start unless one of its profiles is active. Services with no profile always start. This lets one Compose file describe the whole system without forcing the debug tools, the admin UI and the migration runner on every developer.

services:
  api:
    image: acme/api:1.4.2          # always starts

  adminer:
    image: adminer:5
    profiles: ["tools"]            # only with --profile tools

  migrate:
    image: acme/api:1.4.2
    command: node dist/migrate.js
    profiles: ["migrate"]

  # shell
  # docker compose --profile tools up -d
  # docker compose run --rm migrate
  # COMPOSE_PROFILES=tools,migrate docker compose up -d

A service pulled in by depends_on from an active profile starts even if it has no profile of its own — dependencies override the filter. The wildcard --profile "*" starts every profiled service, which is occasionally useful in CI but almost never what a developer wants interactively.

5 · Networks and Service Discovery

The network Compose creates for every project, how to add your own to segment traffic, how DNS resolves a service name to the right container, and when to drop out of the model entirely with network_mode.

5.1 The default network

Created for you, named after the project

If a service does not declare a network, Compose attaches it to a project-wide bridge network called <project>_default. Every service in the project can reach every other service on that network by name. There is no configuration, and for a small stack there is no reason to add any.

# shell - see the network Compose made
docker network ls
# NETWORK ID   NAME            DRIVER   SCOPE
# 1a2b3c4d5e6f shop_default    bridge   local

docker network inspect shop_default --format '{{range .Containers}}{{.Name}} {{end}}'

Why the default is a user-defined bridge, not the legacy bridge

Containers on Docker's legacy bridge network cannot resolve each other by name; they only get IP addresses. User-defined bridge networks enable the embedded DNS server, so a service name is a hostname. That is the entire reason Compose defaults to a user-defined network and why "just use the default bridge" advice from 2016 is now actively harmful.

5.2 Custom networks

Segmenting on purpose

Declare additional networks when you want to separate traffic — typically a frontend that the proxy shares with the app, and a backend that only the app and the database share. A container only reaches another if they share at least one network, so segmentation is a real boundary, not a convention.

services:
  proxy:
    image: nginx:1.27
    networks: [frontend]

  api:
    image: acme/api:1.4.2
    networks: [frontend, backend]

  db:
    image: postgres:17
    networks: [backend]

networks:
  frontend: {}
  backend:
    internal: true      # no route to the outside world

volumes: {}

Options worth knowing

internal: true gives a network no gateway to the outside, so a compromised database container cannot phone home — but it also means that container cannot pull updates or reach a package mirror at runtime, so keep images self-contained. external: true joins a network created outside Compose, which is how you let two projects or a manually-run container talk to a stack. driver_opts passes driver-specific settings such as MTU or a specific bridge name.

networks:
  shared:
    external: true
    name: acme-shared        # the real name, since external skips the prefix
  tuned:
    driver: bridge
    driver_opts:
      com.docker.network.driver.mtu: "1400"

5.3 DNS by service name

The name is the hostname

On any user-defined network, Docker's DNS resolves a service's name to its container's IP. If a service is on several networks, it gets an address on each and the DNS answer is scoped to the network the asking container is attached to — which is precisely why segmentation works. Aliases add extra names.

services:
  db:
    image: postgres:17
    networks:
      backend:
        aliases: [postgres, database]   # extra DNS names

  api:
    image: acme/api:1.4.2
    networks: [backend]
    environment:
      # use the service name, not localhost and not an IP
      DATABASE_URL: postgres://app:secret@db:5432/app

What actually breaks name resolution

Three things routinely cause "could not resolve host" inside a stack. First, a service on only an internal network being asked to reach the public internet — the name resolves, but there is no route. Second, a hard-coded localhost: inside a container that means the container itself, never the host or a sibling. Third, overriding DNS with a custom dns: list can shadow Docker's embedded resolver for service names if you are careless. When in doubt, docker compose exec api getent hosts db tells you what the container's resolver actually returns.

5.4 network_mode

Leaving the Compose network model

network_mode replaces the whole networking setup for a service. It cannot be combined with networks: — Compose rejects the file if you try. The common values are host, none, service:<name> and container:<id>.

services:
  metrics:
    image: prom/node-exporter:v1.8.2
    network_mode: host        # sees the host's real interfaces
    pid: host

  debug:
    image: busybox:1.37
    network_mode: "service:api"   # share api's network namespace

Trade-offs

host mode removes the network boundary: the container shares the host's interfaces, so ports: is meaningless and two containers cannot both bind the same host port. It is occasionally necessary for tools that must see real interface counters, but it gives up Compose's DNS and isolation. service:<name> is the old "the container reaches a sibling at localhost" pattern, useful for a sidecar proxy, but it is fragile because you have now coupled two services by a namespace instead of by a hostname. Prefer normal networking and a service name in almost every case.

On Docker Desktop for Mac and Windows, network_mode: host does not behave like it does on Linux — it refers to the VM, not your laptop. Do not build workflows that depend on it being the real host.

6 · Dependencies, Health and Restarts

Ordering startup with depends_on and its conditions, using healthcheck to define what "ready" means, and picking a restart policy that survives a crash without fighting you during development.

6.1 depends_on and conditions

Start order is not readiness

The classic Compose trap: depends_on: [db] starts the database container before the app container, but starting is not the same as being ready to accept connections. Postgres takes a second or two to initialize; the app starts immediately and crashes with "connection refused". The fix is a condition, not a longer sleep.

ConditionWaits until
service_startedThe container has started (the default).
service_healthyIts healthcheck reports healthy.
service_completed_successfullyIt ran to completion with exit code 0.
services:
  api:
    image: acme/api:1.4.2
    depends_on:
      db:
        condition: service_healthy
        restart: true            # restart api if db is restarted
      migrate:
        condition: service_completed_successfully

  migrate:
    image: acme/api:1.4.2
    command: node dist/migrate.js
    depends_on:
      db:
        condition: service_healthy
    restart: "no"

  db:
    image: postgres:17
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

What depends_on does not do

It orders startup; it does not add retries to your application and it does not restart a crashed dependency. For robust stacks, combine a healthcheck with client-side retry in the app itself — a database that is healthy at boot can still be restarted later, and only the client knows how to reconnect. depends_on also has no effect on docker compose run beyond starting dependencies; it does not gate the command you asked to run.

The restart: true option on a dependency is worth noting: it makes Compose restart the dependent service when the dependency is updated or restarted explicitly. Without it, restarting the database leaves the app connected to a dead socket.

6.2 healthcheck

Defining what ready means

A healthcheck is a command Compose runs inside the container on a schedule. Exit code 0 means healthy, 1 means unhealthy, 2 is reserved. The container starts in the starting state, moves to healthy when the first success arrives, and flips to unhealthy after retries consecutive failures.

services:
  web:
    image: nginx:1.27
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost/healthz"]
      interval: 30s        # time between checks once running
      timeout: 5s          # a check that runs this long counts as failed
      retries: 3           # consecutive failures before unhealthy
      start_period: 20s    # grace period; failures here do not count
      start_interval: 5s   # faster checks during the start period

  queue:
    image: acme/worker:1.4.2
    healthcheck:
      disable: true        # explicitly opt out of any image-defined check

Writing a healthcheck that tells the truth

Two failure modes dominate. The first is a healthcheck that checks nothing useful — test: ["CMD", "true"] reports healthy for a process that is stuck. Check the thing the dependents actually need: an HTTP endpoint that hits the database, or pg_isready for Postgres, or a Redis PING. The second is a probe that is too aggressive: an interval of one second with no start_period marks a slow-starting container unhealthy before it has finished booting.

Use CMD-SHELL when you need shell features such as pipes or variable expansion and CMD (an argv array) when you do not, because CMD avoids a shell and is slightly faster and more predictable. Healthchecks are also what depends_on: service_healthy consumes, so a stack with no healthchecks can only ever order by "started".

6.3 restart policies

Four values, one good default

PolicyBehaviour
noNever restart (the default).
alwaysRestart on any exit, including a clean stop — which can be surprising.
on-failure[:n]Restart only on a non-zero exit, optionally at most n times.
unless-stoppedRestart on exit except when you stopped it yourself. Restarts after a daemon reboot.
services:
  api:
    image: acme/api:1.4.2
    restart: unless-stopped          # the sensible default for a service

  batch:
    image: acme/batch:1.4.2
    restart: "no"                    # one-shot job; do not resurrect it

  flaky:
    image: acme/flaky:1.4.2
    restart: on-failure:5            # give up after five crashes

Restart is not a supervision strategy

A restart policy recovers from a process that exits; it does nothing for a process that hangs while still running. That is what a healthcheck is for, and on a single host Compose does not automatically restart unhealthy containers — you would use docker compose up --wait to fail fast at startup and an external supervisor or a small script for ongoing cases. Also note that restart and a swarm-style deploy.restart_policy are different keys: set restart for plain Compose, and expect the swarm key to be ignored outside a swarm.

Do not put restart: always on a migration or seed job. It will run, exit and immediately run again, forever.

7 · Real Stacks

Three complete, runnable stacks that exercise the whole feature set: a Node application with PostgreSQL and Redis, an Nginx reverse proxy in front of an app, and a WordPress site on MySQL with a CLI helper.

7.1 Node, PostgreSQL and Redis

The stack

This is the shape most web services converge on: an application container, a relational database with a named volume, and a cache. The app waits for the database to be genuinely healthy, connects using the service name as the hostname, and keeps its data outside the container.

# compose.yaml - Node + PostgreSQL + Redis
name: shop

x-log: &log
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "3" }

services:
  api:
    build:
      context: .
      target: runtime
    image: ghcr.io/acme/shop-api:1.4.2
    <<: *log
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    environment:
      NODE_ENV: production
      PORT: "3000"
      DATABASE_URL: postgres://app:${DB_PASS:?set DB_PASS}@db:5432/shop
      REDIS_URL: redis://cache:6379
    ports:
      - "127.0.0.1:3000:3000"
    healthcheck:
      test: ["CMD", "node", "dist/healthcheck.js"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 15s

  db:
    image: postgres:17.2
    <<: *log
    restart: unless-stopped
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASS:?set DB_PASS}
      POSTGRES_DB: shop
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  cache:
    image: redis:7.4-alpine
    <<: *log
    restart: unless-stopped
    command: ["redis-server", "--save", "60", "1", "--loglevel", "warning"]
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

volumes:
  pgdata: {}
  redisdata: {}

Why it is arranged this way

The app binds to loopback only, so nothing on the LAN can reach it directly; a proxy or platform ingress is expected to sit in front. The database uses a named volume and reads any bootstrap SQL from ./db/init, a directory the official image executes once on an empty data directory. Redis is configured with a light snapshot and a real PING healthcheck so the app's depends_on actually waits for a working cache.

The x-log anchor is repeated into each service rather than written three times. Every log driver option here exists to stop a chatty container from filling the host disk, which is a real production incident and not a hypothetical one.

7.2 Nginx reverse proxy plus app

One published port, two containers

A reverse proxy is the standard way to terminate TLS and give several services one front door. The proxy is the only service with a published port; it reaches the app by service name over the shared network. TLS is handled by mounting certificates read-only, and ACME challenges are served from a mounted webroot.

# compose.yaml - Nginx in front of an app
name: edge

services:
  proxy:
    image: nginx:1.27-alpine
    restart: unless-stopped
    depends_on:
      app:
        condition: service_healthy
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./certs:/etc/nginx/certs:ro
      - ./acme-webroot:/var/www/acme:ro
      - proxylogs:/var/log/nginx
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost/healthz"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 10s

  app:
    build: ./app
    image: ghcr.io/acme/edge-app:2.1.0
    restart: unless-stopped
    expose:
      - "3000"                 # reachable on the network, not on the host
    environment:
      TRUST_PROXY: "1"
      BASE_URL: https://shop.example.com
    healthcheck:
      test: ["CMD", "node", "dist/healthcheck.js"]
      interval: 15s
      timeout: 3s
      retries: 3
      start_period: 10s

volumes:
  proxylogs: {}
# nginx/conf.d/shop.conf
server {
    listen 443 ssl;
    server_name shop.example.com;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    location /.well-known/acme-challenge/ {
        root /var/www/acme;
    }

    location / {
        proxy_pass         http://app:3000;   # service name, not an IP
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name shop.example.com;
    location / { return 301 https://$host$request_uri; }
}

The details that make it work

Nginx resolves app once at startup and caches the address. If the app container is recreated and gets a new IP, a running Nginx can keep sending traffic to the old address. Two mitigations: let a resolver do it dynamically, or simply recreate the proxy alongside the app. The expose: key on the app documents that port 3000 is intended for the internal network only — it does not publish it, and the app is unreachable from the host as a result.

7.3 WordPress and MySQL

The full stack

WordPress adds a second web-facing tier and a well-known set of environment conventions. The official images expect database credentials in environment variables and use named volumes for both the database and the uploads.

# compose.yaml - WordPress + MySQL + WP-CLI
name: blog

services:
  db:
    image: mysql:8.4
    restart: unless-stopped
    command:
      - --default-authentication-plugin=caching_sha2_password
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_unicode_ci
    environment:
      MYSQL_DATABASE: wordpress
      MYSQL_USER: wordpress
      MYSQL_PASSWORD: ${MYSQL_PASSWORD:?set MYSQL_PASSWORD}
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?set MYSQL_ROOT_PASSWORD}
    volumes:
      - dbdata:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s

  wordpress:
    image: wordpress:6.7-php8.3-apache
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_NAME: wordpress
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: ${MYSQL_PASSWORD:?set MYSQL_PASSWORD}
      WORDPRESS_CONFIG_EXTRA: |
        define('WP_HOME', 'http://localhost:8080');
        define('WP_SITEURL', 'http://localhost:8080');
        define('DISALLOW_FILE_EDIT', true);
    volumes:
      - wpdata:/var/www/html
      - ./themes/acme:/var/www/html/wp-content/themes/acme
      - ./plugins/acme:/var/www/html/wp-content/plugins/acme
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost/wp-login.php"]
      interval: 30s
      timeout: 5s
      retries: 5
      start_period: 40s

  cli:
    image: wordpress:cli-2.11-php8.3
    profiles: ["cli"]
    depends_on:
      wordpress:
        condition: service_healthy
    user: "33:33"                     # www-data
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_NAME: wordpress
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: ${MYSQL_PASSWORD:?set MYSQL_PASSWORD}
    volumes:
      - wpdata:/var/www/html
    working_dir: /var/www/html
    entrypoint: ["wp"]

volumes:
  dbdata: {}
  wpdata: {}

Running and using it

# shell - start the site, then use the CLI profile
export MYSQL_PASSWORD=devpass
export MYSQL_ROOT_PASSWORD=rootpass
docker compose up -d
docker compose --profile cli run --rm cli core install \
  --url=http://localhost:8080 \
  --title="Acme Blog" \
  --admin_user=admin \
  --admin_password=change-me \
  --admin_email=admin@example.com
docker compose --profile cli run --rm cli plugin list

Mounting only the custom theme and plugin keeps the rest of wp-content inside the named volume, so a rebuild of the image does not wipe uploads while your code still lives in git. The CLI service runs as the web user id because files it creates must be writable by Apache, and it is hidden behind a profile so it never starts during a normal up. The database healthcheck uses mysqladmin ping with the root password, which is the only reliable signal that MySQL is actually accepting logins rather than merely listening.

8 · The CLI Workflow

The commands you actually type every day: bringing a stack up and down, following logs, opening a shell, running one-off commands, inspecting status and validating configuration before it bites you.

8.1 up, down, ps and build

The core loop

# shell - the everyday loop
docker compose up -d                  # create/start in the background
docker compose up -d --build          # rebuild images first
docker compose up -d --force-recreate # throw away containers, keep images
docker compose up --wait              # block until healthy, or fail
docker compose ps                     # what is running
docker compose ps --format json       # machine-readable
docker compose stop                   # stop, keep containers
docker compose down                   # stop and remove containers + network
docker compose down -v                # also delete named volumes (data!)
docker compose down --rmi local       # also remove built images

What each command really does

up is idempotent: it creates only what is missing and recreates a container when its configuration changed. down removes containers, networks and the default network but deliberately leaves named volumes and images alone, because deleting data by default would be indefensible. stop and start preserve the containers, which is the fastest way to pause a stack while keeping its state.

The --wait flag is the one worth adding to every script. Without it up -d returns as soon as containers are created, so the next line of your script races the application's boot. With it, up blocks until services are healthy or the wait times out and the command exits non-zero.

# shell - remove orphans left by a renamed or deleted service
docker compose up -d --remove-orphans

# only build, do not run
docker compose build --pull --no-cache api
docker compose build --progress plain   # readable CI logs

8.2 logs, exec and run

Three different ways to get a shell or output

logs reads the aggregated stdout/stderr of the containers. exec runs a command in an already running container. run starts a new, one-off container from a service definition. Confusing the last two is the most common CLI mistake: exec fails with "container is not running" when the service is down, and run starts a second copy that may try to bind the same port or write to the same volume.

# shell - logs
docker compose logs                 # everything
docker compose logs -f api          # follow one service
docker compose logs --tail=100 -f   # last 100 lines, then follow
docker compose logs --since 10m db
docker compose logs --no-log-prefix api

# shell - exec into a running service
docker compose exec api sh
docker compose exec -u root web bash
docker compose exec db psql -U app -d shop
docker compose exec -T db pg_dump -U app shop > dump.sql   # no TTY, pipeable

# shell - one-off containers
docker compose run --rm api node scripts/report.js
docker compose run --rm --service-ports web            # publish its ports
docker compose run --rm -e LOG_LEVEL=debug api npm test
docker compose run --rm --no-deps api node -e "console.log(1)"

Things that save time

-T disables TTY allocation, which is required whenever you pipe output or run in CI; without it the CLI complains about a non-terminal. --no-deps stops run from starting the service's dependencies, which is what you want for a pure unit-test container. --service-ports is needed because run does not publish ports by default — a deliberate choice so a one-off container cannot collide with the running service.

8.3 config and validation

Resolve, then inspect

docker compose config renders the final document after interpolation, file merging and path resolution, and validates it against the schema. It is the single most useful debugging command in the tool: it shows you what Compose thinks you wrote, not what you think you wrote.

# shell - validate and inspect the resolved config
docker compose config                    # full resolved YAML
docker compose config --quiet            # exit code only, for CI
docker compose config --services         # list service names
docker compose config --volumes          # list top-level volume names
docker compose config --images           # list images the stack will use
docker compose config --profiles         # list declared profile names
docker compose config --hash="*"         # config hashes, for cache keys
docker compose config --format json      # machine-readable

Using it in CI

A single docker compose config --quiet in a pipeline catches the entire class of "the file does not parse" failures before a runner spins up any container, and it is cheap. Pair it with docker compose config --images to feed an image scanner, and with --hash to invalidate a cache only when the effective configuration really changed. Because config performs interpolation, run it with the same environment and --env-file the deployment uses, or the validation is testing a different document.

8.4 pull, images, stats and events

Inspecting and updating a running stack

# shell - update and inspect
docker compose pull                     # refresh all images
docker compose pull db                  # refresh one
docker compose push                     # push built images (needs image: set)
docker compose images                   # local images used by the project
docker compose top                      # host processes running in containers
docker compose stats --no-stream        # CPU/memory snapshot per container
docker compose events --json            # stream daemon events for the project
docker compose port web 80              # what host port mapped to 80
docker compose cp api:/app/logs ./logs  # copy files out of a container

A safe update sequence

To move a running stack to newer images without a surprise: pull first, then recreate, then check health. Running down and up is a larger hammer that drops the network and any anonymous volumes, and it briefly removes the ability of other things to resolve the services. For a single-host stack the routine is:

# shell - rolling-ish update on one host
docker compose pull
docker compose up -d --wait --remove-orphans
docker compose ps
# roll back by pointing TAG at the previous version and repeating
TAG=1.4.1 docker compose up -d --wait

docker compose events is underused. It streams what the daemon is doing — container created, started, died, network connected — with timestamps, which turns "it restarted at some point" into "it restarted at 03:14 with exit code 137", and exit code 137 is the signature of an out-of-memory kill.

9 · Multiple Files and Overrides

The automatic docker-compose.override.yml, layering several files with -f, reusing a service definition with extends, and the merge rules that decide what happens when two files define the same key.

9.1 The automatic override file

What Compose reads without being asked

If compose.yaml exists, Compose looks for compose.override.yaml and docker-compose.override.yml and merges them on top automatically. This is the intended place for developer-only settings — bind-mounting source for live reload, publishing extra ports, running a debug command — so that the base file stays production-shaped and is never edited just to develop.

# compose.yaml (committed - the real shape)
services:
  api:
    image: ghcr.io/acme/api:1.4.2
    restart: unless-stopped

# compose.override.yaml (committed or git-ignored - dev shape)
services:
  api:
    build: ./api                 # build locally instead of using the tag
    command: npm run dev
    environment:
      LOG_LEVEL: debug
    volumes:
      - ./api/src:/app/src       # live code
    ports:
      - "9229:9229"              # node inspector

Turning it off

The automatic merge is convenient and occasionally dangerous: a CI job that expects the base file gets dev settings if the override is present. Pass an explicit -f list to suppress discovery, or set COMPOSE_FILE to pin the exact set. A file named exactly compose.override.yaml is the only one auto-loaded; a second override is not.

# shell - ignore the override and use only the base file
docker compose -f compose.yaml config

# or pin the set for everyone in the environment
export COMPOSE_FILE=compose.yaml:compose.prod.yaml

9.2 Layering with -f

Files apply left to right

Passing several -f flags builds one document by merging each into the result, later files winning. This is how you keep a base, a local override and a production overlay separate instead of maintaining three near-identical files.

# shell - base + local, or base + prod
docker compose -f compose.yaml -f compose.local.yaml up -d
docker compose -f compose.yaml -f compose.prod.yaml up -d

# equivalently, via COMPOSE_FILE (colon-separated on Linux/macOS,
# semicolon-separated on Windows)
COMPOSE_FILE=compose.yaml:compose.prod.yaml docker compose up -d

Ordering and the override gotcha

Order is the whole semantics. -f base.yaml -f prod.yaml means "base, then prod on top", which is almost always what you mean. Reversing the order silently inverts everything. Note also that an explicit -f disables the automatic compose.override.yaml lookup, so if you add -f to a developer workflow, you must list the override yourself.

9.3 extends

Reusing a service definition

extends copies the configuration of another service, either in the same file or in another file. It is a text-level reuse mechanism, not a runtime relationship: there is no dependency created, only settings inherited. It is the right tool when several services share a near-identical block but are otherwise independent.

# compose.yaml
x-service: &service
  restart: unless-stopped
  logging: { driver: json-file, options: { max-size: "10m" } }

services:
  api:
    <<: *service
    image: acme/api:1.4.2
  api-canary:
    <<: *service
    image: acme/api:1.5.0-rc1
  worker:
    extends:
      file: common.yaml
      service: base-worker
    command: node dist/worker.js
# common.yaml
services:
  base-worker:
    image: acme/api:1.4.2
    restart: unless-stopped
    environment:
      QUEUE: default
    volumes:
      - work:/work
volumes:
  work: {}

extends versus YAML anchors

Both remove duplication and they solve different problems. A YAML anchor works only inside one file and is resolved by the YAML parser before Compose sees anything. extends crosses files and is resolved by Compose, so it can pull a block from a shared repository file. The catch: extends cannot inherit depends_on, links or volumes_from, and a few keys are restricted. When you only need to share a few keys in one file, an anchor is simpler and has no restrictions.

9.4 Merge rules

Scalars replace, mappings merge, lists append

Getting the merge rules right is what makes multi-file setups predictable rather than spooky.

Field typeRuleExample
Scalar (image, restart, command)Later file replacesrestart: value is overwritten
Mapping (environment, labels, build.args)Merged by keyNew keys added, duplicates replaced
Unique-resource list (ports, volumes, secrets)Merged by key, then combinedVolumes key on target path
Plain sequence (dns, expose, env_file)AppendedBoth files' entries present
Shell commandReplaced, not appendedcommand: fully overrides
# base
services:
  api:
    environment: { A: "1", B: "2" }
    ports: ["8080:80"]
    command: ["node", "server.js"]

# override
services:
  api:
    environment: { B: "9", C: "3" }
    ports: ["9090:80"]

# result
#   environment: A=1 B=9 C=3     (merged, later key wins)
#   ports: ["8080:80", "9090:80"] (both kept: different published ports)
#   command: fully replaced

Forcing the merge in a direction

Because appending is the default for lists, you sometimes cannot remove an entry from a base file with an override. Compose provides explicit tags for exactly this, and they are the modern answer to a problem people used to solve with duplicate files.

# override that removes a base port and replaces the list outright
services:
  api:
    ports: !reset []
    environment: !override { A: "only-this" }

!reset clears a field so the base value is discarded and the file's own value, if any, is used. !override replaces the base value entirely instead of merging into it. Use them sparingly — a stack whose final configuration depends on two merge tags in a third file is hard to reason about — but when you need to delete an inherited entry, they are the only clean way.

10 · Production, Scaling and Watch

Resource limits, the deploy block and replicas on a single host, why scaling collides with published ports, and the file-watch workflow that quietly fixes the worst part of local development.

10.1 Resource limits

Constrain the container, protect the host

Without limits, one runaway service can consume all the memory on the host and get other containers or the Docker daemon itself killed. Compose expresses limits in two places and it is worth knowing which applies where.

services:
  api:
    image: acme/api:1.4.2
    mem_limit: 512m            # plain-Compose limit
    memswap_limit: 768m        # hard cap including swap
    cpus: 1.5                  # max CPU cores
    pids_limit: 200            # fork-bomb protection
    oom_kill_disable: false
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }

  # the deploy form is what Compose honours in a swarm,
  # and modern Compose also maps it on a single host
  worker:
    image: acme/worker:1.4.2
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 1g
        reservations:
          cpus: "0.25"
          memory: 256m

Limits versus reservations

A limit is a ceiling the kernel enforces: exceeding the memory limit triggers the OOM killer and the container dies with exit code 137. A reservation is a hint about the minimum needed, used by a scheduler for placement; on a single host it has much less effect. Set limits from measurements, not guesses — a limit lower than the application's peak working set converts a slow service into a crashing one, and the crash looks like an application bug until someone checks the container's exit code.

If a container restarts periodically with no application error, check docker compose events and docker inspect --format '{{.State.OOMKilled}}' before blaming the code.

10.2 The deploy block and replicas

What Compose honours without a swarm

The deploy block originated for swarm and Kubernetes-style semantics, and Compose now implements the parts that make sense on one host: replicas, resources.limits, restart_policy, update_config and placement.constraints. Other keys, such as mode: global or the ingress endpoint mode, only take effect under a real orchestrator.

services:
  api:
    image: ghcr.io/acme/api:1.4.2
    deploy:
      replicas: 3
      update_config:
        order: start-first
        parallelism: 1
        delay: 10s
        failure_action: rollback
      restart_policy:
        condition: on-failure
        delay: 5s
        max_attempts: 3
      placement:
        constraints:
          - node.role == worker
    # NOTE: no `ports:` here - see 10.3

replicas versus --scale

deploy.replicas is the declared desired count; docker compose up --scale api=5 overrides it for that run. The scale flag is applied at up time and is not persisted into the file, so a later up without it reverts to the declared number. Replicas of the same service share the service's configuration, so anything that must differ per replica has to come from the environment or from a mounted file.

10.3 Scaling and host-port conflicts

The error everyone meets once

Scaling a service that publishes a fixed host port fails, because only one process can bind a given host port. Compose reports a bind error and the second replica never starts.

# fails: "Bind for 0.0.0.0:8080 failed: port is already allocated"
services:
  api:
    ports: ["8080:3000"]     # a fixed host port
# docker compose up -d --scale api=3   -> error

# works: publish no host port (or a range) and put a proxy in front
services:
  api:
    expose: ["3000"]         # internal only
    # or, for a quick local test, let Docker choose: - "3000"
  proxy:
    image: nginx:1.27
    ports: ["8080:80"]

# shell
docker compose up -d --scale api=3
docker compose ps                     # three api containers, one proxy

Why a proxy is the real answer

Removing the host port makes the replicas start, then creates the next problem: how does traffic reach one of three containers by a stable name? Docker DNS round-robins across replicas of a service on a user-defined network, which is enough for many cases, but a proxy that can retry a failed backend is more robust. The proxy is the only service with a published port, and it forwards to the service name, which now resolves to whichever replica the resolver picks.

Scaling is per service, and a database usually should not be scaled this way. Multiple Postgres containers sharing one data volume is corruption, not redundancy. Scale the stateless tier.

10.4 Watch mode and develop

Rebuild on change, without thinking about it

docker compose watch watches the files a service declares under develop.watch and reacts to changes. The three actions are sync (copy a changed file into the container), rebuild (rebuild the image and recreate the container) and sync+restart (sync, then restart the process). It replaces the two worst local-development habits: remembering to restart, and bind-mounting everything.

services:
  api:
    build: ./api
    develop:
      watch:
        - action: sync
          path: ./api/src
          target: /app/src
          ignore:
            - "**/*.test.ts"
        - action: sync+restart
          path: ./api/config
          target: /app/config
        - action: rebuild
          path: ./api/package.json

# shell
docker compose watch
docker compose up --watch          # same, as part of up

Why watch beats a blanket bind mount

A bind mount of the source directory into the container shadows the dependencies the image installed — the classic "cannot find module" after mounting because node_modules was replaced by an empty host directory. Watch mode syncs only the paths you name, so the image's installed dependencies stay where they are, and CPU-heavy builds use the image's own toolchain rather than the host's. Reach for rebuild only for inputs that genuinely require a new image, such as a changed dependency manifest or a Dockerfile; use sync for ordinary source edits.

11 · Troubleshooting and Best Practices

The error messages you will actually see and what each one means, why a stack drifts away from the image you thought you were running, the truth about links, and the habits that keep a Compose project healthy.

11.1 Common errors and what they mean

The short list

MessageCause and fix
port is already allocatedAnother container or process holds the host port. Change it, or find the holder with docker ps.
no configuration file providedNo Compose file in the directory or upstream. Run from the right folder or pass -f.
dependency failed to startA service_healthy dependency never became healthy. Read the dependency's logs.
service "x" is unhealthyThe healthcheck failed. Check its command and start_period.

# shell - diagnose, in the order that finds answers fastest
docker compose config                     # did the file resolve as intended?
docker compose ps -a                      # exited containers are still here
docker compose logs --tail=200 api        # the service that failed
docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}' \
  "$(docker compose ps -q api)"
docker compose events --json              # what the daemon actually did
docker compose exec db getent hosts api   # can it resolve its neighbours?

Reading an exit code

Exit code 0 is a clean exit — for a one-shot container that is success, for a long-running service it means it returned when it should have kept running. 137 is SIGKILL, usually the OOM killer. 143 is SIGTERM, a normal stop. 1 is a generic application failure whose real message is in the logs. The distinction between 137 and 1 is exactly the difference between "give it more memory" and "fix the bug", and it is worth checking before reading a single line of application output.

11.2 Image drift

The stack that is not the stack you tested

Image drift is the slow divergence between what the Compose file appears to say and what actually runs. Three mechanisms cause it, and all three are silent.

  • Mutable tags. latest, 3 and stable are pointers that move. A rebuild pull returns different bytes than last week.
  • Locally cached images. With the default missing pull policy, Compose never checks the registry, so a stale local copy runs indefinitely.
  • Images built locally under the same tag as a published one. Your development build shadows the registry image and no one notices until a different machine behaves differently.
# shell - detect and prevent drift
docker compose images                        # digests of what is in use
docker inspect --format '{{index .RepoDigests 0}}' postgres:17.2
docker compose pull --dry-run                # what would change
docker compose up -d --pull always --wait

# prevent it: pin a digest, not a tag
#   image: postgres:17.2@sha256:8f7b1d2c... 
# and record the digests in a lockfile-style file in the repo

Why the digest is the only stable identity

A tag is a human convenience; the digest is the content address of the exact image manifest. Pinning @sha256:... means the same bytes every time, on every machine, forever, and makes pull_policy a performance concern rather than a correctness one. The trade-off is that updates become an explicit, reviewable pull request that changes the digest, which is precisely the point: an update should be a decision, not something that happens during a lunchtime restart.

11.3 The links myth

links is legacy, and unnecessary

links dates from Compose v1, before user-defined networks had an embedded DNS server. Back then a service could not resolve another by name, so links created an alias and an environment-variable entry. On any current network, Docker resolves service names automatically, so links adds nothing except a deprecated field that keeps generating warnings and, worse, an environment variable that applications still read and that pins them to an old topology.

# legacy - delete this
services:
  api:
    links:
      - db            # creates DB_PORT_5432_TCP_ADDR etc. in the env

# current - the network already provides name resolution
services:
  api:
    networks: [backend]
  db:
    networks: [backend]
# the app connects to  db:5432  with no link declaration at all

What to use instead

Use the service name as the hostname. If you want an additional name, use a network alias. If you want a container to share another's network namespace — the one thing links approximated — use network_mode: "service:name" and understand that you have given up isolation to do it. The correct migration for a links declaration is deletion, followed by a check that nothing in the application was reading the generated *_PORT_* variables.

If an application code path still reads DB_PORT_5432_TCP_ADDR, the fix belongs in the application, not in a resurrected links entry.

11.4 Best practices

The short, high-value list

  1. Pin everything. Images to a full version or a digest; base images the same. A pin is documentation.
  2. Never bake secrets into an image or a committed file. Use secrets: or an untracked .env.local, and keep .env out of version control if it holds anything real.
  3. Healthcheck every service that others depend on and use condition: service_healthy. Sleeps are lies.
  4. Default to restart: unless-stopped on long-running services and restart: "no" on jobs.
  5. Declare named volumes explicitly and know which of them down -v will delete.
  6. Do not set container_name unless you truly need the name; it blocks scaling and collides across projects.
  7. Set a log driver with a size cap. An unbounded json-file log is a disk-full incident waiting for a busy day.
  8. Validate in CI with docker compose config --quiet, and scan with --images.
  9. Keep the base file production-shaped and put developer conveniences in an override, never the other way round.
  10. Segment networks so the database is not reachable from the thing that faces the internet.
# a CI check worth its bytes
set -e
docker compose config --quiet                 # parses and validates
docker compose config --images | sort -u      # feed to a scanner
docker compose build --pull
docker compose up -d --wait --remove-orphans
docker compose ps
docker compose down -v

Growing out of Compose well

Compose is a single-host tool, and the moment a project needs several hosts, zero-downtime rolling updates across them, or a control plane that heals a failed node, the honest answer is an orchestrator. The graceful path is to keep the Compose file as the source of truth for the development environment and to generate or hand-write the orchestration manifests from the same service boundaries. The worst path is to keep adding shell scripts around Compose until it is an unmaintainable scheduler — at that point the requirements have outgrown the tool, and stretching it further only delays the migration.

12.3 Reusable patterns

Three shapes worth copying

# 1. shared defaults via an extension field
x-defaults: &defaults
  restart: unless-stopped
  logging: { driver: json-file, options: { max-size: "10m" } }
services:
  a: { <<: *defaults, image: acme/a:1.0 }
  b: { <<: *defaults, image: acme/b:2.0 }

# 2. a health-gated dependency chain
services:
  migrate:
    image: acme/api:1.4.2
    command: node dist/migrate.js
    depends_on: { db: { condition: service_healthy } }
    restart: "no"
  api:
    image: acme/api:1.4.2
    depends_on:
      migrate: { condition: service_completed_successfully }

# 3. an optional debug tool behind a profile
services:
  adminer:
    image: adminer:5
    profiles: ["tools"]
    ports: ["8081:8080"]

Final advice

Treat the Compose file as code: review it, validate it in CI, pin its images and keep secrets out of it. The file is the single description of how the system is wired, and everything downstream — local development, the test environment, the single-host deployment — is more reliable when that description is exact and boring. When it stops being enough, that is a signal to move up a level of tooling, not to add another script around it.
