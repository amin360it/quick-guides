1 · Getting Started

1.1 Installing Laravel1.2 The directory structure that matters1.3 The request lifecycle1.4 Artisan: your command centre

Gets a working Laravel application running and explains the request lifecycle. You install the framework, meet the Artisan command line, and trace how a request enters the front controller, passes middleware and routing, and returns a response. This foundation shows where almost every framework feature plugs in.

Laravel is a batteries-included PHP framework built around a small set of ideas: a routing layer, a container, Eloquent, and convention over configuration. This chapter gets a working app running and teaches the request lifecycle you’ll rely on forever.

1.1 Installing Laravel

Shows the two ways to create a new Laravel project: the Laravel installer through composer create-project laravel/laravel or the laravel new command. Either path gives you a fully bootstrapped application ready to serve. Run php artisan serve to finish with a working site on port 8000.

# Option A: the Laravel installer (fastest)
composer global require laravel/installer
laravel new blog        # answer the prompts (starter kit, testing, DB)

# Option B: Composer directly
composer create-project laravel/laravel blog

cd blog
php artisan serve       # http://127.0.0.1:8000
php artisan about       # environment summary

Both options produce a working Laravel app, then php artisan serve starts the local development server on port 8000.

1.2 The directory structure that matters

Maps the directories you touch day to day, such as routes, app for controllers and models, database for migrations and seeders, and resources for views. Knowing where each kind of file lives is half of mastering Laravel conventions. Most placement decisions come with a default answer.

PathWhat lives there
routes/web.php (browser), api.php (JSON), console.php
app/Models/Eloquent models
app/Http/Controllers/Controllers
resources/views/Blade templates
database/migrations/Schema version control
config/Framework configuration
.envEnvironment-specific secrets and settings

1.3 The request lifecycle

Traces a browser request through the Laravel lifecycle: the public index.php front controller, application bootstrap, middleware, route matching, controller logic, and finally the response returned to the client. Understanding this pipeline makes debugging easier because you can localize each failure to a single stage. Almost every framework problem lives somewhere in this chain.

Browser request
  -> public/index.php        (front controller)
  -> HTTP Kernel             (global middleware)
  -> Router                  (matches a route)
  -> Route middleware        (auth, throttle, ...)
  -> Controller / Closure
  -> Response
  -> Middleware on the way out
  -> Browser

This is the journey a request takes through the framework, out to the controller and back through middleware, and locating your position in the chain explains most problems.

Every "why is my middleware not running" question is answered by locating where you sit in this chain.

1.4 Artisan: your command centre

Introduces Artisan, the command line interface built into every Laravel application. Commands such as make:controller, make:model, and make:migration scaffold files, while migrate, tinker, route:list, and test handle schema, debugging, and testing. It is your everyday companion from the very first chapter.

php artisan list                 # every command
php artisan make:controller PostController
php artisan make:model Post -mcr # model + migration + controller + resource
php artisan route:list           # inspect all routes
php artisan migrate              # run migrations
php artisan tinker               # REPL with your app booted

These Artisan commands generate code and run migrations, so most everyday Laravel work starts here. The -mcr flag scaffolds a model, migration, controller, and resource routes at once.

2 · Routing, Views & Blade

2.1 Defining routes2.2 Blade basics2.3 Layouts, components and slots2.4 Named routes, redirects and URLs

Covers routing, the Blade templating engine, layouts, and named routes. These are the core building blocks behind every page your application renders, connecting URLs to logic and to HTML output. Master them and you can build anything from a simple landing page to a multi-section dashboard.

2.1 Defining routes

Shows how to define routes in the routes directory using URL and action pairs, with support for parameters, constraints, prefixes, and groups. Route definitions stay small and readable in routes/web.php and usually point to controllers that hold the real logic. Review the full map anytime with php artisan route:list.

use Illuminate\Support\Facades\Route;

Route::get('/', fn () => view('welcome'));

Route::get('/posts/{post}', function (string $post) {
    return "Post: {$post}";
})->whereNumber('post');        // constrain {post} to digits only

Route::prefix('admin')->name('admin.')->middleware('auth')->group(function () {
    Route::get('/dashboard', [DashboardController::class, 'index'])->name('dashboard');
});   // all admin routes sit behind auth and get the admin. name prefix

Routes map URLs to closures or controllers. whereNumber constrains the route parameter, and the admin group shows prefixing, naming, and the auth middleware in one go.

2.2 Blade basics

Introduces Blade, the templating engine that compiles view files into plain PHP. Use directives such as @foreach, @if, and @section to write loops, conditionals, and layout output with readable syntax. Blade escapes echoed variables automatically, which defends your pages against cross site scripting.

{{-- resources/views/posts/index.blade.php --}}
@extends('layouts.app')

@section('content')
  <h1>{{ $title }}</h1>

  {{-- loops and conditionals --}}
  @forelse ($posts as $post)
    <article>
      <h2>{{ $post->title }}</h2>
      <p>{{ Str::limit($post->body, 140) }}</p>
    </article>
  @empty                  {{-- fallback rendered when there are no posts --}}
    <p>No posts yet.</p>
  @endforelse
@endsection

This Blade view extends a layout and loops over posts with @forelse, which has a built-in empty state. Output inside double braces is escaped automatically.

{{ }} escapes output automatically. Only use {!! !!} when you truly trust the content — that is the XSS door.

2.3 Layouts, components and slots

Shows how to compose reusable user interfaces with layouts, components, and slots. A parent layout defines the shared HTML shell while child views fill named sections, and components wrap repeated markup. Slots pass content into a component so it behaves like a custom tag and keeps your views DRY.

{{-- components/alert.blade.php --}}
<div class="alert alert-{{ $type }}">
  {{ $slot }}          {{-- holds the content passed between the component tags --}}
</div>

{{-- usage --}}
<x-alert type="warning">Careful!</x-alert>

{{-- anonymous component with attributes --}}
<x-button :disabled="$saving">Save</x-button>

Components combine markup with a $slot, and attributes like type flow into the component. Anonymous components simply live in resources/views/components.

2.4 Named routes, redirects and URLs

Covers named routes and the helper functions that generate their URLs. Give a route a name with the name method, then reference it through the route helper in redirects, links, and form actions. Naming routes means your URLs survive changes without breaking every reference.

return redirect()->route('admin.dashboard');   // redirect by route name, not URL
$url = route('posts.show', ['post' => 7]);   // /posts/7
// In Blade: {{ route('posts.show', $post) }}

Route helpers generate URLs and redirects from route names instead of hardcoded paths, so changing a URL later only touches one route definition.

3 · Controllers, Requests & Responses

3.1 Resource controllers3.2 Reading the request3.3 Responses and helpers3.4 Form requests

Moves logic out of route closures and into controllers, and explains requests and responses. You will validate incoming input, handle form submissions, and shape output with view, json, and redirect helpers. Controllers keep routes declarative and put business behavior somewhere testable.

3.1 Resource controllers

Scaffolds a full set of CRUD routes and controller methods with one command. The artisan make:controller PostController -r command generates the seven conventional methods, and Route::resource wires them to REST style URLs. Review the generated routes with route:list and customize only what your app actually needs.

php artisan make:controller PostController --resource --model=Post   # generate the CRUD methods

// routes/web.php
Route::resource('posts', PostController::class);   // registers every CRUD route

One make:controller command scaffolds the full CRUD pattern, and a single Route::resource line registers all its routes with conventional URLs and names.

A resource controller gives you index, create, store, show, edit, update, destroy with conventions for names and URLs.

3.2 Reading the request

Shows how to read validated input from the incoming request. Type hint Illuminate\Http\Request in a controller method and use methods such as all, input, query, and collect to fetch submitted values. The validate helper and FormRequest classes authorize and validate data before your action ever runs.

public function store(Request $request)
{
    $data = $request->validate([      // fails? redirects back with errors
        'title' => ['required', 'string', 'max:255'],
        'body'  => ['required', 'string'],
    ]);

    $post = Post::create($data);      // mass-assign the validated fields

    return redirect()->route('posts.show', $post);   // PRG: redirect after a write
}

The store method validates input, creates the model in one line, and redirects to the new post. Validation failure bounces the user back with error messages.

3.3 Responses and helpers

Lists the common response helpers for shaping output in controllers. Use view for Blade templates, json for API data, redirect for safe post redirect get flows, and response download for files. Choosing the right helper keeps controller code short and makes the result of every action obvious.

return view('posts.show', compact('post'));
return response()->json($post, 201);          // 201 = Created
return redirect()->back()->with('status', 'Saved!');   // flash, survives one request
return response()->download($path);

These four lines cover the responses you will reach for daily: views, JSON with status codes, redirects with flash data, and file downloads.

3.4 Form requests

Moves validation out of the controller and into its own class. Generate one with php artisan make:request, define rules in its rules method and messages in messages, then type hint the form request directly in your controller method. Controllers stay thin and the same validation rules remain reusable across actions.

php artisan make:request StorePostRequest

public function rules(): array
{
    return [
        'title' => ['required', 'string', 'max:255'],
        'body'  => ['required', 'string', 'min:10'],   // enforce a minimum length
    ];
}
// Then: public function store(StorePostRequest $request)

A form request moves validation rules into their own class, keeping controllers thin. Type-hinting it in a method signature validates and authorizes automatically.

4 · Eloquent ORM & Migrations

4.1 Migrations: schema as version control4.2 Models and relationships4.3 CRUD and query building4.4 Casts, accessors and scopes

Introduces the Eloquent ORM and migrations for database work. Migrations version your schema, models represent tables as objects, and relationships express joins as method calls. You will write expressive queries, seed sample data, and keep every developer database in sync with an exact shared schema.

4.1 Migrations: schema as version control

Shows how to version your database schema with migration files. Each migration defines up and down methods that apply and reverse a change, and php artisan migrate runs all pending migrations in order. The whole team can rebuild the exact same schema on any machine by simply running migrate.

php artisan make:migration create_posts_table

Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();   // FK with index
    $table->string('title');
    $table->text('body');
    $table->timestamps();
    $table->softDeletes();   // adds a deleted_at column for soft deletes
});

This migration defines the posts schema, including a foreign key to users and a soft-deletes column. Applied with php artisan migrate, it becomes the source of truth for the schema.

4.2 Models and relationships

Introduces Eloquent models and the relationships you define on them with methods such as hasMany, belongsTo, and belongsToMany. Eager loading with the with method avoids slow N+1 queries when models reference each other. Table and primary key names follow conventions automatically, so model classes stay tiny.

class Post extends Model
{
    protected $fillable = ['title', 'body'];   // fields allowed for mass assignment

    public function user(): BelongsTo { return $this->belongsTo(User::class); }
    public function tags(): BelongsToMany { return $this->belongsToMany(Tag::class); }
}

$posts = Post::with('user', 'tags')->latest()->paginate(20);   // eager load, then paginate

A model ties a table to relationships and controls mass assignment via $fillable. The query eagerly loads both relationships and paginates in one readable line.

Eager loading (with()) is the single biggest performance fix in Laravel. Watch for N+1 queries in the debug bar.

4.3 CRUD and query building

Demonstrates create, read, update, and delete through Eloquent and the query builder. Chain fluent methods like where, orderBy, and get to build queries that read like sentences, then persist with methods such as create, update, and delete. Mass assignment protection keeps records safe from unexpected form fields.

$post = Post::create(['title' => 'Hi', 'body' => '...']);

$post->update(['title' => 'Updated']);
$post->delete();                    // soft delete if trait present

$published = Post::where('published', true)
    ->whereHas('tags', fn ($q) => $q->where('name', 'php'))   // only posts with this tag
    ->orderByDesc('created_at')
    ->get();

Creating, updating, and deleting happen through the model, while whereHas filters by a related model’s field. Every method uses bound queries, so there is no SQL injection.

4.4 Casts, accessors and scopes

Covers casts, accessors, and query scopes for cleaner models. Casts convert column values automatically, such as turning JSON strings into arrays, while accessors and mutators shape attribute values in and out. Define scopes with the scope prefix to package common query filters into reusable model methods.

protected function casts(): array
{
    return ['published_at' => 'datetime', 'meta' => 'array'];   // auto-convert on read and write
}

public function scopePublished(Builder $q): void
{
    $q->whereNotNull('published_at')->where('published_at', '<=', now());
}
// Post::published()->get();

Casts convert column values to PHP types automatically, while scopes wrap common filters so queries read like Post::published()->get().

5 · Validation, Forms & Files

5.1 The validation toolbox5.2 Repopulating forms5.3 File uploads

Covers validation rules, repopulating forms with old input, and handling file uploads. Solid server side validation is the difference between robust and brittle forms. You will define rule arrays, surface field errors, and safely store uploaded files with the Laravel storage system.

5.1 The validation toolbox

Shows the validation rule toolbox for emails, numbers, arrays, and files. Rules such as required, email, min, max, unique, and array read like a contract describing what the data must look like. Combine them into rule arrays and pass them to the validate helper or a FormRequest.

$request->validate([
    'email'    => ['required', 'email', 'unique:users,email'],
    'age'      => ['nullable', 'integer', 'between:13,120'],
    'avatar'   => ['nullable', 'image', 'max:2048'],   // max size is in kilobytes
    'tags'     => ['array', 'max:5'],
    'tags.*'   => ['string', 'distinct'],              // each tag must be different
]);

This validate call defines rules for each field, including uniqueness, ranges, and upload size. The unique rule automatically checks the users table’s email column.

5.2 Repopulating forms

Explains how to repopulate form fields after a validation failure. The old helper returns the previously submitted value for a field, and the @error directive shows the matching validation message. Together they prevent users from retyping every input after a single mistake.

<input name="email" value="{{ old('email') }}">   {{-- keeps the value after a failed submit --}}
@error('email') <p class="error">{{ $message }}</p> @enderror

{{-- CSRF token is mandatory for POST/PUT/DELETE --}}
<form method="POST" action="/posts">
  @csrf             {{-- hidden token required on every POST --}}
  ...
</form>

old() repopulates the input after a failed validation, and @error prints one message per field. The @csrf token is mandatory on every POST form.

5.3 File uploads

Shows how to handle uploaded files safely with the Laravel storage system. Validate declared type and size before accepting a file, then persist it with the store and storeAs methods on the request. Generate safe storage names and never trust the client supplied filename.

if ($request->hasFile('avatar')) {
    $path = $request->file('avatar')->store('avatars', 'public');   // store on the public disk
    // store path; serve via php artisan storage:link
}

Uploaded files are stored on the public disk under avatars, and a symlink makes them web-reachable. The returned path is what you save in the database.

Always validate file type and size. Never trust the client-provided filename — Laravel generates safe names for you.

6 · Authentication & Authorization

6.1 Starter kits6.2 Guards and protecting routes6.3 Gates and policies6.4 Roles and permissions

Covers authentication with starter kits and authorization with gates and policies. Starter kits such as Breeze provide login, registration, and password reset out of the box, while the auth middleware protects your routes. Gates and policies enforce exactly who may perform each action in your application.

6.1 Starter kits

Installs Breeze to get login, registration, password reset, and more in minutes. Run php artisan breeze:install, pick your stack, then migrate and compile the shipped frontend assets. Jetstream is the step up when you need teams, API tokens, and two factor authentication.

composer require laravel/breeze --dev
php artisan breeze:install blade   # or vue / react / livewire
php artisan migrate                # build the auth tables

Installing Breeze and running its installer drops in complete login, registration, and profile scaffolding in minutes, then migrate builds the auth tables.

Breeze gives login, registration, password reset, email verification and profile management in minutes. Fortify/Jetstream add two-factor and team features.

6.2 Guards and protecting routes

Shows how to protect routes with the auth middleware and read the current user. Add auth middleware to guard routes, then use the Auth facade or auth helper to fetch the logged in user. Guards decide how users are authenticated, such as the session based web guard or token based guards for APIs.

Route::middleware('auth')->group(function () {   // every route inside requires login
    Route::get('/dashboard', DashboardController::class);
});

auth()->user();          // current user (or null)
auth()->id();
Auth::check();

Wrapping routes in the auth middleware blocks guests, while the auth() helper gives you the current user anywhere in the app.

6.3 Gates and policies

Introduces policies and gates for authorization rules. Generate a policy with php artisan make:policy to keep a model’s permission checks together, or define gates with Gate::define for simpler app wide rules. Enforce them with the can and cannot methods in controllers and the @can directive in views.

php artisan make:policy PostPolicy --model=Post

public function update(User $user, Post $post): bool
{
    return $user->id === $post->user_id;   // only the author passes
}

// In controller:
$this->authorize('update', $post);
// In Blade: @can('update', $post) ... @endcan

The policy method answers one question: may this user edit this post? authorize() in the controller and @can in Blade enforce the same rule in two places.

6.4 Roles and permissions

Compares a simple role column on the users table with the spatie permissions package. A role string with a small helper covers small apps, while the package adds roles and permissions tables with helpers such as hasRole and givePermissionTo. Pick the simplest option that still covers your needs.

For simple apps a role column plus gates is enough. For complex needs use spatie/laravel-permission (roles, permissions, teams). Resist inventing your own ACL until you’ve outgrown the two above.

7 · Middleware, Sessions & Cookies

7.1 Writing middleware7.2 Sessions, flash data and cookies

Explains middleware, sessions, flash data, and cookies. Middleware filters every request for cross-cutting concerns like authentication, logging, and rate limits, while sessions and cookies carry per-request state across visits. Flash data lives for exactly one request and powers save notices after a redirect.

7.1 Writing middleware

Shows how to write and register your own middleware. Generate a class with php artisan make:middleware, implement the handle method, and register it in the bootstrap HTTP kernel. A Terminable middleware can also run cleanup work after the response has been sent.

php artisan make:middleware EnsureUserIsActive

public function handle(Request $request, Closure $next): Response
{
    if ($request->user()?->isBanned()) {
        abort(403, 'Account suspended');
    }
    return $next($request);   // otherwise let the request continue down the pipeline
}

// Register in bootstrap/app.php (Laravel 11+ style):
->withMiddleware(function (Middleware $middleware) {
    $middleware->appendToGroup('web', EnsureUserIsActive::class);
})

Middleware runs before the route and either short-circuits with a 403 or passes the request on with $next(). Registration happens in bootstrap/app.php.

7.2 Sessions, flash data and cookies

Covers session state, flash data that lives for one request, and cookies. The session helper reads and writes per-visit values, with and flash stage data for the next request, and cookie helpers manage browser cookies. Pick the file, database, or redis driver in the session config.

session(['cart' => $items]);
$cart = session('cart', []);            // read the session with a default

return redirect()->back()->with('status', 'Saved');
@if (session('status')) <div class="ok">{{ session('status') }}</div> @endif

Cookie::queue('theme', 'dark', 60 * 24 * 365);

The session helper stores and reads user data, with() flashes a value for the next request only, and Cookie::queue sets a cookie the response sends.

Flash data survives exactly one request — perfect for "Saved!" notices after a redirect (Post/Redirect/Get).

  3. Persist a user’s theme preference in a cookie.

8 · Frontend, Vite, Livewire & Inertia

8.1 Vite and assets8.2 Livewire vs Inertia vs plain Vue/React8.3 A taste of Livewire

Compares frontend approaches from plain Blade to Livewire and Inertia. Plain Blade with Vite suits server rendered sites, Livewire adds interactivity while staying in PHP, and Inertia pairs Blade with a Vue or React frontend. Pick the approach whose complexity matches your project’s needs.

8.1 Vite and assets

Shows how to compile assets with Vite and load them in Blade. Add your entry points to resources, run npm install and npm run dev for hot reloading during development, or npm run build for production files. The @vite directive in your layout injects the correct asset links.

npm install
npm run dev      # hot reload
npm run build    # production assets

{{-- Blade --}}
@vite(['resources/css/app.css', 'resources/js/app.js'])   {{-- inject the compiled assets --}}

npm run dev serves assets with hot reload during development, and @vite injects the compiled CSS and JS tags into your view.

8.3 A taste of Livewire

Gives a first taste of Livewire components written entirely in PHP. Generate a component with php artisan make:livewire, then use wire:click and wire:model in the Blade template to react to clicks and form input without writing JavaScript. class Counter extends Component

}

A Livewire component pairs a PHP class with a Blade view. Public properties are live state, and wire:click calls increment over the wire without a full reload.

9 · Building APIs with Laravel

9.1 API routes and resources9.2 Authentication with Sanctum9.3 Versioning, pagination, errors

Covers building JSON APIs with resource routes, Sanctum authentication, and versioning. APIs share the same routing, controllers, validation, and Eloquent foundations as web apps, but shape responses for machines with resources and pagination. Sanctum provides token based access for mobile and SPA clients.

9.1 API routes and resources

Shows apiResource routes, API resources, and how to shape JSON output. Model resources generated with php artisan make:resource wrap a model and map it to clean JSON keys through their toArray method. Combine resources with pagination helpers so every client receives a consistent response shape.

// routes/api.php — prefixed with /api automatically
Route::apiResource('posts', Api\PostController::class);

php artisan make:resource PostResource

return [
    'id'    => $this->id,
    'title' => $this->title,
    'author'=> $this->whenLoaded('user', fn () => new UserResource($this->user)),   // only when eager-loaded
    'links' => ['self' => route('api.posts.show', $this)],
];

apiResource registers JSON-only CRUD routes, while a resource class controls exactly how a model appears in JSON, with whenLoaded keeping eager loads optional.

9.2 Authentication with Sanctum

Adds token based API authentication with Sanctum. Force authentication with the sanctum middleware or use token authentication on your API routes, then have users create personal access tokens with createToken. Clients send the token to authenticate without a browser session.

composer require laravel/sanctum
php artisan install:api

// issue a token
$token = $user->createToken('mobile')->plainTextToken;   // return this to the client

// protect routes
Route::middleware('auth:sanctum')->get('/user', fn (Request $r) => $r->user());

Sanctum hands out API tokens, and the auth:sanctum middleware requires one on protected routes. Clients send the token in an Authorization header.

9.3 Versioning, pagination, errors

Shows URL versioning, pagination shape, and consistent error responses. Prefix API route groups with versions such as v1 or v2, paginate with paginate or simplePaginate, and keep error responses uniform across endpoints. A stable contract lets clients upgrade on their own schedule.

Route::prefix('v1')->group(function () { ... });

Post::paginate(20);            // { data, links, meta }

// Consistent error shape
abort(response()->json(['error' => 'Not found'], 404));

Versioning keeps your URL space stable under a prefix, paginate returns a standard pagination envelope, and the abort line produces a consistent JSON error shape.

Design the JSON contract first (OpenAPI), generate docs, then implement. Clients integrate against the contract, not your feelings.

10 · Queues, Jobs, Events & Broadcasting

10.1 Queues and jobs10.2 Events and listeners10.3 Broadcasting and real-time

Covers queues, jobs, events, listeners, and broadcasting. Dispatch slow work to a queue so requests stay responsive, use events and listeners to decouple parts of the app, and broadcast changes to the browser for real-time updates. These patterns keep your application fast and easy to extend.

10.1 Queues and jobs

Shows how to dispatch jobs onto queues with delays and chains. Define a job with php artisan make:job and dispatch it with the dispatch method, optionally on a named connection with delays or chained after other jobs. Start php artisan queue:work so a worker processes items in the background.

php artisan make:job SendWelcomeEmail
dispatch(new SendWelcomeEmail($user));            // off it goes to the queue

// with delay and chain
SendWelcomeEmail::dispatch($user)->delay(now()->addMinutes(5));
Bus::chain([new ResizeImage($img), new NotifyUser($user)])->dispatch();   // run in order

dispatching a job pushes work to the queue, delay() schedules it for later, and Bus::chain runs several jobs in sequence, one after another.

# .env
QUEUE_CONNECTION=redis
php artisan queue:work --tries=3 --timeout=60   # retry failed jobs up to 3 times

Point the queue at Redis in .env, then php artisan queue:work runs a worker that processes jobs and retries failures up to the given tries.

10.2 Events and listeners

Introduces events and listeners as loose coupling. Fire an event with the Event facade or event helper, and let listeners generated with php artisan make:listener react to it. Mark a listener as ShouldQueue to process that reaction asynchronously.

event(new OrderShipped($order));              // every registered listener reacts
// Listeners can be queued automatically
class SendShipmentNotification implements ShouldQueue { ... }

event() fires OrderShipped to every registered listener, and implementing ShouldQueue runs those listeners on the queue automatically.

10.3 Broadcasting and real-time

Shows real-time updates with broadcasting and Reverb. Declare authorized channels in routes/channels.php, push changes from the server with the broadcast helper, and subscribe on the client with Laravel Echo. Reverb is the first party WebSocket server that Laravel ships for live applications.

// Reverb (Laravel's websocket server)
php artisan install:broadcasting

broadcast(new OrderShipped($order))->toOthers();   // skip the sender's own channel
// Frontend: Laravel Echo listens on a private channel

install:broadcasting sets up Reverb, Laravel’s WebSocket server. broadcast() sends the event to clients, and toOthers() excludes the sender.

Make jobs idempotent. Queues retry; a job that charges a card twice on retry is a support nightmare.

11 · Caching, Sessions & Performance

11.1 Cache stores and usage11.2 Redis: cache, queue and session11.3 The performance checklist

Covers caching, Redis, and the performance checklist. Cache repeated work such as query results and rendered fragments, then invalidate it deliberately when data changes. Redis serves as a shared cache, queue, and session store, and the checklist orders the fixes that speed up slow applications.

11.1 Cache stores and usage

Shows the cache API for storing, remembering, and forgetting values. Use the Cache facade methods put, remember, add, and forget across stores such as file, database, and redis. The remember method combines fetch and store in one step, which removes most cache boilerplate.

Cache::put('stats', $stats, now()->addMinutes(10));            // set a value with a TTL
$stats = Cache::remember('stats', 600, fn () => $this->computeStats());   // fetch or compute
Cache::forget('stats');

Cache::remember fetches the value if it exists or computes and stores it, ideal for expensive calculations. forget() lets you invalidate deliberately.

11.2 Redis: cache, queue and session

Positions Redis as the shared cache, queue, and session store in scaled applications. Configure the connection details in config/database.php, then point the cache, queue, and session drivers at redis. One robust Redis instance serves many concerns across web and worker servers.

Redis becomes the shared brain of a scaled app: cache, queues, sessions and rate limiting. Configure one robust Redis and use logical separation (databases/prefixes) per concern.

11.3 The performance checklist

Gives a practical performance checklist: eager load, index, cache, queue, paginate. Follow it in order to fix slow applications, measuring with a profiler before and after each change. This repeatable sequence turns performance guesswork into a reliable optimization loop.

  • Eager load relationships; install a debug bar and hunt N+1s.
  • Add indexes for every column you filter or join on.
  • Cache expensive reads; invalidate deliberately.
  • Move heavy work to queues.
  • Run php artisan optimize and route/config caching in production.
  • Paginate — never load a whole table into a view.

12 · Testing & Security

12.1 Feature and unit tests12.2 Security essentials

Covers feature tests and the security essentials Laravel gives you. Tests lock in behavior while built-in defences stop common attacks. Feature tests act as a user and hit routes, while conventions such as escaping, CSRF tokens, and parameterized queries cover the biggest threats.

12.1 Feature and unit tests

Shows feature tests that act as a user, hit routes, and assert database results. Use methods such as get, post, followingRedirects, assertSee, and assertDatabaseHas in your test case classes. Feature tests verify behavior end to end the way a real visitor experiences it.

php artisan make:test PostTest

public function test_user_can_create_a_post(): void
{
    $user = User::factory()->create();

    $this->actingAs($user)                          // logged in as $user
         ->post('/posts', ['title' => 'Hi', 'body' => 'Body text'])
         ->assertRedirect();

    $this->assertDatabaseHas('posts', ['title' => 'Hi']);   // the row really exists
}

This feature test acts as a user, posts to a route, asserts the redirect, then checks the row landed in the database. It exercises the whole stack.

php artisan test
php artisan test --filter=PostTest   # run just one test class
php artisan test --parallel          # spread across CPU cores

php artisan test runs the suite, --filter targets one class, and --parallel spreads the load across CPU cores.

12.2 Security essentials

Maps the top web attack risks to their Laravel defences. Blade escaping blocks XSS, the CSRF token middleware stops cross site request forgery, parameterized queries prevent SQL injection, and the auth middleware guards sensitive routes. Most protection comes free if you follow framework conventions.

13 · Advanced Laravel: Container, Providers & Packages

13.1 The service container13.2 Service providers13.3 Macros and higher-order collections13.4 Publishing your own package

Explains the service container, service providers, macros, and publishing packages. The container resolves dependencies automatically, providers boot and register services, macros extend core classes, and packages wrap it all into reusable code. This is where the framework opens up for serious customization.

13.1 The service container

Shows how the container binds interfaces and resolves dependencies. Register bindings with the bind and singleton methods on the app, then resolve through the make method or constructor injection. Type hinting a class or interface is exactly how your code asks for what it needs.

// bind an interface to an implementation
$this->app->bind(PaymentGateway::class, StripeGateway::class);

// singleton (one instance per request lifecycle)
$this->app->singleton(CacheWarmer::class);

// constructor injection
public function __construct(private PaymentGateway $gateway) {}

The container maps interfaces to implementations and manages instances. Constructor injection hands your classes exactly what they need automatically.

13.2 Service providers

Explains providers as the boot sequence that wires up your application. Each provider defines register and boot methods and is listed in bootstrap/providers.php, generated with php artisan make:provider. Keep providers thin so they register services rather than doing the actual work.

Providers are the boot sequence of your app. Use them to bind services, register event listeners, publish config and register routes. Keep them thin — business logic belongs in classes, not providers.

13.3 Macros and higher-order collections

Shows macros and higher-order collection helpers. Register a macro with the Macroable trait to add methods to framework classes such as Str or Collection, and chain helpers like map, filter, and reduce to transform data. Macros extend classes without forking core framework code.

Collection::macro('toUpper', function () {
    return $this->map(fn ($v) => strtoupper($v));
});

collect(['a', 'b'])->toUpper();   // ['A', 'B']

Collection::macro adds a brand-new method to every collection instance, letting you extend the framework’s fluent API without touching its source.

13.4 Publishing your own package

Walks through the anatomy of a publishable Laravel package. A package is basically a folder with a composer.json, a service provider, and src code, tested in your app through a path or VCS repository. Publish its config and migrations with the publishable method for consumers.

composer init
# src/, composer.json with "autoload": {"psr-4": {"Acme\\": "src/"}}
# PackageServiceProvider with $this->loadViewsFrom(...), loadMigrationsFrom(...)
composer require acme/your-package   # in another app

A package is just a composer.json plus a service provider that declares PSR-4 autoloading and registers views and migrations. Requiring it in another app loads everything.

14 · Scaling: Octane, Horizon & Infrastructure

14.1 Laravel Octane14.2 Horizon for queues at scale14.3 Horizontal scaling blueprint

Covers Octane, Horizon, and the infrastructure blueprint for scale. Octane holds one booted app in memory across requests, Horizon monitors Redis-backed queues, and the blueprint spreads state across shared services. Together these tools let the same codebase handle far more traffic.

14.1 Laravel Octane

Explains Octane, which keeps one booted application in memory across requests using a RoadRunner or Swoole server. Throughput rises sharply, but because state persists between requests you must avoid static properties and other shared state traps. Run php artisan octane:start to launch it.

composer require laravel/octane
php artisan octane:install --server=frankenphp   # pick FrankenPHP, Swoole, or RoadRunner
php artisan octane:start --workers=4 --max-requests=500   # run with 4 worker processes

Octane install picks a long-running server like FrankenPHP, and octane:start boots it with a set number of workers. The app stays warm in memory between requests for a major speed boost.

Octane boots the app once and serves many requests from memory — huge throughput gains. The price: be careful with in-memory state between requests (singletons that hold user data are now dangerous).

14.2 Horizon for queues at scale

Shows Horizon, the dashboard for Redis-backed queues at scale. Configure your queues in config/queue.php, then run php artisan horizon to get a live dashboard showing throughput, wait times, and failed jobs. Horizon supervises workers and lets you retry failures from the browser.

composer require laravel/horizon
php artisan horizon
// Dashboard at /horizon (protect it!) shows throughput, wait time, failures.

Running php artisan horizon starts a supervised queue dashboard. The /horizon page shows throughput, wait times, and failed jobs — protect it behind auth.

14.3 Horizontal scaling blueprint

Presents the blueprint for scaling horizontally across many servers. Keep web servers stateless, share cache sessions and locks through Redis, and run a fleet of queue workers that scale independently. Migrations run once, and a load balancer distributes traffic across the fleet.

  • Stateless web servers behind a load balancer; sessions in Redis.
  • Separate worker fleet for queues (Horizon), autoscaled by backlog.
  • Shared cache/session across nodes; database with read replicas.
  • Object storage (S3-compatible) for uploads; never local disk across nodes.
  • CDN for assets; queue slow third-party calls.

15 · Deployment & CI/CD for Laravel

15.1 Deployment steps15.2 Zero-downtime releases15.3 A minimal GitHub Actions pipeline

Covers deployment steps, zero-downtime releases, and CI pipelines. A deploy script installs dependencies, caches config and routes, migrates, and restarts workers, while releases switch a symlink atomically. CI runs the test suite on every push so breakage is caught long before production.

15.1 Deployment steps

Lists the exact commands to run on a production server. The sequence is composer install without dev dependencies, then php artisan optimize, config:cache, route:cache, view:cache, event:cache, migrate --force, and queue:restart. Each step is repeatable and safe to run on every release.

composer install --no-dev --optimize-autoloader   # locked deps, optimized for production
php artisan migrate --force                        # run without the confirmation prompt
php artisan optimize          # config + route + view cache
php artisan queue:restart     # tell workers to pick up new code
npm ci && npm run build

This is the production release sequence: locked dependencies, forced migration, cached config, a queue restart so workers load new code, and freshly built assets.

15.2 Zero-downtime releases

Explains zero-downtime releases by switching a symlink to a fresh release. Every deploy creates a new versioned directory and only points the current symlink at it once it is complete. Backward-compatible migrations are the tricky part: run them before the switch so old and new code both work.

Deploy into a fresh release directory, then switch a symlink atomically. Tools: Deployer, Envoyer, or a GitHub Actions pipeline. The database migration must be backward compatible for the window where old and new code both run.

15.3 A minimal GitHub Actions pipeline

Shows a minimal GitHub Actions pipeline that checks out the repo, sets up PHP, installs dependencies, and runs the test suite. Declare the workflow in a .github file with your environment secrets for the database, then run php artisan test. Automating tests catches breakage on every single push.

name: ci
on: [push]                 # triggered on every push
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4           # fetch the repository
      - uses: shivammathur/setup-php@v2     # install PHP
        with: { php-version: '8.3' }
      - run: composer install --prefer-dist --no-progress
      - run: cp .env.example .env && php artisan key:generate
      - run: php artisan test               # run the suite on every push

This workflow runs on every push: it checks out the repo, installs PHP 8.3 and dependencies, generates an app key, and runs the test suite.
