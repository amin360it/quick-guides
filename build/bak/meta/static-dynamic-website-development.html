1 ▸ Orientation: The Static and Dynamic Spectrum

1.1 What actually differs1.2 The spectrum, not a binary1.3 Decision drivers1.4 How this guide is organised

Before you choose a stack, know what genuinely changes between a file sitting on a CDN and a page assembled per request. This chapter separates the three real differences — rendering time, visitor state, and data freshness — from the marketing, places working sites on a spectrum rather than a binary, and sets out the decision drivers the rest of the guide builds on.

1.1 What actually differs

"Static versus dynamic" sounds like one decision. It is three independent ones: when the HTML is produced, whether the server remembers the visitor, and where the data lives.

Rendering time: build once or per request

A static page is finished before anyone asks for it. The HTML is written to disk at build time and the server's only job is to hand over bytes, so throughput is limited by the CDN rather than by application code. A dynamic page does not exist until a request arrives: the server runs code, queries data, renders a template, and only then sends HTML. That single difference explains most of the rest — cost, caching, scaling and the shape of your deployments.

// static — the file exists before the request
10:00  build:    content/ → public/index.html
10:37  request:  GET /index.html
10:37  response: the same bytes for every visitor

// dynamic — the HTML is produced by this request
10:37  request:  GET /dashboard
10:37  server:   run code → query db → render template
10:37  response: HTML assembled for this one visitor

State, identity and the idea of a visitor

A static server has no memory of you. Every request is anonymous and interchangeable, which is exactly why it scales to nothing and costs almost nothing. A dynamic server keeps state: it sets a cookie, stores a session on the server side, and recognises you on the next request. The moment a page depends on who is asking rather than what is asked, you have left pure static territory.

Static file server            Dynamic application server
GET /about → about.html       GET /dashboard → run code
                              Set-Cookie: sid=9f2c41; HttpOnly

no visitor identity           GET /dashboard
no memory of last request     Cookie: sid=9f2c41
                              → session found, user known

Data sources and freshness

Static content is data frozen at build time: a Markdown file, a JSON fixture, or a snapshot pulled from an API while the site was being built. Dynamic content is read at request time from a database or an upstream service, so the page reflects the current truth rather than last night's build. The question to ask is not "is it in a database" but "how stale may this page be before it is wrong".

// static: content is a file, copied at build time
content/posts/hello.md
  → build step
public/posts/hello/index.html

// dynamic: content is a row, read at request time
SELECT title, body
FROM posts
WHERE slug = 'hello' AND published = 1;

Staleness is a product decision, not a technical one. A team page may be correct for a week; a stock level is wrong within seconds. Write the acceptable staleness down before you pick a rendering model, because it decides the model for you.

1.2 The spectrum, not a binary

Real sites are not static or dynamic; they sit at a point on a spectrum, and different routes on the same site can sit at different points. Naming the points helps you choose per route instead of per project.

Five useful points on the spectrum

From cheapest to most flexible: pre-built files, generated files, static with background revalidation, per-request rendering, and browser rendering. Each step buys freshness or personalisation and pays for it in compute, operations and first-paint latency. Most production sites use at least two of these at once.

pure static   pre-rendered files, zero server logic
SSG           files generated from content at build time
ISR / hybrid  static by default, rebuilt in the background
SSR           HTML rendered per request, usually cached
CSR / SPA     shell shipped, page built in the browser

A single site, mapped route by route

The practical skill is decomposition. A marketing homepage barely changes and should be static; a blog post is static until its source is edited; a product page should expire in the background; an account page is different for every signed-in visitor; a search box can be a client-only widget. Assign a strategy per route and the "static or dynamic" argument dissolves.

/                 static     marketing copy, changes weekly
/pricing          static     edited by hand and rebuilt
/blog/*           SSG        rebuilt when a post is merged
/products/*       ISR        revalidate every 60 seconds
/account/*        SSR        rendered per signed-in user
/search           CSR        client-only, calls an API

The words people use loosely

"Static site", "dynamic site" and "web app" are shorthand, not specifications. A documentation site is static files plus a client-side search index; a shop is a generated catalogue plus a server-rendered checkout; a SaaS product is mostly a client-rendered app behind a login with a static marketing shell. When someone says "we need a dynamic site", translate it into the three questions from 1.1 before agreeing to anything.

marketing site   → usually static pages plus a hosted form
docs site        → SSG output, search runs in the browser
shop             → generated catalogue plus a rendered checkout
SaaS product     → client-rendered app plus a static shell

Write the strategy per route in the project README. "The homepage is static; /account is server-rendered" prevents months of accidental complexity, because every new page then has to declare which model it belongs to.

1.3 Decision drivers

Four questions decide the model: how fast content changes, whether pages differ per visitor, what must survive between requests, and how much operational burden the team can carry.

Content velocity and authorship

If a single editor edits a page a few times a month, a rebuild on publish is invisible and a static model wins. If a thousand users generate content continuously, rebuilding the world after every write is the wrong shape and you want a server rendering on demand. Content velocity maps almost directly onto a rebuild strategy.

how often content changes   →  rebuild strategy
once a quarter              →  static, rebuild by hand
daily                       →  SSG rebuilt on every commit
every minute                →  revalidate in the background
per visitor                 →  render per request

Personalisation and authentication

Any page that shows a name, a balance or a permission decision is rendered for a person, not for a URL, and cannot be cached publicly. This does not mean the whole site becomes dynamic: keep the public pages static and cacheable, and render only the signed-in routes per request. That boundary is where almost every sensible architecture draws its line.

public pages      →  cacheable, static
signed-in pages   →  per-user HTML, rendered per request
cart / checkout   →  server-side session state
real-time data    →  client fetch, polling or sockets

Budget, team size and operational reality

Static hosting is a folder of files behind a CDN with almost no failure modes. A dynamic stack adds a runtime to patch, a database to back up, migrations to run, logs to read and a monitoring bill. The code may be similar in size; the operational surface is not. If nobody on the team owns the runtime, do not adopt one you cannot leave.

static                        dynamic
host: CDN or object store     host: server or container
cost: pennies per million     cost: per request plus a server
risk: misconfig, stale cache  risk: injection, auth, uptime
ops:  deploy a folder         ops: migrations, logs, patches

Do not adopt a server "just in case". Every running process is an attack surface and an on-call page. The cheapest architecture that meets the staleness and personalisation requirements is almost always the right one.

1.4 How this guide is organised

The chapters follow the spectrum in order: foundations, then the server, then the build, then the browser, then the hybrid patterns, and finally how to choose and migrate between them.

The arc of the guide

Chapters 2 and 3 are the two ends of the spectrum in full: hand-written static files, and a request-handling server with sessions and a database. Chapters 4 and 5 cover the two ways to get both — generating static files from content, and rendering in the browser. Chapters 6 and 7 are the hybrid patterns and the decision procedure.

1 orientation   what actually differs
2 static        plain files, assets, hosting
3 dynamic       requests, sessions, databases
4 SSG           content → build → files
5 client-side   SPAs, fetch, frameworks
6 hybrid        headless CMS, JAMstack, edge
7 choosing      matrix, migration, cost

How each chapter is built

Every chapter is made of numbered topics; every topic is made of sub-points with a mechanism, a gotcha or a failure mode, and a complete sample you can copy and run. The samples are deliberately small and dependency-light so that the idea survives translation into whatever stack you actually use.

each chapter:
  h3   = a topic you can act on
  h4   = the mechanism or the gotcha
  code = something you can run, copy or adapt

read the topic, run the sample, then decide

A four-question check before you build

Before writing code, answer these four questions for every route you are about to create. The answers select the model; the model selects the tooling; the tooling selects the hosting. Answering them after you have chosen a framework is how projects end up with a static content site rendering client-side for no reason.

1. where does this page's data come from?
2. must the server remember the visitor?
3. how often does the content change?
4. which pages must rank in a search engine?

→ choose the model with the smallest ops bill that passes all four

Keep this list in the repository and answer it in the pull request when a new route appears. It is the single cheapest habit that keeps a site's rendering strategy honest as it grows.

2 ▸ Static Foundations

2.1 Plain HTML, CSS and JavaScript2.2 Files, folders and URLs2.3 Linking, navigation and forms2.4 Hosting a static site anywhere

The static end of the spectrum is HTML, CSS and JavaScript in a folder, served over HTTP with no application code in the path. This chapter covers the files themselves, the way folders become URLs, navigation and forms without a server, and how to host the result anywhere — from a thumb drive to a global CDN.

2.1 Plain HTML, CSS and JavaScript

A complete website can be three files. Structure lives in HTML, presentation in CSS, and behaviour in JavaScript; they are linked, never mixed, and the browser assembles them.

A document that needs no server

Every page starts with the doctype, a lang attribute that drives pronunciation, a character set declared before any text, and a viewport tag so the layout is not secretly zoomed on phones. The scripts come last or carry defer, which lets the HTML paint before JavaScript runs. A plain index.html opened from disk is a working website; nothing above it is required.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>A static page</title>
  <link rel="stylesheet" href="/assets/site.css">
</head>
<body>
  <header><h1>My site</h1></header>
  <main><p>No server needed.</p></main>
  <footer><p>© 2026</p></footer>
  <script src="/assets/app.js" defer></script>
</body>
</html>

CSS: tokens, layout, and one dark-mode switch

Keep colours in custom properties so a theme change is one edit, not fifty. A single max-width and a centred margin give readable line lengths, and a prefers-color-scheme block handles dark mode without any JavaScript. Because the whole page is one HTML document, the browser renders it in one pass with no data fetching to wait for.

:root {
  --ink: #101828;
  --bg: #ffffff;
  --accent: #0b5fbf;
  --measure: 68ch;
}
body { margin: 0; font: 16px/1.5 system-ui, sans-serif;
       color: var(--ink); background: var(--bg); }
main { max-width: var(--measure); margin: 0 auto; padding: 2rem 1rem; }
a { color: var(--accent); }

@media (prefers-color-scheme: dark) {
  :root { --ink: #e6eefc; --bg: #0b1220; --accent: #4dd2ff; }
}

JavaScript: behaviour only, content stays in the HTML

The static-site discipline is to render content in HTML and use JavaScript for interaction. A menu toggle, a filter or a lightbox enhances markup that already exists; if the script fails, the page still reads. Scripts should be small, deferred, and free of any assumption that they must run for the page to be usable.

// assets/app.js — enhance markup that is already there
const toggle = document.querySelector('#nav-toggle');
const nav = document.querySelector('#nav');

toggle?.addEventListener('click', () => {
  const open = nav.toggleAttribute('data-open');   // adds/removes the attribute
  toggle.setAttribute('aria-expanded', String(open));
});

If the page shows nothing until a script has run, it is not a static page anymore in any sense that matters — not to a crawler, not to search, and not to a user on a flaky connection. Keep the content in the markup.

2.2 Files, folders and URLs

On a static site the folder structure is the URL structure. Get the mapping right and hosting, linking and cache control all follow from it.

Folders that mirror paths

A folder named after a route, containing an index.html, is served for that route by almost every static host. This is why about/index.html answers a request for /about and gives you a clean URL. Keep source assets in one assets folder so cache rules and build steps can target a single path.

site/
  index.html
  about/index.html
  posts/hello-world/index.html
  assets/
    site.css
    app.js
    img/hero.webp
  favicon.ico
  404.html

Absolute and relative paths

An absolute path beginning with / resolves from the domain root and is stable no matter how deep the current page is. A relative path resolves from the current file's directory and must be adjusted with ../ as the page moves. On a static site, prefer root-absolute asset paths and document that the site is served from the domain root, not a subfolder.

<!-- absolute: resolves from the domain root at any depth -->
<link rel="stylesheet" href="/assets/site.css">

<!-- relative: resolves from this file's directory -->
<link rel="stylesheet" href="../assets/site.css">

<!-- served under a subpath? every absolute link must include it -->
<link rel="stylesheet" href="/guides/assets/site.css">

Clean URLs and directory indexes

The request /about is served from /about/index.html by a directory index rule. Most static hosts and Python's http.server do this automatically; a bare object store such as S3 does not, so you must configure an index document and an error document there. The 404 page is a real file too, and it is what makes a static site feel complete.

# how a clean URL resolves
/                   → /index.html
/about              → /about/index.html
/posts/hello-world  → /posts/hello-world/index.html

# both files must exist for the host to find them
404.html            → the page served for unknown paths

If a deploy breaks every stylesheet, the usual cause is a site moved to a subpath while its links stayed root-absolute. Either set a base path or keep every link relative — but choose one and apply it consistently.

2.3 Linking, navigation and forms

Navigation on a static site is ordinary anchors, and a form still needs somewhere to post. Both work without any server of your own, using third-party endpoints or the browser itself.

Navigation is just anchors

Because each page is a real document, navigation is a normal <a href> and the browser handles history, bookmarks and the back button for free. Repeat the same nav markup on every page — or generate it with a build step later — and mark the current page with aria-current="page" so assistive technology announces where you are.

<nav aria-label="Main">
  <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/about/" aria-current="page">About</a></li>
    <li><a href="/posts/">Blog</a></li>
  </ul>
</nav>
<!-- no router, no client code: the browser does the navigation -->

Forms without a server of your own

An HTML form posts its named fields to whatever action points at. On a static site that is usually a hosted form service, which accepts the POST and emails or stores the submission for you. This keeps the site a folder of files while still collecting data — the third-party endpoint is the only moving part.

<form action="https://formspree.io/f/abcdwxyz" method="post">
  <label for="email">Email</label>
  <input id="email" name="email" type="email" required>

  <label for="msg">Message</label>
  <textarea id="msg" name="message"></textarea>

  <input type="hidden" name="_subject" value="New enquiry">
  <button type="submit">Send</button>
</form>

Client-side search and filtering

The one feature people assume needs a server — search — can be shipped as data. A build step writes a small JSON index of every page, the browser downloads it once, and filtering happens locally with no request at all. For a few hundred pages this is faster than a server round trip and works offline.

// build step writes /search-index.json: [{ url, title, text }, …]
fetch('/search-index.json')
  .then((r) => r.json())
  .then((pages) => {
    const q = document.querySelector('#q').value.toLowerCase();
    const hits = pages.filter((p) => p.text.toLowerCase().includes(q));
    render(hits.slice(0, 20));
  });

Keep the search index to the fields people actually search. Shipping entire page bodies makes the download heavier than the pages themselves; a title plus the first paragraph and a few headings is usually enough.

2.4 Hosting a static site anywhere

A static site has one deployment artefact — a folder — and any host that can serve files over HTTP will run it. That portability is the whole point of the model.

The portable artefact

Netlify, Vercel, Cloudflare Pages, GitHub Pages and any S3-compatible bucket all accept the same output folder, so you are never locked in. Deploy is a single command or a push to a branch, and a rollback is re-deploying the previous folder. Because there is no runtime, there is nothing to patch while it sits idle.

$ npx netlify deploy --prod --dir=dist
$ npx vercel deploy --prod            # static output
$ npx wrangler pages deploy dist      # Cloudflare Pages
$ git push origin main                # GitHub Pages via Actions

# the artefact is always the same: a folder of files

Caching and headers

Because files never change under a fixed name, fingerprinted assets can be cached for a year while the HTML revalidates on every request. That split is what makes a static site feel instant on the second visit: the page shell is checked cheaply, and every asset it references is already in the browser. Set these headers at the host or in a small config file.

# fingerprinted asset — safe to cache for a year
/assets/*   Cache-Control: public, max-age=31536000, immutable

# HTML must revalidate so a new deploy is seen
/*.html     Cache-Control: public, max-age=0, must-revalidate

# never cache a page that must be current to the second
/news/live  Cache-Control: no-store

What a static site cannot do on its own

A static host does not execute your code, so it cannot read a posted body, verify a password, remember a session or enforce per-user access by itself. Every one of those needs a server or a hosted service. Recognising the boundary is the whole reason the rest of this guide exists: the static model is the base case, and dynamic behaviour is added deliberately.

what a static site cannot do alone:
  read a posted form body
  verify a password
  remember a session
  enforce per-user access
  query a database from the server

→ each needs a server or a third-party service

Never put secrets — API keys, database credentials — in static files. Everything a browser downloads is public. Anything that needs a secret must run on a server or use short-lived tokens minted elsewhere.

3 ▸ Dynamic Server-Side Development

3.1 The request lifecycle on a server3.2 Server runtimes: PHP, Node and ASP.NET3.3 Templating and server-side rendering3.4 Sessions, cookies and state3.5 Databases behind the server

A dynamic server runs code for every request: it routes the path, reads the visitor's state, queries a database, renders a template and returns HTML. This chapter walks that lifecycle, the runtimes that host it, templating and escaping, sessions and cookies, and the database layer underneath.

3.1 The request lifecycle on a server

From the server's point of view, a page is the output of a pipeline that starts with a request line and ends with a response. Knowing the pipeline is how you know where a bug lives.

The shape of an HTTP exchange

A request carries a method, a path, headers and sometimes a body; a response carries a status, headers and a body. Cookies travel as headers, cache directives travel as headers, and the content type tells the browser how to interpret the bytes. Debugging a dynamic site usually means reading exactly these headers.

GET /posts/42 HTTP/1.1
Host: example.com
Accept: text/html
Cookie: sid=9f2c41

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: private, no-store
Set-Cookie: sid=9f2c41; HttpOnly; Secure; SameSite=Lax

Routing: which handler answers

The server matches the method and path against a route table and calls one handler. Everything else in the application is reached from that handler: it parses parameters, calls services, and hands data to a template. Keep the table small and legible; a route map you can read in one screen is a design document.

GET   /                 → home()
GET   /posts            → listPosts()
GET   /posts/:id        → showPost(id)
POST  /posts            → createPost(body)
POST  /logout           → destroySession()

Middleware: the pipeline around the handler

Logging, session loading, authentication and CSRF checks are cross-cutting concerns that run for many routes, so they live in middleware that wraps the handler. Each layer can inspect the request, enrich it, or short-circuit it with a redirect or an error. The order matters: sessions must be loaded before an auth guard can read them.

request
  → logging
  → session lookup
  → authentication guard
  → CSRF check (mutating verbs)
  → route handler
  → template render
response

If a handler needs to know who the user is, that fact should have been established in middleware, not guessed inside the handler. Cross-cutting state set up once and trusted everywhere is the pattern that keeps dynamic code predictable.

3.2 Server runtimes: PHP, Node and ASP.NET

The lifecycle is the same everywhere; the runtime decides the syntax, the deployment shape and the surrounding ecosystem. Three common runtimes cover most of the web.

PHP: a script per request

PHP's model is the simplest to reason about: the web server invokes a script, the script runs, the process ends. With a front controller every URL is handled by one file that bootstraps the app. PHP ships with a database driver and a templating idiom (HTML with embedded PHP) that gets you to a working page in minutes.

<?php
// public/index.php — a single front controller
declare(strict_types=1);
$pdo = new PDO('mysql:host=db;dbname=site;charset=utf8mb4', $user, $pass, [
  PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
]);
$slug = $_GET['slug'] ?? 'home';
$stmt = $pdo->prepare('SELECT title, body FROM pages WHERE slug = ?');
$stmt->execute([$slug]);
$page = $stmt->fetch() ?: ['title' => 'Not found', 'body' => ''];
require __DIR__ . '/../templates/page.php';

Node.js: one long-lived process

Node runs a persistent event loop rather than starting fresh per request, which makes it a good fit for many small I/O-bound requests. A framework such as Express supplies routing and view rendering; handlers are async functions that await the database. Because the process stays up, state kept in memory is available between requests — and is also the first thing that breaks when you run more than one instance.

import express from 'express';
const app = express();
app.use(express.urlencoded({ extended: true }));

app.get('/posts/:id', async (req, res) => {
  const post = await db.posts.findOne({ id: Number(req.params.id) });
  if (!post) return res.status(404).render('not-found');
  res.render('post', { post });
});

app.listen(3000);

ASP.NET Core: pages with a model

ASP.NET Core's Razor Pages pair a .cshtml file with a page model that handles GET and POST. Routing, model binding and HTML encoding are provided by the framework, and the compiled language means most mistakes are caught before runtime. It is the most typed of the three and scales the same way Node does.

@page "{id:int}"
@model ShowModel

<article>
  <h1>@Model.Post.Title</h1>
  <p>@Model.Post.Body</p>
</article>

@code {
  public class ShowModel : PageModel {
    public Post Post { get; set; } = default!;
    public async Task OnGetAsync(int id) => Post = await db.FindAsync(id);
  }
}

Learn one runtime properly rather than three shallowly. The request lifecycle, templating and database access transfer directly; the syntax does not, and the syntax is the smallest part.

3.3 Templating and server-side rendering

Server-side rendering means the server produces finished HTML by filling a template with data. The template engine is not decoration — it is the layer that decides how data is escaped and where output bugs become security bugs.

Filling a template with data

A template is HTML with placeholders. The handler supplies the data, the engine substitutes the values, and the result is a complete document the browser can paint without a single line of JavaScript. This is why server-rendered pages are fast on first load and indexable by anything that can read HTML.

<!-- templates/post.php -->
<article>
  <h1><?= htmlspecialchars($post['title']) ?></h1>
  <time datetime="<?= $post['date'] ?>"><?= $post['date'] ?></time>
  <div><?= $post['body_html'] /* sanitised before storage */ ?></div>
</article>

Escaping at the point of output

Every value that reaches HTML must be escaped for the context it lands in: HTML text, an attribute, a JavaScript string or a URL each need different treatment. Escape on output, not on input, so the stored data stays clean and one template cannot accidentally trust another's choice. Encoding for the wrong context is the root of cross-site scripting.

// escape for the context, at the moment you output
htmlspecialchars($title, ENT_QUOTES, 'UTF-8')    // HTML text and attributes
json_encode($data, JSON_HEX_TAG | JSON_HEX_AMP)  // inside <script>
urlencode($segment)                              // inside a URL path
// never: string concatenation straight into markup

Layouts and partials

Most pages share a head, a header and a footer, so the renderer composes a layout from partials around the page's own content. The layout receives the page's rendered body; partials are included by path. This is the server-side ancestor of the component model, and it keeps a change to the nav in exactly one file.

<?php // templates/layout.php — every page wraps this ?>
<!DOCTYPE html>
<html lang="en">
<head><title><?= htmlspecialchars($title) ?></title></head>
<body>
  <?php require __DIR__ . '/partials/header.php'; ?>
  <main><?= $content ?></main>
  <?php require __DIR__ . '/partials/footer.php'; ?>
</body>
</html>

Do not mix user data into a JavaScript block with plain interpolation. A string containing </script> will end the block and become executable markup. Encode it as JSON with the hex flags, or pass it through a data attribute the script reads.

3.4 Sessions, cookies and state

HTTP is stateless: each request arrives with no memory of the last. Cookies and server-side sessions are how a dynamic application reconstructs a person across requests — and how it goes wrong when they are misconfigured.

Cookies: small values the browser repeats

A cookie is a name and value the server asks the browser to store and return on matching requests. The attributes matter: HttpOnly hides it from JavaScript, Secure sends it only over HTTPS, SameSite limits cross-site sending, and Max-Age sets the lifetime. A non-essential cookie without those flags is a security incident waiting to be reported.

# the server asks the browser to store a value
Set-Cookie: theme=dark; Path=/; Max-Age=31536000; SameSite=Lax

# the browser repeats it on every matching request
Cookie: theme=dark; sid=9f2c41

# clear a cookie by expiring it in the past
Set-Cookie: theme=; Path=/; Max-Age=0

Sessions: state that lives on the server

A session stores the real state — the user id, the cart, a CSRF token — on the server and gives the browser only an opaque identifier. The identifier is worthless without the server-side record, so a stolen cookie is the only way in and can be revoked by destroying the session. This is the standard pattern for keeping someone logged in.

<?php
session_start();
$_SESSION['user_id'] = $user['id'];
$_SESSION['csrf'] = bin2hex(random_bytes(32));

// on a later request
session_start();
if (empty($_SESSION['user_id'])) {
    header('Location: /login');
    exit;
}

Hardening a session

Set the cookie flags when the session starts, and regenerate the session id on login so a pre-login id cannot be fixed and reused. Pair the session with a CSRF token on every mutating form. These three moves — flags, regeneration, token — close most of the classic session attacks.

session_set_cookie_params([
  'httponly' => true,   // JavaScript cannot read it
  'secure'   => true,   // HTTPS only
  'samesite' => 'Lax',  // blocks most cross-site posts
  'path'     => '/',
]);
// stop session fixation by issuing a new id on login
session_regenerate_id(true);

Never store personal data in a cookie the browser can read or edit. Cookies are guesses sent to you; the server-side session is the truth. Trust the id, not the contents.

3.5 Databases behind the server

The database is where a dynamic site keeps the truth. The server's job is to read and write it safely — parameterised, indexed and cached — without turning every page load into a slow full scan.

Schema and indexes first

A table is only as fast as its indexes. A slug that is looked up on every request wants a unique index; a list ordered by publish date wants an index on that column. Getting the schema right before the first row is written costs minutes; adding the right index after a million rows costs a maintenance window.

-- schema
CREATE TABLE posts (
  id           INTEGER PRIMARY KEY,
  slug         TEXT NOT NULL UNIQUE,
  title        TEXT NOT NULL,
  body         TEXT NOT NULL,
  published_at TEXT
);

-- the list page orders by this column on every request
CREATE INDEX idx_posts_published ON posts (published_at DESC);

Prepared statements and parameter binding

Never build SQL by concatenating user input. A prepared statement sends the query and the data separately, so the database can never mistake a value for a keyword or a second statement. Bind every parameter, and give the driver the type so numbers and strings are handled correctly. This single habit removes the whole class of SQL injection bugs.

<?php
// parameters travel separately from the SQL text
$stmt = $pdo->prepare(
  'SELECT id, title FROM posts
   WHERE published_at <= ? ORDER BY published_at DESC LIMIT ?'
);
$stmt->bindValue(1, $now, PDO::PARAM_STR);
$stmt->bindValue(2, $limit, PDO::PARAM_INT);
$stmt->execute();
$rows = $stmt->fetchAll(PDO::FETCH_ASSOC);

Cache the read, invalidate on write

The read path is usually far busier than the write path, so caching rendered output or query results is the highest-value optimisation. Cache with a short time to live and delete the key on write, so an edit is visible immediately rather than after the TTL. Getting invalidation wrong is how a database-backed site serves content that no longer exists.

// read through a cache, and drop the key when the row changes
$key  = "post:$slug";
$html = $cache->get($key);
if ($html === null) {
    $html = render_post(fetch_post($slug));
    $cache->set($key, $html, 300);   // 300s TTL
}

// after an edit
$cache->delete("post:$slug");        // next read refills it

Log the queries, not just the requests. A page that takes 400 ms usually has four queries at 90 ms each, and the fix is an index or a cache, not a bigger server.

4 ▸ Static Site Generators

4.1 What a generator actually does4.2 Content in files4.3 The build step4.4 Choosing a generator4.5 Hydration and islands

A static site generator gives you the authoring comfort of a dynamic site and the deployment profile of a static one: you write content and templates, run a build, and ship files. This chapter covers the model, content in files, the build step, the popular generators, and the hydration question that follows.

4.1 What a generator actually does

An SSG is a program that reads content and templates and writes HTML. There is no magic and no runtime: the output is a folder of files, exactly like the hand-written site from chapter 2.

The build pipeline, end to end

The generator walks a source directory, reads each content file and its metadata, applies the matching layout, runs any plugins, and writes a finished page to an output directory. Because everything happens before deploy, the cost of rendering is paid once per build rather than once per request. The output is portable to any static host.

source files + content
        │
        ▼
   build step (Node, Go, Ruby)
        │  read content, apply layouts, run plugins
        ▼
output: a folder of .html, .css, .js, images
        │
        ▼
deploy to any static host

Front matter: metadata at the top of a file

A content file begins with a block of metadata in YAML or JSON, called front matter, separated from the body by a fence. The generator reads it to get the title, date, tags and status of the page without you maintaining a separate index. Draft posts are simply pages whose front matter says so.

---
title: "Deploying a static site"
date: 2026-10-01
tags: [deployment, netlify]
draft: false
---

# Deploying a static site

The build reads this header and turns it into page metadata.

Collections: indexes generated, not typed

A collection is a group of content files the generator exposes to templates. The blog index is a loop over the collection, sorted by date, so a new post appears the moment its file exists. This is the feature that makes an SSG a system rather than a folder of hand-edited pages.

<!-- the index is generated from the collection, not written by hand -->
<ul class="post-list">
  {% for post in collections.posts | reverse %}
  <li>
    <time datetime="{{ post.date }}">{{ post.date | readableDate }}</time>
    <a href="{{ post.url }}">{{ post.data.title }}</a>
  </li>
  {% endfor %}
</ul>

Keep generated pages out of version control. Commit the content and templates; let the build produce the HTML. A repo full of generated files makes every editorial change look like a code change.

4.2 Content in files

In an SSG the content lives in files — usually Markdown — and is validated by a schema. That constraint is the feature: content is reviewable, diffable and versioned like code.

Markdown as the authoring format

Markdown keeps the source readable while the generator turns it into semantic HTML. Headings, lists, links and code blocks are written with plain punctuation, and because it is text it lives comfortably in Git. The build is where Markdown becomes HTML, so the markup stays clean by construction.

# Hello

Some **bold** text and a [link](/about).

- item one
- item two

    four spaces make an indented code block

A schema that turns typos into build errors

The most valuable gate in an SSG is content validation. A schema checks every front matter block as it is read, so a missing title or a malformed date fails the build instead of shipping a broken page. The build is your content QA, and it runs on every change.

// a content schema turns a typo into a build error
const posts = defineCollection({
  type: 'content',
  schema: z.object({
    title: z.string().max(80),
    date: z.coerce.date(),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),
  }),
});

Layouts and inheritance

Layouts wrap content so a page only declares what is unique about it. A base layout owns the document shell, a post layout extends it with article markup, and templates can include shared partials such as navigation. Changing the header then means editing one file and rebuilding.

<!-- layouts/base.njk -->
<!DOCTYPE html>
<html lang="en">
<head><title>{{ title }} · My site</title></head>
<body>
  {% include "partials/nav.njk" %}
  <main>{{ content | safe }}</main>
</body>
</html>

The safe filter disables escaping and must only wrap HTML you generated yourself from trusted Markdown. Passing a user-submitted field through it reopens the XSS hole the templating engine closed.

4.3 The build step

The build is the heart of the SSG model. It is a program you run locally and in CI, it produces the deployable folder, and its speed decides how pleasant the authoring loop feels.

What a build actually does

A build cleans the output directory, loads content, validates it, renders pages through layouts, writes HTML, copies and hashes assets, and emits supporting files such as a sitemap and feed. Every step is deterministic given the same inputs, so the same source always produces the same site.

$ npm run build
  → clean dist/
  → load content collections
  → validate front matter against schemas
  → render pages through layouts
  → write dist/*.html
  → copy and hash assets
  → emit sitemap.xml, robots.txt, feed.xml

Incremental and parallel builds

When a site grows past a few hundred pages, a full rebuild becomes slow enough to notice. Generators offer partial rebuilds and parallelism: render only what changed, and use every CPU core. Keep the content tree shallow and avoid cross-page queries that force a global rebuild.

# Hugo: rebuild only what changed, using every core
$ hugo --gc --minify --enableGitInfo --parallel 8

# Eleventy: reuse cached templates between runs
$ npx @11ty/eleventy --serve --incremental

Building in CI and deploying

The build runs in CI on every push, so nothing reaches production that was not built from a clean checkout with a locked dependency tree. The pipeline checks out, installs from the lockfile, builds, and publishes the output folder. A failed build blocks the deploy, which is exactly what you want when the build also validates content.

# .github/workflows/deploy.yml
name: deploy
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm run build
      - run: npx wrangler pages deploy dist

Run the build on every pull request and only publish from the default branch. Reviewers then see a build that passes, and content errors fail on the branch instead of in production.

4.4 Choosing a generator

Generators differ in build speed, templating language and how much application framework they bring. Pick by the shape of the content and the team's language, not by popularity.

Hugo: fastest builds, Go templates

Hugo is a single binary with no dependency install, which makes it trivial to run in CI and very fast on large content sets. Its templating is Go's, which is powerful but unlike the JavaScript ecosystem. It is a strong default for documentation and blogs where build time matters.

$ hugo new site myblog
$ cd myblog
$ git submodule add https://github.com/adityatelange/hugo-PaperMod themes/papermod
$ hugo new posts/first-post.md
$ hugo server -D        # -D includes drafts
$ hugo --minify         # writes public/

Eleventy: HTML-first, chooses your templates

Eleventy is deliberately minimal: it takes whatever templating language you already know (Nunjucks, Liquid, JavaScript) and outputs plain HTML with no client runtime. Configuration is a small JavaScript file, and its ethos is to ship no JavaScript unless you add it. It suits teams that want full control over the markup.

// .eleventy.js
module.exports = (eleventyConfig) => {
  eleventyConfig.addPassthroughCopy("assets");
  eleventyConfig.addFilter("readableDate", (d) =>
    new Date(d).toLocaleDateString("en-GB"));
  return { dir: { input: "src", output: "dist" } };
};

Next.js: a framework that can export statically

Next.js is a full React framework whose build can still emit a static site. In export mode every route is rendered to HTML at build time, and the same components could later switch to server rendering without a rewrite. Choose it when static is the starting point but dynamic routes are likely to appear.

// next.config.js — export a fully static site
/** @type {import('next').NextConfig} */
module.exports = {
  output: 'export',
  images: { unoptimized: true },   // no optimiser runs at export time
};

The right question is not "which is best" but "how much framework do I want in my static output". Hugo and Eleventy add none; Next.js adds React, which is only worth paying for if you will hydrate something.

4.5 Hydration and islands

The moment a generated page needs interactivity, JavaScript must attach to the finished HTML. How much JavaScript you attach — and when — is the difference between a fast static site and a slow one wearing a static disguise.

Hydration: attaching behaviour to HTML that exists

Hydration runs the component tree in the browser and connects it to the server-rendered DOM instead of rebuilding it. The page paints immediately from HTML, then becomes interactive once the bundle finishes. It is the standard bridge between server-rendered markup and client-side behaviour, and its cost is the bundle itself.

// the server rendered HTML; the client adopts the same DOM
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

hydrateRoot(document.getElementById('root'), <App />);

Islands: hydrate only what is interactive

Islands invert the default: the page is static HTML and only the interactive components get JavaScript, each loaded when it is needed. A search box hydrates when visible, a cart when needed, a comment widget when idle. The shipped JavaScript is proportional to behaviour, not to page size.

<!-- Astro: the shell is static; only these ship JavaScript -->
<Search client:visible />
<CartButton client:load />
<Comments client:idle />
<Map client:only="react" />

<!-- everything else renders to HTML with no hydration cost -->

What partial hydration buys

Measuring the difference is the fastest way to justify the discipline. A fully hydrated marketing page often ships hundreds of kilobytes of framework code to power a hamburger menu; an island build ships a fraction of it and paints sooner. The number you care about is kilobytes of JavaScript per interactive feature.

JavaScript shipped for the same page:
  full hydration   180 KB   every component runs in the browser
  islands           24 KB   only the cart and the menu
  zero JS            0 KB   nothing requested interactivity

Audit a generated page with JavaScript disabled in DevTools. If it still reads and navigates, the content is genuinely static and only the enhancements are lost — which is the state you want.

5 ▸ Client-Side Dynamics

5.1 Single-page applications5.2 Fetching APIs from the browser5.3 Frontend frameworks5.4 Progressive enhancement5.5 SEO and accessibility of client rendering

The opposite end of the spectrum moves rendering into the browser: the server sends a shell and data, and JavaScript builds the page and keeps it in sync. This chapter covers single-page applications, fetching from APIs, frontend frameworks, progressive enhancement, and the SEO and accessibility consequences of rendering on the client.

5.1 Single-page applications

A single-page application loads one HTML document and swaps views with JavaScript. Navigation feels instant once loaded, and the cost is paid up front.

The shell and the bundle

The server sends a near-empty document with a mount point and a script tag. The browser downloads the bundle, executes it, and only then does any content appear. Everything about first-load performance follows from that sequence: until the bundle runs, the page is blank to a user, a crawler and a social preview bot alike.

<!DOCTYPE html>
<html lang="en">
<head><title>App</title></head>
<body>
  <div id="root"></div>
  <script type="module" src="/assets/index-4f2a.js"></script>
</body>
</html>

<!-- the visible page is built only after the bundle runs -->

Client-side routing

A router intercepts link clicks, updates the URL with the History API, and renders a new view without asking the server for a document. The back button and deep links still work because the URL is real; what changed is that no HTML is requested on navigation. The server must still serve the shell for every route, or a refresh on a deep link returns a 404.

// client-side routing: the URL changes without a document request
window.addEventListener('popstate', render);

document.querySelectorAll('a[data-link]').forEach((a) => {
  a.addEventListener('click', (e) => {
    e.preventDefault();
    history.pushState({}, '', a.href);
    render();
  });
});

The cost of client rendering

For the same content, a client-rendered page ships far more JavaScript and shows content later. The trade is deliberate: an app with heavy, constant interaction amortises that cost, while a content page never does. Compare the two honestly before choosing, because the difference is measured in seconds on a mid-range phone.

first load for identical content on a mid-range phone:
  static HTML      12 KB   first contentful paint ~0.4 s
  SSR + hydrate   160 KB   content paints, interactive later
  CSR shell       190 KB   content appears after the bundle runs

A deep link that 404s on refresh is the classic SPA deployment bug: the server was never told to serve the shell for client-side routes. Configure a catch-all rewrite to index.html before shipping.

5.2 Fetching APIs from the browser

A client-rendered page gets its data from an API over HTTP. The mechanics are a few lines of fetch; the discipline is handling every state and every failure the network can produce.

The Fetch API

fetch returns a promise for a response, and you must check ok before parsing because a 500 response is still a resolved promise. Send an Accept header so the API returns JSON, and throw on a bad status so the error path is a single place. This is the whole of the happy path.

async function loadPosts() {
  const res = await fetch('/api/posts', {
    headers: { Accept: 'application/json' },
  });
  if (!res.ok) throw new Error('HTTP ' + res.status);
  return res.json();
}

Four states, all of them visible

Any asynchronous UI has at least four states: loading, ready, empty and error. Showing only the ready state is why pages appear to do nothing on a slow connection. Render a skeleton while loading, a message when empty, and a retry when it fails, and the interface feels honest.

let state = 'loading';
try {
  const data = await loadPosts();
  state = data.length ? 'ready' : 'empty';
} catch (err) {
  state = 'error';
}
// render: skeleton, list, empty message, or retry button

CORS: why a cross-origin call is refused

The browser enforces the same-origin policy, so a page on one origin cannot read a response from another unless that origin opts in with CORS headers. Non-simple requests trigger a preflight OPTIONS request first, and the response must allow the method and origin. The block is the browser's, not the server's, which is why the request appears in the network panel but the code never sees the body.

OPTIONS /api/posts HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Credentials: true

Allow a specific origin, never a wildcard, when credentials are involved. Access-Control-Allow-Origin: * together with credentials is rejected by the browser, and a naive fix of echoing the origin back opens the door to any site.

5.3 Frontend frameworks

A framework gives you components, reactive state and a build pipeline, so the UI stays in step with data by construction. The concepts are shared across React, Vue and Svelte; the syntax is not.

Components as functions of props

A component is a reusable unit of UI that renders from its inputs. In React it is a function returning markup; in Vue it is a single-file component; in Svelte it compiles away at build time. In all three, data flows down as props and changes are requested upward, so the owner of a value is unambiguous.

// a component is a function of its props
export default function Price({ amount, currency = 'GBP' }) {
  const fmt = new Intl.NumberFormat('en-GB', { style: 'currency', currency });
  return <span className="price">{fmt.format(amount)}</span>;
}

Reactive state and derived values

State is the data that changes; reactivity is the framework re-rendering when it does. Store the minimum — the list, not its count and its total — and derive everything else during render so the copies cannot disagree. Updating state always goes through the setter, never by mutating the value in place.

import { useState } from 'react';

export function Cart() {
  const [items, setItems] = useState([]);
  const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);
  return (
    <>
      <button onClick={() => setItems([])}>Clear</button>
      <p>{items.length} items, {total.toFixed(2)}</p>
    </>
  );
}

The build tool behind the framework

A modern bundler compiles the source into a small number of fingerprinted files, serves it instantly in development, and proxies API calls to your backend so the app and the server share one origin. This is the pipeline that turns components into the bundle the browser runs, and its configuration is part of the application.

// vite.config.js — one entry, hashed production output
import { defineConfig } from 'vite';

export default defineConfig({
  build: { outDir: 'dist', sourcemap: true, target: 'es2020' },
  server: { proxy: { '/api': 'http://localhost:3000' } },
});

Learn one framework well enough to debug it — the render cycle, state updates and the dev tools. The second framework is a week; the concepts you carry between them are the part that matters.

5.4 Progressive enhancement

Progressive enhancement builds a working baseline with HTML and adds JavaScript on top. The page is usable before the script loads, and better once it does.

The baseline is HTML

Start with a form that submits to a URL and a link that navigates. That page works on any device, in any browser, with JavaScript disabled or still downloading. Everything you add after that is an improvement rather than a dependency, and the baseline is also what search crawlers and social bots see.

<!-- works without JavaScript; the script only enhances it -->
<form action="/search" method="get">
  <label for="q">Search</label>
  <input id="q" name="q" type="search">
  <button type="submit">Go</button>
</form>
<noscript><p>Results are shown as a full page.</p></noscript>

Enhancing a form without breaking it

The enhancement intercepts the submit only when JavaScript is available, fetches the results and injects them. If the script never runs, the browser posts the form and the server answers with a full page. The same markup serves both paths, which is why the technique is robust rather than fragile.

const form = document.querySelector('#search-form');

form?.addEventListener('submit', async (e) => {
  e.preventDefault();                 // only reached if JS is running
  const html = await fetchResults(form.q.value);
  document.querySelector('#results').innerHTML = html;
});

Feature detection over user-agent sniffing

Decide what to load by testing for the feature, not by guessing the browser. Modern APIs are widely available but not universal, and a capability check degrades cleanly where a user-agent string does not. This is also how you honour accessibility preferences such as reduced motion.

// detect the capability, not the browser
if ('serviceWorker' in navigator) registerWorker();
if ('IntersectionObserver' in window) lazyLoad();

if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) {
  document.documentElement.dataset.motion = 'reduced';
}

Progressive enhancement is not nostalgia; it is the cheapest way to be resilient. A page built this way keeps working when a CDN blocking the script fails, a corporate proxy strips it, or the user simply has a slow connection.

5.5 SEO and accessibility of client rendering

Rendering in the browser changes what a crawler and a screen reader receive. Modern search engines execute JavaScript, but not all do, not instantly, and not for every kind of bot.

What a crawler actually receives

A client-rendered page sends an empty mount point; the content exists only after the bundle runs. Google can render JavaScript, but reliance on it delays indexing and adds failure modes, and social preview bots generally do not execute JavaScript at all. Server-rendered or generated HTML is indexed reliably and immediately.

what the crawler receives:
  client-only   <div id="app"></div>           empty document
  SSR or SSG    <main><h1>Real headline</h1>…  full document

social previews: a bot that does not run JavaScript
                 sees only the Open Graph tags in the shell

Per-route metadata and canonicals

A single-page app has one HTML document, but every route wants its own title, description and canonical URL. Emitting them per route — server-side or with a head manager — is what makes each view indexable as its own page. Without it, every route competes with the same metadata.

<!-- client-rendered routes must still ship real head tags -->
<meta property="og:title" content="Product: Blue Widget">
<meta property="og:description" content="In stock, ships today.">
<link rel="canonical" href="https://example.com/products/blue-widget">

Accessibility of client-side navigation

A client-side route change swaps content without a page load, so a screen reader is never told that anything happened, and focus stays where it was. Announce the change, update the document title, and move focus to the new heading. These few lines restore the cues a normal navigation gives for free.

// announce client-side navigation, or screen readers stay lost
const live = document.querySelector('#route-announcer');

function announce(title) {
  live.textContent = 'Navigated to ' + title;
  document.title = title;
  document.querySelector('h1')?.focus();
}

Do not ship a client-rendered marketing page and hope the crawler catches up. If a page must rank, render it to HTML on the server or at build time — the SEO risk of a JavaScript-only page is entirely avoidable.

6 ▸ Headless and Hybrid Patterns

6.1 Headless CMS6.2 JAMstack6.3 SSR with revalidation6.4 Edge rendering6.5 When hybrid wins

Most production sites are neither purely static nor purely dynamic; they are deliberate mixtures. This chapter covers the patterns that combine the two — headless CMS, JAMstack, SSR with revalidation, and edge rendering — and the cases where each one earns its complexity.

6.1 Headless CMS

A headless CMS stores and edits content but does not render it. It exposes an API, and the site — a generator, a server or a browser — decides how to present it.

Decoupling content from presentation

The CMS becomes the authors' tool and the source of truth for content; the site becomes the presentation layer that reads it through an API. The two evolve independently, so a redesign does not touch the editorial workflow and a new channel such as a mobile app reuses the same content. The cost is one more system to run and one more boundary to debug.

  Editor writes in the CMS ──▶ content API (JSON or GraphQL)
                                 │
                       build hook ▼
                             static build ──▶ CDN
                                 │
                       at runtime: /account/* ──▶ app server

Two ways to read content

A Git-based CMS commits content to a repository, so the site reads files and a rebuild is just a new commit. An API-first CMS keeps content in a database behind a JSON or GraphQL endpoint the build queries. The first gives you version history for free; the second gives you a real editorial UI and previews.

// Git-based headless: content lives in a repository
const res = await fetch(
  'https://api.github.com/repos/me/site/contents/posts'
);

// API-first headless: content lives behind a service
const { data } = await client.query({ query: GET_POSTS });

The trade, honestly

A headless CMS widens who can publish and keeps content portable, but it moves "why is my edit not live" from a server question to a build question and adds preview plumbing. For a small team editing a handful of pages a week, plain Markdown in the repo is often simpler and strictly more reliable.

headless CMS
  + editors get a real UI; developers get an API
  + content is decoupled from presentation
  - two systems to run; previews need wiring
  - "why is my edit not live" becomes a build question

Wire previews from day one. If editors cannot see an unpublished page before it goes live, they will publish to check, and the CMS has made the process worse.

6.2 JAMstack

JAMstack is a name for a delivery model: JavaScript for behaviour, APIs for data, Markup pre-built and served from a CDN. It is the static model plus a rebuild trigger.

What the acronym commits you to

The letters describe where each concern lives, not a specific technology. Markup is generated ahead of time, JavaScript runs in the browser, and any data that must be current comes from an API. The original tagline claimed no servers; the honest version is that you run no servers of your own for the served content.

JAMstack, expanded:
  JavaScript  behaviour in the browser
  APIs        data from services, not your own monolith
  Markup      pre-built HTML served from a CDN

// no servers of your own for the markup; the CDN does the work

Build hooks: publishing triggers a rebuild

When an editor publishes, the CMS fires a webhook at your build service, which rebuilds the affected pages and deploys atomically. The site is static at rest but current after a publish, and there is never a half-deployed state visible to a visitor. The webhook is the only glue between the CMS and the CDN.

POST /hooks/rebuild
{
  "event": "entry.publish",
  "entryId": "9f2c41"
}

// the build service rebuilds the affected pages and deploys

Where JAMstack stops working

The model breaks when content changes faster than a build can run, when pages are personalised per visitor, or when the work is long-running. A build that takes four minutes is fine for a blog and useless for a live scoreboard. Recognising that boundary is what pushes you toward revalidation or server rendering.

when JAMstack hurts:
  content changes faster than the build (minutes, not hours)
  pages must be personalised per visitor
  a request needs long-running or stateful server work

→ move to incremental revalidation, server rendering or an edge function

Do not trigger a full site rebuild on every keystroke in the CMS. Tie the hook to publish, not to save, or a busy editor will keep the build queue permanently full.

6.3 SSR with revalidation

The middle path renders a page once, caches the HTML, and rebuilds it in the background when it expires. Visitors get static speed and the content stays fresh without a redeploy.

Incremental revalidation

A revalidated route is served from cache, and after its time to live a rebuild is scheduled in the background; the next visitor triggers it and the one after that gets the fresh page. There is no full-site rebuild, so a single changed product updates without touching the other thousand. This is the pattern that makes a catalogue feel static without being stale.

// Next.js App Router: static output, refreshed in the background
export const revalidate = 60;   // seconds

export default async function Page({ params }) {
  const post = await getPost(params.slug);   // cached, revalidated
  return <Article post={post} />;
}

Streaming and partial rendering

Instead of holding the response until the slowest query finishes, a server can stream the HTML: send the shell immediately and fill in slower widgets as they resolve. The user sees a useful page sooner, and the slow part arrives without blocking the rest. Suspense boundaries are how a framework marks the parts that may be deferred.

// stream the shell first, the slow widget when it is ready
import { Suspense } from 'react';

export default function Page() {
  return (
    <>
      <Header />
      <Suspense fallback={<Skeleton />}>
        <SlowRecommendations />
      </Suspense>
    </>
  );
}

Cache headers are the whole contract

Whether a page is per-visitor or shared is decided by its Cache-Control header, not by the framework. Shared pages may be cached publicly and served stale while revalidating; per-user pages must be private and uncached. Getting this wrong is how one user's dashboard ends up served to another.

# the contract between the app and every proxy in front of it
public, s-maxage=3600, stale-while-revalidate=86400   # shared, may go stale
private, no-store                                     # per user, never cached
public, max-age=0, must-revalidate                    # must be rechecked

Revalidating every second does not give you a dynamic site; it gives you a static site that pays a rebuild cost constantly. If content must be current to the second, render it per request instead.

6.4 Edge rendering

Edge functions run your code close to the visitor, in many small regions rather than one data centre. They add personalisation and header logic to a static delivery model with almost no cold start.

What the edge is good at

An edge function runs on every request in the nearest region, so it can rewrite a URL, add security headers, do an A/B split or assemble a personalised page from cached fragments. The distance from user to compute is small, so the added latency is a few milliseconds rather than a network hop to an origin.

// a Cloudflare Worker adds a header at the edge, before the origin
export default {
  async fetch(request) {
    const res = await fetch(request);
    const out = new Response(res.body, res);
    out.headers.set('X-Edge', 'lhr');
    return out;
  },
};

Edge plus cache

The productive pattern is "cache first, edge to personalise": serve a cached static shell, and let the edge function inject the parts that must differ per visitor. That keeps the expensive rendering at build time while the per-visitor work stays tiny and cheap at the edge. It is the pragmatic blend of static speed and dynamic content.

// edge middleware: cached shell in, personalised markers out
export async function middleware(request) {
  const shell = await caches.default.match(request);
  const html = shell ? await shell.text() : render('home');
  return new Response(html.replace('__USER__', userName(request)), {
    headers: { 'content-type': 'text/html; charset=utf-8' },
  });
}

Edge constraints to design around

Edge runtimes are not full servers: CPU time per request is capped, there is no local filesystem, native modules are unavailable, and only part of the Node API surface exists. Anything that needs a database connection pool, a large in-memory cache or a long computation belongs on an origin server, not at the edge.

edge runtime constraints (typical):
  CPU per request:   10 to 50 ms (CPU only, not wall clock)
  no local filesystem, no native modules
  a reduced Node API surface
  cold starts near zero, but a fixed set of regions

Treat the edge as a fast filter in front of your origin, not as a replacement for it. It is excellent at headers, routing and small personalisation, and poor at anything long, stateful or database-heavy.

6.5 When hybrid wins

Hybrid architecture wins when different routes have genuinely different needs. The skill is decomposition, not picking a single platform and forcing every page into it.

Match the model to the route

List the routes, then choose the cheapest model that satisfies each one's staleness and personalisation needs. Marketing pages are static, a catalogue is revalidated, search is client-side, and account pages are rendered per request. The result is a site where each part costs exactly what it must.

route type            best model
marketing pages       static
docs and blog         SSG, rebuild on push
product catalogue     revalidated, refreshed on change
search results        client-side plus an API
account and checkout  rendered per request

A shop, decomposed

The same site uses four strategies and none of them is gratuitous. The marketing shell is static and greets a crawler with full HTML; the catalogue revalidates so a price change appears without a deploy; the cart is server-rendered so it never flashes empty; checkout is per-request with no caching at all. Every dynamic route earns its cost.

a shop, route by route:
  /                static marketing shell
  /catalogue/*     revalidated, refreshed from the feed
  /cart            session-backed, server-rendered
  /checkout        per request, never cached
  /api/*           JSON for the client widgets

The pitfalls hybrids invite

Mixing models multiplies the ways caching can go wrong. A per-user page cached publicly leaks data; two systems holding the same record drift apart; a delete with no purge leaves ghosts for the whole time to live. Every cache needs an explicit invalidation path, and the rule is simple: if it can be cached, something must be able to uncache it.

hybrid pitfalls:
  caching a per-user page publicly   → data leak
  revalidating constantly             → self-inflicted load
  two sources of truth                → silent drift
  no purge on delete                  → ghosts live for the TTL

Write the cache strategy as a table in the repository: route, model, TTL, and what invalidates it. A one-page table prevents the only class of bug that hybrids actually create.

7 ▸ Choosing and Migrating

7.1 A decision matrix7.2 Migration paths7.3 Security and performance7.4 Maintenance and cost realities

The models are all defensible in the abstract; the work is picking one for a specific site and moving between them without a rewrite. This chapter gives a decision procedure, the migration paths, a security and performance comparison, and the maintenance and cost realities that decide the answer in practice.

7.1 A decision matrix

Solve for the constraints in order of how hard they are to change: data authority first, personalisation second, ranking third, and cost last. The matrix is a way to make the trade explicit rather than to hide it.

Five questions, asked in order

Each question eliminates options. If any page must be personalised, pure static is gone; if any content changes between builds, pure SSG alone is gone unless you revalidate. Ask them before you look at a framework, because the framework is downstream of the answer.

Ask, in order:
  1. Who writes the content, and how often?
  2. Does any page differ per visitor?
  3. What must survive between requests (sessions, carts)?
  4. Which pages must rank in a search engine?
  5. What is the smallest operations burden you can accept?

Scoring the models against each other

Score each model on the qualities that matter and let the arithmetic break the tie. The point is not the exact numbers but the shape: simplicity and first-paint favour static, while per-user content favours rendering per request. Where a model scores badly on a requirement you cannot waive, it is out.

score 0-5, higher is better:
                  static  SSG   ISR   SSR   CSR
simplicity           5     4     3     2     2
first paint          5     5     4     3     1
per-user content     0     0     2     5     5
search engine ready  5     5     5     5     2
cheap at scale       5     5     4     2     3

Defaults that rarely disappoint

When there is no strong reason otherwise, a handful of defaults cover most projects. They are deliberately boring, because the site that ships and stays up beats the architecture that reads well in a design document. Start here and deviate only for a named constraint.

defaults that rarely disappoint:
  content site        → SSG plus a CDN
  small business      → static pages plus a hosted form
  authenticated app   → server rendering plus a JSON API
  interactive product → client rendering behind auth,
                        with a static marketing shell

The matrix is a conversation aid, not an oracle. If two models score within a point, choose the one with the smaller operational burden, because that cost recurs every week while the other advantages are usually smaller than they look.

7.2 Migration paths

Migrations between the models should be incremental. You move one route at a time, keep the URLs identical, and leave the old system answering everything you have not yet moved.

Static toward dynamic, one route at a time

Start static and add a server only for the routes that need one. A proxy in front of the CDN sends form posts and signed-in paths to the application and everything else to the static files. This preserves the static site's speed for the majority of traffic while adding exactly the dynamic capability that was missing.

routes = {
  '/':          static,
  '/blog/*':    static,
  '/contact':   proxy to a serverless function,   # form handling
  '/account/*': server,                           # session required
}

Dynamic toward static, by narrowing the boundary

Most dynamic sites render many pages that do not actually depend on the request. Identify them, generate them ahead of time, and keep the remaining per-user routes on the server. The result is the same application code with a much smaller runtime footprint and a much faster read path.

before: every page rendered per request, a database hit each time
after:  public pages pre-built; only /account/* hits the server

steps:
  1. list pages whose output does not depend on the request
  2. give them a build; keep the URLs identical
  3. add a rebuild hook on content publish
  4. leave the genuinely dynamic routes alone

The strangler pattern

Run the new site beside the old one and move routes across one by one, using a proxy that sends each path to whichever system now owns it. Nothing is big-bang, every step is reversible, and the old application is retired only when no route points at it any more. This is the safest way to change a rendering model on a site that must stay up.

proxy rules during a migration:
  /                → new static site
  /blog/*          → new static site
  /legacy/*        → old application
  everything else  → old application

# retire the old app when no route points at it

Keep the URLs byte-identical through a migration. Changing a path while changing the rendering model means you cannot tell which change broke a page, a link or a ranking, and you cannot roll one back without the other.

7.3 Security and performance

The two models differ less in what they can achieve than in what can go wrong. Static removes whole classes of vulnerability; dynamic adds capability and new responsibilities.

Attack surface by model

A static site cannot be injected, because there is no query and no session to steal; the worst case is taking the host down or serving a compromised build. A dynamic site must handle untrusted input, guard authentication and patch its dependencies. The more code runs per request, the more there is to get right, every time.

attack surface by model:
  static    take the host down; no injection, no session to steal
  SSG       build-time supply chain; commit access is deploy access
  SSR       input handling, injection, auth, dependency advisories
  CSR + API everything SSR has, plus tokens stored in the browser

Performance expectations

Given the same content and the same host, static delivery wins on every metric because the response already exists. Server rendering adds compute latency that grows with traffic; client rendering hides that latency in the bundle instead. The honest comparison is time to first meaningful content, not the number on a synthetic benchmark.

same content, same host, mid-range device:
  static    time to first byte ~20 ms, first content ~0.4 s
  revalidated  cache hit, effectively static for readers
  SSR       time to first byte 80 to 400 ms, scales with load
  CSR       shell fast, content waits for the bundle

Measure before you argue

Most performance debates are settled by two commands and a dashboard. Measure time to first byte, run an audit, and load-test the endpoint behind the page. Numbers from your own stack end an argument that opinions cannot.

# measure the thing you are about to argue about
$ curl -o /dev/null -s -w 'ttfb %{time_starttransfer}s\n' https://example.com/
$ npx lighthouse https://example.com --only-categories=performance
$ npx autocannon -c 50 -d 20 https://staging.example.com/api/posts

Track these numbers over time, not once. Performance regresses quietly as content, dependencies and third-party scripts accumulate, and a weekly check catches it long before a user complains.

7.4 Maintenance and cost realities

The cost of a site is mostly the cost of running it, not building it. This closing topic compares the ongoing bill — money and attention — across the models.

The recurring bill

Static hosting for millions of requests costs a few pounds because it is bandwidth and storage. A server-rendered application costs a host, a database, backups and monitoring, and those scale with traffic and with the quality of the code. The difference is not the server's price tag; it is the attention the runtime demands.

static site, 2,000,000 requests per month:
  CDN egress plus build minutes        ≈ a few pounds

server-rendered app, same traffic, one small instance:
  2 vCPU host, backups, monitoring     ≈ tens of pounds
  plus the slice of every week it consumes in maintenance

What the team has to own

A static stack needs HTML, CSS and Git. A dynamic stack adds a runtime, a database, migrations, connection limits and a dependency tree to patch. Both are maintainable; only one of them pages someone at three in the morning when it fails. Match the stack to the team that will actually run it.

static stack              dynamic stack
HTML, CSS, git            plus a runtime and a database
one deploy command        migrations, rollbacks, connection limits
fewer advisories          a dependency tree to keep patched
nothing idle to attack    a service that runs around the clock

A last checklist before you commit

Run through this list once per project and once per significant change. It catches the decisions that are expensive to reverse: content velocity, data reachability at build time, crawlability, invalidation, and ownership. If every box is ticked, the model is the right one for now.

before you commit to a model, confirm:
[ ] content velocity is known, not assumed
[ ] no page needs data you cannot fetch at build time
[ ] a search crawler will see real HTML
[ ] there is a purge or rebuild story for stale content
[ ] someone owns the runtime, not just the code

Revisit the decision when the traffic, the team or the content model changes. A rendering strategy is a snapshot of those constraints, and the constraints are the part that actually moves.
