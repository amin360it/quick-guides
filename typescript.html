The right mindset

Adopt the mindset that types are documentation the compiler enforces on your behalf. Rather than treating type errors as annoyances, see them as TypeScript catching mistakes you would otherwise ship. Let the compiler act as your safety net so runtime bugs surface as compile-time messages before anything reaches users.

Think of TypeScript as documentation that the compiler enforces. The type you write on a function tells every future reader what it accepts and returns — and the compiler checks that the code honours it. The type system is the point, not the syntax.

Keep the official docs open beside this guide at typescriptlang.org/docs. This guide explains the why and the sequence; the docs are the exhaustive reference.

1 · Why TypeScript & Project Setup

1.1 The problems TypeScript solves1.2 Static versus dynamic typing1.3 Installing and compiling1.4 Your first file: compile versus run

Explains the problems TypeScript solves and gets a compiling project running on your machine. You install TypeScript, create a tsconfig.json, and write your first typed .ts file. You finish with a working build command that compiles your file to JavaScript you can actually run with Node.

JavaScript is a dynamic language: anything can hold anything, and mistakes surface at runtime, often in production. TypeScript adds a compile-time type system that catches whole classes of bugs before they ship, while emitting the same JavaScript you already know.

1.1 The problems TypeScript solves

Shows the runtime errors that static typing catches before deployment. The most common bugs are renamed properties, wrong data shapes, and missing null checks, all of which a compiler can detect. Annotating your data and enabling strict null checks turns these silent failures into loud compile-time errors.

// plain JS — fails at runtime, on a real user's machine
function greet(user) {
    return user.firstName;          // TypeError if user is null or misspelled
}
greet(undefined);

// TypeScript — same idea, error at compile time
function greet(user: { firstName: string }) {
    return user.firstName;
}
greet(undefined);                   // Error: undefined not assignable to the shape

The JavaScript version crashes when it runs; TypeScript flags the same mistake the moment you type it, before anything reaches a user.

1.2 Static versus dynamic typing

Contrasts static type checking at compile time with dynamic checking at run time. Dynamic languages verify values while the program runs, but static typing checks before anything executes. Because the checks happen ahead of deployment, errors surface earlier and the compiled output carries no runtime cost.

PropertyDynamic (plain JS)Static (TypeScript)
When errors appearAt run timeAt compile time
Runtime overheadNoneNone — types are erased
AutocompleteHeuristicExact, from your code
Files ship as.js.js (types erased)

1.3 Installing and compiling

Installs TypeScript in a project with npm, then uses the tsc command to compile a folder of files into JavaScript. A single tsconfig.json file controls the whole toolchain, including the target version, the output directory, and strictness. The same configuration drives every build command you run.

npm install -g typescript
tsc --version           # v5.x

mkdir hello && cd hello
npm init -y
npm install --save-dev typescript @types/node
npx tsc --init          # generates tsconfig.json

Installing TypeScript gives you the tsc compiler, and npx tsc --init writes a default tsconfig.json that controls how your project compiles.

1.4 Your first file: compile versus run

Writes a typed .ts file and compiles it to JavaScript, then runs the output with Node. Browser and Node never see your types because tsc erases them during compilation. The source you edit is TypeScript; the code you ship and run is plain JavaScript.

// greet.ts
const name: string = 'Aria';
const visits: number = 42;
console.log(`Hello ${name}, visit ${visits}`);

// terminal
npx tsc greet.ts            # emits greet.js
node greet.js               # Hello Aria, visit 42

// dev loop — run .ts directly, no emit step
npm install tsx
npx tsx greet.ts            # executes the file with no compile step

tsc emits plain JavaScript that Node runs; tsx skips the emit step and executes .ts directly, which keeps the inner dev loop fast.

2 · Basic Types, Inference & Assertions

2.1 Primitives and arrays2.2 Tuples and the special types2.3 Inference versus annotations2.4 Type assertions and satisfies

Covers every built-in primitive type, how TypeScript infers types from values, and the escapes of type assertions and the satisfies keyword. These form the atoms that every larger type is built from. Master these fundamentals because all later chapters compose them into structures, functions, and generics.

Before shapes, unions and generics comes the alphabet: strings, numbers, booleans, arrays and a handful of special types. Learn which type means what, and the rest of the type system reads like prose.

2.1 Primitives and arrays

Shows the core types: string for text, number for numeric values, boolean for true and false, and arrays written like string[] with an element type followed by brackets. Annotations read left to right and match how you describe a value in English, so string[] is an array of strings.

const title: string = 'TypeScript';   // any text
const count: number = 12;             // integers and floats share one type
const active: boolean = true;

const tags: string[] = ['ts', 'guide'];        // array of strings
const matrix: number[][] = [[1, 2], [3, 4]];   // array of array of numbers
const mixed: (string | number)[] = ['a', 1];   // array that can hold either

Primitives use lowercase names, arrays append [], and parentheses group unions so the brackets type every element rather than one position.

2.2 Tuples and the special types

Explains fixed-size tuples written like [string, number], where order and length are part of the type, plus the special types any, unknown, never, void, null and undefined. Each special type exists for exactly one precise job, so use them deliberately and prefer unknown over any for untyped data.

const point: [number, number] = [10, 20];   // tuple: fixed length and positions
const named: [string, number?] = ['Aria'];  // trailing element may be absent

let anything: any = 42;          // opts out of checking — avoid in new code
let data: unknown = JSON.parse(text);   // any value, must narrow before use
function fail(): never { throw new Error('boom'); }   // never returns
function log(): void { console.log('no return value'); }  // returns undefined
const maybe: string | null = null;   // null is an ordinary value

Tuples fix length and position, any turns checking off, unknown says the value exists but its type is unknown, never marks unreachable code, and void means no return value.

2.3 Inference versus annotations

Shows when TypeScript infers types for you and when to write them explicitly. Inference is the default, so variables take their type from their initial value. Reserve explicit annotations for the contracts at your boundaries, such as function parameters, return types, and exported APIs.

let score = 100;         // inferred as number — no annotation needed
score = 'high';          // Error: string is not assignable to number

const settings = { theme: 'dark', open: true };   // inferred object shape

// annotate the boundary: what a function accepts and what it returns
function double(n: number): number {
    return n * 2;
}

Let the compiler infer locals, and write annotations at the boundaries of your program — function parameters and returns — where the contract matters.

2.4 Type assertions and satisfies

Covers the as keyword for type assertions, the non-null operator written as a trailing exclamation mark, and the satisfies keyword for checking a shape without widening the inferred type. Assertions override the compiler’s judgment, so use them sparingly. Prefer satisfies when you want validation without losing inference.

const input = document.getElementById('name') as HTMLInputElement;  // I know better
const el = document.getElementById('name')!;   // non-null: it definitely exists

// satisfies: check a shape WITHOUT changing its inferred literal types
const config = {
    port: 3000,          // inferred literal type 3000, not any number
} satisfies Record<string, number | string>;

config.port.toFixed(1);   // still 3000, so the number method remains available

as overrides the compiler when you know more than it does, ! strips null, and satisfies validates a shape while preserving the specific inferred types.

3 · Functions, Overloads & this

3.1 Parameter and return types3.2 Optional, default and rest parameters3.3 Arrow functions and higher-order types3.4 Function overloads3.5 Typing this in functions

Covers everything about typing functions: parameters, return types, arrow functions, overloads, and the this keyword. Functions are where most real contracts live in a codebase, because every call site is checked against the declared signature. Getting these annotations right types the rest of your program.

A function signature is a promise the compiler checks on both sides: it verifies callers pass the right arguments and that the body returns what it advertised. Learn to read and write these signatures and you can type any codebase.

3.1 Parameter and return types

Shows the basic function signature: typed parameters followed by a typed return value, written with the return type after the parameter list. Every annotation is checked on every call, so passing the wrong argument or expecting the wrong result is caught at compile time. Leave annotations off where inference can fill them.

function total(items: number[], discount: number): number {
    const sum = items.reduce((a, b) => a + b, 0);
    return sum * (1 - discount);
}
total([10, 20], 0.1);       // 27 — number array, number, returns number
total([10, 20], '10%');     // Error: string is not assignable to number

The signature advertises what callers may pass and what comes back; passing the wrong kind of discount is rejected before it reaches the arithmetic.

3.2 Optional, default and rest parameters

Shows the three ways parameters become flexible: optional parameters with a trailing question mark, default values with an equals sign, and rest parameters with three dots that gather remaining arguments into an array. Defaults and optionals overlap in effect, so prefer defaults since they also supply a value.

function greet(name: string, punctuation = '!', excited?: boolean): string {
    const mark = excited ? punctuation.toUpperCase() : punctuation;
    return `Hello, ${name}${mark}`;
}

function joinAll(separator: string, ...parts: string[]): string {
    return parts.join(separator);
}
joinAll('-', 'a', 'b', 'c');   // 'a-b-c' — rest collects the remaining arguments

Defaults make a parameter optional with a value, ? makes it optional and possibly undefined, and rest gathers the remaining arguments into a typed array.

3.3 Arrow functions and higher-order types

Types arrow functions inline and names callable types. A function type reads parameters, then a fat arrow, then the return type, so the signature describes exactly what the function takes and produces. A named type alias or interface makes that signature reusable across many variables and parameters.

const square = (n: number): number => n * n;

type Transformer<T> = (value: T) => T;      // a named function type
const upper: Transformer<string> = (s) => s.toUpperCase();

function applyTwice(fn: Transformer<number>, n: number): number {
    return fn(fn(n));
}
applyTwice((x) => x + 1, 5);                  // 7

A callable type like Transformer<T> describes a whole family of functions, and higher-order functions pass them around like any other value.

3.4 Function overloads

Declares several call signatures for one function so the return type matches the arguments you pass. The header lists the overloads the caller may use, and the body is the broadest implementation that has to satisfy every one of them. This pattern is ideal for functions whose result depends on input shape.

function format(input: string): string;
function format(input: number, places: number): string;
function format(input: string | number, places?: number): string {
    return typeof input === 'string' ? input.trim() : input.toFixed(places);
}

format('  hi  ');       // string overload — trims and returns a string
format(3.14159, 2);     // number overload — "3.14"

Overloads tell the compiler exactly what each call shape returns, while one implementation underneath handles every declared case.

3.5 Typing this in functions

Shows how to type the this parameter and how it drifts in callbacks. In methods this refers to the receiver, but plain callbacks can lose that binding. Timers and event handlers often need arrow functions or bind to keep this pointing exactly where you expect.

interface Counter {
    count: number;
    step(this: Counter, amount: number): void;   // the caller must provide this
}

const c: Counter = {
    count: 0,
    step(this: Counter, amount: number) {
        this.count += amount;
    },
};
c.step(2);                       // this is c
setInterval(() => c.step(1), 1000);   // arrow captures c, so this still works

Declaring this as a first fake parameter makes the compiler enforce the call-site context, and arrows or bind keep that context alive inside callbacks.

4 · Objects, Interfaces & Type Aliases

4.1 Object types, inline and named4.2 Interface versus type alias4.3 Optional, readonly and index signatures4.4 Extending and declaration merging4.5 Excess property checks

Shapes data with object types, interfaces and type aliases. This chapter provides the vocabulary for describing most real-world data, from configuration objects to API responses. Use interfaces for objects and public APIs, and type aliases for unions, tuples, and computed shapes.

Almost every meaningful value in a program is an object, so object typing is where the type system earns its keep. TypeScript checks objects structurally: what matters is the shape you have, not the name it was declared under.

4.1 Object types, inline and named

Writes an object type in place and then with a name. Annotating a parameter is enough for the compiler to check every property access against the declared shape. Inline objects suit one-off uses, while a named interface or alias becomes reusable across your whole codebase.

function printUser(user: { id: number; name: string }) {
    console.log(user.id, user.name);
}

// named with a type alias, reusable in many places
type User = { id: number; name: string };
type Users = User[];   // an array of the same shape

printUser({ id: 1, name: 'Aria' });

An inline object type works for a single signature; giving the shape a name lets every function and data structure reuse it consistently.

4.2 Interface versus type alias

Shows interfaces and type aliases doing the same job in different ways. Interfaces support extends and declaration merging and are preferred for objects and public APIs. Type aliases handle unions, tuples, and computed shapes, and can alias any type expression at all.

interface Animal {
    name: string;
}
type AnimalAlias = { name: string };   // functionally identical for a plain object

// both extend, with different syntax
interface Dog extends Animal {
    breed: string;
}
type DogAlias = Animal & { breed: string };   // intersection

// only a type alias can name a union or a tuple
type Status = 'idle' | 'running' | 'done';
type Pair = [string, number];

For plain objects the two are largely interchangeable, but interfaces extend and merge while type aliases can name unions, tuples and computed shapes.

4.3 Optional, readonly and index signatures

Adds optional and readonly markers, plus index signatures for dictionary objects. A question mark after a property name makes it optional, readonly forbids reassignment of that member, and an index signature like [key: string]: number types any key the object might hold.

interface Config {
    host: string;
    port?: number;               // optional — may be omitted
    readonly apiKey: string;     // cannot be reassigned after creation
}

type Lookup = { [key: string]: number };   // index signature: any string key
const counts: Lookup = { apples: 3, pears: 5 };
counts.apples = 4;               // fine — values are numbers
counts.apples = 'x';             // Error: must be a number

? marks an optional field, readonly freezes the property, and an index signature types dictionary objects whose keys are only known at runtime.

4.4 Extending and declaration merging

Shows interface inheritance with the extends keyword and the unique interface trait of declaration merging. One interface can extend another to add properties, and two interfaces with the same name in the same scope combine automatically. Type aliases can intersect but cannot merge like this.

interface BaseAnimal { name: string; }
interface Pet extends BaseAnimal { owner: string; }
interface Pet { age: number; }            // merging: Pet now has owner AND age

const pet: Pet = { name: 'Rex', owner: 'Aria', age: 3 };

// declaration merging in the wild: augment framework globals
declare global {
    interface Window { analyticsEnabled: boolean; }
}

Interfaces extend other interfaces and merge when declared twice, which is exactly how libraries and your own code augment global types like Window.

4.5 Excess property checks

Explains why object literals get stricter checking than variables. A fresh literal passed directly reports extra keys it was not declared to have, catching typos such as misspelled properties. An existing variable that merely has the same shape does not trigger that check.

interface User { id: number; name: string; }

function save(user: User) {}

save({ id: 1, name: 'Aria', admin: true });   // Error: 'admin' does not exist

const realUser = { id: 1, name: 'Aria', admin: true };   // no error
save(realUser);   // extra props are fine — the required shape still matches

Fresh object literals are checked for extra keys — a typo magnet — while variables are checked structurally, so the same extra property passes silently.

This is structural typing: TypeScript asks "does the value have the shape?", not "is it an instance of X?". That is why plain objects satisfy interfaces.

5 · Unions, Intersections & Narrowing

5.1 Union and intersection types5.2 Narrowing with typeof, instanceof and in5.3 Discriminated unions5.4 Type guards and assertion functions5.5 Exhaustiveness with never

Combines types into unions and intersections, then narrows the possibilities down to one at runtime. Union means or and intersection means and, giving you either free choice or a combined shape. Narrowing is the skill that makes unions safe and practical, with the compiler verifying every case you handle.

A value often legitimately has several possible shapes: a form field is a string or a number, a fetch result is success or failure. Unions describe "one of these", and narrowing — shrinking to one branch with checks — is how the compiler lets you handle each possibility safely.

5.1 Union and intersection types

Defines unions of alternatives with the pipe operator and intersections that require everything with the ampersand operator. Union is or, so the value satisfies at least one member. Intersection is and, so the value satisfies all members at once and carries every property of each.

type Admin = { name: string; permissions: string[] };
type Employee = { name: string; team: string };
type AdminEmployee = Admin & Employee;   // intersection: both shapes at once

const who: AdminEmployee = {
    name: 'Aria',
    permissions: ['read'],
    team: 'platform',
};

type Id = string | number;   // union: exactly one of these
function printId(id: Id): string { return typeof id === 'number' ? String(id) : id; }

A union says the value is any one of the listed types; an intersection demands every shape at once. Both are checked structurally, not by name.

5.2 Narrowing with typeof, instanceof and in

Shows the three built-in ways to narrow a union: typeof for primitives, instanceof for classes, and the in operator for object members. Control flow analysis shrinks the type as you write the checks, so after each guard the compiler knows exactly which branch you are in.

function describe(x: string | number | Date): string {
    if (typeof x === 'string') return x.toUpperCase();
    if (typeof x === 'number') return x.toFixed(2);
    if (x instanceof Date) return x.toISOString();
    return 'unknown';
}

function move(obj: { x: number } | { speed: number }) {
    if ('speed' in obj) return obj.speed;   // narrows to the speed member
    return obj.x;                           // only the other alternative remains
}

typeof, instanceof and in each look at a different kind of evidence, and after the check TypeScript swears to the narrowed branch only.

5.3 Discriminated unions

Uses a literal tag field so every branch of a union is provably distinct. Each member carries a unique literal property, and checking that tag narrows the whole object at once. A discriminated union is the standard pattern for actions, results, and state machines.

type UiEvent =
    | { type: 'click'; x: number; y: number }
    | { type: 'key'; key: string }
    | { type: 'blur' };

function handle(e: UiEvent) {
    switch (e.type) {
        case 'click': return `clicked at ${e.x},${e.y}`;
        case 'key':   return `pressed ${e.key}`;
        case 'blur':  return 'left the field';
    }
}

The literal type field is the discriminator: switching on it narrows e to exactly one variant, and each case sees only its own fields.

5.4 Type guards and assertion functions

Writes user-defined guards with type predicates that test a custom shape, and assertion functions that throw on bad input instead of returning a boolean. A predicate such as value is string teaches the compiler to narrow custom types that the built-in operators cannot handle.

function isFish(pet: Animal): pet is Fish {
    return 'swim' in pet;
}

type User = { name: string; email?: string };
function assertHasEmail(user: User): asserts user is User & { email: string } {
    if (!user.email) throw new Error('Email is required');
}

const u: User = loadUser();
assertHasEmail(u);         // from here on, u.email is a plain string
u.email.toUpperCase();     // no narrowing dance needed

A type predicate says when isFish is true the value is a Fish; an assertion function throws unless its claim holds, then permanently narrows the rest of the scope.

5.5 Exhaustiveness with never

Uses the never type to make the compiler complain when a new union member is forgotten. Every branch narrows away its own case, and the default branch becomes a compile-time tripwire that flags anything missed. This forces you to handle each possibility or update the code deliberately.

function assertNever(value: never): never {
    throw new Error(`Unhandled case: ${JSON.stringify(value)}`);
}

function reactor(e: UiEvent): string {
    switch (e.type) {
        case 'click': return 'click';
        case 'key':   return 'key';
        default:      return assertNever(e);   // Error when a new variant appears
    }
}

If someone adds a fourth UiEvent variant, e narrows to it in the default branch and the compiler rejects passing it to assertNever — the missing case fails the build.

Wide union, narrow fast. Keep unions broad where data arrives and narrow as early as possible; every branch you remove makes the rest of the code simpler.

6 · Generics

6.1 Generic functions6.2 Constraints and multiple type parameters6.3 Generic interfaces and classes6.4 Default type parameters and keyof6.5 Common generic patterns

Makes functions and types work for any type while keeping relationships straight. A type parameter acts as a placeholder that is filled in at the call site. Generics are how you write one function, typed for everything, without losing the connection between the input and output types.

The first array helper you ever wrote probably worked for any element type. Generics formalise that: a type parameter stands in for the real type, the compiler figures it out at each call site, and — crucially — it keeps related types glued together.

6.1 Generic functions

Adds a type parameter to a function so the same function works for strings, numbers, or your own types. The type parameter is a placeholder that inference, plus optional explicit arguments at the call site, fills in. The compiler then checks each call against the specific type supplied.

function first<T>(items: T[]): T | undefined {
    return items[0];
}

first([1, 2, 3]);          // T infers as number — returns number
first(['a', 'b']);         // T infers as string — returns string
const x = first([1, 2]);   // x: number — T was pinned by the argument

The single type parameter T is inferred from the argument, and every T in the signature stays glued together — the return type always matches the element type.

6.2 Constraints and multiple type parameters

Limits type parameters with the extends keyword so a generic only accepts shapes with a required minimum, and coordinates several type parameters that reference each other. Constraints promise the smallest shape a type must have. They let you access those promised members safely inside the generic body.

function longest<T extends { length: number }>(a: T, b: T): T {
    return a.length >= b.length ? a : b;
}
longest('cat', 'elephant');        // strings have .length — works
longest([1, 2], [3, 4, 5, 6]);     // arrays have .length — works

function pair<K, V>(key: K, value: V): [K, V] {
    return [key, value];
}
pair(1, 'one');   // [number, string] — two independent type parameters

The extends constraint admits only types with a length property, while the two-parameter pair function keeps the key type and value type independent yet connected.

6.3 Generic interfaces and classes

Builds reusable structures with type parameters on interfaces and classes. A generic box or stack stores whatever element type you supply while preserving its identity. Instantiate it with a concrete type argument and every method and property reflects that specific element.

interface Box<T> {
    value: T;
    set(value: T): void;
}

class Stack<T> {
    private items: T[] = [];
    push(item: T): void { this.items.push(item); }
    pop(): T | undefined { return this.items.pop(); }
    get size(): number { return this.items.length; }
}

const numbers = new Stack<number>();
numbers.push(7);
numbers.push('oops');   // Error: string is not assignable to number

A generic interface or class parameterizes its members, so a Stack<number> stores numbers and rejects anything else at compile time.

6.4 Default type parameters and keyof

Shows default type parameters and the keyof operator, which turns an object’s keys into a union of literal strings. Combine them to build typed getters and pickers that accept only real keys. A default makes a type parameter optional for the caller.

function getValue<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
}

type Point = { x: number; y: number; label: string };
getValue({ x: 1, y: 2, label: 'p' }, 'x');     // number
getValue({ x: 1, y: 2, label: 'p' }, 'z');     // Error: 'z' is not in keyof Point

function makeList<T = string>(): T[] { return []; }   // default: T = string
makeList<number>().push(1);   // T overridden to number at the call site

keyof collects the object’s keys into a literal union, so getValue accepts only real keys and returns the exact value type at that key; defaults cover the omitted parameter.

6.5 Common generic patterns

Collects the generic patterns you will see daily: typed fetch wrappers that know the response shape, identity helpers that preserve a type, and generic caches keyed by type. Each pattern is the same placeholder logic applied to a different domain. Learn to read these and generics become ordinary.

async function getJSON<T>(url: string): Promise<T> {
    const res = await fetch(url);
    if (!res.ok) throw new Error(res.statusText);
    return res.json() as T;
}
getJSON<{ id: number; title: string }>('/posts/1');   // typed response

function identity<T>(value: T): T { return value; }

function cache<T>(): { get: () => T | undefined; put: (v: T) => void } {
    let slot: T | undefined;
    return {
        get: () => slot,
        put: (v) => { slot = v; },
    };
}

A generic fetch wrapper types the JSON response at the call site, identity passes a type through untouched, and a generic cache closure keeps one consistent element type.

Generics can be over-used. If a type parameter appears once and only once, you usually do not need it — you are handwriting a specific type, not a pattern.

7 · Classes, Access Modifiers & Decorators

7.1 Typing a class7.2 Access modifiers and readonly7.3 Abstract classes and implements7.4 Parameter properties and static members7.5 Decorators overview

Types classes, controls the visibility of members, and meets experimental decorators. Classes blend runtime behaviour with compile-time shape checking, and the class name works as both a value and a type. Modifiers like private and protected are enforced by the compiler, not at run time.

Classes are where TypeScript feels most like a typed language: fields carry types, modifiers set visibility, and the class name works as both a constructor and a type. Modern code increasingly favours functions, but classes remain the backbone of frameworks and domain models.

7.1 Typing a class

Writes a class and lets it serve as both a value and a type. In a type position, the class name refers to the shape of its instances, so any object with the same members is assignable to it. This duality lets you type variables without naming a separate interface.

class Rectangle {
    width: number;
    height: number;

    constructor(width: number, height: number) {
        this.width = width;
        this.height = height;
    }

    area(): number { return this.width * this.height; }
}

const rect: Rectangle = new Rectangle(3, 4);   // Rectangle also names a type
function printArea(r: Rectangle): void {
    console.log(r.area());
}
printArea(rect);   // 12

A class both constructs values and names the type of its instances, so variables and parameters can be typed with the class name directly.

7.2 Access modifiers and readonly

Shows public, private, protected, and readonly modifiers on class members. The access modifiers control who may read or write each member, with private restricting access to the class itself. These defaults are enforced at compile time, so they affect checks but not the emitted JavaScript.

class BankAccount {
    public owner: string;              // visible everywhere (the default)
    private balance = 0;               // only inside this class
    protected history = [];            // class and its subclasses only
    readonly id: number = Math.random();

    deposit(amount: number): void { this.balance += amount; }
    getBalance(): number { return this.balance; }
}

const acc = new BankAccount('Aria');
acc.balance;         // Error: property 'balance' is private
acc.deposit(50);     // fine — deposit is public
acc.id = 4;          // Error: readonly property cannot be assigned

public, private and protected gate each member’s visibility, and readonly freezes the property after construction — all enforced while compiling, not at runtime.

7.3 Abstract classes and implements

Uses abstract classes as templates and the implements keyword to satisfy interfaces. An abstract class can declare abstract methods that force subclasses to fill in the blanks before they can be instantiated. implements checks that a class matches a shape without inheriting any of its implementation.

abstract class Shape {
    abstract area(): number;          // subclasses MUST implement this
    describe(): string { return `Shape of area ${this.area()}`; }
}

class Circle extends Shape {
    constructor(private radius: number) { super(); }
    area(): number { return Math.PI * this.radius ** 2; }
}

interface Describable { describe(): string; }
const thing: Describable = new Circle(2);   // satisfies the interface shape

abstract declares methods the subclass must provide, while the implements-free structural check still accepts Circle as Describable because it has describe().

7.4 Parameter properties and static members

Declares fields directly in constructor parameters and adds class-level statics. Parameter properties, such as a private readonly string in the constructor, collapse the field declaration and assignment into one line. Static members live on the class itself rather than on individual instances.

class User {
    static defaultRole = 'viewer';   // class-level, no instance needed

    constructor(
        public name: string,
        private id: number,
        readonly createdAt: Date = new Date(),
    ) {}                              // all three become fields automatically
}

User.defaultRole;                     // 'viewer' — no new instance
const u = new User('Aria', 7);
u.name;            // public — fine
u.id;              // Error: private
u.createdAt;       // public readonly — fine

Constructor parameters prefixed with a modifier create the field, its type and its visibility in one declaration; static members live on the class itself.

7.5 Decorators overview

Surveys decorators for classes, methods, accessors, and parameters. Decorators are functions that wrap or modify behaviour at definition time, before any instance exists. Classic targets are logging, dependency registration, and validation, and the feature requires enabling the experimental decorators compiler option.

// tsconfig.json: { "experimentalDecorators": true }
function logCall(target: any, key: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    descriptor.value = function (...args: any[]) {
        console.log(`calling ${key} with`, args);
        return original.apply(this, args);
    };
}

class Service {
    @logCall
    run(input: string): string { return `ran ${input}`; }
}
new Service().run('job');   // logs: calling run with ["job"]

The decorator wraps the method’s descriptor, adding logging without touching the method body — the pattern behind routing, dependency injection and validation libraries.

8 · Modules, Declaration Files & @types

8.1 ES module syntax8.2 Type-only imports and exports8.3 Declaration files and DefinitelyTyped8.4 Ambient declarations and augmentation

Organises code into modules and explains how TypeScript finds types for libraries. Declaration files with a .d.ts extension describe the shapes of JavaScript code. They are the bridge that lets a plain JavaScript package provide types, either hand-written or supplied by DefinitelyTyped, to a typed codebase.

A real project lives across dozens of files, and TypeScript needs to know how they connect. Modules are the same ES import/export syntax you already use — TypeScript only adds type-aware variants and the machinery that types untyped libraries.

8.1 ES module syntax

Imports and exports values across files with ES module syntax. Every file with an import or export is a module, not a script, so its top-level declarations stay scoped to that file. Named and default exports give you precise control over what consumers can obtain.

// math.ts
export const PI = 3.14159;
export function circleArea(r: number): number { return PI * r * r; }
export default function hello(msg: string): string { return `hello ${msg}`; }

// app.ts
import hello, { PI, circleArea } from './math';
console.log(circleArea(2));   // imports the named and the default together

// re-export to build a clean public surface
export * from './math';
export { User } from './user';

Named exports, one default export and re-exports compose modules; import picks them up with matching syntax, and the whole module graph is type-aware.

8.2 Type-only imports and exports

Separates types from values with import type and export type statements. Marking an import as type-only lets compilers and bundlers erase it completely, so no runtime dependency is created. Use the same marker on re-exports to keep the type intent explicit.

// types.ts
export interface User { id: number; name: string }
export const seed: User = { id: 1, name: 'Aria' };

// service.ts
import type { User } from './types';   // type-only — fully erased at build time
import { seed } from './types';        // value import — stays in the output

const other: User = seed;

import type erases the import entirely from the emitted JavaScript, while the plain import keeps seed because it is a real runtime value.

8.3 Declaration files and DefinitelyTyped

Explains what .d.ts files are and how to install @types packages for plain JavaScript libraries. When a library ships no types of its own, DefinitelyTyped usually provides community-authored declarations. The compiler and your editor read those files to give you IntelliSense and type checking without loading any runtime code.

npm install lodash
npm install --save-dev @types/lodash   // types live on DefinitelyTyped

// a minimal hand-written declaration file: mylib.d.ts
declare module 'mylib' {
    export function transform(value: string): string;
    export const version: string;
}

@types packages ship hand-written declarations for libraries that do not, and a small declare module block types a private package without touching its source.

8.4 Ambient declarations and augmentation

Declares global shapes and augments existing modules. Ambient declarations describe values that the environment already provides, so the compiler knows they exist without seeing their implementation. Declaration augmentation lets you add members to existing types from the outside.

// globals.d.ts
declare const APP_VERSION: string;       // a global value the bundler injects
interface Window { appName: string }     // merge a field into Window

// augment a library's types from your own code
import 'express';
declare module 'express' {
    interface Request {
        userId?: string;                 // now req.userId exists everywhere
    }
}

Ambient declarations tell TypeScript about values and globals that exist at runtime, and module augmentation adds fields to a library’s types from outside it.

9 · Advanced Types

9.1 Mapped types9.2 Conditional types and infer9.3 Template literal types and key remapping9.4 The built-in utility types9.5 Readonly arrays and tuples

Builds new types from old ones with mapped, conditional, and template literal types. These operate on types the way functions operate on values, taking inputs and deriving outputs. They are the power tools behind every framework’s public API, transforming input shapes into strict, derived output types.

Everything so far named a type. Advanced types compute a type from another type: iterate its keys, test its structure, or build strings from it. These are the tools that frameworks use to give you magically precise IntelliSense.

9.1 Mapped types

Walks a union of keys and produces a new object type property by property. A mapped type iterates over keys, optionally transforming each with modifiers such as readonly or optional. This transforms shapes in bulk instead of writing each property out by hand.

type Flags<T> = { [K in keyof T]: boolean };
type Draft<T> = { [K in keyof T]?: T[K] };   // every field becomes optional

interface User { id: number; name: string }
type UserFlags = Flags<User>;     // { id: boolean; name: boolean }
type DraftUser = Draft<User>;     // { id?: number; name?: string }

function startDraft(d: DraftUser): void {}
startDraft({});                    // no fields needed — all optional

The mapped type iterates keyof T and, for each key, decides the value type — here every field becomes boolean or optional — producing a whole new shape.

9.2 Conditional types and infer

Chooses between two types with a ternary-style expression and extracts inner types with the infer keyword. Conditional types read like type-level functions, taking inputs and producing a result. Infer lets you pull a type out of a larger structure, such as the return type of a function.

type IsArray<T> = T extends unknown[] ? true : false;
type A = IsArray<string[]>;   // true
type B = IsArray<number>;     // false

type ElementOf<T> = T extends (infer E)[] ? E : never;   // pull out the element
type C = ElementOf<(string | number)[]>;   // string | number
type D = ReturnType<typeof fetch>;   // built-in conditional + infer on a function

A conditional type tests a relationship and picks one arm, and infer declares a type variable to capture — here the element type of an array.

9.3 Template literal types and key remapping

Builds string unions from patterns and renames keys while mapping. Template literal types interpolate other types into strings so you can express exact string contracts. Key remapping with as inside a mapped type lets you transform each key as you build the new shape.

type EventName = `on${Capitalize<'click' | 'hover'>}`;   // 'onClick' | 'onHover'
type Size = 'small' | 'large';
type Label = `${Size}-label`;                            // 'small-label' | 'large-label'

// key remapping: transform the keys while you map
type Getters<T> = {
    [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};
type G = Getters<{ name: string }>;   // { getName: () => string }

Template literal types build every matching string union, and remapped keys with Capitalize rewrite the keys themselves while producing value types from the originals.

9.4 The built-in utility types

Lists the utility types you will use daily, including Partial, Required, Pick, Omit, Record, and Extract. Most are exactly the mapped and conditional types you just wrote, shipped built in. Use them to transform existing shapes quickly instead of writing the transformation yourself.

interface Todo { title: string; done: boolean; due?: Date }

type P      = Partial<Todo>;      // every field optional
type R      = Required<Todo>;     // every field mandatory
type PickT  = Pick<Todo, 'title' | 'done'>;   // keep only these keys
type OmitT  = Omit<Todo, 'due'>; // drop these keys
type Exc    = Exclude<'a' | 'b' | 'c', 'a'>;  // remove one union member
type Ext    = Extract<'a' | 'b', 'a' | 'd'>;  // keep the overlap
type Rec    = Record<'left' | 'right', number>;   // map keys to a value type
type Ret    = ReturnType<() => string>;      // string — the return type
type Params = Parameters<(a: number, b: string) => void>;  // [number, string]

Each utility type is a small transform over a shape or union — Partial makes everything optional, Omit drops keys, and ReturnType and Parameters read a function signature.

9.5 Readonly arrays and tuples

Frees arrays from mutation with as const and the ReadonlyArray type. as const narrows a literal to readonly types, producing exact readonly tuples that preserve literal values. Frozen data is safer to share across code and gives you immutability that the compiler enforces.

const roles = ['admin', 'editor'] as const;    // readonly tuple of literals
type Roles = typeof roles[number];             // 'admin' | 'editor'

const points: readonly number[] = [1, 2, 3];
points.push(4);   // Error: property 'push' does not exist on readonly array

function sumAll(values: readonly number[]): number {
    return values.reduce((a, b) => a + b, 0);
}

as const pins values into literal tuples and typeof roles[number] lifts that into a union, while readonly arrays reject mutating calls at compile time.

Write the transform as a question first — "make everything optional", "get the element out" — then reach for the mapped or conditional type that answers it.

10 · TypeScript with Frameworks

10.1 Typing React props and hooks10.2 Typing Vue props and emits10.3 Typing Node and Express handlers10.4 Runtime validation with Zod

Applies the type system to real frameworks: React, Vue, Node, and Zod. Framework types are mostly the patterns from previous chapters wearing different names, with props as interfaces, events as unions, and schemas doubling as types. The same skills transfer directly to any typed framework.

Framework APIs live or die on their types. React’s props, Vue’s emits, and Express handlers are all just interfaces, unions and generics once you know how to look at them — and a runtime validator like Zod plugs the one gap TypeScript cannot close.

10.1 Typing React props and hooks

Types a React component’s props and a couple of standard hooks. Component props are defined as an interface or type alias, and events use the built-in synthetic event types. Hooks like useState infer their state type from the initial value or accept an explicit type argument.

type ButtonProps = {
    label: string;
    onClick: (event: React.MouseEvent) => void;   // callback function type
    variant?: 'primary' | 'ghost';               // restricted union
};

function Button({ label, onClick, variant = 'primary' }: ButtonProps) {
    return <button className={variant} onClick={onClick}>{label}</button>;
}

// hooks take generic parameters
const [count, setCount] = useState<number>(0);
const ref = useRef<HTMLInputElement>(null);

Props become an interface or type checked at every call site, events use the precise React.MouseEvent type, and hooks infer state types from their generics.

10.2 Typing Vue props and emits

Types Vue components with defineProps and defineEmits inside script setup blocks. These compiler macros infer types from the arguments you pass or from TypeScript interfaces. The compiler then checks every prop and emit against both the template and the parent component.

<script setup lang="ts">
type Props = {
    title: string;
    level?: 1 | 2 | 3;                // a restricted heading level
};
const props = defineProps<Props>();   // props is now the typed object

const emit = defineEmits<{
    (e: 'update', id: number): void;  // event signature like a callable type
}>();
emit('update', 42);
</script>

defineProps and defineEmits take generics from your own types, so templates and parent components get full checking on the data flowing in and out.

10.3 Typing Node and Express handlers

Types request handlers, route parameters, and request bodies in Node and Express. Handler parameters carry the full HTTP signature, so request and response objects arrive pre-typed. Validation libraries narrow the body type so what you typed matches what actually arrived over the wire.

import express, { Request, Response } from 'express';
const app = express();
app.use(express.json());

type CreateTodoBody = { title: string };

app.post('/todos', (req: Request, res: Response) => {
    const body: CreateTodoBody = req.body;     // assert the shape at the boundary
    if (typeof body.title !== 'string') {
        res.status(400).json({ error: 'title required' });
        return;
    }
    res.status(201).json({ created: body.title });
});

The handler types its Request and Response, and a runtime check at the boundary narrows the untyped req.body into the shape the rest of the code trusts.

10.4 Runtime validation with Zod

Introduces Zod schemas as runtime parsers that also produce types. Because TypeScript types are erased at runtime, Zod keeps the contract alive after compilation. Parse untrusted input once at the boundary and the parsed value carries the exact type the schema describes.

npm install zod

import { z } from 'zod';

const UserSchema = z.object({
    id: z.number(),
    email: z.string().email(),
    role: z.enum(['admin', 'user']),
});
type User = z.infer<typeof UserSchema>;   // the schema's derived type

const parsed = UserSchema.parse(rawApiData);   // throws if the shape is wrong
parsed.email.toUpperCase();                    // data AND type both guaranteed

zod defines one schema that both validates untrusted input at runtime and, via z.infer, yields the matching TypeScript type — a single source of truth.

TypeScript types do not exist at runtime. Any value that crossed a network or a form boundary must be validated again in code — schemas like zod make that pleasant.

11 · Tooling & Migration

11.1 The tsconfig options that matter11.2 Building: tsc, esbuild and swc11.3 ESLint and Prettier11.4 Migrating JavaScript incrementally11.5 Emitting declarations for libraries

Configures the compiler for strictness and speed, wires linting and formatting, and moves a JavaScript codebase over without a big-bang rewrite. You learn which tsconfig options matter, how tsc compares with esbuild and swc, and how to migrate file by file. The result is a codebase checked and formatted automatically.

The compiler is just the start. Strictness flags, fast transpilers, lint rules and a staged migration plan are what make TypeScript pleasant on a real team — and they all flow from the tsconfig.json you will now understand.

11.1 The tsconfig options that matter

Shows the handful of tsconfig.json settings that define strictness and module output, including target, module, strict, and noEmit. Turning on strict enables the full family of null and implicit checking flags at once. Most other options are fine on their defaults, so you tune only a few.

{
    "compilerOptions": {
        "target": "es2022",              // JS language level in the output
        "module": "esnext",              // module system in the emitted code
        "moduleResolution": "bundler",   // how import paths resolve
        "strict": true,                  // master switch for all strict flags
        "strictNullChecks": true,        // null and undefined are real values
        "outDir": "dist",                // where compiled JS goes
        "rootDir": "src",
        "types": ["node"],               // which @types load globally
        "paths": { "@/*": ["./src/*"] }  // import alias for clean paths
    },
    "include": ["src"]
}

target and module control emit, strict turns on the whole safety family, and paths gives tidy import aliases — most projects run fine on these alone.

11.2 Building: tsc, esbuild and swc

Compares tsc with the faster transpilers esbuild and swc. tsc both checks types and emits JavaScript, while esbuild and swc only transpile and skip type errors. The common setup checks types with tsc and emits with a bundler, giving you fast incremental builds.

npx tsc --noEmit           # type-check only, fast feedback
npx tsc -p .               # check and emit to dist

# esbuild: transpile only, very fast, reports no type errors
npm install -D esbuild
npx esbuild src/main.ts --bundle --outfile=dist/main.js

# swc: a drop-in Rust-based transpiler
npx swc src -d dist

Use tsc --noEmit as the type gate and a fast transpiler like esbuild or swc for emit; that split gives you correctness plus speed.

11.3 ESLint and Prettier

Wires ESLint for rules and Prettier for formatting. tsc checks types, while ESLint enforces style and suspicious patterns and Prettier handles consistent formatting. Together they run in editors and in CI, so problems surface before code ships.

npm install -D eslint typescript-eslint prettier

// eslint.config.js
import tseslint from 'typescript-eslint';
export default tseslint.config(
    tseslint.configs.recommended,
    { ignores: ['dist'] },
);

npx eslint src              # run lint
npx prettier --write .      # format everything

typescript-eslint adds type-aware lint rules on top of tsc, and Prettier handles formatting so reviewers argue about logic, never whitespace.

11.4 Migrating JavaScript incrementally

Moves a JavaScript codebase to TypeScript file by file using allowJs, checkJs, and gradual strictness ramps. Start with the most valuable files and raise strictness as you convert. Migration is a journey, not a rewrite weekend, and each converted file pays off immediately.

npm install -D typescript
npx tsc --init
# tsconfig tweaks for a staged migration
#   "allowJs": true      — keep existing .js files compiling
#   "checkJs": false     — do not type-check them yet
#   "strict": false      — relax first, then tighten module by module

# move files one at a time: copy.js -> migrate.ts
# the big three errors to fix first (in order):
#   1. implicit any on parameters
#   2. possibly-undefined access after narrowing
#   3. non-existent properties on your own objects

allowJs lets new .ts files import old .js files, so you migrate one file at a time and ratchet strictness up as the any pile shrinks.

11.5 Emitting declarations for libraries

Publishes .d.ts declaration files alongside JavaScript so consumers get types. The declaration and declarationDir compiler options make tsc emit them automatically during the build. Declaration emit is how libraries ship their API contract while still running as plain JavaScript.

// tsconfig build profile for a library
{
    "compilerOptions": {
        "declaration": true,        // emit .d.ts files
        "declarationMap": true,     // go-to-definition maps for consumers
        "outDir": "dist",
        "rootDir": "src"
    }
}
npm publish   // dist now contains index.js AND index.d.ts
// package.json: "types": "dist/index.d.ts"

declaration: true emits a .d.ts file per source file, so consumers get IntelliSense and type checking from your library without ever seeing its source.

For a brand-new project, turn strict on from day one. Fixing strict errors on a clean build is cheap; retrofitting them onto a large codebase is a project in itself.

A.5 Glossary

Defines the terms used across the guide in one place, from primitives and generics to declaration files and utility types. Look here when a word repeats but its meaning blurs. Every entry is short, plain, and points to where the guide first explains it.

  • Type annotation — the explicit : Type on a variable or parameter.
  • Type inference — the compiler working a type out from the value.
  • Narrowing — shrinking a union to fewer possibilities inside a branch.
  • Type guard — a predicate function that teaches the compiler to narrow.
  • Assertion function — throws unless a claim holds, then narrows permanently.
  • Discriminated union — a union separated by one literal tag field.
  • Generic — a type parameter that keeps relationships between types.
  • Mapped type — a new object shape built key by key from another.
  • Conditional type — a type-level if/else, often with infer.
  • Declaration file — a .d.ts describing the types of plain JS.
  • Module augmentation — adding types to an existing module from outside.
  • Excess property check — rejecting unknown keys on fresh literals.
