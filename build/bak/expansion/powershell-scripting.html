0.1 What PowerShell is, and when to reach for it

PowerShell is a command-line shell and scripting language built on .NET. Its single design decision — that a command's output is typed objects rather than formatted text — is what separates it from cmd.exe and from every POSIX shell, and almost every practical difference follows from that one choice.

Why objects, and what that buys you

Get-Process emits System.Diagnostics.Process instances carrying Id, CPU, WorkingSet64 and StartTime as real typed properties. Where-Object tests $_.CPU -gt 100 as a number rather than as a column of text it must first parse, so no script has to know which column is which. A property that is a DateTime can be compared with -gt against a date, and a property that is a byte array can be measured with .Length, in either case without the author knowing the underlying type. This is why a PowerShell script that filters on a property does not break when the device manager changes its output formatting, which is the single most common cause of breakage in a script written against a text pipeline.

# The same question, two shells.
# PowerShell: property access, typed comparison, no parsing
Get-Process | Where-Object { $_.CPU -gt 100 } |
    Select-Object ProcessName, Id, @{N='RAM_MB';E={[math]::Round($_.WorkingSet64/1MB,1)}}

# bash: you must know which column is CPU, and that changes
ps aux | awk '$3 &gt; 100 { printf "%-20s %s
", $11, $2 }'
# ...and the equivalent batch is worse still, because there is no
# way to parse a formatted table at all.

Inspecting an object before you use it

The first move when a command returns something unexpected is Get-Member, which prints the type and every property and method it carries. It substitutes for a documentation lookup and it is faster, because the answer is authoritative for the version installed rather than for the version documented. Two companions are worth knowing: Format-List * shows every property with its value, and Format-Table with an explicit property list controls the default view so you get the columns you want rather than the five the cmdlet's author chose.

Get-Process -Name notepad | Get-Member
# TypeName: System.Diagnostics.Process
# Name       MemberType Definition
# CPU        Property  double CPU
# Id         Property  int32 Id
# Path       Property  string Path
# Kill()     Method    void Kill()

# a custom view, so the default output is the one you actually read
Get-Process |
    Format-Table ProcessName, Id,
        @{N='RAM_MB'; E={[math]::Round($_.WorkingSet64/1MB,1)}},
        @{N='CPU_s';  E={[math]::Round($_.CPU,1)}} -AutoSize

Every store is a drive, and the cmdlets never change

PowerShell drives the filesystem, the registry, the certificate store, Active Directory and dozens of other stores through one abstraction called a provider, and a drive prefix selects which one. Get-ChildItem C:Windows lists files; Get-ChildItem HKLM:SOFTWARE lists registry keys; Get-ChildItem Cert:CurrentUserMy lists certificates. The cmdlet is identical in all three cases, which is why a script that manipulates the registry and a script that manipulates files share the same code shape. The four prefixes you will actually meet are the filesystem, HKLM: and HKCU: for the registry, Cert: for certificates, and Env: for environment variables.

Get-ChildItem C:Windows            | Select-Object -First 5 Name
Get-ChildItem HKLM:SOFTWAREMicrosoft | Select-Object -First 5 PSChildName
Get-ChildItem Env: | Where-Object { $_.Name -match 'PATH|USER' }
Get-ChildItem Cert:CurrentUserMy  | Format-Table Subject, NotAfter

# ...and the same operations, on any provider
Get-Content HKLM:SOFTWAREContosoSettings
Set-Content HKCU:Environment -Value 'x=1'
New-Item HKCU:SoftwareContoso -Force

The verbs, and why Get-ChildItem is not Get-Directory

Every cmdlet is Verb-Noun, drawn from a fixed approved list that Get-Verb prints. The verbs worth knowing cold are Get, Set, New, Remove, Test, Start, Stop, Invoke, Convert, Export, Import, Format and Select. The naming is not decorative: a script that invents its own verb names cannot be discovered by tab completion, cannot be mocked in a test, and reads to the next person as an amateur. It also explains the noun choices — Test-Path is a boolean test rather than a getter, Get-Content is a getter whose noun happens to be "Content" rather than "File", and Get-Item and Get-FileHash are both getters distinguished by what they return.

Get-Verb | Select-Object -ExpandProperty Verb
# Add Clear Close Copy Enter Exit Expand Export Find Format Get
# Group Hide Import Insert Join Lock Merge Mount Move New Open
# Optimize Pop Push Redo Remove Rename Reset Resize Search Select
# Set Show Skip Split Step Switch Trace Undo Uninstall Unlock Watch

Test-Path C:WindowsSystem32
otepad.exe   # True / False - a TEST
Get-Item C:Windows
otepad.exe            # metadata, no content read
Get-Content C:Windows
otepad.exe -TotalCount 1   # one line of content

A minimal script, and what each line is doing

param() declares the script's arguments with types and defaults, which is what makes the script callable with -Name value rather than by position alone. Write-Host writes to the console and is the correct choice for anything meant for a person. The backtick at the end of a line continues it, and it is the one piece of PowerShell syntax with no real equivalent elsewhere — most other constructs in the language do not need it.

# hello.ps1
param(
    [Parameter(Mandatory = $true)]
    [ValidateNotNullOrEmpty()]
    [string]$Name,

    [int]$Times = 1,

    [switch]$Loud
)
for ($i = 0; $i -lt $Times; $i++) {
    $msg = "Hello, $Name (iteration $($i + 1))"
    if ($Loud) { Write-Host $msg -ForegroundColor Green }
    else       { Write-Host $msg }
}
# .hello.ps1 -Name World -Times 2 -Loud

Execution policy, and what it actually restricts

The execution policy is not a security boundary and Microsoft has said so; it is a guard against accidental execution. Restricted, the default, runs nothing from a file. RemoteSigned allows local scripts and requires a signature only on downloaded ones, which is the right setting for a developer machine. AllSigned requires a code-signing certificate and is what an enterprise deployment should use. Bypass blocks nothing and is useful for a one-off call without changing machine state.

# the right setting for a developer machine, once
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
Get-ExecutionPolicy -List      # shows all five scopes and which applies

# a one-off run without touching machine state
powershell -ExecutionPolicy Bypass -File .hello.ps1 -Name World

# and the modern cross-platform host, which ignores most of this
pwsh -File ./hello.ps1
# ...PowerShell 7 (pwsh) is available on Linux and macOS too, and
# where you deploy on either, use pwsh rather than powershell.exe

Three disciplines: run Get-Member before using a property you have not used before, because property names are not guessable and the cmdlet is authoritative for the version installed; use providers rather than raw paths, so Get-Content Cert:... and Get-Item HKLM:... carry the same interface as the filesystem; and set RemoteSigned -Scope CurrentUser rather than machine-wide, because a per-user scope needs no administrative rights and does not change the policy for anyone else on the machine.
