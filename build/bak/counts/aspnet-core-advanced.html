1.3 Framework, runtime and package layers

Which assemblies are in-box, which arrive as NuGet packages, and why that distinction drives dependency decisions.

ASP.NET Core ships as a shared framework referenced through the Microsoft.AspNetCore.App framework reference. Anything in that set — Kestrel, the routing system, the DI container, options, logging, configuration, System.Text.Json, System.Threading.Channels — is not versioned by the project and must not be added as a PackageReference. The same applies to Microsoft.NETCore.App and, since .NET 5, to EF Core for the relational providers only if you add them explicitly.

Everything outside the shared framework is an explicit, independently versioned dependency. Treat that boundary as a rule: a package that does not ship in-box is a package you must security-patch on its own cadence.

Framework, runtime and package layers

A hosted application has three layers: the hosting runtime, the service container and the middleware pipeline. The host manages lifetime (start, stop, graceful shutdown). The container wires dependencies and their lifetimes. The pipeline transforms requests and decides the final response. Failures in any layer should produce structured logs and, at the edge, a ProblemDetails response.

Consider cross-cutting concerns: logging, metrics, tracing, health, authentication, authorization and exception handling. Prefer registering them in a composition root (Program or extension methods). Keep third-party adapters behind interfaces owned by the application.

Design for observability from day one: emit structured logs with correlation identifiers, trace spans around key operations and expose health endpoints suitable for orchestrators.

// Directory.Packages.props — central package management (default template)

1.4 What "advanced" means here

The bar this guide holds: trade-offs are named, failure modes are stated, and no pattern is presented without its cost.

Three commitments define the register. First, every pattern is presented with the failure mode it introduces. Second, where a simpler construct is sufficient, the guide says so explicitly and tells you to use it. 1.5 The layer map of a production host

A single reference decomposition showing where each concern lives and which direction dependencies are permitted to point.

The guide uses a four-layer decomposition. Dependencies point inward only: the domain knows nothing, the application knows the domain, the infrastructure knows the application, and the host composes all three. The rule is not stylistic — it is what makes the domain testable without a container and the infrastructure replaceable without touching behaviour.

The layer map of a production host

Map responsibilities to layers: domain (rules), application (use cases, contracts), infrastructure (adapters) and presentation (endpoints). The host composition root wires these. Keep presentation thin: map requests to application handlers, return typed results and translate domain errors to HTTP.

Do not let infrastructure leak into endpoints. Use DI to invert dependencies. For larger apps, organize by feature or by vertical slices to keep cohesion high.

Enforce boundaries with clear contracts and avoid cross-layer shortcuts. Treat the composition root as the only place that knows about concrete implementations and wire adapters behind interfaces owned by the application. Use extension methods per feature to keep wiring discoverable, deterministic and testable in isolation so that architecture decisions remain explicit and enforceable.

Host          Program.cs, DI composition, middleware pipeline, endpoint mapping
   |
Application   Use cases, command/query handlers, ports (interfaces), Result type
   |
Domain        Aggregates, value objects, domain events, invariants
   |

2 · The Request Pipeline

2.1 Registration order is execution order2.2 The terminal case: short-circuiting2.3 Writing conventional middleware2.4 Wrapping the pipeline and failure handling2.5 Grouping and programmatic reordering2.6 Failure modes and their diagnostics

The ASP.NET Core pipeline is an ordered composition of RequestDelegate delegates. This chapter establishes the ordering contract, the three forms of short-circuit, and the practical rules that keep a long pipeline debuggable.

Every request enters a single delegate chain built once at startup. A component receives the next delegate and may invoke it, skip it, or invoke it and post-process the response on the way out. Nearly every confusion about middleware reduces to a misunderstanding of this one contract.

2.1 Registration order is execution order

How the delegate chain is constructed at startup and why the position of a Use call determines its runtime behaviour.

WebApplicationBuilder records each Use call and materialises the chain when the host starts. Component A registered before component B runs before B on the way in, and after B on the way out. The order is fixed at composition time and cannot be altered per request.

Registration order is execution order

Middleware executes in the order registered. Order determines which component sees the request first, whether it can short-circuit and what happens on the way back. Some middleware must run before others (e.g. ExceptionHandler early, HSTS before redirection, CORS before auth endpoints in typical setups). Document order as policy.

Short-circuiting is a valid strategy (e.g. health checks, static files, rate limiting). When you short-circuit, do not call next unless you intend to continue. Also ensure response headers and status codes are set explicitly.

Review order in code reviews and capture rationale in comments when non-obvious.

// Order is load-bearing. Read top to bottom as request-in.
var app = builder.Build();

app.UseExceptionHandler();
app.UseHsts();
app.UseHttpsRedirection();

app.UseRouting();            // precedes UseAuthentication/UseAuthorization
app.UseRateLimiter();
app.UseAuthentication();
app.UseAuthorization();

app.UseOutputCache();
app.MapControllers();
app.MapGet("/health/live", () => Results.Ok());

// LAST. Runs on the way out for every request.
app.Use(async (ctx, next) =>
{
    var sw = System.Diagnostics.Stopwatch.StartNew();
    await next(ctx);
    app.Logger.LogInformation("{Path} -> {Status} in {Elapsed}ms",
        ctx.Request.Path, ctx.Response.StatusCode, sw.ElapsedMilliseconds);
});

The framework validates the common pairings at startup and throws if UseAuthorization appears without UseRouting, or if UseAuthentication is placed after UseAuthorization. Failing at boot is a feature: a mis-ordered pipeline should never reach production.

Routing is implicit in minimal hosting. When endpoint metadata is used, the framework inserts routing and endpoint-execution middleware if you have not placed it yourself. Placing UseRouting explicitly remains correct whenever ordering relative to another component matters, because implicit insertion always goes to a fixed position.

2.2 The terminal case: short-circuiting

The three legitimate ways a component stops the chain, and what each implies for components placed after it.

A component short-circuits by completing its work without calling next. There are three distinct forms, and the distinction determines what a later component sees.

FormExampleComponents after it
Response writtenUseStaticFiles on a hitNever run: no auth, no logging, no cache headers
RejectionUseAuthorization failing a policyEndpoint never executes; 401 or 403 returned
Endpoint matchRouting resolves an endpointEndpoint middleware invokes the handler only

Any component that must observe or mutate every request — request logging, correlation, distributed tracing, rate limiting — has to sit before the first component that can short-circuit. Placing output caching after UseStaticFiles means static files are never cached. Placing it after UseAuthorization is safe only if the policy also varies the cache key.

Distinguish 401 from 403. UseAuthentication does not reject. It populates HttpContext.User; the reject step is UseAuthorization when a policy is unmet. Middleware between the two sees an authenticated but unauthorized principal, which is usually what an audit component needs.

The terminal case: short-circuiting

Keep middleware small and composable. Each component should have one reason to change. Prefer extension methods (UseX) to expose policy. Avoid putting branching logic that depends on many unrelated concerns in a single middleware. If branching is needed, use endpoint routing or MapWhen with a clear predicate.

MapWhen creates a separate pipeline branch. The branch runs only if the predicate matches; inside it you may register additional middleware. Be explicit about what runs in the branch and whether to stop there.

Test branch predicates explicitly to avoid accidental overlaps between branches.

2.3 Writing conventional middleware

The idiomatic shape for a component with dependencies, request-in logic and response-out logic.

Use the factory-delegate registration of UseMiddleware, or implement IMiddleware and resolve it per request. The factory form is explicit about lifetime and avoids the reflection-based activation path.

Writing conventional middleware

Write conventional middleware as either inline delegates or classes that take RequestDelegate in the constructor. Prefer classes when the middleware has state/config or multiple methods. Keep the Invoke/InvokeAsync signature correct and respect cancellation tokens when making async calls.

Do not capture large scopes unnecessarily. Avoid reading the entire body unless required; stream when possible. On exceptions, let the central handler translate to ProblemDetails rather than writing custom error bodies in every middleware.

Log with structured data and include correlation identifiers for traceability across services. Prefer streaming over buffering request and response bodies, validate inputs early and ensure CancellationToken from HttpContext.RequestAborted flows to downstream async calls so shutdown and client disconnects are handled correctly.

public sealed class RequestIdMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestIdMiddleware> _log;

    public RequestIdMiddleware(RequestDelegate next, ILogger<RequestIdMiddleware> log)
    {
        _next = next; _log = log;
    }

    public async Task InvokeAsync(HttpContext ctx)
    {
        var id = ctx.Request.Headers["X-Request-Id"].FirstOrDefault()
                    ?? Activity.Current?.TraceId.ToString()
                    ?? Guid.NewGuid().ToString("n");

        ctx.TraceIdentifier = id;
        ctx.Response.Headers["X-Request-Id"] = id;
        using (_log.BeginScope(new Dictionary<string, object>
        {
            ["RequestId"] = id,
            ["Path"] = ctx.Request.Path.Value
        }))
        {
            await _next(ctx);
        }
    }
}

// Resolved once from the request scope, reused for the process lifetime.
app.UseMiddleware<RequestIdMiddleware>(sp => sp.GetRequiredService<RequestIdMiddleware>());

Activating the middleware class happens once; InvokeAsync runs per request. If you need scoped dependencies, resolve them from HttpContext.RequestServices inside InvokeAsync and never capture them in fields — a field is a process-wide view of a scoped service.

When to use IMiddleware instead. An IMiddleware instance is resolved from the request scope on every request, which is correct but not free. For a component with no scoped dependencies, the factory form is cheaper. Measure before choosing.

2.4 Wrapping the pipeline and failure handling

What the outermost component must do to observe a failure at all, and how the exception path is re-entered.

Code placed before the exception handler runs on the way in for every request, but its post-next code does not run for a request that threw, because the exception propagates past it. A logging component placed first therefore never logs failures unless it catches them itself.

Wrapping the pipeline and failure handling

Wrapping the pipeline safely means: handle exceptions around next, log context (method, path, status), measure duration and propagate cancellation. Also ensure that when next throws, you do not swallow it. Use ProblemDetails via UseExceptionHandler for unhandled exceptions; use try/finally for telemetry.

Consider that response has started: after WriteAsync, headers/status cannot change in some cases. Check HttpResponse.HasStarted before modifying headers in the outbound path.

Ensure metrics and logs record status codes even on exceptions to maintain accurate observability.

app.UseExceptionHandler();   // outermost: converts exceptions to responses
app.UseStatusCodePages();   // turns bare 404/401 into a body

3.1 The three lifetimes and the scope as a unit of work

The container builds a scope per request and disposes it when the response completes. A scoped DbContext is therefore one context per request, and the SaveChangesAsync that runs inside the request is the transaction. No such guarantee exists for a background service, which has no ambient request scope.

The three lifetimes and the scope as a unit of work

ASP.NET Core DI has three lifetimes: transient (new each time), scoped (per request/scope) and singleton (application lifetime). Choosing the correct lifetime is fundamental to correctness, avoiding leaks and preventing captive dependencies. A scope represents a unit of work, such as an HTTP request or an explicit IServiceScope created for a background job.

Scoped services should not be resolved from singletons. Transient services can depend on scoped or singleton services. Singletons must be thread-safe and stateless or have carefully managed state. Always think in terms of disposal: scoped and transient disposable instances are disposed when the scope ends.

Be explicit about the unit of work. For background processing, create a new scope per work item rather than sharing a request scope. This prevents data leakage and ensures resources are released predictably.

3.2 Captive dependencies and the container smell test

The lifetime inversion that silently promotes a short-lived object to process lifetime, and how to detect it before production.

A captive dependency occurs when a longer-lived service holds a reference to a shorter-lived one. A singleton that takes a scoped DbContext in its constructor makes that context live for the whole process, shared across concurrent requests, with a change tracker and connection pool that grow without bound.

Captive dependencies and the container smell test

A captive dependency occurs when a service with a shorter lifetime (transient/scoped) is captured by a service with a longer lifetime (singleton). This extends the captured instance's lifetime and can cause stale data, thread-safety issues or resource leaks. The container does not always prevent this by default in all scenarios, so design reviews are essential.

The smell test is straightforward: if a singleton depends on anything scoped or transient, reconsider. Options include making the consumer scoped, injecting a factory, using IServiceScopeFactory, or redesigning so the shorter-lived dependency is not held as a field. Prefer factories when the dependency is only needed occasionally.

Avoid storing scoped services in static fields or caches without scope awareness. Detect issues early with integration tests and by validating registrations where feasible.

// Opt in explicitly so the check is not environment-dependent.

    ServiceLifetime.Scoped,
    ServiceLifetime.Scoped,
    ServiceLifetime.Scoped);

The test that catches most inversions is simple: read every constructor and confirm that the lifetime of the service is greater than or equal to the lifetime of every parameter. If not, either the dependency or the lifetime is wrong.

3.3 Scoped services, async flow and disposal

How a scope follows an asynchronous call chain, and why fire-and-forget from a request is the sharpest edge.

Scopes travel on AsyncLocal state associated with the request. A scope survives await, Task.Run and fire-and-forget work started from a request. That survival is exactly what makes fire-and-forget unsafe: the response completes, the scope is disposed, and the orphaned continuation then touches a disposed DbContext.

Scoped services, async flow and disposal

Scoped services are disposed at the end of the scope. With async flows, disposal timing remains the same: at the end of the request or explicit scope. Avoid leaking scoped instances across async boundaries into other scopes. Do not capture IServiceProvider from a disposed scope.

When using DbContext (scoped), one context per unit of work is correct. Avoid long-lived contexts. For parallel operations within the same scope, be careful not to share non-thread-safe services. If parallelism spans units of work, create separate scopes.

Always propagate CancellationToken (HttpContext.RequestAborted) through async calls. This ensures graceful shutdown and client disconnects are respected, preventing wasted work and resource leaks.

// Broken: outlives the request that owns the scope.

// Correct: bounded, cancellable, awaited inside the scope.
await _audit.LogAsync("order.placed", ct);

For work that genuinely outlives the request, copy the required values across the boundary and open a new scope on the far side. The background-work chapter develops this for channels and queues, but the rule is universal: a scope is a lexical region, not a message.

3.4 Keyed services for multi-tenant resolution

The AddKeyed registrations introduced in .NET 8, and where a dictionary of instances is a worse answer.

Before .NET 8, resolving a variant by name meant injecting the interface collection and filtering, or injecting a hand-built dictionary. Both leak the discriminator into every consumer. Keyed services make it part of the registration contract while keeping resolution explicit at the call site.

Keyed services for multi-tenant resolution

Keyed services allow resolving different implementations for the same interface based on a key. This is useful for multi-tenancy, feature flags, environment-specific adapters or strategy selection without creating many factory types. Keys can be strings, enums or other types.

Use [FromKeyedServices] in minimal APIs or constructor injection with keyed registration. Keep keys explicit and documented. Avoid overusing keyed services where a factory or strategy pattern is clearer. Validate keys at registration time where possible to fail fast on misconfiguration.

For multi-tenancy, resolve the tenant key early (from header, claim, path or domain) and use it to retrieve tenant-specific services. Ensure tenant isolation is enforced in data access, not just in service resolution.

// [FromKeyedServices] on minimal API parameters: .NET 8 and later.

{

    public CheckoutService([FromKeyedServices("stripe")] IPaymentGateway g)

3.5 Turning misconfiguration into a boot failure

Why every registration in a production host should be resolved once before the server accepts a connection.

The default container does not build the object graph at startup; it builds each node on first resolve. A missing dependency or a lifetime inversion therefore surfaces on a request, in production, under load. A single eager resolution pass over the graph converts that class of defect into a non-zero exit code before the load balancer sees the instance.

Turning misconfiguration into a boot failure

Misconfiguration discovered at runtime is expensive. Validate options and critical dependencies at startup to fail fast. Use ValidateOnStart<T>(), DataAnnotations validation, or implement IValidateOptions<T> for complex rules. Also validate required services can be constructed when using development-time checks.

Health checks cover runtime readiness but not boot-time contract violations. Prefer startup validation for invariants that must hold before accepting traffic. Return clear error messages to aid diagnosis in CI and deployment pipelines.

Combine with configuration binding validation: bind strongly typed options and enforce ranges, required values and cross-property rules. This prevents partial configuration from reaching production.

4 · The Options Pattern

The options pattern is the only supported way to bring configuration into a service. This chapter distinguishes the three interfaces, establishes the validation contract, and covers the reload semantics that decide whether a setting is read once, per request, or continuously.

Options are immutable snapshots by convention. The framework enforces none of this — it only supplies instances — so the discipline is a design decision you make in the composition root and defend in review.

4.1 IOptions, IOptionsSnapshot and IOptionsMonitor

The three accessors differ only in lifetime and reload behaviour, and choosing wrong produces either stale settings or per-request allocations.

IOptionsSnapshot<T>ScopedPer requestSettings that must be consistent within one request
IOptionsMonitor<T>SingletonOn change, with a callbackHot reload, named lookup, reacting to change

IOptionsSnapshot exists for a specific reason: a scoped service that reads the same option twice during a request should see the same value even if a reload lands mid-request. It is implemented by re-reading configuration on each scope creation and caching for the scope, so it is meaningfully more expensive than IOptions.

Never inject IOptionsSnapshot into a singleton. Scope validation throws at startup in Development; in Production you get a snapshot refreshed per scope and read from a process-wide cache — a race that produces intermittently wrong settings. The same prohibition applies inside a BackgroundService.

Prefer IOptions by default. A singleton taking IOptions<T> is trivially testable: pass Options.Create(config). The cost of IOptionsSnapshot buys a guarantee most services do not need.

IOptionsMonitor<T> is singleton and supports change notifications via OnChange, ideal for long-lived services that need to react to configuration updates.

Choose based on lifetime and mutability: use IOptionsMonitor for background services, IOptionsSnapshot for request-scoped consumers that need consistent values within a request, and IOptions<T> for simple read-only singletons. Never mutate options instances directly; treat them as immutable snapshots.

Be aware of caching semantics: IOptionsMonitor caches the last valid value and raises OnChange when the underlying configuration source changes. Ensure change handlers are thread-safe and cheap. Document which options support reload and enforce immutability to avoid accidental mutation across consumers.

4.5 Reload, OnChange and hot configuration

What actually happens when configuration changes, and which changes a running process can honour safely.

The change token fires when a provider reports new data. IOptionsMonitor caches the current value and invokes callbacks with the new instance; IOptionsSnapshot invalidates its per-scope cache. A database connection string is a poor candidate for hot reload because pools are not rebuilt; a feature flag is a good one.

Reload, OnChange and hot configuration

Configuration sources can be reloaded (e.g. appsettings.json watched in development). IOptionsMonitor<T> raises OnChange when values change. Use this to update singleton state safely without restarting the app. Ensure change handlers are idempotent, thread-safe and avoid doing heavy work synchronously.

Not all configuration changes are safe to apply at runtime (e.g. changing connection strings may require recreating pools). Document which options support hot reload. For critical changes, prefer rolling deployments over runtime mutation.

Debounce rapid changes if needed and log reload events for observability. Consider versioning or checksums to ignore no-op updates. Apply changes atomically to avoid partial updates in concurrent consumers.

5.1 The endpoint shape and parameter binding rules

What the framework infers from a handler signature, and where that inference can surprise you.

Parameters bind by explicit attribute first — [FromRoute], [FromQuery], [FromHeader], [FromBody], [FromForm], [FromServices], [AsParameters] — then by inferred default, and finally anything unrecognised is treated as a body parameter.

The inference is deliberately conservative. A complex type appearing exactly once and not registered as a service is read from the body; a simple type is read from the route or query. Two complex types, or one complex type plus a simple one, produce a startup error rather than a guess.

5.3 Route groups as the composition unit

Grouping is not only a prefix; it is the mechanism for attaching cross-cutting metadata to a set of endpoints.

Avoid scattering prefix logic; centralize it in groups. This improves discoverability and keeps endpoint mappings clean.

5.4 Endpoint filters: ordering and short-circuiting

The middleware-equivalent for a single endpoint, and the two ways a filter can prevent the handler from running.

An IEndpointFilter runs after authorization and model binding, immediately around the handler. It receives an EndpointFilterInvocationContext holding the arguments, which it can read, modify or replace, and it decides whether to proceed.

Endpoint filters: ordering and short-circuiting

Endpoint filters run before and after endpoint execution, allowing cross-cutting logic (validation, logging, rate limiting, authorization checks) without polluting handler code. Filters can short-circuit by returning a result early, preventing the handler from running. Ordering is explicit via .AddEndpointFilter or global registration.

Prefer filters for endpoint-specific concerns and middleware for pipeline-wide concerns. Keep filters small, pure and testable. Avoid shared mutable state in filters unless scoped appropriately.

Document filter order and side effects. Use filters to enforce invariants and translate exceptions to appropriate results. Ensure cancellation tokens are respected and filters do not block unnecessarily.

public sealed class UnitOfWorkFilter>(AppDb db) : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        if (db.ChangeTracker.HasChanges()) await db.SaveChangesAsync();
        return await next(ctx);
    }
}

app.MapPost("/orders", CreateAsync)
    .AddEndpointFilter<UnitOfWorkFilter>();

Filters run in registration order on the way in and reverse order on the way out, exactly like middleware. Returning without calling next short-circuits: that is how you implement a cache lookup, a feature gate that returns 404, or an idempotency check.

Order filters with Order; lower values run first on the way in. This matters for a validation filter and a transaction filter: validation must sit outside the transaction, so a rejected request does not hold a database transaction open while the client decides what to send next.

Filters are endpoint-scoped. An unhandled exception in a filter is caught by the exception-handling middleware, not by the endpoint, because no endpoint filter pipeline owns it. Global concerns belong in middleware or in an IExceptionHandler.

The two endpoint models are not ranked; they answer different requirements. This chapter states the differences that have engineering consequences and gives a decision procedure that does not depend on taste.

Both are first-class in ASP.NET Core 10 and are supported for the lifetime of the framework. The recommendation to prefer minimal APIs for data-returning endpoints is about default cost, not about capability.

6.1 The mechanical differences that actually matter

Minimal APIs and MVC differ mechanically: minimal APIs use delegates with parameter binding and typed results; MVC uses controllers with action methods, filters and model binding. Minimal APIs have less ceremony and are faster in many benchmarks; MVC provides richer extensibility and conventions.

Choose based on team skills, complexity and requirements. For simple CRUD and microservices, minimal APIs are often sufficient. For complex applications with many cross-cutting concerns, MVC may be more productive.

6.6 Migrating incrementally

A safe order of operations for moving existing endpoints without a flag day.

The order matters more than the effort. Each step below is independently deployable and independently reversible.

  1. Introduce the minimal API surface alongside the existing controllers, behind a different path prefix, and compare responses byte for byte against the controller under test.
  2. Align the error contract: both models must emit the same ProblemDetails shape for the same failure. Write a shared test that asserts the shape for one endpoint in each model.
  3. Align the authorization contract: the same policy name on both sides, so a permission change lands in one place.
  4. Move traffic at the routing layer, not in the handler, so a revert is a configuration change rather than a code change.
  5. Delete the controller only after the tests that covered it have been rewritten against the new endpoint — not skipped.

Watch the OpenAPI diff. Publish the generated document from both models before cutting over and compare. Differences in response codes and schema names are the most common client-breaking regression in this migration, and the diff is far cheaper to review than a bug report.

7.1 The change tracker and identity resolution

What the tracker does on every query, and the three ways to stop paying for it.

By default a query materialises entities and registers each instance keyed by primary key. A second query returning the same row returns the same instance. This is identity resolution, and it is what makes a two-query aggregate load safe: one object graph in memory, not two copies.

The change tracker and identity resolution

Entity Framework Core's change tracker monitors entity state (Added, Modified, Deleted, Unchanged) and resolves identity so that multiple references to the same entity are treated as one. Tracking is the default for queries; use AsNoTracking for read-only scenarios to improve performance.

Identity resolution ensures that when the same entity is loaded multiple times, the same instance is returned. This is important for consistency within a unit of work. Be aware of tracking overhead with large object graphs.

Disable tracking for read-only projections. Use tracking when you need to save changes. Consider splitting queries when reads and writes have different requirements.

// 1. No tracking: a fresh instance per row, no identity map.
await db.Orders.AsNoTracking().ToListAsync(ct);

// 2. Identity resolution without change tracking (EF Core 5+).
await db.Orders.AsNoTrackingWithIdentityResolution().ToListAsync(ct);

// 3. Query-only context, no tracking anywhere.
builder.Services.AddDbContext<ReadDb>(o => o.UseNpgsql(cs)
    .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking));

The tracker’s cost is not only memory. DetectChanges runs on every SaveChangesAsync and walks every tracked entity, so a long-lived context that has read a large graph makes every subsequent save progressively slower.

Do not attach read entities to a tracking context. Calling Attach on an entity from an AsNoTracking query makes it tracked with its current values. The next save treats it as unchanged even if the row was modified since the read, producing silent divergence rather than an error.

7.4 Concurrency tokens and optimistic concurrency

Row versions, application-level tokens, and the decision to retry or to fail the request.

Optimistic concurrency is opt-in per property. IsRowVersion maps a database-maintained row version and is the correct default when the database supports one — SQL Server’s rowversion, PostgreSQL’s xmin through a provider-specific mapping.

Concurrency tokens and optimistic concurrency

Optimistic concurrency prevents lost updates by detecting conflicts. A concurrency token (rowversion/timestamp or a property) is checked during SaveChanges. If the token has changed since the entity was loaded, a DbUpdateConcurrencyException is thrown.

Configure concurrency tokens via IsRowVersion() or IsConcurrencyToken(). Handle concurrency exceptions by refreshing the entity and retrying or informing the user.

Use optimistic concurrency for most scenarios. Pessimistic locking is rarely needed in web apps. Document concurrency policies and test conflict resolution.

modelBuilder.Entity<Order>()
    .Property(o => o.Version)
    .IsRowVersion();

// Alternatively: an application-managed token the caller supplies.
modelBuilder.Entity<Order>()
    .Property(o => o.Version)
    .IsConcurrencyToken()
    .ValueGeneratedNever();

When a concurrency conflict occurs, EF Core throws DbUpdateConcurrencyException and the entry is left in the Added, Modified or Deleted state with the original values intact. That is enough to compute a meaningful conflict response, provided the handler does it deliberately.

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException ex)
{
    foreach (var e in ex.Entries)
        e.State = EntityState.Unchanged;
    return Results.Conflict(new ProblemDetails
    {
        Status = StatusCodes.Status409Conflict,
        Title = "The order was modified by another request."
    });
}

Return 409, do not retry blindly. An automatic retry of a business operation is only correct if the operation is idempotent. Retrying a non-idempotent command after a concurrency conflict is how duplicate orders appear. Retry at the transport layer for transport failures; surface the conflict to the caller.

7.5 Interceptors and SaveChanges discipline

The two interception surfaces, and the cross-cutting rules that belong in one rather than in every handler.

SaveChangesInterceptor sees the change set before and after it is written. DbCommandInterceptor sees the individual SQL commands. The first is the right place for auditing, soft deletes and tenant stamping; the second is the right place for command-level timing and diagnostics.

Interceptors and SaveChanges discipline

EF Core interceptors hook into SaveChanges and materialization. Use them for auditing, soft delete, multi-tenant filtering, or enforcing invariants. Interceptors are registered via AddInterceptors or OnConfiguring.

Keep interceptors focused and testable. Avoid business logic in interceptors; use them for cross-cutting concerns. Ensure interceptors are thread-safe and respect cancellation tokens.

Document interceptor behavior and order. Test interceptors in isolation. Avoid interceptors that make SaveChanges unpredictable.

public sealed class AuditInterceptor(TimeProvider clock) : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>>
        SavingChangesAsync(DbContextEventData e, InterceptionResult<int> r,
            CancellationToken ct)
    {
        var now = clock.GetUtcNow().UtcDateTime;
        foreach (var entry in e.Context.ChangeTracker.Entries())
        {
            if (entry.State is EntityState.Added)
                entry.Property("CreatedAt").CurrentValue = now;
            if (entry.State is EntityState.Added or EntityState.Modified)
                entry.Property("UpdatedAt").CurrentValue = now;
        }
        return ValueTask.FromResult(r);
    }
}

Use TimeProvider — in-box since .NET 8 — rather than DateTime.UtcNow in an interceptor, so that tests can control time without a clock abstraction threaded through the call graph.

Save the change set exactly once per request. Multiple SaveChangesAsync calls mean multiple audit entries, multiple domain-event dispatches and a transaction boundary nobody can describe from the code.

Interceptors run on bulk paths too. SaveChangesInterceptor methods do not fire for ExecuteUpdateAsync or ExecuteDeleteAsync. If a soft-delete flag must be applied consistently, either stop using the bulk path for deletes or maintain the flag in the database with a trigger.

Multi-tenant schemas and global filters

Multi-tenancy isolates tenant data. Approaches: shared database with tenant discriminator (global query filters), separate schemas, or separate databases. Global query filters automatically apply tenant predicates to queries.

Configure global filters in OnModelCreating. Resolve the tenant from the current user or context. Ensure filters cannot be bypassed accidentally. Test tenant isolation thoroughly.

8 · EF Core Performance: Compiled Queries and Bulk Work

8.1 Measure before optimising: the command log8.2 Removing tracking from read paths8.3 Compiled queries and compiled models8.4 ExecuteUpdate, ExecuteDelete and bulk insert8.5 Projections that stay in the database8.6 Connection management and pooling

EF Core performance work is almost never about the ORM and almost always about round trips, tracking and result shape. This chapter orders that work by measured impact.

Compiled queries sit third on purpose: they are a real but second-order win, and applying them before removing round trips is wasted effort.

8.1 Measure before optimising: the command log

The instrumentation that reveals round trips, and how to read it in a production-safe way.

Enable the relational command log in development and count commands per request. Anything above one for a single logical operation is a candidate for composition or a bulk operation.

// Development only: logs every command and its duration.
builder.Logging.AddSimpleConsole(o => o.SingleLine = true);

// Interceptor form: makes command count assertable in tests.
public sealed class CommandCounter : DbCommandInterceptor
{
    public int Count;
    public override ValueTask<InterceptionResult<DbDataReader>>
        ReaderExecutingAsync(DbCommand c, CommandEventData e,
            InterceptionResult<DbDataReader> r, CancellationToken ct)
    { Interlocked.Increment(ref Count); return ValueTask.FromResult(r); }
}

In production the equivalent is the OpenTelemetry instrumentation of Chapter 16 plus the provider’s own statistics — pg_stat_statements on PostgreSQL, the Query Store on SQL Server. Neither requires application changes and both survive a redeploy.

Assert command counts in integration tests. Registering an interceptor and asserting that a handler issues exactly one command turns a performance regression into a test failure. It is one of the highest-value tests in a data-heavy codebase and costs about fifteen lines.

8.2 Removing tracking from read paths

The largest single-source improvement available without changing the query, and where it does not apply.

Tracking costs memory proportional to the entities materialised, and DetectChanges on save costs time proportional to everything tracked so far. For a read endpoint returning five hundred rows, both are wasted.

// Default for a read-oriented context.
options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

// Per query, when the context is mixed-purpose.
var orders = await db.Orders
    .AsNoTracking()
    .Include(o => o.Lines)
    .Where(o => o.CustomerId == id)
    .ToListAsync(ct);

Tracking is required when the result will be modified, when related entities are updated in the same unit of work, and when tracking is used to detect in-context conflicts. Outside those cases, no-tracking is correct.

Watch the include-then-project pattern. EF Core optimises some of these and not others, depending on whether the projection is a simple member access. Verify with the command log that the generated SQL selects the expected columns rather than the full graph.

8.3 Compiled queries and compiled models

Two distinct caching mechanisms that are frequently confused, with different preconditions and different benefits.

A compiled query caches the parameterised command and its translation for one specific LINQ expression. A compiled model caches model metadata so it is not rebuilt at startup. They are orthogonal and combine freely.

// Compiled query: define once, reuse many times. EF Core 7 and later.
private static readonly Func<AppDb, Guid, CancellationToken,
    Task<Order?>> s_byId =
    EF.CompileAsyncQuery((AppDb db, Guid id, CancellationToken ct) =>
        db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct));

// Compiled model: no model construction at startup.
options.UseModel(AppDbModel.Instance);

// Produced at build time by: dotnet ef dbcontext optimize
public sealed partial class AppDbModel : CompiledModel { }

Compiled queries help when one hot query runs on many concurrent requests. On a warm JIT the remaining gain is typically single-digit percent. Compiled models improve startup time and steady-state memory, not per-request latency.

Regenerate compiled models on every model change. A stale compiled model fails at first use of the affected entity, not at startup. Wire dotnet ef dbcontext optimize into the build step rather than running it by hand.

8.4 ExecuteUpdate, ExecuteDelete and bulk insert

Server-side set operations that bypass the change tracker, and the bulk-insert path when row count is the problem.

ExecuteUpdateAsync and ExecuteDeleteAsync, added in EF Core 7, issue a single statement with a WHERE clause. Nothing is materialised and nothing is tracked. They are the correct tool for bulk state transitions such as expiring sessions or flagging stale records.

var n = await db.Sessions
    .Where(s => s.ExpiresAt < now)
    .ExecuteDeleteAsync(ct);

await db.Orders
    .Where(o => o.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);

Neither raises change-tracker events, so an already-tracked entity with the same key keeps its stale values. Call ChangeTracker.Clear() if the same context will read those rows again.

For inserts, EF Core has no built-in bulk path. Three options exist: the provider’s own API — SqlBulkCopy or Binary COPY through a staging table; bounded batching with SaveChangesAsync; and a stored procedure for very large volumes.

Bulk paths bypass your invariants. SqlBulkCopy and Binary COPY do not raise SaveChanges interceptors, do not populate generated identifiers, and do not honour ValueGeneratedOnAdd. If the model depends on a database-generated GUID or a row version, the bulk path must set them explicitly.

8.5 Projections that stay in the database

Translating a projection into SQL rather than materialising entities and projecting in memory.

Because Select is part of the expression tree, the projection is translated. A projection to a record type with a constructor is translated to a column list plus a constructor call, provided every member is a simple member access or a supported function.

var page = await db.Orders
    .AsNoTracking()
    .Where(o => o.Status == OrderStatus.Placed)
    .OrderByDescending(o => o.PlacedAt)
    .Select(o => new OrderRow(o.Id, o.Total, o.Lines.Count, o.PlacedAt))
    .Skip(skip).Take(size)
    .ToListAsync(ct);

Two things break translation: navigation property access inside a client-side method, and calls to methods the provider does not know. A Select containing a C# method call on an entity instance is evaluated in memory after materialising the entity, which silently reintroduces the cost you were removing. Split the query so the SQL-safe part projects to a DTO and the rest is applied afterwards.

Paging needs a deterministic order. Skip/Take without a total OrderBy produces a result that is correct on average and wrong under concurrency, because the database may return rows in a different order. Always order by a unique tiebreaker such as the primary key.

8.6 Connection management and pooling

Where the connection actually comes from, and the three settings that determine whether the pool is a bottleneck.

Connections are pooled by the provider, not by EF Core. Pool size is bounded by Max Pool Size on the connection string; waiting requests queue and then time out, which presents as a latency spike followed by a timeout wall rather than as a connection error.

The three settings that matter are maximum pool size, connection timeout, and command timeout. Command timeout is the one most often left at the 30-second default, which means a slow query holds a connection for thirty seconds and reduces effective throughput far below the pool size suggests.

// PostgreSQL: 100 connections per instance is a common ceiling.
const string cs =
    "Host=db;Database=app;Username=app;Password=..." +
    ";Maximum Pool Size=100;Timeout=5;Command Timeout=15";

// SQL Server: pool size is bounded by Max Pool Size, not by
// the server's 32767 worker thread limit.

Size the pool from the database’s connection limit divided by the number of instances, with headroom for administrative and migration connections. Add retry-on-failure only if the provider supports it and only for transient errors; a blanket retry on a constraint violation multiplies write load without a chance of success.

9 · Domain Modelling: Aggregates, Values and Events

9.1 The aggregate as a consistency boundary9.2 Value objects and structural equality9.3 Domain events and when they fire9.4 Dispatching events without a framework9.5 Mapping the model: owned types and conversions9.6 The anemic model and where behaviour belongs

Domain modelling pays for itself only when the model encodes rules the database cannot. This chapter defines the boundary, the value semantics and the event mechanism, and states plainly when a simpler model is the right one.

None of this requires an ORM-independent domain. It requires a place where invariants live and a persistence mapping that does not leak through it.

9.1 The aggregate as a consistency boundary

What an aggregate is for, and how to choose a boundary the database can actually enforce.

An aggregate is a cluster of objects treated as one unit of consistency. The boundary answers exactly one question: which changes must succeed or fail together in a single transaction? Everything inside is modified through the root; everything outside is referenced by identifier only.

public sealed class Order : AggregateRoot
{
    private readonly List<OrderLine> _lines = [];

    public Guid Id { get; }
    public Guid CustomerId { get; }
    public OrderStatus Status { get; private set; }
    public decimal Total { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;

    public void AddLine(Sku sku, int qty, UnitPrice price)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Lines may only be added to a draft order.");
        if (qty <= 0)
            throw new DomainException("Quantity must be positive.");
        if (_lines.Any(l => l.Sku == sku))
            throw new DomainException("Duplicate SKU in order.");

        _lines.Add(new OrderLine(sku, qty, price));
        Recalculate();
    }
}

Set the boundary so a single SaveChangesAsync covers it. An aggregate spanning several transactions has no consistency guarantee, and pretending otherwise is worse than a smaller aggregate. When a rule genuinely spans two aggregates, the answer is a domain event plus a process manager, not a wider aggregate.

Large aggregates are a scaling defect. Loading two hundred children to add one line costs two hundred rows and a change-tracker pass. If the collection is unbounded, it is almost certainly a separate aggregate with its own consistency rule.

9.2 Value objects and structural equality

What distinguishes a value from an entity, and the C# features that express the difference directly.

A value object has no identity: two instances with equal components are interchangeable. It compares by value, is immutable, and validates itself at construction so an invalid instance cannot exist.

public readonly record struct UnitPrice
{
    public decimal Amount { get; }
    public string Currency { get; }

    public UnitPrice(decimal amount, string currency)
    {
        if (amount < 0m)
            throw new DomainException("Price cannot be negative.");
        if (currency is null || currency.Length != 3)
            throw new DomainException("ISO 4217 code required.");
        Amount = amount; Currency = currency.ToUpperInvariant();
    }

    public static UnitPrice Zero(string c) => new(0m, c);
}

public sealed record Address(string Line1, string City,
    string CountryCode, string PostCode);

The persistence rule that follows: a value object is an owned type, a complex type, or a primitive collection. It never has its own table with an identity column, and it is never loaded or tracked independently.

Complex types arrived in EF Core 8. OwnsOne with no key and no explicit navigation creates a complex type stored in a single column, which is the shape of most value objects. Prefer it to a value converter when the value has more than one component.

9.3 Domain events and when they fire

The distinction between a domain event and a message, and the constraints that make domain events safe.

A domain event is an immutable fact about something that already happened inside the aggregate. It is not a command, not a message to another service, and not durable. Three constraints keep it honest: raise it from inside the aggregate, carry values rather than entity references, and dispatch only after the transaction commits.

public abstract record DomainEvent(DateTimeOffset OccurredAt)
{
    public sealed record OrderPlaced(
        Guid OrderId, Guid CustomerId, decimal Total,
        string Currency, DateTimeOffset OccurredAt) : DomainEvent(OccurredAt);
}

public abstract class AggregateRoot
{
    private readonly List<DomainEvent> _events = [];
    public IReadOnlyList<DomainEvent> Events => _events;

    protected void Raise(DomainEvent e) => _events.Add(e);
    public void ClearEvents() => _events.Clear();
}

The value-object form — identifiers and primitives, never an entity reference — is not stylistic. A reference keeps the entire aggregate reachable, and therefore tracked, for as long as the event is held in a queue.

Dispatch after commit, not during save. A handler that calls an external service must not run inside the transaction. If the handler succeeds and the transaction then rolls back, the side effect is uncompensated. Raise the events, save, then dispatch.

9.4 Dispatching events without a framework

A dispatcher small enough to read in one screen, and the reason to prefer it over a reflection-based one.

The in-process dispatcher needs three things: a way to enumerate the handlers of a request type from the container, ordering, and a place to invoke them. Writing it explicitly costs about forty lines and removes a reflection dependency from the hot path.

public interface IDomainEventHandler<in TEvent>
{
    Task HandleAsync(TEvent e, CancellationToken ct);
}

public static class Dispatcher
{
    public static async Task DispatchAsync<TEvent>(
        this IServiceProvider sp, TEvent e, CancellationToken ct)
        where TEvent : DomainEvent
    {
        foreach (var h in sp.GetServices<IDomainEventHandler<TEvent>>())
            await h.HandleAsync(e, ct);
    }
}

// Application service: save, then dispatch from the same scope.
order.Place(now);
db.Orders.Add(order);
await db.SaveChangesAsync(ct);

foreach (var e in order.Events)
    await provider.DispatchAsync(e, ct);

Make the dispatch decision explicit per handler: some are required for correctness and should be inside the transaction as a same-context write, others are best-effort and belong in an outbox. Blurring the two produces handlers whose failure semantics nobody can state.

9.5 Mapping the model: owned types and conversions

The three mapping constructs a rich domain needs, and the access-modifier constraints that apply to each.

EF Core cannot map a private setter without a backing field, and it cannot map an immutable collection property without configuration. These are the three cases that account for nearly all rich-model mapping friction.

modelBuilder.Entity<Order>(b =>
{
    b.OwnsOne(o => o.ShippingAddress,
        nav => nav.Property(a => a.Line1).HasMaxLength(200));
    b.OwnsMany(o => o.Lines, lines =>
        lines.ToTable("order_lines", t => t.HasKey(x => x.Id)));
    b.Navigation(o => o.Lines).UsePropertyAccessMode(
        PropertyAccessMode.Field);
    b.Property(o => o.Status).HasConversion<string>().HasMaxLength(24);
    b.Ignore(o => o.Events);
});

OwnsOne without an explicit identity maps a complex type; with a key it maps to a shared primary key, which is the pattern for a one-to-zero-or-one child. OwnsMany maps a child collection in the same table or a related one. UsePropertyAccessMode tells EF Core to read and write the backing field rather than the property, which is required when the property is read-only in practice.

Ignore the event list. The events collection is not part of the aggregate’s persisted state. Without Ignore, EF Core attempts to map it, and the resulting error appears at model validation during startup with a message that does not name the property.

9.6 The anemic model and where behaviour belongs

When a rich domain is the wrong investment, and the specific signals that indicate it.

A rich domain model is not free. It costs a mapping layer, indirection at the call site, and a learning curve for a team that has only ever written services. It is worth that cost when the rules are numerous, non-obvious and change independently of the storage.

SignalVerdict
Rules are two or three simple validationsAnemic is sufficient
Rules change weekly, independently of the schemaRich model
The same rule applies to three entity typesDomain service or policy, not base class
The ORM mapping is fighting private settersAccept it, or reconsider the boundary
Team is small and shipping a single verticalApplication services, anemic domain

The most common serious mistake is not an anemic model but a BaseEntity carrying every behaviour of every subclass. That creates a dependency from every aggregate to every other aggregate’s rules, which is the coupling the aggregate boundary exists to prevent.

Whatever the model, keep invariants out of the controller. A rule enforced in a controller, a filter and a service is three rules that will drift. Exactly one place should be able to fail the request, and it should be reachable from a unit test that constructs no HTTP context.

10 · CQRS Without Ceremony

10.1 What CQRS claims, and what it does not10.2 The seam: two interfaces over one database10.3 Read paths: projections, Dapper and raw SQL10.4 Write paths and the cost of the split10.5 Denormalised read models and refresh strategy10.6 When CQRS is the wrong answer

Command Query Responsibility Segregation is frequently adopted as a naming convention and abandoned when the ceremony exceeds the benefit. This chapter presents the smallest form that is still CQRS and states the costs honestly.

Two definitions must be kept apart: architectural CQRS separates the write model from one or more read models, and library CQRS uses a mediator to dispatch named request objects. The first is a data design decision. The second is an indirection, and Chapter 11 addresses it separately.

10.1 What CQRS claims, and what it does not

The genuine benefit, the false promise, and the measurable test for whether a split has paid for itself.

The genuine benefit is that reads and writes stop competing to serve the same shape. A write model is normalised around invariants; a read model is denormalised around a screen. Optimising either one usually degrades the other, and CQRS is the acknowledgement that one schema cannot serve both well.

The false promise is that CQRS enables event sourcing. It does not. A command handler can write to a single transactional table and remain perfectly valid CQRS. Conversely, event sourcing does not require CQRS, though it usually encourages it.

SymptomDiagnosis
Read queries are slow because of joins and indexes added for writesReal CQRS candidate
The write model is a thin wrapper over a table with no invariantsSplit adds cost, no benefit
One screen needs data from six aggregatesRead model candidate, keep writes shared
Two people edit the same row and need merge semanticsCollaboration, not CQRS — consider CRDTs

The cheapest useful form. Keep one database and one schema. Introduce a read interface returning DTOs, a write interface enforcing invariants, and separate query implementations that bypass the change tracker. That is CQRS in the sense that matters, and it is reversible.

10.2 The seam: two interfaces over one database

The two interfaces that define the split, and how they are registered so neither leaks into the other.

The write side returns aggregates. The read side returns DTOs and accepts query objects, never identifiers plus a list of sort fields. Keeping the signatures different in kind — not merely in name — is what prevents a read model from being mutated by accident.

public interface IOrderCommands
{
    Task<OrderId> PlaceAsync(PlaceOrderCommand cmd, CancellationToken ct);
    Task CancelAsync(Guid orderId, string reason, CancellationToken ct);
}

public interface IOrderQueries
{
    Task<OrderDto?> GetAsync(Guid id, CancellationToken ct);
    Task<Page<OrderRow>> SearchAsync(OrderSearch q, CancellationToken ct);
}

Register both as scoped. The write implementation takes a tracking DbContext; the read implementation takes a factory that produces a no-tracking context, so a query can never accidentally participate in a unit of work.

builder.Services.AddScoped<AppDb>();
builder.Services.AddScoped<IOrderCommands, OrderCommands>();
builder.Services.AddScoped<IOrderQueries, OrderQueries>();

Keep the endpoints honest. An endpoint should depend on exactly one of the two interfaces. An endpoint that takes both and calls a query after a command has loaded an aggregate is using a split that exists only in the type system.

10.3 Read paths: projections, Dapper and raw SQL

Three levels of read sophistication, and the point at which leaving EF Core is the correct decision.

Level one is an EF Core projection to a record type, translated to SQL. Level two is a hand-written SQL query through FromSqlRaw or Database.SqlQuery, mapped to a DTO. Level three is a micro-ORM such as Dapper, for queries where generating efficient SQL through an abstraction is more work than writing it.

// Level one: translated projection.
var rows = await _db.Orders.AsNoTracking()
    .Where(o => o.CustomerId == q.CustomerId)
    .OrderByDescending(o => o.PlacedAt).ThenBy(o => o.Id)
    .Select(o => new OrderRow(o.Id, o.Total, o.Currency, o.Status, o.PlacedAt))
    .Skip(q.Skip).Take(q.Size)
    .ToListAsync(ct);

// Level two: hand-written SQL, still EF Core mapping (EF Core 7+).
var agg = await _db.Set<RevenueByMonth>()
    .FromSqlRaw("""
        SELECT date_trunc('month', placed_at) AS Month,
               sum(total) AS Revenue, count(*) AS Orders
        FROM orders WHERE customer_id = {0}
        GROUP BY 1 ORDER BY 1
        """, q.CustomerId)
    .ToListAsync(ct);

Level two is where most reporting queries belong. The projection at level one is right when the shape matches the entity graph; once the query needs a window function, a lateral join or a provider-specific construct, writing the SQL is clearer and faster to review.

Raw string interpolation is not injection. In the snippet above the parameter is passed through the FromSqlRaw overload, which parameterises it. Constructing SQL by concatenating a variable is not, and static analysis will not always catch it because the value is often a validated filter.

10.4 Write paths and the cost of the split

What the write side gains, and the three costs that appear the moment a read model is added.

The write side gains protection from read-shaped pressure. If a screen wants a denormalised field, the temptation is to add it to the entity; with a separate read model, that temptation has nowhere to land.

Three costs appear. First, a duplicate fact: the same total exists in the write model and in the read model, and something must keep them consistent. Second, latency: a read model populated synchronously after a write makes the caller wait for two operations. Third, a second thing to deploy, monitor and migrate.

public sealed class OrderCommands(AppDb db, IOutbox outbox,
    TimeProvider clock) : IOrderCommands
{
    public async Task<OrderId> PlaceAsync(
        PlaceOrderCommand cmd, CancellationToken ct)
    {
        var order = Order.Place(cmd, clock.GetUtcNow());
        db.Orders.Add(order);
        outbox.Enqueue(new OrderPlaced(order.Id, order.CustomerId,
            order.Total, order.Currency, clock.GetUtcNow()));
        await db.SaveChangesAsync(ct);
        return order.Id;
    }
}

The outbox is what makes a read model consistent without a distributed transaction: the event and the state change commit together, and a separate process projects the event into the read model. The read is then only eventually consistent, and the API contract must say so.

Stating consistency in the contract. If the read model lags by up to a second, the OpenAPI description and the client documentation should say so. A read-after-write guarantee that is not documented is a defect waiting to be reported as one.

10.5 Denormalised read models and refresh strategy

The four refresh strategies, and the operational cost each one introduces.

StrategyLatencyComplexityUse when
Projection at query timeNoneVery lowDefault; the first thing to try
Materialised viewRefresh intervalLowExpensive aggregates over stable data
Outbox projectionSub-secondMediumRead-after-write matters to a specific flow
Change data captureSub-secondHighMany consumers, or cross-service read models

Start at the top of the table and move down only when a measured requirement forces the move. Each step adds an operational surface — a refresh job, an outbox table, a CDC pipeline — and each of those can lag, stall or fail silently.

Whatever the strategy, the projection must be idempotent. Outbox delivery is at-least-once in every practical implementation, so the projector will receive the same event twice after any restart, and the read model must converge rather than double-count.

10.6 When CQRS is the wrong answer

The four conditions under which the split costs more than it returns, stated so they can be checked rather than argued.

  1. The domain has few rules. A CRUD application with validation attributes gains nothing; the interfaces and DTOs double the surface without changing what the database can do.
  2. The team is small and the surface is narrow. Two interfaces plus an outbox plus a projector is four things to understand before the first feature ships.
  3. Strict read-after-write is required everywhere. Eventually consistent reads then need compensating UI, refetching or a wait, and the compensation costs more than the query did.
  4. Operational maturity is low. A projector that can stall without anyone noticing is worse than a slow query that a human notices.

There is a partial version that is almost always correct: keep one schema and one context, but expose reads as DTO-returning query methods and writes as aggregate-returning command methods. That boundary costs almost nothing, prevents the entity graph from leaking into the HTTP contract, and leaves the door open to a real split later without having pre-built the difficult parts.

11 · In-Process Dispatch, MediatR and When to Skip It

11.1 The licensing change that alters the calculation11.2 What the mediator actually provides11.3 Pipeline behaviours: logging, validation, transactions11.4 A hand-rolled dispatcher and what it costs11.5 The five standard objections, answered11.6 A decision rule

The mediator is the most widely adopted and most widely disputed component in the .NET application layer. This chapter states its real function, presents the implementation-free alternative, and gives a decision rule that does not reduce to taste.

The version situation changed materially, so it is stated first.

11.1 The licensing change that alters the calculation

The commercial licensing of MediatR from version 13, and what the 12.x line means for an existing dependency.

MediatR was MIT-licensed through the 12.x line. From version 13 the project moved to a commercial licence under LuckyPennySoftware, with a free tier available under defined conditions. Any architecture that adopted the library assuming a permissive licence now carries a line item that did not exist when the decision was made.

LineLicencePractical position
12.4.x / 12.5.xMITFree, no vendor dependency, no support commitment

This does not make 12.x a bad choice. It is a maintained, MIT-licensed library with a large installed base. It does mean the decision is no longer purely technical, and any new adoption should be justified on that basis explicitly rather than inherited from an article written in 2019.

Pinning a version is a commitment. If the application is licence-sensitive, pin to the 12.x line deliberately, record the decision, and re-evaluate when the library reaches end of support. A floating version reference converts a licensing decision into a silent cost.

11.2 What the mediator actually provides

Four capabilities, stated precisely, so that each can be evaluated independently.

  1. Decoupling of caller from handler. Real when handlers live in a different assembly; cosmetic when they are in the same file.
  2. Pipeline behaviours. Cross-cutting steps wrap dispatch: logging, validation, transaction scope, metrics. This is the strongest reason to use a mediator rather than direct calls.
  3. A uniform unit of work. Dispatch is a natural place to open a transaction and to observe the change tracker once.
  4. Test-time substitution. The weakest reason, and usually unnecessary: a mock mediator replaces handlers that were doing nothing worth mocking.
public sealed record PlaceOrder(Guid CustomerId, string Currency) : IRequest<OrderId>;

public sealed class PlaceOrderHandler(AppDb db) : IRequestHandler<PlaceOrder, OrderId>
{
    public async Task<OrderId> Handle(PlaceOrder r, CancellationToken ct)
    {
        var order = new Order(r.CustomerId, r.Currency);
        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);
        return order.Id;
    }
}

Capabilities one to three are worth having. Capability four is frequently cited and rarely load-bearing, because a handler that only moves data from one call to another does not merit a test double.

11.3 Pipeline behaviours: logging, validation, transactions

The three behaviours that justify the indirection, and the ordering rule that makes them correct.

A pipeline behaviour wraps dispatch with RequestHandlerDelegate in the middle, so it runs on the way in and on the way out. That is the correct shape for request logging with duration and outcome, for a transaction opened around the handler, and for metrics.

public sealed class TransactionBehaviour<in TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull, new()
{
    private readonly AppDb _db;
    public TransactionBehaviour(AppDb db) => _db = db;

    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next,
        CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);
        var response = await next();
        await tx.CommitAsync(ct);
        return response;
    }
}

Behaviours registered before the transaction behaviour run outermost, so a validation behaviour placed first rejects the request before any transaction is opened. Getting this order wrong is the most common pipeline bug, and it stays invisible until a rejected request holds a database transaction for the duration of the client’s think-time.

Behaviour discovery is convention-based. Handlers and behaviours are found by scanning registered assemblies at startup. A behaviour in a project the application does not reference is silently not applied — a failure with no error message at all.

11.4 A hand-rolled dispatcher and what it costs

The interfaces that make the capabilities possible without a library, and the honest cost of owning them.

public interface IRequestHandler<in TRequest, TResponse>
    where in TRequest : notnull
{
    Task<TResponse> HandleAsync(TRequest request, CancellationToken ct);
}

public interface IRequestDispatcher
{
    Task<TResponse> DispatchAsync<TRequest, TResponse>(
        TRequest request, CancellationToken ct);
}

The implementation either reflects over a closed generic — which is what MediatR does, and the reason it exists — or requires a small amount of source-generated registration. The fully explicit alternative is a generic method on the application service, which costs nothing but abandons caller-to-handler decoupling.

Honest summary: a hand-rolled dispatcher is a smaller dependency and a larger maintenance surface. It wins when the team wants full control and can own the code, including its trimming behaviour under Native AOT. It loses when the team wants the library’s ecosystem and its stream-marshalling support.

The property that matters. Whatever dispatches, the handler must be a real class whose dependencies come from the request scope. If the mediator ends up invoking a delegate from a dictionary, the testability argument has already been lost and only the indirection remains.

11.5 The five standard objections, answered

The arguments against the mediator, each stated at its strongest and answered on the merits.

ObjectionAssessment
"It is indirection for its own sake."True when handlers are in the same file. False when a behaviour wraps dispatch.
"It hides the dependency graph."True in IDEs without support; the container still validates it at startup.
"It allocates per request."True of any scoped resolution; the cost is small and measurable, not prohibitive.
"Tests mock the mediator and test nothing."The strongest objection. Answer by testing handlers directly, not through the mediator.
"The reflection breaks trimming."Accurate for Native AOT; use source generation or a different dispatch model.

The fourth row is the one that decides most cases. A test suite where every handler is invoked through a mocked mediator has no coverage of the behaviour that matters, and the indirection has produced a false signal of test coverage rather than real coverage.

The fifth row is decisive for a specific architecture. If the publish target is trimmed or Native AOT, a reflection-based dispatcher is not merely slow — it is a correctness problem under the trimming of unused members.

11.6 A decision rule

A rule that resolves the question with the inputs available, and the migration cost of reversing it later.

Adopt a mediator when at least two of the following hold: there is a cross-cutting behaviour that must wrap dispatch; handlers genuinely live in a separate assembly from their callers; the application is being published trimmed or with Native AOT and a source-generated dispatcher is available; or the team has more than three services that must implement the same behaviours consistently.

Skip it when none of them hold, which for a single service with a small surface is the common case. In that case, an explicit interface per use case — IPlaceOrder implemented by PlaceOrderService — provides the same decoupling with no reflection and nothing to license.

public interface IPlaceOrder
{
    Task<OrderId> ExecuteAsync(PlaceOrderCommand cmd, CancellationToken ct);
}

The migration cost is low in both directions and that is the most important practical point. A mediator over one-request-per-handler is a mechanical change in both directions, so the decision can be deferred until a real requirement arrives. Choose the one with the lower current cost, and record which requirement would change it.

12 · Result Types and Non-Exceptional Error Handling

12.1 Classifying failure: expected, transient, exceptional12.2 The Result type and its invariants12.3 Error codes versus exception types12.4 Mapping Results to ProblemDetails at the edge12.5 IExceptionHandler for the truly exceptional12.6 What the Result pattern does not solve

Exceptions are the right tool for the exceptional and the wrong tool for a foreseeable business rejection. This chapter defines the boundary, presents a Result type with real invariants, and covers the single translation point from internal failure to HTTP response.

12.1 Classifying failure: expected, transient, exceptional

The three-way classification that determines whether a failure is returned, retried or thrown.

ClassExampleMechanismCaller action
ExpectedInsufficient stock, unknown customerReturned as a ResultShow the message, correct the input
TransientTimeout, deadlock, connection resetThrown, caught by resilience pipelineRetry with backoff
ExceptionalNull reference, failed assertionThrown to the global handlerReport; do not retry blindly

The most common defect is treating the first class as the third: a controller catches a domain exception and returns 400. That works, and it puts a type-matching responsibility in every handler. Returning the failure as a value puts it in the type signature, where the compiler can see it.

Validation is not the same as failure. A malformed request is rejected by the framework before the handler runs, as a 400. A well-formed request that violates a business rule fails inside the handler and returns a Result. The two produce the same status code from very different places, and the distinction matters when reading a log.

12.2 The Result type and its invariants

A minimal, allocation-conscious Result type and the three invariants it must enforce.

A result type is a discriminated union of success and failure. The invariants are: it is never both, it is never neither, the failure value is present exactly when the result failed, and a successful result cannot expose the failure. A readonly record struct with a nullable error gives strong guarantees at no allocation cost for the failure-free path.

public enum ErrorKind { None, NotFound, Conflict, Validation, Forbidden, Unavailable }

public readonly record struct Error(ErrorKind Kind, string Code, string Message)
{
    public static readonly Error None = new(ErrorKind.None, "", "");
    public static Error NotFound(string what) =>
        new(ErrorKind.NotFound, "not_found", $"{what} was not found.");
}

public readonly struct Result
{
    private readonly object? _value;
    private readonly Error _error;

    private Result(object? value, Error error)
    { _value = value; _error = error; }

    public bool IsSuccess => _error.Kind == ErrorKind.None;
    public bool IsFailure => !IsSuccess;
    public Error Error => _error;

The continuation-style API — Map, Bind, Tap — is worth having when composition is common, because it prevents the deeply nested if that a Result-returning API otherwise produces after three or four calls. It is not worth having if every call site handles the result immediately.

Do not return Result from a method that cannot fail. Once a signature carries a Result, every caller must handle it, including the ones that know the operation is infallible in their context. Reserve it for the operations where failure is genuinely possible.

12.3 Error codes versus exception types

Using a stable string code for clients and a typed kind for the transport, and never letting a message cross the boundary.

Two audiences need different representations. A client needs a stable, machine-readable code it can branch on. A log needs detail. A user needs a sentence. Keeping one string for all three produces an API that is either unusable by machines or useless to operators.

public static class Errors
{
    public static Error InsufficientStock(Sku sku, int available) =>
        new(ErrorKind.Validation, "order.insufficient_stock",
            $"Only {available} units of {sku.Value} are available.");

    public static Error DuplicateOrder(string reference) =>
        new(ErrorKind.Conflict, "order.duplicate_reference",
            $"Reference {reference} has already been used.");
}

Centralising error construction in a static class makes the code set enumerable. From that set you can generate the documentation, assert that no code is duplicated, and — if a client needs a closed enum — generate a TypeScript or Java client type from the same source.

Never expose an exception message to a client. Messages routinely contain type names, connection strings and file paths. Map to a safe message at the edge, and put the full detail in a correlated log entry with the same code.

12.4 Mapping Results to ProblemDetails at the edge

A single extension method that converts every result to the correct status code and problem document.

Translation belongs in exactly one place. Doing it per endpoint produces inconsistent status codes for the same error kind, which is the kind of defect a client team files repeatedly and nobody can reproduce locally.

public static IResult ToProblem(this Error e)
{
    var status = e.Kind switch
    {
        ErrorKind.NotFound => StatusCodes.Status404NotFound,
        ErrorKind.Conflict => StatusCodes.Status409Conflict,
        ErrorKind.Validation => StatusCodes.Status400BadRequest,
        ErrorKind.Forbidden => StatusCodes.Status403Forbidden,
        ErrorKind.Unavailable => StatusCodes.Status503ServiceUnavailable,
        _ => StatusCodes.Status500InternalServerError
    };

    return Results.Problem(new ProblemDetails
    {
        Status = status, Title = e.Code, Detail = e.Message,
        Extensions = { ["code"] = e.Code }
    });
}

Using the code as the title and as a machine-readable extension gives clients a stable field to branch on while keeping the document RFC 9457 conformant. Register AddProblemDetails so that the framework supplies the trace identifier extension on every response, including those produced by the exception handler.

Assert the mapping in a test. A theory that feeds every ErrorKind through ToProblem and asserts the status code is a five-line test that prevents an entire class of client-visible regression.

12.5 IExceptionHandler for the truly exceptional

The global exception path introduced in .NET 8, and how it differs from a try/catch in the pipeline.

IExceptionHandler implementations are consulted in registration order by the exception-handling middleware; the first that returns a handled result wins. Register them with AddExceptionHandler<T> and activate with AddProblemDetails plus UseExceptionHandler.

public sealed class GlobalExceptionHandler(
    IProblemDetailsService problem, ILogger<GlobalExceptionHandler> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var status = ex switch
        {
            KeyNotFoundException => StatusCodes.Status404NotFound,
            UnauthorizedAccessException => StatusCodes.Status403Forbidden,
            TimeoutException => StatusCodes.Status504GatewayTimeout,
            _ => StatusCodes.Status500InternalServerError
        };

        if (status >= 500) log.LogError(ex, "Unhandled: {TraceId}", ctx.TraceIdentifier);

        ctx.Response.StatusCode = status;
        return await problem.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = ctx,
            ProblemDetails = { Status = status, Title = "Unexpected error" }
        });
    }
}

Log at error level for 5xx and at information or below for 4xx. A handler that logs every exception at error level will page someone for a client sending a bad identifier, and after a week the alert will be ignored.

The handler runs after the response may have started. Once bytes are on the wire, the status code cannot be changed. Throw before writing anything, or the client receives a 200 with a truncated body and no problem document.

12.6 What the Result pattern does not solve

Three problems that the Result pattern is frequently credited with solving, and which it does not.

It does not make failures impossible. A handler can still throw, and a repository that returns a Result can still leak a DbUpdateException. The type improves the signature; it does not enforce the contract at runtime.

It does not reduce the number of failure paths. A Result with a success value and an error value has more states than a plain return, and every additional failure kind is another branch the caller must reason about. The benefit is that the states are visible, not that there are fewer of them.

It does not help with cancellation or process death. A cancelled operation, a killed process and an out-of-memory condition all bypass the Result entirely. The infrastructure that must handle those is the resilience and deployment work of Chapters 15 and 18, and no return type substitutes for it.

A pragmatic middle position. Use Result across the application layer, where business rules live and callers benefit from seeing the failure. Let infrastructure throw, catch at the service boundary, and translate. This keeps the domain expressive without asking a repository to model a connection timeout as a business error.

13 · Authentication and Authorization

13.1 OpenID Connect as the baseline13.2 Validating JWTs correctly13.3 Claims shape and claim mapping13.4 Policy-based authorization13.5 Resource ownership and per-entity checks13.6 The failures that recur

Authentication establishes who is calling; authorization decides what they may do. This chapter covers the OpenID Connect baseline, the claim-mapping decision that silently breaks authorization, and the resource-level checks that policy alone cannot express.

Everything in this chapter assumes tokens are issued by an external identity provider. If the system issues its own tokens, the security burden is substantially higher and the sections on key management apply with full force.

13.1 OpenID Connect as the baseline

Why the API should validate tokens rather than broker them, and where a login UI does belong.

An API validates. It does not redirect to a login page, does not hold a session cookie, and does not run a user-facing sign-in flow. Those belong to a browser application or an identity provider. The consequence is that every request to a protected API carries a bearer token, and the API’s only job is to validate it and derive a principal.

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = builder.Configuration["Auth:Authority"];
        o.Audience = builder.Configuration["Auth:Audience"];
        o.RequireHttpsMetadata = true;
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ClockSkew = TimeSpan.FromSeconds(30),
            NameClaimType = "sub"
        };
    });

Setting Authority causes the handler to fetch OpenID configuration and the signing keys, and to refresh them on the provider’s schedule. That is almost always the right answer. Hard-coding a signing key URL or a symmetric secret is acceptable only where the identity provider cannot publish discovery metadata, and it transfers key rotation from the provider to you.

Discovery is cached, not fetched per request. The first validation triggers the fetch; subsequent validations use the cached metadata until the provider signals a change. In a scaled deployment, each instance fetches once at startup, which is why the first few requests after a cold start can be measurably slower.

13.2 Validating JWTs correctly

The five validation parameters, the two that are commonly wrong, and the header and algorithm checks that must be explicit.

Validation is the security boundary. The parameters that must be enabled are issuer, audience, lifetime, signature and the signing key. The two most commonly misconfigured are audience — often omitted because a development token "already worked" — and the accepted algorithms.

o.TokenValidationParameters = new TokenValidationParameters
{
    ValidIssuer = "https://login.example.com",
    ValidAudience = "orders-api",
    ValidAlgorithms = ["RS256"],
    ValidateAudience = true,
    ClockSkew = TimeSpan.FromSeconds(30)
};

// Enforce a maximum token age independently of the provider.
o.Events = new JwtBearerEvents
{
    OnTokenValidated = ctx =>
    {
        if (ctx.Principal?.FindFirst("scope") is null)
            ctx.Fail("Missing scope claim.");
        return Task.CompletedTask;
    }
};

ClockSkew defaults to five minutes, which means a revoked or expired token is accepted for up to five minutes after its stated expiry. Reducing it trades clock-drift tolerance for revocation latency; thirty seconds is a reasonable default for an internal API.

Never accept alg: none or an unexpected algorithm. Pin ValidAlgorithms explicitly. Also require HTTPS metadata in every environment except local development — the discovery document is fetched over the network, and an unvalidated fetch is a man-in-the-middle waiting to hand you an attacker’s signing key.

13.3 Claims shape and claim mapping

The claim-mapping transform that changes every claim type name, and the class of authorization bugs it produces.

By default the JWT bearer handler maps inbound claims to the long URI claim types used by the older ASP.NET Core identity model. This means sub becomes a claim of type http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier. Code written against the raw names then silently matches nothing.

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.MapInboundClaims = false;   // use short, standard claim names
        o.TokenValidationParameters = new TokenValidationParameters
        {
            NameClaimType = "name",
            RoleClaimType = "role"
        };
    });

Set MapInboundClaims to false and use the standard short names throughout. The failure mode when this is left at its default is severe and quiet: a policy written as RequireClaim("sub", id) never matches, every user is anonymous, and the response is a 401 that looks like a signing problem.

Scope and role claims need explicit handling. A token carrying "scope": "orders.read orders.write" as a single space-delimited value is not matched by RequireClaim("scope", "orders.read") unless a transform splits it, and the correct handling differs between providers.

Write a claim-shape test. A unit test that constructs a token with known claims, validates it through the real handler, and asserts the resulting ClaimsPrincipal is the cheapest defence against a claim-mapping regression. It fails the build rather than the production tenant.

13.4 Policy-based authorization

Building requirements and handlers, and configuring a fallback so a forgotten attribute denies rather than allows.

Policy-based authorization is the model to adopt. Roles alone cannot express "this user may edit orders belonging to their own region"; permissions derived from a role can. The requirement is a marker with data, and the handler is a class that inspects the principal against that data.

public sealed record ScopeRequirement(string Scope) : IAuthorizationRequirement;

public sealed class ScopeHandler : AuthorizationHandler<ScopeRequirement>
{
    protected override void Handle(AuthorizationHandlerContext ctx, ScopeRequirement req)
    {
        var scopes = ctx.User.FindAll("scope").SelectMany(c => c.Value.Split(' '));
        if (scopes.Contains(req.Scope, StringComparer.Ordinal))
            ctx.Succeed(req);
    }
}

builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser().Build())
    .AddPolicy("orders:write", p => p
        .RequireAuthenticatedUser()
        .AddRequirements(new ScopeRequirement("orders.write")))
    .AddPolicy("orders:admin", p => p
        .RequireRole("orders-admin"));

AddAuthorizationBuilder arrived in .NET 8 and is the fluent replacement for chaining AddPolicy calls. Setting a fallback policy is the single highest-value line in the list: without it, an endpoint with no [Authorize] attribute is anonymous, and adding a new endpoint silently creates a public one.

Authorization is additive across metadata. Group-level and endpoint-level requirements combine, and every applicable requirement must succeed. Removing an attribute from an endpoint never relaxes the group policy beneath it, which is what makes group-level defaults safe.

13.5 Resource ownership and per-entity checks

The checks a policy cannot express, and the two shapes — handler and filter — that can.

Ownership is not knowable from the token: the token says who the caller is, not what they may touch. The decision requires a data lookup, so it belongs either in an IAuthorizationHandler or in an endpoint filter that loads the resource first.

public sealed record OrderOwnerRequirement(Guid OrderId) : IAuthorizationRequirement;

public sealed class OrderOwnerHandler(IOrderOwnershipProbe probe)
    : AuthorizationHandler<OrderOwnerRequirement>
{
    protected override async ValueTask HandleAsync(
        AuthorizationHandlerContext ctx, OrderOwnerRequirement req)
    {
        var sub = ctx.User.FindFirst("sub")?.Value;
        if (sub is null) return;
        if (await probe.IsOwnedAsync(Guid.Parse(sub), req.OrderId))
            ctx.Succeed(req);
    }
}

// Resource-aware MVC: the handler is given the action arguments.
app.MapGet("/orders/{id:guid}", GetAsync).RequireAuthorization(async ctx =>
{
    await ctx.SucceedAsync(new OrderOwnerRequirement(ctx.HttpContext.RouteValues.Id));
});

Return 404 rather than 403 when the caller must not know whether the resource exists. A 403 confirms that the identifier is real, which is an enumeration oracle for any identifier the attacker can generate or guess.

Cache the ownership answer, carefully. The probe is a database read on every request. A short-lived cache keyed by subject and resource id is appropriate, but the cache must be invalidated when ownership changes — which for most domains is never, and for some is a support operation.

13.6 The failures that recur

A checklist of the defects that appear in review after the first incident, ordered by consequence.

  1. No fallback policy. A new endpoint without [Authorize] is public. Fix with SetFallbackPolicy and a test that enumerates the endpoint data source and asserts no endpoint is anonymous without an explicit marker.
  2. Audience not validated. A token minted for a different API is accepted. Fix with ValidateAudience and a test that presents a wrong-audience token.
  3. Claim mapping left at default. Short claim names never match. Fix with MapInboundClaims = false and the claim-shape test described in 13.3.
  4. 403 used where 404 is correct. Enumeration is possible. Fix by returning 404 in the ownership handler.
  5. Token in a query string. Query strings appear in access logs, browser history and referrer headers. Fix by requiring the Authorization header and rejecting a query-string token.
  6. Long-lived tokens without revocation. Fix with short access-token lifetimes, refresh tokens held by the client, and a documented revocation procedure.

Enumerate endpoints in a test. 14 · Caching: In-Process, Distributed and Output

14.1 IMemoryCache and its one hard limitation14.2 IDistributedCache and serialisation cost14.3 Hybrid cache in .NET 1014.4 Output caching and Vary correctness14.5 Invalidation: the part that is always hard14.6 A caching policy that survives review

Caching is the technique most often applied before it is justified and invalidated least often. This chapter distinguishes the four caching layers shipped with .NET, and states the invalidation problem for each honestly.

Every layer here is a correctness trade. The question is never whether caching is fast, but what the system is allowed to serve while stale.

14.1 IMemoryCache and its one hard limitation

The fastest option available, and the fact that makes it unusable in a scaled deployment.

IMemoryCache stores objects in the process, with no serialisation and no network hop. It is the right choice for reference data that changes rarely and for a single-instance deployment. Its limitation is structural: each instance holds its own copy, so a value cached on instance A is not visible to instance B until its entry expires.

builder.Services.AddMemoryCache(o => o.SizeLimit = 64 * 1024);

public sealed class RateCardCache(IMemoryCache cache,
    TimeProvider clock, ILogger<RateCardCache> log)
{
    private const string Key = "ratecard:v3";

    public async Task<RateCard> GetAsync(CancellationToken ct)
    {
        if (cache.TryGetValue(RateCard is { } hit, out hit)) return hit;
        await using var scope = _scopeFactory.CreateAsyncScope();
        var card = await scope.ServiceProvider.GetRequiredService<IRateCardSource>()
            .LoadAsync(ct);
        cache.Set(Key, card, new MemoryCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(15),
            Size = 1
        });
        return card;
    }
}

Setting a SizeLimit is not optional in production. Without it the cache grows until the process is killed, and the failure appears as an out-of-memory exception on the busiest instance rather than as a controlled eviction. With a limit, eviction is LRU and predictable.

Cache stampede. When an entry expires under load, every concurrent request misses and issues the same expensive call. For a database query that can be a hundred simultaneous identical queries. Either hold a per-key SemaphoreSlim, or accept a short stale window by using a stale-while-revalidate pattern with two expiry times.

14.2 IDistributedCache and serialisation cost

A cache shared across instances, and the byte cost that appears the moment the value is not a primitive.

IDistributedCache serialises values to bytes. The default formatters are JSON, which costs CPU on both write and read and produces larger payloads than binary serialisation for polymorphic object graphs. Redis also imposes a network round trip, typically sub-millisecond in-region and considerably more across regions.

builder.Services.AddStackExchangeRedisCache(o =>
{
    o.Configuration = builder.Configuration.GetConnectionString("Redis");
    o.InstanceName = "orders:";
    // Microsoft.Extensions.Caching.StackExchangeRedis ships a serializer
    // hook; MessagePack or protobuf beat JSON for object graphs.
});

public sealed record CustomerSnapshot(Guid Id, string Name,
    string Tier, DateTimeOffset AsOf);

Two operational properties matter more than the serialiser choice. First, a distributed cache is a dependency that can be unavailable, and every call to it must have a defined behaviour when it is — the standard answer is to treat a cache exception as a miss and carry on. Second, eviction is often configured as allkeys-lru, which means a hot key can be evicted under memory pressure with no notification and no error.

Cache-aside with a timeout. Wrap the distributed cache call in a short cancellation token — tens of milliseconds — and treat a timeout as a miss. A cache that adds 200 ms to every request during an incident has become the outage.

14.3 Hybrid cache in .NET 10

The two-tier cache added to the framework in .NET 10, and the stampede protection it provides.

Hybrid cache is a two-tier cache over a level-one in-process cache and a level-two distributed cache, shipped in Microsoft.Extensions.Caching.Hybrid for .NET 10. Its purpose is to remove the manual stampede handling described in 14.1 by serialising concurrent requests for the same key within an instance.

builder.Services.AddHybridCache(o =>
{
    o.DefaultName = "default";
    o.DefaultTtl = TimeSpan.FromMinutes(5);
});

builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = builder.Configuration.GetConnectionString("Redis"));

builder.Services.AddHybridCache<CustomerSnapshot>("customers");

// Usage
var snap = await hybrid.GetOrCreateAsync<CustomerSnapshot>(
    "customers", key, LoadAsync, ct);

Adopt it when a distributed cache is already required and stampede protection is currently hand-rolled. Do not adopt it to add a second cache tier where one would do: the stampede problem is real only for expensive recomputation, and an in-memory cache with a generous TTL already solves it within a single instance.

Eviction semantics still apply. Hybrid cache inherits level-one eviction under memory pressure and level-two eviction under the distributed policy. Neither is a notification, so no design may depend on an entry surviving.

14.4 Output caching and Vary correctness

Caching whole responses, and the two headers that decide whether a cached response can be served to the wrong caller.

Output caching stores the serialised response for an endpoint. Applied naively it is a security vulnerability: the first user’s response is served to everyone who requests the same URL. The Vary header is what prevents that, and it must include Authorization for any endpoint whose response depends on the principal.

builder.Services.AddOutputCache();

app.MapGroup("/public").WithOutputCache(o =>
{
    o.AddPolicy("catalog-1m", p =>
    {
        p.Expire(TimeSpan.FromMinutes(1));
        p.Tag("catalog");
    });
});

app.MapGroup("/me").WithOutputCache(o =>
{
    o.AddPolicy("private-30s", p =>
    {
        p.Expire(TimeSpan.FromSeconds(30));
        p.SetVaryByHeader(HeaderNames.Authorization);
        p.NoCache();
    });
});

Output caching is placed after authorization in the pipeline, which is correct: the cache key can then include the principal. Placing it before authorization caches a response that was produced without knowing who the caller is, which is how personalised data leaks.

Tag-based invalidation requires the tag setter. AddPolicy with a tag lets another component evict by tag, but only if the evicted route is also output-cacheable. Invalidating a tag that no policy declares is a silent no-op, so assert tag coverage in a test.

14.5 Invalidation: the part that is always hard

Time-based, event-based and version-based expiry, and the trade each makes about correctness.

StrategyCorrectnessCostUse when
Absolute expiryBounded stalenessNoneReference data with a business-defined TTL
Sliding expiryBounded staleness, hot-key biasNoneEntries whose value improves with use
Event-based evictionImmediate, if the event arrivesCoupling to the writerData with a clear owning command
Version-stamped keysImmediate, at the cost of a lookupOne extra read per requestLarge, hot, frequently mutated data

Event-based eviction couples the writer to the cache. That is acceptable within one service; across services, the event must be published, and the subscriber may be down when the invalidation is emitted, so event-based eviction needs a fallback TTL to bound the damage.

Version-stamped keys are the most robust for a single service: include a monotonically increasing version in the key, read the version from a cheap source, and let the old entry expire naturally. The cost is one extra read, which is frequently cheaper than a wrong answer.

Cache keys are a security boundary. A key that omits the tenant identifier, the user identifier or the relevant culture returns one user’s data to another. Every key builder deserves a test that asserts two different subjects produce two different keys.

14.6 A caching policy that survives review

A written policy that makes cache decisions reviewable instead of individual.

A policy with four clauses covers nearly every case and forces the questions that matter at design time rather than in a post-incident review.

  1. Every cache entry has a named TTL and a named owner. An entry with no TTL is a leak; an entry with no owner is unreachable invalidation.
  2. Every key includes the tenant and every principal-dependent dimension. Verified by a test per key builder, not by inspection.
  3. Cached data is reconstructible. If losing the cache loses data permanently, it is not a cache and must not be treated as one.
  4. A cache failure degrades latency, not correctness. Every call site handles a miss and a thrown exception identically.

The fourth clause is the one most often violated under incident pressure. A code path that returns a stale-empty result when the cache is unreachable will convert a cache outage into a data outage, and the coupling will not be visible in the cache layer’s own metrics.

15 · Background Work: Hosted Services and Channels

15.1 IHostedService and BackgroundService15.2 Creating a scope per work item15.3 Channels as an in-process queue15.4 Bounded channels and backpressure15.5 External queues and the outbox pattern15.6 Shutdown, drain and the hosted-service contract

Work that outlives a request needs its own lifetime, its own scope, and a defined behaviour when the process stops. This chapter covers the in-box primitives and the discipline that keeps them from losing work silently.

Three hosting models exist: IHostedService for a start-and-stay-running task, BackgroundService for a long-running loop, and a queue or broker for work that must survive the process. Choosing a channel over a broker is a durability decision, not a convenience one.

15.1 IHostedService and BackgroundService

The two interfaces, when each applies, and the startup ordering constraint that trips most implementations.

BackgroundService is an IHostedService whose ExecuteAsync is awaited until the stopping token is signalled. Use it for a loop; use plain IHostedService for a one-shot task such as warming a cache or running a migration gate.

public sealed class OutboxRelay : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly ILogger<OutboxRelay> _log;

    public OutboxRelay(IServiceScopeFactory scopes, ILogger<OutboxRelay> log)
    { _scopes = scopes; _log = log; }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopes.CreateAsyncScope();
            var n = await scope.ServiceProvider.GetRequiredService<IOutboxDrain>()
                .DrainAsync(BatchSize, stoppingToken);
            if (n == 0)
                await Task.Delay(250, stoppingToken);
        }
    }
}

Hosted services start in registration order and stop in reverse. Anything that must be listening before another hosted service connects to it must be registered first. This is the usual cause of a "sometimes the consumer cannot connect at startup" report.

Startup is not synchronous. The host calls StartAsync and moves on; a BackgroundService that does real work before its first await blocks host startup. Do the minimum synchronously, then yield.

15.2 Creating a scope per work item

The pattern that makes scoped dependencies usable from background work, and the per-batch versus per-item decision.

A BackgroundService has no request scope. Creating one scope per batch keeps a DbContext alive across several units of work, which is efficient but means one failed item can poison the whole batch. Creating one per item is the opposite. The choice follows from whether the batch is a transaction or a queue drain.

// Per-item: correct when each item is an independent unit of work.
await foreach (var msg in reader.ReadAllAsync(stoppingToken))
{
    await using var scope = _scopes.CreateAsyncScope();
    try
    {
        await scope.ServiceProvider.GetRequiredService<IEmailSender>()
            .SendAsync(msg, stoppingToken);
        await scope.ServiceProvider.GetRequiredService<ISentStore>().MarkAsync(msg.Id, ct);
    }
    catch (HttpRequestException ex)
    {
        _log.LogWarning(ex, "Send failed for {Id}; will retry.", msg.Id);
    }
}

Note that the success marker and the side effect are in the same scope and therefore not in the same transaction unless one is added. A retried message that was actually sent duplicates the email. For anything with an external side effect, record the intent before acting and reconcile afterwards.

A scope per iteration is not free. It builds a new DbContext, a new change tracker and a new connection checkout per item. For a high-rate queue, batch several items into one scope and accept coarser failure granularity — then make the handler idempotent so a re-processed item is harmless.

15.3 Channels as an in-process queue

A lock-free in-process queue, and the precise condition under which it is the right structure.

System.Threading.Channels is in-box since .NET Core 3.0. It is a bounded or unbounded producer-consumer queue with no serialisation, no persistence and no delivery guarantee across process restarts. That makes it exactly right for handing work from a request to an in-process consumer, and exactly wrong for anything that must survive a deploy.

public sealed class InProcessQueue : new(BackgroundService)
{
    private readonly Channel<WorkItem> _channel =
        Channel.CreateBounded<WorkItem>(
            new BoundedChannelOptions(10_000)
            {
                FullMode = BoundedChannelFullMode.Wait,
                SingleReader = true,
                SingleWriter = false
            });

    public ValueTask EnqueueAsync(WorkItem item, CancellationToken ct)
        => _channel.Writer.WriteAsync(item, ct);

    public void Complete() => _channel.Writer.TryComplete();

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var item in _channel.Reader.ReadAllAsync(ct))
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            await scope.ServiceProvider.GetRequiredService<IWorkHandler>()
                .HandleAsync(item, ct);
        }
    }
}

Set SingleReader and SingleWriter accurately. Setting them when they are false removes synchronisation that the channel needs; leaving them false when they are true costs a small amount of unnecessary work. The values are a one-line decision with a measurable consequence.

Complete the writer on shutdown. TryComplete lets the reader drain what is queued and then exit naturally, instead of being cancelled mid-item. This is the difference between graceful shutdown and dropping work.

15.4 Bounded channels and backpressure

The three full modes, and the one design error that turns a bounded channel into an unbounded one.

A bounded channel is the mechanism that makes backpressure real: a producer that writes to a full bounded channel waits, which slows the producer, which is the request path. With an unbounded channel, the producer never waits and the queue grows until memory is exhausted. The bound is the only thing standing between a burst and an out-of-memory termination.

// Wait: producer blocks (or awaits) until space exists. Correct default.
FullMode = BoundedChannelFullMode.Wait

// DropOldest / DropWrite: producer never blocks, items are discarded.
FullMode = BoundedChannelFullMode.DropOldest

Choosing DropWrite or DropOldest is a business decision disguised as a configuration option. It is correct for a metrics or notification stream where the newest or least important sample is genuinely worthless. It is never correct for a payment, an order or an audit record, and for those the correct mode is Wait — with the request failing or being delayed, which the client should be told about.

Measure the depth. A channel’s count is a leading indicator of imminent failure and is available as Reader.Count. Expose it as a metric and alert on it; a channel that fills silently is how a system degrades for twenty minutes before the first 500.

15.5 External queues and the outbox pattern

Why a broker alone is not enough, and the table that closes the gap between the database and the queue.

Publishing to a broker after committing the database creates a dual-write problem: if the process dies between the commit and the publish, the event is lost with no trace. The transactional outbox removes the window by writing the message to a table in the same transaction as the state change, and letting a relay publish it afterwards.

// Outbox row written in the SAME transaction as the state change.
db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage
{
    Id = Guid.NewGuid(), Type = "order.placed",
    Payload = JsonSerializer.Serialize(new OrderPlacedMessage(order.Id, order.Total)),
    OccurredAt = clock.GetUtcNow().UtcDateTime,
    PublishedAt = null
});
await db.SaveChangesAsync(ct);   // atomic

The relay selects unpublished rows, publishes them, and marks them published. Because publication is at-least-once, consumers must be idempotent, and the message identifier is what makes that possible. The relay must also not publish rows it is already publishing — a claim with a lease column, or SELECT … FOR UPDATE SKIP LOCKED, prevents two relay instances duplicating a burst of work.

15.6 Shutdown, drain and the hosted-service contract

The three-phase shutdown the host provides, and the behaviour expected of each phase.

On stop, the host signals the stopping token, awaits each hosted service up to HostOptions.ShutdownTimeout, then terminates the process. A service that ignores the token is killed mid-item. A service that respects the token but does not flush is killed with an unflushed buffer.

builder.Services.Configure<HostOptions>(o =>
{
    o.ShutdownTimeout = TimeSpan.FromSeconds(30);
    o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.StopHost;
});

public override async Task StopAsync(CancellationToken ct)
{
    Complete();                        // stop accepting new work
    await base.StopAsync(ct);   // drains the reader
    await FlushAsync(ct);       // persist anything buffered
}

BackgroundServiceExceptionBehavior decides what an unhandled exception in a background loop does. The default, StopHost, is correct: a background service that has thrown is in an unknown state, and continuing to run it is worse than restarting the process. Set it to Ignore only for a service whose failure is genuinely isolated and observable.

Flush before the host stops. The final FlushAsync is where in-memory buffers, rate-limit counters and unacknowledged channel items are persisted. A service that only respects the cancellation token loses everything queued in the last second of its life, which is precisely the window in which a deploy occurs.

16 · Resilience: Retries, Breakers, Timeouts and Bulkheads

16.1 The four strategies and what each assumes16.2 Polly v8 pipelines and ordering16.3 Retry: which failures, and how many16.4 Circuit breakers and the failure threshold16.5 The standard HTTP resilience handler16.6 Bulkheads and timeouts at the edges

Resilience is the difference between a dependency failing and a system failing. This chapter covers the Polly v8 pipeline model, the ordering rules that make a pipeline correct, and the discipline required to avoid retries that amplify an outage.

Polly v8 replaced the policy-composition API of v7 with a single ResiliencePipeline built from strategies. Polly is not in-box; the standard HTTP integration ships as Microsoft.Extensions.Http.Resilience.

16.1 The four strategies and what each assumes

The distinct failure-handling strategies, and the assumption each one makes about the dependency.

StrategyAssumesEffect on load
RetryThe failure is transient and will clearIncreases load while the dependency is degraded
Circuit breakerThe dependency is down, not slowReduces load to near zero while open
TimeoutThe caller cannot wait indefinitelyReleases resources sooner
Rate limiterDemand must be shaped before arrivalRejects work at the boundary

Retry is the only one that can make an incident worse. If a dependency is saturated and each request consumes a resource that would have served another request, a retry multiplies the pressure. Retrying without a budget, without jitter and without a circuit breaker converts a partial degradation into a total outage.

Never retry a non-idempotent operation without an idempotency key. A timed-out POST may well have succeeded. The client sees a timeout and retries, and the second attempt creates a duplicate. The fix is an idempotency key honoured by the server, not a longer timeout.

16.2 Polly v8 pipelines and ordering

How a v8 pipeline is composed, and why the order of strategies is not interchangeable.

Polly v8 composes strategies into one pipeline. The order determines semantics: outer strategies wrap inner ones, and the exception-handling callbacks see exceptions thrown by everything inside them.

static ResiliencePipeline<HttpResponseMessage> BuildPipeline(ResiliencePipelineOptions o) =>
    ResiliencePipelineBuilder.Create()
        // 1. outermost: give up on the whole call
        .AddTimeout(TimeSpan.FromSeconds(5))
        // 2. stop calling a dependency that is failing
        .AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            SamplingDuration = TimeSpan.FromSeconds(10),
            MinimumThroughput = 20,
            BreakDuration = TimeSpan.FromSeconds(30)
        })
        // 3. then, within one attempt, cap each call
        .AddTimeout(TimeSpan.FromSeconds(2))
        // 4. innermost: retry the individual attempt
        .AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 2,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true
        })
        .Build();

Retry innermost and timeout outside it, so each attempt has its own timeout and the total is bounded. The circuit breaker outside both, so it observes the final outcome of the whole call rather than a single failed attempt — otherwise a dependency that fails on the first attempt but succeeds on the second never trips the breaker, which is the desired behaviour.

Order is the whole lesson. Timeout outside retry with no total bound means a call that retries twice at two seconds each plus backoff can occupy a request for eight seconds, which exceeds most upstream timeouts. Bound the total explicitly, not just the attempt.

16.3 Retry: which failures, and how many

Classifying failures before retrying them, and the backoff formula that prevents synchronised retries.

Retry only what is genuinely transient. In the HTTP case that means 408, 429 and 5xx status codes plus transport exceptions. A 400, a 401, a 403 or a 404 will fail identically on every attempt, and retrying it wastes the client’s timeout budget and the server’s capacity.

// Exponential backoff with full jitter, capped.
var delay = TimeSpan.FromMilliseconds(Math.Min(
    BaseDelayMs * Math.Pow(2, attempt),
    MaxDelayMs));

// Full jitter: uniform random in [0, delay].
delay = TimeSpan.FromMilliseconds(Random.Shared.NextDouble() * delay.TotalMilliseconds);

Jitter is not optional. Without it, every client that failed at the same instant retries at the same instant, producing a synchronised stampede against a dependency that is only just recovering. Full jitter is more effective than equal jitter for this case and is what the UseJitter option applies.

Cap the attempt count at two or three. Beyond that, the probability that all attempts coincide with the same dependency-wide outage is high, and the cost is borne by the caller. A useful additional rule: never retry inside a retry. Nested pipelines — an API calling an API that calls a database, each with a three-attempt retry — produce a worst case of twenty-seven attempts for one user request.

Retry budget. Cap retries as a fraction of total requests — for example, no more than 10% of calls within a rolling window may be retries. This bounds the amplification factor independently of the failure mode, and is far more robust than a fixed attempt count.

16.4 Circuit breakers and the failure threshold

The two threshold models, the state machine, and how to choose parameters that are neither too eager nor too slow.

The standard strategy opens the circuit when the failure ratio over a sampling duration exceeds a threshold with a minimum throughput, holds it open for a break duration, then permits a probe request in the half-open state. Success closes it; failure reopens it with an increasing break duration.

.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
{
    FailureRatio = 0.5,                 // 50% failures
    SamplingDuration = TimeSpan.FromSeconds(30),
    MinimumThroughput = 10,              // do not trip on 2 calls
    BreakDuration = TimeSpan.FromSeconds(15),
    ShouldHandle = new HttpShouldHandlePredicate
    {
        StatusCodePredicate = s => s.StatusCode
            is HttpStatusCode.RequestTimeout
               or is HttpStatusCode.TooManyRequests
               or (>= 500 && <= 599)
    }
});

MinimumThroughput is the parameter people omit. Without it, two failures on a low-traffic endpoint open the circuit, and a brief period of ordinary errors causes a complete outage for that endpoint. Ten is a reasonable floor; raise it for endpoints with bursty traffic.

Expose breaker state as a metric. An open circuit is a decision the system has made, and an operator seeing a rising count of open breakers learns about the incident before the error rate does.

A breaker without a fallback is a hard failure. When the circuit is open the call throws BrokenCircuitException immediately. If the caller has no fallback — a stale cached value, a degraded response — the breaker converts a slow dependency into a fast error. That is usually better, but it must be a chosen outcome.

16.5 The standard HTTP resilience handler

The one-line registration that applies a sensible default pipeline, and the three things to check after adopting it.

Microsoft.Extensions.Http.Resilience provides a standard handler that composes a rate limiter, a total timeout, a retry, a circuit breaker and a per-attempt timeout with defaults chosen to work for most dependencies.

builder.Services.AddHttpClient<IPaymentGateway, StripeGateway>()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 2;
        o.Retry.Delay = TimeSpan.FromMilliseconds(500);
        o.Retry.BackoffType = DelayBackoffType.Exponential;
        o.Retry.UseJitter = true;
        o.CircuitBreaker.FailureRatio = 0.5;
        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(10);
        o.CircuitBreaker.MinimumThroughput = 10;
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(5);
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(20);
    });

Three things to check after adopting it. First, does the gateway require idempotency for retried operations — if so, confirm the handler only retries idempotent verbs. Second, is the total timeout shorter than the caller’s own timeout, so a retry cascade cannot outlive the upstream request. Third, are telemetry and logging enabled, so breaker transitions and retry counts are visible.

Register per client, not globally. A named or typed client with its own handler lets each dependency have its own thresholds. A dependency that tolerates a five-second stall should not share a breaker with one that does not.

16.6 Bulkheads and timeouts at the edges

Isolating resource pools so one saturated dependency cannot consume the whole process.

A bulkhead limits concurrent operations. The practical forms are a semaphore with a bounded permit count, a dedicated connection pool, or a separate HttpClient handler with its own concurrency ceiling. The goal is that a dependency which stops responding occupies at most its own partition, leaving capacity for everything else.

// A simple bulkhead as a shared factory of bounded concurrency.
public sealed class Bulkhead
{
    private readonly SemaphoreSlim _gate = new(MaxConcurrent);
    public int MaxConcurrent { get; }

    public async Task<T> RunAsync<T>(
        Func<CancellationToken, Task<T>> work, CancellationToken ct)
    {
        if (!await _gate.WaitAsync(0, ct))
            throw new BulkheadFullException();
        try { return await work(ct); }
        finally { _gate.Release(); }
    }
}

// Polly v8 ships one: .AddConcurrencyLimiter(permitLimit, queueLimit)

Fail fast with WaitAsync(0) rather than queueing. Queuing a bounded number of requests converts an overload into latency, and latency is what causes the upstream timeout that started the incident.

Timeouts complete the set because they are the mechanism that actually releases resources. A retry without a per-attempt timeout holds a connection for the full upstream default, which is thirty seconds in the common configuration. Set the attempt timeout first, then everything else.

Logs explain, traces locate, metrics detect. Treating them as three views of the same data is a category error that produces three tools none of which answers its question well. This chapter assigns each signal a job and instruments accordingly.

OpenTelemetry is the recommended instrumentation path in .NET 10. Structured logging remains in-box through Microsoft.Extensions.Logging.

17.1 The three signals and what each answers

A decision table for choosing a signal, stated so the choice does not depend on which tool happens to be installed.

QuestionSignalWhy
Is something wrong right now?MetricCheap, aggregated, alertable
Which request was slow, and where in the time?TracePer-request structure and timing
Why did this specific request fail?LogRich, unstructured-in-shape, high cardinality
How often does this happen?MetricA log count is a bad substitute

The most common misapplication is emitting a log line per request. It is expensive to store, expensive to query, and answers none of the questions above well. A single http.server.request.duration histogram with a route label answers "how often and how slow" for every request at a fraction of the cost.

Correlate, do not duplicate. A log line should carry the trace identifier, and the trace should carry the request metadata. When both contain the full payload, the two disagree eventually and neither can be trusted.

17.2 Structured logging and message templates

Why the template — not the formatted string — is the unit of logging, and what that forces on the call site.

A message template is a format string with named holes, and the named values are stored as structured properties alongside the rendered text. This is what allows a log store to index CustomerId as a field rather than requiring a regular expression over free text.

_log.LogInformation("Order {OrderId} placed for customer {CustomerId} totalling {Total} {Currency}",
    order.Id, order.CustomerId, order.Total, order.Currency);

// Scope: properties attached to every line within the block.
using (_log.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = order.Id,
    ["CustomerId"] = order.CustomerId
}))
{
    _log.LogInformation("Order placed.");
    // ... further work, all lines carry the identifiers
}

Because the template is a compile-time constant, the logging call is visible to the source generator and to static analysis. A template built at runtime by concatenation defeats both, and produces a log line that no query can index.

Two rules keep the stream usable. Never log a secret, a token or a full card number; the log store is a broader audience than the application. And never interpolate a value into the template — pass it as an argument, so it becomes a property rather than part of the message text.

Guard expensive arguments. if (_log.IsEnabled(LogLevel.Debug)) around a call whose arguments require a database lookup is not premature optimisation. A debug log that performs a query runs in production, every time, for a level nobody is reading.

17.3 The LoggerMessage source generator

Compile-time log methods, and the measurable reason to use them on a hot path.

The LoggerMessage source generator turns a partial method into a log call with pre-resolved level checks, removing the boxing and the repeated template parsing. It also makes the message template and parameter list a compile-time contract, so a renamed property is a build error.

public static partial class Log
{
    [LoggerMessage(EventId = 1001, Level = LogLevel.Information,
        Message = "Order {OrderId} placed for customer {CustomerId} totalling {Total} {Currency}")]
    public static partial void OrderPlaced(this ILogger logger,
        Guid orderId, Guid customerId, decimal total, string currency);
}

The EventId is worth the discipline it imposes. A stable numeric identifier survives a message-text change, so an alert or a dashboard written against event 1001 keeps working after the wording is corrected. Numeric identifiers without a registry are close to useless, so keep the list in the repository.

Adopt for libraries, allow for applications. The generator pays off most in a shared library where the log calls are on a hot path and the wording is a public contract. In an application, _log.LogInformation with a constant template is already good practice and the generator is optional.

17.4 OpenTelemetry traces and span design

Automatic instrumentation, the two places manual spans are worth adding, and the cardinality limits that keep traces affordable.

ASP.NET Core, HttpClient and EF Core all have built-in instrumentation. Enabling it gives a complete trace of a request across the process and out to dependencies with no application change, which is the correct starting point.

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService(
        serviceName: "orders-api",
        serviceVersion: typeof(Program).Assembly.GetName().Version!.ToString()))
    .WithTracing(t => t
        .AddSource("Orders.Application")
        .AddAspNetCoreInstrumentation(o =>
            o.RecordException = true;
            o.Filter = ctx => !ctx.Request.Path.StartsWithSegments("/health"))
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddOtlpExporter());

Manual spans are worth adding in two places: around a business operation that spans several steps and would otherwise be invisible, and around a genuinely slow external call whose duration the automatic instrumentation does not capture. Adding a span around every method produces noise, cost and no information.

using var activity = ActivitySource.StartActivity("order.place");
activity?.SetTag("order.id", order.Id);
activity?.SetTag("order.total", order.Total);
// No attribute values that are unbounded: no email, no raw token.

Span attributes have a cost and a limit. A high-cardinality attribute such as a customer identifier turns a span into an indexed field across every trace. Bounded values are safe; identifiers are a judgement call; free text and tokens never are.

17.5 Metrics, cardinality and the instruments that matter

Choosing counters, histograms and gauges, and the one rule that governs every label.

InstrumentUse forExample
CounterMonotonically increasing eventsRequests, errors, retries, breaker transitions
HistogramDistribution of a valueRequest duration, payload size, query duration
GaugeCurrent value that can rise and fallQueue depth, active connections, circuit state
Observable gaugeValue pulled from a collection on scrapePool size, in-flight requests

Cardinality is the constraint. Every distinct combination of label values is a separate time series, and a metric backend will either charge for it, drop it, or fall over. The rule is that a label value must come from a bounded set: a route template, a status-code class, a method, a content type. A raw path with an identifier in it is unbounded and is the most common instrumentation mistake.

// Use the route TEMPLATE, never the concrete path.
Meter meter = new("Orders.Application");
Histogram<double> duration = meter.CreateHistogram<double>(
    "orders.place.duration", unit: "ms");
Counter<long> failures = meter.CreateCounter<long>(
    "orders.place.failures");

var sw = Stopwatch.StartNew();
try { duration.Record(sw.ElapsedMilliseconds); }
catch { failures.Add(1); throw; }

Alert on symptoms, not causes. Page on the error rate and the latency at the 99th percentile. A retry counter or a breaker opening is a cause, and paging on it produces an alert for every dependency hiccup whether or not users are affected.

17.6 Wiring it together and the sampling decision

The complete registration, and the trace-sampling policy that determines whether the data is affordable.

builder.Services.AddOpenTelemetry()
    .WithMetrics(m => m
        .AddMeter("Orders.Application")
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()      // GC, heap, thread pool
        .AddOtlpExporter());

builder.Logging.AddOpenTelemetry(o =>
{
    o.IncludeFormattedMessage = true;
    o.IncludeScopes = true;   // makes correlation possible
});

Include scopes, or log lines cannot be correlated to the span that produced them, which defeats the purpose of having both signals. Do not include the formatted message if the collector already renders it — the duplication doubles the storage cost for no gain.

Sampling is the decision that makes traces affordable. Head sampling at a fixed rate — one percent in production — is simple and unbiased for aggregate latency but drops errors you most want to see. Tail sampling keeps every trace containing an error or exceeding a latency threshold, at the cost of buffering in the collector and holding traces in memory until the decision point.

PolicyKeepsCostUse when
Head, fixed rateA uniform sampleLowestLatency analysis, high volume
Head, parent-basedDistributed traces intactLowMulti-service latency correlation
Tail, error-biasedAll errors plus a latency sampleCollector memoryDebugging production incidents

Verify the pipeline in production. Export to a local collector, make a real request, and confirm that a trace, a metric and a log line with a matching trace identifier all arrive. A broken exporter discovered during an incident is the worst time to discover it.

18 · Testing: Units, Integration and Containers

18.1 What each test level can and cannot prove18.2 Unit tests with xUnit v318.3 WebApplicationFactory and the real pipeline18.4 Testcontainers for real dependencies18.5 Database fixtures, resets and parallelism18.6 Common anti-patterns and their replacements

A test that cannot fail on a real regression is worse than no test, because it consumes trust. This chapter defines what each level proves, gives working setups for the .NET 10 stack, and names the anti-patterns that produce green suites over broken systems.

The test tooling is xUnit v3, Microsoft.AspNetCore.Mvc.Testing and Testcontainers for .NET.

18.1 What each test level can and cannot prove

A defect table for each level, used to decide what to test where rather than to justify a distribution ratio.

LevelProvesCannot prove
UnitDomain rules, edge cases, state transitionsWiring, serialisation, SQL correctness
Slice (WebApplicationFactory)Pipeline, DI, auth, serialisation, routingProvider-specific SQL behaviour
Integration (containers)Real SQL, real provider, real migrationsEverything above it simultaneously
ContractClient and server agreeBusiness correctness

The middle row is where most ASP.NET Core projects have the biggest gap. A unit test suite over handlers can be entirely green while the DI graph is broken, the authorization policy is wrong, or a DTO does not serialise. WebApplicationFactory closes that gap without a database, and it is inexpensive enough to run on every build.

Cover the seams, not the getters. Coverage percentage is not a target. The classes worth covering are the ones that translate between representations — mappers, serialisers, validators, converters — because those fail silently when the contract changes.

18.2 Unit tests with xUnit v3

The current xUnit major version, the async lifetime interface it introduces, and the assertion style it favours.

xUnit v3 is the current major release and moves the test project to an executable with built-in parallelism and Microsoft.Testing.Platform support. [Fact] and [Theory] are unchanged; the lifecycle interface is IAsyncLifetime with ValueTask methods.

public sealed class OrderTests : IAsyncLifetime
{
    private readonly Order _order = new(Guid.NewGuid(), "EUR");

    public async ValueTask InitializeAsync() { _order.Open(); return ValueTask.CompletedTask; }
    public async ValueTask DisposeAsync() => ValueTask.CompletedTask;

    [Fact]
    public void AddLine_duplicate_sku_throws()
    {
        _order.AddLine(new Sku("ABC"), 1, new UnitPrice(10m, "EUR"));
        var ex = Assert.Throws<DomainException>(() =>
            _order.AddLine(new Sku("ABC"), 1, new UnitPrice(10m, "EUR")));
        Assert.Equal("Duplicate SKU in order.", ex.Message);
    }
}

Name the test as a sentence: subject, condition, expectation. The name is the only documentation that cannot go stale, because it fails when the behaviour changes. A theory with inline data for the boundary cases — zero quantity, negative price, currency of the wrong length — replaces a dozen near-identical facts.

Test the invariant, not the implementation. A test that asserts a specific set of method calls on a collaborator breaks every refactoring and catches no defect. A test that asserts the aggregate’s state after an operation survives the refactoring and catches the defect that matters.

18.3 WebApplicationFactory and the real pipeline

Booting the actual host in-process, replacing one registration, and asserting on real HTTP responses.

WebApplicationFactory<TEntryPoint> starts the real Program, including its middleware order, its DI registrations and its configuration providers. Replacements are applied through ConfigureTestServices, which runs after the application’s own registrations and therefore wins.

public sealed class ApiFactory : WebApplicationFactory<Program>
{
    protected override void ConfigureWebHost(IWebHostBuilder b)
    {
        b.UseEnvironment("Testing");
        b.ConfigureAppConfiguration((_, c) => c.AddInMemoryCollection(new
            Dictionary<string, string?>
            { ["Auth:Authority"] = "https://test", ["Auth:Audience"] = "orders-api" }));
        b.ConfigureTestServices(s =>
        {
            s.AddSingleton(new TestAuthHandler());
            // Replace the real DbContext with the container-backed one.
            s.RemoveAll<AppDb>();
            s.AddDbContext<AppDb>(o => o.UseNpgsql(_connString));
        });
    }
}

public sealed class OrderEndpointTests(ApiFactory f) : IClassFixture<ApiFactory>
{
    private readonly HttpClient _client = f.CreateClient();

    [Fact]
    public async Task Unauthenticated_get_returns_401()
    {
        var response = await _client.GetAsync("/api/v1/orders/00000000-0000-0000-0000-000000000001");
        Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
    }
}

The test authentication handler is the standard way to control the principal: it sets an identity and always succeeds, letting the test express the caller explicitly rather than minting a real token. For token-specific tests, keep the real JWT handler and supply a signed test token instead.

Entry point discovery. WebApplicationFactory<Program> needs Program to be reachable. With top-level statements add public partial class Program; at the end of Program.cs, or the type is internal and the factory cannot construct it.

18.4 Testcontainers for real dependencies

Running the actual database in a test, and the three lifecycle rules that keep it fast and reliable.

An in-memory provider or an SQLite substitute will not reproduce the SQL your production database generates, its type coercions, its constraint behaviour or its index selection. Testcontainers runs the real engine in a container, which makes the integration suite slower and the results true.

public sealed class PostgresFixture : async IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlContainer()
        .WithImage("postgres:18-alpine")
        .WithDatabase("orders_test");

    public string ConnectionString => _db.GetConnectionString();

    public async ValueTask InitializeAsync()
    {
        await _db.StartAsync();
        await using var db = new AppDb(new DbContextOptionsBuilder<AppDb>()
            .UseNpgsql(ConnectionString).Options);
        await db.Database.MigrateAsync();
    }

    public async ValueTask DisposeAsync() => await _db.DisposeAsync();
}

Three lifecycle rules keep the suite fast. Share one container across all tests in a collection rather than one per test. Create the schema once with migrations and reset data between tests rather than recreating the schema. And reuse containers across test runs where the developer tooling allows it, because container start-up dominates the suite duration.

Reset with a transaction that is never committed. Begin a transaction in setup and roll it back in teardown: isolation guarantees the data disappears and no truncation logic is needed. The exception is tests that assert on concurrency behaviour, which need real commits.

18.5 Database fixtures, resets and parallelism

Making the shared container safe for parallel test classes, and the isolation levels each approach provides.

A shared container plus parallel test classes means two classes can see each other’s data. Three approaches, in ascending cost: unique schemas per test class created from a template, unique tenant or discriminator values on every seeded row, or disabling parallelisation for the integration collection.

// Option A: unique schema per class.
var schema = "t_" + Guid.NewGuid().ToString("N")[..8];
await using var admin = new AppDb(new DbContextOptionsBuilder<AppDb>()
    .UseNpgsql(conn, o => o.MigrationsHistoryTable(
        "__ef_migrations_history", schema)).Options);
await admin.Database.MigrateAsync();
conn = new NpgsqlConnectionStringBuilder(conn) { SearchPath = schema }.ConnectionString;

Option A is the strongest: complete isolation with no coordination. The cost is a migration per test class, which on a large model is seconds. Option C is the fastest and the least safe, and is appropriate only when the suite is small.

Never point a containerised test at a shared database. The migrations run against it. Use a dedicated container or a dedicated database name derived from the environment, and assert that the connection string contains the expected database in test setup.

18.6 Common anti-patterns and their replacements

Seven test smells that produce a green suite and no confidence, with a concrete replacement for each.

Anti-patternWhy it failsReplacement
Assert only on non-nullPasses while the value is wrongAssert the exact value
Mock the system under test’s collaborators wholesaleTests the mock, not the codeTest the real object with real value types
Mock HttpClient with a message handlerReimplements the client badlyUse a real server or a fake HTTP endpoint
Test through the mediator with a mocked mediatorExecutes no handlerInstantiate the handler directly
Shared mutable fixture stateOrder-dependent failuresOne fixture instance per test class, or a reset
Sleeps to wait for async workFlaky in both directionsAwait a signal, or poll with a bounded timeout
Skipped tests with a tracking issueDecays to permanent silenceFail the build and triage the debt

The sleep is worth dwelling on. Task.Delay(500) before asserting is simultaneously too short on a loaded CI agent and too long on a fast developer machine, which is the definition of a flaky test. The correct construct waits for a condition with a bounded timeout and fails with a diagnostic message on expiry.

Test the contract of the error path. A suite that only asserts on 200 responses will pass while every error response leaks a stack trace. One test per endpoint asserting the 401, the 400 and the 500 body shape is worth more than twenty happy-path tests.

Deployment is where the architectural decisions of the preceding chapters either hold or fail. This chapter covers the publish modes, the container structure, the health probes an orchestrator depends on, and the shutdown behaviour that determines whether a rolling deploy drops requests.

19.1 Publishing, trimming and Native AOT

The three publish targets, what each removes, and the capability that each one costs.

Framework-dependent deployment ships your assemblies and relies on the shared runtime. Self-contained ships the runtime with them. Native AOT compiles to a native binary ahead of time. The trade is binary size and start-up time against reflection-based capabilities, and the capabilities lost are specific and predictable.

ModeStart-upPeak RSSLoses
Framework-dependentFastestHighestNothing
Self-containedFastMediumNothing; larger image
Native AOTTens of msLowestRuntime reflection, MVC, dynamic JSON

Native AOT requires MVC to be absent, reflection-based JSON serialisation to be replaced with the source generator, and every dynamically discovered component — interceptors found by scanning, conventional controller discovery — to be registered explicitly. The JsonSerializerContext is the single most common source of a trim-time failure.

// Requires: Microsoft.DotNet.ILCompiler
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
  <TrimMode>full</TrimMode>
</PropertyGroup>

// Required: every serialised type listed explicitly.
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(OrderRow))]
[JsonSerializable(typeof(ProblemDetails))]
internal sealed partial class AppJsonContext : JsonSerializerContext { }

Measure before choosing AOT. For a request-driven service the throughput difference is usually small; the wins are cold start under scale-out and memory per replica. If the service is not autoscaling aggressively and memory is not constrained, self-contained is the pragmatic choice.

19.2 Container images and layer structure

Layer ordering, the non-root user, and the build-versus-runtime split that keeps the image small.

Layer order determines both image size and cache effectiveness. Restore layers change least, build layers change often, and the published output belongs in a separate runtime image containing no SDK.

# Build stage: restore, then publish
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY ["Orders.sln", "Directory.Packages.props", "Directory.Build.props", "./"]
RUN dotnet restore
COPY . .
RUN dotnet publish "-c" Release "-o" /app "--no-restore"

# Runtime stage: no SDK, non-root, exec form
FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble AS runtime
WORKDIR /app
RUN adduser --system --uid 1654 --group app
COPY --from=build --chown=app:app /app ./
USER app
EXPOSE 8080
ENV ASPNETCORE_HTTP_PORTS=8080 DOTNET_gcServer=1
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

Running as a non-root user is a default, not an option, and the numeric UID is required because orchestration ignores the user name from the image. Setting ASPNETCORE_HTTP_PORTS rather than overriding the entrypoint with a shell preserves process-identity signal delivery, which is what makes graceful shutdown work.

Signal handling breaks with a shell entrypoint. In shell form the runtime becomes a child of the shell, and the orchestrator’s stop signal reaches the shell, which may not forward it. Use exec form and rely on the base image’s entrypoint.

19.3 Health checks: liveness, readiness and startup

Three probes with different failure semantics, and the checks that belong in each.

Conflating them is the most common health-check defect and it amplifies outages. A failed liveness probe restarts the process; a failed readiness probe removes it from rotation. A dependency that is briefly unavailable should fail readiness, never liveness — failing liveness restarts every replica simultaneously and turns a dependency blip into a full outage.

builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddDbContextCheck<AppDb>(
        customTestQuery: async (db, ct) =>
            await db.Database.ExecuteSqlRawAsync("SELECT 1", ct),
        failureStatus: HealthStatus.Degraded, tags: ["ready"])
    .AddCheck<BrokerHealthCheck>("broker", tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
    { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new HealthCheckOptions
    { Predicate = r => r.Tags.Contains("ready") });

Add a startup probe for services that do real initialisation — cache warm-up, migration on boot. Without one, the liveness probe kills a slow-starting process before it has finished starting, and the deployment fails in a loop that looks like an application bug.

Write a custom check that verifies what the service actually needs, not merely that a port accepts. A readiness check that reports healthy while the connection pool is exhausted routes traffic into a service that will fail every request it accepts.

Set thresholds from observed behaviour. Health check options carry timeout, interval and failureThreshold. Choose them so the probe fails within seconds of a real outage while remaining immune to one slow response.

19.4 Graceful shutdown and drain

The shutdown sequence the host implements, and what each party must do for it to complete.

On a stop signal the host stops accepting new requests, waits for in-flight requests up to ShutdownTimeout, stops hosted services in reverse registration order, then exits. Three things commonly prevent completion: a hosted service that ignores the stopping token, a database call without a cancellation token, and a timeout shorter than the slowest legitimate request.

builder.Services.Configure<HostOptions>(o =>
{
    o.ShutdownTimeout = TimeSpan.FromSeconds(30);
    o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.StopHost;
});

// The orchestrator must allow the drain to finish.
terminationGracePeriodSeconds: 45

Order the two values deliberately: the grace period must exceed the shutdown timeout, plus the time the orchestrator needs to deregister the endpoint. Setting them equal guarantees that some in-flight requests are killed, which is exactly the class of error a rolling deploy should eliminate.

PreStop and the load balancer. There is an unavoidable window between the stop signal and deregistration upstream. A short preStop sleep is the common mitigation: it lets the balancer observe the removal before the application begins stopping. Measure the deregistration delay before choosing the value.

19.5 Configuration in twelve-factor deployments

The configuration hierarchy in a container, and the three precedence traps that produce silent defaults.

Configuration arrives from files baked into the image, environment variables, and command-line arguments, in that order of increasing precedence. The image must therefore contain no environment-specific values, and every deployment-specific value must arrive as an environment variable or a mounted secret.

// Environment variables, using the hierarchical separator.
Payments__Provider=adyen
Payments__ApiKey=${PAYMENT_API_KEY}
Database__ConnectionString=Host=pg;Database=orders;Username=app;Password=${DB_PASSWORD}
Auth__Authority=https://login.example.com
Auth__Audience=orders-api

Three traps follow. First, the __ separator: a key written with a single underscore binds nothing and the option silently takes its default. Second, precedence: a value set only in the image cannot be overridden at run time without a rebuild. Third, secrets: a connection string in the image is baked into every layer and every registry copy.

Use options validation to catch all three. ValidateOnStart with rules that reject empty values, wrong-length keys and a mismatched issuer and audience turns each of these into a startup failure with a named cause. It costs one registration per options type and is the highest-value configuration measure available.

19.6 A pre-production checklist

A final list, ordered so that a failure is caught as early as it can be.

  1. Configuration. Every options type registered with ValidateOnStart; no environment-specific value baked into the image; every secret supplied at run time.
  2. Container. Non-root user, exec-form entrypoint, no SDK in the runtime image, image scanned in the pipeline.
  3. Health. Liveness checks only the process; readiness checks the dependencies; a startup probe exists if initialisation is slow.
  4. Shutdown. Shutdown timeout shorter than the orchestrator grace period; every hosted service respects the stopping token; a preStop delay matched to the measured deregistration time.
  5. Resilience. A bounded total timeout on every outbound call; a circuit breaker on every remote dependency; no nested retry pipelines.
  6. Database. Connection pool sized for the replica count; command timeout set explicitly; migrations applied as a separate deployment step, never at application start.
  7. Observability. Traces, metrics and logs exported; a synthetic request confirmed end to end in the target environment; alerts on error rate and p99 latency.
  8. Rollback. The previous image retained; the migration verified backward compatible with the previous application version; the procedure written down and rehearsed.

Two entries are routinely skipped. Migrations run at application start will fail during a rolling deploy, because the previous version is still serving traffic and may not tolerate the new schema; run them as a distinct step and make them additive so both versions work. And a rollback that has not been rehearsed is a hypothesis, particularly once a migration has run.

Migrations must be backward compatible across the deploy window. Adding a nullable column is safe. Renaming a column is not, because the previous version still selects the old name. Use expand-and-contract: add, deploy code that writes both, backfill, deploy code that reads the new, then remove the old — five steps, each individually reversible.
