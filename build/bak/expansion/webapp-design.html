How this guide is organised

This guide covers webapp design from interface architecture to error states and offline patterns. Every chapter follows the same rhythm: topic description, prose explanation, two code examples, and a callout flagging the most common mistake.

Structure of every section

Each h3 section is self-contained: intro, walkthrough, two examples, and a callout. Chapters 1–3 cover architecture, data flow, and states. Chapters 4–8 cover forms, errors, loading, offline, and deployment readiness. The remaining chapters go deep on performance, accessibility, and handoff.

The mindset: flows first, UI second

A webapp is a tool, not a document. Users come to complete a task, not read a story. Every screen should answer: what is the user trying to do here?

Follow the user journey

Start with the primary task. Design the screens that serve it. Add visual polish after the flow works. A webapp that looks great but confuses the user is a failure.

Test with real tasks

Every chapter ends with a concrete task: can the user complete this action without help? If yes, it is done.

Tools you will use throughout

Figma, Penpot, VS Code, and a browser’s DevTools cover every stage of webapp design. No paid tool is required for any chapter.

A typical workflow

Sketch the flow in Figma → prototype the main task → write the HTML/CSS → test in DevTools → iterate. Repeat until the task completes without friction.

Before you pixel-polish, ask: can a first-time user finish the core task? If not, fix the flow first.

1.1 Navigation, routing & state

A webapp needs a clear map: where is the user, where can they go, and what state are they in? Routing is the mechanism; navigation is the pattern.

A simple router sketch

const routes = {
  '/': homeView,
  '/projects': projectsView,
  '/project/:id': projectView,
  '/settings': settingsView
};

function render(route) {
  const view = routes[route] || notFoundView;
  document.getElementById('app').innerHTML = view();
}

1.2 Component boundaries

Components are the units of reuse in a webapp. Each boundto a single responsibility: a button is a button, a card is a card, a page is a page.

Component boundary checklist

// One component, one responsibility
function Button({ label, onClick }) {
  return `<button>${label}</button>`;
}
function Card({ title, body }) {
  return `<section>...</section>`;
}
function Page() {
  return `<main>...</main>`;
}

1.3 Data flow & side effects

State changes should be predictable. User input triggers an action; the action updates state; the UI re-renders. Side effects are isolated to the action layer.

A predictable data flow

const state = { items: [] };
function setState(patch) {
  Object.assign(state, patch);
  render();
}
function addItem(text) {
  setState({ items: [...state.items, text] });
}
function render() {
  document.getElementById('list').innerHTML = state.items.map(i => `<li>${i}</li>`).join('');
}

2.1 Forms, validation & submission

Forms are the primary input surface of a webapp. Validation should be immediate and specific; submission should be idempotent and acknowledged.

A minimal form handler

form.addEventListener('submit', async (e) => {
  e.preventDefault();
  const data = new FormData(form);
  try {
    await fetch('/api/submit', { method: 'POST', body: data });
    showSuccess();
  } catch (err) {
    showError(err.message);
  }
});

2.2 Error states & loading patterns

Loading and error states are features, not exceptions. A webapp that never shows a spinner or an error message is hiding its state from the user.

A loading skeleton

<div class="skeleton">
  <div class="skeleton-line"></div>
  <div class="skeleton-line"></div>
  <div class="skeleton-line"></div>
</div>

2.3 Offline and sync behaviour

A modern webapp must work when the network drops. Service workers cache assets; IndexedDB stores data locally; sync queues pending actions.

A minimal service worker

self.addEventListener('install', (e) => {
  e.waitUntil(caches.open('v1').then(c => c.addAll(assetList)));
});
self.addEventListener('fetch', (e) => {
  e.respondWith(caches.match(e.request).then(r => r || fetch(e.request)));
});
