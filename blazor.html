Orientation · Scope and model selection

0.1 Scope and version pin0.2 The three Blazor models0.3 Choosing a model0.4 Conventions used in this guide

Establishes what this guide covers and the exact platform version it documents. It also introduces the single decision that governs every later chapter: which Blazor rendering model your application runs on.

This guide documents Blazor 10 on the .NET 10 (LTS) SDK. There is no separate Blazor runtime to install and no second language: a Blazor component is a C# class that renders HTML through a Razor template, and it runs on whichever rendering model the host provides.

The framework is a single library, Microsoft.AspNetCore.Components.Web, referenced by the ASP.NET Core shared framework and by the WebAssembly client runtime. What changes between applications is not the component API but where the component executes and how the resulting HTML reaches the browser.

0.1 Scope and version pin

Declares the exact SDK, runtime and component library versions the guidance assumes, and names the surfaces that are out of scope so that examples can be applied without ambiguity.

  • Toolchain — .NET 10 SDK, C# 14, net10.0 target framework.
  • Web framework — ASP.NET Core 10 minimal hosting, MapRazorComponents, MapStaticAssets.
  • Component library — Microsoft.AspNetCore.Components.* 10.x, including Web, WebAssembly, Forms, Authorization and QuickGrid.
  • Out of scope — Blazor Hybrid (MAUI) host internals, legacy blazor.server standalone host, Blazor WebView 2 for Windows Forms, and Visual Studio designer tooling.

Version discipline. Where behaviour changed between .NET 8, .NET 9 and .NET 10 — form handling, enhanced navigation, static asset mapping — the guide states the version that introduced the behaviour. Prefer the current name over the deprecated alias.

0.2 The three Blazor models

Summarises the hosting models available in .NET 10 and the rendering modes layered on top of them. This is the taxonomy the rest of the guide assumes.

ModelHost projectWhere components runStartup cost
Blazor Web AppASP.NET Core projectServer process, Interactive Server or static SSRNegligible
Blazor WebAssembly standaloneClient project plus optional hostBrowser (WebAssembly runtime)Download of runtime and app
Blazor Web App with WebAssemblySingle ASP.NET Core projectServer, browser, or both via AutoNegligible to a full download

On top of those hosting models sit four render modes, selected per component or per route:

  • Static server-side rendering — HTML is produced on the server per request. No component is interactive and no circuit is held open.
  • Interactive Server — components stay alive on the server and communicate with the browser over a SignalR circuit.
  • Interactive WebAssembly — the component and its dependencies are downloaded and executed in the browser.
  • Interactive Auto — prerendered on the server, then the component downloads and runs in the browser for subsequent interaction.

0.3 Choosing a model

Turns the taxonomy into a decision. Most applications should default to Blazor Web App with static SSR and opt individual components into interactivity, rather than choosing a runtime up front.

The .NET 10 guidance is to start with the Blazor Web App template and apply interactivity per component. The default, if you specify nothing, is static server-side rendering: the page is a server-rendered form and nothing else.

Default rule. Use static SSR for content that is genuinely static, and add @rendermode InteractiveServer only to the components that need client state. Blazor Auto is a convenience for pages that benefit from client-side speed but must work before the download completes.

Choose standalone WebAssembly only when the application must run with no server of its own — offline-first, edge-hosted, or integrated into a static site. Choose Interactive Server when the app is data-centric, latency-tolerant, and already depends on a server; it keeps the download to a few hundred kilobytes and keeps the database connection on the server side.

0.4 Conventions used in this guide

Defines the reading conventions used throughout, most importantly how each code sample declares the rendering model it targets. Misreading that label is the most common source of Blazor confusion.

  • Every code sample that depends on interactivity is prefixed by a Render mode: note. The command dotnet new blazor -o App creates the server project used throughout.
  • Server-side and browser-side code are never mixed in one component without saying so. Where both are required, the split is shown as two files.
  • Namespace App is used for the server project, App.Client for the WebAssembly client project and App.Shared for Razor Class Library components shared by both.
  • Package versions are omitted from project files; restore the 10.x versions shipped with the SDK.

1 · Rendering models

1.1 Declaring render modes1.2 Static server-side rendering1.3 Streaming rendering1.4 Interactive Server1.5 WebAssembly and Auto

Defines every render mode in .NET 10, shows the exact code that selects one, and explains the consequences each choice has for latency, download size, prerendering and the availability of browser APIs.

Render mode is a property of a position in the component tree, not of a project. Two components on the same page can run in different modes simultaneously, and a page can be prerendered by the server and then hydrated in the browser.

1.1 Declaring render modes

Shows the two places a render mode is declared and the trade-off between the per-component and the global declaration. It also covers the prerender switch, which controls whether a component renders once on the server before it becomes interactive.

A render mode is declared with the @rendermode directive on a component tag, on the <Routes> element, or on the page component itself. The directive is not inherited by nested components; each interactive subtree needs its own declaration.

// Components/App.razor — global default for every routable page
<Routes @rendermode="InteractiveServer" />

// Components/Pages/Reports.razor — per-page override
@page "/reports"
@rendermode InteractiveAuto

Interactive components are prerendered by default: the server sends finished HTML, the browser establishes a circuit, and the component re-renders in place. Turn prerendering off where the component must not run twice — a component that opens a subscription, increments a counter, or writes to a log will do so during prerender unless suppressed.

@rendermode @(new InteractiveServerRenderMode(prerender: false))

The corresponding WebAssembly form is new InteractiveWebAssemblyRenderMode(prerender: false). The named form InteractiveAuto accepts no arguments; the underlying mode can be obtained through RenderMode.InteractiveAuto when a named instance is required.

1.2 Static server-side rendering

Describes the default render mode in .NET 10: a stateless request that produces HTML and closes. It explains what is available to a static component and what is not, and when static SSR is the correct choice.

With no render mode declared, a component renders once on the server during the HTTP request. The request completes, the component instance is discarded, and the browser receives plain HTML. There is no WebSocket, no circuit, and no client-side framework to download.

  • Event handlers such as OnClick do nothing; there is no runtime to dispatch them.
  • Parameter changes are driven by a new request, not by a re-render.
  • Data is fetched synchronously or awaited during the request, so the response already contains the data.
  • Forms post back to the server and are handled by the request pipeline.

Static SSR is the correct choice for marketing pages, documentation, reports, dashboards that tolerate a page reload, and any first request that must reach a search index or a social preview crawler.

Enhanced navigation. Since .NET 9, client-side navigation inside a Blazor Web App uses enhanced navigation by default, fetching only the new page fragment and merging it into the DOM. A static SSR page therefore behaves like a single-page application without a circuit.

1.3 Streaming rendering

Introduces the mechanism that lets a server-rendered page return HTML progressively, so slow data appears in the correct position instead of blocking the whole response. It covers the attribute, the placeholder component and the cancellation contract.

Streaming rendering is a companion to static SSR, not a separate mode. Mark a component with [StreamRendering] and any await that is still pending at the first flush is replaced by a placeholder; the awaited content is written later into the same response stream.

// Components/Pages/Dashboard.razor — Render mode: static SSR
@page "/dashboard"
@attribute [StreamRendering]

<h1>Dashboard</h1>
<Loading>
    <ProgressBar />
</Loading>

@foreach (var m in Data)
{
    <MetricCard Value="m" />
}

@code {
    private IAsyncEnumerable<Metric>? Data { get; set; }

    [Inject] private IMetricService Metrics { get; set } = default!;

    protected override async Task OnInitializedAsync() =>
        Data = Metrics.StreamAsync(CancellationToken.None);
}

Use <Loading> for inline placeholders, or Placeholder with a LoadingFragment when the pending await returns a component. Streaming only applies to static SSR and to the prerender pass of an interactive component; the interactive re-render waits for the data instead.

1.4 Interactive Server

Describes the mode where component instances live in the server process and the browser relays UI events over a persistent circuit. It covers latency, statefulness, scaling behaviour and the failures that follow from a dropped connection.

In Interactive Server the component never leaves the server. The browser downloads the SignalR client library and a small bootstrap, and every click, keystroke and StateHasChanged travels back over a WebSocket. Rendering produces a render batch that is applied as DOM patches.

ConcernInteractive ServerWebAssembly
Initial downloadApproximately 200–500 KBSeveral MB including runtime
Interaction latencyOne network round tripLocal
Server state per userLive for the circuit lifetimeMust be held client-side
Secrets and databaseNever leave the serverUnavailable in the browser
Offline behaviourRequires the connectionSupported after first load

Because state lives on the server, a circuit consumes a scoped service set per connected user. Long-lived circuits hold those services for as long as the tab is open, which affects DbContext lifetime, memory, and how the application scales out across instances.

Do not scale state across servers naively. An Interactive Server circuit is pinned to one process. Sticky sessions or a backplane such as Azure SignalR are required before adding a second instance, otherwise reconnection lands on a different circuit and component state is lost.

1.5 WebAssembly and Auto

Contrasts browser-side execution with the hybrid Auto mode, including what each can and cannot access, and how Auto resolves which runtime a component ends up in.

Interactive WebAssembly downloads the .NET WebAssembly runtime, the component assembly, and the transitive closure of every assembly the component references. Execution is entirely in the browser: no network round trip per event, and no server dependency once loaded.

Interactive Auto is the pragmatic middle. The component is prerendered on the server, so the first paint is immediate and the page is indexable. While the download proceeds the page is not interactive; when it completes, the same component is instantiated in the browser and continues from the prerendered markup.

// Program.cs — server project — registers both runtimes
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents()
    .AddInteractiveWebAssemblyComponents();

Auto has one consequence worth stating plainly: during prerender the code executes on the server, and after hydration it executes in the browser. Any if (OperatingSystem.IsBrowser()) branch or direct browser API call must be guarded, or the prerender pass will throw.

2 · The component model

2.1 Anatomy of a component2.2 Parameters and parameter view2.3 Cascading values and parameters2.4 Render fragments and templated components2.5 Deriving from ComponentBase

Describes the unit of composition in Blazor: a Razor file compiled into a class that accepts parameters, renders a fragment tree, and can be recomposed. It covers plain parameters, cascading values, render fragments and the base class.

A component is a class deriving from ComponentBase, normally authored as a .razor file. The markup and the @code block are compiled into a single class; the markup becomes an overridden BuildRenderTree method and the @code members become class members.

Components are ordinary classes. They can be unit tested without a browser, subclassed, and used as types in collections. Nothing about them requires a hosting model, which is why the same component runs unchanged under static SSR, Interactive Server and WebAssembly.

2.1 Anatomy of a component

Walks through the structure of a Razor component file, mapping each syntactic region to the C# it compiles into. It covers directives, the markup block, the code block and layout resolution.

Every component file may contain directives, markup, and an optional code block. Directives begin with @ and are compile-time instructions, not runtime statements.

// Components/OrderBadge.razor
@namespace App.Components
@using App.Models
@inherits BadgeBase
@implements IDisposable
@attribute [StreamRendering]

<div class="badge badge--@Variant.ToLowerInvariant()">
    @if (IsValid)
    {
        <span class="badge__value">@Value</span>
    }
    @Label
</div>

@typeparam TValue

The order of the regions is not significant. @typeparam declares a generic type parameter on the file, which may be used more than once; @inherits supplies a base class, and @implements adds interfaces such as IDisposable.

Naming. The file name is the component type name, so OrderBadge.razor yields OrderBadge. Filenames may contain a dot, which produces a nested namespace: Forms/Field.razor becomes App.Forms.Field.

2.2 Parameters and parameter view

Explains how a parent passes data to a child through [Parameter] properties, how the framework detects changes by identity rather than by value, and what the ParameterView type provides for manual control.

Parameters are public or private properties annotated with [Parameter]. The parent assigns them through the component tag; the framework supplies the values and triggers a render when the set of parameters changes.

// Components/OrderRow.razor
<tr class="@(IsSelected ? "selected" : null)">
    <td>@Order.Number</td>
    <td>@Order.Customer</td>
    <td>@Order.Total.ToString("C")</td>
    <td><button @onclick="Select">Select</button></td>
</tr>

@code {
    [Parameter, EditorRequired]
    public Order Order { get; set; } = default!;

    [Parameter]
    public bool IsSelected { get; set; }

    [Parameter]
    public EventCallback<Order> OnSelect { get; set; }

    private Task Select() => OnSelect.InvokeAsync(Order);
}

Identity, not equality. The renderer re-renders a child when the parameter set changes, and treats an unchanged reference to a mutated object as unchanged. Mutate a collection in place and the child will not re-render; assign a new instance, or call StateHasChanged, or use an immutable update pattern.

EditorRequired turns a missing parameter into a build-time or start-up diagnostic. For advanced cases, SetParametersAsync(ParameterView) can be overridden to consume parameters manually; ParameterView.TryGetValue reads a single value and SetParameterProperties applies the conventional mapping.

2.3 Cascading values and parameters

Describes the mechanism that passes data down an arbitrary component subtree without threading parameters through every intermediate component. It covers fixed versus mutable cascading values and the correct use of CascadingValueSource.

A cascading value is provided by a parent and consumed by any descendant marked with [CascadingParameter], regardless of depth. It is the right tool for ambient concerns — theme, current user, culture, a feature flag — and the wrong tool for data a component merely needs from its own parent.

// Components/Layout/MainLayout.razor — Render mode: any
<CascadingValue Value="Theme" IsFixed="true">
    <CascadingValue Value="User" IsFixed="true">
        <Body />
    </CascadingValue>
</CascadingValue>

Set IsFixed="true" whenever the value never changes for the lifetime of the subtree. A fixed value is matched by reference and never notifies subscribers, removing a re-render from every descendant whenever the parent re-renders. Leave it unset only when the value is genuinely replaced at runtime.

// A nested search box, four levels down, with no intermediate plumbing
@code {
    [CascadingParameter]
    private Theme Theme { get; set; } = default!;

    [CascadingParameter(Name = "User")]
    private ClaimsPrincipal User { get; set; } = default!;
}

Unnamed ambiguity. If a component declares two cascading parameters of the same type, both must be given a Name in the property declaration. An unnamed parameter matches only the unnamed cascading value.

2.4 Render fragments and templated components

Covers the mechanism a component uses to hand rendering back to its parent, allowing callers to supply markup. It introduces RenderFragment, its generic form, and the Context convention.

A RenderFragment is a delegate returning markup. RenderFragment<TValue> additionally receives a value. Components expose them as parameters — conventionally named ChildContent — which is how @Body, Select, RowTemplate and ItemTemplate work across the built-in library.

// Components/Field.razor
<label for="@Id">@Label</label>
@ChildContent
@if (!string.IsNullOrEmpty(Error))
{
    <span class="field-error" role="alert">@Error</span>
}

@code {
    [Parameter] public string Label { get; set; } = "";
    [Parameter] public string? Error { get; set; }
    [Parameter] public RenderFragment? ChildContent { get; set; }
    private string Id { get; } = "f" + Guid.NewGuid().ToString("N")[..8];
}

A templated component pairs a collection with a fragment that receives each item. Declare the fragment as RenderFragment<T> and accept the Context in the markup with an implicit variable.

<List Items="Orders" Context="order">
    <ItemTemplate>
        <strong>@order.Number</strong> <em>@order.Customer</em>
    </ItemTemplate>
    <EmptyTemplate>
        <p>No orders match the filter.</p>
    </EmptyTemplate>
</List>

2.5 Deriving from ComponentBase

Explains what the base class provides, why subclassing a component differs from composing one, and the specific hazards of overriding BuildRenderTree or OnParametersSet in a derived class.

ComponentBase supplies parameter assignment, the render queue, StateHasChanged, ShouldRender and the event-dispatch path through IHandleEvent. A component that does not derive from it must implement all of that itself; there is no benefit.

Subclassing is appropriate when a family of components shares logic — a shared base for form fields, or for a table that every concrete table extends. It is also the only way to author a component purely in C#, by overriding BuildRenderTree and appending frames with RenderTreeBuilder.

// A code-only component: no .razor file required
public sealed class Separator : ComponentBase
{
    [Parameter] public int Thickness { get; set; } = 1;

    protected override void BuildRenderTree(RenderTreeBuilder b)
    {
        b.OpenElement(0, "hr");
        b.AddAttribute(1, "style", $"border-width:{Thickness}px");
        b.CloseElement();
    }
}

Prefer composition. A base class that a child must subclass to function couples the child to the base’s parameter names and lifecycle order. Inheriting to reuse a few methods is the most common source of lifecycle bugs in Blazor codebases.

3 · Component lifecycle

Enumerates the fixed order in which the framework calls a component’s lifecycle methods, explains what each stage guarantees, and shows how to release resources. The order is identical in every render mode, which makes lifecycle logic portable.

A component instance is created, receives its parameters, renders, may re-render many times as state changes, and is finally disposed. The framework guarantees a specific order; the only method a component is allowed to implement is Dispose, and the only one it may omit is Dispose.

3.1 The lifecycle sequence

Lists the full call order from construction through disposal. It distinguishes the one-time initialisation path from the per-parameter-change path, which is the distinction most lifecycle bugs turn on.

1ConstructorOnceYesYes
2OnInitialized / OnInitializedAsyncOnceYesYes

4OnAfterRender / OnAfterRenderAsyncAfter each renderPrerender onlyYes

Under Interactive Auto the sequence runs twice: once on the server during prerender, and again in the browser after the download completes. Anything with a side effect must therefore be written so that running it twice is harmless, or must be gated on OnAfterRenderAsync(firstRender) within a component that sets prerender: false.

3.2 Initialisation methods

Distinguishes OnInitialized from OnParametersSet and shows the correct placement of data loading. It covers the single await rule and the deadlock that follows from awaiting inside a lifecycle method.

OnInitialized runs once, after parameters have been assigned for the first time. It is the right place for work that depends on no parameter — creating a channel, subscribing to an event, initialising a collection.

// Components/Pages/OrderDetail.razor — Render mode: static SSR
@page "/orders/{Id:int}"
@inject IOrderService Orders

<h1>@Order.Number</h1>

@code {
    [Parameter] public int Id { get; set; }
    private Order? Order { get; set; }

    protected override async Task OnParametersSetAsync()
    {
        Order = await Orders.GetAsync(Id);
    }
}

Only one framework call is awaited at a time. Calling StateHasChanged or yielding to a second framework-triggered event from inside a lifecycle method throws InvalidOperationException about a second render being queued. InvokeAsync(StateHasChanged) is the safe way to request a re-render from a non-renderer thread.

One await. A lifecycle method may await once, and it may not call StateHasChanged after that await. Use Task.WhenAll to issue parallel work and await the combined task, or do the work in a method the component calls itself.

3.3 Parameter-change methods

Explains when OnParametersSet fires and how to react to a changed parameter without an infinite render loop. It covers the cascading-value notification case and the ShouldRender gate that usually solves it.

OnParametersSet runs after every parameter assignment, including the initial one, and also fires when a cascading value the component subscribes to changes. That second behaviour is the most common cause of a component that re-renders in a loop.

@code {
    [Parameter] public Customer Customer { get; set; } = default!;
    [CascadingParameter] private CultureInfo Culture { get; set; } = default!;
    private string _formatted = "";

    protected override void OnParametersSet()
    {
        _formatted = Customer.Name.ToString(Culture);
        // no StateHasChanged here — the framework is already rendering
    }

    protected override bool ShouldRender()
        => !string.Equals(_formatted, _lastRendered, StringComparison.Ordinal);
}

Because ShouldRender is consulted after the lifecycle methods and before the render tree is built, returning false prevents the DOM write entirely. The framework does not call it on the first render of a component, so returning false unconditionally hides the component completely.

3.4 After-render methods and the render tree

Explains the only point at which the DOM exists, and therefore the only safe place to call JavaScript interop or measure an element. It covers the difference between OnAfterRender and its asynchronous counterpart and the discipline of a single await.

OnAfterRender and OnAfterRenderAsync run after the browser has applied the render batch. Interop calls made before this point operate on markup that does not exist yet, which is the cause of most "element not found" interop errors.

// Components/Charts/Sparkline.razor — Render mode: Interactive Server
<svg @ref="_surface" width="200" height="40"></svg>

@code {
    [Parameter] public IReadOnlyList<decimal> Points { get; set; } = [];

    [Inject] private IJSRuntime JS { get; set; } = default!;
    private ElementReference _surface;

    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        await JS.InvokeVoidAsync("chart.draw", _surface, Points);
    }
}

Element references are captured by the @ref directive and are only valid while the element is in the document. If the element is re-created by a conditional branch, the reference must be captured again in a later render. The firstRender argument is true only for the first render of an instance; use it for one-time setup such as event registration.

Not called during prerender. OnAfterRender is never invoked on the server for a static SSR page, and is not invoked during the server prerender pass of an interactive component. Code that must run in the browser belongs here, and code that must run on the server belongs in OnInitializedAsync.

3.5 Disposal

Covers the deterministic teardown contract, the difference between the synchronous and asynchronous forms, and the cases where a component owns resources that will otherwise survive it. It also explains when disposal is delayed by the render queue.

A component that owns a resource implements IDisposable or IAsyncDisposable, declared with @implements. The framework calls Dispose when the component leaves the render tree, when its circuit ends, and at the end of the request for a static SSR page.

// Components/Live/Ticker.razor — Render mode: Interactive Server
@implements IAsyncDisposable
@inject NavigationManager Nav

@code {
    private Timer? _timer;
    private CancellationTokenSource? _cts;

    protected override void OnInitialized()
    {
        _cts = new();
        _timer = new Timer(_ => InvokeAsync(() => { Latest = DateTime.UtcNow; StateHasChanged(); }),
                           null, TimeSpan.FromSeconds(1), TimeSpan.FromSeconds(1));
    }

    public async ValueTask DisposeAsync()
    {
        if (_timer is not null) { await _timer.DisposeAsync(); }
        _cts?.Cancel();
        _cts?.Dispose();
    }
}

Do not dispose injected services. A service resolved through @inject is owned by the dependency-injection container, not by the component. Disposing it breaks every other consumer for the remainder of the scope. Dispose only what the component itself created.

If a component implements both interfaces, the framework prefers IAsyncDisposable and awaits it. Dispose is not called in that case, so shared teardown belongs in a single method invoked from both.

4 · State and re-rendering

4.1 What triggers a re-render4.2 Calling StateHasChanged4.3 EventCallback and the render queue4.4 Immutable state and identity4.5 Imperative DOM updates

Explains the rendering contract in detail: what causes a component to re-render, when a manual call is required, how the framework coalesces rapid state changes, and why mutating a reference in place produces a blank update.

Blazor renders a component, diffs the resulting render tree against the previous one, and applies the differences to the DOM. A re-render is therefore an expensive operation to be minimised, not a mechanism to be used to force an update after every field write.

4.1 What triggers a re-render

Enumerates the four conditions that cause the framework to re-render a component automatically. It separates framework-driven causes from application-driven ones and states clearly what does not qualify.

  • The parent re-renders and this component receives a changed parameter set. "Changed" means the set of supplied parameters, not their deep values.
  • The component raises a state change through an EventCallback dispatched from its own markup.
  • The component calls StateHasChanged directly, or a parameterless StateHasChanged delivered from a framework call.
  • A cascading value the component subscribes to changes, if the cascading value was not marked IsFixed.

The framework does not re-render on property assignment. Writing Count = 5 inside a background task produces no DOM change until a render is requested. Nor does it observe mutations of a collection: appending to a List<T> passed as a parameter leaves the child component’s view unchanged.

Prerender is not a render. Under static SSR the single render happens once, during the request. Calling StateHasChanged in a static SSR component has no effect on the response, because the response has already been written or the request has already completed.

4.2 Calling StateHasChanged

Shows the two legitimate uses of an explicit render request — a background completion and a sub-component that cannot re-render its parent — and the correct marshalling of that request onto the renderer’s synchronisation context.

StateHasChanged is a protected method on ComponentBase. It requests that the component be re-rendered at the next opportunity; the framework coalesces several requests into one render.

// Components/Pages/LivePrices.razor — Render mode: Interactive Server
@implements IDisposable
@implements IAsyncDisposable

@code {
    [Inject] private IPricingFeed Feed { get; set; } = default!;
    private readonly List<Tick> _ticks = [];
    private IDisposable? _subscription;

    protected override void OnInitialized()
    {
        _subscription = Feed.Subscribe(tick => InvokeAsync(() =>
        {
            _ticks.Add(tick);
            if (_ticks.Count > 100) _ticks.RemoveAt(0);
            StateHasChanged();
        }));
    }

    public void Dispose()
    {
        _subscription?.Dispose();
        GC.SuppressFinalize(this);
    }
}

A render request raised from a thread the renderer does not own throws unless it is dispatched through InvokeAsync. InvokeAsync returns a Task that completes once the render has been processed, which is the correct way to await a render from a background source.

// Awaiting a render, from a timer or an external event
await InvokeAsync(async () =>
{
    Status = "Connected";
    await RefreshAsync();
    StateHasChanged();
});

4.3 EventCallback and the render queue

Describes the event model, including the automatic render that follows a callback, the difference between EventCallback and Func<Task>, and the coalescing behaviour that protects the renderer from bursty events.

DOM event handlers declared as @onclick="Handler" are wrapped in an EventCallback. When the callback completes, the framework re-renders the component that declared the handler — but not its parent — automatically. No StateHasChanged call is required.

// A parent passes a callback; the child invokes it
<Counter Value="_count" OnValueChanged="OnCountChanged" />

@code {
    private int _count;

    private void OnCountChanged(int value)
    {
        _count = value;              // parent state changes
        // parent re-renders automatically after the callback returns
    }
}

Bind the callback to the declaring component with EventCallback.Factory.Create(this, action) when a method is stored in a field or passed through several layers. Without it, the automatic re-render targets the receiver of the callback rather than the owner, and a visible update can be silently skipped.

SignatureAuto-renderIntended use
EventCallbackYes, on the ownerComponent-to-component events
EventCallback<T>Yes, on the ownerEvents carrying a value
Func<Task>NoDelegates for services and helpers
ActionNoPlain callbacks in non-component code

If a handler throws, the automatic re-render still occurs, so the component refreshes with whatever state it reached before the exception. The exception is reported separately through ErrorBoundary or the circuit’s unhandled-exception path.

4.4 Immutable state and identity

Explains the identity rule that governs whether a child re-renders, and the consequences of mutating shared state. It shows the immutable update pattern and explains why a new reference is sufficient to propagate a change.

The renderer compares parameters by reference using Equals, which for a class is reference equality by default. A new object with identical contents is therefore a change, and a mutated object with a new field value is not.

// Correct: replace the instance, the child re-renders
Customer = Customer with { Status = CustomerStatus.Shipped };

// Correct for a list: produce a new list
Orders = Orders.Add(new Order { Number = "A-1001" });

// Wrong: mutation, the child's markup is stale
Customer.Status = CustomerStatus.Shipped;   // no re-render below this component
Orders.Add(new Order());                    // the <li> count does not change

The same rule explains a frequent support question: a grid does not update after a refresh button is pressed. The service returned a new list, but the component stored it in a field that is not itself a parameter, and no StateHasChanged was issued — or the list was mutated in place and a StateHasChanged produced an identical render tree.

Records help. Declaring state types as record gives value equality and a with expression, which makes the immutable pattern the shortest code to write as well as the safest.

4.5 Imperative DOM updates

Covers the escape hatches for updating the DOM without a re-render, when they are justified and what they cost. It also explains how elements referenced with @ref are updated and why Blazor’s own diffing will overwrite manual changes.

Two mechanisms bypass the render pipeline. A bound attribute such as @bind on a native element writes the value directly to that element on the change event, without a render. A component can also call JavaScript interop with an ElementReference and set properties on it directly.

// Direct write, no render: @bind:after runs after the DOM is updated
<input @bind="_name" @bind:after="OnNameCommitted" />

@code {
    private string _name = "";
    private string _committed = "";

    private void OnNameCommitted()
    {
        _committed = _name;
        StateHasChanged();   // explicit: the input's value is already correct
    }
}

Manual DOM writes are overwritten by the next render, because the render tree is diffed against the tree that produced the current DOM rather than against the DOM itself. Use them only for high-frequency updates — a progress bar redrawn per frame, a canvas, a drag position — and raise ShouldRender to false so the render pipeline does not fight the manual update.

5 · Data binding and forms

5.1 Two-way binding5.2 Input types and binding modifiers5.3 EditForm and EditContext5.4 Validation and ValidationMessageStore5.5 Form names, SSR and antiforgery

Covers the binding syntax, the form components, the validation pipeline and the differences between form handling under static server-side rendering and under interactive render modes. Form behaviour changed materially in .NET 9.

Blazor offers two binding layers. Native element binding attaches to HTML controls directly and requires no model. EditForm binds a model object, runs validation and raises a single submit callback.

5.1 Two-way binding

Explains the @bind directive, the change event chosen for each element type, and the modifiers that override the default event or the timing of the update.

@bind is shorthand for a value expression plus an event handler that writes back to it. The event is chosen from the element: onchange for most inputs, oninput for text-like inputs, onclick for checkboxes and onchange for selects.

// Equivalent to: value="@Name" onchange="e => Name = e.Value.ToString()"
<input @bind="Name" />

<label>
    <input type="checkbox" @bind="IsActive" />
    Active
</label>

<select @bind="CountryCode">
    @foreach (var c in Countries)
    {
        <option value="@c.Code">@c.Name</option>
    }
</select>

The modifiers change when the write-back occurs. @bind:event="oninput" updates the field on every keystroke. @bind:after runs a method once the DOM reflects the new value. @bind:get and @bind:set supply a getter and a setter, which is how a component exposes a computed two-way binding to a caller that passes plain parameters.

// A component exposing a two-way binding without an EventCallback
<Slider @bind-Value="Zoom" Min="1" Max="20" />

@code {
    [Parameter] public int Value { get; set; }
    [Parameter] public EventCallback<int> ValueChanged { get; set; }
}

The convention is a value parameter plus a matching ValueChanged callback. The framework, the bind directive and the Razor compiler all detect the pair automatically, so a caller can write @bind-Value instead of supplying both properties.

5.3 EditForm and EditContext

Describes the model-bound form component, the three submit callbacks, and the role of EditContext in sharing validation state between a form and its inputs.

EditForm binds a model, hosts the validation display, and exposes three mutually exclusive submit callbacks: OnValidSubmit, OnInvalidSubmit and OnSubmit. Supplying more than one is a compile-time error.

// Components/Forms/CustomerForm.razor — Render mode: Interactive Server
@rendermode InteractiveServer

<EditForm EditContext="_editContext" OnValidSubmit="SaveAsync" FormName="customer">
    <DataAnnotationsValidator />
    <ValidationSummary />

    <label>Name</label>
    <InputText @bind="_model.Name" class="form-control" />
    <ValidationMessage For="@(() => _model.Name)" />

    <label>Email</label>
    <InputText @bind="_model.Email" type="email" />
    <ValidationMessage For="@(() => _model.Email)" />

    <button class="btn btn-primary" type="submit">Save</button>
</EditForm>

@code {
    [SupplyParameterFromForm]
    private Customer _model { get; set; } = new();

    private EditContext? _editContext;

    protected override void OnInitialized() => _editContext = new(_model);

    private async Task SaveAsync()
    {
        await Customers.SaveAsync(_model);
    }
}

Pass Model instead of EditContext for a single-model form. Supply an EditContext when the form is inside a component library and the caller must observe validation, or when several forms share one model with different validation rules.

Validation before a render. The validation summary and the per-field messages require a re-render after validation runs. Under Interactive Server or WebAssembly the submit handler triggers that render automatically. Under static SSR the response is produced after the post-back, so the messages appear in the round-tripped page.

5.4 Validation and ValidationMessageStore

Explains the validation model, how DataAnnotations attributes are discovered, how to apply business rules that attributes cannot express, and how to trigger validation from a field rather than from submit.

Data annotations on the model are discovered by reflection through the ValidatableObjectAdapter in DataAnnotationsValidator. A form without that component performs no validation at all, which is the most common reason a form posts invalid data.

// Models/Customer.cs
public sealed class Customer
{
    [Required, StringLength(80)]
    public string Name { get; set; } = "";

    [EmailAddress]
    public string Email { get; set; } = "";

    [Range(1, 5)]
    public int Seats { get; set; } = 1;

    [CustomValidation(typeof(Customer), nameof(SeatsWithinCreditLimit))]
    public string Plan { get; set; } = "";

    public IEnumerable<ValidationResult> Validate(ValidationContext context)
    {
        if (Plan == "enterprise" && Seats > 500)
            yield return new ValidationResult("Enterprise plans start at 500 seats.", [nameof(Seats)]);
    }
}

For rules that depend on server state, add messages to the ValidationMessageStore obtained from the EditContext and notify subscribers. The OnFieldChanged and OnValidationRequested events are the hooks.

// Uniqueness checked against the database, outside the annotations
_editContext.OnValidationRequested += ValidateEmailAsync;

private async void ValidateEmailAsync(object? sender, ValidationRequestedEventArgs e)
{
    if (await Users.IsEmailTakenAsync(_model.Email))
    {
        _messages.Add(new FieldIdentifier(_model, nameof(Customer.Email)), "That email is already registered.");
        _editContext.NotifyValidationStateChanged();
    }
}

Never trust a submit handler. Client-side validation is a convenience. Under static SSR the post-back arrives as a plain form submission that can be replayed or edited, and under interactive modes the model can be altered by a user with dev tools. Re-validate on the server in the handler that performs the write.

5.5 Form names, SSR and antiforgery

Covers the .NET 9 change that requires every server-rendered form to be uniquely named, and the antiforgery protection applied automatically on the post-back.

Since .NET 9, EditForm rendered during a static server-side post-back must carry a FormName that is unique within the page. The framework uses it to match the incoming post to its handler and to reject ambiguous or forged submissions.

// Two forms on one SSR page: names must differ
<EditForm Model="_login"  OnValidSubmit="LoginAsync"  FormName="login">
...
</EditForm>

<EditForm Model="_preferences" OnValidSubmit="SavePrefsAsync" FormName="preferences">
...
</EditForm>

Antiforgery tokens are emitted and verified automatically for EditForm and for a form element that includes the AntiforgeryToken component. Enhanced form handling, which replaces a full page post-back with a fetch, requires the token to be present and requires the page to opt in.

Plain HTML forms. A hand-written <form method="post"> in a Blazor Web App must contain <AntiforgeryToken />; without it the post is rejected with an antiforgery validation failure. The .NET 10 template includes it in every static SSR form by convention.

6 · Layouts, navigation and routing

6.1 Layouts and Body6.2 Routing and route parameters6.3 NavLink and active state6.4 Query strings and page state6.5 Unconfirmed navigation

Describes the layout system, the router, route templates and their constraints, the navigation helpers, and the mechanisms that keep a page’s state in the URL. Routing behaviour differs between interactive and static server-side rendering, and the difference is stated for each example.

A Blazor Web App combines a router, a layout hierarchy and a navigation abstraction. The router maps the current URL to a page component, the layout supplies the chrome, and NavigationManager performs every URL change.

6.1 Layouts and Body

Explains how a layout wraps a page, how the render mode is inherited from the page through the layout to <Body />, and how @layout selects a layout for a single page.

A layout is a component that renders @Body where the routed page should appear. The router renders the page, and the page is wrapped in the layout resolved from LayoutComponentType.

// Components/Layout/MainLayout.razor — Render mode: declared on the page
@inherits LayoutComponentBase

<div class="page">
    <NavMenu />
    <main>
        @Body
    </main>
</div>

Render mode propagates from the page down through the layout to <Body />. A layout that declares its own render mode takes precedence, which is how a page can be static while its navigation remains interactive.

// Components/Pages/Settings.razor — static page, interactive shell
@page "/settings"
@layout MainLayout
@rendermode InteractiveServer

Where several pages share an identical layout structure, use _Imports.razor to set a default @layout for a folder, and a nested layout that composes the shared one. Nested layouts must render their own @Body; the child’s @Body is the parent layout’s content.

One router per document. <Routes /> is rendered once, inside the layout, and may carry the global render mode. Putting a second router inside a page produces ambiguous route resolution and is not supported.

6.2 Routing and route parameters

Covers route templates, optional and constrained parameters, catch-all routes, and the two sources of a route value: generated links and direct URL entry. It also explains route precedence.

A routable component declares a template with the @page directive. The template may appear more than once in a single file, which registers the component under each URL.

// Components/Pages/Products.razor
@page "/products"
@page "/catalog/{category}"
@page "/products/{Id:int:min(1)}"

<h1>@Title</h1>

@code {
    [Parameter] public int? Id { get; set; }
    [Parameter] public string? Category { get; set; }

    private string Title => Id is not null
        ? "Product detail"
        : Category ?? "All products";
}

Constraints such as :int, :guid, :datetime and :min(1) restrict matching. A route whose constraint fails does not fall through to a less specific template of the same component; it produces a not-found result.

When a parameter is absent from the URL it is never assigned, so a non-nullable property keeps its default. Validate required route state explicitly rather than relying on the property being set.

// Catch-all route, with a page-not-found fallback
@page "/{*slug:nonfile}"

@code {
    [Parameter] public string? Slug { get; set }
}

Route order. More specific templates win. /products/new must be registered before a catch-all, and a literal segment always beats a parameter of the same name. The nonfile constraint on a catch-all prevents it from swallowing requests for static assets.

6.3 NavLink and active state

Shows the navigation component that applies the active CSS class automatically, its match modes, and how to build links without a full page reload when navigating outside the router.

NavLink renders an anchor and adds the active class — and disabled for the current page — when the component’s Href matches the current URL. Matching is by full URL, prefix or a custom predicate.

// Components/Layout/NavMenu.razor — Render mode: InteractiveServer
<nav class="sidebar">
    <NavLink href="" Match="NavLinkMatch.All">Home</NavLink>
    <NavLink href="products" Match="NavLinkMatch.Prefix">Products</NavLink>
    <NavLink href="orders" class="nav-link">
        Orders @if (Pending > 0) { <span class="badge">@Pending</span> }
    </NavLink>
    <NavLink href="reports" Match="@(_ => IsOnReports)">Reports</NavLink>
</nav>

NavLinkMatch.All requires the whole URL to match, which stops a link to / appearing active on every page. NavLinkMatch.Prefix is the default and treats the current URL as a prefix of the target.

Links rendered by NavLink are intercepted by the router and do not reload the document. A plain <a href> inside a Blazor Web App is also intercepted for same-origin URLs when enhanced navigation is enabled, but a cross-origin link always performs a full browser navigation.

Programmatic navigation. Use NavigationManager.NavigateTo for redirects, never HttpContext.Redirect, which is unavailable once the response has begun under SSR. In .NET 10 the overload accepts forceLoad and replace to control full reloads and history entry.

6.4 Query strings and page state

Explains how to bind a page property to a query-string value, why the binding only applies to direct URL entry, and the recommended pattern for making filters shareable and bookmarkable.

Since .NET 9 a routable property can be supplied directly from the query string with [SupplyParameterFromQuery]. The router assigns it once, when the component is created for that URL.

// Components/Pages/Products.razor — Render mode: static SSR
@page "/products"

<SearchBox Term="@Term" />

@code {
    [SupplyParameterFromQuery(Name = "q")]
    public string? Term { get; set }
}

The binding is one-way and happens only when the router instantiates the component. A subsequent in-app navigation to a URL with a different query string creates a new page instance under static SSR and enhanced navigation, so the value updates. Under a purely interactive router, the same component instance may be reused, so the filter must also be applied imperatively.

// Reading the current query string imperatively
@code {
    [Inject] private NavigationManager Nav { get; set; } = default!;

    private string Page => new Uri(Nav.Uri).Query;

    private void ApplyFilter(string category) =>
        Nav.NavigateTo($"/products?cat={Uri.EscapeDataString(category)}");
}

Always encode. Interpolating user input into a URL without Uri.EscapeDataString produces a broken URL and, for template-supplied values, a reflected-input bug. Build the URI with QueryHelpers.AddQueryString when composing several values.

6.5 Unconfirmed navigation

Covers the component that blocks navigation when a form is dirty, and the two handlers it exposes. It also shows how the guard interacts with the browser’s own beforeunload prompt.

NavigationLock intercepts navigation attempts within the Blazor router and invokes a handler. The standard use is preventing a half-completed form from being discarded.

// Components/Forms/LockedForm.razor — Render mode: InteractiveServer
<NavigationLock OnBeforeInternalNavigation="Confirm" />
@* ...form fields... *@

@code {
    [Parameter] public bool IsDirty { get; set; }

    private async void Confirm(NavigationLockContext context)
    {
        if (!IsDirty) return;

        var confirmed = await JS.InvokeAsync<bool>("confirm",
            "Discard unsaved changes?");

        if (confirmed) context.PreventNavigation();
    }
}

Leaving the application entirely, through the address bar or a close of the tab, is not a router navigation and is not intercepted. Pair NavigationLock with a beforeunload listener registered in OnAfterRenderAsync and removed in Dispose if the prompt is required for full navigations as well.

Prompt semantics. PreventNavigation cancels the attempted navigation. The handler is synchronous in its decision, so the confirmation dialog is usually asynchronous and must set the context’s outcome before returning — a common source of a lock that appears to ignore the user’s answer.

7 · Component communication

7.1 The communication ladder7.2 Parent to child7.3 Child to parent7.4 Communication through a service7.5 Scoped state containers

Places communication on a spectrum from direct parent-child binding to a shared service, and explains the cost of each step up the ladder. It also introduces the scoped state container that survives navigation.

Blazor offers no global event bus and no parent-to-child method call. Every communication path is either a data flow through parameters, a callback back up, a cascading value, or a service resolved from the injection container.

7.1 The communication ladder

Orders the available mechanisms by coupling and recommends the lowest rung that satisfies the requirement. It also names the anti-patterns that appear when a component reaches too far up the ladder.

MechanismCouplingUse when
ParameterParent and child onlyThe child renders data owned by the parent
EventCallbackParent and child onlyThe child reports a user intent
Cascading valueAny descendantThe value is ambient and rarely changes
Injected serviceComponent to serviceData is needed by unrelated components
Scoped state containerComponent to containerState must outlive the component

Two anti-patterns dominate Blazor codebases. The first is a cascading value that changes constantly, which re-renders every subscriber in the subtree. The second is a component that injects a service to read a value its own parent already holds, which hides the data flow and makes the component untestable in isolation.

Ask two questions. If a component displays data, ask who owns it; if it changes data, ask who must be told. The first answer is a parameter, the second an EventCallback. Escalate only when the answer crosses a component boundary that is not a parent-child relationship.

7.2 Parent to child

Covers parameter passing in detail, including the requirement that parameters be assigned before the first render and the template-based pattern for passing structured content to a container component.

Parameters flow strictly downwards through the component tree. A parent assigns them by tag; the framework applies them before the child’s first render, so a parameterised component can rely on its parameters in OnInitialized.

// Components/Cards/SummaryCard.razor
<article class="card @(IsPositive ? "card--up" : "card--down")">
    <h3>@Title</h3>
    <p class="card__figure">@Amount.ToString("C", Culture)</p>
    @if (ChildContent is not null)
    {
        <div class="card__body">@ChildContent</div>
    }
</article>

@code {
    [Parameter, EditorRequired] public string Title { get; set; } = "";
    [Parameter, EditorRequired] public decimal Amount { get; set; }
    [Parameter] public bool IsPositive { get; set; } = true;
    [Parameter] public CultureInfo? Culture { get; set; }
    [Parameter] public RenderFragment? ChildContent { get; set; }
}

A container component composes others by accepting RenderFragment parameters. Naming them by role — Header, ChildContent, Footer — makes the parent’s intent readable at the call site and keeps the child free of knowledge of its contents.

<SummaryCard Title="Revenue" Amount="_total" IsPositive="@(_total > 0)">
    <Header><h2>This quarter</h2></Header>
    <ChildContent>
        <TrendChart Data="_series" />
    </ChildContent>
</SummaryCard>

7.3 Child to parent

Describes the callback convention, the difference between a notification and a request, and the correct shape for a callback that reports a value back to its owner.

A child cannot mutate its parent’s state. It invokes an EventCallback supplied as a parameter, and the parent decides what to do with the reported value.

// Components/Forms/TagPicker.razor
@foreach (var tag in Candidates.Where(t => !Selected.Contains(t)))
{
    <button type="button" class="chip" @onclick="() => AddAsync(tag)">@tag</button>
}

@code {
    [Parameter] public IReadOnlyList<string> Selected { get; set; } = [];
    [Parameter] public IReadOnlyList<string> Candidates { get; set; } = [];
    [Parameter] public EventCallback<IReadOnlyList<string>> SelectedChanged { get; set; }

    private Task AddAsync(string tag) =>
        SelectedChanged.InvokeAsync([.. Selected, tag]);
}

The callback returns a Task, which the parent may use to withhold completion — for example to run a save before the child closes a panel. The child awaits it; the framework re-renders the parent when the callback returns.

Notification or command. A notification reports a fact and takes no return value. A command asks the parent to perform work and returns a result, and is better expressed by letting the child raise a request and letting the parent call a method on the child in response. Mixing both in one callback makes both sides harder to read.

7.4 Communication through a service

Explains when a shared service is the right boundary, how components subscribe to its notifications, and the marshalling requirement that applies on the server.

A service breaks the parent-child constraint. It is appropriate when several unrelated components read from or write to the same data, or when a value must change outside the component tree — a timer, a background queue, a WebSocket.

// Services/CartStore.cs — registered scoped
public sealed class CartStore
{
    private readonly List<CartLine> _lines = [];

    public event Action? Changed;
    public IReadOnlyList<CartLine> Lines => _lines;
    public decimal Total => _lines.Sum(l => l.Quantity * l.UnitPrice);

    public void Add(CartLine line)
    {
        _lines.Add(line);
        Changed?.Invoke();
    }

    public void Clear()
    {
        _lines.Clear();
        Changed?.Invoke();
    }
}

// A component subscribing to the store

Explains how the dependency-injection container is shared with the component model, what each service lifetime actually spans in Blazor, and why the right choice of lifetime matters more in Blazor than in a request-per-request web application.

Blazor components are constructed by the renderer, not by application code. A component’s parameters are set immediately after construction, and any constructor argument must be resolvable by the container that created the component.

8.1 The container in a Blazor application

Describes the relationship between the host’s service collection and the renderer’s component activator, and clarifies the lifetimes of the two container roots that exist in a hybrid application.

A Blazor Web App has two service roots. The server host owns the application container, built from builder.Services in Program.cs. The WebAssembly client, when present, owns a second, separate container built by WebAssemblyHostBuilder.

Services registered only in the server container are available to components rendered on the server. A component that runs in WebAssembly resolves from the client container, so a service must be registered in the client project as well — or, preferably, in a Razor Class Library that both projects reference.

// Components/RazorClassLibrary/Services/ApiClient.cs
public sealed class ApiClient

    }
}

Registering the typed client in the shared library’s extension method keeps a single registration that both projects call. A service that reaches the database directly and is also registered in the WebAssembly project will fail at resolution, because no such assembly is available in the browser.

8.3 The four lifetimes and what they mean

Defines the four registration lifetimes and, for each, states the boundary at which a new instance is created in a Blazor application. It identifies the lifetimes that differ from a conventional ASP.NET Core application.

  • Singleton — configuration, caches, HTTP client factories, logger wrappers. Never hold per-user state, and never inject a scoped service into a singleton.

9 · JavaScript interop

9.1 When interop is warranted9.2 IJSRuntime calls9.3 JS module imports9.4 Invoking .NET from JavaScript9.5 Interop by render mode

Covers the interop surface in .NET 10: calling JavaScript from a component, importing a JavaScript module, and calling back into .NET from the browser. It states the render-mode restrictions that govern each direction.

Interop is the escape hatch from the Blazor component model. It is also the boundary at which most Blazor performance problems and most prerender failures originate, because it is the one API that behaves differently in every render mode.

9.1 When interop is warranted

Establishes the boundary between what the declarative component model can express and what genuinely requires JavaScript. It names the cases that do not require interop, which are more numerous than developers expect.

Most requirements are met without interop. A browser API that only reads or writes a value on an element is reachable through @ref and a small interop call; a date picker, a chart, a rich text editor and a virtualised infinite scroller are third-party components that wrap interop for you.

Rule of thumb. Reach for interop when the DOM must be read or written in a way the render tree cannot express — measuring, focusing, animating, opening a native dialog, or calling a library with no Blazor binding. Do not reach for it to avoid re-rendering.

Interop is unavailable in three situations: during static server-side rendering, because there is no browser and the response is already being generated; during the server prerender pass of an interactive component, for the same reason; and in a WebAssembly component for APIs that require a server-side secret.

9.2 IJSRuntime calls

IJSRuntime exposes generic and non-generic InvokeAsync, plus InvokeVoidAsync. Calls are asynchronous in every render mode; the in-process IJSInProcessRuntime synchronous path exists only for WebAssembly.

9.3 JS module imports

Explains why a module reference is preferable to a global function, how the module path resolves relative to the app, and how to place a script file where the browser can find it.

Calling a global function pollutes the global namespace and makes the interop surface invisible to tooling. Importing an ES module returns an IJSObjectReference whose methods are namespaced to that module.

// wwwroot/Components/Maps/storeMap.js
let instance = null;

export function create(element, options) {
  instance = new window.StreetMap(element, options);
  return { version: 1 };
}

export function flyTo(lat, lng) {
  instance?.panTo([lat, lng]);
}

export function dispose() {
  instance?.remove();
  instance = null;
}

Files under wwwroot are served as static web assets. The path passed to "import" is relative to the application base, so "./Components/Maps/storeMap.js" resolves correctly under a virtual directory. A component in a Razor Class Library places its script in that library’s wwwroot and imports it with a _content/ path.

Module state is per instance. A module reference is created per import call, and the browser caches the module itself. Two components importing the same module share the module’s top-level variables, so module-level mutable state is effectively global. Keep per-component state in the object the module returns.

Dispose the reference. An IJSObjectReference holds a handle in the runtime’s interop table. In an Interactive Server circuit those accumulate for the life of the circuit; in WebAssembly the table lives for the page session. Always dispose the module and any object references it returns, in DisposeAsync.

Establishes where data access belongs in a Blazor application, which render modes can reach a database at all, and how to structure queries and writes so that components do not become data access layers.

Entity Framework Core is supported on the server and is not supported in a WebAssembly runtime. That single fact determines most data-access architecture decisions in a Blazor application.

10.1 Where the database call belongs

Compares the options for reaching data from each render mode and names the layer responsible for each. It states the rule for separating a component from persistence in an application that mixes render modes.

A component should not own a query. It should render a result and request a change. Persistence belongs in a service that the component injects, which keeps the component testable and keeps the render model out of the persistence decision.

Render modeDirect EF CoreSupported approach
Static SSRYesService, resolved from the request scope
Interactive ServerYes, with careService using IDbContextFactory

For a project that may move between render modes, the pragmatic structure is a repository interface in a shared library, an EF Core implementation in the server project, and an HTTP implementation in the WebAssembly client. Components depend on the interface and remain unchanged across the move.

10.2 The model and the DbContext

Defines the entity configuration pattern, including key configuration, indexes, concurrency tokens and the consequences of putting the context in the shared library.

Configure the model with explicit IEntityTypeConfiguration classes rather than data annotations. The result is a model that survives a refactor of the domain classes and a design that can be reviewed independently of the entity definitions.

// Data/Configurations/OrderConfiguration.cs
internal sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("Orders");
        b.HasKey(o => o.Id);
        b.Property(o => o.Number).HasMaxLength(24).IsRequired();
        b.Property(o => o.Status).HasConversion<string>().HasMaxLength(16);
        b.Property(o => o.RowVersion).IsRowVersion();

        b.HasIndex(o => o.Number).IsUnique();
        b.HasIndex(o => new { o.Status, o.PlacedAt });

        b.HasMany(o => o.Lines)
         .WithOne(l => l.Order)
         .HasForeignKey(l => l.OrderId)
         .OnDelete(DeleteBehavior.Cascade);
    }
}

The DbContext belongs in the server project, not in the shared library, because its provider packages are not available in the browser. Entities and DTOs may live in the shared library so a WebAssembly client can reference them for the API contract.

AsNoTracking by default. Change tracking adds cost to every query and is only needed when the code will save. Apply AsNoTracking to every read query, and let the service decide which of them become tracked entities when preparing an update.

10.3 Querying from a component

Shows a repository service, the difference between composing a query and materialising it, and the cancellation discipline required when a user navigates away mid-query.

Keep the query in the service as composable expressions, and materialise it once. Executing a query per page of a grid is a common source of latency, because the total work is proportional to the number of pages the user visits.

// Services/OrderQueries.cs — Render mode: any server-side mode
public sealed class OrderQueries(IDbContextFactory<AppDbContext> factory)
{
    public async Task<PagedResult<OrderSummary>> SearchAsync(
        OrderFilter filter, CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);

        var query = db.Orders
            .AsNoTracking()
            .Where(o => o.Status != OrderStatus.Closed)
            .Select(o => new OrderSummary(o.Id, o.Number, o.CustomerName, o.Total, o.PlacedAt));

        if (filter.Term is not null)
            query = query.Where(o => o.Number.Contains(filter.Term));

        var total = await query.LongCountAsync(ct);
        var items = await query
            .OrderByDescending(o => o.PlacedAt)
            .Skip(filter.Page * filter.Size)
            .Take(filter.Size)
            .ToListAsync(ct);

        return new PagedResult<OrderSummary>(items, total, filter.Page);
    }
}

Projecting to a DTO inside Select is essential. It keeps unselected columns and navigation properties out of the result set and avoids materialising the full entity graph. Materialising a navigation property with a large collection is the most common cause of an unexpectedly heavy page.

10.4 Writing and concurrency

Covers the write path, the requirement to re-validate on the server, optimistic concurrency with a row version, and the handling of the two exceptions that represent a lost update.

Writes follow the same rule as reads: a component requests a change, the service performs it. Every validation attribute on the model must be re-evaluated server-side, because the submitted model is untrusted input.

// Services/OrderCommands.cs
public sealed class OrderCommands(IDbContextFactory<AppDbContext> factory)
{
    public async Task<Result> CloseAsync(int id, byte[] expectedVersion, CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);

        var order = await db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct)
                   ?? throw new NotFoundException(id);

        db.Entry(order).Property(o => o.RowVersion).OriginalValue = expectedVersion;
        order.Status = OrderStatus.Closed;
        order.ClosedAt = DateTime.UtcNow;

        await db.SaveChangesAsync(ct);
        return new Result(order.Id);
    }
}

A row version configured with IsRowVersion makes the update conditional on the version the client last saw. If another user has already changed the row, SaveChangesAsync throws DbUpdateConcurrencyException. This must be caught and surfaced as a conflict prompt, not as a generic error page.

Refresh after a conflict. The correct recovery is to reload the entity, reapply the user’s intended change to the current state, and let the user confirm. Blindly retrying the same update will fail identically, and overwriting the current state discards the other user’s work.

10.5 Calling an API instead

Defines the required WebAssembly data path, including the typed client, the error handling contract, and the isolation boundary that a Blazor Web App must enforce when the same code runs in the browser.

Under WebAssembly the component talks to an API. The typed HttpClient is injected, the response is deserialised, and the failure case is modelled as a result type rather than an exception, because a network failure is an expected outcome rather than a defect.

// Services/ApiClient.cs — Render mode: Interactive WebAssembly
public sealed class ApiClient(HttpClient http)
{
    private readonly HttpClient _http = http;

    public async Task<Result<OrderSummary[]>> SearchAsync(string? term, CancellationToken ct)
    {
        try
        {
            var url = QueryHelpers.AddQueryString("api/orders", "q", term);
            var items = await _http.GetFromJsonAsync<OrderSummary[]>(url, ct);
            return Result<OrderSummary[]>.Ok(items ?? []);
        }
        catch (HttpRequestException ex)
        {
            return Result<OrderSummary[]>.Fail("The service is unreachable.", ex);
        }
    }
}

The API must enforce authentication and authorisation itself, because every check in a Blazor page is client-side. A component under WebAssembly can be disassembled, its state inspected, and its requests replayed with modified bodies; the API is the only place where a decision can be enforced.

Interactive Auto blurs the line. A component with InteractiveAuto executes its service calls on the server during prerender and in the browser afterwards. A service that reaches the database directly works during prerender and then fails in the browser. Use the API path for any component that may run in the browser.

11.1 Authentication state as a cascading value

Calling AddCascadingAuthenticationState registers a provider and supplies a cascading value of type Task<AuthenticationState>. A component declares the matching cascading parameter and awaits it.

}

The value is a task because authentication may not have completed when the component tree is first built. The framework resolves it once and caches it, so awaiting the same task from several components does not re-authenticate. Reading a claim requires System.Security.Claims.

Read claims in the shell only. Passing a ClaimsPrincipal down to leaf components spreads authorization logic through the tree. Read the name and role once in the layout, and enforce access in a policy at the page boundary.

11.2 AuthorizeView and AuthorizeRouteView

Contrasts the two declarative components, showing when each is used and how a not-authorised template redirects to a login page rather than rendering dead markup.

AuthorizeView renders one of three fragments based on the current principal. AuthorizeRouteView is the routable equivalent, applied to the page component so a page’s access requirement is declared on the page itself.

// Components/Layout/MainLayout.razor
<AuthorizeView>
    <Authorized>
        <div class="user-menu">@context.User.Identity?.Name</div>
    </Authorized>
    <NotAuthorized>
        <a href="/account/login">Sign in</a>
    </NotAuthorized>
    <Authorizing>
        <Loading />
    </Authorizing>
</AuthorizeView>

// Components/Routes.razor
<Router AppAssembly="typeof(Program).Assembly">
    <Found Context="routeData">

            <NotAuthorized>
                @if (context.User.Identity?.IsAuthenticated != true)

                }
                <else>
                {
                    <h1>Not authorised</h1>
                    <p>Your account does not have access to this page.</p>
                }
            </NotAuthorized>

    </Found>
    <NotFound>
        <LayoutView Layout="typeof(MainLayout)">
            <h1>Not found</h1>
        </LayoutView>

The default NotFound behaviour in the template is a redirect to a static 404 page, which is preferable to a blank screen when the router has nothing to match. FocusOnNavigate moves keyboard focus to the heading after navigation, which is an accessibility requirement rather than a nicety.

Declarative gates are not security. AuthorizeView hides markup the user is not entitled to see. It does not prevent the data behind that markup from being fetched. Every protected query and every command must also be authorised in the service or endpoint.

11.3 Policies in components and handlers

Shows how to declare an attribute-based requirement on a page, how to evaluate a policy imperatively, and how to write a custom authorization requirement for a resource-level rule.

[Authorize] on a routable component applies the policy to that page and is evaluated before the component renders. A policy combines authentication requirements, roles, and custom requirements evaluated against the current principal.

// Components/Pages/Reports.razor — Render mode: static SSR
@page "/reports"
@attribute [Authorize(Policy = "reports.view")]

// Program.cs
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("reports.view", p => p
        .RequireAuthenticatedUser()
        .RequireRole("analyst", "manager"))
    .AddPolicy("orders.close", p =>
    {
        p.RequireAuthenticatedUser();
        p.AddRequirements(new OrderClosingRequirement());
    });

A resource-level rule — "may close an order, but only one belonging to their own region" — cannot be expressed with roles. A requirement handler receives the principal and the resource, and returns a result.

// Authorization/OrderClosingHandler.cs
public sealed class OrderClosingHandler
    : AuthorizationHandler<OrderClosingRequirement, Order>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        OrderClosingRequirement requirement,
        Order resource)
    {
        var region = context.User.FindFirst("region")?.Value;
        if (string.Equals(region, resource.Region, StringComparison.OrdinalIgnoreCase))
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}

To evaluate a policy from a component or a service, inject IAuthorizationService and call AuthorizeAsync(user, policy, resource). The overload without a resource skips the resource-level handlers entirely, which is a common cause of a rule that appears to work everywhere except on the one page that passes the entity.

Identity versus role checks. User.IsInRole in a component is a presentation decision. A service that performs the same check with IsInRole and no policy is a second, divergent implementation of the same rule. Call the authorization service from the service layer instead.

Covers the properties that apply only to a browser-hosted runtime: the load sequence, the consequences of trimming and ahead-of-time compilation, and the storage options available for offline state.

Everything in chapters 1 to 11 applies to any render mode. This chapter covers the behaviour that exists only when the component executes in the browser, and the engineering consequences that follow from it.

12.1 The standalone client host

Shows the client project’s entry point, the difference between a standalone and a hosted WebAssembly project, and how a hosted client resolves its base address.

A standalone WebAssembly project has no server project and is published as static files. A hosted client is paired with a Blazor Web App, which serves the client assets and the API it calls.

// Client/Program.cs — WebAssembly entry point
using Microsoft.AspNetCore.Components.Web;
using Microsoft.AspNetCore.Components.WebAssembly.Hosting;

Compare before committing. WebAssembly wins on interaction latency and offline support. It costs a multi-megabyte first load, removes access to server-side data, and moves every security decision to an API. Choose it for a specific reason and record that reason; the default remains Interactive Server.

12.2 Startup and load sequence

Traces the browser load from the first request to the first interactive render, and identifies each artefact on the critical path. It explains what caching changes and what the user perceives during the wait.

The sequence is: the browser requests index.html; the framework loads blazor.boot.json; it downloads the runtime assemblies, the dotnet.native.wasm and dotnet.js pair, and the application’s managed assemblies; the runtime starts the .NET host; the host invokes the application’s Main; the root components render; the circuit or app lifetime begins.

// Reduce the number of round trips
<link rel="preload" href="framework/blazor.boot.json" as="fetch" crossorigin />
<link rel="preload" href="_framework/dotnet.js" as="script" />

Two options change the shape of the load. Blazor Auto moves the perceived cost away by prerendering the first paint on the server. Ahead-of-time compilation makes the remaining work faster but increases the download, which is why the two are usually combined with a measured budget rather than adopted together blindly.

Measure the compressed size. Application payloads are served compressed. Compare the transfer size of the boot manifest plus assemblies, not the uncompressed size on disk, and track it in a build step so a regression is visible in review.

12.3 Trimming and reflection

Explains why the linker removes code that reflection would have found, and the two annotation mechanisms that keep it. It also covers the runtime error that appears when an annotation is missing.

The WebAssembly linker performs static analysis from the application entry point and removes everything it cannot prove is reachable. Code invoked only through reflection is therefore deleted unless the linker is told to keep it.

// A property serialised by System.Text.Json through reflection
public sealed record OrderSummary(
    [property: JsonPropertyName("number")] int Number,
    [property: JsonPropertyName("customer")] string CustomerName);

// A type used only as a generic argument or a base type
[DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.All)]
public class OrderValidator : IValidatableObject
{
    ...
}

The failure mode is a missing method or property at runtime, not at build time, and it appears only in the published application — never in dotnet watch during development. Setting <PublishTrimmed>true</PublishTrimmed> for development restores the untrimmed behaviour so the problem surfaces earlier.

Trim warnings are build errors. A library that calls a virtual method from a constructor, or that uses reflection over a base type, can break when trimmed even though it compiled cleanly. Treat IL trimming warnings in a CI build as failures rather than as noise.

12.4 Ahead-of-time compilation

Introduces native ahead-of-time compilation, what it improves and what it costs, and the settings that control it. It also notes the components that remain unavailable under native compilation.

By default the runtime interprets IL in the browser. With RunAOTCompilation the IL is compiled to WebAssembly ahead of the request, which improves execution speed and reduces total code size at the cost of a longer build.

// Client/Client.csproj
<PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <RuntimeIdentifier>browser-wasm</RuntimeIdentifier>
    <WasmBuildNative>true</WasmBuildNative>
    <RunAOTCompilation>true</RunAOTCompilation>
    <PublishTrimmed>true</PublishTrimmed>
    <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>

Native compilation is incompatible with interpreted reflection fallback and reduces the set of third-party packages that work, because a package must not rely on runtime code generation. Enabling it should follow a measurement: profile the application under WebAssembly, find a genuine hot path, and confirm the improvement is worth the build time and the size increase.

Trade-off summary. Trimming reduces size and can break reflection. Ahead-of-time compilation increases build time and improves speed. Neither is a substitute for the other, and a project that needs dynamic code generation is a poor fit for WebAssembly in the first place.

13 · Static web assets and CSS isolation

13.1 The static web asset system13.2 Asset mapping and fingerprinting13.3 CSS isolation13.4 Reaching outside a scope13.5 The application stylesheet bundle

Explains how styles and other assets are authored in a component library, compiled into scoped stylesheets, and served with cache headers that make a deploy atomic. It covers the encapsulation model and its limits.

Blazor treats a Razor Class Library as a package that can ship its own CSS and JavaScript. The build transforms scoped stylesheets, rewrites class selectors with a scope identifier, and bundles the result into a single stylesheet the host page links.

13.1 The static web asset system

Describes the content roots, the build target that compiles them, and how a library’s assets are addressed from a consuming application. It explains why an asset in a library is not served without a reference.

Static web assets are files under wwwroot in any project that participates in the build. A library declares them as content with a _content/<PackageId>/ base path; an application serves its own from the web root directly.

// RclStyles/RclStyles.csproj
<PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <AddRazorSupportForMvc>true</AddRazorSupportForMvc>
    <StaticWebAssetBasePath>_content/RclStyles</StaticWebAssetBasePath>
</PropertyGroup>

<ItemGroup>
    <SupportedPlatform Include="browser" />
    <Content Include="wwwroot/box.js" />
</ItemGroup>

The _content/ prefix exists so that a library’s files cannot collide with the host’s. Any path a library serves, including JavaScript imported by interop, must include it. A file referenced at the correct path but served a 404 is nearly always a missing StaticWebAssetBasePath or a missing project reference.

Development versus production. In development the assets are served from the source tree; in production they are fingerprinted and copied. A path that works in development and fails after publish usually indicates a case-sensitivity mismatch, since the publish output is served on a case-sensitive host.

13.2 Asset mapping and fingerprinting

Covers the MapStaticAssets endpoint that replaces the middleware in .NET 9 and later, and the build-time generation of the endpoint map that makes fingerprinted caching correct.

Since .NET 9, MapStaticAssets reads a manifest generated at build time and serves each asset with a content hash in the URL plus an immutable cache header. A changed file produces a new URL, so clients never hold a stale copy, and a deploy becomes atomic without a cache purge.

// Program.cs
var app = builder.Build();

// .NET 9+ replacement for UseStaticFiles
app.MapStaticAssets();

app.MapRazorComponents<App>()
   .AddInteractiveServerRenderMode()
   .AddInteractiveWebAssemblyRenderMode()
   .AddAdditionalAssemblies(typeof(RclStyles._Imports).Assembly);

HTML documents are never fingerprinted, so they must be served with a short cache lifetime or with revalidation. The manifest handles this: it marks fingerprinted assets as immutable and everything else as revalidating, which removes the need to hand-maintain header configuration.

Keep the API separate. Static assets and the API endpoint have different cache semantics. Mounting the whole application behind a CDN cache without excluding the API causes an authenticated response to be served to a different user — a serious incident that is easy to cause with a single cache rule.

13.3 CSS isolation

Explains the transformation applied to a scoped stylesheet, the scope attribute added to the rendered elements, and why a plain HTML tag inside a component is not scoped.

A file named Component.razor.css is scoped. During the build, each selector is rewritten to include a generated scope identifier, and the component’s root elements receive the matching scope attribute in the rendered markup.

// RclStyles/Components/Calendar.razor.css — authored
.calendar {
    display: grid;
    gap: 4px;
}

.calendar__day--selected {
    background: var(--accent);
    color: white;
}

The build produces an equivalent file in which each selector carries the scope attribute, and a stylesheet named after the assembly, for example RclStyles.bundle.scp.css. The rewritten selector matches only elements inside that component, so the same class name in two libraries cannot collide.

Elements rendered by the component’s own markup are scoped. Elements injected by the component through a RenderFragment passed from a parent are rendered by the parent and are not scoped, so a parent’s elements inside a child component’s fragment will not match the child’s selectors. Plan the boundary accordingly.

Global selectors opt out. A rule using :global, or targeting an element the component does not render, will not match. A component that styles a third-party widget’s internals must target them through ::deep or move the style into the global bundle.

13.4 Reaching outside a scope

Documents the deep selector, what it is for, and the circumstances in which using it is correct. It also covers the cascade and specificity consequences, which are the main cost.

::deep removes the scope requirement from the part of the selector that follows it. The selector before the marker keeps its scope, so the rule still only applies within the component that authored it.

// RclStyles/Components/Picker.razor.css
.picker ::deep .third-party__input {
    border-color: var(--border);
}

.picker ::deep ul[role="listbox"] {
    max-height: 18rem;
    overflow-y: auto;
}

Use ::deep for a library’s internals and for HTML elements that a child component renders inside a slot. Do not use it to reach a sibling component or a parent element: the scope is applied to the component’s own elements, so a selector for an ancestor can never match, and the rule is dead code that is easy to misread as working.

// Correct: style markup the component itself renders
.picker__panel { ... }

// Correct: style a child component's internals
.picker ::deep .picker__row { ... }

// Never matches: the panel is the component's own element,
// so a descendant selector cannot reach its parent
.picker__panel ::deep .outer { ... }

Every ::deep rule removes one layer of specificity, which makes the cascade order harder to predict. A component that accumulates many of them is usually better expressed with CSS custom properties, where the consumer overrides a variable rather than a selector.

Prefer custom properties for theming. Declare design tokens as CSS variables on the component’s own root class. A consuming application overrides the variable in its global bundle and no deep selector is required, and the override survives component refactors.

13.5 The application stylesheet bundle

Shows how the host page imports the compiled bundle, what the generated import does, and the order in which global and scoped rules are applied.

The host must link the generated bundle exactly once. In a Blazor Web App the template places the import in the host page’s head; a library must not link its own bundle, or the rules are applied twice.

// Components/App.razor — head outlet content
<link rel="stylesheet" href="RclStyles.styles.css" />

RclStyles.styles.css is generated by the build from every scoped stylesheet in the project, in a deterministic order that follows the project’s file order. A library that references other scoped libraries emits an import for each of them, so linking one bundle is sufficient.

Global styles are a separate concern and are deliberately not scoped. Application-wide resets, typography and design tokens belong in the app’s own stylesheet, which the template links before the component bundle so that a component rule wins on equal specificity.

Link order is a contract. Because scoping does not change specificity, two rules of equal specificity are resolved by document order. Changing the order of the two link elements in the host page can change appearance without changing a single component, which is why the order is fixed in the template and should not be reordered casually.

14 · Rendering performance

14.1 What a render actually costs14.2 The @key directive14.3 Suppressing renders14.4 Virtualisation14.5 Interactive Server latency

Describes the cost model of a re-render, the three techniques that reduce it — keying, render suppression and virtualisation — and the separate cost model that applies to a server-hosted circuit.

A re-render is not free, but it is also not the bottleneck it is often assumed to be. The framework diffs the render tree and applies minimal DOM operations. The expensive cases are large collections, high-frequency state changes, and a network round trip per event.

14.1 What a render actually costs

Breaks a re-render into its constituent steps and identifies which of them are proportional to component size. It contrasts the cost of a text change with the cost of a structural change.

On every render the framework calls the component’s lifecycle methods, rebuilds the render fragment, diffs the new tree against the previous, and applies the differences to the DOM. The diff is proportional to the number of frames in the component, not to the number of frames that changed.

Changing a text value inside a component with one thousand child rows is therefore far more expensive than changing the same text in a component with three, even though the DOM operation is identical. Splitting a large static region into its own component with a stable parameter turns it into a subtree that the renderer can skip entirely.

Split on stability, not on size alone. A child component whose parameters have not changed is not re-rendered. Extracting the expensive-but-static region into a component with a single stable parameter is often the single biggest win available in a slow page.

Structural changes are the expensive DOM operations: inserting, removing or reordering elements. A keyed change preserves the existing DOM node and updates only what differs; an unkeyed change in the middle of a list destroys and recreates the affected nodes, which discards focus, selection, scroll position and any state held by third-party widgets inside them.

14.2 The @key directive

Explains how the diff algorithm matches elements between renders, why identity matters in a list, and the symptoms that indicate a missing key.

By default the renderer matches a node at a given sequence position. With @key, it matches nodes by the supplied value, which lets the framework recognise that a node has moved rather than been replaced.

// Without a key: reordering destroys and recreates every node
@foreach (var row in _rows)
{
    <tr>
        <td><input @bind="row.Name" /></td>
        <td>@row.Value</td>
    </tr>
}

// With a key: reordering moves the existing nodes
@foreach (var row in _rows)
{
    <tr @key="row.Id">
        <td><input @bind="row.Name" /></td>
        <td>@row.Value</td>
    </tr>
}

Use a stable, unique identifier: the database primary key. Do not use the array index — it is not unique across a reorder and it is not stable when the list is filtered, which produces exactly the same problem. Do not use GetHashCode, which is not guaranteed to be unique or stable across processes.

// Conditional content also benefits from a key
@if (_editingId == row.Id)
{
    <input @key="row.Id" @bind="row.Name" />
}
else
{
    <span @key="row.Id">@row.Name</span>
}

Keys must be unique among siblings. Two siblings with the same key produce undefined diff behaviour and, in practice, elements that vanish or appear in the wrong place. A key must be unique within its immediate sibling group, not across the whole page.

14.3 Suppressing renders

Shows the two render-suppression mechanisms, when each applies, and the correctness rules that must be observed when returning false.

Two mechanisms suppress a render. ShouldRender is a virtual method consulted after the lifecycle methods have run. StateHasChanged with no arguments bypasses the check and forces a render; calling it with no argument is therefore the documented escape hatch when a component must update regardless.

@code {
    [Parameter] public IEnumerable<Row> Rows { get; set; } = [];

    private IReadOnlyList<Row>? _snapshot;

    protected override bool ShouldRender()
        => !Rows.SequenceEqual(_snapshot ?? []);

    protected override void OnAfterRender(bool firstRender)
    {
        _snapshot = Rows.ToArray();
    }
}

Three rules govern a correct implementation. Return true on the first render, because the framework does not call ShouldRender for it. Compare against state captured during the previous render, not against the incoming parameters, since the lifecycle methods have already applied them. Do not capture the snapshot in OnParametersSet, which runs before the decision and would always make the answer "changed".

A second mechanism is the automatic suppression that already applies to a child component whose parameters have not changed. No action is required; the framework compares the parameter set and skips the child. This is the reason to pass a stable primitive rather than a freshly constructed object as a parameter.

Do not suppress blindly. A component that returns false from ShouldRender without rendering anything conditional will be permanently blank, and the failure is silent. Always confirm the component’s markup appears on first render.

14.4 Virtualisation

Explains windowed rendering, the parameters that control the window, and the component constraints that virtualisation imposes. It also covers when an alternative such as paging is the better answer.

Virtualize renders only the items near the viewport and reuses spacer elements to preserve scroll height. The item count may be far larger than the number of rendered elements.

// Components/Logs/LogViewer.razor — Render mode: InteractiveServer
<Virtualize Items="_entries" Context="entry" ItemSize="28" OverscanCount="4">
    <div class="log-row @entry.Level.ToString().ToLowerInvariant()">
        <time>@entry.At.ToString("HH:mm:ss")</time>
        <span>@entry.Message</span>
    </div>
    <Placeholder>
        <div class="log-row log-row--placeholder">Loading…</div>
    </Placeholder>
</Virtualize>

ItemSize must be an accurate height in pixels; the framework uses it to compute offsets, and a wrong value causes a scroll position drift on the second page. OverscanCount renders a few extra items above and below the viewport to hide latency. SpacerElement changes the tag used for the spacers, which matters when the list is not a table.

Fixed height is a requirement. A virtualised row whose height changes with its content breaks the offset calculation. Either fix the height in CSS or use a table with a known row height; a variable-height virtualised list requires a different component entirely.

Virtualisation is not always the right answer. A list of fifty items does not benefit from the added complexity, and a list that changes on every keystroke is better served by debouncing the query. For a grid with sorting and paging, QuickGrid combines virtualisation with a server-side items provider, which is usually the correct component for tabular data.

Binding a text input with the default oninput event sends one message per keystroke. Binding with @bind:event="onchange" sends one per commit, which for a filter field is almost always the correct choice. A manual debounce in @bind:after is the middle ground when a live count is needed while the query itself must be throttled.

// Commit on blur or Enter rather than on every keystroke
<input @bind="_term" @bind:event="onchange" placeholder="Search orders" />

// Or keep oninput and debounce the expensive work yourself
<input @bind="_term" @bind:event="oninput" @bind:after="ScheduleSearch" />

@code {
    [Inject] private CancellationTokenSource? _debounce { get; set; }

    private void ScheduleSearch()
    {
        _debounce?.Cancel();
        _debounce?.Dispose();
        _debounce = new CancellationTokenSource();
        var token = _debounce.Token;
        _ = SearchAsync(token);
    }

    private async Task SearchAsync(CancellationToken ct)
    {
        try { await Task.Delay(400, ct); }
        catch (TaskCanceledException) { return; }

        Results = await Queries.SearchAsync(_term, ct);
        StateHasChanged();
    }
}

Measure before optimising. The browser’s performance profiler shows how long a re-render takes; the SignalR frame size in dev tools shows what a round trip costs. Optimising the wrong one produces a faster component that is still slow to use.

15 · Accessibility

15.1 Semantic output and attribute splatting15.2 Labels, errors and focus15.3 Keyboard interaction15.4 Live regions and dynamic content15.5 Render-mode and accessibility traps

Covers the accessibility obligations specific to a component framework: the semantics a component must emit, the focus management the render model does not provide for free, and the two render-mode traps that produce inaccessible output.

Blazor emits exactly the markup it is given. A <div> with a click handler is a div with a click handler — it has no role, no keyboard behaviour and no announcement. Accessibility is therefore a property of the component, not of the framework.

15.1 Semantic output and attribute splatting

Explains how to choose the correct element for a component, and how to forward arbitrary attributes from a caller onto the rendered root so that identifiers, event handlers and test hooks pass through.

Start from the native element and add behaviour, rather than starting from a div. Additional attributes on a component tag are captured and applied to the root element; the framework exposes them through the CaptureUnmatchedValues parameter.

// Components/Controls/Disclosure.razor
<section class="disclosure" @attributes="_attributes">
    <h3 class="disclosure__summary">
        <button type="button"
                id="@Id"
                class="disclosure__toggle"
                aria-expanded="@_isOpen.ToString().ToLowerInvariant()"
                aria-controls="@Id-panel"
                @onclick="Toggle">
            @Title
        </button>
    </h3>

    @if (_isOpen)
    {
        <div id="@Id-panel" class="disclosure__panel" role="region" aria-labelledby="@Id">
            @ChildContent
        </div>
    }
</section>

@code {
    [Parameter] public string Title { get; set; } = "";
    [Parameter] public RenderFragment? ChildContent { get; set; }
    [Parameter(CaptureUnmatchedValues = true)]
    public Dictionary<string, object?>? _attributes { get; set; }

    private bool _isOpen = true;
    private string Id { get; } = "d" + Guid.NewGuid().ToString("N")[..6];

    private void Toggle() => _isOpen = !_isOpen;
}

Attribute splatting must be placed on the element that should receive the extra attributes, and it must be placed last so that the component’s own attributes take precedence. A caller writing class="override" then gets the component’s class, not a merge — which is usually the desired behaviour and is worth documenting on the component.

Splatt onto the right element. A component with a wrapper div that splats attributes onto an inner input produces an element whose accessible name comes from the wrapper, not the control. Put the splat on the element the caller expects to target and document that the component’s root must be a single element.

15.2 Labels, errors and focus

Covers the three requirements for an accessible form control — a programmatic label, a described error, and focus management on validation failure — and shows a field component that satisfies all three.

Every control needs a label associated by the for attribute, an id that matches, and an error message referenced by aria-describedby together with aria-invalid.

// Components/Controls/TextField.razor
<div class="field">
    <label for="@Id">@Label</label>
    <input id="@Id"
           class="field__control @_cssClass"
           value="@Value"
           @attributes="_attributes"
           aria-invalid="@(_error is not null ? "true" : "false")"
           aria-describedby="@(_error is not null ? $"{Id}-error" : null)"
           @oninput="OnInput"
           @onblur="OnBlur" />
    @if (_error is not null)
    {
        <span id="@($"{Id}-error")" class="field__error" role="alert">@_error</span>
    }
</div>

role="alert" is an implicit live region, so a validation message that appears on blur is announced without additional markup. Avoid it for messages that can appear on every keystroke, which would flood the screen reader.

Focus is not moved by the framework when validation fails. A submit handler must move focus to the first invalid control, or to the error summary, so that a screen-reader or keyboard user is not left on a control that did not work.

// Components/Forms/EditorForm.razor — Render mode: InteractiveServer
<EditForm EditContext="_context" OnValidSubmit="SaveAsync" FormName="editor">
    <FocusOnNavigate RouteData="routeData" Selector="h1" />
    ...
</EditForm>

@code {
    private async Task SaveAsync()
    {
        await JS.InvokeVoidAsync(
            "focusFirstInvalid", ".field__control[aria-invalid='true']");
    }
}

Errors are not announced by a failed submit alone. A validation summary rendered at the top of the form needs tabindex="-1" and an explicit focus call, because a screen reader will not move the reading position to a newly inserted element by itself.

15.3 Keyboard interaction

Covers the native elements that provide keyboard behaviour for free, the events to bind for custom controls, and the requirement to prevent only the default action that would interfere.

The most reliable accessible control is a native one. A button, a link, a checkbox and a select all provide focus, activation, roles and states without any additional code.

Native elementKey handlingUse for
<button>Space and EnterAny action
<a href>EnterNavigation
<input type="checkbox">SpaceToggle
<input type="radio">Space, arrowsSingle choice

Where a custom control is unavoidable, bind the keyboard events explicitly and suppress only the ones that would double-fire. tabindex="0" makes a non-interactive element focusable; a positive value reorders the tab sequence and should almost never be used.

<div class="grid-cell"
     role="gridcell"
     tabindex="0"
     aria-selected="@IsSelected"
     @onclick="Select"
     @onkeydown="OnKeyDown">
    @Value
</div>

@code {
    private async Task OnKeyDown(KeyboardEventArgs e)
    {
        switch (e.Key)
        {
            case "Enter":
            case " ":

                break;
        }
    }
}

A <div> with @onclick and no role, tabindex or key handler is invisible to a keyboard user and to a screen reader. This is the single most common accessibility defect in hand-written Blazor components.

Focus must be visible. Suppressing the focus outline in a custom control is a deliberate removal of the only indicator a keyboard user has. If a design system replaces the outline, it must provide an alternative that meets the contrast requirement.

15.4 Live regions and dynamic content

Explains how to announce content that changes without a navigation, the difference between polite and assertive, and why a live region must exist before the message is inserted.

Content that changes in place is not announced. A live region must be present in the DOM before the text is inserted, and it must be marked as either polite, which queues the announcement, or assertive, which interrupts.

<div class="status" role="status" aria-live="polite">
    @_message
</div>

@code {
    private async Task SaveAsync()
    {
        await Orders.SaveAsync(_order);
        _message = "Order saved.";
    }
}

Use role="status" for the result of a user action and role="alert" for an error that must interrupt. A validation summary that appears on every keystroke belongs in neither; it should be associated with its control instead.

Insertion order matters. A live region that is created at the same moment as its content is frequently missed, because assistive technology observes the region after the insertion. Render the container unconditionally and change only its text.

15.5 Render-mode and accessibility traps

Identifies the two situations in which the render model itself produces an inaccessible page — prerendered content that is never interactive, and a reconnection that discards focus — and gives the correct handling for each.

The first trap is a component marked interactive but with prerendering disabled. Its markup is not in the initial response, so the page is empty until the download completes. An empty container is a blank page to a screen reader and a failure to a crawler.

The second is reconnection. When an Interactive Server circuit re-establishes, the DOM is preserved but focus and the reading position are not guaranteed to be. Announce the reconnection politely, and never place focus automatically in a way that interrupts a user who is mid-task.

// wwwroot/reconnect.js — announce, do not steal focus
export function init(dotNetRef) {
  const original = DotNetBlazorError;
  DotNetBlazorError = (e) => {
    original?.(e);
    dotNetRef.invokeMethodAsync('OnReconnecting');
  };
}

Route changes are the third case. After an interactive navigation the new page is rendered into the same document, and focus remains on the element that was activated. FocusOnNavigate addresses this for the router; any custom navigation path that replaces content must do the same.

Test the keyboard path first. A component that cannot be completed with a keyboard alone has an accessibility defect regardless of how its markup validates. Unplug the mouse and complete the primary task before running an automated audit.

Covers the two complementary test tools for Blazor — bUnit for component-level tests without a browser, and Playwright for end-to-end tests through a real browser — and shows the correct arrangement of both with the test pyramid.

Because a component is an ordinary class, most component logic is testable without rendering it. bUnit exists for the code that is not: markup, event dispatch, cascading values and parameter binding.

16.1 The test layers

Places Blazor testing within the standard test pyramid and states what each layer should cover. It argues against writing end-to-end tests for logic that can be covered at a lower level.

16.2 bUnit: rendering a component

Introduces the test context, how a component is rendered, and how the resulting fragment is queried. It shows the difference between a rendered instance and its markup.

A bUnit test derives from TestContext, renders a component with RenderComponent and receives an IRenderedComponent<T> that exposes both the component instance and the rendered markup.

// Tests/Components/OrderRowTests.cs

16.3 bUnit: interaction and assertions

Shows event dispatch, the argument builders, and the asynchronous assertion helpers that handle the render queue. It also covers the failure mode of asserting before a re-render has been processed.

Events are dispatched with the Click, Change, Input and KeyDown helpers. Each returns immediately; the component’s re-render is queued. Assert after awaiting the queue, not synchronously after the click.

[Fact]
public async Task SelectRaisesCallbackWithTheOrder()
{
    var order = new Order { Id = 7, Number = "A-1001" };
    Order? selected = null;

    var cut = RenderComponent<OrderRow>(parameters => parameters
        .Add(p => p.Order, order)
        .Add(p => p.OnSelect, o => { selected = o; return Task.CompletedTask; }));

    cut.Find("button").Click();

    cut.WaitForAssertion(() => Assert.Equal(7, selected!.Id));
}

WaitForAssertion polls until the assertion passes or a timeout elapses, which is the correct way to assert on output that depends on a re-render. WaitForState is the equivalent for waiting on a component property before asserting on the DOM.

[Fact]

Covers service registration in a test context, the substitute-doubles package, and the JS interop mode that replaces the browser with a recording double. It also shows cascading value setup.

Services registered on the test context’s service collection are resolved exactly as they are in the application. Substitute doubles, or hand-written stubs, replace the real implementation.

// Tests/Components/OrderDetailTests.cs

16.5 End-to-end tests with Playwright

Shows the Playwright setup for a Blazor application, the locators that work reliably with generated identifiers, and the scenarios that belong only in this layer.

Playwright drives a real browser against the running application. For Blazor, prefer role and label locators over CSS selectors, because the generated identifiers and the scope attributes are implementation details that change between builds.

// Tests/EndToEnd/CheckoutTests.cs
// dotnet add package Microsoft.Playwright

public class CheckoutTests : PageTest

Four scenario classes belong exclusively here: routing and navigation, sign-in and session behaviour, the render mode actually applied on a given page, and the post-back of a static SSR form. None of these can be reproduced in a component test, because none of them exist in one.

17 · Security

17.1 Cross-site scripting17.2 Encoding and MarkupString17.3 Antiforgery and request forgery17.4 Parameter tampering and over-posting17.5 WebAssembly secrets and exposure

Covers the security boundaries specific to Blazor: how encoding differs from the browser’s normal model, where an explicit unencoded output path exists, how request forgery applies to server-rendered forms, and what is unavoidably public in a browser-hosted application.

Blazor renders a component tree, not a string. Markup is produced as render frames and applied as DOM operations, which removes the concatenation step where most injection bugs live. That protection has deliberate escape hatches, and the rest of this chapter is about where they are and how to use them safely.

17.1 Cross-site scripting

Explains the default encoding behaviour, why it differs from server-side templating, and the three cases where the default is bypassed.

Every value rendered through the @ directive is HTML-encoded by the renderer before it reaches the DOM. A string containing a script element is written as text, not parsed as markup, regardless of what the string contains.

// Encoded by default: displayed as literal text
<span title="@user.Name">@user.Name</span>
<input value="@user.Name" />

// Encoded for the attribute context, not the HTML context
<a href="/profile/@user.Slug">@user.DisplayName</a>

The renderer chooses the encoding from the context: element content, an attribute value, a URL, or a script. That is why a value containing a quote cannot break out of an attribute. Three constructs bypass it, and each is a decision that must be deliberate.

  • MarkupString declares a value to be raw HTML.
  • HtmlEncoder used directly with a string and interpolated markup.
  • JavaScript interop writing to innerHTML on the client.

Never render user data raw. If a value must be interpreted as markup, sanitise it with a proven sanitiser and render the sanitised result, never the original. A sanitiser is a dependency with a security record; a regular expression is not one.

A second class of injection is the URL context. @ does not prevent javascript: in an href. A link whose target comes from user input must be validated against an allow-list of schemes and origins before it is rendered.

@code {
    private static readonly HashSet<string> Allowed = ["https://example.com/", "https://docs.example.com/"];

    public static string? SafeUrl(string? candidate)
    {
        if (string.IsNullOrWhiteSpace(candidate)) return null;
        if (!Uri.TryCreate(candidate, UriKind.Absolute, out var uri)) return null;
        return uri.Scheme == Uri.UriSchemeHttps && Allowed.Contains(uri.GetLeftPart(UriPartial.Authority) + "/")
            ? uri.ToString()
            : null;
    }
}

17.2 Encoding and MarkupString

Shows the correct use of HtmlEncoder for pre-encoded fragments, explains why double-encoding is a bug, and gives the sanitise-then-render pattern.

HtmlEncoder.Default.Encode is the correct way to build a fragment in code rather than in markup, and the result is passed to (MarkupString). The cast is the assertion that the string is already safe; the encoding call is what makes it true.

@code {
    // Correct: build in code, encode, then declare it as markup
    private readonly HtmlEncoder _encoder = HtmlEncoder.Default;

    private MarkupString BuildLink(string label, string url) =>
        new((MarkupString)$"<a href=\"{_encoder.Encode(url)}\">{_encoder.Encode(label)}</a>");
}

Never cast a raw string. (MarkupString)userInput is exactly equivalent to assigning untrusted input to innerHTML. The cast carries no safety; it removes the compiler’s protection and asserts something the compiler cannot verify.

Double encoding produces visible defects rather than vulnerabilities: an ampersand in a search term becomes &amp; and is displayed literally. If a value arrives already encoded from an upstream system, decode it once at the boundary and then encode it once at output, and never both.

17.3 Antiforgery and request forgery

Explains why request forgery applies to a Blazor application that uses cookies, which forms are protected automatically, and the conditions under which a circuit itself mitigates the risk.

An Interactive Server circuit is protected because a cross-origin page cannot open one: the SignalR connection is negotiated with an origin check and requires a token. The exposure is therefore static server-side rendering, where a <form method="post"> is a normal form submission that any page on any origin can cause a browser to send.

// A hand-written form in a Blazor Web App must carry the token
<form method="post" action="/account/change-email">
    <AntiforgeryToken />
    <label for="email">Email</label>
    <input id="email" name="email" type="email" />
    <button type="submit">Update</button>
</form>

// A minimal API endpoint consuming the same form
app.MapPost("/account/change-email", async (ChangeEmail model) =>
{
    var result = await manager.ChangeEmailAsync(await user.GetIdAsync(), model.Email);
    return result.Succeeded ? Results.Ok() : Results.BadRequest();
}).RequireAntiforgeryToken();

EditForm emits and validates the token automatically when the page is server-rendered, and the FormName introduced in .NET 9 strengthens this by binding the post to a specific named form on the page. A hand-written form needs AntiforgeryToken in the markup and RequireAntiforgeryToken on the endpoint.

Cookie configuration completes the protection. SameSite=Strict or Lax prevents the cookie from being attached to a cross-site submission entirely, and HttpOnly prevents script from reading it. All three should be set; antiforgery alone does not cover a browser that omits the cookie.

State-changing endpoints need the token too. A logout link, a delete confirmation and any minimal API endpoint reachable from a page must be protected. The FormName on an EditForm does not cover a separate endpoint the form posts to by hand.

17.4 Parameter tampering and over-posting

Covers the two ways a client can mislead a server-rendered application, the correct defence for each, and the reason client-side validation is never an authorisation control.

Tampering is a modified route or query value; over-posting is an extra property bound from the submitted form that the user was never offered. Both reach the server under static SSR as ordinary form data.

// Model for the view only: never bind a submit to this
public sealed class OrderViewModel
{
    public string Number { get; set; } = "";
    public decimal Total { get; set; }   // displayed, never accepted
    public string? CustomerId { get; set; }  // never bound
}

// Command for the submit: only these fields are accepted
public sealed class CreateOrderCommand
{
    [Required, StringLength(24)]
    public string Number { get; set; } = "";
    [Range(1, 500)]
    public int Seats { get; set; } = 1;
}

Bind to a command type that contains only the fields the form offers, and derive everything else server-side. The total, the customer, the price and the status must come from the database, never from the request.

Where a model must serve both purposes, restrict the binder explicitly with [BindNever] on the display-only properties. The default model binder assigns any property it finds in the form collection, including one that was never rendered.

// Route values are user input too
@page "/orders/{Id:int}"

@code {
    [Parameter] public int Id { get; set }

    protected override async Task OnParametersSetAsync()
    {
        var user = await Auth.GetUserAsync();
        _order = await Orders.GetForUserAsync(Id, user.Id);   // ownership in the query
        if (_order is null) Nav.NavigateTo("/not-found");
    }
}

Filter by owner in the query. Fetching an entity and then checking ownership in C# returns a correct result but a leaking one: a wrong identifier produces a distinguishable response. Filtering inside the query returns not-found in both cases, which is the behaviour an attacker cannot probe.

17.5 WebAssembly secrets and exposure

States precisely what is public in a browser-hosted application and lists the categories of value that must never be present in a WebAssembly payload. It covers the mitigations that are actually available.

Everything published to the browser is readable. That includes the managed assemblies, the boot manifest, every configuration file, every environment value and every string literal in the payload. Obfuscation or a packer raises the cost of reading; it does not make a value secret.

  • Database connection strings, API keys, client secrets, signing certificates, private tokens.
  • Licence keys intended to be non-discoverable.
  • Authorisation rules that differ from the server’s, in case the client is bypassed.
  • Personal data embedded for convenience, such as a lookup table keyed by customer name.
// Program.cs — WebAssembly client: configuration is public
builder.Configuration.AddEnvironmentVariables("ASPNETCORE_ENVIRONMENT");
builder.Configuration.AddJsonFile("appsettings.json", optional: true);

// The only correct use of a client configuration value
builder.Services.AddHttpClient<ApiClient>(c =>
{
    c.BaseAddress = new Uri(builder.Configuration["Api:BaseUrl"]);
    c.DefaultRequestHeaders.Add("X-Client-Version", this.GetType().Assembly.GetName().Version!.ToString());
});

A published WebAssembly application is normally unauthenticated at the API boundary, because there is no cookie to protect and the token is obtained through the browser’s own OAuth flow. Every endpoint the client can reach must therefore be publicly reachable and must perform its own authorisation.

Client-side gating is not a control. A page hidden behind [Authorize] in a WebAssembly component is hidden only from a user who has not opened dev tools. The API must verify the token, derive the caller’s identity from it, and filter every result — the client never supplies the identity.

Where a browser-hosted client must not be able to perform an operation at all, the operation does not exist in the browser. The capability is exposed by a server endpoint with its own authorisation, and the absence of the code from the payload is the control.

Covers what each hosting target requires, the caching model that makes a deploy atomic, and the operational requirements that apply only to a circuit-hosting server. It includes the configuration that must never ship to the client.

The deployment shape follows the render mode. A purely static output is a directory of files; an Interactive Server application is a long-running process that holds stateful connections.

18.1 What gets deployed per render mode

Maps each render mode to its deployable artefact and the host that can serve it. It names the one artefact that constrains the choice of host.

Render modeArtefactHost
Static SSRPublished .NET applicationAny process host
Interactive ServerPublished .NET applicationProcess host with WebSocket support
WebAssemblyStatic filesCDN, object storage or static host
AutoBoth of the aboveServer also serves the client assets

A WebAssembly client is a directory of static files with no server-side requirement beyond correct content types and range-request support. The server component, where present, is an ordinary ASP.NET Core application. This separation is what allows the client to be placed on a CDN and the API to remain on an application host.

// Publish
dotnet publish -c Release -r linux-x64 --self-contained false -o ./publish

Publishing framework-dependent requires a matching runtime on the host. A self-contained publish is larger but removes that dependency, which matters for a container image that must run on an arbitrary base. Both are supported; the decision is an operational one.

18.2 Static hosting for a WebAssembly client

Covers hosting a WebAssembly client on object storage, the header and routing requirements specific to Blazor, and the rewrite rule that a single-page application needs.

A Blazor Web App is a single-page application with a server-rendered root document. Every unknown path must be rewritten to index.html, while paths that name a file must not be, so that a missing asset returns a 404 rather than an HTML document with a 200 status.

// netlify.toml
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

Blazor’s own content negotiation must be preserved for the framework files. Two headers are critical: blazor.boot.json and the blazor.webassembly.* and dotnet.* binaries must be served with the correct MIME types, or the runtime fails to start with a message that names the file rather than the cause.

Compression is not optional for a WebAssembly payload. Brotli typically reduces the managed assemblies by roughly a third, and gzip is the fallback every browser accepts. A host that serves the payload uncompressed turns a two-megabyte download into a substantially larger one.

Range requests. Some hosts strip or ignore Accept-Ranges. The WebAssembly runtime streams its largest module in chunks, and a host that refuses range requests can cause a slow start or a truncated payload on some networks. Verify the behaviour against the target host rather than assuming it.

18.3 Self-hosting a server

Describes the runtime requirements of an Interactive Server deployment, the process and socket configuration that must be explicit, and the graceful shutdown behaviour that affects circuits.

The server must allow long-lived WebSocket connections, and the reverse proxy in front of it must be configured to permit them. A proxy timeout shorter than the circuit lifetime closes the connection and forces a reconnect on every idle period.

// nginx
location / {
    proxy_pass         http://127.0.0.1:5000;
    proxy_http_version 1.1;
    proxy_set_header   Upgrade $http_upgrade;
    proxy_set_header   Connection "upgrade";
    proxy_set_header   Host $host;
    proxy_cache_bypass $http_upgrade;
    proxy_read_timeout 3600s;
}

Interactive Server is stateful, so a rolling deployment must account for circuits. Options are a fixed session affinity, a drain period in which the old instance stops accepting new connections while existing circuits finish, or a short-lived connection limit so that circuits are re-established frequently and state loss is bounded.

A circuit cannot be moved. When a connection lands on a different instance after a deploy, the component state held on the previous instance is gone and the user sees an error unless the application handles reconnection. For an application that persists work in progress, plan the drain before assuming the deployment is transparent.

Applications that need scale-out use a backplane — Azure SignalR, or a Redis-backed option — so that a reconnect can be routed to any instance. A backplane adds a hop to every interaction; its latency is added to the total, which is why a single region is preferred when it is sufficient.

18.4 CDN, compression and cache headers

Explains the fingerprinted-asset model, the resulting header policy, and the route exclusions required when a CDN fronts an application that serves both assets and personalised content.

Since .NET 9, the build generates an endpoint map that assigns each fingerprinted asset a content-hashed URL. MapStaticAssets applies the correct headers from that map, so a changed asset is requested under a new name and cached copies are never reused.

// Desired header policy
/css/app.4F2A1B.css      Cache-Control: public, max-age=31536000, immutable
/_framework/dotnet.wasm  Cache-Control: public, max-age=31536000, immutable
/index.html              Cache-Control: no-cache, must-revalidate
/api/orders               Cache-Control: no-store

The HTML document must not be cached indefinitely, because it references the fingerprinted URLs. A stale document points at assets that may have been removed from the deployment, which produces a hard failure rather than a slow page.

Where a CDN fronts the application, cache the asset paths and exclude everything else. The exclusions that matter are the API routes, the SignalR negotiate and upgrade paths, and any path that returns a response derived from the authenticated user.

Exclude the upgrade path. Caching the SignalR negotiate response is the most common CDN misconfiguration for Blazor. It hands the same connection token to several clients, and the symptom is a connection that appears to succeed and then fails on the first event.

18.5 Configuration, health and scaling

Covers the configuration sources, the environment-specific settings that must not be shared, the health endpoints to expose, and the metrics that indicate a capacity problem in a circuit-based application.

Configuration follows the standard ASP.NET Core order, with environment variables last so that a container or a platform secret store overrides the file. No secret is written to a WebAssembly project’s configuration, because that file is published to the browser.

// Program.cs
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>("database");

var app = builder.Build();

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

// Only in Development: never leak exception detail to a client
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();
    app.UseMigrationsEndPoint();
}
else
{
    app.UseExceptionHandler("/Error", createScopeForErrors: true);
    app.UseHsts();
}

Detail about the exception is the primary leak in a misconfigured deployment. DetailedErrors in the circuit options, and the developer exception page, are both development settings; leaving either enabled in production returns stack traces, file paths and connection information to the browser.

The metrics that matter for an Interactive Server deployment are the number of active circuits, the distribution of circuit lifetime, the number of reconnections, and the length of the interaction queue. A rising circuit count with a flat request rate indicates circuits that are not being released, which usually points to a client that never disconnects cleanly.

19 · Migration and hybrid patterns

19.1 Migrating a page between render modes19.2 Hybrid pages: static shell, interactive island19.3 Moving a page to WebAssembly19.4 Session and state across a render-mode change19.5 Migration checklist

Covers the practical work of moving a page between render modes without rewriting it, the hybrid composition that most applications converge on, and the constraints a change of mode places on data access and security.

Because a component is a plain class, changing its render mode is a directive change in the common case. The parts that do not migrate automatically are data access, JavaScript interop placement, and any assumption the page makes about server-side execution.

19.1 Migrating a page between render modes

Enumerates the code that must change when a page moves from static SSR to Interactive Server, and the smaller set that must change when it moves to WebAssembly. It separates mechanical changes from architectural ones.

Moving from static SSR to Interactive Server requires adding the render mode and moving any side effect out of the initialisation path. Moving to WebAssembly requires that, plus replacing every server-side data path with an HTTP call.

// Before: static SSR, data loaded on the request
@page "/reports"
@inject IReportService Reports

@code {
    private Report? _report;

    protected override async Task OnInitializedAsync()
        => _report = await Reports.BuildAsync(UserId);
}

// After: Interactive Server, same logic, one directive added
@page "/reports"
@rendermode InteractiveServer
@inject IReportService Reports

@code {
    private Report? _report;

    protected override async Task OnInitializedAsync()
        => _report = await Reports.BuildAsync(UserId);

    private async Task RefreshAsync()
    {
        _report = await Reports.BuildAsync(UserId);
    }
}

What must move when a page becomes interactive: work with a side effect belongs in OnAfterRenderAsync or behind a user action, not in OnInitializedAsync, because it now runs on every circuit start. Browser-dependent code must not run during prerender. A scoped service that was previously created per request is now created per circuit and must be safe to hold for hours.

What must not be trusted after the change: the assumption that a service field can retain state between page loads. Under static SSR each request is a new instance; under an interactive mode the field persists, which usually appears as a page that shows a previous user’s data after signing out and in again on the same circuit.

19.2 Hybrid pages: static shell, interactive island

Describes the composition that most applications adopt, with a server-rendered document and interactive components placed individually. It shows the trade-off between a global and a per-page render mode declaration.

The recommended architecture is a globally static shell with interactivity declared on the components that need it. The shell, the navigation and the content are server-rendered on every request; only the interactive islands establish a circuit.

// Components/App.razor — the shell is static
<Routes />

@code {
    // No render mode on <Routes />: the default is static SSR
}

// Components/Pages/Reports.razor — one interactive island
@page "/reports"

<h1>Quarterly revenue</h1>
<p>Rendered on the server for the first paint, cached by crawlers, indexable.</p>

<RevenueChart Data="_series" @rendermode InteractiveAuto />

<ReportFilters @rendermode InteractiveServer />
DecisionGlobal on <Routes>Per component
First paintPrerendered where applicableAlways server-rendered
Circuit countOne per pageOne per interactive island
MaintenanceSingle switchPer-component decision
ScalabilityEvery visitor holds a circuitOnly interactive visitors do

Per-component declaration costs a little more attention and scales considerably better, because a visitor reading a static page holds no connection at all. For a site with a large share of read traffic, that difference determines the hosting cost.

Give interactivity a reason. A component that becomes interactive only to show data the server could have rendered has paid a circuit, a thread-pool continuation and a WebSocket for nothing. Interactivity should be justified by an interaction the user performs.

19.3 Moving a page to WebAssembly

Covers the four categories of change required to move a component from server execution to the browser, and how to structure them so the change is mechanical rather than a rewrite.

Data access, authentication, secret-dependent configuration and interop are the four things that cannot cross to the browser. Structure the component so each of them sits behind an injected abstraction, and the move becomes a registration change.

// Shared library: the contract both render modes satisfy
public interface IOrderSource
{
    Task<IReadOnlyList<OrderSummary>> SearchAsync(string? term, CancellationToken ct);
}

// Server project: the database implementation
public sealed class EfOrderSource(IDbContextFactory<AppDbContext> f) : IOrderSource
{
    public async Task<IReadOnlyList<OrderSummary>> SearchAsync(string? term, CancellationToken ct)
    {
        await using var db = await f.CreateDbContextAsync(ct);
        return await db.Orders.AsNoTracking()
            .Where(o => term == null || o.Number.Contains(term))
            .Select(o => new OrderSummary(o.Id, o.Number, o.Total))
            .ToListAsync(ct);
    }
}

// Client project: the API implementation
public sealed class ApiOrderSource(HttpClient http) : IOrderSource
{
    public async Task<IReadOnlyList<OrderSummary>> SearchAsync(string? term, CancellationToken ct)
        => await http.GetFromJsonAsync<OrderSummary[]>(
               QueryHelpers.AddQueryString("api/orders", "q", term), ct) ?? [];
}

The component that consumes IOrderSource is unchanged when the registration changes from EfOrderSource to ApiOrderSource. This is the only arrangement in which a render-mode change is a low-risk change, and it is worth establishing before the first mode change rather than during it.

Move the authorisation, not copy it. A component moving to the browser cannot reach the server-side UserManager, and an [Authorize] attribute in the browser gates only rendering. The authorisation decision must already exist in the API before the component moves, or the move silently removes the control.

19.4 Session and state across a render-mode change

Covers the three places a render-mode change breaks existing state assumptions — circuit-scoped fields, antiforgery tokens and cached per-request data — and the correct replacement for each.

Three categories of state break when the model changes. Circuit-scoped state is lost on a reconnect. Per-request cached data must become explicitly invalidated. Client-side storage is unavailable to a server-rendered page that has not shipped the value to the browser.

// Fragile: a scoped service holding per-user work in progress
@implements IDisposable
@inject DraftStore Drafts

@code {
    protected override void OnInitialized() => _draft = Drafts.CurrentFor(User);

    public void Dispose() => Drafts.Release(_draft);
}

// Robust: the draft is addressed, not owned, and re-read when needed
@code {
    [Parameter] public int DraftId { get; set; }

    protected override async Task OnParametersSetAsync()
    {
        _draft = await Drafts.LoadAsync(DraftId, CancellationToken.None);
    }
}

Addressed state survives every transition: a reconnection, a new circuit, a page load on a different instance and a render-mode change. Holding state in a scoped field survives none of them, and the failure is intermittent, which makes it expensive to diagnose.

For a component that must survive both a static page load and an interactive transition, the query string is the most durable carrier of state. It survives a refresh, a share and a navigation from another page, which is why the pattern in chapter 6 pairs with this one.

Antiforgery across a mode change. A token issued during a static SSR response is bound to that response. A component that switches to interactive mode mid-session must obtain a fresh token for its first post-back rather than reusing one captured at initialisation, or the request is rejected as a forgery.

19.5 Migration checklist

Summarises the work of a render-mode change as an ordered procedure, so that each step can be verified independently. It names the checks that are commonly skipped and the regression they cause.

Moving a page between render modes, in order:

  • Identify server-only dependencies. Every injected service that reaches a database, a file system or a secret must be behind an interface with a browser-reachable implementation, or the page stays on the server.
  • Relocate side effects. Anything with an external effect moves out of OnInitializedAsync to an explicit user action or to OnAfterRenderAsync with firstRender guarded.
  • Guard interop. Confirm no interop call is reachable during prerender; if the page is Auto, this is the change most likely to fail in testing.
  • Re-verify authorisation. The enforcement point moves to the API. Confirm the endpoint authorises by identity derived from the token, not by an identifier the client supplies.
  • Re-verify validation. Server-side validation is now the only validation. Confirm the command type, not the view model, is the bound type.
  • Check lifetime assumptions. A circuit is hours long, not milliseconds. Any scoped service holding a resource must be safe for that duration and disposable.
  • Run the end-to-end suite. Routing, sign-in and form post-backs are the behaviours a component test cannot observe, and they are exactly what a mode change breaks.

Change one page at a time. A render mode is declared per component, so a migration can proceed incrementally with the application running throughout. Migrating the whole application in one change maximises the blast radius and makes a regression impossible to localise.
