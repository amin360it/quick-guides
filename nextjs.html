Welcome — How to Use This Next.js Guide

Next.js is a React framework, and almost every confusion with it comes from not knowing which of your code runs on the server and which runs in the browser. This guide is organised around making that boundary explicit, because once you can state where a piece of code runs, every Next.js decision becomes obvious.

What this guide assumes

You know React — the component model, hooks, effects and state from a React guide at this level. You do not need Node.js server experience; where it matters, it is explained.

Pin the versions down

Next.js 15 is written against a specific React release. It expects React 19 and the App Router's component rules: async Server Components, the 'use client' boundary, and action props instead of callback props. A library written for React 18 — a drag-and-drop kit, a virtualised list — can still work, but pairing it with a server component that passes functions across the boundary is where the confusing errors start.

Let create-next-app pick the versions. The one thing worth choosing yourself is TypeScript: the framework has first-class types, typed Link hrefs via experimental.typedRoutes, and generated route types that catch a mistyped URL at build time instead of in production.

    "react": "19.0.0",
    "react-dom": "19.0.0"
  },
  "devDependencies": {
    "typescript": "^5.7.0",
    "@types/node": "^22",
    "@types/react": "^19",
    "@types/react-dom": "^19"
  }
}

Node 20 or newer, no excuses

Every Next.js command — next dev, next build, next start — runs on Node.js, and Next.js 15 raises the floor to 20.9.0. Node 18 installs refuse to start with a clear engine error rather than misbehaving halfway through a build, but failing fast is still better: pin the version in engines and an .nvmrc so your machine, CI and deployment all agree.

You can develop with just Node and a text editor; a Docker image or a platform like Vercel is a deployment detail, not a requirement. The exercises in this guide run on next dev alone.

  • A hosted platform is optional. Everything here works with next dev and next build locally, and deploys to Vercel, Netlify, a container, or a VM.

Versions used here: Next.js 15 with the App Router, React 19, and Turbopack as the default dev bundler. The App Router replaced the Pages Router in 13.4 and is the recommended default; the Pages Router is covered in one chapter for migrating existing projects.

The mental model you need first

Hold this one idea and most of the framework stops being surprising.

The default is the server

Most of your components should carry no directive at all. A Server Component renders to HTML on the server, ships no JavaScript for itself, and is never re-executed in the browser — so anything that must be interactive has to be pulled out, not pushed in. Starting with 'use client' on everything and carving server components out of it is the exact inverse of how the framework is designed.

// app/page.tsx - a Server Component; no 'use client' in sight
import { ProductCard } from '@/components/ProductCard';   // also server

export default async function Home() {
  const products = await db.product.findMany({ take: 8 });
  return (
    <ul>
      {products.map((p) => (
        <ProductCard key={p.id} product={p} />
      ))}
    </ul>
  );
}
// the browser never receives this component's code - only its HTML

Two questions classify any component

Ask: does it need state, an effect, an event handler or a browser API? And: does it read secrets, the session or the request itself? Only-serves-data is a server component; only-interactive is a client component; both is a split — fetch on the server, pass plain data down to the smallest possible client leaf.

// Q1: does it need state, an effect, an event handler, or the DOM?
// Q2: does it read secrets, the session, or the request itself?
//
//                    Q1 yes      Q1 no
//   Q2 yes          split them   server
//   Q2 no           client       server
//
// 'split them' means: fetch on the server, pass plain data down to a
// client component that owns the interaction.
// Next.js renders your React tree in TWO places, and a component belongs
// to one of them permanently.
//
//   SERVER                          BROWSER
//   runs Node.js                    runs JS
//   has the filesystem, the         has no filesystem, no secrets,
//   database, the network            can be called directly by anyone
//   renders to HTML                 hydrates the HTML
//   cannot use useState, useEffect  cannot read the database
//
// THE DEFAULT is the server. A component is a Server Component unless it
// says otherwise. 'use client' is an opt-in, not a starting point.
//
// this is the opposite of what most tutorials lead with, and it is the
// single most important fact in the framework.

// 'use client' marks the BOUNDARY. Everything imported into a client
// component becomes client code too, transitively.
'use client';
import Counter from './Counter';   // Counter is now a Client Component
// and if Counter imports a big library, that library is in the bundle

// you do NOT need 'use client' on a component that only renders other
// server components and has no interactivity. Most of your app should
// not have it.

Two consequences follow immediately:

// 1. you cannot import a server-only thing into a client component
//    this is a build error, and it is a feature:
//      import { db } from '@/lib/db';        in a client component
//      -> "You're importing a component that needs db. That React hook
//          only works in a Server Component"

//    the fix is to pass the DATA down as a prop, not the client

// 2. the client boundary is a one-way street
//    a Server Component can render a Client Component and pass it
//    serialisable props. It cannot receive a function from one.
<SearchBox
  results={results}            // data: fine
  onSelect={() => ...}       // function: not serialisable
/>                            // -> "Functions cannot be passed to Client
                               //     Components" - use a Server Action

Conventions and how to read the code

File names in the App Router are meaningful, and the examples use the standard conventions:

The files that mean something

A handful of filenames in every app/ folder are declarations; everything else is inert. page.tsx creates the URL, route.ts creates an HTTP endpoint instead — and a folder cannot have both, because they would fight over the same path. layout.tsx, loading.tsx, error.tsx and not-found.tsx shape the UI around the page, and template.tsx behaves like a layout that remounts on every navigation.

app/
  products/
    page.tsx          UI at /products
    route.ts          CONFLICT - the build refuses two handlers for one URL
    layout.tsx        chrome shared by every page under /products
    loading.tsx       streamed fallback while page.tsx awaits
    error.tsx         per-segment error boundary ('use client')

  api/products/
    route.ts          an API endpoint, no UI, no page.tsx

Folders are either URLs or organisation

The underscore prefix _name removes a folder from routing entirely — the conventional home for helpers is _components/ and _lib/. Parenthesised groups (name) organise without contributing a URL segment, and square brackets [name] create dynamic segments. Between the two you can express any URL structure while keeping the tree readable.

app/
  _lib/             never a URL - the underscore is the escape hatch
    format.ts
  (marketing)/      never a URL - groups organise only
    page.tsx        /
  [lang]/           always a URL parameter
    page.tsx        /en
  • page.tsx — a route. Its presence in a folder creates the URL.
  • layout.tsx — shared UI wrapping this route and everything under it.
  • loading.tsx — a loading UI, streamed automatically.
  • error.tsx — an error boundary for this segment.
  • not-found.tsx — the 404 UI for this segment.
  • template.tsx — like a layout, but remounts on navigation.
  • route.ts — a custom HTTP handler, no UI.
  • Anything prefixed _ is excluded from routing. _components/ and _lib/ are the conventional homes for helpers.
// the shape of an app
app/
  layout.tsx           root layout: html, body, global nav
  page.tsx             /
  globals.css
  (marketing)/         a group: no URL segment, purely organisational
    layout.tsx
    page.tsx           /
    pricing/page.tsx   /pricing
  products/
    layout.tsx
    page.tsx           /products
    [id]/              a dynamic segment
      page.tsx         /products/123
      loading.tsx
      error.tsx
  api/
    route.ts           /api - a POST handler, no UI
  _components/         excluded from routing

1 · The Two Runtimes

A single page request in Next.js passes through several environments with different capabilities and different security properties. Knowing which is which is the foundation for every decision that follows.

What actually happens on a request

A single page load is not one thing. The request crosses the CDN, the Next.js server and the browser, and code runs in three places — middleware, Server Components, Client Components — in a fixed order. Only the cached pieces change between routes.

Render first, hydrate later

Steps 1–5 of the walkthrough happen before the first byte is sent: the URL resolves against the app/ tree, the layouts render top-down, and each Server Component executes — awaiting, reading the database, reading environment variables. The HTML response ships with the serialised RSC payload interleaved, so the browser can both display the document and reconcile later updates. Hydration then attaches behaviour to the already-correct DOM; a page is visible and scrollable before its JavaScript finishes loading.

The practical consequence is easy to verify: curl the route and the content is in the HTML. There is no client fetch and no skeleton for the server-rendered parts of the tree.

# what a browser actually receives for a Server Component page
curl -s http://localhost:3000/products/42 | head -20
# <!DOCTYPE html> - the product name is already in the markup

# what a client-side navigation asks for instead (the Flight stream)
curl -s -H "RSC: 1" http://localhost:3000/products/42
# a serialised React tree, not a document - the router reconciles it

The browser takes over after hydration

From the first soft navigation onwards, the router fetches the next route's RSC payload and reconciles it into the live DOM — no document reload, no full-page data refetch. The Server Components of that route run on the server again; the browser only ever runs the client components. This is why a Link to a product page feels instant twice: once from prefetching, once because there is no full page load.

import Link from 'next/link';

export function Nav() {
  return (
    <nav>
      <Link href="/products">Products</Link>
      <Link href="/cart">Cart</Link>
    </nav>
  );
}
// click -> router fetches the RSC payload -> tree swap in the live DOM
// no document reload; scroll position and component state survive
// GET /products/42
//
//  1. the request hits your server (or the edge, or a CDN)
//
//  2. Next.js matches the URL against the app/ tree
//     /products/[id]/page.tsx  with  id = "42"
//     and collects every layout.tsx on the path:
//       app/layout.tsx          root
//       app/products/layout.tsx products
//       app/products/[id]/page.tsx
//
//  3. layouts render TOP DOWN, page LAST
//     each is a React tree, so this is a normal render
//
//  4. Server Components run HERE, on the server
//     they can await, read the database, read env vars
//     their output is HTML plus a serialised RSC payload
//
//  5. the HTML response is streamed to the browser as it renders
//     (this is why loading.tsx and Suspense work - see ch6)
//
//  6. the browser downloads the JS chunks for the Client Components
//
//  7. the browser hydrates those components and takes over the DOM
//
//  8. from then on, navigation is client-side
//     the RSC payload for the next route is fetched, no full page load
//
// Server Components do NOT run in steps 6-8. They ran once, on the server.
// They are not re-run on the client. If a Server Component's output is
// not there, re-rendering in the browser is not going to produce it.

This is why a Server Component cannot have useState. There is no client instance of it to hold state — the component executed, produced a description, and that is the end of it. The state would have nowhere to live between interactions.

Two environments, two globals

The two environments are not two APIs bolted onto one codebase — they are two different runtime objects with different globalThis. A module that runs in both must use only what exists in both.

Know where you are at runtime

typeof window === 'undefined' is the classic guard, but in Next.js the better answer is structural: split the module so each file lives in one environment, and let the bundler enforce it. When you genuinely need one module for both — a logger, a formatting helper — the guard is enough, because the opposite global does not exist in that environment.

// lib/runtime.ts - safe to import from server AND client components
export const isServer = typeof window === 'undefined';

export function announce(message: string) {
  // server: prints in the terminal. client: prints in devtools.
  console.log(`[${isServer ? 'server' : 'client'}] ${message}`);
}

The intersection is small, and that's fine

fetch, URL, Request and Response, crypto.subtle, Web Streams and structuredClone exist in both environments. Node-specific globals (process, fs, Buffer) are server-only; DOM globals (window, localStorage, navigator) are browser-only. A data module written against the intersection can be imported from anywhere without a directive.

// lib/http.ts - imports cleanly on both sides of the boundary
export async function fetchJson(url: string, init?: RequestInit) {
  const res = await fetch(url, {
    ...init,
    headers: { 'content-type': 'application/json', ...init?.headers },
  });
  if (!res.ok) throw new Error(`${res.status} ${res.statusText}`);
  return res.json();
}
// fetch, RequestInit, Response, Error - all in the intersection
//                    Server            Browser
// process.env        YES               bundled at build - only NEXT_PUBLIC_*
// fs                 YES               no
// path/child_process YES               no
// Buffer             YES               no (unless polyfilled)
// window/document    no                YES
// localStorage       no                YES
// navigator          no                YES
// fetch              full              browser fetch, no caching rules
// setTimeout         yes               yes
// WebSocket          yes               yes
// Deno / Bun globals yes (node runtime) no

// consequences that surprise people
// 1. an object with methods cannot cross the boundary
//   pass plain data: strings, numbers, booleans, null, undefined,
//   Date (yes, serialised), plain objects, arrays, Map, Set,
//   typed arrays, Promise, and JSX elements

// 2. a class instance cannot cross
//   class Money { constructor(c) { this.c = c } }
//   <Price money={new Money(100)} />      Error
//   <Price cents={100} />                  fine

// 3. a function cannot cross
//   <Form onSubmit={() => save()} />     Error
//   <Form action={saveAction} />           fine (ch9)

Marking code server-only

There is a package for this, and it should be used on every module that touches secrets or a database.

The import that makes mistakes impossible

import 'server-only' must be the first statement of a module. It has no runtime effect: nothing is exported, nothing is executed. What it does is make any client bundle that transitively imports the module a build error, with a message naming the import chain. Without it, the failure mode is worse — either a runtime error in the browser or, with sloppy tooling, your connection string baked into a public bundle.

// lib/db.ts
import 'server-only';               // FIRST line. enforced at build time
import { PrismaClient } from '@prisma/client';

const g = globalThis as unknown as { prisma?: PrismaClient };
export const prisma = g.prisma ?? new PrismaClient();
if (process.env.NODE_ENV !== 'production') g.prisma = prisma;
// the global reassignment keeps dev hot-reload from exhausting sockets

The mirror image: client-only

The client-only package enforces the opposite direction: a module that must never execute on the server. It is for code that touches window at module scope — analytics, web workers — where an accidental server import would throw during render and break the route.

// lib/analytics.ts
import 'client-only';               // npm i client-only
export function track(event: string) {
  window.gtag?.('event', event);    // window is safe at module scope now
}
// lib/db.ts
import 'server-only';          // npm i server-only
import { Pool } from 'pg';

export const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// what it does: if ANY client component, anywhere in the dependency
// graph, imports this module, the BUILD FAILS with a clear message.
// without it, the mistake is a runtime error in the browser - or worse,
// a successful build with your connection string in the bundle.

// the reverse: client-only modules
'use client';
import { Chart } from './Chart';   // everything imported is client code
// use 'client' on the LEAF that needs interactivity, not at the top of
// your tree. 'use client' at the root turns your entire app into a SPA
// and throws away most of what Next.js does for you.

process.env.SECRET in a client component is a real leak, not a type error. A non-NEXT_PUBLIC_ variable referenced in client code is replaced with undefined at build time — safe but silently broken. Referenced in a module that reaches the bundle by accident, older tooling inlined it. Always add 'server-only' and always check what you import into a client component.

Environment variables

Environment variables are split by when they are read: at build time for the client bundle, at startup for the server. The NEXT_PUBLIC_ prefix is the single switch between the two.

Which file wins

Files load in a fixed precedence — .env.$(NODE_ENV).local beats .env.local, which beats .env.$(NODE_ENV), which beats .env. .env.local is the one you never commit; .env holds committed defaults. Values are read when the server starts or the build runs, so editing a file requires a restart in dev and a rebuild in production to take effect.

# load order, top wins
.env.production.local    # production machine only, not committed
.env.local               # your machine, not committed
.env.production          # committed, shared production defaults
.env                     # committed, base defaults

# which set is active
#   next dev   -> development
#   next build -> production (build-time inlining happens here)
#   next start -> production

NEXT_PUBLIC_ is a compile-time splice

At next build, every reference to process.env.NEXT_PUBLIC_* is replaced with the literal string. The value ends up in the shipped JavaScript and is readable by anyone who opens the bundle, so it is a broadcast channel, not a secret. Because it is baked in, changing it requires a rebuild — a restart alone is not enough.

# .env.local
NEXT_PUBLIC_API_BASE=https://api.example.com
API_KEY=sk_live_1234          # never NEXT_PUBLIC_ - that would leak

// app/components/Brand.tsx - 'use client'
const base = process.env.NEXT_PUBLIC_API_BASE;
// after next build, the bundle literally contains
//   const base = "https://api.example.com";
// .env.local        not committed, your machine
// .env              committed defaults, safe to share
// .env.production   production values, committed, no secrets
//
// the rule
//   NEXT_PUBLIC_FOO   -> inlined into the client bundle at build time.
//                       public. treat as broadcast.
//   EVERYTHING_ELSE   -> server only. read in server components, route
//                       handlers, server actions and middleware.

// reading them
const url = process.env.DATABASE_URL;            // server only
const version = process.env.NEXT_PUBLIC_VERSION; // any

// a typed accessor, so a missing variable fails at boot not at 3am
// lib/env.ts
import 'server-only';

function required(name: string): string {
  const v = process.env[name];
  if (!v) throw new Error(`Missing required environment variable: ${name}`);
  return v;
}

export const env = {
  DATABASE_URL: required('DATABASE_URL'),
  SESSION_SECRET: required('SESSION_SECRET'),
  STRIPE_SECRET_KEY: required('STRIPE_SECRET_KEY'),
};

// and validate the PUBLIC ones too
if (!/^\d+\.\d+\.\d+$/.test(process.env.NEXT_PUBLIC_VERSION ?? '')) {
  throw new Error('NEXT_PUBLIC_VERSION must look like 1.2.3');
}

Because NEXT_PUBLIC_ variables are inlined at build time, changing one requires a rebuild, not just a restart. This surprises people deploying to a platform that restarts containers. Treat a public env var as part of the build, not the runtime.

Node versus Edge runtimes

Next.js can run your code in two very different runtimes, and the choice is per-route or per-page.

What the edge really takes away

The Edge runtime is a V8 isolate at the CDN, not a Node.js process. fs, path, child_process, Buffer and native addons are absent — often showing up as a missing package — and on some platforms a fresh isolate per request means a module-level Map is not a cache. What you keep is the Web platform: fetch, URL, crypto.subtle, Request and Response. The surprise is usually the opposite of the fear: most auth and routing code runs on the edge unchanged.

// middleware.ts - the edge is the default here, so prove what survives
export function middleware(req: NextRequest) {
  // fs.readFileSync(...)                     - TypeError
  // const b = Buffer.from('x')               - ReferenceError
  const u = new URL(req.url);        // Web API - survives
  u.searchParams.set('v', '2');
  return NextResponse.rewrite(u);
}

Pick per route, not per app

The default is nodejs, and it works everywhere. Reach for the edge for middleware and for read-only, latency-sensitive routes that can live at the CDN; put anything that touches a database back on Node, because a direct TCP connection beats proxying SQL over HTTP. A Node function deployed in the same region as the database is often the better answer than an edge function two network hops away from it.

// app/dashboard/page.tsx - Node runtime, reads Postgres directly
export default async function DashboardPage() {
  const rows = await pool.query('SELECT 1');   // TCP to Postgres: works
  return <Table rows={rows.rows} />;
}

// app/api/geo/route.ts - edge: one HTTP call, no Node APIs needed
export const runtime = 'edge';
export async function GET(req: NextRequest) {
  const ip = req.nextUrl.searchParams.get('ip') ?? '';
  return Response.json(await geoLookup(ip));
}
// DEFAULT: the Node.js runtime. full Node APIs, no artificial limits.
export const runtime = 'nodejs';     // this is the default; no need to say it

// EDGE: a V8 isolate at the CDN's edge. starts in ~1ms instead of ~300ms,
// but NO Node built-ins.
export const runtime = 'edge';

// what you lose on the edge
//   fs, path, child_process, Buffer
//   most npm packages that depend on them
//   native addons
//   long-lived in-process caches (a new isolate per request in some
//     platforms, so a module-level Map is not a cache)

What each choice costs

The cost of a choice shows up in two ledgers: bytes of JavaScript shipped, and work done per request. Both are visible in the build output and both are measured, not guessed.

Client code pays twice

A Client Component pays shipping — its own code plus every transitive import goes to the browser — and it pays again at hydration, when the browser rewrites the DOM it already has. A Server Component pays nothing on the client and a render on the server, which caching can amortise. The cheapest design is therefore: fetch and format on the server, and keep the client leaf small enough to count its lines.

// the same UI, two cost profiles
// server: HTML in the document, ~0 KB of JS for this subtree
export async function Reviews() {
  const rows = await db.review.findMany();
  return <ul>{rows.map((r) => <li key={r.id}>{r.text}</li>)}</ul>;
}

// client: the subtree ships, then hydrates, then fetches (extra round trip)
'use client';
import { useEffect, useState } from 'react';
export function ReviewsClient() {
  const [rows, setRows] = useState<string[]>([]);
  useEffect(() => { fetch('/api/reviews').then((r) => r.json()).then(setRows); }, []);
  return <ul>{rows.map((t) => <li key={t}>{t}</li>)}</ul>;
}

The mechanics of the client boundary: what each kind of component can do, what may be passed between them, and the composition patterns that keep a mostly-server application from turning into a mostly-client one.

Writing a Server Component

A Server Component is just an async function with no 'use client' directive. There is nothing else to declare.

The working parts

A server component is a plain async function that returns JSX. It awaits its inputs — params, searchParams, cookies(), a database call — and the render pauses at each await, resuming when the promise resolves. Anything it returns crosses to the client only as serialised data; anything it imports stays on the server, except client components, whose subtree ships alone.

// app/profile/page.tsx - the full idiom in one file
export default async function ProfilePage() {
  const session = await getSession();          // cookies() under the hood
  if (!session) redirect('/login');

  const profile = await db.profile.findUnique({ where: { userId: session.userId } });
  return (
    <section>
      <h1>{profile?.name ?? 'No profile'}</h1>
      <EditButton userId={session.userId} />  {/* client leaf */}
    </section>
  );
}

What a Server Component cannot do

The build rejects the interactive toolbox outright: useState, useEffect, event handlers and browser globals are compile errors in a server component. That is the point — there is no client instance to hold state, so the failure is surfaced before deployment. The escape is composition, not a workaround: the server component resolves the data and a small client child owns the behaviour.

export default async function Page() {
  // const [n, setN] = useState(0);            // ✗ build error
  // useEffect(() => { ... }, []);             // ✗ build error
  // <button onClick={...}>                    // ✗ function props need an action

  const post = await loadPost();                // ✓ await is the whole point
  return <UpvoteButton count={post.upvotes} />; // ✓ data across, behaviour in
}

Async components and Suspense

A Server Component may be async. That is the mechanism behind streaming, and it is why a slow query does not block a fast one.

Render flows, not waits

Each async server component is an independent unit of work. The parent renders what is ready and suspends on what is not, and each Suspense boundary marks where the stream pauses: the shell goes out immediately, the fallback shows, and the real content replaces it the moment its promise resolves. Streaming cuts time-to-first-byte, not total render time — the same work happens, just delivered in the order it finishes.

// app/dashboard/page.tsx - shell first, tiles stream in
export default function Page() {
  return (
    <div className="grid">
      <Suspense fallback={<TileSkeleton />}><RevenueTile /></Suspense>
      <Suspense fallback={<TileSkeleton />}><OrdersTile /></Suspense>
    </div>
  );
}

async function RevenueTile() {
  const revenue = await getRevenue();   // 600ms
  return <Tile value={revenue} label="Revenue" />;
}

Writing a Client Component

A Client Component is one line of intent — 'use client' at the top of the file — and then ordinary React: state, effects, handlers, browser APIs. The directive turns the whole file and everything it imports into client code.

Put the directive on the smallest leaf

The directive fans out: everything the file imports, and everything those imports import, ships to the browser. So it belongs on the component that owns the state, not on a parent that merely renders it. A button with a local useState is a good client component; a layout with a directive is a mistake you notice three builds later when the bundle has quietly tripled.

// app/components/Counter.tsx - twenty lines, the only client bit on the page
'use client';
import { useState } from 'react';

export function Counter({ initial }: { initial: number }) {
  const [n, setN] = useState(initial);       // initial comes from the server
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

It renders twice in dev, once in prod

In development every client component renders on the server and again during hydration, and React Strict Mode double-invokes effects — so code that reads new Date() or a random value during render produces different output on the two passes, and hydration complains. The fix is to defer output-changing reads to an effect that runs after mount, so the first client render matches the server HTML exactly.

'use client';
import { useEffect, useState } from 'react';

export function RightNow() {
  const [iso, setIso] = useState<string | null>(null);
  useEffect(() => setIso(new Date().toISOString()), []);  // after mount only
  return <time>{iso ?? 'loading'}</time>;                  // stable first render
}

What can cross the boundary

Crossing the boundary is a serialisation step, not a reference pass. Anything a JSON-like formatter cannot express — functions, prototypes, symbols, DOM nodes — fails at build or render time by design.

The exact value types

Strings, numbers, booleans, null, undefined, bigint, plain objects and arrays of those, Date (which arrives as a string), typed arrays, and — with care — Map and Set. The golden rule is to build the exact shape the client expects on the server and convert near the boundary, not deep in the client tree where the loss is harder to see.

// server parent - make the prop shape explicit
export default async function Page() {
  const stats = await getStats();
  return (
    <StatsGraph
      points={stats.points}                   // number[]
      label={stats.label}                      // string
      fetchedAt={new Date().toISOString()}     // string, NOT a Date
    />
  );
}

The traps that fail silently

Map and Set arrive as empty objects — no error, just missing data. Class instances throw outright; getters are stripped; non-plain objects like URL arrive mangled unless they implement toJSON. Convert at the boundary: an array of keys travels cleanly and the client rebuilds the structure it needs.

// server: <FilterPanel selected={new Set(['a'])} />   - arrives as {}
// server: <FilterPanel selected={['a']} />            - arrives intact

'use client';
export function FilterPanel({ selected }: { selected: string[] }) {
  const selectedSet = new Set(selected);   // rebuild on arrival
  return <ul>{[...selectedSet].map((s) => <li key={s}>{s}</li>)}</ul>;
}

Where to put the boundary

The boundary is a design decision, not a syntax detail. One directive at the root silently converts the entire application into a client-rendered SPA; one directive per interactive leaf keeps the rest of the tree on the server.

One directive per interactive leaf

A typical page carries three to eight directives, each on the component that owns state, an effect or an event handler. Everything else renders on the server — including the layouts and pages around those leaves. The position of each directive is the map of your application's interactive surface; if you cannot say what each one is for, it is probably wrong.

Context across the boundary

Context flows from provider to consumer, and the provider must live in the client tree. A server component cannot read a client context, and a client provider cannot wrap server children — so the two runtimes coordinate through props, not context.

Which direction works

Server-to-client is fine: a server component renders a client provider and passes values in as props, and client descendants consume the context normally. Client-to-server is impossible — a client provider's children render on the client, and server components never execute there — which is why "put the whole app in a provider" does not translate to the App Router.

// app/layout.tsx (server) - mounts the client provider, feeds it data
import { CartProvider } from '@/components/cart-provider';
import { Nav } from '@/components/nav';        // still a server component

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <CartProvider initialCount={2}>   {/* client */}
      <Nav />                       {/* server - fine as a child */}
      {children}
    </CartProvider>
  );
}

Split the state by runtime

The pattern that works: read data on the server and pass it down as props; let a client context hold only interactive state. A theme toggle is the canonical example — the server supplies the initial value, the client context stores the choice after the user flips it.

Composition patterns that work

Four compositions cover almost every real layout: a server parent with a client leaf, children-as-a-prop, an interactive wrapper around server content, and Server Actions as props. They all share one idea — the server renders, the client behaves, and the two meet through props.

Server children inside a client frame

A client component can receive children that were already rendered on the server and drop them into its tree. The frame — say an expandable panel — owns the interactivity, while the content keeps all its advantages: it is present in the HTML, it is indexable, and its text never enters the client bundle.

// components/expandable.tsx
'use client';
import { useState } from 'react';

export function Expandable({ title, children }: {
  title: string;
  children: React.ReactNode;
}) {
  const [open, setOpen] = useState(false);
  return (
    <section>
      <button onClick={() => setOpen(!open)}>{title}</button>
      {open ? children : null}      {/* server-rendered, dropped in whole */}
    </section>
  );
}

// app/faq/page.tsx (server) - the content is rendered on the server

Every Next.js page is rendered in one of a small number of ways, and the choice is made for you unless you make it. This chapter is about knowing which one you got, and about the two functions that make the choice explicit.

A request end to end

One request is a pipeline with caching layers at every stop, and the same pipeline serves both the initial load and every later navigation. Two details decide most of what you observe: streaming, and the serialised RSC payload that rides alongside the HTML.

The response is a stream, not a file

Next.js does not assemble a complete document and then send it. The route renders into a stream, and as each segment resolves — layouts first, then the page, then whatever sits inside Suspense boundaries — those bytes flush immediately. The browser paints the shell and keeps painting as chunks arrive, which is why a slow query degrades into a filling page rather than a spinner for the whole route.

# <div id="__next">...Dashboard shell...</div>
# <!-- later chunks replace each Suspense fallback in order -->

The RSC payload is the contract

Every render also produces a serialised React tree — the Flight stream — interleaved into the response. Soft navigation requests exactly that payload with an RSC: 1 header and reconciles it into the live DOM; no document is sent, so no full reload happens. Server Components on the target route execute on the server again; the client only ever renders what the payload describes.

//     app/dashboard/layout.tsx

//  4. Collect what each component needs.
//     layouts render top-down; the page renders last.

//  5. Each Server Component executes on the server.

//  6. React renders the tree to a stream.

Step 6 is the one people miss. Next.js streams by default, which is why a slow query degrades gracefully instead of showing a spinner for the whole page.

Static, dynamic, and how Next decides

"Static" and "dynamic" are not flags you choose — they are the outcome of what the route's render touches. Knowing the inputs that flip the outcome is the skill; the route table prints the verdict at every build.

The inputs that flip the outcome

A route stays static when its render touches none of: request APIs (cookies(), headers(), draftMode()), searchParams, an uncached fetch of a non-static source, an uncached database read, or an explicit dynamic marker. A dynamic segment that omits generateStaticParams is dynamic too, because Next.js cannot know which paths exist. Any one of these makes the whole route ƒ; the fix is usually to move the dynamic read into a Suspense-wrapped child (PPR) or into a Server Action.

// a page that looks static but is not
export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;                       // dynamic segment
  const product = await prisma.product.findUnique({ where: { id } });  // uncached read
  return <ProductView product={product} />;
}
// next build prints ƒ. give it generateStaticParams to prerender the
// known ids, or accept on-demand rendering - decide, do not discover

Opting into dynamic rendering

Four inputs flip a route to dynamic, and knowing them lets you either embrace the route being ƒ or quarantine the exact part that needs the request.

The four culprits, and the 15 surprise

An uncached fetch from a dynamic source, a request API call, a searchParams read, or an uncached database query — any one makes the route ƒ. The surprise in Next.js 15 is the first one: fetch is uncached by default, a deliberate reversal of version 14. An ordinary fetch now pushes a route toward dynamic unless you opt in per call.

// next 15: fetch does NOT cache by default
const res = await fetch('https://api.example.com/prices');   // route is ƒ

// opt back in, per call
const a = await fetch('https://api.example.com/prices', { cache: 'force-cache' });
const b = await fetch('https://api.example.com/prices', { next: { revalidate: 300 } });
const c = await fetch('https://api.example.com/prices', { next: { tags: ['prices'] } });

Embrace it deliberately

Some pages are personal, mutable and request-shaped by nature — a checkout, a dashboard, a session-scoped cart — and caching them would be wrong even if it worked. For those, force-dynamic states the decision in the file so the build, your colleagues and next month's you all know it was a choice, not an accident.

// app/checkout/page.tsx - always per-request; say so, once
export const dynamic = 'force-dynamic';

export default async function CheckoutPage() {

Partial prerendering

PPR splits a route into a static shell, cached at build, and dynamic holes, filled per request. It is the answer to "this page is mostly the same for everyone but has a personalised corner".

The shell is the product

Everything outside a Suspense boundary in a PPR route is prerendered once at build time — navigation, headings, static cards — and then served from cache for every visitor. Only the holes render per request. That changes the economics of a personalised dashboard: the shared shell no longer re-renders for each user, so there is no per-user cache explosion and the personalised feed simply streams in.

// with ppr: 'incremental', opt a route in per file
// app/page.tsx
export const experimental_ppr = true;

export default function Page() {
  return (
    <main>
      <Hero />                          {/* static: prerendered once */}
      <Suspense fallback={<PricesSkeleton />}>
        <LivePrices />                   {/* dynamic: rendered per request */}
      </Suspense>
    </main>
  );
}

What PPR is not

PPR does not make a personalised page static — the shell is still one identical HTML for every user. It only pays off when the shared part is large relative to the holes. The selector is simple: measure what fraction of the HTML is identical across two users. If it is most of the page, a static shell earns its complexity; if nearly everything is personal, you are paying for a cache nobody hits.

// the selector
//   mostly shared (docs, catalogue, marketing) -> PPR or full static
//   mostly personal (feed, dashboard)          -> dynamic + Suspense
//   shared shell with a personal corner        -> PPR is exactly this
//
// measure: what fraction of the HTML is identical across two users?
//   more than half shared -> the static shell pays for itself
// next.config.ts
const nextConfig = {
  experimental: { ppr: 'incremental' },   // or true for the whole app
};

// a route with a static shell and a dynamic hole
// app/dashboard/page.tsx
import { Suspense } from 'react';

export default function Page() {
  // everything outside the Suspense boundary is prerendered at build time
  return (
    <div className="dashboard">
      <h1>Dashboard</h1>
      <Nav />                        {/* static */}
      <Suspense fallback={<FeedSkeleton />}>
        <PersonalFeed />              {/* dynamic, per request */}
      </Suspense>
    </div>

}

  const user = await getSession();          // cookies() -> dynamic

// only the hole is rendered per request.
// this turns "my dashboard is slow" into "the shell is cached and the
// feed streams in", with no per-user shell cache explosion.

PPR is still experimental, but the mental model it teaches is the one you need regardless: separate what is the same for everyone from what is specific to this request, and cache the first. Even without PPR you can achieve most of it with loading.tsx and a well-placed Suspense boundary.

Reading headers and cookies

cookies() and headers() are the two request APIs most routes read, and in Next 15 both are async — a deliberate change that makes it obvious the call performs I/O.

The async store API

Both functions return a Promise of a store: (await cookies()).get('name') returns a cookie object or undefined; headers() returns a header map. The stores are request-scoped, so a read inside a Server Action or a route handler sees the same request as the page — and in an action or handler the cookie store is also writable via .set(), which is how a theme choice or session rotation gets persisted.

import { cookies } from 'next/headers';

export default async function RegionNote() {
  const store = await cookies();
  const currency = store.get('currency')?.value ?? 'USD';
  const session = store.get('session')?.value;   // httpOnly: JS never sees it
  return <p>{currency} - {session ? 'signed in' : 'guest'}</p>;
}

Every read shapes the cache story

Reading a header or cookie during render makes the route dynamic — even when the value is only used for logging. Reading in a layout makes every page beneath it dynamic. The discipline: do not read what you do not render. If the value is only needed later — in a Server Action, a route handler or middleware — read it there, where it costs nothing; if it is genuinely needed during render, use the smallest component possible and wrap it in Suspense.

// the truth, in one line each
// cookies() or headers() anywhere in the render -> route is ƒ
//   ...unless the read is inside Suspense AND partial prerendering is on
// a value needed only on submit:  read it in the Action, not the page
// a value needed only on redirect: read it in middleware, not the page
// both are ASYNC in Next 15, and they are DYNAMIC APIs:
// calling either makes the route dynamic.

import { cookies, headers } from 'next/headers';

export default async function Page() {
  const cookieStore = await cookies();
  const session = cookieStore.get('session')?.value;
  const theme = cookieStore.get('theme')?.value ?? 'light';

  const headersList = await headers();
  const ua = headersList.get('user-agent');
  const lang = headersList.get('accept-language')?.slice(0, 2);

  return <Dashboard theme={theme} lang={lang} ua={ua} />;
}

// in a Server Action the cookieStore is also writable
'use server';
export async function setTheme(theme: string) {
  (await cookies()).set('theme', theme, { httpOnly: true, sameSite: 'lax' });
}

// in MIDDLEWARE, they are not async (it is not a component)
import { NextRequest } from 'next/server';
export function middleware(req: NextRequest) {
  const token = req.cookies.get('session');
}

// in a ROUTE HANDLER, the NextRequest carries them

  const session = req.cookies.get('session');
  return Response.json({ ok: !!session });
}

Reading a cookie to vary content means the page cannot be cached for everyone. For "one small personalised corner of a large page", the fix is usually: read the cookie inside a small child component wrapped in Suspense, so only that child is dynamic. Reading it in the page's top level makes the whole page dynamic, which is a heavy price for one value.

The render cache and a nonce

Next.js keeps a per-request cache so that if a layout and a page both fetch the same thing, it happens once. Understanding it explains some otherwise-baffling behaviour.

Dedup without the client boundary

The render cache deduplicates calls within one render pass; React.cache() (from react) extends that to the whole request, even across module boundaries and client components. Wrap a data accessor in it and every caller — layout, page, and server components rendered behind client frames — shares one fetch per request.

// lib/data.ts
import { cache } from 'react';

export const getProduct = cache(async (id: string) => {
  return db.product.findUnique({ where: { id } });
});

// layout and page both call getProduct(id) in one request:
// ONE query, even with a client component between them, because the
// cache dedupes before the value crosses any boundary

Nonces exist for the CSP, not for you

A strict Content-Security-Policy needs a per-request nonce for inline scripts, and the framework must know it at render time — so middleware mints one, exposes it as a header, and composes the CSP from it. Reading x-nonce in a component is legitimate only when you are applying that policy; if you find yourself checking it to decide what to render, you are working around a design problem.

// middleware.ts - mint a nonce per request, wire it into the CSP
export function middleware(req: NextRequest) {
  const nonce = crypto.randomUUID();
  const csp = [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}'`,
    "style-src 'self' 'unsafe-inline'",
  ].join('; ');

  const res = NextResponse.next();
  res.headers.set('x-nonce', nonce);
  res.headers.set('Content-Security-Policy', csp);
  return res;
}

// and is shared by everything rendered in it.

Seeing what happened

The mental model is cheap to verify with three tools: the build's route table, the browser's Network panel, and a raw HTTP client. Ten minutes with them settles most "is this actually running on the server?" arguments permanently.

The route table is a report card

Every next build prints one symbol per route: ○ static, ● SSG via generateStaticParams, ƒ dynamic, ◐ partial. It is the fastest regression detector in the framework — add a cookies() read and watch ○ flip to ƒ, with the build usually naming the culprit. Make reading it part of every build.

npx next build 2>&1 | grep -E "○|●|ƒ|◐"
# ○ /            static - served from the CDN
# ● /blog/[slug] prerendered for the generateStaticParams set
# ƒ /dashboard   dynamic - find the cookies()/fetch that did it

Fetching in the App Router is easier than it was in the Pages Router, mostly because there is one obvious place to do it. This chapter is about doing it well: in parallel, without waterfalls, with errors that are contained, and with a cache you can reason about.

Where to fetch

In the App Router there are exactly two correct answers to "where do I fetch?": in a Server Component for anything the request can know, and in a client effect only for data that genuinely depends on post-hydration user interaction.

Fetch in the component that renders the data

The component starts, awaits, and renders — there is no loading state to manage, no effect to fire, no cache library, and the data is not in the client bundle. If the fetch fails, the component throws and the nearest error.tsx catches it. The HTML is complete in the first response because the data was resolved before anything was sent.

// app/repos/[owner]/page.tsx
export default async function RepoPage({ params }: { params: Promise<{ owner: string }> }) {
  const { owner } = await params;
  const repos = await getRepos(owner);           // any async source
  return <RepoList repos={repos} />;
}
// no useEffect, no isLoading, no refetch-on-mount

Next 15's fetch is uncached by default

The single biggest behaviour change from version 14: a plain fetch no longer caches. Teams upgrading who relied on implicit caching get dynamic routes and duplicate requests for free. The fix is not to fight it — it is to make caching explicit, per call, with cache, revalidate or tags, and to reserve the client effect for genuinely interaction-driven data.

// upgrading from next 14 - what silently changed
const r = await fetch(API + '/prices');            // 14: cached   15: not cached

// restore caching deliberately
const r1 = await fetch(API + '/prices', { cache: 'force-cache' });
const r2 = await fetch(API + '/prices', { next: { revalidate: 60 } });
const r3 = await fetch(API + '/prices', { next: { tags: ['prices'] } });

// not in an effect, not in a client hook.

//   - no waterfall: the component does not mount before fetching
//   - no cache library required

Parallel and dependent fetches

Fetch shapes come in two: independent calls fan out, dependent calls chain. Sequential await where calls must chain is correct; sequential await where they do not is a waterfall you built yourself.

Fan out with Promise.all

Independent calls cost the maximum of their latencies, not the sum. Promise.all fails fast — one rejection rejects the whole batch — while Promise.allSettled lets you keep the results that succeeded. Pick the semantics that matches the UI: all-or-nothing for a form, best-effort for a dashboard row.

const [nav, hero, deals] = await Promise.all([
  getNav(),          // 50ms
  getHero(),         // 120ms
  getDeals(),        // 90ms
]);
// total ≈ 120ms, not 260ms

const results = await Promise.allSettled([getA(), getB(), getC()]);
const ok = results
  .filter((r) => r.status === 'fulfilled')
  .map((r) => r.value);            // keep what succeeded

Chain only what depends

Two calls that use each other's output must sequence; everything else joins the current batch. The pattern is a staircase: resolve one step, fan out with what it unlocked, resolve the next step. Each fan-out is a Promise.all; each dependency is a single await.

async function getOrderSummary(id: string) {
  const order = await getOrder(id);                    // step 1: depends on id
  const [customer, items] = await Promise.all([        // step 2: both depend on order
    getCustomer(order.customerId),
    getItems(order.id),
  ]);
  return { order, customer, items };
}
// DEPENDENT: b needs a's result, so they must be sequential
const user = await getUser(session.userId);
const orders = await getOrders(user.id);        // must wait

// INDEPENDENT: three of these, so run them at once
const [a, b, c] = await Promise.all([
  getProducts(),
  getCategories(),
  getReviews(),
]);
// three sequential awaits = 300 + 200 + 150 = 650ms
// Promise.all        = max(300, 200, 150) = 300ms

// most common cause in Next.js is a parent awaiting before a child starts.
//
// BAD: layout awaits, so every page under it waits
// app/dashboard/layout.tsx

  return <Shell user={user}>{children}</Shell>;

// parts that need the user sit behind their own Suspense boundary

The practical rule: fetch as close to where the data is used as possible. A layout that fetches forces every page beneath it to wait for data most of them do not need. It is the most common cause of a slow dashboard.

Fetching with Suspense

Suspense is how the App Router turns "wait for all data" into "render what is ready". The parent stays sync; each async child streams in behind its own boundary.

Sync parent, async children

An async parent awaits its children implicitly, which serialises them; a sync parent hands each child to its own Suspense boundary, and the children start fetching the moment the parent renders — in parallel. The distinction fits in one line: async parent -> awaits everything, while sync parent + async children -> streams.

export default function Admin() {
  return (
    <>
      <Suspense fallback={<SlowCard />}><AuditLog /></Suspense>
      <Suspense fallback={<SlowCard />}><QueueStats /></Suspense>
    </>
  );
}

async function AuditLog() {
  const rows = await getAuditRows();          // starts immediately
  return <LogTable rows={rows} />;
}

One boundary per visible region beats one per query: the fallback is what users see, so group work that finishes together. Nested boundaries work — an outer shell streams first, inner details stream later. loading.tsx is the shorthand for "one boundary around this whole segment", the right default for most routes.

// one boundary for a whole region, not one per query
<Suspense fallback={<ActivitySkeleton />}>
  <ActivityFeed />    {/* fetches five things internally, streams once */}
</Suspense>
// make a data-fetching component itself async, and let Suspense handle it
// the parent does NOT await it

Cascades and how to flatten them

A cascade is a request that cannot start until an earlier one finishes. It is the root cause of most slow pages.

Diagnose by shape, not speed

In the Network panel, a cascade reads as a staircase: each later request starts the moment the previous one ends. Ten requests at 50 ms serialised cost 500 ms; one request at 120 ms costs 120 ms. When profiling, look at the shape of the waterfall first — flattening it is usually worth more than speeding up any single request.

// the signature of a cascade in the Network panel
//   /orders/42           200ms
//     /customers/1        50ms   (starts only after #1)
//       /items/...        40ms   (starts only after #2)
//
// each row begins where the previous row ends - that is the smell

Kill the N+1 with one IN query

Collect the ids, run one query, rebuild a lookup Map, and assign in a loop. A loader function that batches and dedupes across the whole render — the pattern behind the dataloader library — does the same thing structurally, so ten components asking for ten ids produce one query with an IN clause.

// before: N queries for N products' categories
const categories = [];
for (const p of products) {
  categories.push(await getCategory(p.categoryId));   // N round trips
}

// after: 1 query
const ids = [...new Set(products.map((p) => p.categoryId))];
const rows = await db.category.findMany({ where: { id: { in: ids } } });
const byId = new Map(rows.map((c) => [c.id, c]));
products.forEach((p) => { p.category = byId.get(p.categoryId) ?? null; });
// THE CASCADE, UNFLATTENED
// app/orders/[id]/page.tsx
const order = await getOrder(id);          // 100ms
const customer = await getCustomer(order.customerId);   // 120ms, after
const items = await getItems(order.id);                // 80ms, after
const productDetails = await Promise.all(
  items.map((i) => getProduct(i.productId)),         // 150ms, after
);
const reviews = await getReviews(productDetails.map((p) => p.id)); // 200ms, after
// total: 650ms, strictly sequential

// FLATTENED
// step 1: what is known at the start? just the id
const order = await getOrder(id);          // 100ms, unavoidable

// step 2: everything now computable runs together
const [customer, items] = await Promise.all([
  getCustomer(order.customerId),
  getItems(order.id),
]);                                        // max(120, 80) = 120ms

// step 3: and the next layer together
const products = await db.product.findMany({
  where: { id: { in: items.map((i) => i.productId) } },
});                                        // ONE query, not N
const reviews = products.length
  ? await getReviews(products.map((p) => p.id))
  : [];
// total: ~370ms, and one round trip instead of N

// THE BIGGEST WIN: batch the N+1
// BAD: 50 products, 50 queries
for (const p of products) p.category = await getCategory(p.categoryId);

// GOOD: one query
const categories = await db.category.findMany({
  where: { id: { in: [...new Set(products.map((p) => p.categoryId))] } },
});
const byId = new Map(categories.map((c) => [c.id, c]));
products.forEach((p) => { p.category = byId.get(p.categoryId); });

// or use a data loader, which batches across an entire render
const getUser = dataLoader(async (id) => {
  return db.user.findUnique({ where: { id } });
});
// 10 components ask for users 1, 2, 3... Next.js issues ONE query with
// an IN clause, and caches it for the request

When profiling, look at the shape of the waterfall in the Network panel, not just the slowest request. Ten requests that each take 50 ms but run in sequence cost 500 ms; one request that takes 120 ms costs 120 ms. The waterfall, not the latency, is usually the problem.

Mutations and the client cache

Reads in the App Router are server-side and cached. That means a mutation must tell the server cache what changed, or the user will see stale data on their next navigation.

The server action is the mutation endpoint

A Server Action is a public HTTP endpoint that looks like a function: it receives FormData or plain arguments, runs with the request's cookies, and may revalidate and redirect. Because it is public, every action needs an authorisation check and schema validation — treat every argument as untrusted, including ids that belong to other users.

// app/notes/actions.ts
'use server';
import { createNote } from '@/lib/notes';
import { revalidatePath } from 'next/cache';

export async function addNote(form: FormData) {
  const title = String(form.get('title') ?? '').trim();
  if (!title) throw new Error('title is required');     // validate first
  await createNote(title);                              // then write
  revalidatePath('/notes');                             // then invalidate
}

// a plain HTML form can post to it - the write works without JavaScript
// <form action={addNote}><input name="title" /></form>

Give the user a pending state

useFormStatus exposes the pending flag of the nearest form action, and useActionState threads a returned state back into the form — neither needs a useEffect or a hand-rolled loading boolean. Disable the submit button while pending, then let revalidation or router.refresh() present the new data.

'use client';
import { useFormStatus } from 'react-dom';

export function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>;
}
// rendered inside the form that owns the action - pending tracks it
// the core tension
//   reads:  happen on the server, and the RESULT is cached
//   writes: happen via a server action, on the server
//   the client router has its OWN cache of the last-visited pages

// so after a write you must invalidate, or the user navigates back to
// the old data. Three mechanisms exist:

// 1. revalidatePath - drop a route from the server cache
// 2. revalidateTag  - drop anything fetched under a tag (ch7)
// 3. router.refresh() - re-fetch the current route's RSC payload

// 'use server'
import { revalidatePath, revalidateTag } from 'next/cache';

export async function updateProduct(id: string, form: FormData) {
  await requireUser();                        // ALWAYS authorise
  const data = validate(form);                // ALWAYS validate
  await db.product.update({ where: { id }, data });

  revalidateTag('products');                  // the list
  revalidatePath(`/products/${id}`);           // the detail page
  // both. the list and the detail are different cache entries.
}

// 3. client-side, when you want a transition
'use client';
const router = useRouter();
const [pending, startTransition] = useTransition();

function onSaved() {
  startTransition(() => {
    router.refresh();       // re-fetch this route's payload, show it
                          // without a loading state
  });
}

Every server action needs both an authorisation check and a validation step, and they are not optional. A server action is a public HTTP endpoint. Anyone can call it with any argument, including an id belonging to another user. Treat every action as untrusted input: check who is calling, check what they are allowed to touch, and validate every field.

Revalidating after a mutation

Revalidation is cache arithmetic: which cache entries does the mutation touch, and which invalidation reaches exactly those? The wrong choice means stale data or a cache thrashed unnecessarily.

Tags reach across routes

A tag is a name attached at fetch time and dropped on revalidation: revalidateTag('posts') invalidates every cache entry fetched under that tag, wherever it is used. Tags survive route restructuring — the same tag serves the list and the detail page. Database reads join the same system via cache from next/cache, which accepts the same tags and revalidate options.

// fetch with a tag and a TTL
const posts = await fetch('http://api.internal/posts', {
  next: { tags: ['posts'], revalidate: 300 },
});

// DB reads join the same system
import { cache } from 'next/cache';
export const getPosts = cache(async () => db.post.findMany(), {
  tags: ['posts'],
  revalidate: 300,
});

// after a mutation:
await createPost(...);
revalidateTag('posts');          // every 'posts' consumer goes stale at once

Order a create: write, revalidate, redirect

For a create, redirect beats refresh: the Post/Redirect/Get pattern prevents double-submits and lands the user on a freshly built page. Revalidate before redirecting so the destination is regenerated in time, and revalidate both granularities — the list and the detail — because they are different cache entries.

// app/posts/actions.ts
'use server';
import { redirect } from 'next/navigation';
import { revalidatePath, revalidateTag } from 'next/cache';

export async function createPost(form: FormData) {
  const post = await db.post.create({ data: { title: String(form.get('title')) } });
  revalidatePath('/posts');                     // the list
  revalidateTag(`post:${post.id}`);             // the detail
  redirect(`/posts/${post.slug}`);              // PRG: fresh target
}
// choosing the right invalidation

// revalidateTag - precise, survives as long as the data is fetched with
// the tag
export async function createPost(form: FormData) {
  const post = await db.post.create({ data: parse(form) });
  revalidateTag('posts');                 // matches fetch(url, { next: { tags: ['posts'] } })

  return post;
}

Error handling per fetch

Error handling has three layers — throw, boundary, local catch — and the right one depends on blast radius. One bad tile should not blank the dashboard.

Boundary or catch?

A thrown error in a server component is caught by the nearest error.tsx, which must be a client component (it needs a reset callback to retry). An error inside a Suspense boundary is caught by that boundary's error file, not the whole page's. Decide per segment how much of the UI one failure may take down.

// app/feed/error.tsx - must be 'use client'
'use client';
export default function FeedError({ error, reset }: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div role="alert">
      <p>This section failed to load.</p>
      <p>digest: {error.digest ?? 'unknown'}</p>
      <button onClick={reset}>Retry</button>
    </div>
  );
}

Local recovery beats a page error

When one widget failing should not affect its neighbours, catch near the fetch and render a fallback — a muted line beats a blank region, and a blank region is worse than an honest message. The pattern is a two-value result: data or error, never a swallowed promise.

async function Recommendations() {
  const [recs, error] = await getRecs().then(
    (r) => [r, null] as const,
    (e) => [null, e as Error] as const,
  );
  if (error) return <p className="muted">Recommendations unavailable.</p>;
  return <RecList recs={recs!} />;
}
// three layers, and you want all three

// 1. a thrown error is caught by the nearest error.tsx (ch16)
//    this is the default and it is correct
async function Widget() {
  const data = await getData();   // throws on failure
  return <Chart data={data} />;
}

// 2. error.tsx catches it for the segment. Note it must be a client
//    component, because it needs useEffect for the reset button
'use client';
export default function Error({ error, reset }: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong</h2>
      <p>{error.message}</p>
      <button onClick={reset}>Try again</button>
    </div>
  );
}

// 3. graceful degradation, when one failure should not blank the page
async function Widget() {
  const data = await getData().catch(() => null);
  if (data === null) return <WidgetUnavailable />;
  return <Chart data={data} />;
}

// the two rules
//   - a failed fetch inside a Suspense boundary triggers the boundary's
//     error handler, NOT the whole page
//   - never catch an error and show nothing. an empty region with no
//     explanation is worse than an error message

Next.js redacts server error messages in production before sending them to the client, and shows a digest instead. That is deliberate: stack traces and database errors leak schema and file paths. Use the digest in logs to find the real error.

A complete data flow

An edit form is the one place every idea in this chapter lands at once: server component reads, server action writes, schema validates, authorisation gates, revalidation refreshes, and the client form is a thin shell around useActionState.

The three files and their jobs

page.tsx (server) reads the record and gate-checks who may edit it; actions.ts declares the action, the Zod schema and the revalidation; ProductForm.tsx (client) binds the action through useActionState. The State type is the contract between form and action: per-field errors, a top-level message, or null for success.

// the data contract the form and the action both speak
export type State = {
  errors?: Record<string, string[]>;   // per-field, rendered with role="alert"
  message?: string;                     // top-level failure (not found, forbidden)
} | null;                               // null = success

// useActionState wires it together
const [state, formAction, pending] = useActionState(action, null);

It works with JavaScript switched off

The form is progressive: a plain form action posts to the server, the action revalidates, and the server re-renders the page — no fetch, no useEffect, no loading boolean anywhere. useActionState only upgrades the experience: pending states, inline errors, no page flash. The test below is the cheapest correctness check in the framework.

# the progressive baseline, in three steps
# 1. DevTools -> Settings -> disable JavaScript
# 2. edit a product, submit
# 3. the server re-renders with the saved values
#    useActionState is an enhancement, not a requirement
// the full pattern: server component reads, form posts to a server action,
// validation and authorisation on the server, cache invalidated, UI
// updates without a manual refetch.

// app/products/[id]/edit/page.tsx - server
import { requireUser } from '@/lib/auth';
import { canEdit } from '@/lib/permissions';
import { updateProduct } from './actions';
import { notFound } from 'next/navigation';

export default async function EditPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const user = await requireUser();                  // redirects if not signed in
  const product = await db.product.findUnique({ where: { id } });
  if (!product) notFound();
  if (!canEdit(user, product)) notFound();           // do not leak existence

    <ProductForm
      product={product}                              {/* plain, serialisable */}
      action={updateProduct}                         {/* a server action */}

// app/products/[id]/edit/actions.ts
'use server';
import { revalidatePath, revalidateTag } from 'next/cache';
import { z } from 'zod';

const Schema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1).max(200),
  price: z.coerce.number().positive(),
});

export type State = { errors?: Record<string, string[]>; message?: string } | null;

export async function updateProduct(
  _prev: State,
  form: FormData,
): Promise<State> {
  const session = await requireUser();

  const parsed = Schema.safeParse(Object.fromEntries(form));
  if (!parsed.success) {
    return { errors: parsed.error.flatten().fieldErrors };
  }

  const { id, ...fields } = parsed.data;
  const existing = await db.product.findUnique({ where: { id } });
  if (!existing || !canEdit(session.user, existing)) {
    return { message: 'Not found' };
  }

  await db.product.update({ where: { id }, data: fields });

  revalidateTag('products');
  revalidatePath(`/products/${id}`);
  revalidatePath('/products');
  return null;                                       // success: no error state
}

// app/products/[id]/edit/ProductForm.tsx - client
'use client';
import { useActionState } from 'react';

export function ProductForm({ product, action }: {
  product: Product;
  action: (prev: State, form: FormData) => Promise<State>;
}) {
  const [state, formAction, pending] = useActionState(action, null);

  return (
    <form action={formAction}>
      <input name="id" type="hidden" value={product.id} />

      <label>
        Name
        <input name="name" defaultValue={product.name}
          aria-invalid={!!state?.errors?.name} />
        {state?.errors?.name?.map((e) => <span key={e} role="alert">{e}</span>)}
      </label>

      <label>
        Price
        <input name="price" type="number" step="0.01" defaultValue={product.price} />
        {state?.errors?.price?.map((e) => <span key={e} role="alert">{e}</span>)}
      </label>

      {state?.message && <p role="alert">{state.message}</p>}

      <button disabled={pending}>{pending ? 'Saving...' : 'Save'}</button>
    </form>
  );
}

Note what is not in there: no useEffect, no useState for the field values, no fetch, no loading boolean, no refetch after submit. The form is progressive — it works without JavaScript, because a plain <form action> posts to the server and the server re-renders.

The App Router derives your URL structure from the folder tree. Almost every routing question — nesting, layouts, parallel routes, modals — is answered by knowing the file conventions.

File conventions

In the App Router, a filename is a declaration. page.tsx creates a URL; a layout, a template and a route handler each answer one question; everything else in app/ is inert.

The special files, in three groups

Group one makes URLs: page.tsx (UI) and route.ts (handler) — never both in one folder. Group two wraps UI: layout.tsx, template.tsx, loading.tsx, error.tsx, not-found.tsx. Group three is adjuncts: default.tsx for parallel slots, redirect.ts for server-side redirects, middleware.ts at the root for pre-route logic. Knowing which group a file belongs to explains most "why is this not a route?" confusion.

app/
  page.tsx        route - UI
  route.ts        route - handler; a folder cannot define BOTH
  layout.tsx      shared chrome, persists across navigations
  template.tsx    chrome that REMOUNTS on each navigation (analytics)
  loading.tsx     automatic Suspense fallback for the segment
  error.tsx       per-segment error boundary ('use client')
  not-found.tsx   the segment's 404
  default.tsx     parallel-route fallback (see ch5-parallel)
  redirect.ts     server-side redirect, no component

Layouts persist; templates remount

This one behavioural difference has the biggest consequences. A layout renders once and stays mounted across navigations inside it, so state it holds survives — a feature for a cart badge, a bug for a per-page form. A template renders again for every navigation, which is what you want for page-view analytics or scroll reset. Choose by asking: should this re-run when the URL changes?

// app/products/layout.tsx - rendered once, reused across /products/*
export default function ProductsLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="products-shell">
      <ProductNav />              {/* stays mounted while children swap */}
      {children}
    </div>
  );
}
// any state in ProductNav survives navigation between product pages
// these filenames have meaning. Nothing else in app/ is special.
app/
  layout.tsx        wraps its segment and all children; ONE root, renders html+body
  page.tsx          makes the segment a route
  loading.tsx       Suspense fallback for this segment, automatic
  error.tsx         error boundary for this segment; MUST be 'use client'
  global-error.tsx  catches root layout errors; replaces the root layout
  not-found.tsx     404 UI, used by notFound()
  template.tsx      like layout.tsx but REMOUNTS on navigation
  route.ts          an HTTP endpoint, no UI
  default.tsx       fallback for parallel routes
  redirect.ts       a redirect, server-side
  middleware.ts     runs before routing

// the four you will use daily
layout.tsx  page.tsx  loading.tsx  error.tsx

One rule about nesting worth internalising: layout.tsx does not re-render on navigation. It renders once and persists. That is why a layout must not hold per-page state, and why state in a layout survives navigation — a feature for a cart, a bug for a form.

Dynamic segments

[name] matches exactly one URL segment and binds it to a route parameter. In Next 15 that parameter arrives as a Promise, which makes optional handling and generateMetadata explicit.

params is a Promise in 15

params — and searchParams on pages — are Promises in Next 15, so the component awaits them before use. Awaited separately they serialise time; awaited together they resolve in parallel. The type tells the truth about the shape: Promise<{ id: string }> for a single [id] segment.

export default async function Page({
  params,
  searchParams,          // also a Promise on pages
}: {
  params: Promise<{ id: string }>;
  searchParams: Promise<{ tab?: string }>;
}) {
  const [{ id }, { tab }] = await Promise.all([params, searchParams]);
  return <Panel id={id} tab={tab ?? 'overview'} />;
}

Pre-render the known set

generateStaticParams lists the parameter values that exist at build time, so Next.js prerenders those pages and renders the rest on demand. With dynamicParams = false, unknown values 404 instead of rendering on demand — visible, predictable, and usually what a catalogue wants.

export const dynamicParams = false;      // unknown ids -> 404, no on-demand render

export async function generateStaticParams() {
  const slugs = await db.post.findMany({ select: { slug: true } });
  return slugs.map((s) => ({ slug: s.slug }));   // page.tsx receives { slug }
}
// [id] matches one segment
// app/blog/[slug]/page.tsx   ->  /blog/anything-here

Catch-all and optional segments

[...name] eats one or more segments; [[...name]] eats zero or more. Catch-alls are the natural home for docs trees and CMS-driven paths — and the shape that most often invites path traversal.

Three widths, one mechanic

[a] matches exactly one segment; [...a] matches one or more; [[...a]] matches zero or more, which means it also renders the base URL that a plain catch-all 404s on. The parameter arrives as string[], so /docs/guides/routing yields ['guides', 'routing'].

// app/docs/[...path]/page.tsx
export default async function Page({ params }: { params: Promise<{ path: string[] }> }) {
  const { path } = await params;
  // /docs/a           -> ['a']
  // /docs/a/b/c       -> ['a','b','c']
  return <Doc path={path} />;
}

// app/docs/[[...path]]/page.tsx - also matches /docs itself
export default async function Page({ params }: { params: Promise<{ path?: string[] }> }) {
  const { path = [] } = await params;
  return path.length ? <Doc path={path} /> : <DocsIndex />;
}

Treat the array as untrusted

A segment of .. — raw or percent-decoded — can escape the intended directory if you build a file path by joining segments. Reject suspicious segments, resolve the result against the root, and assert containment before reading. The check is two lines and it closes the whole class of bug.

import { resolve } from 'node:path';

export async function loadDoc(path: string[]) {
  if (path.some((seg) => seg === '..' || seg.includes('/') || seg.includes('\\'))) {
    throw new Error('bad path');
  }
  const file = resolve(DOCS_ROOT, ...path);
  if (!file.startsWith(DOCS_ROOT)) throw new Error('escape blocked');
  return fs.readFile(file, 'utf8');
}
// [slug]      one segment       /blog/a
// [...slug]   one or more        /blog/a/b/c
// [[...slug]] zero or more       /blog  and  /blog/a/b

export default async function Page({ params }: { params: Promise<{ path: string[] }> }) {

  // /docs/guides/routing/layouts -> path = ['guides','routing','layouts']

}

// /shop/colour/red/size/l   -> filters = ['colour','red','size','l']

Path traversal in a dynamic route is a real vulnerability, not a theoretical one. A segment of ..%2F..%2Fetc%2Fpasswd or a decoded .. in the array can escape the intended directory. Always resolve and then assert the result is still inside the root.

Route groups

(folder) segments organise the tree without appearing in URLs. Their whole purpose is to attach a different layout to a subset of routes at the same depth.

URLs are unchanged by design

A group contributes nothing to the path — app/(marketing)/about/page.tsx is simply /about. Because groups are invisible in URLs, they cannot fix path collisions: two routes resolving to the same URL are a build error, which is the framework refusing ambiguity instead of picking one silently. Groups are for chrome, not for aliasing.

Parallel routes and slots

Parallel routes let one URL render several independent segments at once, and give you named slots to place them.

Slots render independently

Each @name folder maps to a named prop in the segment's layout — children is just the default slot. Each slot navigates independently: a modal can change its slot's content while the page slot beneath stays mounted, which is how the URL changes without the page behind a dialog unmounting.

// app/dashboard/layout.tsx
export default function DashboardLayout({
  children,          // the page slot
  activity,          // the @activity slot
}: {
  children: React.ReactNode;
  activity: React.ReactNode;
}) {
  return (
    <div className="dashboard">
      <main>{children}</main>
      <aside>{activity}</aside>
    </div>
  );
}

default.tsx is the fallback for unmatched slots

A hard refresh, a direct link or a back navigation can reach a URL that only some slots match — and every slot must render something. default.tsx is that something. Forgetting it turns an innocuous refresh into a 404 that makes no sense to the user; each slot should carry one.

// app/dashboard/@activity/default.tsx - what the slot shows when the URL
// matches no @activity route (e.g. a hard refresh of /dashboard/settings)
export default function Default() {
  return <aside><p>No activity for this view.</p></aside>;
}

Intercepting routes

An intercepting route renders a different route's UI in place — usually a modal — when the navigation is client-side, while the real route still serves the full page on a direct load. The mechanism lives entirely in the folder name.

The four matchers, read as sentences

The (...) group tells Next.js which level of the tree to look up when resolving a client navigation. (.) matches the current level, (..) one level up, (..)(..) two levels up, and (...) from the app root. When you write app/@modal/(.)photos/[id]/page.tsx, the (.) says "resolve photos/[id] at the level of the folder that contains @modal". The matcher is a relative path, not a fixed keyword — move the slot and the prefix moves with it.

// the folder prefix IS the matcher. It sits between the slot and the path.
app/
  @modal/
    (.)photos/[id]/page.tsx      // same level as @modal's parent
    (..)dashboard/[id]/page.tsx  // one level up from the slot
    (...)login/page.tsx          // from the app root, any depth

// keep the slot (@folder) at the same level as the route it overlays.
// declared too deep it still compiles, but (.) no longer resolves where
// you expect and the interception silently stops happening.

Interception is a soft-navigation-only trick

Interception fires only for client-side navigation. A hard refresh, a shared URL or a crawler request resolves the real route and renders the full page — which is exactly what makes the pattern safe. The modal is a progressive enhancement: the content is a real, linkable page first, and the overlay is added when JavaScript navigates to it. Because of that, the intercepted page must offer a way out that also works when it is loaded directly.

// the close control must work in both states

    </button>

Programmatic navigation

Most navigation in an App Router app is declarative, through <Link>. The imperative API exists for the moments a link cannot express, and knowing which of the three tools to reach for keeps the client bundle small and the intent obvious.

Reach for Link first, the router second

<Link> is the declarative default and should be the first tool you reach for. It prefetches, it works without JavaScript, and it participates in the router cache. router.push from useRouter exists for the cases a link cannot express: after a form submission, inside a callback, or conditional on state. For a server decision there is neither — call redirect(), which needs no client JavaScript at all.

// 1. declarative -- works with JS disabled, prefetched
import Link from 'next/link';
<Link href="/products">Products</Link>;

// 2. imperative -- only when a link cannot be used
'use client';
import { useRouter } from 'next/navigation';
const router = useRouter();
async function onSubmit() {
  await save();
  router.push('/products/123');   // navigate after an event
}

// 3. redirect on the server -- no client bundle involved
import { redirect } from 'next/navigation';
export default async function Page() {
  const user = await getUser();
  if (!user) redirect('/login');
  return <Dashboard user={user} />;
}

The four navigation hooks

next/navigation ships four hooks you will use constantly: useRouter for the imperative methods, usePathname for the current path, useSearchParams for the query string, and useParams for the dynamic segments. All four are client hooks. useSearchParams is the one that bites — it suspends, so during static rendering it must sit under a <Suspense> boundary or the whole route is treated as dynamic.

'use client';
import {
  useRouter, usePathname, useSearchParams, useParams,

export function Filters() {
  const router = useRouter();
  const pathname = usePathname();      // '/products'

  const params = useParams();          // { id: '42' } from [id]

    const next = new URLSearchParams(search);
    next.set('sort', value);
    router.replace(`${pathname}?${next.toString()}`);
  }

  return <select onChange={(e) => setSort(e.target.value)}>...</select>;
}

Link prefetching

Next.js prefetches links that enter the viewport, turning a click into an instant swap when it can. Understanding what is actually prefetched — and when to stop it — is the difference between a snappy app and a thousand wasted requests.

What actually gets prefetched

A <Link> in the viewport triggers a prefetch. What arrives depends on the route: a static route downloads the full RSC payload, while a dynamic route fetches only the reusable part above the nearest loading.tsx — the static shell. That is why adding a loading.tsx makes a dynamic route perceptibly faster to navigate to: it gives Next.js something cacheable to prefetch in advance.

// static route: the whole payload is prefetched
// app/about/page.tsx
export default function About() { return <h1>About</h1>; }

// dynamic route: only the shell above loading.tsx is prefetched
// app/reports/page.tsx
export const dynamic = 'force-dynamic';

// app/reports/loading.tsx -- the boundary that makes it worthwhile
export default function Loading() { return <ReportSkeleton />; }

// without a loading boundary a fully dynamic route has little to
// prefetch, so the navigation falls back to fetching on click.

When to turn prefetching off

Prefetching is not free: every link in the viewport is a request. A list of a thousand rows prefetches a thousand routes. Turn it off with prefetch={false} on links you do not expect most users to follow — admin pages, a "generate report" action, anything behind a paywall. When you want the benefit without the blanket cost, prefetch on intent instead, from onMouseEnter.

// a long list: opt out of per-row prefetching
{items.map((item) => (
  <Link key={item.id} href={`/items/${item.id}`} prefetch={false}>
    {item.name}
  </Link>
))}

// prefetch on intent instead: the user is clearly heading there
'use client';
import { useRouter } from 'next/navigation';
const router = useRouter();
<Link
  href="/report"
  prefetch={false}
  onMouseEnter={() => router.prefetch('/report')}
>
  Generate report
</Link>

// static routes that is the full HTML; for dynamic routes it is the
// RSC payload up to the nearest loading.tsx boundary, split into a
// static shell and a dynamic part.

// app/reports/page.tsx

// prefetches nothing for a dynamic route, because it cannot know how
// much of the payload is reusable.

If a navigation feels slow and the Network panel shows no request, the route's RSC payload was already prefetched and it is rendering on the client — the cost is then a client render, not a round trip. If you see a request, it was not prefetched. That distinction tells you which problem you have.

Rewrites, redirects and middleware

Rewrites, redirects and middleware all run before your page does, and choosing between them is a question of when the decision can be made. Static rules run at config time, middleware runs on every request, and the route itself has full Node access.

Where each rule belongs

There are three places to put request-time logic, and picking the wrong one is a common source of latency. Static rewrites and redirects in next.config.js are evaluated cheaply and never run code per request. Middleware runs on the edge for every matched request and is right for auth gates, A/B assignment and setting headers. Anything that needs a database or Node APIs belongs in the route itself, not in middleware.

// next.config.js -- cheapest; no request-time code
export default {
  async redirects() {
    return [{ source: '/blog', destination: '/news', permanent: true }];
  },
  async rewrites() {
    return [{ source: '/docs/:path*', destination: '/documentation/:path*' }];
  },
};

// middleware.ts -- per-request, edge runtime
export { default } from './lib/auth-middleware';
export const config = { matcher: ['/dashboard/:path*'] };

// the route itself -- Node runtime, database allowed
export default async function Page() {
  const posts = await db.post.findMany();   // never in middleware
  return <Feed posts={posts} />;
}

What middleware must not do

Middleware runs before routing, on a runtime without Node's full API surface, and on every matched request. Keep it to cheap, stateless decisions: reading a cookie, checking a signed token, rewriting or redirecting, and copying request headers forward. Do not query a database, parse large bodies or block on remote calls — the latency is paid on every request, including the ones that turn out to be for a static asset.

// good: a cheap gate that also forwards a header to the route
import { NextResponse, type NextRequest } from 'next/server';

export function middleware(req: NextRequest) {
  const session = req.cookies.get('session')?.value;
  if (!session && req.nextUrl.pathname.startsWith('/dashboard')) {
    const url = new URL('/login', req.url);
    url.searchParams.set('next', req.nextUrl.pathname);
    return NextResponse.redirect(url);       // no database call here
  }
  const headers = new Headers(req.headers);
  headers.set('x-user', session ? 'authenticated' : 'guest');
  return NextResponse.next({ request: { headers } });
}

  if (token && pathname === '/login') {
    return NextResponse.redirect(new URL('/dashboard', req.url));
  }

  // a request header the server can read
  const headers = new Headers(req.headers);
  headers.set('x-pathname', pathname);
  return NextResponse.next({ request: { headers } });
}
