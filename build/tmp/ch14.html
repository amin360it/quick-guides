Suspense and transitions are two answers to the same question: what does the user see while work is still happening. Suspense draws the line on the screen — here is pending, here is content. Transitions draw the line in time — this update can wait so that one cannot. Used together they are what makes a React app feel deliberate rather than jumpy.

Boundaries and where they go

A Suspense boundary is a promise from the layout to the user: everything below this point may be temporarily unavailable, and when it arrives it will appear in place, without moving what is already on screen. The boundary is what makes that promise enforceable — a component below it may suspend (from use, from a framework data hook, from React.lazy) and React replaces only that subtree with the fallback, keeping the rest of the page mounted, interactive and holding its state. Without a boundary the suspension travels to the root, and the whole screen goes to fallback, which is the failure mode people mean when they say Suspense caused flicker.

Placement therefore follows the layout, not the data. Put a boundary around each independently-arriving region — the sidebar, the table, the chart panel — so each one can resolve on its own schedule, and put none around regions that must arrive together or that are above the fold as a unit, because a boundary inside a region that needs all its children at once just moves the wait without shortening it. A useful test: cover the region with your hand and ask whether the rest of the screen is still usable if it is missing. If yes, it wants a boundary. If no, the boundary belongs higher.

// one boundary per independently-arriving region
function Dashboard({ reportPromise, activityPromise }) {
  return (
    <div className="grid">
      <Header />                                   {/* never suspends */}
      <Suspense fallback={<ReportSkeleton />}>
        <Report promise={reportPromise} />        {/* its own boundary */}
      </Suspense>
      <aside>
        <Suspense fallback={<ActivitySkeleton />}>
          <Activity promise={activityPromise} />  {/* resolves independently */}
        </Suspense>
      </aside>
    </div>
  );
}

// WRONG: one boundary at the root -> a pending sidebar blanks the report
function BadDashboard(props) {
  return <Suspense fallback={<PageSkeleton />}><Dashboard {...props} /></Suspense>;
}

Boundaries compose, and nesting them is how you get granularity without losing the coarse safety net: a page-level boundary catches everything, regional boundaries inside it catch their own subtrees first. The innermost boundary wins, so the finer ones should sit lower. One structural rule keeps this maintainable: a boundary should be rendered by the component that owns the region's layout, not by the component that performs the fetch. A boundary embedded deep inside a data-owning component couples fallback presentation to data plumbing, and the moment you want a different skeleton for a different context you have to move it anyway.

// boundaries owned by layout, data owned by leaves
function SettingsPage() {
  return (
    <section>
      <h2>Notifications</h2>
      {/* layout decides this region exists and how it looks while pending */}
      <Suspense fallback={<SettingsRowSkeleton rows={3} />}>
        <NotificationSettings />     {/* leaf decides HOW to fetch */}
      </Suspense>
    </section>
  );
}

function NotificationSettings() {
  const prefs = use(preferencesPromise);   // suspends; the boundary above pays
  return <PreferenceList prefs={prefs} />;
}

The state-preserving property

When a subtree suspends behind an already-mounted boundary, React does not unmount the existing content — it keeps showing the current content while the new data loads, and swaps when ready. That is the behaviour that makes transitions feel smooth, and it only exists if the boundary is already mounted when the suspension happens. A boundary rendered for the first time at the same moment as the suspending child has nothing to keep showing, so its fallback appears: the flicker case. Ensure boundaries mount before the data they guard, which in practice means the boundary lives in the initial render of the region and the fetch is triggered after.

Suspense is a rendering contract, not a loading contract: it says "this subtree is not ready", and whether that means fetching, a slow computation, or a lazy chunk download is the caller's business. This is why the same boundary covers a data hook and a React.lazy import without knowing which is inside.

Fallbacks that do not lie

A fallback is shown for an unknown duration, so its job is to communicate structure and ownership, not progress. The worst fallback is a spinner on an empty page: it says nothing about what is coming, and the moment the content arrives — often at a different height — the entire layout jumps. The second worst is a perfect skeleton of the loaded content, because if the real content differs in shape the skeleton was a promise broken. The right fallback mirrors the structure of the region at roughly its final size, without pretending to know the values.

Layout stability is the measurable part. Give the fallback the same footprint the content will occupy — same grid, same row count where it is predictable, same minimum height — so that arrival causes zero reflow of surrounding regions. The test is a screenshot comparison with the network throttled: a good fallback and the loaded state should differ in texture, not in geometry. Beyond geometry, fallbacks owe the user two things: they must not remove interactive chrome that does not depend on the pending region (a page title, a back button, a search field that searches something else), and they must not trap focus or steal it — a fallback that renders a button the content will not have is a focus trap waiting to snap shut.

// fallback that keeps the geometry: same grid, same row heights
function Panel({ children }) {
  return (
    <div className="panel-grid">
      <Suspense
        fallback={
          <div className="panel-grid" aria-busy="true">
            {/* same class as the loaded content: identical layout box */}
            {Array.from({ length: 6 }, (_, i) => (
              <div key={i} className="panel-cell panel-cell--pending" />
            ))}
          </div>
        }
      >
        {children}
      </Suspense>
    </div>
  );
}

// the loaded content uses the same panel-grid / panel-cell classes,
// so arrival swaps texture, not geometry - zero layout shift.

Announce the pending state to assistive technology without turning every refresh into noise. Marking the region aria-busy="true" while the fallback shows is the structured signal; a live-region announcement ("Loading report") is appropriate the first time a region loads and irritating on every refetch. The distinction mirrors the visual one: a first load is new content appearing, a background refresh is content being maintained. Design the fallback for both cases rather than only the first — a region that goes blank on every refetch teaches users not to trust it.

// announce the first load, stay quiet on background refresh
function AnnouncedRegion({ promise, firstLoad, children }) {
  return (
    <section aria-busy="true"
             aria-live={firstLoad ? 'polite' : 'off'}
             aria-label="Report">
      <Suspense fallback={<ReportSkeleton />}>{children}</Suspense>
    </section>
  );
}

// and never use the fallback for a REFRESH: under a transition, React keeps
// the current content mounted while the new data loads (next section), so
// the skeleton only ever appears once per region, at first mount.

What a fallback must never contain

Interactive controls whose behaviour depends on the pending content — a submit button for a form that has not loaded, a filter for a table that does not exist yet, a link to a detail view you cannot address. Focus can land on these, activation does nothing or throws, and the user has no way to know why. Static presentation, a status message, and the chrome that stands on its own are all fine; anything that accepts input must either work or be visibly disabled with the disabled reason stated.

A fallback rendered by a region that suspends on every keystroke — the anti-pattern of fetching in render without a transition — turns the skeleton into a strobe. If your fallback appears repeatedly rather than once, the fix is not a subtler fallback; it is chapter 14's transitions: the update causing the suspension must be marked as non-urgent.

Transitions: urgent versus predictable

React 18 divided updates into two kinds: urgent, which the user expects to see immediately (typing, clicking, dragging — the element under the pointer must respond in this frame), and transitional, which the user expects to settle rather than instantaneously appear (filtering a large list, opening a detail view whose data is loading, navigating). startTransition marks a state update as the second kind: React may interrupt it, render it at lower priority, and — critically — keep the current content on screen while it completes instead of dropping to a fallback. The API is two lines; the semantics it activates are the whole of concurrent rendering's user-facing value.

The signature behaviour worth internalising: if a transition's render suspends, React keeps showing the old UI until the new one is ready, even though the state has already changed. That is the difference between a search box that blinks a skeleton per keystroke and one that shows results the moment they are ready while you keep typing. And if a newer urgent update arrives mid-transition, React discards the transition's progress and starts again from the new state — transitions are interruptible, which is exactly why typing during a slow filter never feels locked. The rule for when to use one follows from the two categories: wrap the update if the user would accept waiting; do not wrap it if the user would be surprised that nothing happened.

// urgent: the input must repaint THIS frame
function SearchBox({ query, onQuery }) {
  return <input value={query} onChange={(e) => onQuery(e.target.value)} />;
}

function Results({ query }) {
  const [rows, setRows] = useState([]);
  const [pending, startTransition] = useTransition();

  function handleChange(next) {
    // urgent half: the input is controlled by query state in the PARENT,
    // which updates immediately...
    onQuery(next);
    // transitional half: the expensive derived list can wait and be
    // interrupted if the user keeps typing
    startTransition(() => {
      setRows(filterHugeList(next));
    });
  }

  return (
    <>
      <SearchBox query={query} onQuery={handleChange} />
      {pending && <span role="status">Filtering…</span>}
      <List rows={rows} />
    </>
  );
}

Transitions pair with Suspense to produce the behaviour that defines the modern React feel: inside a transition, a suspending render does not show the fallback — it waits. This is the single most useful fact in this chapter, because it converts a design decision (skeleton or keep-current-content?) from a per-component judgement into a property of how the update was scheduled. Refetching a panel after a mutation: transition it, and the panel keeps its old values until the new ones arrive. Navigating to a route whose data is loading: transition it, and the current page stays while the next one prepares.

// refetch under a transition: old content stays until new arrives
function ProjectView({ projectId }) {
  const [project, setProject] = useState(null);
  const [pending, startTransition] = useTransition();

  useEffect(() => {
    startTransition(async () => {           // async transition body
      setProject(await api.getProject(projectId));   // suspends internally
    });                                          // no fallback shown: the
  }, [projectId]);                               // PREVIOUS project stays
                                                 // visible the whole time
  if (!project) return <InitialSkeleton />;   // only for the very first load

  return (
    <>
      {pending && <span role="status">Updating…</span>}
      <Project project={project} />
    </>
  );
}

What not to transition

Do not transition the urgent half of an interaction. A controlled input whose value only updates inside a transition will lag behind the keystrokes, because urgent typing updates must never queue behind a long render — that is precisely the responsiveness guarantee transitions are built to sacrifice for everything else. Likewise, do not transition a state update that toggles something the user is pointing at: a button that goes unpressed after a delay feels broken even when the work behind it succeeds. Split the update: the pointer-visible state updates immediately, the expensive dependent state transitions.

Expose transition pending state to the user as a status, not a blocking overlay. useTransition's pending flag drives a subtle "Filtering…" label or an aria-busy attribute — enough to explain why results lag, never enough to stop the user typing. If your instinct is a spinner over the list during a transition, the update probably should not have been a transition; it should have been urgent.

useDeferredValue and stale input

useDeferredValue is the read-side counterpart of a transition: given a value, it returns that value immediately on the urgent render and a deferred, possibly-stale copy during subsequent low-priority renders. Where startTransition wraps the state update, useDeferredValue wraps the consumption — which makes it the tool for the cases you do not control the update, because it arrives as a prop from a parent, a URL parameter, or a store. The component stays responsive by rendering with last frame's value while the new one catches up.

The comparison that matters: an input with a derived expensive list has two legitimate designs, and both use the same primitive from opposite ends. If you own the state, split it — urgent input state, transitioned derived state, as in the previous section. If you receive the value as a prop, defer it inside the component — render the input from the prop directly and the list from the deferred copy. Both produce the same frame timing: keystroke paints now, expensive subtree reconciles later. The second is often necessary precisely because the parent that owns the value is far away, and threading a transition down to it would couple a leaf's performance needs to an ancestor's API.

// the value arrives from a parent you do not control - defer the read
function BigFilter({ query }) {
  const deferredQuery = useDeferredValue(query);
  const pending = query !== deferredQuery;

  // the input renders from the REAL value: every keystroke paints immediately
  // the expensive subtree renders from the DEFERRED value: it may lag a frame
  const rows = useMemo(() => filterHugeList(deferredQuery), [deferredQuery]);

  return (
    <>
      <input readOnly value={query} />
      {pending && <span role="status">Updating results…</span>}
      <List rows={rows} />
    </>
  );
}

// equivalent timing, opposite control: you own the state, so split it
function OwnsState({ onQuery }) {
  const [query, setQuery] = useState('');
  const [rows, setRows] = useState([]);
  const [, startTransition] = useTransition();
  return <input onChange={(e) => {
    setQuery(e.target.value);                          // urgent
    startTransition(() => setRows(filterHugeList(e.target.value)));
  }} />;
}

Two traps. First, the stale value must be safe to render: if the deferred list is keyed by a value that the urgent render has already moved past — a selected row id that no longer exists in the stale array — you get an index or lookup error precisely during the frames the user is watching. Guard the derived render against staleness (a null check, a "no longer available" state) rather than assuming the two copies agree. Second, using the deferred value as a dependency of anything imperative — an effect that fetches, a subscription that re-registers — reintroduces the lag into a path that cannot skip frames; defer reads for rendering, keep effects on the urgent value.

// staleness is visible: the selection may point outside the deferred list
function Picker({ query }) {
  const deferred = useDeferredValue(query);
  const results = useMemo(() => search(deferred), [deferred]);
  const [selectedId, setSelectedId] = useState(null);

  // results lags query; selectedId may reference a row not in results yet
  const selected = results.find((r) => r.id === selectedId);

  return (
    <>
      <List rows={results} onSelect={setSelectedId} />
      {/* guard the render: do not assume the two copies agree */}
      {selected
        ? <Detail row={selected} />
        : <p role="status">Selecting…</p>}
    </>
  );
}

Measuring the deferral

Confirm the win the same way chapter 11 confirms anything: with the profiler, before and after, on the real interaction. The signature of a correct useDeferredValue adoption is that the urgent input's commit stays under a few milliseconds while the deferred subtree's render moves out of the keystroke's frame — visible as input-handler work shrinking and a second, lower-priority render appearing afterwards. If both renders are still in the same frame, the deferred work is not the bottleneck and the technique bought you an extra render for nothing.

Deferral and transitions are alternatives, not layers: pick one owner for "this update is non-urgent" per interaction. Running both — a transitioned update whose consumer also defers — doubles the lag between what the user did and what they see, and the extra staleness buys no responsiveness the first one did not already provide.

lazy, code splitting and keeping frames

React.lazy takes a function returning a dynamic import and produces a component that suspends until its chunk arrives — which means, with the previous sections in hand, that it is governed by a Suspense boundary like any other pending region. This is the mechanism behind route-level and widget-level code splitting in applications without a framework: the initial payload ships the shell and the first screen, and heavy secondary features — a charting library, a rich-text editor, an admin panel — download only when first rendered. The win is not bytes saved overall; it is bytes moved off the critical path of first interaction.

What makes splitting pay is choosing boundaries that match usage rather than files that match folders. Splitting every component is worse than splitting none: dozens of small requests, a waterfall of chunk discoveries, and worse total latency than one bundle. The right seams are where a usage pattern changes — the detail view behind a list row, the settings modal, anything behind an authenticated area — so that the common path loads one chunk more and the uncommon path loads its cost only when taken. The measurable targets are first-paint and time-to-interactive for the entry route; if a split moves those, it earned its place, and a bundle report in CI (chapter 11's budget) keeps it honest afterwards.

// route-level splitting: the shell never downloads the heavy panels
import { lazy, Suspense } from 'react';

const AdminPanel = lazy(() => import('./AdminPanel'));   // own chunk
const Reports    = lazy(() => import('./Reports'));      // own chunk

function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/" element={<Home />} />            {/* in the shell */}
        <Route path="/admin" element={<AdminPanel />} /> {/* on demand */}
        <Route path="/reports" element={<Reports />} />  {/* on demand */}
      </Routes>
    </Suspense>
  );
}

// WRONG: splitting every component - dozens of round trips, worse than one
const Button   = lazy(() => import('./Button'));
const Badge    = lazy(() => import('./Badge'));
const ListItem = lazy(() => import('./ListItem'));

Prefetching closes the gap between "split" and "split without the user noticing". If the shell can predict the next likely route — the item row that will be clicked, the nav link being hovered — it can start the dynamic import before navigation, so the transition resolves from cache instead of network. This is a small amount of code with a disproportionate effect on perceived speed: the split exists for the rare path, and prefetching makes the common transition to it indistinguishable from an unsplit bundle. React's own examples pair React.lazy with an intersection observer for exactly this, and any router worth using exposes a prefetch option on links.

// prefetch on intent: hover or viewport-entry starts the chunk download
const Reports = lazy(() => import('./Reports'));
let reportsStarted = false;
export function preloadReports() {
  if (reportsStarted) return;
  reportsStarted = true;
  import('./Reports');            // the same specifier -> the same chunk,
}                                 // now cached before anyone navigates

function NavReportsLink() {
  return (
    <Link to="/reports"
          onPointerEnter={preloadReports}
          onFocus={preloadReports}>
      Reports
    </Link>
  );
}

// viewport prefetch for content far down a long list
function useViewportPreload(ref, preload) {
  useEffect(() => {
    const io = new IntersectionObserver((entries) => {
      if (entries.some((e) => e.isIntersecting)) { preload(); io.disconnect(); }
    });
    if (ref.current) io.observe(ref.current);
    return () => io.disconnect();
  }, [ref, preload]);
}

Splitting, boundaries and state — the three regressions

Three ways a splitting pass makes an app worse, each with a distinct symptom. Losing state across a boundary: because a lazy subtree suspends, anything holding local state inside the shell but above the split point survives, while state inside the swapped subtree resets — so a form half-filled in a modal that lazy-loads must live in the store, not the modal. Chunk waterfalls: one lazy component importing another lazily serialises their downloads; check the network panel for chunks arriving in sequence. And duplicate vendors: two chunks each bundling their own copy of a library doubles its bytes across the session — the bundle report from chapter 11 catches this the week it happens, not the quarter after.

Never lazy-load the element that renders the fallback's destination — a lazy component with no Suspense boundary above it, or one placed above a boundary that itself suspends, produces an unhandled suspension that React resolves by unmounting to the root. Every React.lazy call needs a boundary that is guaranteed to be mounted before it, which in practice means the boundary sits in code that was in the initial bundle.

Exercises 14

  1. Draw your application's main screen as regions. Mark each one independently-arriving or all-or-nothing, then place Suspense boundaries accordingly and compare with where your data hooks currently suspend.
  2. Take a fallback that collapses the layout on load. Give it the content's geometry using shared classes and verify with before/after screenshots that arrival causes no reflow.
  3. Find a list that goes blank while filtering. Wrap the set in a transition, confirm the old rows stay visible, then confirm typing during the filter stays responsive in the profiler.
  4. Adopt useDeferredValue in a component that receives its query as a prop. Intentionally break it by selecting a row outside the deferred results, and fix the render with an explicit staleness guard.
  5. Split your heaviest secondary feature behind React.lazy, add prefetch on the entry link, and compare first-interaction timing and chunk requests against the unsplit build.
