Welcome — Software Architecture Design

How this guide is organisedWho this is for

Software architecture design is the high-level discipline of shaping a system so it stays changeable, scalable and understandable for years. It is practised by defining system structure, responsibilities and relationships up front, then letting quality attributes such as availability and performance make trade-offs explicit. Mature architects document these choices and revisit them as the system evolves.

A practical guide to designing software systems that stay changeable, scalable and understandable over years. Single file, offline, progress saved locally.

How this guide is organised

The guide is organised so time-poor readers can skip the linear read and jump straight to what they need. Chapters cluster into five bands: foundations, design patterns, architectural styles, distributed systems and non-functional properties, finishing with a worked case study and appendices. Each chapter builds on earlier material while remaining usable on its own.

  • Foundations (Ch. 1–4) — what architecture is, quality attributes, modularity, and core design principles.
  • Patterns & styles (Ch. 5–7) — design patterns, architectural styles, and monolith vs services.
  • Distributed systems (Ch. 8–11) — event-driven design, DDD, data consistency, APIs.
  • Non-functionals (Ch. 12–14) — scalability, reliability, security.
  • Practice (Ch. 15–17) — documentation, evaluation, and a worked case study.

Architecture is the set of decisions that are expensive to change. Everything else is just code. Spend your effort on the expensive decisions.

Who this is for

This material targets developers moving into senior or lead positions, and tech leads who must choose and defend a system’s shape. It assumes you can already code and reason about everyday design, then adds the bigger-picture skills of making structural decisions, balancing trade-offs and communicating them. At the end you should be able to own an architecture, not just contribute to one.

Developers growing into senior/lead roles, tech leads, and anyone who must choose how to structure a system and defend the choice.

1 · What Architecture Is

1.1 A working definition1.2 Quality attributes drive structure1.3 Everything is a trade-off

This chapter defines what architecture is and argues that quality attributes, not features, shape a system’s structure. Architects translate non-functional requirements into structural decisions such as module boundaries, communication style and data ownership. Every decision trades one attribute for another, so the aim is to make the trade-off visible rather than to search for a free lunch.

1.1 A working definition

Architecture is the set of structural decisions that are expensive to change later: the organisation of a system into components, their relationships, their responsibilities and the guiding principles that govern evolution. It is driven by non-functional attributes such as scalability, availability and security. Keep the definition practical so it stays usable as a basis for reviews, trade-off analysis and decision records.

Architecture is the structure of a system: its components, their responsibilities, their relationships, and the principles that guide its evolution. It is shaped by quality attributes (the "-ilities"), not by features.

1.2 Quality attributes drive structure

Quality attributes such as scalability, availability, performance and security are what genuinely push a system into a particular shape, while features merely exercise that shape. In practice the architect derives scenarios for each attribute, weights them against business goals and lets the conflicts between them surface structural decisions. Features are easy to add to a shape that the attributes have already justified.

AttributeQuestion
ScalabilityCan it handle 10× load?
AvailabilityWhat happens when a node dies?
MaintainabilityHow fast can we add a feature?
PerformanceWhat is the p99 latency?
SecurityWho can do what, and is it audited?
TestabilityCan we verify a change safely?
DeployabilityHow often can we ship?

1.3 Everything is a trade-off

Every architectural decision trades one quality attribute for another, so there is no universally correct answer, only answers that fit the current goals. The discipline is to name the trade-off explicitly, record why one side won and what it cost. Doing this makes decisions reviewable and prevents later collaborators from silently reversing choices they do not understand.

There is no "best" architecture, only trade-offs against constraints. Adding a cache improves latency and hurts consistency. Adding a queue improves resilience and adds complexity. Name the trade-off or you have not made a decision.

Beware architecture astronauts: complexity that serves the résumé rather than the requirements. The simplest structure that meets the quality attributes wins.

// The same feature, three valid architectures, three different costs.

// Option A: simplest thing that works
public class OrderService
{
    private readonly AppDbContext _db;
    public OrderService(AppDbContext db) => _db = db; // one dependency, easy to test

    public async Task<Order> PlaceAsync(PlaceOrderCommand cmd, CancellationToken ct)
    {
        var order = new Order(cmd.CustomerId, cmd.Lines);
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
        return order;
    }
}

// Option B: same behaviour, one extra seam for auditing and retries
public interface IOrderRepository { Task<Order> AddAsync(Order o, CancellationToken ct); }
public interface IUnitOfWork    { Task SaveAsync(CancellationToken ct); }

// Option C: same behaviour, extracted behind a queue for independent scaling
// _outbox.Enqueue(new OrderPlaced(order.Id));  then a worker consumes it

// None is "wrong". Pick the one your current constraints justify.

One feature, three architectures. A is cheapest to build and hardest to evolve, C is most scalable and most expensive to operate. Architecture is the deliberate choice among these, not the automatic result.

2 · Architectural Thinking

2.1 Separating concerns2.2 Where to draw boundaries2.3 Constraints and forces

Architectural thinking is the mindset of seeing systems at the level of capabilities and boundaries rather than individual features. Practitioners separate concerns, identify the seams where volatility, ownership and scaling differ and draw boundaries along those lines. Tools of the trade include domain analysis, context mapping and cost-of-change reasoning to keep each piece independently evolvable.

2.1 Separating concerns

Separating concerns means dividing a system so that things that change together stay together and things that change for different reasons do not. In practice you group code by capability or business behaviour rather than by technical layer, and you refuse coupling between unrelated concerns, however convenient shared objects might look. The result is that a change in one area needs few or no edits elsewhere.

Group things that change together and separate things that change for different reasons. A billing rule and a PDF renderer are different concerns even if they touch the same object.

2.2 Where to draw boundaries

Good boundaries are drawn where business capabilities, change volatility, data ownership or scaling needs differ between parts of the system. Each bounded piece then owns its data, its model and its lifecycle and can evolve independently. In practice the architect maps these seams early, since moving a boundary after systems are built is far more expensive than drawing it right the first time.

  • By business capability (Orders, Billing, Shipping) — aligns with org and change.
  • By volatility — keep fast-changing policy away from stable mechanics.
  • By data ownership — the component that writes the data owns it.
  • By scaling need — isolate what must scale independently.
Good boundary: Order placement changes with pricing & promotions.
Bad boundary:  "Database layer" and "Business layer" — every feature
               crosses both, so they change together (low cohesion).

A capability-aligned boundary keeps change local; a generic layer split forces every feature to cross both layers.

2.3 Constraints and forces

Constraints act as fixed forces that shape the architecture as strongly as the stated requirements. They include team size and skill mix, budgets, regulation and compliance, existing systems that must integrate and organisational structure. The architect lists them explicitly at the start, because a design that ignores a hard constraint will be redesigned by reality later.

ForceShapes
Team size & skillsConway’s Law: systems mirror communication
Delivery timelineBuild vs buy, monolith vs services
RegulationData residency, audit, encryption
Existing systemsIntegration and migration strategy
Budget/opsManaged services vs self-hosted

3 · Modularity, Coupling & Cohesion

3.1 Cohesion: how focused a module is3.2 Coupling: how much modules depend on each other3.3 Interfaces, contracts and the Dependency Rule

This chapter covers modularity through the two measures that decide whether software ages gracefully: cohesion and coupling. High cohesion keeps each module focused on one job, and low coupling keeps dependencies between modules loose and explicit. Architects apply interface contracts and dependency rules so modules can change independently and be tested in isolation.

3.1 Cohesion: how focused a module is

Cohesion is how well the things inside a module belong together, and high cohesion means the module has one clear responsibility. The classic warning sign is a grab-bag class or module named Utils that accumulates unrelated functions over time. In practice you refactor such modules constantly, grouping functions by the behaviour or data they serve.

High cohesion means everything in a module serves one purpose. A class called Utils is the classic symptom of low cohesion.

3.2 Coupling: how much modules depend on each other

Coupling is the degree to which modules depend on one another, and it determines how easily a change in one module forces changes elsewhere. Dependencies on data types and stable interfaces are healthy; dependencies on shared global state or implementation details are not. Architects reduce coupling by inverting dependencies, publishing contracts and keeping communication through narrow, explicit interfaces.

Coupling typeQuality
Data (passing primitives)Best
Message/interfaceGood
Control (passing flags)Poor
Global/static stateWorst
// Tight coupling: caller knows internals
// Loose coupling: caller depends on an interface
interface Notifier { void Send(string to, string msg); }

class OrderService { // wiring happens here, once
    private readonly Notifier _notifier;   // depends on abstraction
    public OrderService(Notifier notifier) => _notifier = notifier;
}

A service depends on an interface instead of a concrete class, so wiring happens once at construction and the rest of the code stays decoupled.

3.3 Interfaces, contracts and the Dependency Rule

Interfaces, contracts and the Dependency Rule keep modules stable by directing how they depend on each other. The rule, captured in the Clean Architecture school of thought, says dependency arrows always point inward, so the domain model depends on nothing while infrastructure depends on abstractions it implements. Applying it means defining interfaces for databases, queues and services inside the domain and reversing the direction of implementation.

Depend on abstractions, not concretions. Inner (domain) code must not know about outer (database, UI) code. All dependencies point inward.

4 · Design Principles

4.1 SOLID4.2 Other durable principles

This chapter collects the durable design principles that keep code changeable over years rather than weeks. SOLID provides the five structural rules that remove the most common failure modes, while classic heuristics such as DRY, KISS and composition over inheritance restrain ambition. The principles are decision aids, not dogma, and are applied together when designing modules and their relationships.

4.1 SOLID

SOLID is five rules, each aimed at removing one common failure mode: single responsibility limits reasons to change, open-closed supports extension without modification, Liskov substitution keeps inheritance safe, interface segregation avoids fat contracts and dependency inversion points dependencies at abstractions. Applied together they make code more testable and less rigid. The rules operate as design checklists rather than mechanical formulas.

PrincipleMeaning
S — Single ResponsibilityA module has one reason to change.
O — Open/ClosedOpen to extension, closed to modification.
L — Liskov SubstitutionSubtypes must be usable as their base type.
I — Interface SegregationMany small interfaces beat one fat one.
D — Dependency InversionDepend on abstractions, not concretions.
// SOLID, shown by breaking one class on purpose and then fixing it.

// BEFORE: violates S, O and L. One class, four reasons to change.
public class OrderProcessor
{
    public void Process(Order order)
    {
        if (order.Total > 1000) { // volume discount logic }
        EmailSender.Send(order.Email, "Your order is confirmed");      // S: knows about email
        if (DateTime.UtcNow.DayOfWeek == DayOfWeek.Friday) { // promo logic }
        Db.Insert(order);                                    // S: knows about storage
    }
}

// AFTER: one reason to change per class, open for extension, substitutable.
public interface IOrderRule { decimal Apply(Order order); }

public sealed class VolumeDiscountRule : IOrderRule
{
    public decimal Apply(Order order) => order.Total > 1000 ? order.Total * 0.9m : order.Total;
}

public interface INotifier { void OrderConfirmed(Order order); }
public interface IOrderStore  { void Save(Order order); }

public sealed class OrderProcessor
{
    private readonly IEnumerable<IOrderRule> _rules;
    private readonly INotifier _notifier;
    private readonly IOrderStore _store;

    public OrderProcessor(IEnumerable<IOrderRule> rules, INotifier notifier, IOrderStore store)
    { _rules = rules; _notifier = notifier; _store = store; }

    public void Process(Order order)   // S: single reason to change
    {
        foreach (var rule in _rules) order.Total = rule.Apply(order);  // O: new rule, no edit here
        _store.Save(order);
        _notifier.OrderConfirmed(order);
    }
}

The "before" class changes for four unrelated reasons. The "after" version splits each reason into its own type, accepts new rules as a list, and can be tested with fakes instead of a live database and SMTP server.

4.2 Other durable principles

Beyond SOLID, the durable heuristics are DRY, KISS, YAGNI, the Law of Demeter and composition over inheritance. DRY removes duplicate logic, KISS and YAGNI fight accidental complexity, Demeter keeps objects speaking only to their close neighbours and composition over inheritance favours flexible assembly over brittle type hierarchies. They work best when applied deliberately, not as blanket prohibitions.

  • DRY — but only for true knowledge, not incidental similarity.
  • KISS / YAGNI — don’t build what you don’t need yet.
  • Law of Demeter — talk to friends, not strangers.
  • Composition over inheritance.
  • Fail fast and make invalid states unrepresentable.

Over-application of DRY creates premature abstractions that are harder to change than duplication. Duplicate twice before abstracting.

5 · Design Patterns

5.1 Creational patterns5.2 Structural patterns5.3 Behavioural patterns5.4 Enterprise integration patterns

Design patterns are proven, named solutions to recurring structural and behavioural problems, and they give a team a shared vocabulary for communicating design. Knowing them lets an architect recognise a problem, pick the fitting pattern and explain the choice in one word. Patterns are not prizes, so each one is adopted only where it actually removes coupling or duplication.

5.1 Creational patterns

Creational patterns decouple the construction of objects from their use, since object instantiation is where a lot of hidden coupling lives. The classic family is Singleton, Factory, Abstract Factory, Builder and Prototype. Practically, factories and builders centralise construction policy so callers work with interfaces and the concrete type can change without rippling through the codebase.

PatternUse
Factory / Abstract FactoryCreate objects without naming concrete classes
BuilderConstruct complex objects step by step
SingletonOne instance — use sparingly (DI usually replaces it)

5.2 Structural patterns

Structural patterns compose classes and objects to add behaviour or simplify subsystems without rewriting them. The family includes Adapter, Facade, Decorator, Composite, Proxy and Bridge. Architects use them to wrap legacy systems, unify interfaces and attach cross-cutting behaviour such as caching or access control through decoration rather than modification.

PatternUse
AdapterMake incompatible interfaces work together
DecoratorAdd behaviour without subclassing
FacadeSimplify a complex subsystem
ProxyControl access (lazy load, cache, security)

5.3 Behavioural patterns

Behavioural patterns organise how objects cooperate and communicate, covering everything from Strategy and Observer to State and Command. They distribute responsibility among collaborating objects so behaviour stays flexible and callers stay decoupled from concrete implementations. Selecting them is mostly about matching the pattern’s control flow to the problem at hand rather than collecting them for their own sake.

// Strategy: interchangeable algorithms behind one interface
interface ShippingCost { decimal For(Order o); }
class FlatRate : ShippingCost { public decimal For(Order o) => 5m; }   // flat rate
class FreeOver100 : ShippingCost {
    public decimal For(Order o) => o.Total > 100 ? 0m : 5m;   // free over 100
}

// Others: Observer (events), Command (undo/queue),
// Template Method, State, Chain of Responsibility.

Strategy puts each pricing rule in its own class behind one interface, so new rules are added without touching the caller.

5.4 Enterprise integration patterns

Enterprise integration patterns bridge application code and the infrastructure around it, dealing with persistence and messaging plumbing. The set includes Repository and Unit of Work for data access, plus Outbox, Saga and the messaging patterns for reliable communication. They exist to tame the common failure modes of distributed transactions, so an architect applies them where atomicity and delivery guarantees actually matter.

  • Repository — abstract persistence behind a collection-like interface.
  • Unit of Work — commit a set of changes atomically.
  • Outbox — reliably publish events alongside a DB transaction.
  • Saga — coordinate a long-running distributed transaction.

6 · Architectural Styles

6.1 Layered (n-tier)6.2 Hexagonal / Ports & Adapters6.3 Clean / Onion6.4 Other styles

Architectural styles are the big-picture shapes a system can take, from layered through hexagonal to event-driven, and choosing one frames every lower-level decision. Each style encodes a different answer to how components interact, where dependencies point and how data flows. The architect’s job is to match a style to the quality attributes and change profile of the system, not to the fashion of the day.

6.1 Layered (n-tier)

Layered, or n-tier, architecture organises code into horizontal tiers such as presentation, application, domain and data. It is the familiar default, but its downsides are ripple effects when a change crosses layers and the temptation to add layers that only delegate. In practice the architect keeps dependencies strictly downward, bounds cross-layer calls and collapses layers that add no behaviour.

Presentation -> Application -> Domain -> Persistence
Simple and familiar, but changes ripple through layers.
The "lasagna" anti-pattern: many layers doing nothing but delegating.

Layered is easy to reason about, but watch for changes rippling through every layer and empty "lasagna" layers that only delegate.

6.2 Hexagonal / Ports & Adapters

Hexagonal architecture, also called Ports and Adapters, puts the domain at the centre and connects it to the outside world through ports protected by adapter implementations. HTTP, CLI, database and queue adapters can then be plugged in and swapped without touching the domain. In practice you define port interfaces inside the domain and let infrastructure depend on them, which makes the core independently testable.

        [ HTTP adapter ]        [ CLI adapter ]
                 \                 /
              +-----------------------+
              |        Domain         |
              |    (ports inside)     |
              +-----------------------+
                 /                 \
        [ Postgres adapter ]   [ Queue adapter ]

The domain defines "ports" (interfaces); adapters implement them.
Swap a database or UI without touching business rules.

The domain exposes ports and adapters implement them, so swapping the UI or database never touches the business rules.

6.3 Clean / Onion

Clean and Onion architecture push hexagonal thinking further with concentric rings, where the innermost ring is the domain and every dependency arrow points strictly inward. Outer rings contain infrastructure and frameworks, and the dependency rule forbids inner rings from knowing about them. Applied rigorously it produces a highly testable core, at the price of more indirection and boilerplate for simple systems.

Concentric rings: entities at the centre, then use cases, then interface adapters, then frameworks. The Dependency Rule: source code dependencies point inward only.

6.4 Other styles

Beyond the default styles, modular monoliths, microservices, event-driven and serverless architectures each fit specific workloads. A modular monolith keeps deployment simple while preserving seams; microservices offer independent ownership at distribution cost; event-driven decouples producers and consumers; serverless trades control for elasticity. The architect chooses based on scaling, team and operational drivers rather than trend.

StyleGood for
Modular monolithMost systems — clear modules, single deploy
MicroservicesIndependent scaling/teams, high operational maturity
Event-drivenAsync workflows, decoupled reactions
ServerlessSpiky/event workloads, low ops
Pipe & filterData transformation pipelines

7 · Monolith vs Services

7.1 The modular monolith default7.2 When microservices earn their cost7.3 The costs you take on

The monolith-versus-services decision is an economics question, not a fashion statement. In practice you start with a modular monolith and extract capability-sized services only when team ownership, scaling or release cadence makes the extraction pay for its distribution costs. Any premature split simply pays the price of distributed systems for no benefit.

7.1 The modular monolith default

The modular monolith is the sane default: one deployable built from sharply bounded, high-cohesion modules, with transactions and simple operations intact. Its seamlessness is the payoff, because modules are already isolated by interfaces so services can be extracted later without a rewrite. Teams pick it to get most of the architectural benefits at a fraction of the operational cost.

One deployable with strongly separated modules. You get simple operations and transactions now, plus a clean path to extract services later. For most products this is the right starting point.

// A modular monolith: separate assemblies, enforced inward dependencies.

// MyApp.Domain        -> no dependencies at all
// MyApp.Application   -> depends on Domain only
// MyApp.Infrastructure-> depends on Application (EF Core, HTTP, files)
// MyApp.WebApi        -> composes Infrastructure + Application

public sealed class PlaceOrderHandler
{
    private readonly IOrderRepository _orders;      // interface owned by Application
    private readonly IEmailGateway _email;          // interface owned by Application

    public PlaceOrderHandler(IOrderRepository orders, IEmailGateway email)
    { _orders = orders; _email = email; }

    public async Task<OrderId> Handle(PlaceOrder cmd, CancellationToken ct)
    {
        var order = Order.Create(cmd.CustomerId, cmd.Lines);
        await _orders.AddAsync(order, ct);
        await _email.SendConfirmationAsync(order, ct);
        return order.Id;
    }
}

// Composition root wires the concrete adapters, and only this layer knows them.
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<IEmailGateway, SendGridEmailGateway>();
builder.Services.AddScoped<PlaceOrderHandler>();

// Later, if Billing must scale separately, extract this handler plus its
// repository into its own deployable and replace the interface with a
// message call. The seam already exists, so the split is a refactor.

The module boundary is the interface, and only the composition root names the concrete adapters. Because the seam already exists, extracting a service later is a refactor rather than a rewrite.

7.2 When microservices earn their cost

Microservices earn their cost when distinct teams need autonomous ownership, when parts must scale independently or when services need different runtimes and release cadences. Each service then owns its data and its lifecycle, communicating over explicit contracts. The decision is justified by measuring the concrete gain against distribution cost, not by the prestige of a distributed architecture.

  • Independent deployment and scaling are real needs.
  • Multiple teams need autonomous ownership.
  • Different components need different runtimes or scaling profiles.
  • You have the platform maturity to run distributed systems.

7.3 The costs you take on

Every gain from microservices is bought with a distributed cost: versioned contracts, network latency, partial failure and a heavier toolchain for discovery, tracing and deployment. These costs are invisible in small systems and compound as they grow. The architect names each cost explicitly when deciding to split, and budgets for the operational maturity it demands.

GainCost
Independent deployVersioned contracts, backward compatibility
Independent scaleNetwork latency, partial failure
Team autonomyDuplication, distributed debugging
Tech heterogeneityMore tooling, more skills

Distributed transactions are hard. Prefer Saga + eventual consistency over two-phase commit. If a feature needs a transaction across services, the boundary is probably wrong.

8 · Event-Driven Architecture

8.1 Events vs commands8.2 Broker, bus and choreography8.3 Delivery semantics

Event-driven architecture decouples producers from consumers by making system behaviour a stream of facts that components react to. It enables independent scaling of processing and replayable state, but demands discipline around ordering, delivery and failure handling. Architects choose it when loose coupling at the interaction level matters more than strong ordering guarantees.

8.1 Events vs commands

Events are immutable facts in the past tense, while commands are requests that may still be refused. The distinction shapes design because commands carry expectations of a response and possible rejection, whereas events only record that something happened. In practice you route commands when you need an answer and publish events when you want interested parties to react independently.

TypeTenseMeaning
CommandImperative"PlaceOrder" — a request, may be rejected
EventPast"OrderPlaced" — a fact, immutable

8.2 Broker, bus and choreography

Broker, bus and choreography are the three ways to connect producers and consumers in event-driven systems. A broker fans events out to many consumers, choreography lets each service react independently and orchestration names a central coordinator that makes the flow explicit. In practice you combine them, choreographing within boundaries and orchestrating when business processes demand a visible order.

OrderService --OrderPlaced--> [ broker ] --> BillingConsumer
                                       --> InventoryConsumer
                                       --> EmailConsumer

Choreography: consumers react independently (loose, harder to see flow).
Orchestration: a coordinator tells each step what to do (explicit flow).

A broker fans one event out to several consumers; choreography keeps them independent, while orchestration makes the flow explicit.

8.3 Delivery semantics

Delivery semantics decide what a consumer can assume about a published event after a failure. At-least-once is the realistic default for most infrastructure and demands idempotent consumers that tolerate duplicates. At-most-once accepts data loss for speed, and exactly-once, which most systems only approximate, is expensive; the architect matches the semantic to the consequence of loss or duplication.

  • At-most-once — may lose messages.
  • At-least-once — may duplicate; consumers must be idempotent.
  • Exactly-once — effectively at-least-once + idempotency/dedup.
// Idempotent consumer: ignore an event already processed
if (await store.HasProcessed(evt.Id)) return;
await handler.Apply(evt);
await store.MarkProcessed(evt.Id);   // same transaction

Track processed event ids in the same transaction as the effect, so duplicate deliveries are ignored harmlessly — that is the heart of at-least-once handling.

  1. Model an order flow as events.
  2. Make one consumer idempotent.
  3. Choose choreography or orchestration and justify it.

9 · Domain-Driven Design

9.1 Ubiquitous language9.2 Building blocks9.3 Bounded contexts and context maps

Domain-Driven Design aligns the codebase with the language and mental models of the business, so complexity is handled where the money is made. It provides strategic tools, bounded contexts and context maps, and tactical tools such as aggregates and repositories to model invariants. The architect applies it to find the seams worth protecting and to let the domain lead the structure.

9.1 Ubiquitous language

The ubiquitous language is a shared vocabulary used by domain experts, developers and code alike so that no translation layer creeps in. Terms in the codebase, the tests and the conversations must mean the same thing. In practice you cultivate it in design meetings, name classes and methods after business concepts and correct drift whenever technical jargon displaces it.

One shared vocabulary between domain experts and developers. If the business says "policy", the code says Policy — not Record.

9.2 Building blocks

The tactical building blocks of Domain-Driven Design are entities with identity, value objects with no identity, aggregates that protect invariants, repositories for retrieval and domain events for side effects. They give precise names to model pieces so invariants live in one authoritative place. The architect applies them as a toolkit for turning business rules into clean model code.

BlockRole
EntityHas identity that persists over time (Order #123)
Value ObjectDefined by its values, immutable (Money, Address)
AggregateConsistency boundary with one root

Domain ServiceLogic that doesn’t belong to one entity

9.3 Bounded contexts and context maps

Bounded contexts each own their own model and vocabulary, and context maps describe how those models relate, through patterns such as shared kernel, customer-supplier and anticorruption layer. The map makes integration contracts explicit and protects each context from the assumptions of others. In practice you draw the map before wiring systems together, because misaligned models are the source of most integration bugs.

Sales context        Shipping context
  Customer      <-->  Consignee
  "customer"          "recipient"

Same concept, different models per context. A shared "Customer"
table across both is an anti-pattern (coupling). Context maps
describe relationships: Shared Kernel, Customer/Supplier, ACL.

Each bounded context models the same real-world concept differently and maps its relationships with other contexts explicitly.

10 · Data, Consistency & CAP

10.1 CAP and PACELC10.2 Consistency models10.3 Patterns for consistency

Data consistency in distributed systems sits on a spectrum, and CAP and PACELC frame the trade-offs behind every read and write. Strong consistency is cheaper inside a single node and expensive across nodes, while eventual consistency gains availability at the price of visible staleness. The chapter equips the architect with the models and patterns to make deliberate consistency choices per data set.

10.1 CAP and PACELC

CAP states that under a partition you must choose consistency or availability, and PACELC adds the everyday choice: even without a partition you trade latency for consistency. In practice this forces architects to pick a consistency model per data set and to defend the choice. There is no avoiding the trade-off, only knowing which side wins for each read and write.

Under a network partition you choose Consistency or Availability (CAP). When there is no partition you trade Latency against Consistency (PACELC). Most systems are not "CP" or "AP" globally — they are per operation.

10.2 Consistency models

Consistency models, from strong and linearizable through causal and read-your-writes to eventual, define what guarantees replicas and readers actually get. Strong models behave like a single copy of the data but limit availability and add latency. The architect chooses per use case, often dropping from strong to weaker models for hot paths and compensating with explicit reconciliation.

ModelGuarantee
StrongReads see the latest write
Read-your-writesYou see your own writes
Monotonic readsTime never goes backwards for a reader
EventualReplicas converge given time

10.3 Patterns for consistency

The standard patterns for taming distributed consistency are CQRS, event sourcing, sagas and the outbox pattern. CQRS separates reads from writes, event sourcing treats state as a replayable event log, sagas coordinate multi-service transactions with compensating actions and the outbox reliably publishes writes as events. Combined, they turn hard distributed guarantees into achievable, testable designs.

CQRS:  write model (normalised) -> read model(s) (denormalised)
Event Sourcing: state = fold(events); full audit + time travel
Saga:  sequence of local transactions with compensating actions
Outbox: DB write + event enqueue in one transaction

CQRS, event sourcing, saga and outbox are the standard toolkit for trading consistency for scale without losing integrity.

Event sourcing is powerful but heavy: versioning events, projections, and eventual consistency are all real work. Adopt it where the audit/temporal history is genuinely valuable.

11 · API & Integration Design

11.1 Integration styles11.2 Evolving contracts safely11.3 Resilience for integrations

API and integration design treats every integration as a contract plus a failure story, so the same care goes into evolving the contract as into the failure handling around it. Good contracts are explicit, versioned and additive, and callers carry timeouts, retries and circuit breakers. The architect picks the integration style that matches the relationship between the parties.

11.1 Integration styles

REST, GraphQL, gRPC, messaging and webhooks each trade different strengths: REST is simple and cacheable, GraphQL tailors responses, gRPC gives typed high-performance calls, messaging decouples by time and webhooks push without polling. There is no universal best style, so the architect matches the style to the relationship, whether request-response, long-lived stream or fire-and-forget.

StyleBest forCaveat
RESTResource CRUD, public APIsOver/under-fetching
GraphQLFlexible client-driven queriesQuery cost, caching
gRPCInternal low-latency RPCBrowser support, schema tooling
MessagingAsync, decoupledEventual consistency
WebhooksServer-to-server notificationsRetries, idempotency

11.2 Evolving contracts safely

Evolving contracts safely means growing them by addition rather than removal and running old versions until telemetry proves they are gone. Techniques include additive fields, tolerant readers, version fields in the payload and deprecation timelines. In practice the architect pairs each breaking change with a migration window during which both versions are supported.

  • Add fields, don’t remove or repurpose them.
  • Version at the edge (/v2) or via content negotiation.
  • Use tolerant readers (ignore unknown fields).
  • Deprecate with a timeline and telemetry on old-version usage.

11.3 Resilience for integrations

Resilience for integrations keeps a calling service alive even when the partner fails, using timeouts, retries, circuit breakers and bulkheads. Timeouts bound the wait, retries handle transient errors with backoff and jitter, circuit breakers stop hammering a failing partner and bulkheads isolate resource pools per dependency. Together they turn a partner outage into a handled condition instead of a cascading failure.

Timeouts       -> never wait forever
Retries        -> with exponential backoff + jitter (idempotent ops)
Circuit breaker-> stop calling a failing dependency
Bulkhead       -> isolate pools so one failure can't exhaust all
Rate limiting  -> protect yourself and your partners

Each pattern buys one specific protection — timeouts, retries, circuit breakers, bulkheads and rate limits together make integrations fail safely.

12 · Scalability & Performance Architecture

12.1 Scaling dimensions12.2 Caching layers12.3 A performance method

Scalability and performance must be designed in rather than bolted on, because replumbing a system for scale is costly after the fact. Scaling happens along several axes, including more instances, more cores, data sharding and asynchronous work, and the profile of the load decides which axes matter. A measuring-before-optimising discipline keeps effort pointed at the real bottleneck.

12.1 Scaling dimensions

Systems scale in several dimensions: vertically by adding cores and memory, horizontally by adding instances, through data by sharding and using read replicas, and sideways by deferring work into queues. Each axis has a ceiling and a cost, so the architect picks axes the load profile demands. In practice you scale the axis that actually binds, then re-measure.

AxisApproach
VerticalBigger machine (simplest, has a ceiling)
HorizontalMore stateless instances behind a balancer
DataReplicas, partitioning, sharding, caching
AsyncQueues to absorb spikes

12.2 Caching layers

Caching layers sit between clients and storage to cut latency and load, but the cache itself is the easy part and invalidation is the hard part. Strategies such as cache-aside, write-through, read-through and time-to-live each accept different staleness and consistency trade-offs. The architect chooses per data type and always ties the invalidation approach to the consistency guarantees the business actually needs.

  • Client/CDN → edge → application → distributed cache → DB.
  • Strategies: cache-aside, read-through, write-through, write-behind.
  • Invalidation is the hard part; prefer short TTLs + event-based eviction.

12.3 A performance method

A performance method is a small disciplined loop: set measurable targets, instrument the system, find the biggest bottleneck, remove it and repeat. Targets prevent optimisation for its own sake, and measurement prevents guesswork and premature fixes. In practice you profile under realistic load and stop as soon as the target is met, since each further optimisation usually costs complexity.

1 Define targets (p95/p99, throughput, budget)
2 Measure under realistic load
3 Find the bottleneck (queueing theory: Little's Law)
4 Fix the biggest one
5 Repeat — the bottleneck always moves

Performance work is a loop — target, measure, find the bottleneck, fix the biggest one, repeat — because the bottleneck always moves.

13 · Reliability, Resilience & Observability

13.1 Resilience patterns13.2 Observability13.3 Recovering gracefully

Reliability means more than uptime, including failing gracefully when things go wrong, and resilience plus observability turn otherwise invisible outages into handled, instrumented events. Resilience patterns such as timeouts, retries and circuit breakers keep failures contained, while metrics, logs and traces reveal what failed and why. Together they convert surprises into known, monitored conditions.

13.1 Resilience patterns

Resilience patterns each defend against a specific failure mode: timeouts bound hang, retries handle transient errors, circuit breakers stop cascades, bulkheads isolate resources and idempotency makes retries safe. The architect applies them at every network and dependency boundary. Because none is free, each is chosen based on the failure it removes and the latency or cost it adds.

PatternProtects against
TimeoutSlow dependencies
Retry + backoffTransient failures
Circuit breakerCascading failure
BulkheadResource exhaustion
Graceful degradationTotal outage (serve stale/partial)
IdempotencyDuplicate requests/messages

13.2 Observability

Observability answers what is failing, what is slow and where it happened through three signals: metrics, structured logs and traces. Metrics give aggregated health, logs give detailed events and traces follow a single request across services. In practice you instrument every service with the same correlation identifiers so the three signals can be joined during an incident.

Metrics -> RED (Rate, Errors, Duration) / USE (Util, Saturation, Errors)
Logs    -> structured, correlated by trace id
Traces  -> distributed span across services
Alerting-> on symptoms (SLO burn), not on every spike

RED or USE metrics, correlated logs and traces let you answer what is slow, who failed and where it happened.

13.3 Recovering gracefully

Recovering gracefully means designing for failure in advance with reversible deploys, feature flags, game days and blameless postmortems. Reversible deploys let you back out quickly, feature flags decouple release from enablement, game days rehearse failure and blameless postmortems turn incidents into systemic improvements. The chapter treats recovery as a designed capability, not an improvisation.

  • Design for failure: assume every dependency will fail.
  • Reversible deploys and feature flags to limit blast radius.
  • Run game days and chaos experiments.
  • Blameless postmortems that change the system.

14 · Security Architecture

14.1 Threat modelling14.2 Controls14.3 Zero trust in practice

Security is an architectural property, so threats are modelled early and controls are placed where risk actually lives rather than pasted on as an afterthought. The architect connects threat modelling to the structure, routing and trust boundaries of the system. Security then becomes testable requirements, not a set of scattered badges to chase.

14.1 Threat modelling

Threat modelling is the practice of enumerating threats per component before they become incidents, and STRIDE gives a structured checklist: spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. You apply it during design to each trust boundary and data flow. The output is a ranked risk list that drives which controls get built.

Use STRIDE to enumerate threats per component: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege. Then apply controls where the risk lives.

14.2 Controls

Controls span identity, network, data, application and operations, and defence in depth means layering them independently so one failure does not expose the system. Examples are authentication and authorisation, network segmentation, encryption at rest and in transit, input validation and least-privilege access. The architect maps controls to the threats from modelling so coverage is deliberate rather than accidental.

LayerControls
IdentityOIDC/OAuth2, MFA, short-lived tokens
NetworkSegmentation, mTLS, WAF
DataEncryption in transit/at rest, least privilege, tokenisation
ApplicationInput validation, output encoding, dependency scanning
OperationsAudit logs, secrets management, patching

14.3 Zero trust in practice

Zero trust stops assuming the network is friendly and instead verifies every request regardless of origin. In practice you grant least privilege, authenticate and authorise at every hop, inspect and log traffic, and elevate permissions just in time for short-lived sessions. It is a mindset shift that turns the network perimeter from the boundary into just another untrusted channel.

  • Never trust the network; authenticate and authorize every request.
  • Least privilege by default, just-in-time elevation.
  • Defence in depth: multiple independent controls.
  • Secure by design, not bolted on.

Architecture decisions create security posture. A shared database account or an internal API with no auth is an architectural vulnerability, not a bug to patch later.

    identity.Subject, "order.update", order.Id,
    oldValue: before, newValue: after, at: DateTimeOffset.UtcNow), ct);

//    Token TTL: 15 minutes. A stolen token expires before it is abused.

15 · Documenting Architecture

15.1 The C4 model15.2 Architecture Decision Records (ADRs)15.3 Diagrams as code

Documentation keeps architecture alive after its authors move on, and a system whose shape is not written down cannot be reviewed or challenged. Good documentation records decisions, current structure and the reasons behind them at a level senior engineers can trust. In practice it is kept in the repository as living material rather than a wall of detached diagrams.

15.1 The C4 model

The C4 model gives one diagram per zoom level, from system context through containers, components and code, so every diagram has a clear scope and legend. Context shows the system and its neighbours, containers show deployables, components show boundaries and code zooms into a class. In practice you maintain the top two levels and generate the lower ones, since they change fastest.

C1 Context   - the system and its users/systems (one diagram)
C2 Container - deployable units (web app, API, DB, queue)
C3 Component - pieces inside a container
C4 Code      - classes (usually generated, rarely hand-drawn)

Rule: one diagram per level, with a legend and a clear scope.

C4 gives one diagram per zoom level from context down to code, so a single diagram never tries to explain everything.

15.2 Architecture Decision Records (ADRs)

Architecture Decision Records capture the context, the decision and its consequences so future engineers can revisit the why rather than only the what. Each record is a short, dated file written at decision time and linked to related decisions. The practice turns conversations into an auditable history of how the architecture arrived where it stands.

# ADR 0007: Use PostgreSQL for the primary datastore

Status: Accepted    Date: 2026-09-17

Context:  Need JSONB, geospatial, and strong standards compliance.
Decision: Adopt PostgreSQL 16 as the primary OLTP database.
Consequences: Team must learn pg-specific ops; no MSSQL tooling.

An ADR records context, decision and consequences so a future engineer can revisit the why, not just the what.

15.3 Diagrams as code

Diagrams as code keep architecture in the repository, where it versions, reviews and updates exactly like source code. Tools such as Mermaid and PlantUML render text descriptions into diagrams for pull requests and documentation. In practice this makes diagrams reviewable in code review, auditable through git history and cheap to regenerate when the design shifts.

Keep diagrams in the repo (Structurizr DSL, Mermaid, PlantUML) so they version and review like code. Diagrams that live only in slide decks rot immediately.

16 · Evaluating & Evolving Architecture

16.1 Evaluation methods16.2 Fitness functions (automated governance)16.3 Evolving safely

Good architecture is continuously evaluated and evolved, with automated checks proving the shape still stands as the system grows. Evaluation frameworks such as ATAM and risk storming judge the design against quality attributes, while fitness functions encode constraints as CI checks. This turns architecture from a one-off design into a governed, living process.

16.1 Evaluation methods

Architecture evaluation methods give structured lenses for judging a design before it hardens: ATAM runs scenarios against quality attributes, risk storming crowdsources risks from the team, fitness functions automate constraints and cost-of-change tracks how painful modification has become. The architect applies them at milestones and when major changes land. Each answer is only useful if it leads to an action.

MethodQuestion it answers
ATAMHow do decisions affect quality attributes?
Risk stormingWhere is the greatest risk?
Fitness functionsAre we still honouring the architecture?
Cost of changeWhich decisions are expensive to reverse?

16.2 Fitness functions (automated governance)

Fitness functions encode architectural constraints as automated checks that fail loudly when violated, giving continuous governance of the shape. Examples are dependency rules, API compatibility checks, latency budgets and module boundary enforcement implemented as CI tests. In practice you start with a handful of checks for the constraints you care about most and extend the suite as the system evolves.

# Example checks (ArchUnit style, run in CI):
- no dependency from Domain to Infrastructure
- no cyclic dependencies between modules
- controllers must not access the DB directly
- a module's public API only exposes interfaces

Fitness functions turn architectural constraints into automated CI checks that fail loudly the day they are violated.

16.3 Evolving safely

Evolving a live system safely avoids big-bang rewrites by using the strangler fig pattern, parallel runs and explicit rollback paths. New capability grows alongside the old, traffic is shifted gradually and each step is reversible. In practice you keep the seam between old and new wide enough that any release can be backed out, and you only remove the old system when telemetry shows it is unused.

  • Use the Strangler Fig to replace legacy incrementally behind a facade.
  • Parallel-run and compare before cutover.
  • Keep a rollback path for every structural change.
  • Let the system’s real pain drive the next refactor.

Concrete targets for availability, scalability, consistency and team shape turn vague goals into testable requirements. Written this way, requirements become inputs to architectural choices and later to acceptance tests.
