The right mindset

Explains the mindset behind Axios, a promise-based library that wraps plain HTTP requests with sensible defaults. Rather than memorizing every option, learn the single config object that every request is built from. Once you know where to set values and how to override defaults on individual requests, most questions resolve themselves. Approaching Axios this way turns unfamiliar errors and options into variations on the same request shape.

Axios rewards understanding one idea: every request is a plain config object, and every response is a promise that resolves to a rich response object. Sane defaults (JSON in and out, a 2xx rule, a timeout you control) mean small apps barely need configuration — the skill that scales is knowing exactly where to override those defaults.

Keep the official docs open beside this guide at axios-http.com/docs. This guide explains the why and the sequence; the docs are the exhaustive reference.

1 · Axios Fundamentals & Setup

1.1 What Axios is1.2 Installing Axios1.3 Your first request1.4 Supported environments: ESM and CJS

Chapter one covers Axios fundamentals and setup, installing the library in both the browser and Node.js and comparing it with the built-in fetch API. You choose between an npm install for bundler projects or a CDN script tag for plain HTML pages. The chapter ends with your first request, which delivers parsed JSON data from a single line of code, establishing the core request-and-await pattern used everywhere later.

Axios is a promise-based HTTP client for the browser and Node.js: you hand it a method and a URL, and it returns a promise that resolves to a rich response. The request lifecycle stays the same everywhere — browser tab, build tool, tests, or a server function.

1.1 What Axios is

Explains what Axios is and contrasts it with the built-in fetch API so you know when each shines. Both send the same HTTP requests, but Axios adds a convenience layer on top including automatic JSON handling, request config objects, interceptors, and consistent error handling. Use fetch when you want zero dependencies and the native API, and reach for Axios when you want defaults and features that keep request code short.

CapabilityAxiosfetch
JSON handlingParses and stringifies automaticallyManual res.json() / JSON.stringify
Response shapedata, status, headers, config togetherStatus on the response, body via methods
HTTP errorsRejects for non-2xx by defaultRejects only on network failure
TimeoutBuilt-in timeout optionNeeds AbortSignal.timeout
ProgressUpload and download callbacksStreams read manually

None of this is magic that the browser cannot do with fetch — Axios packages it so your call sites stay short and consistent.

1.2 Installing Axios

Shows the two standard ways to install Axios for your environment. In Node or bundler projects you run npm install axios and import the package in your code. For a plain HTML page you add a CDN script tag pointing at the axios bundle, which exposes axios globally in the browser. After following one of these paths you have the package available in scope and ready for a first request.

# Node / bundler projects
npm install axios
# yarn add axios   |   pnpm add axios
# TypeScript types are bundled — no @types package needed

npm install adds axios to your project dependencies, and modern axios ships its own TypeScript definitions, so no separate @types package is required.

<!-- Browser without a build step: a CDN exposes the global axios object -->
<script src="https://cdn.jsdelivr.net/npm/axios/dist/axios.min.js"></script>
<script>
  axios.get('/api/ping');   // works immediately, no import needed
</script>

The CDN build attaches axios to window so a plain HTML page can start calling it at once, which is handy for demos and small static pages.

1.3 Your first request

Makes your very first request with axios.get, awaiting the response and reading the parsed JSON from the data property. The pattern is one await and one response shape: call a method, await it, and use the returned data. Everything Axios does later, from config options to interceptors, is a variation on this same request, await, and read data flow.

import axios from 'axios';

async function loadPost() {
  const res = await axios.get('https://jsonplaceholder.typicode.com/posts/1');
  console.log(res.status);        // 200
  console.log(res.data.title);    // the JSON body, already parsed into an object
}

loadPost().catch((err) => console.error(err.message));   // handle failures separately

axios.get returns a promise that resolves to a response object, and res.data is the JSON decoded for you — no .json() call anywhere.

1.4 Supported environments: ESM and CJS

Covers the environments Axios supports and how to import it, which differs between ES modules and CommonJS. In modern bundlers you add axios as an import from the axios package at the top of your module, while CommonJS projects pull it in with the require function. The API is identical in both cases, so only the import line changes. Choose the import style that matches your project’s module system.

// CommonJS (Node.js)
const axios = require('axios');

// ES modules (Node 18+ or a bundler like Vite/Webpack)
import axios from 'axios';

// Both hand you the same instance: methods, defaults, interceptors, cancel.

Axios supports both module systems plus the browser global, so the import line is the only difference between your Node scripts, bundler apps, and test files.

2 · Making Requests

2.1 The five HTTP verbs2.2 The request config object2.3 params, bodies and headers2.4 Running requests concurrently

Chapter two is about making requests and covers the five HTTP verbs, the shorthand alias methods, the config object, params, headers, and concurrent requests. You learn that aliases such as get, post, put, patch, and delete are sugar over the low-level axios(config) call. By the end you have written every request shape Axios offers, from a simple GET to requests carrying bodies, query params, and custom headers.

Axios exposes two ways to fire a request: method aliases like axios.get, and one config object you pass to axios(). They are the same thing under the hood — aliases are sugar that fills in the method for you.

2.1 The five HTTP verbs

Shows the alias method for each of the five HTTP verbs and the argument order each one expects. For aliases such as get, delete, and head the URL is the first argument and config the second, while post, put, and patch take the data as their second argument and config as the third. Learn this one rule and you can call any verb correctly without looking anything up.

import axios from 'axios';

await axios.get('/api/users');                     // read — data goes in params
await axios.post('/api/users', { name: 'Ada' });   // create — body is arg 2
await axios.put('/api/users/1', { name: 'Enid' }); // replace the whole record
await axios.patch('/api/users/1', { name: 'Ada' }); // update a few fields
await axios.delete('/api/users/1', {               // config is arg 2 here
  headers: { 'X-Reason': 'duplicate account' },
});

Every alias follows the pattern axios.method(url, data?, config?), and objects passed as data are stringified to JSON with the right Content-Type automatically.

2.2 The request config object

Introduces axios(config) as the low-level form of every request, where the whole request is described as one config object. The config holds the URL, method, params, data, headers, timeout, and every other option. Anything you can do with an alias like axios.get you can also do with this object, making it the most flexible way to issue a request. Most other chapters build directly on this object.

import axios from 'axios';

const promise = axios({
  method: 'get',          // default is get
  url: '/users',
  params: { page: 2 },    // serialized into the query string
  headers: { Accept: 'application/json' },
  timeout: 5000,          // give up after 5 seconds
});

// The aliases build exactly this object:
// axios.get(url, cfg) === axios({ method: 'get', url, ...cfg })

The config object is the single vocabulary of Axios, and method aliases are just shortcuts that fill in the method field for you.

2.3 params, bodies and headers

Shows where GET params, POST bodies, and custom headers each live inside the config object. Query parameters for a GET go in the params property, a request body for methods like POST and PUT goes in the data property, and custom headers go in the headers property. Combining them in one config object lets a single request carry query strings, a payload, and authentication all at once.

// GET: params become the query string, array-aware
await axios.get('/api/search', {
  params: { q: 'axios', per_page: 10, tags: ['js', 'http'] },
});
// => /api/search?q=axios&per_page=10&tags%5B%5D=js&tags%5B%5D=http

// POST: data becomes the JSON body, headers can be mixed in
await axios.post('/api/login', { email, password }, {
  headers: {
    'Content-Type': 'application/json',
    'X-Client': 'web',          // any custom header you need
  },
});

params, data, and headers each have their own slot in the config, and Axios serializes params into the URL and data into the body for you.

2.4 Running requests concurrently

Explains how to run several requests in parallel and wait for all of them to finish. Use Promise.all with an array of axios request promises, and note that axios.all and axios.spread are now legacy aliases for the same Promise behavior. This pattern suits loading independent resources at once, where responses can arrive in any order. Await the combined promise and read each result from the data property.

import axios from 'axios';

// legacy pair: axios.all([...]).then(axios.spread(fn))
const responses = await axios.all([
  axios.get('/api/posts'),
  axios.get('/api/users'),
]);   // responses is an array of two response objects

// modern equivalent — plain Promise.all with destructuring
const [postsRes, usersRes] = await Promise.all([
  axios.get('/api/posts'),
  axios.get('/api/users'),
]);

Parallel requests are ordinary promises combined with Promise.all; axios.all and axios.spread exist for older code but do exactly the same thing.

3 · Response Handling & Data

3.1 The response schema3.2 JSON by default, and transforming responses3.3 Upload and download progress3.4 Binary data: blob, arraybuffer and stream

Chapter three covers response handling and data, deconstructing the response schema and showing how to transform payloads, read binary data, and track transfer progress. You learn that Axios parses JSON automatically and that the transformResponse option can reshape data before your code sees it. The chapter also covers responseType for binary formats and callbacks for measuring progress, so you can shape what your app receives and know how long it takes.

A fulfilled Axios promise resolves to a response object with a fixed shape. Its fields are predictable, so the same handling code works for a tiny JSON endpoint or a multi-gigabyte download.

3.1 The response schema

Maps every field on the Axios response object so you know what a resolved request gives you. The data field holds the parsed payload your app actually uses, while status, statusText, headers, config, and request carry the metadata your debugger and error handling want. Learning this shape means you always know where to read the body, verify the status code, and inspect the outgoing configuration.

const res = await axios.get('/api/users/1');

res.data;        // the parsed body (already a JS object for JSON APIs)
res.status;      // 200
res.statusText;  // 'OK'
res.headers;     // response headers (lower-cased keys)
res.config;      // the exact config object this request used
res.request;     // underlying XMLHttpRequest (browser) or request handle (Node)

The response object bundles the parsed body with status, headers, and the config that produced it — everything you need to handle or debug a request.

res.config is a debugging goldmine — it shows the final URL, headers, params, and timeout after interceptors ran.

3.2 JSON by default, and transforming responses

Shows how Axios handles JSON automatically, serializing objects you send and parsing JSON into JavaScript objects on the way back. For payloads that need reshaping, the transformResponse config option runs your function on the response data before your code receives it. Small APIs commonly need no transformation at all because the default JSON behavior covers text, objects, and arrays. Set the transform when an API returns a shape you want normalized.

import axios from 'axios';

// JSON is the default content type: objects in, objects out
const { data } = await axios.post('/api/search', { q: 'router' }, {
  headers: { 'Content-Type': 'application/json' },
});

// transformResponse: an array of functions run after parsing, in order
const api = axios.create({
  transformResponse: [
    ...axios.defaults.transformResponse,   // keep the built-in JSON parser
    (payload) => {
      if (payload && Array.isArray(payload.items)) {
        return { users: payload.items, total: payload.total };   // reshape
      }
      return payload;
    },
  ],
});

JSON just works, and transformResponse lets you reshape every payload centrally — as long as you spread the default transformers first, parsing still happens.

3.3 Upload and download progress

Tracks upload and download progress by passing the onUploadProgress and onDownloadProgress callbacks in the config. Each callback receives an event carrying loaded and total bytes, which you use to compute a percentage for progress bars, upload spinners, and large file feeds. Attach the callbacks per request or per instance, and update your UI from the reported values as transfers proceed.

// Upload: FormData goes straight into data
const form = new FormData();
form.append('file', fileInput.files[0]);

await axios.post('/api/upload', form, {
  onUploadProgress: (e) => {
    const pct = e.total ? Math.round((e.loaded / e.total) * 100) : null;
    updateProgressBar(pct);   // render a bar for each chunk report
  },
});

// Download
await axios.get('/api/report.csv', {
  responseType: 'blob',
  onDownloadProgress: (e) => {
    console.log(`${e.loaded} / ${e.total} bytes`);   // e.total may be null
  },
});

onUploadProgress and onDownloadProgress receive progress events with loaded and total, so you can render a bar on both sides of a transfer.

3.4 Binary data: blob, arraybuffer and stream

Explains how to request binary payloads by setting the responseType config option to blob or arraybuffer in the browser, and to stream in Node. The format you choose determines what lands in the response data, matching the environment’s strengths: blobs and arraybuffers suit client-side downloads, while a stream lets Node process large bodies incrementally. Select responseType based on what your consumer expects to read.

// ArrayBuffer for processing in memory (browser or Node)
const { data } = await axios.get('/api/file.bin', { responseType: 'arraybuffer' });
const bytes = new Uint8Array(data);

// Blob in the browser — make it a clickable image
const res = await axios.get('/img/logo.png', { responseType: 'blob' });
const url = URL.createObjectURL(res.data);
document.querySelector('#logo').src = url;

// Stream in Node — write to disk without holding it all in memory
import { createWriteStream } from 'node:fs';
const resp = await axios.get('https://example.com/big.zip', { responseType: 'stream' });
resp.data.pipe(createWriteStream('big.zip'));

responseType tells Axios to hand back blob, arraybuffer, or a readable stream, letting you transfer files without loading everything into RAM.

4 · Configuration & Defaults

4.1 Global defaults4.2 Instances with axios.create4.3 baseURL, timeout, headers and paramsSerializer4.4 Per-request overrides and environment config

Chapter four covers configuration and defaults, showing how to stop repeating options on every call. You set global defaults directly on the axios object, or better, create instances with axios.create that carry their own baseURL, timeout, headers, and other options. Per-request config always wins over instance defaults, which win over global defaults, letting you override precisely when needed. Environment variables can feed baseURLs so config differs per deployment.

Configuration in Axios has three layers — global defaults, instance defaults, and per-request overrides — merged in that order. Once you internalize the merge order, every configuration question answers itself.

4.1 Global defaults

Shows how to set application-wide defaults directly on the shared axios object, for example axios.defaults.timeout and axios.defaults.headers. Common keys are the timeout, the base URL, and default headers applied to every request. Global defaults are the right layer for one-off apps and demos, but for real projects the axios.create instance approach keeps config better contained. Individual requests can still override any global default with their own options.

import axios from 'axios';

axios.defaults.baseURL = 'https://api.example.com/v2';
axios.defaults.timeout = 10000;
axios.defaults.headers.common['Accept'] = 'application/json';

// short calls now resolve against the defaults
const { data } = await axios.get('/users');   // https://api.example.com/v2/users

Global defaults lift shared settings out of every call, so relative URLs like /users resolve against the baseURL you set once.

4.2 Instances with axios.create

Creates separate HTTP clients with their own defaults using axios.create, passing baseURL, timeout, headers, and other options in the call. Each instance exposes the full request API, so you call instance.get and instance.post exactly as on the global axios. Instances are the recommended approach for real applications because they let different parts of an app talk to different APIs with independent defaults. Per-request config can still override anything on an instance.

import axios from 'axios';

const authApi = axios.create({
  baseURL: 'https://sso.example.com',
  timeout: 5000,
});

const dataApi = axios.create({
  baseURL: 'https://data.example.com',
  timeout: 15000,
  headers: { 'X-Data-Token': process.env.DATA_TOKEN },
});

export { authApi, dataApi };   // two clients, independent defaults and interceptors

Each instance carries its own defaults and interceptors, so one app can talk to several APIs without mixing up tokens or timeouts.

4.3 baseURL, timeout, headers and paramsSerializer

Covers the daily config options: baseURL for prefixing relative URLs, timeout for failing slow requests, headers for per-call HTTP headers, and paramsSerializer for customizing how params become a query string. A custom paramsSerializer is useful when the default style does not match what the API expects. These options can live at the global, instance, or request level, giving you consistent defaults with precise per-request overrides.

const api = axios.create({
  baseURL: 'https://api.example.com',
  timeout: 5000,                      // abort after 5s of inactivity
  headers: { 'X-App-Version': '1.4.0' },

  // some backends want plain key=value pairs, no brackets
  paramsSerializer: (params) =>
    Object.entries(params)
      .map(([key, value]) => `${encodeURIComponent(key)}=${encodeURIComponent(value)}`)
      .join('&'),
});

// now all calls share the baseURL, timeout, and serializer
await api.get('/search', { params: { q: 'axios' } });

Instance options layer up (baseURL, timeout, headers, serializer) so every request inherits them, and paramsSerializer lets you match a backend’s exact query style.

4.4 Per-request overrides and environment config

Shows how config precedence works: a per-request config object always wins, followed by instance defaults, then global defaults, so scarce overrides stay local. Environment variables feed values such as baseURL so the same code adapts to development, staging, and production. Put anything that differs per environment in an env var rather than hard-coding it. Read the value once, apply it in defaults or a create call, and keep secrets out of source.

// per-request options override instance and global defaults every time
const slow = await api.get('/slow-report', { timeout: 60000, params: { full: 1 } });

// environment-driven base URL (Node or a bundler like Vite)
const API_URL =
  process.env.API_URL ??
  (import.meta.env ? import.meta.env.VITE_API_URL : null) ??
  'https://default.example.com';

const client = axios.create({ baseURL: API_URL });

The merge order is request over instance over global, and baseURL should come from environment configuration so the same code runs in dev, staging, and production.

5 · Interceptors

5.1 Request interceptors5.2 Response interceptors5.3 Ordering and ejecting interceptors

Chapter five covers interceptors, middleware that runs on every request and response so cross-cutting concerns live in one place. Request interceptors can stamp auth headers, add logging, or queue retries, while response interceptors normalize errors and unwrap payloads. You register them with axios.interceptors.request.use and axios.interceptors.response.use, and they chain forward in order and reverse on the way back. Centralize once instead of repeating logic at every call site.

Interceptors are functions that run for every request before it is sent and for every response before it is delivered. They are where auth tokens, logging, and common error handling belong — not sprinkled across your call sites.

5.1 Request interceptors

Attaches a handler that runs before each request is sent, registered with axios.interceptors.request.use. The canonical use is stamping an Authorization header onto every call so individual requests stay simple and secure. The interceptor receives the config object and returns it, possibly modified, for the request to continue. This centralizes token attachment so no call site has to think about headers.

api.interceptors.request.use(
  (config) => {
    const token = authStore.getToken();               // from memory or a store
    if (token) {
      config.headers.Authorization = `Bearer ${token}`; // attach it everywhere
    }
    config.metadata = { startedAt: Date.now() };      // stamp for later timing
    return config;                                     // required — hand it onward
  },
  (error) => Promise.reject(error),                   // outbound errors skip the chain
);

The request interceptor mutates config (token, timing metadata) and must return it, so every call downstream carries the same enriched headers.

5.2 Response interceptors

Intercepts both successful responses and failures by passing callbacks to axios.interceptors.response.use. The success callback receives the response object, while the error callback receives the error and can normalize it before it reaches your code. Error normalization here flattens messy API errors into one consistent shape callers can trust. Because the handler runs for every response, one registered interceptor covers the whole application.

api.interceptors.response.use(
  (response) => response,                            // success: pass through unchanged
  (error) => {
    if (!error.response) {
      // network failure — no server ever replied
      console.warn('Network error:', error.message);
      error.userMessage = 'You appear to be offline.';
      return Promise.reject(error);
    }
    // map statuses to a friendly message every caller can rely on
    const messages = { 403: 'No permission', 404: 'Not found', 422: 'Check your input' };
    error.userMessage =
      messages[error.response.status] ?? 'Something went wrong.';
    return Promise.reject(error);
  },
);

Response interceptors see successes and failures: network errors and status codes get normalized to a consistent userMessage that components display.

5.3 Ordering and ejecting interceptors

Explains how Axios executes registered interceptors and how to remove them later. Request interceptors run in registration order, while response interceptors run in reverse order, the last one registered running first on the way back. To remove one, store the id returned by the use call and pass it to axios.interceptors.request.eject or its response equivalent. Removing an interceptor detaches its handler for all subsequent requests.

const first = api.interceptors.request.use((c) => { console.log('first'); return c; });
const second = api.interceptors.request.use((c) => { console.log('second'); return c; });
// log order for one request: 'first', 'second' (registration order)

// response handlers run in reverse: the last one registered is called first

api.interceptors.request.eject(first);    // remove one by the id use() returned
api.interceptors.request.clear();         // or remove them all for a fresh state

Ordering matters when interceptors depend on each other — requests run in, responses run back — and eject() removes a specific handler by its registration id.

6 · Error Handling

6.1 The error shape6.2 Status-based handling with AxiosError6.3 validateStatus and retry patterns6.4 A global error interceptor

Chapter six covers error handling by decoding the AxiosError shape and classifying failures by HTTP status. You learn where failures surface on the error, across the message, the request, and the response, and use instanceof AxiosError plus optional chaining to distinguish network failures from server rejections. The chapter adds validateStatus for controlling which statuses count as errors, and retry patterns for transient failures. A global interceptor centralizes reactions such as toasts and redirects.

Axios rejects with AxiosError for every failure — but failure means different things: a network outage, a timeout, a 404, or a 500. The skill is reading error.code, error.response, and error.request to classify each one.

6.1 The error shape

Maps the three places a failed request can surface: the error message, the error.request object, and the error.response object. A network failure before a response arrives leaves response undefined while request is present, and a server rejection fills response with status, data, and headers. Determining which of these is present tells you where the chain broke. Build your error handling around these three properties.

try {
  await axios.get('/api/users');
} catch (error) {
  error.message;         // readable summary, e.g. 'Request failed with status code 404'
  error.response;        // present when the server answered (has .status and .data)
  error.request;         // present when nothing came back (network failure, timeout)
  error.isAxiosError;    // true for every error Axios produces
  error.code;            // machine code: 'ERR_BAD_REQUEST', 'ERR_NETWORK', 'ECONNABORTED'
}

An AxiosError tells you where the request died: response means the server answered with an error status, request alone means the network never delivered one.

6.2 Status-based handling with AxiosError

Classifies failures by status code using instanceof AxiosError and optional chaining on the response. Treat 4xx statuses as business logic, such as validation errors or rejected auth, where the app should show a message, and 5xx as infrastructure trouble worth retrying or alerting. Read error.response.status to pick the branch, and fall back to generic network handling when status is undefined. Guard every read so a missing response never throws.

import axios, { AxiosError } from 'axios';

try {
  await api.post('/login', creds);
} catch (error) {
  if (error instanceof AxiosError) {
    const status = error.response?.status;

    if (status === 401) return showLoginForm();
    if (status === 422) return showFieldErrors(error.response.data.errors);
    if (status === 429) return showRetryNotice();       // rate-limited
    if (!error.response) return showOfflineBanner();    // network failure
    if (status >= 500) return showServerError();        // upstream broke
  }
  throw error;   // anything unexpected: let it bubble to a global handler
}

instanceof AxiosError reliably detects Axios failures, optional chaining on error.response handles the no-reply case, and each status routes to its own UX.

6.3 validateStatus and retry patterns

Shows how to change which statuses count as errors using the validateStatus config option, which receives a status code and returns a boolean. Returning true for statuses such as 404 lets your code read the response without entering the error path. The chapter also covers retry patterns for transient failures, where you catch an AxiosError, check that it is retryable, and re-run the request a limited number of times. Temporary glitches then never surface as red screens.

// treat 304 as a fulfilled response instead of a thrown error
const api = axios.create({
  validateStatus: (status) => (status >= 200 && status < 300) || status === 304,
});

// retry only what is likely transient: network errors and 5xx
async function getWithRetry(url, { retries = 3, delayMs = 500 } = {}) {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      return await api.get(url);
    } catch (error) {
      const transient = !error.response || error.response.status >= 500;
      if (!transient || attempt === retries) throw error;
      await new Promise((r) => setTimeout(r, delayMs * attempt));   // back off linearly
    }
  }
}

validateStatus redefines what counts as an error, and getWithRetry retries only network errors and 5xx responses with a small backoff, never 4xx client mistakes.

6.4 A global error interceptor

Centralizes error reactions in one global response interceptor so every axios call gets consistent treatment. In the error callback you can show a toast, redirect to login, or reset the session, and then rethrow or resolve so local call sites stay small. Pair the global handler with local catch blocks for per-request details that only that caller knows. This keeps error UI consistent while preserving fine-grained control where needed.

api.interceptors.response.use(
  (response) => response,
  (error) => {
    const status = error.response?.status;
    if (status === 401) redirectToLogin();        // session expired, once
    if (status && status >= 500) toast('Server hiccup — please retry.');
    if (!error.response) toast('You seem to be offline.');
    return Promise.reject(error);                 // local handlers still run
  },
);

// call sites stay readable — the interceptor handles the noise
try {
  await api.post('/comments', body);
} catch (error) {
  if (error.response?.status === 422) showInlineErrors(error.response.data.errors);
}

A response interceptor handles global reactions (toasts, redirects) while call sites handle only local details, because the interceptor still re-rejects the error.

7 · Cancellation & Timeouts

7.1 Cancelling with AbortController7.2 The legacy CancelToken7.3 Timeouts7.4 Race conditions and debouncing searches

Chapter seven covers cancellation and timeouts so stale requests never waste work or hang the UI. The modern approach uses the AbortController API, passed through the signal config option, and the legacy CancelToken API is shown for reading older code. A timeout config option fails slow requests fast with code ECONNABORTED. Race-condition patterns and debouncing ensure the newest request always wins in a user interface.

Two tools control how long a request may live: timeout aborts after silence, and an abort signal cancels on demand. Both exist because the alternative — letting every request run to completion — produces stale UI and wasted bandwidth.

7.1 Cancelling with AbortController

Uses the modern AbortController API to cancel one or more requests. Create an AbortController, pass its signal in the request config, and call controller.abort() to cancel the in-flight request, which rejects with an error whose code is ERR_CANCELED. Aborting is the current recommended approach for new code. Attach the same signal to several requests to cancel them all together.

import axios from 'axios';

const controller = new AbortController();     // one signal, shared if you like

const promise = axios.get('/api/report', { signal: controller.signal });

// cancel from a button handler, an unmount hook, or a timer
controller.abort();

promise.catch((error) => {
  if (axios.isCancel(error)) {
    console.log('Request cancelled:', error.message);   // silently ignore
  }
});

controller.abort() fires the signal and the in-flight request rejects with a cancel error; axios.isCancel lets you ignore those silently and rethrow everything else.

7.2 The legacy CancelToken

Shows the legacy CancelToken API so you can read and fix existing code that uses it. You create a token with axios.CancelToken.source(), pass token in the config, and call source.cancel with an optional message when you want to abort. The cancel reason surfaces in error.code as ERR_CANCELED. Migrate new work to the AbortController approach, keeping CancelToken only for maintaining code that already uses it.

import axios from 'axios';

const source = axios.CancelToken.source();     // a token plus its cancel function

axios.get('/api/slow', { cancelToken: source.token })
  .catch((error) => {
    if (axios.isCancel(error)) console.log('cancelled by caller');
  });

source.cancel('user navigated away');          // choose the message seen above

CancelToken.source gives you a token to pass and a cancel() to call later; it still works but is deprecated in favour of AbortController.

7.3 Timeouts

Sets a timeout config option in milliseconds so slow servers fail fast instead of hanging a request forever. When a request takes longer than the timeout, Axios aborts it and rejects with an AxiosError whose code is ECONNABORTED and whose message describes the timeout. Keep users from staring at spinners by choosing a sane value per request or per instance. Handle the timeout error like any other AxiosError at the call site.

const api = axios.create({ timeout: 5000 });   // 5s of no data aborts the request

try {
  const { data } = await api.get('/stats');
} catch (error) {
  if (error.code === 'ECONNABORTED') {
    console.error('Timed out after 5 seconds');
  }
}

timeout aborts the request after the configured milliseconds with error.code ECONNABORTED, so you can tell a slow server from a down server.

7.4 Race conditions and debouncing searches

Prevents race conditions where a stale response overrides fresh data, and debounces type-ahead searches. Track the newest request by aborting the previous one with AbortController whenever a new call starts, so only the latest response is applied. Debouncing delays a search until the user pauses typing, cutting request volume. Together these patterns guarantee that in the UI the newest request always wins.

let controller = null;
let timer = null;

input.addEventListener('input', (e) => {
  clearTimeout(timer);
  timer = setTimeout(() => search(e.target.value), 300);   // debounce 300ms
});

async function search(q) {
  controller?.abort();                       // kill the previous request first
  controller = new AbortController();
  try {
    const { data } = await axios.get('/api/search', {
      params: { q },
      signal: controller.signal,
    });
    renderResults(data);
  } catch (error) {
    if (axios.isCancel(error)) return;       // superseded request — ignore quietly
    throw error;
  }
}

Aborting the previous request before starting a new one guarantees the last keystroke wins, and ignored cancel errors stop stale responses from clobbering results.

8 · Authentication Patterns

8.1 Bearer tokens8.2 The refresh-token flow8.3 Cookies and withCredentials8.4 CSRF tokens and logout on 401

Chapter eight covers authentication patterns: Bearer tokens, refresh flows, cookies, and CSRF handling. You send an Authorization: Bearer header from a request interceptor, and when an access token expires a response interceptor refreshes it and replays the failed request. Cookie-based sessions need the withCredentials option for cross-origin calls, and CSRF tokens are attached through a small interceptor. The result is authentication that survives page reloads and expired sessions.

Axios does not authenticate for you — but its interceptor machinery is exactly the right place to attach credentials, refresh tokens, and react to 401s. Every pattern in this chapter is built on the interceptor layer you already know.

8.1 Bearer tokens

Sends an Authorization: Bearer header on every request using one request interceptor. Read the token from secure storage, such as a cookie or memory, and set config.headers.Authorization to Bearer plus the token in the interceptor before returning config. Store the token safely and avoid putting it in query strings or logs. This attaches credentials to every call without repeating header code at each call site.

import axios from 'axios';

async function login(email, password) {
  const { data } = await axios.post('/auth/login', { email, password });
  sessionStorage.setItem('token', data.accessToken);   // a token store in real apps
}

api.interceptors.request.use((config) => {
  const token = sessionStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// every api.* call now carries the token automatically
const { data } = await api.get('/me');

After login stores the token, one request interceptor stamps Authorization on every later call, so call sites never think about credentials.

Prefer keeping tokens out of localStorage — an XSS bug can read it. In-memory storage or an HttpOnly cookie are safer homes for JWTs.

8.2 The refresh-token flow

Implements the refresh-token flow inside a response interceptor. When a request fails with 401, the interceptor calls your refresh endpoint to get a new access token, retries the original request with that token, and resolves the promise with its response. Guard against parallel refreshes by sharing one refresh promise across concurrent failures. One interceptor handles the whole cycle, so call sites never see an expired-token failure.

api.interceptors.response.use(
  (res) => res,
  async (error) => {
    const original = error.config;
    if (error.response?.status !== 401 || original._retry) {
      return Promise.reject(error);            // not a token problem — pass on
    }
    original._retry = true;                    // guard against refresh loops
    try {
      const { data } = await axios.post('/auth/refresh', {
        refreshToken: sessionStorage.getItem('refreshToken'),
      });
      sessionStorage.setItem('token', data.accessToken);
      original.headers.Authorization = `Bearer ${data.accessToken}`;
      return api(original);                    // replay the original request
    } catch (refreshError) {
      logout();                                // refresh failed — session is over
      return Promise.reject(refreshError);
    }
  },
);

On a 401 the interceptor refreshes the token once, patches the original request, and retries it transparently — and falls back to logout if the refresh itself fails.

8.3 Cookies and withCredentials

Uses cookies for session-based authentication and the withCredentials config option for cross-origin requests. With withCredentials: true, Axios sends the browser cookies for the target origin and accepts set-cookie headers, which same-origin calls get automatically. Set the option on an instance or per request when credentials must cross origins, and ensure the server is configured to accept them. Same-origin calls need nothing special at all.

import axios from 'axios';

// same-origin: the cookie rides along automatically, nothing to configure
await axios.get('/me');

// cross-origin (app on :3000, API on :8000): opt in with a flag
const api = axios.create({
  withCredentials: true,         // send our cookies, accept Set-Cookie back
});
await api.get('/me');            // session cookie authenticates this call

Cookies authenticate silently on same-origin requests; withCredentials opts cross-origin browsers into sending and receiving them.

8.4 CSRF tokens and logout on 401

Adds the CSRF token dance common in cookie-based frameworks and logs the user out on session expiry. A request interceptor reads a cookie-delivered CSRF token and includes it in a header on mutating requests, matching what the server verifies. A response interceptor catches 401 responses and bounces the user to the login screen or resets session state. Two small interceptors cover both concerns for every request.

// Laravel/Sanctum style: fetch the cookie, echo it back as a header
await axios.get('/sanctum/csrf-cookie');
axios.defaults.headers.common['X-XSRF-TOKEN'] = readCookie('XSRF-TOKEN');

// global 401 reaction: clear local state, then redirect to login
api.interceptors.response.use(
  (res) => res,
  (error) => {
    if (error.response?.status === 401) {
      authStore.logout();               // drop token and user state
      window.location.assign('/login'); // one bounce, app reloads clean
    }
    return Promise.reject(error);
  },
);

Frameworks with cookie-based CSRF usually expect the token echoed back in a header, and a global 401 interceptor centralizes the session-expired logout dance.

9 · Axios with Frameworks

9.1 Vue 3: a service layer and composable9.2 React: a data-fetching hook9.3 Nuxt integration and SSR9.4 Axios in Node and Express

Chapter nine connects Axios to Vue, React, Nuxt, and Node by building a thin service layer reused across components and server handlers. In Vue you expose API calls through a composable, and in React through a data-fetching hook built on useEffect and useCallback. Nuxt wires Axios in as a plugin that handles the server and client baseURL split, and Node uses the same client inside Express routes. One API layer serves every framework.

Axios itself is framework-agnostic. The value in a framework comes from a small service layer — one module that owns the instance, the interceptors, and the typed functions — that components then import.

9.1 Vue 3: a service layer and composable

Separates API calls into a dedicated service module and wires them into Vue components with a composable. The service owns transport, calling axios with the right methods and config, while the component only describes intent such as load, save, or delete. A composable function wraps the service with reactive state and loading flags using ref or reactive. Components stay lean and the transport logic lives in one testable place.

// api/posts.js — thin service layer over the shared client
import client from './client';            // shared instance with interceptors

export const postsApi = {
  list: () => client.get('/posts'),
  byId: (id) => client.get(`/posts/${id}`),
  create: (body) => client.post('/posts', body),
  remove: (id) => client.delete(`/posts/${id}`),
};

The service module wraps the shared client instance so components never touch axios config and the transport stays in exactly one place.

// composables/usePosts.js — Vue 3 composable consuming the service
import { ref, onMounted } from 'vue';
import { postsApi } from '../api/posts';

export function usePosts() {
  const posts = ref([]);
  const loading = ref(false);
  const error = ref(null);

  onMounted(async () => {
    loading.value = true;
    try {
      const { data } = await postsApi.list();
      posts.value = data;
    } catch (e) {
      error.value = e.userMessage ?? e.message;   // normalized by an interceptor
    } finally {
      loading.value = false;
    }
  });

  return { posts, loading, error };   // template: v-for over posts once it settles
}

The composable owns all the reactive state (posts, loading, error) so any component gets a full loading-with-error experience in one import.

9.2 React: a data-fetching hook

Exposes the data-fetching pattern as a React hook built on useEffect and useCallback. The hook holds state for the data, the loading flag, and the error, calls the axios service inside useEffect, and returns a reload function via useCallback. The dependency array decides when the hook refetches, and a cleanup step cancels superseded requests. Components consume the hook and render from its returned state.

import { useEffect, useState, useCallback } from 'react';
import client from '../api/client';

export function useUsers() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  const load = useCallback(async () => {
    setLoading(true);
    try {
      const { data } = await client.get('/users');
      setUsers(data);
    } catch (e) {
      setError(e.userMessage ?? e.message);
    } finally {
      setLoading(false);
    }
  }, []);

  useEffect(() => { load(); }, [load]);   // fetch on mount

  return { users, loading, error, reload: load };
}

The hook keeps error state, loading state, and a reusable reload in one place; an effect runs it once on mount, and callers trigger reload themselves.

9.3 Nuxt integration and SSR

Wires Axios into Nuxt as a plugin so every component and server handler can use a shared client. The plugin creates an axios instance with a baseURL that splits between server and browser, using an env variable such as NUXT_API_URL for the server side and a relative URL or explicit origin on the client. SSR changes where credentials and baseURLs live, so configure both environments. Make the client available everywhere through Nuxt’s plugin mechanism.

// nuxt.config.ts
export default defineNuxtConfig({
  runtimeConfig: {
    public: { apiBase: process.env.NUXT_PUBLIC_API_BASE ?? 'https://api.example.com' },
  },
});

// plugins/axios.ts — expose the instance as this.$axios everywhere
export default defineNuxtPlugin(() => {
  const config = useRuntimeConfig();
  const instance = axios.create({ baseURL: config.public.apiBase });
  return { provide: { axios: instance } };
});

The plugin creates one instance configured from runtime config, and the same $axios is available in client and server renders — with the caveat below.

Server-side renders have no window: interceptors that read cookies or localStorage must check they are running in the browser first, or the first paint breaks.

9.4 Axios in Node and Express

Uses Axios server-side inside an Express route, where the same client API works with a couple of additions. Create an axios instance and reuse it across handlers, pass an http.Agent with keepAlive for connection reuse, and map errors into HTTP responses you send to the client. The promise-based API is identical to the browser, so a handler awaits the request and forwards the data. Centralize baseURL and timeout once in the server client.

import express from 'express';
import axios from 'axios';
import https from 'node:https';

const upstream = axios.create({
  baseURL: process.env.UPSTREAM_URL,       // internal API address
  timeout: 15000,
  httpsAgent: new https.Agent({ keepAlive: true }),   // reuse connections
});

app.post('/api/reports', async (req, res) => {
  try {
    const { data } = await upstream.post('/score-reports', req.body, {
      headers: { Authorization: `Bearer ${process.env.INTERNAL_KEY}` },
    });
    res.json(data);
  } catch (error) {
    res.status(error.response?.status ?? 502).json({   // 502 if upstream never replied
      message: 'Upstream service unavailable',
    });
  }
});

In Node the same Axios client calls other services, with a keep-alive agent for connection reuse and upstream status codes mapped to your own error semantics.

10 · Testing & Best Practices

Chapter ten covers testing and best practices, mocking Axios in tests and structuring a maintainable API layer. You learn axios-mock-adapter for intercepting requests in unit tests and Mock Service Worker for network-level interception that works in Node and browsers. A TypeScript API layer with one typed function per endpoint keeps call sites safe. Security and performance habits, such as avoiding token logging, round out the chapter.

A healthy Axios setup is one you can run in tests without a network. The two mainstream tools are axios-mock-adapter (fakes axios itself) and Mock Service Worker (fakes the network layer) — pick whichever matches your existing test stack.

10.1 Mocking with axios-mock-adapter

Intercepts matching requests in tests using axios-mock-adapter so your suite never touches the network. Create an adapter on your axios instance and register handlers such as onGet or onPost that reply from fixtures with a status, data, and headers. Matching can check the URL and params, and you reset handlers between tests for isolation. It is the friendliest option when your test code already calls axios directly.

import axios from 'axios';
import MockAdapter from 'axios-mock-adapter';

const mock = new MockAdapter(axios, { delayResponse: 200 });   // simulate latency

mock.onGet('/api/users/1').reply(200, { id: 1, name: 'Ada' });

mock.onPost('/api/users').reply((config) => {
  const body = JSON.parse(config.data);
  return [201, { id: 2, ...body }];       // echo the payload back with an id
});

// in tests: axios.get('/api/users/1') now returns the fixture, no server needed
const { data } = await axios.get('/api/users/1');

axios-mock-adapter intercepts matching requests before the real network and returns fixtures, optionally with latency, so tests are fast and deterministic.

10.2 Mock Service Worker

Introduces Mock Service Worker, which intercepts at the network layer so it works identically in Node tests and browsers. MSW uses a service worker in the browser and a polyfill in Node, and your application code cannot tell the difference from a real API. Define handlers that match the request URL and method and return canned responses. This makes tests realistic and reusable across both environments.

// src/mocks/handlers.js — shared by tests (node) and dev tools (browser)
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

export const handlers = [
  http.get('/api/users', () => HttpResponse.json([{ id: 1, name: 'Ada' }])),
  http.post('/api/users', async ({ request }) => {
    const body = await request.json();
    return HttpResponse.json({ id: 2, ...body }, { status: 201 });
  }),
];

// in Vitest/Jest: const server = setupServer(...handlers) in a beforeAll,
// server.listen(), then server.close() in an afterAll.

MSW replaces the network itself, so real axios calls, fetch calls, and browser requests all hit the same handlers, making it the most integration-shaped mock.

10.3 Structuring an API layer with TypeScript

Structures an API layer with TypeScript so call sites stay safe and organized by resource. Define response interfaces, write one typed function per endpoint that calls the axios client and returns the data with the correct type, and group functions by resource such as users or orders. A small amount of shared config, like baseURL and a single instance, keeps the layer consistent. This yields compile-time safety and predictable call sites.

// types.ts
export interface User { id: number; name: string; email: string; }
export interface ListResponse<T> { items: T[]; total: number; }

// client.ts
export const api = axios.create({ baseURL: '/api' });

// services/users.ts — one typed function per endpoint
export async function fetchUser(id: number): Promise<User> {
  const { data } = await api.get<User>(`/users/${id}`);
  return data;
}

export async function listUsers(page: number): Promise<ListResponse<User>> {
  const { data } = await api.get<ListResponse<User>>('/users', { params: { page } });
  return data;
}

Typing each endpoint with a generic return type means a reshape of the API surfaces as a compile error instead of a runtime surprise.

10.4 Security and performance

Hardens the client against leaks and wasted work: never log tokens or sensitive headers, enable keep-alive in Node by passing an http.Agent with keepAlive true, and cancel superseded requests with AbortController. Use short timeouts for user-facing calls and reuse a single instance instead of creating clients per request. These small habits improve security, speed, and reliability across the whole application.

// never log credential headers
client.interceptors.request.use((config) => {
  if (import.meta.env?.MODE === 'development') {
    const safe = { method: config.method, url: config.url, params: config.params };
    console.debug('request', safe);       // Authorization deliberately absent
  }
  return config;
});

// Node: reuse sockets instead of opening a fresh TLS handshake per call
import https from 'node:https';
const api = axios.create({
  baseURL: process.env.API_URL,
  httpsAgent: new https.Agent({ keepAlive: true, maxSockets: 25 }),
});

// checklist: one instance per API, reuse via service modules, timeouts,
// abort superseded requests, keep the JSON default unless you need binary.

A dev-only logger that strips credentials, a keep-alive agent, and a short checklist cover most real-world Axios hygiene in a single glance.

A.3 Response and error fields

Maps the fields on a successful response and on an AxiosError side by side. A response gives you data, status, statusText, headers, config, and request, while an error adds the response and request objects that change depending on where the failure happened. A.4 Interceptor and cancellation reference

Summarizes the interceptor API and cancellation options at a glance. Request interceptors registered with use run in registration order before the request goes out, while response interceptors run in reverse after it returns, and eject removes a handler by its id. The cancellation options are the modern signal from AbortController or the legacy CancelToken. Keep this reference beside you while wiring middleware.

  • axios.interceptors.request.use(onFulfilled, onRejected) — attach a handler that runs before a request is sent.
  • axios.interceptors.response.use(onFulfilled, onRejected) — intercept fulfilled or rejected responses.
  • interceptor.eject(id) — remove one installed interceptor by the id its use() returned.
  • new AbortController() plus the signal config — modern cancellation; pass one signal to many requests.
  • axios.CancelToken.source() — legacy cancellation API; keep AbortController for new code.
  • axios.isCancel(err) — true when the error came from a cancel, so you can ignore it.

A.5 Glossary

Defines the terms used throughout the guide in one place, from core concepts like instance and interceptor to error-related terms such as AxiosError. Skim it whenever a chapter uses a word you have not seen before, so reading is not interrupted by unfamiliar vocabulary. Entries are short, plain definitions of the names and options the rest of the guide assumes you know.

  • AxiosError — the error object Axios produces; carries message, response, request, and code.
  • BaseURL — a prefix prepended to every relative url on an instance.
  • Config object — the plain object describing one request (method, url, params, headers, data, and more).
  • Interceptor — a handler that sees every outgoing request or every incoming response.
  • Serializer — the function turning the params object into a query string.
  • validateStatus — the predicate deciding which status codes settle the promise as fulfilled.
  • Race condition — a stale response beating a newer one; prevented by aborting superseded requests.
  • Bearer token — an Authorization header value of the form Bearer <token>.
  • withCredentials — the flag that lets cookies cross the same-origin boundary.
