<h3 id="ch1-1" data-toc>1.1 How this guide is organised</h3>

<h3 id="ch1-2" data-toc>1.2 The mindset: data over intuition</h3>
<p class="topic-desc">SEO is not a dark art. The pages that rank are the ones that are fast, honest and structured for humans first. Every decision in this guide points at a real number you can check in your own data.</p>
<h4 id="ch1-2-measure">Metrics that do not lie</h4>
<p>Click-through rate, Largest Contentful Paint, index coverage, crawl rate, backlinks gained, visibility in Search Console — pick the number that answers the question you are asking. Set up measurement <strong>before</strong> you change anything, record a baseline, and re-measure after every meaningful change. A change without a baseline is an anecdote.</p>
<div class="codeWrap"><pre><code>import csv
# baseline.py — record today's numbers before the next change
with open("search-console-clicks.csv") as f:
    rows = list(csv.DictReader(f))
clicks = [int(r["clicks"]) for r in rows]
print("baseline mean clicks/day:", round(sum(clicks) / len(clicks), 1))</code></pre></div>
<h4 id="ch1-2-priority">What to fix first</h4>
<p>Not every improvement matters at the same scale. Fix crawlability and indexing before content; fix titles and metas before rendering; fix structured data after content is stable. Rank candidate fixes by impact divided by effort, and do the high-impact, low-effort items first. Skipping ahead costs more than following the order.</p>
<div class="codeWrap"><pre><code>// prioritise.js — impact-per-effort, highest first
const fixes = [
  { name: "fix crawlability",      effort: 1, impact: 5 },
  { name: "rewrite titles/metas",  effort: 2, impact: 4 },
  { name: "add structured data",   effort: 3, impact: 2 },
];
fixes.sort((a, b) => (b.impact / b.effort) - (a.impact / a.effort));
console.table(fixes);</code></pre></div>
<div class="tip"><p>Verify a metric in your own data before trusting a blog post or a course. Tools and rules change; your own Search Console data is the ground truth.</p></div>

<h3 id="ch1-3" data-toc>1.3 Tools you will use throughout</h3>
<p class="topic-desc">You do not need expensive software to start. The single most useful free tool is Google Search Console: add your site, verify ownership, and you get real performance data straight from Google.</p>
<h4 id="ch1-3-stack">A useful free stack</h4>
<p>Google Search Console shows queries, clicks and impressions. Bing Webmaster Tools is the equivalent for Bing. Lighthouse in Chrome DevTools measures Core Web Vitals. Screaming Frog (free up to 500 URLs) crawls your site the way a search bot would. Google Trends shows keyword popularity over time. All of these are free and sufficient for most work.</p>
<div class="codeWrap"><pre><code># Can a crawler reach you today? Check before you optimise anything.
curl -s https://example.com/robots.txt
curl -s https://example.com/sitemap.xml | head -20
# How many of your pages are actually indexed?
# Search Google for:  site:example.com</code></pre></div>
<h4 id="ch1-3-guard">Guard the crawler's path</h4>
<p>Your very first crawl check should be that nothing important is blocked. A robots.txt rule that forbids CSS or JavaScript makes your site look broken to Googlebot, because it cannot render the page without them. Run this check on any new site before you go further.</p>
<div class="codeWrap"><pre><code>import re
# guard.py — refuse a robots.txt that blocks render-critical assets
robots = open("robots.txt").read()
for rule in re.findall(r"Disallow:\s*(\S+)", robots):
    if any(ext in rule for ext in (".css", ".js", ".png", ".woff2")):
        print("WARN: a crawler cannot fetch", rule)</code></pre></div>

<section class="chapter">
<h2 id="ch2" data-toc>2 ▸ How Search Engines Work</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">A search engine cannot rank a page it has not found, parsed and trusted. This chapter walks the three-stage pipeline — crawling, indexing, ranking — and the SERP features your markup can earn.</p>

<h3 id="ch2-1" data-toc>2.1 Crawling: how bots discover your pages</h3>
<p class="topic-desc">Crawlers follow links from page to page, download the HTML, and hand it to the indexer. Your job is to make crawling cheap and obvious — start with the file every crawler reads first.</p>
<h4 id="ch2-1-robots">robots.txt tells bots where to go</h4>
<p>The first request a crawler makes is <code>GET /robots.txt</code>. This text file tells it which paths it may request and which it must skip. A sane robots file for a production site looks like this. Note the <code>Sitemap:</code> line — robots.txt is one of the two places a crawler learns your sitemap's URL.</p>
<div class="codeWrap"><pre><code>User-agent: *
Allow: /
Disallow: /admin/
Disallow: /tmp/
Disallow: /search?q=

Sitemap: https://example.com/sitemap.xml</code></pre></div>
<p>robots.txt is a polite suggestion, not a lock: a crawler may still visit a disallowed URL if it is linked elsewhere, and the directive says nothing about whether a page should be indexed. For per-page control, use <code>noindex</code> instead (chapter 2.2). Never block CSS or JS files in robots.txt — the crawler needs them to render the page.</p>
<h4 id="ch2-1-budget">Crawl budget matters on large sites</h4>
<p>A site with 10,000 pages does not need 10,000 crawl requests a day. Google allocates a crawl budget from a mix of site authority, content freshness and observed demand, and it is visible in Search Console's crawl statistics. Reduce waste with a clean sitemap, canonical tags and stable URLs — pagination with <code>?page=2</code> is usually fine, tracking parameters like <code>?session=abc</code> are not. If the same page is reachable at both <code>/page</code> and <code>/page?utm_source=email</code>, a canonical tag picks one.</p>
<div class="codeWrap"><pre><code># Which crawlers hit you, and how often? (server access logs)
grep -c "Googlebot" access.log
grep -c "bingbot" access.log
# Confirm a hit is really Googlebot: reverse-DNS the client IP
nslookup 66.249.66.1</code></pre></div>
<div class="note"><p>Search Console's Index Coverage report shows exactly which URLs Google considers indexed, excluded or errored. Check it weekly.</p></div>

<h3 id="ch2-2" data-toc>2.2 Indexing: how pages are stored</h3>
<p class="topic-desc">After crawling, Google parses the HTML, extracts text and stores the page in its index. Canonical tags, meta robots and hreflang help it decide which version to keep.</p>
<h4 id="ch2-2-canonical">Canonical tags pick the winner</h4>
<p>If the same content is reachable at multiple URLs, a canonical tag tells the search engine which URL to credit. Add it to the <code>&lt;head&gt;</code> of every page — a self-referencing canonical on the preferred URL is good practice, because it keeps every duplicate pointing at the same place even when you do not control the duplicates.</p>
<div class="codeWrap"><pre><code>&lt;link rel="canonical" href="https://example.com/products/chair"&gt;</code></pre></div>
<p>For pages that exist in multiple languages, use hreflang instead — it is bidirectional, so every language variant must link back to the others, and <code>x-default</code> names the fallback for untagged browsers:</p>
<div class="codeWrap"><pre><code>&lt;link rel="alternate" hreflang="en-US" href="https://example.com/en/chair"&gt;
&lt;link rel="alternate" hreflang="de-DE" href="https://example.com/de/chair"&gt;
&lt;link rel="alternate" hreflang="x-default" href="https://example.com/en/chair"&gt;</code></pre></div>
<div class="warn"><p>A canonical is a strong hint, not a hard rule. If the content genuinely differs, if the page is not in the index, or if internal links contradict it, Google may pick a different URL. Keep canonical, internal links and the sitemap agreeing.</p></div>
<h4 id="ch2-2-norobots">Meta robots controls indexing</h4>
<p>Add <code>&lt;meta name="robots" content="noindex, follow"&gt;</code> to pages you want out of the index but whose links should still be followed for crawling. That is the standard treatment for thank-you pages, internal search results and filtered category pages. For non-HTML files such as PDFs, the equivalent is the <code>X-Robots-Tag</code> HTTP header — a meta tag in a PDF's bytes is ignored.</p>
<div class="codeWrap"><pre><code>&lt;meta name="robots" content="noindex, follow"&gt;
&lt;!-- also useful, per page: -->
&lt;meta name="robots" content="max-snippet:-1, max-image-preview:large"&gt;</code></pre></div>

<h3 id="ch2-3" data-toc>2.3 Ranking: the algorithm that decides order</h3>
<p class="topic-desc">Ranking is a multi-signal scoring system. Relevance matters first — does your page answer the query better than the alternatives — then quality: is the content trustworthy and useful?</p>
<h4 id="ch2-3-signals">The core ranking signals</h4>
<p>Google evaluates hundreds of signals, but they cluster into a few honest buckets: content relevance, the quantity and quality of links, user experience, and E-E-A-T — Experience, Expertise, Authoritativeness and Trust. Relevance gets you in the game; trust decides whether you stay.</p>
<ul>
<li><strong>Content relevance:</strong> do title, headings and body match the query, without stuffing?</li>
<li><strong>Backlinks:</strong> how many reputable, relevant sites link to you?</li>
<li><strong>User experience:</strong> Core Web Vitals, mobile-friendliness, HTTPS.</li>
<li><strong>E-E-A-T:</strong> show who wrote it and why they should be believed. Most decisive on YMYL topics.</li>
</ul>
<div class="codeWrap"><pre><code>{
  "relevance": ["title match", "heading match", "body match"],
  "trust": { "links": "count and quality", "brand": "mentions" },
  "ux": ["core web vitals", "mobile", "https"]
}</code></pre></div>
<h4 id="ch2-3-eeat">Signalling E-E-A-T in markup</h4>
<p>E-E-A-T is not a single tag — it is the sum of signals on the page and around it: a named author with credentials, a publication date that is kept honest, citations, and about/contact pages. Here is the shape of a block that carries several of those signals at once:</p>
<div class="codeWrap"><pre><code>&lt;article&gt;
  &lt;h1&gt;10 Best Espresso Machines&lt;/h1&gt;
  &lt;p&gt;Written by &lt;strong&gt;Jane Doe&lt;/strong&gt;, professional barista since 2012.&lt;/p&gt;
  &lt;p&gt;Reviewed and updated October 2026. Sources: independent lab tests.&lt;/p&gt;
&lt;/article&gt;</code></pre></div>
<div class="warn"><p>Never stuff keywords into a title or body. Modern algorithms detect it and it hurts more than it helps. Write for the reader first; the algorithm will follow.</p></div>

<h3 id="ch2-4" data-toc>2.4 SERP features and rich results</h3>
<p class="topic-desc">The results page is no longer ten blue links. Featured snippets, People Also Ask, image carousels and local packs claim most of the clicks. You can compete for several of these with structured data.</p>
<h4 id="ch2-4-schema">Structured data (JSON-LD) tells the story</h4>
<p>Add schema markup in your <code>&lt;head&gt;</code> so Google can display your content as a rich result. Product markup is the classic example — name, image, offer — and it is what enables the price and rating you see on shopping results:</p>
<div class="codeWrap"><pre><code>&lt;script type="application/ld+json"&gt;
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Espresso Machine X1",
  "image": "https://example.com/images/esp-x1.jpg",
  "description": "A 15-bar espresso machine for home use.",
  "brand": { "@type": "Brand", "name": "BrewCo" },
  "offers": {
    "@type": "Offer",
    "url": "https://example.com/products/espresso-x1",
    "priceCurrency": "USD",
    "price": "299.00"
  }
}
&lt;/script&gt;</code></pre></div>
<h4 id="ch2-4-test">Which rich results are worth the markup</h4>
<p>Not every type pays the same. Product, BreadcrumbList, Article and Organization are broad and safe. FAQPage is a special case: since August 2023 Google only shows FAQ rich results for well-known, authoritative government and health sites, so on a normal commercial site that markup is harmless but rarely displayed. Test your markup with the Rich Results Test before publishing — invalid JSON or a missing required field means no rich result at all.</p>
<div class="codeWrap"><pre><code>&lt;script type="application/ld+json"&gt;
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": [{
    "@type": "Question",
    "name": "How often should I descale my espresso machine?",
    "acceptedAnswer": {
      "@type": "Answer",
      "text": "About once a month with normal home use."
    }
  }]
}
&lt;/script&gt;</code></pre></div>
<div class="tip"><p>Only mark up content that is visible on the page. Google treats hidden structured data as spam; the FAQ answers above must appear in the text of the page.</p></div>

<h2 id="ch3" data-toc>3 ▸ Keyword Research and Search Intent</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Keywords are how you translate what users want into pages you can build and rank. This chapter covers the tiers of keywords, the intent behind them, the free tools that find them, and how to cluster them and map one intent to one page.</p>

<h3 id="ch3-1" data-toc>3.1 Keyword types and volumes</h3>
<p class="topic-desc">Keywords are not all created equal. Head terms have huge volume but brutal competition; long-tail phrases have lower volume, higher intent and far easier rankings.</p>
<h4 id="ch3-1-tiers">The keyword tiers</h4>
<p>A head term is one or two words and describes a whole category. A mid-tail term adds a qualifier. A long-tail term is three or more words and usually matches a specific moment — a problem, a budget, a brand. A single well-targeted long-tail page often converts better than a head-term page that receives a small slice of a huge total.</p>
<div class="codeWrap"><pre><code>// Head term — high volume, high competition
"espresso machine"

// Mid-tail — moderate volume, moderate competition
"best espresso machine for home"

// Long-tail — lower volume, high intent, easier to rank
"cuisinart espresso machine how to clean"
"best espresso machine under 200 dollars 2026"</code></pre></div>
<h4 id="ch3-1-difficulty">Keyword difficulty is an estimate, not a fact</h4>
<p>Volume figures from tools are sampled and extrapolated; the only real number you own is your own Search Console impressions. Keyword difficulty is likewise a commercial estimate built from the strength of the sites that currently rank. You can approximate the same idea for free: look at how many of the top ten results are strong domains and how many match the phrase exactly.</p>
<div class="codeWrap"><pre><code>// kd.js — a naive difficulty score (0-100) from free data
const kw = {
  monthlySearches: 2400,
  topTenDr: [72, 65, 58, 54, 51, 47],   // domain "rating" of the top ten
};
const avgDr = kw.topTenDr.reduce((a, b) => a + b) / kw.topTenDr.length;
const kd = Math.min(100, Math.round((avgDr / 90) * 100));
console.log("estimated difficulty:", kd);</code></pre></div>
<div class="tip"><p>Rank for the long tail first. A 60-position head term earns nothing; a top-three long-tail term earns clicks, and the authority you build moves the head term later.</p></div>

<h3 id="ch3-2" data-toc>3.2 Search intent: knowing what users want</h3>
<p class="topic-desc">Search intent is the why behind a query. There are four main types — informational, navigational, commercial and transactional — and the content format that wins is the one that matches the intent.</p>
<h4 id="ch3-2-mapping">Mapping intent to page type</h4>
<p>Informational searchers want to learn, so a guide wins. Transactional searchers want to buy, so a product page wins. The failure mode is writing a blog post for a transactional query or a category page for an informational one — either way you deliver the wrong object, and the SERP already told you so.</p>
<div class="codeWrap"><pre><code>// Informational — user wants to learn
"how to clean an espresso machine" → guide or how-to article

// Navigational — user wants a specific site
"cuisinart espresso machine official site" → homepage or brand page

// Commercial — user compares options
"best espresso machine under 200" → comparison or review roundup

// Transactional — user wants to buy
"buy cuisinart espresso machine" → product or category page</code></pre></div>
<h4 id="ch3-2-serp">Read the SERP before you build anything</h4>
<p>The ten results already ranking for a query are a free intent survey. If they are all product pages, do not write a blog post; if they are all step-by-step guides, do not build a category page. Match the dominant format, then beat it on depth.</p>
<div class="codeWrap"><pre><code># Infer intent from the shape of the current top ten
# all product/category pages      -> commercial or transactional
# listicles and "best of" guides  -> commercial informational
# wikipedia + forum threads       -> informational, hard to beat
# one local pack + contact page   -> local/navigational</code></pre></div>

<h3 id="ch3-3" data-toc>3.3 Tools and methods</h3>
<p class="topic-desc">You can do solid keyword research without paid tools by combining a few free data sources, and the workflow is the same whatever you spend.</p>
<h4 id="ch3-3-workflow">A simple, repeatable workflow</h4>
<p>Start from a seed, expand it from three independent sources, then ground it in your own data. Search Console is the most neglected of these: queries that already send you impressions are proof of demand you can satisfy better.</p>
<div class="codeWrap"><pre><code>1. Start with a seed topic: "espresso machine"
2. Read Google autocomplete for related queries.
3. Open Google Trends for the seed and read "related queries".
4. Open Search Console → Performance → Queries. See which terms
   already drive impressions to your site.
5. Cross-check with a free tool (Ubersuggest, AnswerThePublic).
6. Group by intent (see 3.2) and pick one intent per page.</code></pre></div>
<h4 id="ch3-3-autocomplete">Autocomplete as a research API</h4>
<p>Google's public suggest endpoint returns the same autocomplete list the search box shows, which makes it scriptable — handy when you have dozens of seeds. Respect each site's terms of use; this particular endpoint is public but undocumented, so don't build a business on it.</p>
<div class="codeWrap"><pre><code>import requests, urllib.parse
# suggestions.py — pull autocomplete for a seed term
q = urllib.parse.quote("espresso machine")
url = "https://suggestqueries.google.com/complete/search?client=firefox&amp;q=" + q
data = requests.get(url, timeout=10).json()
print("\n".join(data[1][:10]))</code></pre></div>
<div class="note"><p>Tool volumes hide the long tail. A "0 volume" phrase that beats you on impressions in Search Console is worth building; a tool that reports 1,000 searches a month for a phrase nobody acts on is worth ignoring.</p></div>

<h3 id="ch3-4" data-toc>3.4 Clusters and mapping queries to pages</h3>
<p class="topic-desc">Individual keywords are noise; clusters are structure. Group queries by topic and intent, assign one page per cluster, and let the page's headings and internal links cover the variations.</p>
<h4 id="ch3-4-clusters">Build the cluster spreadsheet</h4>
<p>Save every candidate query with its cluster, intent, target URL and priority. This is the working document of the whole site — content briefs, internal linking and the sitemap all flow from it. A CSV is fine at this size.</p>
<div class="codeWrap"><pre><code>cluster,query,intent,page_target,priority
buying-guide,best espresso machine under 200,commercial,/buying-guides/under-200,1
buying-guide,best machine for beginners,commercial,/buying-guides/under-200,1
how-to,how to clean espresso machine,informational,/guides/cleaning,1
how-to,how often to descale,informational,/guides/cleaning,2
brand,cuisinart official site,navigational,/brands/cuisinart,2</code></pre></div>
<h4 id="ch3-4-oneintent">One intent per page, variations in the headings</h4>
<p>Each page answers one intent; the cluster's remaining query strings become h2 sections and internal links. Grouping the same queries programmatically keeps the plan honest when it grows past a few hundred rows.</p>
<div class="codeWrap"><pre><code>// cluster.js — group query rows by their cluster field
function cluster(rows) {
  return rows.reduce((acc, r) => {
    (acc[r.cluster] ||= []).push(r.query);
    return acc;
  }, {});
}
const plan = cluster(csvRows);
console.log(Object.keys(plan));</code></pre></div>
<div class="tip"><p>If two queries have different intent, they are different clusters even when the words overlap. Splitting "how to clean" from "best machine under 200" saves you from writing one page that satisfies neither.</p></div>

<section class="chapter">
<h2 id="ch4" data-toc>4 ▸ On-Page SEO</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">On-page SEO is everything on the page you control: the title and description that appear in the results, the URL, the heading hierarchy, the internal links, and the structure of the body itself. It is the cheapest ranking work there is, and it scales to every page.</p>

<h3 id="ch4-1" data-toc>4.1 Titles and meta descriptions</h3>
<p class="topic-desc">The title tag is the single strongest on-page signal for relevance, and the description is your advert in the results. Both should be unique per page, honest, and written for the eye, not the crawler.</p>
<h4 id="ch4-1-title">Write titles that earn the click</h4>
<p>Keep titles under about 60 characters (the SERP truncates around 580 pixels), front-load the benefit, and never repeat the site name in every title — that burns half the space. A stuffed title fails twice: it looks like spam to users and dilutes the message search engines read.</p>
<div class="codeWrap"><pre><code>&lt;!-- Weak: stuffed, generic, truncated in the SERP -->
&lt;title&gt;Espresso Machine | BrewCo | Buy an Espresso Machine Online&lt;/title&gt;

&lt;!-- Strong: unique per page, benefit first -->
&lt;title&gt;Best Espresso Machines 2026 — BrewCo Reviews&lt;/title&gt;</code></pre></div>
<h4 id="ch4-1-description">Meta descriptions set the expectation</h4>
<p>Google may rewrite your description — it samples the page and picks what matches the query — but a well-written one still controls the default and the ad. Keep it 150–160 characters, summarise the page's actual value, and include one concrete detail (a number, a price, a date) that the surrounding blue links lack.</p>
<div class="codeWrap"><pre><code>&lt;meta name="description" content="We ran 12 budget espresso machines for 40 hours each. Read the 2026 rankings and the one model we sent back."&gt;</code></pre></div>
<div class="codeWrap"><pre><code>// check.js — flag a description that will truncate
const meta = document.querySelector('meta[name="description"]');
if (meta &amp;&amp; meta.content.length &gt; 160) {
  console.warn("description truncates in the SERP:", meta.content.length);
}</code></pre></div>

<h3 id="ch4-2" data-toc>4.2 URL structure and headings</h3>
<p class="topic-desc">URLs and headings are the two things a user scans before reading a word. Both should tell the story of the page in plain language.</p>
<h4 id="ch4-2-urls">URLs that survive a move</h4>
<p>Use lowercase, hyphen-separated slugs that describe the page; keep parameters for tracking only; and don't date-stamp URLs you may want to keep ranked forever. A slug is a promise — rename it and every link to it breaks unless you add a redirect.</p>
<div class="codeWrap"><pre><code>good:  /guides/cleaning-an-espresso-machine
good:  /buying-guides/espresso-machines-under-200
bad:   /post.php?id=4821&amp;cat=3
bad:   /2026/01/12/this-article-with-a-dated-slug</code></pre></div>
<div class="codeWrap"><pre><code>// slugify.js — the rule set in one function
const toSlug = (s) => s.toLowerCase()
  .replace(/[^a-z0-9]+/g, "-")
  .replace(/^-+|-+$/g, "");
console.log(toSlug("Best Espresso Machines Under $200!")); // best-espresso-machines-under-200</code></pre></div>
<h4 id="ch4-2-headings">One h1, then a real hierarchy</h4>
<p>Every page gets exactly one <code>&lt;h1&gt;</code> that names the page, then <code>&lt;h2&gt;</code>/<code>&lt;h3&gt;</code> sections that each answer one sub-question. Heading tags are an outline, not a styling tool — skip levels only when the content genuinely has no intermediate step.</p>
<div class="codeWrap"><pre><code>&lt;h1&gt;How to Clean an Espresso Machine&lt;/h1&gt;
&lt;h2&gt;What you need before you start&lt;/h2&gt;
&lt;h3&gt;Descaling solution strengths&lt;/h3&gt;
&lt;h3&gt;When to descale vs. backflush&lt;/h3&gt;
&lt;h2&gt;The weekly routine&lt;/h2&gt;</code></pre></div>
<div class="warn"><p>Do not hide text in headings — "best espresso machine" in a visually hidden span is keyword stuffing, and search engines treat hidden headings as such.</p></div>

<h3 id="ch4-3" data-toc>4.3 Internal linking</h3>
<p class="topic-desc">Internal links are how authority flows around your site and how crawlers discover deep pages. A page with no internal links pointing at it is an orphan that may never be indexed well.</p>
<h4 id="ch4-3-why">Anchor text and authority flow</h4>
<p>Link from nearby, relevant pages with descriptive anchors — the anchor text is the clue that tells a crawler what the target is about. The homepage should reach each pillar page, and each pillar should link down to its cluster. Ten thoughtful internal links beat fifty in a footer.</p>
<div class="codeWrap"><pre><code>// related.js — render cluster links from a small data array
const related = ["cleaning", "milk-frothing", "descaling-solution"];
const links = related.map(slug =&gt; `&lt;a href="/guides/${slug}"&gt;our ${slug.replace("-", " ")} guide&lt;/a&gt;`);
console.log(links.join("\n"));</code></pre></div>
<h4 id="ch4-3-orphans">Find the orphan pages</h4>
<p>After every content push, check that no page is unreachable by following links from the homepage. Web crawlers do the same walk. A cheap pass over your own files finds the strays.</p>
<div class="codeWrap"><pre><code># orphans.sh — pages no other page links to
for f in $(find . -name "*.html" -not -path "./assets/*"); do
  base=$(basename "$f")
  if ! grep -rl "href=.*$base" --include="*.html" . | grep -v "^$f$" &gt; /dev/null 2&gt;&amp;1; then
    echo "orphan: $f"
  fi
done</code></pre></div>
<div class="tip"><p>Deep-link your money pages. A product ranked on page three rarely needs more external links — it needs the authority the catalogue page is already holding, moved down to it.</p></div>

<h3 id="ch4-4" data-toc>4.4 Content structure and readability</h3>
<p class="topic-desc">Structure is on-page SEO you cannot fake: short paragraphs, real subheadings, lists, and images that carry meaning for both sighted and visually impaired readers.</p>
<h4 id="ch4-4-scannable">Write so a scanner can read it</h4>
<p>Users decide in seconds whether a page answers their query; they scan subheadings, bullets and the first sentence of each paragraph. Ordered steps belong in an <code>&lt;ol&gt;</code>, alternatives in a table, and every image needs an <code>alt</code> that describes what it shows — that text is also what image search indexes.</p>
<div class="codeWrap"><pre><code>&lt;h2 id="decaling"&gt;Descaling steps&lt;/h2&gt;
&lt;ol&gt;
  &lt;li&gt;Fill the tank with a 1:1 mix of water and descaler.&lt;/li&gt;
  &lt;li&gt;Run a brew cycle with no coffee in the portafilter.&lt;/li&gt;
  &lt;li&gt;Repeat with plain water to flush the solution out.&lt;/li&gt;
&lt;/ol&gt;
&lt;img src="tank-fill.jpg"
     alt="Filling the espresso machine water tank with a 50/50 mix"
     width="640" height="360" loading="lazy"&gt;</code></pre></div>
<h4 id="ch4-4-lead">The first 150 words carry the query</h4>
<p>The opening paragraph should answer the query's core question in plain language — this is also what appears under the title in the SERP, and it feeds featured-snippet selection. Use the target phrase naturally once or twice; synonyms and related terms are what make the page read like it was written by a human.</p>
<div class="codeWrap"><pre><code># lead.py — sanity-check that the page actually mentions its target
title = "How to Clean an Espresso Machine"
target = "clean espresso machine"
print("target in title:", target in title.lower())</code></pre></div>
<div class="note"><p>Images: use <code>width</code> and <code>height</code> attributes so the layout does not shift while loading — layout shift is a Core Web Vitals failure and a readability problem at once.</p></div>
</section>

<section class="chapter">
<h2 id="ch5" data-toc>5 ▸ Technical SEO</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Technical SEO is the plumbing: HTTPS, the sitemap, structured data, Core Web Vitals, mobile rendering and how JavaScript sites get indexed. None of it shows in the SERP directly, but all of it decides whether the rest of your work counts.</p>

<h3 id="ch5-1" data-toc>5.1 HTTPS and site security</h3>
<p class="topic-desc">Since 2014 HTTPS has been a ranking signal, and there has never been a reason to run a plain-HTTP site since: modern certificates are free, and the browser actively warns your users off insecure pages.</p>
<h4 id="ch5-1-https">Serve everything over TLS, permanently</h4>
<p>Encrypting one page is not enough — every subresource and every redirect must stay on HTTPS, and the <code>Strict-Transport-Security</code> header (HSTS) tells browsers to refuse plain HTTP for a year and never ask again. In nginx the shape is small and the effect is immediate.</p>
<div class="codeWrap"><pre><code>server {
    listen 443 ssl http2;
    server_name example.com;
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}</code></pre></div>
<h4 id="ch5-1-mixed">The mixed-content trap</h4>
<p>After you switch to HTTPS, some page still loads an image or a script over <code>http://</code> — the browser silently blocks those requests, the page looks broken to Googlebot's renderer, and the damage shows up as a "page with issues" in coverage reports. Walk the site after the switch.</p>
<div class="codeWrap"><pre><code># Verify HSTS is served on the real domain
curl -sI https://example.com | grep -i strict-transport-security
# Expect: Strict-Transport-Security: max-age=31536000; includeSubDomains</code></pre></div>
<div class="warn"><p>Serve the redirect layer correctly: <code>http://example.com</code> → <code>https://www.example.com</code> in one hop, then the <code>www</code>/non-<code>www</code> choice reflected in canonical, sitemap and Search Console property. Redirect chains cost crawl budget and dilute links.</p></div>

<h3 id="ch5-2" data-toc>5.2 Sitemap.xml and crawl directives</h3>
<p class="topic-desc">The sitemap is your assertion of which URLs matter. It does not guarantee indexing — it guarantees the crawler knows the URLs exist, and it carries freshness hints.</p>
<h4 id="ch5-2-sitemap">The sitemap format</h4>
<p>One file, UTF-8, a <code>&lt;loc&gt;</code> per indexable URL, and only URLs that return 200. Keep <code>&lt;lastmod&gt;</code> honest — lie about freshness and the crawler learns to ignore it. The hard limits: 50,000 URLs and 50 MB uncompressed per file; beyond that, split and use a sitemap index.</p>
<div class="codeWrap"><pre><code>&lt;?xml version="1.0" encoding="UTF-8"?&gt;
&lt;urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"&gt;
  &lt;url&gt;
    &lt;loc&gt;https://example.com/guides/cleaning&lt;/loc&gt;
    &lt;lastmod&gt;2026-09-30&lt;/lastmod&gt;
    &lt;changefreq&gt;monthly&lt;/changefreq&gt;
    &lt;priority&gt;0.8&lt;/priority&gt;
  &lt;/url&gt;
&lt;/urlset&gt;</code></pre></div>
<h4 id="ch5-2-index">Sitemaps of sitemaps</h4>
<p>Once you pass the per-file limits — or simply want per-section freshness — a sitemap index lists the child sitemaps, and robots.txt advertises the index. The old <code>ping</code> endpoint for Google is retired; discovery now happens via robots.txt and Search Console's Sitemaps report.</p>
<div class="codeWrap"><pre><code>&lt;?xml version="1.0" encoding="UTF-8"?&gt;
&lt;sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"&gt;
  &lt;sitemap&gt;
    &lt;loc&gt;https://example.com/sitemap-guides.xml&lt;/loc&gt;
  &lt;/sitemap&gt;
  &lt;sitemap&gt;
    &lt;loc&gt;https://example.com/sitemap-products.xml&lt;/loc&gt;
  &lt;/sitemap&gt;
&lt;/sitemapindex&gt;</code></pre></div>
<div class="tip"><p>A page in the sitemap that returns 404 (or a redirect) is a defect report from your own file. Build the sitemap from the pages that actually exist, not from a stale export.</p></div>

<h3 id="ch5-3" data-toc>5.3 Structured data (JSON-LD)</h3>
<p class="topic-desc">Structured data cannot make a bad page rank, but it can upgrade a good one into a rich result. JSON-LD is Google's preferred syntax, and half the work is knowing which types to mark up at all.</p>
<h4 id="ch5-3-jsonld">Mark up what matters</h4>
<p>Article, Product, Organization, BreadcrumbList and Person cover most of a normal site. Put the JSON-LD in the <code>&lt;head&gt;</code>, keep the values in sync with the visible page, and remember that structured data describes the page it is on — a Product block on a category page confuses both users and parsers.</p>
<div class="codeWrap"><pre><code>&lt;script type="application/ld+json"&gt;
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "How to Clean an Espresso Machine",
  "author": { "@type": "Person", "name": "Jane Doe" },
  "datePublished": "2026-01-12",
  "dateModified": "2026-09-30",
  "image": "https://example.com/images/cleaning.jpg"
}
&lt;/script&gt;</code></pre></div>
<h4 id="ch5-3-validate">Validate before you ship</h4>
<p>The Rich Results Test checks the whole journey: syntax, required fields and eligibility for rich results. A quick <code>json.tool</code> check catches the syntax half in CI, so an edit cannot ship broken markup.</p>
<div class="codeWrap"><pre><code># CI step — fail the build on malformed schema JSON
python -m json.tool schema.json &gt; /dev/null &amp;&amp; echo "schema JSON is valid"</code></pre></div>
<div class="warn"><p>Never mark up fake content — a review you did not receive, an offer you cannot fulfil. Google's policy enforcement on self-serving reviews and fake offers has ended in manual actions for far bigger sites than yours.</p></div>

<h3 id="ch5-4" data-toc>5.4 Core Web Vitals and mobile-friendliness</h3>
<p class="topic-desc">Core Web Vitals are the three user-experience numbers Google measures in the field: LCP, INP and CLS. They are a ranking factor inside the page experience signal, and they are the ones you can actually fix.</p>
<h4 id="ch5-4-cwv">The three numbers and their thresholds</h4>
<p>Largest Contentful Paint must load the main content within 2.5 s; Interaction to Next Paint (which replaced First Input Delay in March 2024) must stay under 200 ms; Cumulative Layout Shift must stay below 0.1. Measure in the field — CrUX data — not just under a lightbulb: a fast lab on a fast machine proves nothing about a phone on 4G.</p>
<div class="codeWrap"><pre><code># Field-style audit from the command line
npx lighthouse https://example.com \
  --only-categories=performance,seo \
  --output=json --output-path=audit.json \
  --chrome-flags="--headless"</code></pre></div>
<h4 id="ch5-4-measure">Instrument the metrics yourself</h4>
<p>Your analytics can carry real Core Web Vitals if the page reports them. The PerformanceObserver API exposes each metric as it happens; send the values to your analytics instead of relying on a third-party aggregator with a sample of its own.</p>
<div class="codeWrap"><pre><code>new PerformanceObserver((list) =&gt; {
  for (const entry of list.getEntries()) {
    if (entry.entryType === "largest-contentful-paint") {
      console.log("LCP:", entry.startTime.toFixed(0), "ms");
    }
  }
}).observe({ type: "largest-contentful-paint", buffered: true });</code></pre></div>
<h4 id="ch5-4-mobile">Mobile-first indexing is the only indexing</h4>
<p>Google has indexed the mobile experience of new sites since 2021 and of old sites for years before that. The test is brutal and concrete: fetch your URL with a phone-sized viewport and check that the content, links and structured data are all there. If desktop and mobile differ, the mobile version wins.</p>
<div class="codeWrap"><pre><code># The mobile pass — is the content present at a phone viewport?
npx lighthouse https://example.com \
  --form-factor=mobile \
  --only-categories=seo \
  --output=json --output-path=mobile-audit.json \
  --chrome-flags="--headless --window-size=375,812"</code></pre></div>
<div class="tip"><p>CLS is usually the easiest win: reserve sizes for images and ad slots, and stop injecting banners above the content after load. One <code>width</code>/<code>height</code> pass across a site often clears the 0.1 threshold entirely.</p></div>

<h3 id="ch5-5" data-toc>5.5 Rendering and JavaScript SEO</h3>
<p class="topic-desc">Google renders pages with headless Chromium, so JavaScript-only content can rank — but rendering is queued, re-fetched and re-rendered, and anything invisible in the raw HTML waits for that pipeline. Make the crawler's first fetch count.</p>
<h4 id="ch5-5-render">Serve the content in the first HTML</h4>
<p>If your content only exists after client-side JavaScript runs, the crawler must spend a rendering-queue turn to see it — delayed indexing, fragile indexing, and on a slow renderer, sometimes none at all. Server-side rendering, static prerendering or a hybrid (the "islands" pattern) give the crawler complete HTML on the first request.</p>
<div class="codeWrap"><pre><code># Compare what the crawler sees before JavaScript runs
curl -s https://example.com/spa | grep -c "Best Espresso"   # 0 on a client-only SPA
curl -s https://example.com/ssr | grep -c "Best Espresso"   # 1 on a server-rendered page</code></pre></div>
<h4 id="ch5-5-urls">Real URLs, not hash routes</h4>
<p>Each state of an app should be a real URL a crawler can fetch and a user can share. Hash routing collapses every state into one address — one URL, many versions of it, and the crawler only ever sees the first. Use <code>history.pushState</code> and give each route its own title and canonical.</p>
<div class="codeWrap"><pre><code>// Give every state a real URL the crawler can fetch and index
history.pushState({}, "", "/guides/cleaning");

// Avoid hash routing: /#/guides/cleaning is one URL with many states
// and only receives the crawler's render of the first one</code></pre></div>
<div class="note"><p>Blocking Googlebot on <code>robots.txt</code> does not stop it from finding your JavaScript — it prevents it from rendering. A JS-heavy site with JS blocked in robots.txt is the worst combination: an empty page, perfectly crawled.</p></div>
</section>

<section class="chapter">
<h2 id="ch6" data-toc>6 ▸ Content, E-E-A-T and Topical Authority</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Content is where relevance is won or lost. This chapter covers depth (the specification the guides here are graded on), entities and semantic coverage, freshness, and the E-E-A-T and brand signals that turn a page from "has the words" into "is the authority".</p>

<h3 id="ch6-1" data-toc>6.1 Content depth and satisfying the query</h3>
<p class="topic-desc">Depth is the specification, not word count: a page that answers the question, its sub-questions and the follow-ups ranks above a padded one that repeats one paragraph across ten headings.</p>
<h4 id="ch6-1-depth">A floor, not a target</h4>
<p>Thin content used to rank on volume alone; modern quality systems require substance. The library's own depth rule is a useful floor: at least 1,500 bytes of prose per section and at least two code samples — a construct shown but never run is a description. A 300-word "guide" with twelve subheadings is thinner than it looks.</p>
<div class="codeWrap"><pre><code># Strip tags, then count words — a cheap depth floor check
sed 's/&lt;[^&gt;]*&gt;//g' page.html | wc -w</code></pre></div>
<h4 id="ch6-1-outline">Outline the question, then answer it</h4>
<p>Before writing, list the sub-questions a reader has the moment they land: which to buy, how to test, who each pick suits, what breaks. Each one becomes a section that earns its place. This is also the fastest way to win People Also Ask boxes — answer real questions in dedicated headings.</p>
<div class="codeWrap"><pre><code>{
  "query": "best espresso machine under 200",
  "sections": [
    "how we tested: 40 hours across 12 machines",
    "rankings with price-to-performance data",
    "common failure modes and maintenance cost",
    "who each pick is for"
  ]
}</code></pre></div>
<div class="warn"><p>Word count alone is not depth. A 2,000-word page that never states a fact, a number or a decision is still thin — it just takes longer to read.</p></div>

<h3 id="ch6-2" data-toc>6.2 Entities and semantic relevance</h3>
<p class="topic-desc">Search engines match meaning, not just strings. They read a page as a set of entities — machines, people, materials, units — and their relationships, which is why natural language about a topic beats a phrase-lattice of exact-match keywords.</p>
<h4 id="ch6-2-entities">Cover the topic's vocabulary</h4>
<p>If you write about espresso machines, readers and crawlers alike expect the vocabulary of the topic: portafilter, brew pressure, burr grinder, descaling, temperature stability. Naming the entities directly — with correct, precise terms — signals that the page is about the subject, not just a keyword.</p>
<div class="codeWrap"><pre><code>{
  "entities": ["espresso machine", "portafilter", "descaling",
               "brew pressure", "burr grinder"],
  "related_units": ["15 bar", "58 mm", "1200 W", "1.8 L tank"]
}</code></pre></div>
<h4 id="ch6-2-questions">Mine People Also Ask for the question graph</h4>
<p>People Also Ask boxes are a live list of the sub-questions the search engine itself thinks the topic raises. Harvest them, answer the ones your page doesn't, and fold them in as headings — they are the semantic gaps the SERP is showing you for free.</p>
<div class="codeWrap"><pre><code># Questions mined from the PAA box, mapped to the answer page
question,answer_page,type
does a cheap machine make good espresso?,/guides/under-200,explainer
how often should i descale?,/guides/cleaning,how-to
what grind size for a portafilter?,/guides/grind-size,explainer</code></pre></div>
<div class="tip"><p>Answer the question in the heading's own words before you qualify it. "Does a cheap machine make good espresso? Yes — with caveats." is featured-snippet bait; burying the answer three paragraphs down is how you lose it.</p></div>

<h3 id="ch6-3" data-toc>6.3 Freshness and content upkeep</h3>
<p class="topic-desc">Freshness is not a universal signal — "how to clean a machine" does not go stale, "best machine under 200 in 2026" does. The rule is to review what degrades and to leave honest dates on the page.</p>
<h4 id="ch6-3-fresh">The freshness factor is topic-shaped</h4>
<p>Compare-intent, pricing and news pages decay on a schedule; timeless how-tos barely move. Keep a review calendar per page so nothing quietly rots: prices, product lines and rankings date fast, and a page that says "2026" in July 2027 with last year's prices has a credibility problem that no internal link can fix.</p>
<div class="codeWrap"><pre><code># review_schedule.yaml — when each money page gets re-checked
review_schedule:
  - path: /buying-guides/under-200
    cadence: monthly
    last: 2026-09-14
    next: 2026-10-14
  - path: /guides/cleaning
    cadence: yearly
    last: 2026-01-10
    next: 2027-01-10</code></pre></div>
<h4 id="ch6-3-review">Update rather than rewrite</h4>
<p>Significant updates get a new <code>dateModified</code> and a visible "reviewed on" line; the URL stays put so links and rankings survive. Never fake a date just to look fresh — the system compares dates and content, and a "just updated" page with last year's screenshots is a signal you cannot walk back.</p>
<div class="codeWrap"><pre><code># When was the source file last actually changed?
git log -1 --format=%cd --date=short -- buying-guides/under-200.md</code></pre></div>

<h3 id="ch6-4" data-toc>6.4 Author, trust and brand signals</h3>
<p class="topic-desc">E-E-A-T adds up from signals around the page: who wrote it, how they are identified, and what the brand is known for. It matters everywhere and is decisive on YMYL topics — health, money, legal.</p>
<h4 id="ch6-4-eeat">Make the author a real person</h4>
<p>An author byline with a real name, a role and a credential — plus an author page collecting their work — is the cheapest E-E-A-T win available. For YMYL topics it is effectively mandatory: anonymous money advice is a trust vacuum.</p>
<div class="codeWrap"><pre><code>&lt;aside class="author-bio"&gt;
  &lt;img src="jane.jpg" alt="Jane Doe, professional barista" width="120" height="120"&gt;
  &lt;p&gt;&lt;strong&gt;Jane Doe&lt;/strong&gt; has run a specialty coffee bar since 2012
  and writes BrewCo's buying guides.&lt;/p&gt;
&lt;/aside&gt;</code></pre></div>
<h4 id="ch6-4-brand">Brand mentions, linked or not</h4>
<p>Google has long treated unlinked brand mentions as a weaker but real signal, and its 2024 documentation placed brand reputation inside the quality system. Monitor mentions, earn links from the sites that mention you, and keep name, address and contact details consistent everywhere they appear.</p>
<div class="codeWrap"><pre><code># A weekly sweep for unlinked brand mentions
grep -rio "brewco" . --include="*.html" | wc -l
# then: where is the mention, and is a link missing?</code></pre></div>
<div class="note"><p>An about page, a contact page and an editorial policy are not filler — they are the trust documentation the quality raters are trained to look for. Sites that hide who is responsible for them are opted out of the benefit of the doubt.</p></div>
</section>

<section class="chapter">
<h2 id="ch7" data-toc>7 ▸ Off-Page SEO and Link Building</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">Off-page SEO is everything that happens away from your domain: the links pointing at it, the anchors those links carry, and how the rest of the web talks about you. It is also the discipline most likely to get you penalised if you shortcut it.</p>

<h3 id="ch7-1" data-toc>7.1 Why backlinks still matter</h3>
<p class="topic-desc">Links are still the web's citation system, and despite decades of algorithm evolution they remain a top-three ranking signal. What changed is that their value is judged by relevance and intent, not just count.</p>
<h4 id="ch7-1-value">Votes, weighted by relevance</h4>
<p>A link from a page about espresso machines says more than a link from a random directory, whatever the domain's overall size. Build a prospect list scored on relevance and the site's own standing, and keep a status column so the pipeline actually closes.</p>
<div class="codeWrap"><pre><code># prospects.csv — relevant first, then strong
url,relevance,status
https://coffeeblog.example/reviews,high,contacted
https://industry-mag.example/buyers-guide,high,not-contacted
https://random-directory.example/listing,low,skip
https://power-domain.example/anything,low,skip</code></pre></div>
<h4 id="ch7-1-profile">Compare profiles, not counts</h4>
<p>Your competitor may have ten times your links — but if half of yours are from sites in your niche and theirs are from a PBN, the comparison flatters them. Export the backlink lists of the top three ranking pages and diff them against yours; the links they have and you don't are the road map.</p>
<div class="codeWrap"><pre><code># Which sites link to the top-3 pages but not to you?
sort -u mine.txt -o mine.txt
sort -u theirs.txt -o theirs.txt
comm -23 theirs.txt mine.txt</code></pre></div>
<div class="warn"><p>A sudden spike of 900 links from unrelated domains is not a win; it is spam detection waiting to trigger. Real campaigns produce a slope, not a cliff.</p></div>

<h3 id="ch7-2" data-toc>7.2 Anchor text and link diversity</h3>
<p class="topic-desc">The words inside a link describe the target to a crawler — which is why exact-match anchors are powerful, and why too many of them read as manipulation.</p>
<h4 id="ch7-2-anchors">A healthy anchor profile is mostly branded</h4>
<p>Real websites link to you because of your name — so a natural profile is majority <strong>branded</strong> anchors, with partial-match, naked URLs and generic "click here" filling the middle. Exact-match anchors should be a small minority; they are the profile of someone who bought the links.</p>
<div class="codeWrap"><pre><code># Anchor distribution of a healthy site
branded   62%   (example.com, BrewCo)
partial   18%   (best espresso machines guide)
naked      8%   (https://example.com)
generic    5%   (click here, read more)
exact      7%   (best espresso machine under 200)</code></pre></div>
<h4 id="ch7-2-odo">Flag over-optimised anchors early</h4>
<p>If more than about a fifth of your anchors are exact-match for one phrase, you have a problem to unwind before it becomes a penalty: ask for anchor changes first, and log every request so the proportion is on record.</p>
<div class="codeWrap"><pre><code># How many of your total backlinks carry the exact target phrase?
grep -c "best espresso machine under 200" anchors.txt
grep -c "^.*$" anchors.txt</code></pre></div>
<div class="note"><p>Internal links carry the same rules in miniature. Sitewide footer links all saying "espresso machines" do not help anyone — they dilute the headline anchor to a boilerplate row.</p></div>

<h3 id="ch7-3" data-toc>7.3 Digital PR and earning links</h3>
<p class="topic-desc">The only links that compound are ones you earn because the content is worth citing. Digital PR is the craft of giving journalists, bloggers and directories a reason to link — usually something they did not have before.</p>
<h4 id="ch7-3-assets">Build linkable assets, not blog posts</h4>
<p>Original data, runnable tools and honest experiments earn links; another "top ten tips" list does not. The strongest asset for most sites is proprietary data that answers a question no one else can. A pitch that leads with the data and one surprising finding outperforms a generic "check out our article" by orders of magnitude.</p>
<div class="codeWrap"><pre><code>Subject: 40 espresso machines run to failure — we logged every breakdown

Hi [Name],

We ran 40 budget espresso machines through 12 months of simulated daily
use and logged every failure. One finding: the cheapest machine to buy
was not the cheapest to own.

The dataset is here: [link]. Happy to send a one-paragraph summary
written for your readers.</code></pre></div>
<h4 id="ch7-3-broken">The broken-link play</h4>
<p>Resource pages decay — someone's curated list of coffee guides is full of 404s right now. Find the dead links on relevant pages, then offer your live, better page as the replacement. It is a genuine fix for the site owner and a genuine link for you.</p>
<div class="codeWrap"><pre><code># Spot dead resource pages worth rebuilding against
curl -s -o /dev/null -w "%{http_code} %{url_effective}\n" \
  https://example.org/resources/coffee-buying-guide
# 404 → the page is gone; the site still wants that resource</code></pre></div>
<div class="tip"><p>Track every earned link's context: the page, its relevance and the anchor. When the algorithm changes, that log is the first thing you will need.</p></div>

<h3 id="ch7-4" data-toc>7.4 Disavow and link hygiene</h3>
<p class="topic-desc">Links decay, domains get sold, and occasionally you inherit a profile somebody else built badly. Hygiene is a periodic audit and a documented removal process — not a panic tool.</p>
<h4 id="ch7-4-hygiene">Audit, remove, then — only then — disavow</h4>
<p>Quarterly, export your backlinks and triage: links from sites that no longer exist are noise; links from irrelevant, paid or outright spam destinations are liabilities. Ask for removal first — most owners oblige — and use Google's disavow file only for what remains, one domain or URL per line. It is a text file uploaded in Search Console, and it is read as a strong suggestion, not a command.</p>
<div class="codeWrap"><pre><code># disavow.txt — one entry per line; domain: prefix covers the whole site
domain:spam-directory.example
domain:paid-links-network.example
https://old-site.example/directory/listing</code></pre></div>
<h4 id="ch7-4-velocity">Watch the velocity curve</h4>
<p>Link velocity — new referring domains per month — is a health chart, not a score. A flat line means nobody new is finding you; a cliff is a purchased burst. Either extreme earns the wrong kind of attention.</p>
<div class="codeWrap"><pre><code># referring domains gained per month
month,new_domains
2026-01,12
2026-02,9
2026-03,940     # investigate a 40x cliff, don't celebrate it
2026-04,14</code></pre></div>
<div class="warn"><p>Do not disavow a domain "just in case". Removing legitimate links is permanent self-harm — the disavow file is not reversible by simply deleting the line, and Google has cautioned that an over-broad disavow can destroy more value than any penalty would have.</p></div>

<section class="chapter">
<h2 id="ch8" data-toc>8 ▸ Measurement and Audits</h2>
<div class="ch-toc"></div></div>
<p class="topic-desc">The loop closes with measurement: what Google says about your pages, what your analytics say about users, where you rank, and how to find problems before an update does. This chapter also covers surviving algorithm updates without losing your nerve.</p>

<h3 id="ch8-1" data-toc>8.1 Search Console: the source of truth</h3>
<p class="topic-desc">Search Console is the only tool with Google's actual data: queries, average position, click-through, index coverage and the pages Google decided are broken. If you install one tool, install this one.</p>
<h4 id="ch8-1-reports">The reports that matter</h4>
<p>Performance gives you real clicks, impressions and average position per query and per page — volumes from every other tool are estimates; these are receipts. Coverage tells you what is indexed, what is excluded and why. Sitemaps confirms your file parses. Pivot the Performance export: queries with high impressions and low CTR are title-and-description problems; queries just below position 10 are on-page improvement targets.</p>
<div class="codeWrap"><pre><code># ctr.py — find the two failure modes in a Performance export
rows = [
    {"query": "how to clean espresso machine", "clicks": 41, "impressions": 320, "position": 2.9},
    {"query": "best espresso machine", "clicks": 12, "impressions": 480, "position": 9.4},
]
for r in rows:
    ctr = r["clicks"] / r["impressions"]
    print(r["query"].ljust(35), f"ctr={ctr:5.1%}  pos={r['position']}")</code></pre></div>
<h4 id="ch8-1-inspect">URL Inspection is the debugger</h4>
<p>When a page is missing from results, URL Inspection re-fetches it and tells you the crawl, render and indexing verdict, the chosen canonical and any blocking directives. It answers the single most common question — "why is my page not indexed?" — with a definitive report instead of a forum post.</p>
<div class="codeWrap"><pre><code># The Indexing API request shape (OAuth required)
{
  "inspectionUrl": "https://example.com/guides/cleaning",
  "siteUrl": "sc-domain:example.com",
  "inspectionType": "URL_INSPECTION"
}</code></pre></div>
<div class="note"><p>Average position in Search Console is an average of many contexts — device, region, personalisation. Use it to detect direction, not to promise a client "position 4".</p></div>

<h3 id="ch8-2" data-toc>8.2 Analytics: GA4 basics</h3>
<p class="topic-desc">Search Console says how you appeared; GA4 says what happened after the click. It is event-based — every interaction is an event with parameters — and "conversions" are now called key events.</p>
<h4 id="ch8-2-events">Events in, dashboards out</h4>
<p>The gtag snippet is the same for every site: a config call with your measurement ID, then events for the moments that matter — purchases, signups, searches. GA4's automated events cover page views and scrolls; you define the rest. BigQuery export (free tier, up to 1M events/day) turns your raw event stream into SQL territory.</p>
<div class="codeWrap"><pre><code>&lt;script async src="https://www.googletagmanager.com/gtag/js?id=G-ABCDEF1234"&gt;&lt;/script&gt;
&lt;script&gt;
  window.dataLayer = window.dataLayer || [];
  function gtag() { dataLayer.push(arguments); }
  gtag('js', new Date());
  gtag('config', 'G-ABCDEF1234');
&lt;/script&gt;</code></pre></div>
<h4 id="ch8-2-search">Internal search is a content gap detector</h4>
<p>What visitors search for inside your site is demand you are not satisfying with a page. Log the search term and the number of results shown; a term with zero results is a page brief in waiting.</p>
<div class="codeWrap"><pre><code>// Fire on internal search submit — then mine it for content gaps
gtag('event', 'view_search_results', {
  search_term: 'espresso machine under 200',
  results: 3
});</code></pre></div>
<div class="tip"><p>Join Search Console and GA4 on the URL: queries that send traffic that bounces are different from queries that convert. Rank your keywords by conversions, not by clicks — the headline number flatters the wrong pages.</p></div>

<h3 id="ch8-3" data-toc>8.3 Rank tracking without going mad</h3>
<p class="topic-desc">Per-keyword rank is noisy by nature: personalisation, geography and device meaning no two people see the same results. Track direction and rate of change, never today's exact number.</p>
<h4 id="ch8-3-noise">Positions move; directions persist</h4>
<p>Weekly averages smooth the noise. A page that goes 3, 4, 5, 6 is sliding out whether today's refresh says 5 or 4; a page creeping 9, 8, 7 is entering the window where clicks start. Log the weekly value and compute movement across the window.</p>
<div class="codeWrap"><pre><code>// movement.js — direction over a six-week window, one number
const ranks = [3, 4, 5, 6, 2, 3];     // weekly average positions
const delta = ranks[ranks.length - 1] - ranks[0];
console.log(delta &lt; 0 ? `up ${-delta}` : `down ${delta}`);</code></pre></div>
<h4 id="ch8-3-check">The honest manual check</h4>
<p>Tool dashboards drift from reality all the time. A manual check — incognito window, logged out, default region — is the ground truth for a handful of money keywords, and it is free. Keep it to keywords where a single position actually changes revenue.</p>
<div class="codeWrap"><pre><code># Manual spot-check: clean context, no personalisation
google-chrome --incognito \
  "https://www.google.com/search?q=best+espresso+machine"</code></pre></div>
<div class="warn"><p>Do not let a rank tracker gate your campaign. Track the clusters you can influence — and measure the change in clicks in Search Console, which is the number your accounts department will believe.</p></div>

<h3 id="ch8-4" data-toc>8.4 A systematic site audit</h3>
<p class="topic-desc">An audit is a checklist run in order, not a mood: crawl, index, on-page, technical, content, links, then triage what it found. Run it quarterly and after any platform migration.</p>
<h4 id="ch8-4-order">The seven passes, in order</h4>
<p>Start with a crawl (a crawler's free tier covers small sites) so later passes have a real inventory. Then check indexing against that inventory, then titles and metas, then h1s and canonicals, then the sitemap versus actual pages, then redirects and internal links. Stop each pass only when its faults are recorded; the file of faults is the working document.</p>
<div class="codeWrap"><pre><code># audit.sh — cheap per-page structural checks
for f in *.html; do
  h1s=$(grep -c "&lt;h1" "$f")
  canons=$(grep -c 'rel="canonical"' "$f")
  printf "%-30s h1:%s canonical:%s\n" "$f" "$h1s" "$canons"
done</code></pre></div>
<h4 id="ch8-4-triaging">Severity, evidence, fix</h4>
<p>Every finding records how bad it is, the evidence that proves it, and the fix that closes it — otherwise a 200-row audit becomes a 200-item backlog nobody trusts. Fix the high/severe rows in the same month you find them.</p>
<div class="codeWrap"><pre><code>severity,area,issue,evidence,fix
high,index,noindex on 200 commerce pages,coverage report,remove the noindex tag
medium,onpage,32 duplicate titles,audit export,rewrite each title
medium,technical,5 redirect chains,screaming frog,flatten to one hop</code></pre></div>
<div class="tip"><p>Audit the sitemap by hand once a year: does every <code>&lt;loc&gt;</code> still return 200, still have a canonical that matches it, and still belong in the index? The file is a contract, and contracts need reviewing.</p></div>

<h3 id="ch8-5" data-toc>8.5 Algorithm updates and recovery</h3>
<p class="topic-desc">Core updates land a few times a year and can move visibility by double digits overnight. The professional response is calm forensics: confirm the drop is real, find the delta, fix the cause once, and wait out the rollout.</p>
<h4 id="ch8-5-track">Correlate, do not panic</h4>
<p>Keep a log of announced update dates next to your daily sessions and rank data. A traffic dip on the day a core update ships is a correlation worth investigating; the same dip on a bank holiday is a calendar.</p>
<div class="codeWrap"><pre><code># correlate.py — did sessions move on the day core updates shipped?
updates = [("March 2026 core", "2026-03-12"), ("June 2026 spam update", "2026-06-04")]
sessions = {"2026-03-10": 1240, "2026-03-12": 1103, "2026-03-14": 968}
for name, day in updates:
    print(name, "->", sessions.get(day, "no data"))</code></pre></div>
<h4 id="ch8-5-playbook">The recovery playbook</h4>
<p>When a core update costs you positions, the correct order is: prove the drop is real (seasonality, tracking, outages), check index coverage and server logs, compare the pages that fell against the pages that rose, fix the underlying difference — content depth, speed, links, E-E-A-T — once, and then wait. Core updates roll out over weeks, and recovery is measured on the next cycle, not the next day.</p>
<div class="codeWrap"><pre><code>1. Is the drop real?  Seasonality, a tracking tag change, a server outage.
2. What changed in the index?  Coverage report and the pages that fell.
3. Find the delta.  Weaker content, thin sections, lost links, slower pages?
4. Fix the cause once.  Do not re-template the whole site on a hunch.
5. Re-submit and wait.  Core updates take weeks to fully roll out.</code></pre></div>
<div class="warn"><p>Hiring a "penalty removal" specialist in week one is how sites get worse. The systems have no inbox for complaints; they respond to a changed page, a changed profile and a changed measuring stick — all of which you control.</p></div>
