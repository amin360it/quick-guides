Welcome — How to Use This Packaging & Publishing Guide

What this guide coversThe ecosystems coveredHow the chapters fit togetherThe legal ground you stand on

Every ecosystem has a registry, and the differences between them are mostly about trust, immutability and who can publish. Once you know those three questions, the per-ecosystem mechanics in the second half of this guide are variations on a theme rather than forty unrelated procedures.

What this guide covers

You have written something other people could use — a library, a plugin, a theme, a container, a CLI tool — and you want to put it somewhere discoverable and installable. This guide covers the shared foundations, then every major ecosystem, then the parts nobody writes down.

It does not cover building a registry of your own, or the internal mechanics of any one package manager. For a deep dive on one ecosystem, its own guide in this library is the place to go — Composer has a full chapter in php.html, and the npm, Docker and Terraform material has its own guides.

The legal ground you stand on

// BEFORE YOU PUBLISH, SETTLE THESE. They are not code problems.

// 1. LICENCE. Every registry demands one, and a permissive licence
//    on your library can impose terms on everything built with it.
//    MIT, Apache-2.0 and BSD are the common permissive choices.
//    Apache-2.0 adds an explicit patent grant, which is why most
//    companies prefer it over MIT for internal libraries.
//    GPL forces the same licence on anything linking to it, which is
//    a business decision, not a technical one.

// 2. TRADEMARKS. A licence grants rights to the CODE. It does not grant
//    rights to the NAME. Publishing "Acme Logger" to npm gives you no
//    right to the Acme trademark, and squatting on a popular package
//    name is both bad practice and occasionally actionable.

// 3. THIRD-PARTY LICENCES. Your artefact bundles or depends on other
//    people's work. MIT-compatible dependencies are fine under a
//    permissive licence. An AGPL dependency makes your package AGPL.
//    Generate an attribution file and keep it in the artefact.

// 4. THE CONTRIBUTOR AGREEMENT. Who owns contributions? A CLA assigns
//    them, which is what most companies want, and some registries
//    require one. Without a CLA you are relying on the contributor
//    licence in your own LICENSE file, which many contributors accept
//    but not all companies will allow their staff to sign.

// 5. PERSONAL DATA. A package that collects telemetry needs a lawful
//    basis and a privacy policy. Some registries (notably VS Code and
//    the Chrome Web Store) require an explicit privacy policy URL in
//    the listing, and will reject a package that phones home without
//    disclosing it.

// 6. EXPORT AND SANCTIONS. Cryptographic software is subject to export
//    control in several jurisdictions. If your package contains crypto,
//    check before publishing. This is rare but it is not a formality.

// This chapter is not legal advice. It is the list of questions to take
// to someone who can answer them for your jurisdiction.

1 · Versioning, and How Versions Resolve

A version number is the only thing a registry and a consumer agree on. Getting the rules wrong means a release breaks installs for people you will never hear from.

Semantic versioning, precisely

// MAJOR.MINOR.PATCH
//   MAJOR  incompatible API changes. Consumers must change their code.
//   MINOR  backwards-compatible additions.
//   PATCH  backwards-compatible fixes.

// THE ACTUAL SEMVER RULES, which are stricter than most people assume

// 1. THE PUBLIC API IS A CONTRACT
//    anything a consumer can import, call, subclass, or read is public.
//    if it is not in your documentation, delete it or document it.
//    "private by convention" is not a thing: Python has no private,
//    JavaScript has no private without a convention, and Go has
//    unexported but the package boundary is the contract.

// 2. REMOVING IS MAJOR. RENAME IS MAJOR. SIGNATURE CHANGE IS MAJOR.
//    changing a parameter type, adding a required parameter, changing
//    a return type, removing an export, narrowing an accepted type.

// 3. WHAT IS NOT MAJOR, even though it feels like it
//    - adding a new optional parameter with a default
//    - adding a new export, method, class or field
//    - relaxing a validation rule to accept more
//    - widening an accepted type, e.g. string to string | number
//    - improving performance
//    - changing the output of a REPL or a log
//    - fixing a bug that violated the documented contract
//      (this is the one people argue about, and SemVer's own FAQ says
//       it is NOT necessarily major)

// 4. THE 0.x ESCAPE HATCH
//    0.x.y means "no stability promise". Within 0.y.z, MINOR is
//    breaking and PATCH is not. Many ecosystems treat 0.x as
//    pre-1.0, so ^0.2.0 allows 0.2.x but not 0.3.0.
//    Use it honestly. A 0.x package that breaks in a patch release is
//    abusing the convention.

// 5. INTERNAL REFACTORING IS FREE
//    if no public surface changes, it is a patch, even if every line
//    changed. SemVer is about the interface, not the diff.

// THE TEST, in one line
//   a consumer who follows your documented upgrade path and changes
//   nothing but their version constraint should still work.
//   if they must change their code, it was a MAJOR release.

Pre-release versions

// the ordering, which is not intuitive
  1.0.0-alpha    <  1.0.0-alpha.1  <  1.0.0-alpha.2  <  1.0.0-beta
  1.0.0-beta     <  1.0.0-rc.1      <  1.0.0-rc.2      <  1.0.0
  1.0.0          <  1.0.1           <  1.0.2           <  1.1.0

// precedence rules
  - a version WITH a pre-release tag sorts BEFORE the same version without
    1.0.0-beta  <  1.0.0
  - alpha < beta < rc
  - numeric identifiers compare numerically: rc.2 < rc.10
  - alphanumeric identifiers compare lexically: rc.alpha < rc.beta
  - a longer pre-release with more dot-separated parts is HIGHER
    alpha.1 < alpha.1.1

// THE THREE THINGS THAT GO WRONG

// 1. PUBLISHING A PRE-RELEASE TO THE DEFAULT TAG
    npm publish --tag beta        1.5.0-beta.1
    // otherwise `npm install pkg` picks it up, because the default tag
    // is what everyone gets. This has broken production systems.
//    PyPI:  upload to the TestPyPI index, or use a pre-release suffix
//    Maven:  a SNAPSHOT repository

// 2. PROMOTING A PRE-RELEASE BY RE-TAGGING
    // 1.0.0-rc.1 is not 1.0.0. You cannot re-tag a published version.
//    Publish 1.0.0 properly. If rc.1 is close enough to final, that is
//    the honest thing to do: 1.0.0-rc.1 then 1.0.0.

// 3. A PRE-RELEASE THAT DOES NOT SORT BELOW YOUR CURRENT STABLE
    // you are on 1.4.0 stable, then release 1.5.0-beta. A consumer with
//    ^1.4.0 will NOT pick it up, which is correct. A consumer with ^1.0.0
//    WILL, because ^1.0.0 covers 1.5.0-beta. This surprises people.

Version ranges, per ecosystem

Range syntax is not standardised, and the differences are a genuine source of bugs when you maintain a library across ecosystems.

// npm / node-semver
  ^1.2.3        >=1.2.3 <2.0.0    caret: same major
  ~1.2.3        >=1.2.3 <1.3.0    tilde: same minor
  1.2.3         exactly
  1.2.x         >=1.2.0 <1.3.0
  1.x           >=1.0.0 <2.0.0
  >=1.2.3 <2.0.0   explicit, clearest
  *             anything, including 2.0.0
  latest        a dist-tag, not a range. resolves to whatever you tag latest

// THE CARET IS NOT THE SAME IN 0.x
  ^0.2.3        >=0.2.3 <0.3.0    the minor is pinned in 0.x
  ^0.0.3        >=0.0.3 <0.0.4    the patch is pinned in 0.0.x
// if you are pre-1.0, ^0.2.3 will NOT pick up 0.3.0. good.

// PyPI / PEP 440
  ==1.2.3                exact
  ~=1.2.3                >=1.2.3 <1.3.0   compatible release
  ~=1.2                  >=1.2   <2.0
  >=1.2,<2.0          explicit, clearest
  ^1.2.3                 (only in poetry) >=1.2.3 <2.0.0
  1.2.*                  wildcard minor

// Cargo
  "1.2"       ^1.2 default: >=1.2.0 <2.0.0
  "~1.2.3"    >=1.2.3 <1.3.0
  "=1.2.3"    exact
  "*"         any

// Maven - the least intuitive of the lot
  [1.2,2.0)   >=1.2 <2.0      soft bounds, the default
  [1.2]       exactly 1.2
  [1.2,)      >=1.2
  [1.2,1.3]   >=1.2 <=1.3     CLOSED upper bound. the classic bug:
//                                  a consumer writing [1.2,2.0] gets 2.0-rc,
//                                  and a library that works differently in 2.0
//                                  ships into their build silently.

// NuGet
  1.2.3       minimum version, and NuGet picks the HIGHEST available
  [1.2.3,2.0) explicit
  [1.2.3]     exact
// NuGet's bare "1.2.3" meaning "at least" rather than "exactly" is the
// other thing that catches people.

// Go modules
  v1.2.3       exact. there are NO RANGES.
//  v1.2         is a valid v2 path suffix, not a range
//  a library declares v1.2.3, and the main module's go.mod records the
//  exact version selected by MVS (minimal version selection).
//  ranges are expressed with a pseudo-version, which is unwieldy

// Composer
  ^1.2         >=1.2 <2.0
  ~1.2.3       >=1.2.3 <1.3.0

// THE PRACTICAL RULE
//   in your own documentation, always write the range explicitly:
//   ">=1.2.3 <2.0.0". Every ecosystem's shorthand means something
//   slightly different, and the explicit form means the same thing
//   everywhere.

Never document a range in your own library's README using a different ecosystem's syntax. "Requires ^1.2" in a Python library, or ">= 1.2" in an npm package, produces a constraint the consumer's tool cannot parse, and they will either guess or fail. Write the explicit form and let the consumer's tooling convert it.

Lockfiles and the reproducibility question

// a LOCKFILE pins every transitive dependency to an exact version
//   package-lock.json    npm
//   yarn.lock            yarn
//   poetry.lock          poetry
//   Pipfile.lock         pipenv
//   uv.lock              uv
//   Gemfile.lock         bundler
//   composer.lock        composer
//   Cargo.lock           cargo - committed for binaries, ignored for libraries
//   go.sum               go - checksums only, not versions

// WHICH SIDE SHOULD COMMIT IT
//   APPLICATIONS: always commit. An application that installs different
//   versions on two machines is not reproducible and cannot be debugged.
//
//   LIBRARIES: usually do not, and this is a genuinely contested point.
//     Arguments for committing: your CI is reproducible; your tests run
//       against what you tested.
//     Arguments against: you are testing a version of your dependencies
//       your consumers will never resolve, because MVS and the lockfile
//       can pick different trees. And a stale lockfile hides the fact
//       that a dependency released a breaking change.
//     Rust's convention: commit Cargo.lock in binaries, gitignore it in
//     libraries. That is the current best-practice answer.

// WHAT A LOCKFILE DOES AND DOES NOT BUY YOU
//   DOES: exact versions, so a rebuild six months later produces the
//         same dependency tree.
//   DOES NOT: protect you from a compromised version that was already
//             pinned. If 1.2.3 is in your lockfile and 1.2.3 was
//             malicious, you keep reinstalling it.
//   THIS IS WHY YOU ALSO NEED SIGNING AND PROVENANCE. A lockfile
//   guarantees consistency, not integrity. Those are different
//   properties and the next chapters are about integrity.

// YANKING A BAD VERSION
//   most registries let you yank or unpublish a version. Do it, and
//   then open an issue telling everyone who has it pinned what to do.
//   A yank does not reach existing installs. Your users will find out
//   from your changelog, not from the registry.

Build metadata, and why it is dangerous

// PyPI allows local version labels and build metadata
1.2.3+build.456
1.2.3.dev1
1.2.3.post1
1.2.3rc1

// THE RULE THAT BITES EVERYONE
//   PEP 440 says: when comparing two versions, the local version label
//   and build metadata are IGNORED. So 1.2.3 and 1.2.3+build.999 are
//   EQUAL for resolution purposes.
//
//   if you publish 1.2.3+build.1 and then 1.2.3+build.2, a consumer
//   requiring 1.2.3 already matches build.1 and will never upgrade.
//
//   if you try to publish the same version twice, PyPI rejects it,
//   which is the only reason this is caught. The "equal" behaviour
//   bites when the version numbers DIFFER:
//     1.2.3+build.456  and  1.2.4+build.1
//     these are different, so both publish, and 1.2.4 wins on the
//     numeric part. But anyone pinned to ==1.2.3+build.456 gets
//     confused when the resolver says it also satisfies 1.2.4.

// THE RULE
//   never put anything meaningful after a "+" in a published version.
//   use it for local builds, or for a CI identifier you never publish.

// npm dist-tags, the equivalent tool
//   npm dist-tag add mypkg@1.3.0-beta.2 beta
//   npm dist-tag add mypkg@1.2.0   latest
//   tags are MUTABLE, and consumers can install by tag: "beta".
//   a mutable tag is powerful and dangerous: repointing "latest" is how
//   you ship a release without a version bump, and it is also how you
//   break production. Treat latest as a release artefact, not a
//   convenience.

CalVer and why some projects use it

// CALENDAR VERSIONING: 2026.03.14
  Ubuntu            24.04, 25.10          YYYY.MM
  Debian            12, 13                major only, per release cycle
  Kubernetes        v1.31.2              YYYY.MINOR.PATCH on a cycle
  Chrome            120.0.6099.109
  calver            2026.3.14             YYYY.MINOR(DAYS) micro(YYYYMMDD)

// WHEN IT IS THE RIGHT CHOICE
//   - the "version" is really a release date, and users care about
//     recency rather than API compatibility (an operating system, a
//     browser, a container base image)
//   - you release on a fixed cadence and compatibility is a promise
//     about the platform, not about your API
//   - you want a version that sorts chronologically with no thought

// WHEN IT IS WRONG
//   - you have a library with an API. A user must be able to say "I am
//     on 2025.11 and I cannot take 2026.03" and the tooling must help
//     them express that. CalVer with a strict minor line works; CalVer
//     with a daily micro does not, because there is no way to express
//     "this month's release but not today's".

// THE HYBRID, and it is the most defensible scheme
//   2026.3 LTS, or 1.20260314 for a library
//   the API compatibility is in the major; the release is in the rest.
//   This is what Kotlin, and increasingly serverless platforms, use.
//   It gives you a chronological sort AND a compatibility signal.

Deciding what forces a major bump

// A DECISION PROCEDURE, because "is this major?" is a judgement call
// and getting it wrong in either direction is expensive.

// 1. LIST EVERY PUBLIC SYMBOL the release removes, renames, or changes
//    the signature of. A script can find most of them by diffing the
//    API surface. For a typed language, compare the emitted .d.ts or
//    the compiled signature list against the previous tag.
//
// 2. For EACH ONE, ask: is there any input a real consumer could pass
//    that behaved correctly before and does not now?
//    yes -> MAJOR
//    no  -> not major
//
//    removing a class that was only ever used internally -> not major
//    changing an argument from optional to required              -> MAJOR
//    changing a return value's shape                            -> MAJOR
//    throwing a new exception type from a function documented never to
//      throw                                                 -> MAJOR if
//      anyone catches broadly, which someone does
//    changing default behaviour while keeping the signature       -> MAJOR
//    fixing a documented example that did not work              -> PATCH
//    making a performance improvement that changes floating-point
//      results                                               -> MAJOR, and
//      this is why numeric libraries treat it as breaking

// 3. IF YOU CANNOT ANSWER "MAJOR" OR "NOT MAJOR" FOR SOMETHING,
//    IT IS A MAJOR. The asymmetry is deliberate: a needless major
//    costs your users one edit; a needless minor breaks them silently.

// THE EXCEPTIONS WORTH NAMING
//   - dropping a platform (Node 18, Python 3.8). Usually a MAJOR, and
//     most registries and package managers treat the runtime
//     requirement as part of the public contract.
//   - a security fix. Ship it as a patch on the current line AND on the
//     previous major. Do not force an upgrade to a new major to get a
//     security fix, or people will run the vulnerable version longer.
//   - a licence change. This is legally major and nobody reads the
//     changelog. Say it in the release notes, in bold, repeatedly.

Deprecating and yanking

// DEPRECATION, the lifecycle of a version
  1.0.0   released
  1.1.0   a new function added
  1.2.0   old function marked @deprecated, still works
  2.0.0   old function removed. MAJOR.

// THE MECHANICS, per language
//   JSDoc    /** @deprecated since 1.2.0, use fooV2 instead */
//   Python   @deprecated(warning) decorator, PEP 702
//   Rust     #[deprecated(since = "1.2.0", note = "use bar")]
//   Go       // Deprecated: use Bar. Becomes visible in gopls
//   Java     @Deprecated(since = "1.2", forRemoval = true)
//   Kotlin   @Deprecated(message = "...", ReplaceWith = "...")
//   PHP      @deprecated since 1.2.0, use foo2() instead

// THE WARNINGS MUST BE ACTIONABLE
//   BAD:  deprecated
//   GOOD: "use parseV2() instead. Same signature, but it rejects
//          trailing commas and returns an error object rather than
//          throwing. Migrate by replacing the call: the behaviour
//          change is documented at https://..."
//   a deprecation warning that does not say what to do instead is
//   noise, and people suppress warnings.

// WHAT MOST PROJECTS GET WRONG
//   removing in the very next major, with no migration window.
//   Deprecate in a minor, give at least one full major release cycle,
//   and only remove when your own telemetry or issue tracker shows
//   near-zero usage.

// YANKING, for a broken release
//   most registries allow it. Do it when:
//     a broken build shipped
//     a security vulnerability
//     a licence violation
//     a dependency compromise affected you
//   and do NOT yank for
//     "the API changed and I regret it"   (that is a new major)
//     "the description was wrong"          (fix the description)
//   a yank does not remove the artefact from existing installs, so it
//   is a signal, not a recall. Announce it in your changelog and, if
//   it is a security issue, in your advisory.

Exercises 1

  1. Take a library you depend on and write out its public API surface. Then check which of its recent releases should have been major under this chapter's procedure but were not. Report it upstream if you are confident.
  2. Diff your own package's public API between the last two tags, mechanically. Then classify every change and confirm your chosen version numbers match the classification.
  3. Write the explicit version range for your package in five ecosystems' syntaxes and verify each resolves the versions you expect, using npm view, pip index, and equivalent tools.
  4. Publish two builds with the same version and different build metadata to a test index and demonstrate that they compare as equal. Explain the failure mode for a consumer who pinned the first one.
  5. Add a deprecation warning to a function in your own package, with a message that says what to use instead. Verify it appears in the consumer's editor, not just at runtime.

A published artefact is a promise that specific bytes will install everywhere, forever. Most of this chapter is about making those bytes a function of your source rather than of the machine that happened to build them.

What is actually in the published file

// most ecosystems publish a TARBALL or ZIP, not a directory of files.
// what goes in it is your decision, and the default is often wrong.

// npm: an always-generated tarball, packed from .npmignore + .gitignore
$ npm pack --dry-run
npm notice 1.2.3
npm notice === Tarball Contents ===
npm notice 120kB  dist/index.js          (built)
npm notice  14kB  dist/index.d.ts        (types, if you ship them)
npm notice  23kB  dist/index.js.map      (source map)
npm notice   2kB  README.md
npm notice   1kB  LICENSE
npm notice 400kB  src/                   (often included by accident)
npm notice   3kB  .eslintrc.json         (never useful to a consumer)

// npm pack is your preview. ALWAYS run it before publishing.
// the classic accident: your .npmignore is missing, so .gitignore is
// used instead, and that happens to ignore /dist because that is
// where your build output goes, and now you have published a package
// with no code in it. The .npmignore takes precedence when present, so
// an incomplete one is worse than none.

// Python: an sdist and a wheel

Reproducible builds

A reproducible build produces bit-identical output from the same source, on any machine, at any time. This is stronger than determinism, and it is what lets you audit an artefact.

// WHAT BREAKS REPRODUCIBILITY, and the fix for each

// 1. TIMESTAMPS baked into the artefact
//    the single most common cause
   // in a tar: set a fixed mtime
   tar --sort=name --mtime='UTC 2020-01-01' --owner=0 --group=0 \
       --numeric-owner -cf dist.tar build/
   // in Java JARs, the zip entry timestamps come from the filesystem
   //   so normalise them in the build

// 2. FILE ORDER
//    a directory read returns entries in filesystem order, which
//    differs between machines. Sort explicitly.
   --sort=name            GNU tar
   find . -type f | sort  then feed the list

// 3. ABSOLUTE PATHS EMBEDDED
//    build tools sometimes record the build directory in metadata.
   // Go: trimpath
   go build -trimpath
   // Rust: --remap-path-prefix
   RUSTFLAGS="--remap-path-prefix=$PWD=." cargo build
   // node-gyp, cmake, protoc: each has an equivalent

// 4. RANDOMNESS IN THE TOOLCHAIN
//    a build id, a UUID, a hash-map iteration order.
//    sort any map you serialise. Set a fixed SOURCE_DATE_EPOCH.
   export SOURCE_DATE_EPOCH=1700000000   // honoured by many toolchains

// 5. NETWORK ACCESS DURING THE BUILD
//    a downloaded dependency, a timestamped API call. Pin everything
//    and build with --offline or an equivalent.

// 6. RANDOM SEEDS
//    parallel test ordering, hash seeders.
//    fix the seed, or set it explicitly in the artefact.

// 7. USER-SPECIFIC ENVIRONTS
//    $HOME, $PATH, locale, timezone. Normalise in the build script.

// 8. NON-DETERMINISTIC COMPRESSION
//    some compressors embed timestamps. Verify by building twice and
//    comparing hashes.

// VERIFY IT
$ sha256sum dist/myapp-1.2.3.tar.gz
a3f5c9...  dist/myapp-1.2.3.tar.gz
// build again, on a different machine, in a clean container
$ sha256sum dist/myapp-1.2.3.tar.gz
a3f5c9...  dist/myapp-1.2.3.tar.gz      must match

// WHY IT IS WORTH THE EFFORT
//   1. a consumer can rebuild your artefact and compare, which turns
//      "trust us" into "check it"
//   2. it is a prerequisite for SLSA provenance and reproducible-builds
//      attestation, which is the modern answer to supply-chain attacks
//   3. it makes "was this binary built from this source?" a question
//      with a mechanical answer
//   4. it catches accidental non-determinism that would otherwise show
//      up as a mysterious bug report

Rebuilding from the same tag twice and diffing the hashes is a five-minute CI step that catches an enormous class of packaging bugs. It will find files you did not mean to include, timestamps that break a reproducible-build check downstream, and occasionally a dependency that fetches from the network during the build.

Determinism, the weaker property

// DETERMINISTIC: same input, same output, on the same machine
// REPRODUCIBLE: same input, same output, on ANY machine
//   reproducibility implies determinism, not the reverse

// this matters for binary artefacts
//   a Go build embeds the build path, so two identical checkouts in
//   different directories produce different binaries
//   -trimpath fixes it. Always use it, even if you do not intend to
//   publish a reproducible build, because a Go binary that leaks your
//   build path is an information disclosure.

// WHAT IS ACHIEVABLE IN PRACTICE
//   Go           fully reproducible with -trimpath and a pinned toolchain
//   Rust         reproducible with --remap-path-prefix and a pinned version
//   Nix          reproducible by construction. this is its whole design.
//   Debian       reproducible since 2013, and the reason the security
//                community pushed for it
//   Python wheels  harder, because setuptools embeds paths. wheels
//                built in a fixed container are effectively reproducible.
//   Node         possible, but the toolchain has improved more slowly
//   JVM jars     reproducible with a normalising build, e.g. reproducible-builds
//   .NET         deterministic builds exist but embed a MVID that
//                changes unless you set Deterministic and
//                ContinuousIntegrationBuild

// A PRACTICAL TARGET
//   Do not chase bit-identical builds for everything. Do achieve:
//     - a fixed, documented toolchain version
//     - a pinned lockfile
//     - no network access during the build
//     - -trimpath or equivalent
//     - a recorded hash of the artefact in your release notes
//   That is enough for a consumer to verify integrity, and it is what
//   the signing and provenance chapters build on.

Building in CI and only in CI

// PUBLISHING FROM A DEVELOPER MACHINE IS HOW SUPPLY CHAINS GET COMPROMISED
//   a malware incident in a popular npm package in 2022 came from a
//   maintainer's account being phished. The attacker published from
//   the maintainer's laptop, and the registry accepted it because the
//   registry cannot tell a maintainer from a thief who has the token.
//
//   the fix: make the token physically incapable of publishing from
//   anywhere but CI.

// THE SHAPE OF A GOOD PIPELINE
name: release
on:
  push:
    tags: ['v*']

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write          # required for OIDC, no long-lived secret
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false   # the token cannot be reused

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          registry-url: 'https://registry.npmjs.org'

      - run: npm ci               # not npm install. ci honours the lockfile
      - run: npm test
      - run: npm run build

      # verify the artefact is what you expect BEFORE publishing
      - run: npm pack --dry-run
      - run: node scripts/verify-artefact.mjs

      - name: publish
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
        run: npm publish --provenance --access public

// THE FOUR RULES
//   1. BUILD IN CI. Never publish from a laptop. Ever.
//   2. PROTECT THE TAG. Require signed tags and a protected release
//      environment with reviewers, so a stolen token alone is not enough.
//   3. USE SHORT-LIVED CREDENTIALS. OIDC exchange (ch4) means there is
//      no long-lived secret to steal at all.
//   4. VERIFY BEFORE PUBLISH. The artefact you are about to ship is
//      checked by a test, not by your confidence.

// THE TAG-TRIGGERED RELEASE PIPELINE
//   it is the standard because the tag is the immutable statement of
//   intent. The commit is not: it moves under a force-push.
//   combine with: signed annotated tags, and a protected tag pattern
//   in the repository settings.
   git tag -s -m "v1.2.3" 1.2.3
   git push origin v1.2.3

Source maps and debuggability

// a published package that throws a stack trace the consumer cannot read
// is a support burden. Source maps solve it, and most projects skip them.

// npm / node
{
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "files": ["dist", "README.md", "LICENSE"],
  "sourceMap": true,
  "declarationMap": true
}
// ship the .js.map and the .d.ts.map inside the package
//   a consumer's debugger then resolves frames into YOUR source, even
//   though they only have your dist
//   to do this from a bundler, add:
//     "sourceRoot": "https://unpkg.com/your-pkg@1.2.3/"
//   so a browser can fetch the original file from the registry

// TypeScript declarations are not optional for a TS-first package
//   ship the .d.ts, or consumers get an implicit-any error at their
//   import. This is the single most common reason a TS package is
//   described as "broken" and it is a packaging failure, not a bug.
   "types": "./dist/index.d.ts",
   "exports": {
     ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" }
   }

// Python
//   exceptions in compiled extensions reference the C source, not the
//   Python. Ship the .c files in the sdist so the traceback is readable.

// Rust
//   debug=true in the dev profile by default; for release, publish
//   -C debuginfo=2 .so files separately, keyed by version. Never ship
//   them inside the crate, or the artefact gets enormous.

// Go
//   the compiler embeds file paths and line numbers already. With
//   -trimpath the paths are module-relative and a consumer can resolve
//   them against the module cache. This is why -trimpath matters for
//   more than reproducibility.

// THE TRADE-OFF
//   source maps reveal your source structure. For a closed-source
//   commercial package that is information you may not want to publish.
//   For almost everything else: ship them. The debuggability is worth
//   far more than the obscurity, which is not security anyway.

Name collisions and typosquatting

// THE ATTACK
//   you depend on react. an attacker publishes "reacct", "rceact",
//   "reactt" and waits for a typo. This is not theoretical: it has
//   happened in npm, PyPI, and RubyGems, and the payloads have
//   included credential stealers and crypto miners.

// THE MITIGATIONS, in order of effectiveness
//   1. LOCKFILES, always committed, for applications. A lockfile pins the
//      integrity hash of every dependency, so a typo'd package cannot be
//      swapped in without a lockfile change you would see in review.
//   2. DEPENDENCY REVIEW. Look at every new dependency before it lands.
//      A single-character difference from a popular package is the
//      signal.
//   3. SCOPED OR VENDORED NAMES. A scope (npm) or a group id (Maven) is
//      a namespace, and namespaces are registered, so typosquatting is
//      much harder.
//   4. REGISTRY CONFUSION, a newer and subtler problem
//      your internal npm registry is configured under a scope. A
//      developer who forgets the .npmrc line installs from public npm
//      instead. Test for it: a CI step that resolves every dependency
//      and fails if any comes from an unexpected registry.

// THE DEFENSIVE CHECK, worth putting in CI
$ npm ls --all --json | jq -r '
    .dependencies | to_entries[] |
    "\(.value.resolved // "none")  \(.key)"' \
  | awk '{print $1}' | sed 's|https://registry.npmjs.org/||' \
  | grep -v '^none$' | sort -u | head
// every resolved URL should be from a registry you expect.
// a package resolving from a tarball URL or a git URL deserves a look.

// DEFENSIVE SETTINGS in .npmrc
//   ignore-scripts=true     block lifecycle scripts from dependencies
//     this is a real, meaningful protection and it has a cost: some
//     packages legitimately need a postinstall build step. Audit the
//     ones you allow rather than turning it off globally without
//     thinking.
//   audit=true
//   save-exact=true         stop ^1.2.3 from silently accepting 1.9.0
//   provenance=true         request provenance attestation on publish

Scopes, and publishing under a namespace

// npm scopes: @org/name
//   the scope is a namespace you own. The package name is then
//   @yourorg/thing, which removes typosquatting risk entirely for
//   your internal packages, and makes the ownership obvious.
   npm login --scope=@yourorg
   npm publish --access public        // scoped packages default to
                                      // restricted, so this is required
//   a private scope is free and unlimited on the free tier

// Maven group ids: com.yourorg.library
//   the groupId is a namespace, and the central repository requires
//   you to verify ownership of a domain matching it. This is why
//   "com.google.guava" exists and why a squat on com.yourorg is
//   prevented by domain verification.

// PyPI: organisation accounts
//   free, and they own projects and their transfers. Use one for
//   anything with more than one maintainer, and put a working email
//   on it, because PyPI account recovery is email-based and a dead
//   domain means a dead project.

// NuGet: organisation and ownership
//   you can transfer ownership of a package, and reserve a prefix
//   under your verified domain.

// crates.io: an org
//   a GitHub organisation or a verified domain, and the org owns the
//   crates.
//   you can RESERVE a crate name without publishing, so nobody takes
//   it. Do this for every name you might ever use.

// WHY THE NAMESPACE MATTERS MORE THAN IT LOOKS
//   a transfer is a break-glass operation. If your org account email
//   is on a domain you lose, you need a domain administrator to
//   recover it, and that is a genuinely scary dependency to have on
//   your most-used internal package.

Monorepos and per-package releases

// THE PROBLEM
//   a monorepo with 40 packages, all released together, is unusable:
//   every user of one tiny package waits for the 39 others.
//   per-package release is much harder than it looks.

// THREE APPROACHES

// A. INDEPENDENT VERSIONS, changed-path-based release
//   only publish a package when its own files changed
   // lerna --since origin/main, nx affected, turbo
   // hard parts: dependency graph, changelog generation, lockstep
//   dependents that need a release when a dependency changed

// B. FIXED GROUPS
//   group packages that always release together, version each group
     "packages": {
       "group-a": ["packages/a", "packages/b"],
       "group-b": ["packages/c"]
     }
//   simple, and the right answer for genuinely coupled packages

// C. INDEPENDENT WITH A CHANGESET FLOW
//   a changeset is a markdown file describing one change to one package
   //   packages/changesets/brave-lions-jump.md
   //   ---
   //   "@yourorg/core": minor
   //   "fix: handle a null token in refresh()"
   //   ---
   //   a release PR is generated from the accumulated changesets, with
   //   versions computed from the bump types, and you merge it
   //   the best properties: a human reviews the version bump and the
   //   changelog before it lands, and dependents are auto-bumped
   //   this is the most common modern answer

// THE CHANGELOG PROBLEM
//   a monorepo changelog is useless. Generate per-package changelogs
//   from the changesets, and keep a root CHANGELOG that only records
//   changes to the public workspace API.

// THE VERSION PROPAGATION PROBLEM
//   if @yourorg/plugin requires @yourorg/core ^1.2.0 and core goes to
//   2.0.0, the plugin must be released too, and its new version must
//   widen its range. Tools do this automatically. Write the rule down
//   anyway, because the exception cases accumulate.

Minimising the published surface

// every file in your package is installed on every user's disk, and is
// scanned by every security tool they run. Keep it small.

// THE FILE LIST, and it is not optional
// npm
   "files": ["dist", "README.md", "LICENSE", "CHANGELOG.md"]
//   anything not listed is excluded. This is the reliable mechanism;
//   relying on .npmignore is fragile because .gitignore also applies
//   when .npmignore is absent.

// Cargo
[package]
include = ["src/**", "README.md", "LICENSE", "Cargo.toml"]
exclude = ["tests/", "benches/", ".github/"]

// Go: nothing to declare. The module ZIP contains the whole module
//   directory, so a repository with large assets in it ships them all.
//   Use a .gitattributes with export-ignore, and keep assets in a
//   separate module or a release bucket.

// Python: MANIFEST.in
   include LICENSE README.md CHANGELOG.md
   recursive-include src *.py
//   or set the sdist config in pyproject.toml for modern tooling

// Rust
[package]
exclude = ["/.github", "/benches", "/tests", "/docs"]

// THE THINGS THAT ALWAYS GET IN BY ACCIDENT
//   - CI configuration: .github, .gitlab-ci.yml, Jenkinsfile
//   - Dockerfiles and compose files
//   - test fixtures, which are often large
//   - editor directories: .idea, .vscode
//   - lockfiles, when a library should not ship one
//   - .env files. Check for this specifically. It has happened.

// VERIFY THE SIZE, in CI
$ npm pack --dry-run
npm notice package size: 1.2 MB
npm notice unpacked size: 4.8 MB
// set a budget and fail the build if it is exceeded. A package that
// grows 10 MB in a release is usually a mistake, and it is invisible
// without this check.

// A PRINCIPLE WORTH STATING
//   a published artefact is a permanent, public commitment. Adding a
//   file is easy and removing one is a breaking change for anyone
//   deep-importing a path. So the file list is a public API, and it
//   deserves the same deliberation as your exported functions.

Exercises 2

  1. Run npm pack --dry-run or python -m build on one of your own packages and read the file list line by line. Remove everything a consumer does not need to import and run the function.
  2. Add a reproducible-build check to CI: build twice in clean containers on different runners and compare hashes. Fix every source of non-determinism it finds, starting with timestamps and file ordering.
  3. Convert one Go build to be reproducible with -trimpath and a pinned toolchain, and verify two builds produce identical hashes.
  4. Add a size budget to your release pipeline that fails when the artefact grows by more than a set percentage, and confirm it catches a deliberately added large file.
  5. Write a CI step that resolves every dependency in your lockfile and fails if any comes from an unexpected registry. Test it by pointing one dependency at a URL.

Publishing is the moment your code stops being yours. This chapter is about what a consumer can verify, what you can prove, and the uncomfortable truth about where the trust boundary really sits.

What the threat model actually is

// the incidents, and what they actually were
//   event-stream, ua-parser-js, coa, rc, colors, faker: 2020-2022
//   the attacker got a maintainer's NPM token by phishing a login
//   prompt for a "package migration" tool
//   they published a new version with a postinstall script that exfiltrated
//   environment variables, cloud credentials and browser data
//   the package had 2 million weekly downloads
//
//   the token was LONG-LIVED and lived on a developer's laptop.
//   nothing about the registry or the package manager detected it.

// THE FOUR THREATS THAT MATTER, in order of likelihood

// 1. CREDENTIAL COMPROMISE
//    a stolen token, a phished maintainer, a leaked CI secret.
//    the most common by a wide margin.
//    this is why OIDC and 2FA matter more than signing.

// 2. DEPENDENCY CONFUSION
//    your internal package "utils" is public, and someone publishes
//    "utils" to public npm, and your build resolves to theirs.
//    a resolution hijack, an internal-registry confusion, a GitHub
//    action running on a fork.
//    the 2020 event-stream incident was a variant: a developer
//    switched a dependency from flat to nested and npm installed the
//    public version instead.

// 3. THE BUILD ITSELF
//    a compromised build runner, a malicious postinstall script in a
//    transitive dependency, a typosquatted package.
//    signing catches the last of these only if the build was clean.

// 4. THE REGISTRY ITSELF
//    a compromise of npm, PyPI or crates.io. Low probability, very
//    high impact. Signing your artefacts means a registry compromise
//    does not have to be the end of the story.

// WHAT EACH DEFENCE ACTUALLY BUYS YOU
//   checksums       integrity. the bytes are the bytes you published.
//   signing        authenticity. these bytes were signed by that key.
//   provenance     process. built by that workflow, from that source,
//                  at that commit, with that material.
//   short-lived creds  removes the stolen-token attack entirely.
//   2FA            raises the cost of account compromise.
//
//   note what none of them does: they do not make your code good, and
//   they do not stop a maintainer from publishing something bad on
//   purpose.

Integrity and checksums

// CHECKSUMS, the baseline, and where you already have them

// npm: in package-lock.json, for every transitive dependency
  "node_modules/express": {
    "version": "4.19.2",
    "resolved": "https://registry.npmjs.org/express/-/express-4.19.2.tgz",
    "integrity": "sha512-5/PsL6iGPdfQ/lKM1UuielYgv3BUoJfzti8kAvl8RV4Te2Jg=="
  }
//   npm verifies this on every install. Change one byte and it fails.
//   This is a genuine, automatic supply-chain defence and it is why
//   committing a lockfile matters so much.

// PyPI: hashes are in the index metadata, and pip --require-hashes
//   enforces them
   pip install --require-hashes -r requirements.txt
# sha256:...  package-a==1.2.3
# sha256:...  --hash=sha256:abcdef...  package-a==1.2.3
#   with --require-hashes, pip refuses any package not pinned with a
#   hash. This is the Python equivalent of a lockfile, and most teams
#   do not use it.

// Cargo: checksums in Cargo.lock, verified on every build
// Go: go.sum, verified on every build
//   the strongest of the defaults, because go.sum is mandatory
// NuGet: a .snupkg with a signature, and packages.lock.json
// Maven: .asc signature files, verified with -gpg and
//   maven-gpg-plugin-plugin
// RubyGems: a .gem.asc signature beside the .gem

// WHAT CHECKSUMS DO NOT DO
//   they prove the artefact has not changed SINCE IT WAS PUBLISHED.
//   They do not prove it was published by you, and they do not prove
//   the contents are benign.
//   If the attacker has your token, they publish an artefact and the
//   registry computes a valid checksum for it. The checksum is
//   correct. The content is hostile.
//
//   CHECKSUMS ARE NOT ENOUGH. They are necessary, and they are the
//   weakest of the defences listed here.

Signing the artefact

// SIGNING says: "the holder of this private key vouched for these
// bytes". It is the boundary between "a package" and "a package from
// you".

// npm: provenance rather than a PGP signature
$ npm publish --provenance --access public
//   npm generates a Sigstore attestation binding:
//     the artefact hash
//     the publishing workflow file (from .github/workflows/release.yml)
//     the git commit and repository
//     the identity of the workflow runner
//   no key to manage, no key to leak, and it is verifiable with
//   npm audit signatures
$ npm audit signatures
//   checks every installed package against the public transparency log
//   the right verification tool, and almost nobody runs it

// PyPI: trusted publishing, which removes the API token entirely
//   in pyproject.toml
[project.optional-dependencies]
# or, in the dashboard: add a GitHub Actions publisher
//   you configure a one-time token on PyPI, give it a repository and
//   workflow, and PyPI mints a short-lived OIDC token per run.
//   there is no long-lived secret in your CI at all.
$ twine upload --repository pypi dist/*

// Sigstore, the cross-ecosystem answer
$ cosign sign-blob --key env://COSIGN_PUBKEY dist/pkg-1.2.3.whl
$ cosign verify-blob --key env://COSIGN_PUBKEY \
    --certificate-identity https://github.com/yourorg/repo/.github/workflows/release.yml \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    dist/pkg-1.2.3.whl
//   the two flags are the point: not "signed by someone" but "signed
//   by THAT workflow in THAT repo". A signature from an unexpected
//   pipeline is a verification failure.

// PGP, for ecosystems that still want it
$ gpg --detach-sign --armor dist/pkg-1.2.3.tar.gz
$ gpg --verify dist/pkg-1.2.3.tar.gz.asc
$ gpg --keyserver keyserver.ubuntu.com --recv-keys 0xDEADBEEF
//   publish the public key in a well-known location AND in your
//   repository, AND in a keyserver. One location is not enough: each
//   is a different failure mode.

// MANAGING KEYS, if you must use a long-lived key
//   - generate it in a hardware-backed store or an HSM, not on a laptop
//   - one key per project, not one key for everything
//   - back it up OFFLINE. Two copies, in two places, tested once a year
//   - have a revocation plan BEFORE you need it, and document the
//     public key fingerprint in your README so consumers can pin it
//   - rotate, and publish the new key before retiring the old
//   - NEVER store a signing key in the same repository as the code, or
//     in the same CI. That defeats the entire mechanism.

The npm compromise chain of 2020–2022 failed partly because signing was opt-in and nobody verified. A signed package that nobody checks is security theatre. If you sign, your CI should also verify signatures on the way *in* — on every dependency in your lockfile — so a tampered transitive package fails your build rather than your production.

Short-lived credentials with OIDC

This is the highest-value change most projects can make, and it removes the stolen-token attack class entirely.

// THE PROBLEM WITH A LONG-LIVED TOKEN
   $ npm config set //registry.npmjs.org/:_authToken=npm_abc123...
   // that token is valid for months. It is in your CI secrets, in your
   // developer's ~/.npmrc, in shell history, in a screenshot in a bug
   // report. Anyone who copies it can publish as you, indefinitely.

// OIDC, the mechanism
//   your CI provider (GitHub Actions, GitLab, Buildkite, CircleCI)
//   already has a short-lived identity token, signed by the provider,
//   that names the repository, the workflow and the ref.
//   You exchange it at the registry's token endpoint, which verifies
//   the signature and checks that the repository and workflow match
//   what you pre-registered. You get a credential valid for minutes.
//   There is no secret to steal, because there is no secret.

// the permissions block, the key line
   permissions:
     id-token: write    # this is what enables the exchange
     contents: read     # and this is all else you need
//   with only id-token: write and contents: read, a compromised action
//   in your workflow can mint a publish token. With packages: write as
//   well, it could do more.

// PyPI trusted publishing, fully configured
//   1. PyPI dashboard, your project, Publishing -> add a GitHub
//      publisher: owner, repository, workflow filename, environment
//   2. pyproject.toml needs no change
   3. the workflow:
//     - uses: pypa/gh-action-pypi-publish@release/v1
//       with:
//         password: ${{ secrets.PYPI_API_TOKEN }}   omit this entirely
//   there is no token. The action exchanges the OIDC token.

// npm trusted publishing, as of 2025
//   npm supports trusted publishing on the registry side, configured in
//   the package settings, with a linked GitHub repository and
//   workflow. The workflow runs `npm publish` with no auth token set.
//   Check the current npm documentation, because this was newer than
//   the PyPI mechanism and the configuration surface has moved.

// THE RESIDUAL RISK, stated honestly
//   if an attacker can push to your release branch, or modify the
//   release workflow, they can trigger a legitimate publish.
//   OIDC does not protect against that. It protects against credential
//   theft, which is what actually happened.
//   Pair it with protected branches, signed tags, and an environment
//   that requires reviewer approval for releases.

Provenance attestation

Signing says who vouched. Provenance says how it was made: which workflow, from which commit, with which source, using which build definition.

// WHAT A PROVENANCE ATTESTATION CONTAINS
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "pkg-1.2.3.tar.gz", "digest": { "sha256": "a3f5..." } }],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://github.com/actions/runner",
      "externalParameters": {
        "workflow": { "ref": "refs/heads/main",
                      "repository": "https://github.com/yourorg/repo" }
      },
      "resolvedDependencies": [
        { "uri": "git+https://github.com/yourorg/repo@8f2a91",
          "digest": { "gitCommit": "8f2a91c4e7..." } }
      ]
    },
    "runDetails": {
      "builder": { "id": "https://github.com/actions/runner" },
      "metadata": { "invocationId": "..." }
    }
  }
}

// WHY IT IS BETTER THAN SIGNING ALONE
//   a signature answers "was this signed by your key?"
//   provenance answers "was this built by your release workflow, from
//   commit 8f2a91, of the source in this repository?"
//   a consumer can verify the second without trusting the key, because
//   the identity comes from the CI provider's OIDC token, which the
//   consumer can independently check against the provider.

// WHERE IT EXISTS TODAY
//   npm          npm publish --provenance. Stored in the public
//                Sigstore transparency log. Verify with npm audit
//                signatures.
//   PyPI         PEP 740 attestations. Generated by trusted publishing.
//   crates.io    crates support an --attestations flag
//   Maven        CycloneDX and in-toto attestations via
//                the sigstore plugin
//   containers    cosign attest, and the OCI referrers API
//   NuGet        signing, and newer attestation support
//   RubyGems     signing; full provenance is emerging

// THE CONSUMER SIDE, and it should be routine
$ npm audit signatures
# most packages with provenance: verified
# packages without: warn
$ npm ci --ignore-scripts
# and run a signature check in your own CI, per ch3-verify

// THE THING THAT MAKES THIS STRONG
//   the transparency log. Sigstore's Rekor log is append-only and
//   public, so a signature cannot be quietly retracted, and an entry
//   can be independently audited. An attacker who compromises your
//   publishing credential still leaves a public, permanent record.

SLSA, in plain terms

// SLSA is a framework for build provenance. Its levels describe how
// trustworthy a build's provenance is, which is a property of your
// PIPELINE, not of any one artefact.

// THE LEVELS, and what each one means in practice

// BUILDS 0 and 1: the artefact exists
//   a provenance document is attached. It is self-asserted: the build
//   says what it did, and you are trusting that statement.
//   this is most of the ecosystem today. It is better than nothing.

// BUILD 2: hosted build platform
//   provenance is generated by a hosted, isolated build service, so
//   the build cannot be tampered with by the submitting party.
//   GitHub Actions with provenance enabled is in this category.
//   the properties you get: the build ran in an environment the
//   submitter does not control, and the provenance is unforgeable
//   without the platform's key.

// BUILD 3: hard to tamper with, and verifiable
//   the build definition is a first-class, separately reviewed artefact.
//   the source, the build file and the build service are all pinned.
//   a consumer can verify the chain end to end without trusting you.
//   this is very few organisations today, and the barrier is mostly
//   organisational rather than technical.

// BUILD 4: hermetic and reproducible
//   the build is fully hermetic: no network, all dependencies declared,
//   and the output is reproducible from the inputs alone.
//   two parties independently build and get byte-identical output.
//   this is what Nix and Debian aim for, and what makes the
//   vulnerability in ch2-artefact checkable rather than aspirational.

// WHAT IS ACHIEVABLE NOW, IN ORDER OF EFFORT
//   1. Build in GitHub Actions, not on a laptop. (hours)
//   2. Turn on provenance. npm: one flag. PyPI: dashboard checkbox.
//      (an afternoon)
//   3. Sign your release tags. (an hour)
//   4. Pin the build environment: a fixed runner image, a lockfile,
//      no network during the build. (a day)
//   5. Make the build reproducible. (a week, then maintenance)
//   6. Add a third-party verifier to your release process. (a week)
//
//   Steps 1 to 3 eliminate the credential-theft class, which is the
//   class that actually caused every incident in the record. Do those
//   before worrying about level 4.

Account security is the real boundary

// THE UNCOMFORTABLE TRUTH
//   every defence in this chapter assumes the attacker does not have
//   your maintainer account. In every real incident, they did.
//
//   so account security is not a footnote. It is the first control.

// THE MINIMUM, AND IT IS NOT OPTIONAL
   - 2FA on every registry account, with a hardware key (YubiKey or
     equivalent) rather than an app. TOTP is better than nothing; a
     phished session cookie defeats an app-based 2FA that the user
     clicks through, and a hardware key does not have that problem.
   - a sign-in notification, and treat one you did not initiate as an
     incident, not a nuisance
   - hardware-key-enforced for publishing, so a stolen password plus a
     phished TOTP is not sufficient
   - a separate account per person. No shared maintainer logins. The
     event-stream maintainer had a single point of failure in a person.

// THE ORGANISATIONAL CONTROLS THAT ACTUALLY WORK
   - a protected release environment requiring reviewer approval, so
     one person cannot publish
   - signed tags, so a release identifies its author cryptographically
   - branch protection on the release branch
   - an audit log of publishes, reviewed by someone who is not the
     person doing the publishing
   - a documented recovery path: who to email when an account is
     compromised, and how the registry's recovery works. Find out
     BEFORE you need it. PyPI recovery is email-based and goes through
     a domain administrator; npm's goes through support.

// THE BIT PEOPLE SKIP
//   remove maintainers who have left. Every former maintainer is a
//   permanent credential risk. Do it the day someone leaves, not at the
//   next audit, and check every registry you have ever published to,
//   because the one you forgot about is the one that gets used.

Verifying a dependency, and the limits

// WHAT YOU CAN VERIFY, AND WHAT YOU CANNOT
//
// CAN:   the bytes are the bytes that were published
// CAN:   those bytes were signed by a key whose fingerprint you have
//        independently obtained
// CAN:   the artefact was built by a named workflow, in a named repo,
//        from a named commit
// CANNOT: the code is safe
// CANNOT: the maintainer is trustworthy
// CANNOT: the build was not itself compromised
// CANNOT: the dependency is needed at all, or is not malicious in a
//         way that looks like good code
//
// SAY THIS TO YOUR TEAM, because "we verify signatures" gets quoted
// back as "our dependencies are safe" and that is not what it means.

// THE VERIFICATION PIPELINE, in CI
name: verify-supply-chain
on: [push, pull_request]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }

      # 1. every package resolved from a registry we expect
      - run: node scripts/check-registries.mjs

      # 2. provenance where it is expected to exist
      - name: verify npm provenance
        run: npm audit signatures --json > sigs.json
      - run: |
          node -e '
            const s = require("./sigs.json");
            const missing = Object.entries(s.packages ?? {})
              .filter(([name, v]) => !v.verified && v.attestations === undefined)
              .map(([name]) => name);
            if (missing.length) {
              console.error("no signature or provenance: " + missing.join(", "));
              process.exit(1);
            }
          '

      # 3. no install scripts, which is where most compromise payloads live
      - name: no lifecycle scripts
        run: |
          npm ci --ignore-scripts
          if grep -rE '"(pre|post)install"' package-lock.json; then
            echo "a dependency runs an install script - audit it"; exit 1
          fi

      # 4. the audit database, for known CVEs
      - run: npm audit --audit-level=high

// WHY --ignore-scripts IS THE HIGHEST-VALUE SINGLE FLAG
//   the payloads in event-stream and ua-parser-js were postinstall
//   scripts. Blocking install scripts blocks the execution of most
//   supply-chain malware, at the cost of a small number of legitimate
//   packages that need a native build step.
//   If you cannot turn it on globally, turn it on in CI and allow the
//   exceptions explicitly, in a file, reviewed.

// THE HONEST LIMIT OF ALL OF THIS
//   you have not removed trust from the system. You have made it
//   specific, checkable and revocable, which is the most that is
//   achievable without running the entire ecosystem from source. The
//   remaining trust is in the maintainers and the registry, and it
//   should be reduced deliberately: fewer dependencies, and more of
//   them first-party.

Responding to a compromise

// IF ONE OF YOUR PACKAGES IS COMPROMISED, this is the order.
// Deciding in advance is worth an hour, because you will not think
// clearly in the first ten minutes.

// MINUTE 0 TO 5: STOP THE BLEEDING
   - yank the malicious version immediately. Every registry supports it.
   - revoke the publish token, at every registry you use
   - invalidate the CI secrets if the build was the entry point
   - assume any CI secret is compromised if a maintainer account was

// MINUTE 5 TO 30: WORK OUT THE SCOPE
   - what exactly did the payload do? Read it. Do not guess.
   - which versions were affected? Every version published while the
     credential was in the attacker's hands, not just the malicious one.
   - did the build pipeline run attacker code? If the release workflow
     was modified, assume the previous release is also suspect.
//   - an honest answer here is usually "we do not know yet". Say that
//     publicly rather than staying silent.

// HOUR 1 TO 6: NOTIFY
   - npm: npm audit advisory, and the registry has a security process
   - PyPI: report to the PSRT, python-security@python.org
   - Rust: crates.io has a yank-and-report flow; the advisory goes to
     the RustSec database
   - GitHub: advisory in the repository's Security tab
   - YOUR USERS DIRECTLY. A changelog entry and an advisory reach
     developers. An email, a blog post, and a HackerOne report reach
     everyone else. Silence is what turns an incident into a breach.

// DAY 1 TO 7: RECOVER
   - publish a fixed version
   - consider whether the previous good version is still safe to pin.
     If the attack was a maintainer-account compromise, an earlier
     version published before the compromise is probably fine. Say so
     explicitly, so people know whether to downgrade or upgrade.
//   - rotate every credential you touched, and any that shared a
//     mechanism with the one that leaked
//   - turn on 2FA, OIDC and provenance for this package before the
//     next release. Ship the fix and the hardening together.

// AFTERWARDS
   - write the postmortem publicly, including the timeline and the
     decisions you got wrong. The ecosystem learns from these, and
     "we were lucky" is not a finding.
//   - check whether your dependency count is a contributing factor. The
//     event-stream payload ran in the browser; a server package in a
//     container behaves differently, and that difference is design
//     information worth acting on.

The shape of an npm package

// package.json, the fields that matter for publishing
{
  "name": "@yourorg/http-client",     // scoped, so the namespace is yours
  "version": "1.4.2",
  "description": "A small HTTP client with retries and typed responses.",
  "license": "Apache-2.0",
  "type": "module",                     // marks this package's .js as ESM
  "main": "./dist/index.cjs",           // CJS entry, for older consumers
  "module": "./dist/index.js",          // ESM entry, for bundlers
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./package.json": "./package.json"
  },
  "files": ["dist", "README.md", "LICENSE"],
  "sideEffects": false,                 // lets bundlers tree-shake
  "engines": { "node": ">=18" },
  "repository": { "type": "git", "url": "git+https://github.com/yourorg/http-client.git" },
  "publishConfig": { "access": "public", "provenance": true },
  "scripts": {
    "prepublishOnly": "npm run build && npm test",
    "test": "vitest run"
  }
}

// THE THREE FIELDS PEOPLE GET WRONG

// 1. "files", or the absence of it
//    without "files", npm uses .gitignore, and then everything you have
//    ignored is published too. With "files", the list is authoritative.
//    ALWAYS set it.

// 2. "exports", and the deep-import break
    "exports": { ".": "./dist/index.js" }
//   this ENFORCES the public API. ./dist/internal.js stops resolving
//   for consumers. That is the point, and it is a breaking change for
//   anyone deep-importing, so do it in a major release and note it.
//   the escape hatch that keeps it working for most people:
    "exports": {
      ".": "./dist/index.js",
      "./package.json": "./package.json"
    }

// 3. "type", the field with the longest reach
//    "type": "module" makes every .js in the package an ES module.
//    a package without it is CommonJS, and an ESM consumer importing
//    it gets an ERR_REQUIRE_ESM or a named-export error.
//    get this right on day one. Changing it later is a major break for
//    half your consumers.

Publishing to npm

// THE SEQUENCE
$ npm login                        # or use a token in CI
$ npm version patch                # 1.4.1 -> 1.4.2, commits and tags
$ npm publish --provenance --access public

// A PROPER RELEASE, which is what you should actually do

// 1. build and verify
$ npm ci
$ npm run build
$ npm test
$ npm pack --dry-run               // READ THE FILE LIST

// 2. run the changelog tooling, if you use it
$ npx changeset version            # updates CHANGELOG.md and package.json
$ npx changeset git                // commits the release

// 3. publish
$ npm publish --provenance --access public

// 4. tag and push
$ git push origin main --follow-tags

// 5. publish the GitHub release with the changelog section

// THE TWO-PACKAGE PATTERN, and why npm forces you into it
//   you want a patch release of @yourorg/core without releasing
//   @yourorg/plugin. npm couples them only via the lockfile, so this
//   is fine. But git tags for a monorepo need the changesets flow
//   (ch2-monorepo) to be correct.

// WHAT "access" MEANS
   scoped packages default to RESTRICTED (private), unscoped to public
   --access public is required for a scoped public package
   restricted requires a paid plan

// THE FIRST 24 HOURS
   npm unpublish @yourorg/pkg@1.4.2       // within 72 hours, if you own it
   after 72 hours you can only deprecate, never unpublish
   deprecation:
     $ npm deprecate @yourorg/pkg@1.4.0 "security fix in 1.4.1, please upgrade"
   the package still installs; npm shows the warning on install and in
   `npm info`. This is usually what you want, and it is much more
   considerate than yanking.

dist-tags, versions and the release dance

// dist-tags are mutable pointers, and the default one is "latest"
$ npm dist-tag ls @yourorg/core
latest: 1.4.2
next:   2.0.0-beta.3
lts:    1.3.9

$ npm install @yourorg/core            // resolves "latest" -> 1.4.2
$ npm install @yourorg/core@next       // 2.0.0-beta.3
$ npm install @yourorg/core@1.3.9      // pinned, by version

// THE BETA RELEASE, done properly
$ npm version prerelease --preid=beta   # 1.4.2 -> 1.4.3-beta.0
$ npm publish --tag beta                # note --tag. WITHOUT IT the
                                         # beta becomes "latest" and
                                         # every user gets it.
$ npm dist-tag add @yourorg/core@1.4.2 latest   // put latest back

// THE FAILURE THAT HAPPENS EVERY YEAR
//   someone runs `npm publish` on a prerelease version without
//   --tag beta, and for a few hours every `npm install` in the world
//   gets the beta. Adding a CI check is the fix:
   - run: |
       TAG=$(node -p "require('./package.json').version")
       if [[ "$TAG" == *-* ]] && [ "${{ }}..." != "beta" ]; then
         echo "prerelease published without --tag beta"; exit 1
       fi

// THE PATCH-TO-MAJOR FLOW
   1.4.2  current stable
   1.5.0  new feature, backwards compatible
   2.0.0-beta.0   the breaking change, under the next tag
   2.0.0-beta.3
   2.0.0          latest -> 2.0.0
   1.5.1          a patch on the old line, if you still support it
//   keep the previous major maintained for a stated period. npm's
//   dist-tag "lts" exists for exactly this, and using it is a courtesy
//   your users notice.

Dependencies and peer dependencies

// THE FOUR FIELDS, and getting this wrong breaks installs

  "dependencies"         installed with your package, and required
                         for it to work
  "devDependencies"      not installed for consumers; for you only
  "peerDependencies"     NOT installed. The consumer provides it.
  "optionalDependencies" installed if available, failure is tolerated
  "peerDependenciesMeta" marks a peer as optional

// WHEN TO USE A PEER DEPENDENCY
//   when the host application and your package must share ONE instance.
//   the case that matters: a React component library. If your package
//   bundles its own React, the consumer gets two Reacts, hooks fail
//   with "Invalid hook call", and it is very hard to debug.
   "peerDependencies": {
     "react": "^18.0.0 || ^19.0.0",
     "react-dom": "^18.0.0 || ^19.0.0"
   },
   "peerDependenciesMeta": {
     "react-dom": { "optional": true }
   }

// THE RANGE IN A PEER, and it is a promise about your consumers
   "^18.0.0 || ^19.0.0"     you have tested both. say so.
//   ">=16"                  you have tested some future version. you
//                            have not, and a break will find you.
//   "*"                     you make no compatibility claim, which is
//                            both useless and, in most ecosystems,
//                            a guideline violation.

// devDependencies, and the mistake everyone makes
   "devDependencies": {
     "typescript": "^5.4.0"      // the caret in devDeps is correct
   }
//   devDependencies versions are pinned by the LOCKFILE, not the
//   range, so the caret here matters less. But do not write "*":
//   your own CI then changes under you.

// THE PUBLICATION CHECK
   npm publish warns if a dependency is missing from package.json even
   though you import it. That warning catches the most common packaging
//   bug: a file that works for you because of a hoisted transitive
//   dependency that the consumer does not have.

Dual publishing: ESM and CommonJS

// THE PROBLEM
//   Node treats .js as CommonJS unless the nearest package.json says
//   "type": "module". Bundlers prefer ESM. So a modern package that
//   ships only ESM breaks require() consumers, and a package that
//   ships only CJS gets a "named export not found" error in Node ESM.

// THE SOLUTION: build both, publish both
// tsup, rollup, or esbuild. The configuration is short:
{
  "scripts": { "build": "tsup" },
  "type": "module"
}
// tsup.config.ts
import { defineConfig } from 'tsup';
export default defineConfig({
  entry: ['src/index.ts'],
  format: ['esm', 'cjs'],
  dts: true,
  sourcemap: true,
  clean: true,
  target: 'node18',
});
// this emits:
//   dist/index.js     ESM
//   dist/index.cjs    CommonJS, with the .cjs extension
//   dist/index.d.ts

// THE ESM INTEROP TRAP, which produces a very confusing error
//   a CJS module can only export ONE thing to a named ESM import:
     module.exports = { foo, bar }
   // importing { foo } from "pkg" works in most bundlers
   // but in Node's ESM the CJS named-export detection is a heuristic
   // over the source text, and it fails on:
     module.exports = { ...require('./other'), extra: 1 }
   // symptom: SyntaxError: The requested module 'pkg' does not
   // provide an export named 'foo'
   // THE FIX: publish real ESM. Do not rely on the heuristic.

// VERIFY BOTH PATHS
$ node -e "const m = require('./dist/index.cjs'); console.log(Object.keys(m))"
$ node --input-type=module -e "
  import { foo } from './dist/index.js';
  console.log(typeof foo);
"
// run both in CI. A package that only ever tests its ESM build will
// break CJS consumers without anyone noticing until a bug report.

JSR, and TypeScript-first packages

// JSR (jsr.io) is a newer registry from the Deno team, with two
// differences that matter: it publishes TypeScript directly, and it
// scores packages on documentation and type coverage.

// WHY IT EXISTS
//   npm requires a build step before publishing, which means a JS
//   package cannot be consumed as source. JSR publishes the source
//   with types, and the consumer's tooling does the transformation.
//   The result is faster, better-typed, and a better DX for the
//   consumer's editor.

// HOW A TYPED PACKAGE NEEDS TO BE WRITTEN
//   1. every exported symbol must have an explicit type. No inference
//      on an exported function's return type, or the types are
//      unavailable to consumers.
//   2. document with JSDoc that includes @param and @returns. The
//      generated types and the docs come from this.
//   3. no default exports in a library, because the names collide
//      across import styles. Use named exports.

/**
 * Retry an operation with exponential backoff.
 *
 * @param operation The operation to run. It should throw on failure.
 * @param options Retry configuration.
 * @returns The result of the first successful attempt.
 * @throws If every attempt fails.
 */
export async function retry<T>(
  operation: () => Promise<T>,
  options?: RetryOptions,
): Promise<T> { /* ... */ }

// SCORING, and why it improves libraries
//   JSR scores a package on documentation completeness, type coverage,
//   and whether it builds. A package with no JSDoc scores poorly and
//   ranks lower. It is a quality gate by incentive, which is more
//   effective than a review process.

// USING IT FROM NODE AND BROWSERS
   npx jsr add @yourorg/http-client
   // and in a browser, no build step at all:
   <script type="module">
     import { retry } from "https://jsr.io/@yourorg/http-client";
   </script>

// THE PRACTICAL POSITION, and it is not either/or
//   publish to npm for the widest compatibility, because every
//   bundler, every CI system and every corporate firewall handles it
//   publish to JSR as well if your audience writes Deno or wants
//   source-level types. Most serious projects do both, with the npm
//   artefact built and the JSR artefact source.

CDN distribution and import maps

// PUBLISHING A PACKAGE THAT WORKS IN A BROWSER, NO BUILD STEP
//   this is a genuine differentiator for a utility library, and it is
//   how you reach people who are not using a bundler.

   <script type="module">
     import { formatDate } from "https://esm.sh/date-fns@4";
     import debounce from "https://esm.sh/lodash-es@4.17.21";
   </script>

// THE THREE CDN SHIMS, and what each does
//   esm.sh    bundles for the exact target, resolves subpath exports,
//             can pin a target: ?target=es2022, and ?bundle for a
//             single file. Most capable.
//   jsdelivr  a pure file server with /+esm for on-the-fly ESM
//             conversion, and a /npm/ prefix for bare specifiers.
//             Very fast, very dumb, which is why it is popular.
//   unpkg     a file server only, /browse for exploring what is in the
//             package. It is how you discover what a package actually
//             contains when a deep import fails.

// THE IMPORT MAP, for pinning versions without a build
   <script type="importmap">
     {
       "imports": {
         "react": "https://esm.sh/react@18.3.1",
         "react-dom/client": "https://esm.sh/react-dom@18.3.1/client",
         "date-fns": "https://esm.sh/date-fns@4.1.0"
       }
     }
   </script>
   <script type="module">
     import { format } from "date-fns";
   </script>
//   browsers have supported import maps since 2023, so bare specifiers
//   resolve with no bundler at all. This is a real option for a
//   documentation site or an internal tool, and it is not widely
//   adopted yet.

// THE DECISION
//   a library that works from a CDN gets a try-before-install audience,
//   which is how most developers actually evaluate. If your package
//   has a build step and cannot be consumed as source, you have given
//   that up for nothing.
//   "exports", a proper "browser" or "module" entry, and ESM output
//   with no Node built-ins in the browser path are what make it work.

The no-build path

// WHAT YOU CAN DO WITHOUT A BUILD STEP, in increasing ambition
//   nothing      ship a single ESM .js file. Works from a CDN today.
//   a few files  ship src/ as-is. Works if the files import each other
//               with explicit .js extensions. This is what JSR
//               publishes.
//   with TS      publish source .ts and let the consumer transform.
//               JSR does this. In the browser it needs a transform

Untrusted publishing and the new protections

// THE PROBLEM npm IS ATTACKING
//   a maintainer runs `npx some-migration-tool` to upgrade a
//   dependency, and the tool prints "we need your npm credentials to
//   continue". The maintainer pastes the token. That is the entire
//   event-stream compromise, and it is a social engineering attack
//   against a helpful CLI.

// WHAT THE PROTECTIONS ARE
//   1. TRUSTED PUBLISHING, discussed in ch3-oidc. There is no token
//      to paste, so the attack has nothing to steal. This is the
//      single most effective mitigation and it is available on npm,
//      PyPI, crates.io and Maven.
//   2. HARDWARE-KEY-ENFORCED 2FA for publishing, so a phished
//      password is not enough.
//   3. POST-INSTALL APPROVAL. npm 11 prompts before running
//      install scripts from newly added dependencies. Your CI needs
//      --ignore-scripts, and your developers should read that prompt
//      rather than pressing enter.
//   4. INSTALL-SCRIPT BLOCKING. --ignore-scripts, ignore-scripts=true
//      in .npmrc. Most malicious payloads are postinstall.
//   5. AUTOMATED MALWARE DETECTION on the registry side, with
//      automatic yanking.
//   6. RATE LIMITING on new-package publication, and a delay before
//      a brand-new package name is resolvable, which limits the
//      typosquat window.

// THE USER-FACING PART, and it belongs in your docs
   - tell people not to paste credentials into CLI tools
   - tell them a legitimate migration tool never needs their token
   - tell them what to do if they already did: revoke the token now,
//     and audit what was published with it
   - this is a five-line section in your README and it genuinely helps
//     people

// FOR YOUR OWN PACKAGE
   - enable 2FA and prefer a hardware key
   - use trusted publishing
   - publish from CI only
   - keep the maintainer count small and current
   - a 0-dependency package is a package with no supply chain

PyPI: the shape of a Python distribution

// a Python release is TWO artefacts, and they do different jobs

// 1. THE SDIST (source distribution)
//    a .tar.gz containing your source, plus a build backend
//    configuration, plus a PKG-INFO generated from that config.
//    needed because: pip may need to build from source, and because
//    some platforms are not covered by your wheels.
//    this is what a human reviews before installing.

// 2. THE WHEEL
//    a .zip with a PEP 427 layout, built for a specific
//    interpreter, platform and ABI. Installed without compiling.
//
//   yourpkg/
     __init__.py
     core.py
     _speedup.cpython-312-x86_64-linux-gnu.so
   yourpkg-1.2.3.dist-info/
     METADATA        the metadata, generated from pyproject.toml
     WHEEL           the wheel format version and build tag
     RECORD          every file with its hash and size
     LICENSE_FILES   or the licence in METADATA

// WHY TWO
//   the sdist is the source of truth for review and for platforms you
//   did not build a wheel for. The wheel is what almost everyone
//   installs. Publishing only an sdist means every install compiles.

// THE TREE, and what the layout implies
   src/yourpkg/          a src layout, strongly recommended
     __init__.py
   tests/
   pyproject.toml
   README.md
//   a src layout stops a stray local directory from shadowing the
//   installed package, which is a class of bug that is maddening to
//   diagnose and trivially avoided.

Binary wheels and the manylinux problem

This is the hardest practical problem in Python packaging, and understanding it explains a lot of confusing errors.

// THE PROBLEM
//   a C extension produces a .so linked against a specific glibc
//   version. Build on Ubuntu 24.04 and you get a wheel that needs
//   glibc 2.39, which does not exist on the manylinux_2_28 image
//   that a corporate Linux user has.

// THE THREE GENERATIONS
   manylinux2014   glibc 2.17, CentOS 7 era. Still the broadest.
//   manylinux_2_28 glibc 2.28, RHEL 8 era. The modern default.
//   musllinux_1_2  Alpine, which uses musl not glibc. SEPARATE wheels.
//
//   pip on a Linux box checks the glibc version and refuses a wheel
//   that needs a newer one, with:
//     "ERROR: Package 'yourpkg' requires a different Python" - no, the
//     real one is:
//     "manylinux2014_x86_64 wheel is not supported on this platform"

// THE FIX: BUILD IN THE MANYLINUX IMAGE
$ docker run --rm -v "$PWD":/io quay.io/pypa/manylinux_2_28_x86_64 \
    /bin/bash -c "/io/pyproject-build-and-test.sh"
//   or use cibuildwheel, which does this for a matrix of platforms
//   including musllinux, and produces all the tags automatically.

// THE TAGS, and why the filename is a mess
   yourpkg-1.2.3-cp312-cp312-manylinux_2_28_x86_64.whl
//              |    |    |    |                |
//           version |   |    |                platform
//                 CPython  ABI   manylinux tag  architecture
//   and, for the same code:
//   yourpkg-1.2.3-cp312-cp312-musllinux_1_2_x86_64.whl   Alpine
//   yourpkg-1.2.3-cp312-cp312-macosx_11_0_arm64.whl        Apple Silicon
//   yourpkg-1.2.3-py3-none-any.whl                        pure Python
//   3 interpreters x 3 OS x 2 architectures = 18 wheels, from one
//   cibuildwheel run.

// PURE PYTHON IS THE ESCAPE HATCH
//   if your package does not need to be fast, do not use C. The
//   matrix collapses to one wheel and your release process becomes
//   trivial. This is why a great deal of Python is pure Python.

// THE DEBUGGING TIP that saves hours
$ python -c "import yourpkg._speedup"
//   run this on the target platform. "undefined symbol" means a glibc
//   mismatch. "cannot open shared object file" means the .so was not
//   packaged.

// THE PATTERN ACROSS ALL THREE, and it generalises

//   2. the package name is a permanent, global namespace

// THE CENTRAL PORTAL PUBLISHING RULES, which are stricter than
// everything else here
//   1. a namespace verification. You prove you control
//      com.yourorg, usually by a TXT record or a well-known file, and
//      only then may you publish under it. This is the mechanism that
//      makes group-id squatting impractical, and it is the single best
//      anti-squatting control in any ecosystem.
//   2. PINS. Every dependency must have an exact version. A range such
//      as [1.0,2.0) is REJECTED. Rationale: ranges make the artefact
//      you publish non-reproducible.
//   3. every dependency must itself be on Central or a whitelisted
//      repo, or you must bundle it (shade, with relocation).
//   4. sources and javadoc jars must be attached.
//   5. the POM must be valid, with a licence, a description, a URL
//      and SCM information.
//   6. GPG signing of every artefact is mandatory.

// publishing

Go modules and proxies

Go is the odd one out: there is no registry you publish to, only a proxy you push a tag to.

// THERE IS NO PUBLISH STEP FOR A MODULE
//   you have a git repository with semantic version tags
$ git tag -a v1.4.2 -m "v1.4.2"
$ git push origin v1.4.2

//   that is it. The proxy notices the tag and fetches the zip.
//   a module version is the MAJOR.MINOR.PATCH part of a v-prefixed tag.
//   There is no v0.x, no pre-release, and no build metadata.

// THE PROXIES
   proxy.golang.org   the default, in GONOSUMDB/GOPROXY
   goproxy.cn         the widely used mirror
   goproxy.io         a third option
   an internal Athens  a self-hosted proxy, for air-gapped or

// go.mod
   module github.com/yourorg/yourlib
   go 1.22
   require (
     github.com/spf13/cobra v1.8.0
     golang.org/x/sync v0.7.0
   )

// THE THINGS THAT SURPRISE EVERYONE

// 1. MODULE PATHS ARE URLs, AND THEY ARE PERMANENT
     module github.com/yourorg/yourlib
//   this is a hard, permanent identity. Renaming the GitHub org is a
//   breaking change to every consumer, and the proxy will not let you
//   change it. Choose the org name knowing it outlives the repo.

// 2. THERE ARE NO RANGES. EVER.
   require github.com/spf13/cobra v1.8.0        exact
//   and MVS, minimal version selection:
//     if A requires X v1.2.0 and B requires X v1.5.0, the build
//     uses v1.5.0 for BOTH. No negotiation, no conflict.
//   This is Go's deliberate trade: no version conflicts, ever, at the
//   cost of sometimes getting a newer version than a library wanted
//   and tested against. It usually works, and when it does not, the
//   replace directive or a workspace pins it.

// 3. THE +incompatible SUFFIX, which is how v2 happens
     module github.com/yourorg/yourlib/v2
//   for v2 and above you append the major to the module path. There
//   is a stated exception: v0 to v1 needs no suffix, and v1 to v2
//   does. Your go.mod is wrong until you do this, and the error
//   message is famously unhelpful.

// 4. go.sum IS MANDATORY AND VERIFIED
//   every module hash is checked on every build, and a mismatch is a
//   hard failure. This is the strongest default integrity guarantee
//   of any ecosystem in this chapter, and it is why a Go supply-chain
//   attack is much harder than an npm one.

// 5. RETRACTING
     retract v1.2.0  // had a security issue, see GHSA-xxxx
//   a retraction is a comment in the NEXT release's go.mod. It does
//   not delete anything; it tells tooling not to select that version.
//   Same honest model as cargo yank.

// 6. PRIVATE MODULES
   GOPRIVATE=github.com/yourorg/*   skip the proxy and sumdb for these
   GONOSUMCHECK, GONOSUMDB, GOINSECURE  the older, worse-named knobs
//   a private proxy plus GOPRIVATE is the modern answer.

A container image is the one artefact type where the package manager, the version control system and the build system are all the same thing. That is convenient, and it means the usual supply-chain defences have to be recreated rather than inherited.

What OCI actually specifies

// OCI, the Open Container Initiative, is a set of specifications that
// replaced "Docker images" with a portable format. Three specifications:

// 1. THE IMAGE SPEC: a manifest and its layers
// 2. THE DISTRIBUTION SPEC: how a registry stores and serves them
// 3. THE RUNTIME SPEC: how a runtime mounts them (OCI runtimes)

// THE IMAGE, structurally
   manifest
     Config  (JSON): env, cmd, entrypoint, user, labels, history
     Layer 1 (tar.gz, the base image)
     Layer 2 (tar.gz, your dependencies)
     Layer 3 (tar.gz, your build output)
//   each layer is a DIFF, not a full filesystem. Two images sharing a
//   base share those layers on disk and on the registry, which is where
//   the efficiency comes from.

// THE DIGEST IS THE IDENTITY, and it is the important part
   sha256:9f2a1b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0
//   computed from the manifest, which includes the config digest and
//   the layer digests. Change any byte and it changes.
//   a tag is a MUTABLE POINTER to a digest. The digest is the artefact.
//   Everything in this chapter that follows from that sentence.

// MULTI-ARCHITECTURE, which is an index of manifests
   index (manifest list)
     -> manifest   linux/amd64
     -> manifest   linux/arm64
     -> manifest   linux/arm/v7
//   so one tag resolves to the right image for the machine, and the
//   digest you get back is the PLATFORM-SPECIFIC manifest's digest.
//   This surprises people who pin by digest and then get a different
//   digest on a different architecture. Use a tag, or pin the INDEX
//   digest with --platform.

// MEDIA TYPES AND ARTIFACT TYPES
//   a registry can hold more than runnable images. The same manifest
//   and blob storage holds Helm charts, WASM modules, OCI artefacts,
//   and anything else. "Artifact Hub" and registries generally are
//   converging on one storage backend for all of it.

Layers, and why your image is huge

// WHY A 300MB IMAGE HAPPENS
   FROM node:20          // 1100 MB uncompressed
   RUN apt-get update && apt-get install -y build-essential python3
   RUN npm install      // 400 MB of node_modules, plus a build toolchain
   COPY . .
   CMD ["node", "app.js"]
//   result: a 1.4 GB image, and every layer is cached FOREVER, so
//   changing one line of source does not help at all

// THE LAYER RULES, which are counter-intuitive

// 1. A LAYER IS A DIFF. Deleting a file in a later layer does not
//    remove it from the image. It only adds a whiteout entry.
//    the bytes are still in the earlier layer, on disk and on the
//    registry. This is the single most misunderstood thing about
//    image size.
      RUN apt-get install -y curl     # 30 MB
      RUN rm -rf /var/lib/apt/lists/* # does NOT recover the 30 MB
//    the same command in ONE layer does recover it, because the layer
//    is only the net diff.

// 2. A CHANGED LAYER INVALIDATES EVERYTHING AFTER IT
//    COPY . .  near the top, so a code change only invalidates the
//    final layer. COPY . .  first means every code change rebuilds
//    and re-uploads every layer below it.

// 3. CACHE KEYS INCLUDE THE COMMAND AND THE PARENT LAYER
//    change a RUN command and that layer and everything after rebuilds.

// THE MEASUREMENT
$ docker image history yourimage:1.0 --no-trunc
// shows every layer with its size. Find the layer that is 800MB and
// that is your answer. Read this output for every image you build.

// MULTI-STAGE, the actual solution
   FROM node:20 AS build
   WORKDIR /app
   COPY package*.json ./
   RUN npm ci
   COPY . .
   RUN npm run build && npm prune --production

   FROM node:20-slim AS runtime
   WORKDIR /app
   ENV NODE_ENV=production
   COPY --from=build /app/node_modules ./node_modules
   COPY --from=build /app/dist ./dist
   USER node
   EXPOSE 3000
   CMD ["node", "dist/main.js"]
//   the build stage is discarded. The final image contains only the
//   runtime dependencies, no compiler, no source, no dev modules.
//   Typical: 1.4 GB -> 180 MB, and the two stages push in parallel,
//   so the build is also faster.

// AND DISTROLESS, when you need the smallest possible
   FROM gcr.io/distroless/nodejs20-debian12
   COPY --from=build /app/dist ./dist
//   no shell, no package manager, no libc you did not ask for.
//   a useful property: a distroless image has no shell, so a
//   command-injection attacker cannot get one. That is a real
//   security boundary, not a size trick.

A Dockerfile that produces a small image

// BASE IMAGE CHOICE, the biggest single decision
   node:20            1100 MB, full Debian, includes build tools
   node:20-slim       200 MB,  no build tools
   node:20-alpine     180 MB,  musl not glibc: smaller BUT different
   gcr.io/distroless/nodejs20   ~30 MB, no shell, no package manager
   scratch             0 MB,    nothing at all

// THE ALPINE TRAP, which bites everyone once
//   musl libc is not glibc. A package compiled against glibc may not
//   run on musl. It usually works, and then it does not, in production,
//   at 3am, in a way that is very hard to reproduce.
//   also: node-gyp has historically needed build tools that Alpine
//   does not ship, and musl-resolv has DNS bugs.
//   if you use Alpine, test thoroughly with a real workload. The size
//   saving is real; so is the risk.

// THE LAYERING ORDER, which is the whole trick
//   1. base image          rarely changes
//   2. system packages     rarely changes
//   3. dependency manifests COPY package.json, COPY requirements.txt
//      THIS IS THE KEY LINE. the manifest changes less often than the
//      code, so the dependency layer is cached and does not re-upload.
//   4. dependency install
//   5. your source         changes every commit
//   6. build output

// THE FULL EXAMPLE, with the details that matter
   FROM node:20-slim AS build
   WORKDIR /app

   # dependencies first, and only the manifests
   COPY package.json package-lock.json ./
   RUN --mount=type=cache,target=/root/.npm \
       npm ci --omit=dev

   # then the source
   COPY . .

   # build, then drop dev dependencies
   RUN npm run build && npm prune --omit=dev

   FROM node:20-slim AS runtime
   WORKDIR /app
   ENV NODE_ENV=production

   # run as a non-root user
   USER node

   # copy only what is needed, from the build stage
   COPY --from=build --chown=node:node /app/node_modules ./node_modules
   COPY --from=build --chown=node:node /app/dist ./dist

   # no curl, no wget. use the runtime's own healthcheck
   EXPOSE 3000
   CMD ["node", "dist/main.js"]

// THE .DOCKERIGNORE, which nobody writes and everybody needs
   node_modules
   .git
   dist
   .env
   .env.*
   *.log
   coverage
   .vscode
   .idea
   Dockerfile
   docker-compose.yml
   tests
//   without it, `COPY . .` copies your .git directory, your local
//   node_modules with platform-specific binaries, and any .env you
//   have lying around. All three have been in a published image.

// THE CACHE MOUNTS, which are the modern addition
   RUN --mount=type=cache,target=/root/.npm npm ci
//   the npm cache lives outside the layer, so it is fast on rebuilds
//   and it does not end up in the image. Requires BuildKit, which is
//   the default in modern Docker and in every cloud build service.
//   It also means the install is NOT fully reproducible unless you
//   use npm ci with a lockfile, which the first line already does.

Tagging, and the :latest trap

// A TAG IS A MUTABLE NAME
$ docker tag myapp:1.4.2 registry.example.com/team/myapp:1.4.2
$ docker push registry.example.com/team/myapp:1.4.2
//   this is immutable in practice: nobody will let you push 1.4.2 again

$ docker tag myapp:1.4.2 registry.example.com/team/myapp:latest
$ docker push registry.example.com/team/myapp:latest
//   this is MUTABLE. Pushing a new version moves it. Every deployment
//   that says `image: latest` will get a different image tomorrow.

// THE RULES

// 1. NEVER USE :latest IN PRODUCTION
//   it is not "the newest". It is "whatever was last pushed to that
//   name", which may be a broken build, and a rollback through :latest
//   is impossible because the name now points at the new thing.
//   Kubernetes: imagePullPolicy: Always with :latest re-pulls on every
//   restart, so your pods are not all running the same image.
//   with a versioned tag, you can roll back by changing one string.

// 2. PREFER THE DIGEST for absolute determinism
$ docker pull registry.example.com/team/myapp@sha256:9f2a1b3c...
//   now nothing can change under you. This is what you want for a
//   production deployment you cannot easily change.
//   the cost: the digest is opaque. Use it in the deployment, and
//   record the human tag in your release notes.

// 3. SEMANTIC TAGS, and the pre-release problem
   1.4.2        a specific release
   1.4          floats to the newest 1.4.x
   1            floats to the newest 1.x
   main         a branch, pushed by CI. NEVER in production.
   sha-abc1234  a commit, the most reproducible mutable tag
//   pre-releases work too, and this is the correct pattern:
//     1.5.0-rc.1   only pulled if you ask for it
//     1.5.0         floats within 1.5, so 1.5.1 does NOT auto-apply.
//   The difference from npm matters: `1.5` in npm means ^1.5.0, which
//   DOES float across minors. In Docker it does not. Be explicit.

// 4. ONE IMAGE, ONE TAG. Do not build a new image for a different
//    environment that happens to have the same version number.
   myapp:1.4.2           the artefact
   myapp:1.4.2-staging    the same artefact, deployed elsewhere
//   If staging and production need different configuration, that is an
//   environment variable, not a different build.

// 5. SCRAP THE BUILD ID
   myapp:1.4.2-build-8471   ugly, and it means a cache miss on the
//   previous build's layers unless nothing changed. The content hash
//   already guarantees identity. Keep the tag human-readable.

Choosing a registry

// THE OPTIONS, and the real trade-off is not price
   Docker Hub            the default. huge, and the most-attacked.
                         free accounts have pull rate limits that
                         will bite a CI system.
   GitHub Container Registry   the sensible default if you are on GitHub.
                         packages inherit repo permissions, which is
                         genuinely excellent. Anonymous pulls are
                         disabled by default, which is correct.
   GitLab Registry       the same, for GitLab.
   Google Artifact Registry  excellent if you run on GCP. Native
                         integration with Cloud Run and GKE, and
                         vulnerability scanning built in.
   AWS ECR               the same for AWS. Cross-account pull policies
                         and IAM, which is what you want for a
                         multi-account setup.
   Azure ACR             the same for Azure.
   Quay                   Red Hat's. Free for public, and it is the
                         default registry for OpenShift.
   GitLab, Harbor         Harbor is a self-hosted, CNCF project with
                         scanning, signing and replication.
   A private registry      Gravitas, Artifactory, or a hosted
                         equivalent.

// HOW TO CHOOSE
//   1. If your code is on GitHub, GHCR. Permission inheritance alone
//      removes a whole class of credential management.
//   2. If you run on a cloud, that cloud's registry. Private link,
//      no egress cost, native IAM.
//   3. If you have a compliance requirement, check what you can
//      attest to. ACR, GAR and ECR all have certification stories;
//      Docker Hub does not.
//   4. Not Docker Hub, if you are publishing publicly, because of the
//      pull rate limits and the incident history.

// THE PULL RATE LIMIT, which will break your CI
   Docker Hub anonymous pulls: 100 per 6 hours per IP
   authenticated: 200 per 6 hours per user
   a busy CI with a shared runner IP hits this. Symptoms:
//     "toomanyrequests: You have reached your pull rate limit"
//   FIXES
   - log in on the runners, which raises the limit 100x
   - use a mirror or a cache registry in front
   - use GHCR or ACR for your base images
   - cache base images on the runner so a pull is not needed at all

// THE AUTH MODELS
   docker login with a PAT       works everywhere. A long-lived
                                 credential, so it is a ch3-oidc target.
   short-lived tokens            ECR: aws ecr get-login-password
   workload identity             GKE with Workload Identity pulls from
                                 GAR with NO stored credential at all.
                                 This is the correct end state.
   credential helpers            keep tokens in the OS keychain rather
                                 than ~/.docker/config.json

// A CI BUILD THAT PRODUCES A GOOD ARTEFACT
   - uses: docker/setup-buildx-action@v3
   - uses: docker/login-action@v3
     with:
       registry: ghcr.io
       username: ${{ github.actor }}
       password: ${{ secrets.GITHUB_TOKEN }}
//   the GITHUB_TOKEN is short-lived, scoped to this repository, and
//   needs no stored secret. This is ch3-oidc, applied to containers.

   - uses: docker/build-push-action@v6
     with:
       context: .
       push: true
       tags: |
         ghcr.io/${{ github.repository }}:${{ github.sha }}
         ghcr.io/${{ github.repository }}:1.4.2
         ghcr.io/${{ github.repository }}:latest
       provenance: true
       sbom: true
       cache-from: type=gha
       cache-to: type=gha,mode=max
//   note provenance: true and sbom: true. They add small attestations
//   to the manifest, and they are the container equivalent of the
//   signing chapter. Turn them on.

// THE ORDER, and why it matters
   1. login          fail fast if auth is broken
   2. build          with a cache, so it is fast
   3. SCAN           before pushing, not after
   4. push
//   scanning after a push means you have already published something
//   with a known-critical vulnerability.

$ docker buildx build \

Multi-architecture images

// ONE TAG, SEVERAL PLATFORMS
$ docker buildx build \
    --platform linux/amd64,linux/arm64/v8,linux/arm/v7 \
    -t ghcr.io/yourorg/myapp:1.4.2 \
    --push .
//   the pushed artefact is an INDEX: a manifest list pointing at three
//   platform-specific manifests. The registry resolves it at pull
//   time based on the requesting machine.

// HOW TO VERIFY, and the gotcha
$ docker buildx imagetools inspect ghcr.io/yourorg/myapp:1.4.2
//   lists every platform and its digest
$ docker run --rm --platform linux/arm64 ghcr.io/yourorg/myapp:1.4.2 uname -m
//   aarch64. this is the test that proves it works, because a
//   manifest list can list a platform whose image is broken.

// THE DIGEST GOTCHA
//   digest of the INDEX:      sha256:aaa...
//   digest of an arm64 leaf:  sha256:bbb...
//   pinning "image@sha256:bbb" works ONLY on arm64. On amd64 the
//   registry will refuse it.
//   if you want platform-independent pinning, pin the index digest
//   and accept that you have not verified the leaf matches.
//   most people use a tag plus a lock file, which is simpler and
//   adequate.

// QEMU, for building without the hardware
$ docker run --privileged --rm tonistiigi/binfmt --install arm64
$ docker buildx create --use --name multi
//   emulates the target architecture. SLOW, roughly 5-10x, and it
//   does not catch platform-specific code paths. Use real runners
//   with native hardware for anything that matters.

// THE ARM64 PROBLEM, specifically
//   x86-only dependencies are the common failure. If a base image has
//   no arm64 variant, your multi-arch build silently produces an
//   index with one platform, and you find out from a user.
//   check the base image supports every platform you list:
//     $ docker buildx imagetools inspect node:20-slim

Scanning, and what SBOMs are for

// SCANNING FINDS KNOWN CVEs. It does not find MALWARE.
   trivy image myapp:1.4.2
   grype myapp:1.4.2
   docker scout cves myapp:1.4.2
   $ trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:1.4.2
//   --exit-code 1 makes it fail the build. Without it, a scan is a
//   report nobody reads.

// THE THINGS A SCANNER CANNOT DO
//   - it matches versions against a CVE database. A dependency with
//     no published advisory is invisible, whether it is safe or not.
//   - it does not evaluate your code. A deliberate backdoor is
//     invisible to it.
//   - a base image from 18 months ago has hundreds of "vulnerabilities"
//     that were fixed in the OS but are flagged anyway, because
//     scanners do not model the distro's patch state well.
//   - a scanner on the final image is too late for a multi-stage
//     build: the vulnerable compiler is in the build stage, not the
//     final image.

// THE BETTER PLACE TO SCAN
   scan the BASE images separately, in a scheduled job, and pin to
   versions that pass. Then the final-image scan is a fast
   regression check rather than a source of permanent noise.
   # renovate or dependabot for base image updates
   # a scheduled job that rebuilds on a new base and reports

// THE SBOM, which is a different and better artefact
   $ syft yourapp:1.4.2 -o spdx-json > sbom.spdx.json
   $ trivy image --format cyclonedx -o cyclonedx.json yourapp:1.4.2
//   an SBOM is an INVENTORY: every package, every version, every
//   licence, in the image. Not a judgement.
//
//   WHY IT IS WORTH ATTACHING
//   - when the next Log4Shell happens, you can answer "are we
//     affected?" in minutes by grepping the SBOM, instead of scanning
//       every deployment
//   - licence compliance becomes mechanical
//   - it is a regulatory requirement in many jurisdictions now
//   - attach it to the image so it cannot be separated from it:
       --sbom true   in buildx, which attaches it as an OCI referrer
//   then:
       $ cosign download sbom ghcr.io/yourorg/myapp@sha256:...
//   the inventory travels with the artefact. That is the point: the
//   scanner that found the vulnerability will be new, and it will need
//   this file.

Signing container images

// COSIGN, and it is the tool to use
$ cosign generate-key-pair
//   produces cosign.key and cosign.pub. The PRIVATE key must not be
//   in your repository and should be in an HSM or a KMS in production.

$ cosign sign --yes ghcr.io/yourorg/myapp@sha256:9f2a1b3c...
$ cosign verify \
    --certificate-identity https://github.com/yourorg/repo/.github/workflows/release.yml \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    ghcr.io/yourorg/myapp@sha256:9f2a1b3c...
//   KEYLESS, which is the mode to prefer: no key to manage, and the
//   identity comes from the CI provider's OIDC token. The two
//   --certificate flags are what make this specific rather than
//   "signed by anybody", and they are the flags people leave out.

// WHAT GETS SIGNED
$ cosign sign ghcr.io/yourorg/myapp:1.4.2
//   this signs the TAG, which means the tag can be moved and the
//   signature becomes misleading. ALWAYS sign by digest.
$ cosign sign ghcr.io/yourorg/myapp@sha256:9f2a1b3c...

// ADMISSION CONTROL, which is what makes a signature mean something
// a signature nobody checks is decoration. Two places to enforce:
//   the registry refuses to pull unsigned images
     Kubernetes: kyverno, or the Gatekeeper policies below
   the orchestrator verifies on pull
//   Kyverno, the practical version:
     apiVersion: kyverno.io/v1
     kind: ClusterPolicy
     metadata: { name: verify-signature }
     spec:
       validationFailureAction: Enforce
       rules:
         - name: verify
           match:
             any:
             - resources: { kinds: [Pod] }
           verifyImages:
             - imageReferences: ["ghcr.io/yourorg/*"]
               attestors:
                 - entries:
                     - keyless:
                         subject: "*"
                         issuer: "https://token.actions.githubusercontent.com"
                         identity: "https://github.com/yourorg/repo/.github/workflows/release.yml"
//   this refuses to run a pod from an unsigned image. Now the
//   signature is load-bearing, and a compromised publish credential
//   is not enough.

// OTHER THINGS TO SIGN, in rough priority order
$ cosign sign IMAGE                  the image. do this one.
$ cosign attest --predicate FILE \
    --type slsaprovenance IMAGE     how it was built
$ cosign sign SBOM_FILE             the SBOM
$ cosign sign BINARY_FILE           a released binary, for air-gapped
                                    environments that verify locally
//   cosign can also sign arbitrary blobs, which is how you sign a
//   Helm chart, a Terraform module, or a package from any registry in
//   this guide.

Immutability, digests and reproducibility

// THE PROPERTY YOU WANT
//   the same source, built twice, produces the same digest.
//   If it does, the digest IS the build, and a signature over the
//   digest is a statement about the code rather than about a
//   particular build machine.

// THE FOUR THINGS THAT BREAK IT
   1. TIMESTAMPS. A layer's tar entries carry mtimes. Docker's
//      BuildKit sets them from the build time by default.
      # BuildKit normalises layer timestamps when the source is a
      # git context with a known commit time
      docker buildx build --provenance=true ...
   2. FILE ORDER inside a layer. Tar entries are in the order the
//      build wrote them, which is usually stable but not guaranteed.
   3. BUILD ARTEFACTS with non-determinism. A compiled binary with
//      an embedded timestamp, a random build ID, or a path.
   4. BASE IMAGE DRIFT. `FROM node:20-slim` is a moving target.
      The single highest-value change:
      FROM node:20.11.1-slim@sha256:abc123...
//      both the tag AND the digest. The tag for readability, the
//      digest for reproducibility. Rebuild weekly to pick up patches.

// DETERMINISTIC BUILDS, which is achievable
$ docker buildx build --output type=image,rewrite-timestamp=true \
    --no-cache -t myapp:repro .
//   rewrite-timestamp sets every layer's mtime to 0
$ docker buildx imagetools inspect myapp:repro --format '{{.Manifest.Digest}}'
   sha256:aaa...
//   build again, from a clean cache, and compare. If the digests
//   match, the build is reproducible. Most projects that try this
//   succeed within a day, and the failures are always timestamps or
//   an unpinned base image.

// WHY IT MATTERS, in order of importance
   1. a signature over a reproducible digest is a statement about the
//      source, not about one CI run
   2. a rebuild after a base image CVE lets you prove the result is
//      the same code
//   3. it catches accidental non-determinism, which is a source of
//      "it built yesterday" support tickets
//   4. a supply-chain reviewer can rebuild and compare, which is the
//      strongest possible form of verification

Rate limits and the practical workarounds

// THE LIMITS, and they are the most common container CI failure
   Docker Hub   100 anonymous pulls / 6h / IP
                200 authenticated / 6h / user
   GHCR         generous for free, but rate limited on anonymous pulls
   ECR          500 pulls / 6h per user by default, raisable
   GCR/GAR      per the quota page; free tier is limited

// THE SYMPTOM, which is never clear
   toomanyrequests: You have reached your pull rate limit.
//   or, more confusingly, an unrelated-looking 500 from the registry
   or a timeout, because the registry is queueing you behind the limit

// THE FIXES, best first
// 1. DO NOT RE-PULL WHAT YOU HAVE. The right answer for a CI runner.
      $ docker images -q node:20-slim
      # if present, the build can use the local image
// 2. USE A BUILDX CACHE, which stores layers and skips the pull
      --cache-from type=gha
// 3. LOG IN. 100 to 200 per 6 hours is the anonymous limit; a logged
//    in token is far higher.
// 4. USE A MIRROR REGISTRY in front of Docker Hub for your base images
// 5. PIN YOUR BASE IMAGE DIGESTS, so a pull is a cache hit
// 6. RAISE THE LIMIT. Docker Hub: request it. ECR: a one-line call.
//    a paid plan also raises it substantially.

// THE PROBLEM WITH PINNING DIGESTS
//   a digest pin means a base image security patch requires a rebuild.
//   That is correct and also annoying, so automate it:
//     renovate, or dependabot, opens a PR with the new digest
//     the rebuild is triggered by the PR
//     you get patches, and you keep reproducibility
//   this two-piece setup (automated digest updates plus reproducible
//   builds) is the mature answer and it is worth the setup cost.

Exercises 7

  1. Take an existing Dockerfile and measure every layer with docker image history --no-trunc. Convert it to multi-stage and measure again. Record the reduction and identify which layer was responsible.
  2. Pin your base image by digest, add a .dockerignore, and verify no .git, no node_modules and no .env is in the image. Check with docker run --rm img ls -a /app.
  3. Build a multi-architecture image with buildx, verify each platform with --platform and uname -m, and confirm the base image actually supports every platform you listed.
  4. Sign an image with cosign in keyless mode, then add a Kyverno policy that enforces the signature, and prove it rejects an unsigned image and accepts a signed one.
  5. Get a reproducible build: pin the base digest, use --output type=image,rewrite-timestamp=true, and build twice from a clean cache. Record the digests and chase every mismatch to a cause.

Publishing a VS Code extension

// THE PAT token, and why not a password
$ az devops login   // or: create a PAT at
                    // dev.azure.com/orgs/YOUR-ORG/_settings/tokens
//   a Personal Access Token for the Marketplace, with the "Manage
//   extensions" scope, at the ALL ORGANIZATIONS level.
//   it is long-lived. That is the marketplace's design, and the only
//   mitigation available is to keep it in a CI secret and rotate it.

// the publish script
   "scripts": {
     "vscode:prepublish": "npm run package",
     "package": "webpack --mode production --devtool hidden-source-map",
     "vsce:package": "vsce package --no-dependencies",
     "publish": "vsce publish --pat $VSCE_PAT --no-dependencies"
   }

// packaging, and what vsce includes
$ npx vsce package
//   it takes a .vsix, which is a zip with a specific layout:
//     extension/package.json
//     extension/dist/extension.js
//     extension/README.md
//     extension/CHANGELOG.md
//     extension/LICENSE
//     [Content_Types].xml
//     extension.vsixmanifest
//   .vscodeignore controls what is IN it. Without one, everything
//   not gitignored is packaged, including your .git directory.

// publishing
$ npx vsce publish --pat $VSCE_PAT
//   or let the CI do it
   - uses: actions/checkout@v4
   - uses: actions/setup-node@v4
   - run: npm ci
   - run: npm run package
   - run: npx vsce publish --pat ${{ secrets.VSCE_PAT }} --no-dependencies
     env:
       VSCE_PAT: ${{ secrets.VSCE_PAT }}
//   --no-dependencies is important: it stops vsce bundling
//   node_modules, which would make the .vsix enormous. You are
//   responsible for a webpack build instead.

// the publisher must exist FIRST
//   the publisher name in package.json must already be registered on
//   the marketplace. You create the publisher in the Marketplace
//   portal by linking a Microsoft account or an Azure DevOps
//   organisation. Do this before your first publish or the publish
//   fails with an unhelpful error.

// updates
//   a new version of the extension on the marketplace is an UPDATE
//   that VS Code offers automatically. Unlike npm, there is no lock
//   file: users auto-update, and auto-updating extensions have been
//   the default since 1.63.
//   THIS IS A REAL RESPONSIBILITY. You cannot ship a broken patch and
//   expect users to stay on the previous version. They will be moved
//   onto it and your issue tracker will tell you about it.
//   the mitigation is to roll the version back in the marketplace, which
//   you can do by unpublishing or deprecating a version. It does not
//   reach users who already auto-updated, so treat it as damage
//   control rather than a fix.

The webpack and target problems

// THE MOST COMMON PUBLISHING FAILURE, and it is not the marketplace's fault
   Error: The 'main' path in package.json does not exist
//   or the published extension is "installed" and does nothing

// webpack.config.js, the version that works
   const path = require('path');
   module.exports = {
     entry: './src/extension.ts',
     output: {
       path: path.resolve(__dirname, 'dist'),
       filename: 'extension.js',
       libraryTarget: 'commonjs2',      // VS Code loads it with require
       devtoolModuleFilenameTemplate: '../[resource-path]',
     },
     devtool: 'source-map',
     externals: {
       // the vscode module is provided by the host, never bundled
       vscode: 'commonjs vscode',
     },
     resolve: { extensions: ['.ts', '.js'] },
     module: { rules: [{ test: /\.ts$/, use: 'ts-loader', exclude: /node_modules/ }] },
   };

// WHY EACH LINE MATTERS
   libraryTarget: commonjs2      VS Code does require(extension.js). A
                                  webpack UMD or ESM output is not
                                  loadable and you get a silent no-op.
// externals: vscode               bundling the vscode stub module makes
//                                  the extension throw at activation.
// devtoolModuleFilenameTemplate  without it, stack traces reference
//                                  webpack:// paths that are useless
//                                  when a user reports a bug.

// THE TARGET PROBLEM: a 2022 PROBLEM THAT CAME BACK
   Error: Activating extension failed: Cannot read properties of undefined
//   VS Code 1.84+ runs extensions in a separate context. If your
//   webpack config emits ES2022+ syntax, it works locally in dev and
//   fails in the released version.
//   set the target explicitly to what the marketplace minimum allows:
     target: 'node16',          // or node18, matching engines.vscode
   or modern: false, esbuild: { target: 'es2020' },
//   and TEST IT by downloading your own .vsix and installing it in a
//   clean VS Code profile. `F5` debugging runs from source and will
//   not catch a packaging problem.

// THE WEB EXTENSION CASE
   "browser": "./dist/web/extension.js"
   "extensionKind": ["ui", "workspace"]
//   a web extension runs in a browser sandbox: no Node, no filesystem,
//   no native modules. It must be a bundle with no Node built-ins.
//   The web extension host is genuinely restrictive and the error
//   messages are poor. Build both and publish both if you can.

// DEBUGGING A PACKAGED EXTENSION
   1. F5 from source. Fix everything here first.
   2. npx vsce package, then install the .vsix in a clean profile:
      code --install-extension myext-1.4.2.vsix --force
   3. View > Output > My Extension for your own log channel
   4. Developer: Show Running Extensions for activation timing
   5. Developer: Inspect Running Extensions for a live debug console
   6. Never ship with --no-dependencies removed. If the extension
      needs a runtime dependency and you let vsce bundle it, the
      bundle is enormous and will be rejected or will break.

The Chrome Web Store

// THE THREE THINGS THAT GET EXTENSIONS REJECTED
   1. REMOTE CODE. You may not download and execute JavaScript from
//      outside the extension package. eval(), new Function(), and
//      fetching a script and eval-ing it are all permanent rejection.
//      "It is a free API on my own domain" is not an exception.
//      You may fetch DATA, including JSON config, and interpret it.
//      You may not fetch CODE.
//   2. PERMISSIONS. Request the minimum. Every warning a user sees
//      comes from a permission you declared, and declaring more than
//      you use is both a rejection risk and an install-rate problem.
//   3. NOISE. Interstitial ads, new-tab overrides, affiliate injection,
//      and anything that changes the user's default search engine.

// THE MANIFEST, version 3
{
  "manifest_version": 3,
  "name": "My Extension",
  "version": "1.4.2",
  "description": "One sentence. Under 132 characters.",
  "icons": { "16": "icon16.png", "48": "icon48.png", "128": "icon128.png" },
  "action": { "default_popup": "popup.html", "default_icon": "icon48.png" },
  "background": { "service_worker": "background.js", "type": "module" },
  "content_scripts": [{
    "matches": ["https://example.com/*"],
    "js": ["content.js"],
    "run_at": "document_idle"
  }],
  "permissions": ["storage", "activeTab", "scripting"],
  "host_permissions": ["https://example.com/*"],
  "web_accessible_resources": [{
    "resources": ["style.css"],
    "matches": ["https://example.com/*"]
  }]
}

// MV3 CHANGES THAT AFFECT DESIGN, and they are large
//   - NO REMOTE CODE, enforced. MV2 allowed it and it was the single
//     most abused capability in the extension ecosystem.
//   - SERVICE WORKER instead of a background page. It is terminated
//     aggressively. You must handle being killed: store state in
//     chrome.storage, not in memory, and re-register listeners in
//     the top level of the worker, not inside an event handler.
//   - declarativeNetRequest instead of blocking webRequest, for
//     request modification
//   - content scripts are injected via user action or on declared
//     matches, and there is no programmatic injection into arbitrary
//     pages without host_permissions
//   - the "offline" capability is gone. A local file cannot be
//     fetched without user opt-in per file.

// THE PERMISSION ECONOMICS
//   each permission produces a warning at install time, and the
//   warnings are the single largest cause of uninstall.
//     "Read and change your data on example.com"
//     "Read and change all your data on all websites"   <- avoid
//   prefer activeTab, which grants access to the current tab only on
//   user action, over a broad host permission.

// THE PACKAGE
   "scripts": {
     "build": "webpack --mode production",
     "zip": "cd dist && zip -r ../myext.zip . -x '*.map'"
   }
//   a .zip of the manifest and its assets. No bundler requirement, but
//   minify, or the review will note it and your size will be large.
//   MANIFEST V3 DOES NOT ALLOW EVAL EVEN IN A DEV BUILD, so if your
//   build uses eval for source maps, exclude the .map files, which
//   you were going to exclude anyway.

Publishing a Chrome extension

// THE PROCESS
//   1. a Google account, and a one-time developer registration fee
//   2. chrome://extensions, Developer mode
//   3. "Load unpacked" for local development
//   4. for distribution: build a .zip and upload it at
//      chrome.google.com/webstore/devconsole
//   5. fill in the listing: description, category, screenshots, icons,
//      a support URL, a privacy policy URL
//   6. set the visibility: Public, Unlisted, or Private
//      PUBLIC      anyone can find it in search
//      UNLISTED    installable by URL only, NOT searchable. ideal for
//                  a companion to your own product
//      PRIVATE     only testers in your dashboard
//   7. submit for review
//   8. review takes hours to a couple of weeks. First submissions and
//      updates to permissions take longer.

// THE REVIEW, and what reviewers look for
//   - the listing matches the behaviour. A description promising a
//     feature that is not in the build is an instant rejection.
//   - no remote code, verified by reading the bundle
//   - permissions are justified and minimal
//   - a privacy policy URL that resolves, and a privacy practices
//     disclosure form in the dashboard. Chrome requires the
//     disclosure whether or not you collect anything; answer honestly
//   - the single purpose policy: an extension must do ONE thing
//   - no affiliate links, no referral URLs, no coupon codes
//   - the icon is your own, not a trademarked logo

// THE REJECTION REASONS, from experience
   "Minimum permissions not met"           request a broader host pattern
   "Does not match description"            a listed feature is missing
   "Remote code execution"                 any dynamic code loading
   "Single purpose"                        the extension does 4 things
   "Missing privacy policy"                the URL 404s, or is not yours
   "Deceptive metadata"                    a name or icon implying
                                          affiliation with another product

// UPDATES
//   an update to an existing listing is usually faster than a new one,
//   and a permission change triggers a fresh full review. Adding a
//   host permission to an established extension is a significant
//   event: you will be asked to justify it, and your install rate will
//   take a hit from the new warning.

// PROGRAMMATIC PUBLISHING, if you ship often
//   use the Chrome Web Store API with an OAuth2 client:
//     POST https://www.googleapis.com/chromewebstore/v1.4/items/{id}
//   with the zip as base64. Automatable, and it is the only sane way
//   to ship a weekly build.
//   budget: the first upload, and any permission change, still needs a
//   manual review. Automate the submission, not the review.

Figma Community

// THREE SEPARATE FILE TYPES, with three different rules
   UI Kit     a library of components. imports between files are NOT
              published, which surprises people.
   Template   a .fig file. fully published.
   Plugin     a shared plugin. the same review scrutiny as a VS Code
              extension, because it is the same code.

// A UI KIT, the most common
//   one .fig file containing every component
//   in code:
     import { Button } from "yourorg/ui-kit"
//   NOT available in a published file. You must either:
//     a. publish the components as a single library and re-tag
//        consumers
//     b. use "variables" and "modes" for theming, which DO travel
//     c. accept that the file is a template, not a library
//   this is a genuine limitation and it is the most common complaint
//   from people who came from a code-first design system.

// VARIABLES AND MODES, which is the Figma-native answer
   variables: color/bg/default, color/bg/subtle, color/text/primary
   modes:     Light, Dark, High Contrast
//   variables and modes ARE published and do travel between files.
//   If your theming is variable-based, a published library works
//   properly across a file boundary. If it is component-swap based, it
//   does not.

// A TEMPLATE
   export a .fig, upload it, done. No code, no review scrutiny beyond
   the listing guidelines. This is the path of least resistance for
   anything that is a starting point rather than a live library.

// A PLUGIN
//   TypeScript, built with the Figma Plugin API, bundled to a single
//   main.js
     figma.ui.postMessage({ type: 'run', nodes: figma.currentPage.selection.length });
//   publish through the Figma desktop app:
//     Plugins > Development > Publish, or the community plugin portal
//   the listing rules are the strictest here:
//     - the icon must be a 96x96 PNG, no other size
//     - the name must not include the word "Figma", "Fig", or a
//       competitor's name
//     - no external network calls except to a URL you own, and it
//       must not be a proxy for something else
//     - no data collection without disclosure
//   the review is a human reading your manifest and your network
//   calls. A plugin that only reads the current page is accepted
//   quickly. One that reads the whole file takes longer.

// VECTOR NETWORK PATHS, the format to use
   .figma files for anything exported from Figma. They are a zip of
   JSON. Do NOT publish .svg as a "component library": they cannot be
   imported as components, and the file is enormous because each SVG
   repeats its viewBox and defs.
   For a design system shared with developers, publish a real library
   with code: generate a package from the same source of truth
   (Tokens Studio, or a build step) so Figma and code share one source.

Writing a listing that gets found

// A LISTING IS A LANDING PAGE, and it decides whether anyone
// installs. Most listings are written by a developer for developers,
// and read by a person deciding in about eight seconds.

// THE EIGHT SECONDS
   who is it for        one line, the problem it solves
   what it does         one sentence
   why this over the    one line. this is the line people skip.
   other 40
   is it safe           permissions, data handling, one line
   how do I start       three numbered steps, on the page
   what if it breaks    a link to issues, and a version support policy

// THE FIELDS EACH MARKETPLACE ASKS FOR
   VS Code       displayName, description (200 chars), categories,
                 icon, galleryBanner, README as the long form
   Chrome        name, description (132 chars), summary, category,
                 screenshots, a privacy disclosure form
   JetBrains     plugin.xml description, categories, an update note
   Figma         name, description, cover image, icon, categories
   Homebrew      desc, homepage, license, test. no prose.
//   npm/PyPI      the README. this is your landing page. render it.

// THE README, and it matters more than the description
//   npm and PyPI render it as the package page. It is the first thing
//   a person sees, and the only place you can explain anything.
//   the structure that works
     # name
     one sentence, no clever name pun
     ## Why
     the problem in two sentences, in the user's words
     ## Install
     the shortest possible command, plus a manual fallback
     ## Usage
     the smallest example that runs, copy-pasteable
     ## Configuration
     a table of options
     ## Compatibility
     versions, and what you support
     ## Contributing
     how to run the tests locally
     ## License
     not just the word. a link.
//   a README with an Install section and a 10-line example gets more
//   installs than a README with a logo at the top. The logo is not
//   the first thing anyone reads; the sentence is.

// SEO AND DISCOVERY, and it is not optional
   - the title is the primary search signal on npm, PyPI and the
     marketplaces. "yourpkg - a small, fast library for X" beats
     "YourPkg" every time
   - include the technology and the problem in the description, in
     plain words. People search "typescript validation", not your
     invented product name
   - a repository, a homepage and a changelog URL in the package
     metadata. They are indexed and they are trust signals
   - for a paid or commercial extension, the listing is a sales page.
     A free tier on the marketplace and a paid tier on your site
     works better than a paid marketplace listing, because the
     marketplace search is how people find you in the first place

Review responses and triage

// WHEN YOU ARE REJECTED
//   1. read the reason. They are specific and usually correct.
//   2. do not resubmit the same artefact. The second review is not
//      kinder.
//   3. reply in the thread, not a new submission. Explain what you
//      changed, referencing their words.
//   4. if the reason is a policy you disagree with, argue once, with
//      the policy quoted, and accept the outcome if they hold firm.
//      Being pleasant and specific gets a higher success rate than
//      being right.

// THE TEMPLATE THAT WORKS
   "Thanks for the review. Three things:
      1. Remote code: removed. The config fetch in settings.js now
         returns JSON only; the code path that evaluated the response
         is gone (commit abc123).
      2. Permissions: dropped 'tabs' and replaced it with 'activeTab'.
         I have re-tested the three features that used it and they all
         work with activeTab (screenshot attached).
      3. Description: rewritten. It said 'boosts your productivity',
         which does not describe what it does. It now reads: 'Formats
         CSV files in the browser, with column detection'.
    The bundle is in the new upload. Happy to add anything else."

// AFTER APPROVAL, THE WORK STARTS
   - pin the version, do not float
   - monitor the review tab, which is where extensions get reported
   - respond to issues within a few days. A marketplace page with
     unanswered issues is worse than no page.
//   - a version support policy, stated on the page. "Last release
     supports the three most recent VS Code versions" is a reasonable
     and honest policy, and it stops you from being blamed for not
     supporting something you never said you would.

// THE METRICS THAT MATTER
   installs       the primary reach metric

                  is your listing quality
   ratings        the single most influential number, and it lags by
                  weeks
   uninstall rate  a high rate with a low rating means a permissions

Most private registries exist to solve a problem a monorepo workspace or a git reference solves better. The cases where a real registry is justified are narrower than people assume, and worth being clear about before you run one.

When a private registry is the right answer

// THE CASES WHERE A PRIVATE REGISTRY IS RIGHT
   1. You OWN the name, and you need availability and an audit trail
      that a git tag does not give. A company publishing 200 internal
      packages to 500 engineers.
   2. You must not depend on a public service for availability. An
      air-gapped build environment, or a rule forbidding outbound calls.
   3. You need a policy layer: who may publish what, who may read
      what, and an audit log of both.
   4. You are a hosting provider distributing customer artefacts.

// THE CASES WHERE IT IS WRONG
   - ONE internal package used by a few teams. A git repository with a
     path or VCS reference is simpler and has no service to run.
   - You want to avoid a public dependency. Use a scoped name on a
     public registry. No infrastructure required.
   - "We might need to go offline someday." Speculative. A path
     repository is already offline-capable and costs nothing.
   - A small team with "we need our own registry" in a planning
     document. It is a significant ongoing cost for something free.

// THE COST, and it is not zero
   - a stateful service that must be highly available, because every
     build depends on it. An outage stops all engineering.
   - it must be backed up, monitored and upgraded, and it accumulates
     storage forever because nobody deletes old versions.
   - it is a supply-chain chokepoint: whoever administers it can serve
     you anything. You moved trust from a publicly audited registry to
     an internal box.
   - the ch3-oidc options are mostly unavailable to it, so you will
     be managing long-lived tokens by hand.

Why not just a git repository

// THE ALTERNATIVES, and when each is enough

// 1. THE PATH REPOSITORY. A local reference, symlinked.
   // package.json
   { "repositories": [
     { "type": "path", "url": "../packages/shared-utils",
       "options": { "symlink": true } }
   ] }
//   + no service, works offline
//   + edits are immediate
//   - monorepo-only: it is a path on this machine
//   - CI needs the repo checked out alongside

// 2. THE VCS REFERENCE. An install straight from a git URL.
   npm install github:yourorg/shared-utils#v1.2.0
   // + a real version pin: the tag
//   + no service
//   - it installs and builds from source every time, so it is slow
//   - it needs a prepare script that works in a clean checkout
//   - gitlab and bitbucket hosts are inconsistent, sometimes unsupported

// 3. THE MONOREPO WITH WORKSPACES. One repository, many packages.
   // pnpm-workspace.yaml
   packages:
     - 'packages/*'
     - 'apps/*'
   // npm
   { "workspaces": ["packages/*", "apps/*"] }
//   + one clone, one history, atomic cross-package changes
//   + npm 7+ and pnpm both do it well
//   - a large refactor across packages is one enormous pull request
//   THIS IS THE RIGHT ANSWER FOR MOST ORGANISATIONS. A monorepo with
//   workspaces covers the majority of internal distribution with no
//   infrastructure at all.

// 4. A PROXY CACHE, which is a different thing
   // see ch9-proxy. It is not a publishing destination. Many "we need
   // a private registry" requests are actually "we need a cache".

// THE DECISION, in order
   1. Do the packages need publishing at all? A monorepo with
//      workspaces means they are never published anywhere.
   2. Do they need sharing across repositories? Then git plus a VCS
//      reference, with a prepare script.
   3. Do you need availability, policy or an audit trail? Then a
//      registry, and you know why.

Satis, the self-hosted Packagist

// SATIS builds a Composer repository from your VCS hosts. The most
// mature self-hosted registry here, because a Composer package is just a
// ZIP with a composer.json in it.

// the config, in the Satis root
{
  "name": "YourOrg/Internal",
  "homepage": "https://git.example.com/platform/satis",
  "repositories": [
    { "type": "vcs", "url": "https://git.example.com/platform/shared-utils.git" },
    { "type": "vcs", "url": "https://github.com/yourorg/logger.git" }
  ],
  "require": { "yourorg/shared-utils": "*" }
}

// running it
$ composer create-project composer/satis satis/
$ php satis/bin/satis build --no-interaction
// it clones every repository, reads each composer.json, resolves the
// dependency graph, and writes satis.json plus a tree of ZIPs.
// THE OUTPUT IS STATIC FILES. nginx can serve it, and the build can be
// a cron job. There is no daemon, no database, and nothing to keep
// patched. This is why Satis is popular despite being from 2015.

// the consumer config
   // ~/.composer/config.json, or in the project composer.json
   { "repositories": [
     { "type": "composer", "url": "https://repo.example.com" }
   ] }

// the auth
   // Satis reads an auth.json
   {
     "github-oauth": { "github.com": "ghp_token" },
     "gitlab-oauth": { "gitlab.com": "glpat-token" }
   }
//   NOTE CAREFULLY: with a VCS repository listed, Composer
//   authenticates to Git to clone. That token needs repository read
//   scope and a long lifetime, stored in a file on a server. Satis
//   gives you a static registry and then reintroduces the credential
//   problem at the build step.

// VERIFYING THE BUILD, every time
$ php satis/bin/satis build --no-interaction -vvv
//   check the output for:
//   - every package you expected, and nothing you did not
//   - version numbers that match the tags
//   - a resolved dependency graph. A version requiring a package not
//     in the repository will fail at install, not at build.
// then run a real install against the built repository in CI, because
// the happy path is the only path Satis tests.

Verdaccio, for npm

// VERDACCIO is the standard self-hosted npm proxy and registry. Its
// most valuable feature is proxying: it caches npmjs on demand.

// .verdaccio/config.yaml
storage: ./storage
auth:
  htpasswd:
    file: ./htpasswd
    max_users: 1000
uplinks:
  npmjs:
    url: https://registry.npmjs.org/
    cache: true
    timeout: 30s
    maxage: 2m              # cache metadata briefly, so a yank or a
                            # new version is picked up quickly
packages:
  '@yourorg/*':
    access: $all
    publish: $authenticated
    unpublish: $authenticated
    proxy: npmjs
  '**':
    access: $all
    publish: $authenticated
    proxy: npmjs
log: { type: stdout, format: pretty, level: http }
max_body_size: 100mb

// RUNNING IT
$ npx verdaccio --config .verdaccio/config.yaml
// for production, behind TLS and behind SSO. Verdaccio's own auth is
// htpasswd, which is fine for a small team and wrong for a company
// with a directory. Most teams front it with oauth2-proxy, Pomerium,
// or an internal proxy that injects the identity.

// THE PROXY MODE, which is what people actually want
   npm install mypackage   ->  not found locally  -> fetched
                             -> cached
   npm install @yourorg/thing -> found locally, no upstream
// The result: developers get npm-like speed, already-cached packages
// make zero outbound calls, and you have a record of what was
// fetched. For a compliance-controlled environment, that is the whole
// value proposition, and it is cheaper than a full registry.

// THE GOTCHAS
   - the config format changed between major versions. Pin the version
     and read the migration notes before upgrading.
   - the cache is incomplete until something requests a package. A
     build needing an uncached package during an outage still fails.
     Pre-warm with `npm cache add` against the registry, or accept it.
   - npm's audit endpoints need proxying too, or `npm audit` fails
     behind the proxy. Verdaccio can proxy them; the config is fiddly.
   - Verdaccio has no fine-grained per-package publish authorisation
     beyond package patterns. For per-repository control you need
     something in front of it.

devpi, for PyPI

// DEVPI is a PyPI server AND a caching HTTP proxy, with one unique
// feature: per-user indexes, so a developer's staged uploads are
// visible only to them.

$ pip install -U twine devpi-server devpi-client
$ devpi-init --rootdir $HOME/.devpi
$ devpi-server --host 0.0.0.0 --port 3141 &

// a user index, which is the devpi model
$ devpi use http://localhost:3141
$ devpi login alice --password='a-strong-password'
$ devpi user -c alice
$ devpi use alice/dev
$ twine upload --repository dev dist/*
//   alice/dev is a private staging index. Uploads there are invisible
//   to everyone else. This is the best staging workflow of any
//   registry in this guide, and it is nearly unknown.

// the release step
$ devpi upload
//   moves the staged package to the user's root index and can mirror
//   it to pypi.org at the same time. Stage, test, release to both, in
//   one command.

// proxying PyPI
$ devpi-server --outside-url https://pypi.org/simple/ &
//   or run a separate instance
$ pip install requests --index-url http://localhost:3141/dev/+simple/ \
    --extra-index-url https://pypi.org/simple
//   the two-index form is the standard trick. The caveat: pip does not
//   check that the two agree on a version, so a compromised or
//   shadowed internal index can serve a package the public one would
//   have caught. Pin with hashes (chapter 5) if that matters.

// THE INDEXER, for legacy
$ devpi-genindexer debian-packages
//   builds a PEP 503 index from .deb files. There is no Ubuntu
//   equivalent, so dpkg packages are the hard case for Python
//   distribution, and this is the tool that solves it.

// THE COMPARISON
   Verdaccio  npm, the best proxy experience of the four
   devpi      PyPI, unique per-user staging, and PyPI mirroring
   Satis      Composer, static output, near-zero operational cost
//   all three are a single-process Node or Python app with no
//   database and no cluster. That is why they are common.

Artifactory, Nexus and Harbor

// THE COMMERCIAL AND ENTERPRISE OPTIONS

// ARTIFACTORY (JFrog). The most capable, and the most expensive.
//   - every ecosystem in this guide in one product: npm, PyPI, Maven,
//     NuGet, Go, Cargo, Docker, Helm
//   - a remote repository that caches an upstream, so setting it as
//     your only registry caches everything automatically
//   - replication between instances for multi-site setups
//   - PROMOTION between repositories: dev, staging, release, with a
//     rule that an artefact must be promoted rather than rebuilt. This
//     is the feature large organisations actually pay for, and it is
//     the correct answer to "the thing that passed in staging is not
//     the thing that shipped".
//   - real HA, which the self-hosted options do not give you
//   cost: priced per user, and not cheap.

// NEXUS REPOSITORY (Sonatype)
//   - a strong Maven and npm story, a Docker registry, raw repositories
//     for anything else
//   - blob stores: binaries stored by checksum and deduplicated
//   - an unusually good Go module proxy
//   - simpler and cheaper than Artifactory, smaller integration
//     ecosystem

// HARBOR (CNCF, Linux Foundation)
//   - a registry for CONTAINERS only, not a general package registry
//   - PROJECTS with RBAC, which is the model people actually want:
//     "platform/application" is a project with its own members,
//     retention policy and replicas
//   - replication rules, vulnerability scanning wired into the scan
//     step, and content trust
//   - an OPA policy layer for admission control
//   - the right answer for a container registry you run yourself

// THE CHOICE
   General registry, enterprise    Artifactory
   General, lighter, Maven-centric Nexus
   Containers only, real policy     Harbor
   One ecosystem, small team        Verdaccio / devpi / Satis
   Already in your cloud account    ECR / ACR / GAR / GCR

// THE MIGRATION COST, which nobody mentions
//   moving means every developer config, CI secret, Dockerfile and
//   deployment manifest changes. Budget a quarter at scale, and treat
//   the registry URL as an interface you do not churn.
//   the package STORAGE is not portable. A mirror is one direction.
//   Moving means a fresh publish to the new registry, which means new
//   version numbers, which means every consumer must update. Plan
//   for that before you start, not after.

GitHub Packages and packages-as-code

// GITHUB PACKAGES is the cheapest private registry if you are on GitHub
//   - permissions INHERIT from the repository. A package in a private
//     repo is visible to whoever can read the repo. No IAM system, no
//     separate credential store, no rotation problem.
//   - free for public packages, with storage allowances on free tiers
//   - one URL per ecosystem, configured per scope

// .npmrc
   @yourorg:registry=https://npm.pkg.github.com
   //npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
//   the token is the GITHUB_TOKEN you already have in CI

// ~/.m2/settings.xml
   <server>
     <id>github</id>
     <username>yourorg</username>
     <password>${env.GITHUB_TOKEN}</password>
   </server>
// and in the pom
   <distributionManagement>
     <repository>
       <id>github</id>
       <url>https://maven.pkg.github.com/yourorg/repo</url>
     </repository>
   </distributionManagement>

//   - the cost: GITHUB_TOKEN is a PAT with a long lifetime, so you are
//     back to the credential problem. Use a fine-grained token scoped
//     to read:packages and write:packages, with a short expiry, in CI.
//   - it does not PROXY, so it does not solve the offline case. For
//     that you need Verdaccio or Artifactory in front of it.

// GITLAB PACKAGES: the same model, the same trade-off.

// PACKAGES AS CODE, the newer and better answer
//   a manifest in the repository, from which the registries are
//   created. This turns "where do I publish to" into a pull request.

//   the shape, roughly
   packages:
     - name: shared-utils
       kind: library
       ecosystems: [npm, pypi]
       visibility: internal
       registries: [npm.pkg.github.com, pypi.example.com]
       owners: [team-platform]
//   a controller reconciles that manifest into registry configuration.

// WHY IT IS WORTH THE INVESTMENT
//   - registry configuration becomes REVIEWABLE. A hand-managed
//     Verdaccio access rule for 400 packages is not reviewable.
//   - access derives from CODEOWNERS, so permissions follow the people
//     who own the code.
//   - a package cannot exist without an owner, so orphans are
//     structurally impossible.
//   - a new registry or ecosystem is a change to one manifest schema,
//     not 400 manual edits.
//   the pattern is used at scale by Google, Microsoft and Netflix, and
//   open-source tooling exists. The cost is the controller: weeks, not
//   days, and it needs a platform team to own it.

Authentication and authorisation

// THE THREE LAYERS, which are routinely conflated
   1. AUTHENTICATION: who is this? a token, a certificate, SSO
   2. AUTHORISATION: may they publish this package? read? unpublish?
   3. PROVENANCE: was this artefact built from the source it claims?

// TOKEN SHAPES, best to worst
   workload identity   no stored credential at all, in Kubernetes.
                       ECR with EKS, GAR with GKE, ACR with AKS.
   OIDC exchange       minutes-long, no stored secret. Needs registry
                       support. Verdaccio does NOT do this; Artifactory
                       and the cloud registries do.
   short-lived token   minutes to hours. A sensible default.
   long-lived PAT      simple, and a permanent liability.

// PER-PACKAGE PERMISSIONS, and why the coarse model is dangerous
   "authenticated users can publish to @yourorg/*" means any engineer's
   CI token can publish ANY internal package. That is how a typo in a
   package name publishes something, and how a compromised repository
   publishes a backdoored internal library that every other service
   then installs automatically.

//   what you want
     publish    only the CI for that specific repository
     read       everyone authenticated, or a team
     unpublish  platform team only
     admin      nobody but the platform team
//   express it as CODEOWNERS or as a manifest (ch9-github). In
//   Verdaccio this means one package pattern per access rule, which is
//   exactly how a 400-package registry becomes unmaintainable.

// THE AUDIT LOG, which is the reason to run your own
   who published which version of which package, when, and from which
   CI run. Commercial registries have this. Verdaccio and devpi have
   basic HTTP logs. Satis has none, because it is static files.
//   this log is what you read during an incident, and it is the
//   difference between "we think it was the token in that repository"
//   and having no answer at all.

// TOKEN HYGIENE, in order of importance
   1. One token per system, never shared. A shared token means you
//      cannot attribute a publish.
   2. Least scope per token. A build that only needs to read cannot
//      publish.
   3. No long-lived token on a developer machine. Use the SSO login
//      flow, which issues a session.
   4. Rotate on departure, automatically. A leaver holding a publish
//      token is the most common internal-registry incident.
   5. Audit the token list. Most registries will show you every token
//      that exists, and most organisations have never looked.

Caching and proxying public registries

This is a different problem from publishing, it is far more common, and it is usually what people actually mean.

// THE PROBLEM A PROXY SOLVES
   - registry.npmjs.org goes down, or is slow from your region, and
//     every build in the company fails
//   - a compliance rule forbids outbound network calls from the build
//   - you need to know exactly which versions were available at a
//     point in time, for an audit
//   - you need to scan every dependency you install, centrally

// THE THREE MODES
   1. TRANSPARENT. Configure the proxy as the registry and let it
//      fetch on demand. Nothing else changes.
//   2. MIRROR. A scheduled job copies the entire index and every
//      artefact. Complete, deterministic, and expensive in storage.
//   3. MIRROR-WITH-FALLBACK. Mirror, but fall back to upstream for
//      anything not mirrored. The pragmatic default for a large org.

// IMPLEMENTATION NOTES
   - metadata should have a short cache lifetime. A day-long metadata
     cache means a yank or a security removal takes a day to propagate.
     Hours, not days. Verdaccio's maxage, or your proxy's equivalent.
   - artefacts never expire. Once cached, keep them, so a build that
     worked last month still works.
//   - a mirror must be a SUBSET, and the subset must be defined. A
//     full mirror of npm is tens of terabytes. Mirror what your
//     lockfiles reference, refreshed nightly from every repository.
//     that is bounded, and it is a good fit for a compliance need.
//   - the proxy is now a chokepoint. It can serve a compromised
//     package to every build. Mirror verification (checking the
//     upstream signature or hash on every fetch) is worth the effort.

// THE AIR-GAPPED CASE, which is the hard one
   - a real air gap means no proxy: the artefacts must be moved in.
//   - the process that works: build the mirror on a connected host,
//     copy it physically or over a one-way link, serve it inside
//   - verify integrity at the boundary: sign the mirror index and
//     verify it on import
//   - this is a genuinely different discipline, and it is why Nix and
//     Debian are used in defence and aerospace: the binary cache IS
//     the supply chain, and it is built for this.

Migrating away from a private registry

Everyone ends up here, and it is a quarter of work that is entirely avoidable if you plan for it.

// WHY IT IS HARD
   - every consumer's config changes: ~/.npmrc, ~/.pypirc, .m2, the
//     Cargo config, the Go env, the Docker daemon config
   - every CI secret is a registry-specific token that must be replaced
//   - every Dockerfile has a FROM or a COPY from the old registry
//   - every deployment manifest and every Kubernetes image reference
//   - the lockfiles: an entry pointing at the old registry does not
//     resolve from the new one, and a lockfile edit is a real change
//   - and the versions must be re-published, so everything gets a new
//     version number, so every consumer must update its constraint

// THE ORDER THAT MINIMISES DOWNTIME
   1. STAND UP the new registry and mirror everything. Do not tell
      anyone to use it yet.
   2. RE-PUBLISH. Publish the SAME versions to the new registry, not
      new ones. Bumping versions during a migration is what turns a
      configuration change into a dependency-resolution change.
      Run both registries in parallel for a release cycle.
   3. MIGRATE CONSUMERS in batches, with the old registry still
      available. A dual-publish period, not a cutover.
   4. ONLY THEN make the old registry read-only, and only after you
      have measured that nothing is pulling from it. A registry log is
      the only way to know.
   5. Decommission last, and keep the backup for a year.

// THE THING THAT MAKES IT EASIER, AND MOST TEAMS DO NOT DO IT
   - use a repository-scoped or org-scoped alias, not a bare hostname:
//       npm.pkg.example.com
//       pypi.example.com
//     so the registry is a single string in a few hundred config
//     files rather than scattered across many. Then the migration is a
//     DNS change plus a find-and-replace.
//   - and publish a machine-readable registry inventory, so you know
//     the blast radius before you start rather than during.

A registry is one distribution channel, and it is not always the right one. This chapter covers the alternatives — release assets, direct download, self-updating binaries, system packages — and the decision that determines which one you need.

The distribution spectrum

// FROM MOST CONTROLLED TO LEAST
   your own object storage   you control bytes, versions, retention,
                            auth. maximum work, maximum control
   a self-hosted registry    Verdaccio, Satis, Artifactory. ch9
   a git tag plus a submodule exact version, no service, awkward UX
   GitHub/GitLab Releases    free, versioned, discoverable, and a URL
                            people already know
   a public registry         one command to install, discovery,
                            dependency resolution. least control
   your own website          maximum flexibility, minimum trust. nobody
                            knows how to install from it

// THE DECISION QUESTION, and it is one question
   "Does this need to be RESOLVED as a dependency?"
   yes -> a registry. dependency graphs, ranges, conflict resolution
          and lockfiles all assume a registry-shaped interface.
   no  -> release assets or direct download. A CLI tool, an
          application binary, a design system, a font, a database
          dump, a WordPress plugin. None of these are libraries.

// THE HONEST ARGUMENT FOR A REGISTRY ANYWAY
   Even a self-contained application benefits from a registry if it
   HAS dependencies, because your user needs those dependencies too.
//   A Node CLI with 30 dependencies is unusable as a single binary
//   unless you bundle it, and bundling puts you in the business of
//   shipping your user's dependency tree, which is a supply-chain
//   decision you may not want to make.

// THE ARGUMENT AGAINST
   A registry imposes a namespace you cannot leave, an account you
   must maintain, a review process for some ecosystems, and a
   resolution model that can silently pick a version you did not test.
//   For a self-contained artefact, all of that is overhead.

GitHub Releases

// GitHub Releases is the default for binaries, and it is better than
// most people realise: immutable assets, a stable URL, CDN-served,
// and a release page people already know how to find.

$ gh release create v1.4.2 \
    --title "v1.4.2" \
    --generate-notes \
    dist/mytool_1.4.2_linux_amd64.tar.gz \
    dist/mytool_1.4.2_linux_arm64.tar.gz \
    dist/mytool_1.4.2_darwin_amd64.tar.gz \
    dist/mytool_1.4.2_darwin_arm64.tar.gz \
    dist/mytool_1.4.2_windows_amd64.zip \
    checksums.txt \
    dist/mytool_1.4.2_checksums.txt.sig

// THREE THINGS THAT MAKE IT WORK
   1. TAG-BASED. a release is attached to a tag, and a tag is
//      immutable by convention. the URL is stable forever:
//        https://github.com/yourorg/mytool/releases/download/v1.4.2/FILE
   2. ASSETS ARE CONTENT-ADDRESSED by the platform, and served via a
      CDN. No bandwidth cost, no availability problem.
   3. the release page is a changelog. --generate-notes reads the
      merged pull requests since the last release, which is a good
//      changelog with no effort.

// CHECKSUMS, and they are not optional for binaries
   $ sha256sum dist/* > checksums.txt
   $ gpg --detach-sign --armor checksums.txt
//   users verify:
//      $ sha256sum -c checksums.txt --ignore-missing
//      $ gpg --verify checksums.txt.sig
//   this is what makes a downloaded binary trustworthy, and it is a
//   five-line addition that most projects skip.

// THE LIMITS, honestly
   - no dependency resolution. A Node or Python project needs a
     registry; you cannot distribute dependencies through Releases.
   - GitHub is a single vendor. If it is blocked in your region, or
     your corporate policy bans it, the channel dies.
   - a deleted release is a broken link for everyone. Mark a bad
     release as a prerelease or delete the tag, but know that people
     have already downloaded it.
//   - there is no deprecation mechanism. You can edit the notes.

// THE GIT-LAB EQUIVALENT and the same shape
   $ glab release create v1.4.2 --name "v1.4.2" --notes CHANGELOG.md \
       dist/*.tar.gz checksums.txt

Direct download from your own site

Occasionally the only option, and it is worth doing well because it is what several large projects use for their flagship tools.

// THE PATTERN, and why it still works
   https://example.com/downloads/mytool-1.4.2-linux-amd64.tar.gz
   https://example.com/downloads/mytool-1.4.2-linux-amd64.tar.gz.sha256
   https://example.com/downloads/latest/mytool-linux-amd64.tar.gz
   https://example.com/downloads/latest.json
//   three URLs: an immutable versioned one, a mutable convenience
//   pointer, and a machine-readable index.

// LATEST.JSON, the part that matters most
{
  "version": "1.4.2",
  "released": "2026-03-14T09:31:22Z",
  "notes": "https://github.com/yourorg/mytool/releases/tag/v1.4.2",
  "platforms": {
    "linux-amd64": {
      "url": "https://example.com/dl/mytool-1.4.2-linux-amd64.tar.gz",
      "sha256": "a3f5c9...",
      "size": 18432000
    },
    "darwin-arm64": {
      "url": "https://example.com/dl/mytool-1.4.2-darwin-arm64.tar.gz",
      "sha256": "b7e2d1...",
      "size": 17920000
    }
  }
}
//   a client can discover the current version, verify it, and install
//   it with one HTTP request. This is the contract; everything else is
//   an implementation of it. ripgrep, kubectl, helm, terraform and
//   rustup all publish a file of exactly this shape.

// SERVING IT PROPERLY
   - object storage (S3, GCS, R2, Cloudflare R2) behind a CDN. Not a
//     web server: a 200 MB tarball is not a dynamic resource.
   - Content-Length and ETag set correctly, and Cache-Control on the
//     versioned URLs set to a year with immutable.
//   - the mutable "latest" path gets a very short TTL, or no caching.
//   - CORS headers if a browser will fetch it, e.g. for a WASM
//     artefact or a web installer.
//   - a Range-capable origin, so a large download can resume.

// THE PART EVERYONE GETS WRONG: verifying without a trust anchor
   A checksum served from the same host as the binary proves nothing.
//   An attacker who can replace the binary can replace the checksum.
//   Options, in increasing order of strength:
//     checksum file signed by a key whose fingerprint is printed in
//       your documentation and shipped in your other channels
     signature from your release signing key, published in the repo
//     the transparency log from chapter 3
//   "Serve it over HTTPS" is not an answer. TLS protects the channel,
//   not the artefact, and it protects nothing against a compromised
//   origin.

Self-updating clients

A CLI that updates itself is a distribution decision with a security consequence, and it is worth thinking about before you write the code rather than after.

// WHY CLIENTS DO IT
   a released binary is a version you cannot change. Every user is on
   it until they update. For a CLI that talks to your API, a stale
   client is a support burden and sometimes an outage.

// THE FOUR APPROACHES

// A. NOTIFY ONLY. The safest, and the one most tools should use.
   //   print a message, keep running the installed version
   if remote.version != current.version {
     log.Warn(`mytool ${remote.version} is available (you have ${current.version})`);
     log.Warn(`see ${remote.notes}`);
   }
//   no code is fetched, no code is run, nothing to compromise.
//   and it can be disabled: MYTOOL_NO_UPDATE_CHECK=1

// B. WRAPPER-BASED. A tiny separate binary that only replaces itself.
   brew upgrade mytool     apt install --only-upgrade mytool
   nix profile upgrade     scoop update mytool
//   the package manager owns the whole problem: signing, rollback,
//   verification, and the decision not to upgrade. This is the correct
//   answer on any platform with a package manager, and it is free.

// C. IN-PROCESS SELF-UPDATE. The binary replaces itself.
   //   used by rustup's toolchain manager, flyctl, kubectl (partly),
   //   and many Go CLIs. It is popular because it works everywhere,
//   including a machine with no package manager.
   //
   //   THE ALGORITHM, and every step exists for a reason
   //   1. fetch latest.json over HTTPS
   //   2. if the version is not newer, stop. compare semver, not
   //      string equality, or "1.10.0" sorts before "1.9.0"
   //   3. download the asset for this OS and architecture
   //   4. verify the signature or checksum against a PINNED public key
   //      compiled into the binary, not fetched
   //   5. write it to a temp file in the same directory as the current
   //      executable, so the rename is atomic on one filesystem
   //   6. set the mode to 0755
   //   7. rename over the running executable. On Linux and macOS this
   //      works: the running inode is unaffected. On Windows it does
   //      not, and you need a helper.
   //   8. on failure, leave the original untouched and say so

func SelfUpdate(ctx context.Context, current string) error {
  idx, err := fetchLatest(ctx)
  if err != nil { return err }
  if !semver.GreaterThan(idx.Version, current) { return nil }

  asset, ok := idx.Platforms[platformKey()]     // os + GOARCH + GOOS
  if !ok { return fmt.Errorf("no build for %s", platformKey()) }

  f, err := download(ctx, asset.URL)
  if err != nil { return err }
  if err := verify(f, asset.SHA256, pinnedPublicKey()); err != nil {
    return fmt.Errorf("signature invalid, not updating: %w", err)
  }

  exe, err := os.Executable()
  if err != nil { return err }
  tmp := filepath.Join(filepath.Dir(exe), "."+filepath.Base(exe)+".new")
  if err := writeFileMode(tmp, f, 0o755); err != nil { return err }
  if err := os.Rename(tmp, exe); err != nil {   // atomic on one fs
    os.Remove(tmp)
    return fmt.Errorf("could not replace %s: %w", exe, err)
  }
  return fmt.Errorf("updated to %s - restart to use it", idx.Version)
}

// THE SECURITY PROPERTIES YOU MUST KEEP
   - the verification key is COMPILED IN. A fetched key means an
//     attacker who controls the index controls the key.
//   - verification happens BEFORE anything is written, and a failure
//     leaves the original binary untouched.
//   - the new binary is downloaded to a temp path in the same
//     directory, not to /tmp and not to the user's home. A cross-
//     filesystem rename is not atomic and can corrupt the binary.
//   - if you write to a directory the user does not own (a system
//     install under /usr/local/bin), you need elevation, and you must
//     not attempt a silent sudo. Print the command and exit.
//   - the update is opt-out and the opt-out is documented.

// WHAT GOES WRONG IN PRACTICE
   - no rollback. A self-update that lands a bad version has stranded
//     every user on it. Keep the previous binary and support
//     `mytool self-update --rollback`, or publish a fixed release
//     fast enough that it does not matter.
//   - update storms. Every client checking every hour is a thundering
//     herd on your download server. Use a conditional request with
//     ETag or Last-Modified, so the common case is a 304.
//   - the update breaks the user's config. A behaviour change in a
//     patch release that a self-updater installs without asking is a
//     data-loss bug. Minor and major updates should be announced, not
//     applied silently.
//   - it does not work on Windows without care, and on Linux it fails
//     for a system-wide install the user cannot write to.

Distributing binaries and executables

// THE MATRIX YOU HAVE TO COVER. Aim for four: linux-amd64,
// linux-arm64, darwin-arm64, windows-amd64. macOS intel is nearly gone.
// A macOS build must also be signed and notarised, which is a real
// cost and a real requirement.

// GO, which is the easiest case
$ CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
    -ldflags "-s -w -X main.version=1.4.2 -X main.commit=$(git rev-parse HEAD)" \
    -o dist/mytool_linux_amd64 ./cmd/mytool
//   CGO_ENABLED=0 gives a static binary. -trimpath removes the build
//   path. The -X flags inject version info the binary can print.
//   a Go release build should be a five-line script and it works.

// RUST
$ cargo build --release --target x86_64-unknown-linux-gnu
$ cargo build --release --target aarch64-apple-darwin
//   use cross or cargo-zigbuild for cross-compilation from one host.
//   strip the binary unless you are shipping debug symbols:
//     strip = "symbols" in the release profile

// NODE, and this is where it gets uncomfortable
$ npx @electron/packager . --platform=linux --arch=x64
$ npx pkg --targets node20-linux-x64
$ bun build --compile --outfile mytool ./src/cli.ts
//   three tools that each solve it differently. pkg is unmaintained;
//   bun's --compile is the newest and smallest. All of them embed your
//   dependency tree, which means you now own those dependencies'
//   licences and their CVEs. That is the real cost of a bundled
//   binary, and it is not always acknowledged.

// ARCHIVE FORMATS
   .tar.gz   the Unix default. Universal, no dependency
   .zip      required on Windows. Do not make Linux users install unzip
   .tar.zst  better compression, faster. needs recent tar; provide
             .tar.gz as well

// NAMING, and it is a contract with your users' scripts
   mytool-1.4.2-linux-amd64.tar.gz       the clearest
   mytool_1.4.2_linux_amd64.tar.gz       what GoReleaser and Goreleaser
                                         use, and what Homebrew's test
                                         convention expects
//   if you publish to Homebrew, use the underscore form: it is what
//   every Go tool does and the formula looks conventional.

// LICENSE FILES IN EVERY ARCHIVE
   Not "the repo has one". An archive extracted in a temp directory
   has no repository. A licence file inside the archive is what makes
   the distribution compliant, and it is routinely missing.

Deb, rpm and system packages

// WHEN YOU NEED THIS
   - corporate Linux desktops where a self-updating binary is blocked
     by policy, and the IT team will only install signed packages
   - a server fleet where you want one mechanism for everything
   - a system-wide install that a non-root user cannot write to

// DEBIAN/UBUNTU
   debian/
     control              metadata: Package, Version, Architecture,
                          Maintainer, Depends, Description, Homepage,
                          Section, Priority
     changelog            required, in the debian/changelog format.
                          `dch` generates it
     copyright           the licence, in machine-readable DEP-5 form
     mytool.install       install paths
     source/format        "3.0 (quilt)" or "3.0 (native)"
   $ dpkg-buildpackage -us -uc      # produces .deb
   $ debuild -S -us -uc            # source package
//   ARCHITECTURE is per-build, not "all". You build one .deb per
//   architecture: amd64, arm64, armhf.
//   the .deb is a container: DEBIAN/control plus a data tarball. It
//   is not hard, and it is a small amount of metadata.

// REPOSITORY, and signing it
   export GPG_TTY=$(tty)
   gpg --batch --yes --passphrase-file ~/.keys/deb.pass \
       --armor --detach-sign -o dist/Release.gpg dist/Release
   gpg --batch --yes --passphrase-file ~/.keys/deb.pass \
       --clearsign -o dist/InRelease dist/Release
//   apt refuses unsigned repositories. InRelease (inline-signed) is
//   what modern apt wants; Release.gpg (detached) is the fallback.
//   apt-key is deprecated and removed. Do not use it.

// RPM, which is a similar shape with a different grammar
   mytool.spec
   Name:           mytool
   Version:        1.4.2
   Release:        1%{?dist}
   Summary:        A tool that does one thing well
   License:        MIT
   URL:            https://example.com
   Source0:        %{name}-%{version}.tar.gz
   BuildArch:      x86_64
   %install
   install -Dm755 mytool %{buildroot}%{_bindir}/mytool
   install -Dm644 LICENSE %{buildroot}%{_datadir}/licenses/%{name}/LICENSE
   %files
   %{_bindir}/mytool
   %{_datadir}/licenses/%{name}/LICENSE
   %changelog
   * Mon Mar 14 2026 Your Name <you@example.com> - 1.4.2-1
   - Release 1.4.2
//   %config for /etc files, %defattr for permissions, and a %check
//   section. RPM is stricter than it looks: a %files entry for a file
//   the build did not create is an error.
//   rpm --addsign, then rpm --checksig.

// ALTERNATIVES THAT AVOID THE PACKAGING WORK
   Nix / nixpkgs    declarative, reproducible, one expression for
                    every platform. steep learning curve, but the
                    community nixpkgs is enormous and a PR gets
                    reviewed seriously.
   Snap             auto-updates, and the store handles signing. but
                    it sandboxes your binary, which breaks a lot of
                    tools, and the confinement is a real constraint.
   Flatpak          the desktop case. very confined.
   nix-portable     a single self-contained binary with no install.
                    an underrated answer for "just run this".

Publishing from a monorepo

// THE PROBLEM
   40 packages in one repository. You changed one file in one of
//   them. What version numbers move, and what gets published?

// WHAT A CORRECT TOOL DOES, and the reasoning matters
   1. Which packages' files changed?
        changed:  packages/core/src/a.ts
                 packages/core/package.json
   2. Which packages DEPEND on those, directly or transitively?
        core is depended on by plugin-a, which is depended on by app-x
   3. For each, decide the bump:
        the changed package        -> the bump the changeset said
        a dependent with a range that still covers the new version
                                 -> no bump, no publish
        a dependent whose range does NOT cover it
                                 -> bump the minimum and publish
        a dependent in another release train -> leave it alone
   4. Apply the changesets, regenerate the changelog, commit, tag,
//      publish.
//   Step 3 is the one hand-rolled scripts get wrong, and getting it
//   wrong means either a broken publish or a publish nobody needed.

// THE TOOLS, and what each does well
   changesets    the model: a markdown file per change, a generated
                 release PR with the versions and changelog that a
                 human merges. npm and yarn workspaces.
   nx affected   a dependency graph from the project graph, not the
                 package manifests. better when builds have outputs
                 and caching matters.
   turborepo     same idea, built for a task graph and remote caching.
   lerna         the oldest. `--since` and `--force-publish` and the
                 fixed/locked mode distinction, which confuses people
//   lageis        Go, by module. correct MVS handling.
//   cargo-release Rust, one crate at a time.
//   go-modules    Go, and it is the easiest case: tag, push, done.

// THE RELEASE PR, which is the whole point
   packages/changesets/
     brave-lions-jump.md
//   ---
//   "@yourorg/core": minor
//   "@yourorg/plugin": patch
//   ---
//   fix: handle a null token in refresh()
//
//   The CI opens a PR. It contains:
//     - the version bumps in every package.json
//     - the lockfile update
//     - CHANGELOG.md entries, one per package
//     - the new versions, so they can be reverted in one revert
//   A human reads the changelog and merges. Then a second workflow
//   publishes everything, tags, and drafts release notes.
//   The value is not automation. It is that the version bump is a
//   reviewed artefact and a release is one revert.

Publishing to several places at once

// DO YOU NEED TO?
//   Common case, and it is fine: publish the package to npm AND the
//   source to a registry that wants source (JSR, Pub). Or publish to
//   npm and to an internal proxy that caches npm.
//   Also fine and very common: a source repository plus GitHub
//   Releases for the binaries, plus Homebrew and a .deb.
//   That is three channels and each has a distinct purpose. It is not
//   over-engineering; it is how a CLI tool gets installed.

// WHEN IT GETS MESSY
   You are publishing to five registries with five tokens, and a
   release fails on the third. Now you have 1.4.2 on two registries
   and 1.4.1 on the rest, and consumers see inconsistent resolution.
//   This is the real cost of multi-channel publishing and it needs a
//   strategy.

// THE STRATEGY: PUBLISH TO A PRIVATE REGISTRY FIRST
   publish to Artifactory or an internal Verdaccio, which is
   idempotent and re-runnable
   run your install smoke tests against THAT
   then promote to the public registries
//   the private registry is your staging area, it is re-writable, and
//   a failure at step 3 means nothing public was touched. Artifactory's
//   promotion feature does this natively. This is the strongest
//   argument for a private registry and it is not about availability.

// RETRY-SAFELY
   most registries reject a re-publish of the same version, so a
   retry after a partial failure needs to know what already landed:
//     for r in registries; do
//       if ! published_in "$r" "$VERSION"; then publish_to "$r"; fi
//     done
//   query each registry for the version's existence before publishing.
//   npm view, pip index versions, cargo search --limit, curl the
//   registry's metadata endpoint. It is a few lines and it turns a
//   partial failure from a manual incident into a no-op.

// THE ORDER, by ecosystem risk
   internal/private first, so a test runs against what you will ship
   least-critical public registry next, and it is the fastest to query
   the slowest and most durable (Docker Hub, Maven Central) last
//   GitHub Releases last of all, because it is the most visible and
//   the hardest to un-publish

Open source and commercial licensing models

// THE FOUR MODELS THAT WORK, and the trade-off each makes

// A. OPEN CORE. The free version is genuinely useful; the paid adds a
//    capability, not a restriction.
//    Sentry, Grafana, GitLab, HashiCorp historically.
//    + no artificial limits in the free tier, so adoption is not
//      limited by the paywall being annoying
//    + easy to explain: "the thing you need for production is paid"
//    - the boundary must be defensible. A feature a small user can
//      live without is a feature they will keep using.

// B. SOURCE AVAILABLE. You can read the source, not necessarily use it
//    commercially. AGPL, BUSL, SSPL, Elastic's licence, BSL.
//    + contributors can audit it, which builds trust
//    - AGPL is viral in a way that scares companies, and that fear is
//      rational: it does impose obligations on network services
//    - BSL has a date after which it converts to an open licence, which
//      is a promise you must keep
//    - read the actual licence. "Source available" is not a licence.

// C. FREE TIER, PAID CLOUD. The code is open; the managed service is
//    the product.
//    GitHub, Vercel, Netlify, Sentry, Stripe's tooling.
//    + no licence friction at all; anyone can run it
//    + the revenue is not from the licence, so you can be generous
//    - you need the self-hosted version to be genuinely usable, or
//      users will resent you, and that resentment is public
//    - the business depends on hosted conversion, which is a different
//      skill from selling software

// D. FULLY COMMERCIAL. Not published as source at all, or published
//    as a compiled artefact with a proprietary licence.
//    + no ambiguity
//    - nobody can audit it, and security people will say so
//    - enterprise procurement will want a SBOM, a pentest report and
//      an indemnity, which is real work
//    - a proprietary licence is not GPL-compatible, so it cannot be
//      used with GPL libraries, which is a real interoperability limit

// THE DECISION FACTORS, concretely
   do you need contributors?          -> A, B or C. D has no community.
   is adoption the business model?   -> C, or A with a generous tier
   is support the product?           -> D, and price for the support
   will you need enterprise sales?   -> D, and you will need the
                                      procurement paperwork regardless
   are you in a regulated industry?  -> B or C, and document your
                                      SBOM story

// THE ONE MISTAKE THAT IS HARD TO REVERSE
   relicensing. If you published under MIT or Apache-2.0, every
   recipient holds a perpetual licence and you cannot revoke it or
   relicense. Adding a CLA does not change this for past
   contributions. Dual-licensing later is possible but complex.
//   If you might change your mind, publish under a licence with an
//   explicit conversion path (BSL, or MPL-2.0 for a file-level copyleft
   that leaves the option open), or do not publish at all.

The release checklist

// BEFORE YOU PUBLISH
[ ] tests pass on a clean checkout with a clean dependency tree
[ ] the version is correct everywhere: package manifest, code constant,
    changelog, and the tag
[ ] the changelog says what changed and what breaks
[ ] the artefact file list is what you intend, inspected not assumed
[ ] the artefact size is within budget
[ ] licence file present, third-party attribution present
[ ] no secrets, no .env, no credentials, no debug endpoints
[ ] no node_modules, no test fixtures, no editor directories
[ ] CI only. No laptop, ever.

// BUILD
[ ] a fixed toolchain version, recorded
[ ] a committed lockfile
[ ] no network access during the build
[ ] deterministic where the ecosystem supports it, verified by
    building twice and comparing hashes

// VERIFY BEFORE PUSHING
[ ] install the artefact into a clean project in every supported
    language or shell, and import it
[ ] for a library: a consumer can install it with the documented
    command and use the smallest example
[ ] for a binary: run --version on every platform you publish
[ ] for a container: pull it and run the health check
[ ] for a marketplace submission: the review criteria, checked
    yourself, line by line

// PUBLISH
[ ] the private registry first, and install tests against it
[ ] each registry verified as idempotent: query before publish
[ ] provenance or attestation enabled
[ ] short-lived credentials (OIDC where available)
[ ] tags signed, releases cut from the tag

// AFTER
[ ] install the published version from the public registry, from a
    clean cache
[ ] tag the repository release and generate notes
[ ] update the docs: the version, the install command, the changelog
[ ] tell the people who asked for it. A release nobody hears about
    does not get adopted, however good it is
[ ] watch the first errors from real users for a day

// THE TWO THINGS PEOPLE SKIP, both of which have caused incidents
[ ] install the PUBLISHED artefact, not your build output. They
    differ more often than you would think
[ ] verify from a CLEAN cache, because a cached tarball will hide a
    broken publish entirely

Publishing is the easy part. This chapter is about what happens in year three, when you have 4,000 dependents, a maintainer who has left, and a request to pull a version for a CVE.

The maintenance lifecycle

// THE STAGES, and what each one costs
   ACTIVE           adding features, fixing bugs, reviewing PRs,
                    answering issues. the expensive phase, and the one
                    that ends when the maintainer loses interest.
   MAINTENANCE      security fixes and dependency bumps only. no new
                    features. this is where a project should sit for
                    most of its life, and it is far cheaper than
                    ACTIVE.
   SECURITY ONLY    critical fixes only, on a best-effort basis.
                    explicitly time-boxed: "supported until the next
                    release".
   END OF LIFE      frozen. the last release is the last release. say
                    so, in the README, with a date.

// WHY PROJECTS GET INTO TROUBLE
//   A package reaches 10,000 dependents and its maintainer stops
//   answering issues. The dependents cannot tell the difference between
//   "no issues" and "nobody is answering". There is no registry
//   mechanism for this. The only fix is declaring it, and almost nobody
//   does.
//   The second way: a company publishes an internal library publicly,
//   it becomes popular, an employee leaves and stops doing the
//   releases, and 400 companies now depend on something nobody owns.

// THE SIGNAL TO GIVE YOUR CONSUMERS
//   a maintenance status in the README, in the package description,
//   and ideally in the repository as a status badge
   Status: maintenance only
   Security fixes: until 31 March 2027
   See SECURITY.md for the disclosure process.
//   This costs five minutes. It is the difference between users finding
//   out and users deciding.

// THE BUS FACTOR, measured honestly
   how many people could publish a release next week?
   one  -> a bus factor of one. write it in the README, and fix it
           by adding a second maintainer with registry access NOW,
//           while you can
   zero -> this is more common than anyone admits. A repository with
           one maintainer who lost access to their 2FA device is an
//   orphan package, permanently. That has happened to very widely used
//   packages.
//   The mitigation is boring: two accounts on every registry, hardware
//   keys recorded in a company password manager, not a person's
//   password manager.

Deprecating a feature

// THE TIMELINE, and the parts people skip
   MINOR release     mark it deprecated. emit a runtime warning.
   MINOR + 1          document the replacement, with a migration guide.
   one major cycle    remove it. Do not skip this step.

// THE WARNING, and it has to be actionable
   BAD
     @deprecated
     "deprecated"
     console.warn("use the new API")
//   useless. people suppress warnings, and they cannot act on this.

   GOOD
/** @deprecated since 2.1.0, removed in 3.0.0. Use `refresh(token)`.
 *  It handles rotation and retries; this does not. Same signature. */
     function renew(token: string): Promise<Token> {
       warn('renew() is deprecated since 2.1.0 and removed in 3.0.0. '
          + 'Use refresh(token) instead: same signature, and it handles '
          + 'rotation. Migration: https://example.com/docs/m/renew');
       return legacyRenew(token);
     }
//   names the replacement, the version, the removal version, and a URL.
//   this is a migration instruction, not a complaint.

// THE RUNTIME WARNING, and where to put it
   - once per process, not per call. A warning per call turns a
     deprecation into a log-flooding denial of service.
//   - at the boundary, not deep in the implementation. The person who
//     needs to fix it is the caller.
//   - make it suppressible, and document the mechanism:
//       MYLIB_NO_DEPRECATION_WARNINGS=1
//   - include the call stack? Some libraries do. It is genuinely useful
//     and it is noisy. A short stack, or a "set this to get a stack"
//     flag, is the compromise.

// THE MIGRATION GUIDE, and what goes in it
   ## Migrating from renew() to refresh()
   They look the same, but:
   - refresh() retries on a 401 once, renew() did not
   - refresh() rotates the refresh token in place, renew() returned a
     new one and left the old valid for 30 minutes
   - refresh() rejects a token expiring within 60 seconds, renew()
     accepted it and failed later. If you depended on that, you need
     an explicit check.
   ```diff
   - const t = await renew(token);
   + const t = await refresh(token);
   ```
   Runtime warning, or the type error if your consumers are typed,
   tells them where. Say both:
//   the honest migration guide names the behaviour differences, not
//   just the rename. A guide that only shows the rename will generate
//   the bug reports.

// THE REMOVAL, and how to know it is safe
   Deprecating in 2.1 and removing in 3.0 is a promise, and keeping it
   matters more than being right the first time.
//   Before removing, check for real usage:
   - a registry-side usage signal, if there is one (npm downloads by
     package, PyPI downloads). Coarse, but it is a signal.
//   - a CHANGELOG that says "removed in 3.0" for a full major cycle
//   - a GitHub issue asking "who is using X?" with the answers
   - for a widely-used package, an opt-in telemetry list, which
     requires asking first and is worth the trouble
//   If you cannot tell, do not remove. Ship 3.0 with it still there and
//   deprecated. Carrying a deprecated function costs nothing; breaking
//   4,000 builds costs you trust.

Unpublishing, yanking and retracting

// THREE DIFFERENT OPERATIONS, and the names differ per registry

   UNPUBLISH    remove the version. disappears from resolution.
//               npm: 72 hours, then impossible. PyPI: never, for an
//               existing release. Go: no such operation at all.
//               REACH: nothing. Everyone who already installed it
//               keeps it. This is not a recall.
//   YANK         keep it resolvable, mark it as "do not select this".
//               Existing lockfiles keep working; new resolution skips
//               it. Cargo does this natively and it is the best model.
//   DEPRECATE    keep it, warn on install. npm, RubyGems, Composer.
//               The gentlest option.

// WHEN TO USE WHICH

   YANK when: a broken release, a security vulnerability, a build that
             should never have been published.
//   Nothing in your lockfile breaks. New installs get the good version.
//   THIS IS THE DEFAULT FOR "I published something bad".

   DEPRECATE when: the release works but you want people off it. A
             performance problem, a dependency that is now known to be
             compromised, a version with a subtle correctness bug.

   UNPUBLISH only when: you published something you should never have,
             such as a secret. And even then, understand the limits:

   IF A SECRET WAS PUBLISHED
   1. revoke it first. Rotation is the only action that works. A
      published artefact is in caches, mirrors, CI logs and every
      machine that installed it.
   2. then unpublish, so nobody installs it fresh.
   3. check every registry's CDN cache. npm's unpkg, jsdelivr and
      similar will serve the file from cache long after the registry
      removed it. There is an abuse-report process; use it.
   4. assume it leaked. Anything in a package registry was fetched by
      automated scanners within minutes.
//   Do not wait to revoke until you have planned the unpublish. The
//   revocation is the thing that protects anyone using it.

// THE WORST-CASE TIMELINE, from a real incident, to calibrate urgency
   T+0        a maintainer publishes a compromised version
   T+9min     an automated scanner has found it and flagged it
   T+40min    the registry has yanked it
   T+2h       the maintainers have written a postmortem
//   Everything from the registry yank onwards is communication.
//   Rotation and the advisory are what actually protect people, and
//   both are yours to do. The registry is a backstop, not a plan.

What each ecosystem lets you do

// THIS TABLE IS THE REASON TO CHECK BEFORE YOU NEED IT
//          unpublish    deprecate   yank/retract   limit
// npm       72h, owner   yes        no             no
// PyPI      never        no         no             no
// Cargo     never        soft       YES, native    no
// RubyGems  3 versions  yes        no             no
// Composer  never        yes        no             no
// NuGet     never        yes        no             no
// Maven     never        deprecate  no             no
// Go        never        comment    YES, go.mod    no
// Hex       never        no         no             no
// pub.dev   never        no         no             no
// Packagist never        no         no             no

// THE ONES WITH NO REMOVAL MECHANISM ARE A DESIGN DECISION, not an
// oversight. PyPI's reasoning is explicit and correct: a package
// manager that can silently make an existing requirement unresolvable
// is a denial-of-service vector against every project using it. Once
// your build depends on 1.2.3, it must always resolve. So the answer
// to a bad release is a new version, forever.
// This is why the security process in the next section matters more
// than the unpublish button: in most ecosystems you cannot remove the
// artefact, so you can only tell people not to use it.

// THE WORKAROUND FOR A BAD VERSION IN AN IMMUTABLE ECOSYSTEM
   1. publish a fixed version immediately
   2. publish an advisory with the affected and fixed ranges
   3. if the bad version is truly unusable, publish a same-numbered
      version that is a placeholder which throws on import with a
      message pointing at the fix. Some projects do this. It is
      hostile and it breaks builds, so it is a last resort.
//   4. for npm and Maven, unpublish within the window if the version
//      is recent enough
//   5. be loud: GitHub Security Advisory, the project's issue tracker,
//      a mailing list, and the registry's own advisory channel

A vulnerability disclosure process

// TWO FILES, AND NEITHER IS OPTIONAL

// SECURITY.md, at the repository root
# Security Policy

## Supported versions
| Version | Supported |
| ------- | --------- |
| 1.4.x   | yes       |
| 1.3.x   | security fixes only |
| < 1.3   | no        |

## Reporting a vulnerability
Email security@example.com. Please do not open a public issue.

Include: the affected version, what you observed, how to reproduce it,
and the impact you believe it has. Encryption key on request.

We aim to acknowledge within 3 working days and to have a fix or a
mitigation plan within 14 days. We will tell you when the advisory is
published, and we will credit you unless you prefer otherwise.

// Why the table matters
//   Without it, a researcher reports a CVE against 1.0.0 and you have
//   spent a day discovering you do not support 1.0.0. With it, that
//   conversation takes a minute and starts in the right place.
//   The table is also the thing that makes a "security fixes only"
//   line honest and enforceable.

// WHAT THE PROCESS ACTUALLY LOOKS LIKE, in order
   day 0        acknowledge. This is the number one thing that
                determines whether a report escalates publicly.
   day 1-3      triage: is it real, what is the impact, what is the
                blast radius, is it already public
   day 3-7      decide the fix and the disclosure timing
   day 7-14     ship the fix on the current line, and on the previous
                major if the previous major is still supported
   day 14       publish: advisory, changelog entry, release notes, a
                post if it was serious
//   If the report is already public when you receive it, say so
//   immediately and move the disclosure date up. Do not sit on it.

// THE ADVISORY, and the identifiers
   GHSA-xxxx-xxxx-xxxx   GitHub Advisory. Free, and it works with
                         `npm audit` and Dependabot. Use it for
                         anything on GitHub, whatever the language.
   CVE-2026-12345        from MITRE, via a CNA. Some ecosystems'
                         tooling keys off the CVE rather than the
                         GHSA. Some registries (PyPI, crates.io,
                         RubyGems) have their own databases you must
                         file with directly as well:
//                           PyPI     the Python Security Response Team
//                           crates   RustSec / the advisory-db
//                           RubyGems ruby-advisory-db
//                           Maven    the OSSRH / Central process
//   The identifiers must be consistent across every channel. A
//   mismatched version range between your advisory and the registry's
//   is a common and avoidable problem.

// THE VERSION RANGE, and getting it right
   "affects >= 1.0.0, < 1.4.2, fixed in 1.4.2"
//   not "all versions before the latest". Precise ranges let scanners
//   actually protect people, and an imprecise range generates noise
//   that trains people to ignore advisories.
//   If you cannot determine the lower bound, say so explicitly rather
//   than guessing low, because a range that is too wide causes every
//   user of the package to get an alert they do not need.

// THE THINGS THAT MAKE A GOOD REPORT GET TAKEN SERIOUSLY
   - a maintainer who acknowledges within a day
   - an advisory with a precise version range
   - a CVE where one is warranted
   - a credit line, if the reporter wanted one
   - a postmortem for anything serious
//   All four are public. They are the difference between a maintainer
//   people report to and one they publish about.

Handing a package over

// TRANSFER, and the registry mechanics
   npm      npm owner add NEWUSER PACKAGE
           npm owner rm OLDUSER PACKAGE
   PyPI     transfer the project to an organisation, then add a role
           to the organisation. A personal-account project cannot be
           transferred to an individual; the organisation route is
           the only one, so create the org first.
   Cargo    the crate is owned by a GitHub org or a verified domain.
           Transfer the repository to the new org: ownership follows.
   RubyGems gem owner yourgem --add newowner
           gem owner yourgem --remove oldowner
   NuGet    transfer the package to an organisation in the portal
   Composer transfer a Packagist package to another vendor namespace
   Docker   namespace ownership, via the Hub UI
//   Do this the moment a second maintainer appears, not when the first
//   one leaves. The gap is when nothing happens.

// A HANDOVER CHECKLIST
   1. Every registry account has a second person on it, with their
      OWN hardware key. Not a shared credential.
   2. The repository has CODEOWNERS, so an absent person does not
      silently become a bottleneck.
   3. CI can publish, so no release depends on one laptop.
   4. The signing keys are in a shared, backed-up store. Two offline
      copies, tested once a year.
   5. The domain is registered to the organisation, with the
      registrant details current, and the auto-renew is on.
   6. The security contact in SECURITY.md is a role, not a person.
   7. A `MAINTAINERS.md` naming who does what, so a new maintainer
      knows what they inherited.
//   5 is the one that is forgotten and the one that kills projects: a
//   lapsed domain for the security contact, or for the repository
//   itself, means nobody can be reached.

// WHEN THE MAINTAINER IS GONE AND NOT COMING BACK
   This happens, and the recovery path is narrower than people hope.
//   - ask the registry. npm, PyPI and RubyGems all have an abandoned-
//     package process for a maintainer who is unresponsive. It
//     requires evidence and takes weeks to months.
//   - ask the organisation. If a company published it, the company
//     owns it. If an individual did, nobody is obliged to take it.
//   - fork it. The new maintainer can publish under a new name and
//     the old one stays where it is. Everyone has to switch, which is
//     the cost. This is what happened to several very widely used
//     packages and it worked.
//   - the one thing not to do: publish under the same name from a
//     different account without the owner's cooperation. That is
//     namespace squatting, registries have been known to yank for it,
//     and it poisons a package you might otherwise have inherited.

Funding and sustaining maintenance

// THE HONEST ECONOMICS
   A dependency with 1,000,000 weekly downloads is used by tens of
   thousands of companies. Most of them contribute nothing, and that
   is a rational decision for every one of them.
//   Uncompensated maintenance is the norm, and it works until the one
//   person whose job it is leaves. Then it stops working, and the
//   whole ecosystem discovers it simultaneously.
//   This is a market failure, not a personal failing, and the
//   responses below are the practical ones.

// THE FUNDING OPTIONS, honestly assessed

// SPONSORSHIP (GitHub Sponsors, Open Collective, Polar)
   + zero effort, no product decision, no obligation
   + good signal: a maintainer with 40 sponsors has time to review PRs
   - irregular, and it stops the moment the visible work stops
   - best for a maintainer with a following, not for a critical
     infrastructure dependency

// OPEN COLLECTIVE, for governance as well as money
   + a real budget, transparent, with the power to vote on priorities
   + companies will fund this for governance reasons: a vote in the
     roadmap is a purchase
   - administrative overhead, and the monthly reports are real work
   - the right tool once there are 3+ companies depending on you

// A COMMERCIAL TIER, which is the most reliable funding there is
   + money that arrives because a customer got value
   + it funds the work, not the goodwill, so it survives a change of
     heart
   - it splits the codebase, and the split must be maintained forever
   - it changes who the maintainer answers to, which is a real and
     sometimes uncomfortable shift
   - best practice: an open core split on a CAPABILITY, not on scale.
//     OpenTelemetry Collector, Sentry, Grafana, GitLab.

// A SUPPORT CONTRACT
   + predictable revenue, and it is honestly what you are selling
   + SLA obligations, which turn "I will get to it" into a commitment
   - only works with an enterprise audience, so it is useless for a
     library used mostly by individuals

// TIPPING, WHICH DOES NOT WORK
   - very low yield, unpredictable, and it creates an expectation of
     responsiveness you cannot meet
   - fine as an addition to a funded model, poor as the model

// THE PRACTICAL PATH
   1. Start with sponsorship. It costs nothing and it takes a week.
   2. Put funding links in the README, the package page, and the
      issue template. Most maintainers do this badly, and the people
      who would fund never see the ask.
   3. When one company depends on you enough to have an outage
      problem, start a conversation about funding BEFORE the outage.
   4. Move to Open Collective when you have money to administer, not
      when you need it. It will not raise money for a project with no
      budget history.
   5. Build the commercial tier only when you cannot keep up on
      goodwill. It is the most reliable money and the most expensive
//      in engineering complexity.

// THE TENSION NOBODY TALKS ABOUT
   Funding follows visibility. A critical internal dependency used by
   200,000 companies but with no stars, no conference talks and no
   social presence raises nothing. If your package is invisible and
   load-bearing, the fix is partly documentation, partly naming the
   companies using it in the README with permission, and partly just
   asking them directly. A single email to one engineering manager
   has a better hit rate than any amount of documentation.

The operational playbook

// DAILY
[ ] dependency update PRs triaged
[ ] CI green on the default branch

// WEEKLY
[ ] open issues triaged: label, acknowledge, or close
[ ] new PRs reviewed, or told why they will be later
[ ] anything security-shaped triaged today, not in the backlog

// MONTHLY
[ ] release, or a note explaining why not
[ ] download/usage numbers checked for a sudden drop. A 40% drop
    after a release is a bug report you have not received yet
[ ] dependents scanning for newly published advisories against your
    own packages

// QUARTERLY
[ ] audit registry accounts: who has access, who should not
[ ] audit CI secrets, and rotate anything older than a year
[ ] review the two-maintainer rule: does it still hold
[ ] check the domain renewal and the certificate expiry
[ ] read one dependency's changelog for something that should affect
    you

// ON A SECURITY REPORT
[ ] acknowledge within one working day
[ ] triage within three: real or not, impact, blast radius, is it
    already public
[ ] fix on the current line and any still-supported major
[ ] advisory with a PRECISE version range, a GHSA, and a CVE if
    warranted
[ ] file with the ecosystem's own database if there is one
[ ] publish, and credit the reporter unless they opted out
[ ] postmortem if the report was serious, and link it from the
    advisory

Exercises 11

  1. Depprecate a function in your own package with a runtime warning that names the replacement, the version and a migration URL. Verify it fires once per process rather than per call, and that it can be suppressed.
  2. Publish a same-numbered fix over a broken release in two ecosystems — one where you can unpublish and one where you cannot — and document what users experience in each case.
  3. Write SECURITY.md for one of your packages, with a supported-versions table. Then measure how long it takes you to produce an advisory with a precise version range for a hypothetical issue.
  4. Audit your registry accounts across every ecosystem you have ever published to. Produce a list of accounts, owners and removal dates. Remove anyone who has left.
  5. Add funding links to a README, a package page and an issue template, then track inbound funding for a month. Compare with the effort. Decide whether to keep it.
