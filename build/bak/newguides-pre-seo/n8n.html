0.1 What n8n is, and what it is not

n8n is a source-available, node-based workflow automation platform. You draw a graph of nodes on a canvas, and n8n executes that graph as a workflow against streams of data items — on the vendor's cloud or on a server you control.

The problem it actually solves

Most integration work is glue: take an event from one system, reshape it, call two or three APIs, decide something, then write the result somewhere else. Written as a bespoke service, that glue is a repository, a deployment pipeline, retry logic, a credential store, a scheduler, and an audit trail — none of which is the interesting part. n8n replaces that scaffolding with a visual graph plus a runtime that already handles scheduling, HTTP, credential encryption, retries, execution history and concurrency.

The runtime is not a black box. Every node is a TypeScript package that reads an array of items and returns an array of items, and every workflow is a JSON document you can export, diff and version. When the visual layer runs out — a strange pagination scheme, a binary format, a signature you have to compute by hand — you drop a Code node in and write JavaScript, or (since n8n 2.0, with task runners) native Python.

Node-based execution, not a script runner

The unit of work is a node; the unit of data is an item. A node receives items, runs once per item by default, and emits items. That single rule explains most n8n behaviour: a "Send Slack message" node fed five items sends five messages, and a "Set" node fed five items edits five items. Control flow is expressed by connecting node outputs rather than by writing if and for — although a Code node can always do it the imperative way.

This is the same shape as an Excel formula pipeline or a Unix pipe, and the mental model transfers: each stage is small, testable in isolation, and inspectable because n8n keeps the input and output of every node in every execution.

What n8n is not

Being clear about the edges saves a lot of wasted effort later.

  • Not a general application framework. n8n is bad at serving many concurrent low-latency requests for end users, at long-running stateful sessions, and at rich UI. Build that as an app and call n8n from it.
  • Not a high-volume stream processor. Queue mode scales to thousands of executions an hour with enough workers, but a million-message-per-minute Kafka topic belongs in a stream processor; n8n is the orchestration layer around it.
  • Not a data warehouse. Execution data is operational history, not analytics. Prune it.
  • Not open source in the OSI sense. The code is public and self-hostable under the Sustainable Use License, which restricts commercial resale; see 0.2.

Versions matter here. This guide documents n8n 2.x (stable line 2.4x). The 2.0 release changed a lot: Python via Pyodide was removed, task runners became mandatory for code execution, the Start node was deleted, and the old Activate/Deactivate toggle became explicit Publish/Unpublish. If a tutorial predates 2.0, treat its UI instructions as suspect.

0.2 The fair-code licence and the editions

n8n is published under the Sustainable Use License — "fair-code", not open source. Some code directories additionally fall under an Enterprise licence. What that means in practice is narrower than most people assume, but it is not nothing.

Fair-code, not open source

The Sustainable Use License lets you use, modify and self-host n8n free of charge, including inside a company, and including to run your own business processes. What it does not allow is offering n8n itself to third parties as a hosted or embedded service — building "Automation Cloud, powered by n8n" and selling subscriptions, or white-labelling the editor into your product — without a commercial agreement. The source is public, so you can read and audit everything; the restriction is on competing with the vendor using the vendor's own work.

Practical consequences for a self-hoster: internal use, client projects where n8n is the plumbing rather than the product, and forking for your own patches are all fine. Reselling n8n-as-a-service is not.

Editions: what is free and what needs a licence

One product, several editions. The differences are features and support, not the execution engine.

Read the licence before you build a product on top of n8n. The migration path from "self-hosted free" to "we need a commercial licence" is fine; discovering it after launch is not.

0.3 Cloud versus self-hosted

The same product, two very different operational realities. Cloud removes infrastructure work and charges per execution; self-hosting removes execution limits and hands you backups, upgrades, TLS and credential security.

Choosing between them

SituationPickWhy
Trying n8n today, no server skillsCloudSign up, no install; 14-day trial with Pro features
Corporate network, data cannot leaveSelf-hostedRuns where your data already is
Bursty workloads, low average volumeCloudPer-execution billing matches the pattern
High and steady execution volumeSelf-hostedNo per-execution metering; you pay for a server
Custom nodes, private npm modules, unusual networkingSelf-hostedFull filesystem and package control
Need SSO and environments but no ops teamCloud EnterpriseGovernance without infrastructure

The hidden cost of self-hosting

Self-hosting is free in licence terms and not free in time. You own: TLS termination, the reverse proxy and correct WEBHOOK_URL configuration, database backups, the encryption key, n8n version upgrades (which are weekly minor releases), Postgres tuning, execution pruning, log rotation, and monitoring. A production-grade single-node install is a day of work; a queue-mode cluster with multi-main is a project.

The two things that bite hardest are both invisible until they are urgent. The first is the encryption key: lose it and every stored credential becomes undecryptable garbage. The second is the webhook URL: if WEBHOOK_URL does not match the public address, n8n registers webhooks against the wrong host and third-party callbacks silently stop arriving.

The shape of a Cloud instance

Cloud gives you the same editor and the same node library, plus the vendor's n8n Assistant (an in-product AI assistant that can draft nodes and explain errors) without the sandbox stack described in chapter 1. Execution accounting is per production execution: schedule triggers count every fire, polling triggers count only when they find new data, and webhook triggers count every request that starts a workflow. Manual runs from the editor, sub-workflow runs and error-workflow runs do not count.

0.4 Nodes, workflows and the item model

Four ideas carry the whole platform: a workflow is a JSON graph, an execution is one run of that graph, an item is one record of data, and a node is a step that maps items to items.

A workflow is JSON

Export a workflow (⋯ → Download) and you get a document with three top-level arrays: nodes, connections and the workflow settings. Each node entry carries its type, a version number, its position on the canvas, its parameters and (never) its credentials — credentials are referenced by id and stored separately, encrypted.

// an exported workflow, heavily trimmed
{
  "name": "Daily invoice reminder",
  "nodes": [
    {
      "parameters": { "rule": { "interval": [{ "field": "cronExpression", "expression": "0 8 * * 1-5" }] } },
      "id": "a1b2c3d4-0000-4000-8000-000000000001",
      "name": "Weekday 08:00",
      "type": "n8n-nodes-base.scheduleTrigger",
      "typeVersion": 1.3,
      "position": [0, 0]
    },
    {
      "parameters": { "jsCode": "return $input.all().map(i => ({ json: i.json }));" },
      "id": "a1b2c3d4-0000-4000-8000-000000000002",
      "name": "Normalise",
      "type": "n8n-nodes-base.code",
      "typeVersion": 2,
      "position": [240, 0]
    }
  ],
  "connections": {
    "Weekday 08:00": { "main": [[{ "node": "Normalise", "type": "main", "index": 0 }]] }
  },
  "settings": { "executionOrder": "v1", "timezone": "Europe/Berlin" }
}

Because it is plain JSON, the whole workflow is versionable in Git, reviewable in a pull request, and generatable by a script — which is exactly what people do at scale.

Items: the unit of data

Between nodes, data travels as an array of item objects. A normal item wraps its payload in a json key; attachments live under binary.

// the data structure every node speaks
[
  {
    "json": { "email": "ada@example.com", "plan": "pro", "seats": 12 },
    "binary": {
      "data": {
        "data": "<base64>",
        "mimeType": "application/pdf",
        "fileName": "invoice-1041.pdf"
      }
    }
  },
  {
    "json": { "email": "grace@example.com", "plan": "free", "seats": 1 }
  }
]

Two items here, processed independently by the next node. This is why "looping" in n8n usually means "do nothing special": a node that receives two items and can handle one item at a time simply runs twice. The Code node is the exception — it can be told to run once for all items, which is the mode you want for aggregations.

Parameters and Settings are different tabs

Each node has a Parameters tab (what this node does) and a Settings tab (how it behaves in the workflow). The settings are where the operational knobs live: Always Output Data, Execute Once, Retry On Fail with max tries and wait interval, On Error (stop, continue using regular output, or continue using the error output), and free-text notes rendered on the canvas. Beginners lose hours because they hunt for retry logic in node parameters; it has lived in the Settings tab since the 1.x line, where it replaced the old single "Continue On Fail" toggle.

Triggers start executions

Exactly one style of execution begins without you clicking anything: a node that is a trigger. Triggers are the entry points — a schedule, an inbound webhook, a poll against an app, a chat message, a manual button, or a call from another workflow. Every workflow needs at least one because a production execution has to be started by something.

A workflow with no trigger can still be run by hand, which makes it a scratchpad. A workflow with a trigger becomes a service once you publish it. That single act is what registers the webhook route, arms the timer, or starts the poller.

1.1 Running from npx and npm

The fastest path to a working editor is npx n8n. Installing globally with npm adds version control and a permanent entry point. Both store their data in ~/.n8n.

Node.js requirements

n8n 2.x requires Node.js between 20.19 and 24.x inclusive. Anything older fails at startup; anything newer may work but is untested. Check first, because the failure mode when you skip this is a confusing native-module error rather than a clean version message.

# shell - check before installing
node -v      # v20.19.0 or newer, not v25+
npm -v

Running with npx, with no install

npx n8n downloads a temporary copy, starts the server, and opens the editor on http://localhost:5678. Data still persists in ~/.n8n, so workflows survive the temporary install. This is the right choice for a first look and for CI smoke tests.

# shell - no global install, but real persistence
npx n8n                # then open http://localhost:5678
npx n8n start          # explicit subcommand form
npx n8n@2.43.5         # pin one version for a reproducible trial

The first run asks you to create an owner account. That account is local to the instance and is stored in the database, not in an external identity provider.

Installing globally, and the PATH problem

npm install -g n8n puts a launcher on your PATH so you can run n8n from anywhere. On Windows and on Linux boxes where the global prefix is not on PATH, the error is a bare "command not found" that looks like a failed install; npm prefix -g tells you where the binary actually landed.

# shell - install, pin, and run
npm install -g n8n@2.43.5     # pin in production; never rely on "latest"
n8n start                     # or just: n8n
npm prefix -g                 # where the global bin directory lives

# roll back a bad upgrade
npm install -g n8n@2.42.0
n8n db:revert                 # reverse the last database migration, if needed

Global npm installs also cost you the isolation a container gives you: n8n shares the system's Node runtime with everything else installed the same way, so a native dependency upgraded for another tool can break it in a way that looks like an n8n bug. Pin the version in the install command, keep the npm route for the laptop, and use the container image for anything that has to survive an unattended upgrade.

npm-based installs are deprecated from n8n 3.0. For anything that has to survive the next major version, run n8n in a container instead. npm remains perfectly fine for local development.

1.2 Docker

docker run n8nio/n8n is the recommended way to self-host. One volume mount makes the instance persistent; environment variables configure everything else.

A minimal but correct container

The official image runs as the unprivileged user node and stores everything under /home/node/.n8n. Mount a named volume there or you will lose workflows, credentials and the encryption key when the container is recreated.

# shell - the smallest production-shaped run
docker volume create n8n_data

docker run -d --name n8n --restart unless-stopped \
  -p 5678:5678 \
  -e GENERIC_TIMEZONE="Europe/London" \
  -e TZ="Europe/London" \
  -e N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true \
  -v n8n_data:/home/node/.n8n \
  n8nio/n8n:2.43.5

Three environment variables earn their place immediately. TZ sets the container's system time; GENERIC_TIMEZONE is what schedule-oriented nodes use, so they can differ and often should not. N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS sets the config file to 0600, so only the owner can read the encryption key inside it.

Image tags and channels

n8n renamed its release channels in 2.0: stable replaces latest and beta replaces next. The old tags still resolve for now but are scheduled for removal, so pin a concrete version in anything long-lived. A weekly minor release cadence means "latest" is genuinely a moving target — the practical failure is an unattended restart pulling a version whose database migration you have not backed up for.

# shell - pick a channel deliberately
docker pull n8nio/n8n:2.43.5   # a specific version - do this in production
docker pull n8nio/n8n:stable   # newest stable
docker pull n8nio/n8n:beta     # newest release, may be unstable

# update a pinned container
docker pull n8nio/n8n:2.44.0
docker stop n8n && docker rm n8n
# ...re-run with the new tag, same volume

Pointing it at PostgreSQL

SQLite is the default and is fine for a single user. The moment a second person edits, or several workflows poll at once, move to PostgreSQL: SQLite serialises writes, and n8n's execution writes are frequent. In n8n 2.x, MySQL and MariaDB backends were dropped entirely, so Postgres is the only supported server database.

# shell - Postgres as the backing store
docker run -d --name n8n --restart unless-stopped -p 5678:5678 \
  -e GENERIC_TIMEZONE="Europe/London" \
  -e DB_TYPE=postgresdb \
  -e DB_POSTGRESDB_HOST=postgres \
  -e DB_POSTGRESDB_PORT=5432 \
  -e DB_POSTGRESDB_DATABASE=n8n \
  -e DB_POSTGRESDB_USER=n8n \
  -e DB_POSTGRESDB_PASSWORD='change-me' \
  -e DB_POSTGRESDB_SCHEMA=public \
  -v n8n_data:/home/node/.n8n \
  n8nio/n8n:2.43.5

Keep the .n8n volume even with Postgres. It still holds the encryption key, instance logs and source-control assets; the database file is the only thing that moves out.

Run curl -sf http://localhost:5678/healthz after starting. It returns a tiny JSON body when the HTTP server is up, which is the same probe your container orchestrator should use.

1.3 Docker Compose

Compose turns a long docker run into a reviewable file, adds Postgres as a first-class service with a healthcheck, and makes upgrades a two-command operation.

A complete, production-shaped Compose file

This is the shape worth memorising: a Postgres service with a healthcheck, an n8n service that waits for it, one named volume each, and an .env file that holds the secrets so they never appear in the YAML.

# docker-compose.yml
services:
  postgres:
    image: postgres:18
    restart: always
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
      PGDATA: /var/lib/postgresql/data
    volumes:
      - db-storage:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h localhost -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: n8nio/n8n:2.43.5
    restart: unless-stopped
    ports:
      - "5678:5678"
    environment:
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: ${POSTGRES_DB}
      DB_POSTGRESDB_USER: ${POSTGRES_USER}
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      WEBHOOK_URL: ${WEBHOOK_URL}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      N8N_PROXY_HOPS: "1"
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  db-storage:
  n8n_data:

The .env file that goes beside it

Keep this out of version control. Generate the encryption key once and then treat it as a backup-critical secret, because every credential in the database is encrypted with it.

# .env - never commit this file
POSTGRES_USER=n8n
POSTGRES_PASSWORD=a-long-random-password
POSTGRES_DB=n8n
GENERIC_TIMEZONE=Europe/London

# openssl rand -base64 42 (or any long random string)
N8N_ENCRYPTION_KEY=replace-me-with-32-plus-random-characters

# the public address users and third-party services reach n8n on
WEBHOOK_URL=https://n8n.example.com/

Starting, inspecting and upgrading

# shell - the four commands you will actually use
docker compose up -d                  # start everything, detached
docker compose ps                     # is postgres healthy?
docker compose logs -f n8n            # follow n8n's stdout

# upgrade: change the image tag in the file, then
docker compose pull
docker compose up -d                  # recreate with the new image

Note the asymmetry in the healthchecks: Compose will start n8n only once Postgres reports healthy, which prevents the classic "n8n crash-looped three times at boot before the database was ready" pattern. If you skip the healthcheck, add --restart unless-stopped and accept the noise.

Postgres 18 changed its default data directory. Keep the explicit PGDATA: /var/lib/postgresql/data line in the service, or the volume mount covers a directory Postgres no longer writes to and your data appears to vanish on restart. Upgrading an existing cluster from an older major version is a separate job: back up with pg_dumpall and follow the PostgreSQL upgrade guide.

The n8n Assistant stack

Since the 2.x line, self-hosted instances can run the in-product n8n Assistant — an assistant that drafts nodes, explains errors and searches documentation. It is optional, and it is not part of the n8nio/n8n image. You add a sandbox service (sandbox-api plus a privileged Docker-in-Docker runner) and, for web search, a SearXNG container. The vendor publishes a one-line setup script and a get-n8n-compose.yml that wires them together.

Treat the runner container as equivalent to root on the host: it executes AI-generated code inside nested sandboxes and must never be exposed to the internet. For a production instance the vendor recommends an external sandbox provider (Daytona) instead of the bundled Docker-in-Docker one.

The _FILE pattern for secrets

Docker secrets, Kubernetes secrets and most secret managers mount files rather than injecting environment variables. n8n supports this for many variables: append _FILE and point it at a path, and n8n reads the value from that file.

# shell - the secret never appears in the process environment
# a file mounted at /run/secrets/encryption_key containing the key
export N8N_ENCRYPTION_KEY_FILE=/run/secrets/encryption_key

# same idea for the database password
export DB_POSTGRESDB_PASSWORD_FILE=/run/secrets/pg_password

This matters because environment variables leak in obvious ways: docker inspect, /proc/<pid>/environ, crash dumps and child processes. A mounted file with 0600 permissions does not.

Security-relevant defaults in 2.x

n8n 2.0 tightened several defaults, and each one has changed what a working setup looks like:

  • N8N_BLOCK_ENV_ACCESS_IN_NODE now defaults to true. Node code and expressions can no longer read process.env unless you turn this off. Use credentials or variables instead of environment variables inside workflows.
  • N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS requires 0600 on the config file by default. On Windows, where POSIX permissions do not apply, set it to false or the instance refuses to start.
  • Task runners are on by default, so Code node execution happens in a separate process with a restricted API. N8N_RUNNERS_ENABLED is deprecated from 2.0 — you no longer set it.
  • NODES_EXCLUDE ships with Execute Command and Local File Trigger disabled, because both hand a user shell or filesystem access. Re-enable deliberately.
  • N8N_RESTRICT_FILE_ACCESS_TO defaults to ~/.n8n-files, so the file nodes can only touch that directory.
# shell - deliberately re-enabling a dangerous node on a trusted instance
export NODES_EXCLUDE="[]"                  # enable everything (know what you are doing)
# export N8N_RESTRICT_FILE_ACCESS_TO=/srv/n8n/files
# export N8N_BLOCK_ENV_ACCESS_IN_NODE=false

Precedence, and when to use a config file

Environment variables win over the config file; a variable set on the command line wins over both. The config file at $N8N_USER_FOLDER/.n8n/config is rarely needed, but it is the tidiest home for nested settings that have no environment-variable form and for anything you want to diff. N8N_USER_FOLDER relocates the .n8n directory itself, which is how you run two instances on one machine.

1.5 Persistence, backup and the encryption key

Everything n8n knows lives in two places: the database (workflows, credentials, executions) and the .n8n directory (encryption key, config, logs). Back up both, and keep the key somewhere other than the server.

What is stored where

LocationContentsLoss impact
Database (SQLite file or Postgres)Workflows, versions, credentials (encrypted), executions, users, variablesTotal data loss

The encryption key is the whole ballgame

When n8n first starts it generates a random key and writes it into its config. Every credential you create is encrypted with that key before it touches the database. There is no recovery path: restore the database without the matching key and every credential decrypts to nothing, which means every workflow that uses one fails until somebody re-enters the secret by hand.

So the professional setup is: define N8N_ENCRYPTION_KEY yourself, store it in your secret manager, and make it part of every deployment. That way "restore the database on a new machine" works, and rotating the key becomes a deliberate, backed-up operation rather than an accident.

# shell - generate the key once, then store it in your secret manager
openssl rand -base64 42

# queue mode and workers must all share the main instance's key:
export N8N_ENCRYPTION_KEY="the-same-value-on-every-instance"

A backup that actually restores

# shell - Postgres + .n8n volume, the two things that must agree
docker compose exec postgres pg_dump -U "$POSTGRES_USER" -Fc n8n > n8n-$(date +%F).dump

docker run --rm -v n8n_data:/data -v "$PWD":/backup alpine \
  tar czf /backup/n8n-home-$(date +%F).tar.gz -C /data .

# export workflows and credentials through the CLI, as a portable fallback
docker compose exec n8n n8n export:workflow --all --output=/data/workflows.json
docker compose exec n8n n8n export:credentials --all --output=/data/credentials.json

The CLI export is worth doing before upgrades even when you have a database dump, because it produces a human-readable, version-controllable artefact and it is the supported path for moving between instances. Test a restore on a scratch machine at least once; an untested backup is a belief, not a backup.

In 2.x an instance can also use Git-based source control (Business/Enterprise) to keep workflows in a repository. That is versioning for the definition, not a backup for credentials or execution history — you still need the database.

2.1 The canvas, the node panel and connections

The editor is one screen with four regions: the header (publish, save state, history, settings), the left panel (node picker and node names), the canvas, and the node details panel that opens when you select a node.

Opening a node and understanding its two tabs

Double-click any node to open its details panel. Parameters is what the node does; Settings is how it behaves. The INPUT and OUTPUT panes at the bottom of the panel are the single most useful part of the whole editor: after a run they show the exact items that entered and left this node, and they are where you drag fields from.

A node that has not run yet shows nothing there. That is not an error — it means n8n has no data for it in the current execution, which is also what a dirty node looks like: a node whose parameters changed after the data was produced, so its displayed output is stale. n8n marks dirty nodes so you know to re-run.

Connections carry branch indexes

A node output is not a single wire. Each output has a branch index starting at 0, and nodes like IF and Switch emit items on different branches. The rendered connection tells you which is which: hovering over an IF node's two dots shows true and false, while Switch outputs are numbered. When you reference previous-node data from an expression, this branch index is what n8n uses to decide which output to read unless you say otherwise.

// JS - inside a node, outputs are arrays of arrays
// output[0] is the first branch, output[1] the second
return [
  [ { json: { route: "sales" } } ],      // branch 0
  [ { json: { route: "support" } } ]     // branch 1
];

Finding nodes quickly

Press Tab (or click the +) to open the node picker and type. Search matches node names, not app names, so "webhook", "if", "merge", "schedule" work directly. Two prefixes are worth knowing: nodes tagged Trigger can start a workflow, and nodes under the AI group (chat trigger, agent, model, tool and vector sub-nodes) are the LangChain-based cluster covered in chapter 9.

Community nodes are installed from Settings → Community nodes by their npm package name (n8n-nodes-…). On Cloud they are unavailable. On self-hosted they run with the full privileges of the n8n process, so install them the way you would install any npm package you found on the internet: rarely, and deliberately.

Canvas habits worth forming

  • Ctrl/Cmd + Enter runs the whole workflow; double-clicking a node runs only that node, using the last known input.
  • Ctrl/Cmd + S names a version; Shift + P publishes.
  • Select a node and press D to deactivate it without deleting it — the single most useful debugging move, because a disabled node passes items straight through.
  • Pin the canvas zoom with 1; the arrangement of nodes is cosmetic but the export preserves it, so tidying up is worth the minute.

2.2 Your first workflow: manual trigger, run, inspect

The classic first build is a Manual Trigger into an Edit Fields (Set) node into a Code node. It exercises the three things you will do forever: shape data, run, and read the output panel.

Build it

Create a new workflow, add a Manual Trigger, then an Edit Fields (Set) node, then a Code node. Connect them left to right. In the Edit Fields node, switch to JSON output mode and define a small object; keeping a single item there makes the next step easy to read.

// Edit Fields (Set) node - JSON mode
{
  "customer": "Ada Lovelace",
  "plan": "pro",
  "seats": 12,
  "renewal": "2026-11-01"
}

Then in the Code node, run once for all items and emit one summary item per input item. Notice that the expression syntax and the Code node share the same $ helpers, but the Code node needs an explicit return.

// Code node - "Run Once for All Items"
const out = [];

for (const item of $input.all()) {
  const { customer, plan, seats, renewal } = item.json;
  out.push({
    json: {
      customer,
      plan,
      seats,
      monthlyValue: plan === 'pro' ? seats * 20 : 0,
      daysToRenewal: Math.round(
        (new Date(renewal) - new Date()) / 86_400_000
      )
    }
  });
}

return out;

Run it and read the panel

Click Execute Workflow. n8n runs the whole chain and fills the OUTPUT pane of every node. Click each node in turn and read its output as a table; switch to JSON to see the exact shape. This is the entire debugging loop. When something is wrong, the question is almost always "which node produced the wrong shape", and the answer is visible without adding a single log statement.

Two details in the panel are easy to miss. The Schema view collapses items down to their field names and types, which is how you spot an unexpected array or a number arriving as a string. And the little table/JSON/schema toggle persists per node, so once you have set a node to JSON view it stays that way.

Where the first item comes from

A Manual Trigger emits a single empty item, [{ json: {} }]. That is why the first node in a chain usually needs to create data rather than transform it. When you later swap the Manual Trigger for a real trigger, the shape changes: a Webhook Trigger emits { body, headers, query, params } and a Schedule Trigger emits its own small payload. Writing the workflow so each node depends only on its immediate input is what makes that swap painless.

Label nodes as you go — n8n uses the node name in expressions ($('Normalise')), in the execution log and in error messages. "Code2" tells you nothing at 3am.

2.3 Pinning and mocking data

Pinning saves a node's output and replays it on every later run, so you can develop a downstream branch without re-calling the upstream system. Mocking is the related idea of manufacturing test data in the first place.

Why pinners earn their place

Consider a workflow that starts from a Stripe webhook. Testing the last three nodes of it means triggering a real payment, or replaying a real request, every single time — and webhook alerts have rate limits precisely because people do this. Pin the first node's output once and every subsequent run starts from that frozen snapshot. The upstream nodes do not execute at all while their data is pinned; n8n shows a "This data is pinned" banner over the output.

# shell - the same idea from the CLI, for a load test without live calls
# pin by exporting, editing and re-importing is clumsy; use the UI.
# The UI path is: run node -> OUTPUT -> JSON view -> Edit -> Save (pins)

Mocking with Edit Fields or Code

Three ways to manufacture data, in increasing power:

  • Edit Fields (Set) — good for one or two static items with a couple of fields. Fast, readable, no code.
  • Code — good for realistic volume and edge cases. Generate a hundred items, one of which has a null email and one a five-figure seat count, and you have a test suite.
  • Customer Datastore — a built-in node that emits a small fake dataset, useful for exploring nodes when you have no real use case yet.
// Code node - a deterministic mock with deliberately awkward edge cases
const rows = [
  { email: 'ada@example.com', seats: 12, plan: 'pro' },
  { email: null, seats: 1, plan: 'free' },              // missing field
  { email: 'grace@example.com', seats: 0, plan: 'pro' } // zero seats
];

return rows.map(r => ({ json: r }));

The rules and limits

Pinning is a development feature: it does not apply to production executions, and n8n ignores pinned data once a workflow runs from a trigger. You can only pin a node with a single main output, and you cannot pin a node whose output contains binary data. Pinned data is editable directly in the JSON view, which is how you force an edge case without touching the generator code.

There is one more trick worth knowing: you can open a previous execution from the Executions list, copy a node's JSON out of it, and paste that into the pinned data of a node in the current workflow. That is how you reproduce a production bug locally without a production credential.

Unpin when you are done. A workflow published with pinned data still runs the real upstream in production, but a developer who forgets and tests with a stale pin will chase a bug that was fixed in the pin's source an hour ago.

2.4 Saving, versions and publishing

n8n 2.0 replaced the Activate/Deactivate toggle with explicit publishing. Edits autosave as drafts; production runs the last published version, not your working copy.

Autosave and drafts

There is no Save button. Changes persist within a second or two of you making them. What you are working on is a draft: it holds everything you have changed since the last publish, and nothing in it affects production. This is the single biggest behavioural difference from n8n 1.x, where editing a live workflow edited it live.

The Publish button has eight states

Reading the button tells you the state of the workflow without opening anything.

Button stateMeaning
DisabledNo publishable changes; nothing to do
ActiveChanges exist and the workflow is not yet published
Up to datePublished, and the draft matches it
Has changesPublished, but newer edits are not live yet
Invalid changesPublished, but no trigger needs re-registering, so there is nothing to push
ErrorDraft has errors that must be fixed before republishing
PublishingTrigger changes are being applied in the background
Partial / FailedOne or all triggers failed to register; hover for which, then publish again to retry

Publishing is asynchronous and surgical. n8n diffs the triggers between the last published version and the new one and re-registers only the ones that changed, which is why publishing a workflow with a dozen triggers does not cause a blip on all of them.

Version history and naming

Every autosave creates a version. The history icon in the header opens the version list, where you can restore any version, publish an older one, or unpublish entirely. Restoring works on a copy — production keeps running the published version until you publish again, which is the safety property that makes experimentation cheap.

Named versions (Business/Enterprise on self-hosted, Pro/Enterprise on Cloud) attach a label and description to a version and exempt it from automatic pruning, so "the release that fixed the March incident" is still findable a year later.

# shell - the same operations from the CLI, useful in CI
n8n publish:workflow --id=1041 --versionId=<uuid>   # publish a specific version
n8n unpublish:workflow --id=1041
# the old "update:workflow --all" was removed in 2.0 to prevent accidental mass publishes

Collaboration and edit locks

Only one person edits a workflow at a time. If somebody else has it open you get read-only mode; the lock releases when they stop editing or go idle, and you can then take over with their latest changes. This is a locking model, not real-time collaboration — two people cannot co-edit a canvas. Plan merges accordingly, or use source control and environments on a paid self-hosted edition, where workflows live in Git and move between instances through a review process.

If workflow reviews are enabled on your instance, the Publish button can be replaced by a review request. Publishing stays blocked until the review is approved, which is the intended pattern for regulated environments.

3.1 The trigger family

A trigger is the node that starts an execution. Everything else in the workflow is the response. Choosing the wrong trigger is the most common cause of a workflow that "works" but is slow, expensive, or occasionally misses events.

Six kinds of trigger, and when each is right

TriggerEvent sourceBest for
Manual TriggerYou click ExecuteDevelopment; building scratchpads
Schedule Triggern8n's own clockPeriodic jobs, digests, reconciliation sweeps
Webhook TriggerAn inbound HTTP requestPush events from systems with no n8n node; building endpoints
App trigger nodesUsually a webhook underneath (e.g. GitHub Trigger, Stripe Trigger)The normal way to react to a third-party app
Polling nodesn8n calls the app on a schedule and checks for new dataApps that have no webhook support at all
Chat Trigger (AI)A message in the built-in or embedded chatConversational agents (chapter 9)

Triggers only exist once published

This is the rule that surprises newcomers most. Saving a workflow with a Schedule Trigger does not start a timer; the timer starts when the workflow is published. Likewise a Webhook Trigger has two URLs: a test URL that exists only while you are listening in the editor, and a production URL that exists only while the workflow is published. If a third party says "your webhook returns 404", the first question is whether the workflow is published.

Publishing is also where trigger registration is scoped. n8n works out which triggers changed since the last published version and re-registers only those, so editing a mid-workflow node and publishing does not disturb a live IMAP connection or re-register a webhook that was already correct.

One trigger per execution, but several per workflow

A workflow may have multiple triggers; each one can start the execution independently, and the same downstream nodes serve them all. That is useful — a workflow that syncs a product catalogue might accept both a nightly schedule and an on-demand webhook — but it pushes a design constraint onto the rest of the graph: any node that runs early must tolerate input shaped like either trigger's output, or you must branch on $execution information.

A cleaner pattern for genuinely different entry points is a thin per-trigger workflow that immediately calls a shared sub-workflow. The Execute Sub-workflow node takes an explicit input, so the shared logic sees one predictable shape.

Execution order matters

n8n's default executionOrder is v1: branches are executed in the order nodes were added, and a node runs as soon as all of its active inputs have data. Legacy v0 workflows made by very old versions behave differently — they execute branch by branch in a way that can surprise you when a Merge node is involved. This is a workflow setting, not a global one, so a workflow imported from an old template may need it set explicitly. Old v0 workflows will be re-executed awkwardly; converting them to v1 is usually the fix for "the Merge node causes both IF branches to fetch data".

3.2 The Schedule Trigger and cron

The Schedule Trigger is n8n's built-in cron. It supports friendly intervals (every N seconds/minutes/hours/days/weeks/months) and raw six-field cron expressions, and it depends entirely on the instance timezone.

Configuring intervals

Each Trigger Rule selects an interval unit; the remaining fields depend on it. You can add several rules to one node, so "every weekday at 09:00" and "every Sunday at 18:00" can live together without duplicating nodes.

# cron expressions you will actually need (sixth field = seconds, optional)
*/10 * * * * *       every 10 seconds
*/5 * * * *          every 5 minutes
0 * * * *            hourly, on the hour
0 6 * * *            daily at 06:00
0 9 * * 1-5          weekdays at 09:00
0 12 * * 1           Mondays at noon
0 0 */3 * *          midnight every third day
0 0 1 1,4,7,10 *     midnight on the first of Jan, Apr, Jul, Oct

Cron's field order is second, minute, hour, day-of-month, month, day-of-week. n8n treats the seconds field as optional, but including it removes ambiguity when you paste an expression from a generator that emits five fields.

Timezone: the most common scheduling bug

The Schedule Trigger uses the workflow timezone if one is set in workflow settings, otherwise the instance timezone from GENERIC_TIMEZONE. The self-hosted default for that variable is America/New_York, which is nobody's intended default outside the United States — and a "daily 06:00" job that fires at 11:00 is usually this.

The fix is to set the timezone on the workflow itself when the workflow's schedule is part of its contract. That way the workflow behaves identically on Cloud, on your laptop, and on a server in a different region, and a reviewer can see the intent without inspecting the host.

# shell - set the instance default; workflows can still override it
export GENERIC_TIMEZONE=Europe/London

The durable scheduler and missed executions

Since n8n 2.45 the Schedule Trigger uses a durable scheduler by default (gated by N8N_USE_WORKFLOW_PUBLICATION_SERVICE, which is on). Two consequences follow. First, seconds- and minutes-based intervals are measured uniformly from the moment the workflow was published rather than snapped to clock boundaries. Second, missed executions become a real, configurable case: if the instance was down when a job was due, the node's Settings tab lets you choose to discard it, run the most recent missed execution once, or run one catch-up execution per rule.

The grace period (N8N_SCHEDULER_MISFIRE_GRACE, default 60 seconds) decides how late a job may start before it counts as missed. Values below the instance minimum are raised to it, and values above 30 days are capped. Setting N8N_SCHEDULER_ENABLED=false falls back to the old in-memory scheduler, which never runs missed executions at all — acceptable for a job that is idempotent and repeats soon, not for a nightly invoice run.

Cron expressions and variables

Expressions are allowed inside a cron expression, but they are evaluated once, when the workflow is published. Changing a variable afterwards does not change the schedule until you unpublish and republish. This is a genuine trap: the field accepts {{ $vars.send_hour }}, evaluates it at publish time, and gives no hint that the value is frozen.

Never build a Schedule Trigger with a rule that can fire more often than the downstream API allows. A */10 * * * * * rule against a rate-limited API is 8,640 calls a day from one node, and the failure looks like the API being down rather than the schedule being wrong.

3.3 The Webhook Trigger: test and production URLs

The Webhook Trigger turns n8n into a small HTTP server. Two URLs per node — a test URL and a production URL — and a response configuration that decides whether the caller waits for your workflow or gets an immediate acknowledgement.

Test URL versus production URL

The test URL registers while you click "Listen for test event" or run the workflow in the editor, and it displays the incoming request in your canvas. The production URL registers when the workflow is published, and it does not show anything in the editor — you read production runs from the Executions tab.

Getting this wrong is a classic half-hour. Third-party services must be pointed at the production URL, and the workflow must be published. There is also a third route worth knowing: manual executions use /webhook-test/*, while production uses /webhook/*. If you put webhook processors behind a load balancer, only /webhook/* and /webhook-waiting/* should go to the processor pool; /webhook-test/* must reach the main process.

Path, method and route parameters

The Path field accepts route parameters, which makes the Webhook node usable as a small API.

# shell - path patterns supported by the Webhook node
/invoice                      a fixed path
/:tenant                      one variable
/api/:tenant/invoice          a variable in the middle
/:tenant/orders/:orderId      two variables
# the values arrive as {{ $json.params.tenant }} and {{ $json.params.orderId }}

# methods: DELETE GET HEAD PATCH POST PUT

Every incoming request is shaped as { body, headers, params, query }, so a JSON POST is $json.body.someField and a query string filter is $json.query.status. This shape is the same in every expression editor, and it is what makes the node easy to reason about after a request has already arrived.

How to respond

Four modes, and the choice has real consequences for the caller:

  • Immediately — n8n returns 200 with the body "Workflow got started" and runs the workflow afterwards. Best for slow jobs and for third parties that time out after a few seconds. You can set a custom response code and body.
  • When Last Node Finishes — the caller waits and receives the last node's output. Best for genuinely synchronous requests, but the caller inherits your worst-case latency.
  • Using 'Respond to Webhook' node — full control of status, headers and body, which lets you branch and return different codes for different outcomes. This is the only mode that can return, say, a 202 on one path and a 422 on another.
  • Streaming response — for nodes that support streaming (the AI Agent being the main one); the client receives the response as it is generated.
# shell - invoking a production webhook and reading the status
curl -i -X POST https://n8n.example.com/webhook/invoice \
  -H "Content-Type: application/json" \
  -d '{"customer":"ada","amount":1041}'

Securing the endpoint

A published webhook is a public URL. Five independent layers are worth knowing:

  • Authentication — Basic, Header, or JWT auth, configured as a Webhook credential and required on every call.
  • IP allowlist — a comma-separated list of allowed source addresses; anything else gets 403. Good for a known vendor's egress range, useless for a SaaS that rotates addresses.
  • Only Run If — an expression evaluated against the request; if it is false, n8n answers 200 without creating an execution. Essential for filtering a noisy shared endpoint. It runs after the IP allowlist and authentication checks.
  • Ignore Bots — drops link-preview crawlers and similar nuisance traffic.
  • Payload limit — 16 MB by default, raised with N8N_PAYLOAD_SIZE_MAX on self-hosted instances.
// "Only Run If" - drop unrelated campaign traffic before it costs an execution
{{ $json.body.campaign_id === 'user-research-invite' }}

Since n8n 1.103, an HTML response from a webhook is wrapped in a sandboxed <iframe>. JavaScript inside it cannot reach the parent window or local storage, relative URLs such as <form action="/"> do not work, and basic-auth headers are not available inside the frame. Use absolute URLs and embed a short-lived token if you are serving a small HTML tool this way.

3.4 Polling triggers versus webhooks

An app trigger may be a webhook underneath, or it may be a poller that n8n runs on a schedule. The difference changes latency, cost and whether you can ever miss an event.

How a poller works

A polling trigger has an internal schedule (usually every minute, sometimes configurable) and n8n runs the workflow only when the poll finds new data since the last check. n8n remembers the last-seen cursor internally — you do not maintain it — and the crucial benefit is that an empty poll creates no execution and therefore costs nothing against a quota. The cost is latency: up to the polling interval, plus whatever the vendor's API takes.

Webhook triggerPolling trigger
LatencySecondsOne polling interval, typically a minute
Execution countOne per inbound requestOne per poll that finds new data
Missed eventsPossible if the workflow is unpublished or errorsNone while n8n is running and the cursor is intact
Requires public URLYes (or a tunnel)No
Rate-limit pressureLowConstant, and proportional to the interval

Choosing

Prefer the webhook when it exists, because it is faster and cheaper. Prefer polling when: the vendor has no webhook, your instance has no public address and you cannot add a tunnel, the event volume is low enough that one call a minute is cheaper than the engineering for a webhook endpoint, or you genuinely want catch-up semantics after downtime. For an internal instance with no ingress, a polling trigger is often the pragmatic answer even when the vendor documents a webhook.

Reaching a local instance from the internet

Webhook triggers need an address that the outside world can reach. On a development machine, that means a tunnel. n8n's built-in --tunnel option was removed in 2.0, so use Cloudflare Tunnel, ngrok or localtunnel instead, and set WEBHOOK_URL to the tunnel's public URL.

# shell - a Cloudflare quick tunnel against a local n8n
cloudflared tunnel --url http://localhost:5678
# it prints something like https://random-words.trycloudflare.com
export WEBHOOK_URL=https://random-words.trycloudflare.com/
export N8N_PROXY_HOPS=1

N8N_PROXY_HOPS=1 matters: without it n8n sees the tunnel's address as the client IP, so IP allowlists and rate-limit reasoning both break. The same variable is required behind any reverse proxy, and should be set to the number of proxies actually in the chain.

Backfilling after downtime

A poller that finds a gap will happily hand you a large batch, which can be worse than the original outage: a hundred new invoices arriving at once will hit the downstream API a hundred times. The Loop Over Items node with a batch size and a Wait node between batches is the standard mitigation, and the Wait node's resume path is stored durably so a restart does not lose the batch.

// Code node - cap the damage per execution by taking a slice
const batch = $input.all().slice(0, 25);
if ($input.all().length > 25) {
  // log the overflow so you can see it in the Executions list
  console.warn(`truncated ${$input.all().length - 25} items this run`);
}
return batch;

3.5 Trigger settings, states and failure modes

Triggers share the node Settings tab with everything else, but a few of those settings only make sense on a trigger — and a trigger failure is reported differently from a node failure.

Settings that change trigger behaviour

  • Always Output Data — emit an empty item when the node produces nothing, so downstream nodes still run. Useful on a trigger that sometimes has nothing to hand over.
  • Execute Once — for triggers that can fire with multiple items, only the first is processed. Frequently the right choice for a webhook that batches events.
  • Retry On Fail — max tries and wait between tries. On a trigger this mostly helps a poller whose HTTP call occasionally times out.
  • On Error — stop the workflow, continue with the regular output, or continue through the error output. On a trigger, "continue" means the execution proceeds with partial or empty input, which is rarely what you want; usually you want the error workflow to hear about it.

Trigger failures look different

When a mid-workflow node fails, the Error Trigger receives execution.id, execution.url, the failing node's name and a stack trace. When the trigger itself fails — an invalid credential, an unreachable IMAP server, a webhook route that could not be registered — no execution exists yet, so the payload is different: there is a trigger object with a WorkflowActivationError and no execution id or URL.

// what an error workflow receives when the TRIGGER failed
{
  "trigger": {
    "error": {
      "name": "WorkflowActivationError",
      "message": "getaddrinfo ENOTFOUND imap.example.com",
      "timestamp": 1760000000000,
      "context": {}
    },
    "mode": "trigger"
  },
  "workflow": { "id": "41", "name": "Invoice inbox" }
}

An error workflow that assumes $json.execution.id is always present will throw when it is called for a trigger failure — the one case where you most need the alert. Handle both shapes.

Trigger behaviour under load

Triggers have a subtle concurrency property: n8n does not start a second execution of a workflow while the first is still running, for the same workflow. If a webhook fires while the previous execution is still in flight, the request waits. This is usually correct, but it means a slow workflow becomes a queue, and in queue mode it is the main process that accepts the request while a worker executes. A workflow that takes 30 seconds and receives 20 requests a minute will grow a backlog you can see in Redis, not in n8n.

If a webhook's caller requires a fast acknowledgement and the work is slow, use Respond Immediately and let the workflow finish in the background. The client gets its 200 in milliseconds and your slow path stops being the client's problem.

4.1 The item model in practice

Every node reads an array of items and writes an array of items. Internalising "how many items go in, how many come out" predicts almost all n8n behaviour, including why some nodes appear to loop and others do not.

Input count versus output count

NodeItems inItems out
Edit Fields (Set)NN (one output per input)
IFNSplit across two outputs, N total
FilterNM, where M ≤ N, on one output
HTTP RequestNN by default (one call per item), or 1 if "Execute Once"
Aggregate / SummarizeN1
Split OutNMany — one per element of the chosen array field
Merge (Append)N + M across two inputsN + M
Code (all items)NWhatever you return

The table is the reason "n8n loops automatically" is only half true. Most nodes are implicitly per-item. A handful — the Code node in all-items mode, Execute Sub-workflow in all-items mode, several database insert operations, HTTP Request with "Execute Once", RSS Read — run once regardless of how many items arrive. When a workflow does not do what you expect, checking whether a node is one of those exceptions explains it about a third of the time.

JSON items and binary items

An item can carry both a json object and one or more binary properties. Binary data is not stored inline in the item — it is a reference to a payload in the binary data store (filesystem, database or S3, depending on N8N_DEFAULT_BINARY_DATA_MODE), with a fileName, mimeType and fileExtension alongside it.

// Code node - inspect what a webhook-received PDF looks like
const item = $input.first();
return [{
  json: {
    fileName: item.binary.data.fileName,
    mimeType: item.binary.data.mimeType,
    bytesHint: String(item.binary.data.data).length * 3 / 4
  }
}];

Binary items are the reason n8n 2.0 removed the in-memory binary mode. Keeping payloads in RAM worked until a workflow moved a few large files at once; the default is now filesystem (regular mode) or database (queue mode), and S3 is available for anything that needs to survive a container replacement.

Order, identity and pairing

Items have an implicit position and an explicit link back to the items that produced them. That link is item linking, and it is what allows $('Fetch customer').item to return the right customer for the current row rather than the first one. Order is preserved through nodes that map one-to-one and lost through anything that reorders, aggregates or joins — after a Sort, Aggregate or Merge, "the third item" means something different, and pairing may be ambiguous.

// Code node - the correct way to look back at the item that produced this one
const customer = $('Fetch customer').itemMatching($itemIndex);
return [{ json: { id: customer.json.id, ok: true } }];

Empty input and empty output

An empty array is a legitimate value, and the difference between "no items" and "one empty item" causes a lot of broken workflows. If a node receives zero items it does not execute at all; its downstream nodes receive nothing either, and the execution ends quietly. Always Output Data forces a single empty item so the chain continues. Conversely, a node that filters everything out produces zero items and behaves the same way.

// Code node - a defensive pattern: always emit exactly one summary item
const items = $input.all();
if (items.length === 0) {
  return [{ json: { processed: 0, note: 'nothing to do' } }];
}
return [{ json: { processed: items.length } }];

4.2 Edit Fields and the transformation nodes

Before reaching for code, know the built-in transformation nodes. Edit Fields (Set), Aggregate, Split Out, Sort, Limit, Remove Duplicates and Summarize cover most reshaping without a line of JavaScript.

Edit Fields (Set): rename, add, remove

Formerly called "Set", this node is the workhorse. It has three modes — Manual Mapping, JSON, and the older per-field modes — and a Keep Only Set Fields toggle that decides whether it replaces the item or merges into it. Turning that toggle on by accident is a common cause of "where did my other fields go".

// Edit Fields (Set), JSON mode - add computed fields, keep the input fields
{
  "customer": "{{ $json.customer }}",
  "plan": "{{ $json.plan }}",
  "flag": "{{ $json.seats >= 10 ? 'large' : 'small' }}",
  "renewalYear": "{{ $now.toFormat('yyyy') }}"
}

The expression preview underneath each field shows the computed value immediately, which makes Edit Fields the fastest place to iterate on an expression. Prefer it to a Code node for anything a human will need to read later: a field's intent is visible in the node, whereas in code it is buried in a script.

The other reshaping nodes

NodeUse when
AggregateYou want N items collapsed into one item, with chosen fields gathered into arrays (for example, all order ids on one customer)
Split OutOne item contains an array field and you want one item per element — the opposite of Aggregate
SummarizePivot-table semantics: group by a field and count, sum or collect other fields
SortOrder by one or more fields, or take a random sample
LimitKeep at most N items, truncating the rest
Remove DuplicatesDeduplicate across all fields, or a chosen subset

They are not merely conveniences: each is faster than an equivalent Code node, and each keeps the schema visible in the editor. A pipeline of Aggregate → Sort → Limit is instantly legible in a way that a single 40-line script is not.

Worked example: daily revenue by plan

// Input: one item per order
// { "plan": "pro", "amount": 20 }
// { "plan": "free", "amount": 0 }
// { "plan": "pro", "amount": 40 }

// 1. Filter -> 2. Summarize (Group By: plan, Sum: amount)
// Output:
// { "plan": "pro",  "sum_amount": 60 }
// { "plan": "free", "sum_amount": 0 }

The same result in a Code node is five lines and one bug waiting to happen — a missing default for a plan that never appears. The Summarize node only emits groups it saw, which is the behaviour most people want when they then write the rows to a sheet.

Optional fields and type coercion

n8n is permissive to a fault: a field that arrives as the string "12" and a field that arrives as the number 12 both render the same in the table view. Arithmetic in an expression coerces, so {{ $json.seats * 20 }} works either way, but string concatenation does not, and comparisons are the classic trap: "10" > "9" is false as strings and true as numbers.

// coerced, explicit, and safe in both cases
{{ Number($json.seats) >= 10 }}
{{ ($json.seats ?? 0) * 20 }}
{{ String($json.id).padStart(6, '0') }}
Turn on Always Output Data on the last node of a branch that can legitimately produce nothing. It turns a silent, invisible no-op into an item you can see in the output panel.

4.3 Branching with IF, Switch and Filter

Conditions in n8n are nodes with multiple outputs, not expressions inside nodes. IF has two, Switch has several, Filter has one. That shape is why branching is inspectable and why you can see which path each item took.

IF: the boolean case

The IF node compares two values with an operator — equals, not equals, greater than, contains, matches regex, is empty, and the rest — and evaluates either against all items at once or per item, depending on the Combinator setting. A false result is not an error; it routes items to output 1 instead of output 0, and if nothing is wired there the items are simply discarded.

// IF node condition examples (typed into the Value fields)
{{ $json.seats }}   is greater than or equal to   10
{{ $json.email }}   is not empty
{{ $json.plan }}    matches regex   ^(pro|enterprise)$

// and the combinator when you add a second condition:
// AND - every condition must pass
// OR  - any condition passing is enough

Switch: more than two ways

Switch has three modes. Rules lets you define several conditions, each with its own output, plus a fallback output. Value Match compares one expression against a list of literal values, which is how you route on a status string. Expression evaluates an expression that returns the output index or name directly, which is the mode for routing on something computed.

// Switch, Expression mode - route on the index this returns
{{ ['pro', 'enterprise', 'free'].indexOf($json.plan) }}
// 0 -> output 0 (pro), 1 -> output 1 (enterprise), -1 -> fallback

Notice what the Expression mode buys: arbitrary logic, no chain of near-duplicate rules, and an explicit fallback. The cost is legibility — a reviewer has to reason about the array. Rules mode is usually better for anything a colleague will maintain.

Filter versus IF

Filter is IF with the false branch deleted. It keeps matching items and discards the rest, which makes it the right choice when you do not want to handle the negation. Using IF and leaving output 1 unconnected says the same thing, but it leaves a dead end on the canvas that a future reader will wonder about. Prefer Filter when there is no second path.

// Filter node - keep only paid, non-refunded orders
{{ $json.status === 'paid' && $json.refunded !== true }}

Where "branching" breaks down

Two limitations catch people out. First, once items go down separate branches, they do not merge automatically — you need a Merge node, and Merge waits for all its inputs. If one branch only runs conditionally, the waiting Merge never fires and the workflow stalls. Second, n8n does not offer a first-class "switch on the number of items" primitive; "none of the items matched" is something you detect by checking whether a branch produced anything, which is easiest with Always Output Data on the producer and a check downstream.

// Code node - a "did anything come through this branch?" sentinel
const items = $input.all();
return [{
  json: {
    matched: items.length > 0,
    count: items.length,
    first: items[0]?.json ?? null
  }
}];
Never wire an IF node's two outputs into a single Merge node without a way for the Merge to complete. The workflow will hang until the execution timeout, and the execution log will show the Merge node as the last thing that ran.

4.4 Merging data streams

The Merge node is where n8n stops looking like a pipeline and starts looking like a query planner. Its Mode determines whether it concatenates, joins, pairs by position, or picks a branch.

The four modes

ModeBehaviourSQL analogue
AppendOutput the items of every input, one input after anotherUNION ALL
Combine → Matching FieldsCompare fields and join on equality; output type decides which rows surviveINNER / LEFT / RIGHT / OUTER join
Combine → PositionPair item 0 with item 0, item 1 with item 1Zip / ROW_NUMBER() join
Combine → All Possible CombinationsCartesian product, fields with the same name mergedCROSS JOIN
Choose BranchWait for both inputs, output one of them unchangedBarrier + SELECT
SQL QueryWrite the join yourself in AlaSQL over input1, input2, …Full SQL

Matching Fields supports five output types — Keep Matches, Keep Non-Matches, Keep Everything, Enrich Input 1, Enrich Input 2 — mirroring the four join flavours plus the "only the difference" case you want when reconciling two systems.

Clashes and nesting

When both sides have a field with the same name, that is a clash. The default is to let Input 2 win, which is wrong as often as it is right. The Options panel fixes it: choose which input to prioritise, or append the input number to the field name so nothing is lost. For nested objects you also choose between a deep merge (recursive) and a shallow merge (top level only) — a shallow merge on two objects that both contain a meta key silently discards one side's meta.

// Merge, Mode: Combine, Combine By: Matching Fields
//   Input 1 Field: customer_id     (from the CRM)
//   Input 2 Field: id              (from the billing system)
//   Output Type:   Enrich Input 1  (left join: every CRM record, plus billing where present)
//   Options:       Fuzzy Compare   (so "3" and 3 match)
//                  Multiple Matches: Include All Matches

Uneven inputs and the classic hang

Merge only emits as many items as the shorter side permits when pairing by position; the remainder of the longer side is dropped unless you enable Include Any Unpaired Items. In Matching Fields mode, unpaired items are controlled by the output type. And because Merge waits for all of its inputs, a branch that produces nothing leaves the node waiting — the single most common cause of a workflow that appears to do nothing at all.

The fix is almost always one of two things: put a filter or an IF so that exactly one branch always reaches Merge, or replace Merge with Choose Branch, which is designed for "wait for both, then keep one".

// Code node - manual merge when the item counts differ wildly
const left  = $('CRM').all().map(i => i.json);
const right = $('Billing').all().map(i => i.json);
const byId  = new Map(right.map(r => [String(r.id), r]));

return left.map(l => ({
  json: { ...l, billing: byId.get(String(l.customer_id)) ?? null }
}));
Need merge-from-many-executions rather than many-inputs? That is a Code node job, not a Merge node job. A Loop Over Items that runs a node several times accumulates several runs of data, and only code (or the Aggregate node) can stitch them into one dataset.

4.5 The Code node: JavaScript and native Python

The Code node is the escape hatch. In n8n 2.x it runs in a task runner by default, supports JavaScript with the full $ helper set, and supports native Python with a deliberately reduced API.

Two run modes

Run Once for All Items (the default) executes your code once with the whole input available, which is what you want for aggregating, grouping or reordering. Run Once for Each Item executes per item with $json available as the current item's JSON, which is what you want for a per-row transformation where you may want n8n to keep the pairing between input and output.

// Run Once for Each Item - $json is this item, return one item
return { json: { ...$json, checkedAt: $now.toISO() } };

What the sandbox does and does not allow

Code node execution is isolated from the filesystem and the network. There is no fs, and there is no HTTP client — you use the Read/Write File From Disk node and the HTTP Request node for those. On Cloud, only crypto and moment are importable. On self-hosted, you can allowlist external npm modules, but every module you allow is a dependency with the same access as n8n itself.

In 2.0 the sandbox tightened further. Task runners are on by default, and secure mode disables evaluating strings as code, which means $evaluateExpression() no longer works inside a Code node — it was the mechanism for running an expression string at runtime. If you find one in an old workflow, replace it with real JavaScript, or evaluate the expression in an Edit Fields node and read the result. N8N_RUNNERS_INSECURE_MODE=true restores the old behaviour and should be treated as a temporary workaround, not a configuration.

The helper set you actually use

$input.first() / .last()A single item

// Code node - group by a key, the thing Code does best
const rows = $input.all().map(i => i.json);
const groups = new Map();

for (const r of rows) {
  const key = r.plan ?? 'unknown';
  const g = groups.get(key) ?? { plan: key, count: 0, total: 0 };
  g.count += 1;
  g.total += Number(r.amount ?? 0);
  groups.set(key, g);
}

return [...groups.values()].map(json => ({ json }));

Native Python

Python in the Code node no longer runs under Pyodide — that implementation was removed in 2.0 because it was slow and had a different API from real CPython. Native Python now runs on task runners, which means it requires the external runner mode and (for extra libraries) a runner image that contains them. Two API differences will bite anyone porting old code: only _items (all-items mode) and _item (per-item mode) are available, and access is bracket-only — item["json"]["field"], not item.json.field.

# Code node, Python, Run Once for All Items
import json
out = []
for item in _items:
    row = item["json"]
    out.append({
        "json": {
            "email": row.get("email"),
            "domain": (row.get("email") or "").split("@")[-1],
        }
    })
return out
Reach for a Code node last. Every node you skip is one a colleague can still read in six months, and the built-in nodes get fixes you do not have to make. Code is for reshaping, grouping and algorithms — not for making a single HTTP call or setting one field.

5.1 How expressions work

An expression is JavaScript wrapped in double braces, evaluated when a node runs, and written into the parameter it sits in. Where a parameter accepts an expression, the field offers both a fixed value and an expression editor.

The syntax and the evaluation moment

Anything inside {{ }} is evaluated, once per item by default. Anything outside is literal text. That means Order {{ $json.id }} for {{ $json.customer }} is a valid string with two substitutions in it — the braces are not an all-or-nothing switch.

Invoice {{ $json.id }} for {{ $json.customer }} is {{ $json.amount }} USD
// with $json = { id: 1041, customer: "Ada", amount: 120 }
// -> "Invoice 1041 for Ada is 120 USD"

Expressions are evaluated in a sandbox with the same helpers as the Code node but with a different scope: there is no require, no filesystem and no network. They are evaluated in n8n's expression engine, not by the task runner, so $evaluateExpression() still works in a normal parameter — unlike in the Code node.

Where expressions are and are not allowed

Most fields accept them, but not all. Numeric fields with a fixed set of choices, some dropdowns, and structural settings generally do not. When a field refuses an expression you get either a validation error or, worse, the literal string {{ $json.x }} passed through to the API. If an API complains that it received a value starting with {{, that is what happened.

Credentials never accept expressions. That is deliberate — credentials are resolved by the credential system, not by the item pipeline, and a credential built from workflow data would be a privilege-escalation route.

What happens when an expression throws

An expression that throws fails the node, and therefore the workflow, with an error naming the node and the field. The two most common causes are a missing path (reading $json.customer.name when customer is null) and a type error (calling a string method on a number). Both are avoidable with optional chaining and a default.

// brittle
{{ $json.customer.name.toUpperCase() }}

// safe: optional chaining plus a fallback
{{ $json.customer?.name?.toUpperCase() ?? 'UNKNOWN CUSTOMER' }}

Expressions or a node?

ApproachUse when
ExpressionSetting one parameter from existing data; light formatting; you want the live preview
Edit Fields (Set)Several derived fields at once, read by a human later
Data transformation nodeA standard operation: aggregate, split, sort, dedupe, pivot
Code nodeGenuine algorithms, restructures, many items at once, console.log

The rule of thumb: expressions keep logic next to the parameter it configures, which is the best place for something you will need to change at 2am. Move to a Code node when the logic stops fitting on one line.

5.2 Referencing current and previous nodes

Five helpers cover nearly every reference you will write: $json, $binary, $input, $('Node name'), and $items().

The current item

{{ $json.email }}                  // current item's json field
{{ $binary.data.fileName }}        // current item's binary property "data"
{{ $input.item.json.email }}       // the same thing, spelled out
{{ $items().length }}              // how many items are on this node's input

$json is a shorthand, and it only works when there is a "current item". In an expression that is evaluated once per node rather than once per item — a node-level setting, for instance — $json can be ambiguous, and $input.first().json is the explicit form.

Earlier nodes: $('Node name')

The modern syntax is $('Node name'), which returns a node proxy with .item, .first(), .last(), .all() and .params. The older $node['Node name'] form still works in many places but the docs moved to $(), and code should too.

{{ $('Fetch customer').item.json.email }}     // the LINKED item - usually what you want
{{ $('Fetch customer').first().json.email }}  // always the first item - often a bug
{{ $('Fetch customer').all().length }}        // items available at that node
{{ $('HTTP Request').item.binary.data.fileName }}

The difference between .item and .first() is the difference between pairing and position. With ten customers flowing through, .item gives each row its own customer; .first() gives every row customer number one. This is the most expensive typo in n8n, because it produces plausible-looking output that is silently wrong.

Node parameters and outputs by branch

$('Node').params exposes the configuration that node ran with — useful for logging or for conditional logic that depends on how a previous node was configured. $('Node').all(branchIndex, runIndex) reads a specific output branch or a specific run when a node executed more than once (inside a loop).

{{ $('IF plan is pro').all(1).length }}   // how many items went down the FALSE branch
{{ $('HTTP Request').all(0, 2).length }}  // items from run index 2 of that node

Reading data that has not run yet

Referencing a node that has not executed in the current execution returns nothing rather than erroring, which produces an empty string in a parameter and a confusing API error downstream. The output panel is the check: if the node you are referencing has no output in the current run, the reference will not resolve. This is a strong argument for building workflows left to right and running as you go rather than wiring the whole graph and debugging it at the end.

// defensive reference - fail loudly instead of sending an empty value
{{ ($('Fetch customer').item?.json?.email) ?? (() => { throw new Error('no customer email'); })() }}

5.3 Item linking and paired items

Item linking is the mechanism that keeps $('Node').item honest: each item records which item in the previous node produced it, so a reference can follow the data rather than guess by position.

Why it exists

Without linking, the only way to answer "which customer does this order line belong to?" would be positional — and that breaks the moment anything filters, sorts or joins. n8n instead attaches a hidden pairedItem reference to every item as it passes through a node that maps items one-to-one. $('Node').item then walks that chain back to the right source item.

// the pairing n8n maintains (simplified)
{ "json": { "sku": "A-1" },
  "pairedItem": { "item": 3 } }   // this item came from input index 3

When linking breaks

Linking survives one-to-one nodes and dies at anything that changes cardinality: Aggregate (N to 1), Split Out (1 to N), Code that returns a different number of items than it received, and Merge in most modes. After such a node, $('Node').item may return undefined or the wrong item, and n8n raises an item-linking error rather than silently guessing — in the Code node, the fix is itemMatching() instead of item.

// Code node - restore the link by hand when you emit a different number of items
const inputItems = $input.all();

const out = [];
for (let idx = 0; idx < inputItems.length; idx++) {
  out.push({
    json: { ...inputItems[idx].json, emittedFrom: idx },
    pairedItem: { item: idx }        // re-attach the link explicitly
  });
}
return out;

What to do about it in practice

Three habits keep you out of trouble. Prefer a Merge node to a Code node whenever you want a join, because Merge maintains pairing. When a Code node must change cardinality, either attach pairedItem yourself or read the earlier node's data by an explicit key rather than by pairing. And when in doubt, carry the join key forward as a field — a customer_id copied along the pipeline is immune to every linking subtlety, and it costs nothing.

// carry the key rather than relying on pairing
// in the first Edit Fields: add { "customer_id": "{{ $json.id }}" }
// later, instead of $('Customer').item.json.name:
{{ $('Customer').all().find(c => c.json.id === $json.customer_id)?.json.name ?? null }}

5.4 Built-in variables: time, variables and metadata

Beyond item data, n8n exposes the clock, custom variables, execution metadata, workflow metadata and environment values. Luxon's DateTime is available for real date arithmetic.

Dates and times with $now and Luxon

$now is the current time as a Luxon DateTime in the workflow's timezone; $today is midnight today. DateTime, Duration and Interval are in scope, so arithmetic is a method call rather than manual millisecond maths.

{{ $now.toISO() }}                                   // 2026-10-14T09:15:00.000+01:00
{{ $now.toFormat('yyyy-LL-dd') }}                    // 2026-10-14
{{ $now.toFormat('cccc dd LLL yyyy') }}              // Wednesday 14 Oct 2026
{{ $now.minus({ days: 7 }).toISO() }}                // a week ago
{{ $now.plus({ months: 1 }).startOf('month').toISO() }}
{{ $now.diff($json.createdAt, 'days').days.toFixed(1) }}
{{ $now.setZone('America/New_York').toFormat('HH:mm') }}

One warning that costs real debugging time: the expression engine's Luxon build has n8n-specific extensions, and the Code node uses plain Luxon. DateTime.format() is n8n's own method and does not exist in the Code node — use toFormat() there. Likewise plus(7, 'days') takes two arguments in an expression and a single { days: 7 } object in the Code node; using the wrong form does not throw, it produces nonsense.

Execution and workflow metadata

{{ $execution.id }}          // database id of this execution (empty for some manual runs)
{{ $execution.mode }}        // 'manual', 'trigger', 'webhook', 'integrated'
{{ $execution.resumeUrl }}   // the URL a Wait node resumes on - useful in notification emails
{{ $workflow.id }}           // numeric workflow id
{{ $workflow.name }}         // workflow name, as shown in the header
{{ $runIndex }}              // which run of the current node this is (loops)
{{ $itemIndex }}             // index of the current item

$execution.resumeUrl is the key to human-in-the-loop patterns: a Wait node pauses the workflow and produces a URL; email that URL to an approver and their click resumes the run with whatever data they supply. Because the URL identifies a specific execution, it is a bearer credential — treat it as one.

Custom variables with $vars

Variables are instance-wide or project-scoped key/value pairs, created in the UI, read-only in workflows, and accessed as $vars.name. Keys and values are restricted to letters, digits and underscores, values are strings, and a missing variable is undefined rather than an error. Project-scoped variables shadow global ones with the same key. The feature requires a paid edition (Business/Enterprise self-hosted, Pro/Enterprise Cloud).

{{ $vars.support_inbox }}                       // "help@example.com"
{{ $vars.report_recipients.split(',') }}        // variables are strings, so parse them
{{ $json.channel ?? $vars.default_channel }}

Variables are the right home for values that operators change — an escalation address, a feature flag, a threshold. They are the wrong home for secrets: variables are visible to anyone who can edit a workflow.

Environment values are blocked by default

$env reads process environment variables and is gated by N8N_BLOCK_ENV_ACCESS_IN_NODE, which defaults to true in n8n 2.0. Even when enabled, using $env for secrets is an anti-pattern, because anyone who can open a workflow can read it. Credentials and external secret stores exist for that job.

5.5 Drag-and-drop mapping and the expression editor

You rarely need to type an expression from scratch. The INPUT/OUTPUT panes are a mapping surface: drag a field into a parameter and n8n writes the expression, resolving the correct node and branch automatically.

What dragging actually produces

Dragging a field from the INPUT pane into a parameter inserts an expression such as {{ $json.plan }} if the field is on the current node's own input, or {{ $('Previous node').item.json.plan }} if it is further back. n8n picks the shortest correct reference, which is usually $json and occasionally a previous-node reference — and knowing which one it chose matters, because only one of them is pair-safe in every case.

// dragged from the current input
{{ $json.plan }}

// dragged from two nodes back - n8n writes the full reference
{{ $('Filter paid orders').item.json.customer_id }}

The live preview

Under every expression field, n8n renders the computed result using real data from the last run. This is the fastest correctness check in the product: if the preview shows [empty], the path is wrong; if it shows a plausible but unexpected value, the reference is pointing at the wrong node or item. The preview also tells you the type, which catches silent string/number mistakes.

Editor behaviour worth knowing

  • Typing {{ opens the expression editor; typing $ inside it opens autocomplete for the helpers.
  • The editor does not evaluate on every keystroke — it debounces, so a slow instance pauses briefly before showing the preview.
  • Ctrl/Cmd + Space forces the completion list.
  • When a field holds literal text plus an expression, n8n renders it as a highlighted mixture. If the whole field is highlighted, n8n treats the entire field as the expression — which is how a value that looks fine in the preview arrives at the API as something unexpected.

Building a whole body with one expression

For an HTTP Request body or a webhook response, a single expression returning an object is often cleaner than a dozen field-by-field mappings. Switching the parameter to JSON mode and writing one object literal keeps the shape visible in one place.

{
  "id": "{{ $json.id }}",
  "customer": { "email": "{{ $json.email }}", "tier": "{{ $json.plan }}" },
  "lines": {{ JSON.stringify($json.lines ?? []) }},
  "sentAt": "{{ $now.toISO() }}"
}

Note the third line. Inserting a real array into a JSON parameter needs JSON.stringify, because the value is a string substitution; without it you get [object Object] or a quoted string where an array was expected. This is the single most common mistake when hand-building JSON bodies with expressions.

When a JSON field misbehaves, temporarily wrap the whole thing in a Set node first and inspect its output. Separating "did the expression produce the right value" from "did the HTTP request accept it" halves the search space.

6.1 The HTTP Request node

The HTTP Request node is the universal adapter: anything with a REST API is one node away from being part of a workflow. It does method, URL, query, headers, body, authentication, pagination, batching, timeouts and response shaping.

Anatomy of a request

The node exposes the same pieces a curl command has. Everything that can be written as a field can also be written as JSON, and every field accepts expressions — which is what makes the node usable inside a loop over items.

Method:  POST
URL:     https://api.example.com/v2/invoices
Headers: Authorization: Bearer {{ $credentials.apiKey }}   (or use a credential)
         Content-Type: application/json
Query:   status=paid, page={{ $pageCount }}
Body:    JSON
  {
    "customer": "{{ $json.customer_id }}",
    "amount": {{ Number($json.amount) }},
    "currency": "EUR"
  }

Import a curl command with Import cURL and n8n fills in method, URL, headers and body automatically. One caveat: the importer treats every imported parameter as a string, so a numeric field arrives as "10". Switch that field's mode from Using Fields Below to Using JSON and paste the object if the types matter.

Response handling

By default the node treats only 2xx as success and returns just the body. Two options change that. Never Error makes any status code a success, which you want when a 404 is a legitimate answer, and Include Response Headers and Status returns the full envelope so you can branch on the code or read a rate-limit header.

// with "Include Response Headers and Status" enabled
{
  "body": { "id": "inv_1041", "status": "paid" },
  "headers": { "x-ratelimit-remaining": "42", "content-type": "application/json" },
  "statusCode": 200
}
// so: {{ $json.statusCode }} and {{ $json.headers['x-ratelimit-remaining'] }}

Response Format is worth setting explicitly. Autodetect guesses JSON, text or file by content type, which is right most of the time and wrong for APIs that return JSON as text/plain — a surprisingly common mistake that leaves you with a single item whose only field is a big string. Set JSON when you know, and File when you are downloading something to hand to a later node as binary.

Batching, redirects and timeouts

Because the node runs once per input item by default, a hundred items means a hundred requests. Batching (items per batch, batch interval) controls that politely, and Execute Once in the Settings tab collapses it to one call. Timeout is the initial response-header timeout and is the one to set when the other end is flaky; a request that never returns headers will otherwise hold the execution until the instance-level timeout fires.

# shell - the same request, for comparison
curl -sS -X POST https://api.example.com/v2/invoices \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $API_KEY" \
  --max-time 20 \
  -d '{"customer":"cus_9","amount":120,"currency":"EUR"}'

Three gotchas that waste an afternoon each

  • Array formatting. ?tag=a&tag=b, ?tag[]=a&tag[]=b and ?tag[0]=a&tag[1]=b are all "the same query" and every API picks one. Use Array Format in Query Parameters.
  • Redirects. Followed by default, up to a maximum. If a POST is answered with a 302 to a login page, you get a 200 and an HTML body that then fails to parse as JSON. Turn redirects off while debugging.
  • Lowercased headers. Header names are lowercased by default, which matters for APIs that do case-sensitive signing.
When the HTTP Request node is attached to an AI Agent as a tool, extra options appear to trim the response — selecting a JSON field, including or excluding fields, or stripping HTML — so the model receives less text and you pay for fewer tokens.

6.2 Authentication for API calls

Two paths: a predefined credential type when n8n knows the service, or a generic credential type when it does not. Using the predefined one for a custom endpoint is a real trick, not a workaround.

Predefined versus generic credentials

Predefined Credential Type lets you pick, say, "Slack" and have n8n inject the right authentication for the operation you are calling — including the parts that are not a header, such as an OAuth token that needs refreshing. It is always preferred when available. Generic Credential Type offers the standard mechanisms: Basic, Header, Query, Digest, Custom, Simplified Custom Auth, OAuth1 and OAuth2.

# shell - which generic mechanism maps to what
Basic auth        Authorization: Basic base64(user:pass)
Header auth       X-API-Key: secret            (header name is yours to choose)
Query auth        ?api_key=secret
OAuth2            Authorization: Bearer <short-lived access token>
Custom auth       any header shape, with an expression if needed

For a service that has a predefined type but an endpoint that does not, the trick everyone needs eventually: select the service under Predefined Credential Type, and leave the generic authentication empty. The node still sends the service's authentication, so you can call an undocumented endpoint with a managed OAuth token.

The OAuth2 callback, and why it breaks

OAuth2 credentials require a redirect URL that reaches n8n's callback route. That URL is derived from WEBHOOK_URL (or N8N_EDITOR_BASE_URL), so a wrong public address produces a callback that lands nowhere and an error at the provider that reads like a client-secret problem. In n8n 2.x, OAuth callback endpoints also require authentication by default — the N8N_SKIP_AUTH_ON_OAUTH_CALLBACK default flipped from true to false — so a provider that calls the callback without a session needs that reviewed.

# shell - the public address must match what the provider is told
export WEBHOOK_URL=https://n8n.example.com/
export N8N_EDITOR_BASE_URL=https://n8n.example.com/
export N8N_PROXY_HOPS=1
# then register this exact redirect URL at the provider:
#   https://n8n.example.com/rest/oauth2-credential/callback

Signing and HMAC

Some APIs sign the request rather than send a token — the signature is a hash of the method, path, timestamp and body, keyed with a secret. n8n has no "sign this for me" checkbox for arbitrary schemes, so the pattern is a Code node before the HTTP node, using the crypto module (which is available in the Code node even on Cloud).

// Code node - HMAC-SHA256 signed request for an imaginary API
const crypto = require('crypto');
const secret = '...';                    // prefer a credential, not a literal
const body   = JSON.stringify({ id: $json.id, amount: $json.amount });
const ts     = Date.now().toString();
const sig    = crypto.createHmac('sha256', secret)
                     .update(ts + body)
                     .digest('hex');

return [{ json: {
  body,
  headers: { 'X-Timestamp': ts, 'X-Signature': sig, 'Content-Type': 'application/json' }
} }];

Then the HTTP node sends {{ $json.body }} as a raw body and the headers from {{ $json.headers }}. Signing before sending fixes one class of bug entirely: the signature is computed over exactly the bytes that will be transmitted, so no whitespace difference can invalidate it.

Never paste a signing secret into a Code node. Code nodes are readable by anyone who can open the workflow, and the value is stored in the workflow version history too. Use a credential and an expression, or an external secret store.

6.3 Pagination

Most real APIs return a page at a time. n8n can follow either a "next URL" or a page/offset parameter, and exposes $pageCount, $request and $response while it does so.

The two pagination modes

Response Contains Next URL is the simplest: give the node an expression for the next page's URL, and it loops until the expression yields nothing. Typically the URL is somewhere in the response body, and n8n surfaces a warning if it cannot find one.

// "Next URL" expression for a cursor-style API
{{ $response.body.links?.next ?? '' }}
// when it returns an empty string, pagination stops

Update a Parameter in Each Request is for APIs that take a page number, an offset or a cursor in the query or body. You nominate the parameter and the value n8n should set on each iteration, using $pageCount to know where you are.

// query parameter "page", updated each request, starting at 1
{{ $pageCount + 1 }}

// offset-based, 100 per page
{{ $pageCount * 100 }}

// cursor taken from the previous response body
{{ $response.body.nextCursor }}

Stopping, and not fetching the world

Pagination has no built-in page limit, so an expression that always returns a value will fetch until the API gives up or your memory does. Two safety measures: make the next-value expression return an empty string on some condition, and set a maximum page count on the node (or gate the HTTP node with an IF on $pageCount). A missing termination condition is the way to turn a small sync into an out-of-memory incident.

// terminate after 20 pages even if the API keeps offering more
{{ ($response.body.next && $pageCount < 19) ? $response.body.next : '' }}

The pagination variables

VariableMeaning
$pageCountHow many pages have been fetched so far, starting at 0
$requestThe request object as sent, useful for signature recalculation and debugging
$response.bodyThe last response's parsed body — where the next cursor lives
$response.headersResponse headers, including rate-limit and link headers
$response.statusCodeThe numeric status of the last response

Because the node accumulates output across pages, a paginated HTTP Request node outputs one item per page by default in some configurations and a flattened set in others. Check which you have before writing the next node; the cleanest approach is to let the HTTP node paginate, then add a Code node that flattens the pages into individual records explicitly.

// Code node - flatten pages into one item per record
const records = [];
for (const page of $input.all()) {
  for (const row of page.json.data ?? []) records.push({ json: row });
}
return records;

When pagination is not the right tool

If the API offers a bulk export, a delta sync, or a webhook, use it. Iterating pages is the most expensive way to stay in sync: it scales with the size of the dataset rather than the size of the change. A nightly full pagination sweep is sometimes correct, but a five-minute poll over the same pages is a design smell that shows up as unexplained API bills.

6.4 Building an API endpoint with Webhook and Respond to Webhook

A published Webhook trigger plus a Respond to Webhook node is a functioning HTTP endpoint: routing, status codes, headers, JSON bodies. It is how you expose workflow logic to a front end without deploying anything else.

The shape of the endpoint

The Webhook node's 4th response mode — Using 'Respond to Webhook' node — hands full control of the reply to a node placed later in the graph. That node can set the status code, the content type, response headers, and the body from an expression. Because it is a normal node, it can sit on a branch, which is how one endpoint returns different codes for different outcomes.

// Respond to Webhook - success branch
Respond With: JSON
Response Code: 201
Response Headers: { "Location": "/invoices/{{ $json.id }}" }
Body: { "id": "{{ $json.id }}", "status": "created" }

// Respond to Webhook - validation branch
Respond With: JSON
Response Code: 422
Body: { "error": "customer_id is required", "field": "customer_id" }

Validating the request

A public endpoint receives anything. The first three nodes after a Webhook trigger should normally be: a check that the method and content type are acceptable, a check that the required fields are present, and only then the real work. Doing this in one IF node keeps failure cheap — a rejected request costs one execution, not a failed third-party call.

// IF node - is this request usable?
{{ $json.body.customer_id !== undefined && $json.headers['content-type']?.includes('application/json') }}

// and a second IF for a shared-secret header, before anything expensive
{{ $json.headers['x-signature'] === $vars.expected_signature }}

Acknowledge fast, work slowly

The hardest call in this chapter is whether the caller waits. If the workflow can take more than a couple of seconds, return a response immediately and let the work continue in the background. The caller gets a 202 and an id; the workflow writes its result somewhere the caller can poll, or calls the caller back on its own webhook.

// Webhook: Respond = Immediately, Response Code 202
// Body: { "jobId": "{{ $execution.id }}", "status": "accepted" }
// then the workflow proceeds; the caller polls
//   GET /webhook/jobs/{{ $execution.id }}

If you keep the caller waiting, remember that in queue mode a worker runs the execution while the client stays connected to the main or webhook process, and the response travels back through Redis. The default limit on that relayed message is 64 MiB (N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX), and Redis holds about 1.5× that per response in flight. Large responses should be offloaded to storage, or better, replaced with a pointer.

Making the endpoint safe to call twice

Webhook senders retry. If a create endpoint runs twice it creates two invoices, so an endpoint that changes state needs an idempotency key. The conventional design: accept an Idempotency-Key header or a request_id body field, and use the Code node's workflow static data or a database lookup to remember the last processed key.

// Code node - a minimal idempotency check with workflow static data
const store = $getWorkflowStaticData('global');
store.seen = store.seen ?? {};
const key = $json.headers['idempotency-key'] ?? $json.body?.request_id;

if (!key) throw new Error('idempotency key required');
if (store.seen[key]) return [{ json: { duplicate: true, key } }];

store.seen[key] = Date.now();

// bound the store so it does not grow forever
const cutoff = Date.now() - 7 * 86_400_000;
for (const k of Object.keys(store.seen)) {
  if (store.seen[k] < cutoff) delete store.seen[k];
}
return [{ json: { duplicate: false, key } }];

Static data is per workflow and persisted in the database, which makes it a reasonable place for bounded caches and cursors; it is not a database, so for anything beyond a few thousand keys use a real table or the workflow's own Postgres.

6.5 Calling n8n's own API and other n8n instances

n8n exposes a public REST API for managing workflows, executions and (read-only) credentials, plus a CLI for bulk operations. Both are the bridge between your automation and your tooling.

The public API

Enable it per instance, create an API key under Settings → n8n API, and call it with a header credential. The API is versioned (/api/v1) and covers what an integrator needs: list and create workflows, activate/deactivate (publish/unpublish in 2.x terms), read executions and their data, and list credentials without exposing their secrets.

# shell - list workflows, then fetch one execution's data
export N8N_API_KEY=eyJ...
curl -s -H "X-N8N-API-KEY: $N8N_API_KEY" \
  "https://n8n.example.com/api/v1/workflows?limit=5"

curl -s -H "X-N8N-API-KEY: $N8N_API_KEY" \
  "https://n8n.example.com/api/v1/executions/1041?includeData=true"

Two configuration knobs matter operationally: N8N_PUBLIC_API_DISABLED=true turns the API off entirely (a sensible default on an internet-facing instance that nobody integrates with), and N8N_PUBLIC_API_ENDPOINT changes the path from api if your reverse proxy already owns that prefix.

The CLI for bulk work

The CLI is the right tool for exporting and importing at scale, and for the operations you would otherwise script against the API with pagination and retries.

# shell - export and import, the supported migration path
n8n export:workflow --all --output=./workflows.json
n8n export:credentials --all --decrypted --output=./credentials.json   # moves secrets
n8n import:workflow --separate --input=./workflows/                    # one file per workflow

n8n publish:workflow --id=1041                 # 2.x: activate by id
n8n unpublish:workflow --id=1041 --all

export:credentials --decrypted writes real secrets to disk, which is either exactly what you need (moving an instance) or a security incident (leaving the file on a shared volume). Encrypt or delete such files immediately; they cannot be re-encrypted by n8n without a matching key on the target instance.

n8n calling n8n

One instance can call another with the HTTP Request node and an n8n API credential, which is how teams split a shared platform instance from per-team instances. Two rules make this survivable: give the calling instance a credential scoped to only what it needs, and never let the two instances share an encryption key — that would let a credential stolen from one decrypt on the other.

# shell - trigger another instance's workflow by webhook, the simplest bridge
curl -X POST https://n8n-eu.example.com/webhook/sync-invoice \
  -H "Content-Type: application/json" \
  -H "X-Signature: $SHARED_HMAC" \
  -d '{"invoice_id":"inv_1041","region":"eu"}'

The webhook bridge is usually better than the API bridge for workflow-to-workflow calls: it is explicit about the contract, it can be authenticated with a shared secret, and it does not require handing out a management-scoped API key.

Rate-limit yourself before the API does. The Wait node in a loop, or the HTTP node's batch interval, turns a burst that triggers 429s into a steady drip that succeeds — and a 429 in the middle of a paginated fetch is otherwise very hard to resume cleanly.

7.1 How credentials are stored

A credential is a named set of authentication fields, encrypted with the instance key before it reaches the database. Workflows reference credentials by id; the secret value is never stored in the workflow JSON.

The lifecycle of a credential

You create a credential, choose a type, fill in its fields, and n8n encrypts the data and stores it. The workflow node then holds only a credential id and name. At run time, n8n decrypts the credential in memory, hands it to the node, and the node uses it. Two consequences follow directly: exporting a workflow never leaks secrets, and a workflow imported onto another instance will not work until the credentials are created there too.

// a node in an exported workflow - note what is NOT there
"parameters": { "url": "https://api.example.com/invoices" },
"credentials": { "httpHeaderAuth": { "id": "18", "name": "Example API" } },
"typeVersion": 4.2

Sharing and scoping

Credentials have owners and, on editions that support projects, a project scope. The default posture encourages sharing: a team's Slack credential is created once and multiple workflows use it. The risk being managed is lateral movement — a credential that can write to production should not be usable by every workflow in the instance. Projects plus project roles are the mechanism; on the free Community edition you get a single shared space, and the honest mitigation there is fewer users and network-level restriction.

// Code node - read a credential's fields when you genuinely need them
// (only works if the node has a credential attached; prefer not to do this)
const cred = await this.getCredentials('httpHeaderAuth');
// -> { name: 'Example API', value: 'secret' }   <-- the secret, in your code

Prefer the credential slot on the node to reading it in code. A credential attached to a node is masked in the UI, is not written into the workflow's version history, and is not visible to a colleague reading your script.

Types: generic and predefined

A generic credential (Basic Auth, Header Auth, Query Auth, OAuth1, OAuth2) is a shape. A predefined credential (Slack, Google, GitHub, …) is a shape plus the service's specific fields and its token-refresh logic. When a service has a predefined type, use it — especially for OAuth2, where the refresh dance is implemented for you and getting it wrong means an integration that works for an hour and then stops.

TypeTypical useGotcha
Basic AuthLegacy APIs, internal toolsSends the password on every request; requires TLS
Header AuthAPI keys, bearer tokensHeader name is case-insensitive at the API, sometimes not in the API's docs
Query AuthAPIs that take a key in the URLThe key ends up in server logs and browser history
OAuth2Anything with a consent screenRedirect URL must match exactly, and be publicly reachable
PredefinedAny service n8n ships a type forScopes; asking for more than you need invites revocation

Testing and rotating

Every credential form has a connection test — use it. A credential that saves successfully but fails the test is nearly always a scope or redirect problem, and the test surfaces it in the editor rather than at 3am in an error workflow. Rotation is manual for a generic credential (create a new one, repoint the nodes), which is a strong argument for external secrets on a paid edition: the workflow references a secret name and the value can be rotated without touching n8n.

7.2 OAuth2 in practice

OAuth2 is the one credential type where the failure mode is not "wrong password" but a redirect that never arrives. Understanding the flow turns a mysterious error into a checklist.

The flow n8n implements

You paste a client id and secret, n8n generates a redirect URL, the provider redirects the user back with a code, and n8n exchanges the code for an access token and a refresh token. Thereafter n8n refreshes the access token silently as it expires. Three things must be true for the initial exchange to work: the redirect URL is registered exactly, the URL is reachable from the browser doing the consent, and the instance's base URL is configured so n8n knows what its own callback address is.

# shell - the configuration that makes OAuth work behind a proxy
export N8N_HOST=n8n.example.com
export N8N_PROTOCOL=https
export N8N_EDITOR_BASE_URL=https://n8n.example.com
export WEBHOOK_URL=https://n8n.example.com/
export N8N_PROXY_HOPS=1
# register at the provider:
#   https://n8n.example.com/rest/oauth2-credential/callback

Reading the failure

SymptomCause
"redirect_uri_mismatch"The registered callback differs by a trailing slash, scheme or host
Callback lands on a login pageOAuth callback authentication is on and the provider has no session
Consent succeeds, credential unusableThe token was minted for a different instance base URL; the refresh will also fail
Works once, fails tomorrowMissing offline_access or equivalent scope, so there is no refresh token

The first row is by far the most common, and it is a literal string comparison. Copy the URL out of n8n rather than reconstructing it.

Managed OAuth and credential overwrites

An operator can supply the client id and secret centrally so that users only click Connect and never see the secret. The supported way to do that is the credential-overwrite endpoint: point CREDENTIALS_OVERWRITE_ENDPOINT at a path, optionally protect it with CREDENTIALS_OVERWRITE_ENDPOINT_AUTH_TOKEN, and POST a JSON document of credential types and their fields.

# shell - publish overwrites at startup, ideally from your deploy script
export CREDENTIALS_OVERWRITE_ENDPOINT=send-credentials
export CREDENTIALS_OVERWRITE_ENDPOINT_AUTH_TOKEN=secure-token
export CREDENTIALS_OVERWRITE_PERSISTENCE=true     # store them and push to workers

curl -X POST http://localhost:5678/send-credentials \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer secure-token" \
  --data @oauth-credentials.json
// oauth-credentials.json
{
  "googleOAuth2Api": { "clientId": "<id>", "clientSecret": "<secret>" },
  "githubOAuth2Api": { "clientId": "<id>", "clientSecret": "<secret>" }
}

Two details decide whether this is pleasant or painful. Credentials extend other credentials, so setting the parent (googleOAuth2Api) covers every child that extends it. And CREDENTIALS_OVERWRITE_PERSISTENCE=true is required if you run queue mode, because without it the overwrites live only in the memory of the process that loaded them and never reach the workers.

Do not use CREDENTIALS_OVERWRITE_DATA as an environment variable. Environment variables are readable inside n8n, so a user who can write a Code node with environment access can read your client secrets. Use the endpoint, or an external secret store.

Scopes and verification

Ask for the narrowest scopes that work. Beyond the obvious least-privilege argument, providers tie app verification to the set of scopes declared, and n8n 2.x can let users add their own scopes for a listed credential type via N8N_MANAGED_OAUTH_SHOW_SCOPES. That is off by default for a reason: a user adding an undeclared scope to a Google credential can get the app suspended.

7.3 The encryption key

Every stored credential is encrypted with a single symmetric key held in the .n8n directory or supplied as N8N_ENCRYPTION_KEY. That key is the highest-value secret in the deployment.

Where it lives and who needs it

On first start n8n generates a random key and writes it into its config file. In queue mode every worker and webhook processor needs the same key, because any of them may need to decrypt a credential at execution time. This is why N8N_ENCRYPTION_KEY belongs in your deployment configuration rather than in a file that only exists on the main instance.

# shell - supply it explicitly everywhere, from one source
# main, webhook processors and workers all read the same value
export N8N_ENCRYPTION_KEY="$(cat /run/secrets/n8n_key)"

# or, if you prefer a file per variable
export N8N_ENCRYPTION_KEY_FILE=/run/secrets/n8n_key

Rotating the key

Key rotation exists but is deliberately awkward, because it is a one-way operation over a live database. The feature is gated behind N8N_ENV_FEAT_ENCRYPTION_KEY_ROTATION=true on every instance (main and workers), and the documentation is explicit that you take a full database backup first. Do that; there is no undo, and a half-rotated multi-instance cluster is a genuine outage.

# shell - the shape of a rotation, on every instance
export N8N_ENV_FEAT_ENCRYPTION_KEY_ROTATION=true
# 1. full database backup
# 2. set the new N8N_ENCRYPTION_KEY everywhere
# 3. restart all instances together
# 4. verify by running a workflow that uses a credential

What the key does not protect

The key protects credentials at rest in the database. It does not protect: the plaintext in memory during a run, execution data that a workflow happened to log, values written into a Code node, or the exported credential file from n8n export:credentials --decrypted. A stolen database plus a stolen key is a full compromise of every connected system, which is precisely why both halves should live in a secret manager rather than on the same disk.

# shell - restrict execution data as well; two independent controls
export N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true   # config file 0600
export N8N_BLOCK_FILE_ACCESS_TO_N8N_FILES=true      # block node access to .n8n

If you lose the key

Credentials become undecryptable — there is no bypass, no vendor recovery and no workaround. The instance still works: workflows, users and execution history are all intact. Every workflow that uses a credential fails when it tries to authenticate, so the practical remedy is to recreate each credential and repoint the nodes. That is a painful afternoon, and it is the entire argument for storing the key in the same place you store your database backups.

7.4 Variables, external secrets and environment configuration

Three tiers of configuration with different security properties: variables (visible, editable, non-essential), external secrets from a vault (secret, referenced by name), and environment variables (powerful but readable from inside n8n).

Variables: configuration, not secrets

Variables are strings scoped globally or to a project, with a 50-character key limit and a 1000-character value limit, and only letters, digits and underscores allowed. Workflows read them as $vars.key. Because anyone who can edit a workflow can read them, they are the right place for an escalation address or a threshold and the wrong place for a token.

External secret stores

On editions that support it, n8n can read secrets from an external vault (for example AWS Secrets Manager, Azure Key Vault, Google Secret Manager, HashiCorp Vault, Infisical or 1Password) and expose them as $secrets.<provider>.<name> in expressions. The workflow stores a reference; the value stays in the vault and is fetched at run time. Rotation becomes a vault operation with no n8n change, which is the whole point.

// expression referencing an external secret
{{ $secrets.vault.api_base_url }}
{{ $secrets.onepassword.stripe_live_key }}

Two operational notes. The instance needs credentials to reach the vault, and those live in n8n's own configuration — a chicken-and-egg that most teams resolve with a cloud instance role rather than a static key. And a vault outage becomes an n8n outage, because expressions resolve at run time; scope the vault credential's permissions to exactly the secrets involved.

Environment variables inside workflows

$env exists and is blocked by default in n8n 2.0 (N8N_BLOCK_ENV_ACCESS_IN_NODE=true). Operators sometimes enable it because it is convenient, then discover that the database password they put in DB_POSTGRESDB_PASSWORD is now readable from any Code node. If you must use it, put non-sensitive values in the environment and nothing else.

# the checklist: which secret belongs where
#   DB password, encryption key        -> platform secret, never $env
#   third-party API tokens             -> credential or external secret
#   escalation email, thresholds       -> variable
#   feature flags                      -> variable
#   per-environment base URLs          -> environment variable (non-secret)

SSRF and outbound request control

An HTTP Request node can call any URL, including http://169.254.169.254/ — the cloud metadata endpoint. That is the classic server-side request forgery route, and it only takes one workflow that builds a URL from user input. Definitive controls: run n8n where the metadata endpoint is blocked, and use n8n's SSRF protection settings to restrict outbound requests from workflow nodes.

# shell - SSRF protection, plus a blunt network-level control
export N8N_SSRF_PROTECTION_ENABLED=true
# and, at the network layer, block link-local 169.254.0.0/16 egress
# from the container/VM that runs n8n

7.5 Users, roles and instance hardening

User management gives you login, invitation and three built-in instance roles. RBAC adds project scoping and, on Enterprise, custom roles. On a self-hosted instance, the hardening checklist around all of it matters more than the roles themselves.

Instance roles and project roles

Instance roles are Owner, Admin and Member. Owner and Member exist on every edition; Admin requires Cloud Pro/Enterprise or self-hosted Enterprise. Instance roles answer "what can this person do across the whole instance". Project roles answer "what can they do inside this folder of workflows and credentials", and project scoping is available on all Cloud plans and on Registered Community and above self-hosted. Custom roles — defining your own permission sets — are Enterprise.

LevelQuestion it answersAvailability
Instance roleCan this person manage users, credentials and settings?All plans; Admin is paid
Project roleCan this person see and run this workflow?All Cloud; self-hosted Registered Community+
Custom roleA permission set you defined yourselfEnterprise

The practical pattern is one project per team, credentials owned by the project, and Members with execute-but-not-edit where a workflow is production. On the free Community edition there is a single space and every user can see everything — restrict who gets an account instead.

Identity, 2FA and SSO

Configure the Owner account first and disable self-signup implicitly by not inviting anyone you would not trust with the database. Two-factor authentication can be enforced instance-wide with N8N_MFA_ENFORCED_ENABLED=true plus the security-policy-managed-by-env switch, and SSO (SAML, OIDC, LDAP) is a Business/Enterprise feature. If your organisation already has an identity provider, SSO is the difference between "an ex-employee's account" and "deprovisioning handled where it already happens".

The self-hosted hardening checklist

  • TLS only. Terminate HTTPS in front of n8n; set N8N_PROTOCOL=https and don't rely on N8N_SSL_KEY/N8N_SSL_CERT unless you must — a proxy is easier to keep patched.
  • Restrict who can reach the editor. The editor is the highest-privilege surface. An IP allowlist or a VPN on the editor paths, with only /webhook/* exposed publicly, is the single biggest risk reduction.
  • Keep N8N_SECURE_COOKIE=true and leave N8N_SAMESITE_COOKIE at lax unless an embedding requires otherwise.
  • Leave the dangerous nodes out. Execute Command and Local File Trigger are disabled by default in 2.0 for good reason; if you re-enable them, do it on an instance that only trusted users reach.
  • Bound file access. N8N_RESTRICT_FILE_ACCESS_TO defaults to ~/.n8n-files; keep it narrow rather than widening it for one workflow.
  • Prune and redact execution data. Execution payloads contain real business data. Pruning limits how long it lives; redaction hides input and output while keeping status and timing.
  • Disable what you don't use. N8N_PUBLIC_API_DISABLED=true, templates off if you have no internet egress, telemetry off with N8N_DIAGNOSTICS_ENABLED=false (noting that this also disables the Code node's AI help).
  • Pin versions and upgrade deliberately. Weekly minor releases on the stable channel; read the release notes for breaking changes before moving across a major.
  • Watch the audit surface. Log streaming (paid editions) and the security audit are the tools; at minimum, ship container logs to somewhere an attacker cannot delete them from.
  • Never expose the task-runner container. The Docker-in-Docker runner is equivalent to root on the host.
The default self-hosted install has no RBAC, no SSO and one shared space, and it is trivially reachable if you publish port 5678 to the internet. Treat the Community edition as an internal tool: private network, or an authenticated reverse proxy in front of the editor.

8.1 Node-level error settings

Every node has an On Error setting in its Settings tab, plus a retry policy, plus a switch that decides whether the node emits anything when it has nothing. Getting these three right removes most of the need for defensive code.

The three On Error strategies

SettingBehaviourUse when
Stop WorkflowThe default. The node fails, the execution fails, the error workflow runsAnything where continuing would corrupt data
Continue (using error output)Items that failed go out of the node's second (error) outputPer-item handling: you want to retry, log, or report each failure individually
Continue (using regular output)The node emits its placeholder/empty item and the workflow carries onNon-critical enrichment where a missing value is acceptable

Note the history: older n8n had a single "Continue On Fail" toggle. If you are following an old tutorial, that is this setting, and the error-output variant is the piece that did not exist then.

// The error output carries the failure alongside the item, so you can report per row
// On your node: Settings -> On Error = "Continue (using error output)"
// then downstream, on the error branch:
{{ $json.error.message }}      // why it failed
{{ $json.error.node.name }}    // which node
{{ $json.error.description }}  // n8n's human-readable hint, when present

Retry On Fail

Retry On Fail re-runs the node up to a maximum number of tries with a fixed wait between them. It is the correct response to a transient network error, a 429 or a cold-starting API, and the wrong response to a validation error that will fail identically three times. Because the wait is fixed rather than exponential, keep the count small — three or four tries — and add a Wait node for anything that needs a longer backoff.

// Settings tab
Retry On Fail:        on
Max Tries:            3
Wait Between Tries:   5000 ms

// equivalent shape in an old workflow's JSON
"retryOnFail": true, "maxTries": 3, "waitBetweenTries": 5000
Retry makes a non-idempotent node dangerous. A node that "create invoice" and timed out after the POST reached the server will, on retry, create a second invoice. Either make the operation idempotent upstream (an idempotency key) or do not retry it.

Always Output Data and Execute Once

Always Output Data forces a single empty item when the node produces nothing, so a downstream chain still runs. That is how you make "the API returned no results" observable instead of invisible. Execute Once limits the node to the first item, which is what you want for a "send one summary email" node fed by a hundred rows, and is also the usual fix when an HTTP node would otherwise make a hundred calls to a setup endpoint.

// Code node - the explicit version of Always Output Data, with context
const items = $input.all();
if (items.length === 0) {
  return [{ json: { empty: true, reason: 'upstream filter matched nothing' } }];
}
return items;

8.2 Error workflows and the Error Trigger

An error workflow is a normal workflow that starts with an Error Trigger and runs whenever a workflow it is assigned to fails. It receives structured data about the failure, which is what makes alerting useful rather than noisy.

Setting one up

Create a workflow whose first node is Error Trigger; save it. Then in every workflow you care about, open Workflow Settings → Error Workflow and select it. One error workflow can serve many workflows — that is the point, and it is why the payload includes the workflow's name.

// The default error payload
[
  {
    "execution": {
      "id": "231",
      "url": "https://n8n.example.com/execution/231",
      "retryOf": "34",
      "error": { "message": "Example Error Message", "stack": "Stacktrace" },
      "lastNodeExecuted": "Node With Error",
      "mode": "manual"
    },
    "workflow": { "id": "1", "name": "Example Workflow" }
  }
]

Three fields are conditional. execution.id and execution.url exist only if the execution was saved to the database. retryOf is present only when the failing execution was itself a retry of an earlier one. And if the failure was in the trigger, the payload changes shape entirely — there is no execution at all, and instead you get a trigger.error object of type WorkflowActivationError.

// Alert on both shapes without throwing
const isTriggerFailure = !$json.execution;

const summary = isTriggerFailure
  ? `TRIGGER FAILED in "${$json.workflow.name}": ${$json.trigger.error.message}`
  : `FAILED in "${$json.workflow.name}" at node "${$json.execution.lastNodeExecuted}": ` +
    `${$json.execution.error.message} (${$json.execution.url})`;

return [{ json: { summary } }];

What a good error workflow contains

Route, don't broadcast. A useful error workflow does three things and stops: it renders a compact summary, it sends that summary somewhere a human will see it (a Slack channel, an email, a ticket), and it deduplicates so a workflow failing a hundred times does not send a hundred alerts. Anything more elaborate — auto-retrying the whole workflow, auto-disabling it — is a decision that belongs in a human's hands on the first occurrence.

// Code node - collapse repeated failures into one alert per hour
const store = $getWorkflowStaticData('global');
store.alerts = store.alerts ?? {};

const key = `${$json.workflow.name}:${$json.execution?.lastNodeExecuted ?? 'trigger'}`;
const last = store.alerts[key] ?? 0;
const hour = 3_600_000;

if (Date.now() - last < hour) {
  // suppress: emit nothing meaningful and let the IF downstream drop it
  return [{ json: { suppress: true, key } }];
}
store.alerts[key] = Date.now();
return [{ json: { suppress: false, key } }];

Failing on purpose: Stop And Error

Sometimes "no data" should be a failure — a nightly job that finds nothing to process is usually a symptom. The Stop And Error node ends the execution with an error message you choose, which then flows into the error workflow like any other failure. Used sparingly, it converts a silent no-op into an alert; used everywhere, it makes every quiet night look like an incident.

// Stop And Error - a guard against a silently empty import
Error Message: Expected at least one order since {{ $now.minus({ days: 1 }).toFormat('yyyy-LL-dd') }}, got 0

8.3 Reading the executions log

The Executions list is the primary observability tool. It is per-workflow and instance-wide, filterable by status, and it stores the input and output of every node in every execution.

What an execution record holds

  • Status — success, error, waiting, running, or cancelled. "Waiting" is what a Wait node or a human-in-the-loop node looks like: the execution is paused and will resume on a URL or a timer.
  • Timing — start, finish and duration per execution, and — importantly — per node, which is where you find the slow step.
  • Data — every node's input and output, as it was, subject to your pruning and redaction settings.
  • Mode — manual, trigger, webhook or integrated, which tells you whether a human clicked something.
# shell - the same data over the API, for dashboards
curl -s -H "X-N8N-API-KEY: $N8N_API_KEY" \
  "https://n8n.example.com/api/v1/executions?status=error&limit=20" \
  | jq '.data[] | {id, workflowId, startedAt, stoppedAt}'

Debugging from a past execution

The most useful feature in the whole log: open a past execution, find the node whose output was wrong, and copy that data into your current workflow as pinned data. You now reproduce a production bug without touching production, and you can iterate on the fix with the exact input that broke it. This works only if execution data has not been pruned — which is a good argument for keeping a modest retention window rather than zero.

# shell - how long execution data survives, and how much
export EXECUTIONS_DATA_PRUNE=true
export EXECUTIONS_DATA_MAX_AGE=336              # hours (14 days)
export EXECUTIONS_DATA_PRUNE_MAX_COUNT=10000    # cap by count too

When the log is the problem

A high-volume workflow can write tens of thousands of execution rows a day, and each carries its node data. Symptoms: a database that grows by gigabytes a week, an Executions page that takes seconds to load, and a Postgres instance doing more work storing history than running workflows. The remedies are pruning (age and count), redaction of the data itself, and — for the noisiest workflows — switching the per-workflow save setting to only save errors.

# shell - keep only failed executions for a chatty workflow, via workflow settings
# UI: Workflow settings -> Save execution progress / Save manual executions
# instance-level equivalents:
export EXECUTIONS_DATA_SAVE_ON_SUCCESS=none     # only store failures + errors
export EXECUTIONS_DATA_SAVE_ON_ERROR=all

Metrics, health and tracing

For a production instance, three signals matter more than the UI: the number of executions per hour and their error rate, the queue depth (in queue mode, the backlog in Redis), and the health endpoints. Each worker exposes /healthz and /healthz/readiness when QUEUE_HEALTH_CHECK_ACTIVE is on, and a Prometheus /metrics endpoint can be enabled per instance. Exporting those and alerting on error rate is the difference between "we noticed" and "a customer told us".

# shell - the probes worth wiring into your orchestrator
curl -sf http://localhost:5678/healthz                 # instance is up
curl -sf http://localhost:5678/healthz/readiness       # DB (and Redis) reachable
curl -sf http://localhost:5678/metrics | head          # if metrics are enabled

8.4 Debugging techniques that work

Most n8n debugging is not about finding the bug; it is about finding where the data went wrong. These techniques narrow that search quickly.

Isolate by disabling and by partial runs

Selecting a node and pressing D disables it, and a disabled node passes its items straight through. That turns a chain of five suspect nodes into a chain of four plus a bypass, and it is faster than deleting and rewiring. Combined with running a single node (double-click it) against the last known input, you can bisect a workflow in a handful of steps.

Bisection works because a disabled node is a no-op that forwards data, so the only variable is the suspect step. Start from the middle of the chain: if the workflow still misbehaves with the later half disabled, the fault is upstream; if it runs clean, the fault is in the half you removed. Two or three rounds locate it in a chain of twenty.

# shell - disable a node from the workflow JSON, if you are scripting this
# "disabled": true goes on the node object; n8n skips it and passes data through

Logging and inspecting

console.log in a Code node writes to the browser console during a manual run and to the container's stdout during a production run, which makes it the cheapest instrumentation available. In a production run, docker compose logs -f n8n is where you read it.

// Code node - log the shape, not the whole payload
const items = $input.all();
console.log('count', items.length);
console.log('keys', Object.keys(items[0]?.json ?? {}));
console.log('sample', JSON.stringify(items[0]?.json).slice(0, 300));
return items;

The five bugs you will actually hit

{{ $input.all().length }}

Guards that pay for themselves

Add a validation step to any workflow whose input comes from outside n8n. A single IF node that checks the fields you are about to rely on, with a Stop And Error on the false branch, converts dozens of possible downstream failures into one clear message at the boundary.

// IF - all required fields present?
{{ ['customer_id','amount','currency'].every(k => $json.body?.[k] !== undefined) }}

// false branch -> Stop And Error:
Invalid payload: missing {{ ['customer_id','amount','currency']
  .filter(k => $json.body?.[k] === undefined).join(', ') }}

The same idea applies to output. Before a node writes into a system you do not control, check that the value is the shape you expect; a two-line validation step is cheaper than a corrupted record someone has to unpick by hand, and it keeps the failure at the boundary where the cause is still visible.

8.5 Idempotency, retries and safe re-runs

The hard question after any failure is "can I just run it again?". A workflow that can be re-run safely is one you can operate; one that cannot is one you must supervise.

Why retries are dangerous by default

An execution that fails halfway leaves a partial effect: three rows written, an email sent, a payment taken. Re-running from the top repeats the first three. The classic failure is a "charge the customer" node that times out after the charge succeeded, followed by an automatic retry that charges again. Every automatic retry mechanism in n8n — Retry On Fail, a queue retry, a manual re-run — inherits this problem.

Three shapes that are safe to re-run

  • Upsert instead of insert. Write with a key that makes the second write a no-op. Then a re-run converges instead of duplicating.
  • Check-then-act. Look up whether the work was done (by a natural key such as invoice number or message id) and skip if so.
  • Idempotency keys. Send a unique key with the request and let the API enforce single execution. Stripe, for instance, supports this directly.
// Code node - check-then-act against the workflow's own record of what it did
const store = $getWorkflowStaticData('global');
store.done = store.done ?? [];

const todo = $input.all()
  .map(i => i.json)
  .filter(r => !store.done.includes(String(r.invoice_id)));

// mark them BEFORE the side effect, or a crash between the two duplicates them
for (const r of todo) store.done.push(String(r.invoice_id));

return todo.map(json => ({ json }));

Resuming instead of restarting

Two n8n features exist precisely to avoid re-running work. A Wait node resumes an execution after a delay or on a URL, keeping the state in the database rather than in memory — so a restart does not lose the wait. And a sub-workflow can be resumed by its parent, which since 2.0 correctly returns the child's output to the parent even when the child paused for a webhook, a form or a human-in-the-loop approval.

// notify-and-wait pattern, in outline
//  1. compute the approval payload
//  2. Wait node: "On Webhook Call", save the resume URL
//  3. email the approver {{ $execution.resumeUrl }}
//  4. the click resumes this execution with the approver's data
//  5. IF $json.approved -> continue, else -> Stop And Error

Designing a workflow you can operate

Four habits separate a demo from something you can leave running: put the side effects at the end, after all the reading and validation, so most failures happen before anything irreversible. Make each side effect individually idempotent so a partial run is recoverable. Log a stable business key (order id, invoice number) so a re-run can be reasoned about from the execution list. And limit the blast radius — a batch of 25 with a checkpoint after each batch recovers from a failure 40 batches in, whereas one batch of 1,000 starts again from zero.

// Loop Over Items with a checkpoint: Batch Size 25, plus a Wait after each batch
// each iteration's success is visible in the execution log, so a manual
// re-run can start from the batch after the last successful one
State the retry policy in the node's Note field: "safe to retry — upsert", or "do not retry — charges the card". The next person to see a red execution will not work it out from the canvas.

9.1 The LangChain node cluster

AI in n8n is a self-contained set of nodes — the @n8n/n8n-nodes-langchain package — with a parent/child shape unlike any other part of the editor. A model, a memory, a tool and a retriever are not steps in a chain; they attach to a single node that uses them.

The sub-node shape

A normal connection carries items from the output of one node to the input of the next. AI sub-nodes do not work that way. The parent — an AI Agent or one of the chains — has extra connection ports drawn below it, labelled Chat Model, Memory, Tool and, for retrieval, Vector Store. You drop a model node on the canvas and connect it to one of those ports instead of to a data edge. The sub-node is still a node with parameters and credentials, but it produces no items of its own: it is a capability the parent calls.

This is why a canvas can look finished while a node is still missing something it needs. An AI Agent with no chat model attached, or a vector-store insert with no embedding model, does not fail to validate — it has an unfilled port that the editor marks with a small warning. Reading the ports is the fastest way to see what a template still expects you to supply.

What the package contains

Agent or chain?

The decision is the same one you make with any automation step: do you know the sequence, or does the model have to decide it? A chain is a single, deterministic call — summarise this, extract these fields, classify this into one of five labels. It runs once, it is cheap, and its output shape is predictable. An agent is a loop: the model chooses which of its tools to call, reads the result, and decides whether to call another. Use it when the path genuinely varies — "answer this customer's question using our docs and their order" — and not because it sounds more capable.

Agents cost more per execution (one model call per loop iteration, plus the tokens that describe every tool), are slower, and are harder to test because two runs can take different paths. The pragmatic rule is to build the deterministic chain first, ship it, and reach for an agent only when a real request cannot be served by a fixed sequence. When you do, keep the tool count small and the system message short — both are billed on every iteration.

9.2 The AI Agent and its sub-nodes

The AI Agent is the general-purpose "the model decides what to do next" node. Almost nothing about its behaviour is configured inside the node itself; it is configured by what you attach to it and by how you describe those attachments.

System message and user prompt

The node has two text fields with different jobs. The system message, under Options, sets the persona and the hard rules — who the assistant is, what it must never do, how it should phrase things. The prompt (the text parameter) is the actual task for this item, and it is where dynamic data goes. The usual prompt for a chat workflow is a single expression, {{ $json.chatInput }}; for a webhook workflow it is whatever field carries the request, such as {{ $json.body.message }}.

Keep the system message stable and short, and put the varying data in the prompt. A stable prefix is what prompt caching can reuse across calls, and a system message assembled from user input is the easiest prompt-injection surface in the whole node. If a value must come from the caller, treat it as data in the prompt, not as an instruction in the system message.

// AI Agent (Tools Agent) - the parameter shape in exported JSON
{
  "agent": "toolsAgent",
  "promptType": "define",
  "text": "={{ $json.chatInput }}",
  "options": {
    "systemMessage": "You are a support triage assistant. Use the order lookup tool before answering. Never invent an order status.",
    "maxIterations": 6
  }
}

Tools, and why the description is the interface

Every tool you attach is offered to the model with its name, its description and a schema of its inputs. The model chooses between them on that text alone, so a vague description is a bug. An HTTP Request Tool described as "makes a request" will be misused; the same tool described as "look up a customer order by order id; returns status, carrier and estimated delivery" will be called correctly. Give each tool the narrowest possible job, and prefer several precise tools over one general one that takes a free-form URL.

The tool set is also a token budget. Each tool's description and schema is sent on every iteration of every run, so a dozen tools is both a cost and a source of confusion for the model. The AI Agent node in 2.x is the Tools Agent: the older Conversation, OpenAI Functions, ReAct and Plan-and-Execute agent types were deprecated in 1.82, and the original Agent node was removed in 3.0, so a template written before then may not import cleanly.

Memory is keyed by session, and is volatile by default

Simple Memory is a window buffer: the last N turns of a conversation, held in the process that created it, keyed by a sessionKey expression. It is the right default for a single-instance test and the wrong choice for production on two counts. It lives in memory, so it is empty after a restart; and in queue mode two messages from the same session can land on different workers, each with its own copy, so the conversation appears to forget at random. Postgres Chat Memory or Redis Chat Memory stores the turns where every worker can see them.

Window size is a trade-off between recall and cost. Every remembered turn is re-sent to the model, so a large window quietly multiplies the input tokens of every message. A short window plus a retrieved summary of older turns is usually better than a long window of raw transcript.

9.3 The Chat Trigger and conversational workflows

The Chat Trigger gives a workflow a chat interface and a webhook at the same time. Opening it in the editor shows a working chat window; the same trigger also accepts messages over HTTP, so the same workflow can back an embedded widget or another service.

One message, one execution

Each message the chat trigger receives starts its own execution, which matters for two reasons. First, execution accounting: a busy chat is a busy — and, on Cloud, billable — workflow. Second, isolation: the trigger does not hold a long-lived session, so continuity comes from the memory sub-node on the agent, keyed by the trigger's sessionId, not from the trigger itself. Remove the memory sub-node and the assistant treats every message as the first.

Response modes

The node's Response Mode decides how the caller gets an answer.

Streaming only works when the responding node is one that can stream — in practice the AI Agent or a chat chain — and it changes the item shape the responding node sees. It is the difference between a chat that feels instant and one that shows a spinner for ten seconds, so for anything user-facing it is worth the extra wiring.

Calling it as a plain webhook

The trigger exposes a chat page and a webhook URL, both shown in the node. A POST to the webhook with the expected body starts the same flow as typing into the box, which is how you embed the assistant in a page you already have. The body carries an action, a sessionId and the user's text.

# shell - send a message to a Chat Trigger webhook
curl -X POST https://n8n.example.com/webhook/abc123/chat \
  -H 'Content-Type: application/json' \
  -d '{"action":"sendMessage","sessionId":"user-42","chatInput":"Where is my order?"}'

# the response carries the assistant's reply
# { "output": "Your order shipped on Tuesday and arrives Thursday." }

Exposure and access

A public chat trigger is an unauthenticated endpoint that spends your model budget, so it needs a gate before it is left open: an authentication check at the top of the workflow, a rate limit, or — for an internal tool — keeping the trigger internal and putting it behind your own proxy. n8n's built-in basic and header authentication on a regular webhook do not cover the chat trigger's own page, so treat a public chat link as a public API.

A chat session id is a guessable string. Never treat the presence of a sessionId as proof of identity — look the user up in your own system before the workflow does anything that touches their data.

9.4 Retrieval: vector stores, embeddings and loaders

Retrieval-augmented generation in n8n is two workflows that share most of their nodes. One reads your documents, splits them and stores their embeddings; the other embeds the question and fetches the nearest chunks to put in front of the model.

The ingestion workflow

The ingestion path is a short chain: a Document Loader reads a source and produces documents, a Text Splitter breaks each into overlapping chunks, an Embedding model turns each chunk into a vector, and a Vector Store node in insert mode writes them. The splitter's chunk size is the parameter that matters most. Too small and a chunk loses the context that gives it meaning; too large and the retrieved text wastes the model's context window on irrelevant sentences. A few hundred words with a modest overlap is the usual starting point, and the overlap exists so that a sentence cut in half at a boundary still appears whole in one of the neighbours.

Keep metadata with every chunk — source file, URL, section title, last-updated date. It costs nothing at insert time and it is the only way to answer "which document said that?", to filter retrieval to one tenant, or to delete every chunk from a document you have replaced.

// Recursive Character Text Splitter - the two parameters that matter
{
  "chunkSize": 1000,
  "chunkOverlap": 200
}
// store metadata beside the text so retrieval can be filtered and cited
// { "source": "handbook.pdf", "section": "Returns", "updated": "2026-08-01" }

The query workflow

At question time the vector store runs in retrieve mode with a topK — how many chunks to return. There are two ways to wire it. A Vector Store Tool attached to an agent lets the model decide when to search, which suits open-ended chat; a Vector Store Retriever feeding a Q&A Chain searches unconditionally on every run, which is cheaper and more predictable for a single-purpose endpoint. TopK is a quality dial: too low and the answer is missing a fact it needed, too high and the prompt is padded with near-misses that dilute the instruction.

Choosing where the vectors live

StoreGood whenWatch out for
Simple Vector StoreBuilding and testing a flow in one sessionIn-memory: gone on restart, and not shared between workers
PGVectorYou already run PostgresIndex tuning and table growth are now your job
Qdrant / Weaviate / MilvusSelf-hosted, larger corporaAnother service to run and back up
Pinecone / SupabaseManaged; you would rather not operate itPer-vector cost and vendor lock-in

Simple Vector Store deserves the warning it gets: it keeps vectors in the n8n process, so a workflow that works beautifully in a manual test retrieves nothing after a restart or on a different worker. Treat it as a development aid, not a store.

Embeddings must match between insert and query

An embedding is a point in a space defined by one model. Vectors from text-embedding-3-small and vectors from a different model — or even a different version of the "same" model — are not comparable, and searching across them returns confident nonsense rather than an error. If you change the embedding model, you must re-embed the entire corpus; there is no partial migration. Record which model produced a collection, and prefer a model your provider versions explicitly.

A vector search returns the nearest chunks, not the relevant ones. On a corpus that does not contain the answer, the retriever still hands the model its closest matches, and the model will often write a plausible answer from them. Add a guardrail, or a "say you do not know if the context does not answer" rule to the prompt.

9.5 Guardrails, MCP and keeping AI workflows bounded

An AI workflow that works in a demo fails in production for three reasons: it says something it should not, it loops or reaches beyond the tool it was given, or it costs more than anyone budgeted. Each has a node or a setting.

Guardrails

The Guardrails node sits on the model's output and checks it against a policy before anything downstream acts on it: jailbreak attempts, unsafe content, personally identifiable information, or drift away from a supplied topic. Because it is a normal node with true and false outputs, the safe path is the true branch and the failure path is whatever you choose — a canned reply, a ticket, a log. Place it between the model and any side effect, so a blocked answer never reaches a customer or a database.

MCP, in both directions

The Model Context Protocol lets n8n act as a client of someone else's tools and as a server that exposes its own. As a client, the MCP Client Tool attaches to an AI Agent and offers the remote server's tools to the model, so an agent can use a catalog it did not have to re-implement node by node. As a server, the MCP Server Trigger publishes selected workflows as tools that an MCP client — another n8n agent, an IDE, Claude Desktop — can call.

The server direction is powerful and needs the same care as any public API: the workflow you expose is now a capability someone else's agent can invoke, so it should validate its inputs, do one thing, and be versioned. A change to a published workflow's parameters is a change to your tool's contract.

// MCP surface, in outline
// n8n as client:  AI Agent -> [Tool port] -> MCP Client Tool -> remote MCP server
// n8n as server:  MCP Server Trigger -> workflow -> returned to the calling client
// auth for the server direction is a header credential on the trigger

Cost and latency

Two numbers dominate: input tokens, which grow with every remembered turn, every tool description and every retrieved chunk; and the number of model calls, which grows with every agent loop. The cheap wins are structural — a smaller window, fewer and more precisely described tools, a lower topK, a shorter system message — and they usually improve quality too, because a focused prompt beats a padded one. Set maxIterations so a confused agent stops instead of burning budget until the execution times out.

Log what the model node reports. Chat-model nodes attach a usage object to their output in most cases, and a Code node after the agent can pull it out and write it to a metrics store, so cost per workflow becomes a number you can see rather than one you discover on an invoice at the end of the month.

// Code node - pull usage out of the agent's output for logging
const steps = $json.intermediateSteps ?? [];
const usage = $json.tokenUsage ?? {};      // whatever the model node exposes
return [{ json: {
  loops: steps.length,
  tools: steps.map(s => s.action?.tool).filter(Boolean),
  tokens: usage.totalTokens ?? null
}}];
Cap the blast radius before you cap the cost. An agent with read-only tools can afford to be curious; an agent holding a "delete" or "send email" tool cannot. If a tool has a side effect, put a human approval step — a Wait node that resumes on a webhook — in front of it.

10.1 Queue mode and horizontal scale

Queue mode splits n8n into a main instance that serves the editor and dispatches work, a Redis broker, and one or more workers that execute. It is the single biggest operational change you can make, and on the Community edition it costs nothing but the infrastructure.

The roles

In the default all-in-one setup a single process serves the editor, receives webhooks, runs schedules and executes workflows. In queue mode those responsibilities separate. The main instance owns the editor, the REST API and the triggers, and puts each execution on a queue instead of running it. Workers pull executions from the queue and run them. A dedicated webhook process can take inbound webhook traffic off the main instance, and a dedicated scheduler process can own the timer-based triggers. Redis is the queue, Postgres is the database, and every process reads the same encryption key and the same database.

The payoff is threefold: execution throughput scales by adding workers, a heavy workflow no longer competes with the editor for the main process's event loop, and a worker can be replaced or resized without touching the instance users are logged into. The cost is that you now operate Redis, share binary data between processes, and lose the simplicity of one container.

# shell - a queue-mode worker, and the main instance beside it
n8n worker --concurrency=10      # one process, up to ten executions at once
n8n start                        # main: editor, API, triggers, dispatch
n8n webhook                      # optional: dedicated webhook process

The environment

Queue mode is configured almost entirely by environment variables, and the two that cause the most incidents are the encryption key and binary data. The encryption key must be byte-identical on every process; if a worker has a different key it cannot decrypt a credential that the main instance encrypted. Binary data — file uploads, attachments, images a node produced — is written by whichever worker ran the node, so in a multi-worker setup it must go somewhere shared.

# queue mode - the settings that must agree across every instance
EXECUTIONS_MODE=queue
QUEUE_BULL_REDIS_HOST=redis
QUEUE_BULL_REDIS_PORT=6379
QUEUE_BULL_REDIS_PASSWORD=change-me
QUEUE_BULL_PREFIX=n8n                 # namespace if the Redis is shared
N8N_ENCRYPTION_KEY=<same value everywhere>
DB_TYPE=postgresdb
QUEUE_HEALTH_CHECK_ACTIVE=true

# binary data must be reachable by every worker
N8N_DEFAULT_BINARY_DATA_MODE=filesystem   # then mount a shared volume
#   or: s3, with the N8N_EXTERNAL_STORAGE_S3_* settings

Concurrency, timeouts and back-pressure

Worker concurrency is the number of executions one worker runs at once, set with --concurrency. There is no universally right number: it is bounded by what the workflows do. Ten concurrent workflows that each make an HTTP call are fine; ten that each load a 50 MB file are not. Raise it in steps and watch memory. A production-wide ceiling is available through N8N_CONCURRENCY_PRODUCTION_LIMIT, and EXECUTIONS_TIMEOUT stops a stuck execution from occupying a slot forever.

Health checks and high availability

With QUEUE_HEALTH_CHECK_ACTIVE=true, a queue-mode instance answers /healthz/readiness as healthy only when its Redis and database connections are live, which is what an orchestrator should probe rather than a plain process check. Running more than one main instance — multi-main high availability, so a restart does not drop webhooks or schedules — is an Enterprise feature; the Community edition scales workers freely but runs a single main.

Scale the trigger and webhook side with the worker side, not after it. A thousand queued executions are useless if the main instance's webhook process is the thing that is saturated.

10.2 Data, backups and the encryption key

n8n's state is small and concentrated: a database, a configuration directory, and one key. Backing it up correctly is a ten-minute job; discovering that you cannot is the worst day a self-hoster has.

What is actually stored

Everything durable lives in the database: workflow definitions, user accounts and projects, the execution history, workflow variables, and the credentials, which are stored encrypted and never in plain text. The binary data attached to executions can be in the database or on shared storage, depending on N8N_DEFAULT_BINARY_DATA_MODE. The configuration directory, ~/.n8n by default, holds the settings file, which by default contains the auto-generated encryption key. Postgres is the recommended database; the default SQLite file is fine for a single instance and wrong the moment you add a second process. MySQL and MariaDB were dropped in n8n 2.0, so a legacy MySQL setup needs a migration, not an upgrade.

The encryption key

N8N_ENCRYPTION_KEY encrypts every stored credential. Lose it and the credentials are not locked in a way you can undo — they are ciphertext with no key, and you re-enter every API token by hand. In queue mode or any multi-instance setup it must be supplied explicitly and identically, because each process needs to decrypt what another encrypted. Treat it like a root password: generate it once, store it in your secret manager, and back it up separately from the database, so that a single compromised backup does not contain both halves.

# shell - back up the database and the key as a pair, to different places
pg_dump -Fc -U n8n n8n > n8n-$(date +%F).dump
cat ~/.n8n/config | grep '"encryptionKey"'    # store this in a secret manager

# export everything n8n knows, for a portable copy
n8n export:workflow --all --output=/backup/workflows.json
n8n export:credentials --all --decrypted --output=/backup/credentials.json

An export made with --decrypted contains plaintext secrets. It exists so you can move a whole instance to a new key; it is not a backup format to leave on a shared drive.

Pruning execution history

Execution history grows without bound and is the usual reason a database that was fine at launch is slow a year later. Pruning is on by default with a retention age of roughly two weeks and a count cap, both of which you will want to set deliberately for your volume. High-throughput instances often keep far less: the full input and output of every successful run is a lot of bytes for data nobody reads. Failed executions are the ones worth keeping, and the save-on-error and save-on-success flags let you keep those and drop the rest.

# keep failures for a fortnight, successes for almost nothing
EXECUTIONS_DATA_PRUNE=true
EXECUTIONS_DATA_MAX_AGE=336            # hours; 336 = 14 days
EXECUTIONS_DATA_PRUNE_MAX_COUNT=10000
EXECUTIONS_DATA_SAVE_ON_SUCCESS=none
EXECUTIONS_DATA_SAVE_ON_ERROR=all

10.3 Upgrades, node versions and source control

n8n ships a new minor release most weeks, which is either a healthy cadence or a treadmill depending on how you manage it. The upgrade itself is usually uneventful; the risk is concentrated in migrations and in the workflows you forget you changed.

Pin, read, then move

Do not run latest in production. Pin the container image or the npm version to a specific release, read the release notes for the versions you are jumping over, and move deliberately — usually a few minors at a time, not fifty. Database migrations run automatically when the instance starts, which means a rollback is not simply "run the old image": the schema has already moved. Back up before you start, and be explicit about which release you are moving to rather than letting a floating tag decide.

# shell - know what you are running, and what is available
n8n --version
N8N_VERSION_NOTIFICATIONS_ENABLED=true n8n start   # editor shows available updates

# before an upgrade: back up (see 10.2), then stop writes and deploy the new image

Workflows pin node type versions

A node in an exported workflow carries a type version. Upgrading n8n does not silently rewrite your nodes to their newest version, which is why an old workflow keeps working after an upgrade — and why a new node sometimes behaves differently from the one beside it in the same canvas. When you do bump a node's version, read what changed: a renamed parameter or a changed default can alter behaviour on the next run. This is also why "it works in the template, it works in my test, it broke in production" is a real pattern — the production workflow is on an older node version.

Getting workflows into version control

A workflow is JSON, so it can live in Git like any other artefact, and there is no single right way to do it. The free path is the CLI: export all workflows to files, commit them on a schedule or after a change, and diff. The licensed path is n8n's own Git integration with environments, which pushes and pulls from within the product. Either way the goal is the same — the workflow definition is reviewable and a bad change can be reverted, because n8n's audit trail of who edited what is a history, not a version control system.

# shell - a CI job that snapshots every workflow, one file each
git clone https://github.com/you/n8n-workflows.git backup-workflows
cd backup-workflows
n8n export:workflow --backup --output=./
git add -A && git commit -m "nightly export $(date +%F)" && git push

10.4 Monitoring, logging and alerting

You cannot watch a browser tab all day. Production n8n needs three signals — is it up, is work flowing, is anything failing — and each has a cheap way to get it.

Liveness and readiness endpoints

n8n answers /healthz when the process is up, and /healthz/readiness only when its dependencies are reachable, which in queue mode means Redis and the database. Point your orchestrator's liveness probe at the first and its readiness probe at the second, so an instance that has lost Redis is taken out of rotation instead of accepting webhooks it cannot queue.

Metrics and dashboards

Setting N8N_METRICS=true exposes Prometheus metrics at /metrics, covering process health and execution counts — enough to graph throughput and to alert on "no successful executions in an hour", the symptom that catches a stuck trigger or an expired credential before a human notices. For workflow-level alerting, the built-in tool is the Error Workflow: a setting on each workflow naming another workflow to run when it fails. That error workflow is where you send a Slack message, open a ticket, or append to a log table.

# shell - basic availability and throughput checks from a cron job
curl -sf http://localhost:5678/healthz/readiness || echo "not ready"
curl -s  http://localhost:5678/metrics | grep '^n8n_' | head

Logs

n8n logs to stdout by default, which is exactly right for containers: let the platform collect it. N8N_LOG_LEVEL controls how much (raise it to debug while chasing a problem, then put it back), and N8N_LOG_OUTPUT can write to a file instead when there is no log collector. Logs are where node-level failures without an execution record end up, so a log pipeline is not optional — it is the fallback when the execution history has already been pruned.

# verbose logs while debugging, and the container's own view
N8N_LOG_LEVEL=debug
N8N_LOG_OUTPUT=console
docker compose logs -f n8n
docker compose logs -f worker

The audit command

n8n audit runs a set of checks over the instance — credentials, database, filesystem, nodes — and reports risky findings such as credentials that have never been used, nodes that can execute arbitrary code, or a database that allows public schema access. It is not a substitute for review, but it is a fast, repeatable sweep that catches the things humans stop seeing.

n8n audit            # security report against the running instance's data

10.5 Users, roles and secrets in production

Once more than one person uses the instance, the questions shift from "does it work" to "who can see what, and where do the secrets live". n8n's answers here are partly free and partly licensed.

Accounts, roles and projects

User management is on by default: the first account is the instance owner, and further accounts are members or admins. The owner controls global settings; an admin can manage users. Individual workflows and credentials can be shared directly, and on the licensed side projects group workflows and credentials under a team with roles, so permission is granted to a project rather than one workflow at a time. Custom roles — a role that can run a workflow but not edit it, for instance — are Enterprise.

SSO and directory integration

SAML and OIDC single sign-on are Business features and are the usual reason a company that has been self-hosting informally buys a licence, because they turn provisioning and offboarding into an identity-provider action rather than an n8n one. Both map identity-provider claims to n8n accounts; LDAP is Enterprise. Two-factor authentication is available without a licence and should be required for any account that can read credentials.

Credentials, overwrites and external secrets

A credential is a stored, encrypted secret that nodes reference by name. The licensed capabilities around it matter as you scale: external secrets pull values from a vault at read time, so the secret is never stored in n8n's database, and credential overwrites let an administrator enforce that a given credential type always uses one shared value. Together they answer the awkward question of how hundreds of workflows share one API key without anyone pasting it.

Dates, and a worked example

$now and $today are Luxon DateTime objects, not strings, which is why date arithmetic works directly in an expression. Format for display, and add or subtract with plus and minus.

{{ $now.toFormat('yyyy-MM-dd') }}                 // 2026-10-14
{{ $today.plus({ days: 7 }).toISO() }}            // a week from today
{{ $now.minus({ hours: 24 }).toMillis() }}        // epoch ms, usable in a filter
{{ $json.email?.toLowerCase().trim() }}           // guard against a missing field

$json follows item linking: n8n keeps each item paired with the item that produced it, so an expression in a downstream node sees the right row rather than an arbitrary one. In a Code node the equivalent is spelled out — $input.all() and friends — and in native Python the objects are _items and _item.

Operators, types and failure behaviour

Expressions are JavaScript, so the ordinary operators work: ?. for optional access, ?? for a default, || for a fallback, and the ternary ? : for a choice. The $json object is typed loosely, which is convenient and is also the usual source of "Cannot read properties of undefined" — a field renamed upstream turns a working expression into a red node. Guard fields you do not control with ?., and let an expression return an empty string rather than throw when a value may be absent.

Two limits are worth remembering. An expression is evaluated per item, so anything expensive inside it — a regex over a large body, a JSON.parse — runs once for every item and can dominate the node's runtime. And an expression cannot see data that has not run yet: referring to a node whose branch was skipped yields nothing rather than an error, so a downstream expression that depends on a conditional branch needs a guard. When an expression grows past a line or two, move it into an Edit Fields or Code node, where it can be tested on its own.
