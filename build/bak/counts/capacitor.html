Welcome - How to Use This Capacitor Guide

0.1 How this guide is organised0.2 The right mindset0.3 Tools you will use the whole way0.4 What to know before you start

Capacitor turns any web project into a real native app on iOS and Android. This section explains how to work through the guide, what mental model to hold, which tools to install first, and what you should already know before chapter one.

Capacitor is not a framework. It is a runtime and a set of plugins that embed your existing web assets inside a native shell, then expose the operating system to JavaScript through a promise-based bridge. That single sentence is the whole idea, and every later chapter is a detail hanging off it.

0.1 How this guide is organised

Maps the three-part structure of the guide so you can find any topic fast and know what to read first.

What each part assumes you already know

The three parts are ordered by depth of native involvement. Part I (chapters 1-6) is the runtime itself - the shell, the CLI loop, the bridge, the plugin contract and permissions - and it assumes only web skills: HTML, CSS, JavaScript and a build step. You never open Xcode or Android Studio. Part II (chapters 7-11) is where you first write native code: the plugins almost every app needs, custom native code, and the details that make an app feel native. Part III (chapters 12-16) is shipping - performance, security, testing, signing, release builds and troubleshooting - and it is where the native toolchain becomes your problem.

0.2 The right mindset

The three beliefs that separate people who ship Capacitor apps from people who fight the framework.

  1. It is a web app in a container, not a hybrid compromise. The UI is your web code. The shell only provides a window, a bridge and native build tooling. Optimise for fast web, and add native only where the bridge is genuinely required.
  2. The native projects are yours. ios/ and android/ are real Xcode and Gradle projects checked into your repo. You can edit them, add Swift or Kotlin files, and commit the result. Capacitor will not delete your changes unless you run a destructive command.
  3. Prefer official plugins, then community, then custom. The first-party plugin set covers most needs. Reach for a custom plugin only after you have confirmed no maintained plugin does the job.

0.4 What to know before you start

The baseline this guide assumes, and the one topic worth brushing up if you are shaky on it.

  • Comfortable HTML, CSS and modern JavaScript, including ES modules, promises and async/await.
  • A working JavaScript build step. This guide uses Vite because it is the most common pairing, but Capacitor itself is build-tool agnostic. Anything that emits a folder of static files works.

You do not need Kotlin, Swift, Gradle or Xcode knowledge for chapters 1 to 11. You need it from chapter 12 onward, when the focus moves to signing and store submission. That is the point of Capacitor: the native toolchain only becomes your problem at the very end.

1.1 What a native shell actually is

Defines the four components Capacitor puts on the device and why the web view is the only place your app code runs.

The web view component

When you run npx cap add android, Capacitor inserts a platform web view — WebView on Android (based on Chromium) and WKWebView on iOS — and loads your app's built origin into it. This web view is a headless browser engine; it runs your HTML, CSS and JavaScript exactly like a desktop browser, but it has no chrome: no address bar, no bookmarks, no developer tools unless you enable them. The web view occupies the full application window and is the only place where your JavaScript executes. All UI rendering, layout and script lifecycle happen inside this sandboxed browser context.

// verifying the web view is running your origin
const getOrigin = () => {
  return window.location.origin;   // e.g. http://192.168.1.50:5173
};
console.log('Web view origin:', getOrigin());

The native runtime library

Complementing the web view is a thin platform-specific glue library. On Android it is written in Kotlin and shipped as an AAR; on iOS it is written in Swift and shipped as a framework. This library does not contain any of your application logic — it does not know or care about your routes, your state or your UI. Its sole purpose is to expose a minimal async bridge: JavaScript calls a function name and a JSON payload, and the library forwards that across the process boundary to native code. The library also handles app lifecycle events, launch options and permissions that the web view cannot itself manage.

// the minimal plugin bridge entry point
// Android: Kotlin - CAPPlugin interface
@CapacitorPlugin(name = "Example")
class ExamplePlugin(private val context: Context) : Plugin() {
    @PluginMethod
    fun doSomething(call: PluginCall) {
        val result = "hello from native"
        call.resolve(mapOf("result" to result))
    }
}

// iOS: Swift - CAPPlugin protocol
@objc(ExamplePlugin)
public class ExamplePlugin: CAPPlugin {
    @objc func doSomething(_ call: CAPPluginCall) {
        call.resolve(["result": "hello from native"])
    }
}

The JavaScript bridge

Between the web view and the native runtime runs a promise-based bridge. When you call Capacitor.pluginMethod(), the JavaScript side serialises the call and arguments into a JSON payload, which the bridge posts to the native side. The native runtime deserialises the JSON, locates the matching plugin method, executes it, and sends the result back the same way: JSON → deserialise → invoke → serialise → promise resolve. This round-trip is always asynchronous; there are no synchronous cross‑process calls. The bridge enforces that all values are structured‑cloned, which means functions, DOM nodes and class instances cannot cross — only plain objects, arrays, strings and numbers.

// Capacitor.registerPlugin() proxy — the public API
const { Capacitor } = require('@capacitor/core');
Capacitor.registerPlugin('Camera', {
    web: () => import('@capacitor/camera').then(m => new m.Camera()),
});

// the bridge serialises this into JSON and posts it to native:
// { "method": "getPhoto", "params": { "quality": 90, "resultType": "uri" } }
// native resolves the promise and sends the result back as JSON

Your built web assets

Finally, Capaculator copies your compiled web assets — the output of your Vite, Rollup or webpack build — into the native project. On Android these files end up under android/app/src/main/assets/public/; on iOS under ios/App/App/public/. This folder is your webDir, configured in capacitor.config.ts. The native web view loads from this local folder instead of a remote URL. Any change to your assets requires a npx cap sync to copy the updated files into both native projects before the changes appear in the running app.

// capacitor.config.ts - configures where assets are copied
import type { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'com.acme.myapp',
  appName: 'My App',
  webDir: 'dist',           // relative path, relative to project root
};

export default config;

1.2 The layers from URL bar to JavaScript

Walks the call path from your button click down to an OS API and back, so error messages make sense.

The JavaScript call path

When a user interacts with your app \u2014 tap a button, submit a form, navigate to a new route \u2014 the event handler runs on the web view's main thread. If the handler calls a Capacitor plugin method, the function name and its arguments are gathered and serialised into a JSON payload. This payload is handed to the bridge, which posts it to the native side via window.Capacitor (Android) or window.webkit.messageHandlers.Capacitor (iOS/WKWebView). The native side deserialises the JSON, locates the registered plugin method, and invokes it.

// JavaScript: invoking a plugin method
import { Geolocation } from '@capacitor/geolocation';

async function getCurrentPosition() {
  const position = await Geolocation.getCurrentPosition({
    timeout: 10000,
    enableHighAccuracy: true,
  });
  console.log('Latitude:', position.coords.latitude);
  console.log('Longitude:', position.coords.longitude);
}

// the bridge turns this into a JSON post to native,
// then returns a structured-clone of the result as a promise fulfilment

The bridge transport

The bridge itself is a thin message-forwarding layer. On Android, it uses WebView.postJavaScriptMessage() to inject a message event into the web view's JavaScript context. The payload is a JSON string under the data property. On iOS, it uses WKScriptMessageHandler with a configured name \u2014 by default Capacitor \u2014 so the web view receives a message event whose event.nativeMessage contains the serialised call. In both cases the JavaScript side receives an event with event.data set to the parsed JSON object.

// Listening for a bridge response
window.addEventListener('message', (event) => {
  if (event && event.data && event.data.method) {
    const { method, params, result } = event.data;
    if (result) {
      console.log('Plugin result:', result);
    }
  }
});

// The native side posts a message like:
// { "method": "getCurrentPosition", "params": { "timeout": 10000 } }

The return journey

After the native method runs, its return value is structured-cloned into JSON and sent back across the bridge. The JavaScript promise resolves with the deserialised result. If the native method throws or rejects, the promise rejects with an error object containing a code and a message. This round-trip \u2014 JavaScript \u2192 JSON \u2192 native \u2192 JSON \u2192 JavaScript \u2014 typically takes 50\u2013200\u00a0ms on a typical device, which is why plugin calls should always be written as await and never synchronously.

// JavaScript: awaiting the result
import { Camera } from '@capacitor/camera';

async function takePicture() {
  try {
    const photo = await Camera.getPhoto({
      quality: 90,
      resultType: CameraResultType.Uri,
    });
    // this runs after the native bridge resolves
    imageElement.src = photo.webPath;
  } catch (e) {
    console.error('Camera plugin failed:', e);
  }
}

// if the call takes too long, you can set a timeout
const promise = Camera.getPhoto({ quality: 90 });
const timeout = setTimeout(() => {
  promise.then(() => {}).catch(() => console.error('bridge timeout'));
}, 10000);

1.3 Capacitor vs Cordova vs React Native vs Flutter

An honest comparison, including the cases where Capacitor is the wrong choice, so you do not spend a month on the wrong foundation.

Native UI components

Capacitor renders your application inside a native web view, but it does not recreate the entire native UI component library. Standard HTML elements — buttons, inputs, headings, divs — are rendered by the web view's engine and automatically adapt to the host platform's visual language through native theming and CSS system fonts. However, native-specific UI patterns — such as platform-styled modals, action sheets, segmented controls, or bottom navigation bars — must be explicitly built or provided by a plugin. Attempting to mimic native controls purely with CSS often results in a mismatch during OS updates, where the web view's rendering may not keep pace with the native toolkit's evolution.

// Example: platform-styled button using Capacitor's AppLauncher
// (For true native buttons, use the Action Sheet or Modal plugins)
import { Browser } from '@capacitor/browser';

async function openShareMenu() {
  // On iOS, this shows an action sheet; on Android, a context menu
  await Browser.open({
    url: 'https://example.com',
    presentationStyle: 'modal',
    toolbarColor: '#0b1020',
  });
}

Bridge overhead and performance

Every Capacitor API call crosses the JavaScript-native boundary via a serialized JSON payload. This serialisation — structured cloning — imposes a cost: primitive values pass through quickly, but objects and arrays require allocation and deserialisation on the receiving side. For high-frequency interactions (e.g. per-frame input, real-time sensor data), the bridge becomes a bottleneck. In these cases, consider direct native bridging, a WebAssembly module, or keeping the frequent logic entirely on the web side and using Capacitor only for the initial setup and occasional privileged operations.

// High-frequency call — avoid crossing the bridge in a loop
// Instead, expose a single native method that processes a batch of inputs

// Android (Kotlin): processes an array of sensor readings in one call
@PluginMethod
fun processReadings(call: PluginCall) {
    val readings = call.getFloatArray("readings") ?: emptyArray()
    val results = mutableListOf()
    for (r in readings) {
        results.add(nativeFilter(r))
    }
    call.resolve(mapOf("results" to results.toFloatArray()))
}

// iOS (Swift): same pattern
@objc func processReadings(_ call: CAPPluginCall) {
    guard let readings = call.array("readings") as? [Float] else {
        call.resolve(nil)
        return
    }
    var results = [Float]()
    for r in readings {
        results.append(nativeFilter(r))
    }
    call.resolve(["results": results])
}

// JavaScript wrapper
async function batchProcess(values: number[]): Promise {
    const { results } = await Plugin.processBatch({ readings: values });
    return results;
}

Plugin ecosystem maturity

Capacitor's first-party plugin set covers the most common native needs — camera, geolocation, push notifications, splash screen, status bar, and file system. For anything beyond these, you will encounter a mix of community plugins, some of which are unmaintained or forked. Before committing to Capacitor for a feature, verify the plugin: has recent releases, supports the Capacitor version you are using, and works on both iOS and Android. If no plugin exists, the cost of writing a custom plugin (chapter 7) should be weighed against the benefits — for a one-off native interaction, dropping down to a native file in the platform project (chapter 8) may be simpler than publishing a full package.

Choose Capacitor when your team is web-first, you want a single codebase, you need to ship frequently, and your app is form-and-content shaped. Choose React Native when you need a large pre-built component ecosystem or complex native lists. Choose Flutter when graphics-heavy UI, animation quality or a shared engine across three platforms matters more than your existing web skills.

1.4 What Capacitor is genuinely bad at

The four workloads where a web view will feel wrong no matter how much you optimise, and what to do instead.

High-frequency canvas and 3D rendering

A web view runs on the same main thread as your application logic. While it is capable of rendering 2D and even basic 3D graphics, the compositor thread and the JavaScript thread share resources. A sustained 60 FPS frame budget of 16.7 ms per frame is rarely achievable when the web view must also handle layout, garbage collection, and bridge crossings. Games that rely on per-frame physics, WebGL2 contexts, or canvas pixel manipulation will experience jitter, dropped frames, and eventually animation stalls. If your application requires continuous high-throughput rendering, offload the rendering pipeline to a native view (Metal, OpenGL ES, or Vulkan) via a custom plugin, or use a dedicated game engine that can manage its own thread scheduling and present directly to the surface without a web view wrapper.

// Example: checking if your render loop will bottleneck
// Measure real frames per second on a device, not a desktop browser

const frameTimes = [];
function renderFrame(start) {
  const end = performance.now();
  frameTimes.push(end - start);
  if (frameTimes.length > 60) frameTimes.shift();
  const avg = frameTimes.reduce((a, b) => a + b, 0) / frameTimes.length;
  if (avg > 15) {
    console.warn('Frame budget exceeded:', avg.toFixed(2), 'ms');
  }
  requestAnimationFrame(renderFrame);
}
requestAnimationFrame(renderFrame);

// If average frame time consistently exceeds 16ms, consider:
// 1. Reducing overdraw and texture sizes
// 2. Moving the loop to a native view (see chapter 8)
// 3. Using a game engine instead of a web view

Very long scrolling feeds with rich media

DOM recycling is effective for dozens of list items, but once you approach thousands of entries, memory pressure becomes the limiting factor. Each visible with a decoded bitmap holds width × height × 4 bytes in RAM. A gallery of 10,000 thumbnails, each at 400 × 300 pixels, consumes approximately 480 MB of decoded image data if all are loaded simultaneously. Even with loading="lazy", the browser must keep references to detached elements, and the garbage collector may pause the main thread during cleanup. Virtualisation libraries (such as react-virtual or zen-columns) only render the visible window, but Capacitor's web view still carries the overhead of the full DOM tree. For feeds this size, go native or implement heavyweight virtualisation with Canvas or Metal backends.

// Lightweight virtualisation pattern
// Only render items visible in the viewport + buffer

const ITEM_HEIGHT = 80;
const VIEWPORT_HEIGHT = window.innerHeight;
const BUFFER = 2;

function computeVisibleRange(items, scrollTop) {
  const totalHeight = items.length * ITEM_HEIGHT;
  const startIndex = Math.max(0, Math.floor((scrollTop - BUFFER * ITEM_HEIGHT) / ITEM_HEIGHT));
  const endIndex = Math.min(
    items.length - 1,
    Math.ceil((scrollTop + VIEWPORT_HEIGHT + BUFFER * ITEM_HEIGHT) / ITEM_HEIGHT)
  );
  return { startIndex, endIndex };
}

// Usage in your render function
function renderList(items, scrollTop) {
  const { startIndex, endIndex } = computeVisibleRange(items, scrollTop);
  const visibleItems = items.slice(startIndex, endIndex + 1);
  return visibleItems.map((item, i) => renderItem(item, i + startIndex));
}

Background work that must not be killed

JavaScript timers — setTimeout, setInterval, and fetch promises — are cancelled as soon as the application enters the background. The operating system suspends the web view process, and any in-flight timers are lost. If your application requires work to continue while backgrounded (such as playing audio, syncing a local database, or keeping a WebSocket alive), you must use platform-native mechanisms. On iOS, use BGAppRefreshTask or fetch silent pushes. On Android, use WorkManager or a foreground service with an ongoing notification. JavaScript cannot reliably schedule work that survives suspension, and attempting to do so will lead to missed deadlines and data inconsistency.

// DO NOT rely on this in the background — it will not work
setInterval(() => syncData(), 60_000); // suspended when app goes background

// DO use native background mechanisms instead
// iOS: BGAppRefreshTask (see chapter 10)
// Android: WorkManager (see chapter 10)

// Example: scheduling periodic sync with WorkManager
// (registered in the native project, not from JavaScript)

/* Kotlin (Android)
class SyncWorker : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        syncData()
        return Result.success()
    }

Complex text input and IME

Rich text editing, custom IME (Input Method Editor) workflows, and text fields with complex gesture handling are the weakest area of the web view. The native text engine is capable and standards-compliant, but input method coordination — such as composing characters with diacritics, handling prediction and autocorrect, and managing cursor movement via touch — often breaks down when the web view sits between the native keyboard and your application logic. Double-byte input, right-to-left scripts, and voice input all require careful platform bridging. If your application depends on precise text input, test on both platforms and consider whether a native text input component or a dedicated library is required.

// Feature-detect for IME support
// Check whether the native platform supports composition events

function supportsComposition() {
  return 'CompositionEvent' in window || typeof document.oncompositionstart !== 'undefined';
}

// Handle composition events for Japanese/Korean input
textInput.addEventListener('compositionstart', (e) => {
  isComposing = true;
  compositionBuffer = '';
});

textInput.addEventListener('compositionend', (e) => {
  isComposing = false;
  // Process the completed composition
  if (compositionBuffer.length > 0) {
    console.log('Composition completed:', compositionBuffer);
  }
});

// Important: also listen for input events, as compositionend
// may not fire in all browser/engine combinations
textInput.addEventListener('input', (e) => {
  if (!isComposing) {
    // Real-time input handling when not composing
    console.log('Input value:', e.target.value);
  }
});

Common pitfalls and debugging

The most frequent failure mode is running npx cap add android before the first build, which results in an empty assets/public/ folder and a blank white screen on app launch. The second frequent failure is changing webDir after platforms have been added, which requires a full npx cap sync to take effect. A third, more subtle issue is having webDir point at a relative path that resolves differently on different machines — always use a path relative to the project root, and avoid symlinks or absolute paths unless absolutely required.

// capacitor.config.ts
import type { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'com.example.app',
  appName: 'My App',
  webDir: 'dist',            // <- the BUILT folder, relative to project root
};

export default config;

If webDir points at a source folder, a stale folder, or a path that does not exist, you will see a blank white screen with no error in the console. The single most common first-run failure is running npx cap add android before the first build, so the folder is empty. Always build first, then sync.

# the loop, and the order matters
npm run build          # emit ./dist
npx cap sync           # copy ./dist into ios/ and android/, install plugins

# or let the CLI do both
npx cap sync --deployment   # for a release build

Two schemes are supported for webDir: a plain relative path, and an absolute path. Relative is right for almost everyone, because it keeps the native projects portable between machines. The native project actually points at the source folder on disk during development, which is why live reload works without a copy step - see chapter 6.

2.4 Environment switching

Keeping development, staging and production builds apart without three separate repositories.

Capacitor resolves configuration from a single file, but nothing stops you making that file dynamic. The usual pattern is a named environment, injected as a compile-time constant or an environment variable.

// capacitor.config.ts
import type { CapacitorConfig } from '@capacitor/cli';

const env = process.env.APP_ENV ?? 'development';

const config: CapacitorConfig = {
  appId: env === 'production' ? 'com.acme.app' : 'com.acme.app.dev',
  appName: env === 'production' ? 'Field Notes' : 'Field Notes Dev',
  webDir: 'dist',
  server: {
    // only in dev/staging: point at the dev server
    url: env === 'production' ? undefined : 'http://192.168.1.50:5173',
    cleartext: env !== 'production',
  },
};

export default config;
// package.json
"scripts": {
  "dev": "vite",
  "build": "vite build",
  "build:staging": "APP_ENV=staging vite build",
  "android:dev": "APP_ENV=development cap run android --livereload",
  "android:prod": "APP_ENV=production cap run android"
}

Using a different appId per environment is what lets a dev build and a production build live on the same phone side by side. If they share an id, installing one overwrites the other and you lose your local data every time you switch.

2.5 Loading a live dev server

Points the native shell at your laptop dev server so edits appear without a rebuild, and explains the networking trap you will hit immediately.

For day-to-day development you do not want to rebuild the bundle after every edit. Setting server.url makes the web view load from a real server instead of the packaged assets.

const config: CapacitorConfig = {
  appId: 'com.acme.app',
  appName: 'Field Notes',
  webDir: 'dist',
  server: {
    url: 'http://192.168.1.50:5173',   // your machine on the LAN
    hostname: '192.168.1.50',
    androidScheme: 'http',
  },
};

The device cannot see localhost on your laptop. On the device, localhost means the device itself. Use your machine's LAN IP. If the app shows a connection error, check: (1) the IP is right, (2) the dev server is bound to 0.0.0.0 not 127.0.0.1, and (3) your firewall allows the port. Vite needs --host 0.0.0.0 to accept connections from other machines.

# vite.config.js

  server: {
    host: '0.0.0.0',   // required so the phone can reach it
    port: 5173,
    strictPort: true,    // fail loudly instead of silently moving to 5174
  },
};

On the iOS simulator, localhost does work because the simulator shares the host network stack. On a physical device it never does, and on the Android emulator 10.0.2.2 is the standard alias for the host machine.

// which URL to use where

Android emulator   -> http://10.0.2.2:5173
Physical device    -> http://<your-LAN-IP>:5173

3.3 How plugins work in a browser

Why your PWA does not explode when it imports a native plugin, and how to branch on the platform properly.

Every official plugin ships a web implementation. On a browser it either works through an existing web API, or it throws "not implemented on web". That means a single codebase can run in a browser for development and on a device for production, as long as you guard the calls that need native.

import { Capacitor } from '@capacitor/core';
import { Camera } from '@capacitor/camera';

async function pickAvatar() {
  if (!Capacitor.isNativePlatform()) {
    // in a browser: fall back to a plain file input
    const input = document.createElement('input');
    input.type = 'file';
    input.accept = 'image/*';
    input.click();
    return;
  }
  const photo = await Camera.getPhoto({
    quality: 90,
    resultType: CameraResultType.Uri,
  });
  return photo.webPath;
}

// also useful
Capacitor.getPlatform();   // 'ios' | 'android' | 'web'
Capacitor.isNativePlatform();
Capacitor.isPluginAvailable('Camera');

Feature-detect with Capacitor.isPluginAvailable(name) rather than platform-sniffing where you can. Checking getPlatform() === 'android' to decide whether the Camera exists will break the moment a web fallback lands.

3.4 Events and listeners

The listener lifecycle, why cleanup is mandatory, and the pattern that survives hot reloads.

Listeners are held on the native side and keep firing until removed. If you register one on every render or every route entry without removing it, you get duplicate callbacks and a memory leak that only shows up as the app getting slower the longer it is open.

// WRONG: registers a new listener on every call, never cleans up
async function init() {
  App.addListener('appStateChange', ({ isActive }) => {
    console.log('active:', isActive);
  });
}

// RIGHT: keep the handle, remove it deterministically
import type { PluginListenerHandle } from '@capacitor/core';

let handle: PluginListenerHandle | undefined;

export async function watchAppState() {
  handle = await App.addListener('appStateChange', ({ isActive }) => {
    if (isActive) refreshData();
    else persistDraft();
  });
}

export async function unwatchAppState() {
  await handle?.remove();
  handle = undefined;
}
// in a framework, tie it to the component lifecycle
onMounted(watchAppState);
onUnmounted(unwatchAppState);   // the step people skip

4 · Permissions

4.1 Requesting permissions4.2 Handling the answer4.3 The permission prompt taxonomy4.4 iOS Info.plist strings4.5 Android manifest entries

A permission you never request is a permission you never get, and a permission you request at the wrong moment costs you the user permanently. This chapter covers both platforms' models and the UX that surrounds them.

4.1 Requesting permissions

Checking and requesting on both platforms, and why the check must come first.

import { Camera } from '@capacitor/camera';
import { Geolocation } from '@capacitor/geolocation';
import { PushNotifications } from '@capacitor/push-notifications';

// iOS: the plugin itself prompts
const camState = await Camera.checkPermissions();
// -> 'granted' | 'denied' | 'prompt' | 'prompt-with-rationale'
let cam = camState.camera;
if (cam !== 'granted') {
  cam = await Camera.requestPermissions();
}

// Android 13+ splits "ask" from the dangerous permissions themselves
const locState = await Geolocation.checkPermissions();
if (locState.location !== 'granted') {
  const asked = await Geolocation.requestPermissions();
  if (asked.location === 'denied') {
    await Geolocation.openSettings();   // deep-link to the app settings page
  }
}

// Push notifications are async-registered even on iOS
await PushNotifications.requestPermissions();
await PushNotifications.register();

Always call checkPermissions() before requestPermissions(). On Android, calling request without checking can trigger a double dialog on some OEM skins, and on iOS it re-prompts after a denial, which the system will not show again.

4.2 Handling the answer

The three states that are not a straight yes/no, and the UI each one demands.

type Decision = 'granted' | 'denied' | 'blocked' | 'ask-later';

function decide(state: string): Decision {
  if (state === 'granted') return 'granted';
  // iOS 'denied' after the first ask == the user blocked us in Settings
  if (state === 'denied') return 'blocked';
  // 'prompt-with-rationale' means iOS will still show a dialog, but
  // you MUST explain why first, or the app is usually rejected
  return state === 'prompt-with-rationale' ? 'ask-later' : 'ask-later';
}
async function ensureLocation(): Promise<boolean> {
  const { location } = await Geolocation.checkPermissions();
  if (location === 'granted') return true;

  if (location === 'prompt-with-rationale') {
    const ok = await showRationale(
      'Location improves your route history',
      'We use your position only while recording a trip.'
    );
    if (!ok) return false;
  }

  const asked = await Geolocation.requestPermissions();
  if (asked.location === 'granted') return true;

  if (asked.location === 'denied') {
    await showSheet(
      'Location is off',
      'Enable it in Settings to record routes.',
      ['Open Settings'],       // -> Geolocation.openSettings()
      ['Not now']
    );
  }
  return false;
}

There is a permanent difference between the platforms that shapes your whole permission UX. On iOS, once the user taps Deny, the app can never show that dialog again - the only path is Settings, which most users will not find. On Android, a user can be asked again, but the system stops showing your dialog after two or three refusals. Design so the app is fully usable when the answer is no, always.

4.5 Android manifest entries

The manifest permissions, the runtime-only ones, and the Android 13+ split that catches people out.

<!-- android/app/src/main/AndroidManifest.xml -->
<manifest xmlns:android="http://schemas.android.com/apk/res/android">

    <!-- normal permissions: granted at install, no dialog -->
    <uses-permission android:name="android.permission.INTERNET" />
    <uses-permission android:name="android.permission.VIBRATE" />

    <!-- dangerous permissions: must be requested at runtime -->
    <uses-permission android:name="android.permission.CAMERA" />
    <uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
    <uses-permission android:name="android.permission.RECORD_AUDIO" />

    <!-- Android 13+ : this replaced WRITE_EXTERNAL_STORAGE -->
    <uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
    <uses-permission android:name="android.permission.READ_MEDIA_VIDEO" />
    <!-- for anything not in the media set -->
    <uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE"
        android:maxSdkVersion="32" />

    <!-- declare hardware you need, so you can filter on the store -->
    <uses-feature android:name="android.hardware.camera" android:required="false" />

    <application android:label="@string/app_name" ...>
    </application>
</manifest>

Permissions that are only needed for a specific OS version use maxSdkVersion to avoid asking users of newer versions for legacy access. That is why READ_EXTERNAL_STORAGE above is capped at API 32.

Add android:required="false" to uses-feature for cameras and location. Without it your app is hidden from devices that lack the hardware, which quietly costs you installs. If you also provide a web build or a manual-entry path, required="false" is correct.

5.1 Camera and photo library

Capturing and picking images, and the result-type decision that determines your memory usage.

import { Camera, CameraResultType, CameraSource } from '@capacitor/camera';

async function capture() {
  const photo = await Camera.getPhoto({
    quality: 80,                        // 0-100; above 90 the file gets huge
    allowEditing: true,                 // native crop UI
    targetWidth: 1600,                  // native downscale - do it here, not in JS
    targetHeight: 1600,
    resultType: CameraResultType.Uri,   // a file:// path, no memory cost
    source: CameraSource.Prompt,        // let the user pick camera or library
    correctOrientation: true,
    saveToGallery: false,
  });
  return photo.webPath;   // e.g. file:///data/user/0/.../capacitor-captured.jpg
}

// displaying it: the webPath works directly in <img src>
// element.src = photo.webPath;
// result types, and when each one is right
//
// Uri      -> a file path. Use this. Zero memory cost.
//            Only valid while the file exists in the app sandbox.
//
// Base64   -> a string. Use for small thumbnails you must POST
//            immediately, or send to a WebSocket. ~33% larger
//            than the binary, and the whole thing lives in RAM.
//
// DataUrl  -> "data:image/jpeg;base64,..." - same cost as Base64
//            plus the prefix. Convenient, never efficient.

Do the resizing with targetWidth/targetHeight so the native side downsamples while decoding. Reading a 12-megapixel photo into an <img> and shrinking it with CSS keeps the full-resolution bitmap in memory and is a reliable way to get killed on a low-end Android device.

5.3 Preferences and secure storage

Three tiers of storage and the rule for choosing between them.

import { Preferences } from '@capacitor/preferences';

// 1. Preferences: small settings, synchronous feel, plain text on disk
await Preferences.set({ key: 'theme', value: 'dark' });
const { value } = await Preferences.get({ key: 'theme' });

// 2. Secure storage: tokens and secrets, backed by Keychain / Keystore
import { SecureStoragePlugin } from '@aparajita/capacitor-secure-storage';
const Secure = new SecureStoragePlugin();
await Secure.set({ key: 'refresh_token', value: token });

// 3. A real database: anything relational, queryable or large
//    -> IndexedDB / SQLite, see 5.4
// the rule
//
// Preferences     -> theme, locale, last-opened-screen, feature flags.
//                   Small, non-sensitive, read at startup.
// SecureStorage   -> access tokens, refresh tokens, API keys, biometric
//                   unlock keys. Never in Preferences, never in
//                   localStorage, never in a SQLite file unencrypted.
// Database        -> records. Users, posts, offline queue, search index.

localStorage and Preferences are both plain text inside the app sandbox. On a jailbroken or rooted device, or from a backup, the contents are readable. Refresh tokens in localStorage is the single most common way app credentials leak.

5.4 A local database that works offline

IndexedDB from the standard library, an offline write queue, and conflict handling you can reason about.

// db.ts - a small promise wrapper over IndexedDB
const DB_NAME = 'fieldnotes';
const DB_VERSION = 1;
const STORES = ['entries', 'outbox', 'meta'] as const;

export function openDb(): Promise<IDBDatabase> {
  return new Promise((resolve, reject) => {
    const req = indexedDB.open(DB_NAME, DB_VERSION);
    req.onupgradeneeded = () => {
      const db = req.result;
      for (const name of STORES) {
        if (!db.objectStoreNames.contains(name)) {
          db.createObjectStore(name, { keyPath: 'id' });
        }
      }
    };
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}

export async function put<T>(store: string, value: T): Promise<void> {
  const db = await openDb();
  return new Promise((resolve, reject) => {
    const tx = db.transaction(store, 'readwrite');
    tx.objectStore(store).put(value);
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  });
}

export async function all<T>(store: string): Promise<T[]> {
  const db = await openDb();
  return new Promise((resolve, reject) => {
    const req = db.transaction(store, 'readonly').objectStore(store).getAll();
    req.onsuccess = () => resolve(req.result as T[]);
    req.onerror = () => reject(req.error);
  });
}
// offline-first writes: local first, then queue, then sync
type Entry = { id: string; body: string; updatedAt: number; synced: boolean };

export async function saveEntry(entry: Entry) {
  const local = { ...entry, updatedAt: Date.now(), synced: false };
  await put('entries', local);                        // 1. instant, local
  await put('outbox', {                             // 2. queue for later
    id: local.id,
    op: 'upsert',
    payload: local,
    queuedAt: Date.now(),
  });
  void flushOutbox();                                 // 3. best effort
  return local;
}

export async function flushOutbox() {
  const queue = await all<any>('outbox');
  for (const job of queue.sort((a, b) => a.queuedAt - b.queuedAt)) {
    try {
      const res = await fetch(`/api/entries/${job.id}`, {
        method: 'PUT',
        headers: {
          'content-type': 'application/json',
          'if-match': job.payload.version ?? '',
        },
        body: JSON.stringify(job.payload),
      });
      if (res.status === 409) {
        await resolveConflict(job);   // server has a newer version
      } else if (!res.ok) {
        break;                       // keep order, retry the whole queue
      }
      await remove('outbox', job.id);
    } catch {
      return;                        // offline: leave it queued
    }
  }
}

The if-match header with a version is what turns a silent overwrite into a detectable conflict. Send a version you last saw; the server answers 409 Conflict if it has moved on. Then you choose a resolution strategy - last-write-wins, keep-both, or ask the user.

7 · Writing a Custom Plugin

7.1 Why write a plugin7.2 The JavaScript side7.3 The iOS side in Swift7.4 The Android side in Kotlin7.5 Packaging a plugin for your own project7.6 Calling JavaScript from native

When no plugin exists, you write one. This chapter takes a small plugin from an empty folder to working native code on both platforms, and shows how to call back into JavaScript.

7.1 Why write a plugin

The decision criteria, and the three options ranked by cost.

Write a custom plugin when the feature needs an OS API that no plugin wraps, when an existing plugin is unmaintained and its native code is small, or when you want a thin performance-critical path. In order of preference, try:

  1. An official @capacitor/* plugin.
  2. A maintained community plugin.
  3. A small amount of native code in the platform project, reached with a minimal custom plugin (chapter 8 covers the shortcut).
  4. A full custom plugin package if you need to share it across projects or teams.

A rule of thumb: if the native side is under about 150 lines and used by one project, keep it in the platform project. If it is larger, or a second app will need it, make it a proper package. Premature packaging costs you more than it saves.

7.3 The iOS side in Swift

The plugin class, the method table that maps JavaScript names to Swift methods, and the options struct.

// ios/Sources/VibrationPlugin/VibrationPlugin.swift
import Foundation
import Capacitor
import UIKit

@objc(VibrationPlugin)
public class VibrationPlugin: CAPPlugin, CAPBridgedPlugin {
    public let identifier = "VibrationPlugin"
    public let jsName = "Vibration"
    public let pluginMethods: [CAPPluginMethod] = [
        CAPPluginMethod(name: "vibrate", returnType: CAPPluginReturnPromise),
        CAPPluginMethod(name: "isSupported", returnType: CAPPluginReturnPromise),
    ]

    @objc func vibrate(_ call: CAPPluginCall) {
        let style = call.getString("style") ?? "medium"
        let count = call.getInt("count") ?? 1

        let feedback: UINotificationFeedbackGenerator
        switch style {
        case "light":
            feedback = UINotificationFeedbackGenerator()
            feedback.notificationOccurred(.warning)
        case "heavy":
            feedback = UINotificationFeedbackGenerator()
            feedback.notificationOccurred(.error)
        default:
            feedback = UINotificationFeedbackGenerator()
            feedback.notificationOccurred(.success)
        }

        for i in 0..<max(count, 1) {
            DispatchQueue.main.asyncAfter(deadline: .now() + 0.12 * Double(i)) {
                feedback.prepare()
            }
        }

        call.resolve()          // must be called exactly once
    }

    @objc func isSupported(_ call: CAPPluginCall) {
        // every iPhone has a taptic engine; iPads may not
        let supported = UIDevice.current.userInterfaceIdiom == .phone
        call.resolve(["supported": supported])
    }
}

A CAPPluginCall must be resolved or rejected exactly once. Resolve it twice and the bridge throws; never resolve it and the JavaScript promise hangs forever with no error. If your native work is asynchronous, hold the call and resolve it from the completion handler, keeping a strong reference to it in between.

7.4 The Android side in Kotlin

The plugin class, the annotation that registers it, and the call object API.

// android/src/main/java/com/acme/vibration/VibrationPlugin.kt
package com.acme.vibration

import android.content.Context
import android.os.Build
import android.os.VibrationEffect
import android.os.Vibrator
import com.getcapacitor.JSObject
import com.getcapacitor.Plugin
import com.getcapacitor.PluginCall
import com.getcapacitor.PluginMethod
import com.getcapacitor.annotation.CapacitorPlugin

@CapacitorPlugin(name = "Vibration")
class VibrationPlugin(private val context: Context) : Plugin() {

    @PluginMethod
    fun vibrate(call: PluginCall) {
        val style = call.getString("style") ?: "medium"
        val count = call.getInt("count") ?: 1

        val vibrator = context.getSystemService(Context.VIBRATOR_SERVICE) as? Vibrator
        if (vibrator == null || !vibrator.hasVibrator()) {
            call.reject("This device has no vibrator")
            return
        }

        val timings = LongArray(count) { 40L }
        val amplitudes = IntArray(count) {
            when (style) {
                "light" -> 80
                "heavy" -> 255
                else -> 160
            }
        }

        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
            vibrator.vibrate(VibrationEffect.createWaveform(timings, -1, amplitudes))
        } else {
            @Suppress("DEPRECATION")
            vibrator.vibrate(timings, -1)
        }

        call.resolve()
    }

    @PluginMethod
    fun isSupported(call: PluginCall) {
        val v = context.getSystemService(Context.VIBRATOR_SERVICE) as? Vibrator
        val ret = JSObject()
        ret.put("supported", v?.hasVibrator() == true)
        call.resolve(ret)
    }
}
// registering a custom plugin in MainActivity (only for in-project plugins)

7.6 Calling JavaScript from native

The reverse direction: notifying JavaScript from native code, and the thread rule that makes it work.

// iOS: notifyListeners from any thread, but resolve on the main thread
@objc func startTracking(_ call: CAPPluginCall) {
    self.tracking = true
    DispatchQueue.global().async { [weak self] in
        while self?.tracking == true {
            let steps = Int.random(in: 9000...11000)
            self?.notifyListeners("stepCount", data: ["steps": steps])
            Thread.sleep(forTimeInterval: 1.0)
        }
    }
    call.resolve()
}

@objc func stopTracking(_ call: CAPPluginCall) {
    self.tracking = false
    call.resolve()
}
// Android: the same, with an explicit thread hop for UI work
@PluginMethod
fun startTracking(call: PluginCall) {
    tracking = true
    executor.execute {
        while (tracking) {
            val steps = Random.nextInt(9000, 11000)
            val data = JSObject()
            data.put("steps", steps)
            notifyListeners("stepCount", data)
            Thread.sleep(1000)
        }
    }
    call.resolve()
}

private val executor = Executors.newSingleThreadExecutor()

notifyListeners is fire-and-forget: if JavaScript is not listening, the event is dropped. There is no queue and no replay. If a native event arrives before your listener is registered, you have missed it. Register listeners during app initialisation, not when a screen mounts.

8 · Native Code in the Platform Projects

8.1 When to drop to native code8.2 Adding a Swift file to the iOS project8.3 Adding a Kotlin file to the Android project8.4 Hooks: activity lifecycle and app events8.5 Threading rules in both platforms

The shortcut from chapter 7: add a Swift or Kotlin file to the native project and expose it, without packaging anything. This is the right move for one-off native work.

8.1 When to drop to native code

The decision, and the rule about keeping that code out of the sync path.

Native code inside the platform project is faster to write than a plugin package and perfectly legitimate, provided you commit it and understand that cap sync does not delete it. It only overwrites the web assets and the plugin directories.

Do not put native code inside android/app/src/main/assets/public/ or ios/App/App/public/. Those folders are overwritten on every copy, and your work will vanish. Native code belongs in the source folders, which is where it survives.

9.3 Back button and navigation

The Android back button is a contract with the user, and breaking it is an instant one-star review.

import { App } from '@capacitor/app';
import { Capacitor } from '@capacitor/core';

let router: { back: () => boolean } | undefined;

export async function initNavigation(nav: typeof router) {
   router = nav;
   if (!Capacitor.isNativePlatform()) return;

   await App.addListener('backButton', ({ canGoBack }) => {
     // 1. close whatever modal is open
     if (closeTopSheet()) return;
     // 2. let the router handle in-app history
     if (router?.back()) return;
     // 3. at the root: ask before quitting
     if (canGoBack) window.history.back();
     else confirmExit();
   });
}

let exitArmed = 0;
function confirmExit() {
  const now = Date.now();
  if (now - exitArmed < 2000) {
     App.exitApp();
     return;
  }
  exitArmed = now;
  toast('Press back again to exit');
}

Two common mistakes. Letting the default behaviour run means back skips your whole SPA history and drops the user at the launch screen. And calling App.exitApp() immediately at the root feels hostile - the double-tap-to-exit pattern above is what users expect from every other Android app.

9.5 Links, in-app browsers and external URLs

Deciding what opens in your app, what opens in a browser tab, and what leaves entirely.

// route by intent, before the browser tries to navigate the web view
const INTERNAL = new Set(['/dashboard', '/entry', '/settings']);

document.addEventListener('click', async (e) => {
  const a = (e.target as HTMLElement).closest('a');
  if (!a) return;
  const href = a.getAttribute('href') ?? '';

  if (href.startsWith('#') || INTERNAL.has(href)) return;   // router handles it

  e.preventDefault();
  if (href.startsWith('mailto:') || href.startsWith('tel:')) {
   location.href = href;                 // hand off to the OS
  } else if (/^https?:\/\//.test(href)) {
   if (new URL(href).hostname !== location.hostname) {
     await Browser.open({ url: href });   // external -> browser tab
   }
  }
}, true);

Without an intercept, tapping an external link navigates the web view away from your app and the user cannot get back. On iOS the return gesture sometimes works; on Android there is no back button inside a web view, so the app appears to hang. Intercept link clicks at the capture phase and route them deliberately.

10.3 Background tasks that survive suspension

Why your JavaScript interval stops, and the native mechanisms that do not.

This is the single most important constraint of a web-view app. When the app is backgrounded, the operating system suspends the web view, and every timer, interval and pending fetch simply stops. You cannot work around this from JavaScript.

// DOES NOT WORK in the background:
setInterval(() => sync(), 60_000);          // suspended
setTimeout(() => refresh(), 30_000);       // may never fire
await fetch('/api/sync');                  // killed mid-flight

// DOES work:
//  - scheduled local notifications (OS-owned timers)
//  - background fetch / silent push (see below)
//  - WorkManager on Android
//  - BGAppRefreshTask on iOS
//  - a foreground service, which the user must permit explicitly
// iOS: BGAppRefreshTask, declared in Info.plist
<key>BGTaskSchedulerPermittedIdentifiers</key>
<array>
  <string>com.acme.app.refresh</string>
  <string>com.acme.app.sync</string>
</array>
<key>UIBackgroundModes</key>
<array>
  <string>fetch</string>
  <string>processing</string>
  <string>remote-notification</string>
</array>
// iOS: register and schedule in AppDelegate
import BackgroundTasks

func application(_ application: UIApplication,
               didFinishLaunchingWithOptions o: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
    BGTaskScheduler.shared.register(
        forTaskWithIdentifier: "com.acme.app.refresh",
        using: nil
    ) { task in
        self.handleRefresh(task as! BGAppRefreshTask)
    }
    scheduleAppRefresh()
    return true
}

func scheduleAppRefresh() {
    let req = BGAppRefreshTaskRequest(identifier: "com.acme.app.refresh")
    req.earliestBeginDate = Date(timeIntervalSinceNow: 15 * 60)
    try? BGTaskScheduler.shared.submit(req)
}

func handleRefresh(_ task: BGAppRefreshTask) {
    scheduleAppRefresh()                 // always queue the next one
    task.expirationHandler = { /* cancelled: save state and bail */ }
    // do the native-side work here, NOT in the web view
    fetchPendingCount { count in
        UserDefaults.standard.set(count, forKey: "pending_count")
        task.setTaskCompleted(success: true)
    }
}
// Android: WorkManager, the right tool for deferrable work
// build.gradle: implementation "androidx.work:work-runtime-ktx:2.9.1"

import android.content.Context
import androidx.work.*
import java.util.concurrent.TimeUnit

object SyncScheduler {
    fun schedule(context: Context) {
        val constraints = Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .setRequiresBatteryNotLow(true)
            .build()

        val request = PeriodicWorkRequestBuilder<SyncWorker>(6, TimeUnit.HOURS)
            .setConstraints(constraints)
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.MINUTES)
            .build()

        WorkManager.getInstance(context)
            .enqueueUniquePeriodicWork("sync", ExistingPeriodicWorkPolicy.KEEP, request)
    }
}

class SyncWorker(ctx: Context, params: WorkerParameters) : CoroutineWorker(ctx, params) {
    override suspend fun doWork(): Result = try {
        val n = api.pushPendingEntries()
        Result.success(workDataOf("synced" to n))
    } catch (e: IOException) {
        Result.retry()             // backoff is applied automatically
    } catch (e: Exception) {
        Result.failure()
    }
}

On both platforms, the OS decides when background work runs. It may be hours late, it may be skipped entirely, and it may be batched. Design for the worst case: assume background execution is a bonus that improves freshness, never the mechanism that guarantees correctness. The source of truth is the local database, and the app reconciles when it is next opened.

10.5 Crash reporting and analytics

What to measure, what to avoid, and the consent rules that apply.

// A privacy-respecting, offline-first analytics approach
type Event = { name: string; props?: Record<string, string | number | boolean> };

const buffer: Event[] = [];

export function track(name: string, props?: Event['props']) {
  buffer.push({ name, props });
  if (buffer.length >= 50) void flush();
}

export async function flush() {
  if (!buffer.length) return;
  const batch = buffer.splice(0, buffer.length);
  try {
    await fetch('/api/events', {
      method: 'POST',
      body: JSON.stringify(batch),
      keepalive: true,
    });
  } catch {
    buffer.unshift(...batch);      // put it back, cap the buffer
    if (buffer.length > 500) buffer.length = 500;
  }
}

// flush on pause, so queued events leave with the app
import { App } from '@capacitor/app';
App.addListener('appStateChange', ({ isActive }) => { if (!isActive) void flush(); });

Two hard rules. Never send an event that contains personal data, precise location, or anything a user would be embarrassed to see leaked - you cannot delete what you have already transmitted. And if you track anything beyond aggregate usage, GDPR and CCPA require a lawful basis and, in some cases, explicit consent, with a working way to withdraw it.

Play requires an App Bundle (AAB), not an APK. The bundle lets Google generate per-device APKs, so you upload one artefact and each device receives only the native libraries and resources it needs - which is why native plugins add far less download size than the numbers suggest.

Lose the upload keystore and you can never update that app again without a Google support request. Lose the app signing key and the app must be removed and republished, losing your install base. Play Console now enrols you in Play App Signing, which holds the app signing key for you and uses your upload key only for uploads. That is the safe default: keep two keys, both in a password manager, both backed up.

12.3 Rendering and frame budget

The 16 ms budget, and the layout thrash pattern that silently destroys it.

// a frame must complete in 16.7ms for 60fps, 8.3ms for 120fps
// "layout thrash" is interleaving reads and writes of layout properties

// SLOW: read, write, read, write -> forces synchronous layout each time
for (const el of items) {
  const h = el.offsetHeight;      // READ  -> layout
  el.style.height = h * 2 + 'px'; // WRITE -> invalidate
  const w = el.offsetWidth;        // READ  -> layout again
  el.style.marginLeft = w + 'px'; // WRITE -> invalidate again
}

// FAST: all reads, then all writes -> one layout, one paint
const heights = items.map((el) => el.offsetHeight);
const widths  = items.map((el) => el.offsetWidth);
items.forEach((el, i) => {
  el.style.height = heights[i] * 2 + 'px';
  el.style.marginLeft = widths[i] + 'px';
});
// batch DOM writes inside a frame
function commit(changes: Array<[HTMLElement, Partial<CSSStyleDeclaration>]>) {
   requestAnimationFrame(() => {
     for (const [el, styles] of changes) Object.assign(el.style, styles);
   });
}

// never animate width/height/top/left: they trigger layout every frame
// animate transform and opacity: they are compositor-only
.sheet {
  transition: transform .25s ease, opacity .25s ease;  /* good */
  /* transition: height .25s;                          bad  */
  will-change: transform;   /* hint, only where it is actually animated */
}

On Android, hardware acceleration is on by default from API 11, but the layer count is not free. Each promoted layer costs memory. Use will-change: transform on an element for the duration of its animation and remove it afterwards; leaving it on permanently is a common source of memory bloat on low-end devices.

12.4 Memory and image handling

Why images kill mobile web apps, and the discipline that prevents it.

//   200 x  200  avatar  =  0.16 MB

// lazy load below the fold, and give the browser the dimensions up front
<img
  src="/api/thumb/abc123"
  srcset="/api/thumb/abc123?w=320 320w, /api/thumb/abc123?w=640 640w, /api/thumb/abc123?w=1280 1280w"

12.6 Network behaviour

Retries, timeouts, caching and what happens when the network is a mobile network.

// a fetch with no timeout hangs forever on a flaky mobile network
async function getJson<T>(url: string, init: RequestInit = {}, timeout = 8000): Promise<T> {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), timeout);
  try {
    const res = await fetch(url, { ...init, signal: ctrl.signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return (await res.json()) as T;
  } finally {
    clearTimeout(timer);
  }
}

// exponential backoff with jitter, and a hard attempt cap
async function withRetry<T>(fn: () => Promise<T>, attempts = 4): Promise<T> {
  let lastErr: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      lastErr = err;
      const base = Math.min(1000 * 2 ** i, 15_000);
      const delay = base * (0.5 + Math.random() * 0.5);  // jitter
      await new Promise((r) => setTimeout(r, delay));
    }
  }
  throw lastErr;
}

// cache with an explicit TTL, since a web view gives you no guarantees
const mem = new Map<string, { at: number; data: unknown }>();

async function cached<T>(key: string, ttl: number, fn: () => Promise<T>): Promise<T> {
  const hit = mem.get(key);
  if (hit && Date.now() - hit.at < ttl) return hit.data as T;
  const data = await fn();
  mem.set(key, { at: Date.now(), data });
  return data;
}

On mobile networks, latency is high and variable, and the connection can vanish without warning. A request that succeeds on wifi and times out on a train is normal, not exceptional. Always set a timeout, always retry with jittered backoff, and always show a state the user can act on rather than a spinner that never resolves.

A shipped app runs on untrusted devices with untrusted network. This chapter covers the specific risks a web-view app carries and the defences that matter.

13.1 No secrets in the bundle

The mistake that leaks API keys to everyone who unzips your app, and the pattern that replaces it.

// WRONG: a key in the bundle is readable by anyone who installs the app
const API_KEY = 'sk_live_51H8x...';      // shipped in dist/, and in the AAB

// RIGHT: the app authenticates as a USER, and the server holds the key
const res = await fetch('https://api.example.com/charge', {
  method: 'POST',
  headers: {
    'content-type': 'application/json',
    authorization: `Bearer ${await getAccessToken()}`,   // per-user token
  },
  body: JSON.stringify({ amount, currency }),
});
# unzapping an app bundle shows every string you shipped
unzip -p app-release.aab assets/*/index.html | grep -i "key\|secret\|token"

# and so does the iOS app
unzip -q MyApp.app -d /tmp/app
strings /tmp/app/www/assets/*.js | grep -i "sk_\|secret"

Everything in your JavaScript bundle is public. That includes API keys, client secrets, internal hostnames, feature flags and unreleased features. Rotate any key that has ever been in a shipped bundle, and design so there is no key to leak: the server talks to the third party using its own credentials, and the app is issued a user-scoped token.

13.2 TLS, cleartext and network security

Certificate pinning options, and the Android cleartext rules that break debug builds in confusing ways.

<!-- Android: a debug-only exception lives in src/debug/res/xml/network_security_config.xml -->
<network-security-config>
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="true">10.0.2.2</domain>
        <domain includeSubdomains="true">192.168.1.50</domain>
    </domain-config>
    <base-config cleartextTrafficPermitted="false" />
</network-security-config>

<!-- and reference it only in the debug manifest -->
<!-- android/app/src/debug/AndroidManifest.xml -->
<application android:networkSecurityConfig="@xml/network_security_config" />
<!-- certificate pinning, Android (network_security_config.xml) -->
<network-security-config>
    <domain-config cleartextTrafficPermitted="false">
        <domain includeSubdomains="true">api.example.com</domain>
        <pin-set expiration="2027-01-01">
            <pin digest="SHA-256">BASE64_ENCRYPTED_SPKI_HASH==</pin>
            <!-- keep a backup pin: you WILL rotate the key at some point -->
            <pin digest="SHA-256">BASE64_BACKUP_SPKI_HASH==</pin>
        </pin-set>
    </domain-config>
</network-security-config>

Pinning without a backup pin is a self-inflicted outage. The moment the certificate rotates - and it will - every installed copy of your app stops talking to the server, and users cannot fix it. Always configure at least two pins, and only pin hosts you control completely. A third-party domain you do not control should never be pinned.

13.4 Validating everything at the boundary

Why client-side validation is a UX feature and never a security control.

// client: good UX, fast feedback, not security
const form = document.querySelector('form')!;
form.addEventListener('submit', (e) => {
  e.preventDefault();
  if (!form.checkValidity()) { form.reportValidity(); return; }
  void send(new FormData(form));
});

// server: the ONLY place validation counts
// every field, every time, regardless of what the client did

// and never trust identifiers from the client
//   req.body.userId  -> ignore; take it from the verified token
//   req.params.id    -> check it belongs to that user before using it

Every value the app sends is attacker-controlled. The app can be modified, its requests replayed, and its bundle patched. Authorisation is a server concern, always evaluated from the authenticated identity, never from a field the client supplied. An IDOR - fetching another user's record because the client asked for that id - is the most common serious vulnerability in this whole category of app.

13.5 Logging without leaking

Debug logging that is safe in a release build, and what never to log at all.

// redact anything that looks like a credential before it goes anywhere
const SENSITIVE = /(token|password|secret|authorization|cookie|otp|pin|card)/i;

}

14.3 Mocking the plugin layer

The key technique: replace the plugin proxy so tests never touch native code.

// test/mocks/capacitor.ts
import { vi } from 'vitest';
import { registerPlugin } from '@capacitor/core';

export function mockPlugins() {
  vi.mock('@capacitor/core', async () => {
    const actual = await vi.importActual<any>('@capacitor/core');
    return {
      ...actual,
      registerPlugin: (name: string) => fakeRegistry[name] ?? stub(name),
      Capacitor: { getPlatform: () => 'android', isNativePlatform: () => true },
    };
  });
}

const fakeRegistry: Record<string, unknown> = {
  Camera: {
    getPhoto: vi.fn().mockResolvedValue({
      webPath: 'file:///tmp/fake.jpg', format: 'jpeg', saved: false,
    }),
    checkPermissions: vi.fn().mockResolvedValue({ camera: 'granted' }),
    requestPermissions: vi.fn().mockResolvedValue({ camera: 'granted' }),
  },
  Preferences: {
    get: vi.fn().mockResolvedValue({ value: null }),
    set: vi.fn().mockResolvedValue(undefined),
  },
};

function stub(name: string) {
  return new Proxy({}, {
    get: () => vi.fn().mockRejectedValue(
      new Error(`${name} is not mocked in this test`),
    ),
  });
}

// setup.ts
mockPlugins();

The stub proxy is the part that pays for itself. Any test that accidentally calls an unmocked plugin fails loudly with a named error instead of hanging or silently passing. When a new plugin appears in production code, exactly one test tells you to add a mock.

Keep the device suite to a handful of flows that would be genuinely damaging if broken: launch, create-and-persist, permission-refused, and offline-behaviour. Everything else belongs in the fast mocked suite. A device suite that takes forty minutes will not be run, and a suite nobody runs catches nothing.

15.1 The blank white screen

The most common problem, with an ordered checklist that resolves most cases.

// CHECK IN THIS ORDER
//
// 1. is the web output actually there?
ls android/app/src/main/assets/public/index.html
ls ios/App/App/public/index.html
//    missing -> webDir is wrong, or you never built, or you never synced
//
// 2. is the base path right for a custom-scheme origin?
//    an absolute "/assets/x.js" works in dev and 404s in the app
//    vite.config.js:
//      base: "./"      <- relative, correct for Capacitor
//
// 3. is there a JS error at boot?
//    remote inspect (chapter 6) and read the console
//
// 4. does it render when you force the platform?
//    check a Capacitor.isNativePlatform() branch
//
// 5. white but the network tab shows requests -> a CSS problem
//    e.g. body { display:none } until JS boots, and JS threw
//
// 6. still nothing -> read the native logs
adb logcat | grep -iE "chromium|capacitor"
xcrun simctl spawn booted log stream --predicate 'process CONTAINS "WebKit"'
// the most common actual cause: absolute asset paths
// vite.config.js
export default {
  base: './',        // NOT '/' - the app loads over a custom scheme
  build: { target: 'es2019' },
};

15.2 Not implemented / plugin not found

Why a plugin reports unavailable, and the four reasons it happens.

// CapacitorError: "Camera" plugin is not implemented on ios
//
// 1. you added the JS package but never synced
npx cap sync            // <- the fix, 90% of the time
//
// 2. you synced but never rebuilt the native app
//    the native module is new; the installed binary does not have it
npx cap run ios
//
// 3. the plugin was removed from package.json but the native code remains
npm ls @capacitor/camera
npx cap sync
//
// 4. the jsName does not match the native registration
//    registerPlugin('Foo') requires a native class registered as "Foo"

Reading Gradle and Xcode errors, and the two that recur constantly.

// ANDROID: "Duplicate class com.getcapacitor.Plugin" or namespace errors
// -> a plugin was added twice, or a plugin's android project was
//    left in settings.gradle after removing the package
// fix: check android/settings.gradle includes list, then npx cap sync

// ANDROID: "Manifest merger failed : uses-sdk:minSdkVersion 21 cannot be smaller"

// iOS: code signing error

15.5 Android runtime issues

Cleartext traffic, WebView version, back button and notification icons.

// "CLEARTEXT communication to localhost not permitted"
// -> add cleartext:true to server config, or a debug network security config

// the app runs on an ancient WebView
// Capacitor requires a WebView with modern JS. The system WebView is
// updated via Play Store, but users disable updates.
adb shell dumpsys webviewupdate     // check the version in use
// guide users to update, or bundle a fixed WebView (adds ~60MB)

// back button exits instead of navigating
// -> you are not handling App.addListener('backButton') (chapter 9)

// notification shows a white square
// -> the small icon must be white-on-transparent, referenced by name only

// notification does not appear at all on Android 13+
// -> POST_NOTIFICATIONS not granted, and not declared in the manifest

15.6 iOS runtime issues

Crashes on permission use, the silent-push trap, and App Store rejections.

// crash the moment a plugin touches a protected API
// -> a missing NS*UsageDescription in Info.plist. Check first, always.

// silent push (content-available: 1) never arrives
// -> it is throttled, not delivered on a schedule. iOS decides.
//    never depend on it for correctness.

// content is hidden behind the notch or home indicator
// -> use env(safe-area-inset-*) (chapter 9)

// rejected: 2.1 App Completeness / broken links
// -> the demo account you gave the reviewer stopped working
// -> keep the review account alive until the review is finished

// rejected: 5.1.1 Data Collection and Storage
// -> the privacy questionnaire must cover every plugin that
//    touches data, not just the code you wrote yourself

// rejected: 3.2.2
// -> an OTA update changed functionality. OTA is for content only.

// rejected: 4.2 Minimum Functionality
// -> a web-view app that is only a link, or has no real native capability
//    and no offline support, can be rejected. Use the native features.

15.7 Web-side issues

Origin, storage, cookies and service-worker behaviour inside the app's custom scheme.

// localStorage / IndexedDB behave differently than you expect
// the origin is https://localhost (iOS) or http://localhost (Android)
// which is DIFFERENT from the same app viewed in a browser, and
// different again if you change androidScheme. Data does not migrate.

// cookies are not shared with the Safari browser
// -> a web session started in Safari is not visible to the app.
//    Handle auth in-app, or use a token in secure storage.

// a service worker registered in the app serves stale content
// -> you already have native asset versioning via the bundle; a
//    service worker is redundant and a common source of confusion.
//    unregister it in the native build if you do not want it.

// fetch to a cross-origin API is blocked
// -> the app origin is not your API origin, so it is cross-origin.
//    Either serve the API with CORS for the capacitor:// origin, or
//    proxy through your own server. Same-origin APIs are far simpler.
