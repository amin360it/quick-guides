The right mindset: compiled reactivity

This section explains Svelte’s compile-time approach and why it ships no virtual DOM. Your code is compiled at build time into plain JavaScript that updates the DOM directly, so the framework largely disappears from what the browser actually runs. Understanding this model makes later topics such as reactive dependencies and scheduling easier to grasp.

Svelte is a compiler, not a runtime library. It reads your .svelte files during the build and produces tiny, imperative JavaScript that updates the DOM directly. There is no virtual DOM and no reconciliation pass — the framework mostly vanishes from your shipped bundle. That changes how you think: you write count = count + 1 and the compiler generates the code that moves exactly the DOM nodes that need to change.

Keep the official docs open beside this guide at svelte.dev/docs. This guide explains the why and the sequence; the docs are the exhaustive reference.

1 · Svelte Fundamentals & Setup

1.1 Why Svelte: compiler over runtime1.2 Scaffolding a project with Vite1.3 Anatomy of a .svelte file1.4 The dev loop and svelte-check

This chapter gets a working Svelte project running and explains why the compiler approach wins. You scaffold a project with Vite and then dissect your first .svelte file into its script, markup and style sections. By the end you have a dev server with hot reload and a production build on disk.

Svelte turns components into efficient imperative code at build time. This chapter gets a project running, explains the compiler philosophy, and walks through the three sections that make up every component.

1.1 Why Svelte: compiler over runtime

This section compares Svelte’s compile-time approach with runtime frameworks such as React and Vue. Because Svelte compiles away the framework, bundles stay smaller and less library code ships to the browser. The trade that matters is no virtual DOM, which means direct DOM updates arranged at build time instead of runtime reconciling.

Runtime frameworks ship a library that walks a virtual DOM and reconciles differences during execution. Svelte inverts the model: the compiler does that work once at build time and emits direct DOM operations. Every interaction is faster, downloads are smaller, and there is no framework to debug at run time.

// Counter.svelte — a complete first component
<script>
  let count = 0;             // plain JavaScript state, no hooks
  function increment() {
    count += 1;              // an assignment signals the update
  }
</script>

<button on:click={increment}>Clicks: {count}</button>
<style>button { font-weight: bold; }</style>

This component declares state as an ordinary variable and updates it with an assignment. The compiler turns it into direct DOM code that only touches the button’s text node.

1.2 Scaffolding a project with Vite

This section creates a new Svelte project with the official Vite scaffolder using npm. You take the generated files into a running dev server with hot reload, then run a build to produce static output on disk. The result is a working project you can open immediately and keep using for every later chapter.

# create the project: pick "Skeleton" and TypeScript if you want it
npm create svelte@latest my-app
cd my-app
npm install            # install dependencies once
npm run dev            # dev server with hot reload — http://localhost:5173
npm run build          # production bundle into dist/
npm run preview        # serve the production build locally

npm create svelte scaffolds a Vite-powered project, npm run dev serves it with instant hot reload, and npm run build emits a static production bundle into dist/.

1.3 Anatomy of a .svelte file

This section breaks a .svelte file into its three optional sections: the script block for logic, the markup for the template, and the style block for scoped CSS. Understanding this triad gives you the entire mental model used for the chapters ahead. Components, logic and styling all live inside a single file.

// Card.svelte — every component is up to three sections
<script>
  let title = 'Hello';      // 1. logic: state, props and functions
</script>

<h1>{title}</h1>            // 2. markup: HTML plus {expressions}

<style>                     // 3. styles: scoped to this component by default
  h1 { color: teal; }
</style>

A .svelte file is a single component with up to three blocks — script for logic, markup for the template, style for scoped CSS — and the compiler compiles all three into one self-contained piece.

1.4 The dev loop and svelte-check

This section adds svelte-check, the official type-checker for Svelte files, to the development loop. It validates templates and types at build time instead of in the browser, catching mistakes before you ship. Wiring it into npm scripts and your editor keeps every later chapter safer to work in.

# svelte-check reads every .svelte file for type and template errors
npm i -D svelte-check typescript

# during development
svelte-check --watch

# before a release or in CI
svelte-check && npm run build

svelte-check type-checks templates, props, bindings and imports, then reports problems in the terminal. Running it in CI makes broken templates fail the build.

2 · Reactivity & Components

2.1 Assignments trigger updates2.2 Reactive statements: the $: label2.3 Reactive declarations in order2.4 Components and instantiation

This chapter covers the heart of Svelte: assignment-based reactivity, reactive statements, and components as reusable units. A plain variable assignment triggers a component update, and imported components become tags in your markup. Everything else in this guide builds on these two ideas.

2.1 Assignments trigger updates

This section shows that assigning to a variable is the signal Svelte uses to know when to update the DOM. Because reactivity is triggered by assignment, array and object mutations must be followed by a reassignment to be seen. Compile-time tracking of those assignments is the core mechanism behind updates.

<script>
  let count = 0;
  let items = ['compile', 'update'];

  function bump() {
    count += 1;                       // reassigning a primitive: update fires
  }
  function add() {
    items = [...items, 'ship'];       // new array reference: update fires
    // items.push('ship') would NOT — mutation is invisible to reactivity
  }
</script>

<button on:click={bump}>count: {count}</button>
<button on:click={add}>items: {items.length}</button>

In Svelte the assignment is the signal. Mutating an array in place with push is not noticed; building a new reference with spread is, which is why the example reassigns.

Reassign, don’t mutate: prefer arr = [...arr, x] and obj = { ...obj, key: v } whenever your data must stay visible to reactivity.

2.2 Reactive statements: the $: label

This section introduces the dollar colon label, Svelte’s reactive statement. Svelte records which variables the statement reads and re-runs it automatically whenever any of them change. You use it to compute derived values and to run side effects that depend on reactive state.

<script>
  let base = 2;
  let exponent = 3;

  $: result = base ** exponent;     // recomputed when base or exponent changes
  $: console.log(result < 100 ? 'small' : 'big');   // side effects run too
</script>

<button on:click={() => base += 1}>raise base (now {base})</button>
<p>{base} ^ {exponent} = {result}</p>

The $: label marks a reactive statement. Both lines re-run whenever base changes because they read it, so results stay in sync without any manual wiring.

2.3 Reactive declarations in order

This section explains that reactive statements run in source order, before the markup updates. Chains of derived values therefore flow naturally from top to bottom, and each statement can rely on the results of the ones above it. Ordering your reactive statements correctly keeps derived state consistent.

<script>
  let price = 40;
  let qty = 2;

  $: subtotal = price * qty;    // 1st: recomputed first
  $: tax = subtotal * 0.1;      // 2nd: can read subtotal
  $: total = subtotal + tax;    // 3rd: final derived value
</script>

<button on:click={() => qty += 1}>add one</button>
<p>{qty} x 40 = {total}</p>

Reactive statements run in the order they appear, before the DOM updates. The chain subtotal, tax, total guarantees every value used downstream is already fresh.

2.4 Components and instantiation

This section shows how imported components become tags in your markup after an import. Each instance owns its own state, so the same component can appear many times on the page and stay fully independent. This encapsulation is exactly what makes components reusable units.

// Counter.svelte
<script>
  let n = 0;
</script>
<button on:click={() => n += 1}>{n}</button>

// App.svelte — import a component and use it as a tag
<script>
  import Counter from './Counter.svelte';
</script>

<main>
  <Counter />             // self-closing form
  <Counter></Counter>     // explicit closing form
</main>

Importing a component and writing it as a tag instantiates one independent copy per usage. Two Counter tags mean two counters, each with its own n.

3 · Props, Events & Bindings

3.1 Props: export let, defaults & spreading3.2 Custom events: createEventDispatcher & the on: directive3.3 Event forwarding3.4 Two-way bindings: value, checked & group3.5 bind:this and component bindings

This chapter covers how components communicate with each other. Props pass data down, custom events carry messages up, and bindings move data in both directions. This is the shared vocabulary of every component tree you build, so mastering it unlocks composition.

3.1 Props: export let, defaults & spreading

This section declares props with export let and gives them default values. Spreading a props object and using the $$restProps variable let a component accept unknown attributes without naming them at all. Props are the primary way a parent hands data down to its children.

// Greeting.svelte
<script>
  export let name = 'friend';     // a prop with a default value
  export let emphasis = false;    // boolean prop, defaults to false
</script>

<p>Hello {emphasis ? name.toUpperCase() : name}</p>

// App.svelte
<script>
  import Greeting from './Greeting.svelte';
</script>

<Greeting name="Ada" />
<Greeting name="Grace" emphasis />   // bare attribute means {true}
<Greeting />                          // falls back to 'friend'

export let declares a prop and its default. Parents pass values as attributes, a bare attribute like emphasis is shorthand for emphasis={true}, and omitted props keep their defaults.

// Button.svelte — pass through attributes you never declared
<script>
  export let color = 'blue';
  let classes = `btn btn-${color}`;
</script>

<button class={classes} {...$$restProps}>   // forward everything else
  <slot />
</button>

// App.svelte
<script>
  import Button from './Button.svelte';
</script>

<Button color="red" type="submit" id="save" aria-label="Save" />
// type, id and aria-label land in $$restProps and flow onto the real button

{...$$restProps} forwards every attribute the parent supplied that is not a declared prop, so Button accepts type, id and aria-* without declaring each one.

3.2 Custom events: createEventDispatcher & the on: directive

This section uses createEventDispatcher to dispatch custom events from a component and listens for them with the on directive. The payload you pass along always arrives on event.detail. This pattern lets children send messages up to parents without knowing who is listening.

// Clicker.svelte
<script>
  import { createEventDispatcher } from 'svelte';
  const dispatch = createEventDispatcher();

  let taps = 0;

  function tap() {
    taps += 1;
    dispatch('tap', { count: taps });   // custom event carrying a payload
  }
</script>

<button on:click={tap}>taps: {taps}</button>

// App.svelte
<script>
  import Clicker from './Clicker.svelte';

  function onTap(event) {
    console.log('received', event.detail.count);   // read the payload here
  }
</script>

<Clicker on:tap={onTap} />

createEventDispatcher creates a dispatch function, dispatch('tap', payload) raises a custom event, and the parent listens with on:tap. The payload is always read from event.detail.

3.3 Event forwarding

This section explains that component events do not bubble across component boundaries the way DOM events do. Writing an on directive with no handler re-dispatches the event so it can keep travelling upward. You forward events when an intermediate component needs to pass them through untouched.

// Counter.svelte — the origin of a custom event
<script>
  import { createEventDispatcher } from 'svelte';
  const dispatch = createEventDispatcher();
  let taps = 0;
  function tap() {
    taps += 1;
    dispatch('tap', taps);
  }
</script>
<button on:click={tap}>{taps}</button>

// Card.svelte — a middle component that just forwards
<script>
  import Counter from './Counter.svelte';
</script>

<div class="card">
  <Counter on:tap />    // forward: no handler, the event keeps climbing
</div>

// App.svelte — the listener, two levels up
<script>
  import Card from './Card.svelte';
  function onTap(e) { alert('total ' + e.detail); }
</script>
<Card on:tap={onTap} />

Component events do not bubble into parent markup automatically. Writing on:tap without a handler re-dispatches the event so a grandparent can handle it.

3.4 Two-way bindings: value, checked & group

This section shows how bind syncs a variable with a form field in both directions, so typing updates state and state updates the field. Checkbox groups collect their checked values into a single array. It also covers the standard bindings available on input, select and textarea elements.

<script>
  let name = '';
  let agreed = false;
  let tags = ['svelte'];          // checkbox group collects here
</script>

<input bind:value={name} placeholder="Your name">
<input type="checkbox" bind:checked={agreed}> I agree

{#each ['svelte', 'vite', 'typescript'] as tag}
  <label>
    <input type="checkbox" value={tag} bind:group={tags}> {tag}
  </label>
{/each}

<p>Hello {name} — {agreed ? 'signed' : 'not signed'} — {tags.join(', ')}</p>

bind:value syncs an input with a variable, bind:checked does the same for booleans, and bind:group on checkboxes gathers every checked value into the tags array.

3.5 bind:this and component bindings

This section stores a DOM element or a child component instance in a variable using bind:this. Once stored, you can call native methods such as focus and also call functions the child exports. This is the imperative escape hatch that stays inside the reactive model.

// Parent.svelte
<script>
  import Child from './Child.svelte';
  let inputEl;          // filled by bind:this once mounted
  let child;            // the component instance itself

  function focusIt() {
    inputEl.focus();        // native DOM element method
    child.setCount(99);     // function exported by the child component
  }
</script>

<input bind:this={inputEl}>
<button on:click={focusIt}>focus and set</button>
<Child bind:this={child} />

// Child.svelte
<script>
  let count = 0;
  export function setCount(n) { count = n; }   // callable by the parent
</script>
<p>child count: {count}</p>

bind:this stores the DOM element or component instance in a variable. For DOM nodes you get the native element; for components you get the instance and may call its exported functions.

4 · Logic Blocks

4.1 if, else if & else4.2 each blocks, indexes & keys4.3 await, then & catch4.4 Snippets & {@render}

This chapter covers the control-flow blocks you write directly inside markup. If blocks conditionally render branches, each blocks loop over arrays, await blocks handle promises, and snippets reuse chunks of template. They replace loops and conditionals with readable inline templates.

4.1 if, else if & else

This section renders one of several branches conditionally using if, else if and else. Exactly one branch exists in the DOM at any time, and Svelte keeps state inside active branches as long as they stay mounted. Use keys or placeholder elements when you need to preserve or reset that state.

<script>
  let score = 72;

  $: grade =
    score >= 90 ? 'A' :
    score >= 75 ? 'B' :
    score >= 60 ? 'C' : 'F';
</script>

{#if grade === 'F'}
  <p>Keep practising — you will get there.</p>
{:else if grade === 'C'}
  <p>Solid. Push for a B.</p>
{:else}
  <p>Nice work.</p>
{/if}

{#if} renders a branch when its condition holds, {:else if} chains another condition, and {:else} is the fallback. Only one branch is mounted at a time.

4.2 each blocks, indexes & keys

This section loops over arrays in markup with an each block, optionally exposing the index and a key. A keyed each block lets Svelte patch exactly the right row when items reorder instead of rebuilding the whole list. Keys matter for stable row state and for flip animations.

<script>
  let todos = [
    { id: 1, text: 'learn blocks' },
    { id: 2, text: 'keyed each' },
  ];

  function remove(id) {
    todos = todos.filter(t => t.id !== id);   // reassign so the block updates
  }
</script>

<table>
  {#each todos as todo, i (todo.id)}   // value, index, then key in parentheses
    <tr>
      <td>{i}</td>
      <td>{todo.text}</td>
      <td><button on:click={() => remove(todo.id)}>done</button></td>
    </tr>
  {/each}
</table>

Each block iterates with the value, an optional index i, and an optional key in parentheses. Keying by todo.id lets Svelte move and patch the exact row instead of rebuilding the list.

Always key each blocks that can reorder or be filtered. Without a key, Svelte reuses rows by position, which loses per-row state and animates badly.

4.3 await, then & catch

This section handles promises directly in markup with an await block and its then and catch branches. As the promise settles, the block switches between a pending branch, a resolved branch and a rejected branch. This keeps loading and error UI close to the data that needs it.

<script>
  let promise = fetch('/api/user').then(r => r.json());

  function reload() {
    promise = fetch('/api/user').then(r => r.json());   // restarts the block
  }
</script>

{#await promise}
  <p>Loading...</p>
{:then user}
  <p>Hello {user.name}</p>
{:catch error}
  <p>Could not load: {error.message}</p>
{/await}

<button on:click={reload}>retry</button>

{#await} watches a promise and swaps between three branches: pending, resolved ({:then}) and rejected ({:catch}). Reassigning the promise restarts the whole block.

4.4 Snippets & {@render}

This section reuses chunks of markup by declaring them with the snippet block and invoking them with the render tag. Snippets can accept arguments, so they behave like small template functions you can pass values into. This is the modern way to build reusable fragments inside a component.

<script>
  let planets = ['mercury', 'venus', 'earth'];
</script>

{#snippet row(item)}
  <li><strong>{item}</strong></li>
{/snippet}

<ul>
  {#each planets as p}
    {@render row(p)}    // invoke the snippet with this planet
  {/each}
</ul>

A snippet is reusable markup defined once and invoked with {@render}. Passing arguments keeps repeated row markup in one place instead of restating it inside every loop.

5 · Stores

5.1 writable stores & the $ prefix5.2 readable stores5.3 derived stores5.4 Custom stores & the store contract5.5 Context vs stores

This chapter shares state between components with stores, including the writable, readable and derived constructors. The dollar prefix subscribes a component automatically and unsubscribes it on unmount. Stores give you shared state that goes beyond what props and bindings can express.

5.1 writable stores & the $ prefix

This section creates a writable store with the writable function and accesses its subscribe, set and update methods. Reading it in a component with the dollar prefix handles subscribing and unsubscribing for you. Use this store wherever several components need the same live value.

// store/count.js
import { writable } from 'svelte/store';
export const count = writable(0);       // exposes { subscribe, set, update }

// CountPanel.svelte
<script>
  import { count } from './store/count.js';
</script>

<button on:click={() => count.update(n => n + 1)}>{$count}</button>
<button on:click={() => count.set(0)}>reset</button>
<p>Double: {$count * 2}</p>

writable creates a store with subscribe, set and update. In a component the $ prefix auto-subscribes and auto-unsubscribes, so $count always holds the live value.

5.2 readable stores

This section creates readable stores that other code can observe but never set from outside. The start function pushes values into the store and may return a cleanup for when the last subscriber goes away. Use readable for clocks, timers and other external data sources.

// store/clock.js
import { readable } from 'svelte/store';

export const clock = readable(null, (set) => {
  const id = setInterval(() => set(new Date()), 1000);   // push an update every second
  return () => clearInterval(id);   // cleanup runs when the last subscriber leaves
});

readable takes an initial value and a start function that can push new values with set. Its cleanup clears the interval once nobody is subscribed, so timers never leak.

5.3 derived stores

This section computes a store from one or more input stores using the derived function. The derived value recomputes automatically whenever any input changes, and the computation may be asynchronous. Use it to project shared state into the exact shape components need.

import { derived, writable } from 'svelte/store';

export const items = writable(3);
export const perItem = writable(10);

// sync derived: runs whenever any listed store changes
export const total = derived(
  [items, perItem],
  ([$items, $perItem]) => $items * $perItem,
);

// async derived: set() can be called later, e.g. from a fetch
export const label = derived(total, ($total, set) => {
  fetch('/label').then(r => r.text()).then(set);   // push when the data arrives
});

derived accepts one store or an array of stores. The callback recomputes when inputs change, and the two-argument form can set a value asynchronously via the set callback.

5.4 Custom stores & the store contract

This section wraps a writable store to expose a purpose-built API with methods such as increment instead of raw set and update calls. Because any object with a subscribe method is a store, the contract Svelte requires is minimal. Custom stores are the idiomatic way to give shared state a named interface.

// store/cart.js
import { writable } from 'svelte/store';

function createCart() {
  const { subscribe, set, update } = writable([]);

  return {
    subscribe,                    // the contract: subscribe is mandatory
    add: (item) => update(list => [...list, item]),
    remove: (id) => update(list => list.filter(i => i.id !== id)),
    clear: () => set([]),
  };
}

export const cart = createCart();

A store is simply any object with a subscribe method. Custom stores wrap writable and expose methods like cart.add(item), so components read intentions instead of raw updates.

5.5 Context vs stores

This section compares setContext and getContext with stores. Context is per-instance and scoped to a component tree, so different parts of an app can hold different values; stores are global singletons shared by every component. Choose context for dependency injection and stores for app-wide state.

// Panel.svelte — hand a value down the tree, not globally
<script>
  import { setContext } from 'svelte';
  import Child from './Child.svelte';

  setContext('theme', { mode: 'dark' });   // visible to this subtree only
  setContext('language', 'en');            // another key on the same element
</script>
<Child />

// Child.svelte — read it back wherever needed
<script>
  import { getContext } from 'svelte';
  const theme = getContext('theme');       // { mode: 'dark' }
  const lang = getContext('language');
</script>
<p>{lang}: theme is {theme.mode}</p>

// the global alternative: a store shared app-wide
<script>
  import { settings } from './store/settings.js';
</script>
<p>Applied: {$settings.mode}</p>   // any component, any depth

setContext makes a value available to every descendant component and getContext reads it back. Unlike stores it is per-instance — sibling subtrees keep their own copies — while stores share globally.

6 · Lifecycle & Scheduling

6.1 onMount & onDestroy6.2 beforeUpdate & afterUpdate6.3 tick & batching6.4 Actions & the use: directive

This chapter connects you to the moments a component lives through: mount, update and destroy. The onMount, onDestroy, beforeUpdate and afterUpdate functions cover each one. Balancing side effects with these hooks keeps listener registration and teardown in sync.

6.1 onMount & onDestroy

This section runs side effects once the component has been added to the DOM using onMount, and cleans them up when it leaves using onDestroy. Registering a listener in onMount and removing it in onDestroy is the classic pair. These functions are the right home for fetches, timers and subscriptions.

<script>
  import { onMount, onDestroy } from 'svelte';

  let width = 0;

  onMount(() => {
    width = window.innerWidth;                    // DOM is ready here
    const onResize = () => (width = window.innerWidth);
    window.addEventListener('resize', onResize);

    onDestroy(() => window.removeEventListener('resize', onResize));   // paired cleanup
  });
</script>

<p>Viewport: {width}px</p>

onMount runs once the component is in the DOM — the right place for side effects. onDestroy pairs with it for cleanup so removing the component never leaks an event listener.

6.2 beforeUpdate & afterUpdate

This section runs code just before and just after the DOM is patched using beforeUpdate and afterUpdate. afterUpdate is the home for imperative touches such as scrolling a chat log into view. These hooks let you observe and respond to every render cycle of the component.

<script>
  import { afterUpdate } from 'svelte';

  let messages = [];
  let list;

  afterUpdate(() => {
    list.scrollTo(0, list.scrollHeight);   // the DOM just patched — scroll to bottom
  });

  function send(text) {
    messages = [...messages, text];        // this assignment triggers afterUpdate
  }
</script>

<div class="chat" bind:this={list}>
  {#each messages as m}
    <p>{m}</p>
  {/each}
</div>

afterUpdate fires after every dispatch’s DOM patch — ideal for adjusting freshly rendered nodes, like keeping a chat pinned to the bottom. beforeUpdate is its mirror, running just before.

6.3 tick & batching

This section explains that Svelte batches DOM updates into a single flush per microtask. The tick function returns a promise that resolves after any pending updates have been applied to the DOM. Await tick after changing state when you need to measure or read freshly updated DOM.

<script>
  import { tick } from 'svelte';

  let count = 0;

  async function showSnap() {
    count += 1;                       // update is scheduled, not yet applied
    await tick();                     // resolves once the DOM has been updated
    console.log(document.body.innerText.includes('count: 1'));   // true here
    count += 1;                       // a second update flushed independently
  }
</script>

<button on:click={showSnap}>increment</button>
<p>count: {count}</p>

Svelte batches updates and flushes them asynchronously. await tick() pauses until the current batch has been applied, so you can safely read the freshly updated DOM.

6.4 Actions & the use: directive

This section wraps third-party widgets and DOM behaviour in reusable actions using the use directive. An action receives the element it is attached to and may return destroy and update functions. Actions are the clean way to integrate non-Svelte libraries with a component.

<script>
  function tooltip(node, text) {
    // node: the element the action is applied to
    const show = () => node.setAttribute('title', text);
    const hide = () => node.removeAttribute('title');
    node.addEventListener('mouseenter', show);
    node.addEventListener('mouseleave', hide);

    return {
      update(next) { text = next; },        // called when the argument changes
      destroy() {                           // called when the node unmounts
        node.removeEventListener('mouseenter', show);
        node.removeEventListener('mouseleave', hide);
      },
    };
  }
</script>

<button use:tooltip={'save your work'}>Save</button>

An action is a function that receives its element. Returning destroy handles teardown and update reacts to new argument values — the idiomatic way to attach widgets and listeners.

7 · Transitions, Animations & Motion

7.1 Built-in transitions: fade & slide7.2 in:, out:, custom transitions & easing7.3 animate:flip for reordered lists7.4 Motion stores: tweened & spring7.5 Respecting prefers-reduced-motion

This chapter adds life to interfaces with the transition directive, flip animations for reordered lists and physics-based motion stores. Ready-made effects come from svelte/transition and easing from svelte/easing. Every feature respects reduced-motion preferences so interfaces stay accessible.

7.1 Built-in transitions: fade & slide

This section applies the transition directive with ready-made effects such as fade and slide imported from svelte/transition. You add the directive to an element and the effect plays when it mounts and unmounts. Options like duration and delay tune how the motion behaves.

<script>
  import { fade, slide } from 'svelte/transition';
  let shown = true;
</script>

<button on:click={() => shown = !shown}>toggle</button>

{#if shown}
  <p transition:fade>I fade in and out</p>
  <p transition:slide>I slide while fading</p>
  <p transition:scale={{ start: 0.5, opacity: 0 }}>parameterised</p>
{/if}

transition:name animates an element both in and out. The animations come from svelte/transition, and options in braces such as transition:scale={{ start: 0.5 }} tune them.

7.2 in:, out:, custom transitions & easing

This section sets separate enter and exit animations using the in and out directives, or writes a fully custom transition function. A custom transition receives the node and parameters and returns a promise or a callback for completion. Easing functions from svelte/easing shape how fast the motion travels.

<script>
  import { fly, fade } from 'svelte/transition';
  import { expoOut } from 'svelte/easing';
  let open = false;
</script>

<button on:click={() => open = !open}>open drawer</button>

{#if open}
  <div
    in:fly={{ y: 40, opacity: 0, duration: 400, easing: expoOut }}
    out:fade
  >drawer body</div>
{/if}

in: and out: set distinct enter and exit animations. Custom parameters plus an easing like expoOut give the motion its character — they shape the speed curve, not just the duration.

7.3 animate:flip for reordered lists

This section animates elements to their new position when a keyed list reorders using the animate directive with the flip function. FLIP measures start and end positions and eases the difference, so rows glide into place instead of jumping. The each block must be keyed for this to work.

<script>
  import { flip } from 'svelte/animate';

  let words = ['compile', 'bundle', 'ship'];

  function shuffle() {
    words = [...words].reverse();   // reassign; flip animates the movement
  }
</script>

{#each words as word (word)}
  <p animate:flip>{word}</p>
{/each}
<button on:click={shuffle}>reverse</button>

animate:flip measures where each keyed element starts and ends and animates the difference, so reversing the list slides items smoothly instead of teleporting them.

7.4 Motion stores: tweened & spring

This section animates values themselves instead of elements using tweened and spring from svelte/motion. tweened glides toward a target over a fixed duration, while spring chases it with physics so it settles and bounces naturally. Both are stores, so you read them with the dollar prefix.

<script>
  import { tweened } from 'svelte/motion';
  import { spring } from 'svelte/motion';
  import { quartOut } from 'svelte/easing';

  let progress = tweened(0, { duration: 900, easing: quartOut });  // timed glide
  let size = spring(10, { stiffness: 0.15, damping: 0.9 });       // physical chase
</script>

<button on:click={() => progress.set(100)}>run progress</button>
<div class="bar" style="width: {$progress}px"></div>

<button on:click={() => size.set(80)}>grow</button>
<div class="dot" style="width: {$size}px; height: {$size}px"></div>

tweened interpolates between values over a set duration, while spring tracks velocity and behaves like physics. Setting a new value on either animates from the current value.

7.5 Respecting prefers-reduced-motion

This section gates animations behind the operating system’s motion preference. The prefersReducedMotion store exposes the CSS media query reactively, and you can subscribe to it to disable transitions for users who opt out of motion. Reading it in components keeps motion respectful.

<script>
  import { prefersReducedMotion } from 'svelte/motion';
  import { fly } from 'svelte/transition';
</script>

{#if !$prefersReducedMotion}
  <p transition:fly={{ y: 30 }}>slides when motion is allowed</p>
{:else}
  <p>appears instantly when motion is reduced</p>
{/if}

prefersReducedMotion is a readable store reflecting the system motion preference. Reading it inline with $ and dropping transitions keeps the UI comfortable for every user.

8 · Slots, Composition & Special Elements

8.1 Slots & slot props8.2 svelte:fragment & recursive components8.3 svelte:component8.4 svelte:window, svelte:document & svelte:head8.5 svelte:element

This chapter composes interfaces with slots and the special svelte elements. These let components accept caller-provided content, recurse over their own structure, and reach into the window, document and head. Together they cover the escape hatches that go beyond ordinary markup.

8.1 Slots & slot props

This section accepts caller-provided content with a default slot, named slots and fallback content. Slot props pass values from the component back up to the content that fills the slot. This is the primary tool for building layout and wrapper components.

// Panel.svelte — a wrapper with named and fallback content
<div class="panel">
  <header><slot name="title">Untitled</slot></header>
  <div class="body"><slot></slot></div>
</div>

// App.svelte
<script>
  import Panel from './Panel.svelte';
</script>

<Panel>
  <span slot="title">Settings</span>    // fills the named slot
  <p>Your preferences live here.</p>     // fills the default slot
</Panel>

The default slot renders whatever sits between the component tags, while slot="title" targets a named slot. When the caller provides nothing, the fallback content (Untitled) shows.

// Item.svelte — hand data back to the caller's fill
<script>
  export let item = { name: 'ada' };
</script>

<div>
  <slot label={item.name} count={1}></slot>
</div>

// App.svelte
<script>
  import Item from './Item.svelte';
</script>

<Item let:label let:count>
  <p>{label} ({count})</p>    // label and count arrive from the child
</Item>

Slot props let a child pass values up into the content that fills the slot. let:label in the caller binds that exported value so the fill can render it.

8.2 svelte:fragment & recursive components

This section uses svelte:fragment to wrap content for a slot without adding an extra DOM element, and recursive components that render themselves. Together they power trees, menus and other structures of any depth. The fragment itself is invisible in the resulting markup.

// TreeNode.svelte — recursion via a self-import
<script>
  import TreeNode from './TreeNode.svelte';
  export let node;
</script>

<div class="node">{node.name}</div>
{#if node.children && node.children.length}
  <div class="children">
    {#each node.children as child (child.id)}
      <TreeNode node={child} />   // render one level deeper
    {/each}
  </div>
{/if}

// App.svelte — a loop inside a slot needs grouping; svelte:fragment provides it
<script>
  import Select from './Select.svelte';
  let list = ['uncooked', 'boiling', 'ready'];
</script>

<Select>
  <svelte:fragment>                  // groups without rendering a real element
    {#each list as item}
      <button>{item}</button>
    {/each}
  </svelte:fragment>
</Select>

Importing its own file lets a component render itself, giving you recursion for trees. svelte:fragment groups slot content without adding a DOM node, so loops can live inside slots cleanly.

8.3 svelte:component

This section renders whichever component its this value points to using svelte:component. Swapping the value unmounts the old component and mounts the new one, which makes it the tool for tabs and switchable views. You can also pass props through to the chosen component.

<script>
  import Home from './Home.svelte';
  import About from './About.svelte';
  import Contact from './Contact.svelte';

  const pages = { home: Home, about: About, contact: Contact };
  let current = 'home';

  $: active = pages[current];   // a component constructor in a variable
</script>

{#each Object.keys(pages) as name}
  <button on:click={() => current = name}>{name}</button>
{/each}

<svelte:component this={active} />   // swap which component renders

svelte:component renders whatever component this points to. Changing the variable unmounts the old and mounts the new — a clean mechanism for tabbed and dynamic views.

8.4 svelte:window, svelte:document & svelte:head

This section attaches listeners and document tags declaratively using svelte:window, svelte:document and svelte:head. The first two clean up their listeners automatically when the component unmounts, and svelte:head pushes content into the document head. This keeps browser ties explicit in markup.

<script>
  let y = 0;
  let title = 'My app';
  function onScroll() { y = window.scrollY; }
</script>

<svelte:window on:scroll={onScroll} on:keydown={onKey} />
<svelte:document title={title} />   // sets document.title
<svelte:head>
  <meta name="description" content="Set via svelte:head">
</svelte:head>

<p>scroll: {y}</p>

svelte:window and svelte:document bind events on the globals and remove them on unmount, and svelte:head injects tags into the document head — the idiomatic place for per-page metadata.

8.5 svelte:element

This section renders a dynamic tag name from a variable using svelte:element. One component can serve as any heading level or element while keeping its props simple. The tag name resolves at runtime via the this attribute, so you stay flexible without duplicating markup.

<script>
  export let level = 2;   // caller picks the heading level
</script>

<svelte:element this={'h' + level} class="title">
  My heading
</svelte:element>

svelte:element renders the tag named by this, letting one component serve as h1 through h6 (or any element) while attributes and event bindings stay intact.

9 · Context, CSS & Component Styling

9.1 Context: setContext & getContext9.2 Scoped styles & the :global escape9.3 The class: directive9.4 style: directives & CSS custom properties

This chapter covers context for deeper tree communication and the full styling toolkit: scoped CSS, the global escape, and the class and style directives. Styling stays scoped to components by default, and context lets you share values without prop drilling. Together they keep component trees self-contained and themable.

9.1 Context: setContext & getContext

This section passes values from a parent to any descendant without prop drilling using setContext and getContext. Symbol keys and exported helper functions keep context tidy across files. Context is scoped to the component tree, so different parts of the app can hold different values.

// accordion/context.js
import { setContext, getContext } from 'svelte';

const key = Symbol('accordion');   // symbol keys avoid naming collisions

export function setAccordion(api) {
  setContext(key, api);            // hand the API to this subtree
}

export function getAccordion() {
  return getContext(key);          // read it back at any depth
}

// accordion/Accordion.svelte
<script>
  import { setAccordion } from './context.js';
  setAccordion({ register, open, close });   // descendants call open etc.
</script>
<div class="accordion"><slot /></div>

A symbol as the context key prevents collisions between libraries. Exporting set/get helpers gives you an importable API so components at any depth can reach the value without prop drilling.

9.2 Scoped styles & the :global escape

This section explains that Svelte scopes component styles by default by hashing class names, and offers the global escape as a deliberate way to opt out. Scoped styles keep components self-contained so changes never leak outward. Reach for the global escape only when you truly need document-wide reach.

// Box.svelte
<div class="box">
  <p>I match the .box rule.</p>
</div>

<style>
  .box {                       // scoped: the compiler tags matching elements
    border: 1px solid teal;
    padding: 1rem;
  }

  :global(.highlight) {        // escapes scope: applies everywhere
    background: gold;
  }

  :global(body) { margin: 0 }  // document-level, used sparingly
</style>

Component styles are scoped by default: the compiler adds a class to each matching element, so .box here cannot leak. :global() opts out deliberately for shared utilities.

9.3 The class: directive

This section toggles a class on an element from any truthy expression using the class directive. The directive takes an object, a name with a condition, or a shorthand based on a boolean variable. It is the ergonomic replacement for building class strings by hand.

<script>
  let active = false;
  let prefersDark = true;
</script>

<button
  class="pill"
  class:active              // adds 'active' when the active variable is truthy
  class:dark={prefersDark}  // adds 'dark' from any expression
  on:click={() => active = !active}
>toggle pill</button>

class:name toggles that class based on a truthy expression. The bare class:active is shorthand for class:active={active}, and it merges with any static class attribute.

9.4 style: directives & CSS custom properties

This section sets individual CSS properties on an element with the style directive and passes theme values into children via CSS custom properties. Parents can set custom property values that cascade into child components. This is the sanctioned way to theme components without hacks.

// Chip.svelte — a themable component
<script>
  export let color = 'teal';
</script>

<span class="chip" style="--chip: {color}">   // exposes a CSS custom property
  <slot />
</span>

<style>
  .chip {
    background: var(--chip, #eee);   // falls back when --chip is absent
    padding: 0.25rem 0.75rem;
    border-radius: 999px;
  }
</style>

// App.svelte — the parent themes the child without touching its selectors
<script>
  import Chip from './Chip.svelte';
  let busy = true;
</script>

<Chip color="#e91e63">pink chip</Chip>
<Chip>default chip</Chip>
<p style:opacity={busy ? 0.5 : 1}>style: sets one property at a time</p>

Setting a custom property on the wrapper (--chip: {color}) and reading it with var() inside the component is how parents theme children. The style: directive sets a single CSS property directly on an element.

10 · Best Practices & Patterns

10.1 Component design10.2 Avoiding over-reactivity10.3 Performance: lazy loading & keyed lists10.4 Accessibility10.5 Testing with Vitest & Testing Library

This chapter applies everything from the guide: component design, measured reactivity, performance, accessibility and testing. These habits decide whether a project stays pleasant to maintain as it grows. Working through them turns knowledge into production discipline.

10.1 Component design

This section keeps components small and single purpose with explicit props and clear boundaries. Fewer props, clearer names and composition beat clever abstractions and premature flexibility. Design components around the data they receive and the events they emit.

// TodoRow.svelte — one job: render one todo item
<script>
  export let item;            // data in
  export let busy = false;    // UI state reflected in the row
</script>

<label>
  <input type="checkbox" checked={item.done} disabled={busy}>
  {item.text}
</label>

A focused component takes a small explicit prop surface and renders one thing. When a component accumulates many props or concerns, it is ready to be split.

10.2 Avoiding over-reactivity

This section shows how to avoid over-reactivity by keeping derived logic pure and guarding expensive side effects. Reactive statements re-run on every dependency change by default, so they should be used deliberately and kept cheap. Careful structuring keeps updates predictable.

<script>
  let query = '';
  let results = [];

  // guard the expensive side effect: only fetch when the query text changed
  let last = '';
  $: if (query !== last) {
    last = query;
    fetch('/search?q=' + encodeURIComponent(query))
      .then(r => r.json())
      .then(rows => (results = rows));
  }
</script>

<input bind:value={query} placeholder="search">
<ul>{#each results as r}<li>{r.title}</li>{/each}</ul>

Reactive statements fire on every dependency change. Guarding with a last-query check — or debouncing — stops expensive work such as fetch from running on every keystroke.

10.3 Performance: lazy loading & keyed lists

This section defers heavy components until they are needed with dynamic imports, and leans on keyed each blocks for stable, fast lists. Small habits here keep initial bundles and interactions fast. Profile first and only optimise the parts that actually cost.

<script>
  import { onMount } from 'svelte';
  let chart = null;

  onMount(async () => {
    const { default: Chart } = await import('./Chart.svelte');  // load on demand
    chart = Chart;
  });
</script>

<svelte:component this={chart} data={rows} />   // renders once the chunk arrives

Dynamically importing a heavy component defers its JavaScript until it is actually needed, shrinking the initial bundle. Combined with keyed each and reassignment-based updates, most pages stay lean.

Profile, then optimise. svelte-check, keyed lists, lazy imports and avoiding in-place mutation cover the vast majority of Svelte performance issues.

10.4 Accessibility

This section uses the accessibility warnings that svelte-check emits to build accessible components. Sound semantics start with real button elements, proper roles and meaningful labels instead of generic divs. Keyboard support and focus management follow the same checks.

<script>
  let open = false;
</script>

<button aria-expanded={open} on:click={() => open = !open}>
  Toggle menu
</button>

{#if open}
  <ul role="menu">
    <li role="menuitem" tabindex="0">Edit</li>
    <li role="menuitem" tabindex="0">Delete</li>
  </ul>
{/if}

<img src="logo.svg" alt="Acme logo">   // always provide alt text

Svelte’s a11y checks warn on unlabelled buttons and images. aria-expanded reveals menu state to screen readers, real buttons and roles make the menu operable, and alt text covers images.

10.5 Testing with Vitest & Testing Library

This section renders components and simulates real user interaction using Vitest and Testing Library. Tests assert what the user sees and does rather than how the component was built internally. Keeping tests close to behaviour means refactors do not break them.

// Counter.svelte — the subject under test
<script>
  export let start = 0;
  let count = start;
</script>
<button on:click={() => count += 1}>count is {count}</button>

// counter.test.js — Vitest + Testing Library
import { render, screen } from '@testing-library/svelte';
import userEvent from '@testing-library/user-event';
import Counter from './Counter.svelte';
import { it, expect } from 'vitest';

it('increments when a user clicks', async () => {
  render(Counter, { start: 5 });
  await userEvent.click(screen.getByRole('button'));
  expect(screen.getByText('count is 6')).toBeTruthy();
});

// add to package.json: "test": "vitest"

Vitest runs the test, Testing Library renders the component and simulates a real click with userEvent, and the assertion checks the visible DOM — testing behaviour, not implementation.

This section lists the special svelte elements that reach beyond ordinary markup, from svelte:component through svelte:window, svelte:head and svelte:fragment. Each one has a precise job such as dynamic tags, document access or invisible wrappers. This is the reference for escaping the box of a normal component.

A.5 Glossary

This section defines the terms used across the guide in plain language, from reactivity and stores to slots and special elements. Return here whenever a chapter name or concept stops making sense. The entries match the exact vocabulary used throughout the chapters.

  • Reactive statement — a $: labelled block that re-runs when its dependencies change.
  • Store contract — an object with a subscribe method; all stores, custom or built-in, satisfy it.
  • Rune — Svelte 5's compiler symbols ($state, $derived, $effect) for modern reactivity.
  • Action — a function applied with use: that receives the element and returns lifecycle hooks.
  • Slot / slot props — content injected from the parent; slot props hand values back up.
  • Scoped CSS / :global — styles confined to a component unless deliberately escaped.
  • FLIP — first-last-invert-play; the technique behind animate:flip position animation.
  • Transition / animation / motion — svelte/transition (in and out moves), svelte/animate (FLIP), svelte/motion (tweened and spring stores).
  • Keyed each — an {#each} with a key expression, keeping row identity stable through reorders.
