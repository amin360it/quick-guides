11 · Web Components

11.1 Custom elements: autonomous and customized built-ins11.2 Lifecycle callbacks11.3 Shadow DOM encapsulation, template and slot11.4 Styling and theming inside shadow trees11.5 When to reach for Web Components

Web Components are four browser standards that compose into reusable, encapsulated HTML elements: custom elements (define your own tag), shadow DOM (a private subtree for markup and styles), HTML templates (inert markup you can clone) and slots (author-provided content projected into that subtree). They are the platform-level answer to a component model, and because they are built into the engine they work identically in every framework — or with no framework at all.

11.1 Custom elements: autonomous and customized built-ins

A custom element is a class that extends HTMLElement and is registered under a tag name with customElements.define(). Once registered, the parser recognises the tag, constructs your class and upgrades existing instances. The registry is per-document (or per shadow root in the future scoped-registry proposal), so the same page can register the same name only once.

Autonomous elements

An autonomous custom element is a brand-new tag that extends HTMLElement directly. Its name must contain a hyphen, which is the mechanism that keeps the platform extensible: my-card, user-profile and app-shell are reserved for authors, while a hyphen-free name like card stays in the HTML namespace and cannot be defined. Registering an invalid name, an already-used name, or a class that does not extend HTMLElement throws a NotSupportedError or TypeError at that call.

Registration is global to the document. Calling define() a second time for the same name throws, which is why library authors guard with customElements.get() before defining and why two copies of a component bundle on one page conflict.

// JS — autonomous custom element
class UserCard extends HTMLElement {
  connectedCallback() {
    this.textContent = 'Hello from user-card';
  }
}
customElements.define('user-card', UserCard);
// markup: <user-card></user-card>

Customized built-in elements

A customized built-in extends a concrete interface such as HTMLButtonElement or HTMLAnchorElement and is used through a standard tag plus the is attribute: <button is="confirm-button">. The advantage is that the element keeps every native behaviour and accessibility contract of the tag it extends — an anchor still navigates, a button still submits — while adding your logic. The trade-off is support: Safari still does not ship customized built-ins, so in 2026 they remain the less portable of the two styles. Prefer autonomous elements for cross-browser components, and reserve is= for progressive enhancement where a native fallback is acceptable.

When the parser meets an unknown tag it creates an HTMLUnknownElement placeholder and, if a matching definition appears later, upgrades that node in place — running the constructor and lifecycle callbacks. This is why a component must work even if its definition loads late: the initial markup should already be readable before the class arrives.

11.2 Lifecycle callbacks

Custom elements expose a small, precise set of reactive hooks instead of a framework. You implement any subset, and the engine calls them at defined moments in the element's life: construction, insertion, removal, attribute change, and adoption into another document.

The five callbacks

constructor() runs when the element is created — by the parser, by document.createElement(), or by a clone. connectedCallback() runs each time the element is inserted into a document, and may fire more than once if the element is moved. disconnectedCallback() runs on removal. attributeChangedCallback(name, oldValue, newValue) runs for each attribute named in the static observedAttributes getter. adoptedCallback() runs when the element moves to a new document, such as through document.adoptNode().

Order and timing pitfalls

The constructor runs before attributes and children exist, so reading this.getAttribute() or this.children there is unreliable and rendering in the constructor can produce an empty component. The safe pattern is to build structure in the constructor but read attributes and children in connectedCallback(). For an upgraded element, the sequence is constructor, then one attributeChangedCallback per observed attribute, then connectedCallback. Also note that disconnectedCallback is not called when the tab is closed or the browser navigates away, so it is the wrong place for anything that must survive a save.

// JS — lifecycle and observed attributes
class LiveCounter extends HTMLElement {
  static get observedAttributes() { return ['step']; }
  constructor() {
    super();
    this.value = 0;
    this._bound = () => { this.value += Number(this.getAttribute('step') || 1); };
  }
  connectedCallback() {
    this.addEventListener('click', this._bound);
    this.render();
  }
  disconnectedCallback() {
    this.removeEventListener('click', this._bound);
  }
  attributeChangedCallback(name, oldValue, newValue) {
    if (name === 'step' && oldValue !== newValue) this.render();
  }
  render() { this.textContent = 'Count: ' + this.value; }
}
customElements.define('live-counter', LiveCounter);
Add and remove listeners symmetrically in connectedCallback / disconnectedCallback. An element can be connected, removed and reconnected, so every connect must be idempotent — re-adding the same handler twice is a classic duplicate-fire bug.

11.3 Shadow DOM encapsulation, template and slot

Shadow DOM attaches a private, parallel tree to an element. Styles declared inside do not escape into the page, page styles do not reach in, and document.querySelector() does not see the internal nodes. Templates and slots are the building blocks that make that tree declarative and composable.

attachShadow, modes and the host

The element that owns a shadow root is the host, matched inside the tree by :host. attachShadow({ mode: 'open' }) exposes the root through element.shadowRoot, so page scripts can reach in; mode: 'closed' hides it and returns null. Closed mode is weak protection — it stops casual inspection, not determined code — so treat it as an API design choice, not a security boundary. An element can only have one shadow root, and attachShadow throws if the element is an unsupported host such as <a>.

Templates and slots

A <template> holds inert markup: its contents are parsed but never rendered and its scripts and images never run or load until cloned. The content lives in a DocumentFragment at template.content. Cloning it with cloneNode(true) into a shadow root is the canonical declarative pattern, and it lets the browser parse the markup once and stamp out as many instances as needed.

Slots project author-supplied light-DOM children into the shadow tree. A default (unnamed) <slot> receives all children without a matching slot attribute; named slots receive children whose slot attribute matches. Content between the slot tags is fallback, shown only when nothing is assigned. The slotchange event fires on the slot when its assigned nodes change, and slot.assignedElements() gives you the projected elements.

<!-- HTML — a template cloned into every instance -->
<template id="info-card-tpl">
  <style>
    article { padding: 1rem; border: 1px solid #ccd; border-radius: 8px; }
    ::slotted(h3) { margin: 0 0 .5rem; font-size: 1.1rem; }
  </style>
  <article>
    <slot name="heading">Default heading</slot>
    <slot></slot>
  </article>
</template>

<info-card>
  <h3 slot="heading">Deploy</h3>
  <p>Ship the build to production.</p>
</info-card>

<script>
  class InfoCard extends HTMLElement {
    constructor() {
      super();
      const tpl = document.getElementById('info-card-tpl');
      this.attachShadow({ mode: 'open' })
        .appendChild(tpl.content.cloneNode(true));
    }
  }
  customElements.define('info-card', InfoCard);
</script>
Because a slot renders the light-DOM child itself, not a copy, styling from the page still applies to slotted content and the node's id, focus and event handlers are the page's. The shadow tree only controls where it appears.

11.4 Styling and theming inside shadow trees

Shadow encapsulation changes the rules for CSS. Selectors from the page cannot reach in, so a design system must expose deliberate extension points. Three mechanisms do this: inherited properties and custom properties, the ::part() pseudo-element, and ::slotted().

What crosses the boundary

Inherited CSS properties — color, font-family, font-size, line-height, letter-spacing — pass through the host to the shadow content, and CSS custom properties (variables) are inherited properties too. That makes theming straightforward: the host reads var(--card-accent, #0b5fbf) and the page sets --card-accent on the element or any ancestor. Everything else, from background to margin, must be decided inside the component or exposed through a part.

::part, ::slotted and adopted stylesheets

The component author marks an internal element with part="label"; the page then styles it with my-card::part(label) { … }. ::part is the sanctioned escape hatch and can be re-exported through exportparts. ::slotted(selector) styles light-DOM content from inside the shadow tree, but only simple selectors and only the top-level assigned nodes. For performance, a constructable CSSStyleSheet can be built once and attached to many shadow roots with adoptedStyleSheets, avoiding one parsed style element per instance.

/* CSS — theming a component from the page */
my-card {
  --card-accent: #00d1ff;      /* inherited custom property */
  color: #0b1f3a;              /* inherited property */
}
my-card::part(label) { font-weight: 700; letter-spacing: .02em; }

/* JS — one stylesheet adopted by every instance */
const sheet = new CSSStyleSheet();
sheet.replaceSync(':host{display:block} .inner{padding:1rem}');
class FastCard extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.adoptedStyleSheets = [sheet];
  }
}
customElements.define('fast-card', FastCard);
::slotted() cannot target descendants of the slotted node, and its specificity is limited. If you need to style something a slot receives, style it in the page stylesheet — the slotted node belongs to the page, not the shadow tree.

11.5 When to reach for Web Components

Web Components are a platform primitive, not a complete application architecture. They replace the element layer of a framework and nothing else — no reactivity model, no state management, no templating language, no routing. The question is whether the boundary you need is a DOM boundary.

Good fits

They shine as leaf widgets and design-system primitives that must survive a framework change: a date picker, a colour swatch, a data grid, a chat launcher, an auth widget embedded into someone else's page. Because they are real elements, host pages can style them with CSS, drop them into any template engine, and script them with plain DOM. Libraries such as Lit and FAST wrap the standards with a declarative template layer, and a design system built as custom elements can be consumed by React, Vue, Angular, Svelte and plain HTML at once.

The costs to weigh

Integration is not free. React historically passed props as attributes and events needed manual wiring, so wrappers or the newer custom-element support in React 19 are required. Server rendering needs Declarative Shadow DOM (<template shadowrootmode="open">) to avoid a flash of unstyled content, and hydration must reattach without re-rendering. Form participation requires ElementInternals and formAssociated = true rather than a plain input. Accessibility is your responsibility: shadow boundaries hide internals from tooling that walks the light DOM, so roles, labels and focus management must be authored deliberately. If your app is a single framework and stays one, a framework component model is usually less work.

Decision rule. Choose Web Components when the component must outlive a framework, ship to third parties, or be consumed by more than one stack. Otherwise prefer your framework's components and treat the standards as a migration target, not a default.

12 · The Constraint Validation API and advanced forms

12.1 Validity states and the Constraint Validation API12.2 setCustomValidity and novalidate12.3 FormData and the FormData event12.4 Autofill, autocomplete, inputmode and enterkeyhint12.5 Input types, datalist and accessible error messaging

Native HTML forms validate without a line of JavaScript: required, type="email", pattern, min, max and maxlength establish constraints, and the browser blocks submission and shows a message when they fail. The Constraint Validation API exposes that machinery so you can read the exact reason a field is invalid, supply your own message, and integrate it with accessible error UI.

12.1 Validity states and the Constraint Validation API

Every form control implements the same interface. The validity property returns a live ValidityState object whose boolean fields each describe one kind of failure, and validationMessage holds the localised string the browser would display. This is the difference between "this is wrong" and "this is wrong because the value is empty".

The ValidityState booleans

valueMissing is true when a required control is empty. typeMismatch covers a malformed email or url. patternMismatch, tooLong and tooShort map to pattern, maxlength and minlength (the latter only counts user-edited values). rangeUnderflow, rangeOverflow and stepMismatch map to min, max and step. badInput means the browser could not parse what was typed, for example letters in a number field that already had a valid value. customError is set only by setCustomValidity(), and valid is true when all the others are false. A control also has willValidate (false when disabled, readonly, or not a candidate) and a form reference.

checkValidity and reportValidity

checkValidity() returns a boolean and fires a cancelable invalid event on each failing control; reportValidity() does the same and then shows the browser's message. Calling either on a <form> checks the whole form, and on a fieldset it checks that subset. Use checkValidity() for silent checks and reportValidity() when you want the native bubble — for instance after a custom submit button validates a step.

// JS — reading specific validity states
const field = document.querySelector('#email');
field.addEventListener('input', () => {
  const v = field.validity;
  if (v.valueMissing) console.log('Please enter your email.');
  else if (v.typeMismatch) console.log('That does not look like an email.');
  else if (v.valid) console.log('OK');
  console.log('native message:', field.validationMessage);
});
document.querySelector('#signup').addEventListener('invalid', (e) => {
  e.target.classList.add('has-error'); // fires on each invalid control
}, true); // capture, because invalid does not bubble
The invalid event does not bubble, so listen for it on the form in the capture phase. That single listener is the hook for wiring your own error UI instead of the native bubble.

12.2 setCustomValidity and novalidate

Native rules cannot express every constraint — matching passwords, a value that depends on another field, or a cross-field rule. setCustomValidity() adds your own failure to the control's validity, and novalidate hands validation entirely to your code.

setCustomValidity

Pass a non-empty string and the control becomes invalid with that string as validationMessage and customError set to true; pass an empty string to clear it. The message is what the browser shows, so write it for a human. Because the custom error is sticky, every path that can make the field valid again must call setCustomValidity('') — a field that stays permanently invalid after one mistake is the single most common bug with this API. Recompute the message on the events that affect it: the field's own input, and input on any field it depends on.

novalidate and non-blocking validation

Adding novalidate to the form (or formnovalidate to a submit button, useful for a "Save draft" action) stops the browser from blocking submission automatically. You then call reportValidity() yourself when you want to reveal errors. This is the standard pattern for multi-step forms and for validating on blur rather than only on submit: keep novalidate, validate a step with checkValidity(), surface your own messages, and only let the final submit reach the server when everything passes. The CSS pseudo-classes :valid, :invalid, :user-invalid and :user-valid let you style state; prefer :user-invalid so fields are not marked red before the user has touched them.

// JS — cross-field validation with a custom message
const pw = document.querySelector('#password');
const confirmPw = document.querySelector('#confirm');
function checkMatch() {
  confirmPw.setCustomValidity(
    confirmPw.value && confirmPw.value !== pw.value
      ? 'Passwords do not match.'
      : ''            // clear it, or the field stays invalid forever
  );
}
pw.addEventListener('input', checkMatch);
confirmPw.addEventListener('input', checkMatch);
Never use setCustomValidity() to mark a field valid when you are unsure — call it with '' only. A leftover non-empty string silently blocks the form even though the value is fine.

12.3 FormData and the FormData event

FormData is the platform's representation of a form's successful controls: the same set of name/value pairs the browser would have submitted. It is both a way to read a form in JavaScript and a ready-made body for fetch().

Building and reading FormData

new FormData(formElement) collects every submittable control — it skips controls without a name, skips disabled controls, includes only checked checkboxes and only the selected radio, and represents a file input as a File. Passing a second argument, the SubmitEvent.submitter, correctly accounts for the clicked button's name and value. The interface is map-like: append adds a value allowing duplicates (multiple files under one name), set replaces all values for a key, and get, getAll, has, delete and entries work as expected. To send JSON instead, use Object.fromEntries(formData) — but know that it flattens duplicates and loses files.

The formdata event

Just before a form is submitted, the browser constructs the entry list and fires a formdata event on the form whose formData property is the live FormData. A listener can append() server-only fields such as a CSRF token or timestamp without polluting the visible markup. The same list is used for both the native submit and any new FormData(form) call, so a single listener covers both paths. Combining this with event.preventDefault() in submit gives you a fully scripted, progressively-enhanced form.

// JS — add a field, then POST the whole form as multipart data
const form = document.querySelector('#signup');
form.addEventListener('formdata', (event) => {
  event.formData.append('submittedAt', new Date().toISOString());
});
form.addEventListener('submit', async (event) => {
  event.preventDefault();
  const body = new FormData(form, event.submitter);
  const res = await fetch('/api/signup', { method: 'POST', body });
  if (!res.ok) console.error('Signup failed', res.status);
});

12.4 Autofill, autocomplete, inputmode and enterkeyhint

Three attributes shape how the keyboard and password managers treat a field. autocomplete describes what the value is so browsers can fill it; inputmode describes which on-screen keyboard to show; enterkeyhint labels the virtual Enter key. Getting these right has an outsized effect on mobile completion rates.

The autocomplete token grammar

An autocomplete value is a field name optionally preceded by a grouping (shipping, billing), a contact type (home, work, mobile, fax, pager) and an optional section-* prefix to separate repeated groups. Field names cover names (given-name, family-name, name), contact (email, tel, tel-national), address (street-address, address-level2 for city, postal-code, country), payment (cc-number, cc-exp, cc-csc) and credentials (username, current-password, new-password, one-time-code). Using the exact token is what lets a password manager offer the right suggestion; the generic value on tells the browser to guess, and off is widely ignored for login fields because browsers prioritise their own heuristics.

inputmode and enterkeyhint

inputmode selects the keyboard without changing validation: numeric for digits, decimal when a separator is allowed, tel for phone keypads, email for the @ key, url for a slash bar, search and text otherwise. A common mistake is using type="number" to get a numeric keypad for values that are not numbers — ZIP codes, card numbers and phone numbers are strings and may contain leading zeros or plus signs, so use type="text" with inputmode="numeric". enterkeyhint accepts enter, done, go, next, previous, search and send, and should match what the form does next.

<!-- HTML — autofill tokens plus the right mobile keyboards -->
<input name="name" autocomplete="name">
<input name="email" type="email" autocomplete="email" inputmode="email">
<input name="zip" autocomplete="postal-code" inputmode="numeric"
       pattern="[0-9]{5}(-[0-9]{4})?">
<input name="card" type="text" autocomplete="cc-number"
       inputmode="numeric" enterkeyhint="next">
<input name="search" type="search" enterkeyhint="search">
<input name="code" autocomplete="one-time-code" inputmode="numeric">
Keep the visual label, the autocomplete token and the name attribute semantically aligned. When they disagree, browsers trust autocomplete first and users get cards filled into the wrong field.

12.5 Input types, datalist and accessible error messaging

HTML5 shipped a family of input types that give you native pickers and validation for free, plus <datalist> for suggestions. The remaining work is telling assistive-technology users why a field failed, because native validation bubbles are neither persistent nor screen-reader friendly on every platform.

The input types in depth

email and url validate format and may use a specialised keyboard. tel shows a phone keypad but validates nothing — it accepts any text, so pair it with a pattern. The temporal types date, time, datetime-local, month and week provide date pickers with well-defined value formats (YYYY-MM-DD, HH:MM) and support min, max and step. number gives spinners and range checks but should only be used for genuine quantities; range renders a slider, color a colour picker, file a file chooser whose accept hints at types, and search a text field with a clear button. datalist attaches an autocomplete list to an input: it suggests but does not restrict, values are still free text, and its rendering varies between browsers, so it is a convenience, not a constraint. If you must restrict to a list, use <select> or validate the value yourself.

Accessible error messaging

The native bubble disappears on blur and is not reliably announced, so production forms render their own error text and connect it with ARIA. Set aria-invalid="true" on the failing control and point aria-describedby at the element containing the message, so a screen reader reads it when focus lands on the field. Give the message container role="alert" or wrap it in an aria-live="polite" region so it is announced when it appears. Never signal an error with colour alone — add text and, ideally, an icon with a text alternative. Tie the message to the field's id deterministically, keep it in the DOM from the start when you can, and move focus to the first invalid field after a failed submit.

<!-- HTML — datalist plus a wired error message -->
<label for="city">City</label>
<input id="city" name="city" list="cities" required
       autocomplete="address-level2"
       aria-describedby="city-error" aria-invalid="false">
<datalist id="cities">
  <option value="Berlin"></option>
  <option value="Lisbon"></option>
  <option value="Osaka"></option>
</datalist>
<p id="city-error" role="alert" hidden>Enter a city from the list.</p>

<script>
  const city = document.getElementById('city');
  const err = document.getElementById('city-error');
  city.addEventListener('blur', () => {
    const bad = !city.checkValidity();
    city.setAttribute('aria-invalid', String(bad));
    err.hidden = !bad;
    if (bad) city.setCustomValidity('Enter a city from the list.');
    else city.setCustomValidity('');
  });
</script>
Validation runs on user input by default only after the value changes; styling with :user-invalid avoids flagging fields the user has never touched. Pair it with aria-invalid kept in sync in your own code, since the two are independent.

13 · Canvas, SVG and embedded graphics

13.1 canvas 2D context fundamentals13.2 Responsive canvas and devicePixelRatio13.3 SVG inline vs img vs object13.4 Choosing SVG, canvas or CSS — picture and source revisited13.5 dialog and details interactive elements

The browser offers three ways to draw: canvas (a bitmap you paint with JavaScript), SVG (vector shapes that are real DOM nodes), and CSS (gradients, shapes, masks and transforms on ordinary elements). Each has a different cost model, accessibility story and resolution behaviour. Choosing correctly is mostly about whether the artwork is data-driven and whether it should stay crisp at any size.

13.1 canvas 2D context fundamentals

A <canvas> is a fixed-size bitmap with an imperative drawing API. You get a context with getContext('2d') and then issue commands — fill, stroke, path, text, image. Nothing is retained as objects: once a shape is drawn it is pixels, and the only way to change it is to clear and redraw.

The drawing model and state

The coordinate system starts at the top-left, x increasing right and y increasing down, measured in CSS pixels before any transform. The context carries state — fill and stroke styles, line width, the transform matrix, the current clip — and save() pushes it onto a stack while restore() pops it. Always bracket a temporary change (a translation for a chart origin, a rotation for a label) with save and restore, or the change leaks into everything drawn afterwards. Paths are built with beginPath(), moveTo(), lineTo(), arc(), bezierCurveTo() and closePath(), then either fill() or stroke() renders them.

Text, images and accessibility

fillText() and strokeText() draw strings at a point with the context's font, while measureText() returns a width you can use to lay out labels. Images are drawn with drawImage(), which can take a source <img>, another canvas or a VideoFrame. Because canvas output is opaque pixels, it is invisible to search engines, text selection and screen readers; supply fallback content between the tags and an alternative such as a data table or a description, and give the element a role and label when it conveys information.

// JS — 2D context basics with save/restore
const canvas = document.querySelector('#chart');
const ctx = canvas.getContext('2d');
ctx.save();                        // push the current state
ctx.translate(40, 40);             // move the origin for the plot
ctx.fillStyle = '#0b5fbf';
ctx.fillRect(0, 0, 120, 60);
ctx.strokeStyle = '#021336';
ctx.lineWidth = 2;
ctx.beginPath();
ctx.moveTo(0, 80);
ctx.lineTo(120, 80);
ctx.stroke();
ctx.restore();                     // pop back to the previous state
ctx.fillText('Sales', 8, 16);
Prefer the DOM for interactive hotspots. Hit-testing a canvas means doing the coordinate maths yourself; an SVG or an absolutely-positioned overlay gets hover, focus and click for free.

13.2 Responsive canvas and devicePixelRatio

Canvas has two sizes that are easy to confuse. The width and height attributes set the backing store in device pixels; CSS width and height set the displayed size. If the two do not match the device pixel ratio, the browser scales the bitmap and the result looks blurry — the most common canvas complaint.

The CSS-size versus backing-store problem

On a 2× display, a canvas with a 300-pixel backing store shown at 300 CSS pixels is rendered from half the available detail and looks soft. The fix is to size the backing store to cssSize × devicePixelRatio and then scale the drawing context by the same factor so your drawing code can stay in CSS pixels. After setting canvas.width or canvas.height the context is reset — its state and any clip are cleared — so set the transform after resizing, not before. Use setTransform(dpr, 0, 0, dpr, 0, 0) to scale, or scale(dpr, dpr) if the transform is currently identity.

Handling resize without blur or thrash

Resize handlers should re-read getBoundingClientRect(), recompute the backing store, reset the transform and redraw. Debounce or, better, drive it from a ResizeObserver so the canvas follows its container rather than the window. Also listen for changes to devicePixelRatio (a window moved between monitors, or a zoom change) — a matchMedia('(resolution: 1dppx)') listener is a common trick to detect that. Redrawing the whole scene on every resize frame is usually fine, but cache expensive off-screen work in an OffscreenCanvas or a second bitmap when it is not.

// JS — size the backing store to the device pixel ratio
function sizeCanvas(canvas) {
  const dpr = window.devicePixelRatio || 1;
  const rect = canvas.getBoundingClientRect();
  canvas.width = Math.round(rect.width * dpr);
  canvas.height = Math.round(rect.height * dpr);
  const ctx = canvas.getContext('2d');
  ctx.setTransform(dpr, 0, 0, dpr, 0, 0); // draw in CSS pixels again
  return ctx;
}
const canvas = document.querySelector('#scene');
const ctx = sizeCanvas(canvas);
new ResizeObserver(() => {
  ctx = sizeCanvas(canvas);
  draw(ctx);
}).observe(canvas.parentElement);
Setting canvas.width resets every context property, including the transform, fill style and clip. Any code that assumes state survives a resize will draw at the wrong place or scale — reapply state after every resize.

13.3 SVG inline vs img vs object

SVG is XML that describes vector shapes, and it can enter a page three ways: inlined in the HTML, referenced by <img>, or embedded with <object>. Each has different consequences for styling, scripting, caching and accessibility.

Inline, img and object compared

Inlined SVG is part of the document: its elements are selectable, styleable by page CSS, animatable, scriptable and able to inherit currentColor and fonts. That flexibility is why inline SVG is the default for icons and interactive diagrams — but it inflates the HTML, cannot be cached separately, and repeated icons duplicate their markup, which is where an SVG sprite with <use> helps. Referencing the same file from <img src="icon.svg"> keeps it cacheable and isolated: page CSS cannot reach inside and scripts never run, which makes it safe for user-supplied SVGs. <object data="chart.svg" type="image/svg+xml"> frames a separate document you can script through contentDocument, and it supports fallback content for browsers that cannot render SVG — but its cross-document access, sizing and print behaviour are fiddly, so it is rarely the first choice.

Accessibility and currentColor

Give every meaningful SVG a role="img" and an aria-label, or place a <title> as the first child for assistive technology. Decorative graphics should be hidden with aria-hidden="true" and no title, so they are not announced. Inline SVGs can use fill="currentColor" so an icon takes the colour of its surrounding text with no extra CSS, and viewBox makes the artwork scale to any container while preserveAspectRatio controls how it fits. Always include a viewBox; without one an inline SVG has no intrinsic coordinate system and scaling misbehaves.

<!-- inline: inherits colour and is scriptable -->
<svg viewBox="0 0 24 24" role="img" aria-label="Trending up">
  <path d="M3 17l6-6 4 4 8-8" fill="none" stroke="currentColor"
        stroke-width="2" stroke-linecap="round"/>
</svg>

<!-- img: isolated, cacheable, no scripting -->
<img src="logo.svg" alt="Acme Corp" width="120" height="32">

<!-- object: own document, supports fallback -->
<object data="chart.svg" type="image/svg+xml" aria-label="Sales by quarter">
  <img src="chart.png" alt="Sales by quarter">
</object>

13.4 Choosing SVG, canvas or CSS — picture and source revisited

The three graphics technologies overlap, so the decision is about the nature of the image and how many of them there are. Canvas scales to thousands of marks because it is one bitmap; SVG scales in complexity gracefully but not in count; CSS handles decoration and simple shapes with no markup at all.

A decision guide

Use SVG for logos, icons, charts with a modest number of elements, maps with interactivity and anything that must stay crisp at any zoom or be styled by CSS. Use canvas for image processing, pixel manipulation, WebGL-adjacent work, games, and visualisations with thousands of points redrawn every frame where DOM node overhead would dominate. Use CSS for gradients, rounded shapes, masks, transforms and animated decoration — a surprising amount of "graphic" is better as a styled element than as either vector or bitmap. A useful rule: if the picture has fewer than a few hundred discrete objects and users interact with individual ones, SVG wins; if it has tens of thousands of marks or is regenerated at animation speed, canvas wins.

picture and source revisited

<picture> is about choosing between images, not drawing them. It gives you two capabilities: format negotiation, where the first <source> whose type the browser supports wins, letting you offer AVIF or WebP with a JPEG fallback; and art direction, where each <source> carries a media query so a wide crop loads on desktop and a tall crop on mobile. The final <img> is required — it provides the alt, the sizing and the fallback. On that <img>, srcset with sizes handles density and width selection, and width/height prevent layout shift by reserving space before the bytes arrive.

<picture>
  <source type="image/avif"
          media="(min-width: 60rem)"
          srcset="hero-wide.avif 1x, hero-wide@2x.avif 2x">
  <source type="image/webp"
          srcset="hero.webp 1x, hero@2x.webp 2x">
  <img src="hero.jpg" srcset="hero.jpg 1x, hero@2x.jpg 2x"
       alt="Team planning a sprint on a whiteboard"
       width="1200" height="630" loading="lazy" decoding="async">
</picture>
Order matters in <picture>: the browser takes the first <source> that matches both the media query and the type. Put the newest format and the most specific media query first, and the broad fallback last.

13.5 dialog and details interactive elements

Two elements moved from "experimental" to everyday building blocks: <dialog> for modals and non-modal panels with a real top layer, and <details>/<summary> for disclosure widgets that need no JavaScript. Both sit alongside the graphics chapter because they are the interactive chrome around charts, galleries and embedded media.

dialog: show, showModal and the top layer

dialog.showModal() opens the dialog in the top layer, above all other content regardless of z-index, and automatically makes the rest of the page inert so focus cannot leave the dialog. show() opens it non-modally, without the backdrop or focus trap. The ::backdrop pseudo-element styles the overlay, and close(value) sets returnValue and fires a close event. A form inside a modal with method="dialog" closes the dialog on submit and passes the clicked button's value as the return value — the cleanest way to build confirmations. Pressing Esc closes it and fires a cancelable cancel event, so you can veto dismissal for unsaved changes. Give the dialog an accessible name with aria-labelledby pointing at its heading.

details and summary

<details> is a native disclosure widget: the first child, <summary>, is the always-visible label and the rest is revealed when the open attribute is present. No JavaScript is required, and the element is keyboard-operable and announced correctly by default. The toggle event fires when it opens or closes. Adding a name attribute groups several <details> so that opening one closes the others — an exclusive accordion. It is ideal for FAQs, "show password" toggles, and progressive disclosure of long content, and it degrades to expanded content if a stylesheet or script fails.

<!-- HTML — a modal confirm and an exclusive FAQ -->
<dialog id="confirm" aria-labelledby="confirm-title">
  <form method="dialog">
    <h2 id="confirm-title">Delete this item?</h2>
    <p>This cannot be undone.</p>
    <button value="cancel" formnovalidate>Cancel</button>
    <button value="ok">Delete</button>
  </form>
</dialog>

<details name="faq" open>
  <summary>How do I reset my password?</summary>
  <p>Use the link on the sign-in page.</p>
</details>
<details name="faq">
  <summary>Do you offer refunds?</summary>
  <p>Yes, within 30 days.</p>
</details>

<script>
  const dlg = document.getElementById('confirm');
  dlg.showModal();
  dlg.addEventListener('close', () => console.log(dlg.returnValue));
</script>
Because showModal() makes the background inert, you rarely need a focus trap library. Do place focus intentionally — add autofocus to the control you want focused on open, and return focus to the trigger when the dialog closes.

14 · Security and performance in markup

14.1 Content Security Policy via meta and headers14.2 Subresource Integrity, iframe sandbox and rel=noopener14.3 Resource hints: preload, prefetch, preconnect, dns-prefetch14.4 Lazy loading and fetchpriority14.5 Measuring INP and LCP

A large share of both security and speed is decided in the document head, before a single line of application code runs. Security headers and attributes constrain what third-party content may execute and how it may be embedded; resource hints and loading attributes decide when the browser fetches what. Both areas reward getting the markup right, because the browser acts on these signals immediately.

14.1 Content Security Policy via meta and headers

Content Security Policy is an allow-list the browser enforces for what a page may load and execute. It is the strongest single mitigation against cross-site scripting, because injected inline scripts simply will not run. A policy is a list of directives, each naming the sources permitted for one kind of resource.

Writing a policy

default-src is the fallback for resource types you do not name explicitly. script-src limits JavaScript, and 'self' allows same-origin files; 'nonce-<random>' allows only a specific inline script tag that carries the matching nonce attribute, and 'sha256-…' allows a script whose contents hash to that value. style-src, img-src, font-src, connect-src, frame-src and object-src constrain those categories, and object-src 'none' plus base-uri 'self' close two classic bypasses. 'strict-dynamic' lets a nonce-approved script load further scripts, which is how modern bundlers work without listing every CDN. report-uri or the newer report-to sends violation reports so you can tune the policy before enforcing it.

meta versus header

The cleanest delivery is an HTTP response header, because headers cannot be injected by markup and they support every directive — including frame-ancestors, report-uri and sandbox, which <meta> cannot enforce. A <meta http-equiv="Content-Security-Policy"> is a fallback for static hosting where you cannot set headers; it must appear inside <head> before any resource it governs, it applies to exactly one policy, and directives that do not make sense in a meta context are ignored. Because a header policy and a meta policy are both enforced (with the intersection taking effect), shipping an unintended duplicate meta policy is a common way to break a site. Roll out with Content-Security-Policy-Report-Only, watch the reports, then enforce.

<!-- HTML — meta fallback; prefer an HTTP header when you can -->
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self';
               script-src 'self' 'nonce-r4nd0m' 'strict-dynamic' https:;
               style-src 'self';
               img-src 'self' data: https://cdn.example.com;
               font-src 'self';
               connect-src 'self' https://api.example.com;
               object-src 'none';
               base-uri 'self'">

<!-- the matching nonce on an allowed inline script -->
<script nonce="r4nd0m">startApp();</script>
Do not weaken a policy to 'unsafe-inline' just to silence a violation. That re-enables the exact vector CSP defends against. Use a nonce or a hash instead — a strict script policy is the whole point.

14.2 Subresource Integrity, iframe sandbox and rel=noopener

Three attributes secure content you do not control: Subresource Integrity pins the exact bytes of a third-party script or stylesheet, the sandbox attribute removes capabilities from an iframe, and rel="noopener" severs the link between a page and the document it opens.

Subresource Integrity

An integrity attribute holds a cryptographic hash — the recommended algorithm is SHA-384 — computed over the resource, base64-encoded and prefixed with the algorithm. If the served file does not match, the browser refuses to execute or apply it, which defeats a compromised CDN or a tampered build. SRI only works with CORS: cross-origin resources must be requested with crossorigin="anonymous" and the server must send an Access-Control-Allow-Origin response, or the hash cannot be verified and the resource is blocked. Generate hashes at build time and never hand-edit them, because a whitespace change invalidates the hash and breaks the page.

iframe sandbox, allow and noopener

An iframe without a sandbox attribute runs with the full privileges its origin allows, including forms, scripts, popups and top-level navigation. Adding sandbox with no value strips everything, then you re-grant the minimum you need with tokens: allow-scripts, allow-forms, allow-popups, allow-modals and so on. Never combine allow-scripts with allow-same-origin for untrusted content — together they let the frame remove its own sandbox. The allow attribute grants specific features such as geolocation or clipboard-write. For links, target="_blank" once let the opened page access window.opener and redirect the original; modern browsers imply noopener, but state rel="noopener noreferrer" explicitly, which also stops the referrer leaking.

<!-- SRI: pin the exact bytes, requested with CORS -->
<script src="https://cdn.example.com/lib.min.js"
        integrity="sha384-6b1cQ0n2Yt9dK3sV1p8oRq7xLmZf4wHcJkY2uN5aB8eFgHiJlMnOpQrStUvWxYz0"
        crossorigin="anonymous" defer></script>

<!-- iframe: strip capabilities, then re-grant the minimum -->
<iframe src="https://widget.example.com/embed"
        sandbox="allow-scripts allow-forms"
        allow="clipboard-write; fullscreen"
        referrerpolicy="no-referrer"
        loading="lazy"
        title="Embedded payment form"></iframe>

<a href="https://external.example.com" target="_blank"
   rel="noopener noreferrer">Read more</a>

14.3 Resource hints: preload, prefetch, preconnect, dns-prefetch

Resource hints tell the browser about requests the parser has not discovered yet. They do not load anything by themselves in every case, but they start connection or fetch work earlier than the normal discovery order would. Used carelessly they compete with critical resources and make the page slower.

Which hint to use when

dns-prefetch resolves a hostname ahead of time and is cheap; use it for origins you will connect to later but not immediately, and where a full connection would be wasteful. preconnect goes further, performing the DNS lookup, TCP handshake and TLS negotiation, so the first real request saves the round trips; it is worth it for a handful of critical origins and carries a cost per connection, so do not list dozens. Add crossorigin when the destination is fetched in CORS mode (fonts, module scripts, fetch) so the preconnect is reused for the right connection pool. preload fetches a specific resource at high priority for the current navigation — fonts, the hero image, a critical script — and must match the eventual request exactly in as, type, and CORS mode or the browser downloads it twice and warns about an unused preload. modulepreload does the same for an ES module and its dependency graph. prefetch is for the next navigation and runs at low priority when the browser is idle, warming the cache for a likely route.

<!-- HTML — connection hints then specific fetches -->
<link rel="preconnect" href="https://fonts.example.com" crossorigin>
<link rel="dns-prefetch" href="https://analytics.example.com">
<link rel="preload" href="/fonts/inter-latin.woff2" as="font"
      type="font/woff2" crossorigin>
<link rel="preload" href="/hero.avif" as="image" fetchpriority="high">
<link rel="modulepreload" href="/app/main.js">
<link rel="prefetch" href="/pricing" as="document">
A preload that is never used is worse than no preload: it consumes bandwidth at the highest priority and shows a console warning. Only preload what the first paint actually needs, and verify the preloaded request is the one the page later makes.

14.4 Lazy loading and fetchpriority

Loading attributes control when the browser fetches an image or iframe and how high a priority it assigns. The two goals pull in opposite directions: defer everything that is not visible now, while making the largest visible element arrive as early as possible.

loading, decoding and reserved space

loading="lazy" tells the browser to defer an image or iframe until it is near the viewport, saving bandwidth on long pages. Never put it on the largest contentful paint image at the top of the page — lazy loading there delays exactly the element that defines your LCP. decoding="async" lets the browser decode off the main thread and paint sooner, which is safe for images that are not immediately required for layout. Crucially, always provide width and height (or an aspect-ratio in CSS) so the browser reserves space and the page does not shift as images arrive; intrinsic sizing is the cheapest fix for cumulative layout shift. For long, complex sections, content-visibility: auto skips rendering work off-screen, with contain-intrinsic-size supplying an estimate so scrollbars stay stable.

fetchpriority

fetchpriority accepts high, low and auto and overrides the browser's heuristic priority for a resource. Mark the LCP image, and any hero font or critical script, high; mark carousel offcuts, decorative background images and below-fold content low. Use it sparingly and measurably — promoting everything to high is equivalent to promoting nothing, and can starve the render-blocking CSS and JS that actually gates first paint. Combine it with a correct preload only when the image is discovered late (for example generated by JavaScript); for a plain <img> in the initial HTML, fetchpriority="high" alone is usually enough.

<!-- above the fold: eager, high priority, sized to avoid shift -->
<img src="hero.avif" alt="Mountain sunrise over a lake"
     width="1600" height="900" fetchpriority="high" decoding="async">

<!-- below the fold: deferred, low priority -->
<img src="gallery-01.jpg" alt="" width="640" height="480"
     loading="lazy" decoding="async" fetchpriority="low">

<iframe src="https://video.example.com/embed/42"
        title="Product demo" loading="lazy" width="560" height="315"></iframe>

14.5 Measuring INP and LCP

Two Core Web Vitals dominate field measurement: Largest Contentful Paint (loading) and Interaction to Next Paint (responsiveness). Markup decisions move both, and the Performance APIs let you observe them on real devices rather than guessing from a lab run.

LCP: the largest element and when it settles

LCP reports the render time of the largest image, video poster or text block in the viewport. It keeps updating as bigger candidates appear, then stops when the user interacts or the page is hidden. The candidates are exposed through the largest-contentful-paint entry type, and each entry carries the element and url, so you can see exactly which asset is the bottleneck. A good LCP is under 2.5 seconds. To improve it in markup: serve the hero in a modern format at the right size, preload only if it is discovered late, add fetchpriority="high", avoid lazy loading it, and remove render-blocking stylesheets and fonts from the critical path.

INP: the slowest interaction

INP is derived from the latency between a user interaction and the next frame the browser paints, over the whole visit. The event PerformanceObserver entry type provides per-event timing, including interactionId for interactions, and a threshold typically filters out trivial events. The reported INP is close to the longest interaction, so one slow handler dominates. Shortening it usually means less main-thread work in event handlers: defer non-urgent updates, split long tasks, use the scheduler's yield pattern, and avoid layout thrash that forces synchronous reflow. Breakpoints matter — measure on representative mid-range phones, not a fast desktop, because the same handler that feels instant locally can be hundreds of milliseconds there.

// JS — observe LCP and interaction timing in the field
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  console.log('LCP', last.startTime.toFixed(0), 'ms', last.element);
}).observe({ type: 'largest-contentful-paint', buffered: true });

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.interactionId) {
      console.log('interaction', entry.name, entry.duration.toFixed(0), 'ms');
    }
  }
}).observe({ type: 'event', buffered: true, durationThreshold: 40 });
Measure in the field. Lab tools show one run on one machine; Core Web Vitals are defined on real-user data. Collect these entries, send them with navigator.sendBeacon() (or use the web-vitals library), and optimise the p75 — the value 75% of visits meet — rather than the average.
